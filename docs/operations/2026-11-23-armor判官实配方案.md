## 一、当前状态（2026-11-23 实测）

211 生产上 armor 判官**没有实配**，走的是占位判官：

```
docker logs <容器> | grep -i "armor judge"
WARN armor judge not configured, using mock judge (always safe)
     judge=mock(scores always 0 — judgments are noise)
     fix=set ARMOR_JUDGE_ENDPOINT + ARMOR_JUDGE_MODEL + ARMOR_JUDGE_API_KEY to score for real
```

落库形状（`armor_judgments` 表，2026-11-23 实测近 3 天）：

```
judge_model | score | decision | count
-----------+-------+----------+------
mock       | 0     | safe     | 49889      ← 全部是占位判官
```

★ **这就是本条遗留的真实危害**：占位判官的行与真实判官给出的「安全」
在表里**长得一样**（decision='safe'）⇒ 任何按 `decision='safe'` 统计
「安全通过率」的面，都会把「**根本没判过**」当成「判过且安全」。

## 二、本轮已修（观测口径）

1. **占位判官可辨识**：`armor.NewUnconfiguredJudge()` 取代 `NewMockJudge(0.0, "mock")`
   - `judge_model = 'unconfigured'`
   - `reason = "armor judge not configured — no verdict (not a safety pass)"`
   - 判定行为**不变**（分数恒 0、observe 模式永不拦截）
2. **递归防护已就位**：判官请求自带 `X-LLMGW-Armor-Judge: 1` 头，
   网关的 armor 路径见到它就**跳过判定**（判官不判自己）。

### ★ 统计口径（改完后的正确算法）

```sql
-- 真实安全判定（必须排除未配置判官）
SELECT decision, count(*)
FROM armor_judgments
WHERE judge_model <> 'unconfigured'
  AND created_at > now() - interval '1 day'
GROUP BY 1;

-- 未配置判官的量（= 判官缺配的规模，不是「安全」）
SELECT count(*)
FROM armor_judgments
WHERE judge_model = 'unconfigured'
  AND created_at > now() - interval '1 day';
```

## 三、实配方案（待 owner 决策后再开）

### 3.1 三个环境变量

| 变量 | 说明 | 备注 |
|------|------|------|
| `ARMOR_JUDGE_ENDPOINT` | OpenAI 兼容端点（到 `/v1` 为止，代码自己拼 `/chat/completions`） | 例如 `https://llm.itestu.cn/v1`（走网关自身）或某上游直连地址 |
| `ARMOR_JUDGE_MODEL` | 判官模型 | 宜选**便宜、快**的模型（Flash / mini 档） |
| `ARMOR_JUDGE_API_KEY` | 对应端点的 key | **不得进日志**（httpJudge 只打 endpoint/model，不打 key） |

注入点：`scripts/deploy-seamless-docker.sh` 的 `GW_ENV`（与 ASM/AutoLLM 同款
「部署机环境变量 > env 文件」的优先级块），**不要**手工改容器
（会被下次部署冲掉）。

### 3.2 递归防护（已实现，开判官即生效）

- `httpJudge` 给每次判官请求加 `X-LLMGW-Armor-Judge: 1`；
- 网关的 armor 判定路径见到该头 ⇒ 跳过判定。

⇒ **判官指向网关自身是安全的**（不会无限递归）。
★ 但注意：判官请求仍会占用一次**真实上游调用**（等于每个被判定的请求多一次
LLM 调用）。

### 3.3 成本与延迟（开之前必须认清）

- armor 判定在**每个已鉴权的 LLM 请求**上跑（`domains/streaming/handler.go`），
  211 实测未配置时也有 **≈16k 条/天** 的判定量 ⇒
  **实配 = 每请求 +1 次上游调用**（延迟 +5s 超时上限、成本按上游计）。
- 判官模型应选最便宜的一档；先用 `ARMOR_JUDGE_MODEL` 指向一个便宜的模型，
  观察几天再谈准确率。

### 3.4 上游选择的三条判据

1. **不指向会重试风暴的上游**：判官失败会写 WARN（每请求一条），
   上游不稳 ⇒ 日志与上游双重被打爆。
2. **有余额**：2026-11-22 实测 apiclaude/apichina 在 sonnet-5-5 上
   `INSUFFICIENT_BALANCE`、vapeur/速云U站 `permanently_exhausted`
   ⇒ 别选这些。
3. **优先复用已有凭据**：211 上 `LLMGatewayAutoLLMEndpoint`/`LLMGatewayAutoLLMModel`
   已在用（`https://llm.itestu.cn/v1` + `glm-5.3-flash`），
   说明这条链路的余额与延迟是可接受的 ⇒ **判官指向它是最省事的起点**。

### 3.5 开判官后的验收清单

- [ ] 启动日志出现 `armor judge initialized`（不再是 `not configured`）
- [ ] `armor_judgments` 里出现 `judge_model` = **真实模型名** 的行
- [ ] `judge_model='unconfigured'` 的行**不再增长**
- [ ] 判官延迟：`latency_ms` P99 在可接受范围（建议 < 2s）
- [ ] 无递归迹象：判官请求量 ≈ 被判定请求量（不是它的平方）
- [ ] 安全通过率口径已切到「排除 unconfigured」的查询
