## 二、逐项根因与修法

### 1. 时区（两个变量缺一不可）

**现象**：
```
settings: configured timezone invalid, falling back to default
  key: system.timezone  value: Asia/Shanghai
  error: unknown IANA timezone "Asia/Shanghai": unknown time zone Asia/Shanghai
settings: LoadLocation failed, falling back to default timezone
```

**根因（两层）**：
1. 容器镜像**完全没有 tzdata**——`/usr/share/zoneinfo/` 目录不存在，
   `/etc/localtime`、`/etc/timezone` 也不存在。
2. Go 的 `time.LoadLocation` 需要 zoneinfo **数据文件**，不是环境变量。

⇒ **只注入 `TZ=Asia/Shanghai` 是假修复**：实测注入后容器内 `date` 仍输出
`Sun Nov 22 17:12:23 UTC 2026`，警告照旧。必须同时给容器可读的 zoneinfo。

**修法**（`scripts/deploy-seamless-docker.sh`）：
- `GW_ENV` 增加 `-e "TZ=Asia/Shanghai"`
- `GW_MOUNTS` 增加 `-v /usr/share/zoneinfo:/usr/share/zoneinfo:ro`
  （宿主机无该文件时优雅降级：不挂载、保持今天行为、不引入新失败面）

**实测**：容器内 `date` → `Mon Nov 23 01:12:48 CST 2026` ✅

### 2. 存储模式（一个死锁，两个入口）

**现象**：
```
storage: full mode config validation failed (non-fatal, continuing legacy assembly)
  error: storage_mode "full" requires a full_storage section in yaml
```

**根因（死锁）**：
- `config/storage.go` 的 `Validate()` 要求 `c.Full != nil`（否则报上面那句）
- `c.Full` 只在 YAML 有 `full_storage:` 段、或 env 有
  `LLM_GATEWAY_POSTGRES_URL`/`LLM_GATEWAY_REDIS_URL` 时才被创建
  （`applyEnvOverrides`）
- 部署脚本 `GW_ENV` 白名单注入了 `LLM_GATEWAY_STORAGE_MODE=full` 和
  `LLM_GATEWAY_DATABASE_URL`，**但没注入上面两个变量** ⇒ `c.Full` 恒 nil
- `AlignFullPostgresURL` 本可从 `DATABASE_URL` 回填 `postgres_url`，
  但它的前置条件是 `c.Full != nil` ⇒ **永远触发不到** ⇒ 死锁

⇒ 也就是说：`DATABASE_URL` 明明有值、`STORAGE_MODE=full` 也明明设了，
但存储仍降级到 legacy 装配。

**修法**：`GW_ENV` 补两个变量：
```
-e "LLM_GATEWAY_POSTGRES_URL=${DB_URL}"
-e "LLM_GATEWAY_REDIS_URL=${REDIS_URL}"
```
（`REDIS_URL` 引擎已在 2210/2212 行算出，含密码 URL-encode 与 DB 号）

**实测**：启动日志变为
```
storage hotzone trimmer 已装配  mode=full  dir=./data/hotzone  retention_hours=7
storage full 模式热区已装配（hotZoneOnly）
```
—— 不再有 "requires a full_storage section" 警告 ✅

**附带说明**：`LLM_GATEWAY_REDIS_URL` 对 `config.Redis` **不生效**——引擎注释
（2204-2207 行）写明「config.Redis 只认 ADDR/DB/PASSWORD 三段，v2 旧版协议
已废弃」。它在这里的消费者是 `full_storage.redis_url`，两者是不同消费方。

### 3. 插件注册（真代码缺陷，非配置问题）

**现象**：
```
failed to initialize plugin registry
  error: plugin registry not fully configured: approval provider not configured:
         authplugin: approval provider "native" not found (available: [])
```

**根因**：`cmd/gateway/plugin_init.go` 的 `registerNativeProviders` 里，
native approval provider 的注册整块被 `/* */` 注释掉了：

```go
/*
    approvalStore := approval.NewStore(db)          // ← 且 NewStore 根本不存在
    configManager := approval.NewConfigManager(approvalStore, redisClient)
    nativeApproval := native.NewNativeApprovalProvider(configManager)
    if err := registry.RegisterApprovalProvider(nativeApproval); err != nil { ... }
*/
```

而 `loadPluginConfig` 的默认值是 `ApprovalProvider: "native"` ⇒ registry 里
永远不会出现名为 "native" 的 approval provider ⇒ `IsConfigured()` 必挂 ⇒
**211 生产启动日志恒有一条 ERROR**。

**为什么现在能启用**（当时的注释说"domain 未就位"，但现在已就位）：
- `domains/approval` 存在，且其 `*ConfigManager` 方法集与
  `native.ConfigManager` 接口**逐字一致**（GetConfig / UpdateConfig /
  GetApprovers / AddApprover / UpdateApprover / RemoveApprover / GetRules /
  AddRule / RemoveRule）⇒ 天然满足接口，无需适配层
- 构造函数名要改：不是 `approval.NewStore`（不存在），而是
  `approval.NewPGApprovalStore(pool, cache)`，它返回 `ApprovalStore` 接口，
  正是 `NewConfigManager` 的第一个参数类型

**修法**：启用注册 + 抽成具名函数 `registerNativeApprovalProvider`。

**为什么要抽具名函数**：接线才是会退化的那一环——函数体好测，
「调用点还在不在」只有具名函数 + 行为测试才能钉死（AGENTS.md 纪律）。

## 四、maintain proxy：为什么不改

**现象**：`maintain proxy disabled — error: MAINTAIN_SERVICE_URL is not set`

**取证**（`cmd/gateway/maintain_proxy.go` 头部注释 + 第 17-18 行）：
> When MAINTAIN_SERVICE_URL is unset the Gateway falls back to its legacy
> in-process handlers, preserving the pre-migration rollback path.

⇒ **未设置是设计内的降级路径**：网关继续用自带的 legacy in-process handlers
服务运维端点，功能正常，只是走旧路径。

**为什么不改**：
1. 需要一个**真实存在**的 maintain 服务地址——仓内没有该服务的部署信息，
   填错地址比不填更糟（会 503 而不是回退）
2. 启用它会把 `/api/admin/*` 等端点**切走**到另一个服务 ⇒ 行为变更，
   需要先确认那个服务已就位且行为一致
3. 这不是缺陷，是**迁移期状态**——该告警在 maintain 服务上线后自然消失

⇒ 登记为待办，不在本轮变更范围。
