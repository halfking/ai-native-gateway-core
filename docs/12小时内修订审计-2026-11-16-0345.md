### P1-3 · `llmCache` 是**无锁 map** ⇒ 并发写 ⇒ Go runtime fatal ⇒ **整个网关进程退出**

- **位置**：`domains/promptinjection/detector.go:34`（字段）、`:248`（读）、`:270`（**整体替换 map 指针**）、`:272`（写）
- **事实**：`Detector` 是 **boot 期单实例**（`cmd/gateway/main.go:7678` → `piDetectorAdapter` → `SetV2DispatchAnalysisResources`）⇒ **所有请求 goroutine 共享同一个 map**。无 `sync.RWMutex`。
- **后果**：Go 的 `fatal error: concurrent map writes` **不可 recover** ⇒ 不是死一个 goroutine，而是**整个网关进程退出**。`:270` 的「超 10000 条整体 `make` 重建」是第二次无锁写。
- **修复**：`Detector` 加 `llmCacheMu sync.RWMutex`；缓存访问收敛到 `llmCacheGet` / `llmCachePut` 两个方法（写侧清空与写入同一临界区，不存在「换了 map 指针但另一 goroutine 往旧 map 写」的丢失写）。
- **状态**：✅ 已落地。

1. **「修法写了」≠「修法生效了」**——P1-1 与 P1-2 都是上一轮自称「P1 根修」的提交，实际一个**通道没接**、一个**迁移没建**。⇒ 交付前必须问两个问题：**「这条路径的投递/执行通道接上了吗」**、**「读侧引用的东西在库里真的存在吗」**。
2. **COALESCE 挡 NULL，挡不住「列不存在」**——凡是「投影里加了新列」，必须有配套迁移；`COALESCE` 是**读侧对 NULL 的兜底**，不是**对缺列的兜底**。
3. **一个 panic 掩盖整包测试结果**——包级测试中止不是「一个用例坏了」，是「这一包的所有结论作废」。修 panic 常常顺带暴露被掩盖的真缺陷（本案：P2-11 → P2-12）。
4. **无锁 map 在请求路径上 = 进程自杀**——Go 的 `fatal error: concurrent map writes` 不可 recover；boot 期单例 + 请求路径共享 ⇒ 必加锁。
5. **「0 = 禁用」的开关，实现成「0 = 全量」比没有开关更危险**——运维以为省钱、实际最贵。
6. **静态门要锚到真源**——投影↔Scan 的同源自证抓不到「投影列在库里不存在」；门必须解析 `sql/objects/tables/` ∪ 迁移。
7. **同型事故会复发**——926 的「登记未投递」在 966 上原样复发（两者的修复都只做了一半）。⇒ 每次遇到「登记已做」必须追问「投递已做吗」。
8. **把一条迁移接进投递通道 = 让既有守卫第一次真正看见它**——966 接进 embeddata 后，`startup_ddl_lock_guard_gate_test.go` 立刻报出「既有强锁 DDL 又无事务块/无 `lock_timeout`」。⇒ 「以前没红的门」可能是「以前没被看见」。
