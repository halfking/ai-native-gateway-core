## 二、`b5ec9a784` 打红 integration 门（L1）

### L1.1 这道门红得对，而且红得「只有它能看见」

`sql/schema` 的 `TestIntegrationTaggedTreeCompiles`（`ca4c828f4` 加）在本轮**首次变红**：

```
--- FAIL: TestIntegrationTaggedTreeCompiles (53.04s)

```

根因是两个文件的 build tag 不对称：

- `manifest_test.go:1` 是 `//go:build !integration`，`repoRoot` 定义在 `:565`；
- `resolve_test.go:1` **没有** build tag，却在 `:791` 调用 `viewsWithV1Arm(repoRoot(t))`。

> **这是「默认路径看不见的编译错误」**：无 tag 的 `go build ./...` 与
> `go test` 对它完全无感，只有 `go vet -tags=integration` 会炸。
> 也正因如此它能一路活到本轮——**上一轮 R46 的 14 包全绿是「无回归」，不是「跑过了」**。

### L1.2 为什么不能给调用方加标签（两个方向各错一半）

## 三、批量 upsert 的失败路径（L2）

### L2.1 缺陷：写成功与缓存失效被一个 `return err` 拆散

`cd6c89145`（§10.30）把 watcher 从逐行 `Register` 改成 `RegisterBatch`。
原来的 `apihub/service.go:147`：

```go
if err := s.store.UpsertBatch(ctx, prepared); err != nil {
    return err                                  // ← 提前返回
}
for _, a := range prepared { s.cache.invalidate(...) }   // ← 一条都没跑到
```

**为什么 store 报错时库里其实已经写了**——这正是同一笔提交自己写的退路
（`apihub/pg_store.go:379-394`）：分片失败时 `upsertRowsIndividually`
**逐行重跑并隔离坏行**，成功的行已经落库，但 `UpsertBatch` 仍返回 `firstErr`。

⇒ 「500 行里 499 行写成功」与「缓存一条没失效」同时成立。

**症状是静默的**：DB 是新值、`Get` 命中 TTL 内的旧值，默认 60s 后自愈。
运维看到的是「改了名字但资产列表没变」，且**无法复现**。

**为什么改动前不存在**：逐行 `Register` 时代，每个 `Register` 成功后
**自己**失效那一条缓存。批量化把「写」与「失效」拆到两个循环，
中间夹了一个 `return err` ⇒ 失败时两者不再配对。

### L2.2 门先复现，再改产品代码

`apihub/batch_cache_invalidation_test.go` 三条。**未修复时的实测**：

```
--- FAIL: TestRegisterBatchInvalidatesCacheEvenWhenStoreReportsFailure
      ref_id=1 的缓存未失效，仍返回 "stale-name"（DB 里已是 "a"）
      ref_id=2 的缓存未失效，仍返回 "stale-name"（DB 里已是 "b"）
--- PASS: TestRegisterBatchInvalidatesCacheOnSuccess          ← 对照组
--- FAIL: TestRegisterBatchFailureDoesNotStaleReads
      Get 返回 "old-name"，库里是 "new-name" —— 失败路径留下了陈旧缓存
```

对照组（成功路径）在修复前后**都绿** ⇒ 三条门有判别力，不是恒真。

### L2.3 修法

把失效循环提到 `err` 检查**之前**：

```go
err := s.store.UpsertBatch(ctx, prepared)
for _, a := range prepared { s.cache.invalidate(a.Kind, a.RefID, a.TenantID) }
return err
```

取舍写在代码注释里：**宁可多清几条不该清的缓存**（代价是一次 cache miss +
一次回表），也不要留下读得到的陈旧值。

修后三条门全绿。

> ⚠ 我自己写的第三条门**第一版也是红的，但红得不对**：
> `Get` 需要 tenant 上下文（`WithTenant`），我漏了 ⇒ 报
> `asset not found`。那是**我的门的 bug**，不是产品缺陷的证据。
> 修正门之后才拿到上面那条 `old-name` 的真证据。
> ⇒ 门红了先问「红的是被测对象还是我这条门」。

## 八、给下一轮的三条方法论提醒

1. **「默认绿」不等于「编译过」。** 无 tag 的 `go build ./...` 对
   build tag 不对称的错误**完全无感**。R46 记的「14 包全绿」是**无回归**，
   不是跑过了——那道 integration 门才是唯一能看见它的观测手段。
   ⇒ 门禁清单里凡有「编译整个 tagged 树」的门，它红**就是**真缺陷，
   不要先怀疑采集侧。

2. **「部分失败」是批量化引入的新状态，它没有对应判据。**
   批量化把「逐条写 + 逐条失效」拆成两个循环，中间夹一个 `return err`
   ⇒ 失败时两者不再配对。查批量改动时，**成对检查「副作用是否也被批量了」**：
   写、缓存失效、计数上报、指标，三者必须一起搬。

3. **门红了先分清「被测对象错」还是「我这条门错」。**
   §L2.2 我自己的门第一版就因漏 `WithTenant` 而红，
   §L1.3 负控的两次尝试也分别被 `Remove-Item` 策略拦和 PS 编码破坏。
   ⇒ 这三者的输出形态**完全一样**（都是「红」），但处置方向相反。

4. **★ 改名/改扩展名要连带三处，每处都有独立的门。**
   `404050630` 改 `.sql` → `.sql.skip` 这一笔，触发了**两个方向相反**的报错：
   台账门说「台账有、磁盘无」（台账没跟着改），
