## 1. 背景与问题

用户报告：会话在等待用户裁决期间，未获得任何输入却**每隔 ~6 秒发起一次请求**，其中「仍在等你的裁决，无新情况，不会代为决定，也不会重复调用 AskUserQuestion。待办清单内容仍准确，无需更新。」一句重复 **500+ 次**，浪费大量 token。

211 生产取证（acc-pg17 / llm_gateway，只读）：

| 会话 | 轮数 | prompt tokens | 空转形态 |
|---|---|---|---|
| gw_872726fd（2026-11-05） | 550 | **1.15 亿** | turn 424–550 上下文 ~720KB、每轮仅 +700~2000 字节；turn 426–544 **回复逐字节同 md5（108 轮）** |
| gw_264193cb（11-27/28） | 1554 | **6.29 亿** | **93% 轮**上下文增量 ≤2048（均值 +384）；回复多为 paraphrase（1528 个不同指纹） |
| gw_b1be9881（11-02~11-13） | 3280 | 3.93 亿 | **同一请求体逐字节重复 344 次**（节拍 30.9s） |

成因链：agent 编排宿主（completion verifier 判「目标未完成 → 继续调用」）把「人类阻塞性未完成」当「技术性未完成」继续轮询；每轮把模型自己的短回复（216~516 tokens）并回上下文重发整段历史。网关侧可见的确定性信号只有两个：**上下文零增长**与**回复逐字节重复**。

## 2. 方案总纲：三层架构

```
┌─ 语义层（编排层，网关外）────────────────────────────┐
│ blocking_type 标注 / AskUserQuestion 硬退避 / 事件驱动  │  ← 待 owner 排期（§9）
├─ 处置层（网关，守卫的「怎么办」）────────────────────┤
│ 429 + Retry-After 指数退避梯 → 每窗一探针 → 超次终态关停 │  ← 已交付
├─ 判据层（网关，守卫的「怎么拦」，确定性 O(1)/轮）──────┤
│ 判据① 上下文零增长计数      判据② 回复指纹重复计数      │  ← 已交付，双道互补
└──────────────────────────────────────────────────┘
```

原则（与候选挡空 4xx 契约同族）：**网关不伪造模型输出、不猜语义**——只拒绝转发；判据必须便宜且确定性，语义分析（PI/LLM）不入热路径。

## 3. 判据层设计（真库校准）

### 3.1 判据①：上下文零增长（context-delta）

对每个成功轮（emitTelemetry 单一收口，chat/messages/responses 三面共用）：

```
ownOnly = (本轮 prompt_tokens − 上轮 prompt_tokens) − 上轮 completion_tokens
空转轮：ownOnly ∈ [-128, flat_delta_tokens(512)]    （实测均值 +381，上界 ≈1100）
进度轮：ownOnly 超出判据 ⇒ 计数清零、守卫重开
```

- [-128, 0) 容忍 estimated/actual usage 统计噪声
- 连续 `trip_after_turns`（默认 12）轮 ⇒ 进入回退态
- 连续 `terminal_turns`（默认 120）轮 ⇒ 终态（超次数关闭）
- 首轮只建基线不计入（flatRun = 成功轮数 − 1）

### 3.2 判据②：回复指纹重复（reply-fingerprint，第二轮补齐）

背景：宿主每轮可能注入大块 reminder，把上下文增量抬过判据①；但 gw_872726fd 的 108 轮回复逐字节相同——回复纹丝不动是更直接的循环证据。

```
指纹 = fnv64( 空白折叠(reply) 尾标点剥离 截尾 2KB )
同一指纹连续 repeat_identical_limit（默认 5，0=关闭）次 ⇒ 立即进入回退态
回复变化（paraphrase/标点漂移/空白差异）⇒ streak 重置（不误伤）
```

默认 5 对齐 CrewAI「同工具+同参数+同结果 5 次硬停」的工业实践（其固定不可调，本处可调可关）。

### 3.3 双道互补的实证

真实事故回放（§7）证实：gw_872726fd 由**指纹道**先武装（回复先重复）、gw_264193cb 由**上下文道**趟点（回复多为改写、上下文持续零增长 25 连续）——两场各由一条判据抓住，缺一不可。

## 4. 处置层设计（自动回退 ＋ 超次数关闭）

```
回退态（flat ≥ 12 或指纹 streak ≥ 5）：
  429 + Retry-After，窗口沿指数梯：30s → 60s → 120s → 240s → 480s → 600s（封顶）
  每个窗口只放行一个探针轮（窗口即重武装，锤击客户端最多一窗一请求）
  6 秒节拍的空转客户端：从 ~100 请求/10min 压到 1 请求/10min

终态（flat ≥ 120）：
  错误码升级 loop_guard_terminated，探针间隔放宽到 terminal_probe_interval_seconds（默认 1h）
  ≈「超次数关闭」，但探针路径永远存在

重开路径（误判永远可自愈）：
  ① 入口侧请求体估计较上次成功轮增长 ≥ entry_progress_tokens（默认 2048 ≈ 空转上界的 2 倍）
     ⇒ 视为真实新输入，立即重置放行（返程人类不撞死门）
  ② 探针轮出现真进度（ownOnly 超判据）⇒ 整体重置
  ③ 相邻成功轮间隔 > max_gap_seconds（默认 600s）⇒ 计数清零（循环自然中断）
```

拒绝的契约：`429` ＋ `Retry-After` 头 ＋ `X-Gw-Loop-Guard` 头 ＋ error code ∈
`loop_guard_backoff` / `loop_guard_repeat` / `loop_guard_terminated`（编排层可据此机读，
即交接文档 §3.1 blocking_type 的网关侧等价信号）。

**豁免面**（不误伤）：internal 回环 key（探测/健康检查的固定节奏是合法的）、prompt < min_prompt_tokens(256)（sys:anon 零 token 流量）、间隔 <500ms 的并发突发（同会话并行请求无「上一轮」）、失败轮（失败后重试合法）、auto 子请求（auto-title/summary 共享 session id）。

## 9. 编排层建议（网关外，待 owner 排期）

网关拦的是「网关可见」的上游 token 浪费；编排层自身的轮询成本（agent 转录、verifier 调用）需编排服务落地：

1. **blocking_type 结构化标注**（P0）：completion verifier 输出加机器可读 `blocking_type: human_input_required | technical_incomplete`，只有后者允许高频续作；判分口径加问「此阻塞是否可由本会话继续调用工具解决」，答否直接短路「继续」指令
2. **AskUserQuestion 硬性退避**（P0）：未获回复 1~2 次后目标置 `blocked_on_human`，续作秒级 → 指数退避（分钟→小时→天）
3. **重复度去重熔断**（P1）：连续 3~5 轮回复高重复且无新工具证据 ⇒ 熔断（网关 ownOnly/指纹即同一思想的可计算形态）
4. **单目标资源硬上限**（P1）：token/调用次数/墙钟三阈值（本次亿级才停，应压到百万级）
5. **事件驱动取代轮询**（P2）：blocked_on_human 不定时唤醒，改推通知/工单
6. **网关侧后续增强候选**：拒绝计数/免烧 tokens 暴露成 /metrics 与管理台卡片；终态会话清单 API

## 10. 运维口径

- 部署后守卫默认开启；全关改 `loop_guard.enabled` 一个键即可，无需重启
- 观测：容器日志 `grep 'loop guard rejected request'`；响应头 `X-Gw-Loop-Guard`；error_code 三值如上
- 误伤调参顺序：先调 `trip_after_turns` ↑ 或 `flat_delta_tokens` ↑；`entry_progress_tokens` 只在「返程人类输入特别短」时才需要调低
- 诚实边界：只拦「上下文零增长／回复指纹重复」两型循环；宿主每轮注入大块 reminder（增量 >2048 且回复在变）属计费/限额问题，有意不拦；状态不跨重启
