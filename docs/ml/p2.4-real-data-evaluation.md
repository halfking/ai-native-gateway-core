## 3. 根因分析

零数据是**双重原因叠加**，均为部署拓扑问题而非代码缺陷：

1. **生产无 AUTO 流量**：当前生产流量全部显式指定模型，`model=auto` 6 天内
   零请求。没有 auto 请求，decider 不触发，SelectionWriter 无行可写。
2. **245 预发为 traffic-only 角色**：canary 槽位单元模板硬编码
   `LLM_GATEWAY_RUNTIME_ROLE=traffic-only`，autoroute decider / SelectionWriter /
   SettleWorker / AffinityWorker 全部不装配（`cmd/gateway/main.go` 的
   `!bgDataPlaneOnly` 块），auto 请求静默回退 `autoFallbackModel()` 且不记录。
   245 日志中仅有一条 `data-lifecycle: hot cron table done (migrated:0)` 生命周期
   巡检行，零选择写入、零 auto 决策——与 2026-09-05/06 观察期结论一致。

## 8. 缺陷发现与修复实录（2026-09-08 造数期间）

造数数据落地后，特征列质量核查暴露三个真实缺陷；均已修复并验证。

### 8.1 promote 函数漂移 — 热表→分区迁移丢失全部 21 个特征列

- **症状**：`auto_route_selections_all` 按 storage_tier 切分后特征存活完全二值化
  —— hot 表行特征齐全，parent 分区行（10,255 行）`detected_language` 等 21 列
  全部 NULL。
- **根因**：共享库上部署的 `promote_auto_route_selections_hot_to_partition`
  是 658 之前的旧函数体（`DELETE...RETURNING id, partition_date`，不含特征列）；
  658 迁移 §4 的 CREATE OR REPLACE 补丁未落共享库（多网关共享库迁移竞争的
  已知漂移类，参照 supplier_errors_hot promote 未落库先例）。
- **修复**：从仓库 `sql/migrations/startup/658` §4 提取函数体原句，在共享库
  `CREATE OR REPLACE` 重放（幂等）。手动执行 promote 迁移 678 行后特征全部
  存活入分区，`_all` 总行数不变（零丢失）。
- **注意**：此修复只保护**今后**的迁移；已迁移的旧行特征不可恢复。

### 8.2 选择记录信号丢失 — chat 路径 fresh wire 导致特征全表退化

- **症状**：即便留在 hot 表、未经 promote 的行，特征仍是退化值：
  `detected_language='unknown'`、`content_hash` 全表同值（sha256("\n")），
  而同一次调用的 task_type/classifier/confidence 却正确各异。
- **根因**：`recordAutoSelection` 内部用 `decisionToWire(decision)` 重新派生
  了一个 fresh wire，而 `decisionToWire` 从不填充 `signals` 字段（signals 只在
  chat 调用点手工附加到响应头用的那份 wire 上）。`ExtractStructuredFeatures`
  拿到零值 signals → 一切特征按空文本计算。
- **修复**（`domains/streaming/auto_route.go`）：chat 路径改为直接复用已携带
  signals 的 wire 调 `recordAutoSelectionFromWire`；组装逻辑抽为纯函数
  `buildAutoSelection`。删除死代码 `recordAutoSelection`。
- **测试**：`TestAutoRouteE2E_Chat_WireCarriesSignalsForSelection`（钉住返回
  wire 必须携带 signals）+ `TestBuildAutoSelection_TranslatesWireSignalsInto
  Features`（钉住转换层：zh prompt → DetectedLanguage="zh"，ContentHash 不得
  等于零值 signals 的 sha256("\n") 常量）。domains/streaming 全套 -race 通过。

### 8.3 exporter 两个扫描 bug（真实导出首次触发）

- `EXTRACT(EPOCH FROM ts) * 1000` 返回 numeric，pgx 无法 scan 进 int64
  → 改为 `(EXTRACT(EPOCH FROM ts) * 1000)::bigint`（注意括号：`1000::bigint`
  只转字面量，乘积仍是 numeric）。
- `content_hash` 列生产表可空，而 Parquet schema 声明 REQUIRED → SQL 层
  `COALESCE(content_hash,'')`；同时 `dedupRecords` 对空 hash 回退 request_id
  键，防止 content_hash 策略下旧行静默坍缩成一条。
- 之前"工具链健康"结论只验证到空集守卫；真实数据下 scan 路径首跑即暴露——
  快赢导出（§9）验证了修复。

### 8.4 造数方法升级：固定 prompt → 组合式生成

初版脚本仅 ~96 条固定 prompt，同 prompt 的重试产生相同特征向量：
content_hash 去重后训练集会坍缩到 ~400 个唯一向量，且固定 prompt 的重复行
造成 train/test 泄漏（首轮快赢 86.6% 含虚高成分）。改为组合式生成
（zh 12框架×50主题×5限定 + en 10×30×6 + code 20任务×8语言 ≈ 4,960 种唯一
内容），显著提升特征多样性。

## 9. 观察级重训实测（2026-09-08）

### 9.1 快赢管道验证（第一代数据，4 特征存活）

用修复前的 10,933 行（仅 task_type/profile/classifier/confidence 有值）先跑
一次端到端验证：export（config 8，request_id 去重）→ train → evaluate。

- test accuracy **0.8659** vs 最频繁基线 0.5293 / 随机 0.1348；
- 特征重要性 task_type 57.97% + confidence 41.01% 吃掉全部权重，其余 15 特征
  近似常数——正是缺陷 8.1/8.2 的直接后果；deepseek/kimi 等类 recall=0。
- 结论：管道全通，但该模型不可用于生产判定——特征缺失导致类间不可分。

### 9.2 正式观察级重训（修复后二代数据，17 特征）

**数据**：修复版二进制（含 §8.2 修复）+ 组合式 prompt 生成器，09-08 03:10→05:40
在 154 datagen 实例（:8790）产出 11,125 行；content_hash 去重后 **4,636 行**
唯一特征向量（与组合空间 ~4,960 吻合）。特征验收：detected_language 100% 非
空且仅 {en, zh}、4,624 个唯一 hash、0 退化行。

**训练**（config：window 09-08、content_hash 去重；RF n=100/depth=20）：

| 指标 | 值 |
|---|---|
| train/val/test | 3,238 / 694 / 694 |
| 模型 test | **0.6153** |
| 模型 val | 0.6282 |
| 基线: 最频繁 | 0.3948 |
| 基线: 均匀随机 | 0.0951 |
| 基线: 规则引擎 | N/A（无人工标注；标签即规则引擎产出） |
| **诚实泛化（unseen-hash）** | **0.6153（n=694，seen n=0 零泄漏）** |

`eval_honest.py` 按 content_hash 分组复算：去重保证每个 hash 全局唯一，
seen-hash 子集为空——**61.5% 全部来自对未见过内容的泛化，无泄漏虚高**。

- 特征重要性：task_type 55.5% + confidence 43.8% 仍占绝对主导；
  detected_language/profile/complexity 已进入 Top5（合计 ~0.6%）。
- 分类面：minimax-m3 F1=0.948；deepseek/kimi F1≈0.4-0.5；少数类
  （glm/claude/minimax-text）recall=0——特征空间不足区分时模型退回多数类，
  符合"建议者"降级语义（MLReranker 预测不命中候选即保持规则引擎原序）。
- **标签漂移警示**：本窗口标签分布（minimax-m3 34%/kimi 20%/deepseek 20%）
  与前一日（glm-5.1 53%）显著不同——chosen_model 依赖凭据池实时健康度，
  印证 §9.2 前置判断：纯 pre-decide 特征的精度上限受运行时信号约束。

### 9.3 离线结论（任务1 第6步交付）

1. **ML 能否优于规则引擎**：离线口径下**不可直接判定**——训练标签本身就是
   规则引擎的产出（chosen_model），不存在反事实；无人工标注故规则引擎基线
   N/A。离线能证明的是：**17 个 pre-decide 特征对规则引擎决策的 top-1 复现
   率为 61.5%（9 类，多数类 39.5%，+22pp），且全部为对新内容的泛化**。
2. 剩余 38.5% 差距源于规则引擎依赖的运行时信号（凭据健康/渠道质量/成本）
   不在特征集内——与 MLReranker"只提升命中候选、永不改基线"的建议者定位
   自洽。
3. **任务2门禁判定：条件性通过**。基线超越成立（most_frequent/random）；
   "ML vs 规则引擎"的正式比较按设计依赖 A/B 实验本身（annotation_stats +
   请求成功率）。MLReranker 五层降级保证最坏情况等价基线，10% 灰度零风险，
   可启动；放量决策与 7 天观察按 handoff 任务2 执行。产物就绪：
   `models/real-v1/model.onnx`（0.27MB）+ `manifest.json`（zipmap=False，
   9 类标签）。
4. **部署前置**：§8.2 修复必须随主部署火车上线（当前 154/245 slots 二进制
   仍带缺陷，真实流量下会继续产出退化特征行）；§8.1 promote 修复已直接落
   共享库（幂等 DDL），后续版本自然收敛。
