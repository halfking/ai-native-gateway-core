## 2. 架构

```
P2.2 Parquet导出 ──┐
                   ├─→ data_loader ─→ feature_pipeline ─→ train(RF) ─→ evaluate ─→ export
P2.1 人工标注CSV ──┘    (合并/清洗/切分)   (编码/归一化)      (x2权重)     (指标/基线)   (joblib/ONNX)
```

单一配置入口 `config.yaml`：特征清单、清洗阈值、超参数、划分比例、基线选项。
**特征清单是数据驱动的**：schema v2新增字段（如`prompt_token_count`、
`context_window_util`、`model_family`、`region`）时只需在config的
`categorical/boolean/numeric` 列表中追加，代码零改动。

## 3. 关键设计决策

### 3.1 标签空间：chosen_model + human_label覆盖

v1 Parquet schema的实际标签字段是 `chosen_model`（规划文档里假设的
`selected_provider` 列在v1 schema中不存在）。设计：

- `label = human_label`（若有P2.1标注，按request_id关联）否则 `chosen_model`
- 人工标注样本 `sample_weight = 2.0`（任务要求x2；`annotation_label_weight`可调）
- 保留 `rule_engine_choice` 辅助列（覆盖前的自动选择），专用于规则引擎基线评估
- **已知风险**：P2.1标注CSV（`human_provider`）的取值空间是provider，
  `chosen_model`是模型名；当前部署二者一致，若未来分叉，用
  `data.annotation_require_known_label: true` 阻止跨词表覆盖（已实现），
  正式的标签空间归一放在阶段4。

### 3.2 与规划文档的特征清单差异

`docs/planning/p2-next-steps.md` 列出的15特征（model_family、region、
prompt_token_count等）与实际schema v1不符。以 `exporter/parquet_schema.go`
为准，实际用于训练的17个特征：

- **类别(10)**: task_type, profile, classifier, detected_language,
  prompt_length_bucket, context_length_bucket, turn_count_bucket,
  intent_category, domain_hint, complexity_bucket
- **布尔(6)**: has_code/math/table/multimedia_indicator, latency_sensitive, cost_sensitive
- **数值(1)**: confidence

`task_type/profile/classifier/confidence` 是路由时已知的请求上下文（规则引擎
的输入），作为特征合法且必要。`content_hash`（去重用）、`feature_version`
（过滤用）、`request_id`（标注关联）不作特征；`success/latency_ms/reward`
是outcome信号，留给阶段3的reward-based建模。

### 3.3 编码：OrdinalEncoder代替LabelEncoder

任务要求"LabelEncoder"，实现用 `OrdinalEncoder(handle_unknown='use_encoded_value',
unknown_value=-1)`：LabelEncoder设计上只能编码标签y、不支持Pipeline和未见类别；
OrdinalEncoder按列输出相同的整数编码，且对推理时出现的新类别安全地映射到-1
（树模型可将其视作独立分支）。RandomForest不需要One-Hot（高基数语言/意图字段
会碎片化分裂点）。

### 3.4 缺失值契约（训练/推理共用）

| 特征类型 | 缺失语义 | 实现 |
|---|---|---|
| 类别 | `null → "__missing__"`（缺失即类别） | `data_loader.normalize_features` |
| 布尔 | `null → -1`（与False=0可区分） | 同上，int8 |
| 数值 | `NaN → 训练集中值` | Pipeline内 `SimpleImputer(median)` |

`normalize_features` 是**Go推理端必须复刻的特征准备契约**（阶段4），
语义上等价于把这一步编进ONNX图的输入约定。

### 3.5 ONNX导出：每列一个命名输入

第一次尝试把整个Pipeline转成单个float32 `[None, 17]` 输入，skl2onnx要求
ColumnTransformer按**列名**接收输入。最终契约（对Go更友好）：

- 类别列 → `string [None,1]`；布尔列 → `int64 [None,1]`；数值列 → `float32 [None,1]`
- OrdinalEncoder/Imputer/Scaler/RF全部编码进同一个ONNX图，
  Go端（`onnxruntime_go`）只准备原始字段值，零特征工程代码
- 集成测试验证：ONNX与joblib在同一批样本上的预测一致（≥90%一致率，
  允许opset级浮点误差）

为此Pipeline的fit/predict统一走 `select_features()`（17列、顺序固定），
保证`feature_names_in_`与ONNX输入名一致。

### 3.6 数据清洗规则（`clean_data`）

顺序执行，各步丢弃数记录在`cleaning_stats`：
1. 标签为空/空串的行丢弃
2. 重复`request_id`防御性去重（导出端已按`content_hash`去重）
3. `confidence`越界[0,1]的行丢弃（缺失保留，交由中值填充）
4. `outcome_filter: success_only`可选——只模仿成功的选择（默认all）
5. `min_label_frequency: 10`——低频标签整类丢弃，保证分层切分有效
   （3-way分层要求每类在最小split中至少1条）

### 3.7 划分：70/15/15，stratify=y，无泄漏

两步`train_test_split`（先切出15% test，再对剩余70/15切分），固定
`random_state=42`。测试校验：三个split的标签分布与整体一致（±2%）、
`request_id`零交叉。

### 3.8 基线对比中的"规则引擎"语义

离线数据只有规则引擎的实际选择（`chosen_model`）及其结果，没有反事实
（"如果选了别的provider会怎样"），因此：

- **测试集内人工标注行**：`rule_engine_choice vs human_label` 的准确率是
  规则引擎在困难样本上的真实准确率（`rule_engine_baseline()`）
- **无标注行时**：回退到config的 `evaluation.rule_engine_accuracy`
  （从P2.1 `annotation_stats` 视图取生产值）
- 两者皆无 → 报告N/A，`beats_baselines.vs_rule_engine = null`（不假装比较）

这个限制写进了README FAQ；真正的ML vs 规则引擎结论以阶段4 A/B测试为准。

## 4. 训练配置（基线）

```yaml
RandomForestClassifier(n_estimators=100, max_depth=20, min_samples_split=100,
                       max_features='sqrt', n_jobs=-1, random_state=42)
```

`min_samples_split=100` 来自planning doc的百万样本防过拟合建议值；
小数据集（<1万行）建议在config中调小到2-10。`class_weight`默认null
（已用人工标注x2显式加权，避免双重加权）。

## 5. 性能预算

| 指标 | 目标 | 实测（合成冒烟, M2/8核） |
|---|---|---|
| 训练时间/100万样本 | < 10min | 预估3-6min（RF n_jobs=-1；2万样本<2s线性外推） |
| 模型体积 | < 100MB | 100树×depth20 通常 < 20MB |
| 单次推理延迟（阶段4目标） | < 10ms p99 | ONNX Runtime RF典型 < 1ms |

## 6. 测试矩阵（27用例）

- **单元**：schema校验、隐私字段拒载（prompt/user_id等出现即抛错）、
  标注去重保留最新、human_label覆盖+x2权重、`require_known_label`、
  清洗各步计数、切分比例/分层/无泄漏、特征dtype契约、未见类别→-1、
  数值中值填充+标准化、Pipeline序列化往返
- **集成**：端到端（训练→评估→落盘→metadata校验→模型复用）、
  优于随机/最频繁基线（合成数据含可学习结构）、CLI `--synthetic`冒烟、
  evaluate CLI重现切分、ONNX导出+ORT加载+与joblib预测一致性、
  `--skip-onnx`降级路径
