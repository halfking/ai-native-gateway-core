# 测试场景定义

本文档定义了 12 个测试场景, 覆盖 Gateway 全维度能力验证。

## 场景矩阵

| 编号 | 场景名称 | 验证重点 | 故障注入 | 模型数 | 并发数 | 请求量 |
|------|---------|---------|---------|-------|-------|-------|
| S1 | 基准性能 | 理想状态吞吐上限 | 无 | 3 | 80 | 640 |
| S2 | 成本优化路由 | Plan vs PAYG 优先选择 | 无 | 5 | 80 | 640 |
| S3 | 并发能力差异化 | 不同并发限制下的流量分配 | 无 | 5 | 100 | 600 |
| S4 | 配额耗尽与恢复 | TokenPlan 配额耗尽 → failover → 恢复 | C 组配额 2K | 5 | 60 | 600 |
| S5 | 延迟/质量降权 | 慢/不稳定供应商被降权 | G=slow, J=flaky | 5 | 80 | 640 |
| S6 | 混合故障韧性 | 多种故障并发 | G=slow, J=flaky, B=flaky, K=rate_limited | 5 | 100 | 600 |
| S7 | 高峰动态调度 | 高负载下启用更多供应商 | 无 | 5 | 150 | 900 |
| S8 | Sticky 连续性 | Session 粘性路由保持 | 动态故障 | 1 | 30 | 600 |
| S9 | 流式 SSE | 流式响应完整性和性能 | 含 broken_stream | 3 | 40 | 200 |
| S10 | 长 Prompt | 大上下文处理 | 含 context_length_exceeded | 3 | 40 | 200 |
| S11 | 周期性配额恢复 | 短窗口配额恢复 | C 组 60s 窗口 | 5 | 40 | 320 |
| S12 | 全场景综合压测 | 以上全部 + 随机故障注入 | 动态全场景 | 15 | 150 | 12000 |
| S13 | 无可用节点 | 全部供应商故障 → no_candidate | 全部组 disabled/故障 | 3 | 40 | 200 |
| S14 | 模型不存在 | 请求不存在模型 → model_not_found | 无 | N/A | 40 | 200 |
| S15 | 跨组故障迁移 | 主力组故障 → 自动迁移到备用组 | A/B 组全部 server_error | 5 | 80 | 640 |
| S16 | 充值快速恢复 | 配额充值/手动启用后立即恢复 | C 组配额耗尽→充值 | 3 | 40 | 400 |

## 场景详细定义

### S1: 基准性能测试

**目标**: 测量 Gateway 在理想状态下的吞吐上限和延迟基线。

**配置**:
- 所有 12 组 mock 均为 healthy 模式
- 8 个客户端 API Key 轮换
- 短 Prompt (10-30 tokens)

**执行**:
```bash
python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --api-keys "key1,key2,...,key8" \
  --clients 80 --rounds 8 \
  --models "loadtest-mini-alpha,loadtest-mini-beta,loadtest-standard-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S1-baseline.json
```

**预期**:
- 成功率: 100%
- P95 延迟: < 800ms
- P99 延迟: < 1200ms
- 无错误

---

### S2: 成本优化路由

**目标**: 验证 Gateway 优先选择成本最低的可用供应商 (TokenPlan/CodePlan 优先于 PAYG)。

**画像影响**:
- C 组 (TokenPlan, cost≈0) 优先级最高
- D 组 (CodePlan, cost≈0) 次之
- PAYG 组 (A/B/H/I) 在 plan 配额耗尽后才被路由

**配置**:
- 禁用 F 组 (免费池, 避免 cost=0 主导所有流量)
- C/D 组配额充足
- 5 个模型覆盖

**预期**:
- C 组流量占比 > 40% (成本最优)
- D 组流量占比 > 20%
- A/B 组流量 < 30%
- 综合成本低于纯 PAYG 场景

---

### S3: 并发能力差异化

**目标**: 验证 Gateway 根据供应商的并发能力智能分配流量。

**画像影响**:
- A 组 (concurrency=100, fp_slot=50) → 承接多数流量
- H 组 (concurrency=100, fp_slot=3) → 指纹 slot 成为瓶颈
- I 组 (concurrency=20, fp_slot=20) → 并发瓶颈
- C 组 (concurrency=10, fp_slot=5) → 最低流量

**执行**:
```bash
python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 100 --rounds 6 \
  --models "loadtest-pro-alpha,loadtest-pro-beta,loadtest-standard-alpha" \
  --prompt-size short \
  --sessions 20 \
  --output /tmp/test-results/S3-concurrency.json
```

**预期**:
- A 组流量最高
- H 组因 fp_slot=3 限制, 活跃客户端受限于 3
- I 组因 concurrency=20 限制, 达到上限后不再分配
- 各供应商流量与其实力匹配

---

### S4: 配额耗尽与恢复

**目标**: 验证 TokenPlan/CodePlan 配额耗尽时自动切换到 PAYG, 配额恢复后切回。

**配置**:
- C 组 (TokenPlan) 配额降到 2000 tokens/实例
- 快速耗尽 C 组配额
- 观察 failover 到 D 组和 A/B 组

**执行**:
```bash
# 降低 C 组配额
for port in 19090 19091 19092 19093 19094; do
  python3 scripts/mock-orchestrator-v2.py set-quota $port 2000 1800
done

python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 60 --rounds 10 \
  --models "loadtest-mini-alpha,loadtest-standard-alpha,loadtest-pro-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S4-quota-failover.json
```

**预期**:
- 前期: C 组承接大部分流量
- C 组耗尽后: 流量切换到 D 组和 A/B/Payg 组
- 总成功率: 100% (无请求因无供应商可用而失败)
- 检测到 C 组请求返回 429 quota_exceeded

---

### S5: 延迟/质量降权

**目标**: 验证 Gateway 将慢速和不稳定供应商降权, 优先路由到高质量供应商。

**配置**:
- G 组 (slow, 2-4s 延迟) → 应被降权
- J 组 (flaky 30% 错误) → 应被严重降权或零流量

**执行**:
```bash
# 注入故障
python3 scripts/mock-orchestrator-v2.py set-group G slow
python3 scripts/mock-orchestrator-v2.py set-group J flaky

python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 80 --rounds 8 \
  --models "loadtest-mini-alpha,loadtest-pro-alpha,loadtest-ultra-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S5-quality-penalty.json
```

**预期**:
- G 组流量占比 < 5% (因延迟惩罚)
- J 组流量占比 < 1% (因高错误率)
- 总成功率: > 98%

---

### S6: 混合故障韧性

**目标**: 验证 Gateway 在多种故障同时发生时的综合韧性。

**配置**:
- G 组 = slow (2-4s 延迟)
- J 组 = flaky (30% 错误)
- B 组 = flaky (30% 错误) — 原本的主力供应商之一
- K 组 = rate_limited (429)
- 共 20/60 个 mock 故障 (33%)

**执行**:
```bash
python3 scripts/run-multidim-scenarios.sh S6
```

**预期**:
- 总成功率: > 95%
- 故障供应商流量被健康供应商承接
- 无级联故障
- 慢供应商不阻塞整体吞吐

---

### S7: 高峰动态调度

**目标**: 验证高负载下启用更多供应商, 包括高延迟/高成本备用供应商。

**配置**:
- 150 并发, 5 模型
- 压力驱动 tier fallback
- K 组 (tier=3 高峰备用) 应在高负载时被启用

**执行**:
```bash
python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 150 --rounds 6 \
  --models "loadtest-mini-alpha,loadtest-standard-beta,loadtest-pro-alpha,loadtest-ultra-beta,loadtest-vision-alpha" \
  --prompt-size mixed \
  --output /tmp/test-results/S7-peak-scheduling.json
```

**预期**:
- 低负载时段: 流量集中在 tier=1 的 A/B/C/H/I 组
- 高负载时段: K 组 (tier=3) 承接部分流量
- 总成功率: 100%

---

### S8: Sticky 连续性

**目标**: 验证 Gateway 对同一会话保持同一供应商, 以及在供应商故障时的切换行为。

**配置**:
- 30 客户端, 20 轮
- 10 个唯一 session, 复用率 80%
- 每 5 轮注入一次随机故障
- 单模型 (loadtest-mini-alpha)

**执行**:
```bash
python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 30 --rounds 20 \
  --models "loadtest-mini-alpha" \
  --sessions 10 --session-reuse-ratio 0.8 \
  --prompt-size short \
  --output /tmp/test-results/S8-sticky-session.json
```

**预期**:
- Sticky 准确率: > 85% (无故障时段 > 95%)
- 故障后 session 自动迁移到其他供应商
- 迁移后粘性在新供应商保持
- 无 session 因故障而中断

### S11: 周期性配额恢复

**目标**: 验证配额在窗口过期后自动恢复。

**配置**:
- C 组短窗口: 总额 3000 tokens, 窗口 60s
- 第一波耗尽 C 组配额
- 等待 65s 窗口重置
- 第二波验证 C 组恢复

**执行**:
```bash
# 设置短窗口
for port in 19090 19091 19092 19093 19094; do
  python3 scripts/mock-orchestrator-v2.py set-quota $port 3000 60
done

# Wave 1: 耗尽 C 组
python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 40 --rounds 4 \
  --models "loadtest-mini-alpha,loadtest-standard-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S11-quota-recovery-w1.json

# 等待窗口重置
sleep 65

# Wave 2: 验证恢复
python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 40 --rounds 4 \
  --models "loadtest-mini-alpha,loadtest-standard-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S11-quota-recovery-w2.json
```

**预期**:
- Wave 1: C 组配额耗尽后流量自动转移到其他组
- 窗口等待期: C 组无流量
- Wave 2: C 组配额恢复, 流量重新分配到 C 组
- 总成功率: 100%

### S12: 全场景综合压测

**配置**:

- 流式 + 非流式混合 (50/50)
- 多 session 池 (30 个 session, 60% 复用率)
- 总请求量: ~12000

**执行**:
```bash
python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --api-keys "key1,...,key20" \
  --clients 150 --rounds 80 \
  --models "loadtest-mini-alpha,loadtest-mini-beta,loadtest-mini-gamma,loadtest-standard-alpha,loadtest-standard-beta,loadtest-standard-gamma,loadtest-pro-alpha,loadtest-pro-beta,loadtest-pro-gamma,loadtest-ultra-alpha,loadtest-ultra-beta,loadtest-ultra-gamma,loadtest-vision-alpha,loadtest-vision-beta,loadtest-vision-gamma" \

```

**预期**:
- 总成功率: > 99%
- P99 延迟: < 2000ms
- 最大吞吐: > 200 req/s
- 各供应商分布合理, 无单一供应商过载

### S13: 无可用节点 (No Candidate)

**目标**: 验证当所有供应商都不可用时, Gateway 的错误处理和降级策略。

**配置**:
- 禁用所有 12 组供应商 (DB manual_disabled=true)
- 或全部供应商设置为 server_error 模式

**执行**:
```bash
# 方式 1: DB 禁用
psql -d llm_gateway -c "UPDATE providers SET manual_disabled=true WHERE id BETWEEN 9010 AND 9069;"

# 方式 2: Mock 故障
for g in A B C D E F G H I J K L; do
  python3 scripts/mock-orchestrator-v2.py set-group "$g" server_error
done

python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 40 --rounds 5 \
  --models "loadtest-mini-alpha,loadtest-standard-alpha,loadtest-pro-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S13-no-candidate.json
```

**预期**:
- 所有请求返回 503 Service Unavailable 或 500 no_candidate
- 错误消息清晰: "No available provider for model xxx"
- Gateway 不崩溃, 不进入死循环
- 日志包含 no_candidate 错误类型
- 无 panic 或 goroutine 泄漏

### S15: 跨组故障迁移 (Cross-Group Failover)

**目标**: 验证主力供应商组全部故障时, 自动迁移到备用组的能力。

**配置**:
- A 组 (主力高并发快速 PAYG) 全部设置为 server_error
- B 组 (次主力高并发中速 PAYG) 全部设置为 server_error
- 其他组 (C/D/E/H/I/L) 保持健康
- 80 个并发客户端, 持续请求

**执行**:
```bash
# 注入故障: A 组和 B 组全部 server_error
python3 scripts/mock-orchestrator-v2.py set-group A server_error
python3 scripts/mock-orchestrator-v2.py set-group B server_error

python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 80 --rounds 8 \
  --models "loadtest-mini-alpha,loadtest-standard-alpha,loadtest-pro-alpha,loadtest-ultra-alpha,loadtest-vision-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S15-cross-group-failover.json

# 清理
python3 scripts/mock-orchestrator-v2.py reset-group A
python3 scripts/mock-orchestrator-v2.py reset-group B
```

**预期**:
- 总成功率: 100% (无请求因 A/B 组故障而失败)
- A/B 组流量占比: 0% (完全被跳过)
- C/D/H/I/L 组承接全部流量
- 流量分布: C 组 (TokenPlan, 成本低) 优先, D 组次之, H/I 组辅助
- P99 延迟可能增加 (因备用组性能略低), 但仍 < 2500ms
- 日志显示 server_error → 重试 → 切换到其他候选
- 无单一供应商过载 (流量均匀分散)

### S16: 充值快速恢复 (Quick Recovery After Recharge)

**目标**: 验证配额充值或手动启用后, Gateway 能在秒级快速恢复流量分配。

**配置**:
- C 组 (TokenPlan) 配额降到 2000 tokens, 快速耗尽
- 耗尽后流量转移到其他组
- 通过 API 或 mock 命令模拟充值 (重置配额)
- 验证流量在 5 秒内重新分配到 C 组

**执行**:
```bash
# Step 1: 降低配额并耗尽
for port in 19090 19091 19092 19093 19094; do
  python3 scripts/mock-orchestrator-v2.py set-quota $port 2000 1800
done

python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 40 --rounds 4 \
  --models "loadtest-mini-alpha,loadtest-standard-alpha,loadtest-pro-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S16-before-recharge.json

# 验证 C 组已耗尽 (流量为 0)
echo "C group should have 0 traffic now"

# Step 2: 模拟充值 (重置配额到充足状态)
for port in 19090 19091 19092 19093 19094; do
  python3 scripts/mock-orchestrator-v2.py set-quota $port 500000 1800
done

# 立即发起请求, 验证恢复速度
sleep 2
python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 40 --rounds 4 \
  --models "loadtest-mini-alpha,loadtest-standard-alpha,loadtest-pro-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S16-after-recharge.json
```

**预期**:
- Before recharge: C 组流量 0%, 其他组承接
- After recharge (2 秒内): C 组重新收到流量
- C 组流量占比快速恢复到 > 40% (成本最优)
- 总成功率: 100% (充值过程不影响服务)
- 恢复时间: < 5 秒 (从充值完成到第一个请求路由到 C 组)
- Gateway 无需重启或手动刷新
