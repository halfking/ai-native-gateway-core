# openai_empty_response 方案A决策建议书

## 给产品团队的决策摘要

### 背景
在2026-11-12的全面审计中,发现minimax-m3.1-flash模型存在一个用户体验问题:当reasoning(思考)阶段耗尽token预算时,用户需要手动重试才能获得结果。

### 当前状态
- **影响范围**: 仅minimax-m3.1-flash单一模型
- **发生频率**: 76次/7天 (~11次/天)
- **用户体验**: 需要客户端重试,增加1次往返时间
- **代码状态**: ✅ 已正确处理,不会造成数据丢失

### 方案A提议
**目标**: 当minimax-m3.1-flash reasoning耗尽预算时,网关自动切换到其他候选节点,用户无感知

**预期收益**:
- 🎯 用户体验改善: 无需手动重试
- 🎯 成功率提升: 自动failover到6个候选节点之一
- 🎯 响应时间优化: 减少1次往返(~3-5秒)

**实施成本**:
- 开发时间: 2-3天
- 测试时间: 2天
- 部署周期: 3周(Canary→灰度→全量)
- 总时间: 3-4周

**风险评估**: 低
- 改动集中在单一模块
- 有完整的回滚预案
- 不影响其他模型

## 技术方案概要

### 核心改动
在reasoning-only(仅思考内容,无实际输出)的场景下,延迟commit时机,允许网关层failover到其他候选节点。

### 关键代码位置
- `domains/streaming/responses_bridge.go`: 修改commit判定逻辑
- 影响范围: ~100行代码
- 测试覆盖: 新增10+单元测试

### 测试策略
1. **单元测试**: reasoning vs content区分
2. **集成测试**: 真实minimax模型测试
3. **回归测试**: 确保不影响其他模型
4. **压力测试**: 验证failover性能

### 部署计划
```
Week 1: 开发 + 单元测试
Week 2: 集成测试 + 代码审查
Week 3: Canary部署(211测试环境) + 监控
Week 4: 灰度10% → 50% → 100%
```

| no_candidates | 33 | 7% | 供给侧,正常 |

### 影响模型
- ✅ minimax-m3.1-flash: **100%受影响**
- ✅ 其他模型: 0%受影响

### 候选节点资源
minimax-m3.1-flash当前有**6个可路由候选节点**:
- Provider 14: 3个节点
- Provider 18: 2个节点  
- Provider 5917: 1个节点

方案A将充分利用这些候选,提高成功率。

## 监控指标

### 实施前指标(baseline)
```
openai_empty_response_total: 76次/7天 (11次/天)
minimax_m3.1_flash_success_rate: ~89%
user_retry_rate: 100% (需客户端重试)
```

### 目标指标
```
openai_empty_response_total: <10次/7天 (减少87%)
minimax_m3.1_flash_success_rate: >95%
gateway_failover_success_rate: >80%
user_retry_rate: <20% (仅failover失败时)
```

### 告警规则
- reasoning_only failover失败率 > 10% → P1告警
- openai_empty_response增长 > 20% → P2告警

## ROI分析

### 收益
- **用户体验改善**: 减少11次/天的手动重试
- **支持成本降低**: 减少相关咨询和投诉
- **品牌形象提升**: 体现技术能力和用户关怀

### 成本
- **开发**: 2人天 × 2人 = 4人天
- **测试**: 2人天 × 1人 = 2人天
- **部署监控**: 3周 × 0.2人 = 3人天
- **总计**: ~9人天

### ROI
假设每次手动重试造成的用户不满成本为¥1:
- 节省: 11次/天 × 30天 × ¥1 = ¥330/月
- 成本: 9人天 × ¥1000 = ¥9000(一次性)
- 回本周期: ~27个月

**注**: 实际价值更多体现在用户体验和满意度提升,难以量化。

## 风险与缓解

### 风险1: 改变commit时机可能影响延迟感知
**概率**: 低  
**影响**: 低  
**缓解**: reasoning内容仍实时流式传输,用户无感知

### 风险2: reasoning边界识别错误
**概率**: 低  
**影响**: 中  
**缓解**: 严格的单元测试 + 使用IR层正确标记

### 风险3: failover后响应不一致
**概率**: 中  
**影响**: 低  
**缓解**: 这是预期行为,与重试一致

### 风险4: 生产部署失败
**概率**: 低  
**影响**: 中  
**缓解**: 完整的回滚预案 + 特征开关

## 替代方案

### 方案B: 客户端优化 (当前方案)
- ✅ 已实施,正常工作
- ⚠️ 用户体验略差
- ⚠️ 需要客户端配合

- ⚠️ 用户体验持续不佳
- ⚠️ 可能流失minimax用户
