**P0-1　live-stream 空域身份的首帧永不置位　【已修复 `f94c7f36d`】**
`a1a1eba49` 把就绪判据改为 `env.type === 'initial_data' && Array.isArray(env.requests)`，但 `admin/live_stream_sse.go` 的 `Requests` 带 `omitempty`——`encoding/json` 对**零长度切片同样省略**。`h.replay` 无 DB 时返回 `nil`、无行时返回零长切片，于是安静的租户拿到的首帧**根本没有 `requests` 键**，`Array.isArray(undefined)` 为 false，`initialDataReceived` 永不置位：`awaitingInitialData` / `streamAwaitingData` / `coldStartText` 永久停在「接收首批数据中」，而连接其实已 open、后续 `request` 帧正常到达；唯一恢复手段是卸载重挂，而那会重演同一次握手。

**P0-2　迁移台账检出门在纯净检出上就是红的，主门中止　【已修复 `548cbae03`】**
`scripts/ledger-checksum-plaintext-scan.sh` 以 mode `100644` 提交，而 `tests/ledger_checksum_hex_transport_test.sh:30` 断言 `-x`；`verify.sh` 是 `set -euo pipefail` 且在 `:85` 调这道门。本轮实测 `bash tests/ledger_checksum_hex_transport_test.sh` → `rc=1`。检出器**逻辑**是对的（正反对照实测：表名+64hex 同行 → `rc=1` 命中；合规的 `convert_from(decode(...))` → `rc=0` 零命中），坏的只是 mode。

**P0-3　`set -e` + `source` 失败 + EXIT trap ⇒ 退出码 0（假绿原语）　【已修复 `548cbae03`】**
本机 bash 3.2.57 实测复现：

| 形态 | 退出码 | `source` 之后的断言 |
|---|---|---|
| 带 EXIT trap | **0** | **一行未跑** |
| 无 EXIT trap | 1 | 未执行 |

机制：`source` 失败触发 EXIT trap，trap 自身以 0 收尾，覆盖掉 `set -e` 原本要保留的非零码。仓库里 5 个测试脚本同时具备 `trap ... EXIT` 与顶层 `source`，其中 3 个挂在主门（`verify.sh:75/77`）。**这比红更危险**：门自称绿，实际零断言执行。
