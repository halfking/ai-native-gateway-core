# 01 — 网络层优化

> 目标：减少物理衰减与技术衰减，降低跨云/跨地域调度中的网络延迟与连接开销。

---

## 1. 专线与同地域部署

### 问题

调度系统与第三方算力源如果跨地域部署，公网传输会引入：
- 跨地域 RTT：北京 ↔ 乌兰察布 ~10ms、上海 ↔ 北京 ~30ms、跨国 ~100–300ms
- 公网 QoS 抖动：丢包率、带宽波动不可控
- 运营商间延迟：移动 ↔ 电信 ↔ 联通 跨网延迟可能高达 50ms+

### 方案

#### 1.1 同地域部署（推荐优先实施）

| 策略 | 说明 | 影响 |
|------|------|------|
| **同机房 / 同 VPC** | 调度网关与第三方算力源的 API 入口部署在同一数据中心 | RTT < 1ms，零公网开销 |
| **同地域不同可用区** | 同一城市的不同可用区（如北京 3 区 ↔ 北京 5 区） | RTT < 3ms |
| **同运营商同城市** | 无法同地域时，确保客户端与服务端在同一运营商 | 避免跨网延迟 |

**当前现状**：llm-gateway-go 部署在火山引擎（乌兰察布/上海），需要与各 MaaS 供应商确认 API 入口的地域分布，评估“是否已有同地域部署条件”。

#### 1.2 云企业网 (CEN) 专线

当同地域部署不可行时，通过云企业网/专线打通：

```
[ 调度网关 (乌兰察布) ] ──[ CEN 专线 ]── [ 第三方 API (上海) ]
```

- CEN 延迟 ~2–5ms（vs 公网 20–30ms），稳定性显著提升
- 需要与第三方 MaaS 供应商协调专线接入
- 适用场景：DeepSeek（上海）、Minimax（上海）、阿里通义（上海）

## 2. HTTP/3 (QUIC) 协议

### 问题

当前 `upstream/client.go` 使用 HTTP/1.1 + h2c (`upstream/client.go:96-110`)，所有跨云请求使用 TCP+TLS：

```
TCP 三次握手 (1 RTT) → TLS 1.3 握手 (1 RTT) → HTTP 请求/响应
```

对于跨云/公网场景，这 2–3 次 RTT 的建连开销在以下场景尤为显著：
- 短任务（如简单文本生成）：建连时间可能占整个请求的 10–30%
- 频繁切换凭据/候选（Executor 中逐 candidate 尝试）：重复建连叠加
- 跨云部署（RTT 30–100ms）：2–3 RTT = 60–300ms 纯建连延迟

### 方案

#### 2.1 quic-go 集成

```go
// upstream/quic_client.go (新增)
import "github.com/quic-go/quic-go/http3"

func NewQUICRoundTripper() *http3.RoundTripper {
    return &http3.RoundTripper{
        TLSClientConfig: &tls.Config{...},
        // QUIC 无需显式 Keep-Alive，0-RTT 恢复连接
    }
}
```

| 特性 | HTTP/1.1 + h2c | HTTP/3 (QUIC) | 收益 |
|------|---------------|---------------|------|
| 传输层 | TCP | QUIC (UDP) | 0-RTT 建连 |
| 队头阻塞 | 有 (TCP HOL) | 无 (QUIC stream 独立) | 丢包不影响其他流 |
| 连接迁移 | 不支持 | 原生支持 (Connection ID) | IP 变更不断连 |
| 加密 | TLS 1.3 (1-RTT) | QUIC 内置 (0-RTT) | 减少 1 次 RTT |

#### 2.2 Provider HTTP/3 支持矩阵

| 供应商 | HTTP/3 支持 | 优先级 |
|--------|------------|--------|
| OpenAI | ✅ (api.openai.com) | P1 |
| Anthropic | ✅ (api.anthropic.com) | P1 |
| DeepSeek | 部分 | P2 |
| Minimax | 未知 | P3 |
| 阿里 (DashScope) | ✅ | P2 |

#### 2.3 协议协商策略

```
1. 尝试 HTTP/3 (UDP 443)
2. 如果 UDP 被防火墙阻断 → fallback 到 HTTP/2 (h2c)
3. 如果 HTTP/2 不可用 → fallback 到 HTTP/1.1
```

通过 `ProxyResolver` 扩展机制实现：

```go
// upstream/protocol_negotiator.go (新增)
type Protocol int
const (
    ProtocolHTTP3  Protocol = 0
    ProtocolHTTP2  Protocol = 1
    ProtocolHTTP11 Protocol = 2
)

type ProtocolNegotiator struct {
    altSvcCache map[string]Protocol // 记录 alt-svc 协商结果
    mu          sync.RWMutex
}
```

## 3. 长连接连接池优化

### 3.1 当前架构分析

`pool/pool.go` 当前配置：

```go
maxIdleConnsPerHost = 16    // 每主机最大空闲连接数
maxConnsPerHost     = 64    // 每主机最大总连接数
idleConnTimeout     = 90s   // 空闲连接超时
healthCheckInterval = 30s   // 健康检查间隔
poolIdleTTL         = 3min  // 池空闲超时
```

`upstream/client.go` Transport 配置：

```go
MaxIdleConns:       128     // 全局最大空闲连接
ResponseHeaderTimeout: 30s  // 响应头超时
```

已具备的优化能力：
- ✅ 身份隔离的连接池（identity_hash + provider + credential 三级键）
- ✅ 连接健康探测与自动恢复
- ✅ LRU 淘汰（256 池上限）
- ✅ 池状态机：Active → Degraded → Draining → Dead

### 3.2 优化方向

#### 3.2.1 参数调优（跨云场景）

| 参数 | 当前值 | 建议值（跨云） | 理由 |
|------|--------|---------------|------|
| `MaxIdleConns` | 128 | 256—512 | 更多 Provider 缓存，减少回源建连 |
| `MaxIdleConnsPerHost` | 16 | 32—64 | 跨云场景每个 Host 需要更多复用 |
| `MaxConnsPerHost` | 64 | 128 | 提升并发上限 |
| `IdleConnTimeout` | 90s | 180s | 跨云 RTT 高，更长时间复用 |
| `poolIdleTTL` | 3min | 5min | 减少池重建开销 |

#### 3.2.2 跨云候选路由的预热

当前 Executor (`executor.go`) 在路由时遍历 candidate 列表，**每个新候选都要建立新连接**。优化：

```go
// pool/pool.go — 新增 Prewarm 方法
func (pm *PoolManager) Prewarm(ctx context.Context, keys []PoolKey) error {
    for _, key := range keys {
        p, err := pm.GetOrCreate(ctx, key)
        if err != nil {
            continue
        }
        // 提前建立 1–2 个空闲连接
        p.transport.MaxIdleConnsPerHost = maxIdleConnsPerHost
    }
    return nil
}
```

在 Executor 的 `PlanCandidates` 返回后，后台异步预热 top-K 候选池：

```go
// executor.go — 在 PlanCandidates 后异步预热
go func() {
    for _, c := range candidates[:min(3, len(candidates))] {
        key := PoolKey{
            IdentityHash: identityHash,
            ProviderID:   c.ProviderID,
            CredentialID: c.CredentialID,
        }
        poolManager.Prewarm(ctx, []PoolKey{key})
    }
}()
```

#### 3.2.3 双向连接复用 (HTTP/2 Multiplexing)

当前 h2c 已启用 (`cmd/gateway/main.go`)，HTTP/2 多路复用可以在**同一连接**上并发多个请求：

```
[ Client ] ── HTTP/2 (同一连接) ── [ 第三方 API ]
              ├── 请求1 (Stream 1)
              ├── 请求2 (Stream 3)
              └── 请求3 (Stream 5)
```

收益：不需要为每个并发请求建立独立 TCP 连接，减少跨云场景下的连接建立开销。

**优化项**：
- 确保 `MaxConcurrentStreams: 250`（当前已配置）实际生效
- 增加 `MaxIdleConnsPerHost` 以支持高并发场景
- 在 pool 级别添加并发流数量监控

#### 3.2.4 连接优先级调度

对"热"凭据（TTFB 历史好、成功率高、延迟低的候选）的连接给予优先级：

```go
// pool/pool.go — 新增优先级调度
type PoolPriority int

const (
    PriorityLow    PoolPriority = 0  // 冷备 candidate
    PriorityNormal PoolPriority = 1  // 普通 candidate
    PriorityHigh   PoolPriority = 2  // 活跃 candidate
)

func (p *Pool) SetPriority(pri PoolPriority) {
    // High: 保持连接活跃，减少空闲超时
    // Low: 更快回收连接
    switch pri {
    case PriorityHigh:
        p.transport.IdleConnTimeout = 5 * time.Minute
    case PriorityLow:
        p.transport.IdleConnTimeout = 30 * time.Second
    }
}
```

var (

| 指标 | 说明 | 目标 |

| 连接复用率 | `reused / (created + reused)` | > 90% |

| 连接创建速率 | 每秒新建连接数 | 趋势下降 |
