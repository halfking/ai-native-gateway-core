# 02 — 算力损耗补偿与架构优化

> 目标：通过流式传输优化和边缘调度架构，补偿不可消除的网络衰减，提升用户感知性能。

---

## 1. 流式传输优化 (Streaming)

### 1.1 当前能力

llm-gateway-go 已具备完善的 Streaming 基础设施：

| 组件 | 文件 | 能力 |
|------|------|------|
| SSE Streamer | `sse_streamer.go` | 通道式 chunk 分发 |
| Stream Reader | `stream_reader.go` | 带超时 + 上下文取消的 Line 读取 |
| 空流检测 | `stream.go:24-34` | 8 chunk / 64KB 缓冲，透明故障转移 |
| Pre-Stream Keepalive | `handler.go:59-80` | 上游响应前每 15s 发送 SSE 心跳 |
| 首字节超时 | `stream_runtime.go:39` | 30s first-byte-timeout |
| 协议转换 | `executor_chat.go` / `executor_anthropic.go` | OpenAI ↔ Anthropic ↔ Responses 全矩阵 |
| 超时自适应 | `timeout_adapter.go` | 基于请求大小 + Provider + TTFB 历史的自适应超时 |

### 1.2 强制 Stream 模式 (MaaS 销售要求)

#### 现状

当前 Stream 模式由客户端控制（请求中 `stream: true/false`），非 Stream 的请求会引入额外延迟：
- 非 Stream：必须等完整响应体生成后才返回 → TTFB = 完整生成时间
- Stream：首个 Token 在 ~200ms 内即可返回

#### 方案

在路由/分发层强制启用 Stream 模式，对客户端透明转换：

```
[ 客户端 (非Stream) ] → [ 调度网关 ] → [ 上游API (Stream) ]
                            ↓
                    [ 内部 Buffer ] ← 流式接收 chunk
                            ↓
                    [ 拼装完整响应 ] → 返回给客户端
```

```go
// domains/streaming/executors/executor.go — 流式强制模式
func (e *Executor) forceStreamIfEnabled(upstreamReq *http.Request) bool {
    if !e.forceStreaming {
        return false
    }
    // 将请求 body 中的 stream: false → stream: true
    // 在 BuildUpstreamRequest 阶段修改
    return true
}
```

**收益**：
- 非 Stream 请求的首字节等待时间从 "完整生成时间" → "首 Token 时间 + 缓冲时间"
- 对长输出场景（代码生成、长文写作），感知延迟降低 50–80%

**成本**：
- 需要一个内部缓冲层拼装完整响应
- 缓冲会增加少量内存开销（单请求最大 128MB，需注意 OOM 边界）

#### 内存安全边界

| 参数 | 建议值 | 理由 |
|------|--------|------|
| 单请求缓冲上限 | 128MB | 对齐 `maxBodySize` |
| 全局缓冲上限 | 2GB | 约 16 个大请求并行 |
| 超时 | 同 Stream timeout (900s) | 长任务不断连 |

#### Router P2C 增强

在 `router_scoring.go` 的 `calculateLatencyScore` 中，加入"最近 N 次 TTFB 中位数"因素，优先选择 TTFB 更低的凭据：

```go
func calculateLatencyScore(c provider.Candidate) float64 {
    // 当前：基于 MaxUsageWindowTTFB
    // 增强：结合 TTFBTracker 实时数据
    if c.MaxUsageWindowTTFB > 0 {
        p50 := ttfbTracker.Quantiles(c.CredentialID).P50
        ratio := float64(p50) / float64(5*time.Second) // 归一化到 0-1
        if ratio > 1.0 {
            ratio = 1.0
        }
        return ratio
    }
    return 0.5
}
```

#### Stream Chunk 零拷贝优化

当前 Stream 读取在 `stream.go:readStream` 中逐行读到 `[]byte`，经过多次拷贝：

```
upstream TCP → bufio.Scanner → []byte → SSE parser → json.Unmarshal → 协议转换 → http.ResponseWriter
```

优化方向：

1. **Writer 直通 (Zero-Copy)**：检测到无需协议转换时，直接从 upstream 的 `io.ReadCloser` 写入 ResponseWriter，跳过中间 JSON 解析
2. **预分配 Buffer**：对于已知的短 chunk 格式（如 OpenAI SSE），预分配固定大小 buffer 减少 GC
3. **避免反序列化**：某些字段（如 `model`、`created`）在首 chunk 后不再变化，缓存解析结果

```go
// 直通模式检测
func (e *Executor) canZeroCopy(clientFmt, upstreamFmt ProviderFormat) bool {
    if clientFmt == upstreamFmt && !e.qualityFixMode && !e.vendorFieldStripping {
        return true // 无需协议转换 + 无需质量修复 + 无需字段清理 → 直通
    }
    return false
}
```

#### Chunk 缓冲策略

当前空流检测有 8 chunk / 64KB 缓冲，对首 Token 有负面影响：

| 场景 | 建议 | 理由 |
|------|------|------|
| 首请求（无历史） | 缓冲 2 chunk / 4KB | 快速透传首 Token |
| 已有成功流历史 | 缓冲 0 （直通） | 已经验证的流无需缓冲 |
| 已知高失败率 Provider | 保持 8 chunk / 64KB | 需要空流检测保护 |

```go
// domains/streaming/stream.go — 自适应缓冲
type StreamGateConfig struct {
    InitialBufferChunks int     // 默认 2
    InitialBufferBytes  int     // 默认 4KB
    MaxBufferChunks     int     // 默认 8
    MaxBufferBytes      int     // 默认 64KB
}

func shouldUseFullGate(providerID int, history *credentialstate.StateProvider) bool {
    // 如果该 provider 在过去 5 分钟内无空流失败 → 使用轻量缓冲
    // 如果该 provider 空流率 > 5% → 使用完整缓冲
}
```

### 1.4 Keepalive 策略优化

当前 pre-stream keepalive 间隔固定 15s。建议自适应：

| 条件 | 间隔 | 理由 |
|------|------|------|
| 客户端超时 > 120s | 30s | 减少心跳开销 |
| 客户端超时 60–120s | 15s | 默认 |
| 客户端超时 < 60s | 5s | 防止客户端超时断开 |
| 高质量网络 | 30s | 低丢包率下不需要高频心跳 |

## 2. 边缘调度 (Edge Scheduling)

### 2.1 问题

当前所有请求的完整路径：

```
[ 客户端 ] → [ 调度网关 (火山引擎) ] → [ 第三方 API ]
                ↑
            鉴权 + 限流 + 分发 (串行)
```

无论客户端在何处，请求都需要**回源到中心集群**完成鉴权和调度。

代价：
- 中国境内客户端 → 火山引擎乌兰察布：RTT ~30–50ms
- 海外客户端 → 火山引擎乌兰察布/上海：RTT ~100–200ms
- 集中式鉴权成为瓶颈（单节点处理所有请求）

### 2.2 边缘调度方案

#### 2.2.1 架构

```
[ 客户端 ] → [ Edge Gateway (CDN边缘节点) ]
                   │
                   ├─ 鉴权 (本地缓存)
                   ├─ 限流 (本地 Rate Limiter)
                   ├─ 路由决策 (本地 Rule Cache)
                   │
                   ├─ 直接转发 → [ 第三方 API ] (就近接入)
                   │
                   └─ 回源 (仅复杂请求) → [ 中心 Gateway ]
```

**核心原则**：将"无状态"的鉴权和调度决策下沉到边缘，请求无需回源即可完成。

#### 2.2.2 分层职责

| 层 | 职责 | 状态要求 |
|------|------|---------|
| **Edge Gateway** | API Key 验证（缓存）、Rate Limit（本地滑动窗口）、路由决策（缓存 Rule → 直连上游） | 无状态（数据从中心同步） |
| **Layer 7 LB** | TLS termination、Header 路由、灰度分流 | 无状态 |
| **中心 Gateway** | 复杂策略（多级降级、预算控制、Session Management）、非 Streaming 请求、Fallback 兜底 | 有状态（Session/DB） |

#### 2.2.3 可下放的调度逻辑

| 逻辑 | 当前位置 | 可否下放 | 实现方式 |
|------|---------|---------|---------|
| API Key 验证 | `domains/authentication/verifier.go` | ✅ 可 | Key 哈希缓存到 Edge |
| Rate Limit | `ratelimit/` | ✅ 可 (本地 + 中心两级) | 本地滑动窗口 + 周期性同步 |
| 模型策略 (Block/Allow) | `internal/modelpolicy/` | ✅ 可 | Policy 规则缓存 |
| TTFB 追踪 | `executors/ttfb_tracker.go` | ⚠️ 部分 | 本地缓存 + 异步上报中心 |
| 健康探测 | `pool/pool.go` | ✅ 可 | 边缘节点独立健康探测 |
| Session 管理 | `domains/session/` | ❌ 不可 | 需中心协调 |
| 预算控制 | `provider/billing.go` | ❌ 不可 | 需中心协调 |
| 品质修复 | `executor.go` qualityFix | ⚠️ 部分 | 规则可缓存，但修复可能需回源 |

#### 2.2.4 缓存同步机制

Edge Gateway 需要从中心同步的缓存：

| 缓存 | 更新频率 | 同步方式 |
|------|---------|---------|
| API Key 列表 | 分钟级 | Redis Pub/Sub → Edge |
| 模型策略规则 | 变更时推送 | Config Watch → Edge |
| 限流配额 | 秒级增量 | 异步上报 + 中心聚合 |
| TTFB 历史 | 分钟级 | Edge 本地记录 + 异步上报 |
| Provider 健康状态 | 30s | 边缘节点独立探测 |

### 2.3 部署形态

#### 2.3.1 CDN Edge (轻量)

利用现有 CDN 节点的计算能力：

```
[ 客户端 ] → [ CDN Edge (Function Compute) ] → [ 第三方 API ]
                       |
          鉴权缓存 + 规则缓存 (KV Store)
```

适合：读多写少的鉴权 + 简单路由

#### 2.3.2 Sidecar 模式

在每个 Provider 同地域部署轻量 Sidecar：

```
[ Provider A (乌兰察布) ]
    └── [ 调度 Sidecar ] ── 仅处理 → Provider A 的请求

[ Provider B (上海) ]
    └── [ 调度 Sidecar ] ── 仅处理 → Provider B 的请求

[ 中心 Gateway ] ── 兜底 / 复杂策略
```

适合：高流量 Provider（如 DeepSeek、OpenAI）

### 2.4 阶段性实施计划

| 阶段 | 内容 | 收益 | 复杂度 |
|------|------|------|--------|
| **Phase 1** | API Key 缓存下沉到 Edge Layer 7 LB | 减少 30% 回源 | 小 |
| **Phase 2** | Rate Limit 两级架构（Edge 本地 + 中心聚合） | 减少 50% 回源 | 中 |
| **Phase 3** | 路由规则缓存 + 边缘独立健康探测 | 简单请求无需回源 | 中 |
| **Phase 4** | 完整 Edge Gateway 部署 + Session 穿透 | 80%+ 请求无需回源 | 大 |
