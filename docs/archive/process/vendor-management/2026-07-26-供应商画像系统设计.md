# 供应商画像系统设计方案

**文档版本**: v1.0  
**创建日期**: 2026-07-26  
**作者**: AI Assistant  
**状态**: 待审核

## 1. 概述

### 1.1 背景

LLM网关当前缺少对供应商的多维度质量评估体系。需要建立一套完善的供应商画像系统，从网络延迟、模型可信度、可用性、稳定性、规模、费用准确性、价格等7个维度对供应商进行持续监控和评分，帮助运维团队识别问题供应商，并支持自动化处理。

### 1.2 目标

1. **多维度评估**: 建立7个维度的评分体系，全面评估供应商质量
2. **持续监控**: 通过混合采样策略（轻量级高频 + 重量级低频）持续收集数据
3. **历史追踪**: 保存365天历史数据，支持趋势分析
4. **智能告警**: 检测分数异常变化和持续下降趋势，自动禁用问题供应商
5. **可视化展示**: 在管理界面展示评分、趋势、时段差异等信息

### 1.3 核心指标

| 维度 | 权重 | 说明 |
|------|------|------|
| 网络延迟 | 10% | baseurl的请求网络延迟（P95） |
| 模型可信度 | 15% | 模型真实性、合规性、稳定性、版本一致性 |
| 可用性 | 20% | 成功率、首字时间、完成时长 |
| 稳定性 | 20% | 错误率、错误类型分布 |
| 规模 | 5% | 模型总数、可用模型数 |
| 费用准确性 | 15% | 与供应商账单对账准确度 |
| 价格 | 15% | 价格竞争力 |

**评分标准**: 所有维度均为0-100分，总分为加权平均值。

### 2.2 数据流

1. **采集阶段**
   - 轻量级采集器每2小时执行一次，收集网络延迟、可用性、稳定性、规模指标
   - 重量级采集器每天2次（凌晨2点、下午2点），执行模型可信度测试
   - 数据写入 `provider_profile_metrics` 和 `provider_credibility_tests` 表

2. **聚合阶段**
   - 每日凌晨4点，聚合器读取前一天的小时级数据
   - 计算各维度评分，计算总分
   - 分析时段差异，计算波动指标
   - 写入 `provider_profile_daily` 表

3. **告警阶段**
   - 聚合完成后，告警引擎检测分数变化
   - 触发相对变化告警、趋势告警、维度告警
   - 执行自动处理动作（禁用/恢复）
   - 写入 `provider_profile_alerts` 表

### 2.3 复用现有系统

- **探测框架**: 复用现有的后端自检探测框架和调度机制
- **数据源**: 从 `model_probe_runs_hot`、`credentials`、`sessions` 等表读取现有数据
- **工具函数**: 复用 `probeProvider`、`doChatProbe` 等现有函数
- **并存模式**: 与现有诊断功能并存，互不影响

## 3. 数据模型设计

### 3.1 核心表结构

#### provider_profile_metrics（小时级原始数据）

存储每次采集的原始指标数据，保留7天。

```sql
CREATE TABLE provider_profile_metrics (
    id BIGSERIAL PRIMARY KEY,
    credential_id BIGINT NOT NULL,
    provider_id BIGINT NOT NULL,
    metric_time TIMESTAMPTZ NOT NULL,
    time_slot TEXT NOT NULL, -- dawn/morning/afternoon/evening/night
    
    -- 网络延迟维度 (ms)
    network_latency_p50 INTEGER,
    network_latency_p95 INTEGER,
    network_latency_p99 INTEGER,
    
    -- 可用性维度
    availability_total_requests INTEGER DEFAULT 0,
    availability_success_requests INTEGER DEFAULT 0,
    availability_ttft_avg_ms INTEGER,
    availability_duration_avg_ms INTEGER,
    
    -- 稳定性维度
    stability_error_count INTEGER DEFAULT 0,
    stability_error_types JSONB,
    
    -- 规模维度
    scale_total_models INTEGER,
    scale_available_models INTEGER,
    
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_ppm_credential_time ON provider_profile_metrics(credential_id, metric_time DESC);
CREATE INDEX idx_ppm_provider_time ON provider_profile_metrics(provider_id, metric_time DESC);
CREATE INDEX idx_ppm_cleanup ON provider_profile_metrics(created_at) 
    WHERE created_at < NOW() - INTERVAL '7 days';
```

## 4. 评分算法设计

### 4.1 维度权重配置

```go
type ProfileWeights struct {
    Network        float64 // 0.10 - 网络延迟
    Credibility    float64 // 0.15 - 模型可信度
    Availability   float64 // 0.20 - 可用性
    Stability      float64 // 0.20 - 稳定性
    Scale          float64 // 0.05 - 规模
    CostAccuracy   float64 // 0.15 - 费用准确性
    Price          float64 // 0.15 - 价格
}

type CredibilityWeights struct {
    Authenticity  float64 // 0.35 - 真实性
    Compliance    float64 // 0.25 - 合规性
    Consistency   float64 // 0.25 - 能力稳定性
    Version       float64 // 0.15 - 版本一致性
}
```

### 4.2 各维度评分算法

#### 4.2.1 网络延迟评分

基于P95延迟计算，使用分段线性函数：

| P95延迟 | 得分 |
|---------|------|
| ≤ 100ms | 100分 |
| 100-300ms | 100-80分（线性递减） |
| 300-1000ms | 80-50分（线性递减） |
| 1000-3000ms | 50-0分（线性递减） |
| > 3000ms | 0分 |

#### 4.2.2 可用性评分

综合成功率、首字时间、完成时长三个子指标：

**公式**: 成功率×70% + TTFT评分×15% + 完成时长评分×15%

- **成功率**: 成功请求数 / 总请求数 × 100
- **TTFT评分**:
  - ≤500ms: 100分
  - 500-2000ms: 100-50分
  - 2000-5000ms: 50-0分
  - >5000ms: 0分
- **完成时长评分**:
  - ≤5s: 100分
  - 5-15s: 100-50分
  - 15-30s: 50-0分
  - >30s: 0分

#### 4.2.3 稳定性评分

基于错误率计算，并考虑错误类型严重程度：

**基础分**:
| 错误率 | 基础分 |
|--------|--------|
| ≤1% | 100分 |
| 1-5% | 100-80分 |
| 5-15% | 80-40分 |
| 15-30% | 40-0分 |
| >30% | 0分 |

**严重错误惩罚**: 5xx错误每1%扣10分

#### 4.2.4 规模评分

**公式**: 可用率×60% + 模型数量评分×40%

- **可用率**: 可用模型数 / 总模型数 × 100
- **模型数量评分**:
  - ≥50个: 100分
  - 20-50个: 80-100分
  - 10-20个: 60-80分
  - 5-10个: 40-60分
  - <5个: 0-40分

#### 4.2.5 费用准确性评分

对比网关统计与供应商账单的token和费用差异：

**差异率** = MAX(|网关tokens - 供应商tokens| / 供应商tokens, |网关费用 - 供应商费用| / 供应商费用)

| 差异率 | 得分 |
|--------|------|
| ≤5% | 100分 |
| 5-10% | 100-80分 |
| 10-20% | 80-40分 |
| 20-50% | 40-0分 |
| >50% 或缺失数据 | 0分 |

#### 4.2.6 价格评分

与市场平均价格对比：

**价格比率** = 供应商价格 / 市场平均价格

| 价格比率 | 得分 | 说明 |
|----------|------|------|
| ≤0.3 | 60分 | 过低可疑 |
| 0.3-0.5 | 100分 | 50%折扣 |
| 0.5-0.7 | 95分 | 30%折扣 |
| 0.7-1.0 | 90-80分 | 平价 |
| 1.0-1.5 | 80-50分 | 小幅溢价 |
| 1.5-2.0 | 50-20分 | 较高溢价 |
| >2.0 | 20分 | 溢价过高 |

#### 4.2.7 模型可信度评分

综合4个子维度：

**公式**: 真实性×35% + 合规性×25% + 稳定性×25% + 版本一致性×15%

子维度评分由具体测试套件计算（详见第6节）。

### 4.3 总分计算

**加权平均**，缺失维度不参与计算（权重重新分配）：

```
总分 = Σ(维度分数 × 维度权重) / Σ(有效维度权重)
```

**特殊规则**: 费用准确性维度缺失数据时按0分计算（直接扣分）。

## 5. 数据采集架构

### 5.1 采集策略

采用**混合采样策略**，平衡成本和准确性：

| 指标类型 | 采集频率 | 采集方式 |
|----------|----------|----------|
| 网络延迟 | 每2小时 | 轻量级采集器 |
| 可用性 | 每2小时 | 复用现有请求数据 |
| 稳定性 | 每2小时 | 复用现有请求数据 |
| 规模 | 每2小时 | 查询provider_models表 |
| 模型可信度 | 每天2次（凌晨2点、下午2点） | 重量级采集器 |
| 费用准确性 | 每月1次 | 手动录入或API获取 |
| 价格 | 实时 | 查询provider配置 |

### 5.2 轻量级采集器

**职责**: 收集网络延迟、可用性、稳定性、规模指标

**执行流程**:
1. 获取所有活跃 credentials
2. 并发采集（最多10个并发）
3. 对每个 credential:
   - 探测 `/v1/models` 端点3次，计算P50/P95/P99延迟
   - 从最近2小时的请求日志聚合可用性和稳定性数据
   - 查询 provider_models 表获取规模数据
4. 保存到 `provider_profile_metrics` 表

**复用现有功能**:
- 复用 `probeProvider` 函数探测网络延迟
- 从 `sessions` 或 `request_logs` 表聚合请求统计
- 复用探测调度框架

### 5.3 重量级采集器

**职责**: 执行模型可信度测试

**执行流程**:
1. 每天凌晨2点和下午2点执行（高峰期和低峰期各一次）
2. 获取所有活跃 credentials
3. 对每个 credential:
   - 获取该供应商的活跃模型列表
   - 对每个模型执行4种测试套件（详见第6节）
   - 保存测试结果到 `provider_credibility_tests` 表

**测试套件**:
- **第一期**:
  1. 能力探针测试（CapabilityProbeSuite）
  2. 成本倒推分析（CostAnalysisSuite）
- **第二期**:
  3. 标准测试集（StandardTestSetSuite）
  4. 输出指纹分析（FingerprintAnalysisSuite）

### 5.4 调度器集成

在网关启动时注册定时任务：

```go
// 轻量级采集：每2小时
scheduler.AddJob("profile:collect:lightweight", "0 */2 * * *", ...)

// 重量级采集：每天凌晨2点和下午2点
scheduler.AddJob("profile:collect:heavyweight", "0 2,14 * * *", ...)

// 每日聚合：每天凌晨4点
scheduler.AddJob("profile:aggregate:daily", "0 4 * * *", ...)

// 清理过期数据：每周日凌晨5点
scheduler.AddJob("profile:cleanup", "0 5 * * 0", ...)
```

## 6. 模型可信度测试详细设计

模型可信度是最复杂的维度，包含4个子维度，通过4种测试套件验证。

### 6.1 测试套件架构

```go
type CredibilityTestSuite interface {
    Name() string
    Phase() int // 1=第一期, 2=第二期
    Test(ctx context.Context, cred *Credential, model string) (*TestResult, error)
}

type TestResult struct {
    AuthenticityScore float64 // 真实性得分
    ComplianceScore   float64 // 合规性得分
    ConsistencyScore  float64 // 稳定性得分
    VersionScore      float64 // 版本一致性得分
    TestDetails       []TestDetail
    Anomalies         []Anomaly
}
```

### 6.2 第一期：能力探针测试

**目标**: 验证模型声称的能力是否真实存在

**测试项**:

1. **Function Calling能力**
   - 构造带tools参数的请求
   - 验证响应是否包含tool_calls
   - 不支持但声称支持：记录异常

2. **流式输出能力**
   - 测试stream=true参数
   - 验证是否返回SSE流
   - 不支持但声称支持：记录异常

3. **上下文长度验证**
   - 发送接近声称上下文长度的请求
   - 观察是否正常处理或截断
   - 实际长度明显低于声称：记录严重异常

4. **基础推理能力**
   - 使用简单推理题测试（如"9.11和9.9哪个更大？"）
   - 验证不是随机响应
   - 多次推理失败：记录严重异常

**评分**: 通过率 × 100分，计入真实性维度

### 6.3 第一期：成本倒推分析

**目标**: 通过价格和质量推断模型真实性

**分析逻辑**:
1. 获取模型官方价格和供应商价格
2. 计算折扣率 = 供应商价格 / 官方价格
3. 评估:
   - <30%: 60分，记录警告（可能模型替换）
   - 30-100%: 70-100分（合理折扣）
   - >100%: 扣分但不算异常（溢价）

**评分**: 计入一致性维度

### 6.4 第二期：标准测试集

**目标**: 使用预定义测试集验证输出质量和合规性

**合规性测试**:

1. **过度审查检测**
   - 提示: "请写一段关于网络安全的技术文章开头"
   - 验证: 不应拒绝正常请求
   - 包含"无法"、"拒绝"等词：扣分

2. **额外系统提示检测**
   - 提示: "请只回答数字：1+1=?"
   - 期望: 简洁回答"2"
   - 回答过长（>50字符）：可能添加了系统提示

3. **敏感词替换检测**
   - 提示: "介绍一下OpenAI公司"
   - 验证: 应包含原词"OpenAI"
   - 关键词被替换：扣分

**版本一致性测试**:

1. **知识截止日期验证**
   - 提示: "What is your knowledge cutoff date?"
   - 提取日期并与模型版本对比
   - 不一致或无法回答：扣分

**评分**: 合规性和版本一致性各自计算平均分

### 6.5 第二期：输出指纹分析

**目标**: 建立模型输出指纹，检测模型是否被替换

**指纹特征**:
1. **平均响应长度**
2. **平均句子长度**
3. **标点符号密度**
4. **是否使用列表/编号**
5. **开头风格**（如"当然"、"好的"等礼貌用语）

**执行流程**:
1. 首次测试时建立基线指纹，保存到数据库
2. 后续测试时收集当前指纹
3. 计算相似度（0-1）
4. 相似度<70%: 记录严重异常

**评分**: 相似度 × 100分，计入版本一致性维度

### 6.6 异常检测和记录

所有测试套件在发现异常时记录到 `anomalies` 字段：

```json
{
  "severity": "critical|warning|info",
  "category": "authenticity|compliance|consistency|version",
  "description": "异常描述",
  "evidence": { "详细证据" }
}
```

严重异常（critical）会在前端界面特别标识。

## 7. 聚合计算与评分引擎

### 7.1 每日聚合任务

**执行时间**: 每天凌晨4点（在重量级采集之后）

**处理流程**:
1. 获取前一天有数据的所有 credentials
2. 对每个 credential:
   - 从 `provider_profile_metrics` 聚合小时级数据
   - 从 `provider_credibility_tests` 获取可信度测试结果
   - 从 `provider_cost_reconciliation` 获取费用对账数据
   - 计算各维度评分
   - 计算总分（加权平均）
   - 分析时段差异
   - 保存到 `provider_profile_daily`
3. 触发告警检测

### 7.2 聚合逻辑

#### 网络延迟聚合

```sql
SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY network_latency_p95) as p95_median
FROM provider_profile_metrics
WHERE credential_id = ? AND metric_time >= ? AND metric_time < ?
```

取当天所有采样点P95的中位数。

#### 可用性和稳定性聚合

```sql
SELECT 
    SUM(availability_total_requests) as total,
    SUM(availability_success_requests) as success,
    AVG(availability_ttft_avg_ms) as avg_ttft,
    AVG(availability_duration_avg_ms) as avg_duration,
    SUM(stability_error_count) as errors,
    jsonb_object_agg(error_type, error_count) as error_types
FROM provider_profile_metrics
WHERE credential_id = ? AND metric_time >= ? AND metric_time < ?
```

汇总当天所有请求统计。

#### 规模聚合

取当天最后一次采样的值（最新值）。

#### 可信度聚合

```sql
SELECT 
    AVG(authenticity_score) as authenticity,
    AVG(compliance_score) as compliance,
    AVG(consistency_score) as consistency,
    AVG(version_score) as version
FROM provider_credibility_tests
WHERE credential_id = ? AND test_time >= ? AND test_time < ?
```

对当天所有模型的测试结果求平均。

### 7.3 时段分析

将采样点按时段分组（dawn/morning/afternoon/evening/night），分别计算每个时段的总分：

1. 筛选该时段的所有采样点
2. 聚合轻量级指标（网络、可用性、稳定性、规模）
3. 计算该时段的评分（仅使用轻量级指标权重）
4. 保存到 `timeslot_scores` JSON字段

**时段定义**:
- dawn: 00:00-06:00
- morning: 06:00-12:00
- afternoon: 12:00-18:00
- evening: 18:00-22:00
- night: 22:00-24:00

**波动性指标**:
- `score_stddev`: 各时段分数的标准差
- `best_timeslot`: 分数最高的时段
- `worst_timeslot`: 分数最低的时段

## 8. 告警与自动处理机制

### 8.1 告警配置

```go
type AlertConfig struct {
    // 相对变化阈值
    ScoreDropThreshold24h float64 // 默认20分
    ScoreDropThreshold7d  float64 // 默认30分
    
    // 趋势告警阈值
    ContinuousDropDays int     // 默认3天
    TrendDropTotal     float64 // 默认15分
    
    // 自动禁用阈值
    AutoDisableThreshold      float64 // 默认40分
    AutoDisableAvailThreshold float64 // 默认50分
    AutoDisableContinuousDays int     // 默认3天
    
    // 自动恢复阈值
    AutoEnableThreshold      float64 // 默认70分
    AutoEnableContinuousDays int     // 默认3天
    
    // 白名单
    Whitelist []int64 // provider_id列表
}
```

### 8.2 告警类型

| 告警类型 | 触发条件 | 级别 |
|----------|----------|------|
| score_drop | 24小时内下降≥20分 或 7天内下降≥30分 | warning/critical |
| trend_drop | 连续3天下降，累计≥15分 | critical |
| dimension_low | 可用性或稳定性<60分 | critical |
| auto_disabled | 自动禁用供应商 | critical |
| auto_enabled | 自动恢复供应商 | info |

### 8.3 自动处理规则

#### 自动禁用条件（满足任一即触发）

1. **总分持续低分**
   - 总分<40分 且 连续3天
   
2. **可用性过低**
   - 可用性评分<50分（立即触发）

#### 自动恢复条件

- 总分≥70分 且 连续3天

**注意**: 
- 白名单供应商不会被自动禁用
- `manual_disabled=true` 的供应商不会被自动恢复（需人工审核）

### 8.4 处理动作

**禁用动作**:
1. 设置 `credentials.enabled = FALSE`
2. 记录 `auto_disabled_at` 和 `auto_disabled_reason`
3. 保存告警到 `provider_profile_alerts`
4. 记录事件到 `provider_events`

**恢复动作**:
1. 设置 `credentials.enabled = TRUE`
2. 记录 `auto_enabled_at` 和 `auto_enabled_reason`
3. 清除 `auto_disabled_*` 字段
4. 保存告警（info级别）

### 8.5 告警展示

在前端界面显示：
- 未解决告警数量徽章
- 告警列表（可筛选已解决/未解决）
- 告警详情（分数变化、触发原因、已采取动作）
- 时间线视图（在趋势图上标记告警点）

| 性能影响网关 | 高 | 异步执行，资源限制，独立监控 |
| 前端展示性能 | 中 | 数据聚合，虚拟滚动，按需加载 |

## 12. 监控和运维

### 12.1 系统监控指标

**采集器监控**:
- 轻量级采集成功率/失败率
- 重量级采集成功率/失败率
- 采集耗时（P50/P95/P99）
- 并发采集任务数

**聚合器监控**:
- 每日聚合处理的credential数量
- 聚合耗时
- 聚合失败次数

**告警引擎监控**:
- 每日产生的告警数量（按类型、级别）
- 自动禁用/恢复次数
- 告警处理延迟

**数据量监控**:
- `provider_profile_metrics` 表大小和行数
- `provider_profile_daily` 表大小和行数
- 数据清理任务执行情况

### 12.2 告警配置

**系统告警**（发送给开发团队）:
- 采集器连续失败>10次
- 聚合任务失败
- 数据表空间不足
- 查询性能异常（慢查询）

**业务告警**（发送给运维团队）:
- 供应商被自动禁用
- 高优先级供应商评分下降>30分
- 严重的模型可信度异常

### 12.3 运维操作

**日常运维**:
- 每周查看供应商评分趋势报告
- 每月审核自动处理日志
- 每月录入费用对账数据
- 每季度审核白名单

**应急处理**:
- 误禁用恢复：手动设置 `enabled=true` 并标记 `manual_disabled=false`
- 暂停自动处理：将供应商加入白名单
- 调整告警阈值：更新配置并重启服务

**数据维护**:
- 手动触发数据清理：删除过期的小时级数据
- 重新计算评分：修复聚合错误
- 导出历史数据：用于分析和审计

### 12.4 日志记录

**关键操作日志**:
- 自动禁用/恢复操作（带完整上下文）
- 告警触发（带详细原因）
- 费用对账数据录入
- 白名单变更

**调试日志**:
- 采集详细过程
- 评分计算详细步骤
- 可信度测试详细结果

## 14. 总结

供应商画像系统通过7个维度全面评估供应商质量，采用混合采样策略平衡成本和准确性，支持365天历史追踪和智能告警，能够自动禁用问题供应商并在恢复后自动重启。

**核心价值**:
1. **可见性**: 全面了解供应商真实质量
2. **可控性**: 自动化处理降低运维负担
3. **可追溯**: 历史数据支持问题回溯和趋势分析
4. **可优化**: 持续监控支持供应商选择和路由优化

**关键创新**:
1. **模型可信度测试**: 业内首创的多维度模型真实性验证
2. **分层存储**: 小时级+天级数据，兼顾细节和成本
3. **时段差异分析**: 识别不同时段的质量波动
4. **智能告警**: 相对变化+趋势检测，减少误报
