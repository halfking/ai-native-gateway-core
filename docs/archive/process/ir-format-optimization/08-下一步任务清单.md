### 3. ClientCatalogCode 路由层注入
**优先级**: P1
**预计工时**: 4-6 小时
**前置条件**: 路由层架构熟悉
**交付物**:
- 修改 routing 解析逻辑，记录客户端入口 provider
- `ExecParams.ClientCatalogCode` 或 `TransportContext.ClientCatalogCode` 填充
- 完整回归测试

**任务细节**:
1. 审计 routing 层：确认在哪个阶段可以获取客户端入口 provider/credential
2. 设计注入点：
   - 选项 A：扩展 `ExecParams` 新增 `ClientCatalogCode` 字段
   - 选项 B：在 executor 执行前填充 `TransportContext.ClientCatalogCode`
3. 处理特殊场景：
   - 匿名请求（无 credential）→ `ClientCatalogCode = ""`
   - Multi-tenant 路由 → 从 client identity 推断 provider
4. 测试矩阵：
   - Same provider + same protocol → restore extensions
   - Same provider + cross protocol → drop extensions
   - Cross provider + same protocol → drop extensions
   - Cross provider + cross protocol → drop extensions

**验证标准**:
- `go test ./... -count=1` 全仓通过
- 新增 4 个集成测试覆盖测试矩阵
- 无性能回归（路由层耗时 < +5ms）

## P2 中期任务

### 4. ProviderProfile 表与 Allowlist 配置
**优先级**: P2
**预计工时**: 6-8 小时
**依赖**: 任务 2 (Capture) 完成

**任务细节**:
1. 设计 `provider_profile` 表：
   ```sql
   CREATE TABLE provider_profile (
       id SERIAL PRIMARY KEY,
       catalog_code TEXT NOT NULL,
       endpoint TEXT NOT NULL,
       model_family TEXT,
       protocol TEXT NOT NULL,
       request_allowlist JSONB, -- {"top_level": [...], "nested": {...}}
       response_allowlist JSONB,
       headers_allowlist TEXT[], -- RequestExtensions.Headers
       created_at TIMESTAMPTZ DEFAULT NOW(),
       updated_at TIMESTAMPTZ DEFAULT NOW(),
       UNIQUE(catalog_code, endpoint, model_family, protocol)
   );
   ```
2. 从 verified capture 自动生成 allowlist：
   - 读取 `capture/_capture_meta.json` 的 `verified_fields`
   - 生成 profile 初始配置
3. IR converter 接入 profile allowlist：
   - `restoreRequestExtensions` 检查 `request_allowlist`
   - `restoreExtensions` (response) 检查 `response_allowlist`
4. RequestExtensions.Headers 接入 `headers_allowlist`

**验证标准**:
- 未在 allowlist 的字段不会被恢复
- Profile 可以按 endpoint/model_family 精细控制
- 有审计日志记录 allowlist 变更
