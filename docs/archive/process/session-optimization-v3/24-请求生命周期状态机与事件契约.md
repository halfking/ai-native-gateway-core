# 24 — 请求生命周期状态机与事件契约（V3.3-OBS）

> 状态：CURRENT（规范冻结稿，2026-08-15）
> 上游：23 号总体方案。本文冻结"动作事件"词汇表、请求状态机、SSE envelope 扩展与 Redis 回放队列契约。

## 1. 请求状态机（对外可见态）

一个客户端请求（request_id）在实时请求流中的可见状态：

```
arriving → routing → queued(model) → queued(node) → forwarding
                │                                        │
                ├─ model_switch（auto/无可用节点切模型）      ├─ node_switch（节点切换/重试）
                └─ no_route → rejected(503)               ├─ first_byte → streaming → done(success)
                                                         └─ failed(error_kind)
```

- `model_switch` / `node_switch` 不产生新 request_id；它们是同一请求的动作事件。
- 重试（retry_seq 递增）与节点切换共用 `node_switch` 通道，`retry: true` 时前端打特别标。
- probe 请求复用同一状态机，附加 `request_type: probe` 与 `probe_origin`。

## 2. 动作事件词汇表（与 internal/trace 阶段对齐）

| action | 语义 | 关键字段 |
| --- | --- | --- |
| `arrive` | 客户端请求到达网关（S1） | client_protocol, model(原始) |
| `route_resolved` | 模型解析完成（auto 决策/别名/直通）（S3） | model(resolved), auto_decision? |
| `model_enqueued` | 落入模型队列（S4） | model, queue_depth |
| `credential_selected` | 路由选定凭据（S5） | credential_id, weight, tier |
| `node_enqueued` | 落入节点（凭据）队列（S6） | credential_id, queue_depth |
| `node_selected` | 最终选定节点（S7 前） | credential_id, sticky? |
| `upstream_request` | 开始转发（S7） | credential_id, attempt |
| `first_byte` | 收到首字节（S8） | ttfb_ms |
| `reply` | 收到回复/完成（S9，含错误） | status, error_kind?, latency_ms |
| `node_switch` | 切换节点/重试 | from_credential_id, to_credential_id, reason, retry(bool), retry_seq |
| `model_switch` | 切换模型 | from_model, to_model, reason(auto/no_node) |
| `state_change` | 节点状态变更（旁路投影） | credential_id, field, old, new |
| `no_route` | 无可用路由 | blocked_reasons[] |

规则：
- `state_change` 是节点维度事件（不挂请求），走 `node_update`/`state_transition` 通道；其余都是请求维度。
- 事件 `seq` 在 request_id 内单调递增；前端按 seq 排序，不按到达序。
- 所有字段 optional + 向后兼容（继承 13 号契约原则）。

## 3. SSE envelope 扩展

在既有 8 种事件类型上新增 2 种（全部 optional 字段，旧客户端忽略未知类型即兼容）：

```jsonc
{
  "type": "request_lifecycle",        // 请求维度动作事件（§2 词汇表）
  "ts": "...",
  "action": { /* §2 的一行 */ }
}
{
  "type": "child_request",            // 主从关系建立/更新（title/summary/sensitive_word）
  "ts": "...",
  "parent_request_id": "...",
  "request": { /* 与 request 事件同构 */ }
}
```

`child_request` 语义约束（OBS-DV2 #4 收敛）：
- 它是以 `(parent_request_id, request_id)` 为键的**幂等 upsert 生命周期帧**：同一子请求会因「初始 in_progress 写入」与「终态 terminal 写入」各发一帧，前端按 `(parent_request_id, request_id)` 去重聚合即可建立父子树。**两帧都是期望契约语义，不是重复。**
- 父请求行正文仍伴生 legacy `request` 帧（保持向后兼容），`child_request` 是新增的关系视图，二者并存。
- **Redis self-echo 不是契约语义**：同一 hub 既本地 enqueue 又订阅自身 Redis pub/sub，通知 payload 现在带 `instance_id`，接收方对相同 `instance_id` 跳过，从而每个 persistence phase 只产生一个 local `child_request` 帧。历史未带 `instance_id` 的 payload 与其他实例的 payload 仍正常处理。任何观测到的「单 phase 双帧」都属该 self-echo 缺陷，不在契约范围内。

`request` 事件本身扩展字段（13 号 §3 已冻结部分之外的新增）：
- `parentRequestId`、`requestType: chat|title|summary|sensitive_word|probe|unknown`（510 迁移已落 `request_logs.request_type`）
- `retrySeq`、`retryReasonClass`、`stage`（当前所在状态机阶段，§1 枚举）

## 4. Redis 回放队列（刷新兜底）

- Key：`llmgw:live:actions`（LIST/STREAM，有界 5000 条，LPUSH+LTRIM 或 XADD+MAXLEN）。
- 写入方：动作事件发射器（旁路异步，失败丢弃 + 计数器 `live_actions_dropped_total`）。
- 读取方：SSE `initial_data` 时回放最近 N 条（默认 200），保证刷新后动作时间线不缺失。
- 现状 `llmgw:live:main`（请求卡片级）保持不变；actions 是更细粒度的补充，不替代。

## 5. 时间戳口径（9 阶段，收敛版）

以 13 号契约为准命名（`request_logs` 列）：

| 阶段 | 字段 | 说明 |
| --- | --- | --- |
| S1 到达 | `created_at` | 网关收到请求 |
| S2 入总队列 | `pipeline_enqueued_at` | dispatch_v2 提交（TARGET：pipeline 层未暴露前可空） |
| S3 路由完成 | `route_resolved_at` | auto/别名解析完成 |
| S4 入模型队列 | `model_enqueued_at` | dispatch Tier-1 |
| S5 凭据选择 | `credential_selected_at` | router 输出 |
| S6 入节点队列 | `credential_enqueued_at` | dispatch Tier-2 |
| S7 开始转发 | `forward_started_at` | executor 连上游 |
| S8 首字节 | `first_byte_at` | 流式 TTFB |
| S9 完成 | `completed_at` | 终态 |

派生等待时长：`pipeline_wait = S3-S2`、`model_queue_wait = S5-S4`、`cred_queue_wait = S7-S6`、`forward_latency = S8-S7`、`stream_duration = S9-S8`、`total_latency = S9-S1`。
> 注意：历史文档（v3/01、v3/05、v3/20）对 S2-S7 字段名有版本漂移（见 12 号勘误）；以本表为准，旧字段名仅作历史参考。
