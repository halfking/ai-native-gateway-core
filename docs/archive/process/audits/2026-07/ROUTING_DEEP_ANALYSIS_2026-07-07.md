# 路由系统深度分析与系统化改进方案

## 执行概要
基于对 23,122 行路由代码的深度审计，发现三代架构共存、并发控制复杂、负载均衡不公平三大核心问题。
本方案提供三阶段渐进式改进路径，预期收益：代码减少30%、延迟降低60%、状态不一致归零。

## 一、架构演进分析
### 1.1 三代共存的技术债务
- Generation 1 (Legacy): filterAvailable + P2C
- Generation 2 (StateManager): 缓存化状态查询
- Generation 3 (URSM): 统一状态管理（设计中）
- 测试复杂度：2³ = 8种组合
- 技术债务标记：16处 TODO/FIXME

### 1.2 代码行数统计
- 路由相关总代码：23,122行
- Sticky相关引用：183行
- 限流器实现：448行
- 熔断器实现：483行

## 二、并发控制深度分析
### 2.1 死锁风险场景
级联阻塞：请求1持有Global+Pool阻塞在Credential，导致后续所有请求无法获取Pool

### 2.2 资源维度不匹配
FpSlot(20槽) 饱和 但 Limiter(50并发) 仅用40% → 30个并发容量浪费

### 2.3 资源泄漏点
defer顺序依赖：如果 release() panic，FpSlots.Release() 永不执行

## 三、负载均衡算法分析
### 3.1 Sticky机制问题
- L1(1h): 对话平均10分钟，有效期过长5倍
- L2(24h): 导致7天内持续使用同一凭据
- L3(7d): 长期绑定，新凭据永远空闲

### 3.2 Bandit"赢家通吃"
Thompson Sampling正反馈：早期领先者 → 更多流量 → 更高分数 → 更多流量

### 3.3 P2C隐含偏好
相同分数时的随机选择仍受初始采样顺序影响

## 四、故障场景模拟
### 4.1 级联失效时间线
T0: 单凭据故障 → 熔断器打开
T0+30s: 20%流量重路由 → 其他凭据25%→30%负载
T0+2min: Sticky L2未清除 → 持续probe失败凭据
T0+5min: 所有凭据饱和 → 全局不可用
恢复时间: 5-10分钟

### 4.2 雪崩推演
QPS 100→1000 → Global Limiter饱和 → 部分凭据429 → Bandit降权 → 流量集中 → FpSlot降级 → 并发失控 → 全局失败
