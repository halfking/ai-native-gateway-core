# 请求参数全量兼容 — 目标架构

**日期**: 2026-08-11
**前置**: [01-审计基线与研究结论.md](./01-审计基线与研究结论.md)

---

## 1. 设计原则

1. **未知即透传**：任何注册表未登记的字段，无条件跨协议透传。前向兼容优先 ——
   厂商每月新增参数，网关不该成为瓶颈。
2. **已知即受管**：注册表登记的字段带 dialect 归属，跨 dialect 时查表翻译，
   无映射则按目标能力裁剪并上报 loss。避免把 A 厂商私有字段泄漏给 B 厂商。
3. **能力决定成败**：`thinking`/`reasoning_effort` 的下发形态由**目标模型能力**决定，
   不由客户端请求形态决定。
4. **不静默**：任何裁剪/降级/翻译都上报 anomaly 事件。现有
   `ReportProtocolLoss`/`ReportUnknownField` 已具备该能力，复用。
5. **改动可回退**：新增行为全部走开关，默认开启但可一键关掉退回旧行为。

## 2. 分层架构

```
                        ┌─────────────────────────────────────┐
   客户端请求 body ────▶ │ Parse（4 种协议）                    │
                        │  · 已知字段 → IR 规范字段            │
                        │  · 未知字段 → IR.Extensions          │
                        │  · 记录 SourceDialect                │
                        └──────────────┬──────────────────────┘
                                       ▼
                        ┌─────────────────────────────────────┐
                        │ ir.InternalRequest（规范中间表示）   │
                        │  + ReasoningIntent（新，归一化推理） │
                        │  + SafetySettings/CachedContent（新）│
                        └──────────────┬──────────────────────┘
                                       ▼
       ┌───────────────────────────────────────────────────────────────┐
       │ paramreg  参数注册表（新）                                     │
       │   FieldSpec{ Name, Aliases, Dialects, Kind, IRPath, Translate }│
       │   · Classify(key) → unknown | dialect-scoped | ir-handled      │
       │   · RestorePolicy(key, srcDialect, dstDialect) → 透传/翻译/裁剪 │
       └───────────────────────────────┬───────────────────────────────┘
                                       ▼
       ┌───────────────────────────────────────────────────────────────┐
       │ reasoncap  思考能力解析（新）                                  │
       │   Resolve(model, catalogCode) → Caps                          │
       │   三层回退：DB reasoning_caps → 名称模式表 → provider 协议默认  │
       └───────────────────────────────┬───────────────────────────────┘
                                       ▼
       ┌───────────────────────────────────────────────────────────────┐
       │ Serialize（4 种协议）                                          │
       │   1. IR 规范字段 → 目标协议字段                                │
       │   2. ReasoningIntent → 按 Caps.Dialect 渲染（6 种形态之一）     │
       │   3. Extensions → 按 paramreg.RestorePolicy 还原               │
       │   4. paramguard 校验（不变量 + 厂商拒绝清单）                   │
       └───────────────────────────────────────────────────────────────┘
```

## 3. 新增模块

### 3.1 `internal/paramreg` — 参数注册表

单一数据源，登记所有已知参数。这是替代三道门禁的核心。

```go
// Dialect 标识参数的方言归属。
type Dialect string

const (
    DialectCommon     Dialect = "common"      // 跨厂商通用（temperature/top_p/...）
    DialectOpenAIChat Dialect = "openai_chat"
    DialectResponses  Dialect = "openai_responses"
    DialectAnthropic  Dialect = "anthropic"
    DialectGemini     Dialect = "gemini"
    DialectDeepSeek   Dialect = "deepseek"
    DialectQwen       Dialect = "qwen"
    DialectGLM        Dialect = "glm"
    DialectMiniMax    Dialect = "minimax"
    DialectKimi       Dialect = "kimi"
    DialectArk        Dialect = "ark"       // 火山
    DialectGrok       Dialect = "grok"
    DialectMistral    Dialect = "mistral"
    DialectOpenRouter Dialect = "openrouter"
    DialectVLLM       Dialect = "vllm"
    DialectOllama     Dialect = "ollama"
)

// Kind 决定还原策略。
type Kind uint8

const (
    KindIRHandled Kind = iota // IR 已有规范字段，序列化器负责，不进 Extensions
    KindPortable              // 无 IR 字段但语义跨厂商通用，可直接跨 dialect 透传
    KindDialectOnly           // 仅目标 dialect 匹配时才还原
    KindTranslatable          // 有跨 dialect 映射函数
    KindRejectedBy            // 某些 dialect 明确拒绝，须裁剪
)

type FieldSpec struct {
    Name       string
    Aliases    []string          // max_completion_tokens ↔ max_tokens 等
    Kind       Kind
    Dialects   []Dialect         // 哪些方言认识这个字段
    RejectedBy []Dialect         // 哪些方言会硬报错（优先级最高）
    IRPath     string            // KindIRHandled 时指向 IR 字段，便于审计
    Translate  TranslateFunc     // KindTranslatable 时的跨方言转换
    Note       string            // 来源/约束备注
}
```

核心决策函数：

```go
// RestoreAction 是还原决策结果。
type RestoreAction uint8

const (
    ActionRestore   RestoreAction = iota // 原样写入目标 body
    ActionTranslate                      // 经 Translate 后写入
    ActionDrop                           // 裁剪并上报 loss
    ActionSkip                           // IR 已处理，跳过（非丢失）
)

func Decide(key string, src, dst Dialect) (RestoreAction, *FieldSpec)
```

决策矩阵：

| 情形 | 动作 |
|---|---|
| 注册表无此 key（未知字段） | `ActionRestore` — **无条件透传，含跨协议、含 Gemini** |
| `KindIRHandled` | `ActionSkip` — 序列化器已处理 |
| `KindPortable` | `ActionRestore` |
| `KindDialectOnly` 且 `dst ∈ Dialects` | `ActionRestore` |
| `KindDialectOnly` 且 `dst ∉ Dialects` | `ActionDrop` + loss |
| `KindTranslatable` 且有 `src→dst` 映射 | `ActionTranslate` |
| `dst ∈ RejectedBy` | `ActionDrop` + loss（**优先于以上全部**） |

这就同时解决了两个对立需求：Claude Code 的 `CLAUDE_CODE_EXTRA_BODY` 任意字段能透传，
而 Anthropic 私有的 `context_management` 不会泄漏进 Mistral 的
`additionalProperties:false` body。

### 3.2 `internal/reasoncap` — 思考能力解析

```go
// Caps 描述一个模型的思考能力。
type Caps struct {
    Supported   bool      // 是否支持思考
    Dialect     Dialect   // 该模型用哪种表达方式下发
    Efforts     []string  // 支持的 effort 档位（空 = 不支持 effort 形态）
    BudgetMin   int       // 预算下限（0 = 无预算形态）
    BudgetMax   int
    CanDisable  bool      // 能否显式关闭（grok-4.5 不能）
    Adaptive    bool      // 支持 {"type":"adaptive"}
    HistoryFlag string    // 历史保留字段名（clear_thinking/keep/exclude/...）
    Source      string    // "db" | "pattern" | "provider_default"
}

func Resolve(ctx context.Context, model, catalogCode string) Caps
```

三层回退（用户已确认的方案）：

```
tier 1  models_canonical.reasoning_caps (JSONB，新增列)   ← 运营可热改，优先级最高
tier 2  modelname/reasoning_defaults.go 名称模式表        ← 代码内置，零配置生效
tier 3  provider catalog protocol 默认                    ← 兜底
```

**tier 2 的关键约束**：必须在 `modelname` 归一化**之前**用原始模型名匹配，因为
`variants.go:11-21` 会剥离 `thinking`/`reasoning` token。表结构仿照现有
`modelname/modality_defaults.go`（同样的 priority 0/1/2/3 分级），保持代码风格一致。

**反馈闭环**：当上游因推理参数返回 400 时，将该 (model, param) 记入观测，
供运营在 admin 侧确认后写入 tier 1，避免反复踩同一个坑。

### 3.3 `internal/ir` — ReasoningIntent 归一化

替换现有表达力不足的 `ReasoningConfig`（保留旧字段做兼容，逐步迁移）：

```go
// ReasoningIntent 是跨 6 种方言归一化后的推理意图。
type ReasoningIntent struct {
    Mode        Mode   // Unset | Disabled | Enabled | Adaptive
    Effort      string // 客户端原始 effort（未收窄）
    BudgetTokens *int  // 客户端原始预算
    Level       string // Gemini 3 thinkingLevel
    IncludeThoughts *bool
    KeepHistory  *bool
    Summary      string // OpenAI reasoning.summary
    Context      string // OpenAI reasoning.context
    SourceField  string // 来源字段名，用于 loss 归因与调试
}
```

**双向映射**采纳 LiteLLM 生产验证过的表（研究结论 2.4），并遵守其两条覆盖规则：
adaptive 模型忽略 effort；1024 硬下限；预算 cap 到 `max_tokens - 1`。

反向（budget → effort，用于 Anthropic → OpenAI 方向）按区间取最近档位，
这填补了现状「budget-only 配置到 OpenAI 静默消失」和
「effort-only 配置到 Gemini 静默消失」两个缺口。

### 3.4 `internal/ir/paramguard.go` — 参数守卫

序列化后的最后一道校验，落实研究结论 2.5 的硬不变量与 2.8 的厂商约束：

| 规则 | 依据 |
|---|---|
| `max_tokens > thinking.budget_tokens`，否则下调 budget | Anthropic 硬 400；LiteLLM/Cline 均实现 |
| thinking 启用时移除 `temperature`/`top_p` | Claude Code `claude.ts:1691-1695` |
| `temperature` 上限按 dialect 收窄（Anthropic 1.0 / Mistral 1.5 / 其它 2.0） | 各厂商 spec |
| Grok 推理模型移除 `presence_penalty`/`frequency_penalty`/`stop` | 硬报错 |
| GLM `tool_choice` 非 `auto` 时收敛为 `auto` | 仅接受 auto |
| MiniMax `n` 强制为 1 | spec 约束 |
| OpenAI o 系列 `max_tokens` → `max_completion_tokens` | 不兼容 |
| effort 值按 `Caps.Efforts` 收窄到最近档位 | 枚举分歧（2.2） |

### 关于 `fields.go` 的双份清单问题

现状有两套并行的"已知字段"清单：`internal/ir/parse_*.go` 各自的 `knownFields`
与 `domains/transformation/fields.go` 的 `standardRequestFields`。
`fields.go:8-13` 的注释记录了它们漂移导致 `stream_options`/`metadata` 被静默丢弃的真实事故。

目标架构下 paramreg 成为唯一数据源，`standardRequestFields` 由
`paramreg.IRHandledFields()` 生成，从结构上消除这类漂移。

## 5. 开关与回退

| 开关 | 默认 | 作用 |
|---|---|---|
| `PARAMREG_ENABLED` | `true` | 关闭则退回旧的 SourceProtocol 门禁行为 |
| `REASONCAP_ENABLED` | `true` | 关闭则退回无条件下发 |
| `PARAMGUARD_ENABLED` | `true` | 关闭则跳过守卫校验 |

三个开关互相独立，可单独回退。IR 现有熔断器（`circuitCheck`）机制保持不变。

## 6. 验收标准

1. Claude Code（anthropic）→ DeepSeek/GLM/Qwen(openai-chat)：`Extensions` 全量到达上游。
2. 任意协议 → Gemini：未知字段到达上游（当前 100% 丢）。
3. Gemini 入向 `safetySettings`/`cachedContent` 出向不丢。
4. Anthropic `thinking{budget_tokens}` → OpenAI 产出合理 `reasoning_effort`（当前静默消失）。
5. OpenAI `reasoning_effort` → Gemini 产出 `thinkingBudget`（当前静默消失）。
6. 不支持思考的模型不会收到 `thinking`/`reasoning_effort`。
7. `max_tokens <= budget_tokens` 的请求被自动修正，不再 400。
8. thinking 开启时不注入 `temperature`。
9. Mistral 等严格校验厂商不会收到其它方言私有字段。
10. `go build ./... && go vet ./...` 通过；新增单测覆盖上述 9 条。
