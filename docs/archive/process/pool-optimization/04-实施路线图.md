## M1: Smooth WRR 调度器实现

**目标**: 在新增 `domains/scheduler/` 包下实现可独立测试的 Smooth WRR。

### Tasks

```
□ 1.1 实现 wrrItem 结构和 SmoothWRR.Select()
       - wrrItem: candidateRef, configuredWeight, currentWeight
       - Select(): Nginx Smooth WRR, O(N) 每轮
       - Reset(): 重置 currentWeight 到 0
       - UpdateWeights(adjustments): 动态更新权重

□ 1.2 单元测试
       - TestSmoothWRR_Distribution: 1000 次选择, 验证 3:2:1 分布
       - TestSmoothWRR_NoRepeatedStreaks: 验证无连续重复 > ceil(N/2)
       - TestSmoothWRR_UpdateWeights: 动态权重调整后分布正确
       - TestSmoothWRR_SingleCandidate: 单候选边界
       - TestSmoothWRR_EmptyPool: 空池边界

□ 1.3 基准测试
       - BenchmarkSmoothWRR_Select: 10 候选, >1000w ops/s 达标
       - BenchmarkSmoothWRR_UpdateWeights: >100w ops/s 达标
```

### 验收标准

```
✓ 权重 3:2:1 时, 1000 次选择 ≈ 500:333:167 (±5%)
✓ 无任何候选被连续选择 > ceil(N/2) 次
✓ O(N) 复杂度, N=100 时单次 Select < 1μs
✓ 并发安全 (go test -race)
```

## M2: 权重自动计算

**目标**: 根据凭据的 RPM/TPM/历史成功率自动生成归一化权重。

### Tasks

```
□ 2.1 实现 WeightCalculator
       - Calculate(candidate): (rpm * 0.6 + tpm/1000 * 0.3 + successRate*100 * 0.1)
       - Normalize(weights): 归一化到 1-100
       - OnRateLimitHit(credentialID): 权重 × 0.7
       - OnRecovery(credentialID): 权重逐步恢复

□ 2.2 单元测试
       - 高 RPM 凭据权重 > 低 RPM
       - 成功率影响不超过总权重的 10%
       - 429 后权重降低, 恢复后回升
       - 边界: RPM=0, TPM=nil, successRate=0
```

### 验收标准

```
✓ 凭据 RPM=1000 → 权重 ≈ 60
✓ 凭据 RPM=1000 + TPM=100000 → 权重 ≈ 90
✓ 429 后权重从 60 → 42 (×0.7)
✓ 三次连续成功恢复后权重回到 ≈ 90%
```

## M3: 调度器集成

**目标**: 将 Scheduler 接入现有选路管道, 取代/补充 bandit 选路。

### Tasks

```
□ 3.1 实现 Scheduler 门面
       - 支持 StrategySmoothWRR / StrategyBandit / StrategyPriority
       - 从 provider.Policy 读取 routing_strategy 配置
       - 候选加载后先经过健康/限流/熔断过滤, 再进入调度器

□ 3.2 修改 provider/client.go 的选路管道
       - GetCandidates() 返回的 candidates 经过 scheduler.Sort()
       - 提供 sortByStrategy(candidates, policy, strategy)

□ 3.3 配置化
       - 读取 provider_policies.routing_strategy (新增 DB 字段)
       - 动态切换: admin API 可切换策略

□ 3.4 路由策略残留 (rollback safety)
       - 切换回 Bandit 时恢复原行为, 零副作用
       - 配置加载失败时降级到 Bandit (fail safe)
```

### 验收标准

```
✓ v_routable_credential_models 查询后, candidates 按 WRR 排序
✓ admin API 可切换策略 (bandit ↔ smooth_wrr), 秒级生效
✓ 切换回 bandit 后行为完全同 baseline
✓ 配置加载失败时自动降级 bandit, 日志告警
```

## M4: 号池水位监控

**目标**: 每 30s 采集号池状态, 低于安全线时触发告警。

### Tasks

```
□ 4.1 实现 WatermarkMonitor
       - loadPoolStats(): DB 查询凭据状态分布 (active/degraded/open/quarantined)
       - loadRealtimeUsage(): Redis 滑动窗口实时 RPM/TPM
       - calcAvailableThroughput(): 可用吞吐量 = Σ(credential.RPMLimit × healthFactor)
       - evaluateAndAlert(): 分级告警

□ 4.2 告警实现
       - Warn: 飞书 Webhook
       - Critical: 飞书 + Prometheus AlertManager
       - Emergency: 飞书 @所有人 + 短信/电话

□ 4.3 后台轮询
       - bg/pool_watermark.go: 30s tick
       - 轻量级: 仅查 DB 聚合, 不锁表, <100ms
```

### 验收标准

```
✓ 每 30s 输出一次水位指标 (日志 + Prometheus)
✓ 使用率 > 70% → Warn 告警
✓ 使用率 > 85% → Critical 告警
✓ 无可用凭据 → Emergency 告警
✓ 告警不重复 (相同 level 每 5min 最多 1 次)
```

## M5: 并发排队缓冲

**目标**: 在现有信号量基础上增加优先级队列缓冲, 避免 5s 忙等。

### Tasks

```
□ 5.1 实现 PriorityQueue
       - Push(entry): O(logN) 堆
       - Pop(): O(logN), 按优先级 + FIFO
       - Remove(entry): O(logN) 延迟删除

□ 5.2 集成到 Limiter.AcquireAll
       - TryAcquire 失败后进入队列 (而非忙等)
       - 出队后重新尝试 AcquireAll
       - 超时 (5s) 从队列移除

□ 5.3 配置化
       - queue_enabled (bool, 默认 false)
       - queue_timeout_ms (int, 默认 5000)
       - queue_max_size (int, 默认 1000)
```

### 验收标准

```
✓ 排队不改变 AcquireAll 的 4 层信号量语义
✓ 优先级队列: 高优请求插队
✓ queue_max_size 超出时返回 ErrQueueFull (不阻塞)
✓ 队列空时不消耗资源
```

## 风险与应对

| 风险 | 等级 | 应对策略 |
|---|---|---|
| WRR 与现有 Bandit 策略冲突 | 低 | 策略相互独立, 开关切换, 不共存 |
| 水位告警过于频繁 | 中 | 告警去重 (5min cooldown) + 可配置阈值 |
| 排队队列导致自增延迟 | 高 | 默认关闭, 仅在高并发场景启用 |
| 权重自动计算偏离预期 | 中 | 可观测性兜底, 随时手动覆盖权重 |
| 配置变更不生效 | 低 | fail safe: 配置失效降级 bandit |
