# 路由测试审计记录（2026-07-20）

## 审计范围

相对 `HEAD` 审计上一轮新增的 `routing-test` 测试工件和 `sql/routing-test-credentials.sql`，并以仓库现有 schema、mock 工具、Docker 配置和原始测试目标为准。

## 已修复的阻断问题

- 移除了含中文字符目录下的 Go 源文件与独立 module；它们会令 `go list` / `go test` 报 malformed import path。客户端已迁移到根模块：`cmd/routing-test-client` 和 `internal/routingtest`。
- 移除了不匹配现有 schema 的凭据 SQL：字段、状态值、模型绑定关系和凭据加密格式均不正确，且会对本地数据库造成错误写入。
- 移除了会自动启动 Docker、运行 schema 同步、写入凭据、吞掉 `psql` 错误的 `full-test.sh`。
- 移除了调用不存在目录和不支持参数 `--mode` 的 mock 启动脚本。
- 客户端现在区分网关 `202 Accepted + X-Gw-Pending` 与失败，记录 `Retry-After`，不再把它误判为普通错误。
- 客户端改为并发 5 个会话；第 3 轮开始保持约 40K 的累计用户上下文，并在每轮后等待 10 秒。
- 日志分析改用网关当前实际发出的 `upstream_http_attempt`、`goal_retry_attempt` 和无候选事件。

## 未解决的产品缺口

- 现有 `Router.PlanCandidates` 没有 request context，因此无法在不改变接口和调用链的前提下为每个过滤/评分判断输出可关联日志。
- 当前没有统一的网关分阶段时延埋点，不能验证“入口→路由”“路由→上游”“协议转换”“写回客户端”的独立阈值。
- 现有 host mock provider URL 对 Docker 网关不可达；需要专用 compose 服务或明确的 Docker 网络配置。
- 真实模型测试所需的本地供应商、加密凭据和至少三条模型绑定必须在独立的、可清理的测试数据方案中建立；不能从本仓库静态 SQL 猜测或复制真实密钥。

## 下一步建议

1. 先建立 compose 内 mock 服务和可回滚 seed，验证三个模型各至少三条路由候选。
2. 为路由计划与执行阶段设计 request-scoped telemetry 后，再实现 S20/S24 的自动验收。
3. 逐模型执行“ping → 多轮 40K → 故障注入 → 修复/重部署/回归”，每轮保留客户端 JSON Lines 与网关日志摘要。
