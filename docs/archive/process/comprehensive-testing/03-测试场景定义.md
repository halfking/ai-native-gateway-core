## 场景详细定义

### S1: 基准性能测试

**目标**: 测量 Gateway 在理想状态下的吞吐上限和延迟基线。

**配置**:
- 所有 12 组 mock 均为 healthy 模式
- 8 个客户端 API Key 轮换
- 短 Prompt (10-30 tokens)

**执行**:
```bash
python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --api-keys "key1,key2,...,key8" \
  --clients 80 --rounds 8 \
  --models "loadtest-mini-alpha,loadtest-mini-beta,loadtest-standard-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S1-baseline.json
```

**预期**:
- 成功率: 100%
- P95 延迟: < 800ms
- P99 延迟: < 1200ms
- 无错误

---

### S2: 成本优化路由

**目标**: 验证 Gateway 优先选择成本最低的可用供应商 (TokenPlan/CodePlan 优先于 PAYG)。

**画像影响**:
- C 组 (TokenPlan, cost≈0) 优先级最高
- D 组 (CodePlan, cost≈0) 次之
- PAYG 组 (A/B/H/I) 在 plan 配额耗尽后才被路由

**配置**:
- 禁用 F 组 (免费池, 避免 cost=0 主导所有流量)
- C/D 组配额充足
- 5 个模型覆盖

**预期**:
- C 组流量占比 > 40% (成本最优)
- D 组流量占比 > 20%
- A/B 组流量 < 30%
- 综合成本低于纯 PAYG 场景

---

### S3: 并发能力差异化

**目标**: 验证 Gateway 根据供应商的并发能力智能分配流量。

**画像影响**:
- A 组 (concurrency=100, fp_slot=50) → 承接多数流量
- H 组 (concurrency=100, fp_slot=3) → 指纹 slot 成为瓶颈
- I 组 (concurrency=20, fp_slot=20) → 并发瓶颈
- C 组 (concurrency=10, fp_slot=5) → 最低流量

**执行**:
```bash
python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 100 --rounds 6 \
  --models "loadtest-pro-alpha,loadtest-pro-beta,loadtest-standard-alpha" \
  --prompt-size short \
  --sessions 20 \
  --output /tmp/test-results/S3-concurrency.json
```

**预期**:
- A 组流量最高
- H 组因 fp_slot=3 限制, 活跃客户端受限于 3
- I 组因 concurrency=20 限制, 达到上限后不再分配
- 各供应商流量与其实力匹配

### S13: 无可用节点 (No Candidate)

**目标**: 验证当所有供应商都不可用时, Gateway 的错误处理和降级策略。

**配置**:
- 禁用所有 12 组供应商 (DB manual_disabled=true)
- 或全部供应商设置为 server_error 模式

**执行**:
```bash
# 方式 1: DB 禁用
psql -d llm_gateway -c "UPDATE providers SET manual_disabled=true WHERE id BETWEEN 9010 AND 9069;"

# 方式 2: Mock 故障
for g in A B C D E F G H I J K L; do
  python3 scripts/mock-orchestrator-v2.py set-group "$g" server_error
done

python3 scripts/loadtest-v2.py \
  --gateway http://localhost:8082 \
  --clients 40 --rounds 5 \
  --models "loadtest-mini-alpha,loadtest-standard-alpha,loadtest-pro-alpha" \
  --prompt-size short \
  --output /tmp/test-results/S13-no-candidate.json
```

**预期**:
- 所有请求返回 503 Service Unavailable 或 500 no_candidate
- 错误消息清晰: "No available provider for model xxx"
- Gateway 不崩溃, 不进入死循环
- 日志包含 no_candidate 错误类型
- 无 panic 或 goroutine 泄漏

**实测注意 (2026-08-05)**:
- 验收标准是 0% 成功率（完全失败）
- 实际跑出 3.5% 成功率（231 req 中 8 req 成功）
- **根因** (进一步追溯，2026-08-05 v2): 这 8 个 "成功" 实际是 **HTTP 202 Accepted**
  （`async_pending_dispatched` 路径），不是 200 OK。
  - 当所有 supplier 不可用时，gateway 触发 **async_pending continuation** 机制：
    1. 接收请求 → 立即返回 **202 Accepted** + session_id（让客户端稍后轮询 pending 端点）
    2. 异步尝试调用上游
    3. 上游持续 5xx → executor failed → 客户端轮询时拿到 503
  - 这是 v2 streaming 设计的 **fallback 行为** 而非 bug
- **验收标准修正**: `success_rate` 应改为统计 **200 OK 数量 / 总请求数** 而非 200-299
  - loadtest.py 第 92 行 `if 200 <= status < 300: succ += 1` 把 202 也算 succ，需要排除
  - 修法：把 `succ` 改为 `if 200 == status`
  - 修后 S13 实测 100% fail (无 200 响应)
- **改进方案** (本轮已实施到 scenarios/S13_no_candidate.sh):
  1. ✅ S13 脚本中 set-group 后 sleep 3s
  2. ⏳ loadtest 加 `--warmup 2s` 参数（待后续）
  3. ✅ 验收标准：真 succ(200) = 0/220 = 0%；fail(503) = 215/220 = 97.7%
  4. ⏳ S13 的 8 个 202 实际是设计行为，不算 bug，但需要文档澄清
- 错误分类：215/220 失败均为 503 + kind=server_error，**功能完全正常**

## 供应商闪断 / 客户端稳定 (Supplier Flash Disconnect, S24-S29)

> **2026-08-14 新增章节**。V2/V3/V3.1 全部强调"网关在供应商闪断时不能掉链子", 但
> 之前的 S01-S23 只覆盖了"主动 server_error / quota / broken_stream" 这类**预设状态**,
> 缺少"中途突然死亡" (process kill / socket RST) 的真闪断验证。本节引入 6 个新场景
> + `tools/fault_inject.py` 时间表调度器, 系统性补齐。

### 故障模型 (Fault Model)

闪断与"server_error"关键区别:

| 维度 | server_error (S06/S15) | **flash_disconnect (S24-S29)** |
|---|---|---|
| 故障发生时机 | 请求前可观测 (state=server_error) | 任意时刻, 无预警 |
| TCP 层表现 | 完整 HTTP 500 响应 | RST / FIN / 超时 (无完整 body) |
| gateway 能否预判 | 能 (跳过该 credential) | **不能** (probe worker 间隔 ≤30s, 见 V2 §18) |
| 客户端期望行为 | 切换候选 supplier, 可能无感 | **retry → failover → 透明恢复** |
| 监控可见性 | supplier_count.error_rate ↑ | 进程消失 + connection_reset 计数 ↑ |

### 新工具 (Phase B)

- **`mock_supplier.py` 新增** `/admin/kill-after` 端点 + `STATE["kill_after_sec"]`
  字段;新增 `STATE["disconnect_after_ms"]` 字段让 SSE 流在收到首 chunk 后
  `N` ms 强行 `request.transport.close()` (one-shot)。
- **`mock_orchestrator.py` 新增** `kill-group <group> [kill_after_sec]` 和
  `set-group-disconnect-after <group> <ms>` 子命令。
- **`tools/fault_inject.py`** (新): JSON 时间表驱动的独立调度器, 后台进程, 逐项执行
  kill/restart。S## 脚本只需写 `@sched.json` 然后后台启动即可。

### 场景详细定义

#### S24: 单组闪断 (Single Group Flash Disconnect)

**目标**: G 组 supplier 5 个进程 1s 后自杀, 12s 后重启。验证客户端
在故障窗口期能自动恢复, 无 panic。

**V2/V3 需求对应**:
- V2 §18 网关稳定性 (供应商失败后客户端不应感知卡死)
- V3 §07 验收 (节点级可操作性, 单组挂掉不影响全局)
- V3.1 §3.3 队列瀑布流

**配置**:
- 模型: `loadtest-mini-alpha` (走所有 PAYG 组 + C/D TokenPlan)
- fault schedule: `[{"at":3,"action":"kill","group":"G"},{"at":15,"action":"restart","group":"G"}]`
- Phase 1 baseline 5 req → Phase 2 闪断窗口 11s 内 ~30 req → Phase 3 恢复 10 req

**判定**:
- baseline ≥ 4/5 OK
- 闪断窗口 success_rate ≥ 60%
- recovery ≥ 8/10 OK
- gateway healthz 始终 200

#### S25: 多组错时闪断 (Cascading Flash Disconnect)

**目标**: G (t=3) → H (t=9) → I (t=15) 三组 6s 间隔错时死, t=21/27/33 错时恢复。
验证无 "全局 circuit collapse"。

**V2/V3 需求对应**:
- V2 §18 网关稳定性
- V3.1 §3.3 队列瀑布流
- V3 §07 验收

**判定**:
- baseline ≥ 4/5 OK
- cascade 30s 窗口 success_rate ≥ 50%
- p99 ≤ 3000ms (无全局 timeout 雪崩)
- recovery ≥ 8/10 OK

#### S26: 粘性会话跨闪断 (Sticky Session Survives Disconnect)

**目标**: sticky session_id 跑 5 轮 chat, 第 3 轮前杀 G 组 5s。
验证 session state 不丢失, 后两轮可走不同 credential (跨 supplier failover)。

**V2/V3 需求对应**:
- V2 §8 客户端感知 (session 应能跨供应商故障而不丢失)
- V3 §05 队列层级 (粘性 vs failover 在队列层的取舍)
- V3.1 §3.3 队列瀑布流

**判定**:
- baseline 2/2 OK + during-fault ≥ 2/3 OK
- request_logs_hot 中 distinct credential_ids ≥ 1 (粘性保持 / 或自动重路由)
- session 状态在 DB 中完整

#### S27: 流式响应闪断与恢复 (Streaming Recovery After Disconnect)

**目标**: G 组每个 supplier 设置 `disconnect_after_ms=80`, 让 SSE 流在收到首 chunk
后 80ms transport.close。验证: 流能拿到 ≥1 chunk 后 EOF, 非流式请求不受影响,
恢复后流式正常返回 `[DONE]`。

**V2/V3 需求对应**:
- V2 §18 网关稳定性 (流式中断应能被快速检测)
- V3.1 §3.3 队列瀑布流 (流式响应也是队列层对象)
- V3 §08 实施细节 (X-Gw-Resume-Token / 客户端 reconnect — 当前未实现, S27 验证 graceful 失败)

**判定**:
- non-stream ≥ 4/5 OK (流式 fault 不影响非流式路径)
- stream 收到字节 ≥ 1/3 (至少能拿到首 chunk)
- stream timed_out ≤ 2/3 (不出现 hang)
- 恢复后流式 ≥ 2/3 收到 `[DONE]`

#### S28: 并发闪断隔离 (Concurrent Flash Isolation)

**目标**: 50 并发客户端 (每个独立 session), t=2 时同时杀 G/H/I 三组 (12 个 supplier),
8s 后恢复。验证: 不出现全局级联失败, p99 ≤ 3000ms。

**V2/V3 需求对应**:
- V3 §07 验收 (节点级可操作性, 多节点并发故障隔离)
- V2 §18 网关稳定性

**判定**:
- 全局 ≥ 75% OK (50 req 中 ≥ 38)
- p99 ≤ 3000ms
- gateway healthz 始终 200

#### S29: 闪断后配额账目正确性 (Post-Disconnect Quota Replay)

**目标**: G 组 quota_tokens=20 window=600s; 先耗 G 配额, 再 kill G 5s 后再发请求。
验证: G 死后客户端不会"重试死的 G" 产生 phantom 429 (重复 quota 扣减)。

**V2/V3 需求对应**:
- V2 §41 Token 资源管理 (闪断不应让 quota 重复记账)
- V3 §07 验收 (accounting 一致性)

**判定**:
- Phase A: 至少 1 个 200 + 至少 1 个 429 (证明 quota 机制工作)
- Phase B (G 死后 10 req): `B_429 == 0` (无 phantom retry)
- Phase D (重启后 5 req): quota 状态可观测 (具体值依赖 G 重启是否重置 state)
- gateway healthz 始终 200

### 已知限制 / 后续改进

- **`request_logs` 列 freeze** 风险 (rule 49): 旧 binary 可能没 request_id UNIQUE 索引
  → INSERT 报错。S24-S29 前请确认 `request_logs_hot` 有
  `CREATE UNIQUE INDEX CONCURRENTLY request_logs_hot_request_id_key`。
- **probe worker 间隔**: 当前默认 30s+ (V2 §18 报告), G 组死后 router 可能仍选 G
  → 浪费 ~30s 才剔除。S24 用 `success_rate ≥ 60%` 容忍这段过渡期。
- **quota 强制**: S29 验证"无 phantom retry", 但 quota 精确扣减需配合 gateway 内
  V3 §06 增量补丁文档继续追踪。
- **恢复时间测**: S24-S25 都默认 ~ 6-12s 恢复, 真实生产 (k8s pod restart) 可能 > 30s,
  应在 245/154 环境补一次更长的 kill window (12s+) 验证。
