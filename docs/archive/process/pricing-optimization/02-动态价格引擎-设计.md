# 第二重系统：算力依赖与资源池动态价格管理

> 解决"底层算力资产"的效率与成本问题。基于 AWS Spot、GCP Preemptible、Azure Spot 等行业最佳实践，结合 llm-gateway-go 现有 MaaS 体系，构建内部 GPU 资源池的动态定价引擎。

## 1. 问题与目标

### 1.1 当前痛点

| 问题 | 表现 | 影响 |
|------|------|------|
| 算力成本不可见 | 无 GPU 利用率监控，无法按模型/租户拆分算力成本 | 毛利率计算依赖上游报价，无法反映真实硬件成本 |
| 无差异化定价 | 所有请求统一走 token 计价，不区分高峰/低谷、不区分现货/预留 | 低谷时算力闲置，高峰时资源争抢 |
| 外部价格波动被动承受 | 上游 MaaS 调价后手动更新 model_offers 的 unit_price | 调价滞后 → 毛利率被侵蚀 |
| 缺乏资源调度信号 | 无法通过价格信号引导非紧急任务错峰执行 | 训练/批处理与在线推理争抢 GPU |

### 1.2 设计目标

1. **算力利用率可观测**：毫秒级 GPU 指标采集，按节点/按模型/按租户聚合
2. **算力现货市场**：闲置时降价鼓励使用，吃紧时提价抑制需求
3. **外部价格联动**：自动感知上游报价变动，实时调整内部基准加价率
4. **毛利率自动稳定**：通过动态加价率抵消上游成本波动，保障毛利率≥N%
5. **与 MaaS 体系融合**：动态成本作为 MaaS 积分定价的下层输入，形成完整成本→定价→结算链路

### 2.1 组件职责

| 组件 | 职责 | 运行模式 |
|------|------|---------|
| **GPU Metrics Aggregator** | 采集 DCGM 指标，按节点/GPU/模型聚合，计算利用率百分位 | 后台 goroutine，15s 间隔 |
| **External Price Feeds** | 定时抓取上游 MaaS 报价（阿里/百度/DeepSeek/MiniMax 等），计算价格指数 | 定时任务，1h 间隔 |
| **Spot Price Calculator** | 基于 GPU 利用率 + 历史价格，计算各资源池的现货/按需/预留价格 | 事件驱动 + 定时计算 |
| **Markup Controller** | 根据外部价格变动 + 目标毛利率，自动调整 model_offers 的 unit_price | 联动触发 |
| **Gross Margin Monitor** | 跟踪 ConsumptionDetailRow 中的毛利率，低于阈值自动告警 | 实时（每次请求后） |

### 2.1a 管理面与数据面分离（审计优化）

> **审计发现八**：原架构图将定价决策（5 分钟周期）与 API 请求路径（毫秒级）在同一层绘制，
> 未反映异步解耦。优化为事件驱动的两层架构：

```
┌──────────────────────────────────────────────┐
│  管理面（Control Plane）                       │
│                                                │
│  DPE Calculator (5min)    — sigmoid 连续定价   │
│  Markup Controller (1h)   — 上游报价联动       │
│  External Price Feeds     — 定时抓取            │
│  Consolidation Planner    — 碎片整理            │
│  Gross Margin Monitor     — 实时监控 + 告警     │
└──────────┬───────────────────────────────────┘
           │ 事件通道 (Redis Pub/Sub / 消息队列)
           │
           │ compute_pool_prices 变更事件
           │ model_offers.unit_price 更新事件
           │ 毛利率告警事件
           ▼
┌──────────────────────────────────────────────┐
│  数据面（Data Plane）                         │
│                                                │
│  API Server 实时路由 — autoroute + streaming   │
│  Rate Limiter              — 按 pricing_tier    │
│  GPU Metrics Collector    — 15s 间隔采集       │
│  Billing Recorder         — ConsumptionDetail  │
└──────────────────────────────────────────────┘
```

管理面通过 `compute_pool_prices` 和 `model_offers` 的更新来影响数据面，
不侵入实时请求路径。数据面产生的事件（metrics）反向驱动管理面的定价计算。

## 4. 核心算法

### 4.1 利用率驱动的 Spot 定价（审计优化版）

借鉴 AWS Spot 定价模型（2018 年后不再采用竞价模式，改为基于供需的趋势定价），
结合审计对标（详见 `03-审计报告.md §3`）优化为连续函数 + 多维因子：

```
// 定价周期：每 5 分钟重新计算一次
// 输入：pool_utilization_rolling 的 p50/p95 利用率 + 15min 趋势 → queue_depth

spot_price = base_spot_price × utilization_factor × queue_factor × time_factor

// 基准价 = On-Demand 价的 30%~70%（对标 AWS/GCP 折扣）
base_spot_price = on_demand_price × spot_discount[gpu_type]

// ─── 连续利用率函数（替代原 5 档阶梯）───
utilization_factor(util, trend) = base(u) × (1 + trend_boost(trend))

// sigmoid 中心在 50%，陡度 6，输出范围 [0.5, 1.0]
// 替代离散跳变，实现平滑过渡
base(u) = 0.5 + 0.5 × sigmoid((u - 0.5) × 6)

// 利用率趋势前馈（15 分钟斜率 → 提前涨价/跌价）
trend_boost(trend) = clamp(trend_slope_15min × 0.3, -0.15, 0.15)

// ─── 排队深度因子（供需建模，新增）───
// 排队深度越深 → 供不应求 → 涨价
queue_factor(q) = 1.0 + sigmoid((q - 10) × 0.3) × 0.3

// ─── 时间因子（波峰波谷，新增）───
time_factor(hour, weekday) =
    1.0 + peak_hour_boost(hour) × 0.1 + weekend_discount(weekday) × (-0.15)

// ─── 平滑策略（防止颤动）───
// 价格变动上限：单次 ≤ 15%（借鉴 AWS 不突变原则）
// 变动间隔：≥ 5 分钟
// 使用 EWMA 平滑：smoothed = 0.7 × current + 0.3 × previous
```

**参数配置**（通过 `markup_config` 表可调）：

| GPU 类型 | On-Demand 参考价/h | Spot 折扣 | 最低 Spot 价 | 最高 Spot 价 |
|---------|------------------|----------|------------|------------|
| H100-SXM | $3.50 | 60% | $1.05 | $2.45 |
| A100-80G | $1.50 | 65% | $0.53 | $1.20 |
| L4 | $0.60 | 70% | $0.18 | $0.48 |
| T4 | $0.35 | 70% | $0.11 | $0.28 |
| RTX4090 | $0.50 | 60% | $0.15 | $0.35 |

> **参考来源**：AWS Spot 折扣 60-90%、GCP Spot 折扣 60-91%、Azure Spot 折扣 30-90%。
> 我们取保守区间 60-70%，预留空间给后续运营调整（参考 `docs/pricing/raw/` 中各厂商原始报价）。

### 4.2 三态定价模型

```
Tier          Guarantee    定价基准          用途                       参考折扣
──────       ──────────    ───────────      ────────────               ──────
Reserved     100% 保证     On-Demand + 0%   在线推理、核心业务         0%（基准价）
On-Demand    尽力保证      On-Demand + 0%   普通应用、轻度负载         0%
Spot         可被回收      On-Demand × 折扣   批处理、训练、非紧急任务   40-70%
```

**不可抢占保护机制**：

| 信号 | 保护窗口 | 动作 |
|------|---------|------|
| Spot 回收通知 | 30 秒（对标 GCP 标准） | 触发 graceful drain + checkpoint |
| 价格突变 > ±20% | 5 分钟 | 通知运行中 Spot Job 在窗口内完成 |
| 核心业务请求 | 无窗口 | 预留实例自动保障，不触发回收 |

### 4.3 外部价格联动（Markup Controller）

上游 MaaS 报价变动时，自动计算新的内部售价：

```
// 核心公式
new_price = upstream_price × base_markup × pool_multiplier

// base_markup 来自 markup_config，目标保障 margin
base_markup = 1 / (1 - target_margin)
// target_margin = 30% → base_markup = 1.43

// pool_multiplier 由当前池利用率决定
pool_multiplier = utilization_multiplier(from 4.1)

// 最终约束
final_price = clamp(new_price, min_price, max_price)
```

**举例**：

| 场景 | 上游价 ($/1M in) | Target Margin | Markup | 池利用率 | 最终价 |
|------|----------------|---------------|--------|---------|--------|
| 正常 | $1.00 | 30% | 1.43 | 50% → ×1.0 | **$1.43** |
| 上游涨价 | $1.20 | 30% | 1.43 | 50% → ×1.0 | **$1.72** |
| 高负载 | $1.00 | 30% | 1.43 | 85% → ×1.3 | **$1.86** |
| 上游降价+闲置 | $0.80 | 30% | 1.43 | 20% → ×0.7 | **$0.80** |

### 4.4 实时毛利率监控

每笔请求落库后，`ConsumptionDetailRow` 的计算公式：

```
// GrossMarginRate 已在 maas/consumption_detail.go 中实现
// 扩展后：
UpstreamCostUSD    = tokens × unit_price / 1_000_000        // 上游实际成本
ComputeCostUSD     = tokens × compute_unit_cost / 1_000_000  // 算力成本（新）
TenantRevenueUSD   = credits_charged × cents_per_credit / 100
EffectiveMargin    = (TenantRevenueUSD - Max(UpstreamCostUSD, ComputeCostUSD)) / TenantRevenueUSD
```

**告警阈值**：

| 级别 | 毛利率阈值 | 动作 |
|------|-----------|------|
| 🟢 健康 | ≥ 25% | 正常运营 |
| 🟡 警告 | 15% ~ 25% | 通知运营 + 标记上游可能涨价 |
| 🔴 危险 | < 15% | 自动触发 markup 重新计算 + 飞书告警 |

### 5.3 [关键融合点] MaaS 积分 ↔ 动态价格的换算

```
// 1 积分 = cents_per_credit 美分
// x 积分 = x × cents_per_credit / 100 USD

// 当 compute_pool_prices 发生变化时，DPE 建议新的积分费率：
suggested_base_credits_per_1m = ceil(
    on_demand_price_per_token / (cents_per_credit / 100)
)

// 其中 on_demand_price_per_token 来自 compute_pool_prices 中
// 对应 GPU 类型的 on_demand tier 价格 × 模型平均 token 产出率

// 例：
//   A100 on_demand = $1.50/h
//   模型吞吐 = 100K tokens/min = 6M tokens/h
//   token 成本 = $1.50 / 6M = $0.25/M
//   cents_per_credit = 0.01（1 积分 = $0.0001）
//   suggested_base_credits = ceil($0.25 / $0.0001) = 2500 credits/1M
```

## 8. 与行业实践的对比

| 特性 | AWS EC2 Spot | GCP Spot VM | Azure Spot VM | 本设计 |
|------|-------------|-------------|---------------|--------|
| 定价模型 | 供需趋势定价 | 固定折扣（60-91%） | 容量驱动 | 利用率驱动（混合） |
| 中断通知 | 2 分钟 | 30 秒 | 30 秒 | 30 秒~5 分钟 |
| 最大运行时间 | 无限制 | 无限制 | 无限制 | 无限制 |
| 折扣幅度 | 60-90% | 60-91% | 30-90% | 40-70%（保守起步） |
| 预留实例 | 有（1年/3年） | 有（1年/3年） | 有（1年/3年） | 有（时间未定） |
| 外部价格联动 | ❌ 无 | ❌ 无 | ❌ 无 | ✅ **核心特性** |
| Margin 保障 | ❌ 无 | ❌ 无 | ❌ 无 | ✅ **核心特性** |

本设计在**外部价格联动**和**毛利率闭环**上超越三大云厂商的 Spot 定价模型——这是作为 MaaS 中间层的独特优势。

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| Spot 定价过于复杂，运维负担大 | 无人维护 | v1 做 sigmoid 连续定价（替代 5 档阶梯），不引入竞价模型 |
| GPU 利用率数据质量差 | 定价失准 | 先验证 Prometheus recording rules 数据完整性后再开车价格联动 |
| PG 时序写入压力大 | 查询慢、维护成本高 | 改用 Prometheus + VictoriaMetrics，PG 只存聚合结果 |
| 上游价格剧烈波动 | margin 不稳定 | 加价率变动设置上限（单次 ≤20%），做平滑，不做突变 |
| Spot 回收影响用户体验 | 不可接受的推理中断 | 仅对明确标记为 spot 的任务做回收（批处理/训练），在线推理永远走 On-Demand/Reserved |
| 新增表过多 | 运维复杂度 | compute_pools + prices + metrics 3 张核心新表，其余复用现有 request_logs |
