## 1. 审计概要

### 评分

| 维度 | 原方案评分 | 说明 |
|------|----------|------|
| 架构完整性 | 7/10 | 分层合理，但缺少 priority/queue/cohort 语义 |
| 数据模型 | 6/10 | 缺少 unified allocation model、resource specs |
| 算法深度 | 5/10 | 仅做阶梯定价，缺乏历史数据驱动的动态调优 |
| 运维成熟度 | 4/10 | 缺少 graceful interruption 规范、checkpoint 机制 |
| 可观测性 | 6/10 | 有 metrics 采集，但缺少 cost breakdown 标准 |
| 安全性 | 8/10 | 总体合理，但缺少 budget 策略的可审计性 |

### 核心不足总结

1. **缺乏作业优先级和公平调度语义** — 对标 Kueue/Volcano 的 queue + priority 模型
2. **Spot 定价过于简化** — 仅做 5 档阶梯，缺失竞价历史曲线和供需弹性模型
3. **缺少成本分配模型** — 没有对标 OpenCost/Kubecost 的 unified allocation
4. **时序存储方案不成熟** — 直接写 PG 分区表，缺少 Prometheus + VictoriaMetrics 的降采样策略
5. **缺少标准化 Spot 中断处理** — job 级 checkpoint/重试/re-queue 规范

## 2. 发现一：数据模型

### 问题

原设计仅有 `compute_pools` + `compute_pool_prices`，缺少以下关键实体：

| 缺失概念 | 对标项目 | 重要性 |
|----------|----------|--------|
| **Queue** / **Cohort** — 资源队列与租户组 | Kueue ClusterQueue + Cohort | 🔴 高 |
| **PriorityClass** — 作业优先级 | Volcano/job priority | 🔴 高 |
| **ResourceSpec** — GPU 精确规格描述 | Karpenter NodeClaim / InstanceType | 🟡 中 |
| **BudgetProfile** — 租户预算策略 | OpenCost Budget | 🟡 中 |
| **SchedulingStrategy** — binpack/scatter/fair-share | Volcano/Kueue | 🟢 低 |

### 对标分析

**Kueue（kubernetes-sigs/kueue）**：
- `ClusterQueue`: 管理集群资源池（flavor 组）
- `Cohort`: 多个 ClusterQueue 组成资源公平共享池
- `LocalQueue`: 租户/namespace 级别的资源请求入口
- `Workload`: 代表一个作业的资源需求

**Volcano（volcano-sh/volcano）**：
- Queue: 资源队列，支持公平调度（fair-share）
- PriorityClassName: 作业优先级（high/medium/low）
- PodGroup: 支持 gang scheduling 的作业组

### 整改建议

新增实体：

```sql
CREATE TABLE resource_queues (
    id              SERIAL PRIMARY KEY,
    name            TEXT NOT NULL UNIQUE,
    pool_id         INT NOT NULL REFERENCES compute_pools(id),
    queue_type      TEXT NOT NULL DEFAULT 'default', -- default | batch | spot | inference
    priority        INT NOT NULL DEFAULT 0,          -- 队列优先级（越高越优先）
    min_resource    JSONB DEFAULT '{}',              -- 最小保障资源
    max_resource    JSONB DEFAULT '{}',              -- 最大可使用资源
    fairness_weight NUMERIC(5,2) DEFAULT 1.0,        -- fair-share 权重
    owner_tenant_id TEXT,                            -- 归属租户（NULL 为共享）
    status          TEXT NOT NULL DEFAULT 'active',
    created_at      TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE priority_classes (
    id              SERIAL PRIMARY KEY,
    name            TEXT NOT NULL UNIQUE,             -- high / medium / low / batch
    priority_value  INT NOT NULL,                    -- 0-1000
    preemption      BOOLEAN DEFAULT FALSE,           -- 是否可抢占
    spot_eligible   BOOLEAN DEFAULT TRUE,
    default_ttl     INTERVAL,                        -- 最大等待时间
    created_at      TIMESTAMPTZ DEFAULT now()
);
```

## 3. 发现二：Spot 定价算法

### 问题

原 5 档阶梯定价：
```
util < 30% → 0.7
util < 50% → 0.85
util < 70% → 1.0
util < 85% → 1.15
util >= 85% → 1.3
```

- **缺失历史数据维度**：仅看当前利用率，不看趋势
- **没有供需弹性模型**：任务到来速率 / 排队深度未纳入
- **离散跳变**：85% 时从 1.15 跳到 1.3，没有平滑过渡

### 对标分析

**AWS Spot 定价机制（2018 重构后）**：
- 基于长周期供需趋势定价
- 价格不再实时竞标
- 价格变化周期 ~小时级，非分钟级
- 中断率作为隐性价格信号

**GCP Spot**：
- 固定折扣（60-91%），简单可预测
- 价格不随实时利用率波动

**NVIDIA GPU Cloud Economics**：
- GPU 利用率 + 排队深度 + 任务到达率 三元驱动

### 整改建议

```
// 优化后：连续函数 + 历史趋势
spot_price = base_spot_price
    × utilization_factor(utilization, util_trend)
    × queue_factor(queue_depth, queue_trend)
    × time_factor(hour_of_day, day_of_week)

// 连续利用率函数（替代 5 档阶梯）
utilization_factor(u, trend) =
    base(u) × (1 + trend_boost(trend))

base(u) = 0.5 + 0.5 × sigmoid((u - 0.5) × 6)
// sigmoid 中心在 50%，陡度 6，输出范围 [0.5, 1.0]

trend_boost(trend) =
    clamp(trend_slope_15min × 0.3, -0.15, 0.15)
// 利用率上升趋势 → 提前涨价（前馈）

// 排队深度因子
queue_factor(q) = 1.0 + sigmoid((q - 10) × 0.3) × 0.3

// 时间因子
time_factor(hour, weekday) =
    1.0 + peak_hour_boost(hour) × 0.1 + weekend_discount(weekday) × (-0.15)
```

**平滑策略**：
- 价格变动上限：单次 ≤ 15%（借鉴 AWS 不突变原则）
- 变动间隔：≥ 5 分钟（防止颤动）
- 使用 EWMA 平滑：`smoothed = 0.7 × current + 0.3 × previous`

## 4. 发现三：缺少统一的成本分配模型

### 问题

原方案中成本追踪到 `request_logs` + `ConsumptionDetailRow`，但缺少：
- 多维成本拆分：按 namespace / 租户 / 模型 / 环境（prod/staging/dev）
- 共享成本分摊：网络 / 存储 / 控制面 如何按比例分配
- 空闲成本处理：预留但未使用的 GPU 容量成本

### 对标分析

**OpenCost**:
- `CostAllocation` 支持按 namespace/deployment/label 维度
- 统一费率（Unified Rate）将 k8s 资源统一折算为 $/CPU-hr、$/GB-hr、$/GPU-hr
- 支持资源共享成本分摊（网络、存储、LB）

**Kubecost**:
- 按 Cluster / Namespace / Controller / Pod / Label 多层成本分解
- 支持 Showback + Chargeback
- 支持外部成本（External Costs）集成（DB、SaaS）
- idle cost 按比例分配或独立展示

### 整改建议

新增 unified rate + cost breakdown：

```sql
CREATE TABLE unified_rates (
    id              SERIAL PRIMARY KEY,
    resource_type   TEXT NOT NULL,              -- cpu | memory | gpu_a100 | gpu_h100 | storage | network
    rate_per_hour   NUMERIC(12,6) NOT NULL,
    source          TEXT NOT NULL DEFAULT 'manual', -- manual | provider_price | blended
    effective_from  TIMESTAMPTZ NOT NULL DEFAULT now(),
    effective_until TIMESTAMPTZ,
    created_at      TIMESTAMPTZ DEFAULT now()
);
```

在 `ConsumptionDetailRow` 增加：

```go
// 新增成本拆分维度
type CostBreakdown struct {
    ComputeCostUSD    float64 `json:"compute_cost_usd"`
    MemoryCostUSD     float64 `json:"memory_cost_usd"`
    NetworkCostUSD    float64 `json:"network_cost_usd"`
    SharedOverheadUSD float64 `json:"shared_overhead_usd"`
    IdleCostUSD       float64 `json:"idle_cost_usd"`
    TotalCostUSD      float64 `json:"total_cost_usd"`
}
```

**成本分摊公式**：

```
ComputeCostUSD    = GPU_hours × GPU_rate
MemoryCostUSD     = GB_hours × Memory_rate × allocation_ratio
NetworkCostUSD    = bytes_transferred × network_rate
SharedOverheadUSD = TotalCost × shared_overhead_pct（默认 15%）
IdleCostUSD       = ReservedCapacity - UsedCapacity × rate
```

## 5. 发现四：时序数据存储方案

### 问题

原方案直接写 PostgreSQL 分区表 `gpu_metrics_snapshots`，存在：
- PG 不适合高频时序写入（高写入放大 × 分区维护成本）
- 15 秒间隔 × N 节点 × 24h = 海量行
- 长期保留成本高
- 查询复杂聚合慢

### 对标分析

| 方案 | 写入性能 | 查询性能 | 长期存储 | 运维成本 |
|------|---------|---------|---------|---------|
| PG 原生 + 分区表 | ❌ 中低 | 🟡 中 | ❌ 高 | ❌ 高 |
| Prometheus + recording rules | 🟢 高 | 🟢 高 | ❌ 本地存储有限 | 🟡 中 |
| **Prometheus + VictoriaMetrics** | 🟢 高 | 🟢 高 | 🟢 低（对象存储） | 🟢 低 |
| **Prometheus + Thanos** | 🟢 高 | 🟢 高 | 🟢 低（S3/OSS） | 🟡 中 |
| **M3DB / TimescaleDB** | 🟢 高 | 🟢 高 | 🟡 中 | 🔴 高 |

### 整改建议

**推荐：Prometheus + VictoriaMetrics（Single or Cluster）**

```
┌──────────────┐     ┌──────────────┐     ┌──────────────────┐
│ DCGM Exporter│────▶│  Prometheus   │────▶│ VictoriaMetrics  │
│ (每个 GPU 节点)│     │ (Server)      │     │ (长期存储)        │
└──────────────┘     └──────┬───────┘     └──────────────────┘
                            │ recording rules
                            ▼
                     ┌──────────────┐
                     │ 聚合指标       │
                     │ (5m / 30m / 1h)│
                     └──────────────┘
```

**Prometheus Recording Rules（降采样模板）**:

```yaml
# rules/gpu-cost-rules.yml
groups:
  - name: gpu_utilization
    interval: 15s
    rules:
      - record: pool:gpu_utilization:p50_5m
        expr: |
          quantile_over_time(0.5,
            DCGM_FI_DEV_GPU_UTIL[5m]
          ) by (pool_id, gpu_type)

      - record: pool:gpu_utilization:p95_5m
        expr: |
          quantile_over_time(0.95,
            DCGM_FI_DEV_GPU_UTIL[5m]
          ) by (pool_id, gpu_type)

  - name: cost_metrics
    interval: 1m
    rules:
      - record: pool:gpu_cost:rate_per_hour
        expr: |
          avg by (pool_id) (
            DCGM_FI_DEV_POWER_USAGE / 1000 * node:gpu_on_demand_price
          )

    # 新增：cost_allocation_total — 对标 OpenCost
      - record: pool:cost_allocation:total
        expr: |
          sum by (pool_id, namespace, model) (
            container_gpu_allocations
          )
```

**VictoriaMetrics 优势（对标 Thanos）**:
- 单二进制部署，无额外组件
- 向下兼容 PromQL
- 自动降采样（downsampling）
- 对象存储支持（S3/OSS 成本极低）
- 集群模式可水平扩展

## 6. 发现五：缺乏优雅的 Spot 中断处理

### 问题

原方案提到 "30 秒 ~ 5 分钟" 中断通知窗口，但缺少：
- 标准化 Job Checkpoint 机制
- 中断优先级策略（哪些任务先被中断）
- 重试与重新入队策略

### 对标分析

**Kueue**:
- `Preemption` 策略：LowerPriority / LessExpensive 等
- `Eviction` + `Re-queue`: 被抢占的 Workload 自动回到队列末尾
- `AdmissionCheck`: 加入资源前验证

**Volcano**:
- `TaskTemplate` spec 支持 checkpoint
- `LifecyclePlugin`: pre-stop hook
- 支持 `Rescheduling` 策略

**Ray**:
- 分布式 checkpoint 机制（`ray.state.Actor.checkpoint`）
- 自动故障恢复
- `placement group` 保障

### 整改建议

新增标准化的 interrupt protocol：

```go
type SpotInterruptPolicy string

const (
    InterruptPolicyCheckpointThenStop SpotInterruptPolicy = "checkpoint_then_stop"
    InterruptPolicyFailFast            SpotInterruptPolicy = "fail_fast"
    InterruptPolicyGracefulStop        SpotInterruptPolicy = "graceful_stop"
    InterruptPolicyNeverInterrupt      SpotInterruptPolicy = "never_interrupt"
)
```

```
中断流程：
1. DPE 决策回收 → 标记 compute_pool_prices 状态
2. 通知 K8s 或作业调度器 → 发出 Preemption 事件
3. Pod 收到 SIGTERM → preStop hook 执行：
   a. 保存 checkpoint（Prometheus 远端写/对象存储）
   b. 上报最后利用率数据
4. 作业自动回队列 → Kueue Re-queue 或 Volcano 重新调度
5. DPE 记录中断事件 → 计入 spot_eviction_rate
```

## 7. 发现六：缺乏预测性扩缩容和 Binpacking 优化

### 问题

原方案只做价格计算，未利用价格信号指导调度优化：

### 对标分析

**Karpenter（aws/karpenter）**:
- 基于价格的节点选择（Binpacking / cheapest first）
- `NodePool` 配置不同的实例族和优先级
- `Consolidation`: 碎片整理（删除利用率低的节点）
- 支持 spot/on-demand 混合比例配置

**OpenKruise**:
- `CloneSet`: 原地升级 + 缩容优先级
- `SidecarSet`: 统一 sidecar 注入
- `UnitedDeployment`: 多区域/多实例分发

### 整改建议

新增 consolidation + spot 比例优化：

```
// consolidation 触发条件
if pool_avg_util < 40% &&碎片率 > 30%:
    → 触发 consolidation
    → 迁移 Pod 到更少节点
    → 释放空闲节点
    → 更新算力成本

// Spot 比例决策
spot_ratio = f(spot_price_gap, pool_util_trend, job_interrupt_cost)
    // spot 便宜且利用率低 → 加大 spot 比例
    // spot 回收频繁 → 降低 spot 比例
```

## 9. 发现八：管理面与数据面未分离

### 问题

架构图中管理面（DPE 定价决策）和数据面（实时请求路径）混在一起：
- 价格计算频率（5 分钟）与 API 请求路径（毫秒级）耦合
- 线性的架构图未反映异步解耦

### 整改建议

重构为异步事件驱动：

```
┌──────────────────────────────┐
│  管理面（Control Plane）       │
│                              │
│  DPE Calculator (5min)       │
│  Markup Controller (1h)      │
│  External Price Feeds (1h)   │
│  Consolidation Planner (15m) │
└──────────┬───────────────────┘
           │ 事件 (Redis Pub/Sub / 消息队列)
           ▼
┌──────────────────────────────┐
│  数据面（Data Plane）         │
│                              │
│  API Server 实时路由          │
│  Rate Limiter                │
│  GPU Metrics Collector (15s) │
│  Billing Recorder            │
└──────────────────────────────┘
```

管理面通过 `maas_settings` 和 `model_offers` 的更新来影响数据面，不侵入实时路径。

## 10. 优化方案

> 基于以上 8 项发现，对原设计方案进行增量修正。

### 10.1 新增数据模型

| 实体 | 用途 | 来源 |
|------|------|------|
| `resource_queues` | 资源队列，支持公平调度 | Kueue ClusterQueue |
| `priority_classes` | 作业优先级 | Volcano PriorityClass |
| `unified_rates` | 统一资源费率 | OpenCost Unified Rate |
| `spot_price_history` | 历史竞价记录 | AWS Spot Price History |
| `price_sources` | 外部价格源管理 | 现有 price_index 的扩展 |
| `interrupt_events` | 中断事件审计 | 新增 |

### 10.2 算法增强

| 改进点 | 原方案 | 优化后 |
|--------|--------|--------|
| 利用率定价 | 5 档阶梯 | sigmoid 连续函数 + 历史趋势 |
| 供需建模 | 无 | 排队深度 + 任务到达率 |
| 平滑策略 | 无 | EWMA + 单次 ≤15% 上限 |
| 成本分配 | 仅按 token | GPU/内存/网络/共享+空闲多维 |

### 10.3 时序数据迁移

| 阶段 | 存储 | 保留时长 | 用途 |
|------|------|---------|------|
| 热数据 (< 7d) | Prometheus TSDB | 7 天 | 实时监控 + 定价引擎 |
| 温数据 (7-90d) | VictoriaMetrics | 90 天 | 历史趋势 + 报告 |
| 冷数据 (> 90d) | S3/OSS 对象存储 | 永久 | 审计 + 模型训练 |
