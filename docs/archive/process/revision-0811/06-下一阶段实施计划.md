# 下一阶段实施计划：契约与观测基线

> 状态：Ready for implementation
> 范围：只做证据、契约、关联链和测试基线，不改变生产路由、压缩、缓存或会话 ownership
> 依据：`05-方案审计修订说明.md`、`docs/omni-ref2/README.md`、`docs/omni-ref2/02-CROSS-REPO-EVENT-CONTRACT.md`

## 1. 目标

建立企业用户 LLM 质量与成本治理的可信底座，使 provider 状态、路由、错误切换、token、成本、free-tier、压缩和会话派生分析能够通过统一 ID 和版本化事件串联。

本阶段完成的定义：

- 72小时修订报告可重复生成，统计口径固定。
- Gateway 与 ai-session-manager ownership 和 v1 event contract 对账通过。
- 一次请求可用 `tenant_id/request_id/session_id/turn_id` 关联其 canonical facts。
- URSM v2 shadow 对比所需字段、指标和回滚条件明确。
- 性能基线脚本可运行并输出可归档证据。

## 2. 工作包

### WP1：修订统计可复现

交付：

- `scripts/report-72h-revisions.sh`，默认只读，输出全部/非 merge commit、numstat、按 subject type 和目录聚合。
- 脚本输出保存到临时目录或 CI artifact，不自动改文档。
- table-driven shell 测试或 fixture 验证 merge/revert/rename/binary 文件口径。

验收：同一 commit 上重复运行结果一致；报告明确时区、起止时间、HEAD 和排除项。

### WP2：跨仓事件契约对账

核验 Gateway v1 事件：

- `session.opened.v1`
- `request.completed.v1`
- `verdict.recorded.v1`
- `session.deleted.v1`
- `task.execution_host_changed.v1`

交付：

- Gateway producer/outbox 字段映射表。
- 与 ai-session-manager `contracts/` 和 ingress validator 的双向 fixtures。
- duplicate、stale、签名篡改、tenant mismatch、未知字段、敏感字段拒绝测试。
- handshake 仍保持 `event_mode: none`，除非全部门禁通过。

禁止：未经版本升级把 routing/compression 对象塞入 `request.completed.v1`。

### WP3：统一关联链审计

建立字段矩阵：

| 字段 | Gateway 来源 | 存储 | ASM 投影 | 规则 |
|---|---|---|---|---|
| `tenant_id` | 认证上下文 | canonical facts/outbox envelope | signed tenant | 请求参数不能覆盖 |
| `request_id` | Gateway 入口 | request facts | request projection | 全链唯一 |
| `session_id` | session resolver | turns/bodies | session projection | 允许显式受控输入 |
| `turn_id/turn_no` | turn writer | session_turns | turn projection | session 内单调 |
| `task_id` | 受控 metadata | session/task facts | task projection | opaque，不驱动路由 |
| client/agent params | allowlist metadata | request/session facts | 可选投影 | 不记录 secret |

交付：缺失字段、重复生成、跨租户 cursor、fallback 后 ID 变化的测试清单和修复票据；本阶段不批量改代码。

### WP4：URSM v2 shadow 门禁

交付：

- legacy 与 URSM v2 同请求 decision comparison schema。
- drift reason codes：candidate set、health state、quota、sticky、score、selected provider/model。
- 低基数指标，不使用 tenant/request/session 作为 metric label。
- shadow 观察窗口、样本下限、错误预算和 `URSM_V2_MODE=off` 回滚演练步骤。

验收：shadow 不改变流量；comparison 写失败不阻塞请求，但必须计数和告警。

### WP5：性能与成本基线

先选择三类固定场景：

1. 单轮小请求，不启用压缩。
2. 多轮会话，触发 session cache/trim。
3. `model=auto`，包含一次 provider fallback。

每类记录：

- p50/p95/p99、吞吐、错误分类。
- Gateway CPU/内存/goroutine。
- Redis/PG 请求次数和延迟。
- prompt/completion/cached tokens、canonical cost。
- free-tier 是否命中及 quota 状态。

验收：固定版本、固定配置、去除 credential 真值、重复3次、保存原始摘要。完成前不设“提升百分比”。

## 3. 后续能力门禁

### Lite/RTK/Caveman 压缩

进入条件：golden corpus 和保护规则齐备；现有 compressor/context trim/RecoveryCoordinator 的 canonical decision 已对账。

### Auto Combo/路由策略

进入条件：shadow scorer 能解释候选、score 和拒绝原因；unknown price/context/headroom 语义已定义；不绕过 URSM 健康过滤。

### 会话标题、摘要、质量评估

归属 ai-session-manager/Semantic Worker。Gateway 只发布 canonical facts/body refs；派生结果必须版本化、可重放并记录 input hash、模型和失败状态。

### Vibe coding 与软件开发质量

客户端/智能体提交 allowlist metadata，例如 client kind、agent kind、task ID、repository ref、workflow phase。ASM 侧基于版本化规则生成质量结果；任何请求拦截需独立策略契约、shadow 和人工可回退开关。

## 4. 推荐提交顺序

1. `docs(audit): harden revision plan with evidence gates`
2. `test(events): add gateway-asm v1 contract fixtures`
3. `feat(reporting): add reproducible 72h revision report`
4. `test(trace): audit request session turn correlation`
5. `feat(ursm): add shadow decision comparison telemetry`
6. `perf(baseline): add reproducible gateway scenarios`

每个提交独立可回滚，代码提交前运行目标包测试、`go test ./...`、`go vet ./...` 和敏感信息扫描。

## 5. 下一实施会话的第一个任务

从 WP2 开始，只读核验 Gateway 和 ai-session-manager 当前事件 schema，生成字段 diff 和双向 fixture 计划。若发现契约不一致，先提交测试使其稳定复现，再做最小实现修复；不要同时修改路由、压缩或会话缓存。
