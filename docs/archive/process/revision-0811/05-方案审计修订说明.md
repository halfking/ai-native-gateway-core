# 修订0811方案审计修订说明

> 审计时间：2026-08-11
> 审计对象：`docs/修订0811/`、72小时 Git 历史、URSM v2 与 OmniRoute 对比结论
> 结论：原方案可作为讨论稿，不能直接作为实施基线；本文件定义修订后的事实边界和实施门禁。

## 1. 事实核验

### 1.1 Git 统计口径

核验命令：

```bash
git rev-list --count --since="72 hours ago" HEAD
git log --since="72 hours ago" --format='%h|%s' --no-merges | wc -l
git log --since="72 hours ago" --numstat --format=''
```

| 指标 | 结果 | 说明 |
|---|---:|---|
| 全部 commits | 156 | 包含 merge、revert 和自动生成提交 |
| 非 merge commits | 139 | 仍包含 docs/test/chore |
| Git numstat 净增 | 约 42,050 行 | 不能等同于业务代码净增 |

原总结中的 `73 commits`、`+37,650/-4,950` 和“完成6个P0级特性”没有保持同一统计口径。后续报告必须给出命令、时间窗、是否包含 merge、是否排除生成文件。

### 1.2 性能数据

原文中的 `P95=1.85s`、`429=15.6%`、`4.2GB`、`1247 req/s` 未找到对应压测报告、原始日志或可复现脚本，不能作为当前基线。

修订要求：

- 使用固定场景和固定版本录制 p50/p95/p99、吞吐、错误分类、内存以及 Redis/PG 延迟。
- 同一场景至少重复 3 次，保存命令、配置、样本量和输出摘要。
- 没有证据时标记为 `未测量`，不能用估算值替代。

### 1.3 静态分析

原文声称 `golangci-lint` 有 247 个问题，但没有对应输出或归档报告，应改为“待运行”。未引用代码不得直接归类为死代码，必须经过溯源、价值分类和授权流程。

### 1.4 SSRF 风险

仓库中存在多处 `http.Get` 和 `url.Parse`，但大量位于测试、安装器、代理配置或 vendor。仅凭文本搜索不能证明 IR 热路径存在可利用 SSRF。

SSRF 审计必须确认：

1. URL 是否来自租户或上游响应等不可信输入。
2. 请求是否发生在网关进程内。
3. 是否已有 outbound fetch、DNS rebind 防护和私网地址阻断。
4. 是否有 provider endpoint 白名单。

完成数据流审计前，风险等级保持 `待确认`，不全局替换所有 HTTP 请求。

## 2. Ownership 边界

Gateway 是事实产生方，负责请求、供应商、路由、成本、脱敏状态和运行时会话事实。`ai-session-manager` 是会话控制面和派生分析方，负责运营读模型、标题、摘要、质量评估、项目关联和管理动作。

- Gateway 不把标题、摘要、质量分数作为请求热路径事实重新计算。
- `ai-session-manager` 不重算 provider、路由、压缩或计费结论。
- 跨仓通信走 `docs/omni-ref2/02-CROSS-REPO-EVENT-CONTRACT.md` 定义的事件和 outbox，不直接写对方事实表。
- 任务、客户端、智能体参数作为 opaque metadata 保留，供未来拦截器和 vibe coding 质量管理消费。
- 迁移支持 `URSM_V2_MODE=off` 回退，不把会话深层模块一次性塞入 Gateway。

```text
数据面 Gateway
  规范化 → 脱敏 → 供应商选择 → URSM v2 → 压缩/缓存 → 上游执行
  → 错误切换 → 输出合规 → 事实落库 → outbox事件

控制面 ai-session-manager
  事件接入 → 会话读模型 → 标题/摘要 → 质量评估 → 项目/任务关联
  → 运营查询、拦截策略和软件开发质量管理
```

## 3. 修订后优先级

### P0：证据和契约

1. 固化72小时修订统计脚本和报告口径。
2. 为 URSM v2 shadow/canary/authoritative 建立同请求 drift 门禁。
3. 校验 Gateway → outbox → ai-session-manager ingress 的 tenant、签名、幂等键和重放窗口。
4. 自动路由 v6 先恢复测试契约，不在未定位 revert 原因前接入生产热路径。

### P1：可观测闭环

1. 用同一 `request_id/session_id/tenant_id` 关联路由、provider、credential、fallback、token、成本和质量。
2. 以现有 `SessionCacheV2`、`session_turns`、`session_bodies` 和 outbox 为基线，验证真实读写后再优化。
3. 为 free-tier 建立 quota、Retry-After、key cooldown、ToS/来源和成本节省事实模型。
4. 仅在真实数据流确认后补 SSRF guard，优先复用已有安全边界。

### P2：OmniRoute 能力引入

1. RTK/Caveman 先做 golden corpus 评估，保护代码块、工具调用、URL、JSON schema 和敏感占位符。
2. Auto Combo 先作为 shadow scorer，经质量、成本、延迟和 quota 离线回放后再 canary。
3. Free-tier dashboard 只展示已落库事实，不从前端重算额度。
4. Context Relay 只做跨 provider/credential 切换的派生摘要，不覆盖 canonical session facts。

## 4. 实施门禁

### 契约

- 明确 `tenant_id`、`request_id`、`session_id`、`turn_id`、`task_id` 来源和必填性。
- 事件 schema 有版本、幂等键、签名、时间戳、nonce 和 replay window。
- Gateway 与 ai-session-manager 的事实 ownership 不冲突。

### 质量

- 路由候选、评分、拒绝原因和 fallback 原因可查询。
- provider 健康评分包含样本量、窗口和置信度。
- 标题、摘要和质量评估记录模型版本、事实版本和失败状态。

### 性能

- 先建立可复现基线，再设 p95、p99、吞吐和内存目标。
- 压缩优化有 token 节省率、语义保真、代码/工具回归和延迟对比。
- 异步写入有队列容量、丢弃策略、重试、顺序和回压测试。

### 回滚

- URSM v2 可通过 `URSM_V2_MODE=off` 回退。
- 新路由策略按 shadow → canary → authoritative 推进。
- 数据库变更有版本、验证和回滚脚本。
- outbox 消费失败可重放，不阻塞主路径，也不静默丢失事实。

## 5. 审计结论

不建议立即执行原 Phase 1 中的“SessionCompressor 异步化”“全量替换 http.Get”“恢复 v6 生产热路径”。下一实施会话应先完成统计口径固化、事件契约核验、请求关联链审计和可复现性能基线。
