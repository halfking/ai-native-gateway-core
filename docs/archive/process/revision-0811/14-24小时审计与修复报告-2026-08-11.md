## 6. 待跟进问题（已记录，建议后续修复）

以下为审查发现但因「风险/需设计决策/未上线」暂未在本次修复的问题，附定位与建议方案。

### A. Outbox 多实例领取缺事务保护（HIGH，上线前必修）
- **位置**：`internal/outbox/dispatcher.go:108-119`（`dispatchBatch` 的 `FOR UPDATE SKIP LOCKED` 在事务外）。
- **影响**：多实例 Dispatcher 会重复投递同一事件至 ASM（破坏 outbox 的恰好/至少一次语义）。
- **建议**：采用 claim-then-deliver 模式——`UPDATE ... SET status='processing' WHERE id IN (SELECT id ... FOR UPDATE SKIP LOCKED LIMIT N) RETURNING ...` 原子领取（需新增 `processing` 状态 + 迁移修改 CHECK 约束），HTTP 投递后置，再 `markSent/markFailed`。可避免长事务持锁过 HTTP。
- **前提**：当前 Dispatcher/Writer 均未接入 `cmd/gateway`（待 ASM 部署后），上线前修复即可。

### B. integrity 探测 SSE task ID 不一致（MED）
- **位置**：`bg/probe_queue.go:99`（pending/in-flight 用 `task.DedupKey = integrity:<tenant>:<cred>:<model>`）vs `bg/active_probe_emitter.go:240`（terminal 经 `publishSink` 用 `buildNodeProbeTaskID = node_probe:<cred>:<model>`）。
- **影响**：integrity 探测产生永不折叠的 pending tile + 额外 terminal tile。
- **建议**：terminal 路径按 origin 区分——integrity 用其 DedupKey（`publishSink` 需带入 tenant 或由 `ProbeQueueWorker.processTask` 直接走 `publishProbeTask` 发 terminal），node_probe/selfcheck 维持现状。

### C. D5 模型级 failover 复用已耗尽 candidates（HIGH，默认关闭）
- **位置**：`domains/streaming/handler.go:3704` 附近（fallback `Execute` 仍传原模型 candidates；`prepareRequestBody` 把 body 模型改回原模型）。
- **影响**：回退打到同一死模型，「回退成功」分支不可达；`ExecParams` 还缺 `AppID/ApiKeyID/RoutingTracker`（修复 #1 后会引发亲和/审计关联丢失）。
- **建议**：回退前用 `nextModel` 重新 `resolveCandidatesForRequest` 并重算 `modelResolution/txResult/policy`（参照 `refreshedCandidatesAfterProbe`）。
- **现状**：受 `AUTO_ROUTE_FALLBACK_ENABLED`（缺省 OFF）门控，未生效。

### D. Outbox Writer nil-tx 静默丢弃（LOW）
- **位置**：`internal/outbox/writer.go:78`（`w.tx == nil` 时校验后直接 `return nil`，不插入）。
- **影响**：生产侧若漏注入事务，事件被静默丢弃且无错误/日志（与 outbox 目的相悖）。当前为测试校验路径，所有生产调用方均应传入真实 tx。
- **建议**：区分「测试校验」与「生产写入」——生产路径 tx==nil 时返回 error；或抽出独立校验 helper。
