## 🎯 为什么这样设计

### 1. 四层指标模型的合理性

```
L1: 核心可用性 (40%) - 最重要，直接影响用户体验
L2: 性能 (30%)        - 响应速度是竞争力
L3: 稳定性 (20%)      - 长期可靠性
L4: 成本效益 (10%)    - 在质量基础上考虑成本
```

**依据**：
- Google SRE Book 的 SLI/SLO 分层理念
- 可用性优先符合 "能用 > 好用 > 便宜" 的优先级
- 权重可配置，支持不同业务场景调整

### 2. 多时间窗口设计

采用 5分钟/1小时/24小时/7天 四个时间窗口：
- **5分钟**：快速告警，及时发现故障
- **1小时**：过滤短期抖动，判断趋势
- **24小时**：稳定性评估，过滤偶发问题
- **7天/30天**：长期趋势分析，容量规划

### 3. 分阶段实施策略

```
Phase 0: 准备     → 无风险，只建表
Phase 1: 采集     → 低风险，异步写入
Phase 2: 计算     → 中风险，独立服务
Phase 3: 告警     → 中风险，只通知不动作
Phase 4: 路由集成 → 高风险，影子模式验证
Phase 5: 可视化   → 无风险，展示层
```

**优势**：
- 每个阶段可独立验证和回滚
- 风险递增，充分观察后再进入下一阶段
- 灰度上线（观察 → 影子 → 10% → 100%）进一步降低风险

### 4. 数据库设计考量

**为什么用分层聚合表？**
- `request_logs` (原始) → `provider_metrics_minute` (聚合) → `provider_metrics_hour` (再聚合)
- 原因：PostgreSQL 直接查询亿级 request_logs 会很慢，预聚合提升查询性能 100 倍

**为什么 Redis + PostgreSQL 双写？**
- Redis：实时指标（5分钟窗口），低延迟
- PostgreSQL：历史数据，持久化，复杂查询

### 5. 与现有系统的集成点

复用现有能力，最小侵入：
- **数据源**：复用 `request_logs` 和 `candidate_failure_logs`（已增强 context）
- **路由器**：在现有 DecisionEngine 基础上增加质量过滤和权重调整
- **熔断器**：在现有 CircuitBreaker 基础上增加质量驱动判断
- **告警**：复用现有飞书通知通道
