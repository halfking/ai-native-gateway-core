## 四、关键决策记录

### 4.1 技术选型

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 构建工具 | Bash 脚本 | 简单、跨平台、易维护 |
| 交叉编译 | Go 原生支持 | CGO_ENABLED=0 纯静态编译 |
| 前端构建 | Vite + pnpm | 快速、现代化 |
| Docker 构建 | buildx 多架构 | 一次构建，多平台支持 |
| 打包格式 | tar.gz (Unix) / zip (Windows) | 标准格式，兼容性好 |
| 版本管理 | version.json + 自动递增 | SSOT，避免冲突 |

### 4.2 目录结构

```
~/Downloads/deploy/          # 构建工作区（可配置）
  └── 2.4.7-1346/            # 版本号命名
      ├── .git/
      ├── build/             # 构建输出
      └── ...

build/releases/              # 发布产物
  ├── archives/              # 打包文件
  ├── images/                # Docker 镜像
  └── manifests/             # 版本清单
```

### 4.3 命名规范

```
主机包: llm-gateway-go-{version}-{build}-{sha}-{date}-{os}-{arch}.{ext}
Docker包: llm-gateway-go-docker-{version}-{build}-{sha}-{date}.tar.gz

示例:
- llm-gateway-go-2.4.7-1346-3970dbc1-20260723-linux-amd64.tar.gz
- llm-gateway-go-docker-2.4.7-1346-3970dbc1-20260723.tar.gz
```

## 五、风险与应对

### 5.1 已识别风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| 交叉编译失败 | 部分平台无法发布 | 低 | 在 CI 环境预先测试 |
| Docker buildx 不可用 | 多架构镜像构建失败 | 中 | 回退到单架构构建 |
| 磁盘空间不足 | 构建中断 | 中 | 预检查磁盘空间，自动清理 |
| 版本号冲突 | 覆盖已有版本 | 低 | 数据库唯一约束 + 人工审核 |

### 5.2 回滚策略

**构建失败**：
- 保留上次成功构建的产物
- 不递增版本号
- 清理失败的临时文件

**部署失败**：
- 自动回滚到上一个版本
- 保留备份
- 记录失败日志

## 八、FAQ

**Q1: 为什么使用 Bash 而不是 Makefile？**
A: Bash 脚本更灵活，支持复杂逻辑，跨平台兼容性好。Makefile 适合简单构建，不适合复杂的多阶段流程。

**Q2: 如何处理构建失败？**
A: 脚本使用 `set -euo pipefail`，任何命令失败立即退出。通过 trap 捕获错误并记录日志。

**Q3: 如何保证 Customer 版本隔离？**
A: 通过 `verify-binaries.sh` 扫描二进制文件，检查是否包含禁用字符串（如 /api/admin/*）。

**Q4: 如何支持离线安装？**
A: 离线包包含所有依赖（Docker 镜像、DB dump），通过 `--offline` 参数跳过在线检查。

**Q5: 如何回滚？**
A: 保留历史版本的备份，通过 `rollback.sh` 脚本恢复到指定版本。
