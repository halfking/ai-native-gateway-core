## 1. 风险分类

### 1.1 实施期风险

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| URSM 死代码激活引入 deadlock | 中 | 高 | hotconfig 关闭；逐步启用（每次只开 1 个 phase） |
| Columnar 表 DDL 阻塞 | 低 | 中 | DBA 旁路 + 灰度；TRUNCATE 选低峰期 |
| hotconfig 配置错误导致路由全停 | 低 | 极高 | 每次修改前 stop-the-line 演练；kill-switch 默认 off |
| 跨实例 StateRecorder Lua 竞态 | 中 | 高 | Lua 单脚本 + 单元测试覆盖（multi-instance 模拟） |
| 自检 INSERT 在生产误报 staleness | 中 | 中 | 启动 1h 宽限期；阈值 30min 是工程保守值 |
| 部署环境差异（71/184/252） | 中 | 中 | 统一 deploy 脚本 + dry-run；184/71 已下线（诊断报告 §遗留） |

### 1.2 生产期风险

| 风险 | 表现 | 缓解 |
|------|------|------|
| **静默风险（H.3）** | 再次出现 candidate_failure_logs 不写入 → 17 天静默重演 | staleness gauge > 1800s → webhook；insert fail ratio > 5% → webhook |
| **降级过激（H.5）** | 半开误判导致凭据长期 cooling | 灰度 + e2e S25 + 监控 cooling_active{credential} |
| **缓存过激** | 响应缓存回放错对象（raw_model 漂移） | 缓存命中校验 raw_model + binding 一致 |
| **绑定切换过激** | cost 优化把有效凭据切到劣质 | ShouldReEvaluate 触发条件严格化（10 文档 §3） |
| **回滚误操作** | 手动 hotconfig 改坏 → 流量全停 | 配置变更 audit + 二次确认 |
| **kind 误判** | 客户端错误被记为供应商错误 | `error_origin` 强制贯穿 + 单元测试覆盖 |

## 2. 回滚策略

### 2.1 部署回滚

- binary 回滚走 `deploy-154.sh` / `deploy-252.sh`（已就绪）
- 每次部署前创建 git tag，部署脚本 detect tag 与 binary 不匹配 → 报警
- 252 网关非 systemd 管理（诊断报告 §遗留问题 §1），需先定位启动方式

### 2.2 配置回滚（hotconfig）

- 所有 P0/P1/P2 改动必须通过 hotconfig 配置热更新
- 配置变更 audit log 入 `audit_trimmer` 治理
- kill-switch 默认 off，所有 experimental flag 必须显式开启
- 关键 flag 命名约定：`routing.ursm.phase<N>.<feature>=bool`

### 2.3 数据回滚

| 数据类型 | 回滚方法 |
|----------|----------|
| `availability_state` | SQL 反向 UPDATE（保留 before-image 7 天） |
| `candidate_failure_logs` | append-only，纯新增补偿路径（无 UPDATE） |
| `state_change_log` | append-only，仅 audit 回放 |
| `binding` Redis key | DEL key + 失效广播（pub/sub） |
| `fp_slot` / `conc_slot` | 等 lease 自然过期（TTL 1h） |

### 2.4 回滚决策树

```
监控告警 → 是否影响业务？
├── 否：观察 + 标记
└── 是：是否 P0/P1/P2 hotconfig 可关闭？
    ├── 是：立即 hotconfig rollback（< 30s）
    └── 否：是否单实例问题？
        ├── 是：实例隔离 + binary rollback
        └── 否：紧急全量 binary rollback（5 分钟）
```

## 3. Columnar 表 TTL 策略决策

### 3.1 候选方案对比

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| 接受现状 | 简单 | 长期 accumulation | 短期（≤3 月） |
| TRUNCATE 季度重建 | 简单粗暴 | 历史数据丢失 | 配合冷归档 S3 |
| 转回 heap | 恢复 DELETE | 失去 15-40x 压缩比 | 需要长期 TTL |
| 切换到 heap + 分区表 | 恢复 DELETE 且保留分区 | 迁移成本 + 索引重建 | 长期（> 6 月） |
| 物化冷归档到 S3 | 长期可查 | 归档 + 查询链路复杂 | 监管 / 合规 |

### 3.2 当前规模

- `candidate_failure_logs` 13 MB
- `credential_probe_model_log` 21 MB
- 合计 34 MB，占总库 6.7 GB 的 0.5%

### 3.3 决策建议

- **短期**（3-6 月）：接受现状 + staleness monitor 兜底（H.3）
- **中期**（6-12 月）：季度 TRUNCATE + 冷归档 S3（audit 用）
- **长期**（> 12 月）：如果 34 MB 增长超过 1 GB，转回 heap + 分区表

> 不建议转回 heap：失去 15-40x 压缩比且历史数据无法 DELETE。

## 5. 跨项目边界（route-incident 与 v3）

### 5.1 范围划分

| 项目 | 职责 | 不重叠点 |
|------|------|----------|
| **v3 (本方案)** | 自动状态管理：StateRecorder + Breaker + Checker + 主动探测 | 不涉及人工诊断 UI |
| **route-incident (.scratch/route-incident/)** | 人工诊断 UI：SwimLane + Incident + DiagnosticRun | 不修改自动降级逻辑 |

### 5.2 数据流

```
请求路径
  → 自动降级（v3 StateRecorder）
  → telemetry.SetOnRequestLogPersisted（路由决策日志持久化）
  → route-incident observer（订阅 telemetry）
  → Incident 聚合（人工诊断入口）
  → DiagnosticRun（人工触发探测 / recover）
```

### 5.3 边界冲突预防

- **manual disable** 不能与 **route-incident recover** 操作同时（互斥锁）
- **主动探测** 与 **route-incident manual probe** 限速：同一 credential 5 分钟内最多 1 个 probe
- **state_change_log** 是共享事实表（v3 写、route-incident 读）
- **credential.health_status** 字段：v3 写自动状态；route-incident 写人工标记 → 互不覆盖

### 5.4 关键时间窗（route-incident 交付）

| 阶段 | 状态 |
|------|------|
| Phase 1 (read-only) | 已完成（2026-07-13 17:16 截图验证） |
| Phase 2 (DiagnosticRun / mutating) | 计划中 |
| Phase 3 (evidence export) | 待 Phase 2 |
