# 成本评分与路由选择

> CostScorer 四维评分模型 + P2C 增强选择。

## 1. CostScorer 设计

### 1.1 评分公式

```go
score = w_price * price_score
      + w_latency * latency_score
      + w_stability * stability_score
      + w_error * error_score
      + w_pressure * pressure_score

默认权重:
  price=0.30  基于预计 token 成本的归一化价格
  latency=0.30  基于 p95 时延的归一化速度
  stability=0.20  历史成功率
  error=0.10  错误率 (1 - normalized_error_rate)
  pressure=0.10  资源压力 (1 - max(fp_usage, conc_usage))
```

### 1.2 评分输入约束

```
1. 输入来自同一统计窗口 (默认 5 分钟)
2. 价格按预计 input/output tokens 量计算:
   cost = (input_tokens * price_in + output_tokens * price_out) / 1_000_000
3. 稳定性使用 EWMA(α=0.3), 至少 5 样本
   样本不足时使用 provider 先验 (同类凭据平均)
4. 错误率按类别分层:
   - 客户端错误 (4xx 客户端问题) → 不计入供应商错误率
   - 超时/网络/5xx → 计入供应商错误率
   - 内容过滤 → 不计入 (客户端内容问题)
5. 缺失数据使用保守先验:
   - 无价格数据 → 使用同类凭据最高价格
   - 无时延数据 → 使用同类凭据最慢时延
   - 无稳定性数据 → 0.5 (中等风险)
6. cache_affinity_bonus: 如果候选是当前 binding, +10% 分数
   仅对强绑定会话生效
```

### 1.3 归一化方法

```go
func normalize(value, min, max float64) float64 {
    if max <= min {
        return 0.5
    }
    return (value - min) / (max - min)
}

// price_score: 越低越好
//   1.0 - normalize(cost, min_cost, max_cost)
// latency_score: 越低越好
//   1.0 - normalize(p95, min_latency, max_latency)
// stability_score: 越高越好
//   normalize(success_rate, 0.5, 1.0)  — 低于 0.5 直接舍弃
// error_score: 越低越好
//   1.0 - normalize(error_rate, 0, 0.2)
// pressure_score: 越低越好
//   1.0 - max(fp_pressure, conc_pressure)
```

## 2. RouteNode 结构

```go
type RouteNode struct {
    CredentialID int
    RawModel     string
    ProviderID   int
    ProviderName string

    // 可用性
    Available         bool
    UnavailableReason string

    // 成本
    PriceInPer1M    float64
    PriceOutPer1M   float64

    SuccessRate     float64
    P95LatencyMs    int
    ErrorRate       float64

    // 资源限额
    FpSlotLimit      int
    ConcurrencyLimit int

    // 评分结果
    CompositeScore  float64
    ScoreComponents map[string]float64

    // 统计来源
    SampleCount     int
    StatsWindow     int     // 统计窗口秒数
    StatsVersion    int64   // 统计版本 (时间戳)
}
```

## 3. 硬过滤顺序

```
1. provider.IsAvailable()           — 供应商启用/禁用
2. credential.IsAvailable()         — 凭据状态
3. model.IsAvailable()              — 模型绑定/探测状态
4. node.IsAvailable()               — 节点健康/熔断
5. model 上下文窗口匹配             — 请求 tokens <= max_tokens
6. 协议能力匹配                     — 支持 tool/stream/
7. 供应商 gate (auto gate)          — FP/Concurrency 开关
8. 会话策略匹配                     — 客户端 tier 限制
9. 失败候选黑名单                   — 本次请求已失败过的凭据
```

## 4. P2C 选择算法

### 4.1 基本流程

```go
func P2CSelect(candidates []*RouteNode) *RouteNode {
    if len(candidates) == 0 {
        return nil
    }
    if len(candidates) == 1 {
        return candidates[0]
    }

    // 第一轮: 按 score 概率加权选 2 个
    pick1 := weightedRandom(candidates)
    pick2 := weightedRandom(candidates)

    // 第二轮: 比较资源压力, 选压力低的
    // 如果压力相同, 选评分高的
    if pick1.FpSlotPressure < pick2.FpSlotPressure {
        return pick1
    }
    if pick2.FpSlotPressure < pick1.FpSlotPressure {
        return pick2
    }
    if pick1.CompositeScore >= pick2.CompositeScore {
        return pick1
    }
    return pick2
}

func weightedRandom(candidates []*RouteNode) *RouteNode {
    total := 0.0
    for _, c := range candidates {
        total += c.CompositeScore
    }
    r := rand.Float64() * total
    for _, c := range candidates {
        r -= c.CompositeScore
        if r <= 0 {
            return c
        }
    }
    return candidates[len(candidates)-1]
}
```

### 4.2 概率加权优势

```
1. 避免"评分最高者通吃":
   即使 A 评分 95, B 评分 94, B 也有 ~49.7% 概率被选中
   保证候选多样性, 避免所有流量集中一个凭据

2. 天然负载均衡:
   凭据数越多, 流量分布越均匀
   不引入额外轮询或一致性哈希复杂度

3. 与分级降级配合:
   降级节点评分降低 (stability/error),
   自然减少选中的概率
```

## 5. 权重自适应 (可选扩展)

```go
// CostOptimizerPlugin (插件)
func (p *CostOptimizerPlugin) OnCostScored(env *hooks.URSMEnvironment) {
    // 每小时:
    //   1. 统计过去 1h 各凭据的实际成本
    //   2. 对比预测成本 vs 实际成本
    //   3. 如果偏差 > 20%, 调整权重:
    //      - 实际成本高于预测 → 增加 price_weight
    //      - 实际时延高于预测 → 增加 latency_weight
    //   4. 权重调整量: ±0.05, 每项控制在 [0.1, 0.5] 区间
}
```

## 6. 选路决策总流程

```
1. Binding Lookup
   hit + 强绑定 → 直接返回 (跳过评分)
   hit + 软绑定 → ShouldReEvaluate? → 否: 返回绑定节点
                                    → 是: 进入评分
   miss → 进入评分

2. Load Candidates
   DB/Redis → 所有 (credential, model) 组合

3. Hard Filter
   按硬过滤顺序移除不可用候选

4. CostScorer.Score
   计算每个候选的综合评分

5. P2C Select
   概率加权 → 选两个 → 比较压力 → 最终选定

6. Execute
   Provider Gate → FP Slot → Concurrency → CB → Upstream

7. Post-Execute
   success: Binding Create/Update, State Record, Cache Response
   failure: State Record, Circuit Update, Failover (if eligible)
```
