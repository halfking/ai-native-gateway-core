## 1. 今日故障归因（事实）

### 1.1 故障事件链

```
14:00~18:00（持续）
  ├─ credential 19 (NVIDIA NIM) 请求 glm-5.2 → 8 次失败（30 分钟）
  │   └─ 7 × model_not_found + 1 × upstream_credential_invalid
  └─ credential 25 (SenseNova) 请求 glm-5.2 → 15 次失败（30 分钟）
      └─ 9 × model_not_found + 3 × rate_limit + 3 × transient

→ 故障结论：凭据 19 / 25 根本不支持 glm-5.2，请求应被自动冻结 5 分钟以上。
→ 实际行为：流量持续打到凭据 19 / 25；availability_state 一直保持 ready。
```

### 1.2 三根因（叠加放大）

| 层 | 现象 | 根因 | 关键位置 |
|----|------|------|----------|
| R1 写 | 失败从未持久化降级 | `shouldWriteCredentialState` 白名单漏 `KindModelNotFound` | `domains/streaming/executors/executor.go:3092-3102` |
| R2 写 | candidate_failure_logs 17 天未写入 | INSERT `//nolint:errcheck` 静默吞错 + DI 注入 nil-silently | `domains/streaming/executors/candidate_failure_logger.go:43,68-70,95-97`；`cmd/gateway/main.go:882-885` |
| R3 监 | auto-cool 全程静默 | 监控门槛 `coolMinSamples=20/5min` + 无 staleness 检测 | `bg/candidate_failure_monitor.go:89-95` |

### 1.3 R1 详解（为何 16 次请求全被吞）

```go
// executor.go:3092-3102
func shouldWriteCredentialState(kind errorsx.ErrorKind) bool {
    switch kind {
    case errorsx.KindAuth, errorsx.KindAuthRevoked,
         errorsx.KindQuota, errorsx.KindQuotaPeriodic, errorsx.KindQuotaBalance, errorsx.KindQuotaPermanent,
         errorsx.KindConcurrent, errorsx.KindRateLimit,
         errorsx.KindStreamTimeout:
        return true
    default:
        return false  // ← KindModelNotFound / KindUpstreamDown 落此，false 丢弃
    }
}
```

`kind=model_not_found` 走 default → 不写任何 credential state → 同一凭据被反复命中。

### 1.4 R2 详解（17 天静默为何无人察觉）

- `candidate_failure_logger.go:43` 修复前用 `//nolint:errcheck` 静默 INSERT 失败
- `cmd/gateway/main.go:882-885` `dbConn.Pool()` 可能 nil，构造的 `*Writer` 非 nil 但 `pool=nil`，所有 `LogFailure` 调用直接 return，无日志
- 监控 `bg/candidate_failure_monitor.go` 只查 `last 5 minutes` 窗口的表数据，表空→查无结果→无告警

### 1.5 R3 详解（监控门槛 vs 真实流量）

- 门槛：5 min 窗口、20 次 attempt、失败率 80%（≈ 240 req/h 才触发）
- 实际：credential 19 ≈ 16 req/h、25 ≈ 30 req/h → 远低于门槛
- 永远不触发；监控告警永远收不到

## 2. v3 方案遗漏识别（8 项）

> 基于代码现状审计反推，所有结论附 `file:line` 引用。

### H.1 依赖注入失败静默
- **现象**：`main.go:882-885` 注入 `FailureLogger = executors.NewCandidateFailureWriter(dbConn.Pool())`；`dbConn.Pool()` nil 时仍构造非 nil Writer，后续 `.LogFailure` 静默 return
- **v3 状态**：未讨论 DI 失败 fail-fast / 自检
- **补漏方向**：启动后 30s 内 `INSERT ... RETURNING id` 自检 + HealthCheck endpoint + 启动期 fail-fast

### H.2 Columnar 表 TTL 不可达
- **现象**：`candidate_failure_logs` 与 `credential_probe_model_log` 使用 Citus Columnar（append-only）
- **v3 状态**：未讨论 Columnar 表的 TTL 替代（TRUNCATE 分片 vs 转回 heap vs 接受）
- **补漏方向**：13 文档 §3 给出决策表

### H.3 INSERT 路径 metrics 缺失
- **现象**：`candidate_failure_log_inserts_total{result}` 未注册；表空与 INSERT 挂掉无法区分
- **v3 状态**：仅有业务指标，无内部自检指标
- **补漏方向**：每分钟 `candidate_failure_log_staleness_seconds` gauge，> 1800s 告 webhook

### H.4 KindModelNotFound 白名单缺口
- **现象**：`executor.go:3092-3102` 白名单未含 `KindModelNotFound`；今日 16 次请求全 false
- **v3 状态**：v3 §05 §2.2 `IsImmediatePersist` 仅列 Auth/Quota，遗漏 ModelNotFound
- **补漏方向**：v3 §05 §2.2 增加 `KindModelNotFound, KindUpstreamDown` → 立即持久化 cmb.available=FALSE + 30 分钟 cooldown + 主动探测

### H.5 监控门槛 vs 生产流量不匹配
- **现象**：`coolMinSamples=20/5min` 加上 80% 失败率 = 240 req/h 才触发
- **v3 状态**：未提供门槛与真实流量分布的校准方法
- **补漏方向**：按 credential 7 日 p95 分桶：`hot: 20/5min, warm: 8/5min, cool: 3/5min`

### H.6 URSM 死代码风险
- **现象**：`domains/ursm/` 整包（recorder, state, cost_scorer, fp_slot_manager, conc_slot_manager, keys, validator, error_classifier, batch_writer, api_record）共 ~800-1000 行未集成
- **main.go 未实例化**任何 URSM 组件
- **v3 状态**：v3 §08 引用 URSM 但无迁移步骤
- **补漏方向**：11 文档 §B 详述迁移路径（按章节逐步激活）

### H.7 availability_state 多 goroutine 写竞争
- **现象**：4 处写 `credentials.availability_state`：
  1. `bg/candidate_failure_monitor.go:271-282 applyAutoCool`
  2. `domains/credential/writer.go:181-312 WriteOnError`（Quota/Auth/AuthRevoked）
  3. `credentialhealth/checker.go:270-293 RecoverExpired`
  4. `executor.go:2171-2182 disableModelOffer` legacy cooling
- **v3 状态**：v3 §08 §4 级联传播未实现
- **补漏方向**：所有写收敛到 `ursm.StateRecorder`；短期加 OptimisticLock + 更新事件总线（详见 11 文档 §D）

### H.8 route-incident 并发诊断项目与 v3 关系未明确
- **现象**：`.scratch/route-incident/` 今日 17:16 启动（独立 spec：路由故障诊断 UI，按 read-only → mutating 分阶段交付）
- **v3 状态**：未讨论这个独立项目与路由降级的边界
- **补漏方向**：13 文档 §5 明确"v3 = 自动状态管理；route-incident = 人工诊断 UI"，并约定 telemetry hook 订阅方式

## 3. v3 新增场景（基于今日故障）

### S-SenseNova-NIM-model-not-found（v3 §01 §S11 补充）

```
输入: glm-5.2 → 凭据 19 (NVIDIA NIM) / 25 (SenseNova)，两者均不接受此模型
现象:
  上游返回 400 invalid_request_error / model_not_found / not supported
  错误分类: errorsx.KindModelNotFound
 错误源: error_origin=upstream（供应商侧问题，不是客户端）
现有行为:
  shouldWriteCredentialState(kind) → false → 不写任何降级
  StateRecorder 不触发，availability_state 维持 ready
  流量反复打到同一凭据
目标行为:
  1. IsImmediatePersist(kind) 包含 KindModelNotFound
  2. 立即写 cmb.available=FALSE, unavailable_recover_at=now+30min
  3. credential+model 组合标记 broken_confirmed
  4. 触发主动探测（退避 30s → 2m → 5m）
  5. RouteAuditor Hook 记录 credential_model_unsupported 事件
可观测: credential_cooling_total{reason=model_not_found} counter 增 1
```

### S-CandidateFailureLog-Pipeline-Down（v3 §01 §新增）

```
输入: candidate_failure_logs 写入挂掉（DI nil / DB 拒写 / Columnar 异常 / 慢）
现象: 表空，auto-cool 不触发，告警无数据
现有行为: 所有失败"无声"
目标行为:
  1. FailureLogger self-test（启动后 30s 验证 writability）
  2. 每分钟 staleness gauge：max(ts) < now - 30min → webhook
  3. INSERT 失败入 in-memory ring buffer + 异步重试
  4. FailureLogger nil-check 启动期 fail-fast
可观测: candidate_failure_log_inserts_total{result} / staleness_seconds
```

### S-Monitor-Threshold-VS-Traffic-Mismatch（v3 §01 §新增）

```
输入: 长尾 credential 流量 < 50 req/h（占总凭据 60%）
现象: 固定门槛 coolMinSamples=20/5min 不触发
目标行为:
  1. credential 按 7 日 p95 分桶（hot/warm/cool）
  2. 各桶独立门槛与冷却窗口
  3. traffic 极少场景下 manual probe 可强制触发
可观测: bucket_size 分布 + 触发延迟 P50/P95
```
