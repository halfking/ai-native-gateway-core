# 厂商多模态标准与适配矩阵

> 审计日期：2026-07-14
> 目的：把网关内部的附件方案约束到各厂商公开 API 的真实契约。
> 说明：能力和限制会随模型版本变化；上线前必须以目标模型的官方模型页和 API reference 做最终校验。
> 诚信声明：本文的厂商能力描述基于对各供应商公开 API 的既有知识编写。写作时 webfetch 尝试拉取
>   以下原始文档全部因网络限制（Cloudflare/超时）失败，未能在写作时实时比对。
>   官方链接已在 §4 列出，实施阶段必须逐一核实 MIME、大小、字段和计费约束。
> 协议来源：网关提供 OpenAI / Anthropic / Gemini 三条原生协议解析与转换（`internal/ir/types.go`）。
>   Mistral 无原生协议，通过 OpenAI 兼容接口接入；国内厂商（minimax、deepseek、qwen、doubao 等）
>   同样走 OpenAI 兼容协议，其多模态输入字段和限制套用本矩阵 OpenAI 行的基本规则，
>   但以目标模型官方文档为准。

## 1. 结论摘要

1. `data:` URI、供应商托管文件、公开 HTTPS URL、内部文件 URL 不是等价输入。只有上游能访问且允许的 URL 才能替代 base64。
2. 网关可以统一保存附件和元数据，但不能把一个网关 URL 无条件转发给所有上游。必须按目标供应商选择 `data`、可达 URL、供应商 Files API 或供应商专属 URI。
3. “URL 替换会减少 token”不能作为通用验收条件。图片/文档仍会被模型处理和计费，URL 只可能减少网关传输、日志和数据库体积。
4. 日志应默认保存脱敏后的规范化请求和附件元数据；原始 body 只能在显式审计开关、短 TTL、严格权限和加密存储下保留。

| 厂商/接口 | 图片 | 音频 | 文档/文件 | 可用引用形态 | 网关适配要求 |
|---|---|---|---|---|---|
| OpenAI Responses / Chat Completions | `input_image` / `image_url`；支持 URL 和 base64 data URL，细节以目标模型页为准 | 音频能力按模型和接口区分，不能把通用 `input_audio` 假设为所有模型都支持 | Responses API 可使用文件输入；不同接口字段不完全相同 | `https` URL、data URL，或 Files API 返回的 file id/引用 | 保留图片 MIME 和 detail；不支持的模态必须显式拒绝或降级并记录原因 |
| Anthropic Messages | `image` source 支持 `base64`、`url`、`file`（Files API 能力按账户/模型开放） | 不应把音频块直接映射为图片或文本；不支持时拒绝或走明确转写流程 | `document` 支持 base64、URL、文件引用；PDF、纯文本等按文档规定 | base64、可访问 HTTPS URL、Anthropic 文件引用 | `media_type` 必须保真；不要把网关私网 URL 发送给 Anthropic；工具结果与内容块保持顺序 |

| Mistral | Chat Completions 视觉输入支持 image URL 或 base64 data URL，模型和端点以官方文档为准 | 不能从 OpenAI `input_audio` 推断支持情况 | Document AI/OCR 使用独立接口/文件流程，不等同于 chat 图片块 | HTTPS URL 或 data URL；文件处理通常走专用 API | Chat 转换与 OCR/Document API 分流；禁止把 PDF 盲目转成 `image_url` |

## 3. 必须落实的通用约束

### 3.1 URL 可达性

- 上游访问 URL 时，URL 必须从上游网络可达，且不依赖浏览器 Cookie、内网 DNS、管理端登录态或一次性已过期签名。
- 附件服务应支持 HTTPS、正确的 `Content-Type`、`Content-Length`/范围请求和稳定的 2xx 响应。
- URL 中不放 tenant、原始文件名、访问令牌或可枚举的自增 ID。使用随机不可猜测的 file ID，并由附件服务执行授权。
- 对需要鉴权的对象，优先使用短时签名 URL；签名 TTL 必须覆盖上游重试窗口，且不得把签名 URL 写入长期日志。
- 代理转发前必须验证 scheme、host allowlist、解析后的地址和响应 MIME，防止 SSRF 和内容类型混淆。

### 3.2 MIME、大小和生命周期

- 保存 `declared_mime`、`sniffed_mime`、字节数、SHA-256、来源协议、目标供应商和过期时间。
- 不能只根据文件扩展名判断类型；声明类型与探测结果冲突时拒绝或隔离。
- 每个供应商适配器单独维护 `max_bytes`、支持 MIME、最大块数、引用 TTL 和重试规则。不要使用一个全局 20 MB/128 MiB 数值冒充厂商上限。
- 供应商文件引用过期、附件删除或签名失效后，历史会话不可保证可重放；日志标记 `replayable=false`。

### 3.3 转换与保真

- 转换 IR 必须保留原始块顺序、文本、图片/音频/文档数据、工具调用、工具结果和未知字段。
- 不支持的内容不能静默改成 `[Image: ...]` 等文本占位符。应返回结构化错误，或在明确配置下走 OCR/ASR/文档抽取并标注 `derived=true`。
- `data:` URI 解析必须校验 base64、MIME、大小和 padding；HTTP URL 不应被下载后无条件重上传，除非策略明确允许且完成 SSRF 检查。
- 流式响应只转换事件，不重新拼接或丢弃已发送的内容块；未知事件应按协议策略透传或记录不支持原因。

## 5. 对本仓库方案的直接影响

| 原方案表述 | 审计结论 | 修正 |
|---|---|---|
| 所有 base64 替换成 `files.kxpms.cn` URL | 不成立；上游可能不可达、需要供应商 URI 或只接受 data URL | 增加供应商适配器和 `reference_mode`：`data`、`gateway_url`、`provider_file` |
| URL 替换减少 token | 不成立为通用规则 | 只承诺减少网关/日志字节；token、图像细节和计费以供应商返回 usage 为准 |
| 附件提取后原 base64 只需从日志删除 | 不完整 | 上游 body、重试缓存、trace、错误日志、审计导出全部执行同一脱敏策略 |
| 失败时 fail-open 继续发送 base64 | 有数据泄露和超大请求风险 | 按路由策略选择 fail-closed、provider-specific fallback 或拒绝，并暴露结果指标 |
