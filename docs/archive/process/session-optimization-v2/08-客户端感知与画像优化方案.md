---

## 1. 设计目标

把审计报告（07）揭示的"断线"基础设施接通，让一条请求在进入网关时被完整感知——**谁**（智能体/指纹/客户/账户）发的、**什么性质**（原生/重试/探针/第几轮）、**什么上下文**（项目/任务/协议）——并据此驱动客户端画像。设计原则：

1. **request_logs 零改动**：不向已超载的 request_logs 继续塞列，规避 hot 表缺列导致的 42703 事故。
2. **复用优先于新建**：死代码（`request_metadata.go`）、未接线脚手架（`clientprofile` 域）直接复用。
3. **集中而非分散**：三类附属属性集中在一张侧表，审计/分析一次 JOIN 即得全景。
4. **identity_hash 为跨表主键**：侧表、client_profiles、session 体系全部以 identity_hash 贯穿。

## 3. 统一提取层（Phase 2）

### 3.1 选择 requestAttemptMeta 为 chokepoint

`domains/streaming/request_meta.go` 的 `requestAttemptMeta` 已在 `fillAttemptMeta` 从 `*http.Request` 构建并持 `IdentityHash`/`ClientProfile`，是失败/成功 entry 的统一丰富入口（`enrichRequestLogFromMeta` :217 调用）。在此扩展字段，一处提取，全路径受益。

### 3.2 提取口径（全部复用现有逻辑）

| 新字段 | 提取函数 | 来源 | 备注 |
|--------|---------|------|------|
| AgentName | `telemetry.ExtractAgentName` | X-Agent-Name > UA | 死代码复活 |
| AgentType | `telemetry.ExtractAgentType` | X-Agent-Type > UA | 死代码复活 |
| ClientProtocol | `ir.DetectProtocolByURL(body, path)` | body 置信度 > URL path | openai-chat/anthropic-messages/gemini-generate |
| ClientIP | `telemetry.ExtractClientIP` | X-Real-IP > XFF[0] > RemoteAddr | 统一口径 |
| ForwardedFor | `telemetry.ExtractForwardedFor` | X-Forwarded-For 全链 | — |
| APIKeyFingerprint | SHA-256(rawKey)[:16] | 认证阶段 raw key | 复用 gateway-v2 口径 |
| VirtualClientID/IP/MAC | `ClientIdentity.*` | identity 域已算出 | identity 域扩展返回 |
| CustomerID | `KeyInfo.CustomerID` | api_keys JOIN applications.customer_id | 新增映射 |
| ProjectID | X-Gw-Project-Id header | 客户端传入 | 新增 header |
| SourceChannel | X-Client-Channel > agent_type 派生 | web/api/mcp/agent | — |

### 3.3 统一 IP 解析

改 `domains/identity/identity.go:181 extractClientIP` 复用 `telemetry.ExtractClientIP`（当前不查 X-Real-IP，与权威路径不一致）。避免指纹 IP 与落库 IP 口径分裂。

### 3.4 CORS

`middleware/cors_mw.go:33` 补 `X-Agent-Name`/`X-Agent-Type`/`X-Gw-Project-Id`/`X-Client-Channel`。

## 4. 请求附属特性侧表（Phase 1/3）

### 4.1 为什么用侧表而非 request_logs

- request_logs_hot 用 `LIKE request_logs` 创建，observability 列很可能不在热表 → 直接补绑到 request_logs INSERT 会触发 42703。
- request_logs 已有 80+ 列，继续超载损害可维护性。
- 侧表可独立演进 schema，不影响主请求日志的稳定性。

### 4.2 表设计

详见 [09-请求附属特性表设计与执行方案.md](./09-请求附属特性表设计与执行方案.md)。核心：`request_context_attrs`，PK=request_id，承载全部三类附属属性，ON CONFLICT 幂等 upsert，best-effort 写入（失败不阻塞主请求日志）。

### 4.3 写入层

- `telemetry.Client.EmitRequestContextAttrs(entry)`：INSERT into 侧表。
- `RequestLogContext.BuildContextAttrsEntry()`：从 meta + KeyInfo + handler 信号组装。
- `ApplyAttrsFromContext`：ctx→entry 桥接（nil-safe + first-write-wins），**在 emit 站点真正调用**（修复 origin 桥接断线的同类问题）。
- 接入站点：失败 `EmitFailure`、成功 `recordInitialRequestLog`、probe `emitClientDisconnectProbe`/`active_probe_emitter`。

## 5. 请求性质维度（Phase 4）

| 字段 | 派生口径 | 存储 vs 查询 |
|------|---------|-------------|
| is_probe | origin_stage ∈ {self_check,node_probe,system_health,probe_*} | 侧表存储 |
| attempt_no | 网关 failover 轮次（candidate_failure_logs.attempt_index 口径） | 侧表 best-effort 存储 |
| is_retry | 客户端重试=同 client_request_id 多行；follow-up=X-Gw-Follow-Up-Attempt | 侧表存储 |
| turn_no | session 已知请求计数（best-effort）+ ROW_NUMBER 派生（权威） | 侧表 best-effort + 查询派生 |
| source_channel | X-Client-Channel > agent_type | 侧表存储 |

## 7. 风险与约束

| 风险 | 缓解 |
|------|------|
| request_logs INSERT 零改动 | 侧表独立，主日志零回归 |
| 热表缺列 | 侧表是新表，无此问题 |
| 侧表写入失败影响主请求 | best-effort 异步，失败仅日志 |
| 画像聚合风暴 | 复用 analysis 总线限流 + batch（已有 LoopConfig） |
| CustomerID 映射不完整 | 渐进回填 applications.customer_id，空值允许 |
| IP 统一口径改变指纹 | 部署后观察 identity_hash 分布变化，必要时加 salt 版本 |
