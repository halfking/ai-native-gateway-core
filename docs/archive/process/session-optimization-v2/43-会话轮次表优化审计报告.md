## 1. 架构设计 vs 实际实现

### 1.1 设计意图（来自 00-完整方案文档.md）

```
核心创新：
┌─────────────────────────────┐
│ V1: 每轮存储完整历史        │
│ Turn 1: [msg1]              │
│ Turn 2: [msg1, msg2]        │  ← 重复存储
│ Turn 3: [msg1, msg2, msg3]  │  ← 指数增长
└─────────────────────────────┘

┌─────────────────────────────┐
│ V2: 每轮只存储增量          │
│ Turn 1: delta=[msg1]        │
│ Turn 2: delta=[msg2]        │  ← 只存新增
│ Turn 3: delta=[msg3]        │  ← 线性增长
└─────────────────────────────┘
```

**设计目标**：
- 磁盘节省 60-80%
- 发送给 LLM 时**动态拼接**历史增量
- 在拼接过程中**应用压缩和缓存**

## 2. 缓存架构分裂问题

### 2.1 两套独立的缓存体系

#### 缓存体系 A：旧压缩层缓存

**代码位置**: `domains/hooks/compression/session_cache.go`

```go
// Three-tier session state cache for the v3 session-level compressor:
//
//	L1 — in-process sync.Map (< 0.1 ms, bounded by MaxL1Sessions)
//	L2 — Redis Hash session:sc:{tenantID}:{gwSessionID}:v1 (~2 ms RTT)
//	L3 — PostgreSQL request_logs fallback (cold-start / Redis miss / schema
//	     upgrade)
```

**Redis Key**: `session:sc:{tenantID}:{gwSessionID}:v1`

**存储内容**：
- `SessionState` 结构（v1-v6 演化）
- 包含 `LastOutboundHash`、`SummaryMarker`、`CompressionMode` 等

**使用位置**：
- `domains/hooks/compression/session_compressor.go`（主压缩流程）
- 仍在生产环境活跃使用

#### 缓存体系 B：新 V2 缓存

**代码位置**: `domains/session/v2/cache_v2.go`

```go
// SessionCacheV2 is the V2 cache architecture that reads from session_turns
//
// Cache Levels:
//   L0: Turn delta storage (incremental messages in session_bodies)
//   L1: Compression metadata cache (in-memory LRU, no full body)
//   L2: Governance cache (Redis, verdicts only)
//   L3: Cold start (read from session_turns, not request_logs)
```

**Redis Key**: （代码中 L2 GovernanceCache 未实现 Redis 连接）

**存储内容**：
- `SessionStateV2` 结构（轻量化）
- `CompressionMeta`、`GovernanceMeta`

**使用位置**：
- **未被请求处理流程使用**
- 只在测试代码中出现

### 2.2 问题分析

| 问题 | 影响 |
|------|------|
| **两套缓存未统一** | 增加维护成本，容易产生状态不一致 |
| **V2 缓存未接入生产** | V2 表的增量存储优势无法发挥 |
| **旧缓存仍读 V1 表** | 存储优化目标（60-80%）未达成 |
| **Redis key 命名未规划** | 缓存 key 可能冲突或混淆 |

## 3. 动态拼接与压缩的缺失

### 3.1 设计意图

**00-完整方案文档 §4.1 增量提取算法**：

```go
func extractRequestDelta(req *ProcessedRequest) []Message {
    if len(req.LastOutboundBody) == 0 {
        return req.RequestBody // 首轮全量
    }

    // 构建上轮消息集合
    lastSet := buildMessageSet(req.LastOutboundBody)

    // 提取新增消息
    var delta []Message
    for _, msg := range req.RequestBody {
        if !lastSet[messageKey(msg)] {
            delta = append(delta, msg)
        }
    }

    return delta
}
```

**关键点**：
1. 从 `session_bodies` 读取历史增量
2. **在发送给 LLM 之前动态拼接**
3. 在拼接过程中应用压缩策略

### 3.2 当前实现

**压缩层入口**: `domains/hooks/compression/session_compressor.go:135-150`

```go
func (sc *SessionCompressor) Prepare(
    ctx context.Context,
    clientBody []byte,
    tenantID, gwSessionID, protocol string,
    contextWindow int,
    streamStarted bool,
) *PrepareResult {
    // ...
    // 直接从旧缓存读取完整 LastOutboundBody
    // 未从 V2 表动态拼接
}
```

**问题**：
- ❌ 未使用 `TurnReader.LoadChain()` 动态拼接
- ❌ 未使用 `TurnReader.LoadLatestOutbound()` 获取压缩后的状态
- ❌ 压缩决策仍基于旧缓存的 `SessionState`

### 3.3 TurnReader 已实现但未被使用

**代码位置**: `domains/session/v2/turn_reader.go`

```go
// LoadLatestOutbound returns the exact message body most recently forwarded to
// the upstream model. Unlike LoadChain, this preserves gateway compression
// summaries and markers stored in session_bodies.outbound_body.
func (r *TurnReader) LoadLatestOutbound(ctx context.Context, tenantID, sessionID string) ([]Message, error)

// LoadChain 返回最近 N 轮拼接后的消息（用于 L3 冷启动）。
// 不持久化 panorama；仅按需计算。
func (r *TurnReader) LoadChain(ctx context.Context, tenantID, sessionID string, lastN int) ([]Message, error)
```

**使用情况**：
- ✅ 在 `domains/hooks/compression/session_cache.go` 中**有调用**
- ❌ 但**仅作为 L3 fallback**，不是主流程
- ❌ 压缩层主流程仍使用 `request_logs` 的完整历史

## 4. 存储优化目标达成情况

### 4.1 设计目标

**00-完整方案文档 §1.2**：
- 磁盘节省：60-80%（通过增量存储）
- 查询优化：元数据查询更快（分表存储）

### 4.2 实际情况

| 指标 | 设计目标 | 当前状态 | 达成率 |
|------|---------|---------|--------|
| **V1 表存储** | 逐步下线 | 仍在主写入 | 0% |
| **V2 表存储** | 主存储 | 影子写入 | 50% |
| **增量存储节省** | 60-80% | 0%（未使用增量读取） | 0% |
| **查询性能** | 提升 | Admin API 已提升 | 30% |
| **压缩流程优化** | 使用 V2 | 未使用 V2 | 0% |

**结论**：
- ✅ **写入**已实现增量存储（V2 影子写入）
- ❌ **读取**仍使用完整历史（V1 表）
- ❌ **存储节省目标未达成**（因为 V1 和 V2 同时写入）

## 6. 风险与影响评估

### 6.1 当前架构的风险

| 风险 | 影响 | 概率 | 严重性 |
|------|------|------|--------|
| **双写维护成本** | V1/V2 同时维护，数据一致性难保证 | 高 | 中 |
| **存储成本持续** | V1 未下线，存储未节省 | 高 | 高 |
| **缓存架构混乱** | 两套缓存并存，难以理解和调试 | 高 | 中 |
| **V2 投资浪费** | V2 表和代码已实现但未使用 | 高 | 高 |
| **性能优化受阻** | 无法利用增量读取优化查询性能 | 中 | 中 |

### 6.2 切换到 V2 的风险

| 风险 | 缓解措施 |
|------|---------|
| **读取性能回退** | 先做性能测试，确保 V2 读取不慢于 V1 |
| **数据完整性** | 保留 V1 作为 fallback，灰度切换 |
| **压缩逻辑变化** | 单元测试覆盖所有压缩场景 |
| **回滚复杂度** | 通过 Feature Flag 控制，秒级回滚 |
