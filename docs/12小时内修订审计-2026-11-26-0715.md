## 3. 缺陷证据（逐条）

### 3.1 D-1 —— `clipped` 计数的锁内写 / 锁外读（最重的一条）

**基点代码**（`40af488cc`）：

```go
// internal/logging/recent.go:83-92   写侧：持锁
r.mu.Lock()
...
if len(line) < len(rawLine) {
    r.clipped++          // ★ 锁内写
}
r.mu.Unlock()

// internal/logging/recent.go:334     读侧：锁外
res.ClippedLines = recentWarnRing.clipped + recentInfoRing.clipped
// internal/logging/recent.go:448     读侧：锁外
Clipped:   recentWarnRing.clipped + recentInfoRing.clipped,
```

同一个 `int64` 既有锁内写、又有锁外读 ⇒ 按 Go 内存模型是**数据竞争**。
**实测复现**（`go test -race`，本轮新增用例）：

```
WARNING: DATA RACE
Write at ... by goroutine 133:  internal/logging.(*recentRing).push()      recent.go:90
Previous read at ... by goroutine 135: internal/logging.RecentBufferStats()  recent.go:448
...
internal/logging.SearchRecent()  recent.go:334
```

**为什么仓里的 `-race` 复跑一直是绿的**：既有的并发用例
`TestRecentTap_ConcurrentWriters` 写的行**都短于上限** ⇒ **不触发** `r.clipped++`
⇒ 读侧也就**读不到**那个字段的竞争 ⇒ ⇒ **「并发用例跑过了」≠「并发路径被覆盖了」**。

**修法**：加唯一的读出口 `clippedCount()`（持锁读），两个读点改走它；
**并新增一条按「被竞争字段的写入条件」造输入的并发用例**（持续写超长行 ＋ 并发调两个读出口）。

### 3.2 D-2 —— PI 取证 playbook 步漏了 recover / 统一超时 / 必然 cancel

**基点代码**（`40af488cc`）：六路取证里，**五路**走 `run(...) → g.step(...)`，
而 `step()`（`:258-264`）里有全文件**唯一**的 panic 收口：

```go
func (g *PIEvidenceGatherer) step(b *..., name string, budget piEvidenceBudget, fn func(ctx context.Context) error) {
	defer func() {
		if r := recover(); r != nil {          // ★ 全文件唯一的 recover
			b.NoteDegraded(name, ...)
			slog.Error("pi_analysis: evidence step panicked", ...)
		}
	}()
	ctx, cancel, ok := budget.stepCtx()
	if !ok { b.NoteDegraded(name, budget.note(name)); return }
	defer cancel()                            // ★ cancel 由 defer 保证
	...
}
```

**而 playbook 步（⑥）是唯一绕过它的一路**：

```go
c, cancel, ok := budget.stepCtx()   // ★ 手工配对：panic ⇒ cancel() 不执行 ⇒ context 泄漏到超时
if !ok { b.NoteDegraded("playbook", budget.note("playbook")); break }
part, err := g.playbookEntries(c, et)
cancel()
```

⇒ 三处缺陷合一：① panic 打到 HTTP 路径只有 `net/http` 的连接级 recover（请求 500/断连），
打到后台分析 worker 则**整轮分析作废**而不是降级成「这一路没算出来」；
② `cancel()` 手工配对 ⇒ panic 时**不执行** ⇒ context 泄漏到超时；
③ 超时被混进「失败」里 ⇒ 取证摘要**看不出是超时还是出错**（与上游刚修好的「超时判定不看驱动报什么错」不一致）。

**修法**：统一走 `step()`（`run`），一次拿到 recover ＋ `defer cancel` ＋ 统一超时/失败归因；
并用 `called` 标志区分「预算用尽（fn 没被跑）」与「出错/降级」，**逐条保持原语义**（不重复记说明）。

### 3.4 D-4 —— 结束原因存储无上界

**基点代码**：`domains/promptinjection/llm_client_gateway.go:69`
`finishReasons sync.Map`，`:214` 每次 `Analyze` 都 `Store`，
**全文件 1 处 Store、0 处 Delete/Range** ⇒ 键是**逐次不同**的提示词哈希
（提示词含本次取证的摘要 ⇒ 每次分析都不同）⇒ ⇒ **每条分析新增一条永不留存的记录**
⇒ ⇒ 长生命周期进程内**无上界增长**（只有进程重启才释放）。

**修法**：换成**有界 FIFO**（容量 256 ＝ 明显大于并发分析数，又必须有上界）：
同键重复写入**就地更新、不占新槽位**（保住「最近一次」这个语义）；超容量淘汰最老的一条。
**淘汰代价可接受**：读出口 `FinishReasonForCall` 是分析端的**可选扩展**
（`finishReasonForCaller`）⇒ 读不到时返回空串 ⇒ 下游只是少一个可选字段，**不是错误路径**。

### 3.5 D-5 —— S5 的两库归因口径分叉（待 owner，见 §5.4）

**实测**：`usage_ledger_hot` 的 `canonical_id` **只在 INSERT 时写**
（`domains/hooks/observability/telemetry/client.go:1419`）；
**终态 UPDATE 的 SET 清单里没有 `canonical_id`**（该列在 `update_parity_test.go` 里被明确列为 immutable）。

## 6. 本轮方法论记要（四条）

1. **「并发用例跑过了」≠「并发路径被覆盖了」**：D-1 之所以长期是绿的，是因为既有用例写的行
   **短于上限** ⇒ 不触发被竞争字段的写入 ⇒ **量具没咬住被测路径**。
   ⇒ 通用式：**造并发输入要按「被竞争字段的写入条件」造，不是按函数名造**。
2. **「同一口径写两份 ⇒ 迟早分叉」**：D-3 是这条教训的**第二次**复现（上一轮是方案A 的闸与
   `deploy-surface.sh`）。仓里已经有唯一真源，新的门却又手写了一份 regex 抄本。
   ⇒ 通用式：**新判据落地时先找唯一真源；找不到就当场立一个并把抄本钉住**。
3. **「绕门」与「改门」必须由主人选边**：D-7 里，代码改了**自家文件名**去迎合门的正则，
   缺陷留在门里 ⇒ 下一个新文件会以不同形态复发。
