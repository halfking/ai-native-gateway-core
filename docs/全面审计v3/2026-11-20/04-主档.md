### ② TTL「必须一致」的两份拷贝只改了一份（子审计 B → 根修）
spec `lifecycle.session_turns_probe_hot_ttl_days` 自述「Default 就是 fallback 的宿主 ⇒ 两者必须一致（14）」，但 2026-11-17 `b6ee9e543` 有意收窄到 7 时只改了 fallback 与钉测、**漏改 spec 侧**。而 spec 在场时生效的是 spec Default ⇒ **那次收窄从未真正生效**（生产仍按 14 天保留）。
⇒ ★ **通用式：fallback 常量与 spec Default 是同一个值的两份拷贝，改一侧必须改两侧；且 spec 侧生效优先级更高——漏改的那侧恰恰是真正生效的那侧。** 已修：spec Default 14→7（bg+settings 测试绿）。

## 八、本轮沉淀通用式（7 条）

1. **子代理的「生产侧」推定必须主控活体复核后定级**（不能连生产 ⇒ 证据链止于仓内，P1 级结论尤其如此）。
2. **fallback 常量与 spec Default 是同一值的两份拷贝；spec 侧生效优先级更高，漏改侧=改动从未生效**。
3. **增量红归因先跑基线树对拍**；并行列车「各改各的、合并后量具先碎」是常态——量具修法优先钉关键形状，不逐字钉会漂移的细节。
4. **mock 要跟随依赖链演化**：组件接新组件 ⇒ 其传递依赖也进了测试上下文，整模块 mock 会把「没 mock 的导出」变成渲染即抛。
5. **登记表的前提本身也要被审计**（NON_NAVIGABLE 靠「文件无 router.push」前提——前提失效，登记全失效）。
6. **验收脚本「自称就绪」≠可运行**：四个硬伤里每一个都会让活体验证静默跳过——验收资产要真跑一次才算交付（与 58 轮「自述与实现不符」同族）。
7. **共享工作树多车并行的提交纪律**：只 add 自己的文件清单；对方的在途件（哪怕是同族缺陷的修复）不代提交、不重复计功。
