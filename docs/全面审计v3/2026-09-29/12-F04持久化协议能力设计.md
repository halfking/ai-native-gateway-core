## 2. 实际缺口

按 `bg/credential_probe_v2.go::writeHealth` 与 `credentialfpslot.NodeState` 的语义对照：

- `writeHealth` 的 `probeResult{HealthSource: "probe"}` 写入 PG（`nodes` 表）+ 通过 `stateManager credentialstate.StateObserver` 触发 routing 侧 cache 失效
- `credentialfpslot.NodeState` 在 Redis 里维护 cooldown（`Disabled` + `DisabledUntil` + `DisabledReason`），但 **DisabledReason 只是字面 reason，缺少"该 credential 协议能力"的字段**
- 即：探针检测到"Responses 不支持"后，**只触发 cooldown disable**，没有把"协议能力"持久化下来
- `executor_chat.go:498` 在每次请求时**重新调** `ResponsesUnsupportedError`，不查 NodeState 是否有过往结论

实际后果（从代码可推出，未真跑）：
- 同一 credential 在 1h TTL 内**每次**新请求都先发 Responses（probe cooldown 与"协议能力"是两件事：cooldown 是临时健康降级，protocol capability 是"这种模型永远不支持这个协议"）
- 直到 `providercap.ResponsesUnsupportedError` 在新请求的响应里再被检出 → 单请求内回退 Chat
- 没有"探针写过 → 下次直接 Chat"的闭环

## 3. 提案

### 3.1 数据层

最小改动优先复用 `credentialfpslot.NodeState`：

```go
// credentialfpslot/node_state.go
type NodeState struct {
    // ... 现有字段 ...
    Disabled       bool   `json:"disabled"`
    DisabledUntil  int64  `json:"disabled_until,omitempty"`
    DisabledReason string `json:"disabled_reason,omitempty"`

    // F04 新增：协议能力位（durable，按 capability 维度而非 cooldown）
    Capabilities   NodeCapabilities `json:"capabilities,omitempty"`
    CapabilityUpdatedAt int64        `json:"capability_updated_at,omitempty"` // unix seconds
}

type NodeCapabilities struct {
    // SupportsResponses=false 表示该 credential 上 Responses 协议不可用
    SupportsResponses *bool  `json:"supports_responses,omitempty"`
    // 同样方法可加 SupportsChat / SupportsAnthropicMessages 等
}
```

`*bool` 而非 `bool`：缺省（从未探测）= nil，**false 必须是显式观测结果**。否则初次未探测被误判为"不支持"。

### 3.2 写端

`bg/credential_probe_v2.go::writeHealth` 检测到 `providercap.ResponsesUnsupportedError(resp.HTTPStatus, resp.ErrMsg)` 时，**除了写 cooldown** 还写 NodeState 的 `Capabilities.SupportsResponses = ptr(false)` + `CapabilityUpdatedAt = now`。

需要 `credentialfpslot.Manager` 引用被 `CredentialProbeV2` 持有（同 `stateManager` 的位置）。

### 3.3 读端

`executor_chat.go:498` 在尝试 Responses 之前：

```go
state, _ := fpsMgr.GetNodeState(ctx, credID, model)
if state != nil && state.Capabilities.SupportsResponses != nil && !*state.Capabilities.SupportsResponses {
    // 该 credential 已知不支持 Responses，直接走 Chat fallback
    return executeChat(...)
}
```

TTL 由 `NodeState` 整体 TTL 控制（3600s）。**过期的 NodeState 视为"未知能力"，不命中此短路**——保守回退到实时检测路径。

### 3.4 反向恢复

只有某 credential/model 后续真正取得 **native Responses 成功响应**，才能把 `Capabilities.SupportsResponses` 翻转为 true（或 nil 重置）。Chat fallback 成功只证明 Chat 可用，不能作为 Responses 能力的正向证据；该写入应发生在原生 Responses 请求完整成功后，而不是 fallback Chat 成功后。

否则一旦误标"不支持"，会一直阻塞 1h 内所有 Responses 请求。

## 5. 实施顺序

1. `credentialfpslot` 加 `Capabilities` 字段（向后兼容：JSON 解析时缺字段即 nil）
2. `bg/credential_probe_v2.go` 注入 `fpsMgr`，在 `writeHealth` 失败/成功分支同步 NodeState
3. `executor_chat.go:498` 前置查询短路
4. 上面 4 个测试
6. 真 PG + 真 Redis Cluster 下重跑

## 6. 不在范围

- 不动 Lite 模式的 capability 持久化（lite 无 Redis，capability 必重置为实时检测；保留 `Redis 不可用 → capabilities 永为 nil` 的回退路径）
- 不动 cooldown 健康机制（`Disabled` / `DisabledUntil` 与 protocol capability 是两件事，可同时存在）
- 不做端点 / 跨节点协议能力的合并（接口仍然按 credential 粒度）
