# P2-3 架构误判补充说明（2026-11-14）

## 一、误判经过

1. **初始问题陈述**（B 组子代理审计）：responses trim（compressResponsesInput）可产出零 user 的 responses input，转 chat 上游时复现 r1048 的智谱 400 code 1214「messages 参数非法」。
2. **首版修复尝试**：在 `domains/transformation/responses_compress.go` trim 层加 user 守卫 → 被既有钉测 `TestCompressResponsesInputIfNeededKeepsFunctionCallPairAtomic` 当场抓红（「删旧 user 保末项 function pair 原子」是 trim 层合法契约）。
3. **层级裁决**：撤回 trim 层守卫，改判「正确层级 = responses→chat 转换之后、发上游前的 chat 形状」，登记为 P2-3 待修。
4. **深度验证**（2026-11-14 执行阶段）：追踪 responses→chat 转换的真实调用链，发现**三层架构事实证伪原问题**。

## 二、架构事实（证伪依据）

### 事实 1：responses→chat 转换不经过 responses trim

**代码位置**：`domains/streaming/executors/executor_chat.go`

```
946:  nativePair := nativePairFor(params, cand, sourceBody)
990-1030: if nativePair {  // responses 原生上游分支
1019:     bodyBytes, responsesTrimMeta = transformation.CompressResponsesInputIfNeededWithMeta(sourceBody, contextWindow, reserve)
          // ← trim 只在此分支执行
...
1031: } else {  // responses→chat 转换分支
1031:     bodyBytes, err = e.finalizeOpenAIUpstreamBodyNative(params, cand, sourceBody, nativePair)
          // ↓ 此函数内部（3156-3183 行）直接 ParseResponses(sourceBody)
3156:     irReq, err := irScoped.ParseResponses(sourceBody)
          // sourceBody 是原始 body，未经 trim
3183:     bodyBytes, err := irScoped.SerializeOpenAI(irReq)
...
}
```

**结论**：`nativePair` 判定产生两个**互斥分支**：
- `nativePair=true`：responses 原生上游（如 OpenAI 自己的 responses 端点），走 trim → 直接出站
- `nativePair=false`：需要转换的上游（如智谱只认 chat 格式），**不走 trim**，直接拿 `sourceBody` 进入 ParseResponses → SerializeOpenAI

因此「trim 产出零 user，转 chat 上游时触发」的场景**不可能发生**——两者分属互斥分支。

### 事实 2：sessioncontext Reduce 保护首条/最新 human user

**代码位置**：`internal/sessioncontext/protected.go:76-123`

```go
func protectInfo(info []messageInfo) ([]bool, int) {
    keep := make([]bool, len(info))
    // ...
    first, tail, human := -1, -1, -1
    for i, m := range info {
        if m.role == "user" {
            tail = i
            if len(m.refs) == 0 {
                human = i
                if first < 0 {
                    first = i  // 首条 human user
                }
            }
        }
    }
    if first >= 0 {
        keep[first] = true  // 保护首条
    }
    if human >= 0 {
        keep[human] = true  // 保护最新
    }
    // 末项之后全保护 + 工具链闭包传播
}
```

**结论**：LargeIngress 的 sessioncontext Reduce 至少保护一条 human user（首条或最新），除非输入本身就没有任何 user message（那种情况是入口层 `HasUserMessage` 门已拒绝的）。

### 事实 3：responses trim 只作用于 responses 原生上游

responses trim 产出零 user 后，body 直接发往**认识 responses 格式的原生上游**（如 OpenAI 自己的 /v1/responses 端点）。那些上游的零 user 约束是它们自己的 API 规范，不是网关的问题。

## 三、误判教训

1. **架构假设必须代码验证**：「trim 可产出零 user」是真的，「转 chat 上游时触发」假设了两者在同一路径——未验证调用链即做出判断。
2. **互斥分支的隐蔽性**：`nativePair` 判定在 executor 内部，从 trim 函数名（`CompressResponsesInput`）无法直接看出它只作用于原生上游分支。
3. **既有钉测抓红是线索不是阻碍**：`KeepFunctionCallPairAtomic` 抓红说明 trim 层的零 user 是**合法契约**，应该追问「为什么合法」而非「怎么规避钉测」——答案就是两个分支的隔离。

## 四、后续建议

如果未来确实需要「responses 原生上游也强制 ≥1 user」，正确修复层是：
- **位置**：`executor_chat.go:1019` trim 之后、`nativePair` 分支出站之前
- **判定**：检查 trim 后 `bodyBytes` 的 input 数组，零 user 时回插或拒绝
- **不影响**：responses→chat 转换分支（那条路径不走 trim）

但这需要明确的需求裁决：responses 原生上游的零 user 约束应该是**上游自己的规范**，网关不应代为强制（与「chat 上游必须 ≥1 user」的 r1048 修复不同——那是所有 chat 上游的通用约束）。
