## 1. 架构分析

### 1.1 V1 存储架构（Primary）

**核心表**: `request_wal` (partitioned by created_at)

**关联表**:
- `request_wal_hot` - 热数据分区
- `request_wal_bodies` - 请求/响应正文
- `request_wal_archive` - 归档分区
- `request_envelope` - 请求信封元数据
- `session_request_summaries` - 会话级汇总

**写入特性**:
- 同步写入，请求处理的关键路径
- 必须成功，否则整个请求失败
- 事务保证
- 完整的请求/响应数据

### 1.2 V2 存储架构（Shadow）

**核心表**:
- `sessions` - 会话快照（1 per session）
- `session_turns` - 轮次元数据（无正文）
- `session_bodies` - 增量消息增量（列式存储）
- `session_turn_logs` - 处理阶段日志（24h TTL）

**写入特性**:
- **异步写入**，不在关键路径
- 允许失败，不影响请求成功
- 独立事务（V2 内部事务一致性）
- 2秒超时预算

**代码证据**:

## 3. 一致性保证与失败模式

### 3.1 事务边界

| 维度 | V1 (request_wal) | V2 (session_turns) |
|------|------------------|-------------------|
| **事务范围** | 单个请求写入 | turn + bodies + session（V2内部） |
| **跨系统事务** | ❌ 无 | ❌ 无 |
| **失败回滚** | 请求级回滚 | V2内部回滚 |

**关键结论**: ⚠️ **V1 和 V2 之间没有跨系统事务保证**

### 3.2 失败模式矩阵

| 场景 | V1 状态 | V2 状态 | 请求结果 | 数据一致性 |
|------|---------|---------|---------|------------|
| **正常** | ✅ 写入成功 | ✅ 写入成功 | ✅ 成功 | ✅ 一致 |
| **V1 失败** | ❌ 写入失败 | - 未执行 | ❌ 失败 | ✅ 一致（都无数据） |
| **V2 超时** | ✅ 写入成功 | ⏱️ 2s 超时 | ✅ 成功 | ⚠️ **V1 有，V2 无** |
| **V2 DB 错误** | ✅ 写入成功 | ❌ 写入失败 | ✅ 成功 | ⚠️ **V1 有，V2 无** |
| **协程池满** | ✅ 写入成功 | 📋 进队列 | ✅ 成功 | ⚠️ **延迟一致** |
| **队列失败** | ✅ 写入成功 | 💾 内存缓冲 | ✅ 成功 | ⚠️ **可能丢失** |
| **过滤规则** | ✅ 写入成功 | 🚫 跳过 | ✅ 成功 | ⚠️ **V1 有，V2 无（设计）** |

### 3.3 三层容错机制

**层级 1: 直接异步写入**
- 并发限制: 8 个协程
- 超时: 2000ms（可配置 `sessions_v2.write_timeout_ms`）
- 失败处理: 进入层级 2

**层级 2: 持久化队列（Outbox）**
- 表: `session_mirror_outbox`
- 状态: pending → claimed → dead
- 重试策略: 指数退避
- 后台 reaper 处理

**层级 3: 内存缓冲（Backlog）**
- 位置: 进程内存
- 容量: 有限
- 持久性: ❌ 进程重启丢失
- 用途: DB 完全不可达时的降级

**代码证据**:
```go
// internal/sessionv2mirror/hook.go:191-203
default:
    // All shadow-write slots are busy
    metrics.Global().RecordShadowWriteFailure("session_v2")
    if !EnqueueMirrorFailure(entry, sessionID, "semaphore_full") {
        // 队列也失败 → 内存缓冲
        appendBacklog(BacklogItem{...})
    }
}
```

## 5. 数据差异根因分析

### 5.1 过滤规则（Hook 中实现）

基于代码分析，以下请求**不会**写入 V2:

**过滤类别 1: 状态过滤**
- 位置: `hook.go:83-84`
- 规则: `!entry.Success && !isTerminalFailure(entry)`
- 说明: 进行中状态（in_progress）的占位符写入不镜像
- 影响: V1 有占位符行，V2 只有终态

**过滤类别 2: 探针隔离**
- 位置: `hook.go:90-96`
- 规则: `probelane.ShouldIsolate(...)`
- 说明: 物理隔离的探针流量（健康检查、监控）
- 影响: 探针请求进 `session_turns_probe_hot`，不进业务表

**过滤类别 3: 合成会话探针**
- 位置: `hook.go:105-107`
- 规则: `IsProbeSyntheticSession(entry)`
- 说明: 无会话头的探针（`sys:probe:*` 合成会话）
- 影响: 避免探针集中锁争用（实测 ~115/min 失败噪声）

**过滤类别 4: 内部自动请求**
- 位置: `hook.go:126-128`
- 规则: `IsInternalAutoEntry(entry)`
- 说明: 内部标题/摘要生成等回环请求
- 影响: 非用户轮次不计入会话

**过滤类别 5: 特性开关**
- 位置: `hook.go:136-138`
- 规则: `!shadowWriteEnabled()`
- 说明: `sessions_v2.shadow_write` 特性开关
- 影响: 全局或租户级关闭影子写入

### 5.2 差异量化估算

| 过滤类别 | 预估占比 | 说明 |
|---------|---------|------|
| 探针流量 | 30-40% | 健康检查、监控、自检 |
| 进行中状态 | 5-10% | 占位符写入，后续更新 |
| 内部请求 | 5-10% | 标题生成、自动路由 |
| 特性开关关闭 | 未知 | 取决于配置 |
| **合计** | **40-60%** | **与实测 56% 吻合** |

**结论**: ✅ **56% 差异主要由设计意图的过滤规则导致，而非系统故障**

## 6. 迁移状态评估

### 6.1 当前阶段

**阶段名称**: "Shadow Write" / "Parallel Storage"

**特征**:
- ✅ V1 (request_wal) 是主存储和真实来源
- ⚠️ V2 (session_turns) 是影子副本，用于验证和准备
- ⚠️ V2 有意不完整（过滤了非业务流量）
- ✅ 两套系统并行运行
- ✅ 查询主要基于 V1，部分新功能使用 V2

### 6.2 迁移路线图（推测）

```
当前阶段: Shadow Write（V2 验证期）
         ↓
阶段 2: Dual Write（V2 完整性验证）
         - 移除过滤规则，所有流量写入 V2
         - V1/V2 数据对齐验证
         ↓
阶段 3: Dual Read（V2 读取验证）
         - 查询同时读 V1 和 V2
         - 结果一致性验证
         ↓
阶段 4: V2 Primary（切换主存储）
         - V2 成为主存储
         - V1 降级为备份/归档
         ↓
阶段 5: V1 Sunset（淘汰 V1）
         - 完全迁移到 V2
         - V1 下线
```

## 8. 推荐方案

### 8.1 立即行动（P0）

**行动 1: 建立 V1/V2 一致性监控**

目标: 量化和追踪数据差异

实施:
```sql
-- 每日一致性报告
CREATE VIEW v1_v2_consistency_daily AS
SELECT 
  date_trunc('day', rw.created_at) as date,
  COUNT(DISTINCT rw.request_id) as v1_requests,
  COUNT(DISTINCT st.request_id) as v2_requests,
  COUNT(DISTINCT rw.gw_session_id) as v1_sessions,
  COUNT(DISTINCT st.session_id) as v2_sessions,
  ROUND(COUNT(DISTINCT st.request_id)::numeric / 
        NULLIF(COUNT(DISTINCT rw.request_id), 0) * 100, 2) as coverage_pct
FROM request_wal rw
LEFT JOIN session_turns st ON rw.request_id = st.request_id
WHERE rw.created_at > NOW() - INTERVAL '30 days'
GROUP BY date_trunc('day', rw.created_at)
ORDER BY date DESC;
```

告警阈值:
- 覆盖率 < 40% → P2 告警
- 覆盖率 < 30% → P1 告警
- 覆盖率下降 >10% 单日 → P0 告警

**行动 2: 验证 shadow_write 开关状态**

```sql
-- 检查特性开关配置
SELECT key, value, updated_at
FROM settings_kv
WHERE key LIKE '%sessions_v2%';
```

确认:
- `sessions_v2.shadow_write` = true (全局启用)
- `sessions_v2.enabled` = true
- `sessions_v2.write_timeout_ms` = 2000 (或更高)

**行动 3: 检查 Outbox Reaper 健康度**

```sql
-- 监控队列堆积
SELECT 
  status,
  COUNT(*) as count,
  MAX(created_at) as latest,
  NOW() - MAX(created_at) as age

```

告警条件:
- pending 队列 > 1000 条
- 最老 pending 记录 > 1 小时

### 8.2 短期行动（P1）

**行动 4: 明确迁移路线图**

需要 owner 决策:
1. V2 何时成为主存储？
2. 是否移除过滤规则以达到完全覆盖？
3. 探针流量是否需要进 V2？
4. 迁移时间表和里程碑

**行动 5: 数据对账和修复**

针对关键业务数据:
```sql
-- 识别 V1 有但 V2 缺失的关键会话
SELECT 
  rw.gw_session_id,
  COUNT(*) as v1_turns,
  COUNT(st.request_id) as v2_turns
FROM request_wal rw
LEFT JOIN session_turns st ON rw.request_id = st.request_id
WHERE rw.created_at > NOW() - INTERVAL '7 days'
  AND rw.gw_session_id IS NOT NULL
  AND rw.status = 'completed'  -- 只看终态
GROUP BY rw.gw_session_id
HAVING COUNT(st.request_id) = 0  -- V2 完全没有
ORDER BY v1_turns DESC
LIMIT 100;
```

建立回填机制:
- 从 V1 读取缺失数据
- 通过 V2 Writer 写入（标记为 backfill）
- 验证数据完整性

### 8.3 中期行动（P2）

**行动 6: 性能优化**

3. **中期**: 优化查询避免需要并行执行
4. **长期**: 迁移到更大内存的 PG 实例

**行动 7: 统一数据访问层**

创建抽象层:
```go
type SessionDataReader interface {
    GetSessionTurns(ctx context.Context, sessionID string) ([]Turn, error)

// 自动路由到 V1 或 V2
type AdaptiveReader struct {
    v1Reader V1Reader
    v2Reader V2Reader
    config   *ReaderConfig

func (r *AdaptiveReader) GetSessionTurns(ctx context.Context, sessionID string) ([]Turn, error) {

    }
    return r.v1Reader.GetSessionTurns(ctx, sessionID)
}
```

## 9. 结论

### 9.1 核心发现总结

✅ **架构理解正确**:
- V1 是主存储（同步、事务保证）
- V2 是影子副本（异步、最终一致性）
- 两者无跨系统事务

✅ **数据差异符合预期**:
- 56% 差异主要由过滤规则导致
- 探针、内部请求、占位符等被有意排除
- 非系统故障或数据丢失

⚠️ **一致性风险可控但需监控**:
- V1 为准，V2 用于新功能
- 三层容错机制（写入 → 队列 → 缓冲）
- Outbox 为空表示重试机制工作正常

⚠️ **迁移路径尚不明确**:
- V2 何时成为主存储未知
- 过滤规则是否移除待定
- 需要 owner 路线图决策

### 9.2 对会话分析的影响

**当前状态**:
- 会话分析 API 主要查询 V2 (session_turns)
- V2 只有 44% 的数据覆盖
- 探针流量、内部请求不在 V2 → 分析不受影响（正确）
- 但业务请求也有缺失 → 分析可能不完整

**风险**:
