## 一、请求主链（业务流 + 注入/脱敏/输出检测 + 压缩 + 缓存 + 超长支持）

```
客户端(chat/messages/responses/Gemini 四协议)
  → cmd/gateway/main.go 中间件链(Recovery→Logging→maintain→Auth→SecurityHeaders)
  → 协议入口反序列化（请求侧协议适配）
  → IR 归一化（internal/ir/）
  → 拦截链 domains/hooks/：
      入向 request_hook（注入检测 security/ 敏感脱敏）
      → 脱敏三层 provenance（security/sanitize/ + domains/hooks/compression/alignment.go）
      → 上下文压缩（domains/hooks/compression/compressor.go / domains/transformation/ctx_compress.go）
      → 超长归档（domains/sessioncontext/file.go：>1MiB RAW 落盘 + Reduce）
  → 路由 autoroute/ + provider/candidates_circuit.go（候选熔断/park 预算）
  → 队列 domains/dispatch/（forwarder/journal/failover/pipeline）+ key_concurrent_gate.go（按 key 并发闸）
  → 出向协议适配（upstream/client.go + internal/providercap/capability.go 能力探测）
  → 响应流 domains/streaming/（executors 四协议执行器 + response/chain.go 拦截链）
      出向：输出合规 outputcompliance（native_restore.go 还原敏感信息）+ provenance（executors/executor_responses_provenance.go）
  → 落账 request_logger（request_wal → request_logs/session_turns 家族）+ hooks/audit（流式捕获）
```

**闭环缺口检测点**（objective「流程闭环/数据闭环/反馈闭环」）：
- D-F1 每个入向改写（脱敏/压缩/截断）必须在出向/落账侧有对应还原或标记（alignment.go + alignment_reverse.go 双向）。
- D-F2 上游错误 → errorsx 分类 → 错误日志表 → 凭据详情呈现 → think 模式透出（objective「供应商错误记录」）——链路各环节消费方逐个核验。
- D-F3 session.closed → 画像/摘要 worker 认领（`d1f64a879` 修的双行扇出）——幂等性复核。

## 三、存储架构

### 3.1 全量 vs lite 双模式 ✅
`config/storage.go`：full（PG+Redis+memory+files）/ lite（SQLite+本地目录，`lite_storage` 段 + PRAGMA 调优项）。校验：lite 模式要求 sqlite_path 非空（`:214`）。

### 3.2 hot+分区（columnar）✅
- `bg/partition_manager.go`（+ probe_lane_ttl 测试）：分区生命周期。
- 既往定案（191–194 号）：`request_wal` UPDATE 只打 hot，出 hot 即 no longer editable（intended）；分区边界时区污染三种形态（24 显式 +08 + 38 无时区字面量）**未修**（待裁决 78）——本轮只登记不扩修。
- session_turns 家族 probe hot TTL：59 轮已根修 spec Default 14→7 双侧一致。

### 3.3 request_logs → session_turns 切换（objective 第 4 项）
◈ 既有事实（191/192 号）：`request_wal` 与 `request_logs` 并存；「全部切到 session_turns 且原 API 不出错」是**长期工程项**，59 轮未触达——本轮由统计标准化轮审计（子审计 B）顺带核对「request-logs 探测臂」的口径依赖，不启动切表工程。
