## 四、会话压缩与上下文适配

### 4.1 Fit() 函数逻辑

```go
// 文件: internal/sessioncontext/fit.go
func Fit(body []byte, maxBytes int) ([]byte, error)
```

**工作原理**:

1. **保护区识别** (protectedMessages):
   ```
   - 首个任务消息
   - 所有特权指令
   - 最新的完整用户/工具交互组
   ```

2. **可压缩区** (old history):
   ```
   - 除保护区外的历史消息
   ```

3. **压缩策略**:
   ```go
   // 1. 构建基线 (只保护区，无摘要)
   base := build("")
   
   // 2. 如果基线超预算 → 拒绝
   if len(base) > maxBytes {
       return nil, ErrProtectedContext
   }
   
   // 3. 计算剩余预算
   remaining := maxBytes - len(base) - 256
   
   // 4. 采样旧历史文本
   text := plainText(old)
   digest := sha256.Sum256(body)
   prefix := fmt.Sprintf("[Earlier history reduced; source %x. Excerpts...]", digest[:8])
   
   // 5. 迭代尝试不同采样长度
   for limit := remaining / 2; limit >= 64; limit = limit * 3 / 4 {
       summary := prefix + sampleText(text, query, limit)
       out := build(summary)
       if len(out) <= maxBytes {
           return out, nil
       }
   }
   
   // 6. 兜底返回基线 (仅保护区)
   return base, nil
   ```

**新增功能 (48小时内)**:

1. **P1-C (2026-11-23)**: `ErrSingleMessageTooLarge`
   ```go
   // 单条受保护消息本身就超过了剩余预算
   var ErrSingleMessageTooLarge = errors.New(
       "single protected message exceeds context budget")
   ```

2. **P1-D (2026-11-23)**: 媒体省略标记
   ```go
   // 当旧消息包含媒体被移除时，添加明确标记
   for _, msg := range old {
       if fitHasMedia(msg) {
           prefix += "[media omitted from bounded context]\n"
           break
       }
   }
   ```

### 4.2 ⚠️ 信息保真度风险

**风险评估**:

1. **采样策略非确定性**:
   ```go
   func sampleText(text, query string, limit int) string
   ```
   - ⚠️ 采样算法可能不是确定性的
   - ⚠️ 相同输入可能产生不同输出
   - ⚠️ 影响可复现性和调试

2. **跨段上下文丢失**:
   ```
   问题: 段 A 提出的问题在段 B 才回答
   风险: 采样可能割裂上下文关联
   ```

3. **关键细节过滤**:
   ```
   问题: 技术细节、数字、专有名词可能被视为"不重要"
   风险: 对技术讨论影响较大
   ```

4. **迭代衰减**:
   ```
   压缩 → 再压缩 → 多次压缩
   风险: 信息累积丢失
   ```

**建议**:
- [ ] 添加信息保真度测试
- [ ] 对比压缩前后的模型响应质量
- [ ] 考虑添加降级回退机制
- [ ] 记录每次压缩的元数据

## 七、PostgreSQL 性能问题

### 7.1 /dev/shm 限制问题

**问题描述**:
```
环境: acc-pg17 容器
/dev/shm: 64MB (固定)
并行worker: 2个 (默认)
DSM分配: 每次 4-8MB

结果:
- "could not map dynamic shared memory segment" ×338
- parallel worker FATAL ×654 / 45分钟
```

**根本原因**:
```sql
-- 查询计划选择 Gather Merge (并行)
EXPLAIN ANALYZE
SELECT MAX(turn_no) FROM session_turns_with_current_month
WHERE session_id = $1;

-- 结果:
-- Parallel Append + Parallel Hash Right Join
-- 2 workers spawned
-- 242-284ms (并行) vs 90ms (串行) = 2.7× slower!
```

**修复方案** (已实施):
```sql
-- 在 turn_writer.go 的 advisory lock SQL 中:
SELECT set_config('max_parallel_workers_per_gather', '0', true),
       pg_advisory_xact_lock(...)

-- 'true' = SET LOCAL (事务内有效，自动还原)
```

**权衡**:
- ✓ 稳定性: 消除 DSM 分配失败
- ✗ 性能: 2.7× 性能退化
- ✓ 可接受: 写操作不频繁，90ms 仍在可接受范围

**根治方案** (未实施):
```bash
# 增加容器 ShmSize (需要重建 PG 容器)
docker run --shm-size=256m ...

# 或优化查询避免并行计划
```

**⚠️ 影响范围**:
- session_turns 写入操作
- 任何使用 advisory lock 的事务
- 其他可能触发并行计划的查询

### 7.2 Advisory Lock 策略

**实现**:
