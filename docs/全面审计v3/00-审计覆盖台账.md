### 4.3 待裁决第 37 条（89 号新增，**唯一新增的 P1**）

**`session_titles` 回退路径产出非标题内容，并污染会话搜索。**

- 现象：427,770 条标题中 **189,997（44.42%）** 走 `model='auto-extract'` 回退，
  产物形态为 `system: You are ZCode…`（115,615）/ `system: [gateway-handoff-v1]…`（39,778）/
  `[ZCode] {"max_tokens":128000…`（23,867）——**无一例外全不是标题**。
- 根因（定位到一行）：`admin/auto_title_generator.go:637-663`
  `extractTitleFromPreview` 的 **3c 分支**「无 user 内容时直接用原始预览」。
  预览仅 **320 字节**，而 ZCode/Cursor 类 agentic 负载的 system prompt 本身远超 320 字节
  ⇒ `extractUserPrompt` 必然取不到 user 内容 ⇒ **必然**回落到系统提示词。**这是结构性必然，不是偶发选错。**
- 为何是 P1：`admin/turns_sessions.go:466-476` 的搜索 SQL 对 `tstate.title` 做 `ILIKE`
  ⇒ 搜 `You`/`ZCode`/`system` 会命中数万条无关会话，**且把真正要找的会话淹掉**。
- 三个修法见 89 号 §5。**方案甲已由 90 号 §1 修正**：不是「不让标题变丑」，
  而是「**让回退改用它已经构建好的 full-body `corpus`**（含真实 user message）
  而不是 320 字节 `requestPreview`」——改后 44% 的标题会变成真正的会话标题。
- **归因缺口（90 号 §2）**：四条回退路径在 DB（`model='auto-extract'`）与指标
  （`auto_title_trigger_total` 只有 short_user_message/error/ok）上**都不区分**，
  ⇒ **44.42% 的触发原因在现有数据上不可归因**。建议把回退原因并进

  **本例正是靠「74%/93% 两个中间值」才把假设空间收窄的**；只统计总量会得到无法定位的描述，
  并很可能顺手套上「滚动发布」这个现成解释——**而它是错的**。
  配套纪律：**排除一个假设要拿代码说话**——**「最合理的解释」恰恰是最该先验证的那个**，
  因为一旦写进报告，读的人会直接采信。
- **未改动任何生产代码与数据**（全部只读查询）。

### 4.43 R89-AQ（129 号自查更正）—— **「终态缺失」不能区分「从未写入」与「写入后被删」**；另更正一处 `reltuples` 数字错误

- **触发**：129 号 §三 用 `pg_class.reltuples`（**规划器估算值**）下了
  「这 25 万行**从未落库**」这种**终态结论**。
  **方法上不严密——终态缺失无法区分「从未写入」与「写入后被删除」**，
  而两者性质完全不同（缺口 vs 数据被销毁）。**按纪律回灌 129 号，不改原文。**
- **❌ 更正 1（一处数字错误）**：129 号写「07/08/10 月分区均为 0」——
  **精确 `COUNT(*)` 显示 `usage_ledger_2026_07` = 2 行，不是 0**；
  且 `usage_ledger_2026_09` 精确值是 **2,065,720** 而非 `reltuples` 的 2,065,828
  （父表 `COUNT(*)` = 2,065,722，估算与精确**差 106 行**）。
  **§一/§二 的逐日数字来自 `COUNT(*)`，不受影响。**
- **✅ 结论不变但证据从「推断」升级为「三重排除」**：
  ① **`promote_usage_ledger_hot_to_partition` 主体是单条数据修改 CTE**
     （`WITH batch AS (DELETE ... RETURNING ...), inserted AS (INSERT ... SELECT FROM moved)`）
     ⇒ DELETE 与 INSERT 在**同一条语句**内，**结构上不存在「删了没插」路径**；
  ② **hot 无滞留老行**：`min(ts)=2026-10-01 03:00:43`、`max(ts)=11:38:59`（查询时刻 11:43），
     **全部落在约 8.5 小时内** ⇒ 与 8 小时保留一致，**promote 未停摆**
     （若停摆，9 月老行会仍留在 hot 里等着）；
  ③ **绕过视图直查 `usage_ledger_2026_09` 的逐日 `COUNT(*)`**
     （09-05=25,076 / 09-06=33,396 / 09-12=24,726 / 09-13=73,795 / 09-14=36,291 / 09-15=18,272，
     09-01~04 与 09-07~11 无行）与 §二 视图口径**逐日完全一致** ⇒ 空洞在分区内部，非视图口径问题。
  ⇒ **「这 25 万行从未落库」成立**；⚠️ **真因仍未证实**（§六 保持原样）
  ——「从未写入」只排除「写完又丢」，**没有告诉我们当时为什么没写**。
- **⚠️ 同一套 promote 体系里两种写法并存（值得单独记住）**：
  `promote_usage_ledger_default_batch` 是**手写两条语句**，
  带 `RAISE WARNING '... INSERT failed (%), rows preserved in _default'`。
  **查一个表的 promote 安全性不能推广到同体系其他表。**
- **playbook §28 新增**：① 「终态缺失」不能区分「从未写入」与「写入后被删」，
  下结论前先查**删除路径是否原子**（单条 CTE 无丢失路径 / 手写两条有 / 先删后插必然有）；
  ② **`reltuples` 不能支撑「某分区是空的」**——涉及「某处为空、某物不存在」的断言**一律用 `COUNT(*)`**。
  这是 §10.1 的数据库版，**它会直接产出「不存在」这种不可逆的强断言**，是本族里最危险的一种。
