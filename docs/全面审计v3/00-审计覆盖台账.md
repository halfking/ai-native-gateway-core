### 4.3 待裁决第 37 条（89 号新增，**唯一新增的 P1**）

**`session_titles` 回退路径产出非标题内容，并污染会话搜索。**

- 现象：427,770 条标题中 **189,997（44.42%）** 走 `model='auto-extract'` 回退，
  产物形态为 `system: You are ZCode…`（115,615）/ `system: [gateway-handoff-v1]…`（39,778）/
  `[ZCode] {"max_tokens":128000…`（23,867）——**无一例外全不是标题**。
- 根因（定位到一行）：`admin/auto_title_generator.go:637-663`
  `extractTitleFromPreview` 的 **3c 分支**「无 user 内容时直接用原始预览」。
  预览仅 **320 字节**，而 ZCode/Cursor 类 agentic 负载的 system prompt 本身远超 320 字节
  ⇒ `extractUserPrompt` 必然取不到 user 内容 ⇒ **必然**回落到系统提示词。**这是结构性必然，不是偶发选错。**
- 为何是 P1：`admin/turns_sessions.go:466-476` 的搜索 SQL 对 `tstate.title` 做 `ILIKE`
  ⇒ 搜 `You`/`ZCode`/`system` 会命中数万条无关会话，**且把真正要找的会话淹掉**。
- 三个修法见 89 号 §5。**方案甲已由 90 号 §1 修正**：不是「不让标题变丑」，
  而是「**让回退改用它已经构建好的 full-body `corpus`**（含真实 user message）
  而不是 320 字节 `requestPreview`」——改后 44% 的标题会变成真正的会话标题。
- **归因缺口（90 号 §2）**：四条回退路径在 DB（`model='auto-extract'`）与指标
  （`auto_title_trigger_total` 只有 short_user_message/error/ok）上**都不区分**，
  ⇒ **44.42% 的触发原因在现有数据上不可归因**。建议把回退原因并进
  `auto_title_trigger_total` 的 result label（不动 DB schema）。
- **前提已验（91 号，结论：部分成立）**：`extractMessagesForTitle`
  （`auto_title_generator.go:539-552`）**只认顶层 `messages` 键** ⇒
  chat ✅ / Anthropic messages ✅ / **OpenAI responses ❌（用 `input` 键，恒返回 `""`）**。
  ⇒ 方案甲在 chat/messages 上成立；**responses 车道需同时补键名兼容**。
- **根因闭合为三形态两分支（91 号 §2，⚠️ 机制描述已被 92 号推翻并订正）**：不是一种坏路，是**两条不同的坏路**——
  ① **形态甲/丙**（`system: You are ZCode…`、`system: [gateway-handoff-v1]…`）：
  `userPrompt == ""` ⇒ 落 3c 分支「原样用 preview」，属**源选错**；
  ② **形态乙**（`[ZCode] {"max_tokens":128000…`）：`extractUserPrompt` 是**行式启发式**，
  而原始 JSON **是单行**且不以任何 skipPattern 开头 ⇒ 整行被收进 `userPrompt`
  ⇒ 落 3a 分支。
- **【92 号订正，两处】**（原文已加警示框，未改写）：
  ① **91 号 §2.2 那句「换一个更好的源并不能消除形态乙」是错的**，且**与 91 号自己 §3 的表格矛盾**——

     `:582-584` 只保留 user/assistant、**system 已被剔除**）⇒ 方案甲**确实能消除形态乙**。
  ② **形态甲的真因不是「320 字节只装得下 system 行」**：真库 preview 是
     **`|` 拼接的 314 字节单行、用户段就在里面**，整行以 `system:` 开头

   **本就不是同一个量**。立独立条目前必须先问「这两侧量的本来就不是同一个东西吗」。
2. **「未定义」不该编码进 `0`/`NULL`。** F4 的意图是「标记未定义」，
   但 `ComputeDiffRate` 返回 0 → `nullDiffRate(0)` 写 NULL → 读回 `COALESCE(...,0)` 抹平，
   **三处各丢一次**，最终与「差异 0%」完全同形。修法用哨兵/枚举，不用特殊数值。
3. **`AdminMiddleware` 只 `SetAuthContext`**（`admin/auth.go:76-140`，已读函数体确认）——
   不设 GUC、不改写 SQL、不按租户包事务。**租户隔离纯靠每个 handler「记得」调 helper**，
   漏写无编译期错误、无运行期告警、无测试覆盖。**这解释了 94 号漏 1 个 + 本轮 2 个死代码同形态。**

### 4.14 R89-n（102 号）收窄待裁决 42 的触发面：三条路径证伪，剩「歧义提交」一种

- ❌ **证伪 (a)**：`updateRequestLog` 的 `RowsAffected==0` 回落（`client.go:2428-2446`）前有

  （`:2460+`）**全在同一事务内**（函数起 `:2040`、事务 `:2050`）⇒ 第一次尝试被原子丢弃。
  **这段防护是对的**，恰是 100 号 §1.7 里 `api_keys` 累加器**没有**的那种。
- ❌ **证伪 (b)**：`persistRequestLog:1131` 的两条出口互斥——`degraded` 时只写 fallback

- ❌ **证伪 (c)**：`insertRequestLog`（`:1887`）与 `updateRequestLog`（`:2507`）都以

  ⇒ 「已提交但函数返回逻辑错误」不可能发生。
- ✅ **仅剩 (d) COMMIT 结果未知（歧义提交）**。缺口未完全闭合（需 PG 连接中断统计），

  修法不变；**但发生概率显著下降 ⇒ 可按正常排期做，不必按紧急止血做。**
- **本轮新增 P2（102-4）——三表在重复提交下后果非对称**：
  `request_logs_hot` 因 `ON CONFLICT (request_id) DO UPDATE` **自愈**；
  `usage_ledger_hot` 无 `ON CONFLICT` ⇒ **多一行**；`api_keys.total_cost_usd` 加法无幂等 ⇒ **翻倍**。
  **同一个故障事件，三张表三种后果——这正是「缺陷成立却难以观测」的原因**：
  宽表看着正常、台账悄悄多行、预算读数悄悄偏大。
