## 一、⚠️ 先纠正 223 号的一句话：未登记**不会**让 CI 红

223 号写的是「按 221 号坐实的台账口径，新迁移应补登记行」——暗示了它像 221 号那次一样
会让 `verify-migration-checksums.sh` 判 MISMATCH 并 `exit 1`。
**这是错的，而且是我自己没读脚本就外推的。**

`scripts/verify-migration-checksums.sh:80-82` 明写：

```bash
# Files present on disk but absent from the registry are reported as
# warnings only — db-changelog.md only records recent deploys, so older
# startup/ files are expected to be unregistered.
```

`:127` 的收尾也确实是：

```bash
echo "[verify-checksums] OK: $((${#recorded[@]})) registered migrations verified, $missing_in_registry unregistered (warn-only)"
```

⇒ **磁盘有、台账无 ⇒ 只计数 + WARN，不 `exit 1`。**
⇒ 221 号那次（816/817 被改写）是**「台账登记了、但 sha 对不上」**，方向相反；
**「台账没登记」从来就不是红门。**

⇒ 这条纠正的方法论价值高于结论本身：
**「上一轮说它像某个已知红门」不等于「它走的是同一套机制」。**
必须回去读那套机制对**这个具体输入**的处理，而不是套用上一轮的印象。

## 二、真正的发现：脚本注释的前提**曾经成立，现在正在失效**

脚本给「未登记」找的理由是「older files」——即"老文件未登记是正常的"。
**224 号按编号分桶实测，登记率随编号单调上升，这个理由已经不成立了：**

| 编号段 | 文件数 | 未登记 | 占比 |
|---|---:|---:|---:|
| 0–99 | 53 | 53 | **100%** |
| 100–199 | 1 | 1 | **100%** |
| 200–299 | 2 | 2 | **100%** |
| 300–399 | 93 | 93 | **100%** |
| 400–499 | 92 | 92 | **100%** |
| 500–599 | 66 | 52 | 79% |
| 600–699 | 93 | 15 | 16% |
| 700–799 | 63 | 10 | 16% |
| **800–899** | 21 | **2** | **10%** |
| 2000–2099（日期前缀文件） | 1 | 1 | 100% |

**登记是从 542 号前后才开始成体系的**（220 轮前后）。
⇒ 「older files」这个免责在 **< 540** 完全成立，在 **800+ 已经只剩 10%**。
⇒ 而 **803~819 连续 17 个全部有登记行** ⇒ **当前惯例明确：新迁移要登记。**

**近邻窗口（磁盘最大编号 820 往下 20）里的 3 个断档：**

```
802_session_turn_details_gw_task_id_index.sql   ← 2026-10-01 合入（907d67b85）
820_audio_modality_backfill.sql                 ← 2026-10-03 并发会话合入（21e1d66cf）
2026-07-13-multimodal-token-fields-hot.sql      ← 日期前缀命名，非编号迁移
```

⚠️ **mtime 不能当判据**：本机全部 800+ 迁移的 mtime 都是 2026-10-03（checkout 时间）。
**真正的判据是编号 + 合入提交**，本轮用 `git log -1 --format=%h%ad -- <file>` 取证：
802 是 10-01 合入、820 是 10-03 合入 ⇒ **两个都是"近两天刚合入却没登记"**。

## 三、后果：一条忘了登记的迁移会被**静默部署**

两条路径都不拦：

1. `verify-migration-checksums.sh` —— 未登记走 `:87-92` 的 WARN 分支，**不 exit 1**；
2. `deploy/sql/verify-migration.sh` —— 部署侧验证只 `test_case "存在 <file>"`（`:60-62` 形态），
   **只查文件存在，不查台账登记**。

⇒ **登记缺失既不阻断部署，也不会有任何门响。**
⇒ 登记的价值在别处：`docs/db-changelog.md` 是**运维判断"线上到底装了哪些迁移"的唯一账本**。
一份账本漏了最近两条，运维在排查"某列为何不对"时会**得出错误的归因**
（这正是 183/184 号「判迁移有没有跑的尺子本身是坏的」那一族的镜像 ——
**这里坏的是"账本漏记"而不是"尺子量错"**）。

⚠️ **诚实边界**：本轮**没有**证据表明 802/820 真的出过问题。
**"登记缺失"的后果是"归因可能出错"，不是"部署会出错"。**
⇒ 故定级 **P3 / 登记缺口**，不是 P1/P2。

## 五、⚠️ 本轮我又一次把判据写松了 —— 而且方向与 221 号那次**相反**

### 现象

第二门（sha 校验）第一版报了 **3 条"缺陷"**，而 221 号独立重算明明是 **161 通过 / 0 不匹配**。

### 根因

我第一版的台账解析正则写成宽松的 `^.*\`(name)\`.*$`，权威规则
（`verify-migration-checksums.sh:53`）却是**整行形态**：

```bash
if [[ "$line" =~ \|\ [0-9]+\ \|\ \`([0-9]+_[a-zA-Z0-9_]+\.sql)\`\ \|\ \`([0-9a-f]{64})\`\ \|\  ]]; then
```

（必须形如 `| <num> | \`name\` | \`<64位sha>\` | <status> |`）

⇒ 我的宽松版多认了两种东西：
1. **没有 sha 列的行** —— `| 736 | \`736_maas_rate_multiplier.sql\` | code-landed（Wave 3 B1，39b8efbe0）|`
   被我当成了"登记了但 sha 是空的" ⇒ 报"sha 不符"；
2. **正文散文里的反引号文件名** —— `623_...` 命中的是一句说明文字而非表格行
   ⇒ 报"台账有、磁盘无"（fatal），而真相是它**被脚本的正则排除在外**。

改用逐字照抄脚本正则后 ⇒ **161 条校验 / 0 不匹配**，与 221 号**独立重算结果完全一致**
⇒ 这是两轮之间的**交叉验证**。

### 这条比结论更值钱

221 号踩的是**判据比规则更紧**（用 `` `([^`]+)` `` 反而比脚本宽，但用"单行"当单位比脚本严）
⇒ 报 8 条，其中 6 条是单位错。
**224 号踩的是判据比规则更松** ⇒ 报 3 条，全部是假缺陷。

⇒ **两个方向都会造假，且都不是"漏报"而是"虚报"。**
**唯一可靠的做法是：逐字照抄权威规则的实现，然后对比自己的判据宽严。**

## 六、⚠️ 负控 NC-D 抓到一处**自指判据**（与 §171 同源）

### 现象

负控做法：从台账**删掉最大那行（819）的登记行**，模拟"忘登记" ⇒ **门保持绿**。

### 根因

第一版窗口锚点取的是 **`maxRegistered`（台账侧）已登记的最大编号**。
删掉台账里的 819 ⇒ 锚点自动下移到 818 ⇒ **819 被移出窗口** ⇒ 缺口从门里消失。

> **删掉台账里的登记行，反而让那个缺口从检查里消失。**

### 修法

**锚点改取磁盘侧最大编号**，台账只作为"被检查的对象"。
⇒ 「磁盘上最新、但台账没登记」必然落在窗口内。
⇒ 复跑 NC-D ⇒ 转红并点名 `819_request_abandoned.sql`。

⚠️ 与 211 号（断言挂在它要守护的包里）、§171（校验函数与被校验函数同源）同族：
**尺子与被测物同源 ⇒ 尺子错时它跟着错、永远不会响。**
⇒ 判别式：**检查范围不能由"被检查对象当前的状态"定义。**

另一条负控 **NC-E**（篡改 819 的登记 sha）⇒ 转红，命中"任一命中即过"的正确口径。

## 九、playbook §176–§178

**§176 「上一轮说它像某个已知红门」不等于「它走的是同一套机制」。**

223 号结清时写了一句：820 未登记「按 221 号坐实的台账口径，新迁移应补登记行」。
它**没核实后果**，而 221 号那次（816/817 被改写）是 `exit 1` 的红门 ⇒ 读起来像是同一回事。

224 号回读脚本发现**方向相反**：
- 221 号那次是「台账**登记了**、但 sha 对不上」⇒ `:121-123` `exit 1`；
- 820 这次是「台账**没登记**」⇒ 走 `:87-92` 的 WARN 分支，`:127` 收尾时**不 exit 1**。

⇒ **同一个脚本、同一个台账、两个方向，一红一不红。**
⇒ 判别式：**问「这套机制对**这个具体输入**怎么处理」，不要问「这套机制上次红过吗」。**
  同一个文件的两个分支可以完全相反。
⇒ 这条与 §152/§153 同源但更进一步：**前轮结论不能替代对当前输入的查证** ——
  引用它的时候要引用"它证明了什么"，不是"所以现在也会怎样"。

**§177 判据比权威规则更松会造假（221 号那次是更严）—— 两个方向都会，且都是虚报。**

两轮内两个方向各踩一次：

| 轮次 | 我的判据 | 权威规则 | 方向 | 后果 |
|---|---|---|---|---|
| 221 号 | 单位＝「单行 sha」 | 单位＝「同一文件的 sha 集合」（`:94-103` 明写 Accept any） | **更严** | 8 条不符里 **6 条是单位错** |
| 224 号 | 正则 `^.*\`(name)\`.*$` | **整行形态** `\| <num> \| \`name\` \| \`<64hex>\` \| <status> \|`（`:53`） | **更松** | 3 条"缺陷"**全部是假的** |

224 号的宽松版多认了两种东西，**两种都不是登记**：
1. **没有 sha 列的行** —— `| 736 | \`name\` | code-landed（…）|` 被当成"登记了但 sha 为空"；
2. **正文散文里的反引号文件名** —— 命中一句说明文字 ⇒ 报"台账有磁盘无"（脚本判 fatal），
   而真相是**它被脚本的正则排除在外**。

⇒ 改用逐字照抄脚本正则后：**161 条校验 / 0 不匹配**，与 221 号独立重算**完全一致**
⇒ 这是两轮之间的**交叉验证**（同一权威规则、两套独立实现、结果相同）。
⇒ **修法只有一条：逐字照抄权威规则的实现，然后显式对比自己的判据宽严。**
  「我以为它认这个形态」与「它认这个形态」之间没有推理空间。

**§178 检查范围不能由「被检查对象当前的状态」定义 —— 否则删掉记录会让缺口消失。**

224 号的近邻窗口门第一版把锚点取成 `maxRegistered`（**台账侧**已登记的最大编号）。
负控 NC-D：从台账**删掉最大那行（819）** 模拟"忘登记"
⇒ 锚点自动下移到 818 ⇒ **819 被移出窗口** ⇒ **门保持绿**。

> **删掉台账里的登记行，反而让那个缺口从检查里消失。**

修法：**锚点取磁盘侧最大编号**，台账只作为被检查的对象。
⇒ 「磁盘上最新、但台账没登记」必然落在窗口内 ⇒ NC-D 复跑转红并点名 819。

**尺子与被测物同源 ⇒ 尺子错时它跟着错、永远不会响。**
⇒ 判别式：**写任何"范围/窗口/抽样"时，问一句「这个范围是怎么算出来的？它会不会因为

  **曾经成立**（< 540 段 100% 未登记），**现在正在失效**（800+ 段只剩 10% 未登记）。
