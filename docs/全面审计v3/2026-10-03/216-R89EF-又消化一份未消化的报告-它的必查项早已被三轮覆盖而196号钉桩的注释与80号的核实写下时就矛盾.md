## 三、🟠 本轮的实际产出：196 号钉桩的注释**与 80 号的核实写下时就矛盾**

`sanitize_info.go`（196 号写）原来这句话：

```go
// Today this costs nothing because MessageRefs has no production consumer
// (registered as 21号 §四 G2, P3). It is a trap for the first consumer that joins the two.
```

⚠️ **「no production consumer」是错的。** 我在当前 HEAD 上重新走了一遍完整链路：

| 环节 | 证据 |
|---|---|
| 生产者 | `smart_sani_guard.go:270` `info.MessageRefs = messageRefs` |
| 消费者 | `request_log_pipeline.go:1498` `buildOutboundProvenance` 读 `SanitizeInfo.MessageRefs` 并出 `sanitize_message_refs` |
| 三处调用 | `handler.go:4017`（chat，带 `AlignmentMap`）、`responses.go:272`、`messages.go:262`（后两者 `alignment=nil`） |
| 落库 | `logCtx.OutboundProvenance` → `request_logs.compression_meta` |
| V2 读回 | `domains/session/v2/cache_v2.go:797`（`AlignmentMap`）/ `:803`（`SanitizeMessageRefs`） |

⇒ **`MessageRefs` 每次请求都被持久化。** 真正缺的是**窄得多**的一件事：
**两侧都落了库，但没有任何东西把两者 JOIN 起来。**

### 为什么这句错话危险（方向是反的）

「no production consumer」会诱导读者得出「provenance 数据**从没落库** ⇒ 这个接缝伤不到任何人」。
真相反过来：**数据就在库里**，因此接缝对**将来任何一个写 join 的人**都是可达的，
而那个 join 会**静默地用错误的行**回答「第 N 条原始消息去了哪里」
（按 196 号 pin 的实测：同一条 m3 在客户端索引是 3、在对齐表索引是 1，**偏移 −2**）。

⚠️ 也就是说：接缝**今天已经可被触达**，只是**还没人去 join**。

### 已改成的措辞（只改注释，零逻辑改动）

改成明确区分「**都落库**」与「**没人 join**」两件事，并把 216 号自己的复核范围、80 号的核实、
以及本轮对 pin 的负控一并写在注释里，避免下一个接手的人重新推一遍。

### §153 **写「现状」类断言之前，先在**同一份审计目录**里搜前一轮是否已核实过同一对象

196 号在 `sanitize_info.go` 写下「MessageRefs has **no production consumer**」，
而 80 号在**两天前**已核实「`buildOutboundProvenance` 每次请求都把它落进 `compression_meta`」。
两份文档**都在 `docs/全面审计v3/`**。

⇒ 它不是「漂移」，是**写下时就已经和一份在盘的结论矛盾** —— 因为写的时候没有回头读。

⇒ **判别方法**：凡是要写「**X 没有 / X 从不 / X 没有被…**」这类**现状/缺失**断言，
  落笔前先在本审计目录里搜**对象名**（不是搜你要下的结论）——
  `grep -rn "<对象名>" docs/全面审计v3/`。**搜到了就必读那一段**，
  否则你只是在重推一遍别人已经推过的事，而**这次恰好推错了方向**。
⇒ 与 §139（grep 不到 ≠ 不存在）、§152（先查是不是已被别人修了）同族：
  前两条管「代码」，这一条管「**我们自己的历史结论**」。

### §154 「**缺失断言**比存在断言更容易错，因为 0 命中时人会直接采信」

「no production consumer」「从不」「没有消费者」都属于**缺失断言**。
本条实测：`grep MessageRefs/SanitizedMessageRef` 的**生产命中确实存在**
（`smart_sani_guard.go:270` → `buildOutboundProvenance` → 三处调用 → 落库 → V2 读回），
只有**注释**说它没有。

⇒ 缺失断言的正确做法与 §151 同源：**不要靠「搜不到」下结论，要靠「找到它去了哪里」**。
  正确问法是「**它写到哪里去了 / 谁读它**」，而不是「有没有人提到它」。
⇒ ⚠️ 缺失断言的错误**方向特别恶劣**：它会让人**低估**风险
  （本例会让人以为「数据没落库、接缝无害」），
  而存在断言错了通常只是**高估**。
⇒ 与 80 号写进 `conventions.md` §10.2 的「假 0 命中」互补：
  §10.2 管「搜错了名字」，这一条管「**搜对了名字、却把 0 命中当成不存在**」。
