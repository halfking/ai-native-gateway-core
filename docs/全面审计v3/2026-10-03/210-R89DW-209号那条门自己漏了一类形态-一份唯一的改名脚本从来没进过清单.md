## 二、🔴 F1：**209 号那条门漏了「带表别名的 UPDATE」，整份脚本从清单里消失**

209 号 `destructiveRes` 的第 4 条是：

```go
`(?i)\bUPDATE\s+[a-z_][a-z0-9_.]*\s+SET\b`   // 要求表名与 SET **紧邻**
```

而 PostgreSQL 允许表别名。实测四种形态：

| 语句 | 旧判据 |
|---|---|
| `UPDATE work_type_model_route w SET …` | **false** |
| `UPDATE model_aliases ma SET …` | **false** |
| `UPDATE models_canonical mc SET …` | **false** |
| `UPDATE model_aliases SET …` | true |

⇒ **后果不是「少报一条」，而是整份脚本从清单里消失。** `2026-09-21-unmapped-cn-rename.sql` 是 `sql/fixes/` 下**唯一一个真的会自己去改 `models_canonical` / `model_aliases` 的脚本**，而它的两处写操作**都带别名**（`:92` `UPDATE model_aliases ma SET …`、`:116` `UPDATE models_canonical mc SET …`）⇒ 判据数出 **0** 处破坏性动作 ⇒ 脚本**根本没进清单**，而清单**仍然非空**、**下限仍然通过**、门**全绿**，并且自报「8/8 可中止」。

**这正是 playbook §122/§126 说的那个形态，只是这次发生在我自己写的门上**：下限被满足了，而**下限度量的那个集合本身是残缺的**。

### 两条修法

1. **判据容忍可选别名**（含 `ONLY` / `AS`）：
   `\bUPDATE\s+(?:only\s+)?[a-z_][a-z0-9_.]*(?:\s+(?:as\s+)?[a-z_][a-z0-9_]*)?\s+SET\b`
2. **覆盖下限改钉在「宽集合」上**（`reAnyDML`：只看动词，不看语法结构，对别名/格式串/`EXECUTE` 包装统统不敏感）。

第 2 条才是重点：**只要下限还钉在过滤后的集合上，任何一处判据漏掉都会表现为「清单少了一项」而不是「下限失败」**。宽集合与过滤后集合**不再可能是同一件事**，那条断言才真的在约束覆盖面。

### 顺带扩宽：`ALTER TABLE` 与非并发 `CREATE INDEX` 原本也全部漏掉

旧式 `ALTER\s+TABLE\b[^;]*\bDROP\b` 要求同句内再出现 `DROP`，于是 **`ADD CONSTRAINT` 与 `ATTACH PARTITION` 一个都不匹配**。而这两类恰恰是生产上**最需要「能不能中止」**的那类：`ALTER TABLE` 取 **ACCESS EXCLUSIVE**，`ATTACH PARTITION` 还会逐分区扫全表。实测被漏的两个脚本就是 `fix-request-logs-hot-unique-constraint.sql` 与 `fix-request-logs-bodies-reattach-partitions.sql`。

### 修完之后：宽集合 11 / 分类后 11，两者终于相等

```
覆盖面自报：宽集合(含任意 DML)=11，经破坏性分类=11（下限只保证抽取器活着，**不**代表一族逐个审过）
```

**下限不是随手写的整数，是逐文件量出来的**：18 个脚本里宽集合命中 11 个，7 个未命中的**全部是只读的** —— 5 个 `db-audit-252-*`/`db-audit-collect` 采集脚本，加 2 个 DML **全被注释**的模板脚本。取紧下限 11 的意义是**任一脚本掉出去都会红**（10 < 11）。

> 顺带一个意外收获：那个「宽集合只看动词、不看语法」的判据，**独立印证了子代理的结论** —— `fix-glm52-alias-drift.sql` 与 `fix-discovery-junk-canonical-rows.sql` 的 DML 确实**一行都不会执行**（全部在注释里）。两个方法、两个上下文，互相印证。

### 新增 7 条分类器负控（两个方向并列）

① **必须认出来**：带别名 UPDATE / 带 schema 限定 + 别名 / `ADD CONSTRAINT` / `ATTACH PARTITION` / 非并发建索引。
② **必须不认**：**被注释掉的 DML**、纯 SELECT 采集脚本。

②方向不是凑数：若把注释也算进去，宽集合的 11 就是**被注释喂出来的数字**，覆盖下限会变成一个虚高值 —— 那正是「注释不是契约」的变体。

## 三、🔴 F2：`fix-request-logs-hot-unique-constraint.sql` 的判据**查错了系统目录**

原实现：

```sql
IF NOT EXISTS (SELECT 1 FROM pg_constraint
               WHERE conrelid='request_logs_hot'::regclass AND contype='u') THEN
  ALTER TABLE request_logs_hot ADD CONSTRAINT … UNIQUE (request_id, ts);
```

**三处失效**：

1. **判据只认「约束」，不认「索引」。** `CREATE UNIQUE INDEX` 产生的是 `pg_index.indisunique`，**不进 `pg_constraint`**。而 `migrations/startup/341_hot_table_independence.sql:48-49` 正是用 `CREATE UNIQUE INDEX IF NOT EXISTS idx_request_logs_hot_request_id_ts_unique ON request_logs_hot (request_id, ts)` 建的 ⇒ 一个**已经存在**的唯一索引，对这段判据**完全不可见** ⇒ 脚本会再加一个**同列的重复唯一索引**（PG 允许），在热表上白白多一份索引体积与写放大。
   ⇒ **`ON CONFLICT` 认的是唯一索引**，唯一约束只是「索引 + `pg_constraint` 里一行」的复合体 ⇒ **查索引是两者交集的上位判据**。

2. **判据问的是「有没有任意唯一约束」，不是「有没有这一组列上的」。** 任何别的唯一约束（例如只在 `request_id` 上的 —— `01-schema.sql` 里 `request_logs_hot` **恰好就有** `idx_request_logs_hot_request_id`）都会让判据为真 ⇒ 脚本报 `Unique constraint already exists` 而**什么都不做**，而 `ON CONFLICT (request_id, ts)` 依然无法工作。**恒真的谓词不是门，是装饰。**

3. **「验证」段无法失败。** 原验证只是 `count(*)` 任意唯一约束再 `RAISE NOTICE`：既不看列、也不看是否 `indisvalid`、更不会在不符时中止。而文件**没有** `\set ON_ERROR_STOP` ⇒ 即便 `RAISE EXCEPTION`，psql 默认也只打印错误后继续。

### 改法

新增 `pg_temp.r89_has_unique_on(table, cols)` 探针，四个条件缺一不可：`indisunique` / `indisvalid`（INVALID 索引 planner 不可用，例如 `CONCURRENTLY` 中途被打断留下的）/ `indpred IS NULL`（**部分**唯一索引带谓词，不能作为 `ON CONFLICT` 的推断依据）/ 列清单**恰好**等于 `(request_id, ts)`。判定与验证**共用同一个探针函数**，验证失败即 `RAISE EXCEPTION` 回滚。补 `\set ON_ERROR_STOP on`。

### 附带坐实的一条漂移（不下结论，只登记）

`01-schema.sql`（本仓权威基线，也是 reconcile 工具的对账对象）里 `request_logs_hot` **没有任何唯一索引**，只有非唯一的 `idx_request_logs_hot_request_id`；而 `migrations/startup/341` 声明了 `idx_request_logs_hot_request_id_ts_unique`。**对照**同族的 `request_logs` 父表，它的 `idx_request_logs_request_id_ts_unique` 在 `01-schema.sql` 里**是存在的**。

⇒ 即「热表的唯一索引没落进基线、父表的落了」。**本轮无 PG，不判定是 341 没跑还是基线过期**，只登记：这与 205 号那条「`sql/objects/` 漂移无人核对」是同一片盲区。
⚠️ 另：`ON CONFLICT (request_id, ts)` 在全仓 Go 代码里**没有对 `request_logs_hot` 的使用**（grep 零命中）⇒ 所以这条目前**不构成运行期故障**，是「脚本与基线对不上」的记录，不是 P1。

## 四、🔴 F3：`2026-09-21-unmapped-cn-rename.sql` —— 头部的「保持向后兼容」与代码**正好相反**

这是 `sql/fixes/` 下**唯一一个真的会自己改库**的脚本（另两个的 DML 全被注释）。头部 `:6` 写：

> `加老 -cn 名为 deprecated alias, surface='cn', **保持向后兼容**`

而别名解析的**全部**读点都硬过滤 `status='active'`：

- `resolve/resolve.go:384`、`resolve/resolve.go:425`
- `admin/model_normalize.go`、`admin/logs.go` 同款过滤

脚本写的正是 `status='deprecated'` ⇒ **老 `-cn` 名在改名后不再解析**，与「保持向后兼容」**正好相反**。

**更严重的是**：§4 的验证段 `:159` **断言 `deprecated_aliases = 19`** —— 它把这个反效果**当成成功来校验**。脚本的验证在**保护**它想避免的那个结果。

### 另两处注释与代码不符（同一文件）

- 头部原写「per-row 嵌套子事务 + COMMIT 后 SELECT 断言 …**本脚本按此模式写**」，实际是**两段彼此独立的平铺事务**（`:91-113` 别名弃用、`:115-121` 改名）。⇒ 若第二段因 `models_canonical.canonical_name` 唯一键冲突失败（守卫 `:70` **只查 `status='active'`** 的 winner，而该列有 UNIQUE），**第一段已经提交** ⇒ 留下「名字没改、别名已废」的**半应用态**。
- §0 备份的「否则插差量」是**死代码**：`:32` 的 `WHERE NOT EXISTS (SELECT 1 FROM public.bak_…)` 没有相关子句，仅当备份表为空为真 ⇒ 重跑只插 0 行，**既无差量也无回滚材料**。

### 改法与「不擅自决定」的边界

1. 补 `\set ON_ERROR_STOP on`（本文件原先是 `sql/fixes/` 里**唯一没有**它的自动改库脚本）。
   ⚠️ 缺它的后果**不是**「报错后继续改」——事务内失败会中止事务、`COMMIT` 变 `ROLLBACK`。真实后果是这三条：① §0.2 的 preflight `RAISE EXCEPTION 'rename aborted: …'` 位于**任何事务之外**，psql 打印错误后**继续执行** ⇒ **它宣称的中止根本没有发生**；② 脚本整体**以 0 退出** ⇒ 自动化看不出失败；③ §4 的 post-commit 门禁同样不会让 psql 非零退出。
2. 新增**可解析性门禁**，判据与生产读点**同源**（照抄 `status='active'` 这个口径，而不是新造一个），且**放在第二段事务内、`COMMIT` 之前** —— 放在 COMMIT 之后就只是事后报表，**报表不是门**。
3. ⚠️ **本轮不擅自把别名改成 `status='active'`。** 「老名是否应当继续可解析」是**产品裁决**：继续可解析 ⇒ 改 status；不可解析 ⇒ 头部那句「保持向后兼容」应删掉并写明这是**破坏性变更**。脚本只保证这个事实在**跑的时候就炸出来**。
4. ⚠️ 门禁**管不到**的部分已写进文件：两段事务彼此独立 ⇒ 最坏仍是半应用态。**根治要合并两段事务，本轮只登记不重构。**

## 十、playbook 新增

### §128 **覆盖下限必须钉在「宽集合」上，不能钉在「过滤后的集合」上**

210 号撞上的最贵一条，是我自己上一轮写的门：`destructiveRes` 漏了
`UPDATE <表> <别名> SET` ⇒ 一整份脚本从清单消失 ⇒ **清单仍非空、下限仍通过、门仍全绿**。

⇒ **判别方法**：问一句「**如果判据漏了一类，测试会红吗？**」——若下限量的是
**判据自己的输出**，答案是**不会红**。只有当下限量的是一个**判据之外**的量
（例如「文件里出现过任意 DML 动词」，只看不解析）时，漏才会变成红。
⇒ ⇒ **宽集合与过滤后集合必须不是同一件事**，否则那条断言是**自证的**。
⇒ **下限取紧**（按逐文件实测值，不要随手写整数）：宽集合 11 ⇒ 掉一个就红。

### §129 判据问「有没有**任意一个**」还是「有没有**那一个**」——恒真的谓词不是门，是装饰

`IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE … AND contype='u')` 在这张表
**已经有别的唯一约束**时为真 ⇒ 脚本什么都不做而报「已存在」。
与 §120 的恒真谓词同族，但更隐蔽：**它不恒真，它只是被错误的对象满足**。

⇒ **判别方法**：凡是「不存在就建」式的守卫，把 `NOT EXISTS (… 任意 …)`
  改成 `NOT EXISTS (… **且列/键完全等于我要的那一个** …)`。
⇒ **更隐蔽的一层**：`pg_constraint`（约束）与 `pg_index`（索引）是**两个目录**，
  而 `ON CONFLICT` 认的是**唯一索引**。只查约束 ⇒ 一个已经存在的唯一索引**完全不可见**
  ⇒ 会再加一个同列的重复索引。⇒ **判据要查两者交集的上位对象。**
⇒ `ON CONFLICT` 的推断还要求索引 `indisvalid` 且**无谓词**（部分唯一索引不算）。

### §130 「验证」段如果**无法失败**，它证明不了任何事

原脚本的验证是 `count(*) … ; RAISE NOTICE '%'`：既不看列、也不看有效性、
也不会在不符时中止。⇒ 它**永远绿**，而它紧跟在一条会改表的语句后面，
读起来却像一道门。

⇒ **判别方法**：把验证段的**每一个失败分支**列出来；列不出来 ⇒ 它不是验证，是打印。
⇒ **门禁要落在与判定同一个函数/同一套条件上**（本轮改成判定与验证共用 `r89_has_unique_on`），
  并让失败**中止**（`RAISE EXCEPTION` + 显式事务 + `ON_ERROR_STOP`）。
⇒ ⚠️ **门禁要放在它能真正中止的位置**：放在 `COMMIT` 之后就只是**事后报表**。
  **报表不是门。**

### §131 注释里的**否定式断言**（「保持向后兼容」「本脚本按此模式写」）要用**机制**核对

210 号在同一文件里撞到三处：① 写 `status='deprecated'` 却宣称「保持向后兼容」，
而全部解析点过滤 `status='active'`；② 宣称「per-row 嵌套子事务」而实际是两段平铺事务；
③ 宣称「否则插差量」而那个 `NOT EXISTS` 没有相关子句。

⇒ 前两类的共同形态：**注释描述的是一个更温和的意图，而代码做的是更严格的事**。
⇒ **判别方法**：凡是注释里出现「兼容」「保持」「幂等」「安全」「本脚本按此模式写」
  这类**评价性**词，直接去代码里找**读端的那一行**（`resolve/resolve.go:384` 那种）
  核对两边是否一致。评价性词**不能**由代码自动推出，必须人核。
⇒ **验证段可能反过来「保护」那个反效果**（本轮 §4 的 `deprecated_aliases = 19`
  就是把「老名不可解析」当成功校验）⇒ 看到「期望 N」的断言，先问 **N 本身对不对**。

### §132 子代理输出是**证据**，不是结论

本轮子代理报「psql 遇 `RAISE EXCEPTION` 仍继续改名」。**我实测否掉了这一条**：
事务内失败会中止事务、`COMMIT` 变 `ROLLBACK`，所以改名**不会**跑下去。
真实后果是另外三条（preflight 在**任何事务之外** ⇒ 它宣称的中止没发生；
整体**以 0 退出**；post-commit 门禁同样不改变退出码）。

⇒ 结论越像「机制怎么运作」，越要自己实测一遍 —— 那是**最容易被顺接受收**的一类主张。
⇒ 反过来，**两个独立方法互相印证**时才加分：本轮「两个脚本的 DML 全被注释」
  同时被「子代理逐行读」与「宽集合 DML 判据」确认。

### §133 手跑脚本的**「保持兼容」是一个产品裁决，不是一个技术细节**

F3 的正确改法看起来只是「把 `deprecated` 改成 `active`」，但那会改变**解析结果**：
老名会重新指向改名后的 canonical。于是「老名该不该继续可用」变成产品问题。

⇒ 本轮的做法：**判据照抄读点的口径 + 放在事务内让它炸出来 + 把裁决登记**，
  **不擅自改语义**。⇒ 审计里遇到「修法会改变对外行为」时，
  默认动作是**让问题在执行时可见**，而不是**替产品做决定**。

### 附录 · 212 号更正：F2 那一节漏掉了一个事实（**结论方向不变，但依据被削弱**）

212 号复核 `request_logs_hot` 唯一性时发现，`01-schema.sql` 里还有一条我在 210 号**没有查**的记录：

```
01-schema.sql:21827  ADD CONSTRAINT request_logs_hot_pkey PRIMARY KEY (request_id);
01-schema.sql:21907  ADD CONSTRAINT request_wal_hot_pkey  PRIMARY KEY (request_id);
```

⇒ **两张 hot 表本来就有主键**，建在 `request_id` **单列**上。

**这不推翻 210 号 F2 的结论，但修正它的依据**：

- 210 号写的是「`01-schema.sql` 里 `request_logs_hot` **没有任何唯一索引**」。严格说这句话**不准确** ——
  它**有**一个唯一的对象（主键），只是**不是索引、也不是这两列**。
- 210 号的核心结论仍然成立：`ON CONFLICT (request_id, ts)` 要求**恰好**建在
  `(request_id, ts)` 上的唯一索引/约束；只有 `(request_id)` 的主键**不满足**该推断。
  ⇒ 210 号把判据改成查 `pg_index` 并要求**列清单恰好相等**，方向是对的；
  用 `pg_index` 也确实比用 `pg_constraint` 更对（唯一约束底层同样是索引）。
- 但 210 号那句「对照：父表 `request_logs` 的有，热表的没有」把差异归到了
  「热表丢了唯一索引」上，**漏了热表有一个更严格的 `(request_id)` 主键**。
  ⇒ 这条差异的真正含义是**两张表的唯一性口径本来就不同**
  （`request_logs` 允许同一 `request_id` 多行；`request_logs_hot` 不允许），
  而不是简单的「有没有」。

⇒ **教训**：「在某处 grep 不到 X」⇒「不存在 X」是最容易犯的错之一。
我搜的是 `UNIQUE` / `UNIQUE INDEX` / `idx_*_request_id_ts_unique` 这几个**词形**，
而主键的 `PRIMARY KEY (request_id)` **一个词都不沾** ⇒ 词形层面的搜索对
**另一种表达同一约束的对象**完全失明。
⇒ 这与 205 号「引错权威来源」、210 号 F1「正则漏了表别名」是同一族：
**判据只认自己会写的那个词形**。
⇒ 补做的检查：把该表 `pg_constraint` 里**所有** `contype IN ('p','u')` 的约束连同
**实际列清单**打出来（212 号已把这个检查写进
`sql/fixes/fix-request-wal-hot-primary-key.sql`，现在它**只报告、不创建**）。

⚠️ 由此还带出一条 212 号新发现：同目录的 `fix-request-wal-hot-primary-key.sql`
按**约束名**检查 ⇒ 在任何与基线一致的库里都会**命中并直接跳过** ⇒ **整份脚本是 no-op**，
而它的头部宣称修的是「所有请求日志写入失败」。见 212 号文档。
