## 二、于是改立一个轻量门面：`internal/ingressguard`

**它刻意不导入 `domains/streaming`**，只做**静态文本判据**：

1. 读 `cmd/gateway/main.go`，解析出全部 `/v1` 数据面路由 + 每条路由绑定的 handler 表达式；
2. 读各 handler 源文件，数**锚点**出现次数：
   - `.CheckBudget(`（累计配额闸，超了 402）
   - `checkGatewayRateLimit(`（RPM 限流）
3. 断言「登记表的声明」与「代码实际」一致。

实测 **0.371~0.614s**，可安全进 CI。

### 2.1 这是「契约钉桩」型门，不是「检测活缺陷」型门

它断言的是**现状（含缺口）**。缺口如实登记，所以**现在就是绿的**；谁改了行为却不更新登记表，门会转红，强制同步。否则下一个接手的人会把「已登记的缺口」当成「已覆盖」—— 与 216 号对 provenance 接缝的处理同型（playbook §153/§154 那条「**缺失断言比存在断言更容易错**」）。

**登记表每条必须填的东西**（少填即红）：

- `Plane`：`inference`（调上游、消耗额度 ⇒ 必须对两道闸表态）/ `control`（不调上游 ⇒ 只登记不要求闸）
- `HandlerVars`：这条路由在 main.go 上到底交给了谁
- `File`：锚点在哪个文件里核对
- `Budget` / `RateLimit`：`own`（该文件恰好 1 次锚点）/ `delegated`（恰好 0 次 + 必须写委派给谁）/ `none`（恰好 0 次 + **必须写为什么可接受**）
- 判据取**恰好 N 次**而不是「存在/不存在」—— 任何一侧的真实变更都会看见，而不是恒亮（§151）。

## 三、本轮的三次自我推翻（都是**我自己的新门**，不是历史代码）

### 3.1 第一次：门在**自己建起来的当天**就漏了一条真路由

第一版解析器只认 `mux.Handle(`：

```go
if !strings.HasPrefix(rest, `"`) { continue }   // 只认 mux.Handle(
```

而 `main.go` 上的注册有**两种**形式。第一版门跑绿、报「24 个路径全部已登记」，**看起来是完备的**。

把「已登记」当成「已覆盖」是 §154 写过的失效；而**根因是 210 号写过的另一条**：

> **下限必须钉在宽集合上。** 若下限量的是**判据自己的输出**，漏了一类永远不会红。

本轮把同一个错误**又犯了一次**，只是换了场景：

- 当时的宽集合 = 「我的解析器认识的注册形式」= **窄集合**
- ⇒ 门把 `mux.HandleFunc(` 注册的 **`/v1/handoffs/confirm`（`main.go:6366`，`chatHandler.HandleHandoffConfirmation`）**整条漏掉
- 而下限 24 条照样满足、登记表照样齐全、门照样**全绿**

**改法（第二版）**：宽集合改成「`main.go` 里每一个以 `/v1` 开头的**引号字面量**」（本轮实测 **31 处出现 / 26 个唯一字面量**），并要求每一个都必须被归类成三者之一：

1. **路由注册行**（含 `Handle(` 与 `HandleFunc(` 两种形式，且不限定 receiver 名）
2. **日志串**（`slog.*` 调用内，含**跨行**调用）
3. **客户端基址拼接**（`GatewayBase() + "/v1"`）

出现**第四类 ⇒ 直接转红**，而不是被过滤掉。这样「解析器不认识某种注册写法」就从**静默漏掉**变成**硬红**。

**刻意不写例外清单** —— 清单会变成「以后懒得看了」的表。改成「必须能被归类成这三类之一」，将来出现第四种形态会自己响。

### 3.2 第二次：新门的**下限我第一版取错了单位**

第二版门第一次跑是**红的**，报「只解析出 21 条路由，低于下限 25」。

**下限 25 是我手工数「注册行」的数（25 行），而门数的是「唯一路由」**（21 条；多出的 4 行是 `main.go:6419-6425` 的 v2 二次注册）。

⇒ 记一条纪律：**下限取值前先说清「量的是什么单位」**。门自己当天就红这件事其实是好事 —— 它证明了这条下限确实有鉴别力；但**正确的下限必须按逐文件实测取紧**：本轮定为 **21**（掉一条唯一路由就红；新增一条则由「未登记」分支接手）。

### 3.3 第三次：判据取「恰好 1 次」**仍然不够** —— 它没管「在哪个文件里数的」

第二版门绿了之后，我按 §151 自查「**它会不会把缺陷判成通过**」，构造负控 NC3：

> 把 `/v1/embeddings` 的 `File` 从 `embeddings.go` 改成 `handler.go`。

先量前提（证明这不是空想）：

```
handler.go .CheckBudget(          = 1
handler.go checkGatewayRateLimit( = 1
```

**两个锚点在 `handler.go` 里也恰好各 1 次** ⇒ 负控**实测结果：`TestIngressSurfaceGateDeclarationsMatchCode` 全绿**（`ok … 0.521s`）。

根因：「`File` 指向哪个文件」完全靠人写，而**锚点计数对「另一个也合规的文件」一样成立** ⇒ **登记表与真实接线之间没有交叉验证**。

**改法（第三版）**，两条互补的加固：

1. **路由 → handler 变量核对**：每条路由在 main.go 的注册行里必须出现该条目声明的 `HandlerVars` 之一；且**每个声明的变量至少被一条路由用上**（防「死变量」把断言架空）。
2. **一个源文件只登记一次**：把 `embeddings` 的 `File` 改成 `handler.go` 现在会红 ——「两条声明会互相掩盖，且把 File 指向另一个也合规的文件就能骗过锚点计数」。

复测同一负控：红，且**红的正是新加的那条**（`TestIngressSurfaceGateDeclarationsMatchCode` 依旧绿 ⇒ 两条断言职责分离、各管一段，这是想要的结果）。

**残余盲区（如实登记）**：`File` → handler 变量**变量 → 源文件** 这一跳仍是人工的。机械闭合需要解析构造函数与包路径，本轮判断**不相称**（脆弱、收益低）⇒ 明确记为已知边界，不假装已闭合。

## 五、接线：登记到 `GUARD_PACKAGES`（211 号那条教训的直接应用）

- `Makefile:73` 补登记 `./internal/ingressguard`，并在注释里写明**为什么不是**登记 `domains/streaming`（预算 106.471s vs 120s）。
- ⚠️ **这一条是必须登记、不是可选登记**：`scripts/checks/guards-sync.sh` 是按磁盘上 `find internal -maxdepth 1 -type d -name '*guard'` **发现式**枚举的，CI 的 `.github/workflows/audit-guards-ci.yml:87` 会跑它 ⇒ **漏登记直接让 CI 转红**。
- `internal/sqlguard/guard_wiring_test.go` 的 `mustHave` 补 `./internal/ingressguard` —— 211 号的结论：**登记断言必须放在一个已经在登记表里的包**，因为「自证的断言在关键处等于没有断言」。

**预算实测**（与 `make guards` 同参数 `-count=1 -timeout=120s`）：

```
rowsguard 13.735s   errdiscard 14.996s   dbrows 0.992s   jsoncol 0.770s
paramguard 1.074s   sqlguard 8.083s      sqlreadguard 5.274s
metricguard 13.297s partguard 20.380s    routeguard 1.163s
ingressguard 0.614s ← 本轮新增
sql/schema 33.929s
全 12 包墙钟 36.2s
```

`-timeout` 是**每个测试二进制各自计时**，最慢的 `sql/schema` 33.9s 远低于 120s；新包 0.614s 可忽略。

⚠️ **同一套守卫在提交前又跑了一遍，耗时普遍慢了 1.5~1.7 倍**（`sql/schema` 33.929s → **49.288s**、`partguard` 20.380s → **34.768s**、`sqlguard` 8.083s → **13.762s**），**仍然全绿**（墙钟 36.2s → 52s）。

这不是缺陷，是**本轮结论的加强证据**：守卫包本身的耗时在同机、相隔十几分钟内就能波动 1.5~1.7 倍 ⇒ `domains/streaming` 那 **8.2~13.5 秒**的余量，在同等的日常波动下**必然会被吃掉**（`sql/schema` 单是这一项的波动幅度就有 15.4 秒 > 全部余量）。
⇒ **登记前先量预算**这条纪律的适用范围因此比 217 号原以为的更宽：不只是「慢机器」，**日常负载波动**就够了。

## 八、playbook §157–§160

**§157 登记前先量预算 ——「登记」不是既定目标，而是要过预算的动作。**
217 号的顺位是「先纳入 `GUARD_PACKAGES` 再量」；本轮先量得到 **106.471s 与 107.204s**（两次）vs 120s ⇒ 顺位被推翻。**把中间步骤当目标，会把一个跑不进门 CI 的包登记进去。** 配套动作：**用轻量门面替代整体登记**（0.5s 的静态门面 vs 110s 的真包）。

**§158 下限必须钉在宽集合上；「我的解析器认识的东西」永远不是宽集合。**
210 号已写过这一条，本轮在**新场景**又犯了一次：第一版解析器只认 `mux.Handle(`，于是 `mux.HandleFunc(` 注册的真路由整条漏掉，而**下限照样满足、门照样全绿**。
⇒ 判据取「某个对象的**全部实例**」而不是「我抽取出来的那些实例」；**无法归类的实例必须转红，不能被过滤掉**。
⇒ 配套：**下限取值前先说清单位**（本轮把「注册行数 25」当成「唯一路由数」写进下限，门自己当天就红）。

**§159 取「恰好 N 次」还不够 —— 还要问「这个 N 是在哪个对象里数的」。**
NC3 实测：把登记表里的 `File` 指向**另一个也恰好有 1 次锚点的文件**，门全绿。⇒ 「恰好 N 次」只保证**计数**一致，不保证**计数对象**是声明的那个。
⇒ 补法两条：**路由 → handler 变量**交叉核对 + **一个源文件只登记一次**。推广：任何「A 的属性在 B 里核对」的门，都要单独回答「**A 与 B 之间的映射本身，谁核过？**」。

**§160 判据里的「行」是物理行还是解析单元。**
跨行 `slog.Info(...)` 把字面量甩到**续行**上（`main.go:6512`）；而括号深度法会因 `[]string{...}` 用**花括号**而提前闭合。⇒ 凡是需要跨行上下文的判据（多行调用、复合字面量、字符串拼接），**必须按解析单元算，不能按 `\n` 切**。本轮这道门在写完当天就撞上了它，代价是两轮红。
