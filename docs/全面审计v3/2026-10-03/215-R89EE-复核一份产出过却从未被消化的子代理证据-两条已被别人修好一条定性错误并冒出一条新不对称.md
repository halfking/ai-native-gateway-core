## 四、🔴 F4 被证伪：Gemini 原生入站**不是**零脱敏

报告称：`input_protocols.go:48-101` 的 `switch path` 只有
`/v1/messages`、`/v1/responses`、`/v1/completions` 三个 case，

**它的每一条事实都属实，定级却是错的。** 完整链条（我逐环验证）：

| 环 | 证据 | 内容 |
|---|---|---|
| ① | `handler_gemini.go:330` | `irReq, err := ir.ParseGemini(bodyBytes)` —— Gemini body → **IR** |
| ② | `handler_gemini.go:351-352` | `irReq.SourceProtocol = …`；`openaiBody, err := ir.SerializeOpenAI(irReq)` —— IR → **OpenAI body** |
| ③ | `handler_gemini.go:369` | `synthReq := newGeminiSyntheticRequest(r, openaiBody)` |
| ④ | **`handler_gemini.go:239`** | `httptest.NewRequest(http.MethodPost, **`"/v1/chat/completions"`**, …)` ← **决定性** |
| ⑤ | `handler_gemini.go:378 / 388` | `h.chatHandler.ServeHTTP(streamWriter/rec, synthReq)` —— 交给 ChatHandler |

## 五、🟠 N1（本轮真正的产出）：洗/还原两侧对**媒体对象的粒度**不对称 —— 报告里没有这一条

复核 F3 时顺手比对了两个递归函数，发现它们**不是对称的**：

| 侧 | 位置 | 对媒体对象的处理 |
|---|---|---|
| **洗** | `input_tools.go:186-210` `sanitizeToolValueWithLabel` 的 `case '{':` | **递归每一个键，不识别媒体对象** |
| **还原** | `native_restore.go:379-382` `restoreNativeNestedValue` 的 `case map[string]any:` | 开头即 `if nativeMediaObject(current) { return current, false, nil }` —— **整个对象跳过** |

而 `nativeMediaObject`（`native_restore.go:416-420`）**全仓只被定义并使用那一次**，
洗侧**没有任何对应分支**。媒体判定是按 `type ∈ {image, image_url, input_image,
output_image, audio, input_audio, output_audio, video, file, input_file, document}`。

### 实测（`security/sanitize/media_arg_symmetry_test.go`，离线，无 Redis）

构造 tool arguments：
`{"content":[{"type":"image_url","image_url":{"url":"data:image/png;base64,iVBORw0KGgo=","alt":"我的手机号 13800138000"}}]}`

```
洗侧:   changed=true  mapping=map[{SENSITIVE:phone:1}:13800138000]
        alt → "我的手机号 {SENSITIVE:phone:1}"
还原侧: changed=false restored=…alt":"我的手机号 {SENSITIVE:phone:1}"   ← 占位符原样残留
```

⇒ **坐实**：洗侧把媒体对象**元数据字段**（`alt`）里的手机号换成了占位符，
还原侧因整对象跳过**没有还原** ⇒ 占位符外泄。

### 危害形态要说准：这是「占位符外泄」，**不是**敏感信息泄漏

方向与 F3 **完全相反**：
- F3：洗侧少洗 ⇒ 敏感值**原样出境**；
- N1：洗侧多洗、还原侧少还原 ⇒ 占位符**残留**。

⇒ 不构成安全泄露（反而是掩盖了敏感值），但**违反 objective 的「不影响客户端观感」**
——客户端会在图片说明里看到 `{SENSITIVE:phone:1}` 这种残缺值。

### 一条重要的限定（不要把它读成「媒体现在整体会被脱敏」）

主链路上媒体**本来就整体不进文本脱敏**，且**已有测试钉住**：
`input_protocols_test.go:177-182` 断言 `data:image/png;base64,13800138000` 与
`{"data":"13800138000"}` **原样透传**（RawMessage 通道，见 `input_protocols.go:29-30` 注释）。
⇒ 所以 N1 **不是**「媒体脱敏失控」，而是「**tool arguments 的递归这条腿不遵守同一个约定**」。
⚠️ 把这两件事混为一谈，会得出「媒体在泄漏」的错误结论。

### 为什么本轮不修

1. `nativeMediaObject` 整对象跳过是**既有设计**，代码里**没有注释**说明当初为何这样
   （是为了性能、不动 base64、还是别的）⇒ 改它之前得先回答那个未知。
2. 细化它（只跳过 `url`/`data`/`b64_json` 等**载荷键**、让 `alt`/`detail` 照常递归）
   需要一份「各供应商媒体对象形状」的清单 —— 那是**外部证据**，本机取不到。
3. 危害不是安全泄露；触发还需客户端回传**带元数据字段**的媒体对象。
⇒ **顺位第 1 条**，给出三个修法选项供下轮裁决：
  ① 洗侧也跳过媒体对象（**会让 `alt` 里的手机号原样出境** ⇒ 把 N1 换成 F3，更糟）；
  ② 还原侧只跳过**载荷键**、元数据字段照常递归（**当前倾向，但依赖载荷键清单**）；
  ③ 洗侧对媒体对象**只洗元数据、跳过载荷**（与 ② 镜像，需确认另一侧是否也要改）。

## 六、⚠️ 我自己写错又自己抓到：**判据方向写反，把缺陷判成了通过**

本轮第一次写那个对称性判据时，我写的是：

```go
if changed && !strings.Contains(restoredText, "{SENSITIVE:") {   // ← 反了
    t.Fatalf("两侧不对称：…")
}
```

意思是「还原后**不含**占位符 ⇒ 失败」。而缺陷的真实现象恰恰是
「洗侧产生了占位符、还原后**仍含**占位符」⇒ 条件恒为 false ⇒
**判据永远通过**，测试全绿而缺陷就在那儿。

⇒ 改回正确方向（`changed && strings.Contains(...)`）后**立刻转红**，
且红的原因正是「占位符未被还原」⇒ 修正后的判据**有鉴别力**。

⚠️ 这是本仓库记录的「恒真判据」失效形态的**又一次现身**，而它在我写下相关 playbook
条款**之后**才发生。教训见 §八 的 §151。

⚠️ 同类的一次：写完文档后我想核实「这 5 份脚本都带 `default_transaction_read_only=on`」
并**写进了文档正文**，是逐文件 `Select-String` 把它推翻的（实际只有 3 份有）。
**靠重读自己刚写的文字抓不到，必须换成数机制。**

## 八、playbook 新增

### §150 **顺着数据流走到底，而不是在第一个「对不上」的地方就下结论**

F4 的每一条事实都真实（`default` 分支只找 `messages`、Gemini body 没有 `messages`），
结论「整包零脱敏」却完全错误 —— 因为报告在 `sanitizeEnvelope` 发现不匹配就停了，
**没问「调用它的那个请求，body 到底是什么形态」**。往下再走三环
（`ParseGemini` → `SerializeOpenAI` → 合成请求 path = `/v1/chat/completions`）
就看到脱敏正常生效。

⇒ **判别方法**：得出「某段代码没处理 X」之前，先问一句
  **「到达这段代码的输入，长什么样？」** —— 同一段代码对不同上游可能是不同的东西。
⇒ 与 §139（grep 不到 ≠ 不存在）同族：那一条说**搜不到**推不出**不存在**；
  这一条说**没匹配上**推不出**没被处理** —— 中间隔着「输入被谁转换过」。
⇒ **高危方向**：这类错误的处置会**修一个没坏的路径**，把重复脱敏、双份占位符
  引进一条本来正确的链路 ⇒ **一道会误导正确代码的结论，比没有结论更坏**。

### §151 **写完判据先问：「它会不会把缺陷判成通过？」** —— 恒真判据的第 N 次现身

本轮第一次写对称性判据，把「还原后**仍含**占位符」写成了
「还原后**不含**占位符才失败」⇒ **条件恒假 ⇒ 永远绿 ⇒ 缺陷就在那儿而门是绿的**。

⇒ **自查动作**：把判据的条件**反过来念一遍**（念成「它会不会在该红的时候红」），
比直接跑测试更早发现问题 —— 跑测试只能告诉你「绿了」，而绿**本来就可能是恒真**。
⇒ 这与 §128（负控红得太容易时要确认红的原因）**成对**：
  那一条管「红得对不对」，这一条管「**绿得对不对**」。
  **只做负控不做「判据恒真自查」，门就仍然可能永远绿。**

### §152 **接手一份「已产出但从未消化」的报告，第一件事是查它是不是已经被别人修了**

上一轮的子代理报告基于 `e0625c6a5`，而 HEAD 已推进到 `002e15cb6`；
本轮复核的 5 条里**有 2 条已经被并发会话修好**（F1/F2）。
⇒ 若不复核就写进文档，会把**已修的东西当新缺陷**发出去；
  若不复核就照着「修」，会对已正确的代码再改一遍。
⇒ **判别方法**：每条结论都先 `git diff <报告基线> HEAD -- <相关目录>`
  看这个结论涉及的代码**有没有变过**，再决定它是「仍成立」「已修」还是「定性错误」。
⇒ 与 §211 的「子代理定性也要复核」互补：那一条说**要复核结论**，
  这一条说**先复核代码有没有动过** —— 顺序上它更早，成本也更低。
