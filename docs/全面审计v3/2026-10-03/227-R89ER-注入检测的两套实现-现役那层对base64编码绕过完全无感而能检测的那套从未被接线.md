## 九、playbook §184–§185

**§184 「两套实现」的能力差：锚点侧要机械钉，缺口侧只能打印。**

227 号的形式是「A 现役且缺 X / B 孤儿且有 X」。这类结论看起来是一条，
其实由**两个方向相反的断言**组成，而它们的**可靠性差了一个数量级**：

| 方向 | 断言形态 | 失败模式 | 本轮处置 |
|---|---|---|---|
| **锚点侧** | 「`enhanced/detector.go:371` 的递归复检还在」 | 能力被删/被重构 ⇒ 门必须转红 | **作为失败条件**（`TestOrphanDetectorCapabilitiesAreRegistered`） |
| **缺口侧** | 「父包对 `base64\|unicode\|rot13` 零命中」 | 搜错词形 ⇒ 恒「成立」；补上能力 ⇒ 结论过期 | **只 `t.Log` 打印，不失败**（§157） |

⇒ **判别式**：一个能力差结论里，**能指名到「文件:行号 + 具体构造」的**那一侧才是硬证据，
  「grep 零命中」的那一侧永远是软证据。
  把两侧塞进同一个断言，是把软证据的失效方式（恒真）传染给硬证据。
⇒ 缺口侧转为硬证据的**唯一**合法路径不是「把 0 变成 1 的判据」，
  而是**照抄权威规则的判定式**（§168/§177）—— 本轮做不到，因为「父包应当具备编码检测」
  本身还是**待裁决 93**，不是规则。
⇒ 附带的**自我失效**设计：若哪天父包真补上了编码能力，门会打印
  「缺口可能已消失，请人工确认」而不是转红 —— 因为此时**要变的是裁决项，不是代码**。
  一个门不该因为裁决推进就变红。
⇒ 与 §157（0 命中更容易错）互补：§157 说 0 命中易被采信，
  这条说**0 命中连当失败条件都不该**，只能当证据。

**§185 用命中数下否定结论之前，先确认自己搜的词覆盖了所有引用形式。**

本轮我犯的错（报告 §六，当场收回）：
`encodingDetectors` 只 grep 到 `:75`（字段声明）、`:305`（赋值）两处 ⇒
我判「`enhanced` 的编码层是死代码，连它自己都没用」⇒ 差点把「能力差不存在」写进报告。
**再跑一次 `git grep` 找到 `:357` 的 `for _, detector := range d.encodingDetectors`**，
在 `heuristicDetect` 里真实遍历、真实递归复检。

⇒ 失效机制不是「搜错了地方」，而是**「赋值 ≠ 引用，声明 ≠ 使用」**：
  `X` 这个名字在文件里出现 2 次，完全可以对应「声明 1 次 + 写入 1 次 + 读 0 次」，
  **而这三种形态在任何一次 grep 的输出里长得一模一样**。
⇒ **判别式**：把命中逐条**归类**成「声明 / 写入 / 读取」再下结论。
  只要还有一条命中没被归类，「零使用」就还没被证明。
  本轮 3 次命中里前 2 次被归为声明+写入、第 3 次才是读取 ⇒ 结论翻转。
⇒ 与 §216（第一次订正写错了漂移时间线）、§223（尺子输出看起来像结论）同族：
  **一个基于"只找到 N 处引用"的否定结论，差一次 grep 就翻转**，
  而它在翻转前的样子和翻转后一样笃定。
⇒ 成本极低的对策：**否定结论必须附「命中数 + 逐条归类」**，
  只写「零命中」不写归类，等于把结论的支撑留给下一个会话重新怀疑。
