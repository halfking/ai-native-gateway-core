## 〇、起手：一个「看起来权威」的文件，两轮都照抄了它

204 号把 `admin/probe_history.go` 的裸母表读换成 `request_logs_with_current_month` 视图，理由是：

> 两腿在任一快照上互斥（promote 是单条数据修改 CTE 且无 `ON CONFLICT`，冲突时整体回滚），故 `UNION ALL` 不会把同一行数两遍（202 号 §107 的写入侧不变式四步）。

203 号的四步证明整篇都在论证**同一个文件的同一段 SQL**：`sql/objects/views/request_logs_with_current_month.sql` = `FROM public.request_logs_hot UNION ALL SELECT … FROM public.request_logs`。

本轮去还下一笔债（`admin/memora_handlers.go`），顺手查它同文件 `:522` 用的那个视图到底是不是这一个——**不是。**

## 一、🔴 F1：部署形态是**三臂 + 双反连接**，那份 dump 是 **v1 回退体**

### 1.1 部署形态（实测自 composer 源码）

`db/request_logs_view_schema.go:799-822`（`canonicalV2DDL`）：

```sql
CREATE OR REPLACE VIEW public.request_logs_with_current_month AS
SELECT <proj> FROM public.session_turns_hot t <detailsJoin>   -- 臂 1：会话 hot
UNION ALL
SELECT <proj> FROM public.session_turns t <detailsJoin>       -- 臂 2：会话 cold
UNION ALL
SELECT <proj> FROM (
  SELECT <names> FROM public.request_logs_with_current_month_without_request_class_due_at v
  LEFT JOIN LATERAL ( … FROM public.request_logs_hot h … UNION ALL … FROM public.request_logs p … LIMIT 1 ) source ON true
) rl
WHERE NOT EXISTS (SELECT 1 FROM public.session_turns_hot th WHERE th.request_id = rl.request_id)
  AND NOT EXISTS (SELECT 1 FROM public.session_turns tp   WHERE tp.request_id = rl.request_id)
```

活库实测与之一致，且**是三臂**（`db/view_schema_v2_contract_test.go:676-679`，2026-10-02 按 `pg_get_viewdef` 行号）：

| 行 | 臂 |
|---|---|
| `L1` | `SELECT NULL::bigint AS id` ← `FROM session_turns_hot t`（会话 hot） |
| `L146` | `SELECT NULL::bigint AS id` ← `FROM session_turns t`（会话 cold） |
| `L291` | `SELECT rl.id` ← v1 臂（`rl` = `request_logs_hot` 侧） |

### 1.2 那份 dump 是什么

`sql/objects/views/request_logs_with_current_month.sql`：**两条臂** `request_logs_hot ∪ request_logs`，**无反连接**，114 列。

对照 `:213-225`「无会话族（极简/陈旧库）：维持 v1 体」⇒ **它是 v1 回退体**，且**仍然可产出**（不是死件）。

### 1.3 ⇒ 后果不是「文件写错了」，是「**它长得就像权威定义，而没有任何机制会喊**」

`sqlreadguard` 把它登记为 `LEGIT: 双腿视图定义本体`；`.gitignore:196-197` 写明 `sql/objects/` 是 SSOT（`deploy/sql/objects/` 是它的派生副本）。一个 DBA 按 SSOT 同步，看到的就会是这条两臂 `UNION`——**它没有 session 臂，也没有去重**。

## 二、这笔债对 203/204 号各自意味着什么（区分「结论」与「理由」）

| | 203 号 | 204 号 |
|---|---|---|
| **结论** | 「双腿视图不会重复计数」 | 「换视图后计数只可能持平或上升」 |
| 结论是否仍成立 | ✅ 成立，但**范围要缩小** | ✅ 成立 |
| 原**理由**是否成立 | ❌ 「两腿互斥」描述的是**回退体**的 hot/mother 对 | ❌ 同上 |
| 真实的理由 | 部署体的去重是 **v1 臂上的双 `NOT EXISTS` 反连接**（`:821-822`） | 同左 |

**203 号的证明并没有被推翻，而是被降级**：它证明的是**部署体 v1 臂内部**那条 hot/mother 子结构（`request_logs_hot ∪ request_logs`，在 `:811-817` 的 lateral 里）的性质 —— 那条子结构确实存在，四步也仍然有效。错的是**把它当成了「整个视图的两条腿」**。

⚠️ 而这在语义上**更要紧**：部署体里**会话臂与 v1 臂本来就会同时存在同一逻辑请求** —— 那条反连接存在的**全部理由**就是消掉这种重复。203 号的「两腿互斥」若被后来的人当作「视图天然不会双计」引用，会得出一个**比真相更强、且方向相反**的结论。

**204 号同理**：「持平或上升」依然对（反连接保证一逻辑请求一行 + 会话臂/hot 腿补足盲区），但已在 `admin/probe_history.go` 的注释里改成正确表述并标注 R89-DP 更正。

## 四、新门：把「这份 dump 属于哪一代」变成会响的判据

`db/request_logs_view_dump_generation_test.go`，**两个测试**：

### 4.1 `TestRequestLogsViewDumpGeneration`（主断言）

1. **覆盖下限**：从 dump 抽到的源表 **≥ 2**，否则 `t.Fatalf`（空集合同样满足「不是 session-family」）；
2. **世代判定** = `v1-fallback-two-arm`（两条臂精确匹配 `request_logs_hot` + `request_logs`），否则红并附**二选一处置**（保留回退世代并注明 / 删文件并停止把 `sql/objects/views/` 当该视图的部署 SSOT）；
3. **反连接缺席**：dump 里出现 `NOT EXISTS` ⇒ 红（它已被换成部署体，上面那条应当先红）；
4. **指针注释在场**：dump 必须点名 `db/request_logs_view_schema.go`。⚠️ **注释不是契约，但可以被契约引用** —— 这里断言它存在，是为了让它不会在某次重新 dump 时静默腐烂；
5. **composer 侧两代都仍可产出**：5 条代码级字面量断言（两条会话臂 + **两条反连接** + v1 两臂包装重建），任一消失 ⇒ 红并提示「dump 的登记前提已不成立」；
6. **composer 覆盖下限**：`FROM public.session_turns` 出现 **≥ 4** 次 —— 否则上面 5 条可能一起退化成恒真。

⚠️ 判据全部用**代码里的 SQL 字符串字面量**，不用注释（`:21-25` 那段注释恰好在讲会话族，用它当判据就是自证）。

### 4.2 `TestViewDumpVerdictDiscriminates`（鉴别力证明，与主断言同函数）

- **负控 1**：把两条会话臂注入真 dump ⇒ 必须判成 `session-family-three-arm`（证明它分得出两代，而不是「不含 `session_turns` 就算过」）；
- **负控 2**：`CREATE VIEW v AS SELECT 1 FROM public.request_logs;`（**单臂**）⇒ 必须判成 `unknown-shape`（证明判据不是子串匹配）。

**两条负控每次运行都跑**，不依赖临时改文件、不依赖外部 fixture ⇒ 判据的牙不会随时间退化。

### 4.3 文件级负控（在**未修复的真实文件**上跑，绿是改完才拿到的）

## 八、playbook 新增

### §112 「看起来像权威定义」的文件要问**它是不是运行时那一份**

同一个概念在本仓有**多份载体**：composer（Go）、编号迁移 SQL、`sql/objects/*.sql` dump、baseline dump、installer 内嵌副本。
**有门绑住的只是其中一对**（本仓：composer ↔ migration 734）。

⇒ **引用任何一份当「定义」之前，先问：它是被哪道门钉到运行时的那一份？**
  - 钉住了 ⇒ 可以引用；
  - 没钉住 ⇒ 它是**某个世代的快照**，引用它就是在引用一个「可能不存在于任何正常部署库」的结构。
⚠️ 典型误导形态：**回退体长得最像权威定义**（它更简单、更完整、没有条件分支），所以人天然会去引用它。

### §113 判据要用**代码里的字面量**，不要用注释

本轮刻意没用 `request_logs_view_schema.go:21-25` 那段注释当判据 —— 它恰好在讲会话族，用它就是自证。改用 `:801/:804/:821/:822/:125` 这些 **SQL 字符串字面量**。

⇒ 审计/建门时若判据只能落在注释上，通常说明**缺少一个可执行的结构标记**，先找那个标记，别退而用注释。

### §114 负控优先做「在真实文件上」，构造文本是次优

本轮两种都做了，但**证据强度不同**：

- 构造文本负控（`TestViewDumpVerdictDiscriminates`）：**每次运行都跑、不会腐烂**，但它证明的是「函数对给定输入的行为」；
- 真实文件负控（删注释 / 注入臂）：证明的是**这道门在真实仓库状态下真的会红**，但只在改动的那个瞬间做过一次。

⇒ **两者都做**：常驻的用构造文本，落地时用真实文件补一次。
