## 一、结论先行

**`web/src/api/` 里有 7 个后端端点被两个模块各自定义了一份函数，其中 2 个的返回形状互不兼容。**

| 端点 | 声明 A | 声明 B | 后端权威 | 判定 |
|---|---|---|---|---|
| `/api/admin/modules` | `modules.ts:59` → `{ items: ModuleWithStatus[] }` | `ops.ts:163` → `ProductModule[]`（裸数组） | `admin/modules.go:787` 写死 `map[string]any{"items": out}` | **B 与后端不符** |
| `/api/system/license/status` | `customer.ts` → `mode: 'licensed'\|'community'\|'restricted'` | `ops.ts:758` → `mode: 'normal'\|'in_grace'\|'restricted'` | `licensing/customer_api.go` 字段注释 `// "licensed" \| "community" \| "restricted"` | **B 含后端不产出的取值** |

第二组尤其隐蔽：**两个类型名不同只是命名问题，真正的不兼容在 `mode` 的取值域**——
三���取值里**只有 `restricted` 交集**。按错误那套写 `mode === 'licensed'` 的分支**永远不成立**，
而 **TypeScript 不会报错**。

⚠️ **并且两个函数同名**（都叫 `getLicenseStatus`，`customer.ts:89` 与 `ops.ts:758`）
⇒ 将来有人 import 错的那一份，**改 import 路径不会报错、只会换一套语义**。

## 二、⚠️ 诚实边界决定定级：**这两份定义都零调用方**

```
git grep getProductModules -- web/src/   ⇒ 只有 ops.ts:162 定义行本身
git grep getLicenseStatus  -- web/src/   ⇒ 只有 customer.ts:89 与 ops.ts:758 两个定义行
```

⇒ **这不是现役缺陷，是「接口层已分叉、尚未传导到视图」**。
⇒ 故定 **P3**，不发 P1/P2。
⇒ **本门的价值不是抓现役 bug，而是挡住「分叉被接线」的那一刻** ——
那一刻不会有任何编译错误、不会有任何测试失败，只会在运行时静默出错。

⚠️ 诚实边界：**未起前端进程、未跑 `tsc`、未在浏览器里点过任何页面**；
「零调用方」= `git grep` 检索的结论，**不等于**已证明没有任何动态 import 路径。

## 三、本门（`internal/sqlguard` 新增 `TestApiLayerEndpointShapeParity`）的判据

**后端一个端点只应在前端 api 层有一份形状声明。**

两条检查：

1. **顶层形状**：后端写死 `{"items": ...}` ⇒ 声明里必须出现 `items` 键；
2. **字段取值域**：`mode` 的联合类型必须**全部落在后端产出的取值集合内**。

⚠️ **设计要点：逐份与后端比，而不是"彼此不同就算分叉"**（见 §五 尺子 3）。

## 四、⚠️ 量化过程：尺子错了两次才量到东西

### 尺子 1：扫错层（`views/*.vue` → `web/src/api/*.ts`）

第一版在 `web/src/views/*.vue`（105 个）+ `web/src/components/*.vue`（161 个）里 grep 端点，
结果：**"被 >1 个视图调用的端点：0 / 共 16"**。
这个 0 看起来像"前端没有重复调用"，但它是**假的 0**。

**真因**：前端把路径包在 `web/src/api/*.ts`（63 个模块）里，**视图只调 api 模块的函数名**。
⇒ 换到 api 层重扫：**337 个端点、7 个被 >1 个模块定义**。

⇒ **判别式**：「0 命中」是 §157 的老陷阱，这里还多一层：
**0 可能不是"没有"，而是"扫错了地方"**。
⇒ 数字从 16 跳到 337（**21 倍**）这件事本身就是尺子错的信号
（与 §174「数字大得离谱时先怀疑尺子」对称：**数字小得离谱时也一样**）。

### 尺子 2：把"类型名不同"当成分叉证据

第一版的门只比"前端两份声明的类型名是否相同"。
于是 `/api/system/license/status` 那组只报了「`CustomerLicenseStatus` vs `LicenseStatus`」，
**而真正的分叉（`mode` 取值域完全不交集）被整类跳过**。

**真因**：我在 `if len(uniq) > 1` 分支末尾顺手加了一个 `continue`，
下一个端点就**永远走不到**取值域检查。

⇒ **判别式**：**在「已经报了一条」之后加 `continue`，会让另一类缺陷整类失明。**
⇒ 修法：去掉 `continue`，两类检查各自独立跑。

## 五、⚠️ 尺子 3（负控 NC-H 抓出来的）：量的不是「与后端的一致性」，是「彼此不同」

负控 NC-H 的做法：把 `ops.ts` 的 `mode` 改成与后端一致
（`'normal'|'in_grace'|'restricted'` → `'licensed'|'community'|'restricted'`）。

**结果**：`❌` 标记正确消失了，**但门仍然报"分叉"**。

**真因**：判据写的是"两份声明**彼此不同** ⇒ 分叉"。
改成一致之后两份**彼此相同**了……可我在别处还有 `uniq` 是按类型名去重的，
`LicenseStatus` 与 `CustomerLicenseStatus` **类型名仍然不同** ⇒ `len(uniq) > 1` 仍成立 ⇒ 仍报。

⇒ **判据量的东西和它声称量的东西不是一回事**。
⇒ 修法：**逐份与后端比** ——
  - `authoritativeFrontShape(e)` 返回后端权威形状（`{"items":...}` ⇒ `"object"`）；
  - `shapeAgrees(declared, "object")` 逐份判定；
  - **全部一致 ⇒ 不是分叉，只是重复声明**；
  - `authoritative == ""`（形状在类型名层面判不了）⇒ **不下分叉结论**，交由取值域检查裁决。

⇒ 这一条比前两条更值钱，因为它说明：
**「A 与 B 不同」和「A 与权威不同」是两个不同的命题，判据必须写清它测哪一个。**
⇒ 与 §173（数字不回答"是什么"）、§177（判据与权威规则的宽严）同族：
**判据必须显式对齐"权威"，而不是对齐"另一个被测对象"。**

### 两条负控（全部实测）

| 负控 | 手法 | 结果 |
|---|---|---|
| **NC-H** | 把 `ops.ts` 的 `mode` 改成与后端一致 | ✅ 该组分叉消失、转为「只是重复声明」；**`modules` 那组仍报**（证明逐条独立） |
| **NC-I** | 把 `ops.ts` 的 `/api/admin/modules` 类型改成 `{ items: ProductModule[] }` | ✅ 该组分叉消失、转为「只是重复声明」；**license 那组仍报** |

## 九、playbook §181–§183

**§181 「0 命中」有两种成因，而它们需要相反的下一步。**

226 号第一版在 `web/src/views/*.vue`（105 个）+ `web/src/components/*.vue`（161 个）里
grep 端点，结果：**「被 >1 个视图调用的端点：0 / 共 16」**。
这个 0 看起来像"前端没有重复调用" —— **它是假的 0**。

真因：前端把路径包在 `web/src/api/*.ts`（63 个模块）里，**视图只调 api 模块的函数名**。
换到 api 层重扫：**337 个端点、7 个被 >1 个模块定义**。

⇒ **数字从 16 跳到 337（21 倍）这件事本身就是尺子错的信号。**
⇒ 与 §174（数字大得离谱时先怀疑尺子）**完全对称**：
  **数字小得离谱时也一样要先怀疑尺子。**
  一个"0 条缺陷"的结果有三种可能：
  ① 真没有；② 扫错了地方（本轮）；③ 判据的谓词恒假（本审计已记过多次）。
  **三者的下一步完全不同**，而产物形态一样（一个漂亮的 0）。
⇒ **判别式**：拿到"0 条"时，先问「我扫的面是不是数据真的所在的地方」。
  跨层架构里，**数据在哪一层被集中，比数据被怎么使用更决定扫描面**。
⇒ 与 §157（缺失断言更容易错，因为 0 命中时人会直接采信）同源，
  这条补上了它的另一半：**0 命中时，人容易采信的是数字，不是"0"这个结论**。

**§182 在「已经报了一条」之后加 `continue`，会让另一类缺陷整类失明。**

226 号的门第一版结构是：

```go
if len(uniq) > 1 {
    t.Logf("…形状声明有 %d 种…")
    continue              // ← 顺手加的
}
// 下面的 mode 取值域检查
```

⇒ `/api/admin/modules` 那组满足条件 ⇒ `continue`
⇒ `/api/system/license/status` 那组**也满足**条件，但它的真正问题在**另一个维度**（取值域），
  而那个维度的检查在 `continue` 之后 ⇒ **整类失明**。

现象：门一直报「`CustomerLicenseStatus` vs `LicenseStatus`」，
**读起来像是**一个完整结论，**实际上它只覆盖了两个端点里较轻的那个维度**。

⇒ **判别式**：写多个检查维度时，**每个维度必须能独立到达**。
  用 `t.Errorf`/`t.Logf` 分支时不要顺手 `continue`；
  若确实要提前退出，把退出条件写成"**这个对象已经判定完毕**"而不是"已经报过一条"。
⇒ 与 §172（豁免与门要可证伪）配套：**门覆盖的维度集合也要能被检验** ——
  加一条"每个已登记的检查维度都必须至少被一条登记项走到"的断言。

**§183 判据必须显式对齐「权威」，而不是对齐「另一个被测对象」。**

负控 NC-H 抓出来的：把 `ops.ts` 的 `mode` 改成与后端一致后，
`❌` 标记正确消失了，**但门仍然报"分叉"**。

真因：判据写的是"两份声明**彼此不同** ⇒ 分叉"。
而 `uniq` 是按**类型名**去重的（`CustomerLicenseStatus` vs `LicenseStatus` 仍然不同）
⇒ `len(uniq) > 1` 仍成立。

⇒ **「A 与 B 不同」和「A 与权威不同」是两个不同的命题**，而我写的是前者、声称的是后者。
⇒ 修法三步：
  ① `authoritativeFrontShape(e)` 显式给出后端权威形状；
  ② `shapeAgrees(declared, authoritative)` **逐份**与权威比；
  ③ **全部一致 ⇒ 不是分叉，只是重复声明**；
     `authoritative == ""`（该端点形状在当前维度判不了）⇒ **不下结论**，交另一维度裁决。
⇒ 两条负控验证了逐条独立性：改掉一份，**对应**组分叉消失、**另一组照报**。
⇒ 与 §173（数字不回答"是什么"）、§177（判据宽严必须与权威规则一致）同族，
  但补了一个更前置的形态：**判据要对着"权威"写，不能对着"另一个被测对象"写** ——
  后者会让"把两个错的都改成一样的"这种状态继续被报成缺陷。
