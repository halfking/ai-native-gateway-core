## 二、🔴 A1：同一个坏谓词，**两副伪装**，而且加了保护的那一份**更危险**

两处 STORAGE_MIX 的写法不同，但坏在同一个点上。

**`minimal:55-61`（原写法）**

```sql
SELECT 'total = ' || pg_size_pretty(sum(pg_total_relation_size(c.oid)))
     || ' | heap = '  || pg_size_pretty(sum(...) FILTER (WHERE c.relkind IN ('r','m')))
     || ' | index = ' || pg_size_pretty(sum(...) FILTER (WHERE c.relkind='i'))   -- ← 恒假
     || ' | toast = ' || ...
     || ' | relations = ' || count(*)
FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='public' AND c.relkind IN ('r','m','t','p');                      -- ← 不含 'i'
```

**机制**：`WHERE` 已经把行限定在 `relkind IN ('r','m','t','p')`，**`'i'` 不在其中**；于是 `FILTER (WHERE c.relkind='i')` **结构上永远为假** ⇒ `sum(...)` = `NULL` ⇒ `pg_size_pretty(NULL)` = `NULL` ⇒ `' | index = ' || NULL` = `NULL` ⇒ **`||` 链把整行塌成 NULL**，输出一个空行。

**`round2:16-20`（原写法）**：同一处，只是外面套了 `coalesce(..., 0)`。

```sql
coalesce(sum(pg_relation_size(c.oid)) FILTER (WHERE c.relkind = 'i'), 0) AS ix
```

⇒ 报出 **`index = 0 bytes`**。

### 为什么 round2 那一份**更危险**

| | 现象 | 操作人会怎么读 |
|---|---|---|
| `minimal` | **空行** | 看得见不对 ⇒ 会去查 |
| `round2` | **`index = 0 bytes`** | 一个**看起来完全正常的真实数字** ⇒ 会直接拿去做判断 |

**加了 `coalesce` 的那一版，失败形态从「明显异常」退化成「可信的假数据」。** 这是本轮最值得记的一条：`coalesce`/`IFNULL` 这类**兜底**在报表语境里不是「更稳健」，它会把**「无数据」和「判据恒假」压成同一个值**。

⚠️ 这与 208 号 F1 是同一家族（恒真的谓词不是门，是装饰），只是方向相反：208 号是**恒真**，这里是**恒假**。两者都不会报错。

### 改法

索引体积**必须自己扫一张 `relkind='i'` 的表**，不能在已过滤的集合上再 `FILTER`。两处都改成标量子查询：

```sql
pg_size_pretty((SELECT sum(pg_relation_size(i.oid))
                 FROM pg_class i JOIN pg_namespace n2 ON n2.oid=i.relnamespace
                 WHERE n2.nspname='public' AND i.relkind='i'))
```

## 四、🟡 A3：**子代理的定性错了** —— 那个覆盖是刻意的，缺的是「完整性信号」

`.db-audit/d252async.ps1:93-97`：

```powershell

# 单条失败不影响其余,且同样挡住误写。
$wrapped = "\set ON_ERROR_STOP off`n" +
           "SET default_transaction_read_only = on;`n" +
           "SET statement_timeout = '${StatementTimeoutSec}s';`n" + ...
```

⇒ **`ON_ERROR_STOP off` 是作者刻意选的**，注释写明了理由：宁可少一段，也要保住其余段落。**这个取舍本身是合理的**，子代理把它当成「覆盖脚本自己的要求 ⇒ 缺陷」，定性错了。

而且**方向也是安全的**：五个采集脚本全是只读 SELECT，`default_transaction_read_only = on` 才是真正挡误写的那道。

### 真正的缺口：报表**没有办法区分「全跑完」和「第 3 段炸了」**

`:173-175` 数出了段落数但**只打印**：

```powershell

Write-Host "sections: $($sec.Count)"
```

而 `:160` 的 `rc` 因为 `ON_ERROR_STOP off` 而**恒为 0**；错误只出现在 `:167-171` 的 diagnostics 里、**只印前 20 行**、**不落进报表**。

⇒ **A1/A2 就是这样一路静默到没人发现的。**

**子代理说「没有期望值可比对」是错的** —— 期望值就在仓库里：
`.db-audit/sql/batches/MANIFEST.txt` 列了 collect 的全部段落，`batch-0*.sql` 头部写着 `sections: 1..10 **of 38**`。**38 这个数是现成的、可校验的，只是没人去比。**

实测（对着真的 `collect.sql`）：数出 **38** 段，与 `MANIFEST.txt` 完全一致、无重复。PowerShell 解析器语法检查通过（本机**无 bash**，`guards-sync.sh` 未执行，见 §六）。

## 八、playbook 新增

### §134 **兜底（`coalesce`）在报表语境里会把「无数据」和「判据恒假」压成同一个值**

同一个 `FILTER (WHERE relkind='i')` 坏在两处，只因外面套没套 `coalesce` 而得到**两种失败形态**：

- 没套 ⇒ `NULL` ⇒ `||` 链**整行塌成空行** ⇒ 看得见不对；
- 套了 ⇒ `0` ⇒ 报出 **`index = 0 bytes`** ⇒ 一个**看起来完全正常的假数字**。

⇒ **加了兜底的那一份反而更危险**，因为它把「异常」压缩成了「可信的测量」。
⇒ **判别方法**：报表/告警里的 `coalesce(agg, 0)` / `IFNULL(agg, 0)` 要问一句
  「**这个 0 是『真的没有』还是『判据恒假/取不到』？**」。二者必须**可区分**
  （用 `NULL`、或并排列出「采到几行」）。
⇒ 同 §120 家族，方向相反：**恒真**谓词是装饰，**恒假**谓词是假数据。两者都不报错。

### §135 **改完主脚本要回补所有同族副本**

A1/A2 的复盘文档（`docs/database/2026-10-02-db-audit-34pg17-and-optimization.md:709-710`）
**已经记过这两个现象**，`round3` 头部也写了「已修」—— 但**修的只有 round3**，
`minimal` 与 `round2` 两份**没被回补**。⇒ **复盘文档里记下「已修」不等于副本已修。**
⇒ **判别方法**：看到一个 bug 的修复记录，先问「**同族有几份副本？各份的修法一致吗？**」；
  本仓的采集脚本、迁移 down 体、`sql/objects` dump 都存在**同源多副本**的结构。

### §136 **PG 版本升级会改列名，而改名不会报错**

`pg_stat_bgwriter.buffers_checkpoint`（PG17 前）→ `pg_stat_checkpointer.buffers_written`（PG17）。
`minimal` 沿用旧名 ⇒ 整段报错消失，**而该文件自己设了 `ON_ERROR_STOP off`** ⇒ 报表里那段**静默缺失**。
⇒ 升级 PG 时，**所有**采集/报表脚本的 `pg_stat_*` 列名都要复查一遍，
  而不是只改「正在用的那一份」。

### §137 **一个「只在手工执行时绿」的守卫，和一个不存在的守卫是同一种东西**

`sql/schema` 的四个门在 208/209/210 三轮里**一路绿**，但**任何 CI job 都不跑它们**
（`make guards` 不含它 / 无裸 `go test ./...` / integration 清单按构造排除无标签包）。
⇒ 与 208 号 F4 同类失效的另一个面：那里是「门不跑」，这里是**「没人叫它跑」**。

⇒ **建门时必须同时回答**：「**它会被谁执行？**」——并把答案写成**机器可查的登记**，
  而不是靠「我本地跑了」。
⇒ ⚠️ **登记类断言不能挂在它自己要守护的那个包里**：一条挂在 `sql/schema` 的
  「`sql/schema` 已被登记」断言，只有在被登记时才执行 ⇒ **自证的断言在关键处等于没有断言**。
  必须放在一个**已经在登记表里**的包。
⇒ 同 §127：**别把「跑过了」当成「会被跑」**。本地绿 ≠ CI 会绿 ≠ CI 会跑。

### §138 子代理的**定性**也要复核，不只是事实

本轮复核发现：子代理把 `.db-audit/d252async.ps1:95` 的 `ON_ERROR_STOP off` 说成
「覆盖脚本自己的要求 ⇒ 缺陷」，而读完 `:93-94` 的注释发现那是**作者刻意且论证过的取舍**
（宁可少一段，也要保住其余段落；真正挡误写的是 `default_transaction_read_only`）。
它还说「没有期望值可比对」，而期望值（38）**就在 `MANIFEST.txt` 里**。

⇒ ⇒ **事实层复核**（列名对不对、行为是不是这样）与**定性层复核**（这算不算缺陷）
  是**两件事**，两者都要做。只做前者，会把作者的**刻意取舍**当成 bug 去"修"，
  从而**破坏一个有意设计**。
