## 一、起点：208 号的判据**不能**一刀切，但族级公分母是存在的

208 号为回收脚本立的判据是「每个含 DROP/TRUNCATE 的动作必须带**空表**门禁」。它对**回收类**完全正确，但套到全族会立刻变成误报机器：

`sql/fixes/2026-09-20-canonical-dedup-cleanup.sql` 合法地 **DELETE 非空行**——把 canonical 重复项归并掉正是它的目的。要求「删的表必须是空表」等于要求它什么都不做。

⇒ 族级判据必须取**真正的公分母**，而它与脚本做什么无关：**失败时能不能中止**。这一条对「回收 / 归并 / 重定向」三类同时成立，且可由文本判定。

新门 `TestHandRunSqlScriptsInventory` 实测覆盖 `sql/fixes/` + `sql/audit/`：

```

../audit/2026-10-02-db-unused-index-candidates.sql    破坏性动作=4  ⇒ 可中止=是（dry-run 闸）
../fixes/2026-09-20-canonical-dedup-cleanup.sql       破坏性动作=11 ⇒ 可中止=是（RAISE EXCEPTION + 显式事务）
../fixes/2026-10-02-db-storage-reclaim.sql            破坏性动作=6  ⇒ 可中止=是（四项全有）
../fixes/fix-missing-request-wal-hot.sql              破坏性动作=1  ⇒ 可中止=是
../fixes/fix-request-logs-bodies-partition-v2.sql     破坏性动作=1  ⇒ 可中止=是
../fixes/fix-request-wal-hot-primary-key.sql          破坏性动作=2  ⇒ 可中止=是
../fixes/normalize-columnar-historical.sql            破坏性动作=2  ⇒ 可中止=是（ON_ERROR_STOP）
```

## 二、F1：探针的判定与清理都被钉在 default 分区 ⇒ **目的达成后同时误诊 + 永久泄漏**

`sql/fixes/fix-request-logs-bodies-partition-v2.sql`。修改前的形态（`git cat-file blob HEAD:` 取回逐行核对）：

```sql
INSERT INTO request_logs_bodies (...) VALUES (test_request_id, NOW(), ...);   -- 写进父表
SELECT COUNT(*) INTO test_result
  FROM request_logs_bodies_default WHERE request_id = test_request_id;        -- ← 只看分区
IF test_result > 0 THEN
  RAISE NOTICE 'Insert test PASSED …';
  DELETE FROM request_logs_bodies_default WHERE request_id = test_request_id; -- ← 只清分区
ELSE
  RAISE WARNING 'Insert test FAILED';                                         -- ← 非致命
END IF;
```

**这个脚本存在的目的，恰恰是让写入别再落到越界分区。** 于是三个后果同时发生，且时序是「修复成功之后」才开始：

| # | 后果 | 说明 |
|---|---|---|
| ① | **误诊** | 路由修好后写入落在真正的日期分区上 ⇒ 父表/default 分区都该由父表可见，而 `test_result` 只数 default ⇒ 恒为 0 ⇒ 报 `Insert test FAILED`。运维会照着这个假象去查分区路由，而**路由是好的**。 |
| ② | **永久泄漏** | `DELETE` 够不着那行 ⇒ **每次运行都在生产 bodies 表里永久留一行**。 |
| ③ | **对自动化完全不可见** | `RAISE WARNING` 非致命；脚本**没有** `ON_ERROR_STOP`（实测 `on_error_stop` 在修复前后都是 false）⇒ 退出码 0。 |

①和②来自同一个错误：**验证性写入的清理与判定必须回到「写入发生的那一层」，而不是「你期望它去的那一层」。** 这是一条可推广的纪律——它与 208 号 F1 是同一个家族：**判据钉在了「意图」上，而不是「事实」上**。

> 旁证：这个脚本整体在**一个显式事务**里（`:5 BEGIN;` … `:70 COMMIT;`），所以泄漏行确实会被提交；而改成 `RAISE EXCEPTION` 后整块回滚，探针 INSERT 一并撤销。

### 改法

判定与清理都回父表（`:49` 判父表、`:61` 清父表），default 分区命中数降级为**纯诊断**输出、不参与通过与否；`:66` 把 `WARNING` 换成 `EXCEPTION`——「写不进去」是硬问题（分区约束/缺列/表不存在），必须中止，否则「验证失败」与「脚本成功」无法区分。

⚠️ **客户端观感不变**：本脚本无自动执行路径（208 号已确认 `sql/fixes/` 的性质），手跑行为的变化是「验证失败时脚本中止」而不是「报个警继续跑」。

## 三、本轮真正的收获：这条判据**三次**先空过、再一次过宽，每次都绿

新门的「探针泄漏」判据（探针写入的表没有被同表 DELETE 清理 ⇒ 每次运行泄漏一行）在本轮**改了三版才站住**，而三版的失败形态**全都表现为「安静地全绿」或「报一堆假警」**：

| 版本 | 做法 | 失败形态 | 根因 |
|---|---|---|---|
| ① | 拿**表名**去匹配探针 token | **恒空**（全绿） | token 在 VALUES / 变量初值里（`:39` `'fix-verification-' \|\| extract(epoch …)`），不在表名里 |
| ② | 按 `;` 切语句，要求语句内同时含 INSERT 与 token | **恒空**（全绿） | token 落在 `DECLARE … test_request_id TEXT := 'fix-verification-'` 那一条里，在 INSERT **之前**就已被 `;` 切走 |
| ③ | 改成**文件级** token 判定 | **4 处误报** | 要求「文件里所有 INSERT 的目标表」都在 DELETE 集合里，把 `bak_20260920_`（`EXECUTE format` 造的备份表）、`merge_map`（**永久**记录归并关系的表）、`request_wal_hot`、`candidate_failure_logs` 全判成泄漏 |

③的实测误报里有一条最值得记：**那三个文件里根本没有任何探针 token**（`Select-String` 逐文件确认，零命中）。原因比判据本身更严重——**③的实现连 `hasProbeToken` 都没判**，等于对每个脚本都跑了这条判据；而它自己的注释写着「不含探针的普通脚本根本不会被这条判据审视」。**注释与代码不符**，这正是本仓反复出现的那一类缺陷（本轮已第 N 次遇到，见 205 号「注释不是契约」）。

⇒ 最终形态是**三跳**：token 出现在文件里 → 绑定到 `TEXT :=` 该 token 的**变量名** → 该变量名出现在哪条 INSERT 的 VALUES 里 → 那条 INSERT 的**目标表**才是探针表。备份表/临时表/永久映射表都既不携带变量也不携带 token，天然不被误判。

**配套的三条纪律**：

- 变量名匹配必须做**词边界**（`containsWord`），否则 `probe_id` 会被 `my_probe_id_backup` 命中，过宽的老毛病原样回来（负控 7 钉住）。
- 覆盖下限必须**按新形态重算**：原先的「至少检出 1 个探针脚本」在②③下曾与「检测器坏掉」同步为真。现在下限仍是 1，但日志里显式写明「**只保证检测器活着，不声称一族查全**」——覆盖面会随新脚本增长，**不让这一行自动变松**。
- 本仓 `'probe-` 在 migrations 里有**相反**含义（`request_id NOT LIKE 'probe-%'` 是**过滤**探针，不是插探针）。它仍留在 token 表里，只因为本判据只把 token 绑到 **INSERT 的目标表**上；若将来把 token 判据放宽到文件级，它立刻变成误报机。这一条已写进代码注释钉住。

### 负控（7 条，与「能抓坏东西」**并列**）

好那一半就是本轮实测踩到的 4 处误报：

| # | 用例 | 期望 |
|---|---|---|
| 1 | 探针插父表、只从分区清理（本轮缺陷最小复现） | **报泄漏** |
| 2 | 探针插父表、从父表清理（修复后形态） | 不报 |
| 3 | 探针脚本里另有一处备份表写入，备份表永不被删 | **不报**（③ 在此误报） |
| 4 | 完全没有探针 token 的普通写入 | **不报**（③ 在此误报） |
| 5 | token 经 `DECLARE` 变量两跳绑定且未清理 | **报泄漏**（② 在此空过） |
| 6 | token 直接写在 VALUES 里且未清理 | **报泄漏** |
| 7 | 变量名按词边界匹配，不被更长标识符误绑 | 不报 |

⚠️ 负控 5/6 最初被我写成 `wantLeak: false`，**是负控自己抓出了我的错**：那两段探针确实没写清理，判据报泄漏是对的、我的期望是错的。已改正。**这就是必须把反向对照与正向断言写在同一张表里的原因**——否则我就会把判据改坏去迎合一个错期望。

## 四、R89-DV：全仓唯一的 `sql/objects/` 漂移门，**在本机从未真正运行过**

208 号 F4 把 `exec.LookPath("python3")` 换成活性探针 `python3 -c pass`，把「硬红」变成「大声跳过」。本轮接着往下走，发现**那只是把失败换了个方向，没有让门活过来**：

- 本机 `python3` 是 Windows App Execution Alias 桩，exit 9009 ⇒ **永久跳过**；
- 而**真实解释器存在且可用**：`python` = Python 3.13.9。

⇒ 208 号那道门在本机与 **Windows CI 矩阵**上是**永久静默跳过**的：红变成不红了，但它同时也永远不会绿着跑——**比硬红更坏，因为硬红会被人看见**。（205 号已确认这是全仓**唯一**核对 `sql/objects/` 漂移的机制。）

改法：按候选列表（`python3` → `python` → `py -3`）逐个做**活性**探针，取第一个真能执行 `-c pass` 的。`python3` 仍排第一，以兼容 Linux/macOS 与虚拟环境。

### F3：门一旦活过来，立刻暴露一个**报错形态误导人**的缺陷

活性解析让这道门第一次真正运行，随即硬红：

```
objects_registry_test.go: 未输出第三份表示（sql/objects）的对比小节
--- FAIL
```

这个报错形态极具误导性：它把「输出被按 **cp936/GBK** 编码」说成「工具根本没统计第三份表示」，读者会去查对账逻辑、查 objects 目录。**实测证明那行标题一直都在**：

```
## 第三份表示：../objects（2025 对象）
```

工具的中文小节标题随**区域设置**编码输出（中文 Windows 上 stdout 走 GBK，UTF-8 字面量永远匹配不上 GBK 字节）。⇒ 显式设 `PYTHONIOENCODING=utf-8`，判据与环境无关，不依赖「这台机器默认编码恰好是 UTF-8」。

这与 208 号 F4 属同一类：**报错形态把人引向错误的根因。**

修好后本机**首次真实运行**结果：2612 个对象，ADDED / MISSING / REORDERED 全为 0，`第三份表示` 小节正常输出（`仅 sql/objects 有 = 31`）。

⚠️ **这条结果不能读成「schema 无漂移」**：按原设计这是**自比对**（`--committed` 与 `--generated` 都指向 `01-schema.sql`），它证明的是**工具本身健全 + 自比对为零**，不是「已提交基线 == 真实 pg_dump 生成物」。后者需要真库，本轮无 PG，做不了。

### 活性判据的 4 条负控

判据写错有两个方向，各钉一条：

| # | 用例 | 钉住 |
|---|---|---|
| 1 | 候选里混进必然不存在的命令，但有一个活的 | 必须**顺延选中活的那个**（防「过度跳过」——即本轮要消灭的失效） |
| 2 | 全部候选都死 | 必须返回错误，**不得**返回「可用」解释器（防回到 208 号的硬红） |

## 八、playbook 新增

### §124 **验证性写入的清理与判定，必须回到「写入发生的那一层」**

探针插进**父表**，而 `SELECT COUNT(*)` 与 `DELETE` 都只针对**某个分区** ⇒ **目的达成之后才开始损坏**：

- 分区路由修好 ⇒ 写入落到真正的日期分区 ⇒ 计数恒 0 ⇒ 报「验证失败」（**误诊**：读者会去查一个其实是好的路由）；
- 同时 `DELETE` 够不着那行 ⇒ **每次运行永久泄漏一行**；
- 且常配 `RAISE WARNING`（非致命）⇒ 退出码 0 ⇒ **对 CI 完全不可见**。

⇒ 这与 §120 同族：**判据钉在了「意图」（我期望它去 default）上，而不是「事实」（它实际去了哪一层）上。**

⇒ **判别方法**：任何「写进去再查出来/再删掉」的验证块，先问「**我写入用的表名，和我判定/清理用的表名，是同一个吗**」。
⇒ **修法**：判定与清理都回到**写入那一层**；期望落点（如「default 分区应为 0 行」）**降级为纯诊断输出，不参与通过与否**。
⇒ ⚠️ 「写不进去」是硬问题（约束/缺列/表不存在）⇒ 用 `RAISE EXCEPTION` 而**不是** `WARNING`，否则「验证失败」与「脚本成功」无法区分。
⇒ ⚠️ **这类缺陷的时序特征值得单独记住：它只在修复成功之后才开始损坏。** 所以它**越晚修，越可能已经有人在真库上跑过若干次**——定级可以不高，但**不该无限期挂着**。

### §125 判据要泛化之前，先问「**公分母**是什么」；判据不能一刀切时，**先验证它不能**

208 号那条「每个破坏性动作必须带**空表**门禁」对**回收类**完全正确，套到全族立刻变成误报机器——因为归并类脚本**合法地删非空行**。

⇒ **公分母**是那个「与脚本做什么无关、但对每一类都成立」的属性。本例是：**失败时能不能中止**（`RAISE EXCEPTION` / `ON_ERROR_STOP` / 显式事务 / dry-run 闸）。
⇒ **判别方法**：拟泛化的判据，先找一个**它会误报的合法样本**；找得到 ⇒ 它不是族级判据，只是某一类的专属判据。
⇒ ⚠️ 公分母判据**不能替代**各类的专属判据，它只是**兜底**。「8/8 可中止」不等于「8 个脚本都审过了」——**说清这一点，否则清单会冒充覆盖面**。

### §126 判据的**失败史**要留档：它会先**空过**、再**过宽**，而**每一次都是绿的**

本轮那条判据改了三版：① 恒空（token 在 VALUES 里、却拿表名去匹配）；② 仍恒空（按 `;` 切段，token 落在 `DECLARE` 那条、在 INSERT 之前就被切走）；③ 从空转成 **4 处误报**。

⇒ **两处具体教训**：
- **注释会跑在代码前面**：③ 的注释写着「不含探针的普通脚本根本不会被审视」，而**实现里根本没有那个判断**。⇒ 注释里写了「不存在」的分支，要用**测试**钉住，不能靠读注释确认（本仓已第 N 次遇到，见 205 号「注释不是契约」）。
- **收窄到「文件级」不是收窄，是换了个方向放宽**。真正的收窄是**三跳**：token → 变量 → INSERT 语句 → **那条的目标表**。

⇒ **绑定的中间环节不能省**：token 在变量初值里、INSERT 只引用变量名 ⇒ **两跳**。且变量名匹配必须做**词边界**，否则 `probe_id` 会被 `my_probe_id_backup` 命中。
⇒ ⚠️ **词表要查该词在本仓有没有相反含义**：`'probe-` 在 migrations 里是 `NOT LIKE 'probe-%'`（**过滤**探针，不是插探针）。
⇒ **覆盖下限按新形态重算**，并在日志里显式写「只保证检测器活着，**不声称一族查全**」——**别让这一行自动变松**。

### §127 「把失败形态改掉」**不等于**修好；判据必须**与环境无关**

208 号把「存在性探针 → 活性探针」，红变成了**永久跳过**；而本机真实解释器（`python` 3.13.9）**一直存在可用**，只是被 `python3` 桩挡住。

⇒ **静默跳过比硬红更坏**：硬红会被人看见，跳过只是「看起来没问题」。
⇒ **别把失败换方向就收工**：判据写完要问「**在这台机器上它真的会跑吗**」。
⇒ ⚠️ **报错形态本身也是判据的一部分**：门一活过来就硬红「未输出第三份表示」，而那行标题**一直都在**——中文 Windows 上子进程 stdout 走 **cp936/GBK**，而断言是 **UTF-8 字面量** ⇒ **把「输出被按 GBK 编码」说成「工具没统计第三份表示」**，读者会去查错的方向（对账逻辑、objects 目录）。
⇒ **修法**：子进程输出显式钉编码（`PYTHONIOENCODING=utf-8`），**不要依赖「这台机器默认编码恰好是 UTF-8」**。
⇒ **审计看到一个门被 Skip，就去查它在本机到底跳过没有**：红与跳过都可能意味着门没运行，但**只有后者是沉默的**。

⇒ ⚠️ 附一条操作纪律（本轮踩到）：**负控红得太容易时，要先确认它是因为被测缺陷而红**。用 `git show … | Set-Content -Encoding UTF8` 回退文件时，PS 5.1 写入 **BOM 且把文件压成 1 行** ⇒ 整份被当行注释吃掉 ⇒ 门报「什么都没检出」，**红的理由完全不对**。⇒ 回退二进制文件要用 `git cat-file blob`。
