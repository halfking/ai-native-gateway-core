## 一、🔴 F1：这道门的第一版，在**正确代码**上报了 6 处幻影列

### 1.1 症状

门首次全量跑，在**两处从未被人碰过的正确查询**上报：

```
admin/usage.go: 字面量 #110 / #111 / #130 / #131  → success、latency_ms 不存在
admin/usage_provider_detail.go: 字面量 #34 / #55  → success、latency_ms 不存在
```

按我自己的 playbook（§91「一道会误报正确代码的门比没有门更坏」），**这种门必须先修好再谈覆盖面**。所以本轮 F1/F2/F3 全是门自身的缺陷。

### 1.2 根因：一个下标，不是算法

`createTableHeader` 是 `FindAllSubmatchIndex`，`m[1]` 是**整个匹配的末尾**，即开括号**之后**一位。而 `balancedParenBody` 的契约是「从开括号本身开始计数」：

```go
depth := 0
for i := openIdx; i < len(src); i++ {
    switch src[i] {
    case '(':  depth++
    case ')':  depth--; if depth == 0 { return src[openIdx+1 : i], true }
```

于是 `depth` 从未见过那个开括号，**第一次归零就返回** —— 而基线里第一个右括号是 `cost_usd numeric(12,6)` 的那个（`01-schema.sql:18254`）。正文在 `cost_usd` 处被截断：

| | 列数 | 缺哪几列 |
|---|---|---|
| 真实（19 基线 + 1 迁移 = **20**） | 20 | — |
| 截断派生（18239-18254 共 16 + `rate_multiplier`） | **17** | `latency_ms`、`success`、`error_kind` |

`latency_ms` / `success` 正是被误报的两列。**一个偏一位的下标，产出了一份看起来完全合理的错误 schema。**

### 1.3 ⚠️ 顺带查出：**197 号那三道派生护栏，在这起真实事故里全部失灵**

这是本轮最该记的一条，因为它证明那三道护栏的**设计前提是错的**。

截断后的 17 列集合，逐条对 197 号写的护栏：

| 197 号的护栏 | 截断集合上的结果 |
|---|---|
| `anchor: "rate_multiplier"` 必须存在 | ✅ **通过** —— 迁移 736 的列照样被 ALTER 扫描抽到 |
| `forbidden: [work_type, gw_session_id, compression_strategy]` 不得出现 | ✅ **通过** —— 三个都不在 |
| `minColumns: 10` 不得更少 | ✅ **通过** —— 17 > 10 |

**三道护栏全绿，而列集是错的。** 原因很直白：`rate_multiplier` 来自**跨文件的 ALTER 扫描**，与 `CREATE TABLE` 正文的截断**完全解耦**；所以「锚点存在」这条护栏对「正文被截断」这类失效**结构性地失明**。

修法不是给护栏再加一条，而是把 `minColumns` 提到**贴近真实值**（20 → 取 19），让截断（17）落在阈值以下。这条也记进 §93。

### 1.4 修法

```go
if bodyText, ok := balancedParenBody(string(baseline), m[1]-1); ok {
```

外加两道**自护栏**（不是可选的健壮性，是这个失效家族的复发保险）：

1. `balancedParenBody` 入口断言 `src[openIdx] == '('`，不满足直接返回 `false` —— 契约写在代码里而不是注释里；
2. 字符串字面量内的括号不参与计数（含 `''` 转义）。**注意：这一条是防御性的，不是本次的根因**（见 §六 证伪 1）。

## 二、🔴 F2：视图派生**过度收集**了一个 SQL 关键字 `case`

### 2.1 症状

修好 F1 之后，日志里视图仍然不对：派生出 **14** 列，真实 13。多出来的是 **`case`**。

根因在基线 `01-schema.sql:19105`：

```sql
19104  ... )) AS is_routable,
19105      CASE
19106          WHEN (NOT p.enabled) THEN 'provider_disabled'::text
```

`CASE` 独占一行，形状与 `    cmb.credential_id,` **完全一致**，`bareOutputColumn`（`^\s*(?:x\.)?([a-z_][a-z0-9_]*)\s*,?\s*$`）照单全收。

### 2.2 为什么这一条比它本身更值得记

`case` 只是一个关键字，危害接近零。**真正的问题是它暴露了门的失效方向是双向的**：

- 欠收集（§一）会被误报**吵醒**，有人会来修；
- **过度收集是完全安静的**：多出来的名字进 `known` 集合后，一个幻影列如果恰好叫 `case`，就会以「已知列」通过检查，而**没有任何护栏会响**。

所以我没有只加一个关键字过滤，而是做了两件事：

1. 新增 `sqlStandaloneKeywords`（pg_dump 可能让它独占一行的 SQL 关键字集）+ `isNotAColumnWord`，从派生侧堵住；
2. **把 `case` 写进该契约的 `forbidden` 列表**。这是刻意的：让「曾经真的被过度收集过的名字」留在禁用清单里，下次同类回归会**响**，而不是重新安静下去。

`minColumns` 也从 8 提到 12（真实 13），理由同 §一。

## 三、🔴 F3：覆盖面只写在日志里 ⇒ 这道门可以恒真

### 3.1 症状

第一版门自报 `scanned 62 (file, relation) pairs, 0 offending literals`，**PASS**。看着没问题。但「62」只是个 `t.Logf`。

也就是说，以下任一情况发生时，这道门**扫描 0 个文件、0 条违规、干净通过**：

- `repoRootFromCaller` 解析到别的目录；
- 谁往 `skipDir` 里加了一个目录；
- 仓库布局变化导致 walk 提前返回。

这正是 playbook §92 要求「让门自己报覆盖面」的**下一层**：197 号做到的是「报」，本轮必须做到「**低于下限就失败**」。

### 3.2 修法

按关系分别计数，并把下限写成契约字段：

```go
// measured 29 / 33；留出余量给「读端被合法删除」，但不允许静默缩小
minReaders: 25,
```

```go
if readersPerContract[di] < d.contract.minReaders {
    t.Errorf("%s: the gate only reached %d production readers, expected at least %d. …",
        d.contract.name, readersPerContract[di], d.contract.minReaders)
}
```

自报结果（每次运行都打印，便于日后校准阈值）：

```
usage_ledger: 20 columns derived … | reached 29 production readers (floor 25)
v_routable_credential_models: 13 columns derived … | reached 33 production readers (floor 25)
```

29 与 197 号文档里的 29 独立吻合。

### 3.3 ⚠️ 「读端」这个词必须诚实

预筛是**字节级 `strings.Contains`**：一个文件只要**提到**关系名就算数。因此

- **29 / 33 是真实读端的上界，不是精确值**；
- 只在注释里提到该关系的文件也被计入；
- 门的作用域是**字面量**，不是「执行到的查询」。

这三条是本门的固有边界，写在门自己的注释里，不留给下一个人去发现。

## 六、证伪清单（5 条，含我自己犯的三次）

1. ❌ **撤回「根因是 SQL 字符串字面量里的右括号打乱了括号深度」** —— 这是我调试中途的假设。它和真根因**产生完全相同的症状**（都在 `numeric(12,6)` 处提前终止），差点让我把一个防御性改动（引号感知）当成根修。**症状相同不等于根因相同**；真实根因是下标传错一位。
2. ❌ **撤回「197 号那三道派生护栏足以抓住这类失效」** —— §一.3 已证：截断集合下 anchor / forbidden / minColumns **全绿**。护栏集合覆盖的是「垃圾解析」，没有覆盖「解析截断且截断点在 anchor 之后」。
3. ❌ **撤回「视图多派生的那一列可以忽略」** —— 初判为无害噪音，实际是过度收集的实例，且正是**唯一能暴露护栏缺口**的信号。已登记进 `forbidden`。
4. ❌ **撤回「62 = 29 + 33 可以直接相加」** —— `cmd/gateway/main.go` 同时提及两个关系，是重叠文件；我一度以为无重叠。结论不受影响（门按关系分别计数，pairs 与去重文件数无关），但**手算不能当覆盖面证据，只能用门的自报数**。
5. ❌ **撤回「字面量编号可以用来定位」** —— 见 §4.2，负控实际跑完才决定改。

### 7.1 合并后复核：并发会话的 diff 引擎根修**没有推翻 82，反而给它加了一个新的偏移来源**

提交前 `git fetch` 发现 origin/main 领先 **10 个提交**，其中 `05e145267`（"diff引擎专项落地——两段式锚点"）改的正是 **196 号待裁决 82 的那条缝**（`domains/hooks/compression/diff.go`）。⇒ 逐条复核，**结论：F1 / F2 均未被推翻，但 F1 多了一个独立来源。**

| 196 号的结论 | 合并后 | 出处（合并后的行号） |
|---|---|---|
| `merged = lastMsgs ++ deltaTail` | ✅ **仍在**，形态不变 | `diff.go:145-147`（原 142-144） |
| `deltaTail = clientMsgs[anchorEnd:]` | ✅ 仍在 | `diff.go:130` |
| offset = `len(lastMsgs) - anchorEnd` | ✅ 公式不变（`anchorEnd` 仍是 client 侧下标，两条分支皆然：`:235` 返回 `len(lastComparable)`，`:281` 返回 `end = start + len(tail)`） | `diff.go:217-284` |
| `msgHash` = 32 hex（`h[:16]`）且经 Marshal 归一键序 | ✅ **未变** ⇒ F2「32 vs 64」依旧 | `diff.go:369-380` |

**⚠️ 但新增了一个偏移来源（新登记，属 82 的延伸）**：`findDeltaAnchor` 先把 `lastMsgs` **过滤**成 `lastComparable`——摘要标记（`isSummaryMarkerMsg` / `isUnmarkedGatewaySummaryMsg`）被 `continue` **剔除**（`diff.go:220-226`）；而无摘要分支用 `len(lastComparable)` 当锚点（`:235`）、有摘要分支用两段式 `end`（`:281`），**`merged` 用的却始终是未过滤的 `lastMsgs`**。

⇒ offset = `len(lastMsgs) - anchorEnd` 里，`anchorEnd` 由**过滤后**的视图决定，而 `len(lastMsgs)` 由**未过滤**的列表决定 ⇒ **两者之间的差现在额外取决于「缓存里有几条摘要消息」**。这个量随会话状态变化，**存下来的 refs 依然无法重建自己所在的坐标系**——与 196 号 §89 的结论方向一致，**不构成推翻，也不构成闭合**。⇒ **82 维持登记，且范围扩大一条**；本轮不改生产代码（改锚点语义属行为变更，需专轮 + 钉测）。

## 十、playbook 新增

### §93 派生器的护栏必须按「**失效方向**」配对，锚点只能防垃圾不能防截断

- **先枚举失效方向再设计护栏**：本族的两个方向危害完全不对称 ——
  **欠收集**会误报正确代码（吵，会被修）；**过度收集**把多余名字放进已知集合（**静默削弱门本身**，不会有人发现）。
  护栏要按方向配：欠收集靠「贴近真实值的 `minColumns`」，过度收集靠「**曾经真的被误收过的名字**进 `forbidden`」。
- **`anchor` 只防垃圾解析，不防截断**：跨文件来源的锚点（如 `ALTER TABLE … ADD COLUMN` 抽出的列）与正文解析**结构解耦**，正文截断时锚点照样在。
  本轮实测：截断集合 17 列，三道 197 号护栏**全绿**。
- **阈值要贴着真实值，不要贴着「看着合理」**：197 号的 `minColumns: 10` 对真实 20 列、截断 17 列**毫无区分力**。阈值的作用是**让已知的错误解析落在阈值以下**，所以它必须离真实值更近、离正确值更远。
- **同症状不等于同根因**：`numeric(12,6)` 里的右括号会同时让「下标传错」和「字面量里有括号」两种 bug 产生完全相同的截断点。⇒ 改代码前先**证明**哪一处，别把防御性改动当根修。
- **过期的护栏要退役，不要叠加**：发现旧护栏在新事故里失灵时，先想「它防的是不是另一种方向」，再决定补新的还是改旧的；否则护栏集会越堆越多而**每一条都在给错误的失效点头**。

### §94 门的覆盖面必须是**断言**，不是日志；「读端」一词要按它的真实口径说话

- **自报覆盖面是装饰，低于下限才失败才是守卫**。197 号做到「报」，本轮补上「低于下限直接失败」。否则 `repoRootFromCaller` 解析错、目录被加进 `skipDir`、仓库布局变化 —— 任何一种都会让门扫描 0 个文件并**干净通过**。
- **按维度分别计数**。合并成一个总数会让单侧覆盖塌陷看不出来（本轮 `scanned 62` 同时包含两张表；`usage_ledger` 掉到 0 而路由视图不变，总数只从 62 变成 33，不刺眼）。
- **计数口径要诚实**。字节级 `strings.Contains` 预筛意味着「读端」= **提到该关系的文件**，**上界**，注释也算。把它写成上界，而不是在文档里当精确值引用。
- **门的作用域要在门自己的注释里写成上限**。本门看不见 `fmt.Sprintf("… v.%s …", col)` 这类**列名来自变量**的拼接 —— 门是字面量级的，别让下一个人以为它覆盖了全部。
- **报错信息属于门的一部分**。`string literal #40` 要求读者手工数字符串才能定位；`>>` 标出命中行的 SQL 片段才是可执行的报告。**负控实际跑一遍**，往往才会发现报告本身不可用。

### §95 合并进来的改动落在**你已登记的缺陷**上时，结论必须写成三态

提交前的例行 `git fetch` 很可能带进一批**正好压在你那条缝上**的并发提交（本轮：`05e145267` 改的正是 196 号 82 的 `diff.go`）。此时**「合了、没报错」不是结论**，必须逐条回到原始出处复核，并把结论写成三态之一：

1. **已被推翻** —— 缺陷不存在了，降级或撤销登记；
2. **未被推翻** —— 关键行仍在、形态不变（要给出**合并后的新行号**，旧行号会让人查错地方）；
3. **未被推翻但新增来源** —— 原缺陷还在，且改动**又添了一个独立成因**（本轮：锚点从**过滤后**的 `lastComparable` 算，而 `merged` 用**未过滤**的 `lastMsgs` ⇒ offset 额外取决于「缓存里有几条摘要消息」）⇒ 登记**范围扩大一条**，而不是记「无影响」。

- **「无影响」是三种状态里最容易被伪造的一种**：只要没去看就成立。⇒ 复核的证据形式是**行号 + 关键表达式**（`merged = lastMsgs ++ deltaTail` 仍在 `:145-147`；`msgHash` 仍返回 `h[:16]` 在 `:369-380`），不是「跑通了」。
- **顺带被改的门管辖范围内的生产文件，要复跑门**并核对**覆盖面自报数有没有变**（本轮 `admin/usage_enhanced.go` 是 29 个读端之一，合并后仍自报 29/33、门 3/3 PASS ⇒ 新代码未引入幻影列引用）。
- ⚠️ **别把合并后的第一次 `go test` 计时写进文档**：冷编译会让同一棵树从 31.2s 变成 2.3~3.1s。用 `-count=1` 绕开结果缓存、连测三次再写。
