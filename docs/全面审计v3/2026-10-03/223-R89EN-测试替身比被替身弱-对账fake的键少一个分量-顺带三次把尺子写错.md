## 三、净真缺陷（P3，待裁决 89）：对账的 fake 键比真实现的唯一键**少一个分量**

`domains/providerprofile/reconciliation_test.go` 的 `fakeReconciliationStore`：

```go

	records map[int64]*providerprofile.ReconciliationRecord // key: providerID   ← :41
	...
}
func (s *fakeReconciliationStore) SaveRecord(ctx, rec) error {
	s.records[rec.ProviderID] = rec        // ← :62  只按 providerID
}
func (s *fakeReconciliationStore) Get(ctx, providerID int64, month time.Time) (...) {
	if rec, ok := s.records[providerID]; ok {   // ← :67  **丢弃 month**
		return rec, nil
	}
}
func (s *fakeReconciliationStore) ListByMonth(ctx, month time.Time) (...) {
	for _, rec := range s.records {
		if rec.Month.Equal(month) {             // ← :76  **却按 month 过滤**
```

而**真实现**的唯一键是 `ON CONFLICT (provider_id, reconciliation_month)`
（`domains/providerprofile/pg_reconciliation_store.go:58` / `:94`）。

⇒ **同一个 fake 内部自相矛盾**：`SaveRecord`/`Get` 按 providerID 索引，
`ListByMonth` 却按 `rec.Month.Equal(month)` 过滤。
⇒ **全部测试只用单一 `month`**（`TestCostReconciler_ImportBill` 的 `month := 2026-07-01`），
⇒ 键里缺 month 这件事**从未被触发过**。

**负控实测**（跑完即回收，未留在仓库）：按 `providerID` 索引连续存 7 月与 8 月两条记录，
再 `Get(1, jul)` ⇒ 返回的是 **8 月那条**（`GatewayTotalCost = 200`，期望 100）
⇒ 两次 `SaveRecord` 互相覆盖，坐实。

### 定级 P3 而非 P1/P2 的三条理由

1. **真实现是对的** —— 缺的是测试替身的强度，**没有任何生产行为受影响**。
2. **本轮未找到任何依赖该性质的代码**：对账 worker 每次只处理单月
   （`CostReconciliationMonthsToAggregate` 返回当月+上月，逐月调用），
   现有逻辑不会在**同一进程内**跨月读写同一 provider。
3. **风险是"将来"** —— 任何人给对账加「按月重算 / 按月幂等」逻辑，都会在**假绿**下写完。

⇒ 修法是把 `map[int64]` 换成复合键 `map[recKey]`，`recKey struct{providerID int64; month time.Time}`。
**⚠️ 属测试夹具重构**（会让既有断言的形态变化）⇒ 本代理不擅自动手。

## 四、守卫：`internal/billguard` 新增 `TestStoreKeyParitySurfaceCoverage`

判据的方向是**"替身不得弱于被替身"**，两侧都读：

| 侧 | 读什么 | 权威性 |
|---|---|---|
| 权威侧 | 真实现里 `ON CONFLICT (...)` 的列（`pg_reconciliation_store.go:94` 往后 20 行） | **权威** |
| 替身侧 | fake 结构体里 `map[...]` 键 + 行尾 `// key:` 注释声明的列 | 事实 |

**双向检查**：
- 权威侧的键若变了（比登记表多/少一列）⇒ 报「权威已改、登记表没跟上」（**不报成被测代码有缺陷**）；
- 替身侧若缺列 ⇒ 报「替身比被替身弱」。

**豁免是显式且可自我失效的**（承 §172）：`knownMissing: []string{"reconciliation_month"}`，
缺陷用 **`t.Log`** 打印进 CI 输出而非静默 `continue`。
一旦有人把 fake 的键补齐 ⇒ `containsFold` 成立 ⇒ **根本进不到豁免分支** ⇒ 豁免自动失效。

⚠️ **为什么不让门一直红**：一个红的门会让 `make guards` 永久失败，
于是**所有**守卫（含已修好的）都变成"没人敢看"的红。
⇒ 本审计的取舍是 **登记 + 豁免 + 打印**，而不是 **留着红**。

## 五、⚠️ 本轮我把三把尺子写错了 —— 都记进 playbook

这三次全部是**同一个形态**：尺子坏了，而尺子坏了之后的输出**看起来仍然像一个结论**。

### 尺子 1：Go 参数简写的解析（最隐蔽）

```go
func (s *fakeStore) GetSession(_ context.Context, tenantID, sessionID string)
```

我按"每个逗号片段取最后一个标识符当参数名"解析：

```
"tenantID"         → name="tenantID"   ✓
"sessionID string" → name="string"     ✗ 错！真正的参数名是 sessionID
```

⇒ **带类型的参数名被判成了它的类型**，而类型名在方法体里通常不出现
⇒ **系统性高报**。
⇒ 修法：按 Go 语法把参数列表切成"参数组"—— 裸片段先暂存，
遇到带类型的片段时回填给所有待定名字（`a, b string` ⇒ a、b 都是 `string`）。

⚠️ **判别式**：`a, b T` 形态下，**只有最后一个片段带类型**。
任何"取最后一个 token"式的解析在混合参数列表上必错。

### 尺子 2：调用点统计的方法名撞车

按 `.Set(` / `.Get(` 统计全仓调用点，得到 **`calls=2302 files=576`** ——
这个数字大到没有任何信息量（`.Set(` 在本仓到处都是）。
⇒ 与 222 号 §172 同一个信号：**数字大得离谱时，先怀疑尺子。**
⇒ 修法：限定接收者类型，只在"出现过该类型名"的文件里数方法调用 ⇒ **160 → 22**。

### 尺子 3：注释是**唯一的语义来源**（这条最有价值）

`reconciliation_test.go:41` 的 map 键类型是 `int64`（**零信息**），
列名 `providerID` **只写在行尾注释**里：

```go
records map[int64]*providerprofile.ReconciliationRecord // key: providerID
```

判据若只看 `map[...]` 的类型下标 ⇒ 得到 `int64` ⇒ 按"类型名不是列名"丢弃
⇒ 产出空列表 ⇒ 门以"缺两列"的红脸出现，**而真因是判据看不见注释**。

⇒ **这与本审计「注释不是契约」不矛盾**，但它给那条纪律划出了边界：
  - 「不能把注释当契约去信」—— 对**代码形态已表达意图**的情形；
  - **「当代码形态本身不含信息时，注释不是"不可信的契约"，而是"唯一的记录"」** ——
    对**代码形态零信息**的情形（`map[int64]` + 注释说键是什么）。
⇒ 判别式：**先问"这段代码本身能不能表达这个意图"。能 ⇒ 别依赖注释；
不能 ⇒ 注释是唯一可读语义，必须读。**

### 附带一条：跨语言的名字映射会制造假阳性

权威侧是 SQL 列名 `provider_id`，替身侧是 Go 名 `providerID`。
朴素的 `snake→camel` 给出 `providerId`，而 Go 惯例（lint 的 initialism 规则）是 `providerID`
⇒ **已覆盖的那一列被判成"缺"**。
⇒ 修法：按 Go official initialism 名单（`id`/`url`/`api`/`ttl`/`uuid`…）全大写，
**且比较时大小写不敏感**，避免"写法不同但语义相同"再变成一类假阳性。

## 八、playbook §173–§175

**§173 一个数字大到可以直接发 P1，是危险信号，不是发 P1 的理由。**

223 号第一版量到"全仓 641 个测试替身方法丢弃参数、175 个文件"，
第二版量到"138 个作用域参数被丢弃、55 个文件"。
两个数字都**大到足够发一条 P1**。实际是：641 里绝大多数是**该层根本没被测**（哑替身对任何输入返回同一值），
138 那个口径**已被 101 号 P1（待裁决 43）覆盖**，逐条复核后**净真缺陷 1 条**。

⇒ **数字只回答"有多少"，不回答"是什么"。** 收缩过程本身才是发现。
⇒ 判别式：**见到一个足以发 P1 的统计量，先花三轮把它收窄**：
  ① 加语义分类（哪些参数类别会影响结果）→ ② 加"这个替身真被调用过吗" → ③ 逐条人工复核。
⇒ 补一条可推广的量：**本轮 20 条里 4 条是误报（20%）**。
  这个比例意味着**未经人工复核直接采信扫描器，会产出 4 条假缺陷** ——
  而假缺陷的成本（本审计的 §"一道会误报正确代码的门比没有门更坏"）高于漏报。

**§174 写扫描器/判据时，三类解析错误会系统性高报，且输出看起来仍然像一个结论。**

223 号三把尺子各错一次，**三次的输出都长得像结论**：

1. **Go 参数简写**：`func(a, b string)` 里**只有最后一个片段带类型**。
   "取最后一个 token 当参数名"会把 `b` 解析成 `string`（它的类型）而不是参数名
   ⇒ 类型名在方法体里通常不出现 ⇒ **每一条都报"丢弃参数"**。
   修法：裸片段暂存，遇到带类型片段时回填给全部待定名字。
2. **调用点统计的方法名撞车**：`.Set(` / `.Get(` 在本仓到处都是
   ⇒ 报出 `calls=2302 files=576` 这种**大到零信息量**的数字。
   修法：限定接收者类型（只在出现过该类型名的文件里数）⇒ 160 → 22。
3. **跨语言名字映射**：`provider_id` → 朴素 camel 得 `providerId`，
   而 Go 惯例是 `providerID`（lint initialism 名单）⇒ **已覆盖的列被判成"缺"**。
   修法：按 official initialism 名单全大写 + **比较时大小写不敏感**。

⇒ **共通判别式**：**当输出数字大得离谱、或红绿"整齐"到不像真的，先怀疑尺子。**
  与 §172「门变快和门变绿一样是尺子出错的信号」同源 ——
  **尺子坏了之后的输出不会自我暴露，它会看起来像一个结论。**

**§175 「注释不是契约」这条纪律有边界：代码形态零信息时，注释是唯一的记录。**

`records map[int64]*ReconciliationRecord // key: providerID`
—— 键的**类型是 `int64`（零信息）**，列名**只存在于行尾注释**。
判据只看 `map[...]` 的类型下标 ⇒ 产出空列表 ⇒ 门以"缺两列"红，
**而真因是判据看不见注释**。

⇒ 纪律的两半：
  - **代码形态已表达意图**（如 `ON CONFLICT (provider_id, reconciliation_month)`）
    ⇒ 以代码为准，注释可能过期（本审计 219 号 F2 的教训）；
  - **代码形态本身不含信息**（`map[int64]` + 注释说明键是什么）
    ⇒ **注释是唯一可读语义，必须读**。
⇒ 判别式：**先问"这段代码本身能不能表达这个意图"。能 ⇒ 别依赖注释；不能 ⇒ 注释是唯一记录。**
⇒ 与 216 号"注释钉桩的内容会在写下时就与在盘结论矛盾"合看：
  **注释既不能当契约（会与代码矛盾），也不能当不存在（可能是唯一信息源）——
  要问的是"这段意图在代码形态里有没有别的载体"。**
