## 四、⚠️ 本轮真正的 P2：诊断端点污染决策审计统计

### 现象（近 30 天，`admin/analytics.go` 路由漏斗 7 个指标）

| 指标 | 现状（含 probe） | 真实流量 | probe 贡献 |
|---|---|---|---|
| rows | 932,706 | 920,734 | 11,972（1.28%） |
| `traceRows` | 27,237 | 15,265 | +11,972 |
| **`totalPlanned`** | **196,627** | **44,227** | **+152,400（虚高 4.45 倍）** |
| **`totalBlocked`** | **129,353** | **0** | **129,353（真实流量这一格是 0）** |
| `routable` | 67,274 | 44,227 | +23,047（+52%） |
| `success` | 310,680 | 300,944 | +9,736 |

**最刺眼的一格是 `totalBlocked`：129,353 里真实流量贡献 0，全部来自诊断探针。**
⇒ 漏斗图上「被阻断的候选」这一级，**反映的完全是运维自己点诊断接口的次数**。

### 根因：那个本该排除 probe 的反连接是 **no-op**

`admin/analytics.go:1006-1011` 确实写了排除逻辑：
```sql
AND NOT EXISTS (
  SELECT 1 FROM routing_analytics_source probe
  WHERE probe.request_id = routing_decision_log.request_id::text
    AND NOT (businessRequestFilter("probe"))
)
```
`businessRequestFilter`（`:173-181`）把 `request_id LIKE 'probe-%'` / `task_type='probe_triggered'` /
特定 `origin_stage` 视为非业务流量。

**但 `resolve_probe` 行两头都不沾**：
1. `request_id` 是 `uuid.New()`，**不带 `probe-` 前缀**；
2. **它从不写入 `routing_analytics_source`** ——
   实测 **11,972 条 probe 行在该旁表里 0 条命中**
   ⇒ 子查询永远返回空 ⇒ `NOT EXISTS` 恒为真 ⇒ **每一条 probe 行都被放行**。

**⇒ 排除逻辑存在、语法正确、语义合理，但对这个唯一的 probe 来源完全无效。**
**修法方向（待裁决，不擅自动手）**：
① **最小**：在漏斗查询里加 `AND resolution_path IS DISTINCT FROM 'resolve_probe'`（一条件）；
② **更好**：让 `routing_resolve_probe.go` 写入时**自带可识别标记**
   （`request_id` 用 `probe-` 前缀，或 `task_type='probe_triggered'`）⇒ 复用既有约定，不必特判；
   ⚠️ ② 会改变已有历史行的匹配口径（历史行改不了），所以 ① 仍应保留。

## 五、⚠️ 方法论：我这一轮**两次**踩了同一个 SQL 三值逻辑坑

这两次都产出了**干净、自洽、错误**的数字，是本轮最值得记的部分。

### 坑 1：`resolution_path <> 'resolve_probe'`

我第一次算「排除 probe 后」时用了 `<>`。**`resolution_path IS NULL` 的行（579,028 行 = 62%!）
会被 `<>` 整行丢掉**（三值逻辑：`NULL <> 'x'` → NULL → 不满足 WHERE）。

⇒ 我一度算出「**63.4% 的请求是诊断探针**」——**这个数字是假的**，
真实 probe 占比 **1.28%**。
⚠️ 若我直接发出「63.4% 的流量是探针」，那是一条**量级错 50 倍**的 P1。

### 坑 2：`resolution_path = 'resolve_probe'` + `NOT is_probe OR is_probe`

改用 `IS NOT DISTINCT FROM` 之后，我在 CTE 里写 `NOT is_probe OR is_probe`
想表示「全部」，**但 `is_probe` 对 NULL 行是 NULL** ⇒ `NULL OR NULL` = NULL ⇒ **又被过滤掉 579,028 行**。

⇒ `requests_含probe` 一度显示 **353,678**，真值 **932,706**。

### 正确的写法

```sql
-- ✅ NULL 安全
WHERE resolution_path IS DISTINCT FROM 'resolve_probe'
-- 或
WHERE (resolution_path IS DISTINCT FROM 'resolve_probe') IS TRUE
```
⚠️ **只要 WHERE 条件里出现 `col = 'x'` / `col <> 'x'` 与可空列组合，就必须先问「NULL 行去哪了」。**

### playbook §36 新增（本轮）

> **聚合类数字必须先问「NULL 行去哪了」。**
> `col = 'x'` / `col <> 'x'` 遇到可空列会产生 `NULL`（三值逻辑），
> 它在 `WHERE` 里等价于「不匹配」——
> **于是一个占 62% 的 NULL 群体可以在你眼皮底下整块消失，而输出仍然是一个干净的整数。**
>
> **落地**：
> ① 排除某类行用 `IS DISTINCT FROM`（或 `IS NOT DISTINCT FROM`），**不用 `<>` / `=`**；
> ② **报「占比」之前，先单独打一次 `count(*) FILTER (WHERE col IS NULL)`** ——
>    **NULL 占比大到能改变结论时（≥1% 就该警惕），两种口径的差值必须写进报告**；
> ③ **自查问句**：「我这个过滤条件，会不会是靠 NULL 的三值逻辑在悄悄筛掉数据？」
>    会 ⇒ 换写法；
> ④ **与 §34 同族** —— §34 是「属性可能靠数据库默认」，
>    本条是「**集合可能靠三值逻辑少算**」。**共同点：都是「你以为你在量 A，其实你在量 A 减去某个隐式子集」。**
