## 三、⚠️ 机制实证（不靠推测）

`handoff_logs_hot` 不做月分桶，函数体里与时间有关的只有一处：
```sql
WHERE created_at < now() - p_retention
```
`created_at` 是 `timestamp without time zone`，`now()` 是 `timestamptz`
⇒ PG **按会话 `TimeZone` 把前者解释成后者**。用合成值直接证明：

```sql
SET TIME ZONE 'Asia/Shanghai';
SELECT (TIMESTAMP '2026-10-01 02:00:00' < now() - interval '8 hours');
-- TRUE   ← 判为「已超 8 小时」
SET TIME ZONE 'UTC';
SELECT (TIMESTAMP '2026-10-01 02:00:00' < now() - interval '8 hours');
-- FALSE  ← 同一个值，判为「还没到 8 小时」
```

**⇒ 保留期判定确实随会话时区改变。今天 Asia/Shanghai ⇒ 正确。**

⚠️ **这正是 140 号当初「如实登记不报缺陷」的正确之处**：
**机制是真的、后果今天不存在** —— 两件事同时成立，且必须分开说。

## 四、修法方向（待裁决 59，不擅自动手）

**核心不是「给 9 个函数补一行」，而是「让时区不再依赖任何人的环境配置」。** 三个层次：

1. **最小（一词/一行级）**：给 9 个缺失函数补 `SET LOCAL TIME ZONE 'Asia/Shanghai';`
   —— 与已有 11 个对齐。**成本极低，但要逐个确认暴露面**（本轮只坐实 2 个）。
2. **更稳（治本）**：在 `cmd/gateway` 的连接池初始化处统一设 `TimeZone`
   （`SET TIME ZONE 'Asia/Shanghai'` 或 DSN 参数）⇒ **一处生效，所有 SQL 都对**，
   不再依赖「某个函数记得写」。
   ⚠️ **本轮已证 Go 侧目前零兜底**（`SET TIME ZONE` / `TimeZone=` 0 命中）⇒ **这是最大的缺口**。
3. **配套**：把「promote/归档类 SQL 的月分桶必须在固定时区下计算」写进 playbook 与新迁移注释，
   **并考虑加一条守卫**：扫描 `pg_proc` 里 `date_trunc('month', …)` 的函数，
   断言其定义包含 `SET LOCAL TIME ZONE`（与待裁决 58 的守卫测试同思路，**报告而非 fail**）。

⚠️ **诚实风险提示**：方案 2 改连接池时区属于**全局行为变更**，
可能影响其它依赖会话时区的 SQL ⇒ **需产品/运维确认后再动，本代理不擅自动手。**

## 五、playbook §38 新增

> **「时区正确」不是「代码里写了 `SET LOCAL TIME ZONE`」，而是「时区不依赖任何人的环境配置」。**
>
> **要问的三个问题**：
> ① **函数里设了没有？**（本仓 11/20 —— **看覆盖率，不看有没有**）
> ② **没设的那些，函数体里到底有没有时间敏感运算？**（`date_trunc('month')` / `timestamp` × `timestamptz` 混比）
> ③ **上层有没有兜底？**（本仓 **Go 侧零兜底** ⇒ 答案是否 ⇒ **时区完全由容器决定**）
>
> **配套**：
> - **潜伏风险要按「今天/换环境」两栏写**：
>   「机制成立」与「今天不发生」**必须同时报**，只报其一就是误导（140 号的处理是对的）。
> - **补齐硬化时要逐个看函数体**，不能按名字批量补 —— 本轮 9 个里只有 2 个真有暴露面。
> - **合成值可以直接证明机制**，不必等表里有数据（本轮用 `TIMESTAMP '…'` 就把漂移演示出来了）——
>   **「该表零行所以无法验证」不是不验证的理由**（与 §31、§36 同源：
>   **别让「没有数据」把「可以验证的东西」一并挡掉**）。
