## 1. 钉的是什么语义

`safeWindowSource`（`hook.go:471-490`）与它的三个兄弟**语义不同**：

| 函数 | 策略 |
|---|---|
| `safeAlignmentRecords` / `safeSanitizeRefs` / `safeCutMarkerMeta` | **all-or-nothing**（任一条不合法 ⇒ 整段 `return nil`） |
| **`safeWindowSource`** | **逐条过滤**（坏 label `continue`、坏 count 跳过该条，其余照常保留） |

**为什么这条差异值得单独钉**：它不是实现细节，是**语义**。如果哪天有人为了「和兄弟们保持一致」把 `continue` 改成 `return nil`，**一条坏 label 就会让整份来源构成遥测消失**，而遥测丢失是**静默**的——D03 §3 第 4 条要求「窗口遥测能区分内容来源层，**指标不串层**」，反过来「**指标全没了**」同样违约，且没有任何门会红。

⇒ 测试的主断言就是这条：坏条目放在**中间**（不是末尾），确保实现不是「遇到坏的就整体放弃」。

## 2. 其余钉住的边界

| 边界 | 语义 | 反向对照 |
|---|---|---|
| 非 map 输入 / 空 map | 整段 nil | — |
| 全部条目非法 | 整段 nil（`len(out)==0`） | — |
| **>16 个标签** | **整段丢弃**，不是截断到 16 | 恰好 16 个必须全量放行 |
| label 长度 | ≤24 字符 | 24 放行 / 25 丢弃 |
| label 字符集 | 仅 `[a-z0-9_-]` | 大写、空格、空串均被拒 |
| count | `0 <= n <= 2^53` 且为整数 | 负数、小数、字符串、bool、nil 被拒；`0` 与 `2^53` 放行 |

「超 16 整段丢而非截断」单独钉住的理由：截断会让调用方**误以为拿到的是全量构成**。

## 3. 测试数据取自真库实证

- `request_logs`（215 万行）中 `window_source` 出现 **43,787 行**，实测键只有两个：`retained` 43,787 / `summary` 43,787；
- 生产常量（`domains/hooks/compression/alignment_reverse.go:140-142`）`retained` / `summary` / `dropped` **全为小写、≤8 字符** ⇒ 天然满足 `boundedCompressionWord` 的小写 + `[0-9_-]` + ≤24 字符约束。

⇒ **producer 与 filter 之间不存在大小写/长度错配**，测试的「真库形态」对照组据此写成 `{"retained": 12, "summary": 3}`。

## 4. 我自己写错了一处测试（记录）

初版边界用例写了 `{"超过 2^53", float64(1<<53 + 1), false}`，**跑出来是绿的**——查原因是 `1<<53 + 1` 在 Go 里是**无类型整数常量**，转 `float64` 时被**舍入回 2^53 本身**，等于合法上界，压根测不到「超界」。

⇒ 改为 `float64(1<<53) + 1024`（真正可表示为 >2^53 且落在 int64 内的整数值），并在该行留注释说明**为什么不能用前者**。

**这是「测试写错、代码是对的」的镜像情形**——平时我警惕的是「工具/注释说错了」，这里是我自己的断言先错了。**没有把代码改成迎合我的错误断言。**

| # | 变异 | 期望 | 实际 |
