## 0. 一句话回答

**这一轮最重要的产出不是「发现了现网死锁」，而是「用可复现的实验把一个静态锁序警告，精确切成了『构造上真实 / 运行上不可达』两半」。**
子代理报的是 ABBA 死锁；我复现了死锁（同一 qr 双向入道 ⇒ 两条路径双双卡死 3 秒），
但同时证明了反向对照（不同 qr ⇒ 0.31 秒双双返回），从而把「同 qr」钉成必要条件；
再穷举全部调用点证明生产流水线**从不**让同一 qr 同时走两条路径 ⇒ 结论从 P1 降为 P2 潜在缺陷。

这个「先证锁序反转真实存在，再证其前置条件在生产中不成立」的双向做法，
比直接采信静态扫描的「高危死锁」或直接排除都更有价值。

## 第二部分：查出 P2 —— `domains/dispatch` 两条入道路径的锁序反转（ABBA）

### 2.1 事实：两条路径的加锁顺序确实相反

| 路径 | 函数 | 顺序 |
|---|---|---|
| **A** | `enqueueModelLane`（模型泳道重入道） | `pipeline.go:1490` `qr.journeyMu.Lock()` → `pipeline.go:1492` `mq.mu.Lock()` |
| **B** | `enqueueModelFromTotalLane`（总队列首次入道） | `pipeline.go:1311` `mq.mu.Lock()` → `pipeline.go:1336` `qr.emitObservation(...)` |

路径 B 的 `emitObservation` 内部第一件事就是取 `qr.journeyMu`
（`journey.go:36`，`defer` 在 `:37` 释放）。

**⇒ 顺序为 `journeyMu → mq.mu`（A）与 `mq.mu → journeyMu`（B），构成教科书式 ABBA。**

关键结构事实（决定了 ABBA 能否成环）：

- `journeyMu` 是 **per-request** 字段（`queued_request.go:194`，`QueuedRequest` 结构体内）；
- `mq.mu` 是 **per-lane** 字段（`snapshot.go:13`，`modelQueue` 结构体内）。

**⇒ 两个不同的 qr 持有不同的 `journeyMu`，不会相互阻塞。**
ABBA 成环的**必要条件**是：两条路径必须作用在**同一个 `qr`** 上。

### 2.2 实证：用生产函数本体确定性复现死锁

我没有复刻实现，而是在 `domains/dispatch` 包内写临时测试**直接调用生产的
`enqueueModelFromTotalLane` / `enqueueModelLane`**，用一个**合法的扩展点**
（`Deps.QueueObservationSink`）把路径 B 卡在 `pipeline.go:1327` 的
`observeQueue` 调用点 —— 该点位于 `mq.mu` 临界区内、`:1336` 的 `emitObservation` 之前。
于是交错完全确定：

```
G1: enqueueModelFromTotalLane(m, qr)  → 持 mq.mu，卡在 sink
G2: enqueueModelLane(mq, m, qr)       → 持 qr.journeyMu，阻塞在 mq.mu.Lock()
放行 G1                                → G1 走到 :1336，阻塞在 qr.journeyMu.Lock()
                                    ⇒ 成环
```

| 变异 | 条件 | 实测 | 判定 |
|---|---|---|---|
| **M1** | **同一个 `qr`** | `deadlocked=true, g1done=false, g2done=false`（双双卡满 3s） | ✅ **ABBA 死锁真实可复现** |
| **M2**（反向对照） | 两个**不同** `qr` | `deadlocked=false, g1done=true, g2done=true`（0.31s 双双返回） | ✅ 证明「同 qr」是必要条件，且 gate 与超时判定本身有效 |

> **M2 是这份报告里最重要的一行。** 没有它，M1 的「死锁」无法与「我的 harness
> 本身有问题」区分开 —— 第一次运行时 M1 确实「没死锁」，但耗时 0.00s，
> 原因是 harness 缺了等待（`go` 之后立刻读标志位）。若不做反向对照，
> 我会把**harness 的 bug** 读成**「锁序反转不存在」**，得出完全相反的结论。
> 这正是 playbook §9.4「必须带反向对照」的一个实例。

临时测试跑完即删（它是取证工具不是门；留着会变成「修复前必红」的红门）。

### 2.3 可达性穷举：生产流水线**从不**让同一 qr 同时走两条路径

穷举两条路径的**全部**调用点（不是抽样）：

```
路径 B: enqueueModelFromTotalLane ← enqueueModelFromTotal ← drainTotalOne (pipeline.go:1224)
                                               ← runTotalDrainer 的 per-item goroutine (pipeline.go:1188)
                                               ← onScheduledDue (pipeline.go:1450 totalQueue.tryEnqueue)
路径 A: enqueueModelLane          ← enqueueModel ← dispatcher.go:277（模型回退重入道）
```

三条生产者恰好落在 qr 生命周期的**三个互不重叠的所有权阶段**：

1. `Submit` → `totalQueue.tryEnqueue` → per-item goroutine → **路径 B**（qr 尚未进过任何泳道）
2. `onScheduledDue`（定时到期）→ `totalQueue.tryEnqueue` → per-item goroutine → **路径 B**
   （`pipeline.go:1444-1449` 明确记录这是「第二次入队」，且第一次的 goroutine 早已返回）
3. `dispatcher.go:277` → **路径 A**（qr 已被 `runModelDrainer:1618` 从 `mq.ch` 弹出，
   已经历 lane → `dispatchIn` → dispatcher，此刻**不在任何泳道里**）

`QueuedRequest` 全程是**单所有权移动**（queue → lane → dispatchIn → dispatcher），
不存在任何一处把同一个 qr 同时交给两个 goroutine。

**⇒ 结论：锁序反转在构造上真实存在（§2.2 已实证），但其前置条件在当前生产流水线中不成立。**
定为 **P2 潜在缺陷（latent）**，不是 P1。

### 2.4 为什么仍然要登记（不能因为不可达就放过）

这是一个**只差一行调用点就会变成 P1 全局死锁**的构造。任何后续改动只要引入
「同一 qr 并行入道」——例如给回退加并行重试、给定时请求加提前触发、
或让 `dispatcher.go:277` 与总队列 drainer 共享一个 qr —— 立刻变成
**持锁 goroutine 永久阻塞 ⇒ 该 model lane 的所有请求无限排队**。
死锁一旦发生，Go 的 `fatal error: all goroutines are asleep` 只在**全局**无 runnable
goroutine 时才触发；网关有大量常驻 goroutine，因此实际表现是**该泳道静默饿死**，
比 panic 更难排查。

### 2.5 建议修法（登记为 **待裁决 41**，本轮不动代码）

**方案：让路径 B 对齐路径 A 的锁序**（改 1 处、加 2 个 Unlock，风险最低）。

在 `enqueueModelFromTotalLane` 的 `mq.mu.Lock()`（`:1311`）**之前**先取 `qr.journeyMu`，
并把 `:1336` 的 `qr.emitObservation` 换成 `qr.emitObservationLocked`，
在**所有**返回路径上按 `mq.mu → journeyMu` 的逆序解锁：

```go
// :1311 之前
qr.journeyMu.Lock()
mq.mu.Lock()
// ... 其余逻辑不变，把 :1336 的 qr.emitObservation(...) 改为
//     qr.emitObservationLocked(Observation{...})
// 每个 return 前： mq.mu.Unlock(); qr.journeyMu.Unlock()
```

顺带收益：路径 A 用 `OccurredAt: enqueuedAt`（锁前采样，`:1491`），
路径 B 目前让 `emitObservation` 内部取 `time.Now()`（`journey.go:59`）。
对齐后两条路径的时间戳语义一致。

**明确不推荐**的替代方案：把路径 A 的 `emitObservationLocked` 移出临界区、
改为锁后发送 —— 那会削弱 §2.1 中 `emitObservation` 注释所承诺的
「严格 per-request 顺序」（流式首字节与转发 goroutine 并发上报时），
属于用并发正确性换锁序，不划算。

> 本轮**不擅自改动**：dispatch 入队是网关最热的路径，且 40 条待裁决尚未收口，
> 登记后由产品/运维统一决定排期。

## 第三部分：子代理线索的复核结论（3 排除 / 1 确认）

### 3.1 关于扫描器本身的方法论登记

子代理自述其 AST 扫描器「阴性结论不可视为穷尽证明」。我**同意并采纳**：
本仓已有的先例是 `codegraph` 的死代码/可达性判定在本仓系统性假阴性
（playbook §12），而 `golangci-lint` v2 静默接受拼错的配置键（§11.1）。
**扫描器的阴性结论在本仓一律需要第二种检索方式复核。**
本报告的可达性结论因此不依赖扫描器，而依赖 §2.3 的**调用点穷举**。

### 3.2 排除项（附排除理由，避免下一个人重跑整轮取证）

| 线索 | 复核结论 | 排除理由 |
|---|---|---|
| `tool_registry.go:156` check-then-act 写侧是否持锁 | **排除，非缺陷** | 这是**正确的 copy-on-write**：`newCache` 在锁外由 DB 结果集完整构建（`:131-149`），锁内只做一次 `tr.cache = newCache` 原子交换（`:155-157`）。无 check-then-act 窗口、无丢失更新、无撕裂状态。`&tool` 取址安全（`:133` `var tool Tool` 是循环体内声明，每轮独立地址）。 |
| `flusher.go:205` `go f.Flush()` 无界扇出 | **排除，非泄漏** | `Flush`（`:76-105`）在 `f.mu` 内**快照并清空** `dirty` map 后立即释放锁，再在锁外做 DB I/O，失败时回填。因 map 被立即清空，`len(f.dirty) >= batchSize` 的窗口极短，扇出被并发 `MarkDirty` 调用数天然收敛；多余的 `Flush` goroutine 立刻命中 `len==0` 早返回（`:78-81`）。属**有界冗余扇出**。 |
| `tryEnqueueCred` 三级锁 / `proxy/manager.go` per-key 锁 / `live_stream_sse.go` / `node_probe.go` 锁序 | **排除** | 逐条读包围函数后均为**单向嵌套**（A→B→C，无回边），不构成环。 |

### 3.3 顺带核实：另一处嵌套锁序

`pipeline.go:2087-2088` 存在第三组嵌套：`qr.journeyMu.Lock()` → `cf.handoffMu.Lock()`。
这是**单向**的（`:2120-2121`、`:2124-2125` 均按逆序 `handoffMu` → `journeyMu` 释放），
全仓 `handoffMu` 无反向获取点，**不构成环**。登记在此以免后续扫描重复告警。
