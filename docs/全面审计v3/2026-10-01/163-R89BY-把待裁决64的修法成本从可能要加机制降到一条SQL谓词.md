# 163 / R89-BY：把待裁决 64 的修法成本从「可能要加机制」降到「一条 SQL 谓词」

> 日期：2026-10-01
> 目的：让 158–162 号那条**只差产品一句话**的待裁决 64，**在拍板前就知道实现成本有多低**。
> 结论：**「最后引用时间」这个数据现在就有 ⇒ 修法不需要新埋点、不需要迁移、不需要加列。**
> 定级：**不新增待裁决；本轮是把 64 号的修法成本量化。** **未改动任何生产代码或数据库。**

---

## 一、待裁决 64 卡在哪

158 号给出的三条建议修法：

1. 给 `OlderThanDays` 加数据下界；
2. **删除前把候选 `storage_path` 与引用表求差集，只删真无引用的**；
3. 补守护测试。

而它同时留了一句产品前置：**「附件保留期以『最后引用时间』还是『首次写入时间』为准？」**

⚠️ **在产品回答之前，我无法确定修法 2 到底需不需要新建机制** ——
如果「最后引用时间」这个数据不存在，那修法 2 就不是「改一条谓词」，而是「先加一套引用追踪」，
**成本差一个量级**。这会直接影响你拍板时的判断。

**本轮就去把这个问题问掉。**

---

## 二、结论一：`storage_path` 与磁盘相对路径**同形，可直接 join**

真库实测样例：

```
2026/09/50/59/5059ce083d40afb2d8312593bff5809f506eecb064c5d2aa2edf3b02a446cf8f.jpg
2026/09/c4/14/c414cd0e204de974f73753c7e28d7638e7b3691bb8b1a2bab6b25bb7fed7ce77.png
```

而 `domains/attachments/storage_backend.go:15` 声明的布局是：

```
{BaseDir}/YYYY/MM/{hash[0:2]}/{hash[2:4]}/{hash}{ext}
```

⇒ **逐段吻合（月份 / hash 前 2 位 / 后 2 位 / 全 hash + 扩展名）。**

⚠️ 并且 `storage_path` 列**零 NULL**（10,652 行实测 `null_path_rows = 0`）。

⇒ **清理端点遍历出来的相对路径，可以直接 `IN (…)` 或 `JOIN` 引用表，不需要任何路径规整或哈希反解。**

---

## 三、结论二：「最后引用时间」**现在就能算出来**

一条 SQL 即可：

```sql
SELECT storage_path, MAX(created_at) AS last_ref
FROM request_attachments
WHERE storage_path IS NOT NULL
GROUP BY storage_path;
```

真库实测：

| 指标 | 数值 |
|---|---|
| 去重后的 blob 数 | **80** |
| **引用跨度 > 1 天的 blob** | **2** |

⇒ **数据已在库里，不需要新增列、不需要新增埋点、不需要迁移。**

⚠️ **而那个「2」正是修法必要性的实证**：
161/162 号已确认 `OlderThanDays` 只挡 `<= 0`（**管理员可以传 1**）。
**若管理员传 `1`，这 2 份 blob 恰好就是会被误删的那 2 份**（其中一个跨度 14 天）。

## 四、对拍板的影响（把三件事摊开说）

| | 如果产品答「以最后引用时间为准」 | 如果产品答「以首次写入时间为准」 |
|---|---|---|
| 修法 1（加数据下界） | 下界可取 `MAX(MAX(created_at))`（当前 14 天） | 下界无意义，只能写死约定 |
| 修法 2（引用差集） | **一条 SQL 谓词即可**（数据现成） | 不适用 |
| 修法 3（守护测试） | 仿 `cleanup_wiring_test.go` 形态 | 断言 `OlderThanDays` 有下界 |
| **需要新埋点吗** | **不需要** | **需要**（要额外记录 blob 的首次/末次写入） |
| **需要迁移吗** | **不需要** | **不需要**（blob 的 mtime 本身就是首次写入） |

⚠️ **注意第二列有一个反直觉之处**：
「以首次写入时间为准」**表面上更简单**（直接用 mtime，现成的），
但那恰恰是 158 号指出的**缺陷本身**——它与内容寻址去重**在语义上就是矛盾的**
（去重让「一份文件」与「N 个引用者」脱钩，而 mtime 只有一个值）。
⇒ **换句话说：产品若答「首次写入时间为准」，等于选择保留这个已知缺陷，
应当被显式记录为「已接受的取舍」，而不是当作已解决。**

## 五、诚实边界

- **未改动任何生产代码或数据库**（真库只跑 SELECT，临时 SQL 已删）。
- ⚠️ **`storage_path` 与磁盘路径同形，是在本库抽样 3 行上核对的**；
  **未逐行核对全部 80 份**，也**未与远端实例的真实文件树求差集**（本机 `data/attachments` 为空）。
  ⇒ **「可直接 join」是结构级结论，不是逐条实测结论。**
- ⚠️ **未核 `request_attachments` 是否会长期保留**：
  若行侧将来被 `DeleteOlderThan` 清理（它是零调用方，见 R87-j-1），
  **引用数据会先于文件消失** ⇒ **修法 2 依赖「行表比文件活得久」这个前提**。
  ⚠️ **该前提本轮未验证**（行最老 2026-09-07，文件保留期未知），
  **但它恰好说明为什么修法 1（加下界）与修法 2（引用差集）应该一起做** ——
  只做 2 而不做 1，等于把「误删」换成了「漏删」。
