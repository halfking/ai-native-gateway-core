## 1. 已修

### 1.1 模型泳道触顶 → 未路由的请求报成功 【P0】

**位置**：`domains/dispatch/pipeline.go:1213-1221`（`drainTotalOne`）

**事实**：`enqueueModelFromTotal` 失败有两条互不相干的路径，`getOrCreateModelQueue`（`pipeline.go:1529-1535`）在 `MaxModelLanes` 触顶时返回 `nil`，在 shutdown 时也返回 `nil`。旧代码把二者一并翻译成 `ctxOf(qr).Err()`：

```go
p.complete(qr, ForwardOutcome{Err: ctxOf(qr).Err()})
```

`ctxOf(qr).Err()` 在调用方上下文仍存活时**是 `nil`**。于是 `complete()` 收到 `Err == nil` 的 `ForwardOutcome`，`Submit` 走 `return out.Result, out.Err` 返回 `(nil, nil)`。

**影响比「返回错值」更广**：

1. 客户端收到 200 但无内容——容量拒绝被伪装成正常空响应；
2. `terminalActionOf`（`journal.go:162-164`）对 `Err == nil` 返回 `NextActionCompleted`，所以这个请求的执行轨迹里写的是「成功完成」；
3. `complete()` 内的 `terminalKind` 为空、stage metrics / waterfall 采样全部按成功记录。

即：**一个从未到达任何 provider 的请求，在 journal 与监控里是一次成功的执行。**

**触发条件**：`MaxModelLanes` 达上限且请求使用新模型名。`clampInt` 允许配到 16（`config.go:149`）；`ModelLaneIdleSeconds=0` 关闭回收时必然发生。

**修法**：先解上下文，再判泳道。上下文真的结束了就报它的错（这是真实原因）；否则这是准入拒绝，必须用与其它背压路径同口径的显式 `OverflowError`：

```go
if ctxErr := ctxOf(qr).Err(); ctxErr != nil {
    p.complete(qr, ForwardOutcome{Err: ctxErr})
    return
}
p.observeOverflow("model_lane_unavailable")
p.complete(qr, ForwardOutcome{Err: &OverflowError{
    Reason:     "model_lane_unavailable",
    RetryAfter: DefaultOverflowRetryAfter,
}})
```

**变异验证**：退回 `ctxOf(qr).Err()` 一行后 `TestR73_ModelLaneCapRejectsInsteadOfReportingSuccess` 红，报 `err=nil res=<nil>`——正是缺陷本体。

### 1.2 快照状态 gauge 跨凭据互相清零 【P1】

**位置**：`domains/dispatch/governor_metrics.go:223-226`（标签集）、`:288-294`（"1 for current, 0 elsewhere" 循环）、`governor_snapshot_observer.go:216-219`（逐条 emit）

**事实**：gauge `dispatch_governor_snapshot_state` 的标签只有 `{backend, mode, state}`，**没有凭据维度**。而 observer 在一个 tick 内遍历**所有**凭据，逐条调用 `RecordSnapshot`，每条都把「自己命中」的状态置 1、把其余状态置 0。于是**最后一个被遍历到的凭据决定了全池读数**：

```
凭据 7 = ready          → ready=1
凭据 9 = saturated      → ready=0, governor_saturated=1   ← 凭据 7 的 ready 被抹掉
```

Help 文本写的是 "Latest **per-cred** GovernorSnapshot.State value"——描述的是 per-cred 语义，实现是全局 flag 语义。凭据下线后其 `saturated=1` 无重置路径，永久残留。

**为什么加 `credential_id` 标签不合适**：那会让序列数乘以凭据数，与该文件顶部「keep the set tightly bounded」的约束冲突。

**修法**：把 gauge 改成 **每 tick 的聚合计数**（`RecordSnapshotBatch`）——与遍历顺序无关，且每个触及过的 `(backend, mode)` 组合四个状态全部重写（含 0），因此自清零。基数仍受两个闭集枚举约束。

**这是 dashboard 的坐标系变更**，已在代码注释中写明：旧语义 `== 1` 变新语义 `> 0`；`== 0` 的含义从「最后一条不是这个状态」变成「没有凭据处于这个状态」——后者才是它一直声称的含义。

**变异验证**：把批量聚合换回逐条置 1/0 后，聚合测试红四行（`ready 聚合计数 = 1, 期望 3` / `遍历顺序反转后 ready = 0` / 自清零断言失败）。

### 1.3 `Sweep` 的环首 break 钉死整个维度的 TTL 回收 【P1】

**位置**：`domains/dispatch/dimension_index.go:377-403`

**事实**：`Sweep` 原本「只扫环首前缀，遇到第一个未过期条目即 `break`」。两个事实让这个前提不成立：

1. 环序是**插入序**（`insertLocked` 直接 append）；
2. `ExpiresAt` 由 `Complete`（`:268`）与 `UpdateWait`（`:297`）**原地刷新**，不是随插入单调递增。

于是任何被 `Track` 但没走到终态调用的请求（被丢弃 / 被取消），它的 `ExpiresAt` 保持**零值**，永远停在环首，`break` 立即触发——**其后所有已过期条目永远得不到回收**。`DimensionIndexConfig.TTL`（默认 900s）的契约对一个维度整体失效，admin API 返回过期条目、`Dimensions()` 计数虚高。

值得注意的是同文件的 `trimRingLocked`（`:336`）**本来就全环扫描**并带正确注释——只有周期 `Sweep` 这条路径有洞。

**影响边界**：内存仍受 `PerKeyCapacity=128` 兜底，所以不是 OOM，是可观测性失真 + TTL 语义失效。

**修法**：`Sweep` 改为全环扫描，与 `trimRingLocked` 一致。

**变异验证**：退回 `break` 版本后 `TestR73_SweepRecoversPastAnUnterminatedHeadEntry` 红，报 `Sweep 回收 0 条，期望至少 1 条`。

### 1.4 observer 捕获 panic 后仍发布违规快照 【P2】

**位置**：`domains/dispatch/governor_snapshot_observer.go:176-183` → `:216`

**事实**：`Validate()` 对 `State=Ready + BackendErr!=nil` panic，observer recover 后**继续执行**并走到 `collected = append(...)`，该快照随后照样进 `RecordSnapshot` 并把 `ready` 置 1。`governor_snapshot.go:73-76` 明写 Validate「never masks a backend fault」——实际 mask 了。

**修法**：recover 时置 `valid=false` 并丢弃该行，同时计入 `metricGovernorUnknownLabelDrops`（原实现连丢弃计数都没有）。

**变异验证**：把 `if !valid { return nil }` 去掉后 `TestR73_ObserverDropsSnapshotThatViolatesValidateInvariant` 红（`ready 聚合计数 = 3, 期望 2`）。

### 1.5 `circuit_open` / `fp_slot_saturated` 被降级为同节点重试 【P1】

**位置**：`domains/dispatch/planner.go:128-143`（`isCentralPolicyKind` 白名单）、`domains/streaming/executors/executor_dispatch.go:832`（生产路径丢失 `ErrorKind`）

**事实**：`errorsx/action_policy.go:247-256` 有一段专门注释把 `KindCircuitOpen` / `KindFpSlotSaturated` 列为**终态**，理由是「纯网关侧准入信号，未发起上游调用，不得触发上游重试」。

两条路径都让这个决定落空：

1. planner 的 `isCentralPolicyKind` 白名单**漏了这两项** → 落入 `:176-181` 的历史标签兜底 → 改写成 `KindTransient` → `DecideNextAction` 判为 `ActionRetrySameNode`；
2. 即使补了白名单，`executor_dispatch.go:832` 返回的 `ForwardOutcome` **不带 `ErrorKind`**，planner 只能走 `ClassifyError` 去匹配消息串 `"dispatch: circuit open"`——不匹配 `classify.go` 任何正则，落到兜底 `KindTransient`。

**影响**：对一个已熔断 / 指纹槽已饱和的凭据反复发起同节点重试，浪费并发槽、推迟切换到健康兄弟节点——正是 `queued_request.go:44-51` 注释要避免的情形，也与 `PlanAfterFailure` 自己的 `FatalCredential` 短路（`:160-162`）自相矛盾。

**修法**：白名单补两项；生产路径补 `ErrorKind: string(errorsx.KindCircuitOpen)`。

**变异验证**：从白名单移除两项后测试红，动作复现为 `retry_same_cred（precommit_transient_retry）`，与子代理的独立复现一致。

## 2. 更正：权重负载均衡**已实现且在生产生效**

主代理初查（`domains/dispatch` 全包 `Weight` 出现 0 次）得出「objective 要求的按权重负载均衡无机制实现」的结论，**该结论错误**。完整链路：

```
provider/client.go:1920   applyCapacityWeightedLB
  └ 权重来源：SQL 层 COALESCE(mo.weight, 100) → defaultManualWeight=100 作哨兵
     ├ 运营显式设过 weight(≠100) → 尊重人工权重，上限 1000
     └ 否则 → clamp(min(auto 调优值, 人工硬上限), 1, 1000)
                          ↓
domains/streaming/executors/router.go:1088  planByTier
  ├ p2cOrder  : P2C，负载分低者胜；平手时 pickWeightedTie 按 Weight 容量比例（反 83/17 偏置）
  ├ partitionBySelectionLayer : 优先层/常规层/兜底层
  └ promoteWeightedCandidateWithWeights : 平滑加权轮询首跳
       position = (counter % totalWeight) * weightStride(totalWeight) % totalWeight
                          ↓
firstHopLotteryWeights : sticky 会话 / 最近请求 / 余额 / 计划额度 四维惩罚折算进份额
                          ↓
domains/dispatch/dispatcher.go:165  selectAndEnqueue
  RouteFunc 由 executor 注入（executor_dispatch.go:83 → dispatchRoute → PlanCandidatesPinned）
  → dispatch 侧取排序后的第一个有容量的候选
```

**结论**：按权重的负载均衡在**候选与凭据选择路径上是完整的**，dispatch 按设计不重复打分（`executor_dispatch.go:151` 起只做软降序后取 `refs[0]`）。

**三条**此前被列为「不在生产生效」的机制，核实后结论如下：

| 机制 | 核实结论 |
|---|---|
| `pool/scheduler` WRR 加权轮询 | **确为零导入方**，是未被采用的实现，与生效的 `router.go` 平滑 WRR 重复 |
| `scheduler_weight` / `_current_` / `_effective_` 三个 gauge | **确为零调用方**（`metrics/prometheus.go:604-613` 定义，无人调用），归档文档 `docs/archive/process/omni-ref2/03-IMPLEMENTATION-REPORT.md:35` 早已 SOURCE-VERIFIED 记载 |
| `domains/credential` 的 `BanditScorer` / `WeightNudge` / `ScorerWithWeights` | **确为死代码**，且**有 2026-09-14 R28 与 2026-09-19 两次明确登记**：`bg/bandit_flusher.go:1-3` 顶部注释「UNUSED (audit 2026-09-14 R28 #20): Bandit wiring disabled in production」、`executors/router.go:1089-1092`「The Thompson-Sampling Bandit branch was removed 2026-09-19」 |

最后一条不是新缺陷——**是有意移除且有登记的**。按本会话既定纪律「判定能力缺失前先问有没有文档记录这是有意的」，不报为 bug，但 `governor.go:15/77` 仍称 `concurrencyGovernor` 是 "weighted semaphore"（实现是标量计数器），注释需更正。

## 3. 出方案（本轮未修）

| # | 缺陷 | 为什么不本轮修 |

- **溢出/下溢**：`used` 仅在 `<cap` 时 CAS +1；token 债务有 `max(..., -rpm/-tpm)` 下限。
- **策略发布 fail-closed**：`policy_publisher.go` 失败不推进 `lastRevision`；`NotifyRevisions` 先于 swap；任一 backend 错误整体放弃。**未发现「失败变成无限制」的路径**。
- **两套并行限流不存在**：local 与 redis 是同一 `Governor` 接口的互斥后端，由 `pipeline.go:462-463` 唯一决定，无双重计数，无「一个说行另一个说不行」的无解态。
- **Redis 脚本原子性**：全部单键或同 slot 双键（hash-tag `{qbt}` / `{qbl:...}`），cluster 单 slot；`admit` 的求和与 `HINCRBY` 在同一脚本内，无 TOCTOU。
- **journal 跨租户授权**：`ConsumeSnapshot` 在租户不匹配时返回 `ErrJournalNotFound`（不泄漏存在性）+ 二次字段校验；HTTP 层独立复核 role。双层校验正确。
- **队列状态机出队唯一性**：`complete()` 的 CAS + `ResultCh` 容量 1 + `abandoned` 守卫构成完整的一次性交付保证。
- **无界增长**：`maxAttempts`、总队列容量、各 lane 上限、journal/投递队列/瀑布环形缓冲均有界；背压拒绝统一走显式 `OverflowError` + `RetryAfter`，**是明确拒绝不是静默丢弃**。
- **关闭时零丢失**：`drainModelQueueOnShutdown` 的「空观察」与两处 enqueue 的 shutdown 门在同一临界区内，原子性成立。
- **投影深度正确性**：`AbsoluteDepth` 用绝对深度而非累加 delta，乱序事件下计数器不漂移。
- **Lua 权重数学**：`weightStride` 是乘数不是取模上限（初查时我按后者判读，报了两个「异常」——那是我的判据过粗，64 位下 `position*stride` 最大 ~6e11 不溢出，**假警报**）。
