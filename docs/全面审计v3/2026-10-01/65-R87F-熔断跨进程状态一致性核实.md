- 日期：2026-10-01
- 轮次：R87-f
- 性质：**核实 + 次级发现**。本轮**无代码改动**。
- 触发：64 号 §5 登记的未验项「熔断状态有落库同步，跨进程重启后的状态一致性未验证」

---

## 0. 要回答的问题

R87-e 的修复（`breaker.go` 的 `sameIncident`）依赖 `b.lastFailureAt`。若该字段在跨进程恢复后丢失，则 `sameIncident` 恒为 `false` ⇒ **缺陷原样复现**，修复只在单进程内有效。

**⇒ 必须确认：`lastFailureAt` 是否被持久化/恢复。**

---

## 1. 核实结果

### 1.1 `lastFailureAt` 从不持久化

```bash
grep -rn "lastFailureAt" --include=*.go . | grep -v _test | grep -v vendor
```

命中仅 3 处，**全部在 `domains/credential/breaker.go` 内部**（字段声明 `:195`、判定 `:464`、赋值 `:476`、另两处 `RecordSuccess`/`Reset` 清零 `:647`/`:671`、一处 `Stats()` 只读 `:699`）。**无任何序列化/反序列化路径。**

### 1.2 落库是**单向**的，且**没有恢复路径**

`domains/credential/state_sync.go:122-155` 的 `syncOne` 只写三列：

```sql
UPDATE credentials
SET circuit_state = $1, circuit_opened_at = $2, cooling_until = $3
WHERE id = $4
```

方向是 **熔断器 → DB**。全仓**没有任何代码把这三列读回 `Breaker`**——`Breaker` 上根本没有 `Snapshot`/`Restore` 方法（`^func (b *Breaker)` 全量清单里不存在）。

**⇒ 熔断器是纯内存状态机，进程重启后从 `Closed`/`consecutive=0`/`lastFailureAt=零值` 全新开始。**

### 1.3 关键：路由判定**不读** DB 的 `circuit_state`

```bash
grep -n "circuit_state|cooling_until" sql/objects/views/v_routable_credential_models.sql
# → 0 命中
```

`v_routable_credential_models.sql`（F1 的权威视图，`:17` 是 `is_routable` 单一 AND 合取）**完全不含 `circuit_state` / `cooling_until`**。

`circuit_state` 的全部消费方只有三处，且**都是观测用途**：

| 位置 | 用途 |
|---|---|
| `metrics/prometheus.go:205` | `llm_gateway_circuit_state` 指标 |
| `cmd/gateway/main_livestream.go:503` | 实时流/管理界面展示 |
| `cmd/gateway/main_v32_wiring.go:100` | admin 读取展示 |

---

## 2. 结论

**R87-e 的修复没有跨进程正确性问题。** 三点合起来才看得出来：

1. 熔断是纯内存的，重启后本就是全新状态 ⇒ `lastFailureAt` 为零**不是缺陷而是事实**——重启后不存在「同一次事件」可延续；
2. 路由资格由**内存熔断器**决定，重启后从 Closed 起步 ⇒ **路由行为正确**；
3. `credentials.circuit_state` **不在路由视图里** ⇒ DB 里的陈旧值不会导致误摘流或误放行。

**⇒ 64 号的未验项关闭，R87-e 的修复判定为完整有效。**

## 3. 【次级发现】`credentials.circuit_state` 重启后陈旧，且被当作权威展示

**形态**（属「存在物 ≠ 起作用的物」一族）：

- 进程重启后：内存熔断器 = `closed`，而 `credentials.circuit_state` 仍停在重启前的 `'open'` + `cooling_until`（未来时间）；
- 期间**没有任何启动对账**会把它刷回：`main.go:2069` 的注释记载「`credentials.circuit_state` 只有 `RestoreOnSuccess` 一个 `'closed'` 写入方」，`DBStateSync` 只在**发生真实迁移**时写；
- 管理界面（`main_livestream.go:503`、`main_v32_wiring.go:100`）把这一列**当作熔断器的当前状态展示**。

**⇒ 运维在重启后可能看到「凭据熔断中」而实际该凭据完全可用，且该状态会一直陈旧到下一次真实迁移为止。**

**定级：P3。** 不影响路由（已证），只影响观测准确性；窗口不确定（取决于何时发生下一次迁移）。

**修法建议（未实施，仅登记）**：
- 最小：在 `main.go` 启动时对 `circuit_state` 做一次**启动对账**（把内存为 `closed` 的凭据对应行刷回 `closed`），或
- 更轻：展示层在 `circuit_state='open'` 但 `cooling_until < now()` 时标注「已过期，以内存为准」，避免误导。

**为何本轮不做**：属可观测性展示层改动，需确认 admin/实时流的展示契约是否已有「数据可能陈旧」的提示惯例；且与 R87 系列无耦合。

## 4. 建议补的门（下一步）

针对本次核实的空白，最有价值的门是**一条断言「路由视图不依赖 `circuit_state`」的守卫**：

- 判据：`v_routable_credential_models.sql`（及 `is_routable` 相关视图）**不得出现** `circuit_state` / `cooling_until`；
- 理由：这两列是**内存熔断器的观测镜像**，一旦被误加进路由合取，就会出现「DB 陈旧值直接决定摘流」——而 F1 已经证明这个门控是单一 AND 合取，**加一项就是再加一个全体连坐点**（R83b 的教训）；
- 按 `docs/audit/playbook/conventions.md` §9 走准入清单；注意 §9.3：**它天然是「无参数字面量不存在」型判据**，需自行证伪——例如变异方式是把 `circuit_state` 加进视图后确认门转红。

**本轮未建该门**（上下文与预算考虑），登记为下一轮候选。
