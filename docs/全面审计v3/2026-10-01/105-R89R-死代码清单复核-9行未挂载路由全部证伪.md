## 1. 证伪：9 行全部错误

### 1.1 三棵「线上 404」的路由树，逐一定位到挂载点

| 子代理称「从未挂载」 | 实际挂载点 | 状态 |
|---|---|---|
| `SelfCheckHandler.RegisterRoutes` | **`cmd/gateway/main.go:6576`** `selfCheckHandler.RegisterRoutes(mux, adminMw, superAdminMw)` | ✅ **已挂载** |
| `JournalSnapshotAPI.RegisterRoutes` | **`cmd/gateway/main.go:6790-6791`** `journalSnapshotAPI := admin.NewJournalSnapshotAPI(journalSnapshotStore)` + `journalSnapshotAPI.RegisterRoutes(mux, requestJourneyWrapAdmin)` | ✅ **已挂载** |
| `OutputComplianceHandler.RegisterRoutes` | 构造函数外部引用 **6 处**（`admin.NewOutputComplianceHandler`） | ✅ **已挂载** |
| `HealthCheckHandler.RegisterRoutes` | **`cmd/gateway/main.go:6496-6498`** `admin.NewHealthCheckHandler(dbConn.Pool())` + `RegisterRoutes(mux)` + `slog.Info("health-check API registered")` | ✅ **已挂载** |

**构造函数外部引用实测**（排除 `admin/` 包内与测试）：`SelfCheckHandler` **5**、
`OutputComplianceHandler` **6**、`JournalSnapshotAPI` **1** —— **全部非零**。

**它自己列出的证据也是自相矛盾的**：它写「`admin/handler.go` 结构体**不存在**
`selfCheck` / `outputCompliance` / `journalSnapshot` 字段，从类型层面佐证未接线」——
**这恰恰说明它只查了 `admin` 包内的 hub，而没有查 `main.go`**。
三个 handler 本来就不需要在 `admin.Handler` 上有字段（它们在 `main.go` 里就地构造并注册）。

### 1.2 根因：**「只 grep 类型名」看不见构造函数接线**

子代理的取证方法②是「向上追构造函数」。但它的实际执行退化成
「grep **类型名**在 `handler.go` / `main.go` 里出不出现」。

**而 Go 的典型接线形态是：**
```go
h := admin.NewXxxHandler(pool)   // ← 返回值类型从不具名
h.RegisterRoutes(mux)
```
**构造出的值从头到尾没有被具名过**，所以
`grep "XxxHandler"` 在外部文件里**必然 0 命中**——
哪怕它被调用了一万次。

**⇒ 判定「未接线」必须 grep 构造函数名 `NewXxxHandler` / `NewXxx`，
或直接读装配入口函数体，不能只 grep 类型名。**

### 1.3 它对 `RegisterRoutes` 统计的连带错误

它说「`admin/handler.go:898 RegisterRoutes` 实际只调用 **16 个** `Register*Routes`」，
并据此判定其余 9 个「不在任何调用点」。

**实际是：另有 2 个由 `cmd/gateway/main.go` 直接调用**
（`PromptInjectionHandler.RegisterRoutes`（`main.go:6491`）、`DualReadValidator.RegisterRoutes`），
**以及本轮新查出的 3 个（`:6576`、`:6791`、`:6498`）**。
**只数 hub 里的调用点，会把所有「在 main.go 里就地注册」的 handler 一律误判为死代码。**

## 2. 两个新方法论陷阱（与 §16 同族，方向相同）

§16 记的是「**自引用**让死文件显得很热」。本轮撞到的是**同方向的另一个**：

| 陷阱 | 表现 | 后果 |
|---|---|---|
| **§16 自引用** | 死文件 grep 出 10 处命中 | 把死的看成活的（漏报） |
| **§17 构造函数不可见** | 活端点 grep 类型名 0 命中 | **把活的看成死的 → 建议「接线」/「删除」已在生产运行的代码** |

**§17 危害大得多**，因为它的建议方向是**修改**。

**判据（已入册 playbook §17）**：判定某个类型/构造器「无人使用」前，
必须问「**它是不是被某个 `New…` 构造出来、且构造结果从未具名？**」
若是，则类型名 grep 恒为 0，**必须改用构造函数名 grep，或直接读装配函数体**。
