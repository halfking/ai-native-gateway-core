## 四、下一轮的三条明确入口

### 入口 1（**最明确、最短**）：177 号 那个可观测性缺口

`request_logs` 无法区分 `queue_budget_exceeded` / `queue_full` / `bucket_timeout` / `rate_limit_exceeded`。
⇒ **要回答「09-28 那 1,274 次业务限流是配额还是背压」，必须拿 `/metrics` 的
`llm_gateway_rate_limit_rejections_total{reason=...}`。**
⇒ **需运维提供该指标在那几天的曲线**（本机无网关进程，§44③）。
⚠️ 顺带可回答：**32.6 万次里到底有多少是「超配额」、多少是「队列背压」** —— 这会直接改变待裁决 70 的性质。

### 入口 2：175 号 那个未做的差集

> **「自检报的坏端点清单」与「业务实际使用的端点集合」求差集。**
> 若差集非空且自检确实在如实报告它们 ⇒ **自检不是失效，是设计边界**（正面结论）。
> 需 join `credential_probe_queue` × `credentials` × `credential_model_index` × 业务侧实际使用集 —— **本轮未做（成本高）**。

### 入口 3：172 号 修法方案 2 的前置统计

**补 `IsInternal` 写入方会让 89 个系统 key 立即从「300 RPM」变成「不限流」。**
⇒ **动手前必须先统计这 89 个 key 各自的实际流量**（只有自检确认只占 1.4% token，
**其余 88 个 key 的流量本轮完全未统计**）。
⇒ 且必须**同步确认 `verifier.go:104-107` 的快照往返路径**（§55：只改读入会造出「重启前后不一致」）。

## 五、这条线对全审计的**方法论产出**（已落进 playbook §63–§70）

| 条目 | 一句话 |
|---|---|
| §63 | 「没有 X」有两种读法：「不属于这类」vs「在到达这一步之前出局了」；取数顺序 **身份→结局→中间产物** |
| §64 | 「配了闸门 + 从不触发」必须查**该 key 的实际流量**再和阈值比 |
| §65 | 读「0 = 无限制」这类注释时，**必须同时确认 NULL 走哪条路**（这里两者语义相反） |
| §66 | **守卫存在 ≠ 守卫可达** —— 读守卫必须读它的输入有没有生产写入方 |
| §67 | 「事件确实发生」≠「因果链成立」；**表内 A 与表外 B 永远无法互相验证** |
| §68 | 共变 ≠ 因果方向；**判别维度优先选「另一个子系统在同一时间窗的表现」** |
| §69 | 怀疑「两个主体共用一个桶」时，**去读那个数据结构里桶的 key 是什么** |
| §70 | 一个字段在两个出口上待遇不同时，**先确认「哪个出口是我一直在查的」** |

⚠️ **这八条里有五条是本轮用「推翻自己」换来的**（167→168、169→170、171→174、174→175、171→173）。
