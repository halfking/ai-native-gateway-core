## 0. 一句话回答 objective「密钥可用」

**「解密失败 / 失效凭据降级」这两件事在运行时是成体系的**，且多处实现超出基线
（负缓存、generation 栅栏、DB 故障 stale-key 豁免、日志泄露整改、label 防高基数）。
**唯一实质缺口在密钥「轮转」侧**：没有运行时热重载、没有存量 re-encrypt 工具、
Fernet→AES 的 lazy migration 契约只写在注释里、生产全部丢弃。
另有一处死代码（`DecryptCache`）会误导后续维护者。

## 第一部分：解密失败的运行时降级链 —— **成体系，且健康**（这部分是本条的主要答案）

### 1.1 单候选解密失败：四个子问题全部健康

| 子问题 | 结论 | 证据（我复核过） |
|---|---|---|
| 会 panic 吗？ | **不会**。所有解密点返回 error；`keyring==nil` 时提前返回不解密 | `secret/aes_gcm.go:195-245`；`provider/client.go:2277-2280` |
| 会被误当「可用」发 401 吗？ | **不会**。显式降级：`Routable=false` + `APIKey=""` 清空 + 标 `key_decrypt_failed` | `provider/client.go:2413-2417` |
| 路由会 failover 吗？ | **会**。过滤层剔不可用候选 + 队列层跳过已试凭据 | `provider/client.go:274-283`、`router.go:1285-1290`、`dispatcher.go:139-181` |
| 会误入降级模式吗？ | **不会**。`routing_blocked:*` 不在瞬态白名单（解密失败非瞬态） | `router.go:1866-1886` |

### 1.2 负缓存与退避：设计成熟（超出基线）

真实缓存在 `provider/client.go`（非 `decrypt_cache.go`，见 §2）：
- **负缓存 1 分钟**（`decryptFailureCacheTTL`）—— 有意为之：注释记录 154 生产上曾 60+ 次/分钟重复日志，2026-08-17 P0 fix
- 负缓存容量 1024 上限 + 淘汰
- **generation 栅栏**：轮转时 `InvalidateCredentialKeyCache` 先 bump generation 再清缓存，**防止在途 reveal 把旧明文写回**（并发正确性考量到位）
- **DB 故障豁免**：`isRetryableDBError` 时不负缓存，走 1 小时宽限的 stale key（DB 抖动不应把凭据打成不可用）

### 1.3 探针路径确实持久化「不可用」

解密失败 → 写库 `availability_state='unreachable'` + `state_reason_code='decrypt_failed'`
+ 5min 恢复（`bg/credential_probe_v2.go:503-522`）；`node_probe` 另有实例级解密熔断
（阈值+冷却+半开+成功后去 escalate，`bg/node_probe.go:366-419`）。
**注**：请求路径不写库（仅请求内 `Routable=false`），到探针周期之间存在一个窗口——这是设计权衡（请求路径热路径不写库），非缺陷。

### 1.4 泄露面：健康

- 明文 key 不进日志（两种检索零命中）
- 密文 envelope 曾泄露、**已整改**（`bg/node_probe.go:3192-3201`，2026-09-08 审计把 `envelope_prefix` 换成只打 `envelope_kid`/`len`）
- 指标 label 明确防高基数（禁 `credential_id`、reason 封闭词表，`credential_decrypt_metrics.go:20-24,47-54`）
- admin 详情只出 `key_masked`（`admin/crypto.go:78-83`）；明文 reveal 是**受控**端点（POST + `super_admin`/`admin_key` 权限 + 终态拒 + 审计留痕，`provider_cred_lifecycle.go:61-94`）

## 第二部分：三处缺口（均 P3，运维/清理级）

### 2.1 【P3】`domains/credential/decrypt_cache.go` 是**死代码**（我独立证实）

`DecryptCache`（107 行，注释自陈「**P0 优化、降低约 30% QPS 开销**」）在生产中**完全未接线**。
**两种检索方式复核**：
1. `grep "DecryptCache|NewDecryptCache|GetOrDecrypt"` 全仓 → 全部 10 处命中**都在该文件自身**
2. `grep -v decrypt_cache.go` 的排除检索 → **零命中**；且**无任何测试文件**

生产真正用的缓存在 `provider/client.go`（`keyCache`/`keyCacheNeg`）。
**危害**：① 该文件注释里的「~30% 优化」是一个**从未生效**的声明，会误导维护者以为解密已缓存；
② 它**不含负缓存逻辑**，若有人误以为它是真缓存而照抄其语义，会丢掉负缓存这个 P0 修复。

### 2.2 【P3】凭据层 AAD **无租户绑定**（固定常量）

我复核证实：`secret/aes_gcm.go:28` `gcmAAD = "llm-gateway:credential"` 是**固定常量**，
加密 `:130` 与解密 `:169` 用同一个值，**不含 tenant / credential 维度**。
（AAD 的租户绑定机制 `AADBinding{TenantID,TaskID,RequestHash}` 只用于 `durable`/`pending` 域。）

⇒ **把 A 租户的凭据密文放到 B 租户下解密，不会被 AAD 拒绝**。
凭据层的跨租户隔离**依赖 DB 查询的 `provider_id` 过滤 + admin 权限谓词**，不依赖 AAD。

**定 P3**：这不是新漏洞，是**纵深防御的一层缺失**——凭据密文本身没有第二道防线，
一旦某处查询漏了 tenant/provider 过滤，AAD 不会兜底。durable/pending 域反而有这层。

### 2.3 【P3】密钥轮转侧三项缺失

- **运行时热重载 keyring：无**。`SetKeyring` 全是启动期一次性调用 ⇒ **轮转需重启进程**。
- **存量 re-encrypt 工具：无**。`cmd/tools/` 8 个子命令无一相关；`cmd/regen-credentials` 需操作者自带明文。
- **Fernet→AES-GCM lazy migration：契约只在注释**。`secret/aes_gcm.go:192-194` 声明
  「isLegacy=true 时调用方应 re-encrypt」——**我复核：所有生产调用点全丢弃 `isLegacy`**
  （写 `_`；唯一捕获的 `admin/handler.go:642` 经 `decryptCredStr` 也丢弃）。
  ⇒ **存量 Fernet 行永不自动升级格式**。

**多 key 向后兼容是成立的**（这部分健康）：解密按 envelope 里的 kid 取 key、不用 current
（`aes_gcm.go:145-150`）⇒ **加新 key + 切 current 即可新写入用新 kid、旧密文照解，可不停机**——
只是**存量格式迁移（Fernet→AES）**与**改密文 key**（re-encrypt）缺工具。
