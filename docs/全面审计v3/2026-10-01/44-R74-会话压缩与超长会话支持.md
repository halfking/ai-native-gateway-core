## 1. 已修

### 1.1 生存协调器的压缩重试是死代码 【P0】

**位置**：`domains/streaming/survival_coordinator.go`

**事实**：一次性闩锁 `ctxLenCompressRetried` 被**两处**消费，而顺序错了：

| 位置 | 动作 |
|---|---|
| 决策改写处 | `ctxLenCompressRetried = true` + 决策改为 `RetryNow` |
| body 改写处 | 条件 `!ctxLenCompressRetried && …` ⇒ **恒为 false** |

于是 `survivalCompressBodyForRetry`（真正裁剪 body 的函数）、`context_length_compress_retry_failed`（压缩失败即终态的熔断）在生产路径上**从未执行过一次**。

**实际表现**（子代理端到端复现，我独立复核闩锁顺序）：

```
body bytes before = 354026
attempt 1 upstream body bytes = 354026
attempt 2 upstream body bytes = 354026   ← 逐字节相同
TERMINAL action=fail_terminal reason=terminal_candidate
```

客户端观感：收到 `context_length_uncommitted_compress_retry` 的 thinking 提示 → 挂起 **30 秒**（生产默认 `RetryInterval`）→ 收到与第一次一模一样的错误。**多等 30 秒 + 多烧一次上游调用 + 一个误导性提示，收益为零。**

**这正是 objective 那条需求的落点**：「返回上下文超长……保持连接，不返回错误给客户端，自动进行压缩并再次请求数据」。

**注释还把方向写反了**：`:737-742` 写「决策层现在对该形态返回 RetryNow；这是 body 那一半——没有它重试会重发同一个超大的 body」，而实际上（a）决策层明确返回 `FailTerminal`（`attempt_outcome.go:482-484`），（b）body 那一半正因为闩锁顺序错误而不执行，于是**重发的正是注释声称要避免的同一个 body**。

**为什么既有测试没抓到**：`survival_ctxlen_compress_retry_test.go` 只测了三个**纯函数**，没有一个驱动 `SurvivalCoordinator.Run` 走完 ctxlen 路径。这是 R74-A 报告里点名的同一个模式——门锚在原语层，而缺陷在「协调器如何使用原语」。

**修法**：把 body 改写提到决策改写处，让闩锁只由 body 改写本身消费；下游那个不可达分支删除而不是留作陷阱。附带把日志里的 provider 改为从 `res.FinalAttempt` 取（该处 `lastProviderID` 尚未定义）。

**变异验证**：
- 不改写 body ⇒ 红，`第 2 次请求的 body = 199526 字节，未小于第 1 次的 199526 字节`
- 不可压缩时不立即终态 ⇒ 红，`不可压缩时不应再发第二次请求，实际发出 2 次`

修后实测：body 从 **199,526 → 104,766 字节**后重试；不可压缩的 Responses body **attempts=1** 直接 `context_length_compress_retry_failed` 终态。

### 1.2 Anthropic 重建制造孤儿 tool_use 【P0】

**位置**：`domains/hooks/compression/rebuilder_anthropic.go:194-210`

**事实**：`TrimAnthropicTail` 删除 tool_result-only 的 user 消息，注释理由是「避免 Anthropic `tool_use_id` 孤儿错误」。**方向恰好相反**：

```
旧: 删 tool_result  →  声明它的 assistant.tool_use 保留  →  孤儿  →  上游 400
```

Anthropic 要求每个 assistant `tool_use` 都有对应的 `tool_result`。删掉 result 而保留锚点，正好制造上游必拒的孤儿。**压缩把一个原本合法的 agentic 请求变成了必然失败的请求。**

cut 落点决定孤儿在哪一侧：`keepRecentPairs=1` 时 `tool_use` 被切走留下 result（`keepRecentPairs>=2` 时反过来）。旧实现只处理了后者那侧的错误方向，前者靠「也会删 result」而碰巧无害。

**修法**：两侧都收敛——孤儿的 `tool_result` 丢弃；声明了全部未被应答 `tool_use` 的 assistant 锚点整条丢弃。与 OpenAI 侧 `recentAtomicTail`「向前扩展到锚点」的做法对称。

**门第一次红的处理**：改完后 `TestRebuildAnthropicAfterSummary_DropsOrphanToolResult` 与 `TestTrimAnthropicTail_DropsToolResultOnly` 双双转红。按纪律先假设门是对的，逐行读后确认——**两个测试断言的目标（`call_old` 不该残留）本身是对的，红是因为实现方向错**，且我的第一版修法只处理了一侧导致普通 user 消息被误删，是这两个门抓出来的。修后转绿。

**变异验证**：退回旧实现 ⇒ 两条新测试红；只删一侧 ⇒ 被对应的既有测试抓住。

### 1.3 resume 摘要对非 OpenAI-chat 形态全为空 【P1】

**位置**：`domains/hooks/handoff/request_hook.go:315`（旧 `extractConversation`）

**事实**：该函数把 `messages[].content` 反序列化成 `string`，遇到以下形态时 `Unmarshal` 失败直接返回 `""`：

- Anthropic Messages（`content` 是 block 数组）
- Responses 协议（轮次在 `input` 而非 `messages`）
- OpenAI 消息的数组 `content`

于是 `resume_packet.summary` **不含任何对话内容**，新会话开局即失忆，**且无错误、无指标**——只是静默变空。LLM 引擎同样受害（`conversation==""` 时改喂 token 计数）。

**讽刺之处**：handler 早已正确填入 `Request.Protocol`（`protocolForHandoff(r.URL.Path)`），而这个函数从不读它；压缩域也早已有按协议分派且会 `secretmask.MaskSecrets` 的正确实现，只是没导出。**两份实现各写一份，然后漂移了。**

**修法**：导出 `compression.ExtractConversationText` 作为共享入口，按协议分派 + 形状嗅探兜底（`messages` → `input` → `conversation`，content 为字符串或 block 数组都展平）。

**变异验证**：退回旧实现 ⇒ 三种形态的摘要实测均为空串。

## 4. 一条子代理结论我复核后撤回

R74-C 报 D3：「同一 `(tenant, previous_session_id)` 的第二次提案 upsert 覆盖第一次，第一个客户端拿到的 `handoff_id`/`confirmation_token` 立即失效」，定 P1。

我复核后**撤回这条**，理由：改法会让 `TestConfirmationProposalStoresOnlyHashAndRotates` 转红，按纪律先假设门是对的，读完确认——**token 轮换是刻意的安全属性**（旧凭据失效防泄漏），测试名里的 "Rotates" 就是这个意思。而检测矩阵 FLOW-06 说的「同 ID 重试」指的是**同一 ID** 的 confirm 幂等（已被该测试 line 45-48 覆盖），不是「两个不同提案」。

**真正的根因是 D4**：`CommitRequest` 无调用方 ⇒ 冷却与频次只在 confirm 之后生效 ⇒ 同一超限会话每个请求都重新提案，第一份必然被顶掉。所以该按 D4 修（prepare 阶段限频），而不是动 token 轮换。

这条记录本身有价值：**「第二次提案会作废第一次」是症状，「提案没有频次控制」是病因**。

## 6. 已核对确认没问题的部分

- **executor 内层的 4xx 压缩重试是真的**（`executor_chat.go:1309-1367` 等三处）：`ctxLenRecoveryRetry → attempt--` 让压缩后重发不消耗 retry 预算，相关测试实跑通过。**objective 想要的「客户端观感不变」在这一层做到了**。
- **LLM 摘要级联有防重入闩锁**（`context_summarize.go:1104`/`1245`），级联内部不自旋。
- **已提交内容的保护正确**：`survivalCtxLenCompressRetryDue` 拒绝 `CommitState >= Content`；committed ctxlen → `fail_terminal/terminal_candidate`，SSE 以 error frame + `[DONE]` 收尾，**协议自洽**。
- **无限重试风险不存在**：一次性闩锁 + retry ceiling + deadline + attempt budget 四重兜底。
- **dispatch planner 不会掐断压缩重试链**：压缩重试发生在 `executeOpenAI` 内部、`forwardForDispatch` 返回 `ForwardOutcome` **之前**，planner 看到的是压缩已穷尽后的终态。R73 对 `circuit_open`/`fp_slot_saturated` 的终态修复与本链无耦合。
- **压缩缓存并发安全**（R74-A 用 16 goroutine × 40 轮真实并发 `-race` 实测干净）：`updateStripes[256]` 按 key 分片，非进程级全局锁。R71 在同项目发现的「进程级全局锁串行化」缺陷在这条路径上**没有重演**。
- **摘要失败不静默丢弃**：LLM 摘要失败/空/未缩小 → 降级 `mechanicalTrim`（原 body 子集），非凭空构造。
- **无物理删除原始轮次**：`buildSessionState` 同时持久化 `RawSnapshot`/`RawMsgCount`/`AlignmentMap`，三层 provenance 保留。
- **goal_state 跨副本安全**：提案时序列化落 PG，restore 优先读持久化源。
- **confirm 越权面已封**：`TenantID`/`APIKeyID` 取自已验证的 key，不接受客户端 JSON；目标会话存在性与 `TargetCreatedAt` 时序双重校验。
- **resume 摘要脱敏**：`resumeSensitivePatterns` 在摘要/record/prompt 三处均过 `redactResumeSensitive`（本轮修完新路径后仍生效，有回归测试钉住）。
