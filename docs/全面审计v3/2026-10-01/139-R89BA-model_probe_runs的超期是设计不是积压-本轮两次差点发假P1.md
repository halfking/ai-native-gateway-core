# 139 号｜R89-BA：`model_probe_runs` 的「99.5% 超 8 小时未搬走」**不是积压，是设计** —— 本轮两次差点发出假 P1

- 日期：2026-10-01
- 轮次：R89-BA
- 起因：138 号发现 **14/22 张 `_hot` 表没有 `ts` 列**、无法用统一口径核验保留。
  本轮去查这 14 张里**第一张有分区的**（`model_probe_runs`，10,666 行，最大）——
  **结果我两次差点把它报成 P1，两次都是错的。**
- 结论先行：
  1. **`model_probe_runs_hot` 10,666 行里 99.5% 超过 8 小时 —— 但 8 小时是错的阈值。**
     该表 2026-07-14 起是**「纯 hot 表」**（spec 被显式注释掉，不 promote、不归档），
     保留期由 `lifecycle.model_probe_runs_ttl_days` **默认 14 天**控制。
     ⇒ **不是积压，是设计。**
  2. 实测最老行 = 2026-09-17 11:09，距今 **14 天 + 51 分钟**，50 行刚过边界
     ⇒ **TTL DELETE 正在正常跑**（hourly），等下一轮。**无缺陷。**
  3. **唯一的真问题（P3）**：`promote_model_probe_runs_hot_to_partition` 函数**仍存在于库中但永不被调用**
     ⇒ **遗留死函数**，会让后来者以为该表有归档。
  4. **对 objective 的影响**：`model_probe_runs` **超过 14 天的历史不可回溯**——
     而其它大表都保月度归档。**若有任何质量趋势/探针历史分析需要超过 14 天，这张表结构性地给不了。**

---

## 一、我犯的两个错（**本报告的主体**）

### 错 1：grep 命中注释块 ⇒ 当成了代码存在

我跑 `awk '/func promoteSpecs\(\)/,/^}/' | grep -cE "model_probe"` 得到 **3**，
据此写下一句：**「`promoteSpecs()` 里确实有 `model_probe_runs`」**。

**实际读原文，那 3 处全在注释里，spec 是被注释掉的**：

```go
// model_probe_runs_hot 已切换为纯 hot 表策略（2026-07-14），
// 不再 promote 到 columnar 分区。hot 表数据通过 cleanupOldModelProbeRuns()
// 按 lifecycle.model_probe_runs_ttl_days 直接 DELETE 清理。
// {fnName: "promote_model_probe_runs_hot_to_partition", label: "model_probe_runs_hot"},
                    ↑ 被注释掉的那一行
```

⇒ **我不仅数错了，还差点反过来把三处一致的正确注释（`:84`、`:1382`、settings「除 model_probe_runs_hot」）
当成「过期描述」——它们全都对。**

### 错 2：套用全局阈值（8h）去判一张**保留期是 14 天**的表

我量到「10,666 行里 **10,618（99.5%）** 超过 8 小时」，
本能反应是：**「99.5% 超期未搬走 ⇒ promote 坏了 ⇒ P1」**。

**但 `8h` 是 `lifecycle.hot_retention_hours`（其它表的保留窗口），
而这张表的保留期是 `lifecycle.model_probe_runs_ttl_days` = **14 天**，
且它**根本不 promote**。**
⇒ **用错的阈值量正确的表，得到的差值越大，结论越像真的。**

⚠️ **「超期比例 99.5%」这个数字在报告里读起来极有说服力，而它完全无害。**

## 二、正确的事实

```sql
SELECT count(*), count(*) FILTER (WHERE created_at < now()-interval '8 hours'),
       count(*) FILTER (WHERE created_at < now()-interval '14 days'),
       min(created_at), max(created_at) FROM model_probe_runs_hot;
```

| 指标 | 值 |
|---|---|
| hot 行数 | 10,666 |
| 超 8h（**错误阈值**） | 10,618（99.5%） |
| **超 14d（本表真实阈值）** | **50** |
| 最老行 | 2026-09-17 11:09:35 |
| 最新行 | 2026-10-01 11:32:23 |

**当前时间 2026-10-01 12:00 ⇒ 14 天边界 = 2026-09-17 12:00。**
**最老行比边界早 51 分钟，50 行刚过线** ⇒ **TTL DELETE 正在正常跑（hourly），等下一轮。**

分区侧（**精确 `COUNT(*)`，非 `reltuples`**，见 129 号 playbook §28）：

```
model_probe_runs_default = 0 ；_2026_07 = 0 ；_2026_09 = 0 ；_2026_10 = 0 ；parent = 0
```

**分区全空是设计的结果（不 promote），不是故障。**

代码侧确认：`cleanupOldModelProbeRuns` 读 `lifecycle.model_probe_runs_ttl_days`
（`settings/spec_lifecycle.go` 默认 **14**，hot-reloadable），
且有下限保护 `if retentionDays < 1 { retentionDays = 14 }` ⇒ **配置错误也不会变成「无限制保留」。**

## 三、真正的问题（**P3**）

**`promote_model_probe_runs_hot_to_partition` 函数仍存在于数据库中，但永不被调用**
（spec 已注释掉）。
⇒ **这是典型遗留物**：函数名 + 存在性会让人（包括未来的审计者、我这一轮的第一次检索）
**以为该表有月度归档**。本次我正是被它误导的。

**建议**：删除该函数，或至少在 `promoteSpecs()` 的注释里加一句
「**函数仍在库中但已停用，勿以为该表有归档**」。

## 四、对 objective 的影响（**需要产品知道**）

- objective 写「**所有**的大数据表是以 hot+分区（columnar）表来完成…
  通过任务批量转移到分区表中」——
  **`model_probe_runs` 按设计不满足**：它是**纯 hot 表**，14 天后直接 DELETE，**没有任何归档**。
- ⇒ **凡是依赖探针历史超过 14 天的分析（模型质量趋势、探针成功率随时间变化、供应商质量长周期对比），
  这张表结构性地给不了数据。**
  **这与其他大表（都保月度归档）不一致，是一个能力边界，需要产品确认是否可接受。**

⚠️ **诚实边界**：本轮**没有**找到任何**正在读取** `model_probe_runs` 超过 14 天数据的代码路径
（本来就不可能有，数据不存在）。
**登记的是「能力边界 + 一致性问题」，不是「正在出错的缺陷」。**

## 五、playbook §35（本轮新增，§33 的姊妹条）

**核对「保留/积压/超期」时，阈值必须来自该对象自己的配置，不能套用全局默认。**

- **形态 A（本轮错 2）**：全局 `lifecycle.hot_retention_hours = 8`，
  而该表用的是 `lifecycle.model_probe_runs_ttl_days = 14`
  ⇒ **用 8h 量它，99.5% 看起来超期，实际 0% 超期。**
- **形态 B（本轮错 1）**：`grep` 命中了**解释「为什么被移除」的那段注释**，
  把**被注释掉的代码**当成了**存在的代码**。
  ⇒ **grep 命中注释 ≠ 代码存在**；这与 13 号（注释承诺的接线默认不成立）互为镜像：
  **注释承诺的不算，注释宣告的移除也不算——都得看真实代码。**

⇒ **落地纪律**：任何「超期/积压/残留」类数字，
① 先问**「这个阈值是谁定的」**（是全局默认，还是该对象自己的配置）；
② 报「超期比例」之前，**确认该对象的保留机制本身是不是还开着**
（本例：promote 已被显式关闭，8h 这条规则对它**根本不适用**）。
**⇒ 数字越刺眼，越要先确认量它的尺子是不是这把表的尺子。**

**同族**：§27（数据缺失先看形状）、§32（盲区是否引入新实体）、§33（先证明后果再量化规模）、
§28（终态缺失的歧义 / reltuples 不可支撑存在性断言）。
**共同点：全都是「**数字本身干净，但尺子/前提可能不是这一把**」。**
