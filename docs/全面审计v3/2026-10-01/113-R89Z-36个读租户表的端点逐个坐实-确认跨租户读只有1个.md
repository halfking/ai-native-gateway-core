## 二、筛查法连续两轮都先证伪了自己（这是本轮的方法论主体）

**第一轮（112 号 / §20）**：用「函数体有无 `tenant_id`」筛 ⇒ 8 个候选，**至少 3 个假阳性**
（`tenantLogsClause` 以 SQL 片段注入，列名永不出现在函数体）。

**第二轮（本轮 / §21）**：改用「函数体是否出现
`tenantLogsClause | IsTenantAdmin | EffectiveTenantID | requireSessionTaskAccess | assertTaskInTenant`」
这个**自造名单**重筛 ⇒ 9 个候选。

⇒ **第二次仍然是自己把自己证伪了**：本仓至少存在**第三种命名的闸门**
`attachmentTenantScope`（`admin/data_lifecycle_attachments.go:78-83`），
不在我的名单里，于是 5 个**实现正确**的 handler 被判成「无 guard」。

**正确顺序是「先找形态、再取名字」**：

```
grep -rn "AND tenant_id = \|AND .*_id = \$" --include=*.go   # 找所有拼 SQL 片段的地方
```

而不是凭印象列 helper 名。已入册 **playbook §21**。

**⇒ 这恰好证明「机械筛只能缩小范围、最后一个必须读原文」**：
若停在「9 个候选」就发报告，会**凭空造出 8 个缺陷**；
逐个读原文后收敛到 **1 个真缺陷**。

但它是**读出来的**，不是假设的。

## 四、`handleDataLifecycleMetrics`：判为「非隔离缺陷」，低危登记

```sql
SELECT COUNT(*) FILTER (WHERE ts > NOW() - INTERVAL '7 days') AS hot_rows,
       (pg_total_relation_size('request_logs') * …)::bigint AS hot_size, … 
FROM request_logs
```

**没有任何租户维度**，返回的是全库行数与体积估算，挂在 `admin(...)` 下
⇒ 任意 `tenant_admin` 可读到**全库总行数与表体积**。

判**不构成跨租户数据越权读**（不暴露任何一行的业务数据），
但属于**基础设施元信息的越权暴露**，登记为低危、不单独占待裁决条目。
（若将来把 `tenant_id` 加进该聚合，需一并考虑是否要按租户切分。）
