## 1. D1【P1】`load_balance_strategy` / `location_affinity` 配置后对生产流量零作用

**这是本轮最重要的发现，且由主代理独立复核确认。**

**事实链**（三步都可静态判定）：

1. `/api/proxy/policy` 接受并**持久化到 PG** 这两个字段（`admin/proxy.go:947-960, 985-990`），GET 原样回显；`SetLoadBalanceStrategy` / `SetLocationAffinity` 也真的构造了 LoadBalancer（`manager.go:218-239`）。
2. `manager.go:487`：
   ```go
   var selected *Node
   if bestOnly {
       selected = activeNodes[0]      // ← 生产走这里
   } else {
       ...
       selected = m.loadBalancer.SelectNodeWithLocation(...)   // ← :499，真正用策略
   }
   ```
3. 生产唯一入口是 `EgressProvider.TransportFor` → `GetProxyTransport` → **`SelectBestNode`**，它传 `bestOnly=true`。而 **Manager 层的 `SelectNodeWithStrategy` / `SelectNodeWithLocation` 全仓零非测试调用方**（全量 grep 只命中自身定义、注释、以及 `load_balancer.go` 上**另一个类型**的同名方法）。

**危害**：管理员把策略配成 `round_robin` / `consistent_hash` 并开启地域亲和，API 返回 `{"ok":true}`、DB 有行、GET 读得回，但**真实出口恒为排序首位节点**（健康度 → 响应时间）。这是本域最典型的「配置了但不生效」，且直接落空 objective 的「节点地域的优先级配置」。

**注意 `manager.go:218-219` 的注释确实写了**「SelectBestNode always remains best-only」——即**代码作者知道并有意保留了 best-only 语义**。问题在于 admin 的策略面**把这三个字段作为可配置项呈现给管理员**，却没有说明它们对生产流量不生效。这是「注释知道」与「界面承诺」的分裂，属未登记的产品面缺陷。

**是否已登记**：`docs/全面测试/48h-audit/D12-egress-proxy/` 下仅 `plan.md` 一份，检索无相关登记 ⇒ **未登记的设计决定**。

**未实证**：本轮只读，未跑真库流量对照。静态判定充分但运行时影响未实证。

**修法方向（未实施）**：三选一——(a) 让 `SelectBestNode` 尊重已配置策略；(b) admin 端点对这两个字段标注「当前版本不作用于生产流量」并在 UI 隐藏；(c) 下线该配置面。**选哪种属产品裁决**，因为 (a) 会改变真实出口分布。

## 2. objective 3「自动避开香港」：达标，且我独立实证了两处疑虑都不成立

这是本轮 objective 里最具体、最可测的一条，结论是**真自动**：

**验证链**（主代理独立走通，未采信注释）：

1. `proxy/types.go:246` `defaultBannedRegionsOverlay()` 读 `settings.CachedPlatformString(key, "")`——传的是**空串** fallback。
2. 真库确认 **`settings_kv` 里没有任何 `proxy.%` 键**（该键从未被显式设置过）。
3. 于是我怀疑「新装机器上 HK 根本不禁用」。追到 `settings/ttl_cache.go:122 → :45 cachedEffectiveRaw → Global.EffectiveValue(ScopePlatform, key, "")`，默认参数**又是空串**。
4. 最后由 `settings/registry_test.go:116 TestRegistry_EffectiveValue_FallbackChain` 定案：无 DB / 无 env backend 时 `EffectiveValue` 返回 **`"the-default"`（即 Spec 的 `Default: "HK"`）**，source=`default`。⇒ **HK 规避自动生效**。

**第二处疑虑也不成立**：我担心 `CachedPlatformString` 在 `settings.Global == nil` 时返回 `""` 会造成 fail-open 窗口。查 `settings/spec.go:322`——`var Global = NewRegistry()` 是**包级 var 初始化**，`main()` 之前完成 ⇒ 生产环境**永不为 nil**。（它只在单测二进制里为 nil，正是 `sessionv2mirror/hook.go` 注释说「tests override it」的原因。）

**规避强度（独立确认）**：`manager.go:426` 的 `IsRegionBanned(node.Location, subscriptionBans[...], node.BannedRegions, overlayBans)` 是**三向并集**（平台 overlay + 订阅层 + 节点层），存量订阅未回填 `banned_regions` 也被 overlay 覆盖。

**切换时重新评估**：`ForceSwap`（`manager.go:1051`）→ `selectNodeExcluding(..., excludeNodeID)`，与地区过滤在同一函数内 ⇒ **切换不会绕过 HK 规避**。自动切换由 `swapProbeOne`（`manager.go:1265`）在探活周期驱动（`unhealthy` 记 1 次失败、达阈值即换），另有 `admin/proxy.go:878` 手工端点。

**测试覆盖**：`TestIsRegionBanned`、`TestSelectBestNodeRespectsRegionBan`、`TestSelectBestNodeAppliesDefaultBannedRegionsOverlay`（3 个 case：未配置时仍拒唯一 HK 节点 / 置空串放行 / `" hk , US ,"` 归一化）、`TestDefaultBannedRegionsOverlayUnregistered`、`TestForceSwapExcludesCurrentNode`。

## 3. D3【P2】HK 规避对「未知地区」fail-open

`guessLocation` 识别不出即返回空串（`parser.go:605-607`），而 `IsRegionBanned` 对空 region **一律放行**（`types.go:220-223`，注释自陈「不误杀」）。因此**命名不含任何地区 token 的香港节点**（如 `🇭🇰-01`、纯序号、emoji 前缀）Location 为空，**同时绕过 overlay 与订阅/节点层禁用**。

⇒ 规避强度取决于机场供应商的命名规范。R51/R59 已补过 `HONG KONG` 分词与 `HKG` 整词，说明该类绕过**历史上反复出现**。

**未实证**（需真实订阅样本）。这是「保守放行」的有意权衡（宁可漏过也不误杀非 HK 节点），但与 objective 3「均会屏蔽香港」的强度要求有缺口。

## 4. D4【P2】`providers.egress_profile` 默认 `'direct'`，无海外自动判定

schema 默认 `'direct'` NOT NULL，`provider_catalogs.default_egress_profile` 同为 `'direct'`。**本机真库实证：60 个 provider 全部 `direct`，零个 `proxy`。**

已标记 `proxy` 的供应商是 fail-closed 的（`egress_provider.go:35-37` 的 R28-P-1 注释属实：修复前 `egress_profile` 只写不消费，「海外供应商必须走代理」在生产 chat 流量上并不成立）。但**未标记的海外供应商一律直连**。

⇒ **默认部署下 objective 1 不成立**，需逐个人工置位。`admin/free_pool_extra.go:1573` 的注释也明说「默认仍为 direct」。

---

## 5. D2【P2】`Domain.RequiresProxy` 整条域名域能力是孤儿

`Manager.RequiresProxy`（`manager.go:583-597`）零调用方；`CreateDomain`/`UpdateDomain`（`types.go:147,150`）同样零调用方 ⇒ `Domain.RequiresProxy` 字段**在生产中永远不会被写入**，也没有消费方；`admin/handler.go` 无对应路由。

`types.go:81` 的注释宣称「是否需要代理」是域名级一等公民，实际是空壳。**这条本可作为 objective 1「自动判定海外」的第三条路径**，但它是死的。

## 6. D5【P3】地区禁用变更不驱逐当前 active 节点

`ReloadCache` 清 active selection 时只判断**节点是否还存在**，不判断该节点此刻是否已落入禁用地区；`swapProbeOne` 也只按失败阈值触发 `ForceSwap`，无「被禁即换」分支。

⇒ 管理员收紧禁区后，探活循环继续探测一个已违规的节点，`GET /api/proxy/policy` 的 `swap_state` 仍把它报为当前出口——**运营视图失真**。**数据面无害**（`TransportFor` 每请求重选，禁用即时生效）。

## 7. 部署现状（本机真库，只读）

| 项 | 值 |
|---|---|
| `proxy_subscriptions` / `proxy_nodes` / `proxy_selection_policy` | 1 / **116** / 1 |
| 节点协议分布 | **trojan 114 + vless 2，零 http/https/socks5** |
| 节点 `status` | 全部 `active` |
| 节点健康字段 | **全部 NULL**（`last_health_check_status`/`last_health_check_at` 均空，`consecutive_failures` 全 0）⇒ **探活从未执行过**，`active` 是导入默认值 |
| 地区分布 | HK 15、SG 12、JP 11、US 11、TW 10、KR 7 … |
| 标记 `proxy` 的 provider | **0 / 60** |

**⇒ 整个代理子系统在本部署上处于休眠且未验证状态。**

`Dialable()`（`types.go:95`）只对 `ProtocolHTTP/HTTPS/SOCKS5` 返回 true，而 `parser.go:47-50` 明写 trojan/vless/vmess/ss「Go 的 net/http 无法直接拨号，解析后仅作为库存记录保存」。⇒ **116 个节点全部不可拨号**。

**若此刻把任一 provider 置为 `proxy`，因 EgressProvider 是 fail-closed，该 provider 的请求会立即全部失败。**

**但界面已正确提示**：`admin/proxy.go:9` 的注释写着「所有列表与汇总接口都会显式给出 dialable 标记，避免『导入了 116 个节点却一个都用不了』」（**注释里的 116 与本机实测完全一致**），DTO 暴露 `Protocol` / `Dialable`（`:139,:144,:172`），`undialableWarning`（`:188`）在 total>0 且 dialable=0 时返回可操作提示，指明用 mihomo/xray 暴露为 http/socks5 再登记。

⇒ **这是被上一轮审计发现并已修好的形态**，不是新缺陷。当前「0 个 provider 标记 proxy」反而是**安全的状态**（不会触发 fail-closed）。**建议保持现状直到有 http/socks5 网桥入口。**
