# 38 — R68：把「上抛打到丢弃错误的调用方」做成门，并修掉 3 处活实例

> 2026-10-01 03:43 起，基线 `2a0c0fea7`（R67 推送后的合并态）。
> 轮次性质：**给 R67 的教训装上机械门**。R67 抓出 4 处「上抛打到丢弃错误
> 的调用方」，但那类缺陷靠人读调用链才找得到；R68 把这个形状变成可查的门，
> 并用它扫出 3 处**当时还活着**的同类。

## 0. 为什么值得单独做这一轮

R66 的站位级守卫证明「每个 rows 循环旁都有 `rows.Err()`」；
R67 的复审证明「**分型对不对，守卫结构上无感**」。两轮下来结论很清楚：

> 静态门能保证「都做了」，**不能保证「做得对」**。

R67 那 4 处缺陷有同一个可机械识别的形状：

```go
f(...)  改成  return nil, err        //  R66 的上抛
x, _ := f(...)                        //  调用方丢弃
```

上抛的收益是零（调用方本来就不用 err），代价却是把「静默跳过一行」变成
「静默截断整体」，且对调用方**完全不可见**。这个形状值得一个门。

## 1. R68-A：用该形状扫出 3 处活实例

扫描口径：同包内被调函数在迭代终检路径上 `return ..., err`，而调用点用
`, _ :=` 丢弃。逐个回源确认，全部属实：

| | 位置 | 缺陷 |
|---|---|---|
| **E1 (P1)** | `admin/route_incidents.go:489` | `active, _ := h.store.List(...)` ⇒ DB 故障渲染成 `{"active":0,"recovering":0,"recovered_24h":0}`。**而这个端点存在的意义正是「一眼看出事件是否在被丢弃」**（见其自身注释）。在它最需要示警的时刻报出一组全零——把错误伪装成了最让人安心的结论。 |
| **E2 (P1)** | `admin/dashboardapi/session_trend.go:86` | `prevTrend, _ := ...` ⇒ 上一周期查询失败 ⇒ `prevTotal=0` ⇒ 判据不成立 ⇒ `growth_rate_pct` 停在 0 ⇒ **一次 DB 故障被渲染成「本周期增长 0%」**。0% 是看起来像实测值的结论，比缺字段更有害：运维会据此判断「业务没增长」，而真相是「不知道」。 |
| **E3 (P2)** | `admin/usage_enhanced.go:343` | `modelChanges, _ := ...` ⇒ 响应静默少一个维度 key，看不出「没查」与「查了但无变化」的差别。 |

三者的共同点值得单列：**一个错误被渲染成了一个看起来合法的零**。这比
报错更危险——零是「可行动」的数字。

### 修法

- **E1**：`storeCounters` 改为返回 `(map, error)`，失败即 503。诚实答案是
  「我不知道」，不是猜一个 0。
- **E2**：`growth_rate_pct` 是非空数值，改成可空是破坏契约的。改为**追加**
  字段 `growth_rate_known bool`（既有客户端读 `growth_rate_pct` 不受影响），
  并留 `slog.Warn`。
- **E3**：省略本身在契约内（该端点本就可能只返回模型维度），补 `slog.Warn`。

## 2. R68-B：`internal/errdiscard` 门

### 2.1 能力边界（先写清楚，否则这个门会被误信）

- **只覆盖同包调用**。跨包的 `, _ :=`（如 `h.store.List`，store 在
  `domains/routeincident`）不在覆盖内——跨包需要完整类型信息。
- **报出的是候选，不是判决**。每条都要人判断「丢弃之后结果被怎么用」：
  若调用方立刻走有文档的回退路径，那是有意决策，门会误报。
- 当前登记 2 个已知候选：`work_types`（R67 判定的承重上抛）与
  `lite_retention_worker`（假阳性——`_, _, _, err :=` 里的 `_` 是删除行数，
  `err` **有**被检查并 warn）。

### 2.2 我把这个门写成假绿三次（第四次同类错误）

三个 bug，三次都表现为「0 findings、测试全绿」：

1. **根目录被整棵树跳过**：排除规则写成 `strings.HasPrefix(name, ".")`，
   而测试传入的根是 `../..`，其 `Name()` 就是 `..` ⇒ `HasPrefix` 为真 ⇒
   `SkipDir` 掉全部。**正控（把已知缺陷改回去）下也不报**——这是我逐层拆到
   `filepath.Walk` 才定位到的。
2. **扫错了 `:=` 的边**：`a, _ := f()` 是 1 个 RHS / 2 个 LHS，`_` 在 **LHS**；
   我只扫了 RHS 里的 `_`（那是 `_, err = f()` 的形态）。
3. **终检写在 `IfStmt.Init`**：`if err := rows.Err(); err != nil` 的调用在
   `Init`（`AssignStmt`），`Cond` 只是 `err != nil`；我只查 `Cond` ⇒ 仓库里的
   主流写法一个都认不出来。

三次的共同点：**判据锚在错误的节点/边上，于是门对真实对象是瞎的，而它
自己不会报错**。

### 2.3 因此这个门自带 3 条自检

| 自检 | 钉住 |
|---|---|
| `TestErrDiscard_NoNewDiscardingCallSites` | 候选集合**恰好**是已登记的那些：多一条=新缺陷，少一条=门退化了（这正是「空集合时全绿」的解药） |
| `TestCheckDir_ScansNonTrivially` | **钉住扫描文件数 > 500**。这是把「门瞎了」与「仓库干净」分开的关键——两者在候选为空时完全同形 |
| `TestCheckDir_RelativeRootIsNotSkipped` | 相对根与绝对根的扫描量必须一致，直接复现 bug 1 |

**变异验证（三项全部按预期红→绿）**：

- 重新引入一处真实丢弃（把 E3 改回 `modelChanges, _ :=`）⇒ 主门红并指名
  `admin/usage_enhanced.go:343 calls h.queryDimensionChanges discarding its error`
- 撤掉 LHS 检查 ⇒ 两个测试红（`no longer reported`）
- 同时撤掉两道根目录保护 ⇒ `TestCheckDir_RelativeRootIsNotSkipped` 红并报
  「relative root "../.." scanned 0 files but absolute root scanned 2214」

**当前扫描量：2214 个 Go 文件，3 条候选。**

## 3. 保持开放

- E1 的 503 是**有意的契约变更**：此前该端点在 DB 故障时返回 200 + 全零。
  若有前端把「全零」当正常态渲染，改为 503 后会显示为请求失败——这是更
  诚实的失败，但仍需前端确认。
- `errdiscard` 不覆盖跨包调用。若日后要把覆盖面扩到 `h.store.X` 这类经接口
  字段的调用，需要引入类型信息（`golang.org/x/tools/go/packages`），
  成本与误报率都会显著上升，本轮不做。
- R66/R67 登记的既存红门（`autoupdate` FK、`bg` 两处夹具、`provider`、
  `TestReportRollup_HTTPContract`）本轮未动。

## 5. 本轮教训

1. **「0 findings」必须钉住扫描量才能读**。候选为空时，「门瞎了」与「仓库
   干净」在输出上**完全同形**。本轮三次假绿全部靠这条才最终暴露。
2. **判据锚错的三个高频位置**：目录根的排除规则、`:=` 的**左右边**、
   `IfStmt` 的 **Init vs Cond**。三者在 Go AST 里都是「看起来一样」的东西。
3. **正控（把已知缺陷改回去）必须真的执行**。bug 1 逃过主门正是因为我没做
   第一次正控就接受了「0 findings」；补做之后立刻定位到 `filepath.Walk`。
4. **错误被渲染成「看起来合法的零」比报错更危险**。零是「可行动」的数字，
   运维会据此下结论。这与「静默截断」是同一族，但危害更直接。
5. **跨包调用不在本门覆盖内**这条边界必须写进包注释——否则下一个人会以为
   门已经覆盖了 `h.store.X` 这类经接口字段的调用。
