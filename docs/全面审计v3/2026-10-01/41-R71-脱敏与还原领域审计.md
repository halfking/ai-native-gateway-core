## 1. 重叠敏感片段的未覆盖尾部以明文发往上游 【P1 安全】

### 事实

`security/sanitize/sanitizer.go` 的 `sanitizeInput` 过去对**重叠**片段的处理是静默跳过：

```go
for _, f := range fragments {
    if f.Start < lastEnd {
        continue          // ← 无注释、无痕迹
    }
    ...
    sb.WriteString(text[lastEnd:f.Start])
    sb.WriteString(placeholderStr)
    lastEnd = f.End
}
sb.WriteString(text[lastEnd:])
```

这段逻辑只在「后一片段完全落在前一片段内」时才是安全的。当**前一片段较短**时，超出部分的原文会经 `text[lastEnd:]` 原样进入 `SanitizedText`——也就是**发往上游 LLM 的请求体与日志**。

检测器之间互相重叠是常态：`defaultPatternEntries()` 里 `phone`（11 位）与 `id_card`（18 位）会对同一段数字串同时命中。

### 复现（修复前）

```
input : "138001380001234567"（18 位，前 11 位是合法手机号）
frag  : phone   [0,11) = "13800138000"
        id_card [0,18) = "138001380001234567"
输出 : {SENSITIVE:phone:1}1234567      ← 身份证后 7 位明文
```

另一例：19 位以 4 开头的串 → `{SENSITIVE:id_card:1}8`，银行卡末位明文。

### 为什么此前没被发现

`security/sanitize/detector_test.go:20` 早就写着注释：

> `{"id card CN", "身份证号110101199001011234", 2}, // id_card + phone substring overlap; sanitizer position-dedup handles it`

**这条注释描述的是意图，不是实现。** 那个用例恰好是「长片段在前、短片段在后」，被完全覆盖，所以看不出问题。而 `sanitizer_test.go` 的往返测试只断言 sanitize→restore 无损——**往返本来就是无损的，泄漏发生在「发给上游的那份文本」上，往返测试永远看不到**。

### 修复

新增 `mergeFragmentSpans`，在 `sanitizeInput` 内把片段整理成不重叠、并落在 `[0, len(text))` 内的区间；三件事一起做：

1. **丢弃越界/空片段**——`Detector` 是可插拔接口，第三方实现给出越界 `Start`/`End` 会让下标切片 `panic`，把一次规则误配变成请求 500。
2. **稳定排序**——`CustomDetector.Detect` 根本不排序，接口契约没保证有序。
3. **合并重叠**——同起点取跨度更大（更具体）的类型。

合并只改变「哪些字节被占位符覆盖」；因为并集区间对应原文的连续片段，**sanitize→restore 往返仍然精确**。

修复后：

```
"138001380001234567" → {SENSITIVE:id_card:1}      （往返无损）
```

### 回归测试

`security/sanitize/r71_regression_test.go`：
- `TestSanitizeInput_OverlappingFragmentsLeaveNoPlaintext`（3 个用例）
- `TestSanitizeInput_FragmentsAreDisjointAndInBounds`
- `TestSanitizeInput_OutOfRangeFragmentsDoNotPanic`（7 个 hostile 输入）

**变异验证**：把合并退回 `continue` → 报红并复现原文 `sensitive bytes leaked ... "1234567" in "{SENSITIVE:phone:1}1234567"`；把边界检查删掉 → `should not panic` 报红。

## 2. 进程级全局互斥锁把整个脱敏流程串行化 【P1 吞吐】

### 事实

`SanitizeInputMiddleware` 有一把 `stateMu sync.Mutex`，锁住的是**整个** `sanitizeRequestBody`：

```
m.stateMu.Lock()
sanitizedBody, sm, messageRefs, err := m.sanitizeRequestBody(...)
m.stateMu.Unlock()
```

被锁住的不只是 offset 状态，而是：Redis `SETNX` 取租约（**含 3 次 50ms 退避重试**）+ `HGETALL` 读 offset + **对整个请求体的正则扫描** + Lua 提交脚本。全进程共用一把锁，与会话无关。

字段注释写的是「closes the in-process read-modify-write race for concurrent requests」——**但这把锁和它想防的竞态无关**：真正的跨进程/跨请求保护是 `acquireOffsetsLock` 的 Redis 租约（同一个 Redis key 天然覆盖同进程竞争者）。而 `m.sanitizer`、`m.redis`、`m.censorSink` 全都无请求间可变状态，`worker`（`offset`/`mapping`/`usedCount`）是每次调用私有的。

### 复现

20 并发请求 + 5ms 固定耗时检测器：

```
修复前：wall = 108.8ms      （= 20 × 5ms，完美串行）
```

### 修复

换成**按 (租户, 会话) 键控**的互斥锁（`sanitizeSessionLocks`，引用计数回收条目，避免「每会话一把锁」变成内存泄漏），且**只在真存在跨请求共享状态时加锁**（`m.redis != nil && sessionID != ""`）。

同会话串行性必须保留——否则并发轮次会分配到重复的占位符编号。保留 Redis 租约的 3 次 × 50ms 重试预算不变。

```
修复后：无 Redis / 无会话 → 9.5ms；20 个不同会话 → 5.8ms
```

### 回归测试

- `TestSanitizeSessionLocks_SameKeySerializes` / `DistinctKeysRunConcurrently` / `ReleasesEntries`（原语层）
- `TestSanitizeInputMiddleware_DistinctSessionsAreNotSerialized` / `SameSessionIsSerialized`（**穿过 `Wrap()`**，测量点在检测器内部，即被锁区间之内）

> **踩坑记录**：第一版只写了原语层的 `DistinctKeysRunConcurrently`，变异验证时**没有报红**——因为缺陷在「中间件如何使用原语」，而测试锚在了原语本身。补了穿过 `Wrap()` 且测量点在锁区间内部的端到端测试后才报红。这是本项目第三次犯「判据锚错层级」。

## 3. 未识别信封的响应体原样透传内部标记 【P1 fail-closed】

### 事实（由子代理复现，我逐条复核）

`InterceptNonStream` 的守卫只覆盖三种情况：native 形态（block）、畸形 JSON（block）、chat-choices 残余（block）。**合法 JSON 但三者都不匹配的响应体**会一路落到 `return nil, nil`：

```
{"type":"error","error":{"message":"upstream rejected {SENSITIVE:phone:1}"}}   => 原样透传
{"candidates":[{"content":{"parts":[{"text":"call {SENSITIVE:phone:1}"}}]}}]     => 原样透传
{"output_text":"call {SENSITIVE:phone:1}","id":"resp_x"}                          => 原样透传
```

后果有两层：① 客户端拿到网关内部 token `{SENSITIVE:phone:1}`；② **已映射的真实值没有被还原**，该轮回答对用户等于残缺。

另外 `SessionID == ""` 时非流式**连标准 chat-choices 形态都不检查**，而流式在同情形是 block 的——两翼策略不一致。

### 修法选择

子代理建议直接 block。我改成 **mask 后透传**：

- 直接 block 会把**常规的上游错误信封**变成网关 502——那是拿一个内部 token 泄漏换一个真实的可用性事故，不划算。
- `RestoreOutputOrMask(body, sm)`：能还原的还原，不能还原的（模型伪造的）变 `[REDACTED]`，body 仍是合法 JSON，客户端拿到的形状不变。
- 仍残留标记（mask 失败 / body 非法）才 block，作为最后防线。

`SessionID == ""` 走同一路径（此时 map 加载不到，全部 `[REDACTED]`）。

### 回归测试

`TestInterceptNonStream_UnrecognizedEnvelopeNeverLeaksMarker`（5 种信封，含伪造标记）、`TestInterceptNonStream_NoSessionDoesNotLeakMarker`。
**变异验证**：撤掉 mask 分支 → 报红；撤掉无会话分支 → 报红。

### 顺带修掉的数值保真不一致 【P2】

`mustDecodeJSONMap` 的注释声称「2^53 以上的 token 数可精确往返」，但该声称只由 native 分支兑现；`restoreResponseBody` 用的是普通 `json.Unmarshal`，legacy chat 路径会把 `9007199254740993` 改写成 `9007199254740992`、把长整数改写成 `1.23e+29`。改为复用 `mustDecodeJSONMap`，一次改动同时消掉不一致。

## 4. `Match()` 双重 O(n²)：单请求 CPU 耗尽 【P1 可用性】

### 事实

**第一处**（`engine.go:126`，子代理发现）——每次命中都从 0 重算前缀字节长度：

```go
end := len([]byte(string(runes[:i+1])))   // O(i) 的完整拷贝
begin := end - len([]byte(out.Word))
```

**第二处**（`sortResults`，我在修完第一处后实测才发现）——手写 O(m²) 选择排序。

**我只修第一处就以为完事了，实测仍是精确二次**，这正是「修一半」的危险。两处一起修才真正线性。

### 实测（`configs/sensitive_words.json` 真实词表，文本 = 重复「自由」）

| body | 修复前 | 修复后 |
|---|---|---|
| 16 KB | 3.19 ms | 0.52 ms |
| 32 KB | 13.9 ms | 1.01 ms |
| 64 KB | 58.1 ms | 2.33 ms |
| 128 KB | 230 ms | 4.82 ms |
| 256 KB | **937 ms** | **10.2 ms** |

修复前 MB/s 每翻倍腰斩（5.14 / 2.36 / 1.13 / 0.57 / 0.28），修复后稳定在 ~28 MB/s。**256KB：92×**。

### 影响

`SensitiveOutputPlugin.Inspect` 对**整个** `env.UpstreamResponse` 调用 `Match`，而检测跑在**同步的 governance 路径**上。所以不需要绕过任何规则，只要让文本「很容易命中敏感词」就能放大成本——**自伤型 DoS**。并发几个大请求即可打满网关 CPU。

### 回归测试

`TestMatch_ScalingIsLinear`（32KB→64KB 比值 < 2.6；线性≈2.0，二次≈4.0）、`TestMatch_LargeBodyStaysCheap`（256KB < 300ms）。
**变异验证**：退回选择排序 → 比值 4.01 报红；退回前缀重算 → 比值 3.97、256KB 3.81s 报红。

## 5. `configPath` 数据竞争 + 假的「并发安全」注释 【P1】

### 事实

`e.configPath = path` 在**任何锁之外**执行（`BuildFromFile`），而 `ReloadFromFile`、`WatchConfig` 的轮询 goroutine、admin handler 三处并发读它。`go test -race` 证实。

更严重的是 Go 的 string 是 (ptr, len) 两个字长，非原子写，竞争下可产生 ptr/len 不匹配的字符串 → 后续 `os.ReadFile` 拿到野指针。

### 注释与实现矛盾

```go
// ReloadFromFile ... 并发安全：读取中的 Match 不受影响（写锁仅用于替换指针）。
// WatchConfig  ... 并发安全：ReloadFromFile 内部使用写锁，Match 使用读锁。
```

**写锁并未覆盖 `configPath`**，这两处并发安全声明是不成立的。

### 修复

新增独立 `cfgMu sync.RWMutex` 专门保护 `configPath`，`WatchConfig` 入口取路径的**本地快照**后再用。刻意与 `mu` 分开：`Match` 从不碰它，热加载的簿记不会和在途匹配互相争锁。

### 回归测试

`TestConcurrentReloadAndMatch_NoRace`（4 个 reload/match goroutine + WatchConfig 轮询，30 轮）。
**变异验证**：退回无锁写 → `go test -race` 立即 `WARNING: DATA RACE`。

## 6. admin 热加载作用在不拦流量的引擎实例上 【P1 静默失效】

### 事实（我亲自复核，非仅采信子代理）

进程内存在**两个独立的** `SensitiveWordEngine`：

- `cmd/gateway/main.go:5884` → 只交给 admin handler（`main.go:5894`）
- `cmd/gateway/main_pipeline.go:423` 的**局部** `swEngine` → 注册进 `secRegistry` 的输入/输出插件，**这才是真正拦流量的那个**

而 `v2Deps.SensitiveWordEngine = swEngine`（`main.go:6293`）是**死接线**：`v2DispatchMux` 内部已经执行完 `deps.Pipeline = buildV2DispatchPipeline(deps)`（`main_pipeline.go:644`）才返回，所以赋值发生在 pipeline 构建**之后**，且全仓没有任何代码读取该字段。

三处注释都在描述一个不存在的接线：
- `main_pipeline.go:292-294`：「由 buildV2DispatchPipeline 创建，main.go 从中提取并注入到 admin handler」
- `main_pipeline.go:562`：「deps.SensitiveWordEngine is now set in main.go before calling buildV2DispatchPipeline」← 直接与执行顺序矛盾
- `main.go:6290`：「Wire the sensitive word engine created above into v2Deps so the Pipeline plugins can reference it」

### 影响

运维 POST `/api/admin/sensitive-words/reload` 拿到 **200 + word_count + categories**（看起来成功），但**生效的引擎词表纹丝不动**。这是最坏的失败形态：静默的防护失效 + 虚假的操作确认。

### 修复

把引擎**显式穿过调用链**传下去，而不是靠事后赋值：

```
main.go → v2DispatchMux(..., swEngine) → newV2DispatchDepsFromMain(..., swEngine)
        → deps.SensitiveWordEngine = swEngine → buildV2DispatchPipeline(deps)
```

`buildV2DispatchPipeline` 优先用 `deps.SensitiveWordEngine`，为 nil（测试桩）时才退回自建实例。三处注释改为与实现一致。

## 7. 其余收口 【P2】

### 7.1 严重度比较方向反了

`LevelP2=0 < LevelP1=1 < LevelP0=2`（**数值越大越严重**），但两处都用 `highest := LevelP2`（最不严重）作种子、用 `if level < highest` 去找「最严重」——**条件永不成立**：

- `EvaluateSafety` 的 `Category` 恒为 `"mixed"`（300 次相同输入的分布是 `map[mixed:300]`，恒定而非随机）
- `GetHighestAlertLevel` 对 P0 命中恒返回 `P2`(PASS)

当前生产无调用方（仅测试），故按 P2 处理——但这是导出 API，任何按文档语义用它做门禁的调用方都会得到「全部安全」的错误结论。同文件 `plugin.go:81` 的 `> worst` 写法是**正确**的，三处两种写法并存正是 bug 来源。

### 7.2 空词产生零长度片段

`["政变", ""]` 里的空串会写到 root 节点的 outputs，命中时 `begin = end - 0 = end`，产出 `Begin == End` 的畸形片段（`admin/sensitive_words_handler.go` 会直接吐给 API 调用方），且 `LoadedWordCount` 虚高（3 报 3，实为 2）。在 `Build` 里跳过空白词。

### 7.3 `SanitizeStats` 分桶漏计

活实现（`compression.BuildSanitizeInfo`）的 switch 只覆盖 5 类，`internal_ip` / `name` / `custom` 全部落空——而 `internal_ip` 是真库第二大类（8856 行，占 30%）。后果是**各类型计数之和小于 `PlaceholderCount`**，一个自相矛盾的统计被持久化进 SessionState。新增 `other_count`（additive + omitempty，非破坏）并补 `default` 分支。

### 7.4 `db_sink.go` 两处

- 失败日志 `len(args)/6`，而每行是 **7** 个参数（`base := i * 7`）——只在行数是 3 的倍数时正确。改用常量 `censorEntryArgsPerRow`。
- 文件头「双写后 DB 为权威」「可逆」**与真库现实矛盾**（子代理实测）：`session_censors` 29410 行，`count(original_encrypted) = 0`（线上未配 `LLM_GATEWAY_SESSION_CENSOR_KEY`），且全仓**无任何解密读取方**。已把文件头改成事实描述并写明恢复可回溯的前置条件。**验收不要按「DB 为权威」判 PASS。**

## 8. 未修项（需方案或需产品裁决）

### 8.1 审计双写无限重复写入 【P1，本轮只出方案】

`db_sink.go` 是裸 `INSERT`，无业务唯一键、无 `ON CONFLICT`，而传入的是 `worker.mapping`（**本轮全量**而非增量）。真库实测：29410 行 vs 唯一三元组 23827，单 session 最高 **5184 行 / 3258 个唯一占位符**。

后果：① 行数随轮次平方增长；② **无法区分「本轮新增」与「历史重放」**，事后重建不出真实时间线；③ `idx_session_censors_request` 因 sink 不写 `request_id`/`turn_no` 而永远全空；④ `promote_..._hot_to_partition` 的 `ON CONFLICT (id, partition_date) DO NOTHING` 形同虚设（id 是 IDENTITY 恒不撞）。

**方案**：加 `UNIQUE (tenant_id, session_id, placeholder, partition_date)` + `ON CONFLICT DO UPDATE`，或改写增量并补 `request_id`/`turn_no`。**需要先对存量 29410 行去重，故属 migration + 运维决策，本轮不动。**

### 8.2 占位符可被用户文本伪造 【P2，风险模型受限故不提升】

输入侧不转义字面 `{SENSITIVE:`，用户写 `{SENSITIVE:phone:1}` 会被模型回显，命中即用**本会话真实值**替换。

子代理定为 P1。**我不认同这个定级**：能被替换的值只来自该用户自己同一会话的输入，跨租户已被 Redis 键 + `ParsePlaceholder` 约束；能利用的前提是已经拿到别人的 session id（那本身就是会话劫持）。真实风险是「同会话内可枚举自己的槽位」，价值很低。修法（输入侧转义或加随机 nonce）会牵动 `ParsePlaceholder` 往返与 admin 展示，属破坏性变更，留待产品裁决。

### 8.3 RLS 缺 `WITH CHECK` + 写入路径不设 GUC 【P1 潜伏】

真库 4 条策略**全部只有 `qual`(USING)、`with_check` 为空**；全仓只有 `apihub/pg_store.go` 会设 `app.current_tenant`，`db_sink` 写入路径从不设。当前网关连接角色是 `rolsuper=t AND rolbypassrls=t`，RLS 被完全绕过，**掩盖了这两个问题**。

一旦改用非 superuser 角色：① 缺 `WITH CHECK` 使租户隔离对 INSERT 失效；② 未设 GUC 时 `current_setting(...,true)` 返回 NULL，`tenant_id = NULL` 恒 false，**所有审计双写会被 RLS 静默拒绝**（每次仅一条 Warn）。

**方案**：写入前显式 `SET LOCAL app.current_tenant`，并补 `WITH CHECK` 策略。属 DB 权限模型变更，需与部署侧一并决策。

## 10. 已核对、确认无问题的部分

避免下一轮重复审计：

**`security/sensitive`**
- 字节偏移 vs rune 偏移**没有混用**（本次最被怀疑的一点）：中文实测 `恐怖主义 begin=21 end=33`，`text[Begin:End]` 精确还原原文。
- AC 自动机 fail 链构建正确；`root.fail` 从未赋值且永不读取，无空指针。
- `Match` 的读并发安全成立：自动机在锁外构建、锁内只原子替换指针，在途 `Match` 安全。
- **本包无正则**，规则来自 JSON 字面量 + AC 自动机，**无 ReDoS 面**、无包级 `MustCompile` + 全局缓冲。
- reload 失败是 fail-safe（完整解析后才换指针，旧词表继续生效）。
- 启动期词表缺失是显式设计的 fail-open（Warn 日志 + 不阻塞启动）；对内容审核层可辩护，但放大效应值得注意——建议把该 Warn 升为 Error 并接健康检查。
- P1 误报（「我想自由地呼吸」）默认配置下**不阻断**（`BlockThreshold=2`，P1→severity 1 < 2）。

**`security/sanitize`**
- 跨进程 offset 原子预占：租约 token + Lua 校验归属 + 丢租约即 fail-closed，**未发现绕过**。
- `commitSanitizeMapScript` 先全量查重（`HEXISTS`）再写入，避免复用他人占位符。
- 生产响应路径**零调用** `RestoreOutput`（全仓只有测试用），一律 `RestoreOutputOrMask`——伪造占位符必被 mask。
- 流式 `ShouldBlock` 在 chain 层真的生效（`response/chain.go` 聚合 → `handler.go` 置 blocked 只渲染一条终端帧）；`state.blocked` 一旦置位后续 chunk 全 block。
- SSE 残余探针四层（data 行外 marker / 畸形 + marker / 未改动事件 token 迭代含重复 key / 改动后 re-marshal），**未发现绕过**；转义变体 `\u007bSENSITIVE:` 有专门处理与测试覆盖。
- 租户隔离：native 路径 tenant-A/B 对照已固化；`sanitizeMapKey("")` 落 `_unknown` 桶，legacy fallback 读到的仍是**同一 `_unknown` 会话的镜像**，不跨租户。
- `PatternDetector.Detect` 的 `RLock` + 拷贝模式数组，reload 与在途匹配无竞态。
- `detector_config.go` 的 `BuildFromFile` 是「全量校验通过才替换」，配置为空/非法不会静默变成「不脱敏」——**fail-closed 语义正确**。
- `sql` 侧：`db_sink.go` 唯一 SQL 为参数化 `$N`，`fmt.Fprintf` 只写数字下标，**无注入**；单条多行 INSERT 在 PG 中原子，无半截事务；`limit=200 × 7 = 1400` 参远低于 PG 上限。
