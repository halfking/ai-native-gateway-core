# R76-b —— 真库门在 CI 上的结构性沉睡：5 道门永久在 harness 契约之外

日期：2026-10-01
范围：`sql/schema/integration_gate_test.go`（契约推导）、`scripts/audit/run-integration-gate.sh`（注入）、5 个真库门的门控变量
触发：R76 结尾自己写下的覆盖缺口——「这道 P0 门**在 CI 上不会执行**」。

---

## 0. 结论

**已修。零改 harness、零改守卫，5 道真库门从「CI 上结构性沉睡」变为「job 一接回来就会被执行」。**

R76 挖出的 P0 能潜伏至今，根因是三层遮挡叠加。本轮处理掉**第三层**：不是「CI 没跑真库门」，而是**就算 CI 跑了真库门，这 5 道门也不会被叫醒**——它们用了一个仓内契约不认的变量名。

---

## 1. 契约是怎么定义的

`sql/schema/integration_gate_test.go` 的 `TestGateInjectsEveryDBCredentialName`
**从仓内推导**注入清单，而不是手写。它两遍扫描 `_test.go`：

1. `os.Getenv` / `getenv` 的**实参**字面量；
2. 文件里含 env 查找时的**任意全大写字面量**（覆盖 slice 间接传递，如
   `internal/dbx/vacuum_mutex_test.go` 那样）。

关键在于**两遍都要过同一个 `isDBName` 后缀过滤**：

```
_DATABASE_URL / _DB_URL / _PG_URL / _ISOLATED_DB_URL
外加精确名 DATABASE_URL 与 TEST_PG_DSN
```

**任何 `_PG_DSN` 结尾的名字不在契约内** ⇒ harness 永远不会注入它 ⇒
读它的门永远 `t.Skip`。

---

## 2. 实测：5 道门在契约之外

```
domains/hooks/handoff/confirmation_pg_semantics_test.go        LLM_GATEWAY_HANDOFF_PG_DSN     ← R76 的 P0 级门
deploy/sql/verify/supplier_errors_pg_test.go                   LLM_GATEWAY_SUPPLIER_PG_DSN   ← 仓库自有
db/request_logs_view_schema_test.go                            LLM_GATEWAY_TEST_PG_DSN
db/view_schema_v2_contract_test.go                             LLM_GATEWAY_TEST_PG_DSN
domains/hooks/observability/telemetry/request_class_pg_test.go LLM_GATEWAY_TEST_PG_DSN
```

讽刺的是：第 2 个是**仓库自己早就有**的 supplier 错误真库门。也就是说这道门
从写下那天起就没进过 CI 契约，而报告里一直显示 `ok`。

**这正是该守卫自己文档里那句话的另一侧**——它写的是「只注入一部分名字会让
读该变量的 integration 文件全部 skip 而门禁仍显示绿」（读取侧漏注入）。
本轮是**注入侧漏掉**：名字压根不在清单里，守卫连「该注入」都不会要求。
守卫没有洞——它的 `isDBName` 过滤是设计如此；漏的是**门的作者没遵守契约**。

---

## 3. 修法：改门，不改 harness

五个文件全部改为**优先读 `TEST_PG_DSN`**（本就在注入清单、且受守卫强制），
旧名保留为回退以兼容手工运行。**harness 与守卫一行未改**，
`TestGateInjectsEveryDBCredentialName` 仍绿（15 个名字不变，因为
`TEST_PG_DSN` 早就被 `internal/dbx/vacuum_mutex_test.go` 读着）。

在每个 resolver 上写了「为什么是这个名字」，避免下一个人以「更明确」为由
再改回去。

---

## 4. 验证

```
go build ./...                                     exit 0
go vet ./db/ ./deploy/sql/verify/ ./domains/hooks/handoff/ ./domains/hooks/observability/telemetry/   exit 0
gofmt -l <5 个改动文件>                             空

契约名生效（门真正执行，不是 skip）：
  TEST_PG_DSN=<本机 DSN> go test ./deploy/sql/verify/ -run TestVendorRecentFailuresSQL -v
      PASS 2/2 子测试
  TEST_PG_DSN=<本机 DSN> go test ./domains/hooks/handoff/ -run TestPGStoreSavePendingSemantics -v
      PASS 3/3 子测试

旧名仍可手工运行（向后兼容）：
  LLM_GATEWAY_SUPPLIER_PG_DSN=…  → ok
  LLM_GATEWAY_HANDOFF_PG_DSN=…   → ok

无 DSN 时干净 skip（不误报绿）：
  ./deploy/sql/verify/ ./domains/hooks/handoff/ ./db/ ./domains/hooks/observability/telemetry/   全 ok

契约守卫：
  TestGateInjectsEveryDBCredentialName   PASS（15 个名字不变）
  TestWorkflowDoesNotShipAnUnrunnableGateJob   PASS
```

**变异验证不适用于本项**：本项是「变量名与仓内契约对齐」，没有可改坏的生产代码
分支。可验证的是**覆盖真的变宽了**——`TEST_PG_DSN` 存在时两道门从 skip 转为
PASS（上文第 2 段实测），这正是本项要达成的状态变化。

## 5. 对既有自我审计的一处订正

`docs/audit/2026-10-01-integration-gate-ci-preconditions.md`（round 43 留下，
今天早些时候）列了 5 条「重新接入前必须逐条落实」。**它漏了第 6 条，且这一条比
前 5 条更早生效**：门不在契约内时，job 就算原样接回来，这 5 道门仍然沉睡。
已在该文档末尾补记，并把它作为前置条件清单的提醒写明。

该文档记录的三个必败原因（镜像 tag 不存在 / 架构不匹配 / 缺 `PG_PASSWORD`）
本轮**未复核**——它们属于 job 编排层，需要在有 registry 访问权的环境里验证，
本机（arm64）无法证伪 x64 runner 上的镜像可用性。状态行
`ci-gate-preconditions: NOT-SATISFIED` **保持不变**，未擅自改成 `SATISFIED`。

---

## 6. 能力边界

- **本轮没有让任何门真的在 CI 上跑起来。** 只做到了「job 一旦按其前置条件接回
  回来，这些门就会被执行」。真正接回 job 仍卡在镜像 tag / 架构 / 密码三项，
  属既有文档登记的未完成项，未擅自改状态行。
- **harness 会往 `TEST_PG_DSN` 注入一个 disposable 库的 DSN**（一次性 database，
  非 schema）。5 道门在该库上能否自举 schema 取决于各自实现：
  - R76 的门会 `t.Skip`（表不存在）——**这是正确的诚实行为**，不是覆盖；
  - `supplier_errors_pg_test.go` 会自己建 schema（它有 bootstrap）；
  - `db/` 的两个门自己建 scratch database。
  即 job 接回后首跑仍可能出现「部分门 skip」，届时需按包补 schema 自举。
  **本轮无法验证这一点**（需要那个一次性库），如实登记为未知。
- `sql/schema/integration_gate_test.go` 与 `run-integration-gate.sh` **本轮未改**。
