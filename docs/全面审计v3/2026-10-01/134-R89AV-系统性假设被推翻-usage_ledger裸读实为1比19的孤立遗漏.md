# 134 号｜R89-AV：**「这是一类查询的共同失误」这个假设被数据推翻** —— 实际是 **1/19** 的孤立遗漏

- 日期：2026-10-01
- 轮次：R89-AV
- 起因：133 号发现 `budgetCheck` 读裸父表 `usage_ledger` 而丢掉最近 8 小时的 hot 数据。
  **本轮的假设是：这不是一个查询的失误，很可能是一类查询的共同失误。**
- 结论先行：
  1. **假设被推翻。** `usage_ledger` 的生产读点共 **19 处**，其中 **18 处用的是视图**
     `usage_ledger_with_current_month`（含 hot），**只有 `admin/keys.go:973` 一处用裸父表**。
  2. ⇒ **133 号缺陷 A 的影响面被限定为 1/19**；且 **18/19 已经是对的**，
     **这反而强化了 133 号的定性**（孤立遗漏，不是有意设计），修法就是「与另外 18 处保持一致」。
  3. **本轮结论是「没有发现新缺陷」** —— 这本身是一条有价值的交付：
     **它把爆炸半径钉死了**，让 52 号那条从「可能有一片」变成「只有一处」。
  4. `request_logs` 族的裸读点逐个定性后，**同样没有第二个高危点**，但留 3 处**待核实**。

## 一、主假设与它的证伪

### 1.1 假设

133 号的形态很有「系统性」的味道：`_hot` 是独立表、父表不含它、而代码里存在裸读父表的写法
⇒ **同一类错误很可能在别处也犯过。**

### 1.2 计数

```bash
$ grep -rnoE "(FROM|JOIN)[[:space:]]+usage_ledger(_with_current_month)?[[:space:]]" \
    --include=*.go . | grep -v vendor | grep -v _test.go
```

| 读法 | 处数 |
|---|---|
| `FROM usage_ledger_with_current_month`（**含 hot**） | **18** |
| `FROM usage_ledger`（裸父表，**不含 hot**） | **1** —— `admin/keys.go:973` |

分布明细（18 处视图）：

```
admin/usage.go:335,356,450,470,559,577,665,682,790,879,1171,1301   (12)
admin/usage_enhanced.go:97,396,437,445,541                          (5)
admin/usage_provider_detail.go:99,234                              (2)  ← 合并计数
domains/authentication/verifier.go:786                              (1)  ← 认证路径
```

⇒ **假设不成立：1/19。**

### 1.3 这个「推翻」为什么是有价值的交付，而不是白做

- **对修复方**：修 `keys.go:973` **一处即可**，不存在遗漏的兄弟站点。
  **这直接改变了工作量的量级估计**（1 行 vs 「需要全仓排查」）。
- **对定性**：18/19 已经用视图 ⇒ **这不是一种被接受的约定**，
  而是**某一次写这段代码时漏了**。⇒ 133 号「孤立遗漏、不是有意设计」的定性**被数据支持**。
- **对审计方法**：133 号的报告里出现过「可能是一类问题」的暗示，
  **本轮把这个暗示收窄成事实**，避免读者按错误的量级去做决策。

## 二、`request_logs` 族裸读点的逐个定性（**不能批量报**）

初筛出多个 `FROM request_logs`（裸父表）位置。**逐个读包围上下文后，没有第二个高危点**：

| 位置 | 性质 | 结论 |
|---|---|---|
| `admin/request_trace.go:190-192` | **hot ∪ 父表双腿**：`SELECT … FROM request_logs_hot WHERE request_id=$1` **UNION ALL** `SELECT … FROM request_logs WHERE request_id=$1` | ✅ **正确**。这正是本仓既有的「hot∪母表」读法 |
| `domains/analysis/optimizer.go:195-196` | 相关子查询 `SELECT SUM(cache_read_tokens) FROM request_logs WHERE gw_session_id=…` / `COUNT(… compression_strategy …)` | ⚠️ **待核实**：读不到最近 8h ⇒ 近 8 小时的会话其压缩统计可能漏计 |
| `autoroute/recommend_v2.go:399,546` | 推荐引擎从 `request_logs` 取历史 | ⚠️ **待核实**：推荐基于**至多 8 小时前的数据**；是否有意（本就要历史）需读设计文档 |
| `admin/memora_handlers.go:615` | `(SELECT client_model FROM request_logs … ORDER BY ts DESC LIMIT 1)` 取最近一次请求的模型 | ⚠️ **P3**：取到的是**最近一次「已 promote」**的请求而非真正的最近一次；仅作为 memora 提示，影响轻微 |
| `bg/opslog_trimmer.go` / `admin/data_lifecycle*.go` / `bg/lite_retention_worker.go` | 裁剪/生命周期作业 | ✅ **正确**：**不该**裁剪尚未 promote 的 hot 行，读父表是设计要求 |

⇒ **运维类读父表是对的**——若这里「修」成读视图，反而会破坏裁剪语义。
**这与 114/120 号「零导入包必须逐包读原文、不得批量处理」是同一条纪律的另一个面：
同样规模的「同一现象」里，有的是缺陷，有的是正确设计。**

## 三、playbook §31（本轮新增）

**发现一个缺陷后，「这可能是一类问题」的直觉要保留——但必须真的去数，数的结论可能把它收窄成个案。**

**规则**：当某个缺陷的形态**看起来像系统性**（同一张表 / 同一个视图约定 / 同一个易错写法）时，
**下一步不是写进报告，而是去数同类站点**：

```bash
# 数「对的写法」与「错的写法」各多少
grep -rnoE "(FROM|JOIN)[[:space:]]+<table>(_<view>)?[[:space:]]" \
  --include=*.go . | grep -v vendor | grep -v _test.go
```

- **错的只有 1~2 处** ⇒ 收窄为**孤立遗漏**，修法就是「与其它 N−1 处保持一致」，
  **工作量与风险都大幅下降**；
- **错的很多** ⇒ 才成立为「一类问题」，需要系统性修法。

⚠️ **反过来同样危险**：把「1/19」写成「一类查询的共同失误」，
会让修复方以为要全仓排查，**或让读者以为影响面远大于实际**。

**本轮证据**：主假设「这是一类查询的共同失误」⇒ 数完是 **1/19，假设被推翻**。
**这与 §30 是对偶的两条**：
- §30：**不要只验一条腿就宣布结论**（别过早收窄为个案）；
- §31：**不要不数就宣布是系统性的**（别过早放大为系统问题）。
⇒ **两条合起来就是「先数，再定性」**。

**同族**：§20（共享片段让 grep 失效）、§22（零导入是相对量）、
[[计数类结论：口径必须和数字一起发布]]。
**共同点：全都是「数量本身会改变结论的严重性」——
而数量最容易被想象代替（本条）、被过期引用（§22）、或被口径污染（§20）。**
