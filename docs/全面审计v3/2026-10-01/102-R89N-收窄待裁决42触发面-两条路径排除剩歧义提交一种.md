## 0. 一句话

100 号说「重复计费未证」是因为当时手里有**两条**候选触发路径，无法区分。
本轮把其中一条证伪、把另一条压缩到**只剩一种情形**：

## 1. 触发路径 (a)：`RowsAffected==0` 回落导致双重累加 —— **证伪**

子代理 1（F1）给的触发条件 (a)：
「`updateRequestLog` 的 `RowsAffected==0` 回落到 `insertRequestLog`，
而该 entry `Success=true` ⇒ 同一次请求的费用在两个事务里各加一次」。

**这个论证是错的。** `domains/hooks/observability/telemetry/client.go:2428-2446`：

```go
if updated.RowsAffected() == 0 {
    var exists bool
    if err := tx.QueryRow(ctx, `SELECT EXISTS (SELECT 1 FROM request_logs_hot WHERE request_id = $1)`, ...)
    if rbErr := tx.Rollback(ctx); rbErr != nil { ... }
    if exists { return nil }
    fallback := *entry
    fallback.Op = RequestLogInsert
    return c.insertRequestLog(&fallback)
}
```

**回落前有一次显式的 `tx.Rollback(ctx)`。**
而 `usage_ledger_hot` 的两次 UPDATE（`:2066`、`:2095`）与 `api_keys` 的加法累加
（`:2460+`）**都在这同一个事务内**——`updateRequestLog` 起点 `:2040`，
事务开启 `:2050`，全程一个 `tx`（`defer tx.Rollback` 于 `:2055`）。

**⇒ 第一次尝试的全部写入被原子丢弃，才轮到 `insertRequestLog` 接手。
不存在「两个事务各加一次」。** 触发路径 (a) **证伪**。

> 顺带记一句正面结论：**这段代码的防护是对的**，是本仓少见的正确处理。
> 它恰好是 §1.7 里 `api_keys` 累加器**没有**的那种防护。

## 2. 触发路径 (b)：degraded / fallback / replay —— **压缩到只剩一种情形**

`persistRequestLog`（`:1131`）的两条出口是**互斥**的：

```go
if c.degraded.Load() {
    return c.fallback.WriteRequestLog(ctx, entry.RequestID+":"+string(entry.Op), entry)  // :1147 只写文件，不碰 PG
}
... else { insertRequestLog / updateRequestLog }                                          // 只碰 PG，不写文件
```

**同一时刻不会既写 PG 又写文件。** 所以「一次调用双写」不成立。

真正的问题在调用方 `:871-877` 与 `:1008-1014`：
**`persistRequestLog` 返回 error 时，调用方会写 fallback 文件**，
稍后由 `ReplayFallback`（`:725-747`）再走一次 PG 写入。

**⇒ 唯一能造成「PG 一行 + fallback 一行」的路径是：`persistRequestLog` 返回了 error，
但那次写其实已经生效。** 而这只在一种情况下发生：

**`tx.Commit(ctx)` 的结果未知（连接在提交过程中断开）。**

**我复核了为什么没有别的口子**：`insertRequestLog` 以 `return tx.Commit(ctx)`（`:1887`）
结束、`updateRequestLog` 以 `return tx.Commit(ctx)`（`:2507`）结束——
**commit 是这两个函数的最后一条语句，其后没有任何能返回 error 的代码**
（`firePersistedHooks` / `releaseBodies` 等收尾都在 `persistRequestLog` 侧，
且只在 `err == nil` 时执行）。所以「已提交但函数返回错误」**不可能**由逻辑错误造成，
**只能**由提交本身结果未知造成。

## 3. 收窄后的结论

| | 状态 |
|---|---|
| 触发路径 (a) RowsAffected 回落双加 | ❌ **证伪**（显式 Rollback 原子丢弃） |
| 触发路径 (b) degraded 期间双写 | ❌ **证伪**（同一时刻 PG 与 fallback 互斥） |
| 触发路径 (c) 逻辑错误导致的「已提交却报错」 | ❌ **证伪**（commit 是最后一条语句） |
| **触发路径 (d) COMMIT 结果未知（歧义提交）** | ✅ **唯一剩余** |

**这一条对 100 号结论的影响，如实说清楚：**

- **缺陷本身不变**：`usage_ledger_hot` 的唯一键含 `now()`、INSERT 无 `ON CONFLICT`
  （100 号 §1.1/§1.2），这个**已证事实不受影响**，待裁决 42 仍然成立。
- **发生概率显著下降**：从「可能时常发生」收窄为「仅在提交结果未知时发生」。
  对单机/同宿主 PG 而言这是罕见事件。
- **但一旦发生，后果是「非对称」的**，这才是本条真正值钱的地方：

| 表 | 重复提交时的行为 |
|---|---|
| `request_logs_hot` | `ON CONFLICT (request_id) DO UPDATE` ⇒ **自愈**，仍一行 |
| `usage_ledger_hot` | 无 `ON CONFLICT` ⇒ **多一行** |
| `api_keys.total_cost_usd` | 加法累加无幂等 ⇒ **翻倍** |

**⇒ 同一个故障事件，在三张表上留下三种不同的后果：一张自愈、一张多行、一张翻倍。**
**这正是「缺陷成立但难以观测」的原因**——宽表看着正常，台账悄悄多行，预算读数悄悄偏大。

**仍需真实环境才能闭合的一点**：歧义提交在本环境的实际发生率。
这不是代码能回答的，需要 PG 侧连接中断统计或上游网络指标。**维持「未闭合」，但缺口已从
「三条宽路径任一」缩到「单一罕见事件」。**
