## 1. §2 供应商对账：3 条 P1 复核结果

### 1.1 F1「两侧口径不守恒」——**我下调为 P3，并推翻其措辞**

子代理原话：「网关侧把未计费失败 attempt 计入 `gateway_total_cost`，内部侧不收租户钱
⇒ **两侧金额天然不等**」。

**我复核后认为这个论证是错的。**

- 子代理引用的 `domains/maas/consumption_detail.go:87` **路径错了一层**——
  实际是顶层包 `maas/consumption_detail.go`（`domains/maas/` 目录不存在）。
  实质内容属实：`:87` 确有 `AND <alias>.credits_charged IS NOT NULL`。
- **但论证本身站不住**：对账侧问的是「**欠供应商多少钱**」，
  maas 侧问的是「**向租户收多少钱**」。
  **这两个数本来就不该相等**——租户不付钱的失败请求，供应商可能同样不收钱。
  把两者的差额称作「不守恒」是把两个不同量纲的数放在一起比。

**降级理由**：真实残留问题只是「失败请求进了对账侧」，
它**叠加放大** F2（本地估算单价）与 F3（缓存 token 口径）的偏差，
本身不构成独立缺陷。**P1 → P3，从独立条目并入 F2/F3。**

> **教训**：「两侧算出来不一样」是**信号**，不是缺陷。
> 下单独立一条之前必须先问「这两侧量的本来就不是同一个东西吗」。

### 1.2 F4「provider=0 静默归零致大额漏账不可见」——**意图属实，但缺陷不是它说的那个**

子代理原话：`provider == 0` 时 `ComputeDiffRate` 返回 0，不触发告警 ⇒ 大额漏账不可见。

**我复核后：不告警是写明的意图，但缺陷比它说的更根本。**

`domains/providerprofile/reconciliation.go:15-20`（含注释）：

```go
// provider 为 0 时分母无意义，返回 0（调用方以"未定义差异"处理，
// 不触发告警）。
func ComputeDiffRate(gateway, provider float64) float64 {
	if provider == 0 { return 0 }
	...
}
```

**意图是「标记为未定义」——但实现把三态压成了两态：**

| 环节 | 代码 | 发生了什么 |
|---|---|---|
| 计算 | `ComputeDiffRate` 返回 `0` | 「未定义」与「真实 0% 差异」**在返回值上不可区分** |
| 落库 | `pg_reconciliation_store.go:319-324` `nullDiffRate(f)`：`if f == 0 { return nil }` | 「未定义」与「真实 0%」**双双写成 NULL** |
| 读回 | `:152-153` `COALESCE(token_diff_rate, 0), COALESCE(cost_diff_rate, 0)` | NULL 被**抹平成 0**，「未定义」标记**彻底丢失** |

**⇒ 真正的缺陷是：一条本该保留「未定义」语义的状态，在计算的返回值、落库、读回三处各丢一次，
最终在 UI 上与「差异 0%」完全同形。**
子代理说的「不告警」只是这个丢失的**下游后果**，不是根因。

**定级 P2。** 修法方向：用一个显式哨兵值（而非 0/NULL）表示未定义，且**读回路径不得 COALESCE 成 0**。

> **同族教训（值得单独记）**：把「未定义」编码进 `0` 或 `NULL`，
> 会在每个下游环节与真实值坍缩。用**枚举/哨兵**而不是「特殊数值」。

### 1.3 F5「`numeric(5,4)` 溢出中断整月」——**成立，维持 P2**

两条都复核为实：

- 列型 `sql/objects/tables/provider_cost_reconciliation.sql:17-18`：
  `token_diff_rate numeric(5,4)` / `cost_diff_rate numeric(5,4)` ⇒ **上界 9.9999**。
- `ComputeDiffRate` 的 `roundTo`（`reconciliation.go:23-31`）**不夹取**。
- **关键的一环也成立**：`AggregateMonth`（`reconciliation.go:189-201`）逐条循环，
  `SaveRecord` 一旦出错**立即 `return`**：

```go
if err := r.store.SaveRecord(ctx, rec); err != nil {
    return fmt.Errorf("save reconciliation record: %w", err)
}
```

⇒ **单个供应商的差异率溢出，会让当月其余供应商全部不再刷新 diff、也不再告警**，
且 `bg/cost_reconciliation_worker.go` 每日重跑时会在同一位置再次失败 ⇒ **整月对账静默停摆**。
**P2 确认。** 这是典型的「单行坏数据阻塞整批」健壮性缺陷。

## 2. §3 租户隔离：根因成立，两处「不可达」经双方法确认

### 2.1 根因「中间件不注入 tenant，隔离纯靠约定」——**成立，已复核**（本轮最高价值）

子代理原话：`AdminMiddleware` 只 `SetAuthContext`，不做 SQL 改写、不设连接 GUC
⇒ 漏写不会报错、不会被任何测试捕获。

**我读了 `admin/auth.go:76-140` 的 `AdminMiddleware` 函数体，确认属实**：
它做的是 token 提取 → JWT/会话校验 → `SetAuthContext(r, &AuthContext{...TenantID, Role...})`。
**没有 `SET`/`set_config`、没有 GUC、没有 SQL 改写、没有按租户包事务。**

**⇒ 租户隔离的成败，完全取决于每个 handler 是否「记得」调用
`GetTenantID(r)` / `EffectiveTenantID(r)` / `statsTenantScope(r)` 这类 helper。
漏掉一次 = 静默的跨租户读，无编译期错误、无运行期告警、无测试覆盖。**

**这条比任何单点缺陷都重要**，因为它解释了为什么 94 号能漏一个、
本轮又能找到两个同形态的**死代码**里也带着同样的漏。
若不修机制，下一个漏的迟早会出现在活路由上。

**定级 P1（结构性）。** 建议方向：
① 收敛到**单一**作用域构造 helper（仓内已有 5 个语义相近的：
`boardMinuteWhere`/`boardLogsWhere`/`scopedDimensionWhere`/`appendTimeseriesFilters`/`statsWhere`，
它们降低了漏写概率但仍是运行时约定）；
② 或对 `request_logs*`/`usage_ledger*` 启用 **RLS + 连接池统一 `SET LOCAL app.tenant_id`**
（`admin/session_analytics_handler.go` 的 `withTenantTx` 已有此形态，可作样板）。

### 2.2 两处「不可达」——**两种检索方式均确认**

| 文件 | 方法 A（符号引用，排除自身定义） | 方法 B（路由路径注册） | 判定 |
|---|---|---|---|
| `admin/top_problems.go` | `handleTopProblems` 外部命中 3 处，**全部是 `top_problems_test.go`** | `/api/logs/top-problems` 仅出现在注释与测试，**无 `mux.HandleFunc`** | ✅ **不可达** |
| `admin/model_status.go` | `RegisterModelStatusRoutes` **零调用点**；`handleModelStatus` 零调用点 | `model_status.go:323` 有 `mux.HandleFunc`，但它**在一个从不被调用的函数体内** ⇒ 永不执行 | ✅ **不可达** |

子代理这两条**结论正确**。补充一点它没说透的：
`model_status.go` 的注册代码**确实存在**（`:321-323`），
不可达的原因是**它的注册函数没人调用**——这比「压根没写注册」更隐蔽，
将来有人「顺手把 `RegisterModelStatusRoutes()` 加进 `RegisterRoutes`」就会立刻变成活路由越权读。
**维持 P2（补注册即触发），但补注册时必须同时补 tenant 过滤。**
