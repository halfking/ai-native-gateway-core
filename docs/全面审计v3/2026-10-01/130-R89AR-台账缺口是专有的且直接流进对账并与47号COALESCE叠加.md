## 二、为什么台账失败不会「顺带」暴露

两个写方都**直接写 `usage_ledger_hot`、都在自己的事务里**
（`admin/telemetry.go:405-407` 可见 `defer tx.Rollback()` 紧邻其 INSERT）
⇒ **台账事务与 `request_logs` 事务是分开的**。

这正好解释了上表：**台账写失败时，回滚只影响台账那一个事务**，
`request_logs` 与 `routing_decision_log` 照常写入。

⇒ **【结构事实】一次持续 7 天、覆盖 25 万请求的台账完全停写，
在可见的遥测管线里不产生任何报错、告警或缺行痕迹。**
唯一能发现它的方式，是拿台账去和 `request_logs` 对数——**而没人写这个对账**。
**「表里有行」与「表里该有的行都在」是两回事，后者没有任何机制在守。**

## 四、⚠️ 本轮最重要的发现：缺口**直接流进对账**，且与待裁决 47 叠加

`domains/providerprofile/pg_reconciliation_store.go:195-210`
`PGGatewayMonthlyUsageSource.MonthlyUsageByProvider` 的数据源就是它：

```sql
WITH deduped AS (
    SELECT DISTINCT ON (request_id) provider_id, prompt_tokens,
           completion_tokens, total_tokens, cost_usd
    FROM usage_ledger_with_current_month
    WHERE ts >= $1 AND ts < $2 AND provider_id IS NOT NULL
    ORDER BY request_id, ts DESC
)
SELECT provider_id,
       COALESCE(sum(prompt_tokens), 0), COALESCE(sum(completion_tokens), 0),
       COALESCE(sum(total_tokens), 0), COALESCE(sum(cost_usd), 0)
FROM deduped GROUP BY provider_id ORDER BY provider_id
```

⇒ **2026-09 的网关侧对账，就是拿这张有 7 天空洞的表算出来的。**

而这个查询的输出侧还有已知的三重混淆（均已登记）：

| 混淆来源 | 登记处 | 效果 |
|---|---|---|
| **行整体缺失**（129 号：09-03/04、09-07~09-11 = 0） | 本报告 | 总量被低估 |
| **`cost_usd` 为 NULL 被 `COALESCE(...,0)` 编码成 0 成本** | 待裁决 47 | 有行但成本被记为 0 |
| **`cost_usd` 本身四义混同**（无定价 / 未计算 / 真实 / 负数） | 待裁决 46 | 0 究竟是哪种 0 无法回溯 |
| （另有）`CalcCost` 对 Anthropic 形状算出**负金额** | 待裁决 45 | 拉低合计 |

⇒ **这四种原因在 `sum(cost_usd)` 之后指向同一个数字。**
⇒ **对 2026-09 而言，此前实测到的那个「自信的 −95% 差异率」，
其成分里必然包含「网关侧压根没有这些行」，而不是纯粹的供应商价差。**

**这不是「数据不完整导致结论偏了一点」，而是「结论的差异项里混进了缺失量」——
两者在报告上无法区分。** 直接命中 objective 的「费用计帐及与供应商进行对帐」。

### 建议（登记为待裁决，**不擅自动手**）

对账在比较之前应先断言**覆盖前提**，而不是直接比数字。最小可行形态：

1. **覆盖率前置断言**：同窗口内 `count(usage_ledger)` 与 `count(request_logs)`（按月）之比
   低于阈值（建议 0.98）时，**不出差异率**，改出「数据不完整」这一**独立状态**；
2. 该状态**必须能在 UI/接口上被单独看到**，而不是让一个数字把它吃掉
   —— 呼应本会话反复命中的「『未定义』不可编码进 0/NULL」（已在 4 处发现）。
