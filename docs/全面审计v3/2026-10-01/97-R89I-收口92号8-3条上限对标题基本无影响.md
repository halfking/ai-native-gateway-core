# 97-R89-i：收口 92 号 §8 —— 「preview 只取前 3 条消息」对标题**基本不构成影响**

- 轮次：R89-i
- HEAD 基线：`957083acd`
- 触发：92 号 §8「未量化 `summarizeMessagesContainer` 只取前 3 条消息对标题质量的影响」
- 结论：**该担忧在标题场景下基本不成立**（标题只由首轮请求生成，首轮的 user 段落在 3 条上限内）
- 改动：**零生产代码、零配置、零门**

## 1. 原始担忧（92 号 §8 第 2 条）

> `summarizeMessagesContainer`（`domains/streaming/telemetry_summary.go:119-153`）
> **只取前 3 条消息**（`:148-150` `if len(parts) >= 3 { break }`，每条再截 120 字符）。
> 长会话的**第 4 轮及以后对话在 preview 里根本不存在**——这可能是一条独立的可观测性局限，未量化。

## 2. 为什么它在标题场景下基本不成立

**关键前提：标题只由「首轮成功请求」生成。**
`admin/auto_title_generator.go:108` 有硬闸门：
```go
if strings.TrimSpace(sessionID) == "" || !g.isFirstSuccessfulUserTurn(sessionID, tenantID, requestID) {
    return
}
```
⇒ 用于建标题的 preview / corpus 取自**该会话的第一个请求**。

而一个会话的**首轮请求**通常就是 `system + user`（1-2 条消息），
其 user 段**落在 3 条上限内** ⇒ 「第 4 轮及以后不在 preview 里」这一条，
**对「用首轮建标题」的场景不构成影响**。

（对照：若将来标题改为基于第 N 轮或全轮对话生成，本条才会成立——与 96 号 §3 的边界说明同型。）

## 3. 如实登记：真库量化**未能取得可信数字**（不引用错误数）

我尝试用 `session_titles ⋈ request_logs`（`task_id = gw_task_id`）统计
「auto-extract 回退的 preview 中有多少带出 `| user:` 段」。**查询返回了明显不可信的数字**：
`sampled` 计数达 **2.75 亿**，而 `request_logs_2026_09` 整表仅 **215 万行**——
join 结果超过表规模，**数学上不可能**。这与 92 号 §5.1 记录的
「该表 Citus columnar 上 `IN (SELECT unnest(...))` 的 `LIMIT` 失效、计数不可复现」同源。

⇒ **该数字不采信、不写入结论。** 本条的关闭**基于代码事实 + 推理**（§2），
**不是**基于真库统计。**真库侧这条局限（columnar join 计数不可复现）另记为环境事实**，
后续若必须量化，需先解决该 join 的可复现性。

## 4. 结论

- 代码事实成立：`summarizeMessagesContainer` 确实只取 3 条（`:148-150`）。
- 但标题只由首轮请求生成，首轮 user 段在 3 条内 ⇒ **对标题质量基本无影响，不是缺陷**。
- 真库量化因 Citus columnar join 计数不可复现而**未完成**，本条不以该数字为据。
