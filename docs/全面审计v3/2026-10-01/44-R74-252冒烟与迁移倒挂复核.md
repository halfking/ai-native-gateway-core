### 2.2 部署 639cf8aba → 连续三轮 `postgres disabled`

`deploy-252-gateway.sh` 构建干净树（`vcs.modified=false`）部署后，**连续三轮启动在 `ensure candidate_failure_logs heap partitions` 步骤超时**（`timeout: context deadline exceeded`，attempt 1/2 各约 3 分钟），10 分钟 boot 预算耗尽 → `postgres disabled` → admin 路由未注册（三分布 404 "page not found"、tenants stats 503 "database not configured"）。三次重启稳定复现，非偶发锁竞争。

### 2.3 根因链（逐环实证）

1. **导火索**：`candidate_failure_logs_2026_10` 分区为 **columnar**（64 kB、0 行）。689 的 ensure 每次启动发现它即走 DETACH→重建→拷回全套 DDL。
2. **放大器**：252 共享库装有 event trigger `enforce_columnar_trigger`（`ddl_command_end` on `CREATE TABLE/ALTER TABLE`，来自 phase-23 columnar-invariant 体系）。它对 `columnar_insert_only_parents()` 注册表的**每个 parent 全量** heap→columnar 强转。**注册表含 25 个家族**，其中 `candidate_failure_logs`、`request_logs`、`request_wal`、`usage_ledger` 均在册。
3. **拉锯**：689 ensure 的任何 DDL → trigger 对 session_bodies（144 MB 真数据）/session_turns/session_turn_details/usage_facts 等家族逐分区 `ALTER TABLE ... SET ACCESS METHOD columnar`（每分区一条、串行拷数据）→ 3 分钟 ctx 预算内永远完不成 → boot 失败。**实验性 DETACH 实测**：一次手工 DETACH 触发 trigger 连环转换 13 个分区（bodies×3、turns×5、turn_details×2、usage_facts×4，其中 `session_bodies_2026_09` 转换 **out of memory** 失败）——该实验事务已**立即 pg_cancel_backend 回滚**，事后逐分区核对全部还原 heap（残留 columnar 的 bodies_2026_07/2026_10/default、turns_default 经核对**不在**本次 NOTICE 清单内，属 trigger 更早时点的既存状态）。
4. **为什么以前没炸**：09-30 旧进程启动时 `candidate_failure_logs_2026_10` 尚不存在（10 月分区）；10-01 零点后分区被建/转 columnar，导火索才出现。**154/245/kaixuan-1 连同一共享库，任何实例下次重启都会踩同一雷。**

### 2.4 修复（252 库侧，幂等，方向=恢复 689/01-schema 明文语义）

1. **注册表除名 4 家族**（`columnar_insert_only_parents()` 重写为 21 元素）：`candidate_failure_logs`（689 已确立 heap 语义：TTL DELETE/promote 需要 UPDATE/DELETE）；`request_logs`/`request_wal`/`usage_ledger`（仓库 `01-schema.sql` 的 `columnar_healthcheck` should_be_heap 白名单明列三家——它们需要 UPDATE/DELETE 与 764 索引的 Index Only Scan）。
2. **12 个 columnar 分区保数据转回 heap**（689 同款：DETACH→bak→同界重建→拷回→行数守恒校验→DROP bak）。守恒账：`request_logs_2026_09`=2206 行、`request_wal_2026_09`=445987 行、`usage_ledger_2026_09`=1414671 行，其余 9 个分区 0 行，全部 src=dst。副作用修复：764 的 `(tenant_id, ts DESC)` 索引在 heap 分区上恢复 IOS 可用性（R36 的 6.5s→0.379ms 性能修复被 trigger columnar 化无声废掉，本轮恢复）。
3. **trigger 窗口纪律**：全部分两段执行，每段 `DISABLE → 操作 → 立即 ENABLE`，窗口各 <10 分钟，事后核对 `evtenabled='O'`。禁用窗口内其他实例的新分区保持 heap（保守方向，无数据风险；trigger 恢复后任意 DDL 会补转）。
