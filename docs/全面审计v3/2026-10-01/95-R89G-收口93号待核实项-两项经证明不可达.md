## 1. §8.1 关闭：`applyThinkingToOpenAIChat` 与 paramguard **结构互斥**，账本 `Original` 语义错位不可达

### 1.1 待核实的原始担忧（93 号 §8.1）

> `applyThinkingToOpenAIChat`（`internal/ir/serialize_openai.go:278`）会经 `reasonnorm.Render`
> 写出 `reasoning_effort`，**绕过 paramguard 且不产生 Report**。若它先于 paramguard 执行，
> 账本里的 `Original` 记的是 **IR 渲染后的值**而非客户端原值 ⇒ 还原链语义错位。
> **本轮未能确认它与 paramguard 的实际执行先后。**

### 1.2 三条独立的闭合证据（任一条单独都不够，三条叠加才闭合）

**证据 A —— 执行序：paramguard 在 IR 序列化之前，不是之后。**

`finalizeOpenAIUpstreamBody`（`executor_chat.go:2015`）内部顺序：

| 顺序 | 行号 | 动作 |
|---|---|---|
| ① | `:2153` `prepareRequestBody(&p, cand, e.ParamLedger)` | 内含 `applyGuardToLedger`（**paramguard**）——作用在**原始客户端 body** 上 |
| ② | `:2170` `irScoped.ParseOpenAI(bodyBytes)` | 解析进 IR |
| ③ | `:2193` `irScoped.SerializeOpenAI(irReq)` | 序列化，**内含 `applyThinkingToOpenAIChat`**（`serialize_openai.go:198`） |

⇒ **paramguard(①) 早于 IR 序列化(③)**，与 93 号担心的方向**相反**。
且 ① 作用在**原始 body** 上 ⇒ 账本 `Original` 记的就是**客户端原值**。

**证据 B —— 触发源互斥：原生 OpenAI 入向时 `applyThinkingToOpenAIChat` 完全 no-op。**

`openAIReasoningIntent`（`serialize_openai.go:329-344`）：
```go
if req.Thinking != nil { ... return intent, true }              // Anthropic/Gemini 的 thinking 形态
if src := req.SourceProtocol; src == ProtocolOpenAIChat || src == ProtocolOpenAIResponses {
    return reasonnorm.Intent{}, false                            // ← 原生 OpenAI 入向：直接无意图
}
```
而携带 `reasoning_effort`、会被 paramguard 改写的请求，**其 `SourceProtocol` 必然是 OpenAIChat/Responses**
⇒ `haveIntent == false` ⇒ `applyThinkingToOpenAIChat` 在 `:283-285` 就 `return false`，**一个字节都不写**。

**证据 C —— 即便意图存在，也不覆盖。**

`serialize_openai.go:276-277` 注释 + `:314-318` 实现：
```go
// Keys already present in out are never overwritten (IR/serializer output wins...)
if res.ReasoningEffort != "" {
    if _, exists := out["reasoning_effort"]; !exists {   // ← 键已存在则跳过
        out["reasoning_effort"] = res.ReasoningEffort
```

### 1.3 闭合

两个机制由**互斥的入向形态**驱动：
- `applyThinkingToOpenAIChat` 只对 **Anthropic/Gemini `thinking` 意图**触发 ⇒ 这类请求**没有原生 `reasoning_effort`** 供 paramguard 改写；
- paramguard 改写**原生 `reasoning_effort`** ⇒ 只出现在 **OpenAI 入向**，而那里 `applyThinkingToOpenAIChat` 是 no-op。

叠加证据 A（顺序）与 C（不覆盖）⇒ **93 号 §8.1 的「双重改写 / 账本 Original 语义错位」不可达，不是缺陷。**

> 这与 93 号 §1 的 P1 性质不同：那个是**真断线**（已证零可达路径 ⇒ 缺陷成立），
> 这个是**担心一条线断了、结果两条线都健在**。同样的「可达性」方法，
> 一次得出缺陷、一次排除缺陷——**这正说明可达性分析必须双向做，不能只查「哪里能到」。**

## 2. §8.3 关闭：`fixOpenAIOTokens` 不记账是**正确**行为

`internal/paramguard/guard.go:300-319`：
- 触发条件：dialect = OpenAIChat **且** `isOpenAIOSeries`（o1/o3/o4 系列）。
- 动作：把 `max_tokens` **改名为** `max_completion_tokens`，**值不变**；
  两键并存时 `delete(obj, "max_tokens")`（:311）。
- 代码注释（:298）自陈：「键名改写属于纯格式转换（**值不变**），不产生 Report」。

**是否产生客户端可见偏差？——否，三点闭合**：
1. **值从未改变** ⇒ 还原的定义是「把客户端原值写回」，此处**没有需要还原的值变化**。
2. **请求侧键名不被任何响应回显**：核实 `internal/ir/response.go` / `stream.go`——
   唯一含 `max_output_tokens` 的是 `response.go:1003`
   `MapFinishReasonToResponsesIncompleteReason`，那是 **finish_reason 映射常量**
   （`"length"/"max_tokens"` → `"max_output_tokens"` incomplete 原因），**不是请求参数回显**。
3. 两键并存时删的是**客户端自己发的冗余 legacy 键**，语义由 `max_completion_tokens` 承载。

⇒ **不记账是正确行为，不是缺口。** 93 号 §8.3 关闭。
