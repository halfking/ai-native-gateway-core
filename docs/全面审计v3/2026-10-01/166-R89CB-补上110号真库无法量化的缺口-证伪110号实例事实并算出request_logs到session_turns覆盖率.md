## 三、F2：65% 的「未迁移」是分母问题，不是写入问题

### 3.1 覆盖率断崖

```sql
-- 每日：request_logs 有行、但 session_turns 无对应行的比例
SELECT r.ts::date, count(*), count(*) FILTER (WHERE s.request_id IS NULL) AS missing, ...
FROM request_logs r LEFT JOIN session_turns s ON r.request_id=s.request_id
WHERE r.ts >= '2026-09-20' GROUP BY 1;
```

| 日 | `request_logs` | 缺 `session_turns` | 缺失率 | **缺口有 session** | **缺口无 session** |
|---|---|---|---|---|---|
| 09-20 | 35,345 | 54 | 0.2% | 54 | 0 |
| 09-23 | 321,779 | 1,250 | 0.4% | 1,139 | 111 |
| 09-24 | 392,873 | 8,459 | 2.2% | 8,434 | 25 |
| **09-25** | 370,767 | 147,449 | **39.8%** | 4,171 | **143,278** |
| **09-26** | 404,799 | 265,836 | **65.7%** | 3,404 | **262,432** |
| 09-27 | 21,965 | 12,424 | 56.6% | 2,218 | 10,206 |
| 09-28 | 19,034 | 10,547 | 55.4% | 2,169 | 8,378 |
| 09-29 | 11,512 | 7,022 | 61.0% | 233 | 6,789 |
| 09-30 | 9,431 | 5,907 | 62.6% | 90 | 5,817 |
| 10-01 | 1,536 | 998 | 65.0% | **0** | 998 |

**「65% 的流量没迁移到 session_turns」** —— 如果只报这一句，这会是一个重量级且**方向错误**的结论。

### 3.2 判别维度：把缺口拆成「有 session」与「无 session」

两个竞争解释：

- **(a) 双写坏了** ⇒ 65% 的流量没进 `session_turns` ⇒ 对 objective「存储切到 session_turns」是重大缺口。
- **(b) 大量流量本来就没有会话**（无状态单轮调用）⇒ 这类请求**本来就不该**进 `session_turns` ⇒ 「未迁移」是**分母放错**。

**判别结果**：

| 日 | 有 session 的行缺失率 | 无 session 的行缺失率 |
|---|---|---|
| 09-25 | 4,171 / 370,767 = **1.1%** | 143,278 / 239,209 = **59.9%** |
| 09-26 | 3,404 / 404,799 = **0.8%** | 262,432 / 262,432 = **100%** |
| 10-01 | **0 / 1,536 = 0%** | 998 / 998 = 100% |

⇒ **(b) 成立，(a) 被证伪。** 有会话流量的双写缺失率只有 **0.8–1.1%**，而且**逐日收敛到 0**（10-01 整整一天为 0）。

**⇒ 对 objective 的直接回答**：`request_logs → session_turns` 的迁移在**「有会话的流量」上覆盖良好且已收敛**；那个吓人的 65% 是**把无状态流量算进了分母**。

**⚠️ 诚实边界**：本轮证明的是「有 `gw_session_id` 的行几乎都有 `session_turns` 对应行且两表字段一致」，**没有**证明「`request_turns` 里没有多余/错配的行」（`only_in_st = 167,107` 全在 9 月，未核）。

## 四、⚠️ F3：真凶仍未解释 —— 这才是本轮唯一的新缺陷

F2 证伪了 (a)，但把 09-25 的突变摆在了台面上，**不能就这么放过**：

| 日 | 无 session 行数 | 缺 `session_turns` | 缺其中 `is_auto_request=TRUE` |
|---|---|---|---|
| 09-24 | 241,031 | **25** | 241,025 |
| 09-25 | 239,209 | 143,278（60%） | 239,204 |
| **09-26** | 262,432 | **262,432（100%）** | 262,432 |

两个必须解释的反常：

1. **09-25 起每天凭空多出 24–26 万条无 session 流量**，而 09-24 及之前这批量几乎为零（09-24 只有 **25 条**未进 `session_turns`）。
2. 这批流量 **~100% 是 `is_auto_request = TRUE`**（09-24: 241,025/241,031；09-26: 262,432/262,432）。

**两个竞争解释，本轮无法分辨**：

- **(c) 某个客户端/压测/爬虫在裸打无状态接口** ⇒ 这类流量**本来就不该**进 `session_turns` ⇒ 非缺陷。
- **(d) 会话头识别坏了** —— 本该带 session 的请求被当成无状态 ⇒ 那它没进 `session_turns` 就是**真缺口**，(a) 会以变体形式复活。

**判别所需的一个维度**（下轮做）：按 `api_key_id` / `tenant` / 端点路径拆这批流量。已知的线索：`distinct_tenants` 恒为 **1**、`distinct_apikeys` 在 09-24/09-25 为 1–2、09-26 为 **0** ⇒ **集中在单一租户**，且 09-26 起连 api_key 维度都取不到值。

⇒ **待裁决 68（P3）**：需要运维提供 2026-09-25 前后的流量来源说明（是否新接了客户端 / 是否跑过压测），才能在 (c) 与 (d) 之间定性。**本代理不擅自动手，且本机无网关进程无法自查（§44③）。**

## 六、⚠️ F5：`delta_append` 生产零出现 ⇒ 110 号的 P2 建议降为 P3

### 6.1 实测分布（`session_turns`）

| 取值 | 行数 |
|---|---|
| `(empty)` | 1,595,820 |
| `sliding_window_token_absolute` | 43,355 |
| `sliding_window_count` | 24,874 |
| `sliding_window_token` | 16,397 |
| `mechanical_trim` | 58 |
| **`delta_append`** | **0** ★ |

三张表**合计 0 行**。

### 6.2 为什么这条重要

110 号的 P2 建立在这样一个双臂对照上：

> 无 PII 臂 → 145 字节 / **`delta_append`**
> 含 PII 臂 → 0 字节 / **`""`**
> ⇒ `compression_strategy` 列在两类会话上**装的不是同一种事实** ⇒ **压缩看板系统性排除全部 PII 会话且无痕迹**

**而对照臂那个值 `delta_append` 在生产一行都没有。**

代码侧三个赋值点确实都存在，且**都以 PII 会话被排除的同一个条件为前提**：

| 位置 | 条件 |
|---|---|
| `domains/hooks/compression/session_compressor.go:401-403` | `!diffResult.Unchanged && !diffResult.IsNewSess`（mode 关闭/仅增量时） |
| 同上 `:450-452` | 同条件（`winResult.SkipStream` 时） |
| 同上 `:644-647` | 同条件（无窗口触发但 delta 改写了 body 时） |

⇒ **机制成立**（§41 桶① 不成立：代码确实接线了）。
⇒ **但受害面在生产不可观测**：对照组 `delta_append` 零出现，说明**这三条分支在生产几乎不被走到**；而「哪些会话是 PII 会话」在 DB 里**没有标记列** ⇒ **无法用生产数据证实或证伪 PII 会话的分布**。

### 6.3 定级建议：P2 → P3

按 **§52** 四维：

| 维度 | 答案 |
|---|---|
| 会不会失败 | 不会 |
| 会不会波及 | **不会** —— 对照组零出现 ⇒ 没有「本该记成 delta_append 却记成空」的可见损失 |
| 当事方知不知道 | 不知道（这是问题本身） |
| 有没有留痕迹 | 无 |

⇒ **建议 P2 → P3（latent）**。**理由不是「机制不成立」，而是「受害面在生产为零且不可观测」。**
⚠️ **本代理不擅自改 110 号的定级**（那是已登记条目），**以建议形式登记为待裁决 68 的附项**。

## 八、playbook §59 新增

> **§59 尺子错分两种形态：静默的伤结论可信度，响亮的只伤轮次 —— 但都要记**

前八次检测器缺陷（§47/§48/§50/§57）都是**静默**的：输出一个干净、自洽、**完全错误**的数字，不报任何错。

本轮三次是**响亮**的：直接 `ERROR`，零行输出。

**⇒ 两种形态分开记，不要混进同一份清单：**

| 形态 | 症状 | 伤什么 | 记法 |
|---|---|---|---|
| **静默** | 输出干净自洽的错误数字 | **结论可信度** | playbook 正文 + 变体测试/对照样本 |
| **响亮** | `ERROR` / 报错，零输出 | **轮次** | 一条前置动作即可 |

**⇒ 唯一的前置动作：写聚合 SQL 前先查列名。**
本仓已确认三组不同名，直接推翻了「三张表结构一样」的默认假设：

| 表 | 时间列 | 会话列 |
|---|---|---|
| `request_logs` | **`ts`** | `gw_session_id` |
| `session_turns` | **`ts`** | **`session_id`** |
| `request_wal` | **`created_at`** | `gw_session_id` |

**⇒ 推论**：本仓里任何「三表 union 后统一按 `created_at` 分月」的写法都是错的；跨表聚合必须显式写各自的列名。

**同族**：§47（`\S`+`.match()`）/ §48（箭头前有没有 `:=`）/ §50（返回值真的存在吗）/ §57（判据自己写错）/ **§46（尺子不对结论必错）**。
**其中 §46 与本条是同一件事的两端**：§46 说「尺子不对结论必错」，本条说「尺子不对有两种表现，识别形态决定记法」。
