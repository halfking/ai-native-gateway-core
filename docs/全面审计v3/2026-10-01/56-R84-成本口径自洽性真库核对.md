## 1. 成本口径自洽（B7 正面结论）

近 7 天（真库）：

| 表 | 有 cost 的行 | 合计 |
|---|---|---|
| `request_logs.cost_usd > 0` | 1,582 | **$151.8321** |
| `session_turns.cost_usd > 0` | 1,573 | **$151.8300** |

**差 $0.0021**，行数差 9 行（0.6%）。⇒ **objective「将 request_logs 的存储切到 session_turns」没有损坏成本数字**，这是 R79–R81 存储迁移系列结论的收口。

同时注意 V1 的成本**极度稀疏**：近 7 天 1,109,581 行中仅约 1,582 行有 `cost_usd`（99.86% 为 NULL）；而 `session_turns` 的 652,802 行中 `cost_usd = 0` 的占绝大多数、**无 NULL**。两者语义一致（只有真实产生费用的才有值），但**填充形态不同**——这一点在做 V1/V2 逐行比对时会产生大量「一有值一无值」的假差异。

## 2. C1【P2】credits 有两条独立路径，且被声明为「source-of-truth」的那条是空的

### 2.1 事实

| 载体 | credits 合计 | 说明 |
|---|---|---|
| `request_logs.credits_charged` | **0 行非 NULL（全时段 100% NULL）** | `main.go:2856` 称其为 **source-of-truth** |
| `request_stats_minute.credits_charged` | **1,694,550** | 单一真值表，122,118 行 |
| `request_stats_dim_minute.credits_charged` | 各 `dim_type` 约 1.5–1.7M | 8 个 `dim_type`（provider / identity_hash / agent_name / tenant / client_profile / virtual_ip / client_ip / error_kind），**逐维度各存一份** |
| `report_snapshots.credits_charged` | 0（7 行） | 快照表未落 credits |

⇒ **credits 确实在流动（1.69M），但它落在 `request_stats_minute`，而 `request_logs.credits_charged` 是空的。**

### 2.2 矛盾点

`cmd/gateway/main.go:2852-2856` 的注释：

> backfill hourly credit consumption buckets … converges to `request_logs.credits_charged` **source-of-truth** values.

但该 source-of-truth 列**全时段没有任何一行非 NULL**。若 backfill 真的以它为源，则结果恒为 0（`report_snapshots` 的 0 与此吻合）；若它实际从 stats 侧取数，则**注释描述的依赖方向是错的**。

### 2.3 连带影响

`cmd/gateway/dual_read_validator.go:484-485` 的 credits 对帐：

```sql
COALESCE((SELECT sum(credits_charged) FROM v1), 0),
COALESCE((SELECT sum(credits_charged) FROM v2), 0)
```

两侧都读 `request_logs` / `session_turns` 的 `credits_charged` ⇒ **恒为 0 与 0**，`CreditsDriftCount` 结构上永不可能非零。而 `domains/credential/writer.go:62` 把 credits 合计称作「**停写 gate 的硬指标**（plan §8-D）」。

⇒ **一个被称作「硬指标」的对账维度，在当前数据形态下恒等于 0，不具备任何鉴别力。**

### 2.4 定级

**P2**。不影响客户端观感，不产生错误数据（cost 口径是对的），但**一个用于判断「能否停写 V1」的硬指标实际上是空的**，会给出「credits 完全一致」的错误安心。

## 3. 一次被拦下的误判（记录方法论）

我第一版把 `request_stats_dim_minute.credits_charged` 全表求和，得到 **14,037,471**，差点报成「credits 口径相差 1400 万」的重大分叉。

**实际是重复计数**：该表按 `(bucket, tenant_id, dim_type, dim_key)` 键，**同一笔请求的 credits 在 8 个 `dim_type` 下各存一份**，全表求和即 8 倍放大。查 `dim_type` 分组后立刻暴露（各维度均约 1.5–1.7M，与单一真值表的 1,694,550 一致）。

**与 R79 §4 的教训同源**：又一次是「验证装置的聚合方式错了 ⇒ 得出『有重大问题』的假结论」。在维度表上做全表聚合，必须先确认键的基数。

## 4. 已核对无问题

- `cost_usd` 在 V1/V2 间自洽（§1），存储切换未损坏成本。
- `session_turns.cost_usd` 零 NULL，V2 侧填充形态优于 V1。
- `request_stats_dim_minute` 的 8 个 `dim_type` 各自数值与单一真值表一致 ⇒ 维度展开本身没算错（只是不可跨维度相加）。

## 7. B1–B6 结构审计（子代理）与 **F1 撤回**

### 7.1 【撤回】F1「apikey 预算读裸父表 ⇒ 恒≈0」——**前提错误，缺陷不存在**

子代理报 **F1（高危）**：`admin/keys.go:973` 打的是裸分区父表 `FROM usage_ledger` 而非 `usage_ledger_with_current_month`，据此推断父表只有 `_default` 分区有数据 ⇒ `spent_usd` 恒≈0 ⇒ 预算门控形同虚设。

**主代理真库实测推翻**：

| | 行数 | `sum(cost_usd)` |
|---|---|---|
| 裸父表 `usage_ledger` | 2,064,519 | **$1141.8727** |
| 视图 `usage_ledger_with_current_month` | 2,067,015 | **$1141.8727** |
| `usage_ledger_default` | **0** | — |

**错误前提**：PostgreSQL 的分区父表是**虚拟表**，`SELECT ... FROM partitioned_table` 会**路由到全部 5 个分区**。「裸父表只返回 default 分区行」在 PG 中不成立——那是把分区表当成「普通表 + 旁挂分区表」的误解。

**证据自明**：`usage_ledger_default` 有 **0 行**，而裸父表查到 **2,064,519 行**。父表若只看 default 分区，返回的应是 0。

⇒ **F1 撤回，apikey 预算读数正常。** 父子查询的**金额完全相同**（$1141.8727）；视图多出的 2,496 行不带来任何金额差异，属视图的 current-month 去重语义，非缺陷。

**教训**：这是本会话第二次撤回子代理结论。上一条（R83b）是我**低估**了问题；这条是子代理**高估**了问题。两次的共同根因都是**用静态推理替代了可一条 SQL 验证的事实**——而这个域的分区表结构恰好是静态阅读最容易想错的地方。
