## 1. 【修正 89 号】根因不是「预览太短」，是「**丢弃了好源去读弱源**」

89 号 §3 写的是「预览仅 320 字节 ⇒ `extractUserPrompt` 必然取不到 user 内容 ⇒ 必然回落到系统提示词」。

**这个描述对 `extractTitleFromPreview` 本身准确，但对「为什么这条分支会被走到」解释不完整。**

`generateTitleFromFirstRequest`（`admin/auto_title_generator.go:379-405`）构建 corpus 的**优先级**是：

```go
// Step 1. Try the FULL request body first — 这给出真实的 user message（不截断）
if requestBody != "" {
    if extracted := extractMessagesForTitle(requestBody); extracted != "" {
        corpus = extracted; corpusSource = "request_body"     // ← 好源，通常走这里
    }
}
// Fall back to the 320-byte preview if full body extraction yielded nothing
if corpus == "" && requestPreview != "" {
    corpus = requestPreview; corpusSource = "request_preview" // ← 弱源
}
// Step 2. 只有连 corpus 都没有才去查 DB
```

⇒ **正常情况下 `corpus` 已经是完整请求体，里面的 user message 是拿得到的。**

而四条回退分支（`:427` / `:439` / `:461` / `:472`）全都是：

```go
if title := g.extractTitleFromPreview(requestPreview); title != "" { … }   // ← requestPreview
```

**用的是 320 字节的 `requestPreview`，而不是它刚刚构建好的 `corpus`。**

⇒ **修正后的根因**：函数**已经持有包含真实 user message 的 full-body corpus**，却在失败时把它扔掉、退回去读那个在 agentic 负载下必然只有 system prompt 的 320 字节预览。

**这个区别决定修法**：

| | 89 号原先的修法（甲） | 修正后的修法 |
|---|---|---|
| 动作 | 改 `extractTitleFromPreview` 的 3c 分支为占位文案 | **让回退改用 `corpus`（已构建、含真实 user message）**，只对「corpus 里确实没有 user 内容」才用占位 |
| 效果 | 44% 的标题从「系统提示词」变成「（无用户输入）」，**仍然不可读** | 44% 的标题**变成真正的会话标题** |
| 成本 | 小 | 小（把 4 处 `requestPreview` 换成 `corpus`，并对 corpus 走一次 `extractUserPrompt`） |

⇒ **修正后，甲方案不再是「不让它更丑」，而是「让它真的可用」。** 待裁决第 37 条的方案甲据此更新。

## 2. 触发归因：**现有数据无法回答**

89 号要追的是「44.42% 走的是哪条回退」。查完的结论是**做不到**，原因有两层：

### 2.1 DB 侧不区分

`session_titles.model` 在四条回退路径上**都写 `"auto-extract"`**（`:377` 注释明写
「On fallback-extract paths model is `auto-extract` and apiKeyID is 0」）⇒ 四条路径在库里**同值**。

### 2.2 指标侧也不区分

`metrics/auto_summary_metrics.go:64-74` 只有两个 CounterVec：

| 指标 | label | 实际取值 |
|---|---|---|
| `auto_title_trigger_total` | `result` | `short_user_message`(:119) / `error`(:320) / `ok`(:325) |
| `auto_title_llm_call_total` | `result` | `ok`(:964) / `transient_retry`(:972) / 计算值(:990) |

**两者都在「是否触发 / LLM 调用」这一层，没有一条落在「回退原因」这一层**；且**不落库**，本机网关又没在跑（87 号已证），因此连 Prometheus 侧也取不到历史。

⇒ **归因缺口的修法（建议，属可观测性裁决）**：给 `auto-extract` 加归因——最小改动是**把回退原因并进 `auto_title_trigger_total` 的 `result` label**（如 `fallback_corpus_short` / `fallback_no_key` / `fallback_llm_error` / `fallback_invalid_title`），**不动 DB schema**；更彻底的是给 `session_titles` 加一列 `extract_reason`。

## 3. 顺带查实的一件事：闸门与回退失败条件**互斥**

`MaybeGenerateTitle`（`:104-128`）的两道闸门：

| 闸门 | 位置 | 条件 | 结果 |
|---|---|---|---|
| 首轮检查 | `:108` `isFirstSuccessfulUserTurn` | 非首个成功用户轮 | **完全不生成**（无回退）；查询报错同样 `:220` 直接 return |
| short-user-message | `:119` | 末条 user 消息 runes **≤ `sessionTitleMaxRunes`** | **完全不生成**（无回退） |
| → 进入 `generateTitle` | | 末条 user 消息 runes **> 预算** | 才有资格产出 `auto-extract` |

⇒ **失败人群被夹死在中间**：user 消息必须**够长**（否则被闸门拦掉、连标题都没有），
而预览又必须**装得下** user 内容（否则回退取到 system）——
在 ZCode/Cursor 这类 system prompt 动辄上千字节的 agentic 负载下，**装不下是常态**。

⇒ 这解释了为什么回退率高达 44.42%：**它不是长尾异常，而是整个 agentic 负载类别的默认结局。**
