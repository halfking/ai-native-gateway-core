## 一、先说结论

1. **「用 grep 找 `tenant_id` 判断端点有没有租户隔离」这个方法，在本仓系统性失效。**
   因为租户过滤是由**共享 helper 以 SQL 片段形式注入**的，handler 函数体里**根本不会出现**该字符串。
   ⇒ 我本轮机械筛出的 **8 个候选全部不可采信**，其中至少 3 个经读原文**已证伪**。
2. **待裁决 43（「租户隔离无机制兜底」）需要实质降级并改述**：
   租户闸门**存在且集中**（`admin/session_tenant.go` + `admin/context.go` 共 6 个函数），
   25+ 个 admin 文件已在调用。风险形态从「**无机制**」变成「**机制是 opt-in，漏调无编译期错误**」。
3. **94 号那条 `swim-lane-init` 缺租户过滤 —— 经读原文坐实成立**，是本轮唯一的真缺陷。
4. **新发现一条 latent P2（fail-open 默认分支）**，当前真库不发生。

## 二、方法论否定：机械筛选在本仓无效

### 2.1 我做了什么

1. 枚举 `admin/handler.go:898` 的 `RegisterRoutes`：**105 个 `admin(...)` + 57 个 `superAdmin(...)`**。
2. 对全部 **154 个 `admin(...)` 端点**，用 AST 近似取出 handler 函数体，
   筛出其中函数体直接 `FROM request_logs|usage_ledger|session_turns` 的 **36 个**，
   再按「函数体是否出现 `tenant_id`」标注 ⇒ **8 个候选无租户过滤**。

### 2.2 读原文后，8 个候选里至少 3 个是假阳性

| 候选 | 证伪依据 |
|---|---|
| `handleCompressionStats` | `admin/compression_stats.go` **有 3 处** `tenantLogsClause(` / `IsTenantAdmin(` 调用。过滤存在，只是**以 SQL 片段注入**，函数体里没有 `tenant_id` 字面量 |
| `handleRoutingRecentModelFailures` | 读的是 `node_probe_runs` / `passive_probe_state`（`admin/probe_history.go:446/457`）——**节点级表，不是租户级表**，「无 tenant_id」是设计正确 |
| `handleStats` | 实际定义在 `*RouteIncidentsHandler`（`route_incidents.go:461`）与 `*WorkTypeHandlers`（`work_types.go:248`）上，**不是 `*Handler`**。我的「按函数名索引」把不同接收者混并了 |

**根因**：`admin/session_tenant.go:12-16` 的契约是

> `tenantLogsClause` returns an SQL **AND-fragment** filtering request_logs by tenant_id
> for tenant_admin callers on non-default tenants.

即**过滤以字符串片段拼进 WHERE**，而不是在 handler 里写 `WHERE tenant_id = ...`。
`admin/compression_sessions.go:3-6` 甚至在文件头写明了这条契约。

⇒ **凡是用「函数体里有没有 `tenant_id`」判断租户隔离的，在本仓一律失效。**
这不是「候选判错」，是**检测手段本身无效**。已入册 **playbook §20**。

## 三、待裁决 43 需实质降级：闸门是存在的，是 opt-in 的

101 号读 `admin/auth.go:76-140` 得出「`AdminMiddleware` 只 `SetAuthContext`，不设 GUC、不改写 SQL、
不按租户包事务 ⇒ 隔离纯靠每个 handler 记得调 helper」。**方向对，但机制描述不完整**，本轮补齐：

### 3.1 集中闸门有 6 个函数

| 函数 | 位置 | 作用 |
|---|---|---|
| `IsTenantAdmin(r)` | `admin/context.go:42` | `role == "tenant_admin"` |
| `IsSuperAdminOrLegacy(r)` | `admin/context.go:48` | `super_admin` 或 `admin_key` |
| `EffectiveTenantID(r)` | `admin/context.go:57` | tenant_admin → 本租户；**其余 → `"default"`** |
| `EffectiveTenantIDAll(r)` | `admin/context.go:66` | tenant_admin → 本租户；**其余 → `""`（查全部）** |
| `tenantLogsClause(r, argStart)` | `admin/session_tenant.go:16` | 拼 `AND tenant_id = $N` 片段 |
| `requireSessionTaskAccess` / `assertTaskInTenant` | `admin/session_tenant.go:30/64` | **权限门**（不是数据查询），跨租户会话详情直接 404 |

`assertTaskInTenant` 的注释（`:45-63`）质量很高——明确说明它有**四条腿并联**
（session_summaries / session_turn_details_hot / 月分区母表 / v1 镜像链），
理由是「任何一个来源在 S4 停写后查不到行，结果就会从『阻断越权』翻转成『阻断所有人』」，
并记录了 EXPLAIN 实测（Index Only Scan，Buffers: shared hit=4）对照无索引时的 167 万行顺序扫描。

### 3.2 采用率是可数的、且不低

按文件统计 `tenantLogsClause(` / `IsTenantAdmin(` 调用点：
`credential_monitor.go` 7、`keys.go` 6、`analytics.go` 6、`users.go` 5、`pending_handlers.go` 4、
`logs.go` 4、`context.go` 4、`quality_correlations.go` 3、`memora_handlers.go` 3、
`compression_stats.go` 3、`compression_sessions.go` 3、`auto_route.go` 3 …… 共 **25+ 个文件**。

### 3.3 ⇒ 对 43 的改述

| 原表述（101 号） | 本轮修正 |
|---|---|
| 「租户隔离**无机制兜底**，纯靠每个 handler 自觉」 | 「租户隔离**有集中闸门且已被广泛采用**；残余风险是**闸门为 opt-in**——逐 handler 调用，**漏调无编译期错误、无运行期告警**」 |

**降级理由**：机制存在 + 采用面广 + 已有权限门与会话级断言，
这三点合起来与「无机制」不是同一个风险量级。**43 仍是 P1 结构性**（漏调确实无告警），
但**不再是「没有防线」，而是「防线的覆盖面靠自觉」**——修法方向也应随之调整：
不是从零建 GUC 机制，而是**给漏调加可检测性**（例如灰度期用中间件统计
「本请求走过 tenant 过滤但 SQL 命中了多租户」并告警）。

## 四、94 号坐实：`swim-lane-init` 缺租户过滤（唯一真缺陷）

- **端点**：`admin/handler.go:1050`
  `mux.HandleFunc("/api/admin/dashboard/swim-lane-init", admin(h.HandleSwimLaneInit))`
  ⇒ 挂在 `admin(...)`（**非** `superAdmin(...)`）下。
- **SQL**（`admin/swim_lane_init.go:90-111`，全文读过）：

```sql
FROM request_logs_hot rl
LEFT JOIN models_canonical mc … LEFT JOIN model_families mf …
LEFT JOIN credentials c … LEFT JOIN providers p …
WHERE rl.ts >= $1          -- ← 唯一的 WHERE 条件
ORDER BY rl.ts DESC LIMIT 500
```

- **返回字段含**：`request_id`、`ts`、`model`、`vendor`、`provider`、`status`、
  **`error_kind`**、**`cost_usd`**、`prompt_tokens`、`completion_tokens`。
- **可触发性**：真库 `users` 表有 **20 个 `tenant_admin`、6 个租户、7 个绑到非 default 租户**，
  `admin(...)` 接受任意已认证管理员 ⇒ **这是一个可被真实触发的跨租户读**。

⇒ 94 号这条**成立**。但注意它是 §2 那次失效筛选之外的**独立读原文所得**——
**不能算作那次筛选的战果**。

## 五、【新发现，latent P2】`EffectiveTenantIDAll` 的默认分支是 fail-open

```go
// admin/context.go:66
func EffectiveTenantIDAll(r *http.Request) string {
    if IsTenantAdmin(r) { return GetTenantID(r) }
    return ""    // empty string means query all tenants
}
```

而用户表（`admin/auth.go:229`）**带 `tenant_id`**。于是：

| 角色 | `EffectiveTenantID` | `EffectiveTenantIDAll` |
|---|---|---|
| `tenant_admin` | 本租户 | 本租户 |
| `super_admin` / `admin_key` | `"default"` | **全部租户**（合理） |
| **任何其它角色** | `"default"` | **全部租户**（← fail-open） |

**真库现状**：`users` 表只有 `tenant_admin`(20) 与 `super_admin`(2)，
**不存在 role=`admin` 的用户 ⇒ 当前不发生**。

⇒ 判 **latent P2**，登记理由：
**只要将来新增一个既非 `tenant_admin` 又非 `super_admin` 的角色，它会静默获得全租户可见性，
而无需修改任何代码**。叠加 `handler.go` 把 **105 个端点**挂在 `admin(...)`（接受任意已认证管理员），
风险是「**新增一个角色即可越权**」。

⇒ 建议（属待裁决范畴，本代理不动手）：把 else 分支从「查全部」改为
「按用户表的 `tenant_id` 过滤；仅 `super_admin`/`admin_key` 显式返回全部」，
即**让默认值收敛到最小权限**。
