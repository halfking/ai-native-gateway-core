## 1. 【撤回】上一轮我差点用「没有 `time.Sleep`」推出「没有等待」

74 号里我写：

> `executor_dispatch.go` 内 `time.Sleep`/`backoff` **0 命中**……

并据此把模式③标为「只验证了一半」。**这个推理方式是错的**，理由与本会话已记录的
「假 0 命中」同源、但更隐蔽一层：

- `time.Sleep` 是**实现手段**（代理量），不是**语义**（系统会不会等）；
- 主项目确实在等，只是**等在队列层而不是请求协程里**。

**教训**：判「系统有没有做 X」要找**决策层**（planner / state machine / 重试阶梯），
而不是去 grep 某种**语言层面的写法**。`grep sleep=0` 只能证明「没人用阻塞式等待」，
推不出「不等待」。

---

## 2. 追到的真实架构：等待是**队列节奏**（`retry_at`），不是 `sleep`

主项目的重试/切换由**决策阶梯**驱动，决策产出 `NextActionKind` + `RetryAt`：

| 证据 | 内容 |
|---|---|
| `domains/dispatch/notice.go:60-61` | `NextActionSwitchModel = "switch_model"`、`NextActionCapacityWait = "capacity_wait"` |
| `domains/dispatch/planner.go:308-319` | `PlanCapacityWait`：`RetryAt: now.Add(capacityRetryDelay)`，`Reason: "capacity_saturated"` |
| `domains/dispatch/planner.go:48-49` | `capacityRetryDelay = 5 * time.Second`、`maxCapacityRetries = 12` |
| `domains/dispatch/dimension_index.go:287-300` | `UpdateWait` 把 `retry_at` / `LastAction` 盖到索引条目，**park 回 pending** |
| `domains/dispatch/queue_mirror.go:36` | Redis 镜像键 `llmgw:dispatch:mirror:v1:retry_at:{request_id}`（unix 毫秒），注明「error/capacity requeue」 |
| `domains/dispatch/dispatcher.go:370` | `if d.Action != NextActionCapacityWait {` —— 只有 capacity_wait 走等待分支 |

**⇒ 主项目已经具备「给失败一次恢复机会」的能力，且做得比 9router 更好**：
不阻塞协程，而是把请求 park 到 pending 并盖时间戳，由队列按 `retry_at` 放行。

## 3. 那缺口到底在哪

`planner.go:300-305` 的阶梯在「无可用节点」时返回：

```go
for _, a := range alts {
    if _, tried := qr.TriedModels[a]; !tried {
        return Decision{Action: NextActionSwitchModel, NextModel: a, Reason: "no_node"}
    }
}
```

`NextActionSwitchModel` **不带 `RetryAt`** ⇒ **立即换模型**。

9router 模式③（`combo.js:158-165`）恰好补的是这一段：
502/503/504 且 `cooldownMs ≤ 5000` 时先 `await sleep(cooldownMs)` 再落到下一个模型，
注释自陈理由是「给短暂过载的 provider 一次恢复机会，而不是立即跳过」。

**⇒ 唯一真实缺口**：上游返回**瞬时 5xx** 时，主项目是**立刻**把流量切走，
不给该节点一个短暂自愈窗口。容量饱和那条路径**已经有**这个语义，不要重复实现。

## 4. 实施前必须先答的三个问题（本轮不实施）

1. **有没有真实发生率证据？** 我手上**没有**「瞬时 5xx 后该节点随即自愈、而立刻切换反而更差」的
   流量数据。9router 的注释说它修的是 `combo falls through on transient 503`，
   **那是它自己的 bug 报告，不是主项目的**。⇒ 没有数据就不该改路由时序。
2. **会不会与客户端超时预算打架？** 队列等待同样会让客户端多等至多 5s。
   objective 明确「不要影响客户端观感」，需与既有超时预算对齐。
3. **等待该落在哪一层？** 建议复用 `PlanCapacityWait` 的既有机制
   （新增一个 `Action` 或让 `switch_model` 可带 `RetryAt`），
   **不要**引入 9router 那种协程内 `await sleep` —— 那会阻塞 worker，
   在多层队列架构下比队列 park 危险得多。
