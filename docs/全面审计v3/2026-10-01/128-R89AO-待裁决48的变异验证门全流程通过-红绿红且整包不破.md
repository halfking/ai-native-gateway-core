## 一、为什么必须做这一轮

127 号的结论全部来自**只读代码 + git 历史**，它们能证明「**这里曾经有、现在没了**」，
但**不能证明「补回去就一定对」**——修法可能编译不过、可能被 `executeViaDispatch`

## 二、验证门四步（conventions §9）

### 步骤 0 —— 失败必须是**断言**而不是编译失败（§9.4 第 1 步）

第一次运行直接编译失败：

```
domains/streaming/executors/zz_r89an_tmp_test.go:37:51: undefined: provider.Candidate
FAIL	github.com/kaixuan/llm-gateway-go/domains/streaming/executors [build failed]
```

**这一版不作数。** 原因：导入路径写成了 `domains/provider`，实际是 `provider`（顶层包）。
修正后第二次运行又报 `Execute returned error: all 0 candidates failed`——
**这版也不作数**：它证明的是「我的候选没被调度器接受」，不是「trace 缺失」。
根因是 `provider.Candidate` 的 `Routable` 零值为 `false`，被调度器整体过滤
（对照 `executor_no_candidate_probe_test.go:60` 的 `Routable: false` 是在 probe 成功后
由 `OnProbeHoldEnd` 显式翻成 `true` 的）。补 `Routable: true` + `IsStream: false`
+ `OutboundModel` + `StickyKey` 后第三次运行才得到**有效证据**。

> ⚠️ 这三次失败本身有价值：**如果只看最后一次，报告就写不出「夹具必须显式 `Routable: true`」这条**。
> 临时实证的失败要如实保留，不要只留最后那一次。

## 五、本轮的一条方法论补充（并入 §25）

**「只读代码 + git 历史」能证明「曾经有、现在没了」，但**不能**证明「补回去就对」。**
本例的修法经过了三个它无法回答的问题：
① 会不会编译不过；② 会不会被 `executeViaDispatch` 的错误路径绕过（`derr != nil` 时不写）；
③ 会不会让既有测试变红。

⇒ **凡是要交给别人拍板的补丁，先自己跑一遍门。**
「提案」与「已验证的补丁」在决策成本上是两件不同的事：
前者需要用户自己判断风险，后者只需要用户判断**要不要**。
