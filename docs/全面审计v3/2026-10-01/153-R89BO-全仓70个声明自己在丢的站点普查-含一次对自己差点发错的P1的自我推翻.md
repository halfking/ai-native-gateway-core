## 一、结论先行：本轮我推翻了自己

普查开始后我顺着 `context_attrs` 侧表往下查，撞见一个**极其刺眼**的数字：

```
request_context_attrs   project_id 非空 = 0 / 388,821
session_dim             project_id 非空 = 1 / 1,212,805
```

而 `session_dim` 的包注释写着它承载「**项目→任务→会话**」层级视图，
`admin/turns_sessions.go:50` 正是 `COALESCE(NULLIF(ss.gw_project_id,''), sd.project_id)`。
按当时的思路，这已经够写成一条 P1 了。

**我停下来核了台账，结论是：这是 21/22/23 号（2026-09-29）早已查明的旧问题，迁移 762 已修。**
R32 原文「dim 1/120 万」与我实测的 `1 / 1,212,805` **完全吻合**——那不是巧合，那是我重踩了同一个坑。

更关键的是**我拿错了尺子**。762 的设计是**两级回落**：

```
X-Gw-Project-Id 权威值  →  否则 app:<application_code>
```

所以「`session_dim.project_id` 空」**不等于**「项目维度空」。测生产真正读的那个表达式：

| 口径 | 结果 |
|---|---|
| `session_summaries` 总行数 | 334,775 |
| level-2 `app:*` 回填 | **321,093（95.9%）** |
| level-1 真项目（`X-Gw-Project-Id`） | **1（0.0003%）** |
| 完全空 | 13,681（4.1%） |

**回填在工作**（近 7 天新会话 94.2% 有值，无回归）。**若我只测 `session_dim` 就发 P1，
那是一条「已修复的问题被当成新缺陷重发」的假报告**——而且它会强化一个错误结论。

⇒ **本条已升级为 playbook §46：数字越刺眼，越要先确认「生产读的是不是这一列」。**

## 四、本轮真正属于「新」的两条发现

### 4.1 `session_title` 是两个**结构上不可能有值**的死列

| 表 | 行数 | `session_title` 非空 |
|---|---|---|
| `request_context_attrs` | 388,821 | **0** |
| `request_logs_hot`（近 7 天） | 2,303 | **0** |
| `session_titles`（真数据住这里） | **427,770** | — |

产出方核查：`ContextAttrsEntry.SessionTitle`（`telemetry/context_attrs.go:64`）
**全仓只有两处引用 —— 结构体声明 `:64` 与 SQL 实参 `:268`，零个赋值点**。
而标题实际由 `admin/session_title.go` / `admin/auto_title_generator.go` 写入**独立的 `session_titles` 表**（427,770 行）。

✅ **但代码是对的**：`admin/logs.go:402` 注释明写「2026-08-06: `session_titles.title` join (see `requestLogsJoins`)」，
列表页的标题是 JOIN 来的，**不读那两个死列**。

⇒ **不是功能缺陷，是两条从未被使用的死列**（P3 清理项）。
⇒ 这是 §41 三分法的**第四桶**在列级的新实例：**声明了字段、留了实参位，却没有任何写入方**。

### 4.2 项目维度的 level-1 至今是 0.0003%

`X-Gw-Project-Id` 全仓无任何**客户端**发送（前端/SDK 零命中；只有 Go 侧读取 `request_meta.go:371`
与一份测试 `request_log_pipeline_test.go:105`）。实测值分布：

```
app:system 301,186（占全部会话 90%）· brandmind 9,713 · hermes 5,241 · ide 3,885
```

`system` 经核实是**真实 application_code 而非 NULL 兜底**（近 7 天 328,024/367,637 = 89.2%）。

⇒ **当前「项目筛选」实质是 `application_code` 的改名，且 90% 流量塌缩进单一桶。**
⚠️ **这不是缺陷**：迁移 762 注释**自己声明了**「`X-Gw-Project-Id` 在本部署几乎从不出现」
⇒ **§41 桶②（明确声明）**，是部署事实不是代码缺陷。
⚠️ **诚实边界**：我只验证了**本仓**内无客户端发送该头，**不排除仓外客户端在发**——
但若真有人在发，level-1 不会只有 1 条 ⇒ **反向证据支持「确实没人发」**。
