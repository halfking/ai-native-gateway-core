## 〇之二、更正二：117/118 号说的「`sessionaudit` 与 `observ` 重叠」**前提就是错的**

### 1.1 实测 `domains/sessionaudit/events.go`

```go
// domains/sessionaudit/events.go:15
type SessionAuditEvent struct {
    SessionID    string        `json:"session_id"`
    TenantID     string        `json:"tenant_id"`
    Content      string        `json:"content"`       // 用户输入内容
    DetectResult *DetectResult `json:"detect_result"` // 实时检测结果
    ClientInfo   ClientInfo    `json:"client_info"`
    timestamp    time.Time
}
func (e *SessionAuditEvent) Type() string { return EventTypeSessionAudit }
func (e *SessionAuditEvent) Timestamp() time.Time { … }
```

**⇒ 它是 `eventbus.Event` 实现**——**进程内事件总线上的一则「会话内容检测事件」**，
携带**用户输入原文 + 检测结果 + 客户端信息**，用于把检测结果广播给订阅方。
它**不是**「决策与动作的审计记录流」，**不落 `AuditEvent` 表**，
也**不含** `causation` / `correlation` / `fencing token` / `policy version` / `redacted payload hash`。

### 1.2 与 `domains/orchestration/observ` 的职责对比

| | `sessionaudit.SessionAuditEvent` | `orchestration/observ.AuditEvent` |
|---|---|---|
| 回答的问题 | 「**这个会话的内容检测出了什么**」 | 「**谁在什么时候基于什么策略做了什么决定**」 |
| 载体 | 进程内 `eventbus` | `Sink`（落库） |
| 载荷 | `Content`（**原文**）+ `DetectResult` | **redacted payload hash**（明确不落原文） |
| 关联维度 | `SessionID` / `TenantID` / `ClientInfo` | `causation` / `correlation` / **fencing token** / `policy version` |
| 状态 | **在用**（`domains/streaming/{handler,responses,messages}.go` 发布） | 零引用 |

**⇒ 两者根本不是同一类东西，不存在「第二套并存」。**
**117 号与 118 号据此推出的「重叠」判断作废。**

### 1.3 修正后的定性

- `domains/orchestration/observ` **不再**是「与 `sessionaudit` 重叠的第二套审计」；
  它是**尚未启用的「决策审计」能力**，而现役只有「内容检测事件」。
- **但它仍然是本审计里唯一一条把「决策因果 + 关联 + fencing token + 策略版本 +
  脱敏载荷哈希」写进类型契约的代码**——
  这恰恰说明现役**没有**这一层（而不是「现役有但更弱」）。
  117 号留下的那条诚实边界（「**不得**据此断定现役审计更弱」）**方向正确，
  只是当时的对照对象选错了**。
- **⇒ 待裁决问题因此变得更清楚**：
  「**现役的决策审计（谁为什么做了这个路由选择）记录在哪？**」
  **本轮仍未核**（`sessionaudit` 不是它；是否存在别的落库路径未查）⇒ 列入下轮。
