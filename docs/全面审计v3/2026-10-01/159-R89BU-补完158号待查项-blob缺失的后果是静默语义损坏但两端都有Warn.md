## 三、所以后果是「静默语义损坏」，不是「请求失败」

| 维度 | 结论 | 证据 |
|---|---|---|
| 网关会报错给客户端吗 | **不会** | `continue`，不中断出站；无 5xx |
| 整请求会失败吗 | **不会** | 注释明写「不吞掉原请求」 |
| 其它附件受影响吗 | **不会** | 每个附件独立 `continue` |
| 用户会知道吗 | **❌ 不会** | 没有任何面向客户端的提示 |
| **模型实际看到什么** | **看不到这张图** | provider 收到 404 的图片 URL |
| 网关留痕迹吗 | **✅ 留** | 两处 `slog.Warn`（`outbound_fetch_fallback.go:119` + `handler.go:92`） |

⇒ **真实后果：用户上传了图片，请求成功、模型正常作答，但模型实际上没看到那张图，
而用户与模型双方都收不到任何错误提示。**

⚠️ 这属于 objective 注意事项里那条原则的**反面**：
原则要求「不要影响客户端观观感，要通过思考模式把信息转达」；
而此处是**连转达都没有**——**静默的语义损坏比硬失败更难排查**。

## 四、为什么维持 P2，不升 P1

158 号定 P2 的三条理由，逐条复核：

| 158 号的理由 | 本轮复核 |
|---|---|
| ① 机制成立 | ✅ 不变（三段链条仍成立） |
| ② 规模已量化 | ✅ 不变（133× / 1,155× / 14 天） |
| ③ **发生与否未证实** | ✅ **仍未证实**（`audit_attachments_filesystem_cleanup` 仍 0 行） |

**新增的一条判断（本轮唯一的变化）**：

- 后果严重度**从「未知」变成「已完全刻画」**——这是 158 号明确要求的补完项；
- **但严重度并没有升高到 P1 的门槛**：单次发生只导致**单个请求**的图丢失，
  请求不失败、其余附件不受影响、**且两端都有 Warn 日志可查**。

⇒ **P2 维持。** 升级为 P1 需要的是「**已发生**」的证据（运维在远端做只读核对，
或 `/var/log` 里 grep 到 `attachments: open failed` / `fetch fallback load failed`），
**而不是更严重的推演**。
