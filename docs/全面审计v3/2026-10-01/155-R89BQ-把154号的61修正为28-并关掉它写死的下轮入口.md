## 一、154 号的「61」偏高了一倍以上

154 号交付的底表是自洽的，但**「真·发送」这一层判错了**。它的发送判别正则是：

```python
re_send = re.compile(r'^.*<-\s*[^=]')     # ❌ 同时匹配发送与接收
```

用它去匹配 154 号亲自举例的 `domains/dispatch/forwarder.go:257`：

```go
func (cf *credForwarder) drainAndComplete() {   // 停机 drain
	for {
		select {
		case qr, ok := <-*cf.queue.Load():   // ← 接收，不是发送
			...
		default:
			return                           // 「队列空了，drain 结束」
		}
	}
}
```

`.*` 吃掉 `qr, ok :`，`<-` 匹配箭头，`[^=]` 匹配 `*` ⇒ **判成「发送丢弃」**。
而它的真实语义是 **drain 循环的终止条件**——**队列空了就返回，根本没有丢任何东西**。

**这是 §47「算有没有的正则永远要先拿一个已知为真的样本验一遍」的第二次实证**，
而且这次是**我自己在上一轮写下的样本**被自己的脚本判错。

### 修正后的口径

```
107  非定时器/非停止/非工具的 default 分支
 ├─ 72  真·发送（可丢）
 └─ 35  接收/其它（不是丢弃）        ← 154 号误算进 61 的就是这 35 个
```

72 之中：

| 信号 | 数量 |
|---|---|
| 有日志 / 有计数 | 44 |
| **无日志 · 无计数（完全静默）** | **28** |

**⚠️ 61 → 28，缩减 54%。** 154 号的文首已按「不回改历史」的纪律加警示框指向本文。

### 正确的发送/接收判别（判据本身很简单，错的不是想法）

```
接收：case <-ch:            ← 箭头前为空
      case v := <-ch:       ← 箭头前含 ":="
      case v, ok := <-ch:
发送：case ch <- v:          ← 箭头前是 LHS 表达式，无 ":="
      case ch <- struct{}{...}:
```
