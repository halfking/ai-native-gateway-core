## 1. 撤回 54 号 §3

### 1.1 我当时的推理

我真库实测 `health_status` 与 `availability_state` **81/86 行取值不同**，据此判定「二者是探活原始结果 vs 路由可用性，语义不同」，并写下「不能把同一张表的多个状态字段当成状态分叉」。

### 1.2 为什么这个推理是错的

**取值不同 ≠ 语义分属不同子系统。** 它也可能是**同一道门控的两个合取项**——两个合取项本来就取不同的值。

权威证据是视图 `sql/objects/views/v_routable_credential_models.sql:17`，`is_routable` 是**单一 AND 合取**：

```sql
(p.enabled AND NOT COALESCE(p.manual_disabled,false)
 AND c.status = 'active'
 AND c.lifecycle_status = 'active'
 AND NOT COALESCE(c.manual_disabled,false)
 AND c.availability_state = 'ready'                              -- 合取项 1
 AND c.quota_state <> ALL(ARRAY['permanently_exhausted','balance_exhausted','periodic_exhausted'])
 AND pm.available AND cmb.available
 AND cmb.unavailable_reason IS DISTINCT FROM 'manual'
 AND COALESCE(c.health_status,'unknown') = ANY(ARRAY['healthy','unknown'])   -- 合取项 2
 AND NOT EXISTS(... node_probe_state ...))
```

⇒ **`health_status` 与 `availability_state` 同为这道门的合取项**。任何一方被直写都直接影响路由资格，**admin 写 `health_status` 就是绕过统一模块**。我原先的「免责」不成立。

**教训**：用「取值分布不同」推断「语义分属不同子系统」是**代理量推理语义量**。取值分布能证明「不等」，不能证明「无关」。判据应是**该字段是否参与同一个判定谓词**——这个我本来就能查，却用了一个更省事也更弱的证据。

## 2. F1【P1】`health_status='warning'` 把「单模型故障」升级为「凭据级全量摘流」，且无原因码

### 2.1 两个事实拼在一起才看出来

**事实一（门控）**：`is_routable` 要求 `health_status ∈ {'healthy','unknown'}`。**`'warning'` 不在其中** ⇒ 整个凭据的**所有绑定**一起出局。

**事实二（原因码）**：`unavailable_reason` 的 CASE（同视图 `:20-39`）有 `availability_cooling` / `rate_limited` / `auth_failed` / `unreachable` / `suspended` 五个 `availability_*` 臂，有 `quota_*` 臂，有 `health_status='unreachable'` 臂（`:32`）——**唯独没有 `warning` 臂**。⇒ 落到 `ELSE NULL`。

**拼合结果**：一条凭据处于 `health_status='warning'` + `availability_state='ready'` 时——**不可路由，且不告诉任何人原因**。

### 2.2 谁写的

`bg/credential_probe_v2.go:1365-1380`，**同一条 UPDATE** 同时写 `health_status = $1` 与 `availability_state = $6`。子代理指出该路径设 `BindingOnly=true`（`:1264-1270`、`:1283-1288`），即本意是**模型/绑定级**问题。

而代码里的注释白纸黑字承诺相反：`"sibling bindings must stay routable"` / `"sibling models must remain routable"`。**注释承诺绑定级隔离，视图实现的是凭据级连坐。**

### 2.3 这不是新问题，是同一根因的另一面，且至今未修

`bg/credential_recovery.go:730-745` 把根因写得很清楚：

> Root cause (2026-06-12): `v_routable_credential_models.is_routable` requires `health_status IN ('healthy','unknown')`. A single cycler/probe-v2 failure marks a credential as 'unreachable', which sets `is_routable=FALSE`.

该 recovery 分支的复位条件是 `health_status NOT IN ('healthy','unknown') AND health_checked_at < NOW() - INTERVAL '2 minutes'`。所以：

- **`warning` 与 `unreachable` 走的是同一个坑**，`unreachable` 已被 recovery 兜住，**`warning` 同样被兜住**（不是永久损伤）；
- 但兜住的方式是**周期性抖动**：模型下线、endpoint-ID 缺失、绑定级异常等本不该影响其它绑定的场景，会造成**约 2 分钟的凭据级全量摘流**；
- 且抖动窗口内 `unavailable_reason` 为 NULL，运维看到的现象是「凭据突然全部不可用且无原因」。

⇒ 方向上与 migration 460 自述的根因**同类**（`periodic_exhausted` 漏 CASE 臂 / 漏合取），只是那次修了，这次没修。

### 2.4 【R83c 补】真库实证 + 永久门

**已从「未实证」升级为真库实证**（单事务 + ROLLBACK，零残留核验：`warning` 行 0、279 个绑定可路由已恢复）：

```
baseline      credential#3:  14 个绑定， 6 个可路由
after warning credential#3:  14 个绑定， 0 个可路由
原因码                        6 行 unavailable_reason IS NULL
```

**6 行 NULL 恰好就是那 6 个从可路由翻转的绑定**——即「不给原因」的正是受害的那些行。

**新增永久真库门** `deploy/sql/verify/routing_gate_warning_pg_test.go`（`TEST_PG_DSN` 契约名，见 47 号报告）：

- **本门断言的是「当前的缺陷行为」而非期望行为，这是刻意的。** 期望行为（绑定级 warning 不连坐）今天会红，而一道红门不能进主干。钉住现状并标注 `FIXME(F1)`，好处是：将来任何人修 F1、或不小心改坏它，都会让本门红，迫使那次改动是**显式决定**而非无声发生。修 F1 时请同步把断言改成 `afterRoutable == baseRoutable` 并删掉 FIXME 块。
- 门内含**回滚后校验**（回滚后不可路由数必须回到基线），专门抓「忘了回滚留下污染」这类操作失误。
- **选凭据踩过一个坑并写进注释**：第一版只按 `credentials` 侧字段挑「可路由」，选出的 id=20 基线就 0 可路由（`provider_manual_disabled`），**把 F1 效应完全掩盖**。`is_routable` 还有 `p.enabled` / `pm.available` / `cmb.available` / `node_probe_state` 等合取项。门改为**从视图本身**取 `is_routable=true` 的凭据。

无 DSN 时干净 `SKIP`；有 DSN 时 PASS 并在日志里打出复现数据。

**消费侧仍把 `warning` 当正常态**：`admin/provider_diagnose.go:201`、`admin/providers.go:605` 展示时不提示它会导致全量摘流。

**252 生产复现方法**（若需在生产确认影响面）：置一凭据 `health_status='warning'` + `availability_state='ready'`，查 `v_routable_credential_models` 的 `is_routable` 与 `unavailable_reason`。

## 4. F3【P2】`credentials.revision` 不是乐观锁

`db/db.go:5637-5641` 的触发器只在 `concurrency_limit, concurrency_mode, rpm_limit, tpm_limit, fp_slot_limit, max_queue_depth, max_queue_wait_ms` 上 bump。`admin/provider_credential.go:541` 读它、`:697` 回显给客户端，**从不与客户端期望值比较**（无 `WHERE revision = $n`）。只改 `label` 的 PATCH 会返回未变的 revision。

它是 **governor 变更通知计数器**，不是凭据状态版本。并发保护实际靠 `SELECT ... FOR UPDATE` 悲观行锁（`admin/provider_credential.go:545`）+ 事务，那条是**对的**。

## 5. F4【P2】设计文档承诺的统一入口只实现了一半

`docs/03-design/.../unified-credential-state-hook.md` 要求「每个 candidate 尝试后**无论成败强制调用**」。实际 `PostExecutionHook.RecordOutcome` **仅在成功路径一处**被调（`executor_chat.go:1444`），且仅 `routingExec` 接线（`main.go:2177`）；失败路径另走 `executor_nodehealth.go:255/268` 与 `executor.go:3017` 两套。

⇒ **文档承诺 ≠ 实现**（本项目一贯把这类不一致当缺陷）。

## 6. 已核对无问题（子代理结论，主代理采信并复核关键项）

- `credential_state_nodes` 读写全在单一包内，无跨模块分叉。
- `nodestatecache` 严守「只读派生、不双写」。
- `state_sync.go` 的 `QUARANTINED→'open'` 映射是**有记录的设计决定**（注释说明 CHECK 约束只允许三值，配额语义由 `quota_state` / `availability_state='suspended'` 承载）——**非缺陷**。
- URSM v2 authoritative 模式下请求状态单一写入口，有 `CHANGELOG.md:1506` 记录。
- `admin/providers.go:107` 的 `health_status="error"` 看似违反 `chk_credentials_health_status`（值域无 `error`），但该分支 `continue` 在 UPDATE **之前**（`:108` vs `:122`），字面量到不了 SQL——**排除，非缺陷**。这一条排除很重要：它证明 CHECK 约束是真的在兜底。
