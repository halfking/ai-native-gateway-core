## 2. 三条最该立刻做的（子代理建议，主代理已重新定级）

### 建议 1：`v_routable` 补 `warning` 臂 —— **定 P1，接手**

`sql/objects/views/v_routable_credential_models.sql:20-40` 的 reason CASE **无 `warning` 臂**，落 `:39` 的 `ELSE NULL` ⇒ 这正是运维「凭据突然全部不可用且无原因」的**直接成因**。`credentials` 的 CHECK 本就允许该值，**无需改 schema**。

**主代理补充的修法取舍**（比子代理的更保守）：子代理建议把 `:17` 的合取**放宽为含 `warning`**（降权而非硬摘）。但 `:17` 是 `is_routable` 的**单一 AND 合取**，放宽它会改变 F1 的表现形态——从「凭据级雪崩」变成「降级但仍可路由」。**这属于会改变对外行为的裁决，仍走 60 号确立的路径：等 F1 修法定案（待裁决 Y，推荐方案 b）时一并落地，不擅自改。**

### 建议 2：失败计数加「跨冷却期升级窗口」 —— **定 P2，可独立做**

`domains/credential/breaker.go:440-447` 现在**错误族一变就 `coolingCycle=0`**，而 `transientFamily`（`:378`）只覆盖 4 种 ⇒ **Timeout↔UpstreamDown 交替的凭据永远升不上去**。

换成 OmniRoute 的窗口判据（`accountFallback.ts:640`）：`now - lastFailureAt <= resetAfterMs + lastCooldownMs`，再加 cc-switch 的错误率双触发。**与 F1 独立，可先做。**

### 建议 3：修复动作加 `preconditionsHash` —— **定 P2，成本近乎为零**

`bg/credential_recovery.go:748-756` 的 `health_status_reset` 是**无条件 UPDATE** ⇒ 运维「看着 A 的状态、清掉 B」是可能的。OmniRoute 每个修复动作带 `preconditionsHash` + `dryRun`/`confirm`，加一个快照 hash 即可防。

## 3. 明确**不该学**的（比「该学什么」更重要）

| 参照项目的做法 | 为什么不能学 |
|---|---|
| **CLIProxyAPI 健康状态不落库** | `persist()` → `postgresstore.go:189` 只序列化 `auth.Metadata`，`ModelStates` 在 store 层**零引用** ⇒ 重启全归零。主项目**绝不能倒退成内存态** |
| **OmniRoute 健康状态全在进程内 Map** | `accountFallback.ts:413` ⇒ 多副本会「每副本一套冷却」 |
| **OmniRoute 的人肉 provider 白名单** | `providerSets.ts` 靠 #3976/#4202/#4249 连片 issue 补分类器漏洞 ⇒ **学三段式结构，别学这张表** |
| **cc-switch 的 provider 级熔断** | 会把主项目最细粒度压回最粗，**正好反向恶化 F1** |
| **OmniRoute `EmptyState` 的内联 style + 每实例注入 keyframes** | API 可学，样式组织是退步 |

**这五条是本报告最有价值的部分之一**：跨项目借鉴最容易犯的错不是「没学到」，而是「学了对方的架构级取舍」。

## 4. 【更正】59 号 §3.3 的一处事实错误 —— 我自己复核的疏漏

59 号（及 README）写了「**`EmptyState` 组件根本不存在，16 处视图各写空态**」。**这是错的**，主代理已用三条独立证据核实：

```
web/src/components/EmptyState.vue  存在，987 字节，2026-09-04
  - 带 text / padding prop
  - 注释自述「抽取自 ProbeHealthDetailView / SelfCheckPanel / ModulesView /
    ProxyView / PromptInjectionSettingsView 重复模板」
已被 7 个文件引用：DataTable.vue / QueuePerspectivePanel.vue / SelfCheckPanel.vue
                  / RoutingOverviewView.vue / ProbeHealthDetailView.vue
                  / PromptInjectionSettingsView.vue / ApprovalListView.vue
```

**错因**：R85-C 子代理的检索范围限定在 `web/src/components/ui/`，而该组件在 `web/src/components/`（**不在 `ui/` 子目录**）⇒ **典型的「搜错范围得到假 0 命中」**。

**责任在我**：我在重新定级时复核了子代理的**定级**，但**没有复核这条事实断言**，于是原样写进了 59 号与 README。这是我本会话反复警告过的同型失误在自己身上重演。

**更正后的准确表述**：组件存在且有 7 处采用，但**仍有 14 个视图各写各的空态**（采用率约 30%）；且组件**只有 `text`/`padding`、没有 `action` 能力**（OmniRoute 带 `actionLabel`/`onAction`）⇒ **真实缺口是「采用率」与「空态不给下一步动作」，不是「组件不存在」**。

59 号与 README 均已就地标注更正。**教训已并入 `conventions.md` §9.2**（判据钉语义量）与本轮的复核纪律：**重新定级 ≠ 重新核实事实。**
