# ⚠️ 自查更正与结论强化（2026-10-01 R89-AQ，R89-AP 落盘后自查）

**本节按纪律回灌本文件，不改动上文原文。** 触发原因：§三 用 `pg_class.reltuples`
（**规划器估算值**）下了「从未落库」这种**终态结论**，而终态缺失**无法区分**
「从未写入」与「写入后被删除」——两者在数据库里长得一模一样。必须自查。

## 更正 1（一处数字错误）

§三 的分区行数表用的是 `reltuples` 估算。**精确 `COUNT(*)` 为**：

| 分区 | 本文件原文（reltuples 估算） | **精确 COUNT(\*)** |
|---|---|---|
| `usage_ledger_2026_09` | 2,065,828 | **2,065,720** |
| `usage_ledger_2026_07` | **0** | **2** ❗ |
| `usage_ledger_2026_08` / `2026_10` / `_default` | 0 | 0 ✔ |
| `usage_ledger_hot` | 2,592 | 2,592 ✔ |

⚠️ **原文写「07/08/10 月分区均为 0」是错的——07 月分区有 2 行。**
**教训**：`reltuples` 是估算，与父表 `COUNT(*)` 相差 106 行（2,065,828 vs 2,065,720），
**它不能用来支撑「某个分区是空的」这种断言**。§一/§二 的逐日数字来自 `COUNT(*)`，不受影响。

## 更正 2（结论性质不变，但证据从「推断」升级为「三重排除」）

原文的推理是「hot 没有、月分区没有 ⇒ 从未写入」。**这是从终态反推历史，方法上不严密。**
本轮补了三项独立排除：

1. **promote 无「删了没插」路径** —— `promote_usage_ledger_hot_to_partition` 的
   主体是**单条数据修改 CTE**：
   ```sql
   WITH batch AS (SELECT ... FROM usage_ledger_hot WHERE ts < now()-p_retention
                  ORDER BY ts, request_id LIMIT p_batch_size FOR UPDATE SKIP LOCKED),
        moved_rows AS (DELETE FROM usage_ledger_hot h USING batch b
                       WHERE ... RETURNING h.<全部列>),
        inserted  AS (INSERT INTO usage_ledger (...) SELECT ... FROM moved_rows RETURNING request_id)
   SELECT count(*) INTO moved FROM inserted;
   ```
   **DELETE 与 INSERT 在同一条语句内** ⇒ INSERT 失败（约束冲突等）会**整条回滚**，
   行**留在 hot**，不会「被删掉又没插进去」。
   ⇒ **「写入后被静默删除」在结构上不可能。**

   **对照（值得单独记住）**：`promote_credit_ledger_default_batch` 是**手写两条语句**，
   带 `RAISE WARNING 'promote_credit_ledger_default_batch: INSERT failed (%), rows preserved in _default'`
   —— **同一套 promote 体系里两种写法并存**。CTE 那种是安全的；手写那种要靠显式错误处理兜。
   本条针对的是 `usage_ledger`（CTE 写法），**不是** `credit_ledger`。

2. **hot 无滞留老行 ⇒ promote 未停摆** —— `min(ts)=2026-10-01 03:00:43`、
   `max(ts)=2026-10-01 11:38:59`（查询时刻 11:43），**全部落在约 8.5 小时内**，
   与 8 小时保留 + 当前流量一致。**若 promote 曾停摆，9 月的老行会仍在 hot 里等着**，实测没有。

3. **分区内部逐日精确计数复核** —— 直接查 `usage_ledger_2026_09`（绕过视图）：

   ```
   09-05=25,076  09-06=33,396  09-12=24,726
   09-13=73,795  09-14=36,291  09-15=18,272
   （09-01~09-04、09-07~09-11 无行）
   ```
   与 §二 通过视图得到的数字**逐日完全一致** ⇒ 空洞确实在分区内部，不是视图口径问题。

⇒ **结论不变且更强：这 25 万行从未落库。**
**但真因仍未证实**（§六 保持原样：形态已定、真因待外部证据）——
**「从未写入」只排除了「写完又丢」，没有告诉我们当时为什么没写。**

## playbook §28（本轮新增）

**「终态缺失」不能区分「从未写入」与「写入后被删除」。**
下结论前必须先查**删除路径本身是否原子**：

- 单条数据修改 CTE（`WITH batch AS (DELETE ... RETURNING ...), inserted AS (INSERT ... SELECT FROM moved)`）
  ⇒ 安全，失败整体回滚，**无丢失路径**；
- 手写 `INSERT;` 换行 `DELETE;` 两条语句 ⇒ **有丢失路径**，除非有显式错误处理兜住；
- 先 `DELETE` 后 `INSERT` ⇒ **必然有丢失路径**。

⇒ **且别用 `pg_class.reltuples` 支撑「某个分区是空的」**——它是估算，
本文件实测与父表 `COUNT(*)` 相差 106 行，并直接把一个「0 行」的分区说成了实际 2 行。
**涉及「某处为空/某物不存在」的断言，一律用 `COUNT(*)`。**
