## 一、可复现命令与口径（conventions §10.1：口径必须和数字一起发布）

```sql
-- 统一读视图：request_logs 族 = turns 优先 + legacy 回退（111 号已确认）
SELECT count(*)
FROM request_logs_with_current_month r
WHERE r.ts >= '2026-09-03' AND r.ts < '2026-09-12'
  AND NOT EXISTS (SELECT 1 FROM usage_ledger_with_current_month u
                  WHERE u.request_id = r.request_id);
-- → 256,422
```

**可复现性交叉验算**（换成结构不同的 `LEFT JOIN` 写法）：

```sql
SELECT count(*) FROM request_logs_with_current_month r
LEFT JOIN usage_ledger_with_current_month u ON u.request_id = r.request_id
WHERE r.ts >= '2026-09-03' AND r.ts < '2026-09-12' AND u.request_id IS NULL;
-- → 256,422   ← 与上式完全一致
```

反向验算（台账侧问「有没有对应的日志行」）= **2 行**，即台账侧几乎无孤儿。
⇒ 97 号记录的「Citus 列存 join 计数不可复现」**在本查询上不成立**，
因为两侧走的是同一套视图、且 `NOT EXISTS` 与 `LEFT JOIN` 结果逐个相同。

⚠️ **111 号记录的 254,230 已过期**（差 2,192）。本轮只更正数字，不追查当时为何不同
（可能当时窗口边界或数据落库时点不同）。**引用本条时一律用 256,422。**

## 五、111 号的「滚动发布新旧 build 并存」假设：**被证伪**

原假设（111 号 §九）：*「最可能：滚动发布期新旧 build 并存，旧 build 只写 request_logs 族」*。

- 滚动发布的特征是**覆盖率随时间渐变**（旧节点逐步下线，新节点逐步就位）。
- 实测是 **0% → 74% → 93% → 0%（连续 5 天）→ 99.6% → 100% 并保持至今**。
- **先恢复、后又全丢、再永久恢复**——这个形状不是任何单调的发布/迁移过程能产生的。

⇒ **该假设按其原表述证伪。**（此处只否定「滚动发布」这一个候选解释，
**不宣称已经找到真因**——真因未证实，见 §六。）

## 六、真因未证实 —— 但形态给了一个强约束

**形态**：两段完全中断（09-03/04、09-07~09-11），中间两天部分恢复（74% / 93%），
09-12 起永久恢复。

**74% / 93% 这种中间值是最有价值的线索**：单实例的开关翻转只会给 0% 或 100%；
**「部分节点写、部分不写」才产生中间值**。这与「**一个多节点 fleet 中部分实例的构建
不含台账写入路径**」一致，也与 09-12 起全部实例都写一致。

⚠️ **不下结论。** 需要的数据本轮不具备：
① 当时的**部署事件/版本时间线**（哪些实例在 09-03~09-11 跑的是哪个 build）；
② 当时的**实例级日志**（`telemetry ingest decision log failed` 之类的告警行——注意
   台账写入失败的日志与 `request_logs` 写入失败的日志**不是同一条**，见 §七）。
⇒ **登记为「形态已定、真因待外部证据」，不下结论。**

## 七、一个**必须一并记住的口径事实**

待裁决 42（台账行身份缺失幂等）的实测分母是「**0 / 2,067,960 重复**」。
**那个分母只覆盖「已经在台账里的请求」**，而本条说明
**台账的覆盖率本身在某些时间窗口是 0%**。

⇒ **「台账无重复」不等于「台账完整」**。
任何基于台账的成本/对账结论，**必须先声明它的时间窗口是否落在 09-03~09-12 内**；
落在窗口内的部分不是「数据不完整」，是**系统性缺失**，其上的对账结果（差异率、供应商结算）
**不可信**。这条直接影响 objective 的「费用计帐」与「数据闭环」两项要求。

## 九、playbook §27（本轮新增）

**「某段时间数据缺失」排查：先看逐日分布的**形状**，再谈成因。**

| 形状 | 指向 |
|---|---|
| 单调渐变 | 滚动发布 / 灰度迁移 |
| **0% / 100% 整天跳变** | 开关、构建差异、实例集合变化 |
| **出现 1%~99% 的中间值** | **多节点 fleet 里部分实例行为不一致**（最有价值的一档） |
| 逐渐变小但不为 0 | 抽样/降级/背压 |

⇒ **本例正是靠「74% / 93% 这两个中间值」才把假设空间收窄的**；
如果只统计总量（254,230）而不出逐日分布，会得到「一大片缺失」这种无法定位的描述，
并很可能顺手套上「滚动发布」这个现成解释——**而它是错的**。

**配套纪律 —— 排除一个假设要拿代码说话**：
§四 排除了 S4 开关，依据是**台账 INSERT 所在行号早于 `logsWrite` 首次出现 44 行**。
**「最合理的解释」恰恰是最需要先验证的那个**，因为一旦写进报告，读的人会直接采信。
