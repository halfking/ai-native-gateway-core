## 1. 订正 R77 的一处措辞

R77 报告写：「`DualWriter.Write` 文档承诺的第 3 步 `v2_dual_read` 校验全仓只存在于注释里……而双读差异正是 objective 的验证仪器，**目前没有任何自动一致性校验**」。

合并 `origin/main`（`989fd32b3`）后复核，**后半句过强**：

```
cmd/gateway/main.go:6555
    NewDualReadValidator(dbConn.Pool()).RegisterRoutes(mux, adminMw)
```

`cmd/gateway/dual_read_validator.go` 有 586+ 行，暴露 `handleDualRead` / `handleDualReadDrift` 两个 admin 端点，并实现 `Compare` / `CompareDetail` / `Summarize` / `driftBuckets`。它是**可按需调用的核验仪器**。

**但 R77 的核心结论仍然成立**，两条事实未变：
- `sessions_v2_dual_read_diff_total` 仍**零数据点**——`SessionsV2DualReadDiff` 全仓只有声明与注释，无递增点（`internal/metricguard` 的白名单仍登记着它）。
- `DualWriter.Write` 的第 3 步（`dual_writer.go:148-149`）**仍从未实现**，`v2_dual_read` 仍只出现在那两行注释里。

即：**拉取式核验仪器存在，推送式自动校验不存在**。归档文档 `40-V2集成实施总报告-20260724.md:180` 承诺的 `increase(sessions_v2_dual_read_diff_total[1h]) > 10` 告警规则**永远不会触发**。

## 2. 实证：仪器可用，真库首跑报出漂移

用 `Compare` 的原样 SQL 做裸 `PREPARE` + `EXECUTE`（真库 PG 17.10，只读）：

```
EXECUTE drv1('default','gw_adeaaa70-a1c9-4b8a-8565-9e147a42833d');
→ -4061339 | 0.00000000
```

SQL 本身**有效**。（我一度怀疑它踩了 R76 那个「同一 `$1` 绑给两个不同类型列」的坑——`v1` 用 `tenant_id::TEXT=$1`、`v2` 用裸 `tenant_id=$1`，而真库 `request_logs.tenant_id` 是 `text`、`session_turns.tenant_id` 是 `varchar`。实测 PREPARE 成功，PG 把参数推成 text 后对 varchar 隐式转换，**不是 42P08**。差点误报，记录在此。）

按 `request_id` 对齐拆解这 −4,061,339：

| 指标 | 值 |
|---|---|
| 逐条 token **完全一致**的轮次 | 1314 |
| 逐条 token **不一致**的轮次 | **4** |
| 仅 V1 有（V2 缺） | 2 行 / 88,514 tokens |
| 仅 V2 有 | 0 行 |
| 不一致轮次的 token 净差 | **+4,149,853** |

即：1314/1318 轮**完全对齐**，漂移几乎全部来自 4 个轮次。

## 3. 归因：4 个轮次全是「成功打到上游之前就失败」的请求

| turn | V1 tokens | V2 tokens | success | error_kind |
|---|---|---|---|---|
| 1318 | 0 | 1,909,825 | f | `prompt_too_large` |
| 1029 | 0 | 1,490,154 | f | `transient` |
| 365 | 0 | 637,190 | f | `no_candidates` |
| 52 | 0 | 112,684 | f | `invalid_key` |

四条的形态完全一致：**`success=false`、无 `upstream_status_code`、V1 `prompt_tokens=0`、V2 把全部金额记在 `prompt_tokens` 而 `completion_tokens=0`**。

这三类 `error_kind`（`no_candidates` = 网关侧准入拒绝、`invalid_key` = 凭据被拒、`prompt_too_large` = 上下文超长）都是**前置拒绝，请求根本没发到上游**。所以：

- **V1 记 0 是对的**（对供应商计费口径而言，没有实际消耗）；
- **V2 记的是网关构造 outbound body 的估算值**（对「我们尝试发了多大」有意义）。

**这不是数据损坏，是两侧字段语义不同**。但有两个后果：

1. **运维会追一个不存在的漂移。** 端点返回的 `TokenDiff` 把两侧当同义字段求和差，任何人看到 −406 万都会按数据损坏排查，而 99.8% 的轮次其实完美对齐。
2. **【待裁决】存储切换会改变失败请求的 token 口径。** objective 要求「全部转到 session_turns」，而切换后这 4 类请求的 token 统计会从 0 变成实际估算值。objective 同时要求「原则上所有操作不要影响客户端的观感」——这两条在这里冲突，需要产品定口径：是保留 V1 语义（失败记 0），还是接受 V2 语义（失败记估算）？

## 4. 差点报错的一次：49% 缺口是探针流量，不是数据丢失

### 4.1 触发

按 objective 的核心诉求（存储切到 `session_turns` 且「确保原有的 api 不出错能取到正确的数据」）做完整性核对，近 24h：

| success | request_status | V1 行数 | 在 V2 | 缺失率 |
|---|---|---|---|---|
| f | failure | 4308 | 1366 | 68.3% |
| **t** | **success** | **1349** | **687** | **49.1%** |
| f | in_progress | 3 | 0 | 100% |

**成功请求也有 49.1% 在 session_turns 里找不到**。这不可能用「V2 只存完成的轮次」解释，看起来是直击 objective 的 P0 数据丢失。

先排除混淆项：按小时看比例是 46.2%–55.3%、**16 小时稳定无阶跃** ⇒ 系统性而非配置切换；`sessions_v2.rollout_percent` 真库未设置（取 spec 默认 **0**）⇒ 也不是灰度采样。

### 4.2 排除过程

1. **不是 DualWriter 的灰度**：`NewDualWriter` **零生产调用点**（全仓只有文档注释、定义、测试）。`buildV2PipelineHooks` 恒 `return nil`，注释写明「V2 写入由 telemetry onPersisted 独占」。
2. **找到真正的门控**：`internal/sessionv2mirror/hook.go:56` 的 `PersistHook` 有 5 个提前 return，其中 `IsProbeSyntheticSession(entry)` 显式跳过探针——注释记录这是 R51/R60 的教训（探针合成系统会话后集中打 advisory lock，实测失败噪声 ~115/min，99.6% 为该类）。

### 4.3 判别查询（决定性）

| 类别 | success | V1 行数 | 在 V2 | 覆盖率 |
|---|---|---|---|---|
| 无会话头（探针特征） | f | 2934 | **0** | 0%（按设计排除） |
| 无会话头（探针特征） | t | 658 | **0** | 0%（按设计排除） |
| **有会话头（真实流量）** | f | 1377 | 1366 | **99.2%** |
| **有会话头（真实流量）** | t | 691 | 687 | **99.4%** |

**真实流量的 V2 覆盖率是 99.2% / 99.4%。整个 50% 缺口是被有意排除的探针流量。**

**结论：不是缺陷。** 我先前那个数字不是「发现」，是**把两个不同总体的分母混在一起**。若停在这里报 P0，会把一个设计决策当成数据丢失，并可能触发一次「修复」把已经正确的探针排除逻辑改坏。

> 这条是本轮最值得记的：**一个足够吓人的数字（49% 数据丢失）+ objective 明确要求它为 0**，几乎构成一个「必报」的组合。拦住它的不是谨慎，是「先找混淆项」这个动作。**

残余的真实小缺口：有会话头的失败请求缺 11 条（0.8%）、成功请求缺 4 条（0.6%）。**本轮未逐条归因**，登记为待查（见 §6）。

## 5. 其它发现

### 5.1【P2】`DualWriter` 是生产死代码，且 flag 名与注册键不一致

- `NewDualWriter` 零生产调用点；接口方法 `GetRolloutPercent` **全仓唯一实现是测试里的 `MockFeatureFlags`**。
- `dual_writer.go:180` 读 `"sessions_v2_rollout_percent"`（**下划线**），而 `settings/spec_sessions_v2.go:38` 注册的键是 `"sessions_v2.rollout_percent"`（**点号**）。**将来若有人接线，这个 flag 查找会读不到已注册的键**，静默取默认值（spec Default = 0 ⇒ V2 全不写）。

**本轮不改**：改一个死代码的 flag 名属于按猜测修。且照本项目既有纪律（不擅自推翻有记录的设计决定），是否复活 `DualWriter`（它与 `sessionv2mirror.PersistHook` 是两套并行的 V2 写入所有权）应先定架构。已连同 §3 的 token 口径一并登记待裁决。

### 5.2【P2·覆盖缺口】`dual_read_validator` 的测试全部传 nil pool

4 个测试：`Constructor` / `NilPoolCompare` / `SummarizeSignature` / `NilPoolSummarize`——**全部 `NewDualReadValidator(nil)`**。即「nil pool 不得 panic」被证明了，而 `Compare` / `CompareDetail` / `Summarize` / `driftBuckets` 里数百行真实 SQL **零测试覆盖**。

形态与 R76 的 P0 完全同型（sqlmock/假件只验签名与空指针，真实 SQL 从未被执行过）。本轮用真库 `PREPARE` + `EXECUTE` 证明 `Compare` 的 SQL 有效，但 `CompareDetail` / `Summarize` / `driftBuckets` **仍未验证**。

**本轮未补真库门**（上下文预算），登记为 R80 首选项。

## 6. 待裁决 / 待查（新增 3 条，累计 15 条）

1. **失败请求的 token 口径**：存储切换后 `prompt_too_large` / `invalid_key` / `no_candidates` / `transient` 这类前置拒绝的 token 从 0 变为实际估算值。与 objective「不要影响客户端观感」冲突，须定口径。
2. **`DualReadValidator.TokenDiff` 的可解释性**：当前把 V1/V2 当同义字段求和差，会把「失败请求语义不同」报成漂移。要么在 SQL 里排除 `success=false`，要么把该字段重命名/拆分并写进端点文档。
3. **有会话头请求的 0.6%–0.8% 残余缺口**（失败 11 条 / 成功 4 条，近 24h）：本轮未归因。可能是 outbox 重试耗尽、`in_progress` 悬挂、或写侧 best-effort 失败（`PersistHook` 的契约是「任何 DB 错误只 log 不阻断」——**失败会静默**）。

**R80 首选**：给 `dual_read_validator` 补真库门（`TEST_PG_DSN` 契约名，见 47 号报告），覆盖 `CompareDetail` / `Summarize` / `driftBuckets` 三段未验证的 SQL。
