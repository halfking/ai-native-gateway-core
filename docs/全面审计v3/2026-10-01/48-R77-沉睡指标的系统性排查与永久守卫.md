## 1. 危害形态：不是「少了个计数器」，是「面板看起来存在」

这类缺陷不崩溃、不出错值，表现为：

- `/metrics` 上该 series **恒为 ABSENT（不是 0）**；
- 用 `rate(x[5m])` 的告警规则**永不触发**（没有数据点）；
- 看板显示"无数据"，而**没人会因此去翻代码**——指标名在文档里写着，看板上也画着。

这比"指标值为 0"更危险：值为 0 至少说明系统跑过。

---

## 2. 实测：295 个声明 / 16 个零记录

用 Go AST 精确解析（正则抽取先试过，**只抓到 38 个**，不可信的扫描等于没扫），对每个声明的标识符在**非测试**源码里找**记录调用**（`.Inc/.Add/.Observe/.Set/.WithLabelValues/.With/.Dec/.Sub`）。

判据是记录调用、不是标识符引用——Go 不允许包级变量未被引用，所以「有没有被引用」恒为真，问不出任何东西。

**16 个零记录分布**：

| 指标 | 域 |
|---|---|
| `SessionsV2WriteSuccess` / `WriteFailed` / `WriteLatency` | **V2 存储写入**（objective 的存储切换） |
| `SessionsV2CacheHit` / `CacheMiss` / `DualReadDiff` | V2 缓存 / 双读比对 |
| `OmniFreePoolDedupModels` / `DedupPools` / `PreflightRejections` | 免费 token 池（objective 点名的域） |
| `RoutingHealthAutoRecover` / `...TickDuration` | 凭据健康自愈 |
| `autoRouteAffinityRankChurn` / `journeyRecorderWrittenTotal` / `metricActive` / `metricStatsDrop` / `sessionInspectorRecycleTotal` | 各域零散 |

## 3. 已修：V2 写侧 3 个指标接线

`domains/session/v2/turn_writer.go` 的 `appendTurnInLockedTx` 是 turn 写入的唯一漏斗，且是**命名返回值** `(turnNo int, err error)` —— 正好可以用 `defer` 覆盖全部 8 个 return 点。

**埋在 defer 里而不是主路径末尾，是 R74 的教训**：那里第一版放在函数末尾，测试当场 Skip（错误分支在 emit 之前就 return），绿灯只是因为路径没走到。

**观测口径已写进注释**（避免被当成"已提交的轮次"读）：这里量的是 **turn INSERT 自身**的结果。`AppendTurnInTx` 由调用方自管事务，提交点不在本函数内，所以「INSERT 成功但外层 commit 失败」会计入 success 而该行最终回滚。不把提交也纳入，是因为多个调用方各自管事务、没有单一提交点可观测，硬凑只会重复计数。**写失败一个都不漏**（任何非 nil 返回都计 failed）。

### 3.1 行为门（`turn_writer_metrics_test.go`）

用 pgxmock 驱动**真实的** `appendTurnInLockedTx`，断言计数器**真的动了**。为什么必须是行为门：静态字符串断言只证明"看到了调用"，而 R74 的教训恰恰是调用存在而数据点为零。

**门第一次就抓到了我自己的两个错**：

1. 断言方向写反——失败路径我断言 success 增 1。**按纪律先假设门是对的，结果是门错了**（实际 0 才对），改断言。
2. **门因为错误的原因而绿**：第一版只写 `require.Error`，而 pgxmock 的 `expected 0, but got 2 arguments` 同样满足它——真正的 stub 失败根本没发生。改成 `require.ErrorContains(err, "boom")`，并补齐 `WithArgs` / `pgxmock.AnyArg()`。

第 2 条是"门全绿≠门覆盖我"的又一次实例，而且是**我自己刚写的门**。

## 4. 永久守卫：`internal/metricguard`

把一次性排查变成 `make guards` 的一环（`GUARD_PACKAGES` 已登记，`guards-sync.sh` 同步检查通过，8 项全登记）。

四道门：

| 门 | 作用 |
|---|---|
| `TestNoPrometheusMetricIsDeclaredButNeverRecorded` | 任何指标不得处于"已声明但生产代码从不记录" |
| `TestKnownUnwiredEntriesHaveReasons` | 白名单每条必须写清**为什么不接线**（理由过短即红） |
| `TestKnownUnwiredHasNoStaleEntries` | 白名单条目失效或已被接线即红——防止**门对已接线指标失去约束** |
| `TestScannerDetectsUnrecordedMetric` / `TestScannerSkipsVendorAndBuildDirs` | 扫描器自身的判别力 |

**白名单不是免责条款**：本门第一次跑就抓到我在白名单里写的"同上"敷衍（理由过短），逼我把 13 条逐条写成具体原因。

**扫描器不许腐化**：`len(decls) < 100` 即红——一个"恒返回空"的守卫等于没有守卫（取自 `sql/schema/integration_gate_test.go` 的同类教训，那份守卫第一版用硬编码清单，仓内变化后悄悄什么都不匹配了）。

### 4.1 守卫自己缺判别力证据 → 补合成夹具自测

**用 `-overlay` 做变异时守卫照样是绿的。** 原因不是"变异没生效"，而是它靠 `filepath.Walk` 直接读磁盘，**overlay 只影响编译**。换句话说，"这道守卫有判别力"这件事当时没有任何证据——而恒绿的守卫正是本项目反复吃亏的形状。

处置：判别力改由**合成夹具自测**承担（`t.TempDir()` 里现写三个最小文件，分别喂"有记录/无记录/仅测试记录"三种形态，断言扫描器能区分），成为永久属性而非一次性手工检查。**"只有测试在记录"这一档尤其重要**——把它当覆盖就是本守卫最容易被绕过的形态。

### 4.2 真实文件上的变异验证

守卫读磁盘，只能真改文件：从 `turn_writer.go` 移除记录调用 ⇒

```
--- FAIL: TestNoPrometheusMetricIsDeclaredButNeverRecorded
    指标已声明但生产代码从不记录：SessionsV2WriteFailed   (sessions_v2_write_failure_total)
    指标已声明但生产代码从不记录：SessionsV2WriteLatency  (sessions_v2_write_latency_seconds)
    指标已声明但生产代码从不记录：SessionsV2WriteSuccess  (sessions_v2_write_success_total)
```

恰好 3 个、且正是被移除的那 3 个。**立即还原**，`cmp` 逐字节校验与变异前备份一致，埋点在位，两包复跑全绿。

### 4.3 性能：第一版 80s → 现 3.3s

第一版是「每个声明 × 每个文件跑一次正则」= 295 × ~3000，单测 40s、两门合计 80s，**塞不进 `make guards` 的 120s 预算**——等于一道没人会跑的门。改为单遍扫描（每个文件跑一次正则抓全部 `标识符.记录方法` 形态收进集合，再与声明集合求差），复杂度 O(声明×文件) → O(文件)。

`make guards` 全量 8 包 **6.0s**。

## 5. 13 个未接线的指标：为什么不擅自接

**`SessionsV2CacheHit` / `CacheMiss`**：分层缓存命中已有**更细粒度**的实现（`monitoring.StorageMetrics` 的 `RecordL1Hit` / `RecordL15HitForMode` / `RecordL2Hit`，覆盖 L1/L1.5/L2/L3 与 mode 维度）。但那个文件头**明写「刻意不接入 prometheus registry」**，其数据走 `storage` 快照端点。是否再加一个粗粒度的 `sessions_v2_cache_*` 进 Prometheus，是可观测性设计取舍——擅自加会**部分推翻一个有记录的设计决定**，且与 objective 的"数据展示统一性"相悖。故登记白名单并说明。

**`SessionsV2DualReadDiff`**：**它要度量的功能从未实现**——见 §6。

其余 10 个分属 omnifree 池、凭据健康自愈、autoroute affinity、journey recorder、credential quota、dispatch stats、session inspector，各自有明确的"待接线"前提，逐条写进白名单。**接线一个就删一条**，守卫会强制这件事发生。

## 6. 【P2】`DualWriter.Write` 的第 3 步不存在

文档承诺：

```
//  1. ALWAYS write to V1 (primary) - failure blocks request
//  2. IF v2_shadow_write enabled: write to V2 (shadow) - failure is logged
//  3. IF v2_dual_read enabled: validate consistency
```

但 `v2_dual_read` 在全仓**只出现在这一行注释里**，函数体做完第 2 步就 return 了，**没有任何一致性校验**。

这同时解释了 `SessionsV2DualReadDiff` 为什么零数据点：**不是漏接线，是它要度量的功能不存在**。R75 记录过一个同型误判（"某测试零调用" 被误读成缺陷），这次的教训是它的反面——**不是所有"零调用"都是接线遗漏**。

这条对 objective 直接相关：「将 request_logs 的存储切到 session_turns，**并确保原有 api 不出错能取到正确的数据**」——双读差异计数正是验证"切得对不对"的仪器。没有它，存储切换**没有任何自动一致性校验**。

**本轮只订正注释**（改为删除线并说明第 3 步从未实现），**不实现该功能**：它需要双读比对的设计决策（比哪些字段、在哪个采样率、差异算 error 还是仅计数），属需求缺口而非缺陷修复。
