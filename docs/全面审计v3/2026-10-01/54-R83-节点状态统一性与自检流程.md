# 54 号报告 · R83：节点状态统一性与自检流程（objective 的「统一状态模块」条目）

日期：2026-10-01
轮次：R83（主代理独立核实；一个 verifier 子代理的广度审计在本报告提交时**仍在运行**，其结论未纳入本文，见 §7）

## objective 原文

> 「全面检查**自检流程**的处理，并且注意全局的**节点状态需要统一**，状态更新需要**在一个模块中进行**，由它来响应**多个地方**的反馈的请求的正常或失败的结果对系统内的节点状态及统计相关的处理。」

拆成三个可验证断言：
- **A1 统一**：全局节点状态只有一个真源。
- **A2 集中**：状态更新发生在一个模块里。
- **A3 扇入**：该模块响应**多个来源**的反馈，含**请求的正常/失败结果**。

## 0. 结论

**A1/A2 对「请求结果」这条链成立；「自检/探测」那条链不成立。**

| 断言 | 结论 | 依据 |
|---|---|---|
| A1 统一 | **部分成立** | 请求侧真源唯一（`domains/credential/writer.go`）；`health_status` 由 4 处独立写 |
| A2 集中 | **部分成立** | 同上 |
| A3 扇入 | **请求侧成立**（`RecordOutcome` → `RestoreOnSuccess`/`WriteOnError`）；**探测侧扇入无归因**（见 D1） |

## 1. 请求结果确实汇入单一模块（A3 请求侧成立）

链路（逐跳核实）：

```
domains/streaming/executors/executor_chat.go:1444
  e.PostExecutionHook.RecordOutcome(ctx, ExecutionOutcome{...})
    → execution_recorder.go:34 RecordOutcome
      → StateWriter.RestoreOnSuccess(...)   // 成功
      → StateWriter.WriteOnError(...)       // 失败
        → domains/credential/writer.go:62 / :221   ← 生产实现，唯一
```

`credentials.circuit_state` 的 `'closed'` 写入方**只有一个**——`cmd/gateway/main.go:2069` 的注释明写这一点。这是有记录的不变量。

### 1.1 模块内部是刻意的两级设计，且有历史 bug 佐证

`writer.go:431-446` 记录了设计理由与一次已修的结构性 bug：

- **模型级失败**只写 `cmb` / `model_offers`，**不碰** `credentials.availability_state`——防止跨模型污染。
- **凭据级失败**（quota/auth）由 `WriteOnError` 内部的 SQL **直写** `availability_state`（仍在同一模块内，理由是整个凭据不可达而非单模型）。
- 注释记载：**2026-06-23 移除遗留的 `writeModelLevelFailure`**（它会写 `availability_state`），起因是它造成「`minimax-m3` 失败把 `minimax-01` 一并标为不可用」，并称「现在结构上不可能再发生」。

⇒ **请求路径的状态更新确实是集中的、且经过真实缺陷的淬炼。** objective 的 A2 在这条链上达成。

## 2. D1【P2】`health_status` 的 4 个写入方不可归因

### 2.1 事实

`credentials.health_status` + `health_source` 由 **4 处生产写点、跨 2 个包**写入：

| 写点 | `health_source` 取值 | 性质 |
|---|---|---|
| `bg/credential_probe_v2.go`（2 处，SQL 参数化 `health_source = $5`） | Go 结构体里 `probe` 或 `probe_now`（`:2022, :2040`） | 后台自检 |
| `bg/credential_recovery.go` | 硬编码 `'probe'` | 恢复流程 |
| `bg/credential_cycler.go` | 硬编码 `'probe'` | 凭据轮换 |
| `admin/provider_cred_lifecycle.go:363` | 硬编码 `'probe'` | **管理员手动探测** |

真库实测（86 条凭据）：

| `health_source` | `health_status` | 条数 |
|---|---|---|
| `probe` | healthy / unknown / unreachable | 39 / 17 / 2 |
| `probe_now` | healthy / unreachable | 14 / 10 |
| NULL | unknown | 4 |

⇒ **`recovery`、`cycler`、管理员手动探测三者写的是同一个字面量 `'probe'`**，DB 无法区分某条 `health_status` 是谁写的。

### 2.2 为什么这是缺陷而不是风格问题

`health_source` 这一列的存在本身说明它的用途是**归因**：迁移 `sql/migrations/startup/044_health_source_probe_now.sql` 专门为扩展这个词汇而新增了一个值——即有人发现「光有 `probe` 不够用」，但采取的是**加值**而不是**修那三处硬编码**。

后果：当某个凭据被标为 `healthy` 而运维要追「为什么」，可得的结论是「某次 probe」，而无法区分是后台自检、恢复流程、凭据轮换还是人工点的探测。**在「按需归因」的设计意图下，归因链是断的。**

### 2.3 附带：该写点的错误被静默丢弃

`admin/provider_cred_lifecycle.go:362` 的 SQL 带 `//nolint:errcheck // best-effort exec, non-critical`，`h.db.Exec` 的返回值被丢弃。若该 UPDATE 失败（DB 错误、RLS、连接中断），**健康状态不会被记录，且无任何告警**。这与本项目反复出现过的「best-effort 通道静默失败」同型。

**定级 P2**：不产生错误数据（丢的是「一次状态更新」而非「错误的状态」），但让归因链断裂且失败不可见。

## 3. 辨析：13 个状态字段**不是**同一份状态（避免误报）

`credentials` 上有 13 个状态类字段。**必须先分清语义，否则「多处直写」根本不是缺陷**——这一步是本轮的关键防误报动作：

| 字段对 | 真库逐行差异 | 语义判定 |
|---|---|---|
| `health_status` vs `availability_state` | **81/86 不同** | **不同语义**：前者是探活原始结果（healthy/unknown/unreachable），后者是路由可用性（ready/auth_failed/suspended/unreachable）。二者本就不该相等 |
| `status` vs `lifecycle_status` | **17/86 不同** | `status` 含 `deleted`、`lifecycle_status` 对应 `retired`；`status=disabled` 时 `lifecycle_status` 仍常为 `active` ⇒ 生命周期维度的粒度比可用性维度粗 |

⇒ **不能把「同一张表上的多个状态字段」当成「状态分叉」。** 已核对：`availability_state` 的直写集中在 `WriteOnError` 内部（仍在统一模块内）与 `admin/routing.go:4913`（oauth 清理，一次性运维动作）。
