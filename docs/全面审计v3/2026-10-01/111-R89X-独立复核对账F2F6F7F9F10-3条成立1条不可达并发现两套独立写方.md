## 二、F2 成立：网关侧只有 5% 的成功请求有成本，对账结论会是一个自信的错误数字

`PGGatewayMonthlyUsageSource.MonthlyUsageByProvider`（`pg_reconciliation_store.go:195-210`）：

```sql
WITH deduped AS (
    SELECT DISTINCT ON (request_id) provider_id, prompt_tokens, completion_tokens, total_tokens, cost_usd
    FROM usage_ledger_with_current_month
    WHERE ts >= $1 AND ts < $2 AND provider_id IS NOT NULL
    ORDER BY request_id, ts DESC
)
SELECT provider_id, COALESCE(sum(prompt_tokens),0), ..., COALESCE(sum(cost_usd), 0)
```

**网关侧金额 = 台账 `cost_usd` 之和，而 `cost_usd` 是网关自己的本地估算**（104 号已坐实其第二种静默失效：无定价 ⇒ NULL）。子代理只说到「是估算」为止，本轮把它的**实际量级**量出来了：

```
月份            行数        有 cost    占比      sum(cost_usd)
2026-09     2,064,820      14,265     0.69%      1,139.6227
2026-10         3,138          13     0.41%         0.0000

按成功/失败：
success=false  1,783,564 行，27 行有 cost
success=true     284,396 行，14,253 行有 cost  ⇒ 成功请求中仅 5.01% 有成本
```

**⇒ 这就是新的 P1（第 47 条待裁决）**：对账拿「只覆盖 5% 成功流量的估算」去和供应商真实账单比，
`COALESCE(sum(cost_usd), 0)` 又把「没有价格 / 没算出来」**编码成 0**（不是 NULL），
于是差异率会是一个**自信的、看起来完全合理的 −95%**，
运营会照着它去和供应商扯皮「你多收了我 95%」。

这是本审计已记录的「**『未定义』不可编码进 0/NULL**」形态的**第四个出现位置**，
但**在这里危害最大**：前三处最多让 UI 上「未定义」与「差异 0%」同形，
这一处直接驱动一个**对外的商务结论**。

**修法方向**：`MonthlyUsageByProvider` 必须区分三态——
`sum(cost_usd) FILTER (WHERE cost_usd IS NOT NULL)` + `count(*) FILTER (WHERE cost_usd IS NULL)`，
覆盖率低于阈值时**拒绝出具差异率**（或置为哨兵值，不参与告警判定），
而不是拿一个 5% 覆盖的数去和账单对账。

## 三、F6：latent，**当前不发生**——但触发条件可以写死

- **窗口是对的**：`WHERE ts >= $1 AND ts < $2`，`month` 由
  `CostReconciliationMonthsToAggregate`（`bg/cost_reconciliation_worker.go:90-94`）用
  `now.Location()` 构造成**进程本地时区**的月初。`ts` 是 timestamptz，比较按绝对时刻，
  所以**聚合窗口本身是进程本地月**，正确。
- **标签可能错**：`reconciliation_month` 是 `date` 列，传入的 timestamptz 按
  **PG 会话 TimeZone** 转型。标签与窗口因此用**两套时区规则**。
  若会话时区是 UTC 而进程是 +08:00，`2026-09-01T00:00+08:00`（= 08-31T16:00Z）
  转型成 date 会得到 **2026-08-31** ⇒ **整月数据被标成上一个月，且不报错**。
- **本库实测**：`SHOW TimeZone` = `Asia/Shanghai`，与进程一致 ⇒ **当前不发生**。
  `provider_cost_reconciliation` 现为 0 行，无法用数据反证。

⇒ 判 **latent P3**，触发条件写死为「**PG 会话时区 ≠ 进程时区**」。
修法一行：把 `month` 在 Go 侧格式化成该月第一天的**纯 date 字符串**再传参，不让 PG 推断。

## 五、F9：成立，且真实语义是「**每月至多一条，越严重也不会再报**」

`PGReconciliationEventSink.EmitCostDiffAlert`（`pg_reconciliation_store.go:277-283`）：

```sql
SELECT EXISTS(SELECT 1 FROM provider_events
              WHERE event_kind = 'cost_reconciliation_diff'
                AND payload_json->>'provider_id' = $1
                AND payload_json->>'month' = $2)
```

`AggregateMonth` **每天**跑（`provider_profile_init.go:185` interval 默认 86400s），
每次都调 `alertIfBreached`，但 sink 只要看到该 `(provider, month)` 已有事件就静默跳过。

⇒ **一个月份里第一次越线是唯一一次会报的**：
差异率从 5% 恶化到 500%，**不会再有任何事件**；
若首次是 token 差异越线而后来 cost 差异暴涨，**cost 告警被抑制**；
且**没有 resolved / 恢复事件**，无法区分「已解决」与「再没检查过」。

代码注释（`reconciliation.go:184-185`）写的是「告警 sink 侧按 (provider, month) 幂等去重」——
**把限制写成了意图**。按本审计的注释纪律：注释承诺的语义不成立时，
**以代码为准，并把注释列为待修**。

## 六、F10：成立——默认关闭，且端点是**不存在**而非「拒绝」

- `costReconciliationEnabled()`（`provider_profile_init.go:219-229`）默认 **`false`**。
- 关闭时 `CostReconciler` 为 nil ⇒ `main.go:3946-3950` 的
  `SetProviderCostReconciliationHandler(...)` **根本不执行** ⇒ 管理端路由**未注册** ⇒ **404**。

⇒ objective 明确要求的「内部费用计帐及与供应商进行对帐的功能及相关的菜单整理」，
**默认状态下整个不可用，且是 404 而不是 403**——
运维看到 404 会以为「这个功能没开发」，而实际是「开发好了，默认关着」。

## 七、【新发现，比待裁决 42 更重要】这两张表有**两套独立写方**

```
写方 A：domains/hooks/observability/telemetry/client.go:1284  INSERT INTO usage_ledger_hot
                                                          :1339  INSERT INTO request_logs_hot
写方 B：admin/telemetry.go:415                                INSERT INTO usage_ledger_hot
                                :454                          INSERT INTO request_logs_hot
```

**100 号 / 102 号的整条分析（台账行身份缺失幂等、歧义提交、三表后果非对称）
只覆盖了写方 A。** 本轮核到写方 B 后：

- **B 的 ledger INSERT 同样没有 `ON CONFLICT`**（`admin/telemetry.go:414-434`），
  唯一键同样是 `(request_id, ts)` ⇒ **只修 A 不足以消除 42 的触发面**。
- **B 有一个 A 没有的 S4 停写门控**（`admin/telemetry.go:441-445`）：
  `request_logs_write_enabled=false` 时**只写 ledger、跳过 request_logs**，
  且注释明写「提交逻辑不变」。
  ⇒ **在门控开关的不同取值下，「哪张表缺哪张」会反向**：
  写方 A 产出「有账本无宽表」，写方 B 产出「有宽表无账本」**的反面**（有账本无宽表）。
  **任何「两表行数应当相等 / 应当一一对应」的假设在当前代码下都不成立。**

⇒ 42 的修法必须**同时覆盖两个写方**，否则改完 A 之后 B 仍会漏。
（42 属待裁决项，本代理不擅自动手，仅补上这个前提。）

## 八、待裁决 42 终于拿到分母：**2,067,960 次提交，0 重复**

```
台账： rows=2,067,960   distinct request_id=2,067,960   重复行=0
宽表： rows=2,324,470   distinct request_id=2,324,470   重复行=0
```

⇒ **「歧义提交导致台账重复行」在本库 206 万次写入中发生 0 次。**
这与 102 号的收窄结论（「只剩歧义提交一种，且是罕见事件」）一致，
但**从「推断它罕见」升级为「实测 0/2,067,960」**。

⇒ 对 42 的处置建议随之明确：**缺陷成立、修法不变，但按正常排期处理，不需要当紧急止血**。
（诚实边界：本实例未必经历过 commit 阶段的连接中断，
所以 0 只能证明「常规路径不产生重复」，不能证明该触发器不存在。）

## 九、我自己在本轮犯的一次错误结论，**当场拦下并记录**

我先看到 `request_logs_with_current_month` 2,324,470 行 vs
`usage_ledger_with_current_month` 2,067,960 行，**差 256,510**，
且 09-03~09-11 有整天「只在宽表侧、一行都不交集」（如 09-07 的 70,757 行）。
我据此判：**「账本漏写 25 万行」**。

**读视图定义后该结论作废**：`request_logs_with_current_month` **根本不读 `request_logs_hot` 主体**，
它是 objective 那次「request_logs → session_turns」迁移的**统一读视图**：

```
session_turns_hot  LEFT JOIN session_turn_details_hot
UNION ALL
session_turns      LEFT JOIN session_turn_details
UNION ALL
request_logs_..._without_request_class_due_at
    LEFT JOIN LATERAL (request_class FROM request_logs_hot / request_logs)
WHERE NOT EXISTS(… session_turns_hot …) AND NOT EXISTS(… session_turns …)
```

⇒ **那个差值是视图口径差（session 族 ∪ legacy 族的并集 vs 单一台账族），不是写入缺口。**

仍然成立的那一层观察：09-03~09-11 有 **254,230 个 `request_id` 只存在于 session/legacy 族、
不在台账里**。**归因未证实**——最可能是滚动发布期间新旧 build 并存
（旧 build 只写 request_logs 族），但**我没有证据，不下结论**，列入待跟进。

**这条错误的方法论价值比结论大，已入册 playbook §19。**
