## 一、代码：`loadStats` 的三个相关子查询

`domains/analysis/optimizer.go:188-199`（`OptimizationAdviser.loadStats`）：

```sql
SELECT ss.session_key, ss.tenant_id, ss.request_count, …,
       COALESCE((SELECT SUM(COALESCE(cache_read_tokens,0)) FROM request_logs
                 WHERE gw_session_id = ss.session_key), 0),                    -- ① cache 读取量
       COALESCE((SELECT COUNT(*) FROM request_logs
                 WHERE gw_session_id = ss.session_key
                   AND compression_strategy IS NOT NULL AND compression_strategy != ''), 0),  -- ② 压缩次数
       COALESCE((SELECT SUM(COALESCE(outbound_token_est,0)) FROM request_logs
                 WHERE gw_session_id = ss.session_key), 0)                     -- ③ 出站 token 估算
FROM session_summaries ss
WHERE ss.session_key = $1
```

三处都读**裸 `request_logs`**（不含 hot）⇒ 对**请求仍留在 hot 的活跃会话**，三项都会漏掉最近一段；
若该会话的对应值**全部**落在最近 8h，则读出 **0**（`COALESCE` 兜底）。

⚠️ 这是**会话优化建议引擎**的输入。若压缩次数读成 0 而该会话实际在压缩，
引擎会**建议「开启压缩」**——那才是最严重的形态。**本轮就是去证伪它。**

## 二、量化（**统计用含 hot 的视图**，见 135 号 §32 纪律）

| 指标 | 值 |
|---|---|
| 有 `gw_session_id` 的会话总数 | 849,605 |
| **最近 8h 内有行的会话**（⇒ 裸父表读不到那一段） | **748（0.088%）** |
| **`cache_read_tokens` 会被裸父表读成恰好 0 的会话** | **3** |
| **`compression_strategy` 计数会被读成恰好 0 的会话** | **0** ★ |
| 同时出现在 `session_summaries` 与日志中的会话 | 334,009 |

### 两个结论

1. **★ 最吓人的版本被证伪**：
   假如 ② 对某些会话读成 0，优化引擎会对**正在压缩**的会话建议「开启压缩」——
   **实测这样的会话是 0 个**。⇒ **本实例不存在该失效。**
2. **真实形态是「少数会话少算了一截」**：748 个会话（0.09%）的三个指标漏掉最近 8h 那一段；
   其中 3 个会话的 cache 读取量恰好被读成 0。
   ⚠️ ③ `outbound_token_est` **本轮未单独统计**（与 ① 同形）——如实登记，不外推。

## 三、诚实的定性

| 项 | 结论 |
|---|---|
| 「读裸父表 ⇒ 漏最近 8h」 | ✅ 代码层无条件成立 |
| 「优化引擎会对正在压缩的会话建议开启压缩」 | ❌ **证伪**（0 个会话） |
| 「少数会话统计偏小」 | ✅ 成立，**0.09%**，极端 case 3 个 |
| 定级 | **latent P3**（与 135 号同族） |
| 修法 | **一词**：`FROM request_logs` → `FROM request_logs_with_current_month`（三处） |

⚠️ **实例事实 ≠ 生产结论**：0.09% 是**本实例**的分布。
生产若流量更高、活跃会话占比更大，这个比例会同步变化——
**但「压缩次数读成 0 ⇒ 建议开启压缩」这个严重形态，
只要 `session_summaries` 里有会话的全部压缩记录都落在 8 小时内就会发生**，
而 8 小时对一次长会话（objective 里的「超长会话 + 1M handoff」）**是完全正常的时长**。
⇒ **故按 latent 报，不按「已发生」报；但修法成本只有三处一词，值得直接带上。**

## 四、playbook §33（本轮新增，135 号 §32 的姊妹条）

**「会给出错误建议」的类缺陷，必须先证明「建议确实是错的」，再去量化比例。**

- 本轮的叙事顺序刻意是：先读代码发现「三个指标读裸父表」
  → 自然假设「压缩次数会读成 0 ⇒ 建议引擎会说反话」
  → **实测「读成 0 的会话 = 0 个」，假设被证伪**
  → 最后才报「0.09% 少算了一截」。
- **若跳过证伪那一步**，报告就会是「优化引擎会对正在压缩的会话建议开启压缩」——
  **这是一个具体、吓人、且方向完全错误的结论。**

⇒ **纪律：先证明后果，再量化规模。顺序反了会把「可能」写成「正在」，
把 latent 写成现役。**
**配套：严重形态与温和形态要分别取证**——本轮「压缩读成 0」= 0
**不能**用来否定「cache 读成 0」= 3，两者是不同指标，不可互相替代。

**同族**：§32（盲区是否引入新实体）、§31（先数再定性）、§24（证据与前提不同期）。
**共同点：全都是「**先确认后果成立，再谈规模**」——
本轮是「后果不成立时，仍要如实报规模，但不报后果」。**
