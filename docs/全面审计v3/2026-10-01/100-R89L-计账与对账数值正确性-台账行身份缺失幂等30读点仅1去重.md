## 0. 一句话回答 objective「费用计帐与对帐」

**「一次请求被按 attempt 重复计账」这个担心不成立**——成本只在 `emitTelemetry`
按 request 级算一次，中间 attempt 不写任何金额（§1.6）。
**但台账行本身没有幂等身份**：`usage_ledger` 与兄弟表 `request_logs`
走的是两套不同的唯一键口径，而 30 个消费该台账的读点里只有 1 个去重，
且**这 1 个的去重理由在注释里被写错了**——它防的不是真实成因（§1.4）。
一旦同一 entry 被落库两次，费用会同时在**台账行**与**`api_keys` 累加器**上翻倍，
而其中一条读路径是 **API Key 预算强制**（§1.5），后果是客户端被拒。

## 1. 主代理逐条复核的部分（本轮核心，全部代码事实）

### 1.1 台账唯一键比兄弟表弱一档——且这是**已知问题，只是没同步改**

`sql/migrations/startup/344_usage_ledger_hot_independence.sql:32-33`：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS usage_ledger_hot_request_id_ts_key
ON usage_ledger_hot (request_id, ts);
```

对照 `domains/hooks/observability/telemetry/client.go:1477-1481` 的注释——
`request_logs_hot` 曾因**完全同类的问题**把主键从 `(request_id, ts)` 改成 `request_id`：

> Migration 455 (2026-07-23) gave request_logs_hot PRIMARY KEY (request_id),
> so ON CONFLICT must be (request_id). Using (request_id, ts) here triggers
> SQLSTATE 42P10 ...

**两张表本该同口径，`usage_ledger_hot` 漏改。**

### 1.2 台账 INSERT 无 `ON CONFLICT` ⇒ 它没有任何自去重能力

`client.go:1283-1299`：`INSERT INTO usage_ledger_hot (...) VALUES ($1, now(), ...)`
——**没有冲突子句**，且 `ts` 由 `now()` 生成。
⇒ 同一 `request_id` 的第二次插入**必然成功**（`now()` 不同 ⇒ 键不同）。

**关键：三张表的写入在同一个事务里**（`client.go:1258-1262` 注释自陈
"we wrap usage_ledger + request_logs + api_keys updates in a single transaction"），
而 `request_logs` 那侧是 `ON CONFLICT (request_id) DO UPDATE`（`client.go:1481`）——
**它把重复吸收了，台账没有**。
所以「重复插入」这个动作在事务层面**不会失败、不会回滚、不会被察觉**。

### 1.3 视图不做去重，而它有约 30 个生产读点

`sql/objects/views/usage_ledger_with_current_month.sql:5` 起：
`SELECT * FROM usage_ledger_hot UNION ALL SELECT * FROM usage_ledger`——
**裸 UNION ALL，无 DISTINCT**。

全仓生产读点统计（`grep -rn usage_ledger_with_current_month`，排除测试与 SQL 基线）：

| 读点 | 是否去重 |

| `admin/usage_enhanced.go` :97/:396/:437/:445/:541 | ❌ 直接 `SUM` |
| `admin/usage_provider_detail.go` :99/:161/:234 | ❌ |

### 1.4 唯一那 1 个去重，**理由写错了**——这是本轮最有价值的一条

`pg_reconciliation_store.go:182-184` 作者原注释：

> promote 窗口内 hot 与分区可能短暂同时持有同一 request_id，
> **DISTINCT ON 去重防双计**（镜像旧查询形态）。

**我复核了 promote 函数，这个理由不成立。**
`344_usage_ledger_hot_independence.sql:136-157`：函数体是单事务，
顺序是 **先 DELETE（:150）后 INSERT（:154-157）**，两条语句在同一 plpgsql
函数体内，原子提交；MVCC 下**不存在「hot 与分区同时持有同一行」的已提交窗口**。

**⇒ 真正会造重复的是写方（§1.2），不是 promote。**
这个 `DISTINCT ON` 恰好也挡住了写方的重复，但它是**挂在错误理由上的偶然防御**，
而且**只挂在 30 个读点里的 1 个**。

**副作用（次要，但同一处）：** `:155-157` 的 INSERT 被包在
`BEGIN ... EXCEPTION WHEN OTHERS` 子块里，而 DELETE（`:150`）在**子块之外**。
若 INSERT 真的抛异常，plpgsql 的异常子块只回滚子事务，**DELETE 不会被回滚**，
函数仅 `RAISE WARNING` 后 `n := 0` 返回 ⇒ **该批次用量记录被永久删除且无告警升级**。
（触发条件罕见，且父表唯一约束由 `LIKE ... INCLUDING ALL`（:22）继承、
`ON CONFLICT (request_id, ts)` 在 :66 已成功使用过，故判定为 **P3 健壮性缺口**而非现网丢数。）

### 1.5 其中一个读点是**预算强制**——后果直接打在客户端身上

`domains/authentication/verifier.go:786`：

```sql
SELECT COALESCE(SUM(cost_usd), 0)::float8
FROM usage_ledger_with_current_month WHERE api_key_id = $1
```

无去重；`spent >= *budget` 时返回 `BudgetExceededError`（`:799`）。
⇒ 一旦台账存在重复行，**API Key 会在实际花费低于预算时被拒绝**。
这与本审计一贯的「原则上不改变客户端观感」约束**方向相反**——它会改变。

### 1.6 健康的部分：不存在按 attempt 重复计账

`AssignRequestCost`（`domains/streaming/usage.go:255`）的非测试调用点只有
`handler.go:6601`（`emitTelemetry` 内），而 `serveWithExecutor` 是顺序单次调用。
重试/failover 循环封闭在 `executors` 内，per-attempt 表
（`candidate_failure_logs_hot` / `supplier_errors_hot`）**不含金额列**。
**按 qr 记，不是按 attempt 记**——这是本轮最该说清楚的一条正面结论。

### 1.7 `api_keys.total_cost_usd` 是无幂等守卫的加法累加器

`client.go:1844-1852`（INSERT 路径）与 `client.go:2475-2483`（UPDATE 路径）
是**逐字相同**的两条 SQL：

```sql
UPDATE api_keys SET
    total_requests = total_requests + 1,
    total_prompt_tokens = total_prompt_tokens + $2,
    total_completion_tokens = total_completion_tokens + $3,
    total_cost_usd = total_cost_usd + $4,
    last_request_at = now()
WHERE id = $1
```

**无幂等列、无 CAS、无去重键**（不只金额，`total_requests` 同样被重复累加）。
**对照：`domains/session/v2/session_aggregator.go:197-213` 用
`aggregate_applied_at IS NULL` 的 CAS 做了正确防护** ⇒ 本仓知道正确写法，此处是遗漏。

**⇒ §1.2 的台账重复与本条的累加翻倍，共用同一个触发前提：
「同一个 entry 被落库两次」。** 这不是两个 bug，是一个根因的两个出口。

### 1.8 我**没有**闭合的那一环（如实登记）

**「同一 entry 被落库两次」在生产是否真实发生，我没有只靠代码证明。**
已排除的路径：`persistRequestLog`（`client.go:1131-1148`）在 `degraded` 为真时
**只写 fallback 文件、不碰 PG**（`:1143-1148`），`ReplayFallback`（`:725-747`）
的注释自陈「进 fallback 文件的 entry 此前必然从未成功落库」⇒ 设计意图是 exactly-once。

**未闭合的缺口**：`degraded` 标志是在 worker 处理时读的（`:1143`），而 enqueue 时读的是另一个时刻。
若 entry 入队时 `degraded=false`、处理时翻转为 `true` → 写 fallback；
若期间**另有**路径已写过 PG（`updateRequestLog` 的 RowsAffected 回落到 Insert，见 `client.go:2445`），
就会形成「PG 一行 + fallback 一行」，回放时再插一行。
**要证伪/证实需要真实流量或 PG 错误分类统计，我本轮未做（真库 join 计数按纪律不采信）。**

**因此本条定级为 P1 而非 P0**：
**「台账行身份缺失幂等 + 30 个读点只有 1 个去重」是已证的代码事实**；
**「已发生重复计费」未证**。子代理给的是 P0，我按纪律下调并说明理由。

## 2. 供应商对账（**子代理结论，我本轮未逐条复核**）

- 子代理报：对账链路**真实存在**（定时 worker + 2 个 HTTP 端点 + 差异率 + 告警），
  但**两侧口径不同源**——网关侧 `cost_usd` 是本地按 offer 单价**估算**，
  供应商侧是**人工录入**（`DataSource` 硬编码 `"manual"`），无拉单 API。
- 报出 F1–F10，其中自评 P1 的四条：F1 对账侧无计费资格过滤（未复用 `shouldChargeUsage`）、
  F2 金额是本地估算不可作真实成本证据、F3 缓存 token 口径缺失导致差异率**结构性误报**、
  F4 `provider_total_cost = 0` 时差异率静默归零致**大额漏账不可见**。
- 自评 P2 的 F5 值得一提：`cost_diff_rate` 列型为 `numeric(5,4)`（上界 9.9999），
  差异超 10 倍即写库溢出，且失败会**中断整月其余供应商的刷新**。

**⚠️ 这四条我一条都没独立验证。下轮必须逐条回原代码复核后再定级。**
我本轮只确认了一件相关事实：**对账侧确实读的是 `usage_ledger_with_current_month`**（§1.3），
所以它与那 29 个不去重读点**共享同一个台账行**——若 §1.1 的重复成立，
对账侧因有 `DISTINCT ON` 而**幸免**，其余 29 处**全部中招**。
