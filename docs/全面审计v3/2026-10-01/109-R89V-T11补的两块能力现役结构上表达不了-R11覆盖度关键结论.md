  ⇒ T11 不是重复实现，但也不是「全量替换」——它是这两块的补齐。**

## 0. 一句话

108 号把决策悬在「T11 要不要做」。本轮把它落到具体判据：
**现役的压缩缓存失效键全部派生自 outbound body（单层视角），
所以「sanitize 层变了」不会让已压缩产物失效；而修订状态机现役完全没有。**
**这两块是 T11 独有的，不是重复实现。**

---

## 1. 现役有的：单层复用 + TTL 失效

`domains/hooks/compression/session_cache.go:149-171` 的 `SessionState` 存：

| 字段 | 内容 |
|---|---|
| `LastOutboundHash` (loh) | sha256 of last outbound body |
| `ToolsHash` (th) | sha256 of tools array |
| `SystemPrompt` (sys) | 缓存的系统提示词 |
| `FullSessionHash` (fsh) | 完整未压缩 session body 的 sha256 |
| `SummaryMarker` (smm) | `smm_v1:<sha256>` |
| `MsgCount` / `LastStripAt` / `StripsApplied` / `CompressionMode` | 统计与模式 |

外加 `cut_marker.go:104-116` 的 `CutMarker.IsExpired(ttl)`：
纯时间判定，并有一道「未来 marker 不可信」的守卫（`:111-114`）。

**现役也有真实的复用路径**：`recovery_coordinator.go:156,315`
「reused cached cut marker from prior compression」/「reused persisted V2 cut marker」。

**⇒ 所以 R11.4「复用判定」在现役**不是空白**，是另一种形态**（cut marker + TTL + body hash）。

---

## 2. 现役缺的第一块：**跨层失效**

**现役的每一个失效键都派生自 outbound body / tools / system prompt——
它是一个单层视角，压根不看 sanitize 层。**

`domains/hooks/compression/` 全目录检索
`dependencyhash|dependency_hash|revalidat`：**0 命中**（除 `compressor.go:309` 一句
「如果未来支持热更新，需要在这里加锁 + invalidation」的未来时注释）。

**而 T11 的 R11.5 补的正是这个**——`domains/session/preprocess/deps.go`：

```go
func (d RawDependencies) Hash() [32]byte
func (d SanitizedDependencies) Hash() [32]byte
func (d CompressedDependencies) Hash() [32]byte
func ComputeDependencyHashes(deps ArtifactDependencies, committed SessionRevision,
                             rawSource, sanitizedSource [32]byte) DependencyHashes
```

**三层各自的依赖哈希 + 已提交修订 + 上下游 source hash 汇总**，
配合 R11.4 的四条件（`ReadyBit && !StaleBit && SourceRevision==当前修订
&& DependencyHash==当前依赖哈希 && ContentHash 校验通过`）。

**⇒ 真实缺口：sanitize 层的实现变了（占位符格式、还原规则、脱敏策略变更），
现役缓存无法感知，旧的 Compressed 产物会继续被复用。**
**这是结构性的，不是「忘了加个字段」能解决的**——现役的键里根本没有这一维。

---

## 3. 现役缺的第二块：**修订状态机**

在 `domains/hooks/compression/` 与 `domains/streaming/executors/executor_responses_provenance.go`
两个目录检索：`chainhash|chain_hash|provisional|definitive|rebase|sourcerevision|source_revision`
—— **0 命中**。

而 T11 的 R11.6（README `:34-40`）定义的是：
- `Prepare` 产出 **provisional** revision（TurnNo+1 / HeadRequestID / **ChainHash=Advance(prev, deltaHash)**），**不推进**持久修订；
- `CommitFirstForward` 仅在 `beginUpstreamAttempt && AttemptNo==1` 时 CAS 提交 provisional→definitive，**重试/换节点复用同一 bundle**，重复提交幂等；
- **CAS 冲突 reload 后 rebase 到新修订之上，绝不覆盖**；
- `AppendTerminal` 推进 chain hash，使 Sanitized/Compressed 变 stale。

**⇒ 现役是「cut marker + 覆盖式更新」，没有修订链、没有 provisional/definitive 两阶段、
没有冲突 rebase 契约。**

**在多节点 / 重试并发的场景下，「绝不覆盖」这条契约是 T11 独有的保证。**

## 4. 结论：R11.1–R11.9 的覆盖度判定

| R11 | 内容 | 现役覆盖 | 判定 |
|---|---|---|---|
| R11.1 | 会话预处理**唯一所有者** | 预处理逻辑分散在 compression hooks + provenance executors | ⚠️ 未统一 |
| R11.2 | Hook 三方法（Prepare/CommitFirstForward/AppendTerminal） | `SessionCompressor.Prepare/CommitFinal` 近似对应，但语义不同（final 而非 first-forward） | ⚠️ 部分 |
| R11.3 | 契约类型 | 0（生产完全不知道这套类型） | ❌ 无 |
| R11.4 | 复用四条件 | `cut_marker` + TTL + body hash —— **另一形态** | ⚠️ 部分 |
| **R11.5** | **三层依赖哈希** | **完全无** | ❌ **无（跨层失效缺口）** |
| **R11.6** | **修订状态机 + rebase** | **完全无** | ❌ **无（并发覆盖缺口）** |
| R11.7 | 存储接口 + tenant-scoped key + Lua CAS + lease + AES-GCM | 现役有 `loadV2CompressionState` / cut marker Redis 持久化，但**非 T11 那套租约+CAS 契约** | ⚠️ 部分 |
| R11.8 | `session_summaries` tenant scope（P0） | 列已存在，写入侧未核（108 号结论） | ⚠️ 部分 |
| R11.9 | 观测事件（hit/build/bytes saved 等） | 现役有 `logCompressionQuality` | ⚠️ 部分 |

**⇒ 真正为 T11 所独有、且现役结构上表达不了的，是 R11.5 与 R11.6 两项。**

## 5. 决策所需的一句话（替代 108 号那个模糊问题）

108 号问的是「**T11 全量还要不要做**」。本轮把这个问题收窄成：

> **「sanitize 层变更时，已压缩产物必须失效」与
> 「多节点并发下修订绝不覆盖」这两条保证，是不是需求？**
>
> - **是需求** ⇒ **T11 有不可替代的价值**，但**只应移植 R11.5 + R11.6 及其依赖**
>   （`deps.go` + `types.go` 的修订类型 + `reconcile.go` 的依赖图语义），
>   **不必全量接管预处理**（那会与现役 `domains/hooks/compression` 争夺所有权，
>   与 objective 第 26 项「统一在一个模块」冲突）。
> - **不是需求** ⇒ T11 可整体删除。
>
> **注意：108 号那三条 P0 前置的结论不变**——
> 前置②（offset 原子预占）仍是部分实现，**移植前必须先补**。

**⇒ 一句话决策，从「要不要做 4,930 行」变成「要不要两个保证」。**
工作量估算因此从「一次架构改造」降到「一次局部补齐」。
