## 1. §10 三项定点核实（写门前必做）

### 1.1 读包围函数

`domains/freediscovery/template_manager.go:295-318` 处于
`func (m *TemplateManager) Update(ctx, tenantID, id, req *UpdateTemplateRequest)` 之内，
是**运维 PATCH 模板**的更新路径。其注释自证：

```go
// ...操作员重新启用 → 清零自动禁用状态以允许重试

if *req.Enabled {
    addSet("consecutive_scan_failures", 0)

    addSet("auto_disabled_at", nil)
```

### 1.2 查调用方（人工触发 vs 自动触发）

| 复活路径 | 触发方式 | 位置 |

⇒ **存在复活路径，但只有人工一条。** 59 号的表述「模板**无自动复活路径**」**准确**（它说的是"自动"），本轮复核无误。

## 2. 我差点犯的错（与 §10 呼应）

按 59 号的结论，我本来的计划是**新建**一道「自动禁用必须有自动复活」的守卫。§10 的第 1、2 项核实直接否掉了它：

- **人工复活是合理设计**——别持续轰炸一个正在失败的供应商，等人来看一眼，比自动重试更安全。
- 因此那道门会**编码一个不存在的需求**，且与既有测试的意图冲突。

**⇒ 若不先核实，我会写出第二道「重复的、且要求错误」的门。** 这与 R85-C 的 `appNav.test.ts`（21/21 全绿却零业务覆盖）、以及 R78 的 `partguard`（子代理初报 3 处、实测 18 处）同族：**门不是越多越好，多了还要各自正确。**

## 3. 实际做了什么

给既有用例加 `FIXME(R85-D13-1)` 块注释，内容包括：

- 真库证据（6 行全 disabled、5 行 `consecutive_scan_failures=3`、自动禁用时间与最后一条任务日期吻合）；
- 自我锁死的因果链（`return` 在 `createTask` 之前 ⇒ 不写任务行 ⇒ 休眠后不可自愈）；
- 复活路径**只有人工一条**及其行号；
- **定级 P1 但属产品裁决**（整域休眠是「暂不投入」还是「实现未完成」）；
- **裁决为「修」时本用例应怎么改**（断言 disabled 也产生 task 行，或断言存在自动复活入口，并同步更新 59 号）。

**未改任何断言**，所以这道门的判别力与行为**完全不变**——它继续钉着现状，只是现在**带上了「这是未裁决的缺陷」这一信息**。

> 这正是本会话确立的「**红门不能进主干**」纪律的正确用法：未修的缺陷用「断言当前行为 + FIXME 标注」钉住，使将来修改必须显式发生。**F1 的 `deploy/sql/verify/routing_gate_warning_pg_test.go` 是同一模式。**
