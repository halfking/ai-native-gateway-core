## 二、⚠️ 本轮的方法论错误（比结论更值得记）

**我把「调用点存在」读成了「结论被推翻」。**

93 号的原话是「**无任何可达路径**」——**不是「无调用点」**。
调用点存在、位于活的 `executeOpenAI`、由唯一的 dispatch 路径驱动，
**这三件事恰恰是 93 号描述的一部分**（「还原点在那儿，但走不到」）。

⇒ **我犯的错是：只推翻了对方结论的一个分支，就宣布推翻整个结论。**
**而对方结论的恰恰是「两个前提都成立」——调用点存在（我验证了）
＋守卫恒假（我没查就下了结论）。**

**同族已记录的教训**：
- playbook §24「代码推断与真库观测矛盾时」；
- §25「守卫测试与被守卫行为同批被删时，测试通过记录不构成证据」。

**本条是它们的第三种形态**：
**「不可达」类结论有两个独立腿（点存在 + 点走不到），
证伪它必须同时推翻两条腿；只推翻一条就宣布胜利，得到的是方向相反的结论。**

⇒ **落地纪律：读到「零可达 / 永不可达 / 死代码」这类结论时，
先问「它有几条腿」——把每条腿单独列出来，逐条查完再下判断。**
本例若我不查守卫就发报告，会产出一条「P1 被推翻」的错误结论，
**而它是本会话唯一一条做过变异验证的 P1**（93 号 M1/M2 红绿对照 + `cmp` 逐字节还原）。

## 三、【新】与 38 号正交的缺口：**记账宽度 ≫ 还原宽度**

93 号查的是**可达性**（点走不走得到）；本轮查的是**能力边界**（走到了能还原什么）。**两者正交。**

### 账本能记什么（`internal/paramledger/ledger.go:41-48`）

```go
ActionClamp     Action = "clamp"        // 值被就近降/升档（x-high→high）
ActionNormalize Action = "normalize"    // 值被别名归一（x-high→xhigh）
ActionStrip     Action = "strip"        // 参数被整体剔除
ActionModeSwitch Action = "mode_switch" // 请求形态被切换（responses→chat）
```

记账来源是 `paramguard.ApplyReported` 返回的 report，**字段是任意的**（`r.Field`），
外加 `reqprobe` 的参数剔除与模式回退（`paramledger_integration.go:57-83`）。

### 还原函数能还原什么（`ledger.go` 的 `RestoreResponsesEffort`）

```go
if entry == nil || len(data) == 0 || !bytes.Contains(data, []byte(`"effort"`)) { return data }
span, off, ok := reasoningObjectSpan(data)      // 只认 Responses 的 reasoning 对象
if !ok { return data }
for _, adj := range entry.Adjustments {
    if adj.Original == "" || adj.Sent == "" || adj.Sent == adj.Original { continue }  // ← strip 被跳过
    switch adj.Field {
    case "reasoning_effort", "reasoning.effort", "reasoning":   // ← 只认这三个字段名
        ...
        return out                                    // ← 命中第一条即返回
    }
}
return data
```

**三道收窄，逐条可数：**

| 收窄 | 后果 |
|---|---|
| 入口要求 body 含 `"effort"` 且能解析出 reasoning 对象 | **非 Responses 形态一律不还原**（chat / messages / anthropic 全无） |
| `switch adj.Field` 只认 3 个字段名 | **其他字段的 clamp/normalize 一律不还原** |
| `adj.Sent == ""` → `continue` | **`strip` 永不可还原**（参数已被剔除，无从「还原」；但**客户端也永远不知道被剔了什么**） |
| `return out` 命中即退 | **同一请求有多条 reasoning 相关调整时，只还原第一条** |
| `mode_switch` 记在 `Field: "transport"` | **不匹配任何 case ⇒ 永不可还原** |

### 诚实的边界

代码注释与函数名**没有夸大**：
`paramledger_integration.go:86` 写「**当前覆盖 Responses 形态的 `reasoning.effort`**」，
函数名就叫 `RestoreResponsesEffort`。
⇒ **这是被明示的设计边界，不是隐藏缺陷。**
（93 号已同族记录：`ledger.go:17-19` 把「anthropic 不回显」写成事实，
实际只是「网关不解析」——那是另一处需要订正的表述。）

⇒ **但 objective 的要求是通用的一句**「超出原厂的参数缓存下来，在返回时恢复」。
系统**记的远多于还的**：
**4 种 action × 任意字段 ↔ 1 种形态 × 1 个字段族 × 第一条命中。**
⇒ **即使把 38 号的可达性修好，objective 这条要求仍然不满足。**
