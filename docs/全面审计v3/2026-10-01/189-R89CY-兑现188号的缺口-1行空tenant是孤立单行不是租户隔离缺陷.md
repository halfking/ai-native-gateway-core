### F5：补查「它是不是 `agent` 类型特有的」—— ⚠️ **我先前的假设是错的**

初稿我写「该行是全表唯一一条 `task_type='agent'`」—— **这句是错的**。
我当时是用带 `LIMIT 1` 的查询看那一行的完整字段，**没有回头统计 `agent` 的总数**。

**补查结果：**

```sql
SELECT task_type, count(*) FROM auto_route_selections WHERE task_type='agent';
  → 81        （不是 1）
SELECT task_type, count(*) FROM request_logs     WHERE task_type='agent';
  → 80
```

**⇒ `agent` 类型在两表分别是 81 / 80 行，样本量充足，不是孤例。**

**⇒ 正确的问法是「81 个 `agent` 行里，有几条缺日志 / 缺 tenant / 缺 success」：**

| 口径 | 结果 |
|---|---|
| `auto_route_selections` 全表 `tenant_id` 为空 | **1** |
| `auto_route_selections` 全表 `success IS NULL` | **1** |
| `agent` 的 81 行里 `tenant_id` 为空 | **1** |
| `agent` 的 81 行里 `success IS NULL` | **1** |
| `request_logs` 的 80 个 `agent` 行**有**对应选择记录 | **80 / 80（100%）** |

**⇒ 修正后的结论：那 1 行确实是全表唯一的两个异常，且 `agent` 类型本身是正常的
（80/80 全有选择记录）。异常只落在**这一行**上，机制上仍然无法归因。**

**⚠️ 这条自我更正的教训写进了 §81** —— 「唯一的异常行」里，
**「唯一」这个性质本身必须先统计验证，不能从「我只看到一行」推断出来。**

## 六、playbook §81 新增

> **§81 找出一个「唯一的异常行」时，先问「它的同类有几个」—— 样本量为 1 时，任何统计与归因都不成立**

**由来**（R89-CY / 189 号）：`auto_route_selections` 里恰好 1 行 `tenant_id` 为空、`success` 为 NULL、
且是全表唯一一条 `task_type='agent'` 的记录。
**它同时踩中三个「唯一」，非常像一条有故事的坏数据。**

**⇒ 落地三条：**
1. **「唯一的异常行」几乎总是「没有对照组」** ——
   本轮真正的对照组是**同一时间窗内的另外 60+ 行**（全部正常）
   ⇒ **有对照组才能说「孤例」，没有对照组只能说「异常」**；
2. **⚠️ 样本量为 1 时不要做分组统计** ——
   本轮 `task_type='agent'` 全表只有这 1 行
   ⇒ 「`agent` 类型是否更容易丢日志」这个问题**在数据上不可答**，
   **硬答会得到一个 n=1 的百分比，然后被当成结论引用**（§10.1 的量化纪律）；
3. **⚠️ 「唯一的异常行」里，「唯一」这个性质本身要先统计验证** ——
   本轮初稿写「该行是全表唯一一条 `task_type='agent'`」，
   **那是我用带 `LIMIT 1` 的查询看单行时顺手推断的**；
   补统计才发现 `agent` 有 **81 行**（`request_logs` 侧 80 行）
   ⇒ **「我只看到一行」与「全表只有一行」是两回事**（§45 的又一次印证）；
4. **⚠️ 「一列全空」先找注释里的设计声明** ——
   `routing_source` 1,747 行全空，本轮差点报「死列」，
   **读到「仅在 `role_route` 命中时映射」才知道那是设计**（§41 桶②）。

**⇒ 与 §80 的关系**：
§80 说「先拆分母」；
**本条说「先看同类有几个」——
分母拆分解决「比例算错」，同类计数解决「孤例被当成系统性缺陷」。**
