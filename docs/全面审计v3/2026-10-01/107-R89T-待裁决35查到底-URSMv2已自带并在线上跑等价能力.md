## 0. 一句话

`domains/nodestatecache` 是一个完整建成、有 14 个测试文件、**却从未接线**的节点状态缓存。
但复核后发现：**它想加速的那件事，URSM v2 自己已经做了，而且已经在路由热路径上跑了**
（`FilterAndScoreReadyWithSource` + `cache/nodemirror.go`，30 秒软 TTL，有测试钉住语义）。
**所以「把它接上」不是一个安全动作。**

## 1. 这个包是什么

`domains/nodestatecache/nodestatecache.go:12-40` 的 `Options` 自陈了 6 个注入接口：

```go
Scorer        Scorer                // 幸存集评分排序（URSM FilterAndScoreReadyWithSource）
StickyLookup  StickyLookup          // 同会话 sticky 绑定查询
ModelFallback ModelFallback         // 任务类型→品质档位换模型
RecentSuccess RecentSuccessLookup   // 36h 成功回看（NeedProbe）
Authority     AuthoritativeSnapshot // 权威快照（周期对账）
Invalidation  InvalidationListener  // 置脏/回收监听
```

**注释里反复出现「URSM」**：
`FailStreakLimit` 默认 3 且注明「**对齐 URSM FailStreakLimit**」（`:47`），
`Scorer` 注明「URSM FilterAndScoreReadyWithSource」（`:33`）。

**⇒ 它的自我定位很明确：URSM 之上的进程内派生读缓存。**

## 3. 重叠与不重叠的边界（决定「接」还是「删」）

### 3.1 与 URSM v2 **重叠**的部分

`nodestatecache` 的 `registry.go`（LRU id 回收、容量 65536）、
`selector.go`（评分排序）、`nodestatecache.go`（状态机）
—— 这些能力在 URSM v2 的 `FilterAndScoreReadyWithSource` + `cache/nodemirror.go` + `cache/intent.go`（`NewLRU`）**里已有对位物**。

### 3.2 **不重叠**的部分（我实测确认 URSM v2 无对位物）

`domains/nodestatecache/resources.go`（356 行）的**节点级资源占用表**：
`resourceTable.TryAcquire`（`resources.go:157`）/ `Cache.TryAcquire`（`nodestatecache.go:166`）/ `Release` / `ResetWindow`。

我按方法名全仓搜 `TryAcquire`，**URSM v2 内没有任何 `Manager.TryAcquire`**。
唯一的同名方法在 `domains/credential/limiter.go:90,121`（`Semaphore.TryAcquire`），
**那是并发槽位信号量，与「按 node 的资源占用表」不是一回事**。

另有 `bitmap.go`（161 行）。

**⇒ 如果需求是「每节点的资源占用/配额」，那 `resources.go` + `bitmap.go` 补的是 URSM 确实没有的一块。**

## 4. 结论：待裁决 35 的前提需要改写

**台账里现有的表述**是：「前置已具备，但需集成 5 个注入接口，非一个包能完成 ⇒ 需排期」。

**这个表述有一个危险的误导**：它暗示「前置只是没接上」。

**实际情况是：**

1. **原始动机（加速路由决策）很可能已经不成立** ——
   URSM v2 自带的 `nodemirror` + 30s 软 TTL **已经在做这件事，而且在线上跑**。
   再接一层进程内缓存，**换来的是第二个节点状态源**，不是速度。
2. **这与 objective 第 26 项直接冲突** ——
   该项原文：「全局的节点状态需要统一，**状态更新需要在一个模块中进行**」。
   URSM v2 是那个模块；`nodestatecache` 一旦接线，就是**第二个**。
   （它自己也知道这个风险——所以才有 `Authority` + `Reconcile` + `Invalidation` 三套兜底。
   **但这三套兜底本身是未验证的设计意图，仓内没有第二份实现来验证它们是否真的成立。**）
3. **3,324 行 + 14 个测试文件的体量**，与「只剩 `resources.go` + `bitmap.go` 不重叠」这个判断张力很大。
   说明要么当初的设计范围就远超实际需要，要么 URSM v2 是后来的重复实现。

**⇒ 决策所需的是一句话需求确认，而不是排期估算：**

> **是否存在「每节点资源占用 / 配额」这个真实需求？**
>
> - **是** → 只移植 `resources.go` + `bitmap.go`（约 520 行），不移植状态机与注册表；
> - **否** → 整个包可删（3,324 行 + 14 个测试文件），
>   路由侧能力由 URSM v2 的 `FilterAndScoreReadyWithSource` 承担（**已在线上**）。
>
> **两种情况下都不建议「按原描述把 6 个注入接口都接上」。**

  若要动这个包，**必须先做一次逐字段对比**再定移植范围。
- **「原始动机不成立」是基于「URSM 自带镜像且在线上」的推断**，
  我**没有实测路由延迟**（是否有 Redis 往返、往返多少）——
  这属于部署侧性能事实，需真实负载下测。

  （它们无第二实现可对照）。
