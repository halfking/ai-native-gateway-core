## 1. 缺陷（实读确认，非转述）

`breaker.go:438-447`（修复前）：

```go
lastIsTransient := transientFamily[b.lastErrorKind]
nowIsTransient := transientFamily[kind]
if b.lastErrorKind != "" && b.lastErrorKind != kind && !(lastIsTransient && nowIsTransient) {
    b.consecutive.Store(0)
    b.coolingCycle = 0
}
```

而 `:456-466`：

```go
threshold := failureConfirmationThreshold(policy)
if consecutive < threshold {
    slog.Warn("circuit failure pending confirmation", ...)
    return          // ← 直接返回，不升级
}
```

**关键事实**：

| ErrorKind | 策略（`:110` / `:131`） | 在 `transientFamily`（`:379-384`）？ |
|---|---|---|
| `KindTransient` / `KindTimeout` / `KindNetwork` / `KindStreamTimeout` | 各自 | **是** |
| `KindUpstreamDown` | `RecoveryExponential`，Initial 30s / Max 30min | **否** |

⇒ **Timeout ↔ UpstreamDown 交替时，每次都满足「族变化且非同族瞬时」⇒ `consecutive` 归零 ⇒ 永远够不到 `threshold` ⇒ 熔断永不跳闸。**

这与 `:375-377` 注释里 2026-07-09 那次修复的初衷**正好相反**：

> 「如果每次错误类型切换就重置计数，会导致**永远达不到降级阈值**。」

**⇒ 那次修复只覆盖了瞬时族**内部**交替，漏了最常见的「瞬时族 ↔ UpstreamDown」这条路径。**

## 2. 修法

参照 OmniRoute `accountFallback.ts:640` 的**时间窗**判据（而不是按错误族名）：

```go
incidentWindow := policy.InitialCooling
if remaining := time.Until(b.coolingExpires); remaining > incidentWindow {
    incidentWindow = remaining
}
sameIncident := !b.lastFailureAt.IsZero() && now.Sub(b.lastFailureAt) <= incidentWindow
if b.lastErrorKind != "" && b.lastErrorKind != kind && !(lastIsTransient && nowIsTransient) {
    if !sameIncident {
        b.consecutive.Store(0)   // 隔得够久 ⇒ 确属新的一轮事件
    }
    b.coolingCycle = 0          // R34 意图保留
}
```

### 2.1 规格的一处错误，实施前抓出

63 号原稿写 `policy.ResetAfter`。**`CoolingPolicy` 结构体里没有这个字段** —— 只有 `InitialCooling` / `MaxCooling` / `RecoveryType` / `ShrinkFactor`。改用 `max(InitialCooling, 剩余冷却时间)`。

**这条是在动手前读结构体时抓到的，不是编译期才发现** —— 说明「先读实际定义再照规格写」这一步是必要的，规格本身也会有想当然的字段名。63 号已就地订正。

### 2.2 明确登记的代价（不是完美解）

`b.coolingCycle = 0` 仍按 R34 意图执行 ⇒ **交替族下冷却停在第 1 档（15s/30s）不指数爬升**。

| 变体 | 交替族下的表现 | 代价 |
|---|---|---|
| **本次实施（variant A）** | 跳闸，但冷却停在第 1 档 | 长期故障的退避不够陡 |
| variant B（同事件内 `coolingCycle` 也保留） | 跳闸且指数爬升 | **部分推翻 R34（2026-09-17）的记录决策**，按 `conventions.md` §5 须先取得产品认可 |

**选 A 的理由**：R34 的原始诉求是「族变化不继承陈旧升级档，避免下次升级直接从 2³× 起步」——variant A 满足这一点；且「永不跳闸」比「退避不够陡」严重得多。**这是明确的部分取舍，不是无争议修复。**

## 3. 回归用例与变异验证

### 3.1 四个新用例

| 编号 | 用例 | 断言 |
|---|---|---|
| T1 | `Timeout → UpstreamDown → Timeout`（无时间间隔） | 第三次后 `StateOpen`（**修复前恒 Closed、consecutive 恒 1**） |
| T2 | 同上但每次 `lastFailureAt` 回拨 1 小时 | 仍 `StateClosed`（**反向护栏：防窗口过宽**） |
| T3 | 同事件内族变化后 `coolingCycle` | **等于 1**（归零后重新起步），**不是** 2 或 3 |
| T4 | `RecordSuccess` 后 | `consecutive` 与 `coolingCycle` 均归零 |

### 3.2 变异验证 3/3 全红，全部 `cmp` 逐字节还原

| 变异 | 期望 | 实测 |
|---|---|---|
| M-a `sameIncident := false`（退化为修复前行为） | 红 | ✅ **T1 + T3 双红** |
| M-b `sameIncident := true` | 红 | ✅ T2 红 |
| M-c 删掉 `b.coolingCycle = 0` | 红 | ✅ T3 红 |

**M-a 让 T3 也红了，这是我最初没想到的**：没有时间窗时，族变化会把 `consecutive` 清零，于是 `consecutive < threshold` 提前 return，`coolingCycle` 停在 0 而非 1。**⇒ T3 实际守的是「归零不得阻止新一次升级」，比原写的「归零」更强。**

### 3.3 一次「门红 ⇒ 是我的断言错了」

T3 首次运行报 `修复前=2 修复后=1`。**这是我的断言写错，不是实现有问题**：调用内先按 R34 归零，**随后同一次调用**因 `KindUpstreamDown` 是 `RecoveryExponential` 而 `coolingCycle++` ⇒ 终值是 1。

真实语义是「**不继承陈旧档位、从 1 重新起步**」，不是「停在 0」。已按真实语义改断言。**这是本会话第 4 次「门红 ⇒ 先假设门对 → 发现是自己错」**（前 3 次分别是 R74 的 Anthropic 两处、判据锚错层级）。
