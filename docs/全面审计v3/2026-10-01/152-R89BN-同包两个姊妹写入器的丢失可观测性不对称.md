# 152 / R89-BN：同包两个姊妹写入器的丢失可观测性不对称

> 日期：2026-10-01
> 承接 151 号 §五 留下的待查项：**`tuning_signal_writer.go` 是否有等价指标**
> 结论：**有，且比 151 号预期的更好——但只覆盖一半丢失路径。同包姊妹写入器 `selection_writer.go` 覆盖完整。**
> 定级：**P3 / 待裁决 62**（不含 P1、不含 P2）。**未改动任何生产代码或数据库。**

## 一、结论先行

151 号为 auto 选择记录（`selection_writer.go`）坐实了 `llm_gateway_auto_selections_dropped_total`，
并把它变成「33 小时断档」的判别器，同时诚实地登记了一个未查项：

> 未核其它「异步 best-effort 写入器」是否都有等价指标（同包还有 `tuning_signal_writer.go`）。

**本轮把这个未查项关掉了。**结果是：**tuning 侧有等价指标，但覆盖面比 auto 侧少一条路径。**

| | auto（`selection_*`） | tuning（`tuning_*`） |
|---|---|---|
| 队列满 | ✅ 计入 dropped（`:147/:148`） | ✅ 计入 dropped（`:167`） |
| **批量插入失败** | ✅ 计入 dropped（`:223`） | ❌ **只 `slog.Warn`，无任何计数器** |
| 成功落库 | ✅ 计入 total（`:230`） | ✅ 计入 total（`:241`） |
| 上述行为的测试 | ✅ `TestSelectionWriter_InsertErrorCountsAsDropped` | ❌ 无 |

两个写入器**同包、同作者、同构型**（`poolExec` 接口共用、各自 4096 队列 + 批量 flush），
**却在「插入失败算不算丢失」上做了不同决定**，且这个分歧没有任何注释说明是有意为之。

## 二、逐条证据

### 2.1 tuning 侧：指标存在，且接线完整

指标声明在**与 writer 同包的另一个文件** `tuning_metrics.go:74-78`：

```go
tuningSignalDroppedTotal = promauto.NewCounter(prometheus.CounterOpts{
    Name: "llm_gateway_tuning_signal_dropped_total",
    Help: "Number of tuning signals dropped because the writer queue was full.",
})
```

按 151 号的「五处齐全」纪律逐项核：

| 检查项 | 结果 |
|---|---|
| 声明 | `tuning_metrics.go:74-78` |
| 写入点 | `tuning_signal_writer.go:167`（唯一） |
| Record 包装 | `tuning_metrics.go:154 RecordTuningSignalDropped()` |
| 调用方 | 全仓仅 `tuning_signal_writer.go:167` 一处（`grep -rn` 复核） |
| `/metrics` 暴露 | `promauto` → `DefaultRegisterer` → `middleware/prometheus_mw.go:38 promhttp.Handler()` 与 `cmd/gateway-v2/main.go:1024 HandlerFor(DefaultGatherer)`，同机制，151 号已验证 |
| 测试 | ❌ 无 |

**注意 Help 文本自己就承认了范围**：`dropped because the writer queue was full`——
它**只声明了队列满**，没有声称覆盖插入失败。所以这不是「注释承诺了却没实现」，
而是**指标设计范围本身就窄**。这让定级更倾向 P3 而非 P2。

### 2.2 tuning 侧：插入失败路径确实裸奔

`tuning_signal_writer.go:221-235`：

```go
func (w *tuningWriter) flush(batch []TuningSignal) {
	if w.pool == nil {
		return                      // ← 路径 3，见 §2.4（不可达，不报）
	}
	RecordTuningSignalBatch(len(batch))     // :225 直方图在此观测
	ctx, cancel := context.WithTimeout(context.Background(), tuningWriteTO)
	defer cancel()

	if err := w.insertBatch(ctx, batch); err != nil {
		slog.Warn("tuning_signals batch insert failed",
			"count", len(batch), "error", err)   // :230-231 只有日志
		return                                       // :232 无计数器
	}
	RecordSuccessfulBatch(batch)                   // :234
}
```

丢失路径共三条：

1. **入队满** → `WriteTuningSignal` 的 `default` 分支 → 有计数 ✅
2. **批量插入失败** → `flush` `:229` → **只有 `slog.Warn` + `return`** ❌
3. **`w.pool == nil`** → `flush` `:222` → 静默 `return`，连日志都没有 ❌

### 2.3 auto 侧：同一形态的失败路径被计入

`selection_writer.go`：

- `:147 w.dropped.Add(1)` + `:148 RecordAutoSelectionDropped()` —— 队列满，按**行**
- `:222 w.dropped.Add(int64(len(batch)))` + `:223 RecordAutoSelectionDropped()` —— 插入失败，按**行**
- `:228 w.persisted.Add(int64(len(batch)))` + `:230 RecordAutoSelectionWritten(...)` —— 成功

且 `selection_metrics.go:8-13` 的包注释明确承诺：

> `llm_gateway_auto_selections_dropped_total` — Counter — rows lost to a full queue **or a failed insert**.

**这句话对 auto 成立，对 tuning 不成立。**同包两个文件对同一件事的表述不一致。

### 2.4 路径 3 不可达——按 §30 不报

`flush()` 的全部调用点是 `tuning_signal_writer.go:188/193/201/213`，**全部在 `run()` 内**；
`run()` 的唯一启动点是 `StartTuningWriter:130`，它在 `once.Do` 内部、且 **`:127` 先赋 `pool = adapterExec{}`、`:130` 才 `go run()`**。
因此只要 `run()` 在跑，`w.pool` 必非 nil ⇒ `if w.pool == nil` 在生产路径**不可达**。

**「不可达的缺陷不是缺陷」**——该分支不计入发现，仅在此记录已核。

## 三、变异验证（改坏→红，还原→绿）

临时实证测试跑完即删（`mavis-trash`）。它断言的不是「指标存在」，
而是**插入失败这条路径是否被计入**——即把「不对称」从阅读结论变成可复现的数字。

**正向实测**（注入 `failingPool`，`count=3`）：

```
插入失败(3 行)实测: dropped 0→0, written 0→0, batch_size count 0→1 sum 0→3
auto 插入失败(2 行)实测: dropped 0→1
```

**tuning `dropped` 与 `written` 双双不动，只有 batch_size 直方图动了。auto 侧 dropped 动了。**
两个测试同时绿——正反对照都在，才构成「不对称」的证据（单侧通过没有意义）。

**变异**：给 `tuning_signal_writer.go:229` 的失败分支补一行 `RecordTuningSignalDropped()`：

```
--- FAIL: TestR89BN_TuningInsertFailureIsNotCounted
    dropped 0→1, written 0→0, batch_size count 0→1 sum 0→3
    预期不成立：dropped 计入了插入失败（0→1）。若如此，说明上游已补齐，
    本报告的「不对称」结论被证伪，必须改写。
```

测试**自带护栏**：若这个变异将来真的合入，报告会主动响「结论作废」而不是继续挂着。

**还原**：`cmp` 逐字节一致，`git diff -- domains/` 为空，测试回到绿。生产文件全程零改动。

## 四、附带发现：auto 的 dropped 有单位错配（独立于不对称）

同一次实测里暴露的，**与 tuning 无关，是 auto 侧自己的问题**：

| 计数器 | 插入失败 N 行时的增量 | 语义 |
|---|---|---|
| `SelectionWriterStats().dropped`（atomic，`:222`） | **+N** | 丢失**行**数 |
| `llm_gateway_auto_selections_dropped_total`（`:223`） | **+1** | 失败**批**次数 |

而该指标的 Help 与包注释都写的是 **"rows lost"**。
⇒ **Help 文本对「队列满」成立（1 行 = 1 次），对「插入失败」不成立（N 行 = 1 次）。**

后果：把 `SelectionWriterStats().dropped` 和 prometheus 计数器放在一起对账的人
（对账脚本、告警阈值、51 号那类宽度核对）会得到**系统性偏小**的比值，
且偏小倍数随批大小变化，不是固定系数——**这类误差不会自己报警**。

## 五、判别器价值：比 151 号预期的更强

151 号把 auto 的断档变成「一条指标即可判别」。本轮把同一手法套到 tuning 上，
得到**三态**（不是两态）：

| tuning_signals_total | tuning_signal_dropped_total | 判读 |
|---|---|---|
| 涨 | 涨 | 队列满（`written` 涨说明写入侧本身健康） |
| 涨 | 平 | 健康 |
| **平** | **平** | **写入失败或根本没流量**——需查 `batch insert failed` 日志区分 |

第三态之所以能成立，正是因为 `RecordSuccessfulBatch` 只在插入成功后调用
（`:234` 在 `:229` 的成功分支之后）——**`written` 恒平严格蕴含「没有成功插入过」**。

⚠️ **但第三态只到「有东西坏了」为止**：因为失败路径无计数，
**无法从指标区分「DB 不可用」和「根本没来流量」**，必须落到日志。
这是 §2.2 缺口的直接代价。

**旁路补偿**：`llm_gateway_tuning_signal_batch_size`（`:225`）在 insert **之前**观测，
失败批照样计入 `_count`/`_sum`。所以第三态可以用
`rate(batch_size_count) > 0 且 rate(tuning_signals_total) == 0` 进一步确认「有流量进来但一条没落库」，
而不是真的没人调用。**这是巧合成立的旁路，不是设计。**
