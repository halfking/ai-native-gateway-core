## 1. 75 号错在哪：读错了入口函数

75 号读了 `PlanCapacityWait`（容量饱和专用）与 `PlanModelChange`（模型阶梯），
**没有读 `PlanAfterFailure`** —— 而后者才是**失败后的真正决策入口**：

```go
// domains/dispatch/planner.go:162
func PlanAfterFailure(qr *QueuedRequest, out ForwardOutcome, cfg Config) Decision {
    ...
    // 委托给中央策略
    action := errorsx.DecideNextAction(errorsx.DecisionContext{ ... Kind: kind, RetryAfter: out.RetryAfter, ... })
```

`PlanCapacityWait` 与 `PlanModelChange` 是阶梯上**下游**的专门分支，
拿它们代表「失败后怎么办」是取样错误。

## 3. 与 9router 的对比结论

| 维度 | 9router 模式③ | 主项目现状 |
|---|---|---|
| 触发 | 502/503/504 且 `cooldownMs ≤ 5000` | ≥500 → wait_recovery；503 → 同节点重试 |
| 决策位置 | 调用点内联 `if (status==503\|\|502\|\|504)` | **中央策略** `DecideNextAction`，一处改全生效 |
| 等待实现 | `await sleep(cooldownMs)` —— **阻塞协程** | 队列 park + `retry_at` —— **不阻塞** |
| 预算控制 | 靠 `cooldownMs ≤ 5000` 硬编码 | `MaxSameNodeRetries` + `RemainingAttempts` + `defaultRecoveryDelay(kind)` |

**⇒ 模式③ 不适用，且不该照抄。** 主项目已有的实现在三个维度上都更强。

## 4. 【教训】两次连续取样错误，同一根因

| 轮次 | 我看了什么 | 我据此说了什么 | 漏了什么 |
|---|---|---|---|
| R88-g | `time.Sleep` 0 命中 | 「主项目不等待」 | 等待在**队列层**（代理量 vs 语义量） |
| R88-h | `PlanCapacityWait` / `PlanModelChange` | 「唯一缺口是 `switch_model` 无 `RetryAt`」 | 真正的入口是 **`PlanAfterFailure` → 中央策略**（**取样错误**） |

**共同根因：拿「我读到的那几个函数」代表「整个决策面」。**
两次都是**早停**——找到一个看起来相关的函数就下结论，没有先确认「这是不是入口」。

**判据**：落笔前问「**这个函数是谁调用的？它的上游还有谁？**」。
若一个函数与同类函数并列、且各自带 `Plan` 前缀却覆盖不同场景，
**它多半是阶梯上的一节，不是入口**。
（旁证：`PlanAfterFailure` 是唯一接收 `ForwardOutcome` 的，其余都不接收失败结果。）
