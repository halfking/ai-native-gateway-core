# 39 — R69：审计守卫此前**没有被任何强制路径执行**（并发现 3 个同类孤儿）

> 2026-10-01 03:54 起，基线 `573a1567e`（R68 推送后的合并态）。
> 轮次性质：**给守卫接上执行路径**。R66–R68 建了四道守卫，本轮问一个更前置的
> 问题——**它们真的会被执行吗**。

## 0. 本轮的问题

R66 建了 `internal/rowsguard`（764 个 rows 循环、0 违规），R67 建了回归测试，
R68 建了 `internal/errdiscard`。每一轮写完都跑了变异验证，门都是绿的。

但**「门是绿的」和「门被执行」是两件事**。R69 回头查执行路径。

## 1. 发现：四道守卫从未进入任何强制路径

| 路径 | 实际跑什么 | 覆盖守卫吗 |
|---|---|---|
| `.githooks/pre-push` | `tests/*.sh` 11 套件；Go 测试**仅在 `RUN_GO_TESTS=1` 时**且**只跑 `./licensing/... ./envinjector/...`** | ❌ |
| `integration-testcontainers-ci.yml` | `go build ./...` + `go vet ./...`（**无 `go test`**） | ❌ |
| `sessionforensics-ci.yml` | `./bg` `./domains/requestjourney` `./admin` `./domains/session/v2` | ❌ |
| `installer-ci` / `multimodal-ci` / `ml-training-ci` | 各自窄范围 | ❌ |
| `make test` | `go test ./...` —— **会覆盖**，但需人工触发 | ⚠️ |

**结论**：这四道守卫当时只是**文档**，不是门。它们只在有人手动敲
`go test ./internal/rowsguard/` 时才会跑。本仓库已有的
`sqlreadguard` 守卫是手工在各个 review 轮里跑的（其测试注释里能看到历次
手工运行的痕迹），同样没有进 CI。

这解释了 R66–R68 的一个现象：我在守卫上花了大量功夫做变异验证，但**任何一次
push 都不会因为守卫退化而失败**。

## 2. 更进一步的发现：三个更老的守卫也是孤儿

写完「校验守卫是否已登记」的门（§3.2）后第一次运行，它立刻报出**三个我从未
登记、也从未在本会话中接触过**的守卫包：

- `internal/sqlguard`（SQL 字面量守卫）
- `internal/sqlreadguard`（裸 `request_logs` 读守卫，35 号报告 §44.7 还在引用它）
- `internal/paramguard`（参数守卫）

三者都是**真实的、hermetic 的**审计门，同样从未被任何强制路径执行。
**这不是本轮引入的缺陷，而是本仓库长期存在的执行路径缺口**——一个「守卫体系
看起来很完整、实际上整体未接线」的状态。

## 3. 修法

### 3.1 `make guards` + 全部七个守卫登记进 `GUARD_PACKAGES`

七个包合计 **3.8s**（实测），无 DB、无网络。

### 3.2 `scripts/checks/guards-sync.sh` —— 防「加守卫但漏接线」

这是本轮的关键设计。**「加了个守卫但忘了接进执行路径」是这类体系最常见的
腐化方式，且完全静默**：新守卫本地跑是绿的，CI 也是绿的，只是它从来没在强制
路径上跑过。

脚本校验 `internal/` 下每个 `*guard` 包都出现在 `Makefile` 的
`GUARD_PACKAGES` 里，漏一个就红。**它自己就是 §2 那三个孤儿守卫的发现者。**

### 3.3 接进 pre-push，且**不受开关约束**

守卫门作为 pre-push 的独立阶段，**刻意不受 `SKIP_TESTS` / `RUN_GO_TESTS`
约束**。理由：Go 单元测试默认 opt-in 是因为**成本与外部依赖**，而守卫是纯静态
分析、3.8s、零外部依赖——用「opt-in 的理由」去约束它属于归因错误。

**变异/负控验证**：

- 引入一处真实丢弃（把 E3 改回 `modelChanges, _ :=`）⇒ 守卫红 ⇒
  **WOULD BLOCK PUSH (correct)**；还原后恢复绿
- 新建一个未登记的 `internal/fakeguard` ⇒ `guards-sync` 红；删除后恢复绿

## 4. 我在这个脚本上犯的两个错（都已修）

1. **内联 shell 写进 Makefile 失败**：`case ... in *) ;; esac` 嵌在
   `$(...)` 里被 `/bin/sh` 解析不了。改为独立脚本文件——`bash -n` 之外的
   语义失败必须靠实跑发现。
2. **`GUARD_PACKAGES` 写成多行续行**，`sed -n 's/^GUARD_PACKAGES...//p'`
   只读到第一行，脚本于是认为三个已登记包都「未登记」。**改为单行定义**，
   并在 Makefile 旁注明原因——这个坑对下一个改它的人同样会踩。

另外第一次跑 `guards-sync` 时它**立刻报红**。那一刻最容易的反应是「脚本写错了，
改脚本」；实际上它是对的，仓库里确实有三个没登记的守卫。**门第一次就报红时，
先假设门是对的。**

## 6. 保持开放

- **`GUARD_PACKAGES` 需人工维护**，靠 `guards-sync` 强制。加守卫的人若同时改
  Makefile 就会被同步登记，这个门是**双刃**的：它不阻止「登记了但没写测试」。
- **CI 侧仍未接入**。本轮只做了本地 pre-push（它每次 push 都跑，是最可靠的
  本地执行点）。

  > **R70 更正**：本条结论**部分不准确**。`integration-testcontainers-ci.yml`
  > 的 `integration-testcontainers` job 跑的是
  > `go test -tags=integration -timeout 30m -count=1 ./...`，而 `-tags`
  > 是**追加**标签、不排除无标签文件——实测守卫在该命令下确实会执行
  > （`go test -tags=integration ./internal/errdiscard/` 通过）。
  > 所以守卫**并非完全没有** CI 覆盖，但那个覆盖是**偶然的、间接的**：
  >
  > 1. `integration-testcontainers-ci.yml` 的 paths 过滤里**没有 `admin/**`**
  >    （实测 8 个 workflow 无一包含），而本轮及 R66–R68 的大部分改动都在
  >    `admin/`。改 admin 不会唤醒它 ⇒ 守卫也不会跑。
  > 2. 守卫要等 testcontainers 起 docker、30 分钟超时；它红了会被混在
  >    重型 job 的噪声里。
  > 3. 一旦那个 job 因任何无关原因长红或被跳过，守卫信号随之消失。
  >
  > R70 据此新增**独立**的 `audit-guards-ci.yml` job（paths 用 `**/*.go`，
  > 因为守卫扫的是全仓），详见 40 号轮。
- `integration-testcontainers-ci.yml` 跑 `go build ./...` + `go vet ./...` 但
  **不跑任何 `go test`**——这是一个独立于本轮的、更大的执行路径缺口，本轮登记
  不修。
