## 一、F1：判据选择 —— 为什么必须用 git 而不是 mtime

**⚠️ 先说一个我自己差点走错的地方。**

第一遍用的是 **文件 mtime**：

```
可唯一解析: 70
最近修改的 5 个（mtime）:
   2026-10-01 06:20  686_fix_session_module_executions_2026_10_bounds.sql
   2026-10-01 01:31  765_bodies_columnar_storage.sql
   2026-09-30 10:01  764_request_logs_tenant_ts_index.sql
   ...
最久修改的 3 个:
   2026-08-25 22:25  603_repair_request_logs_schema_consistency.sql
   2026-08-25 21:43  564_session_summary_backfill_safe.sql
   2026-08-25 21:43  552_request_journey_durable_outbox.sql
```

**mtime 跨度 08-25 → 10-01，看起来「全都可疑」** ——
**但这是 checkout 时间**（本仓库是 10-01 拉取的，mtime 反映的是文件被写入工作树的时间），
**不是「内容被改过」的时间** ⇒ **用 mtime 会把 70 条全判成可疑，等于没判**（§59 尺子错的形态 B）。

**⇒ 换判据：`git log --reverse` 拿首次提交日 vs `git log -1` 拿最近提交日。**
**⇒ 两者不等 = 该文件内容被改过。这是仓库内可证伪、跨机器一致的事实。**

```bash
head -18 sql/migrations/startup/686_fix_session_module_executions_2026_10_bounds.sql

```
-- Migration 686: 修复 session_module_executions_2026_10 分区上界(+08 字面量污染)
-- Background (2026-09-07 部署后观察, ensure tick 42P17 每次复现):
--   本库 session_module_executions_2026_10 的分区上界是
--     TO ('2026-11-01 08:00:00+08')   -- 应为 00:00:00+08,多出 8 小时
-- ...

-- to_regclass()。::regclass 在分区缺失时直接 42P01 抛错，下方
-- "absent; nothing to repair" 分支从未可达；全新安装没有预建分区

**⚠️ 同一文件里两层时间：**
- `Background (2026-09-07 …)` = **它当初要修的问题发生在 09-07**（应用时点）；
- `2026-10-01 fresh-install e2e 修订` = **今天又改了 `::regclass` → `to_regclass`**。

**⇒ 该文件在真库已被标记为「已应用」（`version=686`，description `fix_session_module_executions_2026_10_bounds`），
而它的内容在今天被修改过。**
**⇒ 补录 checksum = 把「今天这次修改」记成「09-07 应用时的内容」⇒ 篡改历史。**

## 五、playbook §77 新增

> **§77 判断「文件在应用后是否被改过」要用 git 提交历史，不要用 mtime —— checkout 会把所有 mtime 刷成同一天**

**由来**（R89-CU / 185 号）：本轮第一遍用 mtime，得到「70 条跨度 08-25→10-01，几乎全可疑」
**这个结论等于没判** —— 因为本仓库是 10-01 拉取的，**mtime 反映的是写入工作树的时间**，
**不是内容改动时间**。换 `git log --reverse` vs `git log -1` 后才得到可用结论：**11/70 被改过**。

**⇒ 落地三条：**
1. **「文件是否被改过」的权威判据是版本历史，不是文件时间戳** ——
   命令固定为：`git log --reverse --format=%as -- <path>`（首次）与
   `git log -1 --format=%as -- <path>`（最近），**两者不等即改过**；
   ⚠️ **clone/checkout 会把 mtime 全部刷成 checkout 时间**
   ⇒ **mtime 在 CI、在同事机器、在容器里都不成立**（§59 的形态 B 又是同一个根）；
2. **⚠️ 「建议修法」里带前提的条件，必须在推荐之前把前提验掉** ——
   184 号写「补录前必须人工核对这 70 个文件没被改过」，
   **本轮验了，结论是 11 个改过 ⇒ 推荐方案 A 直接不可用**。
   ⇒ **把前提留在报告里当「注意事项」，等于把风险转移给读者**；
   **前提没验就推荐，是本会话第二次**（第一次是 181 号的「根因」被 182 号推翻）**；
3. **⚠️ 「重放迁移」的危险不只在重复执行，还在「重放的不是当初那版」** ——
   本轮发现 11 条已改过 ⇒ **方案 C 的危害比 184 号写的大一档**。

**⇒ 与既有条目的关系**：
§74/§75 说「先确认键、再确认机制会做什么」；
**本条说「推荐动作之前，先把动作成立的前提验掉」——
一个带未验前提的推荐，在报告里和已验证的推荐读起来一模一样。**

**同族**：§33（双向证据）/ §37（四维评估）/ §41（注释三桶）/ §45（命中 ≠ 引用）/
§59（尺子错的形态 B）/ §74（撞车归因）/ §75（尺子要先量）/ §76（缺校验 vs 校验会拒绝）。
