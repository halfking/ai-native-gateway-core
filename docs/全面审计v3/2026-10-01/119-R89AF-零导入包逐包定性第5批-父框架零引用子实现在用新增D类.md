## 〇、【本轮最重要的产出】A/B/C 三分法不够用——出现第 4 类

`domains/hooks`（829 行，**4 个 `.go` 文件**）**自身零引用**，
但它目录下有 **20 个子包**，其中至少这些**在前几轮已被逐个确认在用**：

- `domains/hooks/compression` —— `session_cache.go` / `diff.go` / `cut_marker.go`（105/110/113 号反复读过）
- `domains/hooks/promptinjection` —— `cmd/gateway/main_pipeline.go:112` 明确装配
- `domains/hooks/observability` —— `telemetry/client.go`（113 号读过的两套写方之一）
- `domains/hooks/sessionaudit` —— `domains/sessionaudit/events.go` 的对偶

**⇒ 「`domains/hooks` 零导入」绝不能读成「hooks 体系是死代码」。**

**这是 105 号 playbook §17（构造函数不可见）的目录版本**：
`NewHookRegistry(...)` 若在 `main.go` 里就地构造并注册，**类型名 `HookRegistry` 在外部文件里 0 命中**；
同理，**父包零引用只说明「父包导出的东西没被用」，不说明「子包没被用」**。

**⇒ 判为第 4 类 D 类：「父框架零引用、子实现在用」**，与 A/B/C 都不同：

| 类 | 含义 | 处置 |
|---|---|---|
| A | 真死代码 | 删 |
| B | 能力已在、从未接线 | 确认是否接线 |
| C | 刻意分阶段（文档明写等集成者 + kill-switch） | 先确认阶段是否仍要做 |
| **D（本轮新增）** | **父框架/注册层零引用，子实现各自被单独装配** | **不可按 A 删**；需决定「是否要把框架层接回去」 |

### 0.1 D 类的具体形态（本轮坐实）

`domains/hooks` 导出的是**框架层**：
`HookRegistry` / `NewHookRegistry(configManager, metrics, logger)` /
`Hook` 接口 / `Phase` 枚举 / `ConfigurableHook` / `Environment` / `NewEnvironment(requestID)` /
`Registry` / `ConfigManager` 接口 / `FileConfigManager` / `NoOpConfigManager` /
`PrometheusMetricsCollector` / `NoOpLogger`。

**外部引用 = 0。**

**⇒ 坐实的事实**：**hook 的「注册表 + 统一生命周期 + 声明式配置 + 统一指标」这一层从未被使用**，
而**各个 hook 的实现是被逐个单独装配的**（`main_pipeline.go` 逐个 new）。
**这不是「框架没写完」，是「框架写完了、大家绕过它接线」。**

**⚠️ 未证实项**：各 hook 在 `main_pipeline.go` 里的装配是否**重复实现了**框架已有的
`Phase` / `Environment` / 指标收集能力，**本轮未核**。
若重复，则存在**同一职责两份实现**（那才是真问题）；若不重复，则只是「没用框架」。

## 二、`intentanalysis`（277 行）—— 意图分析链路的「hook 半边」没接

包注释自陈功能：**多轮意图分析（基于会话历史）**、**意图漂移检测（KL 散度）**、
智能模型推荐、**配置热加载（30 秒轮询）**。
`NewIntentAnalysisHook(analyzer *intentconfig.Analyzer, logger *slog.Logger)`。

**⇒ 与 114 号交叉得出一个结构性事实**：

但在 `examples/intent_analysis_demo` 与 `tests` 下** —— 即**只有示例与测试在用**。
本轮确认调用它的 hook `intentanalysis` **零引用**。
⇒ **意图分析这条链在生产上整条没跑**：分析器只活在示例里，hook 没装配。
（`examples/intent_analysis_demo` 反而证明**当初是打算接的**，只是没接。）

**⇒ B 类**。对应 objective 的「auto 模型的实现」与意图驱动路由方向。

## 三、`internal/agent/wsclient`（293 行，1 文件、**无测试**）—— 服务端在，客户端没找到

包注释：

> Package wsclient — **local instance ↔ center WebSocket client**.
> Decision baseline 2=A: WS is the preferred channel for register/heartbeat/cmd.
> **On 3 consecutive failures the client yields to `HTTPHeartbeatFallback`,
> which POSTs to `/maintain-api/public/instances/heartbeat` every 30s.**
> Why stdlib only: the protocol is a few JSON frames; pulling gorilla/nhooyr
> for a 200-line client is not worth the dependency surface.

- 导出：`Frame` / `Handler` / `Config` / `Status` / `Client` / `New(cfg)`。
- **外部引用 = 0，且该包无任何测试文件。**

**现役对照**：`cmd/license-authority/heartbeat_handler.go:13-28`
—— **心跳的服务端接收方是存在的**（`NewHeartbeatHandler(store, serverPubKey)`、
`HandleHeartbeat`），`cmd/license-authority/routes.go:104` 也确实注册了
`heartbeatHandler.RegisterRoutes(instanceTokenGroup)`。

**⇒ 判读**：**服务端在，客户端这条（WS + HTTP 兜底）没找到消费者。**

⚠️ **诚实边界**：我在本轮**只检索了** `maintain-api/public/instances/heartbeat`
与 `HeartbeatHandler` 两个符号，**没有穷举网关侧是否用别的机制上报心跳**
（比如 license 客户端的独立实现、或某个 `collect` 批处理）。
**⇒ 「客户端没接」是本轮检索范围内的结论，不排除网关确实在上报心跳。**
**已列入下轮必核，不在此下断言。**

**⇒ B 类**，并附一条实现层面的观察：该包**没有任何测试**，
而它要处理的是「WS 断线重连 + 连续失败降级 + 30s 兜底定时」——
**这类代码缺测试时不应直接接线**（与 117 号 `remotecontrol` 的判断同型）。

## 四、`internal/errdiscard`（273 行）—— 归类修正：这是 **CI 守卫**，不是运行时能力

包注释把它的来龙去脉写得很完整：

> Package errdiscard 检测「上抛打到了丢弃错误的调用方」这一缺陷形状（R68）。
> R66 给全仓 rows 循环加了迭代终检（return / warn / continue 三选一），
> 守卫 `internal/rowsguard` 只判「`X.Err()` 在不在循环旁边」——
> **它结构上无力发现分型是否选对**。R67 的独立复审据此抓到 4 处真缺陷，
> 全部是同一形状：`f(...)` 改成 `return nil, err`，而 `x, _ := f(...)`。

测试 `TestErrDiscard_NoNewDiscardingCallSites` —— **防新增回归**。

**⇒ 归类修正**：114 号把它算进「32 个运行时候选」是**错的**——
它和 `internal/rowsguard` 一样是 **CI `make guards` 执行的静态守卫**，
只是名字不含 `guard` 所以没被我的排除规则命中。

**⇒ 但要明确说清：它不是死代码，是有价值的活资产。**
它是本审计周期内（R66→R67→R68）**沉淀下来的防回归机制**：
已经用 4 个真实缺陷换来了「这类形状不会再长出来」的保证。

**⇒ 从「运行时候选」移到「非运行时」，并单列一句**：
**守卫的价值不在它跑不跑，而在它拦住过什么。**
