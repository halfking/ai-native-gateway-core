## 一、穷举核验（一条 SQL，三项检查）

```sql
WITH s AS (SELECT DISTINCT storage_path, hash
           FROM request_attachments WHERE storage_path IS NOT NULL)
```

| 检查 | 结果 |
|---|---|
| `storage_path` 形状符合 `^\d{4}/\d{2}/[0-9a-f]{2}/[0-9a-f]{2}/[0-9a-f]{64}\.[A-Za-z0-9]+$` | **80 / 80** |
| 文件名主干 == `hash` 列 | **80 / 80** |
| 分片目录 `{hash[0:2]}/{hash[2:4]}` 与 `hash` 自身一致 | **80 / 80** |

**不合规样本查询返回 0 行。**

⇒ **163 号的结论从「结构级（抽样 3 行）」升级为「穷举已验证（80/80）」。**

**⇒ 待裁决 64 的修法 2（删除前与引用表求差集）确认是一条纯 SQL 谓词，不需要任何路径规整或哈希反解。**

## 二、⚠️ 顺带记一次我自己摆的乌龙（本轮第二个检测器缺陷）

第一条 SQL 我同时算了三项，其中「文件名是否等于 hash」这项我写成：

```sql
split_part(storage_path,'/',5) = split_part(hash,'',1) || '.' || substring(...)
```

**`split_part(hash,'',1)` 的分隔符是空串 —— 它返回空串，不是 `hash` 本身。**

⇒ 该列**恒为 0**，输出 `filename_matches_hash = 0`，
**看起来像「80 份全部不匹配」这个惊人的结论**，实际是我这条 SQL 写错了。

⚠️ **如果我照着这个数往下写报告，就会产出一条「80 份路径全部与 hash 不符」的假发现。**

**形态与 §47/§48/§50 完全同族**：**分类/比对条件写错 ⇒ 输出一个干净、自洽、但完全错误的数字，
且不报任何错。**

**⇒ 这一条印证了 §50 的落地方式是对的**：**「把已知为真的样本喂给判据」**。
本轮如果只盯着「shape_ok = 80/80」就收工，第二个数字会直接被我写进报告。
**是「这个 0 太整齐了」让我回头看了它** —— 与 §39「返回 0 / 反常整齐时先怀疑形态」同源。

**修正后的判据（可用）**：
```sql
regexp_replace(split_part(storage_path,'/',5), '\.[A-Za-z0-9]+$', '') = hash
```
