# 72 号报告：R88 审计守卫的专用 CI 门漏登记 3 个包（含 R87-g 的 routeguard）

- 日期：2026-10-01
- 轮次：R88
- 变更面：`.github/workflows/audit-guards-ci.yml`、`scripts/checks/guards-sync.sh`
- 触发：R87 收口后推进待办「D16 剩余补门」时，先去核实 playbook D16:94 那句「本域验收门对附件域零覆盖」的现状

---

## 0. 结论先说

**发现一处真缺陷，并已修复**：

`audit-guards-ci.yml` 的「audit guards」步骤**硬编码了 7 个守卫包**，
而 `Makefile` 的 `GUARD_PACKAGES` 早已是 **10 个**——
**`metricguard` / `partguard` / `routeguard` 三者从未在这个专用 job 里执行过**。
三个包都是 2026-10-01 当天新增的（含 R87-g 我自己新建的 `routeguard`）。

**且当时文件里那句注释是假的**：

> 显式列出 7 个包而不是 `make guards`，是为了让 CI 日志直接显示哪个包红；
> **两者跑的是同一组（guards-sync 已校验二者一致）**。

`scripts/checks/guards-sync.sh` 在本轮之前**只校验「磁盘 `*guard` 目录 → Makefile 登记」，
从不读任何 CI 文件**。它没有、也不可能校验 CI 那份清单。

---

## 1. 但定级前必须先排除更宽的覆盖——**我第一反应是错的**

第一反应是「routeguard 从来没在 CI 上跑过」，这是**过重的结论**。落笔前核实：

```bash
grep -n "make test-short" .github/workflows/sessionforensics-ci.yml
# :42  run: make test-short
# Makefile:42  test-short: go test ./... -count=1 -short -timeout=120s
```

`sessionforensics-ci.yml`（workflow 名 `llm-gateway-go-ci`，触发条件 `push`/`pull_request` 到 `main`）
每次推送都跑 `make test-short` = `go test ./...`，**`./...` 包含这 10 个守卫包**。

⇒ **三个守卫在 CI 上确实执行过**（经由全量单测门），只是不在那个**专用** job 里。

**定级 P3，不是 P0/P1。** 实际损失是：

- 专用门失去 per-package 归属（红在哪个包要看全量单测那份日志）；
- 超时从该 job 的 180s 降为 `make guards` 的 120s（实测 10 包最慢 6.06s，余量充足）；
- **真正的危害是漂移会继续扩大**——每加一个守卫就多一个「忘了同步第二份清单」的机会。

**教训**：「某门在 CI 上没跑」是个很容易喊出来的结论，而它需要先排除三条更宽的执行路径
（全量单测门 / pre-push / 其他 workflow）。**先问「它真的没跑吗」，再问「它跑在哪」。**

---

## 2. 修法：消灭第二份清单，而不是同步它

把 CI 改成调用 `make guards`，让 `GUARD_PACKAGES` 成为唯一事实源：

```yaml
      - name: audit guards
        run: make guards
```

原来「显式列举是为了 CI 日志能显示哪个包红」这个理由不成立——`go test` 仍逐包打印
`ok github.com/.../xxxguard 6.064s`，定位到包不成问题。**重复清单的维护成本 > 可视性收益。**

---

## 3. 给 `guards-sync.sh` 补上它从来没做的那一跳

原脚本只有「磁盘 → Makefile」一个方向。三处补强：

1. **反方向**：已登记的条目必须真的存在于磁盘。原先一条过期/拼错的登记项不会被发现，
   只会等到 `go test ./internal/<不存在>` 时以另一种方式炸。
2. **CI 不得硬编码守卫包清单**（正则排除注释行）：这是本轮缺陷的根因防复发。
3. **专用门必须还在**：`make guards` 必须以 `run:` 步骤存在，否则守卫静默降级为「只在本地跑的东西」。

### 3.1 顺带查实：原脚本的自述与事实不一致

修完后脚本打印「**全部 7 个**守卫包已登记（GUARD_PACKAGES 内 **10** 项）」。
原因是正向检查靠 `find internal -maxdepth 1 -name '*guard'` 枚举磁盘，而
`errdiscard` / `dbrows` / `jsoncol` **三个目录不以 `guard` 结尾**⇒ 它们从不出现在正向检查的视野里。

实测三个目录都存在且各含 1 个 `_test.go`，`make guards` 确实跑它们（见下），所以**不是缺陷**；
但「7 vs 10」的自述会让下一个人以为覆盖不全。

**本轮不重命名这三个包**：纯机械改名会波及 package 名、import 与既有文档，与 P3 不相称。
改为打印**双向一致**的真实数字，并对 3 个非 `guard` 命名的登记项**告警留痕**（不拦），
残余盲区（将来新建一个不叫 `guard` 的审计包则磁盘枚举看不见它）在注释里写明。

## 4. 【本轮最值得记】变异验证抓出**我自己这道门的自证漏洞**

新加的「专用门必须还在」判据，初版是：

```bash
grep -rqs 'make guards' "$workflow_dir"
```

变异 M2（把 `run: make guards` 换成 `run: echo noop`）**没有转红**。按 §9 四步排查：

1. **变异生效了吗**——生效了（文件确实被改）；
2. **门量的是语义还是代理量**——**代理量**。判据是「文件里出现过这个字符串」，
   而 `audit-guards-ci.yml` 里恰好有一行我刚写的注释
   「# R88 改：直接调 `make guards`」⇒ **注释本身满足了判据**；
3. **判据有无自证漏洞**——**有，而且是教科书式的**：门被「描述它的那段文字」证明存在。

修法是锚到真正执行的命令、并排除注释行：

```bash
grep -rqsE '^[[:space:]]*run:[[:space:]]*make[[:space:]]+guards[[:space:]]*$' "$workflow_dir"
```

硬编码清单那条判据同样加了 `^[^#]*` 排除注释行。

**为什么这条值得单列**：这个漏洞**不可能靠读代码发现**——判据读起来完全合理、
注释也完全合理，只有把它们放在一起才会看见「门的存在被门的说明文字证明了」。
**而这正是 §9 要求变异验证的场合：门第一次报绿和报红一样需要解释。**
