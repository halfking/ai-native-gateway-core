| 基准 | 零导入数 | 错在哪 |

## 二、两次错基准各抓出一个「假死」

### 2.1 第一次错：`./cmd/gateway` 基准 ⇒ 误判 `domains/ursm/v2/migration`（3,778 LOC，最大零导入包）

它在 `./cmd/gateway` 的依赖图里查不到，看起来是最大的死代码包。
实际上：

```
cmd/k2-migrate-ursm/main.go        ← 消费方
cmd/ursm-k2-preflight/main.go      ← 消费方
```

这是**运维迁移工具包**（ledger / preflight / copy / cleanup / 三个 Lua 脚本 / PG store），
**按设计就不该链接进 server 二进制**。它还有 11 个测试文件，
其中一个叫 `g4_isolated_redis_evidence_test.go`——
名字里带 evidence，说明是某次线上事故的证据固化。

**⇒ 3,778 行代码如果按「零导入 = 死代码」删掉，会删掉一整套 K2 迁移工具。**

### 2.2 第二次错：`./cmd/...` 基准 ⇒ 仍误判 `domains/intentconfig`（1,824 LOC）

用 `./cmd/...` 重算后 `intentconfig` 仍在零导入名单里，
但我手工 grep 得到**外部 import 方 2 个**——矛盾。
原因：那两个 import 者在 **`examples/intent_analysis_demo` 与 `tests` 下**，
它们是 `package main` 但**不在 `./cmd/` 目录下**。

**⇒ 正确的枚举方式是 `go list -f '{{if eq .Name "main"}}…' ./...`，不是按目录猜。**

## 三、逐包定性：本轮只做了 1 个（`domains/remotecontrol`）

其余 29 个**未做**，不做任何推测。按纪律逐包读，下面只报读过原文的一个。

### 3.1 `domains/remotecontrol`（1,000 LOC，3 文件）→ **B 类：能力已在，从未接线，且有真实操作权限**

- `lark_commands.go` 是一个**飞书远程指令解析器 + API**：
  `pause/暂停`、`resume/恢复`、`terminate/终止/kill`、`inspect/检查/detail`、
  `status/状态`、`modify/修改`（`lark_commands.go:81-92`）。
- `executor.go` 的 `DefaultCommandExecutor` 自述职责为
  「执行远程指令 / **权限验证** / 审计记录」，并依赖 `AuthorizationChecker`（`executor.go:11-20`）。
- **外部 import 方 = 0**，且不在任何 main 包的依赖图里 ⇒ **从未被装配**。

**为什么这条值得单独登记**：
它不是「一个没人调的工具函数」，而是**一套带 `terminate/kill` 会话能力的远程控制面**。
- 它**从未运行过**，所以 `AuthorizationChecker` 这道权限门**从未被真正执行过**——
  按注释纪律，注释承诺的接线默认不成立，这里连「接线」本身都没有。
- 一旦有人把它接上，`terminate/kill` 从飞书直达会话，**权限模型与审计链路是全新的**，
  且当前没有任何测试覆盖装配路径（`remotecontrol_test.go` 1 个文件，测的是解析与 executor 本身）。

**⇒ 不建议按 A 类（死代码）删除。** 归 **B 类**，登记待产品/运维裁决：
「是否存在飞书远程运维的诉求」——无则整包删（1,000 LOC）；有则必须先设计权限与审计，
**不能直接接线**（这与 107 号 `nodestatecache` 的教训同型：照原描述接线会造出第二个状态源）。
