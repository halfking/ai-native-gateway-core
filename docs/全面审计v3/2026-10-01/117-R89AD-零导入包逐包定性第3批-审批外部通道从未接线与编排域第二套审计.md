## 二、`api/webhooks`（687 行）—— 审批的**外部通道**从未接线

- 内容：`feishu_callback.go` / `wechat_callback.go` / `types.go`。
  飞书回调含 **`crypto/sha256` + `subtle`（常量时间比较）签名验证 + 时间戳验证**
  （`TestFeishuCallbackHandler_VerifySignatureTimestamp`、
  `TestFeishuCallbackHandler_VerifySignatureUsesVerifyTokenWithoutEncryptKey`），
  以及 URL 验证、事件回调的**通过 / 拒绝**两条审批动作
  （`TestFeishuCallbackHandler_HandleEventCallback_Approve` / `_Reject`、
  `_MissingRequestID`）。
- **外部引用 = 0。**
- **现役的审批入口只有 admin API**：
  - `admin/handler.go:1163-1164` — `/api/admin/session-approvals`、`/api/admin/session-approvals/`
  - `admin/handler.go:1185` — `/v1/approvals/`（客户端查审批状态）
  - 队列写入方：`domains/interception/approval_creator.go` + `cmd/gateway/approval_integration.go`

**⇒ 判读**：审批队列本身是**活的**（有 API、有创建器、有 `approval_queue` 表），
但**没有任何外部即时通讯通道**——审批人**必须打开管理端页面**才知道有请求在等他。
对需要人工放行的敏感操作（会话审批），这是一条**产品层面的功能缺口**，
而不是代码缺陷。

**⇒ 与本审计已记录项的关系**：`domains/hooks/compression/session_cache.go:204-205`
的 `ApprovalStatus`（`pending|approved|rejected`）与 `ApprovalID` 字段是**活的**，
说明审批状态在会话侧被正确记录——**缺的只是「通知出去」这一段**。

**不构成安全缺陷**（审批不会因为没有 IM 通道而被绕过——它只是没人知道）。
登记为产品缺口，**B 类**。

## 三、`domains/sessionstate`（661 行）—— 第二个会话状态机

- `SessionStateMachine`，测试覆盖：基本转移、**审批流**、审批拒绝、错误恢复、
  **从任意状态取消**、metadata、**metrics**、**snapshot**、**自定义转移条件**。
- **外部引用 = 0。**
- 与已查的 **URSM v2**（节点状态，`domains/ursm/v2/`，**在用**）是**不同维度**的状态机
  （会话 vs 节点），**不是重复**。

**⇒ 判 B 类**，登记待裁决「会话状态是否需要一个集中状态机」。
按 objective 第 26 项「**全局的节点状态需要统一，状态更新需要在一个模块中进行**」，
本仓已对**节点**做到了（URSM v2），
**对「会话」是否也需要，是一条尚未回答的产品问题**（107/108 号同类）。

## 四、`domains/orchestration/observ`（478 行）—— 与 `sessionaudit` 重叠的第二套审计

- 注释直接引用设计契约：「Unified Auto-Orchestration Plugin — Workflow C
  (Observability & Audit Log)」，并逐字引用 **§9.2**：

  > "Every decision and action records: event_id, type, timestamp, tenant,
  > goal_run/session/request/task, causation/correlation, attempt/**fencing token**,
  > policy version, reason code, **redacted payload hash**."

- `AuditEvent` / `Sink` / `Auditor.Record` / `HashPayload`。
- 测试质量高且**直接钉住安全属性**：
  `TestAuditEvent_NoRawPayloadField`（**保证审计事件不落原始 payload**）、
  `TestHashPayload_DeterministicAndHex`、`TestAuditor_PropagatesSinkError`、
  `TestMemorySink_Concurrent`、`TestNewEventID_UniqueAndNonEmpty`。
- **外部引用 = 0。**
- **现役对照**：`domains/orchestration` 主体**在用**（不在零导入名单），
  但它**自己的 `observ` 子包没接**；而审计事件流**已有现役实现**：
  `domains/sessionaudit/events.go`（在用，被 `domains/streaming/{handler,responses,messages}.go` 写）。

**⇒ 判 A/B 待裁决**：若接，会成为**第二套审计事件系统**（与 `sessionaudit` 并存）。
但要如实指出：**`observ` 的设计维度明显更全**——
有 `causation/correlation`（因果与关联）、**`fencing token`**（防旧写入覆盖新写入）、
**`policy version`**、**`redacted payload hash` 且测试保证不落 raw payload**。
现役 `sessionaudit/events.go` 是否具备这些维度，**本轮未核**，不下结论。

**⇒ 登记为待产品/运维裁决**：「编排域要不要独立的审计事件流？」
要 ⇒ 需先比对 `sessionaudit` 的字段维度再决定合并还是并存；
不要 ⇒ 整包删（478 行）。

## 五、`internal/probe`（440 行，1 文件）—— 凭据健康检测没有逐步 trace

- 包注释自陈用途：为管理端「**立即检测**」点击提供逐步记录——
  **探测了哪个 URL / 上游返回了什么 / 在哪一步失败 / 每步耗时**；
  刻意与全局状态解耦，调用方传 `*slog.Logger` + 关联键
  （`provider_id` / `credential_id` / `task_id` / `model`），
  使每条日志与周围的 `admin.doHealthCheck` 日志**带同样的关联键**。
- 导出：`StepStatus` / `RequestSummary` / `ResponseSummary` / `Step` / `Trace` /
  `Recorder` / `NewRecorder` / `FinishOption` / `WithNotes`。
- **外部引用 = 0**（**且该包无测试文件**）。

**⇒ 判 B 类**，直接对应 objective 的「检查各类场景安全：…网络请求处理的可靠性」
与「全面检查连接供应商端的请求的错误处理逻辑」。
**凭据健康检测失败时，运维只能看到最终失败，拿不到「卡在哪一步」。**
