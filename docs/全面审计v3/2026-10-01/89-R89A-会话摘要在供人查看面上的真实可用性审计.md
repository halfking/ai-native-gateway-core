## 2. `session_titles` 的真实内容（决定性数据）

`session_titles` 同时记录了**标题来源**（`model` 列）——这是本轮最关键的可测量点：

| `model` | 行数 | 占比 | 含义 |
|---|---|---|---|
| **`auto-extract`** | **189,997** | **44.42%** | **回退路径**（非 LLM） |
| `auto-title` | 145,939 | 34.12% | LLM 生成 |
| `minimax-m2.7` | 52,947 | 12.38% | LLM 生成 |
| `minimax-m3` | 36,429 | 8.52% | LLM 生成 |
| `glm-5.1` / `auto-summary:minimax-m3` / `deepseek-v4-flash` / `session-summary` | 2,451 | 0.58% | LLM 生成 |
| **LLM 合计** | **237,766** | **55.58%** | |

**而 44.42% 的回退产物，形态无一例外全是非标题内容**：

| 回退标题形态 | 行数 |
|---|---|
| `system: You are ZCode, an interactive coding agent…` | **115,615** |
| `system: [gateway-handoff-v1] Resume the prior session using…` | 39,778 |
| `[ZCode] {"max_tokens":128000,"messages":[{"content":"You are…` | 23,867 |

对照：同表里**确实有**像样的 LLM 标题（`Solve: determine all functions f: N -> N such that f(f(n))…`、`hz-drill地图终版第三轮修订`、`hz-drill热机B关闭参数配置`）⇒ **生成器本身能用，问题是回退路径占了 44% 且产出全废。**

### 2.1 讽刺之处

网关自己发给标题 LLM 的指令原文是：

> 「用中文生成一个简短准确的标题（不超过18字）…**只输出标题纯文本：不要引号、编号、解释、XML/HTML 标签、thinking/redacted 标记或英文占位符**」

⇒ **网关明确规定「输出里不要有标记」，而它自己 44% 的标题字段里恰恰全是系统提示词、handoff 内部标记和原始 JSON。**

## 3. 根因：定位到一行分支

> ⚠️ **本节在 90 号被进一步修正**：下面对「3c 分支」的描述准确，但它对**为什么这条
> 分支会被走到**的解释不完整。真实机制更锋利——见 90 号 §1。**本节保留原样并在
> 此标注**，不静默改写。

`admin/auto_title_generator.go:637-663` `extractTitleFromPreview` 的四步本意是好的：

```go
idePrefix := g.detectIDESource(preview)          // 1. 识别 IDE 来源
userPrompt := g.extractUserPrompt(preview)       // 2. 明确「skip system messages」
if idePrefix != "" && userPrompt != "" { ... }   // 3a. [IDE] + user prompt
else if userPrompt != "" { title = userPrompt }  // 3b. user prompt
else {                                           // 3c. ← 问题在这里
    title = preview                             //     直接用原始预览
    ... 折叠空白
}
```

**根因**：预览是 **320 字节**（`:92` 注释 `320-byte summary used as fallback`）。在 ZCode/Cursor 这类 agentic 负载里，**system prompt 本身就远超 320 字节** ⇒ 预览里**根本装不下任何 user 内容** ⇒ `extractUserPrompt` 必然返回空 ⇒ **必然走 3c 分支** ⇒ 拿到的就是 system prompt 的开头。

⇒ **这不是「偶尔选错消息」，而是结构性必然**：只要走回退，看到的第一段一定是 system。

对照证据：数据里回退标题长 68–78 runes，正好卡在 `sessionTitleMaxRunes` 附近——**它们是「预览的前 N 字符」，不是「消息摘要」**。

## 4. 影响面与定级：**P1**（落笔时先写 P2，已被自己推翻并订正）

我初稿写的是 **P2**（可观测性/可用性缺陷），理由是「受害的只是给人看的那一行」。
**落笔后补了一次检索，直接把它推翻成 P1。**

`admin/turns_sessions.go:466-476` 的会话搜索 SQL：

```sql
CASE WHEN tstate.tenant_id IS NOT NULL
     THEN COALESCE(tstate.title, '')
     ELSE COALESCE(NULLIF(s.title,''), st.title, ss.title, '')
END ILIKE '%'||$n||'%'
  OR …topic… OR …intent… OR …summary…
```

注释原文：「search 同时匹配标题（含 `session_titles` / `session_summaries` fallback）…**让自动生成的标题/摘要也能被搜到**」。

⇒ **标题是搜索的匹配面之一。** 于是那 189,997 条回退标题不只是「显示难看」：

- 搜 `You` / `ZCode` / `system` / `gateway-handoff` 会**命中数万条与用户意图无关的会话**；
- 反过来，**真正想找的那条会话反而被淹没**——用户搜自己的问题词，命中的是 11 万条系统提示词。

⇒ 定级 **P1**（功能性缺陷：搜索结果被污染），而非展示层瑕疵。

**其余影响面**：

- **不涉及数据丢失**：用户消息本身完整存在别处（`session_turn_details` 等）；
- **可信度限制**：本机流量以本地测试为主（87 号），`You are ZCode` 这类负载的占比可能被本地放大，**生产上的比例可能不同**——但「回退分支产出系统提示词」这个**机制**与流量占比无关，**必然成立**。

## 5. 可选修法（**均需产品裁决，本轮不擅自动手**）

| 方案 | 做法 | 代价 |
|---|---|---|
| **甲（推荐）** | 回退时**不再用原始预览**，改为：跳过 system 后若确实无 user 内容，则用 `detectIDESource` 的结果 + 「(仅系统提示，无用户输入)」之类的**显式占位**，绝不落系统提示词原文 | 小；只改 `extractTitleFromPreview` 的 3c 分支 |
| 乙 | 把预览从 320 字节放大到能容下 system+首条 user | 中；内存/日志面变大，且**长 system 仍可能装不下**，治标不治本 |
| 丙 | 回退时**不写标题**，留空由 UI 显示「未命名会话」 | 小；会改变现有展示 |

⇒ 三者都会改变**客户端观感**，按 objective「所有操作不要影响客户端的观感」的约束，**登记为待裁决第 37 条**。
