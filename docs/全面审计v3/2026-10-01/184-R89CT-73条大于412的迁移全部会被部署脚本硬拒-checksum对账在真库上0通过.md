## 七、playbook §76 新增

> **§76 「没有校验机制」和「校验机制会拒绝」是两个不同量级 —— 查登记缺口时，顺手模拟一遍那条机制的判定**

**由来**（R89-CT / 184 号）：183 号把 118 条无 checksum 记为「改文件不会被发现」（P3 性质）。
**184 号用真库数据复刻脚本判定后发现：其中 73 条不是「不会被发现」，
而是「**部署时会被主动拒绝**」，且 0 条能通过。**

**⇒ 落地三条：**
1. **「缺校验」不要只按「可观测性缺口」定级** ——
   **先看那条校验缺记录时的行为是「警告」还是「拒绝」**。
   本仓是 `|| return 1` ⇒ **量级完全不同**（P3 → P1）；
2. **判定可以离线复刻，不必真部署** ——
   本轮用 Python 逐字复刻 shell 的 glob + 过滤 + 查表三段判定，
   **输入全部来自真库只读查询 ⇒ 无副作用、可重复**。
   ⚠️ **复刻必须逐字对齐**（本轮对齐了：`.down.sql`/`.skip`/`.bak.skip` 三个排除项、
   `head -15` 的行数、忽略大小写的 `DEPRECATED` 匹配），
   **少对齐一条就会得到不同的「唯一可解析」计数**；
3. **⚠️ 阈值来自被审计对象自身配置** ——
   `DB_LEDGER_RECONCILE_FROM:-412` 决定了「哪些该被校验」，
   **套用「全部迁移」会把 45 条有意豁免的历史迁移也算成缺陷**（§35 再一次兑现）。

**⇒ 与 §75 的关系**：
§75 说「先确认你要用的字段真的是键」；
**本条说「确认了之后，还要确认那条机制在数据面前会做什么」——
「不校验」和「校验且拒绝」在报告里读起来只差一个词，代价差一个量级。**
