**PARTIAL。** 已实现 5 个协议的双向转换，超参跨协议保留由注册表驱动（质量高于一般实现），无跨请求串话、无协议私有字段泄漏、文档编解码无损。

但存在 **1 条需求未实现、1 个功能开关的「开」态完全不可用、3 处静默丢字段/静默降级、1 处硬 400**，以及 **1 条 objective 关键需求被 ADR 明确阻塞**。

## 1. 已修

### 1.1 `max_tokens: 0` 导致 Anthropic 上游硬 400 【P1】

**事实**：`serialize_anthropic.go` 无条件写 `"max_tokens": req.MaxTokens`。Anthropic Messages 的 `max_tokens` **必填且必须 > 0**。OpenAI 的 `max_tokens` / `max_completion_tokens` 都是可选的，`parse_openai.go` 在两者都缺失时把 `ir.MaxTokens` 留在 0。

```
IR.MaxTokens=0
anthropic body={"max_tokens":0,"messages":[...],"model":"claude-sonnet-4"}
```

**这是 IR 化引入的回归**：旧的非 IR 转换路径（`domains/transformation/anthropic/chat_to_anthropic.go:23-28`）在缺省时显式填 `4096`。

**触发条件**：OpenAI 客户端省略 `max_tokens`（很常见，流式尤其）且路由到 Anthropic 上游。

**修法**：`anthropicMaxTokens(n)`，`n <= 0` 时回落到 `DefaultAnthropicMaxTokens = 4096`——与旧路径对齐，取的是**已经部署过的行为**，不是新发明的默认值。

> ⚠️ 连带影响待观察：`ClampRestoredReasoningForAnthropic`（`executor_anthropic.go:573`）在 `max_tokens` 过小时会整体丢弃 thinking，改默认值后该路径行为会变化。

### 1.2 Ollama 扩展丢弃无痕 【P1】

**事实**：`SerializeOllama` 是四个之外的第五个序列化器，它只读 `Extensions["ollama.*"]`，其余键无去处。其它四个序列化器（openai/anthropic/gemini/responses）都会对被裁剪的字段调 `ReportProtocolLoss`，**只有 Ollama 静默丢弃**——客户端的厂商私有参数消失时连一条可观测记录都没有。

**我第一次的修法是错的，且被测试当场拦下**：我先加了 `restoreExtensions(body, req, ProtocolOllamaChat)`，结果 `TestSerializeOllama_PrivateOptionsDontLeakAsTopLevel` 报红——该测试**显式断言** `unrelated.trace_id` 不得出现在顶层，注释写明「Ollama 键必须带 `ollama.` 命名空间，无命名空间的键是客户端误用，不盲目转发上游」。

**按「门第一次报红时先假设门是对的」**，我没有覆盖这个已固化的契约，改为**只补可观测性**：`reportUnnamespacedOllamaExtensions` 对每个被丢弃的无命名空间键发一条 `ReportProtocolLoss`，线上字节不变。

> 这是本轮第三次遇到「测试固化了看起来像缺陷的行为」：前两次分别是 R71 的 `native 形态直接 block` 与 R72 的 Ollama 命名空间契约。**测试是规格，不是障碍。**

## 2. 需产品裁决

### 2.1 `n>1` 静默丢弃第二个 choice 【P1】

**事实**：`internal/ir` **根本没有 choice 维度**——`StreamChunk` 无 `ChoiceIndex`、无 `Choices`，`stream.go:345` 与 `response.go:429` 都硬取 `Choices[0]`，`SerializeOpenAI` 产出的 `choice["index"]` 恒为 0。而 `serialize_openai.go:60-62` **把 `n` 原样转发上游且不拒绝 n>1**。

```
客户端发 {"n":2} → 上游真的生成 2 个 → 网关只回第 0 个
客户端拿到"1 个结果"，却以为请求了 2 个，无任何告警
```

Gemini 客户端路径同样受害（`handler_gemini.go:165-176` = `ParseOpenAIStreamChunk` → `SerializeGemini`，两个 candidate 全塌进 `candidates[0]`）。

**为什么需要你裁决**：三条路都不完美，且**都会改变客户端观感**（与 objective「原则上不影响客户端观感」冲突）：

| 方案 | 效果 | 代价 |
|---|---|---|
| (a) `n>1` 显式 400 拒绝 | 诚实，客户端立即知道 | 原本"成功"（其实是错的）的请求变成失败 |
| (b) 给 IR 加 choice 维度 | 真正正确 | 改动大，涉及 StreamChunk/InternalResponse/全部序列化器/流式状态机 |
| (c) 继续静默 | 无 | 客户端拿 1/N 个结果且不知情 |

我倾向 **(a) 作为立即止血 + (b) 作为后续**，但 (a) 确实改变观感，需要你确认。

### 2.2 「超出原厂的参数**缓存**下来（注意 TTL）」的需求边界

子代理把这一条查到底后的结论是：**代码里没有任何缓存，也因此不存在 TTL**。`Extensions` 是挂在 `InternalRequest` 上的进程内字段，生命周期等于单次请求，parse → serialize 之间不落任何存储（无 Redis、无 map、无计数器）。

已实现的是**同请求内透传**；**未实现的是跨请求多轮恢复**（例如第 2 轮把第 1 轮被裁掉的 `include:[reasoning.encrypted_content]` 找回来）。

我倾向认为「客户端每轮重发」是常态（Claude Code 的 `CLAUDE_CODE_EXTRA_BODY` 就是每轮全量下发），因此跨轮缓存**不一定是需求**。但 objective 明确写了「缓存 + TTL」，**需要你确认这是指跨请求多轮恢复，还是只是在描述单请求透传**。若是前者，那是一块尚未实现的功能，需要单独做设计与存储选型。

## 3. 出方案、本轮不修

### 3.1 `FF_OLLAMA_NATIVE=true` 时 Ollama 出站全量 501 【P1】

**这是本轮最重要的发现，但子代理的 P0 定级我下调为 P1。**

**已核实的完整链路**（每一环都亲自验证过）：

```
handler.go:4205  clientProtocol := "openai-completions"
handler.go:4207  if h.executor.IR != nil { clientProtocol = ir.DetectProtocol(body) }
                 → 实测：普通 OpenAI body → "openai-chat"(0.19)；Ollama 原生 body → "ollama-chat"(0.85)
handler.go:4466  ClientProtocol: clientProtocol        → ExecParams
executor_dispatch.go:1001  executeOllama(execParams, …)
executor_ollama.go:1004   finalizeOllamaUpstreamBody(params, …)   ← executeOllama 的第一件事
executor_ollama.go:1419   switch params.ClientProtocol { case "", "openai-completions": OK; default: 501 }
```

**detect 产出的是 IR 词表（`openai-chat`），门禁期望的是 catalog 词表（`openai-completions`），两者字符串永不相等。** 所以 IR 模式下（`h.executor.IR != nil`，即生产路径）`"openai-chat"` 落进 `default` → 501。

**为什么降级为 P1**：`FF_OLLAMA_NATIVE` **默认 false**（`settings/p4_feature_flags.go:51`，且 `envs.samples/02-gateway-features.env.sample:641` 留空 = false）。关闭时 dispatch 降级到 `routeOpenAI`，走 Ollama 的 OpenAI 兼容端点，是能用的。**所以今天生产无影响。**

**但「打开就 501」是最危险的形态**——开关看起来是个能用的旋钮，一开就把所有 Ollama 流量打死。

**关键：修门禁本身是不够的**，会把一条半成品路径暴露到生产。门禁后面还有三个已知缺陷：

1. Ollama 流式终止帧同时丢 `usage` 与 `finish_reason`（`parse_ollama_stream.go:144-156` 挂在 Done chunk 上，但 `stream.go:717-718` 对 `ChunkTypeDone` 直接 `return "data: [DONE]\n\n"`，从不读这两个字段；`executor_ollama.go:485-503` 的 Done 分支也只调 `WriteDone()`）→ **计费 `request_logs.prompt_tokens`/`completion_tokens` 落 NULL**，而费用计帐是 objective 的明确要求。同一 executor 的 `case ir.ChunkTypeUsage` 分支（`:545-553`）与 `audit/stream.go:96-120` 的采集口**都已正确实现**，只是永不触发。
2. 无任何生产代码写 `ollama.` 前缀的 Extensions（`parse_openai.go:100-110` 写的是**无前缀**的 `options`/`keep_alive`/`format`），而 `executor_ollama.go:1000-1002` 的注释称「every Ollama-private field is preserved verbatim」——与实测不符。
3. Ollama NDJSON 的 `message.tool_calls` 未被解析（raw struct 无该字段），流式工具调用全部丢失。

**方案**：先把 `FF_OLLAMA_NATIVE` 显式标注为「不可开启」并在启动日志里警告（避免有人一开就炸），再按「usage 拆分 → ollama.* 命名空间产出 → tool_calls 解析 → 最后才开开关」的顺序接线。

> 我自己在这里犯了一个错：最初 grep 时把 `executor_ollama.go` 整个排除在「谁构造 `OllamaExecutor`」之外，得出「生产零构造、整个执行器是未接线的岛」的结论。差点据此写出一份错误报告。`&OllamaExecutor{}` 恰恰就在那个文件内部。**排除条件本身会制造假结论。**

### 3.2 消息级未知字段全协议静默丢弃 【P1】

顶层未知字段有 `Extensions` + 异常上报的完整闭环（4 个 parser 均实测保留并上报），**消息级没有任何等价机制**——`Message` 结构体无 `Extensions` 字段，`parseOpenAIMessage` 只读 role/content/tool_calls/tool_call_id/name。

不可恢复的丢失清单（子代理实测）：

| 字段 | 可发方 | 后果 |
|---|---|---|
| `messages[].reasoning_content` | DeepSeek/GLM/Qwen 回放助手历史 | 推理链断裂 |
| `messages[].refusal` | OpenAI 拒答回放 | 丢失 |
| `messages[].audio` | OpenAI 音频输出回放 | 丢失 |
| `messages[].function_call` | legacy Completions | 丢失 |
| `messages[].trace_id` 等任意厂商私有键 | 全体 | 可观测性丢失 |

**方案**：`Message` 加 `Extensions map[string]json.RawMessage` + `ReportParseUnknownField`。`ContentBlock` 已有 `RawContent` 先例（`parse_openai.go:419-422`），照此办理。

### 3.2b 消息级未知字段 —— 本轮未动 【P1】

见 §3.2。为 `Message` 增加 `Extensions` 属于 IR 结构变更，需与 §4 的边界文档一并决策，本轮不动。

### 3.3 Gemini part 封闭结构体 【P1 —— 已修】

`parse_gemini.go:143-150` 的 part 结构体只有 6 个字段，`:165-275` 的循环**无 default 兜底**（对比 `parse_openai.go:419-422` 是有的）。Gemini 代码执行的线上真实 part `executableCode` / `codeExecutionResult` 被丢弃，无载体、无异常：

```
3 个 part 输入 → blocks kept = 1，anomaly events = 0
```

**已修**：`Parts` 改为 `[]json.RawMessage`，循环内解码为具名 `geminiPart`；没有任何分支认领的 part 进 `ContentBlock{Type:"raw", RawContent:…}` 并调 `ReportParseUnknownField`。同时收紧了包内约定漂移（parse_openai 早已有 RawContent 兜底，现在两边一致）。

**回归测试**：`TestParseGemini_UnknownPartIsPreservedNotDropped`（3 个 part 进 → 3 个 block 出，且逐块校验 part 名未被吞）／`UnknownPartIsReported`（保留必须伴随可观测）／`KnownPartsAreNotDuplicated`（已建模 part 不得被兜底重复收录）。

**变异验证**：撤掉 raw 兜底 → 报红 `content blocks = 1, want 3`，精确复现原始症状。

### 3.4 解析降级把「无法解析的 content」变成空会话发上游 【P1】

`parse_openai.go:312-325` 的 switch 只覆盖 `string`/`[]any`/`nil`，`content` 为 number/object/bool 时**解析成功**、消息变空，随后被 `validate_and_fix.go` 的 `removeEmptyMessages` 整条删除，请求带空会话发给上游并返回 200：

```
content_is_number -> parsed OK: msgs=1 blocks=0 | after ValidateAndFix msgs=0 => ALL MESSAGES DELETED
```

把客户端 JSON 缺陷转成「模型对空输入作答」的 200，故障归因完全错位（计费、缓存、对话历史全被污染）。子代理跑首轮复现时自己的测试就在 `ValidateAndFixRequest` 之后 index out of range 崩溃——请求已无消息可发。

**方案**：`content` 出现非 string/array/null 类型时 `ParseOpenAI` 直接返回 `KindClientBug`，不要走到 fix 层；`removeEmptyMessages` 需区分「解析导致为空」与「客户端本就为空」。

### 3.5 Extensions 数值精度 【P2 —— 已修】

`extensions_restore.go:88-91` 把值 `json.Unmarshal` 到 `any`，JSON 数字一律落 `float64`：`9007199254740993` → `9007199254740992`，**4 个协议全中**。

**覆盖缺口（重要）**：`request_document_protocol_test.go` 四个用例**正是**用 `9007199254740993` 测的，但断言只检查 `json.Valid` 和 `len(Extensions) > 0`，**从不校验数值**——测试给出了「已覆盖大整数」的假象。

**已修**（顺序刻意：先修夹具，再修代码）：
1. 先把 `request_document_protocol_test.go` 的断言从「`json.Valid` + `len(Extensions) > 0`」收紧为**校验数值**。收紧后立即在 4 个协议上全部报红，精确给出 `9007199254740993 → 9007199254740992`。**这一步证明了那个测试一直在给假覆盖**——它的名字叫「PreservesProtocolParserOutput」，用的输入就是 9007199254740993，但从不看值。
2. 再改 `restoreExtensions`：`preservedRawValue` 直接返回 `json.RawMessage`，不经 `float64` 中转（与 `serialize_ollama.go` 早已在用的做法一致）。

值得注意的是：codec 路径（`request_document_codec.go`）**本来就是无损的**，损失 100% 引入自 `restoreExtensions` 里那句图方便的 `json.Unmarshal(&any)`。

**变异验证**：退回 `float64` 中转 → 收紧后的测试报红。

### 3.6 异常上报被 dedup 折叠 【P2 —— 已修】

`anomaly_reporter.go:203-205` 的注释称「key 含 RequestID，正常流量下同 key 天然不重复」，但**四个 parser 全部硬编码 `"unknown"` 作 requestID**（`parse_openai.go:108` 等），该前提在唯一实际调用面上不成立：

```
5 separate parses -> 1 anomaly event delivered
```

一个 100% 客户端都在发的字段与一个 0.1% 客户端偶发的字段，在日志上不可区分。**已修**：采用「短 TTL」而非改 parser 签名——parser 只拿到 body 字节，要透传真实 requestID 得改 4 个 parser 的签名与全部调用方，代价与收益不匹配。新增 `anomalyDedupTTLNoRequestID = 1min`，对无身份事件单独生效；`hasRequestIdentity` 把 `""` / 空白 / 字面量 `"unknown"` 都判为无身份。同时把那条**前提不成立的注释**改成了事实描述。

抑制本身**没有被削弱**：解析期异常天然会重复（字段畸形对所有客户端都畸形），抑制是为了防热循环刷爆日志。测试刻意守的是**窗口长度**的差异而不是「有没有抑制」——`RequestlessEventsUseShorterWindow` 同时断言短窗口已过期后能再上报、而长窗口仍抑制。

**变异验证**：撤掉短 TTL 分支 → 报红；把两个 TTL 设成相等 → `TestAnomalyDedupNoRequestIDWindowIsShorter` 报红。

## 4. 需澄清的需求边界

objective 要求「将核心数据结构 ir 定义清晰，包括……路由数据、流程跟踪、调度瀑布……供应商、凭据」。

**实测：`internal/ir` 里没有 tenant、没有 credential、没有调度瀑布、没有轮次索引。** 调度瀑布在 `domains/dispatch/waterfall.go`（63 处命中），凭据在 executor（308 处）。`internal/ir` 纯粹是**协议表示层**。

这本身是合理分层（把协议转换与网关内路由可观测性混在一个结构里反而是灾难），但：

1. objective 把两者混在一张清单里；
2. **没有一份文档说明两者的边界**；
3. 因此「IR 定义清晰」这个验收项**无法判定**——不知道该以哪边为准。

**方案**：补一份边界文档，说明 `internal/ir` = 协议表示（跨供应商不变的部分），`domains/dispatch` + executor = 路由/瀑布/凭据（网关内部分），以及两者在什么点上交接。

## 5. 被 ADR 明确阻塞的需求（非缺陷）

objective 要求「能够对多个会话自动进行聚合分析，整理根据项目、任务的合并整合观测」。

**实测**：`InjectGatewayMetadata` / `ProjectRequestMetadata` 在生产**零调用**，`ir.Metadata.Project/Tags/TurnTotal` 只由前者写入，`internal/requestarchive` 没有任何生产导入方。整个 `internal/requestfact` 子系统（canonical request fact / archive）**完全构建、完全测试、零生产接线**。

**但这不是死接线**——`docs/adr/ADR-0003` 明确决策：

> 「本 Track 不在协议 handler 中做半成品生产接线……当前状态明确标记为『契约就绪 / 生产待接线』，避免伪造完整事实或只覆盖单协议。」

理由是：缺统一的 terminal fact builder，在没有终态 builder 前接线会造成协议不对称、重复构建或半成品事实。ADR 还列出了恢复接线所需的前置件：统一 terminal builder、至少一个真实 handler 端到端 fixture、V2 hash projection、V1/V2 golden corpus、迁移/回滚说明。

**结论**：这条需求**被 ADR-0003 明确阻塞**，不是缺陷，是一条待办依赖链。**验收「按项目/任务聚合观测」时应按「前置件未完成」记录，不能判 PASS，也不能记为 bug。**

> 我差点报了个假警。只 grep 到「零调用」就写成「死接线」，是错的——**判定能力缺失前，先问「有没有文档记录这是有意的」。**

## 7. 已核对、确认无问题的部分

**跨请求串话**（本项目已知缺陷模式，重点查过）：`internal/ir` 全部 parser/serializer 都是对 chunk 的纯函数；包级可变状态仅 `anomaly_reporter.go` 的 reporter/dedup（`reporterMu` 保护 + requestID 入 key，有 TTL + 时间闸 + 65536 硬上界）。流式 lane 状态是函数局部变量，非结构体字段。

**协议私有字段无泄漏**：`SourceProtocol` 守卫三处齐备，Gemini 的 `RECITATION` 等原生 stop_reason 不会泄给 Anthropic 客户端。

**数值边界无 panic/溢出**：负数、int64 上限、超 int64、float 混入 `max_tokens`、极端 token id、200KB base64 全部安全；`max_tokens` float/溢出由 `encoding/json` 正确拒绝为 400。

**文档编解码无损**：`ImageSource.Data` / `DocumentSource.Data` / `PDFSource.Data` 全是 base64 `string`（**无 `[]byte` 字段**），IR 内不存在二进制被当 UTF-8 处理的路径；1.2MB base64 图片+PDF 往返 byte-idempotent；畸形 `RawContent` 返回错误而非静默丢弃；`ContentBlock` 12 个字段在 wire 上 1:1 全覆盖。

**顶层未知字段闭环**：4 个 parser 均走 `Extensions` + `ReportParseUnknownField`，实测保留且上报。

**`paramreg` 注册表质量高**：覆盖 15 个方言、约 90 字段，每条带 `Note` 说明厂商分歧（`frequency_penalty` 在 DeepSeek 已废弃、MiniMax `thinking` 2026-09 起拒收 `enabled`），来源标注到具体 openapi spec 版本。决策优先级（rejected > unknown > IRHandled > Portable > Translatable > DialectOnly）自洽且 fail-open 倾向明确。

**`request_capability.go` 与 `extensions_restore` 不重复**：前者只做媒体模态嗅探供路由，后者做参数还原，职责正交。

**Ollama 流式终止处理正确**：`eof_without_done` 会发 error 帧 + `[DONE]` 并标 `Interrupted=true`，不会把截断当成功上报；`scanner.Err()` 路径正确区分 client cancel 与网络错误。

**Anthropic→OpenAI tool args 完整性有双保险**：畸形 JSON 被阻断并发 `malformed_tool_args` 错误帧，不会当完整 JSON 下发。

**被测试固化、建议保留的取舍**（勿当 bug 改）：
- 单 Anthropic 独占字段 + `messages[]` 判为 openai-chat（9 个用例钉桩，曾修 apiclaude 路由错）
- 超长 base64 入口不设限（分工给上游/配额层）
- role 不做白名单（网关不发明语义，让上游 400 归因客户端）
- 入口层对 `max_tokens`/temperature/n/top_p 零校验（无 panic 无溢出）
- `Apply` 对 `KindIRHandled` 判 `ActionRestore` 而非 `ActionSkip`（Extensions 里出现某字段恰恰说明某 parser 没消费它，`Skip` 会静默丢弃）
- 空切片/空 map 被 `omitempty` 合并（IR 归一化既定取舍）

**建议下一轮不要重复审计**：`semantic_analyzer.go`（纯启发式，只用于 anomaly 上报不改内容）、`sanitize_tool_messages.go`、`p3_improvements.go`（纯注释文件）、`source_reasoning_context.go`/`reasoning_dialect.go`（逻辑自洽且陷阱已自注记）、`StreamChunk.SerializeAnthropic` 与 `ParseGeminiStreamChunk`（均**零生产调用方**，接线前需连同其 golden test 一起改）。
