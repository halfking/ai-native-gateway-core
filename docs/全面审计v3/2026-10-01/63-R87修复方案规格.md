## 1. 建议 2【P2】熔断失败计数的跨冷却期升级窗口

> **状态：已于 R87-e 实施完成（64 号报告），本节保留为规格原文。**

### 1.1 缺陷（已实读确认，非转述）

`domains/credential/breaker.go:438-448`：

```go
lastIsTransient := transientFamily[b.lastErrorKind]
nowIsTransient := transientFamily[kind]
if b.lastErrorKind != "" && b.lastErrorKind != kind && !(lastIsTransient && nowIsTransient) {
    b.consecutive.Store(0)
    // R34 (2026-09-17 audit): reset the cooling cycle on any error-family change...
    b.coolingCycle = 0
}
```

而 `:456-466`：

```go
threshold := failureConfirmationThreshold(policy)
if consecutive < threshold {
    slog.Warn("circuit failure pending confirmation", ...)
    return          // ← 直接返回，不升级
}
```

**关键事实**（`:131` + `:378-383`）：

| ErrorKind | 策略 | 在 `transientFamily` 里？ |
|---|---|---|
| `KindTransient` / `KindTimeout` / `KindNetwork` / `KindStreamTimeout` | 各自策略 | **是** |
| `KindUpstreamDown` | `RecoveryExponential`，Initial 30s / Max 30min | **否** |

⇒ **Timeout ↔ UpstreamDown 交替时，每次都满足「族变化且非同族瞬时」⇒ `consecutive` 归零 ⇒ 永远够不到 `threshold` ⇒ 熔断永远不跳闸。**

这与 `:375-377` 注释里写的初衷**正好相反**：

> 「NVIDIA NIM 等不稳定凭据可能返回多种瞬时错误…如果每次错误类型切换就重置计数，会导致**永远达不到降级阈值**。」

**⇒ 2026-07-09 那次修复只覆盖了 4 个瞬时族的内部交替，没覆盖「瞬时族 ↔ UpstreamDown」这条最常见的交替路径。**

### 1.2 参照做法（62 号已核实）

- **OmniRoute** `accountFallback.ts:640`：按**时间窗**判「是否同一次事件」——`now - lastFailureAt <= resetAfterMs + lastCooldownMs`，而不是按错误类型。
- **cc-switch**：错误率双触发（`error_rate_threshold=0.6` + `min_requests=10`）——**本轮不采纳**（引入计数窗口是更大的改动面）。

### 1.3 修法（推荐 variant A：只保 `consecutive`，仍重置 `coolingCycle`）

**【实施时发现规格有误，已订正】** 本规格原稿写 `policy.ResetAfter` ——
**`CoolingPolicy` 结构体里没有这个字段**（只有 `InitialCooling` / `MaxCooling` /
`RecoveryType` / `ShrinkFactor`）。实际实现改用 `max(InitialCooling, 剩余冷却时间)`
作窗口，见 64 号报告。**这条错误是在动手前读结构体时抓到的，不是编译期才发现。**

```go
// 同一事件的判定改用时间窗，而非仅靠错误族名（OmniRoute accountFallback.ts:640 同型）。
// 背景：transientFamily 只覆盖 4 种，而 KindUpstreamDown 不在其中
// （它走 RecoveryExponential，Initial 30s / Max 30min）——
// Timeout↔UpstreamDown 交替时每次都判为「族变化」，consecutive 被清零，
// 永远够不到 threshold，熔断永不跳闸。这正是 2026-07-09 那次修复
// 想解决的问题，但那次只覆盖了瞬时族内部交替。
func sameIncident(prev, now time.Time, policy CoolingPolicy, b *Breaker) bool {
    if prev.IsZero() {
        return false
    }
    window := policy.ResetAfter
    if d := time.Until(b.coolingExpires); d > window {
        window = d
    }
    return now.Sub(prev) <= window
}
```

调用点改为：

```go
if b.lastErrorKind != "" && b.lastErrorKind != kind && !(lastIsTransient && nowIsTransient) {
    if !sameIncident(b.lastFailureAt, now, policy, b) {
        b.consecutive.Store(0)   // 隔得够久 ⇒ 确属新的一轮事件
    }
    b.coolingCycle = 0          // R34 意图保留：族变化不继承陈旧升级档
}
```

**为什么选 variant A 而不是「同事件内 consecutive 与 coolingCycle 都保留」**：

- variant A 修掉了「永远够不到阈值」这个**主缺陷**；
- 保留了 R34（2026-09-17）记录的意图——族变化**不**继承陈旧的 `coolingCycle`，避免「下次升级直接从 2³× 起步」；
- **代价（必须如实登记）**：交替族下 `coolingCycle` 每次归零 ⇒ 冷却最多停在第 1 档（15s/30s），不会指数爬升。**这比「永不跳闸」好得多，但不是完美解。**

> **这是一个明确的部分取舍，不是无争议修复。** 若产品更看重「交替族也要指数退避」，则选 variant B（同一事件内两者都保留）——但那会**部分推翻 R34 的记录决策**，按本项目纪律（`conventions.md` §5「不擅自推翻有记录的设计决定」）**须先取得产品/owner 认可**。**主代理推荐 variant A。**

## 2. 建议 3【P2】修复动作加 `preconditionsHash`（并发护栏）

### 2.1 缺陷

`bg/credential_recovery.go:748-756` 的 `health_status_reset` 是**无条件 UPDATE** ⇒ 运维「看着 A 的状态、清掉 B」在并发下可能发生（读-改-写之间状态已被别人改掉）。

### 2.2 修法

参照 OmniRoute `health-autopilot/actions/route.ts:24`。**不加新表、不加新迁移**：

1. 管理端动作接口接受可选 `preconditions`（一个 `map[string]any`，键为列名）；
2. 执行前用**同一个 UPDATE 的 WHERE** 带这些条件，并在影响行数为 0 时返回 `409 Conflict` + 当前实际值；
3. 前端在发起动作前带上最近一次读到的快照值。

改动面：`admin/` 的对应 handler + `bg/credential_recovery.go` 的 SQL + 前端一处调用。**无 schema 变更 ⇒ 无迁移编号消耗。**

### 2.3 测试与变异

- T6：preconditions 不匹配 ⇒ 409 且**状态未变**；
- T7：preconditions 匹配 ⇒ 正常执行；
- T8：并发两个不同 preconditions 的动作 ⇒ 只有一个成功（`-race`）。
- M-d：把 WHERE 里的 preconditions 条件去掉 ⇒ **T6 必须红**。
