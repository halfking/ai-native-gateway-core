## §二 方法：结构化选择器，而不是行号

守卫要比较的是「item 型 switch 的 case 标签集合」，而这三个文件里**同时存在 item 型与 content-block 型
两种 switch**。所以我不用行号（编辑一次就失效），也不用「包含某个词就算」
（会选错 switch），而用**结构签名**：

> 一个 item 型 switch = 它的 case 标签里**同时**有 `reasoning` **且**有
> `function_call` 或 `custom_tool_call`。

三个文件里被它选中的 switch 各为：合规 lane **2** 处、restore **1** 处、sanitize **1** 处 ——
与代码结构一致。**并且守卫把「选中了几个」本身写成断言**：

```go
if len(compliance) != 2 { t.Fatalf("输出合规 lane 应有 2 处 item 型 switch…若代码真的改了结构，
    请更新本守卫的选择器；不要把断言放宽成「0 也算过」。") }
```

⇒ **选择器失效会让守卫立刻报错，而不是静默地让后面所有比较变成「空集相等」**。

## §三 守卫的三条断言（各自对应一种漂移形态）

| # | 断言 | 拦住的失效 | 后果 |
|---|---|---|---|
| 1 | 合规 lane **非流 ≡ 流式**（集合相等） | 同一载体在两条 lane 走不同检测面 | 195 号那类失效**只在其中一条 lane** 复现 |
| 2 | 合规 lane ≡ 出向 restore（集合相等） | 检测面认了、还原面没认 | 占位符在某载体里**原样回客户端**，而合规侧看到的是占位符文本不是敏感值 ⇒ 不拦 |
| 3 | **restore ⊆ sanitize**（单向包含，非等值） | 还原面处理了、脱敏面没处理 | 敏感值**原文直接发给供应商** |

**第 3 条为什么是单向包含而不是等值** —— 这条是我自己写错过一次（§六）：

`input_protocols.go:290` 是一个 **item + content-block 合并**的 switch，
除 17 个 item 载体外还含 `text` / `input_text` 两个 content-block 型别，
以及两个**请求侧独有**载体（`function_call_output` / `custom_tool_call_output` ——
客户端把工具结果放在**请求**的 input 数组里回传，响应里不可能出现）。
⇒ 要求等值**是在问错问题，会在正确代码上判红**。

## §九 playbook

### §198-A **把「集合关系」写对，比把「集合内容」写对更难**

本轮守卫的第一版对三条关系**一律用等值**，结果在**正确代码**上判红，
而我第一反应是「守卫发现了新漂移」。
⇒ 等值是最容易写、也最容易错的默认。写集合断言前先问一句：
**这两个集合在语义上是「必须相同」还是「必须覆盖」？**
- 检测面 vs 还原面：**必须相同**（少一个就是漏判）。
- 请求侧 vs 响应侧：**必须覆盖**（请求侧天然多出请求独有载体与 content-block）。
⇒ 而「多出来的那几项是否有原则性理由」是**另一问**：
`function_call_output` 出现在请求而非响应，是协议决定的，不是漂移。
**把「多出来的」和「应该多出来的」分开，是这一类守卫能不能落地的分水岭。**

### §198-B **枚举类结论必须先收全，再比较 —— 尤其不要下「方向反转」这种结论**

我读到文件第 267 行就写下了「合规 lane 成了超集、漂移方向反了」，
补读另外两处 switch 后**完全作废**（两处本来就完全相同）。
⇒ 方向性结论（「谁比谁多」「谁在追赶谁」）的**错误代价远高于存在性结论**：
它会让人以为漂移已经止住而停止治理。
⇒ **How to apply**：做 N 份拷贝的一致性普查时，
**先把所有相关 switch 全部收齐并打印计数，再动手比较**；
把「收齐」这一步变成可执行动作（如本轮直接让守卫自己 `t.Logf` 打印普查表），
而不是靠人肉翻页。
