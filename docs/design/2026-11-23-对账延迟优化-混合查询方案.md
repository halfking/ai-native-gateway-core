## 一、背景与目标

### 1.1 当前问题

**对账数据延迟24小时**：
- 数据源：只查询`report_snapshots`表（每日凌晨Worker生成）
- 用户痛点：对账人看不到今日实时数据，必须等到次日
- 业务影响：当日费用监控、异常流量发现均有24小时延迟

### 1.2 优化目标

**实现0延迟实时对账**：
- 历史日期：查`report_snapshots`（快速，~20ms）
- 今日数据：查`usage_facts`（实时，~2-3秒）
- 前端透明：无需修改调用方式
- 数据准确：两个数据源口径完全一致

## 三、混合查询方案设计

### 3.1 整体架构

```
用户请求：start=2026-11-17 & end=2026-11-23
                    ↓
┌───────────────────────────────────────────────────┐
│  后端识别today = SystemDayStart(Now())            │
│  = 2026-11-23 00:00:00 CST                       │
└───────────────────────────────────────────────────┘
                    ↓
            end >= today?
                 /    \
               是       否
              /          \
             ↓            ↓
    ┌────────────┐  ┌────────────┐
    │ 拆分查询    │  │ 只查历史    │
    └────────────┘  └────────────┘
         ↓
┌────────────────────────────────────────┐
│ 历史区间：[start, today-1]              │
│ 数据源：report_snapshots               │
│ 查询时间：~20ms                         │
└────────────────────────────────────────┘
         ↓
┌────────────────────────────────────────┐
│ 今日区间：[today, today]                │
│ 数据源：usage_facts                    │
│ 查询时间：~2-3秒                        │
│ WHERE DATE(occurred_at AT TIME ZONE    │
│       'Asia/Shanghai') = today         │
└────────────────────────────────────────┘
         ↓
┌────────────────────────────────────────┐
│ 合并结果：                              │
│ 1. 历史快照行（report_snapshots）       │
│ 2. 今日聚合行（usage_facts）           │
│ 3. 重新计算总计（Σ历史 + 今日）        │
└────────────────────────────────────────┘
         ↓
    返回 GrainReport
```

### 3.2 关键技术点

#### 3.2.1 today识别与区间拆分

```go
// BuildGrainReport 修改点1：识别today
today := settings.SystemDayStart(time.Now())
yesterday := today.AddDate(0, 0, -1)

var historyEnd time.Time
var includeToday bool

if end0.Before(today) {
    // 情况1：end < today（如查询11-17到11-22）
    // 只查历史快照，原逻辑
    historyEnd = end0
    includeToday = false
} else if start.After(yesterday) {
    // 情况2：start > yesterday（如只查今日11-23）
    // 只查usage_facts，无历史
    historyEnd = time.Time{} // 空值，跳过历史查询
    includeToday = true
} else {
    // 情况3：start <= yesterday && end >= today（如查询11-17到11-23）
    // 查历史 + 查今日
    historyEnd = yesterday
    includeToday = true
}
```

#### 3.2.2 今日数据聚合SQL

**核心挑战**：usage_facts的聚合SQL必须与report_snapshots的GROUPING SETS完全一致。

**解法**：复用grainreport.go的聚合逻辑，只改数据源：

```sql
-- 新增函数：buildTodayAggregationSQL(view, filter) → string
-- 返回查询usage_facts的SQL，格式与report_snapshots查询一致

WITH f AS (
    -- 数据源改为usage_facts，增加occurred_at过滤
    SELECT 
        DATE(occurred_at AT TIME ZONE 'Asia/Shanghai') AS report_date,
        raw_model_name,
        provider_id,
        credential_id,
        api_key_id,
        tenant_id,
        COALESCE(person_hash, '') AS person,
        1 AS request_count,  -- 每行代表1个请求
        CASE WHEN status = 'success' THEN 1 ELSE 0 END AS success_count,
        prompt_tokens AS input_tokens,
        completion_tokens AS output_tokens,
        cache_read_tokens,
        cache_write_tokens,
        CAST(cost_amount * 100 AS bigint) AS estimated_cost_cents,
        cost_currency AS currency,
        credits_charged,
        NULL::jsonb AS price_snapshot,  -- usage_facts无此字段
        
        -- error_kind_breakdown：按error_kind聚合
        CASE WHEN status != 'success' 
             THEN jsonb_build_object(COALESCE(error_kind, 'unknown'), 1)
             ELSE '{}'::jsonb
        END AS error_kind_breakdown,
        
        latency_ms AS latency_p50_ms,  -- 单行无分位数，取原值
        latency_ms AS latency_p95_ms
    FROM usage_facts
    WHERE DATE(occurred_at AT TIME ZONE 'Asia/Shanghai') = $1  -- today
      -- [维度过滤条件，与report_snapshots相同]
),
-- [后续GROUPING SETS与report_snapshots完全相同]
```

**重要差异**：
1. `request_count`：快照里是聚合后的数字，usage_facts每行=1
2. `person`：快照里是person字符串，usage_facts是person_hash
3. `price_snapshot`：快照有，usage_facts无（填NULL）
4. `error_kind_breakdown`：快照是聚合后的jsonb，usage_facts每行构造
5. `latency_p50/p95`：快照是分位数，usage_facts单行只能取原值

#### 3.2.3 结果合并逻辑

```go
// BuildGrainReport 修改点2：合并历史与今日
var allRows []grainScanRow

// 1. 查询历史快照
if !historyEnd.IsZero() {
    historyRows, err := queryGrainRows(ctx, q, day0, historyEnd, grainScope, filter)
    if err != nil {
        return nil, err
    }
    allRows = append(allRows, historyRows...)
}

// 2. 查询今日usage_facts
if includeToday {
    todayRows, err := queryTodayUsageFacts(ctx, q, today, view, filter)
    if err != nil {
        // 今日查询失败：记录日志，降级为只返回历史数据
        slog.Warn("today usage_facts query failed, falling back to history only",
            "error", err)
    } else {
        allRows = append(allRows, todayRows...)
    }
}

// 3. 统一聚合（sink函数不变，只是输入行来自两个数据源）
for _, row := range allRows {
    kind := classify(row)
    sink(kind, row)
}

// 4. 重新计算总计（已在sink中累加）
```

### 3.3 核心挑战与解法

#### 挑战1：聚合口径一致性

**问题**：usage_facts与report_snapshots的聚合逻辑必须完全一致，否则"历史+今日"的总计会与"纯快照"的总计不等。

**解法**：
1. **复用GROUPING SETS结构**：两个数据源的GROUP BY子句完全相同
2. **单元测试覆盖**：生成同一天的快照与实时聚合，逐字段对比
3. **E2E验证**：211生产环境对比"历史+今日"vs"纯快照（次日）"

#### 挑战2：性能

**问题**：usage_facts全表扫描慢，今日可能有几万行。

**解法**：
1. **索引优化**：已有`idx_usage_facts_occurred_at`索引
2. **结果缓存**：今日结果缓存5分钟（前端轮询间隔）
3. **超时降级**：今日查询超时5秒 → 只返回历史数据 + 标记"今日加载中"
4. **只查一天**：today单日，不影响历史查询

#### 挑战3：person字段差异

**问题**：
- `report_snapshots.person`：明文person字符串（如"user@example.com"）
- `usage_facts.person_hash`：SHA256哈希

**解法**：
- 对账页面的person维度**不支持实时查询**（今日数据该维度为空）
- 或：在usage_facts聚合时用`person_hash`作为key，前端显示"用户哈希"

**推荐**：先不支持person维度的今日实时，等后续评估需求后再优化。

#### 挑战4：分位数计算

**问题**：
- `report_snapshots`：已计算好的`latency_p50_ms`/`latency_p95_ms`
- `usage_facts`：每行只有`latency_ms`单值

**解法**：
- 今日数据的分位数**在SQL中计算**：`percentile_cont(0.5) WITHIN GROUP (ORDER BY latency_ms)`
- 或：简化为平均值/最大值，前端标注"今日数据为近似值"

## 五、风险与缓解

### 5.1 风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 聚合口径不一致 | 中 | 高 | 单元测试覆盖所有维度 + E2E对比 |
| 今日查询慢（>5秒） | 中 | 中 | 结果缓存 + 超时降级 |
| person字段差异 | 高 | 低 | 今日数据不支持person维度（文档说明） |
| 分位数不准确 | 高 | 低 | 前端标注"今日为近似值" |
| 内存占用 | 低 | 低 | 只查today一天（vs原可查366天） |

### 5.2 回滚方案

**条件**：生产环境发现严重问题（聚合错误/性能劣化）

**步骤**：
1. 修改`BuildGrainReport`：强制`includeToday = false`（一行代码）
2. 重新部署（约5分钟）
3. 验证：查询结果与原逻辑一致

**数据安全**：只改读面，不写数据，零数据丢失风险

## 六、后续优化方向

### 6.1 person维度支持

**方案A**：usage_facts增加`person`明文列（需迁移）  
**方案B**：前端显示`person_hash`（用户体验差）  
**方案C**：今日数据不支持person维度（当前方案）

**推荐**：先走方案C，等用户反馈再决定是否实施A/B

### 6.2 分位数精确计算

**方案A**：SQL中计算`percentile_cont`（增加查询耗时）  
**方案B**：Go中计算（需保留所有latency_ms，内存占用大）  
**方案C**：今日显示平均值（当前方案）

**推荐**：先走方案C，前端标注"今日为近似值"

### 6.3 多日实时查询

**当前**：只today一天查usage_facts，其余查快照  
**扩展**：最近N天（如3天）都查usage_facts，更实时但更慢

**推荐**：先只支持today，等用户反馈再扩展
