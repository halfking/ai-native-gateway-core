# 对账延迟优化方案评估 - 基于request_metrics统计中间表

**评估时间**：2026-11-24  
**评估人**：Mavis (MiniMax Code)  
**评估对象**：2026-11-23设计的"混合查询方案"（历史查快照+今日查usage_facts）  
**新方案**：统计专用数据表`request_metrics`（983迁移）

## 一、核心变化

### 1.1 旧架构（2026-11-23评估时）

```
对账页面查询流程：
  ↓
report_snapshots（快照表）
  ├─ 每日凌晨Worker聚合
  ├─ 数据源：usage_facts
  └─ 延迟：24小时

问题：今日数据不可见
解决方案：混合查询（历史查快照+今日查usage_facts）
```

### 1.2 新架构（2026-11-24）

```
统计查询流程：
  ↓
request_metrics（统计中间表）★ 新增
  ├─ 异步填充（延迟<5分钟）
  ├─ 数据源：usage_facts
  ├─ 完整维度支持
  └─ 多索引优化

优势：
1. 延迟从24小时 → <5分钟（准实时）
2. 单一数据源（无需混合查询）
3. 口径统一（所有统计页面共用）
```

## 三、关键发现

### 3.1 混合查询方案的核心问题（已被新方案解决）

#### 问题1：聚合口径一致性风险

**旧方案**：
```sql
-- 历史：查report_snapshots（已聚合）
SELECT SUM(request_count), SUM(estimated_cost_cents) ...

-- 今日：查usage_facts（需现场聚合）
SELECT COUNT(*), SUM(cost_amount * 100) ...
```

**风险**：
- usage_facts与report_snapshots的聚合逻辑必须完全一致
- person字段差异（明文vs哈希）
- 分位数计算差异（已聚合vs单值）
- **测试难度高**：需对比"历史+今日"vs"次日快照"

**新方案**：
```sql
-- 全时段：统一查request_metrics
SELECT SUM(cost_cents), COUNT(*) ...
FROM request_metrics
WHERE occurred_at >= $1 AND occurred_at < $2
```

**优势**：
- 单一数据源，零口径风险
- 字段一致（cost_cents/person/等）
- 无需混合查询

#### 问题2：性能瓶颈

**旧方案**：
- 历史查询：~20ms（快照，有索引）
- **今日查询：~2-3秒**（usage_facts全表扫描，今日几万行）
- 总延迟：~2-3秒

**新方案**：
- 全时段查询：**<100ms**（request_metrics，8个索引）
- 分区表（按occurred_at范围分区）
- 窄表设计（只保留维度+计量字段）

#### 问题3：维护成本

**旧方案**：
- **两套聚合SQL**：report_snapshots的GROUPING SETS + usage_facts的现场聚合
- **两套测试**：快照测试 + 实时聚合测试
- **新维度**：需同时修改两处

**新方案**：
- **一套聚合SQL**：只查request_metrics
- **一套测试**：统一的metrics.Query*测试
- **新维度**：只改request_metrics填充逻辑

### 3.2 request_metrics方案的核心优势

#### 优势1：准实时（<5分钟）

```
usage_facts写入
  ↓ <5分钟
request_metrics异步填充
  ↓ <100ms
对账页面查询
```

**对比**：
- 旧快照：24小时延迟
- 混合查询：今日实时，但复杂度高
- **request_metrics：<5分钟，复杂度低**

#### 优势2：统一数据源（所有统计页面）

**迁移目标**（见commit b8f2935f4）：
- 看板页面
- 会话统计
- 供应商对账
- 用量趋势
- 节点负载统计（新）
- 团队预算（新）

**收益**：
- **口径统一**：所有统计页面查同一张表
- **数据一致**：消除D2类去重风险
- **易维护**：改一处，所有页面同步

#### 优势3：完整维度支持

**新增维度**（旧方案不支持）：
- 节点：`gateway_node_id`/`gateway_instance`/`endpoint_node`
- 付款者：`payer_id`/`payer_type`
- 多模态：`modality`/`attachment_count`/`image_tokens`
- 记账日期：`billing_date`（跨日请求的账单归属）

## 四、结论与建议

### 4.1 核心结论

**混合查询方案（2026-11-23设计）已不再推荐实施**：

| 原因 | 说明 |
|------|------|
| ✅ 新方案已落地 | request_metrics已实施（983迁移） |
| ✅ 性能更优 | <100ms vs 2-3秒 |
| ✅ 准确性更高 | 单源零口径风险 vs 双源合并风险 |
| ✅ 延迟可接受 | <5分钟 vs 24小时（提升99.65%） |
| ✅ 维护成本低 | 一套逻辑 vs 两套逻辑 |
| ⚠️ 实施成本已付 | 新方案已实施，混合方案变成重复投入 |

### 4.2 推荐方案

#### 方案A：迁移到request_metrics（★ 推荐）

**实施步骤**：

```
阶段1：双写验证（2周）
  ├─ request_metrics异步填充已运行
  ├─ 验证数据准确性（vs report_snapshots）
  └─ 验证填充延迟（P95 < 5分钟）

阶段2：切流对账页面（1周）
  ├─ 修改 domains/reportrollup/grainreport.go
  │   └─ 数据源：report_snapshots → request_metrics
  ├─ 适配器层：MetricsFilter → GrainFilter
  ├─ 灰度10% → 50% → 100%
  └─ 监控：查询延迟、准确性、错误率

阶段3：清理旧逻辑（稳定后）
  ├─ 移除混合查询代码（如已实施）
  ├─ 移除report_snapshots依赖（保留表，不删数据）
  └─ 文档更新
```

**工作量**：
- 阶段1：0小时（已运行）
- 阶段2：3-5小时（切流+适配器+测试）
- 阶段3：1-2小时（清理）
- **总计**：4-7小时

**风险**：
- 低：新方案已实施，只需切流
- 缓解：灰度发布，监控数据一致性

#### 方案B：保持现状（不推荐）

**理由**：
- report_snapshots仍可用，24小时延迟
- 对账人已习惯"次日看前日数据"
- 零实施成本

**问题**：
- 错过准实时优势（<5分钟 vs 24小时）
- 未来新维度需改两处（report_snapshots + request_metrics）
- 数据不一致风险（两个统计来源）

#### 方案C：同时实施混合查询+request_metrics切流（不推荐）

**理由**：混合查询变成过渡方案，实施后即废弃

**问题**：
- 重复投入（5-9小时混合查询 + 4-7小时切流）
- 维护两套逻辑（短期）
- 测试成本高（两个方案都要测）

## 五、迁移到request_metrics的技术要点

### 5.1 适配器设计

```go
// 新增 domains/reportrollup/metrics_adapter.go

// QueryFromMetrics 从 request_metrics 查询对账数据
// 适配器：将 GrainFilter 转换为 metrics.MetricsFilter
func QueryFromMetrics(ctx context.Context, q Querier, 
    start, end time.Time, view View, filter GrainFilter) (*GrainReport, error) {
    
    // 1. 转换过滤器
    mf := metrics.MetricsFilter{
        TenantID:      filter.TenantID,
        StartTime:     start,
        EndTime:       end,
        IncludeProbes: false, // 对账默认排除探测
        ProviderID:    filter.ProviderID,
        // ... 其他维度
    }
    
    // 2. 查询 request_metrics
    summary, err := metrics.QuerySummary(ctx, q, mf)
    if err != nil {
        return nil, err
    }
    
    daily, err := metrics.QueryDailySummary(ctx, q, mf)
    if err != nil {
        return nil, err
    }
    
    providers, err := metrics.QueryProviderSummary(ctx, q, mf)
    if err != nil {
        return nil, err
    }
    
    // 3. 转换为 GrainReport 格式
    return &GrainReport{
        Start:  start,
        End:    end,
        View:   view,
        Totals: convertTotals(summary),
        Days:   convertDays(daily),
        Providers: convertProviders(providers),
        // ... 其他维度
        Source: "request_metrics", // 标记数据源
    }, nil
}
```

### 5.2 灰度开关

```go
// admin/report_rollup.go

func (h *Handler) handleReportRollupSummary(w http.ResponseWriter, r *http.Request) {
    // ... 参数解析
    
    var rep *reportrollup.GrainReport
    var err error
    
    // 灰度开关：request_metrics vs report_snapshots
    useMetrics := h.settings.GetBool("report.use_request_metrics")
    rolloutPct := h.settings.GetInt("report.metrics_rollout_percent")
    
    if useMetrics && shouldRollout(r, rolloutPct) {
        // 新方案：查 request_metrics
        err = readNoJIT(r.Context(), h.db, func(q reportrollup.Querier) error {
            rep, err = reportrollup.QueryFromMetrics(ctx, q, start, end, view, filter)
            return err

        // 旧方案：查 report_snapshots

            rep, err = reportrollup.BuildGrainReport(ctx, q, start, end, view, filter, 
                h.dimensionNames(ctx), reportDailyDetail(r))
            return err
        })
    }
    
    // ... 返回结果
}
```

## 六、风险与缓解

### 6.1 风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| **填充延迟>5分钟** | 低 | 中 | 监控P95延迟，超时告警 |
| **数据不一致** | 低 | 高 | 双写验证期对比快照 |
| **查询性能劣化** | 低 | 中 | 灰度发布，监控P95延迟 |
| **新表缺维度** | 中 | 低 | 适配器处理，前端标注"暂不支持" |
| **回滚复杂** | 低 | 低 | 灰度开关，一行配置回滚 |

### 6.2 验收标准

#### 功能准确性
- [ ] request_metrics vs report_snapshots差异<0.1%

- [ ] 总计 = Σ各分组（逐维度可验证）

#### 性能
- [ ] P50延迟：<50ms
