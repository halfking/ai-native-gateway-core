## 本轮修正

1. **模型分布多了一列费用。** 效果图 A 节列是模型 / 请求 / Token / 占比，E 节写「不虚构费用列」。实现却渲染 `pies.models.cost_usd`，并标成 Top 8。该字段在供应商饼图上已经被证明经常是 0，模型列同样不能当窗口费用。已去掉费用列，改为 Top 6。占比在指标缺失时不再算出 `NaN%`。
2. **成本卡在用量没回来时回退到饼图。** `d8695f4a2` 只在 `usageRows.length > 0` 时按用量成本排序，否则仍按 `pie.cost_usd` 取前 8。用量请求失败或尚未返回时，页面会先铺 `$0` 的 `__other__`。效果图画的是一行 5 张。现改为只按用量 `total_cost_usd` 取前 5；没有用量行就空着，并显示错误。积分仍按代码或名称回查饼图。
3. **RPM/TPM 分母把今天还没到的小时算进去。** `today` / `7d` / `30d` 的终点是 `now`。自定义范围（昨天以外的「本月」「上月」以及任意含今天的区间）的终点是结束日次日 00:00 UTC。含今天时，分母多出剩余小时，速率被压低。`boardRangeElapsedMinutes` 把终点封到 `now`。已结束的历史窗口仍用完整跨度。第一分钟内分母最低按 1 分钟，避免除零。

## 晚间复审（同一天，本地库 `llm-gateway-pg`，会话时区 Asia/Shanghai）

上午把英雄卡和成本卡的差额写成「分钟表 cost 没写全」。把窗口对齐之后，这个说法不成立。

看板预设「今天」是 `[当天 UTC 00:00, now)`。用量接口只有 `days` 时，起点是 `now` 减去 N 天再截到 UTC 零点（`resolveUsageTimeRange`）。`days=1` 从昨天 UTC 00:00 算到现在，比看板多一整天。`2026-09-29 00:00 UTC` 到采样时刻，用量账本按供应商合计：suyun `$3.379678`（416 笔）、apigpt `$0.194393`。这就是当时成本卡上的数字。同一时刻 UTC「今天」的分钟表费用是 `$0.003286`（5177 笔），用量账本是 `$0.003289`（6092 笔）。费用差约 `$0.000003`。请求数仍少约 900，比旧日期的一半缺口小，因为进程内累加器还在往当前分钟加。有费用的供应商只有 apiclaude `$0.0032`、火山方舟和智码（四位小数后仍非零）。

近 7 个 UTC 日（看板 `days=7` 的起点）对得上的是请求日志和用量账本：都是约 `$151.81`。分钟表是 `$87.01`，请求数 551550，日志是 1097166。按日看，分钟表请求数大约是日志的一半，越旧越接近一半。rollup 每分钟用 `ts > 游标` 聚合，冲突时整桶替换。游标落在分钟中间时，后一次写入只留下这一分钟的后半段。日志和账本的 `cost_usd` 在同一窗口里是对齐的，不是两套价格。

这次改了两处，没有把两个数加在一起：

1. 成本卡、用量表、导出和抽屉改传看板同一对 UTC 日历日。看板汇总接口仍用 `days` 预设。用量 API 的 `days` 语义不动。
2. rollup 扫描下界收到该分钟起点，三条 SQL 的下界改成 `>=`。已经写坏的历史桶不会在这次提交里重算。8782 里正在跑的还是旧二进制，新分钟仍会被旧逻辑覆盖，直到换上这份代码。因此近 7 日英雄卡费用在换二进制并重算之前，仍会低于用量账本。
