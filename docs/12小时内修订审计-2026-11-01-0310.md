### 3.1 ✅ 逐单窗口的读时归因（`426393659`）—— **合理，且是根因级修复**

**原问题**（211 生产实测）：24 条待审单横跨 40 小时，旧读法把整批并成**一个**窗口 + **一个全局 `LIMIT 50`**，
按 `last_seen DESC` 取最近 50 条 ⇒ 预算被**最新**的事件吃光 ⇒ **早期审核单一条候选都没有**，
且「撞上限」被记成**整批**截断 ⇒ 归因档位一律降级成 `unknown` ⇒ **读时归因对真正需要它的历史空白单等于没生效**。

**处理方案**：`LATERAL + unnest` 一次往返、**每单一个窗口**、**逐单预算**（截断只影响那一条）。
`EgressRuleEventWindow.Index` 由调用方给出并**随窗口一起穿过过滤**（`usable` 切片丢窗口时 Index 不丢），
`windowIndexes/los/his` 三者同序 ⇒ **idx ⇔ lo ⇔ hi 对齐**。

**本轮复核结论**：
- 判据与旧读面**逐字一致**（`phase='egress'`、`last_seen` 落窗内、`tenant_id = ANY(...)`、窗内 `last_seen DESC, id DESC`）—— **不许顺手改口径**这条纪律被守住了 ✔；
- 租户门 fail-closed（空集合 ⇒ 返回空，不解释成「不限」）✔；
- 逐单截断标记粒度正确（`len(hits) >= perWindowLimit` ⇒ 保守地标「可能不完整」）✔；
- `r.CreatedAt.IsZero()` 的审核单既不进窗口也不进 `indexOf` ⇒ 前后一致 ✔；
- `policyRuleFromIssues` 取第一条带 `RuleID` 的 issue、`policyIssueDigest` 取第一条带 `Digest` 的 issue
  ⇒ **「无 Issue ⇒ 无 rule_id ⇒ 空审核单」这条链被确认**（本轮 §3.2 的修复正是补这条链的输入端）。

**判定：合理。**

### 3.3 ❌→✅ 批写：失败面比修复前宽 128 倍（本轮 **P1-3**）

**窗口内做对了什么**：`c6ad22f74` 把审计事件落库从「逐条事务」改成「每批一条事务」（`auditWriteBatchSize = 128`），
根因是 211 实测「3 小时丢 44250 条」——**逐条路径的排水速率跟不上 per-hit 生产速率**。
同时把队列 256 → 4096、给 queue-full 告警加了 30s 节流 + 累计计数。**方向完全正确**。

**漏掉的是什么**（本轮实测）：

```go

    if err := writer.RecordEvents(ctx, events, limit); err != nil {
        m.report("sanitize rule audit write failed")   // ← 静态串，无错误、无数量

```

⇒ **一次写失败 ⇒ 整批 ≤128 条审计事件一起消失**，而：
- **修复前**（逐条路径）一次失败只丢 **1** 条 ⇒ **批写把失败爆炸半径放大了 128 倍**；
- 失败**不计入** `m.dropped` ⇒ 管理面的 `Status().DroppedEvents` **只统计队列满**，**完全看不见写失败丢的那批**；
- 上报是**一条没有细节的静态串** ⇒ 操作者既不知道丢了多少、也不知道丢在哪；
- 上报**没有节流** ⇒ 与本轮刚治理的「queue-full 告警风暴」是**同一条告警面**，
  DB 抖动时两条路径**同时**触发（队列满 + 写失败）⇒ 风暴治理只覆盖了一半。

**本轮落地**：批写失败 ⇒ **退回逐条写**（只有真正写不进去的那几条会丢）+ 逐条失败**计入 `dropped`** +
上报带**错误内容**。`Instance.DroppedEvents` 的契约同步改写为「**丢了多少**」而不是「队列满丢了几条」。

### 3.5 ❌→✅ 补发工具的失败面（失败不计数 / 退出码恒 0 / 单一 10 分钟 ctx）（本轮 **P1-5**）

**漏掉的是什么**（本轮实测）：


⇒ 工具可以打印「`done: inserted=100`」而实际 **9999 条全失败** ⇒
**「执行结果是否与预期一致」这个问题，工具自己回答不了**。

叠加另两处：
- **单一 10 分钟 ctx** 同时覆盖候选查询与**全部** INSERT ⇒ `--limit 10000` 时插入阶段可能整体 deadline
  ⇒ 失败又被上面的「不计数」吞掉 ⇒ **静默零产出**；
- **逐条 autocommit** ⇒ 10000 条 = 10000 次往返 ⇒ 极易把预算耗尽。

**本轮落地**：失败**计数**（`failed=`）+ **非零退出码** + 查询/写入**独立预算** +
**分块事务**（每块 200 条独立提交，失败按块回滚计数）⇒ **一次失败只丢一块**。
另加**执行模式必须给 `--from`** 的护栏（`session_turns` 是月分区大表而过滤键是 `ts` ⇒ 分区裁剪不保证生效）。

### 3.6 ✅ 智能体识别轮的失败行兜底（`f6c7da2ef` / `5269313a2`）—— **合理**

本轮逐层复核了这条链：
`recordFailedRequestWithKey` → `ctx.EnsureCaptured()` → `ensureRequestBodyBuffered`（body 已填 ⇒ 早退，不重读）
→ **但仍执行** `ExtractSystemPromptFromBody` 填 `meta.SystemPrompt` → `refreshMeta()` → `fillAttemptMeta`
→ `shouldOverrideAgentName(meta.AgentName, meta.SystemPrompt)` → `DetectAgentFromSystemPrompt` ⇒ **兜底真的跑了** ✔。

★ 关键点：修复前调的是 `refreshMeta()`，而 `refreshMeta` **只消费** `meta.SystemPrompt`、**从不生产**它
⇒ 失败行的 `SystemPrompt` 恒空 ⇒ 兜底恒不触发 ⇒ 失败行只有弱名（`go-client`）。
⇒ 换成 `EnsureCaptured()` 是**对症**的（它才是生产 `SystemPrompt` 的那个入口）。

★ 顺带复核了 `readRequestBodyRestore`（本轮新增）：
`readRequestBody` 用 `io.LimitReader(body, limit+1)` 读，**自己不做限长判定**，判定在调用方。
`readRequestBodyRestore` 的恢复条件是 `err == nil && len(buf) <= limit`
⇒ 超限时 `len(buf) == limit+1` ⇒ **不恢复** ⇒ **不完整字节流不会被当成完整 body 重放** ✔
（注释里「与 `bufferRequestBody` 逐字一致」不准确——`bufferRequestBody` 是**无条件**恢复的，
但那是既有行为，本轮不动）。

### 3.7 ✅ 共识门死锁根修（`c82fa475c`）—— **合理**

**原问题**：`VerifiedConsecutiveRuns ≥ 2` 时 **verified 在生产上不可达**——

## 八、通用式（供 `LESSONS.md` 收编）

1. **「修了主路径、漏了旁路」是本窗口最贵的一类缺陷**——同一语义的两条分支，
   只转一条 ⇒ 审核面在**另一条**上仍然是空白单。判据：**同一 fail-closed 语义在仓内出现几次，
   就必须转几次**；形态表登记与代码转换要**逐条对齐**，缺一条就有半边空白。
2. **「批量优化」必须同时收窄失败面**——把 N 次写并成 1 次 ⇒ 成功路径吞吐上升 N 倍，
   失败路径的损失面也**同步放大 N 倍**。判据：**批写失败必须有逐条退路**，
   否则「为了修丢事件而加的批写」在失败路径上比原来更糟。
3. **计数器要覆盖它声称覆盖的那一类**——`DroppedEvents` 叫「丢了几条」却只统计队列满，
   ⇒ 写失败丢的那批在管理面上完全不可见。判据：**计数器名字承诺的范围 = 实现统计的范围**。
4. **「暂存区」不能当历史真相源**——`session_turns_hot` 会被 `promote` 抽干进 `session_turns`；
   只扫 hot 的「历史补发工具」会漏掉全部历史。判据：**工具的源表要问一句「它会被搬走吗」**。
5. **工具的收尾行必须能回答「是否与预期一致」**——失败不计数 + 退出码恒 0
   ⇒ 工具可以打印 `done: inserted=100` 而实际全失败。判据：**收尾行要有 failed 计数，失败要有非零退出码**。
6. **文档承诺的源必须与 SQL 的源一致**——本轮实测文档写「hot + parent」而 SQL 只扫 hot；
   文档的「and its parent」四个字掩盖了一个 P1。判据：**文档里出现「and X」时，去 SQL 里数一遍**。
