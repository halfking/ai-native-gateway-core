# 请求参数全量兼容 — 审计基线与研究结论

**日期**: 2026-08-11
**范围**: 网关请求方向参数兼容能力 + 模型思考能力识别
**结论**: 🔴 存在 5 处 P0 级参数丢失；思考能力识别能力为 0（完全缺失）

---

## 0. 一句话结论

IR 架构本身是正确的（三段式 parse → IR → serialize，未知字段进 `Extensions`），
但**还原侧被三道门禁锁死**，导致本网关最主要的使用场景（Claude Code → 国产模型）
的厂商私有参数 100% 丢失。同时**没有任何模型级思考能力元数据**，`thinking` /
`reasoning_effort` 是无条件下发的，对不支持的模型必然 400 或被静默忽略。

## 1. 审计基线（已逐条读码核实，非推断）

### 1.1 P0-1：Extensions 跨协议还原被 SourceProtocol 门禁锁死

`internal/ir/serialize_openai.go:179`

```go
if req.SourceProtocol == "" || req.SourceProtocol == ProtocolOpenAIChat {
    for key, val := range req.Extensions { ... }
}
```

同样的门禁在 `serialize_anthropic.go:196`、`serialize_responses.go:166`。

**影响**：`SourceProtocol` 在跨协议路由时必然不等于目标协议。即
Claude Code（anthropic-messages）→ DeepSeek/GLM/Qwen（openai-chat）这条
**本网关最核心的链路**，`Extensions` 一个字段都不会还原。

客户端发的 `enable_thinking`、`thinking_budget`、`repetition_penalty`、
`chat_template_kwargs`、`extra_body` 内的一切，全部在此丢弃。

### 1.2 P0-2：serialize_gemini 完全没有 Extensions 还原

```
$ grep -n "Extensions" internal/ir/serialize_gemini.go
(无输出)
```

**影响**：任何出向 Gemini 的请求，无论来源协议，未知字段全丢。

### 1.3 P0-3：ir_converter 叠加第二道 catalog 门禁

`domains/transformation/ir_converter.go:476-485`

```go
if req == nil || (req.SourceProtocol != "" && req.SourceProtocol != targetProtocol) {
    return body                                    // 门禁 A（与 1.1 重复）
}
if ctx != nil && ctx.ClientCatalogCode != "" && ctx.UpstreamCatalogCode != "" &&
   ctx.ClientCatalogCode != ctx.UpstreamCatalogCode {
    return body                                    // 门禁 B
}
```

**影响**：即使修掉 1.1，门禁 B 仍会在「客户端 catalog ≠ 上游 catalog」时丢弃。
而网关的存在意义就是跨 catalog 转发，所以门禁 B 等价于"几乎永远不还原"。

> 门禁 B 的原始动机见 `docs/IR格式优化/06-Provider-Profile审计与收敛.md` 第 5 节：
> 担心把 A 厂商私有字段泄漏给 B 厂商上游。**动机是对的，手段是错的** —— 正确做法是
> 按字段分类（注册表），而不是整包丢弃。这是本方案的核心修正点。

### 1.4 P0-4：Gemini safetySettings / cachedContent 双向静默丢失

`internal/ir/parse_gemini.go:43` 声明了字段：

```go
SafetySettings json.RawMessage `json:"safetySettings,omitempty"`
CachedContent  string          `json:"cachedContent,omitempty"`
```

`parse_gemini.go:54-55` 又把它们列入 `knownFields`：

```go
"safetySettings": true, "generationConfig": true, "cachedContent": true,
```

但全包只出现一次：

```
$ grep -rn "SafetySettings" internal/ir/*.go
internal/ir/parse_gemini.go:43:   SafetySettings json.RawMessage `json:"safetySettings,omitempty"`
```

**影响**：这是最恶劣的一类丢失 —— 被标记为"已知"所以**不进 Extensions**，
但又从未赋值给 IR、从未序列化、**也没有 loss 事件上报**。完全静默。
`types.go:556` 的 `SafetySetting` 类型是死代码。

安全语义参数（内容安全阈值）被静默丢弃，属于合规风险，不只是兼容性问题。

### 1.5 P0-5：sanitizer 白名单过窄，是一颗地雷

`domains/transformation/sanitizer.go:12-21`，`alwaysKeepFieldsOpenAI` 只有 8 个字段：
`model / messages / stream / max_tokens / temperature / top_p / n / stop`。

`ApplyRequestWhitelist:74-86` 的语义是：一旦某 provider 配了非空
`passthrough_fields`，就转为**白名单模式**，凡不在 `passthrough_fields ∪ alwaysKeep`
里的字段**全部 delete**。

**影响**：给任一 provider 配置 `passthrough_fields` 会立即删掉
`tools`、`tool_choice`、`stream_options`、`response_format`、`reasoning_effort`……
即"配了一个想保留的字段"反而"删光了其它所有字段"。目前只有 MiniMax 配了
`strip_request_fields`（黑名单，安全），所以尚未爆炸，但这是随时会踩的地雷。

### 1.6 P1：IR 已有字段的单向丢失

已在 `reportSerializeXxxLosses` 上报 loss 事件（有可观测性，非静默），但仍是丢失：

| 参数 | 现状 |
|------|------|
| `top_k` | 仅 Anthropic/Gemini；→ OpenAI 丢 |
| `presence_penalty` / `frequency_penalty` | 仅 OpenAI Chat；Gemini 的 `GenerationConfig` 声明了字段但 parse/build 两侧都未接线 |
| `repetition_penalty` | **全网关无任何处理** |
| `seed` / `n` | → Anthropic/Responses 丢 |
| `stream_options` | IR 零处理，仅靠 Extensions；`executor.go:5089` 事后重新注入兜底 |
| `MaxReasoningTokens` | `types.go:437` 声明，**无任何读写方** |
| `includeThoughts` | Gemini parse 读入后丢弃；serialize 侧硬编码 `true` |
| `max_completion_tokens` | 被折叠进 `MaxTokens`，永远以 `max_tokens` 重新发出 |

### 1.7 思考能力识别：完全缺失

- **无任何模型级 `supports_thinking` 标记**。`models_canonical`、`model_pricing.supports_*`、
  `credential_capabilities` 三处能力容器都没有。
- 唯一相关的是 `strengths` 数组里可以填字符串 `"reasoning"`（运营自由文本，
  用于路由打分），**不是能力开关**。
- 名称模式检测只存在于路由打分：`domains/autocombo/engine.go:193-198` 匹配
  `"reason"` / `"o1"` / `"o3"` / `"deep"`。裸子串匹配 `"o1"` 会误命中
  （如 `gpt-4o1`…），且漏掉 `-r1`、`qwq`、`reasoner`、`thinking`、`glm-4.5`、
  `claude-3-7`、`gemini-2.5` 全部主流思考模型。
- **`thinking` / `reasoning_effort` 无条件下发**，从不询问目标模型是否支持。

**一个必须先知道的坑**：`modelname/variants.go:11-21` 的 `removableWrapperTokens`
包含 `"thinking"` 和 `"reasoning"`，`GenerateAliasVariants` 会把
`claude-sonnet-4-5-thinking` 归一成 `claude-sonnet-4-5`。所以
**基于名称的能力推断必须在归一化之前执行**，否则信息已被抹掉。

## 2. 研究结论（一手来源）

### 2.1 最关键发现：思考能力有 6 种互不兼容的表达方式

| 方式 | 厂商 | 形态 |
|------|------|------|
| `thinking` 对象 | DeepSeek / GLM / 火山 Ark / Kimi k2.x / MiniMax | `{"type": ...}`，**取值各不相同**：DeepSeek/GLM/Kimi 用 `enabled\|disabled`；**Ark 多一个 `auto`**；**MiniMax 用 `disabled\|adaptive`（没有 `enabled`）** |
| 布尔 + 整数预算 | Qwen / DashScope | 顶层 `enable_thinking: bool` + `thinking_budget: int` |
| `reasoning_effort` 枚举 | OpenAI / DeepSeek / GLM / Kimi k3 / Grok / Mistral / vLLM | 枚举值**互不一致**，见 2.2 |
| `reasoning` 对象 | OpenRouter / OpenAI Responses | `{effort, max_tokens, exclude, enabled, summary, context}`；`effort` 与 `max_tokens` 互斥 |
| 整数预算 | Anthropic / Gemini / vLLM | Anthropic `thinking.budget_tokens`；Gemini `thinkingConfig.thinkingBudget`；vLLM `thinking_token_budget` |
| 模板参数 | vLLM 托管开源模型 | `chat_template_kwargs: {"enable_thinking": bool}` |

**推论**：`reasoning_effort` 不能盲目透传，也不能用一个固定枚举。必须按目标模型能力收窄。

### 2.2 reasoning_effort 枚举分歧（透传即报错）

| 厂商 | 合法值 | 备注 |
|------|--------|------|
| OpenAI | `none\|minimal\|low\|medium\|high\|xhigh\|max` | 默认 `medium`；官方 spec 明示"并非所有推理模型支持全部取值" |
| DeepSeek | `low\|high\|max` | `medium`/`xhigh` 被静默折叠进 `high` |
| GLM-5.2 | `max\|xhigh\|high\|medium\|low\|minimal\|none` | 默认 `max`；`low`/`medium` 静默映射到 `high` |
| Kimi k3 | `low\|high\|max` | 默认 `max` |
| Grok-4.3 | `none\|low\|medium\|high` | 默认 `low`；**grok-4.5 默认 `high` 且不可关闭** |
| Mistral | `none\|minimal\|low\|medium\|high\|xhigh` | — |
| 火山 Ark | `minimal\|low\|medium\|high` | 无 `max` / `none` |
| Anthropic | `low\|medium\|high\|xhigh\|max`（`output_config.effort`） | 与 `thinking.budget_tokens` 并存 |
| vLLM | `none\|minimal\|low\|medium\|high\|xhigh\|max` | — |

### 2.3 思考历史保留 —— 第三个正交维度，同样全都不一样

| 厂商 | 字段 |
|------|------|
| GLM | `thinking.clear_thinking`（bool，默认 true） |
| Kimi | `thinking.keep`（`"all"` \| null） |
| Qwen | `preserve_thinking: true` |
| OpenRouter | `reasoning.exclude` |
| vLLM | `include_reasoning`（默认 **true**） |
| Anthropic | `thinking.display`（`summarized\|omitted`）+ `context_management.clear_thinking_20251015` |
| Gemini | `thinkingConfig.includeThoughts` |

响应侧字段名也不统一：多数为 `reasoning_content`，但 OpenRouter 用 `reasoning`，
MiniMax 需 `reasoning_split: true` 才拆分，vLLM 把入向 `reasoning_content` 改名为 `reasoning`。

### 2.4 LiteLLM 的 effort → budget 映射（生产验证过的基准，直接采纳）

来源：`litellm/llms/anthropic/chat/transformation.py:1174-1229` + `litellm/constants.py:83-192`

| `reasoning_effort` | 结果 | 默认预算 |
|---|---|---|
| `none` | **完全省略 thinking** | — |
| `minimal` | `{type:"enabled"}` | 1024 |
| `low` | `{type:"enabled"}` | 1024 |
| `medium` | `{type:"enabled"}` | 2048 |
| `high` | `{type:"enabled"}` | 4096 |
| `xhigh` | `{type:"enabled"}` | 8192 |
| `max` | `{type:"enabled"}` | 16384 |
| 其它 | `BadRequestError` | — |

两条覆盖规则：
1. adaptive-thinking 模型忽略 effort，直接返回 `{"type":"adaptive"}`（不带 budget）
2. `ANTHROPIC_MIN_THINKING_BUDGET_TOKENS = 1024` 是硬下限；预算再被 cap 到 `max_tokens - 1`

Gemini 另有按模型的最小值表：`2.5-flash → 1`、`2.5-pro → 128`、`2.5-flash-lite → 512`。

### 2.5 两条必须网关侧兜底的硬不变量

1. **`max_tokens` 必须 > `thinking.budget_tokens`**，否则 Anthropic 直接 400。
   Cline（`gateway.ts:195-204`）和 LiteLLM（`transformation.py:1246`）都各自实现了这条兜底。
2. **thinking 启用时不能带 `temperature`**。Claude Code 源码
   （`claude.ts:1691-1695`）显式注释："the API requires temperature: 1 when thinking is enabled"，
   因此它在 thinking 开启时**根本不发** `temperature`。网关若擅自注入 `temperature` 会导致 400。

### 2.6 智能体客户端实际发送的参数（决定"不许丢"清单）

**Claude Code**（来源：Anthropic 官方 npm source map 还原，`claude.ts:1699-1728`）：

```json
{ "model","messages","system","tools","tool_choice",
  "betas":["claude-code-20250219", ...],
  "metadata":{"user_id":"<JSON 字符串>"},
  "max_tokens","thinking","temperature",
  "context_management":{"edits":[...]},
  "output_config":{"effort","format","task_budget"},
  "speed":"fast" }
```

关键行为：
- `betas` 是 **body 数组**，不是手搓 header。网关必须同时接受 body `betas` 和 `anthropic-beta` header。
- `metadata.user_id` 是 **JSON 编码的字符串**（内含 device_id/account_uuid/session_id），不是普通 ID。
- `thinking` 优先用 `{"type":"adaptive"}`（无 budget），回退 `{"type":"enabled","budget_tokens":N}`，
  且 `budget_tokens = min(max_tokens - 1, budget)`。
- `CLAUDE_CODE_EXTRA_BODY` 环境变量会把任意用户 JSON 展开进 body → **未知顶层字段必须透传**。

**Codex CLI**（来源：`codex-rs/codex-api/src/common.rs:252-275`）：

```json
{ "model","instructions","input","tools","tool_choice","parallel_tool_calls",
  "reasoning":{"effort","summary","context"},
  "store","stream",
  "stream_options":{"reasoning_summary_delivery":"sequential_cutoff"},
  "include":["reasoning.encrypted_content"],
  "service_tier","prompt_cache_key",
  "text":{"verbosity","format"},
  "client_metadata":{...} }
```

关键行为：
- `include:["reasoning.encrypted_content"]` **恒定发送**，丢掉它会静默破坏无状态多轮推理。
- effort 取值含 `xhigh`/`max`/`ultra`，并有 `Custom(String)` 前向兼容 → 网关不能用封闭枚举校验。
- `reasoning` items 里的 `encrypted_content` 必须**字节级原样往返**。

**Roo Code** `src/api/transform/reasoning.ts` 是最清晰的跨厂商映射参考，
其中 Gemini 3 已改用 `thinkingConfig.thinkingLevel`（`minimal|low|medium|high`）而非数字预算。

### 2.7 可复用的能力数据库：LiteLLM model_prices_and_context_window.json

2988 条模型记录，与思考能力直接相关的键：

| 键 | 出现次数 |
|---|---|
| `supports_reasoning` | 815 |
| `supports_xhigh_reasoning_effort` | 123 |
| `supports_none_reasoning_effort` | 82 |
| `supports_adaptive_thinking` | 77 |
| `supports_max_reasoning_effort` | 72 |
| `supports_minimal_reasoning_effort` | 70 |
| `supports_low_reasoning_effort` | 3 |
| `bedrock_output_config_effort_ceiling` | 30 |

这套 schema 证明了一件事：**"支持思考"是不够的，还必须知道"支持哪些 effort 档位"**。
本方案的 `reasoning_caps` 结构照此设计。

### 2.8 各厂商拒绝/约束标准参数（硬错误，优先级最高）

| 厂商 | 约束 |
|------|------|
| DeepSeek | `frequency_penalty`/`presence_penalty` 已废弃且静默忽略；`prefix` 需 `/beta` base URL |
| Grok | 推理模型上 `presence_penalty`/`frequency_penalty`/`stop` **直接报错** |
| Qwen | 仅 `messages[0]` 可为 system，末条须为 user；开源权重模型带 thinking 时**只能流式**；`n` 仅 `qwen-plus` 支持 |
| GLM | `tool_choice` **只接受 `auto`**；`stop` 最多 4 个但只生效 1 个；`do_sample:false` 会禁用 temperature/top_p |
| MiniMax | `n` 必须为 1；penalties/`logit_bias` 静默忽略 |
| Kimi | 采样参数**仅 moonshot-v1 有**，k2.x/k3 schema 里根本没有；`temperature` 上限 1（非 2） |
| Mistral | `temperature` 上限 **1.5**；`additionalProperties:false`（**未知键直接拒绝**） |
| OpenAI | `stop` 在 `o3`/`o4-mini` 上不支持；`max_tokens` 与 o 系列不兼容（须用 `max_completion_tokens`） |
| Anthropic | `temperature` 上限 **1.0**（非 2.0）；thinking 启用时须 `temperature=1` 或不传 |

**Mistral 的 `additionalProperties:false` 是"无条件全量透传"方案的反例** —— 这也是为什么
最终采用注册表分类而非无脑透传。

## 3. 现有方案的核心误判

| 现有设计 | 误判 | 修正 |
|---|---|---|
| 用 `SourceProtocol == 目标协议` 决定是否还原 Extensions | 把"协议相同"当成"字段安全"的充分条件；实际跨协议才是常态 | 改为按**字段**判定：未知字段透传，已知 dialect 字段查注册表翻译/裁剪 |
| 用 `ClientCatalogCode == UpstreamCatalogCode` 二次门禁 | 等价于"网关不转发时才还原"，自相矛盾 | 删除；由注册表的 dialect 归属承担隔离职责 |
| Gemini 的 `safetySettings` 列入 knownFields | 列入 known 却不实现 = 既不进 Extensions 也不被序列化 | 补 IR 字段 + parse + serialize 全链路 |
| `alwaysKeepFields` 只列 8 个字段 | 白名单模式下等于删光其余字段 | 扩展为注册表全集；`passthrough_fields` 语义改为"额外允许"而非"唯一允许" |
| `thinking`/`reasoning_effort` 无条件下发 | 目标模型不支持时 400 或静默忽略 | 引入 `reasoncap` 三层能力解析 + 按能力收窄/降级/剥离 |
| `ReasoningConfig` 只有 effort+budget 两个字段 | 无法表达 adaptive、thinkingLevel、历史保留、6 种 dialect | 扩展为规范化 `ReasoningIntent` + N 向 dialect 适配器 |

### 需要标注的不确定项

- **火山 Ark**：参数集来自 SDK，取值合法性可信，但**每模型的支持情况与默认值无法从 SDK 证实**。
- **DeepSeek**：当前文档只列 `deepseek-v4-flash`/`deepseek-v4-pro`，已不再提及 `deepseek-reasoner`。
- **MiniMax**：旧版 `bot_setting`/`reply_constraints`/`mask_sensitive_info`/`tokens_to_generate`/
  `aigc_watermark` 在现行 OpenAPI spec 中**已不存在**，无证据表明 OpenAI 兼容端点仍支持。
  现有代码 `sanitizer.go` 注释里提到的 MiniMax `bot_setting` 属于过时信息。
- **OpenRouter**：`transforms` 与 `usage:{include}` **已下线**，改为 `context-compression` 插件；
  `stream_options.include_usage` 已废弃为 no-op。
- **vLLM**：`guided_json`/`guided_regex`/`guided_grammar`/`guided_choice` 在 main 分支**已删除**，
  合并为 `structured_outputs:{json,regex,choice,grammar,...}`。
- **Cursor**：无公开请求 schema，无法核实。
