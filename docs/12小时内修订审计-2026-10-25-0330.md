## 3. 重点维度排查

### 3.1 并发锁控制 / 多线程资源竞争

**已核对通过的三处**（逐层验过，不是推理）：

| 位置 | 结论 |
|---|---|
| `internal/extpointledger` | `sync.Mutex` 保护 `entries` map + 环形缓冲；**`entries` 的键来自固定常量**（`extpoints.IDHTTPMiddlewareChain` / `IDResponseIntercept`）⇒ **map 基数有界，不会被请求内容撑爆** ✓ |
| `domains/requestjourney/recorder.go` 的 `Close` vs `enqueuePump` | ★ **无「向已关闭 channel 发送」的竞态**：`Close` 在 `stateMu.Lock()` 下 `close(pump.queue)`；`enqueuePump` 在 `stateMu.RLock()` 下发送 ⇒ ★★ `Lock()` 排除全部 `RLock()` 持有者 ⇒ 关闭与发送**互斥有序** ✓ |
| 同上，`r.pumps` 的并发 | ★ `r.pumps` 只在**构造函数**（`NewDurableRecorder` / `newRecorderWithIngress`）里 append ⇒ 构造完成后**不再变更** ⇒ `Close()` 在锁外遍历 `r.pumps` **不构成数据竞争** ✓ |

### 3.2 内存 / 句柄泄漏

| 位置 | 结论 |
|---|---|
| `extpointledger` 延迟样本 | ✓ 环形缓冲，长度 = 容量，满则覆盖最旧 ⇒ **有界** |
| `recorder` 的 `p.pending` | ✓ `p.pending = p.pending[1:]` + `append` 的组合下，底层数组会周期性重分配；且失败重投有**上界**（`len(p.pending) < p.pendingCap()`，`pendingCap() = cap(p.queue)`）⇒ **有界** |
| `recorder` 的 pump goroutine | ✓ 退出条件 `!queueOpen && p.pendingCount.Load() == 0` ⇒ 队列关闭且无待重试 ⇒ 返回 ⇒ `defer close(p.done)` ⇒ **不泄漏**。★ 注：`Close(ctx)` 超时返回 `ctx.Err()` 时 goroutine **仍在**（等 outbox 的 `due` 到期）⇒ 这是**有界的排空**，不是泄漏，但调用方需知道 `Close` 可能「返回错误而后台仍在收尾」 |

### 3.3 异步处理异常 / 异常错误处理

| 位置 | 结论 |
|---|---|
| `recorder` 的入队失败 | ✓ 队列满 ⇒ `ErrRecorderQueueFull` ⇒ 计数 `enqueueDrops` + `MarkIngressDegraded()` + `recordJourneyDropWithStore` ⇒ **降级是可见的**，不是静默丢弃 |

1. **合并**：`origin/main` → 本地冻结工作树，**逐个冲突按业务逻辑判定**（不是「取一边」）⇒ 5 处冲突：shell 门 / 掏空门 / `LESSONS.md` / `AGENTS.md` / `docs/db-changelog.md`；
2. **验收**：`go build ./...` → `make guards-installer` → `make guards-ursmcheck` → `make guards-shell` ⇒ **全绿**才提交；
3. **落地**：提交 ⇒ 合并进 main ⇒ 推送 ⇒ **各目录最终停留在 main**；
4. **同步**：其余五个同源目录**逐个**（不并发）快进到 main；
5. **分支治理**：查 48 小时内、且已不活跃（>1h 无活动）的未合并子分支 ⇒ 逐个判「变更是否有效」⇒ 有效的逐文件并入 main、无效的删除。
