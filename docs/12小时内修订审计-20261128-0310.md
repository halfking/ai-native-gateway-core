### 2.2 P1-1 ｜ limiter 采样 goroutine 在 cgroup 模式下永不退出（goroutine + ticker 泄漏）

- **位置**：`plugin-runtime/limiter/resource_limiter.go` → `Stop()` / `monitorCgroup()` / `monitorProcess()`
- **事实**：采样循环靠 `select { case <-ticker.C: ... case <-r.monitorCancel: return }` 退出，而 `close(r.monitorCancel)` 写在 `Stop()` 的 **`if r.mode == ModeMonitor` 分支内** ⇒ **cgroup 模式（生产平台 Linux + cgroupv2）的 `monitorCgroup` 永不退出**。
- **实害**：
  1. 每停一个插件泄漏**一个 goroutine + 一个 5s ticker**；插件重启 / 升级反复发生 ⇒ goroutine 数**单调增长**，无回收路径；
  2. 泄漏的 goroutine 仍在**每 5s 读已被 `rmdir` 的 cgroup 文件**（`memory.current` / `pids.current` / `cpu.stat` / `memory.events`），读失败被静默忽略 ⇒ **无声空转**（无日志、无告警）；
  3. 该 goroutine 还持有 `r` 的引用 ⇒ 被泄漏的 limiter 连同其 limits 快照一起不可回收。
- **连带两处（同型，一起收口）**：
  1. `monitorDone` 原先**只有** `monitorProcess` 会 `close` ⇒ `monitorCgroup` 不关 ⇒ 一旦让 `Stop()` 在 cgroup 模式下等 `monitorDone`，**插件停止会永久挂住**（所以「把 cancel 移出模式分支」必须同时补 `monitorCgroup` 的 close，否则是把泄漏换成死锁）；
  2. `cgroupPath` 字段被 `Stop()` **写**、被采样 goroutine 与 `applyCgroupLimits` / `AssignProcess` **读**，**两侧都不持锁** ⇒ 真实数据竞争（`go test -race` 可复现：Stop 与采样拍同时读写同一 string 头指针）。
- **修法（已落地，`1903a10e6a` + `0212ef5ed5`）**：
  1. `Stop()` 的「取消 + 等待」移出模式分支，**两种模式都做**；`close` 走 `sync.Once`（结构上排除双重 close panic——原 `select { case <-ch: default: close(ch) }` 判据在并发 Stop 下不成立）；
  2. `monitorCgroup` 补 `closeMonitorDone()`，`monitorProcess` 改走同一 `doneOnce`；
  3. 等待加 **2s 上限**（原 monitor 模式的 `<-r.monitorDone` 是无上限等待，采样循环卡住 ⇒ 插件停止被无限期挂住）⇒ 异常时降级为 WARN 继续，cgroup 清理照跑；
  4. `cgroupPath` 收口到 `cgroupDir()` / `setCgroupDir()` 访问器（RWMutex）⇒ 消除数据竞争。
- **验证（变异自证）**：
  - 把 `close(monitorCancel)` 改回 `if r.mode == ModeMonitor` 分支 ⇒ `TestStopCancelsSamplingInEveryMode/cgroup` **转红（4.21s）**；还原 ⇒ 全绿。
  - ★ **关键教训**：第一版回归测试只跑 monitor 模式 ⇒ 对本缺陷**恒绿**（变异后照样 PASS ⇒ 门是空的）。改法是在真实采样 goroutine 起来后**强制切换 `rl.mode`**，使「Stop 是否送达取消」在任意平台都可测；真机 cgroup 腿（`TestStopCgroupModeTerminatesSamplingGoroutine`）在 Linux + cgroupv2 可用时另行覆盖。
  - `go test -race ./plugin-runtime/limiter/` → 无竞争。
  - 新增 4 条回归：逐模式取消 ＋ 真机 cgroup 腿 ＋ goroutine 数回落 ＋ 并发 Stop 不 panic。
