### ⚠️ 发现问题

### A-1（P2，本轮修复落地）：egress 策略缓存把 DB 错误结果毒化 60s

- **位置**：`proxy/egress_provider.go` `policy()`（R29 f766a466d 引入）。
- **问题**：`providers` 表查询失败（瞬断/超时/迁移窗口）时无条件回退 `direct` **并写入 60s TTL 缓存**——已被标记 `egress_profile='proxy'` 的海外 provider 在 DB 瞬断后最长 60s 静默直连，绕过 must-proxy 契约；且该错误分支零日志，事后不可见。
- **判据**：R31-4 真实事故（14 个 provider 标 proxy 但 dialable=0 → 30 分钟内 4 次 fail-closed → 回滚 direct）证明 fail-closed 语义已在生产承重；错误缓存直连正是该契约的对称漏洞。与提交信息「marked providers fail-closed」意图相悖。
- **修复（本轮实施）**：DB 错误路径**只对当次请求回退 direct、不写缓存**（下一请求重查）+ `slog.Warn` 落日志；成功读取（direct/proxy 两形态）照旧缓存。`TestEgressProviderDBErrorFailsOpenToDirect` 契约不变（单次调用回退仍 direct）。`go vet` + `go test -run Egress ./proxy` 绿。
- **残留（登记不修）**：错误当次请求对 marked provider 仍是 fail-open 直连——彻底 fail-closed 需要最后已知策略的负缓存（标记过 proxy 的 id 记忆化），属 R31-4 运营处置同类决策（dialable=0 时标记本身就是事故源），移交 Owner 拍板。
