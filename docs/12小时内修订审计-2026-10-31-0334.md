### ★★ P2-1｜`routing_policy` 的**根因**没修：整张表**没有任何唯一约束**

窗口内 `bd5c85af2` / `370040181` 把 `bg/quality_node_source.go` 与 `bg/model_credibility_source.go` 的
发现查询改成 `SELECT DISTINCT`（并按 42P10 契约把裸列 `pm.raw_model_name` 塞进 select list）。
**这两处消费侧的自保是对的、也是必要的**（详见 §四 D4 的复核）。但**根因仍在**，本轮把三环查实了：

**环 ① —— 重复行从哪来（真正的根）**：

- `sql/objects/tables/routing_policy.sql`：`id smallint DEFAULT 1 NOT NULL` +
  `CONSTRAINT routing_policy_id_check CHECK ((id = 1))` ⇒ 这是一张**单例表**。
  ★★ **但它没有 PRIMARY KEY，也没有任何 UNIQUE 约束** ⇒ 「单例」只是**约定**，数据库层面零保证。
- `sql/schema/02-seed.sql:935`：
  `INSERT INTO public.routing_policy VALUES (1, 'default', …) ON CONFLICT DO NOTHING;`
  ★★ **`ON CONFLICT` 没有冲突目标，而表上没有唯一约束可供冲突**
  ⇒ ★★ **这个 `ON CONFLICT DO NOTHING` 子句是空操作**
  ⇒ ★★ **每次全新安装/升级都再插一行 `id=1`** ⇒ 211 生产实测已堆到 **4 行**。

**环 ② —— 重复行怎么放大成事故**：`CROSS JOIN routing_policy pol` ⇒ 4 行 ⇒ 同一个
`(credential, model)` 对被放大成 4 份 targets ⇒ 同轮串行重探 4 次（`inFlight` gate 只防并发、不防同批重复行）。

**环 ③ —— 重复行怎么让写路径也放大**：`admin/routing.go` 的三处写路径都是
`UPDATE routing_policy SET … WHERE tenant_id = 'default'` ⇒ ★ **没有 `id` 谓词**
⇒ ★ 每次管理面改配置都会**同时改 4 行**。

**为什么环 ① 必须单独修**：环 ② 已经被消费侧 `DISTINCT` 挡住了，环 ③ 无害但浪费。
但**只要「没有唯一约束」这件事不变**，**下一个消费者忘了加 `DISTINCT` 就复发** ——
而且这次的注释已经自己承认了这种脆弱性：
「★ 其它消费方都有 LIMIT 1 / GROUP BY 保护，**只有两处发现查询没有** ⇒ 在 SQL 侧去重」。
**这是把防线建在每一个消费者身上，而不是建在数据不变量上。**

**修复**：见 §四 D3（新增迁移 927：去重 + `UNIQUE (tenant_id)` ⇒ ★ **让那个 `ON CONFLICT DO NOTHING` 第一次真正生效**）。

### D4｜复核窗口内的 `SELECT DISTINCT` 修复（结论：**正确，不用改**）

`bd5c85af2` / `370040181` 的两处改动我逐条查证过：

- **42P10 契约**：PG 要求 `SELECT DISTINCT` 的 `ORDER BY` 表达式必须以**裸列**形态出现在 select list。
  两处都把 `pm.raw_model_name` **追加在 select list 末位**，且 `ORDER BY c.id, pm.raw_model_name` 两列都是裸列 ⇒ ✅ 契约满足。
- **扫描是否会踩 NULL**：裸列 `pm.raw_model_name` 被扫进 `string` 变量 ⇒ **若该列为 NULL，`rows.Scan` 会报错**。
  ★ 查证：`sql/objects/tables/provider_models.sql` 与 `sql/schema/01-schema.sql` 均定义
  `raw_model_name text NOT NULL`，且全仓**没有** `DROP NOT NULL` ⇒ **该列不可能为 NULL** ⇒ ✅ 无风险。
  ⇒ 原先的 `COALESCE(pm.raw_model_name, '')` 其实是**冗余**的，改为裸列后语义逐字节等价。
- **`useModel` / `RawModelName` 的口径变化**：`COALESCE(…, '')` → 裸列 ⇒ 因为 NOT NULL，**取值完全相同** ⇒ ✅ 无漂移。
- **DISTINCT 的去重键**：`c.secret_ciphertext`（bytea）在 select list 里 ⇒ 同一凭据的 4 行 ciphertext 相同 ⇒ ✅ 能正确折叠。
- **`CROSS JOIN` 的扇出列是否进了 select list**：`pol` 只在 `WHERE`（`pol.tenant_id='default'`）与
  `featuredFilter`（`pol.featured_models`）里用，**没有任何 `pol` 列进入 select list**
  ⇒ ⇒ 扇出的 4 行在 select list 上**逐列相同** ⇒ ✅ `DISTINCT` 精确折叠。

⇒ **窗口内的这两处修复是正确且完整的**，本轮不动它们。
★ 但**它们只是消费侧的自保** ⇒ 根因由 D3 收口。
