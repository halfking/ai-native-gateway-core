## 2. 会话压缩约束（继承 08-MiniMax-M3-审计与统一标准.md）

### 2.1 工具轮次完整性

**铁律**：

1. 压缩按完整工具轮次删除：`assistant tool call`、全部 `tool result` 和必要的后续确认消息必须作为原子单元。
2. 压缩后必须满足 `assistant call ID -> tool result ID` 一一对应；孤儿结果 fail closed。
3. 合并 consecutive messages 不能跨越 tool round，也不能合并不同 role 的工具消息。
4. 重试复用同一逻辑附件 manifest，不重新改写工具 arguments 或媒体引用。
5. 文本可以摘要，多模态 block、tool call、tool result 和 call ID 不能静默删除。

### 2.2 多模态块保留

**修复前问题**（`domains/hooks/compression/strip.go`）：

- `hasThinkingBlocks()` 把 `image_url` 和 `input_audio` 也视为需要清理的块类型
- `stripThinkingBlocks()` 在过滤时只保留 `text`/`tool_use`/`tool_result`，删除所有 `thinking`/`image_url`/`input_audio` 块
- 更严重的是，过滤保留块时只追加了 `p.Type`（一个 JSON 字段值），而非完整块结构，导致保留的块丢失了除 type 之外的所有数据

**修复后**：

- `hasThinkingBlocks()` 只检测 `thinking` 类型
- `stripThinkingBlocks()` 保留除 `thinking` 外的所有块（完整 JSON）
- 使用 `json.RawMessage` 保持块原始结构

### 2.3 连续消息去重（sanitizer.go）

此前已修复的连续消息去重逻辑：

- `string + array` 混合内容不再误判为重复
- `array + array` 对比时图片块不会被丢弃
- `array + string` 反向同样安全

## 3. 多模态能力矩阵

### 3.1 转换路径（OpenAI ↔ Anthropic Phase 1 修复）

| 来源协议 | 块类型 | 目标协议等价物 | 当前状态 |
|---------|--------|--------------|---------|
| Anthropic `image` (url) | `source.type=url` | OpenAI `image_url` | verified |
| Anthropic `image` (base64) | `source.type=base64` | OpenAI `image_url` (`data:` URI) | verified |
| OpenAI `image_url` | URL 或 `data:` URI | Anthropic `image` (url 或 base64) | verified |
| Anthropic `text` | 文本块 | OpenAI 文本（合并或数组） | verified |
| Anthropic `tool_use` | 工具调用 | OpenAI `tool_calls` | verified |
| Anthropic `tool_result` | 工具结果 | OpenAI `tool` role 消息 | verified |

**关键修复**：

1. **OpenAI → Anthropic**（`chat_to_anthropic.go`）：
   - 新增 `parseImageDataURI()` 函数，检测 `data:` 前缀并解析 MIME 和 base64 payload
   - 正确生成 `source.type="base64"` 块，而非错误的 `type="url"`

2. **Anthropic → OpenAI**（`anthropic_to_chat_request.go`）：
   - base64 图片恢复为 `data:` URI 格式的 `image_url`（不再降级为文本占位符 `[Image: base64 data]`）
   - URL 图片保留为原始 URL 的 `image_url`（不再降级为 `[Image: URL]`）
   - 使用 `hasNonTextContent` 标志位延迟返回，确保 tool_calls 和文本不丢失

3. **Streaming Bridge**（`domains/streaming/messages.go`）：
   - 与上述同类问题修复一致
   - 未知的 passthrough 块也追加到 contentParts，避免丢失

### 3.3 必须落实的通用约束

#### URL 可达性

- 上游访问 URL 时，URL 必须从上游网络可达，且不依赖浏览器 Cookie、内网 DNS、管理端登录态或一次性已过期签名
- 附件服务应支持 HTTPS、正确的 `Content-Type`、`Content-Length`/范围请求和稳定的 2xx 响应
- URL 中不放 tenant、原始文件名、访问令牌或可枚举的自增 ID
- 对需要鉴权的对象，优先使用短时签名 URL；签名 TTL 必须覆盖上游重试窗口
- 代理转发前必须验证 scheme、host allowlist、解析后的地址和响应 MIME，防止 SSRF

#### MIME、大小和生命周期

- 保存 `declared_mime`、`sniffed_mime`、字节数、SHA-256、来源协议、目标供应商和过期时间
- 不能只根据文件扩展名判断类型；声明类型与探测结果冲突时拒绝或隔离
- 每个供应商适配器单独维护 `max_bytes`、支持 MIME、最大块数、引用 TTL 和重试规则
- 供应商文件引用过期、附件删除或签名失效后，历史会话不可保证可重放；日志标记 `replayable=false`

#### 转换与保真

- 转换 IR 必须保留原始块顺序、文本、图片/音频/文档数据、工具调用、工具结果和未知字段
- **不支持的内容不能静默改成 `[Image: ...]` 等文本占位符**。应返回结构化错误，或在明确配置下走 OCR/ASR/文档抽取并标注 `derived=true`
- `data:` URI 解析必须校验 base64、MIME、大小和 padding
- HTTP URL 不应被下载后无条件重上传，除非策略明确允许且完成 SSRF 检查
- 流式响应只转换事件，不重新拼接或丢弃已发送的内容块；未知事件应按协议策略透传或记录不支持原因

## 4. 附件与模型契约

### 4.1 附件提取管线

```text
客户端请求 (base64 image)
  ↓
Extractor.ExtractFromOpenAIBody() / ExtractFromAnthropicBody()
  ↓ 解码 base64 → SHA256 去重 → 落盘
  ↓
request_logs.attachments (JSONB 元数据数组)
  ↓
GET /api/admin/attachments/{path} 下载/预览
```

**Phase 2A 新增**：
- Anthropic 协议附件提取（`messages.go:237`）
- **strict 模式下存储失败直接返回 503，不再 best-effort 转发**

### 4.2 落盘路径格式（Phase 2A：SHA256 两级分片）

```text
{BaseDir}/YYYY/MM/{hash[0:2]}/{hash[2:4]}/{hash}{ext}
```

示例：`/data/attachments/2026/07/a4/91/a491f20c...9d.png`

历史路径 `YYYY/MM/req_{requestID}/...` 仍由读取接口兼容。

**写入规则**：

1. 先写随机临时文件
2. 计算并校验 SHA256、大小和探测 MIME
3. 使用原子 rename 提交最终文件
4. 相同内容并发写入时复用已存在文件，清理自己的临时文件
5. 禁止把客户端原始文件名直接拼入路径

### 4.3 附件生命周期

```text
detected -> storing -> stored -> manifest_ready -> sent
             |
             v
       store_failed
```

**strict 模式**（默认）：
- `LLM_GATEWAY_ATTACHMENT_STRICT` 默认 strict
- store_failed 直接阻断请求转发（返回 503）
- 只有设为 `"0"` 才降级为 best-effort

**修正的结论**：

旧提案中"上传失败后继续发送 base64"只能作为显式 best-effort 模式，不能作为生产默认行为。

### 4.4 供应商引用模式（三种模式）

| 模式 | 说明 | 适用场景 |
|---|---|---|
| `data` | base64 data URI | 小图片、供应商不支持 URL、内网环境 |
| `gateway_url` | `files.kxpms.cn` 或网关可达 HTTPS URL | 供应商可访问公网 URL |
| `provider_file` | 供应商 Files API 引用（如 Anthropic file、Gemini file_uri） | 大文件、长时复用、供应商托管 |

**关键修正**：

- "所有 base64 替换成 `files.kxpms.cn` URL" **不成立**；上游可能不可达、需要供应商 URI 或只接受 data URL
- "URL 替换减少 token" **不成立为通用规则**；只承诺减少网关/日志字节；token、图像细节和计费以供应商返回 usage 为准

### 4.5 模型名标准化

**结论**：

1. 客户端模型进入系统后使用**小写标准模型名**
2. 供应商调用使用**采集到的原始模型名**，保留大小写
3. `standardized_name` 等内部匹配字段在入库时标准化为小写，SQL 使用直接等值匹配，不再用 `lower(...)` 兜底

## 6. 统一转换标准总结

| 层级 | 标准 |
|---|---|
| **会话压缩** | 工具轮次原子性、ID 闭环、多模态块保留、连续消息去重安全 |
| **多模态转换** | 块顺序保持、MIME 保真、不静默降级、未知块保留 |
| **附件管线** | SHA256 去重、两级分片、strict 模式、原子写入 |
| **供应商适配** | 三种引用模式、URL 可达性、Files API 隔离 |
| **模型契约** | 小写标准化入库、原始大小写调用、能力按 model offer 判断 |

**验收标准**：

- Phase 1 已修复路径通过 round-trip 测试
- 附件提取不丢失、不重复、不泄漏原始文件名
- strict 模式下存储失败必须阻断
- 供应商引用模式可按配置切换
- 模型名大小写处理符合契约
