## 四、已登记未修（附处置口径与理由）

> 登记不是「不查」，是**查到了、证到了、但本轮不动**——每条都写明为什么不动、再动该怎么动。

### R-01 ｜`providers.base_url` 与 `provider_endpoint_protocols.base_url` **无写侧同步**（P1，跨表数据源问题）

- **事实**：`provider_endpoint_protocols` 全仓**唯一写入者**是迁移 800 的一次性回填；
  `admin/providers.go` 的 PATCH 只 `UPDATE providers SET base_url = …`，**不动 pep**。
  路由侧 `provider/client.go:2043` 把 pep 行作为 `NativeEndpoints` 喂给 `endpointselect.Select()`
  ⇒ **协议匹配时路由也走 pep 的旧 URL**。
- **为什么本轮不动**：修它要同时处理「base_url 变了 + protocol 也变了」的组合语义，
  且跨两张表写 ⇒ 需要迁移 + 写侧事务，**不是一轮审计能安全落地的改动**。
  本轮已把**探针与路由分叉**那一半修掉（F-06），剩下的「两边一致地停在旧 URL」是**上游真源问题**。
- **再动怎么做**：admin PATCH 的 base_url 分支改成**单条 CTE**同时更新 `providers` 与
  `provider_endpoint_protocols` 的 `(provider_id, protocol)` 行（protocol 取本次 PATCH 后的有效值），
  并补一条「base_url 变更 ⇒ 对应 pep 行必须同步」的守卫。

### R-02 ｜缓存验证面缺三条补充闸 ⇒ F9「判据等价」的说法不成立（P1）

- **事实**：`autoroute/recommend_v2.go:758-763` 的缓存验证加了视图闸，但**没有**决策面
  `autoroute/availability_filter_sql.go:95-104` 的三条补充闸（canonical 停用、模型生命周期、`broken_confirmed`）；
  而供应商候选面 `provider/client.go:1872/:2092/:2114-2123` **有**这三条
  ⇒ 候选面会剔掉该 offer，缓存验证却仍判它「可路由」。
- **为什么本轮不动**：改判据会改变在役路由的命中率（缓存命中的那条 offer 可能突然不被认），
  属于**行为面变更**，需要与 F-03 的还原一起做灰度对拍，不能夹在一次审计修复里单发。
- **再动怎么做**：把三条闸抽成**共享 SQL 片段**（决策面/缓存面/候选面同一份字面量），
  再补「缓存验证 ≡ 决策面」的**同源对拍判据**（不要抄清单，要解析同一份字面量）。

### R-03 ｜`credit_ledger` 对 `tenants` 的外键可能挡住重置（P2，**环境相关**）

- **事实**：启动迁移 `007_maas_billing.sql:97` 有 `tenant_id … REFERENCES tenants(code)`（**无 ON DELETE ⇒ NO ACTION**），
  而基线 dump `sql/objects/tables/credit_ledger.sql` **没有**这条 FK ⇒ 结论依环境而定。
  `credit_ledger` **不在**类别注册表里 ⇒ 若该 FK 存在，`DELETE FROM tenants` 会撞外键 ⇒
  整笔事务回滚 ⇒ **全类别重置 500 且一行未删**（而预览已承诺行数）。
- **为什么本轮不动**：**仓内无法定论**，必须到目标库实查 `pg_constraint`。
- **再动怎么做**：在 211/本地查 `pg_constraint` 里 `credit_ledger` 对 `tenants` 的 `confdeltype`；
  若存在 ⇒ 把 `credit_ledger` 纳入 tenants 类别的前置删除（或加 NO ACTION 阻断说明），
  并把新隔离库夹具（`data_lifecycle_data_init_isolated_db_test.go` 只建 8 表 3 FK）补到能覆盖这类阻塞。

### R-04 ｜16 阶段框架尚未接入真实派发链路（P2）

- **事实**：F-02 补齐了 `extpoints` 的具体实现，但**只有 demo 在用**，dispatch 链路未接。
- **为什么不动**：接入 dispatch 是**功能面**变更（16 个阶段要逐个定义真实语义），不是缺陷修复。
- **再动怎么做**：先定「哪几个阶段真的需要插件介入」，再逐阶段接，不要一次接 16 个。

### R-05 ｜`UserDetailDrawer.vue` 的两处 P2（竞态守卫 / 重复全量取密钥）

- **事实**：`loadKeys()` 无请求序号守卫（切用户时慢响应可覆盖新用户列表）；
  切到 Keys 页签会**重复**触发 `GET /api/keys`（该端点返回**全系统**密钥）。
- **为什么本轮不动**：**该文件当时正被另一个并行会话在改**
  （`llm-gateway-go-cursor` 工作树里 `admin/keys.go` / `UserDetailDrawer.vue` / `web/src/api/keys.ts` 有活跃改动，
  最后写入时间就在审计开始前 31 秒）⇒ **在用工作树不动**是本仓纪律。
- **再动怎么做**：等那侧合入后，补 `useRaceGuard`（同文件 stats 已有先例）+ 去掉重复取数。

### R-06 ｜窗口内新增的三个测试是**源码文本断言**，抓不住语义缺陷（P2）

- **事实**：`bg/node_probe_endpoint_align_test.go`、`bg/stats_minute_probe_rollup_test.go`、

  ⇒ 抓不住「死路由 / 字段映射错 / handler 没接」——F-07/F-08 正是这样漏过去的。
- **为什么不动**：把源码文本断言改成**行为断言**需要可注入的依赖（DB/接口），是**测试架构**改动。
- **再动怎么做**：优先给「纯函数/纯派生」补行为断言（本轮已给 `extpoints` 注册表/引擎补了 4 条行为判据）；
