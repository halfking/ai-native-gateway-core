## 2. 本轮修复的缺陷（全部真库/变异自证）

### 2.1 P1-A ｜billing_retry_queue 三处并发语义缺陷（主审计发现，一次性 PG17 实证）

- **位置**：`maas/billing_retry_queue.go`（EnqueueCreditDeduction / ProcessRetryQueue）＋ `sql/migrations/startup/1002_billing_retry_queue.sql`
- **事实与实害**：
  1. **入队 check-then-insert 竞态**：先 `SELECT id ... WHERE request_id=$1 AND status IN('pending','retrying')` 再裸 `INSERT`——双网关并发入队同一 requestID 会插出**两行在途任务**，无任何唯一约束兜底。重复扣减实害被 `DeductCredits` 的 `pg_advisory_xact_lock`＋alreadyCharged 幂等检查兜住（资金无错），但队列语义坏掉（重复重试、attempts 双计、监控数字失真）。
  2. **消费无行锁**：`ProcessRetryQueue` 的批次 SELECT 无 `FOR UPDATE SKIP LOCKED`——多副本网关各自跑 `BillingRetryWorker`（`cmd/gateway/main.go:3414` 每实例都启动）会捞到同一批任务并发重试。
  3. **refund_credits 假完成**：执行分支只认 `deduct_credits`，`refund_credits` 走到时 `execErr` 恒 nil ⇒ 空跑也被标 `completed`（队列说退了、积分没退）。当前仓内无 refund 入队方（死枚举值），属埋雷。
- **修法**（本轮落地）：
  1. migration 1002 补部分唯一索引 `uq_billing_retry_queue_inflight (request_id) WHERE status IN ('pending','retrying')`（终态行不受限，同请求历史多条合法）；应用层 INSERT 改 `ON CONFLICT (request_id) WHERE ... DO UPDATE SET last_error=...`——撞行退化为更新错误信息，与已存在分支同语义；
  2. 批次 SELECT 加 `FOR UPDATE SKIP LOCKED`（与 metricsstore processor 同模式，副本互斥、互不阻塞）；
  3. 未知/未实现 retry_type 按失败处理走退避路径，超限进 failed 可见，不再静默假完成。
- **验证**（一次性 PG17 容器，kx-pg17-audit1002）：
  - 1002 首跑 EXIT=0、幂等重放 EXIT=0；`\d` 确认 uq 索引在位；
  - 裸 INSERT 同 requestID 第二条被拦（`Key (request_id)=(req_Y) already exists`），首行 last_error 完好；终态后同 requestID 可重新入队（队列语义正确）；
  - 应用层 ON CONFLICT 推断谓词与 uq 索引逐字匹配：第二次 INSERT 走 DO UPDATE（last_error e0→e1），恒 1 行在途；
  - `go build ./...` 绿，`go test ./maas/ ./bg/` 全绿。

### 2.2 P2-B ｜attachments 配额 check-then-act 超卖＋预留泄漏（主审计发现）

- **位置**：`domains/attachments/quota.go`（CheckAndReserve / CommitUsage）＋ `domains/attachments/storage.go` ＋ migration 633
- **事实**：CheckAndReserve 是「读-判断」两步且**不落库**（注释自述「实际不修改数据库」）——并发上传同租户全部读到同一旧 `current_bytes` 全部放行 ⇒ 配额超卖；且 check 与 commit（storage.go:340→385）之间隔着文件写入，保存失败/去重命中时预留无处安放。
- **修法**（本轮落地）：
  - 633 迁移补 `reserved_bytes`/`reserved_files_today` 两列（`ADD COLUMN IF NOT EXISTS`，存量库幂等补列）；
  - CheckAndReserve 改**单条条件 UPSERT**：`WHERE current+reserved+new <= max AND files+reserved_files+1 <= max`，命中即预留写回（行级串行化），未命中 `RowsAffected=0` ⇒ 按 daily_files/storage 区分报 QuotaExceededError；
  - CommitUsage 同步转销预留（GREATEST 防负）；新增 ReleaseReservation，storage.go 三个失败路径（exists 探测失败/去重命中/Save 失败）释放；
  - 钉测 `TestQuotaManager_AtomicReservationSQLShape`＋`TestQuotaManager_ReservedColumnsInMigration`，**变异自证**（去掉 WHERE 容量约束 ⇒ 红；还原 ⇒ 绿）。
- **验证**：633 首跑/重放真库 EXIT=0、reserved 两列在位；`go test ./domains/attachments/` 全绿；三树副本（sql/embeddata/installer-migrations up）SHA 对拍一致（`ffc1de66fc45`）。

### 2.3 P2-C ｜verifyAttachmentOwnership 的 JSONB 探针应用层拼接（代理面复核确证，本轮落地）

- **位置**：`domains/attachments/handler.go:235`
- **事实**：`pathJSON := fmt.Sprintf(`+"`"+`[{"path":"%s"}]`+"`"+`, relPath)` 在应用层拼 JSON——relPath 来自用户可控 URL（`TrimPrefix(r.URL.Path,...)`），内嵌 `"`/`\` 可破坏 JSON 结构使 `@>` 探针语义漂移。危害受限（只影响 EXISTS 判定真假，不跨表），但属第二阶注入形态。
- **修法**：改 `attachments @> jsonb_build_array(jsonb_build_object('path', $2::text))`——整串作为 text 参数化进 SQL 侧构造，探针语义恒为「完整 path 等值包含」。
- **验证**：`go build` 绿；既有 `handler_tenant_isolation_test.go` 全绿。

### 2.4 P2-D ｜PreCheckBalance 异步日志 goroutine 无防护（主审计发现，既往教训复发）

- **位置**：`maas/balance_precheck.go:105`
- **事实**：`go s.logBillingPrecheck(context.Background(), ...)` 裸 goroutine——函数内无 recover（Exec panic 崩进程，与 5f2383ce6 漏项同型）、ctx 无超时（DB 变慢时 goroutine 无界堆积，每请求一个）。

- **验证**：`go build ./maas/`＋`go test ./maas/` 全绿。

### 2.5 P0-A ｜DeductCredits 引用不存在的 quota_used 列，订阅租户持续漏计费（代理1发现，主审计复核确证＋真库复现）

- **位置**：`maas/deduct_credits.go`（5.1 节）
- **事实**：`UPDATE tenant_subscriptions SET quota_used = quota_used + $1`——`tenant_subscriptions` 全部建表迁移（007_maas_billing.sql:57-68）与 census 只有 **quota_remaining**，无 `quota_used`。凡有活跃订阅配额的租户，扣费事务该 UPDATE 直接 SQL 报错 → 整个事务回滚（**ledger 也不写**）→ 进重试队列 10 次全败 → 标 failed。**订阅租户的用量持续漏计费**。旧路径写法是 `quota_remaining = quota_remaining - $2 WHERE quota_remaining >= $2`（service.go:238-239）。
- **修法**（本轮落地）：改回旧路径语义——`quota_remaining` 原子递减＋`WHERE quota_remaining >= $1` 守卫；`RowsAffected=0`（并发下配额已被扣空）时本次不消费订阅，`consume=0`，溢出部分自然落进 5.2/5.3 钱包扣减；订阅消费 ledger 仅在 `subConsumed>0` 时写入。
- **验证**：一次性 PG17 夹具（tenant_subscriptions/tenant_credit_wallets/credit_ledger/maas_credit_consumption_buckets 全真表结构）：`UPDATE ... WHERE quota_remaining >= 30` 执行成功，quota 100→70。

### 2.6 P0-B ｜DeductCredits 不回写 balance_credits，P0-1 预检反馈回路被打断（代理1发现，主审计复核确证）

- **位置**：`maas/deduct_credits.go`（全文）
- **事实**：新扣费路径只更新 `granted_balance`/`purchased_balance` 两个分量，不回写 `balance_credits`；而 `PreCheckBalance` 读的恰是 `balance_credits`（balance_precheck.go:48）。⇒ 扣费后预检读数永不下降 → `balance >= 0` 分支恒命中 → **负余额/信用额度阻断（P0-1 核心目标）对走新路径的流量永不触发**，租户可无限透支，钱包/月账单展示口径漂移。旧路径同事务 `balance_credits = granted + purchased`（service.go:272-280）。
- **修法**（本轮落地）：同事务补 `UPDATE tenant_credit_wallets SET balance_credits = granted_balance + purchased_balance`（仅在有消费时执行）。
- **验证**：真库夹具：扣 20+10 后 balance_credits 正确回写 50（=granted 30＋purchased 20）。

### 2.12 P1-G ｜decisions 用户过滤恒不匹配，user 角色决策面恒空（代理3发现，主审计复核＋真库确证，本轮落地）
