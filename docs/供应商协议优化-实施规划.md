## 1. 范围与目标

### 1.1 业务目标

| ID | 目标 | 验证 |
|----|------|------|
| **G1** | 客户端 Ollama 原生请求（带 `options` / `format` / `keep_alive` 等字段）能路由到声明了 `ollama-native` endpoint 的供应商 | byte-level 通；trace 显示 `endpoint.match_rule=stage1, vendor_native=null` 或按 family 命中 |
| **G2** | Ollama-natively-deployed 供应商（`PROTOCOL=ollama-native`）被 request 命中后，**真正**走 Ollama `/api/chat`（NDJSON + options 子对象），而不是静默降级到 OpenAI 兼容 `/v1/chat/completions` | trace `decision.protocol=ollama-native, execution.upstream_url=.../api/chat`；服务端实际响应 NDJSON |
| **G3** | `EndpointSelector` 决策规则收紧：**协议一致（endpoint.protocol == client.protocol）** 优先级 ≥ family 一致；同协议匹配命中即视为 passthrough 候选 | unit test 覆盖：Stage 1 必须先按 protocol exact 匹配，再叠加 family 校验 |
| **G4** | Ollama 私有参数（`options.temperature`、`options.top_k`、`options.num_predict`、`format`、`keep_alive`、`raw`）在「客户端协议 == endpoint 协议」时**完整透传**到上游，不会被 OpenAI 序列化器裁掉 | golden test：发 IR Extensions + OllamaOptions，序列化后字节级等于 fixture |
| **G5** | 自托管 Ollama 场景：上游 NDJSON chunk 解析出的 `message.thinking`（reasoning）正确落入 IR `StreamChunk.ReasoningContent`；下游 SSE 合成时拼到 `delta.reasoning_content`；`done=true` 行的 usage（`prompt_eval_count` / `eval_count`）正确归一为 IR `Usage` | golden：3 行 NDJSON → OpenAI SSE chat chunk + usage |
| **G6** | settings UI 可视化：每个 endpoint 行显式标注「主协议」/「vendor 原厂」/「探活状态」/「权重」；新增 endpoint 的协议下拉包含 ollama-native | UI 截图 + e2e |
| **G7** | 老供应商（仅声明主协议、`PROTOCOL=ollama-native`、无 endpoint 子表）的所有功能、E2E 不破；metric `endpoint_decision_total{rule=stage4,protocol=ollama-native}` 覆盖迁移灰度 | 现有 + 新增 e2e 全绿 |

## 2. ollama-native 接入的具体设计

### 2.1 wire 形态回忆（避免反复引用）

> 完整 wire 见 [docs/vendor-formats/ollama.md](vendor-formats/ollama.md)

**入站 Ollama native 请求**（OpenAI 兼容客户端发到 Ollama 必须用 `/v1/chat/completions`；Ollama 原生客户端用 `/api/chat`）：

```
POST /api/chat HTTP/1.1
Host: localhost:11434
Content-Type: application/json
Authorization: Bearer <optional>

{
  "model": "llama3.1",
  "messages": [{"role":"user","content":"..."}],
  "stream": true,
  "format": "json",                        // 协议私有：JSON 强制输出
  "keep_alive": "5m",                       // 协议私有：模型存活时长
  "raw": false,                             // 协议私有：不解析 prompt
  "options": {                              // ★ 协议私有：所有采样参数与模型选项的容器
    "temperature": 0.7,
    "top_p": 0.9,
    "top_k": 40,
    "num_predict": 1024,                    // ★ max_tokens 同位概念，但字段名不同
    "stop": ["\n"],
    "seed": 42,
    "num_ctx": 4096,
    "num_gpu": 1,
    "mirostat": 0, "mirostat_eta": 0.1, "mirostat_tau": 5.0,
    "repeat_last_n": 64, "repeat_penalty": 1.1,
    "tfs_z": 1.0, "typical_p": 1.0
  },
  "tools": [{"type":"function","function":{...}}]
}
```

**出站响应**（NDJSON，每行一个 JSON 对象）：

```
{"model":"llama3.1","created_at":"2024-...","message":{"role":"assistant","content":""},"done":false}
{"model":"llama3.1","created_at":"2024-...","message":{"role":"assistant","content":"Hel"},"done":false}
...
{"model":"llama3.1","created_at":"2024-...","message":{"role":"assistant","content":"Hello!","done_reason":"stop"},
 "done":true,"total_duration":...,"prompt_eval_count":10,"eval_count":20}
```

**与 OpenAI Chat 的差别**（关键证据，这是「同协议 baseurl 必须优先」的根本原因）：

| 维度 | OpenAI Chat | Ollama native |
|------|-------------|---------------|
| 端点 path | `/v1/chat/completions` | `/api/chat` |
| Stream framing | SSE (`data: {...}\n\n` + `data: [DONE]\n\n`) | NDJSON (`{...}\n`，靠 `done:true` 终止) |
| Stream header | `text/event-stream` | `application/x-ndjson` |
| Response terminator | SSE `[DONE]` sentinel | 顶层 `done:true` 的 chunk |
| 采样参数容器 | 顶层 `temperature`/`top_p`/... | 顶层 `options.temperature`/... 嵌套 |
| `max_tokens` | 顶层 `max_tokens` | `options.num_predict` |
| `response_format.type` | 完整对象 `{type:"json_schema",json_schema:{...}}` | 顶层字符串 `format: "json"` |
| Reasoning 字段 | `choices[].delta.reasoning_content` | `message.thinking`（cumulative） |
| 错误 | `{error:{message,type,...}}` | 顶层字符串 `{"error":"..."}` |
| Auth | 必须 Bearer | 通常无；如启用（`OLLAMA_API_KEY`）则 Bearer |

**结论**：当 endpoint 声明 `protocol=ollama-native` 时，绝对**不能**把 Ollama 私有字段（`options`、`format`、`keep_alive`、`raw`）塞进 OpenAI 序列化器（那样会被 `paramguard` 当作未知字段裁掉），必须走 Ollama 原生序列化器。即：endpoint.protocol 与客户端协议一致 → 协议专属 schema 与字段守卫生效。

### 2.2 IR 字段 ↔ Ollama 字段映射表

> 这是「协议私有参数透传」的数据契约。IR 层用 `Extensions` 装私有块，专属 marshaler 读取。

| IR 字段 | Ollama native 字段 | 备注 |
|---------|-------------------|------|
| `Request.Model` | `model` | 直通 |
| `Request.Messages[]` | `messages[]` | 直通；role 集合 `{user, assistant, system, tool}`（Ollama 把 system 当 user 走，但 wire 层支持 `"role":"system"`） |
| `Request.Stream bool` | `stream` | 直通 |
| `Request.Temperature *float64` | `options.temperature` | **强制进 options**（不是顶层） |
| `Request.TopP *float64` | `options.top_p` | 同 |
| `Request.TopK *int` | `options.top_k` | 同 |
| `Request.MaxTokens int` | `options.num_predict` | 字段名异构 |
| `Request.Stop []string` | `options.stop` | 数组 |
| `Request.Seed *int64` | `options.seed` | 同 |
| `Request.RepetitionPenalty *float64` | `options.repeat_penalty` | 仅模型支持时 |
| `Extensions["ollama.options.num_ctx"]` | `options.num_ctx` | 仅 Ollama 模型调度有 |
| `Extensions["ollama.options.num_gpu"]` | `options.num_gpu` | 同 |
| `Extensions["ollama.options.mirostat"]` | `options.mirostat` | 同 |
| `Extensions["ollama.options.mirostat_eta"]` | `options.mirostat_eta` | 同 |
| `Extensions["ollama.options.mirostat_tau"]` | `options.mirostat_tau` | 同 |
| `Extensions["ollama.options.repeat_last_n"]` | `options.repeat_last_n` | 同 |
| `Extensions["ollama.options.tfs_z"]` | `options.tfs_z` | 同 |
| `Extensions["ollama.options.typical_p"]` | `options.typical_p` | 同 |
| `Extensions["ollama.format"]` (string\|object) | `format` | Ollama 接受字符串（`"json"`）或 schema 对象（Ollama 0.5+） |
| `Extensions["ollama.keep_alive"]` (string\|number) | `keep_alive` | 直通 |
| `Extensions["ollama.raw"]` (bool) | `raw` | 直通 |
| `Request.Tools []ToolDefinition` | `tools[]` | 形态同 OpenAI；Ollama 0.5+ |
| `Response.Choices[].Message.Content` | `message.content` | 出站解析端 |
| `Response.Choices[].Message.ReasoningContent` | `message.thinking` | 双向解析 |
| `Response.Usage.PromptTokens` | `prompt_eval_count` | 解析 NDJSON `done:true` 行 |
| `Response.Usage.CompletionTokens` | `eval_count` | 同 |
| `Response.Usage.TotalTokens` | `prompt_eval_count + eval_count` | 计算 |
| 流终止信号 | `done:true` | 无 `[DONE]` sentinel |

### 2.3 `extensions` 命名约定

`InternalRequest.Extensions` 是 IR 已有的「未知/未映射字段」承接位（见 [internal/ir/types.go](../internal/ir/types.go) 中 `Extensions map[string]any`）。

约定：**所有 Ollama 私有字段必须进 `Extensions["ollama.<key>"]` 命名空间**，并由 `serialize_ollama.go` 在序列化时**全部**回填到顶层（不丢弃）。同时 paramreg 把 `ollama.*` 标记为 `DialectOllama.owned`，对其做 `Keep`（不裁剪、不重命名）。

### 2.4 客户端协议检测（inbound）

`internal/ir.DetectProtocol` 当前**不**识别 Ollama native 入站请求（F6 审计明确：ProtocolOllamaChat 是 `internal/ir/types.go:42` 常量，「detect.go 不识别该协议」）。需要补一个分支：

```go
// internal/ir/detect.go 新增分支（伪代码，详见 §4.1）
//
// Ollama 私有信号：
//   - 顶层 `options` 对象（OpenAI/Anthropic 都没有这个键）
//   - 顶层 `format` 字符串（OpenAI response_format 是对象）
//   - 顶层 `keep_alive`
//   - 顶层 `raw`
if _, ok := keys["options"]; ok { return ProtocolOllamaChat, 0.85, nil }
if _, ok := keys["keep_alive"]; ok { return ProtocolOllamaChat, 0.85, nil }
if format, ok := keys["format"]; ok { if _, isStr := format.(string); isStr { return ProtocolOllamaChat, 0.7, nil } }
```

> 注：用 `ProtocolOllamaChat`（IR 协议枚举）作为入站识别结果，与出站 enum `ProtocolOllamaNative`（catalog 出站枚举）通过 `paramreg.protocolToDialect` 双映射共占 `DialectOllama`。两套命名因为历史成因（catalog CHECK 约束在先，IR 流解析器在后增「chat」区分是 stream 流类型，已在 [internal/ir/types.go:35-42](../internal/ir/types.go) 注释中说明）。

### 2.5 客户端「同协议 baseurl 优先」语义

**EndpointSelector 决策规则收紧**（接 §5.2 高阶设计，本期把 Stage 1 重写）：

| 阶段 | 匹配条件 | Passthrough |
|------|---------|-------------|
| **Stage 1A（new，协议一致 + family 一致，透传）** | `decision.Protocol == wantProtocol && decision.VendorNative == wantFamily` | ✅ true |
| Stage 1B（new，协议一致 + family 已知但与 endpoint 声明不同，桥接） | `decision.Protocol == wantProtocol && wantFamily != "" && decision.VendorNative != wantFamily` | ❌ false，IR 桥 |
| Stage 1C（new，协议一致 + family 未知，桥接） | `decision.Protocol == wantProtocol && wantFamily == ""` | ❌ false，IR 桥 |
| Stage 2 | `decision.VendorNative == wantFamily && decision.Protocol != wantProtocol` | ❌ false，IR 桥 |
| Stage 3 | `decision.VendorNative == wantFamily` 但 wantFamily 为空 | ❌ false，回主协议 |
| **Stage 4（兼容）** | 兜底主协议 `(cand.BaseURL, cand.Protocol)` | 与 `wantProtocol==cand.Protocol` 比较 |

**关键点**：Stage 1 的协议一致匹配**总是**先于 family 一致匹配，即使 family 不对也应优先选同协议 endpoint（同协议意味着 paramguard 与序列化器匹配，参数零损失）。这是用户原文「优先使用同一协议的 baseurl 与协议，确保协议特有的参数能够发挥作用」的算法兑现。

### 2.6 schema 校验与守卫

#### 2.6.1 入站侧：当客户端协议 = ollama-native 时 passthrough schema 校验

参考 [供应商协议优化.md §6.4](../供应商协议优化.md) 表，新增 Ollama 行：

| 客户端协议 | 必填字段 | Schema 限制 |
|-----------|---------|------------|
| ollama-native | `model`, `messages` | `messages` 数组每项含 `role`+`content`，`role` ∈ `user\|assistant\|system\|tool`；顶层可含 `options`/`format`/`keep_alive`/`raw`/`tools`/`stream`（保留原样） |

#### 2.6.2 出站侧：序列化工件

`serialize_ollama.go` 行为规约：

1. 仅当 `req.SourceProtocol == ProtocolOllamaChat` **或** `decision.Passthrough && decision.Protocol == "ollama-native"` 时被调用（双重入口护栏，防止默认 fallback 误用）。
2. **必填校验**：`model` 非空；`messages` 非空数组。
3. IR → Ollama field map 按 §2.2 表逐项搬运。
4. **所有 `Extensions["ollama.*"]` 100% 透传**到顶层/嵌套位置（这正是「协议特有的参数能够发挥作用」的核心契约点）。
5. `num_predict` if `MaxTokens > 0`（Ollama 默认无限制时 `num_predict` 不发或为 0 — IR `MaxTokens=0` 表示"不限制"）。
6. 顶层 schema key 白名单（`serialize_ollama.go` 不应发未登记的 key，包括 OpenAI `response_format`、`tools[].function` 等必须用 Ollama 等价物 `tools[]`，已是兼容；其他未登记字段**仅当**位于 `Extensions["ollama.*"]` 才下发）。

### 3.2 数据库 schema 详设

```sql
-- sql/objects/tables/provider_endpoint_protocols.sql
CREATE TABLE public.provider_endpoint_protocols (
    id                  bigserial    PRIMARY KEY,
    provider_id         bigint       NOT NULL,
    tenant_id           text         NOT NULL DEFAULT 'default',
    protocol            text         NOT NULL,
    base_url            text         NOT NULL,
    is_primary          boolean      NOT NULL DEFAULT false,
    vendor_native       text,        -- 详见 §3.3 SSOT 复用
    enabled             boolean      NOT NULL DEFAULT true,
    weight              smallint     NOT NULL DEFAULT 100,
    notes               text,
    health_status       text         NOT NULL DEFAULT 'unknown',
    health_checked_at   timestamptz,
    health_latency_ms   integer,
    health_error        text,
    consecutive_failures integer     NOT NULL DEFAULT 0,
    last_failure_kind   text,
    created_at          timestamptz  NOT NULL DEFAULT now(),
    updated_at          timestamptz  NOT NULL DEFAULT now(),
    CONSTRAINT provider_endpoint_protocols_unique
        UNIQUE (provider_id, protocol),
    CONSTRAINT provider_endpoint_protocols_provider_fk
        FOREIGN KEY (provider_id) REFERENCES providers(id) ON DELETE CASCADE,
    CONSTRAINT provider_endpoint_protocols_protocol_check
        CHECK (protocol = ANY (ARRAY[
            'openai-completions','openai-responses',
            'anthropic-messages','gemini-generate','ollama-native'
        ])),
    CONSTRAINT provider_endpoint_protocols_base_url_nonempty
        CHECK (length(base_url) > 0)
);

CREATE UNIQUE INDEX provider_endpoint_protocols_one_primary
    ON provider_endpoint_protocols (provider_id)
    WHERE is_primary = true;

CREATE INDEX provider_endpoint_protocols_provider_idx
    ON provider_endpoint_protocols (provider_id, protocol);
CREATE INDEX provider_endpoint_protocols_family_idx
    ON provider_endpoint_protocols (provider_id, vendor_native)
    WHERE vendor_native IS NOT NULL AND enabled = true;
```

        WHEN pc.code IN ('google-gemini','vertex-ai') THEN 'google-gemini'
        WHEN pc.code = 'ollama'           THEN NULL  -- 由运营指定 vendor_native
        ELSE NULL
    END
FROM providers p
LEFT JOIN provider_catalog pc ON pc.code = p.catalog_code
WHERE p.deleted_at IS NULL
ON CONFLICT (provider_id, protocol) DO NOTHING;

```go
// internal/endpointselect/selector.go

package endpointselect

// Protocol 协议字面量（去重了 catalog 与 paramreg 两套并集）
type Protocol string

const (
    ProtocolOpenAICompletions Protocol = "openai-completions"
    ProtocolOpenAIResponses   Protocol = "openai-responses"
    ProtocolAnthropicMessages Protocol = "anthropic-messages"
    ProtocolGeminiGenerate    Protocol = "gemini-generate"
    ProtocolOllamaNative      Protocol = "ollama-native"
)

type Decision struct {
    Protocol       Protocol
    BaseURL        string
    EndpointID     int64   // 0 = 回退到主端点
    VendorNative   string
    Passthrough    bool    // true = 字节透传，不走 IR
    MatchRule      string  // "stage1a" | "stage1b" | "stage1c" | "stage2" | "stage3" | "stage4"
    Reason         string
}

// wantProtocol = 客户端识别出的协议（IR.SourceProtocol / params.ClientProtocol），
// wantFamily = models_canonical.family（discovery.InferFamily(stdName)）。
//
// 决策矩阵：
//
//   ┌───────────────────────────┬──────────────────────────────┐
//   │ 想命中的条件              │ 优先级 / 行为                 │
//   ├───────────────────────────┼──────────────────────────────┤
//   │ protocol == wantProtocol  │ 1A:  + vendor_native 命中    │
//   │ && vendor_native == family│     → Passthrough=true        │
//   │                           │ 1B: protocol match, family 不 │
//   │                           │     一致 → Passthrough=false  │
//   │                           │     （stage1 协议一致优先）   │
//   │                           │ 1C: protocol match, family 空 │
//   │                           │     → Passthrough=false       │
//   ├───────────────────────────┼──────────────────────────────┤
//   │ vendor_native == family   │ Stage 2 (命中但 protocol 不   │
//   │                           │ 一致；例如 anthropic 客户端   │
//   │                           │ 请求 claude model 但 endpoint │
//   │                           │ 是 chat 兼容 → 走 IR 桥)      │
//   ├───────────────────────────┼──────────────────────────────┤
//   │ 主协议兜底                 │ Stage 4 (兼容老行为)          │
//   └───────────────────────────┴──────────────────────────────┘
func Select(c CandidateLite, wantProtocol Protocol, wantFamily string) Decision { ... }
```

**关键修正**：原 §5.2 的设计把 family+protocol 双匹配定为 Stage 1；本节根据用户反馈「优先使用同一协议的 baseurl 与协议」调整为：**协议一致匹配 ≥ family 一致匹配**。这是选路规则的算法兑现点。

package ir

// SerializeOllama 把 InternalRequest 翻译为 Ollama /api/chat 原生请求体。
//
// 字段映射见 docs/vendor-formats/ollama.md 与 docs/供应商协议优化-实施规划.md §2.2。
//
// 入口护栏：
//   - req.SourceProtocol == ProtocolOllamaChat（来自 detect.go 识别出的客户端协议），或
//   - 上游协议参数明示为 ollama-native（passthrough 路径，serializer 由 executor 在 bypass IR
//     时直接调用；本函数为有 IR 介入场景用）。
//
// 必须保留全部 Extensions["ollama.*"] 字段，不裁剪。
//
// 错误：缺 model 时返 ErrSerializeOllamaMissingModel。
func SerializeOllama(req *InternalRequest) ([]byte, error) {
    if req == nil { return nil, fmt.Errorf("serialize ollama: nil request") }
    if req.Model == "" { return nil, ErrSerializeOllamaMissingModel }

    body := map[string]any{
        "model":    req.Model,
        "messages": serializeOllamaMessages(req.Messages),
        "stream":   req.Stream,
    }

    // 1. 采样参数 → options 子对象
    opts := map[string]any{}
    if req.Temperature != nil { opts["temperature"] = *req.Temperature }
    if req.TopP        != nil { opts["top_p"]        = *req.TopP }
    if req.TopK        != nil { opts["top_k"]        = *req.TopK }
    if req.MaxTokens   > 0    { opts["num_predict"]  = req.MaxTokens }
    if len(req.Stop) > 0      { opts["stop"]         = req.Stop }
    if req.Seed        != nil { opts["seed"]         = *req.Seed }
    if req.RepetitionPenalty != nil { opts["repeat_penalty"] = *req.RepetitionPenalty }
    // 私有 options.* 透传（命名空间: ollama.options.*）
    for k, v := range req.Extensions {
        if strings.HasPrefix(k, "ollama.options.") {
            opts[strings.TrimPrefix(k, "ollama.options.")] = v
        }
    }
    if len(opts) > 0 {
        body["options"] = opts
    }

    // 2. 顶层私有字段透传
    for k, v := range req.Extensions {
        if strings.HasPrefix(k, "ollama.") && !strings.HasPrefix(k, "ollama.options.") {
            topKey := strings.TrimPrefix(k, "ollama.")
            body[topKey] = v
        }
    }

    // 3. tools 直通（Ollama 0.5+ 兼容 OpenAI tool schema）
    if len(req.Tools) > 0 {
        body["tools"] = serializeOllamaTools(req.Tools)
    }

    return json.Marshal(body)
}

// OllamaExecutor 是 Ollama 原生 /api/chat 协议的 executor。
// 与 ChatExecutor 的关键差异：
//   - URL: ollamachat.BaseURL + "/api/chat"
//   - Header: 默认可空 Bearer（Ollama 通常不需认证；启用 OLLAMA_API_KEY 时同 Chat）
//   - Stream framing: NDJSON（application/x-ndjson），非 SSE
//   - 出站 body: 用 SerializeOllama；不打 IR 桥
//   - 入站 stream: 用 ParseOllamaStreamChunk（R52 已实现）
//   - 入站 non-stream: 用 ParseOllamaResponse（本期新增）
type OllamaExecutor struct {
    HeaderProfiles *HeaderProfilesCache
    Compression    *CompressionStrategy
    QualityProcessNonStream func(...) (...)
    QualityProcessStreamLine func(...) (...)
}

func (o *OllamaExecutor) BuildRequest(cand provider.Candidate, body []byte, isStream bool) (*http.Request, error) {
    upstreamURL := upstreamurl.OllamaChatURL(execParams.EndpointBaseURL())
    req, err := http.NewRequestWithContext(ctx, http.MethodPost, upstreamURL, bytes.NewReader(body))
    if err != nil { return nil, err }
    req.Header.Set("Content-Type", "application/json")
    if cand.APIKey != "" {
        req.Header.Set("Authorization", "Bearer "+cand.APIKey)
    }
    // Ollama 0.5+ 流式走 NDJSON，有些客户端/中间件严格要 Accept header
    if isStream {
        req.Header.Set("Accept", "application/x-ndjson")
    }
    return req, nil
}

func (o *OllamaExecutor) WriteNonStreamResponse(w http.ResponseWriter, resp *http.Response, ...) ([]byte, error) {
    body, _ := io.ReadAll(resp.Body)
    parsed, err := ir.ParseOllamaResponse(body)
    if err != nil { /* 原样回 + log */ return body, wErr }
    // synthesize OpenAI Chat wire shape（decoder 通用）
    out := ir.SerializeOpenAIChat(parsed)
    return out, w.Write(out)
}

func (o *OllamaExecutor) WriteStreamResponse(...) {
    // NDJSON framing → SSE chunk
    scanner := bufio.NewScanner(resp.Body)
    scanner.Buffer(make([]byte, 1024*1024), 4*1024*1024)
    for scanner.Scan() {
        line := scanner.Bytes()
        chunk, err := ir.ParseOllamaStreamChunk(line)
        if err != nil { continue }  // skip noise
        chunkBytes := ir.SynthesizeOpenAIChunk(chunk) // 与现有 SSE 合成共用
        if chunkBytes != nil {
            w.Write(chunkBytes)  // SSE-framed chunk
        }
        if chunk.Type == ir.ChunkTypeDone { break }
    }
}

## 5. 阶段性里程碑与回滚策略

### 5.1 6 个 phase（更细粒度）

| Phase | 周期 | 内容 | 回滚手段 |
|-------|------|------|---------|
| **P0** schema + 迁移回填 | 0.5 w | DDL / V8XX 数据回填 / contract_test 准备 | 直接 DROP TABLE，不影响业务（endpoint 子表是增量冗余，fallback 走 providers.protocol） |
| **P1** UI 端点管理（只读不调度） | 0.5 w | admin 6 endpoint CRUD + SettingsTab.vue card；dispatch **仍 bypass** Select，所有请求走主协议 | UI 隐藏 card；CRUD 接口可 disable |
| **P2** EndpointSelector 决策框架 | 1 w | selector.go + 4 stage unit test；dispatch 仍强制 `decision = stage4`，行为 100% 等价旧版 | selector 还没接 dispatch，回退到 candidates.Protocol 直 switch |
| **P3** Ollama-native executor + serializer + parser 落码 | 1.5 w | serialize_ollama / parse_ollama_stream 接线 / parse_ollama（non-stream）/ executor_ollama / detect.go Ollama 分支 / upstreamurl EpOllamaChat | 单元 + 集成测试不通过则 commit revert；旧行为 = chat 兼容 |
| **P4** dispatch + 灰度 | 1.5 w | dispatch 接 Select（Stage 1A-1C 启用）+ ollama-native case；operator 灰度（先 dev-research，验证后再主集群） | feature flag `LLMGW_ENDPOINT_SELECTOR_ENABLED` 默认 false；true 出问题时秒切回 |
| **P5** Passthrough 路径 + UI 护栏 | 1 w | executor_passthrough + passthrough schema 校验（包含 ollama-natie passthrough）；SettingsTab 高亮「NDJSON/Passthrough」徽章 | `passthrough_mode=off` 全局；UI 「禁止透传」开关 |
| **P6** 收口 | 1 w | 文档定稿 / 旧 default-branch 评估退役 / metric 看板 / F6 contract test 完成修正 | — |

合计约 **7 周单人**，与高阶设计 §13 一致。

### 5.2 灰度顺序

按风险递增排，feature flag 控制：

```
FF_ENDPOINT_SELECTOR  default = false   // P2 上线后开
FF_OLLAMA_NATIVE      default = false   // P4 上线后开
FF_ENDPOINT_PASSTHROUGH default = false // P5 上线后开
```

每灰度阶段：
- Phase 2（P2）：dev-research 灰度 1 周 → 主集群灰度 10% 流量 1 周 → 100%
- Phase 3（P4）：先开 `FF_OLLAMA_NATIVE`，**只对自托管 Ollama 实例生效**（catalog code=`ollama`），其它供应商走 Stage 4 fallback；观察 1 周后再开 `FF_ENDPOINT_SELECTOR`
- Phase 4（P5）：passthrough 只对 Claude Code → Anthropic 直连场景启用，由 trace 决定是否扩张到 ollama-natie Passthrough

### 5.3 回滚（应急）

| 事故 | 影响 | 回滚动作 |
|------|------|---------|
| selector 误判导致请求打到错误 endpoint | 部分用户请求得到错误响应 | `FF_ENDPOINT_SELECTOR=false` 紧急热切；dispatch 仍走主协议 |
| ollama executor 把 body 序列化成 OpenAI 形态发到 `/api/chat` | Ollama 报 `error: "invalid chat message"` | `FF_OLLAMA_NATIVE=false`；回到 chat 兼容层（用户文档中说明） |
| Passthrough 把不该透传的字段透传了 | 上游 4xx | `FF_ENDPOINT_PASSTHROUGH=false` |
| migrations V8XX 数据回填出错（如 is_primary 不唯一） | routing 错乱 | 手动 `UPDATE provider_endpoint_protocols SET is_primary=false WHERE id NOT IN (SELECT MIN(id)... GROUP BY provider_id)`；后续补 trigger / unique partial index |

## 7. 风险与缓解

| ID | 风险 | 影响范围 | 缓解 |
|----|------|---------|------|
| R1 | Ollama 无 auth 时 `Authorization` header 被一些反代拦下 | 1.x 之前版本已加 header | `BuildRequest` 仅在 `apiKey != ""` 时附加 Bearer |
| R2 | NDJSON chunk 没 `data:` 前缀，下游误判为非 SSE | stream 输出 | Ollama executor WriteStreamResponse 内置 NDJSON→SSE 转换；trace 标注 `synth.ollama_ndjson_to_sse=true` |
| R3 | 选项冲突：客户端 OpenAI 客户端发 `response_format`，但 Ollama 原生不支持对象形态 | UI/SettingsTab 显示告警 | settings UI 在 vendor_native=ollama 时显式提示 "OpenAI 兼容模式下 response_format 必须为字符串 'json'"（这是从 `docs/vendor-formats/ollama.md §2` 的 wire 规定） |
| R4 | `models_canonical.family` 缺失 / NULL | routing 决策 family 字段为空 | `discovery.InferFamily(stdName)` 兜底；trace `family_source=catalog|infer|unknown` |
| R5 | Passthrough 把 OpenAI 形 `tools` 发到 Ollama 但 Ollama 0.4 不支持 tools | 0.4 模型 4xx | schema 校验先于 passthrough：若 `tools` 非空且 endpoint vendor_native=ollama 且 endpoint 健康度不达 0.5 版本，passthrough=false 退回 IR；metric 记录 |
| R6 | 多个 endpoint 都声明 ollama-native | 选路歧义 | `weight` + `cand.weight` 二级排序；初次配置 reject 重复 protocol |
| R7 | migrations V8XX 在大集群 runtime 上 ALTER 与并发读写 | 短时锁 | `provider_endpoint_protocols` 是新建表，无锁问题；但 INSERT 回填量大时用 `INSERT ... SELECT LIMIT 1000` 分批 |
| R8 | Ollama 流 cumulative content 与现有 SSE 合成器兼容 | stream assembler | `internal/ir/stream.go:60` `CumulativeContent` 字段已在（2026-09-21 P2-1 落码但零消费者），本期在 `OllamaExecutor.WriteStreamResponse` 内首次接线；增 golden test |
| R9 | F6 contract test 修正会引起已有 catalog 校验报警 | CI | 在 PR 中分开两步：先合并 serialize/parse/executor 再合并 contract 修正 |
| R10 | handlers/.../messages.go 中 `messages_count_tokens.go:74-77` 的 input_tokens 估算语义在 ollama 上不一致 | 计费 | count_tokens 走 Ollama `/api/show` 或 `POST /api/chat` with stream=false + 极小 num_predict；统一走 IR.EstimateTokens（不读上游，不影响） |
| R11 | `cmd/gateway/main.go` 注册顺序：若 `/api/chat` 在 `/v1/chat/completions` 之后，Ollama native 客户端可能误命中 chat handler | ingress 路由 | 注册顺序 `/api/chat` 在前 + 路径严格匹配；CDN / 反代层保留 path-only 转发 |
