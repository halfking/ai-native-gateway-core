# 场景分析与处理流程

> 基于现有 errorsx 错误分类、Executor 重试逻辑、Session/Hook 体系及生产问题审计，
> 形成 27+ 个生产场景的详细处理流程。

## 1. 统一决策状态机

```
Authenticated
  → ClientRateAllowed
  → BindingResolved (强/软/无绑定)
  → CandidateSelected (仅未绑定/重评估)
  → ProviderGatePassed
  → FPSlotAcquired / AcquireUntil
  → ConcurrencyAcquired / AcquireUntil
  → CircuitAllowed
  → UpstreamStarted
  → UpstreamSucceeded | UpstreamFailed
  → ResourcesReleased
  → BindingCreated/Kept/Invalidated
  → ResponseCached (新增)
```

每个转换携带 `request_id, session_id, std_model, credential_id, provider_id, raw_model, binding_level, attempt_index, reason, error_origin`。

## 2. 正常流程场景

### S1: 新会话首次成功

```go
输入: stdModel=gpt-4o, 无 route binding, 两个可用候选
流程:
  1. binding_miss → 加载候选 (DB → Redis 状态)
  2. 硬过滤: 不可用凭据/模型/节点移除
  3. CostScorer.Score: 价格 + 时延 + 稳定性 + 错误率 + 压力
  4. P2C 选两轮: 前 2 名随机选一 (概率加权)
  5. Provider Gate → FP Acquire → Conc Acquire → CB Allow
  6. Upstream Call → 200
  7. StateRecorder.Record(success)
  8. DetermineBindingLevel(req, resp)
     如果 cached_tokens > 0 → strong
     如果 prompt_tokens > 2000 → strong
     否则 → soft
  9. SessionRouteBinding.Create(level, cred, prov, rawModel, fpSlot)
  10. 如果成功响应且非重放 → cache 到 sessionResponseCache
输出: 200 + 响应 + X-Gw-Binding: {level, credential_id}
```

### S2: 已绑定会话连续成功

```go
输入: 已存在 binding(A, provider-A, raw-A)
流程:
  1. binding_hit → 只返回 A
  2. 不执行 P2C / 价格重排 / 协议亲和重排
  3. FP AcquireUntil(A 的 slot) → Conc AcquireUntil(A)
  4. CB Allow(provider-A) → Upstream
  5. 200 → 更新 binding.LastSuccessAt
  6. 更新 node + binding 状态
约束: 即使 B 更便宜或更快也不切换
```

### S3: 同一会话短请求

```go
输入: 无缓存, prompt < 阈值, 已有 binding
流程:
  1. binding_hit
  2. 检查 ShouldReEvaluate()
     - 距离上次评估 < 300s? → 不评估
     - 总请求 < 10 次? → 不评估
     - 连续成功 < 5? → 进入探索模式
     - 否则按成本劣化阈值判断
  3. 未触发: 保持 binding, 正常请求
  4. 触发: 进入软绑定重评估流程 (S18)
```

## 3. 限流场景

### S4: API Key RPM/TPM 超限

```go
顺序: Auth → RPM check → TPM check → 429
不执行: 路由 / FP / Concurrency / 上游调用 / 失败记录
释放: 若此前已 acquire key concurrency, 必须幂等 release
前端: 429 + X-RateLimit-* + Retry-After
Hook: auth_completed, rate_limit_checked, request_rejected
```

### S5: API Key 并发超限

```go
流程:
  Redis Lua 原子检查 key counter:
    local c = redis.call('INCR', key)
    if c > limit then
      redis.call('DECR', key)  -- 回滚
      return false
    end
    redis.call('EXPIRE', key, ttl)
    return true
  success: 持有 lease token, defer Release 时校验 token
  fail: 429, 不占用供应商资源
约束:
  Release 必须传 token, 不能只按 keyID 无条件 DECR
  同一 key 的每个并发请求持有独立 token
```

### S6: 客户端主动取消

```go
分类: context.Canceled / deadline exceeded
动作:
  1. 设置 error_origin=client
  2. 取消当前 upstream context (但 PendingStore 继续捕获)
  3. 释放 Conc / FP / Key 资源
  4. 不降低供应商健康度, 不触发 failover
  5. 不更新 binding (保持现有)
  6. 不上报 StateRecorder.Record(failure)
Hook: upstream_cancelled, resource_released, state_record_skipped
```

## 4. 供应商稳定性与自动切换

### S7: 供应商资源暂时不足

```go
输入: FP / Concurrency 获取失败
已绑定:
  → AcquireUntil(binding.cred, deadline)
  → 等待期间不尝试其他供应商
  → deadline 到 → 429/503 + X-Gw-Resource-Wait
未绑定:
  → 释放已获取的资源 (FP/Conc)
  → 尝试下一候选 (保留已获取的 CB 和 Provider Gate)
```

### S8: 供应商连接超时

```go
输入: 已发起 upstream 但连接超时 / 首字节超时
前提: 未向客户端输出任何响应内容
动作:
  1. 记录 KindTimeout, error_origin=upstream
  2. StateRecorder.Record(failure, kind=timeout)
  3. Circuit.RecordFailure
  4. 标记当前 binding 进入 failover 状态
  5. 释放旧资源 (Conc/FP/Key)
  6. 选择下一候选, 重新执行 (Phase 3)
  7. 成功后原子更新 binding
  8. 记录 route_change_reason=upstream_timeout
前端: 只收到最终成功响应 (切换透明)
```

### S9: 上游 5xx

```go
分类: KindConcurrent (503 overload) | KindUpstreamDown (500/502) |
       KindTransient (其他 5xx)

分级降级 (参见 05):
  Circuit 层面: open(30s) → half-open → 再失败 → 再 open
    → 半开失败 >= 3 次才允许 DB 降级
  DB 层面: cmb.available=FALSE + probe_pending
    → 健康检查器确认 (1h 窗口, >=80%, >=10 样本) 才写
  Credential 层面: 多个模型同时 broken → 凭据级降级

切换: 强绑定也切换 (已发生实际上游错误)
约束:
  1. 遵守 max_attempts (默认 3) + 总 deadline
  2. 客户端未收到内容才切换
  3. 切换后记录 route_change_reason=upstream_5xx
```

### S10: 上游 429 rate limit

```go
分类: KindRateLimit (普通配额 429) | KindConcurrent (429+overload body)
普通 429:
  1. 记录 retry_after 值
  2. 当前节点冷却 (30s 内不重投)
  3. 未输出内容 → 切换下一候选
  4. 不能视为凭据永久故障
  5. 已输出内容 → 返回 429 给客户端 (供应商限流)
供应商级 429:
  1. provider gate 降低可用权重
  2. 避免同供应商兄弟凭据同时冲击
```

### S11: 认证失败 / 凭据撤销

```go
分类: KindAuth / KindAuthRevoked
动作:
  1. 立即写 DB: cmb.available=FALSE, unavailable_reason=auth_failed
  2. breaker: 永久 open (不退半开)
  3. 清理 FP pin 和 session binding
  4. 记录 state_change + route_change_reason=credential_fatal
  5. 当前请求未输出响应 → 切换候选
后续请求: 永不尝试该凭据, 直到管理员恢复或探测确认
```

### S12: 配额耗尽

```go
永久 (KindQuotaPermanent / KindQuotaBalance):
  → credential fatal, 同 S11
周期 (KindQuotaPeriodic):
  → cmb.available=FALSE, unavailable_recover_at=now+冷却
  → 允许切换, 恢复后自动重入候选池
约束: 必须同步持久化 credential / model availability
      仅写 node Redis 不够
```

## 5. 客户端可见性边界

### S13: 非流式响应切换

```go
上游 A 未返回有效 body
  → B 重试 → B 返回 200
  → 客户端只收到一次完整响应 (B)
  → request_logs 保留 attempt A/B, route_change_reason 可审计
```

### S14: 流式响应首 token 前切换

```go
连接 / 首字节阶段失败:
  → 由 response writer / stream tracker 确认
  → response_started=false 且 first_replayable_event_sent=false
  → 可切换 B
  → B 返回流, 客户端无感知
```

### S15: 流式响应已输出部分 token

```go
A 已输出 SSE 事件后断流:
  → response_started=true 或 first_replayable_event_sent=true
  → 禁止透明切换到 B 并拼接
  → 记录 KindStreamTimeout, 结束当前响应
  → 返回错误 + 已输出内容 (客户端自行决定重试)
  → 若协议支持客户端续传, 由显式 retry 触发新路由
```

### S16: 内容过滤 / 客户端参数错误

```go
KindContentFilter:
  → 短路, 不换供应商
  → 相同输入会被同类策略拒绝
KindUnsupportedFeature / ToolCallIdMismatch:
  → 客户端或协议问题
  → 不惩罚凭据, 不切换, 不写状态
KindContextLength:
  → 执行一次专用 trim+retry
  → 不能把相同 oversized body 发给下一节点
```

## 6. 成本与评分场景

### S17: 首次选路

```go
硬过滤顺序:
  1. provider.IsAvailable()
  2. credential.IsAvailable()
  3. model.IsAvailable()
  4. node.IsAvailable() && !circuit_open
  5. 客户端 tier / 协议能力匹配
  6. model 上下文窗口匹配
  7. 供应商 gate (fp/conc 开关)

评分公式:
  score = w_price * price_score
        + w_latency * latency_score
        + w_stability * stability_score
        + w_error * (1 - error_rate)
        + w_pressure * (1 - resource_pressure)

约束:
  - 按预计 input/output tokens 计算成本, 非仅单价
  - 稳定性使用 EWMA/p95, 样本不足用 provider 先验
  - 错误率按类别分层, 客户端错误不计入
  - 缺失字段使用保守先验, 非零值
  - 只有未绑定 / 允许重评估的会话才使用评分排序
```

### S18: 软绑定成本重评估

```go
触发条件: ShouldReEvaluate() = true
  1. 距离上次评估 >= 300s
  2. 总请求 >= 10 或连续成功 < 5
  3. 满足以下任一:
     - 当前绑定 error_rate > 5%
     - 当前绑定 p95_latency 比最优 > 50%
     - 当前绑定 price 比最优 > 30%

流程:
  1. 加载所有候选
  2. CostScorer.Score (同 S17)
  3. 对比当前 binding vs 最优候选:
     - 当前仍最优 → 保持, 更新 LastEvalAt
     - 新候选更优 → 切换, 记录 route_change_reason=cost_optimization
  4. 切换时: 旧 binding 标记 invalidated, 新 binding 创建
```

### S19: 成本与稳定性冲突

```go
最低价候选不达稳定性硬门槛:
  → 不可选, 从候选池移除
  → 可靠性约束优先于价格排序
可用候选不足时:
  → 进入受控降级, 记录 cost_guardrail_blocked
  → 运维告警: 模型 X 候选池不足
```

## 7. 探测与恢复

### S20: 主动探测发现失败

```go
探测失败:
  → 更新 node/model health
  → 不直接改变 session binding
  → 已绑定会话只有实际请求失败才切换
  → 断路器已 open 时不重复探测
管理员禁用:
  → binding 立即失效
  → 返回可见错误 (route_reset 结果)
```

### S21: 探测确认恢复

```go
探测成功:
  1. 更新 model: broken_confirmed → active
  2. 更新 node: disabled_until → available
  3. 更新 circuit: open → half-open → close
  4. 不影响已绑定的强绑定会话
  5. 恢复节点进入候选池, 影响新会话和软绑定重评估
```

### S22: rawModel/价格/供应商开关变更

```go
新会话: 使用最新配置
存量强绑定:
  → 保持原 rawModel
  → 除非显式 route reset 或安全失效
存量软绑定:
  → 下一合法重评估点检查配置版本
  → 切换记录原因: config_changed
```

## 8. 基础设施故障

### S23: Redis / DB 故障

```go
Redis 故障 (只读):
  已绑定: 本地 TTL binding 快照继续使用
         无法确认资源所有权 → 503, 不随机换路由
  未绑定: 使用 provider cache / DB
         两者均不可用 → 503

Redis 故障 (写入):
  跳过状态写入 (fail-open)
  异步重试队列

DB 故障:
  已绑定: Redis session binding + node state 继续服务
  未绑定: 使用 model index (ursm:model:{stdModel})
          必须检查 binding/credential safety cache

恢复后:
  异步对账, 不在请求中强制改路由
```

## 9. 新增生产场景

### S24: 5xx 闪烁 (flash 5xx)

```go
条件: 供应商偶发 5xx, 每 5 分钟 1-2 次
当前问题: 2 次 → circuit open → half-open 成功 → close
         但健康检查器 1h 窗口仍保留失败记录
目标: 分级降级 (参见 05)
     断路器保护即时, DB 降级延迟确认
     健康检查器增加连续成功窗口:
       3 次成功恢复可清除窗口内失败记录
```

### S25: 供应商完全宕机 + 恢复

```go
条件: 供应商 500 持续 10 分钟, 然后恢复
流程:
  前 2 次: circuit open → half-open 再 fail → 再 open
  第 3 次 half-open 失败:
    → DB broken_confirmed (probe_pending)
    → 探测 worker 30s → 2m → 5m 指数退避
  恢复后: 探测成功 → 恢复 active
新增:
  provider 级 gate: 连续 3+ 模型 broken → 降低 provider 权重
```

### S26: 响应缓存回放

```go
条件: 客户端发送 "写一篇关于 AI 的文章"
  → 供应商 A 响应完整文章
  → 缓存到 sessionResponseCache (promptHash_1)
客户端重试 (同 prompt):
  → sessionResponseCache 命中 promptHash_1
  → 校验: TTL (默认 5 min) 未超
          rawModel 未变 (同一 binding)
  → 直接回放, X-Gw-Replay: true
客户端 "请继续":
  → promptHash 不同 (不同消息)
  → 正常路由
  → 若前一个请求在 PendingStore 中有完整响应
    → 可返回, X-Gw-Pending-Replay: true
```

### S27: 超时重试命中同一凭据

```go
条件:
  请求 R1 (requestID_1): 路由到 gpt-4o/openai, 60s 超时
  客户端取消, 发送 R2 (requestID_2, 相同 prompt)
当前问题:
  R2 可能重新路由到同一节点, 再超时 3 次 → 503
目标:
  R2 检测到:
    - 同一 sessionID, 同一 promptHash
    - 同一节点上一次超时记录 (circuit open)
  → 不浪费重试, 直接返回 503 + X-Gw-Retry-After: 30s
```

## 10. 场景验收矩阵

| 类别 | 场景 | 核心断言 |
|------|------|----------|
| 稳定 | S1/S2/S3 | 新会话正确选路, 绑定后保持, 短请求不频繁评估 |
| 限流 | S4/S5/S6/S7 | 客户端限流先执行, 释放幂等, cancel 不降低健康 |
| 切换 | S8/S9/S10/S11 | 上游错误可透明切换, 429 不能降级, auth 永久失效 |
| 安全 | S13/S14/S15/S16 | 首 token 前可切, 输出后禁止拼接, 内容过滤短路 |
| 成本 | S17/S18/S19 | 硬过滤先于评分, 稳定性优先于价格, 重评估受窗口约束 |
| 探测 | S20/S21/S22 | 探测不直接影响 binding, 恢复自动重入, 配置变更平滑 |
| 故障 | S23/S24/S25 | DB/Redis 降级有兜底, 5xx 分级降级, 宕机探测退避 |
| 缓存 | S26/S27 | 同 prompt 缓存回放, 超时记录避免重复重试 |
