# 分级降级与探测确认

> 解决"二次 5xx 就写 DB 降级"问题，实现分级确认、探测验证的降级机制。

## 1. 现有缺陷

### 1.1 降级链路 (现有)

```
5xx → ClassifyError → {KindUpstreamDown, KindConcurrent, KindTransient}
  → Circuit.RecordFailure: consecutive++
    → consecutive >= 2: Circuit OPEN (本地保护 30s)
      → shouldWriteCredentialStateOnConfirmedFailure:
        → cmb.available=FALSE, unavailable_recover_at=now+冷却
        → 冷却: KindUpstreamDown=60s, KindConcurrent=5min, KindTransient=30s
  → StateObserver.UpdateOnFailure:
    → transient consecutive >= 3: cmb.available=FALSE, +5min + probe
  → HealthTracker:
    → 滑动窗口 1h, >=80% 失败, >=5 样本 → 15min 冷却
```

**问题**: consecutive >= 2 就写 DB, 未等待探测确认。
供应商瞬时闪断会被持久化, 即使 30s 后断路器已恢复。

### 1.2 需要保护的场景

```
场景 A: 供应商偶发 500, 30s 后恢复
  断路器: open(30s) → half-open 成功 → close ✓
  DB: 已写入 cmb.available=FALSE, 60s 冷却
  → 冷却期内的请求被路由到备份凭据
  → 即使原凭据已恢复, 也要等冷却到期

场景 B: 供应商 500 持续 10 分钟
  断路器: open(30s) → half-open 失败 → 再 open(60s) → ...
  DB: 应降级, 通知运维, 启用探测

场景 C: 负载均衡器闪断 (1 次 502)
  断路器: consecutive=1, 不 open
  DB: 不应写任何降级
```

## 2. 分级降级方案

### 2.1 三级降级

```go
// Level 1: 断路器快速保护 (本地内存, 秒级)
//   2 次失败 → circuit open 30s → half-open → 探测 1 次
//   成功 → close (不写 DB, 不通知路由)
//   失败 → 重新 open, consecutive 累加
//   目标: 保护凭据不被瞬时错误淹没

// Level 2: 半开确认降级 (需多次探测失败)
//   断路器 open → half-open → fail → open → half-open → fail → open
//   half-open 连续失败 >= 3 次 → 允许写 DB
//   约束: 只在 halfOpenFailureCount >= 3 时写 DB
//   目标: 避免瞬时错误写 DB, 但持续错误仍能降级

// Level 3: 滑动窗口确认 (健康检查器, 分钟到小时级)
//   1h 滑动窗口, >=80% 失败率, >=10 样本
//   → 写入 cmb.available=FALSE, pending_recovery
//   → 调度主动探测
//   目标: 长时间故障的持久化降级
```

### 2.2 核心判断逻辑

```go
func shouldWriteDBDegradation(kind ErrorKind, circuit *Breaker, health *HealthTracker) bool {
    // KindQuota/KindAuth/KindModelNotFound: 立即写入
    if IsImmediatePersist(kind) {
        return true
    }

    // 瞬态类 (Timeout/Network/Transient/Concurrent/StreamTimeout):
    //   需要半开探测失败确认
    if IsTransientFamily(kind) {
        // 断路器层面: 半开失败 >= 3
        if circuit.HalfOpenFailureCount() >= 3 {
            return true
        }

        // 健康检查器层面: 滑动窗口确认
        if health.IsConfirmedUnhealthy() {
            return true
        }

        // 都不满足: 不写 DB
        return false
    }

    // 默认: 安全降级
    return true
}
```

### 2.3 断路器新增字段

```go
type Breaker struct {
    // 原有字段
    state        State           // closed / open / half_open
    consecutive  atomic.Int32    // 连续失败次数
    failCount    atomic.Int64    // 总失败次数

    // 新增
    halfOpenAttempts   atomic.Int32   // 半开状态下的尝试次数
    halfOpenFailures   atomic.Int32   // 半开状态下的失败次数
    lastTransitionAt   atomic.Int64   // 最后状态转换时间
}
```

### 2.4 半开状态增强

```go
func (b *Breaker) tryTransitionToHalfOpen() {
    if b.state.Load() != Open {
        return
    }
    now := time.Now()
    if now.Before(b.cooldownUntil.Load()) {
        return
    }

    // 转换到 half-open
    oldState := b.state.Swap(HalfOpen)
    if oldState == Open {
        b.halfOpenAttempts.Store(0)
        b.halfOpenFailures.Store(0)
        b.lastTransitionAt.Store(now.UnixNano())
    }
}

func (b *Breaker) RecordSuccess() {
    b.consecutive.Store(0)
    if b.state.Load() == HalfOpen {
        b.state.Store(Closed)
        b.halfOpenAttempts.Store(0)
        b.halfOpenFailures.Store(0)
    }
}

func (b *Breaker) RecordFailure(kind ErrorKind) {
    b.consecutive.Add(1)
    b.failCount.Add(1)

    if b.state.Load() == HalfOpen {
        b.halfOpenAttempts.Add(1)
        b.halfOpenFailures.Add(1)
        // 半开失败, 回到 open
        b.state.Store(Open)
        b.cooldownUntil.Store(time.Now().Add(b.backoff()))
    }

    if b.state.Load() == Closed && b.consecutive.Load() >= b.failureThreshold {
        b.state.Store(Open)
        b.cooldownUntil.Store(time.Now().Add(b.initialCooldown))
    }
}
```

## 3. 主动探测确认

### 3.1 触发时机

```go
// breaker.go: halfOpenFailureCount >= 3
//   触发 DB 降级 + 调度主动探测

// checker.go: 滑动窗口确认 unhealthy
//   触发 DB 降级 + 调度主动探测

// manager.go: 凭据状态管理器
//   consecutive >= 3 → 调度探测 + DB 降级
//   之前: 先降级再探测
//   之后: 探测 + 降级同时调度, 但降级写入等待探测确认
```

### 3.2 探测退避策略

```go
// 首次探测: 30s
// 重试 1: 2min
// 重试 2: 5min
// 重试 3: 10min
// 重试 4: 15min
// 最大探测次数: 5

// 探测成功: 清除降级, 恢复 active
// 探测全部失败: 维持降级, 等待健康检查器下一次窗口

// 瞬态中断保护: 如果 2s 内有请求成功, 跳过探测
```

### 3.3 恢复流程

```go
func (m *Manager) OnProbeSuccess(ctx context.Context, credentialID int, model string) error {
    // 1. 更新 model_state: broken_confirmed → active
    // 2. 更新 node_state: disabled_until → NULL
    // 3. 更新断路器: open → half-open → close
    // 4. 清理 cmb.available_recover_at
    // 5. 写入 ctx_submit(probe_success)
    // 6. 广播缓存失效
}
```

## 4. 健康检查器增强

### 4.1 滑动窗口增强

```go
type HealthChecker struct {
    window time.Duration // 1h
    minSamples int       // 10 (原先 5)
    failRatio  float64   // 0.8

    // 新增: 连续成功窗口
    consecutiveSuccessReset int // 3 次连续成功清除窗口记录
}

func (c *HealthChecker) RecordSuccess(credentialID int, model string) {
    // 记录成功
    // 检查连续成功次数
    // 如果连续成功 >= consecutiveSuccessReset:
    //   清除该凭据+模型的窗口失败记录
}

func (c *HealthChecker) IsConfirmedUnhealthy(credentialID int, model string) bool {
    // 1. 获取窗口统计
    // 2. 检查样本数 >= minSamples
    // 3. 检查失败率 >= failRatio
    // 4. 排除网络错误和客户端错误

```

### 4.2 凭据级级联

```go
// Provider 级 gate:
//   连续 3+ 模型 broken → provider gate 降低权重
//   新会话选路时, 该 provider 候选排在同等工作量的后面

// Credential 级级联:
//   同一 credential 的不同模型同时 broken
//   → credential 级降级 (credential_state.availability_state)
//   → 影响所有模型
```

## 5. 行为对比

| 场景 | 现有行为 | 新行为 |
|------|----------|--------|
| 偶发 5xx (1 次) | circuit open, 30s 恢复 | 同左 (断路保护) |
| 偶发 5xx (2 次) | circuit open + DB 降级 60s | circuit open, half-open 探测 |
| 持续 5xx (3+ 次) | circuit open + DB 降级 | circuit open + half-open fail >=3 → DB 降级 |
| 滑动窗口未确认 | N/A | 半开失败 < 3 不写 DB |
| 连续成功 3 次 | 不停清除失败记录 | 新: 清除窗口失败记录 |
