### 1.2 `9ea45f7f8` + `025e5d339` + `15d8b7518` — magpie P0-B/C/D 收口 — **合理**

**breaker × PenaltyOf**：`RecordFailure` 的短路前置由窄集 `IsClientBug` 放宽到

### 2. P2 — `MemoryProbeOneFlight.held` 无界增长（内存泄漏）

**位置**：`domains/streaming/executors/executor_probe_one_flight.go:52`

```go
m.held[model] = now.Add(ttl)   // 只覆写，从不删除
```

**键域**：`executor.go:2565` 传入的是 `params.ClientModel` —— **客户端可控字符串**。
不同 model 串各自留下一条**永不过期删除**的记录。

**触发条件**：Redis 缺席时。`cmd/gateway/main.go:1729-1732` 仅在 `fpSlotRedis != nil`

`probeOneFlight()` 的**默认路径**。噪声/恶意客户端发一批不存在的 model 名即可单调推高占用。

### 3. P2 — top-models hot 腿闸门（8d）越过 hot 留存（~7d），7~8d 窗静默少算

**位置**：`admin/logs.go:1312`

```go

```

**错配**：`session_turns_hot` 的实际留存是 **0–7 天**
（`docs/06-deployment/01-environments/deployment/database-migration-fix.md:128`
「`routing_decision_log_hot` — 热数据 (0-7天)」；`db/request_logs_view_schema.go` 里

**后果**：7~8d 窗在 hot 腿上查询已被留存清掉的日期 ⇒ 热门模型排行**静默少算那部分天数**，
不报错、不告警，读起来像「那几天没人用」。

**可达性**：非 default 租户被 `clampQueryWindowForTenant`（`admin/logs.go:1410-1415`）
夹到 72h，**踩不到**；唯一能踩进去的是 **`default` 租户**（只受 366d 上限约束）。

**已修复**：见 §三（闸门收到 `hotLegMaxWindow = 7d`，并把「宁可慢也不静默少算」的

### 4. P2 — 211 契约门只测「字符串在场」，结构上无法发现 P1

### 5. P2 — `session_online` 新查询与既有索引形状不匹配（未落地修，见 §四）

**位置**：`admin/session_online.go` 新查询 vs `db/session_summaries_schema.go:207-208`

新查询谓词/排序为 `tenant_id = $2 AND last_request_at >= $1 ORDER BY last_request_at DESC`，
而最接近的索引是 `idx_session_summaries_status_time (tenant_id, session_status, last_request_at DESC)`
—— **`session_status` 夹在中间且不被过滤** ⇒ 索引拿不到 `last_request_at` 的范围界，
也满足不了 ORDER BY，除非把该租户的行全读出来再排。

- 租户路径：能用 `tenant_id` 前缀，但要扫该租户全部行再过滤再排序。
- **超管路径（无租户过滤）：索引首列就是 `tenant_id`，前导用不上** ⇒ 全表扫 + 排序。

0.76ms 是单次采样；这条改动的动机恰恰是旧查询 52s 撞 5s 超时，
在会话数增长或超管视角下有重蹈覆辙的形状。

**本轮不落地的原因**：补索引要写迁移，而 `session_summaries` 行数未知，
非 `CONCURRENTLY` 的 `CREATE INDEX` 会持 ShareLock 阻断写入 ——
在未实测行数前盲发一条可能卡住启动的迁移，比留着这个问题更危险。
需先取行数与 EXPLAIN（见 §四 第 1 项）。
