```sql
SELECT COUNT(*) as total_feedback, COUNT(DISTINCT user_id) as unique_users,
       COUNT(DISTINCT task_type) as task_types, AVG(confidence) as avg_confidence
FROM routing_feedback_log WHERE created_at BETWEEN [窗口];
```

**实际结果**：

```

----------------|--------------|------------|----------------
      100       |      1       |     3      |     0.800
```

**分析**：
- ✅ 反馈行数与请求数 1:1 吻合（100 请求 → 100 行），证实"记录所有决策"口径
- ✅ task_type 分类正确：creative 50 / reasoning 34 / chat 16（与注入内容分布吻合）
- 批量异步刷盘（100 条阈值）在 30s 回放结束后 ≤10s 内全部落库

**反馈任务×provider 分布（实测）**：

## 8. 遗留问题与关键发现

### 8.1 【高】已部署构建（≤2054）的优化器钩子在 DecideV2 路径缺位

**现象**：2054 构建上优化器装配日志全部正常，但 108 次决策中钩子计数恒为 0、
零反馈行。**根因**：该构建里 P2.2 钩子（PreClassify/PostClassify/Recommend/
RecordFeedback）只接在 legacy `Decide`（decision.go）；运行时
`channel_quality_routing` 特性开关使 `DecideWithFeatureFlags` 全量走 `DecideV2`，
整体绕过钩子。**修复**：63ee0bde4（2026-09-08，已在 main）将钩子接入 DecideV2。
**影响**：任何"构建早于 63ee0bde4 且开启 V2 特性开关"的实例，P2.2 数据流静默失效。
**行动**：生产/预生产开启 ROUTING_OPT 前必须以含 63ee0bde4 的构建发布（本轮验证
即用该构建完成）。

### 8.2 【中】245 staging 拓扑无法承载 P2.2/数据流类验证

canary 槽位 `traffic-only` 角色不装配 autoroute/优化器；`llmgo-245.service`
（active 角色）自 08-31 dead，归属待运维决策。Track E 因此改在 154 旁路实例完成。
**建议**：运维补 245 active 角色实例，或正式确认"154 旁路实例"为 staging 验证的
标准载体（`llmgw-datagen` + 本轮 `p22-verify` 已两次使用该模式）。

### 8.3 【低】文档陷阱：大写 `"AUTO"` 不触发 decider

`autoRequestMagic="auto"` 为精确小写匹配，历史文档示例用 `"AUTO"` 导致请求静默
绕过 decider（503 no_candidate）。两份 P2.2 文档已随本报告修正（2026-09-08）。

### 8.4 【低】selections.success 结算滞后

`auto_route_selections_hot.success` 在决策写入时为初始值，实际成败由 SettleWorker
异步回填；验证窗口内观测到滞后。属既有 autoroute 管道行为，非本轮缺陷。

### 8.5 遥测清理

验证产生的 100 条反馈行（可精确识别：`request_id LIKE 'auto-113-%'` + 时间窗）
已在拆除后删除，`routing_feedback_log` 归零；selections 行交由既有 partition
lifecycle 轮转。

## A4. 关键发现

### F1【高·阻断灰度放量】成功路径 outcome 回填缺失——优化器反馈流≈纯失败样本

**现象**：120 条决策全部 stash（stashed=120），但只有 22 条（恰好 = 全部非 200 请求）被 `ReportRoutingOutcome` 回填落库（matched=22）；98 条成功请求的 stash 全部 TTL（10min）过期驱逐（expired 持续增长至 98），feedback 永不落行。聚合表因此全行 `successful_requests=0, accuracy_rate=0`。

**根因**：闭环回填（`autoroute/outcome_feedback.go`，09-08/09-09 audit 引入）设计上由请求终态统一上报；失败终态调用点 `domains/streaming/request_log_pipeline.go:1123` 正常工作，**成功终态调用点 `domains/streaming/handler.go:6173` 的门控 `reqLog.IsAutoRequest != nil && *reqLog.IsAutoRequest` 恒 false**——成功路径 reqLog 在 `handler.go:5525` 构造时从未赋值 IsAutoRequest（该标记只写在 logCtx 上，从不传递到成功终态 entry）。orphan=0 佐证成功路径从未发起上报（报了但不匹配会计 orphan）。

**影响**：10% 灰度下优化器只能学到失败样本（全负样本），adaptive learning/重训数据系统性偏置；也使本报告 §A3-1 的"ok 增长"封顶于失败数。

**行动**：放量前必须修——成功终态 entry 补 IsAutoRequest 透传（或改用 logCtx 判定）。本轮按验收边界未改代码。

### F2【中·运维】env 文件 60s DB 启动预算在老 systemd 下压过单元 Environment= → 首次启动 postgres disabled 静默降级

首轮部署用单元 `Environment=LLM_GATEWAY_DB_BOOT_RETRY_SECONDS=75s`，但 env 文件已有 `LLM_GATEWAY_DB_BOOT_RETRY_SECONDS=60s`（本机 systemd v219 中 EnvironmentFile 实际覆盖 Environment=）。共享 252 库争用下迁移耗时 ~59s（`session_summaries backfill chunk contended` pgcode=57014 可见），`09:39:03 WARN "postgres disabled" error="context deadline exceeded" retry_budget=1m0s` → dbConn=nil → **全部 DB 门控块静默跳过**：admin 路由不注册（/api/admin/* 404）、路由 executor 缺位（auto 503 executor_unavailable）、优化器/聚合器整体不装配——实例"健康"监听但全模式能力缺位。与 §8.1"装配日志正常 ≠ 钩子生效"互为镜像：**这次是"实例正常监听 ≠ 装配发生"**。修法（已采用，与 canary 模板同款权威做法）：ExecStart `/usr/bin/env LLM_GATEWAY_DB_BOOT_RETRY_SECONDS=180s` 确定性覆盖 + TimeoutStartSec=240s，重启后一次通过。建议运维把 env 文件该值直接上调。

### F3【低】共享 PG max_connections 瞬时耗尽致一次 sweep error

10:05:54（双实例冷启动窗口）8792 一次 sweep 失败：`SQLSTATE 53300 too many clients already`。瞬态资源竞争，非代码缺陷；事务内 advisory lock 保证的正确性未受影响（8791 同周期 ok）。旁路双实例 + 生产实例同时冷启动时需注意连接预算。

### F4【低·文档】metrics 端点鉴权为 JWT，ops 静态 key 401

`GET /api/admin/routing-opt/metrics` 走 admin JWT 中间件（`POST /api/auth/token` 换 access_token），`Authorization: Bearer $LLM_GATEWAY_ADMIN_API_KEY` 返回 401 authentication required。部署指南应注明该端点与 routing-opt 其余三端点一致的 JWT 鉴权口径。
