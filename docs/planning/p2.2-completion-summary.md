- 优先导出置信度 `[0.4, 0.6]` 区间样本（模型最不确定）
- 不足时回填 `< 0.4` 样本（错误更明显）
- 不导出 `> 0.6` 样本（模型已高度自信，标注价值低）

✅ **配额分配策略**
```go
// 伪代码逻辑
totalQuota := 1000  // 导出上限
taskTypes := ["general_qa", "code_gen", "translation", ...]

// 按任务类型均匀分配，避免偏斜
quotaPerType := totalQuota / len(taskTypes)

for each taskType {
  uncertainSamples := SELECT ... WHERE confidence BETWEEN 0.4 AND 0.6 LIMIT quotaPerType
  if len(uncertainSamples) < quotaPerType {
    lowConfSamples := SELECT ... WHERE confidence < 0.4 LIMIT (quotaPerType - len(uncertainSamples))
    samples = uncertainSamples + lowConfSamples
  }
}
```

✅ **隐私保护（红线）**
- **绝不导出** `prompt`、`messages`、`response` 字段
- 仅导出元数据：`request_id`, `user_id`, `task_type`, `selected_provider`, `model_confidence`, `latency_ms`, `success`

✅ **CLI 用法**
```bash
# 不确定性采样
llm-gw-annotator export --sampling uncertain --output ./uncertain_samples.csv

# 原有随机采样（兼容）
```

## 关键设计决策回顾

### 1. Redis 缓存策略

**决策**: 使用 Redis hash 存储用户亲和力，TTL 1 小时
**理由**:
- Hash 结构天然匹配 `task_type_distribution` 嵌套映射
- 1 小时 TTL 平衡缓存命中率与数据新鲜度
- 负缓存（30 秒）防止缓存穿透，但避免长期缓存 miss

**替代方案**:
- String + JSON 序列化：可行但性能略差，且无法原子更新部分字段
- 无 TTL + 手动失效：增加复杂度，缓存一致性难保证

### 2. 批量写入触发条件

**决策**: 满 100 条 **或** 每 5 秒
**理由**:
- 100 条：高流量下快速刷盘，减少内存积压
- 5 秒：低流量下避免数据丢失（如突然 shutdown）
- pgx.Batch 在 100 条时性能提升明显（单次往返 vs 100 次往返）

**风险缓解**:
- Channel 容量 10000（100 批），极端流量下丢弃而非阻塞路由
- `Flush(ctx)` 保证优雅关闭时零丢失

### 3. 主动学习置信度区间

**决策**: 优先 `[0.4, 0.6]`，不足时回填 `< 0.4`
**理由**:
- `[0.4, 0.6]`：模型最犹豫的区域，人工标注收益最大
- `< 0.4`：明显低信心，可能是边缘 case，标注价值中等
- `> 0.6`：模型已高度自信，标注价值低（资源浪费）

**实验依据**:
- 参考 Settles (2009) "Active Learning Literature Survey"
- 不确定性采样 (Uncertainty Sampling) 是主动学习经典策略

### 4. Admin API 设计原则

**决策**: 参考 `annotation_handler.go` 风格，保持代码风格一致
**理由**:
- 项目已有 Admin API 先例，复用相同的错误处理、认证模式
- 降低新代码维护成本，团队熟悉度高

**安全考量**:
- SQL 参数化查询（`$1`, `$2` 占位符）
- 参数边界验证（hours ∈ [1, 168]）
- 敏感端点（如修改参数）未在此阶段实现，留待 P2.3

## 性能影响评估

### 预期性能提升

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 亲和力查询延迟 (P99) | ~15ms (DB) | ~2ms (Redis 命中) | **87% ↓** |
| 反馈写入 DB 负载 | 100 次/100 请求 | 1 次/100 请求 | **99% ↓** |
| 路由端到端延迟 (P99) | ~50ms | ~40ms | **20% ↓** |

### 资源开销

| 资源 | 增量 | 说明 |
|------|------|------|
| Redis 内存 | ~100KB/1000 用户 | 每用户 ~100B (hash) |
| 后台 Goroutine | +1 个 | 批量写入 worker |
| DB 连接 | 不变 | 批量写入复用现有连接池 |

### 风险缓解

- **Redis 故障**: 自动降级到直查 DB，服务不中断
- **批量写入延迟**: 5 秒定时器保底，数据不积压
- **内存泄漏**: Channel 有界（10000），超出则丢弃

## 技术债务与优化空间

### 已识别技术债务

1. **Redis 连接池复用**
   - 当前状态: `fpSlotRedis` 客户端在 `main.go` 硬编码复用
   - 优化方向: 抽象 Redis 客户端工厂，支持多实例配置
   - 优先级: P2（当前方案可工作）

2. **批量写入失败重试**
   - 当前状态: 失败仅记录日志，不重试
   - 优化方向: 实现指数退避重试（最多 3 次），持久化失败到本地文件
   - 优先级: P1（Staging 验证后决定）

3. **Admin API 认证**
   - 当前状态: 无认证（依赖网络隔离）
   - 优化方向: 实现 API Key 或 JWT 认证
   - 优先级: P0（生产环境必须）

### 未来优化方向

1. **自适应 TTL**: 根据用户活跃度动态调整缓存 TTL
2. **批量写入自适应**: 根据流量动态调整批次大小和刷盘间隔
3. **主动学习策略**: 实现更多采样策略（如 Query-by-Committee）
4. **A/B 测试框架**: 抽象 A/B 逻辑，支持多维度实验
