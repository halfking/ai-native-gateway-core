# 供应商耗尽长时保活与持久恢复设计

> **文档编号**：18  
> **日期**：2026-08-14  
> **状态**：设计已确认，已完成 5 轮独立评审修订，等待最终人工门禁  
> **适用范围**：`/v1/chat/completions`、`/v1/responses`、`/v1/messages` 的流式请求，以及显式 durable 的非流式请求  
> **核心目标**：供应商临时限流、周期配额耗尽、并发耗尽、网络故障或暂无候选时，不立即中断可恢复任务；连接存活期间持续保活和重试，断连或网关重启后由持久任务继续执行，环境恢复后尽快完成。

---

## 1. 执行摘要

当前网关已经具备候选轮转、同凭据重试、同步探测、模型降级、SSE 预首包保活和进程内异步 pending，但这些能力尚未形成完整的“请求生存”闭环：

1. 预首包保活默认每 15 秒发送 SSE 注释。当前流式上游从 2026-08-04 起使用无 wall-clock deadline 的 `WithoutCancel + WithCancel`，配置中的 900 秒 `StreamTimeout` 不再构成整个流的绝对截止；真正生效的是 first-byte、chunk-idle、非流式 upstream timeout 和 Handler retry budget。请求生存协调器必须重新提供明确的绝对 survival deadline，并把剩余预算传给每个 attempt。
2. 候选耗尽后，预热流会写 SSE 错误并终止，而不是等待供应商恢复。
3. 流式预热后明确禁止切换到现有异步 pending。
4. 现有异步 pending 使用进程内 goroutine，网关重启后不能恢复。
5. `PendingStore` 只缓存状态和最终响应，不保存可重新执行的请求快照，也没有任务租约或 fencing token。
6. `request_wal_hot` 用于请求阶段审计，不是可领取、可调度的任务队列。
7. `KindQuotaPeriodic` 在凭据状态层被识别为可恢复周期配额，但不在通用 `errorsx.IsRetryable` 中；现有 Goal retry 还将其直接判为不可重试，语义存在分层不一致。
8. 客户端兼容性研究已经证明：未知 `event:` 搭配 `data:` 会触发部分严格客户端（例如 opencode）的 schema 校验失败，因此不能把任意 `thinking` 事件直接写入所有客户端。
9. 当前协议 bridge 并不都等到首个模型正文才写客户端：Responses 会预写 created/item/content-part 元数据，OpenAI→Anthropic 会预写 message/content-block/ping，部分 timeout 路径还会直接写终止错误。仅在协调器外层循环或增加写锁，不能实现透明重试。
10. 当前部分流式路径使用 `context.WithoutCancel` 并捕获 pending，实际断连语义并非简单的“非 durable 立即取消”；实施必须显式区分旧兼容捕获与新的 durable 任务所有权。
11. `pending.Store` 包级 fallback TTL 是 1 小时，但生产默认配置传入 300 秒；24 小时 durable 任务不能依赖当前固定 TTL。

本设计新增独立的 **Request Survival Coordinator（请求生存协调器）**，通过新的 `ExecuteAttempt` 模式调用现有 Executor 核心能力。`ExecuteAttempt` 是 survival 开启时唯一的外层重试入口：关闭 Handler Goal 外循环、旧 async fallback 和跨 attempt 递归，只保留一次 attempt 内部的候选轮转、凭据限流/熔断、协议转换和有界 failover。协调器统一管理：

- 协议安全的连接保活；
- 可恢复错误分类；
- 供应商提示优先的退避；
- 候选刷新和恢复探测；
- 断连接管；
- 数据库持久任务、租约和重启恢复；
- 最终结果写回现有 pending 查询入口；
- 租户级并发、预算和最长等待治理。

第一期只承诺 **首个语义内容输出前** 的透明恢复。供应商已输出部分正文后的纯文本续写与去重放在第二期；工具调用、JSON Schema、音频和未知协议帧不做盲目重放。

## 2. 目标与非目标

### 2.1 目标

1. 临时上游故障不立即向流式客户端返回终止错误。
2. 连接仍在时，通过不污染模型正文的帧维持代理、SDK 和客户端连接。
3. 可恢复故障按退避策略周期重试，恢复探测成功可提前唤醒。
4. durable 任务在客户端断连或网关进程重启后继续执行。
5. 多实例环境中，同一任务同一时刻最多由一个 worker 提交执行结果。
6. 环境恢复后重新解析候选，而不是复用故障发生时的陈旧候选快照。
7. 延用现有 session pending 查询入口，减少客户端迁移成本。
8. 所有等待、重试、接管、恢复、过期和终止状态可观测、可审计。
9. 永久故障、客户端错误和安全拒绝快速失败，不伪装成“仍在处理”。

### 2.2 非目标

1. 不在一期实现通用工作流引擎。
2. 不保证任意部分流式输出都可以无损续传。
3. 不暴露或伪造模型内部推理过程。
4. 不因提高成功率而无限消耗供应商费用。
5. 不通过 User-Agent 猜测客户端一定支持自定义结构化 SSE 事件。
6. 不改变普通非流式请求的同步 API 语义；只有显式 durable 非流式请求可以返回 `202`。

## 3. 现状代码映射

| 能力 | 当前实现 | 可复用点 | 当前缺口 |
|---|---|---|---|
| 预首包保活 | `domains/streaming/handler.go` 的 `preStreamKeepalive` | 初始注释、15 秒周期、写锁、暂停/恢复 | 生命周期绑定单个 HTTP 请求；耗尽后仍终止 |

| 协议 bridge | `stream.go`、`responses_bridge.go`、`anthropic_stream.go` | 三协议转换、捕获和流完整性 | 部分 bridge 在首正文前预写协议元数据或终止帧；必须先写 attempt-local sink，再由 commit gate 提交 |

| 结果缓存 | `pending.Store` | `(session_id, request_id)` 查询契约和最终响应缓存 | 包级 fallback TTL 1 小时、生产默认 300 秒；无请求快照、租约、fencing、CAS 或 DB 结果回源 |

| 客户端识别 | `telemetry.ExtractAgentName`、request identity | ZCode、Claude Code、Codex、Cursor、opencode 等识别 | 识别结果不能等同于协议能力声明 |

### 3.1 必须保留的已有行为

- 默认预首包 SSE 注释保活继续开启。
- opencode 等严格客户端不接收未知 `data:`。
- 现有执行器继续拥有候选选择、限流、熔断、凭据状态写入和模型降级职责。
- 永久配额、鉴权撤销、内容安全和客户端参数错误不进入长时重试。
- pending 查询接口继续按 session/request 返回 `in_progress/completed/failed`。

## 4. 方案比较与决策

### 4.1 方案 A：请求生存协调器（采用）

在 streaming HTTP 边界和现有 Executor 之间增加协调层。Executor 完成一次有界尝试，协调器决定成功、等待、重试、转持久任务或终止。

**优点**：职责隔离；复用现有路由；可渐进启用；便于单测状态机；能同时覆盖长连接和持久任务。  
**缺点**：需要新增任务存储、worker、协议渲染和装配代码。

### 4.2 方案 B：继续扩展 Handler/Executor（不采用）

直接在现有 Goal retry loop 和 Executor 耗尽分支加入长时循环。

**优点**：初始文件数量少。  
**缺点**：`handler.go` 和 `executor.go` 已承载协议、审计、路由、异步、错误渲染等职责；继续叠加会放大并发写、递归和重启恢复风险。

### 4.3 方案 C：完整工作流引擎（暂不采用）

所有 LLM 调用都立即事件化，由工作流 worker 驱动。

**优点**：任务恢复模型最统一。  
**缺点**：会改变同步 API 主链路，迁移范围过大，不符合本次最小闭环目标。

## 5. 总体架构

```text
Client
  │
  ▼
Chat / Responses / Messages Handler
  │  构建 SurvivalPolicy + ClientCapabilities
  ▼
Request Survival Coordinator
  ├── Protocol Keepalive Renderer ─────► HTTP SSE connection
  ├── Attempt Commit Gate
  │     ├── protocol-aware local buffer
  │     └── commit state: none/metadata/content/tool/terminal
  ├── ExecuteAttempt ──────────────────► existing Executor core
  ├── Task-level Outcome Aggregator
  ├── Retry Classifier / Backoff
  ├── Candidate Refresh / Probe Wakeup
  └── Durable Task Store ──────────────► PostgreSQL durable_llm_tasks
                                          │
                                          ▼
                                   Recovery Worker Pool
                                          │
                                          ├── lease + fencing token
                                          ├── rebuild versioned snapshot
                                          ├── execute bounded attempt
                                          └── commit DB result + project PendingStore
```

### 5.1 组件职责

#### SurvivalCoordinator

- 维护单个请求的生存状态机。
- 每次只发起一个有界 attempt。
- 只在首个语义内容未提交时透明替换 attempt。
- 计算下一次重试时间，并响应探测恢复唤醒。
- 连接断开时，根据 durable 策略决定取消还是持久化接管。
- 不直接实现候选排序、凭据限流或协议转换。

#### AttemptRunner / ExecuteAttempt

- 新增显式 `ExecuteAttempt(ctx, params, options)` 契约，而不是把完整 `Executor.Execute` 直接套进另一个重试循环。
- survival 模式下由协调器成为唯一外层重试所有者；关闭 Handler Goal retry、旧 `shouldAsyncFallback/startAsyncRetry` 和跨 attempt 的同步递归，避免嵌套重试、重复费用和重复状态写。
- 一次 attempt 内仍复用现有候选轮转、限流、熔断、凭据级 bounded retry 和安全的候选 failover。
- attempt context 必须真正绑定到内部 `http.Request` 和上游调用；不能只在 attempt 之间检查 deadline。
- 每次 attempt 重新调用 resolver 获取候选，不复用上次错误后的 candidate slice。
- 返回结构化 `AttemptResult`：全部 candidate outcomes、failure scope、Retry-After/recover-at、commit state、响应类型、最终错误和是否允许安全重试；禁止只用 `ExecuteError.LastKind` 决定任务终态。
- 后台执行时不持有原始 `http.ResponseWriter`。

#### AttemptCommitGate

- 每个 attempt 使用协议感知的本地缓冲 sink；bridge 在 commit 前不得触碰真实 writer，也不得直接生成客户端终止/完成帧。
- commit state 至少区分 `none`、`metadata`、`content`、`tool_call`、`terminal`；另将 metadata 分类为 `stable_connection_metadata` 和 `attempt_metadata`。
- Responses 中由网关生成、与具体 attempt 无关的固定 opening envelope 可以提升为 connection-level metadata 并只发送一次；包含供应商 message/response ID、model、usage 或其他 attempt 身份的帧必须留在 attempt buffer。
- Responses 的 attempt-specific created/item/content-part 元数据和 Anthropic 的 message/content-block 起始帧先进入本地缓冲；只有协调器决定提交该 attempt 后才一次性按原顺序写入真实连接。
- `none/metadata` 状态发生可恢复错误时可丢弃整个 attempt 缓冲并重试；`content/tool_call/terminal` 后由恢复安全策略决定，不允许从头拼接新响应。
- metadata 缓冲达到字节/时间上限时返回明确 `attempt_metadata_buffer_exceeded` 并安全阻断或更换未产生 metadata 的 attempt，禁止为了释放内存而强制 `Commit()`；首个 `content/tool_call/terminal` 才触发正常语义 commit。
- first-byte/chunk timeout 路径只返回结构化错误，不在 attempt 内写终止 SSE；最终错误由协调器在确定不再重试后按协议渲染。

#### KeepaliveRenderer

- 根据 API 协议和显式 capabilities 输出保活/状态。
- 所有写操作串行化，禁止 keepalive goroutine 与真实流并发写 ResponseWriter。
- 区分“传输保活”和“可见状态”；保活不进入模型内容、token、审计正文或 pending 最终结果。

#### DurableTaskStore

- 保存可恢复执行所需的最小请求快照和策略。
- 提供创建、状态迁移、到期任务领取、续租、完成和失败操作。
- 所有状态更新校验 fencing token，拒绝过期 worker 提交结果。

#### RecoveryWorker

- 定时领取 `waiting_recovery/retry_scheduled` 且已到重试时间的任务。
- 重建内部请求，重新解析候选并执行一次有界 attempt。
- 成功时先在 fencing 校验的 PostgreSQL 事务内提交终态、规范化结果或不可变对象引用及结果 hash/version；事务成功后再幂等投影 PendingStore。失败则重新调度或终止。
- 网关优雅停机时停止领取，允许租约自然到期被其他实例接管。

## 6. 请求分层启用策略

### 6.1 所有流式请求

默认获得：

- 预首包协议安全保活；
- 连接内短时可恢复重试；
- 普通交互最大等待默认 30 分钟；
- 客户端断连后默认取消，除非满足 durable 条件。

### 6.2 durable 请求

#### 显式启用

- 流式请求：必须显式 `X-Gw-Durable: true`，并且 API key/application/tenant 策略允许 durable。
- 非流式请求：除上述条件外，还必须声明 `X-Gw-Capabilities: durable-recovery` 或标准 `Prefer: respond-async`；否则不得把标准 200 响应自动改成自定义 `202`。
- 后续可以提供独立 async endpoint，避免官方 SDK 把原 endpoint 的 `202 in_progress` 当标准成功对象解析。

#### 可信身份与 session

- `User-Agent`、`X-Agent-Name` 和普通客户端 header 都可伪造，只用于观测，不构成 durable 授权。
- “trusted agent”必须来自服务端验证后的 API key/application/tenant 策略或由受信任入口签名的内部声明。
- Handler 自动生成的 provisional `X-Gw-Session-Id` 不等于可恢复 session。durable 前必须确认 session 已持久化、归属当前 tenant/API key，且 pending 查询鉴权可以读取该 session。
- 保存 `session_source`（client_persisted/server_persisted/provisional）；`provisional` 禁止创建 durable 任务。
- 第一期不按“识别到 agent + session”自动开启 durable；自动策略必须等显式握手、真实 session 和权限模型上线后另行灰度。

获得额外能力：

- 任务执行前持久化快照；
- 客户端断连后继续；
- 网关重启后恢复；
- 默认最长等待 24 小时；
- 可通过现有 pending endpoint 查询最终结果。

### 6.3 能力协商

自定义状态事件只在显式声明时启用：

```http
X-Gw-Capabilities: status-events,durable-recovery
```

客户端识别用于产品策略提示和观测，不替代 capabilities 或 durable 授权。未知或未声明客户端一律使用安全 SSE 注释；非流式客户端未声明 `durable-recovery`/`respond-async` 时一律保持同步终态语义。

## 7. 状态机

```text
accepted
   │
   ▼
running ───────────────► streaming ─────────────► completed
   │                         │
   │ recoverable            │ partial interruption
   ▼                         ▼
waiting_recovery       resume_safety_blocked (terminal)
   │
   │ due / probe wakeup / capacity available
   ▼
retry_scheduled ───────► running
   │
   ├── deadline exceeded ─────────────► expired
   ├── explicit cancel ───────────────► cancelled
   └── task-scope permanent error ────► permanent_failed

connection_attached: true/false   # orthogonal attribute, not scheduler status
```

### 7.1 终态

- `completed`：结果完成并可读取。
- `permanent_failed`：永久错误，继续等待没有意义。
- `expired`：超过任务最大等待时间或预算。
- `cancelled`：客户端/管理员显式取消。
- `resume_safety_blocked`：部分输出或 write-ahead checkpoint 后无法安全自动重放的不可领取终态；可由客户端/管理员发起新的显式 continuation 任务，但原任务不再自动执行。

`detached` 不作为任务状态。连接是否附着由 `connection_attached/last_disconnect_at` 表示，durable 调度不因连接断开停止。`waiting_capacity` 也不单独持久为不可领取状态：资源不足时保持 `retry_scheduled` 并设置短 `next_retry_at`，容量通知可提前唤醒。

### 7.2 不变量

1. 一个任务只有一个终态。
2. 终态不可退回执行态。
3. 同一个 fencing token 只能完成一次状态提交；任务终态与最终结果（正文或不可变对象引用、hash、version）必须在同一 PostgreSQL 事务中提交。
4. Redis PendingStore 只是终态事务后的幂等投影，不能成为 fencing 决策点，也不能由过期 worker 无条件覆盖。
5. 没有 durable 任务记录，不允许在客户端断连后启动新的供应商 attempt；现有 `WithoutCancel`/PendingCapturer 兼容行为必须按 feature flag 单独分流，不能暗中获得 durable 语义。
6. 首个语义内容提交后，不允许将新的完整响应从头拼接到客户端。
7. keepalive/status 帧不改变 `semantic_content_committed`。
8. provisional session、未声明 durable capability 的非流式请求和未通过租户授权的请求不得创建 durable 任务。
9. durable 流首次准备向客户端提交 `content/tool_call/terminal` 前，必须先用当前 fencing token 持久化 write-ahead commit checkpoint；DB 成功后才允许网络写。
10. DB checkpoint 成功但网络写失败时，任务保守进入 `resume_safety_blocked`，不得从头重放；这优先保证无重复工具副作用。

## 8. 错误分类和重试策略

### 8.1 任务级聚合分类器

任务动作不能直接由 `ExecuteError.LastKind` 决定。`LastKind` 会保留诊断优先级较高的凭据 fatal 错误，但不代表整个 canonical model、其他 offer 或整个任务永久不可恢复。

聚合分类器输入：

- 本 attempt 全部 candidate outcomes，而不是最后一个错误；
- error kind、failure scope、HTTP 状态和原始恢复提示；
- `Retry-After`、credential `recover_at`、probe `next_retry_at`；
- 当前是否仍存在其他 provider/model offer；
- commit state 和 response safety class；
- deadline、attempt、租户预算和取消状态。

输出 `TaskAction`：`complete`、`retry_at`、`wait_probe`、`fail_permanent`、`expire`、`cancel` 或 `safety_block`。所有 `errorsx.ErrorKind` 必须在表驱动测试中穷举，新 kind 未映射时默认 fail closed 并告警。

### 8.2 任务级可恢复错误

| ErrorKind / 场景 | 任务动作 | 说明 |
|---|---|---|
| `KindRateLimit` | 等待并重试 | 优先 `Retry-After` |
| `KindQuotaPeriodic` | 等待窗口恢复 | 对当前凭据可 fatal，但对整个任务可恢复 |
| `KindConcurrent` | 短退避重试 | 可切换凭据/供应商 |
| `KindUpstreamOverloaded` | 短退避重试 | 不永久熔断任务 |
| `KindTransient` / `KindNetwork` | 退避重试 | 触发候选刷新或探测 |
| `KindTimeout` / `KindStreamTimeout` | 退避重试 | 仅首语义内容前透明重试 |
| `KindUpstreamDown` | 探测 + 重试 | 恢复事件可提前唤醒 |
| `KindEmptyResponse` | 首内容前刷新候选并有限重试 | 不把空流终止帧提交给客户端 |
| `KindNoAvailableChannel` | 按 binding 冷却/探测重试 | 服从现有 15 分钟模型级冷却 |
| 暂无候选 | 周期刷新候选 | 聚合 no-candidate 原因，不复用旧 candidate slice |
| 供应商 5xx | 按分类重试 | 保留原始错误用于审计 |

### 8.3 candidate/binding 永久排除与任务终止

以下 kind 首先作用于 **candidate/credential/binding scope**，不等于任务立即失败：

- `KindAuth`、`KindAuthRevoked`；
- `KindQuota`、`KindQuotaPermanent`、`KindQuotaBalance`；
- `KindQuotaPeriodic` 在对应恢复时间前临时排除该 credential。

聚合器应先排除/冷却对应 candidate，再检查是否存在其他允许的 credential/provider/model offer。只有全部允许 offer 均已永久排除、且没有合法 fallback 时，任务才进入 `permanent_failed`。

以下错误属于 request/content/safety scope，在现有专用补救（例如一次 context trim）仍失败后可直接终止任务：

- `KindContextLength`；
- `KindContentFilter`；
- `KindModelDeprecated` 且不存在其他有效 offer；
- `KindUnsupportedFeature`；
- `KindToolCallIdMismatch`；
- `KindConversion`、明确的 `KindClientBug` 及无法安全重建的协议错误；
- 明确的客户端取消、参数校验失败和租户预算拒绝。

`KindModelNotFound` 是否继续取决于是否存在同 canonical model 的其他 offer；全部 binding 均永久缺失时终止，否则允许刷新候选后有限重试。

`KindUpstreamContextLoss` 必须结合 commit state：首语义内容前且无工具/结构化副作用时可按质量故障切换 candidate；语义内容后进入 `safety_block`/质量失败，禁止透明从头重放。

任务分类表必须为每个 ErrorKind 固化 `failure_scope + candidate_action + task_terminal_condition + retry_hint_source`。

### 8.4 重试延迟

恢复时间分为三类，不能把已知长期冷却压成每 5 分钟一次供应商调用：

1. **authoritative eligibility time**：上游 `Retry-After`/reset、credential `recover_at` 或明确 probe `next_retry_at`。在该时间前对应 candidate 禁止供应商 attempt；`next_retry_at` 直接取权威时间，若晚于任务 deadline 则任务过期或尝试其他 offer。
2. **probe/recheck cadence**：最长 5 分钟，可刷新 DB/路由/探测状态，但不得调用仍处于权威冷却期的 candidate。
3. **fallback exponential delay**：仅在没有权威恢复时间时使用 `base * 2^attempt` 和 ±20% jitter，单次上限 5 分钟。

提示优先级：

1. 上游 `Retry-After` / rate-limit reset 时间；
2. 凭据状态中的 `recover_at`；
3. 探测系统给出的 `next_retry_at`；
4. 指数退避：`base * 2^attempt`，附加 ±20% jitter。

默认边界：

- 最小等待 1 秒；
- 普通临时错误 base 2 秒；
- 并发/过载 base 5 秒；
- 最大 fallback 退避 5 分钟；权威 eligibility time 不截断；
- 探测恢复事件可立即唤醒并重新评估 eligibility；
- 单次供应商 attempt 受 first-byte、chunk-idle、非流式 upstream timeout 和协调器剩余 survival budget 共同约束；现有流式 900 秒配置不是绝对 wall-clock deadline。

### 8.5 防止重试风暴

- 同一 `(tenant, model, failure_scope)` 的恢复事件做去重广播。
- worker 领取任务时施加租户并发上限。
- jitter 以任务 ID 为稳定种子，避免实例重启后所有任务同时归零重试。
- 同一供应商持续失败时服从现有 circuit/credential state，不绕过冷却硬打。

## 9. 客户端协议行为

### 9.1 默认安全模式

OpenAI Chat、OpenAI Responses 和 Anthropic SSE 均发送 SSE 注释：

```text
: keep-alive

: gateway-status: waiting_for_provider

```

注释满足：

- SSE parser 不触发 `onmessage`；
- 不进入 OpenAI/Anthropic 数据 schema；
- 不产生 choices/content block；
- 不进入模型正文和 token 计费；
- 可穿透禁用 buffering 的反向代理。

### 9.2 显式状态事件模式

只有请求声明 `status-events` 时，按客户端协议发送结构化网关事件。事件必须有独立 gateway namespace，不能伪装为模型 thinking 内容。

建议逻辑字段：

```json
{
  "type": "gateway.status",
  "state": "waiting_recovery",
  "reason": "provider_quota_periodic",
  "attempt": 3,
  "next_retry_at": "2026-08-14T12:00:00Z",
  "task_id": "..."
}
```

一期可以只实现注释模式和能力解析，结构化事件在兼容性矩阵通过后逐协议开放。

### 9.3 写并发

现有 `preStreamKeepalive` 仅保护自身写入，真实 stream writer 不共享同一把锁；同时，仅串行化写还不足以实现透明重试，因为 bridge 会在首正文前预写协议元数据。实施时需要两层写控制：

1. `AttemptCommitGate`：bridge 先写 attempt-local buffer，记录 commit state；协调器决定提交前，真实连接只接收 keepalive/status 注释。
2. `SerializedStreamWriter`：一旦 attempt 提交，keepalive、状态帧和协议 bridge 共用一条串行写通道。

具体要求：

- keepalive、状态帧、协议 bridge 共用一条串行写通道；
- `OnStreamReady` 不再等同于“已经提交给客户端”；只有 commit gate 的 `Commit()` 才能切换真实 writer。
- first-byte timeout、空流和可恢复 stream error 在 commit 前只能返回结构化 outcome，禁止 bridge 自行写 error/[DONE]/message_stop。
- attempt commit 后停止“等待供应商”状态；连接级空闲保活是否继续由协议策略决定；
- 写失败标记连接 detached，不再继续碰 `ResponseWriter`；
- 后台任务使用 capture/sink，不持有 HTTP writer。

### 9.4 非流式 durable `202` 线协议

Phase 0 冻结以下契约：

- capability token 大小写不敏感，按逗号拆分、trim、去重；未知 token 忽略并记录。
- `Prefer` 按 RFC 风格 token 解析；接受 `respond-async` 时返回 `Preference-Applied: respond-async`。
- 返回 `202 Accepted`、`Location: /v1/sessions/{session_id}/pending-response?request_id={request_id}`、`Retry-After`、`X-Gw-Pending`、`X-Gw-Pending-Request`、`X-Gw-Task-Id`。
- 三 endpoint 共用 gateway async envelope，不伪装成标准 Chat/Responses/Anthropic 成功对象：

```json
{
  "status": "in_progress",
  "task_id": "...",
  "session_id": "...",
  "request_id": "...",
  "retry_after": 5,
  "poll_url": "/v1/sessions/.../pending-response?request_id=..."
}
```

- pending `in_progress` 返回 202 和同一 envelope；`completed` 返回 200、原请求协议的 `Content-Type` 和原始规范化正文；`failed/expired/cancelled/safety_blocked` 返回明确 gateway error envelope 和稳定 code。
- DB 回源或对象存储取回必须保持原 `Content-Type`，校验 result hash，且继续执行 tenant/API key/session 归属鉴权。

## 10. 部分流恢复安全策略

### 10.1 一期：首个语义内容前

以下数据不算语义内容：

- SSE 注释；
- gateway status；
- 协议起始元数据且尚未向客户端提交模型正文的内部缓冲。

在 `commit_state` 为 `none` 或仅 `metadata` 且尚未执行 `Commit()` 时，上游失败可丢弃本 attempt 缓冲并透明重试。不能用现有 `StreamOutcome.ChunkCount` 推断该状态；必须由协议 bridge 显式标记 metadata/content/tool/terminal。

### 10.2 二期：纯文本续写

仅在同时满足以下条件时启用：

- 响应只有纯文本；
- 没有 tool call、JSON schema、音频、图片或未知帧；
- 已记录稳定输出前缀和 checksum；
- continuation prompt 明确要求从前缀后继续；
- 输出经过前缀重叠去重；
- 续写失败可回退为 pending 结果，不重复发送已提交内容。

### 10.3 禁止自动重放

- 已向客户端发送 tool call；
- 已执行或可能执行有副作用工具；
- strict JSON schema / response_format；
- 音频或二进制流；
- 无法确认边界的跨协议帧；
- 已发送 finish_reason 后出现异常。

这些场景记录 `resume_safety_blocked`，不以“提高完成率”为由制造重复副作用。

## 11. 持久任务数据设计

### 11.1 新表而不是直接扩展 request_wal

新增 `durable_llm_tasks`。原因：

- `request_wal_hot` 是请求审计 SSoT，生命周期和归档策略与任务调度不同；
- claim/lease 需要高频状态更新、`FOR UPDATE SKIP LOCKED` 和专用索引；
- 任务快照包含敏感请求内容，需要单独加密、保留和访问控制；
- 避免把现有 WAL 查询和分区晋升流程变成调度热表。

建议字段：

| 字段 | 用途 |
|---|---|
| `id` UUID | 任务 ID |
| `tenant_id` | RLS 与配额维度 |
| `request_id` / `session_id` | 现有链路关联 |
| `protocol` / `endpoint` | 重建内部请求 |
| `request_snapshot_ciphertext` | 使用 durable 专用 AAD 加密的版本化 DTO |
| `snapshot_version` / `encryption_key_id` | 快照 schema 与实际密钥版本 |
| `request_hash` | 幂等与防篡改（durable AAD 的一部分） |
| `status` | 状态机 |
| `error_kind` / `reason_code` | 最近失败 |
| `attempt_count` | 总 attempt 数 |
| `next_retry_at` | 调度时间 |
| `deadline_at` | 最长等待截止 |
| `lease_owner` / `lease_until` | worker 租约 |
| `fencing_token` BIGINT | 防止过期 worker 提交 |
| `semantic_content_committed` BOOLEAN NOT NULL DEFAULT FALSE | 是否已形成语义提交 |
| `commit_state` TEXT NOT NULL DEFAULT 'none' | 恢复安全门禁，CHECK 限定 `none/metadata/content/tool_call/terminal` |
| `result_ciphertext` / `result_object_ref` | 加密后的规范化最终结果，或服务端加密的不可变对象引用 |
| `result_hash` / `result_version` / `content_type` | 原子终态与缓存投影版本 |
| `policy` JSONB | 固化请求创建时策略 |
| `created_at` / `updated_at` / `completed_at` | 审计时间 |

索引至少包括：

- `(status, next_retry_at)` partial index for runnable states；
- `(tenant_id, status)`；
- unique `(tenant_id, request_id)`；
- lease expiration index；
- schema 约束：`commit_state TEXT NOT NULL DEFAULT 'none'`，`CHECK (commit_state IN ('none','metadata','content','tool_call','terminal'))`；
- 如迁移作用于已存在试验表，先把历史 NULL 回填为 `none` 再添加 NOT NULL/CHECK。

### 11.2 快照切点、版本与安全

快照切点位于 Handler 完成鉴权、session 归属校验、`tool_ids` 展开和请求规范化之后，但在候选解析和供应商执行之前。定义版本化 `DurableRequestSnapshotV1`：

**必须冻结**：endpoint、client protocol/model、规范化 body 及 hash、API key ID、tenant/application、真实 session ID 与 source、client identity 的安全派生字段、tool/response-format/多模态安全标记、durable/survival policy 版本、原始 request/task correlation ID。

**恢复时重算**：provider candidates、credential、circuit/limiter 状态、模型 offer、Retry-After/recover-at 和动态路由分数。禁止持久化并复用旧候选。

安全要求：

- 剔除 Authorization、Cookie、转发 IP 和内部临时 header。
- API key 明文不落快照；worker 使用 `api_key_id` 重新验证服务端授权上下文，失效则永久终止。
- 新增 domain-separated `EncryptWithAAD/DecryptWithAAD` 安全 API，并返回实际 `key_id`；现有固定 `llm-gateway:credential` AAD 的 API 不可直接用于 durable 数据。
- durable snapshot 与 result 使用不同 AAD domain，例如 `llm-gateway:durable-request:v1`、`llm-gateway:durable-result:v1`，并绑定 tenant/task/request hash。
- envelope 记录 `snapshot_version`、`encryption_key_id`；无密钥、未知版本、AAD/hash 不匹配或数据库不可用时 fail closed，不声称已接管。
- 最终结果与请求同级敏感：数据库保存 `result_ciphertext`；若使用对象存储则必须服务端加密，DB 保存不可变 ref/hash/version。查询 endpoint 服务端取回并校验 hash 后返回原始正文，不能把对象引用直接暴露为响应正文。
- 任务表启用 tenant RLS；worker 使用受控服务角色。
- 快照保留时间默认覆盖 deadline，终态结果读取窗口结束后清理或脱敏归档。

### 11.3 创建、领取与 fencing

#### 首次前台执行：CreateAndClaim

前台 Handler/Coordinator 与后台 RecoveryWorker 使用完全相同的 lease holder 语义。durable 请求开始首次 attempt 前，必须在一个 PostgreSQL 事务中：

1. 插入加密快照和任务元数据；
2. 设置 `status='running'`；
3. 设置 `lease_owner=<gateway-instance/request>`、`lease_until`；
4. 设置初始 `fencing_token=1`；
5. 显式设置 `commit_state='none'`、`semantic_content_committed=false`；
6. 写 accepted→running append-only event。

事务提交成功后，前台 Coordinator 才能调用 `ExecuteAttempt`，其 checkpoint、续租、重排和终态提交全部携带该 owner/token。若产品选择“创建后直接后台执行”，则只创建 `retry_scheduled`，Handler 不得同时调用 attempt，统一由 worker claim。不存在“先创建 waiting、前台无租约执行”的中间模式。

创建事务提交后 Handler 崩溃时，任务保持 `running`；租约过期后按下面的 commit-state reclaim 规则处理。创建事务失败时不得发送 durable 已接管状态或启动供应商调用。

#### 后台领取与过期租约回收

普通 execution claim 必须在事务内完成：

```sql
SELECT id
FROM durable_llm_tasks
WHERE commit_state IN ('none', 'metadata')
  AND status IN ('waiting_recovery', 'retry_scheduled', 'running')
  AND (status <> 'running' OR lease_until < now())
  AND next_retry_at <= now()
  AND deadline_at > now()
  AND (lease_until IS NULL OR lease_until < now())
ORDER BY next_retry_at
FOR UPDATE SKIP LOCKED
LIMIT $batch;
```

同一事务更新：

- `status='running'`；
- `lease_owner`；
- `lease_until`；
- `fencing_token=fencing_token+1`。

`commit_state IN ('none','metadata')` 是所有普通 execution claim 的全局数据库门禁，不依赖 status 分支。对任意非终态且 `commit_state IN ('content','tool_call','terminal')` 的任务，reaper 必须在事务中以行锁/fencing 原子迁移到 `resume_safety_blocked`（或未来专用 reconciliation 状态），绝不进入 `ExecuteAttempt`。原因是现阶段没有供应商流 cursor，无法证明 checkpoint 后网络帧是否成功送达，也无法无副作用续接。

所有 reschedule/retry transition SQL 同样必须包含 `AND commit_state IN ('none','metadata')`。语义 checkpoint SQL 在一个事务中原子设置 `commit_state`，并保持 `status='running'` 或直接形成终态；一旦进入 `content/tool_call/terminal`，数据库 transition 函数/约束禁止迁移到 `waiting_recovery`、`retry_scheduled` 或其他 runnable status。即使应用错误地尝试重排，claim 仍因全局 commit_state 门禁拒绝领取。

必须测试：

- `CreateAndClaim` 提交后、首次 attempt 前 Handler 崩溃；
- 前台创建/首次执行与 worker 并发；
- worker 在 claim 后、首次续租前、语义 checkpoint 前崩溃（可重领）；
- checkpoint 后、网络写前/后、状态更新前崩溃（均安全阻断，不重新执行）；
- 最终提交前崩溃。

完成/重排更新必须携带 `(id, lease_owner, fencing_token)` 条件；重排到 runnable 状态还必须携带 `commit_state IN ('none','metadata')`。更新行数为 0 表示租约已失效或任务已产生语义 checkpoint，旧 worker 不得写 PendingStore 最终结果或继续执行。

#### durable 流 write-ahead commit

`none/metadata` 可只留 attempt 内存。首次准备提交 `content/tool_call/terminal` 时必须：

1. 以 `(task_id, lease_owner, fencing_token)` 在 PostgreSQL 写 `commit_state` checkpoint；
2. `tool_call` checkpoint 同时保存 tool call ID、类型、序号和参数摘要/hash，足以阻止崩溃后的不安全重放；
3. DB 提交成功后，才允许 `SerializedStreamWriter` 向客户端写对应语义帧；
4. DB checkpoint 失败，不得写网络，任务重新调度或明确失败；
5. DB 已 checkpoint 但网络写失败，原任务进入 `resume_safety_blocked`，不从头重放。

该顺序会在极端崩溃点保守地少发一次内容，但不会重复发送可能触发副作用的 tool call。

成功终态必须在同一 PostgreSQL 事务内写入：`status=completed`、加密后的最终结果或服务端加密的不可变对象引用、`result_hash`、`result_version`、content type、完成时间和 attempt 统计。事务提交后才允许投影 Redis。失败、过期和取消同样由带 fencing 条件的事务形成唯一终态。

#### deadline reaper

独立 deadline reaper 扫描所有非终态且 `deadline_at <= now()` 的任务，包括 `waiting_recovery`、`retry_scheduled`、崩溃后的 `running none/metadata`，以及权威 `recover_at` 晚于 deadline 的任务。

- 使用事务、行锁和当前状态条件原子迁移为 `expired`。
- 若任务仍有有效 lease，事务先递增 fencing token/撤销 lease，并通过实例内取消通道终止 attempt；旧 worker 后续完成更新因 token 失效而失败。
- 同一事务写 `reason=survival_expired`、`completed_at`、结果版本、append-only transition 和 PendingStore outbox。
- PendingStore 投影为 `failed`，稳定 error code 为 `survival_expired`；查询不会永久停留 `in_progress`。
- deadline reaper 与 worker 完成并发时，只有先取得行锁并成功校验 fencing 的一方形成终态，另一方更新 0 行并丢弃结果。

### 11.4 PendingStore 投影协议

- Redis value 携带 `task_id`、`fencing_token`、`result_version` 和 `result_hash`。
- 投影使用 Lua/CAS：只有不存在，或新 `result_version` 不小于现有版本且 task ID 相同，才能覆盖。
- PostgreSQL 已完成但 Redis 写入失败时，由 outbox/repair worker 重试投影；查询接口可直接回源 DB，不会出现“任务完成但结果永久丢失”。
- 过期 worker 即使仍持有结果字节，也因 DB fencing 更新失败而没有可投影版本，必须丢弃。

## 12. 与 PendingStore 和 WAL 的关系

### 12.1 PendingStore

继续作为客户端读取结果的兼容层：

- 任务创建后写 `in_progress`；
- 成功写 `completed + body`；
- 永久失败/过期/取消写 `failed + reason`；
- 增加 `task_id`、`next_retry_at`、`attempt_count`、`durable` 等可选字段；
- durable 任务按任务 `expires_at = deadline + result_read_window` 设置 TTL，不能沿用生产默认 300 秒或包级 fallback 1 小时；
- 投影必须遵守 §11.4 的 task/version CAS。

PostgreSQL 任务表是任务状态和最终结果 SSoT，Redis 是查询加速投影。Redis 丢失时，查询接口从任务表返回状态与规范化结果/对象引用；大响应可存不可变对象存储并在 DB 保存 hash/reference，不能只在 Redis 留唯一正文。

### 12.2 Request WAL / request_logs / transition event

- `request_wal_hot` 的 `stage` 当前是 smallint 单值阶段，不适合承载完整可逆任务生命周期；不能直接写 `survival_waiting` 等字符串。
- 原始逻辑 request 在协调器尚未形成终态前保持 pending/in_progress，Handler 不得在单次 attempt 耗尽时立即写 failure；否则现有终态保护会阻止后续 recovered success。
- 新增 append-only `durable_llm_task_events`（或复用已验证的统一 transition event 表）记录 `waiting/connection_detached/retry/recovered/expired`；其中 `connection_detached` 是连接属性事件，不改变 scheduler status。每条事件包含 task/request/session/tenant、attempt、from/to、reason、时间和 fencing token。
- 如果仍需在 WAL 暴露摘要，只新增数值 stage 常量和 migration，且仅表示当前摘要，不替代 append-only event。
- 每次 attempt 写独立 attempt/event，不创建多个逻辑 request。
- request ID、task ID、session ID、parent request ID 必须稳定关联。
- keepalive 不记为模型输出 chunk，不进入 completion token。

## 13. 超时、取消和资源治理

### 13.1 默认上限

| 类型 | 默认值 | 说明 |
|---|---:|---|
| keepalive interval | 15 秒 | 沿用现配置 |
| 可见状态最小间隔 | 60 秒 | 避免刷屏 |
| 普通交互 survival deadline | 30 分钟 | 仅连接内 |
| durable deadline | 24 小时 | 可租户覆盖 |
| 单 attempt connect/TLS | 取现有 transport 配置并受剩余预算截断 | 建连边界 |
| 单 attempt response header | 当前默认 120 秒并受剩余预算截断 | HTTP 响应头到达前 |
| 首 SSE frame/body byte | 当前默认 180 秒并受剩余预算截断 | 已有响应头后首协议帧 |
| chunk idle | 当前默认 300 秒并受剩余预算截断 | 流中相邻 chunk 空闲 |
| 单 attempt wall budget | `min(策略上限, coordinator remaining budget)` | 不继承无 deadline 的 `WithoutCancel` |
| worker lease | 60 秒 | 长 attempt 定时续租 |
| 最大 fallback 退避 | 5 分钟 | 权威 eligibility time 不截断，探测可提前唤醒 |

### 13.2 取消语义

- 非 durable：survival 开启时客户端 context 取消即终止；实施前必须把现有 `context.WithoutCancel`/PendingCapturer 旧行为置于独立兼容开关，并确保其不会启动新的上游 attempt。
- durable：网络断连只把 `connection_attached` 置为 false 并记录事件，不代表取消或改变 scheduler status；前提是 durable task 已事务化创建成功。
- 显式 `DELETE /pending-response` 不应隐式取消任务；新增受鉴权的任务取消动作或参数。
- 管理员取消、租户停用、预算耗尽立即阻止后续 attempt。
- 正在执行的 attempt 通过任务 cancel context 终止。

### 13.3 配额

新增租户级默认限制：

- 最大 active durable tasks；
- 最大并发 worker attempts；
- 单任务最大 attempt 数；
- 单任务最大累计供应商费用/估算 token；
- 单租户每分钟恢复 attempt 速率。

超过限制时任务保持 `retry_scheduled`，写入 `reason=waiting_capacity` 和短 `next_retry_at`；若已超过 deadline/预算则明确失败，不能无限堆积。

## 19. 上线与回滚

### 19.1 上线顺序

1. 合入 schema，但不启动 worker。
2. 仅开启连接内 survival，单租户 allowlist。
3. 观察 429/5xx 成功恢复率、连接时长和资源占用。
4. 开启 durable 创建，但 worker 单实例、低并发。
5. 验证重启和多实例 fencing 后逐步扩容。
6. 最后才评估服务端自动 durable 策略；在此之前只接受显式握手、真实持久 session 和租户授权。

### 19.2 回滚

- 关闭 `request_survival.enabled`：新请求回到现有有界 retry；已有连接按旧错误路径结束。
- 关闭 `durable_enabled`：停止创建和领取新 durable 任务；已有 running attempt 完成或租约到期。
- 回滚应用前不删除任务表；终态和 pending 结果仍可查询。
- 禁止通过删除表或清空 Redis 作为紧急回滚手段。

## 20. 验收标准

1. 可恢复的 429/周期配额/5xx/无候选场景，连接内恢复后请求成功，客户端没有协议解析错误。
2. 等待期间每 15 秒内有传输保活，且保活不出现在模型正文。
3. durable 请求在客户端断连和网关重启后仍能完成。
4. 多实例恢复中不存在重复最终提交和重复工具副作用。
5. 请求/content/safety scope 的永久错误，或聚合后全部允许 offer 均永久排除，在一个有界 attempt 后快速失败，不持续占用 24 小时任务槽。

7. 所有状态可由 request ID、task ID、session ID 和 tenant ID 关联。
8. feature flag 关闭时，现有 API 行为和测试保持不变。
9. `go test -race` 覆盖 writer、coordinator、store 和 worker 并发路径。
10. S30-S35 故障注入场景全部通过后才允许扩大 durable 灰度。

## 21. 已确认决策

- 采用“连接内保活 + 断连/重启持久接管”的混合模式。
- 采用独立 Request Survival Coordinator，不继续把长时状态机堆入 Handler/Executor。
- 默认协议输出使用 SSE 注释；结构化状态事件必须显式能力协商。
- 普通交互默认最长 30 分钟，durable 默认最长 24 小时，可租户配置。
- 所有流式请求在 feature flag/allowlist 内获得连接内首内容前恢复；完整 durable 只对显式标志、显式 capability/async 握手、真实持久 session 和服务端授权同时满足的请求开启。
- User-Agent、`X-Agent-Name` 和 provisional session 不构成 durable 信任依据。
- 一期必须先实现 attempt-local 协议缓冲和 commit state，不能只在现有 bridge 外套循环或写锁。
- survival 模式由 `ExecuteAttempt`/Coordinator 统一拥有外层重试，关闭 Goal retry、旧 async fallback 和跨 attempt 递归。
- 工具调用和结构化响应不做不安全重放。
- PostgreSQL durable task 是任务状态与最终结果 SSoT；终态和结果在 fencing 事务内原子提交，PendingStore 是带版本 CAS 的兼容投影，request WAL 继续承担摘要审计，完整生命周期使用 append-only transition event。
