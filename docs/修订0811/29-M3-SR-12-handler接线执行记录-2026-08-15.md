## 1. 产出（`16316058e`）

### 1.1 handler 侧 durable 装配（domains/streaming/durable_wiring.go）

- **快照切点**：三个 handler（chat `handler.go`、`messages.go`、`responses.go`）统一在「鉴权、session 归属校验、tool_ids 展开、body 规范化之后、候选解析之前」插入 `maybeStartDurable`——与 doc 18 §11.2 冻结切点一致。三协议共用 ChatHandler 上的 `SetDurableExecution(store, tenantAllowed, opts)` 装配（Messages/Responses 经 `h.chatHandler` 复用，未重入 ServeHTTP）。
- **非流式 202 交接**：capability + `Prefer: respond-async` 双条件满足时，构造 `DurableRequestSnapshotV1`（PolicyVersion 固定 `survival-policy-v1`；HasMultimodalContent 由 detectRequestModality 推导；SessionSource 由 body/header 派生）→ `CreateAndClaim`（frontend 短租约 15s）→ 立即 `Reschedule(reason=handoff_to_worker)` 交接给 RecoveryWorker → 渲染 §9.4 冻结的 202 envelope（`Preference-Applied: respond-async`、`Location`、`Retry-After`、`X-Gw-Pending{,-Request}`、`X-Gw-Task-Id` + 共用 gateway async JSON）。这是 §11.3「创建后直接后台执行」模式——Handler 不同时调用 attempt，不存在「前台无租约执行」中间态。
- **fail-closed 矩阵**（每条都有测试钉住）：
  - 流式 durable → 501 `streaming_durable_unsupported`（checkpoint 绑定完成前的保守阻断，不建任务）；
  - tenant 不在 allowlist / 无真实 session / 无 DB 授权 → 保持同步终态语义（capability 未满足不视为错误）；
  - 快照校验失败 → 503 `durable_snapshot_invalid`；
  - CreateAndClaim 失败（非重复）→ 503 `durable_unavailable`——不假 202、也不把显式异步请求静默降级为同步；
  - `(tenant, request)` 重复 → 幂等 202 指向既有 pending response；
  - handoff Reschedule 失败 → 仅告警，frontend 租约到期后 ClaimRunnable 自行重领（任务不丢）。
- **断连安全**：store 操作走 `WithoutCancel + 10s` 有界 ctx——客户端在 202 前断连不会取消任务创建（fix-review 复查发现的修正）。
- **快照安全**：不含 Authorization/Cookie/IP/credential；API key 只落 `api_key_id`。

### 1.2 生产 DurableAttemptRunner（domains/streaming/durable_runner.go）

- `VerifyByID` 重验授权：`InvalidKeyError` → AuthRevoked 永久终态（折叠进 CandidateOutcomes 交给 AggregateTaskOutcome）；DB 瞬态错误 → runner error，由 worker `rescheduleWithError` 重排、deadline reaper 兜底（doc 27 固化的「瞬态不终态」语义）。
- 候选**动态重算**（`resolveCandidatesForRequest` + 重验后的 KeyInfo profile/tenant），禁持久旧候选；无候选 → KindNoAvailableChannel（wait-recovery 窗口）。
- ExecParams 后台形态（对齐 executor 既有 detached 惯例）：`W=nil` + `SuppressSuccessWrite` + 清回调 + 合成 request（携带 run ctx 与 `X-Gw-Session-Id`/`X-Request-Id`/`X-Gw-Task-Id`）；经 `ExecuteAttempt`（nil gate，非流式）执行；结果从 `ExecuteResult.ResponseBody` + Response Content-Type 提取。
- 恢复时身份用 `identity.BuildIdentity`（tenant/app/key 锚点重建），client identity hash 仅做审计锚定不参与重放。

### 1.3 cmd/gateway 装配

- 仅 `cfg.RequestSurvivalDurableEnabled` 且 DB/keyring 就绪时：`durable.NewStore` + `chatHandler.SetDurableExecution`（复用 `cfg.RequestSurvivalEnabledForTenant` allowlist；Deadline 取 durable deadline 配置）+ `NewDurableRecoveryWorker(...).Start()`；keyring 缺失只告警（fail closed，不产生 202 路径）。
- `pendingStore` 换 `NewStoreWithFallback(fpSlotRedis, ttl, NewPGSource(pool, keyring))`——Redis 丢失/不可用时轮询接口回源任务表（§12.1）；`routingExec.PendingStore` 同步更新；Redis 完全不可用时以纯回源形态构造。
- 停机序：`durableWorker.Stop()`（有界 grace）插在 stop goroutine 中 `pools.CloseAll()` 之前、OmniFree 之后。
- keyring 初始化条件放宽为 `CredentialEncryptionKey || KEYRING_JSON`（KeyringFromEnv 本就优先读 KEYRING_JSON）。
