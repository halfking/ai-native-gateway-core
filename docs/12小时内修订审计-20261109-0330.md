## 2. 重点关注项的逐项复核（按任务指定的关注面）

### 2.1 请求数据转换 / 正则口径（`139a552a4`）

**修正原因**：同一棵扫描器在【不同平台 + 不同 locale】下给出不同读数。三个机制：

- **机制 A′**：三条 `INTERNAL_IP` 规则的词边界 `\b` 在 BSD libc（macOS）的 `regcomp` 里**不是词边界、而是字面字符 `b`** ⇒ 该族规则在 macOS 上**恒 0 命中**。修法改为可移植 ASCII 形态 `(^|[^A-Za-z0-9_])…([^A-Za-z0-9_]|$)`。
- **机制 C′**：扫描器**从不设置 locale** ⇒ 读数随宿主机环境而变。修法显式钉死 `LC_ALL=C` / `LANG=C`（选 `C` 而非 `C.UTF-8`：精简镜像必有 `C`，`C.UTF-8` 会静默退化）。
- **机制 E′**：**发现阶段用 `grep -niE`（大小写不敏感）、归因阶段用 `[[ =~ ]]`（大小写敏感）** ⇒ 口径不一致 ⇒ 大写形态的凭据**候选命中却被静默丢弃** ⇒ BLOCK 级**系统性假阴性**。修法把行内容与规则模式同时小写化（`${v,,}`，bash 4.0 起即有 ⇒ 不改 `requires-bash` 契约）。

**本轮独立复核（不采信提交说明，直接实测）**：

| 复核项 | 方法 | 结果 |
|---|---|---|
| 新门有牙齿？ | 撤掉大小写折叠 | **PASS=9 FAIL=2 ⇒ 精确红** ✅ |
| 新门有牙齿？ | 规则退回 `\b` 形态 | **PASS=9 FAIL=2 ⇒ 精确红** ✅ |
| 修法在当前平台生效？ | 正常形态 IP 命中 / 粘连形态不命中 | ✅ 均通过 |
| 摘要自带口径？ | `Locale:` / `Engine:` 两行 | ✅ 均打印 |
| 与既有门共处？ | `scan_secrets_enumeration` / `whitelist_regex_portability` / `gate_scripts_caller_registry` | ✅ 全绿（PASS=8 / 3 / 170） |
| 全量快门 | `make guards-gate-scripts` | ✅ **20 条快门全绿，rc=0** |
| 编译 | `go build ./...` / `go vet ./mcp/...` | ✅ rc=0 |

**方案合理性判定：合理。** 三条机制各自有独立的失败形态与独立的修法，且**互为配套**（只换词边界不钉 locale，CI 侧读数仍会跳；钉了 locale 不做大小写折叠，BLOCK 级假阴性仍在）。

**执行结果与预期一致性**：**不完全一致** —— 修法本身按预期生效，但**它把 CI 那道一直红的门变得更红**（详见 F-3）：机制 A′ 让 macOS 侧多出 1147 条 `INTERNAL_IP`，机制 E′ 让 `CRED_ASSIGN` 从 90 涨到 1525。**这是"更诚实"而非"更糟"**（原来那 1147 条在 CI 上其实一直存在、只是旧键对不上 baseline 才没被计入），但**必须与 F-3 一起看**。

### 2.3 异常错误的处理 / 数据来源与去处（`cc03409b1`）

**修正原因**：`zcat -f`（"force"：非 gzip 输入也直通）是 **GNU gzip 扩展**；busybox/Alpine 的 `zcat` 没有这个语义 ⇒ 混读三族（当前文件 + 未压缩轮转 + 压缩轮转）时**只要有一个非 .gz 文件在列，那次调用就一个字节都读不出来**（rc=1、stdout 空）⇒ **计数器恒为 0 ⇒ 长得和「真的没人用 q=」一模一样** ⇒ 而这正是脚本自己声明的**最危险失效模式**。更糟的是旧实现只 WARN 后**照样打印 verdict**，把一次**读失败**渲染成一条**看起来很确定的负面基础设施结论** ⇒ 877 决策会被一次环境差异静默翻转。

**本轮独立复核**：

- ✅ 修法对：改为**逐文件分派**（`.gz ⇒ gzip -cd`，其余 ⇒ `cat`）⇒ 两者都是 POSIX 工具，GNU/busybox/macOS 行为一致。**本轮实测**：`cat --` 与 `gzip -cd --` 在本机 macOS BSD 下均 rc=0。
- ✅ 修法对：读失败 ⇒ **拒绝打印判定**（rc≠0 ⇒ exit 1 ⇒ 无 verdict）。
- ✅ 静态断言补上「不再出现 `zcat -f --` 调用」，防旧形态被改回来。
- ✅ 自检夹具（`--self-test`）全绿：`ALL PASS`。

**★ 本轮发现的真缺陷 ⇒ 见 F-2。**

## 3. 待修正清单（本轮新发现）

### ★ F-2（★ P1 · ★ 已在本轮修好并提交 ★）—— q-usage 两条行为门「测不出自己被改坏」

**根因**：这两条门通过 `exec.Command` 跑 shell 脚本 ⇒ **Go 的测试缓存不追踪子进程读过的文件** ⇒ 脚本内容变了、**缓存键不变** ⇒ 本门**返回上一次的绿**。

**实测复现（本轮亲跑）**：

```
1. go test … -run TestQUsageScriptDoesNotDependOnGNUSpecificZcat   ⇒ ok（建立缓存条目）
2. 把 read_logs 改回 `zcat -f --`                                     ⇒ 脚本已改坏
3. go test … （不带 -count=1）                                       ⇒ ok … (cached)  ← 假绿！
4. go test … -count=1                                                ⇒ FAIL          ← 同一份脚本精确变红
```

⇒ **门本身有牙齿，但牙齿被 Go 的缓存遮住了** ⇒ 一道门「测不出来自己被改坏」⇒ 门形同虚设。

**本轮修法（`ef5cc58fe`）**：在两条门里各加一次**进程内**读取脚本（`readQUsageScript(t)`）⇒ 脚本内容进入 Go 的测试缓存键 ⇒ 脚本一改 ⇒ 缓存失效 ⇒ 本门重跑。

**修后实测**（同一条命令、**不带** `-count=1`）：脚本改坏 ⇒ **精确变红** ⇒ 缓存盲区已闭合 ✅

**依据**：这是**仓内既有成文做法** —— `scripts/ursmcheck/` 里 54 条 exec 脚本的门中 **48 条**都做了进程内读取（例：`shell_fullwidth_var_gate_test.go` / `monitor_script_exec_gate_test.go` / `pg17_start_script_test.go` / `api_sweep_script_shape_test.go`）⇒ 本轮只是把这两条新门**补齐到与既有做法一致**，不是新立规矩。

### ★ F-3（★ P1 · ★ 登记待裁决 · ★ 本轮不改 CI 闸门 ★）—— 扫描器 baseline 在 CI 调用形态下 100% 失效

**根因（★ 实测定位，非推断 ★）**：扫描器有**两条枚举分支**，产出的**相对路径形态不同**：

| 分支 | 枚举命令 | 枚举产出 | `rel`（去掉 `REPO_ROOT/` 之后） |
|---|---|---|---|
| `--tracked-only` | `git ls-files` | `relative/path` | `relative/path` ✅ **与 baseline 同形** |
| 默认（CI 用这条） | `find "${PATHS[@]}"`，而 `PATHS=(".")` | `./relative/path` | **`./relative/path`** ❌ **与 baseline 不同形** |

而 baseline 键存的是**不带 `./` 前缀**的形态（实测：169 条基线键里，**带 `./` 前缀的 = 0 条**）⇒ **在 CI 的调用形态下，每一条 baseline 键都匹配不上 ⇒ 全部失效**。

**★ 本轮的三重独立验证（不是推断）★**：

1. **枚举形态差异（实测）**：`find . -maxdepth 1 -type f` ⇒ `./.env.local.example`；而 `git ls-files` ⇒ `.env.local.example`（**无 `./`**）⇒ 两者去掉 `REPO_ROOT/` 之后的 `rel` 形态**确实不同**。
2. **键形态差异（实测）**：在扫描器里临时插桩打印实际查表用的键 ⇒ 实测拿到 `[.env.local.example:0:SECRET_FILE]`（`ls-files` 形态）；而**全树扫描的输出行**用的是同一个 `$rel` 变量（`record_finding` 里 `echo "[$sev] $rel:$ln"`）⇒ 走 find 分支时同一文件的输出行是 **`./.env.local.example:0`** ⇒ **而 baseline 存的是 `.env.local.example:0:SECRET_FILE`** ⇒ **键对不上 ⇒ 查表必然 miss**。
3. **效果差异（实测，同一棵树 + 同一份 baseline 文件）**：

| 调用形态 | Total findings | **BLOCK** |
|---|---|---|
| `--tracked-only --baseline=<repo baseline>` | 1732 | **2** ✅ |
| 默认（find 分支）`--baseline=<repo baseline>` | 2769 | **96** ❌ |
| 默认（find 分支）**不传** baseline | 2769 | 96 |

⇒ **94 条 BLOCK 是「已被 baseline 登记为已知存量」的项，却因键形态不匹配而被当作新问题重新计入**；
⇒ 且「传了 baseline」与「不传 baseline」在 find 分支下**读数完全一样** ⇒ 这是 baseline **完全失效**的最直接证据（不是"部分失效"）。

**⇒ 结论**：F-3 的根因是**枚举分支与 baseline 键形态的口径分叉**，而不是 baseline 内容本身有问题（baseline 里 169 条键的内容是对的、只是前缀形态与 find 分支不匹配）。

**为何 CI 一直红、且红得「没有信息量」**：`.github/workflows/security-scan.yml:23` 跑的是
`bash scripts/scan-secrets.sh --mode=strict --format=text` ——
**既不传 `--baseline`（第一重失效），又走默认 find 分支（第二重失效：即使传了也无效）** ⇒ 双重失效。

> ★ **注意**：`scripts/sync-to-github.sh:143`（公开仓同步闸门）用的是
> `--paths=. --tracked-only "${baseline_arg[@]}"` ⇒ **走的是 `ls-files` 分支 ⇒ baseline 在那里是生效的**
> ⇒ **同一个 baseline，在公开仓同步闸门上有效、在 CI 上无效** ⇒ 这正是「同一份量具、两种口径」的分叉点。

### ★ F-4（★ P2 · ★ 登记待裁决 ★）—— balance-floor 恢复通知**按凭据数无上限起 goroutine**

**根因**：`notifyRecoveredBatch` 对 `RETURNING id` 返回的**每个** id 各起一个 goroutine：

```go
func (g *BalanceFloorGuard) notifyRecoveredBatch(ids []int64, reason string) {
	for _, id := range ids {
		g.notifyRecovered(id, reason)   // ★ 每 id 一个 goroutine
	}
}
```

而每个 goroutine 内部做**一次 DB 往返**（`RearmCredentialFailures` → `exec.Exec(ctx, …)`，3s 超时）。

**与仓内既有纪律不自洽**：**同一个文件**里的兄弟实现 `runPlanProbes`（`bg/balance_floor_guard.go:1272-1281`）**明确用了 `semaphore.NewWeighted(int64(limit))` 限流**，其注释写着「probes candidates on a **bounded** worker pool」；而恢复通知这条路径**没有任何上限**（`semaphore` 虽已在该文件 import，但**这条路径没用**）。

**风险量化**：
- 单轮 5 分钟周期内，一批翻转的凭据数 **N** ⇒ 起 **N** 个 goroutine ⇒ **N** 次 DB 往返 ⇒ 全部打向 **同一个 pgxpool**（仓内注释记 `db.MaxConns=32`）。
- 修复提交自己的实测读数（211，2026-11-08）：**29 个用尽凭据里 23 个** `quota_recover_at IS NULL` ⇒ 一次批量翻转可达**数十**量级；**生产面更大**。
- ⇒ **N 远大于 32 时**，多数 goroutine 阻塞在**取连接**上 ⇒ 每个持 3s 超时 ⇒ **一批超时 + 一批成功** ⇒ **恢复通知部分丢失**（`RearmCredentialFailures` 失败只 `slog.Warn`、不重试）⇒ **流程闭环出现「静默漏通知」的口子**。
- 好的一面：`bg.Go` 的 `recover()` ⇒ panic 不会拖垮进程；且**没有** goroutine 句柄泄漏（一次性任务）。

**建议修法（★ 待裁决 ★）**：复用同文件既有的限流形态 —— 在 `notifyRecoveredBatch` 里用 `semaphore.NewWeighted(limit)`（或 `errgroup.SetLimit`）把并发度压到与 DB 池同量级（≤ `MaxConns`），**并给「部分失败」加一个可见计数**（现只有逐条 `slog.Warn`，**没有指标** ⇒ 漏通知在监控上不可见）。

**为何本轮不擅自改**：这会改动**生产并发面**（探测回拉的实际触发时机与批量），且 §2.2 的修法**方向是对的**（补齐恢复通知链）⇒ 本轮**只补并发上限、不改语义**是可行的；但它落在**生产路径**上、且需要一次**生产面读数验证**（N 的真实分布）才能定 `limit` ⇒ 超出「窗口内修正」的边界 ⇒ **登记 + 给方案 + 标注推荐项**。
