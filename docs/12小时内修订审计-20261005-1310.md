## 三、`validate_sessions_v2` 端边界（L2，§9.222 后续）

R44 移交第 1 项「未修」。本轮**已修**。

### L2.1 根因

`-end-date` 用 `time.Parse("2006-01-02", …)` 解析成**该日 00:00:00Z**，而查询是半开的
`AND ts < $3`（`cmd/tools/validate_sessions_v2/loader.go`）。于是：

> 操作员输入 `-end-date 2026-10-04`（=「含 10-04 当天」），
> 查询只返回到 `2026-10-03T23:59:59Z`，
> **10-04 当天的行被整日排除**——而报告仍然打印 `2026-10-04`。

252 实测：最新 v1 行 `2026-10-04 15:53:32Z`，静默少算 **15h53m32s**。

这不是「少报一点」，是**报告说的窗口和实际校验的窗口不是同一个**，而这份报告正是
§9.222 存在的理由——它会被用来论证退役 `request_logs`。

### L2.2 为什么截断门看不见它（**我第一遍判错了，值得记**）

R44 交接里写「门只比 `actual.MaxTS.Before(requestedEnd)`——方向相反故不响」。
我第一遍据此把门的端臂改成日粒度比较，并写了一组"回归"用例。

**负控把这套改动否掉了**：把生产代码还原后，那组用例**照样全绿**。复盘发现两个错误：

1. `a_whole_named_day_is_missing`（MaxTS=10-03 23:00，end=10-04 00:00）在**旧**逻辑下
   `MaxTS.Before(requestedEnd)` 为 **true**，旧门本来就响。⇒ 它不是回归用例。
2. `MaxTS.Before(requestedEnd)` 与 `MaxTS.Before(startOfUTCDay(requestedEnd))`
   **只在 `requestedEnd` 不是午夜时才不同**；而 CLI 的 `time.Parse("2006-01-02")`
   **永远产出午夜** ⇒ 该改动对所有 CLI 可达输入是 **no-op**。

⇒ **门从来不是缺陷所在，查询边界才是。门的端臂已还原，一个字没动。**
真正承重的只有 `endDayExclusiveBound` + 把它接进 SQL 参数。

> 方法论：**「门没响」和「门在错的维度上问」是两回事。** 我差点用一个
> no-op 改动替换掉一个真修复，并给它配上一组证明不了任何事的测试。

### L2.3 修法

`endDate` 保持「操作员命名的最后一天」语义（显示与截断门都用它，**报告不因此改口**），
只在交给 SQL 的那一步转成半开上界：

```go
func endDayExclusiveBound(namedEndDay time.Time) time.Time {
    return namedEndDay.AddDate(0, 0, 1)   // → ts < 次日 00:00
}
```

`ts >= $2` 的起点**不转**（它本来就对，转了反而再丢一天）。

### L2.4 承重证据

- `TestQueryBoundsIncludeTheNamedEndDay` 断言 **SQL 实际收到的参数表**。
- 负控（`go test -overlay` 把生产那一行还原成 `endDate`）→
  `args[2] (the 'ts < $3' bound) = 2026-10-04T00:00:00Z, want 2026-10-05T00:00:00Z`，**转红**。
- 早先一版测试用 `os.ReadFile("loader.go")` 读源码文本断言接线，**overlay 不影响
  `os.ReadFile`** ⇒ 它对着已还原的实现仍然全绿。这版已改为断言参数表。
- 截断门的 10 条子用例在改动前后**全绿**——它们是**对照**，不是回归证明，
  注释已就地写明，免得下一个人再当成回归证据。

### L2.5 合并时撞上并行线：同一缺陷的两种互斥修法（Owner 已裁决）

提交前 `git fetch` 发现 `origin/main` 已前进 **52 笔**（并行会话在活跃），
`git merge origin/main` 在 `loader.go` / `window_guard_test.go` 冲突。
查证后得知：**并行会话独立修了同一个 R44 移交项 1**（`99d625f33`，§R45/M2）。

两种修法**互斥**：

| | 并行线（§R45/M2） | 本轮 |
|---|---|---|
| 查询边界 | **不动**（仍是 `ts < endDate`） | 修成 `ts < 次日 00:00` |
| 截断门 | 新增第三条 end-day 臂 + `HasV1RowsInRange`（`LIMIT 1`）探针 | 回到原两臂 |
| 端臂 | 放宽成 24h slack（`MaxTS.Before(end-24h)`） | 原判据（`MaxTS.Before(end)`） |
| 失败形态 | 探测到当天仍有行就**拒绝这次运行**，提示改用次日 | 正常运行，报告日期与实际窗口一致 |

**为何不能共存**（已核实，非推测）：end-day 臂的前提是「窗口不加载那一天」。
边界一旦修好，那一天**就被加载了** ⇒ 该臂在每一个当天有数据的正常运行上触发，
**把所有合法运行都拒掉**。而 `HasV1RowsInRange` 存在的理由（MaxTS 判断不了
当天有无行）正是**错误边界的下游症状**；边界对了之后 MaxTS 就判断得了。

**Owner 裁决：取根修**，把并行线那条改判为「错误边界的下游症状」并移除其
end-day 臂与探针。

**保留下来的那一部分**：并行线「把该重跑成什么值一并告诉操作员」的 UX 是对的，
已改由 MaxTS（真正有数据的最后一天）推导，落在「命名日整天无数据」这条臂上，
不依赖探针。并行线的用例里两条编码 24h slack 语义的（「end day after the last
data day is clean」「grace boundary」）在根修下语义已变——**命名日改成最后有数据的
那天即可**，命名一个完全没有数据的日确实是「窗口宽于数据」，已按新语义重写并注明。

> 这条冲突的价值不在技术判断，在**发现「同一个缺陷被两条线同时修」**。
> 若不是提交前强制 `git fetch` 重查并逐文件比对，这两份修法会安静地互相覆盖，
> 而且从任何一侧的测试都看不出来。

## 四、迁移通道门：一条红门后面藏着四层（L3）

这是本轮最大的结构性发现，也是 R44 移交第 2 项的真正答案。

### L3.1 关键机制：门在第一个失败处 `exit 1`

R44 记的是「该门**只**红在 829 一条」。这句话是对的，但极易误读为「829 是唯一问题」。
实际上门**逐条 `exit 1`**，所以它报的是**首个失败点**。我按 R44 的说法逐个修，链式揭开了
**四层既有缺口**：

| 顺序 | 首个失败点 | 性质 |
|---|---|---|
| 0 | `829 … missing from the channel files=(…) array` | 真缺口（Owner 已拍板登记） |
| 1 | `819 … has no approved delivery path` | **既有**；门缺一整类豁免 |
| 2 | `830 … has no approved delivery path` | **既有**；两个判定器口径矛盾 |
| 3 | `825/826/827/828 … has an installer leg but no upgrade path` | **既有**；R33 复发族 |

四层**在 origin/main 上就都存在**，只是被前一层挡住。`git show origin/main:…` 逐条核对过。

### L3.2 819：门缺一整类豁免

`819_request_abandoned.sql` 的**文件头自己写着**为什么不能跑：独立 `request_abandoned`
表方案已被 820/821 线取代（821 改在 `session_turns` 上打 `is_abandoned`），
Go 写路径 `markRequestAbandonedPending` / `clearRequestAbandonedPending` **已不存在**，
生产 `*.go` **零引用**；文件是按 `docs/db-changelog.md` 台账 SHA 恢复的，
**只为让迁移校验和门能验它**。

登记进通道 ⇒ 建出一张无人写无人读的表，在 `\d+request_abandoned` 里看着像活的。
登记进 `channel_gap_allowlist` ⇒ 对一个**根本没装过它**的安装谎称「installer-only」。

⇒ 新增第三类 `superseded_migrations`，**按它实际是什么来命名**，不借用另外两个名字。

### L3.3 830：同一文件里两个判定器互相矛盾

`canonical_delivery_path_check` 接受 `startup ∪ sequence ∪ ensure`，
**不接受** `channel_gap_allowlist`；而同文件下方的 ≥690 穷举循环**一直接受**它。
830 依 R44 的 manual-by-design 决定登记在 `channel_gap_allowlist` 里 ——
于是一个**被明确审议过的例外**在一个判定器下过、在另一个判定器下不过。

⇒ 把 `channel_gap_allowlist` 也接进 `canonical_delivery_path_check`，
**对齐两个判定器，而不是削弱任何一个**。

（注意：**830 自身的 manual-by-design 决定完全正确、没动**。它不能进自动升级，
因为 RENAME 那一半会原地改名一张 10GB+ 活表。）

### L3.4 825-828：新装与升级分叉

四条带着**完整 installer 腿**落地（`main.go:765-774` go:embed + `1008-1011` StartupFiles map），
**没有通道腿**。后果不报错，是静默不投递：

> **全新安装会拿到它们；任何在它们之前装的库永远拿不到。**

这正是 R33 在同一文件里点名、并要求「deliberate, commented edit」的复发族：
`693/699/701/703 → 815/816 → 817 → 825-828`。

⇒ 已补登。理由：它们跑的就是 installer 今天在全新安装时**已经跑过**的同一批 SQL，
不是新代码路径，只是把同一条路径接到升级上，让升级库与新装库对齐。

### L3.5 登记 829 会让部署 `exit 5`——这是门替我挡下的第五层

把 829 写进通道数组后，门**没有**转绿，而是换了一张更严重的牌：

```
clobber guard violations (deploy would exit 5):
ensure_request_logs_bodies_partition|694_partition_ensure_timezone.sql|765_bodies_columnar_storage.sql|829_bodies_columnar_rollback.sql
```

**若只做「登记」这一件事，下次升级会在应用任何文件之前直接 abort。**
`ensure_request_logs_bodies_partition` 被三个通道文件重定义
（694 时区钉扎版 → 765 叠加 columnar 分支 → 829 撤掉列存分支），
未登记为「有意链」时部署守卫拒绝执行。

这正好印证了该文件自己写着的纪律：
> *「两侧必须同时改，否则另一道门会红——单侧绿不是绿。」*

⇒ 已按**既定机制**补上 `intentional_function_chains=()` 登记，
链序 `694 → 765 → 829`，**829 必须最后**（它是活库里应有的最终体），
并在 `must-not-disappear` 自检里一并钉住，防止登记日后被无声删掉。

> **这一层是本轮最值得记的：它证明了「门报错」与「对象错」必须分开看。**
> 门红在 clobber 上，不是说 829 不该进通道（Owner 的判断仍然成立），
> 而是说**只做一半**会让升级路径从「静默不投递」变成「直接中止」——
> 后者严重得多。补上链登记之后，829 才真正可投递。

### L3.6 两个自测判据的同向加固

`canonical_delivery_path_check` 有自己的回归自测（原只覆盖三路）。本轮把
「只被 `superseded_migrations` 覆盖的迁移必须通过」「只被 `channel_gap_allowlist`
覆盖的迁移必须通过」都加了进去，并让 orphan 反例带上全部六个参数——
否则新加的两路只是**从未被执行过**的分支。

参数一律写成 `${5:-}` / `${6:-}`：`set -u` 下未绑定的 `$5` 是**硬错误**，
第一版没加默认值时门直接死在 `line 18: $5: unbound variable`。

## 七、给下一轮的三条方法论提醒

1. **「门只报一条」≠「只有一条问题」。** 本轮的核心教训。门逐条 `exit 1`，
   于是「首个失败点」被四轮交接记录成「唯一问题」。**先写脚本把全部缺口一次列全，
   再动手**，否则会像本轮一样一层层揭。
2. **负控不是形式，它会否掉你的诊断。** 我据交接判断「门在错的维度上问」，
   改完配了三条"回归"用例；负控一跑，全绿——暴露那个改动是 no-op、
   用例不区分新旧。真缺陷在别处（查询边界）。
   **一个证明不了新旧之别的测试，等于没有测试。**
3. **给门的"新分支"要真的被执行。** 新加的 `superseded_migrations` /
   `channel_gap_allowlist` 两路若不配自测，就只是两行从未运行过的死代码；
   参数不写 `${5:-}` 默认值，`set -u` 直接让门死在第一行。
