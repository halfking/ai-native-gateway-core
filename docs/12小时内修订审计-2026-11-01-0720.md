### P1-1　`backfill-session-opened` 只读 hot 表 ⇒ 生产上历史会话几乎捞不到（工具达不到其宣称目的）

**文件:行号**：`cmd/tools/backfill-session-opened/main.go:75`（`FROM session_turns_hot`），文档注释 `:10-11`

**问题一句话**：工具的候选源只查 `session_turns_hot`，但该表 8 小时后被排水到父表 `session_turns` ⇒ 真正的「历史」会话早已不在 hot 表 ⇒ 工具在生产上捞不到它要补发的历史会话。而它自己的注释写着事实源是「`session_turns_hot` **and its parent** `public.session_turns`」⇒ **注释比实现更宽**。

**机制解释**：
- `session_turns_hot` 是**独立堆写表**（`installer/…/session_turns_hot_bootstrap.sql:91-92` 的 COMMENT 原文：「Independent heap write table for recent session turns. Cold rows are atomically moved to public.session_turns by promote_session_turns_hot_to_partition()」）。
- 排水函数 `promote_session_turns_hot_to_partition` 是 **`DELETE FROM public.session_turns_hot … INSERT INTO public.session_turns`**（`installer/…/869_promote_session_turns_trace_events.sql:236`）⇒ **搬家**不是复制。
- 保留期：函数签名 `DEFAULT '7 days'`，但**生产实际由 Go 调度器驱动**——`bg/partition_manager.go:1804` 把 `promote_session_turns_hot_to_partition` 列入常态调度，保留期走 `resolvePromoteConfig` 的 default 分支 ⇒ `DefaultRetentionWindow = 8 * time.Hour`（`bg/partition_manager.go:52`），`lifecycle.hot_retention_hours` 默认 8（`settings/spec_lifecycle.go:7`）⇒ **8 小时前的会话全在父表**。
- 仓内自己的会话族读面**一律两侧并读**（`internal/sessionfamily/exists_by_key.go:71` 的 `ExistsByKeySQL` = `hot UNION ALL parent`），本工具是唯一单腿的。

**证据（自建 PostgreSQL 17 实例实跑工具原样 SQL）**：
```
--- 工具原样查询（只读 session_turns_hot） --- tool_candidates = 3
--- canonical 全历史读面（hot ∪ parent）     --- true_sessions  = 13
--- 工具漏掉的会话 --- hist-sess-1 … hist-sess-10（10 个，全在父表）
```
⇒ **工具漏掉 10/13 = 77% 的会话，且漏掉的正是它要补发的「历史」会话**。

**修法**：改为两臂并读（`hot UNION ALL parent`），照仓内 `ExistsByKeySQL` 的形态。
★ **不用视图**：`public.session_turns_with_current_month`（`installer/…/757_session_turns_origin_actor_projection.sql`）**不投影** `end_user_id` / `api_key_id`（grep 计数 0/0），而本工具的 user_id 派生必须用这两列 ⇒ 必须显式两臂并读。

**验证（同一实例、同一数据集）**：修复后查询返回 **13**，与全历史真值 **13 逐字相等**（3 → 13）。

### P1-2　同一工具的 `--from/--to` 窗口作用在 turn 行上 ⇒ 跨窗口会话的 `occurred_at` 取错

**文件:行号**：`cmd/tools/backfill-session-opened/main.go:76-78`（窗口谓词）、`:71-78`（`DISTINCT ON`）、`:154`（写 `env.OccurredAt`）

**问题一句话**：`WHERE ts >= $1 AND ts < $2` 过滤的是 **turn 行**，`DISTINCT ON` 随后在**过滤后的集合**里取最早 ⇒ 一个在窗口**之前**开始、窗口**之内**有后续 turn 的会话，其 `occurred_at` 变成窗口内那个 turn 的时间，而不是会话真正的开始时间 ⇒ 补发事件的 ASM 时间线错位。

**机制解释**：`:71-78` 的 `SELECT DISTINCT ON (tenant_id, session_id) … FROM session_turns_hot WHERE <窗口> ORDER BY tenant_id, session_id, ts ASC` ⇒ `DISTINCT ON` 作用在**窗口子集**上，不是「先取会话最早 turn、再按窗口过滤」。而 `:154` 用 `env.OccurredAt = c.occurredAt.UTC()` 把这个值直接写进事件。

**证据（PG17 实跑，构造 `sess-old`：真开始 2026-08-15、窗口内另有 turn）**：
```
--- 旧语义（窗口在 turn 行级，from=2026-09-01）--- 0 行（hot 侧无此会话）
--- 新语义（窗口在会话级，from=2026-09-01）--- 0 行 ★ 正确排除（会话真开始在 8 月，不落在 9 月窗）
--- 新语义（from=2026-08-01，窗覆盖真开始）--- sess-old | 2026-08-15 18:00:00+08 ★ occurred_at = 会话真开始
```

**修法**：`DISTINCT ON` 不带窗口谓词（取该会话的**全局最早** turn），窗口谓词移到**外层**作用于 `occurred_at` ⇒ 窗口语义变成「会话整体落在窗内」。

**同时修**：`NOT EXISTS` 的反连接也按两侧下推（否则父表里已有的 opened 事件会被漏判 ⇒ 同一会话可能被重复补发；幂等键相同 ⇒ INSERT 被 `ON CONFLICT DO NOTHING` 吞掉，但 `skipped` 计数会失真）。

### P1-3　`deploy-seamless-docker.sh` 的 build_seq floor 锁**不保护读** ⇒ 并发部署必撞号

**文件:行号**：`scripts/deploy-seamless-docker.sh:2411-2412`（base/new_seq 在锁外）、`:2416-2436`（锁）

**问题一句话**：`base` 与 `new_seq` 在**拿锁之前**算好，锁只保护**写 floor** ⇒ N 个并发部署都读到同一个旧 floor、算出同一个 `new_seq`、写同一个 floor ⇒ **撞号**，恰是这段代码要根治的病。

**机制解释**：
- `:2411` `base = max(read_seq(path), read_seq(other), read_seq(floor_file))`、`:2412` `new_seq = base + 1` —— **都在锁外**。
- `:2418-2429` 才 `os.mkdir(hold)` 拿锁，`:2430-2431` 只写 floor ⇒ 读-改-写被拆成「锁外读 + 锁内写」⇒ **不是临界区**。
- 参考实现 `scripts/bump-version.sh:173-189` 是**先拿锁再读 floor**（`seq_floor_acquire` → `seq_floor_read` → 算 → 写 → release）⇒ 语义正确。deploy 脚本注释自称「语义与 bump-version.sh 对齐」，但**读的位置不同**。
- 附带：`os.mkdir(hold)` 只捕获 `FileExistsError`；floor 目录不可写时抛 `PermissionError` ⇒ 整个 python 块**崩溃**（非降级）⇒ 连 `version.json` 的 sha/date 都不改写 ⇒ 与注释承诺的「降级为无 floor 模式——撞号防护失效但不阻塞部署」**相反**。

**证据（用脚本原文 python 块做 6 路并发实跑）**：
```
=== 修复前 ===  6 路并发全部输出 build_seq 101 ⇒ 撞号；floor 仍是 101
=== 修复后 ===  6 路并发输出 101,102,103,104,105,106 ⇒ 全异；floor 正确推进到 106
```

**修法**：把 floor 的**读**移进锁内（`if got_hold:` 块内先 `read_seq(floor_file)` 再算再写）；并把 `os.mkdir` 的异常捕获从 `except FileExistsError` 扩到 `except OSError` ⇒ 目录不可写时走「无 floor 模式」降级而非崩溃。

### P2-1　两处「已登记不修」的漏网路径，其形态表**已存在** ⇒ 延后的前置条件已满足

**文件:行号**：`domains/hooks/outputcompliance/stream_compliance.go:984` / `:987`

**问题一句话**：`219394067` 登记的「`stream_compliance.go:984/:987` 裸 error」延后，理由是「**先补形态表再改代码**」——但形态表**在登记时就已经存在**，且**同形态的 lane 路径**（`releaseCheckedFrames`，同文件 `:700-720`）在**同一个提交 `426393659`** 里已经按 `GuardRewriteRefusedRuleID` / `GuardRedactInvalidRuleID` 归因 ⇒ 延后的前置条件**早已满足**，只剩「event 路径」这一个调用点没跟上。

**机制解释**：
- lane 路径（`releaseCheckedFrames`）：已返回 `&errorsx.PolicyBlockError{RuleID: GuardRewriteRefusedRuleID, …, Evidence: boundedPolicyEvidence(original)}`。
- event 路径（`inspectSSEFrame`）：仍是裸 `errors.New(...)` ⇒ 审核单 rule/reason/evidence 全空。
- ⇒ **同一形态在两条路径上口径不一致**：lane 路有归因、event 路没有 ⇒ 审核员看到 event 路拦截单仍然判不了「拦得对不对」。
- 形态表（`docs/audit/2026-10-31-拦截归因轮-守卫失败可归因与逐单窗口.md` §3 的 F1 表）已收录 `rewrite_refused` / `redact_invalid` 两行 ⇒ **表按形态枚举、不按调用点枚举** ⇒ 同一个形态的第二个调用点天然落在表外 ⇒ 这正是「登记完备但修法没落地」的机制。

**修法**：把 event 路径的裸 error 换成与 lane 路径同款的 `PolicyBlockError`（含 `RuleID` / `Reason` / `Path` / `Evidence`）⇒ 两处调用点口径一致。

★ **未动的另一处**：`security/sanitize/output_sensitive.go:209-210`（工具 JSON 非法 ⇒ `Blocked:true` 但无 `Issues` ⇒ 空 RuleID）——它的形态是「**结果合法但归因缺失**」，与前两处（「**错误裸奔**」）不同类，且该处返回的是 `ComplianceResult` 而非 error ⇒ 需要另一套修法（补 Issue）⇒ 本轮**登记保留**，不混进本轮修法。

### P2-2　`VerdictRank()` 是死代码，SQL 严重度枚举成了第二份无约束事实源

**文件:行号**：`domains/modelcredibility/types.go:74-87`；`domains/modelcredibility/store.go:704-710`

**问题**：`VerdictRank()` 全仓**无调用方**（grep 只命中定义处与 `store.go:685` 的一句注释）；真正生效的严重度序只存在于 SQL 的 `CASE` 里。Go 侧 `verified=0/unknown=1/suspected=2/diluted=3`（越大越严重），SQL 侧写的是反向数字（`diluted=0 … verified=3`）但**相对次序相同** ⇒ 今天行为正确；新增/重排一个 verdict 时两份事实源会**静默分叉**。本仓在 `rule_descriptions.go:17-19` 明写「事实源只有一处」。

**修法**：本轮**不删**（删除会波及 `types.go` 的导出面），而是**加对齐断言**：一条纯函数测试断言 4 个 verdict + default 的 SQL `CASE` 次序与 `VerdictRank()` 严格同序 ⇒ 两份事实源从此**互相钉住**。（登记为下轮候选：把 `VerdictRank` 变成 SQL 的唯一生成源。）

## 八、通用式（已同步进 `LESSONS.md` §609）

1. ★★★★ **「写了腿」≠「门在那里」**：新腿若不在任何入口（Makefile / workflow / audit 脚本）被提到，它在任何自动路径上都会 SKIP ⇒ 门不存在。**判据：新增腿的 `grep -rn <包名> Makefile .github/workflows/ scripts/audit/` 必须命中。**
2. ★★★★ **「注释比实现宽」是静默无操作的来源**：工具注释声明的事实源比实现宽 ⇒ 读者（含审计档与授权步骤）会以为覆盖面更大 ⇒ 实跑得到 0 条也无人察觉。**判据：注释里出现的表名，必须逐条在 SQL 里找到。**
3. ★★★★ **计数器类防撞号机制，读必须在锁内**：读-改-写被拆成「锁外读 + 锁内写」⇒ 不是临界区 ⇒ 并发下必然撞号。**判据：锁的持有区间必须包住 read+compute+write 三步**（参照仓内参考实现的既有形态）。
4. ★★★ **窗口谓词要问「作用在哪个粒度」**：过滤 turn 行再取会话最早 ⇒ 跨窗口会话的时间线错位。**判据：窗口语义必须作用在业务对象本身（会话），而不是它的从属行。**
5. ★★★ **延后的前置条件要在延后时重新核**：形态表按**形态**枚举 ⇒ 同一形态的第二个调用点天然落在表外 ⇒ 「先补表再改码」在表已存在时会把修复无限期推后。**判据：延后条目每次复核都要问「前置条件现在满足了吗」。**
6. ★★★ **「事实源只有一处」要落到断言**：同一语义序（严重度）在 Go 与 SQL 各存一份、无对齐断言 ⇒ 静默分叉。**判据：两份事实源之间必须有互相钉住的测试。**
7. ★★ **基线对照是判定「回归 vs 历史噪声」的唯一手段**：同一门在基线树绿、在 HEAD 红 ⇒ 窗口内引入。
8. ★★ **门自身的读数要复核**：`guards 全绿` 这类读数写下时可能就不成立 ⇒ 复核必须在**该提交的工作树**上跑，而不是在更晚的树上。
