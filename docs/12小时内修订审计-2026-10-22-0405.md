### 4.1 C1：客户端侧失败终于看得见（刷新作业 + 只读巡检）

**根因**：两个脚本的 `de()` 都以 `... 2>&1 || true` 结尾 ⇒ **psql 的退出码被丢弃**；
而判据 `sql_failed()` 只认**服务端** SQL 错误（输出里有 ERROR/FATAL 行）。
⇒ 客户端侧失败**根本不产生那种文本** ⇒ 全部漏判。

**修法（一处改动覆盖全部调用点）**：在 `de()` 里**保留退出码**，并把「退出码≠0」翻译成与服务端错误**同形**的 `ERROR:` 前缀
⇒ 下游既有的 `sql_failed()` 判据**一字不改**就能判出来；**不改变任何调用点的语义**（失败仍然是失败，只是终于被看见）。

**证据（无库实跑，注入假 `PSQL_CMD`，不触碰任何数据库）**：

```
══ ursm-snapshot-slot-refresh.sh（刷新作业）══
  ✔ 服务端 ERROR（psql exit 1）        expect=3 got=3
  ✔ 客户端：连不上（exit 2）           expect=3 got=3
  ✔ 客户端：podman socket 不可用（125）expect=3 got=3
  ✔ 客户端：命令不存在（127）          expect=3 got=3
══ ursm-snapshot-health.sh（只读巡检）══
  ✔ 4/4 同上，expect=3 got=3
```

修前同一组用例的实测（代理 C 复现）：`psql:` / `command not found` 两类分别得到
`exit=1` 且日志行是 `refreshed rows=psql: …` / `refreshed rows=…: no_such_binary_xyz: command not found`
⇒ **错误文本被当成刷新行数**，而退出码是 1（与「检出数据问题」同形，运维分不开）。

> ★ 为什么巡检脚本的同一处缺陷**更严重**：它的量具自检是
> `control=$(de …)` ⇒ `if sql_failed "$control" || [ -z "$control" ]`。
> 客户端失败时 `control` 是「`Error: unable to connect to Podman socket`」⇒
> `sql_failed` 不匹配、但**非空** ⇒ **自检通过** ⇒ 脚本一路跑到底并报 OK
> ⇒ 正是该脚本自己注释里写的**最危险的一种故障形态：「量具坏了却在报绿」**。
