# 供应商协议多路化优化方案

> 目标：将供应商设置从「一对单协议」改造为「一对多协议 endpoint」架构，按模型的原厂 vendor 自动匹配最精准的协议，实现参数透传与原厂兼容性最优解。

参考文档：
- 入站协议规范：[docs/client-formats/](client-formats/README.md)（OpenAI / Anthropic / Responses / Gemini）
- 出站原厂规范：[docs/vendor-formats/](vendor-formats/README.md)（OpenAI / Anthropic / Gemini / DeepSeek / Qwen / GLM / Kimi / Mistral / Grok / Ollama / vLLM / OpenRouter 等）
- 序列化管线：[docs/format-conversion/serialize-pipeline.md](format-conversion/serialize-pipeline.md)
- 方言解析：[docs/format-conversion/dialect-resolution.md](format-conversion/dialect-resolution.md)
- Internal Representation：[internal/ir/detect.go](../internal/ir/detect.go)（`DetectProtocol`）+ [internal/paramreg/dialect.go](../internal/paramreg/dialect.go)
- URL 构造 SSOT：[internal/upstreamurl/upstreamurl.go](../internal/upstreamurl/upstreamurl.go)

## 1. 现状与瓶颈

### 1.1 当前架构：每个供应商只挂一个协议 + 一个 base URL

`providers` 表只有单值列：

```sql
-- sql/objects/tables/providers.sql:16-17
protocol text NOT NULL,            -- 单值枚举：openai-completions / openai-responses / anthropic-messages / gemini-generate / ollama-native
base_url text NOT NULL,            -- 单值 URL
```

`credential_model_bindings`、`upstream_node_view`、以及最终落地的 `provider.Candidate`（`provider/client.go:105-205`）都继承这对单值字段：

```go
// provider/client.go:105-109
type Candidate struct {
    ...
    BaseURL  string `json:"base_url"`
    Protocol string `json:"protocol"`
    ...
}
```

枚举值收紧在 `provider/catalog/protocol.go:21-27`：

```go
ProtocolOpenAICompletions = "openai-completions"
ProtocolOpenAIResponses   = "openai-responses"
ProtocolAnthropicMessages = "anthropic-messages"
ProtocolGeminiGenerate    = "gemini-generate"
ProtocolOllamaNative      = "ollama-native"
```

### 1.2 路由决策：客户端协议 × 候选协议

入站 `internal/ir.DetectProtocol` 推断客户端协议（`openai-chat` / `openai-responses` / `anthropic-messages` / `gemini-generate`），落到 `params.ClientProtocol`。

出站在 `domains/streaming/executors/executor_dispatch.go:839` 走 `switch cand.Protocol` 分发：

```go
switch cand.Protocol {
case providercatalog.ProtocolAnthropicMessages:
    result, execErr = e.executeAnthropic(...)
case providercatalog.ProtocolGeminiGenerate:
    // 目前直接返回 KindUnsupportedFeature，未实现！
    result, execErr = nil, &upstreampkg.Error{Kind: errorsx.KindUnsupportedFeature, ...}
default:
    result, execErr = e.executeOpenAI(...)
}
```

URL 构造单值固定在执行器内：

```go
// domains/streaming/executors/executor_chat.go:126
upstreamURL := upstreamurl.ChatCompletionsURL(cand.BaseURL)
// domains/streaming/executors/executor_anthropic.go 同样
upstreamURL := upstreamurl.MessagesURL(cand.BaseURL)
```

### 1.3 三类典型痛点

| 痛点 | 现状 | 后果 |
|------|------|------|
| **A. 多协议供应商被锁一种协议** | 同一家供应商同时支持 OpenAI Chat 与 Anthropic Messages（如 OneAPI、newapi、自部署的 GoCodeGeek）。当前只能选一种协议并把另一种的所有流量强行 bridge（IR parse→serialize 双向），参数大量被 paramguard 裁掉。 | 客户端发 Anthropic 时，模型虽然是对方 native 的 Claude 模型，body 必须经过 OpenAI Chat 中转+桥接，`thinking`、`cache_control`、`input_schema`、`metadata.user_id` 这些字段丢失 |
| **B. 单一 base URL 不够精准** | 第三方聚合（OpenRouter、Poe、OpenAI Proxy、SiliconFlow）往往把 OpenAI 兼容端点、Google Gemini 端点、Anthropic 兼容端点挂在不同 path。当前的 `https://xxx/v1` 一律 `/v1/chat/completions` 路由，跨端点同协议拼凑错误（Gemini 走 OpenAI path 必 404）。 | OpenRouter 等多端点供应商需要手动支持 `gemini-generate`，但 `providers.protocol` 无法表达「同一 supplier 既有 OpenAI 端点也有 Gemini 端点」 |
| **C. vendor family 与协议强绑定** | `internal/paramreg.dialect.Resolve(catalogCode, protocol)` 在 model 路由选路时只关心 `cand.Protocol`，不关心「这个 candidate 实际承载哪个 vendor family 的模型」。当 candidate 的 catalog 是聚合中转时，模型是 Claude / Gemini 都可能，路由层只能「按 supplier 单 protocol 一种序列化方式」硬塞。 | Claude Code → 任何供应商都会桥接成 OpenAI Chat，原因不是 client 协议不对，而是 supplier 只能声明一种 protocol |

参考：[docs/vendor-formats/README.md](vendor-formats/README.md) §协议摘要表 — 每个厂商都有 native 协议。

## 2. 设计目标

| 目标 | 含义 | 验收 |
|------|------|------|
| **G1. 一对多协议 endpoint** | 一个供应商可注册 N 个 `(protocol, base_url)` endpoint | 新增 `provider_endpoint_protocols` 表（多值子表），CRUD 完整 |
| **G2. 模型原厂自动匹配** | 请求的模型通过 `models_canonical.family`（如 `anthropic-claude` / `openai-gpt` / `google-gemini`）反查到对应 endpoint 的 `vendor_native` 标识，命中即用 | 网关 dispatch 路径上 `EndpointSelector` 显式选择 endpoint，含日志 + metric |
| **G3. 主协议降级** | 未匹配到 vendor native endpoint 时，回退到供应商的 primary endpoint（保留原 `providers.protocol` + `providers.base_url` 语义） | 同主协议改造前行为；回归 P0 探活场景 |
| **G4. 协议完全对齐时透传** | 客户端协议 == 供应商 vendor native endpoint 协议时，跳过 IR 双向桥接，body 仅做 schema 完整性校验，私有字段完整透传 | Claude Code + Anthropic 直连场景，body 字节级与原 SDK 输出一致 |
| **G5. 不匹配时仍走 IR 桥接** | 客户端 OpenAI → 供应商 Anthropic native endpoint → 触发现有 `executeAnthropic` / `executeOpenAI` 桥接管线 | 保留现有一切 asymmetrical 流程；不引入第二套桥接 |
| **G6. UI 改造**：SettingsTab 上可视化管理多协议 + 主协议显式标注 | 在原有「主协议」基础上加「原生支持协议」列表 | `web/src/views/provider-detail/SettingsTab.vue` 新增 endpoint 列表组件 |
| **G7. 向后兼容** | 没有 endpoint 子表的供应商继续走单协议逻辑；只填一项也视为合法配置 | 原有所有功能、E2E、回归测试零破坏 |

## 3. 总体设计

### 3.1 顶层架构图

```
┌────────────────────────────────────────────────────────────────┐
│ Client (OpenAI Chat / Anthropic / Responses / Gemini / ... )   │
└─────────────────────────────┬──────────────────────────────────┘
                              │ POST /v1/{chat|messages|responses|...}
                              ▼
┌────────────────────────────────────────────────────────────────┐
│ IR DTO + DetectProtocol → ClientProtocol                       │
│ params.ClientProtocol = openai-chat | openai-responses | ...   │
└─────────────────────────────┬──────────────────────────────────┘
                              ▼
┌────────────────────────────────────────────────────────────────┐
│ URSM v2 Router: 选 candidate（credential × model binding）     │
│ 输出: Candidate{Protocol=主协议, BaseURL=主URL,                 │
│         NativeEndpoints=[{protocol, base_url, vendor_native},  │
│                          ...]}                                  │
└─────────────────────────────┬──────────────────────────────────┘
                              ▼
┌────────────────────────────────────────────────────────────────┐
│ EndpointSelector (NEW): 按客户端协议 + 模型 family 选 endpoint  │
│ 1. candidate.NativeEndpoints 命中 ClientProtocol & family      │
│    → NativeEndpoint (透传路径)                                 │
│ 2. 命中任一 NativeEndpoint.protocol == ClientProtocol           │
│    → 同协议但不是该 vendor family 的 → NativeEndpoint            │
│      (走现有 IR 桥接, 但用 endpoint 的 base_url)               │
│ 3. 全未命中 → 回退 Candidate 主协议 BaseURL（兼容）              │
└─────────────────────────────┬──────────────────────────────────┘
                              ▼
┌────────────────────────────────────────────────────────────────┐
│ Executor dispatch (executeOpenAI / executeAnthropic / ...)      │
│ 透传路径: SkipIRBridge = true → 不 parse→IR→serialize,         │
│           body 由 paramreg 走「passthrough + 关键字段校验」      │
└────────────────────────────────────────────────────────────────┘
```

### 3.2 关键不变量

1. **SSOT 不迁移**：保留 `providers.protocol` + `providers.base_url` 作为「主协议 / 主 base URL」（`is_primary=true` 的那一行 endpoint 在语义上等价）。这样老数据零迁移。
2. **`Candidate.Protocol` 含义不变**：继续保留「主协议」字段，新增并列字段 `NativeEndpoints []CandidateEndpoint` 描述供应商声明支持的全部 endpoint。
3. **executor 协议分支不变**：现有的 `executeAnthropic` / `executeOpenAI` / `executeOpenAIResponses` 是协议终态。区别在于「目标 URL 从哪取」「body 是否走 IR 桥接」。
4. **endpoint base URL 走 SSoT**：构造 URL 沿用 `internal/upstreamurl` (`ChatCompletionsURL` / `MessagesURL` / `ResponsesURL` / `GenerateContentURL`)，不重新发明。

## 4. 数据模型

### 4.1 新增表 `provider_endpoint_protocols`

```sql
-- 2026-09-24 协议多路化（新建独立子表，避免在 providers 上 ALTER 一对多列）
-- 关系：(provider_id, protocol) UNIQUE
-- 与 providers.protocol/base_url 互为冗余：当只有一条记录且 is_primary=true 时，
-- 该记录与 providers.protocol/base_url 同步（双写）—— 见 §10 同步策略。

CREATE TABLE public.provider_endpoint_protocols (
    id              bigserial PRIMARY KEY,
    provider_id     bigint       NOT NULL,
    tenant_id       text         NOT NULL DEFAULT 'default',
    protocol        text         NOT NULL,
    base_url        text         NOT NULL,
    -- is_primary = true 的记录同步到 providers.protocol + providers.base_url。
    -- 当只有一条记录时强制 is_primary = true（CHECK）。
    is_primary      boolean      NOT NULL DEFAULT false,
    -- vendor_native 标识该 endpoint 服务哪家原厂，路由按模型 family 匹配。
    -- 取值集合 = models_canonical.family 的子集：
    --   anthropic-claude, openai-gpt, openai-image, openai-embedding,
    --   google-gemini, google-gemma, xai-grok, mistral, meta-llama,
    --   cohere-command, deepseek, qwen, glm, kimi, ark-doubao,
    --   openrouter, vllm, ollama, etc.
    -- NULL 表示该 endpoint 是兜底主端点（与 provider 主协议一致），
    -- 不参与 family 匹配，仅被显式请求或 fallback 命中。
    vendor_native   text,
    -- 端点启停 / 探活状态
    enabled         boolean      NOT NULL DEFAULT true,
    weight          smallint     NOT NULL DEFAULT 100,  -- 多 endpoint 同 family 时的优先级，值小优先
    notes           text,
    -- 健康跟踪（与 credentials 健康切分；同一个 provider 跨 endpoint 独立计数）
    health_status         text    NOT NULL DEFAULT 'unknown',
    health_checked_at     timestamptz,
    health_latency_ms     integer,
    health_error          text,
    -- 自动重试触发的次数（最近 24h），便于后续融断
    consecutive_failures  integer NOT NULL DEFAULT 0,
    last_failure_kind     text,
    created_at            timestamptz NOT NULL DEFAULT now(),
    updated_at            timestamptz NOT NULL DEFAULT now(),
    -- provider_id + protocol 唯一（同一供应商不能声明两个同协议 endpoint）
    CONSTRAINT provider_endpoint_protocols_unique
        UNIQUE (provider_id, protocol),
    CONSTRAINT provider_endpoint_protocols_provider_fk
        FOREIGN KEY (provider_id) REFERENCES providers(id) ON DELETE CASCADE,
    CONSTRAINT provider_endpoint_protocols_protocol_check
        CHECK (protocol = ANY (ARRAY[
            'openai-completions','openai-responses',
            'anthropic-messages','gemini-generate','ollama-native'
        ])),
    -- 至少一个端点必须是 primary（与 providers.protocol/base_url 同步）
    -- 唯一性不强制保证，但我们用一个 partial unique index 实现：
    CONSTRAINT provider_endpoint_protocols_base_url_nonempty
        CHECK (length(base_url) > 0)
);

-- 部分唯一索引：每个 provider 至多一条 is_primary=true
CREATE UNIQUE INDEX provider_endpoint_protocols_one_primary
    ON provider_endpoint_protocols (provider_id)
    WHERE is_primary = true;

CREATE INDEX provider_endpoint_protocols_provider_idx
    ON provider_endpoint_protocols (provider_id, protocol);
CREATE INDEX provider_endpoint_protocols_family_idx
    ON provider_endpoint_protocols (provider_id, vendor_native)
    WHERE vendor_native IS NOT NULL AND enabled = true;
```

> 字段选型原因：与现有 `providers` / `credentials` schema 风格一致；`vendor_native` 直接复用 `discovery.vendorCanonicalFamilies` 的 family 字符串（`anthropic-claude` / `openai-gpt` / `google-gemini` 等，见 [discovery/normalize.go:43](../discovery/normalize.go)），避免新建枚举值。

### 4.2 种子数据策略（迁移）

```sql
-- V8XX__multi_protocol_endpoints.sql（同 deployment 一次性数据搬运）
-- 对所有现存供应商，按 (providers.protocol, providers.base_url) 插入主端点。
INSERT INTO provider_endpoint_protocols (
    provider_id, tenant_id, protocol, base_url, is_primary, vendor_native
)
SELECT
    p.id, p.tenant_id, p.protocol, p.base_url,
    TRUE,
    -- 推导 vendor_native：按 provider_catalog.vendor_name + model_canonical 启发式
    -- （详见 §10.1 helper）
    CASE pc.code
        WHEN 'anthropic' THEN 'anthropic-claude'
        WHEN 'openai'    THEN 'openai-gpt'
        WHEN 'google-gemini' THEN 'google-gemini'
        WHEN 'azure'     THEN 'openai-gpt'
        WHEN 'openrouter' THEN 'openrouter'
        ELSE NULL  -- 聚合 / 第三方：vendor_native = NULL，由用户后期填
    END
FROM providers p
LEFT JOIN provider_catalog pc ON pc.code = p.catalog_code
WHERE p.deleted_at IS NULL
ON CONFLICT (provider_id, protocol) DO NOTHING;
```

新增可选项不强制一次性全员回填（迁移仅插入主端点，其他 endpoint 留给运营手动添加）。前端 §7 提供「根据 catalog 推荐」一键生成。

### 4.3 候选加载 (candidate) 集成

`provider/client.go` 中 `Candidate` 增加并列字段：

```go
// provider/client.go ~line 109 之后新增
type Candidate struct {
    ...
    BaseURL    string `json:"base_url"`     // 主 base URL（不变）
    Protocol   string `json:"protocol"`    // 主 protocol（不变）

    // NativeEndpoints 是该 candidate / supplier 声明支持的全部 (protocol,base_url) endpoint。
    // 至少包含一项（is_primary=true 的那一条）。FamilySelector 按 family 或
    // protocol 选出最佳一条；未命中时回退到 (BaseURL, Protocol) 主端点。
    NativeEndpoints []CandidateEndpoint `json:"native_endpoints,omitempty"`
}

type CandidateEndpoint struct {
    ID           int64  `json:"id"`
    Protocol     string `json:"protocol"`
    BaseURL      string `json:"base_url"`
    IsPrimary    bool   `json:"is_primary"`
    VendorNative string `json:"vendor_native,omitempty"` // NULL = 主协议
    Enabled      bool   `json:"enabled"`
    Weight       int    `json:"weight,omitempty"`
    HealthStatus string `json:"health_status,omitempty"`
}
```

SQL 加载（`provider/client.go` 的 `loadCandidatesForResolve` / 类似查询）追加 LEFT JOIN：

```sql
LEFT JOIN LATERAL (
    SELECT
        json_agg(json_build_object(
            'id',            pep.id,
            'protocol',      pep.protocol,
            'base_url',      pep.base_url,
            'is_primary',    pep.is_primary,
            'vendor_native', pep.vendor_native,
            'enabled',       pep.enabled,
            'weight',        pep.weight,
            'health_status', pep.health_status
        ) ORDER BY pep.is_primary DESC, pep.weight ASC) AS endpoints
    FROM provider_endpoint_protocols pep
    WHERE pep.provider_id = p.id AND pep.enabled = true
) ep ON true
```

Candidate 反序列化时 `endpoints []byte -> NativeEndpoints`。

### 4.4 model ↔ family 推导（已存在的 SSOT 复用）

`models_canonical.family` 已由 [discovery/normalize.go:248 `InferFamily`](../discovery/normalize.go) 写入：

```go
"claude" → "anthropic-claude"
```

## 5. 路由匹配策略（EndpointSelector）

### 5.1 模块位置

新增包 `internal/endpointselect/`（或作为 `domain/routing` 子包，正式命名待 2.x 决策）。
对外暴露 `Select(c Candidate, wantProtocol, wantFamily string) EndpointDecision`。

### 5.2 决策算法

```go
type EndpointDecision struct {
    Protocol       string  // 落到哪个 protocol
    BaseURL        string  // 落到哪个 URL
    Passthrough    bool    // true = 客户端协议 = endpoint protocol = model family，body 整包透传
    EndpointID     int64   // 命中哪条 endpoint；0 = 主端点
    MatchedFamily  string  // 命中哪个 vendor family（透传时回填；用于 metric label）
    Reason         string  // human-readable，选路日志输出
}

// Select 优先级（先匹配再降级）：
//
//   Stage 1: NativeEndpoints 中找同时满足
//            - protocol == wantProtocol
//            - vendor_native == wantFamily
//            - enabled = true
//            → Passthrough = true（family 完全对齐）
//
//   Stage 2: 找不到 Stage1 命中；寻找 protocol == wantProtocol & enabled
//            （同协议不同 family，即「客户端协议 = 该 endpoint 协议，但模型来自另一家」）
//            → Passthrough = false（走 IR 桥接，但用 endpoint.base_url 替换 cand.BaseURL）
//
//   Stage 3: 找 vendor_native == wantFamily & enabled
//            （family 对齐但客户端协议不同 — 例：Anthropic 客户端请求 Claude 模型
//             在 OpenAI 端点，必须先跨协议桥再发）
//            → Passthrough = false（走 IR 桥接）
//
//   Stage 4: 回退 cand.BaseURL + cand.Protocol（主协议，兼容老行为）
//            → Passthrough = (wantProtocol == cand.Protocol)
//
//   决策结果必须可解释，每条 reason 落到 trace / metric（label: rule=stage1|stage2|stage3|stage4）。
func Select(c Candidate, wantProtocol, wantFamily string) EndpointDecision { ... }
```

### 5.3 wire 集成点

- `domains/streaming/executors/executor_dispatch.go:839` 改造：在 `switch cand.Protocol` 之前调用 `EndpointSelector.Select(c, params.ClientProtocol, modelFamily)`，把结果写入 `execParams`，再走 switch：
  - `decision.EndpointID == 0` → 完全等价改造前
  - `decision.EndpointID != 0` → 把 `cand.BaseURL` 临时替换为 `decision.BaseURL`，把 `cand.Protocol` 临时替换为 `decision.Protocol`，把 decision 透传给执行器

- 模型 `family` 来源：`params.ModelCanonical.Family`（已在 `models_canonical` 落盘）或由 `discovery.InferFamily(model)` 兜底。

- 关键 metric label：`endpoint_match_rule=stage1|stage2|stage3|stage4|miss` + `endpoint_protocol`、`endpoint_vendor_native`、`endpoint_id`（命中具体 endpoint 时记录，便于运维查「为什么这请求走的是 X 端点」）。

### 5.4 失败 / 无 endpoint 场景

- `NativeEndpoints` 为空：极少数极端（迁移失败），回退 `(c.BaseURL, c.Protocol)` 并记录 `log.Warn` + metric `endpoints_empty`。
- 全部 endpoint 不 enabled：等同主协议强制执行（兼容老语义），但日志 `provider_no_endpoint_enabled` 提示运营补。

## 6. 透传契约（Passthrough Contract）

### 6.1 触发条件

`Select()` 返回 `Passthrough = true` 当且仅当：
- `wantProtocol == decision.Protocol`（客户端协议 == 选中 endpoint 协议）
- `wantFamily == decision.VendorNative`（客户端请求的模型原厂 == endpoint 声明的 vendor family）

这是「客户端协议与供应商原厂协议一致」时的最佳情况：网关既不需要 parse→IR，也不需要 serialize→target，直接把客户端原始 body 字节流（已校验 schema 完整）转给上游。

### 6.2 透传路径的 body 处理

```
原始 body（客户端写入）
   │
   ▼
(1) 字节级 schema 完整性快速校验（不解析为 IR）：
    - 检测必填顶层字段：model 字段存在且非空、messages / contents / input 三选一至少一个
    - JSON 顶层 schema 类型校验（必须是 object/array）
    - 失败 → 400 + 错误: schema_invalid_for_passthrough
   │
   ▼
(2) passthrough paramguard（专用规则，非 IR-based）：
    - 客户端协议 = openai-chat → 检查 stream、tools[].function.parameters 等 OpenAI 必填
    - 客户端协议 = anthropic-messages → 检查 max_tokens 必填、anthropic-version header 必带
    - 客户端协议 = openai-responses → 检查 max_output_tokens / input[] 格式
    - 客户端协议 = gemini-generate → 检查 contents[] 至少一项
   │
   ▼
(3) 直接 POST 到 endpoint.URL
```

### 6.3 响应路径

- 客户端协议 = endpoint 协议 = 模型原厂 → 响应 SSE/JSON 字节流**直接转发**给客户端，不解析为 IR、不裁剪私有字段。
- 实现要点：在 `domains/streaming/executors/executor_chat.go` / `executor_anthropic.go` 中新增 `PassthroughNonStream` / `PassthroughStream` 函数分支，仅做 status code 透传 + SSE chunk 转发。

### 6.4 透传路径的字段白名单

不在透传里裸跑任何字段。passthrough paramguard 对**必填字段**和**字段类型**做严格校验，确保：
- 私有字段（如 `cache_control`、`thinking`、`input_schema`、`previous_response_id`）原样通过；
- 但 OpenAI SDK 客户端发来的非法字段（如 `max_tokens: "100"` 字符串）会在 passthrough paramguard 阶段被拒绝（400 schema_invalid），避免上游返回 5xx 不明错误。

具体规则表（passthrough mode）：
| 客户端协议 | 必填字段 | Schema 限制 |
|------------|----------|-------------|
| openai-chat | `model`, `messages` 或 `prompt` | `messages` 数组每项含 `role`+`content`，`role` ∈ `system\|user\|assistant\|tool\|function\|developer` |
| openai-responses | `model` + (`input` 数组 / `instructions`) | `input[]` 每项必须含 `role`，`role` ∈ `user\|assistant\|system\|developer` |
| anthropic-messages | `model`, `messages`, `max_tokens` | `messages` 数组每项 `role` ∈ `user\|assistant`，`max_tokens` 整数 |
| gemini-generate | `contents` 数组 | `contents[]` 每项 `role` ∈ `user\|model` |

### 6.5 何时「不能」透传

下列情形强制走 IR 桥接，不允许透传（即使协议字面值一致）：

| 场景 | 原因 |
|------|------|
| 请求带 `extensions` 自定义块（自定义 key 非 vendor SDK 输出） | 透传会把无效字段丢给上游，导致 4xx |
| 模型 family 与 vendor_native 不一致（例：gpt-5 落在 anthropic-claude endpoint 上 —— 配置错误） | 应 fail-fast，避免无谓试错 |
| endpoint `supports_native_responses=false`（专指 openai-responses 透传） | 老供应商 Responses API 不一定完整实现，要求按 `SupportsNativeResponses` flag 过滤 |

```go
// 直接 POST body 到 endpoint URL, 响应字节级返回客户端。
func (e *Executor) PassthroughNonStream(w http.ResponseWriter, params *ExecParams,
    cand provider.Candidate, decision endpointselect.EndpointDecision) error {

    upstream, body, err := buildPassthroughRequest(params, cand, decision)
    if err != nil { return err }

    resp, err := http.DefaultClient.Do(upstream)
    if err != nil { return err }
    defer resp.Body.Close()

    w.WriteHeader(resp.StatusCode)
    _, err = io.Copy(w, resp.Body)
    return err
}

    // 与 NonStream 同构, 但用 bufio.Scanner 按行/SSE event 转发, 不解析 IR。
```

## 9. 数据兼容与同步策略

### 9.1 主端点 ↔ providers.protocol/base_url 双写

主端点（`is_primary=true` 那条）与 `providers.protocol/base_url` **始终同步**，写入事务化：

```
UPDATE providers SET protocol = ?, base_url = ?, updated_at = now() WHERE id = ?;
UPDATE provider_endpoint_protocols SET is_primary = true WHERE id = ?;
UPDATE provider_endpoint_protocols SET is_primary = false WHERE provider_id = ? AND id != ?;
```

读路径以 `provider_endpoint_protocols` 为 SSOT：`SELECT ... FROM provider_endpoint_protocols WHERE provider_id=? AND is_primary=true` 得到主协议；`providers.protocol/base_url` 列视为「冗余缓存」，用于旧代码与 EXPLAIN。

### 9.2 旧逻辑兼容

迁移完成后：
- 没有任何 endpoint 记录的 provider（理论上不存在，迁移脚本保证）— 直接当主端点用，等价旧行为。
- 只有 1 条 endpoint 的 provider（最大多数）— Stage 4 永远命中该 endpoint，行为 100% 等价旧版。
- 多 endpoint 的 provider（本次新功能目标用户）— Stage 1/2/3 启用。

### 9.3 GEM-generate 灰度

Gemini 在多协议决策的 Stage 2/3 命中是关键路径，但 §8.3 真实 Gemini executor 是「前置依赖」。
具体灰度计划：
- **Phase 1（仅 endpoint 表 + UI）**：上线 endpoint 表 + UI 主协议编辑，但 dispatch 完全 bypass `decision`，等价旧行为。验证 schema / 性能 / UI。
- **Phase 2（只读 endpoint 选择）**：dispatch 引入 `EndpointSelector`，但只读 `Stage 4 fallback`（任意 endpoint 命中都退回主端点）。观察 metric `endpoint_decision`。
- **Phase 3（实跑多协议）**：Stage 1/2/3 启用，逐 supplier 灰度（OpenAI Chat → Anthropic vendor native first、Anthropic → OpenAI vendor native first，最后全量）。
- **Phase 4（透传）**：开启 `Passthrough=true` 路径，先对 Claude Code ↔ Anthropic 直连场景试点，无回归后铺到所有「family=endpoint.vendor_native」组合。

每个 Phase 配：[docs/01-requirements](../01-requirements) 的 R-template 工单 + metric dashboard。

## 11. 风险与缓解

| 风险 | 影响范围 | 缓解 |
|------|----------|------|
| 迁移脚本「is_primary 必须唯一」被现有数据打破 | 历史脏数据可能有重 primary | 迁移前用一段清理 SQL：`UPDATE provider_endpoint_protocols SET is_primary=false WHERE id NOT IN (SELECT MIN(id) ... GROUP BY provider_id)` |
| 透传路径上的未识别字段导致上游 400 | 客户端 SDK 私有字段（如 Anthropic `cache_control`） | 已通过 §6.4 schema 完整性校验 + passthrough paramguard 双门禁，仅对**字段类型错**返回 400，不裁剪未知字段 |
| Gemini executor 未实现但新决策路径会命中 gemini-generate | 新 dispatch 路径找到 gemini-generate endpoint 时报 unsupported | §8.3 把 Gemini executor 列为「前置依赖」，不与本次多协议同时上线；先开 UI / 数据迁移，决策仍走 fallback，Gemini 实施完成后再开放 Stage 1/2/3 |
| 多 tenant 互串 | endpoint 表跨 tenant_id 误读 | 全部 SQL 加 `tenant_id = 'default' WHERE`；保持与 providers 表的 tenant_id 字段语义一致 |
| 切换主 endpoint 时网络抖动 | 切换瞬间路由可能命中旧 endpoint | 「主 endpoint 切换」是低频管理动作；操作时直接给前端确认提示 + 5s 内仅新连接走新 endpoint（loadbalancer.healthChecker 已在 stage 2 优化） |
| 多 endpoint 模型 family 重叠（如 OpenRouter 同时说自己承载 anthropic-claude 与 openai-gpt） | URSM 选错 candidate 导致 latency / 价格异常 | `endpointselect.Select` 在 family 与 client_protocol 双匹配层之外，加 `cand.Weight` / `weight` 的二次 tiebreak；URSM `routing_resolve` 层面仍按 score 排序，endpoint 决策只是 base_url 的微调 |
| 与现有 `protocol_normalize.go` 拼写不一致 | 用户在 UI 输 `openai-response` 时返回 400 | UI 端做枚举白名单，不允许自定义字符串；后端依然走 `NormalizeProviderProtocol`（[provider/catalog/protocol_normalize.go](../provider/catalog/protocol_normalize.go)） |
| 透传路径读取 response 字节级转发会破现有红黄绿契约 | client SDK 期望 `data: [DONE]` 等 | response 字节级不解析，**直接**拷贝 SSE / NDJSON；不动 chunk 边界、不加 header — 等价于把上游响应当黑盒数据 |
| 性能：每次请求多打一次 endpoint 列表内存读取 | URSM Dispatch 阶段 | `provider_endpoint_protocols` 通过 SQL LEFT JOIN LATERAL 一次拉取（`Candidate.NativeEndpoints` 字段），运行时不查 DB；若有 1w QPS，100μs × 1w ≈ 1 CPU 核心，影响可忽略 |

| 目标 | 验收 |
|------|------|
| G1 一对多协议 | `provider_endpoint_protocols` 表存在、可 CRUD；`Candidate.NativeEndpoints` 在 resolve 接口中存在 |

| G4 协议完全对齐时透传 | Claude Code → Anthropic 直连场景下，gateway 到上游 body 与 Claude SDK 直接发出的 body 字节级一致；metric `gateway_endpoint_passthrough_total > 0` |

| G7 向后兼容 | 旧供应商（无 endpoint 子表但有数据）的所有功能不变；迁移零停机 |
