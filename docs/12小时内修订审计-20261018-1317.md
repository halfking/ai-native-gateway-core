## 2. A1（P0，已落地）：会话级 advisory lock 的解锁失败泄漏

### 2.1 问题

`438a24653`（§61）新增 `domains/ursm/v2/persist/writerguard.go`，
用**会话级** `pg_try_advisory_lock` + `pool.Acquire()` 显式持有的专用连接，
保证同一时刻只有一个快照写入者。

原实现的释放闭包是：

```go
var unlocked bool
err := conn.QueryRow(relCtx, "SELECT pg_advisory_unlock($1)", key).Scan(&unlocked)
conn.Release() // 无论解锁成不成功，连接都必须归还
if err != nil {
    return err
}
if !unlocked {
    return errGuardNotHeld
}
return nil
```

**`conn.Release()` 在错误判读之前无条件执行。**

### 2.2 为什么这是 P0：会话级锁跟着连接一起回池

会话级 advisory lock 绑定在 **PG 会话**上，而不是事务上。
`pgxpool` 归还连接时做什么（`vendor/github.com/jackc/pgx/v5/pgxpool/conn.go`
的 `Release()`，v5.9.2）：

```go
if conn.IsClosed() || conn.PgConn().IsBusy() || conn.PgConn().TxStatus() != 'I' {
    res.Destroy()
    ...
}
if c.p.isExpired(res) { res.Destroy(); ... }
if c.p.afterRelease == nil { res.Release(); return }
```

它只判断 **closed / busy / in-tx / expired**。
`grep -rn advisory vendor/github.com/jackc/pgx/v5/pgxpool/` → **零命中**：
**pgxpool 从不碰 advisory lock。**

⇒ 解锁失败时把这条连接归还，等于把锁连同连接一起借给下一个使用者。
此后该实例**永远**抢不到锁，而症状只是"别的实例一直在写"——
没有任何告警指向泄漏源。这与 §61 已经用变异 M4 防住的
"拿已取消的 ctx 去解锁"是**同一个终局**，但那条路径当时被守卫了，
这条没有。

**关键点**：这不是"锁没释放"的小问题。它精确命中了 §61 整道守卫
要防的那件事——多写入者。而 §61 的注释自己写着
「⚠ 这道门只保证写入者的**数量**是 1」；锁泄漏会让这道门自己失效，
且失效后**仍然显示 held/yielded 的正常日志**。

### 2.3 为什么不是每个连接都会中招

命中需要 `pg_advisory_unlock` **本身失败**（网络中断、2s `guardUnlockTimeout`
打满、服务端断开）。低频，但**一旦命中就是每轮命中**——
每轮 persist 都会重新 `Acquire` 一条连接、解锁失败、再泄漏一条，
直到连接池被泄漏的会话占满。属于低频高代价。

### 2.4 落地处置

抽出纯函数钉住决策表（对齐本仓 `providerErrorAggregatorClassifyStall`
的既有写法），并在失败分支**硬关连接**让服务端结束会话带走锁：

```go
func guardUnlockOutcome(unlockErr error, unlocked bool) (destroyConn bool, err error) {
	switch {
	case unlockErr != nil:
		return true, unlockErr      // 锁可能还在连接上 ⇒ 硬关，不归还
	case !unlocked:
		return false, errGuardNotHeld // 服务端已回答"没有锁" ⇒ 归还安全
	default:
		return false, nil
	}
}
```

`TryLock` 的释放闭包改为按该结论处置：

```go
destroyConn, rerr := guardUnlockOutcome(unlockErr, unlocked)
if destroyConn {
    closeCtx, cancel := context.WithTimeout(context.WithoutCancel(relCtx), guardUnlockTimeout)
    defer cancel()
    _ = conn.Conn().Close(closeCtx)
    return rerr
}
conn.Release()
return rerr
```

`!unlocked` 仍归还而非硬关：服务端明确回答"这条连接上没有该锁"，
归还不会泄漏，硬关属于过度处置（会把一次可恢复的状态异常放大成断连）。

### 2.5 判据（含变异）

3 条决策表门 + 1 条**接线门**：

| 门 | 钉住 |

| B：`Release()` 移到决策之前 | ✅ 红 |
