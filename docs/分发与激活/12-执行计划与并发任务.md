# 12. 执行计划与并发任务

> 本文档是 11-实施路线图 的执行细化，将每个里程碑拆分为**可分配**的并发任务，
> 标注依赖、负责人、产出物、可并行性，便于多 Agent 并行开发。
>
> **编号说明**：本文档使用 `M{milestone}-T{task}` 编号（如 M0-T01），
> 11-实施路线图使用 `M{milestone}-{role}{seq}` 编号（如 M0-M1、M0-C1）。
> 两套编号独立，不一一对应。以本文档的 T 编号为准进行任务追踪。

---

## 一、组织模型

### 1.1 团队角色（10 个 Agent 并行）

| Agent | 职责 | 主要产物 |
|-------|------|---------|
| **A: Master-Go** | 主控端 Go 后端 | cmd/gateway-master / License Authority |
| **B: Client-Go-Core** | 客户端 Go 核心（licensing / 网关核心） | licensing/* 增强 / 网关业务 |
| **C: Master-Service** | 主控端 API 服务 | License / Release / Center / Collect API |
| **D: Client-API** | 客户端 API | /api/system/* |
| **E: Upgrader** | 升级守护进程 | kx-gateway-upgrader / rollback |
| **X: Master-FE** | 主控端前端 | /ops/* / /admin/* |
| **Y: Client-FE** | 客户端前端 | /setup/* / /settings/* / 首页 |
| **O: DevOps** | CI/CD / 打包 | build-master.sh / build-customer.sh |
| **Q: QA** | 测试 | 测试用例 / 报告 |
| **S: Security** | 安全审计 | 防盗版测试报告 |

### 1.2 并发约束

- **冲突文件**：同一文件只能一个 Agent 修改
- **依赖关系**：被依赖任务完成后，依赖方才能开始
- **集成点**：每周一个集成窗口，统一 merge + 测试

## 五、冲突解决规则

1. **同一文件被两人修改**：先合并者赢，后合并者 rebase
2. **API 契约变更**：必须先更新 OpenAPI 规范，再修改实现
3. **数据库 Schema 变更**：必须先更新 migration，再修改代码
4. **前端 variant 切换**：约定 `customer` 为默认 variant

## 七、关键路径与可压缩点

### 关键路径（critical path）

> ⚠️ M1 和 M2 之间无依赖关系，可完全并行。关键路径取两条分支中较长的一条。

```
分支 A（License + 激活）：M0-T01(1d) → M0-T02(2d) → M1-T02(2d) → M1-T03(2d) → M1-T10(1d) = 8d
分支 B（升级守护进程）：  M0-T01(1d) → M0-T02(2d) → M2-T02(2d) → M2-T03(2d) → M2-T07(2d) = 9d

关键路径 = max(分支 A, 分支 B) = 9d
M4 集成测试 (+5d) 在 M1+M2+M3 完成后执行 = 9d + 5d = 14d
```

**总时长估算**：12 周（14d 关键路径 + 缓冲与集成测试回归）。
