**影响面**：`make test-short` / `go test ./...` 在 `main` 上为红 ⇒ 任何依赖它做放行判断的流程（含本仓自己的 pre-push 约定）都会把红读成绿或读成「既有红」。

### P1-1　userscript capture 摄取端点：**共享字段惰性初始化 = 数据竞争**，且装配缺失时 **nil 解引用 panic**

`internal/userscriptcapture/handler.go` 的 `ServeHTTP`（进程级单例、net/http 每请求一 goroutine）在请求路径上做**惰性初始化并写回共享字段**：

```go
if h.sessionExists == nil {
    h.sessionExists = h.store.SessionExists   // ← 对共享字段的读改写
}
```

**实证**（本轮新增 `handler_race_test.go`，修前跑）：

```
WARNING: DATA RACE
Read at 0x00c0002d4db0 by goroutine 18:
  …userscriptcapture.(*Handler).ServeHTTP()  handler.go:116
Previous write at 0x00c0002d4db0 by goroutine 47:
  …userscriptcapture.(*Handler).ServeHTTP()  handler.go:117
--- FAIL: TestHandlerConcurrentSessionExistsIsRaceFree
--- FAIL: TestHandlerSessionExistsWithoutStoreIsSafe
    panic: runtime error: invalid memory address or nil pointer dereference
    …userscriptcapture.(*Store).SessionExists()  store.go:165
```

第二个 panic 的机理：`SessionExists` 直接 `s.db.Begin(ctx)`，而 `db` 是接口字段 ⇒ 装配缺失（`&Store{}`）时**空接口调用 = nil 解引用** ⇒ 这条路径由 HTTP 请求线程直接调用 ⇒ 整个请求以 panic 收场。

**修法**：`ServeHTTP` 只读**局部变量**（惰性初始化从请求路径移出）+ `SessionExists` 加 `s == nil || s.db == nil` 守卫。修后 `go test -race ./internal/userscriptcapture/` 全绿。

### P1-2　`session.closed.v1` 的租户解析**没有租户约束** ⇒ 跨租户污染

`admin/session_closed_outbox.go` 解析会话归属租户时：

```sql
SELECT tenant_id FROM public.sessions WHERE session_id = $1 LIMIT 1
```

而 `public.sessions` 是**按月分区**表，唯一键是 **`UNIQUE (session_id, partition_date)`**（`sql/migrations/startup/430_sessions_v2_schema.sql:74`）⇒ **`session_id` 不是全局唯一**：跨租户可同名、同一租户跨月可同名。`LIMIT 1` 且无 `ORDER BY` ⇒ 多行时返回**任意一行** ⇒ 事件挂到**别的租户**名下 ⇒ `event_id`（由 tenant+session 派生）随之错 ⇒ ASM 投影跟着错。

**对照**：仓内**其余每一处**按 `session_id` 查 `public.sessions` 的地方**都带租户约束**（`turn_logs_aggregator.go:159`、`session_aggregator.go:366`、`session_trash.go:83`、`titlestore/store.go:270`、`userscriptcapture/store.go:178` …）⇒ 本处是**孤例**。

**修法**：`resolveSessionTenant` 改为枚举 `DISTINCT tenant_id` —— 唯一才采用；0 个候选（会话未落库）⇒ fail-open 放弃；**>1 个（多租户同名）⇒ 放弃发布**（宁可少一条事件，也不可把 A 租户的终态写到 B 租户）。纯函数 `pickSessionTenant` 单独可单测。

### P1-3　sessionpush 对账口径：禁用期与空载荷**混档**，文档承诺「直接可读」兑现不了；且该门的断言**不自包含**

`domains/analysis/sessionpush/sessionpush.go` 的注释承诺：

> `dispatched`：Deliver 被调用（含禁用态暗跳，便于算覆盖率分母差） ／ `skipped`：BuildPayload 判定不推（如 Result 空） ／ 差值 = 推送器禁用期 + failed —— **两者都应能从这组计数直接读出**。

而实现是：禁用态记 `skipped`、启用态才记 `dispatched` ⇒ ① `dispatched` ≠「Deliver 调用次数」；② `skipped` 同时装「禁用」与「空载荷」两种原因 ⇒ **禁用期无法直接读出**，只能靠 `dispatched − success − failed` 反推。

**附带**（同一条门自身的问题）：断言用的是**进程级全局计数器**的**绝对值**，而同包 `sessionpush_test.go` 也会调 `Deliver`（同样的 `provisional/final` 标签）⇒ 断言随用例顺序漂移、**不是自包含的门**。

**修法**：① 禁用独立成 `disabled` 档、`dispatched` 覆盖**每次**调用 ⇒ 三档（`disabled`/`failed`/`skipped`）都**直接可读**；② 断言全部改成**增量口径**（before/after 差值）⇒ 与同包其它用例解耦。

### P2-1　基线写回把「本次没量到的页」当成「已删除」⇒ 悄悄摘掉那些页的约束

`design-metric-skeleton-runtime-check.mjs` 与 `design-nested-card-runtime-check.mjs` 的 `--update-baseline` 写回，都只从**本次量到的页**构造新基线（`nextCounts` 只遍历 `report.pages` / `measuredCounts`）⇒ **旧基线里本次没量到的页会被从基线中抹掉**。

基线是**约束集合**（每一条 = 一个页的棘轮上限）⇒ 删条目 = 悄悄摘掉那几页的约束 ⇒ **门在那几页上从此失效**，而且**不留痕**（`updated` 只记当天，history 里看不出条目被删）。

**修法**：写回前**先保留旧基线的全部条目**，再让本次量到的页按 `min(旧值,实测值)` 覆盖上去；被保留的页在 history note 里**显式列出**。

### P2-2　基线写回的审计日期用 **UTC** ⇒ 在 UTC+8 的 00:00–08:00 之间会写成**前一天**

两把尺都用 `new Date().toISOString().slice(0, 10)` 取「今天」。`toISOString()` 是 **UTC** ⇒ 本地凌晨写回时，基线 `updated` 与 history 的日期会**比当天早一天** ⇒ 变更史出现错日期，且与「今天」对不上。

**修法**：改用**本地时区**日期（`getFullYear/getMonth/getDate` 拼装），并抽成共用函数。

### P2-3　基线写回口径**此前没有任何门覆盖** ⇒ 同一族缺陷连吃两次

`web/scripts/` 下 12 个含 `--update-baseline` 的脚本，**没有一处**被测试覆盖；两把尺的写回逻辑**各写一份** ⇒ 改一处忘一处 = 门与门不同源。这正是 P2-1/P2-2 能活下来的原因。

**修法**：写回口径抽成**共用纯函数** `web/scripts/lib/baseline-ratchet.mjs`（`mergeRatchetBaseline` / `localDate`），两把尺改为调用它；新增 **`web/src/baseline-ratchet.test.ts`**（vitest，7 例）把三条口径钉死：棘轮只许降、新页按实测登记、**未量到的页保留**。

### P2-4　双写桥的 `OnEventSent` 回调在**投递事务内同步执行**，且用 `context.Background()`

`internal/outbox/dispatcher.go` 在 `dispatchOne` 里、`tx.Commit()` **之前**调用 `d.onEventSent(env)`；装配层（`cmd/gateway/main.go`）的回调会**同步**做一次 `taskbus.SQLStore.Enqueue`（自带 3s 超时、`context.Background()`）。

- **幂等性成立**：`task_events` 有 `UNIQUE (task_type, idempotency_key)` + `ON CONFLICT DO NOTHING` ⇒ 重复入队被去重（已核 `internal/taskbus/store_sql.go:54` 与 `933_task_events.sql:36`）⇒ 即使 `tx.Commit()` 失败导致事件重投，也**不会**产生重复任务。
- **但**：注释承诺「桥失败只 log，绝不回压主投递」——**「失败不回压」成立，「耗时不回压」不成立**：回调是**同步**的，一次慢 Enqueue（最多 3s）会**卡住串行派发循环**；且它用的是 `context.Background()`，**不吃派发器的取消信号**。
- **本轮不修**：该桥**默认关**（`TASKBUS_ASM_BRIDGE=1` 才启用），且改法涉及派发循环的并发模型（异步化 or 限流）⇒ 属独立设计轮。**已登记**。

### P2-5　`cookieDomain()` 从**请求 Host 头**推导 Domain，且作用域被放大到 `*.itestu.cn`

`admin/auth_cookie_helpers.go` 新增：`Host` 以 `.itestu.cn` 结尾 ⇒ `Set-Cookie Domain=.itestu.cn`（可用 `LLM_GATEWAY_COOKIE_DOMAIN` 覆盖）。两点风险：
① **Host 头是请求方给的**——用请求头推导 cookie 作用域，等于把作用域决定权交给请求方（浏览器只校验 Domain 是请求 host 的后缀 ⇒ 攻击者若能让 victim 访问 `evil.itestu.cn` 指向本机，响应里的 `Domain=.itestu.cn` **会被接受**）；
② 作用域从 host-only 放大到**整个 `*.itestu.cn`** ⇒ **任何同级子域被攻破即等于拿到管理台会话**。

**本轮不修**（改动会牵动已上线的 freellm SSO 联动），**已登记为需独立评估的安全项**。

### P2-6　capture 的 nonce 防重放缓存每次请求**全扫一遍** map（在全局锁内）

`internal/userscriptcapture/hmac.go` 的 `nonceCache.claim`：每次请求在 `sync.Mutex` 内**遍历整个 map** 清过期。窗口内请求越多，map 越大 ⇒ 每次请求的 O(n) 扫描都发生在**同一把全局锁**下 ⇒ 高吞吐摄取端点上的锁竞争与 CPU 消耗。代码注释自陈「规模小（窗内请求数），全扫可接受」，且 ADR 已把「跨副本 nonce 表」记为 M2 债 ⇒ **本轮登记**，不修（改法是分片/分桶或改用有界 LRU 库）。

### P2-7　`tests/deploy_local_contract_test.sh` 在本机红 —— **既有环境性红，非本轮回归**

`FAIL build lock was not released after the early collision`（`tests/deploy_local_contract_test.sh:203`）。AGENTS.md 已把 `deploy_local_contract_test` 列入**已知的既有红**（本机回收器退化所致）。本轮改动**不涉及** `scripts/deploy-lib` / 部署脚本 / 版本工具链 ⇒ 与本轮无因果关系。
