# 提示词优化 —— 端到端效果实验报告

> **这是本仓第一份真实的效果实验报告**（此前只有结构质量分，没有效果结论）。
> 全部数字来自真实执行：真实 Memora 实例 + 本地部署的内部小模型（ollama / qwen2.5:7b）+ 120 次模型调用。
> 原始数据：`docs/audit/prompt-optimizer-experiment-run2/experiment-report.json`（含每一条的模型原始输出）。
>
> 实验日期：2026-11-12　|　执行模型：`qwen2.5:7b`（7.6B, Q4_K_M, 本地 ollama）

## 一、实验设置

| 项 | 值 |
|---|---|
| 执行模型 | `qwen2.5:7b`（OpenAI 兼容端点 `http://127.0.0.1:11434/v1`）|
| 执行温度 | `0` |
| 重复次数 | 5（每个「任务 × 臂」组合）|
| 任务数 | 6（全部带客观判据）|
| 实验臂 | 4 |
| 总模型调用 | 120 次执行 + 30 次改写 |
| 总耗时 | 23 分 17 秒 |
| 判据 | 规则判定（JSON 解析 / 正则 / 计数），**不依赖模型打分** |
| 记忆后端 | 真实 Memora（service JWT + project scope）|

### 1.1 四个臂（每个臂只改一个变量）

| 臂 | 提示词来源 | harness 注入 | 记忆检索 |
|---|---|---|---|
| `baseline` | 原始提示词 | 无 | 无 |
| `rule` | 规则结构化（structural + fewshot）| 无 | 有 |
| `rule_harness` | 规则结构化（structural + fewshot）| 有（安全 + 错误处理）| 有 |
| `llm_harness` | **LLM 驱动改写**（内部小模型 + memora 历史）| 有（安全 + 错误处理）| 有 |

### 1.2 口径声明（写进报告，不可事后改口）

1. **判据只检查原始提示词里已经隐含的要求**（输出格式 / 数量 / 事实 / 纯净度），
   不发明新需求 —— 否则测到的会是"优化器与判据一起改需求"。
2. **判据是规则判定**，可复算、无歧义；不用 LLM-as-judge（那是自证）。
3. **执行错误**（模型不可达等）单独计数，不进正确率分母，也不当作"做错"。
4. 提示词是**唯一自变量**：执行模型、温度、任务、判据在所有臂之间完全一致。

## 二、★ 先说量具层：温度 0 **不等于**确定性

这是本轮最重要的发现，**先于任何效果结论**。

同一「任务 × 臂」跑 5 次，统计**不同输出**的个数：

| 任务 | baseline | rule | rule_harness | llm_harness |
|---|---|---|---|---|
| json_array_3 | 5/5 | 5/5 | 5/5 | 5/5 |
| three_bullets | 5/5 | 5/5 | 5/5 | 5/5 |
| notice_facts | 5/5 | 5/5 | 5/5 | 5/5 |
| python_code_only | 5/5 | 5/5 | 5/5 | 5/5 |
| date_iso | 5/5 | 5/5 | 5/5 | 5/5 |
| no_fabrication | 5/5 | 5/5 | 5/5 | 5/5 |

**24 个 (任务, 臂) 组合，24 个都是 5/5 —— 没有任何一次输出与其它次相同。**

⇒ 执行侧（ollama / qwen2.5:7b）在 `temperature=0` 下**仍然是非确定性的**。

后果是实打实的：第一轮探索跑（n=1）的 baseline 正确率是 **33.3%**，
第二轮（n=5，同一模型同一温度同一判据）的 baseline 是 **53.3%**。
**同一个基线差了 20 个百分点** —— 如果只看 n=1 的结果，
完全可以把"噪声"当成"优化带来的提升"或"优化带来的退化"。

> **纪律**：任何提示词效果对比，**n=1 的结果不可用**。
> 必须多次重复，并同时报告"同组合不同输出数"这个噪声读数。
> 本仓的实验运行器（`internal/prompt-optimizer/experiment`）已把该读数做进报告。

## 三、各臂汇总（n=5 / 任务 / 臂 ⇒ 每臂 30 次执行）

| 臂 | 执行数 | 通过 | 执行错误 | 正确率 | 相对 baseline | 平均延迟 | 提示词长度 | 输出长度 |
|---|---|---|---|---|---|---|---|---|
| `baseline` | 30 | 16 | 0 | **53.3%** | — | 8583ms | 32 字符 | 316 字符 |
| `rule` | 30 | 20 | 0 | **66.7%** | **+13.4pt（+25% 相对）** | 8554ms | 360 字符 | 374 字符 |
| `rule_harness` | 30 | 19 | 0 | **63.3%** | +10.0pt | 11774ms | 900 字符 | 374 字符 |
| `llm_harness` | 30 | 11 | 0 | **36.7%** | **−16.6pt** | 11876ms | 639 字符 | 396 字符 |

> 「相对 baseline」按 `rule`（修正判据后）计：66.7% vs 53.3%。
> 用**运行当时的判据**（修正前）算是 66.7% vs 50.0%，结论方向一致。

### 三个结论

1. **规则结构化优化有效**：+13.4 个百分点（相对 +25%）。这是本轮唯一被数据支持的收益。
2. **harness 注入没有带来额外收益**：`rule_harness` 比 `rule` 低 3.4 个百分点，
   同时延迟 +38%（8.6s → 11.8s）、提示词长度 ×2.5（360 → 900 字符）。
   ⇒ 在当前形态下，harness 注入是**纯成本**。
3. **LLM 驱动改写显著更差**：36.7%，比 baseline 还低 16.6 个百分点。
   —— 这是本次实验最反直觉、也最有价值的发现，下一节给机制。

## 四、逐任务 × 逐臂（通过数 / 5）

| 任务 | baseline | rule | rule_harness | llm_harness |
|---|---|---|---|---|
| json_array_3（严格 JSON 数组）| 0/5 | **4/5** | **4/5** | 1/5 |
| three_bullets（恰好 3 条）| **5/5** | 1/5 | 0/5 | 3/5 |
| notice_facts（保留 3 个事实）| 2/5 | **5/5** | **5/5** | 4/5 |
| python_code_only（代码且无前言）| 3/5 | **5/5** | **5/5** | 2/5 |
| date_iso（YYYY-MM-DD + 正确日期）| 1/5 | 0/5 | 0/5 | 0/5 |
| no_fabrication（保留事实且不编造）| **5/5** | **5/5** | **5/5** | 1/5 |

### 4.1 规则优化为什么会**同时**赢和输

- **赢**：`json_array_3` 0→4、`notice_facts` 2→5、`python_code_only` 3→5。
  原始提示词只说"转成 JSON 数组"/"写邮件"，规则优化补上了
  "输出必须完整覆盖""禁止编造"等约束，模型开始听话。
- **输**：`three_bullets` 5→1。**优化把"3 条"冲淡了**：
  structural 策略给提示词套了固定模板

  ```
  # 输出格式
  请按以下格式输出:
  [主要内容]
  [补充说明]
  ```

  模型于是老老实实按模板填两段，"主要内容"3 条 + "补充说明"5 条 = **8 个要点行**，
  反而比原始提示词的 5/5 更差。
  ⇒ **模板化优化会稀释任务里的数量约束** —— 这是一个具体的、可修的缺陷。

### 4.2 LLM 改写为什么更差：三个可复现的机制

**机制 A（最致命）：改写把原文抽象成占位符，原文事实整段丢失。**

`no_fabrication` 任务 4/5 失败，失败原因全部是「没有保留原文事实」。
看改写后的提示词：

| 原始提示词 | LLM 改写后 |
|---|---|
| 总结这段话的核心观点：'本次发布只修复了登录页的一个样式错位问题。' | 请总结**这段话**的核心观点，并以一句话形式输出。 |
| 同上 | 总结**给定文本**的核心观点，并以一句话的形式呈现。 |
| 同上 | 请总结**输入文本**的核心观点，并以一句话的形式呈现。输出应为一个句子… |
| 同上 | 请总结 **given text** 的核心观点…（保留了原文块）|

⇒ 小模型在改写时，把"要处理的具体数据"也当成了"要改写的措辞"给抽象掉了。
唯一通过的那次，是因为模型恰好把原文当成了独立输入块保留下来 ——
**这是不稳定行为，不是正确行为**。

**机制 B：改写里带示例，反而诱导执行模型输出"示例 + 解释"。**

`json_array_3` 的改写提示词里给出了完整 JSON 示例：

```
要求输出完整的 JSON 数组…格式如下：
```json
[ {"name": "苹果", "price": 3.5}, … ]
```
```

执行结果仍然是：

```
根据您的要求，以下是转换为 JSON 格式的商品信息数组：
```json
[ … ]
```
此 JSON 数组包含了每种商品的名称和价格，严格按照要求生成。如果您有其他问题…
```

⇒ **提示词里给示例，不等于模型会照抄示例**；模型照样加前言。

**机制 C：改写压缩掉了任务的格式硬约束。**

`date_iso` 四个臂全部接近 0（baseline 1/5，其余 0/5）。
原始提示词明确写了"用 YYYY-MM-DD 格式回答"，改写后格式要求被稀释。
而 baseline 偶尔能做对 —— 说明这个任务的瓶颈其实是**模型的日期算术**
（2026-03-05 + 100 天，模型算出 2026-05-12 / 2026-06-14 / 2026-06-34 等），
不是提示词问题。⇒ **`date_iso` 任务区分不出提示词优化的好坏**，
它测的是小模型的日期能力。它在报告里的价值是**阴性对照**：
提醒"并非所有任务都能靠提示词优化救回来"。

## 五、结论（能被数据支持的范围内）

### 5.1 可以说的

1. **在真实执行模型 + 真实记忆后端上，规则结构化优化把任务正确率从 53.3% 提到 66.7%**（+13.4pt，相对 +25%）。
2. **harness 注入当前是净成本**：正确率不升（63.3% vs 66.7%），延迟 +38%，提示词长度 ×2.5。
3. **用小模型做提示词改写，当前是负收益**（36.7%，低于 baseline 16.6pt），
   主要机制是「改写丢原文事实」。
4. **执行侧在温度 0 下非确定**，n=1 的对比无效；必须重复并报告噪声读数。

### 5.2 不能说的（明确划界）

1. **不能说"提示词优化整体提升 X%"** —— 本实验只测了 6 个任务 / 1 个执行模型 / 1 种任务类型。
   66.7% vs 53.3% 是**这 6 个任务上**的结果。
2. **不能把"结构质量分"当效果** —— `prompt_quality` 与本报告的正确率是两个口径。
   事实上本轮出现了反例：`llm_harness` 的提示词结构质量更高（639 字符、含完整示例），
   正确率却最低。**结构更详细 ≠ 效果更好。**
3. **不能说生产流量上的收益** —— 本实验是离线任务集，不是真实流量。
4. **不能外推到 7B 以上** —— 更大的模型改写质量可能不同；
   本实验恰恰说明"小模型改写"这条路需要**先解决占位符泄漏**才能用。

### 5.3 下一步（按优先级）

| 优先级 | 事项 | 依据 |
|---|---|---|
| P0 | 修 `structural` 策略的固定输出模板（`[主要内容]/[补充说明]`），或让它**识别并保留**原任务里的数量/格式约束 | §4.1：数量约束被模板冲淡，`three_bullets` 5→1 |
| P0 | 给 LLM 改写加**占位符泄漏检测**：改写结果里若出现原文中没有的抽象词（"这段话"/"输入文本"/"给定文本"）而丢了具体内容 ⇒ 判改写失败并回退 | §4.2 机制 A：`no_fabrication` 1/5 |
| P1 | harness 注入改为**按需注入**（只在任务确实需要时注入），并复核 900 字符注入的必要性 | §3 结论 2：纯成本 |
| P1 | 任务集扩容：当前 6 个任务里 `date_iso` 无区分度、`three_bullets` 与 `json_array_3` 结论相反，需要更多样本才能谈"总体提升" | §5.2 限制 1 |
| P2 | 换更大的内部模型重跑 `llm_harness` 臂，验证"小模型改写是负收益"是否只是模型太小 | §4.2 |

## 六、判据口径的修正（一次经手的改动，披露在案）

跑完实验后审判据时发现**一处内部不自洽**：

`notice_facts` 任务的判据里，"周六"接受"星期六"、"1 小时"接受"一小时"，
但时间只接受"凌晨 2 点/凌晨2点/凌晨两点"三种写法 —— 模型写
"本周六凌晨2:00至3:00"（事实完整）被判「缺少原始提示词中的要素」。
**把书写差异当成了事实缺失。**

修正：时间组补上 "凌晨 2:00 / 凌晨2:00 / 2:00"。

**处置纪律**：不重跑模型，用新加的 `--rescore` 离线重算（报告 JSON 里存着每条的原始输出），
并**同时披露修正前后的两套数字**：

| 臂 | 修正前（运行当时）| 修正后（重算）|
|---|---|---|
| baseline | 50.0% | 53.3% |
| rule | 66.7% | 66.7% |
| rule_harness | 63.3% | 63.3% |
| llm_harness | 33.3% | 36.7% |

**结论方向未变**（rule > rule_harness > baseline > llm_harness）。
两个报告都在 `docs/audit/prompt-optimizer-experiment-run2/`（`experiment-report.*` 与 `rescored/`）。

> `--rescore` 这个能力本身就是纪律工具：判据一改，立刻能看清"改判据把结论改成什么样"，
> 而不是重跑一遍再挑一个好看的数字。
