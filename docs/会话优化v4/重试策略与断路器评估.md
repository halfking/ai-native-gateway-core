## 1. 现状（已核实，非目标描述）

v4 的重试/切换阶梯**已落地**，分散在三层、共享同一尝试预算，无需新建断路器组件。下面按"归属/默认值/生效条件"三栏列出。

### 1.1 重试预算与退避（共享单源）

### 1.2 dispatch 阶梯（切换节点/模型）

`domains/dispatch/failover.go:49` `Pipeline.move()`：
- 同凭据重试至 `RetryPerCredential`（2）→ 换下一可用凭据（同模型）→ 该模型穷尽 → 换模型（`allow_model_change`，`gate.go:26` 默认关，`AUTO_ROUTE_FALLBACK_ENABLED=true` 强制开）→ 新模型下重新执行 → 组合穷尽或达预算。
- 首字节后默认不跨凭据切换（`forwarder.go:251-256`，ADR-Disp-003）；流中断走 FR-12 恢复阶梯（T13，本次不实施）。

### 1.3 survival 协调器（唯一外层恢复循环）

`domains/streaming/survival_coordinator.go`：retry-now / wait-recovery（等待期发协议适配心跳：OpenAI `: gw-survival-keepalive` 注释 / Anthropic `event: ping`）/ resume-blocked / fail-terminal / fail-closed。survival 是**租户级装配**（SR-07，`survival_wiring.go:28` `SetRequestSurvival`），"100 次不停重试"达成的前提是目标租户启用 survival。

### 1.4 现有"熔断"性质组件（非供应商重试阶梯熔断器）

| 组件 | 位置 | 性质 |
|---|---|---|
| 凭据状态机 + 冷却表 | `domains/credential/writer.go`、`breaker.go` | 凭据级：401 单次即置 `auth_failed`+15min 恢复窗；429 按 `Retry-After`；成功即恢复。**非"连续失败 N 次熔断"模式** |
| URSM 节点降级 | `record_request.lua` | 节点级：`fail_streak≥3` 降级 + 冷却 30s（指数退避封顶 1800s）；冷却期一次成功即刻恢复 |

| sticky 失败断路 | `executors/sticky.go:372-397` | 粘滞绑定失败熔断（2 次/10s 窗口） |

## 2. 评估结论：是否需要新增"供应商重试阶梯熔断器"

**结论：本次（T4 scope）不新增，复用现有机制。** 理由：

1. **重试预算已是单源共享**：`UpstreamAttemptBudget`（100）+ 2h deadline 由 survival 协调器统一钳制，dispatch 阶梯消费同一预算，不存在"无限重试"风险。
2. **节点/凭据级"熔断"已由 URSM + 凭据状态机覆盖**：连败 3 次降级、冷却退避、成功即恢复的闭环已存在；新增一个独立的"供应商重试阶梯熔断器"会与 URSM `record_request.lua` 形成双写冲突（v4 明令禁止，§9 原则）。
3. **T4 是旁路能力（思考帧桥接）**：它不改变重试决策，只把已有的 `liveactions` 事件（`node_switch`/`model_switch`/`retry`/`upstream_request`）回显给客户端。重试/断路器属于 FR-2/T3 范畴，本次不扩大 scope。

## 3. 后续（不在本次 scope）
