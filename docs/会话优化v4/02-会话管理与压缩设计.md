## 1. 会话管理（主题①）

### 1.1 数据模型（CURRENT，public.* schema）

> **老板 08-15 修正**：所有表在 `public.*`（分区表除外）；migration 513（08-14）已 DROP 整库 gateway schema。会话存储按「**项目 + 任务 + 会话 + 轮次 + 附属会话 + 附属信息**」维度分解。

| 表 | 职责 | 分区 |
|---|---|---|
| `public.sessions` | 会话快照（元数据） | 按月分区 `sessions_%s` |
| `public.session_turns` | 轮次元数据（turn_no / request_id / 状态） | **hot + 分区表**（migration 526 已落地 `session_turns_hot`、统一 view 与原子 promote） |
| `public.session_bodies` | 增量 body（delta 存储） | 按月分区（heap，支持冲突更新） |
| `public.session_turn_logs` | 诊断日志 | 按月分区（24h TTL 清理） |

**hot + 分区表模式（CURRENT，对齐 request_logs）**：`session_turns_hot` 为独立 heap 写入口，`session_turns_with_current_month` 统一读取，`promote_session_turns_hot_to_partition()` 原子提升到月分区；双写期与旧模式并存。

**存储维度层级（现状 vs 目标）**：
- 6 维声明：项目(project) + 任务(task) + 会话(session) + 轮次(turn) + 附属会话(子请求/压缩派生 parent_request_id) + 附属信息（tags/注解/provider cache）。
- **现状**（以 `public.session_turns`/`session_turns_hot` 实列为准，2026-08-16 核实）：
  - ✅ **会话 + 轮次**：`session_id` + `turn_no` + `tenant_id` + `request_id` + `partition_date`。
  - ✅ **附属信息**（部分）：`session_bodies.request_attachments`/`response_attachments`（attachments 已存）；`session_turns.model`/`provider`/`credential_id`/`cost_usd`/`tokens`（provider cache + cost 已存）。
  - ✅ **任务**（间接）：`sessions.task_type`（会话级）；但 `session_turns` 无 `task_type` 列，跨轮次查询需 JOIN。
  - ✅ **附属会话**：`parent_request_id` 已由 migration 525 补齐并由 TurnWriter 写入。
  - ✅ **项目/命名空间/任务**：`project_id`、`namespace`、`task_type` 已由 migration 525 补齐并建立 tenant-scoped 索引；Admin turns 查询可直接按维度过滤，无需 JOIN `sessions`。
- **实现依据**：`sql/migrations/startup/525_session_turns_six_dim.sql:23-54`、`526_session_turns_hot.sql:15-19`、`domains/session/v2/turn_writer.go:236-294`、`bg/partition_manager.go:757-835`。后续仅需生产回填与运行期验证。
- **双写策略**：保留旧存储模式（`request_logs` / `request_logs_hot`）与 V2 并存双写，将来逐步移除（见 10 号计划 V1 下线项）。

## 2. 会话压缩（主题②）

### 2.1 压缩读路径（CURRENT）
- **V2 读路径已接通**：`tryLoadV2State → Builder.BuildLatestOutbound`（`domains/session/v2/session_writer_v2.go`）。
- 开关：`sessions_v2_compression_read` 默认 true；失败 slog.Warn + fallback V1。
- OutboundBuilder：`BuildFromDeltas(ctx, tenantID, sessionID, lastN, preserveCompression)` → `([]Message, *BuildMeta)`；`BuildMeta` 含 TotalTurns/TotalMessages/TokenEstimate/HasCompression/LastTurnNo。
- `filterCompressionMarkers` 按 CompactionMarkerPrefix 过滤，保留压缩 marker `smm_v1:` 语义。

### 2.2 压缩器与会话三层数据（CURRENT）

> **老板 08-15 修正：缓存 ≠ Redis/内存缓存，而是会话的三层数据形态**：
> ① **原始多轮会话**（未压缩事实源）→ ② **压缩后的多轮会话**（可为跨轮次合并）→ ③ **安全脱敏后的发送会话**（上游实际收到）。

- `domains/hooks/compression/session_compressor.go`（L196 Prepare / L770）。
- 三层数据衔接：`session_bodies` 增量（①事实源）→ `Builder.BuildLatestOutbound` 重建（②压缩后）→ 设计中的 `SessionSanitizeManager` 脱敏链路（③发送；类型尚未实现）。Redis 仅承载会话级脱敏映射表（TTL 30min），不是缓存层。
- 组件：estimator.go（token 估算）、breaker.go（压缩熔断）、smart_window.go（智能窗口）、recovery_coordinator.go（恢复协调）、diff.go（增量 diff）、rebuilder_openai/anthropic.go（按厂商重建）。
- **AlignmentMap（CURRENT）**：已实现窗口重写时的原始消息→压缩消息位置映射，并持久化到会话状态用于审计和增量处理（`domains/hooks/compression/alignment.go:25`；`session_compressor.go:157-160,815-820`）。独立缺口是 `SessionSanitizeManager` 类型本身尚未实现；不能将其与 AlignmentMap 混写。

### 2.3 修订0811 SC 轨（会话压缩任务，部分待办）
- SC-1..SC-6：压缩链路强化任务（doc 19 六轨表）。M2 已交付 P2-C1（admin bodies 信封适配），压缩链路本体 SC 任务仍待排期。

### 2.4 压缩与脱敏（CURRENT-PARTIAL，08-07 专题）
- 设计中的 `SessionSanitizeManager` 计划使用会话级映射表持久化 Redis（TTL 30min）；Hook 顺序目标为 SanitizerInput(10) → 上游 → SanitizerOutput(50) → OutputCompliance(100)。
- **独立缺口**：`SessionSanitizeManager` 类型尚未实现；存储层脱敏（3-5d）、压缩时映射表快照入 `session_bodies.metadata`（2-3d）、映射表 AES-GCM 加密（1-2d）仍未实施。
