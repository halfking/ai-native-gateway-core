## 2. 当前事实重核（authoritative）

### 2.1 四态定义

| 状态 | 定义 | 是否可发布 |
|---|---|---|
| **IMPLEMENTED** | 代码/schema 已存在，可能仅有单测或静态证据 | 否 |
| **LOCAL_VERIFIED** | 当前基线在本地 build/vet/test/race 或隔离依赖验证通过；所有 SKIP/模拟已明示 | 否 |
| **RELEASE_READY** | G0..G4 全过，真实 Redis/PG/provider/目标环境无关键 SKIP，回滚可执行 | 可进入 G5 |
| **BLOCKED** | 存在产品决策、migration ledger、真实依赖、环境或未解释回归阻塞 | 否 |

状态只能按证据升级；`IMPLEMENTED ≠ LOCAL_VERIFIED ≠ RELEASE_READY`。同一主题有 blocker 时，以最低安全状态为发布裁决。

## 3. 当前阻塞事实

### 3.1 Handoff expiry

`TestConfirmationStoreAcceptsTargetCreatedWithinProposalSecond` 使用固定 `proposalTime=2026-08-17T03:00:00.9Z`，`NewConfirmationProposal` 正确要求 `expiresAt.After(time.Now())`。测试随现实时间推进而失败，说明 fixture 不稳定，不说明生产 expiry 约束错误。

**裁决**：注入可控时钟或使用相对未来时间；禁止删除/放宽 expiry 校验。修复后还需覆盖刚过期、同秒 target、重复确认和重启恢复。

### 3.2 startup migration 528 重复

当前同时存在：

- `528_repair_shared_pg_sticky_and_bodies_2026_07.sql`
- `528_request_logs_bodies_expired_hot_cleanup.sql`

全仓唯一性测试因此失败。编号、down migration、部署 ledger/checksum 必须一并裁决；在此之前禁止新增 startup migration，也禁止宣称全仓绿。

### 3.3 真实依赖边界

- Redis：`miniredis` 与不可达地址 client swap 只能证明客户端错误路径，不能证明真实 Redis restart、script cache、Pub/Sub 和连接池重连。
- PostgreSQL：525/526 已有真实 PG17 隔离 schema 验证；但 handoff/durable fault injection 仍有 PG 场景 SKIP，二者不能混为“真实 PG 全通过”。
- provider：httptest 与 attempt gate 单测不证明真实 TLS/HTTP2、代理、服务端 close 与公网抖动。

以上任一未关闭，整体状态保持 `BLOCKED`，最高只能写 `LOCAL_VERIFIED`。

## 4. M5 并发执行方案

> 总顺序由 10 号冻结为：`M5-0 → M5-2 → M5-3 → M5-4 → M5-1 → M5-5 → M5-6`。

| 工作包 | 可并行子轨 | 主要范围 | 合流条件 |
|---|---|---|---|
| M5-0 | 基线、失败重现、依赖盘点 | git/env/tests | G0 |
| M5-2 | 528 ledger；525/526；527 mirror | migrations/tests/deploy ledger | G1 |
| M5-3 | expiry/幂等；schema/重启；脱敏/兼容/日志 | handoff package + 契约 | G2 |
| M5-4 | authoritative startup；ready/coverage；monitor/rollback | ursm v2/main/metrics | G3 前半 |
| M5-1 | 全仓回归；失败归因；integration 汇总 | repository-wide read/test | G3 后半 |
| M5-5 | Redis；PG；provider；目标环境 smoke | 授权环境 | G4 |
| M5-6 | GO/NO-GO；回滚；观察窗口 | release/runbook | G5 |

### 冲突与协调

- migration 版本裁决必须由单一 owner 修改，避免两个并行任务再次占同一编号。
- Handoff schema/migration 527 与 Handoff runtime 测试可并行取证，但须在 M5-3 前合流验证重启与重复确认。
- URSM authoritative 与 provider fault injection 可分别准备，真实环境执行必须在 M5-5 统一版本上进行。
- 全仓回归 M5-1 必须位于 M5-2/3/4 后；提前跑出的 green 只能作预检。
- 产品阻塞 P0-A/P0-C 不进入本轮关键路径，不得以并发名义先写代码。

## 6. 验证基准

### 每段基础门禁

- `.go` 修改：`go build ./...`
- migration 修改：版本唯一性 + schema lint + 真实 PostgreSQL apply/reapply/down
- 合流：`go vet ./... && go test -race <相关包>`
- M5-1：`go test -count=1 ./...`、全仓 vet/build、相关 race 与 integration tag

### 必须显式记录

1. 命令、commit、开始/结束时间、退出码。
2. Redis/PG/provider 是真实实例、容器、miniredis、sqlmock、httptest 还是不可达地址模拟。
3. 每个 SKIP 的测试名和原因。
4. 失败是否可复现，是否属于当前改动。
5. 发布 smoke 的环境、版本、目标、回滚点；不得记录 secret 原文。
