## 1. 背景与目标

网关代理多上游供应商，上游存在请求失败、空回复、网络中断、无候选节点等不稳定因素。本需求要达成：

1. **无人值守长程任务完成率最大化**：在客户端不主动终止的前提下，自动重试、切换节点、切换模型，直至成功或穷尽所有组合（兜底上限 100 次）。
2. **客户端连接稳定不受上游影响**：上游的断连、切换、重试对客户端透明；网关通过协议适配的心跳维持客户端连接活跃。
3. **全链路可观测**：请求的路由、分配、状态、错误重试痕迹如实落库并可视化。
4. **节点与凭据自愈**：故障节点自动降级、自检、恢复；偶发凭据错误自动恢复。

> 原始需求中「客户端的网络中断不应影响客户端的网络」按语义修正为：**上游网络中断不应影响客户端连接**。

## 2. 术语

| 术语 | 定义 |
|---|---|
| 请求 (Request) | 客户端一次调用，服务端生成唯一 `request_id` |
| 尝试 (Attempt) | 请求在某个「模型 × 供应商节点」组合上的一次执行，有唯一 `attempt_id` |
| 会话 (Session) | 同一逻辑请求（含客户端重发）的多次请求/尝试集合，共享 `gw_session_id` |
| 节点 (Node) | 供应商凭据 × 模型 的路由单元（对应 credential_model_binding） |
| 降级 (Degraded) | 节点被移出调度，不接受新请求，等待自检 |
| 自检 (Probe) | 对节点的主动健康探测（轻量真实调用） |
| 保活 (Keep-alive) | 网关对客户端连接的心跳维持 |
| 连接注册表 | request_id → 缓存的请求信息 + 客户端连接写出流的映射，用于跨组件回写数据/保活帧（R1.6） |
| 组合穷尽 | 所有「同品质候选模型 × 其可用节点」均已尝试且失败 |

## 3. 功能需求

### FR-1 三级请求队列与请求旅程（状态管理/切换/重试调度骨架，v1.2 修订）

**R1.1 总请求队列（请求注册表）**：所有进入网关的请求在此登记，跟踪全生命周期三态：**待执行 pending（含定时重试：条目携带 retry_at，到点由执行器拾取）/ 执行中 in-flight / 已完成 completed（成功或终态失败，保留至被挤出）**；容量默认 **100**（可配置），FIFO 淘汰。条目存请求 ID + 状态 + 关键时间戳，用于与请求实例、客户端连接匹配。
**R1.2 模型请求队列**：模型路由确定后（客户端指定或任务分析）登记（请求 ID + 模型名），同样三态生命周期；容量默认 **30**（可配置），FIFO 淘汰。
**R1.3 供应商节点队列**：每节点一个队列，登记 (请求 ID, 尝试号) 与该节点上每次尝试的成功/失败状态；连续失败达阈值（默认 3）→ 请求改挂其他节点队列、原节点降级；每节点队列配 **Governor 并发与流量限制**（in-flight 硬帽 / RPM / TPM 令牌桶）。
**R1.4 双层结构（定位修正）**：三级队列是**请求状态管理、切换与重试调度的骨架**，分两层实现——
- **调度层**（`domains/dispatch`，真实执行队列）：Tier-1 模型队列 / Tier-2 节点队列为 chan 队列 + worker（dispatcher / forwarder），**执行器只面向队列条目操作**（取请求 → 选路 → 连接节点 → 流转发 → 回写结果），与 HTTP handler 结构解耦（dispatch 不 import executors/provider；`QueuedRequest` 单所有者移交语义）；失败回队即切换/重试的再调度；T1–T6 时间戳即 total / model / credential 三级队列的入队/出队留痕；
- **观测层**（`domains/requestjourney`，投影）：对三级队列做 FIFO 投影（内存/Redis/PG 三源）+ 状态展示，管理端可查；**投影被挤出 ≠ 请求被取消**，调度条目存活至终态。队列登记异步旁路，登记失败不得影响请求执行。
**R1.5 可观测性**：一切状态变迁发事件（`node_switched`、`model_switched`、`retry_scheduled` 等，词表见 `domains/dispatch/observation.go:14-43`）；请求级全流程 action 事件流已有基础设施（`internal/liveactions`：request_id 键控、单调 seq、旁路异步、有界丢弃、Redis LIST + SSE 回放），FR-3 将其桥接到客户端。管理端按 总览/模型/节点 三视图查询队列快照，展示请求当前阶段、所在模型/节点、attempt 历史轨迹（含每次切换与重试原因），错误重试痕迹直观可见。
**R1.6 连接注册表（新增）**：request_id → 缓存的请求信息 + 客户端连接写出流；流式生存期内，执行器/调度器/后台任务可据此直接向客户端回写数据或保活信息（思考帧，见 FR-3）；连接关闭即注销，注册表并发安全、容量有界。

**现状（v1.2）**：调度层已具雏形——`QueuedRequest`（`domains/dispatch/queued_request.go:65-166`）携带 ID/SessionID/Requested·ResolvedModel/每请求切换策略（`AllowModelChange`、`ModelAlternatives`、`RetryPerCredential`、`AllowProviderChange`）/TriedCredentials·TriedModels/AttemptCount/ResultCh/T0–T9（T1/T2 即 total 队列入/出队）；Governor 四模式（concurrency/rpm/tpm/disabled，`queued_request.go:11-16`）；观测层三视图投影 + 管理端 queues 端点已存在。**缺口**：① 总队列（请求注册表）无统一三态生命周期登记——T1 仅是时间戳，无 pending/in-flight/completed 注册表实体与状态字段；② 失败回队的**定时再执行（retry_at）**未落地（dispatch failover 立即改道，退避等待只在 survival 层）；③ **连接注册表不存在**——客户端写出流由 handler goroutine 持有，跨组件按 request_id 找连接需新增注册表；④ journey 投影容量默认 100/100/100（`config.go:5-9`，hotconfig 键 `llmgw_request_history_*` 已有），模型队列需改 30。注意 recorder 三路 store 泵容量（默认 4096，`recorder.go:13`）是另一层，勿混淆。

### FR-2 路由与执行引擎（重试 / 切换 / 预算）

**R2.1 尝试编排**：请求 → 模型解析（指定或任务分析）→ 候选节点集 → 逐组合尝试。
**R2.2 错误二分法（先行条件）**：必须先有错误分类表——
- **指令性/确定性错误**（参数 400、鉴权失败、内容策略拒答、模型不存在）：同配置重试无意义，直接按规则返回客户端（鉴权失败可触发换凭据）；
- **瞬时错误**（网络中断、超时、5xx、429、空回复、连接重置）：进入重试/切换循环；429 优先遵守上游 `Retry-After`。

**R2.3 切换阶梯**：① 同节点重试至连续失败 **3** 次（即 1 次原始 + 2 次重试）→ ② 同模型换下一可用节点 → ③ 该模型所有节点穷尽 → 按任务类型切换到**同品质档位**模型（任务类型→品质→模型映射为运营配置）→ ④ 新模型下重新执行 ①② → 直到组合穷尽或达到全局上限。
**R2.4 重试预算（v1.1 明确归属）**：全局尝试上限默认 **100**（可配置）；回退为指数退避 + 抖动（±20%），初始 2s，**封顶 120s（2 分钟）**，上游 `Retry-After`/`recover_at`/探测时间优先（doc 18 §8.4）。**组合穷尽优先于次数上限终止**。预算归属已核实：外层重试持有者唯一（SR-W0，`internal/retryowner` 在 HTTP 边界冻结），survival 协调器把 `MaxRetries` 注入共享 `UpstreamAttemptBudget`（`survival_coordinator.go:196-198`、`executors/attempt_budget.go:8`），dispatch / executor / survival 三层共用同一预算，**不存在双重计数**；任务级总时限由 survival `Deadline` 承担（默认 24h，`survival_coordinator.go:45-47`）。
**R2.5 客户端主动断开**：立即停止调度、取消进行中的上游尝试（context 传播）、会话标记 `client_aborted`——这是「不停重试」的边界。
**R2.6 首字节语义（ADR-Disp-003 已锁定）**：首字节后不做跨凭据切换（仅同凭据续传 `isResumable`）；首字节前失败可无缝换节点/换模型。透明恢复仅限首个语义内容之前，工具调用后不自动重放（doc 18 §10.1/§10.3）。
**R2.7 成本记录**：每次尝试独立计费，token/成本随尝试记录入库。

**现状**：`domains/dispatch/failover.go:39-125` 已有完整阶梯（同凭据重试 `RetryPerCredential=2`（由 `MaxNodeFailures=3` 推导）→ 换凭据 → 换模型）；`maxAttempts=100` 与 `executors.DefaultUpstreamAttemptLimit=100` 同源；survival 协调器（`domains/streaming/survival_coordinator.go`，doc 18 §5.1）是**唯一外层恢复循环**：retry-now / wait-recovery（等待期发协议适配心跳）/ resume-blocked / fail-terminal / fail-closed，回退 2s→120s 硬钳制、Deadline 默认 24h、MaxRetries 钳制 100；首字节后不切换已实现并锁定（`forwarder.go:251-256`、ADR-Disp-003）；legacy 路径另有 D5 模型回退（仅非流式、至多加一轮，`handler.go:4010-4013`）。survival 下 executor 内部刷新阶梯被抑制，由协调器 `Refresh` 统一重解析候选（`survival_coordinator.go:91-92,302-304`）。**缺口**：① survival 为**租户级装配**（SR-07），「100 次不停重试」达成的前提是目标租户启用 survival——默认启租策略需决策；② `dispatch_v2.allow_model_change` 默认**关闭**（`domains/dispatch/gate.go:56-58`），且缺「任务类型→同品质模型」映射配置；③ 错误分类表未成文；④ 组合穷尽提前终止与聚合错误体未实现（当前以预算耗尽为主）。

### FR-3 客户端连接保活与过程回显

**R3.1 原则**：网关接受请求后即接管客户端连接生命周期；上游切换/重试对客户端表现为一次连续的响应。
**R3.2 流式请求（保活的主战场）**：
- SSE 注释心跳 `: keep-alive`（默认 15s，`LLM_GATEWAY_KEEPALIVE_INTERVAL` 可配；2026-08-04 起默认开启并覆盖全部流式协议，`stream_runtime.go:36`、`docs/STREAM_TIMEOUT_KEEPALIVE.md`）；survival 等待期心跳已按协议分化——OpenAI 族发 SSE 注释 `: gw-survival-keepalive`、Anthropic 族发 `event: ping`（`survival_coordinator.go:150-153`）；
- 调度过程（等待节点、切换节点、已重试 N 次、切换模型）以**思考模式**增量回显，**不污染最终 answer 内容**。现状基线是 SSE 注释形式（`: thinking: <json>`，对 Zod 严格客户端如 opencode 安全，`handler.go:212-231`；节点切换回调 `handler.go:3624-3631`）；`reasoning_content` 增量 / Anthropic `thinking` 块形式为**新增项**，按客户端类型分化时须保持「注释兜底、语义帧仅对确认安全的类型开启」的次序；
- **操作事件目录（v1.2）**：等待、连接上游、重试（第 N 次）、切换节点（A→B，原因）、切换模型（M1→M2，品质档位）、数据解析（IR 转换）、脱敏/内容变换（`disguise`）、安全检查（`safety` / `internal/paramguard`）等全流程事件均纳入思考帧回显；事件源复用 `internal/liveactions` 的 request_id 键控 action 流（旁路异步、有界丢弃、Redis LIST + SSE 回放），经连接注册表（R1.6）桥接到客户端写出流——桥接为新增项，liveactions 现仅面向管理端；
- 按客户端类型自动选择心跳/回显模式（识别信号：`X-Gw-Client-Type` 头 → User-Agent 关键词，`domains/streaming/client_fingerprint.go:23-64`，`internal/clienttype` 为闭集：cursor/claude-code/opencode/zcode/codex/roocode/vscode/copilot/windsurf/zed/jetbrains/unknown；doc 42 锁定「客户端识别仅供建议，绝不替代能力头」），并提供运营开关可关闭过程回显（部分客户端会展示思考内容）。
**R3.3 非流式请求（v1.1 按冻结契约修订）**：非流式 HTTP 响应在协议上**无法心跳**，「用 think 保持住」只对流式语义成立；且「普通非流式保持同步语义」是 doc 18 §2.2 非目标 6 **锁定的先序决策**，不能擅自对无能力握手的客户端自动发 202/心跳。落地策略（基于既有两条 202 通道，而非新造机制）：
- a) **同步保持段**：非流式现状为整包缓冲、状态头仅在终局写出（`executor_chat.go:1167,1278-1307`）；单次上游调用受 `UpstreamTimeout`（默认 150s）约束、跨候选受共享尝试预算约束；服务端 `http.Server` WriteTimeout=0（`main.go:5391-5405`），实际瓶颈是前置 nginx `proxy_read_timeout` 与客户端耐心；
- b) **durable-202 通道（重启安全，契约已冻结）**：客户端携带 `X-Gw-Capabilities: durable-recovery` + `Prefer: respond-async` 即转 202 + 轮询（`domains/streaming/durable_contract.go:141-150`，doc 18 §9.4 冻结信封：Location / Retry-After / X-Gw-Pending）；后台结果仅一次成功结算（durable settlement CAS，`durable/settlement_outbox.go:40-78`）；
- c) **legacy async-pending 降级**：`202 + X-Gw-Pending + Retry-After + poll_url`（`handler.go:4189-4213`）——进程内执行、**重启不保**，仅作兜底，不作为长程任务的依赖通道；
- d) **推广而非破坏契约**：长程任务的无人值守客户端通过适配文档推动携带能力头（或改用流式）；可选「按 client type 自动附加 durable-202 能力协商」作为运营配置（默认关）。
**R3.4 错误返回条件**：非指令性错误时，只有**已穷尽所有匹配模型的可用节点（组合穷尽）或达到 100 次上限**，才向客户端返回最终错误，错误体附带尝试摘要（试过的模型/节点/原因）。

**现状**：pre-stream 保活默认开启（提前提交 `200 text/event-stream` + 注释心跳，`handler.go:186-204,3422-3450`；预热后一切失败必须以 SSE 错误信封返回、绝不 JSON/4xx——`docs/STREAM_TIMEOUT_KEEPALIVE.md` 锁定）；survival 等待期心跳已协议分化（OpenAI 注释 / Anthropic ping）；节点切换 thinking 回调已有；reasoning 跨协议桥已具备（`internal/ir/stream.go`）。`internal/streamretry` 包装器（mux 层 pre-first-byte 重试）判定为**弃用方向**：与 survival 互斥（启动时 survival 胜出并强制关闭之，`main.go:231-235`），且 pre-stream 保活默认开后其重试窗口实际不再存在（200+注释即视为已提交、无 ≥400 状态可录）。**缺口**：过程回显无运营开关；reasoning_content/thinking 语义帧形式的过程回显未实现；非流式 durable-202 的客户端采纳率为零，需推广与（可选的）按 client type 自动协商。另有 `internal/liveactions` 已将 arrive → route_resolved → model_enqueued → … → reply 每步发为 request_id+seq 的 action 事件（V3.3-OBS OBS-B1，旁路异步、有界丢弃），但仅服务管理端实时视图，未桥接到客户端思考帧。

### FR-4 节点健康管理与自检

**R4.1 状态机**：`available → degraded（连续失败≥3）→ probing（自检中）→ available | offline`。
**R4.2 降级**：连续 3 次失败立即降级——停发新请求 + 在途请求按 FR-2 切换。成功一次即清零失败计数。
**R4.3 自检与恢复回退**：降级后延迟启动探测（轻量真实调用，如 1-token 补全）；通过 → 恢复 available；失败 → 保持降级并按阶梯加大探测间隔（封顶如 2h），连续 N 次探测失败 → offline。**自检失败绝不允许直接回 active**（防止抖动节点反复打流量）。
**R4.4 36 小时恢复扫描（新增）**：定时任务（建议 15min 周期）扫描「**最近 36h 内有过成功请求**、当前处于 degraded/offline」的节点，主动触发自检；通过则恢复。36h 窗口与周期均可配置。
**R4.5 全程留痕**：所有状态变迁与探测结果写入 log 与旅程事件。

**现状**：多层健康机制已存在——凭据健康检查器（1h 滑动窗口、80% 失败率、≥5 样本、降级冷却 15min、探测前置防误判，`credentialhealth/checker.go`）、node_probe 错误触发探测（退避阶梯 +5s…+24h 封顶、7 次后 paused；跨实例协调已由 Redis `SELECT … SKIP LOCKED` 承担，`docs/architecture/node-probe-mechanism.md`）、model_probe（3 次共识）、恢复工人（`RecoverExpired` 1min tick、broken_probe_reviver 30min）。**缺口**：**36h 成功回看扫描器不存在**（全库唯一 36h 引用是离线脚本 `scripts/audit-36h.sh`；既有机制均为错误触发或固定周期，无「按历史成功回看」的恢复路径）；「连续 3 次」语义在三层实现中不一致（session 黑名单为 2、credentialhealth 为窗口比率、model_probe 为共识 3），需统一。新增扫描器必须复用 node_probe 的跨实例协调，避免多实例重复探测。

### FR-5 凭据状态管理与自动恢复

**R5.1** 凭据纳入与节点一致的健康状态机：`ready / cooling / rate_limited / unreachable / auth_failed / suspended`。
**R5.2 偶发自动恢复**：任何成功调用即清除 cooling/rate_limited/unreachable（`RestoreOnSuccess`）；冷却到期由后台工人恢复；429 按 `Retry-After`；**鉴权错误连续出现才判定凭据失效**（单次 401 可能是供应商抖动，不立即拉黑）并告警，失效凭据不参与路由。
**R5.3** 凭据状态每次变迁写审计日志。

**现状**：`domains/credential/writer.go` 已实现上述状态机、按错误类型的冷却时长表、模型级隔离（429 只冷却该凭据×该模型绑定，不污染其他模型）、成功即恢复。**缺口**：需按 T1 的 154 错误分类结果审计实际恢复时延是否达标，输出审计报告。

### FR-6 可观测性、持久化与会话聚合

**R6.1 旅程全量落库**：每次尝试（模型、节点、起止、结果、错误分类、HTTP 状态、耗时、重试序号、切换原因）写入 `request_state_transitions`，幂等（tenant+request_id+seq 唯一）。
**R6.2 会话聚合语义**：切换过程产生的多次尝试挂在同一 `request_id`（旅程内），客户端重发产生的多行请求挂在同一 `gw_session_id`（请求级）；**语义约束：一个会话至多一条最终成功记录**，其余行标记为被取代/失败。数据库保存多条请求记录，但仅一条成功。
**R6.3 结构化日志**：所有错误如实记录（slog JSON：等级、错误分类、节点、模型、session、attempt、request_id）。
**R6.4** 会话时间线视图（管理端）聚合展示上述内容，重试痕迹直观。

**现状**：旅程三源落库 + Detail 合并已上线；`request_logs_hot` 已含 `gw_session_id`、`routing_attempts`、`error_kind`、T0–T9；会话时间线端点已存在（`/api/admin/sessions/{id}/timeline`）。进程内单成功已由 retryowner 唯一外层持有者 + durable settlement CAS（`durable/settlement_outbox.go:40-78`）保证。**缺口**：跨 HTTP 请求的「同会话仅一条成功」无库级保证（历史缺陷：客户端 5 次重发曾产生 5 行全 success，migration 054 的背景），需补 request_logs 行级最终成功标记；journey 观测另有 outbox 重放，与本条无关。

## 6. 关键状态机

- **请求**：`received → routing → model_queue → credential_queue → node_selection → upstream → streaming → retrying* → succeeded | failed_exhausted | client_aborted`（与 `requestjourney/contract.go:79-89` 现有阶段词表一致）。注册表三态映射：received/routing/model_queue → pending；upstream/streaming/retrying → in-flight（retrying 携带 retry_at 时回 pending，到点再入 in-flight）；终态 → completed。
- **节点**：`available →(3 连败) degraded →(延迟探测) probing → available | offline(探测连续失败)`，offline 由 36h 扫描器/reviver 唤醒。
- **凭据**：`ready ⇄ cooling/rate_limited/unreachable →(恢复) ready`；`auth_failed/suspended` 需连续确认 + 告警。

## 8. 专业性修正说明（相对原始文本的变更）

1. **三级队列定位（v1.2 修订）**：队列是状态管理/切换/重试调度的骨架（调度层真实队列 + 观测层投影双层，R1.4）；观测投影被挤出 ≠ 取消请求，调度条目存活至终态，completed 条目在注册表保留至 FIFO 淘汰。
2. **非流式保活物理不可行**：think/心跳仅流式语义有效；且「普通非流式保持同步」是先序冻结决策（doc 18 §2.2.6），非流式长程走既有 durable-202 能力握手通道，不自动对无握手客户端发 202（R3.3，v1.1 修订）。
3. **100 次 × 最长 2min ≈ 最坏 3.2 小时**：必须组合穷尽优先终止 + 总时限 + 保活三者配套，否则客户端/代理层先超时。
4. ~~双层 100 次上限需统一~~（v1.1 已核实解决）：三层共享 `UpstreamAttemptBudget`，外层持有者唯一（retryowner），不存在双重计数；任务总时限由 survival Deadline（默认 24h）承担（R2.4）。
5. **重试的计费副作用**：每次尝试独立生成计费，token/成本必须随尝试入库，无人值守长程任务尤其要可审计（R2.7）。
6. **「连续失败 3 次」需全局统一定义**：现三处实现（2 次/窗口比率/共识 3）不一致，统一为「连续 3 次失败、成功清零」（R4.2）。
7. **模型切换「同品质」需运营配置**：任务类型→品质档位→模型回退链，缺此配置切换会乱（R2.3）。
8. **指令性错误直接返回**：不进入 100 次循环，避免无意义重试放大延迟与费用（R2.2）。
9. **网关重启的在途请求语义（v1.1 已明确）**：流式 durable 前台绑定 + 租约续期（SR-12，docs/修订0811/29、31）承担重启恢复；legacy 202 降级为进程内、重启即失；journey 观测有 outbox 重放。长程无人值守任务必须走 durable 通道而非 legacy 降级。
10. **streamretry 包装器弃用**（v1.1 结论）：与 survival 互斥（启动时 survival 胜出并强制关闭之），且 pre-stream 保活默认开后其重试窗口实际不存在；ADR-Disp-003 亦记录 dispatch 不复用 streamretry。T4 不再评估启用。
11. **survival 是租户级开关**：本需求「不停重试至成功」的前提是目标租户启用 survival（SR-07 装配）；默认启租策略是 T3 的必答决策项。
12. **旅程容量已热配置化**：容量部分仅改默认常量（模型队列 30），无需新配置通道；T2 的主体工作是请求注册表三态化（v1.2 新增）；recorder 泵容量（4096）是另一层勿动。
