## 1. 背景与目标

网关代理多上游供应商，上游存在请求失败、空回复、网络中断、无候选节点等不稳定因素。本需求要达成：

1. **无人值守长程任务完成率最大化**：在客户端不主动终止的前提下，自动重试、切换节点、切换模型，直至成功或穷尽所有组合（兜底上限 100 次）。
2. **客户端连接稳定不受上游影响**：上游的断连、切换、重试对客户端透明；网关通过协议适配的心跳维持客户端连接活跃。
3. **全链路可观测**：请求的路由、分配、状态、错误重试痕迹如实落库并可视化。
4. **节点与凭据自愈**：故障节点自动降级、自检、恢复；偶发凭据错误自动恢复。

> 原始需求中「客户端的网络中断不应影响客户端的网络」按语义修正为：**上游网络中断不应影响客户端连接**。

## 2. 术语

| 术语 | 定义 |
|---|---|
| 请求 (Request) | 客户端一次调用，服务端生成唯一 `request_id` |
| 尝试 (Attempt) | 请求在某个「模型 × 供应商节点」组合上的一次执行，有唯一 `attempt_id` |
| 会话 (Session) | 同一逻辑请求（含客户端重发）的多次请求/尝试集合，共享 `gw_session_id` |
| 节点 (Node) | 供应商凭据 × 模型 的路由单元（对应 credential_model_binding） |
| 降级 (Degraded) | 节点被移出调度，不接受新请求，等待自检 |
| 自检 (Probe) | 对节点的主动健康探测（轻量真实调用） |
| 保活 (Keep-alive) | 网关对客户端连接的心跳维持 |
| 连接注册表 | request_id → 缓存的请求信息 + 客户端连接写出流的映射，用于跨组件回写数据/保活帧（R1.6） |
| URSM v2 | Unified Routing State Manager（`domains/ursm/v2`）：Redis 权威的节点路由状态中枢；NodeView 粒度 = (租户, 凭据, raw_model)；Lua 状态机 + 16 分片 LRU 镜像 + 代际 CAS + 发布/订阅失效广播；治理规范见 `docs/会话优化v4/04-节点状态与路由处理设计.md` |
| 组合穷尽 | 所有「同品质候选模型 × 其可用节点」均已尝试且失败 |
| 会话语义制品 (Session Artifact) | 同一会话修订上的原始、脱敏、压缩三类可复用表示；每层由 source revision/hash + dependency hash 决定是否可复用，不能只看“是否存在” |
| 会话轮次制品块 (Turn Artifact Block) | 某一轮 request/response 在某一语义层的不可变块；每层都保存请求侧与返回侧的引用、哈希、状态和变换信息，按块追加/替换，不重复复制整段会话 |

## 3. 功能需求

### FR-1 三级请求队列与请求旅程（状态管理/切换/重试调度骨架，v1.7 审计版）

**R1.1 总请求队列（请求注册表）**：所有进入网关的请求在此登记，跟踪全生命周期三态：**待执行 pending（含定时重试：条目携带 retry_at，到点由执行器拾取）/ 执行中 in-flight / 已完成 completed（成功或终态失败，保留至被挤出）**；容量默认 **1000**（可配置、热更新，hotconfig 键 `llmgw_dispatch_registry_capacity`）——所有请求先完成连接注册与内容缓存（R1.6/R1.7）再入总队列，故总队列可能超过 1000，**不作为拒绝阈值**；观测投影 total 视图仍为 100（见 §5 容量分层）。条目存请求 ID + 状态 + 关键时间戳，用于与请求实例、客户端连接匹配。**v1.15 勘误**：注册表实体与三态（`LifecycleState` pending/in-flight/completed，R1.8 完成的 50 软水位淘汰）、`retry_at`（由 `RetryScheduler` 在 park 时回 pending，到点再入 in-flight）、`registry.MarkRetryScheduled/MarkInFlight` 写路径在当前代码已落地（`domains/dispatch/registry.go:8-90`、`retry_schedule.go`、`pipeline.go:67-238`、`forwarder.go:217-220`、`failover.go:138-145,172`）——R1.1 的状态字段与定时再执行已不缺，剩余是测试与运营路径补完（见 T2/T3 验收）。
**R1.2 模型请求队列**：模型路由确定后（客户端指定或任务分析）登记（请求 ID + 模型名），同样三态生命周期；观测投影容量默认 **30**（`DefaultPerModelCapacity=30`，`domains/requestjourney/config.go:18`，hotconfig 键 `llmgw_request_history_model_capacity` 已存在）——注意与调度层模型队列的**执行容量上限**（R1.3 的 300）是两层不同语义，实现与文档中必须显式区分。**v1.15 勘误**：观测投影模型队列 30 已是现状非目标。
**R1.3 供应商节点队列**：每节点一个队列，登记 (请求 ID, 尝试号) 与该节点上每次尝试的成功/失败状态；连续失败达阈值（默认 3）→ 请求改挂其他节点队列、原节点降级；每节点队列配 **Governor 并发与流量限制**（in-flight 硬帽 / RPM / TPM 令牌桶）与**指纹 slot 配额**（`credentialfpslot`：按凭据指纹 acquire/reclaim/quota，Redis 节点态 TTL 3600s）；两套限额的镜像值进节点状态缓存包的资源仪表（R10.4/FR-10），供选择闭包满载预过滤。**调度层模型队列与节点队列容量上限默认 300**（`llmgw_dispatch_max_queue_depth`，**v1.15 勘误**：当前 `Config.MaxQueueDepth=300` 已为现状默认，见 `domains/dispatch/config.go:32,65,83`，原 1024 已改；hotconfig 键已存在），**达到上限即拒绝入队**——立即返回 `overflow` 可重试错误（dispatch 侧错误分类已有 overflow，`domains/dispatch/journey.go:255-282` `classifyError` `ErrOverflow` → `"overflow"`；requestjourney 契约词表需同步补词）；`MaxQueueWaitMS` 默认 **0**（v1.15 勘误：现状 `Config.MaxQueueWaitMS=0`，`domains/dispatch/config.go:36-39,84`，原 5000ms 已改），并已移除 `queueWaitBudget` 在 `<=0` 时的 30s 硬兜底（见 `Pipeline.queueWaitBudget`，`pipeline.go:794-807`，含 `UT-DQ-02` 历史注释），防止拥堵向内存与上游传导。
**R1.4 双层结构（定位修正）**：三级队列是**请求状态管理、切换与重试调度的骨架**，分两层实现——
- **调度层**（`domains/dispatch`，真实执行队列）：Tier-1 模型队列 / Tier-2 节点队列为 chan 队列 + worker（dispatcher / forwarder），**执行器只面向队列条目操作**（取请求 → 选路 → 连接节点 → 流转发 → 回写结果），与 HTTP handler 结构解耦（dispatch 不 import executors/provider；`QueuedRequest` 单所有者移交语义，`queued_request.go:65-178`）；失败回队即切换/重试的再调度；T1–T6 时间戳即 total / model / credential 三级队列的入队/出队留痕；
- **观测层**（`domains/requestjourney`，投影）：对三级队列做 FIFO 投影（内存/Redis/PG 三源）+ 状态展示，管理端可查；**投影被挤出 ≠ 请求被取消**，调度条目存活至终态。队列登记异步旁路，登记失败不得影响请求执行。
**R1.5 可观测性**：一切状态变迁发事件（`node_switched`、`model_switched`、`retry_scheduled`、`lifecycle_eviction` 等，词表见 `domains/dispatch/observation.go:10-43` 与 `queue_projection.go:25-27`）；请求级全流程 action 事件流已有基础设施（`internal/liveactions`：request_id 键控、单调 seq、旁路异步、有界丢弃、Redis LIST `LLMGW:live:actions` 5000 条上限 + SSE 回放），FR-3 将其桥接到客户端。管理端按 总览/模型/节点 三视图查询队列快照，展示请求当前阶段、所在模型/节点、attempt 历史轨迹（含每次切换与重试原因），错误重试痕迹直观可见。
**R1.6 连接注册表（主要落地，桥接到客户端尚需 T4）**：request_id → 缓存的请求信息 + 客户端连接写出流；流式生存期内，执行器/调度器/后台任务可据此直接向客户端回写数据或保活信息（思考帧，见 FR-3）；连接关闭即注销，注册表并发安全、容量有界。**v1.15 勘误**：`SerializedStreamWriter` 串行写（流内顺序保护）、`http.ResponseController.SetWriteDeadline` 写 deadline 防御均已在 `domains/streaming/handler.go` 落位，T4 剩余主要是 liveactions 桥接到客户端思考帧（新增项）。
**R1.7 请求内容物化（部分落地，缺 codec 编码与 Redis-L2）**：请求进入总队列前，将请求内容写入版本化 request snapshot codec/store：压缩后缓存 Redis（键风格 `gw:reqcache:{request_id}`，TTL 默认 2h，热配置），并异步落库保存可校验的快照元数据/正文引用。`domains/dispatch/snapshot.go` 已承担 Tier-3 显示/统计；durable lane 在 `durable/store.go:5-203` 实现 PG snapshot/lease/fencing（PG `request_snapshot_ciphertext`/`lease_owner`/`lease_until`/`fencing_token`，migration `516_durable_llm_tasks.sql`）；pending 不缓存请求正文（仅 `RequestHash` SHA256，`pending/pending.go:34-79`）。**不得假定 `session_bodies` 已提供应用层 zstd 编解码**（`bodies_writer.go:259-332` 写 JSONB，`430_sessions_v2_schema.sql:199-208,237-240` JSONB 列、zstd 仅在 COMMENT 提及）；需显式新增 codec（版本、大小、hash、完整性、租户绑定/AAD）。执行器可从 Redis 或 DB 装载快照，但只有带 durable lease/fencing 的 durable task 才能在网关重启后继续执行；普通 dispatch 的 Redis 镜像只能支持观测/元数据重建，不能宣称自动恢复执行。缓存 TTL、压缩开关、容量、最大正文大小全部热配置。
**R1.8 完成态淘汰与未完成保留（实现已对位）**：每个实际调度队列的容量上限为 300；`completed` 条目达到 **50 个软水位**即开始按完成时间从旧到新淘汰，只淘汰 completed，不淘汰 pending/in-flight/retrying；未完成条目一直保留到其终态或客户端取消（`registry.go:55-90`、`queue_projection.go:25-27 QueueLifecycleEviction`、`pipeline.go:198-241`、`snapshot.go:23-47`）。若未完成条目已达到 300，任何新请求不得入模型/节点调度队列，立即返回 `overflow`（`errors.go:73-82` `registry_unfinished_full` + `model_queue_full`/`cred_queue_full`）；淘汰、拒绝和状态迁移必须写 journey/action 事件。50、300、淘汰批量和扫描周期全部热配置（`CompletedWatermark` 默认 50，`RegistryCapacity` 默认 1000，`MaxQueueDepth` 默认 300，`domains/dispatch/config.go`）。

**现状（v1.15 复核）**：调度层骨架已对位——`QueuedRequest`（`domains/dispatch/queued_request.go:65-178`）携带 ID/SessionID/Requested·ResolvedModel/每请求切换策略（`AllowModelChange`、`ModelAlternatives`、`RetryPerCredential`、`AllowProviderChange`）/TriedCredentials·TriedModels/AttemptCount/ResultCh/T0–T9；Governor 四模式（concurrency/rpm/tpm/disabled，`queued_request.go:11-16`）；观测层三视图投影 + 管理端 queues 端点已存在；三态注册表（`registry.go`）、`retry_at` 定时重试（`retry_schedule.go`）、队列深度镜像（`queue_mirror.go`，独立版本化键，供跨实例观测与元数据重建）、connection registry（client connection via `SerializedStreamWriter`）均已落地。**剩余缺口**：① 默认值已是 300/0/1000/50/30（v1.15 勘误纠正，无需变更）；② **复活 reducer / 复活 pending 用作执行恢复** / 复活第二 session 表 / 复活第二 node-state authority 等**禁止事项仍需在 P0 门禁中守住**——目前 `ursm/v2/reducer` 已删除（commit `f7eb0eb1b`，Lua 为唯一权威，`store/record_request.go:43-49`）；③ 连接注册表→客户端思考帧桥接（liveactions → SSE/Anthropic thinking/OpenAI reasoning_content）是 T4 主要新增项，OpenAI `: thinking:` 注释形式已可用（`handler.go:211-230`），reasoning 跨协议桥已具备（`internal/ir/stream.go`）；④ request snapshot codec store（Redis L2 + DB）、sanitize Redis key 加 tenant scope、`session_summaries` 主键/tenant scope、P0 URSM Ready/Redis 失败契约（默认档已切回保护性拒绝，可选 `MirrorGraceEnabled` 镜像宽限档热配置，§14.3/§13.1 P0-1 冻结）仍是 P1 阻断项。注意 recorder 三路 store 泵容量（默认 4096，`recorder.go:13`）是另一层，勿混淆。

### FR-2 路由与执行引擎（重试 / 切换 / 预算）

**R2.1 尝试编排**：请求 → 模型解析（指定或任务分析）→ 候选节点集 → 逐组合尝试。
**R2.2 错误二分法（先行条件）**：必须先有错误分类表——
- **指令性/确定性错误**（参数 400、鉴权失败、内容策略拒答、模型不存在）：同配置重试无意义，直接按规则返回客户端（鉴权失败可触发换凭据）；
- **瞬时错误**（网络中断、超时、5xx、429、空回复、连接重置）：进入重试/切换循环；429 优先遵守上游 `Retry-After`。

**R2.3 切换阶梯**：① 同节点重试至连续失败 **3** 次（即 1 次原始 + 2 次重试）→ ② 同模型换下一可用节点 → ③ 该模型所有节点穷尽 → 按任务类型切换到**同品质档位**模型（任务类型→品质→模型映射为运营配置）→ ④ 新模型下重新执行 ①② → 直到组合穷尽或达到全局上限。
**R2.4 重试预算（归属已明确，默认值已落地）**：全局尝试上限默认 **100**（可配置）；回退为指数退避 + 抖动（±20%），初始 2s，**封顶 120s（2 分钟）**，上游 `Retry-After`/`recover_at`/探测时间优先（doc 18 §8.4）。**组合穷尽优先于次数上限终止**。外层重试持有者唯一（SR-W0，`internal/retryowner` 在 HTTP 边界冻结），survival 协调器把 `MaxRetries` 注入共享 `UpstreamAttemptBudget`（`survival_coordinator.go:210-211` 注入；`executors/DefaultUpstreamAttemptLimit=100`，`domains/streaming/executors/attempt_budget.go:8`），三层共用同一预算。**v1.15 勘误**：① survival `Deadline` 默认 **2h** 已生效（`survival_coordinator.go:55-57` `withDefaults`，`// v4 T3: 24h → 2h, aligned with the 2h request-cache TTL`），环境变量 `LLM_GATEWAY_REQUEST_SURVIVAL_INTERACTIVE_DEADLINE_SECONDS` 通过 config wiring 仍覆盖；② survival 协调器已具备 ±20% 抖动（`survival_coordinator.go:444,530-551`，函数 `applyBackoffJitter`，注释 `mirroring the legacy handler retry path (handler.go calculateRetryDelay)`）——T3 该项已不缺；③ `RetryMax` 钳制在 `withDefaults`（行 61-63 `120s`）。**`RetryPerCredential` 由 `MaxNodeFailures-1` 推导**（`config.go:70`、`errors.go:14` `MaxNodeFailures=3`、`errors.go:18` `maxAttempts=100`），不是 `errors.go:9` / `errors.go:13`（原 cite 行号错位）。
**R2.5 客户端主动断开**：立即停止调度、取消进行中的上游尝试（context 传播）、会话标记 `client_aborted`——这是「不停重试」的边界。
**R2.6 首字节语义（ADR-Disp-003 当前回退规则，待 ADR-Disp-007 条件化修订）**：首字节前失败可无缝换节点/换模型；首字节后默认不跨凭据切换，仅同凭据续传 `isResumable`。只有 R12.6 列出的撤销/前缀对齐/运营授权条件经 ADR-Disp-007 评审通过后，才允许受控跨节点/模型恢复；工具调用后的重放仍默认禁止（doc 18 §10.1/§10.3）。
**R2.7 成本记录**：每次尝试独立计费，token/成本随尝试记录入库。

### FR-3 客户端连接保活与过程回显

**R3.1 原则**：网关接受请求后即接管客户端连接生命周期；上游切换/重试对客户端表现为一次连续的响应。
**R3.2 流式请求（保活的主战场）**：
- SSE 注释心跳 `: keep-alive`（默认 15s，`LLM_GATEWAY_KEEPALIVE_INTERVAL` 可配；2026-08-04 起默认开启并覆盖全部流式协议，`stream_runtime.go:36`、`docs/archive/process/process/2026-07/STREAM_TIMEOUT_KEEPALIVE.md`）；survival 等待期心跳已按协议分化——OpenAI 族发 SSE 注释 `: gw-survival-keepalive`、Anthropic 族发 `event: ping`（`survival_coordinator.go:150-153`）；
- 调度过程（等待节点、切换节点、已重试 N 次、切换模型）以**思考模式**增量回显，**不污染最终 answer 内容**。现状基线是 SSE 注释形式（`: thinking: <json>`，对 Zod 严格客户端如 opencode 安全，`handler.go:210-229`；节点切换回调 `handler.go:3618-3625`）；`reasoning_content` 增量 / Anthropic `thinking` 块形式为**新增项**，按客户端类型分化时须保持「注释兜底、语义帧仅对确认安全的类型开启」的次序；
- **操作事件目录（v1.2）**：等待、连接上游、重试（第 N 次）、切换节点（A→B，原因）、切换模型（M1→M2，品质档位）、数据解析（IR 转换）、脱敏/内容变换（`disguise/`）、安全检查（sessionaudit/敏感检测 + `internal/paramguard`）等全流程事件均纳入思考帧回显；事件源复用 `internal/liveactions` 的 request_id 键控 action 流（旁路异步、有界丢弃、Redis LIST + SSE 回放），经连接注册表（R1.6）桥接到客户端写出流——桥接为新增项，liveactions 现仅面向管理端；
- 按客户端类型自动选择心跳/回显模式（识别信号：`X-Gw-Client-Type` 头 → User-Agent 关键词，`domains/streaming/client_fingerprint.go:23-63`，`internal/clienttype` 为闭集：cursor/claude-code/opencode/zcode/codex/roocode/vscode/copilot/windsurf/zed/jetbrains/unknown；doc 42 锁定「客户端识别仅供建议，绝不替代能力头」），并提供运营开关可关闭过程回显（部分客户端会展示思考内容）。
**R3.3 非流式请求（v1.1 按冻结契约修订）**：非流式 HTTP 响应在协议上**无法心跳**，「用 think 保持住」只对流式语义成立；且「普通非流式保持同步语义」是 doc 18 §2.2 非目标 6 **锁定的先序决策**，不能擅自对无能力握手的客户端自动发 202/心跳。落地策略（基于既有两条 202 通道，而非新造机制）：
- a) **同步保持段**：非流式现状为整包缓冲、状态头仅在终局写出（`executor_chat.go:1167,1278-1307`）；单次上游调用受 `UpstreamTimeout`（默认 150s，`config/config.go:386`；stream_runtime 兜底 120s）约束、跨候选受共享尝试预算约束；服务端 `http.Server` WriteTimeout=0（`cmd/gateway/main.go:5347`），实际瓶颈是前置 nginx `proxy_read_timeout` 与客户端耐心；
- b) **durable-202 通道（重启安全，契约已冻结）**：客户端携带 `X-Gw-Capabilities: durable-recovery` + `Prefer: respond-async` 即转 202 + 轮询（`domains/streaming/durable_contract.go:141-150`，doc 18 §9.4 冻结信封：Location / Retry-After / X-Gw-Pending，渲染于 `durable_wiring.go:298-322`）；后台结果仅一次成功结算（durable settlement CAS，`durable/settlement_outbox.go:40-91`）；
- c) **legacy async-pending 降级**：`202 + X-Gw-Pending + Retry-After`（幂等重复请求快速路径，`handler.go:3336-3355`，响应体不含 poll_url；带 poll_url 的 202 仅存在于审批流 `handler.go:2482-2491` 与 durable 信封）——进程内执行、**重启不保**，仅作兜底，不作为长程任务的依赖通道；
- d) **推广而非破坏契约**：长程任务的无人值守客户端通过适配文档推动携带能力头（或改用流式）；可选「按 client type 自动附加 durable-202 能力协商」作为运营配置（默认关）。
**R3.4 错误返回条件**：非指令性错误时，只有**已穷尽所有匹配模型的可用节点（组合穷尽）或达到 100 次上限**，才向客户端返回最终错误，错误体附带尝试摘要（试过的模型/节点/原因）。

**现状**：pre-stream 保活默认开启（提前提交 `200 text/event-stream` + 注释心跳，`handler.go:184-202,3414-3442`；预热后一切失败必须以 SSE 错误信封返回、绝不 JSON/4xx——`docs/archive/process/process/2026-07/STREAM_TIMEOUT_KEEPALIVE.md` 锁定）；survival 等待期心跳已协议分化（OpenAI 注释 / Anthropic ping）；节点切换 thinking 回调已有；reasoning 跨协议桥已具备（`internal/ir/stream.go`）。`internal/streamretry` 包装器（mux 层 pre-first-byte 重试）判定为**弃用方向**：与 survival 互斥（启动时 survival 胜出并强制关闭之，`cmd/gateway/main.go:231-235`），且 pre-stream 保活默认开后其重试窗口实际不再存在（200+注释即视为已提交、无 ≥400 状态可录）。**缺口**：过程回显无运营开关；reasoning_content/thinking 语义帧形式的过程回显未实现；非流式 durable-202 的客户端采纳率为零，需推广与（可选的）按 client type 自动协商。另有 `internal/liveactions` 已将 arrive → route_resolved → model_enqueued → … → reply 每步发为 request_id+seq 的 action 事件（V3.3-OBS OBS-B1，旁路异步、有界丢弃、Redis LIST 上限 5000 条 + SSE 回放），但仅服务管理端实时视图（`GET /api/admin/live-stream`），未桥接到客户端思考帧。

### FR-9 端到端流程基线（v1.7 审计版）

**流程 1 · 接入与生命周期**：收到请求 → 连接注册表登记客户端信息并保持 TCP（R1.6）→ 请求快照物化（R1.7）并在 request-scope 捕获原始/脱敏表示 → 入总队列（注册表三态 pending）→ 第一次真实上游尝试前由会话预处理 Hook 加载或懒生成三级会话制品（FR-11）→ 心跳/思考帧保活（FR-3）→ 超时/取消/出错/成功收到信息 → 关闭连接（注销注册表、按策略清请求缓存；会话制品按 TTL/修订保留复用）→ 结束（completed）。
**流程 2 · 执行器主循环**：从请求队列取一个请求 → 任务判断（客户端已指定模型则跳过；否则 autoroute 任务分析）→ 路由判断（**调用节点选择闭包 R10.2：位图 O(1) 预过滤——不可用/冷却/已试/满载（并发、FP slot、RPM 任一达限，R10.4 资源仪表）——+ URSM 评分排序**）→ 会话预处理 Hook 按修订/依赖哈希复用或生成 raw→sanitized→compressed 制品（FR-11）→ 加入模型/节点队列（上限 300，满即拒）→ 第一次真实发送时提交该会话修订并 TryAcquire 占用资源仪表 → 成功收到回复 → **按请求 ID 查连接注册表找到 TCP** → 回写消息（Release 释放仪表）→ 终态持久化后将 assistant response 追加到会话源日志并使下游制品进入 stale → 在多个队列中变更请求状态（completed）→ 超时或被挤出 → 清除请求级缓存与队列信息 → 结束。
**流程 3 · 失败与切换**：执行中错误/失败 → 首字节前走标准阶梯（换节点排除已试）；**首字节后的流中断走 FR-12 流恢复阶梯（同节点重发 → 可撤销窗口丢弃 → 前缀对齐续传 → 降级），不直接终止**；成功走正常流程，失败再重试或换节点；**记录操作过的节点 ID 与状态**（**NodeUseRecord 紧凑记录 R10.3**；`TriedCredentials` 供 O(1) 排除）；该模型所有节点失败 → 按同类任务配置换模型（同品质档位）→ 新模型下逐节点再测 → 组合穷尽或达预算/时限 → 终态。
**流程 4 · 节点选取**：先计算 `AffinityKey` 并查同会话 sticky 绑定；绑定节点健康、未满载且可访问时直接复用；否则按负载均衡与成本（URSM 评分：0.4·price + 0.4·latency + 0.2·失败率）查询可用节点列表 → 排除本请求已试（首轮为空）→ 取第一节点处理（**由选择闭包一次完成，R10.2**）→ CAS 更新 sticky 绑定并记录切换原因；全程记录节点 ID + 状态，避免重复使用失败节点。

### FR-10 节点状态缓存包与选择闭包（v1.7 审计版，P0/P1 门禁后接入）

**R10.1 定位（派生读模型，不新建权威）**：`domains/nodestatecache`（建议名）是**进程内派生读缓存**——「所有节点的状态的缓存处理包」。权威仍是 URSM v2 Redis（Lua 状态机，v1.3 结论不变）。本包由三条喂入路径保持一致：① RecordRequest 效应链尾部旁路更新；② 复用 NodeMirror 的 pub/sub 失效广播（`manager.go:779-814` 订阅）置脏重拉；③ 低频对账循环（默认 30s，可配）以 Redis 为准全量校准。**禁止双写**：本包永不写 URSM/DB。

**R10.2 选择闭包（NextNode）**：构造器返回闭包，签名（Go 语义）：

```go
type SelectQuery struct {
    Model            string          // 模型（必填；auto 已解析）
    TaskType         string          // 任务类型（可空；同品质档位换模型用）
    Used             []NodeUseRecord // 本请求已用节点与状态（排除表 + 状态参考）
    AllowModelSwitch bool            // 可切换模型标志
    RetryCount       int             // 重试次数
    Flags            uint32          // 其它标志位：bit0 sticky 优先、bit1 free 容忍、bit2 排除冷却中…
}
type SelectResult struct {
    NodeID, ModelID int32
    SwitchedModel   bool
    Exhausted       bool            // 组合穷尽信号（供 R2.4 提前终止）
    Alternatives    []NodeUseRecord // 后备序列（已按评分排序）
}
type NodeSelector func(ctx context.Context, q SelectQuery) SelectResult
```

行为：位图 O(1) 预过滤（剔除不可用/冷却/已试/**满载**——Full 位图命中即剔除，满载=并发或 FP slot 或 RPM 任一达限）→ 幸存集交 URSM `FilterAndScoreReadyWithSource` 排序 → 取第一（流程 4）；`AllowModelSwitch` 且当前模型幸存为空 → 按任务类型→品质档位映射换模型再选；全空 → `Exhausted=true`。粘滞优先由 Flags 控制。

**R10.3 节点使用记录（紧凑整型）**：每次节点调用记一条（序号、标准模型 id、节点 id、是否重试、状态等），位压缩尽量用短整/整型：

```go
type NodeUseRecord struct { // 16B
    Seq     int32  // 序号（请求内递增，1 起）
    ModelID int32  // 标准模型 id
    NodeID  int32  // 节点 dense id（R10.4 注册表分配）
    Packed  uint32 // bit0-7 状态枚举 | bit8-15 错误分类 | bit16 是否重试 | bit17 切换而来 | bit18 sticky | bit19-31 预留
}
```

随 `QueuedRequest` 携带（append-only，上限=尝试预算 100），并镜像为 journey `attempt_*` 事件落库——**紧凑结构用于热路径，全量诊断走 journey，两者字段映射固定**。`TriedCredentials` map 保留用于 O(1) 排除。

**R10.4 位图与统计槽（全节点快缓存）**：

```go
type NodeStateBitmap struct {   // 按 dense node id 位寻址，分片原子更新
    Avail []uint64               // bit=1 可参与路由
    Probe []uint64               // bit=1 需自检（降级/离线且退避到期/36h 命中）
    Full  []uint64               // bit=1 满载（并发/FP slot/RPM 任一达限，v1.6）
}
type NodeStatsSlot struct {     // 每节点 16B，数组按 dense id 索引
    LastUsedUnixSec int32       // 最后请求时间（秒级截断）
    Succ1h, Fail1h  uint16      // 1h 成功/失败次数（饱和计数）
    FailStreak      uint8       // 连续错误次数（对齐 URSM FailStreakLimit）
    State           uint8       // available/degraded/probing/offline 枚举
    WindowStart     uint32      // 1h 翻转窗口起点（读时比较重置）
}
type NodeResourceSlot struct {  // 每节点 16B（v1.6），原子 CAS 快速更新
    ConcUsed, ConcLimit uint16  // 在途并发（Limit=0 不限；源=credentials.concurrency_mode/limits）
    FPUsed, FPLimit     uint16  // 指纹 slot（源=credentialfpslot 配额）
    RPMUsed, RPMLimit   uint16  // 每分钟请求（分钟级翻转窗口，定时重置）
    WindowID, Flags     uint16  // 重置窗口号；Flags.bit0=满载（联动 Full 位图）
}
```

dense id 由节点注册表分配：`(tenant, credential, raw_model) ↔ int32`，容量有界，复用 NodeMirror 的分片与失效广播。位图读无锁（atomic），写分片隔离。**取舍**：饱和计数与秒级截断换密度与速度，精确遥测不在此层重复（URSM 窗口 ZSET SR1m/5m/30m + journey 全量）。

**R10.5 同包其余 API（单一责任分组）**：构造器一次返回四组闭包/方法，职责隔离、互不调用——
- `Updater(nodeID int32, success bool, errKind uint8, latencyMS int32)`：状态/统计更新（RecordRequest 效应链尾部与探测结果调用）；
- `NeedProbe(now time.Time) []NodeRef`：需自检列表（Probe 位图扫描 + 36h 命中 + 退避到期），供 R4.4 扫描器与 node_probe 消费；
- `Selector`（R10.2）；
- **资源仪表组（v1.6）**：`TryAcquire(nodeID, kind) bool` / `Release(nodeID, kind)`（并发/FP slot/RPM 的**快速值更新**，CAS O(1)，挂接 dispatch Governor 的 acquire/release 与 credentialfpslot 的 acquire/reclaim 事件流）；`ResetWindow(now)`（**定时重置**：每分钟 RPM 翻转 + 1h 统计窗口，包内 ticker 驱动，周期热配置）；`Reconcile()`（默认 30s 漂移校正，以 Governor / fpslot / URSM 为准）。**权威准入仍在 Governor 与 fpslot，本缓存持有的是派生镜像值；上限源=credentials 表与 fpslot 配额，缓存内不另建上限配置。**

**R10.6 隔离与性能**：读路径无锁原子；写路径 16 分片（对齐 NodeMirror）；资源仪表增减为 CAS O(1)（无锁、不经过 Redis）；单次选择目标 P99 < 1ms（位图预过滤后至多一次 Redis/镜像调用）；所有操作 O(1) 或 O(幸存集)；包不 import dispatch/executors（避免环，参照 dispatch 的 `CredentialRef` 解耦先例）。可选接线：以本包实现 `domains/ursm/v2/resource/pools.go` 接口，一接两得——URSM `NodeView` 的 Conc/FP/RPM 仪表（现为死脚手架、恒 0）同时被填满。

### FR-11 第一次 LLM 提交的会话语义三级缓存（v1.8）

**R11.1 三层是语义依赖，不是存储介质层级**：固定依赖图为 `Raw → Sanitized → Compressed`；每一层物理上均可有 L1（进程内）/L2（Redis）/L3（PostgreSQL）副本。层级职责：
- **Raw Artifact**：客户端协议规范化后的原始会话/本轮 delta，位于脱敏之前；包含敏感数据，必须加密保存，严禁明文日志/普通管理 API 返回；
- **Sanitized Artifact**：基于 Raw 的占位符脱敏会话，携带 sanitizer 版本、策略哈希、映射引用/哈希和显式结果状态（`sanitized/no_matches/degraded_passthrough/failed`）；
- **Compressed Artifact**：基于 Sanitized 的可发往 LLM 的压缩/摘要表示；按协议、上下文窗口档位、压缩策略版本、tools hash、模型能力 profile 分 variant，模型切换后只有兼容 variant 才可复用。

**R11.2 统一所有者与 Hook 接入（v1.15 勘误：包已存在）**：唯一会话预处理所有者为 `domains/session/preprocess`（**v1.15 勘误**：该包已在当前代码中存在：含 `hook.go / redis_store.go / store.go / types.go / crypto.go / lru.go / events.go / deps.go / turn_block.go` 及对应单元测试；`hook.go:16-31` 已定义 `SessionPreprocessHook` 接口，签名与下文完全一致；`hook.go:9` 已引入 `golang.org/x/sync/singleflight`；`hook.go:12-15` 注释明确其规范来源为 spec R11.2——即原文档描述的"新增接口/引入 singleflight"已在代码层落地）；复用 sanitizer、`SessionCompressor`、Sessions V2 turn lock/delta/reconstruction、`ResultMemo`、`singleflight`，不把三层制品塞入 `nodestatecache`、`pending`、`sessionv2mirror` 或旧 `CompressionHook`。当前 legacy `domains/hooks` Registry 未接生产主路径，optional V2 pipeline 也没有真实 postflight，因此 v1.8 采用明确的生产 Hook 适配器：

```go
type SessionPreprocessHook interface {
    Prepare(ctx context.Context, in SessionPrepareInput) (*PreparedSessionArtifacts, error)
    CommitFirstForward(ctx context.Context, p *PreparedSessionArtifacts, attemptNo int) error
    AppendTerminal(ctx context.Context, turn TerminalTurn) error
}
```

- `Prepare`：在 tenant/session/model 已解析、当前压缩 seam 前加载/懒生成制品，但不推进持久会话修订；
- `CommitFirstForward`：由 `beginUpstreamAttempt` 在 `AttemptNo == 1` 时 CAS 提交“本请求确实第一次发往 LLM”的修订；重试/换节点复用同一 Prepared bundle，禁止重复脱敏/压缩；
- `AppendTerminal`：终态持久化成功后追加 assistant response，推进会话修订并使依赖旧修订的 Sanitized/Compressed 标为 stale。

模块由启动装配器加载并注入 `ChatHandler`/executor seam；保留现有 direct path 作为 kill-switch fallback。待 pipeline 具备真正 preflight/postflight 后，Hook 仅换适配器，不迁移业务状态所有权。**v1.15 缺口**：包体与契约已就绪，剩余主要是 `CommitFirstForward` 在生产主路径的注入、Redis L2 tenant-scoped 加密存储、AES-GCM envelope encryption、配置 dependency hash、AppendTerminal 终态与 `TurnArtifactBlock` 落库全链路贯通——T11 不再"新增包"，而改为"完成集成与上线"。

**R11.3 每轮制品块与快速标志**：三层缓存不能只保存“当前完整会话字符串”，否则追加一轮会复制和重压缩历史。每个会话由不可变 `TurnArtifactBlock` 链和一个可校验的 manifest 组成；块内同时记录请求侧、上游发送侧、上游返回侧和客户端返回侧的引用/哈希，正文按引用存储：


`RawRequest` 是原始输入；`SanitizedRequest` 是脱敏/泛化后的输入；`CompressedRequest` 是准备发给 LLM 的语义输入；`UpstreamRequest` 是候选节点/协议/参数处理后的最终线上请求；`UpstreamResponse` 是供应商原始返回；`ClientResponse` 是经过安全检查、恢复/脱敏策略和协议转换后的客户端返回。相同内容不复制正文，只增加引用和 hash；每一次节点重试只追加 attempt/status 元数据，不复制这六类正文块。

**R11.5 依赖哈希**：
- Raw：canonicalizer 版本 + mutation kind + 前一修订 chain hash + 当前 delta hash；
- Sanitized：Raw source hash + sanitizer 版本 + policy/config hash + placeholder schema；
- Compressed：Sanitized source hash + compressor/schema 版本 + compression mode + summary prompt/model 版本 + protocol + context-window bucket + tools hash + prefix/tool handling 版本 + model capability profile。

配置/算法变化只失效受影响的下游层：追加 Raw → Sanitized/Compressed stale；sanitizer 变化 → Sanitized/Compressed stale；compressor 或模型兼容参数变化 → 对应 Compressed variant stale。

**R11.6 同会话追加语义**：复用 Sessions V2 `(tenant, session)` advisory lock、request-id 幂等和 turn/body 同事务写入。明确 mutation 类型：`append_delta / replace_snapshot / reset / attachment_only`，禁止把 snapshot 当 delta 盲目追加。流程：
1. 当前请求提取新增 user/system/tool delta，生成 provisional revision；
2. Raw 层追加/替换并 CAS；Sanitized 尽量仅处理新 delta；Compressed 尽量用 alignment/diff 增量重建；
3. 第一次真实上游发送时提交 provisional revision；未到上游（去重命中、前置拒绝、客户端提前取消）的请求不得污染会话修订；
4. 终态响应落库后追加 assistant delta，推进 chain hash；下一请求从该修订继续；
5. revision CAS 冲突时 reload/rebase，不覆盖新修订。

### FR-12 首字节后流中断的透明恢复（v1.12）

**R12.1 触发范围**：所有首字节后的流错误统一进入 StreamRecovery，而不是直接终止：`connection_reset / unexpected_eof / eof_without_done / stream_timeout / chunk_timeout / slow-drip 判死 / upstream_close`。零语义内容或仍在可撤销窗口内时可完全透明；已提交语义内容后采用对齐续传或降级策略。

**R12.2 五级恢复阶梯**：

1. **L0 同凭据同节点重发（闪断首选）**：重新向原供应商节点发起最近一轮完整请求，默认最多 2 次（热配置）；保留上游 prompt cache/连接亲和，解决短暂网络闪断；失败后按节点失败记账并**先评估 L1 可撤销窗口**：窗口仍开放则丢弃缓冲并重执行，窗口已关闭/内容已提交则进入 L2；
2. **L1 可撤销窗口（零感知）**：扩展 `AttemptCommitGate` buffered mode，首个语义内容后的前 N 秒/前 N 个 chunk 暂存于网关、不写客户端（建议默认 5s 或 20 chunks，取先到者，热配置）；窗口内中断时丢弃本次 attempt 缓冲，依次执行“原节点重发 → 同模型其它节点 → 同品质其它模型节点”，客户端只收到心跳，**完全不知道发生过中断**；代价是首批语义内容延迟 ≤窗口上限；
3. **L2 已提交内容的前缀对齐续传**：内容已写客户端时，重新发起最近一轮完整请求；网关缓存 `CommittedPrefix`（仅 hash/有限窗口字节，受内存上限保护），新流到达后用现有 message/alignment 基础做 prefix/rolling-window 对齐；对齐分数≥阈值时抑制重复前缀，只转发 suffix，实现客户端无缝续传；
4. **L3 continuation prompt（可选）**：L2 对齐失败且客户端/模型策略允许时，以“原始最近一轮完整请求 + 已发送部分内容 + 从此处继续且勿重复”构造续传请求；默认关（有语义漂移/额外 token 风险），按任务类型/模型能力白名单启用；仍先原节点，失败再换节点/模型；
5. **L4 降级**：L0–L3 全失败时，按客户端能力选择：支持 `stream-undo` 的客户端发送撤销/重开信号后完整重生成；通用客户端发送安全 SSE 注释 `: gw-stream-restarted` + thinking 帧，再完整重生成（可能重复，记录 visible_restart）；若策略禁止重复，则发送协议合法错误信封并让客户端重发（现有行为）。

**R12.3 请求内恢复状态（不新增会话权威）**：

```go
type StreamRecoveryState struct {
    RecoveryNo          uint16
    SameNodeRetries     uint8
    LastNodeID          int32
    LastModelID         int32
    CommittedChunks     uint32
    CommittedBytes      uint32
    HoldbackChunks      uint16
    HoldbackDeadlineMS  int64
    AlignmentScoreBP    uint16 // 0..10000 basis points
    RecoveryMode        uint8  // same_node/discard_replay/aligned/continuation/restart/error
    VisibleToClient     bool
}
```

每个恢复 attempt 继续使用 `NodeUseRecord` + journey attempt，`StreamRecoveryState` 只属于当前 request，不写入 URSM；终态将 recovery 摘要写 request_logs/journey/TurnArtifactBlock attempt metadata。

**R12.4 最近一轮完整请求的来源**：重发不重新跑全会话加工，直接复用 FR-11 同一 `SessionRevision` 的 `CompressedRequestRef/UpstreamRequestRef`（dependency hash 未变，零重建）；仅在切换到协议/上下文不兼容的模型时构建对应 Compressed variant；原 request 的 user turn 不重复追加，assistant 只在最终成功后追加一次。

**R12.5 跨节点/跨模型顺序**：L0 原节点重发失败 → 将该 attempt 记失败 → 同模型节点列表排除已试、按 URSM 评分取第一个 → 同模型全失败后按任务类型同品质模型映射换模型 → 逐节点测试。每次切换共享原始 100 次预算/2h deadline，客户端连接持续心跳。

**R12.6 ADR-Disp-003 条件化修订（需新 ADR）**：现有“首字节后不跨凭据切换”仅在没有撤销/对齐能力时继续成立。新 ADR（建议 ADR-Disp-007）允许以下任一条件下跨节点/模型重执行：
- 语义内容仍在 L1 可撤销窗口、尚未写客户端；
- L2 前缀对齐成功；
- 客户端声明 `X-Gw-Capabilities: stream-undo`；
- 运营策略明确允许 L4 visible restart。

以上条件均不满足或恢复模块降级时，回退 ADR-Disp-003 旧规则（同凭据续传或错误信封），不得静默拼接重复内容。

**R12.7 预算、成本与防风暴**：恢复 attempt 共享 `UpstreamAttemptBudget` 和 2h deadline；额外增加 `stream_recovery_max_attempts`（建议默认 3，热配置）和 `same_node_stream_retries`（默认 2）；每次重执行独立记录 token/成本，达到恢复上限转 L4，不允许无限重生成。

**R12.8 客户端撤销（best effort）**：标准 OpenAI/Anthropic SSE 无法撤回已发送字节，因此通用客户端只能收到注释/思考提示；为支持撤销的客户端定义能力头 `X-Gw-Capabilities: stream-undo` 和版本化控制事件（不作为通用协议默认）；前端/SDK 收到后删除未完成 assistant block，再接收完整重生成。未知/严格客户端只收 SSE 注释，避免 schema 解析失败。

**R12.9 SLO 与可观测性**：把原“流中断率”拆成：
- `stream_interrupt_total`：上游实际中断数；
- `stream_recovery_success_total{mode=same_node|discard_replay|aligned|continuation}`；
- `client_visible_stream_interrupt_total`：最终到达 L4 error/visible restart 的客户端可见中断；
- `stream_alignment_miss_total`、`stream_recovery_cost_tokens`、恢复时延 P95。

质量 SLO 以**客户端可见中断率**为主指标，而不是把所有已恢复中断计为失败。

## 4. 非功能需求

- 队列登记/观测开销为异步旁路，观测降级不影响请求成功路径（recorder 已有 drop/degrade 指标）。
- 心跳带宽开销 < 1KB/s。
- 所有阈值集中配置、支持热更新（复用 `settings_kv`/hotconfig 通道）。
- 兼容 OpenAI / Anthropic / Gemini 三族客户端协议语义。
- 单请求处理逻辑 panic 隔离，不影响网关整体。

## 6. 关键状态机与数据结构总览

- **请求**：`received → routing → model_queue → credential_queue → node_selection → upstream → streaming → retrying* → terminal`（阶段词表见 `requestjourney/contract.go:79-89`：终态统一为单一张 `StageTerminal`，成败由 `Outcome`（success/failure/canceled，`contract.go:262-266`）与终端事件类型（request_succeeded/request_failed/request_canceled）区分——契约中**不存在** `failed_exhausted`/`client_aborted` 阶段词，正文其余处对这两个词的引用应理解为 Outcome+原因语义）。注册表三态映射：received/routing/model_queue → pending；upstream/streaming/retrying → in-flight（retrying 携带 retry_at 时回 pending，到点再入 in-flight）；终态 → completed。
- **节点**：`available →(3 连败) degraded →(延迟探测) probing → available | offline(探测连续失败)`，offline 由 36h 扫描器/reviver 唤醒。
- **凭据**：`ready ⇄ cooling/rate_limited/unreachable →(恢复) ready`；`auth_failed` 单次即置但附 15min 自动恢复窗（R5.2），`suspended` 需人工介入，均告警。

## 8. 专业性修正说明（相对原始文本的变更）

1. **三级队列定位（v1.2 修订）**：队列是状态管理/切换/重试调度的骨架（调度层真实队列 + 观测层投影双层，R1.4）；观测投影被挤出 ≠ 取消请求，调度条目存活至终态，completed 条目在注册表保留至 FIFO 淘汰。
2. **非流式保活物理不可行**：think/心跳仅流式语义有效；且「普通非流式保持同步」是先序冻结决策（doc 18 §2.2.6），非流式长程走既有 durable-202 能力握手通道，不自动对无握手客户端发 202（R3.3，v1.1 修订）。
3. **100 次 × 最长 2min ≈ 最坏 3.2 小时**：必须组合穷尽优先终止 + 总时限 + 保活三者配套，否则客户端/代理层先超时。
4. ~~双层 100 次上限需统一~~（v1.1 已核实解决）：三层共享 `UpstreamAttemptBudget`，外层持有者唯一（retryowner），不存在双重计数；任务总时限由 survival Deadline（默认 24h）承担（R2.4）。
5. **重试的计费副作用**：每次尝试独立生成计费，token/成本必须随尝试入库，无人值守长程任务尤其要可审计（R2.7）。
6. ~~「连续失败 3 次」需全局统一定义~~（v1.3 已核实解决）：URSM v2 authoritative 模式下 `record_request.lua` 即单源（fail_streak≥3 降级、成功清零、退避封顶 1h、冷却期成功即刻恢复），旧状态层自动旁路；剩余工作是旁路核验与 HealthStatus 桥接（R4.2）。
7. **模型切换「同品质」需运营配置**：任务类型→品质档位→模型回退链，缺此配置切换会乱（R2.3）。
8. **指令性错误直接返回**：不进入 100 次循环，避免无意义重试放大延迟与费用（R2.2）。
9. **网关重启的在途请求语义（v1.7 审计纠偏）**：普通 dispatch/普通流式请求进程重启后默认丢失；pending 只负责响应结果回放，不代表重新执行；legacy 202 进程内、重启即失；只有 durable task 的快照、lease、fencing 和 recovery worker 承担重启恢复。**v1.15 勘误**：queue mirror（`domains/dispatch/queue_mirror.go`）已可加载跨实例观测与元数据重建，但仍只承诺观测，不承诺普通 dispatch 执行恢复。journey outbox 只恢复观测事件（`observation_outbox.go`）。长程无人值守任务必须走 durable 通道，不能把 Redis queue mirror 当执行恢复。
10. **streamretry 包装器保留为 fallback**（**v1.15 勘误**）：代码层面 streamretry 仍在 mux 层（`cmd/gateway/main.go:106` import；`main.go:1390,4760` 条件接线），survival 启用时被 `cfg.StreamRetryEnabled=false` 强制关闭（`main.go:253-261` `// the mux streamretry wrapper are mutually exclusive; survival wins`）；当 survival 未启用时仍为 fallback。T4 不应"评估启用"，现状是与 survival 二选一保留的兼容路径。
11. **survival 是租户级开关**：本需求「不停重试至成功」的前提是目标租户启用 survival（SR-07 装配）；默认启租策略是 T3 的必答决策项。
12. **旅程容量与注册表三态化（v1.15）**：观测投影 100/30/100 已是默认值（`requestjourney/config.go`）；调度侧 `MaxQueueDepth=300/RegistryCapacity=1000/CompletedWatermark=50/RetryPerCredential=2` 已是对应默认值（`dispatch/config.go:65-72`）。T2 的主体工作是测试覆盖、运营路径与观测贯通；recorder 泵容量（4096）是另一层勿动。
13. **背压与容量分层（v1.4 → v1.15）**：调度队列（模型/节点）上限 **300**（已是默认）、满即拒（overflow 可重试错误，分类在 `dispatch/journey.go:255-282`）；总队列/注册表 **1000**（已是默认）不设拒绝阈值；观测投影 100/30/100——三层容量语义（执行/登记/展示）必须在实现与文档中显式区分，禁止混用同一配置键。

### 9.2 存储结构与操作 API 核对

**缓存**：通用 LRU 原语 = `domains/ursm/v2/cache/lru.go`（线程安全泛型、`Update` 原子 RMW 消 TOCTOU）；NodeMirror（16 分片、10 万条、软 TTL 30s、代际单调 CAS、pub/sub 失效广播）、StickyStore（L1/L2/L3 + Lua compare-and-del）、IntentStore 均构建于其上。另有 resolve 缓存（120s + 负缓存 + singleflight）、provider 候选缓存（30s + 代数 ABA 防护，`InvalidateCandidateCacheForCredential` 按凭据失效）。**判定**：新缓存一律复用「LRU + Redis 镜像 + 代际 CAS」模式；`Manager.FilterAndScore` 的 mirror-first 契约需按 P0-1（v1.13 修订版）收敛——ready-gate 绕过已修复（afb13c9ea），剩余为「ready=true 且 Redis 故障 + 全量镜像命中仍继续路由」场景的档位决策（见 §14.3）；重构项 = `routing.StickyCache` / URSM StickyStore / fpslot NodeState 三层收敛（authoritative 下前两者已合一；fpslot→URSM 单向迁移 `MigrateFpSlotsNodeStates` **已存在并在启动时执行**，`ursm/v2/cache/migrate_fpslots.go:62`、`main.go:742`）。

**请求存储**：`request_logs_hot`（PK request_id、`ON CONFLICT` upsert、终态守卫防成功回退；`routing_attempts` jsonb + GIN 索引、t0–t9、gw_session_id/parent_request_id/compression 字段），7 天后 `promote_request_logs_hot_to_partition` 进月度分区并列存归档；读视图 `request_logs_with_current_month`；管理查询 `/api/logs`、`/api/logs/{request_id}`。**判定**：复用为审计主轴（36h 扫描、会话聚合、旅程对账）；仅当 t0–t9 + routing_attempts 确证不足时才加列/侧表。

**会话轮次存储**：`sessions`（session_id/total_turns/last_model/task_type 等，月分区）/ `session_turns`（(session_id, turn_no) + request_id 交叉校验）/ `session_bodies`（请求/响应增量，列存分区）/ `session_turn_logs`（24h）/ `session_summaries`（`internal/summarystore`，summary_version 自增 + xmax 竞态检测（非严格 CAS）；**PK=session_key 单列、非 tenant-scoped**——见 R11.8 P0 安全）；V1→V2 双写镜像 `internal/sessionv2mirror`（有界 backlog + Prometheus 水位）。**判定**：复用为轮次账本——「唯一成功」落在 turn_no + 请求行标记，不新建表；重构 timeline 读路径（仅读 hot 导致 >7d 截断、sessions.id 与 session_id 主键歧义）。

**节点状态存储**：运行时层 = Redis `ursm:v2:node:t:{tenant}:{cred}:{model}`（当前 key TTL 3600s，目标 NodeTTL 15min，Lua 原子写）；DB 持久层 = `credentials.availability_state`（凭据级六态 + recover_at）、`credential_model_bindings`（节点级 available/unavailable_reason/unavailable_recover_at + manual 保护触发器 + NOTIFY 自动路由）、`node_probe_state`（探测退避梯，PK (credential_id, raw_model_name)）、`model_offers` 视图；调用历史 = Redis `llmgw:callhist:{cred}:{model}`（LTRIM 100 条 / TTL 2h）。**判定**：authoritative 下路由读 URSM、DB 持久层由 credential writer / credentialhealth 各司其职，双层并存但**禁止双写冲突**（T5 核验并成文职责边界）；新增仅「调度队列状态 Redis 镜像」一项（见 9.1），且镜像只支持观测/元数据重建，不自动赋予普通 dispatch 重启执行能力。

### 14.2 端到端时序剧本（长程不稳定会话推演）

6. **t=41s** 同一 `request_id` 仍由网关持有连接并发送心跳/恢复 thinking，客户端不创建新请求；恢复 attempt 复用同一 `SessionRevision` 的制品 manifest（零重建），若 L0/L2 失败才按 ADR-Disp-007 条件切换节点/模型并进入 L4；
7. **t=42s** 恢复流继续输出；**t=3min** 流完 → 客户端收全量；`AppendTerminal` 只追加一次 assistant、推进链、下游制品 stale；若 T13 尚未上线，则按旧 ADR-Disp-003 记录可见错误并由客户端重发，该路径不得被当作 v1.14 达标结果；
8. **客户端视角（目标）**：同一请求无可见重试、全程无 >15s 无字节间隙、无挂死；**数据面**：旅程完整记录 1 请求 × 3 个 upstream attempt（A 首字节前失败、B 首次流、B L0 恢复后对齐终态），1 次流中断、1 次制品命中、A/B 失败计数与恢复模式；客户端重发仅作为 T13 未上线时的旧行为对照。

### 14.8 模拟结论

**设计验证结论（v1.15）**：目标架构可以把除确定性不可恢复错误外的故障闭环到"重试 / 同节点重发 / 换节点 / 换模型 / durable 恢复 / 明确终态"。相对 v1.14，**当前已可在首字节前闭环 R1.1/R1.6/R1.7/registry/retry_at/queue mirror/dispatch 默认 300/0/1000/50/30/survival `Deadline=2h`/±20% 抖动/HealthStatus 半成品贯通/queue mirror 跨实例观测/P0-1 默认档保护性拒绝/`session/preprocess` 接口契约**。但**当前代码还不能宣称不经常中断**，剩余阻断：① 首字节后 FR-12 五级阶梯未实现；② EOF/空流在部分协议路径误判成功；③ 路由/无候选/状态面瞬时错误在 survival 之前提前返回；④ attempt 间 CommitGate/StreamCapture 未隔离；⑤ 慢客户端无写 deadline；⑥ HealthStatus dispatch EffectUpdateURSM 调用方仍未补字段（半成品）；⑦ sanitize Redis key tenant scope 未修（P0 安全门）；⑧ 36h NeedProbe 未实现。

因此不能把 N14 继续描述为"唯一不可修复中断源"，也不能把五级阶梯描述为已上线行为。真实达标条件：除 T8 外的 T0–T7/T9–T13 全部完成并通过契约、定向和故障测试；T12 混沌矩阵建立四项 SLO（含 `MirrorGraceEnabled` 默认档 vs 灰度档差异）；A1–A18 全部通过后，才可宣称客户端稳定性达标。本轮（v1.15）审计再次校验代码基线、未修改业务 Go/SQL/前端代码；定向测试通过，但未执行完整混沌、kernel-level 慢客户端、Redis 故障多实例和生产部署验证。

## 15. 最终设计验证与执行顺序（v1.15）

### 15.1 必须成立的不变量

以下不变量是设计验收的必要条件，任一不成立都不能进入下一阶段：

| 不变量 | 设计要求 | 违反后的处理 |
|---|---|---|
| I1 客户端连接所有权 | 一个 `request_id` 只有一个 serialized writer owner；心跳、数据、thinking、错误帧全部串行写；写失败立即取消上游 | 终止当前 request，释放所有资源，不能继续后台写 |
| I2 Attempt 隔离 | 每个真实 upstream attempt 独立 CommitGate、capture、attempt_id、资源 lease；丢弃一个 attempt 不污染下一个 | P0，禁止跨节点重试 |
| I3 可恢复错误不提前终止 | 网络、EOF、空回复、429、5xx、timeout、no-channel、临时 route/state error 必须映射到 retry/wait/switch；只有确定性错误或预算/时限/组合穷尽才终态 | P0，补错误分类单测 |
| I4 客户端可见性 | 未提交内容可丢弃；已提交内容只能对齐续传、能力撤销或明确 restart/error，不能静默拼接 | P0，失败则回旧 ADR 行为 |
| I5 资源守恒 | Governor、FP slot、RPM/TPM reservation 的 acquire/release 在成功、失败、取消、超时、panic、进程退出路径均配对 | P1，阻断压测 |
| I6 状态单源 | URSM 是节点资格权威；Governor/fpslot 是准入权威；registry/journey/liveactions 是不同读模型，不互相写权威 | P0，禁止新增第二状态源 |
| I7 会话修订单调 | 只有真实首次 upstream CAS 才推进 request revision；终态 append 一次；并发冲突 reload/rebase | P1，阻断会话恢复 |
| I8 会话最终性 | 同一 `gw_session_id` 至多一个 final success；attempt terminal 与 request final terminal 分开 | P0，阻断自动化和质量统计 |
| I9 观测可重建 | durable journey/request logs 能重建完整尝试；liveactions 可丢但必须标 observation gap；每 attempt usage/cost 可对账 | P1，阻断 SLO |
| I10 供应商公平利用 | 节点排序读取真实 URSM 分数和实时资源；sticky 只在节点健康/未满载时优先，失败后及时失效 | P1，阻断资源利用验收 |

### 15.2 可恢复错误处置矩阵

| 错误 | 可恢复性 | 首选动作 | 失败后 | 允许终态 |
|---|---|---|---|---|
| DNS/TCP/TLS/connection reset（首字节前） | 可恢复 | 原节点/同凭据重试 | 同模型换节点 → 同品质模型 | 预算/时限/组合耗尽 |
| EOF / `eof_without_done` | 可恢复，除非有权威完成标志 | 同节点重发；已提交则 FR-12 | 换节点/模型 | FR-12 上限/预算耗尽 |
| 空回复 | 可恢复 | 丢弃未提交 attempt，同节点重发 | 换节点/模型 | 组合耗尽 |
| 429 / rate limit | 可恢复 | 遵守 `Retry-After`，跳过当前满载窗口 | 换节点/模型 | 预算/时限耗尽 |
| 5xx / upstream down / timeout | 可恢复 | wait-recovery + retry_at | 换节点/模型 | 预算/时限耗尽 |
| stream chunk timeout / post-first-byte reset | 可恢复 | L0→L1→L2→L3 | L4 restart/error | 恢复上限/时限 |
| route Redis/PG transient error | 可恢复 | WaitRecovery + refresh | 状态面恢复后重路由 | 状态面总时限 |
| queue overflow | 可恢复但拒绝入队 | `overflow` + Retry-After | survival/客户端退避重发 | 客户端超时/取消 |
| credential periodic quota / no channel | 可恢复 | recover_at/Retry-After 等待 | 换凭据/节点 | 组合耗尽 |
| credential permanent quota / revoked auth | 不可在当前凭据恢复 | 标记凭据失效，换凭据 | 换节点/同品质模型 | 无可用组合 |
| invalid model / 参数错误 / policy hard reject | 确定性 | 直接返回 | 不重试同配置 | 终态 |
| client cancel / write failure | 不应继续对客户端恢复 | 取消全部上游、释放资源 | 不重试 | `client_aborted` |

### 15.5 设计验证结论（v1.15）

设计目标是可达成的，v1.15 相对 v1.14 把更多底座拉到了”已落地默认”：dispatch 容量分层（R1.3/R1.8 默认值与硬兜底修复已生效）、registry 三态 + `retry_at`（R1.1 落点已具备）、queue mirror 跨实例观测（仅元数据，绝非执行恢复）、survival `Deadline=2h` + ±20% 抖动、URSM 默认参数 30s/1800s/15min、P0-1 默认档切回保护性拒绝、`domains/session/preprocess` 接口契约。但当前代码仍处于”首字节前大部分恢复可用、首字节后透明恢复未实现、错误与观测闭环不完整、HealthStatus 全链路未贯通、36h NeedProbe 未实现、sanitize Redis tenant scope 未修、final-success claim 未落地”的状态。最终目标的判定标准不是”测试包通过”，而是同时满足：

```text
所有可恢复错误 → 有且只有一个恢复 owner → retry/wait/switch
客户端可见输出 → 有 commit/recovery 语义保护
资源 acquire → 有确定 release/reconcile
会话追加 → revision/CAS/最终成功唯一
每次 attempt → 可观测、可计费、可重建
状态面故障 → 行为符合冻结档位（默认档=保护性拒绝，灰度档=软 TTL）且可自动恢复
HealthStatus → URSM 与 dispatch 调用方贯通
sanitize → Redis key tenant-scoped + offset 原子分配
```

在这些条件与 A1–A18 全部通过前，系统只能称为”具备部分稳定性基础”，不能称为”稳定可靠的无人值守长程会话底座”。v1.15 的全文重审不修改任何业务 Go/SQL/前端代码（仅文档），与 v1.14 同样保持”文档是说明、代码是事实”的两分离原则。
