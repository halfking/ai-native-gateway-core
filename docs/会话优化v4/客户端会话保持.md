## 1. 背景与目标

网关代理多上游供应商，上游存在请求失败、空回复、网络中断、无候选节点等不稳定因素。本需求要达成：

1. **无人值守长程任务完成率最大化**：在客户端不主动终止的前提下，自动重试、切换节点、切换模型，直至成功或穷尽所有组合（兜底上限 100 次）。
2. **客户端连接稳定不受上游影响**：上游的断连、切换、重试对客户端透明；网关通过协议适配的心跳维持客户端连接活跃。
3. **全链路可观测**：请求的路由、分配、状态、错误重试痕迹如实落库并可视化。
4. **节点与凭据自愈**：故障节点自动降级、自检、恢复；偶发凭据错误自动恢复。

> 原始需求中「客户端的网络中断不应影响客户端的网络」按语义修正为：**上游网络中断不应影响客户端连接**。

## 2. 术语

| 术语 | 定义 |
|---|---|
| 请求 (Request) | 客户端一次调用，服务端生成唯一 `request_id` |
| 尝试 (Attempt) | 请求在某个「模型 × 供应商节点」组合上的一次执行，有唯一 `attempt_id` |
| 会话 (Session) | 同一逻辑请求（含客户端重发）的多次请求/尝试集合，共享 `gw_session_id` |
| 节点 (Node) | 供应商凭据 × 模型 的路由单元（对应 credential_model_binding） |
| 降级 (Degraded) | 节点被移出调度，不接受新请求，等待自检 |
| 自检 (Probe) | 对节点的主动健康探测（轻量真实调用） |
| 保活 (Keep-alive) | 网关对客户端连接的心跳维持 |
| 连接注册表 | request_id → 缓存的请求信息 + 客户端连接写出流的映射，用于跨组件回写数据/保活帧（R1.6） |
| URSM v2 | Unified Routing State Manager（`domains/ursm/v2`）：Redis 权威的节点路由状态中枢；NodeView 粒度 = (租户, 凭据, raw_model)；Lua 状态机 + 16 分片 LRU 镜像 + 代际 CAS + 发布/订阅失效广播；治理规范见 `docs/会话优化v4/04-节点状态与路由处理设计.md` |
| 组合穷尽 | 所有「同品质候选模型 × 其可用节点」均已尝试且失败 |
| 会话语义制品 (Session Artifact) | 同一会话修订上的原始、脱敏、压缩三类可复用表示；每层由 source revision/hash + dependency hash 决定是否可复用，不能只看“是否存在” |

## 3. 功能需求

### FR-1 三级请求队列与请求旅程（状态管理/切换/重试调度骨架，v1.7 审计版）

**R1.1 总请求队列（请求注册表）**：所有进入网关的请求在此登记，跟踪全生命周期三态：**待执行 pending（含定时重试：条目携带 retry_at，到点由执行器拾取）/ 执行中 in-flight / 已完成 completed（成功或终态失败，保留至被挤出）**；容量默认 **1000**（可配置、热更新）——所有请求先完成连接注册与内容缓存（R1.6/R1.7）再入总队列，故总队列可能超过 1000，**不作为拒绝阈值**；观测投影 total 视图仍为 100（见 §5 容量分层）。条目存请求 ID + 状态 + 关键时间戳，用于与请求实例、客户端连接匹配。
**R1.2 模型请求队列**：模型路由确定后（客户端指定或任务分析）登记（请求 ID + 模型名），同样三态生命周期；观测投影容量默认 **30**（可配置）——注意与调度层模型队列的**执行容量上限**（R1.3 的 300）是两层不同语义，实现与文档中必须显式区分。
**R1.3 供应商节点队列**：每节点一个队列，登记 (请求 ID, 尝试号) 与该节点上每次尝试的成功/失败状态；连续失败达阈值（默认 3）→ 请求改挂其他节点队列、原节点降级；每节点队列配 **Governor 并发与流量限制**（in-flight 硬帽 / RPM / TPM 令牌桶）与**指纹 slot 配额**（`credentialfpslot`：按凭据指纹 acquire/reclaim/quota，Redis 节点态 TTL 3600s）；两套限额的镜像值进节点状态缓存包的资源仪表（R10.4/FR-10），供选择闭包满载预过滤。**调度层模型队列与节点队列容量上限默认 300**（`llmgw_dispatch_max_queue_depth`，现默认 1024 需改；热配置），**达到上限即拒绝入队**——立即返回 `overflow` 可重试错误（journey 错误词表已有 overflow），不再排队等待（`MaxQueueWaitMS` 默认设 0 或极短，热配置），防止拥堵向内存与上游传导。
**R1.4 双层结构（定位修正）**：三级队列是**请求状态管理、切换与重试调度的骨架**，分两层实现——
- **调度层**（`domains/dispatch`，真实执行队列）：Tier-1 模型队列 / Tier-2 节点队列为 chan 队列 + worker（dispatcher / forwarder），**执行器只面向队列条目操作**（取请求 → 选路 → 连接节点 → 流转发 → 回写结果），与 HTTP handler 结构解耦（dispatch 不 import executors/provider；`QueuedRequest` 单所有者移交语义）；失败回队即切换/重试的再调度；T1–T6 时间戳即 total / model / credential 三级队列的入队/出队留痕；
- **观测层**（`domains/requestjourney`，投影）：对三级队列做 FIFO 投影（内存/Redis/PG 三源）+ 状态展示，管理端可查；**投影被挤出 ≠ 请求被取消**，调度条目存活至终态。队列登记异步旁路，登记失败不得影响请求执行。
**R1.5 可观测性**：一切状态变迁发事件（`node_switched`、`model_switched`、`retry_scheduled` 等，词表见 `domains/dispatch/observation.go:14-43`）；请求级全流程 action 事件流已有基础设施（`internal/liveactions`：request_id 键控、单调 seq、旁路异步、有界丢弃、Redis LIST + SSE 回放），FR-3 将其桥接到客户端。管理端按 总览/模型/节点 三视图查询队列快照，展示请求当前阶段、所在模型/节点、attempt 历史轨迹（含每次切换与重试原因），错误重试痕迹直观可见。
**R1.6 连接注册表（新增）**：request_id → 缓存的请求信息 + 客户端连接写出流；流式生存期内，执行器/调度器/后台任务可据此直接向客户端回写数据或保活信息（思考帧，见 FR-3）；连接关闭即注销，注册表并发安全、容量有界。
**R1.7 请求内容物化（目标能力，当前尚未实现）**：请求进入总队列前，将请求内容写入版本化 request snapshot codec/store：压缩后缓存 Redis（键风格 `gw:reqcache:{request_id}`，TTL 默认 2h，热配置），并异步落库保存可校验的快照元数据/正文引用。**不得假定 `session_bodies` 已提供应用层 zstd 编解码**；当前 writer 写 JSONB，数据库 columnar/zstd 是存储层能力，需显式新增 codec（版本、大小、hash、完整性、租户绑定/AAD）。执行器可从 Redis 或 DB 装载快照，但只有带 durable lease/fencing 的 durable task 才能在网关重启后继续执行；普通 dispatch 的 Redis 镜像只能支持观测/元数据重建，不能宣称自动恢复执行。缓存 TTL、压缩开关、容量、最大正文大小全部热配置。

**现状（v1.7 审计）**：调度层已具雏形——`QueuedRequest`（`domains/dispatch/queued_request.go:65-166`）携带 ID/SessionID/Requested·ResolvedModel/每请求切换策略（`AllowModelChange`、`ModelAlternatives`、`RetryPerCredential`、`AllowProviderChange`）/TriedCredentials·TriedModels/AttemptCount/ResultCh/T0–T9（T1/T2 即 total 队列入/出队）；Governor 四模式（concurrency/rpm/tpm/disabled，`queued_request.go:11-16`）；观测层三视图投影 + 管理端 queues 端点已存在。**缺口**：① 总队列（请求注册表）无统一三态生命周期登记——T1 仅是时间戳，无 pending/in-flight/completed 注册表实体与状态字段；② 失败回队的**定时再执行（retry_at）**未落地（dispatch failover 立即改道，退避等待只在 survival 层）；③ **连接注册表不存在**——客户端写出流由 handler goroutine 持有，跨组件按 request_id 找连接需新增注册表；④ journey 投影容量默认 100/100/100（`config.go:5-9`，hotconfig 键 `llmgw_request_history_*` 已有），模型队列需改 30。注意 recorder 三路 store 泵容量（默认 4096，`recorder.go:13`）是另一层，勿混淆；⑤ 调度队列状态（Tier-1/Tier-2 深度、in-flight 槽位）目前**仅进程内**（`pipeline.go` maps、`credentialfpslot/slot.go`），网关重启即失——需评估按 URSM v2 键风格（`ursm:v2:*`）补 Redis 持久镜像以支持重启重建与跨实例观测（见 §9.2 判定）。

### FR-2 路由与执行引擎（重试 / 切换 / 预算）

**R2.1 尝试编排**：请求 → 模型解析（指定或任务分析）→ 候选节点集 → 逐组合尝试。
**R2.2 错误二分法（先行条件）**：必须先有错误分类表——
- **指令性/确定性错误**（参数 400、鉴权失败、内容策略拒答、模型不存在）：同配置重试无意义，直接按规则返回客户端（鉴权失败可触发换凭据）；
- **瞬时错误**（网络中断、超时、5xx、429、空回复、连接重置）：进入重试/切换循环；429 优先遵守上游 `Retry-After`。

**R2.3 切换阶梯**：① 同节点重试至连续失败 **3** 次（即 1 次原始 + 2 次重试）→ ② 同模型换下一可用节点 → ③ 该模型所有节点穷尽 → 按任务类型切换到**同品质档位**模型（任务类型→品质→模型映射为运营配置）→ ④ 新模型下重新执行 ①② → 直到组合穷尽或达到全局上限。
**R2.4 重试预算（归属已明确，默认值需实施变更）**：全局尝试上限默认 **100**（可配置）；回退为指数退避 + 抖动（±20%），初始 2s，**封顶 120s（2 分钟）**，上游 `Retry-After`/`recover_at`/探测时间优先（doc 18 §8.4）。**组合穷尽优先于次数上限终止**。外层重试持有者唯一（SR-W0，`internal/retryowner` 在 HTTP 边界冻结），survival 协调器把 `MaxRetries` 注入共享 `UpstreamAttemptBudget`（`survival_coordinator.go:196-198`、`executors/attempt_budget.go:8`），三层共用同一预算。当前 survival `Deadline` 默认 24h（`survival_coordinator.go:45-47`），目标值为 2h；在代码与热配置完成前不得宣称 2h 已生效。
**R2.5 客户端主动断开**：立即停止调度、取消进行中的上游尝试（context 传播）、会话标记 `client_aborted`——这是「不停重试」的边界。
**R2.6 首字节语义（ADR-Disp-003 已锁定）**：首字节后不做跨凭据切换（仅同凭据续传 `isResumable`）；首字节前失败可无缝换节点/换模型。透明恢复仅限首个语义内容之前，工具调用后不自动重放（doc 18 §10.1/§10.3）。
**R2.7 成本记录**：每次尝试独立计费，token/成本随尝试记录入库。
**R2.8 路由节点匹配以 URSM v2 为单一权威（v1.3）**：候选过滤与排序复用 `Router.PlanCandidatesWithContext` → `URSMv2.FilterAndScoreReadyWithSource`（`domains/ursm/v2/manager.go:356`；评分 `score = 0.4·price + 0.4·latency + 0.2·(1−SR5m)·1000`，低者优先，缺失 SR5m 取中性 0.5）；authoritative 模式下 Redis 读失败或 ready 门未开 = **保护性拒绝**（返回空候选，不回退旧状态层）；三级队列的节点匹配作为 `FilterAvailable` 之后的接入点（参照 pressure-aware hook 的插入方式，`router.go:330`），**不在 URSM 内部新建队列状态**；任务类型→同品质模型的会话意图可复用 URSM `IntentStore`（按 session 存 TaskType/ChosenModel/CredentialID，`domains/ursm/v2/cache/intent.go`）。**节点选取（流程 4，v1.4）**：候选列表经 URSM 评分排序（负载均衡 + 成本 + 近期失败率）→ 排除本请求已试节点（`TriedCredentials`，首轮为空）→ 取排序第一；会话粘滞（StickyStore）在无故障时优先，故障切换后按上述规则；**每个请求记录使用过的节点 ID 与其上的结果状态**（journey attempt 记录 + `TriedCredentials`，杜绝重复使用失败节点）。

**现状**：`domains/dispatch/failover.go:39-125` 已有完整阶梯（同凭据重试 `RetryPerCredential=2`（由 `MaxNodeFailures=3` 推导）→ 换凭据 → 换模型）；`maxAttempts=100` 与 `executors.DefaultUpstreamAttemptLimit=100` 同源；survival 协调器（`domains/streaming/survival_coordinator.go`，doc 18 §5.1）是**唯一外层恢复循环**：retry-now / wait-recovery（等待期发协议适配心跳）/ resume-blocked / fail-terminal / fail-closed，回退 2s→120s 硬钳制、Deadline 默认 24h、MaxRetries 钳制 100；首字节后不切换已实现并锁定（`forwarder.go:251-256`、ADR-Disp-003）；legacy 路径另有 D5 模型回退（仅非流式、至多加一轮，`handler.go:4010-4013`）。survival 下 executor 内部刷新阶梯被抑制，由协调器 `Refresh` 统一重解析候选（`survival_coordinator.go:91-92,302-304`）。**URSM v2 对齐（v1.3）**：每请求尝试→节点健康的记录链路已端到端存在：dispatch 尝试 → `reduceDispatchForwardOutcome`（`executor_dispatch.go:430`）→ `nodehealth.OutcomeReducer`（按 (node, attemptID, phase) 环形去重，10 万条/15min）→ `EffectUpdateURSM`（`executor_nodehealth.go:182-198`）→ `URSMv2.RecordRequest`（DedupKey=AttemptID，`manager.go:877`）→ `record_request.lua` 原子状态机；非 dispatch 遗留路径亦直调 RecordRequest（`executor.go:3017,3283`）。**注意**：`resource/pools.go`（FP/并发/RPM 仪表盘接口）从未注入——NodeView 资源槽位恒 0，若评分需纳入队列压力须先完成注入重构（refactor 而非新建）。**缺口**：① survival 为**租户级装配**（SR-07），「100 次不停重试」达成的前提是目标租户启用 survival——默认启租策略需决策；② `dispatch_v2.allow_model_change` 默认**关闭**（`domains/dispatch/gate.go:56-58`），且缺「任务类型→同品质模型」映射配置；③ 错误分类表未成文；④ 组合穷尽提前终止与聚合错误体未实现（当前以预算耗尽为主）。

### FR-3 客户端连接保活与过程回显

**R3.1 原则**：网关接受请求后即接管客户端连接生命周期；上游切换/重试对客户端表现为一次连续的响应。
**R3.2 流式请求（保活的主战场）**：
- SSE 注释心跳 `: keep-alive`（默认 15s，`LLM_GATEWAY_KEEPALIVE_INTERVAL` 可配；2026-08-04 起默认开启并覆盖全部流式协议，`stream_runtime.go:36`、`docs/STREAM_TIMEOUT_KEEPALIVE.md`）；survival 等待期心跳已按协议分化——OpenAI 族发 SSE 注释 `: gw-survival-keepalive`、Anthropic 族发 `event: ping`（`survival_coordinator.go:150-153`）；
- 调度过程（等待节点、切换节点、已重试 N 次、切换模型）以**思考模式**增量回显，**不污染最终 answer 内容**。现状基线是 SSE 注释形式（`: thinking: <json>`，对 Zod 严格客户端如 opencode 安全，`handler.go:212-231`；节点切换回调 `handler.go:3624-3631`）；`reasoning_content` 增量 / Anthropic `thinking` 块形式为**新增项**，按客户端类型分化时须保持「注释兜底、语义帧仅对确认安全的类型开启」的次序；
- **操作事件目录（v1.2）**：等待、连接上游、重试（第 N 次）、切换节点（A→B，原因）、切换模型（M1→M2，品质档位）、数据解析（IR 转换）、脱敏/内容变换（`disguise`）、安全检查（`safety` / `internal/paramguard`）等全流程事件均纳入思考帧回显；事件源复用 `internal/liveactions` 的 request_id 键控 action 流（旁路异步、有界丢弃、Redis LIST + SSE 回放），经连接注册表（R1.6）桥接到客户端写出流——桥接为新增项，liveactions 现仅面向管理端；
- 按客户端类型自动选择心跳/回显模式（识别信号：`X-Gw-Client-Type` 头 → User-Agent 关键词，`domains/streaming/client_fingerprint.go:23-64`，`internal/clienttype` 为闭集：cursor/claude-code/opencode/zcode/codex/roocode/vscode/copilot/windsurf/zed/jetbrains/unknown；doc 42 锁定「客户端识别仅供建议，绝不替代能力头」），并提供运营开关可关闭过程回显（部分客户端会展示思考内容）。
**R3.3 非流式请求（v1.1 按冻结契约修订）**：非流式 HTTP 响应在协议上**无法心跳**，「用 think 保持住」只对流式语义成立；且「普通非流式保持同步语义」是 doc 18 §2.2 非目标 6 **锁定的先序决策**，不能擅自对无能力握手的客户端自动发 202/心跳。落地策略（基于既有两条 202 通道，而非新造机制）：
- a) **同步保持段**：非流式现状为整包缓冲、状态头仅在终局写出（`executor_chat.go:1167,1278-1307`）；单次上游调用受 `UpstreamTimeout`（默认 150s）约束、跨候选受共享尝试预算约束；服务端 `http.Server` WriteTimeout=0（`main.go:5391-5405`），实际瓶颈是前置 nginx `proxy_read_timeout` 与客户端耐心；
- b) **durable-202 通道（重启安全，契约已冻结）**：客户端携带 `X-Gw-Capabilities: durable-recovery` + `Prefer: respond-async` 即转 202 + 轮询（`domains/streaming/durable_contract.go:141-150`，doc 18 §9.4 冻结信封：Location / Retry-After / X-Gw-Pending）；后台结果仅一次成功结算（durable settlement CAS，`durable/settlement_outbox.go:40-78`）；
- c) **legacy async-pending 降级**：`202 + X-Gw-Pending + Retry-After + poll_url`（`handler.go:4189-4213`）——进程内执行、**重启不保**，仅作兜底，不作为长程任务的依赖通道；
- d) **推广而非破坏契约**：长程任务的无人值守客户端通过适配文档推动携带能力头（或改用流式）；可选「按 client type 自动附加 durable-202 能力协商」作为运营配置（默认关）。
**R3.4 错误返回条件**：非指令性错误时，只有**已穷尽所有匹配模型的可用节点（组合穷尽）或达到 100 次上限**，才向客户端返回最终错误，错误体附带尝试摘要（试过的模型/节点/原因）。

**现状**：pre-stream 保活默认开启（提前提交 `200 text/event-stream` + 注释心跳，`handler.go:186-204,3422-3450`；预热后一切失败必须以 SSE 错误信封返回、绝不 JSON/4xx——`docs/STREAM_TIMEOUT_KEEPALIVE.md` 锁定）；survival 等待期心跳已协议分化（OpenAI 注释 / Anthropic ping）；节点切换 thinking 回调已有；reasoning 跨协议桥已具备（`internal/ir/stream.go`）。`internal/streamretry` 包装器（mux 层 pre-first-byte 重试）判定为**弃用方向**：与 survival 互斥（启动时 survival 胜出并强制关闭之，`main.go:231-235`），且 pre-stream 保活默认开后其重试窗口实际不再存在（200+注释即视为已提交、无 ≥400 状态可录）。**缺口**：过程回显无运营开关；reasoning_content/thinking 语义帧形式的过程回显未实现；非流式 durable-202 的客户端采纳率为零，需推广与（可选的）按 client type 自动协商。另有 `internal/liveactions` 已将 arrive → route_resolved → model_enqueued → … → reply 每步发为 request_id+seq 的 action 事件（V3.3-OBS OBS-B1，旁路异步、有界丢弃），但仅服务管理端实时视图，未桥接到客户端思考帧。

### FR-9 端到端流程基线（v1.7 审计版）

**流程 1 · 接入与生命周期**：收到请求 → 连接注册表登记客户端信息并保持 TCP（R1.6）→ 请求快照物化（R1.7）并在 request-scope 捕获原始/脱敏表示 → 入总队列（注册表三态 pending）→ 第一次真实上游尝试前由会话预处理 Hook 加载或懒生成三级会话制品（FR-11）→ 心跳/思考帧保活（FR-3）→ 超时/取消/出错/成功收到信息 → 关闭连接（注销注册表、按策略清请求缓存；会话制品按 TTL/修订保留复用）→ 结束（completed）。
**流程 2 · 执行器主循环**：从请求队列取一个请求 → 任务判断（客户端已指定模型则跳过；否则 autoroute 任务分析）→ 路由判断（**调用节点选择闭包 R10.2：位图 O(1) 预过滤——不可用/冷却/已试/满载（并发、FP slot、RPM 任一达限，R10.4 资源仪表）——+ URSM 评分排序**）→ 会话预处理 Hook 按修订/依赖哈希复用或生成 raw→sanitized→compressed 制品（FR-11）→ 加入模型/节点队列（上限 300，满即拒）→ 第一次真实发送时提交该会话修订并 TryAcquire 占用资源仪表 → 成功收到回复 → **按请求 ID 查连接注册表找到 TCP** → 回写消息（Release 释放仪表）→ 终态持久化后将 assistant response 追加到会话源日志并使下游制品进入 stale → 在多个队列中变更请求状态（completed）→ 超时或被挤出 → 清除请求级缓存与队列信息 → 结束。
**流程 3 · 失败与切换**：执行中错误/失败 → 换节点（排除已试）→ 重走流程 2 → 成功走正常流程，失败再重试或换节点；**记录操作过的节点 ID 与状态**（**NodeUseRecord 紧凑记录 R10.3**；`TriedCredentials` 供 O(1) 排除）；该模型所有节点失败 → 按同类任务配置换模型（同品质档位）→ 新模型下逐节点再测 → 组合穷尽或达预算/时限 → 终态。
**流程 4 · 节点选取**：按负载均衡与成本（URSM 评分：0.4·price + 0.4·latency + 0.2·失败率）查询可用节点列表 → 排除本请求已试（首轮为空）→ 取第一节点处理（**由选择闭包一次完成，R10.2**）；全程记录节点 ID + 状态，避免重复使用失败节点。

### FR-10 节点状态缓存包与选择闭包（v1.7 审计版，P0/P1 门禁后接入）

**R10.1 定位（派生读模型，不新建权威）**：`domains/nodestatecache`（建议名）是**进程内派生读缓存**——「所有节点的状态的缓存处理包」。权威仍是 URSM v2 Redis（Lua 状态机，v1.3 结论不变）。本包由三条喂入路径保持一致：① RecordRequest 效应链尾部旁路更新；② 复用 NodeMirror 的 pub/sub 失效广播（`manager.go:779-814` 订阅）置脏重拉；③ 低频对账循环（默认 30s，可配）以 Redis 为准全量校准。**禁止双写**：本包永不写 URSM/DB。

**R10.2 选择闭包（NextNode）**：构造器返回闭包，签名（Go 语义）：

```go
type SelectQuery struct {
    Model            string          // 模型（必填；auto 已解析）
    TaskType         string          // 任务类型（可空；同品质档位换模型用）
    Used             []NodeUseRecord // 本请求已用节点与状态（排除表 + 状态参考）
    AllowModelSwitch bool            // 可切换模型标志
    RetryCount       int             // 重试次数
    Flags            uint32          // 其它标志位：bit0 sticky 优先、bit1 free 容忍、bit2 排除冷却中…
}
type SelectResult struct {
    NodeID, ModelID int32
    SwitchedModel   bool
    Exhausted       bool            // 组合穷尽信号（供 R2.4 提前终止）
    Alternatives    []NodeUseRecord // 后备序列（已按评分排序）
}
type NodeSelector func(ctx context.Context, q SelectQuery) SelectResult
```

行为：位图 O(1) 预过滤（剔除不可用/冷却/已试/**满载**——Full 位图命中即剔除，满载=并发或 FP slot 或 RPM 任一达限）→ 幸存集交 URSM `FilterAndScoreReadyWithSource` 排序 → 取第一（流程 4）；`AllowModelSwitch` 且当前模型幸存为空 → 按任务类型→品质档位映射换模型再选；全空 → `Exhausted=true`。粘滞优先由 Flags 控制。

**R10.3 节点使用记录（紧凑整型）**：每次节点调用记一条（序号、标准模型 id、节点 id、是否重试、状态等），位压缩尽量用短整/整型：

```go
type NodeUseRecord struct { // 16B
    Seq     int32  // 序号（请求内递增，1 起）
    ModelID int32  // 标准模型 id
    NodeID  int32  // 节点 dense id（R10.4 注册表分配）
    Packed  uint32 // bit0-7 状态枚举 | bit8-15 错误分类 | bit16 是否重试 | bit17 切换而来 | bit18 sticky | bit19-31 预留
}
```

随 `QueuedRequest` 携带（append-only，上限=尝试预算 100），并镜像为 journey `attempt_*` 事件落库——**紧凑结构用于热路径，全量诊断走 journey，两者字段映射固定**。`TriedCredentials` map 保留用于 O(1) 排除。

**R10.4 位图与统计槽（全节点快缓存）**：

```go
type NodeStateBitmap struct {   // 按 dense node id 位寻址，分片原子更新
    Avail []uint64               // bit=1 可参与路由
    Probe []uint64               // bit=1 需自检（降级/离线且退避到期/36h 命中）
    Full  []uint64               // bit=1 满载（并发/FP slot/RPM 任一达限，v1.6）
}
type NodeStatsSlot struct {     // 每节点 16B，数组按 dense id 索引
    LastUsedUnixSec int32       // 最后请求时间（秒级截断）
    Succ1h, Fail1h  uint16      // 1h 成功/失败次数（饱和计数）
    FailStreak      uint8       // 连续错误次数（对齐 URSM FailStreakLimit）
    State           uint8       // available/degraded/probing/offline 枚举
    WindowStart     uint32      // 1h 翻转窗口起点（读时比较重置）
}
type NodeResourceSlot struct {  // 每节点 16B（v1.6），原子 CAS 快速更新
    ConcUsed, ConcLimit uint16  // 在途并发（Limit=0 不限；源=credentials.concurrency_mode/limits）
    FPUsed, FPLimit     uint16  // 指纹 slot（源=credentialfpslot 配额）
    RPMUsed, RPMLimit   uint16  // 每分钟请求（分钟级翻转窗口，定时重置）
    WindowID, Flags     uint16  // 重置窗口号；Flags.bit0=满载（联动 Full 位图）
}
```

dense id 由节点注册表分配：`(tenant, credential, raw_model) ↔ int32`，容量有界，复用 NodeMirror 的分片与失效广播。位图读无锁（atomic），写分片隔离。**取舍**：饱和计数与秒级截断换密度与速度，精确遥测不在此层重复（URSM 窗口 ZSET SR1m/5m/30m + journey 全量）。

**R10.5 同包其余 API（单一责任分组）**：构造器一次返回四组闭包/方法，职责隔离、互不调用——
- `Updater(nodeID int32, success bool, errKind uint8, latencyMS int32)`：状态/统计更新（RecordRequest 效应链尾部与探测结果调用）；
- `NeedProbe(now time.Time) []NodeRef`：需自检列表（Probe 位图扫描 + 36h 命中 + 退避到期），供 R4.4 扫描器与 node_probe 消费；
- `Selector`（R10.2）；
- **资源仪表组（v1.6）**：`TryAcquire(nodeID, kind) bool` / `Release(nodeID, kind)`（并发/FP slot/RPM 的**快速值更新**，CAS O(1)，挂接 dispatch Governor 的 acquire/release 与 credentialfpslot 的 acquire/reclaim 事件流）；`ResetWindow(now)`（**定时重置**：每分钟 RPM 翻转 + 1h 统计窗口，包内 ticker 驱动，周期热配置）；`Reconcile()`（默认 30s 漂移校正，以 Governor / fpslot / URSM 为准）。**权威准入仍在 Governor 与 fpslot，本缓存持有的是派生镜像值；上限源=credentials 表与 fpslot 配额，缓存内不另建上限配置。**

**R10.6 隔离与性能**：读路径无锁原子；写路径 16 分片（对齐 NodeMirror）；资源仪表增减为 CAS O(1)（无锁、不经过 Redis）；单次选择目标 P99 < 1ms（位图预过滤后至多一次 Redis/镜像调用）；所有操作 O(1) 或 O(幸存集)；包不 import dispatch/executors（避免环，参照 dispatch 的 `CredentialRef` 解耦先例）。可选接线：以本包实现 `domains/ursm/v2/resource/pools.go` 接口，一接两得——URSM `NodeView` 的 Conc/FP/RPM 仪表（现为死脚手架、恒 0）同时被填满。

### FR-11 第一次 LLM 提交的会话语义三级缓存（v1.8）

**R11.1 三层是语义依赖，不是存储介质层级**：固定依赖图为 `Raw → Sanitized → Compressed`；每一层物理上均可有 L1（进程内）/L2（Redis）/L3（PostgreSQL）副本。层级职责：
- **Raw Artifact**：客户端协议规范化后的原始会话/本轮 delta，位于脱敏之前；包含敏感数据，必须加密保存，严禁明文日志/普通管理 API 返回；
- **Sanitized Artifact**：基于 Raw 的占位符脱敏会话，携带 sanitizer 版本、策略哈希、映射引用/哈希和显式结果状态（`sanitized/no_matches/degraded_passthrough/failed`）；
- **Compressed Artifact**：基于 Sanitized 的可发往 LLM 的压缩/摘要表示；按协议、上下文窗口档位、压缩策略版本、tools hash、模型能力 profile 分 variant，模型切换后只有兼容 variant 才可复用。

**R11.2 统一所有者与 Hook 接入**：新增 `domains/session/preprocess` 作为唯一会话预处理所有者；复用 sanitizer、`SessionCompressor`、Sessions V2 turn lock/delta/reconstruction、`ResultMemo`、`singleflight`，不把三层制品塞入 `nodestatecache`、`pending`、`sessionv2mirror` 或旧 `CompressionHook`。当前 legacy `domains/hooks` Registry 未接生产主路径，optional V2 pipeline 也没有真实 postflight，因此 v1.8 采用明确的生产 Hook 适配器：

```go
type SessionPreprocessHook interface {
    Prepare(ctx context.Context, in SessionPrepareInput) (*PreparedSessionArtifacts, error)
    CommitFirstForward(ctx context.Context, p *PreparedSessionArtifacts, attemptNo int) error
    AppendTerminal(ctx context.Context, turn TerminalTurn) error
}
```

- `Prepare`：在 tenant/session/model 已解析、当前压缩 seam 前加载/懒生成制品，但不推进持久会话修订；
- `CommitFirstForward`：由 `beginUpstreamAttempt` 在 `AttemptNo == 1` 时 CAS 提交“本请求确实第一次发往 LLM”的修订；重试/换节点复用同一 Prepared bundle，禁止重复脱敏/压缩；
- `AppendTerminal`：终态持久化成功后追加 assistant response，推进会话修订并使依赖旧修订的 Sanitized/Compressed 标为 stale。

模块由启动装配器加载并注入 `ChatHandler`/executor seam；保留现有 direct path 作为 kill-switch fallback。待 pipeline 具备真正 preflight/postflight 后，Hook 仅换适配器，不迁移业务状态所有权。

**R11.3 快速标志 + 正确性门禁**：确实需要“是否已经有了，不再处理”的标志，但**标志只能作快速路径，不能单独决定复用**：

```go
type ArtifactFlags uint32
const (
    FlagRawReady ArtifactFlags = 1 << iota
    FlagSanitizedReady
    FlagCompressedReady
    FlagRawBuilding
    FlagSanitizedBuilding
    FlagCompressedBuilding
    FlagRawStale
    FlagSanitizedStale
    FlagCompressedStale
    FlagSanitizeDegraded
    FlagBuildLeaseHeld
)

type ArtifactStatus uint8 // missing/building/ready/stale/failed/degraded/superseded

type SessionRevision struct {
    TurnNo        int32
    HeadRequestID string
    ChainHash     [32]byte
}

type ArtifactManifest struct {
    TenantID, SessionID string
    Revision            SessionRevision
    Flags               ArtifactFlags
    Raw, Sanitized      ArtifactMeta
    CompressedVariants  map[string]ArtifactMeta
}

type ArtifactMeta struct {
    Status         ArtifactStatus
    SourceHash     [32]byte
    DependencyHash [32]byte
    ContentHash    [32]byte
    SchemaVersion  uint16
    TransformVer   uint16
    GeneratedAt    int64
    FailureCode    uint16
}
```

复用条件必须同时满足：`ReadyBit == 1 && StaleBit == 0 && SourceRevision == 当前修订 && DependencyHash == 当前依赖哈希 && ContentHash 校验通过`。任一不满足即重新生成；`building` 通过 lease/singleflight 合并并发构建，避免同一会话首次并发请求重复消耗。

**R11.4 依赖哈希**：
- Raw：canonicalizer 版本 + mutation kind + 前一修订 chain hash + 当前 delta hash；
- Sanitized：Raw source hash + sanitizer 版本 + policy/config hash + placeholder schema；
- Compressed：Sanitized source hash + compressor/schema 版本 + compression mode + summary prompt/model 版本 + protocol + context-window bucket + tools hash + prefix/tool handling 版本 + model capability profile。

配置/算法变化只失效受影响的下游层：追加 Raw → Sanitized/Compressed stale；sanitizer 变化 → Sanitized/Compressed stale；compressor 或模型兼容参数变化 → 对应 Compressed variant stale。

**R11.5 同会话追加语义**：复用 Sessions V2 `(tenant, session)` advisory lock、request-id 幂等和 turn/body 同事务写入。明确 mutation 类型：`append_delta / replace_snapshot / reset / attachment_only`，禁止把 snapshot 当 delta 盲目追加。流程：
1. 当前请求提取新增 user/system/tool delta，生成 provisional revision；
2. Raw 层追加/替换并 CAS；Sanitized 尽量仅处理新 delta；Compressed 尽量用 alignment/diff 增量重建；
3. 第一次真实上游发送时提交 provisional revision；未到上游（去重命中、前置拒绝、客户端提前取消）的请求不得污染会话修订；
4. 终态响应落库后追加 assistant delta，推进 chain hash；下一请求从该修订继续；
5. revision CAS 冲突时 reload/rebase，不覆盖新修订。

**R11.6 Store API 与物理存储**：

```go
type SessionArtifactStore interface {
    GetManifest(ctx context.Context, tenantID, sessionID string) (*ArtifactManifest, error)
    Get(ctx context.Context, tenantID, sessionID string, kind ArtifactKind, variant string) (*SessionArtifact, bool, error)
    PutCAS(ctx context.Context, a *SessionArtifact, expected SessionRevision) (bool, error)
    AppendRawTurn(ctx context.Context, mutation SessionMutation, expected SessionRevision) (SessionRevision, error)

```

- L1：复用 byte-bounded LRU 思路，所有 `[]byte` 深拷贝，更新后重新执行 byte-budget eviction；
- Redis：tenant-scoped、版本化 key；Raw payload 必须 envelope encryption/AES-GCM，Sanitized/Compressed 可压缩保存；TTL 默认 2h（层级可独立热配置）；可选字段清除使用新 generation key 或显式 HDEL，不沿用 HSET-only 残值；
- PostgreSQL：`session_turns/session_bodies` 继续作为源日志；新增 artifact manifest/metadata 仅在现表不能表达时使用，不新建第二套 session 账本。

建议键：`session:artifact:v1:{tenantHash}:{sessionHash}:{kind}:{variant}`；sanitize map/offset key 必须升级为 tenant-scoped v2，且 offset 分配用 Lua/HINCRBY 原子更新。

**R11.7 现有代码复用与修复前置**：
- 复用：`TurnWriter.LockSessionInTx`、`AppendTurnInTx`、`SessionBodiesWriter.WriteBodiesInTx`、`TurnReader/OutboundBuilder`、`SessionCompressor.Prepare/CommitFinal` 思路、`ResultMemo`、sanitize context bridge/placeholder restore、alignment/message hash、singleflight；
- 修复后复用：compression `SessionCache` 的 L1/L2/L3（需深拷贝、existing-entry byte budget、Redis 字段清除/序列化补齐）；
- 不直接复用：`RawCacheV2`（单 turn overwrite、无 TTL/Redis、未接生产）、`SessionCacheV2`（治理元数据为主、生产无 Set caller）、legacy HookRegistry、optional V2 pipeline postflight、pending response cache；
- P0 安全：当前 sanitize Redis key 缺 tenant，placeholder offset 存在并发 RMW 竞争；`session_summaries` 主键需核对 tenant scope——完成修复前不得缓存真正 Raw PII 或上线跨租户会话复用。

**R11.8 可观测性**：每次 Hook 记录 `raw_hit/build`、`sanitize_hit/build/degraded`、`compress_hit/build/variant_miss`、build latency、source revision、dependency hash 前 8 字节、lease wait、CAS conflict、artifact bytes/tokens saved；以 liveactions/journey 事件回显“复用/追加/重新生成”，不输出原始正文和敏感映射。

## 6. 关键状态机与数据结构总览

- **请求**：`received → routing → model_queue → credential_queue → node_selection → upstream → streaming → retrying* → succeeded | failed_exhausted | client_aborted`（与 `requestjourney/contract.go:79-89` 现有阶段词表一致）。注册表三态映射：received/routing/model_queue → pending；upstream/streaming/retrying → in-flight（retrying 携带 retry_at 时回 pending，到点再入 in-flight）；终态 → completed。

- **凭据**：`ready ⇄ cooling/rate_limited/unreachable →(恢复) ready`；`auth_failed/suspended` 需连续确认 + 告警。

## 8. 专业性修正说明（相对原始文本的变更）

1. **三级队列定位（v1.2 修订）**：队列是状态管理/切换/重试调度的骨架（调度层真实队列 + 观测层投影双层，R1.4）；观测投影被挤出 ≠ 取消请求，调度条目存活至终态，completed 条目在注册表保留至 FIFO 淘汰。
2. **非流式保活物理不可行**：think/心跳仅流式语义有效；且「普通非流式保持同步」是先序冻结决策（doc 18 §2.2.6），非流式长程走既有 durable-202 能力握手通道，不自动对无握手客户端发 202（R3.3，v1.1 修订）。
3. **100 次 × 最长 2min ≈ 最坏 3.2 小时**：必须组合穷尽优先终止 + 总时限 + 保活三者配套，否则客户端/代理层先超时。
4. ~~双层 100 次上限需统一~~（v1.1 已核实解决）：三层共享 `UpstreamAttemptBudget`，外层持有者唯一（retryowner），不存在双重计数；任务总时限由 survival Deadline（默认 24h）承担（R2.4）。
5. **重试的计费副作用**：每次尝试独立生成计费，token/成本必须随尝试入库，无人值守长程任务尤其要可审计（R2.7）。
6. ~~「连续失败 3 次」需全局统一定义~~（v1.3 已核实解决）：URSM v2 authoritative 模式下 `record_request.lua` 即单源（fail_streak≥3 降级、成功清零、退避封顶 1h、冷却期成功即刻恢复），旧状态层自动旁路；剩余工作是旁路核验与 HealthStatus 桥接（R4.2）。
7. **模型切换「同品质」需运营配置**：任务类型→品质档位→模型回退链，缺此配置切换会乱（R2.3）。
8. **指令性错误直接返回**：不进入 100 次循环，避免无意义重试放大延迟与费用（R2.2）。
9. **网关重启的在途请求语义（v1.7 审计纠偏）**：普通 dispatch/普通流式请求进程重启后默认丢失；pending 只负责响应结果回放，不代表重新执行；legacy 202 进程内、重启即失；只有 durable task 的快照、lease、fencing 和 recovery worker 承担重启恢复。journey outbox 只恢复观测事件。长程无人值守任务必须走 durable 通道，不能把 Redis queue mirror 当执行恢复。
10. **streamretry 包装器弃用**（v1.1 结论）：与 survival 互斥（启动时 survival 胜出并强制关闭之），且 pre-stream 保活默认开后其重试窗口实际不存在；ADR-Disp-003 亦记录 dispatch 不复用 streamretry。T4 不再评估启用。
11. **survival 是租户级开关**：本需求「不停重试至成功」的前提是目标租户启用 survival（SR-07 装配）；默认启租策略是 T3 的必答决策项。
12. **旅程容量已热配置化**：容量部分仅改默认常量（模型队列 30），无需新配置通道；T2 的主体工作是请求注册表三态化（v1.2 新增）；recorder 泵容量（4096）是另一层勿动。
13. **背压与容量分层（v1.4）**：调度队列（模型/节点）上限 300、满即拒（overflow 可重试错误）；总队列/注册表 ≥1000 不设拒绝阈值；观测投影 100/30——三层容量语义（执行/登记/展示）必须在实现与文档中显式区分，禁止混用同一配置键。
14. **任务总时限 24h→2h（v1.4）**：与请求缓存 TTL 2h 对齐（缓存过期后无法物化恢复）。注意最坏重试链（100 次 × 封顶 2min）≈3.2h > 2h，故时限是比次数更强的终止条件——终止优先级明确为：组合穷尽 > 2h 时限 > 100 次预算。
15. **URSM 快恢复参数权衡（v1.4）**：冷却 120s→30s、退避封顶 1h→30min、NodeTTL 60min→15min 提升节点恢复速度，代价是抖动节点更早重入流量——由 free 计费容忍、source-priority guard、两阶段探测共同兜底；三参数需从 env 加载改为热更新，便于线上调节。
16. **紧凑统计的取舍（v1.5）**：NodeUseRecord（16B）与 StatsSlot（16B）用饱和计数、秒级截断、位压缩换密度与速度——精确遥测不在此层重复（URSM 窗口 ZSET + journey 全量）；节点状态缓存包是**派生读模型**，禁止写权威（延续 v1.3「无双写」），不一致时对账以 Redis 为准。
17. **资源仪表定位（v1.6）**：并发/FP slot/RPM 的镜像值进缓存（NodeResourceSlot + Full 位图），**权威准入仍在 dispatch Governor 与 credentialfpslot**；上限源=credentials 表与 fpslot 配额，缓存内不另建上限配置；快速值更新为无锁 CAS，定时重置覆盖 RPM 分钟窗与 1h 统计窗；可选以本包实现 `ursm/v2 resource/pools` 接口，顺带激活 URSM NodeView 的死脚手架仪表。

### 9.2 存储结构与操作 API 核对

**缓存**：通用 LRU 原语 = `domains/ursm/v2/cache/lru.go`（线程安全泛型、`Update` 原子 RMW 消 TOCTOU）；NodeMirror（16 分片、10 万条、软 TTL 30s、代际单调 CAS、pub/sub 失效广播）、StickyStore（L1/L2/L3 + Lua compare-and-del）、IntentStore 均构建于其上。另有 resolve 缓存（120s + 负缓存 + singleflight）、provider 候选缓存（30s + 代数 ABA 防护，`InvalidateCandidateCacheForCredential` 按凭据失效）。**判定**：新缓存一律复用「LRU + Redis 镜像 + 代际 CAS」模式；实施前必须修正 `Manager.FilterAndScore` 的 mirror-first 快路，不能在 Redis 权威不可用时仅凭旧镜像继续路由；重构项 = `routing.StickyCache` / URSM StickyStore / fpslot NodeState 三层收敛（authoritative 下前两者已合一，fpslot 有单向迁移 `MigrateFpSlotsNodeStates` 待执行）。

**请求存储**：`request_logs_hot`（PK request_id、`ON CONFLICT` upsert、终态守卫防成功回退；`routing_attempts` jsonb + GIN 索引、t0–t9、gw_session_id/parent_request_id/compression 字段），7 天后 `promote_request_logs_hot_to_partition` 进月度分区并列存归档；读视图 `request_logs_with_current_month`；管理查询 `/api/logs`、`/api/logs/{request_id}`。**判定**：复用为审计主轴（36h 扫描、会话聚合、旅程对账）；仅当 t0–t9 + routing_attempts 确证不足时才加列/侧表。

**会话轮次存储**：`sessions`（session_id/total_turns/last_model/task_type 等，月分区）/ `session_turns`（(session_id, turn_no) + request_id 交叉校验）/ `session_bodies`（请求/响应增量，列存分区）/ `session_turn_logs`（24h）/ `session_summaries`（summarystore，summary_version 乐观锁）；V1→V2 双写镜像 `internal/sessionv2mirror`（有界 backlog + Prometheus 水位）。**判定**：复用为轮次账本——「唯一成功」落在 turn_no + 请求行标记，不新建表；重构 timeline 读路径（仅读 hot 导致 >7d 截断、sessions.id 与 session_id 主键歧义）。

**节点状态存储**：运行时层 = Redis `ursm:v2:node:t:{tenant}:{cred}:{model}`（当前 key TTL 3600s，目标 NodeTTL 15min，Lua 原子写）；DB 持久层 = `credentials.availability_state`（凭据级六态 + recover_at）、`credential_model_bindings`（节点级 available/unavailable_reason/unavailable_recover_at + manual 保护触发器 + NOTIFY 自动路由）、`node_probe_state`（探测退避梯，PK (credential_id, raw_model_name)）、`model_offers` 视图；调用历史 = Redis `llmgw:callhist:{cred}:{model}`（LTRIM 100 条 / TTL 2h）。**判定**：authoritative 下路由读 URSM、DB 持久层由 credential writer / credentialhealth 各司其职，双层并存但**禁止双写冲突**（T5 核验并成文职责边界）；新增仅「调度队列状态 Redis 镜像」一项（见 9.1），且镜像只支持观测/元数据重建，不自动赋予普通 dispatch 重启执行能力。

### 13.7 当前不可直接承诺的能力

- 普通 dispatch 请求网关重启后继续执行：**不承诺**；需 durable lane。
- `session_bodies` 现成应用层 zstd：**不存在**；需显式 codec。
- URSM 目标参数已经热更新：**未实现**；当前主要 env。
- HealthStatus 已进入 URSM NodeView/NodeMirror：**未完成**。
- requestjourney 投影就是请求注册表：**不是**；需独立 lifecycle registry。
- Redis queue mirror 单独即可完成执行恢复：**不可以**；还需要 snapshot、lease、fencing。
