# 04 · 供应商节点状态与路由处理（主题⑤⑥）

> 状态标签：CURRENT = 已实现接线； CURRENT-PARTIAL = 部分接线；LOCALLY-VERIFIED = 当前工作区代码/测试已核实；DEPLOYMENT-PENDING = 尚待真实部署验证；纸面 = 设计态。
> 节点状态必须拆成「路由资格」「model probe」「probe queue」三个状态机。三者相关但不互相替代。

---

## 1. 三个独立状态机（主题⑤）

### 1.1 路由资格状态机

路由资格回答「当前请求是否允许选择此 tenant/provider/credential/model 节点」。输入来自 binding、credential health、URSM node view、manual hold、circuit 与配置。

```text
eligible
  -> suspect/degraded/cooling/unavailable/quarantined
  -> recovering
  -> eligible
```

资格变化必须使对应 credential 的 candidate cache 失效。candidate cache 不是资格 SSoT，TTL 到期也不能替代状态变更时的显式 invalidation。

客户端请求失败若属于 request/content-policy/cancel，不是节点健康证据。network、timeout、upstream、rate-limit、auth、quota、model-binding 才按 reducer 规则影响节点状态。

### 1.2 model probe 状态机

model probe 回答「一次 direct/gateway 探测对该模型节点证明了什么」，不表示任务是否正在排队。

```text
unknown/unverified
  -> direct_probe_success: recovering
  -> gateway_probe_success: healthy/eligible
  -> probe_failure: suspect/degraded/quarantined + backoff
```

同一恢复 attempt 中，gateway probe 只有在 direct probe 已成功时才能确认 healthy。probe 结果通过 node-health reducer 生成 circuit、binding、credential、URSM、cache invalidation 等显式 effects。

### 1.3 probe queue 状态机

probe queue 只回答「探测工作项如何被调度和执行」，不能直接当作节点健康状态。

```text
ready -> running -> success | failed | expired | cancelled
```

持久队列为 `credential_probe_queue`，由 `ProbeService.Run` 单一执行拥有者处理。claim 使用 `FOR UPDATE SKIP LOCKED + lease_token`，ready/running 受 dedup 唯一约束。

失败后按 probe backoff 重新产生可执行时间；queue `success` 只说明本次 job 完成，最终路由资格仍由探测 outcome 和 reducer/URSM 裁决。

## 2. 节点身份、Ready、coverage 与 TTL

### 2.1 租户化节点身份

逻辑节点身份固定为：

```text
tenant_id | provider_id | credential_id | raw_model
```

`provider_id | credential_id | raw_model` 可用于同一 tenant 内 seed/view 映射，但不得丢失 tenant 维度。空 tenant 仅用于兼容入口，不得与显式 tenant 共用 authoritative key。

cold read 从 Redis 得到的 NodeQuery 字段不足时，Router 必须由相同身份的 `CandidateSeed` 回填 provider、tenant、canonical、价格、billing、trust 和 BaseURL latency。

### 2.2 logical Ready

`Ready=true` 不是「Redis 能 ping」或「存在任意 node key」。logical Ready 表示：

1. rollout mode 允许 v2 参与 authoritative 路由；
2. recovery gate 已打开；
3. coverage manifest 中每个期望的 tenant-aware 节点均存在；
4. 每个节点具备 v2 读路径要求的最小字段；
5. 当前 recovery epoch 没有被集群协调关闭。

Executor 对 Ready 的本地缓存最多 1s，只是读优化。authoritative gate 关闭时必须回到允许的 legacy/off 路径，不能使用部分 coverage 猜测可用性。

### 2.3 coverage

coverage 是 cutover 清单的完整性证明，不是节点成功率。`WarmupFromCoverage/ValidateCoverage` 必须验证期望节点 key 与最小运行字段后才允许 authoritative 首次打开或恢复。

普通 incident recovery 可复用已有 key；authoritative 恢复必须重新验证完整 manifest。多实例同时关/开 gate 的 epoch 与 fencing 仍需部署级故障注入验证。

### 2.4 source priority

同 generation 下的裁决优先级为：

```text
Seed(0) < Request(10) < Probe(20) < Recover(30) < Admin(40)
```

高优先级状态不得被低优先级 request outcome 覆盖。request telemetry 仍可原子累计窗口和延迟，但必须保留更高优先级的 available、generation、source_priority、last_err 等字段。

manual hold 属于 Admin 级。Lua 内部读取 hold 并裁决，避免 Go 侧预读与写入之间的 TOCTOU。

### 2.5 NodeTTL

URSM `NodeTTL` 当前默认 60min。request outcome、probe 成功和 probe 失败都必须刷新同一 NodeTTL；配置为零或负数时回退默认值，禁止 `EXPIRE 0` 删除节点。

进程 NodeMirror 默认 soft TTL 30s，仅是 Redis 的只读加速副本。它不能延长 Redis NodeTTL，也不能在 Redis Lua 写成功前先写本地镜像。

probe queue job 的 backoff/过期与 URSM NodeTTL 是不同时间域。queue 条目存在不代表 node view 仍在 coverage 中；probe 写入没有刷新 NodeTTL 时，coverage 会产生悬空/过期状态。

## 3. 自检调度与两个 heartbeat 来源

### 3.1 调度来源

常用模型由静态精选集合与最近用量 Top-N 合并。深 ping、非常用 watchdog、失败 backoff 只负责把 job 放入统一 probe queue，不拥有执行权。

node probe 使用 7 步 backoff，integrity/selfcheck 使用 5 步 backoff。`LLM_GATEWAY_PROBE_QUEUE_ENABLED=false` 可回退 legacy 直跑，但不得同时启用两个执行 owner。

### 3.2 两个客户端 heartbeat 调度来源

客户端流存在两个 transport heartbeat 调度来源：

1. `StreamSession/startPreStreamKeepalive` 的周期 ticker；
2. `SurvivalCoordinator.waitWithKeepalive` 在连接内 backoff 期间的 heartbeat。

二者必须共享同一个 `SerializedStreamWriter/serializedResponseWriter`，所有客户端写入经同一串行锁，禁止各自直接写底层 `http.ResponseWriter`。

heartbeat 是 SSE comment/transport frame，不进入 durable semantic capture，不推进 `commit_state`，也不等同于供应商首字节。request context 取消或 writer 写/flush 失败后 ticker 应停止或 writer detach。

## 4. 三个生命周期

### 4.1 客户端 SSE/HTTP 生命周期

```text
headers/pre-stream transport comment
  -> waiting/routing/backoff heartbeats
  -> first semantic frame
  -> semantic stream/terminal
  -> client FIN/RST or normal close
```

预先提交 HTTP 200 与 SSE headers 后，后续失败只能用合法 SSE terminal/error envelope 表达，不能重新选择 HTTP status。

客户端 FIN/RST、request context cancel 或 write/flush error 会使 writer detach。网关不能恢复原物理 TCP，也不能把新轮询连接冒充旧连接续写。

### 4.2 vendor HTTP attempt 生命周期

```text
candidate selected
  -> limiter/pool acquire
  -> vendor HTTP connect/headers
  -> attempt metadata buffered
  -> first semantic frame committed
  -> terminal or failure
```

每个 attempt 有独立 body、buffer、gate、计时和 outcome。vendor TCP 失败只终止当前 attempt；候选切换时不得复用旧 attempt 的 metadata 或连接局部状态。

identity-bound pool 至少按 provider/credential 身份隔离。供应商连接池复用不改变客户端连接生命周期，也不提供跨供应商流续传语义。

### 4.3 durable task 生命周期

```text
CreateAndClaim/running
  -> waiting_recovery | retry_scheduled
  -> claimed by RecoveryWorker
  -> completed | failed | expired | canceled
  -> Redis pending projection
```

每次 claim/takeover 推进 fencing token；checkpoint、重排和终态更新必须匹配 lease owner/token。超过语义 checkpoint 后崩溃的任务进入 safety blocked/reaper 路径，不得重新从头执行。

durable worker 脱离原客户端 TCP，只负责完成任务并保存安全结果。它不能恢复已经 FIN/RST 的物理连接，也不能自动 replay 已交付的 content/tool call。

## 5. Failover 与语义提交边界

### 5.1 首语义帧前

```text
Attempt A: metadata buffered
  -> recoverable failure
  -> Gate.Discard()
  -> refresh candidate / connection-local backoff
  -> Attempt B: fresh gate and buffer
  -> first semantic frame
  -> flush B metadata + semantic frame
```

只要 `commit_state` 仍为 `none/metadata`、gate 可 discard 且客户端 writer 未 detach，就可丢弃 attempt-local 输出并透明 failover。

transport heartbeat 可以已经到达客户端；它不构成语义 commit。A 的 metadata 不得进入 B 的协议序列，B 不得从 A 的 vendor stream 中间位置继续。

### 5.2 首语义帧后

首个文本、tool call 或等价语义帧提交后，禁止透明从头重放到另一供应商。否则会重复文本、tool call 或外部副作用。

后续 recoverable upstream failure 只能终止当前流、返回协议内错误，或交付已安全捕获的结果。durable post-content disconnect 不自动 replay。

### 5.3 Legacy 兼容边界

legacy dispatch 仍以 `BytesSent` 判断是否可切节点；survival/durable 以 `AttemptCommitGate + PG commit_state` 判断。

两条轨道都必须遵守「已提交后不透明重放」，但不可把 HTTP headers/heartbeat 的 transport bytes 误记为 durable semantic commit。

## 6. 路由处理与 URSM v2

### 6.1 authoritative 语义

URSM v2 的 authoritative 指「Ready+coverage 成立后，v2 node view 参与最终过滤/排序」，不是「所有来源都能无条件覆盖状态」。

当前默认配置为 `ModeAuthoritative`，但实际是否可用仍受 recovery Ready gate 约束。配置 mode、logical Ready、coverage 三者必须分别观测。

### 6.2 过滤与评分

过滤先于评分。缺失 Redis node key 或缺少最低运行字段时，authoritative 路径默认 `Available=false`，避免冷状态被当作健康候选。

当前评分为越低越优：

```text
score = price_weight * price
      + latency_weight * latency
      + stability_weight * (1 - success_rate) * 1000
```

默认权重为 price 0.4、latency 0.4、stability 0.2。`sr_5m` 缺失、样本不足或 NaN/Inf 时取中性 0.5，越界裁剪到 `[0,1]`。

五维评分、P2C、L1/L2/L3 智能绑定仍不能标为已全面接线。本文只将当前三项加权公式视为 authoritative 排序的已核实口径。

### 6.3 cold identity

Redis fresh/cold read 不携带完整 provider 身份时，必须按 `provider_id|credential_id|raw_model` 找回原 CandidateSeed，并保留 tenant。

这避免 provider=0、不同 provider 下同 credential/model 相互覆盖，以及 cold LRU miss 导致间歇性零候选。

### 6.4 telemetry

request outcome Lua 原子维护 1m/5m/30m 样本、成功数、成功率与 latency EWMA。即使更高 source priority 阻止资格字段更新，telemetry 仍继续记录。

telemetry 写入不得降低 generation/source_priority，也不得绕过 manual hold。NodeMirror 只在 Redis 写成功后失效或刷新。

## 7. 回放边界

`X-Gw-Replay: true` 只允许标记「安全捕获体」的响应回放。安全捕获体必须满足：

- 来自同 tenant/session/request 的已完成 pending 或 durable terminal result；
- body 未超 capture limit，未标记 overflow/incomplete；
- 内容是完整客户端协议体或规范化非流响应；
- 未尝试恢复原 TCP，也未重新执行供应商请求；
- 不包含需要重新触发的 tool call/外部副作用。

仅有缓存命中、PG 行存在或曾收到部分 vendor bytes，不足以设置 `X-Gw-Replay`。首语义帧后中断的残缺流不得以该 header 冒充完整重放。

## 9. 与其他主题的边界

| 相邻主题 | 分界 |
|---|---|
| 请求队列（主题④） | probe queue/dispatch 决定何时执行；节点资格决定能否被选 |
| 缓存映射（主题③） | candidate cache 是候选加速；URSM/PG/配置才提供资格事实 |
