## 1. P0 里程碑 M3：durable 持久恢复（修订0811 SR 轨，doc 24 §3）

> 目标：供应商耗尽时跨连接/跨重启持久接管。当前 Phase 1（连接内）已实现；Phase 2 durable 全未接线。

### M3-1 EncryptWithAAD（无依赖，先开工）
- **现状**：全仓零命中；仅 `secret/aes_gcm.go` 固定 AAD `llm-gateway:credential`，不支持自定义 AAD/不返回 key_id。
- **目标**：新增自定义 AAD 加密 + key_id 返回，复用 Keyring 多 kid 基建。
- **验收**：加解密 round-trip + 错误密钥解密失败 + 单测。

### M3-2 durable_llm_tasks migration + repo（依赖 M3-1）
- **目标**：`durable_llm_tasks` 表 + migration + repo（SR-08）。含任务租约/状态/attempt 维度。
- **验收**：migration `psql --dry-run` + repo 单测。

### M3-3 PG 回源读路径 + PendingStore CAS（依赖 M3-1+2）
- **现状**：survival coordinator 纯连接内内存态；pending 仅 Redis（TTL 1h 无 CAS）；`getPendingResponse` Redis miss 即 PENDING_NOT_FOUND。
- **目标**：PG 回源读路径 + PendingStore CAS（SR-10）。
- **验收**：Redis miss 时 PG 命中恢复；并发写 CAS 冲突处理。

### M3-4 CreateAndClaim / 双 reaper / fencing（依赖 M3-1+2+3）
- **目标**：CreateAndClaim 原子领取 + 双 reaper（超时回收 + 过期清理）+ fencing 防双写。

### M3-5 RecoveryWorker（依赖 M3-4）
- **目标**：断连/重启后从 durable 恢复任务继续执行。
- **验收**：S31 disconnect_durable / S32 gateway_restart 场景通过。

### M3-6 三协议装配（依赖 M3-1..5）

## 2. P0：8 主题待办落地（非 M3 依赖）

### P0-Z1 会话管理接线到 ursm/v2（老板 08-15 修正）
- **现状**：`main.go:609-630` URSM v2 Manager 已构造，`URSM_V2_MODE` 默认 off（`LoadFromEnv` 缺省 `api.ModeOff`；`main.go:1362` 明确"misconfigured install degrades gracefully to ModeOff"）；生产路径仍是 `ursm/v1` 旧循环。
- **目标**：会话管理（会话生命周期/状态/维度）接入 `ursm/v2` 架构；off → shadow → canary 渐进。
- **切换路径**：
  1. **off → shadow**：`URSM_V2_MODE=shadow`（配合 `URSM_V2_SHADOW_DOUBLE_WRITE=true` 同步写旧表用于一致性核对）；
  2. **shadow → canary**：`URSM_V2_MODE=canary` + `URSM_V2_CANARY_PERCENT` 灰度；
  3. **canary → authoritative**：一致性核对 N 天 diff=0 后切换。
- **验收**：URSM_V2_MODE=shadow 下会话状态经 v2 Manager（双写对比无 diff ≥ 7d）→ 切 canary 灰度 → 切 authoritative。

### P0-Z2 session_turns hot+分区表（老板 08-15 确认）
- **现状**：`public.session_turns` / `session_bodies` 为**纯月分区**（`session_turns_YYYY_MM`，`ensure_sessions_v2_partitions(date)` 派生，473 预创建至 2026-10）；**无 hot 表**。参照系 `request_logs` 已是 hot+分区表（`request_logs_hot` 写入口 + `promote_request_logs_hot_to_partition()` 提升）。
- **目标**：session_turns 引入 `session_turns_hot` 写入口（对齐 request_logs_hot）→ 定期 promote 到 `session_turns_YYYY_MM`；`bg.PartitionManager` 滚动预创建下月分区。
- **验收**：session_turns_hot 为唯一写入口；promote 后查询经月分区；下月分区自动预创建；无分区边界溢出。

### P0-Z3 会话三层数据映射完善（老板 08-15 修正）
- **现状**：①原始→②压缩→③脱敏链路已通（见 02/03 号），AlignmentMap 缺失。
- **目标**：补齐三层位置对齐（AlignmentMap），使跨轮次压缩会话可精确定位。
- **验收**：跨轮次压缩重建后消息位置全对齐。

### P0-Z4 session_turns 6 维补齐（审计发现 08-15）
- **现状**（核 schema 01-schema.sql）：`public.session_turns` 实列含 session_id/turn_no/tenant_id/request_id/attachments/model/provider/credential_id/tokens/cost 等，**缺 project_id/namespace 列**（"项目"维度）；**缺 parent_request_id 列**（"附属会话"维度，跨轮次压缩派生链）；**缺 task_type 列**（"任务"维度，目前在 sessions.task_type 间接持有，跨轮次需 JOIN）。
- **目标**：session_turns 增加 `project_id TEXT`、`parent_request_id TEXT`、`task_type TEXT` 列 + 索引，使 6 维存储完整可独立查询，不依赖 JOIN sessions。
- **步骤**：① migration 补 3 列 → ② DualWriter 影子写回填（从 Session.Namespace / request_logs.parent_request_id / sessions.task_type 灌入）→ ③ 读路径回退 V1 兼容期 → ④ 旧列查询停用。
- **验收**：session_turns 6 维全列；跨轮次查询无需 JOIN sessions；hot 表引入后写入正确（见 P0-Z2）。

### P0-E Goal retry 的 HTTP 202 异步协议（DEFER）
- 17 号的 `X-LLM-Gateway-Retry-Scheduled` 是未实施审计建议中的候选命名，不是已冻结契约。若未来实施，须先完成前端/OpenAI SDK 兼容性验证并重新冻结语义。
- 当前 pending/durable 的初始 accepted 响应保持 `202 Accepted` + `X-Gw-Pending` + `X-Gw-Pending-Request` + `Retry-After`（durable 另含 `Location`、`Preference-Applied`、`X-Gw-Task-Id`）；后续轮询的 `in_progress` 202 仅保证 `Retry-After` 和状态 envelope。不增加语义不等价的冗余 header。

### P0-F 旧存储双写逐步移除（V2-3 + 老板 08-15 修正）

- 步骤：① DualWriter 改 V2 单写 → ② 归档历史 V1 → ③ 删除旧 SessionCache → ④ 关闭 request_logs 双写。
- 前置：V2 稳定 ≥4 周 + 存储节省达标（目前双写期未达标）。
