- [ ] **只认当前事实，不按旧表派工**：先阅读 11 号“当前事实重核”，旧完成表不得作为当前发布结论。

- [ ] **范围隔离**：先确认本里程碑允许改动的文件集合；文档、代码、migration、环境操作分别留证。
- [ ] **P0-Z1 以 authoritative 为权威目标态**：当前 `URSM v2` 默认模式已是 `authoritative`，不是旧文档所述默认 `off`。`off/shadow/canary` 仅保留为诊断、比较和回滚模式。
- [ ] **authoritative 启动必须 fail-closed**：Redis、PostgreSQL、`LLM_GATEWAY_SYSTEM_MONITOR_ENABLED=true`、legacy bootstrap、coverage warmup/ready gate 任一不满足，不得启动监听或宣称切流成功。

- [ ] **区分依赖真实性**：当前 URSM Redis 证据主要来自 `miniredis` 或不可达地址 client swap；PG fault-injection 因 `localhost:55432` 不可用而 SKIP。模拟成功不得写成真实 Redis/PG 通过。
- [ ] 每完成一段执行 `go build ./... && go vet ./... && go test -race <相关包>`；全仓失败须逐项列出，不得用 targeted green 替代。

### 0.1 authoritative P0-Z1 不变量

1. `URSM_V2_MODE=authoritative` 时，路由状态读写以 URSM v2 为权威，legacy 不得静默接管并掩盖 ready/coverage 缺口。
2. 启动先关闭 ready gate，完成 PG→Redis bootstrap 与 coverage warmup 后才可打开；旧实例遗留 `meta:ready=1` 不能直接放行。
3. system monitor 必须能在依赖退化时关闭 gate、恢复后按证据重开；多实例场景需要 fencing/一致性验证。
4. `shadow` 的 outcome 双写证据与候选 diff 证据必须分开统计；`canary` 不能替代 authoritative 的全覆盖启动门禁。
5. 任何“authoritative 已实现”仅表示代码路径存在；在 G4 真实 Redis/PG/provider 故障注入通过前，不等于 release-ready。

## 3. M5 拆分与唯一执行顺序

**退出条件**：G0 全部勾选；没有未归属的基线漂移。

### M5-2 · Schema/ledger 收口（G1）

- 修复 startup migration `528` 重复占号，确认 up/down、embed/baseline、checksum/生产 ledger 一致。

### M5-3 · Goal↔Handoff 契约与安全收口（G2）

- 按 12 号验收 202→confirm→restore、expiry、tenant/API-key ownership、幂等重复确认、进程重启后 durable restore、旧 ResumePacket 兼容。

**退出条件**：12 号验收表中 G2 项全部通过；无 secret/token/raw snapshot 日志泄漏。

### M5-4 · authoritative P0-Z1 本地闭环（G3 前半）

- 验证默认 authoritative、依赖缺失 fail-closed、ready gate 初始关闭、bootstrap/coverage 后开启、system monitor 强依赖。
- 验证 off/shadow/canary 仅作为诊断/回滚，不会被误当 authoritative 成功。
- 补齐 outcome 双写、candidate diff、ready/coverage、fallback/rollback 的分离指标和运行手册。

**退出条件**：authoritative 本地集成场景全绿，且没有 legacy 静默兜底掩盖失败。

### M5-1 · 合并后本地回归（G3 后半）

- 在 M5-2/3/4 汇合后执行全仓 build/vet/test/race 与相关 integration tag。
- 对失败逐项分类：本次回归、既有失败、真实依赖缺失；任何未解释失败都阻断 G3。
- M4 结论只可升级为“合并后 LOCAL_VERIFIED”，仍不得标记 release-ready。

**退出条件**：G3 通过，或有明确、已批准的非发布豁免；不得隐藏 SKIP。

### M5-5 · 真实依赖与目标环境门禁（G4）

- 使用真实 Redis 验证 restart、NOSCRIPT、连接池重连、Pub/Sub subscriber 重连。
- 使用真实 PostgreSQL 验证 migration、handoff confirmation/restore、durable lease/fencing/takeover/reaper。
- 使用真实 provider/代理链验证断流、TLS/HTTP2、429/5xx、首语义帧前切换与首语义帧后禁止透明重放。
- 在授权目标环境执行 202→confirm→restore、URSM authoritative、durable outbox HMAC/consumer 幂等/ownership smoke。

**退出条件**：真实依赖无 SKIP；失败注入和恢复均有时间戳、版本、日志与指标证据。

### M5-6 · 发布裁决与回滚演练（G5）

- 汇总 G0..G4 证据，给出 GO / NO-GO；任何真实依赖 blocker 未关闭时只能 NO-GO。
- 演练 authoritative→canary/shadow、Handoff disable/fail-open、session_turns promote 停止与 migration 回滚。
- 发布后持续观察 ready、coverage、route diff、restore 状态、proposal expiry、hot row age、promote 与 durable/outbox 指标。

**退出条件**：G5 签字、回滚可执行、观察窗口和责任人明确。

## 6. 风险与回滚

| 风险 | 缓解 |
|---|---|
| authoritative 默认态被旧文档误写为 off | 以当前代码和 11 号重核为准，启动 fail-closed |
| migration 528 重复导致顺序/ledger 不确定 | M5-2/G1 先修复，未修复禁止新增 migration |

| 模拟 Redis 或 PG SKIP 被写成真实验证 | 证据分级，G4 禁止 mock/SKIP |
| M4 本地绿被误判可发布 | 状态固定为 LOCAL_VERIFIED，G4/G5 后才能 release-ready |
| GoalState/ResumePacket 泄密或膨胀 | 双上限、统一脱敏、日志禁止原文/token |
| V1 过早下线 | 4 周稳定期、回滚演练和存储指标门禁 |
