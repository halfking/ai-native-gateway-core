## 4. 专题三：性能与稳定性——电信级大流量（一天百万级请求）

### 4.1 负载模型与详细计算

**口径假设** [推断，逐条标注]：
- 一天 100 万请求 = 平均 **11.6 QPS**（86400s 均摊）。
- 电信/企业场景日流量集中：80% 落在 10 小时高峰段 → 高峰段平均 **22.2 QPS**；分钟级峰值系数取 3× → **峰值 ≈67 QPS**；设计余量取 2×峰值 → **设计容量 130 QPS**。
- 单请求画像 [假设值，需按 usage_facts 实测分布校准]：请求体 3KB + 流式响应 8KB（约 2K in / 1K out tokens），平均响应时长 15s（SSE）。

| 维度 | 计算 | 1M/天 | 5M/天 | 10M/天 |
|---|---|---|---|---|
| 平均 QPS | 总量/86400 | 11.6 | 58 | 116 |
| 峰值 QPS | ×(80%/10h)×3 | 67 | 333 | 667 |
| 设计容量 | ×2 | **130** | **667** | **1333** |
| 并发 SSE 连接 | 峰值QPS×15s | ~1000 | ~5000 | ~10000 |
| 代理面带宽 | 峰值QPS×11KB | 0.74 MB/s | 3.7 MB/s | 7.3 MB/s |
| usage_facts 写入 | 平均/峰值 rows·s⁻¹ | 12 / 120 | 58 / 583 | 116 / 1166 |
| usage_facts 热存储 | ~2KB/行 | 2 GB/天 | 10 GB/天 | 20 GB/天 |
| 全部日志族热存储 | facts+wal+routing+credit ≈2× | ~4 GB/天 | ~20 GB/天 | ~40 GB/天 |
| 列存归档后 | columnar ≈8-10× | ~0.4-0.5 GB/天 | ~2-2.5 GB/天 | ~4-5 GB/天 |

**判断** [推断]：
1. 数据面吞吐对本仓无结构性压力：usage_facts 写入为 inbox 异步批量消费，PG 单机简单插入能力在数千行/s 量级，1M/天峰值 120 行/s 余量 >25×；**10M/天峰值 ~1170 行/s 时 PG 单实例开始需要专机与调优**（checkpoint/WAL 放大 ~3×）。
2. 存储：1M/天月热数据 ~120GB，211 单机盘可承受；10M/天必须依赖已有"热分区 + columnar 归档"两层自动滚动（053/305/318/343 迁移族），并预建月分区。
3. SSE 并发连接：1000 并发流式连接对 Go goroutine 模型无压力（`net.Pipe`/gorilla 实测基线在 10⁴ 量级），注意 nginx 反代 `proxy_buffering off` 与连接数上限配置核对。

### 4.2 已具备的稳定性机制 [事实]
- 蓝绿部署零停机 + 验收后切流 + 回退（`deploy-seamless-docker.sh`）；熔断统计面 W1-G4 已落地（`bg/system_health.go`、`/api/health/system` circuit_breaker 字段）；上游故障回退梯子 + retry budget；限流三级；usage 真源与账本分区化。

## 8. 专题七：内置智能体的半自动化错误分析与自动纠正（插件化）

### 8.1 定位与现状 [事实]
- `plugin-runtime/` 框架完整：进程外插件（Supervisor/controller/discovery/manifest/handshake/capability/entitlement/eventbus/health/boundary 测试）+ 进程内适配器双通道；生产路由已接 `/api/v1/plugins`（install/activate/deactivate/uninstall/plugin-nav SSE/plugin-config），`cmd/gateway/main.go:7168-7427`。
- **实际插件稀缺**：仅 `plugins/hello/`（演示）与 `plugins/all/`（blank-import 汇聚点）。
- 安全侧已有"插件形态"先例：`domains/security/plugins/`（prompt injection 检测）。
- 集群侧另有 ACC（编排器/DAG/SAG2/预算门）可承接"分析型任务"。

### 8.2 方案：错误处理模板插件（ErrorRemediation Plugin）
**执行方案统一为四步管线，模板化、插件化、可热升级** [推断]：

```
事件(eventbus) → 分类(classify) → 建议(suggest) → 处置(apply: gated)
```

1. **插件能力契约**（capability 扩展）：注册 `error-remediation` 能力，声明订阅事件（upstream_5xx / rate_limit / sse_break / config_drift / budget_exhausted）与可执行动作（suggest / auto-apply）。
2. **错误处理模板** = 数据化 YAML（特征匹配 + 处置动作 + 升级路径），插件装载模板而非硬编码逻辑 ⇒ **模板可不停网关升级**（manifest 版本化 + activate 原子切换）。
3. **半自动化边界**：默认 `suggest`（分析结论+建议补丁进管理面待办，人工确认）；`auto-apply` 仅限白名单动作（如"摘除不健康供应商池"）且必须有回滚——**代码改写类动作一律建议态**，不做无人值守写仓。
4. **首批 3 个模板插件**：
   - `upstream-cooldown`：上游 429/502 聚簇 → 生成"降级路由建议"（复用 modelbudget 梯子语义）；
   - `sse-break-analysis`：SSE 断流聚类 → 归因（上游/反代/网络）→ 输出处置建议；
   - `config-drift`：配置校验和漂移（复用 checksum 门禁语义）→ 提示修复动作。
5. **与 ACC 打通** [推断]：复杂归因任务（跨日志/跨服务）经 ACC 编排为 DAG 任务，插件只做轻量分类，避免网关进程内跑重分析。

### 8.3 验收
- 插件热装载/升级不中断网关流量（boundary 测试扩展）；
- 每条错误分析在管理面留痕（分类/建议/采纳/回滚四态）；
- 3 个模板各有钉测（变异注入对应故障 → 插件产出正确建议）。
