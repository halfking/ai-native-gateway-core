## 6. 本轮结论

1. **窗口内 36 笔提交中，业务逻辑只有 2 簇**（运营计费 P0/P1、记忆预热注入）。
   两簇的**架构形状都是对的**（异步/旁路/超时即弃/fail-open/RLS/两臂并读/有界注入），
   **缺陷集中在「契约与实现的对齐」和「流程闭环的最后一公里」**。

2. **最重的一条（F-1）** 是一类**放大面随业务量线性增长**的缺陷：
   预热被做成了每请求触发，而 ADR 钉的是每会话一次 ⇒ 会话越长、放大越狠。
   本轮已按 ADR 收口（每会话一次 + TTL 有界去重表 + 恰好一个赢家）。

3. **最值得警惕的一条（F-3）** 不是「没写」，而是**同一个陷阱在同一笔提交里只修了一侧**：
   consume 侧 AF-3 明确写了「读父表 ⇒ hot 行系统性漏计」，
   而同一笔提交的 campaign 红线仍然写着 `SUM(credit_ledger.amount)`。
   ⇒ **修复历史不会自动传播到同批新增的代码** ⇒ 这正是「机器护栏」要解决的事：
   **护栏要能挡住「同一陷阱的第二次出现」，而不只是挡住「同一个对象的第二次出现」**。

4. **本轮的两处落地选择**（F-8/F-4 父仓、§4.3 的独占窗口前置）都源于
   **并发会话在本仓跑慢门**这一客观约束 ⇒ 已在 §4.3 写清下一轮的开工前置条件。

5. **★ 推送动作本身带出两条与「代码去哪儿」有关的发现**（§3.2 / §3.3）：
   **F-13** github 镜像是**公开仓**，内网 IP 与本机路径对全网可见——但**归属已钉死：不是本轮引入**，
   本轮增量只有 2 处 IP 提及 + 2 处路径（**无凭据**）⇒ 处置是**镜像可见性**的仓外决策，不代裁；
   **F-14**（★ **已订正**）本仓的秘密扫描器**对「指向本机/示例主机的凭据」整行全盲**——机制**不是**规则缺失（`DB_CONNSTRING` 规则有效），**而是**归因循环里「命中白名单词 ⇒ 整行 `continue`」⇒ `cmd/calc_quality/main.go:16` 因含 `localhost` **永远抓不到**，而它若改成内网地址就立刻会被抓到 ⇒ **「白名单太宽」比「扫描器盲」更值得修**；★ 本条原判断（机制＝规则缺失）**已被并行会话的独立探针推翻**，已按探针订正修法（原「加一条规则」**不必要**）⇒ 严重度 **P2→P1**
