## 二、关键问题分析

### 🔴 问题 1：大量"重写"而非"复用"

#### 案例 1：circuit/breaker.go（熔断器）

**旧代码**（circuit/breaker.go）: **475 行**
- 4 种状态（Closed / Open / HalfOpen / **Quarantined**）
- 指数退避冷却策略
- 按错误类型分类（Auth/Quota → 隔离，Network → 短冷却）
- 半开探测机制
- 完整的测试覆盖

**新代码**（domains/credential/breaker.go）: **98 行**
- 3 种状态（缺少 Quarantined）
- 简单的固定超时
- 无错误分类
- 功能简化了 80%

**复用率**: 11.0%（98/888）

**问题**: 为什么要重写一个已经完整、测试充分、生产验证的熔断器？

---

#### 案例 2：limiter/limiter.go（并发限制）

**旧代码**（limiter/limiter.go）: **444 行**
- Redis + 本地双层限流
- 身份识别集成（redis_identity.go）
- 动态调整并发槽位
- 完整的并发测试

**新代码**（domains/credential/limiter.go）: **63 行**
- 仅接口定义
- 无实现

**复用率**: 4.9%（63/1289）

**问题**: 旧代码有 444 行成熟实现，为什么只迁移了接口？

---

#### 案例 3：compressor/（上下文压缩）

**旧代码**（compressor/）: **8,410 行**（34 个文件）
- 6 种压缩模式（Off / AutoThreshold / On4xx / DeltaOnly / Smart / Aggressive）
- 三层压缩策略（机械去重 → Memora L1 → LLM 总结）
- 与 routing/context_summarize.go 深度集成（1,368 行）
- Rebuilder 支持（OpenAI / Anthropic）
- 完整的 telemetry 集成

**新代码**（domains/hooks/compression/）: **604 行**（4 个文件）
- 仅 3 种策略（None / LCS / LLMSumm）
- LCS 是"简化示例实现"（滑动窗口截断）
- 无 Rebuilder 集成
- 功能简化了 93%

**复用率**: 7.2%（604/8410）

**问题**: 旧代码有 6 种成熟模式，新代码为什么要从头写一个简化版？

---

#### 案例 4：relay/（流式转发）

**旧代码**（relay/）: **23,162 行**（94 个文件）
- 核心处理器（handler.go 3,116 行 + responses_stream.go 341 行）

**新代码**（domains/streaming/）: **402 行**（4 个文件）

**复用率**: 1.7%（402/23162）

**问题**: 这是整个项目最大的代码包，为什么 98.3% 的代码都被抛弃了？

### 3.2 为什么复用率这么低？

#### 原因分析

1. **架构理念优先于代码复用**
   - 优先实现"领域纯净性"
   - 为了适配 Hook Pipeline，重写了大量代码
   - 忽略了"成熟代码"的价值

2. **"简化示例"误区**
   - domains/hooks/compression/ 注释："本包定义最小契约"、"LCSCompressor 是一个简化示例实现"
   - domains/streaming/ 注释："简化实现"
   - 结果：丢失了旧代码 90%+ 的功能

3. **"接口优先"陷阱**
   - domains/credential/limiter.go：仅 63 行接口定义
   - domains/streaming/types.go：仅接口定义
   - 结果：没有实际可用的实现

4. **未按计划执行**
   - 计划说"直接移动 70%"，实际只复用了 20%
   - 计划说"credentialstate + circuit + limiter 合并"，实际重写了简化版

## 六、关键建议

### 6.1 立即纠正的错误

1. **停止"简化示例"思路**
   - ❌ 不要再写"最小契约"、"简化实现"
   - ✅ 完整迁移成熟代码，保留所有功能

2. **停止"接口优先"陷阱**
   - ❌ 不要只定义接口就算完成
   - ✅ 必须有完整可用的实现

3. **停止"重写"浪费**
   - ❌ circuit/breaker.go 从 475 行简化到 98 行
   - ❌ compressor/ 从 8,410 行简化到 604 行
   - ❌ limiter/ 从 1,289 行简化到 63 行
   - ✅ 完整迁移，一行都不要少

### 6.2 架构调整建议

1. **务实的领域设计**
   - 允许领域内包含"非纯净"的依赖（如 compressor 依赖 Memora）
   - 优先保留功能，再渐进重构

2. **增量适配 Pipeline**
   - 不要为了适配 Pipeline 而重写代码
   - 先迁移完整功能，再包装成 Hook

3. **保留旧代码作为对比**
   - 新旧代码并存期间，用特性开关切换
   - 保留旧代码至少 3 个月，确保新代码功能对等

### 6.3 Phase 2 启动条件（修正）

⚠️ **在达到以下标准前，不要开始 Phase 2**：

- [ ] domains/ 总行数 ≥ 46,000 行（不是当前的 13,279 行）
- [ ] 整体复用率 ≥ 70%（不是当前的 20.1%）
- [ ] 所有核心功能有完整实现（不是接口 + 简化示例）
- [ ] E2E 测试通过，功能与旧版完全一致
- [ ] Pipeline 已上线，新架构真正生效
