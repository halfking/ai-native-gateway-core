## 二、P0 — 跨层决策不一致（同一次守卫决策被第二层静默推翻）

### P0-1 `thinking` 对象被重新注入出站体，r1021 的 400 原样复发

**位置**：`domains/transformation/ir_converter.go:538`（根因），对照 `internal/ir/extensions_restore.go:174` `resolveTargetDialect`

**意图**：`f0c07823e` 让 `thinking{...}` 按方言翻译为 `reasoning{effort}`；`31d466e21` 加 `CatalogCodeUnknownRelay` 哨兵，让空 catalog 的中转落到 `DialectUnknown` 走 fail-open。

**实情**：同一份 `req.Extensions` 被**两遍**还原，只有第一遍认哨兵。

```
pass1  internal/ir        TargetProvider 非空且未登记 ⇒ DialectUnknown ⇒ fail-open，正确裁掉
pass2  transformation     paramreg.Resolve(…) ⇒ 回退协议 ⇒ DialectOpenAIChat ⇒ 把 thinking 写回
```

而紧随其后的 `ctx.UpstreamCatalogCode` 补偿分支条件是 `dstDialect == DialectUnknown`——**Resolve 已经把它塌成具体方言，该分支永远进不去**，等于没有兜底。

**实测复现**（overlay，仓内零改动）：

```
PASS1 (internal/ir)      = {..., "reasoning_effort":"high"}
PASS1+2 (transport path) = {..., "reasoning_effort":"high","thinking":{"type":"enabled","budget_tokens":4096}}
```

**触发条件**：客户端经 openai-chat 入向发顶层 `thinking` 对象 + 选中候选的 `catalog_code` 为空或未登记（联界/智码/maishouai/suyun/apigpt/apinext） + 目标协议为 `openai-chat`。Vapeur 的 catalog 即为空 ⇒ **正是 r1021 修的那个组合在复发**。

**为什么 E2E 没抓到**：新增的判据测试直接调 `ir.SerializeOpenAI`，从不进 `TransportIRConverter`；而覆盖该层的集成测试需要真库。

**已修**：pass2 改为与 pass1 逐字同形（非空 `TargetProvider` 一律不回退协议），并把 `UpstreamCatalogCode` 兜底收进 `TargetProvider == ""` 分支内。

### P0-2 `enable_thinking` 裁剪被撤销，且**丢参台账记录了一个没发生过的裁剪**

同一根因。pass1 正确裁掉并上报 `ir_protocol_loss`（`reason=dialect_scoped_field`），pass2 又加了回来。


## 三、P1 — 提交声明的线上复验不成立

### P1-1 费用对账的「聚合超时」修复完全无效，`SET statement_timeout = $1` 恒失败

**位置**：`domains/providerprofile/pg_reconciliation_store.go:248`

PostgreSQL 的 `SET` 是 **utility 语句，不接受绑定参数**。pgx 在带参数时走扩展协议，服务端直接回 `42601`。

**实测**（pgx v5.9.2 = `go.mod` 锁定版本；并用 psql `\bind` 扩展协议对拍复现）：

```
A) SET + 绑定参数       -> ERROR: syntax error at or near "$1" (SQLSTATE 42601)
B) SELECT set_config(…) -> v="9min"  err=<nil>
C) SET + 字面量         -> err=<nil>
```

**影响**：worker 每轮在第一条查询之前就返回错误，网关用量永不写入，费用对账页恒空。它替换掉的那个 57014 超时**反而更难排查**。

**「线上复验」的证伪**（提交 `394f21982`）：提交信息声称在 `build 2574 / 0537eadbf` 上看到 `provider cost reconciliation completed`。但 `0537eadbf` 的时间戳是 `08:52:52`，**比 `394f21982`（09:30:31）早 38 分钟**——那个二进制里不可能含有这段代码。

**本地/CI 为何是绿的**：覆盖测试 `pg_reconciliation_store_test.go:147` 确实调用该函数，但 `pg_store_test.go:19` 在没有 `TEST_DATABASE_URL` 时整包 skip ⇒ 这一行**从未被任何自动化跑过**。

**已修**：改用 `SELECT set_config('statement_timeout', $1, false)`，与本仓既有正解（`session_request_status_backfill.go:442`）同形；并给 `RESET` 加 5s 上限（原写法 `context.WithoutCancel(ctx)` 无超时，连接卡死会拖住 `conn.Release()` 归还池——修好 P1-1 后该路径才真正可达）。

### P1-2 探针队列空闲退避在生产是死代码

**位置**：`bg/probe_queue_worker.go:159` + `cmd/gateway/main.go:4475`

`IdlePollCap` 的字段注释承诺「≤0 时取默认值 `ProbeQueueIdlePollCapDefault`」——**代码里根本没有这句**。实现是 `if maxIdle < base { maxIdle = base }`，而**唯一的生产装配点从未给 `IdlePollCap` 赋值**：

```
maxIdle = 0 → 被抬成 base(250ms) → 封顶恒等于 base → 退避幅度恒为 0
```

`ProbeQueueIdlePollCapDefault`(30s) 是全仓未被引用的常量。提交 `9f4186917` 声称的「省下全库 5.3% 数据库时间」**不会发生**。

> **这条是「注释说有、代码没做」的典型**：缺陷能通过评审、也能通过 review，恰恰因为字段文档已经把承诺写清楚了。**注释与代码不一致本身就是缺陷**，本轮已把该承诺补进代码。

**已修**：`maxIdle <= 0` 时先取 `ProbeQueueIdlePollCapDefault`。

### P1-5 会话族迁移的「仅 0 行才回退」判据：跨镜像切换点的会话被静默截断

**触发**：镜像链启用**之前**就有轮次、**之后**也有轮次的会话（任何跨切换点的长会话）。family 腿返回 >0 ⇒ 回退不触发 ⇒ 只输出 family 侧最新 N 条，**早于切换点的 v1 轮次被整体丢弃**，不报错也无信号。
