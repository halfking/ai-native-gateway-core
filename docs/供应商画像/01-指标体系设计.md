# LLM 供应商质量画像指标体系设计

## 1. 概述

供应商质量画像旨在为每个 LLM 供应商建立多维度的质量评估体系，用于：
- **智能路由决策**：根据质量画像选择最优供应商
- **故障预警**：识别质量下降趋势，提前切换
- **成本优化**：在质量相当时选择成本更低的供应商
- **SLA 监控**：追踪供应商是否满足承诺的服务水平

## 2. 指标体系架构

### 2.1 四层指标模型

```
L1: 核心可用性指标（Core Availability）
    ├─ 成功率 (Success Rate)
    ├─ 错误率 (Error Rate)
    └─ 可用性 (Availability)

L2: 性能指标（Performance）
    ├─ 响应时间 (Latency)
    ├─ TTFT (Time To First Token)
    └─ 吞吐量 (Throughput)

L3: 稳定性指标（Stability）
    ├─ 错误分布 (Error Distribution)
    ├─ 波动性 (Volatility)
    └─ 恢复时间 (MTTR)

L4: 成本效益指标（Cost Efficiency）
    ├─ 单价 (Unit Cost)
    ├─ 性价比 (Cost per Quality)
    └─ 配额利用率 (Quota Utilization)
```

### 2.2 时间维度

每个指标在多个时间窗口计算：
- **实时** (5分钟)
- **短期** (1小时)
- **中期** (24小时)
- **长期** (7天, 30天)

### 2.3 请求维度分层

按以下维度分层统计：
- **模型** (model_name)
- **端点** (endpoint)
- **用户/租户** (user_id/tenant_id)
- **全局** (provider-level)

## 3. 详细指标定义

### 3.1 L1: 核心可用性指标

#### 3.1.1 成功率 (Success Rate)
```
success_rate = successful_requests / total_requests * 100%
```
- **目标**: ≥ 99.5%
- **计算周期**: 5分钟滚动窗口
- **数据源**: `request_logs.status_code`

#### 3.1.2 错误率 (Error Rate)
```
error_rate_5xx = 5xx_errors / total_requests * 100%
error_rate_4xx = 4xx_errors / total_requests * 100%
error_rate_timeout = timeout_errors / total_requests * 100%
```
- **阈值**:
  - 5xx错误率 < 0.5%
  - 4xx错误率 < 2%
  - 超时率 < 1%

#### 3.1.3 可用性 (Availability)
```
availability = uptime / (uptime + downtime) * 100%
```
- **定义**: 连续5分钟成功率 < 90% 视为 downtime
- **目标**: 99.9% (三个9)

### 3.2 L2: 性能指标

#### 3.2.1 响应时间 (Latency)
```sql
-- P50, P90, P95, P99
SELECT
  percentile_cont(0.5) WITHIN GROUP (ORDER BY latency_ms) as p50,
  percentile_cont(0.9) WITHIN GROUP (ORDER BY latency_ms) as p90,
  percentile_cont(0.95) WITHIN GROUP (ORDER BY latency_ms) as p95,
  percentile_cont(0.99) WITHIN GROUP (ORDER BY latency_ms) as p99
FROM request_logs
WHERE provider_id = ? AND timestamp > now() - interval '1 hour'
```
- **目标**:
  - P50 < 2000ms
  - P95 < 5000ms
  - P99 < 10000ms

#### 3.2.2 TTFT (Time To First Token)
```
ttft = first_token_timestamp - request_start_timestamp
```
- **目标**: P95 < 1000ms
- **数据源**: 需要在流式响应中记录 first token 时间

#### 3.2.3 吞吐量 (Throughput)
```
throughput = total_tokens / total_time_seconds
```
- **单位**: tokens/second
- **计算**: 按模型分别统计输入和输出吞吐量

### 3.3 L3: 稳定性指标

#### 3.3.1 错误分布 (Error Distribution)
```sql
SELECT
  error_code,
  error_type,
  COUNT(*) as count,
  COUNT(*) * 100.0 / SUM(COUNT(*)) OVER() as percentage
FROM candidate_failure_logs
WHERE provider_id = ? AND timestamp > now() - interval '24 hours'
GROUP BY error_code, error_type
ORDER BY count DESC
```
- **关注点**:
  - 是否有特定错误占主导
  - 错误模式是否稳定

#### 3.3.2 波动性 (Volatility)
```
volatility = stddev(success_rate_per_5min) / mean(success_rate_per_5min)
```
- **定义**: 成功率的变异系数
- **目标**: < 0.05 (稳定)

#### 3.3.3 恢复时间 (MTTR - Mean Time To Recovery)
```
mttr = avg(recovery_timestamp - failure_timestamp)
```
- **定义**: 从故障到恢复的平均时间
- **目标**: < 5分钟

### 3.4 L4: 成本效益指标

#### 3.4.1 单价 (Unit Cost)
```
cost_per_1k_tokens = (input_tokens * input_price + output_tokens * output_price) / 1000
```
- **数据源**: `provider_models.input_price`, `output_price`

#### 3.4.2 性价比 (Cost per Quality)
```
cost_efficiency = cost_per_1k_tokens / success_rate
```
- **越低越好**: 相同成本下成功率越高

#### 3.4.3 配额利用率 (Quota Utilization)
```
quota_usage = used_quota / total_quota * 100%
```
- **预警**: > 80% 时触发预警

## 4. 综合评分模型

### 4.1 加权评分公式

```
quality_score = w1 * availability_score
              + w2 * performance_score
              + w3 * stability_score
              + w4 * cost_efficiency_score
```

**权重配置**:
```json
{
  "weights": {
    "availability": 0.4,    // 可用性最重要
    "performance": 0.3,     // 性能次之
    "stability": 0.2,       // 稳定性
    "cost_efficiency": 0.1  // 成本最后考虑
  }
}
```

### 4.2 子分数计算

#### 4.2.1 可用性分数 (0-100)
```
availability_score = (
  success_rate * 0.6 +
  (100 - error_rate_5xx * 20) * 0.3 +
  availability * 0.1
)
```

#### 4.2.2 性能分数 (0-100)
```
performance_score = (
  100 * (1 - p95_latency / 10000) * 0.5 +
  100 * (1 - p99_latency / 20000) * 0.3 +
  min(100, throughput / 10) * 0.2
)
```

#### 4.2.3 稳定性分数 (0-100)
```
stability_score = (
  100 * (1 - volatility) * 0.5 +
  100 * max(0, 1 - mttr / 600) * 0.3 +
  error_diversity_score * 0.2
)
```

#### 4.2.4 成本效益分数 (0-100)
```
cost_efficiency_score = 100 * (min_cost_in_pool / current_cost) * (success_rate / max_success_rate_in_pool)
```

### 4.3 等级划分

| 综合评分 | 等级 | 描述 | 推荐策略 |
|---------|------|------|---------|
| 90-100 | S | 优秀 | 优先使用 |
| 80-89  | A | 良好 | 常规使用 |
| 70-79  | B | 一般 | 谨慎使用 |
| 60-69  | C | 较差 | 降低权重 |
| < 60   | D | 极差 | 停用或备用 |

## 5. 数据采集规范

### 5.1 必需字段

在 `request_logs` 表中确保记录：
```sql
- provider_id, model_name, endpoint
- status_code, error_code, error_message
- latency_ms, ttft_ms (新增)
- input_tokens, output_tokens
- timestamp, request_id
```

在 `candidate_failure_logs` 表中确保记录：
```sql
- provider_id, model_name, endpoint
- error_type, error_code, error_detail
- context JSONB (包含 user_id, tenant_id, 请求特征)
- timestamp, request_id
```

### 5.2 采样策略

为减少存储开销，采用分层采样：
- **成功请求**: 10% 采样
- **4xx 错误**: 50% 采样
- **5xx 错误**: 100% 记录
- **超时错误**: 100% 记录

### 5.3 数据保留期

- **原始日志**: 7天
- **分钟级聚合**: 30天
- **小时级聚合**: 90天
- **天级聚合**: 365天

## 6. 指标计算架构

### 6.1 实时计算层

使用 Redis Streams + 滑动窗口：
```
redis_key_pattern: "provider:{provider_id}:metrics:{window}"
window ∈ {5m, 1h, 24h}
```

数据结构：
```json
{
  "window_start": "2026-07-19T10:00:00Z",
  "total_requests": 1500,
  "successful_requests": 1485,
  "error_5xx": 10,
  "error_4xx": 5,
  "latency_p50": 1200,
  "latency_p95": 3500,
  "latency_p99": 5800
}
```

### 6.2 批量计算层

使用 PostgreSQL + TimescaleDB：
- **每分钟**: 从 `request_logs` 聚合到 `provider_metrics_minute`
- **每小时**: 从 `provider_metrics_minute` 聚合到 `provider_metrics_hour`
- **每天**: 从 `provider_metrics_hour` 聚合到 `provider_metrics_day`

### 6.3 画像生成层

定时任务（每5分钟）：
1. 读取各时间窗口指标
2. 计算综合评分
3. 更新 `provider_quality_profiles` 表
4. 触发告警（如果评分下降超过阈值）

## 7. 告警规则

### 7.1 严重告警 (P0)

| 指标 | 阈值 | 持续时间 | 动作 |
|-----|------|---------|------|
| 5xx错误率 | > 5% | 5分钟 | 立即切换备用供应商 |
| 可用性 | < 95% | 5分钟 | 立即切换备用供应商 |
| P99延迟 | > 30s | 10分钟 | 降低权重50% |

### 7.2 警告告警 (P1)

| 指标 | 阈值 | 持续时间 | 动作 |
|-----|------|---------|------|
| 5xx错误率 | > 1% | 10分钟 | 降低权重20% |
| 成功率 | < 98% | 10分钟 | 记录并监控 |
| P95延迟 | > 10s | 15分钟 | 降低权重10% |

### 7.3 通知渠道

- **飞书群**: 实时告警
- **Dashboard**: 实时展示
- **邮件**: 日报/周报

## 9. 与现有系统集成

### 9.1 与智能路由集成

```go
// 路由决策时查询质量画像
profile := qualityService.GetProviderProfile(providerID)
if profile.QualityScore < 70 {
    weight *= 0.5  // 降权
}
if profile.AvailabilityScore < 80 {
    continue  // 跳过此供应商
}
```

### 9.2 与熔断器集成

```go
// 熔断决策参考质量画像
if profile.ErrorRate5xx > 0.05 || profile.AvailabilityScore < 90 {
    circuitBreaker.Open(providerID)
}
```

### 9.3 与配额管理集成

```go
// 根据质量动态调整配额
if profile.QualityScore > 90 {
    quota.Increase(providerID, 1.2)  // 增加20%配额
}
```
