> 契约本身见 [`会话分析元数据契约v1.md`](./会话分析元数据契约v1.md)。本文聚焦**落地层**：模块、调用方、测试、迁移指引。

## 1. 落地模块

- 代码位置：`domains/analysis/sessionmeta/`

## 3. 相对契约 v1 的实现差异

| 契约 v1 条款 | 实现层行为 |
| --- | --- |
| "An older input watermark must not replace a newer result." | 当前 `Extract` 每次返回新 `Result`，**不持久化**；持久层由调用方负责。等 final stage 接线时再校验 |
| "Use strict structured output, candidate project references, no tools" | 当前纯规则实现，不需要 LLM；final stage 接入前需补强 schema 校验 |
| "Sensitive-looking strings not being persisted as evidence" | `evidence[].value` 经过 `bounded()` 截断到 160 字符 + `cleanText` 规范化，**不持久化原始 payload** |
| "Chinese and English text, UTF-8-safe title truncation" | `truncateRunes` 按 rune 计数；`MaxTitleRunes = 80` |

- 本次升级**未修改** `/api/admin/dashboard/*` 任何 endpoint 的语义，仅在 arrival 路径上新增 provisional title 投影（streaming handler）。

## 5. 已落地的边界用例（与 `extractor_boundary_test.go` 一一对应）

1. 空输入 + 空 RequestBody → 全部字段为 `unknown`/`""`，JSON 仍可序列化。
2. 非法 JSON / 非对象 content / 空字符串 content → `ParseMessages` 返回 `nil`，不 panic。
3. 50 条消息 → 截断到 `MaxMessages=20`。
4. 只有 image_url content block → 该消息被丢弃。
5. 多 work_type 命中 → 按规则声明顺序截断到 `MaxWorkTypes=3`（**不是按文本出现顺序**）。
6. `RepoPaths` + system 提示路径 → evidence 去重并保留两者。
7. Header agent 为通用客户端（`curl` 等）时回退到 system 提示检测。
8. 无 user 消息 → `title=""`，且**不会**追加 `title_source` feature。
9. 相同输入两次 `input_hash` 一致；不同输入 `input_hash` 不同。
10. `ProjectRef` authoritative 覆盖系统提示里的路径提示。
11. user 消息里塞 prompt injection 不能篡改 agent / project / work_type。

## 7. Result 持久化设计（provisional → final）

当前 arrival 路径仅将 `Result.Title` 投影到 `session_title_states` / `sessions.title`（via titlestore）。完整 `sessionmeta.Result` 尚未落库。建议 v1.1 按以下契约扩展：

| 字段 | 存储位置 | 写入时机 | 优先级 |
| --- | --- | --- | --- |
| `title` | `session_title_states`（已有） | arrival provisional | auto-title priority 10 |
| `analysis_metadata` JSONB | 新表 `session_analysis_metadata` | arrival + final worker | provisional 可被 final 覆盖（按 `input_hash` / `updated_at`） |
| `agent` / `client` / `work_types` / `project` | `session_analysis_metadata.features` | 同上 | final 优先 |
| `evidence[]` | 同上（截断后） | final only | 不存原始 payload |

**表草案**（252 PG，与 154 共享）：

```sql
CREATE TABLE IF NOT EXISTS public.session_analysis_metadata (
  tenant_id           text NOT NULL,
  scoped_session_id   text NOT NULL,
  schema_version      text NOT NULL DEFAULT 'session-analysis/v1',
  status              text NOT NULL CHECK (status IN ('provisional','final')),
  input_hash          text NOT NULL,
  payload             jsonb NOT NULL,
  source_task_id      text,
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, scoped_session_id, status)
);
```

**写入规则**：

1. arrival：`MaybeGenerateProvisionalMetadata` 在 title 投影之外，异步 UPSERT `status=provisional`（仅当该行不存在或 `input_hash` 更新）。
2. final：LLM worker 完成后 UPSERT `status=final`；若 provisional 更新，比较 `input_hash` 水印，旧输入不得覆盖新结果（契约 v1 §Versioning）。
3. `RepoPaths`：arrival 时从 handler 传入 `sessionmeta.Input.RepoPaths`（当前 handler 未传，待接线）。
4. Dashboard 读取：session-overview 可 LEFT JOIN 该表，不影响现有 title 列。

**测试门禁**：pgxmock UPSERT + 154 集成脚本（首轮 provisional 行存在、多轮 input_hash 单调、final 覆盖 provisional）。
