# 03 · 会话三层映射、缓存与请求队列（主题③④）

> 状态标签：CURRENT = 已实现接线；CURRENT-PARTIAL = 部分接线；LOCALLY-VERIFIED = 已通过本地代码/测试核实；DEPLOYMENT-PENDING = 尚待真实环境验证；纸面 = 设计态。
> 代码事实以当前仓库为准。本文中的「会话三层」「candidate cache」「普通 pending」「durable projection」是四类不同对象，不得统称为缓存。

---

## 1. 会话三层数据映射（主题③）

### 1.1 三层语义

| 层 | 数据 | 权威来源/存储 | 生成 | 消费 |
|---|---|---|---|---|
| ① 原始会话 | 未压缩的多轮消息与轮次增量 | `public.session_bodies`、`session_turns` 体系 | DualWriter / SubmitModeDetector | 重建、审计、重新压缩 |
| ② 压缩会话 | 可跨轮次合并的压缩结果，含 `[smm_v1:` marker | 原始增量 + 压缩 marker；AlignmentMap 记录位置关系 | `SessionCompressor.Prepare` | 脱敏输入、上游上下文 |
| ③ 脱敏发送会话 | 经安全脱敏、prompt 注入检查后允许发送的会话 | 会话维度的发送映射；持久化链路仍为设计态 | `SessionSanitizeManager`（尚未实现） | 上游 LLM |

三层是同一会话的语义变换，不是 L1/L2/L3 介质缓存。映射必须携带 `tenant_id + session_id + turn_no/request_id`，禁止只用 `session_id` 跨租户定位。

### 1.2 重建与降级

当前主路径为：`tryLoadV2State → Builder.BuildLatestOutbound → BuildFromDeltas(10轮, preserve=true)`，完成原始增量到压缩发送上下文的重建。

AlignmentMap 已实现原始→压缩的位置对齐。压缩→脱敏的独立管理器尚未接线；失败时可逐级回退 V1，但不得把缺失的脱敏映射解释为「已安全处理」。

### 1.3 会话访问加速层

| 介质 | Key/对象 | TTL | 职责 |
|---|---|---:|---|
| 进程 LRU | `CompressionMeta`，最多 1024 会话 | 进程生命周期 | 压缩元数据热点访问 |
| Redis Hash | `session:v2:{tenant}:{session}` / `session:sc:*:v1` | 30min | GovernanceMeta、计划中的脱敏映射；失败时 fail-open 回源 |
| PostgreSQL | `session_turns` / `session_bodies` | 按表保留策略 | 冷启动、Redis miss/不可用时重建 |

Redis 是访问加速与短期映射介质，不是三层会话事实的唯一来源。Redis fail-open 必须留下失败率、回源量和重建结果指标。

## 2. 四类易混对象及 TTL

### 2.1 对象边界

| 对象 | 语义 | 是否队列 | 权威来源 |
|---|---|---|---|
| 会话三层 | 原始→压缩→脱敏的数据映射 | 否 | 会话持久数据与变换结果 |
| candidate cache | 路由候选查询结果的短期加速 | 否 | DB/路由状态；缓存可失效重算 |
| 普通 pending | 原连接无法继续交付时，短期保存已捕获响应供轮询 | 否，不承担跨重启执行 | Redis pending entry |
| durable projection | durable 任务终态/结果在 Redis 的可查询投影 | 否；执行队列在 PostgreSQL | PostgreSQL `durable_llm_tasks` |

candidate cache 只缓存候选集合和派生权重。健康、binding、probe 或凭据状态变化后按 credential 精确失效；不得把候选缓存当作节点健康 SSoT。

普通 pending 保存的是捕获结果，不拥有任务 lease，不应被 RecoveryWorker claim。Redis 丢失后，只有关联 durable task 的请求才允许按 durable PG 事实回源。

### 2.2 TTL 总表

| 对象 | 当前 TTL/窗口 | 过期语义 |
|---|---:|---|
| candidate cache fresh | 30s | 到期后重新查询候选 |
| candidate cache stale grace | 额外 30s | 仅 DB 可重试故障且客户端 context 仍有效时可短暂 serve stale |
| 会话 Governance/脱敏映射 | 30min | miss 后按持久会话数据重建；脱敏映射未实现前不得伪造命中 |
| 普通 pending | 默认 1h | 轮询结果过期，不代表后台仍可继续执行 |
| durable Redis projection | `expires_at - now` | 与 PG 结果可读窗口一致；到期或 Redis miss 时可回源 PG |
| attempt metadata buffer | 64KiB 且最长 30s | 超限返回错误；不得为释放内存而强制语义 commit |

TTL 不是一致性协议。candidate cache 依赖显式 invalidation；durable projection 依赖 task/version CAS；PG durable 行依赖 lease、fencing 和状态转换约束。

## 3. 普通 pending 与 durable projection

### 3.1 普通 pending

普通 pending 用于保存安全捕获的客户端协议响应，供同一会话/请求后续轮询。默认 TTL 为 1h，写入受最大 body 限制。

它不保证跨进程继续执行，不拥有 durable task 状态，也不能在未知副作用或捕获体不完整时声称请求已完成。

### 3.2 PostgreSQL SSoT

开启 durable 后，`public.durable_llm_tasks` 及其事件/结算记录是任务状态、租约、重试、checkpoint 和终态结果的唯一事实源。

Redis pending 仅是读取投影。Redis miss、TTL 到期或不可用时，查询路径可从 PG 回源；不得用 Redis 的旧状态反向覆盖 PG。

### 3.3 CAS 与 fencing

- `CreateAndClaim` 在单事务内创建任务并取得首个 lease，初始 `fencing_token=1`。
- claim/takeover 每次推进 fencing token；完成、重排、checkpoint 必须匹配 `(lease_owner, fencing_token)`。
- 旧 worker token 失效后必须丢弃结果并停止推进，不能凭 request_id 覆盖新 owner。
- durable Redis 投影只接受同一 `task_id` 且 `result_version` 不回退的写入；不同 task 或陈旧 version 被拒绝。
- 投影保存 fencing token 用于审计，但 PG 的 lease/fencing 条件才是执行所有权裁决。

## 4. 请求队列与重试域（主题④）

### 4.1 Dispatch 三层队列（CURRENT）

| 层 | 队列 | 建制 | 说明 |
|---|---|---|---|
| Tier-1 | modelQueue | 按 model | 含 `auto` 桶 |
| Tier-2 | credQueue | 按 credentialID | 账户级限流的当前执行粒度 |
| Tier-3 | Stats 事件总线 | 非阻塞 | 满即丢，不阻塞请求 |

调速器支持 concurrency、rpm、tpm、disabled。队列保持单所有者、有界深度、ctx 取消贯穿和 ResultCh 单发；`KILL_DISPATCH_V2=1` 可回退 legacy。

### 4.2 两种 backoff 不得混用

| backoff | 所有者 | 客户端连接 | 状态保存 | 结束条件 |
|---|---|---|---|---|
| 连接内 backoff | 当前请求的 SurvivalCoordinator | 必须仍可写；等待期间发 transport heartbeat | 进程内 attempt/coordinator 状态 | context 取消、写失败、成功或转 durable |
| durable worker backoff | RecoveryWorker + PG task | 不依赖原客户端 TCP | `next_retry_at`、lease、fencing、checkpoint | deadline、终态、lease 丢失或 safety blocked |

连接内 backoff 不能跨进程恢复。durable worker 不能假装恢复原物理连接，只能完成任务并把安全结果写入 PG，再投影供轮询读取。

## 5. 首字节与语义提交双轨

### 5.1 Legacy：`BytesSent`

legacy dispatch 继续使用 `ForwardOutcome.BytesSent` 作为兼容边界：一旦任何被 legacy 统计的客户端字节已经发送，mover 不再透明切换候选。

该规则服务旧流水线，不等同于「首语义帧」。不得用 heartbeat 是否写出反推 durable 的 `commit_state`。

### 5.2 Survival/durable：`AttemptCommitGate + commit_state`

新链路以 attempt-local gate 跟踪单调状态：`none → metadata → content/tool_call → terminal`。metadata 仅在本地有界缓冲；transport heartbeat 不推进状态。

在 `none/metadata` 且首语义帧尚未提交时，可 `Discard()` 当前 attempt，清空其 metadata，重新取候选并 failover。新 attempt 必须使用新 gate 和新缓冲区。

首个 content、tool call 或等价语义帧写网前，durable 链路先执行 write-ahead checkpoint。checkpoint 失败时禁止写网络，避免 PG 状态未知却继续透明重放。

一旦语义状态已提交，禁止透明从头重放到其他供应商。后续错误只能终止当前流、保存安全捕获结果，或进入 `resume_safety_blocked` 等显式状态。

### 5.3 双轨裁决原则

- legacy 路径只读 `BytesSent`，保持兼容行为。
- survival/durable 路径以 gate 是否可 discard 及 PG `commit_state` 为准。
- HTTP 200/SSE headers 或 transport comment 已写出，不自动等于语义 commit。
- 两套信号不得相互覆盖；日志与指标应同时记录 legacy bytes boundary 和 semantic commit state。
