# Session analysis contract v1

## Purpose

Session metadata is produced in two stages:

- `provisional`: deterministic extraction at request arrival. It must be cheap,
  bounded, and safe to discard or replace.
- `final`: analysis after the session has enough completed turns or reaches a
  close boundary. It may refine the provisional result, but must retain
  provenance and an input watermark.

The extractor distinguishes three kinds of values:

- **authoritative**: supplied by a trusted gateway/ACC field. These values may
  participate in billing or accounting semantics.
- **inferred**: derived from request text, paths, client fingerprints, history,
  or a model. These values are for analysis and grouping only.
- **unknown/pending**: the signal was not strong enough. Empty or `unknown` is
  correct; the system must not invent a project or agent.

## Taxonomy

`agent.name` is the product or agent identity (`zcode`, `opencode`,
`claude-code`, `cursor`, etc.). `agent.role` is the semantic role, currently
one of `coding_agent`, `ide_client`, `other_agent`, or `unknown`.

`client.type` is normalized through `internal/clienttype` and remains bounded by
its existing enum. `client.protocol` is the observed wire protocol and is not a
semantic work classification.

`work_types` are bounded candidates such as `debugging`, `refactoring`,
`feature`, `testing`, `deployment`, `migration`, `audit`, `documentation`, and
`research`. Explicit gateway work-type headers outrank text heuristics.

Project signals are intentionally separate from authoritative project IDs. A
trusted project reference is `status=confirmed`; path/remote/keyword evidence
is `status=pending` until it is matched to an allowed project dimension or
manually reviewed. Inferred project data must never overwrite
`session_dim.project_id`.

## Evidence and safety

Only bounded evidence snippets and hashes are retained. Complete transcripts,
secrets, and raw model output are not part of this contract. Transcript text is
untrusted data; future LLM workers must use strict structured output, candidate
project references, no tools, and field/enum/size validation.

The current pure-rule implementation is deliberately side-effect free. It is
suitable for replaying redacted session logs before it is connected to the
arrival or close paths.

## Versioning and precedence

The result carries `schema_version`, `analysis_kind`, `status`, `input_hash`,
and extractor provenance. Future durable writes must be idempotent on tenant,
session, analysis kind, input hash, schema version, and prompt/extractor policy.

Precedence is:

`manual > authoritative > approved rule > inherited rule > LLM > fallback`.

An older input watermark must not replace a newer result. A failed final
analysis must leave the last good provisional/final result available.

## Initial validation matrix

The rule stage must cover and preserve:

1. ZCode/OpenCode/Claude Code/Cursor system signatures.
2. Explicit client/project/work-type headers overriding weak text hints.
3. Short user messages producing a bounded provisional title without an LLM.
4. Tool-heavy transcripts excluding tool output from title intent.
5. Repository paths and git remotes as project hints.
6. Conflicting/ambiguous project hints remaining pending.
7. Unknown agents/projects remaining unknown or empty.
8. Prompt-injection-looking transcript content remaining data, not extractor
   instructions.
9. Chinese and English text, UTF-8-safe title truncation, and sensitive-looking
   strings not being persisted as evidence.
