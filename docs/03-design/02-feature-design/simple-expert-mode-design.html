简易模式与专家模式

当前网关是专家模式：全部能力默认开启、全部面板默认露出。个人用户要在这套默认状态里找到「接上自己的模型、拿一把 key、把客户端指过来」这条最短路径，需要跨过 15 个安装交互点、5 步激活向导、4 种密钥语义和 9 个字段的密钥表单。

方案是加一个注册项 gateway.mode，取值 simple 与 expert，默认 simple。它同时驱动三件事：控制台露出哪些页面、网关启动时装配哪些子系统、设置项给出什么默认值。专家模式是简易模式的严格超集，切换不丢任何数据。

这次要解决的三个问题
默认状态过重

463 个设置项、129 个布尔开关（其中 79 项默认开启）、71 个导航入口、93 个后台 worker、8 套探针默认同时运转。个人用户真正要做的只有五件事。

界面与运行时不匹配

设置项有 25 个后端类别，前端只暴露 10 个筛选桶且没有关键词搜索；专家面还藏在抽屉和页签里，按菜单分组隐藏会漏网。

地基已经现成

仓库已有 lite 存储形态（SQLite + 本地目录，注释写明「单机/个人部署」）、security.mode 的 observe/enforce 二态、以及 useDataViewMode 的偏好/生效/可切换三分离范式。

一条边界

简易模式不降低安全强度，也不改变任何协议的语义。它改变的是「谁在什么时候需要看见什么」和「网关在不需要这些能力时要不要启动它们」。security.mode 的 observe/enforce 语义在两个模式下完全一致——安全检测照常运行，只是把判定面板收进高级区。

模块清单是现成的分组单位

需要先纠正一个容易找错位置的点：模块清单结构不在 settings/ 包里。settings/spec_modules.go（1360 行）只是一份扁平的 94 项模块类设置，真正的清单在 admin/modules.go:21-34 的 ModuleDefinition。

结构字段含义对模式设计的意义
SettingKey 模块总开关绑定的设置键，16 个模块有值 模式预设的天然落点：一个模块一个键，不散落到几十个细粒度旋钮
Capabilities 能力项清单，共 102 项 当前是纯展示文案，与设置注册表无强绑定，需要加一致性门
ConfigKeys 模块下辖的配置项，共 132 项 与设置注册表仅靠这一条弱连接，13 个键悬空
Dependencies 依赖图，必需依赖开启失败时整体回滚 模式切换要复用同一套级联与回滚语义

模块开关的既有语义可以直接复用：resolveModuleEnabled 走 EffectiveValue，解析链是数据库 > 环境变量 > 默认值，查不到或出错时一律按开启处理（fail-open）；DangerLevel 达到 Dangerous 的开关需要超级管理员。

开关面比直觉大得多

463 项设置里只有 129 项是布尔开关，但其中 79 项默认开启，占布尔总数的 61%。如果按「默认开启的都露出来」做简易模式，一次会抛出 79 个旋钮，必然不可用。

同一份数据里还有两条现成的分界线。标记为需要重启才能生效的有 32 项，改了不生效的旋钮放在简易模式里就是骗人，这 32 项应当整体归专家模式。危险等级上，224 项安全加 186 项注意共 410 项，40 项危险加 4 项破坏性共 44 项本来就需要超级管理员才能改——这个既有分权语义与角色体系天然对齐，简易模式不必新造权限位。

个人用户今天在哪一步卡住

下列卡点全部可复现，逐条给出了代码位置。它们共同指向同一件事：门槛不在能力，在默认值和顺序。

激活是硬前置，且发生在配置任何东西之前

router.ts:409-465 的 shouldRedirectToBootstrap() 在 activated !== true 时把任何路径重定向到 /bootstrap。该向导的 5 步是「用户协议 → 设备指纹 → 激活 License → 注册中心 → 完成」，用户第一次打开页面看到的是协议和指纹，不是「把你的模型接进来」。

仓内已有 /activate-quick 端点（licensing/bootstrap_api.go），中心不可达时签发本地免费许可证，限 1 台设备、10 年有效期。简易模式可以直接用它把三步压成一次点击。

管理员密码要从容器日志里捞，捞错就进不去

admin/users.go:226-236：未设 LLM_GATEWAY_SEED_ADMIN_PASSWORD 时生成 Admin_<32位hex>，只以 WARN 打印在启动日志里。落库时 must_change_password=TRUE，登录后除改密外全部 403。

紧接着连错 3 次要验证码（admin/auth_captcha.go:74），每分钟 5 次登录限流（admin/rate_limit.go:62）。「密码打错 3 次 → 要验证码 → 再试 → 429」是第一次登录最常见的死循环。

四种密钥语义在文档里互相打架

LLM_GATEWAY_API_KEY（客户端到网关的静态门）、LLM_GATEWAY_ADMIN_API_KEY（控制面）、sk- 开头的租户密钥（客户端到网关）、凭据（网关到上游）—— 方向两两相反，报错信息不区分。

帮助手册里已经提醒过「凭据与 API Key 方向相反，不要混用」，说明这个坑是被认知到的，只是没有在流程上消掉。

签发一把网关密钥要填 9 个字段

help-manual.zh-CN.md:572-582 列出：租户、应用代码、密钥别名、归属用户、预算上限、每分钟请求数、并发数、每分钟 Token 数、备注。「应用代码」还决定该密钥可用的模型范围与客户端画像。个人用户填不动这些维度。

配一个上游要连过两道网络门

供应商页「填写 Base URL 后点击探测，系统会检查可达性与协议，探测不通过不允许提交」（help-manual.zh-CN.md:353），凭据保存后还要自动探活一次（同文件 :404）。于是「配一个上游」＝填 Base URL → 等探测 → 填 Key → 等探活 → 再建模型绑定。

quickstart 镜像里没有管理台前端

根 Dockerfile:76 只 COPY --from=builder /app/bin/llm-gateway，不含 web/dist；前端产物走 Dockerfile.web-patch 或部署脚本的 bind-mount。而 config/config.go:521-530 的 defaultStaticDir() 找的是相对工作目录的 web/dist。

推论：docker-compose.quickstart.yml 用 build: . 构建出的镜像不含 SPA，README 里的 open http://localhost:8781/admin 在该形态下很可能打开空白。此条为静态推导，未实跑验证。

安装器会在用户没同意的情况下改宿主系统

installer/cmd/llm-gw-installer/main.go:2452-2468：检测不到容器引擎就自动安装 Docker。lite 用户如果只想跑一个二进制，这一步需要显式声明。

三个正交的轴

仓库里已经有多个「模式」概念。新的工作模式必须和它们正交，否则「模式」一词在代码和文案里会指向三件不同的事。这是最容易埋雷的地方。

轴现有实现取值决定什么
存储形态 config/storage.go:29-32 full / lite 数据落在 PostgreSQL + Redis，还是 SQLite + 本地目录。决定基础设施依赖，与界面无关。
安全检测模式 settings/spec_modules.go:594 security.mode observe / enforce 检测到风险时只记录还是直接拦截。决定判定行为，与界面无关。
工作模式新增 gateway.mode simple / expert 控制台露出哪些页面、启动时装配哪些子系统、设置项给出什么默认值。
命名必须错开

security.mode 已经占用「模式」这个词并绑定 observe/enforce 语义。新注册项必须带 gateway. 命名空间，界面文案叫「工作模式」，与「安全检测模式」在同一个设置页里并列展示。文案上任何混用都会让用户误判「改了工作模式，安全检测就变成 observe 了」。

为什么三者要拆开

单机 + 专家能力

存储形态 lite，工作模式 expert。一个高级用户不想装 PostgreSQL，但需要完整的路由观测能力。工作模式不该强迫他换存储形态，反之亦然。

团队 + 精简界面

存储形态 full，工作模式 simple。一个团队只用核心转发能力，不需要把 605 条管理接口和 93 个 worker 当背景噪音。

个人 + 最小依赖

存储形态 lite，工作模式 simple。这是方案的目标形态。简易模式推荐 lite，但两者不互相强制。

五条设计原理

模式是投影，不是第二套实现

两个模式跑同一份代码。差别只在「哪些装配点被调用」和「哪些面板被渲染」。任何为简易模式单独写一套逻辑的做法，都会让两条路径各自漂移，几个月后没人说得清哪条是活的、哪条在跑。

这条决定了实现形态：简易模式不引入新引擎、不引入新进程、不引入第二套配置解析。它是一层投影，投影对象是既有代码。

一个开关，一个真源

模式只有一个注册项 gateway.mode。可见性判定只有一处实现 canShowNavItem()（web/src/config/appNav.ts:291-300）。运行时裁剪只有一处判定 OperatingMode()。

仓库里已经踩过这条的边：web/src/components/ui/AppBottomNav.vue:30-32 明文写着「不要在这里重新推导可见性——复制一遍过滤逻辑，底栏与侧栏就会在角色变更后不一致」。同理，不允许在71 个导航入口各写一个 if (simple)。

显式高于隐式，两种强度分开

模式预设分两种强度。override 表示模式决定，数据库和环境变量都盖不过，用于「简易模式必须保证不跑的重型子系统」。default 表示兜底，优先级是数据库 > 环境变量 > 预设值，用于「给专家旋钮一个保守默认」。

分开的理由：简易模式要保证「不跑 8 套探针」时，部署环境里的 env 不能把它击穿；而「给路由超时一个宽松默认」时，运维在 env 里写的值必须被尊重。把两种意图塞进同一个优先级，就会出现「0=禁用 被实现成 0=全量」那类语义反转——那比没有开关更危险。

降级必须可见

凡是简易模式改变了运行时行为，界面上必须标出「已降级」，并给出详情入口。这是 PRODUCT.md「诚实胜过漂亮」的直接要求。

仓库里有一个现成的反面样本：output_compliance.enabled 默认关闭，但子项 check_secrets、check_internal_ip、check_jailbreak_response 默认开启（settings/spec_modules.go:148-179）。把整个输出合规面板藏起来之后，用户看不到但仍在被检查——这是不可见的强制行为。

专家模式是严格超集，切换不丢数据

简易模式不删除任何数据、不重置任何设置。专家模式下的用户偏好留在 settings_kv 里，切回去立刻恢复。模式自身的写入面只有一个键。

这条同时否掉了「切模式时批量写 settings_kv」的方案：一旦批量落库，就再也分不清哪一行是用户设的、哪一行是模式铺的，回滚也回滚不回来。

实现机制

解析链插入模式层

现有优先级是「数据库 > 环境变量 > 默认值」，实现在 settings/spec.go:286 的 EffectiveValue()，返回值里已经带 source 字段（db / env / default）。模式层插在这里：

DB 显式值 > 模式预设 override > env > 模式预设 default > Spec.Default

source 扩展为第四个取值 mode。这个字段是现成的挂载点：admin/settings.go:177-193 的 settingsList 已经把 source 透传给前端，前端设置页的「来源」列直接就能显示「模式预设」，不需要新接口。

预设表形态

预设表是代码里一张显式的表，不是散落的条件判断。每条声明三件事：接管哪个键、给什么值、什么强度。 

type PresetEntry struct {
    Value    any
    Strength Strength // Override | Default
}

// simplePreset 只接管模块总开关与少数高频项，其余一律不接管。
var simplePreset = map[string]PresetEntry{
    // ── 模块总开关（Override：模式决定，env 与数据库都盖不过）──
    // 会话健康巡检：会持续产生告警，个人场景是噪音；另有 23 个配置项与 5 个依赖
    "session_inspector.enabled":  {Value: false, Strength: Override},
    // 提示词注入检测：依赖外部判官端点，个人部署没有
    "prompt_injection.enabled":   {Value: false, Strength: Override},
    // 错误触发的主动探测：需重启才生效，且属探针体系
    "error_probe.enabled":        {Value: false, Strength: Override},
    // 会话全景分析与审计：面向多租户边界，个人单机用不上
    "session_analytics.enabled":  {Value: false, Strength: Override},
    "session_audit.enabled":      {Value: false, Strength: Override},
    "handoff.enabled":            {Value: false, Strength: Override},
    "goal.enabled":               {Value: false, Strength: Override},

    // ── 高频项（Default：数据库 > env > 预设，运维显式设置优先）──
    "compression.mode":           {Value: "smart", Strength: Default},
    "routing.max_candidates":     {Value: 1, Strength: Default},
}

预设表以模块总开关为主，而不是以布尔开关的默认值为主。理由在上面已经给出：按布尔过滤会一次抛出 79 个旋钮，按模块收敛则只有十余项。

还有第三层覆盖，模式预设要排在它前面

设置的完整覆盖链不止三层。除了数据库、环境变量与默认值，仓内还有供应商级覆盖表 provider_settings（settings/provider_override.go），解析顺序是供应商级 → 平台级 → 默认值，带 5 分钟 TTL 缓存与 epoch 失效。

模式预设插在平台级之上、供应商级之下。供应商级覆盖由具体供应商决定，粒度比整个平台更细，模式不该盖掉它。

两个必须先处理的陷阱

陷阱一：迁移会往 settings_kv 播种

迁移 041、391、880、966 会直接往 settings_kv 写行，例如 sessions_v2.write_timeout_ms = 2000、model_lifecycle.stale_threshold = "2 years"。

这意味着「数据库里有行 = 用户显式设置过」这个假设不成立。预设表要么避开这些键，要么给 settings_kv 加一列 origin 区分 user 与 seed（需要一次迁移）。第一版建议先按键枚举规避，把加列留作独立议题。

陷阱二：迁移声明了后置条件

迁移 880 带守卫 DO $guard_880$，要求最终值必须 ≥ 2000。模式预设把任何键设到违反已声明后置条件的值，都是让迁移的守卫与运行时互相打架。

预设表每一条都要对照对应迁移里的 DO 守卫核一遍，不能只看 Spec 里写的默认值。

陷阱三：lite 模式下设置注册表几乎是空的

cmd/gateway/storage_mode_init.go:340-345：lite 模式只注册 CategoryStorage 一个族，然后调用 settings.Init(nil)，此时只有环境变量到默认值的解析链。

后果是 handoff.* 与 goal.* 这 36 项在 lite 部署下根本不注册，而模块清单仍把这两个模块列为可切换模块，切换必然返回 404。简易模式如果只做「设置项投影」，在 lite 形态下会投影出一堆不存在的键。模式层因此不能假设注册表是完整的，投影必须以模块清单为准，并对未注册的键显式跳过。

陷阱四：模块清单里有点不动的假开关

wechat_bot.enabled 在设置注册表里不存在，切换时 Spec() 返回空，模块开关处理函数直接回 404。该模块声明的 13 个 wechat_bot.* 配置键也全部悬空。memora 与 maintain 两个模块的总开关字段是空字符串，同样落到 404。

模块清单与设置注册表之间只有「总开关键」和「配置项键」两条弱连接，没有一致性校验。简易模式如果按模块清单生成界面，就会造出点不动的开关。这一条应当独立成一扇门：清单里的每个 SettingKey 都必须在注册表里存在。

前端分层

折叠，不隐藏

专家面从菜单里彻底消失，还是收进一个「高级」折叠组？选折叠组。理由有三：

  • 与仓内约定一致。web/src/config/navCoverage.test.ts:79-92 反复强调「不擅自改菜单——改菜单等于改产品信息架构，需属主裁决挂到哪个组」。折叠是加组，不是改路由。
  • 保留可发现性。个人用户以后变专业了，东西还在原地，不需要重新找入口。
  • 深链不失效。/routing-v2、/admin/audit-logs 这类路径被收藏或写进文档时仍然可达。

按菜单分组隐藏会漏掉的两处

粒度必须到组件与页签

模型 IQ 没有独立路由，它是 /models 的模型详情抽屉里内嵌的组件（ModelOfferDetailDrawer.vue:443 → ModelOfferExtrasPanel.vue）。ML 训练也没有独立页面，它是 /routing-v2/auto-ops 的四个页签之一（人工标注 / 标注统计 / 任务档案 / 调参审批）。

按导航分组隐藏，这两处会完整漏网——用户照常能点进去。分层标注必须落到组件和页签粒度。这一条与仓内审计记录的「候选面与读面必须同键」「可见性不等于完整」是同一族问题。

可复用的现成范式

web/src/composables/useDataViewMode.ts 已经把「模式」这件事做对过一次：preference（持久化的偏好）、effective（实际生效的）、canSwitch（允许不允许切换）三段分离，硬约束写在 composable 里而不是模板里，setMode() 在不允许时直接 return 且不写存储。

工作模式照抄这个形状：存储键用同一命名族（如 llmgw_working_mode），偏好与生效分离，effective 受角色约束——非 super 管理员即使存了 expert 也不给 expert 入口。

熔断语义必须一起改写

探针关掉，熔断不能原样留着

候选熔断打开时，请求会被 park 住等待探测恢复。这条链在生产上造成过 300 秒挂起：候选查询失败 → 熔断打开 → 请求 parked → 客户端超时。

简易模式移除了探针，却保留熔断，会出现无探测信号下熔断永不解除或误开。两种可行做法：一起关掉熔断，个人场景一两个上游，直连失败直接报错最简单；或者改写成直连失败即失败，不去 park。无论选哪个，都要写进钉测，因为熔断语义属于「降级了要说降级了」的范围。

开关生效时机

设置项自带 HotReload 字段，而子系统装配是启动期行为。模式切换后有一部分变更立即生效（设置值、面板可见性），另一部分需要重启（装配点）。界面必须按 HotReload 分组明示「哪些立即生效、哪些需要重启」，不能笼统提示一句「已切换」。

功能清单

三档而不是两档。有一类东西不能二元处理：它既不在简易模式里露面，运行时又确实在起作用。这类必须单列并明示，否则就是不可见的强制行为。

降级项的界面表达

降级项在设置页折叠区里要有可见标记。标记内容至少三样：这项能力当前处于降级状态、降级后的实际取值、与专家模式的差异。照 settingsList 已有的 source 字段显示「模式预设」即可拿到后两项。

使用流程

简易模式的目标是把「装到能用」压缩到五步，每一步都有明确的完成标志。

1

安装

一条命令。引导层只问两个问题：装到哪个目录、要不要连中心。其余全部走默认值，密码类留空即自动生成强随机值。

现状：install.sh 2 个交互 + wizard.go 13 步 + 确认 = 15 个输入点
2

激活

默认签发本地免费许可证，一步完成，不再进 5 步向导的协议与指纹两关。

/activate-quick：1 台设备、10 年有效期；LLM_GATEWAY_LICENSE_ACTIVATED=1 可兜底跳过
3

接上游

只填一个上游 API Key。Base URL 从供应商目录选，可达性探测放到后台跑，不阻塞提交。

现状：填 Base URL → 必须探测通过才允许提交 → 填 Key → 自动探活 → 再建模型绑定
4

拿网关密钥

两个字段：别名、预算上限。其余维度取默认，租户与归属用户走默认租户。

现状：租户 / 应用代码 / 别名 / 归属用户 / 预算 / RPM / 并发 / TPM / 备注，共 9 项
5

改客户端指向

接入示例页直接给出当前密钥的完整 curl，复制即用。

help-manual.zh-CN.md:661-673 的示例已存在，缺的只是「带当前 key 生成」这一步

风险与边界

明确不做的四件事

  • 不改任何协议的语义。三套入向协议归一是产品定位，不因模式而变。
  • 不削弱认证强度。main.go:2760-2768 已经规定 lite 模式在无鉴权配置下拒绝启动，简易模式沿用这条，不放宽。
  • 不为简易模式做第二套二进制或第二套配置解析。
  • 不悄悄改判定语义。security.mode 的 observe/enforce 在两个模式下含义一致。
