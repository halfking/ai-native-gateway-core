# 会话无进展循环治理（loop guard）—— 网关侧交付 ＋ 编排层建议

日期：2026-11-28 ｜ 环境：211 生产（acc-pg17 / llm_gateway，只读取证）

## 1. 问题定位（211 真库取证）

用户报告：会话在等用户裁决期间每 ~6 秒重发一次请求，其中一句「仍在等你的裁决，无新情况，不会代为决定，也不会重复调用 AskUserQuestion。待办清单内容仍准确，无需更新。」重复 500+ 次。

库内证据（session_turns / session_bodies_2026_11）：

| 会话 | 轮数 | prompt tokens | 空转占比 | 说明 |
|---|---|---|---|---|
| gw_872726fd… | 550 | 1.15 亿 | 含 127 处命中句 | 2026-11-05，turn 424–550 全部为 ~720KB 上下文＋每轮仅 +700~2000 字节 |
| gw_264193cb… | 1554 | 6.29 亿 | 93%（1449/1553 轮 Δ≤2048，均值 +384） | 2026-11-27/28，纯空转 6.0 亿 tokens |
| gw_ba975808… | 1102 | 3.34 亿 | 96%（1055 轮，均值 +457） | 同型 |

成因链：agent 编排宿主（completion verifier 判「未完成 → 继续调用」）在等待人类输入时把「人类阻塞性未完成」当「技术性未完成」继续轮询；每轮把模型自己的短回复（216~516 tokens）并回上下文重发整段历史。网关只能看到「上下文零增长 ＋ 固定节奏重发」。

判据校准（三个循环会话 vs 七个正常高频会话对拍）：空转轮 `ownOnly = Δprompt − 上轮 completion ∈ [-128, +512]`（均值 +381，最大 ≈1100）；正常会话的最长连续段 10~86 轮且穿插进度轮。

## 2. 网关侧交付（本轮已入库）

新文件 `domains/streaming/session_loop_guard.go` ＋ `settings/spec_loop_guard.go` ＋ 判据测试：

- **判据**：`ownOnly ∈ [-128, flat_delta_tokens(512)]` 连续 ≥ trip_after_turns(12) ⇒ 回退；≥ terminal_turns(120) ⇒ 终态。
- **自动回退**：429 ＋ `Retry-After` 指数梯（30s→60s→…封顶 600s），每窗口只放行一个探针轮；每轮多确认一次空转窗口翻倍。
- **超次数关闭**：终态错误码 `loop_guard_terminated`，探针间隔放宽到 1h。
- **重开路径（误判自愈）**：① 入口侧请求体估计较上次成功轮增长 ≥ entry_progress_tokens(2048，空转上界的 2 倍) ⇒ 立即重置放行（返程人类不撞死门）；② 探针轮出现真进度 ⇒ 整体重置；③ 相邻成功轮间隔 > max_gap_seconds(600s) ⇒ 计数清零。
- **豁免**：internal 回环 key、prompt < min_prompt_tokens(256)（sys:anon 零 token 流量）、并发突发（间隔 <500ms）、失败轮、auto 子请求。
- **接线**：chat/messages/responses 三面入口 Check（session id 终定后、上游工作前）＋ emitTelemetry 单一收口 Observe（三面共用）；拒绝走 rate_limited 记账（不污染 provider 错误数）；`loop_guard.*` 10 键全部 HotReload，管理台设置页新增「循环守卫」类目（8 语种）。
- **判据测试**：梯形/趟点/单探针/梯次延长/终态/入口重开/长间隔/噪声排除/热加载开关/接线源码锚（防 team_budget_gate 式「判定体在、调用点缺」）。
- 读数：`go build ./...` EXIT=0；vet(streaming,settings) EXIT=0；settings ok 0.353s；streaming 全量 ok 139.583s；vue-tsc EXIT=0；SettingsView 测试 passed。

限制（诚实边界）：状态在进程内存——蓝绿换槽/重启后从零重累计（最多损失 trip 前的 12 轮窗口）；守卫只针对「上下文零增长」型循环，宿主若每轮注入大块 reminder（增量 >2048）属计费/限额问题，有意不拦；网关不伪造模型输出，只拒绝转发。

## 3. 编排层建议（超出网关代码面，需编排服务落地）

网关拦的是「网关可见」的浪费（上游 token 烧烧烧）；编排层的空转成本（agent 转录、verifier 调用本身）在网关之外，建议按以下优先级落地：

1. **blocking_type 结构化标注**（P0，与网关互补）：completion verifier 输出加机器可读 `blocking_type: human_input_required | technical_incomplete`；只有 `technical_incomplete` 允许高频续作。verifier 判分口径同步加一问：「此阻塞是否可由本会话继续调用工具解决」——答「否」直接短路「继续」指令。
2. **AskUserQuestion 硬性退避**（P0）：该工具被调用且未获回复 ≥1~2 次 ⇒ 目标置 `blocked_on_human`，续作从秒级切指数退避（分钟→小时→天）。
3. **重复度去重熔断**（P1）：连续 3~5 轮回复哈希/语义比对高度重复且无新工具证据（新 commit/文件变更）⇒ 判无进展循环，熔断续作。网关侧 ownOnly 判据就是同一思想在生产数据上的可计算形态。
4. **单目标资源硬上限**（P1）：token 用量/调用次数/墙钟时间三阈值，任一超限且无状态变化 ⇒ 强制暂停。本次 211 事件是「亿级 token 才停」，应压到百万级。
5. **事件驱动取代轮询**（P2）：`blocked_on_human` 状态不定时唤醒 agent，改推通知/工单（如收件箱、到期提醒类机制），用户输入后触发恢复——零轮询成本。
6. **网关侧后续增强候选**（登记不代做）：把拒绝计数/烧掉 tokens 的估算暴露成 `/metrics` 指标与管理台卡片（可观测面）；终态会话清单 API（运维一目了然哪些会话被关）。

## 4. 方法对比与选型（2026-11-28 第二轮，按「先学习、再定方案、再执行」）

### 4.1 业界实践盘点（网调结果）

| 来源 | 机制 | 默认值 | 可借鉴点 |
|---|---|---|---|
| CrewAI | 同一工具+同一参数+同结果连续 5 次 ⇒ 硬停（ToolExecutionFailedError，固定不可调）＋ max_iter=20 | 5 次 / 20 轮 | **重复指纹硬停的思想**；「固定不可调」是缺点，我们做成可调可关 |
| AWS Builders' Library | 封顶指数退避＋jitter、token bucket 限重试、熔断慎用（模态行为难测）、幂等去重 | 无固定数值 | 本守卫退避梯已是同款；**jitter 建议登记不做**（我们按窗口锁相，jitter 反而破坏「每窗口一探针」语义） |
| OpenAI/Anthropic prompt caching | 重复前缀缓存读 0.1× 输入价 | — | 解释了为何空转烧钱仍是问题：**cache_read 只省 90%，且写价另计**；拦截永远比 0.1× 更便宜 |
| MCP elicitation | 人机交互有正式协议位（服务器可向客户端要输入） | — | 印证「等人类」应走事件通道而非轮询——属编排层建议 ⑤ 的协议依据 |
| LangGraph/OpenAI Agents SDK | 递归上限/human-in-the-loop 挂起，无网关侧先例 | — | 网关侧守卫无现成先例，本实现属补位 |

### 4.2 候选方法对比（用户提出的四个方向＋两个补充）

| 方法 | 能否抓到 211 实测的循环 | 误伤风险 | 成本 | 结论 |
|---|---|---|---|---|
| ① 重复回复次数上限（指纹计数） | **能**——gw_872726fd 108 轮回复逐字节同 md5；gw_b1be9881 同一请求体重复 344 次 | 低（归一化后仍同指纹才算；变化即重置） | O(1)/轮 | ✅ **本轮已实现**（repeat_identical_limit=5，同 CrewAI 值） |
| ② 上下文零增长计数（上一轮已交付） | 能（93% 空转轮 Δ≤2048） | 低 | O(1)/轮 | ✅ 已在役（两条判据互补：②抓「上下文不变」，①抓「回复不变」） |
| ③ 时间自动回退（等人工/等硬件） | 部分——能止损但不识别，且空转 30s 节拍 ≪ 指数梯首档时早几轮拦不住 | 无 | O(1) | ✅ 已在役（退避梯＋探针窗口），作为 ①② 的**处置面**而非判据面 |
| ④ PI（错误分析/取证）介入 | 不需要——循环不是「错误」，status_code=200、success=true，PI 面向的是错误分类与取证 | — | 每轮 LLM 调用 | ❌ 明确不用：判据必须便宜且确定性；语义分析属编排层 completion verifier 的职责（交接 §3.1） |
| ⑤ 请求体整串哈希去重（幂等键思路） | 能（344 次同体）但**误伤真实重试**（网络闪断后客户端合法重发同一请求） | 中 | O(1) | ❌ 不做：与既有 idempotentCache 职责重叠，且误伤面大 |
| ⑥ 语义/embedding 相似度 | 能，但两判据已覆盖实测形态 | 中（ paraphrase 判重复有风险） | 每轮向量化成本 | ❌ 不做：收益低、成本高、不确定性大——CrewAI 用的是精确匹配也够用 |

### 4.3 本轮新增交付（重复回复快道）

`loop_guard.repeat_identical_limit`（默认 5，0=关闭）：成功回复做归一化指纹（空白折叠＋尾标点剥离＋截尾 2KB＋fnv64），同一指纹连续 N 次 ⇒ **立即进入回退态**（不等 12 轮上下文计数）；错误码 `loop_guard_repeat` 并报出重复次数。变化即重置（paraphrase/标点漂移不误伤）。新判据 4 条：快道趟点、变体重置、0 关闭、归一化边界。

### 4.4 三层总结（最终形态）

1. **判据层（网关，确定性、每轮 O(1)）**：上下文零增长 ＋ 回复指纹重复，两道互补；
2. **处置层（网关，指数退避＋探针）**：429+Retry-After 指数梯、每窗口一探针、终态超次关闭；
3. **语义层（编排层，昂贵、需 LLM/协议支持）**：blocking_type 标注、AskUserQuestion 退避、事件驱动（交接 §3）——网关不用 PI 做语义判定，把语义层留给有完整上下文的编排方。

## 6. 运维口径

- 部署后守卫默认开启（`loop_guard.enabled=true`）；要全关改这一个键即可，无需重启。
- 观测：`grep 'loop guard rejected request'` 容器日志；`X-Gw-Loop-Guard` 响应头；error_code ∈ {loop_guard_backoff, loop_guard_terminated}。
- 若出现误伤（合法会话被回退）：先调 `loop_guard.trip_after_turns` ↑ 或 `loop_guard.flat_delta_tokens` ↑；入口进度阈值 `entry_progress_tokens` 只在「返程人类输入特别短」时才需要调低。
