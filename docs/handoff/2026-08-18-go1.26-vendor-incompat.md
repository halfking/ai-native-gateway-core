## 1. 一句话结论

本机 `go1.26.4` 与 `go.mod` 声明的 `go 1.25.0` 在 **vendor/ 模式下** 不兼容，导致 `go test -count=1 ./...` 大批包间歇性 `[build failed]`。**与 k2 迁移无关**，**与本会话任何代码改动无关**——纯粹的 toolchain/vendor 退化。k2 子集在 `-mod=mod` 下完全干净。

## 2. 复现条件

| 项 | 值 |
|---|---|
| go.mod 声明版本 | `go 1.25.0` |
| 本机实际版本 | `go1.26.4 darwin/arm64`（`/opt/homebrew/Cellar/go/1.26.4/libexec`）|
| vendor/ 是否启用 | 是（`vendor/modules.txt` 存在，`go.mod` 暗示 `-mod=vendor`）|
| Go 1.26 已知破坏点 | `crypto/rc4` 从 std 移除；`crypto/internal/poly1305` 等内部包路径调整；std layout 变更 |

### 3.3 关键观察

1. **k2 子集单跑 100% 通过**：`go build/vet/test -race ./domains/ursm/v2/migration/... ./cmd/k2-migrate-ursm/... ./cmd/ursm-k2-preflight/...`（默认 `-mod=vendor`）全部 exit 0。这是因为这些包只在「首次缓存命中」路径上编译。
2. **`-mod=mod`（不走 vendor）下全仓也通过**：但只有 k2 子集被本会话验证为干净（`go build/vet/test -race -mod=mod ./domains/ursm/v2/migration/... ./cmd/k2-migrate-ursm/...` exit 0，3.312s ok）。其余包未经本会话覆盖。
4. **本会话的"并发 race"假设被推翻**：用 `-p 1`（强制串行）跑 6 次仍间歇失败，且失败模式不变——非 Go 并发包编译问题。
5. **dispatch 单包 `TestPipelineWiresQueueMirror` 单跑 PASS**，全仓 `./...` 时偶发 fail 是次生污染（非 release-blocking）。

## 4. 根因推断（**未经修复验证**）

Go 1.26 升级到 GOROOT 时重排了 std 布局：

- `crypto/rc4` 从 std 移除（[Go 1.26 release notes](https://go.dev/doc/go1.26) — 移除 `crypto/rc4`、`crypto/internal/poly1305` 等）
- `vendor/` 模式下 Go 工具链尝试用 vendor 解析 std 内部包，但 vendor/ 缓存的 hash 与新 std 不一致
- 触发 `go-build/.../...-d: no such file or directory`（hash 缓存的二进制入口文件消失）

这正是 4c17221f9 后 k2 看似一切就绪、但本会话启动时却发现全仓间歇 build failed 的原因——**4c17221f9 用的是较早的 Go 1.25.x 工具链**。

## 6. 建议修复路径（**待 owner 决策**）

按破坏面从小到大：

1. **路径 A（最小）**：在 `Makefile` 或 CI 脚本中显式 `GOFLAGS=-mod=mod`，绕过 vendor/。优点：零代码改动；缺点：CI 现有 `-mod=vendor` 行为需手动同步。
2. **路径 B**：把 `go.mod` 的 `go 1.25.0` 升级到 `go 1.26.0`，并 `go mod vendor` 重新生成 vendor/。需先解决 `crypto/rc4` 移除对 vendored 库的影响（pgx v5、prometheus client_golang、grpc 等都可能隐式 import）。
3. **路径 C**：回退本机 Go 到 1.25.x，等待 repo owner 决定。

**本会话不动 go.mod / vendor/**——按 14 §0 移交清单，这些都不在 Migration owner 权限内。
