## 1. 一句话结论

本机 `go1.26.4` 与 `go.mod` 声明的 `go 1.25.0` 在 **vendor/ 模式下** 不兼容，导致 `go test -count=1 ./...` 大批包间歇性 `[build failed]`。**与 k2 迁移无关**，**与本会话任何代码改动无关**——纯粹的 toolchain/vendor 退化。k2 子集在 `-mod=mod` 下完全干净。

### 3.3 关键观察

1. **k2 子集单跑 100% 通过**：`go build/vet/test -race ./domains/ursm/v2/migration/... ./cmd/k2-migrate-ursm/... ./cmd/ursm-k2-preflight/...`（默认 `-mod=vendor`）全部 exit 0。这是因为这些包只在「首次缓存命中」路径上编译。
2. **`-mod=mod`（不走 vendor）下全仓也通过**：但只有 k2 子集被本会话验证为干净（`go build/vet/test -race -mod=mod ./domains/ursm/v2/migration/... ./cmd/k2-migrate-ursm/...` exit 0，3.312s ok）。其余包未经本会话覆盖。
4. **本会话的"并发 race"假设被推翻**：用 `-p 1`（强制串行）跑 6 次仍间歇失败，且失败模式不变——非 Go 并发包编译问题。
5. **dispatch 单包 `TestPipelineWiresQueueMirror` 单跑 PASS**，全仓 `./...` 时偶发 fail 是次生污染（非 release-blocking）。

## 4. 根因推断（**未经修复验证**）

Go 1.26 升级到 GOROOT 时重排了 std 布局：

- `crypto/rc4` 从 std 移除（[Go 1.26 release notes](https://go.dev/doc/go1.26) — 移除 `crypto/rc4`、`crypto/internal/poly1305` 等）
- `vendor/` 模式下 Go 工具链尝试用 vendor 解析 std 内部包，但 vendor/ 缓存的 hash 与新 std 不一致
- 触发 `go-build/.../...-d: no such file or directory`（hash 缓存的二进制入口文件消失）

这正是 4c17221f9 后 k2 看似一切就绪、但本会话启动时却发现全仓间歇 build failed 的原因——**4c17221f9 用的是较早的 Go 1.25.x 工具链**。

## 9. 解决记录（2026-08-18 19:11–19:26，续接会话）

### 9.1 §4 根因推断被证伪

续接会话（ZCode）复检发现 §4 的三个事实性推断均**不成立**：

| §4 原推断 | 复检事实 | 证据 |
|---|---|---|
| Go 1.26 移除 `crypto/rc4` | **未移除**。本机 GOROOT 内 `src/crypto/rc4/rc4.go` 存在，且 GOROOT 自身 `crypto/tls/cipher_suites.go:16` 合法 import 它 | `ls /opt/homebrew/Cellar/go/1.26.4/libexec/src/crypto/rc4` |
| std 内部 vendor 路径重排 | GOROOT 内部 `src/vendor/golang.org/x/crypto/internal/poly1305` 目录**存在** | `ls .../src/vendor/golang.org/x/crypto/` |
| vendor/ 与新 std 不兼容 | `go build ./...`（默认 `-mod=vendor`）**exit 0**；`vendor/github.com/beorn7/perks/quantile` 等 §3.2 报缺失的包全部在 vendor/ 且登记于 `vendor/modules.txt` | §9.2 验证矩阵第 1 行 |

**"package X is not in std / cannot find module" 在包源码与 vendor 登记均存在时出现，指向的不是依赖缺失，而是构建缓存（GOCACHE）中毒后包解析读到损坏元数据。**

### 9.2 真实根因

**构建缓存中毒 + 并发访问损坏**，非 toolchain/vendor 不兼容：

1. 本机长期存在**两个 Go 安装共享同一 GOCACHE**：`/opt/homebrew/bin/go`（1.26.4，PATH 优先）与 `/usr/local/go/bin/go`（1.24.5），且历史上有 1.25.x（brew 升级痕迹）。多工具链交替写入同一缓存。
2. 发现时点存在**长驻 `go run ./cmd/server` 进程**（PID 23664）与 test 会话并发读写缓存。
3. `go clean -testcache` 只清测试结果条目，不清编译产物；中毒的编译产物条目在命中时"凑巧通过"（旧条目有效）、在缺失/损坏时报出 §3.2 那批互相矛盾的错误（`...-a/-d: no such file or directory` 是字面意义的缓存条目文件丢失）。**间歇性 = 缓存命中掩蔽**。
4. `-p 1` 仍间歇失败（§3.3.4）与本根因自洽：损坏条目的存在与编译并发度无关。

### 9.3 修复（路径 D，破坏面小于原 A/B/C）

```bash
go clean -cache && go clean -testcache
```

零 repo 改动（未动 `go.mod`、`vendor/`、Makefile、CI）。原三条路径全部不再需要：A（`-mod=mod`）改变 CI 行为、B（升 go.mod+re-vendor）为不存在的问题做大改、C（回退工具链）无必要。

预防建议（供 repo owner 参考，非本 ticket 范围）：工具链升级后如见矛盾解析错误，先 `go clean -cache`；避免 `go clean -testcache` 循环与长驻 `go run` 进程同时段运行。
