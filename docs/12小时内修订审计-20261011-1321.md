## 二、发现的问题与修正

### 2.1 A1 — `mayCarryMarker` 负过滤性能回退（P1）

**修正原因（上游动机，判定合理）**：无花括号裸形占位符
（`SENSITIVE:phone:1`）在 2026-10-10 进入容错文法后，负过滤仍只认 `{`，
导致「全是裸形的 body」对每个探针都判干净 → 还原器跳过字段 → 残量守卫
反而拦下整条响应。**这是漏判，必须修**。

**处理方案的问题**：修漏判的方向对，但把「memchr 否定过滤」换成了
朴素双重循环 + 一次 `string(payload)` 全量拷贝。

```go
// 改前（security/sanitize/hop.go）
return bytes.IndexByte(payload, '{') >= 0 || bytes.IndexByte(payload, fullWidthBraceLeadByte) >= 0

// 改后
func mayContainMarkerText(text string) bool {
	if strings.ContainsAny(text, "{｛") { return true }
	return containsFoldCaseWord(text, placeholderMarkerWord)  // O(n·m) 朴素扫描
}
func mayCarryMarker(payload []byte) bool { return mayContainMarkerText(string(payload)) }  // 全量拷贝
```

**执行结果不合理——实测回退（本轮亲跑，`-benchmem -benchtime 3000x`）**：

| 输入 | 改前 | 改后 | 回退 |
|---|---|---|---|
| 真实响应体（16KB SSE 文本流） | 5.6 ns / 0 alloc | 2477 ns / **12288 B** | **~444×** |
| 9KB 普通文本 | 505 ns / 0 alloc | 45528 ns / 9472 B | ~90× |
| 512KB 无标记大 body | 15684 ns / 0 alloc | 2362470 ns / 524292 B | ~150× |

**为什么严重**：`mayCarryMarker` 是**每个 SSE 帧**、**每个响应体**都要跑的
否定过滤（`containsNonForeignMarker` 13 个调用点、`hasReservedPlaceholder`
9 个调用点）。上游注释自己写着「大多数响应走这条路，所以必须保持便宜」，
而改动把它从 SIMD memchr（33 GB/s）降到了逐字节比较（~200 MB/s），并引入
**每次调用一次全量堆分配**。这恰好发生在 154/252 事故后正在压延迟的窗口。

**修正（已落地）**：保留「认裸形」的语义，把成本拉回 memchr 量级——
用 `IndexByte` 定位候选首字节的**大小写两种拼写取更早者**，只在命中处做
定长比较；字节切片路径全程不拷贝 body。

★ **实现期真踩了两个坑，都被自测抓出来**（详见 §五.1）：
  1. 「先命中哪条 memchr 就用哪条」**会漏判**——`"SeNsItIvE"` 因小写 `s`
     在 index 3 命中而跳过 index 0 的大写 `S`，把真实存在的裸形标记判成
     不存在。必须取**更早**的那条。
  2. 去掉 `i+n > len(text)` 边界检查会 **panic**（index out of range）——
     循环守卫测的是 `offset`，而实际读取的是 `i`。

**修正后实测（`BenchmarkMayCarryMarker*`，-benchmem 3000x）**：

| 输入 | 参照（改前两次 memchr） | 修正后 | 原 12h 版本 |
|---|---|---|---|
| 真实 SSE 响应体 16KB（常态路径，含 `{`） | 5.24 ns / 0 B | **5.28 ns / 0 B** | 2477 ns / 12288 B |
| 512KB 无标记大 body | 15577 ns / 0 B | 31174 ns / 0 B | 2362470 ns / 524292 B |
| 9KB 无花括号散文 | 291 ns / 0 B | 21049 ns / 0 B | 45528 ns / 9472 B |

结论：**常态路径（真实 SSE 帧含 `{`）与修复前完全同量级**，全部输入
**0 分配**。无花括号散文仍比参照慢（多扫一遍 marker 词），这是 A1
**必须付出的语义代价**——上游要的就是认裸形；相比原 12h 版本已改善 2–12×，
且消除了每次调用的全量堆拷贝。

**永久判据已入库**（`security/sanitize/hop_prefilter_test.go`）：
- `TestFoldCaseWordMatchesNaiveSemantics`：20 万例随机差分 + 真实拼写全部子串
  + 单字节/空串，与朴素实现**逐位等价**；
- `TestMayCarryMarkerStillAdmitsBareForm`：裸形必须继续放行——防「为了快而
  一起把修复目标修掉」；
- `BenchmarkMayCarryMarker*` / `BraceOnly*`：成本判据成对放在一处，allocs/op
  必须为 0。

★ 语义判据与成本判据**必须成对**：只有语义判据，则「退回朴素循环」仍然全绿；
  只有成本判据，则「退回漏判裸形」也看不出来。

### 2.2 A2 — anomaly-reporter 自禁用不可观测（P2）

**修正原因（上游动机，判定合理）**：154 事故里 endpoint 配到了本网关不存在的
路由，`postBatch` 对非 2xx 一律 requeue → 24h 内 9341 次 404 死循环。
「永久性 4xx 重试永远不会成功，自禁用」是正确的止血方向。

**处理方案合理**：区分永久性状态码、连续 3 次后 `CompareAndSwap` 自禁用、
返回 `true` 让调用方丢弃 batch 而非重新入队——闭环正确，
`lockfree_anomaly_reporter_permanent_test.go` 覆盖了计数与轮次边界。

**执行结果不合理**：`Stats()` 的 5 个字段里没有任何一个能区分
「刚自禁用」与「一直没启用」。自禁用后 `enqueue` 立即返回 false、
所有 `Report*` 静默返回，运维从指标上看到的仍是
`QueueSize=0, Enqueued=..., Failed=...`——**量具坏了但显示正常**。
这与同一批 `c88bc79e3`「量具不可用不得报 ok」的整改精神自相矛盾：
脚本侧修好了，Go 侧留了同一个盲区。

**修正（已落地）**：新增 `permanentlyDisabled atomic.Bool`，与 `enabled`
在同一临界区内翻转；`Stats()` 增加两个字段：

```go
type AnomalyReporterStats struct {
	...
	PermanentlyDisabled bool   `json:"permanently_disabled"` // 自禁用＝待处置故障
	PermanentRejections uint64 `json:"permanent_rejections"` // 连续永久性 4xx 计数
}
```

★ **单独一个 flag 而不是读 `enabled`**：`enabled=false` 有三种成因
  （构造时未启用、Close 已调用、自禁用），只有自禁用这一种需要人介入。
  `Close()` 显式清掉该标记——否则进程按计划收尾时，监控读数会把
  「正常关闭」误报成「端点永久拒绝导致停摆」，那是另一种假信号。
  三种成因各有判据覆盖（见 §五.2）。

★ `PermanentRejections` 与 `PermanentlyDisabled` 一起看可区分
  「正在逼近阈值」与「已经停摆」——只有后者才需要立刻叫人。
