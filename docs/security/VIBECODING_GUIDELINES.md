# Vibecoding 规范

> 本规范的每一条都来自真实事故，不是理论推演。
> 主案例：`request_body` 静默落库为 NULL —— **6 次修复、1 个月未收敛**，
> 根因是一次"测试全绿"的修复（`36998a96`）引入的。
> 48 小时内影响 322 条请求、298 个会话。

---

## 零、为什么"AI 写了测试"救不了你

`36998a96` 那次修复：

- 写了 5 个测试，**全部通过**
- 提交信息详实，引用了事故编号
- 通过了 code review
- **丢了 3.7% 的生产数据，并且它要修的问题一个都没修掉**

原因：它要防的输入 `\uZZZZ`（`\u` 后跟非 hex）**在合法 JSON 里根本不可能出现**——`json.Valid` 会先拒绝。而它写的 5 个测试，全部围绕这个不存在的输入，**忠实地锁死了错误前提，还提供了信心**。

> **测试只能证明代码符合假设，不能证明假设为真。**
> AI 极其擅长写出自洽的代码 + 自洽的测试 + 自洽的提交信息——三者可以同时错。

## 一、前提验证：改之前先证伪（成本最低，拦截率最高）

### 规则 1.1　禁止在无证据的情况下写修复代码

修 bug 前必须先回答：**"这个输入/场景真的会发生吗？"** 并给出可复现的证据：

| 证据类型 | 示例 |
|---------|------|
| 一次生产 SQL | `select count(*) ... where <假设条件>` |
| 一行标准库调用 | `json.Valid([]byte(...))` → false，说明该输入不可能存在 |
| 一条真实日志 | 带 request_id 的报错原文 |

本案中，**一行 `json.Valid` 就能证伪整个修复的前提**。

### 规则 1.2　用真实依赖验证，不要只跑单测

本案的两个致命误判都只有真实依赖能发现：

- `\uZZZZ`（假想威胁）：Go 认为**非法**，PostgreSQL 根本没机会看到
- `\u0000`（真实威胁）：Go 认为**合法**，PostgreSQL 报 22P05 拒收

> 涉及 DB / 协议 / 编码的修复，必须过一次**真实的** cast / 解析 / 往返。
> 我这次把 7 种真实 body 形态灌进生产 PostgreSQL 做 `::jsonb`，才确认旧代码
> "丢了 4 条合法数据，且它要修的 22P05 仍然报错"。

### 规则 1.3　先取一条失败样本的真实数据，再读代码

本案前 6 次修复全在改**读取路径**（视图、JOIN、表拆分、并发时序），因为没人先看那一行到底存了什么。

这次第一个动作就是查库：

```
request_logs_bodies_hot：该行存在，response_body 1538 字节，request_body = NULL
request_logs_hot：request_preview 有值
```

`preview` 和 `body` 来自**同一份字节**。preview 有值 ⇒ body 在写入时存在 ⇒ **整个读取层、视图、JOIN、表拆分全部出局**。一次查询排除了 6 次修复的全部方向。

> **判据：先用数据缩小范围，再用代码解释数据。反过来会在错误的层里找一个月。**

## 二、不变量测试：锁定契约，而非已知的坏输入

这是防"改好又改坏"的核心。两类测试的区别是决定性的：

| 类型 | 写法 | 问题 |
|-----|------|------|
| ❌ 示例测试 | "`\uZZZZ` 应被转义" | 锁死了错误前提，重构时误导后人 |
| ✅ 不变量测试 | "**合法 JSON 进 ⇒ 合法非空 JSON 出**" | 与实现无关，任何人以任何方式重写都会被拦下 |

### 规则 2.1　数据处理函数必须有"健康输入必须存活"的测试

不要只测"已知坏输入被正确处理"。**必须测"正常输入没被弄坏"**——这正是本案缺失的那一环。

### 规则 2.2　用生成器覆盖你想不到的情况

本次的属性测试用 `json.Marshal` 生成 576 种内容组合：**任意内容经 `json.Marshal` 必产合法 JSON，合法 JSON 必须存活**。

它不依赖"我猜哪些字符危险"——而猜错正是上一位 AI 栽跟头的地方。

### 规则 2.3　手写扫描器必须过模糊测试

只要函数里有 `s[i+2:i+6]` 这类索引运算，就必须有模糊测试（固定 seed 保证可复现）。本次 20 万随机输入验证两条不变量：**不 panic**、**不输出非空非法 JSON**。

### 规则 2.4　新测试必须在旧代码上失败

> **没在旧代码上失败过的回归测试，不是回归测试。**

我把新测试 checkout 到修复前的代码上跑，确认 3 个测试失败、错误信息准确指向问题。不做这一步，你只是写了一堆恒真断言。

## 三、静默失败清零：让"改坏"立刻可见（优先级最高）

### 规则 3.1　任何降级/丢弃/兜底分支必须留可观测痕迹

本案存活 6 次修复的根本原因：**NULL 的 body 和"本来就没有 body"在数据上完全同形**。

更说明问题的是——同一个文件里 `sanitizeRawJSONField` 打日志、`sanitizeJSONField` 不打，**两套标准**，而漏的那个正好是丢数据的那个。

**可 lint 化的判据**：以下模式出现在错误/兜底分支时，同分支内必须有日志或指标调用：

```go
return nil / return "" / return       // 错误兜底
*p = nil / x = ""                     // 置空已捕获的数据
_ = someCall()                        // 吞掉错误
if err == nil { ... }                 // 无 else，失败时静默跳过
```

### 规则 3.2　日志记尺寸，不记内容

这些字段装的是**用户 prompt**。记 `bytes`、`request_id`、`field`，**不要记内容**。
（我自己第一版写了记录前 120 字节的 `previewForLog`，审计时删掉了。）

### 规则 3.3　成对的函数必须行为一致

`sanitizeJSONField` / `sanitizeRawJSONField` 是同一操作的两半。我第一次提交只给前者加了截断日志——**审计发现后者仍是静默截断**，而它覆盖的 `outbound_body` 是真正发给上游的 prompt，**悄悄变短比直接为 NULL 更糟，因为它看起来是完整的**。

已补测试断言两者对"丢弃决策"和"输出"完全一致，防止再次漂移。

> 发现一处缺陷，**立刻搜索同类**。缺陷从不孤立存在。

---

### 规则 3.4　本仓库的落地通道：日志 + format-anomalies

丢弃事件**同时**写两处，缺一不可：

| 通道 | 用途 |
|-----|------|
| `slog.Warn("data loss: "+类型, ...)` | 错误日志，事后 grep 排查 |
| `RecordDataAnomaly` → `response_format_anomalies` 表 | `/format-anomalies` 页面，运营可见、可标记已解决 |

请求链路（`ChatHandler` 可达）用 `h.recordDataLoss(...)`，它已封装两个通道。
admin 只读路径无 recorder，按既有约定仅打日志。

已定义的 anomaly_type（`domains/streaming/data_loss_anomaly.go`）：

| 类型 | 语义 | 默认级别 |
|-----|------|---------|
| `tools_restore_failed` | tools 未能还原，请求以「无工具」发往上游 | high |
| `request_body_truncated` | body 被读超时/超限截断，截断内容既落库又转发 | high（客户端主动断连为 medium）|
| `body_decode_failed` | 存储的 body 无法解码，展示为 null／安全审计降级放行 | high |
| `metadata_dropped` | 路由尝试链、auto 决策、附件等元数据丢失 | medium |

两条硬性约束：

- **只记尺寸与原因，绝不记内容**——这些字段承载用户 prompt。
- **用 `context.WithoutCancel`**——客户端断连正是截断高发场景，请求 ctx 已取消时仍必须记录成功。

### 规则 3.5　截断字符串必须按 rune，不能按字节

`s[:n]` 会劈开多字节字符产生非法 UTF-8，PostgreSQL 以 SQLSTATE 22021 拒绝并**丢弃整行**。

这是 2026-06-11 事故（glm-5.1/minimax/doubao 整行丢失）的成因。仓库当时新增了安全的 `truncateText` 并在注释中写明事故编号，**但 5 个调用点仍在用字节切片**——修复没有推广到同类，一个月后被再次发现。

用 `streaming.truncateText` 或 `executors.truncateUTF8`。

> 这也是规则 3.3 的推论：**修好一处后必须搜索同类**。



### 规则 4.1　基线对照——归因前先在干净 base 上复现

任何"测试失败 / 格式不对 / 这里本来就是坏的"的断言，**先 `git stash` 到干净 base 复现一次**。

本次三次基线对照的结论：

- `domains/credential` 2 个测试失败 → 干净 main 上同样失败 ⇒ 非我引入
- `gofmt` 报 3 个文件 → 干净 main 上同样未格式化 ⇒ 非我引入，**且不顺手修**

> 不做基线对照，会把既有问题算作自己引入（浪费时间），或把自己引入的算作既有（放过真 bug）。

### 规则 4.2　一次提交一件事

`web/public/menu-config.json`（仅 `exported_at` 时间戳变化）是会话开始前既存的无关改动，**全程未纳入任何提交**。

混进去会让这次修复**无法单独 revert**——而数据丢失类修复恰恰最需要保留干净的回滚能力。

### 规则 4.3　改签名前先全仓搜调用点

`sanitizeJSONField` 加参数前，先搜出全部 5 处调用点（含 2 处测试）确认影响面封闭。

### 规则 4.4　修复要溯源，不要就地打补丁

本案真正的修复不是"把扫描器改对"，而是意识到：**修复启发式被无条件地作用在健康数据上**。

```go
// 本质修复：只对本就非法的 JSON 施加修复
if json.Valid([]byte(cleaned)) {
    return cleaned          // 合法数据必须原样穿过
}
// 以下才是修复路径
```

> 只改扫描器 = 症状修复，下一个字符组合照样出事。
> 加 `json.Valid` 快速路径 = 根因修复，**整类问题消失**（连带修好了另外 7 个 JSONB 字段）。

## 五、收口检查清单

提交前逐条确认（未通过则不提交）：

- [ ] **前提有证据**——修复针对的场景，有 SQL / 标准库调用 / 真实日志佐证
- [ ] **真实依赖验证过**——涉及 DB/协议/编码的，过了真实 cast/解析
- [ ] **有不变量测试**——"健康输入必须存活"，不只是"坏输入被处理"
- [ ] **新测试在旧代码上失败过**——已实际验证，非推测
- [ ] **手写索引运算有模糊测试**——固定 seed
- [ ] **所有丢弃/降级分支有日志 + anomaly 记录**——记尺寸不记内容（规则 3.4）
- [ ] **字符串截断按 rune 不按字节**（规则 3.5）
- [ ] **成对函数行为一致**——已搜索同类缺陷
- [ ] **失败项做过基线对照**——已确认是否为既有问题
- [ ] **无范围蔓延**——无关改动未混入
- [ ] **改签名的全仓搜过调用点**
- [ ] **修的是根因不是症状**——能说清"为什么整类问题消失了"

## 六、AI 协作的红线

| 现象 | 含义 | 应对 |
|-----|------|------|
| "测试全绿" | 只说明代码符合它的假设 | 回到规则 1.1，验证前提 |
| "这个改动很小" | 本案根因就是一个 20 行的辅助函数 | 越小的改动越要看清数据流 |
| "顺手把 X 也修了" | 破坏可回滚性 | 规则 4.2，另起提交 |
| "之前的测试有问题，我改一下" | **最危险信号**——可能在删证据 | 先在旧代码上确认测试的原意 |
| 同一问题第 3 次修复 | 前提或架构错了，不是实现错了 | 停止打补丁，回到规则 1.3 取真实数据 |
