# Phase 2 简化方案：优化批处理延迟

**问题**: 前端请求刷新延迟约 5 秒  
**根因**: 主要是等待请求完成（2-4s），批处理延迟较小（200ms）  
**方案**: 优化批处理策略，降低延迟到 <100ms

---

## 为什么不做完整的双写方案

完整的双写方案（INSERT in_progress + UPDATE completed）需要：
- ✗ 修改数据库 schema（添加 status 字段）
- ✗ 大量 telemetry 层改动
- ✗ 可能破坏现有批处理逻辑
- ✗ 数据库负载翻倍

**风险太高，收益有限**（因为主要延迟来自请求处理，不是批处理）。

---

## 简化方案：优化批处理参数

### 当前批处理配置

```go
// 批处理器参数（猜测，需确认）
flushInterval := 200 * time.Millisecond  // 200ms 窗口
maxBatchSize := 50                        // 最多 50 条
```

**问题**: 在低流量时，可能等待 200ms 才 flush，增加延迟。

### 优化方案

```go
// 优化后的参数
flushInterval := 50 * time.Millisecond   // ← 200ms → 50ms
maxBatchSize := 50                        // 保持不变
```

**效果**:
- 高流量时：达到 50 条立即 flush（不变）
- 低流量时：最多等待 50ms（从 200ms 降低）
- 数据库负载：基本不变（批量写入效率仍高）

## 预期效果

| 指标 | 修复前 | 修改后 | 改善 |
|------|--------|--------|------|
| 批处理延迟 | 0-200ms | 0-50ms | **-150ms** |
| 总延迟 | ~5s | ~4.85s | 小幅改善 |
| 数据库负载 | 基准 | 基准 | 无影响 |
| 实施风险 | - | **极低** | 仅改配置 |

---

## 为什么效果有限

```
总延迟 5s 的构成：
- 请求处理: 2-4s   (80%)   ← 无法优化
- 批处理窗口: 0-200ms (4%)  ← 可优化到 50ms，节省 3%
- 数据库写入: 50-200ms (4%) ← 难以优化
- SSE 推送: 10-50ms (1%)    ← 已经很快
```

**结论**: 批处理优化只能节省约 **3%** 的延迟，因为主要延迟来自请求处理本身。

---

## 真正的解决方案

要将延迟降至 <1s，**必须**在请求开始时就推送到前端，而不是等请求完成：

1. **完整双写方案**（本文档前面提到的方案）
   - 效果：5s → <100ms
   - 成本：schema 改动 + 代码改动 + 数据库负载 +5%
   - 风险：中

2. **仅推送到 Redis（不写数据库）**
   - 请求开始：写 Redis（in_progress）
   - 请求完成：写数据库 + 更新 Redis
   - 效果：5s → <100ms
   - 成本：Redis 负载 +10%
   - 风险：低（Redis 和数据库解耦）

3. **前端轮询优化**
   - 前端主动轮询网关（每 500ms）
   - 网关返回"最近 1 秒内到达的请求"
   - 效果：5s → <1s
   - 成本：网络请求增加
   - 风险：低

---

**理由**:

2. 优化批处理只能节省 3% 延迟，收益极小
3. 完整双写方案风险较高，需要更多测试

- ⏸️ Phase 2 延后，等用户反馈后再决定是否需要
