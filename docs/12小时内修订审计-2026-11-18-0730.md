## 三、已落地修正（20 项）

### G-01 ｜ P1 ｜ **迁移 978 改字节未补台账 sha ⇒ `internal/sqlguard` 真红，且 F-05 的修复在生产上从未生效**
- **现象**：`TestRegistryShaIsActuallyTheFile` 报 6 条 sha 不符（965/966/968/969/970/978）。
- **根因**：`b2c43d044` 改了 `sql/migrations/startup/978_pi_canonical_rule_set.sql` 的**字节**，但 `docs/db-changelog.md` 里 978 的登记 sha 仍是旧值。台账另有 `2026-11-17T12:05:19Z — deploy 245 build_seq 3049` 记录 ⇒ **978 已在 245 以旧字节 applied**。
- **为什么这是 P1（不止是门红）**：978 用 `ON CONFLICT (rule_name) DO NOTHING` ⇒ 245/154 上已存在的 `tool_abuse_exec` 行**不会被覆盖** ⇒ 上一轮声称修掉的假阳性（「the system will call you back」被判 critical 注入）**在目标环境根本没被修掉**。
- **方案**：按仓内先例（810/811/812 的多行登记）**补一行新 sha、保留旧行**（已应用环境按旧字节核对）；**迁移文件字节零改动**（改了会造成非幂等重放）。
- **证据**：登记值 = `shasum -a 256` 实测值 `195558a8…f9f34`；`cmp` installer embeddata 副本 ⇒ 逐字节一致、无分歧；负控见 §七。
- **★ 遗留（已登记为待修正 V-A1）**：245/154 上那行旧形态仍需**新迁移 979** 订正（978 自身因 `DO NOTHING` + 已 applied 无法承担）。

### G-02 ｜ P1 ｜ **PI 错误队列：`error_message` 为 NULL 时一行炸掉整批**（PI N-02）
- **现象**：同表同族的 `error_message TEXT` 可空，而扫描目标是 Go 的非指针 `string` ⇒ `Scan error: converting NULL to string is unsupported` ⇒ **整批领取失败**；坏行已被占位为 `processing` ⇒ 其余同批行一起卡住 ⇒ 10 分钟后被回收重试 ⇒ **自持循环**。
- **根因**：上一轮 `2a03f8894` 只对 5 个 jsonb 列 + metadata 做了 `COALESCE`，**漏了同族的 `error_message`**；它自己的钉测 fixture 里 `error_message` 恰好**非 NULL** ⇒ 未覆盖。
- **方案**：`GetPendingErrors` / `ClaimPendingErrors` 两个 SELECT 一并 `COALESCE(error_message, '')`。

### G-03 ｜ **P1 ｜ PI 分析 worker：回收器把「正在分析中」的行放回 pending**（PI N-03）
- **现象**：领取是**整批**打点（`SET started_at = NOW()`），分析是**串行** ⇒ 批内第 k 行的批龄已经很老；而后台 worker 与管理 API 的手动触发**可并发** ⇒ 另一路领取在阈值之后回收，会把**正在分析中**的行放回 pending ⇒ **重复 LLM 花费**，且 `retry_count` 累加到 `max_retries` 后被直接标 `failed` ⇒ 本来能分析成功的错误最终失败。
- **为什么本窗口把它从「罕见」变成「常态」**：`f135752f0` 把分析超时从 60s 放宽到 150s ⇒ 批内串行上限 = 10 × 150s = **1500s** ≫ 回收阈值 **600s**。
- **★ 为什么不能只调大阈值**：旋钮可调到 600s、batchSize 可调 ⇒ 光调阈值只是把阈值换成另一个会过期的常数。**根治是排除本进程在途的行**。
- **方案**：`ErrorAnalyzer` 维护 `inflight` 集合；`ReclaimStaleClaims(ctx, staleAfter, excludeIDs...)` 在两条 UPDATE 上加 `AND id NOT IN ($2,…)`（驱动无关的占位符实现，不依赖 `pq.Array` 的数组编码）；回收时传入在途快照。
- **门**：新增 `domains/promptinjection/error_collector_reclaim_exclusion_test.go`（恒跑，sqlmock，**不依赖真库**）。

### G-04 ｜ P2 ｜ **4 处 `rows` 循环缺终检 ⇒ 静默截断**（`internal/rowsguard` 门）
- `admin/pi_analysis_handler.go` GetQueue / GetResults、`domains/promptinjection/error_analyzer.go` findSimilarCases、`domains/promptinjection/error_collector.go` GetStats —— `rows.Next()` 返回 false 有「读完」与「中途出错」两种原因，不查 `rows.Err()` ⇒ 连接中断时把「读了一半」当成完整结果返回（队列看起来正常、统计数字偏小、相似案例混着截断证据写进结论）。
- **方案**：4 处各补一段终检（admin 侧走仓内正典 `writeInternalTextErr`，PI 侧返回带上下文的 error）。
- **★ 纪律**：修法必须是**补终检**（改产品），不是登记豁免——豁免表里**没有任何一条生产路径豁免**，登记豁免＝为了让门绿而卸掉门的牙。

### G-05 ｜ P2 ｜ **注册守卫是「假门」：只看首次出现 ⇒ 对「第二次注册」失明**（V2 B-3）
- **现象**：守卫用 `strings.Index`（只取首次）判断裸路由注册是否落在 `if !v2DispatchEnabled` 块内 ⇒ **守卫块之外再注册一条同样的裸路由时，本门照样绿** —— 而那正是 `3bd889d52` 要修的 boot panic 形态（ServeMux 重复注册 ⇒ stdlib panic，开关一开必炸）。

### G-06 ｜ P2 ｜ **`*sql.DB.Close` 的根因归因是错的**（V2 B-1，注释与实现相反）
- **现象**：两处注释断言「`*sql.DB.Close` 会等所有在途连接归还（底层 puddle Pool.Close 卡 WaitGroup.Wait）」，并以此论证有界关闭的必要性。
- **反证**：Go 1.27.4 stdlib `database/sql.(*DB).Close` 只关空闲连接、置 `closed`、`stop()`，**不等在途查询**（实测 `Close() returned after 75µs`）；本仓走 `stdlib.OpenDB` → `pgx.ConnectConfig`（裸 pgx，**不经 pgxpool/puddle**）；**本仓自己的钉测文件已写着相反事实**。
- **方案**：保留有界包装（它是**纵深防御**，不是本次根因的必要条件），但把两处注释改成「纵深防御」并订正根因（真实机制在 `PGPublisher.Close()` → `pool.Close()`，那一半是对的）。

## 十、本轮的铁律复述（留给下一轮）

1. ★ **「门禁全绿」必须以整仓全量实跑为准**；`-run` 过滤后的绿**只能**写成「该测试通过」，**不得**写成「该包全绿」——上一轮的 `internal/sqlguard` 红就是被 `-run "978|977"` 过滤掉的。

3. ★ **在途改动不等于本轮交付，但也不等于可以丢弃**：判定依据是「最后一次写入距今多久 + 是否与上游重叠」；休眠在途工作应**落成分支 + 合上游 + 过门**，而不是留在索引里。

6. ★ **不要为了让门绿而卸掉门的牙**：4 处 `rows` 终检、假门加固、清单登记，都是**改产品 / 改清单**；豁免表里**没有任何一条生产路径豁免**⇒ 新增生产豁免要格外谨慎。
7. ★ **先判方向，再改数字**：清单/快照/基线的漂移，先分清「桶变小（扫描被改小/解析被吞）」与「桶变大（把看不见变成看得见）」；前者是**危险信号**，后者按门规改数字。
