## 二、修复明细

### 2.1 R50-B1/B2 — 数据填充补齐 + 两道防线

**补齐**：临时一次性工具（`cmd/tmp-baseline-sync/`，用完经可恢复删除移除）调官方入口
`bg.LoadEmbeddedBaselineCatalog()` + `bg.SyncBaselinePricesToDB()`（与网关
`RunBaselinePriceSync` 内部 `run()` 同一函数）。`written=16/16`。
幂等实测：第二遍前后指纹 `66e09ee00e09664301fc67707aa937ec` 不变。

★ 同步循环是「排序后逐条写、validate 不过就 `return` 中途退出」，本会造成部分写入；
  核掉风险：`LoadEmbeddedBaselineCatalog` 在**写入前**已对同一批数据全量 validate，
  该路径实际封闭。

**防线 A** — `bg/baseline_price_single_writer_test.go`（纯静态、每次 `go test ./bg/` 都跑、不需库）

| 判据 | 守什么 | 变异 |
|---|---|---|
| `TestBaselinePriceHasExactlyOneWriter` | 全仓只有 `bg/pricing_baseline_sync.go` 能写这族列 | M2 造第二个写入方 ⇒ 🔴 |
| `TestCanonicalBaselineWriterSetsEveryColumn` | 该唯一写入方 SET 子句覆盖全部 9 列 | M1 删 `cache_write` 一行 ⇒ 🔴 |

★ **两条必须都钉**：只钉「唯一」不够 —— 删掉 SET 子句里的 `cache_write`，
  第一条仍绿。实测 M1 正是该形态（第一判据 🟢、第二判据 🔴 并点名列），
  证明两条信号独立。还原后 md5 `1733c90c2827cf012f7e70f9da7fcc3c` 逐字节一致。

**防线 B** — `bg/baseline_price_ssot_parity_realdb_test.go`（SSOT ↔ 真库双向逐字段）

与 A 失效方向不同：A 防「另开写价路径」，B 防「库里的值已不是 SSOT」。
★ 要紧的不是比对逻辑而是**非恒真守卫**：集成门的一次性新库由迁移+种子长出，
种子不带基准价（`sql/schema/` 下无任何文件写 `baseline_input_price_per_1m`），
在那里跑本条会「0 行可比」。若报 PASS，读数与「逐条比对过且一致」完全同形。
故三种「跑不了」**全部具名 SKIP**，只有真比对了才可能 PASS：

| 情形 | 行为 |
|---|---|
| 未设 `TEST_DATABASE_URL` | SKIP：「需要已跑过同步的库；在未同步的库上会比对 0 行，那不是通过是没比对」 |
| 无 `models_canonical` 表 | SKIP：「跑不了」不是「通过」（初版用 `t.Fatalf`，实测在夹具库上因 42P01 变红——因环境而红是噪声，只训练人忽略红色，已改） |
| 表在但 0 行带基准价 | SKIP：「本条没有比对任何东西」 |
| 有可比集 | 双向比（SSOT→库、库→SSOT、缺行），不一致即红并指名字段 |

真库实测 PASS：「比对了 16 个库内模型 × 9 个字段」。

## 四、遗留风险

1. **上游 canonical-delivery 门红 6 条且在扩大**（4→6，轮内又多了 840/841）。只要对方继续加迁移而不登记升级通道，`pre-commit-check` 就保持 FAIL=1，后续任何提交都得走 `--no-verify`。**这是本仓当前最影响协作节奏的债**，且处置方式（四选一）需要迁移属主拍板，不该由旁路会话代决。
2. **`baseline_*_price_per_1m` 仍无计费消费者**。缓存写入价已正确入库，但计费路径没读它 ⇒ 今天不影响钱；等接线那天，缺列就会变成真实少算。防线 A/B 只保证「库里的值 == SSOT」，不保证「SSOT 的值被用上了」。
3. **防线 B 依赖人工指定真库**。它不会在集成门里有牙（那里 0 行可比 ⇒ 具名 SKIP）。若要常态化，得把它接进会在真库运行的检查器，或在门禁清单里显式登记这条命令，否则它的价值取决于有人记得跑。
4. **`_manual_notes` 与 `_comment` 无任何代码解析**——纯人读文档，不构成强制。SSOT 里 `minimax-m3` 的三个旁证目前靠注释承载，无机器校验。
5. **本轮 handoff 与 changelog 都在 main 上，而 origin/main 每小时都在被其他会话推进**（本轮合并前就落后 99 提交）。任何基于读数的结论都有时效，本文件记录的读数带时刻（2026-10-07 17:45）。
