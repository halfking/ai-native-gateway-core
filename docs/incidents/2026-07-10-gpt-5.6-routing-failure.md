## 三、根本原因

### 3.1 问题链

```
1. credential 2 的 availability_state = 'auth_failed'
   ↓
2. discovery.go 要求 availability_state = 'ready'
   ↓
3. credential 2 被过滤，不进入候选池
   ↓
4. gpt-5.6-* 三个模型全部依赖 credential 2
   ↓
5. 路由器报告"无可用候选节点"
```

### 3.2 为什么视图认为可路由？

**v_routable_credential_models 视图定义**:
```sql
WHERE ...
  AND CASE
    WHEN c.availability_state = 'unavailable' THEN 'availability_unavailable'
    ELSE NULL
  END AS unavailable_reason
```

**视图只过滤 `availability_state = 'unavailable'`**，不过滤 `auth_failed`。

**但 discovery.go 代码要求精确匹配 `= 'ready'`**。

### 3.3 为什么是 auth_failed？

**检查 credential 2 详情**:
```sql
SELECT id, label, last_probe_at, last_probe_success, 
       probe_consecutive_failures, availability_state
FROM credentials
WHERE id = 2;
```

**结果**:
```
id | label   | last_probe_at | last_probe_success | probe_consecutive_failures | availability_state
---+---------+---------------+--------------------+----------------------------+-------------------
2  | gpt key | NULL          | NULL               | 0                          | auth_failed
```

**分析**:
- `last_probe_at = NULL` → 从未进行过 probe
- `availability_state = auth_failed` → 可能是创建时的默认状态或历史遗留

**可能原因**:
1. credential 创建时验证失败
2. 历史上某次 API key 失效
3. 后来 API key 已恢复，但状态未更新

## 四、修复方案

### 4.1 立即修复 (已执行)

**SQL**:
```sql
UPDATE credentials 
SET availability_state = 'ready',
    state_reason_code = NULL,
    state_reason_detail = NULL,
    state_updated_at = now()
WHERE id = 2;
```

**验证**:
```sql
SELECT credential_id, raw_model_name, is_routable
FROM v_routable_credential_models
WHERE raw_model_name LIKE 'gpt-5.6%';
```

**结果**: ✅ 3 个模型全部 `is_routable = true`

**discovery 过滤验证**:
```sql
SELECT c.id, c.label, c.availability_state
FROM credentials c
JOIN providers p ON p.id = c.provider_id
WHERE c.status = 'active'
  AND c.availability_state = 'ready'
  AND c.id = 2;
```

**结果**: ✅ credential 2 现在满足所有条件

### 4.2 为什么直连可行？

**推测**:
- 用户直连时使用的是真实的 API key
- API key 本身是有效的
- 只是 gateway 中的状态标记错误

**验证建议**:
1. 触发一次 credential test: `POST /api/credentials/2/test`
2. 观察 probe 结果，确认 API key 确实有效

## 五、长期改进建议

### 5.1 视图与代码不一致

**问题**: `v_routable_credential_models` 视图的过滤条件与 `discovery.go` 不一致。

**视图**:
```sql
WHEN c.availability_state = 'unavailable' THEN 'availability_unavailable'
```

**代码**:
```go
AND c.availability_state = 'ready'
```

**建议**: 统一过滤逻辑
```sql
-- 视图应该改为
WHEN c.availability_state != 'ready' THEN 'availability_not_ready'
```

### 5.2 自动健康检查集成

**刚刚实现的 routing_health_checks 系统可以检测这类问题**！

**新增检查规则** (建议):
```go
func availabilityNotReadyCheck() HealthCheckDef {
    return HealthCheckDef{
        CheckID:  "availability_not_ready",
        Severity: "critical",
        Query: `
            SELECT c.id, c.label, c.availability_state, COUNT(cmb.id) AS binding_count
            FROM credentials c
            JOIN credential_model_bindings cmb ON cmb.credential_id = c.id
            WHERE c.status = 'active'
              AND c.lifecycle_status = 'active'
              AND c.availability_state != 'ready'
              AND cmb.available = TRUE
            GROUP BY c.id, c.label, c.availability_state
            HAVING COUNT(cmb.id) > 0
            ORDER BY COUNT(cmb.id) DESC
            LIMIT 50`,
    }
}
```

**修复 SQL**:
```sql
UPDATE credentials 
SET availability_state = 'ready',
    state_reason_code = NULL,
    state_reason_detail = NULL,
    state_updated_at = now()
WHERE id = {credential_id}
  AND availability_state != 'ready'
  AND NOT EXISTS (
    SELECT 1 FROM model_probe_state mps
    WHERE mps.credential_id = {credential_id}
      AND mps.state IN ('broken_confirmed', 'degraded')
  );
```

### 5.3 probe 机制改进

**问题**: credential 2 的 `last_probe_at = NULL`，从未进行过健康检查。

**建议**:
1. 新创建的 credential 自动触发首次 probe
2. 定期 probe 所有 active credentials
3. probe 失败时更新 availability_state，成功时恢复为 'ready'
