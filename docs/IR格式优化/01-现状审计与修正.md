# 现状审计与修正

## 1. 审计结论

现有 IR 已可靠覆盖 OpenAI Chat Completions 与 Anthropic Messages 的主要文本、thinking、tool call 和 SSE 转换，但不能据此宣称支持所有供应商协议或完整多模态。原方案存在以下阻断性问题。

## 2. P0 问题

### 2.1 Extensions 方向错误

`domains/transformation/ir_transport.go` 在请求阶段提取 `TransportContext.Extensions`，但序列化上游请求后没有恢复；响应阶段反而把同一 bag 合并到客户端响应。结果是：

- 未知请求字段不会可靠到达上游。
- 请求专用字段可能污染响应。
- header 已提取但没有在该路径重新应用。
- `InternalRequest.Extensions` 与 `TransportContext.Extensions` 重复且语义不一致。

**修正**：拆分为方向明确的 `RequestUnknown`、`ResponseUnknown`、`UpstreamHeaders`。仅在源/目标 wire-compatible 且字段通过 provider policy 时恢复请求扩展。响应扩展只能来自上游响应。

### 2.2 Responses 输入被错误降级为 Chat

`ParseOpenAI` 只解析 `messages`。`/v1/responses` 当前先把 `input[]` 转成 Chat messages；`function_call`、`function_call_output`、`input_image`、`input_file`、item reference 等 item 会被错误变为空 user message。

**修正**：新增独立 `ParseOpenAIResponses`/`SerializeOpenAIResponsesRequest`。IR 保留有序 item，不再通过 `convertResponsesToChatBody` 作为规范路径。

### 2.3 热表迁移设计不安全

原方案只给 `request_logs` 增列，但运行时写 `request_logs_hot`，并存在 `SELECT * UNION ALL`、promotion function 和分区列顺序依赖。只改父表会导致写入、union view 或晋升失败。

**修正**：任何日志 schema 迁移必须同时处理父表、hot 表、附着/脱离分区、telemetry INSERT、promotion function 和 union view，并改为显式列清单。

### 2.4 多模态会被重复计费

当前图像估算值已计入 `prompt_tokens`。原方案又把 `image_tokens` 加到基础 prompt cost 上，会重复收费。供应商返回的 modality detail 也通常是总 input/output token 的拆分，不应默认再次相加。

**修正**：usage metric 必须携带 `included_in_total` 和来源；结算规则按 rate component 决定使用 aggregate 还是 detail，禁止二者同时收费。

### 2.5 固定八列无法表示原厂计费

供应商可能按 token、image、tile、second、character、request、service tier 或 context tier 计价。`credits_per_1m_image_*` 等列无法表达这些单位，也无法管理价格生效时间。

**修正**：采用版本化 rate component 表，字段至少包括 metric、direction、unit、currency、rate、scale、region、service tier、effective interval。

### 2.6 供应商成本与租户 credits 被混淆

`Candidate.CalcCost` 计算供应商货币成本；`model_credit_rates`/`CalcCredits` 计算租户 credits。扩展其中一条链不会自动影响另一条。

**修正**：保留两套 rate card 和 calculator，共享 canonical usage metrics，并各自保存计算快照。

### 2.7 Ledger 类型提议无效

现有 CHECK 不接受 `multimodal_consume`，运行时还写 `credit_ledger_hot`。

**修正**：继续使用 `entry_type='consume'`，通过 request-linked charge detail 保存多模态明细，不扩展 entry type。

## 3. P1 问题

### 3.1 图像并非完全无损

OpenAI `image_url.detail` 会影响处理和成本，但 `parse_openai.go` 明确丢弃该字段，顶层 Extensions 也无法保留嵌套字段。

**修正**：将 detail 纳入 canonical media options，并为嵌套 provider annotations 提供 raw JSON。

### 3.2 Responses 流式现状描述不准确

当前代码已产生 output item、content part、text/reasoning/tool delta 等事件，不只是 created/in-progress/completed。真实缺口是 assembler 无法保证 tool-only/mixed 输出的 item index、done event 和最终 `response.completed.output` 一致。

**修正**：实现按 output item 和 content part 建模的有状态 assembler。

### 3.3 `stream_options.include_usage` 不是单纯缺失

主执行路径会强制注入 `include_usage=true`，因此不是“漏 usage”，而是：客户端意图丢失、未知协议也可能被注入、usage detail 未归一化。

**修正**：分离 `ClientStreamOptions` 与 `GatewayAccountingOptions`，仅由 Adapter 决定上游字段。

### 3.4 `modality` 单枚举不足

精确等值过滤无法表达 image+audio、text+document 等集合，也无法让 `multimodal` 自动满足 `vision`。

**修正**：model 和 offer 保存 input/output capability sets；旧 `modality` 由 capability 派生。

### 3.5 原生协议缺少运行时 dispatch

catalog 可以出现 `gemini-generate`、`ollama-native`，但 capability resolver 和 executor 基本只有 Anthropic/OpenAI 两路。只新增 parser 和 URL 不会让协议真正工作。

**修正**：Protocol Adapter 同时负责 codec、URL、auth、stream、usage、probe 和 capability。

### 3.6 文档/文件结构重复

现有 IR 已有 `Documents`、`PDFDocument`、`PDFSource`、RawContent。继续新增 FileSource/DocumentBlock 会产生多套 PDF 表达。

**修正**：统一到 `MediaPart`/`AssetRef`，document 是语义 kind，PDF 是 MIME type。

## 4. 原厂事实修正

| 原方案说法 | 修正后结论 |
|------------|------------|
| OpenAI image 普遍按固定每张价格 | vision 通常转为模型相关 token；规则随模型/detail/尺寸变化 |
| OpenAI chat audio 只走 `/v1/audio/*` | 支持 `input_audio`；音频输出使用 `modalities` + `audio` |
| Anthropic system 支持 document | system 仅文本块；image/document 位于 message content |
| Anthropic 有统一 image token 单价 | image/PDF 通常计入所选模型 input token，无统一 image rate |
| Gemini 所有多模态统一同价 | 价格依 model、modality、tier、context、cache 等变化 |
| Qwen/GLM 有统一固定图像价格 | 必须绑定准确 SKU、区域、单位和生效时间，不能泛化 |
| Ollama `/api/chat` 使用 SSE | 默认是 NDJSON；最终对象含 eval count 和 duration |
| Ollama chat 支持 raw/template/context | 这些主要属于 `/api/generate`；`/api/chat` 字段不同 |
| `previous_response_id` 要求网关存状态 | 通常由 OpenAI 持有状态，网关只需无损转发语义 |

## 5. 可信现状

- OpenAI Chat 与 Anthropic Messages 主路径可用，但不是完全无损。
- DeepSeek、GLM、Qwen、MiniMax 多数走兼容协议和私有字段处理，不等于原生协议支持。
- Gemini 原生 `generateContent` 和 Ollama 原生 `/api/chat` 尚未形成完整 adapter。
- 图像 URL/base64 已有基础转换；audio/video/document/file 未形成统一模型。
- usage 目前主要覆盖 text/cache totals，无法稳定表达 modality detail 和计费单位。
- 现有 strip provider fields 可能删除有价值的 usage/reasoning 信息，后续应改为内部保留、客户端按策略投影。
