### F-10 ｜ **P0** ｜ PI 的「拒绝」判定到不了客户端（拦截形同虚设）
- **现象**：PI 判官把请求判为 reject/block 之后，**客户端照常拿到 200 并被正常服务**。
- **根因（两条独立事实，都对着实现核过）**：
  1. `domains/hooks/promptinjection/hook.go` 的 `OnError` 只写 `env.StatusCode`（403/410/202）并**吞掉错误**（返回 nil）⇒ 管线继续；而 `cmd/gateway/main_pipeline.go` **从不读** `env.StatusCode`（全仓只有 `cmd/gateway-v2/main.go:580` 读，那是独立的 `/v2/*` 命名空间）⇒ **判定丢失**。
  2. 拦截决策只由 `governance_interception` stage 产出，而该 stage 的注册序在 `provider_discovery` **之后**；`provider_discovery` 挂在**内存 demo 凭据仓**（只种 gpt-4 / gpt-3.5-turbo）上，对任何真实模型恒报「no healthy provider」⇒ 管线在此中止 ⇒ **真实流量永远到不了决策闸**，中止前写下的 deny verdict 被丢弃。
- **方案与合理性（三处改动，都不改变「基础设施故障不阻断 v1」这条既有契约）**：
  1. **PI hook 写显式标记**（`prompt_injection_verdict` / `prompt_injection_blocked`），而不是只靠 `env.StatusCode` —— 后者是通用字段，用它当判据等于依赖「只有 PI 会写它」这个隐含约定。
  2. **dispatch 层新增 PI 专属闸**（`promptInjectionGate`）：在落到 v1 fallback **之前**写响应并终止。用显式标记做判据 ⇒ 不依赖隐含约定。
  3. **治理决策收口**：管线中止后若 `Decision` 尚未产出，用**同一个** interception 引擎（同一套阈值/规则）基于已收集的 verdict 补做一次决策 ⇒ 决策闸对真实流量重新可达。
- **为什么不移动 stage 注册序**：移动 `governance_security` 会让 V4 安全插件**开始对真实流量生效**（真实流量的拦截口径整体变化）⇒ 属语义级变更，已登记为 §四·V-01 独立一轮。收口决策在**不动注册序**的前提下达成同一目标，行为面可控。
- **反向钉子（重要）**：普通阶段故障（无 deny verdict）**不得**被本轮修正变成拦截 —— R1.12 既有安全契约「stage error 不阻断 v1 处理」保持不变，已有钉测 `TestV2Dispatch_PipelineErrorDoesNotBlockFallback` + 本轮新增 `TestV2Dispatch_NonBlockingPipelineErrorStillFallsBack`。
- **验证（实跑）**：
  ```
  go test ./cmd/gateway/ -run "TestV2Dispatch_PI|TestV2Dispatch_GovernanceDecisionAfterPipelineAbort|TestV2Dispatch_NonBlocking" -count=1
  ```
  实跑日志：`v2 dispatch gate: short-circuit ... status=403 decision_kind=block`；fallback 调用计数 = **0**。新增钉测文件 `cmd/gateway/pi_verdict_reachability_test.go`（3 条）。

### F-12 ｜ P1 PI ｜ LLM 判官的端点解析器**从未接线** ⇒ 判官层从不产出结论
- **现象**：`LLMDetectionEngine.SetEngineResolver` 零生产调用方 ⇒ `resolver` 恒 nil ⇒ 每次判官调用都返回「endpoint resolver not wired」；又因 `llm_detection_fail_closed` 默认 false ⇒ 只落一条 Warn 就继续用规则分放行 ⇒ **L6 层形同虚设且无痕**。
- **方案与合理性**：新增 `cmd/gateway/pi_engine_resolver.go` 实现 `promptinjection.EngineResolver`，并在检测器构造处接线。解析口径全部对着正典表，**不编造**：

### F-13 ｜ P1 PI ｜ 采集器在默认形态下**无生产者**，而「空队列」与「没有生产者」不可区分
- **现象**：PI 错误采集的**唯一生产者**是 `promptinjection.Detector`（`d.collectError`），而检测器只在 `LLM_GATEWAY_USE_V2_PIPELINE`（**默认关**）开启时才被构造 ⇒ 默认形态下队列**恒为空**，运维会把它读成「没有错误发生过」。
- **方案与合理性（本轮只做「可辨识」，不做架构变更）**：`/api/admin/pi-analysis/stats` 增返回 `collector_enabled` / `detection_chain_wired` / `chain_status`（**稳定状态码** `wired` / `not_wired`）；前端据此显示专门横幅（而不是一张空表）。**文案不在后端给**：后端给中文会让非中文界面拿到中文，也会让文案有两份真值 ⇒ 后端只给状态码，展示文案走 i18n（`common.piAnalysis.*`，8 语种）。**为什么不在本轮把生产者接进 v1 路径**：那等于在**默认生产形态**开启 PI 检测（改默认行为），属架构级变更 ⇒ 登记为 §四·V-02。
- **验证**：`go build ./...` 绿；`admin` 包测试绿。

### F-14 ｜ P2 PI ｜ 审计证据按**字节**截断 ⇒ 切断 UTF-8 多字节字符 ⇒ 整行审计不可用
- **现象**：`domains/promptinjection/detector.go` 的 `extractEvidence`（`evidence[:500]`）与 `createApprovalRequest`（`inputPreview[:200]`）按字节切 ⇒ 中文/emoji 载荷被切成半个字符 ⇒ 写进 `prompt_injection_detections.evidence` / 审批单预览后，读取侧 JSON 解析失败、整行审计不可用。
- **方案与合理性**：改用仓内**已有**的 rune-safe 原语 `truncateUTF8Bytes`（`pi_agent_helpers.go:41`，同族先例：`error_analyzer.go:338-339` 已经用它）。
- **验证**：`go build ./...` 绿；`domains/promptinjection` 包测试绿。

### F-15 ｜ P2 ｜ `Syncer.Backoff()` 是死代码，文档承诺的「失败退避」从未实现
- **现象**：`internal/securitypattern/sync.go` 的 `Run` 用**固定 ticker**（`time.NewTicker(interval)`），`Backoff()` 从未被调用；而 `Run` 的文档注释却写「失败时按 errorBackoff 退避」⇒ **注释与实现不符**（共享域长期不可达时仍按固定间隔反复打满它）。
- **方案与合理性**：改成**可重置的 timer**：一次同步失败后等待 `max(interval, Backoff())`，成功一次即回到 `interval`。取 max 的理由：失败后**不能**比正常间隔更快地重试（否则比固定间隔更糟）；`Backoff()` 随连续失败次数拉长（上限 10 分钟），第 3 次失败起开始生效。
- **验证**：`go build ./...` 绿；`internal/securitypattern` 包测试绿。

### F-16 ｜ P2 ｜ 安全事件出网 sink 关闭时**不排空**，已入队的事件被静默丢弃
- **现象**：`internal/securityevent/sink.go` 的 `worker` 在 ctx 取消时立刻 `return` ⇒ 队列里已入队的安全事件（**攻击现场**，不可恢复）全部丢失；而 `Publish` 仍往一个没人消费的队列里塞（计数还涨）⇒ 静默丢失。`cmd/gateway/main.go` 的停机段只调 `cancel`，**从不调** `sink.Stop`。
- **方案与合理性**：
  1. `Stop` 改为**关队列 + 等在途写入**；worker 以「队列关闭且已空」为退出信号 ⇒ 排空后退出。
  2. `Publish` 在关闭后**明确拒绝并计数**（同时用读锁把「查 closed + 入队」与「关队列」互斥 ⇒ 不会 `send on closed channel`）。
  3. 停机顺序改为 **先 `Stop`（排空）后 `cancel`**（顺序反了排空会被 ctx 取消抢先）—— 原注释「cancel 就够了，队列由 worker 在退出前排空」与实现不符，已订正。
- **验证**：`go build ./...` 绿；`internal/securityevent` 包测试绿。

### F-17 ｜ P2 前端 ｜ 「PI 分析」菜单项在无 DB 时点了就是 404 空页
- **现象**：`/api/admin/pi-analysis/*` 只在「有 DB」且「admin 鉴权材料齐备」时注册（后端**有意的 fail-closed**：没有 pool/secret 就无法鉴权，注册裸 handler 等于把内部错误队列敞在公网）⇒ 无 DB / 未配 secret 的部署上，菜单项点了就是 404 ⇒ 菜单在**宣传一个不存在的功能**。
- **方案与合理性**：
  1. 后端**不能**改成「无条件注册」（那会破坏 fail-closed 的鉴权底线）⇒ 由前端如实反映：新增 `web/src/config/piAnalysis.ts` 运行时探测（乐观默认：未探测时照常展示，避免菜单闪烁与计数漂移），探测到不可用 ⇒ **隐藏该菜单项**。
  2. 页面本身在 API 不可用时显示**明确的不可用横幅**（含「这是后端 fail-closed 行为，不是数据为空」的说明），非 2xx 一律显式带状态码判为不可用（此前只 `console.error` ⇒ 运维看到空表分不清「没数据」与「功能不存在」）。
  3. **新增文案一律走 i18n**（`common.piAnalysis.*`，8 语种），不在 `web/src/` 里加硬编码中文 —— 否则会把**已红**的 `hardcoded_cjk` 棘轮（见 §四·N-05）继续推高。
- **连带**：`web/public/menu-config.json` 是**构建产物**（`node scripts/export-menu-config.mjs` 从 appNav.ts 反向同步）⇒ 已重新生成；新增 `web/src/config/piAnalysis.test.ts` 4 条钉测。
