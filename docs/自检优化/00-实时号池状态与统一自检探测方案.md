# 实时号池状态与统一自检探测方案

> 日期：2026-07-18
> 状态：第一阶段已实现，持久队列默认关闭，状态协调接入待后续灰度
> 范围：账号/凭据状态、请求失败切换、自检探测队列、探测模板、测试验收

## 1. 结论摘要

本需求适合实现，但“5ms 内自动熔断”必须拆成两个指标：

1. **同步决策路径**：收到上游响应后，在当前请求 goroutine 内完成错误分类、账号候选剔除和备用候选选择；目标 p99 < 5ms，不把网络探测耗时计入该指标。
2. **异步验证路径**：将账号+模型加入统一自检队列，立即触发一次或多轮探测；探测结果负责确认恢复、延长冷却或升级为永久停用。

不能把所有 429 当作永久封号。必须区分：

| 信号 | 默认处理 | 是否剔除账号 | 是否允许自动恢复 |
|---|---|---:|---:|
| 上游 401/403 + invalid key/revoked/banned | `auth_failed` / `suspended` | 是 | 否，需人工或权威凭据恢复 |
| 429 + balance/quota/budget/account disabled | `suspended` | 是 | 否，需充值、换凭据或人工恢复 |
| 429 + retry-after/rate limit | `rate_limited` | 当前账号短冷却 | 是，按时间或探测成功恢复 |
| 429 + concurrent/overload | `cooling` | 当前模型绑定优先剔除 | 是，短冷却后探测 |
| 网络错误、超时、5xx、空响应 | `cooling`/`unreachable` | 当前账号+模型优先剔除 | 是，探测成功恢复 |
| 客户端 4xx、模型不存在、上下文过长 | 仅模型绑定或请求失败 | 不剔除账号 | 不适用 |

## 2. 当前代码事实

1. `errorsx` 已有 `429`、`401/403`、配额、并发、网络、超时和封禁相关分类，但错误分类和状态更新仍分布在多个调用路径。
2. `ActiveProbeWorker` 已支持 `(credential_id, model)` 去重和多轮 backoff，但只有单 goroutine、内存队列，无 TTL 持久记录，且主要由连续失败触发。
3. `ActiveProbeEmitter` 已将探测结果写入 `request_logs`，可复用实时流观测能力。
4. `unified_probe_scheduler.go` 明确标记为废弃，且曾与旧 worker 竞争写状态；本方案不直接启用它。
5. `docs/2026-07-15-routing-state-probe-capability-unification.md` 已定义 `RoutingStateCoordinator` 方向，但尚未成为所有状态写入的唯一入口。
6. `credentials.availability_state`、`health_status` 和 `credential_model_bindings.available` 已分别承担账号级、观测级和账号+模型级状态职责。

## 3. 目标状态模型

### 3.1 账号级状态

沿用现有合法值：`ready`、`cooling`、`rate_limited`、`auth_failed`、`unreachable`、`suspended`。

- `auth_failed`：上游明确拒绝凭据，禁止自动恢复。
- `suspended`：封号、永久配额、余额耗尽、人工停用，禁止自动恢复。
- `rate_limited`：供应商限流，记录 `recover_at`，到期后进入探测。
- `cooling`：其它瞬态故障，按指数退避和探测结果恢复。
- `unreachable`：网络或上游不可达，账号+模型候选暂时剔除。

### 3.2 账号+模型状态

`credential_model_bindings.available=false` 只表示该账号无法服务该模型，不得因为单模型错误封禁整个账号。绑定失败原因至少包括：

`auth_failed`、`quota_exhausted`、`rate_limited`、`concurrent_overload`、`upstream_5xx`、`timeout`、`model_not_found`、`unsupported_feature`。

## 4. 统一探测队列

### 4.1 队列记录

新增持久化队列表，建议命名 `credential_probe_queue`，每一条记录表示一个账号+模型探测任务：

```text
id, credential_id, provider_id, tenant_id
canonical_model, raw_model, outbound_model
probe_command, probe_mode, priority
status, reason_code, reason_detail
attempt, max_attempts, next_run_at, lease_until
source, parent_request_id, dedup_key
started_at, finished_at, expires_at, created_at, updated_at
result_http_status, result_latency_ms, result_body_preview
```

约束：

- `dedup_key` 唯一，建议为 `credential_id|raw_model|probe_command`。
- `expires_at=created_at+300s`，过期任务不可再执行。
- `status`：`ready`、`running`、`success`、`failed`、`expired`、`cancelled`。
- `source`：`request_failure`、`periodic`、`external_async`、`admin`。
- 外部异步来源必须携带 `source_event_id`，保证幂等。

### 4.2 领取与并发

worker 使用 PostgreSQL 原子领取：

```sql
SELECT id
FROM credential_probe_queue
WHERE status='ready'
  AND next_run_at <= now()
  AND expires_at > now()
ORDER BY priority DESC, next_run_at, id
FOR UPDATE SKIP LOCKED
LIMIT $1;
```

同一事务内更新为 `running` 并设置 `lease_until`。worker 数量由待执行量和全局上限决定；正在 `running` 的记录由原发起方或租约恢复器处理，不重复领取。

### 4.3 租约与恢复

- worker 崩溃后，`lease_until < now()` 的 `running` 记录回到 `ready`。
- 任务完成必须通过统一 `CompleteProbe` 更新状态、写结果和触发状态裁决。
- 任务过期由清理器标记 `expired`，保留审计记录，不物理删除 24 小时内数据。

## 5. 统一探测执行模板

目标是让所有同步、异步、单轮、多轮探测都调用同一服务：

```text
ProbeService.Run(ctx, ProbeCommand) -> ProbeResult
```

`ProbeCommand` 必须明确：

- 目标：credential、provider 或 credential+model。
- 模型：canonical/raw/outbound 三个名称，不允许只传一个模糊 `model`。
- 指令：`models`、`chat_minimal`、`chat_tool`、`chat_stream`、`embedding`、`multimodal`。
- 轮次：`attempt`、`max_attempts`、`timeout`。
- 来源与父请求：用于审计和实时流关联。

第一阶段已将持久队列和旧主动探测 worker 收敛到 `ActiveProbeExecutor.RunCommand`；现有 `NodeProbeWorker` 仍是后续收敛对象，不能在本阶段宣称已经完全统一。模板固定处理：解密凭据、构造请求、发送请求、读取响应、分类错误、生成 `ProbeResult`、写实时观测。

## 6. 请求失败到切换流程

1. 上游响应返回后立即调用 `errorsx.ClassifyResponseBody`。
2. `RoutingStateCoordinator.Decide` 同步计算当前账号和账号+模型的状态变更。
3. 对 `auth_failed`、永久配额和明确封禁，立即剔除账号；对 `rate_limited`、并发和瞬态错误，至少剔除当前账号+模型。
4. 在同一候选循环中选择备用节点；不等待探测网络完成。
5. 同步提交探测任务到 `credential_probe_queue`；入队失败不得阻塞请求切换，但必须记录指标和日志。
6. 其它错误允许短暂等待前端，但等待必须有上限，建议 50-200ms；期间可并行触发多个不同账号+模型探测，不得对同一 dedup key 重复探测。
7. 无可用候选时返回结构化 `no_candidate`，携带 `retry_after` 和 `trace_id`，前端进入 loading/retry 状态而不是白屏。

## 7. 5ms 指标定义

必须分阶段埋点：

- `error_classify_ms`
- `state_decide_ms`
- `candidate_exclude_ms`
- `fallback_select_ms`
- `probe_enqueue_ms`
- `request_failover_ms`
- `probe_network_ms`

验收目标：

- `error_classify + state_decide + candidate_exclude + fallback_select` p99 < 5ms。
- `probe_enqueue` p99 < 5ms；队列写入失败降级为内存 best-effort 并告警。
- 网络探测不纳入 5ms 同步切换指标。

## 9. 回滚与开关

- `LLM_GATEWAY_PROBE_QUEUE_ENABLED=false`：关闭持久队列，回退现有 ActiveProbeWorker。
- `LLM_GATEWAY_REALTIME_ACCOUNT_FUSE_ENABLED=false`：关闭请求热路径账号熔断。
- `LLM_GATEWAY_PROBE_STATE_WRITE_MODE=shadow|active`：影子或正式状态写入。
- `LLM_GATEWAY_PROBE_WORKERS=N`：限制 worker 数量。
- 数据库变更必须提供 down migration；旧 worker 与新队列不得同时成为同一状态的无协调写入者。

## 10. 验收标准

- 上游 401/明确封禁：当前账号从候选中立即消失，备用节点被尝试。
- 429 配额永久耗尽：账号进入 `suspended`，不被自动探测反复唤醒。
- 429 短期限流：账号进入 `rate_limited`，按 `Retry-After` 冷却并可探测恢复。
- 5xx/超时：当前账号+模型剔除，多个备用探测并行，前端得到稳定等待/重试响应。
- 同一 dedup key 在 300s 内最多一个有效任务。
- worker 崩溃后租约可恢复，过期任务不再执行。
- 所有探测结果可在 `request_logs` 和队列记录中按 parent request、账号、模型、来源追踪。
- 关键同步切换 p99 < 5ms；错误率、切换次数、探测成功率和队列积压可观测。
