# 25 — 节点状态与自检恢复体系规范（V3.3）

> 状态：CURRENT（流程规范 + 审计修正记录，2026-08-15）
> 上游：23 号总体方案；代码核实基准见 29 号审计报告。本文回答三个问题：节点有哪些状态、故障如何触发自检与恢复、管理员操作如何立即生效。

## 1. 状态全景（权威源 + 投影）

一个"节点"= 供应商凭据（credential）× 可路由模型（credential_model_binding）。状态分四层：

### 1.1 DB 持久层（权威，`v_routable_credential_models` 视图消费）
| 层 | 字段 | 取值 | 恢复方式 |
| --- | --- | --- | --- |
| 凭据可用性 | `credentials.availability_state` | ready / cooling / rate_limited / unreachable / auth_failed / suspended | `availability_recover_at` 到期由 `bg/credential_recovery.go`（60s ticker）恢复 |
| 配额 | `credentials.quota_state` | ok / periodic_exhausted / permanently_exhausted / balance_exhausted | `quota_recover_at` 到期恢复；periodic 由 quota probe 验证 |
| 熔断（DB 侧） | `credentials.circuit_state` + `cooling_until` | closed / open | 到期关闭 |
| 生命周期 | `lifecycle_status` / `manual_disabled` / `admin_protected` | — | 手工（manual_disabled 不自动恢复） |
| 绑定 | `credential_model_bindings.available` + `unavailable_reason` | manual% / continuous_failure / probe_* / auto_* / mnf_cooling / model_probe_broken | `unavailable_recover_at` 到期；probe 成功恢复 |
| 模型探测 | `model_probe_state.state` | broken_confirmed / recovering | BrokenProbeReviver 复活 |

### 1.2 进程内三层（请求热路径实际判定）
1. **熔断器** `domains/credential/breaker.go`：CLOSED/OPEN/HALF_OPEN；OPEN 阻塞直到 cooling 到期或半开探测成功。
2. **credentialstate**（legacy/off/canary 模式；URSM_V2 authoritative 时不参与）：内存 10s / Redis 5min / DB 三级缓存。
3. **URSM v2**（authoritative/canary）：Redis per-node 状态（fail_streak/cool_until_ms/manual_hold）。
4. **fpslot NodeState** `credentialfpslot/node_state.go`：per (credential, model) 健康滑窗，失败禁用默认冷却 300s，`IsUsable` 冷却到期即恢复。

> 关键不变量：**手工禁用三重标记**（`manual_disabled` + `unavailable_reason LIKE 'manual%'` + `admin_protected`）必须被所有自动恢复 SQL 排除——手工禁用永不自动恢复，系统降级全部可自动恢复。这是"两种禁用"语义的根基。

## 2. 两种禁用与恢复矩阵（R7）

| 操作 | 入口 | 生效范围 | 恢复 |
| --- | --- | --- | --- |
| 手工禁用 | `force_disable`（emergency-repair）/ credential monitor `manual_disabled` | DB 标记 + URSM manual_hold | 仅人工（force_enable / 清除手工禁用） |
| 系统降级 | 错误分类自动触发（availability/quota/circuit/binding） | DB + 内存态 + URSM | 到期自动恢复或探测成功恢复 |
| 强制启用 | `force_enable`（emergency-repair） | 必须清空**全部**状态层（见 §5） | — |
| 清除熔断 | `clear_circuit` | DB circuit + 内存熔断 + fpslot 冷却 | — |

## 3. 故障分类 → 自检动作矩阵

错误分类权威在 `errorsx/classify.go`。按类别的处理：

| 故障类 | 定级 | 请求侧动作 | 状态侧动作 | 自检（probe） |
| --- | --- | --- | --- | --- |
| rate_limit（429） | transient | 切节点；Retry-After 解析（`ClassifyQuota429Body`） | availability=rate_limited + recover_at（按 Retry-After 或默认） | **首败即触发 active probe**（2026-08-15 修正，原为 ≥2 次才触发） |
| 服务器过载（5xx→upstream_overloaded） | transient、偶发 | 切节点，不累计永久惩罚 | transient 计数；不直接降级凭据 | 首败即触发 active probe |
| timeout / network / upstream_down / stream_timeout | transient | 切节点 | transient ≥3 → cooling 5min（付费）/软降权（免费） | 首败即触发 active probe |
| auth / auth_revoked | permanent | 切节点 | permanent ≥2 → 熔断 15min | 探测确认，auth_failed |
| quota（periodic/balance/permanent） | quota | 切节点 | quota_state + recover_at | periodic_quota_probe（5min）/ balance probe |
| client_bug / context_length / content_filter / model_not_found | 不惩罚凭据 | 跳过该候选或该 provider | 无 | 模型侧探测（model_probe） |

自检通道一览：
1. **active probe**（错误触发）：`credentialstate` → `bg/active_probe_worker.go`，退避链 5s→30s→2m→5m→15m，直连上游验证，结果写 request_logs（task_type=probe，会出现在实时请求流）并 `UpdateFromProbe` 恢复状态。
2. **no-candidates 同步探测**：executor 无候选时并行探测全部候选，5s 上限，首个成功即刷新候选重发（对客户端近似无感）。
3. **定期探测**：credential_probe_v2（每小时）、node_probe（backoff ladder 5s/30s/60s/5m/1h）、model_probe、periodic_quota_probe（5min）。
4. **手动探测**：`POST /api/admin/providers/{id}/test-now`（受控、不改长期状态）。

## 4. 负载均衡（同模型多供应商）

- 权重 = 凭据并发能力：`concurrency_limit_auto`（自动调参）优先，封顶手动 `concurrency_limit`，clamp [1,1000]（`provider/client.go:1424 applyCapacityWeightedLB`）。
- tier 内选择：Bandit（Thompson Sampling）或 P2C；平局按权重加权（`pickWeightedTie`）。
- 会话首请求或出错切换时按均衡原则分配到所有正常同级节点（权重比例）；sticky 仅在成功后建立（保 prompt cache 亲和）。
- 计费轮次拆分：套餐/免费池优先于按量（`splitByBillingRound`）。

## 5. 强制启用（force_enable）语义 — "立即回到可用集"

修复后（2026-08-15，见 29 号）force_enable 必须清空**所有**状态层，缺一不可：

| 层 | 清理动作 |
| --- | --- |
| DB 凭据 | manual_disabled=false、availability=ready、quota=ok、circuit=closed、health=healthy、failures=0 |
| DB 绑定 | cmb.available=true（指定模型或全部） |
| DB 探测态 | node_probe_state 复位、model_probe_state broken_confirmed→recovering |
| **内存熔断** | `credential.Manager.Reset(providerID, credentialID)`（新增单节点 Reset） |
| **fpslot NodeState** | 清 cooldown（指定模型或该凭据全部绑定模型） |
| **credentialstate** | 以探测成功语义写入（UpdateFromProbe，Available=true） |
| URSM v2 | ApplyAdmin(manual_hold=false) + 逐模型 ClearStateForTenant（raw_model 为空时枚举全部绑定模型，不再跳过） |
| 缓存 | `invalidateRoutingCaches` + `InvalidateAvailableModelsCache`（已有） |

验收标准：force_enable 返回 200 后，**下一个路由周期**（≤30s 候选缓存失效后）该节点可被选中。

## 6. 自检队列流转规范（R8）

### 6.1 三态生命周期
```
planned（计划生成，不入队列）
   └→ pending（待请求队列：probe_queue PG 租约表，status=pending）
        └→ in_flight（正在请求队列：Claim 后，系统按目标参数生成真实探测请求）
             └→ completed（已完成队列：Complete 后保留最近 N 条供回放）
```
- 定期自检：生成计划（schedule），到期时才 Enqueue 进 pending——**不提前占坑**。
- 智能回退（active probe backoff）：只生成第一跳需求（5s 后）；下一跳是否生成取决于本轮结果——本轮失败按退避链在到期时再入队，不长期驻留 pending。
- 错误触发自检：立即 Enqueue（优先级高于定期）。
- 租约过期（executor 崩溃）由 `RequeueExpiredLeases` 回收重入 pending。

### 6.2 展示规则（与实时请求流对齐）
- 大小两种形态：大形态=探测详情卡（目标、参数、结果、耗时、错误码）；小形态=队列行内徽标（origin: direct/gateway/scheduled + attempt）。
- 从右侧加入新数据（时间轴向左滚动），与实时请求流泳道方向一致。
- 数据通道：`GET /api/admin/probe/stream`（SSE，probeStreamStore.ts）+ Redis 队列数据（probe_lifecycle_sink）；刷新回放最近 completed。
