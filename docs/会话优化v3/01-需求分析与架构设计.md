## 1. 需求概述

### 1.1 核心目标

**构建一个统一的实时可观测性平台**，在首页"实时请求流"中完整呈现：

1. **请求生命周期全景**：从请求到达 → 路由选择 → 节点分配 → 执行 → 响应/错误 → 重试/切换
2. **多层队列透视**：总请求队列 + 模型队列 + 供应商节点队列的实时状态
3. **节点级可操作性**：实时查看节点状态、一键测试验证、快速切换节点状态
4. **扩展请求链路**：展示请求衍生的子任务（标题生成、总结、敏感词检查等）的主从关系
5. **在线会话管理**：浏览多轮次会话、查看会话扩展请求、统计会话健康度

### 1.2 与现有系统的关系

**现有架构**（已实现）：

```
│   - 请求详情抽屉（RequestLogDrawer）                         │
```

**缺失环节**（需要补齐）：

1. ❌ **队列状态不可见**：dispatch.Pipeline 的三层队列（总队列、模型队列、credential 队列）没有暴露到前端
2. ❌ **节点级操作缺失**：无法在首页快速测试/切换供应商节点（需要跳转到 Provider 详情页）
3. ❌ **请求链路断裂**：主请求与衍生子任务（扩展请求）无法关联展示
4. ❌ **会话可视化不足**：SessionStatsPanel 只有统计数据，缺少实时会话列表与多轮次浏览
5. ❌ **状态变更追踪弱**：请求的路由决策、节点切换、重试逻辑无法回溯

## 1.5 需求深化（V3.1 补充）

### 1.5.1 队列处理流程不清晰

**现状问题**:

- ✅ 已有 dispatch.Pipeline 三层队列（总队列、模型队列、credential 队列）
- ❌ 队列之间的**流转关系**不清晰（请求如何从总队列→模型队列→节点队列）
- ❌ 请求在每个队列的**等待时长**无法追踪
- ❌ 队列拥堵的**根因定位**困难（是模型排队还是节点排队？）

**深化需求**:

1. 清晰展示请求在三层队列中的**流转路径**（9 个阶段可视化）
2. 每个队列的**入队时间、出队时间、等待时长**可追踪
3. 队列拥堵时，能快速定位是**哪一层**的问题（智能诊断）
4. 可视化展示队列**瀑布流**（类似 Chrome DevTools Network Timeline）

### 1.5.2 会话层级结构需要深化

**现状问题**:

- ✅ 已有 session_summaries 表（V353 迁移）
- ✅ 已有 gw_project_id、gw_task_id 字段
- ✅ 已有 v_session_flow、v_task_summary、v_project_summary 视图
- ❌ 缺少**用户级**的聚合（按 api_key 归属的用户）
- ❌ 缺少**请求轮次**的可视化（会话内的多轮对话）
- ❌ 缺少**附属会话**与轮次的并级展示

**深化需求**:

1. **5 级层级结构**（最终确认）:

   ```
   L1: 用户 (by api_key)
     L2: 项目 (gw_project_id)
       L3: 任务 (gw_task_id)
         L4: 会话 (session_key)
           L5: 请求轮次 + 附属会话（并级）
   ```
2. **顶层运营视角**:

   - 看到所有**活跃用户**（按 api_key 分组）
   - 看到每个用户的**项目列表**和进度
   - 看到每个项目的**任务列表**和完成度
   - 看到每个任务的**会话列表**和健康度
   - 看到每个会话的**轮次时间线**和附属会话树
3. **会话稳定性监控**:

   - 会话健康度评分（50% 成功率 + 30% 延迟 + 20% 成本）
   - 会话成功率、平均延迟、成本趋势
   - 会话异常检测（连续失败、超时、高成本）

### 2.2 数据流设计

#### 2.2.1 请求全生命周期事件流

```
用户请求 → Gateway
    ↓
1️⃣ [EnqueueEvent] 进入总队列
    → SSE: { type: "enqueued", queue_depth: 12, position: 8 }
    ↓
2️⃣ [RouteDecision] 路由选择
    → 记录: { model: "claude-sonnet-4", provider_id: 587, reason: "lowest_latency" }
    → SSE: { type: "routed", selected_node: "claude-sonnet-4@587" }
    ↓
3️⃣ [NodeEnqueue] 进入节点队列
    → SSE: { type: "node_queued", node: "587", queue_depth: 3 }
    ↓
4️⃣ [ExecutionStart] 开始执行
    → SSE: { type: "executing", node: "587", attempt: 1 }
    ↓
5️⃣ [FirstByteReceived] 收到首字节
    → SSE: { type: "first_byte", latency_ms: 45 }
    ↓
6️⃣ [StreamingProgress] 流式进度（可选）
    → SSE: { type: "streaming", bytes_sent: 1024 }
    ↓
7️⃣ [Complete/Error] 完成或错误
    → SSE: { type: "completed", status: "success", total_latency: 1200 }
    ↓
8️⃣ [RetryDecision] 重试决策（如果失败）
    → 记录: { reason: "timeout", next_node: "588", retry_count: 1 }
    → SSE: { type: "retrying", new_node: "588", retry_count: 1 }
    ↓
9️⃣ [SubTaskSpawn] 衍生子任务
    → 标题生成请求: { parent_id: "req-001", type: "title_gen" }
    → SSE: { type: "subtask_created", parent: "req-001", child: "req-001-title" }
```

#### 2.2.6 请求在三层队列中的生命周期（V3.1 新增）

**9 阶段定义**:

| 阶段 | 名称         | 持续时间                                | 说明                 |
| ---- | ------------ | --------------------------------------- | -------------------- |
| 1    | 请求到达     | -                                       | 请求进入网关         |
| 2    | 总队列等待   | `t_total_enqueue → t_total_dequeue`  | 等待模型路由决策     |
| 3    | 模型路由     | `t_total_dequeue → t_model_enqueue`  | 确定使用哪个模型     |
| 4    | 模型队列等待 | `t_model_enqueue → t_model_dequeue`  | 等待该模型的可用节点 |
| 5    | 节点分配     | `t_model_dequeue → t_cred_enqueue`   | 选择具体的供应商节点 |
| 6    | 节点队列等待 | `t_cred_enqueue → t_cred_dequeue`    | 等待该节点的并发槽位 |
| 7    | 请求转发     | `t_cred_dequeue → t_forward_start`   | 准备向上游发送       |
| 8    | 上游处理     | `t_forward_start → t_response_start` | 上游供应商处理中     |
| 9    | 响应流式返回 | `t_response_start → t_response_end`  | 流式返回 tokens      |

**队列瀑布流可视化**（类似 Chrome DevTools Network Timeline）：

```
┌─────────────────────────────────────────────────────────────┐
│ 请求 ID                时间轴（横向）                        │
├─────────────────────────────────────────────────────────────┤
│ req-001  █▓▓░░░░░░░░░▓▓░░░█████                             │
│          ^  ^        ^  ^  ^    ^                            │
│          1  2        3  4  5    6                            │
│          到  总队列   模  模  节  响应                        │
│          达          型  型  点                              │
│                      路  队  队                              │
│                      由  列  列                              │
└─────────────────────────────────────────────────────────────┘
```

**颜色编码**:

- 🟦 蓝色 - 总队列等待（阶段2）
- 🟩 绿色 - 模型队列等待（阶段4）
- 🟨 黄色 - 节点队列等待（阶段6）
- 🟧 橙色 - 请求转发（阶段7）
- 🟪 紫色 - 上游处理（阶段8）
- ⚪ 灰色 - 响应流式返回（阶段9）

## 2.4 会话层级结构设计（V3.1 新增）

### 2.4.1 五级层级定义（最终确认）

```
Level 1: 用户 (User)
  ├─ 识别方式: api_key → api_keys 表 → user_id
```

### 2.4.3 会话健康度评分算法

```typescript
// 健康度评分算法（0.00 ~ 1.00）
function calculateHealthScore(session: SessionSummary): number {
  // 1. 成功率权重 50%
  const successRate = session.success_count / session.request_count;
  const successScore = successRate * 0.5;
  
  // 2. 延迟权重 30% (延迟越低分数越高)
  const latencyScore = Math.max(0, 1 - session.avg_latency_ms / 5000) * 0.3;
  
  // 3. 成本效率权重 20% (成本越低分数越高)
  const costPerToken = session.total_cost_usd / session.total_tokens;
  const costScore = Math.max(0, 1 - costPerToken / 0.00005) * 0.2;
  
  return Math.min(1.0, successScore + latencyScore + costScore);
}
```

**健康度等级**:

- 🟢 **健康** (0.90 ~ 1.00): 成功率高、延迟低、成本合理
- 🟡 **一般** (0.70 ~ 0.89): 偶尔失败或延迟较高
- 🔴 **异常** (< 0.70): 频繁失败或成本过高

```vue
    ElMessage.error('测试失败');
  } finally {
    testing.value[node.provider_id] = false;
  }
}

async function handleToggle(node: NodeStatus) {
  toggling.value[node.provider_id] = true;
  try {
    await toggleNode(node.provider_id, node.enabled);
    ElMessage.success(node.enabled ? '已启用' : '已禁用');
  } catch (e) {
    ElMessage.error('切换失败');
    node.enabled = !node.enabled; // 回滚
  } finally {
    toggling.value[node.provider_id] = false;
  }
}
</script>
```

## 5. 与现有系统的集成策略

### 5.1 最小侵入原则

1. **不破坏现有 SSE 结构**：新增的 queue-snapshot 端点独立于现有 live-stream 端点
2. **兼容现有 LiveRequest**：使用 `LiveRequestWithChildren` 扩展而非修改原结构
3. **渐进式启用**：通过 feature flag 控制新功能开关，默认关闭

### 5.2 向后兼容保证

1. **数据库迁移**：新增字段使用 DEFAULT 值，不影响现有查询
2. **API 版本控制**：新增端点使用 `/admin/v2/` 路径，保留旧版 API
3. **前端组件隔离**：新组件独立于现有组件，不修改 LiveRequestStreamV2 核心逻辑

### 5.3 性能考量

1. **队列快照频率**：2 秒一次，避免过度推送
2. **子请求查询优化**：使用索引 `idx_request_logs_parent`，限制查询深度
3. **活跃会话缓存**：使用 Redis，避免频繁查询数据库
4. **状态变更历史**：异步写入，不阻塞主流程
