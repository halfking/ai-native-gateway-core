## 1. 需求深化背景

基于初版方案讨论，识别出两个**核心缺失**：

### 1.1 队列处理流程不清晰

**现状问题**:
- ✅ 已有 dispatch.Pipeline 三层队列（总队列、模型队列、credential 队列）
- ❌ 队列之间的**流转关系**不清晰（请求如何从总队列→模型队列→节点队列）
- ❌ 请求在每个队列的**等待时长**无法追踪
- ❌ 队列拥堵的**根因定位**困难（是模型排队还是节点排队？）

**用户诉求**:
> "需要理清我们请求的多个队列的处理流程，并能在看板中可视化"

**具体要求**:
1. 清晰展示请求在三层队列中的**流转路径**
2. 每个队列的**入队时间、出队时间、等待时长**可追踪
3. 队列拥堵时，能快速定位是**哪一层**的问题
4. 可视化展示队列**瀑布流**（类似 Chrome DevTools Network Timeline）

---

### 1.2 会话层级结构缺失

**现状问题**:
- ✅ 已有 session_summaries 表（V353 迁移）
- ✅ 已有 gw_project_id、gw_task_id 字段
- ✅ 已有 v_session_flow、v_task_summary、v_project_summary 视图
- ❌ 缺少**用户级**的聚合（按 api_key 归属的用户）
- ❌ 缺少**请求轮次**的可视化（会话内的多轮对话）
- ❌ 缺少**附属会话**的定义（扩展请求、子任务会话）

**用户诉求**:
> "需要根据客户端的 apikey，自动将它发出的会话进行用户归类，然后再根据解析的项目、任务、会话、请求轮次、附属会话等分为 4 级的结构，能够一眼就看清任务执行的情况"

**具体要求**:
1. **4 级层级结构**（从顶到底）:
   ```
   用户 (by api_key)
     └─ 项目 (gw_project_id)
         └─ 任务 (gw_task_id)
             └─ 会话 (session_key)
                 ├─ 请求轮次 (turn_number)
                 └─ 附属会话 (扩展请求：title_gen, summary, etc.)
   ```

2. **顶层运营视角**:
   - 看到所有**活跃用户**（按 api_key 分组）
   - 看到每个用户的**项目列表**和进度
   - 看到每个项目的**任务列表**和完成度
   - 看到每个任务的**会话列表**和健康度
   - 看到每个会话的**轮次时间线**和子请求树

3. **会话稳定性监控**:
   - 会话成功率（成功轮次 / 总轮次）
   - 会话平均延迟
   - 会话成本趋势
   - 会话异常检测（连续失败、超时、高成本）

## 2. 队列流转可视化设计

### 2.1 请求在三层队列中的生命周期

#### 阶段定义

| 阶段编号 | 阶段名称 | 持续时间 | 说明 |
|---------|---------|---------|------|
| **1** | **请求到达** | - | 请求进入网关 |
| **2** | **总队列等待** | `t_total_enqueue → t_total_dequeue` | 等待模型路由决策 |
| **3** | **模型路由** | `t_total_dequeue → t_model_enqueue` | 确定使用哪个模型 |
| **4** | **模型队列等待** | `t_model_enqueue → t_model_dequeue` | 等待该模型的可用节点 |
| **5** | **节点分配** | `t_model_dequeue → t_cred_enqueue` | 选择具体的供应商节点 |
| **6** | **节点队列等待** | `t_cred_enqueue → t_cred_dequeue` | 等待该节点的并发槽位 |
| **7** | **请求转发** | `t_cred_dequeue → t_forward_start` | 准备向上游发送 |
| **8** | **上游处理** | `t_forward_start → t_response_start` | 上游供应商处理中 |
| **9** | **响应流式返回** | `t_response_start → t_response_end` | 流式返回 tokens |

#### 时间戳采集点（9 个）


### 2.3 队列拥堵根因分析

#### 智能诊断逻辑

当队列深度 > 阈值时，自动分析：

```typescript
// 拥堵根因诊断算法
function diagnoseQueueBottleneck(snapshot: QueueSnapshot): BottleneckDiagnosis {
  const totalDepth = snapshot.total_queue.depth;
  const modelDepths = snapshot.model_queues.map(q => q.depth);
  const nodeDepths = snapshot.node_queues.map(q => q.depth);
  
  // 1. 如果总队列深度高，但模型队列深度低 → 路由慢
  if (totalDepth > 50 && Math.max(...modelDepths) < 10) {
    return {
      bottleneck: 'routing',
      message: '路由决策慢，考虑优化 route 阶段',
      suggestion: '检查 router.SelectModel() 耗时',
    };
  }
  
  // 2. 如果某个模型队列深度高 → 该模型节点不足
  const topModel = modelDepths.indexOf(Math.max(...modelDepths));
  if (modelDepths[topModel] > 30) {
    return {
      bottleneck: 'model_capacity',
      message: `模型 ${snapshot.model_queues[topModel].model} 节点不足`,
      suggestion: '增加该模型的供应商节点',
    };
  }
  
  // 3. 如果某个节点队列深度高 → 该节点并发不足
  const topNode = nodeDepths.indexOf(Math.max(...nodeDepths));
  if (nodeDepths[topNode] > 20) {
    return {
      bottleneck: 'node_concurrency',
      message: `节点 ${snapshot.node_queues[topNode].credential_id} 并发不足`,
      suggestion: '提高该节点的 max_concurrency 或禁用该节点',
    };
  }
  
  return { bottleneck: 'none', message: '队列正常' };
}
```

**UI 展示**:
- 拥堵警告卡片（红色）
- 一键跳转到瓶颈队列
- 显示建议操作按钮（如"禁用节点 587"）

## 3. 会话层级结构设计

### 3.1 五级层级定义（最终确认）

```
Level 1: 用户 (User)
  ├─ 识别方式: api_key → api_keys 表 → user_id
  ├─ 聚合维度: 用户名、团队、租户
  └─ 展示信息: 活跃项目数、总成本、总会话数、最近活跃时间
  
  Level 2: 项目 (Project)
    ├─ 识别方式: gw_project_id (已有字段)
    ├─ 聚合维度: 项目名称、状态、开始时间
    └─ 展示信息: 任务数、会话数、成本、进度百分比
    
    Level 3: 任务 (Task)
      ├─ 识别方式: gw_task_id (已有字段)
      ├─ 聚合维度: 任务名称、状态、优先级
      └─ 展示信息: 会话数、成功率、成本、时长
      
      Level 4: 会话 (Session)
        ├─ 识别方式: session_key (已有)
        ├─ 聚合维度: 会话标题、状态、创建时间
        └─ 展示信息: 轮次数、成功率、成本、模型使用
        
        Level 5: 请求轮次 (Turn) 与 附属会话 (Child Session) 【并级】
          ├─ 请求轮次:
          │   ├─ 识别方式: turn_number (新增)
          │   ├─ 聚合维度: 角色（user/assistant）、时间戳
          │   └─ 展示信息: 延迟、tokens、成本、状态
          │
          └─ 附属会话:
              ├─ 识别方式: parent_request_id (V3 新增)
              ├─ 类型: title_gen, summary, sensitive_check
              └─ 展示信息: 类型、状态、延迟
```

**注意**: 最终确认为 **5 级层级**，其中 Level 5 包含两种并级元素（轮次 + 附属会话）。

#### 3.2.2 新增表：session_turns (会话轮次表 - Hot + 分区表架构)

**设计原则**: 当天数据写入 hot 表，凌晨批量迁移到分区表

```sql
-- Migration V511: 创建会话轮次表（Hot + 分区表架构）

-- 1. Hot 表（当天数据，高频写入）
CREATE TABLE IF NOT EXISTS session_turns_hot (
  id BIGSERIAL PRIMARY KEY,
  tenant_id BIGINT NOT NULL,
  session_key TEXT NOT NULL,
  turn_number INTEGER NOT NULL, -- 轮次编号（从1开始）
  request_id TEXT NOT NULL,     -- 对应 request_logs.request_id
  role TEXT NOT NULL,            -- 'user' 或 'assistant'
  content_preview TEXT,          -- 内容预览（前200字符）
  status TEXT NOT NULL,          -- 'success', 'error', 'timeout'
  latency_ms INTEGER,
  tokens INTEGER,
  prompt_tokens INTEGER,
  completion_tokens INTEGER,
  cost_usd DECIMAL(10,6),
  model TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  
  -- 外键约束
  CONSTRAINT fk_session_turns_hot_session 
    FOREIGN KEY (tenant_id, session_key) 
    REFERENCES session_summaries(tenant_id, session_key) 
    ON DELETE CASCADE
);

-- Hot 表索引
CREATE INDEX idx_session_turns_hot_session 
  ON session_turns_hot(tenant_id, session_key, turn_number);

CREATE INDEX idx_session_turns_hot_request 
  ON session_turns_hot(request_id);

CREATE INDEX idx_session_turns_hot_created 
  ON session_turns_hot(created_at); -- 用于批量迁移查询

-- 2. 冷数据分区表（历史数据，按月分区）
CREATE TABLE IF NOT EXISTS session_turns (
  id BIGSERIAL,
  tenant_id BIGINT NOT NULL,
  session_key TEXT NOT NULL,
  turn_number INTEGER NOT NULL,
  request_id TEXT NOT NULL,
  role TEXT NOT NULL,
  content_preview TEXT,
  status TEXT NOT NULL,
  latency_ms INTEGER,
  tokens INTEGER,
  prompt_tokens INTEGER,
  completion_tokens INTEGER,
  cost_usd DECIMAL(10,6),
  model TEXT,
  created_at TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (id, created_at) -- 分区键必须在主键中
) PARTITION BY RANGE (created_at);

-- 创建最近 3 个月的分区（示例）
CREATE TABLE session_turns_2026_08 PARTITION OF session_turns
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

CREATE TABLE session_turns_2026_09 PARTITION OF session_turns
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

CREATE TABLE session_turns_2026_10 PARTITION OF session_turns
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

-- 分区表索引（每个分区自动继承）
CREATE INDEX idx_session_turns_session 
  ON session_turns(tenant_id, session_key, turn_number);

CREATE INDEX idx_session_turns_request 
  ON session_turns(request_id);

-- 3. 联合查询视图（Hot + 冷数据）
CREATE OR REPLACE VIEW v_session_turns_all AS
SELECT * FROM session_turns_hot
UNION ALL
SELECT * FROM session_turns;

-- 注释
COMMENT ON TABLE session_turns_hot IS '会话轮次热表：当天数据，高频写入';
COMMENT ON TABLE session_turns IS '会话轮次冷表：历史数据，按月分区';
COMMENT ON VIEW v_session_turns_all IS '会话轮次联合视图：Hot + 冷数据';
COMMENT ON COLUMN session_turns_hot.turn_number IS '轮次编号：会话内的第N轮（1-based）';
```

**批量迁移脚本** (每日凌晨 2:00 执行):

```sql
-- scripts/migrate_session_turns_to_partition.sql
-- 将昨天的数据从 hot 表迁移到分区表

BEGIN;

-- 1. 插入到分区表
INSERT INTO session_turns 
SELECT * FROM session_turns_hot 
WHERE created_at < CURRENT_DATE;

-- 2. 删除 hot 表中的旧数据
DELETE FROM session_turns_hot 
WHERE created_at < CURRENT_DATE;

-- 3. 清理索引碎片
REINDEX TABLE session_turns_hot;

COMMIT;

-- 4. 记录迁移日志
INSERT INTO admin_logs (action, details, created_at)
VALUES ('session_turns_migration', 
        format('Migrated %s rows from hot to partition', 
               (SELECT COUNT(*) FROM session_turns WHERE created_at >= CURRENT_DATE - INTERVAL '1 day')),
        NOW());
```

#### 3.2.3 新增视图：v_user_hierarchy (用户层级视图)

```sql
-- Migration V512: 创建用户层级视图
CREATE OR REPLACE VIEW v_user_hierarchy AS
SELECT 
  ss.tenant_id,
  ss.user_id,
  u.username,
  u.email,
  -- 项目统计
  COUNT(DISTINCT ss.gw_project_id) as project_count,
  COUNT(DISTINCT ss.gw_task_id) as task_count,
  COUNT(DISTINCT ss.session_key) as session_count,
  -- 时间范围
  MIN(ss.first_request_at) as first_activity_at,
  MAX(ss.last_request_at) as last_activity_at,
  -- 成本和请求
  SUM(ss.request_count) as total_requests,
  SUM(ss.total_cost_usd) as total_cost_usd,
  SUM(ss.total_tokens) as total_tokens,
  -- 健康度
  AVG(ss.health_score) as avg_health_score,
  -- 活跃度
  CASE 
    WHEN MAX(ss.last_request_at) > NOW() - INTERVAL '1 hour' THEN 'active'
    WHEN MAX(ss.last_request_at) > NOW() - INTERVAL '1 day' THEN 'recent'
    ELSE 'inactive'
  END as activity_status
FROM session_summaries ss
LEFT JOIN users u ON u.id = ss.user_id
WHERE ss.user_id IS NOT NULL
GROUP BY ss.tenant_id, ss.user_id, u.username, u.email;

COMMENT ON VIEW v_user_hierarchy IS '用户层级视图：按用户聚合所有会话统计';
```

### 3.4 会话健康度评分算法

```typescript
// 健康度评分算法（0.00 ~ 1.00）
function calculateHealthScore(session: SessionSummary): number {
  // 1. 成功率权重 50%
  const successRate = session.success_count / session.request_count;
  const successScore = successRate * 0.5;
  
  // 2. 延迟权重 30% (延迟越低分数越高)
  const latencyScore = Math.max(0, 1 - session.avg_latency_ms / 5000) * 0.3;
  
  // 3. 成本效率权重 20% (成本越低分数越高，但有底线)
  const costPerToken = session.total_cost_usd / session.total_tokens;
  const costScore = Math.max(0, 1 - costPerToken / 0.00005) * 0.2;
  
  return Math.min(1.0, successScore + latencyScore + costScore);
}
```

**健康度等级**:
- 🟢 **健康** (0.90 ~ 1.00): 成功率高、延迟低、成本合理
- 🟡 **一般** (0.70 ~ 0.89): 偶尔失败或延迟较高
- 🔴 **异常** (< 0.70): 频繁失败或成本过高

## 8. 风险与挑战

### 8.1 性能风险

**风险**: 6 级层级查询可能导致性能问题

**缓解**:
- 用户级使用缓存（Redis，TTL 5 分钟）
- 项目/任务级使用物化视图（每小时刷新）
- 会话级按需查询（用户点击时才加载）
- 轮次级懒加载（虚拟滚动）

### 8.2 数据量风险

**风险**: session_turns 表数据增长快（每个请求一行）

**缓解**:
- 分区表（按月分区）
- 归档策略（保留 30 天热数据）
- 旧数据迁移到对象存储

### 8.3 UI 复杂度风险

**风险**: 6 级层级展开会导致 UI 混乱

**缓解**:
- 面包屑导航（始终显示当前位置）
- 智能折叠（自动折叠非活跃层级）
- 快速跳转（点击用户直接跳到会话列表）
