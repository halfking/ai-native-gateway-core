> **审计追加（收口后复核）**：`actionArmed` 布防仍残留一个 ≤250ms 的漏投窗口（客户端刚连接、回放已读、光标未布防），且无客户端时轮询造成共享 Redis 常驻扫描流量。收口后审计已改为更简语义——无客户端跳过轮询、cursor 为空即全部按新事件投递（at-least-once，与回放幂等），见 08-执行记录 `v33obs-20260815-be2audit`；空转后接入客户端的 seq 1/2 送达已实测回归。

### 3.3 #4 child_request 进程内实流验证 + 466 约束前置（2026-08-16）

**背景**：原 #4 因「需真实上游子请求生成」长期 BLOCKED。本轮在不依赖真实上游的前提下，用**进程内真实 SSE hub（连 miniredis）**复现 #4 的两个运行时根因并断言其修复，同时将 DB 约束前置（migration 466）纳入部署门禁。

**根因 A — Redis self-echo 双帧**：同一 hub 既本地 enqueue 又订阅自身 Redis pub/sub。修复前 `NotifyChange` 不带实例标识，订阅方对「自己发的 notify」无法区分，于是每个 persistence phase（in_progress 一次、terminal 一次）既本地 enqueue 又 re-enqueue 一次 → 每 phase 双 `child_request` 帧。
修复：notify payload 新增 `instance_id`；hub 构造时生成 `instanceID`（`generateLiveStreamInstanceID`，crypto/rand 8 hex）；`Publish` 经 `Record(..., instanceID)` 落库并带标 publish；`handleRedisNotify` 对 `notify.InstanceID == h.instanceID` 直接跳过。无 `instance_id` 的旧 payload 与其他实例 payload 仍正常处理。

**实流断言（admin 包集成测试，连 miniredis）**：
- `TestLiveStreamRedisNotifySelfEchoSkipped`：带本实例 ID 的 notify 不写入 broadcast；无 ID 的 legacy notify 仍驱动 broadcast。
- `TestLiveStreamSelfEcho_NoDuplicateAcrossPhases`：同一 request 经 in_progress + terminal 两次 `Publish`，broadcast 恰好收到 2 帧（in_progress、success），**无 self-echo 额外帧**（断言超时阈值内仅 2 帧、之后 150ms 无更多帧）。
- `TestLiveStreamRedisNotify_DrivesBroadcast`（既有）：跨实例（无 ID）notify 仍驱动 broadcast，确保分布式多实例场景不受影响。

**根因 B — branch session 被当作 no-session 重建 + last-session 漂移**：child 请求的 `X-Gw-Session-Id` 为 `gt_/gs_` branch 形态，解析后 hangup 路径 `Get` 返回 NotFound 时原函数会 `CreateV2` 新 `gw_<uuid>` 并把它写入 `lastSystemSession`（no-session 恢复指针），既吞掉 branch、又污染 last-session。
修复：`isBranchSessionID` 判定 `gt_`/`gs_`（`isBranchSessionID` 单测覆盖，含 `gt:`/`gs:` 冒号变体必须判否以防被误当 branch）；chat handler 在 `Get` NotFound 时，branch id **保留原 `gt_/gs_`** 不 CreateV2，`lastSystemSession` **仅接受 `gw_` 主会话**（branch 永不写 last-session）。

**根因 C — terminal 子请求父子关联丢失**：并行修复 `38cd3fce9` 已在 `emitTelemetry` 调用 `applyParentCorrelationFields(reqLog, logCtx)`，把 `logCtx.ParentRequestID`、`logCtx.OriginActor` 写入 `request_logs.parent_request_id`/`origin_actor`。`TestApplyParentCorrelationFields` 已锁定该 helper（nil/空/有值三种形态正确映射）。

**466 约束前置（部署门禁）**：loopback child 行带 `parent_request_id` + `origin_actor` 但**无** `compression_reason`，会被严格 `chk_compression_parent_single`（`parent_request_id IS NULL OR compression_reason IS NOT NULL`）判为 23514 → telemetry fallback 吞掉该行（标题仍可生成，但父子关联 DB 行丢失）。migration 466 已放宽为 `… OR origin_actor IS NOT NULL`。
**实流核验（本机 PG）**：`llm_gateway` 运行库约束已含 `origin_actor IS NOT NULL`（松弛态）；但 `llm_gateway_test` 仍是 strict——**环境间漂移，需把 466 纳入所有目标库的启动/迁移流程**，否则 CI 测试库与运行库行为不一致。

**可清理探针（部署前必跑，零业务副作用）**：
```sql
-- 466 前置探针：确认 loopback child 行可落库（不违反 chk_compression_parent_single）。
-- 命中 request_logs_hot（constraint 同时作用于 request_logs 与 request_logs_hot）。
DO $$
DECLARE v_id text;
BEGIN
  v_id := 'probe_466_hot_' || replace(now()::text, ' ', '_');
  INSERT INTO request_logs_hot
    (request_id, parent_request_id, origin_actor, tenant_id,
     client_model, outbound_model, error_kind, success, ts)
  VALUES (v_id, v_id || '_p', 'auto_title', 'default',
          'probe-model', 'probe-out', 'probe-err', true, now());
  RAISE NOTICE '466 probe OK: %', v_id;
  DELETE FROM request_logs_hot WHERE request_id = v_id;  -- 清理
END $$;
```
失败（23514）即 466 未应用，阻断部署；成功且清理即前置通过。
实测：运行库 `llm_gateway` 探针通过；测试库 `llm_gateway_test` 仍报 23514（strict）——**环境间漂移，466 必须纳入所有目标库迁移流程，否则 CI 测试库与运行库行为不一致**。

**结论**：#4 的「Redis self-echo 双帧」「branch 保留」「terminal 关联」「466 约束前置」四个运行时根因均已用进程内实流 + 单元/集成测试 + 可清理探针闭合；仅「真实上游驱动 title/summary 子请求的可视化链路」仍 BLOCKED（需测试环境真实上游凭据流量）。
