# R76-3：已应用迁移字节冻结的 CI 级检测

**日期**：2026-11-17  
**类型**：防护加固（P2）  
**影响范围**：部署流程（新增 CI 检测）  
**根因**：已应用迁移被就地改写时，只有部署期 fail-closed 兜底，无 CI 级检测

---

## 1. 问题定位

### 1.1 触发场景
部署 154（2026-11-17）时，迁移 966 校验和不符：

```
[installer] FATAL: checksum mismatch for migration 966
  ledger:     c9cd0ddd1b8c7f3e...
  file:       96d0ff6bfc4a2e1d...
  ⇒ 部署中断（符号链接未切换，生产未动）
```

### 1.2 根因
迁移 966 于 **2026-11-15 23:50** 应用到 252 PG（245/154 共用），账本记录校验和 `c9cd0ddd`。  
**2026-11-16 03:45** 另一轮提交（6d93373f1）**就地改写**该文件（补 `setval` 逻辑），校验和变为 `96d0ff6b`。

⇒ 账本与仓内文件**字节不一致** ⇒ 部署期校验和闸门拦截。

### 1.3 现有防护
**只有部署期闸门**（`installer/internal/dbinit/runner.go:applySQL`）：

```go
if dbSHA256 != "" && dbSHA256 != fileSHA256 {
  return fmt.Errorf("checksum mismatch for migration %s", name)
}
```

**缺口**：
- 仓内无自动检测 ⇒ **先撞生产再修**（本轮实测：部署被打断，手工修复账本后重跑）
- 改写者不知道「该文件已应用」⇒ 无警告，直到部署才发现

---

## 2. 解决方案

### 2.1 新增 CI 级检测
`scripts/ci-migration-checksum-verify.sh`：

**功能**：
- 连接生产环境（211 / 252），读取账本 `llm_gateway_migration_checksums`
- 逐条比对：账本 sha256 vs 仓内文件字节
- 字节漂移 ⇒ **退出码 1**，输出：
  ```
  [$version] $migration_name: ★ 字节漂移 ★
    账本 sha256: c9cd0ddd...
    仓内 sha256: 96d0ff6b...
  ```

**使用**：
```bash
# 默认检查 252（245/154 共用）
bash scripts/ci-migration-checksum-verify.sh

# 检查 211
bash scripts/ci-migration-checksum-verify.sh --env 211
```

**退出码**：
- 0：全部一致 / 账本未初始化（首次部署）
- 1：检测到字节漂移
- 64：参数错误 / 环境不可达

**失败安全**：
- 账本不存在 ⇒ 退出码 0（首次部署或未初始化，不应阻断）
- 账本为空 ⇒ 退出码 0（无已应用迁移）
- 文件不存在 ⇒ 记录「文件缺失」但不算漂移（可能是远端独有的老迁移）

### 2.2 修复指引
检测到漂移时，脚本输出三条修复路径：

1. **改写是修复 bug**（如 966 补 setval）：
   - 先在目标环境手工执行修复 SQL（幂等）
   - 更新账本校验和：`bash scripts/repair-252-migration-ledger.sh --apply`

2. **改写是语义变更**（改 DDL / 改数据）：
   - 还原迁移文件到原始版本
   - 把语义变更写成**新的 forward-only 迁移**

3. **绝对不要**：
   - 绕过这个检测（静默降级）
   - 直接改账本（让账本与实际不一致）

## 4. 集成建议

### 4.1 CI 流水线
在**合并到 main 之前**运行：

```yaml
# .gitlab-ci.yml 或类似
migration-checksum-check:
  stage: test
  script:
    - bash scripts/ci-migration-checksum-verify.sh --env 252
    - bash scripts/ci-migration-checksum-verify.sh --env 211
  only:
    - merge_requests
    - main
```

### 4.2 pre-commit hook（可选）
对**改动了 `sql/migrations/` 的提交**自动运行：

```bash
# .git/hooks/pre-commit 或 husky
if git diff --cached --name-only | grep -q '^sql/migrations/'; then
  bash scripts/ci-migration-checksum-verify.sh || {
    echo "检测到迁移文件改动，且账本校验和不符 ⇒ 提交被拦截"
    exit 1
  }
fi
```

## 5. 影响面

### 5.1 修复前
**只有部署期闸门** ⇒ 改写已应用迁移时：
- 仓内无警告（改写者不知道该文件已应用）
- 部署期才发现 ⇒ **先撞生产再修**
- 修复流程：中断部署 → 手工执行修复 SQL → 更新账本 → 重跑部署

**量级**：
- 本仓 966 于 2026-11-15 23:50 应用，2026-11-16 03:45 被改写（12 小时窗）
- 154 部署被打断（RC=1），手工修复后重跑

### 5.2 修复后
**CI 级检测 + 部署期闸门** ⇒ 改写已应用迁移时：
- 合并前就发现 ⇒ **在开发阶段拦截**
- 提供三条修复路径的可执行指引
- 部署期闸门作为最后兜底（深度防御）

## 6. 遗留与后续

### 6.1 本轮**不**处理的
**迁移文件的「前置守卫」**：在改写迁移文件**之前**就拦截（而不是改写后才检测）。

- 现状：CI 检测在「改写后、合并前」运行
- 理想：改写迁移文件时（git add / 编辑器保存），当场弹警告「该文件已应用于 252，不得改写」
- 不做：需要文件系统监听 / 编辑器插件 / git hook，超出 CI 检测的范围

**登记为待办**：给迁移文件加「前置守卫」（编辑器 / git hook / 文件监听）

### 6.2 已知局限
**跨环境差异**：
- 211 与 252 的账本可能不同步（各自独立部署）
- CI 检测两个环境时，任一不符就失败 ⇒ 可能需要「按环境分支」的策略

## 8. 通用式

### 形态
**「已应用且不得改写」的文件** ⇒ 只有部署期兜底、无开发期检测 ⇒ **先撞生产再修**。

### 判据
- 开发期检测：改写前 / 改写后、合并前（CI / pre-commit hook）
- 部署期闸门：最后兜底（深度防御）
- 失败安全：首次部署 / 账本未初始化 ⇒ 不应阻断（退出码 0）

### 适用
任何「已应用于生产且不得改写」的文件（迁移 / 配置 / schema），都应该有**双层防护**（开发期检测 + 部署期闸门）。
