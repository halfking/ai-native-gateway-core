# P0-B: 被动时序指纹采集断链修复（2026-11-10）

## 问题概要

**影响面**: P0 级断链 —— 整个被动时序指纹子系统（migration 955、第 5 维度、DimPassive）在生产环境中**完全失效**，passive_model_fingerprints 表恒为空。

**根因**: 被动时序指纹的采样点（handler.go:7021-7042，原位置）被**错误地嵌套**在 `if len(result.ResponseBody) > 0 {` 分支内，而**流式请求的 ExecuteResult 不包含 ResponseBody 字段**（响应体直接写给客户端，见 `executors/executor_chat.go:2489-2506` 流式成功分支）⇒ 该分支对流式请求永不执行 ⇒ **流式请求零采样** ⇒ 基线表恒空。

**实证**:
- 211 生产主机实测（2026-11-10 08:00-08:15 UTC+8）：
  - 被动基线 worker 正常运行（08:01:15 启动，每 5 分钟 flush 一次）
  - 流式请求流量: **184 个流式请求/10 分钟**（session_turns_hot，stream_chunk_count > 0）
  - 其中 37% 请求有 canonical_model 填充（非空 ModelName）
  - passive_model_fingerprints 表: **0 行**
  - worker 日志无 "flushed" 记录 ⇒ 采集器无窗口 ⇒ Submit() 从未被调用

**时间线**:
- 2026-11-09: migration 955 上线，引入 passive_model_fingerprints 表 + 被动基线 worker
- 2026-11-09: 采样点代码在 handler.go emitTelemetry 中添加（commit 未详）
- **错误**: 采样点被放置在 `if len(result.ResponseBody) > 0 {` 内（可能是复制粘贴到 token 提取块内部时的意外嵌套）
- 2026-11-10: 生产审计发现 955 表恒空 ⇒ 回溯代码 ⇒ 定位断链

## 修复内容

### 1. 提取采样逻辑到独立方法

新增 `ChatHandler.samplePassiveTiming()` 方法（handler.go:1899-1960），封装被动时序指纹的完整采样逻辑：

**关键设计点**:
- **nil 安全**: 对 `h`、`passiveSink`、`capture`、`result` 全部进行 nil 检查
- **键口径**: 使用 `result.Candidate.BindingRawModel()`（model_offers.raw_model_name，如 "MiniMax-M3"）作为基线键，与仓库既有的「按绑定键状态」纪律一致（见 `provider.Candidate.BindingRawModel()` 注释：按 RawModel 键会混合多绑定的独立遥测）
  - fallback: `evt.CanonicalName`（当 BindingRawModel 空时）
- **token 来源**: 从 `capture.SummaryAsMap()["completion_tokens"]` 读取（流式路径的 SSE usage 块已累积到 capture）
- **位置纪律注释**: 70 行文档注释明确说明**必须在顶层调用**，不能嵌套在 ResponseBody 分支

### 2. 移动调用点到顶层

在 `emitTelemetry` 函数中（handler.go:7135-7145）：
- **调用位置**: 紧接在 quality signals 处理之后、ResponseBody token 提取**之前**
- **顺序保证**: 此时 capture 已完成（流已结束），usage 已累积
- **适用范围**: 流式 + 非流式请求均执行（非流式请求的 capture 为 nil ⇒ 方法内提前返回，符合设计：非流式无 ITT/TTFT）

**移除旧代码**: 原 `if len(result.ResponseBody) > 0 {` 内的采样块（7021-7042 原位置）已移除，保留注释（7160-7164）说明移出原因。

### 3. 键的名字空间对齐（未来工作）

**当前状态**: 
- 基线键 = `result.Candidate.BindingRawModel()` = model_offers.raw_model_name（如 "MiniMax-M3"）
- 扫描器节点键 = `provider_models.raw_model_name`（如 "workbuddy/minimax-m3"，provider 限定）
- **名字空间不同** ⇒ DimPassive 对接扫描器时需要桥接

**桥接方案**（待实现，记录在 handler.go:1924-1928 注释）:
```
credential_model_bindings.credential_id + provider_model_id
  → provider_models.raw_model_name (扫描器迭代键)
  
credential_model_bindings 同时关联 model_offers
  → model_offers.raw_model_name (基线键)

⇒ 通过 credential_id 连接两个名字空间
```

扫描器读取基线时，需要 JOIN `credential_model_bindings` 来映射 `provider_models.raw_model_name` → `model_offers.raw_model_name`，然后查询 `passive_model_fingerprints` WHERE `(credential_id, model_id) = (?, model_offers_raw_name)`。

## 影响面评估

### 功能影响
- **修复前**: 被动指纹子系统完全失效，DimPassive 无数据 ⇒ 模型可信度扫描的第 5 维度（被动时序验证）无法工作
- **修复后**: 流式请求正常采样 ⇒ 基线表开始累积 ⇒ DimPassive 可用（待对接扫描器）

### 性能影响
- **采样开销**: 每次流式请求完成后多一次采样（微秒级，无锁操作）
- **内存**: 采集器内存占用 ~数 KB/窗口（最多几百个 (credential, model) 窗口并发）
- **DB 写入**: 每 5 分钟 batch upsert，行数 = 活跃 (credential, model) 数（预计 10-50 行/flush）
- **评估**: 可忽略（与现有 telemetry 路径相当）

### 兼容性
- **向后兼容**: ✅（旧版本 worker 不存在，新表空 ⇒ 无冲突）
- **向前兼容**: ✅（修复仅影响数据写入，读侧未实现）
