# R76-3：部署闸门合并提交取包盲区修复

**日期**：2026-11-17  
**类型**：缺陷修复（P2）  
**影响范围**：`scripts/deploy-test-gate.sh`（部署前测试闸门）  
**根因**：合并提交时 `git diff HEAD~1 HEAD` 只看被合入侧，feature 分支改动不进测试清单

---

## 1. 问题定位

### 1.1 症状
部署 f3c1374ab 时，闸门**实际只跑了 4 个包**（admin / sanitizerules / outputcompliance / sanitize），而本次修复的核心包 `./provider/` **根本没进清单**。

### 1.2 根因
`scripts/deploy-test-gate.sh:182-186` 用以下逻辑选包：

```bash
changed_files="$({
  git diff --name-only -z HEAD 2>/dev/null || true
  git diff --name-only -z --cached 2>/dev/null || true
  git diff --name-only -z HEAD~1 HEAD 2>/dev/null || true  # ← 问题在这里
} | tr '\0' '\n' | sort -u)"
```

当 HEAD 是**合并提交**时，`HEAD~1` 是**第一父提交**（被合入侧，通常是 main），`git diff HEAD~1 HEAD` 只看「main 到 merge 结果」的差异，**完全看不到 feature 分支的改动**。

### 1.3 实测证据
用 f3c1374ab（R76-3 的合并提交）对比：

```bash
# 旧口径（HEAD~1 HEAD）
$ git diff --name-only f3c1374ab~1 f3c1374ab
（空输出 —— 看不到任何改动）

# 新口径（merge-base HEAD）
$ merge_base=$(git merge-base f3c1374ab~1 f3c1374ab~2)
$ git diff --name-only $merge_base f3c1374ab
provider/candidate_diag_dedup.go
provider/candidate_diag_dedup_cause_test.go
provider/candidate_diag_dedup_test.go
provider/candidate_empty_diag.go
provider/client.go
```

**结论**：旧口径下 provider/ 包**完全不可见**（盲区），新口径能正确提取。

---

## 2. 修复方案

### 2.1 修改点
`scripts/deploy-test-gate.sh`：在选包逻辑前**检测合并提交**（多个父提交），改用 **merge-base 与 HEAD 的 diff**：

```bash
parents_count="$(git rev-list --parents -n1 HEAD 2>/dev/null | wc -w | tr -d ' ')"
# parents_count = 父提交数 + 1（HEAD 自己）⇒ 合并提交 ≥ 3
if [[ "$parents_count" -ge 3 ]]; then
  merge_base="$(git merge-base HEAD~1 HEAD~2 2>/dev/null || true)"
  if [[ -n "$merge_base" ]]; then
    log "★ 检测到合并提交 ⇒ diff 对比 merge-base 与 HEAD，覆盖两侧差异"
    changed_files="$({
      git diff --name-only -z HEAD 2>/dev/null || true
      git diff --name-only -z --cached 2>/dev/null || true
      git diff --name-only -z "$merge_base" HEAD 2>/dev/null || true
    } | tr '\0' '\n' | sort -u)"
  else
    # 拿不到 merge-base ⇒ 回落常规 diff（失败安全）
    ...
  fi
else
  # 非合并提交 ⇒ 保持原逻辑
  ...
fi
```

### 2.2 新增判据
`scripts/test-gate-merge-coverage.sh`：

- 用已知展示盲区的合并提交（f3c1374ab）作为测试用例
- 断言：按 merge-base 口径能提取到 provider/ 包
- 对比：旧口径（HEAD~1 HEAD）完全看不到 provider/（盲区为 1 个包）
- 退出码：0=通过；1=失败

## 4. 影响面

### 4.1 修复前
**任何从 feature 分支合并到 main 的部署**，闸门都只测被合入侧（main）的改动，**feature 分支的全部改动不进测试清单** ⇒ 那些包的红灯不会被闸门拦住。

**量级**：
- 本仓约 **60%** 的提交是合并提交（`git rev-list HEAD --merges | wc -l` vs `git rev-list HEAD | wc -l`）
- R76-3 轮实测：5 个改动文件（全在 provider/）× **100% 漏测**

### 4.2 修复后
合并提交时，闸门提取 **merge-base 到 HEAD 的全部差异**，覆盖两侧改动 ⇒ feature 分支的包进入测试清单。

## 5. 遗留与后续

### 5.1 本轮**不**处理的
**「自上次部署基线」的取包口径**：当前实现按 `HEAD~1 HEAD`（或合并时按 merge-base），而更精确的口径是「自上次成功部署的提交」。

- 现状：连续两次部署（第二次是 hotfix）时，第二次闸门只看 hotfix 的 1 个提交的改动
- 理想：第二次闸门应该看「自第一次部署基线」的全部改动
- 不修的原因：需要持久化「上次部署基线」（文件 / 环境变量 / git tag），超出本轮「修合并提交盲区」的范围

**登记为待办**：修 `deploy-test-gate.sh` 的取包基线改用「自上次部署基线」（需要持久化机制）

### 5.2 已知局限
- **三路及以上合并**（octopus merge，`parents_count ≥ 4`）：当前实现只取 `HEAD~1` 和 `HEAD~2` 的 merge-base，第三个及以上父提交的改动**仍有盲区**
  - 量级：本仓历史 0 次 octopus merge（`git log --merges --parents | awk 'NF>3' | wc -l` = 0）
  - 不修：形态未出现过，修了也测不出来

## 7. 通用式

### 形态
**「按相邻提交 diff」在合并提交时只看一侧** ⇒ 另一侧的改动不可见（盲区）。

### 判据
- `git rev-list --parents -n1 HEAD | wc -w`：≥ 3 ⇒ 合并提交（至少两个父提交）
- 合并提交的 diff 基线应该是 **merge-base**，不是 `HEAD~1`

### 适用
任何「按 diff 选作用域」的工具（测试选包 / lint 选文件 / 增量构建），在合并提交下都要明确：是只看被合入侧，还是要覆盖两侧差异。
