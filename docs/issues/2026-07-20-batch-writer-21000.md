# 2026-07-20 — SQLSTATE 21000 in batch writers under high concurrency

## Summary

During the 2026-07-20 S07 peak_dispatch load test (150 concurrent clients
× 5 RPS × 30s, ~31k requests against 60 mock suppliers), the gateway log
surfaced a class of errors that had been masked by the "too many clients"
PG connection storm that dominated the same window:

```
WARN  batch writer: write failed count=85
  error="ERROR: ON CONFLICT DO UPDATE command cannot affect row a second time (SQLSTATE 21000)"
WARN  request_logger: persist update in batch failed request_id=...
  error="ERROR: current transaction is aborted, commands ignored until end of transaction block (SQLSTATE 25P02)"
WARN  request_logger: flush batch commit failed
  error="commit unexpectedly resulted in rollback"
```

The root cause is two distinct bugs in the request-persistence path.
Both were fixed in commit `0fc9d711` (2026-07-20).

## Bug A — `domains/credentialstate/batch_writer.go`

`batchUpsert()` builds **one** multi-row INSERT ... ON CONFLICT DO UPDATE
statement for every state update in the flush window. PostgreSQL refuses
to update the same row twice within a single statement: if two rows in
the batch share the same `(credential_id, raw_model_name)` ON CONFLICT
key, Postgres raises `SQLSTATE 21000 ("ON CONFLICT DO UPDATE command
cannot affect row a second time")` and aborts the entire statement.

Concurrent probes naturally produce duplicate `(credential_id,
raw_model_name)` pairs in one batch — when 60 mock suppliers × 15 models
hit the credential health probe loop, two probes for the same
credential+model can land within one flush window. Pre-fix, the entire
batch (typically 50–100 rows) was dropped on the floor and a single
warning was logged. 85 rows × N batches × multiple P99 spikes compounded
into the perceived "PG too many clients" failure mode.

### Reproduction (manual, requires local stack from
### `docs/全方面测试/00-总览.md`)

```bash
# Mock cluster + gateway already running per the README.
# Bump PG max_connections so the connection storm does not dominate:
docker exec llm-gateway-pg psql -U llm_gateway -d postgres -c \
  "ALTER SYSTEM SET max_connections = 300;"
docker restart llm-gateway-pg

# Drive a 30s peak load:
cd docs/全方面测试/tools
python3 loadtest.py \
  --gateway http://127.0.0.1:8781 \
  --api-keys "sk-loadtest-01" \
  --models "loadtest-mini-alpha" \
  --n-clients 150 --rps-per-client 5 --duration 30 \
  --prompt long

# Observe the 21000 line:
grep "SQLSTATE 21000" /tmp/gateway-test.log
```

### Fix (commit 0fc9d711)

`dedupByCredentialModel()` collapses entries that share the same
`ON CONFLICT` target before building the SQL, keeping the row with the
latest `UpdatedAt` (ties prefer the later occurrence). Insertion order
of the surviving rows is preserved via `sort.SliceStable` on the
original index. A 32-bit FNV-1a hash of the model name is composed with
`uint32(CredentialID)` into a `uint64` map key — collision-free for our
input sizes and zero allocations on the hot path beyond the winner
slice.

Unit tests (`batch_writer_dedup_test.go`) cover the four cases:
- no-duplicates passthrough
- latest `UpdatedAt` wins
- ties prefer later occurrence
- S07-shaped 100-row-with-50-dup-pairs input that originally triggered
  the failure

## Bug B — `domains/hooks/observability/telemetry/request_logger.go`

`flushBatch()` loops `persistUpdateInTx()` over a single transaction.
The first update can legitimately fail (terminal-state guard, FK, etc.);
the next call into the same tx then hits `SQLSTATE 25P02 ("current
transaction is aborted")`. Pre-fix the loop kept iterating, so every
remaining update produced one misleading "persist update in batch
failed: 25P02" warning, and the final `tx.Commit()` failed with
"commit unexpectedly resulted in rollback".

Net effect: the gateway log during S07 / S12 was dominated by ~17,000
lines of `25P02` warnings whose root cause was unrelated to the abort
itself — usually a single credential_state_log 21000 from Bug A
contaminating a shared pool, or a slow-query timeout. Real issues were
drowned in noise.

### Fix (commit 0fc9d711)

When `persistUpdateInTx()` fails, return immediately. Route every
remaining update in the batch through the configured
`dbdegradation.BackupWriter` (or log a `skipped due to prior tx abort`
notice when no fallback is configured). The deferred `tx.Rollback` at
function exit reclaims the aborted tx — no more wasted round-trips.

### Why no end-to-end unit test

The "tx abort → fallback remaining" path requires a live Postgres to
drive `SQLSTATE 25P02`. The unit test in
`request_logger_flushbatch_test.go` covers the existing `rl.db == nil`
short-circuit as a regression tripwire and documents the live-PG
reproduction steps above. A future change that re-introduces the
"iterate after abort" loop will fail this test or visibly pollute the
S07 gateway log, whichever fires first.

## Verification

```bash
go vet ./domains/credentialstate/... ./domains/hooks/observability/...
go test -short -count=1 ./domains/credentialstate/...
go test -short -count=1 ./domains/hooks/observability/telemetry/...
go build -tags=nokxmemo,noaudit -o /tmp/llm-gateway-test ./cmd/gateway
```

All four commands succeed with zero output. The 4 dedup unit tests
plus the 2 request_logger flushBatch tests are part of the package's
`go test -short` suite and run in well under a second combined.

## Lessons

- **Single-statement multi-row INSERT ... ON CONFLICT** is the most
  expensive primitive for write batching. The round-trip savings come
  at the cost of a sharp failure mode that PostgreSQL cannot soft-fail.
  Pre-flight dedup is the cheapest insurance.
- **`tx.Exec` after a failed `tx.Exec` does not return the original
  error** — it returns `25P02 current transaction is aborted`. Always
  break the loop on first failure, or run each statement in its own
  sub-tx.
- **Log volume is a signal**: 17,500 PG-exhaustion lines in 30s is
  noise from a non-database root cause (macOS ephemeral port exhaustion
  + `request_logger` 25P02 storm). When a single integration test
  produces 5-figure log volume, the root cause is upstream of the most
  frequent line.
