二、发现的问题

❌ 问题1：上游错误信息被重写

严重程度：严重

位置：handler.go:writeErrorJSON() 及多个调用点

问题描述：

  • 网关在多处错误处理点使用了硬编码的错误消息，而非透传上游原始信息
  • 典型案例：
    writeErrorJSON(w, http.StatusServiceUnavailable, requestID, "Authentication service temporarily unavailable", "server_error", "auth_unavailable")
  • 客户端看到的是网关的通用消息，无法获知上游具体的错误原因

影响：

  • 客户端无法区分是哪个供应商出错
  • 无法获取供应商返回的详细错误信息（如配额详情、具体限流原因等）
  • 故障排查困难，用户无法判断是自己的问题还是供应商问题

❌ 问题2：错误位置信息缺失

严重程度：严重

问题描述：

  • 当前错误响应格式不包含source字段来标识错误来源
  • 客户端无法判断错误发生在网关层还是供应商层
  • 错误类型error_type和code混合了网关和供应商语义

实例：

// 当前响应格式 { "error": { "type": "server_error", "message": "Internal routing service error", "code": "routing_database_error" } } // 问题：客户端无法知道这是网关自身的数据库问题，还是供应商的问题

⚠️ 问题3：供应商错误信息丢失

严重程度：中等

位置：extractUpstreamReason() 函数

问题描述：

  • 虽然代码中有extractUpstreamReason()来提取上游错误信息
  • 但提取后的信息经过SanitizeErrorText脱敏处理，可能丢失关键信息
  • 提取的信息仅限200字符，可能截断重要的上下文
  • 在很多错误处理路径中，根本没有调用此函数

⚠️ 问题4：自动路由切换的可观测性不足

严重程度：中等

问题描述：

  • 当错误触发ActionSwitchNode时，客户端不知道发生了切换
  • 重试次数、已尝试的节点信息未在响应中返回
  • 客户端无法判断是首次失败还是已重试多次后的最终失败

四、解决方案

✅ 方案1：增强错误响应结构

目标：让客户端能清楚地知道错误来源和详细信息

实施：

  1. 扩展错误响应格式，添加source字段：
    { "error": { "type": "rate_limit_error", "message": "上游返回的原始错误消息", "code": "rate_limit", "source": "provider", // 新增：gateway | provider "provider_id": 7, // 新增：供应商ID "provider_name": "openai", // 新增：供应商名称 "upstream_error": { // 新增：上游原始错误 "type": "rate_limit_error", "message": "Rate limit exceeded for model gpt-4", "code": "rate_limit_exceeded" }, "retry_info": { // 新增：重试信息 "retryable": true, "retry_after": 60, "attempts_made": 2, "max_attempts": 3 } }, "request_id": "req-xxx" }
  2. 修改writeErrorJSON系列函数，支持传入上游错误信息
  3. 保留供应商的原始错误响应体（在upstream_error字段中）

✅ 方案2：改进错误信息传递

实施步骤：

  1. 修改错误写入函数：
    // 新函数签名 func writeErrorJSONWithUpstream( w http.ResponseWriter, status int, requestID string, gatewayMsg string, // 网关层面的描述 errType string, code string, upstreamErr error, // 上游错误对象 providerID *int, // 供应商ID retryInfo *RetryInfo, // 重试信息 ) { resp := ErrorResponse{ Error: ErrorDetail{ Type: errType, Message: gatewayMsg, Code: code, Source: determineSource(upstreamErr, providerID), }, RequestID: requestID, } // 如果有上游错误，提取并附加 if upstreamErr != nil { if upstreamBody := extractUpstreamBody(upstreamErr); upstreamBody != nil { resp.Error.UpstreamError = upstreamBody resp.Error.ProviderID = providerID } } // 添加重试信息 if retryInfo != nil { resp.Error.RetryInfo = retryInfo } // ... 序列化并写入响应 }
  2. 修改执行器错误传递：确保ExecuteError携带完整的上游响应体
  3. 修改错误分类器：在分类时保留上游错误的原始信息

✅ 方案3：增强自动路由切换的可观测性

目标：让客户端和运维人员都能清楚地看到重试和切换过程

实施：

  1. 在响应头中添加路由信息：
    X-Gateway-Attempts: 3 // 已尝试次数 X-Gateway-Provider-Chain: 7,8,9 // 尝试过的供应商ID链 X-Gateway-Final-Provider: 9 // 最终响应的供应商 X-Gateway-Retry-Reason: rate_limit // 触发重试的原因
  2. 在错误响应体中包含切换历史：
    { "error": { ... }, "routing_history": [ { "provider_id": 7, "provider_name": "openai", "attempt": 1, "error_kind": "rate_limit", "action": "switch_node" }, { "provider_id": 8, "provider_name": "anthropic", "attempt": 2, "error_kind": "auth", "action": "switch_node" }, { "provider_id": 9, "provider_name": "minimax", "attempt": 3, "error_kind": "terminal", "action": "fail" } ] }
  3. 添加详细的结构化日志：记录每次切换的决策依据

✅ 方案4：错误信息脱敏的精细化控制

问题：当前SanitizeErrorText可能过度脱敏，丢失有用信息

解决：

  1. 区分内部日志和客户端响应的脱敏级别
  2. 对客户端响应：只脱敏凭据、密钥等敏感信息，保留错误类型、限额值等
  3. 对内部日志：保留完整信息以便排查
  4. 示例：
    // 原始上游错误 "Rate limit exceeded: 100 requests per minute. Current usage: 150/100" // ❌ 过度脱敏（当前） "Rate limit exceeded" // ✅ 适度脱敏（建议） "Rate limit exceeded: 100 requests per minute. Current usage: 150/100" // 这里没有敏感信息，应完整保留

六、自动化路由切换机制评估

✅ 已有的自动化能力

  • 错误分类精准：通过errorsx.DecideNextAction对20+种错误类型做精细化处理
  • 智能切换：
    • ActionSwitchNode：自动切换到备用供应商节点
    • ActionWaitRecovery：对可恢复错误等待后重试
    • ActionRetrySameNode：对临时故障在同节点重试
  • 历史追踪：DecisionHistory机制防止循环重试
  • 健康度管理：节点健康状态驱动路由决策（node_probe_state）
  • 熔断保护：候选查询熔断器（ErrCandidatesCircuitOpen）

⚠️ 需要改进的地方

  1. 缺少客户端可见的切换通知：
    • 当前切换对客户端透明，无法判断是否发生了failover
    • 建议：在响应头添加X-Gateway-Failover: true标记
  2. 重试预算不透明：
    • 客户端不知道还剩多少次重试机会
    • 建议：返回retry_info.attempts_made和max_attempts
  3. 缺少手动干预接口：
    • 客户端无法指定"跳过某些供应商"或"优先使用某供应商"
    • 建议：支持请求头X-Gateway-Preferred-Providers和X-Gateway-Exclude-Providers

9.1 修改writeErrorJSON函数
