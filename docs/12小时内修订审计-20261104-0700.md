### 2.2 ★★ P0-1：全新安装基线自相矛盾 ⇒ 全新安装当场中止

> **这是本轮最重要的发现，且上一轮把它判成了「不能手改、须等真实库 dump」。**

**现象**：`sql/schema/01-schema.sql`（及其两份副本）里，`subscription_plan_entitlements` 的外键
`FOREIGN KEY (plan_id) REFERENCES public.subscription_plans(id)`，
而同一份文件里的 `subscription_plans` **只有 `UNIQUE (code)`、`id` 上没有任何唯一约束**
⇒ PostgreSQL 拒绝该外键：**SQLSTATE 42803**（`there is no unique or exclusion constraint matching given keys`）
⇒ `scripts/init-local-db.sh` 步骤 1 与 `scripts/deploy-local.sh` 的 `apply_schema_if_empty`
（`ON_ERROR_STOP=1` + `die`）⇒ **全新安装当场中止**。

**成因（逐条取证）**：

| 时间 | 事实 | 出处 |
|---|---|---|
| 2026-08-04 | 重新 dump 生产库 252 ⇒ 该库当时 `subscription_plans` **无主键** ⇒ canonical 里的 `subscription_plans_pkey` **被删掉** | `f1c5fdfe6`（diff 里那行 `- ADD CONSTRAINT subscription_plans_pkey …`） |
| 2026-11-04 02:20 | `2b0731675` **手工**把 936 的新表**连同它的外键**抄进 canonical（+436 行）⇒ **但没把 936 自带的「幂等补主键」DO 块的效果一起抄** | `git log -S 'CREATE TABLE public.subscription_plan_entitlements' -- sql/schema/01-schema.sql` |
| ⇒ | canonical 变成「**自带一条引用、却引不到唯一约束**」的形态 | 三份副本逐字节相同（1,038,063 bytes） |

**★ 第二处中止点（D-5，同族）：分区的列集合必须覆盖父表**

`2b0731675` 手工给**父表** `credit_ledger` 和 `credit_ledger_hot` 加了

⇒ PostgreSQL 要求分区在 `ATTACH` 时刻带上父表的**每一个列**

### 2.3 P1-1：旁路写的 `EXPIRE` 覆盖会话 hash 的 TTL（把有意调过的保留期截短）

**机制**：`internal/memoraprewarm` 的旁路写打的是**同一个 key**（`session:{id}`），
而 Redis 的 `EXPIRE` 是 **key 级**的 ⇒ 一次旁路写就把**整个会话 hash** 的 TTL 覆盖掉：

| 写方 | TTL | 出处 |
|---|---|---|
| `session.Manager.Touch`（心跳续期） | `cfg.SessionTTLHours`（默认 **72h**） | `domains/session/session.go:516` |
| `memoraprewarm` 旁路写 | **24h**（`DefaultSessionTTL` 硬编码） | `internal/memoraprewarm/wiring.go`（修复前） |

⇒ 两值不同 ⇒ **后写的那个赢** ⇒ 旁路写晚于心跳一个 ASM RTT ⇒ 最终 TTL = 24h。
⇒ **会话状态**（标题 / 标签 / 注解 / 设备 / api-key 绑定 / `last_active`）在 **24h 而不是 72h** 被丢弃。
⇒ 反向配置（`LLM_GATEWAY_SESSION_TTL_HOURS < 24`，如隐私口径的 2h）下，
预热又会把保留期**延长**到 24h ⇒ 两种方向都是错的。
★ 原注释写的「会话 hash 自身由 session.Manager 心跳续期，本值只兜 memora_context 悬挂」
**在 Redis 上不可实现**——TTL 是 key 级的，没有 per-field TTL。

⇒ ⇒ `requested` 永远大于终态之和 ⇒ 漏斗不闭合 ⇒ **且没有日志** ⇒
运维看到的只是一条单调上涨的 `requested`。

### 5-H2 · D-1 · `NO ROW LEVEL SECURITY` 不是合法语法

| 项 | 内容 |
|---|---|
| 缺陷 | `ALTER TABLE … NO ROW LEVEL SECURITY;` —— PostgreSQL **没有**这个子句（合法形态只有 `ENABLE` / `DISABLE ROW LEVEL SECURITY`）⇒ 语法错误 ⇒ 文件在 `BEGIN/COMMIT` 里 ⇒ **整个事务回滚** ⇒ **935 从未能真正回滚过**；且其尾部 `DROP COLUMN` 三列的意图会**打断应用写路径**（`maas/service.go` 仍 INSERT 这三列 ⇒ SQLSTATE 42703） |

| 真库实测 | 旧写法：`错误: 语法错误 在 "ROW" 或附近的`；新写法：`ALTER TABLE`（成功） |
| 副本同步 | `installer/cmd/llm-gw-installer/embeddata/startup/` 的两份 down 同步（**逐字节一致**是仓内既有约定） |

## 6. 本轮结论

| 维度 | 结论 |
|---|---|
| **窗口内修订是否合理** | 主体合理（A/B/C/D/E 簇的根因分析、修法方向都对），但**落地质量有 6 处不达标**：1 处让全新安装装不上、1 处静默截短会话保留期、1 处让 main 上的门变红、1 处把 404 变成 500、1 处权限标注无强制力、1 处漏斗不闭合 |
| **数据来源与去处** | ★ 活动额度的**读侧口径**正确（hot ∪ 全部分区，无月份洞）；★ 但**写侧闭环成立、读侧执行器零调用方** ⇒ 红线仍只活在注释里（F-3 闭环留待下一轮） |
| **并发锁控制** | 预热去重：单锁 check-then-set、锁内无 I/O、恰好一个赢家、有界表 ⇒ **无问题**；★ 本轮修掉的 P1-1 本身就是**跨组件的写序竞态**（两个 EXPIRE 写同一个 key） |
| **多线程资源竞争** | 预热 goroutine 生命周期有界（ctx 800ms + `defer cancel`；HTTP body `defer Close`）、`recover()` 兜住 panic ⇒ **无 goroutine 泄漏** |
| **内存 / 句柄泄漏** | 去重表有界（1e4 + 75% 驱逐）、注入预算 2 KB、Redis client 共享 ⇒ **无泄漏**；★ 错误响应体只 drain 4 KiB ⇒ 大错误体时连接不可复用（低影响，未修） |
| **异步处理异常** | ★ 本轮修掉 P2-2（构造失败无终态无日志）⇒ 五态漏斗在「请求都发不出去」这条路上也能闭合 |
| **异常错误的处理** | ★ 本轮修掉 P1-3（`fmt.Errorf` 丢 `%w` ⇒ `errors.Is` 链断 ⇒ 404 变 500）；★ 上一轮 F-12 的**同类兄弟位置**一并收口 |
| **请求数据转换** | 上轮 F-5（ledger detail 手工拼 JSON）**已成立**；★ 本轮新增的门（剥注释引号感知）也是这一族的守护 |
| **门本身是否可信** | ★ 发现**一道门是红的**（P1-2）且**三道门对同一缺陷全绿**（P0-1）⇒ **「门全绿」≠「门覆盖了我关心的那一维」**；本轮新增的每一道门都做了**变异验证** |
