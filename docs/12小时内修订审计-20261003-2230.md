## 三、深审一：音频转写网关（本轮重点）

### 3.1 音频域四文件（audio_service/transcriptions/speech/mcp）

**P1-1（🔴 已修）流中错误帧被吞，截断转写伪装成功**
`relayChatAudioSSE`（audio_service.go:632-673 原貌）把 SSE 事件名丢弃、
data 行宽松解析：`data: {"error":{...}}` 帧落进只声明 Choices/Usage 的结构体
（未知字段忽略 → choices 空 → 整帧蒸发），非 JSON data 行 `continue`。上游
输出若干 delta 后发错误帧关流时，reader.Err()=nil，函数返回**部分文本+nil**
⇒ handler 发 transcript.text.done ⇒ 客户端把截断转写当完整结果落盘。这是
数据完整性 P1（转写场景错误文本比失败更贵）。
修法：chunk 结构补 `error` 字段显式检出上抛（携带 message/type/code）；
连带修 failover 语义——**部分增量已发出后 Transcribe 禁止换候选重跑**
（emitted 闩锁），否则客户端收到两段拼接的增量流。

**P2-1（已修）流式路径 X-Gw-Audio-Transport 头从未生效**
serveStream 在 WriteHeader(200)+Flush 之后再 Set 头——Go net/http 语义下
进不了已发送的响应头；audio_service.go:58-64 对客户端的承诺在流式路径
落空（ResponseRecorder 不快照头，测试测不出）。修法：transport 信息改走
`transcript.transport` SSE 事件（未知事件名消费者按规范忽略；非流式路径的
响应头不受影响）。

**P2-2（已修）无并发闸的内存放大**
单请求峰值：multipart 形态 ~190MiB（表单副本+file+重打包+响应），chat 桥接
~120MiB（file+base64 4/3+marshal 再一份），TTS 桥接 ~240MiB；端点 mux 直挂、
限流是 RPM 分钟窗语义可突发。修法：AudioService 构造期信号量
maxConcurrentAudioOps=8（最坏 ~1.9GiB 峰值预算），ctx 取消时让位退出；
探针流量同闸（容量满探针红牌是正确语义）。

**P2-3（已修）全链路无整体 deadline**
上游 client 只有 ResponseHeaderTimeout=120s、服务端 WriteTimeout=0，首字节
之后读体（96MiB 全量缓冲/SSE 整读）无 deadline，trickling 上游无限期钉住
handler+内存。修法：Transcribe/Synthesize 入口
context.WithTimeout(maxAudioRequestDuration=10min)。

**P2-4（已修）TTS 桥接 Content-Type 可能与字节不符**
桥接实测固定回 24kHz16bit WAV，而 ContentType 标客户端请求的
audio/{format}（mp3/opus…）；下游按 Content-Type 解码即失败。修法：RIFF/WAVE
魔数嗅探钉回 audio/wav（透传形态仅在上游未标/错标 JSON 的兜底分支嗅探）。

**P3（登记未修）**：multipart 再封装丢未知表单字段（timestamp_granularities[]）
与 file part Content-Type 降级；非 xiaomi 候选回落桥接时 language/prompt 同样
丢弃；429/5xx 一律 502 不透传 Retry-After（embeddings 有，见 embeddings.go:222-248）；
透传 SSE 后追加第二个 [DONE]；SSE 写出错误忽略+newSSELineReader 死 ctx 参数；
MCP 面 base64 4/3 膨胀致有效上限 ~24MiB（HTTP 面 32MiB）；静态密钥降级模式
音频端点 404（无鉴权暴露，可用性缺口）；multipart 临时文件靠标准库请求末
清理（无泄漏，建议解析后主动 RemoveAll 提前释放）。

**干净面（逐项验证过）**：resp.Body 四个 Do 调用点全 defer Close（错误路径/
failover 切换/SSE 中断覆盖；upstream.Do 重试耗尽自关；upClient 无内部重试
放大）；音频代码零 goroutine/零 channel，failover 循环状态全为局部变量，
无竞态；鉴权与 embeddings 逐行同链（missing_key 401→Verify→throttle→RPM→
budget fail-closed），MCP 三方法统一 servePost 入口鉴权先于 dispatch；
SSE 解析器对多 data 行拼接/注释行/CRLF/残块处理正确。

### 3.2 探针/迁移/接线面

**P2（已修）migration 820 漏 transcribe 家族 + vision 错标无自愈**
820 谓词只有 -asr/-tts/-stt/whisper，缺新 InferModality 的 -transcri 包含
规则——存量 text 行不自愈；更糟：旧规则下 gpt-4o-transcribe 被 gpt-4o-
前缀抢标 **vision**，而 820 只升 text 行 ⇒ 一旦目录出现该名即复现
no_candidate 503（正是本特性要修的病）。修法：SQL 与 db.go ensure 镜像
同步补 `-transcri` + 白名单 vision→audio 定向纠正
（^(gpt-4o(-mini)?|gpt)-transcribe，不碰真 vision）。820 不在 checksum
登记册（warn-only），双改不破门。

**P2（登记移交）默认 unified-queue 模式 gateway 轮仍是文本 ping**
2026-08-13 起队列模式默认开，gateway 轮走 ActiveProbeExecutor.RunGateway
硬编码文本 ping（bg/active_probe_executor.go:494），node_probe 的
directProbeBody 修复只覆盖 legacy 模式。缓解：gateway 轮仅细化证据不上
梯子（probe_service.go:451 success=direct.ok），可用性无碍，但音频模型
每次探测写 http_400 审计行。移交探针 Owner：让 RunGateway 复用
directProbeBody。

**P2（登记移交）音频面未接 failure ledger/telemetry**
main.go 只给 embeddings 接 SetFailureLogger（"keeps credential quality
views complete across all data planes"），音频候选失败不进
candidate_failure_logs，request_logs 也不写——审计链上音频请求不可见。
移交：AudioService 加 SetFailureLogger 与 embeddings 同点接线。

**P3（登记）**：probeTinyWAVB64 注释尺寸错一个数量级（**已顺手订正**：
3244B/4.3KB，非 560B）；8-bit PCM 全零非规范静音（0x80 中点，小米实测
接受 0，保持已验证载荷不改）；残余文本 ping 探测面比文档口径广
（probe_responses_fallback/self_check_worker/credential_selfcheck/
model_probe TriggerManual）；ensure 每次开机重跑会覆盖管理员对 -asr/-tts
名字的 text 手工改写；镜像不 stamp schema_migrations('820')；
ttsProbeShapeName 含 "speak" 片段较宽（有 InferModality 双重门控）。

**干净面**：WAV 构造数学全对（RIFF size/byteRate/blockAlign/dataLen）；
失败判定纯 HTTP 状态码不 parse JSON，非 JSON 2xx（TTS 音频体）不误判红；
探针 400ms 计费副作用已在 commit 声明取舍；modality 匹配顺序由 matcher
tier 强制（gpt-4o-transcribe 17 字符稳赢 gpt-4o- 7 字符），大小写全链
Lower，无误伤；820 WHERE 范围精确（text+active 守卫）；三端点与
embeddings 完全同门同中间件链，路由无冲突。
