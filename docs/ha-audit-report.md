# 56 Nginx + PostgreSQL HA 方案审计报告

**审计时间**：2026-07-06  
**审计对象**：v4.0 最终实施方案  
**审计结论**：🔴 **发现重大架构矛盾，需修正**

---

## 1. 审计发现的关键问题

### ❌ **问题 1：nginx 负载均衡与 PG 主从的根本矛盾**

**问题描述**：

用户原始需求是：
> "让 71 与 184 负载均衡，以前端的特性来固定链路，不出错不要变更链路。我们将 71 与 184 上的数据库进行隔离，不互通，只是相当于两个完全一样的站点提供服务。"

但我们设计的方案是：
- **nginx 层**：71 和 184 负载均衡（双活，各自处理 50% 流量）
- **数据库层**：71 PRIMARY + 184 STANDBY（主从，184 只读）

**矛盾**：
- 如果 nginx 把写请求路由到 184，但 184 PG 是 STANDBY（只读），**写入会失败**
- 如果 nginx 把写请求全部路由到 71，那就不是负载均衡，而是主备模式
- 如果 71 和 184 各自有独立数据库（用户原始需求），那就不是主从，而是**数据库隔离的双活**

**根本原因**：
我把用户的两个需求混合了：
1. **需求 A（原始）**：71 和 184 是两个完全独立的站点（数据库隔离）
2. **需求 B（修正后）**：71 主库 + 184 从库（数据库主从同步）

这两者是**互斥的**。

---

### ❌ **问题 2：用户真实需求理解偏差**

重新阅读用户的核心需求：

> "我们能否让 71 与 184 上的服务器指向 71 上的数据库（主库），然后 184 自动同步 71 上的数据库，当 71 上的数据库出现问题时，71 与 184 自动切到 184 上的数据库。这个时候自动切换 71 为从库，让 184 成主库。"

**用户真实意图**：
1. **71 和 184 的 llm-gateway-go 都指向同一个数据库**（初始都指向 71 PG）
2. **184 PG 作为 71 PG 的热备**（流复制同步）
3. **71 PG 故障时**：
   - 184 PG promote 为 PRIMARY
   - **71 和 184 的 llm-gateway-go 都切换指向 184 PG**
4. nginx 的负载均衡只是**应用层的负载均衡**，数据库层是主从

**正确架构应该是**：

```
nginx 负载均衡（应用层）
  ├─→ 71 llm-gateway-go ────┐
  └─→ 184 llm-gateway-go ───┴─→ 指向同一个 PRIMARY PG
                                     │
                                  71 PG (PRIMARY)
                                     │ streaming replication
                                  184 PG (STANDBY, hot backup)
```

**故障切换后**：

```
nginx 负载均衡（应用层）
  ├─→ 71 llm-gateway-go ────┐
  └─→ 184 llm-gateway-go ───┴─→ 指向同一个 PRIMARY PG
                                     │
                                  184 PG (PRIMARY)
                                     │ streaming replication
                                  71 PG (STANDBY)
```

---

### ❌ **问题 3：sticky session 的误解**

**我之前的理解**：
- sticky session 是为了让同一用户固定到同一个后端（71 或 184）
- 因为 71 和 184 有独立数据库，session 不共享

**实际情况**：
- 如果 71 和 184 都指向同一个 PG，session 是共享的（存在同一个数据库）
- sticky session 在这种架构下**只是为了减少后端连接数**，不是为了数据隔离

**用户原始需求中的"前端特性固定链路"**：
- 可能只是为了**性能优化**（减少跨机房延迟、连接池复用）
- **不是**为了数据隔离

---

### ❌ **问题 4：现有脚本的适配性问题**

我发现的脚本（`scripts/db-backup-71/`）：
- `failover.sh`：71 standby → primary
- `failback.sh`：184 primary → 71 standby

但这些脚本的**假设**是：
- **71 上的 PG 容器叫 `pg-backup-184`**（端口 5433，备份用途）
- **184 上的 PG 是 k8s pod**（hostNetwork 5432，业务主库）

而我们的目标是：
- **71 上的 PG 容器叫 `llm-pg-71`**（端口 5432，业务主库）
- **184 上的 PG 是 k8s pod**（hostNetwork 5432，热备）

**脚本需要大幅改造**，不能直接用。

---

### ❌ **问题 5：实施步骤的破坏性**

我设计的 Phase 1.1-1.4 步骤：
- 会**停止 71 和 184 的 PG**
- 会**重新 pg_basebackup**（破坏性重建）
- 会导致**业务中断 > 30 分钟**（不符合 < 15 分钟承诺）

**原因**：
- 我假设 71 上没有正在运行的业务 PG
- 实际上 71 可能已经在跑 llm-gateway-go，连接到某个 PG

## 2. 修正后的正确架构

### 2.1 正确理解用户需求

| 需求 | 正确理解 |
|------|----------|
| **71 与 184 负载均衡** | nginx 应用层负载均衡，两者都是活跃节点 |
| **前端特性固定链路** | sticky session（性能优化，非数据隔离） |
| **数据库主从同步** | 71 PG (PRIMARY) ← streaming → 184 PG (STANDBY) |
| **71 和 184 都指向主库** | 初始都指向 71 PG，故障时自动切换到 184 PG |
| **数据库隔离** | ❌ **错误理解**！应该是主从同步，不是隔离 |

### 2.2 修正后的架构

**初始状态**：

```
┌─────────────────────────────────────────────────────────────┐
│ 56 nginx (14.103.169.56) — sticky hash 负载均衡             │
│   upstream llm-backend {                                    │
│     hash $sticky_key consistent;                            │
│     server 172.31.0.3:8781;  # 71 llm-gateway-go           │
│     server 172.31.0.4:10023; # 184 llm-gateway-go          │
│   }                                                         │
└─────────────────────────────────────────────────────────────┘
        │                              │
        ↓                              ↓
┌──────────────────┐          ┌──────────────────┐
│ 71               │          │ 184              │
│ llm-gateway-go   │          │ llm-gateway-go   │
│ (应用层活跃)     │          │ (应用层活跃)     │
│                  │          │                  │
│ DB 配置:         │          │ DB 配置:         │
│ → 172.31.0.3:5432│          │ → 172.31.0.3:5432│
│   (71 主库)      │          │   (71 主库)      │
└─────┬────────────┘          └─────┬────────────┘
      │                              │
      └──────────────┬───────────────┘
                     ↓
             ┌──────────────────┐
             │ 71 PostgreSQL    │
             │ 【PRIMARY】      │
             │ (172.31.0.3:5432)│
             └────────┬─────────┘
                      │ WAL streaming
                      ↓
             ┌──────────────────┐
             │ 184 PostgreSQL   │
             │ 【STANDBY】      │
             │ (172.31.0.4:5432)│
             │ (hot backup only)│
             └──────────────────┘
```

**故障切换后（71 PG 故障）**：

```
┌─────────────────────────────────────────────────────────────┐
│ 56 nginx — 继续负载均衡（两节点都健康）                     │

        │                              │
        ↓                              ↓
┌──────────────────┐          ┌──────────────────┐

│                  │          │                  │
│ DB 配置:         │          │ DB 配置:         │
│ → 172.31.0.4:5432│          │ → 172.31.0.4:5432│
│   (184 新主库)   │          │   (184 新主库)   │
└─────┬────────────┘          └─────┬────────────┘
      │                              │
      └──────────────┬───────────────┘
                     ↓
             ┌──────────────────┐
             │ 184 PostgreSQL   │
             │ 【PRIMARY】      │
             │ (172.31.0.4:5432)│
             └────────┬─────────┘
                      │ WAL streaming
                      ↓
             ┌──────────────────┐
             │ 71 PostgreSQL    │
             │ 【STANDBY】      │
             │ (172.31.0.3:5432)│
             │ (恢复后重建)     │
             └──────────────────┘
```

### 2.3 关键修正点

| 原设计 | 修正后 |
|--------|--------|
| 71/184 各自连本地 PG | 71/184 **都连同一个 PRIMARY PG** |
| 184 PG 是 standby，不接受写 | 184 PG 是 hot standby，**71/184 应用都不直连** |
| nginx 负载均衡 = 数据隔离 | nginx 负载均衡 = **应用层分流，数据层共享** |
| sticky 为了数据一致性 | sticky 为了**性能优化**（连接池复用） |
| 数据库隔离的双活 | **主从同步的应用双活** |

## 3. 修正后的实施方案

### 3.1 前置条件确认

**需要先确认当前状态**：

1. **71 上当前 PG 状态**：
   - 是否已有 `llm-pg-71` 容器？
   - 是否已有业务数据？
   - 当前 71 llm-gateway-go 连哪个 PG？

2. **184 上当前 PG 状态**：
   - k8s pod `llm-gateway-pg` 当前状态？
   - 当前 184 llm-gateway-go 连哪个 PG？
   - 184 PG 有哪些业务数据？

3. **当前数据一致性**：
   - 71 和 184 的数据是否一致？
   - 是否已经有主从关系？

### 3.2 最小改动方案（推荐）

**方案 A：以 184 PG 为主库（最小改动）**

**假设**：
- 184 k8s PG 已经是生产主库（有完整业务数据）
- 71 llm-gateway-go 当前连 184 PG（从 `scripts/_lib/llmgw-deploy-lib.sh:50-52` 看确实如此）

**步骤**：
1. **保持 184 PG 为 PRIMARY**（不动）
2. **在 71 上启动一个新 PG 作为 184 的 STANDBY**
   - 用 `scripts/db-backup-71/init-pg-standby.sh`（已存在）
3. **71 llm-gateway-go 继续指向 184 PG**（不动）
4. **56 nginx 配置负载均衡**
5. **部署 HA 监控**

**优点**：
- ✅ 不需要停 184 PG（零停机）
- ✅ 利用现有脚本
- ✅ 数据不丢失

**缺点**：
- ❌ 71 和 184 llm-gateway-go 都通过内网访问 184 PG（71 跨机器连接，略有延迟）

---

**方案 B：以 71 PG 为主库（用户原意）**

**假设**：
- 用户希望 71 是主库

**步骤**：
1. **在 71 上准备新 PG**
2. **从 184 pg_dump 导出数据 → 导入 71**
3. **71 PG 设为 PRIMARY**
4. **184 PG 重建为 71 的 STANDBY**
5. **71 llm-gateway-go 改为连 71 PG**
6. **184 llm-gateway-go 改为连 71 PG**

**优点**：
- ✅ 符合用户原意（71 主库）

**缺点**：
- ❌ 需要停机（pg_dump + 导入 ≈ 30-60 分钟）
- ❌ 风险高（数据迁移）
