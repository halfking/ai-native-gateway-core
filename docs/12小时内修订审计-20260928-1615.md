### 3.1 `9fe387ac8` fix(sanitize): restore placeholders across stream deltas（R73 收口，12 files +743/-86）

**原因**：跨 SSE 事件的占位符拆分此前原样透传——脱离前缀的尾片可泄漏敏感值片段或内部 token 形态；Redis 映射加载失败时旧实现整块透传（fail-open）。属"数据去处/请求数据转换"维度缺口。

**方案复核**（✅ 合理）：
- per-stream `streamRestoreState` 挂在 `StreamMeta.State`（每流一个 writer 实例初始化，`domains/streaming/handler.go:114`），不在共享 interceptor 上——无跨请求共享，随流生命周期释放，**无内存泄漏**；
- 双上限：lane 数 64 + 尾片 256 字节；超限 fail-closed 阻断整流（防尾片脱离前缀泄漏），256B 超长前缀降级 `[REDACTED]`；
- 尾片语法判定 `validPlaceholderPrefix` 严格（`{SENSITIVE:` + 小写/下划线 key + 数字索引 + 无 `}`），普通 JSON/代码尾部的大括号仅在严格匹配语法时扣留；
- 锁纪律正确：`loadMap`（Redis IO）在 `state.mu` 外；锁内纯内存操作；
- `streamLaneID` 对 provider 传入的 item_id 做 SHA-256 定长化——不可信输入不进 request-local 携带态，防 key 注入放大；
- fail-open 收紧：映射缺失/读取失败时仍遮蔽已知 marker（`InterceptNonStream` 的 `sm = SanitizeMap{}` 路径）。

**结果**：`go test ./security/sanitize/...` ok（2.554s，含新增 343 行测试 + cross_tenant_race 调整）。

**遗留（本轮新发现，见 §四 N-1/N-2）**：流结束钩子不释放扣留尾片；lane 用尽即整流阻断的保真度取舍。
