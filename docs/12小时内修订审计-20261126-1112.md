## 2. 本轮修复的缺陷（全部变异自证）

### 2.1 P1-A ｜投影报表静默跳过模型名展开，canonical 过滤恒空（代理发现，主审计确证）

- **位置**：`domains/reportrollup/grainreport.go:813`
- **事实**：本车道 `11dc125c4` 给模型名展开加了 `projection == nil &&` 前置 ⇒ V2 投影路径（`BuildProjectedReport`）的 canonical → raw 名展开被完全跳过且不打日志。投影行的 `raw_model_name` 存外发/客户端 raw 名，`outbound_model` 存供应商侧 raw 名或 client model——canonical 名（如 `minimax-m2.5`）在 fallback 的 `raw_model_name=$1 OR outbound_model=$1` 上**两头都不命中**。
- **影响**：前端用 canonical 名筛选时 V2 报表恒空、V1 同参数有数据 ⇒ 静默数据缺失（正是函数注释自己写明要防的形态）。
- **修法**：去掉 `projection == nil` 前置，两路径统一展开（`ResolveModelRawNames` 查 3 张目录表 LIMIT 1，代价低）；注释如实留痕归属。
- **验证**：`go test ./domains/reportrollup/ ./admin/` 全绿。

### 2.2 P1-B ｜scope_key 长度前缀整数溢出绕过守卫 → 读面 panic（代理发现，独立程序实测复现）

- **位置**：`domains/reportrollup/rollup.go:59`（`splitInternalPersonScopeKey`）
- **事实**：守卫 `i+1+n+1 > len(k)` 在 `n` 接近 `MaxInt64` 时先溢出为负 ⇒ 比较恒假 ⇒ `k[i+1:i+1+n]` 负上界切片 panic。独立程序实测：`splitInternalPersonScopeKey("9223372036854775807:abc")` → `panic: runtime error: slice bounds out of range [:-9223372036854775789]`。
- **可达面**：`report_snapshots.scope_key` 任意历史/外来行（含人工回填），`report.go:486` 在 HTTP 请求路径上直接调用 ⇒ 一行脏数据 500 整个 internal 视图报表。
- **修法**：守卫补 `n > len(k)` 上界前置判断（溢出前先拦）。
- **验证**：新增两条 MaxInt64 级用例进 `TestSplitInternalPersonScopeKey_MalformedKeysDoNotPanic`；**变异自证**——去掉 `n > len(k)` ⇒ panic 红；还原 ⇒ 绿。

### 2.3 P1-C ｜财务日历 env 通道绕过校验，坏时区使 V2 对账全 500 且报错无上下文（代理发现）

- **位置**：`domains/reconciliation/financial_calendar.go:42-55`
- **事实**：env 通道（`LLM_GATEWAY_REPORTS_RECONCILIATION_FINANCIAL_CALENDAR`）不经 `Spec.Validate`（那只把关 HTTP 写路径）；管理员用 env 塞 `open@No/Such/Zone` ⇒ `ParseReconciliationCalendar` 错误一路返回 ⇒ 所有 V2 对账报表 500，报错是泛化的 "invalid financial calendar timezone"——无键名、无来源。
- **修法**：读路径解析失败一律包装出 **key ＋ 取值来源（settings_kv / env:<名>）＋ 原值**；来源判定顺带修正（原实现 env 有值但 DB 行存在时 source 标错）。
- **验证**：`go test ./domains/reconciliation/` 全绿；错误文案三要素（key/source/value）落进全部三条错误分支。

### 2.4 P2-A ｜投影 INSERT 无 clamp：单条畸形 fact 毒停全部租户的 V2 统计（代理发现，真库复现）

- **位置**：`internal/metricsstore/processor.go`（projectBatchSQL 的 normalized/published 段）
- **事实**：`usage_facts` 的 token 列是 **bigint**（迁移 537），`request_metrics` 的是 **INTEGER**（迁移 983:90）。一个 `total_tokens=4294967296` 的坏 fact 让 INSERT 报 `integer out of range (22003)` ⇒ **整批事务回滚** ⇒ 游标不推进 ⇒ 每轮重试同一批 ⇒ **队头阻塞、全部租户 V2 统计停摆**，无隔离路径需人工删数解卡。
- **修法**：投影 SQL 的 `normalized` CTE 对 13 个 token/latency 列做 `least(greatest(coalesce(x,0),0), 2147483647)` 钳制（同 `stats_event_inbox` 负值守卫先例：坏值钳到上界落表，好过毒停管线）；SELECT 侧同步换用 clamped 列。
- **验证**：真库 fixture（隔离 PG17 容器、`request_metrics_fixture_*` 空库、template0 防 template1 污染）——新增 `oversized_tokens_clamped_not_poison` 子测试：坏 fact 落表为上界、下一批正常 fact 仍投影；**变异自证**——把 SELECT 换回原始列 ⇒ `integer out of range` 红现形；还原 ⇒ 绿。全套 10 子测试（含既有 9 个）真库全绿。

### 2.5 P2-B ｜投影 readiness 假绿：投影器停摆 / 积压无界时长期 200（代理发现）

- **位置**：`internal/metricsstore/readiness.go`
- **事实**：就绪判定只看 `backfill_complete && updated_at` ⇒ 投影器停摆或 pending 无界积压时仍长期 200；`pending_since` 字段已返回但无人消费。
- **影响**：与 2.4 叠加 ＝「停摆且假绿」的最坏组合；运维探活与 `wait-request-metrics-ready.py`（部署闸门 DD_REQUIRE_REQUEST_METRICS=1 时）都拿不到降级信号。
- **修法**：新增 `projectionStaleThreshold=60m`——水位 `updated_at` 距今超阈值、或积压头 `pending_since` 入队超阈值未消化 ⇒ 判 stale ⇒ **503 ＋ `stale:true ＋ reason`**；判定时钟取 `checked_at`（DB statement_timestamp，非本机时钟）。
- **行为面披露**：部署闸门在「投影器已停摆 >60m」的环境会**快速失败**而非等到 1800s 超时——方向 fail-closed，符合闸门语义；正常部署（水位新鲜）不受影响。
- **验证**：新增 `readiness_test.go`（sqlmock 三态：健康 200 / 水位停摆 503＋reason / 积压无界 503）＋ `projectionIsStale` 单元边界（阈值两侧、nil 安全）；真库全套 10 子测试回归绿。

## 7. 教训登记

1. **「各自闸门绿 ≠ 合并树绿」第三次复现（M-1）**：合并轮跑全了主仓门禁但漏了 installer 子模块的测试 ⇒ V2 分支带来的棘轮在合并树上静默红了一小时。⇒ **合并轮的门禁清单必须按「合并带入的子模块/新测试文件」扩展，不是按主仓既有清单跑**。
2. **fixture 隔离的 template 陷阱**：共享 PG 容器上 `CREATE DATABASE` 默认克隆 template1，而 template1 已被其它测试污染（14 张表）⇒ fixture「空库」断言红。⇒ 隔离 fixture 一律 `TEMPLATE template0`。
3. **钳制先例的边界**：投影 SQL 里已有负值守卫先例（`least(...) < 0 THEN NULL`），本轮的超界钳制沿同一思路落到 CTE 层——**在写入侧守住类型边界，比在所有读侧加容错便宜一个量级**。
4. **深审代理的发现必须逐点复核后才采信**：本轮代理报的 2 个「P1」在复核中确认（溢出 panic 独立程序复现、canonical 过滤失配链路走读），1 个 P2 在复核中发现报告里漏了「outbound_model 也参与 fallback 匹配」这一半事实——采信度按「能否独立复现」分级，不按报告级别。
