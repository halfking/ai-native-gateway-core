## 1. 项目概述

### 1.1 背景

当前request_logs表存在以下问题：
- 每轮存储完整JSONB（request_body + outbound_body + response_body）
- 长会话导致磁盘线性膨胀
- 元数据和正文耦合，无法独立优化
- 历史数据查询性能下降

### 1.2 目标

- **磁盘节省**: 60-80%（通过增量存储）
- **查询优化**: 元数据查询更快（分表存储）
- **零风险迁移**: V1/V2并行，完全可回滚
- **扩展性**: 易于添加新功能（如会话总结、标签等）

### 1.3 核心创新

```
┌─────────────────────────────┐
│ V1: 每轮存储完整历史        │
│ Turn 1: [msg1]              │
│ Turn 2: [msg1, msg2]        │  ← 重复存储
│ Turn 3: [msg1, msg2, msg3]  │  ← 指数增长
└─────────────────────────────┘

┌─────────────────────────────┐
│ V2: 每轮只存储增量          │
│ Turn 1: delta=[msg1]        │
│ Turn 2: delta=[msg2]        │  ← 只存新增
│ Turn 3: delta=[msg3]        │  ← 线性增长
└─────────────────────────────┘
```

## 2. 架构设计

### 2.1 表结构设计

#### V1体系（保持不变）
```
request_logs
├─ 所有字段混在一起
├─ request_body (JSONB全量)
├─ outbound_body (JSONB全量)
└─ response_body (JSONB全量)
```

#### V2体系（新建）
```
public.sessions
├─ session_id (主键)
├─ total_turns, total_tokens, total_cost_usd
├─ last_request_summary, last_response_summary
└─ 分区键: partition_date (按月)

public.session_turns
├─ session_id, turn_no (复合主键)
├─ 元数据: model, provider, tokens, cost
├─ 压缩元数据: compression_strategy, compression_meta
├─ 治理元数据: injection_verdict, output_verdict
└─ 不含正文！

public.session_bodies
├─ session_id, turn_no (复合主键)
├─ request_delta (只存新增消息)
├─ response_delta (本轮回复)
├─ outbound_body (压缩后，审计用)
└─ columnar格式，优化存储

public.session_turn_logs
├─ session_id, turn_no
├─ stage, stage_status (处理环节)
├─ event_data (详细数据)
└─ expires_at (24小时TTL)
```

### 2.2 数据流设计

#### 写入流程
```
请求到达
  ↓
处理Pipeline
  ↓
DualWriter
  ├─ V1Writer (主写) ← 失败则请求失败
  │   └─ request_logs
  └─ V2Writer (副写) ← 失败只记录日志
      ├─ TurnWriter → session_turns
      ├─ BodiesWriter → session_bodies
      ├─ TurnLogsWriter → session_turn_logs
      └─ SessionAggregator → sessions (异步)
```

#### 读取流程
```
查询请求
  ↓
Feature Flag判断
  ├─ V2_enabled=true
  │   └─ SessionCacheV2
  │       ├─ L1: 内存LRU (元数据)
  │       ├─ L2: Redis (verdict)
  │       └─ L3: session_turns (冷启动)
  └─ V2_enabled=false
      └─ SessionCache (legacy)
          └─ request_logs
```

### 2.3 并发安全

#### Turn_no分配机制
```go
BEGIN;
  -- 获取会话锁
  SELECT pg_advisory_xact_lock(hash(tenant_id, session_id));

  -- 串行分配turn_no
  SELECT MAX(turn_no) + 1 FROM session_turns
  WHERE session_id = ?;

  -- 插入新记录
  INSERT INTO session_turns (...);
COMMIT; -- 自动释放锁
```

**保证**:
- ✅ turn_no单调递增
- ✅ 无并发冲突
- ✅ 高性能（锁粒度细）

## 4. 技术细节

### 4.1 增量提取算法

```go
func extractRequestDelta(req *ProcessedRequest) []Message {
    if len(req.LastOutboundBody) == 0 {
        return req.RequestBody // 首轮全量
    }

    // 构建上轮消息集合
    lastSet := buildMessageSet(req.LastOutboundBody)

    // 提取新增消息
    var delta []Message
    for _, msg := range req.RequestBody {
        if !lastSet[messageKey(msg)] {
            delta = append(delta, msg)
        }
    }

    return delta
}
```

### 4.2 SubmitMode检测

**优先级顺序**:
```
P0: X-Gw-Submit-Mode header (显式)
  └─ "delta" | "snapshot" | "full"

P1: 消息数回退 (客户端压缩)
  └─ len(client) < len(lastOutbound) && overlap < 30%

P2: Summary marker (压缩标记)
  └─ 包含 "[smm_v1:" 或 "[summary:"

P3: Orphaned tool_result (工具调用缺失)
  └─ tool_call_id 无对应 tool_calls

P4: LCS重叠分析
  └─ overlap >= 70% → full
  └─ overlap < 30% → inferred_compressed

P5: 首轮 → full
```

### 4.3 缓存架构

```go
L0: Turn Delta Storage
├─ 存储位置: session_bodies (columnar)
├─ 内容: 增量消息
└─ 用途: 增量存储源

L1: Compression Meta Cache
├─ 存储位置: 内存LRU (1024 sessions)
├─ 内容: 压缩元数据（不含body）
└─ 用途: 快速压缩决策

L2: Governance Cache
├─ 存储位置: Redis (30min TTL)
├─ 内容: injection_verdict, output_verdict
└─ 用途: 治理决策

L3: Cold Start
├─ 存储位置: session_turns表
├─ 内容: 元数据（不含body）
└─ 用途: 缓存未命中时重建
```

### 5.3 增量提取逻辑

```sql
-- 伪代码：提取本轮新增消息
WITH turn_messages AS (
    SELECT
        request_id,
        request_body->'messages' AS current_messages,
        LAG(outbound_body->'messages') OVER (
            PARTITION BY gw_session_id
            ORDER BY ts
        ) AS previous_messages
    FROM request_logs
    WHERE gw_session_id = :session_id
)
SELECT
    -- 提取不在previous_messages中的消息
    jsonb_array_elements(current_messages) AS new_message
WHERE NOT EXISTS (
    SELECT 1 FROM jsonb_array_elements(previous_messages) AS prev
    WHERE prev = new_message
);
```

## 10. FAQ

### Q1: V2写入失败会影响请求吗？
**A**: 不会。V2是shadow write，失败只记录日志，不影响请求。V1写入失败才会导致请求失败。

### Q2: 如何验证V2数据正确性？
**A**: 使用数据校验工具：
```bash
go run cmd/tools/validate_sessions_v2 --session-id=<id>
```

### Q3: 回填会影响线上服务吗？
**A**: 不会。回填脚本有限流机制（pg_sleep），每批处理后COMMIT，不会长时间占用资源。

### Q4: 如何判断是否可以切换到V2？
**A**: 满足以下条件：
- V2写入成功率 >= 99.99%
- 数据一致性差异率 < 0.01%
- V2稳定运行 >= 7天
- 回滚演练通过

### Q5: V2和V1的磁盘占用对比？
**A**: 预计V2节省60-80%，实际取决于：
- 会话长度分布
- 客户端压缩行为
- 附件大小占比

### Q6: turn_no会不会冲突？
**A**: 不会。使用PostgreSQL advisory lock保证串行分配，即使并发请求也不会冲突。

### Q7: 如何紧急回滚？
**A**:
```bash
# 1. 禁用Feature Flag
sessions_v2_shadow_write: false
sessions_v2_l3_read: false

# 2. 热重载
curl -X POST http://localhost:8080/api/admin/reload-config
```

### Q8: 前端需要改动吗？
**A**: Phase 4会提供新的API，但V1 API继续可用，前端可以渐进式升级。

### Q9: columnar格式有什么限制？
**A**:
- 只能追加，不支持UPDATE
- 适合大批量INSERT
- 查询性能优于heap（对于分析查询）

### Q10: 历史数据回填要多久？
**A**: 取决于数据量，估算：
- 1000条/批
- ~100ms/批
- 100万条 ≈ 17分钟（单线程）
- 支持并行回填（按月分区）
