# 多模态技术方案

> 创建日期：2026-07-14
> 状态：Phase 1 已完成，Phase 2-3 待启动
> 关联提案：`docs/changelogs/2026-07-14-multimodal-attachment-pipeline-proposal.md`

## 1. 目标

建立统一的附件存储与供应商感知引用管线，使多模态内容（图片/音频/视频/PDF）
在跨协议转换、会话压缩、上下文传递中不再丢失或静默降级。
统一存储只解决网关侧持久化和审计，不代表所有上游都能读取同一个 URL。

## 4. Phase 2：统一附件 URL 管线（待启动）

### 4.1 目标

将附件内容保存到统一存储，并按目标供应商选择安全的引用形态。
这可以减少网关内部重复传输和日志体积，但不能保证减少上游 token 或费用。

### 4.2 组件

#### 4.2.1 files.kxpms.cn 上传服务

```
POST files.kxpms.cn/upload
  Content-Type: multipart/form-data
  → { url: "https://files.kxpms.cn/2026/07/req_xxx/abc.png" }

GET files.kxpms.cn/{path}
  → 图片内联，其他类型强制下载
```

#### 4.2.2 请求改写 hook

在 Extractor 落盘后、转发上游前，按目标供应商选择引用模式：

```
原: { "type": "image_url", "image_url": { "url": "data:image/png;base64,..." } }
后: { "reference_mode": "data" | "gateway_url" | "provider_file" }

只有在上游可访问、允许该 MIME 且策略允许时，才能使用 gateway URL。
Gemini 等供应商文件 URI 不能作为通用 HTTPS URL 透传。
```

#### 4.2.3 request_logs 清理

`request_logs`、trace、重试缓存和错误日志统一执行附件脱敏。
默认保存规范化后的引用和元数据；原始 body 仅在显式审计开关、短 TTL、加密和严格权限下保存。

### 4.3 OSS/S3 后端修复（Phase 2 前置）

在实现供应商引用前，需要先让存储后端支持 OSS/S3，并补充引用策略：

1. 修复 `storage_backend_oss.go` / `storage_backend_s3.go` 编译错误
2. 对齐 `StorageBackend` 接口签名
3. 在 `main.go` 启动链路中根据 `storage.type` 创建对应后端
4. 管理端 PUT handler 支持写入 `storage.oss.*` / `storage.s3.*`
5. settings spec 注册 OSS/S3 配置键
6. 前端 StorageConfig 页面增加存储类型选择和 OSS/S3 表单
7. 增加 OpenAI、Anthropic、Gemini、Mistral 的 provider adapter，明确支持的块类型和引用模式
8. 对 gateway URL 做 host allowlist、签名 TTL、MIME 探测、SSRF 防护和下载鉴权

### 4.4 验收标准

## 6. 风险与约束

| 风险 | 影响 | 缓解 |
|------|------|------|
| base64 替换破坏签名校验 | 上游拒绝请求 | 保留原始请求体备份 |
| OSS 凭据泄露 | 安全事件 | settings_kv 加密存储；API 脱敏返回 |
| 大文件迁移超时 | 服务不可用 | 异步迁移 + 进度展示 + 超时回滚 |
| 存储后端不可用 | 附件丢失 | 降级为本地存储 + 告警 |
