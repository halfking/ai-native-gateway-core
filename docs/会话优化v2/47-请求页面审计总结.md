## 📋 快速总结

已完成对现有请求列表和详情页面的审计，并制定了**新增 V2 页面**同时**保留旧页面作为回退**的完整实施方案。

---

## 🎯 核心发现

### 现有页面

| 类型 | 路由 | 数据源 | 状态 | 问题 |
|------|------|--------|------|------|
| **会话列表** | `/api/admin/sessions` | `request_logs` | ✅ 正常 | 按会话聚合，无法查看单个请求 |
| **会话详情** | `/api/admin/sessions/{id}` | `request_logs` | ✅ 正常 | 返回完整历史，存储冗余 |
| **请求追踪** | `/api/admin/requests/{id}/trace` | `request_logs` + Redis | ✅ 正常 | 只有追踪数据，无消息体 |
| **轮次列表** | `/api/admin/sessions/{id}/turns` | `session_turns` | ✅ 已实现 | 只有元数据，无 body |
| **会话详情 V2** | `/api/admin/sessions/detail` | V2 表 | ✅ 已实现 | 返回增量，未动态拼接 |

### 缺失功能

| 功能 | 优先级 | 说明 |
|------|--------|------|
| **请求列表页面** | P0 | 按时间倒序查看所有请求（跨会话） |
| **单轮次详情页面** | P0 | 查看单个轮次的原始请求/响应 |
| **完整会话上下文** | P1 | 动态拼接所有轮次为完整对话 |
| **旧页面回退保障** | P0 | 确保旧页面可用作 fallback |

## 📐 设计方案

### 新增 API 端点（V2）

| 方法 | 路由 | 功能 | 数据源 |
|------|------|------|--------|
| GET | `/api/admin/v2/requests` | **请求列表** | `session_turns` |
| GET | `/api/admin/v2/requests/{request_id}` | **单轮次详情** | `session_turns` + `session_bodies` |
| GET | `/api/admin/v2/sessions/{session_id}/context` | **完整会话上下文** | 动态拼接所有 delta |

### 保留 API 端点（V1）

| 方法 | 路由 | 功能 | 保留方式 |
|------|------|------|---------|
| GET | `/api/admin/sessions` | 会话列表（旧） | ✅ 完全保留 |
| GET | `/api/admin/sessions/{id}` | 会话详情（旧） | ✅ 完全保留 |
| GET | `/api/admin/requests/{id}/trace` | 请求追踪 | ✅ 完全保留 |

### 核心特性

1. **请求列表页面**
   - 按时间倒序展示所有请求（跨会话）
   - 支持分页（page/size）
   - 支持过滤（时间、模型、状态）
   - 轻量级，只返回元数据

2. **单轮次详情页面**
   - 展示单个轮次的完整数据
   - request_delta：本轮新增的消息
   - response_delta：本轮响应
   - outbound_body：实际发送给 LLM 的内容
   - 上下文导航：prev/next turns

3. **完整会话上下文页面**
   - 动态拼接所有轮次
   - 使用 OutboundBuilder 重建完整对话
   - 保留压缩 marker（可选）
   - 展示压缩策略效果

## 💡 关键决策点

### 1. 是否与压缩层改造并行？

**选项 A**: 并行开发
- ✅ 优点：加快整体进度
- ❌ 缺点：资源压力大，风险叠加

**选项 B**: 串行开发（先完成压缩层）
- ✅ 优点：风险隔离，逐步推进
- ❌ 缺点：整体时间更长

**推荐**: **选项 B**（串行开发）

**理由**:
- 压缩层改造是核心功能，优先级更高
- 请求页面是展示层，可以等压缩层稳定后再做
- 风险隔离，更稳健

### 2. 是否需要前端配合？

**需要**，但可以分阶段：

- **Phase 1**：后端 API 开发（独立进行）
- **Phase 2**：前端集成（后续配合）
