# 多模态能力审计报告

> 审计日期：2026-07-14
> 审计范围：OpenAI ↔ Anthropic 跨协议多模态转换、附件提取、会话压缩
> 审计方法：源码静态分析 + 全量测试验证 + diff 复核
> 协议覆盖说明：网关原生支持三个协议（OpenAI Chat / Anthropic Messages /
>   Gemini Generate，见 `internal/ir/types.go`、`parse_gemini.go`、`domains/streaming/handler_gemini.go`）。
>   本次 Phase 1 修复与审计仅覆盖 OpenAI ↔ Anthropic 路径；Gemini 原生路径的多模态保真属独立范围，尚未审计。

## 1. 多模态内容类型

网关处理的多模态内容块类型：

| 来源协议 | 块类型 | 目标协议等价物 |
|---------|--------|--------------|
| Anthropic `image` (url) | `source.type=url` | OpenAI `image_url` |
| Anthropic `image` (base64) | `source.type=base64` | OpenAI `image_url` (`data:` URI) |
| OpenAI `image_url` | URL 或 `data:` URI | Anthropic `image` (url 或 base64) |
| Anthropic `text` | 文本块 | OpenAI 文本（合并或数组） |
| Anthropic `tool_use` | 工具调用 | OpenAI `tool_calls` |
| Anthropic `tool_result` | 工具结果 | OpenAI `tool` role 消息 |

## 2. 转换路径与修复前问题

### 2.1 OpenAI → Anthropic（chat_to_anthropic.go）

**修复前问题**：`data:image/jpeg;base64,...` 格式的 image_url 被错误地标记为
Anthropic `source.type="url"`，导致下游模型收到的是无效 URL 而非 base64 数据。

**修复后**：新增 `parseImageDataURI()` 函数，检测 `data:` 前缀并解析 MIME 和 base64 payload，
正确生成 `source.type="base64"` 块。

### 2.2 Anthropic → OpenAI（anthropic_to_chat_request.go）

**修复前问题**：
1. base64 图片被降级为文本占位符 `[Image: base64 data]`
2. URL 图片被降级为 `[Image: URL]`
3. 图文混合消息遇到 image 块时提前 `return`，丢失后续文本和 tool_calls

**修复后**：
1. base64 图片恢复为 `data:` URI 格式的 `image_url`
2. URL 图片保留为原始 URL 的 `image_url`
3. 使用 `hasNonTextContent` 标志位延迟返回，确保 tool_calls 和文本不丢失

### 2.3 Streaming Bridge（domains/streaming/messages.go）

与 2.2 同类问题，修复方式一致。
额外修复：未知的 passthrough 块也追加到 contentParts，避免丢失。

## 3. 会话压缩保真

### 3.1 修复前问题（domains/hooks/compression/strip.go）

`hasThinkingBlocks()` 把 `image_url` 和 `input_audio` 也视为需要清理的块类型。
`stripThinkingBlocks()` 在过滤时只保留 `text`/`tool_use`/`tool_result`，
删除所有 `thinking`/`image_url`/`input_audio` 块。

更严重的是，过滤保留块时只追加了 `p.Type`（一个 JSON 字段值），
而非完整块结构，导致保留的块丢失了除 type 之外的所有数据。

### 3.2 修复后

- `hasThinkingBlocks()` 只检测 `thinking` 类型
- `stripThinkingBlocks()` 保留除 `thinking` 外的所有块（完整 JSON）
- 使用 `json.RawMessage` 保持块原始结构

### 3.3 dedupConsecutive（sanitizer.go）

此前已修复的连续消息去重逻辑：
- `string + array` 混合内容不再误判为重复
- `array + array` 对比时图片块不会被丢弃
- `array + string` 反向同样安全

## 4. 附件提取管线

### 4.1 当前流程

```
客户端请求 (base64 image)
  ↓
Extractor.ExtractFromOpenAIBody() / ExtractFromAnthropicBody()
  ↓ 解码 base64 → SHA256 去重 → 落盘
  ↓
request_logs.attachments (JSONB 元数据数组)
  ↓
GET /api/admin/attachments/{path} 下载/预览
```

> Phase 2A 新增 Anthropic 协议附件提取（`messages.go:237`），
> strict 模式下存储失败直接返回 503，不再 best-effort 转发。

### 4.2 落盘路径格式（Phase 2A：SHA256 两级分片）

```
{BaseDir}/YYYY/MM/{hash[0:2]}/{hash[2:4]}/{hash}{ext}
```

示例：`/data/attachments/2026/07/a1/b2/a491f20c...9d.png`

历史路径 `YYYY/MM/req_{requestID}/...` 仍由读取接口兼容。

### 4.3 元数据结构（AttachmentMetadata）

| 字段 | 说明 |
|------|------|
| type | image \| file |
| content_type | MIME 类型 |
| size | 解码后字节数 |
| path | 相对 BaseDir 的存储路径 |
| hash | SHA256 十六进制 |
| original_url | 原始引用（data URI 截断至 200 字符） |
| message_index | 所在消息索引 |
| block_index | 块索引 |
| created_at | 保存时间 |
| status | 最新持久化生命周期状态（detected / storing / stored / manifest_ready / sent / store_failed） |
| error_code | 存储失败原因（storage_unavailable / invalid_data_uri / file_too_large / storage_failed） |

### 4.4 配置

| 环境变量 | 默认值 | 说明 |
|---------|--------|------|
| `LLM_GATEWAY_ATTACHMENT_DIR` | `./data/attachments` | 存储根目录 |
| `LLM_GATEWAY_ATTACHMENT_MAX_SIZE` | 20MB | 单文件上限 |

## 6. 已知限制

1. **base64 仍在请求体中传输**：附件提取后，原始 base64 数据
    仍留在 request body 中转发给上游，未替换为供应商兼容的引用。
    这会增加网关带宽、日志和重试缓存体积；是否影响 token/费用取决于供应商和模型，不能由网关假设。

2. **无 video/audio/PDF 提取**：Extractor 只处理 image 类型，
   不提取 video、audio、PDF 等其他多模态块。

3. **附件预览仅限图片**：admin 前端只渲染图片预览，
    不支持 video/audio/PDF 内联预览。

4. **OSS/S3 后端不可用**：附件只能存本地文件系统（详见 01 审计报告）。

5. **供应商引用未建模**：当前附件元数据只有本地 `path` 和截断的 `original_url`，
   尚未记录目标供应商、引用模式、签名 TTL、provider file id、MIME 探测结果和可重放状态。
