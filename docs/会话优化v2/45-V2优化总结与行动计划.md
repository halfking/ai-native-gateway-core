# 会话优化 V2 总结与行动计划

> **文档版本**: v1.0  
> **创建日期**: 2026-08-06  
> **文档性质**: 执行摘要（Executive Summary）  
> **适用对象**: 技术决策者、项目管理者

## 📋 一句话总结

**V2 表已实现增量写入，但压缩层仍使用 V1 完整历史读取，导致存储优化目标（60-80%）未达成。**

---

## 1. 问题诊断

### 1.1 设计意图 vs 实际状态

| 维度 | 设计目标 | 实际状态 | 差距 |
|------|---------|---------|------|
| **数据写入** | V2 表增量存储 | ✅ 已实现（影子写入） | 0% |
| **数据读取** | 从 V2 表动态拼接 | 🔴 仍读 V1 表完整历史 | 100% |
| **存储节省** | 60-80% | 0%（V1/V2 双写） | 100% |
| **展示层** | 使用 V2 表 | ✅ Admin API 已用 V2 | 0% |
| **压缩层** | 使用 V2 表 | 🔴 仍用 V1 表 | 100% |

### 1.2 核心问题

```
┌────────────────────────────────────────────┐
│  当前架构：V2 只写不读                      │
├────────────────────────────────────────────┤
│                                            │
│  请求处理流程                               │
│    ↓                                       │
│  压缩层 (SessionCompressor)                 │
│    ↓                                       │
│  旧缓存 (SessionCache)  ← 问题点            │
│    ↓                                       │
│  V1 表 (request_logs)   ← 完整历史          │
│                                            │
│  V2 表 (session_turns/bodies) ← 未被使用    │
│                                            │
└────────────────────────────────────────────┘
```

**结论**：
- ✅ V2 架构**写入侧**已实现（增量存储）
- ❌ V2 架构**读取侧**未实现（仍读完整历史）
- ❌ **存储优化目标未达成**（V1/V2 双写，磁盘未节省）

---

## 2. 根因分析

### 2.1 为什么压缩层没有使用 V2？

**技术原因**：

1. **缓存架构分裂**
   - 压缩层使用 `SessionCache`（旧架构，读 V1 表）
   - V2 提供了 `SessionCacheV2`（新架构，读 V2 表）
   - **两套缓存未统一**，压缩层未切换

2. **TurnReader 未接入生产**
   - `TurnReader.LoadChain()` 已实现增量拼接
   - `TurnReader.LoadLatestOutbound()` 已实现压缩状态恢复
   - **但仅用于测试和 L3 fallback，不是主流程**

3. **OutboundBuilder 缺失**
   - 设计文档中有"动态拼接"概念
   - **实际代码未实现**从增量重建完整上下文的逻辑

**项目管理原因**：

1. **Phase 划分不清晰**
   - Phase 0-2.2 完成了"写入侧"
   - **Phase 2.3-2.6 未启动**（读取侧切换）
   - 导致 V2 投资未完成闭环

2. **验收标准缺失**
   - 缺少"存储节省 60-80%"的明确验收点
   - 缺少"压缩层使用 V2"的里程碑检查

### 2.2 影响评估

| 影响维度 | 严重程度 | 说明 |
|---------|---------|------|
| **存储成本** | 🔴 高 | V1/V2 双写，成本上升而非下降 |
| **维护成本** | 🟡 中 | 两套缓存并存，增加复杂度 |
| **技术债务** | 🔴 高 | V2 投资未完成，代码存在但未用 |
| **用户体验** | 🟢 低 | 不影响功能，性能未优化 |

---

## 3. 解决方案

### 3.1 整体策略

**三步走**：

```
Step 1: 压缩层切换到 V2 缓存
  └─ 让压缩层使用 SessionCacheV2 + TurnReader

Step 2: 灰度验证
  └─ 10% → 50% → 100% 切换，监控指标

Step 3: V1 表下线
  └─ 停止 V1 写入，归档历史数据
```

### 3.2 核心改动

#### 改动 1: 实现 OutboundBuilder

**新增文件**: `domains/session/v2/outbound_builder.go`

```go
// BuildFromDeltas 从增量重建完整会话上下文
func (b *OutboundBuilder) BuildFromDeltas(
    ctx context.Context,
    tenantID, sessionID string,
    lastN int,
    preserveCompression bool,
) ([]Message, *BuildMeta, error)
```

**职责**：
- 调用 `TurnReader.LoadChain()` 读取增量
- 拼接多轮 delta 为完整消息数组
- 过滤或保留压缩 marker

#### 改动 2: 完善 SessionCacheV2 L2 层

**新增文件**: `domains/session/v2/cache_v2_redis.go`

```go
// RedisGovernanceCache 实现 L2 Redis 缓存
type RedisGovernanceCache struct {
    client *redis.Client
    ttl    time.Duration
}
```

**职责**：
- 存储治理元数据（verdict、audit 结果）
- Redis key: `session:v2:{tenantID}:{sessionID}`
- TTL: 30min

#### 改动 3: 改造 SessionCompressor 依赖

**修改文件**: `domains/hooks/compression/session_compressor.go`

```go
type SessionCompressorDeps struct {
    Cache *SessionCache // 标记 deprecated
    
    // 新增依赖
    CacheV2 *v2.SessionCacheV2
    Builder *v2.OutboundBuilder
    
    CompactionDeps *Dependencies
    Disabled       bool
}
```

**改造 Prepare 方法**：
- 通过 Feature Flag 选择 V1/V2 路径
- V2 路径：`CacheV2.Get()` → `Builder.BuildFromDeltas()` → 压缩决策
- V1 路径：保留作为 fallback

#### 改动 4: Feature Flag 配置

**新增配置**: `settings/spec_sessions_v2.go`

```go
sessions_v2_compression_read: bool  // 启用 V2 压缩读取
sessions_v2_rollout_percent: int    // 灰度百分比
```

**目标**: 压缩层使用 V2 表读取历史

**任务**:

#### **Phase V2-2.5: 灰度切换**

**目标**: 安全切换到 V2 读取

**灰度计划**:
- Week 1: 10% 灰度（3 天观察）
- Week 2: 50% 灰度（3 天观察）

**监控指标**:
- 错误率 < 0.1%
- p99 延迟 < V1 * 1.2
- 缓存命中率 >= 90%

**回滚条件**:
- 错误率 > 1%
- p99 延迟 > V1 * 2

**工时**: **2 天开发 + 13 天观察**

#### **Phase V2-3: V1 表下线**（未来）

**目标**: 停止 V1 写入，达成存储节省目标

**前置条件**:
- V2 稳定运行 >= 4 周
- 存储节省目标达成（60-80%）

**任务**:
1. DualWriter 改为 V2 单写
2. 归档历史 V1 数据
3. 删除 SessionCache 旧代码

**工时**: **1 周**

## 8. 关键决策点

### 8.1 是否立即推进？

**推荐**: ✅ **是**

**理由**:
1. **技术债务明确**：V2 投资已完成 50%，需要闭环
2. **收益明确**：存储节省 60-80%，ROI 320%
3. **风险可控**：Feature Flag 秒级回滚，V1 保留作为 fallback
4. **时间窗口**：当前无重大功能上线，可以专注优化

**不推进的风险**:
- V2 投资浪费（已投入代码未产生价值）
- 存储成本持续上升（V1/V2 双写）
- 技术债务累积（两套缓存并存）

### 8.2 快速通道 vs 保守通道？

| 通道 | 时间 | 风险 | 推荐场景 |
|------|------|------|---------|
| **快速** | 3.5 周 | 中 | 存储成本压力大，团队资源充足 |
| **保守** | 2-3 月 | 低 | 追求稳健，观察期可以更长 |

**推荐**: **快速通道**

**理由**:
- 代码改动量不大（~1,810 行）
- 已有完整测试策略
- Feature Flag 回滚快速
