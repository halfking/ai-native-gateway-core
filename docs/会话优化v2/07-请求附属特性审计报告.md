# 请求附属特性审计报告

> 审计日期：2026-07-15
> 审计范围：请求的三类附属特性——**客户端信息**（智能体、IP、客户端识别码、客户ID等）、**请求信息**（原生/重试、测试、轮次等）、**会话扩展信息**（项目、任务、标题、摘要等）
> 审计方法：源码静态分析 + 迁移文件核对 + 写入路径逆向追踪 + 死代码检测
> 目的：为"客户端感知·审计·画像优化"提供事实基础，回答"我们现在到底采集/落库了什么"

---

## 0. 核心结论

基础设施**大多已存在但处于"断线"状态**。具体表现为四种典型病灶：

1. **死代码**：`telemetry/request_metadata.go` 写好了 AgentName/AgentType/ClientIP/协议提取逻辑，但全仓库仅其自身测试引用，主管线与 INSERT 路径均未调用。
2. **脚手架齐全零接线**：`client_profiles` 表 + `domains/clientprofile`（Store/Aggregator/Worker/EventEmitter/integration.Setup）全部就绪，但 `SetupClientProfileIntegration` / `Setup` 零调用方，画像从不运行。
3. **桥接函数只在测试调用**：`ApplyOriginFromContext`（origin→entry 的 ctx 桥接）只被 `client_test.go` 调用，生产路径从不调用——连已绑定的 `client_ip`/`origin_stage` 实际也可能未真正落库，与代码注释声称的"2026-07-14 起已写入"矛盾。
4. **迁移超前于实现 + 热表缺列**：2026-07-11 observability 迁移给 `request_logs` 加了 26 列（agent_name/agent_type/api_key_fingerprint/customer_id/client_protocol/session_title 等），但写入方从未补齐；且 `request_logs_hot`（INSERT 真实目标）用 `LIKE request_logs` 一次性创建，observability 迁移只 `ALTER request_logs`，**hot 表很可能缺这些列**（2026-07-13 multimodal P0 事故的同型问题）。

**架构取向**：不向 request_logs 继续塞列，**新建 `request_context_attrs` 侧表**承载全部三类附属属性，request_logs INSERT 零改动（规避 hot 表缺列的 42703 事故）。

## 1. 客户端信息维度

### 1.1 客户端身份（identity）—— 基础最完整

| 字段 | 计算位置 | 是否落 request_logs | 现状 |
|------|---------|-------------------|------|
| `identity_hash` (SHA-256 64hex) | `domains/identity/identity.go:226` | ✅ 写入（client.go INSERT $32） | 完整 |
| `VirtualClientID` (vc-+hash[:16]) | `identity.go:230` | ❌ 基表有列无写入方 | 缺口 |
| `VirtualIP` / `VirtualMAC` | `identity.go:228-229` | ❌ 基表有列无写入方 | 缺口 |
| `DeviceSeed` / `MachineID` | `identity.go:148-149` | 仅作哈希输入，不单独存 | 设计如此 |
| `ClientProfile` | `identity/hook.go:72` | ✅ 写入 | 完整 |

身份锚点：`tenantID + appOrKey(app{N}/key{N}) + PrimarySeed + salt`，salt 来自 `LLM_GATEWAY_IDENTITY_SALT`。

### 1.2 智能体 / User-Agent —— 死代码

| 字段 | 提取逻辑 | 是否落库 | 现状 |
|------|---------|---------|------|
| User-Agent（原始） | `identity.go:154`（混入指纹） | ❌（仅 slog + 指纹材料） | 部分 |
| `agent_name` | `telemetry/request_metadata.go:95 ExtractAgentName` | ❌（列存在无写入方） | **死代码** |
| `agent_type` (web/cli/api/bot) | `telemetry/request_metadata.go:137 ExtractAgentType` | ❌（列存在无写入方） | **死代码** |

`ExtractAgentName` 优先 `X-Agent-Name`，否则解析 UA 识别 claude-code/opencode/cursor/vscode/jetbrains/postman/curl 等；`ExtractAgentType` 优先 `X-Agent-Type`，否则推断 web/mobile/cli/api/bot。CORS 允许头 `cors_mw.go:33` **未列** `X-Agent-Name`/`X-Agent-Type`。

### 1.3 客户端 IP —— 4 套不一致逻辑

| 提取器 | 位置 | 优先级 | 用途 |
|--------|------|--------|------|
| `middleware/origin_mw.go:248 resolveClientIP` | 权威 | X-Real-IP > XFF[0] > RemoteAddr | 存 ctx → entry（但 entry 桥接从未调用） |
| `domains/identity/identity.go:181 extractClientIP` | 指纹用 | **XFF > RemoteAddr（不查 X-Real-IP）** | 混入指纹 |
| `telemetry/request_metadata.go:57 ExtractClientIP` | 死代码 | X-Real-IP > XFF[0] > RemoteAddr | 未接入 |
| `cmd/gateway/customer_helpers.go:97` | 限流用 | XFF[0] > echo.RealIP() | license 公共面 |

**关键风险**：`identity.go` 的 IP 解析不查 X-Real-IP，与权威路径不一致 → 同一请求指纹里的 IP 与落库 IP 可能不同源，导致 NAT 后客户端的指纹分裂。

### 1.4 API Key 指纹

| 实现 | 位置 | 口径 | 是否落 request_logs |
|------|------|------|---------------------|
| `cmd/gateway-v2/main.go:99 fingerprintKey` | 独立二进制 | SHA-256[:16] | 写 `api_key_fp`（仅 gateway-v2） |
| `request_logs.api_key_fingerprint` 列 | 迁移注释 | "first 8 chars" | ❌（主 gateway 无写入方，列名/口径都不一致） |

### 1.5 账户 / 租户 —— 完整但有 customer 缺口

| 字段 | 来源 | 是否落库 | 现状 |
|------|------|---------|------|
| `tenant_id` | `keyInfo.TenantID` | ✅ | 完整 |
| `application_id` / `application_code` | `keyInfo` | ✅ | 完整 |
| `api_key_id` / `api_key_prefix` / `api_key_owner_user` | `keyInfo` | ✅ | 完整 |
| `end_user_id` | `handler.go:3730 resolveEndUser`（body.user > X-End-User-Id > anonymous） | ✅ | 完整 |
| `customer_id` | **无数据源** | ❌（列存在无写入方） | **缺口** |

auth 模型：无 JWT claim，身份来自 API key 查表（`keyVerifier.LookupKeyMeta` → `authentication.KeyInfo`）+ 请求指纹。`KeyInfo` 结构体无 `CustomerID` 字段；`applications` 表无 `customer_id` 列；`api_keys` 表无 customer/org 关联。**customer 维度需从 application（账户）→ customer 映射新建**。

## 2. 请求信息维度

`request_logs` 是"结果行"而非"性质行"——它记录结局（成功/失败/token/延迟），但不内建"第几次重试/是否探针/第几轮/来自什么渠道"。

### 2.1 原生 vs 重试 —— 分散且语义不一

| 类型 | 表达方式 | 落库 | 现状 |
|------|---------|------|------|
| 客户端重试 | `client_request_id`（X-Gw-Client-Request-Id）跨行聚合 | ✅ | 行内无 `is_retry` 标记 |
| 网关 failover | `candidate_failure_logs.attempt_index`（迁移 392） | 仅失败行 | 成功 failover 不可见 |
| 网关 follow-up 重试 | `X-Gw-Follow-Up-Attempt` + context `FollowUpDepth` | 产生独立行 | 无落库列 |

### 2.2 测试 / 探针 —— 双轨重叠

| 机制 | 写入方 | 表达 | 落库 |
|------|--------|------|------|
| 重载 `task_type` | `bg/active_probe_emitter.go:138` | `task_type='probe_triggered'` + `task_type_chosen` ∈ probe_* + `auto_decision{probe_attempt:N}` | ✅ |
| 专用列 `origin_stage` | `middleware/origin_mw.go` | self_check/node_probe/system_health/business + legacy probe_* | ✅（但桥接未调用，见 §0） |

无统一的"这是探针而非真实用户请求"布尔位，需多处字段拼合（`admin/probe_request_info.go:34 extractProbeInfo`）。

### 2.3 会话轮次 —— 基本未落地

| 表 | 列 | 写入方 | 现状 |
|----|----|--------|------|
| `session_turn_snapshots`（迁移 385） | `turn_no` | **无 Go writer** | 建表未启用 |
| `session_intent_evolution`（迁移 359） | `turn_number` | `intentconfig/store.go` | 仅意图分析用 |
| request_logs 派生 | — | `ROW_NUMBER() OVER(PARTITION BY gw_session_id ORDER BY ts)` | 查询时现算（extract_session_test_data.sql:48） |

### 2.4 请求来源渠道 —— 完全缺失

`telemetry.RequestMetadata.AgentType` 推断 web/api/mcp/cli/bot 后即丢弃，无落库列。`origin_stage` 表达"谁产生了这行"而非"客户端渠道类型"。

## 3. 会话扩展信息维度

会话核心关联键统一为 `gw_session_id`（`gw_`+UUID，`domains/session/session_v2.go:14`），传递链路清晰（header→middleware→RequestLogContext→DB）。

### 3.1 字段存储现状

| 字段 | 表 | 写入方 | 现状 |
|------|----|--------|------|
| 会话ID/任务ID | `request_logs.gw_session_id/gw_task_id` | ✅ | 完整 |
| `project`（项目） | — | — | **完全缺失**（仅 vibecoding 模块有 project_id，与会话主链路无关） |
| `task`（任务） | `gw_task_id` / `session_dim.task_id` | ✅（客户端 X-Gw-Task-Id，默认 "default"） | 弱概念，无元数据表 |
| `title`（标题） | `session_titles` + `session_summaries.title` | LLM 双轨生成 | 双轨存储 |
| `summary`（摘要） | `session_summaries.summary` + `session_request_summaries` + `session_turn_snapshots` | LLM 异步 | 三处存储 |

### 3.2 标题/摘要生成链路

- **Summarizer**（`domains/sessionsummary/summarizer.go`）：`GenerateSummary` LLM 生成 title+summary+key_topics，maxTokens 500；`GenerateTitle` 基于首条消息前 200 字。
- 触发路径 A（V4 pipeline 首请求标题，`domains/hooks/sessionanalysis/hook.go`）、路径 B（会话关闭事件，`domains/analysis/workers/session_summary_worker.go`）、路径 C（V1 ChatHandler `handler.go:2979 autoTitleGenerator.MaybeGenerateTitle`）。
- `session_summaries` 的合规列（compliance_status/pii_detected）**存在但无人写入**（悬空契约）。

### 3.3 打标 / 画像体系

- `session_tags` 统一表（迁移 351），双投影器：OLAP `SessionTagger`（`domains/analysis/tagger.go`）+ 热路径 `SessionStateProjector`（`domains/analysis/state_projector.go`）。
- `client_profiles` 表（迁移 132）以 `identity_hash` 为主键，跨会话聚合模型偏好/任务分布/活跃时段。
- `domains/clientprofile` 实现完整：`Store`/`Aggregator`/`ProfileWorker`/`EventEmitter`/`integration.SetupClientProfileIntegration`。
- **但 `SetupClientProfileIntegration` 零调用方** → `client_profiles`/`client_behavior_events` 表实际无数据写入。
