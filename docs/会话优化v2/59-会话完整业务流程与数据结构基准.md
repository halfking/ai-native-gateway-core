## 1. 业务流程全景（5 大主流程 + 3 大横切关注）

### 1.1 流程边界与编号

| 编号 | 名称 | 入口 | 出口 | 关键不变量 |
|------|------|------|------|-----------|
| **BP1** | 客户端请求 → Gateway → Provider 全链路 | HTTP `/v1/chat/completions` 等 | 客户端接收流式/非流式响应 | 单 `QueuedRequest` 单所有者；首字节前可跨凭据切换，首字节后不可 |
| **BP2** | Goal 模式持续会话（Auto Continue / Retry / Loop / Audit） | BP1 响应拦截器链 | 任务完成 / 失败 / 降级 | retry_count 持久化；预算超限降级；loop 检测切换模型 |
| **BP3** | 会话压缩与 V2 增量存储（Submit Mode + OutboundBuilder） | BP1 压缩 hook | 写入 `gateway.session_*` 表或 V1 fallback | turn_no 单调递增；V2 失败仅日志不影响主请求 |
| **BP4** | Token 资源管理（FpSlot holder + Limiter semaphore + ClientType 识别） | BP1 Acquire 路径 | Release（请求结束/失败/取消） | holder = `{userKey}\|{clientType}`；Lua 脚本与 Redis key 模板不变 |
| **BP5** | Dispatch 多层队列调度（三层队列 + 三模调速器 + 故障转移） | BP1 `executor.Execute` 入口 | 客户端接收响应 | 队列有界；首字节前失败切节点；Stats 非阻塞 |
| **X-1** | 配置加载与热重载（横切） | 启动 + admin PUT settings | settings.Global 内存视图 | 单一权威 → 多层缓存同步 |
| **X-2** | 可观测性（横切） | 各流程关键埋点 | Prometheus / 日志 / 快照 API | 指标命名 `llmgw_*` / `dispatch_*` |
| **X-3** | 持久化与回滚（横切） | deploy 脚本 | 服务可用 + 数据库 schema 一致 | 备份 → 改 → 验证 → 回滚 |

### 1.2 流程交互矩阵

```
                 BP1 请求全链路
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
   BP4 Token 资源    BP5 Dispatch    BP3 压缩
   (Acquisition)    (调度)          (V2 增量)
        │              │              │
        └──────────────┬──────────────�
                       │
                       ▼
                Provider 上游
                       │
                       ▼
                BP2 Goal 模式
              (响应拦截器链)
                       │
                       ▼
                客户端响应
```

- BP4（Token 资源）与 BP5（Dispatch）**并列在请求入口**，都作用于"凭据抢占 + 限流"语义，但维度不同（FP 槽位 vs 队列调度）。
- BP3（压缩）作用于**写路径**：把每轮对话增量落库 `gateway.session_*`；读路径上 BP3 也会被 SessionCacheV2 L1/L2/L3 复用。
- BP2（Goal 模式）作用于**响应拦截**：检测未完成 / 循环 / 审计。

### 2.1 流程图

```

  ▼

  │
  ▼
[2] Executor.Execute (domains/streaming/executors/executor.go)
  ├─ Feature-flag 分支：dispatch_v2.enabled ?
  │   ├─ ON  → executor.dispatchPipeline.Submit(qr)  (BP5)
  │   └─ OFF → 原始候选循环（executor.Execute legacy 路径）
  │

  │
  ▼
[4] Forwarder.attempt (domains/dispatch/forwarder.go)

  │
  ▼

  │
  ▼
[6] Response Interceptors 链（domains/streaming/response_interceptor*）

  └─ OutputCompliance.InterceptNonStream
  │
  ▼
[7] 响应写回客户端（流式 / 非流式）
  │
  ▼
[8] Async Follow-up（response_interceptor_helpers.go::injectFollowUpRequest）
  ├─ 深度检查 < 15，会话计数 < 50
```

## 3. BP2 · Goal 模式持续会话（Auto Continue / Retry / Loop / Audit）

### 3.1 流程图

```
LLM 响应到达
  │
  ▼
[1] ModeHook.InterceptNonStream / InterceptStreamEnd
  │
  ▼
[2] CompletionDetector.Detect (三策略)
  ├─ P0: Structured Output (tool_calls.status = completed/in_progress/failed)
  ├─ P1: Keywords（"任务完成"、"done"、"finished" 中英文）
  └─ P2: LLM Analysis（调用 LLM 返回 0-1 信心分数）
  │
  ├─ 信心 ≥ preset.CompletionConfidence → 任务已完成
  │   └─ AuditHook.InterceptNonStream  [BP2.3]
  │
  └─ 信心 < preset.CompletionConfidence → 任务未完成
      └─ ModeHook.shouldAutoContinue?
          ├─ NO  → 透传响应
          └─ YES → 注入 continue follow-up（增加 auto_continue_count）
              │
              ▼
[3] LoopDetector.RecordResponse (LoopHash)
  ├─ hash 命中次数 >= LoopThreshold → 切模型（增加 model_switch_count）
  └─ hash 未命中 → 透传
  │
  ▼
[4] Goal Store 持久化
  ├─ goal_sessions 表：retry_count / auto_continue_count / model_switch_count
  │   / repeat_count / last_response_hash / current_model
  └─ store.AddRetryCount(...) [DEF-003 修复后真正写入]
  │
  ▼
[5] AuditHook.InterceptNonStream (仅当任务完成)
  ├─ UseAudit=true → 调用 LLM 审计代码质量
  │   ├─ UseAutorouteAudit=true → autoroute.Decider 选审计模型
  │   └─ FallbackModel 配置兜底
  ├─ AuditResult.Issues[]
  └─ AutoFixEnabled && severity ∈ {high,medium}
      └─ 注入 fix follow-up prompt
  │
  ▼
[6] OutputCompliance（脱敏处理）
  │
  ▼
[7] 响应回写客户端
```

| Mode | Retry | Auto-Continue | Loop Detect | Audit | Auto-Fix | Monthly Budget |
|------|-------|---------------|-------------|-------|----------|----------------|
| **minimal** | ✅ (2次, 40s) | ❌ | ❌ | ❌ | � | 500K |
| **balanced** | ✅ (3次, 50s) | ✅ (5次) | ✅ (阈值2) | ❌ | ❌ | 2M |
| **aggressive** | ✅ (5次, 120s) | ✅ (10次) | ✅ (阈值3) | ✅ | ✅ (medium) | 10M |

## 4. BP3 · 会话压缩与 V2 增量存储

### 4.1 流程图（写路径）

```
请求处理完成 / 响应拦截前
  │
  ▼
[1] DualWriter.Write (domains/session/dual_writer.go)
  │
  ├─ FeatureFlag.IsEnabled("sessions_v2.shadow_write") ?   ⚠️ 勘误：实际 key 是 shadow_write，不是 enabled（60 号 NOTE-2）
  │   ├─ false → 仅写 V1
  │   └─ true → 继续
  │
  ├─ FeatureFlag.IsEnabledForSession(rollout_percent) ?
  │   ├─ 不在灰度 → 仅写 V1
  │   └─ 在灰度 → 继续
  │
  ├─ [V1 路径] RequestLogWriter.Write
  │   └─ 失败 → 请求失败（V1 是主写入）
  │
  └─ [V2 路径] SessionWriterV2Interface.Write
      ├─ TurnWriter.AppendTurn（advisory lock 串行分配 turn_no）
      ├─ SessionBodiesWriter.WriteBodiesInTx（增量 deltas）
      ├─ TurnLogsWriter.AppendLog（24h TTL）
      └─ SessionAggregator.UpdateSession（goroutine 异步，由 Stop 等待）
          └─ 失败 → 仅 slog.Warn（V2 是影子写入）
```

### 4.2 流程图（读路径，压缩层）

```
SessionCompressor.Prepare(ctx, clientBody, tenantID, gwSessionID, ...)
  │
  ▼
[1] 决定使用 V1 还是 V2 读路径
  │
  ├─ settings.GetPlatformBool("sessions_v2_compression_read", true)  ⚠️ 默认 true
  │   │
  │   ├─ V2 启用 + CacheV2/Builder 注入
  │   │   └─ tryLoadV2State
  │   │       ├─ CacheV2.HasState → 无历史 → ok=true, body=nil（视为首轮）
  │   │       └─ Builder.BuildLatestOutbound → 取最近一次 outbound_body（保留压缩 marker）
  │   │
  │   └─ 失败 → Fallback 到 V1
  │
  └─ V1 fallback: SessionCache.GetOrLoad
      └─ L3 fallback: request_logs.LastOutboundForSession
  │
  ▼
[2] 计算 delta（BuildOutboundMessages）
  │
  ▼
[3] 压缩决策（shouldCompress）
  │
  ▼
[4] 写入 outbound 到下一轮 SessionBodies.outbound_body
```

### 4.3 SubmitModeDetector 决策矩阵

| 优先级 | 信号 | 结果 | 说明 |
|--------|------|------|------|
| **P0** | `X-Gw-Submit-Mode` 头 | `delta`/`snapshot`/`full` | 客户端显式声明 |
| **P1.5** | 附件变化（消息不变，仅附件变化） | `attachment_only` | 新增优先级 |
| **P1** | 消息数回退 `len(client) < len(lastOutbound) && overlap < 30%` | `inferred_compressed` | 客户端可能压缩 |
| **P2** | Summary marker（`[smm_v1:` / `[summary:`） | `inferred_compressed` | 客户端已压缩 |
| **P3** | Orphaned tool_result（tool_call_id 无对应 tool_calls） | `inferred_compressed` | 异常检测 |
| **P4** | LCS 重叠 ≥ 70% | `full` | 客户端发了完整历史 |
| **P4** | LCS 重叠 < 30% | `inferred_compressed` | 客户端可能压缩 |
| **P5** | 首轮（`LastOutboundBody` 为空） | `full` | 默认 |

### 4.4 三层缓存（V2 读路径）

| 层 | 存储 | 内容 | TTL | 命中率期望 |
|----|------|------|-----|----------|
| **L1** | 内存 LRU（1024 sessions） | `CompressionMeta`（不含 body） | - | >70% |
| **L2** | Redis Hash `session:v2:{tenantID}:{sessionID}` | `GovernanceMeta`（verdict / audit） | 30min | >90% |
| **L3** | `gateway.session_turns` 表 | 元数据（不含 body） | 永久 | 100%（cold start） |

**L0（Turn Delta Storage）**：直接读 `gateway.session_bodies`，**不缓存**（按需计算）

### 6.2 三种并发模式映射

| `concurrency_mode` | 适用厂商 | 上限来源 | 网关行为 |
|---------------------|----------|---------|---------|
| `concurrency` | DeepSeek / 智谱 / Kimi | `concurrency_limit` | in-flight 信号量，超限入凭据队列 |
| `rpm` | OpenAI / Gemini / Groq / Cerebras / SambaNova | `rpm_limit` | 令牌桶（每 `60/rpm` 秒释放 1），队列削峰 |
| `tpm` | OpenAI / Anthropic / Azure / DashScope | `tpm_limit` | 发送前预估 token，按 token 预算放行 |
| `disabled` | 内部/不限流 | — | 直通，不走队列调速 |

> 历史回填：有 `rpm_limit` 且无 `concurrency_limit` → `rpm`；否则 `concurrency`。

### 6.3 关键不变量

1. **单所有者**：任意时刻一个 `qr` 只被一个执行器持有（hand-off，非共享）。`qr` 可变字段无需 mutex。
2. **ResultCh 单发**：`qr.ResultCh` 在请求生命周期内恰好被发送一次（成功/失败/拒绝）。
3. **有界队列**：Tier-1/Tier-2 全部为有界 channel；满即触发 overflow 策略（切凭据/切模型/拒绝），绝不无限堆积。
4. **Stats 不阻塞**：Stats 事件 send 用 `select { case ch <- ev: default: drop++ }`，满即丢弃并计数。
5. **ctx 取消贯穿**：`qr` 携带请求 ctx；客户端断开 → ctx.Done() → 当前持有者放弃 qr 并释放资源。
6. **首字节后不切节点**：沿用 `executor` 包内 `isResumable` 机制（`internal/streamretry` 当前未接线）。
7. **避免双重计数**：`AcquireAllNoCredLayer` 让 dispatch governor 独占凭据层并发/速率，Limiter 只管外层。
8. **热路径可回退**：`dispatch_v2.enabled` 默认 ON，OFF 立即回退原同步候选循环（executor.Execute 旧路径完整保留）。

### 6.4 Overflow 策略

```
Tier-2 满（max_queue_depth 达到）
  ├─ 不入该凭据 → 改试同模型下一凭据
  └─ 同模型全满/全不可用 → 触发模型变更（仅当 allow_model_change=true）

Tier-1 也无路
  └─ ResultCh ← ErrNoRoute → 503 + Retry-After
```

### 6.5 重试预算

- 同凭据重试 ≤ `Policy.RetryPerCredential`（默认 1），再切凭据
- 切凭据/切模型分别计入 `dispatch_failover_total{kind}`

## 10. 核心不变量清单（Cross-Process）

| 不变量 | 含义 | 守护点 |
|--------|------|--------|
| **I-1 turn_no 单调递增** | 同一 session 内 turn_no 严格递增 | `TurnWriter.AppendTurn` 使用 `pg_advisory_xact_lock(hash(tenant_id, session_id))` 串行分配 |
| **I-2 V2 失败不影响主请求** | V2 写入失败仅 slog.Warn | `DualWriter.Write` 分离 V1 主写 / V2 影子写 |
| **I-3 holder 不含 IdentityHash** | 避免设备指纹漂移导致 holder 变化 | `clientTokenOf` 只接受 `userKey + clientType` |
| **I-4 Lua 脚本不变** | 避免破坏 Redis slot 兼容性 | `credentialfpslot/slot.go` Lua 脚本未触碰 |
| **I-5 ResultCh 单发** | dispatch 路径不出现"多发"或"漏发" | `qr.ResultCh` 在 `complete` 中单发 + atomic 守卫 |
| **I-6 首字节后不切节点** | 避免客户端已读字节后被回滚 | `ForwardOutcome.BytesSent` 判定 |
| **I-7 Stats 不阻塞热路径** | 高并发下指标不拖累请求 | `select { case ch <- ev: default: drop++ }` |
| **I-8 retry_count 持久化** | DEF-003 修复后真正写入 | `store.AddRetryCount` + Handler 调用 |
| **I-9 sticky 凭据首次成功即固定** | 保留 prompt cache 亲和 | `dispatchCtx.stickyCredID` 在首次传入 `RouteFunc` |
| **I-10 Goal Retry ctx 取消立即退出** | 客户端断开不浪费 goroutine | retry loop 检查 `retryCtx.Err()` |
