# 请求日志“先有后无”审计与修复报告

> **日期**：2026-07-23  
> **范围**：154 生产实例的实时流、`request_logs_hot`、`request_logs_bodies_hot` 与 Session V2 shadow write  
> **结论**：已定位到 JSONB 参数编码导致的异步更新失败；不是分钟级分区迁移，也没有证据表明已提交的热表记录被删除。

## 1. 现象与证据

用户观察到实时流中的请求初次可查看，数秒至一分钟后详情失败。154 服务日志在一小时内记录了约 537 次：

```text
request_logger: persist update in batch failed (aborting batch)
ERROR: invalid input syntax for type json (SQLSTATE 22P02)
```

同一时段还记录了：

```text
sessionv2mirror: V2 shadow write failed
write bodies: insert bodies: ERROR: invalid input syntax for type json (SQLSTATE 22P02)
```

对日志中多个失败的 request ID 进行数据库核验后，`request_logs_hot` 和 `request_logs_bodies_hot` 中均存在记录且正文非空。这说明：

1. 初始 INSERT 已提交，不是“数据先写后删除”。
2. 失败发生在随后的异步 UPDATE 事务，导致最终状态、路由尝试、追踪等增量信息未落盘。
3. 实时流在内存事件和持久化状态之间存在时间差，失败后的详情问题仍须在部署后结合 API 租户过滤继续验证。

## 2. 根因

### 2.1 V1 telemetry：未清洗的扩展 JSONB 字段

`sanitizeRequestLogEntry` 仅清洗了 `RequestBody` 与 `ResponseBody`。但 `request_logs_hot` INSERT/UPDATE 还会将以下字段使用 `$N::text::jsonb` 写入 PostgreSQL：

- `auto_decision`
- `compression_meta`
- `outbound_body`
- `outbound_msg_hashes`
- `quality_fix_actions`
- `tool_calls`
- `attachments`
- `routing_attempts`

其中任一 `json.RawMessage` 含不完整 JSON、非法 UTF-8 或无效 escape 都会触发 SQLSTATE `22P02`，继而使该次更新事务回滚。

### 2.2 Session V2：JSONB 绑定使用 pgx 二进制路径

`gateway.session_bodies` 将 JSON `[]byte` 直接绑定到 JSONB 参数。生产日志已显示这种写法触发 `22P02`。V1 中已有约定：将 JSON 作为字符串绑定，并在 SQL 使用 `::text::jsonb`，以绕开 pgx 的 JSONB 二进制编码问题。

## 3. 修复内容

### V1 请求日志

- `AutoDecision` 改用 JSON 清洗，而非普通字符串清洗。
- 对全部扩展 JSONB 字段执行 `sanitizeUTF8JSON`。
- 无法修复的字段被置空，记录字段名与字节数，不记录请求正文或其他敏感内容。
- `strPtrToJSON` 保留末端校验，确保晚到的字段变更不会再使整个事务回滚。

结果是：单个扩展字段异常只会丢失该字段，不会丢失请求日志更新。

### Session V2 shadow write

- `session_bodies` 的 JSON 参数改为字符串绑定。
- SQL 明确使用 `::text::jsonb`。
- 空的可选 JSON（如 `outbound_body`）写入 JSON literal `null`，不传空字符串。

V2 保持 shadow write：失败不会影响 V1 业务请求或 V1 日志主写。

## 4. 测试

新增回归覆盖：

- 无效 `AutoDecision` 和全部扩展 JSONB 字段被清空。
- 有效 JSONB 保持原样。
- V2 `jsonTextOrNull(nil)` 生成合法 JSON literal `null`。

执行结果：

```bash
go test ./domains/hooks/observability/telemetry ./domains/session/v2
go vet ./domains/hooks/observability/telemetry ./domains/session/v2
go build ./cmd/gateway
```

均通过。

## 5. 部署后验证

1. 部署并重启 154 的 `llm-gateway-go.service`。
2. 观察 15 分钟：

```bash
journalctl -u llm-gateway-go --since '15 minutes ago' \
  | grep -E 'SQLSTATE 22P02|persist update in batch failed|sessionv2mirror.*failed'
```

预期无新输出。

3. 用实时流中一个新 request ID 验证：
   - 刚完成时详情可打开；
   - 1 分钟后仍可打开；
   - `request_logs_hot`、`request_logs_bodies_hot` 均存在该 ID；
   - 若详情仍返回 404，单独审计 `GET /api/logs/{request_id}` 的租户过滤和 live-stream 请求 ID 来源。

## 6. 后续事项

- 为 JSONB 字段降级增加指标和告警，不依赖日志 grep。
- 为 `/api/logs/{request_id}` 添加“主记录不存在、租户不可见、正文不存在”的可区分诊断。
- 实现原始请求详情的 metadata/body/routing 分阶段加载；这与本次持久化修复解耦。
