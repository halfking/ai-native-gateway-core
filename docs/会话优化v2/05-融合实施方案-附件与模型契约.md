# 会话优化 v2 融合实施方案

> 日期：2026-07-14
> 状态：供审阅
> 范围：多模态附件、慢上传与重试、会话保真、供应商模型名称契约、全方面测试

## 1. 方案结论

现有 Phase 1 已修复 OpenAI 与 Anthropic 跨协议转换中的主要丢图问题，且本地目录附件存储已经可用。后续不应把“统一存储 URL”误认为“所有供应商都能使用同一个 URL”。融合后的目标是：

1. 附件先进入网关控制的本地目录，使用 SHA256 两级分片和临时文件原子提交。
2. 可选同步到 `files.kxpms.cn`，得到稳定的文件 URL、缩略图 URL 和下载 URL。
3. 根据供应商能力选择 `data`、可达 HTTPS URL 或供应商 Files API，不支持时明确拒绝或保留原始格式。
4. 附件上传失败不再静默丢失，按 strict/best-effort 策略记录并告警。
5. 供应商 failover 复用已经落盘的附件和同一个 manifest，不重复上传。
6. 会话压缩、重试和协议转换前后校验附件引用数量、顺序和内容哈希。
7. 客户端模型进入系统后使用小写标准模型名；供应商调用使用采集到的原始模型名，保留大小写。
8. `standardized_name` 等内部匹配字段在入库时标准化为小写，SQL 使用直接等值匹配，不再用 `lower(...)` 兜底。

## 2. 与现有方案的融合与修正

### 2.1 保留的结论

- `docs/会话优化v2/02-多模态能力审计报告.md` 中 Phase 1 的协议保真修复继续作为基础。
- `docs/会话优化v2/03-多模态技术方案.md` 的供应商感知引用模式继续保留。
- `docs/会话优化v2/04-厂商标准与适配矩阵.md` 的 `data`、`gateway_url`、`provider_file` 三种模式继续作为适配器契约。
- 当前本地目录存储保留为生产可用的第一阶段后端，不把 OSS/S3 修复作为本需求的硬前置。

### 2.2 修正的结论

旧提案中“上传失败后继续发送 base64”只能作为显式 best-effort 模式，不能作为生产默认行为。默认采用 strict：附件保存失败时不向供应商发送，并在 `request_logs` 与附件状态中留下可重试记录。环境变量 `LLM_GATEWAY_ATTACHMENT_STRICT` 默认 strict，只有设为 `"0"` 才降级。

旧提案中的 `request_logs.request_body` URL 化必须分层实施：先保证上游真实 body、日志脱敏和重试缓存的一致性，再按供应商能力替换引用。不能无条件把 `files.kxpms.cn` URL 发送给无法访问该 URL 的供应商。

## 3. 附件生命周期

```text
detected -> storing -> stored -> manifest_ready -> sent
             |
             v
       store_failed
```

> 实际代码中 `cancelled` 和 `rewrite_rejected` 尚未实现。
> strict 模式下 store_failed 直接阻断请求转发（返回 503）。

### 3.1 本地目录

目录采用时间和内容哈希分片：

```text
{baseDir}/YYYY/MM/{sha256[0:2]}/{sha256[2:4]}/{sha256}{extension}
```

例如：

```text
/data/attachments/2026/07/a4/91/a491f20c...9d.png
```

写入必须遵循：

1. 先写随机临时文件。
2. 计算并校验 SHA256、大小和探测 MIME。
3. 使用原子 rename 提交最终文件。
4. 相同内容并发写入时复用已存在文件，清理自己的临时文件。
5. 禁止把客户端原始文件名直接拼入路径。

这比当前 `YYYY/MM/req_{requestID}/...` 更适合全局去重和目录均衡；请求 ID 继续保存在逻辑附件记录中，不作为物理分片键。

### 3.2 慢上传和超时

附件处理必须发生在供应商请求发送之前。客户端 body 未读完、附件未落盘或 manifest 未完成时，不得向供应商发送不完整请求。

建议配置：

```text
单附件存储超时：可配置，默认 30s
单请求附件总超时：可配置，默认 120s
并发上传数：默认 5
临时文件清理：启动扫描 + 定时扫描
```

本地写入失败仅对临时性错误重试 2-3 次，指数退避；格式错误、超限、权限错误和磁盘不足直接失败。

### 3.3 供应商 failover

附件保存和 manifest 生成只执行一次：

```text
保存附件 -> attachment manifest
供应商 A 失败 -> 复用 manifest
供应商 B 重试 -> 只重建供应商请求格式
```

不得在每次供应商重试时重新解析 base64、重新计算哈希或重新写文件。附件物理文件以 SHA256 去重，逻辑引用以 `request_id + attachment_index + sha256` 幂等。

## 4. 数据与日志

推荐新增 `request_attachments` 逻辑表，至少包含：

```text
request_id, tenant_id, attachment_index
message_index, block_index
file_id, file_url, thumbnail_url, download_url
content_type, sniffed_type, size_bytes, sha256
source_type, upload_status, upload_error_code
provider_id, provider_reference_mode, provider_file_id
stored_until, provider_reference_until, replayable
```

`request_logs` 只保留轻量字段：

```text
attachment_count
attachment_manifest_status
attachment_url_rewritten
```

历史 `attachments` JSONB 保留兼容读取，但新请求不得写入 base64、data URI 或临时路径。原始 request body、outbound body、trace、重试缓存和错误日志统一执行脱敏策略；只有显式审计开关、短 TTL、加密和严格权限下才允许保留原始 body。

## 5. 会话和协议保真

Phase 1 修复继续有效，但需要增加统一附件引用校验：

```text
request refs == transformed refs == outbound refs
```

校验内容包括数量、顺序、消息索引、块索引和 SHA256/file_id。含附件的消息默认不可被摘要删除；允许压缩文本，但必须保留附件块。校验失败时返回结构化 `attachment_integrity_error`，不能静默发送已丢附件的请求。

必须覆盖 OpenAI Chat、Anthropic Messages、Gemini Generate 三条入口。Gemini 的 `file_uri` 不能当作通用 HTTPS URL 透传，必须由 Gemini adapter 管理。

## 6. 模型名称契约

| 字段 | 规则 |
|---|---|
| 客户端输入 | 可保留原文用于审计，进入路由前生成小写标准值 |
| `models_canonical.canonical_name` | 小写标准模型名 |
| `provider_models.standardized_name` | 小写匹配名 |
| `provider_models.raw_model_name` | 供应商采集的原始名称，保留大小写 |
| `outbound_model_name` | 供应商 API 实际名称，保留大小写 |
| 客户端输出模型 | 小写标准模型名 |
| 供应商请求模型 | 原始供应商模型名 |

采集入库时必须同时写入：

```text
raw_model_name = vendor response exact value
standardized_name = NormalizeRouteKey(raw_model_name)
canonical_id = matched standard model ID
```

需要清理以下风险：

- `RawModels` 不得使用 `lowerUnique`，否则会破坏供应商原始名称。
- 内部 SQL 参数在调用前完成标准化。
- `provider_models.standardized_name`、`model_aliases.raw_name_key` 等匹配字段增加小写约束或独立 key。
- 路由 SQL 从 `lower(column) = lower($1)` 收敛为 `column = $1`。
- 原始模型名只用于向供应商发送、诊断和展示，不用于标准模型匹配。

## 8. 分阶段实施

### Phase 2A：本地附件可靠性

- 两级 hash 目录和原子写入；
- strict/best-effort 策略；
- 上传状态和失败原因；
- 慢上传、超时、取消和临时文件清理；
- failover 复用 manifest。

### Phase 2B：供应商感知引用

- files.kxpms.cn adapter；
- data/gateway_url/provider_file 三种引用模式；
- URL 可达性、签名 TTL、MIME、SSRF 和大小校验；
- OpenAI、Anthropic、Gemini、Mistral 适配器契约测试。

### Phase 2C：日志脱敏和数据迁移

- 新增逻辑附件表；
- 新请求只写 URL/manifest 引用；
- 历史附件兼容读取和 backfill；
- request body、outbound body、trace 和重试缓存统一脱敏。

> **2026-07-15 状态**：逻辑附件表已落地（migration 401），与
> `request_logs.attachments` JSONB 双写；request body 脱敏已默认启用

> 历史 backfill 和 URL 化引用待 Phase 2B 上传契约确认后启动。

### Phase 2D：模型名称治理

- 全局修正 raw/standardized/canonical 字段；
- SQL 等值匹配；
- 数据库校验和历史数据清洗；
- S25-S28 回归。

### Phase 3：管理端体验

- 视频、音频、PDF 预览；
- Cloudreve 缩略图和下载 URL；
- 上传失败和不可重放状态展示；
- 数据生命周期中的文件和逻辑记录双向清理。

1. `go test ./...`、`go build ./...`、`go vet ./...` 通过。
