## 2.1 视口档位矩阵（模拟级，2026-10-07 新增）

§2 的 M-1~M-7 是**真机**矩阵。本节是**另一件事**：把「一条 CSS 视口宽高」映射到
[01 §2](./01-原则与断点.md) 的语义档，并说明每档**专门抓什么**。

⚠️ **两者的证据等级不同，不可互相顶替**：
视口矩阵是**模拟级**（Chrome headless + CDP 设视口，跑的是本仓构建 × 生产数据）；
真机矩阵是**运行级**（真实 WebView、真实 GPU、真实输入法、真实 ROM）。
**视口全绿不等于真机过了** —— 它证明的是「几何与样式在该宽度下自洽」，
证明不了「在 360dp 真机上看起来对」（这正是 V-8 的现状）。

### 档位判据（真源，不手写数字）

⚠️⚠️ **订正（10 §4.6.61）**：本节原先把 [01 §2](./01-原则与断点.md) 的
`768 / 1024 / 1440` 当成 `/m/*` 的分档依据，**用错了 SSOT**。
`768/1024/1440` 是**桌面侧 `web/`** 的断点（SSOT：`web/src/config/breakpoints.ts`）；
**移动端 `web-mobile/` 有自己一套**：`web-mobile/src/composables/useWindowClass.ts`
的 `BREAKPOINT_MEDIUM_PX=600 / EXPANDED_PX=960 / LARGE_PX=1280`，
该文件头注明确写着「600/960/1280 **不是** 01 §2.1 的 768/1024/1440，也不是笔误……
**不要拿一套去改另一套**」。⇒ 下面这张表按移动端真源写。

| 语义档 | 移动端宽度区间（`useWindowClass.ts`） | 关键形态 | 桌面 `web/` 同名档 |
| --- | --- | --- | --- |
| `compact` | `< 600` | 抽屉导航、单列、卡片化表格、**吸底栏**、贴底 sheet | `< 768` |
| `medium` | `600 – 959` | 2 列栅格、抽屉导航、**无吸底栏** | `768 – 1023` |
| `expanded` | `960 – 1279` | 现状桌面顶栏布局 | `1024 – 1439` |
| `large` | `>= 1280` | 大屏内容最大宽度约束 | `>= 1440` |
| （微调）`small` | `< 480` | 只调字号/按钮尺寸，**不改变布局结构** | 同 |

两套数字**并存且都是事实**（17 号文档第 33 行已登记），差别不是笔误而是两侧各自的取舍。
**读 `/m/*` 的档位只能查左列。**
`small` 的 480 来自 01 §2 的微调档，移动端未另设阈值，仍按左列读。

### 14 档审计视口 → 设备档位

| 视口 | 语义档 | 对应真机形态 | 这一档专门抓什么 |
| --- | --- | --- | --- |
| `320×800` | compact + small | iPhone SE 1 代 / 最小窗 WebView | 窄屏地板：长 ID 断破、栅格收缩、底栏压末行 |
| `360×800` | compact + small | 主流 Android（红米 / Galaxy A） | **基数机型**，绝大多数国产机的实际宽度 |
| `390×844` | compact + small | iPhone 12/13/14 | compact 主路径基准 |
| `412×915` | compact + small | Pixel / 大屏 Android | 大屏 compact：留白是否过多、元素是否被拉伸 |
| `568×320` | compact | **窄横屏手机**（iPhone SE / 小屏 Android 横握） | ★ 唯一会同时出现「compact + 横屏 + 吸底栏」的档：矮视口下吸底栏与内容区争用 |
| `600×800` | ★ **medium** | 折叠屏**折叠态** / 小平板竖屏 | 断点线本身（`>= 600` 即离开 compact，吸底栏消失） |
| `740×360` | ★ **medium** | **横屏手机**（矮视口） | 2 列栅格在 360px 高度上的纵向预算 |
| `914×411` | **medium** | **横屏手机**（宽而矮，iPhone 14 Pro Max 横握约此宽） | 横屏刘海/手势区：浮层有没有消费横向 inset（10 §4.6.61） |
| `840×673` | **medium** | **折叠屏展开态**（Fold 类，内屏约 840 CSS px 宽） | 展开后仍是 medium：铰链两侧的列宽与 2 列栅格 |
| `768×1024` | medium | 平板竖屏（iPad） | medium 常规 |
| `1024×600` | expanded | 平板横屏 / 分屏 | 矮 expanded：顶栏 + 多列栅格同时成立 |
| `1024×768` | expanded | 平板横屏（iPad Pro） | expanded 常规 |
| `1194×834` | expanded | **iPad Pro 11" 横屏** | 大屏 expanded 的真实宽度（非 1024 的整数档） |
| `1280×800` | ★ **large** | 常规笔记本 | `>= 1280` 即 large（不是 expanded）；桌面零回归基准 |
| `1440×900` | large | 大屏作业台 | 内容最大宽度约束 |

★ 标记的 4 行是本轮**订正**过的（原先按 768/1024/1440 贴档，贴错）。
本表的档位列由 `web-mobile/src/composables/viewport-matrix.spec.ts`
对着 `useWindowClass.ts` 的常量**逐行验算**，手改错会红。

### ★ 订正后的真结论：横屏手机**几乎全部**落 medium，不是 compact

`600 <= 宽 < 960` 一整段都是 medium。而横握时手机 CSS 宽度通常落在
`568`（SE 横屏）~ `932`（Pro Max 横屏）之间 ⇒ **14 档里 13 档与横屏相关的宽度中，
只有 `568×320` 一档是 compact**。

后果有两条，都可实测：

1. **吸底栏（`AppBottomNav`）在绝大多数横屏形态下根本不存在** ——
   `HyperApp.vue` 的 `showBottomNav = windowClass === 'compact'`。
   实测 `740×360` 与 `914×411` 的 `position:fixed` 元素只有顶栏（sticky），
   `.bottomnav` 不在 DOM 里（10 §4.6.61 实测读数）。
2. 因此**「横屏手机」在本仓从来没有被当作 compact 设计过**，
   而 `568×320` 是唯一能同时验到「compact + 横屏 + 吸底栏」的视口 ——
   它必须留在矩阵里，且**不能**被「横屏就是跑 914×411」的说法替换掉。

⇒ 横屏验收**至少**要跑 `568×320`、`740×360`、`914×411` 三档：
它们分别是 compact / medium 矮 / medium 宽，只跑一档等于没测。
这条已并入 [10 §4.6.54](./10-审计与实施路线.md) 的读数口径与 §4.6.61 的实测。

### 本节的证据边界（不得当作已验证）

- 本节登记**档位映射关系**，其正确性由 `web-mobile/src/composables/viewport-matrix.spec.ts`
  对 `useWindowClass.ts` 的常量**逐行验算**保证；**不是**本轮手工核对。
- 每档「专门抓什么」是**设计意图**；该档**实际抓到了什么**要看
  [10 §4.6.54](./10-审计与实施路线.md) 与 §4.6.61 的实测读数，**两者不要混为一谈**。
- **零真机读数。** 本节全部结论在 M-2/M-4 取证前都不解除「模拟级」标注。
