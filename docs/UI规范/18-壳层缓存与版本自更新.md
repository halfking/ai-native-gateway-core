## 1. 为什么不用「把前端打进 APK」

先排除一个看起来更直接的方案，因为它在本类项目里是**错的**：

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 壳内打包完整 SPA（`webDir: dist`），数据走 API | **不采纳** | ① 页面 origin 变成壳 origin，API 变成**跨源**调用，而后端默认不注册 CORS（前端由它同源托管），必须为壳 origin 单独开白名单；② 每次前端改动都要发 APK，"免发版更新"这个收益直接归零；③ origin 变化会破坏同源带来的会话 / 滚动历史 / 上传下载 |
| **远端同源 + 设备本地缓存框架（Service Worker）** | **采纳** | ① origin 不变，API 零改动、零 CORS；② 框架缓存在设备上，打开不依赖网络；③ 服务端换构建后由部署序号触发更新，**仍然免发版** |

> 结论不是「本地缓存更好」，而是「**在保持同源的前提下**才有本地缓存」。任何要求改 origin 的方案都要先回答 CORS 与发版两个问题。
>
> 本仓注：D1 与「壳内只装引导页」的既有决策（00 §5.1「壳内不打包 web/dist」）同向，
> 本篇把「为什么不打包」从直觉升级为三条可核验的理由。

## 2. 三层缓存与各自的失效口径

「打开快」不能靠把所有东西都缓存。三层各有各的失效理由，**混在一起就会出现「界面很快但数据是昨天的」**：

| 层 | 存什么 | 失效口径 | 允许陈旧吗 |
| --- | --- | --- | --- |
| **L1 框架**（Service Worker Cache Storage） | `index.html`、带内容哈希的 JS/CSS、图标、manifest | `index.html` 每次回源校验（network-first）；哈希资产只随内容变（cache-first） | 允许：拿到的仍是**可运行的**框架 |
| **L2 读缓存**（内存 Map，随会话消亡） | GET 响应 | TTL + 宽限回源；**任何写操作后整份作废** | 仅限读多写少、且用户不照着旧值做决策的端点 |
| **L3 数据** | 不缓存 | 每次请求都到服务器 | 否 |

**硬规则**：

1. **API 响应不进 L1**。SW 的 fetch 事件对 `/api/*` 与健康端点**直接放行**（既不读缓存也不写缓存）。缓存数据请求等于让用户看到过期金额且界面不报错——这是本类项目最危险的静默失败。
2. **写操作不进任何缓存**，且**成功后作废 L2**。写完还显示旧值 = 用户以为没生效。
3. **L2 只在内存里**，不落 localStorage/IndexedDB。落盘会引入跨会话陈旧值，而数据本就该每次从 API 拿。
4. **后端自述的「没有数据」不缓存**：`status ∈ {empty, unavailable}` 的载荷不进 L2。`empty` 是「我现在没有」，缓存它等于把「暂时没有」说成「一直没有」；`unavailable` 是故障态，缓存它会让降级在 TTL 内无法自愈。
5. **用户会照着数字做决策的读，不开宽限回源**（余额、账单、审批状态、签名结果）。宁可多等一次网络，也不能先给旧值再改口。

> 本仓注：规则 5 的「决策类读不宽限」与本仓 13 §6 的「确认类动作必须重新读」同源；
> 规则 1/2 与 13 §1 六态的「如实显示不可用」同源。本篇是它们在**跨会话缓存**维度的延伸。

## 3. 部署序号：定义与比较口径

「自动检查服务端的部署序号」要成立，序号必须满足三个条件：**同源可得、随构建变化、不依赖前端与后端协商**。

- **取值来源**：构建期写入 `index.html` 的 `<meta name="<app>:deploy-seq" content="…">`。取值优先取环境变量，其次取构建工具的版本标识（git 短 SHA），都没有时退化为字面量并**在界面标为不可判定**。
- **为什么落在 `index.html`**：它是指向「当前是哪一批哈希资产」的**唯一入口文件**，与那批资产同属一次构建 ⇒ 天然同源、零后端改动。**不需要新增 `/api/v1/deploy-seq` 端点**：让后端知道前端的存在是本末倒置，它只是静态托管方。
- **比较方式**：本页 `meta` 的值 vs 拉一份远端 `index.html` 读同名 `meta`。不等 ⇒ 服务端换了构建。

**三条禁止**（每条都对应一种看起来在工作、实际在骗人的实现）：

| 禁止 | 后果 |
| --- | --- |
| 拿 `/healthz` 或任何**不变**的端点当版本号 | 永远判定「无更新」，界面显示「已是最新」 |
| 拿**客户端时间戳**与服务器时间戳比 | 时钟漂移与构建耗时造成误报/漏报 |
| 远端**读不到序号**时判定为「一致」 | 服务端跑旧构建时用户永远收不到更新提示，而界面显示「已是最新」——把「我不知道」显示成「我知道没问题」 |

⇒ **读不到就是「不可判定」**，界面必须显示这个状态与原因，不得折叠成绿色 badge。检查请求本身必须绕过 HTTP 缓存（`cache: no-store`），否则读到的是旧序号。

> 本仓注：本仓已有 `/api/system/version`（17 §5 状态条在用）。它是**网关后端**的版本，
> 与**前端构建**序号是两个量——前端换了构建而后端未升版时它不变，恰好踩中第一条禁止。
> 状态条继续用后端版本，前端更新检查只认 deploy-seq meta，两处不得混用。

## 4. 检查时机与自动更新的前提

| 时机 | 动作 |
| --- | --- |
| 启动后空闲 | 第一次检查（**必须晚于首屏落地**，不与首屏数据抢网络） |
| 周期轮询 | 默认 5 分钟；**页面不可见时暂停**，回前台补查一次 |
| 用户手动 | 系统配置页常驻「检查更新」，并显示当前序号、来源、已检查次数 |
| 序号变化 | 静置且无输入焦点 → 自动重载；否则显示非阻塞提示条（立即更新 / 稍后） |

**「自动更新」的前提是不丢用户输入**。重载会清空正在填的表单，所以自动应用必须满足：页面已静置一段时间 **且** 焦点不在输入控件 **且** 距上次交互超过阈值。三者任一不满足就降级为提示条——这是「自动」与「不丢数据」之间的边界，不是可以省掉的细节。

> 检查失败**绝不打断页面**。任何异常降级成「不知道」，由状态字段承载原因。

## 5. 平台可用性与**诚实降级**（必读）

壳缓存依赖 Service Worker，而它**在两类真实环境里不可用**。这不是理论风险，是部署形态的必然结果：

| 环境 | 可用性 | 降级到 |
| --- | --- | --- |
| Android WebView | **可用**（MDN：WebView Android 自 Chrome 40 起支持；`ServiceWorkerController` 为 API 24+） | — |
| **iOS WebView** | **不支持**（MDN 兼容性表：WebView on iOS = No support） | 浏览器 HTTP 缓存 |
| **内网明文 http**（`http://192.168.x.x:8100`） | **不可用**：非安全上下文（只有 `localhost` 豁免） | 浏览器 HTTP 缓存 |
| 壳内引导页 | 不注册（它不是业务前端） | 壳内自带资源 |

**硬规则**：系统配置页必须显示「本地框架缓存：已启用 / 待生效 / 不可用」**并给出原因**。把「不可用」折叠成一个没有解释的灰 badge，等于把「这个功能对你无效」变成「看起来该有却没有」。

> ⚠️ 由此推出一条**文档纪律**：**不得声称 iOS 侧有离线壳**。iOS 上只有 HTTP 缓存，写文档、对外介绍、验收报告都要按这个事实说。
>
> 本仓关联：本仓壳（`llm-gateway-client`）当前只有引导页（§5 表末行）；且 04 §7.1 的
> 结论是「业务页留在 WebView 但桥不注入」——SW 属于页面自身能力、不依赖桥，
> 与桥注入决策**互不阻塞**，但接本篇前应先落该决策。

## 6. 离线兜底与首屏预算

### 6.1 离线只兜框架，不伪造数据

导航请求网络失败时回退到缓存的 `index.html`——这就是「飞机上打开也能看到界面」。**但数据失败必须如实显示不可用**，绝不用缓存值或占位数字填充（与 13 §1、§6 的保旧边界一致：可读 ≠ 可写，确认类动作必须重新读）。

### 6.2 ★ 网络尝试必须有超时上限

真机实测（Android 14，服务器端口不可达）：**`fetch()` 不一定立刻 reject，可以长时间挂着**。而 `event.respondWith(promise)` 会让**整个导航等这个 promise**，于是缓存里明明有 `index.html`，用户看到的却是浏览器自己的导航错误页。

⇒ **网络这一侧必须设上限（建议 3s），到点就放弃网络用缓存。** 没有这个上限，「有缓存」和「用得上缓存」是两件事。

### 6.3 缓存查找必须 `ignoreVary`

静态托管常对资源回 `Vary: Origin`（实测 `vite preview` 即如此）。而构建产物给入口标签加了 `crossorigin`，**页面请求带 `Origin` 头**，预取时用 `new Request(url)` 造出来的请求**不带**。按 Cache API 的匹配算法，Vary 逐头比较后判定**不匹配** ⇒ 缓存里有资产也永远取不出来，离线时整页只剩内联骨架。

命中对象是**内容哈希**资产与同源文档，URL 已唯一决定内容，Vary 不承载语义 ⇒ 一律用 `{ ignoreVary: true }`。

### 6.4 入口资产必须在 install 阶段预取

SW 是在页面**已经把 JS/CSS 加载完之后**才 activate 的，那批请求它截不到。只靠 fetch 事件「顺手缓存」的话，**第一次访问结束时框架缓存是空的**——本地缓存等于没生效（实测：`smm-assets-v1` 压根没建出来）。

⇒ install 阶段主动读 `index.html`、抠出入口资产预取；运行期再由页面把已加载的路由 chunk 清单补给 SW（该通道**必须校验同源与路径前缀**，否则等于让页面往缓存里塞任意 URL）。

### 6.5 怎么量「打开快了多少」（先说清楚测的是什么）

在 localhost 上用受控浏览器量「第二次打开」**会得到漂亮但错误的数字**：基线侧本来就命中浏览器 HTTP 缓存（第二次只传 index.html），localhost 又复现不出真网处境；而经 Service Worker 返回的响应体大小与 HTTP 缓存命中的响应**不可比**。两种误差叠加，结论会指向「本地缓存没带来收益」。

⇒ 承诺口径只用这三类，它们不依赖实验室条件：
1. **结构性移除**（如：冷启动去掉两次探测往返）——按工作项计数，不按耗时估。
2. **类别性改善**（如：服务端不可达时从「浏览器错误页」变成「完整外壳」）——用状态判定，不用毫秒。
3. **能力已具备**（如：`controller` 非空 + 缓存清单非空 + 离线可启动）——读状态，不读时钟。

真实速度数字需在**真机 + 真实网络**下采样；拿不到就写 NOT_RUN，**不要用实验室数字顶替**。

### 6.6 首屏：critical CSS 内联 + 骨架放在挂载点内

- **内联首屏必需的 CSS**（背景、字体、骨架）。少这一步，WebView 会先画一帧默认白底与默认字号再被外部 CSS 拉回，弱网下这一帧被用户直接看见。
- **骨架放在应用挂载点内部**，由框架挂载时清空。⇒ 不需要「挂载后手动删骨架」的代码，也就不存在「删失败 → 骨架永久压在界面上」的白屏失败模式（与 13 §2 同一原则）。
- **首屏预算**（目标值，需按项目实测校准）：入口 JS+CSS 压缩后 ≤ 60KB；关键请求 ≤ 4 个（文档、入口 JS、入口 CSS、首个数据请求）；可见内容不依赖二次往返。

> 本仓注：`web-mobile/` 首轮实测入口 gzip ~47KB（17 §10），落在预算内；
> `web/` 桌面 SPA 是 Element Plus 量级，**不适用 60KB 预算**，其首屏预算另行制定——
> 本节预算约束的对象是「移动端轻实现」，不是无条件全域。

## 7. 落地实测（SMM `smm-client`，2026-10-05）

以下为**实测读数**（参考仓载体），不是设计目标。设备：小米 2411DRN47C / Android 14 / WebView 153；离线行为在受控 Chromium 中复现（真机 WebView 的调试通道在反复重启中不稳定，故离线项分开取证）。

| 项 | 实测 |
| --- | --- |
| Service Worker 注册 | 真机 `activated`，scope `/`，`controller` 非空 ⇒ **Android WebView 上本地框架缓存可用** |
| 框架缓存 | 壳缓存 4 项（index/图标/manifest）+ 资产缓存 9→11 项（入口 JS/CSS + 已访问路由 chunk） |
| 入口体积 | 文档 5.6KB；入口 JS 126KB（gzip 49KB，两个 chunk 由 `modulepreload` **并行**拉取，非串行阻塞）；入口 CSS 23KB（gzip 5KB） |
| 冷启动 | 引导页**零探测直进**业务页（此前每次冷启固定多两个往返）；焦点全程留在 App 的 WebView |
| 离线 | 停服务端后重载：外壳**从本地缓存挂载成功**，仅 API 请求失败并显示「加载失败 / 网络失败」 |
| iOS / 内网 http | **明确不可用**（见 §5），未做 iOS 侧验证 |

### 7.1 三个只有真机/真浏览器才暴露的坑

这一节是本篇最有价值的部分：**三条都通过了代码审查与单元测试，只有在真实宿主里才失败。**

| # | 症状 | 真因 | 判据形态 |
| --- | --- | --- | --- |
| ① | 首次访问后资产缓存**根本没建出来** | SW 在页面资源加载完**之后**才 activate，那批请求它截不到 | SW 行为测试：install 后资产缓存必须含入口 JS |
| ② | 缓存明明有 4 项，离线却是浏览器**导航错误页** | `fetch()` 不一定立刻 reject，可长时间挂着；`respondWith` 让整个导航等它 | SW 行为测试：网络悬挂时必须在超时内回退缓存 |
| ③ | 资产缓存有 9~11 项，离线时入口 JS/CSS 全部 `ERR_FAILED`，页面只剩内联骨架 | 入口标签带 `crossorigin` ⇒ 页面请求带 `Origin`；预取请求不带；静态托管对 `/assets/` 回 `Vary: Origin` ⇒ Cache API 按 Vary 判定**不匹配** | SW 行为测试：带 `Vary` 的资源，查询请求头不同也必须命中 |

③ 的教训值得单列：**它同时骗过了「代码审查」和「单元测试」**。单元测试之所以没抓到，是因为假 `caches` 实现没有复现 Vary 的匹配语义；补上语义后，第一版判据仍然是**恒真断言**（拿请求计数和它自己比），第三版才真正能分开两种实现。

⇒ 通用要求：**缓存策略的判据必须复现宿主的匹配语义**（Vary、`ignoreSearch`、`ignoreVary`），不能只断言「调用了某个方法」。

## 8. 验收清单（可核对，不接受「已完成」）

| # | 判据 | 怎么算通过 |
| --- | --- | --- |
| C1 | API 不进框架缓存 | 断网重载后，界面显示数据不可用，**不是**旧数据 |
| C2 | 导航网络优先 | 缓存热了之后服务端换构建，导航必须拿到新文档 |
| C3 | 离线兜底有上限 | 网络悬挂（不 reject）时，导航在超时内用缓存返回，不是错误页 |
| C4 | 入口资产已预取 | 首次访问后框架缓存里有入口 JS，不是空缓存 |
| C5 | 降级状态可见 | 不可用环境显示原因；iOS 不得出现「本地缓存已启用」 |
| C6 | 读缓存不缓存「没有数据」 | 连续两次读到 `empty`/`unavailable` 会发两次请求 |
| C7 | 写后失效 | 写成功后再次读同一端点，网络上出现新请求 |
| C8 | 不可判定不谎报 | 服务端旧构建（无序号 meta）时显示「不可判定」及原因 |
