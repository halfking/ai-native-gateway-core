# 01 — 原则与断点

> 版本 1.0 · 2026-10-04 · 范围：`web/` + `../llm-gateway-client`
> 本文是**现行约束**。目标设计见 [00-需求与优化方案](./00-需求与优化方案.md)。
> 状态标记：**[已落地]** §1–§4 断点与镜像层；**[部分落地]** §4 的 1px 差异为已知取舍；
> **[未落地]** §5 记录的四项未解决问题（K-1…K-4）。

## 1. 设计原则

1. **桌面零回归**
   ≥1024 的专业顶栏、高密度表、居中弹窗、表格密度，不得因移动适配被改写。
   响应式一律用「新增 `@media` / 新增档位分支」，不改桌面既有规则。
   本轮所有 compact 组件都用 `v-if` 而非 CSS 隐藏，正是为了让「桌面 DOM 里
   根本不存在该节点」可被测试直接断言。

2. **一套代码、按窗口形态**
   不维护独立 mobile 站点。形态由 **window class** 决定，不由 User-Agent 猜测。

3. **手机做快查与审批，不做桌面作业**
   批量配置、密集对账是桌面工作。compact 上可读、可跳转、可确认类轻操作；
   重编辑页标 `desktopOnly`，显示「建议桌面端」横幅，**不藏入口**。

4. **向主流 App 学交互，不抄视觉皮肤**
   底栏对标 iOS TabBar / Material Bottom Navigation（≤5 席、图标+文字、安全区）。
   账户对标系统「我的」页，而不是桌面 dropdown 的缩小版。

5. **壳与 Web 分层**
   壳负责进程、图标、启动屏、网络豁免、引导页、插件位。
   业务 UI 仍是 SPA，财务/网关规则与写入在现有后端。**模式与原生能力分开协商**
   —— `hyperMode` 是交互形态开关，`capabilities` 才证明原生能力可用。

6. **触控优先的下限**
   存量主按钮/菜单项/关闭钮下限 ≥44px；新增 Android 触控控件目标 ≥48 CSS px；
   compact 输入字号 ≥16px（防 iOS 聚焦缩放）。

## 2. 窗口四档（SSOT）

### 2.1 映射表 —— 与参考仓不同，这是本项目的选择

| 档 | 本项目边界 | 典型设备 | 主导航 | 列表 | 对话框 |
| --- | --- | --- | --- | --- | --- |
| **compact** | `<768` | 竖屏手机、壳内 WebView | 底栏 + 汉堡抽屉 | **强制卡片** | **全屏** |
| **medium** | `768–1023` | 折叠展开、平板竖横持 | 抽屉侧栏 | 默认表格，可切卡片 | 居中 |
| **expanded** | `1024–1439` | 平板横屏、常规桌面 | 常驻顶栏 | 同上 | 同上 |
| **large** | `≥1440` | 大屏作业 | 专业壳 | 同上 | 同上 |

参考仓用的是 `600 / 960 / 1280`。**本项目不采用**，理由见 README 的差异表：
本仓已有 95 个视图与一套断点白名单审计门，沿用其数值可保住存量与桌面红线。

### 2.2 数值与双镜像

数值真源只有一个：`web/src/config/breakpoints.ts`。

```
mobile 0 / tablet 768 / desktop 1024 / wide 1440 / small 480
CSS 白名单 MEDIA_QUERY_WHITELIST = [480, 640, 768, 1024, 1440]
```

语义四档在 `web/src/config/window-class.ts`，**由上面派生，不是第二套数值**：

```
compact  下界 0        上界 BREAKPOINTS.tablet   (768)
medium   下界 tablet   上界 BREAKPOINTS.desktop  (1024)
expanded 下界 desktop  上界 BREAKPOINTS.wide     (1440)
large    下界 wide     上界 Infinity
```

- JS 侧入口：`useWindowClass()`（模块级单例 + 三条 `min-width` 查询）。
- JS 判移动**只**走 `useWindowClass` / `getWindowClass()`，禁止新造 px 常量。
- `useBreakpoint`（`isMobile` = <1024）是**布局决策口径**，已被既有代码消费，
  本轮**不改它**。新代码不要混用两套口径。
- `window-class.spec.ts` 钉住双镜像：改 SSOT 而忘同步映射层会立刻报红。

### 2.3 已知 1px 差异（不要"顺手修"）

`styles/responsive-base.css` 存量写的是 `@media (max-width: 768px)`（**含** 768），
而 compact 语义是 **<768**。在恰好 768.0 CSS px 这一条线上，CSS 走移动兜底、
JS 走 medium。

这是 P0 阶段留下的既有形态：改它要动 43 个存量文件并重跑视觉回归，
收益为零、风险为正。**新增 Hyper CSS 一律用 `767.98px`**；存量不动。

## 3. 媒体查询语法

iOS 15 WebView / Safari 15 不支持 Media Queries Level 4 范围语法
（`width <= 959.98px`）；Vite 默认 cssTarget 会把传统 `@media (max-width: …)`
压成范围语法，导致**整层响应式在解析期被丢弃**。

- `vite.config.ts` 必须声明 `cssTarget: ['safari15']`。
- 门禁：`scripts/responsive-audit.mjs`（`pnpm responsive:check`）按白名单审计。
- 新增 media 只用 `min-width` / `max-width` / `min-height` 等传统特性。
- 禁止 `width <=` / `width >=`（`hyper/gates.spec.ts` 也单独钉这一条）。

## 4. 安全区与视口

- `index.html`：`width=device-width, initial-scale=1.0, viewport-fit=cover`
- 令牌：`env(safe-area-inset-*, 0px)`
- **每条边只消费一次**。底栏、顶栏、全屏层各消费自己负责的那条边。
- 不把键盘高度当 safe-bottom；键盘由 Web 视口或原生键盘事件二选一处理。

### 4.1 壳内 inset 的唯一所有者

**Capacitor 8 的 `SystemBars` 插件是系统栏与 inset 的唯一所有者。**
配置位置：`capacitor.config.ts` → `plugins.SystemBars`（`style` / `insetsHandling`）。

三条硬规则：

1. **不要在 `MainActivity` 里手工调 `setDecorFitsSystemWindows`。**
   实测：会让 SystemBars 注入 safe-area CSS 时抛
   `TypeError: Cannot read properties of null (reading 'style')`，页面直接白屏。
   两个所有者抢同一件事。
2. **meta 必须保留 `viewport-fit=cover`。** SystemBars 会检查它，
   缺失时改走 native padding，与 Web 侧 `env()` 叠加 —— inset 加两次。
3. **`prefers-color-scheme` 不等于系统栏外观。** 系统栏图标样式由
   `SystemBars.style` 决定（`'DARK'` = 深色底 + 浅色图标），与 Web 主题无关。

## 5. 已知未解决：API 35+ 系统栏底色（K-1）

**现象**：模拟器 API 36 / targetSdk 36 下，引导页与业务 SPA 内容正常，
但状态栏与手势条仍是**白底**；系统栏图标已按 `SystemBars.style='DARK'` 变浅色，
视觉上白底浅字几乎看不见。

**根因（逐条实测，非推测）：**

| # | 事实 | 证据 |
| --- | --- | --- |
| 1 | Capacitor 的 `SystemBars` 与 `Bridge` **都没有**调 `setDecorFitsSystemWindows` | 在 `node_modules/@capacitor/android` 源码中 grep 无此调用 |
| 2 | 实测 WebView major = **134**，低于 SystemBars 判定 passthrough 的阈值 140 | `dumpsys package com.google.android.webview` → `versionName=134.0.6998.135`；阈值见源码 `WEBVIEW_VERSION_WITH_SAFE_AREA_FIX` |
| 3 | 因 WebView <140，SystemBars 走「**原生 padding**」路径：内容被内缩，露出的窗口背景是白的 | 源码 else 分支 `v.setPadding(systemBarsInsets…)` |
| 4 | `setStatusBarColor()` 后回读为 **`#0`**，即 API 35+ 框架已强制重置为透明 | MainActivity 日志 `statusBarColor=#0` |
| 5 | 改 `res/values/styles.xml` 无效 | `BridgeActivity.onCreate` 调 `setTheme(R.style.AppTheme_NoActionBar)`，那是**库**里的同名主题，运行时覆盖 app 模块定义 |

**已排除的修法**：手工 `setDecorFitsSystemWindows(false)` → SystemBars 报
`Cannot read properties of null` → 白屏。已回退，代码里有注释防止再加回来。

**修复路径（未验证，需后续处理）**：WebView major ≥140 时 SystemBars 走 CSS
passthrough，届时与显式 edge-to-edge 不冲突；或推动 Capacitor 上游统一该所有权。

**影响面**：仅系统栏配色。引导页、业务 SPA、返回仲裁、登录链路均正常。
**不得**在修复前对外宣称「系统栏已适配深色」。

## 6. 原生壳零凭据（红线）

- 壳层**零凭据**。禁止在原生 UserDefaults / SharedPreferences / Keychain 存 JWT。
- Token 只在 SPA `sessionStorage`，杀进程即登出。
- 引导页只把**服务器地址**写进 `localStorage` —— 那是「连哪台机器」，不是凭据。
- 引导页只探测 `/healthz`，不登录。
- 核验方法：解包 APK 后 `grep -iE 'jwt|bearer|api[_-]?key' assets/public/index.html`，
  只应命中**说明该策略的注释**，不应出现真实值。
