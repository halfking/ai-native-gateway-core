## 1. 壳层与 Web 层的责任

**[已落地]**

| 壳层（原生） | Web 层（SPA） |
| --- | --- |
| 进程、启动屏、图标 | 业务规则、请求、渲染 |
| 系统栏、inset | `env(safe-area-inset-*)` 的**消费** |
| 生命周期事件 | 页面可见性 |
| 桥与插件注册 | **能力协商**（不假定存在） |
| 网络豁免 | 鉴权（WebView 持有服务端 HttpOnly session cookie） |

**一句话**：壳提供"可能"，Web 通过协商"确认"，**协商不通过就降级**。

## 2. 远端 SPA 必须先过能力门

**[已落地] 门控 / [未落地] 验证**

引导页 `location.replace` 到业务 origin 后，**页面不一定在 WebView 里**。
不在 WebView 里 ⇒ 桥没注入 ⇒ 插件全不可用。

```ts
// lib/shell/hyper/capabilities.ts —— 四关 fail-closed
桥存在 → 协议版本相符 → origin 精确匹配 → 能力注册表非空
```

**任一关不过即整体降级为普通 Web**，页面功能不变、无原生能力。

**[未落地] 见效性未取证**：[04 §7 A-2](./04-Hybrid外壳.md) / [09 V-1](./09-原生与AI能力调研.md)。
**这是所有原生能力的总闸，未验证前不应开发任何原生能力。**

## 3. 安全区、视口与键盘：只有一个消费策略

**[已落地]**

```ts
plugins: { SystemBars: { style: 'DARK', insetsHandling: 'css' } }
```

`css` = 原生不 padding，只由 Web 侧 `env(safe-area-inset-*)` 避让 —— **单次消费**。
另有 `native`（原生 padding）与 `disable`（全不管），本项目都不选。

**视口 meta 必须含 `viewport-fit=cover`**，否则插件认为不需要 passthrough，
改走 native padding，与 CSS inset **叠加**（双倍避让）。

### 三条禁止回退的实测结论

| # | 禁止 | 实测后果 |
| --- | --- | --- |
| 1 | `MainActivity` 手工调 `setDecorFitsSystemWindows` | `TypeError: Cannot read properties of null (reading 'style')` → **白屏** |
| 2 | 引导页用 `env(safe-area-inset-*)` | 该阶段尚未注入 → **无避让** |
| 3 | 去掉 `viewport-fit=cover` | inset **双倍避让** |

**全局键盘视口避让未实现。** `[未落地]`，iOS 与 Android 的
`visualViewport` 高度变化时机不同，须逐端实测。控件焦点有单独规则：触控设备打开
选择器/表单 Sheet 时先聚焦关闭按钮，不自动聚焦文本框或 select，避免意外弹出键盘；
登录页也不自动聚焦用户名，用户主动点击后再输入。

### 7.1 登录状态跨启动与退出

移动 WebView 使用服务端 `llmgw_session` cookie 保留登录状态。cookie 为
HttpOnly、SameSite=Strict、HTTPS 下 Secure，Max-Age 与 JWT TTL 一致（**当前 7 天**）。
WebView 冷启动后由 `GET /api/auth/me` 水合用户资料；有效 cookie 保持登录，失效或过期
则回到登录页。`localStorage` 只存非敏感用户展示资料与偏好，不能存 JWT、密码或 API Key。

Android 原生 Activity 在进入后台时必须调用 WebView `CookieManager.flush()`，确保刚签发的
HttpOnly 会话 cookie 在进程被系统回收前落盘。此操作只刷新 WebView 的服务端 cookie，
不能把 token 复制到 SharedPreferences、数据库或其它原生凭据存储。

账户 Sheet 的「退出登录」必须请求 `POST /api/auth/logout`，并清理本地用户资料、会话代次
和 Hyper 导航恢复状态。登出后重开 App 必须落在登录页。iOS/Android 不另存一份凭据到
原生偏好或 Keychain/Keystore。

**免登录窗口的实现口径（2026-10-13 由 24h 改为 7d，业务要求）**：

- 「保持登录」勾选 → cookie `Max-Age` 与 JWT `exp` **同步**为 168h；不勾选 → 会话级
  cookie（无 `Max-Age`），关掉即失效。三处取值同源：`admin/auth_params.go` 的
  `CookieMaxAge` / `JWTDefaultTTL` 与 `admin/jwt.go` 的 `jwtExpiry()` 兜底。
  ⚠️ 只改其中一处会出现「cookie 还活着但 JWT 过期 ⇒ 401」。
- ⚠️ **这是绝对有效期，不是滑动续期**：服务端没有 refresh 端点，7 天到期仍需重新登录。
  真机无法把时间快进 7 天，故「7 天内一直不用登录」**未被端到端实测**；
  已实测的是「签发 `expires_at` 确为 168h 后」+「cookie 与 JWT 同步」。

⚠️ **未满足项（沿用本文档原有条款，不得视为已关闭）**：原文要求
「如需超过 24 小时的免登录，需要先增加有轮换与撤销语义的服务端刷新会话，
再评审安全要求，不能靠延长本地 token」。本次**只做到了延长有效期**，
刷新会话未做。已知代价如实登记：

| 项 | 24h 旧口径 | 7d 新口径 |
|---|---|---|
| token 泄露后的可用窗口 | ≤24h | **≤7d** |
| 单会话撤销（踢出某设备） | 不支持 | **仍不支持** |
| 全部设备登出 | 不支持 | **仍不支持** |
| 改密码吊销本会话族 | 支持（`authRevocationProbe`） | 支持（未变） |

⇒ 若安全评审不接受 7d 窗口，**正确做法是上 refresh 会话（轮换 + 撤销 + 单会话
吊销），而不是把 TTL 调回 24h 假装问题不存在**。

**验收**：登录后切到后台并结束进程，在 cookie 有效期内重启 App 应仍是登录态；账户面板登出后冷启动
应要求重新登录；cookie 过期或 `/api/auth/me` 返回 401 时不得残留旧账户界面。
