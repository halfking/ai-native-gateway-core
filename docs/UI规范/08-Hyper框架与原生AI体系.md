## 1. 分层责任与 SSOT

| 层 | 拥有什么 | 绝不能拥有 |
| --- | --- | --- |
| 原生壳（Capacitor） | 进程、系统栏、生命周期、**桥**、插件注册 | 业务状态、金额、鉴权决策 |
| Web 运行时（`lib/shell/hyper/`） | 导航上下文、覆盖层、返回分派、能力协商、连续加载 | 任何绕过协商的插件直调 |
| 业务 SPA（`views/` + `composables/`） | 业务规则、请求发起、渲染 | 原生能力的"假定存在" |
| 服务端（`llm-gateway-go`） | 权威数据、鉴权、限流、模型路由 | 客户端不可信的任何输入 |

**一句话红线**：**原生层不拥有业务决策，Web 层不假定原生能力存在。**
后者由 `capabilities.ts` 的四关 fail-closed 握手保证 —— 任一关不过即整体降级为普通 Web。

## 2. 能力协商与 Bridge 契约

**[已落地] 框架；[未落地] 具体能力]**

握手四关（`PROTOCOL_VERSION = 2`）：

| 关 | 不通过时 |
| --- | --- |
| 桥存在（`window.Capacitor?.isNativePlatform?.()`） | 整体降级为 Web |
| 协议版本相符 | 整体降级为 Web |
| origin **精确**匹配（非 `*` 通配） | 整体降级为 Web |
| 能力注册表可读且非空 | 该能力单独不可用 |

**新增任何能力时的义务**：

1. 在 `HyperCapabilities` 类型里加字段（[06 §5](./06-Hyper导航上下文.md)）
2. 在 `WEB_CAPABILITIES` 里声明**降级值**（Web 侧该能力"没有"时返回什么）
3. **调用点必须先查 `capabilities`，不得用 try/catch 吞掉"插件不存在"**
4. 加门禁：未协商就调用应被 `capabilities.spec.ts` 拦住
5. 真机取证：模拟器与真机都要跑

> ### ★ 为什么第 3 条是红线
>
> "调用了但被 try/catch 静默吞掉"是 AI 能力层最常见的失败形态：
> 功能永远不生效，**没有任何报错**，用户以为是自己数据的问题。
> 能力缺失必须是**可观测**的 —— 降级提示、明确的 disabled 态、或直接报错。

## 3. 通用多层后台任务（目标）

**[未落地]**

三层分类（按"离开页面后是否继续"）：

| 层 | 页面离开后 | 进程被杀后 | 恢复方式 |
| --- | --- | --- | --- |
| **页面态** | ❌ 中止 | ❌ | 重新发起 |
| **应用态** | ✅ 继续 | ❌ 中止 | App 重启后不可恢复，需显式重建 |
| **云端态** | ✅ 继续 | ✅ 继续 | 轮询 / 推送 |

**不能承诺任意后台永久保活。** Android 的后台限制（尤其是国产 ROM 的自启与后台管控）
使"应用态"在部分机型上会被杀。凡是**必须不丢**的任务，只能放云端态。

**建议**：本仓的模型请求本来就是服务端行为，**天然云端态**。
本地任务（导出、日志下载）建议走"用户显式触发 + 前台可见"，
不要假装支持后台续跑。
