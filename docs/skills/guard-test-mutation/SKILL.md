# 守门测试的变异验证

来源：`docs/audit/2026-11-17-PI智能体审计与完善-主档.md` §七（21 变异）+ §8.10（M1 探针门）+ §8.11（978 轮 9 变异）。可复现实现在 `scripts/audit/pi-agent-mutation-test.py`、`pi-agent-978-mutation-test.py`。

## 为什么必须做

全绿的守门测试可能只是断言写错了。两个实测案例：

1. 路由守卫断言 `Contains(source, "RegisterRoutes(mux)")` —— 同段里还有**同款调用** ⇒ 把目标调用整行删掉断言仍绿（装饰性断言）。修法：断言**指名道姓**（`piAnalysisHandler.RegisterRoutes(mux)`）。
2. 变异锚点先命中**注释里的修法示例**，代码行原封不动 ⇒ 门不红 ⇒ 看起来「守卫失效」，其实是**变异压根没发生**。

## 变异器的三条强制纪律

1. **锚点唯一**：变异目标串在全文件出现次数 ≠ 1 ⇒ 拒绝执行（避免改到别处造成假阴性）。**行级定点**并断言「那一行确实变了」。
2. **编译红不算数**：变异后包编译不过 ⇒ 记 INVALID，不算「通过」（代码坏了 ≠ 判据有牙）。
3. **必须能还原**：变异前保存原文件字节，测完逐字节写回并校验。

## 标准流程

```
对每个守卫断言:
  1. 选唯一锚点（在实现侧，不在测试侧）
  2. 改坏实现（删调用 / 反转谓词 / 换宽断言等最小变异）
  3. 跑对应守门测试 ⇒ 必须红
  4. 从原字节还原 ⇒ 复跑 ⇒ 必须绿
```

一个变异对应一个守卫点；守卫点 = 「这项缺陷如果复发，哪条测试会抓到」。

## 各类守卫的变异手法速查

| 守卫类型 | 变异手法 | 必红信号 |
|---|---|---|
| 路由可达（真发 HTTP） | 把注册调用换成 `_ = handler` | 该端点 404 ⇒ 测试红 |
| SQL 谓词（sqlmock） | 删谓词 / 写反方向（`<` ↔ `>=`） | 期望不满足（正则匹配不上） |
| 安全性质（禁跟随重定向等） | 删 CheckRedirect / 恢复默认 | 302 被跟随 ⇒ 目标命中标志置位 ⇒ 红 |
| 台账/清单登记 | 删 map 条目 / 删 tsv 行 | delivery test 红 |
| 缺席型判据（探针） | 把「剥注释」退化回裸 `prosrc` | gate test 红 |

## 路由类必须「真发 HTTP」

handler 层单测自己 `new` handler 直接打，覆盖不到「路由到底注册没有」「是否被更长的前缀路由吞掉」。做法：

1. 同一 mux 上注册**竞争路由**（目标前缀、更长前缀、根兜底）；
2. `httptest.NewServer` 起真服务、真 client 发请求；
3. 断言响应**不是 404**（无凭据时期望 401 = 中间件跑到了）；
4. 另配一条断言 main.go 真的接线（HTTP 测不到装配点）。

## 通用式

- **断言写宽 = 没写**：`Contains` 型断言在同款调用密集的代码里天然失明；指名道姓才有效。
- **守卫测试自己也要被验证**：新守卫第一次跑就应该经历过「红→绿」；只见过绿的守卫不可信。
- **静态扫描型门对新代码同样有效**：只要新代码落在被扫描的包里（例：`admin/internal_error_guard_test.go` 抓过新 handler 的错误回显）——新包要主动纳入扫描范围。
