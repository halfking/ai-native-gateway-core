### 2.1 cache 架构改造（5 commits） — ⚠️ 含 P0 写读分裂

**修改链路**：
- `14aa6909f`（-112/+9）：删 local fallback，限 Redis-free 路径；
- `2581906e2`（-74/+28）：删 metadata-only writes，文档化共享契约；
- `010fc89ab`（+74/-32）：`Update()` 改写为 `withSharedLease → loadSharedLocked → commitShared`；
- `ab9509f40`（+44/-23）：legacy state 原子退役；
- `d302a2ab7`（新增）：read shared revisions + 序列化 legacy backfill。

**8 维度评估**：
- **流程闭环** ✅ `Update` 在 `ctx.Err()` 检查→租约→load→fn→ctx.Err()→commit→nil 显式 no-op 路径上各点都有 ctx 取消处理；fn 回调后的 state==nil 被识别为"无变化"，不会误写。
- **数据来源与去处** ❌ **P0 写读分裂**：`session_cache.go:327` 的 `redisKey()` 返回 v2（`session:sc:{t}:{s}:v2`），但 `Update()` 调用的 `loadSharedLocked`/`commitShared`（位于 `session_cache_shared.go`）内部仍使用 `legacyRedisKey()` 读/写 **v1**（`session_cache_shared.go:149` `Eval` 脚本的 KEYS[1]、`:322` `HGetAll`）。结果：所有走 `Update()` 的 shared 写都进 v1 key，session_cache.go 文件头注释 `With Redis configured, session:sc:{tenant}:{session}:v2 is authoritative` 与实际行为**不一致**。`session_cache.go` 的 v2 `redisKey` 在新 Update 路径下未被使用（死代码或仅被旧路径调用）。**会写 v1、读 v1**（shared 路径内部一致）但**注释/命名/v2 redisKey**误导未来维护者将 v1 数据迁到 v2 时断链。
- **并发锁控制** ✅ `updateStripe` + 新 `withSharedLease`（token-based）双层：进程内 per-key stripe 互斥 + Redis 端 token 持有跨实例串行化。`010fc89ab`: `c.redis != nil` 才走 lease 路径，避免 Redis 不可用时的悬挂。
- **多线程资源竞争** ✅ `nil receiver` 检查 `c == nil` + `ctx.Err()` 多点插桩；`func(token)` 闭包捕获租约 token 避免泄露。
- **内存/句柄泄漏** ⚠️ 需核 `withSharedLease` 的 token 是否在所有路径（含 fn 抛错）下通过 `defer` 释放。当前 diff 显示 `defer c.releaseSharedLease(token)` 模式（commit 共享），假设正确但建议追加 lint。
- **异步处理异常** ✅ `ctx.Err()` 在 fn 调用前后双重检查，fn 抛错透传不提交。
- **异常错误处理** ✅ 新增 `ErrSessionCacheLeaseLost` 哨兵错误 + 显式 `state==nil` 不写语义。
- **请求数据转换** ✅ fn 仍接收 caller-owned 拷贝（`fn(*SessionState, []byte) → (*SessionState, []byte, error)`），调用方契约不变。

**关键证据**：
