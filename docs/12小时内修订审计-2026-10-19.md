## 2. 逐项审计

### 2.1 `9f007ce28` — emergency-cleanup L1 的 DROP 地雷（P0）

**缺陷本体**（成立，已被生产实测坐实）：
L1 分支用 `n_live_tup = 0` 当「这张表是空的」然后直接 `DROP TABLE IF EXISTS`。
`n_live_tup` 是 **ANALYZE 的估计值**，PG 重启后清零、ANALYZE 前恒为 0。
生产实测该判据**当前命中 6 张表 / 2,817 MB，其中 5 张并非空表**
（`ursm_node_snapshot_min_legacy` 真实 2,836,620 行 / 852 MB）。

**PG 不保护已挂载分区**（本地 PG 17.10 实测）：`DROP` 一个 ATTACH 分区会成功，
父表静默丢行，之后该范围 INSERT 直接报 `no partition of relation found`
⇒ 这不是「省空间」，是**写路径事故**。这条机理判断正确且重要。

**三道闸评估**：SQL 层 `AND NOT c.relispartition` + 行为层 `is_partition` 复核 +
`COUNT(*)` 复核，层次分明。`actual_count != 0 ⇒ SKIP` 且 psql 失败时
`|| echo "-1"` 落到 SKIP ⇒ **失败方向是保守的**，这一点做对了。
门禁里保留「真空表仍必须被 DROP」的反向用例，防过度加固把脚本改瘫，也做对了。

> **审计意见**：修法本身无问题。问题在 §4.1 —— 它还没部署。

### 2.2 `b386f7cf7` + `8b7e2735d` — VACUUM FULL 确认闸

**缺陷本体**（成立）：头部注释承诺「用 pgstattuple 扩展（如果没有就用 dead_tup_pct 估算）」，
但代码里**只有估算那一条路径**——承诺从未兑现。估算 `dead_pct` 取自 `pg_stat`，
同一量具已被证伪过多次（§116 高估 2.5×、低估 2.9×）。

**`8b7e2735d` 的校准是本轮最有价值的一段**：在 `session_summaries`（857 MB，全库唯一
`n_live_tup` 归位的表）上实测 估算 7.29% vs `pgstattuple_approx` 0.346%
⇒ **高估约 21 倍**。作者同时诚实指出「这一趟闸确实没拦住任何东西，
不能拿它当『闸有用』的证据」，并据此把门禁改成**只可能由闸拦住**的组合
（估算 30.0% / 实测 0.3%）。这个自我修正是对的。

**列存表永久失效的发现也成立**：`pgstattuple_approx` 对非堆表报
`only heap AM is supported`，而旧 WHERE 只排除了 `columnar_internal` 这个 schema，
排不掉 `public` 下的列存表 ⇒ 它们必然进候选、必然失败、被 fail-safe 跳过，
日志与「扩展没装」**完全同形**。改到候选层 JOIN `pg_am` + `amname='heap'` 是对的修法。

### 2.3 `a0c54f056` — index-bloat 两个结构性盲区

**成立**：`AND NOT c.relispartition` 挡的是分区父表上的索引（`relkind='I'`），
而那些**压根不在** `relkind='i'` 的候选集里 ⇒ 这一条什么都没挡，
却把**叶分区**上的 72 条 / 4,555 MB 索引全挡在外面。删除该条件是正确的。

且**没有**因此把判据退化成按尺寸一刀切，仍保留 `pgstatindex` 双信号
（`deleted_pages OR avg_leaf_density`）—— 这个取舍是对的，
因为实测 pg_toast 里 3 条 ≥16MB 的只有 1 条真膨胀。

### 2.5 `6d5db3a7c` — REFRESH 会话级 work_mem 256MB

**归因成立**：`work_mem=8MB` 而单次刷新要排 9~136 MB ⇒ 必然落盘。算术没错。

**实现形态评估（本轮逐行核对）**：

```go
conn, _ := r.db.Acquire(ctx)          // 692：钉住连接
defer conn.Release()                  // 696
SET statement_timeout = '180s'        // 702（既有）
defer RESET statement_timeout         // 706
SET work_mem = '256MB'                // 714（新增）
defer RESET work_mem                  // 717
```

- **LIFO 顺序正确**：`RESET work_mem` → `RESET statement_timeout` → `Release`。
  归还连接池之前两个会话级 GUC 都已复位 ⇒ **不会污染连接池**。这是本条最关键的正确性点，做对了。
- **失败方向保守**：`SET work_mem` 失败 ⇒ 直接 `return err`，整个刷新跳过（不做 ⇒ 安全）。
- **与既有 `statement_timeout` 同形**：`bg/materialized_view_refresher.go:702` 也是
  `if err != nil { return }`，不是新引入的不一致。
- **`SET` 早于 advisory lock**（721/729）：抢不到锁的实例会白做一次 SET+RESET，
  但连接已 Release 且已 RESET ⇒ 无害，只是多一次往返。可接受。

> **未核实的前提**：256MB 这个值的依据是「每轮全网只有一个实例执行刷新
> （Redis 令牌桶 + advisory lock 兜底）」，但**PG 宿主（172.16.2.210）的内存余量本轮没核到**。
> 作者已在常量注释里写明这一点，做法诚实。
> ⇒ 见 §4.3：这是一个**未闭环的前提**，不是缺陷。

### 2.6 `37944e9d2` — search_text GIN trigram 索引(877) + duration_ms 按轮写入

**索引侧**：`search_text ILIKE '%'||$n||'%'` 是**前导通配符**，btree 结构上无法服务，
而 session 族全族无任何 `search_text` 索引 ⇒ 对每个 6.4GB 级月分区顺序扫描 TOAST 宽列。
补 GIN trigram 是对的；**刻意不建 model/client_model 的 trigram** 也对
（session_turns 上根本没有 `client_model` 列；`?model=` 自 2026-08-29 起是精确 `=`）。

迁移工程质量高：`CREATE INDEX IF NOT EXISTS` 幂等、`SET LOCAL statement_timeout/lock_timeout`、
`COMMENT` 与创建腿同守卫（避免「守卫掉的对象留无条件 COMMENT ⇒ COMMIT 后非零退出 ⇒ 迁移永不记账」）、
`.down.sql` 完整、embeddata 两副本 + installer `go:embed` + runner `StartupFiles` + TSV 六点齐备。

**判据是 planner 层而非「索引存在」**、门内自带 DROP 反证段、夹具刻意用 ~0.2% 命中率
（第一版 100% 命中率时 planner 选顺序扫是**正确的**）—— 这套判据设计是本轮质量最高的部分。

**duration_ms 侧**（本轮重点核对「请求数据转换」）：

```sql
-- INSERT 臂：created_at 与 updated_at 同为 $3，已流逝为 0
duration_ms = 0
-- UPDATE 臂：
duration_ms = CASE WHEN public.sessions.created_at IS NOT NULL
  THEN GREATEST(0, (EXTRACT(EPOCH FROM (EXCLUDED.updated_at
         - public.sessions.created_at)) * 1000)::BIGINT)
  ELSE public.sessions.duration_ms END
```

- **起点取存量 `sessions.created_at` 而不是 `EXCLUDED.created_at`** —— 这是本条最容易写错的地方，
  写错会让起点每轮重置到"现在"、`duration_ms` 恒为 0。作者显式写出了这个警告，写对了。
- `GREATEST(0, …)` 挡时钟回拨/乱序到达，正确。
- INSERT 臂写 `0`、UPDATE 臂单调整数语义，形状一致。

> **语义变更的影响面核验**：这一列从「生产恒 NULL」变成「已流逝时长」。
> 本轮 grep 全仓**确认 `sessions.duration_ms` 没有生产读消费方**
> （`admin/turns_sessions.go:85` 的 `DurationMs` 是另一个结构体的字段，不是本列）。
> ⇒ 语义变更**不会破坏任何现有读方**，风险为 0。§4.2 记的是文档层面的一致性缺口。

### 5.1 `scripts/252-monitor/pg17-vacuum-bloat.sh` —— 标识符未引用（§4 之外的**新发现**）

**审计中发现的、本轮新引入的问题**：`BLOAT_SQL` 用
`s.schemaname||'.'||s.relname` 拼出 `tname`，然后**直接插进两条要发给 PG 执行的语句**
（确认闸的实测调用、最终的重建调用）。裸拼名只在「所有标识符都是朴素小写单段」时恰好合法。

- **失败方向**：psql 报错 ⇒ 量不出来 ⇒ 走 fail-safe SKIP ⇒ **不是错做**，
  但形态恰恰是 §118 刚花一轮拆掉的「静默永久失效」。
- **修法**：候选层新增 `format('%I.%I', …) AS qname`，循环里**执行一律用 `qname`**，
  `tname` 只用于日志；候选集缺第 4 列时回退到 `tname`（向后兼容，既有门禁喂的是 3 列）。
- 与同族 `emergency-cleanup` 的 DROP 路径（早已用 `format('%I.%I')`）**形态对齐**。

> `format('%I.%I')` 对朴素标识符**不加**引号 ⇒ 日志与既有行为完全不变。

**门禁**（新增 `scripts/ursmcheck/vacuum_bloat_identifier_quoting_test.go`，4 条）：

| 用例 | 钉住什么 |

| `TestVacuumBloatMeasuresQuotedIdentifier` | 确认闸的实测调用也必须拿 qname |
| `TestVacuumBloatFallsBackWhenQnameAbsent` | 3 列旧候选集必须回退（守住 §117 既有门） |
| `TestVacuumBloatCandidateSQLQuotesIdentifiers` | 候选层必须由 `format('%I.%I')` 产出 qname |

### 5.2 `scripts/ursmcheck/*` —— 行为门在维护者机器上**从未真正执行**（P1，本轮最重要的发现）

`bashForScript` helper 此前**只接受 bash >= 4，找不到就 `t.Skip`**。
macOS 自带 `/bin/bash` 是 **3.2**，且默认没装 homebrew bash
⇒ **本包所有行为门在维护者自己的机器上全部 SKIP，跑出来是绿的，一条判定分支都没走到。**

这直接冲击了 §2.1/§2.2 那几条提交信息里的「变异 2/2 全红」「变异 3/3 全红」——
**在本机它们从来没有真正运行过。**

**修法：按被测脚本判，而不是一刀切。**

- `bashForScriptFor(t, script)`：优先找 bash >= 4；没有则读目标脚本，
  若**不含** bash-4 专有语法 ⇒ 用 bash 3 跑（门真正执行）；含 ⇒ Skip 且说清原因。
- `scriptUsesBash4Only()`：`${x^^}` / `${x,,}` / `declare -A` / `mapfile` / `readarray` / `coproc`。

> **⚠ 本轮自己也差点栽在这里**：第一次判定用的正则是 `\${[A-Za-z_]…\^\^}`，
> **漏掉了 `${2^^}`**（变量名以数字开头），于是把
> `pg17-emergency-cleanup.sh:72` 这个**真需要 bash 4** 的脚本判成 bash3 兼容，
> 导致它的 4 条 DROP 门从"跳过"变成"红"。正因如此，这条警示已写进代码注释。

**修完后的诚实状态**（macOS + 无 homebrew bash）：

| 门 | 状态 | 说明 |
|----|------|------|
| 全部 vacuum-bloat 门（含新增 4 条） | ✅ **真正执行并通过** | 该脚本 bash3 兼容 |
| 4 条 EmergencyL1 DROP 门 | ⏭️ Skip，**且 Skip 文本已说明原因** | 该脚本用 `${2^^}`，需 `brew install bash` |

### 5.4 `scripts/252-monitor/pg17-vacuum-bloat.sh` —— 双引号串内的注释纪律

§5.1 的注写在 `BLOAT_SQL="…"` 里，本轮因此连踩两次。已在原处留**两条纪律**：

1. 不可出现反引号、美元-花括号或双引号（否则 bash 在**赋值时**就做命令替换/参数展开，
   `set -u` 下未定义变量直接把脚本打死）；
2. 也**不要**写出下方那两条语句的函数名/关键字全文——
   行为门注入的假 docker 是**按子串匹配 SQL 应答**的，注释里出现同样的字面量会让它认错分支。

> 第 2 条是本轮独有的坑：**SQL 注释里的字面量会改变测试替身的应答**。
