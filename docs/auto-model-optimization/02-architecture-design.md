# AUTO 架构设计

## 设计边界

AUTO 优化器围绕现有路由链路提供分类、候选排序和反馈闭环；本目录文档不新增生产 Go/SQL 逻辑。路由事实只写入现有 `auto_route_selections`，由现有 settle/affinity 流程补齐结果并计算模型亲和度。

## 数据流

```text
请求进入 AUTO
  -> 仅在内存中提取结构化特征
  -> 规则/结构化特征模型给出 task_type 与 confidence
  -> 现有候选过滤与模型排序
  -> 写入 auto_route_selections（ID、决策快照、指标）
  -> settle 后补 success/latency/cost/reward
  -> affinity worker 从事实表学习 task -> model 权重
```

请求正文只在请求处理边界内使用，不进入优化器持久化、标注导出、训练集或缓存。不得保存 prompt、messages、response、summary、关键词原文、截断正文、embedding 或其他可逆内容特征。

## 结构化特征提取

首期特征应为低敏感、不可逆、固定 schema 的值：语言枚举、长度桶、上下文长度桶、轮数桶、代码/数学/表格/多媒体标志、意图枚举、领域枚举、复杂度桶、延迟/成本敏感标志、特征版本和 hash。不要把特征放成包含原文或关键词的自由 JSON。

## 分类与排序

1. 规则引擎负责冷启动和确定性边界。
2. 初期 ML 使用结构化特征模型（例如逻辑回归、树模型或小型线性分类器），输入只来自上述特征；以离线评估和 shadow 结果决定是否放量。
3. 置信度不足或模型失败时回退规则。
4. 亲和度是软权重，只能重排已通过可用性、封禁和固定策略检查的候选，不能复活不可用模型。
5. 所有线上实验都必须可回退到现有规则/基础排序。

## 存储布局

`auto_route_selections` 是唯一事实表：最近 8 小时作为热查询窗口，历史按 `partition_date` 月分区；通过统一 `v_auto_route_selections_all`（或仓库最终约定的等价 all view）读取全量语义。all view 不复制数据，也不产生第二事实源。

## 反馈与标注

用户覆盖、重试、错误、评分和结算结果都作为事实表上的指标或可关联元数据使用。人工标注只保存事实行 ID、结构化特征、自动决策和标注元数据；不复制正文。训练集从事实表派生并带版本、时间范围和质量门槛。
