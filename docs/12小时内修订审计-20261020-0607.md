### A1 · 目录体积不再等于「没有证据」（**行为回退**）

**核验**（`git diff 009f6f896 6e6f32c3f -- bg/probe_http.go`）：

- 旧写法（基线）：`body, _ := io.ReadAll(io.LimitReader(resp.Body, 65536)) // 64KB to capture full model list`
  ⇒ 超长**静默截断**，仍按 2xx 判 ok。
- 新写法：`readCredentialProbeBody` 对 >64KiB **返回错误**；
  而 `probeModelsHaveEvidence` 要求 `json.Valid(body)`（**完整** JSON）
  ⇒ 超长 ⇒ `classifyProbeHTTPResponse` 把 2xx 判成 `probe_response_inconclusive`。

**为什么严重**（`bg/model_probe.go:1386-1390` 实测）：
`mode := ProbeModeModelsList` 是**所有非 anthropic 协议的主健康探针**。
⇒ 该模型**永远到不了 `healthy_confirmed`**，且 `computeConsensus` 对 inconclusive
返回 `applied=false` ⇒ 每轮周期都被重新选中。
目录条目约 50 字节 ⇒ 64KiB 只装得下约 1.3k 个模型，聚合型供应商很容易越线。

**修正**：目录型端点单独放宽到 1MiB（`credentialProbeModelsBodyLimit`，**仍是有界读**），
其余 13 个 `readCredentialProbeBody` 调用点**一行未动**（新增带上限的变体，默认值不变）。

**门禁**：`TestModelsProbeAcceptsCatalogLargerThan64KiB`（>64KiB 目录必须拿到正向证据）
+ 对照臂 `TestModelsProbeStillRejectsBodyOverModelsLimit`（>1MiB 仍须判"不确定"，
证明放宽不是无界）。
**变异**：把上限改回默认 64KiB ⇒ 门红在
`large model catalog was rejected as inconclusive: category="skipped" ... errCode="probe_response_inconclusive"`。

### A2 · 确定性的 404 不再被当成「不确定的观察」（**行为回退**）

**核验**：

- 基线 `009f6f896` 的 `bg/active_probe_executor.go` 里**根本没有 `ObservationOnly` 这个概念**
  （`grep -c ObservationOnly` = **0**），404 一律按 HTTP 状态分类 ⇒ `ProbeStatusHTTP4xx` ⇒ 状态机照常落库。
- 窗口内新增的 `if parsed.category == probeCategorySkipped { ObservationOnly = true; return }`
  把 **`endpoint_id_required`**（火山方舟那类「模型必须配 endpoint id」，`internal/probeutil/endpoint_id.go`）
  也算成了"观察"——**同一个 category 被两处复用**，而两者语义相反。

**三重后果**（逐条回到代码核实）：

1. `applyProbeResult` 的 ObservationOnly 分支不写 state manager ⇒ **旧行为里的 5 分钟摘流被取消**，
   模型继续留在路由池里持续 404；
2. 该 pair 的重试链被终止（`delete(w.running, ...)` 后直接 return，不再 `markFailedRetry`）；
3. `classifyProbeErrorKind` 返回 `probe_direct_inconclusive`
   ⇒ 真实原因（缺 endpoint ID 的**配置**问题）被误报成"上游不确定"，运维诊断被带偏。

**修正**：「观察」改为按 **errCode** 判定（只认 `probe_response_inconclusive`），
`endpoint_id_required` 走正常 HTTP 状态分类落库，同时**保留**这个可诊断的 errCode
（不被 `http.StatusText(404)` 覆盖成 "Not Found"）。

**门禁**：`TestDeterministicEndpointIDRequired404IsNotObservation`
+ 对照臂 `TestInconclusive2xxRemainsObservation`（真正不确定的 2xx **仍然**是观察 ——
没有这条对照，门有可能被"把所有 skipped 都放行"骗过）。
**变异**：退回按 category 判定 ⇒ 门红在
`deterministic 404 was swallowed as an observation: ... ObservationOnly:true`（转储里直接看得到 `ObservationOnly:true`）。

### A3 · provider 错误「不改状态」但「要记账」（**流程缺口**）

**核验**：

- 基线的 `computeConsensus` default 分支是 `newSucc = 0; newState = "recovering"`（`applied` 仍为 true）
  ⇒ 会经 `writeAvailabilityCache(..., available=true)` **把 `broken_confirmed` 的模型恢复回路由**
  —— 这是**真缺陷**，窗口内改成 `applied=false` **修对了**。
- 但修法是「`applyResult` 整段 return」⇒ `model_probe_state` 这一行
  （`applyResult` 的**唯一**写入口）**完全不被推进**：
  - `next_retry_at` 永远停在过去值 ⇒ **每轮周期都被重新选中**（探针空转）；
  - `last_status` / `last_attempt_at` / `total_attempts` 对运维**永久显示旧值**；
  - 而 `model_probe_runs` 一直在写 `provider_error`
    ⇒ **审计表与状态表口径分裂**。

**修正**：「不改状态」与「不推进调度」拆开：状态继续不动，同时用
`advanceProbeBeat` **只写节拍四列**（`total_attempts` / `last_attempt_at` /
`next_retry_at` / `last_status`），**绝不**碰 `state`、`consecutive_*`、
`last_state_change_*` 与绑定可用性。
⇒ 只推进 provider 错误这一类；`manual_disabled` / `suspended` / `endpoint_unresolved`
仍保持"完全不写"的旧语义（无证据支持改它们）。

**门禁**：`TestBeatUpsertTouchesOnlyCadenceColumns`（逐字钉住 SQL：
`DO UPDATE SET` 里不得出现 `state` / `consecutive_*` / `last_state_change_*`）。
**变异**：往 SET 里加 `state = EXCLUDED.state,` ⇒ 门红在
`beat upsert must not touch state in DO UPDATE SET`。

### D1 · 脱敏面：真地址明文外泄（**HIGH**，数据泄漏）

**核验**（回到 `security/sanitize/detector.go` 的 `dropLabelWrappedAddressFragments`）：

原实现对「被更精确类型片段**完全包住**」的 custom 片段**整段丢弃**。
但「包住」只说明 custom 的**跨度更大**，**不说明**它多出来的那部分只是标签：

| 输入 | custom 残余 | 残余是什么 | 整段丢弃的后果 |
|---|---|---|---|
| `手机号 13800138001` | `手机号        ` | 标签 | ✅ 丢弃是对的（让位给 phone） |
| `北京市朝阳区建国路88号 13800138001` | `北京市朝阳区建国路88号` | **真地址** | ❌ **地址明文留在脱敏结果里** |

两者在结构上**完全同形**（都是「前缀 + 空格 + 精确值」）⇒ 原实现**无法区分**。

**★ 为什么既有门没抓到**（这是本条最有价值的部分）：
既有门 `TestR1036AddressNextToPreciseValueNotOverDropped` 用的是
「手机号 …，**地址**北京市朝阳区建国路88号」——**精确值在前**。
那个顺序下 address 规则匹配的是「地址北京市…88号」这一段，它**不包住** phone 片段
⇒ 不触发丢弃 ⇒ 门自然绿。
⇒ 既有门是**单向覆盖**：只钉住了「精确值在前」的方向，漏的是**地址在前**。

**修正**：把 custom **裁成残余**（而不是丢弃它）；残余里若出现**地址专有字**
就**继续按 custom 脱敏**，否则才让位给精确类型。

- **判据为什么是「地址专有字」**：address 正则的字符类是
  `省市区县镇乡村路街道巷弄` + `号栋单元室`。
  前一组**只出现在地名/路名**里；后一组是**通用尾字**，
  同时也出现在「手机号 / 房间号 / 工单号 / 订单号」这类**标签词的尾字**上
  ⇒ 只能拿前一组当判别式。
- 为此抽出常量 `addressSpecificChars`（= `省市区县镇乡村路街道巷弄`）
  与 `hasAddressSpecificChar`，并由既有门
  `r1036_label_suffix_address_test.go` 断言**本组每一字都仍在 yaml 的地址正则字符类里**
  ⇒ **yaml 改了地址规则而本常量没跟着改时，门会红，不会静默失配**。

**门禁**：`TestR1036AddressBeforePreciseValueKeepsAddressRedacted`（地址在前必须仍被遮蔽）。
**变异**：恢复成整段丢弃 ⇒ 门红在
`真地址明文留在脱敏结果里：地址是北京市朝阳区建国路88号 {SENSITIVE:phone:1}`。

**★ 附带发现（顺手补的防回退门）**：本条修正引入的 `subtractSpans`，其输入 `inner`
**不保证按位置升序**——`precise` 列表是**按规则迭代顺序**收集的（片段按规则 `append`），
而片段的位置排序（`sort.SliceStable`）发生在 `dropLabelWrappedAddressFragments`
**返回之后**。
⇒ 同文件里那个用途相近的 `outsideReservedSpans`（上游 r1038 引入）**假定输入已升序**
（遇 `marker[0] >= end` 就 `break`）⇒ **不能**复用它：
未排序的 `inner` 会被它提前 `break` 截断，后面那个片段**整个被忽略**
⇒ 残余区间算错 ⇒ **电话号码会被卷回 custom 残余**。
⇒ 已加**代码注释**说明这条前提差异，并加 **2 条门**钉住：
`TestR1039SubtractSpansHandlesUnsortedInner`（直接钉 `subtractSpans`）
+ `TestR1039LabelWrappedKeepsAddressResidualWithUnsortedPrecise`（走本体）。
**变异**：去掉排序 ⇒ 两条门同时转红，且失败信息是
`残余 [0,45) 与内部片段 [33,44) 重叠 ⇒ 未排序输入被漏算`。

### D2 · 攻击向量指纹：原文 hex ⇒ ≥33 字节必写不进（**HIGH**，写入失败）

**核验**：`domains/promptinjection/detector.go` 的写入侧用
`fmt.Sprintf("%x", ...)` 把**原文的 hex 编码**当指纹
⇒ 指纹长度 = **2 × 输入字节数**；而列是 `VARCHAR(64)`。
⇒ **输入 ≥33 字节时必然写失败**（PG 会报 `value too long for type character varying(64)`），
且失败发生在**写入路径**上 ⇒ 攻击向量在长文本场景下**静默不入库**。

**改动安全性**：`attack_hash` 全仓**只有一处生产者、一处只读展示方**
⇒ 改算法不会砸到别的读写路径。

**修正**：改用**真 SHA-256**（与列声明 `VARCHAR(64) -- SHA-256` 一致），
抽成 `attackVectorHash`。

**门禁**：3 条（宽度固定为 64、长度不随输入增长、且**不与旧 hex 混淆**）。
**变异**：退回原文 hex ⇒ 门红在 `hash length = 20, want 64` 与 `20 vs 20000`。

> ★ **已知且已接受的副作用**：旧行是**原文 hex**、新行是**真 SHA-256**
> ⇒ 同一条 `attack_text` 在新旧算法下指纹不同 ⇒ 可能出现**同文两行**。
> 已在提交信息中写明。**未取证**：生产库现有 `attack_hash` 的实际取值分布（本轮无 PG 连接）。

### D3 · 两个凭据端点缺角色门（**MEDIUM**，越权读）

**核验**：`admin/credential_monitor.go`（`/api/credentials/decisions`）与
`admin/credential_routing_log.go`（`/api/credentials/routing-log`）**没有**
`IsTenantAdmin(r) || IsSuperAdminOrLegacy(r)` 的 403 门，
而同族其它端点**都有** ⇒ 普通租户可读**租户级**决策记录与路由日志。

**修正**：补 403 门，**位置必须早于 nil-db 门** ⇒ 否则未初始化时返回 500 而不是 403
（门的位置错了，语义就错了）。

**门禁**：8 个子例（租户管理员 / 超级管理员 / 普通租户 / 未登录 × 两个端点）。
**变异**：去掉角色门 ⇒ 门红在「普通租户读到租户级路由日志」。

> ★ **本条动了两个既有用例（必须披露）**：补门后，全量 `go test ./admin/` 有 **2 个既有用例转红**：
> `TestHandleCredentialDecisions/requires_credential_id` 与 `TestHandleCredentialDecisions_NilDB`
> —— 它们**期望 503**（nil-db），而新门让无角色请求先拿到 **403**。
> ⇒ ★ **处置不是改断言，是给请求补上角色**：
> 两处请求加上 `SetAuthContext(req, &AuthContext{Role: "super_admin", IsJWT: true})`，
> **状态码断言一字未动**（仍是 503）。
> 理由：这两个用例的**本意**是测"穿过角色门之后的 nil-db 路径"，
> 它们此前之所以能过，只是因为**当时根本没有角色门**；
> ⇒ 补门后它们必须显式声明"我是一个管理员"。
> ⇒ ★ 另有一处**本机不红、CI 会红**的：`TestCredentialDecisionsIntegration`
> （本机因无 `TEST_DATABASE_URL` 被 skip，CI 有真库时会跑）
> —— 它的 3 个请求同样补了管理员角色，**否则 CI 上会拿到 403 而不是 200**。
> ⇒ ★ **教训**：给端点加门时，**"本机全绿"不等于"CI 全绿"**——
> 被 `t.Skip` 掉的集成用例是**被本机门禁遮住的那一面**，必须逐个读过去。

### D4 · 主键列序无人守（**MEDIUM**，唯一性语义漂移）

**核验**：`sql/objects/constraints/ursm_node_snapshot_min_ursm_node_snapshot_min_pkey.sql`
声明 `PRIMARY KEY (snapshot_ts, tenant_id, credential_id, raw_model_name)`。
PG 的 `ON CONFLICT` **按集合匹配**索引列、**不要求顺序**
⇒ 列序写反**不会报错**，但 `(a,b)` 与 `(b,a)` 是**不同的键序**，唯一性语义会漂移
⇒ 同一行可能被当成两条并存。

**★ 为什么既有门没抓到**：既有门只比**列的集合**；
而巡检脚本 `ORDER BY a.attname` **主动丢弃了顺序**
⇒ **集合相等**与**顺序相等**在读数上同形。

**修正**：新增一条**比列序**的门（声明文件的列序 vs Go 侧 `ON CONFLICT` 目标的列序）。
**变异**：调换列序 ⇒ **新门红**，且**既有集合门仍绿**
（这正是"新门补的是既有门看不见的那一面"的证据）。

### D5 · 流式路径漏报「有 id 无 name 键」的 tool_call（**MEDIUM**，质量门被绕过）

**核验**：`domains/streaming/tool_call_quality.go`——**非流式**路径会报这种 tool_call，
**流式**路径**不报** ⇒ 同一个请求走流式就绕过质量门。

**修正**：改判据 + 用 `empty:` 槽位**防重复计数**（否则一条空 name 会被计多次）。

**门禁**：5 条。**变异**：退回旧判据 ⇒ 门红在「流式路径漏报有 id 无 name 的 tool_call」。

1. **本文结论绑定 `6e6f32c3f`（第一批）与第二批/第三批的修正提交**。
