## 1. B1 — Graceful shutdown timeout 完整修复（commit 109752b53）

### 1.1 根因链

```
22:20:51 systemd SIGKILL gateway (PID 6828)
  ↓ journal: "State 'stop-sigterm' timed out. Killing."
  ↓ systemd TimeoutStopSec=25s 但 srv.Shutdown timeout=30s
  ↓ 25s 超时 systemd 强制 SIGKILL
  ↓ cgroup oom_kill=0 + memory.failcnt=0 → 不是真 OOM
  ↓ Restart=always 自动重启新 PID 9360
```

### 1.2 修复链

**Step 1: systemd drop-in** (`/etc/systemd/system/llmgo-245.service.d/timeout-override.conf`)

```ini
[Service]
TimeoutStopSec=35s
```

- daemon-reload OK
- `systemctl show llmgo-245` 显示 `TimeoutStopUSec=35s` ✅
- 但 **仍 SIGKILL**（journal 23:26:28: stop 用了 35.2s 触发超时）

**Step 2: 找真正的根因** — main.go L5678 + L5694

```go
// srv.Shutdown 用 30s timeout
shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
...
// worker stopCtx 用 20s timeout
stopCtx, stopCancel := context.WithTimeout(context.Background(), 20*time.Second)
```

总耗时预算：30 + 20 = 50s，远超 systemd 35s。

**Step 3: 改 main.go L5678+L5694**（commit `109752b53`）

```diff
- shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
+ // 2026-08-19: 30s→23s. systemd TimeoutStopSec=35s (drop-in), srv.Shutdown 必须 ≤ 23s
+ // 留 12s 余量给 worker stop (stopCtx 5s + 启动新进程 ~3s + 系统开销 ~4s).
+ // 245 实测 in-flight drain < 5s, 23s 足够覆盖 (handoff changelog §3 B1-follow-up).
+ shutdownCtx, cancel := context.WithTimeout(context.Background(), 23*time.Second)

- stopCtx, stopCancel := context.WithTimeout(context.Background(), 20*time.Second)
+ // 2026-08-19: stopCtx 20s→5s. systemd TimeoutStopSec=35s 总预算下, srv.Shutdown 23s 后
+ // 仅剩 12s, worker stop 必须快速失败. 5s 足够让 in-flight workers drain, 超时则 SIGKILL.
+ stopCtx, stopCancel := context.WithTimeout(context.Background(), 5*time.Second)
```

### 1.3 验证（待 245 deploy 后看实际生效）

- go build ./cmd/gateway: exit 0 (62MB binary)
- go vet ./cmd/gateway: exit 0
- ⚠️ **实际 deploy 待 B4 commit + push 后做**

## 3. ⚠️ 未修复 — INSERT 路径 SQL/参数错位（需老板团队专人修）

### 3.1 错误现象

```
stderr: "db_error":"unused argument: 95"
```

意思是：SQL 用 95 个 `$N` + 1 个 `now()` = **96 个 values**，但参数列表传了 **98 个 entry.X**。

pgx 检测到第 96+ 个参数没 SQL 占位符，报"unused argument: 95"。

### 3.2 根因分析

**INSERT INTO request_logs_hot 在 `domains/hooks/observability/telemetry/client.go:889-1100`**

- Column 列表: **102 列**（含 ts）
- VALUES 子句: **96 个 values**（95 个 `$N` + 1 个 `now()`）
- 参数列表: **98 个 entry.X**
- **差 6 个 column 没在 VALUES 中！**

这是 SQL **语法错误**（column 比 values 多），PG 应该报 "INSERT has more target columns than values"。**但实际从未报** — 因为 unused argument 错误**先抛出**，INSERT 根本没执行到 PG。

mock test `TestUpdateRequestLog_UsesTerminalStateGuard` 用 `make([]interface{}, 101)` + `pgxmock.AnyArg()`，**不校验参数数量**（mock 接收任何数量），所以 CI 没抓到。

### 3.3 这违反的规则

- **rule 49 §2.1 列名假设禁止**：错位是参数顺序假设错误
- **rule 49 §6.1 schema 对账**：SQL/参数列表必须 lockstep
- **rule 49 §3 fail-loud**：测试不严格 → bug 漏到生产
- **rule 11 §14 持续验证**：测试通过但生产失败的反面案例
- **rule 17 test gate**：mock test 必须验证参数数量，不只是 AnyArg

### 3.4 推荐修复方案

**方案 A（推荐）**: 重写 INSERT SQL 让 column 数 = values 数

```sql
-- 当前 column 列表 102 列, VALUES 96 个 (95 + 1 now())
-- 需要补 6 个 VALUES: 找出哪些 column 漏写
-- 然后改 INSERT INTO (col1, col2, ..., col102) VALUES ($1, now(), $2, ..., $N)
-- 参数列表也同步调整到 101 个 entry.X (去掉 now() 占位, 95 + 6 = 101)
```

**方案 B**: 缩短 column 列表到 96 列（删除不再用的列）

**方案 C**: 加 mock test 验证参数数量（rule 17 test gate 加严）

### 3.5 风险等级

🔴 **HIGH** — 这是生产数据库 INSERT/UPDATE 路径，错误导致 telemetry 落库失败，业务影响 dashboard 数据不准、URSM 决策信号缺失。但**不影响主流程**（gateway 转发正常工作）。

按 rule 10 §2.3 + rule 09 §4.2：**建议老板团队安排专人修，不要 AI 自主改**。

### 3.6 不修复的影响（24h 累计）

- telemetry 请求日志落库：~100% 失败
- FileWriter fallback：~10% 失败（daily limit 10 files）
- 请求日志丢失：估计 60-80% 业务请求（fallback 写文件部分失败 + daily rotate 限制）
- 影响：admin/dashboard 数据陈旧（最近 24h 数据不完整）
- 不影响：gateway 转发 / chat completion 业务 / 鉴权 / 计费主流程
