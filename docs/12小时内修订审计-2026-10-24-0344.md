### 2.2 T2 · 成功终态补 origin 元数据 —— ★★ 本轮判断：**正确；根因定位准确，nil 安全链完整**

**根因**（我逐层复核过）：`sessionv2mirror` 的 hook **只镜像终态 entry**（初始 in_progress INSERT 被刻意跳过，因为 turn 幂等、写入后不可更新）⇒ 初始 INSERT 携带的 origin 元数据**永远到不了 `session_turns`** ⇒ 而成功请求落库的唯一入口是 `emitTelemetry` 构造的终态 entry（从零构造、不带任何请求上下文派生字段）⇒ ⇒ **成功行 100% 漏标**。

**修法**：`applyRequestContextFields(reqLog, keyInfo, logCtx)` 在终态构造之后、发射之前补齐 `applyAutoRouteFields` / `applyOriginMetadata` / `ClientEndpoint` / `ClientRequestID`，语义是「**只补空位**」（first-write-wins），与失败终态的 `buildEntry` 顺序一致。

**★ nil 安全链我逐个函数验过（这是本切片最需要盯的地方——新增函数在 nil 上崩溃会打穿整个流式链）**：

| 函数 | nil 入口 | 结论 |
|---|---|---|
| `applyRequestContextFields` | `entry == nil` → 直接 return | ✓ |
| `applyAutoRouteFields(entry, c)` | `entry == nil \|\| c == nil` → return | ✓ **它在调用方的 `if c == nil` 之前就被调用，所以这里的 nil 守卫是承重的** |
| `applyOriginMetadata(entry, keyInfo, ctx)` | `entry == nil` → return；`ctx != nil` 才调 `ApplyOriginFromContext` | ✓ |
| `middleware.ResolveOriginForSystemKey(ctx, owner)` | `ctx == nil \|\| ownerUser == ""` → return | ✓ **ctx 为 nil 时不会 panic** |

⇒ ⇒ **无 nil 解引用风险**。

**★ 一个「业务闭环」观察（已确认无害，登记备查）**：

### 2.3 T3 · §143.102 迁移 902（索引合并） —— ★★ 本轮判断：**DDL 纪律高，但有一条「可重入性」缺口（★ 本轮唯一实测复现的真缺陷 ⇒ 见 §3 问题 ①）**

**做得好的部分**（逐条核对过）：
- `dbinit:no-transaction` 标记 + `CREATE INDEX CONCURRENTLY` 配套（PG 不允许 CONCURRENTLY 在事务块内跑；无标记则**新装必败**于 `cannot run inside a transaction block`）✓ 与 877/888 同款 ✓
- `SET lock_timeout='60s'` + `SET statement_timeout='10min'`（该表是活写表，`event_writer` 每请求一次 upsert）✓
- **换体窗口**：注释声称「`DROP CONSTRAINT` + `ADD CONSTRAINT ... USING INDEX` 在同一 DO 块 ⇒ 不会撞见『无唯一约束可匹配 ON CONFLICT』的瞬时窗口」—— 我核对了 SQL：**DO 块本身就是一个事务** ⇒ DROP 与 ADD 在同一事务内原子完成 ⇒ **该声称成立** ✓（这是本切片最容易被误读成有洞的地方，实际是对的）
- **幂等三重守卫**：① 目录态判定（pkey 已带 INCLUDE ⇒ 整段跳过）；② tmp 索引必须 `indisvalid AND indisready AND indisunique` 且形状正确，否则 `RAISE EXCEPTION`；③ pkey 不存在则 `RAISE EXCEPTION` ⇒ **全部 fail-close** ✓
- 兜底 `DROP INDEX CONCURRENTLY IF EXISTS <tmp>`（重跑不留孤儿）✓
- 冗余证明正确：pkey(event_id) ⇒ event_id 全表唯一 ⇒ `(event_id, occurred_at)` 复合索引相对 pkey 的唯一增值是 covering ⇒ INCLUDE 体完整承接 ✓

**★ 缺口**：`CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS` 的 `IF NOT EXISTS` **只看名字是否存在，不看索引是否有效** ⇒ ⇒ **上一次构建失败留下的 invalid 索引会让这条迁移永久卡死** ⇒ ⇒ 详见 §3 问题 ①（★ 已实测复现）。

## 3. 发现的问题清单（待修正清单）

### ★★ 问题 ①【中·幂等/可重入性·流程闭环】迁移 902 在「上一次 `CREATE INDEX CONCURRENTLY` 失败」之后**永久卡死**

**位置**：`sql/migrations/startup/902_stats_event_dedup_pkey_include.sql`（步骤 ①）与 `installer/cmd/llm-gw-installer/embeddata/startup/902_stats_event_dedup_pkey_include.sql`（孪生副本）

**机制**（不是推理，★ 已实测，见 §5.1 的实测原文）：
1. PG 的既定行为：`CREATE INDEX CONCURRENTLY` 失败后**留下一个 invalid 索引**（`indisvalid = false`）。
2. 902 的步骤 ① 是 `CREATE UNIQUE INDEX CONCURRENTLY **IF NOT EXISTS** <tmp>` ⇒ `IF NOT EXISTS` **只按名字判存在**，**不看 validity** ⇒ ⇒ 遇到上一步留下的 invalid 索引 ⇒ **跳过创建**（只打一条 NOTICE）。
3. 步骤 ② 的形状守卫要求 tmp 索引 `indisvalid AND indisready AND indisunique` 且形状正确 ⇒ invalid 索引不满足 ⇒ ⇒ **`RAISE EXCEPTION ... refusing to swap pkey`** ⇒ 迁移失败。
4. 失败后下一次重跑走**完全相同**的路径（① 跳过 → ② 抛错）⇒ ⇒ **永久卡死**，除非人工 `DROP INDEX`。

**为什么这条重要**：
- 902 是 installer `StartupFiles` 的**链尾** ⇒ ⇒ 它失败 ⇒ **新装链与升级链都断**（不是「一条迁移跳过」而是「安装器起不来」）。
- 触发条件不是臆想：`statement_timeout='10min'` 在 409 MB 的活写表上被触发、连接中断、构建被取消 —— **任一都足以留下 invalid 索引**。
- 迁移 902 **仍在属主待授权状态**（本窗口提交明确写「属主待拍板 …902授权…」）⇒ ⇒ **现在修的成本最低；等它上生产后再修就是热修**。

**★ 注意它 fail-close（不损坏数据）**：实测证明换体**没有发生**（pkey 仍是 `PRIMARY KEY (event_id)`，无 INCLUDE）⇒ ⇒ 这是**活性/可重入性缺陷**，不是数据损坏缺陷。风险等级因此定为「中」而非「高」。

### ★ 问题 ②【中·门覆盖·流程闭环·潜伏】§143.103 的 L3 短路判据**没有门**钉住它的承重不变式

**位置**：`domains/hooks/compression/probe_session.go`（判据 `IsProbeSyntheticSessionID`）+ `cmd/gateway/section_143103_l3_probe_shortcircuit_test.go`（现有 4 腿门）

**承重不变式**（§2.4 已逐层证明）：`entry.GwSessionID` **不可能**以 `sys:probe:` 开头 ⇒ 所以「前缀命中」≡「网关合成的探测会话」⇒ 所以短路是零语义的。

**缺口**：这条不变式由 **3 个文件的 3 处独立代码**共同保障（`sanitizeGwSessionHeader` 的前缀白名单 / `deriveGatewaySessionID` 的前置 `gw_` / 会话库只 mint `gw_<uuid>`），**彼此零交叉校验，且没有任何门断言它**。现有的 4 腿门覆盖的是「生成器形状 ↔ 判定一致」「默认关」「接线位置」「文档登记」—— **没有一腿断言「客户端够不到 `sys:` 命名空间」**。

**后果（一旦不变式被破坏）**：客户端造出 `gw_session_id = "sys:probe:cred99:20261024"`
⇒ ⇒ `GwSessionID` 非空 ⇒ `IsProbeSyntheticSession` 为 false ⇒ **该条目被镜像**（`session_turns` + `session_bodies` 都有行）
⇒ ⇒ L3 本该读到它的 outbound 正文
⇒ ⇒ 而短路判据前缀命中 ⇒ **L3 被跳过**
⇒ ⇒ **静默丢失该会话的 outbound 正文**（不报错、不崩溃 ⇒ 最难发现的一类）
⇒ ⇒ 且因为开关默认关，**一旦属主为拿 L3 收益而打开开关，缺陷即刻生效**。

**为什么定「中」而不是「高」**：今天**不可达**（已逐层证明）；开关默认关；且现有形态下 L3 的本地路径还有腿①②兜底（腿①命中即提前返回）。但它是「**未来一改就成真缺陷**」的高危潜伏项 ⇒ 按本仓「一致性由测试保证，不由注释保证」的纪律，**必须补门**。

## 5. 实施落地记录（本轮实际改了哪些）

### 5.1 问题 ① 的修法：902 加步骤 ⓪ —— 只清理 **invalid** 残留，绝不碰合法的 tmp 索引

**修法**（在步骤 ① 之前插入）：

```sql
-- ⓪ 兜底：清掉「上一次 CONCURRENTLY 构建失败」留下的【无效】tmp 索引。
--
-- ★ 为什么必须这一步（★ 本轮实测复现，不是推理）：
--   PG 的既定行为 = CREATE INDEX CONCURRENTLY 失败会留下一个 invalid 索引。
--   而步骤 ① 是 `CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS <tmp>` ⇒
--   `IF NOT EXISTS` **只按名字判存在、不看 validity** ⇒ ⇒ 遇到这个残留
--   ⇒ 步骤 ① **跳过创建**（只打一条 NOTICE）⇒ ⇒ 步骤 ② 的形状守卫
--   （要求 indisvalid AND indisready）**必然抛错** ⇒ ⇒ 迁移失败。
--   ⇒ 而失败后每次重跑都走同一条路径 ⇒ ⇒ **永久卡死**，除非人工 DROP INDEX。
--   ⇒ 触发条件不是臆想：statement_timeout=10min 被触发 / 连接中断 / 构建被取消。
--
-- ★ 只删【无效】的：合法的 tmp 索引是步骤 ①→② 的中间产物，删了会让
--   步骤 ① 重建（白跑一遍 CONCURRENTLY 构建）。
-- ★ 用普通 DROP INDEX（不是 CONCURRENTLY）：本文件是 dbinit:no-transaction，
--   但 DO 块本身是一个事务块 ⇒ `DROP INDEX CONCURRENTLY` 在事务块内会被
--   PG 拒绝（"cannot run inside a transaction block"）⇒ ⇒ 这里必须用普通
--   DROP；且它只作用在一个 invalid 索引上（无并发写者依赖它）。
DO $pre$
DECLARE
    v_bad boolean;
BEGIN
    SELECT EXISTS (
        SELECT 1
          FROM pg_index ix
          JOIN pg_class i     ON i.oid = ix.indexrelid
          JOIN pg_namespace n ON n.oid = i.relnamespace
         WHERE n.nspname = 'public'
           AND i.relname = 'stats_event_dedup_pkey_include_tmp'
           AND NOT (ix.indisvalid AND ix.indisready)
    ) INTO v_bad;

    IF v_bad THEN
        EXECUTE 'DROP INDEX IF EXISTS stats_event_dedup_pkey_include_tmp';
        RAISE NOTICE '902: dropped INVALID leftover tmp index from a previously failed CONCURRENTLY build';
    END IF;
END
$pre$;
```

**★ 实测（一次性 PG 容器 `postgres:16-alpine`，PG 16.15）**：

*修前*（跑仓内**真实**的 902 迁移文件，起点 = 人为制造的 invalid 残留态）：
```
psql:/tmp/902.sql:67: NOTICE:  relation "stats_event_dedup_pkey_include_tmp" already exists, skipping
psql:/tmp/902.sql:122: ERROR:  902: tmp index stats_event_dedup_pkey_include_tmp missing/invalid/wrong-shape — refusing to swap pkey
```
⇒ **步骤 ① 跳过 + 步骤 ② 抛错**，且残留索引状态为 `indisvalid = f / indisready = f`。

*修后*（同一坏起点）：
```
NOTICE:  902: dropped INVALID leftover tmp index from a previously failed CONCURRENTLY build
psql:/tmp/902.sql:122: NOTICE:  ALTER TABLE / ADD CONSTRAINT USING INDEX will rename index "stats_event_dedup_pkey_include_tmp" to "stats_event_dedup_pkey"
...
        conname         |             pg_get_constraintdef
------------------------+------------------------------------
 stats_event_dedup_pkey | PRIMARY KEY (event_id) INCLUDE (occurred_at)
```
⇒ ⇒ **迁移从坏起点成功完成，换体落到预期形状，且不留孤儿 tmp 索引** ✓

**★ 为什么不动步骤 ① 本身**：`CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS` 是 PG 的既有语义（名字级幂等），改它等于在迁移里自造一条非标准语义；把「清残留」做成**独立的前置步骤**语义更清楚，也不影响步骤 ① 的可读性。

### 5.6 问题 ④ 的修法：**改门不改代码** —— 把 shell 门的判据对齐到 Go 门，并加自检矩阵

**修法（`scripts/guards/check-shell-fullwidth-var.sh`）**：

1. **判据逐字对齐 Go 门**（`scripts/ursmcheck/cjk_var_expansion_test.go` 的 `cjkCodeSegment` / `stripBracedVars` / `bareVarMatches`），共五条：
   - ① 只认**裸** `$VAR`；`${VAR}` 安全；
   - ② 剥掉**尾随注释**（`#` 在引号外**且**处于**词首** ⇒ `a#b` 是字面量，不是注释）；
   - ③ 剥掉**单引号**区段；
   - ④ `\$`（**奇数个**连续反斜杠）不是展开点；
   - ⑤ 其余位置：`$VAR` 后紧跟一个 **>= 0x80 的字节** ⇒ 1 个站点。
   - ⇒ 实现载体是 **awk**（**全程 `LC_ALL=C`**，按**字节**处理）；「非 ASCII」用 `[\200-\377]` 精确表达（**不用** `[^ -~]` —— 后者还会命中控制字节，而 bash 不会把控制字节并进变量名 ⇒ 会把 `$VAR<TAB>` 误判成站点）。
   - ⇒ **预筛**（grep `\$[A-Za-z_][A-Za-z0-9_]*[^ -~]`）是**超集**（注释里、单引号里、`\$` 转义的、`${VAR}` 的都会进候选）⇒ ⇒ **不会漏**真站点（真站点在原始字节里就是「`$VAR`」紧跟一个 `>= 0x80` 的字节）⇒ ⇒ 真正的判定交给 awk。
2. **加 11 条自检矩阵**（阳性 5 / 阴性 6）：**每条期望值都用真实 bash 实测钉死**（`LC_ALL=en_US.UTF-8` + `set -u` + 变量先定义 `v=X` ⇒ 只观察「变量名是否被那个非 ASCII 字节吞掉」，签名 = 报错文案里出现该字节）。
   - ★ 阳性 5 条：`"X$v中Y"` / `"$v）"` / `"$v（"` / `a#b "$v中"`（**`#` 不在词首 ⇒ 不是注释**）/ `"X\\$v中Y"`（**`\\` ⇒ `$` 仍展开**）
   - ★ 阴性 6 条：`"X${v}中Y"` / `"X\$v中Y"` / 整行注释 / 尾随注释 / 单引号 / 普通 ASCII
   - ⇒ ⇒ **自检不过 ⇒ ABORT exit 2**（门不产出「零命中」这种无法区分「干净」与「门坏了」的读数）。
3. **扫描面**（有意与 Go 门不同，已在脚本头与 `Makefile` 里写明）：
   - Go 门只扫 **git 追踪**的文件（它要拿读数去对**棘轮登记册** ⇒ 读数必须确定）；
   - shell 门扫 **已跟踪 ∪ 未跟踪未忽略** ⇒ 「新写好还没 `git add` 的脚本」也在视野里 ⇒ **本门无登记册 ⇒ 宽面不引入不确定性** ⇒ ⇒ 扫描面 = shell 门 ⊇ Go 门，**判据则逐字一致**。

**★★ 顺手堵掉的两处「静默失败」（★ 本轮审脚本时发现，★ 属「门坏了却报干净」类）**：
1. `_scan_line` 原本写成 `awk ... | grep -q .` ⇒ ⇒ 在 `set -o pipefail` 下，**「awk 自己执行失败」与「没命中」是同一个退出码** ⇒ ⇒ 扫描器坏了，门也会**假装干净** ⇒ ⇒ 改为：显式取 awk 的输出，**awk 非零 ⇒ ABORT exit 2**。
