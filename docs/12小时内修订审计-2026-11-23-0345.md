### A 族｜会话分析 Top5 / 排行口径（`614b72e9c` `f268599de` `0a1b56237`）

- **原因**：Top5「用户」榜按 `rl.end_user_id` 原值分组，而部分客户端把 `user`
  报成 JSON 对象 ⇒ ① 界面渲染成一坨被截断的 JSON；② 该 JSON 内含 `session_id`
  ⇒ 实际按**会话**分组（现网 14,674 行 JSON 只对应 1 个 device_id、117 个 session_id）。
- **方案**：排行侧与**过滤侧共用同一个表达式常量** `userIdentityExpr`
  （`admin/logs.go` 定义、`admin/usage.go` 引用），按 device_id 归一、
  NULL/空串/无 device_id 归 `unknown`。
- **判定**：**合理**。共用常量是这类修复的关键——两处各写一份表达式是
  「卡片显示 14,674、点进去 0 条」的最常见假绿来源，作者显式点出了这一点。
  SQL 用 `substring(... from ...)` 正则形式而非 `::jsonb->>`，是因为该列混着
  `anonymous` / NULL / 纯 id 等**非法 JSON** 值，`::jsonb` 会对它们抛错（整条查询 500），
  而 `CASE` 的惰性保证非 JSON 行不做正则运算——**这一层是正确且必要的**。
  ★ 注释里也钉住了「表达式不得含 `%`」（会与 `fmt.Sprintf` 的格式动词冲突），
  说明作者踩过或预判过该坑。
- **执行结果**：cursor 侧 `0a1b56237` 已落 main，并配真库钉测 +
  前端契约钉测。**通过**。
- ★ 残留观察（非本轮缺陷）：`userIdentityExpr` 目前只用在排行侧与日志过滤侧，
  其余读 `end_user_id` 的地方（如看板维度）是否也需要归一，**未逐一核**——
  登记为待核项，不在本轮改。

### C 族｜时间区间统一（`594e5fd43`）

- **原因**：全站统计页面用统一日期选择器，但后端多数端点只收 `?days=N`
  并解释为「相对现在的**滚动窗口**」；前端 `useSpanDaysRange` 又把用户选的
  **自定义日期区间**压成「跨度天数」⇒ 用户选 2026-09-01~09-10，实际拿到**最近 10 天**。
  实测：`GET /api/admin/work-types/stats?start_date=...&end_date=...`
  → 200 且 `window="24h"`（参数被静默忽略）。
- **方案**：后端 `parseStatsTimeRange` 同时接受 `start`/`end`（真实区间）
  与 `days`（天数预设），两者皆缺才用端点默认；前端透传真实区间。
- **判定**：**合理，且四个设计选择都站得住**：
  1. 用**既有** `settings.SystemDayRangeUtc` 转换，不自拼 `ParseSystemDate(...).UTC()`
     —— 后者在 UTC+8 会把起点显示成前一天（作者明说时区轮单测已钉过这条）；
  2. 半开区间 `[Start, End)`，`End` = end 日 +1 天零点 ⇒ **end 日整天计入**，
     且 `spanDays` 不再二次 `+1`（否则 10 天区间会被算成 11 天）；
  3. `days` 分支保留**零参数字面量 interval**（`NOW() - INTERVAL '24 hours'`）
     —— 在库里求值、客户端时钟不参与，改成 `INTERVAL '1 day' * $1` 在 DST 时区会差 1 小时；
  4. 超 90 天 ⇒ **400 而不是静默夹紧**；只给半截区间 ⇒ 报错而不是回落
     （回落会静默给出错误窗口）。
- **执行结果**：**通过**（含 `admin/stats_time_range_test.go` 钉测）。
- ★ **P3 残留**：`spanDays := int(endUtc.Sub(startUtc) / (24 * time.Hour))`
  在**有 DST 的系统时区**下，两个午夜之差可能是 23h/25h ⇒ 整除截断成 29/31 天。
  影响面仅限 90 天上限判定（`Days`/`Hours` 在 Custom 模式下不进 SQL）。
  当前部署时区 Asia/Shanghai **无 DST** ⇒ 暂不成立。**登记待观察**：若将来支持
  DST 时区部署，此处须改为按日历日差计算。

### D 族｜物化视图刷新器（`b0ef800ff`）

- **原因**（两台生产各一处，同一天实证）：
  - 211：matrix 的 `REFRESH CONCURRENTLY` 选并行计划 ⇒ DSM 撞 64MB `/dev/shm`
    （SQLSTATE 53100 秒败）⇒ 刷新戳冻结 ⇒ 详情端点恒 503 `analytics_view_stale`；
  - 252：981 族单视图 mean 134~266s / max 494~578s，把**整轮共享**的 20min ctx 吃光
    ⇒ 尾部 matrix 跑 87~94s 被 ctx 掐死，后面的视图带着已死 ctx 秒败。
- **方案**：① 357 全族收编进 `serialRefreshViews`（串行）；
  ② 整轮共享 ctx（20min）→ **每视图独立预算**（`SessionViewRefreshBudget` 15min）；
  ③ 视图顺序按 252 实测 mean 重排（SJF）。
- **判定**：**合理**。核心判断——「7 张视图最坏和 ≈43min，任何整轮 ctx 都装不下
  ⇒ 结构性修法是每视图一份」——是对的：整轮预算是**不可能满足**的约束，
  继续抬整轮钉子只是把同一个洞挪位置。
- **★ 并发 / 泄漏专项核查（本轮重点核的一项）**：
  - **ctx 泄漏：无**。每视图 `ctx, cancel := context.WithTimeout(parentCtx, SessionViewRefreshBudget)`
    写在**循环体内**，且 `cancel()` 是**显式调用**、**不是** `defer`——
    ⇒ 不会累积到函数返回才释放（本审计特意核了这一点：`defer` 写在循环里是典型泄漏形态）。
  - **tick 堆积：无**。`refreshLoop` 单 goroutine，`sessionTimer` 在**整轮结束后**才 `Reset`。
  - **锁预算共享**：`retryDeadline` 在循环外算一次，四视图共享一份 4min 锁等待预算。
    这是**显式取舍**（注释写明「skipped_no_lock 不是新鲜度损失——持锁方正在刷
    同一批视图并落同一张戳表」），且有钉测
    (`bg/materialized_view_refresher_lockretry_test.go`) ⇒ 判定**合理**。
  - **代价已知悉**：病态轮可推迟 routing tick（routing 有 15min 预算与退化路径，可恢复）
    ——「用可恢复的 tick 延迟换用户可见的 503」是刻意取舍，且写在注释里。
- **执行结果**：**通过**。

### F1【P0】团队预算门的 SQL 引用**真实 schema 里不存在**的两列 ⇒ 运行必 42703

**位置**：`maas/team_budget_gate.go`（`sumTeamPeriodConsumption`）

**缺陷 SQL**：

```sql
SELECT COALESCE(SUM(ccb.credits), 0)
  FROM maas_credit_consumption_buckets ccb
 INNER JOIN api_keys ak ON ccb.api_key_id = ak.id
 WHERE ak.team_id = $1
   AND ccb.period_start >= $2
   AND ccb.period_start < $3
```

**真实 schema**（`sql/migrations/startup/389_maas_credit_consumption_buckets.sql`
+ `sql/schema/01-schema.sql:9409`，两者一致）：

```
tenant_id      text        NOT NULL,
bucket_start   timestamptz NOT NULL,
credits        bigint      NOT NULL DEFAULT 0,
request_count  integer     NOT NULL DEFAULT 0,
updated_at     timestamptz NOT NULL DEFAULT now()
PRIMARY KEY (tenant_id, bucket_start)
```

⇒ **`ccb.api_key_id` 与 `ccb.period_start` 两列都不存在**
⇒ 运行时必然 `SQLSTATE 42703 column does not exist`。

**为什么被掩盖（三层假绿）**：

1. **未接线**——`CheckTeamMonthlyBudget` 零调用点 ⇒ 查询永不执行；
2. **零测试**——连单测都没有 ⇒ 假 store 不会告诉你列不存在
   （B 族的 `analytics_schema_guard_test.go` 已经把这条教训写进仓内，本轮是**同一族错误的另一次发作**）；
3. **自我声明与实现不符**——文件头原文写
   「★ 口径锚点：花费与租户预算门同源 …… 门与账单不能打架：同一换算，禁止另起聚合」，
   而实现与真实 schema 完全对不上 ⇒ **照着注释验收的人会验到一个不存在的保证**。

**★ 更深的一层：只把列名改对也是错的。**
`maas_credit_consumption_buckets` 只有**租户粒度**（PK 是 `tenant_id + bucket_start`），
没有 `api_key_id` ⇒ 团队粒度**根本无法**从该表聚合；
若硬凑（例如按 `tenant_id` 关联），结果是「把**整个租户**的消费记到每个团队头上」
⇒ **比不实现更危险**。

**正确真源**：`usage_facts`（迁移 537）—— 唯一同时具备
「按 key 归因」（`api_key_id`）与「credits 计费」（`credits_charged`）的真源；
`domains/stats/reconciliation.go:42` 自称 usage_facts 为 **source of truth**；
写侧 `cmd/gateway/main.go:9970` 把 `keyInfo.ID` 落进 `api_key_id`，
`domains/stats/inbox_consumer.go:507` 落进 `usage_facts`。

**本轮处置**：换真源 + 订正注释 + 加 schema 守卫（见 §六）。

### F3【P1】零候选归因诊断在**失败路径**上没有独立时间预算

- **位置**：`domains/streaming/no_candidate_cause.go`（`diagnoseNoCandidateCause`）
  → `provider/candidate_empty_diag.go:364`（`diagnoseEmptyCandidates`）。
- **缺陷**：诊断直接用请求 ctx（`r.Context()`），**没有自己的时间上限**
  ⇒ 失败路径（恰是 DB 最可能吃紧的时刻）的旁路查询一旦慢，
  **503 的应答就被拖住**；且三个协议面（chat/completions / messages / responses）各付一次。
- **既有纪律的盲区**：仓内已有「诊断是旁路，失败就退回通用文案，绝不让诊断失败变成新的请求失败」
  ——但那条纪律只挡得住「诊断**出错**」，**挡不住「诊断很慢」**。
- **本轮处置**：给诊断加**独立**的 2s 预算（从请求 ctx 派生 ⇒ 客户端取消仍透传），
  超预算走既有的「诊断出错」分支 ⇒ 不新增任何失败形态。

## 五、通用式（本轮沉淀）

1. **「注释/提交信息里的口径声明」也是交付物**，同样要对着实现核——
   F1 的文件头那句「门与账单不能打架」正是**自我声明与实现不符**的例子。
2. **「写想象中的 schema」会复发**，且**复发时会被「未接线 + 零测试」双重掩盖** ⇒
   凡是有真源可比的 SQL 改动，**同一轮就要把源码守卫一起落**（B 族做对了，F1 没做）。
3. **守卫必须带负控**：本轮 F1 的 schema 守卫**第一版是假绿**（见通用式 6）——
   只看「主门绿」看不出它一条都没判。⇒ **守卫自己要能证明「它会红」**。
4. **失败路径上的旁路工作必须自带预算**：既有「诊断失败不许变成请求失败」的纪律是对的，
   但它只覆盖**错**、不覆盖**慢** ⇒ 旁路工作需要**自己的**时间上限。
5. **schema 真源＝基线 ∪ 迁移**：`sql/schema/01-schema.sql` 是**快照**，
   不含 `usage_facts` / `teams` / `team_budgets` 等新表；
   `sql/migrations/startup/` 是**增量**，不含 `api_keys` 等基线表。
   ★ 只扫任一边都会得到「假红或假绿」的守卫（本轮两次踩中）。
6. **假绿的形态之一是「查无对象」**：守卫的正则若把**可选组**写成永远匹配空，
   就会「一条引用都跳不过去 → 恒绿」。⇒ 守卫要**统计判定了多少条**，
   并用负控断言「判定数 > 0 且坏输入确实报红」。
7. **「已建表」≠「已生效」**：schema 迁移落地后，运维侧会自然认为能力已具备
   ⇒ 未接线的门必须在**源码 + 审计档 + AGENTS.md** 三处显式登记。
