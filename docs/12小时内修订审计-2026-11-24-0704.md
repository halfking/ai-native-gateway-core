### 2.1 后端 Go（`internal/metricsstore` + `cmd/gateway`）

#### ✅ [P0-1] 4xx 行为契约已改，**行为守卫却停在旧契约** ⇒ 主干带着一个红测试

- **机制**：`540a3f763`（owner 明确要求「候选被永久性原因挡空时更换成 4xx 并返回正确错误信息」）把 `no_candidate` 的状态码由 503 改为**按归因派生**（`model_not_registered`→404 / `provider_not_in_tenant`→403 / `upstream_quota_exhausted`→429 / 其余→503），但 `domains/streaming/no_candidate_cause_test.go` 的行为守卫 `TestNoCandidateCause_BehaviouralWiring` 仍硬断言 `503`。
- **提交自称**「测试调整：`no_candidate_cause_test.go` 文案断言更新」——**实际只改了一行文案**（`模型未登记`→`未在此网关登记`），行为断言一字未动。
- **实测（审计起点 origin/main）**：三协议面全红：`status = 429, want 503`。
- **本轮修法**：按**已定契约**订正断言（主因＝配额耗尽 ⇒ 429），并保留「无归因 ⇒ 仍 503」的阴性对照（`TestNoCandidateCause_BehaviouralWiring_LegacyWithoutDiagnosis` 不动）。
- **同类第二处**：全包跑完后又暴露一条**同源的陈旧断言** —— `TestWriteNoCandidateWithCause_Envelopes` 对**所有**臂都断言 503，而实现里「**没有替代模型可给**」这一支已按归因派生 4xx（「有替代」仍 503，因为还能换模型重试）⇒ 本轮把该用例改成**分臂期望**（无替代 ⇒ 429 + Anthropic `type=rate_limit_error`；有替代 ⇒ 503 + `type=overloaded_error`）。
  ⇒ **教训**：`540a3f763` 改了**状态码契约**，但**只改了文案断言**；**行为断言分散在两个用例里**，只跑其中一个（或只跑 `-run` 定向用例）就会漏掉另一处 ⇒ **凡是改契约，必须跑整包**。
- **复核**：`go test ./domains/streaming/ -count=1` → **ok（整包）**。

#### ✅ [P1-1] 模型别名映射**不确定** ⇒ 同一模型在不同批次可能落到不同 `canonical_id`

- **机制**：`model_aliases` 的唯一约束是 **`UNIQUE (canonical_id, raw_name)`**，**不是** `UNIQUE(raw_name)` ⇒ **同一个 `raw_name` 合法地对应多个 `canonical_id`**（旁证：承重索引 `idx_model_aliases_raw_name_active` 本身就是 `(raw_name, canonical_id)`）。
  原批量写法既无 `LIMIT` 也无 `DISTINCT ON` ⇒ 同名多行时 `mappings[rawName] = …` **被后扫到的行覆盖** ⇒ 胜者取决于 PG 扫描顺序 ⇒ 不可复现。
- **后果**：按模型聚合时同一标准模型被拆成两个口径，且**同一请求在不同批次可能拿到不同的 `canonical_id`**。
- **证据**：`sql/migrations/domain/357_repair_model_aliases_unique.sql:32-33`（约束定义）、`sql/migrations/startup/864_model_aliases_bare_raw_name_active_idx.sql:41-43`（索引形状）、`internal/metricsstore/processor.go`（批量映射 SQL 无 `DISTINCT ON`）。
- **本轮修法**：`SELECT DISTINCT ON (ma.raw_name) … ORDER BY ma.raw_name, ma.canonical_id` ⇒ 每个 `raw_name` 恰好一行、胜者恒为最小 `canonical_id`（可复现），且该 `ORDER BY` 正好由既有部分索引支撑。
- **钉测**：`TestBatchEnrichModelInfoSQL_IsDeterministicPerRawName`（钉 `DISTINCT ON` + `ORDER BY`，并禁止再混入 `LIMIT 1`）。

#### ✅ [P1-2] 批量映射失败被**静默吞掉** ⇒ 整批标准模型维度永久丢失

- **机制**：批量映射查询失败时，原实现只打一行 `log.Printf` 就继续 ⇒ 该批带 `raw_model_name` 的行 **没有 `canonical_id` / `outbound_model`**，但**行照样落库、水位线照样推进** ⇒ **不会被重试补齐**（永久丢失），且**失败计数为零** ⇒ 无任何可见出口。
- **与仓内纪律的冲突**：同文件 `enrichDimensions` 的失败被**显式计数 + 汇总一条日志**（注释写明「静默失败正是这次事故的根因」），而模型映射这条路径没有 ⇒ **同一份代码里两套失败可见性**。
- **本轮修法**：映射失败计入失败计数并在批末**汇总一条**（含受影响行数、模型名数、首条原因）⇒ 不阻断计量（计量不能丢），但**不可静默**。
- **钉测**：`TestProcessBatch_ModelMappingFailureIsNotSilentlySwallowed`（捕获标准 logger 输出，断言汇总日志出现「模型映射失败」）。

#### ✅ [P1-3] 「解决 N+1」只批量化了轻查询，**重查询仍是逐行 N 次**

- **机制**：`enrichDimensions` 在循环内按 `request_id` 逐行查 **`request_logs_with_current_month`**（双腿视图＝`session_turns_hot ∪ session_turns` 全族）⇒ 每批 N 次重查询；而 `df48c5d4b` 只批量化了 `model_aliases`（轻查询）。
- **提交说明与实测不符**：「查询次数：从 N 次降低到 1 次」「性能提升：10倍+」——实测每批仍是 `1（来源）+ N（重查询）+ 1（映射）` 次。
- **本轮修法**：维度增强改为**整批一次**（`WHERE request_id = ANY($1)` + `DISTINCT ON (request_id) … ORDER BY (request_id, ts DESC)`，与逐行 `ORDER BY ts DESC LIMIT 1` 等价）；「没有会话行」在批量形态下＝「结果集里没有这个 request_id」，与逐行的 `sql.ErrNoRows` 同义 ⇒ 仍**不算失败**（保住「良性情况不刷假警报」这条既有纪律）。
- **钉测**：`TestEnrichDimensionsSQL_BatchesAllRequestIDsInOneQuery`（SQL 形态）+ `TestProcessBatch_EnrichesDimensionsInOneQueryPerBatch`（两条来源记录 ⇒ 维度查询**仍然只有 1 次**；实现若退回逐行，sqlmock 有序匹配会直接红）。

#### ✅ [P2-1] 后台 processor 用 `context.Background()` ⇒ 停机后 goroutine 不可停

- **机制**：`cmd/gateway/main.go` 里 `go metricsProcessor.Run(context.Background(), 5*time.Minute, 100)` ⇒ 该 goroutine **在进程内永远不可停** ⇒ 优雅停机后它仍在跑，而此时连接池已关 ⇒ 每 5 分钟刷一批「连接已关闭」错误，且**批次里的维度永远补不回来**。

## 3. 有序执行方案

### 3.1 分批原则

1. **先让主干可编译、可测试**——一个编译红的仓，任何后续结论都不可信（量具本身是坏的）。
2. **再让「数据能落地」**——迁移没被投递 ⇒ 写入必失败 ⇒ 功能等于不存在；这一层不修，上面所有优化都是空转。
3. **然后修「行为与预期不符」**——口径漂移、不可复现、失败被吞。
4. **最后是质量项**——死代码、格式漂移、量具覆盖不足。
5. **凡触及生产 schema 字节 / 行为契约的，一律停在方案层**（§4），不夹带。

### 3.2 批次表（本轮实际执行顺序）

### 3.3 为什么这个顺序

- **B1 必须最先**：installer 编译红 ⇒ `make guards` 整族红 ⇒ **B2/B3 的验收信号全部不可信**（量具失效）。先修量具，再修被测对象。
- **B2 早于 B4~B7**：973 是 B5/B7 那两条链路能真正跑起来的前提（列不存在 ⇒ 钉测再多也只是在测 mock）。
- **B4 与 B2/B3 无关但同属「主干红」**：红灯不放着——它会让后续任何 CI 信号失真。
- **B5→B6→B7 是同一条链路上「对 → 准 → 快」的次序**：先让口径确定（否则批量查询的结果本身就不可信），再让失败可见（否则不确定性的失败会静默），最后才是批量化的性能收益。
