## 二、实现：三个取值，不合并

```
alive  v1 侧在窗口内有行                    ← 判定只看行存在性
dead   v1 侧两面都零行、session 侧有行     ← 写腿死了
quiet  两侧都零行                          ← 什么都没证明
```

★ **`quiet` 不能并进 `dead`**：把「死了」与「没人用」合成一个布尔量，
等于让运维在集群安静时收到死亡告警 —— 那类告警的真实结局是被忽略，
然后下一次真的死亡也一起被忽略。这与 `dual_read_gate.go` 规则 2
（「空扫描 = 什么都没证明」）同源。

⚠ **判决里没有开关这一项**，所以它只可能来自行存在性 ——
这正是 §9.238 要的那条性质。门 `TestClassifyV1WriteLivenessIsNotDrivenByTheSwitch`
用 §9.238 的原始形状（v1 零行 + session 在写）钉住。

## 三、★ 实测：单面实现此刻就会误判（活的假阳性）

本地真库，2026-10-06 22:5x，**最近 30 分钟**：

| 关系 | 行数 | 落后 |
|---|---:|---:|
| `request_logs_hot` | **160** | 1 分钟 |
| `request_logs`（父） | **0** | **491 分钟** |
| `session_turns_hot` | 52 | 1 分钟 |
| `session_turns`（父） | 0 | 491 分钟 |

⇒ v1 活得好好的（30 分钟 160 行），而**只读父表的实现会判成 `quiet`**
——「什么都没证明」。

真库门把两种常见单面实现都跑了，并断言**它们都不是 `alive`**：

| 实现 | 判决 | 问题 |
|---|---|---|
| 两面都只读父表 | `quiet` | **「什么都没证明」—— §9.238 的原始失效形态** |
| v1 读父表、turns 读 hot | `dead` | 假死警 |
| **双面（本实现）** | `alive` | ✅ |

★ 记下「错成哪个」取决于实现怎么写，是因为**两种都错**才是要拦的东西；
只断言一种会让人以为另一种是安全的。

**为什么父表落后 491 分钟是正常形态**：`request_logs_hot` 只保留最新窗口
（本地库里它总共只有几小时的数据），父表按月分区、靠晋级填充。
把「父表近 30 分钟无行」当成死亡信号，会让运维去修一个健康的系统。

**这已经是同一个陷阱的第 N 次**：`dual_read_gate.go` 文件头记的是
「§9.160.7 的 trap，在本节里第三次命中」；
§9.263 是第四次（父表总体 1h/6h 读成 0/0，两面是 150/1000），
**本轮是第五次**。新门 `TestV1WriteLivenessSQLReadsBothFaces` 把它变成会红的断言。

## 四、门（3 道）

| 门 | 断言什么 | 变异检验 |
|---|---|---|
| `TestV1WriteLivenessSQLReadsBothFaces` | 四个面各读一次；带**负控制**（单面片段必须被判成单面） | 删 `request_logs_hot` → 红 |
| `TestClassifyV1WriteLiveness` | 6 种形状各一条，含「只有 hot 面有行」（本地此刻的形状） | 分类函数只读 hot → 红；`quiet` 塌进 `dead` → 红 |
| `TestClassifyV1WriteLivenessIsNotDrivenByTheSwitch` | §9.238 形状必须判 `dead`；同一时刻热面有行必须判 `alive`；**单面喂入必须判 `dead`**（负控制） | 分类函数退回单面 → 红 |
| `TestV1WriteLiveness_RealDB` | 真 SQL **能执行**；判决 `alive`；两种单面实现都**不是** `alive` | 删掉 hot 面 → 红 |

4 个变异全部按预期变红（M1 连真库门一起红）。

## 五、限度与未验项

- **本轮没有接线。** `v1WriteLiveness()` 是一个可调用的函数，
  **没有任何 HTTP 端点、后台 worker 或指标在用它** ——
  「常驻信号」要接到哪里（admin 端点 / `/metrics` gauge / 告警）是**属主的决定**，
  涉及新增对外表面，本轮不做。
- **真库门会跳过**（`TEST_PG_DSN` 未设时），所以 CI 上默认只跑静态那两道。
- 窗口取 30 分钟是本实现的选择，**没有论证**。父表晋级延迟、hot 窗口长度
  与它的关系没有量过 ⇒ 窗口太短会误报 `dead`，太长会延迟发现。
  这一点**未验**。
- **「父表落后 hot 是正常形态」这一条我只量了本地库一个时点**（491 分钟），
  没有查父表晋级机制，也没有在任何生产环境核对过。
- 生产 252 未做任何查询。
