## 1. 审计方法：怎么查「锁到底互斥吗」

★ 上一轮的四问法（见第一轮审计档 §2）查的是「**功能有没有被测到**」；本轮换四问，
查的是「**互斥这个性质本身**」：

| # | 问法 | 查出了什么 |
|---|---|---|
| ① | **「持有者还活着吗」这个判据本身对吗？**（不是「有没有锁」，是「**活着的持有者会不会被当成死的**」） | ★ **F1**：EPERM ≠ ESRCH ⇒ 活锁被接管 |
| ② | ★ **这半边实现**在生产上会被执行到吗？**（门有没有覆盖到**） | ★ **F2**：flock 分支从未被执行过 |
| ③ | ★ **锁的「身份」是什么**（一个路径？两种形态？）**——形态变了会怎样？** | ★ **F3**：形态由工具可用性决定 ⇒ 撞上另一种形态 ⇒ 致命 exec |
| ④ | ★ **同一个问题的两个函数会不会给出相反答案？** | ★ **F4 / F5**：恢复命令 vs 残锁判定 |

★ **纪律**：每条发现都必须配一条**能红**的判据 ⇒ 本轮 **7 条变异臂**逐条验证
（§8），且每条臂还原后 **md5 逐字一致**。

## 2. F1（高）：★ 存活判据把 EPERM 当成「进程已死」⇒ 会接管别人的活锁

### 2.1 缺陷本体（★ 实测复现，不是推理）

★ 本仓旧实现（`scripts/deploy-local-lib.sh`）：

```bash
# ★ 用 `kill -0` 而不是 `ps`：ps 在部分容器里缺 procfs 语义。
# ★ EPERM（存在但无权限）也**算活着** ⇒ 只在「确实没有这个进程」时才判死。
dl_pid_alive() {
  local pid="$1"
  [[ "$pid" =~ ^[0-9]+$ ]] || return 1
  kill -0 "$pid" 2>/dev/null
}
```

★★ **注释说「EPERM 也算活着」，而实现恰恰相反**：`kill -0` 对
① ESRCH（进程真没了）与 ② EPERM（进程**还活着**、只是不属于我）
**返回完全相同的失败退出码** ⇒ ⇒ 旧实现把 ② 判成「死了」。

★ **真机实测（本机 uid 501，非 root）**：

```
$ kill -0 1 ; echo rc=$?
/bin/bash: line 0: kill: (1) - Operation not permitted
rc=1                      ← 失败（EPERM）
$ ps -p 1 -o pid=,comm=
    1 /sbin/launchd       ← 它**活着**
```

⇒ ★★ **pid 1 一直活着，但旧判据说它死了。**

### 2.2 后果：互斥被拆

★ 持有者是**别的用户**的进程时（root cron vs 操作员 shell —— 共享部署库
`lock.sh` 的注释点名的真实场景）：

```
部署 A（root 跑的）持锁 → 元数据 pid=1234（活着，但属于 root）
部署 B（niuer 跑的）抢锁 → kill -0 1234 ⇒ EPERM ⇒ 判「持有者已死」
                        ⇒ **接管掉 A 的活锁** ⇒ A 和 B 同时切流 8781/8782
```

⇒ ★★ **这正是这把锁存在的理由被自己拆掉。**

### 2.3 ★ 来历：这是共享部署库 **2026-09-18** 就修过的同一个 bug

★ 共享部署库 `~/workspace/ai-native-tools/deploy-lib/lock.sh` 的 `lock_pid_alive`
注释原文：

> 2026-09-18 (concurrent-deploy race audit): the previous checks used
> `kill -0 "$pid"`, which conflates ESRCH (process gone) with EPERM
> (process ALIVE but owned by another user) — both exit nonzero. A deploy
> launched by a different user (root cron vs operator shell) therefore looked
> DEAD to force recovery, which then deleted a live holder's lock and let two
> deploys interleave. `ps -p` reports existence regardless of ownership on
> macOS and Linux, so EPERM can no longer masquerade as death.

⇒ ★★★ **本仓 2026-10-27 新写的 `dl_pid_alive` 抄回了那个已经修掉的版本。**
⇒ ⇒ **本轮的核心结论不是「这个函数写错了」，而是「★ 同一套机制有两份实现，
而其中一份停在了旧版本 ⇒ 两侧必然漂移 ⇒ 仓内没有任何门比对过两侧」**
⇒ ⇒ 这就是新增**跨仓对拍门**（§7）的直接理由。

### 2.4 修法

```bash
dl_pid_probe_kill() { kill -0 "$1" 2>/dev/null; }   # 同用户快通道
dl_pid_probe_ps()   { ps -p "$1" -o pid= >/dev/null 2>&1; }  # 跨用户通道

dl_pid_alive() {
  local pid="$1"
  dl_pid_valid "$pid" || return 1
  dl_pid_probe_kill "$pid" && return 0
  dl_pid_probe_ps "$pid" && return 0
  return 1
}
```

★ 三点设计：
1. **取值顺序让「证据不足」偏向「活着」** ⇒ 宁可拒绝接管，不可误杀活锁。
2. ★ **pid 0 显式排除**（`kill -0 0` 探的是**进程组**、恒成功 ⇒ 一份 `pid=0` 的坏
   元数据会让锁**永远不可接管** ⇒ 机器被永久卡死）；前导零也拒收（进制语义歧义）。
3. ★ **两个探针独立成函数 = 判据的缝** ⇒ EPERM 那一支在**任何 uid** 下都能被测
   （root 跑判据时 `kill -0` 谁都成功 ⇒ 真机复现不出 EPERM ⇒ 必须有模拟臂）。

## 3. F2（高）：★ flock 分支从未被执行过一次 ⇒ 门抓不到的那一半实现

### 3.1 事实

★ 本机：**没有 `flock`**（`command -v flock` ⇒ 空），且 `/bin/bash` 是 **3.2.57**
⇒ `exec {var}<>` 语法（bash 4.1+）不可用 ⇒ ⇒ 旧实现的双重条件
`[[ -n "$flock_bin" ]] && dl_bash_ge 4 1` ⇒ **在本机恒为假**
⇒ ⇒ ★★ **旧判据（8 条不变量）一次都没进过 flock 分支**。

★ 而 flock 分支恰恰是**会崩**的那一支（§4）⇒ ⇒ **「门抓不到」的那一类缺陷**。

### 3.2 修法（两处）

1. **去掉 bash 版本门**：fd 分配在 bash 3.2 上也可用（固定 fd 200，避开 0~9 的
   常用区）⇒ 「有没有 flock」成为**唯一**的形态判据 ⇒ 两种形态在所有 bash 上
   都可执行 ⇒ ⇒ **判据覆盖到了生产链上的那一段**。
2. **用真语义的假 flock 把 flock 分支拉进生产路径**：判据里放一个 python
   `fcntl.flock` 的小壳（与 util-linux `flock -n` 同语义：抢不到就退出 1）
   ⇒ 判据走的是**真的** `dl_acquire_switch_lock`（自己按可用性选分支），
   **不是**直接调内部函数。

★ 顺带修掉一个隐藏地雷：固定 fd 会被「重复获取」二次 `exec` 覆盖 ⇒ 上一把锁被
**静默释放** ⇒ ⇒ 「已经是持有者时重复获取返回 75」这条契约现在在**入口**判定
（`DL_SWITCH_LOCK_HELD`），与 fd 分配方式无关。

## 4. F3（高）：★ 形态由「本机有没有 flock」决定 ⇒ 撞上另一种形态 ⇒ 致命 exec

### 4.1 缺陷本体（★ 实测）

★ 旧实现：先看 flock 能不能用，再 `exec <> "$path"` ⇒ 若路径上留着**另一种形态**
的锁（老版本 mkdir 建的目录锁、或装上 flock 之前建的目录锁）：

```
$ bash -c 'd=$(mktemp -d); exec {fd}<>"$d"; echo "SHOULD NOT REACH"'
bash: /var/.../tmp.XXXX: Is a directory
exit=1                      ← ★ 整个脚本死了，"SHOULD NOT REACH" 没打印
```

⇒ ★★ **POSIX 规定 exec 的重定向失败是致命的** ⇒ 部署脚本带着一句
"Is a directory" 死掉 ⇒ **运维看到的是「脚本崩了」，不是「有人在切流」**
⇒ ⇒ 与这把锁的设计意图（rc=75 快速失败 + 告诉运维谁在切流）**完全相反**。

### 4.2 修法（**两层**防御）

1. **形态由路径状态判定**：`[[ -d "$path" ]]` ⇒ 一律走目录语义（残锁接管 / 拒绝）
   ⇒ 绝不碰 exec。
2. **exec 前一道守卫**：路径存在但**不是可写普通文件** ⇒ 干净地 rc=75 ⇒
   （在 bash ≥ 4.1 上，exec 重定向失败仍是致命的 ⇒ 这一层必须存在）

★ 变异臂 N2 / N2b 分别证明**两层各自都承重**（§8）。

## 5. F4（中）：★ 恢复命令与残锁判定给出**相反**的结论

★ 旧实现的两个函数：

| 函数 | 「持有者 pid 读不出来」时的结论 |
|---|---|
| `dl_switch_lock_is_stale` | **不算残锁**（保守：宁可拒绝也不误杀） |
| `dl_recover_switch_lock` | **直接清掉**（holder_pid 为空 ⇒ 不算「活着」⇒ 放行） |

⇒ ★★ 同一把锁、同一个时刻、两个函数**相反** ⇒ 且「清掉」的那个可能是**别人的活锁**
⇒ ★ 共享部署库 `lock_recover_local` 在同样情形下是**拒绝**
（`refusing to force-remove …: lock metadata is missing`）⇒ **两侧又是一次漂移**。

★ **修法（两档）**：
* **默认档（fail-closed）**：持有者**读不出来** ⇒ **拒绝**，并说清原因与出路；
  持有者**还活着** ⇒ 拒绝；持有者**已死** ⇒ 清掉。
* **强制档（`--force`）**：运维的**显式授权** ⇒ 无论元数据能否读出来都清掉，
  并把读到的元数据原样打印（读不到就明说读不到）。
  ★ 与共享部署库 `unlock-local.sh --force` **同构**；★ 差别：本仓**不杀进程**
  （杀掉别的用户的部署是更重的动作 ⇒ 属需要 owner 裁决的语义变更 ⇒ §9 只登记）。

★ **为什么必须有 `--force` 这一档**：若默认档一律 fail-closed 而**没有**任何
升级路径 ⇒ 「元数据坏掉的锁」就变成**永久卡死** ⇒ ★ **那正是上一轮 F2 修掉的
那个病** ⇒ ⇒ **fail-closed 必须配一条显式出路**，否则只是把「偶发互踩」换成
「必然卡死」的另一个版本。

★ CLI 接线：`recover-switch-lock --force` ⇒ 顶层参数解析 + **只允许与
`recover-switch-lock` 同用**（与别的动作同用 ⇒ 直接 exit 64 ⇒ 静默忽略一个
「强制」标记比报错危险得多）。

## 6. F5 / F6 / F7（中/低）：★ 元数据完整性 · unlink-after-unlock · 「no-op」的假注释

### 6.1 F5：半截元数据被当成存活证据

★ SIGKILL 打断的写入留下 `pid=999998`（真实持有者是另一个 pid）⇒ 旧实现把那个
**错误的** pid 当证据 ⇒ 它大概率不存在 ⇒ 判成残锁 ⇒ **接管掉一把可能还活着的锁**。
⇒ 修法：元数据必须**完整**（`pid` 行之后还要有 `started_at` 行 —— 写入顺序
target → source_user → source_host → pid → started_at → …）才配作存活证据。

### 6.2 F6：flock 释放后删锁文件

★ 旧实现：`关闭 fd` 之后 `rm -f "$path"` ⇒ 关闭与删除之间的窗口里，别的进程可能
刚好在**旧 inode** 上 flock 成功，随后第三个进程在**同名新文件**上再 flock 一次
⇒ **两个持有者** ⇒ 互斥失效。
⇒ 修法：flock 锁的正确释放就是**关 fd**（内核自动释放），文件留在原地即可
（下一次 acquire 会截断重写元数据）。

### 6.3 F7：「未持有时是 no-op」的注释是假的

★ 旧实现：mkdir 形态下 `dl_release_switch_lock` **无条件 `rm -rf` 锁路径**
⇒ 任何误调用都会**删掉别人的锁** ⇒ ⇒ 与注释相反 ⇒ **声名与实现不符**。
⇒ 修法：引入 `DL_SWITCH_LOCK_HELD` 明确持有关系（acquire 成功才置位）。

## 7. ★ 新增门：跨仓口径对拍（`tests/deploy_switch_lock_parity_test.sh`）

★ **动机**：F1 的来历说明「两份实现 ⇒ 必然漂移」⇒ ⇒ 必须有一道门**比对两侧**。

★ **判据**：
* **P1 存活判据逐 pid 对拍**：同一个 pid ⇒ 本仓 `dl_pid_alive` 与共享部署库
  `lock_pid_alive` 必须给出**同一个**答案，且都等于 **OS 的事实**（`ps -p` 看得见
  ⇒ 存在）。pid 矩阵覆盖：同用户的活进程 / **别的用户的活进程**（pid 1）/ 死 pid /
  pid 0 / 畸形 pid / 空串。
* **P2 元数据字段集对拍**：本仓注释声称「与共享部署库 lock.sh 同字段集」⇒
  那是一条**声名** ⇒ 这里把它变成可证伪的判据（实测两侧都是 7 个字段，一致）。

★ **刻意不对拍的部分（★ 政策差异，不是语义漂移）**：
本仓的 acquire 会对残锁**自动接管**（否则机器被永久卡死）；共享部署库的 acquire
一律快速失败。共享部署库 `unlock-local.sh --force` 会**杀掉**活着的持有者；
本仓的 `--force` 只清锁不杀进程。⇒ 这两条是**有意**不同，判据只钉
「持有者是否还活着」这一个**共同前提**。

★ **缺 SSOT 时怎么办**：共享部署库在仓外，CI runner 上可能没有 ⇒ 此时**明确留痕
SKIP** 并说明「本次没比对」，**不**输出 `ALL PASS` ⇒ 避免「假绿」。
