### 1.2 救命稻草：克隆库就是旧环境的完整快照

| 库 | OID | 大小 | 内容 |
|---|---|---|---|
| `itgate_sessfam_94339` | 382501 | 327 MB | **旧环境完整快照**：`api_keys=6` / `credentials=3` / `providers=47` / `provider_models=249` / `session_turns=1267` / `model_aliases=954` / `models_canonical=246` … **131 张非空表** |

⇒ ★ **教训**：真库回归脚本克隆源库时，**源库就是一份备份**；事故后它是唯一的恢复源。克隆脚本的命名习惯（`itgate_*`）与"用完即删"相冲突时，**先别删**。

### 1.3 恢复手法：同实例 `postgres_fdw` 跨库搬运（不是 dump/restore）

选它的理由（三个量具坑把 plain-dump 路线打穿了）：

| 坑 | 现象 | 结论 |
|---|---|---|
| **psql `\restrict` 安全模式** | PG 17.10 的 `pg_dump` 明文输出首行带 `\restrict <token>`；**在 dump 前插入任何 SQL** ⇒ token 失配 ⇒ psql 进入受限模式 ⇒ **COPY 数据行被当命令**（`backslash commands are restricted`）⇒ 数据行当 SQL 解析 ⇒ 大量假语法错 | dump 必须**原样**喂给 psql；任何前后拼接都会破 |
| **生成列** | `INSERT INTO pricing_plans (..., offer_scope_key, ...)` ⇒ `cannot insert a non-DEFAULT value into column "offer_scope_key"`（生成列） | 列交集时必须排除 `attgenerated <> ''` |
| **触发器在 COPY 时误触** | 复制 `session_dim` 时触发 `session_dim_project_attr_trg` → `public.sync_session_project_attr` → 内部又碰 `session_summaries` | 搬运会话要 `SET session_replication_role = replica`（**参数名是 `session_replication_role`，不是 `session_replica_role`**）⇒ 触发器/外键/RLS 一并关闭 |
| **主键冲突** | 活库有种子行（`providers=44` 种子）⇒ COPY 撞 PK ⇒ **整条 COPY 回滚** ⇒ 半恢复状态（最坏） | 先 `TRUNCATE ... CASCADE` 再搬 |

⇒ 最终形态（一次事务，零足迹到台账）：

```sql
CREATE EXTENSION IF NOT EXISTS postgres_fdw;
CREATE SERVER clone_srv FOREIGN DATA WRAPPER postgres_fdw
  OPTIONS (host 'localhost', port '5432', dbname 'itgate_sessfam_94339');
CREATE USER MAPPING FOR CURRENT_USER SERVER clone_srv
  OPTIONS (user 'llm_gateway', password :'pw');
IMPORT FOREIGN SCHEMA public LIMIT TO (<120 张表>) FROM SERVER clone_srv INTO foreign_clone;
SET session_replication_role = replica;
TRUNCATE TABLE <120 张表> CASCADE;
-- 逐表：列交集（排除生成列/identity 列）⇒ INSERT INTO public.t (…) SELECT … FROM foreign_clone.t
RESET session_replica_role;
DROP SCHEMA foreign_clone CASCADE; DROP SERVER clone_srv CASCADE;
```

- **排除两本台账**：`gateway_db_revision_sequences` 与 `schema_migrations` 不搬（活库的台账才是当前链的真相：含 890/891/893）。
- 逐表容错：单表失败记 `restore_failures` 不中断整体 ⇒ 最终**0 失败表**。
- **读数**：120/120 表行数与克隆库**逐表一致**，合计 **1,008,708 行**；v1 族关系数恢复后仍为 **0**（台账 890 在位、族确已 DROP）。

### 1.4 用户的网关 key：不是"新建"，是"回到原 id"

- 克隆库 `api_keys.id=2`（`key_prefix='local-test'`, `key_alias='retirement-local-test'`, app=13）**就是用户的 key**（`key_hash` = `HMAC-SHA256(SECRET_KEY, 明文)` 的值相同 ⇒ 同一把 key）。

  ⇒ **修法**：把行号**改回 id=2** 并对齐原属性 ⇒ 快照与活表重新一致 ⇒ 预算检查通过。

## 2. 事故二：890 之后仍有三处运行时引用 v1（本轮真正的产品缺陷）

**共同形状**：890 把 v1 族（表 + 分区 + 索引 + promote 函数）整体 DROP 后，**运行时路径**里仍有引用。表名扫描（`sql_source_indirection_audit`）抓不到它们，因为它们是**字符串常量里的 SQL**，而退役改动只改了"数据面"（读源切换），没覆盖"运维面/后台面"。

### 2.1 缺陷①：`rollupCredentialModelIndexSQL` 会话腿投影无别名 ⇒ autoroute 指标停更

- **位置**：`bg/auto_index_refresher.go`（`rollupCredentialModelIndexSQL`）。
- **机制**：890 删掉 half-1 的 v1 腿、换成会话腿；会话腿内层是 8 个**表达式**，而外层沿用 v1 腿的**列名**引用它们：
  `rl.credential_id` / `rl.model_key` / `rl.mo_canonical_id` / `rl.mo_billing_mode` / `rl.mo_price_in` / `rl.mo_price_out` / `rl.success` / `rl.latency_ms`。
  表达式无别名 ⇒ PG 列名 `?column?` ⇒ 外层 **42703 `column rl.credential_id does not exist`** ⇒ **整条 rollup 失败** ⇒ `credential_model_index` 停更 ⇒ autoroute 候选池退化。
- **活库证据**：`rollup credential_model_index: insert: ERROR: column rl.credential_id does not exist (SQLSTATE 42703)`，**每 5s 一条**（旧构建 8772 上；修复后的构建 0 条）。
- **修法**：给 8 个投影各补一个别名（形状与 v1 腿的列名逐字对齐）。
- **为什么既有门没抓住**：`bg/auto_index_refresher_s3_wave3_test.go` 是**纯文本形状门**（数 `FROM session_turns_hot t` 出现次数、查 `FROM _request_logs_hot` 是否消失、查 alias 链子串）⇒ **完全不涉及列解析** ⇒ 少一个别名照样绿。
- **补门**：
  - `bg/auto_index_refresher_rollup_realdb_test.go`（新）：**真库执行**整条语句（显式事务 + ROLLBACK，零足迹）⇒ 任何列解析错/关系不存在/语法错直接变红。
  - `bg/auto_index_refresher_rollup_alias_gate_test.go`（新）：**静态别名闭包门** —— 会话腿投影每项必须带别名，且外层引用到的每个 `rl.<col>` 都必须被产出。判据前**先剥注释**（本文件新注释里就写着 `rl.credential_id`，不剥会把注释当引用）。
- **变异验证**：去掉 `AS credential_id` ⇒ 静态门红（「投影项没有别名」）+ 真库门红（42703）⇒ **两道门都有牙**；文件 sha256 逐字还原。

### 2.2 缺陷②：`columnsAllPresent` 注释与实现相反，848 的安全压在它上面

- **位置**：`db/db.go`（helper）+ `ensureBillingUnitAndAudioSeconds`（迁移 848 的 boot ensure）。
- **机制**：helper 的注释写「表不存在 / 任一列缺失 / 探测出错 → **false**（走原 ensure 路径）」；**实现**是把 `to_regclass(...) IS NOT NULL` 写在 `WHERE` 里 ⇒ 表不存在时该列无行 ⇒ `missing=0` ⇒ 返回 **true**。
  ⇒ 真实语义是「表不存在 ⇒ true（没有缺列）」。
- **为什么这条要紧**：848 的短路条件 `hotOK = columnsAllPresent(ctx, "_request_logs_hot", ["audio_seconds"])`。
  退役后 `_request_logs_hot` 不存在 ⇒ 按**实现** ⇒ `hotOK=true` ⇒ 短路触发 ⇒ 恰好不炸；按**注释** ⇒ `hotOK=false` ⇒ 每次 boot 都 `ALTER TABLE` 一张已 DROP 的表 ⇒ **42P01 ⇒ 网关起不来**。
  ⇒ **安全是"巧合式"的**：它挂在一条**注释与实现相反**的 helper 语义上。
- **修法**：
  ① 848 自己加**显式存在性闸**（`to_regclass` 探族在不在）+ v1 DDL 只在族在位时拼进语句 ⇒ 承重语义从「helper 的空真」挪到「848 自己判断」；
  ② 把 helper 的注释**订正成实现事实**，并写明「这条语义曾是 848 的承重前提，现已由 848 的显式闸接管」。
- **补门**：`db/db_848_v1_family_guard_test.go`（新）：钉住显式闸存在、闸在 DDL 之前、v1 DDL 形状未被删改。

### 2.3 缺陷③：data-lifecycle 自动 hot cron 每轮 42883

- **位置**：`admin/data_lifecycle_hot_partition.go`（`hotPromoteTableMap`）+ `admin/data_lifecycle_cron.go`（`runOnce`）。
- **机制**：890 把 v1 族与它的 promote 函数（`promote_request_logs_hot_to_partition` / `promote_request_logs_bodies_hot_to_partition`）**一起 DROP**；而 `hotPromoteTableMap` 仍列着这两项 ⇒ 自动 hot cron 每轮去调 ⇒ **42883**。
  ⇒ 被调用的表**根本不存在**、没有任何东西可搬 ⇒ **纯噪声**（每轮 2 WARN + 1 ERROR），且 ERROR 会淹没真实故障。
- **特别注意**：`promoteHotRetiredReason` 的注释声称「the automatic lifecycle job is gated the same way」——**其实没有**：手动 promote 路径查了它，**cron 路径没查** ⇒ 注释与实现不一致（与缺陷②同型）。
- **修法**：
  ① 清单里摘掉两条 v1 死引用（退役语义仍由 `retiredV1HotTables` + `promoteHotRetiredReason` 承载，手动 promote 仍按原口径拒绝并给理由）；
  ② cron 加**能力探针**：promote 函数不存在 ⇒ 记一条 **INFO 的 SKIP**（不是 ERROR）⇒ 今后任何被 DROP 的函数都不会再刷错误日志。
- **补门**：`admin/data_lifecycle_v1_retirement_test.go`（新）：退役族不得出现在 promote 清单；清单函数名不得以 `promote_request_logs_` 开头；在位族一个都不能少（防"清空整张清单"那种变异）；cron 必须有 `pg_proc` 能力探针且探针早于调用。
