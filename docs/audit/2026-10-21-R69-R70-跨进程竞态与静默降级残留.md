## 2. R69（真缺陷）：rollup 跨进程互删 ⇒ 新模型/新凭据在候选池里消失 8 小时

### 2.1 现象与读数

| 项 | 观察值 | 含义 |
|---|---|---|
| `pg_stat_user_tables` on `credential_model_index_hot` | `n_tup_ins=1036` / `n_tup_del=968` / **`n_live_tup=0`** | 写进去又被删掉 |
| 8781 实例日志 | `auto index refreshed credential_rows=75`（每 5 分钟） | 确实写进去了 |
| 8782 容器日志（当时） | 每 5 秒一条 `42703 column rl.credential_id does not exist` | 旧构建的 rollup 在失败 |
| `credential_model_index_hot` 实际行数 | **0** | 被别的进程删了 |

### 2.2 机制（逐步）

rollup 是 **DELETE + INSERT 两条语句**（`bg/auto_index_refresher.go`）：

```
实例 A（新构建，rollup 正确）： INSERT 75 行（bucket=B） → 提交
实例 B（旧构建，rollup 42703）： DELETE bucket=B 成功 → INSERT 42703 失败
⇒ hot 表被「删掉且没补回」
```

**为什么这不只是「指标陈旧」**：autoroute 候选池读的是视图
`credential_model_index_with_current_month`（hot ∪ 月分区）。
新出现的 `(credential_id, raw_model)` 组合在月分区里要等 **8 小时**排水窗口才可见 ⇒
在此之前该组合在候选池里**根本不存在** ⇒ 路由层 `model_not_found` / `no_candidate`
⇒ **该模型 100% 流量失败**。

### 2.3 根因（两个独立缺陷叠加）

1. **非原子**：两条语句各走一次 `r.db.Exec`（= 两个隐式事务）⇒ 中间态对读者可见；
2. **进程内互斥只覆盖本进程**：`tryBeginRefresh` / singleflight 拦的是**本进程**的三个触发源
   （5 分钟 ticker / LISTEN 监听 / admin 手动接口），**跨进程完全无效**。

### 2.4 为什么这不是「本地特例」

仓库自己就有蓝绿部署（`scripts/deploy-seamless-docker.sh`：**候选槽 → 验收 → 切 nginx upstream → 停旧槽**）⇒
**部署窗口内两个实例同时对着同一个 PG** ⇒ 这不是本地特例，是部署形态自带的风险面。

### 2.5 修法

```go
// bg/auto_index_refresher.go
tx, _ := r.db.Begin(ctx)                      // ① 两条语句同事务
tx.Exec(ctx, `SELECT pg_advisory_xact_lock(hashtextextended($1, 0))`,
        credentialModelIndexRollupLockKey)   // ② 先取跨进程锁
tx.Exec(ctx, deleteSQL, bucket)              // ③ DELETE
tx.Exec(ctx, insertSQL, bucket)              // ④ INSERT
tx.Commit(ctx)                               // ⑤ 原子提交
```

- 键的取法沿用仓内既有约定（`settings/session_write_safety.go`：`hashtextextended('<literal>', 0)`）；
- **同库所有实例在同一把锁上排队** ⇒ 蓝绿窗口也不再互删；
- **顺带消掉一个坑**：INSERT 失败时 DELETE 随事务回滚 ⇒ 不再留下「删掉了却没补回」。

### 2.6 诚实边界（必须写下来）

- advisory lock **只对同样会取锁的构建有效**。旧构建（未修 42703 的那个）不会取锁，
  它照样能删掉我们的行 ⇒ **要彻底消除，仍需把对方升级到含修复的构建**。
  本地的事实：并行会话在 23:47 把 8782 重建到含别名修复的 2785 后，
  **hot 表立刻恢复稳定**（连续 5 次采样：77 行 / bucket 23:45 不变），42703 归零。

### 2.7 新门（`bg/auto_index_refresher_rollup_atomic_test.go`）

| 门 | 形态 | 钉住什么 |
|---|---|---|
| 门 A | **AST 形状门**（离线） | DELETE/INSERT 必须在**同一事务**上；必须**先取锁**再取行锁；必须有 Commit；**不得有裸 `r.db.Exec`** |
| 门 B | **真库阻塞门** | 另一个会话持有同一把 advisory lock 时，产品代码的 rollup **必须被挡住**；锁释放后必须成功完成 |

> ⚠ 门 A 第一版是**恒绿门**：它只认 `*ast.ExprStmt`，
> 而 `if _, err := tx.Exec(...); err != nil {}` 里那次调用挂在 **IfStmt 的 Init**（AssignStmt）上
> ⇒ 扫描器**看不见**它 ⇒ 门红但红因是「扫描器没看见那行」而不是「代码没取锁」。
> ⇒ 改成遍历**所有 CallExpr**，不再按语句类型分流。

### 2.8 变异验证（真应用 + sha256 逐字还原）

| 变异 | 门 A | 门 B | 还原 |
|---|---|---|---|
| M1 删掉 advisory lock | 红（没有 pg_advisory_xact_lock） | 红（rollup 没有等锁，立即返回） | ✔ sha 逐字一致 |
| M2 DELETE 改回 `r.db.Exec` | 红（存在不在这条事务上的写，接收者 `r.db`） | —（该腿不覆盖原子性） | ✔ sha 逐字一致 |

## 3. R70（四处「静默降级」残留）：页面上看不出报错

### 3.1 新量具：把 2s 慢查询日志打开，读 PG 错误日志

本地 PG 的 `pg_stat_statements` **装了但没进 preload**（与 §143.20 在 211 上的发现同源）⇒
慢查询量具不可用 ⇒ 改走 **PG 错误日志**通道：

```sql
ALTER DATABASE llm_gateway SET log_min_duration_statement = 2000;  -- 只影响新连接
```

（`log_destination=stderr` + `logging_collector=off` ⇒ PG 日志直接进 `docker logs llm-gateway-pg`。
测完 `ALTER DATABASE llm_gateway RESET log_min_duration_statement;` 复原。）

**这条量具一开就看见 4 组此前没被发现的报错**（此前所有验证都是「接口返回 200 就当没事」）：

### 3.2 缺陷 1：任务分析详情页两个面板恒空（42703）

```
ERROR: column sd.session_id does not exist at character 185
STATEMENT: SELECT DATE(ss.first_request_at) … FROM session_summaries ss
           INNER JOIN session_dim sd ON ss.session_key = sd.session_id AND ss.tenant_id = sd.tenant_id
```

- `session_dim` 的真实列是 **`gw_session_id`**（另有 `session_key`），**没有 `session_id`**；
- 同一包里另有 **7 处** JOIN 用的是正确写法（`sd.gw_session_id = ss.session_key`）⇒ 这两处是漏改；
- 代码用 `if err == nil { ... }` **把错误吞掉** ⇒ 面板静默变空 ⇒
  **页面上分不清「本来没数据」和「SQL 坏了」**。

修法：列名改 `gw_session_id`；并把被吞掉的错误记成 WARN（降级可接受，降级原因必须留痕）。

### 3.3 缺陷 2：标签列表接口恒空（42601 + 42804）

```
ERROR: syntax error at or near "[" at character 349
       … ARRAY_AGG(canonical_name ORDER BY canonical_name)[1:5] AS samples
```

- PG 不允许直接给聚合表达式下标 ⇒ 正确写法是 `(ARRAY_AGG(...))[1:5]`
  （仓内 `bg/integrity_fingerprint_drift.go` 与 `catalog/vendor_sweep_test.go` 都是这个形态）；
- 同一段 SQL 还有第二处错：
  `COALESCE(mc.tags,'[]'::jsonb)` —— 而 `models_canonical.tags` 的真实类型是
  **`text[]`**（`sql/objects/tables/models_canonical.sql: tags text[] DEFAULT '{}'::text[] NOT NULL`）
  ⇒ `ERROR: COALESCE types text[] and jsonb cannot be matched (42804)`；
- 两处错都被 `if err != nil { writeJSON(200, 空列表) }` 吞掉 ⇒ 接口 200 + 空列表。

### 3.4 缺陷 3：已退役的表每次查询都 42P01（42P01）

```
WARN data_lifecycle_partitions: failed to get status  table=_request_logs
     error="failed to get table stats: ERROR: relation \"_request_logs\" does not exist (SQLSTATE 42P01)"
```

迁移 890 已把 `_request_logs` 族物理删除，但 `admin/data_lifecycle_partition.go` 的
`partitionedTables` 清单（admin UI 的手动清理列表）**仍留着它** ⇒
每次 `/api/admin/data-lifecycle/partitions` 都刷一条 WARN，且该表状态永远拿不到。

修法：**先探表在不在**（`to_regclass`），不在 ⇒ 返回「已退役」状态（新增 `retired` 字段，JSON 加字段是加法式变更）
⇒ **不再查它**。
**清单条目保留**（既有端点契约：UI 仍列出该表名；手动 archive 端点对无 archive 函数的表回 400，
那个路径不碰数据库因此不产生 42P01）。

### 3.5 缺陷 4：系统监控「近 1 小时」四个计数恒为 0（42703）

```
ERROR: column "total_tokens" does not exist at character 198
       SELECT COUNT(*) FILTER (WHERE status='success'), …, COALESCE(SUM(total_tokens), 0)
       FROM system_probe_runs WHERE created_at >= NOW() - INTERVAL '1 hour'
```

- `system_probe_runs` **没有任何 token 列**（真库实测的列：id / task_id / task_type / automaticity /
  credential_id / provider_id / raw_model / source / worker_id / status / attempt / max_attempts /
  http_status / latency_ms / dns_ms / tls_ms / request_url / request_body_preview /
  response_body_preview / err_code / err_detail / skip_reason / recent_request_id / created_at …）⇒ 42703；
- 错误被 `_ =` **整个丢掉** ⇒ 四个计数**全部停在 0** ⇒「近 1 小时完成/失败/跳过/Token」恒为 0。

修法：去掉那个聚合；错误不再丢弃（记 WARN）；响应键 `total_tokens_1h` **保留**
（`web-mobile` 的 `SystemMonitorStats` 类型与 `SystemMonitorView` 都在读它）⇒ 值恒 0，
并在代码里注明原因（探针运行表只记状态与时延，不记 token；另接计量表是另一个口径问题，不擅自改语义）。

### 3.6 新门（`admin/session_family_runtime_sql_test.go`）

| 门 | 形态 | 钉住什么 |
|---|---|---|
| 真库执行门 | 真库跑 4 段 SQL（只读 ⇒ 零足迹） | 列名错 / 语法错 / 类型错一律打红 |
| 端到端门 | 对**已退役**的表调产品代码的 `getPartitionTableStatus` | 必须不报错且 `Retired=true`；对**在位**的表必须 `Retired=false`（防止「一律标退役」这种偷懒修法） |

> ⚠ 静态守卫自己踩了三个坑（都已写进门注释）：
> 1. **假阳性 1**：第一版用「session_dim 之后 400 字符内出现 `.session_id`」判 ⇒
>    误判了 `admin/session_turns_v2.go:766` 与 `admin/turns_sessions.go:167`
>    （那两处的正确写法是 `sd.gw_session_id = s.session_id`，窗口跨到了下一张表的合法列上）
>    ⇒ 改成**别名感知**：先从 `session_dim <别名>` 取别名，再只找 `<别名>.session_id`。
> 2. **假阳性 2**：第一版 ARRAY_AGG 守卫只看「ARRAY_AGG 前面有没有左括号」⇒
>    把 `ARRAY_AGG(ma.raw_name ORDER BY ma.raw_name) AS aliases` 这种**根本没有下标**的写法也判红
>    ⇒ 改成先配平括号找到聚合表达式的收尾，再看它后面是不是跟着 `[`。
> 3. **必须剥注释**：断言 SQL 文本前要剥 Go 注释，否则注释里的说明文字被当成代码判红
>    （第一版假红过一处自己的注释）⇒ 复用仓内既有的 `stripGoComments`（**不重复实现**）。

## 5. 阴性结论（都带证据，不靠推断）

| 命题 | 结论 | 证据 |
|---|---|---|
| 模型第 7–8 轮退化是代码缺陷 | **否** | 上游 429 rpm exhausted + 熔断；复测 8/8 绿；并行会话同期 3 分钟 953 请求 |

| 8782 仍在每 5 秒报 42703 | **否**（已随并行会话的重建消失） | 容器日志 42703 = 0；`auto index refreshed` 正常 |
