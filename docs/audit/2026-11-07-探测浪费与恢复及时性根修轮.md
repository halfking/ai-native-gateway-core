## 2. 根因（四个叠加机制）

**G1 · 恢复 SLA 封顶把退避削平（probe_recovery_policy.go）**
`probe.recovery_max_backoff_seconds`（默认 300s，2026-11-05 引入）把网络/5xx/429 族的
长尾削到恒 5 分钟——spec 的 DescriptionLong 自己登记了这笔账（持续故障对 1次/6h→1次/5m＝72×；
recoveringSweeper 5m ⇒ 最坏 2,880/day/对）。设计假设「失败迟早会成功或凭据被停」，对
**持续失败**（cf≈1000）没有出口 ⇒ 每 ~5 分钟盲探一次、永不停止。

**G2 · 恢复循环绕过梯子（credential_recovery.go expiredCmbRecoverySQL）**
绑定冷却（unavailableBindingHorizon 恒 5min）到期后，到期绑定复检分支每 30s tick 重新
Submit——**不看 node_probe_state.next_retry_at**（兄弟分支 freshDegradedCmbSQL 有该守卫，
它没有；2026-07-24 有意移除，理由是当时梯子会沉 1h–24h 造成搁浅）。每次 Submit 开一代
全新队列任务（attempt=1）→ 7 次梯内重试（5s/15s/30s/60s/5m×3）→ 任务终态 → 5min 后再开
新一代 ⇒ 稳态 ~7 探/22min ≈ **480 次/天/对**（与 1.1 实测逐字吻合）。

**G3 · 用尽窗口内非配额形态失败不钉（quotaResetAlignedBackoff 只认配额体）**
F4 钉只认「402/403/429 + 配额体」。凭据 35（periodic_exhausted）在窗口内以
503 Service Unavailable 形态失败 ⇒ 不钉 ⇒ 每 ~70s 盲探（availability 反复翻转 +
`probeSubmitterImmediate`/rearm 每次翻转全量触发，health_status_reset 这类**家务翻转**
也在 F5 补全线里被当恢复事件回拉）。

**G4 · write-through 无新鲜度守卫（R4 竞态）**
探测成功恢复绑定（healthyBindingSQL 无条件恢复）与业务拉黑竞态：
- 拉黑落在 (探测完成, 记账) 窗口内 → 无条件恢复**覆盖更新的失败证据**；
- mirror 的 `last_attempt_at = now()`（记账时刻）> 证据时刻 → R4 审计把「合法更新的拉黑」
  误判为 write-through 缺口，且真缺口（恢复写丢失）最长活到小时审计 `--fix`。

## 3. 修复（8 项，全部「证据定节奏、事件管及时」哲学，与 F4/F5 同构）

| # | 落点 | 内容 |
|---|---|---|
| W1 | bg/probe_recovery_policy.go | **持续失败升级**：attempt（跨代＝cf+1）≥ `probe.sustained_failure_attempt_threshold`（默认 21＝三代完整梯零成功）且梯级本会被 SLA 削平时，升到 `probe.sustained_failure_recheck_seconds`（默认 1h，下限＝恢复 SLA）。networkProbeBackoff 与 rate/concurrent 两处 cap 位点同走 `capRecoverBackoffForAttempt`。阈值以下行为与 2026-11-05 口径逐字一致。 |
| W2 | bg/node_probe.go unavailableBindingHorizon | 绑定冷却与梯子同档升级（attempt≥阈值 ⇒ 冷却=sustained 档；404/协议族保持自有 6h 档）。 |
| W3 | bg/credential_recovery.go expiredCmbRecoverySQL | **梯子守卫**：`(nps.paused = TRUE OR nps.next_retry_at > now())` NOT EXISTS——与 freshDegradedCmbSQL 对齐。**有意反转 2026-07-24 的「无视梯子」**：搁浅的两条腿（梯子无界→现有界；无事件回拉→F5 已有）都已消除，而「无视梯子」的浪费已实测。 |
| W4 | bg/node_probe.go clampRecoverableProbeSchedulesSQL | `COALESCE(consecutive_failures,0) < $3`（阈值参数）——clamp 不得把升级裁决拉回 5 分钟。 |
| W5 | bg/probe_recovery_policy.go quotaResetAlignedBackoff | **配额窗口钉第二臂**：凭据行自身 `quota_state ∈ 用尽族 + quota_recover_at 未来` ⇒ 钉 recover_at+60s（失败形态无关；211 凭据 35 形态）。臂 1（配额体判定）原样保留；查询改 `SELECT quota_state, quota_recover_at`。typed-nil pool 显式拦（臂 2 让每次失败都查 ⇒ nil pool 会 SIGSEGV）。 |
| W6 | bg/credential_recovery.go dispatchRecoveryHooks + bg/node_probe.go rearm | **回拉分级**：`rearmEligibleRecoveryKind`——家务类翻转（health_status_reset / consecutive_failures_clear）不触发 rearm（不是恢复证据，且 health_status_reset 每 ~2min 一次会把全部失败行反复拉回 now()）；真恢复类（quota/availability/stale/circuit/mnf）保留。rearm SQL 加**用尽窗口守卫**：`quota_state ∈ 用尽族 + quota_recover_at 未来` 时不回拉（重置点由 quota_periodic_recover 翻 ok 后统一回拉；提前充值由凭据级探测成功→翻 ok→onQuotaRecovered 回拉，两条路都已出窗口）。 |
| W7 | bg/node_probe_write_through.go healthyBindingSQL | **新鲜度守卫**：只恢复 `unavailable_at <= 证据时刻` 的行（$3 参数）——更新的失败证据存活。`updateBindingAvailability` 增加 `evidenceAt`（成功分支用直连轮完成时刻；ProbeSync/runOne/applyOutcome 三条路径贯通；业务成功 syncHealthyNodeSurfaces 用 now）。 |
| W8 | bg/probe_service.go mirrorNodeProbeState + runOne 成功簿记 | 成功镜写 `last_attempt_at = 证据时刻`（$4/$directDone）而非记账 now()——R4 审计的时序判据度量「拉黑 vs 证据」，(证据, 记账) 窗口内的合法拉黑不再误判。 |

**settings spec 登记**（spec_probe.go，两键均热更新）：
- `probe.sustained_failure_attempt_threshold`（默认 21，7..1000）
- `probe.sustained_failure_recheck_seconds`（默认 3600，300..86400；调到 300＝等效关闭升级）

**恢复及时性论证（升级不降级感知）**：持续失败对的恢复发现路径＝
① 梯子复检（≤1h 盲探兜底）；② **事件回拉**（quota/availability/stale/circuit 翻转 →
RearmCredentialFailures → 泵 30s 接管）——最常见的恢复形态（配额重置/冷却结束）都走这条路；
③ 业务成功（MarkNodeProbeHealthy 立即停放+恢复绑定）。新失败（阈值以下）仍 5 分钟内复检。
W5+W6 合起来＝F4「用尽期 0 探测」对非配额形态失败与事件面的补全：窗口内零盲探、
重置点后 30s 内全量复检。
