## §2 三处自我推翻的证据

### §2.1 推翻①：ensure 函数一直都在

§19.7.2 的根因写的是「这 11 个函数的来源迁移（319/330/334/335/382/383/305/328a/430/043/473）
在 installer 链里全部未登记 ⇒ 新装库既没有函数、也没有分区」。

★ **后半句是错的**（逐个核对 baseline）：

```
ensure_request_logs_partition              ✓ 在 baseline
ensure_request_logs_bodies_partition       ✓ 在 baseline
ensure_request_wal_partition               ✓ 在 baseline
ensure_routing_decision_log_partition      ✓ 在 baseline
ensure_credential_model_index_partition    ✓ 在 baseline
ensure_usage_ledger_partition              ✓ 在 baseline
ensure_credit_ledger_partition             ✓ 在 baseline
ensure_tool_usage_stats_partition          ✓ 在 baseline
ensure_dashboard_events_partition          ✓ 在 baseline
ensure_session_module_executions_partition ✓ 在 baseline
ensure_sessions_v2_partitions              ✓ 在 baseline        ⇒ 11/11
```

⇒ **函数有，缺的是分区这个产物**（baseline 只建了 2026_07/2026_08）。
⇒ ⇒ 迁移 893 **不负责建任何函数**（建了就是与 baseline 的既有版本抢名字、参数名/返回类型都不同的死代码）。
⇒ ⇒ 顺带解开了「那 5 个旧文件为什么不登记」：它们**不是函数来源**，是「顺带补分区/补表」的迁移
⇒ 直接登记会撞既有对象（实测 `cannot change return type` / `credit_ledger_old already exists`）。

### §2.2 推翻②：**分区在 + 函数在，仍然可能是坏的**

893 第一版用 `p_parent || '_' || YYYY_MM` 拼子分区名。★ **这对两个族是错的**：
`_request_logs` / `_request_logs_bodies` 的子分区真名是 `request_logs_YYYY_MM` /
`request_logs_bodies_YYYY_MM`（**没有下划线**）—— S4 把父表改名成 `_request_logs` 时子分区沿用旧名，
**baseline 与生产 252 都是这个约定**。

实测后果（**执行出来的，不是推理**）：

```
ERROR:  partition "request_logs_2026_10" would overlap partition "_request_logs_2026_10"
SQLSTATE 42P17
```

⇒ baseline 自带的 `ensure_request_logs_partition` **每次都判「不存在」→ 重建 → 边界重叠报错**
⇒ ⇒ **该族永远无法自愈**（运行期每 24h 只 `slog.Error` 一次，不中断、不自愈）。

⇒ ⇒ ★★★ **本轮最值钱的一课**：
**「分区在」是形状断言，「函数造出来的名字对不对」是行为断言** ⇒ 只查存在性的门看不见
⇒ ⇒ ★ **只有真的调用那个函数才看得见**。

⇒ **修法**（已落地）：
① 子分区**前缀按族内既有兄弟的「众数命名」推导**（新助手 `llm_gateway_monthly_family_prefix`）；
② **幂等判定按「边界覆盖」**（`FROM <= 目标月 < TO`）而不是按名字；
③ **default 兜底按「该族有没有 default 子分区」判定**（PG 不允许同父两个 default）
   ⇒ 不再靠 `EXCEPTION WHEN OTHERS THEN NULL` 吞冲突（那会**静默**）。

⇒ 修完后逐个调用 11 个函数 ⇒ **11/11 零报错**（第一版是 9 OK / 2 ERR）。

### §2.3 推翻③：D5 的前提被证伪 ⇒ **真缺口集 = ∅**

R62 轮问卷超时自动采纳了推荐项「D5 = 补 ALTER 迁移并登记（补那 20 列）」。
★ **执行前的前置核对把它推翻了** —— 拿**生产 252** 把 20 列逐条核对：

| 生产侧 | 列数 | 结论 |
|---|---:|---|
| **生产也没有** | **16** | 「没人跑过的死 DDL」（对应迁移的 `CREATE TABLE` 形状在「表已存在」上整段静默空操作 ⇒ 那段 DDL 从未真正生效过）⇒ **产品走不到那条路径** ⇒ **按名命中必然是假阳性** |
| **生产有** | **4** | `prompt_injection_detections.{detection_layers,detection_score,matched_rules,matched_rules_count}` ⇒ 不是死 DDL；但产品读写**不依赖这些物理列**（写路径是正典形状 `risk_level/rule_name/category`；读路径是派生别名 `risk_level AS detection_score` 等）⇒ 仍是 benign |

⇒ ⇒ ★★★ **没有一列需要补 ALTER** ⇒ **D5 不执行**。
⇒ ⇒ 登记册里 **11 行原本被判 high/medium**
（`diagnostic_runs.audit_log_id`、`goal_run_actions.tenant_id`、`goal_run_steps.tenant_id`、
`goal_runs.fencing_token`、`goal_runs.goal_run_id`、`request_stage_events.trace_id`、
`usage_ledger.{cost_currency,department,employee,id,position}`）⇒ **全部降级 benign**
⇒ 若照原采纳项执行，就会补出 **11 个「没人依赖、连生产都没有」的列**。

⇒ ⇒ ★★ **新立的第一道闸门**（写进登记册头）：
**severity 的第一道闸门 = 「生产侧有没有这一列」** ——
★ **一个列在生产里都不存在，产品就不可能真的依赖它** ⇒ 按名命中必然是假阳性。
⇒ ⇒ ★★ 于是**判缺口必须三侧对照**：**生产有 ∧ 新装没有 ∧ 产品依赖**。

⇒ ⇒ ★ 三类假阳性（每一类都是「量具口径」问题，不是产品缺陷）：

| 类 | 口径 | 症状 | 修法 |
|---|---|---|---|
| ① R60 | 量在「装完但 ensure 链没跑」 | 把 20 个 **ensure 自愈**的列算成缺口 | oracle 换成「装完 **且启动过**」 |

| ③ 若只按「生产 vs 新装」判 | — | 把**生产多留的历史列**（实测 26 列）算成缺口 | 三侧对照 |

## §3 迁移 893 的设计

### §3.1 做什么

| 件 | 说明 |
|---|---|
| `llm_gateway_monthly_family_prefix(p_parent text)` | 该族子分区的**前缀**（按既有兄弟的**众数命名**推导） |
| `llm_gateway_ensure_monthly_partition(p_parent text, p_month date)` | 按「库里已有最新月分区」的**边界约定**建出目标月分区；幂等按**边界覆盖**判定 |
| §② 发现式补分区 | 给所有「有月分区」的 RANGE 族补**当月 + 次月**；时区 `Asia/Shanghai`（与 `bg/partition_manager.go` 的 `partitionTZ` 同源） |
| §② default 兜底 | 该族**一个 default 子分区都没有**时才建（rule 33 §2：DEFAULT 是仓库规范要求的兜底，不是可选项） |

### §3.2 **不**做什么（都是实测结论，不是偏好）

① **不建任何 ensure 函数** —— 11/11 都在 baseline（§2.1）；
② **不覆盖生产既有函数** —— 只在「不存在时」创建；
③ **不用 `parent_YYYY_MM` 拼子分区名**（§2.2）；
④ **不写 `BEGIN/COMMIT`** —— 调用方 `--single-transaction` 下会早提交、破坏回滚。

### §3.3 为什么不能直接登记旧文件（实测硬伤）

| 文件 | 实测结果 |
|---|---|
| `473_partition_precreate_2026_09_10.sql` | 新装库上直接失败：`relation "public.request_logs" does not exist`（引用 S4 退役改名前的表名）；且它是 **dated** 的（只到 2026_10）⇒ 2026-11 起又缺 |
| `330` / `334` / `335` | `cannot change return type of existing function` / `credit_ledger_old already exists` |
| `328a` | `request_logs parent not found`（同上，改名前） |

⇒ ⇒ 正解是**新的、幂等的、认得现表名与现命名约定**的迁移。

## §7 ⚠ 诚实边界与本轮**没有**做的事

1. ⚠ **生产 252 上 4 个族没有 default 分区**（`credential_model_index` / `request_wal` /
   `routing_decision_log` / `usage_ledger`；另 4 族有）⇒ 新装库与生产在这 4 族上形态不一致
   ⇒ 补生产那 4 个属**生产写入**，需属主另行拍板 ⇒ **本轮未动**。
2. ⚠ **D5 未执行**：因前提被证伪（真缺口 = ∅）。若属主希望那 20 列进新装库，
   需要一个**产品侧理由**（当前产品读写都不依赖，生产也没有），而不是「登记册说有」。
3. ⚠ **生产侧默认关**：`settings.RequestLogsWriteEnabled()` 默认 `false`
   ⇒ `v1LifecycleRetired()` 为真 ⇒ `_request_logs` / `_request_logs_bodies` 的两个 ensure
   **不在 24h 轮转里** ⇒ §2.2 那个命名缺陷在生产上**不会发作**（潜伏缺陷），
   但**一旦有人打开 request-logs 写入就会发作** ⇒ 新装库这条已被 893 修掉。
4. ⚠ **门的覆盖面**：只验「有月分区的族」；**按日分区**的族（`usage_facts` /
   `ursm_node_snapshot_min`）不在本门范围内（`ursm_node_snapshot_min` 的来源迁移 830 是
   **手工迁移、刻意不进 installer 链** ⇒ 该函数在 830 执行前一直不存在）。
5. ⚠ **未部署生产**：893 只影响**全新安装**的形态，已装好的库不需要跑它
   ⇒ 生产 154 / 245 **未重启、未变更**。
6. ⚠ **一次性库探针读的是 embeddata 副本**（`installer/cmd/llm-gw-installer/embeddata/startup/`）
   ⇒ 改 canonical 后若忘同步副本，**测的还是旧的**（本轮踩过一次：改完读数完全没变）。
