## §2 ★★★ D18 收口：覆盖判定口径（★ 本轮主体）

### §2.1 起点：167 条 `undetermined` 到底是什么

★ 精确拆解（★ 不是「路由名没解析出来」这么简单）：

| 类别 | 条数 | 说明 |
|---|---|---|
| handler 名为空（闭包字面量） | 19 | 路由注册处写的是 `func(...)` 字面量 |
| 全仓定义**唯一**（跨包可解） | 56 | ★ 定义体在**别的包** ⇒ 旧口径只在注册目录里找 ⇒ 找不到 |
| 同名**多义** | 35 | `ServeHTTP`×36 / `Pool`×7 ⇒ 消歧失败 |
| 全仓**零定义** | 57 | `wrappedSession` / `legacy` / `staticHandler` ⇒ ★ **根本不是具名函数** |

⇒ ★★ **全部 167 条都是「消歧失败」（`deffile` 为空）**
⇒ ★★ ⇒ **加跑 coverprofile 单独解决不了** ⇒ ★ 必须「**多包 profile** + **跨包查找**」两件事一起做。

### §2.2 ★★ 真缺陷 A：「各包各跑再合并」漏判跨包执行（★ 会制造**假缺口**）

★ 机理：★ 一个 handler 的**定义体**在包 A，★ 而**调用它的测试**在包 B
⇒ ★ 只跑 `go test ./A/` ⇒ ★ A 的 profile 里那个块 `count=0`
⇒ ★★ **被误判成「零覆盖」** ⇒ ★★ **台账会凭空多出一条假缺口**。

★ 实测证据（★ 5 包联合覆盖后逐块对拍）：

```
blocks with differing counts across profiles: 8642
blocks covered in one profile but 0 in another (= cross-package execution): 8642
```

⇒ ★★ **8642 个语句块**在一份 profile 里 `count=0`、另一份里 `count>0`
⇒ ★★ 「各包自跑」口径**必然漏判**。

★ 读数差（★ 实测，同一批路由 606 条不变）：

| 口径 | covered | zero_coverage | undetermined |
|---|---|---|---|
| 各包各跑（`-coverpkg` 缺失） | 150 | **346** | 110 |
| **`-coverpkg` 联合覆盖** | 150 | **349** | 107 |

⇒ ★★ 联合覆盖多判出 **3 条真零覆盖**，★ 且**没有一条 `covered → zero` 的翻转**
⇒ ★★ ⇒ 联合覆盖是**严格更准**的口径。

★ 那 3 条是 `internal/quality` 的 `CalculateNow` / `ListProfiles` / `GetProfile`
⇒ ★ 它们此前判「判不了」，★ 是因为 `internal/quality` 自己的测试没碰它们
⇒ ★★ 联合覆盖后才有执行记录 ⇒ ★ **是真零覆盖**（★ 不是合并去重引入的假象）。

### §2.3 ★★ 真缺陷 B：Go 的多包 profile 合并**不去重**

★ 机理：★ Go 工具链的 `cmd/go/internal/test/cover.go` 的 `mergeCoverProfile` 就是
★ **`io.Copy` 追加** ⇒ ★ **同一个语句块会在多份 profile 里各出现一次**。

★ 实测：

```
5 份 profile 朴素追加 = 99003 行
唯一语句块           = 36441 个
⇒ 放大 2.72×
```

⇒ ★★ 语句总数被放大 ⇒ ★★ `pct` 失真 ⇒ ★★ 「零覆盖」判定虽不受影响（判定只问
★ 「范围内有没有 `count>0` 的块」），★ **但台账的 `stmts` 列会虚高** ⇒ ★ **必须去重**。

⇒ ★★ **修法**：★ 按 **(file, startLine, endLine)** 去重，★ `count` 取 **max**
⇒ ★★ 语义 = 「**任一次执行即算覆盖**」⇒ ★★ 与 `covered`/`zero_coverage` 的判定语义**一致**。

★ ★ 为什么取 max 而不是 sum：★ `count` 是「执行次数」，★ 不同测试包里的执行次数**不可加**
（★ 那是**不同进程**的计数）⇒ ★★ 只问「有没有被执行过」⇒ ★★ **max** 才是对的。

### §2.4 ★★ 口径收敛后的读数（★ 四段递进 + 迁移矩阵逐条对拍）

| 阶段 | covered | zero_coverage | undetermined |
|---|---|---|---|
| ① 仅 admin（R154 口径） | 108 | 331 | 167 |
| ② 多包 profile（各包自跑） | 134 | 336 | 136 |
| ③ ＋跨包回退 | 150 | 346 | 110 |
| ④ ＋`-coverpkg` 联合覆盖（★ **最终**） | **150** | **349** | **107** |

★ 迁移矩阵（★ 按 `(path, method, handler)` 三元组严格对拍，★ 606 条一条不差）：

```
331 zero_coverage -> zero_coverage
108 covered       -> covered
110 undetermined  -> undetermined
 38 undetermined  -> covered          ★ 解掉 38 条
 13 undetermined  -> zero_coverage    ★ 解掉 13 条（★ 真零覆盖）
```

⇒ ★★ 606 = 331+108+110+38+13 ✔（★ 逐条对得上，★ 不是靠凑）

★ ★ **`zero_coverage` 仍是【下界】**：★ 剩下的 107 条 `undetermined` **可能已被覆盖**
⇒ ★★ 「349 是真零覆盖数」这句话**不成立** ⇒ ★★ 正确表述是「**≥ 349**」。

★ ★★ **三件必须一起承认的事**：

1. ★ **covered 那一栏也涨了（108 → 150）** ⇒ ★ 「API 覆盖率从 17.8% 提到 24.8%」
   ⇒ ★★ **不是因为测试变多了**，★ 而是因为**判据变准了**（★ 原先判不了的 42 条其实有覆盖）。
2. ★ **零覆盖下界也涨了（331 → 349）** ⇒ ★ **缺口没有变小，只是变得可见了**。
3. ★ **剩余 107 条 `undetermined` 仍未判掉** ⇒ ★ 其中 57 条**根本不是具名函数**
   （`wrappedSession` / `legacy` / `staticHandler`）⇒ ★★ **需要另一种口径**（★ 见 §8）。

### §3.1 ★★ 台账头为什么记「生成口径」

★ 缘由：★ **台账会过期，而过期不报错** ⇒ ★ 台账会**悄悄**变成一份关于旧口径的断言。
⇒ ★ 工具在生成台账时把**口径**写进注释头：

```
# gen_tool_sha=…        ← 生成时工具自己的 sha256
# gen_pkgs=…            ← 跑测试的包集
# gen_cover_sha=…       ← 合并后 profile 的 sha256
# gen_defpkgs=…         ← ★ 由读数**推导**出的「handler 定义包」
# gen_coverpkg=…        ← ★ 联合覆盖的包清单（★ 「各包自跑」时写明那句）
# gen_two_pass=1        ← ★ 是否两遍模式
```

⇒ ★★ 于是「**工具改了但台账没重生成**」变成**机器可判**（★ 门的第一条新断言）。

★ ★ 诚实边界（★ 写在门里，也写在这里）：★ 这只能发现「**工具**变了」；
★ 「**代码**变了」同样会让覆盖度变，★ 而那要重跑 `go test` 才知道
⇒ ★★ **代码改过必须手动重生成台账**。

### §3.2 ★★ 门的两条新断言

| 断言 | 断什么 | 为什么必须有 |
|---|---|---|
| `TestApiHandlerCoverageLedgerWasGeneratedByCurrentTool` | 台账头 `gen_tool_sha` == **当前**工具的 sha | ★ 「改了工具忘了重生成」此前**门不会红** ⇒ 台账悄悄过期 |

## §4 ★★ 本轮踩到的坑（★ 全部有实测）

### §4.1 ★★ 「包规格」粒度太粗 ⇒ 一颗老鼠屎坏一锅汤

★ 现象：★ `--pkgs` 里给了 `domains/...`，★ `domains/nodestatecache` 的
★ `TestSelectP99Under1ms`（★ **计时敏感 flaky**）失败
⇒ ★★ **整个 `domains/...` 组被丢弃** ⇒ ★★ 覆盖面反而**更小**。

★ 修法：★ 包清单**必须来自「哪个包真的定义了 handler」**（★ 由读数反推）
⇒ ★ 实测：★ 606 条路由的 `def_file` **只**落在 **5 个包**
（★ `admin` / `api` / `cmd/gateway` / `internal/quality` / `taskprofile`）。

★ ⇒ ★★ 由此有了 `--two-pass`：★ 第一遍粗读 ⇒ ★ 推导定义包 ⇒ ★ 第二遍按它重跑。

### §4.2 ★★ 顶层 `security/` 目录**没有 Go 文件**

★ `--pkgs` 里写了 `security` ⇒ ★ `go test ./security` 报 `no Go files` ⇒ ★ 该包不进 profile。
⇒ ★★ **「包不存在」与「包测试失败」是两种不同的排除**，★ 读数里必须区分。

### §4.3 ★★ bash：`$VAR` 后紧跟**非 ASCII 字节** ⇒ 变量名被吞

★ 现象：★ `echo "… = $AHK_DEFPKGS⇒ …"` ⇒ ★ `set -u` 下报
★ `AHK_DEFPKGS?: unbound variable` ⇒ ★ **脚本中止**。

★ 实测对照：

```

LC_ALL=C            ⇒ 值保留                                ★ 正常
```

⇒ ★★★ **这是 locale 依赖的** ⇒ ★★ 修法：`${AHK_DEFPKGS}`（★ 加界定）。

★ ★★ **仓内早已登记过这个坑**（★ `scripts/252-monitor/ursm-snapshot-payload-bloat.sh:167`
★ 明确写了「必须写 `${fr_live}` 而不是 `$fr_live`」）⇒ ★★ **我踩的是已被登记的坑**
⇒ ★★ ⇒ 通用式：**踩到已登记的坑时，要补的是「为什么它当时没拦住我」，不是「这个坑」**。

### §4.4 ★★★ ★★ 「拿修好的代码验门」的自证陷阱（★ 本轮最该记的一条）

★ 我修好 `$AHK_DEFPKGS` 之后才去跑全角变量门 ⇒ ★ 门报「✓ 无隐患」
⇒ ★★ **差点得出「门没覆盖这个形态」的错误结论**。

★ ★★ 正解：★ **注入 bug 回退到修好的状态之前**，★ 门精确报出第 310 行
⇒ ★★ ⇒ **门完全有效**。

⇒ ★★★ **通用式**：★★ 「门报绿」在**代码已修好**之后是**零信息**；
★★ 要判断门有没有牙，★★ **必须把 bug 注入回去再跑一次**。
★★ ⇒ 这与「★ 证伪一道『保证』的唯一办法是【真的把它打破一次】」是同一条。

### §4.5 ★ `psql -F"\t"` **不解释转义**
