一、结论 / 根因

总判定：首轮实现方向正确，但只切了「写入侧」，读侧与出口仍有 6 处混合口径缺陷 —— 已全部修复并钉测，验证全绿。

首轮任务（上一 goal 轮已交付）建立了系统时区底座：settings.ParseSystemDate / SystemDayStart / SystemDayEnd / SystemTimezoneLocation 公共转换函数族 + system.timezone 设置端点（默认 Asia/Shanghai）+ 写入侧日切与 dashboard 层接入。本轮批判式审计按「一条时间值从用户输入 → 查询 → 存储 → 返回 → 前端显示」全链路逐段对表，发现链路上仍有 6 处用 UTC 硬解析或硬格式化 —— 根因一致：写入侧切换后，读侧解析、前端出口、次级页面没有跟着切，形成「同一语义两种时区」的混合口径。

#发现根因处置
F1 report_rollup 读侧仍 UTC：缺省「昨日」范围、start/end 解析、手动重跑 /run 的日切，全部 UTC 语义 写入侧（worker 打 day 标签）已系统时区，读侧解析没切 ⇒ +08 时区早晨 0–8 点取到错误的「昨天」 修复reportRange 缺省/解析 + /run 缺省切 ParseSystemDate/SystemDayStart；BuildRangeReport 内部按字段重锚 UTC 过滤 DATE 列（标签保真）
F2 前端 Board 面板 custom 日期窗与日串出口硬编码 UTC（T00:00:00Z、toISOString().slice(0,10)） 前端把「日历日」当成「UTC 瞬间」构造，窗口错位 8 小时 修复systemTzNoonMs(dateStr)-12h 构造法 + 出口统一 systemTzDateStr（boardTimeRange.ts / BoardPanel.vue / BoardProviderSection.vue）
F3 时区下拉 choices 偏移写死（纽约固定 UTC-5，半年错 1 小时） 静态表无法表达 DST 修复timezoneEntry 改按当前时刻动态计算偏移（DST 正确，含 :30 半偏移）
F4 后端漏网点：user_profile 3 处窗口解析、session_analytics_timeseries date_from/to、usage_enhanced parsePeriod 月窗 首轮只切了 dashboard/report 主链路，次级端点仍是 time.Parse UTC 修复统一走 ParseSystemDate（RFC3339 优先，YYYY-MM-DD 兜底；月窗 period+"-01"）
F6 前端 useFormat.ts 8 处 Intl.DateTimeFormat 无 timeZone ⇒ 显示跟随浏览器而非系统设置 Intl 默认取浏览器时区，与系统设置脱钩 修复全部注入 tz()（systemTimezone()）+ 钉测（+08 Aug 30 01:30 vs UTC Aug 29 17:30 对照）
F5/F8 （合并入 F1/F2 复核，无独立缺陷） — 复核确认无独立问题
F7 bg/partition_manager.go 与 dashboard_rollup_rebuild.go 是否也要切系统时区？ 判定：不切是对的 —— 物理分区名日历与运维修复工具需要确定性历史定位；跟着可变设置走会让同一日期串不同时期解析到不同分区 ⇒ 迁移静默错位 保持补注释钉死「为何独立」，防止后续被误统一
设计不变式（审计后仍然成立的三条边界）：
  • 数据库 timestamptz 一律 UTC 存储（仓内既有事实，本轮零迁移、零 schema 变更）；
  • 只改「日切 / 日期串解析 / 显示格式化」的语义层，后端 API 返回 UTC 瞬间（索引与缓存友好）；
  • 前端显示按 system.timezone 渲染 —— 用户表达什么时间，查询就命中什么时间。
