## 2. ★★ 本轮最值钱的一条：**位置信号搬到了源码侧**

### 2.1 第 12 增量的死路

语言包侧的**键路径**分不出两类值：

| 键 | 值 | 是什么 |
|---|---|---|
| `providerDetail.models.refreshSummaryFailed` | 「失败 {n}」 | **计数摘要** |
| `common.feedback.saveFailed` | 「保存失败」 | **错误陈述** |

⇒ 用键路径当位置信号 ⇒ 假阳性必然高 ⇒ 第 12 增量只能列人工清单。

### 2.2 本轮的解法：**源码上下文分得出**

★ 源码侧的**赋值目标 / 报错调用**分得出：

```ts
error.value = e instanceof Error ? e.message : t('keys.loadFailed')  // ← 错误陈述
providerDetail.models.refreshSummaryFailed                          // ← 计数摘要，不在这个位置
```

⇒ **位置信号从「键路径」换成「源码侧错误位置」**
⇒ 复用 R1 门**已有**的四类位置识别器（兜底形状 / 错误槽位 / 报错调用 / throw）
⇒ ★★ **R1 门与本轮 L1 门共用同一份实现**（`src/i18n/errorPositions.ts`），
**不另写一份**（★「同一口径只能有一份实现」）。

### 2.3 ★★ R1 门原本**看不见**的那一半

★ 本仓**已经有**一道源码侧的门 `src/i18n/copyClarity.ts` 的 R1 规则
「错误位置的文案必须给出恢复动作」，但它**只判字面量**：

```ts
error.value = '加载失败'          // ← R1 判红 ✔
error.value = t('keys.loadFailed') // ← R1 看不见 ✘（值在语言包里）
```

⇒ 实测：**语言包侧 145 条错误文案是「加载失败」「保存失败」这种裸失败短语**
⇒ **R1 门全绿，而界面在混同。**
⇒ ★★ 这就是 §424 的同款病：**门测的东西（字面量）≠ 要的东西（用户看到的文案）**。

## 4. 判据设计

### 4.1 六条判据

| # | 规则 | 含义 |
|---|---|---|
| ① | `L1a-unregistered-bare` | 错误位置上的语言包值若是**裸失败短语**，该键**必须登记** ⇒ 漏网即红 |
| ② | `L1b-regressed` | 已登记的错误陈述位**不许退回**裸失败短语（8 语种逐语种判） |
| ③ | `L1c-exemption-misused` | 豁免项必须**仍然**落在它的豁免类别里 ⇒ 豁免不能被用来藏违规 |
| ④ | `L1d-missing-locale` | 登记键 8 语种齐备 |
| ⑤ | `L1e-duplicate-value` | 同语种内登记键的**值互不相同**（同一句话不许两份） |
| ⑥ | `L1f-no-recovery` | 登记键的值**必须含恢复动作**（无条件） |

### 4.2 ★★ 「裸失败短语」的分句口径

```
裸失败短语 = 含失败信号 ∧ 无原因槽 ∧ ¬∃「不含失败信号的分句」里含恢复动作
```

★ **为什么要分句**：整句词表匹配会把**主体里的动词**当成恢复动作 ——
`加载选择策略失败` 里的「选择」是**主体的一部分**（选择策略），不是恢复动作
⇒ 整句口径**漏判整族**
⇒ 实测修正后多抓到 **3 条**（`proxy.error.loadPolicyFailed` /
`proxy.error.refreshSubFailed` / `keys.list.limits.loadFailed`）。

★ 与 R1 的同款陷阱同源：「恢复词不能是失败的那个动作」
（R1 注释里已记：`alert('清理失败: ' + …)` 里的「清理」是**失败的主体**不是恢复动作）。

★ 与第 12 增量的 L2/L3 同款纪律：**「点名目标」只认引号内容 / 模板插值 / 箭头**
⇒ 本轮的「恢复动作」只认**独立分句**。

### 4.3 ★★ L1a 的触发只用**源语种**（zh-CN）

★ 第一版在 **8 个语种**上各判一遍 ⇒ **1938 条假阳性**：

| 假阳性类型 | 例 |
|---|---|
| 成功语被当成错误陈述 | `approval.list.success.rejected` = "Request rejected" |
| 确认提示被当成错误陈述 | `dataLifecycle.confirmLogCleanup` = "…This cannot be undone." |
| 取消通知被当成错误陈述 | `dataLifecycle.dirMigrateCancelled` = "Abgebrochen (…)" |

★ 根因：**词表判据在「不是错误陈述」的值上照样会命中**。
⇒ 改法：只用源语种判「这是不是裸失败短语」（单一判据、单一语种 ⇒ 无跨语种噪声），
跨语种的措辞一致性交给 ②/⑥（只跑**已登记**的槽位 ⇒ 精确）。

### 4.4 登记簿（SSOT）

`web/scripts/i18n-error-clarity-registry.json`：

- `kindVocabulary`：35 个操作种类（load / save / create / delete / probe / scan / …）
- `slots`：**143 个**错误陈述位，每条带 `kind` + `subject`（zh-CN 主体词）+ `new`（zh-CN 目标文案）
- `exemptions`：**9 条**豁免，每条带 `category` + `reason`：
  - `runtime-reason`（6 条）：值只是前缀，**具体原因在运行时被拼上**
  - `count-summary`（2 条）：里面的「失败」是**计数项名**
  - `info-missing`（1 条）：陈述的是「信息缺失」而不是一次失败

### 6.2 ★ 建门过程中被自证抓到的 4 类**判据自身**的缺陷

| # | 缺陷 | 现象 | 修法 |
|---|---|---|---|
| 1 | 分句切分**漏了 ASCII 句点** | 英文/德文整句被当一个分句 ⇒「The list could not be loaded. Please retry.」里前半句的 "could not" 把整句标成失败句 ⇒ 后半句的 "Please retry" 看不见 ⇒ **整族漏判** | 分句切分补 `.` |

### 6.3 ★ L1a 的第一版曾报 **1938 条假阳性**
