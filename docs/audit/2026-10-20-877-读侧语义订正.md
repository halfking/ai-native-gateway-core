## 1. `search_text` 到底装什么（这是核对的关键）

`domains/hooks/observability/telemetry/client.go:3319-3330`：

```go
func searchText(entry *RequestLogEntry) *string {
	parts := make([]string, 0, 6)
	for _, value := range []*string{
		entry.ClientModel, entry.OutboundModel, entry.ClientProfile, entry.RequestMode,
		entry.GwSessionID, entry.GwTaskID, entry.APIKeyPrefix, entry.APIKeyOwnerUser, entry.ApplicationCode,
	} { ... }
```

⇒ `search_text` = **9 个元数据字段**的拼接
（客户端模型 / 出站模型 / 客户端画像 / 请求模式 / 网关会话 ID / 任务 ID /
密钥前缀 / 密钥属主 / 应用码），**不含请求/响应正文**。

这同时解释了三件此前只被观测到、没被解释过的事实：
- 实测长度 p50 = 81 字符、avg 93 字节 ⇒ 元数据袋的典型长度，不是正文长度；
- `show_trgm` distinct avg 84.59 ⇒ 9 个字段拼接后 3-gram 几乎不重复；
- **877 文件头「search_text 是 TOAST 宽列」不成立**（max 148 字符、恒内联），
  旧夹具 455 字符把写放大高估约 5.3 倍。

★ 正文在**另外两列**（`request_preview` / `response_preview`），
它们**既不被 `?q=` 搜索、也没有 trigram 索引**。

## 2. 前端承诺搜什么 —— 与 §1 的内容**完全一致**

`web/src/views/RequestLogsView.vue:1481`：

⇒ UI 承诺的就是「模型 / 会话 ID / 密钥前缀」——

## 3. 877 的 GIN 服务的是哪条路径（读路径核对）

`admin/logs_turns_source.go:62-67`：

```go
func logsSourceFromSQL() string {
	if settings.GetPlatformBool(nativeTurnsReadSetting, false) {
		return db.SessionFamilyTurnsSourceSQL() + " rl"   // session 族原生投影
	}
	return "request_logs_with_current_month rl"              // canonical 视图

```

- 视图侧（默认）：`db/request_logs_view_schema.go:25` 明写
  「session 家族拼装体——`session_turns(_hot)` 113 列会话投影 **UNION ALL** v1 体」

  `admin/logs.go:540` 的 `rl.search_text ILIKE '%'||$n||'%'` 对这些臂
  落在 **`session_turns.search_text`** 上 ⇒ **877 的 GIN 在这条活路径上被用上**。
- 开关 `storage.admin_logs_native_turns_read`：生产 `settings_kv` **无记录**
  ⇒ 取 fallback `false` ⇒ 走视图。**这是有意保持关闭**（复核轮 L5：
  为省列表页的 v1 臂 + 反连接成本），**与搜索能力无关**。
- 877 迁移自身的文件头也写着同一件事：
  「S4 停写（`storage.request_logs_write_enabled=false`，生产 2026-10-13 生效）
  后新请求只落 session 家族」「session 族**从未迁移过** v1 族的
  `idx_%s_search_trgm`，本迁移补齐」。

⇒ **877 的 GIN 确实服务 `?q=`，前提（读路径）成立。**

**如果将来真要做正文检索**，正确的做法不是让 `?q=` 去搜 `search_text`，
而是给 `request_preview`/`response_preview` 单独建 trigram 索引
（那才是「TOAST 宽列」的真身）——877 当前的**选型没错，只是它索引的是元数据**。

## 6. 判据纪律（本轮新增两条）

1. ★ **「能力坏了」与「需求为零」是两个命题**，各自需要各自的证据：
   「坏了」要证明**链路某一段断了**（本例：查 `search_text` 的填充率、
   查读路径的 FROM 源、查 UI 承诺）；
   「需求为零」要证明**请求从未发出**（本例：nginx 访问日志的 `[?&]q=` 计数）。
   本轮两段都查了 ⇒ 结论是「能力按广告工作，且零使用」，
   **不是**「坏了所以没人用」，也**不是**「没人需要正文搜索」。
2. ★ **别把「正文搜不到」当「功能坏了」**：能力边界由**承诺**定义
   （UI placeholder），不由实现里恰好有哪个字段定义。
   查「坏了」之前先读**用户被承诺了什么**。
3. ★ **对「读数 = 0」这类结论，先问「这个 0 有几种成因」**：
   （a）真没人用；（b）能力坏掉（发不出请求）；（c）能力没被承诺过（用户不会用）。
   本例把 (b)(c) 都查掉后，剩下 (a) ⇒ 结论才成立。
