# FileWriter 根治候选评估:每进程独立文件名 vs 启动孤儿 header 检测(owner 决策材料)

- 日期:2026-10-01(local)
- 上游:docs/audit/2026-09-30-hotzone-o5o1r9-closure.md §1.6 遗留第 2 条(「FileWriter 侧的根治未做,列后续候选」)
- 性质:**只出材料不动代码。** 本文所有代码事实按 origin/main 935be9493 实勘。

## 一、问题与现状

fallback 文件写入(`domains/dbdegradation/file_writer.go`)的三个事实叠加,构成 2026-09-30 O5
损坏现场(「孤儿 gzip header 连排 + 完整 member + 截断尾」)的成因链:

1. **跨进程同文件 O_APPEND**:文件名按日 `sessions-YYYY-MM-DD[-NN].jsonl.gz`
   (file_writer.go:212-215),打开用 `O_CREATE|O_WRONLY|O_APPEND`(file_writer.go:219);
   蓝绿切换重叠窗内新旧两代网关共享宿主 `backups/` bind mount,各自 `ensureFile` 后追加**同一个**
   base 文件(当日序号是进程本地内存值,两代都从 seq=0 起,必然撞同一文件)。
2. **硬杀跳过 gzip.Close**:容器被杀时最后 member 无 trailer;下一代重启后继续 O_APPEND 追加,
   产生孤儿 header 与截断 member 混流(交错写还会产生残行坏行)。
3. **写侧无任何损坏感知**:append 语义对既有内容零校验。

已落地的缓解(2026-09-30 O5 收口):`FileReader` 打捞路径逐 member 重同步+坏行跳过
(file_reader_salvage.go),真文件 55/55 实证+12 钉测;`HasLoss` 归档护栏阻止带损归档;
256MB 压缩字节上限内自动打捞。**损坏已从「整文件不可恢复」降级为「可恢复+计损+文件保留」**——
本决策是写侧根治的「要不要做得更干净」,不是补数据丢失。

## 二、候选 A:每进程独立文件名

每个 FileWriter 实例生命周期内独占文件:文件名掺入进程身份(如
`sessions-YYYY-MM-DD-<boot短id>[-NN].jsonl.gz`,boot id 进程启动时生成一次)。

**收益**

- 单写者/文件,交叉写残行与 header 混流**结构性消失**;硬杀截断被限死在死进程的文件里,
  该文件永不再增长(死进程不会回来追加)——损坏不再扩散。
- 新文件不再产生打捞需求(打捞 reader 保留,只服务存量损坏文件)。
- 无需任何跨进程协调(候选 B 绕不开这一点)。

**代价(命名/清单/保留期三联动)**

- 文件名正则 `backupFilenamePattern`(file_reader.go:20)、`ListBackupFiles` 的日期提取与排序、
  `validateBackupFilename` 全部要跟着改;恢复/对账/监控脚本的文件名假设同改。
- `maxDailyFiles=50`(file_writer.go:39)语义变化:每次蓝绿部署/重启都新开文件,当天代际多时
  序号消耗加速;**打满上限=写失败重试 3 次后整条丢弃**(writeRecord,file_writer.go:72-93),
  上限需要随新语义重估并加告警。
- 恢复 runbook 从「按日一文件」变为「按日多文件按序回放」(GenericRecovery 单文件粒度,需循环)。
- retention/清理(目前 backups/ 无自动清理,见 §四)增加一个维度。

## 三、候选 B:启动时孤儿 header 检测

`ensureFile` 打开既有非空日文件时,扫尾部判定最后一个 member 是否完整(可复用打捞原语
`tryMemberOK`/`gzipMemberEnd`);不完整即「文件已损坏尾」→ 直接轮转到下一序号开新文件,
不往损坏尾后追加。

**收益**:命名/清单/保留期/运维肌肉记忆**全不动**;新写入不再与损坏尾混流,新 member 干净完整。

**代价与两个硬边界**

- **B 单独不解决跨进程碰撞**:seq 是进程本地值,蓝绿两代同时检测到损坏尾、同时轮转,
  会同时选中同一个 `-01` 文件继续交叉写。要闭环必须配合「打开前扫目录取现存最大 seq+1」
  ——蓝绿启动间隔通常分钟级,竞态窗小但无强保证(无锁文件/原子占位语义)。
- 损坏尾仍留在原文件里,打捞 reader 对存量损坏仍必不可少;B 的收益是新文件干净,不是免打捞。
- 误判成本 = 多轮转一个文件(加剧 50/日上限消耗);检测逻辑本身成为新的正确性面。

## 四、与本决策联动的两个独立挂账(无论选哪个都建议处理)

1. **backups/ 无任何自动清理**:trimmer 只管热区三子树(cache/session_bodies/requests);
   R-9(2026-09-30 9bc266f65)把 `data/` 挂载后,backups 若纳入 data/ 语义将跨部署**永久累积**。
   建议随根治一并定 retention(现有 archive/ 目录只被手动恢复归档使用)。
2. **50/日上限打满 = 静默丢条目**:现状 writeRecord 重试 3 次失败仅 slog.Error
   (file_writer.go:87-92),无 Prometheus 告警、无 fallback 兜底。至少补告警。

## 五、对比与建议

| 维度 | A 每进程文件名 | B 启动检测轮转 |
| --- | --- | --- |
| 交叉写根治 | 结构性消失 | 需补 seq 扫目录,且无强保证 |
| 硬杀截断影响面 | 限死在死进程文件,不再扩散 | 检测后的新写干净,损坏尾仍在 |
| 命名/清单/保留期联动 | 三处全改+runbook 变更 | 零改动 |
| 新增正确性面 | 文件名兼容(旧文件仍要能读) | 检测误判/竞态 |
| 实现规模 | 中(一波改齐) | 小-中 |

**建议:A(每进程独立文件名)为根治方向**——它是唯一让「新文件不再产生打捞需求」成立的方案,
且不需要跨进程协调;B 可作为 A 落地前的低风险过渡(只加检测+轮转,改动小,先止血交叉写)。
若采纳 A,建议一批内改齐:正则+日期提取+上限重估+告警+runbook,旧文件名保持可读
(打捞 reader 的正则同时收新旧两形)。

**决策点**:① 选 A / B / 先 B 后 A / 不做(维持打捞兜底);② 50/日上限新语义与告警是否随批;
③ backups/ retention 是否随批定值。
