## 一、结论先行

对账页的**读面**（报告本身）是可信的：总计 = Σ 各分组恒成立，provider/model 两张表的口径与快照一致。
但**筛选栏（候选面）**与**模型选择器**有两处结构性错位，导致「审计页看不到该看的数据」：

| # | 现象 | 量级（211 真库） | 根因 |
|---|---|---|---|
| F1 | 「未落定」供应商桶**看得见、筛不出** | 占全量流量 **30.8%**（38,035 / 123,367 笔） | 报告读面把 `provider_id IS NULL` 映射成哨兵 `-1` 显示成一行；候选查询用 `IS NOT NULL` 把它整桶滤掉 |
| F2 | 零流量供应商**完全不可见** | providers 表 69 家（58 enabled）→ 候选只有 **18** 家 | 候选只来自快照 ⇒ 只有区间内有流量的才进下拉框；「开着却一单没有」（配错/被限流/模型没接上）这个最该被审计看见的信号被藏起来 |
| F3 | 模型候选**静默截断** | 旧上限 500，代码注释自记「30 天内 527 个模型名」 | `maxDimensionOptions = 500` 硬砍且不告诉任何人，砍掉的正是请求数靠后的长尾 |
| F4 | 模型选择器与路由页**不是同一套名字** | 区间内 356 个有请求的模型里，只有 **212** 个字面等于某个 canonical 名，**144** 个（含 `MiniMax-M2.*` 全族、`<unknown>`）压根不在目录里 | 对账维度是 `raw_model_name`，路由页选择器给的是 `canonical_name`；直接换组件会让 4/10 的流量**变得不可选** |

> ★ **F4 是本轮最关键的一条**：owner 说「模型选择要用路由页那种方式」——如果直接把 `<el-select>` 换成
> `<ModelPicker>`（它发 canonical 名），对账页会从「144 个模型不可选」变成「144 个模型筛不出」，
> **恰好把 owner 要修的「数据丢失」做成了另一种数据丢失**。所以本轮不是「换组件」，是「换组件 + 补口径」。

### 关键原始数据

**快照口径覆盖（`report_snapshots`）**

| scope | 行数 | 天数 | 区间 | 请求数 |
|---|---|---|---|---|
| `daily_grain` | 2792 | 6 | 11-10 ~ 11-15 | 123,367 |
| `daily_total` | 13 | 13 | 11-03 ~ 11-15 | 123,367 |
| `daily_by_provider` | 94 | 6 | 11-10 ~ 11-15 | 85,832 |
| `internal_grain` | 545 | 6 | 11-10 ~ 11-15 | 64,949 |

- 11-03 ~ 11-09 的 `daily_total` 行 **request_count = 0** ⇒ 那 7 天**不是**数据丢失，是真没流量
  （`coverage.legacy_dates` 只列 11-09 一，正确）。
- `daily_by_provider` 的请求数**低于** `daily_grain`（85,832 vs 123,367）：旧边缘 scope 只覆盖 business 流量，
  grain 覆盖全量（含探针）。读面在有 grain 的日期**只用 grain**，所以读面没有被放大/缩小 ⇒ 读面可信。

**provider 维度对拍**

```
dims.providers        = 18 项
report.providers      = 19 行     ← 差额 = provider_id = -1（未落定）
未落定桶              = 38,035 笔 = 全量 123,367 的 30.8%
providers 表          = 69 家（61 未软删、58 enabled）
⇒ 候选覆盖率：18 / 61（缺 43 家「有配置、零流量」的供应商）
```

**未落定流量的构成**（`usage_facts`，11-15 当日）——不是数据损坏，是**没走到供应商**的流量：

| error_kind | traffic_class | 笔数 | provider_id |
|---|---|---|---|
| `no_candidate` | probe | 5,148 | NULL |
| `rate_limit_exceeded` | business | 282 | NULL |
| `request_processing_timeout` | business | 47 | NULL |
| `routing_database_error` | probe | 32 | NULL |

⇒ 未落定桶**有业务含义**（探针找不到候选 / 限流 / 超时），必须**可筛**（F1）。

**模型维度对拍（catalog ⇄ snapshot）**

```
区间内 356 个 raw_model_name（daily_grain）
  ∩ 目录 canonical_name          = 212
  ∩ 目录 raw_names（家族展开）  = 355      ← 家族展开后仅 1 个落空
  落空的那 1 个                = claude-3-7-sonnet-20250219
历史全量 1200 个 raw 名 → 1199 个可落 canonical，落空 1 个（同上）
```

⇒ **家族展开是可行的、且覆盖面 99.9%**；剩下那 1 个必须靠「本区间有请求的模型」这一段兜住。

## 三、修复

### 后端（`domains/reportrollup/`）

| 文件 | 改动 |
|---|---|
| `dimensions.go` | ① provider 分支改用 `COALESCE(s.provider_id::text, '-1')` 且**不再过滤 NULL**（F1）；② 新增 `mergeIdleProviders`：把 `providers` 表里在册（`deleted_at IS NULL`）但区间零流量的供应商并进候选，`requests=0`，排在有请求的之后（F2，兼「优先显示有请求的」）；③ 上限 500 → **5000**，且超限时在 `Truncated` 字段**显式回报**砍了几项（F3，不再静默）；④ 候选排序统一为「请求数降序 → 键升序」 |
| `grainreport.go` | ① `provider_id = -1` 落成 `provider_id IS NULL`（F1 的过滤侧；原来 `= -1` 永远 0 行）；② 模型过滤支持 `ModelNames []string` 集合（`= ANY($n)`）；③ `filterArgCount` 同步新语义（占位符连号性不变） |
| `modelnames.go`（新） | `ResolveModelRawNames`：把用户给的模型名（canonical 名 / raw 名 / 别名）展开成 raw 名集合。三条解析路径：`models_canonical.canonical_name` / `model_offers.raw_model_name` / `model_aliases.raw_name`（都按 `lower()` 折叠）。★ 集合**始终含原值** ⇒ 目录外的 raw 名（`<unknown>`）照常精确命中，一行不丢；查不到 canonical 时退化为精确匹配（不把过滤悄悄丢掉） |

### 前端（`web/src/`）

| 文件 | 改动 |
|---|---|
| `components/ModelPicker.vue` | 新增可选 prop `requestRanked` / `requestRankedTitle` / `requestRankedLimit`：**置顶分组**「本区间有请求的模型」（按请求数降序，带请求数徽标，超出预览条数可展开全量图层）。★ 纯增量：不传这两个 prop 时渲染结果与从前**逐字相同**（路由页不受影响） |
| `components/reconciliation/ReconciliationToolbar.vue` | 模型筛选器由 `<el-select>` 换成**与 `/routing-v2?tab=resolve` 同一个 `<ModelPicker>`**（owner 明确要求），并把 `dims.models` 作为「有请求的模型」喂进去；供应商下拉的 `-1` 项显示人话「未落定」而不是裸 `-1`；后端回报截断时显示「已截断 N 项」 |
| `api/reportrollup.ts` | `DimensionOptions` 增 `truncated?: Record<string, number>` |
| `locales/*/{plugin,reports}.ts` | 9 语种补词条（`reports.modelsWithRequests` / `modelPickerTitle` / `candidatesTruncated`；`plugin.providerConfig.*` ×31） |

### 为什么模型筛选最终是「家族展开」而不是「精确 raw 名」

owner 要的「用路由页的模型选择方式」= 选择器给 **canonical 名**（`minimax-m2.5`）；
对账维度是 **raw 名**（`MiniMax-M2.5` / `minimax-m2.5` / `auto/minimax-m2.5`）。
两者字面不等 ⇒ 后端统一展开成 raw 名集合再过滤。

副作用（**有意为之**）：点「按模型」表的某一行也会落到家族口径——同一个模型的不同拼写
（provider 前缀、大小写）不再被拆成互不相干的行。这是审计想要的：「MiniMax-M2.5 和 minimax-m2.5
是同一个模型，流量不该被拆开藏起来」。

## 六、遗留与登记

1. **未落定桶的归因还可再拆**：`no_candidate`（探针找不到候选）是当前未落定桶的大头（5,148 / 11-15 当日）。
   本轮只保证它**可筛**；「为什么探针找不到候选」是另一条线（候选健康面），不并入本轮。
2. **`daily_by_provider` / `daily_by_model` 旧 scope 的请求数天然低于 grain**（只覆盖 business）。
   读面在有 grain 的日期不用它们，但**没有 grain 的历史日期**（11-03 ~ 11-09）只有 `daily_total`——
   那些天维度分解不可得（`coverage.legacy_dates` 已披露）。若要把历史也补齐，需要对那些日跑一次
   `/api/admin/report-rollup/run` 回填 grain（本轮未做：那些日 request_count = 0，回填无收益）。
3. **`model_offers` 与快照的覆盖差**：家族展开依赖 `model_offers` / `model_aliases`；
   若某个 raw 名从未进过 `model_offers`，它只能靠「本区间有请求的模型」这一段选到（仍可选，只是不成家族）。
4. **CJK 棘轮的并行债**：本轮把 `PluginSettingsPage.vue` 的 38 处收进 i18n（计数 4517 → 4479）。
   后续并行特性提交仍可能再次抬高——建议把 `i18n:cjk:check` 放进 PR 必跑项（当前只在 `pnpm test` 里）。
