## §2 实测证据（全部可复跑）

### §2.1 基线时点的约束（一次性库，只应用 prereqs + 基线，未跑启动序列）

```
public.request_logs     存在 = 1
public.session_turns_hot 存在 = 0        ← 基线不建它
```

⇒ 在基线时点创建**会话族形态**的视图：

```
ERROR:  relation "public.session_turns_hot" does not exist
```

⇒ ⇒ **实测**（不是推理）：**基线里不能写会话族形态** ⇒ **源里的 v1 体是必需的**。

### §2.2 源文件自己写明了（`sql/objects/views/customer_cost_view.sql` 头）

> ⚠️ **本文件不是部署形态的视图定义**，它是 **v1 fallback 体**（两个活指标子查询
> 仍读 v1 族 `request_logs`），只在「基线时点」成立。
>
> 为什么基线必须留 v1 体（2026-10-20 实测）：基线 schema 是**逐语句**应用的，
> 而 `CREATE VIEW` 会**急切校验**它引用的关系 ⇒ 若这里写成会话族形态
> （`session_turns_hot` / `session_turn_details*`），新装环境会在此处报
> **42P01: relation "public.session_turns_hot" does not exist** 并中止
> （那两张表由**启动序列**的 `session_turns_hot_bootstrap.sql` 与迁移 734 建，
> 基线时点还不存在）。升级路径绿是因为那些表早就存在
> ⇒ **「升级路径绿」≠「新装路径绿」**。
>
> 部署形态（会话族）由 **迁移 883** 换上 ……
> 两条路径（全新安装 / 存量升级）跑完启动序列后**形态一致**。

### §2.3 机制链（链序实测）

| 链索引 | 迁移 | 作用 |
|---:|---|---|
| 280 | `883_session_family_cost_view_metrics.sql` | 把 `customer_cost_view` / `model_cost_per_task_view` 换成**会话族**形态 |
| 281 | `884_session_family_v_analytics_views.sql` | 把 `v_continuation_effectiveness` / `v_node_switch_analysis` / `v_timeout_effectiveness` 换成会话族形态 |
| 282 | `890_drop_request_logs_v1_family.sql` | **退役 v1 族**（DROP 表 + DROP 函数）；★ **刻意不用 CASCADE**（原话：「若出现**预期外**的依赖者，让它**响亮失败**而不是被顺手删掉」） |

⇒ ⇒ **链序是自洽的**：先换形态、再退役 ⇒ 视图不再引用 v1 ⇒ 890 才能干净地 DROP。
⇒ ⇒ ★ **890 的「不用 CASCADE」正是一个响亮的守卫**：若有人把 883/884 的顺序放到 890 之后
（或漏跑），**890 会当场失败**而不是静默留下坏视图。

### §2.4 实况是干净的（全新安装 + 生产）

- 一次性库（295 条链全绿）上，这 5 个视图的 `pg_get_viewdef` **不含** `request_logs` / `_request_logs`；
- 生产 252 上 v1 族仍在（未退役），但部署形态由 883/884 换上 ⇒ 同样不含 v1 臂。

⇒ ⇒ ★ **实况（生产 + 新装）都是对的；只有「基线形态快照」里还有 v1 臂。**

## §3 ★ 真正的缺口：一份「按文档操作就会炸」的说明

`deploy/sql/sync-objects.sh` 把 `sql/objects/` 同步到 `deploy/sql/objects/`，并在生成的
`deploy/sql/objects/views/README.md` 里给出**逐个应用**的命令：

```bash

psql "$DATABASE_URL" -f deploy/sql/objects/views/<object_name>.sql
```

⇒ ⇒ ★★ **对这 5 个视图，那条命令在 v1 退役后必然失败**（实测）：
`ERROR: relation "public.request_logs" does not exist`（42P01，在全新安装上）
⇒ ⇒ **这是本轮找到的真缺口**：不是「源错了」，而是**说明没有把「这 5 个是基线形态、勿单独应用」写出来**。

⇒ **建议修法**（小、在文档侧、不碰源 DDL）：在 `deploy/sql/objects/views/README.md`
与这 5 个源文件的头部各加一句「★ 本文件是**基线形态**，**勿单独应用**；
部署形态由迁移 883/884 换上」。

## §4 建议的判据改法（给那道门）

- **A（推荐）**：v1 臂检测**分两个时点** ——
  「**基线时点形态**」（`sql/schema/01-schema.sql` + `sql/objects/views/` 的基线体）**允许** v1 臂；
  「**部署时点形态**」（composer + 迁移 883/884 + 启动序列跑完后的实况）**不该有** v1 臂。
- **B**：给那 5 个「基线形态 fallback 体」加**机器可读的声明标记**
  （如 `-- dbinit:baseline-v1-fallback`），让审计**按声明豁免**而不是按名单硬编码
  ⇒ ⇒ 「源里出现 v1 臂」由**声明**承担，而不是靠一道会要求危险改动的门来断言。

⇒ ⇒ ★ **这与 R62 的教训完全同族**：**判据必须钉住「量的是哪个时点 / 哪个形态」**。
