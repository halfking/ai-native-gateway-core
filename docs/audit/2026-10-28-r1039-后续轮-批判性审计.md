## 1. 审计方法：怎么查「只是声名一下」

上一轮给自己写了一条通用式（LESSONS §476 通式一）：**复核一条安全策略时，判据是「枚举所有注册点」**。
本轮把这条反过来用在**自己身上**，问三个问题：

1. **这条功能在生产路径上，被测到了吗？** —— 不是「中间件调用了探针」，而是「**探针真的读了真库、真的判了吊销**」。
2. **我引入的新机制，会不会把系统从「偶发坏」变成「必然坏」？** —— 新锁的**失败模式**必须比它防的问题**更轻**。
3. **审计档里写的每句「运维可以自己恢复」，在仓内是**真命令**还是只是**一句话**？**

⇒ 第 1 问查出 F1，第 2 问查出 F2，第 3 问查出 F2 的后半段。

## 2. F1（高）：判据只 stub 探针 ⇒ 生产链零覆盖

### 2.1 缺陷本体

上一轮新增的 6 条判据（`cmd/gateway/r1039_jwt_middleware_revocation_test.go`）换的是
**package main 的 `jwtRevocationProbe`** ⇒ 它们证明的是：

> 「中间件**会调用**探针，且调用时给的 user_id / 签发时间是对的。」

它们**没有**证明：

> 「探针**真的**从 `settings_kv` 读到改密纪元，并据此吊销会话。」

⇒ 而**生产路径上的 `admin.RevokedByPasswordChange`（上一轮新导出的那个外壳），
在任何测试里都没有被执行过一次**。
⇒ 若这个外壳坏了（恒返回 false、绕过探针、读错表、纪元格式理解错），
**上一轮的 6 条判据一律全绿**。

★ **这正是「声名」**：功能被声明了，判据却只测了它的**调用形状**。

### 2.2 修法：补两层真腿

**① `admin` 单元腿**（`admin/r1039_revoked_by_password_change_test.go`）：
用**真探针**（`probeAuthRevocation`，不 stub）+ 进程内纪元缓存，四个断言**双向**：
签发早于纪元 ⇒ 吊销；晚于纪元 ⇒ 存活；无纪元的用户 ⇒ 存活；无库 ⇒ fail-open。
⇒ 恒假 ⇒ 第 1 条红；恒真 ⇒ 第 2/3/4 条红 ⇒ **「外壳只是转发」被钉死**。

**② `cmd/gateway` 真库端到端腿**（`cmd/gateway/r1039_jwt_middleware_revocation_realdb_test.go`）：
**一次性库**（退出即 DROP，不碰 `llm_gateway`）+ 最小 `settings_kv` + 真实纪元行：

| 用例 | 钉住什么 |
|---|---|
| `RevokesAgainstRealDatabase` | 真实 JWT（签发早于纪元）→ 真实中间件 → 真实外壳 → 真实探针 → 真表 ⇒ **401 + 逐字同一句提示**；且**不得到达 handler** |
| （同上用例内的反向对照） | **没有纪元行**的同一形状会话 ⇒ **必须放行**（否则「一律 401」也能让本条全绿） |
| `EchoAndServeMuxRevocationAgreeOnRealDatabase` | **两侧口径对拍**：同一串凭据 + 同一张真库，ServeMux 侧（`admin.AdminMiddleware`）与 Echo 侧**必须给出同一个判决** ⇒ 证明「对齐」是真的，不是「两边各自有个看起来对的实现」 |
| `RevocationFailsOpenOnDatabaseOutage` | 池不可用 ⇒ **放行**，不把管理面锁死 |

⚠ **真库腿不可用时必须显式说明「本次没跑」**（仓内既有约定：skip 不等于证据）。

## 3. F2（高）：我引入的切流锁，会把偶发互踩变成必然卡死

### 3.1 缺陷本体（实测复现）

上一轮的切流锁有两条获取路径：**flock**（Linux 有 `flock` 时）与 **mkdir 回退**（macOS 默认）。

★ **flock 路径没有这个问题**（进程退出即自动释放）；★ **mkdir 回退有**：
进程被 SIGKILL / 机器重启 ⇒ 锁目录**留在原地** ⇒ 而上一轮的实现**只有一条出路：rc=75 拒绝**。

实测（2026-10-28，本机）：

```
造一个「持有者 pid 已死」的残锁 ⇒ dl_acquire_switch_lock ⇒ rc=75
再试一次（= 模拟后续每一次部署）  ⇒ rc=75
⇒ ★ 永久卡死，且仓内没有任何命令能解开
```

⇒ **新机制把「偶发互踩」换成了「必然卡死」**——这比它防的问题更糟
（互踩只坏一次部署；卡死让**之后所有部署都坏**）。
★ 而且上一轮审计档里那句「残锁元数据里有 pid ⇒ 运维核对后手工删除」是**纯声名**：
仓内**没有任何命令**能删它（共享部署库的 `unlock-local.sh` 管的是它自己的锁路径，不是我的）。

### 3.2 修法：两处，都落在仓内

**① 残锁接管**（`scripts/deploy-local-lib.sh`）：
争用时读持有者元数据的 pid ⇒ **pid 已死 ⇒ 判定残锁 ⇒ 接管**（并大声告警）；
**pid 还活着 ⇒ 仍然拒绝**（那是真的有人在切流）。
⇒ 口径与共享部署库 `lock.sh` **一致**：**只看 pid 存活，不按年龄判**
（部署可能正在长时间跑，按年龄清锁会打断别人）。

**② 仓内真恢复命令**（`scripts/deploy-local.sh`）：
新增动作 `recover-switch-lock` ⇒ `dl_recover_switch_lock`：
- 持有者**还活着** ⇒ **拒绝**（不打断正在跑的部署）；
- 持有者**已死** ⇒ 清掉；
- 没有锁 ⇒ 幂等成功。
⇒ 注册在**三处**（usage / 参数白名单 / case 分派）—— 三处都缺，判据就红。

### 3.3 判据（`tests/deploy_switch_lock_contract_test.sh`，8 条不变量）

| # | 不变量 |
|---|---|
| I1 | 锁路径**机器级**（逐字等于 `${LOCK_TMP_ROOT}/kx-llm-gateway-switch.lock`，且换 cwd 再算一次必须一样） |
| I2 | 争用**快速失败**（rc 75）+ 打印持有者元数据 + 提示可恢复 |
| I3 | 释放后可再次获取 |
| I4 | 持锁窗口**覆盖候选起跑**（源码行号顺序） |
| I5 | 释放点在**切流完成之后**（源码行号顺序） |
| I6 | **失败路径（trap）也释放** |
| **I7** | **残锁（持有者已死）必须被接管**（rc 0 + 告警 + 元数据改写），**不得**把部署路径永久卡死 |
| **I8** | **活着的持有者仍然被拒**（rc 75）且其元数据**未被破坏**（接管逻辑不得把互斥拆了） |

### 3.4 变异臂（N5~N7，全红）

|---|---|---|---|

## 4. F3（中）：本轮自己写的「端到端」判据，一度把连接池传成 nil

★ **编译器当场抓住的**（`declared and not used: pool`）——
因为我的助手函数 `r1039RevocationEcho` 把池**写死成 nil** ⇒ 探针恒 fail-open ⇒
那条「端到端」判据会**恒不吊销**⇒ ⇒ **它本来又是一条「声名」判据**。

⇒ 修法：池改成**显式参数**（`r1039RevocationEcho(t, db, reached)`），
真库腿**必须传真池**；并把这条写进助手的注释。

⇒ ★ **这是本仓「量具不对 ⇒ 假红」的又一形态**（第三次）：
前两次是「探针查得太早」「列表当单串」，这次是「**量具的输入本身就是空的**」。

★ **另一处同族**：`RevocationFailsOpenOnDatabaseOutage` 第一版**红了**，
而**红得有道理**——改密纪元表是**进程内 5s TTL 缓存**，前面的用例已把缓存焐热
⇒ 此时的探针**根本不碰数据库** ⇒ 「把池关掉」这个前提**不成立**
⇒ 第一版量的其实是**缓存**，不是**宕机**。
⇒ 正解：**先等缓存过期（> TTL）再掐断连接**；判据注释里写明了为什么必须等。

## 5. F4（中，登记为遗留风险）：改密吊销有 ≤5s 滞后窗口

`admin/auth_revocation.go` 的纪元表走**进程内 5s TTL 缓存**
（`authRevocationEpoch`）⇒ **改密之后，最长 5s 内旧会话仍可用**
（写侧改密时会 `invalidateAuthRevocationCache()`，但**只影响本进程**；
多副本部署下，其它副本最长滞后 5s）。

⇒ 这是**既有性质**，ServeMux 侧与 Echo 侧**同口径** ⇒ 本轮**不改**
（改它要动共享缓存策略，属另一条工作线）。
⇒ 登记为**遗留风险**：需要「改密即刻踢出」语义时，要单独裁决。

## 6. F5（低，登记）：切流锁被占 ⇒ 白烧一个 build_seq

`deploy()` 的顺序是 `bump_local_version`（改 `version.json`）→ 构建 → 释放构建锁
→ **取切流锁** ⇒ 若此刻切流锁被占 ⇒ `die` ⇒ **版本号已经被抬走了**。

⇒ 这与仓内其它「构建之后才失败」的路径同语义（构建失败也烧版本号）⇒ 本轮**不改**。
⇒ 但它让「切流锁被占」的成本比看上去大一点 ⇒ 登记。
