3.2 ★ 真库抓到的坑之一：cannot add column to a partition
  现象：999c 的第 6 段（用 DO 块遍历 pg_inherits 给每个分区子表 ADD COLUMN）报
        ERROR:  cannot add column to a partition
  根因：★ PostgreSQL **不允许**直接对分区子表 ALTER TABLE … ADD COLUMN；★ 而**父表加列本来就会
        自动传播到全部分区子表** ⇒ ⇒ 我那一整段是**多余且有害**的 ⇒ 删掉。
  ★ 静态核对抓不到这个（它读起来完全合理）；★ 只有真库能抓。
  ★ 保留那段注释（写明「为什么这里曾经有一段遍历 pg_inherits 的 DO 块，而它被删了」），免得有人按
    「父表加列不传播」的旧认知再写回来。

3.3 ★ 真库抓到的坑之二：usage_date 漏去 NOT NULL
  现象：写侧的 INSERT（domains/toolexecution）不提供 usage_date，而目标表 usage_date 是 NOT NULL。
  ★ 静态对拍抓到过 tool_id／tenant_id，★ 但 usage_date 是第三个（写侧给的是 `date`）⇒ 三列都要去。
  真库确认：去 NOT NULL 后写侧 INSERT 成功（INSERT 0 1）。

3.4 ★ 真库抓到的坑之三：读侧扫 NULL 进 string 会报错
  现象：999c 补列后，父表里**旧口径的行 tool_name 是 NULL**（新列，老行没值）⇒ 读侧 list 查询
        （hot ∪ 父表 UNION ALL）会把这些行带出来 ⇒ ★ Go 侧 ToolName 是 `string`（不是 sql.NullString）
        ⇒ database/sql 扫 NULL 进 *string 会**直接报错**："converting NULL to string is unsupported"
        ⇒ ⇒ 只要父表里有一行旧数据，ListStats 就整个失败。
  修法：读侧 list 查询的父表腿加 `p.tool_name IS NOT NULL`（★ GetStats 那条不用改：它按 tool_name 精确查，
        NULL = $1 不成立 ⇒ 天然只命中新口径行）。
  真库验证：★ 造了一行旧口径数据后对比 ⇒ 修好的查询只返回 tool_name 非空的行；未修的对照会把 NULL 行带出来。
