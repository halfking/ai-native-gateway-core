## 一、973 加固方案分析

### 1.1 问题历史与当前状态

#### 背景
- **原始问题（L87 报告）**：合并轮二十二号段归位时，把加固版 973 一起归位回 057，现仓 057 缺事务包裹 ＋ 两条锁超时设置
- **加固内容**（973 vs 057 差异）：
  - `BEGIN;` / `COMMIT;` 事务块
  - `SET lock_timeout = '5s';`
  - `SET statement_timeout = '10min';`
  - `public.` schema 限定（057 裸表名）

#### 当前事实（已闭合）
**生产实测（2026-11-24 20:5x 只读复核）**：
```
✅ api_keys.team_id 列在位
✅ ledger 055/056/057/058 全 applied
✅ api_keys 2 条 RLS 策略（api_keys_team_owner_all / api_keys_team_admin_select）
✅ applied 的就是现仓那份 057 字节（sha256: 399525282ac62d4a2f317fdb9bf9c64059e79c4316365adfcedee3ed2c98d542）
```

**证据链**：
- 仓内：`sql/migrations/startup/057_api_keys_team_id.sql`（40 行，9 条语句）
- 生产台账：`schema_migrations` 含 057 记录
- 生产对象：`api_keys(team_id)` 列 ＋ 2 索引 ＋ 2 RLS 策略 ⇒ 与 057 声明逐字对应

### 1.2 技术分析

#### 057 当前形态（上游版本）
```sql
-- 实测 9 条语句（去注释后）
ALTER TABLE api_keys ADD COLUMN IF NOT EXISTS team_id bigint REFERENCES teams(id) ON DELETE CASCADE;
CREATE INDEX IF NOT EXISTS idx_api_keys_team_id ON api_keys(team_id);
CREATE INDEX IF NOT EXISTS idx_api_keys_tenant_team ON api_keys(tenant_id, team_id) WHERE team_id IS NOT NULL;
DROP POLICY IF EXISTS api_keys_team_owner_all ON api_keys;
CREATE POLICY api_keys_team_owner_all ON api_keys FOR ALL USING (...);
DROP POLICY IF EXISTS api_keys_team_admin_select ON api_keys;
CREATE POLICY api_keys_team_admin_select ON api_keys FOR SELECT USING (...);
COMMENT ON COLUMN api_keys.team_id IS '团队 ID（可选）：NULL 表示个人 key，非 NULL 表示团队 key';
INSERT INTO schema_migrations (version, applied_at) VALUES ('057', now()) ON CONFLICT (version) DO NOTHING;
```

**无事务包裹的风险**：
1. **中途失败场景**：
   - 若在第 2 条索引创建时失败 ⇒ 列已加、第一索引在、第二索引缺、策略全缺
   - 部署通道「首个失败即停」⇒ 台账不再前进 ⇒ 后续文件全被卡
2. **与 252/392 同型问题**：同一文件多条语句不在事务里 ⇒ 半成品卡点

#### 973 加固版的超集性
逐字证明（归一化后）：
- 上游 057 有的 30 条语句 ⇒ 973 **全部包含**（0 条丢失）
- 973 多出 4 条 ⇒ `BEGIN;` / `SET lock_timeout` / `SET statement_timeout` / `COMMIT;`
- **结论**：973 是 057 的严格超集，加固不减功能

### 1.3 为什么「已闭合」

#### 字节冻结规则与唯一窗口
**规则**：一旦迁移 applied，字节不可改（除非豁免）  
**窗口**：057 在生产 applied 之前，仓内字节可自由修改  
**时间线**：
- L86 合并轮二十二：973 归位 → 057（仓内）
- 2026-11-24 20:5x：生产实测确认 057 已 applied
- **窗口关闭**：生产 applied 后，改 057 字节 → 触发 L23 分叉（已应用迁移的字节修改）

#### P0 本体已不存在
**原 P0 定义**：现役二进制写 `api_keys(..., team_id)` 而生产库无该列 ⇒ 整条统计管线静默丢数  
**当前状态**：
- ✅ 生产库有 `team_id` 列
- ✅ 两条 RLS 策略生效
- ✅ 团队 key 写入路径与统计管线已恢复
- **结论**：P0 本体已闭合，功能面已恢复

### 1.4 遗留与建议

#### 遗留问题
「多语句迁移文件必须事务包裹」这道门仍待做（字节已冻结 ⇒ 只能立门、不能改字节）

#### 建议处置
**方案 A（推荐）**：**维持现状 ＋ 立门防护未来**
- **理由**：
  1. 生产已 applied 且功能正常 ⇒ 改字节无收益、有分叉风险
  2. 057 虽无事务，但已成功应用 ⇒ 历史既成事实
  3. 新门覆盖未来迁移 ⇒ 防止新文件重犯
- **动作**：
  - 仓内 057 保持现状（上游版本）
  - 新增门：`TestMultiStatementMigrationsMustHaveTransaction`
  - 豁免表：登记 057（已 applied 豁免）

**方案 B（不推荐）**：回退到 973 加固版
- **代价**：
  1. 触发 L23 分叉（生产已 applied 057，仓内改成 973 ⇒ 字节不一致）
  2. 需 owner 明确授权改已应用迁移
  3. 生产需手工处理（DROP 重建或豁免）
- **收益**：加固未来重放安全性（但 057 已不会再被重放）
- **结论**：代价 >> 收益

**真实问题**：

- 权威账缺 **306 条** ⇒ 一旦唤醒，会重投数百个「已应用过、但形状已被后来迁移改过」的迁移
- 392 只是**首颗可证明会炸的**，那批其余的今天**没有任何门能覆盖**

### 2.2 风险分层

#### 风险 A：392 本身（已知会炸）
- **触发**：增量部署唤醒 252 通道
- **后果**：中止在第 22 个条目，台账停在 391
- **影响范围**：252 部署通道不可用，需人工介入
- **可预测性**：✅ 已实测确认会炸

#### 风险 B：前置 14 条（未知）
- **触发**：同上，但先于 392
- **后果**：未实测，可能成功可能失败
- **影响范围**：若失败，中止点更早（第 1-21 个之间）
- **可预测性**：❌ 未实测

#### 风险 C：断层 306 条（成片未知）
- **触发**：同上，且前 21 条全部通过
- **后果**：重投已应用迁移，形状已被后续迁移改过 ⇒ 大概率冲突
- **影响范围**：整条部署通道，可能引发数据不一致
- **可预测性**：❌ 无门覆盖，量级 300+ 条

**通用式**：
> 「一个已知会炸的点」很容易掩盖【同一机制下的成片问题】⇒  
> 处置一个已知地雷之前、先量「同一个机制下还有多少个」——否则你修完那一个、下一个还在那儿  
> 量级差异极大（1 颗 vs 313 个）⇒ 这就是「量级」比「单点」重要的场合

### 2.3 处置选项分析

#### 选项 ① 保持沉睡（推荐）
**动作**：
- 252 升级改走**安装器通道**（与现状一致）
- 部署通道维持休眠状态
- 仓内 392 保持现状（不修）

**理由**：
1. **现状已稳定**：252 自 2026-09-12 起走安装器通道，零生产事故
2. **改动成本最低**：零代码变更，零生产写
3. **避开未知风险**：不唤醒 ⇒ 不触发那 313 个迁移重投
4. **投递面分离已是既成事实**：仅部署 26 / 仅安装器 62 ⇒ 两本账不互通

**风险**：
- 部署通道永久废弃 ⇒ 需明确 252 升级策略（走安装器通道）
- 未来若需唤醒，前置工作量不变（仍需处理断层）

**决策要点**：
> **问题不是「修 392 一个文件」，而是「252 的部署通道要不要被唤醒」**

#### 选项 ② 全量干跑（环境/成本轴）
**动作**：
1. 252 同构克隆（需独立环境）
2. 全量重放 415 条迁移
3. 识别所有冲突点（不只 392）
4. 逐个修复 ⇒ 回归测试
5. 生产执行

**代价**：
- **环境成本**：需 252 同构克隆 ⇒ 资源申请 ＋ 数据同步
- **时间成本**：415 条迁移 × 单测 ⇒ 预估数天
- **人力成本**：需专人盯守全量重放
- **风险**：克隆环境与生产差异 ⇒ 干跑通过不等于生产安全

**适用场景**：
- 252 未来必须走部署通道（业务强依赖）
- 有独立测试环境
- 有充足时间窗口

#### 选项 ③ 补账（不推荐）
**动作**：
- 只补 392 一行到 `gateway_db_revision_sequences`
- 或补全 306 条断层

**风险 A**（只补 392）：
- 前置 14 条仍会被重投 ⇒ 未实测能否成功
- 断层 306 条仍在 ⇒ 下次增量部署仍会触发重投

**风险 B**（补全 306）：
- 补账逻辑复杂：需构造 `applied_at` / `content_sha256` / `execution_sha256`
- 生产写操作 ⇒ 需 owner 授权
- **不安全的根本原因**：权威账 47 行无指纹 ⇒ 补的指纹是推测值，不是实际执行的

**结论**：
> 补账治标不治本，且补一行不安全（前置 14 ＋ 断层 306 仍在）

### 2.4 门的覆盖边界

**现有门覆盖**：
- `TestLegacyCrossFaceViewPairsReplayability`：覆盖 legacy 跨面视图对（11 对）
- `TestDeploymentChannelLedgerAccountability`：覆盖通道此刻会重放什么（5 类）

**覆盖边界**：
- ✅ 本门覆盖 392 本身（确定会炸）
- ❌ 不覆盖前置 14 条（重投能否成功未实测）
- ❌ 不覆盖断层 306 条（成片未知风险）

**通用式**：
> **「门全绿」≠「唤醒安全」**  
> 门只覆盖已知类型（如 legacy 跨面视图对），不覆盖那批重投
