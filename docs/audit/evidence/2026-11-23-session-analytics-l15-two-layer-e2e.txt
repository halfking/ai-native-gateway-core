             | 已捕获 api-keys status=500
  ⇒ 结论：探针的 2.5s 等待**不够**（实测落定要 ~6.5s）⇒ 探针是在 **spinner 态**取样
    ⇒ 「既没有表、也没有空态」是因为 DataTable 的 loading 分支**优先于** empty 分支
    ⇒ **这一层是量具时序失效**（不是产品红）。

── 诊断 B：页面自己收到的那份 api-keys 响应 ----------------------------------
  url    = https://llm.itestu.cn/api/admin/session-analytics/user-ranking/kaixuan-1/api-keys?start_date=2026-11-17&end_date=2026-11-23
  status = 500
  body   = {"error":"failed to get user api key usage"}

── 诊断 C：211 现役容器日志（同一时刻）──────────────────────────────────────
  {"msg":"sessionAnalytics: user api key usage failed","owner":"kaixuan-1",
   "error":"ERROR: could not resize shared memory segment \"/PostgreSQL.2842516414\"
            to 4194304 bytes: No space left on device (SQLSTATE 53100)",
   "severity_text":"ERROR","level":"error",
   "version":"2.6.1-a798423f-20261123-211"}
  ⇒ **根因＝PostgreSQL 并行查询申请 DSM 共享内存失败**（SQLSTATE 53100 / 53100 = out of shared memory）
  ⇒ 该端点的 SQL（userAPIKeyUsageSQL：3 个 CTE + GROUP BY + ARRAY_AGG）命中并行计划。

── 诊断 D：211 的 PG 容器 /dev/shm 实测 --------------------------------------
  容器 acc-pg17：
      shm  64.0M  45M used  20M avail  70% use  /dev/shm
      段数 70 个（`ls /dev/shm | wc -l`）
      用量 45M
  对照（同机其它 PG 容器）：64M shm、仅用 1.0M、2 个段 ⇒ 差异只出在 acc-pg17
  ⇒ **与 AGENTS.md 登记的 N11/L3 完全同族**：211 的 acc-pg17 容器 /dev/shm 仅 64MB
    且残留大量 DSM 段；根治需**重建该容器并加大 ShmSize**（owner 决策项，2026-11-20 起挂账）
  ⇒ 同族前例：迁移 994 当年用 `SET max_parallel_workers_per_gather = 0` 显式关并行绕过；
    本端点的 SQL **没有**这道绕过 ⇒ 撞上同一个雷。

── 最终定性（三层分开说，不混）──────────────────────────────────────────────
  ① **量具失效**（本轮已修）：探针等 2.5s < 实际落定 ~6.5s ⇒ 在 spinner 态取样 ⇒ 假红。
  ② **产品红·基础设施**（本轮**只登记，不修**）：PG `/dev/shm` 不足 ⇒ 并行查询 500。
     归属＝N11/L3 owner 决策项（重建容器加大 ShmSize），**非会话分析族代码错、非本轮引入**。
  ③ **产品红·前端错误态吞掉**（本轮**只登记**）：该 tab 自己的 loader（apiKeysLoader）报错时，

     这是上游详情族的口径问题，本轮不擅改（改口径 vs 改断言需裁决）。

  ★★ 通用式：**「端点 500」与「端点返回空」在页面上的默认表现都是「表格区域空着」**
