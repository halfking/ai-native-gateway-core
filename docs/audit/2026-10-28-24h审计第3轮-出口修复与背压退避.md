## 2. 发现一：出口代理结构性不可路由（已修，211 生产实测）

**现象**：网关 ERROR 日志 ~52 条/10min 持续，全部 `executor failed`，
模型集中在 riva/nemotron/llama-guard 族，错误三态：`dispatch: circuit open` /
`pool closed` / `[upstream_down] provider requires egress proxy but none is
available`。

**定位链**：
1. usage_facts 近 2h provider=18 的流量 **100% 是 traffic_class=probe**
   （api_key 175）——风暴全部来自探针，无真实用户流量；
2. provider 18 = nvidia（`integrate.api.nvidia.com`），`egress_profile='proxy'`；
   而 `proxy_subscriptions` = **0 行**、`proxy_nodes` = **0 行** ⇒ 出口代理池
   结构性为空 ⇒ R28-P-1 的 must-proxy 契约让 `EgressProvider.TransportFor`
   必然报错（`upstream/client.go:236`）；
3. **关键反转**：211 宿主机与网关容器**直连** `integrate.api.nvidia.com/v1/models`
   实测 **200 / 0.2s** —— 不可路由不是网络事实，是**配置事实**；
4. provider 18 自 2026-10-12 起 **29,280 条 usage_facts、成功 0**（16 天纯噪声）；
   14 家 catalog 播种的外商全部 `egress_profile='proxy'`，同病但只有 nvidia
   有凭据在产生探针流量。

**修复**：`UPDATE providers SET egress_profile='direct' WHERE id=18`（1 行）。
生效路径：`EgressProvider.policy` 现读 DB、TTL 60s ⇒ 无需重启。

**验证（修复后 75s）**：
- ERROR 从 ~52/10min 降至 ~23/10min，且残全是熔断未复位的衰减尾巴；
- `node_probe_state` 出现**真实上游响应**：`meta/llama-guard-4-12b`
  `last_gateway_ok=t`（网关路径探针成功），幻影模型如实报 `http_404/410`
  （进入既有协议红处置通道），不再有 egress 类错误。

**回滚**：`UPDATE providers SET egress_profile='proxy' WHERE id=18;`
（前置条件：先给 proxy_profile 配置订阅与节点，否则回到纯失败循环。）

**边界（如实记）**：其余 13 家 proxy 出口供应商**未动**——它们无凭据无流量
（静默），直连可达性未实测，不扩大爆炸半径。

## 3. 发现二：outbox 背压固定退避 = 永久锤击（已修，随本轮部署生效）

**现象**：`dispatch failed ... attempts=550 error="ai-session-manager
returned 503 event_retryable"`；outbox_events 积压 3,909 条
`request.completed.v1`（全部 2026-10-28）；近 8 分钟 **28,742 次 dispatch
failed vs 117 次成功**（0.4%/拍）。

**定位链**：
1. 今天上午并入的 319cc1e5e（背压永不 DLQ）语义正确（不再丢合法事件），
   但 `markBackpressure` 用**固定 64s**（`backpressureRetryCap`）；
2. 3,904 条积压 ÷ 64s ≈ **61 req/s** 持续 POST + 每条一个 DB 事务 + 每秒
   ~60 条 WARN，打在一个本就在 503 的 asm 上；
3. asm 侧（兄弟产品，只读审计）：503 = `consumer.Consume` 返回基础设施错误
   （`internal/consumer/http_ingress.go:113` err 分支，非缺口分支）；asm 自己的
   audit sink 在 13:30 UTC 窗口失败过（`audit: write to audit_events failed`），
   现已恢复写通（实测 asm 角色可写 audit_events、近 2h 写入 3,476 行），
   但对网关事件仍大部分拒绝；
4. 成功速率（~880/h）< 事件产生速率（~1400/h）⇒ 积压不降反升。

**修复**（`internal/outbox/dispatcher.go`）：`markBackpressure` 退避改
`backpressureBackoff(attempts) = 8s × 2^(attempts-1)`，封顶 10min；
移位先钳位（老积压 attempts=665 不溢出、首拍落 cap —— 长背压先安静正是
想要的行为）。永不 DLQ 语义不变。新增 `TestBackpressureBackoff_Exponential`
8 例（首拍/翻倍/cap/溢出/防御）。asm 的 `Retry-After: 5` 是单事件地板提示，
不构成对数千积压的重放时间表（注释写明）。

**验证**：`go test ./internal/outbox/` 全绿；生产生效待本轮部署（背压修复
在 1ffdeeeb8，部署后预期稳态压力 61 → ~6.5 req/s）。

## 6. 发现五：全量 Go 测试唯一红 = 测试侧抢跑竞态（已修）

`TestGenericRecovery_CleanFileArchives` 全量并发下偶发 `stat archive/ ENOENT`
（单跑 -count=3 必绿）。根因：`GenericRecovery.execute` 在锁内置
`task.Status="completed"`，**归档 I/O 在锁外之后**；测试观察到 completed 即
断言归档文件存在 ⇒ 高负载下 rename 未落盘。修法：终态等待
`!task.CompletedAt.IsZero()`（CompletedAt 在归档后落，是既有的「真正完成」
信号，recovery.go 同款语义）。产品代码零改动（f4246ef8a）。
