## §0 一句话结论

★★★ **本轮观察到的全部「慢页 / 慢端点」，其主因是本机一个遗留 35 小时 51 分的孤儿压测进程（4 个 `bash stress-gate.sh`，脚本文件与目标目录均已被删除、进程在空转烧 CPU），不是产品缺陷。**
⇒ ★★ 停掉它之后，同一批端点的耗时**塌缩 4~100 倍**（`/api/admin/probe/system-health`
从 **6.2~9.9 s** 降到 **0.06~0.09 s**）。
⇒ ★★★ 而**「浏览器侧 >2 s」本身还有第二层量具假象**：浏览器 resource 的 `duration`
**含浏览器连接排队**（HTTP/1.1 同源并发上限 6，SPA 一次打 20~60 个 XHR）⇒
`/api/routing/resolve?model=…` 浏览器侧读到 **4273~5261 ms**，**服务端直连只要 0.01~0.53 s**。
⇒ ⇒ ★★ 两层假象剥掉之后：**87 个页面里没有一个端点慢；有效页面里 0 个慢页。**

## §2 量具的三次自我修正（本轮方法论主体）

★★ 本轮最值得留下的**不是结论，而是「结论是怎么被推翻三次才站住的」**。

### §2.1 第一次推翻：把「浏览器侧 duration」当成「端点慢」

- **初判**：`/api/routing/resolve?model=glm-5.2` 浏览器侧 **5261 ms** ⇒ 「这个端点慢」。
- **证伪手段**：**服务端直连**（curl，串行 + 6 并发）。
  - 串行：`/api/routing/resolve?model=z-ai%2Fglm-5.3-flash` = **0.22~0.53 s**
  - 6 并发：全部 **1.15~1.33 s** ⇒ **并发并不显著涨延迟** ⇒ 不是服务端排队。
- **结论**：浏览器侧多出来的 ~3 s 是**浏览器自己的连接排队**（HTTP/1.1 同源并发上限 6）。
  ⇒ ★ 页面扫脚本的注释里其实**早就写着**这条（「resource 的 duration 含浏览器连接排队」），
  但**工具没有任何一列能把它分离出来** ⇒ ★★ **「知道有假象」≠「量具能剔掉假象」**。

### §2.2 第二次推翻：把「EXPLAIN 的 4760 ms」当成「稳态规划成本」

- **初判**：`SELECT * FROM v_probe_system_health` 的 `EXPLAIN`（**不带 ANALYZE**）耗时 **4760 ms**
  ⇒ 「规划成本 4.7 s，是真凶」。
- **证伪手段**：**普查全部 76 个视图**的纯规划耗时。
  - ⇒ `v_probe_system_health` 在普查里 **< 11 ms**（不在 Top 22）。
  - ⇒ ★★ **差 400 倍** ⇒ 那 4760 ms 是**首次 catalog / JIT 冷启动**，不是稳态成本。
- ★★ **教训（与 R152「运行时刻 vs 进程启动时刻」同族）**：★ **单次冷测不能当稳态**；
  ★ **「EXPLAIN 很慢」与「执行很慢」是两件事**，必须**分开**测。

### §2.3 第三次推翻：把「`count(*)` 的耗时」当成「视图的执行耗时」

- **初判**：`SELECT count(*) FROM (SELECT * FROM v_probe_system_health) t;` = **2.9~47 ms**
  ⇒ 「legacy 视图不慢」。
- **证伪手段**：直接跑 `SELECT * FROM v_probe_system_health;`（**不包 count**）⇒ 仍然只有 **9~62 ms**。
- ★★ **教训**：★ **包一层 `count(*)` 会让 PG 把未用列全部优化掉** ⇒ 测到的是**假的执行成本**。
  ⇒ ★★ **「SELECT count(*) 很快」不能推出「这个视图很快」**。

### §2.4 第四次（真正的原因）：宿主机 CPU 饱和

- **同窗量具**（★ 本仓纪律：判「是不是负载问题」必须用**宿主机级**量具且**同窗**采样）：
  - `ps -A -o %cpu=` 求和 ≈ **883~961%**
  - `uptime` load average = **421 / 456 / 492**（!!!）
  - PG 侧同窗：`12 个连接 / 1~4 active / 0 lock` ⇒ **不是数据库慢**
- **定位污染源**：`ps` 找到 **4 个 `bash stress-gate.sh /tmp/r85-baseline 20 28`**，
  `etime` = **01-11:51:30**（**35 小时 51 分**），`ppid=1`（launchd ⇒ **孤儿**）。
  ★ ★ 关键旁证：`/tmp/stress-gate.sh` 与 `/tmp/r85-baseline` **都已不存在**、**无子进程**
  ⇒ ★ **bash 在已删除的脚本上空转烧 CPU**。
- ★★ **这解释了为什么 R99 之后每一轮的本地读数都带噪声**（并行会话在 `2155e6730` 里
  独立得出同向结论「过载机器上的负载假红」，并引用 R76 轮 load 474~563；
  ★ 它用「重启机器」清掉了负载，★ **而本轮定位到了具体的元凶**）。

### §5.2.1 ★★ 仓内既有门**当场抓到新脚本的一个真缺陷**（本轮最硬的证据）

★ 第一次跑全量 `scripts/ursmcheck` ⇒ **红了**：

```
--- FAIL: TestPipefailRaceLedgerCoversCandidateSet
    ★ 台账缺少 2 个候选点：
        scripts/audit/api-sweep.sh  9dd57f8689c7  1
        scripts/audit/api-sweep.sh  bce6c13914be  1
    ★ 候选物理行 = 363 / 台账行 = 361
```

★ ★★ **这不是假红，是真缺陷**：本仓的 SIGPIPE 竞态台账门把新脚本里的
`if printf '%s' "${path}" | grep -qiE "${RE}"; then` 列为竞态候选点
⇒ ★★ **`grep -q` 一旦命中就提前退出** ⇒ 写端 `printf` 可能收到 **SIGPIPE(141)**
⇒ ★★ **`set -o pipefail` 会把整条管道判成非零** ⇒ ⇒ **条件可能误判成「不匹配」**
⇒ ★★ ⇒ **SSE 跳过与副作用跳过都可能失效**（被误判成「不匹配」的路径会被真的发出去）。

★ ★★ **修法 = 消除管道，而不是登记成 benign**：
`if [[ "${path}" =~ ${RE} ]]`（bash 原生 POSIX ERE，**语义与 `grep -E` 等价**）
+ `shopt -s nocasematch`（★ 对应 `grep -qi` 的大小写不敏感）⇒ ★★ **没有写端 ⇒ 没有 SIGPIPE**。

★ 修后复验：★ **候选点 2 → 0**；★ `TestPipefailRaceLedgerCoversCandidateSet` ⇒
**候选物理行 361 / 台账行 361** ⇒ **PASS**；★ ★★ **台账一行没改**（⇒ ★ 判定的是**行为**，
不是「新增一行登记」）；★ 行为复验：4 条 SSE 全部跳过、2 条巡检、`rows_written == routes_expected`。
