## 3. 573 的机制（官方跑法 + 克隆重放一致）

**官方跑法首报**（`startup rerun` 阶段）：

```
- rerun:573_drop_request_logs_body_columns.sql :: ERROR:  cannot drop view request_logs_with_current_month because other objects depend on it
```

**克隆重放拿到的完整 DETAIL**（门禁只打首行，这一层是重放才有的）：

```
ERROR:  cannot drop view request_logs_with_current_month because other objects depend on it
DETAIL:  view routing_analytics_source depends on view request_logs_with_current_month
materialized view routing_analytics_7d depends on view routing_analytics_source
materialized view routing_audit_summary_7d depends on view routing_analytics_source
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

⇒ ★★★★ **依赖链比想象的长两层**：canonical 视图 → `routing_analytics_source` → **两个物化视图**
（`routing_analytics_7d` / `routing_audit_summary_7d`）。
⇒ ★★ 这条依赖链**是 890 把 `routing_analytics_source` 换成 canonical 形态之后才有的**
⇒ ⇒ 573 **首遍**跑时它们还不存在 ⇒ DROP 成功；**第二遍**时已存在 ⇒ DROP 被挡。

★ ★★ **★ 为什么不能靠加 `CASCADE` 消掉**（这是本轮最该记住的一条）：
`CASCADE` 会把 canonical 视图 + `routing_analytics_source` + **两个物化视图**一起删掉
⇒ ⇒ 把「重跑失败」升级成「**静默毁掉下游对象**」。
⇒ ⇒ 而 573 随后的 `CREATE VIEW` 在 v1 族退役后本来就建不出来（实测见 §4.3）⇒ ⇒ **CASCADE 是错的方向。**

## 4. ★★★★★ 新机制 [M10]：「第二遍把已退役的族按旧名复活」

### 4.1 机制（一句）

**官方重跑 = baseline 三件套 → 启动链**，而 **`01-schema.sql` 是裸 pgdump 基线**
⇒ ⇒ 它把 v1 族**按旧名**重新建了出来（`request_logs` / `request_logs_hot`）
⇒ ⇒ 链的前段（448/459/532…）再按旧名重建 v1 臂视图
⇒ ⇒ **已退役的 573/603 因此「有对象可动」**
⇒ ⇒ 但那些对象**已被视图依赖** ⇒ ⇒ 它们的 DROP 被挡住。

★ 佐证链：
- `341_hot_table_independence.sql:29` = `CREATE TABLE IF NOT EXISTS request_logs_hot`（**旧名**）
- `448_request_logs_view_routing_attempts.sql:99-101` = `SELECT %s FROM request_logs_hot` / `FROM request_logs`（**旧名**）
- `860_rename_request_logs_family_pending_delete.sql:87,102` = `ALTER TABLE public.request_logs_hot RENAME TO _request_logs_hot` / `public.request_logs → _request_logs`
- ⇒ 重跑末尾 890 再把 `_request_logs*` 删掉 ⇒ **净效果为零**（实测 kept 库里 4 个名字全无）
  ⇒ ★★ **⇒ 第二遍对 v1 族的净效果是零，但中途它把这一族「复活」了一阵。**

### 4.2 ★★ 573 与 603 的报错**不同**，但根因相同

| 文件 | 官方跑法首报 | 被挡住的对象 |
|---|---|---|
| 573 | `cannot drop view request_logs_with_current_month because other objects depend on it` | DROP **视图** |
| 603 | `cannot drop desired object(s) because other objects depend on them` | DROP **列** |

⇒ ★★★★ **⇒ 同一个根因（族被复活 ⇒ 有对象可动 ⇒ 对象已被视图依赖），只是被挡住的对象不同。**
⇒ ⇒ ★★ 所以是一条机制、两个条目，不是两条机制。

### 4.3 ★★ 变体：不重跑 baseline 时，603 的首报**完全不是这句**

克隆重放（**不**跑 baseline 三件套）时，603 的首报是：

```
ERROR:  relation "public.request_logs" does not exist
```

⇒ ★★★★ **⇒ 根因是 `ALTER TABLE … DROP COLUMN IF EXISTS` 的 `IF EXISTS` 只覆盖「列」、不覆盖「表」**
（表本身不存在时照样 42P01）。
⇒ ⇒ 同文件的其余三处**同样实测失败**：
- §B-K 的 10 条 `ADD COLUMN IF NOT EXISTS` ⇒ `relation "public.request_logs_hot" does not exist`
- §L 的 3 条 UPDATE ⇒ 同上
- §M 的存在性自检查 `request_logs_with_current_month_without_customer_id`（已被 890 删除）
  ⇒ `rule 49 §9.2 violation: views broken after schema change: relation … does not exist`

⇒ ⇒ ★★★ **⇒ 登记原因必须引官方跑法的报错原文**（官方跑法才是门禁会看到的那句），
**手工变体另标**。⇒ ★ 这条纪律在本轮差点被违反（第一版登记稿引的是手工变体）。

### 4.4 ★★ 与 [M8] 的方向对比

- **[M8] 向后级联**：上游中止 ⇒ 下游全灭。
- **[M10] 向前依赖**：**上一遍留下的依赖方** ⇒ 挡住本遍的 DROP。

⇒ ★★ 判别动作：**问「依赖方是在本遍之前建的，还是本遍建的」**
⇒ 这决定它属不属于「级联」（随上游修好而自愈）还是「向前依赖」（要单独处理）。

### 5.2 ★★★★ 那 4 条红**不是**「t.Fatal 该改成 t.Skip」

★ ★★ 看守卫的完整结构（`internal/trace/trace_retirement_test.go`、
`admin/request_trace_retirement_test.go`、`domains/streaming/session_retire_fidelity_realdb_test.go`、
`internal/sessionv2mirror/status_fidelity_realdb_test.go`，四处逐字相同）：

```go
dsn := os.Getenv("TRACE_RETIREMENT_TEST_DSN")
if dsn == "" {
    t.Skip("TRACE_RETIREMENT_TEST_DSN not supplied")      // ★ 没配 ⇒ 已经正确地 SKIP

cfg, err := pgxpool.ParseConfig(dsn)
if err != nil {
    t.Fatal("invalid isolated PG configuration")            // DSN 坏了 ⇒ Fatal 正确

    t.Fatal("requires loopback trace_retirement database or explicitly authorized local 54318 schema isolation")
}
```

⇒ ★★★★★ **⇒ 同一个守卫里，「没配」已经用 `t.Skip`，只有「配了但指向不安全的地方」才 `t.Fatal`。**
⇒ ⇒ ★★ **⇒ 那个 `t.Fatal` 是**安全拒绝**，不是「跑不起来」**：
它拒绝把破坏性的 trace-retirement 清理打到共享库上。
⇒ ⇒ ⇒ ★★ **⇒ 红的原因是「谁给它喂了不该喂的 DSN」，不是「守卫太严」。**

### 5.3 ★★★★ 喂它的是官方 runner 自己

`scripts/audit/run-integration-gate.sh:850`（本轮**之前**）：

```bash

```

⇒ ★★★★★ **⇒ 官方 runner 把破坏性测试指向了门禁自己的共享库 ⇒ 守卫正确地拒绝 ⇒ 门禁永远红。**

### 5.4 ★★★★ 为什么这条错误配置能活这么久？——「豁免即盲区」

`scripts/ursmcheck/pg_test_env_registry_test.go` 的**差集完备**判据是：

```go
for name, files := range used {
    if _, ok := ds[name]; ok { continue }   // ★★ 事实源承载的 ⇒ 免于被要求登记
    if _, ok := reg[name]; ok { continue }
    missing = append(missing, …)
}
```

⇒ ★★★★★ **⇒ 凡是被事实源导出的名字，永远不会被要求分类** ——
哪怕它**根本不该**在事实源里。
⇒ ⇒ ★★ 真实链条：
1. `TRACE_RETIREMENT_TEST_DSN` 在事实源里 ⇒ ⇒ **免于被分类**；
2. 没分类 ⇒ ⇒ 没人说「它必须专用值」；
3. 于是 runner 把通用库 URL 绑给它；
4. 守卫拒绝 ⇒ 4 条红 ⇒ **门禁永远红**。

⇒ ⇒ ★★★★ **⇒ 通用式：任何「豁免规则」都会变成盲区 ——
豁免必须由「分类」本身给出，而不是由「它恰好在某个清单里」给出。**
