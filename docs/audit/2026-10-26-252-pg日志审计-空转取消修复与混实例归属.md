## §4 慢 SQL 判定

### §4.1 「候选机器」簇的读数是排队伪影，不是结构慢

| 指纹 | n(>1s) | p50 | p95 | 表规模 |
|---|---|---|---|---|
| WITH matched AS MATERIALIZED（provider/client.go:1634）| 1,420 | 1.9s | 7.2s | model_offers **1,962** 行 |
| SELECT COALESCE(cmb.available…nps…（候选可用性）| 601 | 3.1s | 8.8s | bindings **2,007** 行 |
| SELECT c.id FROM credentials…（v1 退役注释版）| 432 | 1.5s | 3.4s | credentials **74** 行 |
| WITH latest_bucket（autoroute/index.go:521 刷新器）| 852 | 3.6s | 17.2s | credential_model_index **458,883** 行 |

- 前三张表都是千行级 ⇒ 全扫亚毫秒 ⇒ 多秒读数只能来自 **4 核 load 23**（uptime 实测）
  下的 CPU/IO 排队——凌晨 00-01 时仍有 12-15 次/时 withmatched 慢线，与本机夜间后台
  作业群（promote/rollup/REFRESH/ursm）共存，与 R153「宿主 CPU 饱和 ⇒ 负载假红」同族。
- **latest_bucket 例外**：458,883 行的 `GROUP BY credential_id, raw_model + MAX(bucket)`
  每 5 分钟一次（bg.AutoIndexRefresher），26min/天，是真实的结构成本；但 CMI 正处于
  R146/R147 存储工作线与 promote/8h 保留语义管理之下，本轮**登记不动**。

## §5 错误 SQL 归属对账

### §5.1 `scheduled_tasks` UPDATE 参数 $4 —— **pocket 库，移交**
- `UPDATE scheduled_tasks SET last_run_at=$1, …, run_count = run_count + $4, …`
  恒定 **12 次/小时**（每 5 分钟一次）× 3 天 = 681 次 ERROR，从不自愈。
- `pg_stat_statements`（llm_gateway 库内查询）→ 同指纹成功调用 130,925 次全部落在
  **`pocket` 数据库** ⇒ 非 llm-gateway-go 代码（本仓 scheduled_tasks 无此写路径）。
- 定性：pocket 侧定时循环对必炸 UPDATE 无限重试（$4 在 `run_count + $4` 处类型不可定）。
- **处置：移交 pocket 属主；本仓不动。**

### §5.2 trace flush 2s 预算击杀 —— 登记不动
- `internal/trace/trace.go` FlushToPG 用 2s runCtx 包住 Redis GET + hot/parent 两面
  UPDATE + stage events + DEL；窗口内 41 次 user_req 击杀（36 集中在 10-24 两个事件窗），
  样本命中 `session_turns` 父表臂。
- 核对：父表 `idx_session_turns_request` valid=true、6 个子索引挂载 ⇒ **不是无索引全扫**；
  击杀 = 载荷 × 负载窗口的偶发。失败路径保留 Redis 供重试（代码自带）。
- **处置：登记。若复发加密，可考虑把 2s 预算只施加于读侧 / 写侧独立预算。**

## §6 修复本体（本仓唯一代码改动）

**改动**：`domains/streaming/model_alternatives.go`
- `ModelAlternativesFinder.db` 字段类型收窄为单方法接口 `alternativesQueryer`
  （`*pgxpool.Pool` 天然满足；构造函数签名与全部调用点零改动）。
- `Find` 入口新增守卫：`ctx.Err() != nil ⇒ 返回空表`，不触碰连接池。

**语义**：客户端已断开时建议列表必然随响应一起被丢弃 ⇒ 空转查询的产出无人消费。
空表本就是 Find 的合法返回（「Never returns an error… degrades to an empty list」），
503 响应体形状不变。

**测试**：`TestFind_DeadContextSkipsQuery`（model_alternatives_test.go）
- ★★ 反证量具是「记录自己是否被调用」的假 queryer（`called` 标志），**不是 pgxmock**：
  第一版用 pgxmock 武装应答行做断言，变异摘守卫仍 ok（pgxmock 对已取消 ctx 自行返回
  错误 ⇒ 守卫缺失也走错误路径返回空表 ⇒ 断言恒绿）——恒绿门在提交前被变异臂当场揭穿。
- **变异 M1**：摘守卫 ⇒ 红，点名 `dead request context must not reach the pool (Query was called)`；
  还原 ⇒ 绿（md5 由备份回拷保证）。
- `go build ./...` ✓；`go test ./domains/streaming/ -count=1` 全包 ✓（150s）。
