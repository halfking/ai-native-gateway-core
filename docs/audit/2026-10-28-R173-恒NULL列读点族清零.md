## §0 一句话

canonical 视图 `request_logs_with_current_month` 的第一列是
`NULL::bigint AS id`（v1 遗留列）⇒ **视图给不出真值**；
仓内登记簿里因此有一类读点被标成「读恒 NULL 列」，并注明
★「这不是『迁移候选』，这是**缺陷**」。

本轮把这一族（**3 个读点**）清零：
`rl.id` ⇒ `rl.request_id`（实测非空、视图内唯一），
死次序键 `ORDER BY …, id` ⇒ 稳定键 `ORDER BY …, request_id`，
并**顺手补上了导出消息的轮次身份**（`ExportMessage.RequestID` 此前从未被赋值）。

## §1 背景：canonical 视图的 `id` 是「恒 NULL 填充列」

### 1.1 视图现在读什么

★ 视图**已经不是** v1 `request_logs` 族了（v1 族已物理退役）⇒ 它是会话族的两臂体：

```sql
FROM session_turns_hot t
     LEFT JOIN session_turn_details_hot d
            ON d.tenant_id::text = t.tenant_id::text
           AND d.request_id = t.request_id
           AND d.partition_date = t.partition_date
UNION ALL
…（同样的形状，母表腿）
```

★ 而它的**第一列**是：

```sql

```

⇒ ★★ **`id` 被视图显式置成了 NULL** ⇒ ★★ 读它就永远读不到真值。

### 1.2 实测（本地真库）

| 项 | 读数 |
|---|---|
| 视图行数 | 2,758 |
| `id IS NULL` 的行 | **2,758 / 2,758**（恒 NULL ✔） |
| `request_id IS NULL` 的行 | **0** |
| `DISTINCT request_id` | **2,758**（唯一 ✔） |

⇒ ★★ **`request_id` 是视图里现成的、实测非空且唯一的稳定键。**

## §3 实测证据

### 3.1 ★★ 死次序键：真库上的排序对照实验

★ ★★ **「`id` 恒 NULL ⇒ 次序键失效」不能靠读代码断言，必须在真库上看排序结果。**

★ 做法（★ 无副作用：用 CTE 构造「同 ts 并列」的输入，★ 且**故意让物理顺序与
`request_id` 字典序相反**，★ 这样两种排序必然给出不同答案）：

| | 顺序 |
|---|---|
| 物理（输入）顺序 | `fffd35…` \| `ffe320…` \| `ffb9a2…` |
| **[改前]** `ORDER BY ts ASC, id ASC` | `fffd35…` \| `ffe320…` \| `ffb9a2…` ⇒ **= 物理顺序** |
| **[改后]** `ORDER BY ts ASC, request_id ASC` | `ffb9a2…` \| `ffe320…` \| `fffd35…` ⇒ **= `request_id` 字典序升序** |

⇒ ⇒ ★★ **改前的第二排序键完全没起作用**（`id` 恒 NULL ⇒ 退化成「只按 `ts` 排」
⇒ 并列行的相对顺序由**物理顺序**决定）⇒ ⇒ **而物理顺序随写入/回收而变
⇒ ⇒ 「取哪一行随机」是真的。★★**

★★ ★★ **★ 第一版实验设计错了（自己抓到并订正）：★★ ★★**
第一版**没把三行的 `ts` 设成相同** ⇒ ⇒ `ORDER BY ts` 已经定了序 ⇒ 第二键根本没参与
⇒ ⇒ 两条 SQL 给出**完全相同**的顺序 ⇒ ★★ **一个「没测到东西」的实验看起来像「测过了」。★★**
★ ★★ ⇒ **★ 教训：★★ 要证明「第二键无效」，输入必须**制造并列**；★★
★★ 否则「结果相同」既可能是「第二键无效」，也可能是「第二键根本没被触发」——
★★ ★★ **★ 这两种解释必须靠【构造并列】区分开。★★**

## §7 本轮通用式（候选，见 `LESSONS.md` §482）

1. ★★★★★ **★ 「结构性缺陷」与「正在发生的故障」是两件事，写结论时必须分开** ——
   本轮修的三个读点，真实数据里「同 ts 并列」实测 **0 组** ⇒ ⇒
   **改前的随机性当前不发作** ⇒ ⇒ ★★ 但诊断是真的（`id` 恒 NULL ⇒ 次序键失效，
   真库对照实验已证实）★★ ⇒ ⇒ ★★ **★ 价值在【结构】：一旦出现并列，行为就分叉了。
   ★★ 「当前不发作」≠「不是缺陷」。★★ ★★
2. ★★★★★ **★ 「要证明第二排序键无效」，输入必须【制造并列】** ——
   ★★ 第一版实验让三行的 `ts` 各不相同 ⇒ ⇒ `ORDER BY ts` 已定序 ⇒ 第二键从未被触发
   ⇒ ⇒ **两条 SQL 结果相同** ⇒ ⇒ ★★ **一个「没测到东西」的实验，长得和一个「测过了」的实验一模一样。★★**
   ⇒ ⇒ ★★ **★ 两种解释（键无效 / 键没被触发）必须靠【构造并列】区分。★★ ★★
3. ★★★★★ **★ 「恒 NULL 列」这类缺陷的正确修法不是【补值】，是【换键】** ——
   ★★ 视图把 `id` 置成了 `NULL::bigint` ⇒ ⇒ 读点无论怎么读都拿不到真值
   ⇒ ⇒ ★★ 只能在读点侧**换成一个视图给得出真值的列**（`request_id`：实测非空、唯一）
   ⇒ ⇒ ★★ ★★ **★ 反过来：★ 「给 `id` 补一个值」（改视图）⇒ 影响 118 列视图的所有读点
   ⇒ ⇒ 风险面大一个数量级 ⇒ ⇒ ★★ **改读点永远比改视图便宜。★★ ★★
4. ★★★★ **★ 编译器会替你抓住「读出来又丢掉」** ——
   ★★ 把 `id` 改名 `requestID` 后，Go 的「declared and not used」立刻要求它被使用
   ⇒ ⇒ ★★ **于是「读出来却丢掉」这个症状在编译期就变成了错误**
   ⇒ ⇒ ★★ ★★ **★ 有些缺陷可以用【改名】而不是【加检查】来根治。★★ ★★
5. ★★★★ **★ 门要同时查【登记簿】与【源码实测】两侧** ——

   ⇒ ⇒ ★★ ⇒ **两侧都查**（本轮判据 ① 走实测、判据 ② 走登记簿）
