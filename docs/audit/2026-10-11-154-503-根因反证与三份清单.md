## 〇、结论先行

任务书给的假设是「根因=上游凭据/节点大量不可路由，属模型目录漂移，待拍板清退/修目录/降权重」。

**路由器不记录理由、因而至今无法归因**的 no_candidate。

|---|---|---|

### 1.2 本轮踩到的四个口径坑（务必写进后续任何统计）

1. **`error_kind IS NULL` 被 `NOT LIKE` 静默丢弃。** 成功请求的 `error_kind` 是 NULL，
   而 `NULL NOT LIKE 'probe_direct%'` 求值为 NULL（不是 TRUE），这些行会被 `WHERE` 过滤掉。
   第一次写这条查询时得到「1865 请求、成功率 0.0%」的荒谬结果——**成功请求被整批吞掉**。
   必须写成 `coalesce(error_kind,'') not like ...`。
2. **`error_kind IS NULL` ≠ 成功。** 锚点窗口内有 12 条 `success=false` 但 `error_kind`、
   `failure_stage`、`failure_detail_code` 三者全 NULL 的失败。按 `error_kind` 分组算比率
   会静默漏掉它们；算成功率必须以 `success` 列为准。
3. **`no_candidate` 与 `no_candidates` 是两个不同的 kind**（141 / 49），
   按 kind 前缀过滤时不要漏掉复数变体。
4. **join 扇出 + 探针混入**。用 `left join node_probe_state on raw_model_name = client_model`
   统计时，一个模型名匹配多行会让每个请求行被复制，`minimax-m3` 的 no_candidate 数
   被放大成 **378**（锚点窗口实际 `no_candidate` 总数只有 141）。必须 `count(distinct r.id)`。
   另：探针流量混在 `request_logs` 里，滑动窗口测得占总量 44%，不算剔除会得出 26.4%。

## 四、最大的一块：无法归因（需改代码，非数据问题）

C 类的典型样本 `minimax-m3`（54 次 no_candidate，占 6h no_candidate 的 39%）：

| label | availability | circuit | 探针 ok | 过期 | 绑定 |
|---|---|---|---|---|---|
| demo-tokenplan | ready | closed | **true** | 否 | 100 并发 |
| glm-5.2-new | ready | closed | **true** | 否 | 12 并发 |
| glm-5.2 | ready | closed | false | 10-12 | 10 并发 |

| augest / sp1-2 | **suspended** | closed | true | 否 | — |
| lj-minimax-free | **auth_failed** | closed | false | 10-12 | — |

存在**两个完全健康、circuit 关闭、探针 ok、未过期、并发额度充足**的绑定
（demo-tokenplan、glm-5.2-new），却仍然 54 次选不出候选。

**为什么至今查不出来**：`routing_decision_log_hot.decision_trace` 在锚点窗口的 887 行里有
**828 行为空（93.3%）**，no_candidate 的行 `decision_trace` 就是 `{}`。
路由器**没有把「为什么没候选」写下来**，所以这一类失败从数据侧不可归因。
`resolution_path` / `canonical_model` 虽有相当比例的行非空，但**没有候选过滤阶段的逐项淘汰记录**
（记录了"选了谁"，没记录"排除了谁、为什么排除"）。

⇒ 这是本轮唯一指向**需要改代码**的发现（补结构化淘汰日志），属数据层修不动的部分。

## 五、对任务书原假设的反证（逐条留证）

| 原判断 | 反证 |
|---|---|
| 「node_probe_state 553/755 `last_direct_ok=false` ⇒ 大量凭据不可路由」 | 锚点实测 556/752。但 `nvidia-build-new`（94/96 探针失败）与 `nvidia-build-v2`（91/92 失败）6h 承载 393+377=**770** 次请求，成功率 84.0%/86.2%——**探针大面积红 ≠ 凭据不可用**，它们是当前主力 |
| 「12 凭据、96 模型名 404/410 ⇒ 该清退」 | 288 个 404/410 绑定上只落 **7** 次成功流量（1624 次成功中的 0.4%），清退收益≈0；而 blanket 清退会误伤主力凭据的健康绑定 |
| 「降权 nvidia 系」 | nvidia 两凭据是成功率最高的一档（84–86%），降权把失败推给更少的凭据，净掉量 |
| 「根因是模型目录漂移」 | 目录漂移影响 ~214 次/6h，在 3478 用户请求中占 6%；最大失败桶是无效 key（1266），其次是欠费凭据触发的 no_candidate 与 nvidia 系上游不稳（transient/provider_error ~287） |

### 5.1 一刀切清退为什么不安全（本次最硬的量化论据）

用 `EXISTS`（无扇出）统计锚点窗口内 1624 次成功请求：

| 成功请求落在哪类绑定上 | 次数 | 占比 |
|---|---:|---:|
| 探针 `last_direct_ok=true`（健康） | 1327 | 81.7% |
| 探针失败但错误码是 `upstream_down`/`400`/`503` 等**抖动** | **290** | **17.9%** |
| 探针失败且错误码是 `404`/`410`（**硬失效**） | **7** | **0.4%** |

即：探针标红≠绑定死亡。**18.3% 的成功流量跑在"探针标红"的绑定上，其中 97.6%（290/297）
是抖动而非失效**。按 `last_direct_ok=false` 一刀切清退，会直接打掉 290 次成功。
真正硬失效的只有 7 次——**清退硬失效项风险极低，但收益同样极低**。

（5.1 节的 1327/290/7 已经是这一点的严格版本，旧版按 error_code 分组的加总口径
有 join 扇出，已废弃。）

## 六、复现用查询（固定锚点，逐条可复现）

所有查询用同一锚点窗口 `$A`。**建议用 heredoc 传 SQL**：多层 shell 引号嵌套会把
`'anthropic'` 这类字面量传错，本轮就因此把 `request_mode` 的值误读成了 `client_profile`，
用 stdin 传参可彻底规避。

```bash
DSN=$(ssh 245 "grep '^LLM_GATEWAY_DATABASE_URL=' /etc/llm-gateway-go/env")
A="ts > '2026-10-11 16:35:00+08' and ts <= '2026-10-11 22:35:00+08'"

# ① 口径修正（注意 coalesce：NULL 不参与 NOT LIKE，会静默丢掉成功行）
ssh 245 "psql \"\$(grep '^LLM_GATEWAY_DATABASE_URL=' /etc/llm-gateway-go/env | xargs)\" -A -F'|'"
#   <<'SQL' ... where $A and coalesce(error_kind,'') not like 'probe_direct%'
#        and coalesce(error_kind,'') <> 'invalid_key'; SQL
# 实测 2212 / 593 / 73.2      ← 真实路由成功率

# ② 未分类失败（12 条）
select success, count(*) from request_logs_hot where $A and error_kind is null group by 1;
-- 实测 success=t:1620 / success=f:12

# ③ 22 个失效凭据
select label, health_checked_at, health_error from credentials
where status='active' and availability_state='auth_failed' order by health_error;
-- 实测 22 行，其中 ok6h=0 的 18 行

# ④ 目录缺口（权威口径）
select client_model, count(*) from routing_decision_log_hot
where $A and failure_detail_code='model_not_found' group by 1 order by 2 desc;
-- 实测合计 214

# ⑤ 路由器可归因性
select count(*) rows,
  count(*) filter (where decision_trace is null or decision_trace='{}'::jsonb) empty_trace
from routing_decision_log_hot where $A;
-- 实测 887 / 828（93.3%）
```
