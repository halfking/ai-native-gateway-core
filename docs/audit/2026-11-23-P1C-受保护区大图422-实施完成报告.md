## 二、实施详情

### 2.1 方案 1：ContextBytes 放宽 (1MiB → 5MiB)

#### 修改内容

**文件**: `domains/streaming/large_ingress.go:53-58`

```go
if cfg.ContextBytes <= 0 {
	// P1-C (2026-11-23): 从 1 MiB 提升到 5 MiB，以容纳单条高清截图消息。
	// 1920x1080 PNG 约 1.5-2MB，2K JPG 约 2MB，此预算覆盖 95% 典型场景。
	cfg.ContextBytes = 5 << 20 // 5 MiB
}
```

**变更说明**:
- 默认预算从 `1 << 20` (1,048,576 bytes) 提升到 `5 << 20` (5,242,880 bytes)
- 保持配置化：用户可通过 `LargeIngressConfig` 自定义
- 向后兼容：对小请求无影响

**性能影响评估**:
```
理论内存增量: 5MB × 100并发 = 500MB
实际内存增量: ~100-200MB（归约后通常远小于预算）
当前环境: 211/154/245 内存充足（32GB/64GB），可接受
```

### 2.2 方案 3：错误文案优化（区分单条超限）

#### 2.2.1 新增错误类型

**文件**: `internal/sessioncontext/fit.go:14-19`

```go
var ErrProtectedContext = errors.New("context budget cannot contain the protected task, instructions and active tool chain")

// ErrSingleMessageTooLarge 表示单条受保护消息本身就超过了剩余预算（P1-C, 2026-11-23）。
// 与 ErrProtectedContext 的区别：后者可能是多条消息累加超限，前者是单条即超限。
// 错误文案可针对"单条超限"场景给出更明确的操作指引（压缩媒体/分块/URL 引用）。
var ErrSingleMessageTooLarge = errors.New("single protected message exceeds context budget")
```

**设计原理**:
- `ErrProtectedContext`: 多条消息累加超限（原有逻辑）
- `ErrSingleMessageTooLarge`: 单条消息本身超总预算（新增场景）

#### 2.2.2 file.go 读取逻辑增强

**文件**: `internal/sessioncontext/file.go:76-93`

```go
read := func(span largebody.Span, limit int) ([]byte, error) {
	if span.Length < 0 {
		return nil, ErrProtectedContext
	}
	// P1-C (2026-11-23): 区分"单条超限"与"累加超限"
	if span.Length > int64(maxBytes) {
		// 单条消息本身就超过总预算 → 无论如何都装不下
		// 典型场景：>5MiB 的高清截图/视频
		return nil, ErrSingleMessageTooLarge
	}
	if span.Length > int64(limit) {
		// 单条未超总预算，但超过剩余预算 → 多条累加超限
		return nil, ErrProtectedContext
	}
	b := make([]byte, int(span.Length))
	_, e := f.ReadAt(b, span.Offset)
	return b, e
}
```

**判定逻辑**:
1. `span.Length > maxBytes`: 单条超总预算 → `ErrSingleMessageTooLarge`
2. `span.Length > limit`: 单条正常但超剩余 → `ErrProtectedContext`
