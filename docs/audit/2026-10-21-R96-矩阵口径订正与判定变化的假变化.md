## 1. 独立复核：官方门到底是怎么算的

并行会话说「官方门是**文件级 × 注释感知**」。我逐个函数读过 `scripts/ursmcheck/datasource_env_test.go`：

| 函数 | 位置 | 口径 |
|---|---|---|
| `stripGoComments(src)` | :138 | 剥 `//` 与 `/* */`，**字符串字面量感知**，**保留行数**（注释用空格替换） |
| `goStringLiteralValues(src)` | :216 | 走一遍源码取**每个字符串字面量的完整值**，**自带跳注释** |
| `dsnNameLiterals(src)` | :283 | 全部**大写**字面量（含 `const x = "NAME"` 形式）＋ 须含 `DSN` 或以 `_URL` 结尾 |
| `opensPostgresConn(src)` | :303 | `rePGConnector` 匹配 `stripGoComments(src)`；`rePGConnector = pgxpool\.New|pgx\.Connect|pgxpool\.Connect|sql\.Open\(\s*"postgres` |

⇒ **★ 结论：官方门的文件级粒度是设计正确的**（分类轴 = 「这个文件是否打开 PG 连接」，
而不是「名字长得像不像 DSN」）。
⇒ ⇒ **有洞的只有我的矩阵脚本**（它用的是 `grep -rl <名字>`：文本里出现就算，且不要求开 PG）。

## 3. ★★★ 我自己探针出的真 bug（本轮最重要的一条自我订正）

### 3.1 现象

我上一轮（R96 前半）用 `/tmp/r96probe` 的临时探针量到 **D = 19 文件 / 71 函数**，
而并行会话报的是 **21 / 75**。两者的树**逐字相同**
（`git diff --name-only 9e7a9242e 99601adaf -- '*_test.go'` 为空；`99601adaf` 是纯文档提交），
⇒ ⇒ **同一棵树、同一批变量、同一套官方函数 ⇒ 不可能给出不同答案 ⇒ 必有一个量具坏了。**

### 3.2 根因（实测钉死）

旧探针用**从脚本文本里解析**的方式拿变量名：

```go
for _, line := range strings.Split(string(raw), "\n") {
    if strings.HasPrefix(line, "MISSING_VARS=") {
        names = strings.Fields(strings.TrimPrefix(line, "MISSING_VARS="))
    }
}
```

而脚本里那一行是：

```bash
MISSING_VARS="BOOTSTRAP_TEST_DSN D07_S01_ADMIN_URL … TEST_RETIREMENT_HTTP_DSN"
```

⇒ `TrimPrefix` 只去掉 `MISSING_VARS=`，**引号还在** ⇒ `strings.Fields` 之后：

| 位置 | 得到的名字 | 后果 |
|---|---|---|
| 第 1 个 | `"BOOTSTRAP_TEST_DSN`（**带前引号**） | 与 `dsnNameLiterals` 返回的**值**（`BOOTSTRAP_TEST_DSN`，无引号）**永不相等** ⇒ 该名字**命中 0 个文件** |
| 末个 | `TEST_RETIREMENT_HTTP_DSN"`（**带后引号**） | 同上 ⇒ **命中 0 个文件** |

⇒ ★★ **实测证据**（把探针改成打印解析结果）：

```
NAME[0]="\"BOOTSTRAP_TEST_DSN"
NAME[1]="D07_S01_ADMIN_URL"
```

⇒ 被这两个名字漏掉的文件正是 `db/omnifree_bootstrap_test.go`（读 `BOOTSTRAP_TEST_DSN`）
与 `admin/session_retirement_http_test.go`（读 `TEST_RETIREMENT_HTTP_DSN`）
⇒ **2 个文件 / 4 个函数** ⇒ **19/71 → 21/75**，与并行会话**逐字吻合**。

### 3.3 为什么这么危险

- ★ **那个错数「19/71」看起来完全合理** —— 没有一处会报警；
- ★ **口径 A 恰好不受影响**（A 是「文本包含子串」⇒ 带引号的名字仍是源码里 `"BOOTSTRAP_TEST_DSN"` 的**子串**）
  ⇒ ⇒ **A 与 D 同时用同一份错名字，却只有一个偏** ⇒ 极易误判成「口径差异」；
- ⇒ ⇒ **「从文本里解析常量」是 bug 温床**：首个/末个 token 必然吃到引号。

### 3.4 修法（三层，缺一不可）

1. **名字从环境变量传入**（`MATRIX_SCOPE_NAMES`）⇒ 不再解析脚本文本；
2. ★★ **名字必须过形态闸门**：`^[A-Z][A-Z0-9_]*$`（与官方门 `reRSNNameValue` **同源**）
   ⇒ 带引号 / 带空格 / 带小写的名字在**出读数之前**就 `t.Fatalf` 中止；
3. ★ **每个名字的命中文件数逐条打出来**（`PROBE-NAME`）⇒
   **「某个名字命中 0 个文件」必须一眼可见**（本轮的 bug 正好藏在这里）。

⇒ ★★ **通用式：★ 判据的输入若是「从文本里解析出来的常量」，就必须在解析后再过一遍形态闸门；
否则「解析成功」与「解析正确」会被混为一谈。**

## 4. 「4 条假变化」的成因（订正 3）

### 4.1 证据

- 旧日志 `/tmp/factsource_matrix_out/A1__tests_48h-audit_D07-hot-columnar_stress.log`
  **只有 3 行**：`=== RUN` + 错误文本（2 行）⇒ **无 `--- FAIL:` 行、无 `FAIL` 汇总**；
- 同一轮的 **44 个**其它日志**全部完整**（都有结尾的 `ok `/`FAIL`）⇒ **是个一次性事件**；
- 同包的 B1 档日志 19 行（4 个测试全跑、4 个全红），**错误文本与 A1 同源**
  （`scratch DSN substitution failed … landed on "itgate_factmatrix_b1"`）。

### 4.2 机制（读 Go 框架源码确认，不是猜）

`GOROOT/src/testing/testing.go`：
- 失败测试的**错误文本**由 `root.flushPartial()` 写出；
- `--- FAIL: <name> (<d>)` 由 `t.report()` → `t.flushToParent(...)` 写出；
- ⇒ **这是两次独立的写**。

⇒ ★★ **所以「有错误文本、没有 `--- FAIL:` 行」= 进程恰好在这两次写之间被杀**
⇒ 形状完全对得上（不需要半截写）。

### 4.3 复现实验（关键：排除 env 差异）

用 **A1 的确切 env**（19 个官方变量，DSN 指向一个 `itgate_*` 库）跑同一个包：

```
A1 rc=1  bytes=2833  lines=19  verdict-lines: 4
```

⇒ **4 个测试全跑、4 个 `--- FAIL:`、退出码 1** ⇒ ⇒ **env 差异不是成因**。

同时排除：
- **进程被杀**：不是「被杀」之外的别的机制（见上，两次独立写 ⇒ 杀在中间即为此形）；
- **输出被截断**：脚本是 `> log 2>&1`，无 `head`/`tail`；
- **worktree 代码漂移**：两处提交的该文件**逐字相同**（599 行）；
- **`t.Fatalf` 在 goroutine 里**：`withScratchDB`（:132）内**无 `go` 语句**。

### 4.4 结论

⇒ ★ **成因 = R90 轮跑批时的一次性进程中断**（宿主当时超载），
**不是**口径差异、**不是**代码漂移、**不是**env 差异。
⇒ ⚠ **诚实边界**：**精确的 killer 不可从产物判定**（没有内核/运行时日志留存），
只能定到「进程在两次写之间被杀」这一级。

⇒ ★★ **⇒ 可执行的修法在【读数侧】而不是【被测侧】**：
「某档没跑出这条 verdict」**不是判定**（旧实现 `sx.get(k,"-") != sy.get(k,"-")` 把它算成判定变化）
⇒ ⇒ 聚合必须**三义**（见 §5.3）。

## 5. 矩阵脚本的三处改动

### 5.1 scope 口径 A → D（零漂移）

- 脚本**运行时**往 worktree 里生成 `scripts/ursmcheck/zz_matrix_scope_probe_test.go`，
  探针**同包**（`package ursm_test`）⇒ **可以直接调官方门的未导出函数**
  （`dsnNameLiterals` / `opensPostgresConn` / `stripGoComments`）
  ⇒ ⇒ **官方门改判据，本脚本的口径自动跟着改** ⇒ **不存在副本漂移**；
- 探针**跑完即删**（`trap` 兜底，含 `INT`/`TERM`）；
- ⚠ 探针**刻意不含任何 DSN 名字面量、不含 PG 连接器**
  ⇒ 官方门扫全仓 `_test.go` 时既不会把它算成违规、也不会扰动 `pgFiles` 计数；
- ⚠ 探针**刻意放在 worktree**（不是共享树）⇒ 共享树永远干净。

### 5.2 三道自检（全部**跑在读数之前**，不一致即 `exit 3`）

| # | 自检 | 失败含义 |
|---|---|---|
| ① | 探针**名字形态闸门**（`^[A-Z][A-Z0-9_]*$`） | 名字被解析坏了 ⇒ 口径会静默漏算（**本轮真踩**） |
| ② | **两实现对拍**：Go 走出的「口径 A」必须与 python 文本 grep 走出的「口径 A」**逐字相同** | 两个实现里有一个坏了 |
| ③ | **包含关系**：口径 D 的文件集 ⊆ 口径 A 的文件集 | 探针认了「文本里压根没有那些名字」的文件 ⇒ 探针坏了 |

⇒ 实测：① 触发过（§3）；②③ 绿（`✓ 口径 A 的文件集一致（29 个）` / `✓ D(21) ⊆ A(29)`）。

### 5.3 verdict 聚合三义化

- **判定变化** = **两档都观测到**且 verdict 不同；
- **未观测**（任一档缺 verdict 行）**单列，不计入判定变化**，
  并**附另一档同一条的错误文本**（便于人工判「是不是同一种红」）；
- **每包观测完整性**自检：期望函数数 vs 实测 verdict 数；
- ⚠ **只要存在「未完整观测」的包 ⇒ 打印完整读数后 `exit 3`**
  ⇒ ⇒ **读数不完整时，脚本拒绝把它当结论发布**（而不是打一行需要人脑比对的日志）。

### 5.4 顺带修

- **`$SHAPE_DB（` 的 CJK 变量展开 bug**（潜伏：形态库「复用」分支从未被触发过）
  ⇒ 与并行会话 §19.20.58 ⑫ 修的是同一处 ⇒ **已在 origin/main 上修好，本轮不重复提交**；

### 5.5 ★★★★ 顺带抓到我自己的 R94 量具里的一个真缺陷：`pipefail` + `grep -q` ⇒ 判据随机翻转

- **现象**：同一个量具、同一棵树，**连跑 40 次出现 3 种输出**（28×A / 2×B / 1×C）
  ⇒ **危险候选在 7 与 8 之间漂** ⇒ 差的那一行 = `scripts/deploy-seamless-docker.sh` 的
  **C2（有没有 trap）标志在 1/0 之间翻转**。
- **根因（实测钉死）**：
  - 判据原写法 = `printf '%s' "$body" | grep -qE '…'`；
  - **`grep -q` 命中即退** ⇒ 写端 `printf` 被 **SIGPIPE** 打死；
  - **本脚本 `set -uo pipefail`** ⇒ 整条管道退出码变成 **141（SIGPIPE）** ⇒ `if` **随机地**走错分支；
  - **触发阈值**：写端数据量 **> 管道缓冲（64 KB）** ⇒ 实测该文件剥注释后 **65,937 字节**
    ⇒ **恰好卡在线上** ⇒ ⇒ **「跑一次看着对」完全不能证明没有竞态**（小文件上永远不触发）。
- **修法**：**去掉管道**（`grep -qE '…' <<< "$body"` ⇒ herestring 不产生 SIGPIPE 写端）⇒ 4 处全改。
- **★ 顺带加了一道【读数确定性自检】**（本轮新增的第三道量具自检）：

  | 自检 | 回答什么 |
  |---|---|
  | 候选集非空自检 | 「读数是不是在空集上的恒等式」 |
  | 台账自检（`--verify`） | 「有没有人逐条裁决过」 |
  | ★ **读数确定性自检**（新） | **「同一量具在同一棵树上能不能给出逐字相同的读数」** |

  ⇒ 实现 = 跑两遍比指纹 ⇒ **不等 ⇒ `exit 3` 拒绝出结论** ⇒ 复现：修后连跑 12 次输出**逐字相同**。
- **★ 全仓面已测量（本轮只测不修）**：`set -o pipefail` 且含 `| grep -q` 的脚本 **≈ 100 个 / 240 处**
  ⇒ ⇒ **不修**（多半是别人的文件、改动面巨大、每处都要单独验证语义）
  ⇒ ⇒ **登记为下轮项**（同族：需要「候选集 + 台账 + 逐条裁决」，不能一刀切）。
- **★ 同步了并行会话台账里【我那一行】**：`scripts/ursmcheck/selfcreated_cleanup_quality_ledger.tsv`
  里我那行的 `signal_trap` 因本轮新增 `INT/TERM` trap 而陈旧（`no` ⇒ `yes`）⇒ **该门当场变红**
  ⇒ ⇒ 已按该门自己的判据同步（只改我这一行、其余行逐字不动）⇒ ⇒ 复现：`TestSelfCreatedCleanupQualityLedger` ⇒ **ok**。

### 5.6 ★★★★ 「回收」原来只是**一句声称** ⇒ 改成**可核实**（三态判据）＋ 一处**我自己的归因订正**

- **观察**：脚本第 4 节跑完打印了「DROP `itgate_factmatrix_a1` / `_shape`」，
  但**几分钟后这两个库仍在** ⇒ ⇒ ★★ 我第一反应 =「**回收失败了**」。
- **⇒ 但这个归因是错的**（我自己的两个判据推翻的）：

  | 判据 | 实测 | 结论 |
  |---|---|---|
  | 逐字复现脚本那条 DROP | rc=0，库真没了 | 回收**本身是好的** |
  | 故意让脚本 exit 3 | **EXIT trap 把 3 个库都删了** | trap **是好的** |
  | 那两个库为什么还在 | ⇒ **更可能是并行会话同时在跑同类脚本**（他们当轮主题正是「自建资源回收」）⇒ **回收之后又被建了出来** | ⇒ **不是回收失败** |

  ⇒ ⇒ ★★ **⇒ 订正：真缺陷不是「回收失败」，而是「回收的结果【不可核实】」。**
- **真缺陷（已修）**：原 `cleanup_dbs` 把 stderr 丢掉 + `|| true`
  ⇒ ⇒ **DROP 失败会被完全吞掉**；而第 4 节只 `say "DROP xxx"`
  ⇒ ⇒ **无论删没删掉，输出都一模一样** ⇒ ⇒ 回收是**声称**不是**核实**。
- **修法（三件）**：
  1. **DROP 的真实报错不再被吞**；
  2. **回收后逐个查库核实** ⇒ 还在 ⇒ **报出来 + exit 3**；
  3. ★ **判据三态化**（同 R94 量具的 C5 纪律）：`db_state()` = **存在 / 不存在 / ★查不到**
     ⇒ ★★ **「查不到」≠「不存在」** ⇒ ⇒ **不能算「已回收」**。
- **新模式 `RECLAIM_ONLY=1`**：只做「回收 + 核实」，不建库、不跑读数
  ⇒ ★ **可单独验证「回收」这条路径本身**（否则它只在大跑批末尾被执行一次 ⇒ 平时测不到失败分支）。

  | 场景 | 实测输出 | 退出码 |
