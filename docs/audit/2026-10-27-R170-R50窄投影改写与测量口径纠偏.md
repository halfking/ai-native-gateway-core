## §3 ★ 推翻：同一计划形状，44× 的耗时波动

### §3.1 同快照三形态对拍（252，只读，单会话）

| 形态 | Planning | Execution |
|---|---|---|
| ① 视图（bounded 谓词） | 90.753 ms | 661.676 ms |
| ② 窄投影 + 转型 | 8.348 ms | **702.817 ms** |
| ③ 窄投影去转型 | 11.207 ms | 406.370 ms |

★ **视图（661 ms）并不比窄投影（703 ms）快** ⇒ §2 的 12.6× 在这里**不成立**。

### §3.2 生产谓词形态、三轮交错复测（252，只读）

三形态各跑三轮、**交错**（V1,C1,N1,V2,C2,N2,V3,C3,N3），谓词用**生产形态**
（`now() - interval '7 days'`，无上界）：

| 形态 | R1 | R2 | R3 |
|---|---|---|---|
| 视图 | **16,194.686 ms** | 735.207 ms | 816.854 ms |
| 窄投影 + 转型 | 422.931 ms | 989.380 ms | 3,142.849 ms |
| 窄投影去转型 | 524.225 ms | 368.840 ms | 924.606 ms |

★★ **九个执行的计划形状逐项相同**（同一访问路径、同一实际行数、
`session_turns_2026_10` 全部走 `Index Scan … credential_ts` + `Rows Removed by Filter: 1612`、
`session_turn_details_2026_10` 全部走 `Index Scan … tenant_id_request_id_partition_key`，
buffer 计数**全部** `521,376 hit / 0 read`），
但 Execution Time 落在 **368 ms ~ 16,194 ms** ⇒ **44× 波动**。

⇒★★ **结论一：252 上的单次执行耗时不能用来比较查询形态。**
   §2 的「15,576.913 ms vs 1,238.901 ms」是**一个慢样本 vs 一个快样本**，
   两者**计划形状不同**（慢的那个走 `Parallel Bitmap Heap Scan`），
   而**形态差异不是主因**（三轮里三个形态都走过同一套访问路径）。

⇒★★ **结论二：「视图 118 列 ⇒ 每行物化 118 列」这个前提是错的。**
   PostgreSQL 会**内联**视图并**裁剪**未被引用的列（`remove_unused_subquery_outputs`）⇒
   只取 1 列时视图并不物化 118 列 ⇒
   **证据（计划代价，确定性量，不受 IO 噪声影响）**：
   视图 `GroupAggregate (cost=2026.88..2027.14)` vs 窄投影 `(cost=2025.29..2025.55)`
   ⇒ **几乎相同** ⇒ 规划器眼里两者**等价**。

⇒ **结论三：真实且可复现的收益在「规划」而不是「执行」**：
   视图 Planning **25~91 ms** vs 窄投影 **8~13 ms** ⇒ **3~11×**。
   规划是 CPU 成本、与 IO 噪声无关，且**每次调用都要付**。

## §4 语义边界：三条都必须查过才能下结论

### §4.1 varchar vs text 的尾空格相等（252 实测）

```sql
SELECT ('a'::varchar(255) = 'a '::varchar(255))::text,   -- false
       ('a'::text = 'a '::text)::text,                     -- false
       ('a'::varchar(255) = 'a'::text)::text,             -- true
       ('a'::char(255) = 'a'::char(255))::text;            -- true
```

⇒ ★ **纠正本会话早先的判断**：「PG 里 varchar 比较忽略尾空格」**不成立** ——
只有 `char(n)`（bpchar）忽略尾空格；`varchar` 与 `text` 都是**尾空格敏感**。

⇒ 但**保留 `::text` 转型仍然是对的**，理由换成更硬的一条：
`text` 相等是**字节相等**，`varchar` 相等走**排序规则**（确定性 ICU 排序规则下
可能把规范等价的两种写法判相等）⇒ `d.tenant_id::text = t.tenant_id::text`
是**字节精确**的，且与 canonical 视图的 join 谓词**逐字相同**。
★ 而实测两形态**计划代价相同、buffer 相同** ⇒ **转型是免费的** ⇒ 保守优先。

### §4.2 RLS / 权限等价性（252 实测）

| 对象 | RLS | owner |
|---|---|---|
| `request_logs_with_current_month` | **OFF**（且无 reloptions ⇒ 非 security_invoker） | llm_gateway |
| `session_turns` / `session_turns_hot` | **ON** | llm_gateway |
| `session_turn_details` / `session_turn_details_hot` | **ON** | postgres / llm_gateway |

★ 视图**没有** `security_invoker` ⇒ 读视图时底层表以**视图属主**身份访问；
而 `llm_gateway` 的 `rolbypassrls = t`（**BYPASSRLS**）⇒ **视图读直接绕过 RLS**。

⇒ **等价性成立的条件是「调用角色 = llm_gateway」**。252 上实测：
`pg_stat_activity` 显示 **51 个 client backend 用的是 `llm_gateway`**
（另有 `acc_app` / `kxuser` / `smm` / `memora_worker` 是别的应用）⇒
⇒ 生产应用连接角色就是 `llm_gateway`（BYPASSRLS）⇒
⇒ **视图读与原生直读看到同一批行**。

★ 且这是**既有事实**，不是本轮引入：R168（`admin/credential_monitor.go`）与
R169（`domains/session/v2/turn_writer.go` 写路径）**早已**把读点改成会话族原生两臂。

### §4.3 等价性对拍（252 生产规模，同快照，逐值）

```
view_groups=9 / cast_groups=9 / nocast_groups=9
cast_only_in_cast=0 / cast_only_in_view=0
nocast_only_in_nocast=0 / nocast_only_in_view=0
view_total=14317 = cast_total = nocast_total
top1_view=minimax-m3|6862 = top1_cast
tie_size_view=1 / tie_size_cast=1
```

`ORDER BY count(*) DESC LIMIT 1` 在并列时**本身不确定**（既有性质，不是本轮引入）。

## §11 守卫的第二次加强（★ 由一条**没被抓住的变异臂**逼出来的）

### §11.1 触发

守卫生成后我加了第 8 条臂 **A8 =「产品形态窗口 7d→30d」**，期望它被真库判据抓住
（理由：形状门全绿 ⇒ 只有「产品形态 vs 视图 top-1」那条比对能看见）。
⇒ ★ **实际 PASS —— 门没反应。**

### §11.2 真因（两条，各占一半）

1. ★ **我的比对不成立**：它拿「产品形态的实际产出」与「**手写**的视图形态（写死 7 天窗）」直接比
   ⇒ ⇒ 只有两边**问同一个问题**时才等价 ⇒ ⇒ 口径一变，这个比对**既可能假红也可能假绿**。
2. ★ 而且 A8 本身**不是缺陷**：把窗口从 7 天改成 30 天是**合法的口径变更**
   ⇒ ⇒ 一个「合法变更」被门判红 ⇒ 那就是**假红** ⇒ ⇒ 门不该抓它。

⇒ ⇒ **结论：门没错，是我设计的臂错了**（臂要选**真缺陷**，不是口径变更）；
★ 而门的缺口是真的：**口径没有被钉死** ⇒ ⇒ 于是「口径变了」与「读面不等价」两件事混在一处。

### §11.3 改法：★ 把口径**钉死**在形状门里

判据 2 新增**口径钉**（逐字）：

| 钉住的东西 | 为什么必须钉 |
|---|---|
| `interval '7 days'` | 窗口是「问题」的一部分 |
| `ORDER BY count(*) DESC` | 排序决定「取哪一行」 |
| `LIMIT 1` | 取行数 |

⇒ ⇒ 口径一变 ⇒ **判据 2 先红** ⇒ ⇒ 真库那条比对**永远在同一个问题上** ⇒ ⇒ 不再假红。

### §11.4 ★★ 真库判据补上「直接跑产品形态」那一段（★ 原设计的真缺口）

★ 原判据 3 比的是**手写**的窄投影形态 ⇒ 它证明的是「窄投影这个**想法**与视图等价」，
**没有**证明「生产函数**实际发出的那条 SQL** 与视图等价」⇒ ⇒ 调用点若漂移
（忘了换 helper / 别名写错 / 谓词拼错 / FROM 的别名与 WHERE 不一致），上面两段**照样绿**。

⇒ ⇒ 判据 3 新增第三段：**直接执行 `mostUsedClientModelSQL("n")`**（产品形态本身），
把它的产出与「视图形态的 top-1」比：
- 并列规模 = 1 ⇒ **严格相等**；
- 并列规模 > 1 ⇒ 只要求落在并列集合里（`LIMIT 1` 在并列时**本身不确定**）。

⇒ ★ 本地真库读数：`凭据 1：视图形态 3 组 · 窄投影形态 3 组` /
`产品形态产出 model="glm-5.2"（视图 top 计数 60，并列规模 1）` ⇒ **PASS**。
