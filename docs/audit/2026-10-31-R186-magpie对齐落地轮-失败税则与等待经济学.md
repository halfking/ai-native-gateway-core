## 二、A2 —— 429 累计升级（`domains/credential/ratebackoff.go` 新）

| 判据 | 实现 | 门 |
|---|---|---|
| ① 单次 429 = 3min 不变 | `RateBackoffBase`，n=1 不升级 | `TestRateBackoffFirstHitIsThreeMinutes` |
| ② 连续升级 6/12/24/30 封顶 | `<<min(n-1,4)` + `min(30min)` | `TestRateBackoffEscalates`（6 点序列） |
| ③ 遗忘窗 30min 后回 3min | `RateForget` 计数归零 | `TestRateBackoffForgetWindowResets`（29min 窗内仍升 / 31min 后归零） |
| ④ Retry-After 信任上限 1h | `MaxRateRetryAfter`；**且 vendor 说了等待时长时不消耗计数**（升级退避没有发言权） | `TestRateLimitedCoolingHonorsRetryAfterWithCap` |

**接线**：`writer.go` WriteOnError 的 KindRateLimit 分支改走
`rateLimitedCoolingDuration(RetryAfter, tracker, key)`；同臂的
Concurrent/StreamTimeout/NoAvailableChannel 走原 `coolingDuration` 零变化。
**绑定粒度**键 `RateBackoffKey(cred, model)`（同凭据其它模型不受影响，
`TestRateBackoffIsBindingScoped`）。

**红线**（本轮不动，注释写明）：429 不进断路器（breaker.go Wave 1 A4）；
HALF_OPEN 探针撞 429 不加计数——探针写路径（`SetCredentialUnavailable` /
`writeProtocolCredentialStateOnError` 的 `DispatchAttempt` 分流）不经过
WriteOnError 的 KindRateLimit 分支，结构上豁免。

**载体已知局限**（与 slowrest ② 同款，文件头写明）：计数进程内，
多实例下退避起点偏保守（少罚不会多罚）。v6 §五 A2 首选 Redis 载体
（SETEX 30min），但 Writer 只持 DBQuerier，为行为升级单独引跨域依赖
性价比低于慢启动同款实现——先落地再观测。

## 三、A1 —— quota reset 时长来源链（`writer.go`）

v6 §五 A1 实施要点：coolingDuration 的 KindQuota 分支补「body 词表 reset
时间」来源并写明信任上限 + 来源写进 state_reason_detail。

**现状核对后的真实缺口**（与文档略有出入，如实记）：quota 类的恢复点
**已经**消费 body 词表（`inferQuotaRecoverAt` → `ParseQuotaResetAt` +
5h 窗 + 周/月/零点启发式）；缺口是 ① **Retry-After 在 quota 路径完全不
被消费**（v6 §三 B4 的「落后」点）；② **来源不可观测**（运维看不出
恢复点信了谁）。本轮修的是这两点：

来源链（`inferQuotaRecoveryAtNow`）：
1. **body 词表 reset**（`quotaSourceBodyReset`；信任上限 =
   ParseQuotaResetAt 自带的 maxQuotaResetLead 40d——既有语义不动）；
2. **Retry-After**（`quotaSourceRetryAfter`；**新增消费**，信任上限
   **8d** = `maxQuotaRetryAfterTrust`——对齐文档「词表 8d」口径，
   防单个畸形 header 挂出月度窗口）；
3. **窗口启发式**（`quotaSourceWindowHeuristic` = 既有
   `inferQuotaRecoverAtNow` 整体，行为逐字节不变）。

来源写进 `state_reason_detail` 尾部：`... [recover_source=body_reset]`
（`quotaRecoverySuffix`；500 字符 trim 帽保持；空 detail 保持 nil 语义）。

**门**（`quota_reset_chain_test.go` 7 条）：body 绝对时间戳赢（Retry-After
同场时仍赢）/ 相对时长 / Retry-After 第二级 / 8d 帽（40d header 压到 8d）/
启发式回落（含 5h 窗归来源 3）/ 后缀标记 + trim + nil 三面 /
`inferQuotaRecoverAtNow` 既有行为不变（月度词表回归钉）。

## 五、B2 —— 429 沉底排序（`rate_sink.go` 新）

判据与实现：`RateSink`（判据① 写键 `Mark`）+ planByTier 尾段
`applyRateSinkOrder`（判据② 沉底；sunk 段按时刻升序=**先沉者在前**，
magpie sinkOrder 语义：最早被限流者最先轮到再试）+ TTL 5min 过期
（判据③ 回原序）+ 判据④ quota 不写键（调用面只有 KindRateLimit 进
`MarkRateLimited`——executor_dispatch.go recordDispatchError 接线）。

载体：`RateSinkStore` 接口 + `MemoryRateSink` 进程内默认；Redis 适配器
（gw:sink:{cred}:{model}）按需注入 main——接口面与 StickyRedisStore 同构，

**与 A2 的分工**（文件头写明）：冷却升级管「摘出一段时间」，sink 管
「回来时的顺序」——没有 sink，冷却一过凭据带着与从未失败者相同的 P2C
分数回队首又撞 429。两者互不替代。

**门**（`rate_sink_test.go` 6 条）：写键 / 沉底排序 / TTL 过期回原序 /
nil 接线 no-op / 先沉者在前 / 无信号逐元素一致。

## 六、C1 —— sticky 缓存经济学（`sticky_cache_economics.go` 新）

判据与实现：`recordStickySuccess` 的 L1 多级路径接
`stickyCacheWorthRenewal`——① CacheRead+CacheWrite ≥ **1024**
（magpie cacheWorth）⇒ 正常续期（即便已粘远超半程）；② <1024 且
**TTL 已过半** ⇒ 不续期（cacheCold，让下次自然换号；未过半仍续期——
会话还年轻）；③ **fail-open 矩阵**：Capture nil / cache 字段缺失 /
cache=0 / L1 键查不到 / 绑定指向别的凭据 ⇒ 全部续期（行为与 C1 前
逐字节一致）。

cacheCold 取「TTL 过半」而非 magpie 固定 5m：本仓 L1 TTL 按 model 分档
（10/30/15min…），固定 5m 在 30min 档过早放走；「过半」对每档等价于
「粘住时间已超剩余时间」，与 magpie cacheCold 的经济学意图一致。

**新增访问器** `StickyCache.GetL1BindingAge(l1Key, model, credID)`：
stickyEntry 没有 setAt，年龄从 expiresAt 反推
（elapsed = TTL(model) − (expiresAt − now)）；Redis 镜像无 setAt ⇒
跨实例下年龄不可得 ⇒ 走 fail-open（与 C1 矩阵一致）。

**只拦 L1 多级路径**的理由（注释写明）：L1 = session+model 是 prompt
cache 亲缘的载体；stickyPreserveBinding 保持分支本就不重写绑定；L3 兜底
是 client 级、Policy.TTL 是管理员显式配置（不属经济学范围）。

**门**（`sticky_cache_economics_test.go` 5 条）：大 cache 续期（9min 龄
1100 tokens 仍 true）/ 小 cache 过半放走（6min 龄 100 tokens false）/
小 cache 未过半续期（2min 龄 true）/ fail-open 三面（无 cache 字段 /
nil Capture / 异凭据绑定）/ GetL1BindingAge 三面（found ~3m / 异凭据
not found / 过期 not found / nil 安全）。

## 八、本轮明确没做 / 已知边界（如实记）

1. **A2/B2 的 Redis 载体**：进程内计数/信号（多实例偏保守，与 slowrest
   同款已知局限）。Redis 适配器接口面已留（RateSinkStore），跨实例一致
   性按 211 实测读数再升级。
2. **B2 的 211 量化前置**（v6 原判「先在 211 量化 429→立即重试同一凭据
   的频率，>5% 再落」）：本轮直接落码——理由：接线是 fail-open 的
   （nil = 零变化），落码后 211 只需灌 `Router.RateSink = NewRateSink(nil)`
   一行即生效，量化与生效可并行；未灌线前生产行为零变化。
3. **C1 依赖厂商报缓存的比例**（v6 原判 P2）：CacheRead/CacheWrite 无
   上报 ⇒ fail-open，故默认部署零风险；收益面取决于 Anthropic/OpenAI
   之外的厂商报数比例，先观测 SummaryAsMap 的 cache 字段填充率。
4. **目标文本不动清单**（已论证不必追，本轮未动）：patience 分轮节奏 /
   strict 亲缘 / JS 中间件 / 订阅轮换——v6 §5.4 裁决维持。
5. **routeorder 接线（B3）**：v6 P2 项，不在本轮目标内，未动。
6. **211 部署**：本轮只提交代码；部署与生产读数按惯例留给部署轮。
