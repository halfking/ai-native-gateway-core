## 1. 用户设想的分解

原话：**「将注意力放在最近的任务，在最上层有一个执行的总结摘要信息（每一步的目标与结果），但每一步的详细细节信息放在记忆中，需要时再进行加载」**。

把它拆成 4 个**可判定**的命题（后面逐条对照现状）：

| 编号 | 命题 | 判定标准 |
|---|---|---|
| **P1** | 网关能识别出「一步」 | 有稳定的步边界，且步与存储单元对得上 |
| **P2** | 能为每一步生成「目标与结果」，并**放在上下文最上层** | 索引可生成 + 装配器能把摘要/索引置顶 |
| **P3** | 每一步的**细节**有权威存储，且能**按需**取回 | 按步号可寻址、取回内容与写入时一致 |
| **P4** | 有一个机制决定**「现在要加载哪一步」** | 网关可观测到加载意图 |

★ **P4 是整个方案的关键分水岭**：P1–P3 都是**网关自己能做**的；P4 天然**不属于网关**——网关是代理，它看不到模型「接下来需要第 7 步的细节」这种意图，除非客户端提供表达通道。这决定了落地形态（见 §6）。

## 2. 仓内现状（逐项取证）

### 2.1 P1「步」的识别 —— 有两个粒度，且**都不完全对得上用户的「一步」**

网关的原生粒度是**轮（turn）= 一次 HTTP 请求 = 一次 agent 迭代**，不是「步」。

- 存储侧：`public.session_turns.turn_no`（一轮一号）、`public.session_bodies.turn_no`（`sql/migrations/startup/430_sessions_v2_schema.sql`）。
- 任务级（跨轮）边界由 `domains/hooks/compression/task_analyzer.go` 的 `AnalyzeTasks` 推断，产出 `TaskBoundary{StartIdx, EndIdx, Completed, Description}`。

**★ 缺口 G1（实测）**：`AnalyzeTasks` 的触发词表**全是英文字面量**——

```go
// domains/hooks/compression/task_analyzer.go:65-78
var completionPatterns = []string{
    "done", "completed", "finished",
    "next task", "next question", "next step",
    "that's all", "that is all", "all done",
    "thank you", "thanks", "proceed", "continue with next",
    "move on", "go ahead",
}
var newTaskPatterns = []string{
    "new task", "next task", "another task",
    "now I need", "now I want",
    "first,", "firstly",
    "next,", "next:",
    "another thing",
    "also,", "additionally",
    "what about",
}
```

实测（真实 `AnalyzeTasks` + 中文合成会话，120 步）：**识别 0 个边界，对齐率 0%，覆盖率 0%**；同构造的英文会话：识别 121 个边界 / 真值 120，**对齐 99.2%、覆盖 100%**。

本仓的主要用户与压缩提示词是**中文优先**（`compactionSystemPrompt` 是中文版、英文版是变体）⇒ **「按步分层」在中文语境下当前完全不成立**。

**★ 缺口 G2（构造缺陷）**：`AnalyzeTasks` 的 span 构造是 `[prevSignal+1, signalIdx-1]`（`task_analyzer.go:152-157`）⇒ **触发边界的那条用户消息本身被排除在 span 之外**。bench 的"覆盖率"指标就是为了暴露这一点而设（当前英文侧覆盖率仍为 100%，因为目标消息很短、内容段都在下一段里；但这意味着**目标句本身不在任何一步的 span 内**）。

### 2.2 P2「每一步的目标与结果」+ 置顶 —— **写侧已有，读侧完全没有**

**写侧（已存在）**：

| 资产 | 内容 | 位置 |
|---|---|---|
| `session_request_summaries` | `gw_session_id / request_id / **step_index** / request_summary / response_summary / tool_calls_summary / is_llm_generated` | `sql/migrations/startup/351_session_analytics_tables.sql:63-77` |
| 写入器 | `analysis.RequestSummarizer.SummarizeSession`（幂等，按 `request_id` 跳过） | `domains/analysis/request_summary.go:57-92` |
| 触发 | `sessionanalysis` Hook，PostResponse 阶段、优先级 250、**全异步不阻塞** | `domains/hooks/sessionanalysis/hook.go:100-101` |
| 另有 | `session_turns.title / summary / digest / tools`（逐轮） | `domains/session/v2/turn_writer.go` |

**读侧（★ 缺口 G3 —— 完全没有）**：全仓 `session_request_summaries` 的读取方**只有一个**：

```
admin/session_panorama_handler.go:440:  FROM session_request_summaries WHERE gw_session_id=$1
```

即**运营全景分析页**。**没有任何代码把这份逐步摘要回灌进模型上下文**。⇒ 用户设想的"最上层放一份执行摘要"，**数据早就在库里，只是没人把它端上桌**。

**★ 缺口 G4（语义不够）**：现有 rule 模式摘要不是"目标与结果"，而是**截断**：

```go
// domains/analysis/request_summary.go:96-110
func (r *RequestSummarizer) ruleExtract(row requestLogRow) (reqSummary, resSummary string) {
    reqSummary = truncatePtr(row.RequestPreview, 200)
    resSummary = truncatePtr(row.ResponsePreview, 300)
    ...
}
```

LLM 模式的提示词是「用一句话（30字以内）概括这一步的请求与回复」⇒ 是"问了什么/答了什么"，不是"目标/结果"。实测（bench，120 步）：**按此契约生成的 L0 索引，只有 62.5% 的步保住了关键标识符**（文件路径/错误码/端点）——因为约 1/3 的步，其标识符**只出现在工具输出里**，不在目标句也不在结果句里。

⇒ 对用户方案而言这是**实质缺口**：索引行里没有文件路径，模型就没有理由去重载那一段。

**置顶机制（★ 已存在，可直接复用）**：

```go
// domains/hooks/compression/rebuilder_openai.go:141-146
// Reassemble: A-track system + C-track summary + head (first user) + tail.
merged = append(merged, ret.SystemMessages...)
merged = append(merged, dynCtxRaw...)   // ← 摘要就落在 system 之后 = 最上层
merged = append(merged, headMsgs...)
merged = append(merged, tailMsgs...)
```

装配结果形状 = `[system] [dynamic_context(摘要/索引)] [首条 user] [最近 N 组消息]`。守护测试 `domains/hooks/compression/context_layering_feasibility_test.go` 钉住了这三条：**摘要置顶 / 尾部保留 / 前缀稳定可判**。

★ 好消息：**摘要正文可以是任意多行文本**（守护测试里直接塞了一个多行的"一行一步"索引）⇒ **从"一段总结"升级成"步索引"不需要改装配器**，只改喂进去的内容。

⇒ **「按需只取最近 N 轮」这条路今天就能走通**，守护测试 `domains/session/v2/context_layering_feasibility_test.go` 用 `pgxmock` 跑了真实的 `LoadChain` / `BuildFromDeltas`，验到：取最近 2 轮 ⇒ 恰好 4 条消息、顺序按 `turn_no`、重载内容与写入**逐字节一致**（含 `tool_calls` 结构）。

**★ 缺口 G5（★ 权威存储有生产级缺陷，本方案的地基）**：

```go
// domains/session/v2/session_writer_v2.go:1067
func extractRequestDelta(req *ProcessedRequest, submitMode string) []Message {
```

该函数的**设计意图**是「只存本轮新增」，但仓内自带的 FIXME-14372 / FIXME-14373 记录了它**在生产上被击穿**：

- 差集基准读的是**上一轮压缩后的出站**，不是上一轮客户端完整历史 ⇒ 差集 = 「压缩残留」而非「本轮新增」；
- 生产最常见的一条分支（上一轮 `outbound_body` 在库里是 jsonb 字面量 `'null'`）⇒ **delta = 客户端完整历史**，即**每轮把整份历史重存一遍**；
- 实测（252 共享库，仓内记载）：`request_delta` 合计 **2.63 GB**（占分区 5.09 GB 的 51.6%），而 `response_delta`（≈每轮真实新增）只有 **57.8 MB** ⇒ **delta 是真实新增的 45 倍**；≥10 轮的 220 个会话里 **127 个（57.7%）呈二次方形态**，持有 **747 MB（55.4%）**；
- 行为**刻意未改**，等属主决策（⑭/⑮）。

本轮 bench 把这个差额**复现**了（合成会话，同口径）：

| 步数 | 理想 delta | 生产实际形态 | 放大倍数 | 二次方系数（prod/最终历史） |
|---|---|---|---|---|
| 12 步 / 29 轮 | 43,821 B | 674,796 B | **15.4×** | 14.6× |
| 40 步 / 95 轮 | 223,926 B | 11,069,738 B | **49.4×** | 47.7× |
| 120 步 / 285 轮 | 1,002,025 B | 146,528,689 B | **146.2×** | 142.6× |

⇒ 与仓内生产实测（45×）**同向同量级**。

★ **对本方案的含义**：用户说"每一步的详细细节信息放在记忆中" ⇒ 若"记忆"指 `session_bodies.request_delta`，那么今天它**既不干净（不是增量）也不便宜（二次方）**。**要么先修 delta 语义（属主决策⑭/⑮），要么另建一张干净的按步明细表**——这是落地的**前置条件**，不是可选项。

### 2.4 P4「谁来决定加载哪一步」 —— **网关观察不到 ⇒ 必须由客户端提供通道**

现状的压缩链**没有任何一处**能表达"模型要第 7 步的细节"：

- 4xx 恢复链（`domains/streaming/executors/context_summarize.go:1287-1313`）是**网关自己**决定用哪一档：机械裁剪 → Memora L1 注入 → LLM 摘要；
- Memora L1 注入是**语义检索 top-8**（`context_summarize.go:230`：`e.Memora.Search(ctx, userID, query, 8)`）⇒ 拿回来的是"语义上像的 8 条"，**不是"第 7 步"**；
- 网关没有任何"给模型一个可调用的加载工具"的机制。

⇒ **P4 有三种可落地形态（见 §6），其中只有前两种能让"需要时再加载"真正成立**。

### 2.5 Memora 的能力边界（★ 与用户设想的对位关系）

| 事实 | 证据 |

Memora 的正确角色是**跨会话的语义召回层**（"我以前在别的会话里踩过这个坑"）——它**已经**在做这件事（4xx 恢复链第 1 档、ASM 预热注入）。
**按步寻址的明细层应该是网关自己的 PG**（`session_bodies` / `session_turns`），它已经有 turn_no / request_id / 逐轮正文。

### 2.6 一个必须澄清的同名概念

仓内 `domains/hooks/compression/threetier/` 的「三层」指的是 **raw（原始）/ compressed（压缩后）/ sanitized（脱敏后）** 三档**会话状态缓存**，与用户说的"记忆分层"**不是一回事**：

```go
// domains/hooks/compression/threetier/tiers.go
TierRaw        Tier = iota + 1 // 1: 原始会话（uncompressed body）
TierCompressed                 // 2: 压缩后（after Lite/Caveman/ToolFocused/LLM summary）
TierSanitized                  // 3: 脱敏后（after security/sanitize smart_sani_guard）
```

本文档所说的 L0/L1 是**记忆分层**（索引层 / 明细层），与它无关。落地时命名要区分开，否则会踩"名字已存在"的坑。

## 3. 实测读数（bench）

### 3.1 超窗场景（主读数）

> ★★ **2026-11-10 晚间口径订正（重要）**：本节初版只按 **32,768 token** 一个窗口读数，
> 并据此写下「现状 LLM 摘要仍然超窗 1.34×」的结论。
> **该结论在生产会话窗口（≈200K）下不成立** —— 44,055 token 的摘要装得下 200K；
> 装不下的是**完整历史**（293,510，1.47× 超窗）。
> 真正成立、且更锋利的约束是：**32K 是网关自己做「步边界识别 / 记忆处理」的
> 本地模型的窗口**，而一段扁平摘要（44,055）**连本地模型自己都读不完**。
> 下面按**两个窗口**重列读数；bench 工具本身也已改成双窗口判据
> （`cmd/context-layering-bench/main.go` 的 `Params.Window` / `Params.LocalWindow`），
> 并由 `TestSessionWindowAcceptsLLMSummaryButNotFullHistory` /

### 3.2 三条可下的结论

**结论 1 —— 方案成立的理由不是「装进会话窗口」，而是「让网关自己的识别/记忆处理链在 32K 内能工作」。**

订正前写的是「现状摘要装不进会话窗口、分层装得下」；订正后的事实是：
会话窗口 200K 下**摘要本来就装得下**（44K，占 22%），真正装不下的是
**喂给本地 32K 识别/记忆处理模型的那份表示** —— 一段扁平摘要 44,055 token
**超本地窗口 11,287**，也就是说本地模型**读不完**这份摘要，
它就无法在摘要上做步边界识别与记忆抽取，更谈不上「按步加载细节」。
分层基座 8,861 token 装得下（占 32K 的 27%），且本地窗口内还能再叠加 9 步明细。

根因不变：**现状摘要是与历史长度成正比的一段扁平文本**（12% 压缩比随历史增长），
而索引是**每步一行**（45 token/步，线性且系数极小）。
这条订正把方案的价值从「省会话窗口」搬到了「**让本地处理链真的能跑**」——
后者才是「网关内建一个上下文识别 + 记忆分层加载的智能体」这条需求的前置条件。


**结论 2 —— 「按需加载」这条链今天是通的。**
`TurnReader.LoadChain(lastN)` + `OutboundBuilder.BuildFromDeltas(lastN)` 已经在活跃链路上（`session_compressor` 用它），实测重载内容与写入**逐字节一致**、顺序按 `turn_no`。加载一步的代价 ≈ 1.8K token，可同时持有 9 步。
⇒ **P3 的"机制"不缺，缺的是"决定加载谁"（P4）与"干净的按步存储"（G5）。**

**结论 3 —— 中文语境下「步」当前识别不出来。**
这不是精度问题，是**零**：中文会话里 `AnalyzeTasks` 返回 0 个边界。用户方案的前提"每一步"在中文会话里**没有落地载体**。

### 3.3 bench 的方法学边界（诚实登记）

| 边界 | 说明 |
|---|---|
| 合成会话，非真实流量 | 内容形状仿 agent 循环（user→assistant(tool_calls)→tool 结果），但非真实业务语料；**绝对 token 数不可外推**，可比的是**同构造下三种策略的相对关系** |

## 5. 与「引入 Memora」这个前提的关系

用户的问法是「**如果引入 memora**，我们能否用总结摘要 + 分层加载的技术来处理？」。取证后的回答要**纠正这个前提**：

1. **Memora 不是引入/未引入的问题**——它**已经在仓内且已经接在 4xx 恢复链的第 1 档**（`context_summarize.go:1289`），只是生产默认关闭（G8）。
2. **Memora 不能承担用户设想里的"每一步的细节"**——它是纯向量库，没有 id/step 寻址（G7）。把"每一步的细节"放进 Memora，做不到"需要时**加载第 N 步**"，只能做到"需要时**语义捞 8 条像的**"。
3. **Memora 能承担的**：跨会话的**长期偏好/事实**召回——它已经在做（4xx 恢复链 + ASM 预热注入，后者读的是 ASM 不是 Memora 客户端）。
4. ⇒ **正确的分层职责**：

```
┌─────────────────────────────────────────────────────────┐
│ L0 索引层   每步一行「目标 → 结果」                      │
│             权威源：session_request_summaries（+ 新列）  │
│             形态：随请求注入最上层（置顶机制已有）        │
├─────────────────────────────────────────────────────────┤
│ L1 明细层   每一步的完整正文                             │
│             权威源：public.session_bodies（按 turn_no）  │
│             前置：先修 delta 语义（G5 / 属主决策⑭⑮）    │
│             取回：TurnReader.LoadChain(lastN)（已有）    │
├─────────────────────────────────────────────────────────┤
│ L2 长期层   跨会话的事实/偏好                           │
│             权威源：Memora（向量）/ ASM（预热）          │
│             定位：语义召回，**不做按步寻址**              │
└─────────────────────────────────────────────────────────┘
```

★ 一句话：**Memora 留在 L2；L0/L1 用网关自己的 PG。** 这样既满足用户设想，又不需要给 Memora 造它不具备的寻址能力。

## 6. 落地方案（三形态，按代价排序）

### 形态 A（★ 推荐）：**客户端驱动的按需加载**——网关当"记忆服务器"

- 客户端 agent 增加一个工具（如 `load_step_detail(step_id)`），或复用自己的 todo/plan 机制；
- 工具落到网关的一个轻量端点（`GET /api/system/session-steps/{task_id}/{step_id}`），网关用 `TurnReader` 按 `turn_no` 取回该步正文；
- 网关在**每次请求**把 L0 索引注入最上层（装配器已有，只需把喂进去的内容从"扁平摘要"换成"一行一步的索引"）。

**为什么推荐**：这是唯一能让"**模型决定**要加载哪一步"成立的形态；且它把"注意力放在最近的任务"这件事交给模型自己的工具预算去管，比网关猜要准。

**代价**：需要客户端配合（一个工具 + 一个端点）；需要 L0 索引的读侧（G3）与语义升级（G4）。

### 形态 B：**网关主动预取 + 语义召回**（无客户端改动）

- 网关在每次请求按当前 query 做语义检索，捞回 top-k 步的明细，一并注入；
- 索引仍注入最上层，让模型知道"还有哪些步可以要"。

**代价**：召回是概率性的（G7）；但**零客户端改动**，且 Memora/ASM 已经在做同类事（`memoraprewarm` 的 2KB 有界注入）⇒ 可作为形态 A 的过渡。
★ 注意其已知失效模式：`internal/memoraprewarm` 的注入是**默认关闭**的，且按 `settings/spec_memory_prewarm.go:18` 的描述，它必须与「P1-4 评测门禁（Recall@5 ≥ 0.25 且 nDCG@10 ≥ 90%）」联用放量 ⇒ **仓内已有召回质量门禁的先例**，形态 B 上线应当复用同一门禁。

### 形态 C：**纯网关侧改写**（最省事，但语义最弱）

- 不注入索引，只把 L0 逐步摘要（已有的 `session_request_summaries`）拼成一段"执行摘要"接到现有摘要位。

**代价**：只解决 P2，不解决 P3/P4；收益远小于前两者。**不推荐单独做**，但它是 G3 的最小验证，成本很低。

### 分期建议

| Phase | 内容 | 依赖 | 备注 |
|---|---|---|---|
| **P0-a** | **L0 读侧**：给 `session_request_summaries` 加读路径 + 注入最上层（复用 `RebuildOpenAIAfterSummary`） | G3 | 工作量最小、收益最大；先在形态 C 下验证"索引置顶"不劣化 |

## 8. 给用户的直接回答

> **「如果引入 memora，我们能否使用总结摘要 + 分层加载的技术来处理？」**

**能，但 memora 不是那个东西，而且这个方案的成本比你想的低、收益比你想的高。**

1. **方案本身可行，实测成立。** 在一个 293K token 的会话里（生产会话窗口 ≈200K）：完整历史**装不下**（超 93.5K）；现状第 3 档（LLM 摘要）产出 44K，**在会话窗口里装得下**，但**装不下本地 32K 识别/记忆处理窗口**（超 11.3K）——本地模型读不完它，就无法在其上做步识别与记忆抽取；分层方案（顶层索引 + 最近尾部）只要 8.9K，**本地窗口里还剩 73% 余量**（会话窗口里占 4.4%），按需加载一步再花 1.8K 仍在两个窗口内。根因是分层索引每步只有 ~45 token，而扁平摘要随历史线性膨胀。
   > ★ 这一条在 2026-11-10 晚间做过**口径订正**：初版把「本地处理窗口 32K」当成了「会话窗口」，因而写下「摘要依然超窗 1.34×」——该说法在生产 200K 窗口下不成立，已按双窗口重测并订正（见 §3.1 顶部订正框与 bench 的双窗口断言）。
2. **底座大部分已经在了**：「摘要置顶 + 保留最近」的装配器在活跃链路上（`RebuildOpenAIAfterSummary`）；「按步取回最近 N 轮」也在（`TurnReader.LoadChain(lastN)`），实测重载**逐字节一致**；**逐步摘要的数据早就写在库里了**（`session_request_summaries`）——只是全仓唯一的读方是运营全景页，**没人把它端给模型**。
3. **memora 要降级。** 它是纯向量库：没有 id/step 寻址、没有结构化过滤、客户端连 get-by-id 都没有 ⇒ **它做不到"加载第 N 步的细节"**，只能"语义捞 8 条像的"。而且它生产默认关闭、样例里的 `MEMORA_PROJECT_ID` 和客户端读的 `LLM_GATEWAY_MEMORA_PROJECT_ID` 还对不上。**正确分工：memora 留在 L2（跨会话长期事实），L0 索引层与 L1 明细层用网关自己的 PG。**
4. **真正的三个卡点**（都不是"要不要引入 memora"）：
   - **G1 中文步边界识别 = 0/120** —— 现有识别器全是英文字面量，中文会话根本分不出"步"。**这是前提级缺口**，优先做。
   - **G6 没有"加载意图"通道** —— 网关是代理，看不到模型"我要第 7 步的细节"。要么客户端给工具（形态 A，**推荐**），要么网关猜（形态 B，召回是概率性的）。
   - **G5 明细存储是二次方的** —— `request_delta` 生产上存的是整份历史（实测 45–146×，仓内已登记为等属主拍板）。**要先把地基修平**，否则"细节进记忆"既脏又贵。
5. **建议的第一步**（成本最低、收益最大）：**G3 + G4** —— 把已经在库的逐步摘要读出来、升级成"一行一步的目标与结果、强制保留标识符"，注入最上层。这一步**不需要动 Memora、不需要客户端配合、不需要等 delta 语义**，用现有的置顶装配器就能做，且能立刻验证"索引置顶不劣化"（可沿用 `compression.NeverWorse` 那套守门）。
