## 二、根因一：仓库里混进一个**无法检出的文件**，阻塞全仓同步

### 现象

```
$ git merge --ff-only origin/main
error: invalid path ' if max(max(v)-min(v) for v in d.values())>max(ms)-min(ms) else '
```

`git merge --ff-only` 直接失败 ⇒ 本地无法与远端同步 ⇒ 任何「拉取主分支」的动作都被卡死。
连 `git read-tree origin/main` 也会在同一条路径上失败（`verify_path` 在索引读取阶段就拦）。

### 根因

- **引入提交**：`ba753ddee13c`（2026-10-14 15:17，`docs(runbook): §10.110.27 直接 A/B 掉最后一个可修假设`）
- **文件形态**：**0 字节空文件**（blob `e69de29bb2d1d6434b8b29ae775ad8c2e48c5391` = 空 blob）
- **文件名**：` if max(max(v)-min(v) for v in d.values())>max(ms)-min(ms) else `（含 `>` 与**尾随空格**）
- **成因**：一次 shell 命令里 Python 一行式被 `>` 截断，**后半句成了文件名**：
  ```bash
  python3 -c "... if max(max(v)-min(v) for v in d.values())>max(ms)-min(ms) else ..."   # 未加引号
  ```
  ⇒ shell 把 `>` 当重定向 ⇒ 生成了一个名字是「表达式后半句」的空文件。

### 为什么它在 Windows 上是**硬阻塞**

git 的 `verify_path` 在检出时校验路径合法性：含 `>`（Windows 保留字符）+ 尾随空格的文件名
在 NTFS 上不可表示 ⇒ git **拒绝检出** ⇒ 该文件一旦进入历史，
**任何 Windows 上的 clone/checkout 都会失败**。

### 修法（不在工作树里做）

`read-tree` + `update-index --force-remove` 走不通（路径校验在索引读取阶段就拦）。
改用 `git mktree` 直接构造新根树：

```js
const entries = run(['ls-tree', base]).split('\n').filter(Boolean);
const kept = entries.filter((e) => !e.endsWith('\t' + BAD));
const newTree = run(['mktree'], kept.join('\n') + '\n').trim();
const commit  = run(['commit-tree', newTree, '-p', base, '-m', msg]).trim();
```

**验证**（`git ls-tree -r -z` 精确比对 mode/type/object）：

```
base=origin/main paths=22549
commit=1dcc1213ed9d paths=22548
added=0 removed=1 modified=0
REMOVED: {"path":" if max(max(v)-min(v) for v in d.values())>max(ms)-min(ms) else ",
          "mode":"100644","type":"blob","object":"e69de29bb2d1d6434b8b29ae775ad8c2e48c5391"}
VERIFIED: tree delta == exactly one removed path, zero modifications.
```

⇒ 提交 `1dcc1213ed9d` 已推送到 `origin/main`（`b48082ade612..1dcc1213ed9d`），
之后 `git merge --ff-only origin/main` 一次通过。

### 遗留

- ★ **历史里仍带这个文件名**（`ba753ddee13c` 及其后所有提交）。任何 Windows 上的
  `git clone` 仍会在 checkout 阶段失败 ⇒ **需要 `git filter-repo` 重写历史**才能根治。
  本轮**未做**：重写历史会改变所有后续 SHA，且本仓库多会话共享、推送频繁 ⇒ 风险与属主决策，
  留给下一轮/属主裁决。**在本轮之前的历史上做全量重写需要停摆所有并发会话。**
- ⇒ **新增防复发门**：见 §四 D3。

### 3.3 ⚠ 方法论：`git cherry` 不是「已合入」的可靠判据

本轮实测：`git cherry origin/main <branch>` 对 #1/#4/#5/#6/#7 给出 `+`（未合入），
但 #1/#4/#5 的文件在 main 上**确实存在且是后继版本**；#3/#6/#8/#9 给出 `-`（已合入），
但逐行比对又显示 main 有分支没有的代码。⇒ **两个信号都不足以单独定案**：

- `cherry` 比的是 **patch-id** ⇒ 对「同一改动被重写/演化」会误判为未合入；
- 逐行比对会被「main 已重构成别的写法」误判为缺失。

⇒ **可靠判据 = 路径级 + 内容级双确认**：① 分支改过的每个文件在 main 上是否存在；
② 分支新增的文件在 main 上是否有**同名或改名后**的对应物，且内容是 EXACT / 后继版本。

## 四、根因三：一族跨平台门禁缺陷（Python 编码）—— 本轮修复

### 4.1 现象

`bash scripts/apply-db-revision-sequence_test.sh` 在本机直接崩：

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0x94 in position 7461: illegal multibyte sequence
  File ".../scripts/apply-db-revision-sequence_runtime_test.py", line 20, in <module>
    SOURCE = SCRIPT.read_text()
```

### 4.2 根因（三面）

本机 locale = `cp936`（GBK）。Python 的 `read_text()` / `write_text()` / `subprocess(text=True)`
**缺省编码取自 locale** ⇒ 仓库里大量 UTF-8 中文文件一读就炸：

| 面 | 症状 | 受影响（本轮实测会崩） |
|---|---|---|
| ① **读** | `UnicodeDecodeError` ⇒ 门在**判据之前**就崩 | `apply-db-revision-sequence_runtime_test.py`（读 `apply-db-revision-sequence.sh`）、`tests/deploy_sdk_stdout_test.py`（读 `deploy-local.sh`）、`tests/verify_245_full_heredoc_test.py`（读 `verify-245-full.sh`）、`mutate-autoroute-index-sql-gate.py`（读 `autoroute/index.go`）、`mutate-tuning-view-coordination-gate.py`（读 `bg/tuning_view_refresher.go`）、`mutate-candidate-failure-monitor-classify-gate.py`（读 `bg/candidate_failure_monitor.go`）、`mutate-s4-recorded-cost-skip-gate.py`（读 `bg/routing_health_checker.go` 等 3 个） |
| ② **写** | `write_text()` 把 UTF-8 源码**静默改写成 GBK** ⇒ 门把源码改成乱码 | 同上 4 个 mutate 门（它们会**就地改写 Go 源文件**做变异） |
| ③ **子进程输出** | `subprocess(text=True)` 用 locale 解码 `go test` 的 UTF-8 输出 ⇒ reader 线程抛 `UnicodeDecodeError` ⇒ `r.stdout` 变 `None` ⇒ 门死于 `unsupported operand type(s) for +: 'NoneType' and 'str'` | 同上 4 个 mutate 门 |
| ④ **stdout** | `print()` 输出含「⇒」的中文 ⇒ cp936 编码不了 ⇒ `UnicodeEncodeError` | 同上 4 个 mutate 门 |

### 4.3 仓库已有正确约定，只是**这几处漏了**

`scripts/redact-docs.py`、`scripts/perf/bench_compare.py`、`scripts/sanitize-protocol-matrix.py`
都写了 `encoding="utf-8"` ⇒ 这是**仓库既定规范**，那几处是**遗漏**而非「风格之争」。

### 4.4 修法

- ① 读：`read_text(encoding='utf-8')`
- ② 写：`write_text(..., encoding='utf-8')`（★ **写比读更危险**：读只是崩，写会把源码改成乱码）
- ③ 子进程：`text=True` → `encoding='utf-8', errors='replace'`
- ④ stdout：`sys.stdout.reconfigure(encoding='utf-8')`（UTF-8 locale 下是 no-op ⇒ POSIX 行为不变）

### 4.5 附带发现：两个「环境限制型崩溃」⇒ 改成**显式跳过**

| 门 | 崩溃 | 根因 | 修法 |
|---|---|---|---|
| `apply-db-revision-sequence_runtime_test.py` | `OSError [WinError 1314]` | fixture 用 symlink 造「封闭 PATH」目录；Windows 需 `SeCreateSymbolicLinkPrivilege`；且被测脚本以 `/bin/bash` 绝对路径启动 | 显式跳过。★ **判据用「实测能力」而非平台名**（`_posix_runtime_available()`：探测能否建 symlink + 有无 `/bin/bash`）⇒ 平台名会把「Windows 开发者模式已开」误判成不可跑 |
| `tests/deploy_sdk_stdout_test.py` | `FileNotFoundError` | `subprocess.run(['bash', ...])` 依赖 PATH 里有 `bash`；Windows 的 Git Bash 是 `bash.exe` 且通常不在 PATH | 解析 bash 绝对路径（PATH → `C:\Program Files\Git\bin\bash.exe` → `/bin/bash`） |

★ 并且 `deploy_sdk_stdout_test.py` **本来就是 macOS 专属**：它断言
`/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk`，而 resolver 用 `[[ -d "$base" ]]`
探测真实目录 ⇒ 非 macOS 必然红。**断言逻辑本身已实测为正确**（把 resolver 的两个 base 路径
改写到可创建的临时目录后，stdout 恰是 SDK 路径、trash 日志恰在 stderr）⇒ 门按 macOS 门控。
