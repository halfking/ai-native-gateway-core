## 2. 根因定位（本轮的核心工作）

### 2.1 P0-3 的机制早已存在并已上线

- 提交 `ab871558c`（迁移 953）加了 `models_canonical.featured` 列；
- `bg/model_tier.go` 的 `refresh()` 读取该分支；
- 线上 slot a 日志：`model_tier: featured set refreshed static=45 usage=9`；
- 实测 `routing_policy.featured_models`（36 条）∪ `models_canonical.featured`
  去重后 = 45 ⇒ **canonical 分支在生产生效**。

⇒ P0-3 的实施是**数据侧**动作，不是新写机制代码。

### 2.2 决定性发现：匹配键不一致

| 调用点 | 匹配键 |
|---|---|
| `bg/probe_model_scope.go:91`（scope 门） | `globalIsFeaturedModel(model, "")` ⇒ **只比 raw 名** |
| `bg/probe_service.go:582`（backoff 乘数） | `globalIsFeaturedModel(model, "")` ⇒ **只比 raw 名** |
| `bg/model_tier.go:333`（队列优先级） | `globalIsFeaturedModel(rawModel, "")` ⇒ **只比 raw 名** |
| `bg/model_probe.go:971`（featuredCycle 深探） | `globalIsFeaturedModel(t.RawModel, standardized)` ⇒ 比 raw + standardized |

而 static 集合装载的是**裸名**：
- `routing_policy.featured_models` → 36 条裸名（`glm-5.3-flash`、`minimax-m3`…）；
- `models_canonical.featured` → `canonical_name`（也是裸名）。

**免费供应商的 raw 名形态**（211 实测）：

```
z-ai/glm-5.3-flash          ← 带命名空间前缀
minimaxai/minimax-m3.1-flash ← 带命名空间前缀
codex/gpt-6-sol              ← 带命名空间前缀
01-ai/yi-large               ← 带命名空间前缀
agnes-2.0-flash              ← freellm 是裸名
```

⇒ **裸名 ∩ raw 名 = ∅**（namespaced 形态）⇒ 免费对在 scope 门 / backoff 乘数 /
队列优先级三处**拿不到 featured 待遇** ⇒ 恢复检测仍迟到。

## 3. P0-3 实施（提交 `9ddff8656`）

### 3.1 代码修复（主体）：`bg/model_tier.go`

装载 featured canonical 时**同步展开** `provider_models.raw_model_name` 变体，
裸名与命名空间形态一起进 static 集合：

```sql
SELECT mc.canonical_name, COALESCE(pm.raw_model_name, '')
FROM models_canonical mc
LEFT JOIN provider_models pm ON pm.canonical_id = mc.id
WHERE mc.featured = TRUE AND mc.status = 'active'
```

⇒ 三个门（scope / backoff / 队列优先级）都用 `globalIsFeaturedModel(raw,"")`，
所以**只要 raw 变体进了集合，三处同时生效**，不需要改调用点。

`sql/migrations/startup/956_minimax_m31_flash_featured.sql` —— 标记
`minimax-m3.1-flash` featured。与 953 的关键差别：

1. **只写经真库核对存在的名字**（§2.4 的教训）；
2. **存在性前置守卫**：目标不存在 ⇒ `RAISE EXCEPTION` 中止（不是静默 0 行）；
3. **终态断言**：更新后必须 `featured = TRUE`；
4. **幂等守卫**：`WHERE featured = FALSE`。

★ **分工**：956 只负责"标 canonical"这一半；另一半是 §3.1 的代码改动。
**两者叠加才闭环** —— 只标裸名对 namespaced 免费对零效果。

#### 5.9.2 修法：两个来源合并为**一套统一装载查询**

`bg/model_tier.go` 的 `refresh()` 里，两段独立查询合并为一段：

```sql
WITH feat_names AS (
    SELECT DISTINCT lower(btrim(f)) AS name
    FROM routing_policy, unnest(featured_models) AS f
    WHERE tenant_id = $1 AND btrim(f) <> ''
    UNION
    SELECT DISTINCT lower(btrim(canonical_name)) AS name
    FROM models_canonical
    WHERE featured = TRUE AND status = 'active'
)
SELECT fn.name, COALESCE(pm.raw_model_name, '')
FROM feat_names fn
LEFT JOIN models_canonical mc ON lower(btrim(mc.canonical_name)) = fn.name
LEFT JOIN provider_models pm ON pm.canonical_id = mc.id
```

⇒ ★★ **方向与本轮修复相反**（我们的修复给它们 featured 待遇 = backoff 减半，
watchdog 却把它们按非 featured 拉长）。
⇒ ★ **影响面极小**：`model_probe_state` 真库**仅 6 行**（对照 `node_probe_state` 749 行）。

#### 5.9.11 ★★★ 机制闭环：★ 「为什么恢复迟迟不被感知」的完整链条（含「资格 ≠ 调度」）

`bg/probe_model_scope.go` 的 scope 门：

```go
if globalIsFeaturedModel(model, "") { return true, nil }     // ★ featured ⇒ 直接放行
// 否则回落：automaticProbeRecentUsageExistsSQL(model)          // ★ 要有真实业务流量
```

★ ⇒ **era2 之前**，那 106 个 namespaced 变体：featured 匹配不上（裸名 ∩ raw = ∅）
⇒ 走 usage 回退 ⇒ **冷门免费模型没有业务流量** ⇒ ★★ **根本进不了自动探测范围**
⇒ ★★★ **⇒ 这就是「免费供应商 ~24h 未感知恢复」的完整机制链**：

**scope 门直接放行** + backoff 乘数减半（1800 vs 3600）+ 队列优先级提升 ⇒ **三门同时解锁**。

★★ **但「资格 ≠ 调度」——★ 这是判读收益面时必须分开的两个口径**：

| 口径 | 含义 | era2 实测 |
|---|---|---|
| **资格面**（M6） | 免费在服对里**拿到 featured 待遇**的对数 | **80 / 1060** |
| **行为面**（M3 / M12 / M3b） | 探针**实际去探了**的那些对的行为读数 | 需 24h / 7 天窗口 |

⇒ ★★ 直接实测（211 真库）：那 106 个新覆盖变体在 `node_probe_state` 里**一行都没有**、
近 24h 在 `node_probe_runs` 里**零探测** ⇒ ★ **它们拿到了资格，但泵目前没有理由调度它们**
（无错误证据 ⇒ 泵不挑）⇒ ★★ **这也解释了为什么修复的效果是「渐进的」而不是「立刻的」**：
★ 门只负责**移除障碍**（scope/backoff/队列），**调度由需求信号驱动**。
⇒ ★★ **判读纪律**：★ M6 是**资格面**、不可当"行为已改善"的证据；★ 行为面只认
M3 / M3b / M12 的读数。⇒ ★ 这与本轮开头的爆炸半径分析一致（"58 对从未进入探测调度"）。

#### 5.9.12 ★★ 右删失（censoring）与一个被证伪的假设（★ 度量纪律的又一次兑现）

**① 右删失是实测出来的，不是推出来的**：era2 部署后 1 小时复采 ⇒ 免费面 14 次失败
（13 bare + 1 ns）**0 次已复检**（全部待复检）；而部署前 24h 是 bare 588→564 已复检(96%)、
ns 400→320 已复检(80%)。⇒ ★★ **M12 的 post 段会系统性漏掉「复检慢」的对**
⇒ ★★ **偏差方向对我们有利**（post 会显得比实际更快）⇒ ⇒ ★ **必须披露 + 修正**。

修正方式（已固化进脚本）：

| 指标 | 作用 |
|---|---|
| **M12s**（结算版） | 只取「失败已发生 ≥6h」的事件（复检阶梯上限就是 6h ⇒ 绝大多数已结算）⇒ 剔掉最年轻、最易被删失的那批。★ pre 段读数与 M12 基本一致（ns|not med 360 min）⇒ **pre 基线本身未被删失污染** |
| **M12p**（护栏） | ★ 报**被删失掉的事件数**（失败已 ≥6h 仍无后继探测）⇒ 分布看不到的那部分必须单独报，否则分布被系统性美化 |

**② 一个被证伪的假设（★ 阴性结论也要像缺陷一样复核）**：
「免费供应商迟迟不感知恢复」最自然的假设是「**失败后没人再去探它**」。实测证伪：

| 分组（pre 段，6h 结算） | failures | pending | pending_pct |
|---|---|---|---|
| bare featured | 1128 | 1 | **0.1%** |
| bare 非 featured | 1238 | 27 | 2.2% |
| ns featured | 214 | 4 | 1.9% |
| ns 非 featured | 1176 | 13 | **1.1%** |

⇒ ★★ **pending ≈ 0–2% ⇒ 失败几乎总是会被再探一次** ⇒ ★★ **假设被证伪**。
⇒ ★★★ **真正的机制是「去探了，但阶梯让 ta 等 ~6 小时」**：
M12 实测 **ns 非 featured 的复检间隔中位 = 360 分钟** vs **ns featured = 3 分钟**（20×）
⇒ ★★ **本轮修复的作用点因此更清晰了**：它把 featured 对的复检阶梯**减半**
（backoff 3600s → 1800s，M3b 直接读数）⇒ **缩短「上游好了之后我们多久去看一眼」的节奏**。
⇒ ★★ 这也解释了 §5.9.11 的现象（资格 ≠ 调度）：**资格是前提，节奏才是效果**。
