## 2. 根因定位（本轮的核心工作）

### 2.1 P0-3 的机制早已存在并已上线

- 提交 `ab871558c`（迁移 953）加了 `models_canonical.featured` 列；
- `bg/model_tier.go` 的 `refresh()` 读取该分支；
- 线上 slot a 日志：`model_tier: featured set refreshed static=45 usage=9`；
- 实测 `routing_policy.featured_models`（36 条）∪ `models_canonical.featured`
  去重后 = 45 ⇒ **canonical 分支在生产生效**。

⇒ P0-3 的实施是**数据侧**动作，不是新写机制代码。

### 2.2 决定性发现：匹配键不一致

| 调用点 | 匹配键 |
|---|---|
| `bg/probe_model_scope.go:91`（scope 门） | `globalIsFeaturedModel(model, "")` ⇒ **只比 raw 名** |
| `bg/probe_service.go:582`（backoff 乘数） | `globalIsFeaturedModel(model, "")` ⇒ **只比 raw 名** |
| `bg/model_tier.go:333`（队列优先级） | `globalIsFeaturedModel(rawModel, "")` ⇒ **只比 raw 名** |
| `bg/model_probe.go:971`（featuredCycle 深探） | `globalIsFeaturedModel(t.RawModel, standardized)` ⇒ 比 raw + standardized |

而 static 集合装载的是**裸名**：
- `routing_policy.featured_models` → 36 条裸名（`glm-5.3-flash`、`minimax-m3`…）；
- `models_canonical.featured` → `canonical_name`（也是裸名）。

**免费供应商的 raw 名形态**（211 实测）：

```
z-ai/glm-5.3-flash          ← 带命名空间前缀
minimaxai/minimax-m3.1-flash ← 带命名空间前缀
codex/gpt-6-sol              ← 带命名空间前缀
01-ai/yi-large               ← 带命名空间前缀
agnes-2.0-flash              ← freellm 是裸名
```

⇒ **裸名 ∩ raw 名 = ∅**（namespaced 形态）⇒ 免费对在 scope 门 / backoff 乘数 /
队列优先级三处**拿不到 featured 待遇** ⇒ 恢复检测仍迟到。

## 3. P0-3 实施（提交 `9ddff8656`）

### 3.1 代码修复（主体）：`bg/model_tier.go`

装载 featured canonical 时**同步展开** `provider_models.raw_model_name` 变体，
裸名与命名空间形态一起进 static 集合：

```sql
SELECT mc.canonical_name, COALESCE(pm.raw_model_name, '')
FROM models_canonical mc
LEFT JOIN provider_models pm ON pm.canonical_id = mc.id
WHERE mc.featured = TRUE AND mc.status = 'active'
```

⇒ 三个门（scope / backoff / 队列优先级）都用 `globalIsFeaturedModel(raw,"")`，
所以**只要 raw 变体进了集合，三处同时生效**，不需要改调用点。

`sql/migrations/startup/956_minimax_m31_flash_featured.sql` —— 标记

1. **只写经真库核对存在的名字**（§2.4 的教训）；

4. **幂等守卫**：`WHERE featured = FALSE`。

★ **分工**：956 只负责"标 canonical"这一半；另一半是 §3.1 的代码改动。

#### 5.9.2 修法：两个来源合并为**一套统一装载查询**

`bg/model_tier.go` 的 `refresh()` 里，两段独立查询合并为一段：

```sql
WITH feat_names AS (
    SELECT DISTINCT lower(btrim(f)) AS name
    FROM routing_policy, unnest(featured_models) AS f
    WHERE tenant_id = $1 AND btrim(f) <> ''
    UNION
    SELECT DISTINCT lower(btrim(canonical_name)) AS name
    FROM models_canonical
    WHERE featured = TRUE AND status = 'active'
)
SELECT fn.name, COALESCE(pm.raw_model_name, '')
FROM feat_names fn
LEFT JOIN models_canonical mc ON lower(btrim(mc.canonical_name)) = fn.name
LEFT JOIN provider_models pm ON pm.canonical_id = mc.id
```

#### 5.9.15 ★★★★ 自查抓到：**我自己的度量口径有一个静默丢 70% 事件的缺陷**（★ 本轮最硬的一条方法论）

★ **体检方法（★ 可复用）**：不靠读代码，而是**同一口径写两版做计数对拍** ——
严格版（`provider_model_id = (SELECT pm.id … WHERE pm.raw_model_name = … LIMIT 1)`）
vs 宽松版（`EXISTS`）⇒ 实测 **4,073 vs 13,555** ⇒ ★★ **差 3.3 倍 ⇒ 立刻定位到映射层**。

★ **根因**：`provider_models.raw_model_name` 是**一对多** —— 实测 1560 个名有 1 行、
**441 个名有 2 行**、47 个 3 行、最多 14 行；典型如 `zcode/GLM-5.3` 有 **9 行**
（9 个不同凭据各一行）⇒ ★ `LIMIT 1` 只取**任意一行** ⇒ **另外 8 个凭据的事件全部被丢弃**
⇒ ★★ **丢掉的恰恰是那批"一个 raw 名挂在多个免费凭据上"的热门变体**
⇒ ★★ **也就是本轮最想观测的那批**（`zcode/*`、`codex/*`、`z-ai/*`）。

★ **修法**：改成**半连接（EXISTS）**：
```sql
EXISTS (SELECT 1 FROM credential_model_bindings b JOIN provider_models pm ON pm.id = b.provider_model_id
        WHERE b.credential_id = n.credential_id AND b.billing_mode = 'free'
          AND pm.raw_model_name = n.raw_model_name)
```
⇒ ★ 半连接**不会放大行数**（实测 `(credential_id, raw_model_name)` 每个组合只有 1 个绑定，
4,053 个组合全部 dup=1）⇒ 增加的事件**全是找回的被丢弃事件**。

★★ **修正前后对照（★ 结论方向不变、但数值与判定计划都变了）**：

| 指标 | 修正前 | ★ 修正后 | 影响 |
|---|---|---|---|
| M11 namespaced episodes（7 天） | 17 | **49** | ★★ **样本率 2–3/日 → 7/日 ⇒ Stage 1 从「不可判」变成「可判」** |
| M11 namespaced med / p90 / max | 6 / 511 / **1791** | **3 / 360 / 1791** | ★★ **尾部 1791 分钟（29.9h）不变 ⇒ 症状的定性结论确认**；★ p90 由 511 修正为 360 |
| M11 bare med / p90 / max | 3 / 120 / 360 | 3 / **180** / 360 | — |
| M12s ns featured（n / med / p90） | 210 / 3 / 120 | **394 / 3 / 60** | ★★ **p90 差距由 3× 扩大到 6×**（60 vs 361） |
| M12s ns 非 featured（n / med / p90） | 1178 / 360 / 368 | **1703 / 360 / 361** | ★ 中位 **360 分钟**不变 ⇒ **20× 差距是硬结论** |
| M14 目标人群事件数（7 天） | 92 | **461** | ★★ **目标人群可观测性从「≈14/日」升到「≈66/日」** |
| M15 冷金丝雀 | 3 只 | **4 只**（新增 `z-ai/glm-5.3`） | ★ 逐对样本仍薄（≈1.9/对/日）⇒ 幅度判定留 Stage 2 |

★★ **教训（★ 写给下一个人）**：
① ★ **度量层的缺陷比代码层的缺陷更贵** —— 它不会报错，只会**安静地少报 70% 的事件**，
   而且**恰好少报你最想看的那部分**（多凭据挂载的热门变体）。
② ★ **凡是把「一对多」的映射写成「取代表行」（`LIMIT 1` / `DISTINCT ON` 无序），
   就要立刻做「严格 vs 宽松」计数对拍**。
③ ★ **体检要早**：★ 本次是在**窗口关闭前**抓到的 ⇒ 若留到关窗才发现，
   **pre 基线与 post 观测会建立在不同口径上 ⇒ 整轮结论作废**。
④ ★ **修正 pre 基线是安全的**（pre 段是历史数据，与部署无关）⇒ ★ **但 post 段必须用新口径**，
   ⇒ ★ 所以「修正」动作必须**同时**改脚本 + 改基线 + 改判定器，三处一起。

### 5.9.18 ★★★★★ 窗口关闭前 22.6h 抓到：**判定器自己的解析有一个会让判据恒假的缺陷**

> **时间**：2026-11-10 15:0x +08（era2 切点后 ~1.4h；**窗口满 2026-11-11 13:42:30 +08**）

> **结论**：★★ 抓到**一个真缺陷**——若留到关窗才发现，**Stage 1 会给出一条恒假的 ❌**。

#### 5.9.18.1 缺陷：`p90=` / `p99=` 的**标签里自带数字** ⇒ 按位置取数会把标签当数据

判定器原来用 `re.findall(r"\d+", text)` **按位置**解析 SQL 的 `k=v` 复合值。实测：

```
输入： "394 events | med_min=30 | p90=60 | p99=1200"
findall → [394, 30, **90**, **60**, **99**, 1200]
                    ↑标签   ↑真p90  ↑标签
```

★ `p90=` 与 `p99=` 里的 **90 / 99 本身被当成数字** ⇒ 位置整体错位：

| 指标 | 真实值 | 旧解析读成 | 后果 |
|---|---|---|---|
| M12s `p90` | 60 | **90** | 判据「p90 ≤ 60」⇒ **恒假** |
| M12s `p99` | 1200 | **60**（真 p90） | 判据「p99 ≤ 1791」恒真（更弱） |
| M11 `max` | 1791 | **真 p90** | ★ **max 校验被静默削弱**（实际在比 p90） |

★★ **后果的严重性**：M12s 是本轮**唯一的高样本行为判据**（≈550 事件/日），
它的判据是「post 的 p90/p99 不劣于 pre」⇒ **旧判定器无论真实数据如何，
都会把 M12s 判成「尾部变差」** ⇒ 关窗时会输出**一条恒假的 ❌**，
而这条 ❌ 恰好落在本轮最核心的判据上 ⇒ ★★ **结论会被量具带偏，且带偏的方向是「假红」**。

★ 真库值格式已逐条核对（211 实测）：
M12s 用 `med_min/p90_min/p99_min`、M11b 用 `med/p90/max`、M15 用 `med_min/p90_min/…`、
M12p 用 `pending_pct=` ⇒ ⇒ **两种写法都要认**（`p90` 与 `p90_min`）。

#### 5.9.18.2 修法（判定器加固，6 项）

1. ★ **定点取字段**：`field(text, "p90")` 按字段名取（兼容 `_min` 后缀）+ `head_count(text)` 取行首计数；
   **彻底移除按位置取数**。
2. ★★ **「量具算不出」≠「未达成」**：分位是 `?` 时单列 **「⚠️ 不可判（量具缺数）」**，
   不并入 ❌（否则用一条坏读数把结论判成红的）。
3. ★★ **守卫缺失 = 守卫失败**：原逻辑只看有没有 `★★` ⇒ 指标没产出时**空值被当成通过**
   ⇒ 改为「空值同样判失败 ⇒ 整表作废」。
4. ★★ **基线展示统一从 `BASELINES` 取**（基线值/期望/阈值/单位同处一源）——
   消除「判定器基线显示是硬编码字面量」的脱钩面（§5.9.15 纪律三之三）。
5. ★ **M12p 从「参考行」升级为真判据**：`pending_pct` 定点解析（旧 `ints()` 会把 `0.2` 切成 0 和 2），
   判据「post 待复检率 ≤ pre 1.3%」⇒ ★ **复检不能反而变慢**（护栏有了牙齿）。
6. ★ **键缺失也要出行**：M14 两段、M12p 恒出行；缺键显式报「指标缺失」⇒ **沉默不会被读成「没查」**。
