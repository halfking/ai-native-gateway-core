## 2. 缺陷：启动检查被 full-only 闸门挡住

### 2.1 上游引入

`9aa973e56`（批判审计轮）新增了探测车道的**启动期表存在性检查**：

```go
// cmd/gateway/main.go（上游原样）
if !bgDataPlaneOnly {
    ...
    statsMinuteRollup = bg.NewStatsMinuteRollup(dbConn.Pool())
    statsMinuteRollup.Start(context.Background())
    // 物理车道开启时启动期校验探测族表存在，避免 PersistTurn 全失败却
    // 只打一条 error、下游 hooks 静默不发（12h 审计 §六 P1-3）。
    if err := probelane.AssertWithQueryRow(context.Background(), func(...) probelane.DBRow {
        return dbConn.Pool().QueryRow(ctx, sql, args...)
    }); err != nil {
        slog.Error("probelane lane table check failed", "error", err)
    }
    ...
}
```

检查的目的明确（把静默失败变响亮）：`LLM_GATEWAY_PROBE_LANE_PHYSICAL=1`
且迁移 928 未应用 ⇒ `session_turns_probe_hot` / `request_stats_probe_minute`
缺失 ⇒ `probelane.PersistTurn` 每条探测都失败 ⇒ 只留一条 error 日志 ⇒
下游 hooks（stats / live / mirror）静默不发 ⇒ **探测流量悄悄停止落表**。

### 2.2 为什么闸门挡住的是**真**场景

探测**写路径**的可达性由 `telemetryClient.SetDB(dbConn.Pool())` 决定，
而那处**只看 `dbConn`，不看 `bgDataPlaneOnly`**：

```go
// cmd/gateway/main.go:2667-2669（上游原样，未改）
if dbConn != nil && dbConn.Enabled() {
    telemetryClient.SetDB(dbConn.Pool())
```

⇒ telemetry 落库管线在 data-plane-only 模式下**照样启用**
⇒ `domains/hooks/observability/telemetry/client.go:1352` 与 `:1616`
两处 `probelane.PersistTurn(...)` 在 data-plane 模式下**照样会跑**。

而 `bgDataPlaneOnly`（`cmd/gateway/main.go:3192`）的判定是
`cfg.BGMode == "data-plane" || cfg.IsTrafficOnly()` ⇒ **245 走的就是这条**
（AGENTS.md 记载「245 uses bgDataPlaneOnly=true」）。

⇒ **组合起来**：245 开 flag + 缺迁移 928 ⇒ 探测写路径每条都失败，
而启动检查**一次都不跑**（它在 `!bgDataPlaneOnly` 里）⇒ 运维看不到任何
「车道未就绪」的提示 ⇒ 正是这个检查要防的静默失败面。

### 2.3 AST 实测（修前的祖先链）

修前该调用点的 AST 祖先链（临时探针打印，**不含** `bgDataPlaneOnly` 才合格）：

## 3. 修法

把检查**移到 `!bgDataPlaneOnly` 闸门之外**（仍在
`if dbConn != nil && dbConn.Enabled() && ...` 块内，仍有 `dbConn.Pool() != nil` 守卫）：

- 检查语义不变（flag 关 ⇒ no-op；flag 开 ⇒ 校验两张探测表存在）。
- 位置变化：full 模式照跑；**data-plane 模式现在也跑**。
- 同时把 `cmd/gateway/main.go` 的 import 注释对齐修好（该文件此前
  **不是 gofmt-clean** —— 上游加 `probelane` import 后对齐漂移；
  ★ 仓库整体 11279 个 .go 里 540 个非 gofmt-clean ⇒ **gofmt 不是本仓的门**，
  本轮只修**自己动过的这个文件**，不做全仓改写）。

### 修后 AST 祖先链

```

IfStmt   @5668  cond=err != nil
BlockStmt@5667
IfStmt   @5667  cond=dbConn.Pool() != nil
```

⇒ **祖先链上没有任何 `bgDataPlaneOnly` 引用** ⇒ full 与 data-plane 两种模式都会执行。

## 4. 门禁：AST 判据（不是文本判据）

新增 `cmd/gateway/probelane_boot_check_wiring_guard_test.go`。

★ **为什么用 AST 而不是 `strings.Contains(text, "if !bgDataPlaneOnly")`**：
本仓已有同族先例与**实测过的绕过**——`TestAutoRouteWiringNotGatedOnDataPlaneMode`
的注释明写：自然写法是**反向拼写**
`if bgDataPlaneOnly { } else { <检查> }`，此时**被搜索的那个串根本不出现**，
文本门恒绿而故障照旧（2026-09-09→09-14 autoroute 停摆即此族）。

⇒ 本门改为判 **AST 祖先链**：对调用点的每一层 `IfStmt.Cond` /
`ForStmt.Cond` / `SwitchStmt.Tag` 检查是否引用标识符 `bgDataPlaneOnly`；
反向拼写同样落在 `else` 分支的条件链上 ⇒ 一样被抓住。

门禁同时钉住**另一半**（写路径的 DB 接线 `telemetryClient.SetDB`）：
两处必须**同时**与运行模式无关，否则「检查该跑的地方」与「写路径该跑的地方」
会分叉 ⇒ 耦合悄悄腐化。

### 4.1 变异臂（2/2 检出，CONTROL 绿，还原逐字一致）

| 臂 | 变异内容 | 判据 | 结论 |

**编译失败 ≠ 判据红** —— 按本仓纪律（LESSONS §609 族）必须让每个变异体
**先能编译**，再要求「rc == 判据红的约定码 且 输出点名被拆的守卫」。
本轮补了「变异体先 `go build` 通过」的前置，M1/M2 重生成后两臂均编译通过且被抓住。

## 6. 双仓同步

- **镜像侧 `github/main`** 与 **权威侧 `origin/main`（codeup）历史互相独立**
  （`merge-base` 停在 2026-10-07；codeup 侧 3345 提交 github 侧没有，
  github 侧 13503 提交 codeup 侧没有）⇒ **`git merge` 合不动**。
- ⇒ 同步办法 = **树移植**（AGENTS.md 双仓同步契约；`sync-to-github.sh`
  的 filter-repo 管线与之**互斥**，仅作 `--dry-run` 诊断）：
  ```bash
  TREE=$(git rev-parse origin/main^{tree})
  SYNC=$(git commit-tree "$TREE" -p "$(git rev-parse github/main)" -m "sync(codeup): …")
  git push github "$SYNC:refs/heads/main"
  ```
- ⇒ 验收口径 = **两仓 main 的 `tree` SHA 必须相同**
  （`git rev-parse origin/main^{tree}` == `git rev-parse github/main^{tree}`，
  且 `git diff --stat origin/main github/main` 为空），推完用
  `git ls-remote` 对拍远端真值。
