## 二、合并后 flow 12 变红：归因链（每一步都有实测，不是推测）

### 2.1 症状

`12-live-stage-tree` 红在 `Assert that "请求阶段树" is visible`；失败现场截图＝**访客营销页**。

### 2.2 逐级排除

1. **换回合并前的共享登录流**（`inputText + pressKey: Enter`）重跑同一条 flow ⇒ **49 步全绿**
   ⇒ 变红**归因于并行车新写的 `_shared/login.yaml`**，与阶段树代码、与生产环境无关。
2. **失败现场取证**（截图 + 视口层级 JSON）：
   - 弹窗内**没有任何错误横幅** ⇒ `handleLogin` **没有报错**（不是 401）；
   - `#login-password` 的 DOM 值 ＝ **`Veritrans&9527` 逐字完整** ⇒ Maestro 的 `inputText` **没有吞字符**
     ⇒ 上游那版注释里的「键入/插值吞片段」在本驱动**不成立**；
   - 密码值仍在 ⇒ 页面**没有 reload** ⇒ 不是「原生表单提交把页面刷掉」。
   ⇒ 结论：**`handleLogin` 压根没被触发**。
3. **决定性探针**（web 驱动 / Maestro 2.11.0 / 154 生产站 / 2026-11-18）：

   | 探针 | 结果 |
   |---|---|
   | `evalScript` 往 `document.body` 插一个可见 div | 视口层级里**没有它**（页面一字未变），命令报 COMPLETED |
   | `evalScript` 里**同步** `throw new Error(...)` | **仍报 COMPLETED / rc=0**（异常被吞） |
   | `evalScript: '${output.probe = ...}'` 后 `openLink: ${output.probe}` | **不插值**（原样当 URL 打开 ⇒ `ERR_NAME_NOT_RESOLVED`）⇒ 值是**只写不读** |

   ⇒ **web 驱动上 `evalScript` 根本不执行**（不带 `${}` 的那一种压根不发给浏览器；带 `${output.*}` 的只在 **JVM 侧**求值）。
4. ⇒ 并行车新登录流里的 `await fetch('/api/auth/token')` **从未执行过** ⇒ **从未登录**；
   而它自带的 `throw LOGIN_HTTP_*` / `LOGIN_NO_ACCESS_TOKEN` / `LOGIN_NO_SESSION`
   **一次都没触发过** ⇒ **假强门**：flow 报绿，浏览器其实还是访客。
5. **main 基线树取证**（`origin/main@94d736c62`，**未改动**）跑同一条 flow ⇒ **rc=1 / FAILED=1，失败点完全相同**
   ⇒ ★ **这条红是 main 自己的存量红，不是合并引入的**；合并只是把它带进了本分支。
6. **仓内早已写明这条约束**：`maestro/README.md` §6.6 的能力边界表第一行 ——
   「`evalScript`｜**no-op**：命令报 COMPLETED，页面一字未变｜**不要用**。
   `javap -p maestro.drivers.CdpWebDriver` 的方法表里根本没有 `evaluateScript`」。
   ⇒ 上游违反的是**本仓 README 已写明的约束**，不是本轮新发现的坑。
   ⇒ 而 §6.3 仍给出「页内 fetch 注入 cookie」的配方（依赖 evalScript）⇒ **README 自相矛盾**，本轮一并订正。

## 三、修法：共享登录流重写（**零 `evalScript`**）

`maestro/flows/_shared/login.yaml`：

- **提交路径＝SPA 自己的路径**：`inputText` + `pressKey: Enter` ⇒ 触发
  `LoginModal` 的 `<form @submit.prevent="handleLogin">`
  ⇒ **服务端会话（HttpOnly cookie）与 SPA 内存态同源** —— 这正是「页内 fetch」那版丢掉的一半
  （fetch 只落 cookie，不更新 SPA 状态 ⇒ 下游在访客态上跑）。
- **三段驱动原生判据**（全部不会静默空转；缺一段都算红）：

  | 判据 | 断言 | 证明了什么 |
  |---|---|---|
  | ① | `notVisible: id: login-modal-title` | `handleLogin` 走完且成功（失败时弹窗不关 + 红色横幅） |
  | ② | `visible: text: "系统管理员"` | **SPA 内存态**已更新（`store.userInfo` 有值 ⇒ `isLoggedIn` 为真 ⇒ 顶栏布局）。「系统管理员」是**种子账号的 `display_name`**（`admin/users.go:247`）⇒ 与环境无关；同一标记已被 `11-simple-overview` / `12-live-stage-tree` 的「起点归零」段复用 ⇒ 单一真源 |
  | ③ | `openLink /dashboard` 后 `visible: text: "系统管理员"` 仍在 | **服务端会话真的建立了**：web 驱动的 `openLink` **清 localStorage 但保留 cookie**（见 `_shared/switch-simple-mode.yaml` 头注）⇒ 重载后只能靠 cookie + `/api/auth/me` 水合出用户 ⇒ 排除「只有内存态、cookie 没落袋」 |

- ★ **判据 ③ 就是上游想要的「HTTP 200 但没有会话 cookie」的真判据** —— 只不过用**驱动原生**方式实现，
  不依赖任何页面内 JS（页面内 JS 在 web 驱动下**根本跑不起来**）。
- ★ **失败是响亮的**：口令不对 ⇒ 后端 401 ⇒ 弹窗不关 ⇒ 判据① 立刻红；
  不会像 evalScript 那版一样「报绿但没登录」。

## 五、通用式（本轮新增）

1. ★ **「报绿但没做」是最危险的失败模式**：判据自身不执行时，flow 全绿而产品是坏的
   ⇒ **判据要单独验一次「它到底执行了没有」**（本轮：可见标记 div / 同步 throw / 值不插值，三条探针）。
2. ★ **「文档里的能力边界」比代码更权威**：上游违反的是**本仓 README 已写明的约束** ⇒
   **合流前先读被改文件的既有约定**，别把「别人写的」当成「对的」。
3. ★ **存量红要归到「谁的树」**：在 **main 基线树**上跑同一条 flow ⇒ 红属于 main；
   合并只是把它带进本分支 ⇒ **不该由合并方来背**。
4. ★ **二手记载要当二手对待**：README §6.3 的「cookie 注入」配方与 §6.6 的能力边界**互相矛盾** ⇒ 以实测为准，
   并把矛盾处**改成明确的「不可用」**（留着的配方＝下一个人的假绿门）。
5. ★ **「内存态 / 服务端态 / 失败态」要各有一条独立证据**：只验其中一层，就会漏掉
   「cookie 没落袋」或「登录其实失败了」这两类**静默**失效。
