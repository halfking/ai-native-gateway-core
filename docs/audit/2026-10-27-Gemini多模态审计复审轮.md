## 二、实锤缺陷（审计③族，四处）

上一轮修的是「file_uri → 空载荷块」这一个**到达方式**；本轮按「同一 builder 的
所有输入形态 × 所有槽位」枚举，同族还有四种：

1. **file_id-only video → `video_url.url:""`**：`parseOpenAIMediaBlock` 可产出
   `Type:"file_id"` 的 video（`video_url.file_id` 引用形态），Chat Completions 的
   video_url 没有 file_id 槽位 ⇒ 原实现无条件写 `url:""` 空串。
2. **`Document.Source == nil` → `content:[null]`**：`serializeOpenAIDocumentBlock`
   开头 `doc.Source == nil` 返回 nil，而 OpenAI 侧调用点
   （serializeOpenAIMessageContent）**没有 nil 守卫** ⇒ nil 入
   `[]map[string]any` ⇒ json 序列化成**字面量 null 元素**（探针实测打出
   `content:[...,null]`）。★ 上一轮在 **Responses 侧**修过同款问题（注释里
   明写 "a nil entry would marshal as a literal null"），OpenAI 侧漏网 —— 
   「两侧同修」教训见 §437 通用式二。
3. **`Type:"url"` 而 URL 为空的 audio → `input_audio.url:""`**：`case "url"`
   无条件写槽位。本轮新增的回归测试**当场抓到**（第一版守卫 `len(inner)==0`
   挡不住「键在、值空」）。
4. **url/text 双空的 document → `file.file_data:""`**：`serializeOpenAIDocumentBlock`
   的 url 与 text 分支、`buildResponsesInputFile` 的 url 与 default 分支同款。

## 三、修法

- `serializeOpenAIVideoBlock`：无 URL/FileURI/Data ⇒ 返回 nil（调用方跳过）。
- `serializeOpenAIAudioBlock`：**每个槽位写入前单独判空**（写前判，不是写后数）；
  全空返回 nil。
- `serializeOpenAIDocumentBlock` / `buildResponsesInputFile`：url/text 分支解析出的
  值为空 ⇒ 返回 nil；OpenAI 侧尾部加 `len(fileInner)==0` 护栏（filename-only 块
  保持 2026-09-05 既有行为：发出 + 损失上报）。
- OpenAI 侧三个 append 点补 nil 守卫。
- **跳过留痕**：`reportSerializeOpenAILosses` 新增三条损失上报（video 无载荷 /
  document 无 source / audio 无载体），与 image.file_id 既有惯例对齐。
