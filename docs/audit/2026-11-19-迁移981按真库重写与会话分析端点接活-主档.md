## 二、迁移本体：按真库重写

### 2.1 首版为什么必炸（幻写 schema）

首版按「sessions 有 `owner` / `total_input_tokens` / `total_cost` / `turn_count`」
写。真库（211 / `acc-pg17`）实测：**这些列全部不存在**。

| 首版写法 | 真库真名 |
|---|---|
| `sessions.owner` | `sessions.owner_user`（且有 **9,720 条是空串**不是 NULL） |
| `total_input_tokens` / `total_output_tokens` | 只有 `total_tokens`（**无输入输出拆分**） |
| `total_cost` | `total_cost_usd`（且**无外部成本列**） |
| `turn_count` | `total_turns` |
| `rl.model` | `client_model` / `outbound_model` |
| `rl.provider` | `provider_id`（bigint 外键 → `providers.code`） |
| `rl.status = 'success'` | `success`（**boolean**） |
| `rl.cache_read` | `cache_read_tokens` |
| `rl.cost` | `cost_usd` |
| `rl.created_at` | `rl.ts` |

⇒ 建视图当场 `42703 column does not exist`。

★ **通用式：物化视图的列名必须对着真库的 `information_schema` 抄，不许照设计文档抄。**
设计文档是意图，真库是事实；两者不一致时，**以真库为准并回改文档**。

### 2.2 底座换成会话分析既有三件套

真库实测发现，仓里**早就有**会话分析的规范数据面（357 迁移建的 `session_summaries`），
首版绕开它直接写 `sessions` 裸表是重复造轮子。重写后的底座：

| 源 | 行数 | 提供的维度 |
|---|---|---|
| `session_summaries` | 250,575 | 会话级指标：duration / request_count / success / error / cost / credits / tokens / latency / primary_model / **gw_project_id** / gw_task_id |
| `session_dim` | 250,552 | **owner_user（人员）** / task_id（任务）/ client_id（应用） |
| `sessions` | 249,943 | **agent_name（智能体）** / owner_user / title / is_probe |
| `request_logs_with_current_month` | 410,680 | 请求级：模型 / provider / 成功 / 缓存 / 成本 / 延迟 |

★ **口径分层（必须写下来，否则两个面会互相打架）**：
前三个视图是**会话级**，第四个（模型维度）是**请求级**——
缓存率/成功率/延迟只有请求级有（`session_summaries` 没有缓存列）。
⇒ 「会话数/会话成本」看前三视图；「请求数/成功率/缓存率」看第四视图；**两者不可相加**。

### 2.3 日桶：显式 CST，不依赖会话 TimeZone

日期桶 = `(ts AT TIME ZONE 'Asia/Shanghai')::date`，**显式写时区**。
迁移 992 已把「面向用户的统计 API 用 CST 业务函数」定成产品口径（`cst_today` / `cst_date`
等价于此式）⇒ 物化视图的日桶与看板/对账面天然对齐。

★ 会话级三视图取 **`first_request_at`**（会话开始日）而不是 `last_request_at`：
后者会随每次刷新把行**搬家**到别的日期 ⇒ 物化视图每次刷新都在增删行，
REFRESH CONCURRENTLY 的差分成本与抖动都变高；`first_request_at` 稳定。

## 三、三个测出来的硬约束（本轮最有价值的部分）

### ① REFRESH MATERIALIZED VIEW CONCURRENTLY **拒绝表达式唯一索引**

首跑实测报错：

```
ERROR:  cannot refresh materialized view "public.project_task_aggregates" concurrently
HINT:  Create a unique index with no WHERE clause on one or more columns of the materialized view.
```

根因：PG 的 `findCommittedUniqueIndex` 会**跳过 `indexprs` 非空的索引** ⇒
`ON ...(owner, tenant_id, project, COALESCE(task,''), date)` 这种表达式索引**不算数**。
而且纯列唯一索引遇到 NULL 值时「NULL 互不相等」⇒ 唯一性不成立 ⇒ 差分阶段也会失败。

⇒ **修法**：`project_task_aggregates` 的 `task` 列用 `''`（而非 NULL）表示「无具体任务」，
四个键列全部恒非空 ⇒ 纯列唯一索引 `(owner, tenant_id, project, task, date)` 成立。
⇒ Go 侧随之改口径：`COUNT(DISTINCT NULLIF(p.task,''))` / `task <> ''`（原写法 `task IS NOT NULL`
会把所有空任务行当成真任务返回）。

### ② REFRESH MATERIALIZED VIEW CONCURRENTLY **可以在事务块内执行**

⇒ **`dbinit:no-transaction` 豁免没有正当理由，仓库门禁判红是对的。**

实测（211 / PG 17.10）：

```
BEGIN; REFRESH MATERIALIZED VIEW CONCURRENTLY <有唯一索引的视图>; COMMIT;  → 成功
BEGIN; REFRESH MATERIALIZED VIEW CONCURRENTLY <无唯一索引的视图>; COMMIT;  → 报
   "cannot refresh materialized view ... concurrently / Create a unique index"
   （说明确实走了 CONCURRENTLY 分支，不是静默降级）
对照组：BEGIN; CREATE INDEX CONCURRENTLY ...; COMMIT;  → "cannot run inside a transaction block"
```

真正不可事务化的是 `CREATE/DROP INDEX CONCURRENTLY` / `REINDEX CONCURRENTLY` /
`CREATE DATABASE` / `VACUUM` 这一族，REFRESH CONCURRENTLY 不在其中
（`installer/internal/dbinit/no_transaction_test.go` 的白名单也是这一族）。

⇒ **修法**：去掉 981 的 `dbinit:no-transaction` 标记 ⇒ 走 installer 的
`--single-transaction` 通道 ⇒ **建视图与刷新在同一个事务里** ⇒ 失败不留半套视图（原子性）。

★ **通用式：门禁把"豁免没有正当理由"判红时，先信门禁**——
本轮正是这个门禁拦住了我给 981 加的假豁免。

### ③ `SET LOCAL lock_timeout` 在事务块外**只报 WARNING 且不生效**

实测：

```
SET LOCAL lock_timeout = '5s';  →  WARNING: SET LOCAL can only be used in transaction blocks
                                    且 SHOW lock_timeout 仍是 0（没生效）
```

而 981 有**两条投递通道**，其中 211 docker 走的 `apply-db-revision-sequence.sh`
是**非事务流式**执行（`psql -X -v ON_ERROR_STOP=1 "$DATABASE_URL" -f -`，无 `--single-transaction`）
⇒ 用 `SET LOCAL` 会让锁守卫在**那条真正生效的通道上静默失效**。

⇒ **修法**：用会话级 `SET lock_timeout = '5s';`（两条通道都生效；作用域止于本 psql 会话，
`psql_file` 每次独立起会话 ⇒ 不污染其它迁移）。

★ **通用式：守卫要问"它在**每条**投递通道上都生效吗"**，
而不是"它在作者写的那条通道上生效吗"。

⇒ **判定收敛到单一函数** `session_analytics_is_probe(owner, client, title)`，

## 九、本轮沉淀的通用式

1. **物化视图的列名对着真库 `information_schema` 抄，不许照设计文档抄**（文档是意图，真库是事实）。
2. **新迁移的登记清单按「投递通道」枚举**：211 docker 的投递面是
   `apply-db-revision-sequence.sh` 的 `files=()`，漏了它 = 迁移从未投递（首轮只补 installer 侧）。
3. **REFRESH CONCURRENTLY 要纯列唯一索引 + 列上无 NULL**：表达式索引不算数（`indexprs` 被跳过），
   NULL 会让唯一性不成立 ⇒ 用 `''` 归一而不是 NULL。
4. **REFRESH CONCURRENTLY 可以在事务块内跑** ⇒ 不需要 `dbinit:no-transaction` 豁免
   ⇒ 门禁把"豁免无正当理由"判红时，先信门禁。
5. **守卫要在每条投递通道上都生效**：`SET LOCAL lock_timeout` 在非事务流式通道上只报 WARNING 且不生效
   ⇒ 用会话级 `SET`。
6. **单测绿 ≠ 代码在生产路径上**：必须补「路由可达 / 列名对得上真库 / 身份键与角色词表对齐仓内真源」三类钉测；
   测试自己造了一套假上下文键是最隐蔽的一种。
7. **探测流量必须排除才有意义**（本仓 80% 会话是非人工流量）⇒ 判定收敛到**单一函数**、
   四个视图共用 ⇒ 各维度数字互相自洽。
8. **空串 ≠ NULL**：owner 为空串时只判 `IS NOT NULL` 会聚出一个带 340 美元的假人 ⇒ 一律 `NULLIF(...,'')`。
