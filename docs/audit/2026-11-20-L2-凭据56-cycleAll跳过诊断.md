# L2 诊断：凭据级探针 v2 cycleAll 为何跳过凭据 56

> **问题来源**：2026-11-20 节点探测配额族落账轮登记项 L2（P2）  
> **背景**：主档记录凭据 56 的 `last_probe_at` 停在 2026-11-13（7 天没跑过）  
> **目标**：定位 cycleAll 跳过凭据 56 的具体判定分支

---

## 一、问题陈述

根据主档 §1.4 的完整闭环描述：

```
凭据 56 / claude-sonnet-5-5 在修复前：
  node probe 看到 403 INSUFFICIENT_BALANCE
     ↓ 只写绑定面（凭据面不落账 ⇒ quota_state 仍是 'ok'）
  凭据面 quota_state='ok' ⇒ ★ 响应式的余额复检探针（bg/balance_quota_probe.go:
     选 quota_state IN ('balance_exhausted','permanently_exhausted')）**看不到它**
     ↓
  凭据级探针也不看它（bg/credential_probe_v2.go cycleAll 的 last_probe_at
     停在 2026-11-13 —— 7 天没跑过）⇒ **没有任何凭据级探针会来复检它**
     ↓
  只剩模型对的通用梯子 ⇒ 333 次连败 ⇒ 每 3 小时一轮
```

**关键疑问**：F2 修复（探针写凭据配额面）之后，余额复检探针会接管；  
但为什么 cycleAll **自身**跳过凭据 56？

## 二、cycleAll 的完整过滤条件

来源：`bg/credential_probe_v2.go:439-469`

### 2.1 SQL WHERE 子句（9 个条件）

```sql
WHERE c.status = 'active'                                    -- ①
  AND c.lifecycle_status = 'active'                          -- ②
  AND COALESCE(c.manual_disabled, FALSE) = FALSE             -- ③
  AND COALESCE(p.manual_disabled, FALSE) = FALSE             -- ④
  AND COALESCE(p.enabled, FALSE) = TRUE                      -- ⑤
  AND COALESCE(c.quota_state, 'ok') NOT IN 
      ('permanently_exhausted', 'balance_exhausted')         -- ⑥
  AND c.availability_state <> 'suspended'                    -- ⑦
  AND (c.availability_recover_at IS NULL 
       OR c.availability_recover_at <= now())                -- ⑧
  AND COALESCE(c.default_probe_model, '') <> ''              -- ⑨
```

### 2.2 行内跳过条件（循环中，第 504 行）

```go
if skipProbeOnRecentTrafficSuccess(timeoutCtx, c.db, s.ID) {
    skippedRecentSuccess++
    continue
}
```

`skipProbeOnRecentTrafficSuccess` 逻辑（`bg/credential_probe_v2.go:705-726`）：

```sql
SELECT (
    -- 分支 A：最近 30 分钟有成功流量 + 健康状态 + 上次探针成功
    COALESCE(c.last_used_at, to_timestamp(0)) > now() - INTERVAL '30 minutes'
    AND c.health_status IN ('healthy', 'unknown')
    AND COALESCE(c.last_probe_success, TRUE)
) OR (
    -- 分支 B：当前健康 + 上次探针失败 + 但无近期失败证据
    c.health_status = 'healthy'
    AND COALESCE(c.last_probe_success, FALSE)
    AND NOT credentialFailureEvidenceSQL(...)
)
FROM credentials c WHERE c.id = $1
```

### 3.2 预期结果解读

**若 SQL WHERE 子句未通过**：
- 找到具体失败的条件（①-⑨）
- 记录该字段的实际值
- 追溯该值的来源（是否被其他流程改写）

**若 SQL 通过但被 skipProbeOnRecentTrafficSuccess 跳过**：
- 判定是分支 A（近期流量成功）还是分支 B（健康但无近期失败）
- 检查 `last_used_at` / `health_status` / `last_probe_success` 的实际值
- 验证是否存在"绑定面不可用但凭据面健康"的矛盾状态

**若两者都通过**：
- 说明凭据 56 **应该被探测**但实际未被探测
- 需进一步检查：
  - cycleAll 是否实际运行（查日志）
  - 是否在 decrypt 阶段失败（第 510-531 行）
  - 是否在 probeCredentialWithCapability 阶段卡住

### 3.3 已知线索

根据主档 §1.1 的实测（2026-11-20 09:37~10:00）：

| 字段 | 实测值 | 说明 |
|---|---|---|
| `availability_state` | `'ready'` | 凭据面显示"节点正常" |
| `quota_state` | `'ok'` | 未被探针写入配额状态 |
| `cmb.available` | `FALSE` | 绑定面不可路由 |
| `cmb.unavailable_reason` | `'probe_http_403'` | 探针记录的失败原因 |

**关键矛盾**：
- 凭据面 `availability_state='ready'` ⇒ **应该通过条件 ⑦**
- 凭据面 `quota_state='ok'` ⇒ **应该通过条件 ⑥**
- 绑定面全部 `available=FALSE` ⇒ **应该有近期失败证据** ⇒ skipProbeOnRecentTrafficSuccess 分支 B 不成立

**推测方向**：
1. **条件 ⑧**：`availability_recover_at` 是否有未来时间？
   - 探针写入的冷却时长（修复前是 5 分钟假账，修复后与探针下一跳同源）
   - 若该字段仍在未来 ⇒ cycleAll 会跳过
2. **条件 ⑨**：`default_probe_model` 是否为空？
   - 凭据 56 是 apiclaude-china，catalog 可能未配置默认探针模型
3. **skipProbeOnRecentTrafficSuccess 分支 A**：
   - `last_used_at` > 30 分钟前 + `health_status='healthy'` + `last_probe_success=TRUE`
   - 这需要**真实成功流量**，但绑定面全红 ⇒ 不应该有成功流量
