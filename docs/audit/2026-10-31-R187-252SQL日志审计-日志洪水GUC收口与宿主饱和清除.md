## §3 主修复①：日志洪水与 15.6h 灭失（log_parameter_max_length=0）

### §3.1 洪水构成（两个时代、同一张 1GB 天花板）

| 时代 | 形态 | 巨条目家族（归档日 840MB 实测） |
|---|---|---|
| flip 前（SimpleProtocol，≤10-30 凌晨） | `statement: INSERT ...` 多行 VALUES **全内联** | provider_metrics_minute ×172 / request_stats_minute ×44 / CMI_hot ×71 / **assets ×313**（巨型 rollup/资产 upsert，每条 100-500KB）|
| flip 后（扩展协议，10-30 起） | `bind stmtcache_*:` 语句骨架 + **`DETAIL: Parameters: $1=...` 全量参数** | assets upsert（live 窗慢日志字节 **60.9%**）/ WITH matched 18.1% / WITH policy 8.5%；live 窗 DETAIL **2,102 条** |

- **客户端归因**：pg_stat_activity 活捉 assets upsert 连接 = **172.16.2.241（245）**；
  `stmtcache_*` 命名 = pgx QueryExecModeCacheStatement = R183 flip 后的默认池。
- **灭失链**：归档止 03:45（logrotate copytruncate）→ 洪水续灌 ~1GB → podman
  log_size_max **静默截断**（无 NUL、无痕迹，首行时间戳断崖 19:20:34 为唯一侦破通道）
  → **10-30 05:47→19:20（13.5h）未审计且不可恢复**（03:53-05:47 段 R184 已读）。
- **周维护量对照**：flip 前正常日 ~80-150MB/天（10-27/28 归档 gzip 19.8-26.8MB），
  洪水日 840MB、live 半天 113MB——**~5-8×**。

### §3.2 修法与实证

- `ALTER SYSTEM SET log_parameter_max_length = 0`（单语句；auto.conf 已确认写入；
  SIGHUP 06:28:55 生效；**容器重建会丢**——与 log_statement=none+1s 同一 registered 运维项，
  最好随下次受控重建一并固化进 `-c` 参数）；
- **语义**：仅压「非错误语句日志」的参数值；语句骨架 + duration 保留 ⇒ 审计通道的
  「哪条语句、多慢、多久一次」三个维度无损；错误路径参数本就由
  `log_parameter_max_length_on_error`（保持 0）另管；
- **实证三步**：① SIGHUP 后 param DETAIL = **0**（前窗 2,102）；② `\bind` 主动 A/B：
  1.2s 查询只留 `$1::text` 骨架、参数值零落盘（全日志 grep 参数值 = 0 命中）；
  ③ 帧率 75k/h → 154/h（叠加饱和解除，见 §6 读数）。副作用核对：
  修复后 06:3x 窗 assets upsert 本身降至 <1s（不再触发慢日志）——其 DB 成本
  （med 1.74s@饱和）本就饱和通胀，非内在回归。

### §3.3 遗留（登记）

- **log_size_max=1GB 静默截断**仍是结构性隐患（SimpleProtocol 巨条目时代一样会撞）；
  GUC 修复后紧迫性解除；根治 = podman `--log-opt max-size` 提高或 k8s-file 轮转，
  属容器受控重建窗口（与 auto.conf 固化同一窗口，登记一起做）。
- apihub assets 每 2-5min 全量 upsert ~700 行本身**不是缺陷**（2,200 行表的增量同步，
  DB 成本 <1% 单核）；本轮不动。

## §9 通用式（本轮）

1. ★★★★★ **「日志通道本身」是被审计的第一张表**：慢日志的形状由「客户端协议 × 日志 GUC」
   共同决定——R183 的协议翻转（无日志侧联动）让每条慢查询从 1 条变 2 条、且多出
   不限量的参数 DETAIL；「翻开关」的爆炸半径要沿**所有观测通道**走一遍。
2. ★★★★ **「0 条告警」必须区分「条件消失」与「观测失效」**：日志被 1GB 静默截断后，
   灭失窗内的「无错误」是伪读数；首行时间戳断崖是唯一侦破通道（fact 0- 第二次应验）。
3. ★★★★ **A/B 验证要先验证「通道」再验证「结论」**：psql 的 PREPARE/EXECUTE 走 simple
   协议，测不到 Bind 通道；通道协议形态搞错，A/B 会给出「机制无效」的假阴性。
4. ★★★ **审计聚合量具的单位要过「不等式体检」**（总时长 ≤ 窗口墙钟）；ms/s 混写
   一次性虚报 1000×，靠「读数不可能」当场抓住。
5. ★★★ **宿主饱和是慢 SQL 的乘法器**：同一查询族饱和期/安静期读数可差 5-25×
   （ursm slot-refresh 1,330s→187s→待 47s 基线）；「回归」判定必须双窗对照，
   否则会把饱和症状修成代码。
6. ★★ 孤儿女 AI 侦察进程（grep -r / bash -s）是 252 的**慢性病**（第 4 次复发）：
   每轮清除只能治标，宿主侧 ssh 会话治理是治本位（超出本仓，持续登记）。
