## 5. 真库复现（本机 PG 17.10，一次性库 `llm_gw_v1audit`）

### 5.1 忠实的投递路径（本轮最关键的方法论修正）

★ 前两次真库跑都用了「基线 + **从 000 起**的整条链」⇒ **那是错的投递方式** ⇒ 撞出 74 个「表已存在 / 约束不匹配」的假失败 ⇒ 一路级联 ⇒ 连累 890 中止。

★ **正确的路径**由 installer 的 `StartupFiles` 给出（实测 312 条，**从 388 起**）：

```
基线快照（= 迁移 387 之前的世界）  +  installer 显式顺序的 388+（313 个文件）
```

⇒ 走这条路径 ⇒ **带错误的迁移 = 0** ⇒ 上一轮的 74 个错误**全部是路径错**，不是仓库坏。

★ 两处必要的偏离，逐条说清：

1. ★ **基线要装扩展**：基线快照是 pg_dump 产物，**不含 `CREATE EXTENSION`**（dump 假定扩展已预装）⇒ 本机只装了 `plpgsql` + `vector` ⇒ `pg_trgm` 没装 ⇒ `gin_trgm_ops` 不存在 ⇒ 级联失败（§2.4）。⇒ 本轮**先装** `pg_trgm` / `pg_stat_statements` / `btree_gin` / `btree_gist` / `citext` / `pgcrypto` / `hstore`。
2. ★ **本机没有 `pg_columnar`** ⇒ 跑的是 `columnar→heap` 的派生副本。★★ 这个变换**只改冷分区的存储引擎**，不改关系名 / 列 / 存在性 ⇒ **对「表还在不在」这个问题完全等价**；且**交付清单里那 39 个提到 columnar 的迁移**，`USING columnar` 全在**条件分支**（`citus_columnar` 扩展不存在 ⇒ 不执行）或**动态 SQL** 里 ⇒ 链在无 columnar 的 PG 上也是 **0 错误**。⇒ 变换只作用于 `/tmp` 下的副本，**仓内文件零改动**。

### 5.2 ★★★ 终态读数（本轮的核心确认）

```
投递 313 个迁移；带错误的迁移 0 个

(1) public 里所有名字含 request_log 的关系：
      v|request_logs_with_current_month          ← ★ 只剩这一个，且它是**视图**
(2) ★★★ v1 表数量（relkind r/p）= 0
(3) 会话族关系数 = 6
(4) canonical 视图体 = 读会话族 ✔
(5) v1 专属函数是否还在 = 0
```

⇒ ★★★ **确认：所有 `request_log` 与 `_request_log` 相关的**表**都已移除**（实测 = 0）；唯一幸存的 `request_log` 命名关系是 canonical 视图 `request_logs_with_current_month`（它按设计不删名字，只把视图体换成会话族两臂）；v1 专属函数也清零。**

★ 前后对照：基线之后是 **10 张** v1 表（含分区子表）⇒ 投递完 313 个迁移后是 **0 张**。

### 5.3 仓内那道真库腿在本机的状态（诚实边界）

★ 仓内新门 `TestRetiredV1TablesAreAbsentInRealDB` 用 `pgx` 连库 ⇒ ★ **本机 pgx 连不上**（`failed SASL auth: password authentication failed for user "postgres"`），而 `psql` 用**同一个 DSN** 能连。

## 7. 通用式（本轮沉淀）

1. ★★ **上一轮清了「代码里的活操作」，不等于清了「全仓语料里的活操作」** —— 两种语料（Go 字符串字面量 / SQL 语料）要用**两把尺**。★ 门的视野决定了它能发现什么：★ **看不见 SQL 的门，发现不了 SQL 脚本**。
2. ★★★ **「清单完备」≠「清单之外没有别的路」** —— 退役一个族要问**两遍**：① 清单里覆盖全了吗；② ★ **清单之外还有没有别的文件会建出同一个族**（链外的脚本、手跑修复、废弃夹具、dev 脚手架）。★ 第二遍是本轮真正的缺口。
3. ★★★ **「跑不出预期终态」的第一嫌疑是环境，不是被测物** —— 本机真库第一轮读数（v1 表 13 张还在）看起来像 890 彻底失效，真因是**基线快照不含 CREATE EXTENSION** ⇒ 缺 `pg_trgm` ⇒ 级联失败 ⇒ 890 的前置对象没建成 ⇒ 890 自己中止。⇒ ★ **先把环境的完备性验掉，再谈被测物的结论**。
4. ★★★ **「先后」是「通道 × 文件」的二元属性** —— ★★ **只有 glob 通道是字典序**；★ **两条显式列表通道都是手写的依赖序** ⇒ ⇒ 判据必须**逐通道取顺序再并集**，★ **绝不可用「目录的字典序」替代显式列表**（本轮实测： installer 顺序里 890 之后有 5 个编号更小的、部署通道顺序里 890 之后有 1 个两位数前缀的 ⇒ 旧判据**一个都没检视到**）。
5. ★★★ **「门绿」要追问「它绿的理由是不是它声称的那个理由」** —— ★ 写进注释里的「实测」**会过期，而且过期得毫无声响**（注释不会自己报错）⇒ ★ 本轮那道门绿了，但绿的理由（字典序=投递序）是假的 ⇒ **结论碰巧对、检视范围是漏的**。
6. ★★★ **修完判据必须能证明「修之前漏、现在不漏」** ⇒ 在门里加**覆盖率自证**（「按旧判据会被漏掉的文件，必须出现在新集合里」）⇒ ★ 这样「改造」本身**可证伪**（实测：改回旧判据 ⇒ 门红并逐条点名那 6 个文件）。
7. ★★★ **变异臂全绿时先问靶点、再问门** —— M1 第一版的靶点表名压根不含 `request_log` ⇒ 门保持绿是**正确的**。⇒ **注入必须先断言「靶点真的落在被测面上」**。
8. ★★ **「退役」要留台账、不要就地删** —— 退役族的历史夹具有**复现价值**（它存在的意义就是造出「退役之前的库」）⇒ 登记 + 机器可查标头 + scope 兑现，比删文件更负责任。
9. ★★ **注释里的历史引用不算「可执行入口」** —— 门做「无自动入口引用」判定时**必须先剥注释**，否则会逼着人去删承重证据。
10. ★★★ **一条链的「起点」不是目录里的第一个文件，而是「基线快照已经包含了什么」** —— ★ 装机路径由**显式列表**定义（installer 从 388 起）⇒ ★ **复现一条链必须用那条链自己的列表** ⇒ 否则会撞出一堆「表已存在 / 约束不匹配」的假失败，并**级联**到把真正的结论淹没（本轮：74 个假失败 vs 忠实路径的 0 个）。
11. ★★ **`psql` 在 `ON_ERROR_STOP=0` 下的退出码不反映 SQL 错误** —— 用退出码当「这条迁移成功了」的判据 ⇒ 会把失败记成成功（本轮第一次真库跑就中了这招）。
12. ★★ **「连不上」与「连上了但结论是坏」是两个命题** —— 真库门在 DSN 设了却连不上时应当 **SKIP + 明说没跑成**，而不是 FAIL（★ 与仓内既有真库门同口径）⇒ 否则「DSN 写错了」会被读成「退役没做」。
13. ★★ **RE2 不支持前瞻** ⇒ 「正则不许跨块配对」写不成正则 ⇒ 改成**手工切块**；★ 且**抽取器自己要有阳性对照**（清单里必须**确实有**那 4 张视图 + 10 张底表，缺一个就红）⇒ 否则「抽取器坏了」与「仓库干净」同步为真。
