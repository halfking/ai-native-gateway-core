# 方案A：延迟检查 + 自动重试 - 中期规划及评估

## 执行摘要

**方案A** 是根本性解决方案，通过在检测点之前缓冲完整 tool arguments，实现真正的自动重试能力。

**建议时机**：在方案B运行1-2周，收集足够数据后启动。

## 评估维度

### 1. 技术可行性分析

#### 1.1 架构改动点

**核心修改**：`domains/hooks/outputcompliance/stream_compliance.go`

```go
// 当前架构（逐帧检查）
上游SSE → [帧1检查] → [帧2检查] → ... → [帧N检查❌] → 客户端已收到N-1帧
                ↓           ↓                    ↓
            客户端      客户端              不可重试

// 方案A架构（延迟检查）
上游SSE → [缓冲区积累] → [完整检查] → [❌候选切换] or [✅输出]
                                    ↓
                              可重试（流未committed）
```

**关键数据结构**：
```go
type deferredToolCheck struct {
    toolName   string
    lane       string
    frames     []string      // 缓冲的增量帧
    accumulator strings.Builder  // 累积的完整内容
    startedAt  time.Time     // 开始时间（超时保护）
}

type complianceStreamState struct {
    // 现有字段...
    deferredChecks map[string]*deferredToolCheck  // lane → 延迟检查
    deferMode      bool  // 是否启用延迟检查模式
}
```

#### 1.2 实现要点

**A. Tool lane 识别**：
```go
func isToolArgumentLane(lane string) bool {
    // 识别工具参数 lane
    // 格式：__tool_json@<toolName> 或 chat.choice.0.delta.tool.0.arguments
    return strings.HasPrefix(lane, "__tool_json@") ||
           strings.Contains(lane, ".tool.") && strings.HasSuffix(lane, ".arguments")
}
```

**B. 延迟检查触发**：
```go
func (state *complianceStreamState) shouldDeferCheck(field visibleTextField) bool {
    return isToolArgumentLane(field.lane)
}

func (state *complianceStreamState) bufferFrame(field visibleTextField, text string) {
    check := state.deferredChecks[field.lane]
    if check == nil {
        check = &deferredToolCheck{
            toolName: extractToolName(field.lane),
            lane:     field.lane,
            startedAt: time.Now(),
        }
        state.deferredChecks[field.lane] = check
    }
    check.frames = append(check.frames, text)
    check.accumulator.WriteString(text)
}
```

**C. Done 帧统一检查**：
```go
func (state *complianceStreamState) checkDeferredOnDone() error {
    for lane, check := range state.deferredChecks {
        completeJSON := check.accumulator.String()
        
        // 1. 格式验证
        if !json.Valid([]byte(completeJSON)) {
            // 尝试修补
            if repaired, ok := tryRepairToolJSON(completeJSON, check.toolName); ok {
                completeJSON = repaired
            } else {
                // 格式错误 → 触发重试
                return &errorsx.UpstreamFormatError{
                    Lane: lane,
                    Text: completeJSON,
                    Kind: errorsx.KindUpstreamFormatError,
                }
            }
        }
        
        // 2. 内容合规检查
        result, err := state.checker.CheckField(ctx, tenant, lane, completeJSON)
        if err != nil {
            return err
        }
        if result.Blocked {
            // 内容违规 → 仍然拦截（不重试）
            return &errorsx.PolicyBlockError{...}
        }
    }
    return nil
}
```

**D. 错误分类与重试触发**：
```go
// errorsx/upstream_format_error.go
type UpstreamFormatError struct {

func (e *UpstreamFormatError) Error() string {

// 在 executor 层识别并触发重试
if errors.As(err, &errorsx.UpstreamFormatError{}) {
```

#### 1.3 重试逻辑接入

**现有重试机制**（executor_dispatch.go:3668）：
```go
if interrupted == nil || !interrupted.resumable || params == nil || params.SurvivalAttempt {
    return nil
}

// 有可重试的候选 → 切换
nextCandidate := selectNextCandidate(params)
```

**方案A 接入点**：
- 将 `UpstreamFormatError` 标记为 `resumable: true`
- 利用现有的候选切换机制
- 无需新增重试逻辑

### 2. 成本分析

#### 2.1 内存开销

**缓冲大小估算**（需实际数据验证）：

| 场景 | Tool Arguments 大小 | 缓冲时长 | 内存开销/请求 |
|------|-------------------|---------|--------------|
| 简单工具调用 | 100-500 bytes | 0.5-1s | <1KB |
| 中等复杂度 | 1-5 KB | 1-3s | <10KB |
| 复杂工具（文件操作） | 10-50 KB | 3-10s | <100KB |
| 极端情况（大文件内容） | 100KB-1MB | 10-30s | <2MB |

**风险控制**：
```go
const (
    MaxToolArgumentsSize = 256 * 1024  // 256KB 上限
    MaxDeferDuration     = 30 * time.Second  // 30秒超时
)

func (check *deferredToolCheck) shouldFlush() bool {
    // 超过大小上限或时间上限 → 立即检查，不再缓冲
    return check.accumulator.Len() > MaxToolArgumentsSize ||
           time.Since(check.startedAt) > MaxDeferDuration
}
```

#### 2.2 延迟影响

**用户体感**：

| 指标 | 当前（逐帧） | 方案A（延迟） | 差异 |
|------|------------|--------------|------|
| 首个 tool call 可见性 | 实时（0ms） | 延迟至 done（500ms-3s） | -500ms ~ -3s |
| 整体响应时间 | 不变 | 不变 | 0ms |
| 重试成功后 | N/A | 自动获得结果 | +5-10s（但零人工干预） |

**缓解策略**：
1. **渐进式输出**：先输出 `tool_calls` 框架（name, id），arguments 延迟
2. **进度指示**：客户端显示「工具调用准备中...」
3. **仅对必要工具延迟**：只缓冲有格式错误风险的工具

**用户价值权衡**：
- 损失：首次可见性延迟 0.5-3s
- 收益：格式错误自动修复，省去手动重试（30s-5min）
- **结论**：对于会格式错误的场景，净收益明显

### 7. 替代方案

如果方案A因成本或复杂度被否决，考虑以下替代：

#### 7.1 方案B增强版

**策略**：持续扩展修补规则，覆盖更多格式错误模式

**优势**：
- 改动最小
- 零延迟影响
- 风险可控

**劣势**：
- 修复率上限 ~95%
- 需要持续维护规则库
- 无法处理未知格式

#### 7.2 客户端智能重试

**策略**：客户端识别格式错误并自动重试

**实现**：
```typescript
// ZCode 客户端
if (error.message.includes("格式有误，请重试")) {
    if (retryCount < 3) {
        await sleep(exponentialBackoff(retryCount));
        return retryRequest();
    }
}
```

**优势**：
- 网关零改动
- 客户端完全可控

**劣势**：
- 浪费网关资源（整个请求重来）
- 延迟更长（包括 prompt 处理）
- 需要所有客户端实现

#### 7.3 上游质量改进

**策略**：推动上游修复根本问题

**行动**：
- 向 apiclaude.cc 等中转反馈格式错误样本
- 提供详细的错误模式分析
- 协助调试和验证

**优势**：
- 从根本上解决问题
- 零网关改动

**劣势**：
- 依赖外部团队，周期长
- 无法解决网络闪动等临时性问题
