## 三、总体结论

1. **全仓统计类 API 约 137 个**（路由分散在 45+ 文件的 `mux.HandleFunc`，无集中路由表）；另有 **3 个前端声明、后端不存在的路由**（恒 404）。
2. **真正落到新方案的只有少数几个面**：`dashboard/board` 英雄区、`/api/logs` 探测臂、对账三面（`report-rollup` / `request-reconciliation` / 供应商对账）、`session-overview` 的**宇宙层**、会话分析的 **MV 族（经 981/984 间接继承宇宙）**。
3. **口径分裂仍然存在且用户可见**：同一个「会话与统计」面板里，**7 个端点只有 1 个（`session-overview`）消费 `include_probes`**，其余 4 个数字面（趋势/健康/错误/性能）仍在旧宇宙；其中错误/性能/模块三张卡**恒为空表**。
4. **上周 11-18 的 P0 三条（F1 / F2 / F3）一条都没有修**，F4 / F5 / F8 同样未修。
5. **本周 11-24 的 984 迁移修的是 D1（探测误杀），不是口径统一** —— 修完后会话侧与看板的差距从「少 $6,452.73」变成「口径不同」，但**队列制窗口 vs 请求级窗口**的结构性差异（11-23 方案 C）仍未动。

## 六·补记（本轮实施前的三处订正）

> ★ **通用式**：审计结论在动手前必须回到**构造过程**复核一遍 ——
> 「这个数字是怎么被构造出来的」。本轮三处订正全部由此而来，
> 且其中一处若不订正，实施方向就会整个反过来。

### 订正 ① —— N10（对账页 USD 挂 `¥`）**证伪，撤回**

- 原判：`internal_cost_cents` 来自 `grain.go:123` 的 `SUM(cost_amount)*100`
  （`cost_amount` ← `usage_facts.cost_amount` ← `e.CostUSD` ＝ **USD**）
  ⇒ 前端 `fmtCny` 打 `¥` ⇒ 美元数值挂人民币符号。
- **实测复核**：`internal_cost_cents` **不是**那条 SQL 的产物。它是
  `domains/reportrollup/report.go:167-170` 由
  `internalCents(snapshot)` 现算的：Σ(`credits_charged` × 快照冻结的
  `cents_per_credit`)，且服务端显式写死 `t.InternalCurrency = "CNY"`；
  `cents_per_credit` 取自 `maas_settings`（默认 0.2 **CNY**/积分，
  `domains/reportrollup/rollup.go:150,248,718`）。
- ⇒ **`internal_cost_cents` 就是人民币分** ⇒ `fmtCny` **正确**。
  真正走美元那条链的是 `estimated_cost_cents`
  （`grain.go:123` 的 `cost_cents` ← `cost_amount` ← `CostUSD`），
  而它在 `ReconciliationKpiGrid.vue:86` 用的是 `fmtUsd` —— **也是正确的**。
- ⇒ **N10 不存在，撤回**。教训：同一个响应里有两个「cents」字段，
  币种完全不同（`internal_cost_cents`＝CNY，`estimated_cost_cents`＝USD），
  **看字段名/渲染函数就下结论必然出错**，必须回到写入侧。

### 订正 ② —— 「external_cost 恒 0」的**范围**比原判大得多，且根因在写面

- 原判：只有 `model-ranking` / `provider-ranking` 的 `external_cost` 恒 0。
- **实测复核**：`external_cost` 的来源分两种，而**两种都恒 0**：
  - 会话级三视图（`user_session_aggregates` / `agent_usage_aggregates` /
    `project_task_aggregates`）：`external_cost = SUM(ss.total_credits_charged)`
    （`981:192,260`；`994:89,147,197`）；
  - 请求级 `model_usage_aggregates`：字面量 `0::numeric`（`994:246`）。
- **根因**：`session_summaries.total_credits_charged` **没有写方** ——
  - 迁移 990 建了该列（`990_stats_consistency_fixes.sql:23`），
  - 990 同时定义的 plpgsql `update_session_summary()`（`:71-194`，
    写该列于 `:117,165`）**从未建触发器** ⇒ 孤儿函数，永不执行；
  - 生产写方是 Go 镜像写器 `internal/sessionv2mirror/session_summary_dim.go`，
    其 INSERT 列清单**不含**该列。
- ⇒ **「成本分列」在会话分析族是结构性落空，不是部分落空**：
  `external_cost` 在**全部四个**物化视图上恒为 0。
  原判「只有模型榜/供应商榜」严重低估 ⇒ 已在本轮实施中修掉（§十一）。

### 订正 ③ —— 「有正确参考实现」这句要改口径

- 核查时以为存在一个「已经分两卡渲染」的现役页面可供照抄。
- **实测**：`SessionAnalyticsOverviewView.vue`（唯一实现分两卡的页面）
  已在 `614b72e9c` 被**删除**（总览页并入 users 页）⇒ **现役页面无一处**
  实现 framework §3.2/§4.2 承诺的分两卡 ⇒ 那个面本身就是 N9 的受害者之一。
- ⇒ 本轮的分列实现**按成文口径（framework §3.2/§4.2）+ 被删页面的键集
  （`sessionAnalytics.metric.internalCost` / `metric.externalCost` +
  `unit.usd` / `unit.credits`）重建**，不是照抄现役代码。
