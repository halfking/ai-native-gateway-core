## §2 取证：坏文件的真实形态

### §2.1 `gzip -t` 全量扫描（154，100 个文件）

```
BAD 53 / 100
```

坏文件清单（节选，按时间序）：

```
sessions-2026-08-17 / 08-18 / 08-19 / 08-21 / 08-24 / 08-25-10 / 08-26 / 08-27
sessions-2026-09-08 / 09-11 / 09-12 / 09-13 / 09-16 / 09-17 / 09-18 / 09-19 / 09-20 / 09-21
sessions-2026-09-22-02 / 09-22-03 / 09-23 / 09-24 / 09-25-02 / 09-25-03 / 09-26-01 / 09-26
sessions-2026-09-27-02 / 09-28 / 09-29 / 09-30 / 10-01 / 10-02 / 10-03 / 10-04 / 10-05 / 10-06
sessions-2026-10-07 / 10-08 / 10-09 / 10-10-01 / 10-10 / 10-11 / 10-13 / 10-14 / 10-15 / 10-16
sessions-2026-10-17 / 10-18 / 10-19 / 10-20 / 10-22 / 10-24
```

⇒ ★ **53%**。这与 FIXME-14370 登记的「154 上 98 个文件里 **51 个**单遍读不出」**同量级** ⇒
⇒ **不是新问题，是既有缺陷一直存在**；R81 只是让摘要链路**踩上去**。

### §2.2 十六进制取证（孤儿 header 连排）

```
损坏: 1f8b 0800 0000 0000 00ff | 1f8b 0800 0000 0000 00ff | 1f8b 0800 0000 0000 00ff | ec9d4b… ← 真实数据
完好: 1f8b 0800 0000 0000 00ff | ec9d4b…
```

⇒ 每个孤儿 header **只有 10 字节头、没有任何 deflate 数据**；
它的 deflate 位置直接是下一个 gzip header ⇒ `gzip.NewReader` 把它当 deflate 数据解码
⇒ Go 报 `flate: corrupt input before offset 1`，GNU gzip 报 `invalid compressed data--format violated`。

### §2.3 坏行 = 多进程 O_APPEND 的**字节级交错**

```
…{"type":"request_wal","timestamp":"2026-10-23T21:22:46.520898008Z","record_key":"cae50071d9039847ed98b7ab4a521d
b440000000000003dates failed: stream_inte6d3d:a1f03mey":"cae50071d9039847ed98b7ab4a521d…
```

⇒ 两条记录的内容**互相插进对方的字节流** ⇒ 行不是合法 JSON
⇒ ⇒ ★ **流式路径遇到第一个坏行就整体失败**；**打捞路径跳过坏行继续** ⇒
⇒ **回退打捞不只救「孤儿头」，还救「坏行」**。

### §2.4 「跳过孤儿头」不足以救回（自我修正）

第一版扫描脚本用 `od | tr` 算字节偏移（**分词 ≠ 字节**）⇒ 读数错误。
用 `xxd -p` + 十六进制串定位后重扫：

```
坏文件总数 = 53
带孤儿头前缀 = 53（孤儿头 1~5 个）
跳过孤儿头后**仍有行**的文件数 = 1
```

⇒ ⇒ ★ **「只跳孤儿头」救不回数据**（真实损坏在中段/尾部）⇒
⇒ **必须走打捞**（它逐字节重同步到下一个 magic，并对截断 member 做宽容解码）。

## §3 根因：三个**互相独立**的缺陷

### §3.1 缺陷①：R81 的流式切换 = **口径回归**（不是数据问题）

★ 仓库自有注释（`domains/dbdegradation/file_reader_salvage.go:3-9`）：

> 蓝绿部署多进程 O_APPEND 追加同一日文件 + 容器硬杀跳过 gzip.Close，
> 产生「孤儿 gzip header 连排 + 中段一个完整 member + 截断尾巴」。
> **gzip.NewReader 首个 member 即解码失败 → 整文件 0 条可恢复**，
> PG 恢复后即使运维手动触发恢复也拿不回任何记录。

`domains/dbdegradation/file_writer.go:65-68`（FIXME-14370）：

> 单遍 `gzip.NewReader` 读这些文件会**整文件 0 条可恢复**
> （多进程 O_APPEND + 容器硬杀跳过 gzip.Close ⇒「孤儿 header + 完整 member + 截断尾」）
> —— 仓内 `file_reader_salvage.go` 的**打捞通道才是正确读法**。
> 154 上 98 个文件里 **51 个**单遍读不出。

⇒ ⇒ ★★★ **R81 把「摘要」这个只读统计链路改成了「仓库自己标注为错误读法」的路径。**
⇒ ⇒ 这正是 LESSONS §329 的反面：**「慢」的根因在默认分支选择里** —— 但反过来，
**「快」的分支选择也可能正好落在错误读法上**。

### §3.2 缺陷②：后台刷新**几乎从不启动**

见 §1.2。指纹（`name|size|mtime`）每天/每次日文件改写都会变 ⇒ 走路径 ③ ⇒ 不触发刷新。

⇒ ⇒ 结果：**只有「缓存命中且指纹不变」的请求**（运维手动刷新页面、且那天没有新备份）才触发后台刷新。
⇒ ⇒ ★ 生产上这几乎不发生 ⇒ 「R80 的后台刷新能把真实数字算出来」这个设计**在生产上没兑现**。

### §3.3 缺陷③：`total_sessions` **恒为 1**（会话数口径失真）

证据链：

1. 端点读数：`total_records: 57644` 与 `total_sessions: 1` 并存。
2. 记录抽样（3 个好文件，各前 5000 行）：
   ```
   sessions-2026-10-23.jsonl.gz : 1331 行，全部 "type":"request_wal"，**带 session_id 的行数 = 0**
   sessions-2026-10-20.jsonl.gz : 167 行，request_wal + 1 request_log，带 session_id = 0
   sessions-2026-08-25-05.jsonl.gz: 1010 行 request_log（其余是 payload 内的类型词），带 session_id = 0
   ```
3. 记录顶层字段：`['type','timestamp','record_key','payload']` ⇒ **没有 `session_id`**。
4. `payload` 字段：`RequestID, Stage, Status, Error, OutboundBody, CompressionStrategy,
   CompressionMeta, CompletionTokens, PromptTokens, CompletedAt, UpstreamRequestAt,
   UpstreamResponseAt, UpstreamProviderID, UpstreamCredentialID` ⇒ **也没有会话维度**。

⇒ ⇒ ★★ 结论：`request_wal`/`request_log` 记录**只有请求维度（RequestID），没有会话维度**
⇒ ⇒ `BackupRecord.SessionID` 恒为空 ⇒ 「跨文件唯一 session 数」= |{""}| = **1**
⇒ ⇒ **「会话数 1」是实现把空串当成了会话**（**空串不是会话**）⇒ 这是**读数失真**，不是口径。

## §4 R82 的修法

### §4.1 摘要链路 = **快路径 + 打捞回退**（口径与 R80 逐字相同）

新文件 `domains/dbdegradation/file_reader_resilient.go`：

```
readFileSummaryResilient(ctx, filename, allowSalvage)
   ① 快路径：readFileSummaryStreaming（纯流式，完好文件 ~2.9s/106MB，比打捞快 ~15×）
   ② 快路径失败 ⇒ 回退打捞：readFileSummarySalvage（= ReadRecordsWithStats，与 R80 同一底座）
   ③ 打捞读出但**有损**（LostBytes/SkippedLines>0）⇒ 单独记账
```

⇒ ★ **口径零回归**：回退路径用的就是 R80 的 `ReadRecordsWithStats` ⇒ 记录数/会话数**逐字相同**。

### §4.2 请求路径**不做**打捞（避免 IO 风暴）

打捞会 `os.ReadFile` 整个文件（**不理会 ctx**）⇒ 5s 预算里逐个打捞 = IO 风暴
⇒ ⇒ 请求路径（inline compute）**只走快路径**；**后台刷新**才做回退（预算 30min）。

⇒ 并且：回退前先查 `ctx.Err()` ⇒ 预算耗尽后**不再**逐文件 `os.ReadFile`。

### §4.3 「有损」与「读不出」**分开记账**

```
"N/M 个备份文件读取失败：…"        ← 完全读不出
"K/M 个备份文件有损（已打捞出可恢复部分，仍有内容不可恢复）"  ← 读出来了但不完整
```

⇒ 运维能区分「文件坏了要去查链路」与「部分可恢复、档案还能救」。

### §4.4 冷启动路径**也**触发后台刷新（修缺陷②）

### §4.5 会话数口径修正 + 不可用时显式标记（修缺陷③）

- **空串不再算会话**（三处读路径统一：`readFileSummary` / `readFileSummaryStreaming` / `readFileSummarySalvage`）。
  ⇒ ★ 这是**实现 bug 修正**（空串不是会话），**不是口径变更**。
- `BackupSummary` 新增 `session_count_available bool`：
  「有记录、却一个真实 session id 都没有」⇒ `false`。
- admin handler：`false` ⇒ `degraded=true` + reason 点名「会话数不可用」。

### §4.6 顺手收敛：降级原因前缀**只加一次**

域层 `backupSummaryError()` 是唯一真值源；admin handler 不再加前缀
⇒ 修掉「`backup summary incomplete: backup summary incomplete: …`」与「冷启动路径没前缀」。

## §7 诚实边界与未做的

1. ⚠ **R82 不修「备份文件为什么会被写坏」** ⇒ 孤儿 header 的**根因**（多进程 O_APPEND + 容器硬杀跳过 `gzip.Close`）**仍在** ⇒ 新文件还会继续以同样形态产生 ⇒ **待属主裁决**（写端修复 / 保留期 / 归档口径）。
2. ⚠ **R82 不改「会话数」的口径定义**（仍是「跨文件唯一 `session_id`」）⇒ 只是修正了「空串被算成会话」并**显式标注不可用**。
   ⇒ 「会话数」到底该是什么（唯一 RequestID？唯一凭据？快照会话？）**待属主裁决**。
3. ⚠ **请求路径仍拿不到真实数字**（5s 预算 + 100 个文件）⇒ 真实数字来自**后台刷新**（约 13min）⇒ 端点在刷新完成前会显示 partial。
   ⇒ ⇒ **未做**：per-file 增量缓存（把「每天全量重算」降到「只重算变化的文件」）⇒ 属**下一轮**候选。
4. ⚠ **`ttl_stats` 那条腿仍然是「每次请求全量 SCAN ~1M 键」** ⇒ 5s 预算下**必然被打断** ⇒ 生产上 `degraded` 会长期为 true（读数里 `sessions_count` 在 30 万~61 万间波动 = 部分计数）⇒ **待属主**（是否加缓存/后台刷新）。
5. ⚠ 53 个坏文件的**可救回总量未量化**（本轮只测了 3 个样本：`394 / 0 / 148` 行）⇒ 上线后从端点读数反推。
6. ⚠ 我在生产上跑过一个「全量 `gzip -dc` 统计」脚本 ⇒ **它被 IO 阻塞 549s 且 0% CPU** ⇒ 已 kill。
   ⇒ ★★ **教训**：生产机上**不要**与网关的后台任务抢 IO；本轮的证据收集全部改成「抽样 + `gzip -t` 全量（不落盘）」。

### §9.3 ★★★ 2830 的生产读数暴露了**第三个问题（活锁）**

现象：后台刷新**已跑完**（日志 `background backup summary refresh produced incomplete result` = 1），
但端点**仍然** `total_records = 0`。

日志证据（同一时刻）：
```
"summary fell back to salvage path"            = 30   ← ★★ 打捞回退在生产生效了
"background backup summary refresh produced incomplete result" = 1  ← 后台刷新已产出结果
```

★ **机制**：指纹 = `name|size|mtime` ⇒ 当天日文件被改写 ⇒ 指纹变 ⇒ 下一次请求走
「冷启动」路径 ⇒ **就地计算**（5s 预算 ⇒ 记录数 **0**）⇒ ★ **覆盖掉了后台刷新的好结果**
⇒ ⇒ 指纹**每天都会变** ⇒ ⇒ **真实数字每天只存在十几分钟**。

★ ⇒ **修法（R82b）**：
① **只有后台刷新的结果写缓存**；请求路径的就地结果**只给本次请求**（零 IO 浪费，也零覆盖）
② **后台刷新正在跑**时 ⇒ 请求路径**不做**就地计算（否则刷新窗口内每个请求白烧 5s CPU）
③ ⇒ ★ **R80 的门判据必须改**：「部分结果要缓存」这条门守的**意图**（避免重复解压）仍成立，
　但它当时用的**手段**（请求路径就地结果写缓存）**已被生产读数证明有害**
⇒ ⇒ 判据改为「请求路径**不**写缓存」+「后台刷新结果**要**写缓存且带 partial 标记」（成对）
