## §四 usage_facts tick 首建 ATTACH"全扫 vs 30s"证伪（R71 L10 / R73 P3-2 性能半边关闭，落档）

本地 pg17 scratch（ai-native-postgres:15433，537 真实 38 列结构 + 749-equivalent DEFAULT 索引）实测 750 move-then-attach 全流程：

| 场景 | DEFAULT 行数 | ensure 耗时 |
|---|---|---|
| 首日建分区 | 1M（界外历史行） | **216ms** |
| 次日建分区 | 5M | **1.4s** |
| 跨午夜停机（界内行落 DEFAULT） | 5M + 10 万界内行 | **3.2s**（DELETE+搬移+ATTACH，行全部正确转移） |

- **机制**：ATTACH 对 DEFAULT 的约束校验**不是全扫**——带界内范围谓词，走 `usage_facts_default_occurred_at_idx`（749 产物）**Index Only Scan（0.019ms / 3 buffers）**，成本与 DEFAULT 总行数近无关。750 注释"PG 无法凭空证明，扫描仍会发生"只对一半：扫描发生但被 749 索引钉在毫秒级。
- **结论**：30s 预算（partition_manager.go:363 tick 30s + 角色级 statement_timeout）余量 20×+。owner 拍板 usage_facts/752 mock_probe_history DEFAULT TTL 时**性能半边解除**，仅剩存储增长考量。前提 749 索引在位（INVALID 由 Go ensure 自愈机理覆盖）。
- 实验方法可复现：scratch 库 537 全文 + DEFAULT 分区建 occurred_at DESC 索引 + generate_series 灌行 + `\timing` ensure。
