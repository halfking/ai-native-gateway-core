#### 3.9.0 先更正计划书的三个坐标（三处各有一处偏）

#### 3.9.1 现状读数（谁在扣、什么时候扣、失败退不退）

**A. 调用方 key 的花费预算**（★ 这才是 magpie「预算」的对位物）

| 问 | 答 | 坐标 |
|---|---|---|
| **谁在扣** | `api_keys.budget_usd`（`numeric(14,6)`）为上限；已花费用取 `usage_ledger_with_current_month` 的 `cost_usd` 求和（`DISTINCT ON (request_id)` 去重）⇒ **窗口 = 当月** | `sql/objects/tables/api_keys.sql`、`domains/authentication/verifier.go:823-866` |

**B. 凭据的并发/速率限额**（magpie 的「预算」在**这个**维度上才勉强对位）

| 机制 | 扣什么 | 什么时候扣 | 失败退不退 |
|---|---|---|---|
| 并发四层信号量（global/pool/credential/identity） | 并发名额 | `Acquire` 时占 | **退**（`ReleaseFunc` 成对释放；获取失败的路径也逐层回滚） |
| RPM 滑窗预约（`domains/credential/rpm_memory.go` / `rpm_redis.go`） | 每分钟**请求数** | `CheckAndReserve` 时记入 60s 窗口 | **不退**（`RPMLimiter` 接口只有 `CheckAndReserve`，**无 refund**） |

★ RPM 的扣减**时序是刻意设计**的，代码里写了理由（`domains/credential/limiter.go:548-552`）：
> "Reserve RPM only after the request owns a credential slot. Recording before semaphore
> acquisition would charge requests that timed out or failed at an outer concurrency layer,
> causing false rate-limit failures."

⇒ 即：**外层超时/失败的请求不扣 RPM**；但**预约成功后上游调用失败 ⇒ RPM 名额不退还**
（这大概率是**对的**：RPM 限的是「上游收到了多少请求」，请求已经发出去了）。

#### 3.9.2 缺口（★ 这才是 P1-3 真正的问题）：**并发双花**

`CheckBudget` 是**只查不占** ⇒ ⇒ **从检查到用量落库可见之间，同一 key 的 N 个并发请求
全部通过检查** ⇒ **实际花费可以超出 `budget_usd` 达「N × 单请求成本」**。

★ 这个窗口**没有**被别的东西兜住：
- per-key 的并发上限（`api_keys.rate_limit_concurrent`）是**软上限**
  （`TryAcquire` 失败即 bypass，只打 warn）⇒ **不构成有界约束**；
- 限流器是**进程内**的 ⇒ 多实例部署下窗口更大；
- `budget_usd` 的窗口是**当月**，跨月自动重置（这是设计，不是缺陷）。

⇒ ⇒ 这正是计划书验收②说的「**含并发双花**」。

#### 3.9.3 结论：**本轮不引入** magpie 式的「预留—释放—拒绝」三态（登记为待裁决）

理由三条：

1. **语义不对齐**：magpie 的三态服务的是「**按预估花费**预留、结束后**按实际**结算」；
   本仓**没有「预估成本」这个量**（成本要等上游返回才有）⇒ 硬做只能预留一个
   **拍脑袋的保守值** ⇒ 要么过松（形同虚设）、要么过紧（误杀正常请求）。
2. **真正的收口需要跨节点预留存储**：本仓是多实例部署 ⇒ 进程内预留只能把超支上界
   从「N × 单请求成本」降到「实例数 × N × 单请求成本」⇒ 要真收口就得有
   **Redis/DB 预留 + 结算口径 + 价格表来源** ⇒ **属新增产品能力，不是「对齐 magpie」**。
3. **现有闸门的失败策略已经是对的**（fail-closed）⇒ 没有「先把闸门变松」的风险；
   **唯一要做的是把双花窗口显式化**，而不是悄悄换个语义。

⇒ **待裁决项（需属主拍板，本轮不猜）**：
① 预留存储放哪（Redis vs DB vs 不做）；② 预估成本从哪来（模型价格表 vs 该 key 上次用量均值）；
③ 窗口沿用「当月」还是另设；④ 超限时是 402 拒绝还是降级到更便宜的候选。

#### 3.9.4 本轮可落地（**零生产语义变更**）：把现状钉成契约

### 3.10 P1-4 · 按候选改写的类型化契约（`RewritePoint`）

#### 3.10.1 落点：**不新建第二套机制**

计划书 §5.2 的取舍是「(a) 进程内脚本引擎 vs (b) **Go 侧的类型化改写点**」，
并明确建议走 **(b)**（「本仓 S4 改造矩阵承担改写职能，脚本会引入第二套改写机制」）。

★ 而本仓的「S4 改造矩阵」**已经存在**，就是
`domains/streaming/executors/executor_chat.go` 的
`prepareRequestBody(params, cand, ledger...)` —— 它**逐候选**成型请求体：
换模型名 → 注入 `stream_options` → 白名单 → 折叠 tool 历史 → 能力消毒 →
合并连续消息 → 上下文压缩。⇒ ★ **它就是「按候选改写」唯一的收口点**。

⇒ 所以 P1-4 的产出是**把这条管道上的「改写」定成契约**，而不是再加一层。

#### 3.10.2 契约（`internal/rewrite`，stdlib-only）

| 类型 | 作用 |
|---|---|
| `RewritePoint{Point, Provider, Model}` | ★ **计划书的原词**（仓内无同名冲突）：在哪个**位置**、对哪个**候选**。`Provider`/`Model` **留空 = 匹配任意** ⇒ 选择器是**逐维收窄**的 |
| `Point` | 管道位置：`after_model`（已按候选换完模型名）/ `before_send`（即将发往上游） |
| `Spec{RewritePoint, Field, Value, Timeout, OnFailure}` | 一条规则：**只允许改一个顶层字段**；`Value` **原样写入**（不规范化 ⇒ 保真） |
| `Apply(ctx, point, body, cand, specs)` | 应用全部匹配规则；**纯函数** |

**三条硬语义**（都是「结构性保证」，不是事后校验）：

1. **字节保真** ⇒ 实现是**外科式字节替换**：定位目标字段的**值区间** `[start,end)`，
   结果 = `body[:start] + 新值 + body[end:]` ⇒ **其余字节逐字不动**。
   ★ 若改成「反序列化再序列化」，键序/空格/数字字面量全变 ⇒ 这条契约就无从谈起。
   ★ 定位只看**顶层**：嵌套对象里的同名字段**不算数**。
2. **失败 ⇒ 原样发出**（默认 `fail-open`）：改写是**增强**不是**闸门**，
   把一个本来能成功的请求打死是更坏的结果；确需 fail-closed 必须**显式声明**。
   每条规则**独立超时**（默认 2s），超时按失败处理。
3. **逐候选隔离** ⇒ `Apply` 是**纯函数**（不改入参、不持有可变状态）
   ⇒ 同一请求的不同候选互不污染。★ 这也是「失败不污染后续候选」的根保证。

#### 3.10.3 门（`internal/rewrite/rewrite_test.go`，9 条）

- ① **只动目标字段**：结果与原 body 相比**只有**目标字段的值区间变了（前缀/后缀**逐字**比对）
- ② **嵌套同名字段不被改**（★ 用例里嵌套的那个**故意放在前面** ⇒ 抓得住「朴素全文搜索」的实现）
- ③ **失败 ⇒ 原样发出**（5 个失败形态：字段不存在 / `Field` 为空 / `Field` 是路径 / `Value` 非法 JSON / 未知失败策略）
- ④ **fail-closed ⇒ 返回错误**且不返回 body
- ⑤ **超时 ⇒ 原样发出**（★ 用**注入点**确定性触发 ⇒ 不用 1ns 赌运气）
- ⑥ **不同候选互不污染**（各自命中自己的规则 + **原始 body 一个字节没变** + 两个结果不同）
- ⑦ 选择器**逐维收窄**（只填 `Provider` ⇒ 匹配任意模型）
- ⑧ `Point` 是选择器的一维（位置不匹配 ⇒ 不生效）
- ⑨ `Apply` 是**纯函数**（不改入参 + 两次调用结果逐字相同）

**变异证据**（全红、还原绿、md5 逐字校验）

| 变异 | 手法 | 结果 |
|---|---|---|
| M1 | 改成「反序列化再序列化整个 JSON」 | **红**（字节保真那条：「目标字段之前的字节变了」） |
| M2 | 失败默认从 fail-open 翻成 fail-closed | **红**（失败原样发出那条） |
| M3 | 定位器退化成「朴素全文搜索第一个同名字段」 | **红**（嵌套那条：命中了嵌套的 `model`） |
| M4 | 改写改成**原地修改入参** | **红**（候选隔离 + 纯函数两条） |
| M5 | **忽略** `Spec.Timeout`（固定 10s） | **红**（超时那条） |

#### 3.10.4 诚实边界

★ 本包是**契约 + 参考实现**，**尚未接线到 `prepareRequestBody`**：
计划书 P1-4 的措辞是「把 (b) 路径**定成接口**」⇒ 契约先定死；
「**规则从哪来**（配置面：settings / DB / 管理端？）」与**接线**属后续。

### 3.13 P2-2 · 扩展点台账（运行期计数 + 静态裁决合并）

> 计划书 §6-P2-2：「按扩展点登记『调用次数 / p99 / 失败数 / 超时数 / 最近错误』，
> admin 可查」
> ⇒ 验收 = 读端能查到这五个量。

#### 3.13.1 现状读数：台账是**两半**，一半已有、一半缺

| 半 | 内容 | 本仓现状 |
|---|---|---|
| **静态半** | 名称 / 代码位置 / 裁决 / **是否在生产** / 所挂 phase | ✅ **已经有了** —— `internal/extpoints` 的裁决表（P0-1 落的） |
| **运行期半** | 调用次数 / p99 / 失败数 / 超时数 / 最近错误 | ❌ **缺** —— 本轮补的就是这一半 |

⇒ ⇒ 本轮**不重造**静态半，而是把运行期半做成 `internal/extpointledger`，
并让两者**共用同一套机制 ID**（`extpoints.ID*`）⇒ 机制 ID 是**单一真值源**。

#### 3.13.2 ★ 为什么合并逻辑住在 `internal/` 而不是 `admin/`

门必须住在**CI 一定跑**的地方。⇒ `admin` 包的测试套件实测 **65.8s**
（逼近 `GUARD_PACKAGES` 快门的 `-timeout=120s`）⇒ 门放进 `admin/` ⇒
它要么跑不到、要么把 CI 拖到超时。⇒ ⇒ **合并逻辑与载荷形状下沉到
`internal/extpointledger`**，门住 `scripts/ursmcheck`（CI 必跑），
`admin/` 只做**薄壳**（序列化 + 鉴权，零业务判断）。

> ⚠ `admin` 包**故意不登记**进 `GUARD_PACKAGES` ⇒ 它的门**故意不带**
> `AUDIT-GUARD` 标记 ⇒ 主要判据放在台账包与 ursmcheck。

#### 3.13.3 为什么是「进程内、内存有界」而不是写 DB

台账是**观测面**，不是**账本**：

1. 它要能在**进程崩溃后消失**（那才是它没有撒谎的证据）；
2. 写 DB 会在请求热路径上引入 IO ⇒ 观测面拖慢数据面 ⇒ 观测面被关掉。

⇒ 口径：**进程内、只读快照、可随时丢**；每个机制只保留**最近 256 个**延迟样本
（环形缓冲，覆盖最旧）⇒ 内存有界（6 机制 × 256 个 `time.Duration` ≈ 12 KiB）。
⇒ p99 = **最近窗口**的 p99（最近秩法 `idx=(99*n+99)/100`）⇒
★ 这个口径**必须写在读端上**（每行 `p99_window` + 载荷级 `ledger_scope`）。

#### 3.13.4 ★ 记账粒度 = **单个拦截器的一次调用**（不是一次链调用）

`domains/hooks/response/chain.go` 的三个入口
（`InterceptNonStream` / `InterceptStreamChunk` / `InterceptStreamEnd`）
**逐拦截器**记账。

⇒ 理由：**被吞掉的失败**（拦截器报错、链继续往下走）才是台账最该看见的东西
⇒ 链级记账会把它们算成「成功」⇒ ★ **「失败数」永远是 0** ⇒ 台账失去意义。
⇒ 门用**增量**断言（默认台账是进程级全局 ⇒ 不能用绝对值）。

#### 3.13.5 ★ 两份**独立来源**可互相印证

- 静态半的 `Production` 来自**源码扫描**（裁决表）；
- 运行期半的计数来自**运行期计数**（台账）。

⇒ 「裁决表说不在生产」⇒「台账调用次数为 0」⇒ 两份来源一致；
⇒ 「裁决表说在生产、但台账恒为 0」⇒ ★ **有人把扩展点悄悄摘了**。

#### 3.13.6 ★ 诚实边界：「0」有两种成因 ⇒ 必须显式区分

`calls = 0` 有**三种**成因，读端若分不清就会误读：

| 形态 | 含义 | 现状 |
|---|---|---|
| `Production=false`（判死 / 别名 / 骨架） | **正常**，本来就不在生产路径上 | ★ **4 个**（`request_pipeline` / `hook_registry` / `hook_phase_vocabulary` / ★★ `executor_hooks` —— 最后这个是 **§3.14 订正**后才变成 dead 的） |
| `Production=true` 且**没接台账**（★ **静态**事实：源码里没有记账调用） | ★ **这个扩展点还没接台账** | ★ **0 个**（★ §3.15 把最后一个也接上了） |
| `Production=true` 且已接、但本次进程内**没流量**（★ **运行期**事实） | 没流量 | **2 个**（`http_middleware_chain` / `response_intercept`，取决于进程内是否被调过） |

★ ⇒ 这两种「0」现在**由两个不同的字段**表达：`Wired`（静态：接没接）
与 `Recorded`（运行期：有没有流量）⇒ ★ `Unwired` = `Production && !Wired`
⇒ **与流量无关** ⇒ ★★ 初版把 `Unwired` 定义成 `Production && !Recorded`
⇒ 「刚启动还没来请求」会被误标成「未接线」⇒ ★ **自查修掉**（§3.15.7）。

⇒ ⇒ 因此读端**显式暴露** `unwired`（= `Production && !Recorded`）
⇒ ★ 它**不蕴含**「它真的没流量」（进程重启即清零）⇒ 措辞是「尚未接入台账」。

⇒ ★ **本轮只有 `response_intercept` 一个机制真的接线了** ⇒ 其余 5 个机制的
运行期计数**恒为 0** ⇒ 这是**如实反映现状**，不是缺陷；但**必须可见**
⇒ 否则 admin 页面会把「还没接线」读成「这个扩展点没人用」。

### 3.15 P2-2 续 · 主链接进台账（`http_middleware_chain`）+ 接线覆盖率门

#### 3.15.1 ★ 先量成本，再决定接不接

★ 台账住在**请求热路径**上 ⇒ 「观测面拖慢数据面 ⇒ 观测面被关掉」这条纪律
要求**先量**，而不是先写再猜。

实测（`internal/extpointledger/bench_test.go` —— ★ **常驻**的 benchmark，
不是一次性测量；Apple M4 Max / Go 1.27.2）：

| 场景 | 每次成本 |
|---|---|
| 1 goroutine | **40.1 ns/op** |
| 4 goroutines | 144.2 ns/op |
| 16 goroutines | 147.5 ns/op |
| 64 goroutines | 131.6 ns/op |
| 读端快照 | 642.0 ns/op |

⇒ **百纳秒量级**，且 64 并发**没有出现拐点** ⇒ ⇒ **不需要分片**
⇒ 相对网关请求的百毫秒～数十秒级（LLM 调用）⇒ 占比 < 0.001% ⇒ **可以接主链**。

#### 3.15.2 ★★ p99 量的是「主链自身的开销」，不是整个请求的耗时

★ 主链包着业务处理（LLM 调用动辄百毫秒～数十秒）⇒ 若把「整段耗时」
当扩展点的 p99 ⇒ ★★ 那个数会被 LLM **主导** ⇒ 「扩展点耗时」这个指标**废了**
⇒ 读端会被一个「秒级 p99」误导。

⇒ ★ 而**只在外面包一层也减不出来**（通用式见 `LESSONS.md §361`③）：外层看到的 `inner` **包含主链自己**
⇒ `总耗时 − inner` ≈ 0 ⇒ 量不到链的开销（★ 这是本轮实现时踩到的一个真实错误）。

⇒ ⇒ 拆成**两个探针**：

| 探针 | 装在哪 | 量什么 |
|---|---|---|
| ★ 外层 `LedgerMiddleware` | **整条链**外面 | 总耗时 |
| ★ 内层 `LedgerInnerProbe` | 链的**最里侧**（业务处理器外面） | 业务耗时 |

⇒ **链开销 = 总耗时 − 业务耗时**；两者通过 **request context** 里
**每请求一份**的计时结构通信 ⇒ ★ **并发安全**（不共享变量、不用全局）。
⇒ ★ **降级可工作**：只装外层探针 ⇒ 仍然记账，只是 p99 口径变粗
⇒ **不会因为漏装内层探针就数据全错**（有门钉住，见 §3.15.4②）。

#### 3.15.3 ★★ 拒绝与出错**分开**（`rejected` vs `failed`）

主链有两种「没让请求通过」：

| 形态 | 状态码 | 含义 | 计入 |
|---|---|---|---|
| **拒绝** | 4xx | Auth / Origin / SecurityHeaders **按设计**拦下来了 ⇒ 扩展点在**正常工作** | `rejected` |
| **出错** | 5xx | panic 兜底、下游处理器报错 | `failed` |
| 超时 | — | ctx 到期 | `timeout` |

⇒ 混在一个「失败数」里 ⇒ ★ 运维看到主链失败数飙升，第一反应是「网关坏了」，
而真相可能只是**有人在狂刷坏 key** ⇒ ⇒ **口径失真**。
⇒ ⇒ 台账模型因此新增 `OutcomeRejected`（`internal/extpointledger`）。

⚠ **口径边界（写进 `ledger_scope.outcome_caliber`）**：4xx 也可能来自**客户端**
（400 参数错、404 路由不存在）⇒ 本仓的 4xx **绝大多数**来自鉴权闸门 ⇒ 口径成立；
★ 若日后要区分「闸门拒绝」与「客户端自己错」，那是**读端**的事（拆两个字段）。

#### 3.15.4 ★ 接线覆盖率门（**源码级**，不与「有没有流量」混淆）

| 门 | 判据 |
|---|---|
| ① 在产的机制必须接了台账 | 每个 `Production=true` 的机制，生产代码里必须有**记账调用**（按 `internal/extpoints` 的**常量名**扫描；★ **排除裁决表自身** —— 同 §3.14） |
| ② 两个探针都装了 | `cmd/gateway/main.go` 里 `middleware.LedgerMiddleware(` 与 `middleware.LedgerInnerProbe(` 都在 |

★ **为什么是源码级而不是运行期**：运行期只能看到「本次进程内有没有流量」
⇒ 那会把「**没接线**」与「**没流量**」混成同一件事（§3.13.6 的三种成因）
⇒ ⇒ **必须分开放**：源码级只看「记账调用点存在与否」⇒ 与流量无关。

★ 门里的「ID ⇒ 常量名」映射**硬编码**在门里（不从裁决表派生）⇒
裁决表改不动断言；且它同时断言了「ID 与常量名的对应关系」本身。

#### 3.15.7 ★★ 自查抓到的设计缺陷：「**没接线**」是**静态**事实，我一开始用成了**运行期**事实

★ 这是本轮**自己写完门之后**被自己的门抓到的（不是被别人抓的）：

初版 `Unwired` 定义成 `Production && !Recorded`（`Recorded` = 运行期
「本次进程内被记到过」）⇒ ★★ **这是错的**：

| 场景 | `Recorded` | 初版 `Unwired` | 读端会说 | 真相 |
|---|---|---|---|---|
| **接好了**，本次进程内**还没流量**（刚启动还没来请求） | false | **true** | 「**尚未接入台账**」 | ★ **它接了** |

⇒ ⇒ 也就是说，我原本声称要解决的误读（「分不清『没接线』与『没流量』」），
★ **自己又犯了一遍** —— 只是把它从「没流量」挪到了「没接线」。

⇒ ⇒ **修法：把三个事实彻底分开**：

| 事实 | 来源 | 字段 |
|---|---|---|
| **接没接台账** | ★ **静态**（源码 + 静态接线表） | `Wired` / `WiringLocation` |
| 有没有流量 | ★ **运行期**（计数器） | `Recorded` / `Calls` |
| 在不在生产 | ★ **静态**（裁决表） | `Production` |

⇒ `Unwired` = `Production && !Wired` ⇒ ★ 语义终于对上，且**与流量无关**。

⇒ ★ **静态接线表**（`internal/extpointledger/wiring.go`）的值刻意选成
**仓库相对文件路径**（而不是一句自由文本）⇒ ⇒ 门可以**真的去读那个文件**、
确认它**真的用到了**该机制的常量（`extpoints.ID…`）⇒ ★ **静态半与源码半
两份来源对拍** ⇒ ★ 改了接线位置忘了改表 ⇒ **门会红**（而不是让读端默默说假话）。

**变异证据**（M16–M18 全红；还原后 md5 逐字校验）：

| 变异 | 手法 | 结果 |
|---|---|---|
| M16 | ★ 静态接线表里删掉一个在产机制 | **红**（包内「接线表 vs 裁决表」门 + ursmcheck 接线门） |
| M17 | ★ `Unwired` 退回运行期口径（`!Recorded`） | **红**（包内 unwired 语义门 + ursmcheck 空台账断言） |
| M18 | ★ 静态接线表里的文件路径写错 | **红**（ursmcheck 接线门：读不到文件） |

⇒ ★★ 通用式：★★ **「静态事实」与「运行期事实」不能共用一个标志位** ——
★★ 一个字段一旦要同时表达两件事，**它必然在其中一个场景下说假话**。
★★ ⇒ 凡读端要区分「A 造成的」与「B 造成的」，**A 与 B 必须来自不同来源**。

#### 3.15.6 ★ 顺带修掉一处「**天天红**的门」

★ `middleware` 包的门 `TestWebPublicRootFilesAreAllAccountedFor`
在**每个 macOS 检出上都是红的**：`web/public/.DS_Store`（macOS 产物）
既没登记为「匿名豁免」、也没登记为「构建期产物」。

### 3.16 ★ 合并他人提交时撞见的「main 上已经红着」——以及一条**钉形态**的门

> 这条是本轮的**流程教训**，不是 magpie 对齐本身的内容。
> 但它同时暴露了一个**可复用的判据原则**，所以留档。

#### 3.16.1 现象

★ 合并并行会话的提交（`f204e4c6a`）后，我按惯例跑了**本轮自己涉及**的包
（`cmd/gateway` / `middleware` / `internal/extpointledger`）⇒ 全绿
⇒ ★★ **但我没跑 `admin` 包** —— 理由是「我这一轮没改 `admin`」
⇒ ★★ **错**：那笔提交改了 `admin/turns_sessions.go` ⇒ **`admin` 包是「受影响包」**
⇒ ⇒ 跑起来：**红**。

⇒ 用 worktree 对拍 `origin/main`（`git worktree add --detach`）⇒
★ **红在 main 上**（不是我的合并引入的）⇒ 是那笔提交把
`admin/turns_sessions_test.go` 的断言**留在了旧形态**。

#### 3.16.2 根因：门钉的是**形态**，不是**语义**

★ 谓词形态在两天里**变过两次**：

| 轮次 | 形态 | 断言 |
|---|---|---|
| R90 | `rl.api_key_id = $2` | 改成「CASE 表达式 = $2」 |
| R92 | ★ **派生表 UNION ALL + 单一 EXISTS** ⇒ `ft.api_key_id = $2` | ★ **没跟着改** ⇒ 红 |

⇒ ⇒ ★★ **通用式**：★★ **判据要钉【语义】，不要钉【形态】** ——
★★ 形态会随实现演进，**语义（「api_key_id 谓词必须绑到 $2」）不会**。
★★ ⇒ ★★ 钉形态 ⇒ 形态一变就**假红**，而**实现可能完全正确**
★★ ⇒ ★★ **假红比假绿更费**：它会让人去改**本来正确的实现**。

⇒ ⇒ 改法：断言 `api_key_id = $2` **或** `END) = $2`（两种已知形态都接受）
⇒ ★ 仍能抓住本门真正的猎物（占位符被 `fmt.Sprintf` 吃掉）。
⇒ ★ 变异验证：把 `$2` 改成 `$1` ⇒ **红** ⇒ 门**仍有牙**。

⇒ ⇒ ★★★ **同一条形态迁移，一共有【三条】断言过期**（全在
`admin/turns_sessions_test.go`，全在 `f204e4c6a` 之后变红）：

| # | 位置 | 过期断言 | 改成的**语义**断言 |
|---|---|---|---|
| 1 | `:415` | `(CASE … END) = $2`（R90' 形态） | `api_key_id = $2` **或** `END) = $2`（形态不限） |
| 2 | `:278` | 同上（另一处） | ① 归一表达式在 SQL 里（**口径**）＋ ② 谓词绑到 `$2`（**绑定位置**） |
| 3 | `:213/:216` | `EXISTS (SELECT 1 FROM public.session_turns_hot t` / `OR EXISTS (… FROM public.session_turns t`（R90 的两腿 OR 形态） | 两腿的 `FROM public.session_turns_hot t` / `FROM public.session_turns t` **都在** + 有 `EXISTS` |

⇒ ★ 顺带修掉一处**名实不符**：第 3 条的兄弟断言里写着 `"t.model = $2"`，
⇒ 而 R92 形态的 `ft.model = $2` **恰好含子串** `"t.model = $2"` ⇒ **侥幸命中**
⇒ ⇒ 改成 `"model = $2"`（**不带** `t.` 前缀）⇒ 两种形态都成立，且语义明确。

⇒ ★ 变异验证（合并后跑）：把 `"model = $2"` 改成 `"model = $9"` ⇒ **红**
⇒ 还原 ⇒ **绿**，md5 逐字一致 ⇒ ⇒ **门仍有牙**。

#### 3.16.3 ★★ 结构性缺口：不在任何 CI 路径上的包，它的红没人看见

★ `admin` 套件实测 **66s** ⇒ 我当初**故意**没把它登记进快门（`-timeout=120s`）
⇒ ⇒ ★★ 于是**它没有任何 CI 路径** ⇒ ⇒ **它在 main 上红着，而 CI 是绿的**。

⇒ ⇒ ★★ 推论：★★ **「把重包排除出快门」是对的，但必须给它一条【别的】CI 路径**
★★ ⇒ ★★ 否则「排除」就等于「放弃监督」⇒ ★★ 而**放弃监督的东西一定会烂**
★★ （本轮就烂了 ⇒ 潜伏到被人合并时才暴露）。

⇒ ⇒ 建议：★ `admin` 登记进**慢门**（`GUARD_PACKAGES_SLOW`，`-timeout=900s`）
⇒ ★ 而不是快门（66s 在 120s 上限里太悬 ⇒ CI 机慢一倍就超时 ⇒ ⇒ 会把 CI 拖垮）。
⇒ ⚠ 本轮**未**登记（属**结构性改动**，且慢门目前只放 `scripts/ursmcheck`）⇒ 登记。
