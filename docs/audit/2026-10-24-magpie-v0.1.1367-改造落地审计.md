## 〇、结论（先读这一节）

1. **计划书对本仓现状的断言，逐条回源码核实完毕：11 条断言里 8 条成立、1 条漂移、2 条是计划书自身的错误。**
   两处计划书错误都是**可执行判据的错误**（不是措辞问题）：
   - 「rest 词表 **19 类**」⇒ magpie 源码里实测 **20 个** `fail*` 常量（计划书自己列出的名字也是 20 个）；
   - 「首字节超时**第三次**才 rest」⇒ magpie 的 `slowRests = 2` 实际是**第 2 次**就 rest。

2. **P0 的 5 项**全部落地**（P0-1 … P0-5），每一项都带**去掉即红**的门；
   另落地 **P1-1（统一请求级观察者，已接 v1 真实路径）**、
   **P1-2（策略只排序的契约，含"迁移前后顺序一致"的对拍）**、
   **P1-5（失败策略表：16 个 phase × 终止/继续/挂起，`domains/hooks` 已改为引用）**，
   以及 **P1-3 的「先出结论」部分**（见第 7 条）。

3. **本轮落地了三处真实的语义修复**（不是"把计划书抄成代码"）：
   - **首字节超时第一次不再罚任何人**（此前第一次就冷却 (凭据,模型) 绑定 5 分钟）；
   - **账号被厂商限制不再被永久摘除**（此前 403 一律归 `KindAuth`，而它是 `Permanent=true`）；
   - **回复陷入循环不再与"空回复"混为一谈**（此前一律记 `KindEmptyResponse`）。

4. **三条"声明与实现不同源"被消掉**（本仓反复吃过的亏）：
   - 插件能力表里 3 条**没有 handler** 的路由 ⇒ 现在标 `Implemented:false` 且 **manifest 声明即拒**；
   - 扩展点裁决表写在**代码**里（`internal/extpoints`），门禁逐条**扫源码对拍现实**；
   - 「罚/不罚」的判定写在**代码**里（`errorsx/restclasses.go` 的 `Target` 字段），
     而不是注释里 ⇒ 门可以直接对拍 `PenaltyOf`。

5. **P1-2 落地的同时纠正了一处命名陷阱**：本仓**已经有** `autoroute.Strategy`
   —— 它是**分类器**的 A/B 策略（产出"这次请求判成什么任务类型"），
   与 magpie 的**候选顺序**策略**不是一回事** ⇒ 新契约用 `internal/routeorder`
   命名空间（`routeorder.Strategy`），避免"一个名字指两件事"。

6. ★★★★★ **本轮抓到一处「自证型门」：门从被测对象取被测集合 ⇒ 改表即改断言 ⇒ 变异静默通过。**
   P1-5 的门最初把行为级断言的被测集合取自**被它监管的那张策略表**
   ⇒ 变异「把 `routing` 从终止改成继续」之后，它直接从被测集合里消失 ⇒ **门照样绿**。
   ⇒ 修法：期望**硬编码在门里**、与表**互为对照**。
   ⇒ ★★ 通用式：**「表即真值源」与「门从表里取被测集合」是互相打架的两条** ——
   真值源可以只有一份，但**断言的期望不能从真值源派生**。
   ⇒ 详见 §3.8 与 `LESSONS.md §355`。

7. ★★★★ **P1-3 找到了一个真实的并发双花缺口，但本轮判为「不照搬、只钉现状」。**
   本仓**确实有** per-key 月度预算（`api_keys.budget_usd` + 当月账本 `usage_ledger_with_current_month`），
   闸门在**认证之后、执行之前**做 pre-flight check，且**失败是 fail-closed**（DB 故障 ⇒ 503，不是放行）。
   ⇒ ★ **缺口**：它是**只查不占**的 ⇒ **从检查到用量落库可见之间，同一 key 的 N 个并发请求全部通过**
   ⇒ 实际花费可超出 `budget_usd` 达「N × 单请求成本」。
   ⇒ ★ **不引入** magpie 式的「预留—释放—拒绝」三态：本仓**没有「预估成本」这个量**（成本要等上游返回），
   硬做只能预留一个拍脑袋的保守值；且真正的收口需要**跨节点**预留存储 ⇒ **属新增产品能力，需属主裁决 4 项**。
   ⇒ 本轮落地的是 **6 条现状契约门**（零生产语义变更），其中「**并发下 RPM 不双花**」
   补上了全包**此前完全没有**的一格覆盖。详见 §3.9。

#### 3.9.1 现状读数（谁在扣、什么时候扣、失败退不退）

**A. 调用方 key 的花费预算**（★ 这才是 magpie「预算」的对位物）

|---|---|---|

| RPM 滑窗预约（`domains/credential/rpm_memory.go` / `rpm_redis.go`） | 每分钟**请求数** | `CheckAndReserve` 时记入 60s 窗口 | **不退**（`RPMLimiter` 接口只有 `CheckAndReserve`，**无 refund**） |

★ RPM 的扣减**时序是刻意设计**的，代码里写了理由（`domains/credential/limiter.go:548-552`）：
> "Reserve RPM only after the request owns a credential slot. Recording before semaphore
> acquisition would charge requests that timed out or failed at an outer concurrency layer,
> causing false rate-limit failures."

⇒ 即：**外层超时/失败的请求不扣 RPM**；但**预约成功后上游调用失败 ⇒ RPM 名额不退还**
（这大概率是**对的**：RPM 限的是「上游收到了多少请求」，请求已经发出去了）。

#### 3.9.2 缺口（★ 这才是 P1-3 真正的问题）：**并发双花**

`CheckBudget` 是**只查不占** ⇒ ⇒ **从检查到用量落库可见之间，同一 key 的 N 个并发请求
全部通过检查** ⇒ **实际花费可以超出 `budget_usd` 达「N × 单请求成本」**。

★ 这个窗口**没有**被别的东西兜住：
- per-key 的并发上限（`api_keys.rate_limit_concurrent`）是**软上限**
  （`TryAcquire` 失败即 bypass，只打 warn）⇒ **不构成有界约束**；
- 限流器是**进程内**的 ⇒ 多实例部署下窗口更大；
- `budget_usd` 的窗口是**当月**，跨月自动重置（这是设计，不是缺陷）。

⇒ ⇒ 这正是计划书验收②说的「**含并发双花**」。

#### 3.9.3 结论：**本轮不引入** magpie 式的「预留—释放—拒绝」三态（登记为待裁决）

理由三条：

1. **语义不对齐**：magpie 的三态服务的是「**按预估花费**预留、结束后**按实际**结算」；
   本仓**没有「预估成本」这个量**（成本要等上游返回才有）⇒ 硬做只能预留一个
   **拍脑袋的保守值** ⇒ 要么过松（形同虚设）、要么过紧（误杀正常请求）。
2. **真正的收口需要跨节点预留存储**：本仓是多实例部署 ⇒ 进程内预留只能把超支上界
   从「N × 单请求成本」降到「实例数 × N × 单请求成本」⇒ 要真收口就得有
   **Redis/DB 预留 + 结算口径 + 价格表来源** ⇒ **属新增产品能力，不是「对齐 magpie」**。
3. **现有闸门的失败策略已经是对的**（fail-closed）⇒ 没有「先把闸门变松」的风险；
   **唯一要做的是把双花窗口显式化**，而不是悄悄换个语义。

⇒ **待裁决项（需属主拍板，本轮不猜）**：
① 预留存储放哪（Redis vs DB vs 不做）；② 预估成本从哪来（模型价格表 vs 该 key 上次用量均值）；
③ 窗口沿用「当月」还是另设；④ 超限时是 402 拒绝还是降级到更便宜的候选。

### 3.10 P1-4 · 按候选改写的类型化契约（`RewritePoint`）

#### 3.10.1 落点：**不新建第二套机制**

计划书 §5.2 的取舍是「(a) 进程内脚本引擎 vs (b) **Go 侧的类型化改写点**」，
并明确建议走 **(b)**（「本仓 S4 改造矩阵承担改写职能，脚本会引入第二套改写机制」）。

★ 而本仓的「S4 改造矩阵」**已经存在**，就是
`domains/streaming/executors/executor_chat.go` 的
`prepareRequestBody(params, cand, ledger...)` —— 它**逐候选**成型请求体：
换模型名 → 注入 `stream_options` → 白名单 → 折叠 tool 历史 → 能力消毒 →
合并连续消息 → 上下文压缩。⇒ ★ **它就是「按候选改写」唯一的收口点**。

⇒ 所以 P1-4 的产出是**把这条管道上的「改写」定成契约**，而不是再加一层。

#### 3.10.2 契约（`internal/rewrite`，stdlib-only）

| 类型 | 作用 |
|---|---|
| `RewritePoint{Point, Provider, Model}` | ★ **计划书的原词**（仓内无同名冲突）：在哪个**位置**、对哪个**候选**。`Provider`/`Model` **留空 = 匹配任意** ⇒ 选择器是**逐维收窄**的 |
| `Point` | 管道位置：`after_model`（已按候选换完模型名）/ `before_send`（即将发往上游） |
| `Spec{RewritePoint, Field, Value, Timeout, OnFailure}` | 一条规则：**只允许改一个顶层字段**；`Value` **原样写入**（不规范化 ⇒ 保真） |
| `Apply(ctx, point, body, cand, specs)` | 应用全部匹配规则；**纯函数** |

**三条硬语义**（都是「结构性保证」，不是事后校验）：

1. **字节保真** ⇒ 实现是**外科式字节替换**：定位目标字段的**值区间** `[start,end)`，
   结果 = `body[:start] + 新值 + body[end:]` ⇒ **其余字节逐字不动**。
   ★ 若改成「反序列化再序列化」，键序/空格/数字字面量全变 ⇒ 这条契约就无从谈起。
   ★ 定位只看**顶层**：嵌套对象里的同名字段**不算数**。
2. **失败 ⇒ 原样发出**（默认 `fail-open`）：改写是**增强**不是**闸门**，
   把一个本来能成功的请求打死是更坏的结果；确需 fail-closed 必须**显式声明**。
   每条规则**独立超时**（默认 2s），超时按失败处理。
3. **逐候选隔离** ⇒ `Apply` 是**纯函数**（不改入参、不持有可变状态）
   ⇒ 同一请求的不同候选互不污染。★ 这也是「失败不污染后续候选」的根保证。

#### 3.10.3 门（`internal/rewrite/rewrite_test.go`，9 条）

- ① **只动目标字段**：结果与原 body 相比**只有**目标字段的值区间变了（前缀/后缀**逐字**比对）
- ② **嵌套同名字段不被改**（★ 用例里嵌套的那个**故意放在前面** ⇒ 抓得住「朴素全文搜索」的实现）
- ③ **失败 ⇒ 原样发出**（5 个失败形态：字段不存在 / `Field` 为空 / `Field` 是路径 / `Value` 非法 JSON / 未知失败策略）
- ④ **fail-closed ⇒ 返回错误**且不返回 body
- ⑤ **超时 ⇒ 原样发出**（★ 用**注入点**确定性触发 ⇒ 不用 1ns 赌运气）
- ⑥ **不同候选互不污染**（各自命中自己的规则 + **原始 body 一个字节没变** + 两个结果不同）
- ⑦ 选择器**逐维收窄**（只填 `Provider` ⇒ 匹配任意模型）
- ⑧ `Point` 是选择器的一维（位置不匹配 ⇒ 不生效）
- ⑨ `Apply` 是**纯函数**（不改入参 + 两次调用结果逐字相同）

**变异证据**（全红、还原绿、md5 逐字校验）

| 变异 | 手法 | 结果 |
|---|---|---|
| M1 | 改成「反序列化再序列化整个 JSON」 | **红**（字节保真那条：「目标字段之前的字节变了」） |
| M2 | 失败默认从 fail-open 翻成 fail-closed | **红**（失败原样发出那条） |
| M3 | 定位器退化成「朴素全文搜索第一个同名字段」 | **红**（嵌套那条：命中了嵌套的 `model`） |
| M4 | 改写改成**原地修改入参** | **红**（候选隔离 + 纯函数两条） |
| M5 | **忽略** `Spec.Timeout`（固定 10s） | **红**（超时那条） |

#### 3.10.4 诚实边界

★ 本包是**契约 + 参考实现**，**尚未接线到 `prepareRequestBody`**：
计划书 P1-4 的措辞是「把 (b) 路径**定成接口**」⇒ 契约先定死；
「**规则从哪来**（配置面：settings / DB / 管理端？）」与**接线**属后续。
★ 本轮**没有**引入进程内脚本引擎（P3）⇒ 避免第二套改写机制（计划书 §5.2 的原话）。

### 3.11 ★ 门禁接线：★ **「门是绿的」在 CI 上原本是【空转】**

> 这一节不属于计划书的 P0/P1/P2 任何一项 —— 它是**本轮落地过程中撞到并修掉的**
> 一个**执行面**缺陷，但它比任何一项 P0 都更致命：**门是绿的，而 CI 从来没跑过它。**

#### 3.11.1 现象

本轮新增的**契约门**分别落在
`internal/rewrite` / `internal/routeorder` / `internal/requestobserver` /
`domains/credential` / `domains/authentication` —— ★ **五个包一个都不在**
`Makefile` 的 `GUARD_PACKAGES` 里。

⇒ CI 的 `make guards`（`.github/workflows/audit-guards-ci.yml` 的唯一执行路径）
**从不执行它们** ⇒ ★ **「门是绿的」在 CI 上是空转**（本地跑绿、CI 也绿，
但 CI 从没跑过）。

★ 而这**正是仓库自己的 Makefile 注释早就写下的腐化方式**：
「加了个守卫但没人跑是这类体系最常见的腐化方式，且**悄无声息**」。

#### 3.11.2 为什么既有的「漏登记」检查抓不到

`scripts/checks/guards-sync.sh` 的正向检查靠
`find internal -maxdepth 1 -type d -name '*guard'` 枚举磁盘
⇒ ★ **只认「`internal/` 下且目录名以 `guard` 结尾」的包**。
⇒ 我这几个包**既不以 `guard` 结尾，又不在 `internal/` 下**（两个在 `domains/*`）
⇒ ⇒ ★ **既不被检查，也不被执行** ⇒ ★ **检查机制的覆盖面 = 它的发现规则**。

#### 3.11.3 修法（三步）

1. **登记**：`GUARD_PACKAGES` 补 5 个包。
   ★ 登记**之前**先量了「干净环境」（`env -i`，无 DB / Redis / 网关环境变量）：
   五包**全绿**，合计 **15.7s**（每包远低于 `make guards` 的 `-timeout=120s`）
   ⇒ ⇒ 可以安全登记进一个**承诺「无外部依赖」**的快门。
   ⚠ 前三个包名不以 `guard` 结尾 ⇒ `guards-sync.sh` 的命名检查会**告警**（不拦）
   ⇒ 因为它们是**契约包**（被生产代码引用），不是守卫包。
2. **让门自己声明**：门文件头加 `// AUDIT-GUARD:` 标记
   ⇒ 新门 `scripts/ursmcheck/audit_guard_registration_test.go` 扫出所有带标记的门文件
   ⇒ ★ **断言它们所在的包出现在 `GUARD_PACKAGES ∪ GUARD_PACKAGES_SLOW`** ⇒ 漏登记即红。
   ★ 为什么用**显式标记**而不是「按 `*_contract_test.go` 命名自动发现」：
   仓内已有 **70+** 个同名文件散落在几十个包（admin / bg / db / sql/…），
   它们**本来就不在 CI 快门里** ⇒ 按命名自动发现会要求把几十个包全拖进 CI
   ⇒ ★★ **那是另一个决策，不能由这道门偷偷做**。
3. **门自己有牙**（变异验证）：把 `./internal/rewrite` 从 `GUARD_PACKAGES` 拿掉
   ⇒ `TestAuditGuardMarkedPackagesAreRegistered` **红**（消息直指「CI 从不执行它」）
   ⇒ 还原 ⇒ 绿；`Makefile` 的 md5 与备份逐字一致。

#### 3.11.4 门（3 条）

- ① **量具自检**：仓内至少有一个带 `AUDIT-GUARD` 标记的门文件（否则本门恒绿）
- ② ★ **带标记的门文件，其所在包必须被登记**（漏登记 ⇒ 红）
- ③ **反向检查**：`GUARD_PACKAGES` 里登记的**每一个**包都必须真实存在于磁盘上
  （「登记了一个不存在的包」⇒ 登记本身是假的）
