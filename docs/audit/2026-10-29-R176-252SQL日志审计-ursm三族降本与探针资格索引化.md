## §4 修复一：迁移 919（P11 第二期；让号记录：初拟 917，push 前实测 origin 已被并行会话 ddd762e7a 占用 ⇒ 重取 919/920）

**病根链**：892 只把 base_buckets（7 天行数）搬上汇总表；base_active（活跃分钟，
ACTIVE_DAYS=3）仍实时扫源表。R97 时代注释里的实测「3 天 = 9.7s」基于当时行量
（7 天 600 万）；**本轮实测日分区 n_live_tup ≈286-314 万行/天（×3.4）** ⇒
3 天扫描 = 800 万索引项 + 83 万堆取数 = **158.1s**（独立臂 EXPLAIN ANALYZE，
2026-10-29）⇒ 主判据 242.7s 均值 × 每小时 1 次。

**修法**（`sql/migrations/startup/919_ursm_slot_daily_active_minutes.sql`）：
- `ALTER TABLE ursm_snapshot_slot_daily ADD COLUMN active_minutes integer`
  （hour: count(DISTINCT minute)；minute: 恒 1 —— 与巡检 G_ACTIVE 同语义）；
- 填充函数 CREATE OR REPLACE（**签名不变**，调用方零改动）；INSERT..SELECT 增列，
  **ON CONFLICT DO UPDATE 同步更新 active_minutes**（迟到行既改 rows 也改分钟数，
  只更 rows 会留半截基线）；
- **部署次序契约**：列加后存量行 NULL ⇒ 巡检 active 探测失败 ⇒ 回退 892 老路
  （慢但不失明）⇒ 落地后手工全量回填（不放迁移文件：全量按现行量需 10min+，
  迁移通道预算承不住；252 已触发，hour 臂 216/216 全填充）。
- 巡检脚本（`scripts/252-monitor/ursm-snapshot-health.sh`）三处：
  ① 新 `BUCKETS_SQL_DAILY_V2` 变体（与 DAILY 唯一差异 = base_active 走汇总表
  UNION ALL 今天腿——今天腿沿用 R97 的范围谓词下推）；
  ② active_minutes 覆盖探针（三失败形态：列缺/窗口内 NULL/无行 ⇒ 回退）；
  ③ 三态选择 SOURCE / DAILY / DAILY_V2（V2 叠加在 daily 之上，base_probe 是前置）。
- **判定输入的真实改动（属主知情项，与 892 当年桶对齐同族同方向）**：
  base_active 下界从行时间 `now()-3d` 改为桶对齐 `date_trunc(unit, now()-3d)`
  （边界桶半截→完整）。

**252 同刻 A/B（2026-10-29 06:5x，两臂判据输出逐字相同
`3|0|0|0|0|3|110992|117825|111929|100`）**：

| 臂 | Execution Time |
|---|---|
| V1（892 现行，base_active 扫源表） | **100,884 ms** |
| V2（917，base_active 走汇总表） | **2,686 / 2,903 ms**（两跑） |

## §5 修复二：迁移 920

**病根**：INV-4 双模型探测成功门的关联子查询按 `credential_id` 关联、按
`completed_at > now()-24h` 过滤，而 node_probe_runs 的 credential 前导索引只有
`(credential_id, raw_model_name, started_at DESC)` —— **completed_at 不在任何
索引里** ⇒ 每次评估 Bitmap Heap Scan 该凭据全史（顶层凭据 3.3-3.8 万条），
24h 内只有 ~1,300 条（4%）。门是关联子查询，在五个调度读点逐行求值。

**修法**（`920_node_probe_runs_cred_completed_idx.sql`）：
`btree (credential_id, completed_at) INCLUDE (raw_model_name, started_at, success)`
—— 前导=关联键；第二键=时间谓词成 Index Cond；INCLUDE 三列=DISTINCT ON 输出列
⇒ Index Only Scan。普通表单条 CONCURRENTLY（探针写入与 TTL DELETE 在跑）。

**252 A/B（同刻，UPDATE pg_index 失活新臂 → ROLLBACK 还原，indisvalid 复查 t）**：

| 臂 | plan | buffers |
|---|---|---|
| 新索引在位 | Index Only Scan（1,511 行，Heap 304） | **321** |
| 新索引失活 | Bitmap Heap Scan（扫 38,446 行，Filter 丢 36,935） | **18,885** |

**58× buffer 缩减**；均值 4.29s 的慢查与 224 次取消（应用侧 30s ctx）应随之塌缩
（下轮对账：probe-eligibility 族慢查+取消 → 0）。

## §8 本轮量具坑（新增）

1. **awk 对 NUL 洞行无害、但对「按字节量级直觉」是陷阱**：655MB 的「爆发」
   第一读法数 NUL（R21 纪律 55 第四次复发）。
2. `heredoc` 切 V2 块时以「恰为 `"` 的行」收束（此前按 `\n"\n` 找会撞行尾引号）。
3. A/B 失活索引用 `UPDATE pg_index SET indisready/indisvalid=false` 必须包
   BEGIN..ROLLBACK 且**同事务跑 EXPLAIN**（planner 读内存态，commit 前生效）；
   还原后必须 pg_index 复查 indisvalid=t（纪律⑫的镜像）。
4. 917 down 的顺序陷阱写进门里：先还原函数（不再写列）再 DROP COLUMN；
   反序会在删列后留下仍引用该列的旧函数 ⇒ 下次刷新 42P01。
5. `EXPLAIN (ANALYZE)` 跑两遍取时间（首跑含冷 cache），两臂同刻交叉执行。
