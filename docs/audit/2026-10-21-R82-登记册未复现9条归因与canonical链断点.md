## 3. ★ 9 条未复现的逐条归因（两组互斥机制）

### 3.1 机制 A（6 条：610/680/696/700/710/733）—— **守卫命中「已具备」分支 ⇒ no-op**

根因：**canonical 视图已经是会话族 v2 体**（`883/884` 建的，118 列，实测 `pg_get_viewdef` 含 `session_turns`）。

| 文件 | 守卫 | 命中结果 |
|---|---|---|
| 610 | `already_extended`（canonical 已含 `request_class`）| **RETURN** ⇒ 不失败，**且不建包装链** |
| 680 | 形状守卫（`customer_id`+`request_class`+`due_at` 三者齐）| **no-op** ⇒ 不重建 |
| 696 | 「已具备 `system_fingerprint`」| no-op |
| 700 | 「已具备 `raw_model_name`」| no-op |
| 710 | `v2_already`（视图体含 `session_turns`）| no-op |
| 733 | `to_regclass` 守卫 + 列交集降级为 `NULL::type` | 不报错 |

⇒ ★★ **这 6 条的文件「成功」了，但什么都没做** ⇒ 尤其 610 走 RETURN 分支时**不建包装链**
⇒ ⇒ 包装链（两个 intermediate 视图）**在链上从未存在** ⇒ ⇒ 见 [M11]。

### 3.2 机制 B（3 条：562/808/860）—— **谓词按旧名写，而重跑的起点是 baseline**

- `01-schema.sql` 是**裸 pgdump 基线** ⇒ 它把 v1 族按**旧名**重建出来（`request_logs` / `request_logs_hot` / `request_logs_bodies` …）
  ⇒ ⇒ **重跑起点的旧名形态是自洽的** ⇒ 按旧名写的谓词**反而对上**：
  - 562 的 VERIFY 按 `request_logs_bodies` 找分区 ⇒ baseline 重建后分区就挂在它下面 ⇒ 通过；
  - 808 的内层谓词按 `p.relname='request_logs'` 找 DEFAULT 分区 ⇒ baseline 重建后父表名就对得上 ⇒ 不撞名；
  - 860 的守卫在「新旧命名**并存**」时 RAISE ⇒ pass-1 末尾 890 已退役 v1 族（`_request_logs*` 不存在）⇒ **并存不成立** ⇒ 不触发。
- ⇒ ⇒ ★★ **这正是 [M10] 与 [M7]/[M9] 互相抵消**：[M10] 按旧名复活 ⇒ [M7] 的旧名谓词成立。

### 3.3 ★★ 共同根因一句话

> **官方重跑的起始形态是 baseline，不是首遍终态。**

⇒ ⇒ **9 条不是「修好了」，是「测的不是同一件事」** ⇒ ⇒ **不删**（理由见 §8.1）。

## 5. ★ 新机制 [M12]：「`v.*` ＋ 追加同名列」⇒ 列重复（577）

577 的形态：先把 canonical **改名**成 `request_logs_with_current_month_without_customer_id`，再

```sql
CREATE VIEW public.request_logs_with_current_month AS
SELECT v.*, m.customer_id
FROM public.request_logs_with_current_month_without_customer_id v
LEFT JOIN LATERAL (SELECT customer_id FROM public.request_logs_hot …) m …
```

⇒ 首遍时 canonical 还没有 `customer_id` ⇒ 正常；
⇒ **第二遍时 canonical 已含 `customer_id`** ⇒ `v.*` 已带它 ⇒ 再追加一个 ⇒
**官方跑法实测首报 `ERROR: column "customer_id" specified more than once`**。

⇒ ★ 与 [M1] 是**同一族 PG 规则的两面**：[M1] 是「`CREATE OR REPLACE` 不能丢列」，
这里是「**追加列写法不能与已有列重名**」⇒ 两者都源于「**视图列集只会变宽，不会变窄**」。
⇒ ⚠ R82 轮订正：此条原先登记为 [M2]「无守卫 CREATE VIEW，重跑时关系已存在」——
**与实测首错不符**（撞名会报 `relation already exists`）。

## 6. ★★ 对属主决策 E3 的硬约束（已写进登记册 DECISION PENDING 段）

[E3] = 给 `InitSchema` 一个「已初始化」守卫 ⇒ **重跑不再重放 baseline**。

⇒ ★★ **E3 会改变重跑的起始形态（baseline ⇒ 首遍终态），而失败集依赖起始形态**：

- 起始形态 = baseline ⇒ 旧名形态自洽 ⇒ **562/808/860 不失败**（机制 B）；
- 起始形态 = 首遍终态（旧名已被 860 改名、v1 族已被 890 退役）⇒ **旧名谓词不再成立** ⇒ **这 3 条会重新失败**。

⇒ ⇒ **「E3 落地 ⇒ 这一整类问题消失」是错的**（它只是换了形态）。
⇒ ⇒ **E3 落地前后的失败集必须各测一遍**；[M13] 的 9 条要按新形态重新评估（保留还是退役，不能沿用本轮结论）。
⇒ ★ 与 E1/E2 的关系：E1/E2 改的是**链上文件本身**（DROP+CREATE / 拓宽投影）⇒ **不受起始形态影响**
⇒ **E1/E2 与 E3 不互斥，也不能互相替代**。
