## 五、archive 42703：生产函数是 S-01 修复前的坏版本（已写好步骤，未执行）

- 现象：`bg/partition_manager.go:781` 每天 03:xx 报
  `request_logs archive rows failed — ERROR: column "session_id" does not exist (42703)`
  （本日实锤 03:40:46 一条）。
- 根因：754 迁移的 **2026-09-29 S-01 修正**（`session_id→gw_session_id`、
  `status_code→upstream_status_code`）只进了仓库文件；生产 DB 在修正前就已
  应用过 754，迁移台账判 applied **跳过重放**——754 文件头注释自己预言了这一点：
  「已应用 754 的环境需要重跑本文件……不重跑就拿不到修正」。
- 生产实锤：`pg_proc.prosrc` 含裸 `session_id`（无 `gw_session_id`）。
- 修复（幂等 `CREATE OR REPLACE FUNCTION`，仓库 SSOT 已有修正版）：

  ```bash
  # 任一台可连生产库的机器；文件：sql/migrations/startup/754_archive_request_logs_default.sql
  ssh 245 'set -a; . /etc/llm-gateway-go/env >/dev/null 2>&1; set +a; \
    psql "$LLM_GATEWAY_DATABASE_URL" -f -' < sql/migrations/startup/754_archive_request_logs_default.sql
  # 验证：函数体应含 gw_session_id 且无裸 session_id；次日 03:xx tick 应出现
  # "partition_manager: request_logs archived" 而非 42703。
  # 手动触发验证（可选）：
  #   SELECT archived_partition, rows_archived FROM archive_request_logs_default(30);
  ```

- 808 未重定义该函数（仅注释提及），排除「新迁移种回坏版本」。

## 六、观测口径陷阱：request_logs 父表有 8 小时滞后

- 实时写入只进 `request_logs_hot`（独立 heap 表，非分区）；promote 腿健康
  （08:43/09:46/10:46 分别搬 1552/30/2083 行），retention=8h。
- 推论：查 `request_logs` 父表（或月分区）时，**最近 8 小时的行不可见**。
  本轮调研初期「request_logs 6h 零写入」的假象即由此产生（后经
  `request_logs_hot` max(ts)=now 证伪）。
- 上轮审计的 24h 逐时 503 统计全部查的父表——**其中最近 8h 的数据缺失/滞后**，
  结合 §二 的口径问题，上轮「503 率」结论双重失真。
- **建议**：审计查询一律用 `request_logs_hot`（≤8h 龄）或父表（>8h 龄），
  两者拼接时以 8h 为界。
