## 2. 发现的问题（按严重度）

**P1-1 · 08 证据包未并入 ASM 主干**
ASM 主工作树缺 `docs/operations/ownership-gate-evidence-2026-10-28.md` 与 `evidence/`。状态板写“完成”，实际只完成了 worktree 内的证据采集，Gate 本身仍为 NO-GO。需把 `wip/ownership-gate-evidence` 合入 ASM 主干后再谈“完成”。

**P1-2 · 网关→ASM 事件缺口（生产可靠性）**
08 证据（154，2026-10-30 只读）：ASM inbox `retryable=21,245`，其中 21,244 条属于 21,227 个**缺 `session.opened.v1` 的会话**；网关 `outbox_events` `DLQ=23,975`。根因是终态请求没有 opened 父事件，completed 落到 `projection row missing` 后整批 503 重试。
- **代码侧已修**：`domains/hooks/observability/telemetry/client.go:1716-1743` 终态路径同事务补发 opened（2026-10-29 轮）。
- **未闭合**：①154 历史积压 21,227 个会话尚未回填；②154 当时运行的 release（`2.5.8-008546aa-20261029-2909`）是否包含该修复，需对照 release SHA 确认（本轮无 git 无法核实）；③DLQ 23,975 未消化。回填与重放属生产写，需授权。

**P1-3 · ASM 的 GATEWAY_URL 随网关蓝绿端口漂移（节点状态感知的结构性缺陷）**
网关 active-port 在 8781/8782 间切换，ASM `GATEWAY_URL` 硬编码 8781 ⇒ 每次切流都可能断开 ASM 的 shadow/body 腿。2026-10-29 为人工改回 8781，**结构问题未解**（应改为读 active-port 或稳定入口）。

**P1-4 · 01 的“单一真值源”仍有第二套解析路径，门禁有盲区**
- `domains/session/middleware.go` 的 `WithSession` 自行读 `X-Gw-Session-Id` / `X-Session-Id`，不走 `sessionid.Resolve`，不认 body 与 bare-UUID 派生。**生产代码无调用点，仅被测试引用**（死代码形态的第二真值）。
- 01 日志把它记为“中间件双头兜底（残留，建议改调）”，**描述不准确**：它不在生产路径上，正确处置是删除（连同测试）。
- `scripts/ursmcheck/sessionid_single_source_test.go` 只匹配 `[]string{"X-Gw-Session-Id","X-Session-Id"` 字面量表，**漏掉分两次 `Header.Get` 的形态**，所以这个残留没被门禁抓到。

**P2-1 · 03 taskbus：挂载条件与持久性**
- cache_save 的 TaskBus 挂载位于 `buildV2DispatchPipeline`（`cmd/gateway/main_pipeline.go:539`），而该函数只由 `newV2DispatchDepsFromMain` 经 `v2DispatchMux` 调用，后者受 `LLM_GATEWAY_USE_V2_PIPELINE` 门控（默认 false）。**默认生产路径不经过 TaskBus**。日志“已真实挂载”已订正。
- `NewDemoBus` 使用 `MemoryStore`，进程重启丢队列；dispatcher 以 `context.Background()` 启动，无优雅停止。cache 写是 best-effort，可接受，但须在文档中明说。
