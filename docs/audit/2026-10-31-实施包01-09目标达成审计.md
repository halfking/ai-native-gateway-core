### 7.2 新发现并修复：两层路由的可选信号被做成了硬依赖（高优先）

- **病灶**：候选查询以 `CROSS JOIN LATERAL recent_cache_hit_rate(...)` 引入 prompt-cache 亲和信号 chr。它的默认权重为 0，本应是“无信号则中性”的可选维度，实际却是硬依赖。函数缺失（部署顺序竞态、新装库、误删）时，整条候选查询报 42883；而 `isRetryableDBError` 把它判为不可重试，于是记入熔断，所有 /v1 请求 500。前一轮的熔断器只把“全瘫”换成了“park 后快速全瘫”，病灶仍在。
- **修复（fail-open）**：函数缺失时改用等价降级 SQL（chr 投影为 NULL/0，路由侧 cache 维度已把 NULL 视作中性）；该错误不计入熔断；60 秒周期重探测全量 SQL，函数补齐后自愈。`recent_success_rate` 是硬过滤信号，**不**降级。
- **真库证据**（installer 全量新装的一次性库，`TestCandidateOptionalSignal_ChrFunctionMissing_OnRealDB`）：
  - 删除函数后，全量 SQL 报 `function recent_cache_hit_rate(bigint, text, integer) does not exist (SQLSTATE 42883)`，与 211 事故同款；
  - 修复后，`loadCandidatesByModalityDB` 无错误返回，进入降级态，熔断未打开；恢复函数后新 Client 走全量 SQL 成功、不降级。
  - **变异**：关闭降级分支 → 测试红，并报出与事故同款的错误；还原后文件 md5 逐字一致。
- **并行修正（重要）**：我的降级实现已被提交者 `huangzhouzixuan` 在 `24990d164` / `84582461c` 中修正两处缺陷，我已逐条审查、方向正确并在 main 上复跑：
  1. `sync.Once` 把依赖环境变量 `LLM_GATEWAY_MODALITY_ROUTING_STRICT` 的 SQL 永久冻结 → 改为每次按当前 SQL 现算（新增判据 `…FollowsCurrentModalityGate`）。
  2. 模板形态不匹配时仍打点“已降级”，指标谎报 → 改为 fail-closed（不进入降级态、按硬失败处理）；打点改为 CAS，只有赢得状态切换的那一个请求计数。
