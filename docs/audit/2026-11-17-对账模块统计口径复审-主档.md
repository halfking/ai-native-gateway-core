## 一、结论先行

**先说好消息**：对账模块的统计数字本身是**忠实**的——这一轮把最关键的两条对账都实测了一遍：

| 对账项 | 方法 | 结果 |
|---|---|---|
| 快照 vs 真相源 | `daily_grain` 逐日 vs `usage_facts` 同 UTC 日窗 | 请求数 / 成功数 / 四类 token **逐日完全相等**（差 0） |
| 总计 = Σ 各分组 | 线上 API + 独立 SQL，六维度 × 两视角 × 汇总/明细 | **全部成立**（总计 123,367 = Σ人员 = Σ凭据 = Σapikey = Σ模型 = Σ供应商 = Σ按天） |
| 错误分布 = 失败数 | `error_breakdown` 合计 vs `request_count - success_count` | 45,182 = 45,182，**gap 0** |

**但「筛选栏（候选面）」与「报表（读面）」不是同一套键**，而且**归属维度在分组时被 GROUPING 折叠掉了**——
本轮定位并修复 **3 处结构性错位**（都属「同一类病：读面有、候选面没有，或读面丢了归属」）：

| # | 现象 | 量级（211 真库） | 根因 |
|---|---|---|---|
| **F1** | 「未落定」桶在**凭据 / apikey** 两个维度上「看得见、筛不出」 | 凭据 **38,035 笔（= 全量 30.8%）**、apikey **16 笔**；候选合计凭据 85,332（少 38,035）、apikey 123,351（少 16） | 上一轮 F1 的修法**只覆盖 provider 一个维度**：候选面没给这两个维度配 nullKey（NULL 行整桶被滤掉）、过滤面 `-1` 仍落成等值（**恒 0 行**） |
| **F2** | 旧口径回落的**整天总量**被算进「未落定」桶 | 隔离 PG 真库实测：筛「未落定供应商」得 **277** 笔，真实未落定只有 **200**（多出 77 = 旧口径整天总量） | 旧口径 scope（`daily_total` / `internal_tenant`）**根本不分解 id 维度** ⇒ 它的 NULL 列含义是「这个 scope 没有这一维」，不是「这批请求没落到该维度」 |
| **F3** | 分组集漏掉归属维度 ⇒ **归属丢失 + 跨租户同名人员被合并** | 人员行的租户**恒为空**（真库所有行 `tenant_id` 都是 `default`）；凭据行**永远拿不到供应商**（导出里「凭据名 @ 供应商」那个分支**从未执行过**）；apikey 行租户恒空 | `grainGroupSets` 写的是 `(person)` / `(credential_id)` / `(api_key_id)` ⇒ 归属维度被 GROUPING 折叠成 NULL |

另登记 2 项（本轮**不修**，见 §六）：**F4** 成本按组取整再求和（6 天差 4 分）、**F5** 用户身份是 JSON 串（6,787 笔）。

> ★ **F1 是上一轮的漏网之鱼**：上一轮 F1 修完 provider 维度后，测试里留了一条「阴性对照」断言
> **「其余维度仍排除 NULL」**——把「只修一个维度」这件事**固化成了契约**。
> 本轮的第一件事就是把那条例外**取消**，改成「三个 id 维度共用同一个 `-1` 键」。
> **教训**：门一旦写成「某个维度是特例」，下一轮就会有人把它当成设计而不是遗漏。

### 为什么「凭据未落定桶」和「供应商未落定桶」是同一批流量

真库实测：`provider_id IS NULL` 与 `credential_id IS NULL` 命中的是**同一批 1,298 行**（探针找不到候选 / 限流 / 超时这类**没走到供应商**的失败流量）。
所以凭据维度的未落定桶也是 **30.8%** 量级——不是「小尾巴」。

### ★ 候选的 N ＝「点它之后会得到的总量」（本轮确立的候选面口径）

候选面上每个值后面的请求数，**必须等于点这个值之后报表里那个过滤结果的总量**——
这是候选面唯一的计数契约（读面的维度行在旧口径日上可能更小，因为旧口径那天进不了维度分解，
这一点由 `coverage.legacy_dates` 披露）。

| 场景 | 候选的 N | 点它之后的总量 | 一致？ |
|---|---|---|---|
| provider 视角 · 未落定（-1） | grain 支的未落定量 | 同左（旧口径支不参与 id 维度过滤） | ✅ |
| provider 视角 · 真实供应商 | grain 支的该供应商量 | 同左 | ✅ |
| internal 视角 · 租户 | grain + 旧口径 `internal_tenant` 支 | 同左（旧口径**真的带租户** ⇒ 过滤照常生效） | ✅ |
| internal 视角 · 未落定（-1） | grain 支的未落定量 | 同左 | ✅ |

⇒ 修法必须**成对**：候选面排除旧口径支（F2）与读面回落不参与 id 维度过滤（F2）
**必须同时做**——只做一边就会出现「候选说 277、点进去只有 200」。

## 五、本轮沉淀（通用式）

★ **「看得见、筛不出」是**键空间**问题，不是单个维度的问题**——三个 id 维度共用一个 `-1` 哨兵，
就必须**三处同时改**：候选面出键、过滤面落 `IS NULL`、前端说人话。上一轮只改了 provider 一处，
另外两个维度原样留着——**修一半比不修更坏**：审计人看到「未落定」行就去点，另两个维度点不动。
★ **门写成「某个维度是特例」，下一轮就会有人把它当设计**——上一轮那条「其余维度仍排除 NULL」的
阴性对照，把**遗漏**固化成了**契约**。本轮把它取消，改成「三个 id 维度同一个键」。
★ **NULL 有两种含义**：「确实没有这个值」与「**这个 scope 没有这一维**」。旧口径 scope
（`daily_total` / `internal_tenant`）的维度列全是 NULL，把后者当成前者 ⇒ **整天的总量被灌进
「未落定」桶**（实测 277 vs 200）。写 SQL 时必须问一句：**这个 NULL 是谁给的**。
★ **分组集与 `classify()` 是两份必须一一对应的清单**——改一边忘了另一边**不报错**，而是
静默错账：派发不中时兜底分支把行算进 `gkTotal` ⇒ 总计凭空翻倍；派发串了 ⇒ 分组互相污染。
★ **写代码时想的口径与 SQL 实际产出的行，可能不是一回事**——导出里那句

## 六、遗留与登记（本轮**不修**）

1. **F4｜成本按组取整再求和**：`daily_grain` 每组 `ROUND(SUM(cost_amount)*100)`，读面把各组
   整数相加 ⇒ 与「整天取整一次」差 **−1 ~ −2 分/天**（6 天共 **−4 分**：201,279 vs 201,283）。
   同一天的 `daily_total` scope（取整一次）是 201,283 ⇒ **两个 scope 自相矛盾 4 分**。
   量级 0.002%，根因是**精度在写面就丢了**（列是整数分）。修它要么改 schema（存 sub-cent 精度），
   要么在写面按日分配尾差（把整天总额按组比例分摊并让尾差落在最大的一组）——后者要动写路径的
   两遍聚合，风险远大于 4 分。**建议单独立项**。
2. **F5｜用户身份是 JSON 串**：`usage_facts.end_user_id` 的 59 个不同取值里 **57 个是
   `{"device_id":...}` 这类载荷**，覆盖 6,787 笔（4.7%）。对账页与导出把整段 JSON 当「用户名」
   展示。统计**忠实于真源**（不是对账模块的错），但可读性与口径需登记：审计人看到的是设备
   载荷而不是人。
3. **租户 / 人员维度的候选面**：文本维度的 NULL 与空串在候选侧被排除，读面则映射成空串键。
   真库当前无 NULL 租户、无空人员 ⇒ **两侧一致**；一旦出现 NULL 租户，会重演 F1 的
   「看得见、筛不出」。**待登记为潜在项**（修它要动文本维度的键空间，代价大于当前收益）。
4. **CJK 棘轮的并行债**（上一轮登记项，仍在）：建议把 `i18n:cjk:check` 放进 PR 必跑项。
