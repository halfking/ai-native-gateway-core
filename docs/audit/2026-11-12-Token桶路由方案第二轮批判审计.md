## 〇、一句话结论

## 三、211 生产取证（需求①「通过 211 的 log 分析」——补方案缺失的地基）

只读查询 `provider_error_details`（211 acc-pg17，2026-11-12 00:0x +08，24h 窗）：

```
concurrent|429          618 行 / 1906 occurrences   ← 绝对主体
rate_limit|429           70 行 /   82
quota_permanent|429      49 行 /   56
canceled|               145 行 /  180
empty_response|         125 行 /  337
（其余各族 ≤ 67 行）
```

**归因下探一层**：concurrent|429 的 618 行里 **617 行** 聚在 sensenova 三 provider（326+151+140），error_message 同文：`upstream 429: {"error":{"message":"inference exceeds tpm/rpm limit",...}}`；仅 1 行是网关自身并发门（"ZCode turned away 5 requests"）。

**含义（对方案的三点修正力）**：
1. 需求①说的「too many requests/超限」主体是 **每分钟重灌的 tpm/rpm 族** → 直接支撑 W1 的窗口重灌语义（60s）与「拒绝 ≠ 硬断、沉序保活」的设计；若按方案硬拒绝 + 1min 起探，sensenova 场景即仿真 S2 形态（同源限流）。
2. quota 族（periodic/permanent）**本就不进 sink**（`rate_sink.go:119-122` 判据④，quota 走恢复点路径）——方案的 RateLimitHandler 若按「429 一律进限流态」会把两类形态混在一起，恰好破坏这条已验证的区分。
3. 现状 429 噪声水平（618 行/24h，且 617 行同源）证明「真实流量 failover 的摩擦噪声」在生产可接受——方案 §3.1 优化的「上游噪声」不是当前的主要矛盾。

### 4.3 判读（五条，全部可复现）

- **(a) 一阶因素 = 兜底与硬拒绝语义，不是冷却时长**：P4 每场景 926~1297 个请求、P4f 每场景 1293~1926 个请求**一次尝试都没拿到**（硬拒绝 + 无兜底 ⇒ 全桶一限流，请求直接饿死；而这些时刻仿真里明明还有其它桶存在 token）。P0 的 B1 兜底保证 starved 恒 0。
- **(b) P4f（3min 地板）全面更差**：client_ok 再降 4~6pp、S1 恢复 0.9→5.0min、S3 抖动场景恢复 9.8min（爬坡重置税 × 地板延迟）。⇒ 自审 D1「延长探测启动到 3min」**不救设计**；设计的病根在兜底缺失，不在地板数值。
- **(c) 给 P4 补上兜底后，合成探测机制即告冗余**（变异 M1 实测：饥饿指纹当场消失、A2a 红）：兜底在场时真实流量重新承担「探测」职能 ⇒ **方案 §3.1 的新增机制面（RateLimitHandler + ProbeScheduler + 第四套状态）不再提供额外行为收益，只剩合成探测的额外上游噪声与第四套状态面**——这正是 11-07 W2「只读影子层」原案的判据。（诚实边界：M1 只实测饥饿消失与断言红；「无额外行为收益」是从兜底语义推出的推断，非 M1 直接量测。）
- **(d) 噪声口径要诚实**：P0 的 ~3300 次真实 429 是**真实流量的 failover 摩擦**（其中含峰值 15min 的不可避免亏损 ~315 次），多数随后被其它桶服务；P4 用 ~70 次 429 换 −4~−12pp client_ok。生产 24h concurrent|429 = 618 行（§三）证明现状噪声水平可接受。**「上游噪声最小化」不能以客户端成功率为代价——这正是需求⑥的 client 成功率第一性。**
- **(e) 冷却时长是二阶因素（诚实披露）**：P0x 与 P0 的 client_ok 四场景同数（94.3/92.7/92.7/93.6；噪声列微差——up429 ±1.2%、up_ok ±0.05% 内）——在本负载形态（base 40 < 容量 89、峰值短促）下 W1 的 60s vs 3min 对客户端成功率不可测；冷却时长成为一阶因素的形态（长亏空 + 高基数持续负载）已在 11-07 仿真 §1.4 验证过。**据此，方案 D1「统一冷却值」的预期收益在本形态不可见，不值得排实施。**

## 六、需求⑥（双重成功率）与需求④⑤（两层路由/会话粘性）的现状对照

- **两层路由**：现状第一层 = auto_route/模型解析（GRRQ/240 例套件，auto-routing-v2 闭环），第二层 = planByTier 候选序（P2C + sink + sticky）。「两个模块分别计算与维护」在代码形态上已接近，差距在**显式接口化**（方案 §4.1 的 RoutingEngine 接口抽象方向正确，可作为 W2 影子层之后的重构目标，不必与 W2 绑定）。
- **会话粘性**：stickyCredID（首尝试保 prompt-cache 亲和）+ stickyFailed/stickyFailKind（2026-09-19）+ C1 经济学已落地；重试等待 5s 地板已存在（`dispatch/errors.go:31`）。方案 §3.4 的「历史环记录桶/延时/成败」= 11-07 W3 原案（进程内环 + TTL/容量/回放测试），方向一致。
- **桶类型/参数**（需求③「探测或基础信息查询后给桶定义类型」）：现状已有等价物——billing_mode（paid/free/trial）+ breaker 状态 + ratebackoff 冷却 + B1 满槽判定。方案的「桶类型」应是这四源的**只读投影**（W2 verdict+reasons），不是新权威源。
