## 0-A. ⚠️ 批判复核结论（第二轮审计，**推翻本文档 §7 第 1 批的部分结论**）

第一轮做完第 1 批后，又对本轮三个仓各做了一次**对抗性复核**（要求逐条复现
原始声称、并在临时 worktree 里做变异）。三份复核的判决是
**FAIL / FAIL / FAIL**。我逐条亲自复跑过，下面是被推翻的声称：

| 原声称 | 实情 |
|---|---|
| `ai-session-manager`「两张空表终于有生产者」 | **假。** 任何部署里两表仍恒空：drainer 被 `!= "1"` 默认关；更致命的是**全仓没有任何地方 enqueue 过 `task_summary`/`project_summary` 作业**——唯一生产 INSERT 由 sampling policy 驱动，而 policy 只列 `session_summary`/`quality_review`/`vibe_pattern`。这是一个**被充分测试的消费者，队列却没有生产者**。它援引的 000027 先例经查同样是死代码。 |
| memora「prerequisites 同时返回 ok 与不 ok 的条目」 | **假。** 生产路径从不返回 ok 条目——该属性**只存在于测试夹具**。且 enabled 模式下 `config-check` 返回 `ok:true, prerequisites:null`，是本轮**新造**的一处成功形状声称，正是本提交要消灭的缺陷。 |
| memora「监控在主动上报全部健康」 | **夸大。** `/api/v1/capabilities` 本就报 `dream_cycle:false`；谎话只在 `/api/dream/health`。 |
| `llm-gateway-go` 迁移 877「父表普通 CREATE INDEX，870/874 同款取舍」 | **危险的类别错误。** 在一次性 PG 上实测：该构建对 `session_turns_hot`（**每个会话轮次真正 INSERT 的表**）持 `ShareLock`，**并发 INSERT 实测被阻塞**；吞吐 ~14.6MB/s ⇒ 6.4GB 约 **7.3 分钟**，对 `statement_timeout=10min` 只有 ~1.4× 余量。而 874 自己的注释写明其前提是「部分索引、约 1/9 行、btree、**秒到十秒级，随部署窗口应用**」——877 是 100% 行的 GIN trigram + TOAST 宽列，分钟级，前提不成立。已重写。 |

**两次失败的形状完全一样**：组件本身写得不错、孤立变异验证也真的做了，
但没有任何门能看见「这段代码路径是否真被走到」。ASM 的三道门各自被变异
打穿：删掉整个生产接线 `cmd/session-manager` 全绿；把 worker 默认门翻成
**默认开**（每次部署都花钱）仍全绿；把手写常量里的默认值改掉仍全绿。
⇒ **判据纪律要再加一条：证明「这条路径被走到」的门，和证明「这条路径是对的」
的门是两件事，后者不能替代前者。**

复核还推翻了我自己两条未经核实的怀疑（**均已证伪，不是遗留缺陷**）：
727/729 用 `CONCURRENTLY` 却没有 `no-transaction` 标记——看着像全新装失败，
实则它们根本不在 installer 的 StartupFiles 清单里，`applySQL` 不会碰；
`duration_ms` 看着可能因 `created_at` 被刷新而恒为 0——实则冲突臂不改写
`created_at`（只出现在注释里），该修复成立。

## 0. 一句话结论

四件事的地基都已经打了，但**几乎每一件"要能跑起来"的事都停在最后一米**：
schema 和读路径已就位而写路径缺失；能力存在但被 feature flag 关死且失败时返回成功形状；
接口存在但没有生产者在调。真正的工程量不在"加功能"，在**把已经付过款的骨架接通**，
以及**让"没跑"这件事变得可见**。

**并发踩坑之二（memora，更棘手）**：memora 是本轮最热的仓，推送被拒 **6 次**。

`web/src/`、vite 配置、`node_modules/`，外加 `internal/console/` 的改动），
rebase 直接以 `You have unstaged changes` 失败。
**没有 stash、也没有替对方提交**。改为：新建一次性 worktree 于 `origin/main`
→ cherry-pick 自己的提交 → rebase → 从那里 push → 删除 worktree。
对方工作树全程未被触碰；共享 checkout 的本地 `main` 刻意留在旧位，
在别人有未提交改动时移动分支指针正是会破坏对方状态的那种操作。

**教训二**：共享仓上"我要推一个提交"和"我拥有这个工作树"是两件事。
后者不成立时，用独立 worktree 绕开，不要在别人的工作树上做任何 git 操作。

## 4. `memora`

### 存在的（比预期多）

42 个迁移、pgvector、PG17 on kx-citus、Qdrant + Redis + MinIO、60+ 表、
三条摄入路径、**真实的图谱**（`internal/graph/`，PG 或 Neo4j 双后端）、
**真实的 wiki**、**真实的混合 RAG**（BM25 + 向量 + RRF + MMR，`internal/memory/hybrid.go`）。

**需求"合并 + 排重"是真的达成了**：所有来源（网关推送 + 智能体提交）都落到同一张 `memory` 表，
经 `INSERT … ON CONFLICT (tenant_id, project_id, user_id, content_hash)`（`service.go:296-313`），
来源溯源记录在 `ingest_receipt.go:37-48`，幂等回放被拒（`ErrIdempotencyKeyReuse`）。

### 缺的（且有几个是"静默失败"）

1. **dream cycle 在所有已发布配置里都是死的**，四道闸门串联
   （flag 默认关且各 compose 硬写 "false" → PG graph 关故回落 Neo4j → `NEO4J_URI` 空
   → 无后端即 stub）。**stub 返回成功形状的响应**（`server.go:493-495`）
   ⇒ 冒烟测试会通过，操作者无法分辨"跑了"和"空转"。这是整个任务里最危险的一条。
2. **仓内无 MCP server**——只有 `/api/mcp/sandbox/{tools,call}` 代理，
   它宣告的 `full_mcp_url: https://mcp.kxpms.cn/memora/mcp` **不在本仓**。
3. **无插件机制**（Go 代码里 `plugin` 零命中）⇒ 见 §5 决策。
4. **精炼只是部分**：`ON CONFLICT DO UPDATE` 是**后写覆盖**，**无跨源矛盾仲裁**。
   单一生产者时无害，两边都写就会静默覆盖。

## 5. 插件还是独立服务（需求明确要求再分析）—— **结论：独立服务，用 API 耦合**

证据链：
1. memora **没有插件机制**（零命中），做"插件"等于先造一套插件机制。
2. ASM 已经是**网关插件**（`gateway-plugin-v2`、unix socket、独立生命周期与授权），
   且有自己 27 个迁移和自己的 `internal/knowledge`/`skill`。嵌入会丢掉让两者各自发布的边界。
3. ASM 清单里的 memora **只是配置声明**——`config_schema.groups[].key == "memora"`，
   而 ASM 的 Go 代码里 `MemoraEndpoint|ingest_from_asm` **零命中**。
   ⇒ **ASM→memora 的推送目前是"只写在清单里、一行代码都没有"。**

⇒ 正确形态：ASM 做**生产者**，推事实/记忆进 memora 现成的 `POST /api/v2/memory/ingest`
（该契约已带 `Idempotency-Key` 与来源字段）；memora 的 `internal/v2` 读侧负责回读。
共享的是**契约**，不是运行时。

## 6. harness2 采纳评估

- **不是会话分析引擎**——它不摄取流量或第三方会话，源是一个自己枚举任务并执行 rollout 的
  `BenchmarkAdapter`（`core/spec.py:201-250`）。仓内**没有任何外部会话转录的导入器**。
  要用于我们的会话，必须**自己写第 4 个 adapter**，把 session→task_id、
  聚类→domain_of、摘要→task_prompt、转录→trajectory、答复→deliverable_text 映射上去。
- **接缝是文件制品，不是 HTTP 也不是 MCP**——它没有服务端/队列/常驻进程，
  状态全是磁盘 JSON + 树目录。⇒ **Python sidecar + 目录监听**。
  （demo 已证明可绕开 substrate 直接 `subprocess.run`，这正是驱动我们自己的 agent 的方式。）
- **唯一真阻塞是模型通道**：`CHANNELS = ("claude_cli","opencode")` 硬编码，
  `Proposer` 靠 **shell 调外部 CLI 二进制**（`proposer.py:162-164`）。
  **逃逸口已存在**：`harness2-bridge` 就是这个模式，直接把
  `HARNESS2_CODEX_BASE_URL` 指向我们网关即可，无需改代码。
- **core 是纯标准库**（`dependencies = []`，core/ 与 substrate/ 每个 import 都是 stdlib）
  ⇒ 若只采纳 core+substrate，**运行时足迹 = Python 3.12 stdlib + 一个可达的模型端点**，
  无需 Docker/bun/gcloud/pandoc。
- **许可：Apache-2.0**，可嵌入/封装/移植。商标条款要求**不得随产品发布 "Harness²" 字样**。
  ⚠ **第三方才是重量**：WorkBuddy-Bench 是腾讯自定义许可，条款 0 写明
  "NOT INTENDED FOR USE WITHIN THE EUROPEAN UNION" 且"冲突时本条优先"。
  ⇒ **只采纳 core+substrate、不发布 third_party/ 与 benchmarks 包，即可完全绕开该条款——
  这是采纳范围决策的决定性理由。**
- **成熟度诚实说**：3 个提交、**无 CI**、5 个测试、v0.1.0、单人首个快照。
  但工程质量高于典型首版：运行不变量是**断言**而非文档（预算恒等、prompt 泄漏词拒绝、
  resume 身份守卫、配置 pin 漂移检测）。
- **两个采纳风险**：
  1. **网络默认不受限**（`README.md:166-171`）——指向生产 agent 前必须先做出口管控。
  2. **选择刻意对分数盲**（`spec.py:178,247-250`）⇒ **闭环自我优化无法在带内度量自身改进**，
     收益只能靠独立的 `harness2-judge` 事后看到。
