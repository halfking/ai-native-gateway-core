## 一、报障与口径纠偏（先纠指标，再修代码）

监控脚本 `scripts/audit/f3-auto-check.sh` 的口径：

```sql
SELECT COUNT(*) FROM credential_model_bindings
WHERE unavailable_recover_at IS NOT NULL
  AND unavailable_at IS NULL
  AND available = TRUE;
```

★ **这不是「当前不可用的节点数」**，而是「**已恢复、但恢复标记没被清掉**的残留行」。

211 真库取证（2026-11-17 10:00 实测 192 行）：

| 指纹项 | 实测 | 含义 |
|---|---|---|
| `unavailable_reason IS NULL` | **192/192** | 触发器清 reason 的签名 |
| `unavailable_recover_at > NOW()` | **176/192** | 标记仍指向未来（当初判不可用时写的「计划重试时刻」） |
| `admin_protected` | **0/192** | 无管理员手工保持行被误伤 |
| `updated_at` 集中区间 | 09:48:53~09:56:48（8 分钟一批） | 一次批量「镜像恢复写入」 |
| 所属凭据状态 | 100% `ready` + `active` | **这些绑定现在都是可路由的** |

⇒ 指标不是可用性指标，是**写面一致性计数器**。

## 三、根因（逐点量出来的，不是推测）

### 3.1 视图路径：`model_offers_update_trigger()` 漏列

`model_offers` 是 **INSTEAD OF UPDATE 触发器视图**，触发器的 SET 清单是**手写的一串列名**。211 实测（`pg_get_functiondef`）：

```
available = COALESCE(NEW.available, …),
unavailable_reason = CASE … END,
unavailable_at = CASE … END,
admin_protected = CASE … END,
…
-- ★ 清单里没有 unavailable_recover_at
```

⇒ 经视图的「置可用」写入 → 触发器清 reason、清 unavailable_at，**唯独把 recover_at 留着** ⇒ 矛盾态。

★ **仓内早已自述此事**（`credentialhealth/checker.go:469-473`）：

> Note: the view DOES expose unavailable_recover_at, but the INSTEAD OF UPDATE
> trigger does NOT propagate that column to cmb, so writing it here would be
> silently dropped.

⇒ 该处的处置是「cmb 侧先写好、视图侧只镜像触发器认得的列」——**只覆盖了 cmb 侧先行写好的那一次**；凡「只有视图侧动作、cmb 侧没先清」的场景，标记被永久留下。

### 3.2 锯齿机制：两条路径打同一块地平线

- 涨 = 经视图的镜像恢复写入（触发器丢字段 ⇒ 标记留下）
- 跌 = cmb 侧直写（`cmbExpiredRecoverySQL` 等，四列一起清）

⇒ 谁节奏快谁说了算 ⇒ 永久拉锯。

### 3.3 直写路径：触发器管不到的那半边（**部署后才暴露**）

迁移 972 部署到 211（build_seq 3090，槽 a @8781 接管）后：触发器已生效（`pg_get_functiondef` 含新分支），残留 127 → **14，但没有归零**，且这 14 行的 `updated_at` **全部集中在迁移事务的同一秒**（16:41:20~24）。

⇒ 存在**第二条产生路径**。用 **go/parser 走 AST** 扫全仓 Go 代码里的 cmb 写入语句，量出三处漏网：

| # | 位置 | 形态 | 说明 |
|---|---|---|---|
| ① | `modelcatalog/upsert.go`（目录批量刷新） | `INSERT … ON CONFLICT (credential_id, provider_model_id) DO UPDATE SET …` | cmb 段把 `available` 置 TRUE（ELSE TRUE）却不碰 recover_at ⇒ **实测的主要产生源**（每轮目录刷新踩一遍） |
| ② | `bg/model_probe.go`（`healthy_confirmed`） | `UPDATE credential_model_bindings …` | 恢复绑定时只清三列 |
| ③ | `admin/credential_monitor.go`（手动上线） | `UPDATE credential_model_bindings …` | 同上 |

⇒ 这三条都是**直写 cmb** ⇒ **各有各的 SET 清单** ⇒ 视图层的触发器管不到。

### 3.4 部署通道层：产物探针把**运行时状态**当成了**迁移产物**（第二次部署被打死时暴露）

第二次部署（`f3a19fa44`）在最后一步 FATAL：

```
error: 台账 ↔ 产物对账失败：972_model_offers_trigger_recover_at.sql 本轮按指纹认账但其产物缺失
       （EXISTS (... pg_get_functiondef ... LIKE '%unavailable_recover_at = CASE%')
         AND NOT EXISTS (SELECT 1 FROM public.credential_model_bindings
                         WHERE unavailable_recover_at IS NOT NULL AND unavailable_at IS NULL AND available = TRUE) ⇒ f）
[211] FATAL: DB 修订序列失败——直接启动会降级 lite，先修库再部署
```

★ **此刻库里一切正常**：迁移 972 早在 16:41 落地（双账本 sha 齐备、applied_at 16:41:03）、触发器函数体**确实**含新分支、存量清理**确实**执行过。真正让探针判失败的是探针**自己多写的第二半句** —— 「库里当前没有残留行」。

三层错：

| 层 | 错在哪 | 实据 |
|---|---|---|
| ① 层级 | 「事实表当前有多少行」是**运行时状态**，不是迁移的**产物** | 残留由运行中的二进制决定；迁移 972 落地后残留从 0 反弹到 93（凭据 99023 占 80） |
| ② 前提 | 探针原注释断言「cmb 侧直写路径（域内全部 Go 写入方）本就四列一起清 ⇒ 无第二条产生路径」——**被第二轮实测证伪** | §3.3 的三条直写路径确实漏清第四列 |
| ③ 处置 | 探针失败时的处置建议是「重放本序列（迁移幂等）」，但重放**消不掉**运行中旧二进制重新制造的残留 ⇒ 探针从「守卫」退化成**毒丸** | 211 实测：探针失败 → 部署中止；而重放对同一状态**无效**（幂等重放后残留仍在） |

⇒ 迁移 972 的探针由「产物层 + 运行时层」两半组成，本轮把运行时那半**摘到运行时层**（§4.5）。

## 四、修法

### 4.1 视图路径：迁移 972 补第四列

```sql
unavailable_recover_at = CASE
    WHEN NEW.available IS NOT NULL AND NEW.available = TRUE THEN NULL
    WHEN NEW.unavailable_recover_at IS NOT NULL THEN NEW.unavailable_recover_at
    ELSE credential_model_bindings.unavailable_recover_at
END,
```

★★ **分支顺序不能照抄两个兄弟列的写法（「显式给值」在前）**：INSTEAD OF UPDATE 的 NEW 行里**未被 SET 触碰的列携带旧值** ⇒ 调用方通常只写 `SET available=TRUE, unavailable_reason=NULL, unavailable_at=NULL`（**不写** recover_at）⇒ NEW.recover_at = OLD 的那个未来时间戳（非 NULL）⇒ 「显式给值」在前会命中第一个分支 ⇒ **旧标记被原样保留 ⇒ 缺陷照旧**。

★ 这一版错误是被**隔离 PG 真跑腿抓到的**（写法「看起来」与兄弟列同款，真跑却是 RESIDUE）⇒ 门禁因此改为钉**分支顺序**而非弱判据 `contains unavailable_recover_at`。

### 4.2 直写路径：三条都按「置可用 ⇒ 四元组全清」补列

- `modelcatalog/upsert.go` 目录批量刷新段：与同语句 `unavailable_reason` / `unavailable_at` **同款同守卫**的 CASE（手工保持 / admin_protected 的行保留原值）
- `modelcatalog/upsert.go` 手工加入段：`EXCLUDED.available` 为 TRUE 时清 NULL
- `bg/model_probe.go`、`admin/credential_monitor.go`：SET 清单加 `unavailable_recover_at = NULL`

### 4.3 存量清理（必须在触发器修好之后）

迁移 972 内一次性清空，谓词 = F3 监控口径本身（只动「已恢复但标记没清」的矛盾行；211 实测该集合 `admin_protected` 全 0 ⇒ **不改变任何绑定的可路由性**）。

★ **顺序不可颠倒**：先清存量、后修触发器 ⇒ 下一次镜像写入立刻踩回 ⇒ 那正是观测到的「清完又涨」。

### 4.4 门禁

| 门 | 文件 | 钉住什么 |
|---|---|---|
| 投递六点位 | `internal/sqlguard/migration_972_trigger_recover_at_test.go` | canonical / embeddata 副本 / go:embed+var / embeddedSQLFiles map / dbinit StartupFiles / deploy 通道 files+probe / tsv 台账 |
| 触发器不变式 | 同上 | **分支顺序**（available=TRUE 分支在前）+ 兄弟列不许丢 + 正典快照同款 + clobber 守卫不会因本件中止部署 |
| **全仓写入侧四元组** | `internal/sqlguard/credential_binding_health_tuple_gate_test.go` | 任何把 cmb 的 `available` 置 TRUE 的语句（`UPDATE` / `INSERT…ON CONFLICT` 两种形态）都必须处理 `unavailable_recover_at` |
| **产物探针作用域** | `internal/sqlguard/migration_artifact_probe_scope_gate_test.go` | 产物探针**不得**断言运行时可变事实表的当前数据状态（除非显式豁免 + 理由）；且 972 的探针**仍必须**断言产物 |

### 4.5 第三轮修法：**分层**（产物层 / 写入侧层 / 运行时层）

同一条事实（残留该不该是 0）由**三层各自负责**，各有各的判据与各自的失效形态：

| 层 | 判据 | 形态 | 失效时谁负责 |
|---|---|---|---|
| **产物层** | 迁移自己造出来的对象在不在场 | `ledger_artifact_probe "972_…"`：**只**断言触发器函数体含 `unavailable_recover_at = CASE` | 部署通道（台账 ↔ 产物对账） |
| **写入侧层** | 有没有写路径能制造新的矛盾行 | `credential_binding_health_tuple_gate_test.go`（全仓 AST 不变式门） | CI（静态） |
| **运行时层** | 残留归零了 & 不再反弹 | `scripts/audit/f3-auto-check.sh`（监控）+ `scripts/audit/f3-postdeploy-verify.sh`（**部署后验收**：等待归零 + 观察窗口内不反弹） | 监控/告警/部署后验收 |

★ 为什么产物层**一个判据就够**：迁移 972 是**单事务**（函数替换 + 存量清理 + 台账登记同在一个 `BEGIN…COMMIT`）⇒ 原子性 ⇒ 「函数体含新分支」成立即蕴含「存量清理已随同事务执行过」⇒ 两个判据是同一个事实的两次陈述，删掉一个不减覆盖。

★ 运行时层新增 `scripts/audit/f3-postdeploy-verify.sh`（原先没有能判「归零且不反弹」的脚本，监控脚本只报数）：
两阶段 —— 阶段一按分钟轮询等残留归零（超时即失败）；阶段二在观察窗口内反复取数，任一次非 0 即判「反弹」失败。口径与监控脚本**逐字相同**。

★ 迁移 972 的**产物**没变（文件字节未动）⇒ 211 台账里 972 行的 `content_sha256` 仍然有效 ⇒ 第三次部署仍走「按指纹认账」路径，不需要重放迁移。

## 八、通用式（本轮沉淀）

1. **「同一张表的同一组列，必须由每条写入路径写同一套」**——触发器是**一层**的契约，直写 SQL 是**另一层**的契约；修了一层不等于修了这件事。本轮两次部署才把两层都摸清。
2. **「NEW 行里未被 SET 触碰的列携带旧值」**——INSTEAD OF UPDATE 触发器里，「调用方给了值没有」这件事**分辨不出来**（显式写 NULL 与没写，长得一样）⇒ 判据必须落在**状态语义**（available=TRUE ⇒ 无待恢复）而不是**来源语义**（调用方给没给值）。
3. **「写法看起来与兄弟列同款」不等于对**——隔离 PG 真跑腿的第一版修法就是这么错的；**弱判据（`contains xxx`）会放走它** ⇒ 门禁要钉**顺序**，不只钉**存在**。
4. **门被 `-run` 过滤器漏掉 ⇒ 变异全「绿」**⇒ 变异脚本的门过滤器必须与新增门**同步扩**，否则「变异 9/9 红」是自证的假绿。
5. **用 AST 扫源码，不要用正则切反引号**——Go 的结构体标签也用反引号 ⇒ 配对错位；且 SQL 是 tab 缩进 ⇒ 带空格的字面量匹配不到。两处都实测踩过。
6. **部署后的「没归零」是最有价值的信号**——它把「我以为修完了」变成「还有第二处」，而且是**部署**给的证据，不是单测给的。
7. **指标口径先纠偏再修代码**——同一个数字，「不可用节点数」与「恢复标记残留行数」的修法完全不同（前者查上游，后者查写面）。
8. **判据必须与它断言的那一层东西同层**——产物探针断言运行时状态 ⇒ ① 判据不成立（迁移在位也可能判失败）；② 处置无效（重放消不掉运行中二进制造的脏）；③ 探针退化成**毒丸**（部署被死锁）。**判据写在哪一层，决定它失效时的处置还有没有效。**
9. **门/探针失败时，先问「它给的处置建议有效吗」**——本轮探针失败时的建议是「重放本序列（幂等）」，而真实病因是**运行中的二进制在持续制造残留** ⇒ 「重放了也还是不行」就是**判据写错层**的信号，而不是「再重放一次」。
10. **「原子 ⇒ 一个判据足矣」**——迁移 972 把函数替换与存量清理放在同一事务 ⇒ 「函数体含新分支」蕴含「清理已执行」⇒ 两个判据是同一事实的两次陈述；**弱化判据不等于放走缺陷**，前提是**上层事实能蕴含下层事实**（这里靠原子性）。
11. **并发部署会让「观测到的现场」不属于自己**——本轮差点把并列车拉起的槽当成自己的部署结果去验收；⇒ 上线前后必须核对**镜像 id + 版本号 + 二进制内容**（本轮用 `grep` 二进制里的修复标记确认，比读版本号更硬）。
12. **单次「0」样本不能证明修复生效**——本轮在**旧二进制仍在服务**的情况下采到过 **0 行**（17:41 前后），但**跑着的二进制不含第二轮修复**（`grep` 二进制 = 0 处标记）⇒ 那只是**锯齿的谷值**：旧代码里「目录刷新（1 小时一次）批量造 ~200 行」与「checker 逐条清掉」两个过程叠加出的**周期波**，30 分钟一次的采样会**混叠**到谷底。⇒ **验收观测窗必须覆盖至少一个完整的产生周期**（本例 = 目录刷新周期 1 小时 ⇒ 观察窗 ≥ 75 分钟），否则「归零」只是相位巧合。
13. **「相对基线」的判据，基线必须真的是「改动前的树」**——部署门的新红判据是 `当前红 − 基线红`；当 `HEAD == BASE_REF`（例如刚合完并行车、还没开新提交）时，**基线树 == 当前树** ⇒ 存量红**两边都在** ⇒ 被差集消掉 ⇒ 门对存量红**完全失明**却照常报绿。⇒ **必须配一条与基线无关的直接判据**（扫全量 FAIL 行），否则「门绿」这句话在存量红面前**不承载任何信息**。★ 与 §八.8 同源：**判据的强度取决于它与被断言对象的层级关系**。
14. **修在数据层与写面的修复，会跟着别人的版本继续生效**——本轮收尾复验时，在役版本已被并行车推进到 `cce2c6bb`/3097（**不是**本轮的 `f6f99545`/3092），但 F3 残留仍恒 0 ⇒ 因为修复落在**触发器 + 三条写入路径**（数据面契约），而不是某个发布物 ⇒ ★ **这正是「把契约修在数据层」的收益：发布物被换掉，修复不被换掉**。反向也成立——若把修复只做在某个二进制的逻辑里，换版本即失效。
15. **观测纪律：先看采样间隔，再看采样值**——本轮 19:00 → 23:14 之间出现**采样空档**（休眠/断连）⇒ 「连续 N 次 0」的连续性假设不成立 ⇒ 判定「未反弹」时，**必须同时核验采样间隔本身是否连续**；否则「没有反弹」可能只是「没采到」。
16. **「验收判据必须由被验收者自己写下收尾标记」**——本轮有一条后台**监控包装循环**因撞上 3600s 运行上限被掐（`failed`），而**被验收的验收脚本**独立跑完并自己写下 `✅ 观察窗口内保持 0，未反弹`。⇒ 包装循环输出的 `verify_done=0` 是**观察时刻的快照**，不是结论；★ **观察者的存亡与被观察者的结论无关** ⇒ 验收结论必须能在**被验收者自己的输出**里逐字找到收尾标记，否则就是「自述与实现不符」。
17. **「门绿」这句话的信息量，取决于门实际跑了什么**——部署门是**增量门**（按最后一个提交触及的带测试目录选包，无触及时才回落核心清单）⇒ 同一句「闸门通过」在不同提交下可能只覆盖 3 个包、或覆盖 15 个包 ⇒ ★ **读门结论必须连「跑了哪些包」一起读**；否则会把「增量全绿」当成「全量全绿」，把一个窄结论当宽结论用。★ **更要命的是「没跑 ≠ 不算红」**：改动目录若**没有测试文件** ⇒ 它**根本不进包列表**（本轮实测：并行车新建包 `contracts/maascontracts`（M1 启动）**0 个测试文件** ⇒ 合流后门只报 `./cmd/gateway 全绿`，该包**零测试证据**）⇒ **「门绿」对无测试的新代码不承载任何证据** ⇒ 判读时必须逐个目录核对「进了包列表没有」。
