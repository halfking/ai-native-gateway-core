# 移动端菜单 PC 对齐整理 — 主档（2026-11-20）

> owner 需求＝「检查我们的移动端的菜单系统，分析其合理性，然后进行整理，从 PC 端的菜单的角度进行整理，并提交代码和推送。」
>
> 交付＝**合理性分析（§2，5 项发现）→ 按 PC 端 NAV_GROUPS 分类学把抽屉 89 席重组为 6 组（§3 映射表）→ 分组手风琴 UI（§4）→ i18n 组标题两端同名（§5）→ 判据更新（§6）→ 全部门禁绿 + 基线 10 红逐字对拍为存量（§7）→ 提交推送（§8）**。
> ★ 零迁移 / 零 schema 变更 / 零路由变更 / 零权限档变更 —— 本轮是**纯导航结构整理**：席一席不增一席不减、`requiresRole`/`requiresCapability` 逐字不变、页面与端点全部不动。

## 1. 对象与现状（改前取证）

移动端菜单系统 = 底栏 4 席（`BOTTOM_NAV`：总览 / 节点 / 模型 / 密钥）+ 抽屉「更多」（`DRAWER_NAV`，`web-mobile/src/config/appNav.ts`）。

改前的抽屉是一张**无分组的平铺清单**：

- **89 席**一字排开（`grep -c "key: '"` = 93 含底栏 4 席），抽屉打开后深页要**滚 4~5 屏**才能点到——`AppDrawer.vue` 文件头（2026-10-15 批注）原话：「DRAWER_NAV 已 85 席（还会继续涨），深页要滚 4~5 屏才能点到——真机验收轮实测这是可达性硬伤」。
- 唯一的导航手段是**搜索**（2026-10-15 加的）：它解决「我知道要什么」，解决不了「我大概知道在哪、想看看这层还有什么」。
- 席的书写顺序 = **接入批次顺序**（2026-10-06 起按批追加），不是功能分类：`alerts → usage → users → reconciliation → report-rollup → dispatch-journal → routing → providers → integrity → logs → journey → …`——同一族的功能（路由四姊妹：routing / routing-audit / overrides / routing-policy）散落在相隔几十屏的位置。
- 每席带大量**权限推导注释**（本仓最有价值的部分：哪席 admin 档、哪席 super_admin 档、为什么），但注释只服务「改权限的人」，不服务「找页面的人」。

对照 PC 端（`web/src/config/appNav.ts`）：PC 侧栏早已是**分组菜单**——`NAV_PRIMARY_ITEMS`（总览/实时拓扑/阶段树）+ 8 个 `NAV_GROUPS`（运营管理 / 供应商与模型 / 密钥与用户 / 请求与会话 / 数据运维 / 运维平台 / 接入指南 / 对话），组 id、组标题键（`nav.group.*`）、组内排序都有契约测试看守。

## 2. 合理性分析（5 项发现）

| # | 发现 | 严重度 | 本轮处置 |
|---|------|--------|---------|
| A1 | **89 席无分组**：抽屉是全系统唯一的「功能目录」，却只有线性滚动 + 搜索两种手段；PC 端同功能早就是 8 组分类。两端信息架构**不同构**，跨端用户要重新学一遍 | 高 | ★ 本轮主修：按 PC 分类学分 6 组（§3）+ 分组手风琴（§4） |
| A2 | **席序 = 接入批次序，不是功能序**：路由四姊妹、MaaS 六席、凭据监控族、审批三席都散落各处，「找齐一族」只能靠搜索逐个搜 | 高 | 同族席在组内聚合排布（§3 映射表 B/C/D/E 段） |
| A3 | **权限语义与分组无关，但注释里混着「方位词」**：「与上面那席相反」「对比上面四条超管线」这类指位在多年插席后已漂——本轮实测抓到 **2 处注释漂移**：`routing-policy` 的权限注释（2026-10-08 第一百零一批）漂在 `errors-trend` 席上方；`request-anomalies` 的权限注释（2026-10-14 第一百一十八批同段）漂在 `compliance-hits` 席上方。**注释归错了席 ⇒ 下一个改权限的人会照着错的席改** | 中 | 注释归位到本席（`appNav.ts` 内标注「本轮整理归位」）；「方位词」改为按名指涉（「与凭据×模型状态那席相反」） |
| A4 | **底栏与抽屉的分界是健康的**：底栏 4 席 + 「更多」满足 ≤5 席约束（UI 规范 02 §4），高频消费面（总览/节点/模型/密钥）直达；抽屉承载低频管理面。这一层**不动** | — | 保持 |
| A5 | **抽屉搜索仍是好资产**：平铺命中 + 权限先行的口径（2026-10-15）无需推翻；分组只是给「浏览」补了结构 | — | 保留，搜索态平铺跨组 |

**结论**：移动端菜单的**权限层**（requiresRole / requiresCapability / fail-closed 能力位）是本仓质量最高的部分之一（有白名单钉测、有逐席注释、有路由层同源对拍），**不合理的是信息架构层**——它从 2026-10-06 的 10 席长到 89 席，始终没有结构。本轮只动信息架构层，不碰权限层。

## 4. 抽屉 UI：分组手风琴（AppDrawer.vue）

- **浏览态**：6 组手风琴，**默认全收起**——组头 = 组名 + 席数 + 展开箭头，89 席的抽屉从「4~5 屏滚动」变成「6 行目录 + 2 次点击」，与 PC 端 topbar 分组（点组名展开子项）同一交互成本。展开态存在 script ref 里：组件实例常驻（App.vue 只切 modelValue），**本次会话内重新打开抽屉仍停在上次展开的组**。
- **组体用 `v-show` 收放**：席仍在 DOM（display:none），路由激活态与权限语义不随收放变化；display:none 内容不入 a11y 树、不进 Tab 序。
- **搜索态**：组头隐藏、命中席平铺跨组（沿用 2026-10-15 的匹配面：本地化标题 + key + 路径，权限先行）——搜索是「我知道要什么」的最短路径，不强制过组。
- **组级过滤**：`navItemsFor` 在组内逐组做（与 PC `visibleNavGroups` 同口径），空组整组隐藏；权限门控发生在渲染之前，被挡的席**真的不在 DOM**（与 v-show 无关）。
- **触控**：组头 `min-height: 48px`（R1 新增控件标准），`:focus-visible` 描边与既有控件同款；chevron 过渡受 `prefers-reduced-motion` 约束。

## 6. 判据更新（两处，均因「结构前提被整理打破」而非口径变化）

1. **`RequestAnomaliesGuard.spec.ts` ⑤ seatEntries 锚订正**：该普查器把 `appNav.ts` 从 `export const DRAWER_NAV` 起 slice——旧布局里席位区在 export **之后**；新布局席位在 `DRAWER_GROUPS` 里、`DRAWER_NAV` 的 export 在各组**之后** ⇒ 原锚把席位区整个切掉 ⇒ 普查报 0（恰是本 describe 头注警告的「安安静静给出全都没有」静默失效形态）。修法：锚改为「`export const DRAWER_GROUPS` / `export const DRAWER_NAV` 两个 export 里**先出现**的那个」，新旧布局都成立。⑤-2/⑤-3（席档位 vs 路由 meta 逐条对账、sliding-window 已知分歧钉测）修复后全绿。
2. **`AppDrawer.spec.ts`**：`mountDrawerAs` 增加 `expandGroups` 参数（默认展开全部组），既有 30 条判据的强度不变（它们量的「画出来的每一席」在展开后照旧可量）；新增两个 describe（9 条）：
   - 「AppDrawer 分组」：默认全收起（组体 display:none + aria-expanded=false + 权限挡的席真不在 DOM）、点组头展开/再点收起与 display 同步、组头计数 === 展开后实际席数（逐组对拍，合计=89）、搜索态平铺跨组且清空回分组态。
   - 「DRAWER_GROUPS 配置不变量」：扁平 DRAWER_NAV === 各组依序拼接（无丢席/重复席）、**89 席 / 6 组守门数字**（增减席必须是对接新面的轮次，不许重构轮悄悄改）、组 id 与 PC 同名同序、席 `to` 全局唯一（routeAllowedFor 按 to 精确查一项依赖它）、组标题键落词典、组内过滤并集 === 扁平过滤（组不改变权限口径）。
