## 一、方案与结构（对应 owner 需求逐句）

```
错误事件（worker 摄取 candidate_failure_logs_hot 按 error_kind 窗口聚合 / 管理面手动注入）
  → 匹配手册 error_playbook_entries（正文模式命中 > 类型级条目 > 未命中）
    ├─ 命中 ⇒ 标准模式：条目 auto_execute=TRUE 且全局闸开且过冷却期 ⇒ ExecuteEntry
    │         否则记 awaiting_approval / skipped（管理面可见、可手动执行）
    └─ 未命中 ⇒ pending 累计 ≥ kind_threshold(默认3) ⇒ AnalyzeUnknown：
          SQLLogContext（供应商/模型/状态码分布 + 3 条样本）
          → 外部分析端点 LLM（复用 LLM_GATEWAY_ANALYSIS_*，SSRF 装配侧校验）
          → Proposal{root_cause, confidence, plan_kind, plan}
          → NormalizePlan 白名单校验（非法 ⇒ prompt 兜底，条目仍落库）
          → 变更类方案（Mutating）须 confidence ≥ 0.80 才执行一次修正
            （TriggerAutoAnalyze）；低置信 ⇒ awaiting_approval
          → UpsertFromAnalysis 落条目（source='pi_analysis'）供后续标准模式
  → 自动完善：hit/execution/success/failure 计数；失败条目带失败上下文
    自动重新提炼（source='refinement'，refinement_count++）
```

**方案三形态（plan_kind 闭集）**：
- `script`：白名单动作步骤 DSL（≤8 步）。动作闭集 = `record_note`（只读）/ `set_settings_kv`（代码级 allowlist：仅 `security.enabled`、`security.mode`、`sanitize.output_check_enabled`）/ `disable_pi_rule`（规则必须存在，快照 enabled/severity/pattern）/ `call_admin_api`（闭集路由表 + 装配侧注入扩展）。任意 shell / 任意 SQL 结构性排除。
- `api`：单次管理面调用，path 必须 `/api/admin/` 前缀；归一化成单个 `call_admin_api` 步骤。
- `prompt`：AI 执行提示词，执行 = 把提示词+错误上下文+日志摘要交给 LLM，输出进执行留痕（不改状态）。LLM 不确定安全自动化时**必须**选这种（提示词硬性约束）。

**安全三件套**（与 PI ApplyFix 同纪律）：①白名单动作；②变更类方案 0.80 置信度门；③每步旧值快照进 `error_playbook_executions.steps` ⇒ `/executions/{id}/revert` 按快照逐条回滚。

**默认 fail-closed**：`error_playbook.enabled=false`（worker 惰性壳，管理面 CRUD/手动执行/手动分析始终可用）；条目 `auto_execute` 默认 FALSE——只有**非变更**方案才在 PI 落库时默认 TRUE；5 条种子全 prompt 型 + auto_execute=FALSE。

## 三、批判式审计（本轮）——发现与修正

审计方法：不采信上轮自述，逐条独立复算/实跑；真库契约测试对本地 kx-citus（15433/llm_gateway）实测。

| # | 发现 | 定性 | 修正 |
|---|---|---|---|
| F1 | script 多步执行第 N 步失败 ⇒ 前 N-1 步变更**留在生产**（PI ApplyFix 是事务 all-or-nothing，本执行器各动作独立副作用） | 真缺陷（半截变更） | 失败即按快照**逆序 best-effort 自动回滚**，回滚留痕进 steps；回滚也失败 ⇒ errorMessage 追加 `/executions/{id}/revert` 人工指引；无快照步骤不产生回滚噪音 |
| F2 | 提炼候选判据缺陷（两层）：首版用 `updated_at < last_executed_at`，但 **updated_at 触发器在任何 UPDATE 时顶成 NOW()** ⇒ 与 last_executed_at 恒相等 ⇒ 守卫把**所有**失败条目永久排除出提炼（假绿级回归）；不修则失败条目每轮 worker 重启被重复提炼 | 真缺陷（首版修正被真库当场打回） | 改**提炼标记行**判据：UpdatePlanFromRefinement 同步写 `trigger_source='refinement'` 留痕（不碰计数/last_status）；ListRefineCandidates 加 `NOT EXISTS(标记行 AND created_at > last_executed_at)` ⇒ 提炼后退出候选、再失败（失败时间晚于标记）重新入围 |
| F3 | LLM 未配置时 RefineEntry 每轮空转刷 WARN（内存 dedup 只在提炼成功后置位） | 噪音缺陷 | worker 提炼段加 `HasLLM()` 前置守卫 |
| F4 | api 形态方案引用未登记路由 ⇒ 执行期才发现 ⇒ 「失败→提炼→再失败」循环 | 真缺陷（循环空转） | 新增 `RouteChecker` 可选接口；归一化期 fail-fast ⇒ LLM 此类提案走 prompt 兜底（手册仍落库） |
| F5 | UpsertManualEntry「先查后插/改」两步 ⇒ 并发创建撞唯一键 23505 ⇒ 500 | 竞态 | 原子化：单条 `INSERT ... ON CONFLICT (表达式唯一键) DO UPDATE ... RETURNING id` |
| F6 | 执行留痕无保留期（命中/跳过/待确认每轮各一行，错误风暴下表无限增长） | 运营缺陷 | worker 每 24h 清一次 >30 天旧行（PruneExecutions；失败只 WARN 下轮再试） |
| F7 | `/stats` 条目统计走 `ListEntries(Limit 200)` 逐行累加 ⇒ 条目 >200 静默欠数 | 统计失真 | `EntrySummary`：SQL `COUNT(*) FILTER` + GROUP BY 直出 |
| A1 | **主档缺失**：交付轮未产出 docs/audit 主档（违背仓内惯例） | 文档缺口 | 本文档即补 |
| A2 | 基线红复核：上轮登记的 sqlguard 三项 + installer 993 三项 + admin D13 —— **全部已被上游列车收口**（本轮实测全绿） | 状态更新 | 无需动作 |

★ 审计最有价值的一条：**F2 的假绿**——首版修正只过了单测（假 store 不建模触发器），真库契约测试当场打回。这正是「单测打不穿 SQL 语义、真库才能证明」这条仓内既有通用式的再次应验；若没有真库腿，这个「修复」会以全绿门禁的姿态上线并静默废掉整个自动提炼。

## 五、遗留风险（登记不修/待拍板）

- **R1** 前端管理页未做：手册的呈现/编辑目前只有 API（entries CRUD 已齐）——UI 归 UI 列车；上线自动化前建议先有页面，否则只能 curl 运维。
- **R2** `call_admin_api` 闭集路由目前仅 1 条内置（pi-analysis/trigger）+ 装配注入面——手册条目的「api 方案」实际可执行面很小；扩路由须逐条登记（安全边界）。
- **R3** 未知错误分析每次消耗 2 次 LLM 调用（提案 + prompt 方案执行）——错误风暴下 `kind_threshold`/24h dedup/冷却期是唯一闸门；费用敏感场景先观察。
- **R4** watermark 用 `ts > maxTS` 严格大于，同微秒时间戳碰撞行会漏计（概率极低，影响=计数欠账非丢事件本身）。
- **R5** 995 尚未确认已在生产三台应用（docker 通道登记齐备，但本轮未部署；下次任一台部署时台账闸门会自动应用+探针对账）。
- **R6** `AnalyzeUnknown` 的执行修正不区分租户（Event.TenantID 只是记录）——手册条目是平台级；租户级差异化处置待产品口径。
- **R7** 本地 docker daemon 停机过 ⇒ 真库契约测试依赖本地 kx-citus 在场；CI 无 DSN 自动 skip（不会假红）。

## 六、通用式（本轮沉淀）

1. **「修好了」必须过真库腿才成立**——F2 首版守卫单测全绿、真库一跑即红（updated_at 触发器）。凡判据依赖 DB 列的时序/默认值/触发器行为，必须有真库契约测试。
2. **带触发器的表上，`updated_at` 不是可靠的时间线**——任何「A 时间 vs B 时间」判据前，先查该表有没有 BEFORE UPDATE 触发器顶 `updated_at`。
3. **失败处理与成功路径同等设计**——多步执行器的失败语义（回滚？留痕？半截？）要在第一版就定义；PI ApplyFix 的事务语义不能默认继承到跨表动作。
4. **量具/守卫的判据要选「不会被旁路更新的列」**——提炼标记行（事件行）比时间戳列可靠，因为事件行只由提炼动作自己写入。
5. **统计面禁止「列表聚合」**——`ListXxx(limit)` 逐行累加的统计在数据量过限后静默欠数（与 session-analytics 轮「聚合列必须对真库 information_schema 抄」同族：统计的口径必须与数据的真实规模同源）。
