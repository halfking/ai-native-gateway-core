## 2. 重点② asm audit sink 失败最初根因（真根因，两层）

**第一层（直接死因）—— acc-pg17 连接耗尽**：
asm 日志 1,572 条 `audit sink failed`（error=`retryable: audit: write to audit_events failed`）
全部落在 7 个突发（10-28 09:20/09:21/10:40/11:34/11:56/13:18/13:30 UTC）；**每一个突发
分钟** acc-pg17 日志都有 `FATAL: remaining connection slots are reserved…` /
`sorry, too many clients already`（全窗共 **724 次**，突发分钟密度最高 164 次/小时）。
突发分钟同时是维护作业分钟（`promote_*_hot_to_partition` / `REFRESH … CONCURRENTLY` /
URSM health 4.3s 全窗扫）+ 10-28 下午正是 DLQ 34,183 排空的高负载窗。
**最后一次耗尽 10-28 21:30，此后 26h+ 零复发**（与排空结束、负载回落后移相容）。

**第二层（诊断黑洞）—— asm 二进制丢弃底因**：`internal/audit/mapping.go` 的
`Sink.RecordEvent` 在 `repo.Insert` 失败时 `return consumer.Retryable(errAuditWrite)`
——**底层 pgx 错误（连接耗尽 vs 死锁 vs 超时）整体丢弃**，ingress 的 WARN 只剩外层一句话。
上轮建议「补底层 pgx 错误」本轮落地：

```go
// 双 %w：外层 sentinel 供 errors.Is 判别，底层原因（pgconn.PgError）
// 可被 errors.As 取出并随 ingress 的 WARN 一并上日志。
return consumer.Retryable(fmt.Errorf("%w: %w", errAuditWrite, err))
```

提交 asm 仓 `61aa202`（已推 origin/main）；`go build ./...` + `go test ./internal/audit/
./internal/consumer/` 全绿。**asm 容器下次镜像构建后生效**（本轮不动 asm 部署，见 §8）。

**损失对拍（数据零丢失）**：`audit_events` 97,100 行 ==
`gateway_event_inbox` completed 97,100 == 网关 outbox sent 97,100 ==
`gateway_projection_events` 97,100 == checkpoint 97,100，逐位一致；
失败窗内 `audit_events` 仍有 10,259 行写入 ⇒ 当时是**部分失败**（1,572/重投后全部成功），
不是整段断供。另注：`audit_events` 最早行 10-21 18:08 ⇒ 上轮「10-21 起被挡」的会话族
在 audit_events 侧没有更早的行可对拍（与「挡在 claim 之前」的定性自洽）。
