## 2. 重点② asm audit sink 失败最初根因（真根因，两层）

**第一层（直接死因）—— acc-pg17 连接耗尽**：

全部落在 7 个突发（10-28 09:20/09:21/10:40/11:34/11:56/13:18/13:30 UTC）；**每一个突发

`sorry, too many clients already`（全窗共 **724 次**，突发分钟密度最高 164 次/小时）。

URSM health 4.3s 全窗扫）+ 10-28 下午正是 DLQ 34,183 排空的高负载窗。
**最后一次耗尽 10-28 21:30，此后 26h+ 零复发**（与排空结束、负载回落后移相容）。

**第二层（诊断黑洞）—— asm 二进制丢弃底因**：`internal/audit/mapping.go` 的

上轮建议「补底层 pgx 错误」本轮落地：

```go

// 可被 errors.As 取出并随 ingress 的 WARN 一并上日志。
return consumer.Retryable(fmt.Errorf("%w: %w", errAuditWrite, err))
```

提交 asm 仓 `61aa202`（已推 origin/main）；`go build ./...` + `go test ./internal/audit/
./internal/consumer/` 全绿。**asm 容器下次镜像构建后生效**（本轮不动 asm 部署，见 §8）。

### 6.1 ★★★ 本轮最大发现：912 家族失踪的根因 = 容器通道 `docker exec` 缺 `-i`

部署后核对 R176 的 919/920 时**当场撞见 912 形态复现**：runner 报 applying、
台账写入、执行 sha 逐字一致，而 `active_minutes` 列与 `idx_node_probe_runs_cred_completed`
索引**不在库里**。逐层排除（不同库 / pre_cutover / 本地容器 / 双集群 / 适配器改字节）
后定位：

```
_dl_container_psql() { docker exec -e PGPASSWORD=... acc-pg17 psql ... -f - }
                                        ^^ 没有 -i ⇒ stdin 不接通
```

`psql -f -` 读到**立即 EOF ⇒ 零语句执行 ⇒ exit 0** ⇒ 上游 `set -euo pipefail` 看不到
任何失败 ⇒ 台账 INSERT 照写。**实证两批同根**：912/913（10-28 08:49）与 919/920
（10-29 09:58）——「sha 逐字一致、PG 日志静默、全集群搜不到产物」的完整解释。
宿主有 psql shim 的机器走宿主通道不受影响 ⇒ 缺陷只在「无宿主 psql 的机器部署」时
显形（211 宿主无任何 psql，ssh 直跑必中）。

**修复**：`docker exec` 补 `-i`（c659154a5，已推 origin/main）；在 211 上实跑验证：
删除 stale 标记 → 重放 → 本次真出语句结果（`ALTER TABLE / COMMENT / CREATE FUNCTION`
/ `CREATE INDEX`）→ **列与索引落地** → 912/913 探针 PASS。
`request_logs_sql` 管道左侧 sha 一致性证明字节正确 —— 字节对而执行器没拿到，
这类「零输出 + 零报错 + 成功退出」要**先验执行器真的拿到 stdin**，再验 SQL。
