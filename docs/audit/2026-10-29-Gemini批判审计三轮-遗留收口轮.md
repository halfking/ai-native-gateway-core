## 二、③ 损失上报点（serialize_responses.go）

- **跳过点与上报点的对齐方式**：不重写判据——`reportSerializeResponsesLosses`
  逐消息循环里直接调用 `buildResponsesInputAudio` / `buildResponsesInputFile`，
  **返回 nil 才上报** ⇒ 「上报的恰好就是序列化器会丢的」，两份判据永远不会漂移。
- **同协议守卫**沿用函数顶部早退（`src == ProtocolOpenAIResponses` 直接返回）：
  parse_responses 产不出无 data 的音频，URI 载体只会来自跨协议源或退化 IR。
- **document 分支与既有 file_id 分支不双报**：file_id 双空的 document 走既有
  `document.file_id` 分支（块以 filename-only 形态发出，不算消失）；新分支判
  「buildResponsesInputFile == nil」= 整块消失（nil source / url+data 双空 /
  非法载体空 data），有测试钉住两分支互斥。
- 真机链路实证（临时实例 8799）：Gemini 入站 `fileData{fileUri}` → 合成
  OpenAI 体 → openai-responses 候选的**主动升级桥**（proactive upgrade，凭据能力行
  `native_responses_nonstream/stream` 驱动）→ `SerializeResponsesRequest` ⇒
  捕获体里文本在、音频块整块消失（正确语义），且日志出现
  `ir.anomaly anomaly_type=ir_protocol_loss field_path=messages[0].content[0].audio
  carrier=url … "audio without base64 data cannot be expressed on the Responses API"`——
  **修复前这一跳是纯静默**。`carrier=url` 说明 parse_openai 的 URI 还原把
  FileURI 规范成了 `Type="url"` 载体——上报 metadata 里的 carrier 忠实记录了它。

## 四、④ alt=sse 缺省形态（handler_gemini.go）

- **SDK 行为（决策依据）**：Python `google-genai` 2.33.0 的流式路径**无条件**拼
  `'{model}:streamGenerateContent?alt=sse'`（models.py:4758 等 8 处）；JS
  `@google/genai` 1.7.0 同（dist/index.mjs 仅有一种拼接形态）。官方客户端永远
  走 SSE ⇒ 数组模式只服务「按厂方文档缺省行为写」的手写客户端 ⇒ 改动零回归风险。
- **实现**：`geminiWantsSSE(r)`（`?alt=sse` 显式才 SSE）→ 数组模式
  `newGeminiJSONArrayStreamWriter`。帧转换复用 `StreamChunk.SerializeGemini()`
  的**同一份 body 实现**（剥 `data: ` 前缀重排为数组元素），不第二份实现。
- **三个形态细节**（都由测试钉住）：
  1. SSE 注释（`: keep-alive`）在数组模式下**丢弃**——JSON 数组没有注释通道，
     厂方缺省形态本身也是静默的；`data: [DONE]` 哨兵同样不落数组。
  2. **错误终态也保持合法数组**：`failClosed` 数组分支按 arrayStarted/arrayClosed
     写 `[error]\n]` 或 `,error\n]` ⇒ 客户端任何时刻断在流尾都能解析。
     第一版实现「数组未开时写裸错误对象」被测试当场抓包（body 不再是数组）⇒
     修为「数组模式的 body 恒为数组」这一条不变量。
  3. **零帧流写 `[]`**，不可解析的非 SSE 诊断（`json.Valid` 才入数组）否则
     fail-closed 错误元素。
- **真机抓到的一个真缺陷（Content-Type）**：首版在 ServeHTTP 里按形态设
  `Content-Type`，真机 A/B 发现数组响应头仍是 `text/event-stream`——根因：
  ChatHandler 对合成请求**无条件**重设 SSE Content-Type，覆盖了预先设置。
  修法：数组模式的 writer 在 `WriteHeader` 提交响应头**前一刻**重设
  （header 决策必须在真正提交的时刻做，提前做的都会被下游覆盖）。
- **真机 A/B**（8799 + mock）：无 alt ⇒ `application/json` + 合法数组
  （3 元素、usageMetadata 尾帧、文本连接正确）；`?alt=sse` ⇒
  `text/event-stream` + 标准 Gemini SSE 帧 + keep-alive 注释。
  fileData 音频请求经 Responses 桥完整闭环：200 + 数组（4 元素）。
  第三轮请求一度 `All 3 candidates failed`——根因是 mock 首版不支持
  `stream:true` 的 Responses SSE（网关 failover 正确），mock 补流式分支后闭环。
  错误终态数组 `[{"error":…}]` 也被真机抓到一次（前述失败响应），形态正确。
- 遗留记实：数组模式没有心跳——上游停滞时客户端只能靠读超时发现（与厂方
  缺省形态一致，是方言选择不是缺陷）。

## 六、遗留（如实记）

1. Responses 侧损失上报的**非 audio/document 字段**（thinking/cache_control 等）
   既有覆盖不变；本 轮只补了审计点名的两族。
2. 数组模式的心跳缺失（见 §四末）——如需停滞感知，客户端要设读超时。
3. `parse_openai` 把 URI 音频规范成 `Type="url"` 载体（而非保留 `file_uri`）
   ——上报 metadata 如实记录 carrier，语义无损，未改。
4. 本地 `schema_migrations` 台账与真实结构的其他潜在漂移未做全量对拍
   （本轮只治了 42703 点名的 885）。
