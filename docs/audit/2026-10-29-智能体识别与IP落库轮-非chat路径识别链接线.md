## §2 根因（两个，各自独立）

### 2.1 非 chat 路径识别链整块未跑（本批修，★ 用户指认会话的根因）

`/v1/responses`（ResponsesHandler）与 `/v1/messages`（MessagesHandler）主流程：
- **从不调用 `logCtx.SetKey(ki)`**（只有限流分支调了）；
- **从不调用 `logCtx.EnsureCaptured()`**（chat 主路径在 handler.go:2477 调）；
- ⇒ `refreshMeta → fillAttemptMeta` 从未执行 ⇒ meta 全零；
- ⇒ `recordInitialRequestLog`（handler.go:8107）用空 meta 发 `request_context_attrs`
  ⇒ agent_name / client_ip / client_protocol / fingerprint_raw / turn_no **整块 NULL**，
  只剩 fillFromKeyInfo 的 api_key_id / application_code（与库里签名逐字段吻合）；
- ⇒ **系统提示词兜底**（`DetectAgentFromSystemPrompt`）依赖 `meta.SystemPrompt`，
  而它只在 `EnsureCaptured` 里从 body 抽取 ⇒ 这条兜底在非 chat 路径**从未有机会运行**。

**DB 签名验证**（key 89 huangxt-coding / key 134 minimaxcode）：
空名行 = `api_key_id ✓ + application_code ✓ + 其余全空`；
同一 key 偶发的**已识别**行（如 16:41 的 minimax-code / 192.168.31.37 / openai-responses）
= meta 填满。同一 key 两种形态并存 ⇒ 路径差异而非客户端差异。

**路径实锤**：抽空名行 request_id 反查网关日志 `path=/v1/responses`。

### 2.2 用户指认的 ZCode 提示词【不需要新判据】

单元测试实锤：`DetectAgentFromSystemPrompt("You are ZCode, an interactive coding agent")`
= `"zcode"`（`you are zcode` 锚点早已在表里）。用户给的会话
`23c2ab5e64da83709b794f952b8ca94e` 在 DB/log 精确检索 0 命中（id 可能经转写或为

## §5b 批判式审计轮（同日第二轮，对上一批改动本身）

审计对象＝上一批（88e277974）的**改动与其文档断言**。结论：上一批的方向与
落库验证正确，但**缺三样东西**——一处真缺陷（失败路径丢 body）、一处真副作用
（client_model 空）、以及**一整层回归门**。另订正上一批文档里一处**错误断言**。

### §5b.1 发现 1（真缺陷）：失败路径拿不到 body ⇒ 系统提示词兜底在失败行上恒失效

`readRequestBody`（request_meta.go:172）**消费 body 但不复原**；只有
`bufferRequestBody` 才复原（:168）。responses / messages 直接调
`readRequestBody(r.Context(), r.Body, maxBodySize)` ⇒ body 被读走后，
后续 `captureAttemptBody(r, &attemptRequestBody, …)` 拿到**空 buffer**
⇒ 认证成功之后的失败分支（attachment_store_failed / body_too_large /
panic 兜底等）产出的行**没有 body** ⇒ **系统提示词兜底恰好在运维最需要看的
失败行上失效**。

⇒ 修复：新增 `readRequestBodyRestore(r, limit)`（request_meta.go:172）——
读后复原，**读失败或超限时不复原**（残缺字节流不能当作完整 body 重放，
否则下游解析器会看到「看起来合法但其实是截断」的请求）。
responses / messages 改用它；`readRequestBody` 本身语义不动（chat 路径的
调用方期望不变）。

### §5b.2 发现 2（真副作用）：client_model 在非 chat 路径恒空

`EnsureCaptured` → `ensureRequestBodyBuffered` 在 `c.Body` 已非空时**提前
return** ⇒ **不会**提取模型。而上一批为了避免二次读 body，恰恰先给
`logCtx.Body` 赋了值 ⇒ 这一步被跳过 ⇒ `c.ClientModel` 恒空 ⇒ 主表
`_request_logs_hot.client_model` 在 /v1/responses 与 /v1/messages 流量上空白。

⇒ 修复：两处 handler 在 body 读后显式补 `SetClientModel(extractModelFromBody(bodyBytes))`
与 `"<unknown>"` 兜底（与 chat 路径 handler.go:2433 同款语义）。

### §5b.3 发现 3（最严重）：上一批**没有任何回归门**——等于把本轮的核心教训又犯了一遍

本轮的核心教训是「**判据收口 ≠ 接线收口**」。而上一批把接线补上了，却**没有
钉住接线** ⇒ 下一次重构删掉那两行时，测试全绿、现象复发。

⇒ 修复：新增 `domains/streaming/identification_nonchat_test.go`，两层断言：
- **行为层**：`BuildContextAttrsEntry`（侧表 `request_context_attrs` 的唯一
  构造函数）——弱 UA（Go-http-client/1.1）+ 系统提示词自报 ⇒ agent_name=zcode /
  minimax-code；强 UA（pi/1.4.0）⇒ 强名不被兜底覆盖。
- **接线层**：**AST 级**断言两个 handler 各自调用 `SetKey(ki)` 与
  `EnsureCaptured()`。

**为什么接线层必须用 AST 而不是文本匹配**：第一版用 `strings.Contains`，
变异验证（把两行注释掉）时**测试仍然全绿**——注释里还留着同样的字符串 ⇒
自证式测试。改用 `go/ast` 后，注释对 AST 不可见 ⇒ 变异即红。

**变异验证读数**（回退修复 → 复跑）：
```

注释掉 responses.go/messages.go 的 SetKey(ki) 与 EnsureCaptured() 后:
  --- FAIL: TestNonChatHandlersCallIdentificationChain/responses.go
      responses.go never calls SetKey(ki) …
      responses.go never calls EnsureCaptured() …
  --- FAIL: TestNonChatHandlersCallIdentificationChain/messages.go
      messages.go never calls SetKey(ki) …
      messages.go never calls EnsureCaptured() …

```
⇒ 断言形状含**首参**（`SetKey(ki)` 而非 `SetKey`）：文件里另有 rate-limit
分支调 `SetKey(keyInfo)`，只断言方法名会在主流程丢失调用时仍然通过。

### §5b.4 订正：上一批文档里的一处**错误断言**

上一批 AGENTS/LESSONS 写「`turn_no` 侧表恒 NULL（权威口径在 ROW_NUMBER 派生，
SetTurnNo 无调用方）」。审计实测：
- `SetTurnNo` 确实**无任何调用方** ⇒ 侧表 `request_context_attrs.turn_no` 恒 NULL **属实**；
- 但「权威口径在 ROW_NUMBER 派生」**不属实**——全仓 `row_number()` 只有
  `admin/annotation_handler.go:390` 一处，与该侧表无关；`session_turns_hot.turn_no`
  由会话写手（`domains/session/v2/turn_writer.go` 的 MAX+1 分配）正常写入
  （实测4063 行 turn_no=1）。
⇒ 正确表述：**侧表 turn_no 无写入方（best-effort 字段，实际缺）**；
**会话轮的 turn_no 正常**（权威口径在会话写手，不在派生查询）。

### §5b.5 发现 4（**本轮最实质的发现，生产实测坐实**）：失败行的系统提示词兜底**根本没跑**

前三个发现都是静态审查所得；这一条是**部署后用真实流量实测出来的**——同一请求、
同一 UA、同一系统提示词，**成功行**落 `agent_name=zcode`，**失败行**落
`agent_name=go-client`。

根因不在 body 是否拿到，而在**谁生产 `meta.SystemPrompt`**：
- `meta.SystemPrompt` **只在 `EnsureCaptured()` 里生产**（从已缓冲 body 抽取）；
- `refreshMeta()` 只是**消费**它（把它喂给 `shouldOverrideAgentName`）；
- 而 responses/messages 的**失败行**走 `recordFailedRequestWithKey` → 它新建一个
  RequestLogContext 后只调了 **`ctx.refreshMeta()`** ⇒ `meta.SystemPrompt` 恒空
  ⇒ **兜底链的最后一环没有输入** ⇒ 弱 UA 名（go-client）留在失败行上。
- 对照：chat 路径的失败行走 `captureAndEmitFailure` → **已经调 `logCtx.EnsureCaptured()`**
  ⇒ chat 的失败行本来就有兜底（211 生产读数：chat 失败行 2248 条全部带
  `prompt_tokens`，即 EnsureCaptured 确实跑过）⇒ **两条路径本来就不对齐**。

⇒ 修复：`recordFailedRequestWithKey` 里把 `ctx.refreshMeta()` 换成
`ctx.EnsureCaptured()`（body 已在 ctx 上，EnsureCaptured 不会重读请求）。
副作用核对：`EnsureCaptured` 顺带做 receipt-time token 估算 ⇒ 失败行会多出
`prompt_tokens` + `usage_source=estimated` ⇒ 这**与 chat 路径既有行为一致**
（不是新语义），本轮是让 responses/messages **对齐** chat。

⇒ 教训（进 §7 通用式 13）：**「同一个兜底在成功路径生效、在失败路径失效」是
可观测的**——它的表现是**同一请求两行落库值不同**（成功行有名字、失败行只有弱名）。
⇒ **失败行是运维最常看的行**：一个只在成功路径生效的识别，其价值在排障场景里
趋近于零。⇒ **凡有兜底链的字段，必须逐条路径核销「兜底的输入由谁生产」**。

## §7 通用式（详见 LESSONS）

1. **收口判据 ≠ 收口调用**：㊻ 把判据收敛成一份实现，但「哪个入口调用它」
   没有收敛——三个 handler 三份接线，两份是空的。判据唯一化之后，**接线点
   也必须唯一化或至少逐一核销**。
2. **「主流程没有，分支才有」是一类结构性盲区**：SetKey 只写在限流分支里，
   成功路径（99% 流量）反而不跑——按「谁写日志谁负责」的直觉找不到它，
   要按「这条字段在哪条路径上第一次被赋值」倒查。
3. **侧表字段的「整块同空」是路径缺失的指纹**：api_key_id 有而
   agent_name/client_ip/protocol/fingerprint 全空 ⇒ 不是客户端不发，
   是 meta 没被填——用字段组的相关性定位代码路径，比逐字段猜快得多。
4. **兜底链的每一层都要「喂到」**：系统提示词兜底的输入（meta.SystemPrompt）
   只在 EnsureCaptured 里生产；一个入口不调它，兜底就是死代码——「链存在」
   与「链被运行」要分开验证。
5. **memo 必须感知其输入的到达时机**：在「先 header 后 body」的路径上，
   依赖 Body 的 memo 会在空输入上提前终判。
6. **「补上接线」和「钉住接线」是两件事**：上一批把识别链接线补上了，却没有
   任何回归门 ⇒ 下次重构删掉那两行时全绿通过、现象复发 ⇒ **改接线必须同批
   交付一个会因接线消失而变红的门**。
7. **静态门必须对注释免疫**：文本匹配（`strings.Contains`）在「把调用注释掉」
   这种最常见的回退方式下**仍然绿**（注释里还留着同样的字符串）⇒ 用 AST 或
   「剥注释后匹配」；本轮第一版测试就是这样被自己的变异验证判死的。
8. **断言形状要含首参**：同一文件里 `SetKey(ki)`（主流程）与 `SetKey(keyInfo)`
   （限流分支）并存 ⇒ 只断言方法名则主流程丢失调用时仍绿 ⇒ 断言到「方法名+首参」。
9. **变异验证是测试有牙齿的唯一证据**：本轮对自己上一批改动做的第一版测试，
   变异（回退修复）后**仍全绿** ⇒ 那是不合格的门；改 AST 后同一变异红 4 处。
10. **文档里的「权威口径」也要实测**：上一批写「turn_no 权威口径在 ROW_NUMBER
    派生」，实测全仓 `row_number()` 只有一处且无关 ⇒ 断言错在**方向**（把
    「无写入方」说成「有派生口径」）⇒ 文档断言与代码断言同样需要变异/实测。
11. **消费型读取函数要问「读完还在不在」**：`readRequestBody` 消费 body 不复原
    ⇒ 下游任何「再读一次」都拿到空 ⇒ 静默失效往往发生在**异常路径**（运维最需要
    看到的那批行）。新增「读后复原」变体时，**超限/读失败必须不复原**。
12. **预填 Body 会关掉同函数里的其它副作用**：`ensureRequestBodyBuffered` 在
    Body 已非空时提前 return ⇒ 顺带跳过了模型提取 ⇒ 预填不是「等价于不预填」，
    每跳过一个副作用都要单独补齐。
13. **兜底链的「输入由谁生产」要逐路径核销**：`meta.SystemPrompt` 只在
    `EnsureCaptured()` 里生产，`refreshMeta()` 只消费它 ⇒ 只调 refreshMeta 的
    路径（失败行构建器）⇒ **兜底静默失效**。⇒ **同一请求「成功行有名字、失败行
    只有弱名」是可观测的差异** ⇒ 它比「全都不识别」更难发现 ⇒ **失败行是运维
    最常看的行，只在成功路径生效的识别在排障场景里价值趋近于零**。
