## 三、修复的问题

### F1(P2)压缩缓存 V1 回退路径:L2 复水的 hash 形状失配使增量匹配静默失效

**根因链**(两份代码各自正确、组合错误,r1021「两路径政策必须一致」的再犯形态):

1. `CommitFinal` 存的 state:`LastOutboundHash = sha256(完整出站 envelope)`(session_compressor.go:1023,`{"model":...,"messages":[...]}`);
2. L1 逐出/进程重启后,L2 Redis 只存元数据;复水走 `loadFromDB` → turnReader 从 session_bodies 取回**消息数组**重组为 `{"messages":[...]}`;
3. `session_cache.go` 复水分支用 `c.turnReader != nil ||` 短路 hash 校验**收下了这个 body**(注释自认形状不可比),但**没改 state 里残留的 envelope hash**;
4. 下游 `diff.go:118` 的 lineage 守卫(2026-09-03 d6a027169 引入)比对 `sha256(lastOutboundBody) != state.LastOutboundHash` → 判新会话 → **全量重发 + 压缩血统重置**。
5. 时间线:复水路径 2026-08-04(4e3ae0158)先在,守卫 09-03 后加,后者没适配前者的形状差。

**触发面**:V2 读路径失败的窗口(V2 DB 抖动、`sessions_v2_compression_read=false` 时为常态)× L1 逐出/重启。每次触发 = 该会话一轮全量重发(压缩收益归零一次),随后 CommitFinal 自愈。非安全问题(客户端历史本就是全量、已脱敏),是缓存有效性缺陷。

**修复**(`domains/hooks/compression/session_cache.go`):复水分支收下 turnReader body 时,校验消息数一致(`st.MsgCount == countMessages(persistedBody)`,对抗性「不同轮次内容」仍被拒)后,**重derive hash 使 state+body 配对自洽**;计数不一致落回保守的 mismatch 分支(body 不采纳)。

**判据**(`session_cache_v2_rehydrate_test.go`,同层驱动):
- `TestSessionCache_L2RehydrateFromV2KeepsDeltaLineage`:envelope-hash 的 Redis state + turnReader 消息数组 → 断言配对自洽 **且 `BuildOutboundMessages` 走增量合并(3 条=旧 2+新 1,非 IsNewSess)**——判据落在真实消费层。
- `TestSessionCache_L2RehydrateRejectsCountMismatchedV2Body`(前提在场配对):计数不一致的 V2 body 不被采纳、state hash 不被洗写——保守行为保持。

**变异验证**(cp 备份恢复,不用 git):
- M1(回退为「收 body 但保留 envelope hash」)→ lineage 判据红("lineage guard rejected the V2-rehydrated pair");
- M2(去掉计数守卫,无条件采纳)→ 前提配对判据红("count-mismatched V2 body was adopted")。
- 恢复后三测(含既有 legacy 腿用例)全绿。

**接口顺带改动**:`SetTurnReader` 参数从 `*v2.TurnReader` 收窄为新接口 `TurnReaderSource`(LoadLatestOutbound/LoadChain 两法)——*v2.TurnReader 天然满足,唯一生产调用点(main.go:2832)不变;这是让 L3 复水行为可单测的最小改动(此前该分支只有真 PG+Redis 的集成测试覆盖,而那测试从未在任何 CI 门里跑过,见 §六)。

### F2(P3)非法 `LLM_GATEWAY_SANITIZE_OUTPUT_ACTION` 值静默回落

运维把 `block` 拼成 `Block `/`true`/`deny` 时无声降级为 mask,无任何日志。修复:唯一消费点(goal_control.go)对非空非 `block` 值打启动 Warn;回落语义不变。

# 续轮(同日晚,§五-3/§五-4 收口):首次执行审计套件抓到 F3 + 建立常设门

## F1 续(真缺陷,同族异支):计数失配分支丢弃 L3 自洽配对,塌缩成「陈旧 state + 空 body」

**发现链**:首次执行 `run-session-storage-stream.sh` → `TestStorageAuditObserveV2MetadataBodyMismatch`
FAIL(base 断言 `require.NotEmpty(body)`)。时间线考古:该集成测试(2026-10-02,
`11cc07710`)先于 r1031 的 F1 修复(10-14 `9a66472f1`)存在,但从未运行——r1031 给
「计数失配」钉的保守钉子(`TestSessionCache_L2RehydrateRejectsCountMismatchedV2Body`
:body 必须保持空)与它**对同一场景钉了相反契约**,两份判据从未同场执行,矛盾不可见。

**产品缺陷本体**(`session_cache.go` L2 复水 default 分支):Redis 元数据与 V2 body
计数失配(元数据陈旧:Redis 回写失败 / mirror 反向滞后 / 多实例竞态)时,legacy 兜底
不可用即返回「陈旧 state + 空 body」,且 `setL1` 把这个明知不配对的组合缓存进 L1:
空 body 使 diff.go lineage 守卫判新会话 → 全量重发 + 压缩血统重置(F1 同机制);
陈旧字段(SummaryMarker/切割标记)还可能复活旧决策。而 `loadFromDB` 明明构造了
自洽的 L3 配对却被 `_,` 丢弃。

**修复**:default 分支 legacy 兜底失败后**整体采纳 L3 自洽配对**(`st, body =
persistedState, persistedBody`),不混绑——「不把失配 body 洗进 Redis 元数据」的
反洗写原则保留(旧 state 的 Redis-only 字段不存活);legacy 命中 hash 的优先路径
不变;turnReader 为 nil 时不再重复查 legacy(loadFromDB 已是 legacy)。修复后
`TestStorageAuditObserveV2MetadataBodyMismatch` 连 `--require-coherence` 强断言
都通过(state.hash==sha256(body) 且计数一致)。

**判据**:r1031 的前提配对判据**改写**为
`TestSessionCache_L2CountMismatchDropsStaleRedisMetadata`(同层):body 非空、
配对自洽、Redis-only 的 SummaryMarker 不被洗入、BuildOutboundMessages 走增量
(3=旧2+新1,非 IsNewSess)。变异验证:M1(恢复空 body 行为)红在「塌缩成空
body」断言;M2(洗写变异:保留 Redis state 只换 body+hash)红在「配对自洽 +
计数」断言。恢复后全包绿。
