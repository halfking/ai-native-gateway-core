## 一、新门「节号唯一性」

### 1.1 它为什么值得建（实测规模）

| 位置 | 顶级节号数 | 重复 | 性质 |

⇒ ★★ **handoff 那 15 对不是「同名小节」** ⇒ 两个会话各自建了**一整套** `§19.18` / `§19.19` 号段
⇒ ⇒ **撞车面 = 15 对小节 ＋ 2 对父节** ⇒ ⇒ ★★ **「只查我关心的那个号」完全看不见**。

### 1.2 为什么「缺一道门」是根因

★ `scripts/ursmcheck` 里读 `LESSONS.md` 的门**只有两道**：
`TestLessonsFileHasNotBeenClobbered`（体量地板）＋ `TestLessonsFileHasNoConflictMarkers`（冲突标记）。
★ **零道门查「节号是否重复」**；★ **handoff（33k+ 行、300+ 顶级节号）一道门都没有**。

⇒ ⇒ **⇒ 结果就是 19 对重复长期躺在 main 上** ⇒ ⇒ ★★
★★ **⇒ 而我 R103 轮自己两次撞号（`§19.20.75`、`§230`）、对方两次让位、另一次换段（`§19.20.x` → `§19.21.x`）**
⇒ ⇒ ★★ **⇒ 这不是「谁不小心」的问题，是【缺一道门】的问题** ⇒ ⇒ 人靠自觉必然漏。

### 1.3 门做什么

1. **按【文件全量枚举】**解析全部带节号的标题（`##` / `###` / `####` 三级）⇒ ★ 不抽查
2. **主判据**：每个节号的出现次数 **必须 == 豁免表登记的次数**（默认 1）
   - ⇒ 新增任何重复 ⇒ 次数 1→2 ⇒ **红**
   - ⇒ 存量被修掉 ⇒ 次数 2→1 ⇒ **红**（提示对齐豁免表）
3. **总量钉死**：重复【对】总数 == **19** ⇒ 防止豁免表被悄悄做大（把真重复登记成「合法」）

### 1.4 设计取舍（★ 有一条是被实测推翻的）

- ★★★ **豁免表的键用【节号 → 次数】，不是【节号 → 标题指纹】**
  ⇒ 原因（实测）：`§19.18.1` 的两处标题**完全相同**（「一句话结论」）⇒ **指纹分不清** ⇒ 指纹方案不可用。
  ⇒ 次数方案更稳：**改标题不影响判定** ⇒ 而「存量被修掉 ⇒ 次数变化 ⇒ 红」正好是我们要的。
- ★★ **子节命名空间不需要分治**：实测子节号形态是 **含父节号** 的（`#### §19.20.19.9`）
  ⇒ ⇒ 子节号与顶层号**不在同一字符串空间** ⇒ ⇒ 「全局唯一」就是正确判据。

### 1.5 ★ 三类自检 + 四条真实变异（门有牙的证据）

| 变异 | 手法 | 门的反应 |
|---|---|---|
| **M1** | `LESSONS.md` 追加一个**当前唯一节号**的副本 | **RED** ✔（`TestSectionNumbersAreUniqueBeyondKnownBaseline`） |
| **M2** | handoff 追加一个重复 | **RED** ✔（同上） |
| **M3** | **删掉**存量重复中的一条（次数 2→1） | **RED** ✔（同上 ⇒ 证明「存量被修掉也会提示对齐」） |
| **M4** | 把一条存量重复**改成新号**（冗余对数 19→18） | **RED** ✔（`TestSectionNumberDuplicatePairCountIsPinned`） |

⇒ ★★ **还原后 md5 逐字一致**（`LESSONS.md` `5999ab6308b5…` / handoff `92acdcb6320d…`）
⇒ ⇒ ★★ **⇒ 「门有牙」是实测的，不是推断的**。

### 1.6 ★★ 判据形态：本轮已连续四次栽在判据上（★ 这道门把它们写进了注释）

1. **结构标记必须【整行完全相等】判** —— `startswith("<<<<<<<")` 与子串计数都会把「**被引用的示例行**」（`grep -c '<<<<<<<'`）当真标记。
2. **「有多少对重复」不是客观事实，是「用什么口径数出来的」** —— 我先读数「16 对」，其中 1 对是假阳性（`§19.25.10bis` 被正则截成 `§19.25.10`）。
3. **结构解析不要用 `\b`** —— 它与全角字符（`·`）相邻时行为不可靠 ⇒ 我用它数出「313 个 / 我的 `§19.20.77` 出现 0 次」，**实际是 314 / 1 次**
   ⇒ ⇒ ★★ **「我的东西不见了」的根因是【我的判据】，不是【合并】** ⇒ ⇒ **又一次「0 命中的第一嫌疑是量具坏了」**。
4. ★★ **零丢失校验的判据必须与【变更形态】匹配** —— 追加 ⇒ 逐行完全匹配成立；**行内插入 ⇒ 逐行与片段连续性判据都必然假阳性**
   （实测 40/20/10/6 字粒度各报 1 个「缺失」，**全部是假阳性**）⇒ ⇒ **决定性判据 = 字符/词集合级比较**。

## 三、提取器设计蓝图（★ 实现留给下一轮）

### 3.1 ★ 定位：它的真正价值不是「重做 R63」

R63 已**手工**把 98 条功能表候选逐条定性完（真缺口 = 0），且结论「**对超集成立**」
⇒ ⇒ 若提取器只是一次性脚本 ⇒ **价值有限**（仓内已有大量一次性脚本）
⇒ ⇒ ★★ **所以把它指向一个【永续有效的不变量】**：

```
悬空引用 = (产品按名引用的关系) \ (仓内全部 DDL 建出的关系)
```

⇒ 这是 R63 §5「三侧对照」第③侧的机械化 ⇒ ★★ **它不随「生产 / 新装」变化**
⇒ ⇒ **门不会因正常演进而红** ⇒ ⇒ **值得做成门**。

### 3.2 两条腿（★ 两侧都必须「扫全」）

**腿 A：仓内「建出了哪些关系」（DDL 侧）** —— ★ **只扫 `CREATE TABLE` 的提取器必然漏**（R63 §2.4 实证）：
`CREATE TABLE` / `CREATE TABLE … PARTITION OF` / `CREATE VIEW` / `CREATE OR REPLACE VIEW` /
`CREATE MATERIALIZED VIEW` / `CREATE FUNCTION … RETURNS TABLE|SETOF` / `ALTER TABLE … RENAME TO` / `CREATE SCHEMA`

**腿 B：产品「引用了哪些关系」（产品侧）** —— ★ **只在 SQL 上下文取名**，三档桶：
| 桶 | 判据 | 含义 |
|---|---|---|
| ① 强命中 | 出现在 SQL 上下文（`FROM`/`JOIN`/`INSERT INTO`/`UPDATE`/`DELETE FROM`/`COPY`/`TRUNCATE`/`FROM ONLY`） | 候选依赖 |
| ② 弱命中 | 在代码但**不在** SQL 上下文 | 需人工核（★ R63 那 11 条误报**全在②**） |
| ③ 零命中 | 完全没有 | ★ **可判定不依赖**（单向蕴含） |

### 3.3 ★ 自检清单（peer 的硬要求 + R63 §2.4 的通用式）

1. **搜索面完整性**：两侧集合**非空** ＋ 命中条数 == 期望条数（期望来自「不加过滤的原始命中数」）
2. **无截断自检**：断言原始命中数 == 解析后条数（★ 直接抓 `head` 截断）
3. **动态拼名前缀探测**：★ 这是「按名零命中 ⇒ 不依赖」的**前提守卫** ⇒ 一旦发现 `prefix+变量` 形态 ⇒ **必须显式报出**（不能静默）
4. **幂等**：同输入两次跑逐字相同
5. **归属 ≠ 使用**：输出表述为「**候选依赖**」，不是「依赖」
6. **变异验证** ＋ 7. **反向夹具**（造一个真悬空引用 ⇒ 门必须红）

### 3.4 ★★★ 口径决策（本轮实测得出 ⇒ 下一轮可直接实现，不再重新拍板）

★★ **R63 那条线卡住提取器的真正原因不是「怎么提取」，而是「什么算产品引用」** ⇒ 本轮实测得出三条口径：

| # | 口径 | 取值 | 依据 |
|---|---|---|---|
| ① | **产品代码的范围** | 仓内**几乎所有顶层 Go 包**（`admin`/`api`/`apihub`/`bg`/`cache`/`cmd`/`db`/`discovery`/`domains`/`internal`/… 共 30+ 个） | 实测：非测试 `.go` 文件数 `domains` 921 / `admin` 304 / `internal` 228 / `bg` 155 / `cmd` 154 ⇒ **不是一个或两个目录** ⇒ ⇒ 单目录口径会漏掉大半产品代码 |
| ② | **明确排除** | `vendor/`（4994 个 .go）｜`installer/`（48）｜`scripts/`｜`tools/`｜`test/`｜`tests/`｜`examples/`｜`npm/`｜`web/`｜`web-mobile/`｜`deploy/`｜`docs/`｜`sql/`｜`migrations/` | ★ 这些目录**也大量引用表名**（安装器建表、脚本查表）⇒ **但它们不是「产品读写」** ⇒ ⇒ 若不排除，差集会被淹没 |
| ③ | **`_test.go` 一律排除** | 是 | ★ 测试引用表名 ≠ 产品依赖 ⇒ ★★ **但要登记为口径项**：若某表**只有**测试引用，它在「产品依赖」口径下**不算被依赖** ⇒ ★ 这与「产品依赖 ⇒ 必然按名出现」的单向蕴含**不冲突**（蕴含方向是「依赖 ⇒ 按名出现」） |

★★ **★ 实现形态的结论（★ 本轮实测得出的一个硬约束）**：
★ **提取器应当用【Go】写（`cmd/tools/extract-product-referenced-relations/`），而不是用正则扫 `.go` 文本** ——
⇒ 理由：**Go 的 SQL 几乎都在字符串字面量里** ⇒ ⇒ **正则扫整行会把注释里的 SQL、文档字符串、非 SQL 文本一并算进来**
⇒ ⇒ ★★ **正确做法 = 用标准库 `go/parser` + `go/ast` 解析每个 `.go` 文件，提取全部 `*ast.BasicLit`（STRING）** ⇒
⇒ ⇒ ★★★ **★ 而且这同时解决了 R63 教训里的「剥注释」问题**（★ `go/ast` 天然把注释与字面量分开 ⇒ **不需要自己写剥注释器** ⇒ ⇒ **不会踩「剥注释把普通字符串字面量也剥掉」那个坑**）
⇒ ⇒ ★ **零第三方依赖**（★ 与本仓 `scripts/audit/page-sweep-cdp.mjs` 的「零依赖」取向一致）。

★★ **规模实测（供下一轮估工）**：3460 个 `.sql` 文件 ｜ 10763 个 `.go` 文件 ｜
DDL 形态计数：`CREATE TABLE` 2300 ｜ `CREATE VIEW` 366 ｜ `CREATE OR REPLACE VIEW` 337 ｜
`CREATE MATERIALIZED VIEW` 40 ｜ `CREATE … FUNCTION` 1360 ｜ `PARTITION OF` 445 ｜ `ALTER TABLE … RENAME` 56
｜ Go 侧 SQL 上下文原始命中 **28282** 处（去重后落到「关系名」量级 = 数百~数千 ⇒ ⇒ **差集口径完全可行**）。
