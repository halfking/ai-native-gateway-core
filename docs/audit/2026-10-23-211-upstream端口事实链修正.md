## 二、根因链：读事实 → 改事实 → 切流 → 停槽

「活跃槽端口」这个事实**只存在于 nginx 里**，引擎整套蓝绿状态机
（判活跃槽 → 选候选槽 → 切 upstream → 停旧槽）全靠它 ⇒ **读错 = 切错**。

而 nginx 的 upstream 块里**经常留着旧端口的注释**（245 实况原文）：

```nginx
upstream llmgo_local_245 {
    # 2026-08-31: Atomic blue-green fragment; deployer replaces this file and reloads nginx.
    # Original hardcoded `server 127.0.0.1:8781;` did not allow nginx -s reload to
    # switch traffic between the active (8781) and the canary (8782) candidate.
    include /opt/llm-gateway-go/run/active-upstream.conf;
    keepalive 32;
}
```

⇒ 引擎的**读**（`dd_upstream_port`）与**写**（`dd_switch_upstream`）都用
**不剥注释**的正则：

1. ★ **读侧**：先命中**注释里那个旧端口** ⇒ 「活跃槽」判错 ⇒ 候选槽选错。
2. ★ **写侧**：**改的是注释**并报 `patched` ⇒ nginx reload 后活的上游**根本没变**
   ⇒ 引擎以为「已切流」⇒ 随后停掉「旧槽」⇒ 流量落空 ⇒ **502**。

⇒ 第三条：**上游端口与槽位是两份事实**（脚本的 `DD_SLOT_*_PORT` + nginx 里的那个），
可以漂移。漂移形态＝同机另一个产品占了网关的端口（211 上 ASM 占了 8782，
而 upstream 仍指向它 ⇒ 网关流量打到别人的服务上）。

★ 形态差异（**为什么只有 211 有这个病**）：
- 154/245（systemd 形态）：nginx 里是 `include run/active-upstream.conf;`
  ⇒ 端口在**部署时生成的文件**里 ⇒ 不存在「端口烤死在 nginx」这个形态。
- 211（docker 形态）：端口**烤死**在 upstream 块里 ⇒ 需要额外机制兜住。

## 三、修法（`52093b157`）

1. **单一真值源** `scripts/ops/nginx-upstream-port.py`
   —— 掩码（注释 + 引号 → 等长空格）后定位 ⇒ 注释里的端口一律不算数；
   认「烤死」与「include 生成文件」两种形态；跳过 backup 行；
   写模式只改**活的上游行**、备份每次写「改前内容」、include 形态 fail-closed。
   引擎的读与写都改调它（引擎里不再留内嵌正则副本）。
2. **绑定闸** `dd_check_slot_binding`：upstream 端口不属于任何配置槽位 ⇒
   **在写任何东西之前**（迁移重放 / 起容器 / 切流 / 停旧槽之前）拒绝部署，
   并把现场事实 + 处置方法一并打出来（不再拿状态文件猜一个槽位去切流）。
3. **只读体检** `scripts/ops/deploy-doctor.sh`（+ `bash scripts/deploy-211.sh --doctor`）：
   打印 upstream 主端口 / 配置槽位 / 该端口被哪个容器占着；
   脱节 ⇒ 退出码 2 + 处置方法；连不上 ⇒ 退出码 3（**不是**「正常」）。

## 五、顺带修掉的一条本机环境坑

★ 本机的 `rm -rf` 被包装成**可恢复删除工具**，而它**往 stdout 打印一行**
⇒ 医生在**命令替换**里做删除 ⇒ 那行提示被当成了「现场事实」
⇒ 「连不上」被误报成「conf 读不到」。
⇒ 修法三件：删除重定向 stdout；用**返回码**判「取不到事实」（不靠「输出为空」）；
门里用替身 ssh 钉住这条（⑩：不可达 ⇒ 退出码 3 且说清「连不上」）。
