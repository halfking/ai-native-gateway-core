# 2026-10-28 输出策略拦截反馈明确化轮（goal 会话）

> 需求原文（用户）：「请常碰到网关输出：ZCode 报错信息 / Response blocked by
> output policy / TraceID: hydrate-trace，便是没有明确的原因，并且检查整个
> 输入没有违规的地方。我们需要将这些信息返馈更明确，并且解决这些误报的
> 问题，或者可以在后台有个开关一次性关掉。或者在后台有个列表，需要审核，
> 审核完成后可以返回给前端。前端的显示是等待审核，有敏感内容。」

## §0 结论一句话

拦截反馈从「一句常量 + 客户端自造标签」升级为**规则名 + 人读原因 + 参数
位置 + 网关请求 ID + 审核单号全部进 message 文本**（按最弱客户端设计），
每次硬阻断自动生成**后台待审单**（批准 ⇒ 服务端精确放行该载荷 ⇒ 用户重试
即拿到内容），硬阻断清单新增**运行时开关**（后台一键开/关，无需重启），
并修掉一处**非托管 OutputBlock 完全绕过硬阻断清单**的真实误报源。

## §1 需求完善（把口语落成可验收的口径）

| # | 用户的话 | 落成的口径 |
|---|---|---|
| R1 | 「反馈更明确」 | 拦截错误的 **message 文本本身**携带规则名、人读原因、参数位置、网关请求 ID；旁键（rule/reason/field/digest/request_id/review）继续保留给能读它们的客户端。判据：只显示 message 的客户端也能知道「被什么拦、去哪查、怎么办」。 |
| R2 | 「解决误报」 | 误报的判据面是 output/egress（**模型生成的工具参数**），不是 input——用户「检查输入没有违规」是符合预期的，因为被拦的根本不是输入。修法分两层：代码层修掉仍存在的结构性误报源（本轮：非托管 OutputBlock 绕清单）；运维层给出可见性与开关（R3/R4），让管理员能对单次误报放行而不是只能关整条规则。 |
| R3 | 「后台有个开关一次性关掉」 | 硬阻断清单的**运行时** GET/PUT 入口（super_admin）：整表替换、立即生效、无需重启；清空（含请求侧底线）必须显式确认。 |
| R4 | 「后台有个列表，需要审核，审核完成后可以返回给前端」 | 每次硬阻断登记一条待审记录（rv-N，含规则/原因/位置/载荷摘要/请求 ID）；管理员批准 ⇒ 服务端写入放行记录（精确绑定载荷摘要）；**用户重试即拿到内容**（流式响应在拦截那刻已终止，无法也不应事后补发——「返回给前端」的实现语义是重试即返回）。 |
| R5 | 「前端的显示是等待审核，有敏感内容」 | message 尾部固定话术：「内容含敏感信息，等待审核（审核单 rv-N）：管理员在网关后台放行后，重试即可获得内容。」——客户端（含 ZCode 这类只显示 message 的）上屏即达意。 |

## §2 原因分析（为什么用户只看到一句话）

四个互相叠加的缺口，全部在 211 生产形态上可复现：

1. **message 是常量串**。`"Response blocked by output policy"` 在所有路径上
   都是同一句话；r1039（2026-10-20）把 rule/reason 放进了错误信封的**旁键**，
   但 ZCode 的报错卡只显示 message——旁键一个字都上不了屏。「TraceID:
   hydrate-trace」是 ZCode 自己的内部标签：网关从未给过它任何可对账的 ID。
2. **三条非流式路径连旁键都没有**（r1039 D3 只补了 chat 路径）：
   `/v1/responses` execErr 分支（responses.go）、`/v1/messages` execErr 分支
   （messages.go）、两者的 native body 拦截分支（`interceptNativeResponseBody`
   把 InterceptResult 连同 Metadata 一起丢弃，只返回一个 blocked 布尔）。
3. **流式终帧没有 request_id**。nativeStreamPolicyFailureFrame 只有
   rule/reason——用户拿不到网关侧的请求 ID，后台日志对不上号。
4. **误报面本身**：硬阻断清单（`LLM_GATEWAY_HARD_BLOCK_RULES`）是 env 配置、
   进程内生效，管理面**看不到也改不了**；被拦记录（sanitize_rule_events）
   只有结构指纹，没有载荷摘要与请求 ID——管理员看到「有拦截」也无法把
   它变成一次放行。
5. **结构性误报源（本轮代码修复）**：`outputSensitiveChecker.Check()` 的
   `block := action == OutputBlock && !managed()` **完全绕过硬阻断清单**——
   部署设 `LLM_GATEWAY_SANITIZE_OUTPUT_ACTION=block` 且规则管理器不可用
   （fallback 检测器）时，正文里出现**任何一个**敏感片段（一个 email 就够）
   就整条响应 output_policy_blocked。r1037「默认不硬阻断」的 owner 裁决在
   这条路上从未生效（托管路径的 ErrRuleBlocked 早就过清单，见 detector.go
   的 HardBlockAllowed 判定；非托管文本 lane 是唯一的漏网分支）。

## §3 方案与实现

### 3.1 反馈明确化（R1/R5）

- `domains/streaming/policy_block_feedback.go`（新）：
  - `policyBlockClientMessage(rule, reason, field, requestID, reviewID)` 组装
    message：稳定前缀（既有子串匹配不破）→ `(rule=…)` → `: 原因` →
    ` at $.路径` → ` request=<id>.` → 中文行动指引（等待审核 rv-N /
    联系管理员兜底）。
  - `registerPolicyBlockReview(...)` 登记审核单并返回 rv-N。
  - `policyBlockErrorExtras(...)` 组装旁键（空值不出现）。
- 六个拦截落点全部接线：
  - 流式：`interceptingStreamWriter.finish()` 终帧（`nativeStreamPolicyFailureFrame`
    新签名带 requestID/reviewID/field，帧内新增 `request_id`/`review`/`field` 键）。
  - chat 非流式 ×2（handler.go 4966/5947 现场）、`/v1/responses` 非流式 ×2、
    `/v1/messages` 非流式 ×2。
  - `writeResponsesError` / `writeAnthropicError` 增加 extras 变参（非拦截
    调用点形状不变）。

### 3.2 审核队列（R4）

- `domains/sanitizerules/review_queue.go`（新）：进程内队列（与放行表同一层），
  环形上限 1000；登记去重（同键 pending 复用同一单）；`DecideBlockReview`
  批准时同步 `AddEgressRelease`（**精确绑定载荷摘要**；无摘要时退化为该
  租户该规则的整条放行）。
- **载荷摘要贯通**（这是「批准后重试即放行」的钥匙）：
  `ComplianceIssue.Digest`（新字段）← `setToolIssueRule` 在拦截那一刻计算
  `EgressPayloadDigest(ruleID, path, value)`（与 `egressReleaseAllowed` 的
  放行判定**逐字节同键**）→ `PolicyBlockError{Path, Digest}`（新字段）→
  chunk metadata（`policy_field`/`policy_digest`）→ 非流式 InterceptResult
  metadata → 六个落点。
- 安全边界：记录里**没有载荷原文**（sha256 不可逆摘要 + 结构信息）；
  放行决定只在服务端进程内，客户端自带头/参数影响不了（与 hop-header
  教训同线）；批准不绕过其它规则——同载荷命中多条规则时逐条放行（判据
  `TestR1041ToolBlockDigestMatchesReleaseKey` 的收敛循环钉住这个语义）。

### 3.3 运行时开关（R3）

- `admin/sanitize_rules_hardblock.go`（新）：
  - `GET /api/admin/sanitize-rules/hardblock`：当前生效清单。
  - `PUT`：整表替换（ParseHardBlockAllows 逐条校验，egress 只接受逐条内建
    规则的 r1039 限制在解析层继续生效）；空清单必须带
    `confirm_disable_all=true`（等价 env 语法 "-"，防止误点关掉请求侧底线）。
  - 变更进结构化日志（进程内清单没有版本表，日志是它的变更史）。
  - 重启后回落 env 装载的清单（响应 note 与 UI 均写明）。

### 3.4 误报源修复（R2 代码层）

## §6 明确没做 / 如实记

1. **审核队列与放行表的持久化**：与 egress 放行表同一层——进程内、重启
   即清空（两处 UI 与 API 响应均写明）。跨重启持久化需要新表 + 启动迁移
   （迁移号要与并行会话协调），留下一轮。
2. **「审核完成后推送原文给前端」**：不做——流式响应在拦截那刻已终止，
   事后补发陈旧的模型输出既做不到（连接已关）也不该做（内容可能已被
   判定敏感）。契约是**重试即返回**（R4）。
3. **output 侧文本 lane 的按载荷放行**：放行机制只有 egress scope（r1039
   契约）；output 侧文本拦截的审核批准只标记「已人工看过」，治理通道是
   硬阻断清单。列表 UI 已按此语义展示。
4. **后端下发文案**（writeError 1852 处英文）与移动端 8 语言：不在本轮。
5. **211 部署**：本轮改动未部署到 211（部署需按 deploy-211 钉根纪律单独执行）。

## §7 本轮的教训（详见 LESSONS.md §513；原拟 §512，推送前与上游 r1039 三轮撞号让位）

1. **旁键不是反馈**——只显示 message 的客户端让 r1039 的「带规则名」在
   用户侧等于没做；按最弱客户端设计，信息必须进 message 文本本身。
2. **一条载荷可命中多条规则，批准是收敛的链条不是一次点击**——审核流按
   「批一条、重试、暴露下一条、再批」收敛，判据用循环钉住。
3. **拦截那一刻要记下「放行的钥匙」**——摘要的键（ruleID+path+value）必须
   与放行判定逐字节一致，错一位就是「批了也不放行」。
4. **进程内开关是运维面不是安全面**——它解决的是「误报时一分钟止血」，
   安全边界仍在服务端持有清单与放行表。
