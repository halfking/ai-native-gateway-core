## 1. 为什么是这一轮

### 1.1 病：四个「主动作」＝ 没有主动作

规范原文：

- impeccable `skill/reference/distill.md`：
  「**Clear hierarchy: ONE primary action, few secondary actions, everything else tertiary or hidden**」
  「**Clear next action: ONE obvious next action, not five competing ones**」
- impeccable `skill/reference/colorize.md`：
  「**Keep the primary action easy to find; do not spend its color on decoration.**」
  「**Let the strongest color own a deliberate region or role instead of scattering tiny accents.**」
- impeccable `skill/reference/operate.md`：
  「Accent color used for primary actions, current selection, and state indicators only, not decoration.」
- 仓内 `DESIGN.md` §视觉世界：「状态用最小的颜色量表达、**每个元素都承担信息职责**」

第 20 增量治的是「**主色被重复消费到每一行**」（实心主色不得落在数据行内，§458）。
本轮治的是**另一个形态**：**同一排动作里并排多个实心主色**。

真仓两处（浏览器截图取证，§7）：

| 位置 | 现状 | 用户看到的 |
|---|---|---|
| `views/FreePoolView.vue` 页头工具栏 | **四个**并排实心主色：快速录入 / 写入 DB 凭据 / 添加 Provider / 多 Key 批量池化 | 四个等重的「主动作」⇒ **等于没有主动作** |
| `views/ProxyView.vue`「状态概览」动作区 | **两个**并排实心主色：批量探活全部节点 / 强制切流到最优节点 | 两个「主动作」⇒ 同上 |

★ 第二处特别值得记：**同一个文件的另外三个动作区**（订阅管理 / 节点管理 / 选择策略）
本来就都是「**一个主色 + 其余次级**」⇒ 状态概览这处是**该文件内部的不一致**，不是设计意图。

⇒ 修法有**同文件先例**可循，不必凭口味。

### 1.2 选主题时排除的两条路（不要重试）

| 候选 | 排除理由（实测） |
|---|---|
| **祖先口径**（动作区 = 最近的含 ≥2 个实心主色后代的祖先） | 命中 **32 个区 / 107 个按钮**，但绝大多数是**整页容器**（`.users-page` / `.work-types-view` / `.cred-models` …）⇒ 「一页多区、每区各有自己的主动作」是**合法的**（`colorize.md`：「the strongest color own a **deliberate region** or role」）⇒ 假阳性爆炸 |
| **类名口径**（动作区 = 最近的 class 含 `toolbar`/`actions` 的祖先） | 只命中 **1 处** —— 因为 `FreePoolView` 的工具栏 div **根本没有类名** ⇒ ★★ **靠类名找动作区 ⇒ 改个类名门就瞎了** |

## 2. 判据（唯一实现：`web/src/design/primaryClarity.ts`）

### 2.1 一条判据

> **一个「动作区」里，最多一个实心主色。**
> —— 主色是**稀缺资源**；两个并排的实心主色 = 两个「主动作」⇒ 焦点被稀释回「每行都一样」。

★ 判据只有**一条**（判据越少越可证伪）。

### 2.2 「动作区」的口径 = **直接父容器**

这是本轮**最贵的一个决定**，用**三套候选实测对拍**定下来（数据见 `§1.2` 与 `§6.1`）：

| 候选口径 | 命中 | 为什么不用 |
|---|---|---|
| ① 祖先口径 | 32 区 / 107 按钮 | 假阳性爆炸（整页容器） |
| ② 类名口径 | 1 处 | **漏**（工具栏 div 无类名） |
| ③ 含控件祖先口径 | 3 处 | 第三处 `components/RequestTracePanel.vue` 是**假阳性**（「生成提示词」在 `.ai-actions`、「复制」在 `.ai-result-header` ⇒ 分属**不同子区域**，且后者只有出结果后才出现） |
| ★ **④ 直接父容器** | **2 处 / 6 按钮** | ✅ 既是最严格的「一排并排按钮」定义，又**不依赖类名** |

⇒ ★ **改类名不会让门失明** —— 这是选它而不是选 ② 的根本理由。

### 2.3 排除（复用第 20 增量，不新增）

- **焦点区域**（模态 / 抽屉）内 —— 那里主色属于「这个浮层的主动作」；
- **数据行**内 —— 第 20 增量已治（`primaryFocus.ts` 的行容器形态）。

★ **「刻意区域」天然满足**：卡片自己的主色按钮独自占据一个动作区 ⇒ ≤1 ⇒ 不判。

★ **复用** `primaryFocus.ts` 的实心主色判定（`isSolidPrimary` / `inFocusRegion` / `rowContainerForm`）
—— ★ **同一口径只能有一份实现**（§411）。

## 4. 运行时尺（第二把尺）

`web/scripts/design-primary-clarity-runtime-check.mjs`

- 口径：**同一个直接父容器下**出现 ≥2 个「主色控件」⇒ 竞争组。
- ★★★ **认颜色不认类名**：取根元素上 `--accent` / `--kx-primary` / `--el-color-primary` 的**计算值**当主色集合，
  再比按钮的**计算后背景色** ⇒ ★ Element Plus 的 `type="primary"` 渲染成的是 `--el-color-primary`

| 层 | 判据 |

| 源码（声明位） | 这条模板声明把按钮声明成了**实心主色**，而它的**直接父**里还有另一个实心主色 |

⇒ 两层都指向同一个病，但不是同一个判据。

## 6. ★ 本轮抓到的真缺陷（都是本轮自伤，非既有代码）

### 6.1 ★★★ 普查脚本自己静默失效 ⇒ 「零命中」是假的

普查脚本 v1 用了 `SolidPrimaryButton.openStart`，而**那个字段在接口里根本不存在**
⇒ `byStart.get(undefined)` ⇒ 每个按钮都返回 null ⇒ **输出「零命中」**
⇒ ★ **「量具挂起」被写成了「读到 0」**（§450 形态八的老坑，第 N 次复现）。

★ 修法：普查里**不反查**已有结果的字段，而是**直接在标签树上判**（复用 `isSolidPrimary(node)`）
⇒ 节点身份天然可靠。

★ v2 改用 snippet 反查也踩了坑：只比对 attrs 的**前 40 个字符**
⇒ 4 个结构相同的按钮**全部匹配到同一个节点** ⇒ `isPrimaryNode.size = 2`（实际应为 9）
⇒ ★★ **「模糊匹配」产出的集合大小会骗人** ⇒ 第三版改为**在树上直接判**，一次解决。

### 6.2 ★★★ 变异臂的【注入量】必须与判据阈值匹配

首版臂 B 往工具栏注入**一个**实心主色，而判据是「**≥2** 个并排」
⇒ 门**不**判红是**对的** ⇒ 臂失败。

★ **臂没通过时，先问注入量与阈值，再问门**（§419「三臂全绿时先问靶点」的同族第三式）
⇒ 重做为注入**两个**后即通过。

### 6.3 ★★ 排除分支必须用读数证明是【活分支】

两条阴性臂顺带给出的读数：

| 排除分支 | 注入后读数变化 | 结论 |
|---|---|---|
| 焦点区域 | 焦点区域 29 → **31** | 不是「什么都没扫到」，是**真的排除了** |
| 数据行 | 数据行内 5 → **7** | 同上 |

★ 若读数不变 ⇒ 那条排除分支是**死的**（形同虚设）⇒ 门会误判红。
