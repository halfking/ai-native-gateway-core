# R72g · 护栏退役 —— discovery 的 stale 下架判据换源（2026-10-21）

> 属主裁决：**Q4 = 退役该护栏**（它已无判据，继续留着只会静默跳过）。
> 本档记录：护栏为什么必须退役、退役的**正确形态**是什么、以及退役的**影响面实测**。
> **本轮对生产的写入 = 0**（Phase1 全部在仓内）。

---

## 0. 一句话结论

**退役 ≠ 删网。** 这道护栏要防的是「否定式守卫在证据源停写时把在用模型全量下架」
——那个危险**依然存在**（会话族也会停写，例：R62 修过的 23514）。⇒ 正确形态是
**换源**：判据从「v1 能否写」改成「**会话族证据源近期有没有成功行**」。

---

## 1. 护栏为什么必须退役

### 1.1 现状：它已经恒不成立

- 判据：`staleExpiryMayRun(settings.RequestLogsWriteEnabled())`
- 源：v1 `_request_logs`（**已随 890 物理删除**）
- ⇒ 判据**恒为 false** ⇒ 护栏**恒 skip** ⇒ **陈旧模型永不再自动下架**。

**211 生产日志实证**（本轮只读）：

```
discovery: skip stale-model expiry
  reason="S4 停写中：宽限守卫依赖 v1 证据源（_request_logs，已随 890 退役），证据源停止写入
          ⇒ 下架判定不成立；⚠ 该护栏判据现已失效（证据源已是会话族，一直在写），待父会话裁决是否退役它"
```

### 1.2 ★ 订正一个易被误读的事实：护栏是**全局**恒 skip，不只 211

`settings.RequestLogsWriteEnabled()` 的 fallback 是 **false**
（`settings/key_request_logs_write_enabled.go:43-45`），而 252 共享库的
`settings_kv` 里**没有** `request_logs.write_enabled` 行 ⇒ fallback false
⇒ **154/245 上的这道护栏同样恒 skip**。

⇒ 「v1 写侧已停」这件事在**所有连着已退役 v1 的实例上**都成立 ⇒ 护栏在全局恒 skip。

## 2. ★ 退役的正确形态：换源，不删网

### 2.1 为什么不能简单删掉判断

这道守卫是**否定式**的：

```sql
AND NOT EXISTS (SELECT 1 FROM <证据源> WHERE … success = TRUE AND ts > 近 N 小时)
```

否定式守卫的危险在于：**证据源停止写入时**，子查询不是「查不到」，而是
**结构性恒空** ⇒ 守卫从「已验证：近期无成功」退化成「根本没有证据」，
而代码**照常执行下架** ⇒ 无论模型是否真在用，都被判 `auto_discovery_expired`。
这**不是降级，是主动禁用仍在工作的凭据模型**，且写成功就是成功，**无任何异常信号**。

⇒ 会话族**也会**停止写入。**实测反例就在本仓的历史里**：R62 修过的
`no partition of relation "session_turns" found for row`（新装库缺当月分区
⇒ 写路径直接失败）⇒ 那段时间会话族是**死的** ⇒ 那一刻否定式守卫同样恒空
⇒ 在用模型会被全量下架。

⇒ **删掉判断 = 把安全网一起删了。**

### 2.2 新判据：直接问要问的那个问题

| | 旧判据 | 新判据 |
|---|---|---|
| 问法 | 「**另一个**源（v1）能否写？」 | 「**证据源本身**近期有没有成功行？」 |
| 形态 | 代理指标（proxy） | **实测事实** |
| 现状 | 恒 false（v1 已退役） | 有判据（会话族一直在写） |
| 证据缺失时 | —— | 仍阻断（安全方向） |

⇒ ★ **通用式：「问 A 是否可写来推断 B 是否有数据」是判据问错的标准形态。**
代理指标在 A 退役后就变成恒值，而**它守护的那个风险一点没消失**。

### 2.3 实现要点

- 新增 `(*Service).sessionFamilyHasRecentSuccess(ctx)`：
  `EXISTS` 查会话族 **hot ∪ parent** 两臂的 `success = TRUE` 行。
  - **两臂都要查**：只看 hot 会在 hot 轮转/清空后把「无证据」误判出来 ⇒ 恒 skip。
  - 查询失败 ⇒ 按「证据缺失时不动」处理（`slog.Warn` 留痕）。
- 新增 `(*Service).staleExpiryGraceHours()`：**窗口的唯一实现点**。
  探针窗口与守卫窗口必须同源，否则会出现「探针说有证据（48h 窗口里看到了行）、
  而守卫自己在 24h 窗口里看不到任何行」⇒ 否定式守卫退化成「没有证据」。
- `discovery.go` 的 `settings` import 随之移除 ⇒ **编译期**就是「判据已换源」的证明。

## 3. ★ 影响面实测（退役会下架多少）

### 3.1 252 共享库（154/245 用）

单事务**可重复读快照**（`BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`）：

| 口径 | 行数 |
|---|---|
| `model_offers` 总行 | 1951 |
| `available = TRUE` | 1855 |
| 其中 `admin_protected` | 4 |
| ⇒ **候选（available 且未保护）** | **1851** |
| 其中 24h 内有成功会话（宽限挡住） | 25 |
| ⇒ 粗算 would_expire | 1826 |

**★ 量具自相矛盾的排查**（仓内纪律：分桶之和必须 == 输入条数）：
第一轮量到「would_expire 1809」而「候选 1746」⇒ 子集不可能更大
⇒ 定位为**两次不同快照**（表在被写）⇒ 改用单事务快照后算术自洽
（1855 − 4 = 1851 = 1826 + 25 ✅）。

**收紧口径**（上表是**上界**，未建模「本轮 discovery 仍返回该模型」）：

| 收紧口径 | 行数 |
|---|---|
| `last_seen_at` 早于 24h（⇒ provider 很可能已不再提供）∧ 无 24h 成功会话 | **1109** |
| 同上 ∧ **有** 24h 成功会话（会被宽限挡住） | 1 |

⇒ ⇒ **真候选 ≈ 1109 行**，且这 1109 行**本来就该下架**（provider 已不再提供
＋ 24h 内无人使用）⇒ 与 stale expiry 的**设计本意一致**。

### 3.2 211 库（独立实例）

| 口径 | 行数 |
|---|---|
| available ∧ 未保护 | 1904 |
| would_expire | 1893 |
| 宽限挡住 | 11 |

### 3.3 证据源活性（判据会不会放行）

| 库 | `session_turns_hot` 24h 成功 | `session_turns` 24h 成功 | 7d |
|---|---|---|---|
| 211 | 47 | 830 | 7957 |
| 252 共享库 | 319 | 1470 | 24324 |

⇒ ★ 判据**会放行**（证据源是活的）⇒ 退役后 stale 下架**真的会开始执行**。
⇒ 这是属主 Q4 明确批准的语义（「陈旧模型不再被自动下架」→ 恢复自动下架）。

### 3.4 ★ 未量化的边界（诚实声明）

- **`last_seen_at` 是代理量**：它近似「provider 是否还在提供该模型」，
  但真正的 `seen` 集合来自**本轮 discovery 的 `/v1/models` 响应**
  （`expireStaleModels` 的 `raw_model_name NOT IN (seen)`）。
  ⇒ 真实下架量 = **上表 1109 与本轮 seen 集合的差** ⇒ 只能实跑才知道。
- **可逆性**：下架只写 `available = FALSE` + `unavailable_reason='auto_discovery_expired'`
  ⇒ **可逆**（改回 TRUE），不是不可逆销毁。
  ⇒ ⇒ 建议：升级后**盯 `expired stale models` 的 count 日志**，
  数量异常时立即回滚 `available`。

### 4.4 ★★ 本轮挖出的三个**量具缺陷**（量具坏了 ≠ 被测坏了）

1. **`-run` 过滤器漏检**：`go test -run 'StaleExpiry'` **匹配不到**
   `TestExpireStaleModelsConsultsTheGate`（名字里没有 "StaleExpiry" 子串）
   ⇒ 那道断言**根本没被执行** ⇒ M2 看起来"没牙"。
   ⇒ **教训：变异验证必须全包跑，或用精确的测试名列表。**
2. **`callsName` 只认 `*ast.Ident`** ⇒ `s.staleExpiryGraceHours()` 这种
   **方法调用**（SelectorExpr）被判成「没调用」⇒ 断言恒红。
3. **文本计数把注释算进去**：`DISCOVERY_GRACE_HOURS` 在注释里出现 2 次 +
   代码 1 次 ⇒ 「必须恰好 1 次」恒红。
   ⇒ 改用 AST **只数 `os.Getenv` 的字符串字面量实参**。
4. （附带）`public.session_turns` 是 `public.session_turns_hot` 的**前缀**
   ⇒ 朴素子串匹配产生假阳性 ⇒ 改用**标识符边界**判定。

### 4.5 顺手清掉的既有债（stash A/B 基线确认）

`admin/request_logs_control_plane_gated_flag_test.go` 的
`TestGatedFlagExemptionIsNotStale` **在干净 HEAD 上就红**（stash A/B 实测）：

```
gatedFlagExemption 里有 2 条已失效的豁免：
  domains/hooks/observability/telemetry/client.go（不在控制面登记表里）
  internal/trace/trace.go（不在控制面登记表里）
```

⇒ 根因：**890 轮清空了控制面登记表**（v1 族物理删除 ⇒ 不存在 v1 控制面）
⇒ 豁免表是它的**子集** ⇒ 父表为空 ⇒ 豁免表必须为空。
⇒ 处置：豁免表清空；那 2 条的**原始措辞**降级为
`retiredGatedFlagExemptionsKeptForHistory`（**不参与任何判定**的文档表），
并加断言「历史表与豁免表不得重叠」。
