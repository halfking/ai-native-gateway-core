## 一、根因坐实

### 1.1 用户诉求（原文）

> 我们需要核实费用的情况，做到统一标准，不要现现重复计费的情况，统计的费用应该与每条请求的费用总和一致，分有探测和无探测请求两种情况。

### 1.2 D2 量级（生产实测，2026-11-23）

同 7 天窗口同谓词：

| 指标 | session_summaries JOIN sessions（改前） | 去重后 | 差异 |
|------|--------------------------------------|--------|------|
| 费用 | $2,721.09 | $1,692.78 | **+60.7%** |
| 请求数 | 72,815 | 53,702 | **+35.6%** |
| 会话数 | 19,341 | 19,314 | +0.14% |

**样本验证**：`gw_5992d833…` 在 `sessions` 有 11-16/17/18 三行（不同 `partition_date`），而 `session_summaries` 仅一行（1888 请求 / $394.66）⇒ 被计 3 次。

### 1.3 根因

`domains/analytics/session_probe_scope.go` 的 `SessionUniverseJoin` 直接 `JOIN sessions s ON s.session_id = ss.session_key`，而 `sessions` 是**按天分区的会话历史表**（同一会话每天续一行）⇒ **一对多 JOIN 必然放大**。

```sql
-- 改前（会一对多放大）
FROM session_summaries ss
JOIN sessions s ON s.session_id = ss.session_key AND s.tenant_id = ss.tenant_id
```

**为什么不能直接用 `session_summaries` 判定探测**：`session_summaries` 缺探测判定所需字段（只有 `title`，没有 `is_probe`/`owner_user`/`client_type`/`api_key_owner_user`）。

## 二、修法

### 2.1 代码改动

**① `domains/analytics/session_probe_scope.go`**  
改 `SessionUniverseJoin` 为先对 `sessions` 去重再 JOIN：

```go
func SessionUniverseJoin(ssAlias, sAlias, sdAlias string) string {
	return fmt.Sprintf(
		"JOIN (\n"+
			"  SELECT DISTINCT ON (session_id, tenant_id)\n"+
			"    session_id, tenant_id, is_probe, owner_user, client_type, title\n"+
			"  FROM sessions\n"+
			"  ORDER BY session_id, tenant_id, partition_date DESC\n"+
			") %[1]s ON %[1]s.session_id = %[2]s.session_key AND %[1]s.tenant_id = %[2]s.tenant_id\n"+
			"LEFT JOIN session_dim %[3]s ON %[3]s.session_key = %[2]s.session_key AND %[3]s.tenant_id = %[2]s.tenant_id",
		sAlias, ssAlias, sdAlias)
}
```

- `DISTINCT ON (session_id, tenant_id)` 按会话去重
- `ORDER BY partition_date DESC` 取**最新分区行**（＝当前状态，而非首日历史状态）
- 子查询只选出探测判定所需 6 列，避免全表投影

**② `sql/migrations/startup/994_session_analytics_owner_key_and_close_path.sql`**  
三个物化视图（`user_session_aggregates` / `project_task_aggregates` / `model_session_aggregates`）的 `JOIN sessions` 改为同样的去重子查询（`replace_all=true` 一次改完 3 处）。

**③ 新增契约门**  
`domains/analytics/session_universe_dedup_test.go`（验证去重子查询 SQL 形态）+ 更新 `session_probe_scope_contract_test.go` 的期望值（994 迁移 SQL 与 Go 侧必须逐字同构）。

### 2.2 为什么不新开迁移号

- 物化视图定义在 `startup/994_*.sql`（启动时重建）
- 仓内三位迁移号规范（`migrationNumPrefix = ^[0-9]{3}_`），999 已最大，`1000_` 会落在门之外
- 本轮只改**查询定义**不改 schema，下次服务启动时自动重建 MV 即生效

### 4.3 真库对拍结果（211 生产实测，2026-11-23）

同一会话宇宙（去重后）+ 同一窗口（会话首请求落 7 天窗）+ 同一探测判定下，
**会话侧（session_summaries 聚合）与请求侧（request_logs 逐条）逐项相等**：

| 口径 | 侧 | 会话数 | 请求数 | 费用 |
|---|---|---|---|---|
| 非探测（owner 非空 + `NOT is_probe` + `NOT session_analytics_is_probe`） | 会话侧 | 19,468 | 55,481 | $1,708.83 |
| 非探测 | 请求侧 | 19,468 | 55,481 | $1,708.83 |
| 探测（`is_probe` 或三维模式命中） | 会话侧 | 15,637 | 17,671 | $6,795.29 |
| 探测 | 请求侧 | 15,637 | 17,671 | $6,795.29 |

⇒ **两种口径都逐项相等**（会话数 / 请求数 / 费用三项全部一致）。

**逐会话复核（FULL JOIN 两边）**：0 行差异 ⇒ 不是「总数凑巧相等」，是**每个会话**
的请求数与费用都相等（口径实现正确，不是统计误差）。

**为什么两次总额偶尔差 $0.01**：`session_summaries.total_cost_usd` 是
**numeric(12,6)**（会话侧逐请求 upsert 累加，每次落库舍入到 6 位小数），
`request_logs_with_current_month.cost_usd` 是 **numeric(14,8)**（原始 8 位小数求和）
⇒ 每会话最多 ~1e-6 的舍入残差，× 约 1.9 万会话 ⇒ 累计到 $0.01 量级。
**这是存储精度残差，不是口径差异**（请求数与会话数完全相等、逐会话 0 行差异已证明口径一致）。

**「含探测」口径的真源数**（同一会话宇宙、同一窗口）：

| 口径 | 会话数 | 请求数 | 费用 |
|---|---|---|---|
| 排除探测（owner 非空 + 非探测）＝页面默认 | 19,426 | 55,563 | $1,711.39 |
| 含探测（旧 FROM 形状，不做 owner/探测过滤） | 36,140 | 74,476 | $8,522.51 |
| 探测会话单独（不加 owner 约束） | 15,637 | 17,671 | $6,795.29 |

⚠️ 三行**不能直接相加**：排除探测口径要求 owner 非空，探测口径与含探测口径不含
该约束 ⇒ 差额里含「owner 为空」的会话（1,076 会话 / 1,241 请求 / $15.83）。

放大量级（同一查询、去重前后）：费用 $2,737.02 → $1,708.71（−37.6%），
请求 74,584 → 55,471（−25.6%）。放大来源：`sessions` 是按天分区的会话历史表，
同一会话多天各有一行 ⇒ 一对多 JOIN 把那些会话的费用/请求数重复计入了 N 次。

**性能代价**（同窗口同一 SQL 实测）：去重版 807ms vs 原 JOIN 418ms（约 2×）。
根因是 `DISTINCT ON` 要全表扫 + 排序（211 上 sessions 263,034 行、26MB 外部排序）。
实测对比过三种写法，结论是**保持现状**：
- `DISTINCT ON (session_id, tenant_id)`：676ms（子查询单独测）
- `DISTINCT ON (tenant_id, session_id)`（键序对齐既有索引 `(tenant_id, session_id, partition_date DESC)`）：678ms（planner 仍不选索引）
- 强制索引路径（`enable_seqscan=off`）：1005ms（更慢）
- `JOIN LATERAL (... ORDER BY partition_date DESC LIMIT 1)`：848ms（数值等价，形态不变）

⇒ planner 的选择是对的，**不建索引**（建了也不会被选中，且多一个 schema 变更面）。

## 七、部署踩坑补记（2026-11-23，两次 FATAL）

修复逻辑本身在真库对拍上是对的，但**落地 211 时连续两次 FATAL**，两次都不是代码逻辑错，
而是「迁移形状」与「生产环境约束」的碰撞。两次都留下了可复用的教训。

### 7.1 第一次：去重子查询漏列 ⇒ 视图建不出来

**现象**：`psql:<stdin>:205: ERROR: column s.agent_name does not exist` ⇒ 迁移 FATAL。

**根因**：D2 把 `JOIN sessions s`（表）换成 `JOIN (SELECT DISTINCT ON … <列清单> FROM sessions) s`
（**投影**）。投影只选了 6 列，而 `agent_usage_aggregates` 视图体引用 `s.agent_name`
⇒ 建视图那一刻直接 42P03。

**★ 最值得记的是量具盲区**：既有契约门 `TestSessionUniverseJoinMatches994`
只对拍「Go 侧产物 == 迁移 SQL 里的规范片段」——**两边同样漏一列时依然全绿**。
对拍守卫只能防「两边不一致」，防不住「两边一致地漏」。
⇒ 补了一道**从消费面反推生产面**的闭合守卫
（`domains/analytics/session_universe_column_closure_test.go`）：
抽出每段 SQL 里所有 `s.<col>` 引用，断言全部落在该段去重子查询的 SELECT 列表里。
含量具自证（故意漏列必须判红）。**变异自证已复验**：删掉 `agent_name` ⇒ 精确报红并指名缺列。

**修法**：994 的 agent 视图子查询补 `agent_name`（另两处视图不引用它，保持 6 列），
Go 侧不加（Go 侧不需要 agent 维度，加了会给非 211 实例引入新列依赖）。

### 7.2 第二次：大聚合视图重建撞 `/dev/shm` 上限 ⇒ 视图被 DROP 后缺失

**现象**：`ERROR: could not resize shared memory segment "PostgreSQL.1600769404" to 8388608
bytes: No space left on device`（SQLSTATE 53100）⇒ 迁移 FATAL。

**根因**：994 Part 3 重建 `model_usage_aggregates`（对 `request_logs_with_current_month`
的大聚合）⇒ PG 选并行计划 ⇒ 并行 worker 要 resize DSM 共享内存段（8MB/worker）。
211 的 PG 容器 `/dev/shm` 只有 64MB，常态水位 35~43MB（滞留 DSM 孤儿段）
⇒ 一 resize 就炸。这正是 request-logs 轮登记为 L1 的地雷，**本轮在迁移侧首次撞上**。

**★ 致命之处不在失败本身，而在失败位置**：本迁移是 `DROP` + `CREATE`，
**DROP 已执行、CREATE 失败** ⇒ 生产上 `model_usage_aggregates` 视图**缺失**
（请求级读面挂），且迁移未登记 ⇒ 每次启动重放 ⇒ 反复踩。

**修法**（`d587edc47`）：994 的 SET 段补
`SET max_parallel_workers_per_gather = 0;`（会话级，与同文件既有 `lock_timeout` /
`statement_timeout` 同族；docker 通道是非事务流式 psql，`SET LOCAL` 会静默失效）
⇒ 大聚合重建走串行计划，不再申请 DSM 段（视图是预聚合、不在请求路径上，串行代价可接受）。
配套门禁 `sql/migrations/startup/migration_994_parallel_guard_test.go`：
① 关并行 SET 必须存在且必须是会话级；② 该 SET 必须落在模型视图重建之前。
**变异自证已复验**：删掉 SET ⇒ 两条门禁精确报红。

**★ 已发生的生产影响与补救**：失败部署已把 `model_usage_aggregates` DROP 掉，
且迁移的 Part 4（16 个索引）整段没跑到 ⇒ 三个已建视图也都没索引。
已用修好的 994 文件在生产库直接重跑一次（关并行）补救：
四视图重建成功（110 / 124 / 176 / 928 行）+ 16 个索引建齐 + 台账自登记完成。

### 7.3 两条通用式

1. **「把表换成投影」是一次静默的接口变更**：JOIN 的目标从表变成子查询后，
   下游引用的任何列都必须**显式**出现在投影里；漏一列不是「少一个字段」，
   而是**建视图/跑查询那一刻整条语句失败**。⇒ 用**消费面反推生产面**的闭合守卫，
   不要用「两边对拍」代替。
2. **DROP + CREATE 的迁移，失败点在 CREATE 就等于「把旧结构删了还没建回来」**：
   生产上留下的是**缺视图**状态，比迁移整体失败更隐蔽（迁移报 FATAL 会让人以为「没生效」，
   实际是「生效了一半，而且坏的那一半正好是读面」）。
   ⇒ 迁移里的重建语句要么先建后切（shadow table + 原子 RENAME），
   要么像本轮一样把「可能失败的大语句」显式护住（关并行 / 抬 statement_timeout）。

## 八、「L7 修复轮」（2026-11-23）：「包含探测」开关不生效 ⇒ 根因全在前端两处（提交 `25e5d3c26`，211 现役 seq 3234）

### 8.1 结论先行：后端一直是对的，断点全在前端

L8 登记的现象是「勾选并手动刷新后，页面仍是排除探测口径的数字」。本轮**先证伪「后端没读
`include_probes`」这个假设，再动代码**——否则会去改一段没坏的逻辑。

**后端链路逐段验通（本轮未改任何一行后端逻辑）**：

| 环节 | 位置 | 读数 |
|---|---|---|
| 参数解析 | `admin/dashboardapi/session_overview_alignment.go:95` `parseSessionWindow` | 接受 `1/true/on/yes` ⇒ 取值正确 |

| 口径分流 | `admin/dashboardapi/session_overview.go:439` `querySessionSummaryAggregates` | `includeProbes=true ⇒ withUniverse=false`（走旧全量宇宙）；`false ⇒` 子查询绑小 + `universeJoin` + `universeWhere` |

⇒ **两个断点都在前端**：

### 8.7 通用式（本轮三条）

1. **「参数生效了吗」的排查顺序：先证伪「后端没读」，再动代码。**
   本轮后端链路逐段验通后才动前端 ⇒ 避免去改一段没坏的逻辑。
   ★ 反面代价：若直接改后端，会把一段**语义正确**的口径逻辑改成另一个口径 ⇒ 「修了开关反而改错数」。
2. **「开关不生效」有两类断点：「没发出去」与「发了没接住」，而用户看到的症状完全一样。**
   本轮两个都在前端（watch 不重载 + 页头刷新不刷面板）⇒ 用户点刷新也没用 ⇒ 被误判成后端忽略参数。
   ⇒ 排查时**先看网络面板有没有发请求**，比逐行读代码更快定位。
3. **「结论是『某处一直是对的』」也要有门。**
   本轮「后端一直对」是读出来的，不是门出来的 ⇒ 若哪天 `parseSessionWindow` 取值集被改窄，
   没有任何门会红 ⇒ 补行为门（3 条）+ 前端契约门（5 条）。
