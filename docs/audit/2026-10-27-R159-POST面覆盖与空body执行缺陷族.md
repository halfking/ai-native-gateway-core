## §3 ★★★★ 机理链闭合：空 body 的遥测上报 ⇒ 写出业务表

★ ★★ **最值得单独记的一条**：`/api/telemetry/request-log`。

```go
// admin/telemetry.go:651
func (h *Handler) handleTelemetryRequestLog(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPost { …405… }
	var entry requestLogInput
	if err := readJSON(r, &entry); err != nil {   // ★★ 只校验【JSON 能否解析】
		writeError(w, http.StatusBadRequest, "invalid body")
		return
	}
	if ingester != nil {
		select {
		case ingester.queue <- &entry:            // ★★★ 空 body ⇒ 一个【全零 entry】入队
		default: …
		}
	}
	writeJSON(w, http.StatusOK, map[string]string{"status": "queued"})
}
```

★ ★★★ **⇒ 机理链（每一环都已实测/读码确认）**：

```
POST {} ⇒ readJSON 成功（★ JSON 语法合法 ⇒ 【不是】语义校验）
       ⇒ 一个全零 requestLog 入队
       ⇒ 消费端落库
       ⇒ 钩子 sessionv2mirror.PersistHook（★ cmd/gateway/main.go:2889）
       ⇒ 写 session_turns + session_dim + session_summaries
```

★ ★★ 实测证据：★ 探测之后 `session_summaries` 出现 `session_key = 'gw_<uuid>'` 的新行（★ `gw_` 前缀 = 网关会话键）。

★ ★★ **三个遥测端点的空 body 行为（★ 分档清楚）**：

| 端点 | 空 body 实测 | 机理 |
|---|---|---|
| `/api/telemetry/decision-log` | **200 `{"status":"ok"}`** | ★★ `ingester == nil` 时走 `else if h.db != nil` ⇒ ★★ **同步写库** |
| `/api/telemetry/request-log` | **200 `{"status":"queued"}`** | ★★ 入队 ⇒ ★★ **异步落库**（★ 钩子再写 3 张表） |

★★★ ★★ **「语法校验通过 ≠ 语义校验通过」** ⇒ ★★★ **⇒ 空 body 被当成一条合法的（空的）业务数据入库。**

## §4 ★★★★ 三层安全模型（★ 本轮最值钱的设计决策）

### §4.1 静态分级（★ 缩小爆炸半径，★ **不是**安全保证）

★ `post-surface-classify.py` 解析每个注册点的 handler 源码，按词法分四类：

| 类 | 判据 | 条数 |
|---|---|---|
| `read` | 无写库调用、**无出网调用** | 402 |
| `write` | 命中写库模式 | 50 |
| `external` | 命中出网调用（★ + 文件级粗筛） | 9 |
| `unknown` | ★ 解析不出（★ 局部 `:=` 变量、★ 名字撞车） | 115 |

★★ ★★ **★ `read` 的定义必须包含「会不会校验请求体」**：★★ **校验了 body ⇒ 空体 POST 必然 4xx ⇒ 零副作用**
⇒ ★★ ⇒ 探测器**第一梯队（148 条）**是**可证明安全**的；★ ★★ 第二梯队（252 条）靠护栏兜底。

### §4.2 ★★★ 静态分级**漏判**了（★ 实证）

| 路由 | 静态分级 | 实测 | ★ 判定 |
|---|---|---|---|
| `/api/telemetry/decision-log` | ★ **`write`** | ★★★ 空 body 就写库（★ **同步**） | ★★ **★ 分级【判对了】** |
| `/api/telemetry/request-log` | ★ **`read`** | ★★★ 空 body 就写库（★ **异步入队**） | ★★★ **★ 分级【漏判了】** |
| `/api/admin/cache-metrics/timeline` | `read` | ★ 疑似写库 | ★★ **★ 归因不可靠**（★ 见 §4.3） |

★ ★★ **⇒ 「分级说它只读」**不等于**「它不写」** ⇒ ★★★ **⇒ 护栏（运行时观测）才是真正的安全网。**

★★★ ★★ **★ 漏判的机理（★ 比「看不穿调用链」更精确）**：
★★★ ★★ **同步写**的端点，★ ★★ **静态分级是【判对的】**（★ `decision-log` 命中 `exec` ⇒ 判 `write` ⇒ ★★ 自动不参与批量探测）。
★★★ ★★ **★ 真正漏判的是【跨组件的异步写入】**：★ ★★ `request-log` 的 handler **自己一个字都不写**
（★ 它只把 entry 塞进队列）⇒ ★★ **落库发生在【另一个组件】（★ 消费端 + `sessionv2mirror` 钩子）里**
⇒ ★★★ **⇒ 词法判据只看得见 handler 的【函数体】⇒ ⇒ 跨组件的写入【必然漏判】。**
⇒ ⇒ ★★★★ **⇒ 这恰恰是【护栏】存在的理由**：★ ★★ 护栏观测的是【真实副作用】，★ ★★ 不管它发生在哪个组件里。

★★★ ★★ **而且我试过把调用链追下去（★ v4/v5）⇒ ★★ 两次都失败**：
★★ ★★ 按名解析深度 ≥1 ⇒ ★★ **全仓同名函数互相污染** ⇒ ★★★ **449/576 ⇒ 195/576 被误判成 `external`**
⇒ ★★★ **⇒ 那是【更宽的假阳性】，★ 不是【更准的判据】** ⇒ ★★ **⇒ 收窄到「只追含出网调用的文件」仍不够** ⇒ ★★★ **⇒ 干脆回退到词法层，★ 把安全交给护栏。**
