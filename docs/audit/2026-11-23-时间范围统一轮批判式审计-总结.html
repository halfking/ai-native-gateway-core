缺陷链（修复前）

用户 在 KxDateRangePicker 选 2026-09-01 ~ 2026-09-10
↓

　days.value = 跨度天数 = 10
↓
GET ?days=10 （真实区间被丢弃）
↓
NOW() - INTERVAL '240 hours'
↓

　↑ 界面显示 A，数据是 B ⇒ 静默错误答案

修复后：预设与自定义分流

用户 选预设（今天/7d/30d/90d）
　→ customRange = null
　→ 走 days 快路
　　（缓存键 / MV 选择 / 索引扫描不变）

用户 选自定义历史区间
　→ customRange = 原样保留
　→ 走 start + end
　　（[start,end) 半开、end 日全天计入）

✓ 界面显示的区间 = 数据反映的区间

六、通用式（可复用的教训）

  1. 「控件统一」≠「语义统一」：统一了输入控件，但没统一「输入如何被解释」。 审计要验的不变量是「界面显示的区间 = 数据反映的区间」，不是「有没有控件」。
  2. 静默回落比报错危险得多：参数被忽略时端点返回 200 + 合理数据，用户无从察觉 ⇒ 区间类参数要么生效、要么明确报错，绝不静默回落默认窗口。
  3. 后端已有能力要先查清再动前端：本轮最反直觉的发现是「start/end 早就通了，是前端压成了天数」 ⇒ 改前端比改后端便宜一个数量级。
  4. 多端点同窗是一致性底线：matrix/flow/funnel 共用一个时间选择器 ⇒ 必须共用同一区间参数， 否则同一页面上半屏是自定义区间、下半屏是「最近 N 天」。
  5. 共享工作树上禁止 git checkout -- . / git clean -fd： 在途改动必须先导出 patch，或全程只在隔离 worktree 操作。
