## 三、根因分析

### 3.1 主档记录的性质

主档中的「`last_probe_at` 停在 2026-11-13」**不是直接数据库查询结果**，而是基于以下逻辑的**推断**：

```
凭据 56 配额耗尽但 quota_state='ok'
→ 余额复检探针看不到它
→ 如果凭据级探针也在跑，应该会更新凭据面状态
→ 但凭据面状态一直是 'ok'
→ 推断：凭据级探针没在跑
→ 推断：last_probe_at 应该很久没更新了
```

### 3.2 推断与实际的差异

**主档观测时间**：2026-11-20 09:37~10:00  
**数据库更新时间**：2026-11-20 15:24:46

**时间差**：约 5.5 小时

**实际情况**：
1. ✅ 凭据级探针**确实在运行**（`last_probe_at = 2026-11-20 15:24:46`）
2. ✅ 模型绑定探针**也在运行**（10 条近期失败记录，最近 13 秒前）
3. ❌ 主档推断「7 天没跑过」**不准确**

### 3.3 为什么推断会出错

**推断的前提假设**：
- 如果凭据级探针在跑 → 应该会发现配额问题 → 应该会更新 `quota_state`

**前提不成立的原因**（正是本轮修复的 D1/D2 缺陷）：
1. **D1**：探针的分类器只看 err code，看不见响应体 → 配额裁决在探针侧不成立
2. **D2**：探针只写绑定面，不写凭据面 → 即使探针在跑，`quota_state` 也不会被更新

**结果**：
- 凭据级探针**确实在跑**
- 但因为 D2（探针不写凭据面），`quota_state` 一直保持 'ok'
- 主档基于「`quota_state='ok'`」推断「探针没跑」→ **推断错误**

## 五、主档推断的合理性

### 5.1 推断逻辑的合理性

在**不知道 D2 缺陷存在**的前提下，主档的推断逻辑是**合理的**：

```
IF 探针在跑 AND 发现配额问题
THEN 应该更新 quota_state
BUT quota_state='ok'（实际观测）
THEREFORE 探针可能没跑（推断）
```

### 5.2 推断的局限性

推断**没有考虑到**探针可能存在「跑了但不写凭据面」的缺陷（D2）。

**正确的推断应该是**：

```

→ 两种可能：
  (a) 探针没跑
  (b) 探针跑了但没写凭据面（D2 缺陷）
→ 需要直接查询 last_probe_at 来区分
```
