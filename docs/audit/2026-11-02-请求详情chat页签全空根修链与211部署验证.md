## 一、一句话结论

★ **不是前端 bug，是「正文压根没落库 + 读路径不读热区镜像」两层叠加**，而这两层各自的**上游**还有一个真缺陷：
**租户级设置写路径在生产库上 100% 失败（SQLSTATE 42P10）** ⇒ 「会话正文录制同意」开关**永远写不进去** ⇒ 正文永不落库 ⇒ 四页签全空。
★ 修法分三层（写路径 / 读路径回源 / 前端诚实空态），另加一处**并发加固**（详见 §5）。

## 三、修法（三层）

### ① 写路径：去掉对不存在的唯一约束的依赖
`settings/store_db.go` 的 `SetTenant`：`INSERT … ON CONFLICT (tenant_id,key) DO UPDATE` ⇒ 改为与平台级 `Set` 同款的
**「先 UPDATE，未命中再 INSERT」**（不依赖那条约束）；同时抽出 `poolDB` 接口 + `newStoreDBForTest` 以便注入 pgxmock。
★ **不改 schema**：补唯一约束要同时改新迁移 + 基线 + DB 对象台账（跨环境、体量大），而写路径本就不需要它。
★ 该缺口自 2026-07-18 起已在 `docs/archive/process/changelogs/2026-07/2026-07-18-pgx-jsonb-cast-fix.md` 登记。

### ② 读路径：热区镜像兜底回源
- 新增 `admin/hotzone_body_source.go`：读 `{requestsDir}/{tenant}/{UTC日}/{rid}.{req,resp,out}.json.gz`（候选日 + 有界目录扫描；路径穿越/超限拒绝）。
- `admin/unified_detail.go`：PG 三件套**全空**且 `settings.RecordingConsentEnabled(tenantID)` 为真时回源；**PG 有值绝不覆盖**（权威载荷优先）；回源后**重算 `body_status`**。
- `domains/requestdetail/types.go` + `locator.go`：新增 `SourceHotzoneMirror="hotzone_mirror"`、`Meta.BodySource`、`Detail.RecordingConsent`；读面是 `request_logs` 时 `Detail.Source` 跟着说真话。
- `cmd/gateway/main.go` + `storage_mode_init.go`：启动时把热区镜像目录接进统一详情。

> ★★ **回源也受同一个同意门控**：同意关闭的租户，镜像里有正文也不在详情接口吐出 ⇒ 否则同意开关对详情面形同虚设。

### ③ 前端：把「正文未落库」与「无消息」分开说
`web/src/api/requestDetail.ts`（`DetailSource` 加 `hotzone_mirror`、透出 `meta.body_status` / `recording_consent`）、
`web/src/composables/useRequestDetailLoader.ts`、`RequestDetailSectionHost.vue`、`RequestDetailFullscreenView.vue`、
`ConversationMessagesPanel.vue`（空态改为诚实文案；正文未落库时**不**渲染 assistant 回复块），8 语种新增 `requestDetail.conversation.bodyUnavailable`。

## 五、加固（`7748d3bc8`）：并发同 key 写会落重复行

★ 「先 UPDATE 再 INSERT」只在**单写者**前提下等价于 ON CONFLICT；而表上**没有**唯一约束可依赖 ⇒
两个并发写者各自 UPDATE 未命中、然后各自 INSERT ⇒ 同 key 落**两行** ⇒
读侧 `GetTenant` 用 `QueryRow` 取首行、`ListTenant` 用 map 覆盖 ⇒ **哪行胜出取决于物理顺序** ⇒ 可能读到旧值。
★ 而这个键控制的正是「会话正文录制同意」⇒ 读到旧值 ⇒ 正文又停止落库 ⇒ **本轮修复的孪生缺陷**（写返回 200、读却是旧值，比原缺陷更难诊断）。

**修法**：事务 + `pg_advisory_xact_lock(hashtext('tenant_settings_kv:<tenant>:<key>'))` ⇒ 同 key 并发写排队 ⇒ 恒等原语义；**不改 schema**。
★ 真库验证：`BEGIN; SELECT pg_advisory_xact_lock(hashtext('…')); COMMIT;` 以应用自身连接用户（`acc_super`）实测通过。
★ 门：两条既有腿补 `ExpectBegin`/咨询锁/`ExpectCommit`（pgxmock **按序匹配** ⇒ 锁不在写之前就红）+ 新增回滚腿 + 新增形状门（锁必须存在且在写语句之前）。
★ **变异臂 2/2 检出**：M1 删锁 ⇒ 3 腿红；M2 锁挪到 UPDATE 之后 ⇒ 顺序腿 + 形状门红（`"1127" is not less than "775"`）；两次还原后 md5 逐字一致。

## 六、遗留与已登记项（本轮明确**未做**）

0. ★★★ **时效性事实：热区镜像是 7 小时滚动缓存 ⇒ 镜像回源只覆盖「近 7 小时」**。
   实测（211，`llm-gateway-211-a`）：trimmer 装配 `retention_hours=7 max_size_gb=1 trim_interval=30m`；
   `requests/default/2026-11-01/` 已 **0 文件**（保留期在执行），`2026-11-02/` 尚有 4830 个文件。
   ⇒ 本次报障请求 `698677f8…`（ts **2026-11-02 11:22:48+08**，镜像写入 03:22 UTC）
   的正文**当前仍在窗口内**，但会在 **2026-11-02 18:22 +08 前后**被 trimmer 删掉；
   **此后**该请求正文在磁盘与 PG 两处都不可恢复 ⇒ 详情接口会返回 `body_status=unavailable`
   ⇒ 页面**诚实显示「正文未落库」**（而不是再变回"静默空页签"——那是本轮前端那一层修好的）。
   ⇒ ★ **新请求不受此限**：同意开启后正文直接落 PG（`session_bodies_hot` 已持续增长到 2341 行），**永久可查**。
   ⇒ ★ 若要让那 7 小时窗口内的旧请求也**永久**可查 ⇒ 需「从热区镜像回填 PG」的导入工具（本轮**未做**，见下）。
1. ★ **`tenant_settings_kv` 仍无 `(tenant_id,key)` 唯一约束** —— 本轮用咨询锁在**运行时**兜住了并发，**schema 缺口本身未补**（补它要同时改新迁移 + 基线 `sql/schema/01-schema.sql` + DB 对象台账三份，跨环境体量大）。缺口自 2026-07-18 起已登记。
2. ★ **热区镜像的写入侧不受同意门控** —— 镜像文件里仍有同意关闭租户的正文（灾备镜像覆盖用途，未改）。本轮只在**读侧**加了门控。
3. ★ **未做「从镜像回填 PG」的导入工具** —— 迁移 890 退役时已废 `cmd/tools/backfill_session_bodies`；重做一个须先裁决「回填窗口 / 去重口径 / 是否也回填 `outbound_body`」，且属数据写入动作 ⇒ 需 owner 拍板，不在本轮「修 bug」范围内。
4. ★ **`meta.body_status` 在 `request_logs` 主路径上不填** —— 主路径「三件套全空 ⇒ 返回 ErrNotFound ⇒ 走会话族/镜像路径」，故主路径成功时**必有正文** ⇒ 前端行为无差异（可观测性差异，非行为差异）。
5. ★ **两态契约表达不了「请求体在、响应体缺」** —— `body_status` 只有 `available|unavailable`，故部分正文的请求仍会把回复显示成「(无回复)」。属**契约层**限制，要改需动 `domains/requestdetail/types.go` + 前端类型 + i18n，超出本轮范围。
6. ★ Gemini/OpenAI 的 **retrieve 端点**（`GET /v1/models/{model}`）仍未做；`cmd/gateway-v2` 的第二套 `/v1/models`（无 scope 口径）不在生产路径。
7. ★ **`meta.body_status`/`body_source` 的 i18n 与前端契约门**依赖 `web/src/api/source-contract.test.ts` 的**单行联合提取**约定；改动该文件时须保持单行。

## 七、通用式（可复用）

1. ★★ **「写不进去」要先查 schema 假设，而不是先改逻辑**：`ON CONFLICT (a,b)` 是**对 schema 的断言**，不是对代码的描述 ⇒ 断言错 ⇒ 写入静默变 500，而表里**一行都没有**。
2. ★★ **「正文在磁盘上但接口拿不到」是独立的一层缺陷**：镜像（灾备）不受录制同意门控，而读路径按 H3 原设计不参与回源 ⇒ 两个设计各自合理，组合起来就是「空页签」。
3. ★★ **"没有消息" 与 "没采到消息" 必须分开说**：空态文案错一个字就是**错的量具** ⇒ 前端要能区分 `body_status=unavailable`（未落库）与「确实没有消息」。
4. ★★ **绕过唯一约束的 upsert 写法必须自带串行化**：没有唯一约束时，「先 UPDATE 再 INSERT」在并发下会落重复行 ⇒ 要么补约束，要么加咨询锁，**不能只改写形态**。
5. ★★ **派生台账/部署产物必须按「将要提交的树」生成**，且**部署要从干净 worktree 走**（本轮共享工作树里躺着并行会话未提交的 WIP，第一次提交因此编译不过）。
