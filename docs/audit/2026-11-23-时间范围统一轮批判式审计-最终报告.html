🎯 结论与根因

问题现象

用户在统计页面选择 2026-09-01 ~ 2026-09-10 自定义历史区间，实际拿到的数据是「最近 10 天」的滚动窗口。这是 静默错误答案（界面显示 A、数据是 B），不是量具问题。

实测取证

GET /api/admin/work-types/stats?start_date=2026-09-01&end_date=2026-09-10
⇒ HTTP 200 且 window="24h"（参数被静默忽略、回落默认窗口）

GET /api/admin/work-types/stats?days=10
⇒ window="10d"（days 参数生效）

根因分析

两条链相乘：

  1. 后端 days 语义是滚动窗口（NOW() - INTERVAL '{hours} hours'），无法表达任何历史区间
  2. 前端把区间压成跨度天数：useSpanDaysRange.applyRange 执行 days.value = 跨度天数

最反直觉的一点：后端能力早就在，只是前端扔掉了 —— admin/board_time_range.go:boardTimeRangeFromRequest 收 start/end、admin/usage.go:resolveUsageTimeRange 是通用解析器、web/src/api/board.ts 早就有 start/end 参数。

通用式

  • 审计要验的不变量是「界面显示的区间 = 数据反映的区间」，不是「有没有控件」
  • 静默回落比报错危险得多 —— 参数被忽略还返回 200 + 合理数据，用户无从察觉
  • 后端已有能力要先查清再动前端 —— 改前端比改后端便宜一个数量级

⚠️ 真踩的三个坑（已钉测）

坑 1：跨度天数不能再 +1

SystemDayRangeUtc 的 End 已是「end 日 +1 天零点」（独占端），再 +1 会把 10 天区间算成 11 天。

// 错误写法
days = int(tr.End.Sub(tr.Start).Hours() / 24) + 1  // ❌ 多加 1

// 正确写法
days = int(tr.End.Sub(tr.Start).Hours() / 24)  // ✅

坑 2：标签必须用原始日期串

标签必须用 StartDate/EndDate（原始日期串），不能用 UTC 瞬时 Format —— UTC+8 下 2026-09-01 的零点 = 2026-08-31T16:00Z，起点会显示成前一天。

// 错误写法
label = tr.Start.Format("2006-01-02")  // ❌ UTC+8 下会差一天

// 正确写法
label = tr.StartDate + "~" + tr.EndDate  // ✅ 使用原始日期串

坑 3：旧标签规则判的是「天数 n」不是「小时数」

旧标签规则判的是「天数 n」不是「小时数」—— n%24==0 判 n 才是 7d；按 Hours 判会因 168h%24==0 误成 168h。

// 错误写法
if hours%24 == 0 {  // ❌ 168h%24==0 误判

// 正确写法
days := hours / 24
if days == 7 || days == 30 {  // ✅

💡 关键决策

后端双入口契约
  • start+end ⇒ [start,end) 半开真实区间
  • days ⇒ 旧行为逐字保留（零参数字面量 interval，端点内其它占位符编号不变）
  • 半截区间/越界/非法值 ⇒ 400 报错不静默回落
自定义区间一律绕开物化视图

MV 只覆盖固定窗口（7d/30d），用它等于另一种静默改写 —— 自定义区间必须走基表查询。

funnel 自定义区间不入缓存

缓存键只带天数档位（7d/30d），两个历史区间会撞同一把键导致串数据 —— 自定义区间每次查库。

预设仍走 days 快路

预设区间本身就是「相对今天」的窗口，与 days 语义等价 —— 后端缓存键/MV 选择/索引扫描不受影响。

组件加 presetsOnly

端点确实只收 days 的页面，宁可不给自定义入口，也不给会被悄悄改写的区间 —— 用 presetsOnly 禁掉自定义起止输入。

部署用隔离 worktree

共享工作树有兄弟会话未跟踪的在途件，会随 tar 上树污染部署 —— 必须在隔离 worktree 里打包。
