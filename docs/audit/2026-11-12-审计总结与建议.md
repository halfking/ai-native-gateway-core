### 4. 需要修复的错误 (1类)

#### 🔴 P0: openai_empty_response (错误#1/10/13/19/25)

**问题描述**:
- 影响模型: **100% minimax-m3.1-flash**
- 发生频率: 76次/7天 (~11次/天)
- 占executor failed的15%

**根因**:
```
MiniMax M3.1-Flash在思考(reasoning)阶段耗尽token预算
→ 返回大量reasoning_content但零delta.content
→ 网关按r1029规范判定为空响应
→ reasoning帧已commit,无法failover到其他候选节点
→ 返回retryable=true,客户端可重试
```

**当前行为评估**:
- ✅ 正确: 设置retryable=true,允许客户端重试
- ✅ 正确: 正确分类为KindEmptyResponse
- ❌ 问题: 已commit后无法在网关层failover

**修复方案选择**:

**方案A: reasoning-only帧延迟commit (推荐)**
```go
// 在 domains/streaming/responses_bridge.go
// 只有在收到实际content或tool_calls时才commit
func shouldCommit(scaffold *chatScaffold) bool {
    // reasoning_content不算实际输出
    hasContent := scaffold.textBuf.Len() > 0
    hasTools := len(scaffold.toolStates) > 0
    return hasContent || hasTools
}
```

**优点**:
- 允许transparent failover到其他minimax候选
- minimax-m3.1-flash有6个可路由绑定
- 用户无感知,网关内部自动切换

**缺点**:
- 改变流式commit语义
- 需要全面回归测试
- 需要owner裁决

**方案B: 客户端级别智能重试 (短期方案)**
```go
// 保持当前retryable=true
// 客户端检测reasoning_tokens ≈ completion_tokens
// 自动重试时优先选择其他minimax候选
```

**优点**:
- 最小侵入性
- 不改变服务端语义

**缺点**:
- 需要客户端配合
- 用户体验略差(多一次往返)

**推荐**: 方案A(长期) + 方案B(短期)组合
