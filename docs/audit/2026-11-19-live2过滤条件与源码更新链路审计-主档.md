### 1.2 条件数据处理模式（展示）

整条链是「**后端只推请求瓦片，前端在内存里聚合选项**」——没有 filter-options 端点，SSE 帧里也没有选项字段：

```
请求热路径                     后端（SSE 通道）                        前端（/live2 内存）
──────────                    ───────────────                        ─────────────────
telemetry 钩子 ──┐
  agent_name     │  initial_data（首帧回放）:
  credential_id  ├─▶ Redis 主队列 ZREVRANGE 最近200条 ─┐             realRequests（滤掉 idle_marker 心跳）
  canonical_model│  （Redis 挂 ⇒ DB 兜底：          ├─▶ SSE ──▶   requestsRef（滚动缓冲 MAX_VISIBLE
  ...            │   request_logs 2h 窗 JOIN 显示名）┘                =max(20,min(200,视口×2×12)) 条）
                │                                                    │
                │  实时增量帧（LiveRequest）──────────────────────────┘
                │                                                    ▼
节点健康投影 ────┴─▶ node_update 帧（credentials 表 2s 投影）──▶ nodesRef ─▶ invalidNodes/down 集合
                                                                        │
                                                                        ▼
                                              optionRequests = realRequests − 无效节点流量（本轮修正，见 §1.4-F1）
                                                                        │
                                                                        ▼
                       filterOptions(optionRequests, now, windowMs)（liveTopologyFilter.ts:84）
                         逐条过 withinWindow（ts ≥ now−windowMs，窗外丢弃）
                         四维各建 Map 计数 → 按 count 降序 top12（带命中数）
                                                                        │
                                                                        ▼
                       LiveTopologyFilterBar 四个下拉（与 /live 同一组件）
                                                                        │
                       选中后：applyFilters 纯前端内存过滤（同维 OR、跨维 AND、
                       默认剔除无效节点流量）——「过滤只影响呈现，不下推 SSE」
```

**时间范围**：预设 5m/30m/2h 三档（默认 5m），选项只含窗内值（有钉测：liveTopologyFilter.test.ts:155「ignores out-of-window traffic when listing candidates」）。
**设备状态**：节点的在线/健康（down=熔断 open/不可达/手动停用）不参与**选项生成**的加法，只在两处参与减法——①本轮修正后无效节点的流量不进候选（§1.4-F1）；②过滤生效时默认剔除无效节点的带（勾选「显示无效节点」放行）。

### 1.3 口径限定（如实登记，均非目录泄漏）

1. **选项受两层滚动缓冲截断**：后端回放上限 200 条（Redis）/ DB 兜底 2h 窗（本轮从 1h 对齐，§1.4-F2）；前端 store 再按视口裁剪 20~200 条。⇒ 30m/2h 窗口的选项反映「仍留在缓冲里的最近请求」，不是该窗口的完整历史——这是实时页面的设计边界（页面本身也只显示这些带）。
2. 前端窗口预设没有 all 档；URL 参数只有网络层开关（probe/slim/dims），过滤值不进 URL。

## 四、通用式（本轮沉淀）

1. **「更新」的第一守卫是「别碰不该碰的」**——更新链路里每一处写操作都要先问「这是版本物还是用户配置/数据」：.env/数据库数据是用户的，镜像 tag/迁移是版本的。install 与 update 共用一个入口时，入口必须自己识别身份（已有 .env/台账 = 更新），不能指望用户记得「该用哪个命令」。
2. **手抄清单必然停滞**——离线包迁移清单停在 654 七十天无人报错，因为「没进包」是静默的。凡「目录 → 子集」的投递面，要么动态枚举+防停滞门，要么有对账门让缺口爆出来。
3. **bash 数值比较会按八进制解析前导零**——`[[ 008 -lt 412 ]]` 报 "value too great for base" 且判假，过滤静默失效；版本号比较一律 `$((10#$v))`。
4. **字典序只在同位数下等于数值序**——迁移号跨千位（999→1000）时字典序反转；一切「按编号递增执行」的通道都要显式数值序。
5. **选项的口径要跟呈现的口径对齐**——下拉候选项必须来自「图上默认看得见的同一数据池」，否则会出现选中后空无一物的死选项（选项生成多减一次「无效节点」，与渲染的减法同源）。
6. **兜底路径的窗口要跟主路径对齐**——DB 兜底 1h vs Redis TTL 2h vs 前端窗 2h：降级发生时差值不报错、只少数据，是最隐蔽的一类口径漂移。

## 五、遗留登记（不修，附理由）

- **L1**：installer 增量模式按 version 跳过、不做 content 指纹重放——同编号文件被内容加固时该差异在 installer 通道不重放（内部开发通道有 content_sha256 指纹机制）。按仓内纪律「内容变更走更高编号迁移」时无影响；已写入 InitSchema 注释与 installer/README。

- **L3**：在线升级（systemd 布局）仍不投递 SQL 文件链（结构上二进制制品不含 SQL）——已文档化指路离线包；若未来 systemd 布局复活为主要形态，需给在线通道加迁移制品。
- **L4**：/live（LiveTopologyView）的选项口径是「过滤后集合」（随当前选中收缩）——与 live2 修正后的「窗内真实请求−无效节点」不同形。/live 有既有测试钉住该行为，属两页各自的交互决策，本轮不动；若 owner 要求两页完全同口径，另起一轮统一。
- **L5**：live2 选项 top12 上限与滚动缓冲 20~200 条截断（§1.3）为设计边界，非缺陷。
- **L6**：fresh_installer_integration_test.go 的 e2e（真 docker 装 PG）未在本轮本机复跑（无 docker 环境）；增量模式的行为由纯函数钉测 + 既有全量链 e2e 组合覆盖，首次真实升级窗口建议观察 InitSchema 日志里的「增量模式」行。

### 6.1 部署测试门的一次活体打回（并记录处置）

首跑 deploy-211.sh 被 admin 的**降级契约门**拦下：`TestDegradePayloadsCarryMarker` 报 `installer/internal/dbinit/runner.go:2053` —— 增量探测首版用 `strings.Contains(out, "42P01")` 捕获「表不存在」错误，而契约扫描器把 `"42P01"` 字面量视为降级判定点（schema 落后 ⇒ 返回空载荷必须带 degraded 标记）。**根修而不是豁免**：改用 `SELECT to_regclass('public.schema_migrations')` 探测（对不存在的表返回 NULL 而不是报错）——「全新库」从「要捕获的错误路径」变成「普通查询结果」，函数不再依赖任何 PG 错误码字面量，语义也更干净（探测优于异常捕获）。修正后 dbinit 包 + 契约测试双绿。★ 通用式：**契约门抓到你，先问「能不能换成根本不需要被豁免的写法」**——豁免表是给「语义上确实不属于契约」的场景留的，不是给「换种写法就能合规」的场景留的。

### 7.4 通用式（追加轮沉淀）

1. **「唯一的 active 升级指南」若整体过期，比没有指南更坏**——它会以官方身份教错每一条命令；重写优先于打补丁（499 行里没有一条命令可原样执行时，补丁无从下手）。

3. **迁移登记断链的门会说话，前提是有人跑它**：embed 同步门在 origin/main 红着被推上来——「门红着推 main」本身说明并行车没跑门；收口方以基线对拍定归属后修到绿。
4. **不可运行的迁移要撤得干净**：留在 embeddata/正典任一处都会被某个门或通道扫到（门红/部署炸）——「未就绪」的正确形态是全部撤出+修复版存档+登记恢复路径，而不是「留着但不登记」。
