## 二、根因：缺陷为什么会同时发生

上一轮把「管理员管理用户密钥」当成**纯前端任务**做，而后端其实早就有一套完整的
密钥管理端点（`/api/keys` 的 CRUD + reveal + approve + enable/disable/revoke）。
于是出现两类问题：

1. **前端按错误的契约接后端**（F2/F3/F5/F7）—— 前端以为 `enabled` 就是"状态"、
   以为 `status` 只是冗余字段，于是把后端的"静默失败"当成"成功"渲染出去。
2. **复用了不该复用的读面**（F7）—— `getKeys()` 没有过滤参数，前端只能拉全量再筛。

★ 通用式：**「端点已存在」不等于「端点语义与你的用法一致」**。
`setKeyEnabled` 只写 `enabled` 而不写 `status` —— 这在别的页面（KeysView）无害，
因为那里没人对 revoked 密钥点启用；换到「用户密钥管理」这个新场景，它立刻变成
一个骗人的成功提示。

## 三、缺陷清单（按严重度）

### ★★ P0-1 「启用」对已吊销密钥是**静默失败**（骗管理员）

**事实链**

| 事实 | 出处 |
|---|---|
| 请求鉴权谓词：`ak.enabled = TRUE AND COALESCE(ak.status,'active') NOT IN ('revoked','disabled')` | `domains/authentication/verifier.go` 的 `callVerifyDB` |
| `setKeyEnabled` 只写 `enabled`，**不写 `status`** | `admin/keys.go` |
| 吊销（`deleteKey`）写 `status='revoked', enabled=FALSE` | `admin/keys.go` |
| 上一轮 UI 只看 `enabled`，对 revoked 密钥也显示「启用」按钮 | `UserDetailDrawer.vue` |

**后果**：管理员点「启用」→ 后端返回 200 `{"message":"updated"}` → 前端弹「密钥已启用」
→ 但 `status` 仍是 `'revoked'` ⇒ **认证照样拒绝** ⇒ 管理员以为修好了，密钥实际仍不可用。

**修复**
- 后端：`setKeyEnabled(enabled=true)` 时先读 `status`，`'revoked'` ⇒ **409 + 明确说明**
  （不自动改写 status —— 吊销的语义是「不可撤销」，改写它等于偷偷推翻吊销）。
- 前端：`revoked` 密钥**不渲染「启用」按钮**，并单独提示「已吊销的密钥不可恢复，如需继续使用请重新签发」。

### ★★ P0-2 签发密钥**必然失败**（只要不填预算/速率）

**事实链**

| 事实 | 出处 |
|---|---|
| `v-model.number` 在空输入时，Vue 3 的 `looseToNumber` 返回**原字符串 `''`**（不是 null） | Vue 3 运行时 |
| 上一轮写的是 `budget_usd: newKeyForm.value.budget_usd ?? undefined` | `''` 既不是 null 也不是 undefined ⇒ 发送 `budget_usd: ""` | 
| 后端 `BudgetUSD *float64` 反序列化 `""` 失败 ⇒ `readJSON` 报错 ⇒ 400 `invalid body` | `admin/keys.go` `createKey` |

**后果**：表单里两个数字输入框只要有一个留空（默认就是空的），签发就 400。

**修复**：输入框改用 `v-model`（不带 `.number`），提交前经 `numOrUndef()` 归一
（空 ⇒ `undefined`，非数字 ⇒ `undefined`）。

### ★★ P0-3 明文密钥**跨用户残留**（跨账号泄露）

**事实链**

| 事实 | 出处 |
|---|---|
| `createdKeyResponse` 只在 `resetCreateKeyForm()` 里清空 | 上一轮实现 |
| 该函数只在点弹窗的「关闭/取消」时调用 | 上一轮实现 |
| 抽屉关闭**不**调用它 | 上一轮实现 |

**后果**：签发成功 → 显示明文 → **直接关掉抽屉**（不点弹窗关闭）→ 再打开另一个用户
⇒ 弹窗仍显示**上一个用户的完整密钥**。

**修复**：`resetSecretState()` 在三个时机调用 —— ① 抽屉关闭（`modelValue` 变 false）
② 切换用户（`props.user.id` 变）③ 显式关闭弹窗。明文统一存一个 state 变量。

### ★★ P0-4 缺「查看存量密钥完整信息」（客观需求的直接缺失）

**事实**：后端 `GET /api/keys/{id}/reveal` 早已存在（`admin/keys.go` `revealKey`，
且写审计日志 `apikey.secret_revealed`），前端 `api/keys.ts` 也早有 `revealKey()`。
**上一轮一个字都没接** ⇒ 存量密钥的完整信息根本看不到。

**修复**：接入 `revealKey`，与签发结果共用一个「完整密钥」对话框（含复制按钮 +
一次性警告文案）。

### ★ P1-5 状态徽章只反映 `enabled`，掩盖 `status`

**事实**：`api_keys.status` 的权威取值域来自表约束
（`sql/objects/tables/api_keys.sql`）：
`CHECK (status IN ('active','pending','disabled','throttled','revoked'))` —— **5 个态**。
上一轮只显示 `enabled` 一个布尔量。

**后果**：
- `revoked` 显示成「禁用」⇒ 与「可恢复的禁用」混为一谈；
- `pending`（待审核）显示成「正常」；
- `throttled`（仍可用但被限流）显示成「正常」⇒ 管理员会以为密钥坏了。

**修复**：`keyState()` 按真 `status` 优先判定，5 个态各有独立徽章与文案。

### ★ P1-6 i18n 门禁红 + CJK 棘轮 +42

**事实（实测）**

```

$ node scripts/i18n-cjk-count.mjs

```

换回上一轮改动前的 `UserDetailDrawer.vue` 重测 ⇒ **4590** ⇒ **本轮净贡献 +42**。

**修复**：45 个新键全部落进 8 个语种 locale 文件（`users.ts` × 8），
CJK 计数 **4632 → 4568（相对 HEAD 净减 22）**。

**★ 追加发现（同一门禁，本轮顺带修掉上一轮的另一处缺口）**：
`keys.detail.logs.{title,viewAll,empty,success,pending}` 与
`keys.detail.error.loadLogsFailed` —— 上一轮的 KeyDetailView「最近日志」用了这 6 个键，
但**只在 zh-CN / en-US 存在**，其余 6 语种缺失 ⇒ `localeKeyParity` 硬闸红。
⇒ 本轮补齐 6 语种，并按「不得与源语/英文逐字相同」口径选词。

**★ 关于「同形词」的取舍**：`localeValueQuality` 按「值与 en-US / zh-CN **逐字相同**
= 没翻」计数 ⇒ 德语 `Budget`/`Status`/`Optional`、法语 `Budget`/`Application`、
日语漢字 `正常`、繁中 `速率限制` 这类**同形词会被计成缺陷**。
本轮不写「豁免」，而是换成**语义更准且字面不同**的译法
（德 `Ausgabenlimit`/`Zustand`、法 `Plafond de dépense`/`Application liée`、
日 `有効`、繁 `限流設定`/`啟用中`/`已被節流`）⇒ **我的 `untranslated` / `sameAsSource`
计数净贡献 = 0**（复测数值与 HEAD 逐字相同）。

### ★ P1-7 拉全站密钥回浏览器（越权下发 + 全表下载）

**事实**：`listKeys` 对 super_admin 不加租户过滤 ⇒ `getKeys()` 返回**全站**密钥
（含其它租户的 `owner_user` / 前缀 / 用量 / 备注）。上一轮在浏览器里 `filter`。

**后果**：① 浏览器内存里已拿到其它租户的密钥元数据 ② 每次打开抽屉下载全表。

**修复**：后端 `listKeys` 新增 `owner` 过滤参数（`AND ($3='' OR ak.owner_user=$3)`），
前端改 `getKeys({ tenant, owner })` ⇒ 服务端过滤。

### ★ P1-8 密钥操作无角色门禁

**事实**：上一轮无条件渲染密钥标签页与操作按钮。后端 `requireUserManager` 允许
`super_admin` / `tenant_admin` / `admin_key`，其它角色连 `/users` 都进不来
⇒ 实际越权风险低，但 UI 契约应当自洽。

**修复**：`canManageKeys = isSuperAdmin() || isTenantAdmin()`，标签页与操作区按它渲染。

### ★ P2-9 `ElMessageBox` 的 `'close'` 被当成错误

**事实**：element-plus 的 confirm 点「取消」reject `'cancel'`，点 X / ESC reject `'close'`。
上一轮只排除了 `'cancel'` ⇒ **按 ESC 关掉确认框会弹一条红色的「吊销失败」**。

**修复**：`isDialogDismiss(e)` 同时排除两者。

## 八、通用式（本轮可复用的教训）

1. **「端点已存在」≠「端点语义与你的用法一致」** ——
   `setKeyEnabled` 只写 `enabled` 不写 `status`，在 KeysView 无害，换个场景就是骗人的成功提示。
   ⇒ 复用端点前先读它的**写入面**，不只读它的路由。
2. **鉴权谓词是唯一权威** ——
   "这个密钥能不能用"由 `enabled AND status NOT IN (...)` 决定，不由 UI 徽章决定。
   ⇒ UI 必须按谓词建模，否则必然出现"显示正常但不可用"。
3. **v-model.number 的空值不是 null** ——
   Vue 3 的 `looseToNumber` 对 `''` 返回原字符串。⇒ 数字字段要么显式归一，要么用 `v-model` + 提交前转换。
4. **一次性状态必须在三个时机清零** ——
   「关弹层」「切实体」「关容器」是三件不同的事，漏一个就是跨实体泄露。
5. **守卫自己也要被审计** ——
   本轮第一版契约断言写的是 `not.toContain('v-model.number')`，结果命中了**文件头描述缺陷的注释**
   ⇒ 假阳性。⇒ 断言要查**属性用法形态**（`v-model.number=`），不是裸串。
6. **权威 DDL 优于代码里的枚举** ——
   `status` 的 5 个取值域来自表约束 CHECK，不来自任何 TS 类型或 Go 常量。
   ⇒ 照着 `sql/objects/tables/*.sql` 读，比照着代码读准。
7. **读面的过滤口要开在服务端** ——
   "拉全量回来前端筛"在小规模下是便利，在多租户下是**越权下发**。
