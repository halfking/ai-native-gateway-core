# 2026-11-18 security 两死开关接活——211 误报 403 根修（主档）

> 任务来源：owner 报障「当前访问 211 上的 llm.itestu.cn 网关，出现如下错误，请检查 211 上的 log，找到原因并修复：ZCode 报错 `provider=new-provider-2 provider_code=governance_blocked model=minimax-m3 request=af50d063-… reason=auth_failed status=403 retryable=false`，还有一种错误就是认证失败」。

> 修复提交：`e368b0479`（fix(security): security.enabled/security.mode 两开关接活）。零迁移、零 schema 变更、零路由变更；无数据处置（被拦请求本就不落 WAL，无需修复数据）。

## 一、取证链（211 现场 + 用户端双面）

1. **报文里的 request 在网关日志里的真身**：`client_request_id=af50d063…` ⇒ `/v1/messages`（ZCode/3.18.2，117,755B）在 `2026-11-18T05:10:13Z` 被**网关自己** 118ms 内 403，`error.kind=unauthorized`，响应仅 93B。请求**从未出网关**——所谓 `provider=new-provider-2` 是 ZCode 对这个网关端点的本地命名，`provider_code=governance_blocked` 是网关 403 body 里的 code（`domains/interception/dispatch_gate.go` `blockBody()`）。
2. **拦截点**：`v2 pipeline: preflight error … stage 'security' … hook 'security.check' failed: security: request blocked: critical threat detected` ⇒ `v2 dispatch gate: short-circuit … decision_kind=block` ⇒ `WriteDecisionResponseWithApprovals` 403。当日共 **4 笔**（04:51 一笔 /v1/chat/completions，05:08/05:10/05:10 三笔 /v1/messages，其中两笔 body 高达 **7.1MB**——同一个自动化任务的反复重试）。
3. **拦截器实现**：`domains/hooks/security/hook.go`（legacy v3 SecurityHook）读 `env.Metadata["user_content"]`（v1 wrapper 的 F-41 提取器取**最后一条 user 消息**，64KiB 截断）⇒ `ThreatDetector.Detect()` 打分 ⇒ `isCriticalAt(threats, severity≥7)` ⇒ block。

## 二、根因（三因叠加，一因引爆）

### F1（引爆因）：昨日 P0 修复把误报第一次收口到客户端

`b2c43d044`（2026-11-18，「PI 拒绝判定此前到不了客户端」）在 v1 wrapper 管线中止后**补做 governance Decide**——「中止前已经写下的 deny verdict（PI 检测、legacy security 的 critical threat）被丢弃 ⇒ 拦截形同虚设」的问题被修掉。副作用：**legacy security.check 的误报 verdict 也第一次真正生效**。部署（`c264acb5` build_seq 3100，≈12:5x 本地）后 25 分钟内即出现第一笔误拦（04:51Z）。

> ★ 通用式：**「拦截形同虚设」不是安全态，是带毒的侥幸态**——闸门失明的岁月里积累的错误判定，会在闸门复明的第一天集中兑现。修拦截时必须先盘点「拦截器质量」，否则修好管道 = 把污水接进用户杯子里。

### F2（死开关×1）：`security.enabled=false` 无消费者

211 `settings_kv` **已经写着 `security.enabled=false`**（运维早已关闸），但全仓唯一出现处是 spec 定义（`settings/spec_modules.go:582`）与管理面挂载（`admin/modules.go:317`）——**零运行时消费者**。钩子实际只受 boot 期 env `LLM_GATEWAY_V2_SECURITY`（默认 true）控制注册。spec 承诺「关闭后跳过所有安全检测」⇒ 契约违约。

### F3（死开关×2）：`security.mode` 默认 observe 但从不被读取

spec：`observe=仅记录不拦截（推荐测试期），enforce=高风险请求直接阻断`，**默认 observe**。`loadSecurityConfig()` 加载了 Mode 字段，`Execute()` **从不使用**——`isCriticalAt` 命中即 block。⇒ 生产一直在「文档说 observe、行为是 enforce」的状态下运行。

### F4（误报源，登记不修）：规则库是子串级的误报机器

`threat_detector.go` 规则形态 vs 正常工程内容：

| 规则族 | 形态 | severity | 误报示例 |
|---|---|---|---|
| jailbreak EN | 裸子串 `"dan"` | **10** | `redundant`/`abundant`/`verdant` |
| jailbreak EN | 裸子串 `"you are now"`/`"act as if"`/`"no limits"` 等 | 10 | 正常对话/文档 |
| jailbreak ZH | 「忽略」「无视」「绕过」「扮演」 | 10 | 「忽略此配置」「扮演重要角色」 |
| injection | 裸子串 `"system:"`、`"ignore all"`、`"new instructions"` | 9 | 日志摘录、工具文档 |
| PII | `(电话\|phone\|mobile\|tel\|手机号?)[\s:=]*[\d+][\d\s\-()]{8,20}` | 8 | `tel` 子串 + 任意 9 位以上数字串 |

**实证**：把该规则集逐字移植成脚本，重放出事会话（sess_06c98ff4，minimax-m3）同窗口 **54 笔全部 200 成功**的请求 body——**54/54 全部命中 `jailbreak(sev10)`（'dan' 子串）**。即：拦截与否的真正分野不在规则命中（命中是常态），而在**最后一条 user 消息**（F-41 提取器只取它）里是否恰好含关键词。af50d063 的 117KB body 比同会话成功请求大 ~28KB，其最后一条 user 消息命中了规则清单中的至少一条 ⇒ 拦。被拦请求不落 request_wal（pre-routing 短路），body 无存档 ⇒ 具体命中词条不可精确归因（已用同会话重放 + 规则形态学给出 above 界）。

> ★ 通用式：**「检测器命中」与「该拦」之间差着一整个误报率**。子串级规则在 117KB 工程内容上的命中是必然事件，拦截决策不能建立在「命中即拦」上；顺带，**只取最后一条 user 消息**的提取口径让拦截变成「看运气」——同会话前 54 笔全过、第 55 笔撞词即死。

## 三、「认证失败」的真相

用户报文中的 `reason=auth_failed` 是 **ZCode 客户端对任何 403 的归因渲染**，不是网关或上游的认证失败。同 API key 在同时段大量 200（含 minimax-m3、claude-opus-5-5 真实作答）。网关侧 24h 内对 ZCode 流量**零笔 401**（日志中的 401 全部是 curl 扫页面的探询）。⇒ 用户看到的「两种错误」实为同一笔 403 的两个展示字段（provider_code=governance_blocked + reason=auth_failed）。

另两类当日 503（与本次报障无关，登记）：
- `gpt-6-astra` ⇒ 503 `no healthy provider`（会话标题生成小请求反复失败）——模型目录有、211 无健康凭据，运营/凭据面事项。
- 4.7MB `/v1/chat/completions` 每 ~2.5 分钟一笔 503（04:33–05:12，13 笔）——某自动化任务对无健康供应商模型的固定重试。
- request_wal 当日 failure 分布（minimax-m3.1-flash 44、deepseek-v4-flash 20…）为探针/路由面既有形态，与本轮无关。

## 四、修复（提交 `e368b0479`）

`domains/hooks/security/hook.go`：

1. **`security.enabled` 接活**：`SecurityConfig.Enabled`（默认 true）← settings；`Execute` 开头 `!Enabled ⇒ return nil`（跳过全部检测，含 metadata/governance 副作用）。
2. **`security.mode` 接活**：仅归一化后等于 `enforce` 才进入拦截模式；observe（spec 默认）只留痕放行。**observe 不写 deny governance verdict**——否则 interception 引擎的 Decide 照样产出 Block，开关等于没接。
3. **命中留痕**：critical 命中时 `slog.Warn("security: threat detected", action=observe|block, threshold, threats=type(sev):evidence…)`（evidence 只含规则形态不含用户原文）。修复前拦截零日志——本轮取证只能靠 body 重放反推，运营无法定位。

既有钉测改判：`TestSecurityHook_DangerousContentBlocked`（钉「默认必拦」）⇒ 拆为 `EnforceModeBlocksCritical`（显式 enforce 才拦）+ `ObserveModeRecordsButDoesNotBlock`（默认 observe 不拦且无 deny verdict）+ `ObserveModeLetsDanSubstringThrough`（211 事故形态回归）+ `DisabledSkipsAllDetection`（总开关）+ `LoadSecurityConfig_Switches`（装载三态）。旧钉测正是「把 observe 契约从未被执行固化」的反向锁。

## 七、遗留登记（不修，单独立项）

- **L1（P2）检测规则误报债**：`threat_detector.go` 子串级规则（'dan'、中文日常词、`tel`+数字、裸 `system:`）在 enforce 模式下仍会产生大量误拦。当前 211 因 `security.enabled=false` + observe 默认而**双保险不拦**；若运维未来要启用 enforce，**必须先重写规则**（词边界匹配/白名单域/置信分），并先用 observe 模式观察留痕数据。规则重写涉及检测语义裁决，归 owner。
- **L2（P3）user_content 提取口径**：只取最后一条 user 消息 ⇒ 拦截面只看最后一跳，历史消息带雷则完全不可见；反之历史干净、最后一跳撞词即死。与 L1 一并裁决。
- **L3（P3）被拦请求零留痕**：pre-routing 短路的 governance 拦截不落 request_wal/审核单 ⇒ 误拦无法事后审计（本轮只能靠客户端 rollout 反查）。建议给 block 决策落一行审计（含 threat types/evidence/规则版本）。
- **L4（P3）gpt-6-astra 无健康凭据**（503）：目录有模型、211 无可用供应商，标题生成请求反复失败；归运营补凭据或下架目录项。

## 八、通用式沉淀

1. **死开关比没有开关更坏**：`security.enabled=false` 写在库里的那刻起，运维以为闸已关；实现却照常执法。开关的验收判据是「关掉它改变行为」，不是「配置项存在」。
2. **修复拦截通道前先审计拦截器质量**：P0 修「拦截到不了客户端」是正确方向，但欠一步「拦截器的误报率盘点」——把不可靠判官接上法庭，错判立即执行。
3. **文档契约（spec Description）是可执行断言**：observe=仅记录不拦截写进了管理面给运维看，实现却从未读它 ⇒ 「settings 页显示的状态」与「运行时行为」分叉必然以生产事故收场。
4. **客户端错误归因要对着网关侧日志核对**：`auth_failed`/`governance_blocked` 是两层各自渲染的结果（ZCode 归因 403 + 网关 governance code），报障原文 ≠ 系统真相，取证钥匙是网关自己的结构化日志行。
