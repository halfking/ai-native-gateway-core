## 2. 缺陷与修复

### 2.1 ★★★ verified 共识门死锁（修复①）

**判定链**：`Evaluate` 对原始判定=verified 的结果做连续共识
（Config.VerifiedConsecutiveRuns=2）：streak < K ⇒ 降级 unknown +
`evidence.consensus_pending=true`。streak 延续的条件原实现是
`in.Previous.Verdict == VerdictVerified`——但 Previous 是
`LoadPrevious` 从**当前态表**读回的**最终落盘 verdict**：
共识未满的轮落盘的是 unknown ⇒ 下一轮读到 unknown ⇒ streak 重置为 1
⇒ **streak 永远无法累积到 K ⇒ verified 在生产上永远不可达**。

**为什么既有测试没抓住**：TestVerifiedConsensus 第二子例喂的前置态是
`Previous{Verdict: verified, VerifiedStreak: 1}`——这个形态在生产上**不可能
由真实落盘产生**（streak=1 的轮必然以 unknown 收场）。测试测的是「如果上一
轮是 verified」，而真实世界上一轮永远是 unknown(pending)。
★ 通用式：**单测构造的前置态必须是「落盘方真的会写出的形态」**——
断言链路时，先问「这个输入谁生产」。

**修法**（两层）：
1. `Previous` 增 `ConsensusPending bool`；`LoadPrevious` 的 SELECT 增读
   `COALESCE((evidence->>'consensus_pending')::boolean, FALSE)`；
2. `Evaluate` 的 streak 延续条件改为
   `prev.Verdict == verified || prev.ConsensusPending`——「原始判定达标」
   的两种落盘形态（verified 或 pending-unknown）都能接续 streak。

**测试**（verdict_test.go 重写 TestVerifiedConsensus，5 子例）：
真实落盘形态续判 verified / 平 unknown 不续 / verified 延续 / K=3 链 /
首轮 pending。**变异臂 A**：退回旧延续逻辑 ⇒ 2 子例红（含「生产唯一真实
路径」）⇒ 还原 md5 一致。
**链路真库腿**（变异臂 B 的产物）：把 `consensus_pending` 从 LoadPrevious
摘掉 ⇒ **单元测试全绿**（单元测试直接构造 Previous，不走 LoadPrevious）
⇒ 暴露覆盖缺口 ⇒ 补
`TestConsensusStreakSurvivesPersistence`（SaveResult 落 pending 形态 →
LoadPrevious 读回 → Evaluate 续判 verified 的端到端），变异臂 B 重跑 ⇒
链路测试当场报「LoadPrevious lost evidence.consensus_pending」。
★ 通用式：**「读端摘字段」这类变异，单元测试结构性测不到——跨层字段
必须有真库往返腿**。

### 2.2 ★★ rollup 分数与结论不同源（修复②）

`RollupProviderModel` 原实现
`MIN(credibility_score), COUNT(*), MIN(verdict)`——分数与结论各自独立聚合。
两条线 `(diluted, 88)` + `(unknown, 20)` ⇒ 读出「20 分 + diluted」：
**数据里不存在的组合**。`MIN(verdict)` 按字典序恰好与严重度序一致
（d<s<u<v）是巧合不是契约；且即使字典序对齐，分数仍可能来自另一行。
迁移 922 的注释契约写的是「取最差**那条凭据**的结论」。

**修法**：`SELECT DISTINCT ON (provider_id, raw_model_name) ... ORDER BY
provider, model, CASE verdict(diluted=0/suspected=1/unknown=2/verified=3)
ASC, credibility_score ASC`——每组取「结论最重、分数最低」的**同一行**；
样本数改 `count(*) OVER (PARTITION BY ...)` 保持全组计数。
（SQL 侧显式 CASE 枚举严重度，不依赖字典序；与 types.go VerdictRank 同序。）

**测试**：`store_rollup_integration_test.go`（`//go:build integration` +
`TEST_PG_CONTRACTS_ISOLATED=1` + 库名 `*_test` 守卫，照搬
bg/provider_error_aggregator_integration_test.go 的隔离规矩）：
真库一次性库 credibility_rollup_test（应用迁移 922）实测两组夹具，
含「字典序陷阱反向」组（suspected 91 vs diluted 55 ⇒ MIN(verdict) 会选中
suspected，正确答案是 diluted 55）。**变异臂 C**：退回 MIN 聚合 ⇒
当场红（got score=20 verdict=diluted, want score=40）⇒ 还原 md5 一致。

### 2.3 ★★ ScanNode 全量写回（修复③）

`ScanNode`（POST /trigger 的后端）落库后调
`WriteProviderQualityProfiles(rollupCtx, nil)`——nil 走全量路径，把判定表里
**所有**历史残留行（已下线/已移出特色清单的模型）原样重写一遍。

残留行被误写」）自己就写明了这个坑，单点触发却没对齐。
**修法**：传 `[]modelcredibility.NodeTarget{*target}`。

### 2.4 ★ 前端两处（修复④）

- **anomaly 映射缺被动键**：ca161ce34（被动流量证据融合）新增
  `identity_passive_mismatch` / `consistency_passive_drift` 两个异常常量，
  前端 `anomalyLabel` 映射表与 8 语种语言包都没跟上 ⇒ 真实流量里出现被动
  mismatch 的节点在详情弹窗里裸上屏 snake_case（内部标识泄漏族，
  §431/第 19 增量同族）。修法：映射表 +2 键，8 语种各 +2 值
  （逐语种独立措辞，句式与相邻键对齐）。
- **catalog 死消费**：视图每次 load 并行拉 `/catalog`（按 canonical 聚合的
  rollup）但**从未渲染**——统计卡注释明确写了「计数来自当前列表而不是
  catalog」⇒ 每次刷新白付一次聚合查询。修法：删视图内消费
  （ref/import/Promise.all），API 层 `getModelCredibilityCatalog` 与后端
  端点保留（合法 API 面）。

## 5. 通用式（→ LESSONS §604）

1. ★★★★ 单测构造的前置态必须是「落盘方真的会写出的形态」——测链路先问
   「这个输入谁生产」（死锁潜伏两轮的直接原因）。
2. ★★★★ 跨层字段必须有真库往返腿——「读端摘字段」的变异，单元测试
   结构性测不到（不走读端的构造路径）。
3. ★★★ 多列独立聚合 = 可能拼出数据里不存在的组合；「取最差那条」的
   语义必须 DISTINCT ON 整行取，字典序对齐是巧合不是契约。
4. ★★ 同一写回面有两条触发路径（定时/手动）时，防误写的过滤参数必须
   两边对齐——单点路径常漏。
5. ★ 新增异常常量的同一次提交要把消费面（前端映射 + 语言包）一起带上；
   「拉了数据但没渲染」是死消费，API 面保留、消费面收口。
