## 1. 遗留 1：ModalityAccepts ↔ candidateQuerySQLBase 模板级锁步门

**新文件**：`provider/modality_accepts_lockstep_test.go`（3 个测试）。

设计：把 `candidateQuerySQLBase()` 剥注释后的**接受臂原文解析**成
(请求模态 → 登记模态集合) 的结构化判据（`parseModalityArms`），对每一格
(登记, 请求) 与 `ModalityAccepts` 对拍。SQL 判据改语义 ⇒ 对拍当场红；这不再
是「两份 Go 抄本互拍」（第二轮 §1.2 的病根），而是 Go 判据对 **SQL 原文**。

- 对拍域取**运行时事实值域**，不是想象全集：
  - 请求侧 = detectRequestModality 产物（text/vision/audio/video）∪ image
    （/v1/images）∪ ""（无过滤）。`embedding`（/v1/embeddings）**不在域内**——
    它走 `GetCandidatesByModality` 的 SQL 但不进诊断（诊断只在 chat 三协议
    的零候选臂被调）。
  - 登记侧 = models_canonical.modality 的 CHECK 值域
    （text/vision/audio/video/multimodal/embedding）+ 空串（COALESCE 归一）。
    **image 不在登记值域**（admin validModalities 与 DB CHECK 均无 image；
    211 现网实测 0 行）。
- **已知语义分歧，登记不改**（§497「声明的强度要跟量具的强度一致」）：
  Go default 臂在 (multimodal, embedding) 格判 true、SQL 兜底精确臂判
  false——不可达格（诊断入口收不到 embedding 请求值），写进测试头注释。
  若未来 detect/诊断入口扩值域，必须先统一两臂再扩对拍域。
- **变异臂**（测试内 M1/M2/M3 + 真文件两臂）：
  - 真文件 A 臂：改 SQL 接受集（`IN ($3, 'multimodal')` → `IN ($3)`）⇒ 红，
    报出 `(multimodal, video)` 漂移 ⇒ 还原绿。
  - 真文件 B 臂：改 Go default 臂（删 multimodal 通配）⇒ 红，报出
    `(multimodal, vision/audio/video)` 漂移 ⇒ 还原绿，md5 与 HEAD 一致。
- 解析器第一版两个自身缺陷（都写在测试头）：多值列表的 `', '` 里的引号
  不能被 `[^']*` 跨过（要用 `[^)]*` 取整段再拆）；接受集里的 `$3` 占位符
  意思是「请求模态自身」，不展开则每个联合臂都假报漂移。
- 顺带发现：`domains/streaming/model_alternatives.go` 的 `alternativesSQL`
  $5 臂是同一判据的**第二份 SQL 抄本**（含 multimodal 专属臂）；本轮未对
  它做锁步（登记为下一轮可领：三份 SQL 表达 + 两份 Go 表达共五份）。

## 3. 遗留 3：VERSION 旧戳 + DD_BUILD_SHA 远端为空的根因

### 3.1 根因（/version 谎报家族，已实证）

- `/root/llm-gateway-go-211` 是 tar 同步树（`--exclude=.git`，实测
  `git rev-parse` 报 `not a git repository`）。
- 引擎在部署机侧取号：`DD_BUILD_SHA="$(git -C "$DD_REPO_ROOT" rev-parse …)"`
  只在 **--via 路径**成立并由 ssh 行转发 `DD_BUILD_SHA='…'`。
- **目标机直跑**（不经 --via）时：`git rev-parse` 必失败 ⇒ `|| true` 吞掉 ⇒
  DD_BUILD_SHA 为空 ⇒ 下游**三道闸全部静默跳过**：
  ① 槽 version/<slot>.json 的身份改写（`if [[ -n "${DD_BUILD_SHA:-}" ]]` 整段跳过，
  连 warn 都没有）；② 部署后版本核验（`[[ -n … ]] && ! grep` 同样跳过）；
  ③ 切流后公网身份核对（同上）。候选槽于是沿用仓库 version.json 里
  **任意一次 154/245/本地部署留下的旧戳**上生产。
- 现网读数佐证：211 当前活跃槽 b.json = `dc55570a-dirty`（真 sha，--via 路径
  带的号；旧槽 a.json = `28776060`/2893 同理）——**正因为走了 --via 才没谎报**；
  直跑路径没有任何一道闸会拒绝。

### 3.2 修复（`scripts/deploy-seamless-docker.sh`）

目标机直跑（deploy 模式 + DD_BUILD_SHA 未显式给 + 树无 .git）⇒ **fail-closed
die**，报文给两条出路：① 正路 = 从部署机跑 deploy-211.sh（--via 自动取号）；
② 逃生门 = 显式 `export DD_BUILD_SHA=<8位提交号>`（运维声明的身份，日志注明
「身份来自运维声明而非 git」）。有 .git 的本机路径行为不变（原地取号 + 既有
dirty 判定）。`--status/--probe-only/--stop` 不受影响（只对 deploy 模式设闸）。

验证：`bash -n` 语法过；`deploy-211.sh --dry-run` 合同 JSON 正常；
`tests/deploy_211_contract_test.sh` **135 通过 / 0 失败**（含 --via 转发
DD_BUILD_SHA 的既有契约）。

### 3.3 VERSION 旧戳

仓内戳 `a6c7204c/2896`（上次 bump 时的 HEAD）已落后当前 HEAD。按 R168 收口

## 8. 本轮明确没做（留给下一轮，别重复排查）

- **alternativesSQL（$5 臂）的锁步**：同一判据的第二份 SQL 抄本（含
  multimodal 专属臂 `COALESCE='multimodal'`），未纳入本对拍——五份表达
  （candidateQuerySQLBase / alternativesSQL / ModalityAccepts /
  supportedModalitiesFor / 错误载荷 supported_modalities）的统一锁步是
  独立小工程。
- **(multimodal, embedding) 语义分歧的统一**：当前不可达；若统一，Go default
  臂应收窄为精确相等（SQL 兜底臂形态），需先确认没有调用方依赖 multimodal
  通配的宽解释。
- **行为通道对 images/videos/embeddings 端点的铺开**：那些端点的零候选分支
  没有诊断接线（返回通用 503）——是否要接诊断是产品判断，不是守卫缺口。
- **211 部署**：本轮无行为变更需上线（引擎闸是部署时 fail-closed，下次
  部署自然生效）；协议红残留（http_410 连败凭据）的清退属运维处置。
- **测试库重建的脚本化**：本轮手工按记忆配方重建；配方本身在
  pg-verify-environment-gotchas 记忆里，未固化成仓内脚本。
