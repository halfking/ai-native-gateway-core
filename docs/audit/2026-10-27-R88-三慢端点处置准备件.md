## §4 准备件 C：`session-overview` 剩余杠杆 —— rollup vs 服务端缓存

> 前提：R87 已把 DB 侧语句从 10 条降到 6 条（pgss 差分证实），墙钟从 2.994s 降到 ~2.6s；
> ★ **SQL 层候选全部被实测否证**（加 `first_request_at` 索引 / 改连接形态 / 覆盖索引 / 合并 join 腿）⇒ 剩下只有「预聚合」与「缓存」。

| 维度 | **服务端 60s 缓存** | **日粒度预聚合 rollup** |
|---|---|---|
| 墙钟收益 | 命中 ⇒ **~ms 级**（端点墙钟 −99%） | 汇总表每天每租户一行 ⇒ 端点只读汇总 ⇒ **~ms 级** |
| 陈旧语义 | ★ **浏览器本来就有 60s 缓存**（端点已下发 `Cache-Control: private, max-age=60`，`session_overview.go:304`）⇒ **服务端 60s 不引入新的陈旧语义** | 汇总延迟由刷新策略决定（可做「近 N 天实时 + 更早用汇总」的混合口径）⇒ **需要新定义口径** |
| 改动面 | 单文件 `admin/dashboardapi/session_overview.go`（`executor` 字段**本就预留给缓存**，`session_overview.go:29`）；键必须含 `(tenant_id, days, 全部影响口径的参数)`；并发击穿需 singleflight；响应体需 TTL + 上限淘汰 | 新增汇总表 + **写入侧增量维护**（会话数据持续写入 ⇒ 触发式增量或物化视图刷新）+ 历史回填 + 与迁移序列的 **7 点同步面**登记 + 空分区/孤儿行处理 |
| 风险 | 多实例（154/245）各持一份缓存 ⇒ 轻微不一致；击穿未防则雪崩 | ★ **写入路径风险**：汇总错了就是数据错了（R80 已记录「端点变快但数据变错」的教训） |
| 实测依据 | R87 的墙钟读数（2.6s ⇒ 命中即 ~ms） | ★ **未实测**（未建汇总表） |

★ **建议顺序**：**先缓存、后 rollup** —— 理由：① 改动面小、可回滚（去掉缓存即恢复）；② **不引入新的陈旧语义**（浏览器已是 60s）；③ 写路径零风险。
★ 若缓存后仍嫌慢（或要求「更实时的数据」），再上 rollup，并把「近 N 天实时 + 更早汇总」的口径单独交属主定义。

### §5.2 根因链（三项交叉坐实，不是推理）

1. ★ **目标路径必然碰撞**：`domains/dbdegradation/file_writer.go:238-244` 的文件名规则是
   `sessions-<日期>[-NN].jsonl.gz` ⇒ **只含日期 + 进程内序号**，**无 PID / 无实例标识**；
   而轮转序号 `currentSeq` 是**进程内内存计数**（`:131-140`）⇒ **两个进程各自产出 `-01`、`-02` ⇒ 轮转文件同样撞名**。
2. ★ **写端是 `O_APPEND` 且每次 open 新建 gzip 成员**：`file_writer.go:247`
   `os.OpenFile(filePath, os.O_CREATE|os.O_WRONLY|os.O_APPEND, 0600)` + `:253` `gzip.NewWriter(file)`
   ⇒ **每开一次就写一个新 gzip header** ⇒ 同一文件里出现多个 member 与孤儿 header。
3. ★ **蓝绿部署有 20~26s 双活窗口，且两个实例共用同一 env 与工作目录**：
   `deploy/llm-gateway-go.service` 与 `deploy/llm-gateway-go-canary@.service` 的
   `EnvironmentFile=/etc/llm-gateway-go/env` + `WorkingDirectory=/opt/llm-gateway-go` **完全相同**
   ⇒ 同一备份目录；journal 显示 `Started 8782` → `Stopped 8781` **重叠 26s**；
   ★ 两份日志**都**出现 `"file writer: opened new backup file"` 指向**同一个日文件**。
4. ★ **容器硬杀跳过 `gzip.Close()`** ⇒ 尾部截断（`file_writer.go:268-282` 的 `gzip.Close()→file.Close()`
   没有 `Sync()`；且 `os.Exit` 路径与 `TimeoutStopSec=25s` 超时后的 SIGKILL 都会跳过 `defer fileWriter.Close()`）
   ⇒ 2 个「单 member 但 `gzip -t` 失败」的文件 = **纯截断尾单独确证**。

### §5.3 推荐修法（**属主已自动选中「只出方案」这一侧 ⇒ 本轮不改代码**）

| 方案 | 核心 | 兼容影响 | 代价 | 新增门禁 |
|---|---|---|---|---|
| ★ **(a) 分片 + 原子 rename + 每目标路径 flock** | 不再「长开一个文件追加」：每成片（N 条 / T 秒 / M 字节）写**独立完整 gzip** 到 `CreateTemp` 唯一临时名 → `Sync()` → 取当日 `.lock`（flock）→ 取最小空闲 NN → `os.Rename` ⇒ **文件名形状不变** ⇒ **读端零改动** | ★ 读端正则/校验/打捞/归档**全部零改动**；`Date` 字段解析需顺手按正则取（现由「掐头去尾」得出） | 每片多一次 fsync（片频 = N/T，不是每记录）；**必须**在 shutdown 路径 flush+close+rename | G1 禁 `O_APPEND`；G2 必须有 `CreateTemp`+`Sync()`+`os.Rename` 三件套；G3 必须持 flock 且**锁只覆盖 rename**；G4 **行为门**：两个 FileWriter 并发写同一目录 ⇒ 每个产物 `gzip -t` 通过且记录数之和 == 写入总数；G5 写者中途被杀 ⇒ 目录无 0 字节/不可读文件、无临时文件泄漏；G6 打捞口径回归门（老坏文件的打捞记录数**不得变**） |
| (b) 每进程独立文件 + 事后合并 | 每进程写自己的文件，gzip member 原生可拼接 ⇒ 合并 = `cat` | ★ **必须改读端**（`backupFilenamePattern` / `validateBackupFilename` / `ListBackupFiles` 前缀过滤 / `Date` 解析 / `ArchiveFile` / 打捞工具 / 14370-14371 门） | 文件数 ×N ⇒ 摘要与列表成本 ×N | 同 G1~G6 + G7「文件名必须含实例标识」 |
| (c) 只做保留期/归档 | 不动写端 | 无 | 释放磁盘但**不阻止新增坏文件** | ★ **14370 门会红**（其判据 ③ 要求包内**不存在** `os.Remove`/`os.Truncate`）⇒ 落地时必须同步改判据 |

★ **推荐落地顺序**：**先 (a)（纯缺陷修复，不撞属主语义决策，可换二进制回滚）→ 同批做 (c)（4.9 GB + 91% 满是当下风险）→ 再做 per-file 增量缓存 → (b) 不做**。

（★ `cmd/tools/dbdegradation-salvage` 受 14371 门约束：**拒绝**写进 `{base}/backups` ⇒ 只能在旁路目录出料）。

### §5.4 ★★ per-file 增量缓存：**必须排在 (a) 之后**（决定性耦合）

★ 当前日文件被**持续追加** ⇒ size/mtime 每秒变 ⇒ **任何 per-file 缓存对它是永不命中** ⇒ **增量缓存在 (a) 之前根本做不出来**；
★ 只有 (a) 把文件变成**不可变分片**后，「文件身份 = (name, size, mtime)」才稳定。

设计要点：
- **指纹**：每文件 key = `filename`，value = `(size, mtime_nanos, recordCount, sessionIDs)`；分片不可变 ⇒ 该三元组即内容代理（建议加 inode 防 rename-over）。
- **增量算法**：维护 **refcount map** `sessionID → 出现该 id 的文件数`；旧文件的 id `decrement`（归零即删）、新文件的 id `increment`
  ⇒ ★ **删除文件 ⇒ 会话数正确下降**（与「全量重算」口径一致）；`TotalRecords`/`TotalSize` 直接加减。
- **条目存储**：L1 内存 LRU（per-file `{recordCount, sessionIDs}`，⚠ 生产备份记录几乎都是 `request_wal/request_log`（**无 session_id**）⇒ 实际集合为空，但通用形态要设上限：单文件 >50k id 时只存 64-bit 哈希草图并标记「会话维度不可增量」）；L2 **append-only 索引文件** `backups/.index.jsonl`（写端在 **rename 之后**追加一行并 fsync；★ **索引是缓存不是真相源**：读端以目录列表为准，缺条目 ⇒ 现算，末行截断 ⇒ 当作缺失 ⇒ 现算）。
- **摘要合并**：`TotalRecords/TotalSize` 求和；`TotalSessions` = refcount map 的 size（★ **口径不变**：跨文件全局唯一，不是各文件之和 —— `file_reader.go:490-491` 明确要求）。
- **收益**：★ **「指纹变 ⇒ 就地算被 5s 截断」这条 ③ 号路径被消掉** ⇒ 成本从「4.9 GB 全量重算（约 13 min）」降到「一片」⇒ **`degradation/status` 周期性掉到 5s 的根因随之消失**。

## §6 `inspector-stats`（2.765s med）：**零口径变更的修法已实测**

★ 归因（只读，生产数据）：端点只有 **3 条串行 SQL 腿、全部无时间窗的全表聚合**（`admin/session_health_api.go:668-744`）：

| 腿 | 每次调用 | 瓶颈 |
|---|---|---|
| **L1** `session_summaries ⨝ session_dim` 全量哈希连接 | **1,961~2,034 ms（73~76%）** | 861k × 902k 行、无时间窗、无可用索引；双列 `Hash Cond` ⇒ `Batches: 8`（~120MB 溢写） |
| **L2** `AVG(health_score)` | **393~474 ms（15~17%）** | 无 `health_score` 索引 ⇒ 扫 396MB heap，552,804 行被 `IS NOT NULL` 过滤 |
| **L3** `COUNT(*) WHERE status='closed' AND closed_at >= CURRENT_DATE` | **226~281 ms（9~10%）** | 无 `status`/`closed_at` 索引 ⇒ 扫 206MB heap 换来**一个恒为 0 的计数** |

⇒ pgss 差分合计 **2.58~2.79s/次** vs HTTP 墙钟 2.815s ⇒ **Go 侧仅 ~26ms（0.9%）** ⇒ 时间 99% 在 PG；★ **不是** Go 等待、**不是**子预算降级。
⇒ ★ 三条腿 = **同一批表被完整扫了 4 遍**（`session_summaries` 2 遍 + `session_dim` 2 遍）⇒ 「多腿串行累加」是放大器。

### §6.3 三个值得进 LESSONS 的量具坑（本轮取证会话踩到并纠正）

1. ★ PG 的 `E'\s+'` 是**字面量 's'**（不是空白字符类）⇒ 展示正则把 query 文本里的 `s` 全吃掉 ⇒ 文本要用 `E'\\s+'`。
