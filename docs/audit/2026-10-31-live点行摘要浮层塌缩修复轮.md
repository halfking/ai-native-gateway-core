## §1 结论（一句话）

**部署在 llm.itestu.cn 的 /live 点击逻辑本身没有回归**：点左/右栏请求行 = 弹摘要浮层
（RequestZoomPanel）、不开新窗；「查看全景」/行尾 ↗ 才开 `/request-detail/:id` 新窗——
静态 bundle 解析 + 线上 runtime 实测（铸 JWT 注入登录态 + CDP 受信点击）双双证实。
**owner 看到的「点行没有摘要、直接开新窗」的真因是一个 5 轮都没被测到的几何缺陷**：
在 ≤1439px 宽（两栏布局）或较矮的窗口下，头部统计面板吃掉主区高度后，
`.live-topology__body` 的第 1 行（左栏+拓扑）被 `minmax(0,1fr)` 压到 **0px**，
摘要浮层 `max-height: calc(100% - 24px)` 以 0 高列为基准 ⇒ **塌成 16px 的一条缝**
——点行后用户实际上**看不见任何摘要**，只能去点行尾 ↗（直达新窗），
主观上就是「点行直接开新窗」。

## §3 根因（两层叠加）

1. **栅格行无下限**（10-28 那轮修的是「行被 50 行明细撑爆」这一头，
   用 `minmax(0,1fr)` 让行收进视口；本轮塌的是**另一头**：当头部统计面板足够高
   （1280×713 实测 ~450px）而 `.live-topology` 钉死 `height:100%` 时，
   body 只剩 90px，`minmax(0,1fr)` 的 min=0 允许第 1 行整行塌 0。
2. **浮层尺寸依赖 containing block**：`.zoom { max-height: calc(100% - 24px) }`
   以所属列为基准；列塌 0 ⇒ 浮层塌 0。两者叠加 = 点行只剩 16px 一条缝。

## §4 修法（`web/src/views/LiveTopologyView.vue`，纯 CSS）

第 1 行加下限 **`minmax(min(320px, 50vh), 1fr)`**（≥1024 与 ≥1440 两个断点都改）：

- 空间充足时 = 旧版行为完全一致（1fr 吃满剩余）；
- 空间不足时行保住 320px（与既有 `.live-topology__clients { min-height: 320px }` 对齐；
  `min(320px, 50vh)` 在极矮窗口自动放低下限），栅格内容溢出由 `.main-body`
  （`overflow-y:auto`）滚动兜底 —— **宁可滚，不可塌**；
- 浮层随之恢复 ≥296px 可读高度（浮层自身样式一字未动）。

## §8 通用式（详见 LESSONS §593）

1. ★★★★★ 「门绿/部署绿」与「用户看到的行为」之间隔着**用户的视口**——
   同一份 bundle 在 1680×1050 全绿、在 1280×713 浮层塌成一条缝；
   用户报「行为不对」时可能是「几何不对」，几何读数必须按用户实际视口取。
2. ★★★★★ absolute 浮层的百分比尺寸以 containing block 为基准；
   containing block 塌 0 ⇒ 浮层塌 0——「内容在 overflow 里还看得见」会骗过肉眼。
3. ★★★★ 同一处栅格的两种失败模式（撑爆 vs 塌 0）要分开测；修掉一头不等于另一头不存在。
4. ★★★ `window.open` 弹窗拦截只挡非受信点击——CDP synthetic click 会把
   「开新窗」断言打成假红；验证开新窗必须 `Input.dispatchMouseEvent`。
5. ★★★ 无 admin 密码的生产机，铸 JWT（HS256 + SECRET_KEY fallback +
   `/api/auth/me` 验签）→ 种 cookie 是合法走查通道（§586 的复用与扩展）。
6. ★★ 修完先在「生产 DOM + 注入修复 CSS」上验证，再等部署——量具先行的最短回路。
