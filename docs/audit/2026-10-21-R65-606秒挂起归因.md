# R65 轮（2026-10-21）—— `domains/session/v2` 606.375s 挂起归因 ⇒ **根因不是性能，是夹具失配被产品的重试路径放大**

> 触发：R63 轮摸底跑全仓 `go test ./...` ⇒ `domains/session/v2` 整包 **606.375s**
> 且 FAIL。这是 handoff 里挂账项「`TestRequestLogsViewV2EnsureMatchesMigration` 30s 耗时归因」
> 的**更严重版本**。
> 本轮**对生产的写入 = 0**（真库侧只有一次性夹具库，退出即 DROP）。

## §0 一句话结论

**606 秒里没有一秒是「慢」**：整包里已完成的测试最慢 **0.28s**；唯一没结束的那个
（`TestSessionRequestStatusBackfill_GaugeSampledBeforeFirstDrain`）**永远不会结束** ——
它卡在 `run()` 的「探针失败 ⇒ 退避重试」循环里，唯一的出口是 `go test` 的默认 600s 超时。

而让探针**永久失败**的原因，是一个**测试夹具过期**：
迁移 885 把 `sessionRequestStatusRemainingSQL` 从
`SELECT count(*) … JOIN public._request_logs` 改成了 `SELECT 0::bigint`，
**夹具却还在按旧文本匹配**。

⇒ ★★ 本轮同时挖出**两个更硬的东西**：
1. ★★★★ **实现侧有一颗定时炸弹**：885 删掉了 UPDATE 里的 `JOIN public._request_logs l`，
   **却没改 SET 子句** ⇒ 语句仍在写 `l.request_status` ⇒ 别名 `l` 已不存在 ⇒
   **`ERROR: missing FROM-clause entry for table "l"` (42P01)** ——**解析期**错误，
   与 `AND FALSE` 会不会命中任何行**无关**。当时是「候选集恒空 ⇒ UPDATE 永不可达」把它藏住了。
2. ★★★★ **挂起掩盖了另外 3 条红**（在另一个文件里）⇒ 修完挂起才暴露出来。

## §1 归因：606.375s 的完整机制链

### §1.1 第一步：定位到唯一未结束的测试（不是「最慢的测试」）

`go test ./domains/session/v2/ -v -count=1` 写到 717 行后不再增长：

```
=== RUN   TestSessionRequestStatusBackfill_GaugeSampledBeforeFirstDrain
（此后再无输出）
```

- 已 RUN 340 个（含子测试）、已结束 227 个顶层用例；
- ★ **已完成的测试里最慢只有 0.28s**（`TestFileCacheIndexConsistency`）；
- ⇒ ★★ **606 秒不在任何一个测试的「慢」里** ⇒ 判据从「谁最慢」换成
  **「谁没结束」**（RUN 与 PASS/FAIL 集合的差集）。

### §1.2 第二步：抓栈（`-timeout 45s` 单跑，45 秒自杀）

```
panic: test timed out after 45s
	running tests:
		TestSessionRequestStatusBackfill_GaugeSampledBeforeFirstDrain (45s)

goroutine 146 [select]:
...(*sessionRequestStatusBackfill).run(...)
	domains/session/v2/session_request_status_backfill.go:327 +0x32c
...TestSessionRequestStatusBackfill_GaugeSampledBeforeFirstDrain(...)
	domains/session/v2/session_request_status_backfill_test.go:842 +0xf4
```

⇒ 卡点就是 `run()` 的**退避定时器**（`:327` 的 `select`）。

### §1.3 第三步：★ 读到 pgxmock 的**报错原文**（决定性证据）

```
WARN session_turns request_status backfill: remaining count failed
  error="could not match actual sql: \"-- ★ 2026-10-20（迁移 885，v1 族退役）… SELECT 0::bigint\"
         with expected regexp \"JOIN public\\._request_logs l ON l\\.request_id\""

WARN session request_status backfill: source probe failed, will retry
  error="begin source probe: call to method BeginTx(), was not expected,
         next expectation is: ExpectedQuery => expecting call to Query() or to QueryRow():
         	- matches sql: 'JOIN public\\._request_logs l ON l\\.request_id'
         	- is without arguments
         	- returns data: row 0 - [1520530]"
```

★ **这三条错误连起来，就是整条机制链**：

| 步骤 | 发生了什么 | 后果 |
|---|---|---|
| ① | 夹具的期望正则仍写死旧 SQL 文本 | 期望**失配** |
| ② | pgxmock 失配时**不消费**该期望 | 它**卡在队列头** |
| ③ | 后续每一次调用都撞上这个永不满足的 `ExpectedQuery` | 全部报 `was not expected` |
| ④ | 探针因此**永久失败** | 走 `err != nil` 分支，**不**进 `retired` 终态 |
| ⑤ | `run()` 的退避重试 | **永不返回** |
| ⑥ | 测试传 `context.Background()` | 唯一出口 = `go test` 的 **600s** 默认超时 |

⇒ ★★★ **放大器是产品的错误处理路径**：探针失败 ⇒ 退避重试（这是**正确**的产品行为）；
**放大器是夹具与实现的脱节**；**放大器是测试没给 ctx 设时限**。
三者叠乘 ⇒ 一次 1 秒的夹具失配被放大成 **10 分钟的 CI 挂起**。

### §1.4 第四步：根因的提交定位


`git show --stat 5f64031cb -- domains/session/v2/` ⇒ **只改了 1 个文件（实现）**，
**测试文件一行未动** ⇒ ★ **夹具在主干上就带着旧形态**。

## §3 ★★★★ 顺带挖出：**实现侧的真实缺陷**（42P01，定时炸弹）

### §3.1 实测（真库，一次性库 `itgate_r59_shape`）

```sql
BEGIN;
UPDATE public.session_turns t SET request_status = l.request_status
  FROM (VALUES (1::bigint, '2026-10-01'::date, 'x'::text)) AS v(id, partition_date, request_id)
 WHERE t.id = v.id AND t.partition_date = v.partition_date
   AND t.request_status IS NULL AND FALSE;
ROLLBACK;
```
```
ERROR:  missing FROM-clause entry for table "l"
LINE 1: ...PDATE public.session_turns t SET request_status = l.request_...
                                                             ^
```

⇒ ★★★ **这是解析期错误** ⇒ 与 `AND FALSE` 会不会命中任何行**无关**：
**只要有人把这条语句送给 PG，它就炸**。
当时藏住它的是「候选集恒空 ⇒ UPDATE 永不可达」⇒ 一颗定时炸弹：
任何人去掉 `AND FALSE`、或把语句挪到别的路径上，立刻 42P01。

⇒ ★★ **「门红」在这里是**对的**：静态契约门要求 `SET request_status = l.request_status`
**和** `JOIN public._request_logs l …` **同时存在** ⇒ 885 删了 JOIN 却留着 SET ⇒
**门抓住了一个真缺陷**。
⇒ ★★⇒ **通用式：门红了先读门在守什么，再判「是它错还是它对」**（R64 轮的教训是「它错」，
本轮是「它对」）。

### §3.2 修法：`SET request_status = t.request_status`（自赋值）

- 参数个数与形状不变（每行仍 3 个占位）⇒ 夹具与实参不用动；
- ★ **自赋值是恒等的** ⇒ 即使 `AND FALSE` 被误删，**也不会改坏任何标签** ⇒ 双保险；
- 语句在真库上可解析（`PREPARE` 通过）⇒ 42P01 这一类彻底消失。

## §4 ★★ 修法（分两层：治本 + 防复发）

### §4.1 治本：夹具不再「钉文本」，改「钉行为」

pgxmock v4 的匹配器是**池级**的（`ExpectedQuery` 没有自己的 `QueryMatcher`），
所以按期望分派只能从**期望字符串**出发 ⇒ 引入**标记前缀 + 语义匹配**：

```go
const statusRemainingCountTag = "<<remaining-count>>"

func statusBackfillQueryMatcher(expectedSQL, actualSQL string) error {
	if strings.HasPrefix(expectedSQL, statusRemainingCountTag) {
		return matchStatusRemainingCount(actualSQL)   // 按**形状**认：单列 bigint 计数
	}
	return pgxmock.QueryMatcherRegexp.Match(expectedSQL, actualSQL)
}
```

⇒ 夹具从此认「这是一条返回单列 bigint 的计数查询」，**不认它的字面量**。

### §4.2 防复发（三道）

| 门 | 钉什么 | 变异 |
|---|---|---|
| `TestStatusBackfillRuntimeSQLNeverReferencesTheRetiredV1Family` | 运行时 SQL 不得引用已删的 v1 族 | M2 红 |
| `TestStatusBackfillBatchUpdateNeverNamesTheVanishedAlias` | UPDATE 不得引用已消失的别名 | M1 红 |
| `TestStatusBackfillCountMatcherIsNotAnAlwaysYes` | **匹配器本身**不得退化成「永远匹配」 | M3 红 |
| `TestStatusBackfillCommentStripperActuallyStrips` | **剥注释器本身**必须真剥 | M7 红 |
| `TestStatusBackfillTestsNeverHandAnUnboundedContextToTheRetryLoop` | 调 `run()/Start()` 必须传**有界 ctx** | M4 红 |

★ 最后一道是本轮**最便宜也最有效**的一道：它把「600 秒挂起」这类事故的**放大器**直接去掉
（见 §1.3 的第 ⑥ 步）。

### §4.3 ★★ 把「挂起」变成「几秒内的明确失败」

所有调 `run()/Start()` 的测试改传 `context.WithTimeout(…, 5s)`。

⇒ ★★ **可量化的效果**：变异 M5（删掉 `run()` 里的启动采样）⇒ 探针失配 ⇒ 本该挂 600s，
**实测 6.5s 红**（其余变异都是 1.5s）⇒ **有界 ctx 把 600s 换成 5s**。

| 变异 | 期望红的门 | 读数 |
|---|---|---|
| M1 UPDATE 改回 `l.request_status` | `…NeverNamesTheVanishedAlias` | RED 1.5s |
| M2 remaining SQL 改回 JOIN v1 族 | `…NeverReferencesTheRetiredV1Family` + `RemainingSQLContract` | RED 1.7s（2 条） |
| M3 匹配器退化成「永远匹配」 | `…CountMatcherIsNotAnAlwaysYes` | RED 1.4s |
| M4 挂起测试改回无界 ctx | `…NeverHandAnUnboundedContext…` | RED 1.7s |

⇒ 还原核对：**按【原路径】读 md5，两个文件逐字一致**。

### §5.1 ★★ 变异脚本本身翻过两次车（**量具坏了**，不是门坏了）

**v1 脚本的两个缺陷**：

1. ★★★ **`restore()` 把备份拷到了【仓库根目录】而不是原路径**
   ⇒ 源文件**从未被还原** ⇒ M2~M5 是在**未还原的树**上叠加跑的
   ⇒ 而且脚本还在仓库根目录留下了两个野文件；
2. ★★★ **「还原校验」读的是同一个错路径**
   ⇒ 报出「全部逐字一致」的**假读数**（它读的是备份自己）。

⇒ ⇒ ★★★ **通用式：还原校验必须校验【被改的那个路径】的文件**，
而不是「备份那份」或「随便哪个同名文件」。
⇒ 另：v1 还把**编译红**（`declared and not used`）读成了「门有牙」——
⇒ ★★ **编译红 ≠ 断言红**（本仓库的老坑，第 N 次撞上）：M4/M5 的「红」其实来自编译错误，
**必须重做成编译干净的形态**再验。

**v2 脚本**（已修正）：还原按原路径回写 + 每次变异前核对原路径 md5 +
编译红与断言红**分开计数**（编译红 ⇒ 该变异**作废**）⇒ 上面那张表才是有效读数。

### §5.2 ★★★ M6 揭穿了**我自己新写的恒绿门**

M6 第一次跑是 **GREEN** ⇒ 查下去发现：候选查询的契约门断言 `"AND FALSE"`，
而 **`AND FALSE` 这个词同时出现在子句上方的注释里**
⇒ 删掉子句，注释还在 ⇒ 断言照样满足 ⇒ **恒绿门**。

⇒ ⇒ ★★★★★ **断言 SQL 文本前必须【剥注释】**（本仓库的老坑，第 N+1 次撞上）：
★ 剥完之后 M6 才变红。
⇒ 配套：`stripSQLComments` / `executableSQL` 两个助手 +
`TestStatusBackfillCommentStripperActuallyStrips` 这道**量具自身的门**。

1. ⚠ **D9 放行门已经结构性失效**（属主决策项，**本轮未改**）：

   的人会看到一个**永远绿灯**的量表。

   但**没有任何自动化流程在读它**（实测：全仓只有量表定义与两处审计文档提到它）
   ⇒ ⇒ **要么把 D9 门从流程里撤掉，要么给它换一个真实的放行量**（属主决策）。
2. ⚠ **本轮只改了 `domains/session/v2` 一个包的测试面**；
   其它 3 个 FAIL 包（`cmd/tools/sql_source_indirection_audit` / `domains/streaming` /
   `internal/sessionv2mirror`）属**并行会话在制品**，本轮**未碰**。
3. ⚠ **真库门在本机跑过（带 DSN）**，CI 无 DSN 时它会 `t.Skip` ⇒
   **PREPARE 那部分在无库环境下是空跑** ⇒ 静态门是它的常驻替身。

5. ★★ **同族隐患的全仓扫描（已做，结论是「收敛」）**：
   - 精确条件「**同步调用** `.run(context.Background())`」⇒ **全仓 0 命中**

   - `Start(context.Background())` 全仓 36 个文件命中，但**不是同一类**：
     ★ **不等待**的异步启动只会泄漏 goroutine，**测试不会挂**；
