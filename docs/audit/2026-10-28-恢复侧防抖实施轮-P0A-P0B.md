## 1. P0-B：NodeState 判死退避对齐 URSM（消费 disable_count）

**公式（与 URSM v2 `record_request.lua:267-268` 逐操作对齐）**：

```
第 N 次禁用时长 = base_cooldown × 2^(N−1)   封顶 backoff_cap（默认 1800s）
```

URSM 侧原式：`new_cool = cool × 2^disable_count → min(backoff_cap, 1800)`
（幂取递增前的 disable_count，然后 `disable_count+1`）。本轮把同一形状搬进
`credentialfpslot/node_state.go` 的 `recordNodeOutcomeScript`：

- **正常路径禁用**（streak ≥ limit）：`disabled_until = now + disable_cool_seconds(disable_count)`
  （幂取递增前值），再 `disable_count+1`。**首次禁用（dc=0）= 300s，与旧行为
  逐秒相等**——行为漂移只发生在第 2 次及以后的禁用上，这正是防抖想要的。
- **冷却到期 + 失败**（恢复试探失败）：旧行为固定 `now + cooldown` 且**不动
  disable_count**——这是「振荡节点以恒定周期无限翻红」的直接根因。改为同公式
  消费计数（首次到期失败 = 第 2 次禁用 = 600s）+ 计数 +1 + 补写
  `last_disabled_at`（该分支本质是再次禁用，旧代码漏写）。
- **冷却到期 + 成功**：计数归零（既有行为）+ 新写 `recovered_at`（P0-A）。
- **纯 min 封顶**，不加 base 下限——base 被调到超过 cap 时以 cap 为准
  （URSM 同样如此；两套状态面不产生第三种语义）。

**settings 热更键**：`routing.node_disabled_backoff_cap_seconds`
（默认 1800 = URSM `BackoffCapSeconds`，`domains/ursm/v2/config.go:241`；
env `LLM_GATEWAY_ROUTING_NODE_DISABLED_COOLDOWN_BACKOFF_CAP_SECONDS`；
clamp 60~7200；热路径 ≤5s 生效）。默认值下首禁用行为与线上现状逐秒一致。

**顺手修掉的一个既有缺陷**（本轮实读发现）：正常路径禁用分支的
`after_recovery` 判定里 `state.last_success_at > state.last_disabled_at` 是
**死条件**——`last_disabled_at` 在判定前一行已被覆盖为 `now`，条件恒 false。
改为覆盖前先取 `prev_disabled_at`。影响面：`disabled_reason` 的
`consecutive_N_failures_after_recovery` 分类（此前只靠
`recovered_before_disable` 一条路命中）。

## 2. P0-A：恢复期渐进回流量（slow-start 的打分层实现）

**方案原文**（审计档 §4 P0-A）：不动状态机，Breaker 与 NodeState 各记
`RecoveredAt`；评分加 `recoveryPenalty`（默认权重 0.10）；首跳抽签份额乘
线性 ramp 因子（0.2→1.0）。

### 2.1 信号源（两路，取较晚）

| 路 | 粒度 | 介质 | 写入点 | 读取点 |
|---|---|---|---|---|
| breaker.RecoveredAt | (provider, credential) | 进程内存（atomic） | `RecordSuccess`（prev≠CLOSED 时）/ `Reset`；`RecordFailure` 翻红清零 | `Router.CircuitRecovery`（新增窄接口，main.go 装配 `cm`——与 `Executor.Circuit` 同一 Manager） |
| NodeState.recovered_at | (credential, model) | Redis JSON | Lua `cooldown_expired+success` 分支（「实际流量验证恢复」的时刻）；管理面 reset 脚本清 | `c.RoutedNodeState`（filterHealthyNodes 已挂的快照，**零额外 IO**） |

取较晚的一路：候选的总体恢复风险由最晚恢复的那个状态面决定。

**语义边界（如实记）**：
- 「冷却到期但还没等到第一个成功请求」的节点**没有** recovered_at——它要先
  接一个真实请求（失败 ⇒ P0-B 指数再禁用；成功 ⇒ recovered_at 落地、ramp
  起算）。这等价于 HAProxy「rise=1 探测 + 探测成功后 slow-start」的组合，
  P0-A/P0-B 两个半圆恰好扣上。
- Go 读侧 `recoverIfCooldownExpired`（懒翻转）**不**伪造本地 recovered_at——
  到期 ≠ 验证。此处若伪造，评分会把「未验证到期」当「已验证恢复」。
- **URSM authoritative 模式下 NodeState 一路无快照**（filterHealthyNodes 只在
  非 authoritative 跑），但 breaker 一路两种模式都有写入（executor 层
  `Circuit.RecordSuccess` 不分路由模式），ramp 在生产主路径（authoritative）
  上仍生效于凭据级信号。

### 2.2 两个消费面

1. **评分**（failover 顺序）：`calculateLoadScore` 加 `recoveryPenalty`
   （形状同 recencyPenalty：线性 1→0 over ramp 窗口；时钟回拨保守 1.0），
   权重 `LLM_GATEWAY_ROUTING_W_RECOVERY`（默认 0.10，进 `LoadScoreEnvWeights`
   启动期预解析，第 7 个维度）。`LOAD_SCORE_V2` 新增 `recovery_penalty` 字段。
2. **首跳份额**（slow-start 本体）：`firstHopLotteryWeights` 对恢复期候选
   份额乘 `recoveryRampFactor`（刚恢复 0.2 → 窗口边界 1.0），与既有
   p 折算（0.9）叠加、与 `max(1,…)` floor 叠加——满载恢复节点份额下限
   = `max(1, W×0.1×0.2)`，绝不饿死。
   **ramp 因子不进 p 折算**（方案原文：「抽签份额**再乘**线性 ramp 因子」，
   独立于四惩罚折算），`sum<=0`（其余权重全关）时 p=0 不折算、仅 ramp 生效。

**窗口**：`LLM_GATEWAY_ROUTING_RECOVERY_RAMP_SECONDS`（默认 300）。现场 env
读（与 recency horizon 同理由：窗口是运营可动态调整的量）。

**关闭开关**：`W_RECOVERY=0` 或 `RAMP_SECONDS=0` 任一置 0 ⇒ 惩罚恒 0 +
因子恒 1.0 + lottery 返回 nil ⇒ **全链路与现状逐字节一致**（单测钉住）。

### 6.2 抓到并修正的三处缺陷

1. **NodeState reset 脚本的 ramp 语义与 breaker.Reset 相反（真缺陷）**：
   breaker.Reset 写 recoveredAt（手动恢复进 ramp——「未经流量验证的恢复
   恰是 re-flapping 风险最高的时候」是实施轮自己写进注释的理由）；但首版
   `resetNodeHealthStateScript` 却把 `recovered_at` **清零** ⇒ admin 手动
   恢复路由健康（admin/routing.go:2087 ResetNodeHealthState）在熔断面进
   ramp、NodeState 面不进——**同一场景两种语义**。修正：reset 脚本写
   `recovered_at = redis TIME`（与 breaker 对称），新增
   `TestNodeState_ResetWritesRecoveredAt` 钉住。
2. **settings 注册守卫测试没覆盖新键（守卫缺口）**：实施轮加了
   `KeyNodeDisabledBackoffCapSeconds` 的 Spec，但没加进
   `TestThresholdSpecs_RegisteredInPlatformSpecs` 的 want 清单与
   `TestThresholdSpecs_DefaultsMatchLegacyConstants` 的 cases——未来重构
   若弄断 ThresholdSpecs↔PlatformSpecs 接线，该键热更静默失效而测试不红
   （默认值恰与 Lua fallback 同为 1800，失效后更难察觉）。补两清单。
3. **热路径 env 读序（效率）**：首版 `recoveryPenaltyForCandidate`/
   `recoveryRampFactor` 先读 RAMP_SECONDS env 再查信号——绝大多数候选无
   恢复证据，却每候选一次 getenv+ParseFloat。改为**信号前置早退**：无
   恢复信号的候选 0 env 读返回。

### 6.3 补的测试

- `TestNodeState_ResetWritesRecoveredAt`：reset 写 recovered_at（禁用中
  reset → 回池 + 恢复证据落地）。
- firstHop **乘法叠加**用例：低余额（p=1）无恢复 = `int(100×0.1)` = 9
  vs 低余额 + 刚恢复 = `int(9.99…×0.2)` = 1——9→1 证明 p 折算与 ramp
  因子是相乘叠加（若 recovery 被错误放进 p 折算，两者会是同一个数）。
  首版断言写 2 是**笔误**：int() 截断 1.99…= 1（R46 F8② 注明的截断
  语义）——测试断言也要经得起浮点语义的推敲。
- 实施轮的两个测试断言错误（「两路取较晚」期待值写错）已在实施轮当次修正，此处如实记录。
