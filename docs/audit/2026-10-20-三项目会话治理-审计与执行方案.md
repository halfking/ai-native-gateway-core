### 5.4 ★ 一条**量具**教训（本轮亲历两次）

**同一张表 `memory`，两次读数分别是 0 行与 19 行** ——差别不在数据，在**读法**：
`memora` 的表开 `FORCE ROW LEVEL SECURITY`，**不钉租户 GUC 的查询恒返 0 行**：

```sql
-- 读法错（恒 0）
SELECT count(*) FROM memory;
-- 读法对
SET app.tenant_id='default'; SET app.current_tenant='default'; SET app.project_id='memory-bank';
SELECT count(*) FROM memory WHERE tenant_id='default' AND project_id='memory-bank';   -- 19
```

⇒ 二轮审计报告里的「live `memory` = 0 行 ⇒ M-5 的『DB 是权威源』是空的」这条**结论是量具造成的**（审计方未钉 GUC），**已订正**；但其**内核问题成立**（摄取无自动化 ⇒ 漂移无人发现）。
⇒ 同源的另一条：`pg_stat_user_tables.n_live_tup` 对这张表给出 **876**（陈旧估计），真实是 **0**。
⇒ **通用式：判「某表有没有数据」之前，先确认你的读法能穿过该表的隔离策略；`count(*)` 返回 0 有三种成因（真空 / RLS 过滤 / 统计陈旧），必须三者排除。**

### 12.1 B4 的决策与**「不是照抄」**的三处差异

属主选的是**完整移植**（asr 用自己的 embedding 客户端 + 自建 `session_clusters`
表算聚类，插件端点改读本地）。但「完整移植」**不等于**把网关的算法原样搬过来 ——
两个仓的**会话模型不同**，原样搬会得到一个**说谎**的实现。三处差异都写进了
`internal/clustering/clustering.go` 的包注释：

| # | 网关的做法 | asr 的做法 | 为什么 |
|---|---|---|---|
| 1 | 粗键 = `(user_intent, primary_model, key_topics[0])` | 粗键 = `(intent, key_points[0])` | ★ asr 的摘要契约**根本没有 `primary_model` 这个维度**（字段是 title / intent / outcome / key_points / decisions / open_questions / metrics）⇒ 保留一个**恒空的维度**等于在分组键里塞了一个**不含信息**的槽位 ⇒ **删掉它，而不是伪造它** |
| 2 | 向量 = `pgvector` `vector(1024)` | 向量 = **JSONB**，余弦在 Go 侧算 | asr **没有 pgvector 扩展**（`migrations/` 内零命中），且已有同形态的 `session_memory_compressions.embedding` 就是 JSONB ⇒ 保持一致，不引入「装得上但没有索引能力」的依赖 |
| 3 | 一轮 = 按 `cluster_id` **UPSERT** | 一轮 = **整租户替换** | ★ 网关的 `cluster_id` 由**成员集**派生 ⇒ 成员一变就是**另一个 ID** ⇒ 旧行**永远留着**（孤儿累积）⇒ 本仓改成整租户替换，让「簇 X 存在」= 「簇 X 在本租户当前的聚类里」，并让「跑两遍」在**可观测的最终状态**上幂等 |

不变的：两阶段顺序（粗聚类 → 组内向量细分）、余弦阈值 **0.85**、
簇 ID 形状（`cl_` + `sha256(粗键|排序后的成员ID)` 前 8 字节）。

### 12.4 ★ 变异验证抓到的 4 个「门不够硬」——**本轮最有价值的部分**

第一轮变异跑下来 **10 条里只有 6 条真的变红**。逐条查清后发现：**4 条里有 3 条
是判据的问题，1 条是脚本自身的问题**。没有这轮变异，这 4 条判据会以
「绿」的状态被写进文档。

| 变异 | 现象 | 根因 | 处置 |
|---|---|---|---|
| **M1** 粗键丢掉第二个维度 | **编译红**（`declared and not used: topic`） | ★ **编译红 ≠ 断言红**（R65 已吃过一次）⇒ 锚点选错了（改了 `return` 行 ⇒ 变量没人用） | 改锚点为 `topic = point` ⇒ 编译干净且**断言**变红 |
| **M2** 阈值塌成 0 | **锚点 0 次命中** | 阈值常量在 `clustering.go`，脚本却去改 `clusterer.go` ⇒ **变异根本没发生**，测试当然绿 | 改对文件；脚本现在要求锚点**恰好命中 1 次**，否则直接失败 |
| **M4** 一轮不再替换整租户的簇集 | **仍绿** | ★★ 判据太弱：簇 ID 由成员集派生 ⇒ **输入不变**时 UPSERT 与替换**结果完全相同** ⇒ 「不替换」根本观察不到 | 判据改成「**制造一个会消失的簇**」（删掉一条摘要 ⇒ 该簇必须消失且**不留孤儿**）⇒ 立刻变红 |
| **M10** 列表不按租户过滤 | **仍绿** | ★★★ **RLS 才是守卫**：`WHERE tenant_id = $1` 是**纵深防御**，策略照样把行滤掉 ⇒ 去掉谓词**观察不到任何变化** | 换一条策略盖不住的变异（去掉 `OFFSET` ⇒ 分页判据变红）；并在 `store.go` 注释里写明「谓词是纵深防御，策略才是守卫」 |

> ★★ **M10 是本轮最值得记住的一条**：**「这条 SQL 有没有租户过滤」不是可观察属性**
> —— 只要 RLS 开着，删掉过滤**什么都不会变**。⇒ **变异必须打在「策略盖不住」的那一层**，
> 否则你会得到一个「绿得毫无意义」的结论。
>
> ★★ **M4 是第二条**：**判据要制造「状态消失」，而不是「状态重复」** ——
> 因为「内容派生的 ID + UPSERT」在输入不变时**天然幂等**，
> 于是「不替换」这条缺陷**在幂等判据下完全隐形**。
