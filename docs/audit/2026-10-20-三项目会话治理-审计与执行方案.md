### 5.4 ★ 一条**量具**教训（本轮亲历两次）

**同一张表 `memory`，两次读数分别是 0 行与 19 行** ——差别不在数据，在**读法**：
`memora` 的表开 `FORCE ROW LEVEL SECURITY`，**不钉租户 GUC 的查询恒返 0 行**：

```sql
-- 读法错（恒 0）
SELECT count(*) FROM memory;
-- 读法对
SET app.tenant_id='default'; SET app.current_tenant='default'; SET app.project_id='memory-bank';
SELECT count(*) FROM memory WHERE tenant_id='default' AND project_id='memory-bank';   -- 19
```

⇒ 二轮审计报告里的「live `memory` = 0 行 ⇒ M-5 的『DB 是权威源』是空的」这条**结论是量具造成的**（审计方未钉 GUC），**已订正**；但其**内核问题成立**（摄取无自动化 ⇒ 漂移无人发现）。
⇒ 同源的另一条：`pg_stat_user_tables.n_live_tup` 对这张表给出 **876**（陈旧估计），真实是 **0**。
⇒ **通用式：判「某表有没有数据」之前，先确认你的读法能穿过该表的隔离策略；`count(*)` 返回 0 有三种成因（真空 / RLS 过滤 / 统计陈旧），必须三者排除。**

### 12.1 B4 的决策与**「不是照抄」**的三处差异

属主选的是**完整移植**（asr 用自己的 embedding 客户端 + 自建 `session_clusters`
表算聚类，插件端点改读本地）。但「完整移植」**不等于**把网关的算法原样搬过来 ——
两个仓的**会话模型不同**，原样搬会得到一个**说谎**的实现。三处差异都写进了
`internal/clustering/clustering.go` 的包注释：

| # | 网关的做法 | asr 的做法 | 为什么 |
|---|---|---|---|
| 1 | 粗键 = `(user_intent, primary_model, key_topics[0])` | 粗键 = `(intent, key_points[0])` | ★ asr 的摘要契约**根本没有 `primary_model` 这个维度**（字段是 title / intent / outcome / key_points / decisions / open_questions / metrics）⇒ 保留一个**恒空的维度**等于在分组键里塞了一个**不含信息**的槽位 ⇒ **删掉它，而不是伪造它** |
| 2 | 向量 = `pgvector` `vector(1024)` | 向量 = **JSONB**，余弦在 Go 侧算 | asr **没有 pgvector 扩展**（`migrations/` 内零命中），且已有同形态的 `session_memory_compressions.embedding` 就是 JSONB ⇒ 保持一致，不引入「装得上但没有索引能力」的依赖 |
| 3 | 一轮 = 按 `cluster_id` **UPSERT** | 一轮 = **整租户替换** | ★ 网关的 `cluster_id` 由**成员集**派生 ⇒ 成员一变就是**另一个 ID** ⇒ 旧行**永远留着**（孤儿累积）⇒ 本仓改成整租户替换，让「簇 X 存在」= 「簇 X 在本租户当前的聚类里」，并让「跑两遍」在**可观测的最终状态**上幂等 |

不变的：两阶段顺序（粗聚类 → 组内向量细分）、余弦阈值 **0.85**、
簇 ID 形状（`cl_` + `sha256(粗键|排序后的成员ID)` 前 8 字节）。

#### 14.1.3 ★ 判据口径：为什么**不用**填充率

直觉做法是「库里这一列全是 NULL ⇒ 它是死列」。**在开发库上这条判据不可用**：

（`tools` / `host` / `tags` / `client_protocol` …），不是死列 ⇒ 按填充率判据，这道门一上来就红 24 条
⇒ 变成**恒红门** ⇒ 没人看。

⇒ 因此判据改用**写方集合**（静态可复核），填充率只作**旁证**（生产 252 的 0 非空）。

#### 14.1.4 ★★ 本轮最有价值的一步：**门自己抓到自己的恒绿盲区**

第一版的「未登记写路径扫描」腿是**绿的，但它是恒绿的**：变异 M8 摘掉 `is_abandoned` 的登记后，它**仍然绿**。

- 根因：`internal/sessionv2mirror/abandoned_turn.go` 的写方是
  `UPDATE `+tbl+` SET is_abandoned = TRUE` —— **Go 字符串拼接把一条 SQL 拆成了两个字面量**
  （`"...UPDATE "` 与 `" SET is_abandoned = TRUE..."`）⇒ 只扫单个字面量时，
  前者没有 `SET`、后者没有 `UPDATE` ⇒ **整条路径静默丢失**。
- 修法：① 用 `go/ast` 把 `+` 拼接表达式**还原**成一段文本（非字符串部分替换成 `<dynamic>` 标记）；
  ② 动态表名的语句按「**同文件上下 20 行内**出现这两张表的字面量」保守归属；
  ③ 消费子树的条件改成「文本含目标表 **或** 含动态表名标记」——
  ★ 只判「含目标表」会**再次掐死**这条路径（拼接文本里表名**正是**那个变量）。
- 复验：M8 现在 ⇒ **断言红**（精确报出 `is_abandoned ← internal/sessionv2mirror/abandoned_turn.go:213`）
  ⇒ 还原后 md5 逐字一致。

⇒ ★ **LESSON**：「门红了先读门在守什么」的反面是「**门绿了先确认它在守东西**」——
一个**永远绿**的门和一个**恒真**的门，在结果上无法区分，只能靠**变异**逼它表态。

  ⇒ 两条路径互为对照。

### 14.3 asr A-3：变异留痕 + EXPLAIN 收紧 + 补两族

#### 14.3.1 收紧 facts 那条断言

旧断言：`!Contains(plan,"Index Scan") && !Contains(plan,"Bitmap Index Scan")`
⇒ 「Bitmap Index Scan」是「Index Scan」的**子串** ⇒ 整个条件退化成
「计划里出现**任意**索引扫描即可」⇒ **任何**索引（包括与全文检索无关的 btree）都能过
⇒ 判据要的「走 GIN」其实没被钉住。
⇒ 现在指名道姓：必须是 **`idx_facts_search_tsv`**。

#### 14.3.2 补齐另两族 + 新的变异 harness

- 新门 `internal/knowledge/search_index_plan_test.go`（4 条）：
  - `TestMemoryItemsFullTextIndexIsUsable` / `TestKnowledgeFullTextIndexIsUsable`：
    **可匹配性**腿（`enable_seqscan=off` ⇒ 计划里**必须**出现对应的 GIN 索引名）；
  - `TestFullTextIndexesExist`：四个 GIN 索引的**存在性**（无数据依赖）；
  - `TestFullTextIndexCatalogDefinition`：索引**必须是 `USING gin` 且建在 `search_tsv` 上**
    ⇒ ★ 守的是「**存在性 ≠ 可用**」（同名 btree 能骗过存在性检查）。
- 新脚本 `scripts/audit/verify-a3-knowledge-fts.sh`（照 `verify-b4-clustering.sh` 模板）：
  **5 条变异** —— 删掉 4 个 GIN 索引（各自对应腿红）+ 把 facts 的 GIN 换成**同名 btree**（形状腿红）
  ⇒ ★ **§5.1 那句「确实变异验证过」从此在仓内可复核**。

#### 14.3.3 ★★ 新发现：A-3 判据的适用面比审计以为的**窄**

实测（PG17，20000 行种子，读真实 `EXPLAIN`）：

| 族 | 生产查询形状的计划 | 结论 |
|---|---|---|
| `facts` | `Bitmap Heap Scan` → `Bitmap Index Scan on idx_facts_search_tsv` | ✅ **走 GIN**，判据成立 |
| `memory_items` | `Seq Scan on memory_items` + `Filter: (search_tsv @@ …)` | ❌ **不走 GIN** |
| `knowledge_documents` / `knowledge_versions` | 两个 `Seq Scan`，FTS 条件成了**连接后的 Filter** | ❌ **不走 GIN** |

- `memory_items` 的原因（量化）：GIN 路径成本 **2134.04** > seq scan **1181.00** ⇒ planner 选顺序扫描
  ⇒ 把 planner 逼到只能用索引（`enable_seqscan=off`）时，GIN **能被匹配**（`Bitmap Index Scan on
  idx_memory_items_search_tsv`）⇒ ⇒ **索引没问题，是成本模型的选择**。
  ⚠ 且带不带 `tenant_id` 过滤会改变结果：带过滤时 planner 先满足 `tenant_id`（那张表上有以 tenant_id
  打头的 btree `idx_memory_items_review`），GIN 只剩 Filter ⇒ 能力腿的查询**刻意不带租户过滤**。
- `knowledge_*` 的原因（结构性）：生产谓词是
  `(d.search_tsv @@ q OR v.search_tsv @@ q)` —— **OR 跨两个关系** ⇒ PostgreSQL 无法把它下推成
  单表索引条件 ⇒ 两个 GIN 在生产形状下**用不上**。
- ⇒ ★★ ⇒ **「A-3 判据满足」这句话要改口径**：它**只在 `facts` 一族成立**；
  另两族成立的是「索引在、且能被同一个 FTS 谓词匹配」。
  ⇒ **处置需属主拍板**（① 改谓词形状：拆成两条单关系谓词 / UNION；② 接受现状并把判据改写；
  ③ 对 knowledge 族改成「先查标题再查正文」的两段式）⇒ **本轮只登记，不改产品**。
- ⚠ **一个被实测推翻的假设**：「`m.search_tsv` 的**别名限定**挡住了索引匹配」——
  实测 `facts` 带不带别名都用 GIN、`memory_items` 带不带别名都用 Seq Scan
  ⇒ 变量是**表 × 谓词形状**，不是限定写法。（这条假设若成立，改一行就能修好整个问题 —— 幸好先测了。）
