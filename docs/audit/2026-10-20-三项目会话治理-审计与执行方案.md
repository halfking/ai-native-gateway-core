### 5.4 ★ 一条**量具**教训（本轮亲历两次）

**同一张表 `memory`，两次读数分别是 0 行与 19 行** ——差别不在数据，在**读法**：
`memora` 的表开 `FORCE ROW LEVEL SECURITY`，**不钉租户 GUC 的查询恒返 0 行**：

```sql
-- 读法错（恒 0）
SELECT count(*) FROM memory;
-- 读法对
SET app.tenant_id='default'; SET app.current_tenant='default'; SET app.project_id='memory-bank';
SELECT count(*) FROM memory WHERE tenant_id='default' AND project_id='memory-bank';   -- 19
```

⇒ 二轮审计报告里的「live `memory` = 0 行 ⇒ M-5 的『DB 是权威源』是空的」这条**结论是量具造成的**（审计方未钉 GUC），**已订正**；但其**内核问题成立**（摄取无自动化 ⇒ 漂移无人发现）。
⇒ 同源的另一条：`pg_stat_user_tables.n_live_tup` 对这张表给出 **876**（陈旧估计），真实是 **0**。
⇒ **通用式：判「某表有没有数据」之前，先确认你的读法能穿过该表的隔离策略；`count(*)` 返回 0 有三种成因（真空 / RLS 过滤 / 统计陈旧），必须三者排除。**
