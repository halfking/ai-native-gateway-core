# 2026-10-29 nvidia 直通事故轮：参数兼容学习闭环（厂商感知 nativepair + learnedTTL 可配）

> goal 会话。用户报障：经 llm.itestu.cn（211）请求 nvidia 的 `z-ai/glm-5.3-flash`
> 经常碰到 `{"message":"Validation: Unsupported parameter(s): `reasoning`","type":"Bad Request","code":400}`，
> 要求：检查日志分析 → 修正不同模型的思考模式参数 → 碰到这类错误自动回退（剥参重试）→
> Redis 记录需拿掉的参数（**时效 1 小时**）→ 后续请求发送前先查该 (供应商, 模型) 的
> 参数兼容缓存并前置剥离 → 缓存定期失效以利再探测。

## §0 摘要（结论先行）

1. **剥参-重试-学习-预剥离管线本仓早已有且在生产工作**（`internal/reqprobe` +
   `internal/paramrefusal` + executor 接线）：211 实测 53 个事故请求全部被
   「400 点名 → 剥参 → 免费重试」救回（客户端最终 200），Redis
   `llmgw:reqanom:records` 里的学习记录（`param=reasoning,enable_thinking`、
   `recovered_count=1`）完好。
2. **真正的根因是 2026-10-28 原厂直通轮的「按模型名前缀判原厂对」**：
   `nativepair.Match(zcode, "z-ai/glm-5.3-flash")` 命中（glm 前缀）⇒ nvidia 候选
   首发全参数透传，且**直通腿豁免「学习式预剥离」**（executor_chat.go
   `if !nativePair { reqprobeApplyLearned(...) }`）⇒ 学习记录永远无法回应用于
   预剥离 ⇒ **永不收敛**：每个 ZCode 请求都要吃两轮 400 剥参重试
   （~600KB body × 2 次白费往返，TTFB 29s+；01:27–01:31Z 五分钟窗口 36 次 400、
   53 个请求 ×2 轮）。用户偶尔看到的原始 400 即该族在轮次耗尽/其它窗口的透传。
3. **参数兼容性是【端点 API 形状】的属性，不是模型权重的属性**：ZCode 的
   `reasoning`/`enable_thinking` 是智谱线格式参数，nvidia 的 OpenAI 形状端点不认
   （`thinking`/`reasoning_effort` 却容忍——剥完前两者后 200 实证）。10-28 验证档
   §10.1 自己登记「第三方宿主路由 + 厂商参数组合部署后尚未自然出现，待自然复现」
   ——本轮就是那次自然复现，结论推翻「按模型名判原厂对」。
4. **修法**（两处，均落地）：
   - ★ **nativepair 厂商感知**：`Match(clientType, catalogCode, outboundModel)`，
     每条原厂对登记**原厂 catalog code 集**（glm→{zhipu,glm,bigmodel,zai} 等，
     与 paramreg.catalogToDialect 同源）⇒ nvidia/其它已知厂商/空 catalog 中继
     一律不再直通 ⇒ 正常路径（paramguard + 方言裁剪 + **学习式预剥离**）生效。
     nvidia 腿在正常路径上：`enable_thinking`/`thinking` 被 RejectedByUnknown 裁、
     `reasoning` 还原后由 Redis 学习记录**首发前剥掉**（记录已在，部署即收敛）。
   - ★ **learnedTTL 可配 + 默认 24h→1h**（`LLM_GATEWAY_REQPROBE_LEARNED_TTL`，
     默认 1h）——即用户要求的「时效 1 小时、定期失效再探测」；过期代价 = 每
     (provider, model, wire) 每窗口一跳 400 剥参重试，换取兼容状态持续再确认。
5. **真原厂对（zcode→zhipu 等）行为不变**：仍首发全参数（10-28 生产验证 85/85
   保真）；第三方宿主回归 10-28 之前的正常适配路径（该路径本就被 r1021 政策与
   reqprobe 学习兜底）。

## §2 211 生产取证（2026-10-29 00:04–01:32 UTC）

- **报错原文**（Redis 台账 error_sample，与用户粘贴逐字一致）：
  `{"message":"Validation: Unsupported parameter(s): `enable_thinking`","type":"Bad Request","code":400}`
  / 同形 `reasoning`。NVIDIA 一次只点名一个参数（round1 enable_thinking、round2 reasoning）。
- **请求形态**：`POST /v1/chat/completions`，UA `ZCode/3.16.3 ai-sdk/provider-utils/4.0.39`，
  body ~650KB（369 messages），出站 `z-ai/glm-5.3-flash` @ provider 18（nvidia，
  integrate.api.nvidia.com），wire=openai-completions，流式。
- **五分钟窗口（01:27–01:31Z）读数**：z-ai/glm-5.3-flash 上游 400 ×36；
  「retrying with params stripped」×112（round1 ×56 / round2 ×56，无 round3）；
  53 个唯一 request 全部「probe retry recovered」且客户端终态 200——**机制在救，
  但每个请求都白付两轮往返**（例 rid 92df028c：TTFB 29.4s / 总 35.1s，其中两轮
  400 各 ~8–10s）。
- **学习闭环断裂的实锤**：同一时间窗「applying learned param strips」×13 全部只有
  `prompt_cache_key`——`reasoning,enable_thinking` 的学习记录在 Redis 里
  （id 9/10/11 等，occurrences 246/257、recovered_count=1、last_seen 持续刷新），
  但**从不回应用于预剥离**。逐行核对：出事故的请求（nativePair 腿）连
  「applying learned」日志都不打——executor_chat.go `if !nativePair` 把学习应用
  与 paramRefusalApply 一起豁免了。
- **为什么学习不收敛是「设计如此」**：10-28 直通轮注释「原厂直通对不预剥离
  （首发永远全参数；上游拒绝由本请求内的 4xx 剥参重试回退），否则一次瞬态 400
  会让原生参数被静默剥离 24h」。该顾虑对**真原厂端点**成立（已验证），对
  **第三方宿主**是灾难：nvidia 对 ZCode 参数的拒绝是**必然**而非瞬态。
- request_logs 侧：近 7 天 `upstream_status_code=400` 记录为 0（400 被剥参重试

  10-28 验证档亦记录了同形 nvidia 3 连 upstream_down。

## §3 机制盘点（既有资产的接线面）

```
客户端 body（ZCode 全家桶参数）
  └─ executor_chat.ExecuteOpenAI
       ├─ nativePairFor(params, cand, body) ──→ nativepair.Match   ← ★ 事故点（只看模型名）
       ├─ finalizeOpenAIUpstreamBodyNative(nativePair)
       │     └─ IR parse→serialize + restoreExtensions
       │           ├─ nativePair=true  → Extensions 全量原样还原（NativePassthrough）
       │           └─ nativePair=false → paramreg.Decide 按目标方言裁/译/还原
       ├─ if !nativePair → reqprobeApplyLearned（Redis 学习参数首发前剥离）← ★ 被豁免
       ├─ if !nativePair → paramRefusalApply（进程内 24h 记忆）
       └─ 4xx 终端分支 → reqprobe.Diagnose → StripParamsForWire（多轮，≤3）
             → 重试成功 → RecordTerminal(recovered) → Redis 学习（本轮修 TTL）
```

关键事实核对：
- `RefusedOptionalParam`/`Diagnose` 对 NVIDIA 文案（kimi 形态 `Unsupported
  parameter(s): \`reasoning\``）**提取正常**（211 日志 named_param=reasoning 实证，
  本轮又以事故原文加了回归断言）。
- `reasoning`/`enable_thinking` 均在 `optionalLearnFamily`（拒绝即学习白名单），
  非骨架 ⇒ 可学、可剥。
- `resolveTargetDialect`：TargetProvider="nvidia" 不在 catalogToDialect →
  **DialectUnknown**（不做协议回退）⇒ 正常路径上 `enable_thinking`/`thinking`
  （RejectedByUnknown）被裁、`reasoning`（KindIRHandled 无方言守卫）被还原。
  nvidia 对 `thinking`/`reasoning_effort` 容忍（剥完 reasoning/enable_thinking
  后 200 实证）⇒ 正常路径的出站形态对 nvidia 是**安全的**，唯 `reasoning` 由
  学习剥离收口（Redis 记录已在，部署即收敛）。

## §4 修法

### 4.1 nativepair 厂商感知（根修）

`internal/nativepair`：`pairRules` 一行一对 `{client, modelPrefix, homeCatalog}`；
`Match(clientType, catalogCode, outboundModel)` 要求模型族匹配 **且** 候选
CatalogCode ∈ 原厂集：

| 对 | 模型族 | 原厂 catalog 集 |
|---|---|---|
| zcode | glm | zhipu / glm / bigmodel / zai |
| minimax-code | minimax | minimax / minimaxai |
| deepseek-code | deepseek | deepseek / deepseek-ai |
| claude-code | claude | anthropic |

- 第三方宿主（nvidia / openrouter / siliconflow / apiclaude …）与**空 catalog
  中继**（联界/智码形态）一律不直通 → 回归 10-28 之前的正常路径（该路径有
  r1021 RejectedByUnknown + reqprobe 学习双兜底，战损检验过）。
- 两个调用点（executor_chat / executor_anthropic 共用的 `nativePairFor`）只改
  一处：传 `cand.CatalogCode`。
- 真原厂对（zcode→zhipu）行为零变化：直通、首发全参、学习豁免——10-28 生产
  验证 85/85 保真的场景原样保留。

### 4.2 learnedTTL 可配 + 默认 1h

- `learnedTTL` 常量 → `sync.OnceValue` 函数：env `LLM_GATEWAY_REQPROBE_LEARNED_TTL`
  （Go duration），默认 `1h`，非法回退默认。Redis/Memory 两 Store 同步改调用。
- 记录保留期（Redis 30d）与异常台账不受影响——**学习资格窗口**与**记录留存**
  是两件事，只动前者。
- 过期语义（用户要求的「不停探测」）：TTL 过期后该 (provider, model, wire) 的
  下一请求首发全参 → 若上游仍拒绝 → 一跳 400 剥参重试 → 重新学习并刷新窗口；
  若上游后来支持了该参数 → 首发即 200，规则自然沉寂。

### 4.3 有意不动（如实登记）

- **真原厂对的学习豁免**维持（10-28 产品决策 + 生产验证）；1h TTL 使「瞬态 400
  固化」的老顾虑窗口从 24h 缩到 1h。
- paramreg 注册表未加 nvidia 专属 RejectedBy：注册表是方言粒度（DialectUnknown
  覆盖所有未知中继），nvidia 专属硬拒登记会误伤其它未知中继；学习系统正是为
  此存在（仓内教义：无跨端点实证不登记）。
- `maxParamStrips=3`、剥参重试免费、`LLM_GATEWAY_REQPROBE_LEARN` 总开关均不动。
