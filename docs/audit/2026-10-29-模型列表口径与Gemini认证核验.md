## 二、模型列表口径改造（Part 1）

### 2.1 为什么默认只列特色模型

仓内早就有「特色/精选模型」这个一等概念，而且**四处都以它为准**：

| 位置 | 用途 |
|---|---|
| `autoroute/popularity_weight.go` | 路由排序的 `FeaturedBonus` 加权 |
| `bg/shared_pick.go` | 选凭据时的「featured 优先」 |
| `domains/streaming/model_alternatives.go` | 候选建议的 tier-2 |
| `admin/routing.go` | 管理侧「精选」过滤 |

而 `/v1/models` 此前**无条件输出全量**（生产实测 685 条）⇒ 客户端拿到的是一份
没有优先级、没有上下文长度、名字还带供应商后缀的清单。
⇒ 精选清单才是「这个网关推荐什么」的答案；全量清单只是「技术上能路由什么」。

### 2.2 口径的来源与优先级

```
请求参数（?scope=… / ?all=…）  >  运维默认（models.list_scope，热加载）
```

- 请求参数优先于运维默认：运维设的是「默认」不是「上限」——需要全量的客户端不必等运维改配置。
- `models.list_scope`（新设置，`TypeEnum{featured,all}`，默认 `featured`，热加载）= **逃生舱**：
  改它即可让默认回到全量，**无需发版**。与 r1027 的 `models.list_only_routable` 同款形状
  （公开契约的默认值变更必须可无发版回退）。

### 2.3 落到 SQL 的形状（`domains/streaming/models_scope.go`）

- 精选过滤是**同一个查询里的一个布尔参数** `$1`，**不是第二份 SQL 常量** ⇒
  十几条活度门只存在一份（第二份必然漂移 —— r1027 的契约测试就是为此写的）。
- **两个发现查询都带同一份过滤**（`modelsRoutableSQL` 与 `modelsLegacySQL`）：
  scope 与活度源是**正交**的两件事，翻活度开关不得顺带改变公布哪些模型。
- 匹配**三种名字形态**：`canonical_name` / `raw_model_name` / `standardized_name`。
  ★ 只认 canonical 名是不够的：`bg/shared_pick.go` 解析「featured 优先」时认的是
  供应商侧的名字 ⇒ 只认 canonical 会让**路由当特色、发现当不存在**的模型被藏起来
  （客户端没法选它看不见的东西）。

### 2.4 ★★ 本轮最值钱的一处：PostgreSQL 的 SRF 先于 LIMIT 展开

写成一行会静默只认**一个**模型：

```sql
-- ✘ 错：target list 里的 set-returning function 先展开，LIMIT 1 只留下数组的第一个元素
SELECT LOWER(unnest(featured_models)) AS name
FROM routing_policy WHERE tenant_id='default' ORDER BY id LIMIT 1;
```

正确形状是**先把行钉住、再展开数组**（两个 CTE）：

```sql
WITH policy  AS (SELECT COALESCE(featured_models, ARRAY[]::TEXT[]) AS names
                 FROM routing_policy WHERE tenant_id='default' ORDER BY id LIMIT 1),
     featured AS (SELECT LOWER(unnest(names)) AS name FROM policy)
```

★ 这条**纯文本判据钉不住**（两种写法都「含 unnest 且含 LIMIT」）⇒ 必须真库跑。
本轮已加真库判据（见 §四），并留了结构级判据（policy 不得含 unnest、featured 不得含 LIMIT）。

### 2.5 安全降级：精选口径筛不出模型 ⇒ 退回全量

两种很不一样的情况都会让精选口径产出**空**：

- (a) 运营的精选清单为空（或 `routing_policy` 那行不在）；
- (b) 精选模型当前**全都不可路由**。

两种情况下正确答案都是「这里是我们能路由的全部」，**不是**一张空清单 ——
发现端点回空会打断所有读它的客户端（模型选择器、SDK 健康检查、挑默认模型的工具）。

★ 降级是**可见**的：`slog.Warn`，并走**第二次查询**；快照仍按**请求口径**缓存
⇒ 之后数据库故障时，同一个口径会得到与在线路径相同的答案。

### 2.6 缓存按口径分槽（`ModelsHandler.stale`）

精选过滤在 SQL 里 ⇒ 查询结果本身随口径变化。缓存若只有一格，一次「精选」请求填进去的
快照会在故障期间被「全量」请求当成「这就是全部」端出去（= **静默少报模型**）。
⇒ 两个口径各存各的快照；某个口径没有快照时，行为与「从未缓存过」一致（显式 500）。

## 三、Gemini 认证核验（Part 2）

### 3.1 厂方文档怎么说（本轮实读并留证）

| 来源 | 原文要点 |
|---|---|
| [Gemini API reference](https://ai.google.dev/gemini-api/docs/api-overview) | "**All requests to the Gemini API must include a `x-goog-api-key` header with your API key.**" |
| [Using Gemini API keys](https://ai.google.dev/gemini-api/docs/api-key) | REST 示例：`-H "x-goog-api-key: YOUR_API_KEY"` |
| [OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai) | 兼容端点 `https://generativelanguage.googleapis.com/v1beta/openai/…`，鉴权是 `-H "Authorization: Bearer GEMINI_API_KEY"` |

⇒ **两个端点的厂方契约不同**：原生端点用 `x-goog-api-key`（+ `?key=`），
OpenAI 兼容端点用 `Authorization: Bearer`。

### 3.2 本仓实现（复核结论：正确）

| 方向 | 实现 | 判定 |
|---|---|---|
| 入向（客户端 → 网关） | `internal/auth.ExtractClientKey`：Bearer → `x-api-key` → `x-goog-api-key` → `?key=`（`?key=` 仅在 Gemini 原生路径生效） | ✅ 与厂方契约一一对应 |
| 出向（网关 → 厂方） | 走厂方 **OpenAI 兼容端点**（`.../v1beta/openai`），executor 统一 `Authorization: Bearer <cand.APIKey>` | ✅ 与兼容端点文档一致 |

★ **出向用 Bearer、入向收三种，不是「不一致」，是「两个端点的契约本来就不同」**。

### 3.3 ★ 本轮实际修掉的一处：仓内厂方文档缺一种形态

`docs/vendor-formats/gemini.md` 的「注意」原文只有一句：

> API key 通过 query string 或 `Authorization: Bearer` 头传递。

⇒ **漏了厂方强制的 `x-goog-api-key` 头形态**（同仓 `docs/QUICK_REFERENCE.md` 的 Gemini
示例用的恰恰是这个头 —— 仓内两份文档彼此就不自洽）。
⇒ 本轮已订正该文档，并把三种形态、优先级、`?key=` 的**路径限定**理由、
以及「模型列表」一节（原生形状 + scope 口径）补齐。

### 3.4 顺带核到的另一处不一致

`docs/06-deployment/01-environments/154-production-release-checklist-20260905.md`
把「`/v1/models` 模型数与 245 同级（245 实测 685）」当**部署放行标准**。
⇒ 默认口径改成 featured 后，这个读数**必然变小** ⇒ 按原文判会读成「掉模型」而误回滚。
⇒ 已改为**两个口径分列**（默认口径 vs `?scope=all` 全量口径），并写明「变少是预期的」。

## 六、通用式（详见 `LESSONS.md` §557）

1. ★★★★ **公开契约的默认值变更，必须配一个「无发版回退」的逃生舱**（请求参数 + 热加载设置）。
2. ★★★★ **SQL 里 target list 的 set-returning function 先于 LIMIT 展开** —— 写成一行只取到
   数组第一个元素，而**纯文本判据钉不住**（两种写法都含 unnest 与 LIMIT）⇒ 必须真库判据。
3. ★★★ **「两份拷贝必然漂移」**：过滤做成查询里的**一个布尔参数**，不要做成第二份 SQL 常量。
4. ★★★ **降级必须可见**：筛不出结果时退回全量 + WARN，而不是静默换口径或交空清单。
5. ★★★ **缓存要按口径分槽**：口径进了查询，缓存就不能只有一格（否则会静默少报）。
6. ★★ **仓内厂方文档要与厂方原文逐条对拍** —— 本轮就是仓内文档漏了 `x-goog-api-key`
   才被发现的；「读一遍原厂文档」要读**逐字**，不是读个大概。
7. ★★ **开工前先读当前树**：本轮开工时的 `AGENTS.md` 快照比当前树旧 4 天，
   按快照得出的「Gemini 认证没做」是**过期结论**。
