# 2026-11-23 用量趋势折线图「加载完成后被清空」——根因归档（布局塌陷，非数据清空）

> **一句话**：折线图**从未**被清空——是**画布被 flex 压成 0 高**（canvas 渲染高度 0）。
> 上一轮把它判成「loadSeries 的 catch 清空 series」是**误诊**，据此做的修复无效。
> 本轮用「线上 bundle 对拍 + jsdom 探针 + 浏览器内实测高度」三路取证定案，改的是 CSS 布局，不是数据流。

## 二、上一轮的误诊（为什么「改了 catch 却没修好」）

上一轮提交 `f32fb368d` 把 `UsageTrendExplorer.vue` 的 `loadSeries` catch 块改成：

```js
} catch (err) {
  if (token !== seriesToken) return
  // series.value = []      ← 注释掉
  error.value = surfaceError(err)
}
```

结论写的是「请求失败时保留已有数据，避免图表在排行榜加载时被清空」。
**这个结论是错的**，理由是它把「排行榜加载完成」与「图表消失」之间的**相关性**当成了**因果**。

### 三路证伪

| 证伪手段 | 结果 |

| **线上 bundle 对拍** | 把 211 容器内 `UsageTrendExplorer-CLQRdfs1.js` 拉下来反解，catch 分支实际是 `catch(e){if(a!==j)return;F.value=ue(e)}` —— **确无清空动作**，且该 bundle 与本地构建同名同大小（17608B，md5 一致）⇒ 修复**确实已上线**却**无效** |

⇒ 数据从未被清空。**真因必须在渲染/布局层。**

## 三、真因：定高 flex 列里的布局塌陷

### 3.1 现场实测（211 生产页，浏览器内量得）

| 元素 | 实测 | 说明 |
|---|---|---|
| `.ute` 容器 | **610px** | `display:flex; flex-direction:column; height:100%; overflow:hidden` |
| `.ute__rankings` | **1304px** | `flex:0 0 auto` ⇒ **永不让步**；6 张 Top5 卡片撑出来的自然高 |
| `.ute__table` | 160px | `flex:0 1 34%; min-height:160px` ⇒ **有下限** |
| `.ute__chart` | **26px** | `flex:1 1 auto; min-height:0` ⇒ **整个列里唯一可无限收缩的项** |
| `.mtc` | **0px** | 图表根容器 |
| `canvas`（渲染高） | **0px** | CSS `height:100% !important` ⇒ 父容器 0 ⇒ **画布 0** |
| `canvas`（Chart.js 内联） | 607px | Chart.js 以为自己有 607px ⇒ **两边对不上** |

### 3.2 因果链

```
① .ute 是「定高(610px) + overflow:hidden」的 flex 列
② .ute__rankings = flex:0 0 auto ⇒ 1304px 且**不可收缩**（不让步）
③ .ute__table    = flex:0 1 34% + min-height:160 ⇒ 有下限
④ .ute__chart    = flex:1 1 auto + min-height:0  ⇒ **唯一可无限收缩项**
   ⇒ 兄弟一长高，缺口全部压在它身上 ⇒ 26px ⇒ .mtc 0px
⑤ canvas 的 CSS 是 height:100% !important（压过 Chart.js 的内联 height）
   ⇒ 父容器 0 ⇒ 画布渲染高度 0 ⇒ 肉眼 = 「折线图被清空」
⑥ .ute 的 overflow:hidden 把多出来的 1304px **直接裁掉**（用户也够不着）
```

### 3.3 为什么「先显示、后消失」

排行榜加载**中**时 `.ute__rankings` 只有 ≈150px（标题 + 加载占位）⇒ 图表拿得到几百 px ⇒ **显示出来**；
排行榜加载**完**（+1304px）才塌 ⇒ **消失**。

接口耗时实测坐实了这个时序：

| 接口 | 耗时 |
|---|---|
| `GET /api/admin/usage/trend-series` | **0.06–0.17s**（快 ⇒ 先画图） |
| `GET /api/admin/usage/top-rankings` | **0.68–0.85s**（慢 5–10 倍 ⇒ 后插网格 ⇒ 后塌） |

⇒ 「数据一来图就没」= 「排行榜卡片一插进来图就没」。**与数据本身无关。**

## 四、修法（3 条 CSS + 1 条钉测）

改动文件：`web/src/views/admin/UsageTrendExplorer.vue`（**纯 CSS，零 JS 逻辑改动**）

```css
/* ① 图表区硬下限（桌面端此前漏了，≤768 断点一直有） */
.ute__chart { flex: 1 1 auto; min-height: 280px; }

/* ② 排行榜不再独占空间：可收缩 + 有上下限 + 内部滚动 */
.ute__rankings {
  flex: 0 1 auto;          /* 原 flex-shrink:0 = flex:0 0 auto */
  min-height: 180px;
  max-height: 34%;
  overflow: auto;
}
/* ②b 标题在内部滚动时保持可见 */
.ute__rankings-title { position: sticky; top: 0; z-index: 1; background: var(--card); }

/* ③ 残差滚动可达，而不是被裁掉 */
.ute { overflow: auto; }   /* 原 hidden */
```

**两个易被忽略的点**：

1. `overflow:auto` 不只是「能滚」——它还把 flex 项的**自动最小尺寸**从 `min-content` 降为 **0**。
   不加它，`.ute__rankings` 的 `min-height:auto` 会反过来顶住图表（缩减量根本不够）。
2. `min-height:180px` 在排行榜上是**必需**的：只给 `max-height` 时，矮视口里它会被压成 34px 的细条，
   「有滚动条但几乎看不见」比「看不见」更糟（用户不知道下面还有内容）。

### 钉测

新增 `web/src/views/admin/UsageTrendExplorer.layout.spec.ts`（4 条）：

1. `.ute__chart` 必须有 `min-height ≥ 280px`
2. `.ute__rankings` 必须有 `max-height:%` + `overflow:auto`，且**不得**再是 `flex-shrink:0` / `flex:0 0 auto`
3. `.ute` 必须是 `overflow:auto`，不得是 `hidden`
4. `.ute__chart` 不得出现 `min-height:0`

> **为什么是源码级 CSS 断言而不是组件测试**：jsdom **没有布局引擎**（所有元素高度恒 0），
> 组件逻辑测试也证明图表组件是稳定的（见 §2）。这类塌陷在单测里**天然不可见**，
> 只能把 CSS 契约钉住。

## 五之二、二次调整轮（owner 追加诉求：「全部展开 + 页面不内部滚动」）

> owner 在根修轮之后追加：**「这个页面不需要内部滚动，需要将所有的列表展开，不要在列表内滚动。」**
> 这一条把根修轮的方案 ②（排行榜 `max-height:34%` + `overflow:auto`）**变成了反向需求**——
> 它确实修好了塌陷，但代价是把 6 张 Top5 卡片关进了一个 180px 的小窗口。
> ⇒ 二次调整的思路不是「把图表撑大」，而是**把排行榜放开 + 把滚动责任上移**。

### 改法（4 处 CSS）

| # | 位置 | 改前 | 改后 |
|---|---|---|---|
| ① | `App.vue` `.main-body--fill` | `overflow:hidden`（内容被裁） | `overflow-y:auto; overflow-x:hidden`（**页面级滚动**） |
| ② | `.ute` | `flex:1 1 auto; min-height:0; height:100%; overflow:auto` | `flex:0 0 auto; min-height:100%; height:auto; overflow:visible`（**高度由内容决定**） |
| ③ | `.ute__table` / `.ute__rankings` | `max-height` + `overflow:auto`（内部滚动） | `flex:0 0 auto` + 无 `max-height` + `overflow:visible`（**整段铺开**） |
| ④ | `.ute__chart` | `flex:1 1 auto` | `flex:0 0 280px`（**高度唯一确定**） |

同时移除上一轮为内部滚动加的 `.ute__rankings-title{position:sticky}`（已无内部滚动容器）。

### 两条被钉住的新不变量

1. **「不内部滚动」必须与「外层能滚」成对。** 只放开列表而页面自己不滚 ⇒ 内容超出视口后**无处可滚＝被裁**，
   等于换了个姿势的同一缺陷。⇒ 钉测第 ⑤ 条跨文件断言 `.main-body--fill` 必须承担滚动。
2. **内容驱动的页面要显式 `flex:0 0 auto`。** 默认 `flex-shrink:1` 会在内容超高时把本页压回一屏高、
   内容溢出容器并与下一段**重叠**（不是滚动，是叠字）。

### 源码级 CSS 契约解析踩的三个坑

1. **分组选择器**：`.ute__chart,\n.ute__table { … }` —— 用 `indexOf('.ute__table {')` 会命中分组里那一行，
   拿到的却是另一个选择器的规则体（背景/边框那组）⇒ 必须按「选择器列表逐项匹配」。
2. **@media 里的同名规则在文件里更靠后** ⇒ 「取最后一条」会取到断点内的覆盖值而非桌面端基线
   ⇒ **只扫顶层（花括号深度 0）**。
3. **注释里的字面量 `<style>`**：让 `/<style[^>]*>([\s\S]*?)<\/style>/` **从注释处开始匹配、把整段脚本吞进来**
   ⇒ 提取时必须取**最后一个** `<style` 标签（本仓 `.vue` 注释里出现 `<style>` 字面量并非孤例）。

## 六、通用式（本轮沉淀）

1. ★★★★★ **「元素消失」先量高度，再怀疑数据。** 现象是「图没了」，默认假设是「数据被清空」——
   于是去改数据流（catch、token、竞态），改三遍都不对，因为**数据一直都在**。
   先量 `getBoundingClientRect().height` 与 `canvas` 渲染高，一步就能分叉两条路。
2. ★★★★ **JS 库的内联尺寸与 CSS 的 `!important` 会互相覆盖，两边都可能与肉眼不一致。**
   本例 Chart.js 内联 `height:607px`，CSS `height:100%!important` 把渲染高压到 0。
   只看库自己报的尺寸（或只看 DOM 属性）会得出「图表正常」的**反向错误结论**。
3. ★★★★ **「兄弟区块一长高，我就被压没」是定高 flex 列的经典塌陷。**
   判据：谁是唯一 `min-height:0` 的项，谁就是被压的那个。
   修法不是给被压项调参，而是**让长兄弟可收缩/可滚动**（`overflow:auto` 同时降自动最小尺寸）。
4. ★★★ **「先有后无」的时间相关性会伪装成因果。** 本例「排行榜加载完成」与「图表消失」同时发生，
   于是被写成「排行榜加载把 series 清空了」。**把两个独立机制绑成因果，要靠排除法**：
   bundle 对拍（有没有清空代码）+ 组件探针（有没有竞态）+ 接口实测（数据对不对）—— 三路都排除才敢换方向。
5. ★★★ **`<canvas>` 塌成 0 高时，人眼看到的是「空白区域」而不是「报错」。**
   这类缺陷没有任何错误日志、没有任何告警，**只有量高度才能发现** ⇒ 关键可视化元素应有高度下限断言。
6. ★★ **`overflow:hidden` 是「内容消失」，`overflow:auto` 是「内容可达」。**
   定高容器里宁可滚动也不要裁：裁掉的部分用户既看不到也够不着。
