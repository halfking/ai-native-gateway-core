### P1 ★ gpt-5.6-sol 三连 400「Unsupported parameter: 'temperature'」无自愈

- **现象**：T1 首跑 503；上游 `/v1/responses` 三次 400 同 body_digest，
  错误体 `{"error":{"message":"Unsupported parameter: 'temperature' is not
  supported with this model.",...,"code":"invalid_request"}}`。
- **根因拆成四环（一事故链）**：
  1. **D1 剥参保护集过宽**：`internal/reqprobe/strip.go` 的 `coreParams`
     把 temperature 列为「永不触碰」——上游**明确点名**拒绝也不剥，
     免费剥参重试拿不出可剥清单 → 静默不触发。
  2. **D2 400 落 transient**：该错误形态不匹配任何专用正则 →
     `ClassifyResponseStatus` 默认 KindTransient → 同 body 盲重试三连 +
     节点被拉黑风险。
  3. **D4 流式腿 502 包 4xx 无人解包**：Vapeur 聚合中转在**流式**出站腿
     把上游真实 4xx 缓冲后重发成 HTTP 502
     （`{"error":{"code":"stream_error","message":"400|{原错误JSON}"}}`），
     外层 502 被收编 KindUpstreamDown：请求侧错误当节点故障，
     node_probe_state 3 连败 + 300s 退避 → 候选清空（db_empty）→
     整个模型停 5 分钟（实测 07:31-07:36 gpt-5.6-sol 不可路由）。
     且流式 5xx 走 `uErr != nil && StatusCode >= 500` 分支对不可重试
     kind 直接 return，**到不了 reqprobe 诊断门**。
  4. **D5 诊断器不认 chat 腿值拒绝形态**：chat 腿（流式首跳）400 文案
     `Unsupported value: 'temperature' does not support 0.2 with this
     model.`（无 "for"、动词是 "does not support"）两条点名正则都断链。
- **修复**（四处，全部带判据 + 变异验证红→绿）：
  - D1 `strip.go`：新增 `skeletonParams`（点名路径只保护结构骨架
    model/messages/input/stream/tools/tool_choice/stream_options），
    采样参数（temperature/top_p/stop/max_tokens…）在**上游明确点名**时
    允许剥。无名兜底路径行为不变（coreParams 照旧）。
    判据：`TestStripParamsNamedTemperatureRecoversVapeurIncident` 等。
  - D2 `errorsx/classify.go`：新增 `unsupportedParamRe`
    （"Unsupported parameter: 'x'" / "Unknown parameter: 'x'" /
    "Unrecognized request argument" / 括号复数），400/422 → KindClientBug
    （两个分类器同判）。判据：`classify_unsupported_param_test.go` 五件套。
  - D4 `errorsx/stream_unwrap.go` 新增 `UnwrapStreamWrapped4xx`
    （判形保守：`NNN|` 前缀 4xx + 余下为完整 JSON 对象）；
    两个分类器入口 5xx 先解包递归；executor 两处诊断门按解包后
    状态/错误体走；`uErr!=nil && 5xx` 分支入口解包成功即改写 resp 落回
    常规 4xx 流程（attemptLog 已先记真实 502）。判据：
    `stream_unwrap_test.go` 三件套（含 5xx 内层不解包的负例）。
  - D5 `internal/reqprobe/diagnose.go`：点名正则补
    「Unsupported value: 'x' 冒号前缀」形态 + 动词表补 "does not
    support"；paramRejectionHints 补 "unsupported value"。
    判据：`diagnose_value_form_test.go`。
- **验证**（部署 2573/2577 后）：
  - T1/T1b/T2 三项全绿：T1 200+tool_calls；T1b 三轮工具循环最终中文
    总结（18℃/393.67/光伏报告三合一）；T2 流式 10 帧、三个工具
    name/arguments 分片完整、finish_reason=tool_calls。
  - 同请求内自愈日志实证：`upstream rejected request, retrying with
    params stripped (temperature)` → `probe retry recovered the request
    (param_rejected)` —— 不再依赖学习规则的 60s 负缓存。
  - redis 学习台账对照：修复前记录 id=8（occurrences=3, recovered=0,
    kind=transient）vs 修复后 id=9（kind=client_bug, recovered=1）。
- **波及面评估**：D1 语义收窄仅影响「上游点名」路径；D2/D4 只新增
  分类分支不动旧路径（5 项负例）；D5 仅加形态。executors 全量回归绿
  （43.9s），errorsx/reqprobe/ir/paramguard/paramreg/reasoncap 全绿。

### P2 ★ phone_intl 正则把算术 `+100` 当国际电话，响应侧改写工具参数

- **现象**：T2 流式 tool 参数增量里模型回写的 `(23*47+100)/3` 到达
  客户端变成 `(23*47[REDACTED:phone])/3`。
- **根因**：DB `pii_patterns.phone_intl`
  `\+\d{1,3}[-\s]?\d{1,14}` 第二段只要 1 位数字，回溯后任意「加号+数字」
  （算术、分数、版本号）都命中；响应侧 write-time
  `redact_body` → `outputcompliance.Checker` 按此表遮蔽 message.content
  与流式工具参数。**数字和消歧实验证明请求侧完好**（模型能答出表达式
  数字和 17，即上游收到原文），遮蔽全部发生在响应侧——对按 JSON 解析
  工具参数执行的 agent 客户端是实体故障。
- **修复**：迁移 **857**（canonical + installer 五点同步 + 通道腿）：
  正则收窄为 `\+\d{1,3}[-\s]?\d{7,14}`（被叫号码 ≥7 位，E.164 现实
  区间）。选收窄而非停用（区别于 851 对 ip_address 的裁决）：国际电话
  是真实 PII 类别且可按位数精确切分；误漏极短号的代价低于误伤所有
  「+数字」算术。UPDATE 存活 316 幂等重放。
- **验证**：部署 2577（迁移已应用，`schema` 层确认 regex 已更新）后
  E2E：`(23*47+100)/3` 原样到达客户端；`+1 5551234567` 仍正确遮蔽为
  `[REDACTED:phone]`；`+8613812345678` 仍遮蔽。
- **顺带发现（登记不修，与 Vapeur 转换无关的存量合规怪癖）**：
  1. 裸手机号 `13812345678` 在同路径**不被遮蔽**（phone_cn_mobile
     未生效于该路径）——潜在 PII 漏遮，待 owner 裁决。
  2. `+8613812345678` 双规则重叠匹配产出残缺嵌套标记
     `[REDACTED:phone]hone]`（intl 与 cn_mobile 对同一数字串的交叠
     替换互踩）——输出形态缺陷，待 owner 裁决。

### P7 ★ reqprobe 剥参一次性守卫 × OpenAI 系逐参数报错 = 多未知参数死局

- **事故链（request c7a2565a，09:02，2581）**：混合方言客户端同时带
  `thinking:{type:enabled,budget_tokens}` + `enable_thinking:true` →
  unknown-relay fail-open 双双还原出站 → Vapeur 400 点名 `enable_thinking`
  → 剥参免费重试（第一轮）→ 再 400 点名 `thinking` → **剥参守卫
  paramTried 已消耗** → client_bug 上抛 503。OpenAI 系校验器一次只报
  一个未知参数，N 个未知参数需要 N 轮，一次性守卫在第二个参数上死局。
- **修复**：`reqProbeRuntime.paramTried bool` → `paramStrips int`
  （上限 maxParamStrips=3，剥参重试仍不耗 attempt 预算但封顶上游调用）；
  `strippedAccum` 累计各轮剥掉的参数，成功时随 diag.Param 一并学习
  （LearnedParams 按逗号拆分原生支持）——只学最后一个的话同形态请求
  每个都要再吃一轮 400 才收敛。
- **判据**：`TestExecuteOpenAIReqProbeMultiRoundStripRecovers`
  （httptest 假上游逐参数报错：3 跳收敛 + 学习记录
  `enable_thinking,kimi_future_param` 双参数）。变异验证：守卫回到
  一次性即红。
- **E2E（2588）**：事故原形态（grok-4.6 + thinking + enable_thinking）
  200 正常作答；responses 原生客户端带 thinking（R1 字节透传路径，
  主动层管不到）同样经两轮剥参 200。
