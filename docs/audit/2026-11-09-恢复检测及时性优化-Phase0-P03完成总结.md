## 核心发现

### 1. F-A/F-B 已在生产工作 ✅

**这改变了实施路径**：
- 原计划：实施 P0-1 (F-A) + P0-2 (F-B) + P0-3 (featured)
- 实际路径：跳过 P0-1/P0-2，直接执行 P0-3

**证据**（211 日志实测）：
- `balance_floor_guard` 检测到 credential 41 配额部分恢复并触发探测
- `credential_probe_v2` 对 credential 50 在主模型失败后成功用 fallback 模型恢复

### 2. 问题不只在免费凭据

**数据显示**：
- 免费凭据可用率: 98.7% > 全局 81.6%
- P50 探测间隔正常 (3h)，但 P95/P99 极端 (11-27 天)

**真正根因**：
- 探测优先级机制缺失
- 无流量模型（无论付费/免费）都会掉入长尾
- featured 标记是解决方案核心

### 3. 双数据源设计

**并存而非替换**：
- `routing_policy.featured_models` (租户级配置，已有)
- `models_canonical.featured` (全局模型属性，新增)
- 两者都进 `fs.static` 集合

**优势**：
- 向后兼容（不破坏现有 routing_policy 配置）
- 分层管理（运营可通过 DB 直接标记，无需改 routing_policy）
- 渐进迁移（可逐步将模型从 routing_policy 迁到 models_canonical）

## 技术亮点

### 1. fail-open 设计

```go
// DB 读失败时放行（恢复探测不能被读抖动卡死）
if err != nil {
    slog.Warn("model_tier: load canonical featured failed; keeping previous featured set",
        "error", err)
    return  // 保持旧集合，不覆盖为空
}
```

### 2. 幂等迁移

```sql
-- 使用 DO 块 + IF NOT EXISTS
DO $$ 
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM information_schema.columns 
        WHERE table_name = 'models_canonical' AND column_name = 'featured'
    ) THEN
        ALTER TABLE models_canonical ADD COLUMN featured BOOLEAN NOT NULL DEFAULT FALSE;
    END IF;
END $$;
```

## 经验教训

### 1. Phase 0 取证的价值

**如果没有 Phase 0**：
- 会重复实施 F-A/F-B（浪费 1-2 天）
- 可能误判问题在免费凭据（数据显示免费凭据可用率更高）
- 无法量化改进效果（缺少基线）

**Phase 0 的投入**：
- 0.5 天取证
- 发现 F-A/F-B 已部署
- 识别真正根因（探测优先级机制）
- 建立量化基线

**回报**：
- 节省 1-2 天重复工作
- 精准定位问题
- 可测量的验收标准

### 2. 日志是最好的证据

**对比**：
- 代码审查：看到 commit 存在，但不知道是否部署
- 数据库查询：看到数据状态，但不知道原因
- **日志分析**：看到实际行为，证明功能在工作

**示例**：
```
2026/11/09 02:07:33 WARN balance_floor_guard: credential quota-suspended 
  but vendor plan windows have capacity; dispatching recovery probe
```
这一行日志证明了 F-B 不仅部署了，而且正在触发。

### 3. 长尾问题需要分位数指标

**如果只看平均值**：
- P50 = 3h ⇒ "探测间隔正常"
- 会错过 P95/P99 的 11-27 天

**使用 P50/P95/P99**：
- P50 正常 ⇒ 大部分绑定 OK
- P95/P99 极端 ⇒ 长尾有严重问题
- **这正是「~24h 未感知恢复」的数据证据**

## 风险与缓解

### 风险 1: Featured 模型过多导致探测量激增

**缓解**：
- 初始标记仅 26 个模型
- 主要是免费/入门级（本就应该高优先级）
- Featured 只影响 probe scope，不是「全部重新探测」

**监控**：
- 部署后观测探测调用量
- 如果 >2× 基线，考虑减少 featured 模型数量

### 风险 2: 数据库读失败导致探测停止

**缓解**：
- fail-open 设计：DB 读失败时放行（保持旧集合）
- 不会因为一次读抖动就把恢复探测挡掉

**监控**：
- 观测 model_tier 日志中的 WARN
- 如果频繁出现读失败，检查 DB 性能

### 风险 3: 迁移 953 应用失败

**缓解**：
- DO 块 + IF NOT EXISTS（幂等）
- 部署后立即验证（检查列是否存在）

**回滚**：
- down 迁移已准备好
- 或简单 UPDATE featured = FALSE
