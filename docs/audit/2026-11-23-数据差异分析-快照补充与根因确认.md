## 三、根因分析

### 3.1 时区边界问题

**现象**：
- 2026-11-18 快照请求数（26,391）**大于** usage_facts（22,905）
- 其他日期快照请求数**小于** usage_facts

**根因推测**：
1. **快照聚合使用 UTC 时区边界**
2. **usage_facts 查询使用 Asia/Shanghai 时区边界**
3. **时差 8 小时导致日期边界错位**

**证据**：
- 11-18 多出 3,486 请求 ≈ 11-17 少的 3,987 请求的一部分
- 说明 11-17 晚上 20:00-24:00（UTC 12:00-16:00）的请求被计入了 11-18

### 3.2 数据完整性问题

**费用差异异常大的原因**：
```
请求数差异：-4.7%
费用差异：-42.9%
```

**可能原因**：
1. **成功请求缺失更多**：
   - usage_facts 中成功请求产生成本
   - 快照可能主要缺失成功请求，而保留了失败请求

2. **高成本模型请求缺失**：
   - 缺失的 8,257 请求中，可能大部分是高成本模型（如 GPT-4）
   - 这些请求产生了 $3,653 的成本

3. **cost_amount 字段统计口径不同**：
   - usage_facts 使用 `cost_amount`（供应商成本）
   - report_snapshots 使用 `estimated_cost_cents`（可能是不同口径）

### 3.3 验证时区问题的SQL

```sql
-- 验证：UTC 边界 vs 系统时区边界
-- 11-18 UTC 00:00:00 = 11-18 CST 08:00:00
SELECT 
    DATE(occurred_at AT TIME ZONE 'UTC') as utc_date,
    DATE(occurred_at AT TIME ZONE 'Asia/Shanghai') as cst_date,
    COUNT(*) as requests
FROM usage_facts
WHERE occurred_at >= '2026-11-17 00:00:00+00'::timestamptz
  AND occurred_at < '2026-11-19 00:00:00+00'::timestamptz
GROUP BY 
    DATE(occurred_at AT TIME ZONE 'UTC'),
    DATE(occurred_at AT TIME ZONE 'Asia/Shanghai')
ORDER BY utc_date, cst_date;
```
