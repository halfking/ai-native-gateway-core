## 二、费用差异 42.9% 的根本原因

### 2.1 总体对比

| 维度 | 差异 | 说明 |
|------|------|------|
| **请求数差异** | -4.7% | 相对较小 |
| **费用差异** | **-42.9%** | **异常大** |
| **比例不匹配** | **9.1 倍** | 费用差异是请求数差异的 9 倍 |

### 2.2 成功 vs 失败的费用分布

**实测数据**（2026-11-17 到 2026-11-23，usage_facts）：

| 状态 | 请求数 | 总费用(USD) | 平均成本 |
|------|--------|-------------|----------|
| success | 89,227 | **$8,522.76** | **$0.0955** |
| failure | 84,915 | $5.78 | $0.0001 |
| rate_limited | 226 | $0.00 | $0.0000 |
| **总计** | 174,368 | $8,528.54 | $0.0489 |

**关键发现**：
- ✅ **成功请求占 51.2%**，但产生了 **99.93% 的费用**
- ⚠️ **失败请求占 48.7%**，但只产生了 **0.07% 的费用**
- ✅ **成功请求的平均成本是失败请求的 955 倍**

### 2.3 费用差异的三层原因

**原因① 时区边界错位导致高成本请求被漏计**

**11-17 晚上 20:00-24:00（UTC 12:00-16:00）**的请求：
- 应该计入 11-17 CST（系统时区）
- 但被计入了 11-18 UTC（快照）
- 这部分请求中**包含大量成功请求**

**证据**：
```
11-17 CST 费用：$2,127.73
11-17 UTC 费用：$843.57
差异：-$1,284.16 (-60.3%)
```

**原因② 快照缺失的主要是成功请求**

**逐日分析**：
- 总请求数差异：-8,257（-4.7%）
- 总费用差异：-$3,653.29（-42.9%）
- **推断**：缺失的 8,257 请求中，大部分是成功请求

**验证**：
```
如果缺失请求的平均成本 = 总体平均成本：
-8,257 × $0.0489 = -$403.77

实际费用差异：-$3,653.29

差异：-$3,653.29 / -$403.77 = 9.0 倍

结论：缺失请求的平均成本是总体平均成本的 9 倍
     → 缺失的主要是成功请求（$0.0955）而非失败请求（$0.0001）
```

**原因③ estimated_cost_cents 计算口径不同（次要）**

**11-18 费用对比**：

| 数据源 | 费用(cents) | 费用(USD) |
|--------|-------------|-----------|
| usage_facts.cost_amount × 100 | 98,675.03 | $986.75 |
| report_snapshots.estimated_cost_cents | 105,438.33 | $1,054.38 |
| **差异** | **+6,763.30** | **+$67.63** |
| **差异比例** | **+6.9%** | **+6.9%** |

**代码验证**（`domains/reportrollup/rollup.go:290`）：
```go
COALESCE(SUM(f.cost_amount) * 100, 0)::numeric(24,6) AS cost_cents
```

**结论**：
- ✅ 计算公式正确：`cost_amount × 100`
- ⚠️ 但 11-18 快照费用**比实时数据多 6.9%**
- **原因**：混合了两种时区边界的数据（如前文分析）

### 2.4 完整的因果链

```
UTC 时区边界（旧快照）
  ↓
日期边界错位 8 小时
  ↓
11-17 晚上的请求被计入 11-18
  ↓
11-17 缺失 3,987 请求 / -$1,284（高成本时段）
  ↓
11-18 多出 3,486 请求（但不是同一批）
  ↓
总请求数差异：-4.7%
总费用差异：-42.9%（缺失的主要是成功请求）
```

## 四、对账数据不及时的问题分析

### 4.1 当前架构

**数据流**：
```
usage_facts (实时写入)
    ↓
RollupDay worker (每日凌晨 02:00 UTC 聚合)
    ↓
report_snapshots (快照表)
    ↓
供应商对账页面 (查询快照)
```

**延迟**：
- **写入延迟**：请求完成后立即写入 `usage_facts`（实时）
- **聚合延迟**：每日凌晨 02:00 UTC（北京时间 10:00）聚合昨日数据
- **查询延迟**：前端查询快照表（无额外延迟）

**总延迟**：**最长 24 小时**（今天发生的请求，明天 10:00 才能在对账页面看到）

### 4.2 延迟影响分析

**场景1：用户在下午 15:00 查看对账页面**
- 看到的是昨天及之前的数据
- **今天 00:00-15:00 的 15 小时数据看不到**
- 延迟：15 小时

**场景2：用户在早晨 09:00 查看对账页面**
- 看到的是前天及之前的数据（昨天的快照还未生成）
- **昨天 00:00-24:00 的 24 小时 + 今天 00:00-09:00 的 9 小时数据看不到**
- 延迟：33 小时

**场景3：看板实时查询**
- 看板直接查 `usage_facts`（实时）
- **延迟：0**

### 4.3 为什么不能实时？

**设计权衡**（`domains/reportrollup/rollup.go:5-8`）：
```go
// 数据流：usage_facts（请求级真相源）→ RollupDay 按天聚合成**八个** scope
// 的快照行写入 report_snapshots → 区间汇总读面只读快照行按任意时间区间
// （日/周/月/自定义）二次汇总。日维度落地一次、区间汇总不回扫原始请求日志。
```

**原因**：
1. **性能**：`usage_facts` 是请求级表（百万行），实时聚合太慢
2. **一致性**：快照一次生成，多次查询结果一致
3. **多维度**：需要按 8 个 scope 预聚合，实时聚合成本太高

### 4.4 优化方案对比

| 方案 | 延迟 | 性能 | 实现成本 | 推荐 |
|------|------|------|----------|------|
| **A. 保持现状** | 24h | ✅ 快 | ✅ 低 | ⭐⭐⭐ 适合对账 |
| **B. 增加"实时模式"** | 0 | ⚠️ 慢 | ⚠️ 中 | ⭐⭐ 适合监控 |
| **C. 缩短聚合周期** | 1h | ⚠️ 中 | ⚠️ 中 | ⭐⭐ 折中方案 |
| **D. 混合模式** | 0/24h | ✅ 快 | ⚠️ 高 | ⭐⭐⭐⭐ 最优 |

### 4.5 推荐优化方案：混合模式（D）

**设计**：
- **历史数据**：查询 `report_snapshots`（快照，快速）
- **今日数据**：查询 `usage_facts`（实时，慢但必要）
- **前端合并**：两部分数据在前端合并显示

**实现**（伪代码）：
```go
func handleReportRollupSummary(...) {
    start, end := parseRange(r)
    today := settings.SystemDayStart(time.Now())
    
    var historicalData, todayData Report
    
    // 查询历史快照（start 到 yesterday）
    if start.Before(today) {
        historicalEnd := today.AddDate(0, 0, -1)
        historicalData = querySnapshots(start, historicalEnd)
    }
    
    // 查询今日实时数据（如果 end >= today）
    if !end.Before(today) {
        todayData = queryUsageFactsRealtime(today, end)
    }
    
    // 合并
    return mergeReports(historicalData, todayData)
}
```

**优点**：
- ✅ 历史数据仍然快速（查快照）
- ✅ 今日数据实时可见（查 usage_facts）
- ✅ 兼容现有架构，渐进改造

**缺点**：
- ⚠️ 今日数据查询较慢（但可接受，只影响当天）
- ⚠️ 需要前端合并逻辑

**时间线**：
- **短期**：先修复时区问题（见第五节）
- **中期**：实现混合模式（1-2 周）
- **长期**：考虑引入缓存层（Redis）
