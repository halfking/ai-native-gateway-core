## §1 根因链（每一环都有读数）

### §1.1 匹配形态：`%q%` ⇒ 等值索引天然用不上

`admin/session_catalog_usage.go:118`：

```go
func likeContains(q string) string {
	...
	return "%" + replacer.Replace(q) + "%"     // ★ 前缀 + 后缀都有 ⇒ 中缀匹配
}
```

⇒ ★★ **中缀匹配** ⇒ `session_summaries` 上的 `session_key` **等值索引**（pkey /
`unique(tenant_id, session_key)`）**用不上**；★ 而 `pg_trgm` 索引**根本不存在**。

### §1.2 索引面：252 生产实测

```
pg_trgm 扩展          = 1（★ 已装 ⇒ 修法不需要装扩展）
全库 trigram 索引数   = 8（★ 在别的表上）
session_summaries 上 title 索引         = 0
session_summaries 上 primary_model 索引 = 0
session_summaries 上 session_key 索引   = 只有等值索引（pkey / (tenant_id, session_key)）
```

⇒ ★★ **`title` / `primary_model` 零索引** ⇒ ★★ **三列 OR ⇒ 规划器无法把任何一支变成索引条件**
⇒ ⇒ **放弃全部索引 ⇒ Seq Scan**。

### §1.3 ★ 决定性对照实验（同一张表、同一条件、只改列数）

★ 生产 252，`EXPLAIN`（**不带 ANALYZE** ⇒ 不执行）：

| 变体 | 计划 |
|---|---|
| **A** 三列 OR（真实形态） | `Limit → Gather Merge → Sort (last_request_at DESC) → **Parallel Seq Scan on session_summaries**` |
| **B** 只查 `session_key` 一列 | `Limit → Gather → **Parallel Index Only Scan using session_summaries_pkey**` |
| **C** 等值 `session_key = 'x'` | `**Index Only Scan using session_summaries_pkey**`（Index Cond） |

⇒ ★★★★ **加两列 OR（`title` / `primary_model`）就把索引优化掉了** ⇒ ★★★
⇒ ★★ 这是「三列 OR ⇒ 规划器放弃索引」的**教科书级生产实证**。

### §1.4 ★ 真实执行耗时（`EXPLAIN ANALYZE`，只读 SELECT，90 s 保护）

```
Parallel Seq Scan on session_summaries (actual rows=34 loops=3)
  Rows Removed by Filter: 289543
  Buffers: shared hit=34435 read=17177
Planning Time: 16.679 ms
Execution Time: 40415.968 ms
```

★ ★★ **40.4 秒**。★ ⚠ 在此之前先用 `statement_timeout='10s'` 跑过一次 ⇒ **直接超时**，
★ ⇒ ★★ **这不是「慢一点」，是「根本跑不完」**。

### §1.5 ★ 与 2 秒超时的相乘 ⇒ 静默假阴性

★ `mergeCatalogSearch`（`admin/session_catalog_usage.go:210`）：

```go
ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
hits, err := h.db.Query(ctx, catalogSearchHitsSQL, ...)
if err != nil {
    slog.Warn("catalog search failed", "err", err)
    return items          // ★★ 静默降级：返回【不含搜索命中】的列表
}
```

⇒ ★★★ **40.4 s ≫ 2 s ⇒ 必然超时 ⇒ 必然走这条分支** ⇒
⇒ ★★★ **用户在会话搜索框里输任何词，都得到「没搜到」**，★ 而**没有任何用户可见的错误提示**。

★ ★★ **这就是「超时会静默降级成假阴性」**：★ **一个「搜索无结果」的界面，
★ 看起来和「确实没有匹配」一模一样** ⇒ ★★ **最难发现的一类故障**。
