# r1027 —— /v1/models 只列真正可路由的模型（发现端点活度源与路由对齐）

> 会话轮：2026-10-14 00:30–01:40（本仓 llm-gateway-go-4）。用户指令：把
> 「/v1/models 只列出真正有 provider 的模型」做掉，从源头避免客户端选中死模型。
> 背景：r1026 轮排查确认 grok-4.6 主链路健康后，剩余用户面失败来自
> 客户端按发现列表/旧配置选中死模型（opencode 对 minimax-m2.7-quickspeed
> 的固定辅助请求每次 400 invalid_model；grok-4.7 no_candidate 503）。

## 根因：发现端点与路由使用两张不同的活度表

旧查询（domains/streaming/models.go serveFromDB）以
`model_offers.available = TRUE` + `credentials.status='active'` +
`providers.enabled` 为门。而路由实际走
`credential_model_bindings.available` + `credentials.availability_state /
quota_state` + URSM v2 视图。故障阶梯（探测失败/余额耗尽/协议失配）只翻
后者——`model_offers` 永远说 available。

生产实测（154，共享库直查）：

- 旧列表 **620** 个模型，含 nvidia nemotron 全家族（cred 19 协议失配
  http_404）、glm-5.3-prime、grok-4.7（五凭据 67/68/69/70/72 全部
  `availability_state=auth_failed` + `quota_state=permanently_exhausted`，
  但 bindings 仍 available=TRUE 且 lifecycle status='active'）。
- 客户端选中即失败：minimax-m2.7-quickspeed 零目录行 → 400；
  grok-4.7 → no_candidate 503。

## 修复（两层缝隙，第二层是生产复核抓的）

1. **绑定 + 探针状态层**：活度源换
   `credential_model_bindings.available`（排除 manual%/admin_protected）
   + `node_probe_state.consecutive_failures=0`（与
   UrsmlHealthyKeyReconciler 的 healthyCandidateSQL 同款谓词）。探针门是
   必要的：余额死凭据的 binding 在「探测翻红→自动恢复重挂」间抖动，
   只看 binding 会让死模型在列表里闪烁（grok-4.7 第一版部署后仍在列）。
2. **凭据级死活层**（403→127 的生产复核抓到）：加
   `credentials.availability_state='ready'` +
   `quota_state NOT 'permanently_exhausted'`。五个死凭据的 binding 全部
   available=t、`credentials.status` 也是 'active'（lifecycle 列）——
   只查 binding/status 会把它们全放进来。

结果：620 → **139**（生产实时），grok-4.6/claude-sonnet-5/claude-opus-5/
deepseek-v4-pro 等全部保留；grok-4.7、nvidia nemotron 家族、glm-5.3-prime、
minimax-m2.7-quickspeed 出局。

## 逃生舱（热加载）

`settings_kv` 平台键 **`models.list_only_routable`**（默认 true，
CategoryModels 新类别，spec 注册于 settings/spec_models.go）。置 false 即
回到 model_offers 旧语义，无需部署。生产实测翻转：
138（on）→ 617（off，即时生效）→ 138（on）。

## 开放项 / 登记不修

1. 列表随探测/恢复瞬时闪烁（模型短暂进出）：如实反映当前可路由性，
   客户端本就该在选中失败时刷新发现列表。若未来要「结构层静态名单」，
   另立产品决策。
2. `credentials.status='active'`（lifecycle）与路由死活
   （availability_state/quota_state）是两组独立列——本次又在
   grok-4.7 上踩了一次。任何「凭据是否可用」的判定都应以后者为准。

## 量具坑（本轮新增）

1. **部署管道 `| grep | tail` 会吞掉部署失败**：`set -o pipefail` 缺席时
   管道退出码取最后一个命令，任务通知显示成功而部署实际死于构建锁
   （2582/2583 两次假成功）。部署命令一律 `> file 2>&1; rc=$?`。
2. **共享构建锁（kx-llm-gateway-build.lock）是全机共享的**：本地
   deploy-local 与生产 deploy-seamless 互斥。错误信息
   `shared build lock held` 就是「有别的部署在跑」，判持有者 pid 存活
   后等待即可，不要动锁。
3. pgxmock 的 Rows.Scan 不支持二级指针（**int）目的标——真 pgx 对可空列
   的 `&ptr` 形态在生产代码里是常态；mock 夹具里该列给 NULL。
4. seq 计数器是 per-checkout 的：2580(154)/2581(245)/2582(154)/2586(245)
   交错不递增属正常，以 handoff 回显与 healthz 为准。
