# r1027 —— /v1/models 只列真正可路由的模型（发现端点活度源与路由对齐）

> 会话轮：2026-10-14 00:30–01:40（本仓 llm-gateway-go-4）。用户指令：把
> 「/v1/models 只列出真正有 provider 的模型」做掉，从源头避免客户端选中死模型。
> 背景：r1026 轮排查确认 grok-4.6 主链路健康后，剩余用户面失败来自
> 客户端按发现列表/旧配置选中死模型（opencode 对 minimax-m2.7-quickspeed
> 的固定辅助请求每次 400 invalid_model；grok-4.7 no_candidate 503）。

## 根因：发现端点与路由使用两张不同的活度表

旧查询（domains/streaming/models.go serveFromDB）以
`model_offers.available = TRUE` + `credentials.status='active'` +
`providers.enabled` 为门。而路由实际走
`credential_model_bindings.available` + `credentials.availability_state /
quota_state` + URSM v2 视图。故障阶梯（探测失败/余额耗尽/协议失配）只翻
后者——`model_offers` 永远说 available。

生产实测（154，共享库直查）：

- 旧列表 **620** 个模型，含 nvidia nemotron 全家族（cred 19 协议失配
  http_404）、glm-5.3-prime、grok-4.7（五凭据 67/68/69/70/72 全部
  `availability_state=auth_failed` + `quota_state=permanently_exhausted`，
  但 bindings 仍 available=TRUE 且 lifecycle status='active'）。
- 客户端选中即失败：minimax-m2.7-quickspeed 零目录行 → 400；
  grok-4.7 → no_candidate 503。

## 修复（两层缝隙，第二层是生产复核抓的）

1. **绑定 + 探针状态层**：活度源换
   `credential_model_bindings.available`（排除 manual%/admin_protected）
   + `node_probe_state.consecutive_failures=0`（与
   UrsmlHealthyKeyReconciler 的 healthyCandidateSQL 同款谓词）。探针门是
   必要的：余额死凭据的 binding 在「探测翻红→自动恢复重挂」间抖动，
   只看 binding 会让死模型在列表里闪烁（grok-4.7 第一版部署后仍在列）。
2. **凭据级死活层**（403→127 的生产复核抓到）：加
   `credentials.availability_state='ready'` +
   `quota_state NOT 'permanently_exhausted'`。五个死凭据的 binding 全部
   available=t、`credentials.status` 也是 'active'（lifecycle 列）——
   只查 binding/status 会把它们全放进来。

结果：620 → **139**（生产实时），grok-4.6/claude-sonnet-5/claude-opus-5/
deepseek-v4-pro 等全部保留；grok-4.7、nvidia nemotron 家族、glm-5.3-prime、
minimax-m2.7-quickspeed 出局。

## 逃生舱（热加载）

`settings_kv` 平台键 **`models.list_only_routable`**（默认 true，
CategoryModels 新类别，spec 注册于 settings/spec_models.go）。置 false 即
回到 model_offers 旧语义，无需部署。生产实测翻转：
138（on）→ 617（off，即时生效）→ 138（on）。

## 判据与变异验证

`domains/streaming/models_routable_test.go`：

- `TestModelsRoutableQueryIsUsedAndShaped`（pgxmock）：默认走
  credential_model_bindings 查询面；夹具 context_window 用 NULL
  （handler 以 **int 扫可空列，真 pgx 支持而 pgxmock 只对 NULL 放行——
  量具坑，见下）。
- `TestModelsRoutableSQLGatePredicates`：字符串契约钉死全部承重谓词
  （binding/nps/凭据三级门 + 禁止 model_offers + legacy 形状）。
- `TestModelsRoutableKeyIsRegisteredInSettingsSpecs`：开关键必须注册 spec
  （GetPlatformBool 对未注册键静默回退默认值——开关会永远扳不动）。
- `TestModelsQueryForKillSwitch`：回切分支。

变异验证（cp 备份恢复）：M1 撤 `cmb.available` 门 → 谓词契约红 ✓；

## 开放项 / 登记不修

1. 列表随探测/恢复瞬时闪烁（模型短暂进出）：如实反映当前可路由性，
   客户端本就该在选中失败时刷新发现列表。若未来要「结构层静态名单」，
   另立产品决策。
2. `credentials.status='active'`（lifecycle）与路由死活
   （availability_state/quota_state）是两组独立列——本次又在
   grok-4.7 上踩了一次。任何「凭据是否可用」的判定都应以后者为准。

## 量具坑（本轮新增）

1. **部署管道 `| grep | tail` 会吞掉部署失败**：`set -o pipefail` 缺席时
   管道退出码取最后一个命令，任务通知显示成功而部署实际死于构建锁
   （2582/2583 两次假成功）。部署命令一律 `> file 2>&1; rc=$?`。
2. **共享构建锁（kx-llm-gateway-build.lock）是全机共享的**：本地
   deploy-local 与生产 deploy-seamless 互斥。错误信息
   `shared build lock held` 就是「有别的部署在跑」，判持有者 pid 存活
   后等待即可，不要动锁。
3. pgxmock 的 Rows.Scan 不支持二级指针（**int）目的标——真 pgx 对可空列
   的 `&ptr` 形态在生产代码里是常态；mock 夹具里该列给 NULL。
4. seq 计数器是 per-checkout 的：2580(154)/2581(245)/2582(154)/2586(245)
   交错不递增属正常，以 handoff 回显与 healthz 为准。

# 追加：r1028 —— `=== pwd ===` 分节装饰误触发密钥规则，grok-4.6 工具调用整流（2026-10-14 凌晨续轮）

> 用户报告：ZCode 报 `Turn execution failed provider_code=output_policy_blocked
> model=grok-4.6 request=f6f90e5e...`。取证与修复见
> `security/sanitize/r1028_secret_value_equals_decoration_test.go` 与
> `domains/outputcompliance/r1028_dbengine_pwd_decoration_test.go`。

## 取证链（raw_data 帧重建）

1. 客户端 request_id f6f90e5e → 网关 5d9e1267（04:17:45，1.7MB 上下文，
   vapeur /v1/responses 上游 200）→ `output_compliance: blocked stream lane
   label=__tool_json@Bash lane_bytes=1279 issues=0`。
2. 被拦参数未落 session_bodies；从 `/var/log/llm-gateway-go/raw_data/`
   （LLM_GATEWAY_RAW_LOG_DIR）上游响应帧重建——**1279 字节纯 git 检查命令**
   （log/ls-files/diff/ps aux/pwd），无 URL 无 IP 无邮箱。
3. 离线二分（生产 YAML + CheckField 同层）定位触发行：`echo '=== pwd ==='`。

## 两条独立规则、三份副本，同型误伤

| 位置 | 规则 | 误伤机制 |
|---|---|---|
| `configs/sensitive_patterns.yaml` secret.password（+Go fallback `operational_patterns.go`） | `(?i)(?:...|pwd|...)\s*[:=：]\s*(...[^\s"',;，；<>{}\]]+)` | 值字符类放行纯 `=` 串：`pwd ===` → 「pwd = 赋值 ==」→ secret 片段 → ScopeEgress 硬拦 |
| `domains/outputcompliance/checker.go` detectSecrets（**第二套 DB 引擎**，无 CheckField，共享拦截器整段回退 Check） | `(?i)(password|passwd|pwd)\s*[:=]\s*\S+` | `\S+` 吃掉 `==` → 工具 lane 改写保护把 redact 升级成整流 block；redact 路径产生 `[REDACTED:password]`（probe 实测） |

第二套引擎是本条误伤的**主拦截者**（生产 403 由它产出），第一套是流式 lane
`issues:0` 拦截的来源——修复必须三份同步，漏一份就复发。

## 修复

三处值匹配统一为「未加引号的值首字符不得为 `=`，引号值走引号分支」：

- yaml/Go sanitize：`[^\s"',;，；<>{}=\]][^\s"',;，；<>{}\]]*`
- DB 引擎：`("[^"]*"|'[^']*'|[^=\s'"][^\s]*)`（`pwd ='` 尾引号形态由
  引号分支的闭合要求排除——第一版只排 `=` 时 `='` 仍命中，判据抓到后补引号
  分支；这正是判据配对的价值）

真实口令（`password=hunter2`、`PASSWORD: opensesame1`、`password="=="`）照常
命中；redact 侧分节标题不再被遮。

## 部署与线上验证

- 154=**2606**、245=**2607**（2580→2606 间含并行会话交错部署与一次
  DB 就绪失败自动回滚，均无碍）。
- 线上探针（grok-4.6 经 llm.kxpms.cn，tool_choice=required）：
  `echo '=== pwd ==='` → **PASS 参数逐字透传**（修复前 403 整流）；
  `curl -d password=...` → 参数中口令被按租户策略脱敏（`[REDACTED:password]`）；
  公网 IP 形态模型自拒（r1013 契约由 sanitize 既有判据覆盖，未受影响）。

## 量具坑

1. **raw_data 帧重建是被拦内容的唯一取证源**：被 compliance 拦下的 lane 不落
   session_bodies，raw_data（LLM_GATEWAY_RAW_LOG_DIR）按 request_id 存
   client_request/upstream_request/upstream_response 三段 base64 帧。
2. `deploy | grep | tail` 无 pipefail 吞失败（本次再次实证：2582/2583 两次
   假成功 + 一次 DB 未就绪自动回滚被误读）——`> log 2>&1; rc=$?`。
3. systemd WorkingDirectory=/opt/llm-gateway-go，进程读的 yaml 是
   `/opt/llm-gateway-go/configs/`，与 release 内副本是两份——验证修复落地要
   同时 md5 两处 + `grep -a` 二进制内 Go 常量片段（strings 对含 CJK 的
   Go 字符串会断行，`strings` 漏报时改 `grep -a`）。
4. **同一误伤家族有三份正则副本**（yaml + sanitize fallback + outputcompliance
   DB 引擎）——修漏任何一份都会以另一条路径复发。这是继 installer 五点同步、
   迁移双腿登记之后第三处「同一语义多处落地」的同步面。
