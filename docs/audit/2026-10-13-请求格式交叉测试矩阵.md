# 请求格式交叉测试矩阵（2026-10-13）

> 目标：对网关的 4 种入向请求格式 × 6 个目标模型做交叉测试，确保格式转换
> **不丢失会话扩展信息**。核心判据来自需求：
>
> 1. **同格式全样保留**——入向请求协议与上游供应商协议一致时，会话中的
>    扩展信息（厂商私有参数、未知前向兼容字段）必须全样传递；
> 2. **出错打标**——透传/还原导致上游报错时，给该节点打标，下次不再全量传输
>    （对应仓库既有机制 `internal/reqprobe`：4xx 诊断 → 剥参免费重试 →
>    学习规则 24h 滑窗前置应用）。
>
> 判据纪律（AGENTS「判据设计的硬教训」第 3 条）：凡「放行/200」都要单独验证
> **前提在场**（出站体里确实带着扩展字段），不用「没报错」冒充「没丢失」。
> 单元层直接断言出站体；E2E 层用 `request_logs_bodies_hot.outbound_body`
> 存档核验出站体。
>
> **结果摘要**：单元层 17/17 通过（修复 2 个真缺陷后）；E2E 9 格通过、
> 5 格环境失败（凭据/路由健康，非格式问题）、2 格按预期取证不可路由。
> 「出错→打标→下次不全量传」在生产形态网关上**现场实证两轮完整循环**。
> 详见 §三、§四。
>
> **第二轮（同日 06:00 轮，部署 2563/2564 后）**：再修 1 个真缺陷
> （reqprobe 诊断器不认 `parameter(s)` 括号复数措辞——kimi-k3 六候选
> 全灭的根因）+ 缺陷①空 catalog 哨兵细化 + 观测缺口①修复（anthropic
> 入向出站体入档）。E2E 复验：**需求的全循环三段在三个节点组合上实测
> 闭环**——全样保留到达上游 → 上游 400 表态 → 剥参重试成功 → 学习规则
> 打标 → 后续请求出站前自动不全量传（零 400 往返）。kimi-k3 从

### 1.4 paramreg 决策规则（`internal/paramreg/decide.go`，矩阵期望值的来源）

1. 目标方言明确 RejectedBy → 裁剪（如 grok 拒绝 frequency_penalty）；
2. **未登记字段（未知/厂商新参数）→ 无条件还原**（前向兼容核心）；
3. KindIRHandled/Portable → 还原；
4. 可翻译 → 翻译后写入；
5. 方言私有 → 目标方言认识才还原，否则裁剪并**上报 loss**；
6. dst=DialectUnknown（catalog_code 为空的供应商）→ knownBy=true /
   rejects=false，**最宽松全放行**（宁可多传不静默丢）。

方言私有字段登记现状（测试样本即取自这些**真实厂商参数**）：

- GLM：`do_sample` `request_id` `user_id` `tool_stream`
- MiniMax：`reasoning_split` `reply_constraints` `tokens_to_generate` `aigc_watermark`（+IR 一等 `mask_sensitive_info` `bot_setting`）
- Grok：`search_parameters` `deferred`；RejectedBy grok：`frequency_penalty` `presence_penalty`
- **Kimi/Moonshot：无任何已登记私有字段** → 一切 kimi 扩展参数都走「未知→无条件还原」分支
- Anthropic：`context_management` `container` `mcp_servers` `betas` `output_config` 等

## 三、「出错→打标→下次不全量传」现场实证（E2E，两轮完整循环）

以 B1.4（chat 客户端 × grok-4.6 → Vapeur `/v1/responses`）为例，gateway-8782.log：

```
05:26:57 upstream_call_starting  POST https://api.vapeur.ai/v1/responses  body_bytes=193
05:26:59 upstream_http_attempt   upstream_status=400          ← 全样透传（未知参数原样发出）
05:26:59 reqprobe: upstream rejected request, retrying with params stripped
           stripped="grok_future_param" named_param="grok_future_param"   ← 诊断+剥参免费重试
05:27:06 reqprobe: probe retry recovered the request
           trigger=param_rejected param=grok_future_param      ← 重试成功 → 节点打标（学习）
05:35:01 reqprobe: applying learned param strips
           provider_id=36 raw_model=grok-4.6 stripped="grok_future_param" ← 下一请求前置剥参
```

第二轮（B2.4，anthropic 客户端 × grok-4.6）同构：`anthropic_future_beta`
400 → 剥参重试成功。学习规则持久化在 Redis db2（`llmgw:reqanom:*` zset+hash，
24h 滑窗，admin resolve 可清）。这正是需求第 2 条的完整闭环：**先全量传，
上游报错才打标，之后该 (provider, model) 节点自动不全量传**。

## 四、发现与修复

### 已修代码（本轮提交，测试文件即判据，修复前红/修复后绿=变异验证）

1. **缺陷①：`resolveTargetDialect` 吞掉未登记厂商的 fail-open 承诺**
   （`internal/ir/extensions_restore.go`）。catalog_code 非空但未登记的供应商
   （suyun/apigpt/apinext 等中转）此前回退到协议方言（openai_chat），导致
   别家方言私有字段（grok 的 `search_parameters`、DeepSeek 的 `prefix`）被
   「目标不认识」裁剪——违背 `DialectForCatalogCode` 注释承诺的「未登记厂商
   不该因为没登记就丢参数」。**grok-4.6 的本地全部同协议绑定都属此类**，
   是用户所说「因兼容被不传递」的直接实体。修复：未登记即返回
   DialectUnknown（最宽松），错误面交 reqprobe 兜底。判据：A1.6（修复前红）。
2. **缺陷②：`serialize_openai` 从不发射 `top_k`**（`internal/ir/serialize_openai.go`）。
   Anthropic/Gemini 入向的 top_k 被 parser 消费进 IR 后只在序列化层记 loss，
   依据的「top_k is Anthropic-only」注释已过时（paramreg spec 自身注明
   GLM/Qwen/DeepSeek/vLLM/OpenRouter 支持该字段）。修复：按 R52 方言门控
   发射（openai 形态方言经 BaseProtocol 继承全放行；responses 方言不放行
   时仍记 loss）。判据：A6（修复前 top_k 红）。

### 设计行为澄清（非缺陷，如实记录）

- 跨协议/跨方言的**方言私有**字段会被 paramreg 裁剪并记 `ir_protocol_loss`
  台账（非静默）。未知字段（厂商新参数）无条件透传——被上游拒了由 reqprobe
  反应式兜底。这是「预裁已知风险 + 反应式学习」的分层设计，与需求
  「同格式全样保留、出错再打标」在**跨方言**场景上有意识偏差（防 400 优先），
  同协议同方言场景无偏差。
- thinking 意图：anthropic/gemini 入向到 minimax/glm/deepseek/ark/qwen 渲染，
  到 kimi/grok/mistral/vllm/未知方言不渲染（仅记 loss）——推理面未验证的
  厂商宁可不上报也不猜。

### 遗留（登记不修）

1. **观测缺口①（P3）**：anthropic 入向（`/v1/messages`）请求的
   `request_logs_bodies_hot.outbound_body` 恒为 NULL——chat 入向有
   `applyActualOutboundBody` 兜底，messages 路径没有。B2 系列出站体无法
   直接核验，只能靠日志 body_bytes + 单元层判据。
2. **观测缺口②（P3）**：Q4（anthropic→apiclaude 原生透传）本地无健康节点，
   E2E 未覆盖；Q4 的保真证据=代码路径（字节透传）+ A4。
3. **环境失败（待 owner）**：kimi-k3 / gpt-5.6-luna 两模型 URSM 视图零候选
   （DB 各有 19/12 个 available 绑定但全被过滤）——与 AGENTS 登记的
   凭据真死/probe_direct_auth_failed 同源，非格式问题。恢复后 B1.3/B1.6/
   B2.3/B2.6/B3 可直接复跑（矩阵与 sk- key 建法见 §五）。
4. **量具坑（判据纪律 +1）**：按 marker LIKE 匹配 `request_body` 会被
   「会话标题生成」后台任务污染（其 prompt 嵌入会话原文，marker 随之入库），
   必须加 `request_body->>'model' = '<client_model>'` 过滤，否则把标题任务
   的出站体当成业务请求的。
5. E2E 反映的是修复前二进制（2562-e65e181e）；缺陷①②的修复需随下次部署
   上线后复验 B1.4 的 `search_parameters` 与 B4 的 `top_k`。

## 七、gpt-5.6-sol tools 事故轮（2026-10-13 06:40 轮，部署 2566）

### 7.1 症状与根因

用户报告：访问 gpt-5.6-sol「一步就结束」，tools 相关信息未被正确处理。

- **复现（硬证据）**：chat 客户端 + 命名强制 tool_choice
  （`{"type":"function","function":{"name":"get_weather"}}`）→ Vapeur
  `/v1/responses` 三跳全 400：`Invalid value: 'function'. Supported values
  are: 'none', 'auto', and 'required'.` → 503 → 熔断开启 → 后续请求
  （含流式）no_candidate 连锁，agent 单步夭折。
- **根因（GAP-2 家族漏网）**：IR 的 `ToolChoice.Type` 存方言值，chat 入向
  `{type:function,function:{name}}` 与 responses 原生 `{type:function,name}`
  都存 `Type="function"`。round 31（2026-10-02）的 GAP-2 修复补了
  `serialize_openai` 与 `serialize_anthropic` 的 `function` 分支，
  **`serialize_responses.buildResponsesToolChoice` 漏网**——switch 无此
  case，落到兜底 `return tc.Type` 把裸字符串 `"function"` 发给上游。
  连 responses 原生客户端的 roundtrip 都会踩。
- **放大器**：ba1987a4d（2026-10-12）的 proactive chat→responses 升级把
  带强制 tool_choice 的 chat 客户端引流到该转换器——缺口从休眠变必踩。
- **同类缺口**：`serialize_gemini.buildGeminiToolChoice` 无 `function`
  分支落到 default 变 AUTO——强制语义静默丢失（不 400，但模型可能不调
  指定工具）。

### 7.2 修复（本轮提交，部署 2566）

- `serialize_responses.go`：`case "tool", "function":` → 对象形态
  `{"type":"function","name":…}`（经 SanitizeResponsesFunctionName）。
- `serialize_gemini.go`：同款分支 → mode=ANY + allowedFunctionNames。
- 判据：`internal/ir/tool_choice_forced_matrix_test.go` 六件套
  （chat→responses 对象形态 / responses roundtrip / 宽容值不回归 /
  anthropic any→required / gemini ANY+allowed / 事故现场等比复现含
  `$schema` 保留）。**变异验证：回退修复 3 红（chat→responses、
  roundtrip、gemini），恢复全绿。**
