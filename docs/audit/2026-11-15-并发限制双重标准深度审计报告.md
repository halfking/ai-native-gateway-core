**结论**：需要统一为 **ConfiguredConcurrent（explicit-only）** 标准。

##三、代码层深度分析

### 3.1 双重标准的具体体现

#### 标准一：KeyConcurrentGate（硬执法）—— **已修正**

**文件**：`domains/streaming/key_concurrent_gate.go`

```go
// 第 67 行：explicit-only（2026-11-15 修正）
limit := keyInfo.ConfiguredConcurrent()

    next.ServeHTTP(w, r)  // NULL/0 = 不设帽
```

### 3.2 EffectiveConcurrent vs ConfiguredConcurrent

**文件**：`domains/authentication/verifier.go`

```go
// EffectiveConcurrent：包含 tier 默认回退
func (ki *KeyInfo) EffectiveConcurrent() int {
    if ki.RateLimitConcurrent != nil {
        if *ki.RateLimitConcurrent == 0 {
            return 0 // explicit unlimited
        }
        if *ki.RateLimitConcurrent > 0 {
            return *ki.RateLimitConcurrent
        }
    }
    // ← NULL 时回退到 tier 默认
    tier := ki.KeyTier
    if tier == "" {
        tier = "default"
    }
    if d, ok := tierDefaults[tier]; ok {
        return d[1]  // default 档的 [1] = 6
    }
    return tierDefaults["default"][1]
}

// ConfiguredConcurrent：explicit-only（2026-11-15 新增）
func (ki *KeyInfo) ConfiguredConcurrent() int {
    if ki.RateLimitConcurrent != nil && *ki.RateLimitConcurrent > 0 {
        return *ki.RateLimitConcurrent
    }
    return 0  // ← NULL = 0，不回退
}
```

## 四、根因总结

### 4.1 历史演进

1. **初始态**：rate_limit_concurrent 列存在但从未真正执法（executors 仅 WARN）
2. **2026-11-15 初版 KeyConcurrentGate**：使用 EffectiveConcurrent → 82 个 NULL key 突然被 tier 默认（6）帽住
3. **2026-11-15 ea1aea3c6 修正**：KeyConcurrentGate 改用 ConfiguredConcurrent → NULL key 不再被误拦
4. **当前状态**：KeyConcurrentGate 已修正，但 **executors 仍使用 EffectiveConcurrent**

### 4.2 双重标准造成的问题

| 维度              | KeyConcurrentGate (硬)     | Executors (软)             | 一致性 |
|-------------------|----------------------------|----------------------------|--------|
| NULL 处理         | 不设闸                     | tier 默认（6）             | ❌     |
| 0 处理            | 不设闸                     | 不设闸                     | ✅     |
| 正整数处理        | 硬拒绝 429                 | 软警告（继续）             | ❌     |
| 执法点            | middleware（telemetry 前） | dispatch 深处              | ❌     |
| 可观测性          | WARN + 指标                | WARN only                  | ❌     |

**核心矛盾**：
- 对于 82 个 NULL key：
  - KeyConcurrentGate 认为"无限制"
  - Executors 认为"限制 6"（但只警告不拒绝）
  
**为什么生产未暴露**：
1. KeyConcurrentGate 是真执法，已修正为 explicit-only → NULL key 放行 ✅
2. Executors 虽然用 EffectiveConcurrent，但 **TryAcquire 失败只警告不拒绝** → 无用户可见影响
3. 实际并发未达到 tier 默认值 6 → executors 软告警也未触发

## 五、修复方案

### 5.1 对齐点

**统一为 ConfiguredConcurrent（explicit-only）标准**：

**理由**：
1. 与 EffectiveTPM 的 explicit-only 语义对齐（同为"死字段复活"）
2. 符合 ea1aea3c6 commit 的设计意图："NULL 列在执法接入前从未代表「tier 默认 6 并发」"
3. 避免混淆：executors 软告警虽不拒绝，但不一致的数值会误导运维

### 5.2 需要修改的文件

**4 处 handler 调用点**：

1. `domains/streaming/handler.go:5033`
2. `domains/streaming/handler.go:5558`（另一处）
3. `domains/streaming/messages.go`（类似位置）
4. `domains/streaming/responses.go`（类似位置）

**修改内容**：
```go
// 修改前：
KeyConcurrentLimit: func() int {
    if keyInfo != nil {
        return keyInfo.EffectiveConcurrent()  // ← 改这里
    }
    return 0
}(),

// 修改后：
KeyConcurrentLimit: func() int {
    if keyInfo != nil {
        return keyInfo.ConfiguredConcurrent()  // ← 统一为 explicit-only
    }
    return 0
}(),
```

### 5.3 影响分析

**行为变化**：
- **82 个 NULL key**：executors 软告警从"监控 6 并发"变为"不监控"
  - ✅ 与 KeyConcurrentGate 语义对齐
  - ✅ 历史行为保持（软告警从不拒绝）
  
- **2 个显式配置 key（10/199）**：无变化
  - key 10: 100 并发 → 100 并发
  - key 199: 20 并发 → 20 并发

- **6 个显式 0 key**：无变化
  - 0 → 0（无限制）

**风险评估**：
- **零用户可见变化**：executors 软告警从不拒绝请求
- **零性能影响**：仅改变软告警的监控阈值
- **改善一致性**：消除双重标准，统一语义

### 5.4 测试覆盖

**需要验证的场景**：
1. NULL key → executors 不再生成 "per-key concurrent limit reached" WARN
2. 显式配置 key → executors 软告警仍按配置值监控
3. 0 key → executors 完全跳过监控（与 NULL 等价）

## 七、遗留问题与建议

### 7.1 架构层面

**问题**：为什么需要两层并发限制？

| 层级              | 位置         | 执法强度 | 用途                     |
|-------------------|--------------|----------|--------------------------|
| KeyConcurrentGate | middleware   | 硬拒绝   | per-key 硬限制（新引入） |
| Executors         | dispatch 深处| 软警告   | 软监控（历史遗留）       |

**建议**：
1. **保留 KeyConcurrentGate 硬执法**（用户配置的真实意图）
2. **Executors 软告警保留为纵深观察**（注释 key_concurrent_gate.go:23 已说明）
3. **统一语义为 ConfiguredConcurrent**（explicit-only）

### 7.2 运维层面

**当前限流体系**（从严到宽）：
```
1. KeyConcurrentGate (per-key, hard)     ← 本次对齐
2. Ingress capacity (global)             ← LargeIngress 并发槽
3. Credential pool (per-provider)        ← 日志中的 concurrent-overload
4. RPM limits (per-credential)           ← 日志中的 RPM 族
5. Executors soft (per-key, warn-only)   ← 本次对齐
```

**建议**：
- 文档化限流层级与用途
- 监控面统一展示（避免运维混淆）

### 7.3 数据完整性

**发现**：82/90 keys 的 rate_limit_concurrent = NULL

**建议**：
- **保持 NULL**：符合 explicit-only 语义（不想限制就不配置）
- **或者批量设 0**：显式表达"无限制"（更清晰）
  ```sql
  -- 仅建议，需 owner 裁决
  UPDATE api_keys 
  SET rate_limit_concurrent = 0 
  WHERE rate_limit_concurrent IS NULL 
    AND enabled = true;
  ```
