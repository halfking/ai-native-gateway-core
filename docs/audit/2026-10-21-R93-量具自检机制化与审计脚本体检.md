## 3. 门的判据：为什么不用正则

Go 的 RE2 **既不支持 lookbehind 也不支持 lookahead** ⇒ 「`col` 后面不能跟着 `::cast`」这类否定断言正好需要 lookahead
⇒ ⇒ 判据改成**按标识符切 token**（纯字符串逻辑）：

- 左操作数 = token 是白名单列名，且**下一个 token 就是 `||`**；
- 右操作数 = token 是白名单列名，且**向前跳过「标识符 + `.`」后就是 `||`**；
- **下一个 token 是 `::` ⇒ 已有 cast ⇒ 跳过**（这条必须在两个形态判断**之前**，否则 `|| c.relkind::text ||` 会被右操作数规则误判）。

白名单 = **PG 17.10 实测**的 `pg_catalog` 里 `udt_name='char'` 的**全部**列名（46 行 ⇒ 去重 45 个）。

★ **为什么必须是全集**：第一版只修了量到的 3 个列（relkind / attstorage / attcompression）⇒ 重测后**仍残留 1 条** `a.attalign`
⇒ ⇒ **「修样本」不等于「修族」**。

★ **为什么 `information_schema.columns.data_type` 查不到**：`"char"` 的 `data_type` 是 `character`，但 `udt_name='char'`
⇒ 必须按 `udt_name` 查。

## 4. ★★★ 门的判据本身出过 3 个 bug（都是自检抓到的）

### 4.1 分词器把**空白**也当 token ⇒ 相邻性判定全失效

**现象**：单元自检 4 条「期望 1 得 0」，而真实文件里能抓到 4 处。

**根因**：`r93Tokenize` 把空格也 emit 成 token ⇒ 「下一个 token 就是 `||`」这类判定全部错位
⇒ ⇒ 而真实文件里那 4 处恰好是**无空白**的 `||t2.attstorage` 形态 ⇒ ⇒ **有空格的真阳性会被漏放**。

**修法**：分词器**跳过空白**。

⇒ ★★ **可复用的通用式**：**「相邻性」判据的分词器必须把空白当【分隔】而不是【token】** ——
否则它只在「恰好没空格」的样本上有效 ⇒ **看起来能用，实质漏放**。

### 4.2 注释语法必须**按扩展名分派**

用 `//` 当通用行注释标记 ⇒ **SQL 行被从中截断** ⇒ 漏掉了 `09_final.sql:9` 的 `a.attalign` ⇒ ⇒ **漏放比误报危险**。

| 扩展名 | 行注释 | 块注释 |
|---|---|---|
| `.sql` | `--` | `/* … */` |
| `.go` | `//` | `/* … */` |
| `.sh` / `.py` | `#` | `/* … */` |

### 4.3 ★★ 门把**变异脚本自己**判成真阳性（⇒ 不是门误报，是脚本真有一处裸拼接）

收尾的「整包必须回绿」红了 ⇒ 报的是 `scripts/audit/verify-char-concat-guard-mutations.sh:42` 的 `c.relkind || 'x'`
⇒ ⇒ **门判对了**（那确实是裸拼接）⇒ ⇒ 改的是**脚本**：探针内容改为**运行时拼接**，源码里不留裸形态。

⇒ ★★ **可复用的通用式**：**「门抓到了我自己」先假定门对** ⇒ 查自己的源码里是不是真有那个形态。

## 6. ★★★★ 体检工具：`.db-audit/sql/*.sql`（38 个手工审计脚本）

### 6.1 为什么这批脚本值得体检

- 它们是**手工审计脚本**，设计环境是「psql 与 PG 同机」（给 252 生产机用）⇒ `PSQL="psql -U llm_gateway -d llm_gateway ..."` **没有 `-h`**；
- ⇒ 在开发机上跑 ⇒ psql 走**本地 Unix socket** ⇒ **一条 SQL 都没执行**；
- ⇒ 而它们用 `-v ON_ERROR_STOP=0` ⇒ 报错不中断 ⇒ 连「ERROR 行」都没有
- ⇒ ⇒ **静默失败的最深一层：整个脚本零读数**。

### 6.2 ★★ 第一版量具的 3 个坑（都记在脚本头部）

| # | 坑 | 后果 | 修法 |
|---|---|---|---|
| ① | 建库失败没检查 | 38 个脚本全跑在**不存在的库**上 ⇒ **全是假读数** | 建完必须自检（能连 + 表在位） |
| ② | `grep -c ... \|\| echo 0` | `grep -c` 命中 0 行时**打印 0 且退出码 1** ⇒ 得到 `"00"` ⇒ 判定全错 | 不要加 `\|\| echo 0` |
| ③ | **psql 没给 `-h`** | 走本地 socket ⇒ **一条 SQL 都没执行** | **注入 `PGHOST=127.0.0.1`**（改运行环境，不改被测脚本） |

### 6.3 ★★★ 量具自检（跑在读数之前，不过就中止）

1. `current_database()` == 目标库名（逐字相等）；
2. `inet_server_addr()` **不是 null** ⇒ 证明走的是 **TCP 不是 socket**（★ 这条是本工具的命门）；
3. `public` 表数 > 100 ⇒ 证明确实是**形态库**；
4. **库名必须全小写**（PostgreSQL 折叠未加引号的标识符）。

### 6.4 ★★ 破坏性腿的守卫

★ `.db-audit/sql/17_bench_columnar.sql` **有写操作**（`CREATE SCHEMA` / `CREATE TABLE` / `ALTER TABLE` / `INSERT`）
⇒ ⇒ 本工具**只允许**跑在**一次性库**上（库名必须匹配 `itgate_*`）⇒ 否则中止。
⇒ ⇒ 跑在长驻库上 = 把审计脚本变成事故。

### 6.5 ★★★★ 双口径交叉校验（本工具的「自证有牙」）

| 口径 | 做法 | 优点 |
|---|---|---|
| **A 逐单元**（主口径） | 把脚本拆成「单条 SQL」与「heredoc 块」，逐个执行 | 每条错误能归因到 **文件:行号** |
| **B 整脚本** | 原样 `bash <脚本>` | 复现运维真实看到的 ERROR 行 |

★ **两个口径的 ERROR 总数必须相等** ⇒ 不等即说明**本工具有盲区** ⇒ **拒绝出读数（exit 3）**。

⇒ ★★ 这道校验**真的抓到了本工具自己的 3 个盲区**：

| # | 盲区 | 现象 | 修法 |
|---|---|---|---|
| ① | 抽取器「取行内最后一个 `"` 当闭合引号」 | SQL 里**没有 `"`** 时找不到闭合点 ⇒ 整条语句被跳过 ⇒ 37 条错误只读到 32 条 | 按**未转义引号**配对 |
| ② | 只认 `-c "..."` ⇒ **heredoc 块整块看不见** | `17_bench_columnar.sql` 的 3 条错误凭空消失 | 支持 `<<'SQL'` 块 |
| ③ | 用 `psql -f` 跑块 ⇒ 报错行前缀是 `psql:<文件>:<行>: ERROR:` | **不以 `ERROR:` 开头** ⇒ 被 `grep -E '^(ERROR\|FATAL):'` 漏掉 | grep 前缀改成 `(^\|: )(ERROR\|FATAL):` |

⇒ ★★★ **可复用的通用式**：
1. ⭐⭐⭐⭐⭐ **量具必须自带一条「能判出我自己瞎了」的判据** —— 最便宜的形式是**两个独立口径对拍**（口径不同 ⇒ 盲区不重叠）。
2. ⭐⭐⭐⭐⭐ **对拍不一致时，输出必须是「不可采信」而不是「取一个口径的数」** —— 否则你会把量具的盲区当成事实。
3. ⭐⭐⭐⭐ **单元内容必须逐字保真**（落文件，不压平成一行）—— 第一版把 heredoc 块压成一行 ⇒ psql 的 `\echo` 把**整块剩余内容**当成自己的参数吞掉 ⇒ **一条 SQL 都没执行**。
4. ⭐⭐⭐⭐ **分隔符必须是非空白字符** —— `IFS=$'\t'` 里 **tab 属 IFS 空白** ⇒ bash 会把连续 tab 折叠成一个分隔符 ⇒ **空字段被吃掉** ⇒ 字段整体错位。
5. ⭐⭐⭐ ★ **报错行的前缀不固定**（`psql -f` 会带 `psql:<文件>:<行>:`）⇒ grep 不能锚定行首。

### 6.7 ★★★★ 收尾时发现：**工具自己**在漏资源（一次性库在「提前退出」路径上不回收）

★ 这是本轮**最后**才发现的一处真缺陷，而且**只有真的去清残留库才看得见**。

**事实**：调试期反复跑体检，容器里攒下 **5 个 `itgate_r93_health_*` 残留**（每个 ~1 GB）⇒ 加 `itgate_r93_attr` / `itgate_r93_shape2` 共 **7 个**。
⇒ 别的会话的 `itgate_*`（17 个）**未被动**（只清自己 `r93` 前缀的）。

**根因**：回收块挂在**函数尾部** ⇒ 任何**提前退出**都跳过它：
- 量具自检不过 ⇒ `exit 2`
- 双口径不一致 ⇒ `exit 3`（本轮调试期正是反复触发这条）

⇒ ⇒ ★★ **通用式：「自己建的资源」必须用 trap 兜住【所有】退出路径**，而不是指望「正常跑完」这一条路径。

**第一版修法**：`trap 'cleanup || true' EXIT` + 尾部回收复用同一个 `cleanup()`（消除重复实现）。

**★ 但第二次实测又抓到一层**（只挂 EXIT trap 不够）：

| 打断时机 | 现象 | 结论 |
|---|---|---|
| build 子进程**仍在跑**时发 SIGTERM | 父进程立刻死（退出码 143）⇒ 建库子进程被**孤儿化**、继续跑 ⇒ 它在父进程的 DROP **之后**才把库建出来 ⇒ **残留 = 1** | ★ **EXIT trap 在「父进程被信号打死」时不保证会跑**；且**孤儿子进程会在 cleanup 之后才建库** |
| build **已完成**时发 SIGTERM | 残留 = 0 | EXIT trap 生效 |

⇒ ⇒ **第二版修法（三件事一起做，缺一不可）**：
① 建库子进程改**后台**跑（这样才拿得到 PID）；
② `cleanup` **先收割仍在跑的建库子进程**（`kill` + `wait`），**再** DROP；
③ 显式接管 `INT` / `TERM`（不只靠 `EXIT`）。

⇒ ★ **实测两个场景都归零**：build 中途打断 ⇒ 残留 0；build 完成后打断 ⇒ 残留 0。

⚠ **诚实边界**：**SIGKILL 不可捕获** ⇒ 被 OOM / 运行器强杀时**仍会留库**（实测真发生了一次）
⇒ ⇒ 兜底只能靠「**库名里带工具自己的 PID** ⇒ 可按「进程已死」判定归属并清理」⇒ **库名里带 PID 这件事本身是有用的**，不是随手写的。

## 10. 诚实边界

1. ★ **「修完 43 → 15」是**在一次性形态库**上测的** ⇒ 形态库只有当月 + 次月分区 ⇒ 涉及历史月分区的脚本在形态库上**必然**报 `relation does not exist`
   ⇒ ⇒ **那 15 条里有 2 条（`session_turns_2026_09` / `sessions_2026_09`）是「环境差异」而非「脚本 bug」** ⇒ 已按此分类登记。
2. ★ **双口径一致只证明「抽取器没有漏放/多放」**，不证明**分类正确** ⇒ 族级分类靠的是逐条拿**原始报错文本**（不是聚类后的模式）再判。
3. ★ **PG 版本漂移族的替代列是语义决策** ⇒ 本轮**不代属主拍板** ⇒ 台账登记 + 依据。
4. ★ **门只管「`"char"` 列裸拼接」这一族** ⇒ `round(double precision, int)` 与 `pg_stat_user_tables.reltuples` 的判据不可靠 ⇒ **不进这道门**（进了是恒绿门/误报门）⇒ 登记台账。
5. ★ 本轮**对生产的写入 = 0**；审计脚本的写操作只落在一次性库上。
6. ★★ **SIGKILL 不可捕获** ⇒ 体检工具被 OOM / 运行器强杀时**仍会留下一次性库**（实测真发生过一次）

## ★★★★★ 订正横幅（R101 轮 · 2026-10-22）：本节那句「`EXIT` trap 在『父进程被信号打死』时**不保证**会跑」**成立** ⇒ ⇒ ★★ **曾被误判为「已被实测证伪」，那个裁决已撤回**
