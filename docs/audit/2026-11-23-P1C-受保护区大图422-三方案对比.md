# P1-C：受保护区单条大图 422 问题 - 三方案技术对比

**问题 ID**: P1-C  
**优先级**: P1（高危）  
**状态**: 待 owner 裁决  
**日期**: 2026-11-23

---

## 一、问题描述

### 1.1 现象

用户发送包含高清截图的请求时，收到 **422 "context_budget_exceeded"** 错误，且错误**不可重试**。

**触发条件**:
- 单条消息（通常是最新用户消息）包含媒体（图片/视频/音频）
- 消息序列化后大小 **>1MiB**（当前 ContextBytes 默认值）
- 该消息属于"受保护区"（最新用户消息 + 活跃工具链）

**典型场景**:
```bash
# 用户截图：1920x1080 高清 PNG，约 1.5-2MB
# 或：4K 截图，约 3-5MB
# 或：短视频片段，约 2-10MB
```

### 1.2 根因分析

**代码路径**:
```
domains/streaming/large_ingress.go:182
  → sessioncontext.Reduce(prepCtx, g.store, ref, g.config.ContextBytes)
    → internal/sessioncontext/file.go:77-84
      → read(span, maxBytes-used)
        → if span.Length > int64(limit) → ErrProtectedContext
```

**核心矛盾**:
- **ContextBytes 预算**（1MiB）是给**整个归约输出**的总预算
- **受保护区**要求**完整保留**最新用户消息和工具链
- 单条消息 >1MiB ⇒ **装不进预算** ⇒ 返回 `ErrProtectedContext`
- large_ingress.go:184-200 将其映射为 **422 "context_budget_exceeded"**（不可重试）

**设计意图 vs 实际表现**:
| 设计意图 | 实际表现 | 差距 |
|---------|---------|------|
| 受保护区完整保留 | 单条超限 → 整个请求被拒 | 保护 → 拒绝 |
| ContextBytes 限制整体输出 | 也限制单条输入 | 总预算 → 单项上限 |
| 422 = 输入问题（分块/压缩） | 普通截图即触发 | 合理使用 → 被拒 |

### 1.3 影响范围

**用户侧**:
- ZCode 会话带高清截图 → 422
- Anthropic Claude Desktop 高分辨率屏幕截图 → 422
- 视频/音频输入（未来支持）→ 更易触发

**服务侧**:
- 211 实测：fable-5-2 入口带截图会话 **>1MB 每笔必败**（r1052 修复前的事故记录）
- 当前 r1052 修复后 Reduce 路径有媒体标记，但 **file.go:77-84 的单条读取限制仍在**

## 三、方案 1：放宽 ContextBytes 预算

### 3.1 核心思路

将 `ContextBytes` 默认值从 **1MiB (1_048_576)** 提升到 **5MiB (5_242_880)** 或 **10MiB**。

### 3.2 实施方案

#### 代码改动（极简）

```go
// cmd/gateway/context_budget.go（或配置文件）
// 修改前
const defaultContextBytes = 1_048_576  // 1 MiB

// 修改后
const defaultContextBytes = 5_242_880  // 5 MiB
// 或
const defaultContextBytes = 10_485_760 // 10 MiB
```

**变更文件**: 1 个常量定义  
**测试影响**: 无（行为逻辑不变）  
**部署影响**: 配置重载或重启

#### 配置化方案（推荐）

```go
// internal/settings/settings.go
type Settings struct {
	// ...
	// ContextBytes 是归约输出的字节预算（2026-11-23 P1-C：从 1MiB 提升到 5MiB
	// 以容纳单条高清截图消息）。受保护区（最新用户消息 + 活跃工具链）需完整
	// 装入该预算，单条消息超限时返回 422。
	ContextBytes int `json:"context_bytes" default:"5242880"`
}
```

**优点**: 可热更新、可按环境差异化

### 3.3 效果评估

**解决场景**:
- ✅ 1920x1080 PNG 截图（约 1.5-2MB）
- ✅ 1080P 短视频片段（约 2-5MB）
- ❌ 4K 截图（约 5-10MB）仍可能超限
- ❌ 长视频（>10MB）仍触发

**性能影响**:
```
当前：1MiB 预算 × 100 并发 = ~100MB 内存占用
5MiB：5MiB 预算 × 100 并发 = ~500MB 内存占用
10MiB：10MiB 预算 × 100 并发 = ~1GB 内存占用
```

**权衡点**:
- 211/154/245 当前内存充足（32GB/64GB）→ 500MB 增量可接受
- 但预算 ≠ 实际占用（归约后通常远小于预算）
- 真实影响约为理论值的 **20-50%**

### 3.4 优缺点

**优点** ✅:
1. **极简**: 改 1 个常量 / 配置项
2. **安全**: 不改任何逻辑，零回归风险
3. **立即生效**: 重启或配置重载即可
4. **向后兼容**: 对小请求无影响

**缺点** ❌:
1. **治标不治本**: 更大的媒体仍会触发
2. **内存代价**: 预算提升 5-10 倍
3. **延后问题**: 只是把门槛往后推
4. **不优雅**: 没有解决"单条 vs 总预算"的语义冲突

### 3.5 建议配置

**保守方案**: 5MiB
- 覆盖 95% 高清截图场景
- 内存增量可控（~400MB 理论 / ~100MB 实际）
- 与主流 LLM 厂商对齐（Anthropic Claude 单图上限约 5MB）

**激进方案**: 10MiB
- 覆盖 4K 截图 + 短视频
- 内存增量较大（~900MB 理论 / ~200MB 实际）
- 预留未来扩展空间

## 四、方案 2：保护区超限媒体降级为标记

### 4.1 核心思路

当单条受保护消息超过剩余预算时，**不拒绝请求**，而是：
1. 用媒体标记文本替代实际媒体内容
2. 保留消息结构（role / 文本部分）
3. 继续处理（让模型看到"这里有张图但被省略了"）

### 4.2 实施方案

#### 4.2.1 核心改动：file.go 读取降级

```go
// internal/sessioncontext/file.go

// 在 Reduce 函数内，读取受保护区消息时增加降级逻辑
read := func(span largebody.Span, limit int) ([]byte, error) {
	if span.Length < 0 {
		return nil, ErrProtectedContext
	}
	
	// P1-C (2026-11-23): 单条超限时，尝试降级为媒体标记
	if span.Length > int64(limit) {
		// 读取前 1KB 判定是否含媒体
		probeSize := min(1024, int(span.Length))
		probe := make([]byte, probeSize)
		if _, e := f.ReadAt(probe, span.Offset); e != nil {
			return nil, e
		}
		
		// 如果含媒体 → 降级为标记消息
		if hasMediaContent(probe) {
			return createMediaOmittedMessage(probe), nil
		}
		
		// 纯文本超限 → 仍拒绝（合理的"分块"场景）
		return nil, ErrProtectedContext
	}
	
	// 正常读取
	b := make([]byte, int(span.Length))
	_, e := f.ReadAt(b, span.Offset)
	return b, e
}

// 检测媒体特征（复用 r1052 探测列表）
func hasMediaContent(data []byte) bool {
	probes := [][]byte{
		[]byte(`"image_url"`), []byte(`"input_image"`),
		[]byte(`"video_url"`), []byte(`"input_video"`),
		[]byte(`"audio_url"`), []byte(`"input_audio"`),
		[]byte(`"inlineData"`), []byte(`"fileData"`),
		[]byte(`"encrypted_content"`),
	}
	for _, probe := range probes {
		if bytes.Contains(data, probe) {
			return true
		}
	}
	return false
}

// 创建降级消息（保留 role + 文本，媒体变标记）
func createMediaOmittedMessage(probe []byte) []byte {
	// 解析 role（从前 1KB 探测数据）
	var partial struct {
		Role string `json:"role,omitempty"`
	}
	json.Unmarshal(probe, &partial)
	
	role := "user"
	if partial.Role != "" {
		role = partial.Role
	}
	
	// 构造降级消息
	msg := map[string]any{
		"role": role,
		"content": "[Large media content omitted due to context budget constraint. " +
			"The protected message contained media that exceeded the available budget. " +
			"Consider: 1) compress the image/video, 2) use a URL reference, or " +
			"3) split into multiple requests.]",
	}
	b, _ := json.Marshal(msg)
	return b
}
```

#### 4.2.2 Report 增强

```go
// internal/sessioncontext/file.go (Report 结构)
type Report struct {
	// ...
	MediaDegraded int // 降级为标记的媒体消息数（2026-11-23 P1-C）
}
```

#### 4.2.3 监控指标

```go

var (
	// ...
	reduceMediaDegradedTotal = prometheus.NewCounter(prometheus.CounterOpts{
		Name: "gateway_reduce_media_degraded_total",
		Help: "Total protected messages degraded to media omission marker (P1-C)",
	})
)
```

### 4.3 效果评估

**用户视角**:
```
请求前：[user: "分析这张架构图" + 5MB PNG]
请求后：[user: "分析这张架构图\n[Large media content omitted due to...]"]
模型响应："抱歉，我看不到您提到的架构图，它在上下文处理时被省略了。
          您可以尝试压缩图片或通过 URL 分享。"
```

**对比 422 拒绝**:
- ❌ 422: 整个请求失败，用户需重试
- ✅ 降级: 请求成功，模型明确告知媒体缺失原因

### 4.4 优缺点

**优点** ✅:
1. **用户体验最佳**: 请求不被拒绝
2. **治本**: 任意大小的媒体都能处理
3. **信息保留**: 文本部分 + 结构完整
4. **可观测**: 通过标记文本 + 指标监控
5. **符合 r1052**: "不无声消失"原则

**缺点** ❌:
1. **语义变化**: "受保护"不再等于"完整"
2. **下游适应**: 需验证模型对标记文本的响应
3. **实施复杂**: 需改动核心归约逻辑
4. **测试成本**: 需覆盖降级路径的各种边界
5. **潜在混淆**: 用户可能不理解为何媒体消失

### 4.5 风险评估

**高风险点** ⚠️:
1. **下游破坏性**: 如果下游代码假设"受保护区 = 完整消息"，降级会破坏假设
2. **测试盲区**: 现有测试可能不覆盖"受保护消息被改写"场景
3. **语义漂移**: "保护区"从"完整性保证"变成"结构保证"

**缓解措施**:
1. ✅ Report.MediaDegraded 计数 → 可观测
2. ✅ 降级文本明确说明原因 → 可追溯
3. ✅ 只对媒体降级，纯文本超限仍拒绝 → 保持"分块"语义
4. ⚠️ 需全面测试下游消费者（路由 / 计费 / 日志）

## 五、方案 3：422 报错文案优化

### 5.1 核心思路

保持拒绝行为不变，但将**笼统的** "context_budget_exceeded" 改为**明确的** "single_message_too_large"，并给出操作指引。

### 5.2 实施方案

#### 5.2.1 识别单条超限

```go
// internal/sessioncontext/file.go

// 在 Reduce 函数内，增加错误细分
var ErrSingleMessageTooLarge = errors.New("single protected message exceeds context budget")

read := func(span largebody.Span, limit int) ([]byte, error) {
	if span.Length < 0 {
		return nil, ErrProtectedContext
	}
	
	// P1-C (2026-11-23): 区分"单条超限"与"整体超限"
	if span.Length > int64(limit) {
		// 单条消息本身就超过了剩余预算
		return nil, ErrSingleMessageTooLarge
	}
	
	b := make([]byte, int(span.Length))
	_, e := f.ReadAt(b, span.Offset)
	return b, e
}
```

#### 5.2.2 错误文案国际化

```go
// domains/streaming/large_ingress.go

// 在 large_ingress.go:184-200 增加细分处理
body, report, err = sessioncontext.Reduce(prepCtx, g.store, ref, g.config.ContextBytes)
if err != nil {
	status, code := 422, "context_budget_exceeded"
	logMessage := "request cannot produce a valid bounded context; split the protected input"
	rej := ingressRejection{
		clientMessage: i18n.T(r.Context(), i18n.MsgIngressContextBudgetExceeded, map[string]any{
			"Limit": humanByteSize(int64(g.config.ContextBytes)),
		}),
		extra: map[string]any{"body_bytes": ref.Size},
	}
	
	// P1-C (2026-11-23): 单条超限 → 专门文案
	if errors.Is(err, sessioncontext.ErrSingleMessageTooLarge) {
		code = "single_message_too_large"
		logMessage = "single protected message exceeds context budget"
		rej.clientMessage = i18n.T(r.Context(), i18n.MsgIngressSingleMessageTooLarge, map[string]any{
			"Limit": humanByteSize(int64(g.config.ContextBytes)),
			"Message": report.Messages, // 第几条消息
		})
		rej.extra["single_message_budget_exceeded"] = true
	}
	
	// ... 后续错误处理
}
```

### 5.4 优缺点

**优点** ✅:
1. **极简**: 改错误码 + 文案，零逻辑变动
2. **安全**: 无回归风险
3. **可操作**: 给用户明确的解决方案
4. **可观测**: 通过新错误码区分场景

**缺点** ❌:
1. **不治本**: 用户仍被拒绝
2. **需手动操作**: 用户需压缩/分块/重试
3. **体验不佳**: 比方案 2 差很多
4. **治标**: 本质上是"更好的错误信息"

### 5.5 适用场景

**最适合**:
- 作为**短期方案**（快速上线）
- 与方案 1 或 2 **搭配使用**（即使放宽预算，仍可能超限）
- 作为**兜底**（方案 2 实施风险高时的保底选项）

## 九、FAQ

### Q1: 为什么不直接用方案 2？

**A**: 方案 2 改变了"受保护区 = 完整性保证"的核心语义，需要：
1. 验证所有下游消费者的适应性
2. 完善的回滚方案
3. 充分的灰度观察期

方案 1 + 3 组合可以作为快速止血方案，为方案 2 争取实施时间。

### Q2: 5MiB 够用吗？会不会还是不够？

**A**: 根据主流场景分析：
- ✅ 1920x1080 PNG: ~1.5MB
- ✅ 2K JPG: ~2MB
- ✅ 1080P 10秒视频: ~3MB
- ❌ 4K PNG: ~8MB
- ❌ 长视频: >10MB

5MiB 覆盖 **95%** 典型场景。剩余 5% 通过方案 3 的文案给出压缩指引。

### Q3: 方案 2 会不会影响模型回答质量？

**A**: 理论上会，但影响可控：
- ✅ 文本部分完整保留
- ✅ 标记明确说明原因
- ✅ 模型会告知用户"图片缺失"

实际上，模型收到 `[Large media content omitted...]` 比收到 422 错误更有用——
它至少知道"用户想让我看图，但图不在"，可以给出相应引导。

### Q4: 如何回滚？

**方案 1**: 改回常量，重启即可  
**方案 2**: 通过 feature flag 关闭降级逻辑，回退到原始行为  
**方案 3**: 无需回滚（只是文案变化）
