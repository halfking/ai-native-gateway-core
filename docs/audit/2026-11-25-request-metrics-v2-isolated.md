# 请求统计 V2 隔离验收

工作分支为 `codex/request-metrics-v2`，已同步主干 `a5fabfc4e` 的审计更新。初始 PostgreSQL 实测基于 `29b3dfbd5` 上的同一投影代码和迁移字节。后续读路径与双槽演练的基线分别见各节。实验使用 PostgreSQL 17.10 夹具和从同源快照恢复的无网络 211 副本。生产切换需要单独确认。

当前候选采用 211 已投递的 973 投影，兼容迁移为 `983j` 至 `983o`。验收读数见[现行 973 隔离候选](#现行-973-隔离候选)。下文 `983d` 至 `983i` 的记录对应早期隔离实现。

## 投影与迁移

- 采用排序在 983/983b/983c 之后的 `983d_request_metrics_projection`。在自动枚举顺序中执行 preview 的 973，PostgreSQL 因 `public.request_metrics` 尚未创建而退出。211 原始两本台账没有 973、983d 或 988b 投递记录。
- 旧槽按旧表的全局最大 `(occurred_at, request_id)` 取水位。夹具在水位前插入一个晚到事实，同时修订水位上的事实，旧查询只读到下一条请求。按两候选的保留键写入新版行后，旧查询把新版行当成了旧水位。V2 因此使用独立的 `public.request_metrics_projection`，以 `(tenant_id, request_id, occurred_at)` 为主键，保留 983 的实际读写和回退路径。
- 回填按 `(fact_id, occurred_at)` 分批。持久队列记录事实变更及上下文、热会话维度变更。每次以事实版本、终态时间、事实 ID 确定胜出行。发布、队列确认及回填水位同事务提交，两槽用同一行锁仲裁。维度按同租户、同请求 ID 和距离请求时间最近的记录匹配，时间上限为 24 小时。此补数覆盖 `request_context_attrs` 和 `session_turns_hot` 的写入。
- 旧上下文表仍以请求 ID 为唯一键。跨租户同号的终态事实在 V2 中独立投影。历史维度来源如果已发生同号覆盖，单凭现存上下文无法恢复原归属，需核对来源覆盖。
- 上游 925、985–988 与两候选的历史字节不同。211 快照的指纹逐条匹配当前主干。旧候选 988b 的台账回填因此没有进入新投影迁移。

### 可重算日汇总接入

`983e` 在 `983d` 后增加派生表。原请求投影和旧槽水位仍是各自的事实来源。按北京时间整日、租户和流量分类存储可加度量、计量覆盖数、模型集合及精确会话掩码。均值由和与样本数合并，成功率及缓存率所需的计数或 Token 保留原精度。活跃会话用租户和会话联合编号，跨日按位合并去重。日历史分位数仍走原明细路径，币种明细仍以各原币单列。

投影写入通过同事务触发器将受影响日标为待重算。后台每次领取一天，替换度量与成员并在相同事务发布。读侧覆盖完整时使用整日汇总。窗口切到某天内部时，该段读取原投影。写入让某天失效时，该天也读取原投影，直至重算完成。完整窗口的查询单独规划，移除了试验版本中未执行的明细分支触发 JIT 编译的开销。

PostgreSQL 夹具比较了完整日、切边窗、租户和探测流量。跨日修订、删除和晚到会话期间及重算后都与明细逐字节一致。注入提交前失败验证了派生行不外泄。另一组试验让终态投影在日发布持锁期间提交晚到事实，验证待重算标记仍保留，直至第二次重算。两槽并行领取、触发器重放以及两次向下迁移均通过。

### 看板覆盖整日与混合窗口

`983f` 增加可从终态投影重算的看板度量。每日保存维度分布、供应商分子分母、API 密钥位掩码与四种现有趋势粒度所需的度量。多租户总览直接读取预合并的每日全局度量。模型依然按所选窗口全局排行，前六之外的模型由桶总量减去入选模型的度量得出。看板的请求范围、权限过滤、字段和默认粒度沿用原接口。细粒度筛选以及未覆盖的时间段仍读取投影明细。

派生行在同一事务发布。看板和通用日汇总共用日期行锁，投影将当天标为待重算时同步撤销看板发布标记。PostgreSQL 夹具覆盖不同租户、黑盒明细接口、空维度、跨日移动、删除、失败回滚、同名其他模型、探测流量和四种趋势粒度。正式接线前的初版对拍发现空维度会错误落入租户桶，最终实现按分组对应字段取键，修正后整份响应逐字节一致。在 48 万条合成样本上连续初建 90 天耗时 42.3 秒。修正维度键后，单独重算 90 天分布耗时 4.1 秒。派生表和索引实占 726 MB。

### 211 的 973 投递与兼容验证
