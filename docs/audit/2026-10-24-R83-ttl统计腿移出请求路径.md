## §1 背景：为什么 degraded 会长期为 true

R82/R82b/R82c 把**备份摘要腿**修好后，端点的 `degraded_reason` 里仍然长期挂着：

```
"ttl stats unavailable；backup session count unavailable: …；backup summary incomplete: 52/100 个备份文件有损…"
```

⇒ ⇒ **`ttl stats unavailable` 这一项从未消失** ⇒ ⇒ 端点**永远不会**变成 `degraded=false`。

### §1.1 机制

`domains/dbdegradation/ttl_manager.go`（R79 轮已把它从 4 次 SCAN 合并成 2 次）：

```
client.Scan(ctx, cursor, "session:*", 1000)   ← COUNT 1000
client.Scan(ctx, cursor, "ursm:*",  1000)
```

⇒ 生产 `session:*` ~1M 键 ⇒ COUNT 1000 ⇒ **~1000 次往返** ⇒ 远超端点的 5s 预算
⇒ ⇒ 扫描被打断 ⇒ `countSessionScopedKeys` 返回**部分计数 + ctx 错误**
⇒ ⇒ 端点 `degraded = true` + reason `ttl stats unavailable`
⇒ ⇒ **计数在 30 万~83 万之间波动**（取决于被打断的位置）⇒ ★ 这正是「部分计数」的指纹。

### §1.2 为什么不能靠「调大 COUNT」解决

COUNT 只降往返次数，不改**总量**：1M 键无论 COUNT 多大都要**全部读一遍**
⇒ ⇒ 要么在预算内读完（生产读 1M 键 ≫ 5s ⇒ 读不完），要么**不在请求路径上读**
⇒ ⇒ ⇒ 与备份摘要腿（R80~R82b）**同款**的结论：**把成本移出请求路径**。

## §2 R83 的落地

### §2.1 新增 `domains/dbdegradation/ttl_stats_snapshot.go`

`GetTTLStats` 的新行为（**签名不变**：`(map[string]interface{}, error)`）：

```
① 有快照 ⇒ 零 SCAN ⇒ 返回快照 + snapshot_at + snapshot_age_seconds
     ⇒ 快照过期 ⇒ 返回旧快照（真实但旧，**不报错**）+ 触发后台刷新
② 无快照 ⇒ 内联算一次（受请求 ctx 限制）
     ⇒ 算得完 ⇒ 存快照并返回（degraded=false）★ 保住 R79 的「全部成功 ⇒ 不降级」
     ⇒ 算不完 ⇒ 返回**部分统计 + 显式错误**（★ R79 语义保留）
                  且 ★ **不把部分结果进快照**（★ R82 教训：坏结果会冒充好结果）
                  且 ★ 触发后台刷新（单飞，预算 2min）
```

### §2.2 快照必须带年龄

TTL 计数是**活的状态**（session 键不断增删）⇒ 快照是「**某个已知时刻**的真实计数」
⇒ ⇒ 必须让运维知道它有多旧 ⇒ `snapshot_at`（RFC3339）+ `snapshot_age_seconds`
⇒ ⇒ **过期不等于错误**：返回旧快照 + 年龄，让运维自己判断（这才是诚实的做法）。

### §2.3 SCAN COUNT 1000 → 10000

COUNT 只是「每批取多少」的**提示**，**不影响计数结果** ⇒ **口径不变**
⇒ 往返次数降 10× ⇒ 后台刷新（1M 键）从「可能跑不完」变成「十几秒可完成」。

### §2.4 可断言的成本读数

新增 `TTLStatsScans()`（SCAN 次数探针）⇒ 门用它断言「快照命中 ⇒ 请求路径零 SCAN」
⇒ ★ 计时断言天然 flaky ⇒ 用探针（与 R81 的 `SalvageMemberProbes()` 同款思路）。

## §4 诚实边界

1. ⚠ **TTL 计数是「快照」不是「此刻的实时值」** ⇒ 用 `snapshot_age_seconds` 让运维判断；
   快照 TTL 60s ⇒ **每分钟最多一次全量 SCAN**（而不是每个请求一次）。
2. ⚠ **快照里的计数不参与任何清理决策**（已核实：只有 2 个只读调用方）⇒ 不会误删。
3. ⚠ **首次请求仍会看到 `ttl stats unavailable`**（没有快照）⇒ 十几秒后后台刷新完成 ⇒
   后续请求拿到完整快照 ⇒ **`degraded` 会转 false**（生产读数见 §5）。
4. ⚠ **`degraded=false` 不代表端点全绿**：备份腿仍会报「52/100 有损 + 会话数不可用」
   ⇒ ⇒ 这是**诚实**的（备份文件确实损坏、记录确实没有会话维度）。
5. ⚠ 本轮**未做**：per-file 增量缓存（备份摘要腿仍每次全量重算）⇒ 属主裁决项。
