# R92 · `?model=` 仍 500@30s：R90 结论被证伪，真因是**稀有过滤 ⇒ 外层扫 35 万会话**

> 轮次标签 **2026-10-27**（沿用 R87~R91 口径）；**实测时钟 2026-10-24**（本机 / 252 / 154 三方一致）。

## 0. 一句话结论

R90 把四条过滤路径改成「hot ∪ 父表两腿 EXISTS」并宣称全部修好，**上线后的生产验收证明那是错的**：
`?api_key_id=` / `?provider=` / `?status_code=` 三条已 200，★ **`?model=` 仍 500@30s**。
真因不是「形状」而是**稀有度**：该 model 只命中 **30 / 441,112 个会话**，而会话列表是
`ORDER BY s.updated_at DESC LIMIT 21` ⇒ **必须扫到凑够 21 行** ⇒ 实测外层扫了 **350,354 个会话**。
修法是**两条腿缺一不可**：**model 维度索引**（让轮次侧可枚举）+ **「派生表 UNION ALL + 单一 EXISTS」形态**
（让规划器能自己选驱动方向）⇒ `?model=` **30,008 ms → 8.0 ms**，而两条常见过滤**不劣化**（48.6 / 249.6 ms）。

## 2. 归因（252 生产只读实测，2026-10-24）

### 2.1 稀有度：同一形状，稀有度差 4 个数量级

| 过滤值 | 命中轮次 | 命中会话 | 生产耗时 |
|---|---|---|---|
| `model=deepseek-ai/deepseek-coder-6.7b-instruct` | **458** | **30** | **30,008 ms（500）** |
| `provider=14` | 181,907 | 大量 | 0.358 s |
| `status_code=500` | 671,117 | 大量 | 0.554 s |
| `api_key_id=105` | — | 28,263 | 0.216 s |

`public.sessions` = **441,577 行 / 441,112 个会话**；会话列表固定
`ORDER BY s.updated_at DESC, s.session_id DESC LIMIT 21`
⇒ ★ **稀有过滤值 ⇒ 必须扫穿整个会话表才凑得出 21 行**。

### 2.2 外层扫描量：EXPLAIN 实测

```
Index Scan using sessions_2026_09_updated_at_session_id_idx  → Rows Removed by Filter:  72,455
Index Scan using sessions_2026_10_updated_at_session_id_idx  → Rows Removed by Filter: 277,899
⇒ 外层共扫 350,354 个会话才凑出 21 行（父表侧另有 458 行匹配）
```

### 2.3 ★ 排除项一：不是「统计信息陈旧」

| 表 | last_analyze | last_autoanalyze |
|---|---|---|
| session_turns | 2026-10-19 00:53 | — |
| session_turns_2026_10 | — | 2026-10-24 00:14 |
| session_turns_hot | 2026-10-24 17:36 | 2026-10-24 18:14 |

`pg_stats`：`model` n_distinct=567、MCV 100 个、top_freq 0.16；
规划器对 `model = 'deepseek-ai/...'` 的行数估计 **109 + 19 = 128**，实际 **458** ⇒ 只低估 3.6×。
⇒ ★ **「VACUUM ANALYZE 就能修」被排除**（省下一次生产写）。

### 2.4 ★ 排除项二：不是「视图反连接」（那是 R90 已修的）

R90 已把视图（hot 腿带 `NOT EXISTS` 反连接）换掉 ⇒ 现在的形态里**没有视图**。
⇒ 本轮要解决的是**驱动方向**，不是「每行的反连接成本」。

### 2.5 ★ 机理：OR 形态**锁死了驱动方向**

- R90 形态 = `EXISTS(hot) OR EXISTS(parent)` ⇒ 规划器只能**会话驱动**
  （外层扫会话、每行去 EXISTS 里查轮次）。
- **派生表 UNION ALL + 单一 EXISTS** ⇒ 派生表可被 planner **pull-up**
  ⇒ 半连接的两个驱动方向都可选：
  - 稀有 ⇒ **轮次驱动**（先枚举 458 个匹配轮次 → 30 个会话 → 外层只剩 30 行）
  - 常见 ⇒ **会话驱动**（前 21 个会话立刻凑齐）

★ 而 **JOIN 形态（V3，把轮次驱动写死）是错的**：实测在常见过滤上退化到 **10,080 ms**
（规划器只能走轮次驱动 ⇒ 顺序扫 110 万轮）。

## 3. 修法

### 3.1 代码侧：`db.SessionFamilyTurnsSessionExistsSQL` 的形态（V2）

```go
func SessionFamilyTurnsSessionExistsSQL(colExpr, colName, pred string) string {
	return "(EXISTS (SELECT 1 FROM (" +
		"SELECT t.tenant_id AS tenant_id, t.session_id AS session_id, " + colExpr + " AS " + colName +
		" FROM public.session_turns t" +
		" UNION ALL " +
		"SELECT t.tenant_id, t.session_id, " + colExpr +
		" FROM public.session_turns_hot t" +
		") ft WHERE ft.session_id = s.session_id AND ft.tenant_id = s.tenant_id AND " + pred + "))"
}
```

★ `colExpr` 用别名 `t`（`db.SessionFamilyAPIKeyIDExpr` 依赖它），
派生表别名 `ft`，`pred` 引用 `ft.<colName>`。

### 3.2 数据库侧：**startup 迁移 905**（两条 model 维度复合索引）

- `public.session_turns (model, tenant_id, session_id)` —— 分区父表 ⇒ 自动传播到子分区
- `public.session_turns_hot (model, tenant_id, session_id)` —— 3,073 行

★ **只给 model 建索引**：provider n_distinct=20、status_code n_distinct=8 ⇒ 没有选择性
⇒ 建索引会让规划器更倾向「轮次驱动 + 大哈希构建」⇒ 实测退化到 10,080 ms。
★ 该「故意不建」的决定被门禁**带理由钉住**（`TestMigration905_IndexColumnMatchesGoFilterColumn`）。

|---|---|---|
| 旧形态（R90 两条 OR 腿 EXISTS） | 17,501 ms ✗ | 0.358 s ✓ |
| 只加索引、不改形态 | 17,501 ms ✗ | （仍会话驱动） |
| JOIN 派生表（V3，轮次驱动写死） | 8.0 ms ✓ | **10,080 ms** ✗✗ |

| 族 | only_r90 | only_v2 | r90_rows | v2_rows |
|---|---|---|---|---|
| model（稀有） | **0** | **0** | 21 | 21 |
| provider='14' | **0** | **0** | 21 | 21 |

★ 结构上等价：旧形态 =「hot 腿 EXISTS ∨ 父表腿 EXISTS」，

## 7. 诚实边界

1. ★★ **V2 形态的「轮次驱动」分支硬依赖 905 的索引**：无索引时实测 V2/model=稀有 = **205,708 ms**
   （规划器退化成「每行对 110 万轮顺序扫」的嵌套循环半连接）。
   生产上由**启动迁移在切换前**建好索引 ⇒ 窗口为 0；
   但若索引被回滚而二进制未回滚 ⇒ HTTP 症状与今天**相同**（30s 语句超时 ⇒ 同样 500@30s），
   **不更差**，只是白烧 30s DB 时间。
2. ★ 只给 model 建索引 ⇒ **provider/status_code 的极稀有值**仍可能慢（它们没有选择性 ⇒ 不值得建索引）。
   实测常见值是 48.6 / 249.6 ms；极稀有值的上界**本轮未测**。
3. ★ 本轮**没有**动跨分区去重子查询（`turnsSessionsLatestPartitionSQL`）：
   它在「深扫」形态下每行跑 6 个分区索引探测（实测 350,429 次循环）⇒ 是另一个可观的杠杆，
   但改它要处理 `MAX()` 与 `ORDER BY … LIMIT 1` 的 NULL 语义差异 ⇒ 划为独立议题。
4. ★ 只改了 `?model=` / `?provider=` / `?status_code=` / `?api_key_id=` 四条**会话列表**过滤；
   `loadTurnsForSessions`（会话内轮次展示）仍读视图（**会话级读** ⇒ 无 LIMIT 深扫 ⇒ 不是本轮病灶）。
5. ★★ **`admin` 包整包跑出 600.8 s 超时 —— 既有红，非本轮引入（已用独立 worktree 定性）**：
   本轮跑 `go test ./admin/` 整包 ⇒ **FAIL 600.847s（超时）** ⇒ 看着像新引入的回归。
   ★ 用 **origin/main 的独立 worktree 复跑同一包**（`bg_d5a4a6a7`）⇒ **同签名**：
   两边都卡在 `TestDataLifecycleStorageOverviewFieldsAreComplete`（真库端点，恒慢），
   且**都不是断言失败而是超时** ⇒ ⇒ **既有红** ⇒ 本轮**不动**它
   （划为独立议题：data-lifecycle 存储概览慢；它同时对应「恒失败且产出恒空的 12 s 趋势腿」那个待裁决项）。
   ⇒ ★ **纪律**：「超时」与「失败」是两种签名，判责任必须有 **同包 + 同门 + 独立 worktree** 的对照读数。
6. ★ **本地真库规模比生产小 3 个数量级** ⇒ 本地门的「跑通」只能证明**形态正确 + 无运行期错误**，
   **不能**证明生产计划形态；生产形态的证据在 §2/§4 的 252 实测里。

   R90 的四条过滤里**三条真的修好了**、**一条没修好**，而「四条全修」写进了结论。
   ⇒ ★ **形状门证明「改成了什么形态」，不证明「端点不再超时」** ⇒ 形状门之后必须有一道
   **生产端点级读数**（含**稀有取值**，否则测的是快路径）。
2. ★★★★ **稀有度会独立地制造 100 倍以上的差距** ——
   同一形状下 `provider=14` 0.358 s、`model=X` 30,008 s。
   ⇒ ★ **验收必须至少取一个「稀有的真实取值」**；只测热门取值 = 只测快路径。
3. ★★★★ **OR 组合的子查询会锁死驱动方向；派生表（可 pull-up）才能让规划器选** ——
   ⇒ ★ **写半连接时，「驱动方向由谁决定」必须显式设计**，否则规划器只能在
   「会话驱动」和「轮次驱动」里被动挑一个，而挑错的那个在稀有度极端时是灾难。
4. ★★★★ **「只加索引」与「只改形态」都不够，实测是乘法关系** ——
   只加索引：17,501 ms（仍会话驱动）；只改形态：205,708 ms（轮次侧顺序扫）；
   两者合起来：8.0 ms。⇒ ★ **修「慢计划」要先问「瓶颈在两侧的哪一侧」**，
   两侧都要动才有效。
5. ★★★ **门禁的正则窗口会跨条目** ——
   「索引名 + 200 字符窗口」在两条相邻的 CREATE INDEX 之间会**互相顶替** ⇒ 漏判。
   ⇒ ★ **结构化文本应当按分隔符切句后逐条比对**，而不是开窗口匹配。
6. ★★★ **Go 的 RE2 不支持负向先行断言** ——
   写 `(?!CREATE INDEX)` 这类约束会**直接 panic**（编译期才发现）⇒
   「窗口内不得出现 X」这类需求必须换实现方式。
7. ★★★ **「故意不做」也要钉住** ——
   「每个过滤列都必须有索引」会把**故意不建索引**的列判成违规；
   正确形态是**带理由的例外清单**（把决定钉住，而不是放任漂移）。
