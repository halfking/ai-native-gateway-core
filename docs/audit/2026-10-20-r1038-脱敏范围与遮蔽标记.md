# 2026-10-20 r1038 — 脱敏范围（地址族）与遮蔽标记（每处必带类型）

> 起因：用户报告反复看到 `export https_proxy=http://[REDACTED]:7890 http_proxy=http://[REDACTED]:7890`，
> 并给出两条口径：①「原则上每个占位符都有特殊的标记」；②「脱敏的范围应该不包含
> 域名、地址、ip这些内容，这些不是足够敏感」。
> 验收原文（用户逐字给出，命令必须仍可复制执行）：
>
> ```
> export https_proxy=http://127.0.0.1:7890 http_proxy=http://127.0.0.1:7890
> git config --global http.proxy $http_proxy
> curl -o /dev/null -w '%{http_code}\n' https://github.com      # 期望 200
> git clone --depth 1 https://github.com/octocat/Hello-World /tmp/gt   # 期望成功
> ```

## 一、结论先说

用户看到的 `[REDACTED]` **是**网关脱敏造成的，且有**两个独立缺陷**：

| 缺陷 | 现象 | 本轮修法 |
|---|---|---|
| D1 | 已在发布规则里的**地址族规则**会在**输出面**遮蔽 IP，产出 `http://[REDACTED:server_ip]:7890` | 地址族在脱敏面**一律放行**（fallback 与托管规则同口径），只撤遮蔽、不撤检出 |
| D2 | 类型不可知时遮蔽物退成**裸** `[REDACTED]`，客户端无从追问遮掉了什么 | 遮蔽物**一律带类型**；类型确实不可知时是 `[REDACTED:unknown]` |

另有第三条**代码级缺口**（本轮一并补上）：legacy `pii_patterns` 导入把 `ip` 类行造成
`type=server_ip / scopes=[output] / action=mask` 的规则 —— 这是 D1 的**触发器**。
851 迁移停用的是 **DB 行**（数据修复），而基线快照**不可变**：851 之前发布过基线的部署，
拿到的快照里那行仍然是 enabled ⇒ 遮蔽会一直存在，直到有人手工重发一版规则。

### 2.3 根因定位（代码侧）

`security/sanitize/detector.go` 的 `DetectScope`：

```go
if snapshot == nil && scope != ScopeEgress && scopedType(p.sType) {
    continue
}
```

`snapshot == nil` 意味着「**不是托管规则**」。于是：

- **内建 fallback**（`snapshot == nil`）：地址族在脱敏面被排除 ✓（r1010 的修复）；
- **托管 / 已发布规则**（`snapshot != nil`）：**没有这层排除** ✗。

而输出侧的判定面正是托管路径：

- 输入侧 `SanitizeInput` → `DetectScope(ScopeInputDeclarations)` ⇒ 相位 **"input"**
  ⇒ 只挂 `output` 相位的地址规则**不适用**；
- 输出侧 `outputSensitiveChecker.Check` → `detector.Detect`（= `ScopeRedact`）
  ⇒ 相位 **"output"** ⇒ **legacy 地址规则正是在这里适用**。

⇒ 用户报告的形态（**响应里**出现 `http://[REDACTED]:7890`）精确对应这条路径。
变异验证实测：把排除条件改坏后，输出立刻变成

```
export https_proxy=http://[REDACTED:server_ip]:7890 http_proxy=http://[REDACTED:server_ip]:7890
```

——与用户 2026-10-10 报告的 `http://[REDACTED]:7890` **同形**（当时标记是裸形态，
本轮 D2 修完后带类型）。

### 门禁自身的一次返工（重要）

第一版门禁写在**输入面**，而输入面走 "input" 相位、legacy 地址规则挂 "output"
相位 ⇒ **该规则在输入面压根不适用** ⇒ 门禁**恒绿**（假绿）。变异验证时只有边界那条
转红，主门禁纹丝不动 —— 靠变异验证才发现。

改法两条：① 输出面单独设门（用户症状所在的那条路径）；② 输入面的门改用
**同时挂 input 相位**的规则形态，并配**结构性前提断言**（规则在快照里 / 作用域 /
正则确实匹配），而不是「另一个面看得见」。

## 六、遗留（不擅自改，留给 owner 裁决）

**`pii.address`（中文地址规则）7 天命中 90,091 次**，且误伤面是**运营编号**：

```
'员工工号 12345'   → 整段被当成地址遮蔽
'订单号 20241012'  → 同上
'任务号 88' / '房间号 1201' / '工单号 12345' → 同上
'北京市朝阳区建国路88号' → 真地址（应遮）
```

根因是规则的**前导字符类**含「号」——「号」既表示门牌号，也命中「工号 / 订单号 /
房间号」这类标签词的尾字。

**为什么不在这轮改**：① r1036（2026-10-20，154 生产取证）**明确冻结**了这个行为
（`TestR1036NonAddressLabelWithoutPreciseTypeUnchanged` 断言「订单号 20241012」→
`{SENSITIVE:custom:1}`），理由是「修复只处理 custom 内含精确类型子片段，不重新解释
地址规则的其他命中」；② 用户本轮的「地址」指的是**网络地址**（示例里的 proxy host
与其并列的域名、ip），不是中文邮政地址；③ 改它会缩小 PII 覆盖面，属安全姿态变更。

**建议（owner 一句话即可裁决）**：把规则的**前导**字符类去掉「号」，**后置**类保留
（`[^\s]{2,}[省市区县镇乡村路街道巷弄栋单元室]\s*[\d\-号栋单元室]+`）——
真地址（`建国路88号` / `文三路100号`）仍命中（后置类里有「号」），而
`工号 / 订单号 / 任务号 / 房间号` 这一族不再命中。**注意这与 r1036 的顾虑不同**：
r1036 反对的是删掉**后置**的「号」（那会让真地址整体失效），本建议只动**前导**类。
