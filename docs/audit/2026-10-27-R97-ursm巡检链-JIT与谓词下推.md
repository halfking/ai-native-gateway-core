## §1 怎么找到的：pgss 按库拆开后的榜首

252 是**混库实例**（§143.19 的教训：慢查询清单必须按 `dbid` 拆库）。
把 `pg_stat_statements` 按 `dbid` 拆开后，指向本仓语句的榜首是：

```
llm_gateway | 79 calls | 20,278.7 s | mean 256.7 s | max 591.6 s | uses_rollup=f
   WITH win AS ( SELECT date_trunc($1, now() - make_interval(hours => $2)) AS lo, ...
```

同一批里另有：

```
llm_gateway | 24 calls |  2,751.2 s | mean 114.6 s | max 284.6 s | uses_rollup=t   ← ★ 现在跑的是这条
llm_gateway | 21,247,030 calls | 8,011.9 s | mean 0.0 ms | max 1.0 ms | INSERT INTO ursm_node_snapshot_min
llm_gateway |  7 calls |    894.7 s | mean 127.8 s | max 188.3 s
llm_gateway |  4 calls |    223.5 s | mean  55.9 s | max 102.9 s   ← 汇总表刷新作业（每 6 小时）
llm_gateway |  3 calls |    252.8 s | mean  84.3 s | max 123.1 s   ← 巡检自己的「量具自检」探针
```

`uses_rollup` 这一列是**本次归因的关键判别**：PG 会把不同文本的语句分成不同的
pgss 条目，所以「用了汇总表的那条」和「没用的那条」是**两条独立记录** ——
⇒ ★ **不要把 79 calls 那条当成「现在在跑的」**。

## §3 缺陷①：「今天」这条腿的谓词不可下推

`BUCKETS_SQL_DAILY` 的 `base_buckets` 是「汇总表 UNION ALL 今天实时读源表」。
今天那条腿（修前）：

```sql
   WHERE snapshot_ts >= date_trunc('$G_UNIT', $NOW_EXPR - make_interval(days => $BASELINE_DAYS))
     AND snapshot_ts <  (SELECT lo FROM win)
     AND $G_TRUNC snapshot_ts) >= (now() AT TIME ZONE current_setting('TimeZone'))::date::timestamptz
```

第 3 个条件是**列上的函数表达式**。PG 的规划器**不能**把它换成 `snapshot_ts` 的
范围条件 ⇒ 它只能当 **Filter** 挂在第 1 个条件（7 天前）那个 **Index Cond 之上**。

252 实测（`EXPLAIN`，不带 ANALYZE）：

```
->  Parallel Append
      ->  Parallel Index Only Scan using ursm_node_snapshot_min_20261019_pkey ...
            Index Cond: ((snapshot_ts >= date_trunc('hour', now() - '7 days')) AND (snapshot_ts < date_trunc('hour', now())))
            Filter: (date_trunc('hour', snapshot_ts) >= ((now() AT TIME ZONE ...)::date)::timestamptz)
      ->  Parallel Index Only Scan using ursm_node_snapshot_min_20261017_pkey ...   ← 同款
      ... 20261018 / 20261020 / 20261021 / 20261022 / 20261023 / 20261024
```

⇒ ★★ **8 个分区全被扫**，其中 **7 个分区的行扫完即丢**（Filter 恒为假）。
这就是「快路为什么还慢」的第一层原因。

### 修法与等价性证明

把第 3 个条件改成**纯范围谓词**：

```sql
     AND snapshot_ts >= (now() AT TIME ZONE current_setting('TimeZone'))::date::timestamptz
```

它直接成为 **Index Cond** ⇒ 只扫今天那一个分区，其余分区 `Subplans Removed` / `never executed`。

**等价性**（必须成立，否则这就是口径改动）：令 `T` = 本地日期零点（恰好落在
hour / minute 的边界上），`ts ∈ timestamptz`：

- (a) `ts >= T` ⇒ `date_trunc(unit, ts) >= date_trunc(unit, T) = T`（`date_trunc` 单调不减；`T` 本就在 unit 边界上 ⇒ 截断后不变）；
- (b) `ts < T` ⇒ `date_trunc(unit, ts) < T`（否则 `ts` 与 `date_trunc(unit, ts)` 落在同一个 unit 桶里，而该桶下界 `>= T` ⇒ `ts >= T`，矛盾）。

⇒ 合起来：`date_trunc(unit, ts) >= T ⟺ ts >= T`。
★ 边界：夏令时「午夜不存在」的时区里 PG 会把零点规范化到 01:00，而 01:00 仍在
unit 边界上 ⇒ 等价性照旧（Asia/Shanghai 自 1991 年起无夏令时）。
★ **本地真库穷举验证**：以 1 分钟为步长覆盖今天零点 ±2 天共 **5,761 个时间点**，
两种粒度下差异均为 **0**（门 `TestSection14397TodayLegPredicateIsEquivalentOnRealDB`）。

## §4 缺陷②：每小时的 JIT 重编译

巡检的 `de()` 每条查询都起一个**新的 psql 会话** ⇒ 后端一连就退
⇒ ★ **PG 的 JIT 编译产物缓存在后端内存里** ⇒ 下一轮**全部重新编译**。

252 实测（`EXPLAIN (ANALYZE)` + `jit_explain=on`）：

```
=== 现状（无下推，jit=on）===
  Functions: 259
  Timing: Generation 45.118 ms (Deform 3.433 ms), Inlining 857.426 ms,
          Optimization 2871.232 ms, Emission 3387.077 ms, Total 7160.853 ms
  Execution Time: 61439.248 ms

=== 下推后（jit=on）===
  Functions: 181
  Timing: Generation 28.810 ms (Deform 4.233 ms), Inlining 1476.864 ms,
          Optimization 2647.788 ms, Emission 2397.474 ms, Total 6550.937 ms
  Execution Time: 19776.393 ms

=== 下推后（jit=off）===
  Execution Time: 14428.455 ms
```

⇒ ★★ **6.55 s/次**的纯编译时间，×24 次/天 ≈ **157 s/天**，与判据结果毫无关系。

**修法**：`de()` 的 `PGOPTIONS` 加 `-c jit=off`。
★ 只关**本脚本自己的会话** ⇒ 不波及共享库上的业务会话；
★ 改服务端 `jit_above_cost` 会波及所有人 ⇒ 那是属主决策项，本轮**不做**。
★ 语义零影响：JIT 只是编译器，PG 保证编译前后结果逐字相同（A/B 实测同证）。

（同一段数据），每个变体**独立 psql 会话**（⇒ 每次都是真实的「一次性会话」形态），
**交错**跑 4 轮，取中位。

| 变体 | R1 | R2 | R3 | R4 | **中位** |
|---|---|---|---|---|---|
| A0 现状（无下推 + jit 开） | 135.0 | 40.7 | 62.4 | 77.8 | **70.1 s** |
| A1 仅 `jit=off` | 41.8 | 31.9 | 38.5 | 37.9 | **38.2 s** |
| A3 下推 + jit 开 | — | — | 26.9 | 19.2 | 23.0 s |
| **A2 下推 + `jit=off`** | 12.7 | 19.5 | 16.2 | 16.5 | **16.4 s** |
| A4 下推 + F3 + `jit=off` | — | — | 81.1 | 70.0 | 75.5 s |
| A5 下推 + F3 + jit 开 | — | — | 84.1 | 68.5 | 76.3 s |

★ **口径一致性**：18 次运行的 10 个判据字段，**唯一值只有一个**：
`3|0|0|0|0|3|132643|133616|133778|100` ⇒ 六个变体（含被弃的 F3）判定逐字相同。

★ **同会话口径**（`EXPLAIN (ANALYZE, BUFFERS)`，缓存状态一致 ⇒ 最干净）：
**61,439 ms → 19,776 ms（下推，−67.8%）→ 14,428 ms（再关 JIT，−27.0%）** ⇒ 合计 **4.26×**。

★ **配对比值**（同轮内 A0→A2）：10.6× / 2.1× / 3.9× / 4.7× ⇒ 中位 **4.3×**。

⚠ **诚实边界（共享库读数）**：A0 的四轮跨度是 **40.7 ~ 135.0 s**（冷缓存 + 负载波动），
**单次读数不可比** ⇒ 这就是 AGENTS.md 里「共享库单次读数没有可比性」那条纪律的又一次实证。
本轮靠**交错多轮取中位 + 同会话 EXPLAIN** 两层证据把结论钉住，**没有**用单次读数下结论。

### ★★ 顺带查清的一件事：午夜存在**覆盖空洞**

三轮 live 对照全落在 `base_source=source` ⇒ 查因：

```
[2026-10-25 00:07:04] start ursm-snapshot-slot-refresh … now=2026-10-25 00:07:04
[2026-10-25 00:07:06] coverage_before=6/7 days
[2026-10-25 00:07:06] plan days_back=8 reason=repair
[2026-10-25 00:09:32] refreshed rows=192 days_back=8 reason=repair
[2026-10-25 00:09:33] coverage_after=7/7 days
```

★★ 机制：跨过 00:00 ⇒ 「今天」变成新的一天 ⇒ 快路的基线窗下界也前移一天
⇒ 而汇总表按设计**不含今天** ⇒ 新的一天**此刻还没被补进汇总表**
⇒ ⇒ 覆盖天数从 7 掉到 6 ⇒ ★ **低于 `BASELINE_DAYS`** ⇒ 巡检**自动回退到源表路**。
★ 这个回退是**既有设计**（「慢，但不失明」），不是本轮引入的。
★ **自愈**：刷新作业（cron `7 */6 * * *`）在 00:07 发现 `coverage_before=6/7`
⇒ 自选 `days_back=8 reason=repair` ⇒ 00:09:33 恢复到 **7/7**。
★ ★★ **对 cron 的影响 = 无**：cron 的巡检在 **:17** 跑，而刷新作业在 **:07** 已恢复覆盖
⇒ ⇒ 00:17 那轮实测 `base_source=daily`、`slot_daily_cov_days=7` ⇒ **走的是快路** ✓。
⇒ ⚠ **但仍留下一条口径事实**：★ **每天 00:00~00:07 之间，任何手动触发的巡检都会走慢路**
（`base_source=source`）⇒ ★★ **读数必须带 `base_source=` 这一列才有意义** ——
★ 这也是 §5 那两条 pgss 记录**不能混着比**的根因。

### 折算到日常

pgss 里快路那条的均值 **114.6 s** × 24 次/天 = **2,751 s/天**；
修后中位 16.4 s × 24 = **394 s/天** ⇒ 省 ≈ **2,357 s/天 ≈ 39 分钟/天**的共享库 DB 时间。
⚠ 这是**按中位**折算，pgss 均值里含冷缓存轮 ⇒ 真实节省区间约 **2,000~2,400 s/天**。

## §6 ★ 阴性结论：F3（把 `base_active` 的 slot 过滤改成可下推的 `EXISTS`）**实测是反效果**

修完之后，剩下的成本分布（`EXPLAIN (ANALYZE)` 节点耗时）：

```
CTE joined        570.9 .. 693.2 ms      ← cur 腿（3 小时窗）
CTE slot_ref   13,640.9 .. 13,843.9 ms   ← ★ 基线腿 = 剩余 14.4 s 的 94.6%
   ├ base_buckets（今天腿，下推后）        2,845.1 ms      ← 只扫今天一个分区
   └ base_active（3 天扫 + slot 过滤）    10,794.3 ms      ← ★ 主项
        Hash Join (actual rows=773027)
          ->  Append (actual rows=8226068)   ← ★ 读进 822 万行，只留 77 万
                Index Only Scan 20261021 / 20261022 / 20261023 / 20261024
```

⇒ `base_active` 的过滤 `AND extract(hour from date_trunc('hour', snapshot_ts))::int IN (SELECT slot FROM joined)`
**同样不可下推** ⇒ PG 只能把 3 天的 822 万行读进来再用 Hash Join 过滤（丢掉 90.6%）。

**看起来显然的修法**：把这个过滤改写成可下推的**区间**形式 ——
`EXISTS (… snapshot_ts >= 某日某小时 AND snapshot_ts < 某日次小时 …)`，
把 3 天 × 3 小时变成 12 个可下推的范围。

★ **实测结果：A4/A5 中位 75.5 / 76.3 s，是 A2（16.4 s）的 4.6 倍慢。**
