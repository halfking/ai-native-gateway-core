### 1.2 供应商对账（`/admin/reconciliation?view=provider`）

**数据源**：`report_snapshots` 表的 `daily_grain` scope（**每日快照**）

**查询链路**：
1. `admin/report_rollup.go:handleReportRollup` → 路由分发
2. `domains/reportrollup/grainreport.go:BuildGrainReport` → 构建报表
3. `domains/reportrollup/grain.go:GrainScopes(ViewProvider)` → 返回 `ScopeDailyGrain`
4. 查询 `report_snapshots` 表，`WHERE scope = 'daily_grain'`

**快照生成逻辑**（`domains/reportrollup/grain.go:77-192`）：
```go
// grainDaySQL 最细粒度日聚合。两个口径共用一段 SQL：businessOnly 只切换
// traffic_class 过滤（provider 面全流量 / internal 面业务流量）。
func grainDaySQL(businessOnly bool) string {
    classFilter := ""
    if businessOnly {
        classFilter = "\n      AND traffic_class = 'business'"
    }
    return `
WITH f AS (
    SELECT provider_id, credential_id, api_key_id, tenant_id, ...
    FROM usage_facts
    WHERE occurred_at >= $1 AND occurred_at < $2` + classFilter + `
),
...
`
}

func queryGrainDay(ctx context.Context, q Querier, scope Scope, ...) {
    rows, err := q.Query(ctx, grainDaySQL(scope == ScopeInternalGrain), start, end)
    // scope == ScopeDailyGrain 时，businessOnly = false → 全量
    // scope == ScopeInternalGrain 时，businessOnly = true → 业务流量
}
```

**关键**：
- `daily_grain` scope 的 `businessOnly = false` → **全量流量**（含探测）
- 快照由 `RollupDay` 函数每日聚合生成，写入 `report_snapshots` 表
- **快照生成依赖后台 worker 定时执行**

### 1.3 两者的理论口径对照

| 维度 | 看板（含探测） | 供应商对账 |
|------|----------------|------------|
| 数据源 | `usage_facts` | `report_snapshots.daily_grain` |
| 时效性 | **实时** | **快照**（每日聚合） |
| 探测过滤 | 无（全量） | 无（全量） |
| 生成方式 | 直接查询 | 后台 worker 聚合 |

**理论上**：看板（含探测）= 供应商对账（都是全量）

**实际上**：173.9K ≠ 144,958（相差 20%）

## 二、差异根因分析

### 2.1 根因：快照数据不完整

**证据链**：

1. **代码证据**（`domains/reportrollup/rollup.go:5-8`）：
   ```go
   // 数据流：usage_facts（请求级真相源，含 success/failure/rate_limited 终态、
   // error_kind 分类、四类 token、供应商成本 cost_amount 与内部计费
   // credits_charged）→ RollupDay 按天聚合成**八个** scope 的快照行写入
   // report_snapshots（迁移 745+746+759）→ 区间汇总读面只读快照行按任意时间
   // 区间（日/周/月/自定义）二次汇总。日维度落地一次、区间汇总不回扫原始
   // 请求日志。
   ```

2. **快照缺失语义**（`admin/report_rollup.go:22-24`）：
   ```go
   // 快照缺失语义：区间内当日无快照行 = worker 未跑或当日无流量，summary 以
   // snapshot_dates 透出覆盖日期，不视为错误（与 stats 的 STATS_NOT_MIGRATED
   // 降级同思路：表缺席时返回 degraded 而非 500）。
   ```

3. **用户实测数据**：
   ```
   时间范围：2026-11-17 到 2026-11-23（7天）
   看板（含探测）：173,900 请求
   供应商对账：144,958 请求
   差异：28,942 请求（16.7%）
   ```

**结论**：
- 供应商对账少统计了约 **29K 请求**（16.7%）
- 这些请求**存在于 `usage_facts` 中**（看板能查到）
- 但**不在 `report_snapshots.daily_grain` 中**（供应商对账查不到）
- **原因**：快照 worker 未完整执行或部分日期快照缺失

### 2.2 费用差异的解释

```
看板（含探测）：173.9K 请求 / $8,502
供应商对账：144,958 请求 / $6,306
```

**单请求平均成本**：
- 看板：$8,502 / 173,900 ≈ **$0.0489/请求**
- 供应商对账：$6,306 / 144,958 ≈ **$0.0435/请求**

**差异原因**：
- 缺失的 29K 请求中，成功请求占比更高（产生更多成本）
- 或者缺失的是特定高成本模型的请求

### 2.3 "未落定"的真实含义（修正）

**第一版错误**：认为"未落定"是失败请求

**真相**（`web/src/api/reportrollup.ts:34-35` + `components/reconciliation/ReconciliationToolbar.vue:54-61`）：
```typescript
/** 未落定维度的哨兵 id（未路由到 provider 的失败行没有这些维度）。 */
export const UNASSIGNED_ID = -1

/**
 * id 类维度（供应商 / 凭据 / apikey）下拉的展示名：-1 是「未落定」哨兵
 * （未路由到 provider / 未落到具体凭据 / 未落到具体 apikey 的失败行）。
 */
```

**正确理解**：
- "未落定"= `provider_id=NULL` 的请求（已终态）
- 通常是**路由前失败**或**未选中供应商就失败**的请求
- 68,033 个"未落定"请求都是**失败请求**，$0 成本
- **这与数据不一致无关**，只是失败请求的一个子分类
