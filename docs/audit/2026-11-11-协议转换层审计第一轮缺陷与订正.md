## 一、订正上一版审计的两处误报

第一版审计（`TEST_EXECUTION_REPORT.md`）把两个**已实现**的能力报成缺陷。根因是**探针打错了层**：

| 上一版结论 | 实际情况 | 证据 |
|---|---|---|
| ❌ "Anthropic 缺少 max_tokens 默认值" | ✅ 序列化层已填 `4096` | `internal/ir/serialize_anthropic.go:1314` `anthropicMaxTokens()` |
| ❌ "孤立 tool_result 未被过滤" | ✅ `SanitizeToolMessages` 已清理，且已接进生产管线 | `internal/ir/validate_and_fix.go:74`；`domains/streaming/executors/executor_chat.go:3046/3138/3206` |

**通用式（写入本轮纪律）**：
> ★ **验收「客户端可见行为」不看中间态，看 wire。**
> ★ IR 层记的是**客户端真实意图**（max_tokens=0 表示"客户端没给"），
> ★ 默认值属于**线级语义**（线上必须有 >0 的 max_tokens）。
> ★ 把断言打在 parse 层 ⇒ 既会误报已实现的能力，也会漏掉真正的静默丢弃。

## 二、实测撞出的真实缺陷（已修复）

### 🔴 缺陷 1：OpenAI 工具定义发到 Anthropic 端点 → 工具名丢失

**现象**：客户端把 OpenAI 形态的工具定义发到 Anthropic 端点：
```json
{"tools":[{"type":"function","function":{"name":"get_weather","parameters":{...}}}]}
```
解析后 `ToolDefinition.Name == ""` ⇒ 线上输出 `{"name":""}` ⇒ 上游拒绝 / 工具调用静默失效。

**根因**：`internal/ir/parse_anthropic.go` 的 builtin 判据只排除了 `"custom_tool"`：
```go
isBuiltin := toolType != "" && toolType != "custom_tool"
```
⇒ `type="function"` 被当成 Anthropic 的 provider-specific builtin ⇒ 走 `Raw` 兜底分支
⇒ Name/Description/Parameters 全丢。

**修法**（`parse_anthropic.go` + `tool_extra.go`）：
1. 与 `parseOpenAITools` 同构：检测嵌套 `function` 对象并归一化到标准 function 工具；
2. `"function"` 键标记为**已消费**（新增 `toolKnownKeysWith`）——否则会落进 `Extra`
   并在 serialize 时并回 Anthropic 输出，造成 `name/input_schema` 与 `function` 两套形态并存；
3. builtin 判据补上 `toolType != "function"`（平铺形态 `{"type":"function","name":...}` 也走 function 路径）。

**验证**：`scripts/audit/ir-client-error-fix-mutation.sh` —— **5/5 变异全被抓住**：

| 变异 | 内容 | 结果 |
|---|---|---|
| M1 | 把 builtin 判据改回旧版 | ✅ 门变红 |
| M2 | 让嵌套 function 分支永不命中 | ✅ 门变红 |
| M3 | 不把 `function` 标记为已消费 | ✅ 门变红 |
| M4 | 不设 Description | ✅ 门变红 |
| M5 | 不设 Name | ✅ 门变红 |

### 🔴 缺陷 2：Gemini 专有参数跨协议**静默丢弃**（无 loss 事件）

**现象**：Gemini 客户端的 `safetySettings` / `cachedContent` 转到 OpenAI/Anthropic/
Responses/Ollama 目标时，**消失且没有任何丢失上报**。

**根因**：
1. `parse_gemini` 把这两个字段**消费进 IR 的结构化字段**（`SafetySettings` / `CachedContent`）；
2. ⇒ 它们**不在 Extensions 里** ⇒ paramreg 的 `Decide` 看不到它们；
3. ⇒ 非 Gemini 序列化器也看不见 ⇒ 静默丢弃。

**为什么是合规风险**：`safetySettings` 是**内容安全阈值**。丢掉它 = 网关替客户端
放宽了安全边界，且无人知晓。`internal/ir/types.go` 的 P3 修复注释原话：
「安全语义参数被静默丢弃属于合规风险」。

**为什么是「上报丢失」而不是「还原到目标 body」**：
- `internal/paramreg/decide.go:140` 对 `KindIRHandled + Dialects=[gemini]` 的字段，
  在非 Gemini 目标上返回 **`ActionDrop`** —— 仓库既有裁决就是「不许把 Gemini
  专有字段塞进 OpenAI body」；
- 盲还原会让上游对未知顶层键 400（OpenAI 严格校验 body 参数）；
- ⇒ 正确处置 = **诚实披露丢失**，与 `cache_control` / `documents` / `thinking`
  的既有处理同款。

**修法**：新增 `internal/ir/gemini_only_loss.go`：
```go
func reportGeminiOnlyLosses(req *InternalRequest, targetProtocol string)
```
四个非 Gemini 序列化器共用（单一实现，不复制粘贴 ⇒ 不会漂移）：
`serialize_openai.go` / `serialize_anthropic.go` / `serialize_responses.go` / `serialize_ollama.go`。

**验证**：`scripts/audit/ir-gemini-only-loss-mutation.sh` —— **4/4 变异全被抓住**
（含"把字段名改掉"这种形似而神不似的变异）。

## 三、211 真实会话回放（黄金对拍）

### 数据来源

| 来源 | 内容 |
|---|---|
| `session_bodies.request_delta` | 客户端**当轮**的消息数组（增量） |
| `session_bodies.outbound_body` | 网关**实际出站**给上游的消息数组 |
| `request_logs_with_current_month.client_protocol` | 客户端协议（join 覆盖 100%） |

**网络注意**：`acc-pg17` 是**同宿主 docker 容器**，宿主 DNS 把它解析到公网名
（`acc-pg17.home.itestu.cn → 115.29.212.252`），从宿主直连会超时
⇒ psql 必须在 **postgres 容器内执行**（`docker exec`）。

### 实测结论

**① 黄金对拍：IR 管线输出 == 生产实际出站（30 条样本逐条一致）**

对拍维度：消息数 · 逐条角色 · `tool_call_id` · 工具名集合 · 内容存在性。

**唯一差异来源**（实测撞出）：客户端发了**两条连续 user 消息**，网关按
`LLM_GATEWAY_FIX_ROLE_ALTERNATION` 合并成一条 ⇒ 对拍时显式对齐生产口径
（该开关默认是 warn-only，`validate_and_fix.go:269`）。

**② 客户端自身的错误形态（网关已正确修复）**

211 真实样本里出现 **tool 结果的 `tool_call_id` 在客户端自己的 `tool_calls` 里
找不到对应调用**（孤儿 tool 结果），其中一条的 id 是 **UUID**
（`11341237-1aba-4243-8d80-93a9ffb38a9d`）而非 `call_` 前缀。
`SanitizeToolMessages` 把它们**恰好**清掉、不多删一条 ⇒ 断言写成
「tool 条数 == 客户端条数 − 客户端孤儿条数」。

**③ 协议归一化的三处既定行为（不是缺陷）**

| 行为 | 证据 |
|---|---|
| `system` 消息被规范化进 `req.System`（不再是消息） | `internal/ir/types.go` SystemPrompt 注释 |
| Responses 的并行 `function_call` item 被**合并**成一条 assistant 消息 | `parse_responses.go` r1030 行为（MiniMax-M3 曾因此停发工具调用） |
| Responses 的 `reasoning` item 被丢弃（外泄面 + 非 wire-legal） | `parse_responses.go` P2-I（2026-11-11） |

⇒ 因此 1:1 消息序列断言**只对 openai-chat 施加**；协议无关的不变量是
「工具调用 ID 集合 / 工具名集合 / tool 与 user 消息数」。

### 覆盖率

| 项 | 数量 |
|---|---|
| 真实会话样本 | **90**（openai-chat 30 / anthropic-messages 30 / openai-responses 30） |
| 转换次数（样本 × 5 目标协议） | **450** |
| 黄金对拍（逐条 vs 生产出站） | **30** |
| 确定性验证（3 次逐字节一致） | **90** |

### 隐私处理

真实会话含用户内容（源码、对话、路径）⇒ 夹具**默认脱敏**：
- 载荷键（`content` / `text` / `arguments` / `input` / `data` …）→ 占位符替换并截断到 128 字符；
- **结构判别值原样保留**（`role` / `type` / 工具名 / `tool_call_id` / 消息顺序）——
  这些正是转换语义的载体。

⚠️ 第一版脱敏有**严重缺陷**：把所有裸字符串都 mask 了 ⇒ `role` / `type` 也被打码
⇒ 夹具失去测试价值。已修正为「只 mask 载荷键的值」。

## 四、性能与并发（实测）

### 性能（Apple M4 Max，2000 次迭代）

| 项 | 实测 | 目标 | 结论 |
|---|---|---|---|
| Parse OpenAI | **15.9 μs** | < 100 μs | ✅ 余量 6× |
| Parse Anthropic | **18.8 μs** | < 100 μs | ✅ 余量 5× |
| Serialize OpenAI | **7.2 μs** | < 100 μs | ✅ 余量 14× |
| Serialize Anthropic | **9.1 μs** | < 100 μs | ✅ 余量 11× |
| 往返 OpenAI→Anthropic | **34.8 μs** | < 500 μs | ✅ 余量 14× |
| 往返 Anthropic→OpenAI | **23.4 μs** | < 500 μs | ✅ 余量 21× |
| ValidateAndFix | **1.15 μs** | — | ✅ |

### 并发

- `go test -race` —— **零竞态**；
- 并发输出与串行基线**逐字节相同**（防共享状态污染，如 Extensions 泄漏到别的请求）；
- Parser **不改写输入请求体**（防并发下的顺序依赖）。
