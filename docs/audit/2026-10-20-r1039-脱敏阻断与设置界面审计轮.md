### 1.2 部署：踩到一个真缺陷（已修）

`scripts/deploy-local.sh deploy` 第一次**失败**在 PG 数据目录搬迁这一步：

```
[deploy-local] migrating llm-gateway-pg data to /Users/niuer/kaixuan/postgres
[deploy-local] creating new llm-gateway-pg with shared storage at /Users/niuer/kaixuan/postgres
[deploy-local] docker-run: ... Bind for 127.0.0.1:5432 failed: port is already allocated
[deploy-local] error: existing PostgreSQL data migration failed; no application was started
```

**两处根因（都是真缺陷，不是本机环境问题）：**

1. **硬编码宿主端口**：重建容器时写死 `-p "127.0.0.1:5432:5432"`，而原容器发布在
   `127.0.0.1:54318`（本机 `acc-pg17` 占着 5432）。两重后果：
   - 宿主 5432 被占 ⇒ `docker run` 直接失败（本次即如此）；
   - **即使 5432 空闲也是错的**：容器 env 里的 DSN 仍写 `@127.0.0.1:54318`，
     而重建后的容器监听 5432 ⇒ 网关去连一个**没人监听**的端口。
2. **不认识运维刻意选定的数据目录**：本机 PG 数据目录是 `~/kaixuan/postgres-citus`
   （镜像 `kx-citus-pg17:13.3.0-vector-arm64`，带 `citus 13.3-1` + `citus_columnar 13.3-1`
   + `vector 0.8.1`），而 deploy 只看 `KAIXUAN_ROOT` ⇒ 判定「不在 shared 位置」⇒
   试图把它搬回 `~/kaixuan/postgres`（一个**空壳**目录：既没有 citus 扩展，
   又是被别的迁移失败拷贝污染过的）。
   ⇒ **运维刻意选定的目录会被静默换掉**，而且那一跳本身还带着硬编码端口的缺陷。

**修法**（两处 + 契约门）：

- `scripts/deploy-local-lib.sh` 的 `dl_shared_pg_dir()` 现在尊重 `LLM_GATEWAY_PG_DATA_DIR`
  —— 这**不是新造的口径**：本仓 `scripts/local-dev/recreate-llm-gateway-pg.sh:51` 与
  `scripts/local-dev/recover-pg-citus-image.sh:81` 早就把它当作既有契约，
  只有 deploy 这条链没接上。
- 新增 `dl_pg_publish_spec()`：从原容器的 `NetworkSettings.Ports` 读回
  `(HostIp, HostPort)` 并沿用（`LLM_GATEWAY_PG_PORT_BIND` 优先级最高，
  与 `local-dev/recreate-llm-gateway-pg.sh:52` 同契约）⇒ **端口与 DSN 成对沿用**。
- 契约门 `tests/deploy_local_contract_test.sh` 追加 2 组共 8 条断言。

**变异验证**（本仓纪律：判据写完必须确认它会红）：

| 变异 | 预期变红的判据 | 实测 |
|---|---|---|
| 把 `-p "$pg_publish_spec"` 改回 `-p "127.0.0.1:5432:5432"` | `deploy-local.sh must not hardcode the PG publish spec to 127.0.0.1:5432` | ✅ 红 |
| 去掉 `LLM_GATEWAY_PG_DATA_DIR` 覆盖 | `LLM_GATEWAY_PG_DATA_DIR must win over KAIXUAN_ROOT` | ✅ 红 |
| 还原 | — | 29 条全绿 |

**修完的部署结果**：`VERIFY_PASS=1`，`VERIFY_RELEASE=2.5.8.2760`，`VERIFY_PORT=8782`，
凭据解密冒烟 `providers=2452,2453,2454 creds=3 failed=0`。
PG 容器未被动过（仍是 `llm-gateway-pg` / `postgres-citus` / `127.0.0.1:54318`）——
**「不搬迁」正是修对了的证据**。

### 1.5 部署再次被真缺陷挡住：boot ensure 链**索引了它自己不补的列**（已修）

第二轮重新部署时，`deploy-local.sh` 在**数据库迁移**这一步中止：

```
2026/10/20 21:29:32 INFO postgres connected max_conns=16 min_conns=2
2026/10/20 21:29:37 WARN schema migrations failed transiently, retrying attempt=2 max=2
            error="ERROR: column \"provider_id\" does not exist (SQLSTATE 42703)"
[deploy-local] error: database migration failed; structured report follows
    {"status":"error","message":"db open: ERROR: column \"provider_id\" does not exist (SQLSTATE 42703)"}
```

**根因（结构性，不是本机环境问题）**：

`db/db.go` 的 `ensureRequestLogSchema` 在 `_request_logs` 上建两个带 `provider_id` 的索引
（`idx_request_logs_provider_quality`、`idx_request_logs_provider_tool_calls`），
但**从不补 `provider_id` 这一列**。这两个索引是 2026-06-19（`9cd51d8a7`
「per-provider tool_call quality fix mode」）引入的，当时目标表是 v1 的 `request_logs`；
v2 改名（迁移 `860`：`request_logs` → `_request_logs`）把它们**一起搬到了新表名**上，
而改名后的表在最小/新装基线形态下**没有**这一列。

⇒ **任何 `_request_logs` 不带 `provider_id` 的库上，整条 boot 迁移在第一个索引处报
42703 ⇒ 迁移中止 ⇒ 网关起不来。**
⇒ 已是 v1→v2 改名产物的库（211/252 等）本来就有这一列 ⇒ 那边**看不见**这个洞。
⇒ 本机库是**最小基线形态**（`_request_logs` 只有 `id / tenant_id / ts / work_type`
四列，无 v1 `request_logs` 表），所以正好踩中。

**修法**（两处，一起改——`db.go` 自己的注释就要求「新增列/索引时两处一起改」）：

1. ensure 体的 `ALTER TABLE _request_logs` 补 `ADD COLUMN IF NOT EXISTS provider_id BIGINT`
   （与该块「自己索引的列一律自己先补」的既有写法一致；可空、无默认值 ⇒ 零数据影响；
   已有该列的库上是 no-op）。
2. **目录短路清单**（`catalogShortCircuitSQL` 的期望列数组）同步加上 `'provider_id'`。
   ⚠ 这一处漏掉会造成更隐蔽的后果：缺列的库被判成「齐备」⇒ **零 DDL** ⇒ 列永远补不上。

**判据**：`db/r1039_request_logs_provider_id_column_test.go`
（真库行为验证 + 源码顺序判据，变异 M1/M2 全红，见 §9.1）。
真库判据跑在**一次性库** `itgate_r1039` 上（退出即 DROP，不碰 `llm_gateway`）。

⇒ **这条同时命中用户诉求里的「新装路径必须绿」**：新装/最小基线库此前**起不来**。

> ★ **2026-10-21 合并上游后的订正**（见 §1.7）：本条**至今仍成立**——上游
> `origin/main` **仍然没有**这一列的补法（本轮是唯一一处补上它的改动）。
> 但本机当时那次中止**还叠加了第二个原因**：本 checkout 落后上游 99 个提交、
> 且**缺** `890_drop_request_logs_v1_family.sql` ⇒ 代码按「族还在」的世界写、
> 而库已经是「族已退役」的形态 ⇒ 后续又连撞两次 42P01。
> ⇒ 单看「provider_id 缺列」不足以解释那一串失败，**形态错配**才是主线。

### 1.6 修完 provider_id 后，露出下一个同族洞：**族表退役 ≠ 族表还在**

修掉 `provider_id` 之后，同一条 boot 迁移链继续往下走，撞上第二个洞：

```
ERROR: relation "_request_logs_hot" does not exist (SQLSTATE 42P01)
```

**根因仍是「体与清单口径不一致」**：

- 目录短路清单（`catalogShortCircuitSQL`）判断「列缺不缺」时用的是
  `WHERE to_regclass('public._request_logs_hot') IS NOT NULL` ⇒
  **它早就承认「这张表可以不在」**（request_logs 族退役后确实不在）；
- 而 ensure **体**却**无条件** `ALTER TABLE _request_logs_hot …` ⇒ 表不在就 42P01。

⇒ 修法：新增 `db.tableExists()`（`to_regclass` 口径，与清单**同一把尺子**），
ensure 体按表的存在性分别执行 hot 侧与母表侧的 DDL；母表整个不在时整族跳过。

**再往下一个洞**（同一族）：

```
ERROR: relation "providers" does not exist (SQLSTATE 42P01)
```

⇒ 这已经不是 ensure 链的「族表」问题，而是**本机库本身缺核心表**：

| 对象 | 本机库实测 | 说明 |
|---|---|---|
| `providers` | **不存在**（只有 `provider_catalog`，那是**静态目录**：`code / tier / base_url_template / …`，不是租户的 provider 实例） | 代码多处 `FROM providers` ⇒ `/api/providers` 实测 **500** |
| `credentials` | **不存在** | — |
| `request_logs` / `_request_logs_hot` | **不存在** | 族已退役（request_logs → session_turns） |
| `session_turns` / `session_turns_hot` | 存在 | 新族 |
| `users` / `api_keys` / `agents` / `_request_logs` | 存在 | — |

⇒ **本机库是个「半迁移」产物**：台账 `gateway_db_revision_sequences` 记着
`860_rename_request_logs_family…` 已于 2026-10-16 应用，而被它改名的
`request_logs` / `request_logs_hot` **压根不存在** ⇒ **台账与现实不一致**（§8 第 6 条）。

⇒ 而 `scripts/deploy-local.sh` 的 `apply_schema_if_empty` 判「库是否已装 schema」的探针是
`('users','_request_logs','credentials','api_keys','agents')` 里**任一存在就跳过快照**
⇒ 本机库命中「任一存在」（4/5）⇒ **快照从未被应用** ⇒ 核心表一直缺。

**处置**：按 deploy 脚本的**设计新装路径**重建本地库 —— 先 `pg_dump` 备份
（`/tmp/kx-pg-backup/llm_gateway_backup.dump`，16 MB），再 drop + create 空库，
让 `apply_schema_if_empty` 走「库是空的 ⇒ 应用 `sql/schema/{00-prereqs,01-schema,02-seed}.sql`」
这条**本来就被设计好的**分支，然后由启动迁移序列 + ensure 链补齐其余部分。

⚠ 这一步**丢掉了本机库的既有数据**（usage_ledger / request_logs 等本地测试数据）。
用户诉求是「更新本地的 pg17 数据库，确保本地的网关与数据库为最新版本」⇒
重建到「与仓内同版本且自洽」正是该诉求要的结果；备份已留，可回滚。

#### 更关键的一条：上游有 `890_drop_request_logs_v1_family.sql`，**本 checkout 没有**

- 上游的 `installer/internal/dbinit/runner.go` **注册了** `890_drop_request_logs_v1_family.sql`
  （退役链的最后一跳：canonical 视图砍掉 v1 臂、删掉 4 张 v1-only 视图、删掉 v1 族全部表）。
- 本 checkout **既没有这个文件，也不在本 checkout 的 git 历史里**（`git log --all --diff-filter=D` 查不到）。

⇒ **推论（这解释了本轮两次 42P01 为什么出现在我的 checkout 上）**：

| 库形态 | 怎么来的 | 族表在不在 |
|---|---|---|
| **上游安装器形态** | 基线建 `request_logs` → 860 改名 `_request_logs` → **890 删除** | **不在** |
| **本 checkout 单独部署** | 基线建 `request_logs` → 860 改名 `_request_logs` → **没有 890** | **在** |
| **本机真实库** | 并发会话用**另一份 checkout**（`llm-gateway-go`，含 890）部署过 | **不在**（523 张表，无族） |

⇒ 本机真实库是「族已退役」形态，而本 checkout 的代码是按「族还在」的世界写的
（work_type 的索引探针、848 的族侧 ALTER 都假设族在）⇒ **代码与库的形态不匹配** ⇒ 42P01。
⇒ **这不是「代码更差」，是「基线更旧 + 形态不同」。**

⚠ 顺带暴露的**多 checkout 陷阱**（AGENTS.md 已列，此处给出实证）：
本机 `llm-gateway-go` / `llm-gateway-go-3` / `llm-gateway-go-5` 三份 checkout 的
`HEAD` 各不相同（`8cb279a46` / 本轮 / `f6a92a1ae`），**同一台机器的同一个部署目标
可能被不同基线的代码先后改过**。本机的 `llm_gateway` 库就是 `llm-gateway-go`
那份 checkout 部署出来的形态，而本轮一直用 `llm-gateway-go-3` 部署 ⇒ 形态错配。

#### 判据：链级判据（本轮新增，承重）

前几轮立的都是**单点**判据（某个 ensure 写对了）。但 2026-10-21 实测说明**逐点修不够**：
同一个库形态上，先撞 `relation "_request_logs" does not exist`，
修完再撞 `relation "_request_logs_hot" does not exist` —— 两次在**同一条链的不同步骤**上。
⇒ 真正的不变量是「**整条 boot ensure 链必须能在族已退役的库形态下跑完**」。

⇒ 新增 `db/r1039_boot_chain_fresh_install_test.go`：
- **自造安装器形态的一次性库**（不依赖任何外部夹具）：基线（`sql/schema/{00-prereqs,01-schema,02-seed}.sql`）
  + `installer/internal/dbinit/runner.go` 的 `StartupFiles` 清单里全部 startup 迁移
  （清单从**安装器的 Go 源码字面量**里解析，解析不到就判红）。
- 跑之前先断言**族表确实不在**（防空跑）+ 核心表确实在（防残废夹具）。
- 直接调 `db.applyMigrationsOnce`（boot 时执行的函数本体）**两遍**（第二遍验幂等）。
- 跑完之后族表必须**仍然不在**（不许被复活）。

⚠ **一处必须写下来的坑**：只做「基线 + ensure 链」会**误判**——基线**不含** startup
迁移建的表（实测 `session_aggregate_outbox` 来自 startup 630）⇒ 链会在那里报 42P01，
而那是**夹具缺口的假阳性**，不是产品缺陷。2026-10-21 实测正好踩了一次，先记在这里。

⚠ 另一处：含 `\gexec` 的 startup 迁移（3 个）**不能用 pgx 直跑**（仓库自己在文件头
写明「必须走 psql」）⇒ 判据跳过它们并留痕；另有 6 个 `dbinit:no-transaction` 文件
（`CREATE/DROP INDEX CONCURRENTLY`）在 pgx 的隐式事务里必然失败（25001）⇒ 同样留痕。

### 1.8 ★★ 合并后本机部署仍起不来：**三项默认全 false ⇒ 网关拒绝启动**

合并上游后 boot 迁移链整条跑通了（族退役闸全部命中，日志里逐条可见
`v1 request_logs family is retired (890) — … skipped`），但候选实例在
`/healthz` 60s 内没起来：

```
ERROR unsafe request storage configuration
      error="request storage requires v1 writes or enabled V2 shadow writes"
      accepted configurations:
        - V1-only:    LLM_GATEWAY_STORAGE_REQUEST_LOGS_WRITE_ENABLED=true  (no V2, no PG required)
```

| 键 | 默认 | 来源 |
|---|---|---|
| `storage.request_logs_write_enabled` | **false** | `settings/spec_storage.go`（`c2fae70ea` 改的） |
| `sessions_v2.enabled` | **false** | `settings/spec_sessions_v2.go` |
| `sessions_v2.shadow_write` | **false** | 同上 |

⇒ `ValidateSessionWriteState(v1, enabled, shadow)` = `!v1 && !(enabled && shadow)`
⇒ **三个默认全 false ⇒ 恒为 true ⇒ 启动即 `os.Exit(1)`。**

⚠ 这不是本机环境问题，是**仓内的默认组合自相矛盾**：
`scripts/deploy-local-lib.sh` 对这三个键是「显式写入 opt-in，未设就写空行
（gateway 侧视为未设置，走注册表默认）」⇒ **全新 clone + `deploy-local.sh deploy`
⇒ 网关必起不来**（除非 `.env.local` 显式给出合法形态）。

**本机处置**（`.env.local`，gitignored，属**本地部署配置**不是仓库改动）：

```
LLM_GATEWAY_SESSIONS_V2_ENABLED=true
LLM_GATEWAY_SESSIONS_V2_SHADOW_WRITE=true
```

⇒ 选 **V2-only** 形态而不是 V1-only / V1+V2 dual 的理由：
v1 族已退役（860 改名 → 890 删除）⇒ v1 写侧**无表可写**；
而 v1 写侧本来就被 `storage.request_logs_write_enabled=false` 门控
（`domains/hooks/observability/telemetry/client.go:40`）⇒ 双开也不会真写 v1；
读侧走 890 之后的 canonical 视图（会话族双臂）⇒ 不依赖 v1。
⇒ **V2-only 是与「族已退役」自洽的唯一形态。**

⚠ **留给 owner 的两条**（本轮**未**擅自改仓内默认）：
1. `scripts/deploy-local-lib.sh` 是否该给这三项一个**与族退役自洽的默认形态**
   （V2-only）？否则「全新 clone → deploy → 起不来」是默认路径。
2. 211 / 252 的 env 是否已经是合法形态？它们若也依赖「v1 写侧默认 true」，
   合并后同样会起不来 —— **上线前必须先查**（见 SQL 台账 §2.2）。

## 4. 设置界面

### 4.1 脱敏设置界面（`/admin/sanitize-rules`）

**页面本来就存在**，且已覆盖：按 pattern 配置匹配规则（pattern/group/priority/tools/
fields/exemptions/samples）、按模式配置（`scopes` = input/output/egress）、单条 `enabled`、
版本发布/回滚/事件复核/每实例生效版本上报。**不需要新建页面。**

本轮补的是**「按模式启停」的可用性**：运行期判定是
`domains/sanitizerules/model.go` 的 `Applies(phase, tenant, tool, field)`：

```
r.Enabled && scope 命中 && tenant 命中
```

⇒「这条规则在某个模式上是否生效」= **全局开关 ∧ scopes 含该模式**。
此前 UI 只有一列 scopes **文本（只读）** + 一个全局 enabled 开关 ⇒
「这条规则现在在哪些模式上真的开着」**看不出来**。

本轮：规则表加一排 `input / output / egress` 开关，勾选态与 `Applies()` **同源**；
勾上 ⇒ scopes 加该模式 **且**把全局 `enabled` 带上（否则运行期仍不生效）；
取消 ⇒ 从 scopes 摘掉该模式。**零 schema 变更**（改的是既有 `scopes` + `enabled` 两个字段），
保存路径仍是既有的 validate → publish。

判据（含**变异验证**）：

| 判据 | 变异 | 实测 |
|---|---|---|
| 勾选态 = 全局启用 ∧ scopes 含该模式 | `phaseActive` 去掉 `enabled` 维度 | ✅ 该条红 |
| 勾上某模式 ⇒ scopes 加该模式 **且** `enabled=true` | `onPhaseToggle` 不带 `enabled` | ✅ 该条红 |
| 取消某模式 ⇒ 从 scopes 摘掉（**看发出去的草稿**，不看组件内部） | — | 绿 |

⚠ 判据纪律：`<script setup>` 的内部变量**不挂在 `vm` 上**，写 `w.vm.draft` 只会拿到
`undefined`，再套个 `if (draftScopes)` 就成了**恒不执行**的假绿 ⇒ 改用
「validate 发出去的草稿」这个**可观测契约**做断言。

### 4.2 提示词注入规则详情（`/admin/prompt-injection?tab=rules`）

**此前完全没有详情入口**：rules tab 里没有任何查看/编辑的入口，唯一的行内写操作是
enabled 开关，唯一另一个动作是删除。需求是「点击检查规则详情并修改保存」。

本轮：

- `GET /api/admin/prompt-injection/rules/{id}`（**新增**；此前该路径返 **405**）
  ⇒ 详情弹窗按 id 重新读一次，「规则不存在」有独立的 404 语义。

#### 缺陷 A：Echo 侧 admin 端点**不认 cookie** ⇒ 浏览器 cookie 会话被 401

**根因（两套中间件对「凭据从哪来」的认知不一致）**：

| | 取凭据方式 | 校验 | 覆盖范围 |
|---|---|---|---|
| ServeMux 侧 | `admin/auth.go` 的 `extractBearerOrCookieToken`：**头或 cookie 都认** | `identity.Verify` + issuer/audience | `admin` 组全部端点 |
| **Echo 侧** | `cmd/gateway/main_jwt_middleware.go`：**只认 `Authorization: Bearer`** | 同一个校验器 | `cmd/gateway/main.go:7174` 的 `adminGroup := e.Group("/api/admin", requireSuperAdmin)` |

而前端 `web/src/api/_core.ts` 的 `headers()` 在 **JWT 登录态下刻意不发** Authorization 头
（`const bearer = isAuthenticated() && store.userInfo ? '' : authBearer()` ——
注释写明「让 HttpOnly cookie 承载鉴权，避免内存里的 JWT 盖住别的标签页更新的 cookie」）。

⇒ **浏览器 cookie 会话访问 Echo 注册的 admin 端点 ⇒ 401**。本机实测受影响的 8 个：
`/api/admin/tiers`、`/api/admin/licenses`、`/api/admin/vibecoding/projects`、
`/api/admin/faults`、`/api/admin/releases`、`/api/admin/autoupdate`、
`/api/admin/center/*`、`/api/admin/routing-opt/ml`。

**修法**：Echo 中间件改用 `admin.ExtractBearerOrCookieToken(c.Request())`
（该函数已导出；cookie 里就是 `SignToken` 签的同一串 JWT，**校验器/issuer/audience
一律不变**，只改**传输方式**，不扩大凭据类型）。
⇒ cookie 是 HttpOnly + SameSite=Strict，不构成 CSRF 面。

**判据**：`cmd/gateway/r1039_jwt_middleware_cookie_test.go`（5 组用例）。
**变异验证**：M1（改回只认 Bearer 头）→ 红；M2（不注入身份）→ 红；还原 → 绿。

**遗留**（本轮**不**扩大）：ServeMux 侧那个「**改密码后撤销会话**」的探测，
Echo 侧**没有**对应实现 ⇒ 改密码后，Echo 侧用旧 cookie 的会话**不会**立刻失效。
这是**既有差异**（不是本轮引入），本轮只补了「cookie 能过认证」这一半。

### 7.13 ★★ 混拼形态的标记词，此前**扫描器本体也看不见**（§8 第 8 条：**已修**）

#### 7.13.1 缺陷比登记的更重：不是「便宜门短路」，是**生产扫描路径 0 spans**

§8 第 8 条当时登记的是「便宜门 `mayContainMarkerText` / `containsFoldCaseWord`
只认全 ASCII 词或全全角词 ⇒ 折宽副本不会被构造」。**实测（2026-10-21，
走生产扫描路径 `looseMarkerSpans`）**：

| 输入 | 修复前 spans | 修复前 cheapGate | 修复后 spans | 修复后 cheapGate |
|---|---|---|---|---|
| `SENSITIVE:phone`（全 ASCII） | 1 | true | 1 | true |
| `ＳＥＮＳＩＴＩＶＥ：phone`（全全角） | 1 | true | 1 | true |
| `ＳENSITIVE：phone`（首字全角） | **0** | false | **1** | true |
| `SENSITIVＥ:phone`（末字全角） | **0** | false | **1** | true |

⇒ **根因不在便宜门本身**，而在 `foldMarkerWidth` 的**前置门**是
「全 ASCII 词」与「全全角词」的**析取** ⇒ 混拼两者皆不成立 ⇒
**折宽副本根本不构造** ⇒ **扫描器一个字都没扫到**（0 spans）⇒
标记原样到达客户端。

⇒ 这一点**很重要**：先前登记的「便宜门短路」暗示「扫描器本体能看见、
只是被过滤器挡了一下」，那样只需改过滤器；**实际是扫描器本体看不见**
⇒ 便宜门只是**症状**，真正要放宽的是**折宽的前置门**。

⚠ 定级不变（§8 第 8 条原判）：泄漏的是**占位符 token**
（`SENSITIVE:phone`），**不是**被脱敏的秘密值 ⇒ 低于 D2 那种「秘密值外泄」。
现实性也未变：r1039 那轮实测到的形态是「全全角词」与「ASCII 词 + 全角冒号」，
**逐字混拼没有生产证据**。

#### 7.13.2 修法：**扫描器本体一个字都没改**，只放宽两处门

落在逐字符这一层：

- `matchMarkerWordAnyWidthAt`：标记词的 9 个字符**各自**决定宽度
  （ASCII 大小写不敏感，或全角字母 Ａ-Ｚ/ａ-ｚ）⇒ 2^9 = 512 种组合全部认得。
- `containsMarkerWordAnyWidth`：两条 memchr（ASCII 的 `'s'`/`'S'` 与全角首字节
  `0xEF`）各自定位候选 ⇒ **成本形状与被它取代的两条门完全相同**
  （旧门也是这两条 memchr）⇒ 不放大常态成本。
- 接到**两处**门：`foldMarkerWidth` 的前置门、`mayContainMarkerText`。
  ⇒ 混拼形态被认出来 ⇒ 折宽副本照旧由 `foldMarkerWidth` 构造 ⇒
  **扫描器（折宽后按 ASCII 正则扫）一个字都不用改**。
- `internal/markerbound` 是本包文法的**刻意副本** ⇒ 同一个修法**必须同步**，
  否则截断切点会把混拼标记切成两半 ⇒ 半截标记随上游跑掉。
- 清理由修复而**变死**的代码：`containsFullWidthMarkerWord` /
  `matchFullWidthMarkerWordAt` / `containsFoldASCII`（留着会让人复用它们，
  把 bug 重新引入）。

#### 7.13.3 判据（`security/sanitize/r1039_mixed_width_marker_test.go`，9 条）

- **差分判据**（语义）：新门必须与一条**朴素参照**（逐字节位置试、逐字符解码）
  **逐位等价**，且**穷举 2^9 = 512 种宽度组合** ⇒ 语义用「差分 + 穷举」钉，
  不靠「挑几个例子看着对」。
- 生产扫描路径看得见（`looseMarkerSpans` ≥1 span）+ 便宜门放行。
- 端到端：映射表里有 ⇒ **还原成真值**；没有 ⇒ **遮蔽**（且必须有遮蔽标记 ——
  「什么都没发生」与「干净」必须长得不一样）。
- **误报门**：普通中文/全角数字/全角标点不得触发门、不得产生 span、不得被遮蔽。
- **成本门**：便宜门在 16KB 中文/英文/全角正文上**零分配**（`hop.go` 里记着

  **逐条相同**。

**变异验证**（`scripts/mutate-r1039-mixed-width-marker-gate.py`，M1~M5，

### 7.14 ★★ 自审轮：探针路径缺「内层重扫」⇒ JSON 里的裸形标记**原样到达客户端**

#### 7.14.1 自审审出了两处真实缺陷（均**实测**确认，不是「读代码觉得」）

上一轮（§7.13）把「标记词的半角全角混拼」修了。本轮回头**审自己上一轮的成果**，
沿用上一轮那条纪律（「**这个族有几处门？本轮改了几处？**」），查出**两处**：

**缺口一：混拼族的**第三处**门被漏掉。**
这一族共有**三处**门，上一轮只放宽了两处（`foldMarkerWidth` 的前置门、
`mayContainMarkerText`）。第三处是 `hasReservedPlaceholder` 的**预筛** ——

实测（修复前）：`{"phone":"ＳENSITIVE：phone"}` ⇒ 守卫 **false**，
而 canonical ASCII 同形态 ⇒ **true**。

**缺口二（与混拼无关，**canonical 形态也漏**）：探针路径缺「内层重扫」。**
brace 分支会把一整段 JSON 吞成一个候选（`{"pwd":"SENSITIVE:phone"}`
整个就是一个候选），而那个候选**既不匹配占位符语法、也不像标记** ⇒ 被判掉
⇒ **裸形标记就在它内部，却没人看见** ⇒

- `placeholderCandidate` 假 ⇒ **工具调用参数车道整个被跳过**
  （`function.arguments` 是一段 JSON 字符串，标记就落在里面）；
- `hasReservedPlaceholder` 假 ⇒ 残留守卫不触发。

实测（修复前，**拦截器层面**）：客户端**原样收到**
`{"choices":[…{"arguments":"{\"pwd\":\"SENSITIVE:phone\"}"}…]}`
—— canonical ASCII 与混拼形态**都漏**。

⇒ ⇒ **缺口二比缺口一更重**：它不挑拼写，**规范拼写也漏**。

#### 7.14.2 根因很干净：**内层重扫只在重写路径存在，不在探针路径**

`rewriteLooseSpans` 的 case (b) 早就在做内层重扫（brace 分支吞掉的段里
可能藏着裸形标记 ⇒ 段内重扫 ⇒ 把结果拼回去）；
**只有探针路径（`markerSpans`）没有** ⇒ 探针低报 ⇒
**该触发的门不触发** ⇒ 泄漏。

⇒ ⇒ 这正是 §7.13.6 那条纪律的**第三次生效**：
「**一个机制要在几条路径上生效，就得在每条路径上都补齐**」
（上一轮：刻意副本 `internal/markerbound`；这一轮：探针路径 vs 重写路径）。

#### 7.14.3 修法：**重写路径一字未动**，探针路径复用同一个原语

- `markerSpans`（探针侧）：候选不是标记时，**内层重扫**它的内部
  ⇒ 复用重写路径的**同一个原语**（`looseBareMarkerSpans`）⇒ 两边不会漂。
- `internal/markerbound`（刻意副本）**同步**同样的内层重扫
  ⇒ 否则两个副本的 span 集合分叉（**契约门当场红**——纪律第三次生效）。
- 成本：内层重扫先用 `containsMarkerWordAnyWidth`（两条 memchr）**短路**
  ⇒ 只有**真的含标记词**的候选才付一次正则扫描。
- 新增原语 `innerBareMarkerCandidates`（`placeholder_loose.go`）：
  先短路筛，再用 `looseBareMarkerSpans` 扫内部，**只返回内部那一截裸形**。

⇒ **根因修在扫描器层，不在各个门上**：一处修复即覆盖所有探针
（`placeholderCandidate` / `hasReservedPlaceholder` / `containsNonForeignMarker`）。
