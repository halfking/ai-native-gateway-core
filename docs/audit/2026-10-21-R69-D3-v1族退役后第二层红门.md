## 3. ★ 三处方法学修正（比那 5 条门更值钱）

### 3.1 ★★★★ 「全仓 `go test ./...`」在共享真库上**不是有效读数**

`go test ./...` **并行跑包** ⇒ 多个包同时写同一个库 ⇒ 互相污染。

★ **实测证据**（同一份代码、同一个库）：

| 门 | 全仓跑法的读数 | 逐包隔离跑法的读数 |
|---|---|---|
| `domains/hooks/observability/telemetry::TestRequestClassPGRoundTrip` | 红：`relation "public.request_logs_hot" does not exist` | 逐包跑时**红**（真实缺陷） |
| `admin/v_analytics_views_session_source_test.go` | 红：`premise broken: public._request_logs 又存在了` | **绿**（前提在逐包跑时成立）⇒ ⇒ 全仓读数里的这条是**污染产物** |
| `sql/migrations/startup::TestMigration817HostileClientIPValues…` | 红 | 逐包跑时**红**（同一症状） |
| `db::TestRequestClassPg*` | 红：`public.request_logs_hot does not exist` | 逐包跑时**绿** ⇒ ⇒ 污染 |

⇒ ⇒ **「R59 的 75 条 / R67 的 63 条」是包间污染下的读数** ⇒ 任何以它为前提的结论都要重新核。

### 3.2 ★★★★ 同一个包，**全新库**与**用过的库**读数不同

★ **实测**：`db/` 包，**同一份代码**：

| 库 | 失败数 | 差出来的 7 条 |
|---|---|---|
| **全新库**（刚建、只跑过 ensure 链） | **4** | — |
| **用过的库**（同一轮里被别的测试改过） | **11** | `TestEnsureReportSnapshots_RealDB`、`TestEnsureSqlAuditPartialIndexes_RealDB`、`TestFreshInstallPartitionShape`、`TestFreshInstallRuntimeShape_EnsureChain` … |

⇒ ⇒ **一次性库必须每次新建**（`scripts/audit/probe-onetime-db-shape.sh` 的 `DB_NAME` 覆盖就是为此），
⇒ ⇒ **同一个库上跑第二遍，数字就不可比了**。

### 3.3 ★★★ integration 树编译不过（**别人提交里的缺陷，本轮顺手修掉**）

`admin/section_14336_board_single_scan_test.go`（origin/main 提交 `2c628fd7b`）调用
`stripGoCommentsKeepingStrings`，而该 helper 定义在
`admin/request_logs_retirement_tiering_test.go` 里 —— ★ **那个文件带 `//go:build !integration`**
⇒ ⇒ `-tags=integration` 的树里它不存在 ⇒

```
vet: admin/section_14336_board_single_scan_test.go:69:9: undefined: stripGoCommentsKeepingStrings
```

⇒ ⇒ 整棵 integration 树编译失败 ⇒ ⇒ 连带拉红
`sql/schema::TestIntegrationTaggedTreeCompiles`（★ **那道门本来就是为抓这种问题而存在的**）
⇒ ⇒ 并且**挡住所有 `-tags=integration` 的跑法**（本仓有多道真库门带 integration tag）。

⇒ **修法**：把 helper 移到**不带 build tag** 的新文件 `admin/go_comment_strip_test.go`，
原文件留一行说明 ⇒ **不动那一会话的文件**（同文件单写者纪律）。
⇒ 验证：`go vet -tags=integration ./...` 干净；`sql/schema` 那道门**转绿**。

⇒ ⇒ ★ **通用式**：★ **共享 helper 的定义文件不能带任何 build tag** ——
只要**任何一个**使用方在另一种 build 里，它就必须两边都在。
判别方法：`grep -rn "func <helper>"` 看定义文件头两行有没有 `//go:build`。

## 9. ★★★★★ 收尾复验时的**决定性发现**：**probe 建出来的库不是产品的真实形态**

### 9.1 现象

合并 origin/main（35 个提交）后，在**全新 probe 库**上复验时，我本轮改好的两条门**变红**：

```
v1_write_liveness_realdb_test.go:69: v1WriteLivenessSQL 执行失败：
    ERROR: relation "session_turns_hot" does not exist (SQLSTATE 42P01)
request_class_pg_test.go:97: ★ canonical 视图只投影 0/2 个分类列
```

⇒ ★★ **但代码是对的** —— 在一个**有 `session_turns_hot`** 的库上，两条门**全绿**（实测）。

### 9.2 根因

★ `scripts/audit/probe-onetime-db-shape.sh` 建出来的库**缺 `session_turns_hot`**：

| 关系 | probe 库（全新） |
|---|---|
| `session_turns`（母表） | **在** |
| `session_turns_hot`（hot 表） | ★ **不在** |
| `session_turn_details_hot` | 在 |

⇒ ⇒ 而脚本第 ⑥ 步跑完 ensure 链后打印的是
**「✓ ensure 链已跑（库现在 = 产品真实形态）」** ⇒ ⇒ **这句话是错的**。

⇒ ⇒ ★★★ **更要命的是**：ensure 链自己的门
`db::TestFreshInstallRuntimeShape_EnsureChain` **PASS**（实测 5.56s）
⇒ ⇒ **它在「hot 表缺失」的状态下照样绿** ⇒ ⇒ **它没有检 hot 表** ⇒ ⇒ **一道漏检门**。

### 9.3 ★★ 为什么这条发现比那 5 条门更值钱

本轮追的「v1 族退役后的红门」里，**相当一部分是在这个不完整形态上测出来的**：

- 「canonical 视图只投影 0 列」⇒ **视图建在缺失的会话族上**；
- 「`_request_logs` 父表还在、hot 表不在」⇒ **半退役**这个形态**可能就是 probe 链的产物**
  （母表在、hot 表不在 —— 与「会话族母表在、hot 表不在」是**同一种形态** ⇒ ★ 值得比一比）；
- 「会话族两腿不同形」⇒ hot 腿压根不在。

⇒ ⇒ ★ **通用式**：
1. ⭐⭐⭐⭐⭐ **量具要断言「形态」，不能只断言「跑过了」** ——
   「ensure 链跑过了」≠「库 = 产品形态」⇒ **守卫必须点名校验关键关系在不在**；
2. ⭐⭐⭐⭐⭐ **一条门在自己缺关键对象时仍然绿 ⇒ 它是漏检门** ——
   ⇒ 判据里必须包含「**那个对象在不在**」这一条；
3. ⭐⭐⭐⭐ **自己新写的门变红时，先确认「是不是环境变了」** ——
   本轮的红来自 **incoming 的 35 个提交 + probe 库形态** ⇒ **不是我的代码坏了**；
4. ⭐⭐⭐⭐ **「库 = 产品真实形态」这类断言必须能被证伪** ⇒ 脚本里的成功文案不算证据。

### 9.5.4 ⇒ 三处方法学缺陷合看

| # | 缺陷 | 判据 |
|---|---|---|
| 1 | **包间并行污染** | 逐包隔离，不跑 `go test ./...` |
| 2 | **库状态漂移** | 每次重建一次性库 |
| 3 | ★ **树不是最新的** | `git merge-base --is-ancestor <关闭提交> HEAD` |

⇒ ⇒ ★ **通用式：共享仓里的任何读数必须带三个坐标** ——
**树**（`git rev-parse HEAD`）＋ **库**（新建/复用）＋ **DSN 集**（全量/部分）⇒ 缺一个就不可比。
