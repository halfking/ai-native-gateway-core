## §3 生产日志追踪：ASM 事件派发 503 风暴（目标④·主根因）

**读数**（211 实测）：网关容器 24h WARN `dispatch failed ... ai-session-manager returned 503
event_retryable` = **294,722 条**；风暴峰值 ~64 次/秒（10 分钟 38,436 条）；outbox_events
failed=4191（attempts 最高 691，2026-10-21 起）；ASM 侧 `gateway_event_inbox` retryable=14,447
**30 秒采样 +1 ⇒ 排空速率为 0**。

**根因链**（逐环实证）：
1. ASM audit sink 故障（09:20–13:30 UTC，1572 条 `audit: write to audit_events failed`）
   ⇒ ASM 对网关事件入口回 503 `event_retryable`；
2. 网关 outbox 积压推到 4191 条 failed；
3. 每条按各自退避独立重试 ⇒ **N 条积压 = N/64 次/秒的送达风暴**（当时固定 64s 退避：
   4191/64 ≈ 65 req/s），asm inbox 排空为 0 —— 风暴没有换回任何进展，只是给关门的入口持续加压；
4. 蓝绿切换后（b 容器 15:38 UTC 接管）ASM audit sink 恢复（1h 内 0 失败），但 inbox 消费仍卡。

**修复（网关侧，本轮实施）**：`internal/outbox` 背压熔断器（commit `24b6ddf3`）：
- `dispatchOne`：`IsBackpressure` ⇒ markBackpressure（语义不变：永不 DLQ）+ **停批**并挂起整个循环；
- `Start`：暂停期 tick 只刷新仪表、不发探测；cooldown 到期后第一个 tick 自然恢复；
- 风暴从 ~65 req/s + 65 WARN/s 压到 **每 cooldown 一次探测**（暂停期 0 req/s、1 条 WARN）。
- **合并防漂移**（commit `5b753fc5`）：并行会话 1ffdeeeb83 同日把单条退避改指数
  （8s×2 封顶 10min），`backpressureRetryCap` 从 64s 变 10min ⇒ 我的默认 cooldown 引用它而
  **被动漂移成 10 分钟盲区** ⇒ 解耦为独立常量 `backpressureProbeCooldown = 64s`
  （探测是单条廉价请求，10min 盲区换不来任何减压，只拖慢「门已重开」的发现）。
- 两套机制互补关系：熔断器管「整循环暂停期内的探测节奏」（0→1 req/64s），指数退避管
  「恢复后各事件的排空次序」（cap 10min 保证 ≤10min 全量排空）。
- 测试：`BackpressureStopsBatch`（sqlmock 序断言第二条不被 claim）/`BackpressurePauseWindow`
  （窗口延长不叠倍，判别点选 90~120s）/`Start_PauseProbesOncePerCooldown`（暂停期 0 HTTP）；
  更新 `BackpressureNeverDLQs` 断言新 outcome。`go test ./internal/outbox/` 全绿。
