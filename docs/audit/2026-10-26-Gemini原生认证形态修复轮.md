## 1. 症状与判据

用户报：**Gemini 的数据转换好像认证没通过**。

「认证没通过」在本仓有三种可能的落点，逐一实测排除：

| 落点 | 判据 | 实测 |
|---|---|---|
| 网关自身把请求拒了 | 全局静态 key 门 / 数据面 KeyVerifier | ★ **命中** |
| 网关把凭据转给了上游但形态不对 | 上游请求的 header/query | 不命中（上游请求由 executor 重建，只带供应商自己的 key） |
| IR 层丢了凭据 | `internal/ir` 的解析/序列化 | 不命中（IR 层不承载凭据） |

⇒ 根因在**第一层：网关自己的认证门不认 Gemini 原生客户端的凭据形态**。

---

## 2. ★★★ 根因链：**两份互不知情的凭据提取实现，且两份都只认两种形态**

修复前，本仓有**两份**凭据提取实现：

```
middleware/auth_mw.go          → Authorization: Bearer  +  x-api-key（Anthropic）
domains/streaming/handler.go   → Authorization: Bearer  +  x-api-key（Anthropic）
```

而厂方标准文档写明的 Gemini 认证形态，**一张都没实现**：

| 文档（仓内保留的厂方标准） | 写明的认证形态 |
|---|---|
| `docs/vendor-formats/gemini.md` §HTTP 形态 | `POST /v1beta/models/{MODEL}:generateContent?key={API_KEY}`；「API key 通过 query string 或 `Authorization: Bearer` 头传递」 |
| `docs/archive/process/format-conversion/厂家数据格式/gemini/generate-content.md` §认证 | `?key={API_KEY}` 或 `Authorization: Bearer {ACCESS_TOKEN}` |
| `docs/供应商协议优化.md` §8.3 | 「Header：`x-goog-api-key: <key>` 或 `?key=<key>`」 |
| `docs/QUICK_REFERENCE.md` §Gemini协议 | `POST /v1/models/gemini-pro:generateContent` + `x-goog-api-key: xxx` |

⇒ ★ **`docs/QUICK_REFERENCE.md` 记的就是本仓自己的对外契约**（网关的 Gemini 端点该用什么头认证），
  而实现里**没有这条契约** ⇒ 照文档写的客户端必然 401。

### 三层断点（修前逐层实测）

```
Gemini 客户端
  │  x-goog-api-key: sk-xxx   或   ?key=sk-xxx
  ▼
① middleware/auth_mw.go（全局静态 key 门，链最外侧）  ★ 401 missing_key ← 死在这里
  ▼
② domains/streaming/handler_gemini.go → newGeminiSyntheticRequest
  │    · 头被克隆（x-goog-api-key 活着）
  │    · ★ query 被丢弃（合成请求 URL 是新建的）⇒ ?key= 这一形态当场蒸发
  ▼
③ domains/streaming/handler.go: extractBearerToken（数据面 KeyVerifier）
       ★ 只认 Bearer / x-api-key ⇒ 两种形态都取不到 ⇒ 401 missing_key
```

★ **即使把①放行，③仍会拒**：①与③是**两份**实现，只修一份就是**半修**。

实测（修复前，红）：

```
--- FAIL: TestAuthMiddleware_AcceptsGeminiNativeCredentialForms
        401 {"error":{"code":"missing_key",...}}
--- FAIL: TestNewGeminiSyntheticRequest_NormalizesGeminiCredential
        Authorization = "", want "Bearer sk-gemini-key"
--- FAIL: TestExtractBearerToken_GeminiCredentialForms
        extractBearerToken = "", want "sk-gemini-key"
```

## 3. 修法

### 3.1 唯一事实源：`internal/auth/clientkey.go`（新）

四种形态收成**一份**实现，优先级：

```
Authorization: Bearer  >  x-api-key  >  x-goog-api-key  >  ?key=
```

★ `Authorization: Bearer` 永远优先 ⇒ 同时带多种形态的客户端不会被**静默改指**到另一把钥匙。

★ 顺带修掉两份实现的历史分叉：数据面认 `bearer`（小写），全局门不认 ⇒ 现在统一按 RFC 7235 大小写不敏感。

### 3.2 ★ `?key=` **只在 Gemini 原生路由上生效**

`key` 是极通用的 query 参数名。全局认它当凭据源 ⇒ 未来任何一个把 `?key=` 当**业务参数**用的端点都会被静默劫持。

⇒ 收口到 `auth.IsGeminiNativePath(p)`，其锚点就是**挂载 Gemini handler 的两个 mux 子树**
（`/v1beta/models/`、`/v1/models/`，cmd/gateway/main.go:6795-6796）。

★ 锚点**只锚头不锚尾**：handler 自己的路径解析器是**子串匹配**（`geminiModelPathRe`），
  它会连 `/v1beta/models/x:generateContent/extra` 这种畸形尾巴一起服务
  ⇒ **收口面必须覆盖 handler 服务到的每一条路径**，否则会出现「路由在服务、却没法认证」。

### 3.3 入口一次性归一（`domains/streaming/handler_gemini.go`）

Gemini handler 把请求转成**合成的 `/v1/chat/completions`** 交给 ChatHandler ⇒ 下游全是 OpenAI 形状的代码。

⇒ 在**边界上**把厂商形态归一成 `Authorization: Bearer`：

```go
func normalizeGeminiCredential(synth, original *http.Request) { … }
```

★ 为什么不在合成请求里保留 `?key=`：合成请求的 URL 是 `httptest.NewRequest` 新建的，
  query 本来就带不过来；而把 key 留在 URL 上 ⇒ 它会进内部请求的 URL 字段 ⇒ 有落进日志的风险。
  归一成头之后，凭据只存在于 `Authorization` 头里。

★ 归一后下游**一行都不用改**（key verifier / static data-plane key / request-meta / sanitizer 全部走
  `extractBearerToken`）⇒ 不会出现「入口认了、下游不认」的半修状态。

★★ **只归一**本轮新增的**两种**形态（`x-goog-api-key` / `?key=`）**：
  `x-api-key`（Anthropic）本来就能被下游 `extractBearerToken` 读到（合成请求克隆了原始头）
  ⇒ 把它改写成 `Authorization` 会**顺带改变另一条既有路径的行为**
  （无 verifier 模式下 handoff 会把 `Authorization` 里的客户端凭据转给摘要上游，
  见 `trustedHandoffUpstreamAPIKey`）⇒ ⇒ 那是本轮范围之外的行为，本轮**不动**。
  ⇒ 门：`TestNewGeminiSyntheticRequest_LeavesAnthropicCredentialAlone`（反向钉）。

### 3.4 ★★ 配套安全面：凭据不许落日志

`?key=<API_KEY>` 把 key 放进 URL ⇒ 而访问日志记录的是**原始 query 串**
（`middleware/logging_mw.go` 的 `compactQuery` 此前**只截断、不脱敏**）
⇒ 一旦开始认这个形态，客户端 API key 会以明文写进滚动日志文件（以及 panic 日志）。

⇒ `compactQuery` 改为**先脱敏再截断**（被截断的 query 永远不会露出半个 secret）：

| 参数 | 处理 | 理由 |
|---|---|---|
| `key` | 脱敏 | 本轮新增认作凭据的 Gemini 形态 |
| `token` | 脱敏 | admin EventSource 的凭据形态（`admin/auth.go` 把它提升成 Authorization 头）—— **同一缺陷族** |
| `api_key_id` / `credential_id` | **不脱敏** | 是**标识符**不是凭据，脱敏会毁掉运维可读性 |
| 其它一切 | 原样 | 参数顺序与编码都不动 |

★ 脱敏只认**精确参数名** ⇒ `apikey=` / `monkey=` 这类只是「含有 key 字样」的参数不受影响。

### ★ 契约测试当场抓到的真漂移（★ 以及它抓到的其实是**量具的错**）

`TestGeminiNativePathMatchesHandlerParser` 第一版断言「收口面 ≡ handler 解析面」，
当场报出**一处真漂移**：

```
route-set drift on "/v1beta/models/gemini-2.5-pro:generateContent/extra":
    handler parses it = true, credential scope covers it = false
```

⇒ 根因是**断言本身写错了**：handler 的解析器是子串匹配，而它**只在两个 mux 子树下**才被调用。
  `/prefix/v1beta/models/x:generateContent` 这种路径**永远到不了 handler**（mux 直接 404），
  却会被子串解析器「接受」⇒ 把「解析器接受」当成「路由被服务」是**量具缺陷**。

⇒ 判据改成**「被服务面」**：

```
被服务 ⇔ 在某个挂载前缀下 ∧ 解析器接受
⇒ 被服务的 ⇒ 收口面必须覆盖
⇒ 未被服务的 ⇒ 收口面必须不覆盖
```

★ 第二版又把「在挂载前缀下、但解析器不接受」（`/v1beta/models/x:countTokens`、
  `/v1beta/models/x`、`/v1beta/models/`）当成违规 ⇒ 那也是**断言的错**：
  这些路径**根本不是 Gemini 路由**（handler 对它们回 404），收口面不覆盖它们是**对的**。

★ 这正是本仓反复吃过的那口教训：**断言写错时，报出来的「漂移」是量具的，不是被测物的。**
  ⇒ 两版断言的错误都被同一处漂移逼出来 ⇒ **契约测试的价值不在「抓到漂移」，在「逼你把语义问清楚」。**

## 6. ★ 本轮明确没做（留给下一轮，别重复排查）

- ★ **`citationMetadata` 捕获（IR 能力缺口，非本轮症状）**：厂方文档写「Gemini 在响应中提供引用元数据，
  IR 需要捕获并可在序列化为 OpenAI 时映射为 annotations」，但**IR 里根本没有承载它的字段**
  （`ParseGeminiResponse` 的候选结构里没有 `citationMetadata`；OpenAI/Responses 侧的
  `annotations` 是写死的空数组）。
  ⇒ 要实现 = 新增 IR 字段 + Gemini 响应解析 + 两种上游序列化 ⇒ **是一笔独立的特性工程**，
  且**对用户报的症状无帮助**（Gemini 客户端 → 网关 → OpenAI 形状上游 ⇒ 上游压根不产 Gemini 引用）⇒ 本轮**只登记不实现**。
- **Gemini 原生模型列表**：`GET /v1beta/models`（不带 `:generateContent`）在本仓**不可用**
  —— mux 把它导到 Gemini handler，而 handler 只认带 action 的路径 ⇒ 404。
  这是**路由面缺口**，不是认证面缺口，本轮未动。
- **Gemini 原生出站（上游）executor**：`provider/catalog` 的 `gemini-generate` 作为**出站**协议
  仍是 `routeUnsupportedGemini`（`executor_dispatch.go`）⇒ 网关只能把 Gemini 客户端的请求
  转成 OpenAI 形状发给上游（Google 的 OpenAI 兼容端点）。`docs/供应商协议优化.md` §8.3
  描述的「Gemini executor + `x-goog-api-key` 出站头」**仍未实现**。
- **`?key=` 形态在 nginx access log 里的明文**：本仓只能保证**自己**的日志脱敏；
  边缘 nginx 若记录完整 query，key 仍会落在那里 ⇒ 需运维侧配合（关闭 `$request_uri`
  或对该前缀做脱敏）。
- **计数为凭据形态**：`/v1beta/models/{m}:countTokens` 之类动作未挂载。
- **`web-mobile` 的 Gemini 客户端形态**：未核查。
