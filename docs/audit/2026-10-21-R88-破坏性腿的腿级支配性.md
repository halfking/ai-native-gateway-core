## 3. ★ 审计发现 1：R87 的门是**文件级**断言，而危害的单位是**腿**

### 3.1 原口径

R87 的门问的是（`r87AnalyzeFile` 原实现）：

```
first := live[0].pos
if !r87HasGuardBefore(f, fset, first, ...) {   // ← 只看「第一条破坏性语句之前」
    ...判成候选...
}
```

而 `r87HasGuardBefore` 的实现是**文件内的位置序**：

```go
for _, h := range r87CollectHits(fset, f, assigned) {
    if h.pos < pos {   // ← 只要「判定」在「破坏性语句」前面就算有守卫
        return true
    }
}
```

⇒ ⇒ **它问的是「这个文件里有没有一个判定排在破坏性语句前面」**，
**它没有问「执行这条破坏性 SQL 的那条路径上，那个判定会不会真的执行」**。

### 3.2 恒真推论

危害的单位是**腿**（一条会真的执行破坏性 SQL 的测试路径）⇒ ⇒ 于是：

> **「一个文件里有一条腿带守卫 ⇒ 整个文件（含别的腿）都被判成有守卫」**

这��推论**恒真**，所以门不会红。

### 3.3 变异 M1（决定性证据，同基线对照）

**形态**：给一条**已带守卫**的文件（`scripts/audit/promote_integration_test.go`）追加一条
**不带守卫**的第二入口 —— 它自己读事实源 DSN、自己建池、自己 TRUNCATE 产品表，全程无任何目标库判定：

```go
func TestR88Mutation_UnguardedSecondEntryPoint(t *testing.T) {
	dsn := os.Getenv(auditDBEnv)
	if dsn == "" { t.Skipf(...) }
	pool, err := pgxpool.New(context.Background(), dsn)   // ★ 绕过 openPool ⇒ 绕过守卫
	...
	_, err = pool.Exec(context.Background(), "TRUNCATE public.session_bodies_hot")
}
```

**读数**：

| 口径 | 读数 |
|---|---|
| **BEFORE**（`origin/main` = `f0a1af2be`，文件级） | ★ **绿**：`ok ... scripts/ursmcheck 2.435s` ⇒ **洞成立** |
| **AFTER**（本轮，腿级） | ★ **红**：`探测到 6 条…台账登记 5 条（未登记 1、腐化 0）` ⇒ **抓到那条新腿** |

⇒ ⇒ 危害量化：事实源（`scripts/audit/datasource_env.sh`）给什么值，那条新腿都会
`TRUNCATE public.session_bodies_hot`（**产品表**）⇒ **数据事故级**，
而 R87 的门**看不见它** —— 恰恰是这道门存在的目的被自己绕过去了。

### 3.4 为什么这不是「理论洁癖」

R87 自己写下的判据文案是：

> 「事实源给什么值它都会清空那张表（数据事故级）」

⇒ ⇒ 门**声称**守的是「这条腿」，**实际**守的是「这个文件」⇒ ⇒ **声称与覆盖不一致**
⇒ ⇒ 这正是本仓反复登记的「声明了什么 vs 覆盖了什么」族。

## 4. ★ 审计发现 2：腿根必须取**调用者侧的测试入口**（反向变异实证）

直觉方案：把腿根改成「破坏性语句所在函数」。**实测这条是错的。**

原因：仓内四条真腿的破坏性字面量住在**兄弟 helper** 里，守卫住在**另一个** helper 里：

| 腿 | 破坏性字面量所在 | 守卫所在 |
|---|---|---|
| `scripts/audit/promote_integration_test.go` | `reset` | `openPool` |
| `domains/session/v2/session_aggregate_outbox_reaper_integration_test.go` | `resetOutboxAndSessions` | `openAuditPool` |
| `admin/data_lifecycle_attachments_integration_test.go` | `attachFixtureReset` | `openAttachPool` |
| `deploy/sql/verify/supplier_errors_pg_test.go` | `bootstrapSupplierSchema` | `openSupplierPG` |

⇒ ⇒ 两者是**兄弟**，不是祖先 ⇒ ⇒ 支配关系在**调用者**那一侧：测试函数**同时**调了那两个 helper
（`pool := openPool(t)` 在前，`reset(t, pool, …)` 在后）。

**反向变异 M2**（把腿根改成「语句所在函数」）的读数：

```

夹具门：RED（夹具 ⑫ 抓出的腿根应是 TestUnguardedLeg，实得 "reset"）
```

⇒ ⇒ **修好漏放 ≠ 不会误报** ⇒ ⇒ 必须用**反向变异**同时验证两侧。

## 5. 修法：腿级支配性

### 5.1 判定

- **腿根** = 能到达该破坏性语句的**测试入口**（`Test` 前缀的函数）；
  若没有任何测试入口能到达它（退化形态，例如整文件只有一个非 `Test` 函数）⇒ 以**该语句所在函数**为腿根。
- **被守卫支配** ⇔ 腿根的**同文件可达集合**里，存在一个
  「体内含目标库判定证据」或「调用了跨包闸门（按包自己声明的 `GuardFunctions` 名单）」的函数。
- 跨包闸门名单沿用 R87 的口径：**优先按包自己声明的名单**（`internal/testguard.GuardFunctions`），
  包没声明才退回包级粗口径 ⇒ ⇒ R87 变异 M1 的教训（包级能力 ≠ 函数级契约）**继续成立**。

### 5.2 改动

| 文件 | 改动 |
|---|---|
| `scripts/ursmcheck/destructive_target_guard_test.go` | 删 `r87HasGuardBefore`（**文件级位置序**口径）⇒ 换 `r88AnalyzeLegs` / `r88CollectFuncs` / `r88Reach` / `r88Guarded` / `r88Enclosing`；`r87Pair` 加 `Root` 字段；报错文案点名**腿根** |
| `scripts/ursmcheck/leg_dominance_guard_test.go` | ★ **新文件**：腿级判据的 6 个夹具门 |

### 5.3 诚实边界（登记，不掩饰）

★ 可达性是**同文件**的 ⇒ ⇒ **跨文件同包**的 helper 调用**判不出来**
⇒ ⇒ 若守卫与破坏性语句分居同包的两个文件，本门会**判成无守卫**（假阳性方向）。
⇒ 当前仓内四条真腿的守卫与破坏性语句**同文件**，台账三条也同文件 ⇒ **实测无影响**。
⇒ 该缺口与 R87 台账里「跨文件自建库」那条**同性质**（都是跨文件形态静态判不出）。
