# R91 · 发版 2841 被「远端锁」挡住：真因是 SSH 传输层四层缺陷，不是锁冲突

> 轮次标签 **2026-10-27**（沿用 R87~R90 口径）；**实测时钟 2026-10-24**（本机 / 252 / 154 三方一致）。
> ⚠ 修复代码落在 **deploy-lib 仓**（`~/workspace/ai-native-tools/deploy-lib/`，monorepo `ai-native-workspace`），
> 不在 llm-gateway-go 仓；本档放在 llm-gateway-go 是因为它是本项目审计链的一环。

## 0. 一句话结论

发版 2841 报的 `ERROR: remote lock held or initialization failed at /var/lib/llm-gateway-go/deploy.lock on 154`
**是误报**：154 上该锁目录**根本不存在**（父目录是空的）⇒ 锁既没被持有、也没初始化失败。
真因是 **SSH 传输层在 pre-auth 阶段被 154 的 sshd 按 `MaxStartups` 默认值随机丢弃 ~30%**，
而部署工具的 pipe 通道 **既不重试、又丢掉了判定重试所需的 stderr、还从不走 252 跳板**，
⇒ **一次链路抖动就把整个部署打死**，且报错文案把「传输层失败」说成「锁冲突」，把排查方向带偏。

## 1. 症状（2026-10-24，llm-gateway-go build 2841 → 154）

```
[ssh-retry] init target=154 socket=/var/folders/.../T/ssh-retry-79912/cm-154.sock
[ssh-retry] target=154 pipe attempt=1/3 rc=255 retry in 2s (proxy=true)
[ssh-retry] target=154 pipe attempt=2/3 rc=255 retry in 4s (proxy=true)
ERROR: remote lock acquisition on 154 failed at the SSH transport layer (exit 255) — this is NOT a lock conflict.
DEPLOY_EXIT=75
```

（★ 上面的日志是**修复后**的重跑，它恰好证明「重试已经生效但 hop 也不通」；
首次失败时报的是旧文案 `remote lock held or initialization failed`。）

⇒ **关键观察**：远端加锁是整个部署的**第一个** SSH 操作 ⇒ 它的失败概率 = 整个部署的失败概率。

## 2. 归因（四层叠加，逐层实测）

### 2.1 第一层：154 的 sshd 在 pre-auth 阶段随机丢连接（服务端根因）

| 证据 | 读数 |
|---|---|
| 154 sshd 日志 | `Connection closed by 5.231.242.181 port NNNNN [preauth]` —— 连续刷屏 |
| fail2ban sshd jail | `Currently failed: 2`，**Total failed: 401,449** |
| 近 10 分钟 preauth 次数 | **1,224** |
| 实测并发 preauth 连接 | **12** |
| `MaxStartups` | **未设置** ⇒ 默认 `10:30:100` |
| `MaxSessions` / `LoginGraceTime` | 5 / 60 |

★ **机制**：sshd 在未认证连接数 ≥ `MaxStartups` 的起始值（10）时，会**随机丢弃 30%** 的新连接。
观测到的并发 preauth = 12 > 10 ⇒ 丢弃条件长期成立。
★ **实测失败率与理论丢弃概率吻合**：直连 154 连续 10 次成功 7 次（**30% 失败**），
间隔 5s 连发 6 次仍失败 2 次（**33%**）⇒ **不是「快速连发触发限流」，是持续性的**。

★ **客户端看到的现象**：连接在**认证之前**被服务端关闭 ⇒ ssh 退出码 **255**，
stderr 一行 `Connection closed by 47.97.111.154 port 25022`。

### 2.2 第二层：`ssh_run_pipe` 把 stderr 丢掉 ⇒ 255 也判 fail ⇒ **完全不重试**

```bash
# 旧实现（deploy-lib/ssh-retry.sh）
ssh ... "$host" "$script" >/dev/null 2>&1      # ← stderr 被丢弃
exit_code=$?
classify=$(_ssh_retry_classify "$exit_code" "") # ← 传的是空串
```

`_ssh_retry_classify` 的关键字表里明明有 `Connection closed`，但它拿到的 `output` 是空串
⇒ 正则永不命中 ⇒ exit 255 落到 `fail` 分支 ⇒ **直接 return，连一次都不重试**。

★ 对照：`ssh_run`（非 pipe 侧）用的是 `output=$(ssh ... 2>&1)` ⇒ 能拿到 stderr ⇒ 能分类。
**两个函数本来应该对称，实际不对称。**

### 2.3 第三层：`ssh_run_pipe` **从不走 252 跳板**

`_ssh_retry_fallback_hop` 对 154 返回 `root@115.29.212.252`，
`ssh_run` 用它构造 ProxyCommand；**`ssh_run_pipe` 里根本没有 `hop` 这个变量**。
⇒ 管道类操作（远端加锁、release tar 上传、配置下发）**永远走直连**，
而直连正是那 30% 失败率的链路。

★ 同时 `SSH_RETRY_FALLBACK_AFTER` 的注释写的是
`# 154 默认立即使用跳板机（0=不先尝试直连）` —— **实现却是先直连** ⇒ 文档与实现不符。

### 2.4 第四层：hop 路径**从来没通过**（端口丢失）

```bash
proxy_flag="-o ProxyCommand=ssh -W ${host#*@}:${port} $hop"
#        ⇒ ssh -W 47.97.111.154:25022 root@115.29.212.252
```

★ 跳板机写的是**裸 IP** ⇒ ssh 走**默认端口 22**；
而 252 的 sshd 听在 **25022**，端口只挂在 `~/.ssh/config` 的 **`Host 252` 别名**上
（裸 IP 匹配不到那段配置）⇒ 隧道必失败。

实测（2026-10-24）：

| 写法 | 结果 |
|---|---|
| `ssh -W ... root@115.29.212.252`（无 `-p`） | 失败 |
| `ssh -W ... -p 25022 root@115.29.212.252` + 外层 `-p 25022` | **5/5 成功** |

⇒ ★ **这条 hop 路径从来没通过过**；旧代码只是把它的失败藏在重试里（且 pipe 侧压根不重试）。

### 2.5 第五层：错误文案把三类成因揉成一句

`lock_acquire_remote` 的失败分支无论何种原因都打印
`remote lock held or initialization failed` ⇒ **「传输层失败」被说成「锁冲突」**，
⇒ 运维的直觉动作是去 unlock / 删锁 —— 而锁根本不存在。

★ 顺带实测到一个 bash 陷阱：`if ! cmd; then echo "$?"; fi` 里 **`$?` 恒为 0**
（`!` 把状态取反了）⇒ 想按退出码分类必须用 `cmd || rc=$?`。

## 3. 修法（落在 **deploy-lib** 仓，不在 llm-gateway-go）

### 3.1 `deploy-lib/ssh-retry.sh`

| 改动 | 解决的问题 |
|---|---|
| `ssh_run_pipe`：**stdin 只读一次并落盘缓存**，每次尝试从该文件重放 | §2.2 的连带危害：重试时 stdin 已被消费完 ⇒ 远端 `bash -s` 读到**空 stdin 直接 exit 0** ⇒ **假成功**（锁目录根本没建出来，调用方却以为拿到了锁） |
| `ssh_run_pipe`：**stderr 喂给分类器** | §2.2：让传输层失败可被识别、可重试 |
| `ssh_run_pipe`：**支持 252 跳板**，与 `ssh_run` 对齐 | §2.3 |
| `ssh_run` / `ssh_run_pipe`：**兑现** `SSH_RETRY_FALLBACK_AFTER=0` 的契约（首次即走跳板） | §2.3 的文档/实现不符 |
| ProxyCommand **显式带跳板端口**（`SSH_RETRY_HOP_PORT`，默认同 `SSH_PORT`）+ `StrictHostKeyChecking=accept-new` / `BatchMode=yes` / `ConnectTimeout` | §2.4 |
| stdin 缓存文件登记进 trap 清理列表 | 异常退出时不在 TMPDIR 留几十 MB tar 残骸 |

### 3.2 `deploy-lib/lock.sh`：按退出码区分三类成因

| 退出码 | 结论 | 运维动作 |
|---|---|---|
| 75 | **锁真被持有**（并发部署） | 等或 unlock |
| 255 | **SSH 传输层失败 —— 不是锁冲突** | 重跑部署 |
| 其它 | 初始化失败 | 看远端日志 |

## 4. 门禁与变异

### 4.1 新增 `deploy-lib/test/test-ssh-retry-pipe.sh`（10 场景 / **30 条断言**）

| 场景 | 断言要点 |
|---|---|
| S1 | 首次成功 ⇒ 1 次调用，stdin 原样送达 |
| S2 | 传输层失败 ⇒ 重试，且 **两次的 stdin 逐字一致** |
| S3 | 远端命令失败（exit 1）⇒ **不重试**，退出码原样返回 |
| S4 | 154 ⇒ 首次就走跳板；**ProxyCommand 内部带 `-p 25022`** |
| S5 | 255 但非可重试成因（认证失败）⇒ 不重试 |
| S6 | 每次都失败 ⇒ 尝试满 `SSH_RETRY_MAX` 次后返回 255 |
| S7 | 空 stdin 也走完 |
| S8 | 远端 `bash -s` 在重试后**真的执行**（直击「空 stdin ⇒ 假成功」） |
| S9/S10 | `ssh_run` 侧对称契约：跳板优先 + 传输层失败重试 |

### 4.2 变异验证 **5/5 全红**，且逐字还原（md5 校验）

| 变异 | 回退成什么 | 结果 |
|---|---|---|
| M1 | 去掉 stdin 缓存 | RED |
| M2 | 不把 stderr 喂给分类器 | RED |
| M3 | pipe 侧不走跳板 | RED |
| M4 | `ssh_run` 不兑现 `SSH_RETRY_FALLBACK_AFTER` 契约 | RED |
| M5 | 去掉跳板机端口 | RED |

★ **M5 第一版是绿的（门禁无牙）**：断言写成 `grep '-p 25022'` ⇒ 命中的是**外层** ssh 的 `-p`，
不是 ProxyCommand 里的 ⇒ 改断言为 `'ProxyCommand=ssh -W 10.0.0.1:25022 -p 25022'` 才抓住。
⇒ **断言必须指向「区分度所在的那个片段」**，否则它会给出一个假的安全感。

### 4.3 ★ 门禁自身的第一版也会挂死

`ssh-retry.sh` 的 EXIT trap 会调 `ssh -O exit` 关 master，那次调用**不重定向 stdin**，
继承门禁脚本的 stdin ⇒ 调用方 stdin 若是未关闭的管道，stub 里的 `cat` **永久阻塞**。
⇒ 门禁里 `exec </dev/null` 脱钩；
★ 同时发现 **`source ssh-retry.sh` 会覆盖调用方的 EXIT trap**（bash trap 是替换语义）
⇒ 门禁重装了一个 `ssh_retry_close_all; rm -rf "$E2E"` 的合并 trap，否则临时目录泄漏。

## 8. 通用式（并入 `LESSONS.md` §360）

1. ★★★★ **「锁被持有」与「初始化失败」揉成一句话，会把排查方向带偏** ——
   真实原因是**传输层失败**，而运维的直觉动作是去删锁。
   ⇒ 失败分支必须**按退出码分类**并给出**可执行结论**（等 / 重跑 / 看日志）。
2. ★★★★ **「重试逻辑存在」不等于「重试会生效」** ——
   `ssh_run_pipe` 把 stderr 丢掉后传空串给分类器 ⇒ 关键字表形同虚设 ⇒ exit 255 判 fail。
   ⇒ ★ **量具（分类器）必须拿到被观测对象的输出**；「函数里有 retry 字样」不是证据。
3. ★★★★ **不重试的通道比不稳定的通道更危险** ——
   pipe 侧一次抖动 = 部署直接死；而重试的前提是**输入可重放**，
   否则重试会变成「空 stdin ⇒ 假成功」（锁没建出来却当成拿到了）。
   ⇒ **重试 + 输入可重放** 必须成对实现。
4. ★★★★ **「失败路径从未被测过」会让重试代码里的错永远活着** ——
   hop 路径因为端口写错而**从来没通过**，却因为 pipe 侧不重试而从未暴露。
   ⇒ ★ **每个「备用通道」都要有一条「它真的能用」的断言**（本轮 M5 就是这条断言的回归）。
5. ★★★ **`if ! cmd; then echo "$?"` 的 `$?` 恒为 0** ——
   要按退出码分类必须 `cmd || rc=$?`。
6. ★★★ **门禁自身也是量具，也会挂死、也会泄漏、也会被覆盖** ——
   本轮门禁的第一版：`ssh -O exit` 继承 stdin ⇒ 永久阻塞；`source` 覆盖 EXIT trap ⇒ 临时目录泄漏。
   ⇒ ★ 写门禁时把「门禁自己会不会挂/会不会泄漏」当成一条要测的用例。
7. ★★★ **断言必须指向「区分度所在的那个片段」** ——
   M5 第一版用 `grep '-p 25022'` 命中的是外层 ssh 的端口，变异因此漏网。
