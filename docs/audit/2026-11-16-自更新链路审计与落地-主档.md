## 一、结论速览（一句话）

**这条链路此前是「组件齐全、从未跑通」的**：`autoupdate` 包里下载器/安装器/回滚器都写好了，
但 `AdminAPI` **从不调用**它们，`/api/system/upgrade/check` 只读本地表、**从不联网**，
全仓**没有任何周期任务**，所以「自动检索 / 自动提醒 / 点击安装 / 本地编译启动」**四项全都不存在**；
而且即便把安装接上，也会在三道闸门上**100% 失败**（校验契约、制品权限、安装路径）。

本轮把这条链路从「写了一半」补成「端到端可跑」：远端检索 → 双写提醒（升级日志 + 运维告警）→
点击安装（下载制品 / 本地源码编译）→ 校验 → 备份 → 替换 → 迁移 → 重启，全链路有钉测与变异负控。

★ **复核轮补齐的一条容易被忽略的不变量**：提醒必须**有生命周期**。
「提醒行」与「安装任务日志行」是**同一行**（同一件事的两个阶段）⇒ 检索器建 `pending` 行、
执行器复用并推进它 ⇒ 升级成功后提醒自动闭合；
**回滚之后提醒不能消失**（新版仍在、节点仍在旧版，这正是最该提醒的场景）⇒
可行动状态集合 = `{pending, failed, rolled_back}`，只有 `success` 才撤下。
且回滚必须**同时还原 `version.json` 真源** —— 否则节点顶着新版号跑旧二进制，
检索基线失真 ⇒ 远端答「已是最新」⇒ **该节点永远停在旧二进制上，且再也不会被提醒**。
详见 §二 F13–F16 与 §5.2.2。

## 二、缺陷清单（逐条带证据）

### F1（P1）点击安装升级**没有入口**——下载器与安装器是死接线

| 项 | 内容 |
|---|---|
| 现象 | `AdminAPI` 结构体持有 `downloader`/`installer`，但**零调用**；`/api/admin/releases/*` 只有 CRUD/发布/灰度/回滚 |
| 证据（修复前） | `grep -n "a\.downloader\|a\.installer\|a\.rollback" autoupdate/admin_api.go` → **只有 1 命中**（`a.rollback`，在 `RollbackRelease` 里）；downloader/installer 零命中 |
| 影响 | 用户在控制台点任何「升级」按钮都不存在可调用的执行路径；安装器是纯死代码 |
| 修法 | 新增 `POST /api/admin/releases/:version/install`（制品）与 `POST /api/admin/releases/:version/source-build`（源码），由 `Executor` 后台执行、立即返回任务快照 |

### F2（P1）安装校验契约与被装二进制不一致 ⇒ 安装 100% 失败并回滚

| 项 | 内容 |
|---|---|
| 现象 | `Installer.verifyBinary` 执行 `<new-binary> --version`；而网关**只认 `migrate` 子命令** |
| 证据（修复前） | `autoupdate/installer.go:152` `exec.CommandContext(ctx, path, "--version")` vs `cmd/gateway/main.go:244` `if len(os.Args) > 1 && os.Args[1] == "migrate"` |
| 影响 | 传 `--version` 会让新二进制**整体启动**（连数据库、抢监听端口），5s 后被 context 杀掉 ⇒ `execute --version: signal: killed` ⇒ **每次安装都走到回滚分支** |
| 修法（双侧对齐） | ① 网关新增 `--version`/`-v`/`version` 早退分支（打印版本后 exit 0）—— 被装的二进制必须能用 `--version` 自证身份；② 安装器改为**先结构校验（魔数+体积+可执行位）、后语义探测（尽力而为，失败只记 WARN）** |

### F3（P1）下载的制品不是可执行文件 ⇒ 校验必然失败

| 项 | 内容 |
|---|---|
| 现象 | `Downloader.Download` 用 `os.Create` 以 **0644** 落盘；安装器在替换**之前**校验 ⇒ 校验看到的文件没有执行位 |
| 证据（修复前） | `autoupdate/downloader.go` `os.Create(tmpPath)`（默认 0644），全文件无 `Chmod` |
| 影响 | 与 F2 同型：即使 F2 修了，`<bin> --version` 也会 `permission denied` ⇒ 仍然 100% 失败 |
| 修法 | 下载器落盘后 `os.Chmod(tmpPath, 0o755)`（制品本就是可执行文件） |

### F4（P1）安装路径与真实部署布局完全不符 ⇒ 装到「没在跑的文件」上

| 项 | 内容 |
|---|---|
| 现象 | 网关硬编码 `/usr/local/bin/llm-gateway-go` + `/var/backups/llm-gateway` + `/var/lib/llm-gateway` |
| 证据（修复前） | `cmd/gateway/main.go` Phase 4 段 vs `deploy/llm-gateway-go.service:11-14`（`WorkingDirectory=/opt/llm-gateway-go`、`ExecStart=/opt/llm-gateway-go/llm-gateway-go`） |
| 影响 | 即使安装链路跑通，替换的也不是正在运行的那个二进制 ⇒ 「升级成功」是假话 |
| 修法 | 全部改为环境变量可配置，默认值对齐真实部署布局（`/opt/llm-gateway-go/...`） |

### F5（P1）「自动检索最新版本」**根本不存在**

| 项 | 内容 |
|---|---|
| 现象 | `/api/system/upgrade/check` 只查**本地** `releases` 表；全仓无任何远端拉取、无任何周期任务 |
| 证据（修复前） | `autoupdate/customer_api.go:89` `api.store.GetLatestReleaseAfter(ctx, api.channel, currentSeq)`；`grep -rn "Ticker.*upgrade\|poll.*release\|fetchLatestRelease"` → **零命中** |
| 影响 | 本地表里的 `releases` 行只能由管理员手工 POST 产生 ⇒ 「系统自动检索」未实现；且本地表是**检索器的产物**，读它是自证 |
| 修法 | 新增 `RemoteSource` 抽象 + `HTTPRemoteSource`（对接仓内既有 authority 契约 `/api/v1/updates/latest` + `/api/v1/updates/manifest`）+ `Checker` 周期检索（默认 6h） |

### F6（P1）「自动提醒」**根本不存在**

| 项 | 内容 |
|---|---|
| 现象 | 无轮询、无推送、无通知面；前端只在 `onMounted` 查一次 |
| 证据（修复前） | `web/src/views/lifecycle/UpdateActivateView.vue` `onMounted` 单次取数；后端无任何通知写面 |
| 影响 | 「有新版」这件事只有人工想起来去点才看得见 |

### F7（P1）「本地自动编译然后启动」**根本不存在**

| 项 | 内容 |
|---|---|
| 现象 | 安装器只支持「下载二进制 → 替换」；无源码构建路径 |
| 证据（修复前） | `autoupdate/installer.go` 全文无 `go build` / `git` 调用 |
| 影响 | 离线环境、灰度环境、需要带本地补丁的场景无法自更新 |

### F11（P1·本轮真跑新发现）源码构建器把 `git worktree` 执行成了 `go worktree`

| 项 | 内容 |
|---|---|
| 现象 | `SourceBuilder` 的执行入口只有一个，git 子命令也走 `b.goBin`（默认 `go`）⇒ `git worktree add` 实际执行成 `go worktree add` |

### F12（P2·本轮真跑新发现）`worktreeDir` 被块内 `:=` 遮蔽 ⇒ `UsedWorktree` 恒假

| 项 | 内容 |

| 影响 | 编译其实走了 worktree，但对外报告的 `UsedWorktree=false` ⇒ 运维侧会误判「没走隔离检出」 |

### F13（P1·复核轮发现）提醒行**永不变更状态** ⇒ 升级成功后仍显示「待处理」

| 项 | 内容 |
|---|---|
| 现象 | 检索器建 `upgrade_logs` 一行 `status=pending`（提醒行）；安装执行器 `createLog` 却**另起一行**写安装日志 ⇒ 提醒那一行永远停在 `pending` |
| 证据（修复前） | `checker.go:293` 建 pending 行；`executor.go` 的 `createLog` 调 `store.CreateUpgradeLog` 新建 ⇒ 两个 id 不同源；`GetUpgradeHistory` 虽然 `SELECT id`，却扫描进**局部变量后丢弃**（`store_pgx.go`）⇒ 调用方拿不到那一行的主键 |
| 影响 | 提醒列表里永远挂着一条「待处理」，运维不知道升级到底成没成；提醒与任务两处对不齐 |
| 修法 | ① `ReleaseStatus` 新增 `LogID`（`upgrade_logs.id`），`GetUpgradeHistory` 扫进该字段；② 执行器 `createLog` 改为**复用**该版本上仍可行动的那一行（`findActionableLog`），无则新建；③ 提醒行 ≡ 安装任务日志行（**同一行**：待处理 → 执行中 → 终态） |

### F14（P1·复核轮发现）回滚**不还原 `version.json` 真源** ⇒ 版本身份漂移

| 项 | 内容 |
|---|---|
| 现象 | `restoreVersionFiles(oldVersion)` 只回写 `VERSION`，注释还写着「version.json 保持原值」——而此时 `version.json` **已被新版覆盖**，「保持原值」事实上是错的 |
| 证据（修复前） | `installer.go` 旧 `restoreVersionFiles`：`os.WriteFile(dataDir/VERSION, oldVersion)`；`version.json` 的旧内容**从未被快照**（写之前直接覆盖） |
| 影响 | 回滚后**二进制是旧的、网关报的是新版号** ⇒ 见 F15，这是本轮最危险的一条 |
| 修法 | 写版本元数据**之前**先快照（`versionSnapshot` / `snapshotVersionFiles`），任一步失败按快照**原样还原** `version.json` + `VERSION`；快照里本来没有该文件时（首次安装）⇒ 删掉新建的那个，不留「假装装过」的元数据 |

### F15（P1·复核轮发现）版本身份漂移 ⇒ **该节点永远停在旧二进制上，且再也不会被提醒**

| 项 | 内容 |
|---|---|
| 现象 | 网关的版本真源就是 `version.json`（`cmd/gateway/version.go:40` 明写「唯一的 SSOT」）；`currentGatewayVersionProvider()`（`cmd/gateway/customer_helpers.go:147`）读 `Version()` + `BuildSeqInt()` ⇒ 读的正是那份被漂移的 `version.json` |
| 因果链 | 回滚只还原二进制 ⇒ `version.json` 留着新版号 ⇒ 网关自报新版 ⇒ **Checker 拿错误基线去问远端** ⇒ 远端答「已是最新」 ⇒ 检索器不再生成提醒行 ⇒ 节点永远停在旧二进制上、再也没有人知道该再升一级 |
| 影响 | 恰好打掉本轮要修的「自动检索 + 自动提醒」**在最需要它的场景（坏版本）里的作用** |
| 修法 | ① F14：回滚必须同时还原 `version.json` 真源；② 提醒去重判据从「该版本上有没有任何一行」改为「**有没有未完成的尝试**」（`h.Status != StatusSuccess` 才抑制）⇒ 上一次装成功后若被**手工回滚**，远端再次报「有新版」时会**重新提醒** |

### F16（P2·复核轮发现）提醒列表只取 `pending` ⇒ 回滚之后提醒彻底消失

| 项 | 内容 |
|---|---|
| 现象 | `GetNotifications` 筛 `h.Status == StatusPending`；而 `failed`（下载/校验失败）与 `rolled_back`（装了起不来、已还原）**都仍待处理** |
| 证据（修复前） | `admin_api.go` `if h.Status == StatusPending {` |
| 影响 | 最需要提醒的两种状态恰好被过滤掉 ⇒ 新版还在、节点还在旧版，却不再提醒 |
| 修法 | 新增 `IsActionableStatus(status)`：`pending` / `failed` / `rolled_back` ＝ **可行动**；`success` ＝ 告一段落；`downloading` / `ready_to_restart` / `upgrading` ＝ 进行中。提醒列表 = 可行动状态集合 |

## 三、落地后的完整流程

```
                        ┌──────────────── 后台 Checker（默认 6h 周期，首次 30s）────────────────┐
                        │                                                                │
 远端发布源              │  ① GET {source}/api/v1/updates/latest?current_version=…            │
 (license-authority      │     → {up_to_date:true} | {version, build_seq, mandatory, …}       │
  / maintain)  ─────────▶│  ② GET {manifest_url} → {binary_url, binary_sha256, changelog}    │
                        └───────────────┬────────────────────────────────────────────────┘
                                        │ 发现新版
                        ┌───────────────▼────────────────────────────────────────────────┐
                        │ ③ 落库：本地 releases 表写入 + 置为已发布                       │
                        │    ⇒ 既有读面 /api/system/upgrade/status 立刻可见「有更新」      │
                        │ ④ 提醒双写：                                                  │
                        │    · upgrade_logs + status=pending   （提醒记录 ≡ 安装任务日志）│
                        │    · runtime_alert_events 'update_available'（运维告警面）      │
                        └───────────────┬────────────────────────────────────────────────┘
                                        │
  运维在控制台点击                        ▼
  「立即检查更新」 ───────────────▶ POST /api/admin/releases/check      （真联网，非读本地表）
  「立即升级」     ───────────────▶ POST /api/admin/releases/:version/install
  「源码编译升级」 ───────────────▶ POST /api/admin/releases/:version/source-build
                                        │
                        ┌───────────────▼────────────────────────────────────────────────┐
                        │ Executor（后台 goroutine；HTTP 立即返回 job 快照）             │
                        │  artifact 模式：下载 → sha256 校验 → 结构校验（魔数/体积/执行位）│
                        │  source   模式：git worktree 检出 → go build → 同上校验        │
                        │  → 备份旧二进制 → 原子替换 → 写 version.json/VERSION           │
                        │  → 执行数据库迁移（<bin> migrate）→ 安排 systemctl 重启        │
                        │  任一步失败 ⇒ 还原旧二进制 + 还原版本元数据（version.json 真源 │
                        │              + VERSION，按写入前快照原样还原）                │
                        │              + 提醒行落成 rolled_back（仍可行动，不撤提醒）    │
                        └───────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
                        GET /api/admin/releases/install-status  （前端轮询进度）
```

★ **为什么「还原版本元数据」必须包含 `version.json`（这不是洁癖，是一条会致死的因果链）**：

```
回滚只还原二进制
   ⇒ version.json 留着新版号
   ⇒ 网关自报新版（version.json 是唯一 SSOT，cmd/gateway/version.go:40）
   ⇒ Checker 拿错误基线去问远端 ⇒ 远端答「已是最新」
   ⇒ 检索器不再生成提醒行
   ⇒ 节点永远停在旧二进制上，且再也不会被提醒
```

⇒ 这条链恰好打掉本轮要修的「自动检索 + 自动提醒」**在最需要它的场景（坏版本）里的作用**。
修法见 F14 / F15：写版本元数据**之前**先快照，失败时按快照原样还原；且「上次装成功后被手工回滚」
必须**重新提醒**（去重判据＝「有没有未完成的尝试」，而不是「有没有任何一行」）。

★ **回答 owner 的最后一问**：「可以在本地自动进行编译然后启动吗？」
—— **可以**，且已落地为 `mode=source`：在本机用 `git worktree` 检出指定 ref，
`go build` 出新二进制，走**与制品完全相同**的校验/备份/替换/迁移/重启链路。

### 5.2.1 实施期自审发现的两处（不是历史缺陷，是本轮做出来就必须自己对齐的语义）

1. **落库失败 ≠ 检索失败**：`CheckResult` 拆成 `Error`（致命：远端查不成 ⇒ 界面必须显示
   「状态未知」）与 `Warning`（非致命：本地落库失败 ⇒ **「有没有新版」的结论仍然成立**）。
   混进 `Error` 会让界面把「本地没写进去」读成「连远端都没查成」，
   **于是「有更新」这个事实被一起抹掉** ⇒ 运维据此跳过补丁。
2. **无鉴权的公开检查端点必须节流**：`/api/system/upgrade/check` 一旦真的出网，
   就等于给任意调用者一个「每次调用都打一次远端」的**外呼放大器**。
   ⇒ 公开面走 `CheckThrottled`（默认复用 60 秒内的最近结论），
   管理员面走 `CheckOnce`（「立即检查」必须真查一次）。

## 七、遗留与边界（如实登记）

1. **未在真实节点跑过自更新**：本轮验证覆盖到「下载→校验→备份→替换→写版本元数据→迁移调用→安排重启」
   的进程内全链路，并已用**真实 105MB 网关二进制**在沙箱里真跑一遍（§5.3），
   但**没有**在 211/245/154 上真跑一次自更新（会替换在役二进制并重启服务）。
   ⇒ 上线前建议在灰度节点做一次演练，且**先确认 `LLM_GATEWAY_UPDATE_SOURCE_DIR` 指向的源码树是干净提交**。
2. **`systemctl` 重启路径**只按 Linux/systemd 语义实现（`Installer.restartService` 走 `systemctl`）；
   容器形态需要改为进程内重启（未做）。
3. **远端源契约取自仓内 `cmd/license-authority`**（`/api/v1/updates/latest` + `/manifest`）。
   若生产实际使用 maintain 的 `/downloads/catalog`，需要给 `HTTPRemoteSource` 增加一种响应解析形态
   （当前只认 authority 形态的 JSON）。
4. **`release.ImageDigest` 兼作 sha256**：沿用仓内既有约定（authority 的 manifest 处理器就是
   `BinarySHA256: release.ImageDigest`）。若 release 行没有 digest，制品模式会**拒绝安装未校验的包**
   （明确报错，不静默放行）。

### 复核轮追加登记（本轮修复后仍然存在的边界）

10. **仍未在 211 / 245 / 154 真跑过一次自更新**（同 §七.1）：本轮修的是「提醒生命周期」与「回滚还原真源」，
    两条都是**进程内**可验的逻辑（已有钉测 + 变异），但「真机装一次坏版本、确认回滚后
    `version.json` 与二进制都回到旧值、且提醒行仍可行动」这一整条**只在沙箱与单测层验过**。
    ⇒ 上线前灰度节点建议专门演练一次**失败路径**（不是成功路径）。

12. **远端源只认 authority 形态的响应**（同 §七.3）：`HTTPRemoteSource` 当前只解析
    `/api/v1/updates/latest` + `/manifest` 的 JSON 形态。
13. **源码编译不含未提交改动**（同 §七.5）：语义＝「编 ref 所指的那个提交」。
14. **前端未活机联调**（同 §七.6）：8 条判据 + 5 项变异都跑在 mock 上，
    没有真网关可供点按钮；接缝点按契约写死（202 / 409 / 503 / 502）。
15. **web-gates 9 项失败为存量**（同 §七.7，隔离 worktree 对拍，差异集为空），违规条目指向他人文件。
16. **回滚后「远端也会重新报有新版」这一前提依赖远端源的诚实性**：本轮的重提醒判据
    （`h.Status != StatusSuccess` 才抑制）解决的是「本地不再生成提醒行」；
    但若远端源在节点已回滚后仍答「已是最新」（例如远端把该版本标记为不可用），
    本地**不会**凭空造出提醒 —— 那种情况需要运维侧从 `upgrade_logs` 的 `rolled_back` 行人工发现。
    ⇒ 本轮把 `rolled_back` 纳入提醒列表（`/api/admin/releases/notifications` 可见），
    就是为了让这种情况**至少有一个人工抓手**，而不是彻底沉默。
17. **`GetUpgradeHistory` 的分页上限 200**：执行器 `findActionableLog` 按版本号在最近 200 行里找可行动行。
    若同一实例在 200 条之内产生过 200 次以上升级记录且目标版本的行被挤出窗口，
    则复用不命中 ⇒ 会新建一行（行为退化但不致错：新行同样是 pending，仍会被提醒）。
    ⇒ **登记为已知边界**，未做全表扫描（避免每次安装都全表扫 `upgrade_logs`）。
18. **失败路径的 `rolled_back` 与 `failed` 在安装器层面仍依赖 `result.RolledBack` 正确置位**：
    迁移失败与服务重启失败两条路径已置位；但**备份失败**与**新二进制校验失败**这两条
    都发生在**替换二进制之前**（`installer.go`：备份 → 校验 → 替换 → 写版本元数据 → 迁移 → 重启），
    此时压根没换二进制、不存在回滚 ⇒ 提醒行落 `failed`（仍可行动，语义正确）。
    ⇒ 运维看告警正文时需区分两者：`failed`＝没换过二进制；`rolled_back`＝换过又换回来了。
    ★ 这也是「提醒行 ≡ 安装任务日志行（同一行）」的附带好处：终态本身就说明了**卡在哪一步**。
