# 格式错误自动重试方案分析

## 背景

用户问题：工具调用格式错误（tool_json_invalid）能否自动重试或修补，避免网络闪动导致的数据不完整？

当前状态（2026-11-15 修复后）：
- 格式类守卫（tool_json_invalid / redact_invalid / frame_encode_failed）不生成审核单
- 客户端看到「上游返回的内容格式有误，请重试」
- **用户需要手动重试**

## 问题分析

### 1. 格式错误的根本原因分类

根据 211 取证（rv-2089）和代码分析，tool_json_invalid 有三类成因：

#### A. 上游中转格式转换错误（rv-2089 实例）
```
{"description</arg_key><ac7a3bd7><arg_value><b88a6f17>查找项目目录</arg_value>...
```
- **根因**：apiclaude.cc 的 GLM 工具调用解析器漏出原生 XML 标签
- **特征**：116 字节，包含 `<arg_key>` / `<arg_value>` 等 GLM 原生标记
- **可重试性**：✅ **高** - 上游重新生成可能修复（模型输出非确定性）
- **可修补性**：⚠️ **中等** - 需要识别具体上游格式并编写解析器

#### B. 网络传输截断
- **根因**：TCP 连接中断、代理超时、SSE 流未完整传输
- **特征**：JSON 结构不完整（缺少闭合括号、字段截断）
- **可重试性**：✅ **高** - 网络瞬态问题，重试大概率成功
- **可修补性**：❌ **低** - 数据丢失无法恢复，只能重试

#### C. 模型原生输出错误
- **根因**：模型直接生成了非法 JSON（罕见但存在）
- **特征**：语法错误、引号不匹配、控制字符未转义
- **可重试性**：⚠️ **中等** - 同样的 prompt 可能重复出错
- **可修补性**：⚠️ **中等** - 简单语法错误可尝试修复，复杂的不行

### 2. 当前重试机制的限制

**关键发现**：网关的流式处理架构导致格式错误**结构性不可重试**

```
检查点位置：security/sanitize/output_sensitive.go:209
触发时刻：tool arguments 已经开始流式输出给客户端

流程：
1. 上游 SSE → 网关解析 → 逐帧检查
2. 检查到 tool_json_invalid → 生成 PolicyBlockError
3. executor 分类为 content_filter（kind）
4. sie.resumable = false（流已 committed）
5. 不会触发候选切换或重试
```

**executors/executor.go:3668 的判断**：
```go
if interrupted == nil || !interrupted.resumable || params == nil || params.SurvivalAttempt {
    // 已 committed 的流中断不可恢复
    return nil
}
```

**为什么不可重试**：
1. **流已开始输出**：客户端已经收到部分 chunks（rv-2089 实测 48 chunks）
2. **无法撤回**：HTTP/SSE 流式响应不支持"取消前面发的内容"
3. **状态不一致**：客户端看到的是半成品流 + 错误帧，无法原子切换到重试结果

## 方案对比

### 方案 A：在检测点之前缓冲完整 arguments（推荐）

**设计**：
```
当前：逐帧检查
上游 SSE → [帧1 检查] → [帧2 检查] → ... → [帧N 检查 ❌ 格式错误]
                ↓             ↓                    ↓
              客户端        客户端              客户端（已收到 N-1 帧）

修改后：延迟检查
上游 SSE → [缓冲区] → 完整 arguments → [检查 ❌] → 重试
                                              ↓ ✅
                                         完整输出 → 客户端
```

**实现要点**：
1. 在 `stream_compliance.go` 的 tool arguments lane 启用"延迟检查模式"
2. 缓冲所有 `tool_calls[].function.arguments` 的增量帧，直到 `done` 事件
3. 在 `done` 帧时一次性检查完整 JSON
4. 如果格式错误：
   - 标记该候选失败（kind=upstream_format_error）
   - 触发候选切换（如果有其他候选）
   - 或返回 503（而不是当前的客户端可见错误帧）

**优点**：
- ✅ 真正可重试（流未 committed）
- ✅ 客户端体验一致（要么全成功，要么全失败）
- ✅ 可以利用现有的候选切换机制
- ✅ 对网络闪动、上游格式转换错误都有效

**缺点**：
- ⚠️ 增加内存开销（需缓冲 tool arguments，但通常不大）
- ⚠️ 延迟首个 tool call 的可见性（用户体感稍慢）
- ⚠️ 需要修改流式检查器的核心逻辑

**成本估算**：
- 代码改动：~200 行（stream_compliance.go 的 tool lane 分支）
- 测试用例：~10 个（延迟检查 / 缓冲释放 / 重试触发）
- 风险：中等（触碰流式核心，需要充分测试）

### 方案 B：格式修补器（Sanitizer）

**设计**：
```go
func tryRepairToolJSON(malformed string) (repaired string, ok bool) {
    // 1. 补全截断的 JSON
    if strings.Count(malformed, "{") > strings.Count(malformed, "}") {
        repaired = malformed + strings.Repeat("}", diff)
    }
    
    // 2. 移除 GLM 原生标记（针对 rv-2089 形态）
    if strings.Contains(malformed, "</arg_key>") {
        // 提取 <arg_value>...</arg_value> 之间的内容
        repaired = extractGLMArgValue(malformed)
    }
    
    // 3. 修复常见转义问题
    repaired = fixCommonEscapes(malformed)
    
    // 4. 验证修复后的 JSON
    if json.Valid([]byte(repaired)) {
        return repaired, true
    }
    return "", false
}
```

**实现位置**：
```
security/sanitize/output_sensitive.go:209
在 json.Valid() 失败后、返回 Blocked 之前插入修补尝试
```

**优点**：
- ✅ 改动最小（局部修改，不触碰流式架构）
- ✅ 对特定已知格式错误立即生效
- ✅ 零用户感知（透明修复）

**缺点**：
- ❌ 只能修复可识别的格式错误（无法处理所有情况）
- ❌ 修补逻辑容易过时（新的上游错误形态需要持续维护）
- ❌ 不能解决网络截断（数据丢失无法恢复）
- ❌ 可能引入"修好了但语义错了"的风险

**适用场景**：
- 针对 rv-2089 这种**已知的、高频的、有规律的**上游格式转换错误
- 作为方案 A 的补充，不是替代

**成本估算**：
- 代码改动：~100 行（修补器 + 测试）
- 测试用例：~15 个（各种格式错误形态）
- 风险：低（局部修改，影响面小）

### 方案 C：客户端自动重试（当前默认）

**设计**：
```
网关返回格式错误 → 客户端识别 "格式有误，请重试" → 自动重新发起请求
```

**优点**：
- ✅ 网关零改动
- ✅ 客户端完全可控（可以实现自己的重试策略）

**缺点**：
- ❌ 浪费网关资源（整个请求重来，包括 prompt 处理）
- ❌ 用户体验差（可见的失败 + 重试延迟）
- ❌ 对长会话不友好（session 状态可能不一致）

**当前状态**：
- ZCode 等客户端**尚未实现**自动重试
- 用户需要手动点击重试

---

### 方案 D：不做自动重试，改进监控和运营

**设计**：
1. **主动监控**：每小时统计 tool_json_invalid 的分组
   - 按 provider_id 分组：识别问题上游
   - 按 credential_id 分组：识别问题凭据
   - 按 error pattern 分组：识别格式错误类型

2. **自动降级**：
   - 同一 provider 1 小时内 tool_json_invalid > 10 次 → 自动禁用
   - 管理员收到告警 + 自动工单

3. **上游反馈**：
   - 自动向上游中转（如 apiclaude.cc）报告格式错误样本
   - 推动上游修复根本问题

**优点**：
- ✅ 从根本上解决问题（而不是在网关层打补丁）
- ✅ 运营成本可控（自动化程度高）

**缺点**：
- ❌ 不能立即解决用户问题（依赖上游修复）
- ❌ 对网络闪动无效

## 技术细节

### 方案 B 实现示例

```go
// security/sanitize/output_sensitive.go

func tryRepairToolJSON(text string, toolName string) (repaired string, ok bool) {
	// 1. 识别 GLM 原生格式（rv-2089 形态）
	if strings.Contains(text, "</arg_key>") && strings.Contains(text, "<arg_value>") {
		// 提取 <arg_value>...</arg_value> 之间的内容
		start := strings.Index(text, "<arg_value>")
		end := strings.Index(text, "</arg_value>")
		if start != -1 && end > start {
			extracted := text[start+len("<arg_value>"):end]
			// 尝试解析为 JSON
			if json.Valid([]byte(extracted)) {
				return extracted, true
			}
			// 如果不是 JSON，构造一个简单的 JSON 对象
			return fmt.Sprintf(`{"value": %q}`, extracted), true
		}
	}
	
	// 2. 补全截断的 JSON
	openBraces := strings.Count(text, "{")
	closeBraces := strings.Count(text, "}")
	if openBraces > closeBraces {
		repaired = text + strings.Repeat("}", openBraces-closeBraces)
		if json.Valid([]byte(repaired)) {
			return repaired, true
		}
	}
	
	// 3. 修复未闭合的字符串
	if strings.Count(text, `"`) % 2 == 1 {
		repaired = text + `"`
		if json.Valid([]byte(repaired)) {
			return repaired, true
		}
	}
	
	return "", false
}

// 在 CheckField 中使用
if toolName, isToolJSON := parseToolJSONLabel(label); isToolJSON {
	if !json.Valid([]byte(text)) {
		// ★ 2026-11-15：尝试修补格式错误

				"tenant_id", tenant,
				"tool_name", toolName,
				"original_bytes", len(text),
				"repaired_bytes", len(repaired),
			)
			// 用修复后的文本继续检查
			text = repaired
		} else {
			// 修补失败，返回 Blocked
			return &outputcompliance.ComplianceResult{
				Blocked: true,
				Issues: []outputcompliance.ComplianceIssue{{
					// ... 现有的 tool_json_invalid 逻辑
				}},
			}, nil
		}
	}
	// 继续正常的 JSON 解析和检查...
}
```

## 风险评估

### 方案 B 风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 修补逻辑错误，改坏语义 | 高 | 低 | 充分测试 + 修补后再次验证 JSON 结构 |
| 新的格式错误形态无法识别 | 中 | 高 | 监控未修补的错误 + 持续迭代规则 |
| 修补器被绕过（边缘 case） | 低 | 中 | fail-safe 设计（修补失败仍返回原错误） |

### 方案 A 风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 内存开销过大 | 高 | 低 | 设置缓冲上限（如 256KB）+ 监控 |
| 延迟影响用户体验 | 中 | 中 | 灰度发布 + 用户反馈 |
| 流式架构改动引入 bug | 高 | 中 | 充分测试 + code review + 灰度发布 |

## 总结

**立即可做**（本周内）：
1. ✅ 已完成：格式类守卫不生成审核单 + 提示文案修正
2. 🔜 方案 B：实现 GLM 格式修补器（针对 rv-2089）
3. 🔜 方案 D：监控告警 + 自动降级

**中期规划**（1-2 月）：
4. 🔜 方案 A：延迟检查 + 自动重试（根本性解决）

**不推荐**：
- ❌ 方案 C（客户端自动重试）：浪费资源，体验差

**关键决策点**：
- 是否接受"修补可能改变语义"的风险？→ 建议：先试点 GLM 格式（模式明确），观察效果
- 是否接受"延迟检查增加内存"的成本？→ 建议：先做成本评估（统计 tool arguments 平均大小）

**预期效果**：
- 短期（方案 B）：rv-2089 类问题透明修复，用户无感知
- 中期（方案 A）：所有格式错误自动重试，成功率提升到 >95%
