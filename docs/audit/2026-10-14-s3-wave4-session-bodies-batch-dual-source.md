## 1. 对象：`admin/session_bodies_batch.go`

会话域正文批量取数，**会话导出 / 会话对比 / 会话摘要三条路径共用**的供给点，
也是这个仓库最贵的单条查询（文件头实测：171 个 request_id 要 17~19 秒，
连接池上限 16 ⇒ 16 个并发就能把池占满）。

停写后它的 v1 腿对新会话**恒 0 行**，而调用方把 map 里的缺项当成
"没有存正文" ⇒ **导出/对比/摘要会拿到"有轮次、无正文"的结构自洽结果**。

真库实测（本地，2026-10-14，停写后 100 个真实 request_id）：

| 口径 | 命中 |
|---|---:|
| v1 腿 | **0** |
| 会话族腿（含内容过滤） | **100** |
| 并集 | **100** |

## 2. 为什么是「双源」而不是切换层

切换层 `db.SessionBodiesSourceSQL()` 是**单臂开关**（开=会话族、关=v1）。
直接换掉 v1 腿会让**镜像启用之前的历史会话**变成"查得到轮次、没正文"。

而两族各自都有对方没有的 `request_id`（2026-10-12 单日：v1 有 **1,201**
个会话侧没有）。⇒ 两腿各查一次，在 Go 侧按 `request_id` 合并。

**合并规则 = 执行顺序**（后跑的覆盖先跑的）：

| 情形 | 结果 |
|---|---|
| 只有 v1 有（镜像启用前的历史） | v1 条目保留 |
| 只有会话族有（停写后的新流量） | 会话族补上 ← **本轮修复的退化** |
| 双生且两侧都有内容 | 会话族覆盖（停写后的权威源） |

反过来写（会话先、v1 后）会让 v1 的空正文盖掉会话族的真实正文，
症状是"导出成功、每条消息正文为空"。

## 3. 三处承重的细节

### 3.1 谓词形态：`IN (SELECT unnest(...))`，不是 `= ANY`

这是本文件最贵的教训（文件头有实测对照表）：
`= ANY($1::text[])` 与 `IN (SELECT unnest($1::text[]))` **返回完全相同的行**，
但在列存分区上前者让规划器放弃主键探针——**17.43s vs 2.20s**，
且 `N=1/2/4/8/16/32/64` 全部如此。

⇒ "加一条会话腿"这件事极易顺手把谓词写成 `= ANY`，而**那不会报错**，
只会把新查询变成一次全分区列存扫描。

本轮真库 EXPLAIN ANALYZE（200 个真实 request_id）：两条腿都是 Index Scan /
分区裁剪，**Execution Time 0.943 ms**。

### 3.2 会话腿必须带 jsonb-null 过滤

会话族用 jsonb `null` 表示"这一列没有正文"（第二片实测：`request_delta`
1,882 行、`outbound_body` 11,420 行，SQL NULL 各 0 行）。

不滤掉全空的会话行，它会**盖掉**双生 `request_id` 在 v1 腿里的真实正文
（双写期本地实测 **11,711** 个双生）。⇒ 只让**至少一列真有内容**的会话行进 map。

### 3.3 两条腿共用一个扫描函数

`scanSessionBodies(ctx, q, sql, ids, dst)` —— 把扫描逻辑只写一份。
分开写两段是"只改一段"的温床，而这里的失效形态恰好是**静默**的。

## 4. 明确登记「不迁」的一条：元组键变体

`sessionBodiesByRequestIDAndTSSQL` 配的是 `(request_id, ts)`，而 `ts` 是
**正文写入时间**不是轮次时间（两侧 99.85% 不等，差 8~16 秒），
所以这条查询长期近乎恒空。

文件头明确记载：两种键对应**两个端点各自的既有行为**，
"把其中一个悄悄改成另一个就是在重构里夹带行为变更"。

**本轮不改它**：停写对它没有新影响（双写期它就已经 99.85% 落空）。
钉子 `TestSessionBodiesTupleVariantStaysV1Only` 的作用是防止后人看到
"bodies 逐点评估"就顺手把它一起迁走。要迁移必须另立一轮并单独评估
两个端点的行为变化。

## 5. 判据与变异验证

判据 `admin/s3_wave4_session_bodies_batch_test.go`（3 条，同层驱动包级
`sessionBodiesByRequestIDV1SQL` / `sessionBodiesByRequestIDSessionSQL`
以及 `querySessionBodiesByRequestID` 的函数体）：

| 变异 | 结果 |
|---|---|
| M1 会话腿谓词退化成 `= ANY`（8~9 倍列存全扫，**返回行完全相同**） | ✅ 红 |
| M2 会话腿去掉 jsonb-null 过滤 | ✅ 红 |
| M3 删掉会话腿 | ✅ 红 |
| M4 合并顺序倒置 | ✅ 红 |
| M5 元组键那条被顺手迁走 | ✅ 红 |

变异 5/5 红，还原后全绿。驱动脚本显式区分
**build failed（变异无效、判据未被检验）** 与断言失败——
这是第二片踩过的坑（第一轮 M1 的变异拼出的 Go 非法，脚本却记成"变红"）。

★ M1 值得单独记：它是本族最贵的一个失效形态——**返回行完全相同、不会报错、
只在生产规模上体现为 17 秒**。本地库小（20K 行正文），实测 0.943ms 与
`= ANY` 版本的差距不显著 ⇒ **真库验证在这里证明不了它**，只有形状钉桩能拦。
