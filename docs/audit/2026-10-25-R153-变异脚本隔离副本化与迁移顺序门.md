## §2 遗留 4（＋遗留 2 的一半）：新增「切流前必须先应用 pending 迁移」门

### §2.1 缺口本体

部署链 `scripts/deploy-seamless.sh` 的 `[6.5/9]` 步做的是：

```bash
log "[6.5/9] 切换前 pending 迁移 + db-changelog"
deploy_apply_pending_migrations "$SSH_CMD" … \
  || { err "DB 迁移失败，中止（未切换符号链接）"; exit 1; }
```

⇒ **失败即 `exit 1`、不切符号链接** ⇒ **部署路径本身是安全的**。
⇒ ★ **但全仓没有任何门钉住这个顺序** ⇒ 下次有人把这一步挪到切流之后、或把 `exit 1` 改成 `|| true`，
**没有任何东西会红**。

### §2.2 五条判据

| 判据 | 内容 | 读数 |
|---|---|---|
| **J1 顺序腿** | 迁移调用必须在 Nginx 原子切流步**之前** | 迁移行 **1087** < 切流行 **1114** |
| **J2 失败阻断腿** | 迁移失败的分支必须 `exit 1`（不得吞掉） | `\|\| { …; exit 1; }` |
| **J3 安装器腿** | 891 在 installer 的 `StartupFiles` ＋ `go:embed` ＋ embeddata map 三处齐备 | 新装库拿得到 |
| **J4 升级腿** | 891 在部署链编号迁移通道 `files=()` 里 | 升级库拿得到 |
| **J5 裸重启腿** | Go ensure 链（`db/` 非测试 .go）**不**创建 891 的两条索引 ⇒ **缺口钉成显式事实** | 现状变了就红 |

★ **J5 为什么是「事实」而不是「要求」**：裸重启只跑 `db.Open` 里的 Go ensure 链，**不跑编号 SQL 迁移**
⇒ 「891 先于新二进制」在裸重启路径上**不受保护**。
⇒ ★ **这不是门能修掉的**（把编号迁移塞进 ensure 链是**产品级语义决策**，属主项）⇒ 门只做两件事：
① 把它**钉成显式事实**（哪天 ensure 链吸收了它，门会红并要求同步更新缺口登记）；
② 明确 **J3/J4 两条腿才是编号迁移的投递保证**。

### §2.3 ★★ J5 的判据演进（本轮两起量具事故之一）

第一版判据 = 「手写剥掉行/块注释 ⇒ 再搜索引名」。

★ **手写剥注释被吞了**：`db/` 下有**大量内嵌 SQL DDL**，里面就有 `/* … */`
⇒ 剥注释器把它当成块注释起点 ⇒ **整段代码被误吞**
⇒ ★★★ **注入的索引名连同它所在的行一起消失** ⇒ **J5 恒绿** ⇒ **M5 变异跑成「绿」**
⇒ ★★ **差点交出一道恒绿门**。

⇒ **正解**：用 **`go/parser` ＋ `go/ast`** 判 ⇒ **注释不是 AST 节点** ⇒ 天然排除文档提及，
也不怕字符串字面量里的 `/*`。

## §4 生产侧只读复核 B：刷新器 2× 放大**已消除**

### §4.1 穷尽式对账（互斥的正确证据口径）

| 实例 | 族 | success | skipped_follower | 周期合计 | uptime | 周期速率 | 名义 | 倍率 |
|---|---|---|---|---|---|---|---|---|
| 245 | tuning_signals_5m | 144 | 241 | **385** | 31.993 h | **12.035/h** | 12 | 1.00 |
| 245 | routing_analytics_7d | 26 | 39 | **65** | 31.993 h | **2.032/h** | 2 | 1.02 |
| 245 | session_*（三视图） | 13 | 20 | **33** | 31.993 h | **1.032/h** | 1 | 1.03 |

⇒ ⇒ **三族全部落在名义 ±3%** ⇒ **ticker 完全按名义在跑**；
且 **每个周期都被归类为「刷了」或「因别人是 leader 而跳过」**（`success + skipped_follower = 周期数`，无一遗漏）
⇒ ⇒ **集群刷新率 = 名义，不是 2×**。

⇒ 与 R76 轮（handoff §19.21.2）在**另一个窗口、另一个实例为主 follower** 的读数**同构复现**
（R76：154 = 254 周期/21.1 h = 12.01/h、245 = 256 周期/21.3 h = 12.00/h ⇒ 1.98× 放大被抑制）。

★ **本次的放大倍数是 2.67×**（385 周期 / 144 真刷），比 R76 的 1.96× 更大
⇒ 因为这 32 h 里 245 更常当 follower（241/385 = 62.6%）
⇒ ⇒ ★ **放大倍数是「谁当 leader」的函数，不是「协调有没有生效」的函数** ⇒ 引用它时要带 uptime 与角色。

### §4.2 ★★★★ 本轮发现的一处「惰性层」

| 主机 | Redis | 库 | PG |
|---|---|---|---|
| 154 | `172.16.2.210:6389` | **DB 0** | 共享 252 PG |
| 245 | `172.16.2.210:6389` | **DB 2** | 共享 252 PG |
| 211 | `nbjl-redis:6379` | DB 5 | **自己的** acc-pg17 |

⇒ ★★★ **154 与 245 的 Redis 键空间不同（DB 0 vs DB 2）** ⇒ 令牌桶键
`llmgw:distlock:{bg:tuning_view_refresh}:lock` **在两个库空间里是两个键**
⇒ ⇒ **Redis 令牌桶层在两台之间根本不构成互斥**。

⇒ 实际互斥链（`bg/tuning_view_refresher.go`）：
① Redis 令牌桶（**首选**）→ ② **PG advisory lock 逐视图无条件取**

⇒ ⇒ **今天互斥成立，但 100% 靠 ②** ⇒ **「Redis ＋ PG 双保险」是假的**。

⇒ ★ **推论一（量具）**：`gateway_mv_refresh_coordination_result_total{result="redis_leader"/"redis_follower"}`
**不度量**跨实例互斥（154/245 键空间不同；245 在**独占**的 DB 2 上仍报 `redis_follower=59`）
⇒ ⇒ **不能拿它当「谁在刷、谁在让」的互斥证据** ⇒ 互斥证据要用

⇒ ★ **推论二（配置）**：两台同库实例的 `LLM_GATEWAY_REDIS_DB` 不一致 ⇒ **属主决策项**
（统一成一个库，还是明确「本部署的互斥只靠 PG 锁」并把 Redis 层从「双保险」的叙述里去掉）。
⇒ ★ **推论三（否证）**：我一度怀疑 **211 在偷 245 的令牌**（它有独立的 PG ⇒ 偷了也只会让 252 的视图少刷）⇒
