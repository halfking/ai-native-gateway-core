> 日期：2026-11-23

> 性质：**审计轮**——对上一轮（commit `13b6800dd`）的实现做批判式复核，修正发现的问题
> 结论先行：上一轮实现有 **3 处硬伤 + 5 处次生问题**，本轮全部修正；门禁从「破」到「绿（除 3 条基线同红）」

## 一、结论 / 根因

### 1.1 上一轮实现为什么错

上一轮把「Top5 模型/用户/供应商/任务」直接塞进 Dashboard 的 `SessionStatsPanel`，数据源用
`/api/admin/session-analytics/overview`。审计发现三个**结构性**错误：

| # | 缺陷 | 根因 | 后果 |
|---|------|------|------|
| **D1** | **供应商维度算错** | 后端 `overview.top_models` 只返回 **3 条**（`GetOverview` 里 `getTopModels(…, 3)`），且 `model_usage_aggregates.model` 列是**纯模型名**（无 `provider/` 前缀）⇒ 前端 `split('/')[0]` 把模型名当供应商 | 「Top5 供应商」最多 3 行，且供应商名是错的（如显示 `claude-sonnet-4-5`） |
| **D2** | **普通用户必然 403** | `session-analytics` 全系端点有 `isAdminFromRequest` 门（限 `super_admin`/`tenant_admin`/`admin_key`），而 Dashboard 对**所有登录用户**可见 | 普通用户看到两个**空卡片** + 控制台 403 |
| **D3** | **同一区块混两种时间口径** | Dashboard 腿读 `session_summaries`（实时），session-analytics 腿读物化视图（15min 缓存） | 同一页不同卡片的数字时间戳不同，读者无从判断哪个是哪个口径 —— 直接违背用户「确认数据统计标准一致并且正确」的要求 |

次生问题（5 项）：

| # | 缺陷 | 影响 |
|---|------|------|
| S1 | 供应商 `total_cost` 恒为 `$0.0000`（`top_models` 只有 `count` 字段，代码里 `total_cost: 0` 从未赋值） | 假数据 |
| S2 | i18n 门禁破：新增 10 个键只加中英文，缺 6 语种 × 10 键 = 60 条 | `localeKeyParity` 红 |
| S3 | 路由重定向后，顶栏出现**两个**「会话分析中心」 | 正是 2026-11-20 L9 收口当初要避免的形态，反而复发 |
| S4 | `SessionAnalyticsOverviewView.vue` 成为孤儿文件（router import 已无用但仍在） | 死代码 + 无谓打包体积 |
| S5 | 「全局任务排行」**根本没有数据源**（本包只有「某 owner 的某 project 下的任务列表」） | 任务维度无解 |

### 1.2 本轮的修正路线

**把 Top5 四件套从 Dashboard 挪到 `/admin/session-analytics/users`**，理由是用户需求本身就这么写的
（「结合 /admin/session-analytics/users，需要对 top5 的模型、用户、供应商、任务等进行统计」），
而且该页本就是 admin 域 —— 权限模型与数据源天然自洽。

- Dashboard 回到**单一数据源**（自身实时腿），口径一致的证据仍在它的「对齐指标行」上
  （`aligned` 块读 `domains/analytics` 单一真源，与会话分析页同一实现）；
- 四个 Top5 维度统一落在 users 页，**全部来自 session-analytics 物化视图族**；
- 供应商与任务维度**新增后端端点**由 SQL 按真实列聚合（不再前端瞎猜）。

## 四、遗留风险

### R1（高·待并行车收口）i18n 值质量棘轮 3 条红

- **现象**：4 个语种「值仍等于 en-US 的键数」超 baseline 1 条。
- **归因**：**非本轮引入**。已用 `git stash push -u` 隔离到 origin/main 状态复跑，同样红 ⇒ 是并行会话在 origin/main 上新增的键未翻译。
- **谁能修**：该并行车（或任何跑 `--update-baseline` 的人）需先把那 1 条真正翻译，或按纪律显式抬基线并写明 `baselineRaiseReason`。
- **对本轮的影响**：不阻塞 build / 部署。

### R2（中）供应商榜的成本单位是「跨单位相加」

`total_cost = internal_cost + external_cost`（美元 + 积分）。这是**本包既有口径**
（`ModelRanking` / `UserRanking` 同样如此），UI 上以 `$` 显示会失真。
**未擅自改动** —— 改口径会影响既有排序与其它页面，属产品裁决。
若 owner 要求，需要一轮专门的「成本分列」改造。

### R3（中）Top5 四件套的请求级/会话级不可相加

模型/供应商走 `model_usage_aggregates`（**请求级**），用户/任务走 `project_task_aggregates`
/`user_session_aggregates`（**会话级**）。二者**不可相加**。
已在 UI 的 `top5.scopeNote` 文案里显式披露（8 语种）。

### R4（低）任务维度的跳转落点

仓内**没有**独立的任务详情路由 ⇒ 任务行跳回 `/admin/session-analytics/users` 并带 `task` 定位参数。
后续可补 `/admin/session-analytics/tasks/:task` 详情页。

### R5（低）Top5 榜单与全量排行的口径差

Top5 取的是物化视图聚合的前 5 行，与 `/admin/session-analytics/model-ranking`（全量排序表）
同源同窗口 ⇒ 数字自洽；但 Top5 的排序字段固定（模型按请求数、供应商按请求数、用户按 Token、任务按会话数），
与全量排行页可切换的排序字段不同。

### R6（低）共享工作区的并行改动

`admin/handler.go` 与 `admin/team_handlers.go` 是并行会话的**在途**改动（W2-Q2 团队预算），
当前**编译不过**（缺 `database/sql` import）。
本轮**未触碰**这两个文件，验证一律走隔离 worktree。owner 需提醒该会话收口。

## 五、通用式（本轮沉淀）

1. **「Top N 榜单」不是「把已有列表截前 N」** —— 上游端点只给 3 条时，前端聚合出的
   「Top5」既不是 Top5，数据也可能来自错误的列。维度榜必须由**该维度自己的列**聚合。
2. **权限门是端点的属性，不是页面的属性** —— 一个 admin-only 端点挂到全员可见的页面上，
   普通用户必然拿到空数据 + 403 噪音。跨页复用 API 前先对两边的权限模型。
3. **同一区块不要混两种缓存语义** —— 实时腿与 15min 缓存腿并排展示，读者无法判断数字新旧。
   要么统一数据源，要么在 UI 上显式标注每个卡片的来源与新鲜度。
4. **补 i18n 键会激活此前「查不到就不查」的门禁** —— 键从「全语种缺失」变成「存在」时，
   占位符/死参数类门禁才会开始检查它 ⇒ 补键前要先看该键的调用点。
5. **`default` 在 vue-i18n v9 是保留键** —— 当插值参数传进去既不显示、又会被门禁判死参数。
6. **改菜单要连带记账** —— navCounts 的 ITEMS/PATHS/FOLDED/groupItems 四档 + 三份方案文档的数字，
   是「菜单真源 ↔ 文档」的闭环；删一项要四处同步。
7. **门禁红了先分清「谁引入的」** —— `git stash push -u` 隔离到基线复跑，是区分
   「本轮引入」与「基线同红」最快的判据（本次据此确认 3 条红非本轮引入）。
8. **共享工作区上并行会话的在途改动会挡住编译** —— 验证走隔离 worktree
   （`git worktree add --detach /tmp/x HEAD`），既不碰别人的在途状态，也能拿到
   「提交树的真实样子」。

## 1. 棘轮归因：差集取证推翻了「基线同红」的笼统说法

### 1.1 现象

`localeValueQuality` 报 5 项 OVER LIMIT：

```
untranslated de-DE : 1108 (limit 1107)      same-as-source zh-TW : 760 (limit 758)
untranslated es-ES : 1017 (limit 1016)
untranslated ja-JP :  698 (limit  697)
untranslated zh-TW :  665 (limit  664)
```

### 1.2 判定方法（不是印象，是差集）

在**三棵树**上跑同一个量具（探针脚本按 `localeValueQuality.ts` 的同源口径，输出**逐条键名**）：

| 树 | de-DE | es-ES | ja-JP | zh-TW | zh-TW sameAsSource |
|----|-------|-------|-------|-------|--------------------|
| `ebe22a9d9`（棘轮基线最后一次写入） | 1107 | 1016 | 697 | 664 | 758 |
| `614b72e9c^`（本审计轮**之前**） | **1108** | **1017** | **698** | **665** | 758 |
| `614b72e9c`（本审计轮**之后**） | **1108** | **1017** | **698** | **665** | **760** |

⇒ **差集一**：4 个语种的 `untranslated +1` 在本审计轮**之前就已经存在**（两树数字逐条相同）⇒ **非本轮引入**。
⇒ **差集二**：`sameAsSource.zh-TW +2` **是本审计轮引入的**。

### 1.3 两个真因（逐键定位，非估计）

| 指标 | 键 | 引入者 | 说明 |
|------|----|--------|------|
| `untranslated +1`（6 语种同因） | `sessionAnalytics.state.loadingStats` | `ba7b54c4a`（feat(ui): 会话分析页面加载状态优化） | 该键以**英文原文** `Loading statistics…` 写进 6 个非英语语种；后来进入源码引用集 ⇒ 被「与 en-US 逐字相同 = 没翻」计入 |
| `sameAsSource.zh-TW +2` | `sessionAnalytics.top5.models`、`sessionAnalytics.action.viewAllModels` | **本审计轮（614b72e9c）** | zh-TW 取值「Top5 模型」「查看所有模型」与 zh-CN **逐字相同**（繁简里本就同形）⇒ 被「还留着原文」计入 |

### 1.4 ★ 归因更正（推翻并行车 AGENTS.md 的说法）

并行会话在 AGENTS.md 的登记里写：**「归因兄弟会话 `614b72e9c`（session-analytics 审计轮改了 4 语种 locales，每个语种 +1 未翻译键）」**。

**实测不成立**：证据是「隔离 worktree at HEAD 同样 4 条红」——那只证明**HEAD 是红的**，不证明**是本轮弄红的**。
按上表差集，`+1` 在本轮**之前**就红（`614b72e9c^` 同样是 1108/1017/698/665）⇒ 归因对象错了。
本轮真正引入的是**另一个指标**（`sameAsSource.zh-TW +2`），且**已被本补充轮修掉**。

### 1.5 修法（真译 + 台湾本地化，**不抬基线**）

棘轮纪律是「只许降不许升；抬基线必须人工显式改 JSON 并写 `baselineRaiseReason`」。本轮**没有抬任何基线**：

1. 6 语种 `loadingStats` 补真译：
   `de-DE`/`es-ES`/`fr-FR`/`ar-SA`/`ja-JP`/`zh-TW` 各写该语种自己的说法；
2. zh-TW 本地化：`top5.*` 统一「Top 5」排版（与 en-US 一致）、`viewAllModels` 改台湾用语「檢視所有模型」
   （仓内 `zh-TW` 已有 10+ 文件用「檢視」，与同文件 `action.viewDetail` 一致）。

## 5. 本补充轮新增的通用式

1. **「HEAD 同红」不等于「你引入的」——归因要用差集，不用印象。**
   在「变更前」与「变更后」两棵树上跑**同一个量具**并**逐条比对键名**，
   才能分清「基线同红」与「本轮引入」；本次被指认的那项恰恰**不是**真正引入的那项。
2. **「统计口径正确」要对着库直查复刻同一段 SQL，而不是只看接口 200。**
   接口 200 只证明「通」，不证明「数得对」。
3. **数字对不上时，先分清「口径差」还是「数据源差」。**
   不先查 DB 指向就改 SQL，等于对着错库调口径。
4. **棘轮红了先问「能不能不抬基线就修掉」** —— 真译通常能做到；抬基线是最后手段，不是首选。
