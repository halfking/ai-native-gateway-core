# 2026-10-23 211 整机失联 —— 取证与恢复手册

> **对生产的写入**：本手册只取证与备料；**未对 245 / 211 / 任何生产路由做变更**（属主选择「先不切兜底」）。

## 0. 一句话结论

**部署是成功的；随后 211 这台主机在 2026-10-23 02:12–02:16 之间整机失联**，
导致 `llm.itestu.cn` 的 origin 不可达 ⇒ 公网持续 502 ⇒ 用户看到的「登录失败」。
**登录链路本身没有缺陷**（同一凭据在 245 的库上实测登录成功）。

## 1. 现象

- 用户报障：「部署结果是失败的，请检查并修正，无法登录后访问，登录失败，用户是 admin/…」。
- 实测（05:36 起）：`GET /`、`/healthz`、`/readyz`、`/version`、`POST /api/auth/token`
  **全部 502** ⇒ 不是认证问题，是 **origin 不可达**。
- ★ **量具陷阱（必须记）**：本机 HTTP 代理（`127.0.0.1:7897`）会把「origin 不可达」显示成
  **502**（0.06s 返回，代理自己的错误页）；`curl --noproxy '*'` 直连得到的是
  **000 / 20s 超时**。⇒ 判「服务端 502」之前必须先做直连对照。

## 4. 「登录失败」不是认证缺陷（对照实验）

在 245 的本机网关（`127.0.0.1:8782`，版本 `2.5.8-bd0a27f7-20261022-2815`）上实测：

- `GET /` ⇒ 200 `text/html`（3086 B SPA）；
- `POST /api/auth/token`（同一套 admin 凭据）⇒ **200**，`user.id=41 / tenant=default /
  role=super_admin / enabled=true / must_change_password=false`；
- 带 token `GET /api/auth/me` ⇒ 200；**不带 token ⇒ 401**（负控）;
- 在**公开链路**上同款复核：`https://llmgo.kxpms.cn`（245 已在线的同款 upstream 腿）
  ⇒ SPA 200 / 登录 200 super_admin / 鉴权后 200 / 未鉴权 401。

⇒ **凭据、用户表、bcrypt 密码、签发链路在 245 上全部正常** ⇒ 211 上的「登录失败」
是 502 的表象，不是认证缺陷。⇒ ★ **通用式：★ 「登录失败」先看 `/version` 与 `/healthz`
的 HTTP 码**——它们和登录走同一条 origin，一样 502 ⇒ 说明问题在可达性，不在登录。

## 5. 与本次部署的因果关系：**目前无证据**

- 部署在 01:12 完成并复验通过，02:11:41 之前线上一直 200 ⇒ 部署**没有**立即破坏它。
- 引擎内**没有**任何「定时自毁」类动作（无 `crontab` / `at` / `systemd-run` / `nohup` /
  延迟 `sleep` 后再 `docker rm`）；所有破坏性动作都在部署流程内同步发生。
- 部署确实**停了旧槽 a**（保留容器可 `docker start` 回滚）⇒ 若 211 之后重启，
  容器**不会**自动拉起（`docker run` 不是 `--restart=always` 语义）⇒ 必须重部署。

  仓库内**无** 211 的 IPMI/PDU/BMC/带外管理记录；本机 ARP 也拿不到它的 MAC。

## 6. 恢复路径 A —— 现场/带外（唯一可靠，**优先**）

1. 现场给 211 **断电重启**（或经 PDU/BMC 上电）——**这是最省事也最可靠的一条**。
2. 211 起来后，**先别急着切公网**：
   ```bash
   # ① 确认宿主活着、容器在不在
   ssh 211 'hostname; uptime; docker ps -a --format "{{.Names}} {{.Status}}" | grep llm-gateway-211'
   # ② 确认 mesh 腿回来了（netbird peer 状态应为 Connected）
   ssh 252 'podman exec nb-252-host netbird status -d | sed -n "/docker.netbird/,/^$/p"'
   ```
3. 重部署（走仓内标准入口，本轮已验证端到端 rc=0）：
   ```bash
   cd <repo> && bash scripts/deploy-211.sh
   ```
4. 复验：`/version` 的 `git_sha` 与本地 HEAD 一致、`/` 200 `text/html`、`/api/auth/token` 200。
5. 切回公网上游（若此前切过兜底）：
   ```bash
   ssh 245 'sudo bash /tmp/llm-itestu-upstream-fallback.sh --rollback'
   ```

## 7. 恢复路径 B —— 临时兜底切 245（**已备料，属主未授权 ⇒ 未执行**）

  本机 `--resolve` 验收 → **失败自动回滚**）。

## 9. 附：本轮同时修掉的另一个缺陷（与本次失联无关）

**`/maintain-api/*` 被全局 API-key 门抢先拦成 401，遮蔽了设计的 503 信封。**

- 现象：访客未登录时前端探 `/maintain-api/healthz` / `/maintain-api/menu/ops`
  （`web/src/config/edition.ts` 的 `probeMaintainAvailable`）⇒ 拿到
  `401 {"error":{"code":"missing_key"}}`（**网关自己的 API-key 门**拦的），
  而不是 `cmd/gateway/maintain_proxy.go` 设计的 `503 + maintain.not_configured`
  ⇒ 前端**分不清「运维平台没配」与「真维护态」** ⇒ 首页常驻一条黄色告警
  「运维平台暂时不可用，已保留在网关登录页。」
- 根因：`AuthMiddleware`（`middleware/auth_mw.go`）排在 mux 路由**之前**
  （`cmd/gateway/main.go` 的 `middleware.NewBuilder()` 链内，链尾 `Then(publicSurface)`，
  而 `publicSurface` 里才挂 `newMaintainGatewayHandler`）⇒ **任何没进 bypass 名单的前缀，
  匿名请求在到达 maintain 挂载之前就被拒**。名单里有 `/m`、`/maintain`，
  **唯独漏了 `/maintain-api`**。
  ★ 关键歧义：名单里的前缀 `"/maintain/"` **不匹配** `"/maintain-api/..."`
  （`"-"` 不是 `"/"`）⇒ 两条都得显式登记。
- 修法：`middleware/auth_mw.go` 的 bypass 名单补 `"/maintain-api"`（exact）
  与 `"/maintain-api/"`（prefix）。
- ★ **为什么这不是「开洞」而是「补对称」**：同一批 maintain 端点的**旧兼容前缀**
  （`/api/downloads`、`/api/admin/licenses`、`/api/system/upgrade`…，见
  `maintain_proxy.go` 的 `maintainCompatPrefixes`）**本来就在**全局门的
  `"/api/"` 前缀豁免里 ⇒ 匿名请求早就能到达 maintain 后端；
  而 canonical 前缀 `/maintain-api` 却被门先拦 ⇒ **同一个后端，两条路待遇不同**，
  且被拦的那条正是前端探针用的那条。本次修复只把两边拉齐，
  端点级鉴权仍由 maintain 后端自守卫（代理会剥掉客户端 `X-Tenant-ID`，
  租户范围只来自已认证会话；未配置 `MAINTAIN_SERVICE_URL` 时命中 503 兜底，**不泄露数据**）。
- 门：`cmd/gateway/maintain_api_bypass_contract_test.go`（行为腿：匿名 ⇒ 503
  `maintain.not_configured` 且**不是** 401；反向腿：数据面 `/v1/*`、`/v1beta/*`
  仍 401）+ `middleware/maintain_api_bypass_test.go`（静态腿：名单两条都在；
  不得写成越界宽前缀）+ 变异台
  `scripts/audit/mutate_maintain_api_bypass_gate.py`（M1/M2 摘名单 ⇒ 必须变红；
  M3 少尾斜杠 ⇒ 行为腿仍绿而静态腿必须红；M4 无语义改动 ⇒ 仍绿）。
