## 三、差异根因分析（逐项核实）

### 3.1 请求数差异：74.8K vs 144,958（相差93%）

**初步判断**（❌ 错误）：
> 供应商对账包含68,033个"未落定"请求（未完成的流），看板不统计

**核实结果**（✅ 正确）：
1. **真因 = 探测口径不同**
   - 看板默认：`traffic_class='business'`（排除探测）
   - 供应商对账：全量（含探测）

2. **探测流量占比估算**:
   ```

   看板默认（业务）: 74,800 请求
   探测流量 ≈ 70,158 请求（48.4%）
   ```

3. **"未落定"请求的真实含义**:
   - 不是"未完成"，而是**已终态的失败请求**
   - `provider_id=NULL`（未路由到具体供应商就失败了）
   - 前端代码: `components/reconciliation/ReconciliationToolbar.vue:54-61`
   - API 类型: `api/reportrollup.ts:34-35` (`UNASSIGNED_ID = -1`)

4. **代码证据**:

### 3.2 费用差异：$8,632 vs $6,306（相差37%）

**初步判断**（❌ 部分错误）：
> 成本计算口径不同（总成本 vs 供应商成本）

**核实结果**（✅ 正确）：
1. **真因 = 探测流量的成本分布**
   - 看板默认统计的是**业务流量**，这部分请求成功率较高，产生较多费用
   - 供应商对账统计的是**全量**，包含大量探测流量
   - 探测流量中有大量失败请求（68,033个未落定 + 7,260个其他失败），这些**不产生供应商成本**

2. **费用分布分析**:
   ```
   供应商对账全量: 144,958 请求 / $6,306.16
     - 成功: 69,665 请求 / $6,306.16（所有成本来自成功请求）
     - 失败: 75,293 请求 / $0.00（失败不烧钱）
   
   看板默认（业务）: 74,800 请求 / $8,632.30
     - 业务流量成功率更高，单请求成本更高
   ```

3. **单请求平均成本**:
   ```
   供应商对账（全量成功请求）: $6,306 / 69,665 = $0.0905/请求
   看板默认（业务流量）: $8,632 / 74,800 ≈ $0.115/请求
   ```
   
   **结论**: 业务流量单请求成本更高（模型质量更好、token 更多）

## 七、初步分析的错误点（总结）

### 7.1 错误① ："未落定"是"未完成的流"

**初步判断**（❌）:
> 供应商对账中的"未落定"分类（68,033请求）的真实含义需进一步核实

**暗示**: "未落定"可能是未完成的请求，导致数据不一致

**真相**（✅）:
- "未落定"是**已终态的失败请求**（`provider_id=NULL`）
- 这些请求在 `usage_facts` 中已经是终态行（`status='failure'`）
- 前端映射为 `-1` 只是为了显示和筛选
- **不影响数据一致性**，只是失败请求的一个子分类

### 7.2 错误② ：统计实体不同

**初步判断**（❌）:
> 统计实体不同（看板统计终态请求，供应商对账可能包含所有请求状态）

**暗示**: 供应商对账可能包含"进行中"的请求，导致数据膨胀

**真相**（✅）:
- **两者都只统计终态请求**
- `usage_facts` 表只含终态行（`success/failure/rate_limited`）
- `report_snapshots` 是 `usage_facts` 的每日聚合
- **实体完全相同**，差异只在于**探测口径**

### 7.3 错误③ ：费用差异来自"总成本 vs 供应商成本"

**初步判断**（❌）:
> 费用差异可能来自成本计算口径不同（总成本 vs 供应商成本）

**暗示**: 看板和对账使用不同的成本字段

**真相**（✅）:
- **两者都使用 `cost_amount`（供应商成本）**
- 看板: `SUM(cost_amount) FROM usage_facts`
- 对账: `SUM(cost_amount) FROM usage_facts` 的每日聚合
- 费用差异的真因是**探测流量的失败率高**（75,293/144,958 = 51.9% 失败，$0 成本）
