## 2. 先量：仓内有多少「自建资源」的脚本？

量具：`scripts/audit/measure-selfcreated-cleanup.sh`（★ 本轮新写）。

**第一版读数 = 29 个候选 / 17 个「危险」⇒ 这个读数是假的。**

逐条读源码后发现 **7 类假阳性**：

| # | 假阳性类 | 实测例子 |
|---|---|---|
| ① | 匹配只在**注释**里 | `destructive_target_guard_test.go:23/69/477`（全是注释） |
| ② | 匹配在**正则字面量**里 | `datasource_env_target_guard_test.go:77` `regexp.MustCompile("(?i)CREATE\s+DATABASE")` |
| ③ | **量具脚本自匹配** | 量具自己的 grep 模式串里就含 `CREATE DATABASE` |
| ④ | 建的是**长驻库** | `deploy-local.sh` / `user/client-deploy.sh` / `sync-gateway-db-to-211.sh` |
| ⑤ | **测试夹具**里的字面量 | `datasource_env_target_guard_test.go:325`（夹具里伪造的源码片段） |
| ⑥ | **日志字符串** | `user/client-deploy.sh:724` `log "DRY_RUN=1 — skip CREATE DATABASE"` |
| ⑦ | 只**拼 query 字符串**给调用者 | `pg-instance-connections.sh:164`（它根本不执行建库） |

⇒ ⇒ ★★★ **这是 R63 轮那条纪律的再次印证**：「按名命中」几乎总是假阳性；「按名零命中」才是可信证据。
⇒ ⇒ ★★ **静态判据的假阳性类是无界的** ⇒ ⇒ **静态判据只能给「候选集」，不能给「泄漏清单」** ⇒ 结论必须**逐条读源码人工裁决**。

## 3. ★★★ 量具自己出过的 5 个 bug（每个都改变了读数）

| # | 量具 bug | 症状 | 修法 |
|---|---|---|---|
| ① | **注释未剥** | 候选集含注释里的匹配 | 按扩展名分派剥注释（`//` / `#` / `--` + `/* */`） |
| ② | **执行上下文过滤太紧** | ★ **漏放 5 个真创建者**（多行 `psql -c` 的 psql 在上一行；Python 的多行 SQL 字符串里 psql 在 30 行外，且**字符串里含空行** ⇒ 连「块级窗口」也切不对） | ⇒ **降级为显示列，不做过滤**（★ 漏放比误报危险） |
| ③ | **C4 只认 `exit`/`return` 字面量** | 漏判 `die`（包装函数）、漏判 Python 的 `sys.exit`、把 Python **函数体内**的 `return` 当成退出 | 语言感知：`die`/`abort`/`quit`/`sys.exit`/`raise SystemExit`；Python 只认**零缩进**的 `return` |
| ④ | **C2 只认 `trap`** | ★ **漏掉 Python 的 `atexit` 与 Go 的 `defer`** ⇒ 明明有兜底的脚本被判成「危险」 | C2 语言感知：`shell⇒trap` / `python⇒atexit\|try-finally` / `go⇒defer` |
| ⑤ | **首次 DROP 取错** | 取到**建库之前**那个（自愈用的 DROP）⇒ C4 的窗口恒空 ⇒ 漏判 | 分别取「建库前」（⇒ C6 自愈）与「建库后」（⇒ C4 窗口） |

★ ⇒ ⇒ **C5（是不是一次性库）必须三态**：`1 是 / 0 否 / ? 未知`。
★ **「未知」不许当成「否」** —— 解析不出库名时（库名是变量、在别处赋值）必须进人工裁决。
★ 第一版 C5 只看建库行 ±3 行 ⇒ **漏放**了 `DB="${DB_NAME:-itgate_r59_shape}"` 这种形态 ⇒ 修法：**回溯变量赋值**。

⚠ **另有一处自伤**：删函数时把 `throwaway_verdict` / `has_exec_ctx` 一起删掉 ⇒ 它们的输出是空串 ⇒ 而 `"" != "0"` 为真 ⇒ **所有文件都被判成「危险」** ⇒ ★ **空值参与比较是静默的**。

## 4. ★★★ 真缺陷：**5 处**真泄漏（全修，含 A/B 实测）

判据：**自建一次性库 + 回收块挂在尾部 + 存在提前退出路径** ⇒ 提前退出 ⇒ 库留在容器里（每个 ~1 GB）。

| # | 文件 | 提前退出路径 | 修法 | A/B 实测 |
|---|---|---|---|---|
| ① | `scripts/audit/probe-onetime-db-shape.sh` | 建库后 **3 条 `exit 2`**（建库失败 / prereqs 失败 / 基线失败） | `trap cleanup_db EXIT` | ★ **修前残留 1 ⇒ 修后残留 0**（同库名、同失败路径，独立副本实测） |
| ② | `scripts/_lib/db-init-lib.sh`（**库文件**） | 建库后 **4 条**（`return 1` / `exit 1` / `exit 2` / `exit 3`） | `trap` + **保存并恢复调用方的 EXIT trap**（本文件是被 source 的库） | 代码审读 + trap 语义 |
| ③ | `scripts/audit/verify_columnar_bulk_write_local.py` | `setup()` / `rebuild_source()` 的 `sys.exit(2)` | `atexit.register` | 覆盖 sys.exit / 异常 / 正常返回 |
| ④ | `scripts/audit/verify_archive_orphan_local.py` | `main()` 的 `return 2` ⇒ 经 `sys.exit(main())` 变成脚本退出 | `atexit.register` | 同上 |
| ⑤ | `scripts/audit/measure-factsource-cost-matrix.sh` | `mk_db()` 的量具自检失败 `return 1` ⇒ 调用方 `continue`（**不退出**）⇒ 已建好的库留下 | `trap cleanup_dbs EXIT` | 同上 |

★ ① 的额外要点：**`DB_NAME` 是每会话独立的名字** ⇒ 脚本开头的「先 DROP 再 CREATE」只能自愈**同名**的库 ⇒ 别的会话的残留救不了。

★★ **一个跨语言的共同形态**：
> **shell 的 `trap` ≈ Python 的 `atexit`/`try-finally` ≈ Go 的 `defer`**
> ⇒ 判据 C2 必须**语言感知**，否则会把已有兜底的脚本误判成「危险」。

★★ **一个更彻底的形态**（`run-session-storage-stream.sh`）：库建在**一次性 docker 容器**里 ⇒ 回收 = `docker rm -fv` 整个容器 ⇒ 比「逐库 DROP」更原子，且天然覆盖所有退出路径。

## 8. 诚实边界

1. ★ **「5 处真泄漏」是逐条读源码 + 对 ① 做 A/B 实测得出的**；②③④⑤ 只做了**代码审读 + 机制等价性**论证，**没有**逐个跑出「修前漏 / 修后不漏」的实测（它们的失败路径需要更长的时间窗才能复现）。
2. ★ **`SIGKILL` 不可捕获** ⇒ 被 OOM / 运行器强杀时**任何** trap / atexit / defer 都不跑 ⇒ 仍会留库 ⇒ 只能靠「资源名带 PID ⇒ 按「进程已死」判定归属再清理」兜底。
3. ★ **`atexit` 不覆盖 `os._exit`**；**`defer` 覆盖 panic 但不覆盖 `os.Exit`**。
4. ★ **量具的候选集（26）不是泄漏清单**；结论一律看台账。**静态判据的假阳性类无界**（本轮已见 7 类，还可能有第 8 类）。
5. ★ 本轮**对生产的写入 = 0**；所有建库只落在一次性库与一次性容器上；容器里**其他会话的 17 个 `itgate_*` 一律未动**。
