## §2 最值钱的发现：「dedup 只认 success」=「失败没有记忆」（§1 的成本根因）

- scheduled 763 failed / 24h：`DiscoverPerNodeTargets` 的 min-interval 去重条件是
  `r.status = 'success'` ⇒ **失败节点每个 scheduled 周期都重新入列全量重烧 50 题**
  （单模型最多 92 次/24h：deepseek-v4-pro 92、kimi-k3 72、deepseek-v4.1-flash 72）。
- 每跑 50 题都是真实 token（失败也付 prompt tokens）⇒ 重试风暴是成本大头。
- **根修**：新增 spec `model_quality.per_node_failed_interval_hours`（默认 4h），
  failed/partial 在冷却窗内也跳过。失败窗独立且更短（4h vs 成功窗 24h）——
  失败可能是瞬时的，窗太长会让上游恢复后迟迟不被重测。
- 装配：`DiscoverPerNodeTargets(ctx, scope, minInterval, failedInterval)` 签名扩展；
  SQL 侧两个独立 NOT EXISTS（语义天然并集：success 在窗内**或** failed 在窗内 ⇒ 跳过，
  比取「更近的一扇」更保守）；worker 默认 4h；main.go 读 spec 装配；
  钉住测试 `TestPerNodeTargetsScopedAndDeduped` 同步收编。
- ★ 通用式：**门/冷却/缓存的条件里凡是排除某个状态，都要问「被排除的状态下一步会走到哪」**。

## §3 score.Error 空（goal ② / 第 7 轮遗留①）

- 链路：`TestResult.Error` 在 executor/invoker 有值，但 `CalculateScore` 从不填
  `score.Error` ⇒ DBStorage 落 `model_iq_runs.error` 恒空 ⇒ 排障要翻 report 文件。
- 修：`deriveStableErrorCategory(report.Results)`（benchmark.go）：
  - 只认**已固定的错误前缀形态**（invoker.go 的五种 + upstream HTTP 状态码 + timeout）；
  - timeout（context deadline/canceled）**优先于** http_request_failed 前缀
    （第一版被契约测试抓到：`http request failed: context deadline exceeded` 落了
    http_request_failed，丢了「超时」这个更有用的语义）；
  - 取众数、并列取字典序 ⇒ 确定性；
  - **绝不回显原始错误串**（可能带 URL/响应体；契约测试断言分类里不含 `{`）；
  - success / 全空 ⇒ 不编造（返回 ""）。
- 契约测试 5 例：failed 众数 / partial 众数 / timeout 归类 / success 恒空 / 无证据不编造。
