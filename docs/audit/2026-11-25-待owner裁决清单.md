### 甲-1 ★ 服务端：登录失败计数要不要加 TTL / 加管理端点重置？★

**事实（逐行可查，本轮已钉死）**

| 环节 | 位置 | 事实 |
|---|---|---|
| 计数形态 | `admin/auth_captcha.go:217` | `loginFailuresGlobal = newLoginFailureCounter()` —— **纯内存、无 TTL** |
| 阈值 | `admin/auth_captcha.go:74` | `CaptchaFailureThreshold = 3` |
| 判定 | `admin/auth_captcha.go:202` | `required(key) = consecutive(key) >= 阈值` |
| 闸门位置 | `admin/auth.go:229` | `if !h.verifyLoginCaptcha(...) { return }` —— 上方注释明写「刻意放在任何 DB 查询与 bcrypt 之前」 |
| 清零条件 | `admin/auth_captcha.go:509` | `clearLoginFailures` **只在成功登录时**被调用（`admin/auth.go` 四条成功路径） |

⇒ **闸门在密码校验之前** ⇒ `captcha_required` 时走不到密码校验 ⇒ **成功不可达** ⇒ 计数永不清
⇒ 某个 IP 一旦连错 3 次，**连正确口令都过不去**，直到网关进程重启（仓内**无任何管理端点能重置**）。

**实测证据（2026-11-25，隔离桶，未污染真实桶）**

- 隔离桶（`X-Forwarded-For: 10.99.99.99`）连错 3 次 ⇒ 第 4 次用**正确口令**仍回
  `HTTP 400 {"code":"captcha_required"}` ⇒ **死锁成立**。
- 同一隔离桶：`GET /api/auth/captcha` ⇒ `required=true`；不带 XFF 的真实桶 ⇒ `required=false`
  ⇒ **真实用户桶没被污染**（分桶依据 `admin/auth.go:639` 取 `X-Forwarded-For` 首段）。
- 同一隔离桶带**预置 cookie** ⇒ `GET /api/auth/me` ⇒ **200** ⇒ **会话路径不受闸门约束**。

**我方建议：建议加 TTL（最小改动、零新端点）**
- 形态：失败计数带 `expires_at`（例如 10–15 分钟），过期即失效 ⇒ 闸门**会自愈**。
- 代价：一次 `admin/auth_captcha.go` 改动 ＋ 一次部署；**不改任何对外契约**。
- 替代方案：加一个 `POST /api/admin/auth/captcha/reset`（超管、仅本机/内网）—— 功能更强、
  但**新增对外端点** ⇒ 安全面更大 ⇒ 我方**不主动建议**。
- **本轮我方未改服务端语义**（改动属超范围且需 owner 决策）—— 自动化侧已用「预置会话」绕开，
  但**人工在浏览器里登录**的问题依然存在（这正是要 owner 拍板的原因）。

**不做会怎样**：任何一次误连错（3 次）就会把该来源 IP 锁到进程重启为止；运维/值班同学
在自己浏览器里会看到「要验证码」，且**重试无用**。
