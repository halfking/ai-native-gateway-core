## 一、同类问题收口：失败终帧下的截断误判（上轮 L1）

### 1.1 缺陷形态

上轮（`2026-11-20-断流截断工具参数误判tool_json_invalid-主档.md`）修了「无终帧 flush（断流）⇒ 截断参数被当完整参数判 `tool_json_invalid`」并登记 L1：**Responses 协议的失败终帧（`response.failed` / `response.incomplete`）按旧判据属「终帧」⇒ `terminalSeen=true` ⇒ 截断豁免不生效**。失败终帧＝响应没写完（失败/超预算截断），与断流同语义——判 `tool_json_invalid` 同样会把真实的失败原因（终帧本身携带的 failure 信息）顶成「output_policy_blocked 请报告网关管理员」。

### 1.2 修法（stream_compliance.go）

- `isStreamTerminalFrame` 重构为 `streamTerminalKind`：返回 `"done"`（`[DONE]`/`message_stop`/`response.completed`＝正常收尾）/ `"failed"`（`response.failed`/`response.incomplete`＝失败终帧）/ `""`（非终帧）。布尔契约由包装函数保持（既有调用方零改动）。
- 终帧分支置位改为 `state.terminalSeen = kind != "failed"`——失败终帧刻意**不**算正常收尾 ⇒ 走截断豁免；豁免释放后失败终帧照常转发（客户端看到真实失败原因）。

### 1.3 验证

- 钉测 +2：`TestFailedTerminalTruncatedToolLaneReleasesNotBlocks`（response.failed/response.incomplete 两子用例：截断 lane 释放 + 失败终帧转发）＋ `TestResponsesCompletedMalformedToolJSONStillBlocks`（response.completed 正常收尾 + 非法参数照拦）⇒ 全族 6 用例绿。
- 变异 M4（失败终帧误置位 terminalSeen）⇒ 新钉测红 → 还原绿。
- `go test ./domains/streaming/`（全量）✅。

## 二、PI 智能体接入：输出守卫格式类拦截 → 动态分析 + 继续建议/操作

### 2.1 现状与缺口（探索轮结论）

- PI 队列（`error_analysis_queue`）的**生产者原本只有 PI 检测器自身的 6 个失败分支**（detector.go），无任何「其它子系统错误入队」先例。
- 输出合规拦截与 PI 队列**零交集**；其中**格式类守卫（tool_json_invalid / redact_invalid / frame_encode_failed）连持久化记录都没有**（2026-11-15 起不生成审核单，只剩一条 WARN 日志）⇒ 事故复盘只能 grep docker logs——上轮 211 取证正是这么做的。
- 既有分析轨道：内容类命中走「审核单 + 影子判官（r1047）」；格式类守卫**两条轨道都不在**。

### 2.2 设计（挂在统一出口，仿影子判官装配）

```
拦截现场（8 个协议路径的 registerPolicyBlockReview 统一出口）
  └─ maybeEnqueueOutputGuardPIAnalysis(in)      ← 仅格式类守卫触发
       └─ outputGuardPISink（streaming 包级变量，cmd/gateway 装配）
            └─ piCollector.CollectAsync(CollectedError{
                  ErrorType: "output_guard_blocked", Priority: 5,
                  InputText: Evidence(有界摘录), ErrorMessage: Reason,
                  ErrorDetails: {rule, field, digest, client_type, degraded} })
                 └─ 既有管线：内存 chan(256) → 落库(深度闸 1000 + 24h error_hash 去重)
                    → worker 5min 轮 → LLM 分析(专用模板) → error_analysis_results
                    → /admin/pi-analysis 详情页展示
```

关键决策与边界：

| 决策 | 理由 |
| --- | --- |
| **只入队格式类守卫**（`errorsx.IsFormatGuardRule`） | 内容类命中已有审核单 + 影子判官两条 LLM 轨道，再入队＝同一事件双份分析；格式类才是「零分析」的洞 |
| **挂在 `registerPolicyBlockReview` 顶部** | 8 个协议路径（流式/非流式 × chat/anthropic/responses）的唯一收口，一处挂全链覆盖 |
| **sink 是 func 类型 + `SetOutputGuardPISink` 装配** | `SetShadowJudge` 同款形态；streaming 不 import promptinjection，依赖方向保持「装配层指向两个域」 |
| **专用模板 `getOutputGuardBlockedTemplate`** | 归因四分类（upstream_interrupted / upstream_format_defect / gateway_guard_misjudge / redaction_side_effect）+ `suggested_fix` 分受众（客户端侧「可重试/换模型」+ 运维侧「查 request_id 日志/换中转/报告网关管理员」）；模板明令 `rule_adjustment` 必须为 null |
| **apply 恒 view-only（类型闸）** | 动作白名单（disable_rule/adjust_severity/update_pattern）指向 `prompt_injection_rules` 表，与输出守卫规则（errorsx 合成规则名）是**两张表**——即便 LLM 幻觉出合法动作 + 置信度达标，`ApplyFix` 查 `error_type=output_guard_blocked` ⇒ 422 view-only。建议是「继续的操作指引」，不是可执行的规则变更 |
| **collector 自带开关/深度闸/去重** | 不做二次开关（PI 总开关默认关 ⇒ 未开启的环境零行为变化）；同型拦截风暴被 24h error_hash 去重收敛 |
| **stats 注释订正** | `detectionChainWired` 的「唯一生产者是 Detector」表述已过时——新源不依赖 v2 pipeline，chain_status 只反映检测器接线 |
