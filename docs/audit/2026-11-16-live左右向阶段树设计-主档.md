## §0 摘要

**改版主张**：把 `/live` 从「静态结构图 + 两张解耦的请求清单」改成「**以请求为主体的左右向阶段树**」。

| 维度 | 现状（上→下三栏） | 改版后（左右向阶段树） |
|---|---|---|
| 视觉轴向 | 上下（客户端在顶、模型在底），1280×720 视口下**供应端/模型层落在折叠线以下** | 左右（客户端固定在左，供应商固定在右），**一屏看全一条请求的全程** |
| 观察主体 | 拓扑图看**聚合**（节点+计数），左右栏看**逐条**（两张表） | **一条请求 = 一条带**，图与列表合为一体，不用脑内对拍 |
| 阶段可见性 | 静态模块格（进站链/选路/存储/出站链），只有计数 | **每条请求逐阶段**显示到达/进行/完成/跳过/失败/告警 + 耗时 |
| 失败定位 | 只能在右栏列表里看 `error_kind` | **失败节点就地变红 + 断线**，一眼看出「错在第几步」 |
| 中间环节 | 脱敏/压缩/路由在图里是**格子**，与具体请求无关联 | 注入检测/脱敏/审批/压缩/路由/还原逐段点亮 |
| 空闲语义 | 后端 `idle_marker` 心跳被**排除**出行（只留一条灰条） | **前端自造「静默带」**：动态追加、≤5 分钟随新请求清除、>5 分钟加高并累计时长 |

**统计与过滤不丢（owner 第 3+4 轮追加要求）**：原 `/live` 的**统计**与**过滤**全部保留，一条不删。
第 3 轮形态是「顶栏 note + 第二行过滤栏」，第 4 轮进一步收敛为**一个可拖动、可三档缩放的浮动层**：
收起＝顶栏页角胶囊（区间标签 + 请求数/成功率/在途 + 过滤摘要），展开＝浮窗（统计在上、过滤在下）。
同批还做了三件事：**版面紧凑化**（带高 150→118px，说明文字移入 tooltip）、**hover 冻结列表滚动**（鼠标停在某条请求上时新请求只追加、视图不动）、**点击请求带内展开详情**。
完整规格见 §5.12 / §5.7 / §5.9；原页统计/过滤的保留清单见 §7 第 17–18 行，第 4 轮新增诉求见第 19–22 行。

**数据地基（已核实，不是设想）**：
- `internal/liveactions` 的动作词表已在役并经 SSE `request_lifecycle` 帧下发（**初稿 13 个 → 本轮实施后 17 个**，新增审批/注入/脱敏/tools 还原 4 个）—— 这是唯一在跑的**实时阶段流**，阶段树主干直接复用它。

- `domains/requestjourney` 提供**有序、无内容**的旅程事件契约（含 `stage`/`outcome`/`error_kind`/切节点切模型），是补齐缺口的正规扩展面。

**诚实边界（★ 实施轮订正）**：初稿写「注入检测 / 脱敏命中 / 审批 / 还原 这四段的**实时**数据当前**不存在**」——

**仅剩「还原（脱敏占位符回填，响应侧）」仍无数据**（详见 §6.1 与 §12.6）。
⇒ live2 对该段按纪律显示「⋯ 未测量」/「– 不适用」，**不假装跑过**。

**实测结论（4 条）**
1. **轴向错位**：客户端在顶、模型在底，供应端节点层在 1280×720 下**已被推到折叠线以下** ⇒ 「看不清楚」是几何事实，不是主观感受。
2. **图与请求解耦**：中间是**聚合结构图**（模块格里全是计数 0），左右两栏是**逐条清单**，三处数据没有「同一条请求」的连接 ⇒ 用户的「核心想法没显示完整」＝ 无法把「这条请求走到哪一步」和「它属于哪个客户端/供应商」连起来。
3. **中间环节是静态格子**：脱敏/压缩/路由只是大方块里的一个矩形，**与任何一条具体请求无关联**，也无法显示「哪条请求经过了它」。

## §3 设计总纲

### 3.1 一句话

**把「图」改成「请求带」**：屏幕上一行 = 一条请求；行内从左到右是它真实走过的每一段；上行是**发**（客户端→供应商），下行是**收**（供应商→客户端）；失败就地变红；空闲时底部长出一条会呼吸的静默带。

### 3.2 为什么左右而不是上下

| | 上下（现状） | 左右（改版） |
|---|---|---|
| 读者视线 | 纵向扫 4 层，层与层之间靠连线猜 | 横向扫一条链，天然符合「请求从左到右流过系统」的直觉 |
| 一屏容纳 | 4 层 × 节点高度 42px + 大方块 320px ⇒ 必然超一屏 | 1 条请求带 ≈ 120px 高 ⇒ 1280×720 可同时看 5~6 条请求的全程 |
| 失败定位 | 要在「上下 4 层」里回溯找红点 | 失败节点**就在那条链上**，带内自解释 |
| 与「请求为主」契合 | 图是聚合，请求是清单，二者打架 | 一条请求一条带，**没有第二套数据** |

### 3.3 为什么一条带要分上下两轨

owner 要求「一个请求分两块，发送与接收」。技术上也必须：**返回方向与发送方向相反**（供应商在右、客户端在左）。若挤在同一水平线上，来回箭头会缠成一团（§1.1 现状的边也是这个问题）。故：

- **上轨 = 发送轨（send rail）**：蓝系，箭头向右，客户端 → … → 供应商/令牌池。
- **下轨 = 接收轨（receive rail）**：青系，箭头向左，供应商 → … → 客户端。
- 两轨在**右端（供应商节点）**汇合、在**左端（客户端节点）**汇合 ⇒ 视觉上形成一个**横向的「括号/回环」**，这就是「树」的形状：枝干向右生长，到供应商折返向左回到客户端。

## §5 详细设计

### 5.1 请求带（band）几何

- **带高**：常态 118px（发送轨 54px + 接收轨 34px + 摘要行 30px）；失败带 132px（失败说明占 2 行）。
- **列（x 轴）**：全局共享列头，所有请求带**列对齐** ⇒ 竖着看是一列阶段，斜着看是一条链。这是「树」的网格基础。
- **列宽**：`客户端 168px`（吸左）、`鉴权/审批 104px`、`注入检测/脱敏/压缩/路由 124px`、`供应商 150px`；总宽 ≈ 1140px + 内边距。视口 <1180px 时**横向滚动**，客户端列 `position: sticky; left: 0`（身份不丢）。
- **行序**：新请求从**底部**插入，列表整体**向上翻动**（`flex-direction: column-reverse` 或滚动锚定底部），与用户「逐个请求往上翻动」一致。
- **列头 sticky**：顶部一行固定，显示每列名称 + 本列**在途数/失败数**（如「脱敏 3 ⚠1」）。

### 5.2 阶段模型（**按真实管线顺序**，非拍脑袋顺序）

### 5.3 阶段状态机（每段 6 态）

```
未到达 pending ──(到达事件)──▶ 进行中 active ──▶ 完成 done
                                  │
                                  ├──▶ 跳过 skipped      （未命中：压缩未触发/审批免审/注入检测未开启）
                                  ├──▶ 告警 warn         （命中但放行：注入 score 高未达拦截线、压缩降级）
                                  └──▶ 失败 failed       （拦截/超时/上游错误）
未到达 ──────────────────────────────────────────▶ 失败 failed   （到达即失败：鉴权拒绝、限流）
```

- 「进行中」的判定：已收到该段的**开始**事件、尚未收到**结束**事件。
- 「失败」必须有**失败点**：失败节点红闪 + 相邻连线断开 + 带尾给出 `失败阶段 + 错误码`（`failure_detail_code` 优先，退化到 `error_kind`）。
- 「未测量」是**第六种展示态**（灰 `⋯`），用于「数据缺口」段（如还原）——**必须显式区分于「未到达」**：否则用户会以为系统没跑这一步，而真相是「我们没埋点」。这与本仓库既有诚实性纪律一致（`unknown ≠ down`）。

### 5.4 连线语义

| 连线 | 含义 |
|---|---|
| 发送轨实线蓝 | 该段已成功通过 |
| 发送轨虚线 | 该段未走到 |
| 发送轨断线红 | 失败发生在该段之后（断点＝失败节点） |
| 点划线 + 队列徽标 | 排队等待中（`model_enqueued`/`node_enqueued`，带 `queue_depth`） |
| 接收轨实线青 | 该段已返回 |
| 接收轨虚线青 | 该段未返回（上游未响应/失败） |
| **切节点/切模型** | `node_switch`/`model_switch` 事件在路由段上叠一个「⇄ 切节点」徽标并显示 from→to |

### 5.5 客户端标识（owner 明确要求）

客户端节点三行：
1. **行1（名称）**：`agent_name`（如 `Claude Code`）/ 无则回落 `client_profile`；再回落 `client_protocol`。
2. **行2（类型）**：`agent_type`（如 `coding_agent`/`sdk`/`cli`/`browser`）→ 译成中文徽标（编码助手 / SDK / 命令行 / 浏览器 / 未知）。
3. **行3（协议·模型）**：`client_protocol`（openai/anthropic/gemini）+ 请求模型名。

> 数据来源全部现成：`LiveRequest.client_profile / agent_name / agent_type / client_protocol`（`admin/live_stream_sse.go:386-393`）。

### 5.6 静默带（idle band）规则 —— 本方案最需要精确的部分

> **必须与后端 `idle_marker` 心跳严格区分**（2026-11-03 教训：心跳行会把真实请求整页顶掉）。
> - `idle_marker`：后端心跳（`status=idle`/`error_kind=no_traffic_*`），**不渲染成请求行**，只用于「某条泳道安静了」的弱提示。
> - **静默带**：前端**自造**的纯展示元素，表示「**整个网关此刻没有流量**」。它不是一条请求，因此不进入请求计数、不参与过滤、不进详情页。

**状态表**

| 状态 | 触发 | 行高 | 文案 | 何时消失 |
|---|---|---|---|---|
| `idle-fresh` | 距上一次真实请求 ≥ 3s 且当前无请求 | 34px（矮） | `系统静默 · 已等待 0:42` | **新请求到达即清除**（≤5 分钟规则） |
| `idle-long` | 静默持续 **> 5 分钟** | 随等待时长增长：34 → 96px 封顶（`h = 34 + min(62, wait_min*12)`） | `系统静默 · 已等待 12:37` + 更醒目的斜纹底 + 呼吸光 | **不再新增静默带**；该带原地更新时长与行高 |
| `idle-recovered` | 长静默后新请求到达 | 保持原高度 | `曾静默 12:37 · 已恢复` | 保留为历史，随 50 条上限淘汰 |

**规则逐条落地**

1. 「没有请求时，**动态加上一行**闲置状态」→ 静默开始后 **3 秒**追加一条 `idle-fresh` 带（3 秒是「短暂抖动不算静默」的工程阈值，写进配置常量 `IDLE_ONSET_MS`）。
2. 「**闲置不超过 5 分钟**，后面有请求上来后，这个闲置的一行就被清除」→ 新请求到达时，删除所有 `idle-fresh` 带（它们是短暂安静，不留痕）。
3. 「**时间超过 5 分钟，不用增加闲置的状态**，只是在最后一行闲置的状态上修改闲置的时长，适当加高行高」→ 静默满 5 分钟时：把当前 `idle-fresh` 升级为 `idle-long`；此后**不再追加任何新静默带**，只对**最后一行**静默带做「时长 + 行高」原地更新（每 1s tick）。
4. 「显示等得时间更长」→ 行高随等待时长线性增长到 96px 封顶（34px 一行文字放得下，超过就多余）；视觉上加斜纹底纹与呼吸光点，等待越久越显眼。
5. 长静默后恢复 → 该带转 `idle-recovered` 并**保留**（这是一次有意义的系统事件），计数仍受 50 条上限约束。

### 5.7 内存与滚动

| 项 | 规则 |
|---|---|
| 请求带上限 | **固定 50 条**（owner 明确「内存中只保留不超过50个请求」）：`MAX_BANDS = 50`，超出丢弃**最旧**（连带它的子事件与计时器），与 `liveStreamStore.trimOldest` 同一手法 |
| 上限计数 | 静默带**计入** 50 的预算（它们占内存）；但计数徽标「请求 N」只数真实请求 |
| 翻动方向 | 新带从底部插入、整体向上滚；用户手动上滚后**暂停自动跟随**（回到底部才恢复），避免和阅读打架 |
| **hover 冻结**（第 4 轮） | 指针停在某条请求上 ⇒ **暂停自动跟随**：新请求照常追加到列表末尾，视图一动不动；指针离开 ⇒ 解冻（若此前处于跟随态则一次性追平）。提示：底部左侧「列表已冻结 · 已追加 N 条新请求（视图不动）」 |
| 冻结期的两个约束 | ① **被 hover 的那条不淘汰**（正在读的内容不能被抽走）；② 淘汰发生在锚点上方时**补偿 scrollTop**（内容变短 ⇒ 滚动位置同步上提 h），保证锚点在屏幕上**原地不动** |
| DOM 规模 | 50 带 × 12 节点 ≈ 600 节点 + 100 条连线。**性能预算见 §5.11**（必要时对带内不可见部分用 `content-visibility: auto`） |

> ★ **「冻结」与「暂停跟随」是两个独立信号**：上滚＝用户想翻历史；hover＝用户正在读这一条。
> 两者都只回答「要不要滚动」，互不覆盖；生产实现里也要保持这种**单一职责**，否则会出现「一边冻结一边自相矛盾」。
> ★ 冻结期的淘汰补偿是**列表虚拟化**的通用手法：删除视口上方的内容必须同步调整滚动位置，
> 否则整个视口内容会被上拽（本轮实测 13 次淘汰 ⇒ 悬停那条上移 1534px，直接跑出屏幕）。
> ★ 另外必须**关掉浏览器的自动滚动锚定**（`overflow-anchor:none`）并给自己的程序化滚动打标记 ——
> 否则浏览器与我们各补一次 ⇒ 位移翻倍（实测 scrollTop 跳 −3068px）。

### 5.13 最终匹配模型 · 回复侧指标 · 节点可信度（owner 第 5 轮）

> ★ 本节三项诉求**共用一条纪律**：任何一个数都必须能回答「它从哪来、在什么范围内成立、
> 测不出来时显示什么」。三项里有两项**生产数据已经现成**（零补点），一项**必须补点**，
> 一项**生产上不可得**（上游不发）—— 不可得的那项要显式写「未提供」，不能造一个假的。

#### (1) 最终匹配模型：**「客户端要什么」与「实际用了什么」分列两端**

请求进入时有三种形态，各自有不同的解析链：

| 进入形态 | 客户端请求名 | 解析结果 | 树上呈现 |
|---|---|---|---|
| **auto 自动选型** | `auto` | 分类任务类型 → 选出 canonical 模型 | 客户端节点挂 `AUTO` 徽标、第 3 行写 `auto → 选中模型`；摘要行 `⇢ auto·reasoning → gemini-3-pro`；路由节点显示最终模型 |
| **别名** | `gpt-6` | 别名表 → canonical | 客户端节点第 3 行写 `请求 gpt-6`；摘要行 `⇢ gpt-6 → gpt-6-astra` |
| **canonical 直达** | `gpt-6-astra` | 原样（仍走 canonical 归一） | 客户端节点第 3 行写 `请求 gpt-6-astra`；摘要行**不出解析 chip**（请求名＝最终模型，无差异不制造噪音） |

> ★★★★ **口径陷阱（本轮复核生产代码时才发现，必须写进实现）**：
> **`client_model` 不是「客户端原始请求名」。**
> `domains/streaming/handler.go:3570` 的 `preAutoModel := clientModel` 捕获了客户端**原始**请求名，
> 但它在 `:3663` 只进了 `resolveRequestJourney(r, tenant, preAutoModel, clientModel)`
> —— **`preAutoModel` 不进 `request_logs`、不上实时帧**；
> 而 `client_model` 存的是 **auto 改写之后**的模型。
> `admin/live_stream_sse.go:3206-3209` 的注释把这条写死了：
> 「auto 请求的 client_model 在 handler 侧已被改写为『选中的模型』……所以『客户端要的是 auto』
> 这件事由 IsAutoRequest 表达，**不能靠 ClientModel=="auto" 反推**」。
>
> ⇒ 三个直接后果：
> 1. **auto 场景下客户端节点不能写「请求 auto」** —— 生产拿不到这个字面量。
>    正确写法是 `auto → 选中模型`（左边的 `auto` 来自 `is_auto_request` 这个**标志**，不是来自字符串）。
> 2. **auto 场景下 `client_model == canonical_name`** ⇒ 「请求名 → 最终模型」这条链在 auto 场景
>    没有信息增量；真正的信息是「auto 选型 ⇒ 选了哪个 + 任务类型 + 决策置信度」。
> 3. **摘要行 chip 的出现条件不能用 `clientModel != model`** —— auto 场景两者相等，
>    那个条件会让 **auto 请求的解析 chip 整条消失**（本轮原型实测：改正前 auto 带 14 条、chip 0 条）。
>    正确条件是 **`isAuto || clientModel != model`**。
>
> ⇒ 别名场景不受影响（别名不改写 body，`client_model` 保持别名原样）⇒ 「⇢ 别名 → canonical」成立。

**落位分工**（左＝意图，右＝事实，中间是解析动作）：

| 位置 | 显示 | 数据字段 | 生产可得性 |
|---|---|---|---|
| 客户端节点标题行 | `AUTO` 徽标 | `is_auto_request` | ✅ SSE 已有 |
| 客户端节点第 3 行 | auto：`auto → 选中模型`；否则：`请求 <client_model>` | `is_auto_request` + `client_model` + `canonical_name` | ✅ SSE 已有（★ 语义见上方口径陷阱） |
| **路由节点第 2 行** | 最终匹配模型名 | `canonical_name` | ✅ SSE 已有 |
| 摘要行 chip | `⇢ auto·reasoning → gemini-3-pro` / `⇢ gpt-6 → gpt-6-astra` | 上面两项的组合（判定条件 `isAuto \|\| clientModel != model`） | ✅ SSE 已有 |
| 详情块「模型解析链」 | 逐项：客户端请求模型（auto 改写后）/ auto 选型（任务类型 + 决策置信度）/ 最终匹配模型 / 切换链 / outbound + **口径注记行** | `task_type` / `auto_decision` / `auto_confidence` | ⚠ 前两项 SSE 已有；**`auto_decision`/`auto_confidence` 需补点**（`telemetry.RequestLogEntry` 已有，SSE 未带） |

| 证据 | 来源 | 现状 |
|---|---|---|
| 上游系统指纹 | 响应头 `X-System-Fingerprint` | ★ **不可得**：211 全量实测 `system_fingerprint` **非空率 = 0**（上游从不发这个头；`deploy/prometheus/rules/integrity_fingerprint_drift_test.go:152-188` 有可复现查询）⇒ 只能显式写「**未提供 —— 上游不发**」 |
| 上游自报模型名 | 响应体 `model` | 可得（需上实时帧） |
| 分词器签名 | 标定提示词的 prompt token 计数 | 可得（`modelcredibility` 已采集） |
| 被动时序指纹 | 真实流量的 ITT/TTFT/吞吐 vs 基线 | 可得（`DimPassive` 第五维，2026-11-09 起在跑） |

⇒ **「指纹」在 live 上必须呈现为证据链，而不是一个指纹字符串**。单值显示「未提供」，
但同时给出「自报模型名 + 分词器签名 + 被动时序偏差」三行 —— 这才是真正能判断「上游有没有换模型」的东西。

**判定有时效 —— 旧结论必须标出来**：可信度是「**最近一次检测**」的结果，不是实时值。
把三天前的结论挂在实时视图上、却不标时间，用户会当成「刚刚验证过」。
⇒ 角标与详情块都带**判定时间**；超过 **7 天**未复测 ⇒ 角标**虚化（opacity .6）+ 虚线边框**，
tooltip 与详情块写「⚠ 结论已过期 N 天（> 7 天未复测）」。
（原型实测：28 个角标中 18 个判为过期，虚线边框与 0.6 透明度均生效。）

**可信度是节点级判定，不是本次响应实时验证**（`domains/modelcredibility`）：

- 判定维度 5 个：身份自洽 / 能力水位 / 指纹一致 / 参考基线 / 被动时序；
  结论 4 态：`verified` / `suspected` / `diluted` / `unknown`；
  口径纪律：**缺失维度不计入**（不按 0 分算）、**证据不足写 `unknown` 不写 `verified`**。
- 它挂在 **(凭据, 模型)** 上，**不随单条请求变化** ⇒ 树上落位在**供应商节点角标**，
  tooltip 与详情块必须写明「节点级判定 · 最近一次检测 … · **非本次响应实时验证**」。
- 子系统与 admin API 都已存在（`GET /api/admin/model-credibility/list|catalog|detail|history`，
  前端已有独立页 `ModelCredibilityView.vue`）⇒ **生产接入只是把结论挂到实时帧，不是在造新判定**。

★★ **三个「置信度」必须分开命名，否则必然误读**：

| 名字 | 回答什么 | 来源 | 不可混用 |
|---|---|---|---|
| **auto 决策置信度** | 「auto 这次选这个模型有多大把握」 | `auto_confidence`（0–1） | 路由决策层 |
| **节点可信度** | 「这个供应商给我的，是不是它声称的那个模型」 | `modelcredibility`（0–100 + 4 态） | 身份层 |
| **证据强度** | 「这个判定有几把尺撑着」 | `measured_dimensions`（0–4） | 结论层 |

⇒ 摘要行只放**节点可信度**角标（短）；auto 决策置信度放**详情块**（它是单请求属性）。
混成一个「置信度」会让「路由选型不确定」被读成「上游在掺水」。

#### 6.3.2 四个必须写进实现的判据

1. **「缺失维度不计入」与「unknown ≠ verified」**（`domains/modelcredibility/types.go:50-58`
   与 `verdict.go`）：证据不足时必须写 `unknown`，不能写 `verified` —— 否则「没查过」
   会被读成「查过且没问题」。
2. **缓存分母口径随上游协议变**（`domains/streaming/usage.go:243-284`）：OpenAI 与 Anthropic
   口径**相反**；2026-10-06 真库已因此产生 1628 行负成本。⇒ 实时帧必须带上游协议，
   且必须有「>100% ⇒ 口径异常」的护栏。
3. **可信度是节点级属性**：它挂在 (凭据, 模型) 上，不随请求变化。树上展示必须带
   「节点级 · 最近一次检测 … · 非本次响应实时验证」，否则会被读成「这条响应刚被验证过」。
4. ★ **`client_model` ≠ 客户端原始请求名**（`domains/streaming/handler.go:3570/3663` +
   `admin/live_stream_sse.go:3206-3209`）：auto 请求的 `client_model` **已是选中的模型**，
   原始请求名 `preAutoModel` 只进 requestjourney、不上实时帧。
   ⇒ 「客户端要的是 auto」只能由 `is_auto_request` 这个**标志**表达；
   客户端节点写 `auto → 选中模型`，**不得写「请求 auto」**；
   摘要行 chip 的出现条件必须是 **`isAuto || clientModel != model`**
   （用后者会让 auto 请求的解析链整条消失）。

> 且键盘用户无路可退。判定标准不是「能不能开」，而是「开着的两个会不会打架、能不能用键盘关掉」。

> ★ D9 的通用式：**「一行控件」在窄屏下最容易被自己的长文案顶出视口**。两个数据开关＋一条长提示的组合，
> 在 721px 下把最关键的「清除筛选」挤到了屏幕外 —— 过滤功能等于残废。
> 修法不是加滚动条（滚动条在窄屏上不可见 ⇒ 等于没有），而是**允许换行**。

> ★ D10 的通用式：**「固定偏移」与「动态布局」不能混用**：只要上游容器高度会变，锚点就必须实测量。

> ★ D11/D12 的通用式：**「删除列表项」必须连滚动位置一起算** —— 删除视口上方的内容要同步上提滚动位置，
> 否则「列表自己动了」；而这个补偿**只能有一份**（浏览器与业务各补一次 ⇒ 位移翻倍）。
> ★ D13 的通用式（与 D6 同族但更隐蔽）：**任何由数据变化引起的滚动位移都不能读成用户意图** ——
> 判据必须是「这次位移是不是我们自己造成的」，而不是「位移方向像不像用户操作」。
> ★ D14 的通用式：**「就地展开」比「在旁边展开」更稳** —— 展开物若改变布局，同一坐标的第二次点击就会落到别的东西上；
> 让被展开的对象**自己长高**，光标下的东西才不会被下面的内容顶走。

| # | 现象 | 根因 | 修法 |

| **D15** | 缓存命中率**出现 131%**（`cache_read 4209 tok / prompt 3224 tok`） | 模拟器把 `cacheRead` 与 `tokensIn` **独立生成** ⇒ 造出违反口径不变式的数据。★ 这正是本仓 2026-10-06 真库事故（`_request_logs.cost_usd < 0` **1628 行 / −$4.79**，其中 11837 行里 cache 是 prompt 的 **25 倍**）的形态：两个并列数被当成包含关系 | ① 生成端按上游协议分别造数：OpenAI 口径 `cache_read ≤ prompt`、Anthropic 口径两者并列；② **加护栏**：OpenAI 口径下算出 >100% ⇒ 显示「**口径异常**」并说明「两口径混用」，不显示假百分比；③ 加**静态不变式断言**（数据源侧 `cacheRead ≤ prompt` 违例数必须为 0） |

> ★ D15 的通用式：**造演示数据时也要守口径不变式** —— 演示数据一旦违反业务不变量，
> 评审者会拿它当「产品会算出这种数」的证据（这轮就差点把一个 131% 的假命中率写进方案）。

> ★ D17 的通用式：**「看起来排对了」不等于 DOM 排对了** —— 未闭合标签会静默改变层级，

> ★ D18 的通用式：**角标是「加在别人身上的」** —— 它的宽度必须从宿主元素里**预留**出来，

> ★ D19 的通用式：**「背景色生效」不等于「这条样式生效」** —— 同一个 `border` 简写里的

> 要么就别用简写写基础规则。

#### 11.1.0.1 第 5 轮的两个假缺陷（留档：都是断言写错，不是产品错）

#### 11.1.1 一个被证伪的「假缺陷」（同样重要，故留档）

上一轮自测记录过一条：**「统计面板点开后立刻自己关掉」**，当时的归因是「document 级 click 监听误关」。
本轮用 `setAttribute/removeAttribute` **堆栈捕获**复测，结论是**页面逻辑无误** —— 真正的触发者是**测试探针自己**：

| 探针缺陷 | 现象 | 真凶 |
|---|---|---|
| 用**一次性坐标**点击顶栏按钮 | 顶栏读数随请求数实时变化 ⇒ 按钮宽度/位置**漂移**，坐标失效 | 点击落到按钮外 ⇒ 被 outside-click 判定为「点到空白」⇒ 关面板 |
| 用来测「点空白」的坐标**落在请求带上** | 请求带会打开**抽屉**，抽屉遮住顶栏 | 后续所有点击都被抽屉吃掉 |
| 用 MutationObserver 抓 `hidden` 变更 | 捕获到的栈是**观察者自身**的回调栈 | 看不见真正的设置者（误以为「栈在 observer 里 = observer 关的」） |

修复后的复测（真实鼠标点击，非脚本 `click()`）：开 → 点面板内 → 保持打开；点标题空白 → 关闭；再点按钮 → 打开；同按钮再点 → 关闭（toggle）。**全部符合预期**，且每一步的关闭方都能从堆栈明确指认。

> ★ 通用式：**「元素位置」不能当常量** —— 顶栏读数随数据变化 ⇒ 按钮会漂移；
> 任何依赖坐标的自动化测试都**必须每次重新取 `getBoundingClientRect()`**，
> 否则会把「点空」误判成「功能坏了」，再顺着假象去改正确的产品代码（最坏情况：把对的实现改坏）。
> ★ 派生的加固（虽然不是缺陷，但值得留）：开关收敛到单一入口 `setStatOpen()`（`hidden` + `aria-expanded` 同点同步），
> outside-click 判定改用 `e.composedPath()`（对 target 重定向免疫）—— 让「谁关的」永远可指认。

#### 11.1.2 第二个假缺陷：第 3 轮的教训在第 4 轮**复演了一次**

第 4 轮测「点详情里的抽屉按钮」时，按钮**点了没反应**（抽屉不开）。用堆栈捕获复测后发现：
按钮的 `onclick` 正常（程序化 `btn.click()` 可打开抽屉，15 项 + 10 条动作齐全），
真实鼠标点击却落空 —— 因为**模拟器仍在跑**：持续的新请求 ⇒ 50 上限淘汰 ⇒ 布局不停变化 ⇒
**测量的坐标在点击前就失效了**。

处置：
- 交互类测试**先暂停模拟器**（点「⏸ 暂停」），让布局静止；
- 每次点击前**重新取 `getBoundingClientRect()`**，不使用上一轮缓存的坐标。

> ★ 这与 §11.1.1 是同一条纪律：**「元素位置」不是常量**。数据一变，位置就变；
> 自动化测试若不复位坐标，就会把「点空」写成「功能坏了」，再顺着假象去改本来正确的实现 ——
> 这是最坏的一类误伤（把对的改坏）。本轮两次假缺陷都出自同一根因。
>
> ★ 另附一条**测试基建**教训：`python3 -m http.server` 是**单线程**的，
> 浏览器 keep-alive 连接会把它卡死 ⇒ 后续请求 ERR_ABORTED、页面反复「加载不出来」。
> 改用 `ThreadingHTTPServer` + `Cache-Control: no-store` 后稳定。

> ★ D5/D6 的通用式：**「列表自动跟随」不能用 scroll 事件反推用户意图** —— 自身的内容增长与淘汰会污染同一个信号。
> 判据必须是**独立于被观察量的意图信号**（滚轮/触摸方向），否则会出现「自己把自己卡住」的死锁。
> ★ D6 与 D3 同族：**「谁最后写状态」与「事件真实顺序」是两回事**；阶段推进与跟随状态都必须有单一可信来源。

> ★ D3 的通用式：**「阶段推进」类视图里，事件到达顺序必须由排程保证，不能由「谁最后写状态」决定** ——
> 否则时间线会自己撒谎（先到的后写、后到的先写）。生产实现里这条对应「按 `seq` 归并 liveactions 事件流」
> （`ActionEvent.Seq` 已是单调序号，`internal/liveactions` 契约自带），**不得按到达顺序直接覆盖状态**。

### 13.4 通用式（本轮沉淀）

- ★ **「口径」标签是承诺**：面板写「当前时间范围」就必须真的随时间走，否则**标签与实现互相打脸**——静态快照配动态口径，比没有口径更误导。
- ★ **图标 ≠ 状态**：**图标表达「哪一步」，角标字形表达「现在怎么样」，小数字表达「这一步最关键的那个数」**——三者分离才读得懂；把三者挤进同一个图形必然歧义。
- ★ **「有请求的优先」是排序契约不是过滤契约**：完整 = 有请求的 + 零流量的都在，优先 = 有请求的排前面。
- ★ **换组件前先对拍两套名字**（canonical ⇄ raw）——本轮虽未换组件，但同一原则用于错误来源：**来源由词表推出，不手填**。

### 14.5 通用式（本轮沉淀）

- ★ **「同一行」是版面契约**：状态、目标模型、路由这三样是**读一条请求的终点信息**，一旦另起一行，读者就得在两行之间来回对位；把它们钉在行的右端，整条带才「完整一致」。
- ★ **去边框会放大「元素相撞」的代价**：有边框时轨道线穿过图标只是「有点脏」，无边框时直接变成「划掉图标」⇒ 去边框必须**同时**给每个元素划出互不重叠的格位（图标 / 状态字形 / 小数字 / 路由标记各占一角）。
- ★ **计数型语义应当有「量」的视觉**，不只有数字：把「N 次尝试」同时画成 N 个标记，读者不用读数字就知道这条重试过。

### 14.6 遗留（如实登记）

- **浏览器缓存**：本地 `python3 -m http.server` 不发 no-cache 头，浏览器可能拿到**旧版原型**（实测有一次导航命中了缓存 ⇒ 页面渲染成完整模式）。评审前请**强制刷新**（`Cmd+Shift+R`）或给 URL 加任意参数（如 `?v=8`）破缓存；headless 出图每次是新 profile，不受影响。
- 生产端 `/live2` 的 Vue 实现**仍未同步**本轮两轮改造（完整/紧凑双模式、顶部过滤、来源徽标、多次路由链、全景面板，以及本轮的单行右置与路由标记）——本轮仍只交原型 HTML。
- 同族历史变体疑似互为覆盖（`-多标签版-备份` / `-正确布局版` / `-双主题版` 字节数相同 40109）——未查，遗留登记。

### 15.2 ★ 「未执行」为什么选靛紫（配色不是随手挑的）

### 15.6 ★ 本轮抓到并修掉的 5 个真缺陷

1. **紧凑模式仍显示 ✓**：字形表 `GLYPH` 被瓦片、局部刷新两处共用 ⇒ 只改 CSS 没用 ⇒ 新增 `CGLYPH`（紧凑专用，`done:''`）并改两处调用点。

### 15.8 通用式（本轮沉淀）

- ★ **状态色要成体系地选**：先数「已经用掉的色相」，再选剩下的；并且**同一语义在全局只有一处颜色**（瓦片 / 图例 / 徽标必须同色）。

- ★ **「详情与背景重叠」的根因往往在**「写死的尺寸常量」**：紧凑模式带高 40，展开逻辑却用完整模式的 118 ⇒ 带没长高，详情就溢出。修法＝所有尺寸常量改**读当前模式**。

- ★ **初始化时调用的函数如果不存在，症状不是「报错」而是「整页空」** —— 排查「数据不出来」时，先看控制台有没有 `ReferenceError`，再怀疑数据。

### 16.2 ★ 为什么错误信息要做成「一列」，而不是「行尾再挂一个 chip」

第一版就是挂在行尾的（chip 放在行内流的最后）。实测立刻暴露问题：

| 做法 | 实测 | 问题 |
|---|---|---|
| chip 挂在**行内流末尾** | 最宽失败行右缘 **1265px**（超出带宽 1200）⇒ 内容溢到带外；且不同失败行的 chip 右缘**各不相同**（1131 / 1265 / …） | ① 视觉上「挂在带外」；② 眼睛**没法竖着扫**——owner 要的「最右边看错误」落空 |
| ★ chip 放进**带级的固定右列** | 所有 chip 右缘**恒等于 1390** | ⇒ 变成一条真正的**列**：扫一眼右边缘就知道哪些行错了、错在网关还是供应商 |

代价是**树宽 1200 → 1400**（+200：错误列 210 + 右留白 10 + 与行内块间距 12 + 余量）。这是**明码标价的取舍**，不是免费午餐：
行内块实测最宽 509px（失败徽标 43 + 会话 45 + 模型 chip ≤187 + 路由 ≤114 + 候选 36 + 尝试 48 + token ≤105 + 耗时 30），
新可用宽 1400−622−232 = **546px** ⇒ 余量 37px。
★ 窄屏（≤1023px）会自动切成**卡片版面**，此时错误列退回普通流（`.layout-narrow .band .cerr{position:static}`），不会跑出卡片。

### 16.6 通用式（本轮沉淀）

- ★ **「在最右边」有两种实现，差别是能不能扫**：把信息**挂在内容流末尾** ⇒ 每行位置都不一样，眼睛要逐行找；给它**一条固定列** ⇒ 位置恒定，眼睛一次竖扫就看完。**owner 说「在最右边显示 X」时，要先问：是想看到，还是想一眼扫到？**
- ★ **加一列的代价必须明码标价**（本轮＝树宽 +200px），并且**必须量出内容的真实最宽值**（本轮实测 509px），否则新列要么挤掉内容，要么被内容顶穿。
- ★ **列表要按「人怎么找」分层，不要按「数据怎么存」分层**：运营标注的（特色/精选）与统计出来的（热门）**分段分开**，别混在一张榜里；混了就会出现「把标注当测量」或「把测量当推荐」。
- ★ **实时刷新会吃掉交互**：任何「定时重画列表」都必须保住**滚动位置 + 焦点 + 正在点的那个元素**；重画前先问「用户此刻在不在这个列表里操作」。
- ★ **筛选器的候选集＝「目录 ∪ 实际出现过」**：只给目录里的，目录外的就「筛不出」；只给出现过的，没流量的就选不到。

| `band.credits` | `credits_charged` | 1¥ = 100 积分（模拟） |

★ **用户 ↔ key 是一对多**（`API_KEYS` 按客户端派生 1~3 把 key，用户按 key 轮转归属）⇒ 两个维度可**交叉核对**：
「Top5 key 的请求数之和 ≤ 对应用户的请求数」恒成立 —— 这是**两个独立维度互相验账**的入口。
★ **诚实登记**：这些值是**模拟器造的**。生产侧应取真实表，原型口径区已把这一点写在明处（不藏在角标里）。

### 17.3 ★★★ 「费用估算」与「成本估算」必须**两套独立的数**——否则「毛利」是假数

| 口径 | 算法 | 含义 |
|---|---|---|
| **费用估算**（对用户计费） | 模型**目录价目表** `MODEL_PRICE` × token；缓存读按折扣价 `cachedIn`；缓存写按上游协议加价（Anthropic 1.25× 输入、OpenAI 自动缓存写入不另计） | 用户付了多少钱 |
| **成本估算**（上游采购） | 目录价 × **供应商采购系数** `PROVIDER_COST_FACTOR` | 网关实际付给上游多少 |
| **毛利估算** | 费用 − 成本（**两者已折算到同一币种 ¥ 才可直接相减**） | 折让空间 |

★★ **一个必须写进界面的陷阱**：生产侧 `credits_charged` 是**积分**、`cost_usd` 是**美元**，
**单位不同、不可直接相减**（须按 `credits_rate_multiplier` 折算）。
本原型之所以能算毛利，是因为**先统一折算到 ¥**；口径区明写这一点，避免评审把原型的「毛利」直接套到生产上。

★ **没有价目表的模型 ⇒ 不给数**：该条请求标 `priced=false`，费用/成本显示「—」，
口径区计数披露「N 条因无价目表口径而未计入」——**绝不按均价硬摊**（第 9 轮 F3「静默截断最容易被读成数据正常」的同款纪律）。
★ 缓存命中率的分母口径**随上游协议变**（OpenAI：cache⊆prompt；Anthropic：cache∥prompt），
每条按自己的协议算分母再聚合；未触达供应商的口径不可判定，**单独计数不进分母**。

### 17.4 ★ 周期统计：分桶的三个坑（都踩了、都修了）

| 坑 | 现象 | 修法 |
|---|---|---|
| **区间被夹住 ⇒ 控件形同虚设** | 第一版把有效窗口做成 `min(统计区间, 顶部过滤条时间窗)`；而顶部时间窗默认 5 分钟 ⇒ 用户把统计区间选成「近 2 小时」**只得到 5 分钟的数据**，控件看起来能选、选了没反应 | 统计集合改为 `bandMatches(b,{noWindow:true})`（**只跳过时间窗**，维度/状态筛选照旧）∩ 统计区间。顶部过滤条的「时间范围」**只管树上显示**，不参与统计 —— 两个区间各司其职，口径区写明 |
| **桶数退化成 1 根柱子** | 「全部（内存内）」区间的跨度是**数据实际跨度**（可能只有几十秒），按固定粒度切 ⇒ `round(span/gran)=0` ⇒ **1 个桶**，看着像「没有趋势」（其实有数据） | 跨度短于所选粒度时**按跨度自适应细分**（至少 4 桶），并把**实际粒度**写进提示（`实际粒度 20.0 秒（数据跨度短于所选粒度，已按跨度细分）`）——**改了口径就要说**，不静默 |
| **表格尾注塞进 `<table>`** | `<p>` 放进 `innerHTML` 的 `<table>` 会被浏览器**提升到表外** ⇒ 版面错位 | 尾注移到表格**外部**的独立容器 `#sfTableNote` |

### 17.5 ★ 交互语义：行点击＝**面板内下钻**，不是改顶部过滤条

顶部过滤条里**没有**「用户 / apikey」控件（只有客户端·供应商·模型·节点四维）⇒
若把行点击定义成「联动顶部过滤」，这两个维度就点不动。于是统一为**面板内下钻**：

- 点明细行 ⇒ 压入下钻栈 ⇒ 面板内所有统计（KPI / 趋势 / 六维表）都收窄到该子集；
- 面包屑逐层显示并**可点 ✕ 撤销**（点中间一层 ⇒ 撤销该层及其后）；
- 顶栏胶囊的读数与顶部过滤条**保持联动**（过滤条改条件 ⇒ 面板基线跟着变）。

★ 为什么不用「给顶部过滤条再加两个下拉」：顶栏在 1280 宽下已经换行成 3 行；
而且「用户 / key」是**分析维度**而不是**常规过滤条件**，放进下钻更贴切。

### 17.8 通用式（本轮沉淀）

- ★★★ **「完整」的含义是「不藏」，不是「多」**：第 4 轮那个 460px 小浮窗塞不下 17 个 KPI ＋ 6 个维度 ⇒ 真正的解法不是把数字压缩进小窗，而是**换版面**。**布局容量不够时，先换布局，别先砍指标**——被砍掉的指标会被读成「数据正常」（第 9 轮 F3 同款纪律）。
- ★★★ **两个「时间」控件必须各司其职**：一个是**显示范围**（树上显示哪些），一个是**统计范围**（统计算什么）。把它们**求交集**看起来「严谨」，实际是让其中一个控件**形同虚设**。正确做法：**各管各的 + 界面上写明各自的口径**。
- ★★★ **两套钱（收入 / 成本）不可共用一个数，且换算必须在同币种内完成**：生产侧积分与美元不可直接相减；原型为了能算毛利先折算到 ¥，**但必须写明这一步**，否则「毛利」会被当成可直接对账的口径。
- ★★ **没有口径就不给数，并计数披露**：无价目表的模型不给费用/成本，但要报「N 条未计费」——不给数 + 不说 ⇒ 读成「免费」；给数 + 不说口径 ⇒ 读成「精确」。
- ★★ **维度之间要能互相验账**：用户 ↔ key 是一对多 ⇒ 两个维度的请求数之和可以互相校验。**独立维度比一个维度多出的是「交叉验证」**，不是「多一列」。
- ★ **周期统计的粒度必须随窗口走，并披露实际粒度**：窗口短于粒度时细分（至少 4 桶），并写「实际粒度 X（已按跨度细分）」——**静默改口径＝假数据**。
- ★ **下钻优于加下拉**：面板内的分析维度用「下钻 + 面包屑」承载，不去挤顶部过滤条；顶部栏在 1280 宽下已经 3 行。

### 17.9 遗留（如实登记）

- **apikey / 用户是模拟器造的字段**：生产侧对应 `api_key_id` / `api_key_prefix` / `key_alias` / `api_key_owner_user`，接入时应取真实表；原型的「用户 ↔ key」归属关系是**按客户端派生 + 用户轮转**的模拟关系，**不可当作真实归属**。
- **价目表是原型内置的 6 个模型目录价**（`MODEL_PRICE`），**不是真实价目表**；生产应取 PG 价表 / 计费配置，且缓存读折扣、缓存写加价、批量折扣等规则以生产为准。
- **供应商采购系数 `PROVIDER_COST_FACTOR` 是模拟值**（0.06~1.0）；生产的上游实际成本应取 `cost_usd`，不是「目录价 × 系数」。
- **积分换算 1¥ = 100 积分是模拟值**；生产的倍率由 `credits_rate_multiplier` 决定。
- **统计只覆盖内存里保留的最近 50 条请求**（`MAX_BANDS`）——「全部（内存内）」不是全量历史；口径区已明写。生产统计应走 DB 直查 / 日桶（滞后 ≤1h）。
- **「全部」区间的桶按数据实际跨度切**，⇒ 页面刚打开时跨度只有几十秒，趋势图形状与稳态不同（这是真实状态，不是缺陷）。
- **P95 延迟在样本少时退化为最大值**（原型内存只有几十条）——生产需足够样本才有意义。
- 生产端 `/live2` 的 Vue 实现**仍未同步**第 6/7/8/9/**10** 五轮任何改造 —— 本轮仍只交原型 HTML。
