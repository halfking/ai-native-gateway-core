## §5 节奏归因（+15% 与 14 次差，两项都收口）

### §5.1 「55.2 次/天」是窗均值，稳态是 48 次/天

journal 逐日 r7d 执行数（四槽合计；10-20 前有保留窗缺口）：
10-18:1（22:03 起）、10-19:23、10-20:51、10-21:53、10-22:59、10-23:39（journal 窗
拼接缝）、**10-24:70**、10-25:51、**10-26:48**、10-27（→04:14）:7。

- **10-26 恰 48 = 名义节奏**（30min 对齐 tick，全网单 winner）。10-25 的 51 = 48 tick
  + 2 次部署初始（10:28、10:32，908 应用日）+ 1 次 off-tick（13:09 cutover）。
- 10-20~10-24 的 51~70 次 = 部署 churn（10-24 单日 154 侧 ~15 次 boot，boot+30s 的
  初始 refreshAll 每次都是一次 off-tick 执行）。canon 纪元 off-tick 占 16%（46/294），
  907 稳定纪元 4%（4/105，全部是 4 次部署应用），910 纪元 0/3（初始那次 03:02:56
  落在分钟≤3 被分类器并入 on-tick，实际是部署初始，见 §2）。
- ⇒ **R166 的「+15% 偏离」不是刷新器的设计缺陷，是部署频率的函数**；点名「候选：
  一致性检查触发、失败重试、ensure 路径」三候选全部排除（代码全查：r7d REFRESH
  只有 periodic tick / boot 初始 refreshAll / admin TriggerRefresh（无自动调用方）三个
  发射器；tuning_view_refresher 只管 tuning 两视图）。

### §5.2 r7d−audit=14：trailing view 的记账不对称

- journal 窗（保留窗起点到 04:14）：r7d 402 / audit 392；配对 377；
  **unpaired-r7d 25 / unpaired-audit 15**（净 +10；pgss 全窗净差 14，差 4 ≈ 保留窗
  缺口与击杀反向效应的混合）。
- 机制：refreshAll 先刷 r7d 再刷 audit，两视图**各自**抢 per-view advisory 锁
  （`mvRefreshLockKey`，与 session 族共用）。多实例在同一 tick 竞争时：
  (a) 同一实例连赢两轮 = 正常配对；(b) r7d 轮 A 赢、audit 轮 B 赢 = 交叉配对
  （不产生净差）；(c) 周期被中断（部署停止/ctx 超时）落在 r7d 之后 audit 之前 =
  **r7d +1 无 audit**；(d) audit 轮锁被 session 族长事务占住 = **audit 被跳过**。
  r7d 是每轮第一个视图 ⇒ 结构性领先；两方向都发生（25/15）但净偏为正。
- 良性：被跳过一方的陈旧度由下一 tick（≤30min）兜底，无数据缺陷。
