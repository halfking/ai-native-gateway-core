# 2026-11-23 大会话归约提速 —— 守卫判决缓存 + 逐条并行 —— 主档

> **owner 需求**＝「我们是否可以记录分层或逐层压缩的数据，快速进行压缩处理？每一段进行一次摘要，这样有大的会话的时候，可以快速处理。」⇒「请根据建议继续执行任务」。
> **结论先行**：大请求体归约（`sessioncontext.Reduce` + 历史守卫）**每轮的耗时 211 真机 1.87s → 0.097s（约 19 倍）**，进程冷启动后的第一轮 1.47s → 0.42s。两件事：① 历史守卫的判决是纯函数 ⇒ **缓存判决**，同一会话后续每一轮只判定新增的消息；② 归约对每条历史消息的处理**逐条并行**。**输出与此前逐字节相同**（8 种形态 × 两个平台的输出 SHA-256 全等）。顺手修掉上一轮登记的 L1（暂存目录空壳泄漏）。
> **范围**：零迁移 / 零 schema 变更 / 零前端改动。提交 `e06083d40`（功能 + 测试 + 量具），经合并 `23f8c21f4` 推上 origin/main。211 现役 `2.6.1-9237afec-20261123-211`（seq 3226，含本轮代码，见 §八）。
> **没有做的（等 owner 拍板）**：第三步「分段摘要 + 分层合并」会改变模型看到的内容，摘要方式（抽取式 / LLM 生成）需要 owner 定；候选被永久性原因挡空时是否把 503 换成 4xx 同样待定（见 §六）。

## 一、问题与测量基线

agent 会话（ZCode 等）每一轮都把**整段历史**重发一遍。请求体超过 1MB 时入口归约要把历史压到预算内：每条历史消息都要过一遍历史守卫（`security/sanitize` 的策略守卫：预筛 + 逐规则组正则）。第 N 轮的历史 = 第 N-1 轮的历史 + 新增的几条消息 ⇒ **旧消息的判决每轮被原样重算**。

上一轮（Defect-1，`df1777c9a`）把归约从 128 秒降到 5 秒（真实归档 7.7MB / 3953 条）。本轮开工时的基线（同一份合成会话 7.85MB / 3213 条 + 211 导出的 21 条历史规则）：

| 量法 | 不带守卫 | 带守卫（线上现状） | 守卫占比 |
| --- | --- | --- | --- |
| 本机（开工时；负载 2~5） | 0.40s | 3.4~3.9s | ≈ 88% |
| 211 真机（定稿时复测） | — | 1.85s | — |

带守卫那一次的 CPU profile：正则 NFA ≈45%、两种文本视图解码 ≈13%、bufio ≈6%。

⇒ 两级结论：**守卫是主战场**（缓存命中即完全跳过）；守卫未命中时的冷路径靠**并行**兜底（正则 NFA 是纯 CPU）。

## 二、设计

### 2.1 守卫判决缓存（`security/sanitize/history_memo.go`）

**为什么可以缓存**：守卫对一条消息的判决是纯函数 `判决 = f(编译后的规则策略, 消息原始字节)`。策略由 `HistoryGuard` 的 policy key（规则集 JSON 的 sha256，已按租户过滤）唯一确定；两者都不含可变状态（守卫只用 ctx 做取消）。

| 关注点 | 做法 |
| --- | --- |
| 缓存键 | `sha256(policyKey ‖ 0x00 ‖ 消息字节)`。**策略 key 进键** ⇒ 规则一变（mask→block / 换租户）旧判决自然失效，不需要任何失效逻辑 |
| 存什么 | 只存一个布尔判决。**缓存里没有会话明文**；被判「含敏感内容」的消息也只留下一个 false |
| 出错 | 读失败 / ctx 取消 / 判定错误（含 block 规则）一律**不缓存**、原样返回；命中也尊重 ctx 取消 |
| 超大消息 | >1MB 不读进内存算哈希，照旧走流式判定 |
| 没有规则组 | 策略里没有需要匹配的规则 ⇒ 包装层连源都不读 |
| 本地层 | 进程内、有界（默认 131072 条 ≈ 10MB）、32 分片、FIFO 淘汰。FIFO 而非 LRU：会话是追加式的，一条消息要么接下来每轮都复用、要么再也不出现，二者命中率几乎一样，而 FIFO 的读路径不改任何状态 |
| 共享层 | **可选，默认不启用**（见下） |

装配点与生产同构：`PatternDetector.HistoryGuard` 返回的就是 `memoizeHistoryGuard(policy.guard, key, d.verdictMemo(), …)`；未装配缓存时原样返回 `policy.guard`。

**共享层（Redis）为什么默认关**：有了并行之后，冷路径一次也只要 0.42 秒——211 每次蓝绿部署后「第一轮冷一下」的代价可以忽略，而单实例 / 蓝绿都只有本地层就够。共享层只在**多实例同时服务、同一会话相邻两轮可能落到不同进程**时才有意义，代价是把 Redis 的健康状况拉进请求路径。211 实测它的 Redis（`wm-acc-chain-redis`）**没有内存上限也不淘汰**（`maxmemory=0 / noeviction`，已用 283MB，与限流/会话/队列共用）⇒ 启用时必须自带硬边界：

- **TTL**（建议 6h）+ **每小时写入预算**（默认 50 万次 ≈ 50MB）+ **used_memory 水位线**（默认 512MB，超过即停写，读照常）——防「写太多」；
- **熔断**——防「后端卡住」。连续 5 次失败**或变慢**（单次 >5ms）即绕过共享层 30 秒（本地层照常），冷却期满半开放一个探测，探测失败立即重开。没有它，一次 Redis 卡顿会被逐条消息放大成几千次 50ms 超时。

### 2.2 归约逐条并行（`internal/sessioncontext/parallel.go` + `file.go`）

每条消息的处理是彼此独立的纯计算：元数据轮只看这条消息的字节；守卫/摘录轮只看这条消息的字节、编译后的规则策略、只读的查询词项。

- **两种资源分开**：`load(i)` 在调用方协程里按下标顺序执行（归档文件只有一个游标，顺序读最省）；`work(i, v)` 在工作协程里只做 CPU 计算。
- **≤64KB 的消息**读一次进内存，守卫 + 摘录在工作协程里做；**>64KB 的消息**走流式路径（共用归档文件游标）⇒ 串行，顺序不变。
- **不变量**：结果按下标槽位存放，最后仍按下标顺序做 best-16 选择 ⇒ **输出与串行逐字节相同**。

**出错语义**（并行最容易悄悄改变的东西）钉成规则，与串行对齐：

1. 返回**下标最小的那条错误**（串行就是在那里返回的）；
2. **出错后不再装载**——而且有硬上界：装载是**有序窗口**，装载第 i 条之前第 i−window 条必须已完成（window = 8×协程数），出错条目先置失败标记再发完成信号 ⇒ 下标 e 出错后至多装载到 e+window−1；
3. 元数据轮的 1MB 上限：有条目错误时只看 [0, 该下标] 这段的累计，溢出点更靠前则返回溢出（与串行「逐条处理、谁先出问题返回谁」同口径）。

**并发安全是显式声明的**：守卫是任意外部注入的函数，归约器无法判断它是否线程安全 ⇒ 默认串行；只有注入方（streaming）调用 `SetHistoryGuardConcurrencySafe(true)` 后，请求 ctx 才带 `WithReduceWorkers(n)`。并行度默认 `min(GOMAXPROCS, 8)`（上限 8 是有意的：入口并发槽可达 32，每个请求再各开满核只会互相抢 CPU）。

### 2.3 装配、开关与指标（`cmd/gateway/history_guard_memo_init.go`）

| env | 默认 | 含义 |
| --- | --- | --- |
| `LLM_GATEWAY_HISTORY_GUARD_MEMO` | on | `off` 关闭缓存（归约回到逐条重算；显式列出 off/0/false/no/disabled） |
| `LLM_GATEWAY_HISTORY_MEMO_LOCAL_ENTRIES` | 131072 | 进程内缓存条目上限 |
| `LLM_GATEWAY_REDUCE_WORKERS` | min(GOMAXPROCS, 8) | 单次归约的最大工作协程数，夹在 [1, 32] |
| `LLM_GATEWAY_HISTORY_MEMO_SHARED_TTL` | （未设＝关） | 设了才启用共享层（如 `6h`） |
| `LLM_GATEWAY_HISTORY_MEMO_SHARED_MAX_USED_MB` | 512 | 共享后端内存水位线 |
| `LLM_GATEWAY_HISTORY_MEMO_SHARED_MAX_WRITES_PER_HOUR` | 500000 | 本进程每小时写入上限 |

指标：`history_guard_memo_{local_hits,shared_hits,misses,shared_errors,shared_writes,shared_skipped,breaker_opens}_total`、`session_context_reduce_duration_seconds{parallel,outcome}`、`session_context_reduce_messages{outcome}`。**命中率 = (local_hits + shared_hits) / (三者之和)**，直接就是「省掉了多少次守卫计算」。

### 2.4 暂存目录空壳（上一轮登记的 L1）

大请求先以每请求一个 uuid 的暂存身份落盘（`gw_staging_<uuid>`），解析出真实会话后 `Rebind` 过去。`Rebind` 此前只删 `ref.json` / `raw.json`，留下 `gw_staging_<uuid>/large-v1/requests/<reqid>/` **四层空目录**，每个大请求一份，从不清理（211 实测一晚 1800+ 个）。

修法：rebind 成功后删掉**暂存身份自己的四层**，到暂存会话目录为止。边界：只对暂存身份做（它的目录是这一个请求私有的；非暂存身份的会话目录可能有并发 Capture）；不碰共享的分片/租户目录——即使此刻恰好是空的（并发 Capture 正往里建目录时删掉它们会让那次 Capture 失败）；`os.Root.Remove` 只删得动空目录 ⇒ 任何一层还有别的东西就在那一层停下。

## 三、实测

量具：合成会话 7,849,303 字节 / 3213 条（中英混排、思考块、工具调用），规则＝211 导出的 21 条历史规则（3 个规则组）；守卫的构造与 `PatternDetector.HistoryGuard` 的返回值同构。「追加一轮」＝旧消息逐字节不变、末尾追加一条新的 user 消息——这是每一轮的真实形态。

| 形态 | 211 真机（32 核，带线上流量，nice 10） | 本机（负载 70~160，仅看形态） |
| --- | --- | --- |
| 线上现状：串行 + 无缓存 | **1.85s** | 2.6~3.2s |
| 冷缓存 + 串行（第一轮） | 1.47s | 2.0~3.1s |
| **冷缓存 + 并行（第一轮）** | **0.42s** | 0.8~1.6s |
| 热缓存 + 串行 | 0.28~0.30s | 0.34~0.48s |
| **热缓存 + 并行** | **0.10s** | 0.14~0.16s |
| **追加一轮 · 线上现状** | **1.87s** | 2.4s |
| **追加一轮 · 热缓存 + 并行** | **0.097s** | 0.15s |

- 热缓存时 3212 条历史全部命中，一次未命中为 0。
- **输出逐字节相同**：8 种形态的归约输出 SHA-256 与各自请求体的「串行 + 无缓存」基线全等（`3bd3055a5f0426b0…` / `fc04f2e08e35f36c…`），且 macOS 与 Linux 两个平台一致。
- **有序窗口没有吞吐代价**（211 受控 A/B，两个二进制交替 3 轮）：热并行 95~99ms（有序窗口）vs 93~102ms（不限窗口），整轮耗时相同。
- 量具入库：`go test ./security/sanitize/ -run '^$' -bench ReduceWithHistoryGuard -benchtime 3x`（只用仓内规则文件与合成会话，不依赖外部数据）。

## 五、本轮自查抓到的问题（全部在提交前）

这一轮「测试抓测试」的密度很高，按发现顺序记下来——每一条都是「量具先红、结论后改」：

1. **M1 首轮是绿的**：「返回最小下标错误」这个规则只在**相邻条目都出错**（都落在在途窗口里）时才起作用，而首版测试里两个出错条目离得很远——第一条出错后装载就停了，第二条根本不会被处理。⇒ 补相邻出错的两条测试。
2. **属性测试 8 个种子里 3 个在空转**（seed 2/5/7 的请求体没超过测试预算 ⇒ `Reduce` 原样返回，「串行 vs 并行」只是在比「什么都没做」）。是加了「必须触发归约」的覆盖断言才抓到的。⇒ 生成器保证请求体 ≥ 320KB。
3. **计数型窗口的上界推理是错的**：先实现的是「未完成条目数 ≤ 2×workers」，自以为出错后至多再装载 2×workers−1 条；实测装载了 902 条——出错的那条还在队列里没被处理，别的名额被后面的条目**循环**占用（装载→瞬间完成→归还名额），装载方就能一直往前走。⇒ 改成**有序窗口**（第 i−window 条完成才能装载第 i 条）。
4. **有序窗口的变异首版抓不到**：不加 `-race` 时出错的协程几乎立刻被调度，装载量靠运气也没超上界 ⇒ 测试自己控制节奏（出错条目睡 20ms 再报错）。
5. **测试自己的守卫有数据竞争**（`CancelMidWay` 后半段手写的守卫用普通计数器 `seen++` 却声明 8 个并行协程）——`-race` 抓到。产品代码没问题：产品规则就是「守卫可并发才能并行」。
6. **M7 的测试是空转的**：把假数据放在了键 `[1]` 下，而包装后的守卫查的是 `verdictKey(策略, 消息)` 推导出来的键，根本没读到它。⇒ 重写为直接命中坏值。
7. **`Store` 在「只有本地层」时空指针**（改默认值时把提前返回改丢了）——如果就这样上线，默认配置下**每一次未命中都会 panic**。现有钉测当场抓到。
8. **`strconv.ParseBool` 不认 `off`**：首版 `LLM_GATEWAY_HISTORY_GUARD_MEMO=off` 根本关不掉缓存 ⇒ 显式列全「关」的拼法并钉测。
9. **共享层默认开的取舍**：原设计默认开（TTL/预算/水位）——复审时意识到三道保护都是防「写太多」，没有防「Redis 卡」⇒ 补熔断 + 默认改关。
10. **暂存清理首版会一路向上删空目录**：正常情况下祖先非空会自然停下，但在几乎没有归档的机器上、叠加并发创建的极窄窗口，理论上可能删到共享的祖先目录 ⇒ 收紧到「暂存身份自己的四层」并用 M9 钉住。

另：本机负载均值 70~160（10 核）时基准完全不可用——同一个二进制的基线在 1.45~3.24s 之间乱跳，首版本机 A/B 因此得出「有序窗口慢 2 倍」的假结论（基线 A 在两个二进制之间就差 2 倍，而 A 的代码两边相同）。A/B 挪到 211 才得到可信结论。

## 六、登记

- **L1 热缓存的真实命中率取决于客户端是否逐字节重发历史**：本轮量的是合成会话（旧消息逐字节不变）。真实客户端（ZCode 等）大多数会稳定序列化，但缓存标记位置移动、工具结果裁剪等都会让少数消息的字节变化。⇒ 以线上指标为准：`history_guard_memo_local_hits_total / (local_hits + misses)`。**活体验证的 6 分钟窗口内线上没有出现 >1MB 的多条消息会话 ⇒ 真实命中率尚无样本**，需要过一段时间再看。
- **L2 第三步「分段摘要 + 分层合并」待 owner 拍板**：会改变模型看到的内容。抽取式（逐段保留与当前任务最相关的句子，再合并）零额外成本、可逐字节复现；LLM 生成式摘要更省 token 但引入额外调用、延迟与「摘要丢信息」的风险。
- **L3 候选被永久性原因挡空时 503 → 4xx 待 owner 拍板**（上一轮 L6）：多数 SDK 对 5xx 自动重试，永久性原因换 4xx 可止损无效重试，代价是监控口径从 5xx 挪到 4xx。
- **L4 热并行仍有约 0.1 秒**：剩余成本是读归档（两轮各读一次）、逐条哈希、`sampleTextWords` 的 JSON 解码——都在装载方协程里串行。单遍装载 + 逐条结果缓存可再降，但收益已小，未做。
- **L5 共享层未在生产启用**：默认关，只有单测（miniredis）覆盖；多实例 active-active 上线前建议先在一台机器上开着观察 `history_guard_memo_*`。
- **L6 211 上存量的暂存空壳目录有 318,201 个**（远超上一轮「一晚 1800+」的估计——是一个分片目录 `session-archive/default/gw` 里 53.5 万个条目中的 31.8 万个）：代码修复只管新产生的（活体验证 5 笔请求后数字不变）。存量清理是在生产归档目录里删东西，**等 owner 点头**；下面这条命令只删「60 分钟前创建、且整棵树里没有任何文件」的暂存目录里的**空目录**（`-type d -empty -delete` 碰不到文件）：

  ```bash
  cd /opt/kaixuan/data/llm-gateway/data/session-archive/default/gw
  ls -U | grep '^gw_staging_' | while read -r d; do
    [ -n "$(find "$d" -maxdepth 0 -mmin +60 2>/dev/null)" ] || continue
    [ -z "$(find "$d" -type f -print -quit 2>/dev/null)" ] || continue
    find "$d" -depth -type d -empty -delete
  done
  ```
- **L7 失败 / 未绑定的大请求在暂存目录保留完整 RAW 归档**（上一轮 L1 的另一半，本轮未查）：这些目录非空，不属于「空壳」，本轮的清理不会碰它们。

## 七、通用式

1. **「纯函数结果每轮重算」是大会话最便宜的提速点**——先问「这段计算的输出只由什么决定」，答案是「不可变的输入」时就缓存它的输出，键里带上全部输入（这里是策略 key）。
2. **并行的正确性标志不是「结果一样」而是「结果一样 + 出错语义一样」**：串行在下标最小的错误处返回，并行必须显式复现这一点；而「最小下标」规则只在**相邻条目同时出错**时才起作用，测试要打在那里。
3. **「出错后不再做」要做成有上界的性质，不要做成「大概会停」**：计数型窗口挡不住循环占用，窗口必须有序；而这类性质靠调度碰运气是测不出来的，测试要自己控制节奏（让出错的那条慢下来）。
4. **属性测试要断言「被比较的路径真的被走到」**：请求体没超预算 ⇒ 归约原样返回 ⇒ 比的只是「什么都没做」。覆盖断言抓到了 8 个种子里的 3 个。
5. **变异之后测试仍绿，先问三件事**：变异打上了吗（`grep -c`）？测试碰到被变异的那行了吗（M7：假数据放错了键）？这条性质是不是本来就靠调度（M8）？
6. **可选组件的默认值按「不启用时的代价」定**：共享层的增量收益只有「部署后第一轮少 0.6 秒」，而它把 Redis 的健康拉进请求路径 ⇒ 默认关；启用时「防写太多」（TTL/预算/水位）与「防后端卡」（熔断）是两类保护，缺一不可。
7. **基准先看基线稳不稳**：同一份代码的基线在两个二进制之间就差 2 倍 ⇒ A/B 结论作废；本机负载 70+ 时一切数字都不可信，换机器。
8. **删空目录的清理逻辑要写明「删到哪一层为止」**：靠「祖先非空会自然停下」在几乎为空的机器上不成立；边界要显式，并用「越界」的变异钉住。
