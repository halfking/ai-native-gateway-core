## 二、逐项

### 2.1 ① `session_summary_dim` 的退役语义（头号项）

**缺陷本体**：`internal/sessionv2mirror/session_summary_dim.go:121` 有一道门
「`storage.request_logs_write_enabled` 为 true ⇒ 整体 no-op」。它当年是**双喂防护**
（v1 停写前 `_request_logs_hot` 上的 `trg_update_session_summary` 还在计数）。
门要成立需要**两个事实同时为真**：① 有 v1 写入方往 `_request_logs_hot` 落行；
② 该触发器还存在。**两个都已随 v1 族退役消失**：

* ① PG 侧 v1 写入分支已从 `domains/hooks/observability/telemetry/client.go` 整段删除
  （两处 insert/update 路径都在注释里写明「v1 族退役后写它必然 42P01」）；
* ② 890 物理删除了 v1 族、两个触发器与 `update_session_summary()` 函数
  （真库实测：`pg_trigger` 上零触发器、`pg_proc` 里无该函数、`pg_class` 里只剩
  `request_logs_with_current_month` 这个视图）。

⇒ 门不再是「双喂防护」，而是**纯粹的停摆开关**：把退役开关拨到 true，
`session_summaries` 的聚合**静默停写**——而本写入器是这些聚合列的**唯一写方**
（其余写方只碰 `title` / `summary` / `key_topics` / `user_intent` / `handoff_*` /
`archived_at` 等旁列，已逐个核对）。后果是用户面（admin 会话列表/详情、会话分析、
`usage_enhanced` 意图列）在新会话上**永远不出现**，且**无日志、无错误**。

**改法**：门删除，聚合**无条件**写入。等价性不靠「相信前提」，而是**把前提变成持续可见的事实**：

| 门 | 判据 | 变异臂 |
|---|---|---|
| `TestSessionSummaryDimWriter_IgnoresRetiredV1Switch`（静态） | 源文件的**可执行代码**不得出现 `RequestLogsWriteEnabled(` / `KeyRequestLogsWriteEnabled` / 引号包起来的键字面量 / `settings.` | M1 塞回退役开关门 ⇒ 红 |
| 同上门第二颗牙 | `UpsertSessionDim` 在 `w.pool.Exec` **之前**只允许 2 个 `return`（entry 空 / pool nil）⇒ **任何**门都会被抓住 | M2 塞一扇与退役开关无关的门 ⇒ 红 |
| `TestSessionSummaryDimWriter_NoV1TriggerPremise`（真库） | `session_summaries` 上零触发器、v1 族关系不存在、`update_session_summary()` 不存在 | M3 真库挂一个触发器 ⇒ 红 |

★ **静态门要剥注释**（本轮又踩了一次）：判据落在**语句**上，文件头的注释必须能自由
讨论「这道门为什么被删」（含开关名）⇒ 否则这道门会逼着作者闭嘴。
`stripCommentsAndStrings` 把注释与字符串剥掉再判。

### 2.7 ⑦ `/api/admin/turns` 的 hot 臂反连接

**缺陷本体**：`public.session_turns_with_current_month` 的 hot 臂带一个**相关反连接**，
而**相关子查询的内侧拿不到外层谓词** ⇒ 内侧 Append 遍历**全部**月分区，
每个分区按 `(tenant_id::text)` 索引定位后**扫该租户的全部索引项**、再用
`Filter: request_id` 过滤 ⇒「每 hot 行扫该租户全部索引项」（R181 §5.5 的原话）。

**★ 本轮推翻了自己的第一个假设**：先试「把反连接里的 `::text` 去掉 ⇒ 规划器就能用
`(tenant_id, request_id, partition_date)` 唯一索引」。**实测不成立**：
两表 `tenant_id` 都是 `character varying`，PG 会把 varchar 比较**一律归一**成
`::text` 形态 ⇒ 索引选择与 buffer 数**逐项相同**（A 360 buffers / B 362 buffers）。
⇒ 「去 cast」不是这轮的杠杆。

**★ 真正的杠杆是「把分区窗口推进反连接的内侧」**（只有两腿形态能写自己的反连接）：
内侧 Append 裁到窗口所在的 **1 个分区**，反连接从「每 hot 行一次嵌套循环 × 5 分区」
变成「一次性扫描窗口分区」。

真库 A/B（**用真实生成的 SQL**，24h 窗口）：

| 形态 | 计划 | buffers |
|---|---|---|
| 改前（视图形态） | Limit → Incremental Sort → Merge Append → … → Nested Loop Anti Join × **5 分区** × N loops | **145** |
| 改后（两腿形态） | Limit → Sort → Append → Nested Loop Anti Join（内侧 **1 个分区**的索引探测） | **59** |

★ **等价性**：内侧加 `partition_date` 界后，反连接只问「窗口内的父表分区里有没有
同键行」。它与视图（全分区）的差别**只可能**来自一种数据形态：**同一个
`(tenant_id, request_id)` 出现在父表的两个不同 `partition_date` 上**。三条依据说明
正常路径不产生这种行：晋级路径**逐字保 `partition_date`**
（`promote_session_turns_hot_to_partition` 的 `INSERT … SELECT` 取 `h.partition_date`）；
写路径的幂等探针 `ExistsByKeySQL` **不带分区界**；父表唯一键含 `partition_date`。
⇒ 该前提**当场可测** ⇒ 真库门 `TestTurnsListTwoLegs_NoCrossPartitionDuplicateKeys`
持续检验（本地实测：0 个跨分区同键行）；前提破了 ⇒ 那道门当场报红 ⇒ 必须把内侧的界
拿掉，而不是让差异静默发生。

另配**等价门**（真库）：同一 `REPEATABLE READ` 快照内，视图形态与两腿形态读出的
行集**逐行相等**（本地实测通过）；**形状门**：不得引用视图、两腿齐全、谓词落在臂内部、
反连接内侧必须带分区界（带阳性对照）。

★ **本地执行时间**：0.25 ms → 0.66 ms（两腿形态丢了 Merge Append、改成整体 Sort）。
本地只有 2806 行 ⇒ 绝对值无意义；**收益在缩放性质上**（视图形态的成本随
「hot 行数 × 每租户索引项 × 分区数」增长；两腿形态的内侧是一次扫描）。

### 2.8 ⑧ 写路径计划缓存

`db/db.go` 重新开启 pgx 语句缓存（`QueryExecModeCacheStatement`），带杀开关
`LLM_GATEWAY_DB_STATEMENT_CACHE=false`。

★ **★ 本轮更正了 R181 的读数**：R181 记的是「写路径每请求 29.8 ms 规划时间」。
本轮实测把它拆开后发现，**那 38 ms 里绝大部分是冷启动成本**（首次访问这些分区的
目录/统计），**不是**稳态的每次规划成本：

| 模式 | 首执行 | 稳态 20 次平均 |
|---|---|---|
| `CacheStatement` | 34~44 ms | **0.72 ms/次** |
| `SimpleProtocol` | 34~44 ms | **2.19~3.02 ms/次** |

⇒ 首执行在两种模式下**相同** ⇒ 那 38 ms **不是**「缓存省掉的规划」；
缓存真正省掉的是**稳态每次 1.5~2.3 ms**（本地 4.2×）。
⇒ R181 的 29.8 ms 若成立，成立在**别的维度**（252 的目录/统计规模更大 ⇒ 每次规划更贵
⇒ 缓存省下的绝对值更大）⇒ 本轮**不否认**生产侧的收益，但**拒绝**把冷启动成本
算进缓存的功劳。

★ **四条安全依据**（逐条查证，不是推断）：

1. **pgx 在任何错误上失效该语句的缓存**（`vendor/…/pgx/v5/conn.go:519-528` 的
   `defer`：err ⇒ `sc.Invalidate(sql)`）⇒ 陈旧语句失败一次之后重新准备；
2. **迁移期不产生预编译语句**：网关进程内的迁移链全是**无参** SQL ⇒ pgx 对无参语句
   强制走 simple protocol（`conn.go:513-515`）⇒ 迁移期**从不 prepare**；
   SQL 文件迁移由安装器/部署序列执行，不在本进程内；
3. **迁移结束 `pool.Reset()`** 丢弃全部连接（连同它们的缓存）⇒ boot 期 DDL 不残留；
4. **运行期 DDL 只动分区** ⇒ 父表的缓存语句由 PG **自动重规划**（plan invalidation），
   不是报错。

★ **真库 DDL 门**（两条真实形态）：

* **DROP + 同名重建** ⇒ 缓存语句**照常可用**（PG 按依赖 OID 失效并重规划）——
  这是运行期最常见的 DDL（分区增删）；
* **RENAME** ⇒ 必然 42P01（2026-07-15 的事故形态）⇒ 门断言的是
  **连接没有被毒化**：出错之后同一条连接上别的语句照常可用。

★ **门必须走生产同一条构造路径**（`newPoolConfig`）：若门自己起池并硬编码执行模式，
「把生产配置改回 SimpleProtocol」这个变异**不会让门变红** ⇒ 门变成恒绿的摆设。
⇒ 本轮为此把池配置构造从 `Open()` 里抽成 `newPoolConfig()`。

### 2.9 ⑨ 详情路径两阶段化

`admin/logs.go` 的 `getLog` 详情路径原本是
`SELECT … FROM <source> <5 个维度 JOIN + 2 个 LATERAL> WHERE … ORDER BY rl.ts DESC LIMIT 1`
⇒ LIMIT 写在 JOIN **之后** ⇒ planner 必须先为每个候选行跑完 JOIN，再排序取 1 行
⇒ **LIMIT 没有减少 JOIN 的工作量**。

**改法**：阶段一在**不 JOIN** 的源上定位唯一一行（只取 `request_id`），
阶段二再拿这一行的 JOIN 结果 ⇒ JOIN 只发生 **1 次**。
★ **等价性**：JOIN 全是**行保持**的（维度表按 id 的 LEFT JOIN + 两个
`LEFT JOIN LATERAL … LIMIT 1`）⇒ 同一 `rl` 行的 JOIN 结果与「先排序取 1 行再 JOIN」
逐字相同 ⇒ 阶段二按 `request_id` 定位到**同一行**（`request_id` 是该族的行身份）。

实测（真库，同一个 `request_id`）：

| 阶段 | 计划 | 耗时 / buffers |
|---|---|---|
| 改前（单条） | Limit → Sort → **Nested Loop Left Joins** → Append | 0.48 ms / **65** |
| 阶段一（无 JOIN） | Limit → Sort → Append | **0.09 ms / 16** |
| 阶段二 | 与改前的 JOIN 段相同（只作用于 1 行） | — |

★ **诚实结论**：本地候选行 = 1（`request_id` 精确命中）⇒ **总体持平**
（多一次扫描与一次 RTT，收益接近 0）；收益出现在**候选行 > 1** 时
（`client_request_id` 腿、谓词放宽）。**结构上** LIMIT 现在确实先于外层 JOIN 生效。
★ 视图**内部**的 `session_turn_details` JOIN 仍在视图臂内 ⇒ 两阶段化**管不到**它。
