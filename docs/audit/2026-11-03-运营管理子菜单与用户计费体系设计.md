## 0. 摘要

### 0.1 用户的诉求拆成三件事

1. **把运营能力收进一个新子菜单「运营管理」**：运营策略（含套餐设定）、价格设定、市场价格采集、对比分析、活动/套餐/计费手段。
2. **补齐商业闭环**：用户与租户**选套餐 → 充值 → 计费 → 结算账单**。
3. **从用户角度补齐自助视图**：每个用户能看到**请求历史、充值、费用、结算**。

### 0.2 必须先说的一件事：**这套商业骨架已经在仓里了，但几乎是空的**

本轮把网关的商业相关表全查了一遍（真库读数）：

```
subscription_plans          3      ← 套餐定义（已存在）
topup_packages              3      ← 充值档位（已存在）
tenant_credit_wallets       9      ← 租户钱包（已存在）
billing_orders              3      ← 充值/订阅订单（已存在）
maas_monthly_bills          3      ← 月账单（已存在）
maas_credit_consumption_buckets 266 ← 消费桶（已存在）
────────────────────────────────────────────────
tenant_subscriptions        0      ★ 没有人订阅过套餐
maas_coupons                0      ★ 没有一张券
maas_coupon_redemptions     0
maas_invoice_requests       0      ★ 没有一张发票申请
maas_reconciliation_findings 0     ★ 没有一条对账结论
model_credit_rates          0      ★★ 零售价表是空的 ⇒ 所有模型都在按全局默认值计价
credit_ledger               0      ★★ 积分流水是空的 ⇒ 「我的消费/我的账单」没有底账
maas_settings               1 行   alipay_account 空、wechat_mch_id 空、stub_qr 空
                                  ⇒ ★★ 支付通道一个都没配
```

⇒ **结论（本方案第一判断）**：**「运营管理」这一节的第一件事不是做页面，是先把「价 → 扣 → 记 → 账单 → 对账」这条链跑通一次真实闭环。**
现在 `model_credit_rates` 空 ⇒ 零售价全靠 `maas_settings` 的全局默认（`base_credits_per_1m=600` / `out=1500` / `global_discount=0.82` / `cents_per_credit=0.01`）；
`credit_ledger` 空 ⇒ **用户看不到自己被扣了什么**；
支付通道未配 ⇒ **充值单创建了也付不掉**。
⇒ 若先做菜单与页面，这一节上线后就是**一排空表 + 一排空页面**，比不做更伤信任。

### 0.3 一句话给决策者

> **商业骨架（套餐/充值包/钱包/订单/账单/券）全部已存在，缺的是「填上值」与「把散在五个菜单里的入口收成一节」；而用户侧最缺的那一块——按人维度的消费与结算——数据维度其实早就在了（`api_key_owner_user`），只是没有对外开放。**

### 1.5 ★★ 一个必须避开的混淆陷阱

**`/admin/subscription-tiers`（「订阅层级」）与商业套餐完全无关。**

实测（`web/src/views/SubscriptionTiersView.vue:1-13`）：它读的是 `GET /api/admin/tiers` —— **nginx 反代到 `license-authority` 独立 service 的跨仓端点**，返回 `code/name/description/price_cents/sort_order/module_keys`，作用是**许可证档位与模块授权**，视图层明确写「不参与授权判断，前端仅呈现已就位数据」。

⇒ 它**恰好也叫「订阅」「层级」「也有 price_cents」**，是最容易被误当成「套餐管理」而错误合并/迁移的一个。**必须显式分开。**

### 1.6 本轮实测到的两处「半接线」

1. **`model_credit_rates` 空 ⇒ 零售价不存在**。`maas/model_rates.go:101` `effectiveModelRates` 会回落到全局 base（`maas/rates.go:42-73`）：`base_credits_per_1m=600`（输入）/ `1500`（输出）/ `global_discount=0.82` ⇒ **所有模型同价**。真实售价只能通过 `manual_*` 标志逐模型覆盖。
2. **`credit_ledger` 空 ⇒ 积分流水不存在**。`maas/consumption_detail.go:116-119` 的毛利是从 `_request_logs.cost_usd` 反查的（**上游成本**，不是积分流水）⇒ 「用户被扣了多少积分」这件事，**当前无处可查**。

## 2. 信息架构：「运营管理」子菜单

### 2.1 设计原则

| # | 原则 | 理由 |
|---|---|---|
| O1 | **一节两态**：同一组 `operations`，平台运营看到「设定面」，租户看到「消费面」 | 仓内 `NavItem` 已支持按角色过滤（`super` / `platformOps` / `tenantOnly` / `hideForTenant`，`appNav.ts:263-272`），无需两套导航 |
| O2 | **入口只搬不改语义**：迁移过来的页面 **path 不变** | 避免破坏收藏链接、避免孤儿路由门变红 |
| O3 | **收编而非新建**：先合并已有入口，再谈新页面 | 现状是 12 个入口散在 3 组 |
| O4 | **每个入口都要能回答一个运营问题** | 不能回答问题的页面不进这一节 |
| O5 | **用户侧只暴露「自己的」** | 租户隔离由 PostgreSQL RLS 承担（51 条 `tenant_isolation_*` 策略），新表必须带策略 |

## 3. 业务模型设计

### 3.1 套餐（`subscription_plans` 扩展）

现状只有「月费 ＋ 月度积分」两个数，**不够卖**。按扩展列（**加列，不改既有语义**）：

| 新增列 | 含义 | 为什么必须有 |
|---|---|---|
| `billing_period` | `monthly`/`quarterly`/`yearly`/`one_time` | 现状 CHECK 只有 tier，年付/季付表达不了 |
| `quota_credits` | 周期内含额度 | ★ **现状 `tenant_subscriptions.quota_remaining` 有「剩余」却没有「总额」定义** —— 额度从哪来没写 |
| `overage_price_cents` | 超额单价（每 N 积分） | 「套餐用完了怎么办」是运营最常被问的问题 |
| `effective_from` / `effective_to` | 生效窗 | 新套餐/旧套餐并存要有依据 |
| `auto_renew` | 是否自动续费 | 续费工单量最大的来源 |
| `concurrency_limit` | 并发上限 | 套餐分档的主要技术差异 |
| `sla` | 承诺（响应时间/可用性） | 对客承诺需要可写、可查 |
| `overage_allowed` | 是否允许超额 | 与 `overage_price_cents` 联动 |

**子表 `subscription_plan_entitlements`**（新）：套餐内含的**按模型额度**（行业务刚需：某套餐含 claude-opus 免费 N 积分）。
```
plan_id · canonical_id · included_credits · overage_multiplier · notes
```

### 3.2 充值（`topup_packages` 扩展 ＋ `billing_orders` 打通）

`topup_packages` 加：`bonus_credits`（**充值赠送** —— 商业最常用的钩子）/ `effective_from` / `effective_to` / `min_amount_cents` / `max_amount_cents` / `first_time_only`。

**支付链路要正视现状**：`maas_settings` 的 `alipay_account` / `wechat_mch_id` / `stub_alipay_qr_url` / `stub_wechat_qr_url` **全空**，而 `billing_orders.payment_channel` 的 CHECK 允许 `{alipay, wechat, manual}`。
⇒ **设计取舍**：**短期以 `manual`（人工确认收款）为主路径**（`handleAdminMaasOrder` 的「确认收款」已经存在），把 `alipay`/`wechat` 在 UI 上**显式标为「未开通」**，而不是留一个点了没反应的选项。
⇒ 长期再接真实渠道（届时 `qr_payload`/`qr_url` 字段已就位）。

### 3.3 活动与权益（`maas_coupons` 只是其中一种）

**现状的 `maas_coupons` 只是一次性额度券**（code / credits_amount / max_redemptions / expires_at），**不是活动引擎**。运营要的「各种活动」至少 5 类，需要一张活动表 + 规则：

| 活动类型 | 语义 | 兑现方式 |
|---|---|---|
| 新用户赠送 | 首次开通送额度/送券 | 发放到 `granted_balance` |
| 充值赠送 | 充 100 送 20 | 发放到 `granted_balance` |
| 限时折扣 | 期间内按量打折 | 计入 `model_credit_rates` 的临时覆盖 ＋ 生效窗 |
| 套餐升级/降级 | 周期中换套餐，按比例补差价 | 订单 `order_type` 扩展 |
| 推荐返利 | 推荐人/被推荐人双向返 | 券 ＋ 台账 |

**新表 `promotion_campaigns`**：
```
code · name · type∈{new_user_gift,recharge_bonus,limited_discount,plan_change,referral}
rule jsonb · starts_at · ends_at · status∈{draft,active,paused,ended}
priority · stackable · per_tenant_limit · created_by · created_at
```
**新表 `promotion_redemptions`**：`campaign_id · tenant_id · owner_user · order_id · benefit jsonb · created_at` ⇒ 活动效果可归因、可对账。

★ **一条不可省的设计约束**：**每一笔因活动而发的额度，都必须有一条 `credit_ledger` 记录，且记录里带 `campaign_id`** ⇒ 否则「活动送了多少」「这个月活动成本多少」永远算不出来。

### 3.4 计费手段

**已有的三层**（不要重造）：
1. **上游计费模式**：`credential_model_bindings.billing_mode` ∈ `{per_token, token_plan, code_plan, monthly, free}` ＋ `pricing_plans.plan_type`（`pricing_plans` **284 行**，有数据）⇒ 决定**我们的边际成本**（`router_scoring.go:335-358` `calculateCostPenalty` 按 billing round 判 0/1）。
2. **零售计价**：`model_credit_rates`（**空**）＋ `maas_settings` 全局 base ＋ `global_discount` ＋ `maas/rate_periods.go` 的**峰谷倍率**（周期时段，非 DB 时间版本；SQL 侧镜像函数 `maas_resolve_rate_multiplier()`，迁移 736）。
3. **积分换算**：`maas_settings.cents_per_credit`（0.01 分/积分）。

**要补的计费手段**（按运营诉求排序）：
- **按租户/按用户的折扣与承诺量阶梯**（`tenant_model_rates` / `tenant_discounts`）—— 现状只有全局 `global_discount`，**没有分层折扣**。
- **按 API Key 的配额与封顶**（防止一个 Key 跑爆整个租户）。
- **最小消费 / 预付费 / 后付费**（`billing_orders` 只有一次性充值与订阅，**没有后付费月结**）。
- **超额与欠费策略**（`overage_allowed` ＋ 欠费降级到哪个套餐）。
- **单价展示双口径**（积分 ＋ 人民币），见 §4.2。

### 3.5 结算与对账

**已有**：`maas_monthly_bills`（租户月账单）、`maas/reconcile.go:23` `ReconcileTripartite`（A 消费桶 / B 月账单 / C 积分流水，**三方对账**）、`maas_invoice_requests`（发票）、`maas_reconciliation_findings`（对账结论）、`/api/admin/report-rollup/*`（供应商/内部双视角聚合 ＋ xlsx 导出）。

**要补**：
- **三方对账要真跑起来**：`credit_ledger` 空 ⇒ C 侧永远对不上 ⇒ `TripartiteOK`（`maas/reconcile.go:65`）永远不成立。⇒ **先补流水，再谈对账**。
- **第四方：市场参考价**（接上一轮方案 §5 的 `market_price_reference`）⇒ 变成「我方成本 vs 市场价 vs 客户实付」四方对账 —— 这是**发现「我们卖亏了」的唯一定期机制**。
- **按人对账**：见 §4.3。

### 4.3 ★ 关键结论：「按人」不需要新数据模型

实测三处证据链：

1. **`_request_logs` 有 `api_key_owner_user` / `owner_user` 列**（`sql/schema/01-schema.sql:3759,3785,3811` 的投影、`:5202`/`:5372` 的列定义）。
2. **`maas/consumption_detail.go:63` 已在投影 `api_key_owner_user`，`:91` 已有 `AND alias.api_key_owner_user = $3` 的过滤，`:95` 的 GROUP BY 已含它** ⇒ **按人聚合与按人过滤都写好了**。
3. **`web/src/api/maas.ts:418` 的 `getAdminMaasConsumptionDetail(tenantCode, days, ownerUser)` 已把 `ownerUser` 作为参数暴露**。

⇒ **用户级消费/结算＝「加一个租户可见的端点 ＋ 一个页面」，不是「建一套模型」。**
唯一缺的是**鉴权收窄**：让租户侧只能查**自己**（`owner_user` = 当前登录用户），租户管理员可查全租户。⇒ 靠 RLS（`get_current_tenant()`）＋ 显式的 `owner_user` 归属校验。

### 4.4 用户体验要点（便捷性设计）

1. **单位双口径**：每个金额都同时给 **积分（计费口径）** 与 **人民币/美元（理解口径）**。客户算不清积分就没法跟公开的 MaaS 报价比。⇒ 复用 `maas_settings.cents_per_credit` ＋ `currency_display`。
2. **四层下钻必须闭合**：**账单 → 用量 → 请求 → 单次明细**，四页共用一套筛选器（时间范围 / 模型 / API Key / 用户），互相可跳转。★ 现状只有前三层的零散片段，**闭合路径不存在**。
3. **可解释**：每笔扣费能追到「模型单价 × token 数 × 折扣 × 峰谷倍率 × 是否活动」⇒ 需要 `credit_ledger` 的 `detail jsonb` 记下这五个因子。
4. **导出**：CSV/XLSX（已有 `/api/maas/bills/export` ＋ `exportMaasBillsCSV`），用量与请求明细也要（租户常见诉求是「拿给财务」）。
5. **空状态必须友好**：★ 当前 `model_credit_rates` ＝ 0 ⇒ **所有价格页都是空的**。仓内已有 `i18n:empty-state:check` 门 ⇒ 空状态文案要走 i18n，且要给出「为什么空 + 下一步做什么」。
6. **充值不能是死路**：支付通道未配 ⇒ 「充值」按钮要么跳「联系客服/对公转账」，要么走 `manual` 人工确认流。★ **不能留一个点了没反应的按钮**。
7. **预算与告警**：余额低于阈值、额度即将耗尽、套餐即将到期 —— 三种提醒要有落点（站内/邮件/企微）。仓内 `notification` 域存在（`domains/notification/`，已见 `email.go` / `dingtalk.go`）⇒ 可复用。

⇒ **判定**：现有列**够表达「入账/扣减 ＋ 关联单据 ＋ 池归属 ＋ 扣后余额」**（`entry_type`/`ref_type`/`ref_id`/`pool`/`balance_after` 都在）⇒ **不是要重建表**。

| 缺列 | 对应哪个交付能力 | 不加会怎样 |
|---|---|---|
| **`owner_user`** | §4.2 的「每个用户看自己的账」 | 只能按租户算，**按人算不出来** |

### P3 · 商业化增强
