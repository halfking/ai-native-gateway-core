#### 指纹（211 真库，2026-11-17 01:09 CST）

⇒ 这 478 行只有一种解释：**绑定被"恢复"了，但恢复动作清不掉冷却地平线**（`unavailable_recover_at` 是过期残留；`available/reason/unavailable_at` 已被清空 ⇒ 没有任何"它曾经坏过"的痕迹）。

#### 三个机制（缺一不成立）

**① 凭据级归因会把一个模型的故障放大成整凭据的地平线**
`domains/credential/writer.go:SetCredentialUnavailable`（凭据级归因）对**该凭据的全部绑定**写同一组值：
`available=false, unavailable_reason='auto_credential_'||kind, unavailable_at=now(), unavailable_recover_at=$2, updated_at=now()`。
同一事务 ⇒ **全凭据共享同一个 `unavailable_at` 与同一个 `unavailable_recover_at`**。
⇒ 211 实测：凭据 99031 的 **266 条绑定**在 `2026-11-06 08:37:48.164211+08` 被一次性写成
`available=false / reason='auto_credential_quota_permanent' / unavailable_recover_at=08:38:18.164211`（＝`now()+30s`）。

**② 镜像恢复走视图 ⇒ 触发器根本不回写冷却地平线**
`model_offers` 是 `credential_model_bindings JOIN provider_models` 的视图，带 INSTEAD OF UPDATE 触发器
（211 上 `model_offers_update_trigger()` 函数体实测）：触发器的 SET 列表里有
`available / unavailable_reason / unavailable_at / admin_protected / … / updated_at`，
**唯独没有 `unavailable_recover_at`** ⇒
**任何「UPDATE model_offers SET available=true, unavailable_reason=NULL, unavailable_at=NULL」的恢复动作，都会把绑定恢复成可用，却把冷却地平线原样留在行上。**
★ 本仓**早就知道这件事**：`credentialhealth/checker.go` 的注释写着「the INSTEAD OF UPDATE trigger does NOT propagate that column to cmb, so writing it here would be silently dropped」——
当时的处置是**绕开**（不写那一列），而不是修触发器 ⇒ **缺陷被固化成契约**。

**③ ★ 三值逻辑陷阱：被镜像恢复过的行，从此再也进不了唯一会清地平线的那条语句**
唯一会清 `unavailable_recover_at` 的是 cmb 侧恢复语句（`credentialhealth.RecoverExpired`），守卫写着
`AND cmb.unavailable_reason <> 'model_probe_broken'`。
**SQL 三值逻辑：reason 为 NULL 时 `<>` 求值为 NULL ⇒ 整行被排除。**
而**②的镜像恢复恰恰把 reason 清成 NULL** ⇒
⇒ **被镜像恢复过的行，从此再也进不了这条语句 ⇒ 它的 `unavailable_recover_at` 永远清不掉 ⇒ 地平线永久残留。**
⇒ 这是一条**随镜像恢复次数单调累积**的漂移来源（今天 289 行，下个月更多）。

**④ 孤儿绑定：两条恢复语句双盲 ⇒ 永久卡死**
cmb 侧恢复语句原本带 `FROM provider_models pm WHERE pm.id = cmb.provider_model_id`（内连接）——
它改的是 cmb 自身，join pm **毫无语义用途**，却把**父行已被删除的孤儿绑定**整类挡在恢复之外；
model_offers 侧（视图同样是内连接）也看不到它们 ⇒ **双盲**。
211 实测：**45 行孤儿绑定**（3 个凭据），其中 **32 行 `available=false`**，reason 全是 `auto_credential_quota_permanent`
⇒ **靠自动恢复永远救不回来**。

### D3 ★★★ 降级有守卫、恢复没守卫 ⇒ **过期失败复活健康节点**

* 恢复侧 `bg/node_probe_write_through.go:40` 有新鲜度守卫
  （`COALESCE(cmb.unavailable_at,'epoch') <= $3::timestamptz`）；
* 降级侧 `bg/node_probe.go:3988-4001`、`domains/credential/writer.go:589-601` **没有等价守卫**；
* 而 `cmb.available` 的**恢复源有 5 条**（`credentialhealth/checker.go:539` RecoverExpired、`bg/credential_recovery.go:1227` recoverExpiredBindings、`:1350` recoverFreshDegradedBindings、`bg/credential_autoheal.go:68` dueAutoHeal、`writer.go:135` + `node_probe_write_through.go:24`），

## 三、三类新报错定案

### #30 / #33 `request cannot produce a valid bounded context; split the protected input`（422）

入口：`domains/streaming/large_ingress.go:166-185`
```go
if ref.Size > largeMemoryThreshold {
    body, report, err = sessioncontext.Reduce(prepCtx, g.store, ref, g.config.ContextBytes)
    if err != nil {
        status, code := 422, "context_budget_exceeded"
        message := "request cannot produce a valid bounded context; split the protected input"
```
根因：`internal/sessioncontext/fit.go:18-91` 的 `Fit` 保留「**受保护区**＝首个任务 ＋ 全部特权指令 ＋ 完整的最新 user/tool 组」；
`fit.go:64-67` 判据是「受保护区本身 > 1MiB 预算」⇒ `ErrProtectedContext` ⇒ 422。

★ 与 r1051/r1052/r1053（媒体 / tool_calls 帽 / opus 半窗帽）**同族但不同形态**：
那三轮修的是「**可压缩的历史**里有畸形块导致整个 Reduce 失败」；
本轮形态是「**受保护区本身就装不下**」⇒ **客户端无法 split**（历史里的任务/指令/最新工具组不是客户端能拆的）⇒ **会话砖化**。
⇒ 处置方向：**受保护区超预算时不能只回 422**，需要给出可行动的出路（把超出部分显式省略并标注，或按模型窗口降级为「仅保留当前轮」），否则同一个 TraceID（`hydrate-trace`＝会话持续重放）会永远失败。

### #32 / #33 `request preprocessing exceeded its time limit`（503，`retryable=true`）

同一入口的另一个分支：`prepCtx` 是 **120s 超时**（`large_ingress.go:133`），`Reduce` 超时 ⇒
`errors.Is(err, context.DeadlineExceeded)` ⇒ 503 `request_processing_timeout`。

★ **`retryable=true` 在这里是误导**：这是**入口层拒绝，网关根本没走到路由**（没有上游可换）⇒
客户端拿到的 503 重发**同一个 1MB+ body**，只会再超时一次（而且 120s 的预处理期间一直占着 ingress 槽位）。
⇒ 真正该做的：① 让 Reduce 在预算内收敛（媒体/工具链已做，还差别的形态）；② 明确告知客户端「需要分片」而不是「可重试」。

### #31 `Response blocked by output policy (rule=builtin.guard.tool_json_invalid)`（403，`retryable=false`）

定案：`builtin.guard.tool_json_invalid` 是**格式类守卫**（`security/sanitize/output_sensitive.go:237-249`）：
「工具参数**本身**不是合法 JSON ⇒ 无法在结构上做脱敏/判定 ⇒ fail-closed 阻断（**非内容规则命中**）」。

★ 顺带一条队列观察：211 上 `sanitize_block_reviews` 里最多的不是它，而是
`builtin.guard.capacity_exceeded`（**2104 条**，近 48h 143 条）—— 那是**守卫缓冲越界**的**降级放行**单
（响应照常返回、只留痕），不是拦截；按 2026-10-30 的口径它本就该是遥测而非待决单，
却仍挂着「待审」状态与批准按钮（放行表无消费方）⇒ 管理面噪声的最大来源。

★ 211 取证：该规则的**拦截审核单共 32 条，最后一条是 2026-11-15 20:46，此后为零**
⇒ 2026-11-15 的「格式类守卫收口轮」（`domains/streaming/policy_block_feedback.go:118-127` 的 `isFormatGuard`）
**已经把「生成审核单 ＋ 误报『内容含敏感信息』」修好了**（owner 报障里那句「审核单 rv-1989」属于该修复之前的形态）。

★ **但「不可重试」仍然存在**，这就是 owner 说的「简单的错误应该可以重试，解决不了」：
`domains/streaming/executors/output_policy.go` 的 `outputPolicyError` 此前**只认 `error.code`，丢掉了 `error.rule`** ⇒
执行层只拿到一个裸的 `errorsx.ErrOutputPolicyBlocked` ⇒
**「内容策略拦截（终态）」与「上游输出畸形（可换兄弟节点重试）」被压成同一个 `KindContentFilter`** ⇒ 终态、不可重试、`retryable=false`。
⇒ 本轮修复（见 §四）。

AND (

## 五、通用式（本轮沉淀）

1. **「组件齐全」≠「链路能跑」**：判定标准是「谁调用了它」。`model_probe.go` 的双向 reconcile 在 new 模式下读的是**冻结表**，却仍在改新栈 —— 组件在、语义已死。
2. **写面和读面必须同键同口径**：`v_routable_credential_models` 用「退避中」判不可路由，路由用「连败≥3」判 ⇒ 两者天生不一致 ⇒ 8.1% 的节点两套结论。
3. **降级与恢复必须对称**：恢复有守卫、降级没有 ⇒ 过期失败能复活健康节点；降级即时、恢复排队 ⇒ 抖动。
4. **多写者必须共享一份名单**：`isFormatGuard` 一份在 `domains/streaming`、执行层拿不到 ⇒ 执行层把「格式错」和「内容敏感」压成同一类 ⇒ 简单错误不可重试。名单要下沉到**所有层都能 import 的低层包**。
5. **失败分类丢失元数据＝语义降级**：`outputPolicyError` 只认 `code` 不认 `rule` ⇒ 规则名在非流式面整段丢失 ⇒ 后续所有基于规则名的处置全部失效。
6. **「可重试」要有物理边界**：格式守卫可重试，但**已提交过字节的响应不可重放** ⇒ 判据必须落在「客户端是否已收到字节」这个可观测事实上。
7. **人工意图是最高优先级状态**：运维手工下线（`paused` + `manual_offline`）不得被任何自动路径（探针成功、业务成功）抹掉 —— 三条腿必须同一口径。
8. **审计报告里的每个数字都要可复现**：本档所有数字都来自 `scripts/audit/q-211-readonly-sql.sh` 的可重跑 SQL，且标注了观测时点。
9. ★ **三值逻辑是 SQL 守卫的默认形态**：`<>` / `=` 与 NULL 相遇时求值为 NULL ⇒ 行被**静默排除** ⇒
   「守卫越严、实际命中越少」，而症状是**「恢复不生效」而不是报错** ⇒
   **凡是要「不排除某类行」的守卫，一律 `COALESCE` 化**（本轮：289 行残留就是这一条）。
10. ★ **视图的 INSTEAD OF 触发器是一张「字段白名单」**：视图暴露的列 ≠ 触发器能回写的列 ⇒
   **对视图写的每一列都可能被静默丢弃** ⇒ 镜像写必须逐列核对触发器的 SET 列表；
   而「知道了却绕开」（本仓旧注释的选择）= **把缺陷固化成契约** ⇒ 根治要落在触发器本身（P8）。
11. ★ **内连接是「静默过滤器」**：给自身 UPDATE 加一个**语义无关**的 JOIN（如 cmb UPDATE join provider_models），
    会把某类行（父行已删的孤儿）整类挡在修复之外，而且**没有任何报错** ⇒
    自表 UPDATE 上的 JOIN 一律先问「它参与过滤了吗」。
12. ★ **降级与恢复必须对称到「同一批列」**：降级写 6 列、恢复只写 3 列 ⇒ 残留列永远清不掉 ⇒
    **残留列就是漂移的载体**（本轮：`unavailable_recover_at`）。
13. ★ **「没人再探它」与「它永远回不来」互为因果**：探针停了、凭据被永久摘了，两个状态各自看都合理，
    合起来就是一个**永不自愈、也不被观测**的节点（凭据 99031）⇒ 审计「永久态」时必须同时问「谁还在看它」。
14. ★ **钉测必须能证明「旧行为过不了」**：本轮 F3 的真库腿内置了**负控**（拿修复前的旧 SQL 对**独立重放**的同款夹具跑一遍 ⇒ 清不掉地平线、恢复不了孤儿）
    ⇒ 否则「绿」只是因为断言写得太松。
    ★ 负控必须**独立重放**：复用已被生产路径改过的夹具 ⇒ 负控变成在断言「已经修好的状态」⇒ 恒绿。
15. ★★ **两个测量面可能测的不是同一批对象**：探针面（探针自己挑的通道）与业务面（业务实际命中的通道）
    在同一时刻可以是「0.3%~9% 成功率」与「95.4%~98.7% 成功率」⇒ **两个结论同时成立**。
    ⇒ **口径必须写清楚「测的是谁」**；用探针成功率代表「模型可用性」会把「上游坏了」与「池子结构坏了」混为一谈。
16. ★★ **复核对不上的第一嫌疑是「自己的旧口径」，不是「数据变了」**：
    本轮用业务侧时间轴复核 owner 报障 ④，**推翻了上一轮自己的「别名归一」归因**（那是放大器不是起因）
    ⇒ 审计结论必须能被**另一条独立数据源**（探针 vs 业务）交叉验证，否则就是单口径自证。
17. ★ **「唯一健康通道被周期配额关掉」是供给侧事件，代码层看不见**：
    凭据级 `availability_state='suspended'` + `availability_recover_at`（周期窗口）是**设计内**行为，
    但当池子里**只剩这一条**健康通道时，它就等价于「整个模型不可用」⇒ **需要供给侧告警**（P13），不能只靠看板看单凭据状态。
