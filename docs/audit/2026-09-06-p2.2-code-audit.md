### ✅ P1-3: 导出记录自动清理 — 已修复

**位置**: `sql/migrations/startup/663_training_export.sql`

**修复内容**:
添加PostgreSQL函数`cleanup_stale_training_exports()`，自动清理超过24小时仍在running状态的记录。

```sql
CREATE OR REPLACE FUNCTION cleanup_stale_training_exports()
RETURNS INTEGER AS $$
DECLARE
  affected_rows INTEGER;
BEGIN
  UPDATE training_exports
  SET status = 'failed',
      error_message = 'Export timed out or process crashed (auto-cleanup)',
      duration_seconds = EXTRACT(EPOCH FROM (NOW() - created_at)),
      completed_at = NOW()
  WHERE status = 'running'
    AND created_at < NOW() - INTERVAL '24 hours';
  
  GET DIAGNOSTICS affected_rows = ROW_COUNT;
  
  IF affected_rows > 0 THEN
    RAISE NOTICE 'Cleaned up % stale training export records', affected_rows;
  END IF;
  
  RETURN affected_rows;
END;
$$ LANGUAGE plpgsql;
```

**使用方式**:
- 在gateway启动时调用（推荐）
- 配置为定时任务（例如每小时执行）

**验证**: ✅ Migration语法正确

## 延后优化（P2-2）

### P2-2: SQL过滤优化 — 延后到下一个sprint

**位置**: `exporter/training_exporter.go:458-483`

**问题描述**:
Parquet writer (`pw`) 在创建后没有使用`defer`保护，如果在写入循环中发生panic或某些错误路径，writer可能不会正确关闭，导致：
- 文件未正确flush，数据丢失
- goroutine泄漏（ParquetWriter使用4个goroutine）
- 文件句柄泄漏

**当前代码**:
```go
pw, err := writer.NewParquetWriter(fw, new(TrainingDataRecord), 4)
if err != nil {
    return 0, fmt.Errorf("create parquet writer failed: %w", err)
}

// 写入记录
for _, rec := range records {
    if err := pw.Write(rec); err != nil {
        pw.WriteStop()  // ⚠️ 如果WriteStop也失败，没有保护
        return 0, fmt.Errorf("write record failed: %w", err)
    }
}

if err := pw.WriteStop(); err != nil {
    return 0, fmt.Errorf("write stop failed: %w", err)
}
```

**修复方案**:
```go
pw, err := writer.NewParquetWriter(fw, new(TrainingDataRecord), 4)
if err != nil {
    return 0, fmt.Errorf("create parquet writer failed: %w", err)
}
defer func() {
    if err := pw.WriteStop(); err != nil {
        slog.Error("failed to stop parquet writer", "error", err)
    }
}()

// 写入记录
for _, rec := range records {
    if err := pw.Write(rec); err != nil {
        return 0, fmt.Errorf("write record failed: %w", err)
    }
}
```

**影响**: 高 — 在高负载或错误情况下可能导致资源泄漏。

### P1-2: 空数据集边界条件缺失

**位置**: `exporter/training_exporter.go:230-280` (Export函数)

**问题描述**:
如果查询返回0行数据（例如时间范围内没有数据，或质量过滤过于严格），代码仍然会：
1. 创建Parquet文件（即使是空文件）
2. 插入导出记录到数据库（row_count=0, status=completed）
3. 消耗I/O和数据库资源

这会导致：
- 无意义的空文件堆积
- 导出历史记录混乱（成功但无数据）
- 浪费存储空间

**当前代码**:
```go
// queryRecords返回空切片时，直接调用filterRecords和dedupRecords
filtered := e.filterRecords(records, qualityFilters)
deduped := e.dedupRecords(filtered, dedupStrategy)

// 即使deduped长度为0，也会写入Parquet文件
rowsWritten, err := e.writeParquetFile(deduped, result.OutputPath, "snappy")
```

**修复方案**:
```go
// 查询后检查
if len(records) == 0 {
    return nil, fmt.Errorf("no records found in time range %s to %s",
        config.TimeRangeStart.Format("2006-01-02"),
        config.TimeRangeEnd.Format("2006-01-02"))
}

// 去重后检查
if len(deduped) == 0 {
    return nil, fmt.Errorf("no records after quality filtering and deduplication (filtered: %d -> %d)",
        len(filtered), len(deduped))
}
```

**影响**: 中高 — 导致运维混乱和资源浪费。

### P1-3: 导出执行记录未使用事务

**位置**: `exporter/training_exporter.go:195-220, 250-260`

**问题描述**:
导出过程涉及两次数据库写入：
1. `createExportRecord()`: 创建初始记录（status='running'）
2. `updateExportStatus()`: 更新最终状态（status='completed'或'failed'）

如果在第2步之前进程崩溃或数据库连接断开，会留下永久处于`running`状态的记录，导致：
- 导出历史记录不准确
- 监控指标失真（成功率计算错误）
- 需要手动清理"僵尸"记录

**当前代码**:
```go
// 1. 创建导出记录（独立事务）
exportID, err := e.createExportRecord(ctx, configID, outputPath)

// ... 执行导出 ...

// 2. 更新状态（独立事务）
if err := e.updateExportStatus(ctx, exportID, "completed", ...); err != nil {
    return nil, err
}
```

**修复方案**:
使用数据库事务或增加自动清理机制：

**方案A（事务）**:
```go
tx, err := e.db.Begin(ctx)
if err != nil {
    return nil, err
}
defer tx.Rollback(ctx)

// 创建记录
exportID := createInTx(tx, ...)

// 执行导出
result := export(...)

// 更新状态
updateInTx(tx, exportID, result)

// 提交
tx.Commit(ctx)
```

**方案B（自动清理 - 推荐）**:
保持当前设计，但添加后台清理任务（在migration中）：
```sql
-- 每小时清理超过24小时仍在running的记录
CREATE OR REPLACE FUNCTION cleanup_stale_exports()
RETURNS void AS $$
BEGIN
    UPDATE training_exports
    SET status = 'failed',
        error_message = 'Export timed out or process crashed',
        duration_seconds = EXTRACT(EPOCH FROM (NOW() - created_at))
    WHERE status = 'running'
      AND created_at < NOW() - INTERVAL '24 hours';
END;
$$ LANGUAGE plpgsql;
```

**影响**: 中 — 不影响正常流程，但会导致运维问题。

### P2-2: filterRecords可以优化为流式处理

**位置**: `exporter/training_exporter.go:335-410`

**问题描述**:
当前实现是全量加载到内存后再过滤，对于千万级数据集可能导致内存压力。

**优化建议**:
将过滤逻辑移到SQL WHERE子句中：
```go
// 当前：在Go代码中过滤
records := queryAll()  // 1000万行
filtered := filterInMemory(records, filters)  // 可能只剩100万行

// 优化：在SQL中过滤
query := buildQueryWithFilters(filters)  // WHERE confidence >= 0.7 AND ...
records := queryFiltered()  // 直接返回100万行
```

这样可以减少网络传输、内存使用和CPU开销。

**实施复杂度**: 中（需要重构SQL构建逻辑）
