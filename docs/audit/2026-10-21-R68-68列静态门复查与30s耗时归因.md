### §2.3 ⚠ 本门**已知**的覆盖边界（门自己写了，这里复核确认）

- 粒度是**逐条 SQL 字面量** ⇒ 跨字面量拼接（`strings.Join`）的形状看不见
  ⇒ 由真库门 `TestCredentialHeatmapSQL_ExecutesOnRealDatabase` 互补；
- **无限定**列引用在**多关系**字面量里**跳过**（归属是 PG 的解析问题，不是本门能判的）
  ⇒ `bindsToView` 的 `relCount == 1` 分支；
- 清单的口径是「**当前族的物理独有列**」⇒ **不覆盖**其它 `session*` 表（会话摘要/意图/附件…）
  的列；实测那些表有 244 个「不在视图契约」的列名**不在**清单里
  ⇒ ★ 但那些列若被 view-sourced 查询引用，**别名解析**会让它们绑定到**别的表**（不是视图）
  ⇒ 本门按设计不报 ⇒ **不是漏报，是另一个语义**。

## §3 ★★★★ 「30s 耗时」归因（并推翻挂账的两处记错）

### §3.1 读数（一次性库 `itgate_r68_coord` 作为 `TEST_PG_DSN`）

```
$ go test ./db -count=1
--- FAIL: TestRequestLogsCurrentMonthViewEnsureRoundTrip (30.29s)
    request_logs_view_schema_test.go:385: canonical view column count = 0, want 10 (base 7 + customer_id + request_class + due_at)
--- FAIL: TestRequestLogsViewV2EnsureMatchesMigration (13.14s)
    view_schema_v2_contract_test.go:366: derive clone DDL from live catalogs: table public._request_logs not found in live catalogs
FAIL  github.com/kaixuan/llm-gateway-go/db  44.523s
```

⇒ ★★★ **推翻点 1（测试名）**：**30.29s 的是 `TestRequestLogsCurrentMonthViewEnsureRoundTrip`**
（`db/request_logs_view_schema_test.go:252`），
**不是**挂账四轮都在写的 `TestRequestLogsViewV2EnsureMatchesMigration`（实测 **13.14s**）。
⇒ ⇒ ★ **挂账把「30s」记在了错的测试上** ⇒ 这就是它连续四轮「归因未做」却总找不到 30s 的原因。

⇒ ★★★ **推翻点 2（包名）**：两条都在 **`db/`**；
`domains/session/v2` 内 **0 命中**（该包有 339 个测试函数）⇒ **包名也记错了**。

### §3.2 ★ 30s 到底花在哪 ⇒ **不是性能问题**

`TestRequestLogsCurrentMonthViewEnsureRoundTrip` 的 30s = **夹具 setup**：
建 scratch 库（`CREATE DATABASE … TEMPLATE template0`）→ 在里面**手工造 v1 形态**
（`_request_logs_hot` / `_request_logs` + 列）→ 跑 `ensureRequestLogsCurrentMonthView`
→ 校验视图列数。
⇒ ★ **ensure 本身是毫秒级的** ⇒ ⇒ **30s = 建库 + 造表的成本**，
**不是** ensure 慢、也不是「退化成 30s 的性能回归」。

★ ⇒ **R60 记的「耗时从 0.52s 变成 30.17s」也随之被解释**：
那是**同一个测试**在不同形态下的**失败位置**变化
（早失败 = 0.52s；走完 setup = 30s）⇒ **不是性能变化，是「它走到了哪一步」的变化**。

### §3.3 ★★★ 两条测试各自怎么死的（**不同的死法**）

**（A）`TestRequestLogsCurrentMonthViewEnsureRoundTrip`** —— 死法：**断言与产品现状矛盾**

- ensure 的现行形态（`db/request_logs_view_schema.go:40-95`，v4 / 890 期）：
  canonical 视图**只剩 session 两臂**；**会话族缺席时没有可退的形态 ⇒ 不做任何 DDL**；
- 实测日志原文（本次运行）：
  ```
  WARN request_logs_with_current_month missing; self-healing the session-only view (mirror of …885_drop_v1_request_logs_family.sql)
  WARN request_logs_with_current_month: session_turns absent and the v1 family is retired (890) — no fallback body to install; leaving the view as-is
  ```
- ⇒ 夹具造的是 v1 形态、会话族不在 ⇒ **ensure 什么都不做** ⇒ 视图列数 **0**
  ⇒ 而断言要的是 **「v1 动态重建形态 = base + 3 列」**（`base 7 + customer_id + request_class + due_at`）
  ⇒ ⇒ ★★ **它断言的是一个 890 之后**不再存在**的产品形态**
  ⇒ ⇒ **改瞄夹具救不了它**：断言本身必须改成「session-only 两臂体」。

**（B）`TestRequestLogsViewV2EnsureMatchesMigration`** —— 死法：**夹具整体退役，但断言仍有效**

- 它的**断言**全是**会话族**形态：
  「ensure must produce the 734 details-joined body」「must compose the 740 client_ip column」
  「must produce the 738 credits_rate_multiplier column」「816/817 的 client_ip 守卫形态」…
  ⇒ ★ **这些断言与今天的 ensure 逐条对得上**（ensure 今天就产出 session-only 两臂体）；
- 但它的**夹具**要从**真库目录**克隆 v1 表（`cloneTablesFrozenDDL`）
  ⇒ 890 之后真库里没有 `_request_logs` ⇒ **红在 setup**；
- ⇒ ⇒ ★ **它的目标没死，死的是「从真库克隆 v1」这个前提** ⇒ **可以改瞄**。

⇒ ⇒ ★★ **两条不能用同一种药治**：
（A）是「**门在守一条已退役的形态**」⇒ 要么退役、要么改断言；
（B）是「**门在守正确的形态，但夹具取不到料**」⇒ 改夹具即可。

### §3.4 ⚠ 处置（**属主决策**，本轮不替属主拍板）

| 选项 | 内容 | 代价 / 风险 |
|---|---|---|
| **A** | **退役 (A)**，把 (B) 的夹具改写成会话族形态 | (A) 的覆盖（冷启动自愈路径）会丢 ⇒ 须先确认 (B) 改完后能覆盖同样的性质 |
| **B** | **两条都改瞄会话族**：(A) 的断言改成「session-only 两臂体 + 118 列」；(B) 的夹具改成在 scratch 里造**会话族**（`session_turns` / `session_turns_hot` / `session_turn_details`）而不是克隆 v1 | 成本高（造会话族 scratch 本身就是那 30s 的量级）⇒ 但**这才是产品今天真正的冷启动形态** |
| **C** | 两条都退役，改由 v4 形态的**专门**新门承担 | 覆盖面需要重新论证 ⇒ 不能默认「旧门覆盖的东西新门也覆盖」 |

⇒ ★ **推荐 B，但需要属主拍板**：它改的是「这两道门还守不守、守什么」，
且 (A) 的断言改写会**改变判据语义**（从「v1 动态重建」到「session-only 两臂体」）。

### §3.5 ★ 诚实边界

1. ⚠ **本轮只做归因与登记，没有改这两条测试的任何一行** ⇒ 它们现在仍然红。
2. ⚠ **第一次读数是我的口径错**：我最初把 `TEST_PG_DSN` 指向 `postgres` 库
   （那里没有 canonical 视图）⇒ 读成「frozen base contract = 0 columns, want 108」
   ⇒ ★ **那是量具指错库，不是产品现象**；换指到装满 295 条迁移的库后才读到真消息
   ⇒ ⇒ **「0 列」有两种完全不同的成因，消息长得几乎一样** ⇒ 归因时必须先确认 DSN 指向的库**有没有那个对象**。
3. ⚠ **「30s」是在本机（16 核、当时 load 56）读到的**；别处会不同 ⇒
   ⇒ **它不是阈值敏感型问题**（断言的是**形态**，不是耗时）⇒ **归因不依赖精确毫秒数**。
4. ⚠ `db` 包**整体**红只有这 2 条（本次实测 `44.523s`，其余全绿）。
