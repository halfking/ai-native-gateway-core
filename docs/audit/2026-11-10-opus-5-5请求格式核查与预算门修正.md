## 2. 缺陷一（请求格式，对照 Anthropic Messages API 内容块闭集）

**OpenAI Responses 的 `reasoning` item 被逐字透传进 anthropic-messages wire。**

- ZCode/AI-SDK 会在 `input[]` 回放前轮 reasoning item（无 role，带
  `encrypted_content`/`summary` 信封）；`parseResponsesInputItem` 无该类型特判，
  落入 unknown-item fallback ⇒ assistant + `raw` 块 ⇒ `serializeAnthropicContentBlock`
  default 分支原样回注 `{"type":"reasoning",...}`；
- Anthropic 合法内容块闭集（官方 Messages API reference）：text/image/document/
  tool_use/tool_result/thinking/redacted_thinking/server_tool_use/
  web_search_tool_result（+ legacy search_result 等）——`reasoning` 不在其中
  ⇒ 上游 400（apiclaude 文案 "Malformed conversation content"）；
- 完美解释全部证据形态：带思考历史的真实会话必 400、无 reasoning 的合成测试全过、
  直连成功（对方自己转换 OpenAI 格式）。
- 佐证：`gemini_raw_replay_e2e_test.go` 早已登记「raw 回注 = 同族 400 风险」，
  本轮在生产引爆。

**修复**（7dabda830）：
- `parse_responses.go`：特判 `itemType=="reasoning"` ⇒ 丢弃 + anomaly（外族思考
  信封在任何 anthropic-messages 上游都不 wire-legal；Anthropic 思考有自己的
  signature 门控）；
- `serialize_anthropic.go`：default 分支纵深防御——raw 解码 type 不在
  `anthropicLegalBlockType` 闭集 ⇒ 降级 text 包裹（schema 合法、信息不丢）；
- 新守护测试 ×2；Gemini raw 回注钉测按其自身纪律显式改判 + 留痕。

## 3. 缺陷二（预算门 × 数据缺口，422 `context_budget_exceeded`）

修复一部署后验证暴露第二层：82ms 内 4 次 failover、**零 upstream 尝试**，
全部候选被**网关本地**预算门拒绝。

- `EnforceContextBudget=true`（main.go 硬编码常开）× 生产 ~90% 模型
  `models_canonical.context_window=NULL` ⇒ `Resolve` 对未知窗口 fail-closed
  （UnknownContext）⇒ NULL 窗口模型全量 422 `input cannot fit the selected
  bucket budget`——与 2979 灾难同根，回滚只是买时间；
- **修复语义**（382e60d6d）：未知窗口 =「无法核实精确窗口」，不是「超预算」。
  `Resolve` 对 `ContextWindow<=0` 回落包级全局保守上限（MaxInputTokens=500k /
  DefaultMaxJSONBytes=8MB）——「绝不当无限」的设计意图保持（全局封顶仍在），
  已知窗口精确算术与 media/uncountable 检查不变；
- 钉测改判 ×5（budget/counter/request/executors×2/compression），均留事故注；
  核心不变量保留：本地拒绝不耗物理尝试、dispatch 映射保真、legacy 零值兼容。

## 附：第三轮（同日追加）——minimax「不行」的三层归因与修复

用户反馈：glm-5.3-flash 可行、minimax 不行；要求大输入合理压缩、不能直接报错；
minimaxcode 仍见 context_budget_exceeded (upstream)。

### 1. fit 字节目标单位混淆（cd3f2a6a）
fitCandidateContextBudget 的字节目标 = min(JSONBytes, InputTokens/2) 把 token
预算当字节：minimax 512k 窗 → 256k-token 预算被压成 128KB 字节目标，ZCode 受
保护区（指令+工具链）放不下 ⇒ ErrProtectedContext ⇒ 压缩机制名存实亡。修 =
InputTokens×3（校准估计器下 bytes≈tokens×3，紧缩后估计 ≈0.86×limit，Check 必过）。

### 2. Redis 环境漂移（部署引擎缺陷，1f66b4bdb）
大请求 503 "session store unavailable"：并行会话的测试 redis
（lgw-mock-only-redis）出现在 docker ps 前列，引擎按扫描顺序选中 ⇒ gateway.env
被改写为凭据不匹配的空 mock ⇒ 网关 auth 失败 ⇒ large-ingress 必走 session 归档
全断。修 = 与 pg_persisted_host 同纪律：redis_persisted_container（gateway.env
的 REDIS_ADDR = 上次绑定）sticky-first，探活复核后复用，mock 抢不走绑定。
部署实证：2988 起 "Redis: wm-acc-chain-redis (复用)" 稳定。

### 3. reasoning 烧光输出预算（c3cca311）
session 修复后归因转向：压缩链全部正常（459KB → 1273 prompt tokens 上行），
但 MiniMax-M3.1 把 max_tokens 全部烧在思考上（finish_reason=length、
reasoning≈completion、零可见输出）⇒ empty_response ⇒ 全候选失败 ⇒ 503。
glm 系无此行为 ⇒ 用户看到的「glm 可行、minimax 不行」。修 = empty 检测处
（budget_exhausted_by_reasoning + finish=length）加倍 max_tokens（≥2048，
cap 32768）同候选免费重试一次（reasoningBudgetBumped 旗标仿
ctxLenRecoveryRetry）；二次仍烧完才走既有 empty failover。

### 4. 验证（211 = 2989/c3cca311，槽 b）
459KB minimax 会话：**200 / 19.9s / 真实内容**；日志链实证 reasoning 加倍
重试命中 1 次。executors 全包 ok；守护测试 ×3（阶梯/端到端/有界性）。

1. nvidia 的 minimaxai 镜像腿（provider 18）当天大面积挂起（60s+ canceled）
