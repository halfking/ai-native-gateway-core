## 二、历史守卫误伤修复

### 2.1 根因

**此前行为**：`HistoryGuard` 只看正则匹配，不走输入面的候选过滤链（`DetectScope`）：
- 只要消息解码文本里含「tokens」「keyboard」「email」等词 ⇒ 整条省略
- 而输入面的真实判据是「候选过滤链」：正则 + 字段选择器 + 叶子值判定 + 范围判定

**211 真实数据对照**（三份真实大请求体拷贝到临时目录 × 线上现行 59 条规则）：
- 7.3MB/8226 条：被守卫省略 735（8.9%）→ 修复后 38（0.5%）
- 7.9MB/3999 条（2026-11-22 超时事故的那场 ZCode 会话）：2285（57.1%）→ 151（3.8%）
- 16.7MB/3276 条：745（22.7%）→ 44（1.3%）

**★ 最严重案例**：7.9MB 会话里 57.1% 的历史被误丢——用户的工具调用结果、助手的完整回复，只要含「tokens left」「keyboard shortcuts」就整条不给模型看 ⇒ 模型失去上下文连贯性。

### 2.2 修法

**核心设计**：守卫以输入面同一份检测主体为准，字段规则维持原行为。

**实现**（`security/sanitize/history_guard.go` + `detector.go`）：
1. **快路径不变**：先看正则（regex-only 规则 + 其它规则的正则部分），未命中直接放行 ⇒ 热路径零开销。
2. **快路径说可能命中后复核**：把已解码文本交给输入面同一份检测主体（`detectPatterns`，从 `DetectScope` 机械抽取）。
3. **字段规则维持原行为**：键名选择器（`$.tool[*].input.password` 等）+ 任意值 ⇒ 守卫直接省略，不复核——输入面对它们按字段上下文 + 叶子值判定，整条消息的解码文本复现不了这个上下文。
4. **复核有 1MB 上限**：超限保守省略（大消息的文本解码成本高，且大消息本身就可能被摘要功能省略）。
5. **复核前按规则必含字面量逐条预筛**：每条规则若有 required literals（如 `email` 规则的 `@`），先 `strings.Contains` 预筛；未命中跳过该规则的正则匹配。7.9MB 会话实测：逐条预筛前 3.7s，预筛后 2.7s。
6. **策略 key 带版本号 2**：`sha256(策略键 + "v2" + 消息字节)` ⇒ 策略一变旧判决自然失效。

**抽取 `detectPatterns` 是纯机械搬移**（diff 仅新增 11 行、零删除）：
```go
// detector.go (新增函数，从 DetectScope 机械抽取)
func detectPatterns(text string, patterns []*CompiledPattern) (bool, string, string) {
    // ... 原 DetectScope 主体 ...
}

// history_guard.go (调用方)
if fastResult {
    text := string(decoded)
    if len(text) > 1<<20 { // 1MB 上限
        return false, nil
    }
    // 逐条预筛
    for _, rule := range filteredRules {
        if !shouldCheckRule(text, rule) {
            continue
        }
        // 调用抽取的检测主体
        if matched, _, _ := detectPatterns(text, rule.Patterns); matched {
            return false, nil
        }
    }
}
```

## 三、分段抽取式摘要

### 3.1 设计

**目标**：给超大会话归约时保留历史精华，让模型看到首/中/尾代表性内容，而不是因为历史太长直接全丢。

**方法**：抽取式（extractive），不是 LLM 生成式（abstractive）：
- **抽取式**：从原文按分数挑行，零额外成本、可复现、不丢信息
- **LLM 生成式**（未采用）：更省 token 但多一次调用且可能丢信息

**pipeline**（`internal/sessioncontext/digest.go`）：
```
原始历史消息
  ↓ 切段（默认 64KB）
  ↓ 每段抽取式摘要（稀有词占比 + 数字/路径/标识符信号 + 人类消息开头句 + 角色权重）
  ↓ 合并保留树结构、按需求比例自顶向下分预算并给每段保底一行
  ↓ 段摘要按内容哈希缓存（下一轮只有新段需要算）
  ↓ 输出：<=16KB 的代表性历史摘要
```

### 3.2 实现细节

**1. 切段**（默认 64KB）
- 按原始字节切，不按消息边界 ⇒ 超大单消息会被切成多段
- 段边界对齐消息边界（尽量不切碎一条消息）

**2. 每段抽取式摘要**（`scoreMessageForDigest`）

**评分维度**：
- **稀有词占比**：TF-IDF 思想，出现次数少的词更有信息量
- **数字信号**：含数字的行（统计数据、版本号、ID）权重 +0.5
- **路径/标识符信号**：含 `/` 或 `_` 的行（文件路径、变量名）权重 +0.3
- **人类消息开头句**：user 消息的前 2 句权重 ×1.5（用户意图集中在开头）
- **角色权重**：user 2.5 / assistant 1.5 / tool_result 0.35（工具结果冗长但信息密度低）

**排序规则**（先按类别再按分数）：
1. 人类消息（user）的行
2. 助手消息（assistant）的行
3. 工具结果（tool_result）的行

**去冗余**（Jaccard 相似度 ≥0.9）：
- 只去掉近乎逐字重复的行
- 阈值取 0.9 而非 0.5~0.8 ⇒ 避免把用户第二次提的要求当成第一次的重复丢掉

**每条消息至多 2 行**：
- 防止单条消息占用过多预算
- 超大消息（>64KB）只留省略标记 `[large message omitted, N bytes]`

**3. 合并保留树结构**（`mergeSegmentDigests`）

**按需求比例自顶向下分预算**：
- 每段按其需求（段内消息总行数）占比分配预算
- 每段保底一行 ⇒ 保证首/中/尾都有名额
- 段内再按分数填预算

**为什么不按分数直接填预算**：按分数填会让内容同构的一段包揽名额，其它段被挤出 ⇒ 失去首/中/尾的代表性。

**4. 段摘要缓存**（`digestCache`）

**缓存键**：`sha256(段内容字节)` ⇒ 下一轮只有新段需要算，旧段直接命中缓存。

**缓存管理**：
- 进程内有界缓存（131072 条、分片、FIFO）
- 只缓存成功的摘要结果
- 缓存不含会话明文（只存摘要结果）

### 3.3 配置与装配

**环境变量**（`cmd/gateway/session_digest_init.go`）：
- `LLM_GATEWAY_SESSION_DIGEST`：默认 `on`；`off`/`0`/`false`/`no`/`disabled` 关闭
- `LLM_GATEWAY_SESSION_DIGEST_SEGMENT_BYTES`：默认 65536（64KB）
- `LLM_GATEWAY_SESSION_DIGEST_BUDGET_BYTES`：默认 16384（16KB）

**接入点**（`domains/streaming/handler.go`）：
- `prepareHistoryGuard` 注入 `WithDigest` 到请求 ctx
- `sessioncontext.Reduce` 在 ctx 里找到 `WithDigest` 即启用摘要

**指标**（`metrics/session_context_reduce_metrics.go`）：
- `session_context_digest_segments_total{cache="hit"|"miss"}`：段缓存命中/未命中次数
- `session_context_digest_bytes`：摘要输出字节数（应 ≤ 预算）
- `session_context_reduce_omitted_total`：被守卫省略的历史条数（新增，此前线上看不见）

### 6.2 活体验证

**为什么必须主动发请求**：新实例只起了 4 分钟时，`digest_bytes_count` 与 `reduce_omitted_total` 都是 0。而且归约只在请求体超过 5 MiB 时发生（`ContextBytes` 默认 `5<<20`；256 KiB ~ 5 MiB 只归档不归约），线上那些 1.9MB 的请求根本不经过摘要。被动等真实流量撞上不可控，所以合成一场受控会话。

**合成会话**（`gen_body.py`，确定性、纯 ASCII，agent 形态）：system + 首条 user + 2,159 对 `assistant(tool_calls) ↔ tool(结果)` + 每 4 轮一条 user + 末条 user = **4,860 条 / 5,507,937 B**。受保护 3 条，进守卫的历史 4,857 条，其中 **4,846 条每条都含修复前会被整条误丢的词**（tokens / tokens left / token count / keyboard / Bearer），另植 **11 条**含 `{"api_key": "sk-fake-…", "password": "fake-passphrase-…"}` 的工具结果，作为「必须被省略」的对照。

**预测值是算出来的**：`gen_body.py` 复刻归约器自己的算术——`protectInfo` 决定哪些受保护、`segmentHistory` 按 eligible 消息的原始字节每 ≥64KB 切一段、`segmentKey` = sha256(版本 ‖ 段大小 ‖ 段内逐条消息哈希)——所以每一项指标增量在发请求之前就有确定的期望值。

**结果**（同一网关进程 seq 3244）：

| 状态 | 段缓存 miss / hit（预测） | 实测 | omitted（预测 11） | 判决缓存 hit / miss | digest_bytes（上限 16384） | 归约耗时 | HTTP |
|---|---|---|---|---|---|---|---|
| 冷（首次） | 83 / 0 | **83 / 0** | **11** | 0 / 4,857 | 16,373 | ≈1.0 s | 上游超时（见下） |
| 同体重发 | 0 / 83 | **0 / 83** | **11** | 4,857 / 0 | 16,373 | 0.11 s | 200 |
| 追加一轮 | 1 / 82 | **1 / 82** | **11** | 4,857 / 2 | 16,365 | ≈0.1 s | 200 |

- **两侧对照成立**：4,846 条含 tokens / keyboard / Bearer 的历史省略 0 条；11 条种植的假凭据字段省略 11 条。
- **压缩**：5.5MB → 发往上游 46.6KB（追加一轮 50.5KB）；响应头 `X-Gw-Context-Reduced: extractive_history`；入口（读体 + 归档 + 归约 + 摘要 + 绑会话）冷 ≈1.6 秒、温 ≈0.7 秒。
- **判决缓存**：追加一轮里的 2 次 miss 正是上一轮的末条 user 与助手回复——它们上一轮受保护，没进过守卫。
- **上游提示缓存**（附带读数，单次样本，不外推）：`cached_tokens` 10,240 / 10,343 与 11,115 / 11,116 ⇒ 归约输出跨轮稳定，上游的提示缓存能接上。
- **临时 key**：两把（id 374、375）用完即吊销，复核 `DELETE 200 → GET 404 → 旧 key 401`。

**冷的那一轮客户端在 180 秒内没有拿到响应体**，原因不在归约。网关轨迹显示入口 ≈1.6 秒就完成了，之后 `glm-5.3-flash` 在 NVIDIA 上先返回 200，但日志写明 `reasoning exhausted the completion budget; retrying same candidate`（`max_tokens: 32` 被推理耗尽，没有产出正文），重试又撞上 120 秒上游超时。同一时段别人的 1.94MB 生产请求（未归约）在同一上游也要 60~144 秒。换成日志实测健康的上游（`minimax-m3.1-flash`，中位 0.9 秒）并放宽 `max_tokens` 之后两轮都是 200。网关侧读数三轮都完整。

### 6.3 生产回归：`POST /api/keys` 全量 500

**发现**：活体验证第一步「铸临时 key」返回 500。网关日志：

```
createKey insert failed | error=ERROR: column "team_id" of relation "api_keys" does not exist (SQLSTATE 42703)
```

**根因**：`83e3c5694`（07:33，「团队层级链落地」）给 `createKey` 的 INSERT 无条件加上 `team_id` 列；加这一列的迁移 057 从未在 211 / 252 / 新装环境应用（投递链缺失，AGENTS.md L22）。`a798423f`（seq 3239）不含该提交，`90d2df96`（seq 3240）起都含 ⇒ **211 自 seq 3240 上线起，每一次经管理端建 key 都失败**。154/245（`8d97cc17`）不含该提交，未受影响。

**影响面**：留存日志窗口内（槽 b `42ae8b70` 09:35→14:26、槽 a `10f24d33` 14:26 起）只有 `GET /api/keys` ×7，`POST` 只有本次验证那一笔。更早的容器日志已随部署轮换消失，所以只能说「留存日志里没有真实用户撞上」，不能说「没人受影响」。

**修法**（零 schema 变更，不预判「团队功能上不上生产」）：

- 个人 key（请求不带 `team_id`）的 INSERT 不引用 `team_id` 列。列默认 NULL 与显式写 NULL 等价，个人 key 从此不依赖迁移 057。
- 团队 key 才引用该列；写入路径原样保留，迁移应用之后照常工作。

**为什么既有测试没拦住**：`h.db` 是具体的 `*pgxpool.Pool`，单测注入不了 pgxmock，此前建 key 的测试都停在 DB 面之前，「落库语句引用了未应用迁移的列」这种缺陷没有任何东西会红。

**补门**：给 `createKey` 的落库面开一个窄注入面 `keyCreateDB`（nil ⇒ `h.db`，与 `teamGuardDB` 同款范式），新增两条行为级钉测，让 pgxmock 按语句形状钉住落库语句：

- `TestCreateKey_PersonalKeyInsertOmitsTeamColumn`：个人 key 语句不得含 `team_id`；
- `TestCreateKey_TeamKeyInsertWritesTeamColumn`：团队 key 语句必须写 `team_id`。

**变异自证 4 臂全部精确报红**：

| 变异 | 报红的钉测 |
|---|---|
| 个人 key 照旧写 team 列（＝生产缺陷本身） | 个人 key 那条：`got 500 "query failed"`，与线上失败形状一致 |
| 个人语句文本重新带上 `team_id` | 个人 key 那条 |
| 团队语句丢掉 `team_id` | 团队 key 那条 |
| 调用点不再追加 team 参数 | 团队 key 那条 |

**线上复核**：部署 `c8289d60a` 后 `POST /api/keys` 返回 200（两次，id 374 / 375，均已吊销）。

## 七、登记

**L1** 热缓存的真实命中率取决于客户端是否逐字节重发历史（缓存标记移动、工具结果裁剪都会让少数消息字节变化）⇒ 真实客户端以线上指标 `history_guard_memo_*` 与 `session_context_digest_segments_total{cache="hit"}` 为准；合成会话的受控读数见 §6.2。

**L2** 守卫修复改变的是「哪些历史消息被保留」：模型会看到更多历史——以前因 tokens / keyboard / token count 这类词被误丢的那些；电话、邮箱、身份证号、带敏感键名的工具参数、真实凭据仍然照旧省略。代价是冷路径第一轮更慢（7.9MB 会话约 2.7 秒）。如线上出现异常可回滚到 `6076df408` 之前的版本。

**L3** 摘要功能默认开启，`LLM_GATEWAY_SESSION_DIGEST=off` 可关闭；关闭时归约输出与此前逐字节相同。

**L4** 去冗余阈值取 0.9（只去近乎逐字重复的行）——0.5~0.8 会把用户第二次提的要求当成第一次的重复丢掉。

**L5** 合并用「按需求比例分预算 + 每段保底一行」——按分数直接填预算会让内容同构的一段包揽名额。

**L6** 211 暂存空目录已清零（第一遍 315,815 个 + 清理链代码回收）；现存 965 个含文件的归档待 owner 定保留期（§4.3）。
