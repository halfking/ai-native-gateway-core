## §0 一句话结论

**R79 把两个最慢的端点从「≥120s / 31.6s」压到「5.0s」，但它在生产读数里暴露了 R79 自己引入的一条【静默的错误数据】路径：**

> 备份摘要的计算需要解压 **5.18GB / 100 个文件**（冷路径 ~48s），
> 而 R79 给端点加了 **5s ctx 预算** ⇒ 计算**必然被截断**
> ⇒ 而 R79 的实现把**截断结果当完整结果缓存**
> ⇒ ⇒ 端点对外说：「**100 个备份 / 5.18GB / 记录数 0 / 会话数 0**」
> —— ★★ **这不是「慢」，是「错」：一个面板看起来正常，数字却是假的。**

⇒ R80 修三件事：**部分结果可识别**、**请求路径不再付解压代价**（后台刷新）、
**每个文件只解压一遍**（源头级消掉 R79 的根因）。

## §2 ★★ 真正的发现：响应体里的**假数字**

发版后取 `degradation/status` 的响应体（154，2827）：

```
backups         {"total_files": 100, "total_records": 0, "total_sessions": 0,
                 "total_size": 5178223189, "date_range": "2026-08-17 to 2026-10-24", ...}
degraded        true
degraded_reason "ttl stats unavailable"
ttl_stats       {"sessions_count": 758873, "session_keys_count": 225310, ...}
```

⇒ ★★ **「100 个备份 / 5.18GB / 记录数 0 / 会话数 0」** ——
**5.18GB 的备份不可能没有记录** ⇒ 这个 `0` 是**假的**。

### §2.1 机制（三步，代码级可复算）

1. `admin/degradation_control_handlers.go`（R79）给端点加了 **5s ctx 预算**；
2. `domains/dbdegradation/file_reader.go` 的 `GetBackupSummary` 里
   - `GetFileSummary(ctx, ...)` 失败 ⇒ **只 `slog.Warn` 然后 `continue`**
     ⇒ 该文件的记录数**按 0 计**，**且没有任何错误上抛**；
   - `fr.ReadRecords(ctx, ...)` 的**返回值被直接丢弃**（R80 之前）
     ⇒ ctx 截断时「跨文件唯一 session 集合」也被静默低估；
3. 计算结束后**无条件写缓存**（`summaryCache`）⇒
   ★ **被截断的结果被当成完整结果缓存** ⇒ 之后 5 分钟内的每个请求都拿到这份假数据。

⇒ ★ **「有缓存」把一次偶发的截断，变成了 5 分钟的持续错误数据。**

⇒ ★ 而 `degraded_reason` 只说了 **ttl**（Redis 那条腿）⇒
**备份腿的截断在响应里完全不可见** ⇒ 前端无从判断「这 0 是真的 0 还是假的 0」。

### §2.2 为什么 48.9s 那一次没被预算拦住

`ReadRecordsWithStats` 的打捞路径**会**检查 `ctx.Err()`（`file_reader_salvage.go:128`），
但 `salvageGzipMembers` 的**整段 member 解码**期间不检查 ⇒
⇒ 大文件的解压**可以在 ctx 过期后继续跑完** ⇒ 那一次请求用了 48.9s 才返回。
⇒ ★ **「ctx 预算」只在能被检查的粒度上生效** ⇒ 大文件的整段解码是「不可中断区」。

## §3 R80 的三条修法

### §3.1 ① 部分结果必须**可识别**（不再有「假的 0」）

* `computeSummary` 新增**失败计数**：`GetFileSummary`/`readFileSummary` 出错 ⇒
  **计入 failed**；`ReadRecords` 的错误**必须接住**（旧实现直接丢弃）；
* failed > 0 ⇒ 返回 `(summary, partial=true, err)` ⇒
  **缓存条目带 `partial` 标记** ⇒ 调用方据此 `error` ⇒ 端点标 `degraded`；
* `admin` 侧：备份腿出错 ⇒ `degraded=true` + `degraded_reason` **点名 backup**，
  且**部分摘要照样返回**（前端能显示「部分值」，但**必须**同时有降级标记）。

### §3.2 ② 请求路径不再付解压代价（后台刷新）

* 备份摘要的重算要解压 5.18GB（~48s）⇒ **装不进 5s 预算**
  ⇒ **请求路径绝不付这个代价**：
  - 缓存命中 ⇒ 直接返回（毫秒级）；
  - 缓存过期 ⇒ **触发后台刷新**（单飞 `summaryRefreshing`），请求**立即返回旧值**；
  - 缓存里是**部分结果** ⇒ 同样触发后台刷新去补完整版；
  - 冷启动（无任何缓存）⇒ 就地算（可能不完整 ⇒ **报错**）。
* 摘要缓存 TTL = **30min**（`summaryCacheTTLDefault`）⇒
  稳态 CPU ≈ 48s / 30min ≈ **2.7% 单核**（而不是每次请求都付 48s）。

### §3.3 ③ 每个文件只解压一遍（源头级消掉 R79 的根因）

★ R79 只是把「解压两遍」**缓存掉了**；R80 把它**消掉了**：

* 新增 `readFileSummary(ctx, filename) (*BackupFile, map[string]struct{}, error)`
  ⇒ **一趟**解压同时产出「文件元信息 + 记录数 + **该文件的 session id 集合**」；
* `computeSummary` 用这个集合求并集 ⇒ **不再需要第二遍 `ReadRecords`**
  ⇒ 摘要计算成本**减半**；
* ★ **口径不变**：并集 ≠ 各文件求和（门禁用**旧实现（两趟）作对照**逐字对拍）。

## §7 ★★ 顺带查实的**工装缺陷**（与 R80 无关，但比 R80 更危险）

★ 本轮发版时（2827）从部署日志里看到：

```
/Users/niuer/workspace/ai-native-tools/deploy-lib/db-changelog.sh: line 255: declare: -A: invalid option
[db]  无 pending startup 迁移；checksum ledger 校验通过
```

⇒ ★★ **在 macOS bash 3.2 上，`deploy-lib/db-changelog.sh` 的 pending 迁移计算是【空跑】的**：

* `_deploy_pending_startup_migrations()` 第 255 行 `declare -A applied=()`
  在 bash 3.2 上**失败**（`declare: -A: invalid option`）；
* 该函数在 `set -euo pipefail` 下 ⇒ **在那一行直接退出**（函数返回非 0）
  ⇒ ⇒ **`pending` 列表恒为空** ⇒ ⇒ 日志恒打印「无 pending startup 迁移」
  ⇒ ⇒ ★ **那是【空集读数】，不是「算出来是空」**；
* ⇒ ★★ **后果**：**任何从 macOS 发起的发布会静默跳过 pending 迁移**，
  而日志看起来一切正常（本次侥幸无害：真值 pending 确实 = ∅，
  已用**独立复算**逐条对拍确认，见 §8.2）。

⇒ 复现（bash 3.2 实测）：

```
$ bash -c 'set -euo pipefail; f(){ local -a a=(); declare -A b=(); echo REACHED; }; f; echo OK'
declare: -A: invalid option
exit=2                      # ← 「REACHED」从未打印 ⇒ 函数在这里死了
```

⇒ ★ **修法方向**（**未实施**，在仓外 `deploy-lib`）：把两处 `declare -A` 换成
**数字键的普通索引数组**（`applied[$((10#$line))]=1` 已是数字键 ⇒ bash 3.2 语义等价）
⇒ ⚠ 需注意 `_deploy_validate_pending_migration_versions` 里的 `seen["$ver"]`
用的是**字符串键** ⇒ 索引数组下 `08x`/`09x` 会被当**八进制** ⇒ 必须写成 `seen[$((10#$ver))]`。
