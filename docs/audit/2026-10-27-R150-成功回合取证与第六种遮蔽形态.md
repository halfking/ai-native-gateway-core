## §2 ★ 自我推翻 ①：「调宽 `error_probe.timeout_ms` ⇒ node 探针不再判死慢模型」**不成立**

**做法**：本地 `PUT /api/admin/settings/error_probe.timeout_ms = 60000`（上限）⇒ 读回
`{"source":"db","value":60000}`（`settings_kv` 落库，`value_type=int`）⇒ **重启网关**
（该键 `HotReload=false`，启动时读取）。

**结果**：★ **无效**。原因是**两条执行路径**：

```
settings.ErrorProbeTimeoutMs()            cmd/gateway/main.go:4547
   ├─► bg.NewActiveProbeExecutor(..., epTimeoutMs)   main.go:4586   ← 唯一真正的消费者
   └─╳► bg.NewNodeProbeWorker(...)                    main.go:4682/4946  ← 不接收超时参数

bg/node_probe.go:558/569/573   Timeout: 30 * time.Second   ← ★ 硬编码字面量
```

⇒ ★★ **「可配置的超时」与「真正执行探针的那个超时」不是同一个量。**
⇒ ⇒ **D9 细化**：D9 不是「把 30 s 调大」，而是「**node 探针的超时预算要不要可配**」，
且在它可配之前，**任何「调宽设置就能救活慢模型」的说法都是错的**。

## §4 ★ 自我推翻 ③：`v_routable_credential_models` **不是**路由器的唯一真值源

**实测**（本地 PG）：探针退避过期后，

```
credential_id=2, raw_model_name='z-ai/glm-5.3-flash'
  v_routable_credential_models.is_routable = t      ← 「可路由」
  但客户端请求 = 503 no_candidate                    ← 「不可路由」
```

**根因**：路由器在 `v.is_routable = TRUE`（`provider/client.go:1900`）**之外**还有一道排除：

```
provider/client.go:1926 / 2686  brokenPairExcludeSQL("mps", ...)
   FROM v_node_probe_state_compat mps   （internal/probemode/probemode.go:47 GuardStateTable）
   WHERE mps.state = 'broken_confirmed'
```

而 `v_node_probe_state_compat.state` 的口径（视图定义）：

```sql
WHEN consecutive_failures >= 3 THEN 'broken_confirmed'
```

⇒ ★★ **`broken_confirmed` 没有时间界** ⇒ 探针退避过期（`next_retry_at <= now()`）
**并不能**让该对重新可路由；必须先有一次**成功**的探针把 `consecutive_failures` 打下来。
⇒ ⇒ ★ **R149 的「三层遮蔽链」要补第 4 层**（见 §9 的 D2 扩展）。
⇒ ⇒ ★ **「门控必须与被测系统同源」这条通用式要再收紧一格**：
**「同源」= 路由器**判定**的那张视图 + 那几道排除**，不是「那张看起来像的视图」。

## §6 ★ 第六种遮蔽形态：**上游 200 + 预算被推理吃光 ⇒ `empty_response` ⇒ 注定重试 ⇒ 503 `model_not_found`**

### 6.1 现象（实测，请求 `106a971487ad4cf8becd0b98ee7eff25`）

```
upstream_http_attempt  attempt=0  latency_ms=37754  upstream_status=200
executor: non-stream empty response, failing over to next candidate   status=200
request_flow  kind=empty_response  action=switch_node  reason=empty_response_candidate_failover
upstream_http_attempt  attempt=0  latency_ms=21173  upstream_status=200   ← ★ 同一 body 重来
upstream_http_attempt  attempt=0  latency_ms=19150  upstream_status=200   ← ★ 又重来
goal_retry_exhausted  last_error="all 3 candidates failed: [empty_response] upstream returned empty response (zero content): <nil>"
http_request  status=503  error.message="No available provider for model 'deepseek-v4.1-flash'. All 3 candidates failed."
```

### 6.2 机制（决定性实验）

同一模型、同一提示词，只改 `max_tokens`：

| `max_tokens` | HTTP | content | reasoning | completion |
|---|---|---|---|---|
| **1024** | **503** | **空** | 1024（吃满） | 1024 |
| **8192** | **200** | 640 字符 | 6725 | 2297 |

⇒ ★★ **根因**：**推理模型把整个输出预算吃光，正文通道从未产出** ⇒
上游返回的是**合法 200**，但 `message.content` 为空。

⇒ ★★ 而 `internal/emptyoutcome` 的注释（r1029 / 2026-10-17）**早已记载这一形态**：
「a body whose entire completion went into reasoning (max_tokens exhausted by
deliberation, content never emitted)」⇒ ★ **「推理不算 assistant 答案 ⇒ 必须 failover」
是 2026-10-17 的属主裁决** ⇒ ⇒ **本条不是新缺陷**（★ 自我推翻 ⑤）。

### 6.3 但真问题有三个（本轮新发现）

| # | 真问题 | 证据 |
|---|---|---|
| **P1** | ★★ **重试不放 `max_tokens`** ⇒ 三次**同一 body**（`body_bytes=169` 三次一致）⇒ **注定失败**，白烧 93 s | 日志三次 `body_bytes=169` |
| **P2** | ★★ **客户端措辞完全误导**：上游正常 200、实际有 **1 个**候选，却报 503 `model_not_found`「No available provider … All **3** candidates failed」 | `routing_resolve candidates_count=1` ＋ 消息里的「3」= `execErrTyped.Tried`（**尝试数**，不是候选数，`domains/streaming/handler.go:5581`） |
| **P3** | ★★ **服务端日志不记上游 usage** ⇒ 「预算耗尽」与「上游挂了」读起来一模一样（都只有 `status=200`） | 改动前的 WARN 只有 6 个字段 |

⇒ ⇒ **D2 扩展**（措辞/可观测性）、**D10 新增**（重试预算策略）。

### 6.4 本轮处置：**只补可观测性，不改任何行为**

新增 `internal/emptyoutcome.InspectEmptyBody(body) (EmptyReason, EmptyUsage)`：

- 口径：`finish_reason=="length" && completion_tokens>0` **或** `reasoning_tokens>0 && reasoning_tokens>=completion_tokens`

- ★ **只做「归因说明」，不改变空/非空判定**（空/非空仍由 `ChatBodyIsEmpty` / `ChatChunkHasOutput` 决定 —— 那是属主裁决过的口径）。

  `empty_reason` / `finish_reason` / `completion_tokens` / `reasoning_tokens` / `prompt_tokens`。
- ★ **端到端实测（本地重部署 `2.5.8-2d586a2a-20261024-2849` 之后）**：


  ★ **同一个 `request_id` 连续出现 3 行、token 数逐行相同** ⇒ ★★ **既验证了新增字段按设计出值，

## §7 ★ 量具失效（本轮第 4 次，也是最隐蔽的一次）：**共享临时文件 ⇒ rid 串行**

**现象**：脚本报告 R1P3 = `200 / 69.4 s / rid=2e6520cc1df4`，而 DB 里
`request_id=2e6520cc…` 那行是 **503 / 111.8 s**；真正对应的是另一行
（`3a14c720…`，200 / 69.2 s）。

**根因**：被 `pkill` 掉的旧跑批**留下了存活的 curl**（脚本被杀了，curl 没有），
它与新跑批**共写同一个** `/tmp/kx-h.txt` ⇒ 新跑批读到的响应头可能是旧请求的。

⇒ ⇒ **通用式**：★ **量具自己的临时文件也必须 per-invocation 独占** ——
「两个跑批并发」不只是抢资源，还会**把 A 的读数配到 B 的记录上**，
而**读数看起来完全正常**（只是对不上号）。
⇒ ⇒ 修法：每次调用 `mktemp -d` + 独立文件；且**被 kill 的跑批要连带清掉它的子进程**
（`pkill -f` 杀的是脚本，不是 curl）。

★ 同族第 5 次：本仓库已登记「并发跑的写面门会互相把对方读到掏空态」（§392）。

```

06:02:52 http=200  next_retry_at=06:02:57 cf=0

```

⇒ ★★★ **封锁纯粹是探针退避窗**：到期即恢复、`consecutive_failures` 归 0、模型从未死。
⇒ ⇒ ★★★ **这是 D9 在「成功路径」上的完整因果链**（R149 只在失败路径上量到过）。

★ ⚠ **同时暴露的活锁风险**：`consecutive_failures` 再涨 2 次就到 **3 ⇒ `broken_confirmed`**
⇒ 而**唯一能清掉它的是「一次成功的探针」** —— 若探针的 30 s 预算一直不够，
⇒ ⇒ ★★ **该对就会一直被硬排除**，客户端持续看到「没有可用 provider」。
⇒ ⇒ ★★ **D9 不只是可用性问题，还是可用性活锁的维持者**。

## §10 诚实边界

1. ★ **成功回合用的是 `deepseek-v4.1-flash`，不是 Goal 清单里的 `glm-5.3-flash`** ——
   `glm-5.3-flash`（nvidia 侧）在本地探针上 **30 s 超时**（`z-ai/glm-5.3-flash`，
   `consecutive_failures=4` ⇒ `broken_confirmed` ⇒ 路由器硬排除，§4）。
   ⇒ **本轮没有证明 `glm-5.3-flash` 可用**；只证明了「在同一个网关、同一套写入路径上，
   一条长提示词可以成功并被正确落盘」。
2. ★ **15 次请求里只有 9 次成功**（§8.1）：1 次**客户端超时**（上游 240 s 未答完，★ 这不是网关缺陷），
   5 次**被探针退避挡在路由层**（★ 机制已在 §8.2/§8.3 定案 ⇒ **不是「不可用」，是「被判死」**）。
   ⇒ ⇒ ★ **Goal 的 5 条样例提示词各至少成功 1 次**；★ 但「3 轮全部成功」这个更强说法**不成立**，已作废。
3. ★ **`error_probe.timeout_ms` 只在本地改了**（`settings_kv` 一行 + 重启），**生产未动**；
   ★ 且实测它**对 node 探针无效**（§2）⇒ 本轮并未真正改变探针行为。
4. ★ **provider 2452 的 `egress_profile` 由 `proxy` 改为 `direct` 只在本地**（生产未动）。
5. ★ **本轮没有对生产做任何写入**（全部读数走本地 8782 + 本地 PG）。
6. ★ **`empty_response` 的分类口径本轮未改**（属 2026-10-17 属主裁决）；本轮只加日志字段。
7. ★ **「重试不放 max_tokens」这条只做到「证据 + 门 + 文档」**，没有改执行器行为。
8. ★ **父表面的「真搬运」已在本轮实测发生**（§8.1.1）：手动 promote（保留期临时改 1 秒）
   搬了 **235** 行，目标行落到 **`session_turns_2026_10`** 且**逐列保真**。
