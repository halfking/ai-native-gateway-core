## 一、结论先行

**最重要的一条结论不是任何单个 bug，而是这条元事实**：

> **PI 智能体此前整条链「组件齐全、从未接线」。**
> 错误收集器、分析器、后台 worker、管理 API、auto 第二层分类器、LLM 判官层——
> 全都**写好了、有单测、从未被生产代码调用过**。
> ⇒ owner 问的三件事，实际产出**全部为零**。

三份子审计共登记 **49 条**缺陷（Area1 错误管线 24 条、Area2 auto 第二层 14 条、Area3 PI/PII 检测层 17 条，其中若干条互相重叠计数）。
本轮**修了其中能被安全修的 31 条**，另登记 **7 条未修/降级**与 **12 条诚实边界**。

按「安全后果」排序，最要命的三条：

| # | 缺陷 | 后果 | 证据 |
|---|---|---|---|
| **F-PI-01**（P0） | L6 判官引擎配置查询读 `model_name / api_key / base_url / confidence_threshold` —— 这四个列在正典表 `prompt_injection_llm_engines` 里**都不存在** | 每次调用必报 PG **42703** ⇒ **判官层从不产出任何结论**；又因 `llm_detection_fail_closed` 默认 false ⇒ 只落一行 `slog.Warn` 就继续用规则分放行 ⇒ **L6 形同虚设且无痕** | 正典表列清单 vs 查询列清单逐列对拍 |
| **F-PIERR-02**（P0，已实测） | `Collect` 把 `inputText[:10000]` 按**字节**切 | 纯中文输入落在切点 ⇒ 产出**非法 UTF-8** ⇒ PG **22021** ⇒ **整行丢失**。实测：中文 3334~3399 字 **66/66** 命中切点 ⇒ 真实中文流量上错误队列**一条都插不进去** | 隔离 PG 17.10 实跑 |
| **F-PIERR-12**（P0） | `GatewayLLMClient.Analyze` 返回**空成功桩** `("", 0, nil)` | 每条队列记录失败 3 次被标 `failed`，而日志只有一行 Info「sending analysis request」—— **看起来像在正常工作** | 代码即证 |

以及一条**元教训**（本轮最重要的产出之一）：

> **「自述与实现不符」比代码写错更危险。**
> 本轮复核新发现 6 处「注释/配置声称了一个比实现更强的性质」：
> 例如 L3 启发式的注释白纸黑字写着「下划线也绕不过去」，而实现用 `\b`——
> RE2 把下划线算作单词字符 ⇒ **下划线确实绕过去**。
> 复核者照着注释去验收，**验收项本身是假的**。

| ID | 缺陷 | 根因 | 修法 |
|---|---|---|---|
| F-PIERR-01 | jsonb 列直接绑 `[]byte` | pgx 在 **SimpleProtocol** 下把 `[]byte` 编码成 bytea 十六进制 ⇒ PG **22P02** | 统一 `jsonbArg(...)` 产出 `string` + SQL 写 `NULLIF($N,'')::text::jsonb`（与本仓正典 `internal/dbx.NormalizeJSONB` 同形） |

### 5.2 本轮复核**新发现**的（4 条）★ 这四条最值得看

| ID | 缺陷 | 为什么重要 | 修法 |
|---|---|---|---|
| **F-PI-05b**（P1） | **本轮上一版实现引入的**：头尾截断的「尾」实际写的是 `truncateUTF8Bytes(input[len(head):], tailBudget)` —— 那是「从**头部之后**再取前 N 字节」，在**前置填充**（正是这个函数要防的攻击形态）下取到的**全是填充** ⇒ 函数名义上「头尾都保留」，实际上在攻击场景里只剩头部 ⇒ **攻击者前置 50KB 填充依然能把注入藏到检测面之外** | 守门测试 `TestTruncateForDetection_KeepsHeadAndTail` **当场抓出**（首轮跑就红） | 新增 `tailUTF8Bytes`（从**末尾**倒取、起点落在 rune 边界）+ 极小 limit 时**优先保尾部** |
| **F-PI-08b**（P1） | L3 启发式的**注释**白纸黑字写着「关键词之间允许插入任意**非字母数字**的分隔符 ⇒ 换行/下划线/连字符/空格都绕不过去」，而实现用 `\b…\b` —— RE2 的 `\b` 把**下划线算作单词字符** ⇒ `ignore_all_previous_instructions` **整体绕过** | ★ **「注释与文档也是交付物」**的典型形态：注释描述了一个比实现更强的性质，复核者照着注释验收，**验收项本身是假的** | 边界改为「起始或非字母数字」/「非字母数字或结尾」⇒ 下划线成为合法分隔符，**与注释一致** |
| **F-PI-06b**（P2） | 判官提示词的「载荷不能闭合框架」只依赖 `json.Marshal` 的**默认 HTML 转义** —— 那是**标准库默认行为**（`json.Encoder` + `SetEscapeHTML(false)` 就会失效），不是本仓写下的不变量 ⇒ 有人改用 Encoder，防护**无声消失**且**没有任何断言会红** | 安全承诺必须能被**断言**，否则「以为有防护」与「真的有防护」在运行期不可区分 | 显式 `neutraliseUntrustedText` + 门禁断言**产出物性质**（闭合围栏只出现一次）而不是「我们恰好用了某个 API」 |
| **F-PI-ENV-01**（P2） | Go 1.19+ 的 gofmt 会把 doc 注释**正文**里的两个单引号转成排版引号（U+201D）⇒ 文档里的 SQL 字面量 `NULLIF($N,'')` **失真** | 文档失真 = 「自述与实现不符」的另一种形态 | 把 SQL 放进**缩进块**（gofmt 的预排版区域 ⇒ 原样保留），并在两处留注释说明这个坑 |

### 8.1 PG init 脚本 `exit 126`：宿主 bind mount 是 **noexec**，而分发判据问错了地方

| 项 | 事实 |
|---|---|
| 症状 | `lgw-mock-only-pg` → `Exited (126)`；日志末行 `/docker-entrypoint-initdb.d/10-init.sh: /bin/bash: bad interpreter: Permission denied` |
| 机理 | postgres entrypoint 按 **`access(X_OK)`** 分发 `/docker-entrypoint-initdb.d/*.sh`（`[ -x "$f" ]` ⇒ 直接 `"$f"`，否则 `. "$f"` 源码化）。Docker Desktop 的 virtiofs 挂载**禁止 exec**，且它的 `access(X_OK)` 回答与 `stat(2)` **不一致** ⇒ `ls -la` 显示 `-rw-r--r--`，而 `[ -x … ]` 却返回 **真** ⇒ entrypoint 走「running」分支直接 exec 挂载文件 ⇒ EACCES |
| 证伪 | 同一 pattern 在**镜像层**里 exec 正常（`/bin/bash` 是完好的 ELF 755）；`bash <挂载文件>` 也正常（读取不需要执行位）⇒ **不是脚本问题、不是镜像问题、不是 PG 版本问题** |
| 修法 | 新增 `tests/mock-system-test/Dockerfile.mock-pg`：把 init 脚本 **COPY 进镜像层**（`chmod 0755` + `bash -n` 语法闸），compose 的 pg 服务改用 `build:` + `PG_BASE_IMAGE` 参数 ⇒ 脚本**字节不变**、Linux 主机行为不变 |

★ 通用式：**「宿主挂载点不可执行」是所有 bind mount 场景的雷**；分发逻辑用 `access()` 判可执行性时，
**必须确认目标文件系统对 `access(X_OK)` 的回答与实际可执行性一致**。

### 8.9 ★ 引擎边界：**PG 的 `\b` 是退格符，不是词边界**

- 实测（PG 17.10）：一个「sudo + 删除根目录命令」的串 ~ `'\bsudo\b'` ⇒ **false**；
  同一个串 ~ `'\ysudo\y'` ⇒ true；`chr(8) ~ '\b'` ⇒ true
  ⇒ **PG 的 `\b` 匹配的是退格符**（PG 的词边界是 `\y`）；Go RE2 的 `\b` 才是词边界。
- 后果：迁移 977 的 F4 pattern（用 `\b`）**只能用 Go RE2 验证**（检测器的真实引擎）⇒ 拿 PG 复核会得**假阴性**
  （「以为没命中、其实命中了」）。
- 好消息：本仓的规则 pattern **只在 Go 侧评估**（全仓 SQL 只 INSERT/UPDATE `pattern` 列，**没有任何 SQL 用它做匹配**）⇒ 无生产风险。
- ★ 该结论已写进 **977 的迁移注释**与 **db-changelog 台账行**（交付物的自述必须与实现一致）。

## 九、通用式（本轮沉淀）

1. **「组件齐全」≠「链路能跑」** —— 判定标准是「**谁调用了它**」，不是「它写了吗」。PI 智能体三个职责链的组件全在，调用方全无。
2. **「自述」也是交付物** —— 注释、配置项名、环境变量说明都必须对着实现核。本轮 6 处「注释/配置声称了比实现更强的性质」。
3. **安全承诺必须能被断言** —— 否则「以为有防护」与「真的有防护」在运行期不可区分；断言要落在**产出物的性质**上，不是「我们恰好用了某个 API」。
4. **守门测试必须变异验证** —— 全绿的守门测试可能只是断言写错了；「改坏 ⇒ 变红」才有牙。
5. **真发 HTTP 才能证路由可达** —— handler 单测覆盖不到「路由注册没有」与「被前缀路由吞掉」。
6. **同一条数据两处不同键 ⇒ 看得见、筛不出** —— 本轮同型：正典表的列名与查询列名不一致 ⇒ 每次调用 42703。
7. **注释里写了一个更强的性质，就是一个待修的缺陷** —— 复核时先问「实现真的满足这条注释吗」。
8. **测试夹具的失败要按「谁的错」归因，不要按「报错文本」归因** —— 本轮三处详情页失败报了三种错
   （invalid provider id / tenant not found / invalid id），**同源**：`resolve-ids` 把**另一个网关**的 id
   灌给了本栈 ⇒ 报错文本指向「数据不存在」，真因是「**ID 属于别的栈**」。
9. **shell 变量 ≠ 环境变量** —— 脚本里 `BASE_URL=…` 不 `export`，子进程就拿不到 ⇒ 静默回落到默认值
   （本轮：`resolve-ids` 回落成 8782 的本地开发网关）。
10. **判据要用「真实执行引擎」** —— PG 的 `\b` 与 RE2 的 `\b` 不是一回事 ⇒ 拿错引擎复核会得假阴性；
    同理，**自己的口径写错时第一嫌疑永远是自己的口径**（本轮我把 `~` 的操作数顺序写反，误判出「PG 与 RE2 语义不同」）。
11. **★ 探针表达式要拿到活库上求值，而不是读代码** —— 本轮把 977 的产物探针**原样**丢给 245 的 PG 算了一遍，
    才发现它**恒假**（注释里的 `RETURNING` 命中了缺席判据）⇒ 读代码永远看不出「注释会污染判词」。
12. **★ 缺席型判据必须剥注释** —— `prosrc` 与 `pg_get_functiondef()` **都保留 plpgsql 体的注释**
    ⇒ 「某 token 缺席」这种判据**必须先 `regexp_replace(…,'--…','','g')`**；
    ⇒ **注释解释得越详细，守卫越致命**。
13. **★ 「种子数据」也是要投递的交付物** —— 规则集住在两条**未投递**的历史迁移里（315 / 364）
    ⇒ 全新安装的规则表**恒空**、存量库缺两条 ⇒ **「表在」不等于「表里有货」**；
    ⇒ 数据种子的交付面必须和 schema 迁移一样被**登记 + 门禁钉住**。
14. **★ 变异必须落在「生效面」上** —— 本轮一次假阴性：变异锚点**先命中了注释里的修法示例**，
    代码里的探针行原封不动 ⇒ 门当然不红 ⇒ **锚点未命中 ≠ 守卫失效，它意味着变异压根没发生**
    ⇒ 变异器必须**行级定点**并断言「那一行确实变了」。
