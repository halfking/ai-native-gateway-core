## 审计范围

### 错误分类

#### 1. 流中断与恢复类 (Stream Interruption & Recovery)
- `gateway_survival_resume_blocked` - 流恢复被阻断

#### 2. 空响应类 (Empty Response)
- `empty_model_response` - 模型返回空响应
- `upstream completed without an assistant answer` - 上游完成但无助手回答

#### 3. 工具调用类 (Tool Invocation)

- `Tool call ended without a terminal event` - 工具调用无终态事件

#### 4. 请求限制类 (Request Limits)
- `prompt exceeds gateway budget` - 提示超出网关预算
- `request cannot produce a valid bounded context` - 无法生成有效边界上下文

#### 5. 上游服务类 (Upstream Service)

- `upstream stream returned an error` - 上游流返回错误
- `upstream closed the stream without sending [DONE]` - 上游关闭流但未发送[DONE]

#### 6. 策略与安全类 (Policy & Security)
- `output policy blocked stream lane (rule builtin.guard.tool_json_invalid)` - 输出策略阻断
- `output policy refused to rewrite` (`rewrite_refused`) - 拒绝重写

#### 7. 协议与格式类 (Protocol & Format)
- `request rejected: the request body failed the provider wire format validation` - 请求体格式验证失败
- `messages 参数非法` - messages参数非法

#### 8. 网络与连接类 (Network & Connection)
- `Network connection failed for the provider request` - 提供商请求网络连接失败
- `Cannot connect to API: The expression evaluated to a falsy value: assert(statusCode >= 100)` - API连接断言失败
- `ERR_ASSERTION` - 断言错误

#### 9. 流式输出类 (Streaming Output)
- `Partial assistant output was discarded before a streaming retry` - 部分助手输出在重试前被丢弃
- `gateway request survival ended: committed_output` - 网关请求存活结束

**频率**: 24小时内至少3次
**影响模型**: minimax-m3.1-flash, MiniMax-M3.1-Flash-Preview
**典型场景**:
```json
{

  "resumable": false,
  "reason": "eof_without_done"

```

**根因分析**:
- 上游 MiniMax API 在发送大量chunk后意外关闭连接

- 正确记录为 WARN 级别
- 发送 mid-stream terminal failure notice
- 抑制重试 (goal_retry_suppressed_after_stream_commit)
- 最终标记 executor failed

**评估**: ✅ 处理正确,这是上游问题,网关已正确处理

### 关键发现

#### 🔴 P0: openai_empty_response (76次,100%来自minimax-m3.1-flash)

**问题描述**:
- MiniMax M3.1-Flash 模型在思考(reasoning)阶段耗尽token预算
- 返回大量 `reasoning_content` 但零 `delta.content`
- 网关按 r1029 规范判定为空响应

**根因** (来自2026-11-11审计):
```
上游返回纯 reasoning_content 增量后以 [DONE] 结束、
零 delta.content ⇒ 网关按 r1029 判 openai_empty_response；
此时 reasoning 帧已前传客户端 ⇒ attempt 已 commit 
⇒ 网关内 failover 被阻断
```

**当前行为**:
- ✅ 正确: 设置 `retryable=true`,允许客户端重试
- ❌ 问题: 已提交后无法failover到其他候选节点
- ✅ 正确: 正确分类为 `KindEmptyResponse`

**改进方案** (需owner裁决):
1. **reasoning-only帧延迟commit**: 在确认有实际content前不commit
2. **usage帧检测**: 当 `reasoning_tokens ≈ completion_tokens` 且 content=0 时允许无损回滚
3. **候选节点扩展**: minimax-m3.1-flash 有6个可路由绑定,应在commit前尝试failover

**影响范围**:
- 频率: ~13次/小时 (稳定复发)
- 延迟: 42-85秒
- chunk_count: 700-8600
- completion_tokens: 0

## 修复建议与优先级

### 优先级 P0 (立即修复)

#### 1. openai_empty_response - MiniMax reasoning耗尽预算

**问题**: 当前最活跃的生产错误(76次/7天,100%来自minimax-m3.1-flash)

**修复方案** (三选一,需owner裁决):

**方案A: reasoning-only帧延迟commit**
```go
// 在 domains/streaming/responses_bridge.go 中
// 仅当收到实际 content 时才设置 committed=true
if hasActualContent(scaffold) {
    if pc != nil {
        pc.markCommitted()
    }
}

func hasActualContent(scaffold *chatScaffold) bool {
    // reasoning_content 不算实际输出
    return scaffold.textBuf.Len() > 0 || len(scaffold.toolStates) > 0
}
```

**优点**: 允许transparent failover
**缺点**: 改变流式语义,需要全面测试

**方案B: usage帧检测回滚**
```go
// 在收到 usage 帧时检查
if usage.CompletionTokens == 0 && usage.ReasoningTokens > 0 {
    // 允许回滚到未commit状态
    if pc != nil && pc.canRollback() {
        pc.rollbackCommit()
        return RetryWithNextCandidate
    }
}
```

**优点**: 精确识别问题场景
**缺点**: 需要实现回滚机制

**方案C: 客户端级别重试优化 (当前方案)**
```go
// 保持 retryable=true (当前已有)
// 在客户端实现智能重试:
// - 检测 reasoning_tokens ≈ completion_tokens
// - 自动切换到其他 minimax 候选
```

**优点**: 最小侵入性
**缺点**: 需要客户端配合

**推荐**: 方案A + 方案C组合,短期先实施方案C,长期实施方案A
