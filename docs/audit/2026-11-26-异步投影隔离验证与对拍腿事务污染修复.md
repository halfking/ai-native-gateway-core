## 1. 真缺陷：turns 对拍腿的「soft-fail」名存实亡（已修）

### 1.1 现象

隔离夹具上跑 main 的 `TestRequestMetricsProjectionPostgres`：10 个子用例里 9 绿，唯一红的 `session_dashboard_calendar` 报：

```
ERROR session statistics unavailable error="commit unexpectedly resulted in rollback"
session dashboard HTTP 500, want 200
```

### 1.2 根因（机制必然，不是夹具巧合）

- 夹具库没有 turns 家族表（`session_turns_hot`/`session_turns`）⇒ 对拍查询 42P01。
- handler（`admin/dashboardapi/session_projected.go`）把对拍腿与 KPI 主查询放在**同一个只读事务**里，失败时只「吞掉错误」（`if … err == nil`）。
- **PG 里一条语句失败会把整个事务置为 aborted**：吞错不回滚 ⇒ 后续 `tx.Commit` 必报 "commit unexpectedly resulted in rollback" ⇒ 整个面板 500。
- 生产库有 turns 表所以平时不炸，但**任何瞬时错误**（语句超时、锁等待失败）都会把「KPI 可用的降级面板」变成硬 500——与该腿注释声明的姿态（soft-fail、缺席比假绿诚实）正好相反。
- 引入点：今晚 21:36 的 `080451568`（turns_alignment 接线轮）。该缺陷自接线起就存在。

### 1.3 修法（`901e753f2`）

对拍腿跑在 pgx 伪嵌套事务（`tx.Begin()` ⇒ SAVEPOINT）里：成功 `sp.Commit`、失败 `sp.Rollback` ⇒ 外层事务保持可用 ⇒ soft-fail 真正成立（turns 表缺失/瞬时错误都只降级对拍腿，KPI 主查询不受牵连）。

### 1.4 判据（负控验证过，不是恒绿）

| 状态 | 结果 |
|---|---|
| 未修版 + 同一夹具 | `session_dashboard_calendar` 红（HTTP 500）|
| savepoint 修复 + 同一夹具 | 全绿 |
| 撤修复（stash）→ 复跑 | 红（复现）|
| 恢复修复 | 绿 |

契约门文件（`session_projected_turns_align_test.go`）头注已补第 4 条订正：该项不再是「静态审查项」，已由真 PG 夹具在运行期钉死。

## 6. 通用式（本轮两条）

1. **「soft-fail」必须是可降级的执行结构，不是「吞错误」**：PG 里同一事务一条语句失败 ⇒ 整个事务 aborted ⇒ 只吞错不回滚，后续 Commit 必炸。跨腿共享事务的 soft-fail 必须 SAVEPOINT，否则语义名存实亡——且在生产「表都在」时永不暴露（夹具缺表才现形）。
2. **桩测测不出真装配才存在的互斥**：sqlmock 能钉「锁行缺 ⇒ 跳过」，钉不出 SKIP LOCKED 的真行锁互斥；双实例并发这种判据必须上真 PG（本轮 8 次稳绿）。
