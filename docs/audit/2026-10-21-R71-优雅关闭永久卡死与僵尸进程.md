# R71 审计档：优雅关闭永久卡死 ⇒ 僵尸进程（97 分钟挂起）

> 日期：2026-10-21
> 会话：`mvs_bbd1346d211a4eb3ac41b552c82eaecf`
> 前序：[R69/R70 跨进程竞态与静默降级残留](2026-10-21-R69-R70-跨进程竞态与静默降级残留.md)
> **对生产的写入 = 0**（全程只读活库 + 本地一次性库；修复只落在代码与测试）
> **本轮不做**：浏览器逐页扫（被首次激活门挡住，属对外可见动作，待属主授权）；
> 用户点名模型的多轮实测（上游凭据随活库销毁，不可恢复，待属主重新提供）

---

## 0. 一句话结论

**每一次优雅关闭都会把网关进程变成僵尸**：关闭序列是一个 goroutine，
其中一个 `Stop()` 在「构造了但从未启动」的 worker 上永久阻塞，
连带 LISTEN 连接永不归还，`defer db.Close()` 在 `pgxpool.Close()` 里永久等待，
`main()` 永不返回 ⇒ 进程不退出、攥着全部 Redis 连接、后台 goroutine 对着已关的池
继续刷 `closed pool`。

- 触发条件：**默认路径**（`LLM_GATEWAY_USE_NEW_PROBE_MODE` 未设 ⇒ 视为 true）。
- 实测挂起时长：**97 分钟**（两个僵尸进程的 `SIGQUIT` 栈）。
- 存量影响：本机同时跑着 **3 个僵尸实例**（2781 / 2784 / 2787），已清理。

## 4. 修复

### 4.1 21 个 worker 的 `Stop()` 加「未启动就不等」护栏

**病根形状**（本仓 21 个类型同形）：

```go
func (w *W) Stop() {
    if w.cancel != nil {   // ← cancel 只在 Start() 里赋值
        w.cancel()
    }
    <-w.done               // ← 条件保护错了位置：等待在守卫之外
}
```

**正确形状**（本仓早已存在的惯用法，`CostReconciliationWorker` 等 6 个类型
就是这么写的）：把等待移进守卫内。

```go
func (w *W) Stop() {
    if w.cancel != nil {   // cancel != nil ⟺ worker 已启动
        w.cancel()
        <-w.done
    }
}
```

覆盖：`ApprovalTimeoutWorker` / `AssetHealthProbe` / `AutoIndexRefresher` /
`CredentialCycler` / `DefaultProbePicker` / `EnvelopeCleaner` /
`FeatureStatsWorker` / `FeedbackAnalyzer` / `MaterializedViewRefresher` /
`ModelConfigValidator` / `ModelProbeRunner` / `PassiveProbeListener` /
`ReportRollupWorker` / `SessionHealthWorker` / `SettingsAuditCleaner` /
`SlotSuggester` / `StickyCleaner` / `TaxonomySync` / `WeeklyPeakRollup` /
`boardcache.Service` / `MinuteAccumulator`。

**两个特例**（不能机械套用）：

- `ModelProbeRunner`：`Start()` 设 `r.cancel`，`StartFeaturedOnly()` 存
  `r.featuredCancel` —— 两条入口各持一个 cancel，**任一存在**即代表已启动。
  改成 `started := false; …; if started { <-r.done }`。
- `AssetHealthProbe`：没有 cancel 字段（用 `stop` channel）⇒ 加 `started atomic.Bool`。

### 4.2 `db.Close()` 加超时兜底（最后一道防线）

即使将来某个 `Stop()` 又卡住，**进程也必须能退出**。

```go
const poolCloseTimeout = 15 * time.Second

func closePoolWithTimeout(pool *pgxpool.Pool, timeout time.Duration) bool {
    // 关闭放到自己的 goroutine，泄漏的连接钉不住调用方
}
```

★ `pgxpool.Close()` 会先关自己的 close-channel 再等待 ⇒ 超时被放弃时
**池已经拒绝新请求**，放弃的只是「等存量连接归还」这一段；
被放弃的 goroutine 自己会跑完并归还连接。

### 4.3 关闭序列的顺序问题（未改，记录在案）

`main.go:8312-8316` 先停 `autoIndexRefresher` 再停 `autoRouteListener`，
而 listener 会调用 refresher。理论上存在互等风险。
本轮**未改**（改顺序属于语义变更，需要独立论证），靠 4.2 的兜底保证不产生僵尸。

方法形态 `w.started()`、`select` 分支。

★ 扫描器迭代中踩到的两个坑（都记下来）：
1. **局部别名**：`started := m.started; if started { <-m.done }` 最初被误报

⇒ **两轮误报都是「量具太严」而不是「被测真错」** —— 与 R66 的教训一致：

## 8. 顺带发现：admin 存储快照在本机采集中超时（**环境放大，不是生产形态**）

追查「关闭时还有连接没归还」时，抓到另一条**真慢查询**：

```sql
SELECT COALESCE(SUM(pg_total_relation_size(c.oid)), 0)::bigint
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog','information_schema');
```

| 测量 | 耗时 |
|---|---|
| 冷（01:54） | **102.8 s** |
| 暖（02:03） | **91.3 s** |
| 453 个关系全量算 size + 排序（02:09） | **73.9 s** |

**逐项拆解（同一个库、同一时刻）**：

| 表达式 | 耗时 |
|---|---|
| `SELECT 1`（基线往返） | 32.6 ms |
| `pg_relation_size('credentials')`（1 个文件） | 16.8 ms |
| `pg_indexes_size('credentials')`（若干索引文件） | 129.3 ms |
| `pg_total_relation_size('credentials')` | 263.0 ms |

⇒ **成本在「每次文件 stat」**：≈163 ms/关系 × 453 ≈ 74 s。
这是 **macOS Docker Desktop 的 gRPC-FUSE 挂载**特征（每次 `stat()` 一次网络往返），
叠加当时 **load average 340**（并行会话在跑构建）。
⇒ ★ **生产（211/252：Linux + 本地盘）上 `pg_total_relation_size` 是微秒级** ——
仓内注释记录的 252 实测就是 **1.26–2.36 s**（3362 个关系）。
⇒ ⇒ **不能把这条当生产慢 SQL**。

**但它在本机暴露了一个真实的降级行为**（这是有价值的部分）：

- `storageCollectTimeout = 60s` ⇒ 本机采集**每次都被自己的预算掐死**；
- 实测日志：`WARN storage: background table sizes refresh failed err=timeout: context deadline exceeded`（02:09:59）；
- ⇒ 快照**永远刷新不了**：`collected_at` 冻结在 `00:56:31`（1 小时前）；
- ⇒ 页面仍返回 200 + 完整数字（**看起来是真的**）。

★ **自我修正**：第一反应是「这是缺陷」，**不是** ——
产品的 stale-while-revalidate 是**有意设计**（过期即返回旧读数 + 后台单飞刷新），
`collected_at` **本来就把陈旧度暴露给了调用方**，刷新失败也留了 WARN。
⇒ **不是缺陷，是降级环境下的既定降级行为**；本机之所以降级，是因为采集预算
（60s）小于本机采集耗时（74–103s）。

⇒ **本轮不改**：
- 抬 `storageCollectTimeout` 是**调参**，而触发条件是本地 FUSE + 超载的**环境放大**，
  照着它改会把一个环境产物写进产品默认值；
- 真正该做的是**把这条测量记在案**，让 211/252 的复测知道它在本机会出现、
  而在生产不会。

⇒ **给属主的一个可选项**（不在本轮范围）：若某天生产上也出现采集超时，
可选「按关系数分批 + 采样」或「采集预算随关系数自适应」，
而不是单纯抬预算。

## 10. 诚实边界

- 本轮**未**改关闭序列的顺序问题（4.3 末条），靠 4.2 兜底。
- `Stop()` 的护栏用的是 `cancel != nil ⟺ 已启动` 这个**推断**。
  对本轮覆盖的 21 个类型，逐个核对了 `Start()` 里「先赋 cancel、再起 goroutine」的顺序；
  但这是**约定**而非类型系统保证 ⇒ `internal/stopguard` 的门把形状钉住，
  行为门把效果钉住，两者都不依赖这个约定继续成立。
- 扫描器是**保守**的：只认本仓在用的 7 个 liveness 字段名。
  将来引入新写法时，它可能**漏报**（假绿）而不是误报（假红）——
  所以行为门与真库腿不能省。
- `credential_model_index` 的 rollup 在本机是被 8782 另一个实例顶上来的
  （本实例的 rollup 自 10-20 23:00 起全失败）⇒ 修复后本实例的 rollup 应恢复；
  本轮未做该项的在线复验（需重启新构建后观察）。
- §8 的慢查询是**本机环境放大**（macOS FUSE + load 340）⇒ **不代表生产**；
  生产实测口径见仓内注释（252 上 1.26–2.36 s）。
- 关闭耗时 16s 中的 15s 是「等一条在飞的 admin 存储快照查询」⇒ 那是
  **采集预算内的正常等待**，不是卡死（§8 已定性）。若采集被掐死（>60s），
  兜底会让退出更快（不等那条连接）。

## 11. 通用式

1. ★ **「有守卫」不等于「守卫护住了正确的语句」** ——
   `if cancel != nil { cancel() }` 后面跟一句裸的 `<-done`，
   是最容易被读成「已经加了保护」的形状。判据要落在**可达性**上，不是落在
   「这段代码看起来有没有判断」。
2. ★ **「关闭超时」只是告警，不是出口** ——
   超时分支必须**真的让进程退出**，否则只是把「卡死」变成「卡着刷日志」。
3. ★ **一个序列里的单个阻塞点会吃掉后面全部** ——
   关闭序列是串行的，任何一个 `Stop()` 卡住，后面的 `Stop()` 一个都跑不到，
   于是「负责归还长连接的那个」也被跳过 ⇒ 资源泄漏从「一个 worker」升级成
   「整个进程」。
4. ★ **「默认路径」比「配置错误」更危险** ——
   `useNewProbeMode()` 的默认值是 true ⇒ 这不是有人配错，是所有人默认踩。
5. ★ **僵尸进程不会自己消失** ——
   它不监听端口，看起来像「已退出」，但仍攥着 Redis 连接与 FD；
   `ps` 看得到、端口看不到 ⇒ 需要用「进程 + 端口 + 连接」三者交叉才能发现。
