## 一、真缺陷：会话详情页 500（SQL 列名二义）

### 现象

`/admin/sessions/:id` 整页拿不到数据。服务端日志：

```
ERROR querySessionDetail failed
  err="query session: ERROR: column reference \"updated_at\" is ambiguous (SQLSTATE 42702)"
```

### 真因

`admin/session_detail_v2.go` 的查询：

```sql
SELECT id, session_id, tenant_id, created_at, updated_at, closed_at, status, ...
FROM public.sessions s
LEFT JOIN LATERAL (...) sam ON true     -- sessionAnalysisJoinSQL()
```

LATERAL 暴露了 `status` 与 `updated_at` 两列（见 `sessionAnalysisSelectCols`），
与 `public.sessions` 同名 ⇒ 裸列名二义 ⇒ PostgreSQL 直接拒绝。

实测两表共有列是 `created_at / status / tenant_id / updated_at`，
但只有 `status` / `updated_at` 出现在 LATERAL 输出里，所以只有这两个真的二义。

### 修法与验证

全部列加 `s.` 前缀（LATERAL 那几列保持 `sam.` 前缀，Scan 顺序不变）。

真库双向验证：

| 版本 | 结果 |
|---|---|
| 修前（裸列名） | `ERROR: column reference "updated_at" is ambiguous` |
| 修后（全限定） | PREPARE 通过 |

回归门 `admin/session_detail_sql_gate_test.go`（静态扫 SELECT 列表，CI 上跑得动）：
把 `s.` 去掉 → 两条断言都红，且指名道姓报出 `updated_at status`。

**为什么同族查询没事**：`session_turns_v2.go` 的快照查询本来就写 `s.xxx`，
`turns_sessions.go` 走的是全限定的 `sessionAnalysisSelectCols()`。只有 detail 这一条是裸的。

### 这个缺陷为什么一直没被发现

它在一个**从未被自动化扫到**的页面上。补上动态路由覆盖后，它第一轮就被打出来。

**排序键必须与首列显示的主键一致** —— `ModelsTab` 首列渲染的是
`credentialDisplayName(credential_id)`，所以排序也用同一个函数的返回值，
而不是按 `credential_id` 数字排。

### 共享工具的扩展与不污染保证

`NameLike` / `DEFAULT_KEYS` 追加 `canonical_name` / `model` / `model_name`（加在**末尾**），
`key_alias` 只进接口、**不进默认候选**（同 `label`）。

追加在末尾意味着**只能影响「前面所有候选都取不到值」的行**（原本沉底），
已上线的供应商/租户/用户/密钥/Agent/凭据六处行序不变 —— 有测试钉死：

```ts
it('追加 canonical_name 不会改变已有 name 的行的行序', () => {
  const rows = [{ name: 'Zeta', canonical_name: 'aaa-first' },
                { name: 'Alpha', canonical_name: 'zzz-last' }]
  expect(sortByName(rows).map((r) => r.name)).toEqual(['Alpha', 'Zeta'])
  // 鉴别力：若 canonical_name 被插到 name 前面，会排成 Zeta, Alpha
})
```

### 接线门（防「加了 computed 却忘换模板」）

## 四、AttachmentManager 弹层：从「无法判定」到「判据可判」

### 我先前的说法是过头了，必须更正

我一度写「静态核对为无裁切」并据此认为这条已判定。复核发现**不是**：
契约 B 的「限高必须可滚」规则当时被**降级成待人工确认项**（因为它连着误报三次），
而降级的副作用是 —— **把 `.json-block` 的 `overflow:auto` 抽掉，报告一字不变**。

也就是说：那个桶里的项**恒定存在、从不变化**，它既不能证明「有滚动路径」，
也不能提示「滚动路径没了」。**0 违规 ≠ 被检查过**，这两件事在报告上长得一样。

### 修法：把「按名字找滚动来源」换成「按模板结构找」

前三种豁免都只在**命名**上找滚动来源：

| # | 形态 | 能否覆盖 AttachmentManager |
|---|---|---|
| ① | 滚动写在同一条规则 | ❌ |
| ② | 同前缀兄弟（`.modal-content` / `.modal-body`） | ❌ |
| ③ | 任意命名的 `flex:1` 子项 | ❌（`.json-block` 名字对不上） |
| ④ | **滚动的元素在限高元素的模板子树里** | ✅ |

第 ④ 条的判别力来自**结构**而不是名字：问的是
「带着这个 `max-height` 的元素，其子树里有没有声明了 `overflow` 的元素」。

比「同组件」严得多 —— 页面上别处有 `overflow:auto` 不会误豁免；也不依赖任何命名约定。

### 锚点踩了两次，都记在代码注释里

1. 最初锚在**模板根**上。AttachmentManager 的模板根是 `.attachment-manager`
   （页面外层 div），弹层是嵌在里面的 ⇒ `containers` 为空 ⇒ 判据直接放弃。
2. 改成锚在 `containers` 上，仍失败（见上）。
3. 最终锚在**这条限高规则自己的类**上 —— 问的问题只剩一个：
   「带这个 `max-height` 的元素，其子树里有没有可滚元素」。

另外配对子树时踩了第三个坑：只扫「同名标签的 class」不够 ——
`<div class="modal"><pre class="json-block">…</pre></div>` 配对时遇到的是 `</div>`，
中间的 `<pre>` 会被整段跳过，又变成「看不出来」。改成**截出整段子树再扫所有 class**。

### 现在的实测（三态）

| 状态 | 待确认桶 |
|---|---|
| 真实代码（`.json-block` 是弹层后代且有 `overflow:auto`） | **0** |
| 抽掉 `.json-block` 的 `overflow:auto` | 1（`AttachmentManager.vue L126`） |
| 把 `.json-block` 移出弹层（页面级滚动不算数） | 1（同上） |

**第三行是关键的反向对照**：它证明这不是「同组件里有 overflow 就算」的恒绿装饰。
自检里也固化了这两条夹具（`g8` / `b8`）。

### 仍然剩下的限制（不夸大）

- 这仍是**静态**判定，验的是「存在一条可滚路径」，**没有在真页面上量过**
  长 JSON 的实际滚动行为。运行时侧的 `SessionSummaryDrawer` 等 6 个弹层
  由 `ui-sweep --overlays` 真量过，但那个 case 因本地无附件数据仍标 manual。
- 待确认桶现在全仓为 **0**。零样本意味着**无法从本仓数据判断这条规则的误报率** ——
  它在本仓只有「全部正确」这一个观测点。下一条限高而无滚动路径的代码出现时，
  那才是它的第一个真实样本。

## 六、本轮踩坑（都是「环境伪装成产品缺陷」）

1. **vite dev 代理在扫描中途崩**（`ERR_HTTP_INVALID_STATUS_CODE`），
   65 条路由瞬间全报 `P0 导航失败 ERR_CONNECTION_REFUSED`。
   看起来像全线回归，其实是我自己把服务扫挂了 —— 看到 P0 齐刷刷同一种错误，
   先查服务活没活，再查产品。
2. **中文 localeCompare 顺序我连错两次**：先按 ASCII 直觉写死
   `['abab-7','Zeta','glm-4.6']`，实际 zh-CN 下大小写是三级差异，
   `glm-4.6` 排在 `Zeta` 前。写测试时**把期望值从 `localeCompare` 推导出来**，
   而不是写死我猜的顺序 —— 写死猜的顺序等于写下假判据。
