## 一、真缺陷：会话详情页 500（SQL 列名二义）

### 现象

`/admin/sessions/:id` 整页拿不到数据。服务端日志：

```
ERROR querySessionDetail failed
  err="query session: ERROR: column reference \"updated_at\" is ambiguous (SQLSTATE 42702)"
```

### 真因

`admin/session_detail_v2.go` 的查询：

```sql
SELECT id, session_id, tenant_id, created_at, updated_at, closed_at, status, ...
FROM public.sessions s
LEFT JOIN LATERAL (...) sam ON true     -- sessionAnalysisJoinSQL()
```

LATERAL 暴露了 `status` 与 `updated_at` 两列（见 `sessionAnalysisSelectCols`），
与 `public.sessions` 同名 ⇒ 裸列名二义 ⇒ PostgreSQL 直接拒绝。

实测两表共有列是 `created_at / status / tenant_id / updated_at`，
但只有 `status` / `updated_at` 出现在 LATERAL 输出里，所以只有这两个真的二义。

### 修法与验证

全部列加 `s.` 前缀（LATERAL 那几列保持 `sam.` 前缀，Scan 顺序不变）。

真库双向验证：

| 版本 | 结果 |
|---|---|
| 修前（裸列名） | `ERROR: column reference "updated_at" is ambiguous` |
| 修后（全限定） | PREPARE 通过 |

回归门 `admin/session_detail_sql_gate_test.go`（静态扫 SELECT 列表，CI 上跑得动）：
把 `s.` 去掉 → 两条断言都红，且指名道姓报出 `updated_at status`。

**为什么同族查询没事**：`session_turns_v2.go` 的快照查询本来就写 `s.xxx`，
`turns_sessions.go` 走的是全限定的 `sessionAnalysisSelectCols()`。只有 detail 这一条是裸的。

### 这个缺陷为什么一直没被发现

它在一个**从未被自动化扫到**的页面上。补上动态路由覆盖后，它第一轮就被打出来。

### 取不到的不静默丢弃

11 条里 2 条本地取不到，逐条点名：

```
○ /admin/session-analytics/users/:owner  端点里取不到可用 ID（本地无该实体的数据）
○ /admin/approvals/:id                  同上（审批队列本地为空）
```

`router.ts` 里若出现**没登记进 `DYNAMIC_ROUTES`** 的动态路由，扫描时直接告警 ——
「表里没有」不等于「没有这种页」。

### 踩到的两个坑

1. **响应键猜错**：分析类三个端点返回的键是 `clients` / `tasks` / `users`，
   不是 `items`。我按 `items` 取，三页全部「取不到 ID」被跳过。
   跳过是安全的（报告里可见），但覆盖率白丢。
2. **ID 空间选错造成假阳性**：`client_id` 我第一版从 `request_logs.virtual_client_id` 取，
   详情页稳定 404 —— 那是**我取的 ID 空间不对**（列表里叫 `claude-opus-4-8` 这种），
   不是产品缺陷。**假阳性比漏报更坏**：它会让下轮去查一个不存在的 bug。

## 三、名称排序：18 → 0（10 条逐条豁免）

### 补上的 8 处真·名称列表

| 视图 | 首列 | 排序键 |
|---|---|---|
| `tenant/TenantModelsView` | 模型 | `canonical_name` |
| `provider-detail/CredentialModelsPanel` | 模型身份 | `canonical_name`（优先） |
| `provider-detail/ModelsTab` | 凭据 | `credentialDisplayName(id)` |
| `TenantDetailView`（用户表） | 用户名 | `username` |
| `TenantDetailView`（密钥表） | 别名 | `key_alias` → `key_prefix` |
| `KeyDetailView` | 模型 | `model` |
| `TenantDashboardView` | 模型 | `model` |
| `provider-detail/QualityTab` | 模型 | `model_name` |
| `UserProfileListView` | 账号 | `owner_user` |

**排序键必须与首列显示的主键一致** —— `ModelsTab` 首列渲染的是
`credentialDisplayName(credential_id)`，所以排序也用同一个函数的返回值，
而不是按 `credential_id` 数字排。

### 共享工具的扩展与不污染保证

`NameLike` / `DEFAULT_KEYS` 追加 `canonical_name` / `model` / `model_name`（加在**末尾**），
`key_alias` 只进接口、**不进默认候选**（同 `label`）。

追加在末尾意味着**只能影响「前面所有候选都取不到值」的行**（原本沉底），
已上线的供应商/租户/用户/密钥/Agent/凭据六处行序不变 —— 有测试钉死：

```ts
it('追加 canonical_name 不会改变已有 name 的行的行序', () => {
  const rows = [{ name: 'Zeta', canonical_name: 'aaa-first' },
                { name: 'Alpha', canonical_name: 'zzz-last' }]
  expect(sortByName(rows).map((r) => r.name)).toEqual(['Alpha', 'Zeta'])
  // 鉴别力：若 canonical_name 被插到 name 前面，会排成 Zeta, Alpha
})
```

### 接线门（防「加了 computed 却忘换模板」）

`nameSortWiring.test.ts` 逐个视图断言「`v-for` 用的是排序后的数组，
且原始数组不再出现在 `v-for` 里」。变异验证：

| 变异 | 结果 |
|---|---|
| `v-for` 换回未排序数组 | **17/18 红** |
| 删掉 `sortByName` 调用 | **17/18 红** |

### 豁免的 10 条（逐条写明理由，代码里的 `NAME_SORT_EXEMPT`）

- **按时间倒序才对**（7 条）：`KeyApplicationsView`（申请时间）、
  `provider-detail/{LogsTab,ProbeHistoryTab,DiagTab}`、`tenant/{MaaSAccountView,MaaSUsageView}`
- **按频次更有用**（1 条）：`provider-detail/ErrorDetailTab`（错误类型聚合）
- **启发式误报**（1 条）：`UserProfileView` —— 它是**单个 owner 的详情页**，
  表里是这个 owner 的模型分解，不是用户列表；契约 C 按文件名里的 `User` 命中
- **待决策**（2 条）：`ModelIntegrityView` / `StandardModelPricingView` ——
  排序发生在 `useModelCatalogFilters` 内部，会连带改筛选/分组语义

### 契约 C 纳入阻断

```

```

## 四、AttachmentManager 弹层：从「无法判定」变成「已判定 + 明写限制」

复核结论：**结构上不会裁切**。

- `.modal` 是 flex column + `max-height: 80vh`
- 内容区 `.json-block` 带 `overflow: auto; flex: 1` ⇒ 内容再长也滚它
- `<style scoped>` ⇒ `.modal` / `.json-block` 这两个通用类名不会外泄

仍是 manual 的原因：本地 `request_logs.has_attachments = true` 的行数为 **0**，
「查看 JSONB」入口根本不渲染，没有可点的按钮。

**限制写清楚了**：上面是静态核对 CSS 形态，**没在真页面上量过长 JSON 的弹层**。
一旦本地有了附件数据，这条应转成自动 case 并实测。

## 六、本轮踩坑（都是「环境伪装成产品缺陷」）

1. **vite dev 代理在扫描中途崩**（`ERR_HTTP_INVALID_STATUS_CODE`），
   65 条路由瞬间全报 `P0 导航失败 ERR_CONNECTION_REFUSED`。
   看起来像全线回归，其实是我自己把服务扫挂了 —— 看到 P0 齐刷刷同一种错误，
   先查服务活没活，再查产品。
2. **中文 localeCompare 顺序我连错两次**：先按 ASCII 直觉写死
   `['abab-7','Zeta','glm-4.6']`，实际 zh-CN 下大小写是三级差异，
   `glm-4.6` 排在 `Zeta` 前。写测试时**把期望值从 `localeCompare` 推导出来**，
   而不是写死我猜的顺序 —— 写死猜的顺序等于写下假判据。
