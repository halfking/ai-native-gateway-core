# 原厂工具 ↔ 原厂模型 直连全参数直通轮（2026-10-28）

> 会话：goal 会话（用户目标：「原厂工具与原厂模型直连时，工具客户端所有的参数保留并上传到模型端；只有在出错情况下才回退，只传必要的参数」）。
> 结论先行：**可行且必要，已执行**。方案取「内置映射表 + 首发全参数 + 出错才剥参回退」，
> 未取「DB 属性」方案（理由见 §3）。

## §2 链路盘点：网关在「首发」时一共动了客户端参数几处

盘点方式：读 `domains/streaming/executors/executor_chat.go`（`executeOpenAI` →
`finalizeOpenAIUpstreamBodyNative` → `prepareRequestBodyWithNative` →
`applyOpenAITailTransformsNative`）与 `internal/ir/extensions_restore.go`。

**结论：首发路径上共有 5 处主动改写/剥离客户端参数**（本轮对原生对全部跳过）：

| # | 位置 | 动作 | 影响 |
|---|---|---|---|
| ① | `prepareRequestBodyWithNative` → `ApplyRequestWhitelist` | 按 transform 规则删 `strip_request_fields` | 客户端私有参数被删 |
| ② | `prepareRequestBodyWithNative` → `ApplyCapabilitySanitizer` | minimax 简化工具 / deepseek 砍 `max_tokens` 到 8192 / nvidia 删布尔参数 | 客户端参数被改写 |
| ③ | `prepareRequestBodyWithNative` → `applyGuardToLedger`（paramguard） | GLM `tool_choice`→`auto`；MiniMax `n`→1；`reasoning_effort` 按能力钳制 | 客户端参数被改写 |
| ④ | `applyOpenAITailTransformsNative` → `applyParamguardLedger` | 同 ③ 的第二次应用（IR 路径不经过 ③） | 客户端参数被改写 |
| ⑤ | `executeOpenAI` → `reqprobeApplyLearned` + `paramRefusalApply` | 按 24h 记忆预剥离「曾被拒的参数」 | 首发就丢参数 |

另有一处在 **IR 序列化层**（`internal/ir/extensions_restore.go`）：Extensions 按目标方言
裁剪 / 翻译（实测：MiniMax 目标上 `thinking{type:enabled}` 被改写成
`{"type":"adaptive"}`，`budget_tokens` 丢弃）。

**回退路径（已有、本轮未改）**：`reqprobe` 在上游 4xx 时
（`executor_chat.go:1754` 起的诊断 + `StripParamsForWire`）按错误点名剥参重试，
最多 `maxParamStrips` 轮，剥到骨架参数（model/messages/stream/tools/tool_choice）。
⇒ 用户要的「只有出错才回退、只传必要参数」**机制本来就有**，缺的是
「原生对在首发时不要被主动改写」。

## §3 方案裁决：内置映射表（取） vs DB 属性（不取）

用户给了两个方案。裁决如下。

### 方案 A：内置代码表（**本轮采用**）

`internal/nativepair/nativepair.go`：

```go
var clientModelPrefixes = map[string][]string{
    "zcode":         {"glm"},
    "minimax-code":  {"minimax"},
    "deepseek-code": {"deepseek"},
}
```

匹配规则：模型名等于前缀，或以「前缀-」开头；容忍 `vendor/name` 宿主前缀
（`z-ai/glm-5.2` → `glm-5.2`）。**不匹配**「同前缀但非前缀段」的形态
（`glmm-x`、`glmxx` 均判否）。

理由：

1. **仓内有同款先例**：厂商归属本来就用「内置默认表 + DB 覆盖」解决 ——
   `internal/reasoncap/reasoning_defaults.go`（按模型名推能力）、
   `catalog/display.go` 的 `nameVendorPrefixes`（按模型名推厂商）、
   `internal/reasoncap` 的 `Dialect` 枚举。**模型→厂商的判断早就是内置代码**，
   本轮只是把「客户端→厂商」这半边也内置化，两边用同一套前缀口径。
2. **集合极小且变动慢**：跟随各厂商发布官方编码工具的节奏（当前 3 条），
   新增一对只需加一行；DB 化的收益（运营可改）在此规模上抵不过成本。
3. **失败面小**：内置表改动走代码评审 + 单测；DB 属性的错配会直接改变生产
   发往上游的 body。
4. **有紧急回退开关**：`LLM_GATEWAY_NATIVE_PASSTHROUGH=off` 整体关闭
   （与 `PARAMREG_ENABLED` 同款惯例）。

### 方案 B：DB 属性（`provider_catalog.vendor_agent` 之类）——**本轮不取**

用户建议「在模型原厂信息中加一个属性：原厂的智能体名称，这样就可以自动对应」。
评估结论：**方向对，但落点选错**。

- **落点错**：厂商归属是**模型**的属性（一个 glm 模型只有一个厂商），
  而「原厂智能体名称」是**客户端**的属性（zcode 是一个客户端，能配多个厂商的模型）。
  把它塞进 `provider_catalog`（描述上游供应商类型）或 `models_canonical`
  （描述标准模型）都会造成「同一个客户端在 N 行里各写一遍」的重复真值。
- **写路径缺**：`provider_catalog` **没有 admin 写路径**（只读 API，
  `admin/catalog.go:12-23`；写入仅靠迁移/种子工具）。加属性意味着
  迁移 + admin API + 前端三面工程，而本轮只需要一个 3 行的映射。
- **自动对应并不成立**：DB 属性仍要回答「客户端名 ↔ 属性值」这一跳，
  而客户端名有大小写/别名形态（`MiniMax-Code`/`minimax-code`/`X-Code-Session-Id`
  头），**归一化逻辑在代码里**（`internal/clienttype`）。DB 存表省不掉这段。
- **保留扩展位**：若将来原生对多到需要运营自助（例如客户自研的
  「智谱原厂 CLI」），正确落点是**新表**（client→vendor 映射），
  而非往 `provider_catalog` 塞一列。届时的迁移路径是：
  `nativepair` 读内置表 ∪ DB 表（DB 优先），本轮的接口不用改。

## §4 实现

### 4.1 判定（`internal/nativepair`）

- `Match(clientType, outboundModel) bool` —— 纯函数，无依赖。
- `Enabled()` —— 默认开；`LLM_GATEWAY_NATIVE_PASSTHROUGH=off/false/0` 关闭。

### 4.2 客户端身份（`domains/streaming/executors/executor_chat.go:nativePairFor`）

取用顺序（保守优先）：

1. `ExecParams.ClientType` → ② `X-Gw-Client-Type` 头 / UA 关键词
   （`extractClientType`，已归一化）；
2. **仅当上面是弱名（空 / `unknown`）时**才采信 body 标记
   （`telemetry.ExtractClientTypeFromBody`：`metadata.zcode_version` /
   `metadata.client_type=minimax_code` / `X-Code-Session-Id` 头）——
   沿用 R52 语义「body marker 只覆盖弱名」，**强名冲突时保守判非原生对**
   （例：header 说 cursor、body 带 zcode 标记 ⇒ 不直通）。

### 4.3 按候选判定（重要）

判定输入是**候选的出站模型**（`cand.RawModel`），不是客户端请求的模型名：
zcode 首发打 GLM 命中（直通），失败后转移到 deepseek 候选时**不命中**
（该候选按旧路径改写）。⇒ 直通不会「粘」到不相干的厂商上。

### 4.4 跳过清单（nativePair=true 时）

| 层 | 跳过项 | 位置 |
|---|---|---|
| IR 序列化 | Extensions 方言裁剪 + thinking 翻译 | `internal/ir/extensions_restore.go` 新增 `NativePassthrough` 分支 |
| 请求体准备 | transform 白名单 strip | `prepareRequestBodyWithNative` |
| 请求体准备 | 能力清洗器（minimax/deepseek/nvidia） | 同上 |
| 请求体准备 | paramguard 语义级改写 | 同上 |
| 尾段 | paramguard 第二次应用 | `applyOpenAITailTransformsNative` |
| 首发前 | 学习式预剥离（`reqprobeApplyLearned`） | `executeOpenAI` |
| 首发前 | 拒识记忆预剥离（`paramRefusalApply`） | `executeOpenAI` |

**保留不动**（结构性/上下文类，不是「厂商参数」）：模型名替换、
`stream_options` 注入（客户端自带时不覆盖）、消息合并、上下文压缩、
工具历史折叠（仅对不支持工具用的上游生效）、`NormalizeOpenAITools`。

**回退不动**：上游 4xx ⇒ `reqprobe` 剥参重试（最多 3 轮）到骨架参数。
⇒ R3 由「既有机制 + 未门控」满足。

### 4.5 IR 层的 `NativePassthrough`

`internal/ir/types.go` 新增 `InternalRequest.NativePassthrough bool`（`json:"-"`，
不进会话恢复快照）；执行器在 IR 路径盖章
（`irReq.NativePassthrough = nativePair`，紧邻既有的 `TargetProvider` 盖章点）。
序列化器只读该标志。

## §8 通用式（可复用）

1. **「全参数透传」与「出错回退」是两件事，必须分别有证据** —— 只做前半
   = 参数删了没回退；只做后半 = 原厂参数照样被改写。本轮两半各有一条断言。
2. **同一把尺子的两个观测层** —— 参数是否被改写，只能在**出站 body** 上
   断言（源码层看到的是「规则存在」，不是「这条请求走了哪条规则」）。
3. **跳过一门 = 在【每一处生效点】都跳过** —— 本轮 paramguard 有**两处**
   生效点（请求体准备 + 尾段），漏一处就等于没跳（M3 臂）。
4. **「原厂对」要按【候选】判定，不按【请求模型】判定** —— 否则失败转移
   到别厂候选时会错误地享受直通。
5. **弱名才用弱证据** —— body 标记只覆盖弱客户端名；强名冲突时保守判否。
6. **突变臂首跑不红，先问靶点** —— M3 首跑不红是**靶点选错**（没覆盖尾段），
   不是「门没牙」。
7. **内置表 vs DB 属性的裁决依据** —— 看「事实的归属维度」：客户端属性放
   客户端侧模型，模型属性放模型侧；跨维度的映射不塞进任一侧的既有表。
