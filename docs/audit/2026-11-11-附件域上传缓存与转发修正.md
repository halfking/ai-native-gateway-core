## 1. 缺陷清单（全部有钉测 + 变异臂）

| 编号 | 缺陷 | 后果 | 钉测 | 变异臂 |
|---|---|---|---|---|
| ① | `IRTransformer` 只处理 image | 文档 / 视频 / 音频**不落盘** ⇒ 载荷每次请求全量重传 | `TestIRTransformer_DocumentVideoAudio_AreStoredAndReplaced` | AT01 / AT02 / AT03 |
| ② | `URLFetchFallback` 只内联 `image_url` | 文档 / 视频的网关 URL **原样发给**不支持 URL 的上游 ⇒ **附件在链路上丢失** | `TestURLFetchFallback_InlinesImageFileAndVideo` | AT04 |
| ③ | `URLFetchFallback` 全 body `bytes.ReplaceAll` | 文本消息里的同名 URL 也被替换成 base64 ⇒ **内容污染 + 载荷外泄** | `TestURLFetchFallback_DoesNotTouchTextMessages` / E2E-③ | AT05 / AT10 |
| ④ | `OutboundURLRewriter` 只改写 `image_url`（Anthropic 侧只处理 image） | 文档 / 视频每次请求全量重传 | `TestOutboundURLRewriter_RewritesFileAndVideoBlocks` / `..._RewritesAnthropicDocument` / E2E-④ | AT06 / AT07 |
| ⑤ | ★ 本轮钉测**当场抓出**：`storage.SaveBase64Image` 成功路径硬编码 `Type:"image"` | file / video / audio 的落盘记录被**静默误标**成 image ⇒ 改写器的类型闸会跳过它们 ⇒ 退回缺陷 ④ | 同 ① | AT08 |
| ⑥ | 请求内去重键只有载荷、不含附件种类 | 同载荷的 image 与 document 共用 manifest ⇒ document 被误标 image | `TestIRTransformer_Multimodal_DedupKeyIncludesKind` | AT09 |

⑤ 的成因值得单列：第一版实现写的是「只在 `meta.Type == ""` 时才覆盖」，而
`SaveBase64Image` 成功路径**总是**写入 `Type:"image"` ⇒ 该条件永不成立 ⇒ 缺陷静默存在。
现按 `extractor.go` 的同口径改为**无条件覆盖**（`meta.Type = kind`）。

## 2. 修法：把「附件在 wire 上长什么样」收敛到唯一事实源

新增 `domains/attachments/attachment_fields.go`：

- `chatAttachmentFields`：**块类型 → 载荷字段路径**的唯一事实源
  （`image_url→image_url.url`、`file→file.file_data`、`video_url→video_url.url`）
- `chatBlockAttachmentType`：块类型 → Extractor 记录的附件类型（类型闸用）
- `rewriteChatAttachmentFields`：两个消费者（改写器 / 回退器）**共用**的遍历器

效果：修一族缺陷只改一处 ⇒ 不会再出现「一边修了另一边没修」（②④ 的成因正是两个消费者
各写一份、各漏两类）。

诚实边界（写进代码注释）：**有替换时** body 整体重新序列化 ⇒ 键序规范化、空白去掉 ⇒
**不是**逐字节保持；但只有被显式改写的字段会变，其余字段原值不变（数字用 `json.Number`
承载 ⇒ 不被 float64 改写）。**无替换时**原样返回入参 ⇒ 逐字节不变。

## 3. 端到端测试（`domains/streaming/executors/e2e_multimodal_outbound_test.go`）

链路与 `executor_dispatch.go` 的 MM-1/MM-2 段一一对应：
**Extractor（上传/缓存侧）→ OutboundURLRewriter 或 URLFetchFallback（转发侧）→
`finalizeOpenAIUpstreamBody`（网关 IR 转换）→ 断言最终出站字节**。

| 用例 | 断言 |
|---|---|
| E2E-① URL 模式上游 | 图片 / 文档 / 视频三类都换成网关 URL |
| E2E-② 非 URL 模式上游（deepseek） | 三类都回内联为 data URI |
| E2E-③ 字段精确替换 | 文本消息（字符串 content **与** text 块两种形态）里的同名 URL 逐字不动 |
| E2E-④ Anthropic 客户端 → OpenAI 上游 | 图片 + 文档都改写 |

修复前四个**全红**（精确暴露缺陷），修复后 4/4 全绿。

踩坑留痕：客户端连着两条 user 消息时网关清洗链会**合并** ⇒ 出站 content 变块数组、
消息**条数不固定** ⇒ 断言必须打在「全部消息的文本」上（`e2eAllMessagesText`），
不能钉某一条的下标（否则是假锚点）。

## 4. 变异验证（AT01–AT10，十臂全被抓住）

沿用仓内既有 Python harness（`scripts/audit/mutation-verify-2026-11-11.py`）**按组调用**，
新增 `--group attachments`（10 臂）⇒ **不需要把臂名单手抄进 Makefile**。

四段证据（同既有纪律）：① 变异生效的**独立证据** = 目标文件 SHA 变化（不是「锚点命中 1 次」
这种同源证据）② 门必须变红**且定位精确**（输出须含期望串）③ 还原后 SHA 复核 ④ 还原后正向复跑。

### 4.1 本轮修掉的 harness 自身缺陷（守卫自己也要被审计）

1. **多文件臂不可用**：旧实现把每条 edit 套用到 arm 的**每个文件**上 ⇒ 一条臂同时改两个
   文件根本没法写 ⇒ 而「一条臂同时撤掉两处协作的决策点」正是组合缺陷的形态。
   现改为：**每条 edit 必须恰好落在一个文件里**（落 0 个 ⇒ 锚点写错；落 ≥2 个 ⇒ 锚点不唯一）。
2. **「红了」≠「有牙」**：AT05 的第一版变异体是**臆造的新行为**（只把 text 块纳入遍历器）
   ⇒ 前缀判断仍在 ⇒ **根本没被抓住** ⇒ 门是**哑的**。
   ⇒ 变异体必须**复原旧实现的行为**：AT05 改为「全 body 字节级替换」（旧实现形态）⇒ 才被抓。
3. **编译错不算「门有牙」**：变异体类型写错导致 `[build failed]` ⇒ 门红了，但红的原因不是断言
   ⇒ harness 判「红了但定位不准」⇒ 修正类型后重跑。

### 4.2 断言顺序也是「定位精度」的一部分

`TestURLFetchFallback_DoesNotTouchTextMessages` 里，处数断言原本是 `t.Fatalf` 且排在前面
⇒ 组合臂先撞上它 ⇒ 后面的语义断言永远跑不到 ⇒ 判「红了但定位不准」。
现已把**语义断言（文本没被污染）提到前面**，处数断言放最后。

### 4.3 「text 块携带同名 URL」这一形态原本没被覆盖

原用例只在**字符串 content** 里放 URL；而遍历器只处理 content **数组** ⇒ 字符串形态压根不进
遍历 ⇒ 用例虽能区分「全 body 替换」与「字段精确替换」，但**覆盖不到「遍历范围被扩大」**。
现补上 text 块形态（单元层 + E2E 层各一处）⇒ 并配组合臂 AT10（遍历范围 + 匹配放宽同时被撤）
证明这条新覆盖**有牙**。

## 6. 诚实边界（不假装覆盖）

1. **Responses（`input[]`）形态未纳入共享字段表**：native Responses 能力表当前为空、默认不启用
   ⇒ 该路径当前不可达 ⇒ 改它属于「改不可达路径」；等启用时单开一轮。
2. **`IRTransformer` 当前无生产调用方**（仅测试）⇒ 修它的收益取决于后续接线；本轮仍修
   （用户明确点名「上传缓存」），但收益尚未兑现。
3. **附件存储的扩展名映射**对 `video/mp4` 落成 `.bin` ⇒ 存储侧既有缺口，不在本轮范围。
4. **有替换时 body 不是逐字节保持**（键序规范化、空白去掉）—— 已写进代码注释与本档。
5. 本轮**未改动生产配置的 provider 能力表** ⇒ openai 仍是 URL 模式、deepseek/gemini 仍是非 URL 模式。
