# 2026-10-29 — 模型可信度（防掺水）判定体系

> 本轮交付：把「**这个供应商给我的，是不是它声称的那个模型**」从**看不见**变成**可判定、可查看**。
> 它**不会**自动下线路由。告警只在 `provider_profile.enabled=true` 时才可能间接发生，默认是关的。
>
> 交付物：`domains/modelcredibility`（判定内核）+ 迁移 922（两张新表 + 一处既有缺陷修复）
> + 后台扫描 worker + `/api/admin/model-credibility/*` 六个端点 + 管理端页面 + 8 语种文案。

---

## 0. 一句话

仓内已有的能力面覆盖「**质量**」，没覆盖「**身份**」：

| 已有能力 | 测的是 | 测不到的是 |
|---|---|---|
| `domains/modelquality`（MMLU 精简题库） | 这个模型**答对多少题** | 上游**到底在跑哪个模型** |
| `domains/streaming/integrity` | 真实流量里**已经发生**的 `model_mismatch` / `fingerprint_drift` | 还没被用户撞上的偷换 |
| `models_canonical.standard_iq` | 外部评测站点的**平台级基线** | 本地实测与之的**可比性** |
| `domains/providerprofile`（画像） | 可用性 / 稳定性 / 成本 / 限流 … | 以上全部 |

⇒ 「你买的是 `claude-sonnet-4-5`，上游实际给你 Haiku」这类**渗水**，本仓此前**完全看不见**。
⇒ 而 MMLU 智力分**本身也测不出**这类偷换：Haiku 依然是 Haiku，它在题库上稳定地答对 60 分，
   只是它不是用户以为的那个模型。**质量正常 ≠ 身份正确。**

## 1. 缺口本体：为什么现有能力覆盖不到

### 1.1 智商分只与「自己上一次」比

`domains/modelquality` 的 `checkQualityDrop` 比较的是**同一节点**的新旧成绩。
它能抓「同一个模型突然变笨了」（供应商换了后端、模型被下线），但抓不到
「**它一直就是这个水平**，只是比它声称的低」——后者的「上一次」同样低 ⇒ 永远不降。

### 1.2 外部基线与本地题库不是同一把尺

`models_canonical.standard_iq` 是 Artificial Analysis Intelligence Index（0-100 的**平台级指数**）。
本地 MMLU 精简题库的准确率是**题目集上的正确率**。两者题库、满分口径、归一化方式都不同
⇒ **直接相减没有意义**。本轮的做法不是硬减，而是用**全平台的实测数据**拟合出一条
「标准 IQ ⇒ 期望本地准确率」的回归线（见 §3.4），再与本地实测比。

### 1.3 被动检测的时间窗

`domains/streaming/integrity` 是**被动**的：只有当真实流量里出现模型名不符或指纹漂移，
才落一条事件。而中转商换模型通常发生在**无人投诉的时段**，等用户发现时已经过了很久。

## 2. 判定口径：四把互补的尺

| 维度 | 测什么 | 数据来源 | 抓得住的偷换 |
|---|---|---|---|
| **身份自洽** `identity_score` | 上游自报的模型名 vs 请求的模型名 | 直连探测一次（读响应里的 `model` 字段） | **跨族换模型**（要 Claude 给 GPT） |
| **能力水位** `capability_score` | 本节点实测准确率 vs **同款模型**在别家的最好成绩 | 复用 `model_iq_runs` 的历史实测 | **同族降级**（Sonnet→Haiku） |
| **指纹一致** `consistency_score` | 同节点前后的请求签名是否稳定 | `prompt_tokens` 计数 + `system_fingerprint` | 后端被整体替换 |
| **参考基线** `reference_score` | 本地实测 vs 平台拟合出的期望准确率 | 全平台实测 + `standard_iq` | 整体性的降智 |

### 2.1 同族降级是「唯一抓手」

跨族换模型（Claude → GPT）会**换分词器** ⇒ prompt token 计数漂移 ⇒ 抓得到。
但**同族降级**（`claude-sonnet-4-5` → `claude-3-5-haiku`）：

- 模型名自证：Haiku 会**如实**回答自己是 Haiku ⇒ 身份自洽拿到 50 分，但**不是铁证**；
- 分词器：同族，分词器相同 ⇒ prompt token 计数**不变** ⇒ 指纹维抓不到；
- 能力：Haiku 在 MMLU 上稳定地比 Sonnet 低 ⇒ **只有这一维能抓**。

⇒ **能力维度必须拿「同款 canonical 模型跨供应商」的实测做对照**，而不是跟别的东西比。

### 2.2 同伴样本必须跨供应商

同一家中转商下的多个凭据，背后**很可能是同一个后端** ⇒ 它们会**一起**降级。
拿自己家的 A 号跟 B 号比，得到的结论是「我们两家一样差」⇒ 永远发现不了掺水。
⇒ 同伴样本必须来自 **≥2 家不同供应商**（`PeerParityConfig.MinProviders`）。

### 2.3 能力对比只用 `status='success'` 的行

`domains/modelquality/executor.go` 的 `Accuracy = CorrectCount / TotalQuestions`，
而 `partial` 行的分母**含出错题** ⇒ `partial` 行的准确率被**系统性压低**。
拿它做同伴对比，会把「当时网络抖了一下」误判成「这家在掺水」。
⇒ 能力维度只取 `model_iq_runs` 里 `status='success'` 的行。

### 2.4 缺失维度**不计入**，不是按 0 分算

四把尺都没测到 ⇒ 结论是 `unknown`（证据不足），**不是**「综合分 0」。
按 0 分算会产生两个坏后果：
① 健康但没跑过扫描的节点全部变成「综合 0」⇒ 看板上一片红 ⇒ 告警淹没；
② 「测了但极差」与「没测过」在数值上**无法区分** ⇒ 运维分不清该查谁。

⇒ 落库时 `credibility_score` 与四个子分数都可为 NULL，`measured_dimensions` 记 0~4。

## 3. 实现要点

### 3.1 探测成本

每次扫描对每个节点只发**一次**极小的请求（约 20 token 输出）。能力维度**复用**已有的
MMLU 实测，**不重跑题库**。⇒ 单节点单轮成本 ≈ 一次普通对话请求；100 节点 6 小时一轮
≈ 3.5k token/天。

### 3.2 三种请求形态

探测按上游协议走 `chat/completions` / `messages` / `responses` 三种形态（由
`providers.protocol` 决定），请求体**不带 `temperature`**（推理模型对 `temperature≠1`
直接 400）。

### 3.3 指纹基线

`prompt_token_signature` = **标定提示词**（一段固定文本）的 `prompt_tokens` 计数。
标定提示词固定 ⇒ 同一节点的两次探测 token 数应当一致；跨族换模型会换分词器 ⇒ 计数漂移。

### 3.4 参考基线的拟合

不用「`standard_iq` 直接映射到准确率」（那需要一个魔法系数），而是：

1. 把全平台每个 canonical 模型的实测准确率**按模型取中位数**（避免个别节点拉偏）；
2. 用 `(standard_iq, median_accuracy)` 做**最小二乘线性回归**；
3. 拟合的质量门（`MinModels` / `MinProviders` / `MinRSquared`）**不达标时该维度整体不参与判定**。

⇒ 宁可缺一维，不给假结论。

### 3.5 结论的四个取值

| verdict | 含义 | 触发条件 |
|---|---|---|
| `verified` | 身份与能力都与声称一致 | ≥2 个维度有数据，且都干净 |
| `suspected` | 有异常信号，证据不足以定性 | 同族身份不符 / 能力低于同伴但差距不大 |
| `diluted` | 能力显著低于同伴，或跨族身份不符，或指纹漂移 | 硬阈值 |
| `unknown` | 证据不足 | 有数据的维度 < 2 |

## 4. 落库：写进哪些「质量 / 可信度参数」

| 参数 | 粒度 | 写入方 | 说明 |
|---|---|---|---|
| `provider_model_credibility.credibility_score` + 四个子分数 + `verdict` | 凭据 × 模型 | 扫描 worker | **新建**，节点级可信度参数（带证据 JSONB 与指纹基线） |
| `provider_model_credibility_runs.*` | 凭据 × 模型 × 时间 | 扫描 worker | **新建**，判定历史（append-only） |
| `provider_quality_profiles.model_credibility_score` / `_verdict` / `_sample_count` | 供应商 × 模型 | 扫描 worker | **新建列**：供应商×模型粒度的可信度参数（取**最差**一条凭据的判定） |
| `provider_profile_daily.credibility_score` | 凭据 × 天 | `domains/providerprofile` 的评分链 | **原来恒为 0 的死维度**（权重也是 0）⇒ 本轮接上真数据，并把权重从 0 提到 0.08 |

### 4.1 为什么「取最差」而不是「取平均」

掺水是「**这家供应商在卖这个模型时至少有一条线是假的**」。
平均会把掺水的那条线稀释掉（3 条好线 + 1 条渗水线 ⇒ 平均分仍很高 ⇒ 看板上看这家仍然「正常」）。
⇒ 供应商级与凭据级的可信度**都取最差节点**。

### 4.2 为什么模型可信度**不写进** `provider_quality_profiles.reliability_score`

`reliability_score` 在仓内已被 `internal/quality/scorer_reliability.go` 占用，含义是
「**服务可靠性**」（在线率 50% + 成功率一致性 30% + 错误率趋势 20%）。
它与「这个供应商给的是不是它声称的那个模型」**不是同一件事** ⇒ 写进同一列就是**一列两义**，
读方无法分辨 ⇒ 另起 `model_credibility_*` 三列。

### 4.3 `provider_profile` 权重的取法

可信度维度拿到 0.08 权重，其余**已实现维度按比例下调到 0.92** ⇒ 既有维度之间的相对权重
**逐字不变**（不偏袒任何一个既有维度），总和仍为 1.0（`TestExtendedWeightsSumToOne` 守住）。

0.08 而不是更高的理由：这一整套评分的告警引擎（`ProfileAlertWorker`）会真的翻转凭据生命周期
（把命中告警的凭据置为 `disabled`）⇒ **内容维度**的权重必须显著低于「服务是否可用」类维度。
且缺失即跳过 ⇒ 没跑过可信度扫描的凭据，总分与本轮之前**逐字相同**。

## 5. 顺带修掉的既有缺陷

**`provider_quality_profiles` 在全新安装上会缺两列。**

## 7.1 批判审计后修掉的落库缺陷（2026-10-29 同轮）

初版把「没测到」写成 0。这会让列表、画像、质量页把「没测」读成「极差」。

| 缺陷 | 证据 | 修法 |
|---|---|---|
| `SaveResult` 对未测维度调用 `round2(0)`，综合分 0 也落成 0 | `store.go` 原 INSERT 参数 | `scoreOrNull`：未测维度与「零维综合分」写 NULL |
| 列表 `COALESCE(score,0)` + `ORDER BY score ASC NULLS FIRST` | 没测的行排在真渗水前面 | 指针返回 NULL；排序改 `NULLS LAST` |
| `/api/quality` 用 `COALESCE(credibility_score,0)` | 质量页把没测显示成 0 分 | 指针字段，前端 `null` 显示「—」 |
| 画像写入恒写 `CredibilityScore`（未测时是 0） | `pg_profile_store.go` | `CredibilityMeasured=false` 时写 NULL |
| 探测失败仍用响应里的 `model` / usage 判身份和指纹 | 500 体里的回显模型名可被当成「身份 100」 | HTTP 非 200 或传输错误时，身份与一致性都不计 |
| 失败探测用空签名覆盖上一轮基线 | `ON CONFLICT` 原样覆盖 | `COALESCE(EXCLUDED, 旧值)`，空值不覆盖 |
| worker 默认开，且网关在 settings 读空时把开关当 true | 重启即对全部活跃节点打真实请求 | settings 默认 false，网关空值也当 false |

这些不是文档订正。`verdict_test.go` 的 `TestProbeFailureDoesNotCountReportedModelAsIdentity` 与 `TestScoreOrNull` 钉住前两条。

## 8. 已知局限（如实记，审计后仍在）

1. **不能从真实会话被动判定。** 目标写了「根据会话或主动探测」。本轮只有主动探测。
   会话侧已有 `domains/streaming/integrity` 的 `model_mismatch`，**没有**接进本判定。
2. **同族降级在没有跨供应商同伴时抓不到。** 能力维要求 ≥2 家供应商都有 `status='success'` 的智商实测。
   `model_quality.enable_per_node` 默认关。不开它，能力维结构性缺失，结论多为 `unknown`。
3. **上游可以改写 `model` 字段。** 身份维只在它不改写时有效。
4. **不改路由。** `credential_model_bindings` 未接可信度分。`diluted` 不会自动下线。
5. **`tenant_id` 写死 `'default'`。** 非默认租户的判定读不到。
6. **参考基线拟合在样本不足时不参与。** 这是有意的，不是已校准的生产尺。
7. **探测只覆盖 OpenAI chat / Anthropic messages / Responses。** Gemini 与 Ollama 原生协议直接报不支持。
8. **未在生产库跑过迁移 922，也没有对真实供应商打过探测。** 测试是单元级与包级，不是端到端。

扫描默认关闭。打开后每节点每轮一次真实上游请求，周期由 `model_credibility.interval_hours` 控制。

### 9.1 本轮修掉的两个自身缺陷（记在这里而不是只在 commit 里）

1. **同伴对比把「健康节点」判成「没数据」**：初版 `ComputePeerParity` 在
   `GapPP < MinGapPP` 时返回 `Usable=false` ⇒ 而**健康的节点恰好是同伴里最好的那个**
   （差距为 0）⇒ 差距小被当成了「没测出来」⇒ 所有健康节点的能力维度全部落空
   ⇒ 判定永远只剩一两个维度 ⇒ 永远 `unknown`。
   ⇒ 修法：**「数据够不够」与「有没有差距」分成两件事**。`Usable` 只看数据可得性
   （有准确率 + 有同伴 + 同伴跨够供应商）；差距大小只决定**结论有多严重**。
   噪声带内的差距判为**持平**（不产生异常项）。
2. **一列两义**：`provider_quality_profiles.reliability_score` 被 `internal/quality`
   占着「服务可靠性」的含义 ⇒ 模型可信度另起三列（§4.2）。
