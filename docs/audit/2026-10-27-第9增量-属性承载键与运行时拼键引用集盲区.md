# 第 9 增量审计档：属性承载键与「运行时拼键」两类引用集盲区修复

> 仓库：`llm-gateway-go`（`main`）
> 基线：`eb4ffe7b9`（第 8 增量已推送）
> 性质：**只读生产**；本轮对生产的写入 = 0（仅本机 Docker 网关 + 本地 vite）
> 关联：第 8 增量审计档 `docs/audit/2026-10-27-ja-JP-zh-TW-中文清零轮.md`、`LESSONS.md` §414

## 0. 一句话结论

上一轮把 ja-JP / zh-TW 的**用户可见**简体残留清零并加了新门，但**新门的「用户可见」口径只认字面量调用** ⇒
**运行时拼键**（`t(\`prefix.${x}\`)`）与**属性承载键**（`labelKey: 'nav.item.xxx'`）这两类**用户可见**的键**从未进过引用集**，
于是它们既没进过任何工单、也没被任何门看过。
本轮把这两类补进引用集，暴露并清掉 **172 个值**的用户可见残留（含 39 条「整条中文原文」），并把 CJK 门的 referenced 口径修准。

## 1. 盲区是怎么被发现的（方法 + 观测值）

### 1.1 第一步：把「键扫描器」扩到属性承载键 ⇒ parity 门立刻爆 29 处

- 改 `web/src/i18n/scanner.ts`：新增 `KEY_PROP_RE`（`labelKey|titleKey|hintKey: '字面量'`）与 `PROP_PREFIX_RE`（`t(\`prefix.${…labelKey…}\`)`）。
- **方法**：改完立刻复跑 `node scripts/i18n-key-parity-count.mjs`。
- **观测值**：`reachable keys` 由 5252 → 5380；**hard gate violations = 29**（`promptInjection*` 全语种缺失）。
- **判读**：29 处是**我的误报** —— 真实渲染是 `t(\`sessions.config.${layer.labelKey}\`)`（运行时前缀），
  真键 `sessions.config.promptInjectionFieldBasic` 在 `zh-CN/sessions.ts` 存在。
  ⇒ **不解析前缀就会把「后缀」当整键** ⇒ 加前缀解析后 29 处归零。

### 1.2 第二步：前缀解析后仍剩 9 处 ⇒ 定位到**命名误导**

- **观测值**：hard gate violations 29 → **9**（`routing` / `model_queue` / `credential_queue` / `node_selection` / `upstream` / `streaming` / `retrying` / `terminal` / `union`）。
- **取证**：`web/src/utils/journeyStageMap.ts` 的 `labelKey: 'routing'` 等 9 个值。
- **真相**：这 9 个值是 **journey stage 名**，不是 i18n 键；真键是 `requestDetail.flow.diagram.stages.<stage>`
  （`zh-CN/requestDetail.ts` 9 个全在），消费方 `RequestProcessingFlowDiagram.vue:38` 负责拼前缀。
- **修法（治根因，不是治症状）**：把字段改名 `labelKey` → `stageKey`（含 `stageLabelKey()` 内部引用、Vue 消费点、vitest 断言），
  并在字段上方写明「它不是 i18n 键」。
- **观测值**：`i18n-key-parity-count.mjs` ⇒ **hard gate violations = 0，全指标 PASS**；
  `journeyStageMap.test.ts` 4/4 通过。
- ★ **可复用的判据**：**「属性名」是扫描器判断「这是不是一个 i18n 键」的唯一信号** ⇒ 名不副实就会污染引用集。

### 1.3 第三步：属性承载键实测 110 个 ⇒ 8 语种零缺失，但 zh-TW 30 / ja-JP 9 条仍是中文原文

- **方法**：全 `src/` 扫「属性名以 `Key` 结尾且值像 i18n 键」；实测承载 i18n 键的属性名**只有 3 个** ——
  `labelKey`(97 去重) / `titleKey`(9) / `hintKey`(4)。
  ⇒ **不用泛化 `*Key` 规则**（会误吃 `apiKey` / `dedup_key` / `copiedFullKey` 等业务字段）。
- **观测值**：110 个键 × 8 语种 **零缺失**；zh-TW **30** 条 / ja-JP **9** 条与 zh-CN 逐字相同。

### 1.4 ★★ 第四步：把「动态拼键」纳入 referenced 口径 ⇒ 门暴露 39 条用户可见的整条中文原文

- **根因**：`i18n-cjk-native-simplified-guard.mjs` 的 `refKeys` 来自 `scanner.ts` 的**字面量**引用集
  ⇒ `t(\`dataLifecycle.hotPartition.hotTableNames.${x}\`)` 这类**运行时拼键**下的键**全部落进「未引用」桶**，
  而它们**是用户可见的**（`HotPartitionManager.vue:749` 直接渲染）⇒ **硬闸形同虚设**。
- **方法**：用 `callSiteParams.ts` 的 `scanAllCallSiteKeys()` 取 template 形态的静态前缀（实测 **34** 个），
  落在这些前缀下的键一律算 referenced。
- **观测值（改口径前后同一门）**：

  | | 用户可见残留（硬闸） | 未引用残留（棘轮） |
  |---|---|---|
  | 改口径前 | ja-JP 0 / zh-TW 0（**假绿**） | ja-JP 333 / zh-TW 315 |
  | 改口径后（补译前） | ja-JP **39** / zh-TW **27** | — |
  | 补译后 | ja-JP **0** / zh-TW **0** | ja-JP 294 / zh-TW 288 |

- **交叉印证**：用**独立脚本**（`/tmp/dyn_prefix_scan.mjs`，判据 = 仓内字表 + 动态前缀）复算，
  补译后 zh-TW / ja-JP 均为 **0 条** ⇒ 两条独立路径互证。
- **自证**：门自证由 20/20 增至 **22/22**（新增 S15b「运行时拼键前缀下的键算 referenced」、S15c「前缀不匹配的键仍算 unreferenced（不许把潜伏存量洗白）」）。

### 1.5 ★ 第五步：字表判据**不完备** —— Big5 自己收录了简体字形

- **问题**：判据是「Big5 转不出来的汉字 = 简体专用字」，但 `iconv -f UTF-8 -t BIG-5` 对**「异」返回 `c9dd`**（该码位存的是繁体「異」）
  ⇒ 「能转」只说明「该码位有对应字」，**不代表这个字形在繁体里合法**。
- **实测**：`异` / `据` / `与` / `余` / `卖` 均能转 ⇒ 永远进不了 iconv 推导的 notBig5 ⇒ 门抓不到。
  对照：`活` / `量` / `常` / `聚` 是**简繁同形**，**不能**加（加了会误报合法繁体文本）。
- **修法**：`gen-cjk-native-simplified-chars.mjs` 新增 `BIG5_TRAPS`（**人工审定的正名单**），
  `notBig5 = iconv 推导 ∪ BIG5_TRAPS`；「与」「余」因出现在 ja-JP 已本地化值里而**自动**进 `japaneseOk` ⇒ ja-JP 不误报、zh-TW 照抓。
- **观测值**：字表 notBig5 453 → **458**、japaneseOk 103 → **105**；
  门因此多抓出 1 条（ja-JP 死键 `keys.list.create.keyMissing` 含「异」）⇒ **直接修掉**（日文化）⇒ 棘轮持平 294/288，**无需调高基线**。
- ⚠️ **已知未穷尽**：用「zh-CN 字频 ≫ zh-TW 字频」反查，实测还有 **185 个候选字**无法自动区分
  「简繁同形的合法用字」与「Big5 收录的简体字形」⇒ 已登记为下一轮工程（需人工逐字审定的完整正名单）。

### 1.6 ★ 第六步：`untranslated` 棘轮超限 ⇒ 逐条定性后**人工重铸**

- **方法**：`/tmp/delta_ref.mjs` 对比 HEAD 版与当前版扫描器 ⇒ 引用集 **5252 → 5371（+119）**；
  再筛出「新增键 ∩ 与 en-US 逐字相同」⇒ 共 **28** 条，逐语种数量与门报的 7 个语种超限量**逐个吻合**
  （zh-CN +2 / zh-TW +8 / ja-JP +9 / de-DE +21 / es-ES +19 / fr-FR +20 / ar-SA +21）。
- **逐条定性**（28 条）：**82 个值是真未翻译**（拉丁/阿语的 pie 图标题、Registry 类菜单名、`Offline Activation`、
  `Prompt Injection Detection`、`Data Collection Scope`、`Update & Activate`，以及 6 语种的 `1 day / 7 days / 30 days / 90 days` 单位词）
  ⇒ **已全部补译**；**剩余增量是合法英文同形**（产品专名 `VibeCoding` / `Agent Registry` / `WeChat Bot`，
  与德/西/法语的外来常用词 `Chat` / `Plugins` / `Download` / `Support`）⇒ 保留不改。
- **基线处置**：`web/src/i18n/localeValueBaseline.json` 的 `untranslated` **人工显式**重铸
  （ar-SA 983→984 / de-DE 1122→1127 / es-ES 1034→1037 / fr-FR 1120→1124 / ja-JP 712→713 / zh-CN 166→168 / zh-TW 678→680），
  并在同文件写入 `baselineRaiseReason`（逐条理由）；`sameAsSource` 同步**下调**（ja-JP 1345→607、zh-TW 2133→1474，因本轮补译 197 个值）。

   「7 días」才暴露出来 —— ★ **「多脚本读数不一致」时，先怀疑装置，再怀疑产品**。
