## 一、owner 需求原文与本轮结论

> 请检查并对比 https://llm.itestu.cn/dashboard 中「看板」与「会话与统计」中的费用数据及请求相关的数据的一致性，需要注意分析相关的统计的 api，确定数据统计的正确性，并且在这些页面中增加帮助信息的按钮，点击可以查看所有数据的统计标准，但于核实。

**结论（一句话）**：两页的数字**本来就不该相等**——它们不是同一套口径：看板是**请求级**（真源 `usage_facts`，窗口＝系统时区日历日零点→此刻），会话与统计是**会话级**（真源 `session_summaries` + 物化视图，窗口＝滚动 N 天）；更关键的是**两页「排除探测」剔的不是同一批流量**，实测会话侧把 **$6,452.73 的业务流量**当成探测剔掉了。⇒ 本轮把这件事**写进用户可见的「统计标准」正文**，并把 6 项已定位的缺陷登记待裁决。

1. **同窗口 A/B**：同一登录态（`demoadmin`），对两个 API 用**同一时间语义**分别取数并逐项对拍。

## 五、六项差异根因（已定位，未在本轮修复）

### D1 ★ 会话侧「排除探测」过度剔除（费用差的头号原因）

- **现象**：会话与统计费用只有看板的 34%（2,717.62 vs 8,013.93）。
- **证据**：被会话宇宙剔除的 15,898 个会话，其主请求在 `usage_facts` 里 **100% 是 `traffic_class='business'`**，合计 **$6,452.73**；同一窗口请求级事实源里真正标为探测的流量合计仅 **$1.81**（89,903 笔探测请求只花 $1.81）。
- **根因**：两侧判定面不同——请求级按 `usage_facts.traffic_class`（写入时由 origin_stage 派生）；会话侧按 `sessions.is_probe`（运维手工位）+ `session_analytics_is_probe(owner, client_type, title)`（**标题/客户端类型模式**）。后者把大量真实业务会话判成探测。
- **影响**：会话与统计的费用、请求数、成功率、缓存率**全部**系统性偏低。
- **建议**（待裁决）：会话侧改用与 `usage_facts` 同源的 traffic_class 判定；或在两处用**同一份**「探测判定」服务（当前是三套：usage_facts.class / sessions.is_probe / session_analytics_is_probe）。

### D2 ★ `sessions` 表重复行被 JOIN 放大（请求数倒挂）

- **现象**：会话与统计「总请求数」72,098 **大于**看板 65,774——尽管会话口径只覆盖子集。
- **证据**：同窗口按会话去重后请求数合计只有 **53,031**，比面板显示少 **36%**；`sessions` 表存在重复 `(session_id, tenant_id)` 行，最严重的一个会话键有 **30 行重复**（全表 261,753 行 vs 261,545 个唯一键）。
- **根因**：`session_summaries JOIN sessions` 按 `(session_id, tenant_id)` 连接，重复行让同一会话的 `request_count`/`total_cost_usd` 被累加多次。
- **建议**（已采纳并实施）：连接侧对 `sessions` 去重（`DISTINCT ON (session_id, tenant_id)`）——2026-11-23 由 `761e641ed` 落地（面板 SQL 与物化视图 994 同步改）。

### D3 ★ 看板「总积分」与时间范围无关

- **现象**：看板积分卡在「今天 / 近 7 天 / 近 30 天」三档下**完全相同**（实测三者同为 **86,925**）；而同一页趋势图的积分合计（7 天）是 **1,767,183**。
- **证据**：`usage_facts.credits_charged` **全表 298,037 行恒为 0**；`session_summaries.total_credits_charged` 全表 262,370 行**也恒为 0**；看板英雄区的积分来自 `boardcache` 的**实时增量**（`domains/stats/boardcache/fold.go` 把同一批 delta 折进各 days 预设）。
- **根因**：请求级与会话级事实表的积分列都没写入；页面显示的是 Redis 实时增量。
- **建议**（待裁决）：积分要么接回真实账目源（`maas/credits_sql.go` 有 `COALESCE(credits_charged, 估算)` 的口径可复用），要么在卡片上明示「实时增量·非窗口值」。本轮**已在帮助正文写明**。

### D4 看板自身两套真源不一致（卡片 vs 趋势图）

- **现象**：30 天窗口下，英雄区卡片 140,969 笔 vs 趋势图各桶合计 160,451 笔，**差 +13.8%**。
- **根因**：卡片读 `usage_facts`（事务内落库、无丢失面），趋势图读 `request_stats_minute`（游标 + 30min 有界 resweep 的扫描器，重启/迟到会**永久漏统或重复**）。
- **建议**（待裁决）：趋势图也改读 `usage_facts`（按桶聚合）。

### D5 会话与统计「今天」档位 100% 失败（30 秒超时）

- **现象**：`GET /api/admin/dashboard/session-overview?days=1` **稳定 500**（4/4 次复现，每次恰好 30.0s）；服务端日志 `details: "timeout: context deadline exceeded"`，阶段名 `session summary aggregates`。`days=7 / days=30` 正常。
- **根因**（`EXPLAIN` 实测）：`session_dim` 只有 `(tenant_id)` 索引（`idx_session_dim_tenant`），没有 `(session_key, tenant_id)`。窗口越小 → `session_summaries` 命中的行越少 → 计划器改走**嵌套循环**，每行对 `session_dim` 做一次 `Index Scan ... cost=7078`（按 tenant 全量回表）⇒ 窗口 1 天实测 1,540 行 ⇒ 估算代价 1,090 万 ⇒ 30 秒打满。
  > 典型形态：**输入越小计划越差**——「今天」档恰好是最小输入。
- **建议**（待裁决）：给 `session_dim` 加 `(session_key, tenant_id)` 索引（或把 `session_dim` 连接改成按 `session_key` 的哈希表 + 显式 `enable_hashjoin`/`SET LOCAL` 提示）。

> 触发：第一轮交付并核实后，目标里第 (2)(4) 项仍有未闭合处——「会话与统计」页

### 10.1 D5 根因坐实（211 生产库 EXPLAIN ANALYZE，真实聚合查询）

`session_dim` 只有 `tenant_id` 前缀索引，而会话宇宙的 JOIN 键是
`sd.session_key = ss.session_key AND sd.tenant_id = ss.tenant_id` ⇒ PG 只能
「用 tenant_id 索引取回整个租户、再按 session_key 过滤」：

```
-> Index Scan using idx_session_dim_tenant on session_dim sd
     Index Cond: (tenant_id = …)   Filter: (session_key = …)
     Rows Removed by Filter: 262531      ← 每个循环丢 26 万行
     loops=2236                          ← build 侧有几行就循环几次
  Buffers: shared hit=407,833,935 read=7,566,565
  Execution Time: 121788.473 ms           ← 2 分钟
```

⇒ **输入越小计划越差**：大窗口 build 侧行数多 ⇒ PG 走 hash join（几秒）；
「今天」档 build 侧只有几百行 ⇒ PG 反选嵌套循环 ⇒ 每个 build 行重扫 26 万行
⇒ 平方级放大。API 只等 30 秒就被 context deadline 掐断 ⇒ 页面显示失败而非 0。

**零写入证明**：把 `session_dim` 的连接键换成等价的 pkey 列 `gw_session_id`
（实测 `session_dim` 262,536 行 **零行** `gw_session_id <> session_key`），
同一条查询变成 `Index Scan using session_dim_pkey (actual rows=1 loops=2237)`
⇒ **Execution Time: 194.910 ms（121,788 ms → 194.9 ms，625 倍）**。
但「`gw_session_id` ≡ `session_key`」**未被 schema 约束** ⇒ 不拿它当修法，
只拿它当「瓶颈确实在这条连接上」的证据。

### 10.2 修法与投递面

- **修法**：补 `idx_session_dim_session_key (tenant_id, session_key)` ⇒ 计划
  变成 `Index Cond: (tenant_id=… AND session_key=…) ⇒ 命中 1 行`；**JOIN 键、
  谓词、任何数字口径逐字不变**（不改查询，只补索引）。
- **投递**：走 **db-open ensure 链**（`db.ensureSessionDimSessionKeyIndex`）：
  ① `CREATE INDEX CONCURRENTLY` 不能在事务里执行 ⇒ installer 的
  `psql --single-transaction` 承载不了 ⇒ ensure 才是存量库的收敛通道
  （与 `ensureUsageFactsOccurredAtIndex` / `ensureSqlAuditPartialIndexes` 同款）；
  ② 三位迁移号（`NNN_*.sql`）是仓内规范、999 已是当前最大编号 ⇒ 本轮不新开号。
- **失败语义刻意非致命**（记 Error 日志并继续启动）：一个 dashboard 统计档位
  用得上的索引，不该有能力把整个网关拉下线。
- **门**：`db/db_session_dim_session_key_index_test.go`
  ① 文本契约门（DDL 键/列/`CONCURRENTLY`/INVALID 残留清理/挂进 ensure 链/
  非致命/索引列 ⊇ 会话宇宙连接键）；
  ② 真库回归（scratch 一次性库：建出 → `indisvalid` → 幂等 → EXPLAIN 走索引）。
- **验证**：`go build ./...` ✅；`go test ./db/` 全绿 ✅；`./admin/dashboardapi/`、
  `./domains/analytics/` 全绿 ✅；`gofmt` 零漂移 ✅；真库回归实跑通过 ✅。

### 10.3 D2 的量级补齐（费用层面前一轮没量到）

`sessions` 是**按 UTC 日分区的会话历史表**——同一会话每天续一行（实测样本：
`gw_5992d833…` 有 2026-11-16/17/18 三行），而 `session_summaries` 每会话只有
一行累计值（该会话 `request_count=1888`、`total_cost_usd=394.66`）⇒ JOIN 按
`session_id` 跨分区命中 3 行 ⇒ **同一会话被累计 3 次**（正好对上接口里的
`max_cost_session=394.66`——它被记成了 3×394.66）。

同 7 天窗口、同一套会话宇宙谓词：

| 口径 | 会话侧报出 | 按会话去重后 | 虚高 |
| --- | --- | --- | --- |
| 请求数 | 72,815 | 53,702 | **+35.6%** |
| 费用（USD） | 2,721.09 | 1,692.78 | **+60.7%** |
| 会话数 | 19,341 | 19,314 | +0.14%（可忽略） |

⇒ **会话侧的费用虚高幅度（+61%）远大于请求数**，且**看板（请求级）不受影响**
⇒ 跨页比费用时，会话侧数字偏高 ⇒ 第一轮正文里「费用明显低于看板」的解释
（只归给 D1 探测过度剔除）**不完整**：去重后会话侧费用 $1,692.78 + 被剔除的
$6,452.73 ≈ $8,145.51，与看板 $8,013.93 已在同一量级内。

**去重口径尚有一处需裁决**：150 个多行会话里有 **11 个**在分区行之间存在属性
漂移（`client_type` / `is_probe` / `owner_user` / `title` 不同）⇒「一个会话
用哪一行代表」有取舍（最新分区行＝当前状态 vs 首日行＝会话开始时的状态）。
另 139 个会话属性完全一致 ⇒ 取哪一行都一样。
