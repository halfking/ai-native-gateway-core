# 会话分析闭环审计与根修 · 主档（2026-11-20）

> 需求：「将用户发出的提示词进行合并和总结，分析任务的标题与相关的项目，修正会话的元数据，再进行统计分析」——对此链路做批判式审计，修正发现的问题，更新文档，提交合并推送，部署 211（蓝绿）→ 154 → 245。
> 结论先行：**这条链在生产上是断的**——断点不在「实现质量」，而在「接线与事件供给」。本轮修 6 处断点 + 2 处口径债，全部活体/钉测/变异三层验证。

## 六、通用式（本轮沉淀）

1. **「列在 schema 里」≠「通道存在」的姊妹命题：「worker 写好了」≠「事件供得上」**——订阅者三件全接线、发布者零个，整条链静默空转且无任何测试红（消费侧断言不了供给侧的存在）。
2. **假红掩护真错的取证版：二手叙述掩护假缺陷**——子审计 A 的 P1 D1 从提交信息推定「生产已演进」，活体取证发现两个库都不存在演进版。**跨库取证必须实测 pg_get_viewdef，不能从提交信息倒推库状态**。
3. **迁移的执行预算必须写进文件**：共享 PG 服务端 30s statement_timeout 掐断 90s+ 的视图构建 ⇒ 「台账记了、对象没建」的半途而废态；`SET statement_timeout`（会话级）是唯一双通道生效形态。
4. **钉测要钉「调用行」不是「标识符出现」**——M4 变异首版幸存实证：条件判断与调用共享标识符，Contains 标识符的钉测对「删调用留条件」免疫。
5. **死代码接活前先对真库验证它的 SQL**：UNUSED 标记的 worker 不只是没人用，还坏着（42703）；接活=修根因+接线+护栏三件同轮。
6. **降级要分层**：LLM 缺席不该拖死零成本的规则层（元数据 final/归属/关闭）——worker 的早退语义从「summarizer nil ⇒ 全跳」改成「跳摘要、跑钩子」。
