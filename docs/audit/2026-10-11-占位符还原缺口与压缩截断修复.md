# 脱敏占位符还原：方案全景、三处未还原缺口与压缩截断修复（2026-10-11）

> 任务：拉取最新代码后重查敏感处理——「有些替代的占位符没有正确还原」；
> 总结全部方案；对脱敏与还原做完整验证；确保压缩与 LLM 往返间不丢数据。

## 一、方案全景（截至本轮，全部机制一览）

**可逆脱敏核心（security/sanitize）**

| 机制 | 位置 | 职责 |

| 输入侧预留 | `input_tools.go` `reserveInputPlaceholders` | 客户端带回的既有标记（含改写形）抬高高水位，防新分配撞号 |

| 非流式还原 | `native_restore.go` + `restoreResponseBody` | Anthropic Messages / OpenAI Responses 结构树按可见 lane 还原；tool arguments JSON 解码→还原→重编码；残留探针 fail-closed |

| 防外传 | `DetectScope(ScopeEgress)` | 公网地址进 tool 参数硬阻断；私网/环回豁免（r1008/dc63f19ff/0d2367ba2） |

**压缩 × 脱敏数据流（domains/hooks/compression + domains/transformation）**

```
输入中间件产出 sanitized body + ctx 桥（WithSanitizeMap / WithSanitizeInfo /
  WithGeneratedTextGuard）
→ SessionCompressor.Prepare：缓存 outbound（含旧摘要+占位符）→ generation
  守卫（map 过期/换代即整体弃用压缩层、全量重发——防旧占位符新值错误还原）
→ 摘要生成（LLM 或机械兜底）：摘要**有意保留**占位符原样，等回注后由响应
  侧还原；生成文本守卫只遮新敏感值、不碰既有标记
→ 摘要拼接回注（rebuilder / IncrementalBuild / findDeltaAnchor）
→ 上游 LLM → SanitizeRestoreInterceptor（generation 守卫 + TTL 刷新）
```

`session_summaries` 表是观测面摘要，不回注请求。观测面摘要截断
（sessiondigest 260 rune / sessionsummary 500/300 rune，rune 安全）仅影响
仪表盘观感，不在本轮范围内。

## 二、本轮抓到的三处「占位符未正确还原」

### 缺口 1：Anthropic 流式 thinking 增量不在任何还原通道

`restoreStreamAnthropicDelta` 只处理 `delta.text / delta.input /
delta.partial_json`。thinking 增量（`delta.type=thinking_delta`，字段
`delta.thinking`）有两个真实来源：原生 Anthropic extended thinking 透传，
以及 chat→anthropic 桥把上游 `reasoning_content` 合成成 thinking_delta
（`anthropic_stream.go:574`）。非流式侧的 `thinking` 块**有**还原
（native_restore），流式侧漏了——不对称就是缺陷本身。

后果分两支：已映射占位符在思考流里**原样下发**（未还原）；残缺标记则触发
`containsReservedJSONToken` → `maskUnmappedStreamMarkers`（同样没有
thinking lane）→ 整帧阻断并锁死后续所有帧——流被拦腰截断。

**修复**：`restoreStreamAnthropicDelta` 增加 `thinking` lane
（`anthropic.<index>.thinking`，纯文本通道）；`maskUnmappedStreamMarkers`
的 content_block_delta 字段表补 `thinking`。

### 缺口 2：Responses 终态事件内嵌全文无还原，整帧阻断截断流

`response.completed` / `response.incomplete` 内嵌完整 response 对象、
`response.output_item.done` 内嵌完整 item、`*.part.done` 内嵌最终
summary/text——上游从未见过还原值，这些嵌套树里**永远是原始占位符**，
即便每个 delta 都已逐段还原。此前这些事件不在还原通道里，直接撞
`containsReservedJSONToken` → 整帧阻断：所有内容帧送达之后，终态帧丢失，
客户端流截断。

**修复**：新增 `restoreStreamResponsesTerminal`，嵌套树复用非流式同款
restorer（`restoreNativeResponsesBody` / `restoreNativeTextField`）——
已映射还原、未映射 `[REDACTED]`、未知 vendor 字段残留照旧 fail-closed。

### 缺口 3：探针早退过滤只认花括号，裸形态（brace-less）标记漏检

2026-10-10 给容错阶段加了裸形态（`SENSITIVE:phone:1`，minimax-m3 实测会
剥掉花括号），但三处早退过滤仍是裸形态之前写的「无花括号即无标记」：

- `markerSpans` 的 `ContainsAny("{｛")`（全部探针的地基：placeholderCandidate /
  hasReservedPlaceholder / containsNonForeignMarker）
- `mayCarryMarker` 同款（hop.go）
- 连带：JSON 字符串值里的裸标记会被 span 模式的**花括号分支吃掉**
  （JSON 结构本身是 brace run），裸分支永远看不到它

后果：非流式响应里字段级 gate（placeholderCandidate）判假 → 还原被跳过 →
残留探针随后把**整条响应阻断**；未覆盖流式 lane 里的裸标记则直接放行。

**修复**：过滤改为「无花括号**且**无 fold-case `sensitive` 词才放行」
（零分配 ASCII 折叠扫描，成本类不变）；`hasReservedPlaceholder` 在
fold-词预筛命中时走 JSON 解码逐叶探测，叶子检查换成 hop 感知的
`looksLikeUnparsedNonForeignMarker`（`containsResidualPlaceholder` 原先
的 `looksLikeUnparsedMarker` 不认识 hop 豁免——把下游网关的合法标记误判
为残留，本轮在 hop 契约测试上现形后一并修正）。

## 三、压缩与 LLM 往返间的数据丢失：四处截断可切裂占位符

压缩链路有四处字节/字符级截断，切点落在 `{SENSITIVE:…}` 内部时产生残缺
标记——残片进入摘要输入（摘要 LLM 会带回摘要文本）或直接进入出向请求；
模型回显后该占位符的还原永久失效，残片还会让响应侧探针阻断响应：

| # | 位置 | 原行为 | 产物去向 |
|---|---|---|---|
| 1 | `compaction.go` `truncateForLog(512)` | 字节截断 | 摘要输入（tool 参数/结果） |
| 2 | `compaction.go` `trimTextToTokenBudget` | 头部字节截断 | 摘要输入（900K token 预算） |
| 3 | `recovery_coordinator.go` `extractSummaryText` 500/300 | 字节截断 | **机械兜底摘要→出向 body+SessionCache**（最高危） |
| 4 | `transformation/responses_compress.go` 砍半循环 | rune 砍半 | **直接上行**（Responses 独立压缩链） |

**修复**：新叶子包 `internal/markerbound`——与 sanitize 同款 span 语法
（花括号形+裸形+残缺尾），暴露 `SafeCutKeepHead / SafeCutKeepTail /
SafeCutKeepTailRunes`：切点落在标记内则移到标记边界，保留侧保住完整标记
（≤96 字节超限）。单独一处例外：砍半循环中标记横跨切点且起点为 0 时，
保整枚会令循环停滞，改为在标记末尾整枚丢弃保终止性（测试钉住）。

为什么放 `internal/`：sanitize→compression 有 import 边（SanitizeInfo 桥），
compression 不能反向 import sanitize；transformation 是刻意保持的叶子包。
语法副本的漂移由 `security/sanitize/markerbound_contract_test.go` 钉死：
两套实现对共享语料必须给出**完全一致**的 span 集（沿用
`hashTenantForSanitizeKey` + r1013 标记契约的既有模式）。

**保留的已知边界（记录，不属缺陷）**：摘要重建时旧摘要消息被新摘要替代
（其中的占位符引用随消息离场，映射仍在 Redis）；整条消息/轮删除属设计内
有损压缩（Lossiness 有记录）；session cache TTL 可配至 24h 而 sanitize map
TTL 30min——空闲超时后 generation 守卫每轮重置压缩层（全量重发），行为
正确（防错还原），只是摘要上下文反复重建，配置联动留 owner 决策。

## 五、测试写判据时踩到的坑

1. **`hasReservedPlaceholder` 的解码走树必须 hop 感知**。把逐叶探测从
   「仅 `\u` 转义包体」扩展到「fold-词命中即走」后，4 个 hop 契约测试立刻
   红：`containsResidualPlaceholder` 的叶子检查里 `looksLikeUnparsedMarker`
   不认识 hop 豁免，下游网关的合法标记被误判残留 → 整响应阻断。豁免语义
   必须贯穿**每一层**探针，缺一层就是假红/假绿。
2. **JSON 值里的裸标记对 span 扫描不可见**：花括号分支把 JSON 结构消费掉，
   裸分支根本轮不到。逐叶（解码后）探测才是裸形态的正确观测层。
3. **跨包测试的 import 环**：compression 的**包内**测试不能 import
   sanitize（sanitize→compression 已有边）；端到端测试放
   `package compression_test`（外部测试包）即可两侧都用。
4. **r1014 编号撞号**：并发会话先占了 r1014（egress 豁免判据），本轮全部
   改用 r1015——多会话共享仓库，命名前先 `git fetch` 查远端最新编号。
