## §4 头号发现二：★★ `bundle` 把每环境的 `collected_at` 丢了（★ 而这正是三轮诚实边界的直接成因）

### §4.1 现象

★ R163 轮产出的 `db-object-census.tsv` 头部长这样：

```
# ★ bundled_at=2026-10-26T05:22:08+00:00
# ★ env=local rows=2667 sha256=d1d56383b8d9930e1ec698551c92ed2a5ed9a8f64db6d0fe48e4979262afedc4
# ★ env=fresh rows=2487 sha256=…
# ★ env=252 rows=3473 sha256=…
# ★ env=211 rows=2853 sha256=…
```

★★ **每环境只有 `rows` 与 `sha256`，★ 没有 `collected_at`** ⇒ ⇒
★★ ⇒ **「252 这批数据是几号采的」在产物里查不到** ⇒ ⇒
★★ ⇒ ★★ **而 `bundled_at` 是【bundle 的时刻】，不是【采集的时刻】** ⇒ ⇒
★★ ⇒ ⇒ **⇒ 四个环境的数据可能隔了三周，却看不出来** ⇒ ⇒ ⇒
★★ ⇒ ⇒ **⇒ 这就是 R161/R162/R163 三轮 §9 里那句话的直接成因。**

### §4.2 修法

★ `collect` 本来就写了 `collected_at`（★ 在单环境文件的头部）⇒ ★ **只是 `bundle` 没透传** ⇒ ⇒
★ ⇒ **改 `bundle` 与 `columns-bundle` 各加一行透传** ⇒ ⇒ **产物自带每环境的采集时刻** ⇒ ⇒
★★ ⇒ **⇒ 「快照有多旧」从此可查。**

### §4.3 ★★ 而第一次透传【没生效】—— ★ 被自证逮到

★ 第一版写完，直接 bundle ⇒ ⇒ 头部出来是：

```
# ★ env=local rows=2667 sha256=… collected_at=unknown
```

★★ **全部 `unknown`** ⇒ ⇒ **⇒ 透传被静默吞掉了。**

★★ **真因**：★ 正则写成 `r"#\s*collected_at=(\S+)"` ⇒ ⇒ **而头部 token 前面还带着 `★ `**（★ 形如 `# ★ collected_at=…`）⇒ ⇒ ⇒ **`#\s*` 锚不到 `★ `** ⇒ ⇒ ⇒ **正则零命中 ⇒ ⇒ 而代码把它当「没找到」⇒ ⇒ 写成 `unknown` ⇒ ⇒ ⇒ **「查不到」被伪装成「有值」。**

★★ ⇒ ★★ **⇒ 通用式：★★★ 透传类字段的兜底值不许是 `unknown`/`-` 这类【看起来像有值的字符串】⇒ ⇒ 它会把【透传失败】伪装成【采集时刻未知】⇒ ⇒ ⇒ 兜底必须【显式为空】⇒ ⇒ 空 ⇒ ⇒ 门才判得出「没透传」。**

★★ 修法：★ 正则改成无锚 token 匹配（`collected_at=(\S+)`）⇒ ⇒ ★ **顺带把 `env=` 的匹配也改了**（★ 原来那个 `#\s*env=` 其实同样匹配不到 ⇒ ★ 只是靠「从行首字段兜底取 env」才没出事 ⇒ ⇒ ★ **两处都是「锚错了但被兜底掩盖了」**）。

## §5 头号发现三：★★ 手搓采集 SQL ⇒ 两边口径分叉（★ 252/211 各采到 **0 行**）

### §5.1 现象

★ 列底账的采集 SQL 要带一个 `(表, 列)` 白名单（★ scope=expected-index-key-columns）。
★ 本地采集走工具自己的 `--keys-from`（★ 工具内部从期望集解析白名单）⇒ ⇒ **local=879 / fresh=891 行** ⇒ ⇒ **与 R163 逐字一致** ✔。

★ 而远程采集（★ 252 / 211）要先把 SQL 喂给远端 psql ⇒ ⇒ 那份 SQL **我手搓了**。

★★ **结果：252 与 211 各采到 0 行。**

### §5.2 真因

★ 期望集 TSV 的列是：

```
migration_no | index_name | table | source_file | declared_columns | note
```

★★ **我把手搓脚本里的 `parts[3]` 当成了 `declared_columns`** ⇒ ⇒ **它其实是 `source_file`** ⇒ ⇒
★★ ⇒ 白名单里全是 `('_request_logs', '862_partition_family_leading_ts_idx.sql')` 这种**垃圾对** ⇒ ⇒
★★ ⇒ ⇒ **一个都匹配不上 ⇒ ⇒ 0 行。**

★★ ⇒ ★★ **⇒ 通用式：★★★★ 「手搓采集 SQL」= 自造一个口径 ⇒ ⇒ 它必然与工具内部的口径分叉 ⇒ ⇒ ⇒ 而分叉的表现是【静默地空】，不是【报错】⇒ ⇒ ⇒ 所以【采集 SQL 必须由工具生成】。**

### §5.3 修法：★ 工具新增 `--emit-sql`

★ `db-object-census.py columns --keys-from <expect.tsv> --emit-sql <file>` ⇒ ★ 只产出采集 SQL，不连库。

★★ ⇒ ★★ **⇒ 修完之后，工具产出的 scoped SQL 与 R163 轮那份**逐字相同**（★ 38096 bytes，★ `diff` 零差异）⇒ ⇒ ⇒ **⇒ 这证明 R163 的远程采集本来就是对的**（★ 252=912 / 211=894）⇒ ⇒ ⇒ **⇒ 本轮的 0 行纯粹是本轮手搓造成的。**

## §8 诚实边界（★ 本轮**没有**证明的事）

1. ★★ **「快照没过期」只覆盖【结构】。** ★ 指标层（★ 行数 / 大小 / 统计信息）**每时每刻都在动** ⇒ ⇒ **本轮没有也不可能把它做成稳定基线** ⇒ ⇒ ⇒ **⇒ 稳定判据只有结构漂移。**
2. ★★ **结构漂移的判据只认【对象集合 + 形态】。** ★ ★ 它**不认**「对象里的数据变了」（★ 数据变化本来就不该进对象底账）⇒ ⇒ **⇒ 本门不是数据一致性检查。**
3. ★★ **对拍只在采集时刻成立。** ★ 采集完到对拍之间，现场可能又变了 ⇒ ⇒ **⇒ 本轮四环境的「结构漂移 = 0」是【2026-10-26T10:16Z 那一刻】的结论** ⇒ ⇒ ⇒ **⇒ 要持续保证，必须把它接进部署序列**（★ §9-1）。
4. ★★ **本轮没有改任何生产部署脚本。** ★ ⇒ ⇒ 「对拍自动执行」这件事**尚未成立** ⇒ ⇒ ⇒ **⇒ 现状仍是【要人记得跑】。**
5. ★★ **新鲜度判据里【没有时间阈值】。** ★ ★ 这是有意的（★ §2）⇒ ⇒ **⇒ 副作用是：一个【从来没人重采】的快照，只要现场没变，就一直显示「没过期」** ⇒ ⇒ ⇒ **⇒ 这是本设计已知的盲区，★ 留给属主裁决**（★ §9-2）。
6. ★★ **`verify` 的对拍面是【17 列底账】**，★ **不含列底账**（★ `db-object-columns.tsv`）⇒ ⇒ **⇒ 「列被 DROP 了但对象集合没变」这件事，本轮的对拍看不见** ⇒ ⇒ ⇒ **⇒ 它要靠缺口台账那条线（★ R163 的「列级联退役」判据）**。
