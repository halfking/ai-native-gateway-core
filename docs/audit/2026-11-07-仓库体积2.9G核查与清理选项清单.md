> 性质：**只读核查轮，零删除、零提交、零部署**。所有体积结论均取自本机 git 对象库实测读数。
> 待用户裁决后再执行对应选项。本文只登记事实与选项，不做决定。

## 0. 一句话结论

codeup 仓库 2.9G 的构成 = **① 几个「每轮追加重写」的巨型台账文档被提交了近千个版本（主因）＋
② 约 365MB 编译二进制 / 工具数据库曾被打进仓库（存量）＋ ③ 少量单件大文件**。
源代码本身（Go + 前端）只占小头。仓库已有 .gitignore 与 binary gate 防护（增量已止血），剩下全是存量。

## 6. 选项（按风险从低到高；**均待裁决，本轮未执行任何一项**）

- **选项 0｜先问 codeup 管理员跑服务端 GC（成本最低，建议第一步）**
  假设 H1：codeup 报告的 2.9G ≈ 每 push 一包、服务端未积极 repack ⇒ 无跨包 delta，且垃圾包未回收。
  本地同内容 gc 后只有 990MiB ⇒ 服务端 GC 后可能直接降到 ~1.0-1.5G。零代码、零历史改写。
  本轮无法从本地验证服务端行为，此为与实测差值吻合的最简假设。

- **选项 1｜HEAD 减肥（低风险，一次普通提交）**
  删除 `cmd/llm-gw-annotator/llm-gw-annotator`（14MB）、`installer/llm-gw-installer`（13MB）两个二进制
  （gate 豁免行同步收口）＋ 处置 `test-image-large.jpg`（16.6MB：压缩 / 移外部存储 / 直接删，三选一）。
  效果：快照 -44MB、不再随 checkout/clone 传播；**仓库历史体积不变**（codeup 总量基本不动）。
  另建议顺手把 `.scratch/` 补进 .gitignore。

- **选项 2｜治理增长速度（低风险，流程约定）**
  `LESSONS.md`（691 版）按 AGENTS-archive 先例做周期性分档归档（如按月/按量），避免单文件无限追加。
  台账类文档已有分档先例，属既有范式扩展。

- **选项 3｜历史改写删除大 blob（高危，需全员协同，最后考虑）**
  `git filter-repo` 从全历史剔除 §2 的 14 项二进制/工具库 ＋ §4 的 2 项（≈370MB 未压缩；
  按服务端口径收益可能显著更大）。**代价必须先知情**：16,884 个提交 sha 全变；所有部署记录钉的
  git_sha 失效（版本戳台账读数口径破坏）；github 镜像 sync 链路需按新历史重建；全部 active
  checkout 重新 clone；open 分支（docs/bank-security-profile）需要 rebase。二进制无审计价值，
  删了不损失历史信息，但操作窗口需要停写协调。
  台账文档的历史版本**不在本选项范围内**（审计正文价值）。

## 11. 核查方法（可复现）

```bash
git rev-list --objects --all                     # 178,393 个可达对象
git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(objectsize:disk)' --batch-all-objects
# blob>1MiB 按路径聚合：1,787 个；未压缩合计 4,014MB；pack 内（近似）≈700MB
git ls-tree -r -l HEAD | sort -k4 -rn            # HEAD 仍挂的 >512KB 文件
git log --diff-filter=A/D -- <path>              # 每个二进制的进入/删除时间
```
