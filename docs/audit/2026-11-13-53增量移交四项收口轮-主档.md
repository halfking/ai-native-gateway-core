## §六 慢包实测回填（round 纪律）

- **本轮实测（两个会话的并发现场，比单点读数更有信息量）**：
  ① 并行会话（另一会话，homebrew go1.27.3）在同一 checkout 跑 solo 掏空门（25m 预算）⇒
  **1500.707s panic 超时**（/tmp/hollowout-solo.log，含两臂「读方超时（10m0s）」）⇒
  **25m 不够的活体实锤**（其两臂失败形态＝掏空门内部的 600s 探针预算在重载下也顶穿）。
  ② 本会话全包实测（sdk go1.27.2，-timeout=2400s）与之并发 ⇒ **2400.679s 撞死**；
  user 234.56s + sys 97.68s / 墙钟 2405s ⇒ **~86% 时间在等待**（整仓掏空锁排队 + CPU 排队），
  不是包的计算变慢。
  ③ 结论（§707①③）：代价 = f(树状态 × 缓存温度 × 并发会话)；预算上界 =
  自身一轮（暖 ~16min / 冷 36min+ / 并发日掏空门 51m15s 仍在探）+ 掏空锁排队
  （hollowoutLockWait ≤15min）⇒ **7200s** 覆盖；「实测撞死先看 CPU 占墙钟比例」＝
  分辨「包重了」vs「包在等」。
- 历史暖图读数（低负载档）：766s（48h 第四轮）→952s（53 增量）→1122.817s（r1050）。
- 判据：7200s / 上界（并发日掏空门 51m+ 完成余量）≈ 1.3~1.5x；若 7200s 在常态机
  仍越线 ⇒ 重开 §648 二选一（拆通道收益比翻转）。
