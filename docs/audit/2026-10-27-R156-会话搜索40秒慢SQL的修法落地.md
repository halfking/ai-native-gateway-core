## §1 缺陷本体（R154 已取证，本轮复述作为修法依据）

`admin/session_catalog_usage.go` 的 `catalogSearchSQL`：

```sql
WHERE session_key IS NOT NULL
  AND btrim(session_key) <> ''
  AND (session_key        ILIKE $1 ESCAPE '\'
    OR COALESCE(title, '')         ILIKE $1 ESCAPE '\'
    OR COALESCE(primary_model, '') ILIKE $1 ESCAPE '\')
  AND ($2 = '' OR tenant_id = $2)
ORDER BY last_request_at DESC NULLS LAST
LIMIT $3
```

★ 252 生产只读实测（868,711 行）：

- `EXPLAIN`（**不带** ANALYZE）⇒ **Parallel Seq Scan on session_summaries**
- `EXPLAIN ANALYZE` ⇒ **Execution Time = 40,415.968 ms（40.4 秒）**
  （Planning Time 仅 16.679 ms ⇒ ★ **不是规划问题，是执行问题**）
- Rows Removed by Filter = 289,543 × 3 workers；Buffers hit=34,435 read=17,177

⇒ ★★ `mergeCatalogSearch` 的 ctx 超时是 **2 秒**
（`admin/session_catalog_usage.go`：`context.WithTimeout(ctx, 2*time.Second)`）
⇒ ⇒ ★★★ **它每次都超时** ⇒ ⇒ `slog.Warn("catalog search failed")` ⇒ ⇒ **静默降级成「没搜到」**
⇒ ★★ 用户看到的是**空结果**，**不是报错**。

★ 决定性对照（同一张表、同一条件）：**只查 `session_key` 一列** ⇒ `Parallel Index Only Scan using session_summaries_pkey`；
**三列 OR** ⇒ **Parallel Seq Scan**。
⇒ ★★ **只要 OR 的三支里有任何一支不可索引，整条 OR 就退回全表扫描**。

## §2 修法（三个决策，每一个都有代价）

### 2.1 决策 A：三列各一个 GIN trigram 索引（不是只给主列建）

`%q%` 是**前导通配符** ⇒ btree 的死区 ⇒ 只有 trigram 能服务。

★ **为什么必须三列而不是一列**：三列 OR ⇒ 规划器必须能把**每一列**变成可索引条件
⇒ ★★ **只给 `session_key` 建索引不解决问题**（另外两支仍不可索引 ⇒ 仍然 Seq Scan）。

★ **写放大口径（★ 为什么在热写表上仍可接受）**：
`session_summaries` 每次请求都触发一次 UPDATE（累加计数、刷新 `last_request_at`），
★ 但 **PG 对 UPDATE 逐索引检查「被索引列的值是否真的变了」** ⇒ 没变就不重写索引项；
★ 本次 UPDATE **不触碰** `session_key`（主键）、`title` / `primary_model`（由摘要器单独写）
⇒ ⇒ ★★ **三条索引的写放大 ≈ 0**。
★ **判据**：**只给「低频写」的列建 trigram 索引** ⇒ 收益极大、代价近零。

### 2.2 决策 B：索引表达式与查询表达式必须**逐字**对齐（★ 本轮最关键的一条）

★ PG 的表达式索引匹配是**逐字**的：

| 索引建成 | 查询写成 | 结果 |
|---|---|---|
| `(title gin_trgm_ops)` | `title ILIKE $1` | ★ **可索引** |
| `(title gin_trgm_ops)` | `COALESCE(title,'') ILIKE $1` | ★ **不可索引 ⇒ Seq Scan** |
| `((COALESCE(title,'')) gin_trgm_ops)` | `COALESCE(title,'') ILIKE $1` | ★ 可索引，★ **但任何人把查询「顺手简化」成 `title ILIKE` 就会静默失去索引** |

⇒ ⇒ **正解 = 索引裸列 + Go 侧裸列，两者同时改**。

★ **口径等价（★ 可证，不靠实测）**：COALESCE(x,'') 与 x 在 WHERE 谓词里逐行等价，
前提是**模式串永不为空**：

- `likeContains(q)` 返回 `"%" + escape(q) + "%"`，而 q 非空 ⇒ 模式串**至少含 1 个字符**
  ⇒ `'' ILIKE 模式串` **恒为假**（`%X%` 至少要 1 个字符）；
- `x IS NULL` ⇒ `x ILIKE 模式串` = NULL ⇒ WHERE 判为不通过；
  `COALESCE(x,'') ILIKE 模式串` = `'' ILIKE 模式串` = 假 ⇒ **同样不通过**；
- `x IS NOT NULL` ⇒ 两边**逐字相同**。

⇒ ⇒ 两边的「通过/不通过」集合**完全一致** ⇒ ★ **行集不变** ⇒ ★ **响应形状不变**。
★ q 非空由**调用方**保证：`mergeCatalogSearch` 开头 `strings.TrimSpace(q) == ""` 即返回。

★ SELECT 列表里的 `COALESCE(title,'')` **保留**（它决定**返回给调用方的值**，与索引可用性无关）。

### 2.3 决策 C：迁移形态 = `dbinit:no-transaction` + `CREATE INDEX CONCURRENTLY`

- `session_summaries` 是**热写表** ⇒ 普通 `CREATE INDEX` 会在整个构建期持 ShareLock 阻断写入；
- ★ 它是**普通表**（不是分区父表）⇒ **不需要** 877 的「父表 ON ONLY 壳 + 逐分区 ATTACH」三段式；
- ★ 会话级 `SET lock_timeout='60s'` / `SET statement_timeout='10min'` + `RESET`
  （★ 非事务通道里 **`SET LOCAL` 无意义**）；
- ★ 第 0 段**自愈** `indisvalid=false` 的半成品（★ `IF NOT EXISTS` 对无效索引也命中 ⇒ 不先 DROP 就重跑 = 什么都没修）；
- ★ 第 2 段**形状校验**：半成品必须当场炸出来让迁移不记账。

## §5 ★★ 台账语义的自相矛盾（R154 轮的遗留缺陷，本轮订正）

R154 轮写了两条**互相打架**的规则：

1. 「加了索引的列**从台账里删掉**」（台账只许缩小）；
2. 门有「**集合相等**」判据（★ 源码的每一个 LIKE 列都必须在台账里，★ 不多不少）。

⇒ ★★ **索引一落地就必然撞上**：删行 ⇒ 集合不等 ⇒ 门红；
★ 而唯一能让门绿的办法是**留着行、把 verdict 改成 `indexed`** ⇒ ★★ **门在逼人撒谎**。
⇒ ★★ **一个撒谎的台账比没有台账更坏**（★ 它会让下一个读的人以为「还没修」）。

★ **本轮订正**：

- 「只许缩小」重新定义为 ★★ **待办集（`needs-index` 行数）只许减少**；
- 台账的 `verdict` 变成 ★★ **可机器验证的**：
  ★ `verdict == indexed` ⟺ **该列在迁移 909 的索引清单里**
  ★ `verdict == needs-index` ⟺ **该列不在迁移 909 的索引清单里**
  ⇒ ⇒ 说 indexed 而迁移没建 ⇒ **红**；★ 迁移建了而台账说 needs-index ⇒ **红**。

★ 台账三行已全部翻成 `indexed`，★ 且每行的 `evidence` **明写「生产 252 / 211 尚未应用」**
⇒ ★★ **台账不声称生产已修**（★ `indexed` 指的是**仓内已交付**）。

## §6 两条门（★ 都自带阳性对照 / 有牙证明）

### 6.1 909 契约门（`sql/migrations/startup/migration_909_..._test.go`，5 条）

★ 最有价值的是第 ⑤ 条：**索引列 ⟷ Go 侧 LIKE 列**的**集合相等**：

- 迁移侧：从**剥掉注释后**的 up 文件体抽 `CREATE INDEX … USING gin (<col> gin_trgm_ops)` 的列；
- Go 侧：用 **go/ast** 取常量 `catalogSearchSQL` 的**真实字面量**，再在**那段 SQL 文本**上扫 LIKE 列；
- ★ 断言**双向**：Go 加了第 4 个 LIKE 列却忘了建索引 ⇒ **红**；★ 迁移建了 Go 没查 ⇒ **红**；
- ★ 并单独断言「Go 侧 LIKE 谓词**不得**被 COALESCE 包裹」⇒ ★ §4.2 那 520 ms 就是它要拦的。

★ **阳性对照**：断言 `catalogSearchSQL` 里确实有 `ILIKE` ⇒ ★ 「源里把查询删了」会让门**假绿**。

### 6.2 R154 台账门（`scripts/ursmcheck/session_summaries_like_index_gate_test.go`）

★ 本轮改了它的**源码列解析口径**与**「只许缩小」判据**：

- ★ **解析口径**：R154 轮的正则**扫的是整个 Go 文件（含注释）**

  就会被当成一个**真实的查询列** ⇒ ★ 集合比对凭空多一列 ⇒ ★ **假红**。
  ⇒ ⇒ **改成 go/ast 取常量字面量**（★ 通用式：**文本判据必须剥到「对的那一层」**）。
- ★ **判据**：`TestSessionSummariesLikeIndexLedgerOnlyShrinks`
  ⇒ `TestSessionSummariesLikeIndexLedgerVerdictMatchesMigration`（§5）。
