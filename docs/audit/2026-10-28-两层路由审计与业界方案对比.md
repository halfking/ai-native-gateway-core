## 0. 结论速览（TL;DR）

本仓两层路由的**判死侧**（错误分类 → 分级冷却 → 指数退避 → 双确认 → 协议红分级）已达到
甚至超过主流网关的被动健康检查深度；**打分选路**（成本约束 P2C + 11 因子 composite +
首跳加权轮询）比 one-api/new-api 的"优先级+权重随机"精细一个量级，与 OpenRouter 的
四因子排序同档。**结构性差距集中在四处**，全部指向"及时更新但不闪动"：

| # | 差距 | 业界成熟解法 | 本仓落点 |
|---|---|---|---|
| G1 | **恢复无渐进**：1 个成功 → 全量回池（Envoy/HAProxy 有 slow start） | 恢复窗口内按 ramp 回流量，或至少 N 次连续成功才全量 | breaker.go RecordSuccess / NodeState Lua |
| G2 | **hysteresis 反向不对称**：判死要 2~3 连败、恢复只要 1 成功 → 抖动节点呈 5min 周期振荡 | 判死易/恢复难的窗口不对称（HAProxy rise≥fall）+ 恢复期降权而非全量 | breaker 阈值 + 恢复期 sticky/weight 压制 |
| G3 | **无成功率统计弹出**（Envoy success-rate outlier detection 的"与池均值偏差"判定） | 池内成功率均值对比，低偏差者弹出——专治"慢性病节点不触发连败阈值" | RecentSuccessRate 已有，缺池化对比判定 |
| G4 | **无重试预算/退避无 jitter**：重试风暴有放大面（退避无 jitter 是仓内注释自认的有意行为） | Envoy retry budget（重试占比上限）+ gRPC retry throttling；指数退避加全抖动 | retry_schedule.go + attempt budget |
| G5 | **工程一致性**：六状态面静默写失败可架空退避（R149 实证）；URSM v2 与 legacy P2C 双真值叠加 | 单一事实源 + 写回对拍门 | §4 P1-D |

另有三项**工程一致性**风险（非算法）：多状态面（Redis NodeState/内存 breaker/内存
reducer/DB 三面/credentialstate/URSM v2 六面）的一致性税与静默写失败活锁（R149 实证）；
成本打分的双币种未折算（CNY/USD 同 cohort 比 P75）；价格覆盖率 46.8% 造成的排序扭曲。
详见 §3/§4。

### 1.1 "两层路由"的定义与本仓语义

本仓语境里"两层"有三个嵌套的层次（docs/design/2026-09-19-two-layer-priority-and-cost-routing.md）：

1. **计费两轮**：Round 1（free/token_plan/code_plan/agent_plan/monthly，边际成本≈0）整层
   永远优先于 Round 2（per_token 按量）——`splitByBillingRound`（router.go:1060）+
   候选 SQL 天然按轮排序（provider/client.go:1939-1951）。
2. **选路段三层**：tier bucket 内 P2C 排序后按饱和度分区——L1 优先层（priority 标志 +
   quota ok 且有余量）→ L2 常规层 → L3 兜底层（已满的优先节点，只作最后 failover）
   （router.go:1095-1105 `partitionBySelectionLayer`）。
3. **模型解析 → 凭据选择**的大两层：第一层 canonical→alias→raw 三段 SQL 解析
   （resolve/resolve.go:341/379/420；alias 歧义取最短名 :392；全 miss 时 auto-seed
   防抖 5min + 负缓存 ≤30s :178/:63；`model="auto"` 走 autoroute
   `Decider.DecideWithFeatureFlags`（auto_route.go:610）选出具体模型）；第二层按模型
   取候选凭据（model_offers×别名×canonical 五路匹配，client.go:1688-1710；过滤
   manual 禁用/broken_confirmed 探针 :1933 / routing_scope :1917）、六道可用性过滤、
   打分、排序。

### 1.2 一次 /v1/chat/completions 的完整调用链

```
ServeHTTP → resolver.Resolve（模型解析：canonical→alias→raw 三段，resolve/resolve.go:100）
  → resolveCandidatesForRequest → provider.Client.getCandidates
    （provider/client.go:694，30s TTL 缓存 + singleflight，DB 挂 30s 宽限→1h outage 陈旧兜底）
  → Executor.Execute → executeViaDispatch（executor_dispatch.go:425）
  → dispatch.Pipeline → Router.PlanCandidatesPinned（router.go:255→269）
      ├─ 去重（283）
      ├─ URSM v2 authoritative 过滤（344-447；Ready 50ms 超时；Redis 不可达→outage mirror）
      ├─ StateBackend.FilterAvailable（467；DB-only / StateManager / URSM v2 三选一）
      ├─ filterHealthyNodes（557；Redis NodeState 批量 MGET 100ms；fail-open）
      ├─ 全冷却兜底：chooseLeastCooledCandidate（577-594；最小 DisabledUntil 优先）
      ├─ splitByBillingRound（599；Round1 整层前于 Round2）
      ├─ planByTier（630；tierOrder {1,2,3,9}；每 tier：
      │    p2cOrder 全排序 → partitionBySelectionLayer 三层分区 → 首跳加权轮询 promote）
      ├─ prioritizeSticky（642；sticky 凭据提首）
      └─ applyProtocolAffinity（646；出站协议偏好排序）
  → dispatch 派发（失败重试/换凭据/换模型梯子）
```

**failover 梯子**（domains/dispatch/failover.go:104-279）：同凭据重试（预算
`RetryPerCredential = MaxNodeFailures−1 = 2`，errors.go:14）→ 换凭据（PlanSwitchCred，
planner.go:258，provider-scope 受限）→ 换模型（`RecommendModelAlternatives` 换梯，
autoroute/model_alternatives.go:26）→ 终止。总尝试上限 maxAttempts=100（planner.go:56），
UpstreamAttemptBudget 硬顶 601（executors/attempt_budget.go:13）。退避 2s×2ⁿ 夹
[2s,120s]、Retry-After 优先、**无 jitter**（retry_schedule.go:75-90，注释自认为 v4 spec
决定）。容量满 5s×12 轮（planner.go:47）。错误分类走中央策略 `errorsx.DecideNextAction`
（planner.go:204），cred-fatal（quota/auth 族）跳过同凭据重试。**每次失败重路由都重新
planCandidates**（failover.go:167）。

### 1.3 打分公式（P2C composite）

**P2C 是成本约束的 P2C**（router.go:1426 `p2cOrder`）：先按 `blendedCost`（in+out 每 1M
混合价）圈出 ≤minCost×1.10 的"近价池"，池内随机抽两个比 `calculateLoadScore`，胜者进入
failover 序列（循环淘汰产出完整顺序，不是只选首跳）。

`calculateLoadScore`（router_scoring.go:128，越低越好）11 因子：

| 因子 | 权重 | 语义（file:line） |
|---|---|---|
| concurrency 压力 | 0.4 | LiveLoad in-flight / capacity，clamp 1.0（:337） |
| identity 压力 | 0.1 | 同一信号（:363） |
| 延迟惩罚 | 0.3 | 1−latencyScore；P95 + queue-amplification（pressure>knee 0.6、α1.2/β1.8）分段表 <800ms=1.0→>30s=0（:440-472） |
| 质量惩罚 | 0.2 | 1−成功率；RecentSuccessRate（最近 50 条，samples≥10 才用）优先于 lifetime（:546） |
| headroom 惩罚 | 0.05 | (1−pressure)^γ（:536） |
| 容量惩罚 | 0.02 | Weight<100 线性（:319） |
| **成本惩罚** | 0.15（env） | Round1=0（边际成本≈0）；Round2 blended/$30 软帽线性；**无价=1.0**（unknown ≠ free，:264） |
| IQ 惩罚 | 0（默认关） | 标准 IQ 反比，未知=0.5 fail-open（:294） |
| sticky 会话惩罚 | 0.15 | 5min 滑窗 sticky 会话数/容量（:567） |
| recency 惩罚 | 0.05 | 距上次请求 30s 线性衰减（:599） |
| 余额惩罚 | 0.05 | PAYG 余额<$5 线性，0=1（:628） |
| 计划额度惩罚 | 0.10 | plan_quota_used_percent/100，探测值（:657） |

**首跳**不是 P2C 第一名，而是**确定性加权轮询**（`promoteWeightedCandidateWithWeights`
router.go:1199）：counter mod totalWeight × 黄金比例 stride（weightStride 618/1000 + GCD
互质，router.go:1270），抽签份额被四惩罚折算 `w'=max(1, W·(1−0.9p))`（floor 防饿死）。
候选上限 12，TierFallbackMax 限制跨 tier。

### 1.4 熔断器（节点状态判死核心）

`domains/credential/breaker.go`——四态机 CLOSED/OPEN/**HALF_OPEN**（单探针槽 + 5min
泄漏强制回收，:283-297）/QUARANTINED：

- **连续失败 2 次跳闸**（:73，从 3 下调）；HALF_OPEN 探针失败 1 次即回 OPEN（:616）
- **按错误族差异化冷却**（defaultPolicies :108-140）：transient/timeout/network 60s 平坦；
  auth 5min→24h 指数（ShrinkFactor 0.5）；quota 永久隔离（QUARANTINED）；
  upstream_down 30s→30min 指数；overloaded 30s→5min；concurrent 2min
- **free 池独立更短 profile**（freeTierPolicies :162-171，15s/5s）——2026-09-15 245 free
  池 326 熔断循环/24h 的直接修法
- **429 不进熔断**（:545-550，2026-09-22 设计红线"429 是容量信号不是健康故障"），改走
  绑定级冷却降权（Retry-After 优先、默认 3min）
- **quota reset 对齐**（:427-483）：上游声明的重置时刻直接决定冷却窗口，clamp 30s~2h
- **model-scoped 失败不连坐凭据**（:501-514）
- **同事件时间窗**（R87，:592-608）：冷却期内到达的失败属同一次事件，不被错误族切换清零
- **escalation**（:672-714）：transient 族连续 ≥2 → 升级 UpstreamDown 指数冷却（R31
  修正 coolingCycle 推进，指数才为真）
- 指数冷却 float64 计算防 int64 溢出（R34，:759）
- onChange 观察者 → Prometheus + DB 同步（三十七轮审计 §三#4）
- Reset 清 coolingExpires（R18，"手动恢复不能把熔断器恢复成更敏感的形态"，:810）

**DB 层对级硬门**：`v_routable_credential_models` 视图（sql/objects/views/）——
`node_probe_state.last_direct_ok=false AND next_retry_at>now()` → 整个（凭据,模型）对被
踢出可路由集（与 NGINX max_fails/fail_timeout 同构）；另有 availability_state='ready'、
quota_state 不在耗尽集、health_status∈{healthy,unknown} 等门。

### 1.7 节点状态保持全景（六面状态机 + 四栈探针）

**六套并行状态面**（同一"节点健康"语义需六面同步——一致性税，见 §3/§4）：

| 状态面 | 粒度 | 介质 | 角色 |
|---|---|---|---|
| Redis NodeState | (credential, model) | Redis Lua 原子脚本 | **热路径权威**（300s 滑窗、Disabled/DisabledUntil、DisableCount；node_state.go:843-1006） |

| DB credential_model_bindings + credentials | 绑定/凭据 | PG | available/unavailable_reason/recover_at + availability_state/quota_state/health_status |
| URSM v2 | (credential, model) | Redis + 100k/30s LRU 镜像 | authoritative 路由过滤+打分（config.go:211 默认 authoritative；与 NodeState 是两个关注点非替代关系，node_state.go:1-8 头注释） |

**四栈探针 + 被动记账**：

| 栈 | 触发 | 判据 |
|---|---|---|
| credential_probe_v2 | 1h 周期 + 失败分级延迟 30s/2m/5m | `credentialProbeHasOutput`（交付：有语义输出，reasoning 不算）/ `HasLivenessEvidence`（存活叠加，只许 credential 探针用——2026-10-27 语义分层界线） |
| NodeProbeWorker（node 级） | 失败触发（5s 重臂）+30s tick、SKIP LOCKED 跨实例去重 | direct+gateway 两轮、direct 为真值；成功停泊 30 天 |
| ActiveProbeWorker | 连败≥2 | 直连 chat ping 30s 超时；auth/4xx/failed 写 5min hold |
| probeOne | 全灭（no_candidates） | 按 CoolUntil 最早到期者单飞 + Redis SET NX 防扇出 |

## 2. 业界成熟方案普查（13 个主题）

### 2.1 Envoy outlier detection（被动健康 + 防抖的金标准）

来源：[Envoy outlier detection 官方文档](https://www.envoyproxy.io/docs/envoy/v1.35.3/intro/arch_overview/upstream/outlier.html)

- **consecutive 5xx**：连续 N 个 5xx 弹出（默认 5）
- **success rate ejection**：滑动窗口内**与集群成功率均值的统计偏差**弹出（stdev 因子）——
  专治"慢性病节点"（成功率 70% 但从不触发连败阈值）
- **max_ejection_percent**（默认 10%）：同时弹出比例上限，防止级联弹出
- **panic threshold**（healthy_panic_threshold 默认 50%）：健康节点不足时全量回弹——
  **宁可路由到坏节点也不整体 503**
- **base_ejection_time + max_ejection_time**：弹出时长指数增长有上下界；被弹节点会周期性
  尝试恢复
- 关键点：被动检测与主动 health check 并用；`success_rate_minimum_requests`（默认 100）
  保证统计显著性

### 2.2 NGINX / HAProxy 的 hysteresis 与 slow start

来源：[NGINX max_fails/fail_timeout 讨论](https://stackoverflow.com/questions/65656728/)、
[HAProxy observe layer7 + on-error mark-down](https://stackoverflow.com/questions/32270741/haproxy-http-load-balancing-and-status-handling)、
[HAProxy rise/fall 论坛](https://discourse.haproxy.org/t/haproxy-servers-staying-down-after-failed-health-checks/1169)

- **HAProxy rise/fall 不对称**：`rise 3 fall 2`——恢复要 3 次成功、判死只要 2 次失败，
  **hysteresis 方向与本仓相反**（本仓判死 2~3 败、恢复 1 成功）
- **slow-start `<time>`**：恢复后流量**渐进回升**（防止"恢复即全量 → 二次打挂 → 再翻红"
  的 re-flapping；这是防抖恢复侧的标准答案）
- **observe layer7 + error-limit + on-error mark-down**：真实流量的被动观察可不等下一轮
  主动检查直接 mark-down
- NGINX OSS 只有被动 max_fails/fail_timeout；slow_start 是 Plus 功能

### 2.3 LiteLLM Router（LLM 网关最广泛使用的开源实现）

来源：[LiteLLM cooldown #871](https://github.com/BerriAI/litellm/issues/871)、
[DeltaLLM router 文档](https://docs.deltallm.io/en/latest/configuration/router)

- **cooldown ≈ 熔断**：失败部署冷却 ~1min（可配），状态内存或 Redis 共享
- **半开探测恢复**：cooldown 到期放行**一个** half-open probe（Redis 共享保证多实例只有
  一个探针），成功恢复正常路由、失败重启冷却——与本仓 breaker HALF_OPEN 单探针槽同构
- 多策略：simple-shuffle（加权随机）/ least-latency / usage-based（TPM/RPM 配额感知）
- fallbacks 有序列表、超时与重试可配
- 已知痛点：权重在各策略间不统一生效（[#9200](https://github.com/BerriAI/litellm/discussions/9200)）、
  RPM 计数缓存竞态（[#7395](https://github.com/BerriAI/litellm/issues/7395)）

### 2.4 OpenRouter（商业 LLM 聚合路由的成熟范式）

来源：[OpenRouter Decisions 组件文档](https://openrouter.ai/docs/client-sdks/go/models/components/decisions)、
[Sacra 分析](https://sacra.com/chat/h/a7b37e60-48db-42fb-8cb2-fc599700d6ce)

- 路由四因子：**price、latency（p50/p75/p90/p99 分位跟踪）、throughput（tok/s）、uptime**
- `provider.order`：priority 排序 + `max_price` 过滤 + "throughput"/"latency" 提示——
  **把"成本优先还是速度优先"显式化成客户端可选项**
- 自动 failover + 可 pin provider
- 教训（[LinkedIn 实测](https://www.linkedin.com/posts/sihan-frank-chen_latency-on-openrouter-can-get-insane-when-activity-7503135161241243648-YF_6)）：
  纯自动选择在高峰会踩到高延迟供应商——自动路由必须带延迟上限护栏

### 2.5 KV-cache 感知路由 / 会话亲和（推理集群方向）

来源：[SGLang router per-request KV 命中指标](https://github.com/sgl-project/sglang)、
[NVIDIA Dynamo vLLM 集成文档](https://docs.nvidia.com)、[llm-d prefix-cache routing 实测（23x 提速）](https://dev.to/andygolubev/how-llm-d-prefix-cache-routing-made-qwen-7b-on-eks-23x-faster-2h8j)、
[llm-d router 指标文档](https://llm-d.ai/docs/operations/observability/router-metrics)、
[CacheRoute 论文](https://www.alphaxiv.org/abs/2608.19677)

- 原则：**按缓存局部性路由，而不是按空闲槽位路由**——同一会话/同一前缀路由回同一路由
  侧可复用 KV cache
- llm-d（Red Hat + NVIDIA + Google Cloud 共建，K8s 生态）：scheduler 用 vLLM 遥测做
  prefix-cache 感知 + KV cache 负载感知决策，路由指标显式区分"cache affinity 决策"与
  "被 load gate 覆盖"
- SGLang router 把 per-request KV 复用指标回报到路由层——**亲和路由的实际收益是可观测、
  可回归验证的**（router 决策命中率 vs worker 实际命中）
- CacheRoute：prefix 亲和与负载做**联合规划**（不是先亲和后负载的贪心）
- 对上游网关（本仓）的含义：上游供应商内部的 prompt cache 命中率决定 TTFT——
  **会话粘性的真实收益是跨请求的 prompt-cache 命中**，应在网关侧度量

### 2.6 Azure OpenAI / OpenAI 的 prompt-cache 粘性（商业标杆）

来源：[Microsoft prompt caching 文档](https://learn.microsoft.com/azure/ai-services/openai/how-to/prompt-caching)、
[OpenAI 社区：user 参数影响缓存路由](https://community.openai.com/t/prompt-cache-routing-the-user-parameter/1267103/2)、
[LiteLLM affinity TTL 硬编码 5min bug](https://github.com/BerriAI/litellm/issues/28427)

- Azure/OpenAI 后端按**精确前缀匹配**路由到缓存节点；`user` 参数参与粘性路由
- **粘性 TTL 必须匹配缓存 TTL**：LiteLLM 曾把 affinity TTL 硬编码 5min，而缓存 TTL 是
  1h——粘性过期早于缓存过期 = 缓存白写（教训直接适用于本仓 L1 TTL 按模型类型的设置）
- 代理层不保持会话亲和会直接打断 prompt caching（社区多起实证）

### 2.7 负载均衡算法：P2C / EWMA / least-outstanding

来源：[P2C 详解](https://frontend-interview-bank.vercel.app/blogs/system-design/bonus-e-load-balancing-algorithms)、
[LinkedIn：EWMA 延迟感知负载均衡的振荡问题](https://www.linkedin.com/posts/md-ali-jaffry-54530a274_why-can-latency-aware-ewma-load-balancing-activity-7367163262385188866--TmY)

- **P2C（two random choices）**：随机抽两取优——O(1) 状态、避免全局排序的羊群效应；
  大池子首选。本仓已在用（且是成本约束变体）
- **Peak EWMA（Finagle/Linkerd）**：对延迟**尖峰**敏感的 EWMA（近 p95 行为），配合 P2C
  采样。**已知缺陷：延迟反馈滞后于真实负载 → 重负载下振荡**——纯 EWMA 排序在高流量下
  会自己制造抖动（与本仓"不致于闪动导致服务抖动"目标直接相关）
- **least outstanding requests**：按 in-flight 计数路由——信号最实时，无延迟反馈的滞后
  问题（本仓 concurrency 0.4 权重因子即此思想的归一化）
- 实践结论：**延迟估计（EWMA/分位）只做排序倾斜，不做硬门槛**；硬并发信号（in-flight/
  容量）才能承担实时性

### 2.8 一致性哈希有界负载（CHWBL）——粘性与平衡的经典折中

来源：[CHWBL 论文](https://arxiv.org/pdf/1608.01350)、
[Maglev 讨论](https://www.reddit.com/r/programming/comments/1946xru/maglev_hash_consistent_hash_with_guaranteed_even)

- 纯一致性哈希：粘性最好但负载不均（热点）；Maglev：均匀但成员变更需重建查找表
- **CHWBL**：哈希定位 + 负载上限 ε 溢出顺延——粘性优先、超载才牺牲粘性
- 对本仓：sticky 是"会话→节点"精确映射而非哈希环（节点集小、会话键明确，无需环）；
  CHWBL 思想的对应物 = 粘性惩罚（sticky 会话数/容量 0.15 权重）+ 饱和让位（L1→L2 外溢）

### 2.9 Circuit breaker / 自适应并发

来源：[failsafe-go circuitbreaker](https://pkg.go.dev/github.com/failsafe-go/failsafe-go/circuitbreaker)、
[Netflix concurrency-limits（AIMD/Gradient/Vegas）](https://javadoc.io/doc/com.netflix.concurrency-limits/concurrency-limits-core/0.0.28/com/netflix/concurrency/limits/Limiter.html)、
[SREcon23 Adaptive Concurrency Control](https://www.usenix.org/conference/srecon23americas/presentation/kleiman)

- 半开态 + 受限试探调用是标准恢复模式（resilience4j 的 HALF_OPEN permitted calls 可配
  ——试探调用数本身就是渐进恢复的抓手，比"1 探针全量"更平滑）
- **Netflix AIMD/Gradient**：按错误率/延RTT 自动调并发上限——加性增、乘性减，天然自带
  慢启动行为；Google SRE「Handling Overload」用 BDP 式并发预算
- 对本仓：breaker 的 ShrinkFactor 字段（auth 0.5 等）已有"冷却期收缩并发"概念，但未见
  与 Limiter 的实际联动消费方（待 agent 报告确认）

### 2.10 重试预算 / 重试风暴防护

来源：[Envoy retry budget](https://www.envoyproxy.io)、
[DZone retry budgets](https://dzone.com/articles/prevent-retry-storms)

- **Envoy retry budget**：并发重试数 ≤ 活跃请求数 × 百分比 + 最小值——重试占比被硬顶住，
  上游故障时总放大系数有界
- **gRPC retry throttling**：失败比例超阈值时**概率性禁用重试**（令牌桶），客户端侧自动
  退避
- 配合**指数退避 + 全抖动（full jitter）**防止同相位重试惊群

### 2.11 one-api / new-api（中文生态多渠道网关）

来源：[new-api 渠道管理文档](https://docs.newapi.ai/zh/docs/guide/feature-guide/admin/channel)、
[new-api FAQ](https://doc.newapi.pro/support/faq)、
[new-api 分流与重试降级实战](https://tendcode.com/subject/article/newapi-routing-retry-failover)

- **priority 分层 + 同层 weight 加权随机**——与本仓 Round1/Round2 + tier + weight 抽签
  同构（本仓在其上多了 11 因子打分与 P2C）
- 多 key 池自动轮换、失败自动禁用、恢复自动重启用；重试默认关（new-api）需手动开
- 已知问题：内存缓存下自动禁用导致重试下标错位（[#6095](https://github.com/QuantumNous/new-api/issues/6095)）；
  渠道亲和 TTL 内禁用渠道仍被命中——**状态翻转与缓存 TTL 的不一致**是通用坑

### 2.12 Hedged requests / 尾延迟

来源：[Dean & Barroso, The Tail at Scale (CACM 2013)](https://codito.in/paper-the-tail-at-scale)

- p95 未返回时向另一副本发对冲请求，取先到者——交互式请求尾延迟的教科书解法
- 前提：幂等 + 对冲比例受控（否则就是变相重试风暴）
- 对 LLM 网关：**流式场景对冲成本极高（双份 prefill）**，更实用的是"首字节超时换节点
  重试"（本仓已有 TTFB 类超时换道设计的话可直接对标；无则作为流式尾延迟方案储备）

### 2.13 RouteLLM / cost-aware 模型路由（学术）

来源：[RouteLLM (LMSYS)](https://news.ycombinator.com/item?id=40922739)、
[Response-Informed Value Estimation for Cost-Aware Multi-Turn Routing](https://alphaxiv.org/abs/2610.23239v1)

- 强弱模型分级路由（难度分类器决定走强还是弱模型）省成本
- 本仓 autoroute 的 task→model 决策树 + IQ 惩罚维度与此同构；routingopt 的 ML 学习器
  （默认关）对应 bandit/在线学习方向
- 多轮路由研究的新结论：**逐轮独立路由不如带响应信息的联合估计**——会话粘性 + 历史质量
  反馈是成本路由的增益来源（与本仓 sticky 保留 + affinity 学习回路互证）

### 3.1 总矩阵

### 3.2 关键差距展开

**G1 恢复无渐进（对"闪动致抖动"影响最直接）**。三处恢复点同构"1 成功 = 全量回池"：
breaker `RecordSuccess` 直接 CLOSED + coolingCycle=0（breaker.go:772-793）；NodeState
成功清空整个滑窗（recordNodeOutcomeScript Lua 910-932）；探针成功一次性恢复全部绑定。
配合"判死 2-3 连败 / 恢复 1 成功"的反向不对称（G2），一个亚健康节点会以
「OPEN(冷却)→到期→全量回池→再 2-3 败→再 OPEN」为周期持续振荡，**每个振荡周期都有
2-3 个真实用户请求被押上去验证失败**。UAProxy slow-start / resilience4j HALF_OPEN
递增试探正是治这个的标准答案。注意一处**天然缓冲**：sticky 会话 failover 后不重写绑定
（executor.go:3385-3403），恢复节点的冲击面天然限于新会话首跳——这层缓冲存在但没有被
量化，也没有覆盖无 session 的流量。

**G2 hysteresis 反向**。HAProxy 的 rise/fall 是"判死易、恢复难"（fall 2 / rise 3）；本仓
是"判死难（2-3 连败）、恢复易（1 成功）"。Envoy 的 outlier 弹出时长随弹出次数指数增长
（本仓 URSM v2 已有 `cool×2^disable_count` 封顶 1800s——record_request.lua:267-268——
**但 NodeState 的 DisableCount 字段存续而未消费**，冷却固定 300s：node_state.go:104，
两套 Redis 状态面在这一点上不同步）。

**G3 无成功率统计弹出**。RecentSuccessRate（last-50）只做 0.2 权重的排序倾斜，不做
"与池内均值的统计偏差"判定——一个成功率 60% 的慢性病节点（从不连败）永远不会被弹出，
只在排序上被压低；若池小，P2C 抽对时仍会以概率命中。Envoy 的 success-rate ejection +
minimum_requests 显著性护栏是成熟解法。**前提注意**：LLM 网关池子常只有 2-5 凭据，
统计偏差判定必须带最小池深/最小样本护栏，且本池过小时不启用。

**G4 重试防护缺一角**。attempt 预算（601）是"总量上限"不是"占比上限"；Envoy retry
budget 限定"并发重试 ≤ 活跃请求 × N%"，在整体故障（大面积 5xx）时把放大系数钉死。
退避无 jitter（注释自认为可测试性决定）在大规模同相位失败时有惊群面；survival 层有
±20% jitter 而 dispatch 层没有，两层不一致。

**G5 工程一致性风险（非算法但已实证咬人）**。① 六状态面一致性税：历史至少三次镜像
断裂，R149 证明"探针结果静默不落地"能把 7 级退避架空成 45s——**恢复侧做得再好，写回
失败一样抖动**；② 双真值：URSM v2 Score 与 legacy P2C composite 口径完全不同，
authoritative 下叠加生效，可维护性风险（agent 报告 #10）；③ 每次失败重路由全量重跑
planCandidates（failover.go:167），最坏 100 attempts ×（DB 缓存 + 3 次 Redis + P2C）。

## 4. 差距清单与可行方案（分优先级）

> 原则（来自本轮对比研究的元结论）：**判死侧继续沿用现有分错误类 + 指数退避体系
> （已达标），改动全部集中在恢复侧与占比防护侧**；每项按仓内惯例给判据、落点、
> 验收量具与风险；全部可 env 关闭、先观测后启用。

### P0-A 恢复期渐进回流量（slow-start 的打分层实现）——治 G1，首选

- **方案**：不动状态机。Breaker 与 NodeState 各记一个 `RecoveredAt`（恢复时刻）；
  在 `firstHopLotteryWeights`（router_scoring.go:707）对 `now−RecoveredAt < ramp 窗口`
  （建议 5min，env `LLM_GATEWAY_ROUTING_RECOVERY_RAMP_SECONDS`）的候选，抽签份额再乘
  线性 ramp 因子（0.2→1.0，floor 与现有 `max(1,…)` 兜底叠加）；`calculateLoadScore`
  同步加一项 recoveryPenalty（权重 env，默认 0.10，形状同 recencyPenalty）。等于把
  "恢复的节点慢慢接客"做在**份额层**——低流量节点不会因"没有流量证明恢复"而卡死
  （对比 P0-B 硬阈值的优点），流量来了自然收敛。
- **落点**：domains/credential/breaker.go（RecoveredAt 字段 + RecordSuccess/Reset 写入）、
  credentialfpslot/node_state.go（Lua 成功分支写 RecoveredAt + Go 结构体）、
  router_scoring.go（recoveryPenalty + firstHopLotteryWeights 折算）、provider/client.go
  （候选快照不需要改——走 Router 内存查询，与 StickyLoad Snapshot 同模式）。
- **验收**：① 单测钉"恢复后 ramp 窗口内份额 < 全量份额、窗口外恢复原值、env=0 时
  逐字节等于现状"（仓内 OffIsByteIdentical 惯例）；② 仿真臂：注入 3 连败→冷却→恢复
  循环，断言 flap 计数（DisableCount/min）下降；③ 观测：LOAD_SCORE_V2 增加
  recovery_penalty 字段；新增指标"恢复节点 5min 内首跳占比"。
- **风险**：与 stickyPenalty 叠加时恢复节点可能过度饥饿——floor 已兜底（份额 ≥
  max(1, W×0.1×0.2)），且 ramp 窗口有限。

### P0-B NodeState 判死退避对齐 URSM（消费 DisableCount）——治 G2 的一半，最小改动

- **方案**：recordNodeOutcomeScript 的禁用时长从固定 300s 改为
  `cool × min(2^disable_count, cap)`（cap=1800s，与 URSM record_request.lua:267-268
  **同一公式**——两套 Redis 状态面判死侧行为对齐）；DisableCount 字段已存在
  （node_state.go:104），只差消费。
- **落点**：credentialfpslot/node_state.go Lua + settings/spec_thresholds.go 常量。
- **验收**：单测"第 N 次禁用时长 = 300×2^(N−1) 封顶 1800"；与 URSM 同公式的对拍测试。
- **风险**：反复翻红节点冷却指数拉长→可用容量下降——这正是目的（防抖优先于容量），
  但 cap 1800s 保证不失控；free 池可沿用 freeTierPolicies 思路用更短初值。

### P0-C 重试占比预算 + 退避 jitter——治 G4

- **方案**：① dispatch 层全局（或按 provider）"在途重试并发 ≤ 活跃请求 × 25% + 10"
  的 retry budget（Envoy 形态），超预算的重试直接走 failover 换凭据而不是等退避；
  ② NextRetryDelay 加 ±20% 全抖动（与 survival 层 jitter 对齐；可测试性用注入
  randSource 解决，retry_schedule.go 已有 RealRetryClock 注入点惯例）。
- **落点**：domains/dispatch/retry_schedule.go、planner.go（预算计数器）、
  executors/attempt_budget.go（复用挂点）。
- **验收**：仿真同相位失败（100 并发同时 5xx）下总上游尝试次数对比（预算 on/off）；
  jitter 分布单测。
- **风险**：预算过紧会牺牲正常重试成功率——25%+10 起步、env 可调、先 shadow 观测
  "预算触达率"再 enforce。

### P1-A 成功率池化弹出（Envoy success-rate ejection 的池深护栏版）——治 G3

- **方案**：`filterHealthyNodes` 之后对候选集计算 RecentSuccessRate 的均值/最值；
  低于 (均值 − 3×绝对差) 且 samples≥30 且**池深 ≥3** 的候选标记 outlier——第一步只
  加**强惩罚**（loadScore +0.5）不硬弹出；shadow 观测一段时间后再评估硬门槛。
- **落点**：router.go filterHealthyNodes / router_scoring.go。
- **验收**：观测指标"池内成功率离群候选数/请求"；仿真慢性病节点（成功率 60% 无连败）
  的份额变化。
- **风险**：与 qualityScore 双重惩罚——先只观测离群计数，惩罚权重从 0 开始 env 调起。
