# 2026-11-20 看板对账口径对齐轮 —— 主档

owner 需求：`/dashboard?tab=board` 总请求数加「包含探测 / 不包含探测」条件——包含探测应等于 `/admin/reconciliation` 供应商对账，不包含探测应等于内部对账；总流量与总费用也必须一致，不一致要找到原因并修正；`/request-logs` 与同一时间的 board 总请求应一致（对比 SQL 及条件）。修完提交推送、部署 211、Maestro 全面测试。

## 一、211 真库实测定案（对拍窗口 = UTC 日，psql 会话 TZ 必须 `SET timezone='UTC'`）

| 读面 | 数据源 | 探测口径 | 2026-11-13~19 逐日对拍 |
|---|---|---|---|
| 供应商对账 | `report_snapshots daily_grain` | 全量 | == `usage_facts` 全量，**逐日 0 差** |
| 内部对账 | `report_snapshots internal_grain` | `traffic_class='business'` | == `usage_facts` business，**逐日 0 差** |
| request-logs（默认 lane） | session 家族 + `businessRequestFilter` | stage 探针排除 | == `usage_facts` business（11-18 实测 15437==15437） |
| board（修前） | `request_stats_minute` | 写入时 markers 排除 | **部署日漏行**：11-19 16:00/18:00 UTC 两个部署窗口 -1/-21 笔、-3.0M tokens；11-13/15/17 各 -1 笔 |

（量具坑：psql 默认会话时区是宿主 +08，`occurred_at >= '2026-11-19'` 实际是上海日窗——第一轮对拍把它当 UTC 日窗，得出「快照与 usage_facts 对不上」的错误结论。对拍必须显式 `SET timezone='UTC'`。）

### 根因一（修）：board 主源 `request_stats_minute` 在部署窗口漏行

生产写入者 `bg.StatsMinuteRollup` 是「游标 + 30min 有界 resweep」的扫描器（`statsResweepDefaultSpan=30min`）：重启/终态迟到超过 resweep 窗的行永久漏统。211 一天多次部署（并行车），所以 board 在部署日常态性低于内部对账。`usage_facts` 由 EventWriter 事务内落库（`insertUsageFactTx`，ON CONFLICT (event_id,revision,occurred_at)），无此丢失面，且对账快照就是从它聚合的——**它是对账级真源**。

### 根因二（修）：board 没有「包含探测」口径

探针行物理隔离（`session_turns_probe_hot`）后业务分钟表根本没有探测行；`request_stats_probe_minute` 计的是事件不是请求（11-19 上海窗 43771 vs usage_facts probe 14504，约 3 倍）——不能当 include 口径的源。

### 根因三（核实为一致，无需修）：request-logs 与 board

同窗口（UTC 日）下 `session 家族业务 lane` == `usage_facts` business == board（修后）逐字相等。残余差异面（有意，登记不修）：
- request-logs 预设是**本地时区**窗口（今天=本地 00:00 起），board 预设是 **UTC 日历日**（今天=UTC 00:00 起）——对拍请用两边自定义范围对齐同一窗口；board 的 UTC 口径与对账有意对齐（2026-11-19 简易总览轮 L3）。
- request-logs 聚合含 `in_progress` 行（页面语义：进行中的请求要显示）；usage_facts 只含终态——过去窗口 in_progress=0（实测），实时窗口下「进行中未落账」是语义差不是丢失。
- `listLogs` 的 `ts <= to`（闭端）与 board 半开窗 `[start,end)` 差一个边界瞬间，量级可忽略。

## 二、修法

### 后端（`admin/dashboard_board_queries.go` + `dashboard_board.go` + `dashboard_board_cache.go`）

1. **`queryBoardSummary` 主源换 `usage_facts`**（新 `queryBoardSummaryFacts`）：
   - 不含探测（缺省）→ `AND traffic_class='business'`（与 `reportrollup.grainDaySQL` businessOnly 同一列同一谓词）⇒ == 内部对账 == request-logs 业务 lane；
   - 含探测（`include_probes=1`）→ 无 class 过滤 ⇒ == 供应商对账全量；
   - 成功率/均延迟/积分从同表算（`status='success'` / `latency_ms` / `credits_charged`）。
2. 降级链保持既有形状：usage_facts 缺（42P01）或查询失败 → exclude 模式落回旧分钟表口径（`queryBoardSummaryMinute`，即修前的数字）；**include 模式不落回分钟表**（它无探测行，落回=拿业务数冒充全量数）。
3. `include_probes=1` **绕过 Redis 看板缓存**（缓存键只含 scope/days/provider，存默认业务载荷，混用会互相污染）；响应新增 `probe_scope: included|excluded`，summary 新增 `summary_source: usage_facts`。
4. 刻意**不**用 `bg.ProbeTrafficExclusionPredicateView`（markers 口径）过滤 usage_facts——class 在写入时由 origin_stage 派生，对账快照按它分面；board 要与对账逐字相等就必须用同一列，再按 markers 算一遍必然在边缘行分叉。

### 前端

- `useDashboardBoard`：`includeProbes` 持久化偏好（`board-probe-scope`）；include 时停用 SSE 业务增量合并（live 流是业务口径，往全量总数上叠会漂移），轮询静默对账兜底；`setIncludeProbes` 即切即重载。
- 切换控件放**下方（非紧凑）筛选条**（顶部合并行的单行高度契约不动）；英雄区「总请求」标签带 `含探测` 徽标（`probe_scope==='included'` 时）披露当前口径——include 模式下英雄区（全量）与趋势/分布（业务）不同源，差异显式说而不是让用户猜。
- `BoardFilterBar` 数据源徽标把 `usage_facts*` 归并 PG 基线组。

## 五、遗留登记

- **L1** request-logs 预设窗口是本地时区、board 是 UTC 日历日——对拍要用自定义范围对齐；两边语义各自有意（board=对账口径），不合并。
- **L2** include 模式下趋势/分布图仍是业务口径（分钟表）；英雄区与图表口径差异已用徽标披露，若 owner 要 include 模式的趋势图需另开一轮（usage_facts 按桶聚合）。
- **L3** `request_stats_probe_minute` 计事件不计请求（≈3 倍），当探针运营视图用可以，当对账口径用不行——本轮已绕开。
- **L4** 分钟表部署窗口漏行是 StatsMinuteRollup 的有界 resweep 设计代价；board 已切真源不再受影响，但趋势图仍读分钟表（部署窗口的趋势桶会略低）——修趋势属另一轮。
- **L5** psql 会话时区坑：跨面 SQL 对拍必须显式 `SET timezone='UTC'`（本轮第一轮结论曾被它带偏）。
