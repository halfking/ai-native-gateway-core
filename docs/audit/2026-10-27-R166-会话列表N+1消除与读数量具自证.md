## §2 归因：两层 N+1 ＋「同一份数据取了两遍」

### 2.1 第一层：两个 API 读的是**同一个** Redis hash

| 位置 | 调用 | Redis 侧 |
|---|---|---|
| `domains/session/session.go:346` `Manager.Get` | `redissafe.SafeHGetAll(ctx, client, "session:"+sessionID)` | `TYPE` + `HGETALL` |
| `domains/session/session_state.go:177` `Manager.GetStats` | `redissafe.SafeHGetAll(ctx, client, "session:"+sessionID)` | `TYPE` + `HGETALL` |

★ `internal/redis/safe_operations.go:119` 的 `SafeHGetAll` = `checkType`（1 条 `TYPE`）+ `HGETALL`（1 条）
⇒ ★ **每次调用 2 次往返**。

⇒ ★★ **每会话 4 次往返，且同一份 hash 取了两遍**。
⇒ ★★ 这是比 N+1 **更深一层**的浪费：★ N+1 是「读的对象多」，★ 这一层是「**读的对象不多，但同一份读了多遍**」。

★★ **为什么这层在旧代码里看不出来**：`Get` 返回 `*Session`、`GetStats` 返回 `*SessionStats`，
★ 两个**不同的类型** ⇒ ★ 读代码的人看不出它们来自同一个 hash ⇒ ⇒ ⇒ **只有把两者的 Redis 调用并排看，才看得见**。

## §3 实现（仓内 3 个文件 ＋ 1 处过期注释）

### 3.1 `domains/session/session_state_batch.go`（★ 新增）

```go
func (sm *Manager) GetBatch(ctx context.Context, sessionIDs []string) (map[string]*Session, map[string]*SessionStats, error)
```

★ **复用仓内既有原语**，★ 不是新造轮子：
- `internal/redis.SafeHGetAllPipeline`（★ 仓内早已存在，★ `domains/ursm/v2/store/{pipeline,probe_evidence}.go` 在用）
- `internal/redis.DefaultHashBatchSize = 512`（★ 仓内实测的批量工作点，★ 见 `safe_operations_batch.go` 的读数表）

★ 做法：**一次 TYPE 流水线 + 一次 HGETALL 流水线**取回整批 hash
⇒ 再由**同一份快照**分别派生 `Session` 与 `SessionStats`（★ 不重复读）。

★ **语义对齐表**（★ 逐键路径 → 本方法）：

| 逐键路径（`Get`） | 本方法 |
|---|---|
| key 不存在 → `ErrSessionNotFound` | 该键不进任何 map |
| TYPE 非 hash → 记 mismatch + 跳过 | 该键不进任何 map（★ 并记 mismatch） |
| hash 为空 → `ErrSessionNotFound` | 该键不进任何 map |
| 已过期 → `ErrSessionExpired` | 该键不进任何 map |
| 其它 Redis 错误 → 返回 error | 返回 error（★ 由调用方决定降级） |

★ **一处刻意的差别**：旧路径里 `Get` 成功后 `GetStats` 是**第二次**读，★ 若两次读之间 key 消失，stats 会是 nil；
★ 本方法从同一份快照派生 ⇒ **stats 恒非 nil** ⇒ ★ 这消掉了两次读之间的竞态窗口。

★ **失败粒度**：★ 批量是**整批失败**，逐键是**坏键跳过** ⇒ ⇒ **调用方必须退回逐键读**。
★ 唯一会让整批失败的窄竞态是「两次流水线之间键的类型翻转」（★ 错类型键在 TYPE 阶段就被逐键识别，不会）。

## §6 ★★★ 量具自身的三个缺陷（本轮最值钱的一段）

★ 本轮的 A/B 数字**先后错了三次**，★ 三次都是**量具自己的错**，★ 三次都**表现为「读数很干净」**。

### 6.1 每次读 Redis 都开新连接 ⇒ `SELECT 2` 不持久 ⇒ 读的是**另一个 DB**

★ 网关用 `LLM_GATEWAY_REDIS_DB=2`；★ 我第一版量具每次 `socket.create_connection` 后单独 `SELECT` ⇒ ⇒ **下一次调用是 DB 0**。
★ **症状**：查 `session:*` 得 0 条 ⇒ ★ 差点得出「本地根本没有会话 ⇒ N+1 是潜伏的、不影响本机」的结论。

### 6.2 按「读够 N 字节就 break」截断回复 ⇒ RESP 连接错位

★ `INFO commandstats` 的回复 > 4096 字节；★ 我的读取循环在首块就 break ⇒ ★ **回复被截断**
⇒ ⇒ **剩余字节留在 socket 缓冲里 ⇒ 连接从此错位** ⇒ ⇒ ⇒ 之后每次读到的都是上一条回复的尾巴。
★ **症状**：`hgetall` 恒 0。

★ **修法**：★ 按 RESP 协议读**完整**回复（`$` 批量串按长度读满）。

### 6.3 ★★ `calls=172` 是 INFO 行的**第一个 token 的后缀** ⇒ `startswith` 恒不匹配

★ INFO 的一行是：`cmdstat_type:calls=172,usec=195,...`
⇒ ⇒ **`calls=172` 不是独立 token**，★ 它是第一个 token `cmdstat_type:calls=172` 的**后缀**
⇒ ⇒ ⇒ 我原来的 `tok.startswith('calls=')` **永远不匹配** ⇒ ⇒ ⇒ **计数器恒 0**。

★★ **这才是最危险的一种**：★ 「计数器恒 0」在报告里**长得和「Redis 没被访问」一模一样**
⇒ ⇒ ⇒ 一个「解析器写错」会被读成「被测量为 0」⇒ ⇒ ⇒ ★ **量具必须能自证读到过非零值**。

### 6.4 ★ 三次的共同教训

| | 缺陷 | 症状 | 为什么没被当场识破 |
|---|---|---|---|
| ① | 连接不复用 | 读到空 | ★「空」看起来像「本来就没有」 |
| ② | 回复截断 | 读到 0 | ★「0」看起来像「没访问」 |
| ③ | token 匹配错 | 读到 0 | ★ 同上，且 ★ **与 ② 的症状完全一样** |

⇒ ★★★ **只有「预期非零」的断言能把它们揪出来** ⇒ ⇒ ⇒ ★ **写读数脚本时先问一句：「这个读数在什么条件下会等于 0？」**
⇒ ⇒ ★★★ 而且 ★ **同一轮里被自己的量具骗到三次** ⇒ ⇒ ⇒ **这不是运气问题，是「量具也必须被量」的第三次实证**。
