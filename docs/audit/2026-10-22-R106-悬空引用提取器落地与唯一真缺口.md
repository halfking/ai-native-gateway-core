## 二、架构：两腿 + 三档桶 + 一个前提守卫

```
internal/relrefs/          ← ★ 可导入包（★ 门与工具【同源、同一次编译】⇒ 口径不可能漂移）
  ddl.go        腿 A：枚举仓内全部 DDL 形态建出的关系名
  product.go    腿 B：从产品代码提取按名引用的关系（go/ast）
```

### 2.1 三档桶（★ 把 R63 §4「按名命中几乎总是假阳性」机械化）

| 桶 | 判据 | 证据强度 |
|---|---|---|
| **强命中** | 出现在 SQL **关系位置**（`FROM` / `JOIN` / `UPDATE` / `TRUNCATE` / `REFERENCES` / `COPY` / `INSERT INTO` 之后）⇒ ⇒ **括号深度 == 0** | ★★★ 最强：产品确实按名读它 |
| **弱命中** | 出现在 SQL 字面量的**非关系位置** | ★★ 可能误报 ⇒ 需人验 |
| **零命中** | 产品代码里**完全查不到** | ★★★ 在【无拼接嫌疑】前提下 ⇒ 可判定「产品不依赖它」 |

### 2.2 ★★★ 第四件必须单列的：**拼接嫌疑**（= 「零命中 ⇒ 不依赖」这条推论的前提守卫）

★ `SELECT … FROM " + tbl + " …"` 这类拼接点里，**表名在 Go 变量中** ⇒ ⇒ 静态提取**抓不到** ⇒ ⇒ ★★ **「按名零命中 ⇒ 可判定不依赖」这条推论被它推翻**。

⇒ ⇒ ★★ **判据 = 存在一个字面量，它【以该关系名开头】且【比它更长】** ⇒ ⇒ ★★ **凡有拼接嫌疑的名字，不得判为「可判定不依赖」**。

★ 实测规模：**138 个名字**有拼接嫌疑（占 856 个裸名的 16%）⇒ ⇒ ★★ **这条守卫把「零命中 ⇒ 不依赖」这条推论的适用范围砍掉了 16%** ⇒ ⇒ ★★ **⇒ 不守卫就会得出 138 个「产品不依赖」的错结论**。

## 四、★★★ 七个真陷阱（★ 每个都有实测证据，不是理论）

### 4.1 ★★★ `git ls-files` 默认对非 ASCII 路径做**八进制转义并加引号** ⇒ ⇒ 那批文件**静默读不到**

★ 实测：`git ls-files '*.sql'` 输出里含 `"docs/\345\205\250\346\241\210..."` ⇒ 拿这个字符串去开文件 ⇒ **`no such file or directory`** ⇒ ⇒ **而【数目完全正常】（转义后仍是一行）⇒ ⇒ 量具一声不吭**。

⇒ ⇒ ★★ **修法 = `git ls-files -z`（NUL 分隔 ⇒ 不加引号也不转义）**。
⇒ ⇒ ★★★ **★ 这就是「量具自身的读取方式」的坑：★ 它不会报错，只会少读。**

### 4.2 ★★★ 「数目相等」≠「清单可用」

★ 自检的第一版只比「文件系统枚举数 ≥ git 清单数」⇒ ⇒ **数目相等却每个中文路径都打不开** ⇒ ⇒ ★★ **判据必须是【逐个可打开】**，不能只是【数目相等】。

### 4.3 ★★ 「双口径互证」的两个口径**边界不对齐** ⇒ ⇒ 互证本身会误报

★ 自检第一版：文件系统枚举**跳过 `vendor/`**（vendor 有 4994 个 .go），而 `git ls-files '*.go'` **包含** vendor ⇒ ⇒ 报出「文件系统 5774 < git 10764 ⇒ 清单被截断」⇒ ⇒ ★★ **那是假红**：真因是【口径边界不对齐】。
⇒ ⇒ ★★★ **通用式：「双口径互证」⇒ 先把两边的【排除规则】对齐，否则互证本身会误报。**

### 4.4 ★★ 两腿的预处理**刻意不对称**（★ 不是「必须对称」）

| | 剥注释 | 剥字符串 | 理由 |
|---|---|---|---|
| 腿 A（DDL） | ✔ | **✘** | 函数体整体包在 `$$…$$` 里 ⇒ ★★ 剥掉字符串 ⇒ 函数体里的 `CREATE TEMP TABLE` **全部消失** ⇒ ⇒ **腿 A 少建一批关系 ⇒ 悬空引用被高估** |
| 腿 B（引用） | ✔ | ✔（**保留 dollar-quote 区段**） | SQL 里当消息用的字符串里全是英文散文 ⇒ 不剥 ⇒ `real` / `the` 被当表名 |

⇒ ⇒ ★★★ **★ 「两腿预处理必须对称」是我先写进代码的一句话，★ 实测证明它是错的 ⇒ ⇒ 已订正为「各自取舍」**（★ 代码里的注释已改，★ 旧话不留）。

### 4.5 ★★ 关系位置必须**括号深度感知**（纯正则不够）

★ `EXTRACT(day FROM ts)` / `SUBSTRING(x FROM y FOR z)` / `TRIM(BOTH x FROM y)` ⇒ 函数**参数里的 `FROM`** 不是关系位置 ⇒ ⇒ 纯正则把字段名当表名。
⇒ ⇒ ★★ 判据 = 该关键字处的**括号深度 == 0**（`FROM (`（子查询）本来就匹配不上 ident）。

### 4.6 ★★ CTE / 函数调用 / 别名.列 / SQL 关键字 —— 四类「长得像表名」的东西

| 类 | 判据 | 实测假阳性 |
|---|---|---|
| CTE 名 | `WITH [RECURSIVE] name [(cols)] AS (` ⇒ **全局**收集（拼接场景下定义与引用分处不同字面量） | `base` / `buckets` / `f` / `w0` / `merged` / `refreshed` |
| 函数调用 | 名字后紧跟 `(` | `generate_series` |
| 别名.列名 | 限定名第一段 ∉ 仓内建出的 schema 名 | `c.ts` / `b.credential_id` / `excluded.carry_level` |
| SQL 关键字 | 黑名单 | `set`（**178 处**）/ `skip`（`FOR UPDATE SKIP LOCKED`）/ `lateral` / `of` |

### 4.7 ★★★★ ★★ **DDL 不只存在于 `.sql` 文件里 ⇒ 它也在 Go 字符串里**

★ 实测：`db.ensureCredentialClientQuotaSchema`（ensure 链 ⇒ 运行时建表）｜`admin/session_export.go:375` 的 `CREATE TABLE IF NOT EXISTS session_packs`。
⇒ ⇒ ★★ **若腿 A 只扫 `.sql` ⇒ ⇒ 这两张表被误报成「悬空引用」** ⇒ ⇒ ★★★ **⇒ 腿 A 的搜索面缺口 = 「DDL 的载体不止一种」** ⇒ ⇒ ★★ **解法 = 同一个字面量集合，既抽 DDL 也抽引用**（⇒ 两腿共用一遍扫描）。

## 八、诚实边界

1. ⚠ ★★ **工具给的是【候选集】⇒ ⇒ 终值必须逐条人工/实测**（★ R63 §4：按名命中几乎总是假阳性；**按名零命中**才是可信证据）。
2. ⚠ ★★ **「零命中 ⇒ 可判定不依赖」的前提守卫只挡住【前缀拼接】** ⇒ ⇒ 若产品用**运行时拼名**（如 `fmt.Sprintf("%s_%s", base, suffix)` 且 `base` 来自配置）⇒ ⇒ **守卫挡不住** ⇒ ⇒ ★★ **⇒ 那类依赖只能靠「动态拼名前缀探测」之外的机制（如配置白名单）来覆盖**。
3. ⚠ ★★ **腿 B 的排除清单是【人工维护的】** ⇒ ⇒ 上游若在别处新增引用型目录 ⇒ ⇒ 腿 B 看不见 ⇒ ⇒ ★★ **⇒ 它不覆盖「上游新增目录」这类变化**（★ 与 R104 轮的门同一条边界）。
4. ⚠ ★★ **腿 A 的 DDL 形态覆盖仍可能不全** ⇒ ⇒ 实测已覆盖 `table` / `view` / `materialized view` / `function…RETURNS TABLE` / `RENAME TO` / `CREATE TYPE` / `CREATE SCHEMA` / `TEMP TABLE` ⇒ ⇒ **但没覆盖**：`CREATE TABLE … AS SELECT`（名字仍被 `createTableRE` 抓到 ✔）、`CREATE INDEX`（不是关系）、`CREATE OPERATOR`、物化视图的 `REFRESH` 等 ⇒ ⇒ ★★ **⇒ 新增形态 ⇒ 腿 A 会漏 ⇒ ⇒ 悬空引用被高估（★ 方向安全：高估 ⇒ 门红 ⇒ 不会漏报真缺口）**。
5. ⚠ ★★ **`isAliasQualified` 会误伤「非 schema 的限定名」**（例如 `otherdb.tbl`）⇒ ⇒ **已知漏检**（★ 方向危险：会漏掉真缺口）⇒ ⇒ ⇒ **若将来出现跨库访问，须放宽这条**。
6. ⚠ ★★ **生产库上 `prompt_injection_approvals` 是否存在【本轮未核实】** ⇒ ⇒ **⇒ 需属主裁决（§六.3）** ⇒ ⇒ ★★ **本轮对生产的写入 = 0**。
7. ⚠ ★★ **本轮【未实现】的部分**：★ 「动态拼名前缀探测」的**完整版**（目前只做了「字面量以关系名开头且更长」这一档）｜★ 三档桶的**弱命中桶尚未逐条人验**（★ 254 个名字）。

## 九、★ 通用式（已沉淀进 LESSONS `§236`）

1. ⭐⭐⭐⭐⭐ **★ 「先量后建门」在【提取器】上的形态 = ★ 「先把候选压到【可人验的量级】，★ 才值得做成门」** ⇒ ⇒ ★★ **⇒ 第一版 309 个名字 / 904 处若直接做成门 ⇒ 门一上去就恒红 ⇒ ⇒ ★★★ 而【恒红】比【没有门】更坏**（★ 它会让人养成「忽略红灯」的习惯）⇒ ⇒ ★★★ **⇒ 判据：★ 候选集必须小到【能逐条读完】**（★ 本轮：309 → 12）。
2. ⭐⭐⭐⭐⭐ **★ 「量具自身的读取方式」也会静默出错 —— ★ 它不会报错，只会少读** ⇒ ⇒ ★★★ **★ `git ls-files` 默认对非 ASCII 路径做八进制转义并加引号 ⇒ ⇒ 那批文件打不开、而【数目完全正常】** ⇒ ⇒ ★★ **⇒ 修法 = `git ls-files -z`** ｜★ ★★ **⇒ 推论：★ 「数目相等」≠「清单可用」⇒ ⇒ 判据必须是【逐个可打开】**。
3. ⭐⭐⭐⭐⭐ **★ 「双口径互证」⇒ ★ 两边的【排除规则】必须先对齐 ⇒ ⇒ 否则互证本身会误报** ⇒ ⇒ ★★ **本例：文件系统枚举跳过 `vendor/`、而 `git ls-files` 不跳 ⇒ ⇒ 报出「清单被截断」的假红** ⇒ ⇒ ★★★ **⇒ ⇒ 互证前先问「两边扫的是同一个集合吗」**。
