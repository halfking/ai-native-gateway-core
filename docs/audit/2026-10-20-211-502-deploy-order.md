# 211 部署后 llm.itestu.cn 502 复盘（2026-10-20）

**一句话**：守卫（前端新鲜度检查）本身是对的，但它跑在**拆掉旧容器之后**——一次「部署失败」因此被放大成「服务下线」。

## 现象

- 部署 211 后，`https://llm.itestu.cn/?login=1` 返回 **502 Bad Gateway**（nginx 生成）。
- 同一次部署的日志停在：

  ```
  [211] 应用镜像已推送: registry-211.itestu.cn/app-images/llm-gateway-go:211-3eb2be91
  [211] FATAL: /root/llm-gateway-go-211/web/dist 陈旧：.../web/src/composables/useNodeDetailDrawerLoad.ts
         晚于 /root/llm-gateway-go-211/web/dist/index.html，拒绝部署陈旧前端
  ```

- 现场复核（211 本机）：

  | 读数 | 结果 |
  |---|---|
  | `docker ps -a --filter name=llm-gateway-211` | **空**（容器根本不存在） |
  | `ss -lntp \| grep 8781` | **无监听** |
  | nginx upstream `ns_llm_gateway_upstream` | 主 `127.0.0.1:8781`，备 `100.106.169.63:8782` |
  | `curl -k https://llm.itestu.cn/?login=1` | 502（nginx 生成） |

## 根因：顺序，不是规则

`scripts/deploy-211-docker.sh` 的旧阶段顺序：

```
① 同步仓库 → ② 构建镜像 → ③ 推送镜像
④ docker rm -f llm-gateway-211            ← 旧容器在这里被销毁
⑤ seed_web_dist：判定前端是否陈旧 → die   ← 守卫在这里才跑
⑥ docker run -d ...（新容器）
```

守卫失败（`die`）落在 ④ 与 ⑥ 之间 ⇒ **旧容器已删、新容器未起** ⇒ 8781 无监听 ⇒ nginx 502。
守卫要拒绝的东西（陈旧前端）确实该拒绝；错的是**拒绝发生在服务已被拆之后**。

守卫的失败形态应当是「**这次部署不发生**」，而不是「服务下线」。

## 为什么只有 211 中招

| 目标 | 形态 | 判定/验收失败时 |
|---|---|---|
| 154 / 245 | `deploy-seamless.sh` 蓝绿：候选实例先起在候选端口，验收过才切流 | `_bluegreen_abort` → 旧实例一直在服务（`deploy-seamless.sh:1515/1523/1550` 全部验收在 `systemctl stop '$active_service'`（:1566）**之前**） |
| local | `deploy-local.sh` 原子 `current` 符号链接切换 + verified release 回滚 | `rollback()` 切回上一版；前端构建失败在 staging **之前** die |
| **211** | **单容器 docker，没有候选端口** | **旧容器已 `rm -f` ⇒ 停机** |

⇒ 单容器形态必须自己实现「**可回滚的退役**」，否则任何拆后失败都是停机。

## 修法（三层）

1. **输入判定前移**
   - 部署机侧（`--via`）：**同步之前**就判 ⇒ 失败则连目标机都不碰（不 sync、不 build、不 push）。
   - 211 本机侧：远端树是「真正要部署的那份」，是权威判据，同样在一切破坏性动作之前。
   - DB 迁移重放腿一并前移到退役之前（154/245 家族也是「切流前迁移」）。
2. **退役改成可回滚**
   - `docker rm -f` → **改名 + 停机**（`llm-gateway-211` → `llm-gateway-211-prev`），容器对象与镜像都留着。
   - 拆后任何失败走 `d211_fail` → `d211_rollback_gateway`：删新容器 → **还原种子**（web/dist、web-mobile/dist、version.json、configs）→ 旧容器改名回来 → 重新拉起。
   - 还原种子是必须的：旧容器挂的是同一批宿主路径，不还原就会跑起「旧二进制 + 新 SPA」的错配组合。
3. **网页面验收移植到 211**（154 的教训：**API 全绿 ≠ 网页可用**）
   - 154 那次 500 事故中 readyz / healthz / 登录全过，只有 nginx 读静态页失败。
   - 211 原来只探 `/readyz` 与 `/`（且 `/` 只 warn）⇒ 补两层：
     - 直连容器：真实 HTML → 抽出入口 JS → 校验它以 JavaScript MIME 发出来；
     - 公网入口：`llm.itestu.cn` 经 nginx 必须 200（不能 502）。
   - ⚠ 211 的 nginx upstream 有 backup（mac mini :8782），公网 200 可能是 backup 顶上的 ⇒ 直连层是「211 自己的责任」，两层都要过。

## 顺带修掉的两个真缺陷

1. **前端构建在 HEAD 上就是坏的**：`web/src/views/CredentialHeatmapView.test.ts` 的
   `writeButtons(w: ReturnType<typeof mountHeatmap>)` —— `mountHeatmap` 改成 async 之后
   `ReturnType` 变成 `Promise<VueWrapper>`，`w.findAll` 类型不成立 ⇒ `vue-tsc --noEmit` 失败
   ⇒ **所有前端构建都失败** ⇒ 部署机永远拿不到新 dist ⇒ 守卫永远拒绝。
   引入于 `e19318817`（2026-10-20 01:31），而最后一次成功构建的 dist 是 00:47。
   修法：`Awaited<ReturnType<typeof mountHeatmap>>`。
2. **本机链路（`deploy-local.sh`）没有同款新鲜度门**：`--no-frontend` 与「node_modules 缺失 →
   沿用既有 dist」两条路径都会把**可能陈旧**的 dist 打进发布包（无声前端回滚）。
   已补 `check_web_dist_freshness`（口径与 211 一致，逃生舱 `DL_ALLOW_STALE_WEB=1`）。

## 判据

`tests/deploy_211_teardown_order_test.sh`（22 条）：

- **行为层**（docker 替身驱动被测脚本抽出的真函数）：守卫拒绝时旧容器仍在服务且没被改名退役；
  拆后失败时旧容器原样拉回并重新拉起；回滚时旧种子被还原。
- **语义层**：前端新鲜度判定的四种结局（新鲜 0 / 陈旧 1 / 缺失 2 / 缺失但上一轮种子还在 3）。
- **结构层**：守卫在退役之前；退役之后不再硬删在跑的容器；退役是「改名 + 停机」；
  失败点走 `d211_fail` 而非裸 `die`；部署机侧也有同步前的门。

**变异验证（6 条，全部被捕获且红在被测对象上）**：

| 变异 | 期望 | 实得 |
|---|---|---|
| M1 守卫挪到退役之后 | 顺序门红 | 红 1 条（顺序断言） |
| M2 退役改回硬删 | 退役形态门红 | 红 1 条 |
| M3 `d211_fail` 不回滚 | 行为层红 | 红 4 条 |
| M4 回滚不还原种子 | 种子还原红 | 红 1 条 |
| M5 守卫恒放行 | 语义层红 | 红 3 条 |
| M6 就绪失败改回裸 die | 结构层红 | 红 1 条 |

⚠ 第一次跑变异时 M5/M6「红了」但红在**判据脚本自己**（`$out）` 在 bash 3.2 下把多字节首字节
并进变量名 ⇒ unbound variable ⇒ 脚本提前退出）。已修判据脚本并复跑，两条变异转为真实断言红。
这条本身也是一条经验：**「红」的读数与「不红」一样要先验量具**。

既有门 `tests/deploy_211_contract_test.sh` 110 条仍全绿。

> ⚠️ **订正（2026-10-21 轮）**：上面这句「110 条仍全绿」**不成立** —— 那道门
> **本身是随机假红的**，本轮实测复跑 5 次红 1 次、再 10 次红 1 次，且**失败项在
> 复跑间漂移**（这轮是「configs 种子」那条，下轮是「GO 基础镜像」那条）。
> 根因不是断言写错，是**量具自身有竞态**：`set -o pipefail` 下
> `printf '%s' "$_nocomment" | grep -q` —— `grep -q` 命中即退出 ⇒ 上游 `printf`
> 还在写 ⇒ 收 **SIGPIPE(141)** ⇒ pipefail 把整条管道判成非零 ⇒ `if` 走 else 分支。
> 实测单条断言 60 次里 `printf` 收 SIGPIPE **1 次**（`_nocomment` 52KB）。
> ⇒ 已在同轮修掉（35 处 `printf|grep` → here-string + 结构自检门），
> 修后 **30/30 次全绿**。详见 `docs/96小时内修订审计-20261007-1350.md` §十。
> ⇒ **教训**：「门全绿」这句话本身也要有证据（复跑次数 + 失败项是否漂移），
> 单次全绿不能作为「门可靠」的结论。

## 154 / 245 / local 的核查结论

- **154 / 245**：结构安全。全部验收（网页面 `verify_public_web`、DB、登录、凭据冒烟、公网版本身份）
  都在 `systemctl stop '$active_service'`（`deploy-seamless.sh:1566`）之前，失败一律 `_bluegreen_abort`。
  2026-10-20 的 154 修复（`3462a8e09`）已补齐「release 目录权限归一化 + 公网网页面验收」。
- **local**：切流是原子符号链接切换，失败可回滚到 verified release；前端构建失败在 staging 之前 die。
  本轮补上了它缺的**新鲜度门**（见上）。
