### 2. 字节数追踪 (`domains/streaming/responses_bridge.go:770-772`)

```go

scaffold.contentBytes += len(chunk.Delta.Content)
scaffold.reasoningBytes += len(chunk.Delta.ReasoningContent)
```

**位置**: `StreamAnthropicSSEToResponsesWithDiagnostics`函数内
**覆盖**: Anthropic和OpenAI两种协议

### 3. 核心判定逻辑修改 (`domains/streaming/responses_bridge.go:1273-1303`)

**原逻辑**:
```go
responsesHasSemanticOutput := func() bool {
    if fullText.Len() > 0 {  // 任何文本都算
        return true
    }
    // ... tool_calls检查
}
```

**新逻辑**:
```go
responsesHasSemanticOutput := func() bool {
    // 优先使用精确的contentBytes追踪
    if scaffold.reasoningBytes > 0 || scaffold.contentBytes > 0 {
        if scaffold.contentBytes > 0 {  // 只有非reasoning的content才算
            return true
        }
    } else if fullText.Len() > 0 {
        // 回退到fullText(向后兼容)
        return true
    }
    // ... tool_calls检查
}
```

**关键设计决策**:
1. **双路径策略**: 优先使用精确追踪,回退到原有逻辑(向后兼容)
2. **判定条件**: `reasoningBytes > 0 || contentBytes > 0` 表示已追踪
3. **向后兼容**: 未追踪的路径仍使用`fullText.Len()`

## 关键发现与修正

### 🐛 发现的问题 #1: 判定逻辑与数据来源不一致

**问题**: 初版实现只检查`scaffold.contentBytes`,但未考虑某些代码路径可能直接填充`fullText`而不经过追踪代码

**症状**: 多个测试失败,报告有content但被误判为空

**根因**: 
- `StreamOpenAIToResponsesSSE`和`StreamAnthropicSSEToResponses`是两个独立函数
- 判定逻辑在闭包内,无法确定fullText是如何被填充的
- 只追踪一个路径会导致另一个路径的误判

**修正**: 采用**双路径策略**
```go
if scaffold.reasoningBytes > 0 || scaffold.contentBytes > 0 {
    // 已追踪:使用精确判定
    if scaffold.contentBytes > 0 { return true }
} else if fullText.Len() > 0 {
    // 未追踪:使用原有逻辑(向后兼容)
    return true
}
```

**教训**: 
- ⚠️ **修改判定逻辑时,必须确保所有数据来源都被正确处理**
- ⚠️ **向后兼容性不是可选项,是必须**
- ⚠️ **测试失败是好事,它们捕获了设计缺陷**

### ✅ 验证的正确性

1. **字节数追踪准确**: content和reasoning分别计数,无重复无遗漏
2. **判定逻辑正确**: reasoning-only场景正确识别
3. **向后兼容**: 未追踪路径使用原有逻辑
4. **tool_calls处理**: 独立于text内容,正确判定为semantic output
