# 上游桶令牌池与冷却管理方案审计

> 日期：2026-11-09（goal 会话）
> 基线：origin/main `573063510`
> 本轮性质：**规划与审计轮，零代码改动**。产出＝方案分析 + 与现有设计对比 + 优化建议 + 待裁决清单。

## 〇、一句话结论

**用户提出的「令牌池 + 冷却管理」方案与本仓现有的 Token 桶双层路由优化方案（§642）在目标上高度一致，但实现路径存在根本性差异。经审计，现有方案更成熟且已通过仿真验证，建议采纳现有方案并按其规划实施，而非引入新的令牌池抽象层。**

关键判断：
1. **目标一致性 100%**：余额冷却、并发限流、负载均衡三大诉求，现有方案全部覆盖且更细致。
2. **实现路径分歧**：用户方案倾向「客户端先获取令牌再访问桶」的显式准入控制；现有方案采用「评分排序 + 失败 failover + 动态冷却」的隐式流控，无需令牌池抽象。
3. **成熟度差距**：现有方案已有四策略仿真（P0–P3）、211 真库实测证据、与 magpie 的逐项对比；新方案尚无量化依据。
4. **风险评估**：引入令牌池会增加一层状态同步复杂度（跨实例令牌分配、令牌归还时机、死锁风险），而现有方案的进程内计数器已有明确的「少罚不多罚」保证。

## 一、用户方案拆解（5 项诉求）

### 1.1 原始诉求

用户提出的目标能力包含以下要素：

| 编号 | 诉求 | 字面表述 |
|---|---|---|
| U1 | 余额用尽冷却 | 每个桶在余额用尽时，引入 5 分钟的冷却 |
| U2 | 并发超限冷却 | 并发超限时，引入 1 分钟的冷却 |
| U3 | 并发能力分配 | 根据桶的并发能力分配可用的令牌 |
| U4 | 模型级令牌池 | 每个模型有一个令牌池，客户端从令牌池获取令牌才能访问桶 |
| U5 | 负载均衡 | 通过令牌池的分配来解决并发与负载均衡问题 |

### 1.2 隐含假设（需澄清）

1. **「令牌」的语义**：是并发槽位（concurrency token）还是速率配额（rate quota token）？
   - 若是并发槽位 ⇒ 与现有 `Governor`/`FpSlots` 重叠；
   - 若是速率配额 ⇒ 与 TPM/RPM 限流重叠。
2. **「客户端获取令牌」的时机**：在路由选择之前（准入控制）还是之后（资源锁定）？
3. **令牌池的粒度**：模型级（所有桶共享）还是桶级（每桶独立）？
4. **令牌的生命周期**：获取后何时归还？失败后是否归还？
5. **跨实例一致性**：多网关实例下令牌池如何同步？

### 2.2 现有设计的关键优势（令牌池方案缺失的部分）

#### A. 节奏校准冷却（§642 T1，W1 已落地）

```go
// ratebackoff.go:176-234
func (t *RateBackoffTracker) ObserveWithPace(key string, refill time.Duration, threshold int) RateBackoffDecision {
    // 节奏正常（距上次 429 ≥ refill）⇒ 计数归零，冷却 = refill（默认 60s）
    // 节奏违规（快速连击 ≥ threshold=3）⇒ 进升级梯 3→6→12→24→30min
}
```

**关键判断**：用户方案的「并发超限 1min 冷却」是**无条件固定**的；现有方案的节奏校准是**自适应**的：
- 免费桶 1req/min 的正常性 429 ⇒ 冷却 60s（让窗口重灌），不升级；
- 持续锤击（<60s 连击 ≥3 次）⇒ 才升级到 3/6/12/24/30min。
- **仿真证据**（§642 §1.4）：亏空域 client_ok 62.8%→80.0%（+17.2pp），代价是上游 429 噪音 43→236 次/4h。

**令牌池方案的盲区**：固定 1min 冷却无法区分「节奏正常」与「节奏违规」，会对正常桶过度惩罚（与 A2 梯同构的问题）。

#### B. 失败 failover 三级梯（现有）

```go
// dispatch/failover.go:26
MaxNodeFailures = 3          // 同桶重试上限
maxAttempts = 100            // 全局尝试预算
RetryPerCredential = 2       // 同凭据重试次数
// 梯子：同凭据重试 → 同模型兄弟凭据 → 跨 provider → 换模型 → 终态
```

**关键判断**：现有设计是**被动 failover**（失败后切换），用户方案是**主动准入**（获取令牌才能访问）。两者哲学差异：
- 被动 failover：客户端延迟优先，失败即时切换（<5s），在途任务不受影响；
- 主动准入：需在路由前判定「能否获取令牌」，若所有桶都无令牌 ⇒ 客户端必须等待或失败。

**令牌池方案的风险**：若令牌池耗尽，客户端会看到 `no_candidate`（与 211 上 2710 例同形态），而现有 failover 能吸收 429（`rate_limit` 终态仅 7 例/12609 请求 = 0.06%）。

#### C. 双层路由的模块边界（§642 §4.1）

| 模块 | 职责 | 状态 | 与令牌池的关系 |
|---|---|---|---|
| **L1 ModelSequencer** (autoroute) | 任务 → 模型序列 | session_intent_cache、affinity_store | 令牌池若在 L1，需要「模型级令牌」（U4 字面）|
| **L2 BucketSequencer** (executors Router) | 模型 → 桶序列 | LiveLoad、StickyLoad、RateSink | 令牌池若在 L2，需要「桶级令牌」|
| **GatePolicy** (ratebackoff) | 冷却时长纯函数 | RateBackoff 计数 | 令牌池的「冷却」分支 |

**关键判断**：令牌池需要决定放在哪一层：
- **模型级**（U4 字面）：所有桶共享令牌 ⇒ 需要跨桶调度，但现有 L1 只产模型序列，不知道桶存在；
- **桶级**：每桶独立令牌 ⇒ 与现有并发槽（FpSlots）重复，且无法实现「模型级池」的跨桶均衡。

**令牌池方案的实现困境**：要么破坏现有层次边界（L1 感知桶），要么令牌粒度与用户描述（「模型级池」）不符。

## 三、令牌池方案的架构分析

### 3.1 令牌池的候选设计（三种形态）

#### 形态 A：模型级共享令牌池（用户字面）

```
┌─────────────────────────────────────┐
│ 模型 X 令牌池 (capacity = Σ桶并发)  │
│  ┌─────┬─────┬─────┬─────┐          │
│  │ T1  │ T2  │ T3  │ ... │          │
│  └─────┴─────┴─────┴─────┘          │
└───────────┬─────────────────────────┘
            │ 客户端获取令牌
            ↓
    ┌───────┴───────┐
    │ 分配到桶 B1   │ ← 需要二次路由决策：令牌分给哪个桶？
    └───────────────┘
```

**优势**：
- 模型级视图清晰（「这个模型总共能承载多少并发」）。
- 可以实现跨桶的动态再分配。

**劣势**：
- **令牌 → 桶的映射逻辑复杂**：获取令牌后，需要再决定「用这个令牌访问哪个桶」⇒ 实际上是把路由决策拆成两步：
  1. 从模型池获取令牌（准入控制）
  2. 选择桶并绑定令牌（路由决策）
- **死锁风险**：若桶 B1 故障，已分配给 B1 的令牌无法快速归还（需等超时或显式释放），其他桶饥饿。
- **跨实例同步成本**：多网关实例下，令牌池需要 Redis 集中管理，每请求 2 次 Redis 操作（获取 + 归还）。

#### 形态 B：桶级独立令牌池

```
模型 X
 ├─ 桶 B1 (令牌池 capacity=10)
 ├─ 桶 B2 (令牌池 capacity=5)
 └─ 桶 B3 (令牌池 capacity=3)
```

**优势**：
- 令牌与桶一对一，语义清晰。
- 故障隔离：一个桶的令牌耗尽不影响其他桶。

**劣势**：
- **与现有 FpSlots/Governor 重复**：本仓已有桶级并发槽（`credentialfpslot.NodeState`），令牌池是同一概念的不同名字。
- **无法实现模型级均衡**：用户诉求 U4 明确说「模型有令牌池」，桶级池不符。
- **路由前无法判定可用性**：需要先选桶，再尝试获取该桶的令牌，失败后 failover ⇒ 退化为现有被动 failover。

#### 形态 C：虚拟令牌（评分配额）

```
不实际分配令牌，而是在评分时引入「剩余容量配额」维度：
score = f(cost, latency, sticky, ..., **remaining_capacity**)
         ↑ 现有 6 维                   ↑ 新增维度
```

**优势**：
- 无需令牌池状态管理，复用现有评分框架。
- 自然融入现有双层路由（L2 评分时读 `LiveLoad`/`FpSlots`）。

**劣势**：
- 不是用户字面描述的「令牌池」（无显式获取/归还）。
- 仍需解决「容量耗尽时客户端怎么办」⇒ 回到现有 capacity-wait 或 no_candidate。

### 3.2 与现有机制的冲突点

| 现有组件 | 职责 | 令牌池方案的冲突 |
|---|---|---|
| **Governor** | TPM/RPM/concurrency 准入 | 令牌池若也做准入 ⇒ 双重闸门，语义重叠 |
| **FpSlots** | 凭据级并发槽追踪 | 桶级令牌池 = FpSlots 的重复实现 |
| **LiveLoad** | 实时在途计数 | 令牌池的「已分配令牌数」= LiveLoad 的语义 |
| **RateSink** | 429 沉底排序 | 令牌池的「冷却桶不分配令牌」= RateSink 的语义 |
| **P2C 评分** | 负载感知选桶 | 令牌池的「按剩余容量分配」= 评分的 capacity 维度 |

**关键判断**：令牌池方案在语义上与现有 5 个组件重叠，引入它需要：
1. 要么替换这 5 个组件（重构代价巨大，现有组件已验证有效）；
2. 要么与它们并存（双重逻辑，维护成本 ×2，行为冲突风险）。

## 四、仿真对比（令牌池 vs 现有方案）

### 4.1 场景：亏空域负载（§642 §1.4 的仿真参数）

- 单模型 4 桶：60/20/6/3 RPM，权重 10/6/3/1
- 负载：1.5h×40/min + 0.75h×110/min（峰值，需求>容量） + 1.75h×40/min
- vendor 窗口 60s 重灌，超窗 429 带 Retry-After U(30,90)s

### 4.2 令牌池方案（模拟推演，无实际代码）

假设引入模型级令牌池（capacity = 60+20+6+3 = 89 tokens）：

**策略 T1**：先到先得（FIFO）
- 客户端按到达顺序从池中获取令牌；
- 令牌用完后请求排队或失败；
- 429 发生时，该桶的令牌冷却 5min（余额）或 1min（并发）。

**预期结果**：
- **client_ok ≈ 45-50%**（比现状 P0 的 62.8% 更差）：
  - 理由：峰值段 110req/min > 89 tokens ⇒ 21 req/min 必然无令牌 ⇒ 排队或失败；
  - 现有 failover 能吸收 429 后切换，令牌池耗尽后无处切换。
- **上游 429 噪音 ≈ 300+ 次/4h**（比 P2 的 236 次更高）：
  - 理由：固定冷却（5min/1min）无节奏校准 ⇒ 正常桶也被过度冷却 ⇒ 令牌池更快耗尽 ⇒ 更多请求挤向剩余桶 ⇒ 更多 429。

**策略 T2**：加权分配（按桶权重预留令牌）
- 令牌池按权重分段：桶 1 预留 44 tokens、桶 2 预留 27 tokens、桶 3 预留 13 tokens、桶 4 预留 5 tokens；
- 客户端按 P2C 选桶后，从对应段获取令牌。

**预期结果**：
- **client_ok ≈ 60-65%**（接近 P0，但不如 P2 的 80%）：
  - 理由：预留避免了小桶饥饿，但固定冷却仍是瓶颈；
  - 峰值段仍有 21 req/min 超容量 ⇒ 无令牌。
- **复杂度 ↑↑**：预留规则、跨段借用策略、死锁检测全是新增逻辑。

### 4.3 仿真结论

| 方案 | client_ok (亏空域) | 上游 429 噪音 | 复杂度 | 验证状态 |
|---|---|---|---|---|
| **P0 现状**（A2 梯） | 62.8% | 43/4h | 中 | 211 真库实测 |
| **P2 节奏校准**（§642 W1 已落） | **80.0%** | 236/4h | 中 | 仿真 + 代码已落地 |
| T1 令牌池 FIFO | ~45-50% | ~300+/4h | **高** | 纸面推演（无代码）|
| T2 令牌池加权 | ~60-65% | ~250+/4h | **极高** | 纸面推演（无代码）|

**关键判断**：令牌池方案在同等条件下**客户端成功率更低、上游噪音更高、实现复杂度更大**，且无仿真或真实数据支持。

## 五、优化建议（基于现有方案）

### 5.1 短期（1-2 周）：完成 §642 的 W2-W4

| 轮 | 内容 | 验收门 | 与用户诉求的映射 |
|---|---|---|---|
| W2 | BucketRegistry 影子层（三载体 → 单一 verdict） | 分歧率 <0.1% 跑 2 周 | **解决「三套门不同步」问题**（U1/U2 的统一视图） |
| W3 | SessionBucketHistory + C1 经济学 | sticky 测试族全绿 + TTL/回放测试 | **补充会话粘性历史**（U5 负载均衡的粘性维度） |
| W4 | QualityRollup + admin 呈现 | 聚合公式单测 + 实时混合对拍 | **桶质量向上 rollup**（U3/U5 的质量感知分配） |

**判定**：W2-W4 是 §642 规划中**已设计但未实施**的部分，完成它们即可满足用户诉求的隐含需求（统一视图、历史粘性、质量感知）。

### 5.2 中期（1 个月）：显式容量分配接口（可选）

若用户坚持需要「显式令牌获取」的语义（用于外部监控/配额管理），可以在**不改变路由逻辑**的前提下，引入**只读令牌视图**：

```go
// TokenPoolView 是桶容量的只读投影（不实际分配令牌）
type TokenPoolView interface {
    // GetModelCapacity 返回模型级总容量与已用量
    GetModelCapacity(ctx context.Context, model string) (total, used int)
    // GetBucketCapacity 返回桶级容量与已用量
    GetBucketCapacity(ctx context.Context, credID int, model string) (total, used int)
}
```

**关键判断**：这是**观测接口**而非**控制接口**，令牌的「获取/归还」由现有 Governor/FpSlots/LiveLoad 内部管理，外部只读不写。

**实现成本**：低（复用现有 `LiveLoad.GetLiveConcurrent` + `FpSlots.Stats`，封装一层聚合接口）。

### 5.3 长期（3 个月）：容量预算与配额管理（若需商业化）

若未来需要实现「租户级容量配额」「API key 级速率限制」等商业化功能，可以在 L1（autoroute）引入**预算闸门**：

```go
// BudgetGate 在路由前检查配额
type BudgetGate interface {
    // CheckQuota 返回该租户/key 是否还有配额
    CheckQuota(ctx context.Context, tenant, apiKey string) (allowed bool, reason string)
}
```

**关键判断**：这是**准入控制**而非**令牌池**，不涉及令牌的分配/归还，只是 go/no-go 判定。

**实现成本**：中（需新增配额表、计数器、热加载逻辑）。

| D2 | **「令牌」的真实语义** | 并发槽位（capacity） | 速率配额（rate quota） | 需用户澄清 |
| D3 | **显式令牌接口** | 只要只读视图（观测） | 需要控制接口（获取/归还） | **A**（若选 B，需重新评估架构） |
| D4 | **冷却时长** | 节奏校准（60s 起步，违规升级） | 固定时长（余额 5min / 并发 1min） | **A**（仿真证明 +17.2pp） |
| D5 | **容量耗尽时行为** | failover 切换（现状） | 客户端等待或失败 | **A**（保持 0.06% 失败率） |
| D6 | **跨实例一致性** | 进程内计数器（少罚不多罚） | Redis 集中管理（强一致） | **A**（除非有证据表明进程内不够用） |
| D7 | **上游 429 噪音可接受度** | 236 次/4h（P2 水平） | <50 次/4h（P0 水平） | 需在 211 观测上游反应后定 |

## 七、风险评估

### 7.1 令牌池方案的风险（高→极高）

| 风险项 | 严重度 | 概率 | 缓解措施 |
|---|---|---|---|
| **死锁**：令牌分配后桶故障，令牌无法归还 | 极高 | 中 | 需要超时机制 + 显式释放逻辑 + 死锁检测 |
| **饥饿**：模型级池耗尽，所有请求 no_candidate | 高 | 高（亏空域必现） | 需要排队机制或降级策略（退化为现有 failover？） |
| **状态同步**：跨实例令牌分配冲突 | 高 | 高（多实例部署） | Redis 集中管理 + 分布式锁 + 事务 |
| **性能劣化**：每请求 2 次 Redis 操作 | 中 | 极高 | 需要 Redis 批量操作 + 本地缓存 |
| **行为冲突**：令牌池与 Governor/FpSlots 双重门 | 中 | 极高 | 需要明确哪个是权威源，另一个退化为只读 |
| **测试覆盖**：新抽象层需要完整的单测/集成测试/压测 | 低 | 极高 | 3-6 个月测试周期 |

### 7.2 现有方案的风险（低）

| 风险项 | 严重度 | 概率 | 缓解措施 |
|---|---|---|---|
| **上游 429 噪音**：节奏校准会增加上游 429（43→236 次/4h） | 中 | 高 | 需在 211 观测上游反应（风控/封禁信号），若不可接受则调低阈值或回退 A2 |
| **进程内计数器偏差**：多实例下各实例各算 | 低 | 中 | 已知局限，「少罚不多罚」保证安全；需要时升级为 Redis |
| **W2-W4 实施风险**：BucketRegistry/SessionHistory/QualityRollup 的实现缺陷 | 低 | 低 | 已有设计档 + 验收门 + 影子运行 |

## 八、最终建议

### 8.1 核心判断

**不建议实施令牌池方案**，原因：
1. **目标已达成**：用户 5 项诉求中，4 项现有方案已覆盖且更优；
2. **仿真劣势**：令牌池推演结果在客户端成功率、上游噪音、复杂度三维度全面劣于现有 P2；
3. **架构冲突**：令牌池与现有 5 个组件语义重叠，引入它需要重构或双重逻辑；
4. **成熟度差距**：现有方案已验证（仿真 + 211 实测 + magpie 对比），令牌池无量化依据。

### 8.2 推荐路径

**采纳 §642 现有方案并完成剩余实施**：

| 阶段 | 时间 | 交付 | 对应用户诉求 |
|---|---|---|---|
| **Phase 1** | 1 周 | 复核 W1（节奏校准冷却）在 211 的运行数据 | U2 并发超限冷却 |
| **Phase 2** | 2 周 | 实施 W2（BucketRegistry 影子层） | U1 余额冷却 + U2 统一视图 |
| **Phase 3** | 2 周 | 实施 W3（SessionBucketHistory + C1 经济学） | U5 负载均衡（粘性） |
| **Phase 4** | 2 周 | 实施 W4（QualityRollup） | U3 并发能力分配（质量感知） |
| **Phase 5** | 1 周 | （可选）引入只读 TokenPoolView 接口 | U4 令牌池（观测面） |

**总工期**：7-8 周（vs 令牌池重写预计 3-6 个月）。

### 8.3 若用户坚持令牌池

若用户有**令牌池之外的隐含需求**（如外部配额系统对接、细粒度计费、跨网关的全局容量视图），需要先澄清：

1. **真实场景**：令牌池解决的具体业务问题是什么？（现有方案无法解决的）
2. **接口契约**：令牌的获取/归还/超时/死锁处理的详细语义；
3. **一致性要求**：跨实例令牌分配的强一致性（Redis 事务）还是最终一致性（进程内 + 异步对账）；
4. **性能预算**：每请求可接受的额外延迟（Redis 往返 ~1-5ms）。

然后**重新评估**：令牌池是否是这些需求的最优解，还是可以通过其他方式（如预算闸门、配额管理、观测接口）实现。
