## 四、三个问题

### D1（真缺陷）两份「地址族」名单已漂移

「地址族 = 域名 / 地址 / ip」这条口径在仓内被写了两遍：

| 位置 | 名单 |
|---|---|
| `security/sanitize/detector.go` 的 `scopedType` | server_ip / internal_ip / server_ipv6 |
| `domains/outputcompliance/checker.go` 的 `isAddressPIIType` | ip / ip_address / ipv6 / server_ip / internal_ip / **address / domain / hostname** |

⇒ **同一个类型在两个面得到相反待遇**：一条 `domain` 类型的规则，
在合规面「只检出不遮蔽」，在脱敏面**照遮**。
⇒ 修法：口径收进 `domains/sanitizerules.IsAddressFamilyType`（清单取两份的**并集**，
只增不减 ⇒ 不意外收紧任何一面的豁免），两个面各调同一个函数。

### D2（真缺口·潜在）legacy 映射静默丢弃声明类型

`legacyPIIRule` 的 `default: typ = "custom"` 把**所有未知类型**降级成 `custom`。
`custom` 不在地址族豁免名单里（豁免按**声明类型**判定，不按正则内容判定）
⇒ 若有人给 `pii_patterns` 增一行 `pattern_type='domain'`，它会被降级成 custom
⇒ 脱敏面**仍然遮蔽域名**。

生产上当前没有这种行 ⇒ **潜在缺口，不是现行缺陷**。但缺口位置危险：
一行 `default` 兜底，且没有任何判据会报警。

⇒ 修法：`domain` / `hostname` / `address` 显式映射进地址族。
★ **`url` 刻意不映射**：URL 能携带凭据（`?token=…` / `/user/<secret>`），
整类豁免等于给查询串里的令牌开后门 —— 那比「域名被遮蔽」严重得多。
（判据里有一条**反向对照**专门守这个边界：谁把 `url` 加进豁免名单，门就红。）

### D3（判据盲区）生产真实规则集从未被任何判据跑过

r1038 的判据用 `r1038LegacyIPRule()` 这类**手工构造**的规则；生产规则集却是
「基线 + legacy 行 + 内置补充」。而且 legacy 映射当时住在 package main 里
⇒ **测试无法调用** ⇒ 想验真实规则集只能手抄一份映射（会漂移）。

⇒ 修法：
① 把 legacy 映射下沉为 `domains/sanitizerules.LegacyPIIRule`（生产与判据调**同一个函数**）；
② 新判据从**生产事实源**拼规则集（316 迁移 SQL + `RuleConfig()` + 内置基线）；
③ 判据形态从「拿一条规则测一次」改成**属性判据**（遍历规则集找违例）——
生产种子新增一行或改宽正则时，门会跟着变。

## 五、修复过程中我自己踩的两个坑（都记在这里）

### 坑 ①：`git checkout` 把一半改动还原了

清理残留时 `git checkout -- security/sanitize/detector.go` 把 detector 侧的
`scopedType` 改动一并还原（只补回了合规面那半）⇒ **提交里仍有两份名单**。

**当时新判据全绿** —— 因为生产种子里没有 domain 类型的行 ⇒
「生产真实规则集」这条路根本走不到域名分支 ⇒ **判据的适用面有盲区**：
它守得住「已存在的规则」，守不住「被声明的类型」。

⇒ 因此补了一条判据：**声明为网络定位符的规则 + 域名形态的正则 ⇒ 脱敏面不得遮蔽**，
并用 `custom` / `secret` 形态做反向对照（必须照遮）——
一正一反同时成立，才能证明「豁免是按**声明类型**判定的」。

### 坑 ②：造了一个词表外的类型，会让整份规则集装载失败

修 D2 时，我一度把声明的域名类型映射成**新造的 `domain` 类型**。
而规则类型词表是**封闭的**（`Compile` 只接受 phone / id_card / email / credit_card /
secret / internal_ip / server_ip / account / name / custom 这 10 个）
⇒ `NewManager` 直接拒绝**整份配置**：
`invalid sanitize rule configuration: rules[0].type must be a restorable sensitive type`。

**那比原缺陷严重得多**（整个脱敏规则集起不来）。它是被新判据当场抓住的，
不是上线后才发现。

⇒ 改用仓内既有约定：legacy 导入已经把 ip / ip_address / ipv6 全映射成 `server_ip`
⇒ 域名类也映射成 `server_ip`（「网络定位符」），词表与语义都不破。
⇒ 并新增一条判据：**legacy 映射对任何输入类型产出的规则都必须能被 `Compile` 接受**。

## 九、遗留（不擅自改，留给 owner）

**`pii.address`（中文地址规则）7 天命中 90,091 次**，误伤面是运营编号：
`员工工号 12345` / `订单号 20241012` / `任务号 88` / `房间号 1201` 整段被当地址遮蔽
（真地址 `北京市朝阳区建国路88号` 应遮）。根因是规则的**前导**字符类含「号」。

- **为什么不在这轮改**：① r1036（2026-10-20，154 生产取证）**明确冻结**了这个行为；
  ② 用户当年的「地址」指的是**网络地址**（示例里的 proxy host 与其并列的域名、ip），
  不是中文邮政地址；③ 改它会缩小 PII 覆盖面，属安全姿态变更。
- **建议（owner 一句话即可裁决）**：只从**前导**字符类去掉「号」、**后置**保留
  （`[^\s]{2,}[省市区县镇乡村路街道巷弄栋单元室]\s*[\d\-号栋单元室]+`）
  —— 真地址（`建国路88号` / `文三路100号`）仍命中，而「工号 / 订单号 / 任务号 / 房间号」
  这一族不再命中。**注意这与 r1036 的顾虑不同**：r1036 反对的是删掉**后置**的「号」。
