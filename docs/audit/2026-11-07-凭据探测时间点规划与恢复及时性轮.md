# 凭据探测时间点规划与恢复及时性轮（2026-11-07）

> 用户目标：检查凭据节点可用性探测（对象＝24h 内使用的模型 ∪ 特色模型；目标凭据＝出错/用尽）；
> 解决「凭据已恢复但状态未及时更正」；规划探测时间点做到**节约并有效**；

## 2. 场景模拟发现的问题（5 项）

- **P1【恢复永远不到达·核心】** 冷模型失败对的 Catch-22：失败 → 摘出路由 → 无流量 → 滚出热腿窗口 →
  scope 门永久 skip → 上游恢复后状态永不更正。中招面＝泵复检（source=periodic）与 expired-binding 恢复提交
  （source=request_failure，同时被 60s pair 频控误伤）。
- **P2【验证探针被静默丢弃】** `credential_recovery` 恢复事件的验证探针传 `model=""`，
  而 `NodeProbeWorker.Submit` 对空模型直接 return——「恢复后立即验证」链路实际断裂
  （main.go:4957 注释声称的「worker 自选 default_probe_model」哨兵语义不存在）。
- **P3【45s 空转】** scope skip 返回 `(false, nil)`，泵把到期行按 45s holdoff 无限重拾
  ⇒ 每行每 45s 一次 scope SQL 空转（P-1 修复残留形状：不再烧重试，但仍烧查询）。
- **P4【用尽期探测打爆】** 配额用尽（周/月窗口，智谱 1310 族）的节点级探测失败按 rate_limit 族
  每 3~5 分钟复检，而重置点已知（`quota_recover_at`）。7 天窗口 ≈ 2000+ 次注定 429 的探测/对；
  在「1 分钟最多 30 次含失败次数」类上游（凭据 29 形态）直接挤占业务配额，且与凭据级
  BalanceQuotaProbe（2^n due 闸封顶 1h）双流并行。
- **P5【注释失真】** BalanceQuotaProbe 头注声称 fallback「pick the cheapest routable model」，
  实现是「字典序第一可用绑定」（`fallbackProbeModel` sort.Strings）。

## 4. 修后恢复检测 SLA（时间点矩阵）

| 失败形态 | 恢复检测时间点（修后） | 修前 |
|---|---|---|
| periodic（5h 窗口） | 窗口边界 −60s 预探 / +5min tick（不变） | 同 |
| balance/permanent **已知重置点**（周/月） | 凭据级 ≤~7min（BalanceQuotaProbe）→ F5 回拉 → 泵 ≤30s 全行验证；节点行重置前 **0 次探测** | 节点行每 3~5min 空打整个用尽期 |
| balance **未知充值点** | 充值 webhook / ForceProbe / 2min tick×2ⁿ due 闸 → F5 回拉 → 泵 ≤30s | 同左（无回拉） |
| 瞬时/网络/限流 | ≤5min 恢复 SLA（不变） | 同 |
| 404/协议/网关侧 | 6h / 15min 长停放（不变，设计如此） | 同 |
| **冷模型失败对** | 恢复复检不再被拦（正常梯子）；scope 重评 15min | **永久 skip** |
| 凭据级恢复事件 | 即时 v2 探针（修前已通）＋ F1 修复的空模型验证探针 + F5 全行回拉 | 空模型探针被丢弃 |

## 7. 部署验证补记（本地 2946 → 2948）

- **2946 首次本地部署暴露第 6 个缺陷（本轮自己引入的漏检）**：F1 启用的 `source="credential_recovery"`

  5 分钟 +151。
