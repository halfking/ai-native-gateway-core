# 扩展指南 —— 让检查与项目推进并行生长

playbook 的价值在于**滚动演进**：每轮审计、每次新功能合入，都应当回流检查项。本文规定怎么加。

## 1. 何时回注

| 时机 | 动作 |
|---|---|
| 一轮审计结束 | 新发现的通用缺陷模式 → 对应域文档 §4 历史回归点追加一条 |
| 新功能/新 RFC 合入 | 该功能命中的域文档 §3 检查清单增补条目；若是全新领域 → 新建域文档 |
| 设计文档反转（如 storage-optimization-plan v2 推翻旧 hot 表口径） | 更新对应域文档 §2 参考基线，标注"以此为准" |
| 某检查项连续 3 轮零发现且无架构变化 | 标记 `低频`，可降为抽检（不删除，保留编号） |

## 2. 回注格式（域文档 §4）

```
- <R轮> <缺陷一句话>（<根因类型：契约/并发/闭环/边界>）— 修复 <commit>；钉桩 <测试名>
```

## 3. 新增域文档的规则

1. 编号接续最大 D 编号（当前 D17），slug 用 kebab-case 英文。
2. 必须包含五个固定章节：§1 领域边界（管/不管，与相邻域划界）/ §2 参考基线（设计文档+代码入口，路径必须真实存在）/ §3 检查清单（可核对句式）/ §4 历史回归点 / §5 子代理派发提示词。
3. 派发提示词必须**极短**：只说"Read 本文档 + conventions.md，然后按清单执行"，实质内容留在文档里（上下文经济原则）。
4. 建档后在 README.md 目录结构与映射表补一行，CHANGELOG.md 记一行。
5. 新域与既有域重叠时：在两域的 §1 互相点名划界（如 D05 不管队列重试编排，那属于 D04）。

## 4. 检查清单条目写法

- 用**可核对句式**：存在/不存在、唯一、有界、幂等、失败时 X 而不是 Y。避免"处理好""注意"这类不可判定表述。
- 每条尽量绑定证据获取方式：grep 什么符号、看哪张表、跑哪个测试。
- 引用真实路径与真实不变量（来自设计文档或历史缺陷），不确定的写"以 <文档> 为准"。

## 5. 版本与变更记录

- 域文档头部维护：`最近更新: <日期> (R<N>)`。
- 所有增删改在 `CHANGELOG.md` 追加一行：`- <日期> <R轮或事件> <域/文件> <一句话变更>`。
