## 二、核实为健康的面

- **firePersistedHooks 抽取是逐字搬运，原调用点行为不变**：`client.go:1017-1031` 与旧 persistRequestLog 内联块（diff 前 client.go:1024-1036）完全一致——lifecycleMu.RLock 快照、逐 hook 闭包 recover、同一 slog.Warn 文案（"telemetry onPersisted panic"）；persistRequestLog 内调用点仍在 `RecordSuccessfulResponseBodyMissing` 与 `releaseBodies` 之前（`client.go:1054-1066`），顺序未变。
- **panic 隔离与原路径一致**：ReplayFallback 与 persistRequestLog 走同一函数（`client.go:646` / `1055`），hook panic 只 Warn 不冒泡、不影响回放返回值。
- **"置位成功 ⇒ 必有一次 entry 流过 hook"的代码级不变量成立**：`claimSessionFinalSuccess` 仅有两个调用点 `client.go:1679`（insertRequestLog）与 `client.go:2284`（updateRequestLog）；这两个函数的顶层调用方只有 persistRequestLog（触发 hooks，含 lite sink 分支 `client.go:1045-1055`）与 ReplayFallback（现也触发）。updateRequestLog 的 RowsAffected==0 回落 insertRequestLog（`client.go:2236`）发生在外层调用内，hooks 只在外层触发一次，无双发。`CorrectEstimatedUsage`（`client.go:1819-1837`）只 UPDATE usage 字段+usage_source，不触 is_final_success——R44 对台账"后台 job"猜测的证伪属实。
- **"turns 按 request_id 幂等"的假设有真实且跨月完整的落点**：`domains/session/v2/turn_writer.go:373-380` INSERT 带 `WHERE NOT EXISTS (tenant_id, request_id)` 反连接 + `ON CONFLICT (tenant_id, request_id, partition_date) DO NOTHING`；反连接视图 `session_turns_with_current_month`（`sql/migrations/startup/526_session_turns_hot.sql:296-334`）= hot（未归档）UNION ALL **全部 attached 分区**（注释明言 "all attached partitions"，名字有误导性但覆盖面跨月完整）；冲突后重读真实 turn_no（`turn_writer.go:414-428`），不会追加重复 turn。E6"补发非双计"对 mirror 消费者成立——即使发生发现 #1 的双回放。
- **失败不补发、不丢登记**：ReplayFallback 仅 `err==nil` 补发；ring buffer `Replay` 对失败 record requeue 而非丢弃（`domains/dbdegradation/ring_buffer.go:240-251`），下次重放成功才补发——无漏发窗口。
- **degraded 路径无双发**：persistRequestLog degraded 分支（`client.go:1035-1040`）直写 fallback 即返回，不触发 hooks；hooks 只在回放侧补发一次。
