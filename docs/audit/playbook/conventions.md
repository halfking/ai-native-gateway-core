# 审计通用纪律（所有代理必读）

> 任何域子代理与主代理在动手前必须遵守本文件。域文档只写"查什么"，本文件写"怎么查、怎么报、怎么修、怎么收尾"。

## 1. 审计窗口

- 默认窗口：`git log --since="48 hours ago"`（滚动 48h）；主代理可在派发时显式给定 SHA 区间（`BASE..HEAD`）。
- 窗口**必须**写进轮文档头部与每个子代理报告头部。
- 窗口内所有 commit 的 `--name-only` 并集是"改动面"；改动面之外的代码只在"横向不变量"（如分区不变量、RLS、时区钉扎）需要追溯调用链时才读。

## 2. 发现分级

| 级别 | 含义 | 判据示例 |
|---|---|---|
| P0 | 部署阻断 / 硬失败 | CI 必挂、启动崩溃、放量阻断（如 F1 终态回填缺失） |
| P1 | 功能正确性缺陷 | 数据丢失、RLS 绕过、契约破裂、闭环断裂、空壳成功响应 |
| P2 | 边界 / 一致性 / 并发缺陷 | 双实例重复计数、乒乓配置、阈值分叉、TTL 缺失 |
| P3 | 顺带清账 | 死代码、注释漂移、文案、低风险债、UI 未复用套件 |

## 3. 证据纪律

- 每条发现必须给出 **`file:line` + 一句触发路径叙述**（谁在什么输入下走到这里、错误后果是什么）。
- **子代理报告一律视为线索而非事实**：主代理必须亲读对应代码复核后才允许登记为发现、动手修正。子代理的"说法"（包括它转述的文档内容）可能过时或张冠李戴（历史教训：R30 中子代理"上海日历"说法经核实不成立）。
- "核实为健康的关键面"也要留档（轮文档固定章节），避免下轮重复怀疑。

## 4. 输出格式（域子代理统一）

每域报告按以下结构输出 markdown：

```
# DXX <域名> 子代理报告（窗口：<BASE..HEAD 或 since>）
## 一、发现（候选，待主代理复核）
| # | 级别候选 | 发现 | 证据 file:line | 建议处置 |
## 二、核实为健康的面
- <不变量/链路> —— 证据
## 三、未覆盖项与原因
- <清单条目> —— <为什么没查成：超出窗口/需要真机/需要凭据>
```

## 5. 修复与验证门

- 顺序：P0 → P1 → P2 → P3；每修一条配**钉桩回归测试**（防复发）。
- 三门全绿才算修完：
  ```
  go build ./...
  go vet <改动包...>
  go test <改动包...> -count=1     # 涉并发的包加 -race
  ```
- 涉及 DB 迁移的修复：新增迁移前 `git fetch` 核对远端编号（当前已至 719），走 revision-sequence 登记通道。
- **迁移三纪律**（R37/R38 教训入册，2026-09-17）：
  1. **新迁移必须至少在一个存量真库实跑后再定稿**（717 登记时未实跑，真库首跑连崩三缺陷；R38 的 719 落账后另做复活扫描）。
  2. **追加进迁移文件的每一行都要重新过创建者核查**（718 B2 追加 parent_ts drop 未查 ensure 创建者，drop 被复活且扰动 ATTACH 拓扑）。
  3. **对并行轮"覆盖面"的断言必须以 origin/main 代码为准，不得以字面量 grep 计数代替亲读**（checker 误判即例）；同理，对活库状态的断言必须以真库查询为准，不得沿用上一轮文档记载（R38 修正 R37 的 FORCE 表计数即例）。

## 6. 上下文预算（goal 模式 / 500K 纪律）

- 主会话上下文接近 **500K** 时：先用 **handoff 技能**生成续跑提示词（含：当前窗口、已完成域、未完成域、已登记发现清单、BASE SHA）→ `/new` 清空上下文 → 用生成的提示词开新会话继续。
- 子代理派发数量据此节制：单轮并发 ≤8 路；每路提示词保持极短（内容在文档中）。
- 长会话续写前**先 `git diff HEAD` 核对工作树实际状态，勿凭记忆重写权威文件**（历史教训：凭记忆重写 worker 导致返工）。

## 7. Git 纪律

- 提交前：`git fetch` + 重新 `git status`——并行会话共享工作树，可能拾取你的未提交改动先行提交；**绝不丢他人 WIP**。
- 逐文件 `git add`（不用 `git add -A`）；`menu-config.json` 是生成物，冲突时取远程。
- 本仓 main 惯例 **merge 而非 rebase**。
- 收尾必须：审计 → 提交 → 推 main。

## 9. 新增静态守卫的准入清单（2026-10-01 入册）

> 依据：R85 期间 `web/src/config/navCoverage.test.ts` 的判据改了**四版**才收敛，
> 变异验证累计 7 次「未按预期红」且**每次根因都不同**。
> **一半的教训是「门本身写错了」，而不是「被测代码写错了」** —— 故立此清单。

写任何新的静态守卫/回归测试前，逐条过下面四组。**任何一条缺失，门都可能在真实回归面前是绿的。**

### 9.1 白名单三件套（豁免型守卫必备）

| 条 | 要求 | 首次逼出它的失败 |
|---|---|---|
| **条目有效** | 白名单项若已不再违规（或已不存在），必须转红 | `partguard` R78：代码已改而登记未跟，下一个人会误以为该文件已合规 |
| **理由具体** | 每条理由有实质长度下限，禁「同上」「已知问题」式占位 | `metricguard` R77：白名单一度写成「未接采集点」——那是**未核实的假设** |
| **与实测集合同源** | 白名单必须与**本次实测出的违规集合**双向比对（多出即红、失效即红） | `navCoverage` R85：判据被整体绕过时，静态白名单会全体失效而门仍绿 |

> `internal/partguard` 的做法更强：除路径键外**逐条钉住条数**（`n != w` 即红），
> 于是「某文件违规从 1 处变 2 处」即使还在白名单也会被抓。新写豁免型守卫建议照此办理。

### 9.2 判据钉语义量，不钉代理量

- 「表里没有某列」「0 行」「取值分布不同」**都不能**直接推语义结论。
- 典型翻车：`attachments` 表没有 `version` 列 ⇒ 误判「版本管理缺失」；真实实现是**内容寻址**（同 key 命中即跳过写，物理上不可能同 key 异内容），且 playbook 已明文接受该设计。
- 典型翻车：`health_status` 与 `availability_state` 取值 81/86 不同 ⇒ 误判「二者语义分属不同子系统」；真实情况是它们是**同一道门控的两个合取项**（`v_routable_credential_models.sql:17` 是单一 AND）。
- **自检问法**：「如果这个 bug 的表现是『数值不变但构成变了』，我的门会红吗？」不会 ⇒ 门是装饰。

### 9.3 防「判据自证漏洞」

判据不得允许**被测对象给自己作证**。
实例：`navCoverage` v1 用「该路径字面量是否出现在任意视图的导航上下文里」判可达，
而 `UserProfileListView.vue` 内的 `router.push('/admin/session-analytics/users/${owner}')`
让列表页的**子树给自己背书** ⇒ 删掉真正的菜单入口时门依然全绿。
修法：判定某对象时**排除它自己那个文件里的证据**。

**解析类判据的两个常见漏洞**：
- 归一化必须**两侧都做**（只归一被测侧 `:owner` 而放过引用侧 `${owner}`，模板字面量永远匹配不上）；
- 剥离必须**query 与 fragment 都剥**（`:to="\`/x#\${id}\`"` 是常见写法）；
- 分级匹配要**取最长前缀**，否则短前缀（`/routing-v2`）会抢先命中 `/routing-v2/credentials`。

### 9.4 判据自身不腐化 + 变异验证

- **下界断言**：扫描器「恒返回空」等于没有守卫。`metricguard` 用 `len(decls) < 100` 即红；
  新守卫必须给出同类的**量级下界**，或用 `t.TempDir()` 合成夹具自测（读磁盘的守卫**不受 `go test -overlay` 影响**，overlay 只影响编译）。
- **变异验证是硬要求**：改坏 → 必须红 → `cmp` 逐字节还原 → 复跑必须绿。
- **变异后仍绿/未按预期红时，固定按此顺序排查**（本项目 7 次的根因分布）：
  1. **变异生效了吗**——先 `grep` 确认改动真的写进去了（3 次是变异没生效，含 1 次编译失败）；
  2. **搜对范围了吗**（2 次是搜错范围拿到假 0 命中）；
  3. **门量的是语义还是代理量**（1 次）；
  4. **判据有无自证漏洞**（1 次，环形 vouch）。

- **变异验证必须带反向对照**：除了「改坏要红」，还要有一条「**改的东西不该影响时不得变红**」
  （R88：删掉 workflow 里提到 `make guards` 的注释、但保留完好的 `run:` 步骤 ⇒ 必须仍绿）。
  没有反向对照时，一个「凡是有注释就红」或「凡是有这个字串就绿」的判据都能通过全部正向变异。

> **不要为了「让门红」而削弱判据**，也不要把判据的错误结论当门有判别力。
> 两次「门绿」的正解都是先修判据/定位成因，再重新验证。

### 9.5 未修缺陷的钉法

- **红门不能进主干**：未修的缺陷用「断言**当前缺陷行为** + `FIXME` 标注」钉住，
  使将来修它或改坏它都必须**显式发生**（见 `deploy/sql/verify/routing_gate_warning_pg_test.go`）。
- 断言若**只在「数据恰好包含该类」时才生效**，在数据不含该类时看起来在守着、实际一行都没守
  ⇒ 必须补**数据无关**的合成版本。
- 真库门的环境变量名必须符合仓内契约（`TEST_PG_DSN` 等），否则 harness 永不注入、
  门在 CI 上**结构性沉睡**却照样显示 `ok`。**改门不改 harness。**

### 9.6 守卫的「执行路径」本身也要有门（R88 入册）

> 依据：`audit-guards-ci.yml` 的守卫步骤**硬编码了 7 个包**，而 `Makefile` 的
> `GUARD_PACKAGES` 早已是 10 个 ⇒ `metricguard`/`partguard`/`routeguard` 从未在那个
> 专用 job 里跑过；而文件里那句「guards-sync 已校验二者一致」是**假的**，
> `guards-sync.sh` 从不读任何 CI 文件。详见 72 号报告。

- **判据不得锚在「文件里出现过某字符串」，要锚在真正执行的那条命令。**
  反例（变异验证抓出，读代码发现不了）：判据 `grep 'make guards' .github/workflows/`，
  而同一文件里有一行注释「直接调 `make guards`」⇒ 把 `run:` 换成 `echo noop` 后
  **注释本身满足了判据**，门绿着而专用门已经没了。正确形态：
  `^[[:space:]]*run:[[:space:]]*make[[:space:]]+guards[[:space:]]*$`，并让所有
  文件扫描判据**排除注释行**（`^[^#]*`）。
- **规则只写在两处就一定会漂移**，且漂移无声。**单一事实源**（CI 调 `make guards`）
  优于**同步两份清单**——同步需要人记得，而人不会。
- **报「某门在 CI 上没跑」之前，先排除更宽的执行路径**：`go test ./...` 型全量单测门、
  pre-push、其他 workflow。本例三个守卫其实经 `make test-short` 跑到了，
  正确定级是 P3 而不是 P0。**先问「它真的没跑吗」，再问「它跑在哪」。**
- **守卫的准入检查要双向**：磁盘 `*guard` 目录 → 登记表，**且** 登记表 → 磁盘存在性。
  单向时自述会失真（本例曾打印「全部 7 个已登记」而登记表有 10 项，
  因 `errdiscard`/`dbrows`/`jsoncol` 不以 `guard` 结尾而落在正向视野外）。


## 10. 定点核实纪律（2026-10-01 入册）

> 依据：本会话因「先写结论、后找依据」而由**我自己**出错 **6 次**
> （R83b 语义推断、61 号未核实即建议、62 号转述未复核、63 号 §1.3 写了不存在的
> 字段、63 号 §2 把后台作业当运维接口、62 号建议 1 未意识到改变对外行为）。

**对任何「建议在 X 处加/改 Y」的修复意见，落笔前必须完成三项核实，缺一不得写入方案文档：**

1. **读包围函数** —— 该行属于哪个函数、这个函数的契约是什么（定时作业 / 请求处理器 / 迁移）；
2. **查调用方** —— 谁调用它、参数从哪来、**是人工触发还是自动触发**；
3. **读 SQL 的 `WHERE`**（若是 SQL）—— **它是否已经自带前置条件**。

**为什么第 3 条必须单列**：一段「无条件 UPDATE」看起来缺前置条件，但若它是带自守卫
`WHERE` 的幂等批量作业，那么「缺前置条件」本身就是**误读**——给它补前置条件等于给
正确设计加无用复杂度。（真实例：`bg/credential_recovery.go:748` 的
`health_status_reset`，其 `WHERE` 已含「陈旧 >2 分钟」这一设计意图。）

**为什么不能只靠子代理的结论**：子代理说「那段是无条件 UPDATE」**可能是对的**
（本次就是对的）——**错的往往是我对它的用途推断**。整合阶段**必须回到原代码**
读包围函数与调用方，不能只转述子代理的措辞。

**与 §9 的关系**：§9 管「门本身写得对不对」，§10 管「结论本身站不站得住」。
**先过 §10 再写 §9 的门** —— 门写对了，被测对象的判断错了，门一样是错的。

### 10.1 量化结论必须自己数一遍（R88-d 入册）

> 依据：本条**由我自己违反**。R85 域 B 审计里子代理报了「`domains/attachments`
> 有 18 个非测试文件、0 个 `_test.go`」，我把它**原样抄进 playbook D16 回注**
> （`d1da463c4`）而没自己数。R88-d 实测：非测试 **23** 个（且 `2a594fea6` 时也是
> 23 ⇒ 与本轮无关，是当时的计数错误）；`_test.go` **13 个**，其中 12 个早在
> 2026-07~08 就存在。**两条都错，且「0 个 `_test.go`」是危险方向**——它会让
> 后来者以为本域无测试而跳过一个实际有 13 个测试文件的域。

- §10 的三项核实针对的是**定性判断**（用途、触发方式、前置条件）。
  **量化/覆盖类结论是另一类**，规则更简单也更强：
- **凡是把「N 个文件 / N 处 / N 行 / 0 个」写进长期文档，一律自己重新数一遍**，
  不采信子代理、不采信自己几小时前的记忆。数法要**能复现**：
  `find … -name '*.go' ! -name '*_test.go' | wc -l` 而不是 `ls | grep | wc -l`
  （前者递归、后者只看顶层）。
- **计数要带基线**：只说「现在 23 个」没有说服力，要说「`2a594fea6` 时也是 23」，
  才能区分「我数错了」与「期间变了」。
- **指代必须无歧义**。原句「D16 目录亦 0 个 `_test.go`」里的「D16 目录」
  可以指代码目录、也可以指 playbook 文档目录，两者结论相反。
  文档里出现目录名时**要写全路径**——歧义本身就是缺陷，
  它让错误读法看起来和正确读法一样有道理。

### 10.2 判定「某结构是否存在」：先读产出它的函数体，再决定用什么去搜（R88-n 入册）

> 依据：objective 要求核实 `SanitizedMessageRefs` / `AlignmentMap` 接入 V2 metadata。
> 我先搜 `SanitizedMessageRefs` → 全仓 **1 个文件**（且只在一个**注释**里）；
> 再搜 snake_case 的 `sanitized_message_refs` → **0 命中**。
> **两个信号叠加，差一步就报「该字段从未实现」**——而实际上它完全实现了。

真读函数体才发现，**注释里的名字是概念名，代码里的标识是另一套**：

| 注释（概念名） | 代码（真实标识） |
|---|---|
| `SanitizedMessageRefs` | `compression.SanitizeInfo.MessageRefs` / JSON 键 `sanitize_message_refs` |
| `AlignmentMap` | `compression.AlignmentMap` / JSON 键 `alignment_map` |

- **这是「假 0 命中」家族的第 10 次，且是新变种**：前 9 次是搜错范围 / 模式写错 /
  截断导致假干净；**这一次是「拿注释里的字面量去搜代码」**。
  注释用自然语言描述概念，代码用另一套标识，**两者不必同名**。
- **判据**：判定「某字段/结构/能力是否存在」时，
  **顺序是「先定位产出它的那段函数体 → 读出真实标识符 → 再去搜」**。
  只凭注释里的字面量去搜，**搜到的是文档作者的记忆，不是代码**。
- **低命中数是危险信号而非「已证伪」**：`grep` 只命中 1 处时，
  **第一反应应是「我搜的名字对吗」**，而不是「只存在于注释里，所以没实现」。
  正确反应是**打开那 1 处、读它周围的函数体**——本例正是这么救回来的。
- 同理适用于**文档里出现的类型名/字段名**：它们是**指代**，不是**定义**。


### §11.1 配置类工具：「没报错」不等于「配置生效」（R88-s）

**规则**：用工具的**配置**（而不是**输出**）去改变它的行为时，
**「配置被接受、无报错」不能作为「配置生效」的证据**。
必须用**输出是否改变**来判定。

**证据**：`golangci-lint` v2.13.2 **静默接受 `settings.<linter>` 下的未知键**——
本例想用 `settings.bodyclose.skip` 豁免本仓标准 helper，于是做了**反向对照**：

| 配置 | 是否报配置错 | 告警是否消失 |
|---|---|---|
| `bodyclose: { skip: ["ReadPrefixAndDrain"] }` | **否** | **否**（仍 1 issues） |
| `bodyclose: { totally_bogus_key_xyz: 1 }` | **否** | — |

（第 2 行是**反向对照**：连一个纯粹胡编的键名都不报错，
说明第 1 行「不报错」**不能**推出「`skip` 被识别」。）

⇒ `settings` 下的**拼错的键**是静默的。
**没有反向对照就会把「没有配置错误」读成「我的豁免写对了」**——
那正是「配置看着生效、实际没生效」这一整类静默失效。

**怎么用**：
- 改工具配置后，**必须跑一次并比对输出**，而不是只看退出码或 stderr。
- 拿一个**故意写错的同类配置**做反向对照，确认该工具在这一层**是否会报错**。
- 这条推广到任何「配置文件驱动的门」：`.golangci.yml`、`Makefile` 变量、
  workflow 矩阵——**先确认它对拼写错误是否敏感**。

### §11.2 选型成熟工具：量「触达面」与「误报面」，不要量「覆盖类别」（R88-s）

**规则**：判断一个现成工具该不该接进本仓，看**两个数**：
① **触达面**——它在本仓**真正能看见**多少条目标缺陷的路径；
② **误报面**——本仓的**标准写法**会不会被它判成缺陷。
**不要看它「是否覆盖该缺陷类别」**——那是工具的营销口径，不是它在本仓的净收益。

**证据（R88-s，HTTP 响应体泄漏门）**：`bodyclose` 正是「覆盖该类别」的成熟工具，
本仓也已具备接入条件（`golangci-lint` 已在 CI 跑 ratchet 模式）。实测两个数都是负的：

| 维度 | 实测 |
|---|---|
| 信号量 | 全仓 3 条，**逐条读包围函数后 3/3 误报**，真信号 0 |
| 误报面 | 命中的第 1 条**正是本仓标准写法**（`httputil.ReadPrefixAndDrain`，生产 12 处） |
| 触达面 | 主出口是**三层自定义包装**（`doCompactionHTTP` → `doCompactionUpstream` → 消费者），**跨函数，工具看不见** |

⇒ 净形态是「**主路径没覆盖、标准写法却报**」。这是**负收益**门：
在 ratchet 模式下它会给每个按标准写法新增的出口出假新发现，
训练开发者用**无差别的 `//nolint`** 绕过——而 `//nolint` 注释一旦写下
就与该行长期共存，将来 helper 换实现、注释仍在，**门静默失效且无任何信号**。

**为什么值得单列**：这里的失败形态是**绿**。「工具是成熟的」「类别它覆盖」
「本仓也已有工具链」三条都成立，于是启用看起来零风险；
**只有把「它在本仓能看见什么」实际数一遍**才会发现净收益为负。

**怎么用**：
- 接一个新 linter/守卫前，先做**全量跑 + 逐条读包围函数**，
  **不逐条读就下结论等于把工具的输出当证据**。
- 数「本仓标准写法的调用点有多少处」——这个数就是未来的误报面。
- 找「本仓的主路径是否走了自定义包装」——如果是，工具多半在盲区。
- 唯一的负向结论也要**回灌到配置文件**（本例在 `.golangci.yml` 写入原因注释），
  否则下一个人会把同一轮调查重跑一遍。

### §12 调用图工具的「死代码」判定在本仓不可信（R88-v）

**规则**：**不要**用 `codegraph` 的 `roles --role dead*` 或 `where ... No uses found`
判断「该函数无人调用 / 是死代码」。本仓（Go，跨包 + 结构体字段接收者）里这些判定
**系统性假阴性**。

**证据（三条，可复现）**：
1. `codegraph where "Manager.Allow"` → `[dead-ffi] No uses found`，
   实际有 2 处跨包调用（`domains/streaming/executors/context_summarize.go:463`、
   `executor_dispatch.go:810`）；
2. **规律是「只解析同文件内的调用边」**——`Manager.GetOrCreate` 的 4 个 use
   **全部在 `breaker.go` 内**（兄弟方法互调），而跨包字段接收者
   （`e.Circuit.Allow(...)`，`Circuit *credential.Manager` 是**具体类型不是接口**）
   一条都没进图；
3. `codegraph stats` 自报 **caller coverage 37.2%**、`entry` 角色**只有 4 个**，
   而那 4 个是 **JS 脚本里的 console 输出**（`deploy/*.mjs`、`docs/**/mockup.js`）
   ——真实 HTTP 路由注册 **598 处**（`grep -rE '\.(HandleFunc|Handle|GET|POST|...)'`），
   **一个都没被认成 entry**。

**怎么用**：
- **可用**：模块地图、耦合热点（fan-in/fan-out）、复杂度、community 划分——
  这些是**文件/导入级**，不受调用边缺失影响；
- **不可用**：调用级可达性。**照着 `dead-ffi` 删代码会直接删掉热路径在用的对外 API**；
- **判据**：任何「无人调用 / 是死代码」的结论，**必须换一个触达面不同的方法独立复核**
  （本例用 grep 对照，并配了「同文件内 use 能被正确识别」的反向对照，
  才定位出规律而不是把它当成抽样运气）。

**与 §11.2 的关系**：codegraph 在「覆盖类别」上远不输 bodyclose，
但**触达面在本仓的关键问题上等于 0** —— §11.2 只要求量这两个数，
**本条补的是「量出来之后还要验证那个数不是工具自身的缺陷」**。
**方向备注**：本条与「恒真的门」「门全绿≠门覆盖我」同族但**方向相反**——
那三类是**门看起来在守、实际不守**，本条是**工具报告「这里是死的」、实际是活的**。
共同点：**输出都很干净很有说服力，唯一能识破的手段是换触达面 + 反向对照。**

## §14 「这里缺 X」之前，先问「仓里有没有已经实现好的 X」（R89-f 入册）

**规则**：审计中每遇到一处「这里缺某能力」，**先全仓搜该能力是否已存在**。
存在 ⇒ 这是**接线遗漏**（低成本可修，且说明设计已想清楚，优先级应抬高）；
不存在 ⇒ 才是**能力缺失**（要设计、要排期）。

**证据（4 例，全在本仓）**：

| 能力 | 已有实现 | 未接的路径 |
|---|---|---|
| 每帧写看门狗 30s + goroutine 配额 | `connection_registry.go:61-62,77` | **数据面**（94 号 §1，P1） |
| 写 deadline | `admin/live_stream_sse.go:2017` 5s | **数据面** |
| `ForceAttemptHTTP2` | `safehttpclient.go:89`=true / `proxy/transport.go:109`=false | **`upstream/client.go`**（94 号 §3） |
| handler 级查询超时 | `logs.go:470`、`analytics.go` | **17 个 admin 文件**（94 号 §8） |

**为什么这条值钱**：接线遗漏的修法是「把已有的一行接过去」，
而能力缺失要进设计评审。**两者的工作量差一个数量级，但审计报告里如果都写成
「缺少 X」，下游会按最贵的那条估工。**

**同族**：R88 的「写门前先查是否已有门」——那条查的是**测试资产**，
这条查的是**运行时代码资产**。合起来是一句话：
**先确认「有没有」，再决定「要不要造」。**

## §15 锁序/死锁结论必须切成两半判定（R89-k 入册）

**规则**：拿到一条「ABBA 锁序反转 ⇒ 死锁」的静态告警，**不许直接定 P1**，
也不许直接排除。必须分别回答两个问题，各给一份独立证据：

| 半 | 问题 | 证据形态 |
|---|---|---|
| **构造半** | 锁序反转**在代码上真实存在**吗？ | **用生产函数本体**构造确定性交错，跑出真死锁 |
| **可达半** | 其**前置条件在生产中成立**吗？ | **穷举全部调用点**（不是抽样）证明前置不成立 |

**证据（R89-k，`domains/dispatch`）**：路径 A `enqueueModelLane`
（`pipeline.go:1490` `journeyMu` → `:1492` `mq.mu`）与路径 B
`enqueueModelFromTotalLane`（`:1311` `mq.mu` → `:1336` `emitObservation`
内部取 `journeyMu`，`journey.go:36`）顺序相反。
**构造半**：同一 `qr` 双向入道 ⇒ 两条路径双双卡死满 3s（真实死锁）。
**可达半**：穷举发现两条路径的调用方落在 qr 生命周期的**三个互不重叠的所有权阶段**
（`drainTotalOne` 首次入道 / `onScheduledDue` 二次入道 / `dispatcher.go:277` 回退重入道），
qr 全程单所有权移动 ⇒ **不可达**，P1 降 P2（latent）。

**子规则 15.1 —— per-resource 互斥量之间的 ABBA，成环需要「同一个资源对象」**：
本例 `journeyMu` 是 per-request（`queued_request.go:194`）、`mq.mu` 是 per-lane
（`snapshot.go:13`）。**两个不同 qr 持不同的锁，不会互相阻塞。**
所以「两条路径锁序相反」只说明**必要条件具备**，不说明**会死锁**。
判据：先把每个互斥量的**粒度**（per-request / per-lane / per-key）标出来，
再问「两条路径能不能拿到同一个资源对象」。

### §15.2 异步实验的假阴性陷阱（本轮真踩了一次）

**规则**：构造交错实验时，**「启动 goroutine 后立刻读标志位」会把
「实验根本没跑起来」读成「假设不成立」**。
本轮 M1 首次运行输出 `deadlocked=false` 且耗时 **0.00s** —— 0.00s 本身就是
「gate 从未触发」的信号，若不察觉就会把 **harness 的 bug** 写成
**「锁序反转不存在」**，结论完全相反。

**怎么用**：
- 读异步实验的结果时，**先看耗时**。远短于设定的等待窗口 ⇒ 实验没生效，不是假设为假。
- 注入点/gate 之后**必须显式等待**（轮询 + 超时），超时要与「假设为假」**分别上报**，
  不要合并成一个 bool。
- **反向对照是唯一能区分「harness 坏了」和「假设为假」的手段**：
  本轮 M2（两个不同 `qr`）0.31s 双双返回，既证明 gate 与超时判定有效，
  又反证「同 qr」是必要条件。若 M2 也失败，说明是 harness 的问题。

**同族**：§9.4（变异必须带反向对照）、[[工具输出很有说服力的错值]]。
共同形态：**失败时的输出依然干净、像结论、且不会自己报警**。
区别：那一类是**值算错**，这一类是**实验压根没运行**。

## §16 「grep 引用数」这个指标本身有毒 —— 必须用**外部引用数**（R89-q 入册）

**规则**：报告死代码/零调用点时，**「grep 命中数」不能直接当热度指标**。
必须区分**自引用**（定义文件内部的注释、类型名、构造函数的返回值、方法名）
与**外部引用**（别的文件真的调用它）。
**判定零调用只看外部引用数，且必须把两个数都写进报告。**

**证据（我自己踩到，2026-10-01）**：
复核基线时 grep `DecryptCache`（排除 vendor 与 `_test.go`）得到 **10 处命中**。
朴素读法「引用 10 次，肯定不是死代码」——**完全错误**。
逐条打开后发现 **10 处全在 `domains/credential/decrypt_cache.go` 内部**
（`:8`/`:25` 注释、`:14` 类型、`:28` 构造函数、`:32` 自己的
`return &DecryptCache{...}`、以及自己的 5 个方法 `:41/:72/:80/:96/:103`）
⇒ **外部引用 = 0**，确系死代码。
同轮 `RegisterModelStatusRoutes` 得 2 处命中 = `admin/model_status.go:321` 注释 + `:322` 定义本身
⇒ 外部引用 = 0，路由从未挂载。

**为什么这条值钱（危害不对称）**：
- **假阴性方向**（把死代码判成活的）会漏报，
- **假阳性方向**（把活代码判成死的）会**建议删除一段正在跑的生产代码**。
两个方向都危险，但**后者代价大得多**——
本会话已多次出现「文档说它弃用、实际承载 204 条日请求」那类教训。
**所以宁可多花两分钟打开每一处命中，也不要相信计数。**

**为什么计数会骗人（机制）**：
一个死文件可以轻松凑出十几处**自引用**（类型+构造+方法+注释），
比一个**只被调用 1 次**的活函数「命中数」还高。
**跨条目比较热度时一律用外部引用数，计数只在同定义文件内横向比较才有意义。**

**怎么落地**：报告每行的「零调用证据」栏固定写两个数
（`命中总数` / `外部引用数`，并注明排除了哪些文件）；
报告开头给**外部引用 = 0 的候选总数**，而不是「grep 0 命中的个数」。
**已把这条作为硬性规则补给正在跑的子代理**（见 105 号的子代理任务轨迹）。

**同族**：[[「弃用/遗留」≠「没人用」]]（那是标签骗人）、[[判定「不存在」前至少两种检索]]。
**这一条是「计数本身骗人」**，前两条是「标签/单点检索骗人」。

## §17 「只 grep 类型名」看不见构造函数接线 ⇒ 活端点会被判成死的（R89-r 入册）

**规则**：判定「某类型/构造器无人使用」时，**禁止只用类型名 grep**。
必须先问：**它是不是被某个 `New…` 构造出来、而构造结果从未具名？**

**Go 的典型接线形态**：
```go
h := admin.NewXxxHandler(pool)   // 返回值类型从头到尾没被具名
h.RegisterRoutes(mux)
```
⇒ `grep "XxxHandler"` 在外部文件里**必然 0 命中**，**哪怕它被调用了一万次**。

**证据（R89-r，2026-10-01）**：子代理报「9 棵 admin 路由树已实现但从未挂载，
其中 3 棵前端正在调用 ⇒ **线上 404，最高优先接线**」。
**9/9 全部证伪**——实际挂载点：
`main.go:6576` `selfCheckHandler.RegisterRoutes(mux, adminMw, superAdminMw)`、
`main.go:6790-6791` `journalSnapshotAPI.RegisterRoutes(...)`、
`main.go:6496-6498` `healthCheckHandler.RegisterRoutes(mux)`（还带 `slog.Info` 日志行）。
构造函数外部引用实测 **5 / 6 / 1**，全部非零。

**它自己的证据就自相矛盾**：它写「`admin.Handler` 结构体不存在 `selfCheck` 字段，
从类型层面佐证未接线」——**这恰恰说明它只查了 `admin` 包内的 hub，没查 `main.go`**。
**这些 handler 本来就不需要有 `admin.Handler` 字段，它们在 `main.go` 里就地构造并注册。**

**同族（方向相同，危害不同）**：
| 陷阱 | 表现 | 后果 |
|---|---|---|
| **§16 自引用** | 死文件 grep 出 10 处命中 | 把死的看成活的（漏报） |
| **§17 构造函数不可见** | 活端点类型名 grep 0 命中 | **把活的看成死的 → 建议「接线」/「删除」已在生产运行的代码** |

**§17 危害大得多，因为它���建议方向是「修改」。**

**怎么落地**：
- 查「某 handler / 类型是否接线」，**先 grep 构造函数名 `NewXxx`**，再看装配函数体
  （`admin/handler.go:RegisterRoutes` **和** `cmd/gateway/main.go` **两处都要看**）。
- **只数某个 hub 里的调用点会系统性误判**——凡是在 `main.go` 里就地注册的，
  一个都不会出现在 hub 的计数里。
- **判定「未接线」时，凡结论会导致「建议接线/建议删除」的，必须读到装配函数体原文**，
  不能只靠检索计数。本轮若不做复核，就会同时产生
  「去接线已接好的端点」和「已登记的 P1（待裁决 39）其实是空穴来风」两个错误。

**同族**：§16、§10.2（先定位函数体再决定搜什么名字）、
[[「弃用/遗留的东西」≠「没人用的东西」]]。
**§10.2 说「先找到函数体再决定搜什么名字」，§17 补上了一个具体的名字陷阱：
有时候该搜的不是类型名而是构造函数名。**

## §18 实测拿到否定结论时，从「成因链」继续走，不要在原问题上打转

**规则**：当一个「A 会不会导致 B」的问题被实测**否定**之后，
不要把结论改个说法交差，也不要就地结束。
要问的是：**「让这个否定答案成立的那条机制是什么？它还带来别的什么后果？」**

**证据（2026-10-01 R89-w，llm-gateway-go，110 号）**：
问「sanitize 规则热更后旧的已脱敏缓存产物会不会被误复用、导致新规则命中的明文外泄」。
109 号凭键结构推断「会」（`LastOutboundHash` 是自洽哈希，结构上不可能发现
「产生这些字节的脱敏器已不是当前那个」），准备按泄漏方向定级。
**实测：不外泄。** 但随后又连错两次——
① 改口成「`outbound_body` 会因 PII 丢失」：**只读到代码的一半**，
  漏了 `handler.go:4183-4186` 在 `CommitFinal` 成功分支里用 `bodyBytes` 覆盖；
② 改口成「每轮重算全量比对 ⇒ 长会话 O(n) 劣化」：**根本没测就估了方向**，
  实测 120 消息历史 PII 臂 543µs vs 无 PII 臂 805µs（**0.68x，反而更快**——
  锚点第一条就失配立刻返回，而无 PII 臂要走完 120 条比对）。

**正确走法**：否定答案把矛头指向了「占位符序号跨轮递增」这条机制
（`sanitizer.go:141-162` 的 `typeIndex` + 会话级 offset），
因为它让 `diff.go:210` 的逐字节 delta 锚点**每轮都失配** ⇒ 整轮重新脱敏 ⇒ 不外泄。
顺着同一条链立刻找到真实代价：
**`IsNewSess=true` 让三处 `else if` 分支跳过 ⇒ `compression_strategy` 对含 PII 的会话恒为空**
⇒ 该列在两类会话上装的不是同一种事实 ⇒ 压缩看板系统性排除全部 PII 会话且无痕迹。

**更重要的是这条链的形状**：让「不外泄」成立的机制，
**一旦被优化掉，安全属性就静默消失**。若有人把 delta 锚点改成忽略序号 / 按语义匹配，
缓存复用立刻恢复成「按旧规则脱敏的字节继续外发」，且无任何告警。
⇒ 这类保证必须从「确认它成立」升级为「**做成显式契约**」（如在 SessionState 落规则集指纹，
与 `LastOutboundHash` 并列参与复用判定）。

**判据**：
- **实测得到的否定结论，价值在于它锁死了哪条机制链。找不到这条链，说明测的是个孤立现象。**
- 拿到否定结论后，**第一件要做的事是回头检查自己此前基于「会」写下的每一条推论**
  ——它们的前提已经被推翻了，不能只推翻结论、留着推论。
- 「性能劣化」「数据丢失」这类**代价型断言，必须实测**；
  它们和原问题一样容易被键结构带偏（本轮两次都错，且第二次错在方向上）。

**与既有条目的关系**：§15.2 讲「异步实验的 0.00s 耗时是实验没跑起来」，
§18 讲「实验真跑了、结论为负之后该往哪走」——**两者合起来才是一条完整的方法**。

## §19 名字长得像表的东西不一定是表：下「写入缺口」结论前先 `pg_get_viewdef`

**规则**：任何「A 表比 B 表多/少 N 行 ⇒ 某条写入路径漏了/重了」的结论，
**先确认这两个名字解析成什么**。PostgreSQL 里 `xxx_with_current_month` 这类名字
几乎都是**视图**，且很可能是多表 `UNION ALL` + `LEFT JOIN` 的**统一读视图**，
行数差来自**口径**而不是**写入**。

**证据（我自己当场推翻的一次结论，2026-10-01 R89-x，111 号）**：
`request_logs_with_current_month` = 2,324,470 行，
`usage_ledger_with_current_month` = 2,067,960 行，**差 256,510**，
且 09-03~09-11 有整天完全不交集（09-07 单日 70,757 行只在宽表侧）。
我据此写下「**账本漏写 25 万行**」。

`select pg_get_viewdef('request_logs_with_current_month'::regclass, true)` 的结果是：

```
session_turns_hot  LEFT JOIN session_turn_details_hot
UNION ALL  session_turns LEFT JOIN session_turn_details
UNION ALL  request_logs_..._without_request_class_due_at
              LEFT JOIN LATERAL (request_class FROM request_logs_hot/request_logs)
WHERE NOT EXISTS(…session_turns_hot…) AND NOT EXISTS(…session_turns…)
```

**它根本不读 `request_logs_hot` 主体**——它是「request_logs → session_turns 迁移」的
**统一读视图**（session 族 ∪ legacy 族，带跨族去重）。
⇒ **那个差值是视图口径差，不是写入缺口。结论作废。**

**怎么落地**：
- 判定「某表漏写」之前，一条命令：
  `select pg_get_viewdef('<name>'::regclass, true);`
  看它 `FROM` 的到底是**物理表**还是**别的表/视图**，有没有 `UNION ALL` / `LEFT JOIN` / `WHERE`。
- **LEFT JOIN 会吞行**：`d` 侧无匹配的请求在并集里直接消失 ⇒ 行数天然不等，
  且**与写入是否成功无关**。
- **统一读视图的命名会误导**：名字里的 `request_logs` 指的是**逻辑实体**，
  不是物理表。看到 `xxx_with_current_month` 先当视图处理。

**为什么这条特别容易踩**：objective 本身要求「把 `request_logs` 切到 `session_turns`」，
所以这一族**按设计就是多表并集的视图**。**越是本项目重点改造的表族，
越要先看视图定义再谈行数。**

**同族**：§10（读 SQL WHERE）、§10.1（量化结论自己数一遍，数不可信就不引用）。
**§10.1 说「自己数一遍」，§19 补上「数出来的那个东西要先确认它是什么」。**

## §20 共享 SQL 片段 helper 会让「grep 列名判断隔离」彻底失效

**规则**：判断某个读端点/函数**有没有做租户隔离**时，
**禁止**用「函数体里是否出现 `tenant_id` / `org_id` / `user_id`」这类字面量筛查。
先问：**这个项目的隔离是不是由共享 helper 以 SQL 片段形式注入的？**
如果是，字面量筛查**必然产出假阴性**，且假阴性会伪装成「一批真缺陷」。

**证据（我自己证伪自己的检测手段，2026-10-01 R89-y，112 号）**：
我枚举 `admin/handler.go:898` 的 `RegisterRoutes`（**105 个 `admin(...)` + 57 个 `superAdmin(...)`**），
对 154 个 `admin(...)` 端点取 handler 函数体，筛出 36 个直接读
`request_logs|usage_ledger|session_turns` 的，再按「有无 `tenant_id`」标注
⇒ **8 个候选「无租户过滤」**，看起来是一份很有说服力的缺陷清单。

**读原文后至少 3 个是假阳性**：

| 候选 | 证伪依据 |
|---|---|
| `handleCompressionStats` | `admin/compression_stats.go` **有 3 处** `tenantLogsClause(` / `IsTenantAdmin(` 调用；`admin/compression_sessions.go:3-6` 甚至在文件头写明这条契约 |
| `handleRoutingRecentModelFailures` | 读 `node_probe_runs` / `passive_probe_state`——**节点级表不是租户级表**，「无 tenant_id」是设计正确 |
| `handleStats` | 实际在 `*RouteIncidentsHandler` / `*WorkTypeHandlers` 上，不是 `*Handler`；**「按函数名索引」把不同接收者混并了** |

根因（`admin/session_tenant.go:12-16` 自陈）：`tenantLogsClause` 返回的是
**SQL AND-fragment**（`" AND tenant_id = $N"`），**拼进 WHERE 字符串**，
所以 handler 函数体里**永远看不到该列名**。

**怎么落地**：
- 判隔离前，先 `grep -rn "func.*Clause(r \*http.Request" ` 一类**返回 SQL 片段的 helper**，
  以及 `Is<Scope>Admin` / `Effective<Scope>ID` 这类**返回租户标识的 helper**。
  它们存在 ⇒ 字面量筛查作废。
- **按函数名建索引时必须带接收者**（`func (h *T) Name`），
  否则同名方法跨类型混并（本次就踩了）。
- **判「表是不是租户级」先看表本身**：节点级/全局级表（`node_probe_runs`）
  没有 `tenant_id` 是**正确的**，不是缺陷。
- **这类筛选的输出默认不采信**，除非逐个读原文坐实。
  本轮唯一坐实的真缺陷（`swim-lane-init`）是**独立读 SQL 原文**发现的，
  **不是那次筛选的战果**——这个区分必须写清楚，否则会把一次失效的方法
  包装成一次成功的审计。

**判据**：**筛查工具产出的「一批整齐的候选」越可信，越要先证伪工具本身。**
整齐来自工具的假设，不是来自代码的事实。

**同族**：§16（grep 引用数有毒）、§17（构造函数不可见）、§19（名字像表的不一定是表）。
**共同点：全都是「检索计数/字面量匹配」这一类便宜手段的失效形态，
而失效方向都是「把事实判错」而不是「查不到」。**

## §21 「无 guard」≠「没有闸门」：helper 名单本身也必须先枚举全

**规则**：用「函数体里是否出现闸门 helper 名」做隔离筛查时，
**闸门名单必须先从代码里枚举全**，不能只列自己记得的那几个。
否则筛出的「无 guard」**只是「我没听说过这个 helper」**。

**证据（2026-10-01 R89-z，113 号，接 §20）**：
§20 让我否定了「grep `tenant_id`」的筛查。R89-z 改用「函数体是否出现
`tenantLogsClause|IsTenantAdmin|EffectiveTenantID|requireSessionTaskAccess|assertTaskInTenant`」
这个**自造名单**重筛，36 个读租户表的 handler 里 9 个「无 guard」。
**读原文后 8 个是假阳性**：

| 候选 | 真实原因 |
|---|---|
| `handleDataLifecycleAttachments` 等 **5 个** | 用的是**第三种命名的闸门** `attachmentTenantScope`（`admin/data_lifecycle_attachments.go:78-83`），实现正确：tenant_admin → `GetTenantID(r)`（取自身份），super_admin + 显式参数 → 收窄，否则不过滤 |
| `handleRoutingRecentModelFailures` | 读节点级表 `node_probe_runs`/`passive_probe_state` |
| `handleStats`（`*RouteIncidentsHandler`） | **根本没有 SQL**，只读内存 store 计数器（`active`/`recovering`/`recovered_24h`） |
| `handleDataLifecycleMetrics` | 纯 `COUNT(*)` + `pg_total_relation_size` 聚合，无租户维度（仅全库行数/体积暴露，低危，登记不判缺陷） |

**⇒ 确认跨租户读的只有 1 个**（`HandleSwimLaneInit`，112 号已坐实）。
**筛选法连续两轮（§20、§21）都先证伪了自己**，但第二轮把 36 个收敛到了 **1 个真缺陷**——
**这正是「机械筛只能用来缩小范围，最后一个必须读原文」的证明**：
若停在「9 个候选」就发报告，会凭空造出 8 个缺陷。

**怎么落地**：
- 找闸门 helper 的正确顺序：**先 `grep -rn "AND tenant_id = \|AND .*_id = \$" --include=*.go`**
  （找所有**拼 SQL 片段**的地方），再回溯它们的函数名。
  **先找形态（返回 SQL 片段的 helper），再取名字**，而不是凭印象列名字。
- 同一个仓库里闸门**通常不止一个**（本仓至少 3 个命名：`tenantLogsClause` /
  `attachmentTenantScope` / 各文件自带的 scope builder），**命名不统一是常态**。
- 筛到「无 guard」后，**先问「这个表是租户级表吗」**（§20 已记），
  再问「这个函数真的有 SQL 吗」（本轮 `handleStats` 就没有）。

**同族**：§16（grep 引用数有毒）、§17、§19、§20。
**共同点升级**：前四条是「检索命中数被判错」，§21 是**「连检索词表本身都可能是错的」**——
**任何自造的名单（helper 名、类型名、列名）在使用前都要先证明它全**。

## §22 「零导入」是相对量：基准必须写明，否则同一包有三种身份

**规则**：判定「某包是死代码，因为它零导入」时，
**必须先声明基准是「仓库内所有 `package main` 的依赖图」**。
用 `./cmd/gateway`（主二进制）或 `./cmd/...`（按目录猜）都会得出**不同的、且部分错误的**结论。

**证据（连错两次，2026-10-01 R89-AA，114 号）**：

| 基准 | 零导入数 | 错在哪 |
|---|---|---|
| `./cmd/gateway` 依赖图 | 59 | **把运维工具包误判为死代码** |
| `./cmd/...` 全部 main 包 | 55 | 漏掉 `examples/`、`tests/` 下的 main 包 |
| **`go list -f '{{if eq .Name "main"}}…' ./...`（57 个 main 包）** | **45** | ✅ |

- **第一次错**抓到 `domains/ursm/v2/migration`（**3,778 行，最大的零导入包**）——
  它实际被 `cmd/k2-migrate-ursm/main.go` 与 `cmd/ursm-k2-preflight/main.go` 消费，
  是**运维迁移工具包**，按设计不进 server 二进制。
  **按「零导入 = 死代码」删掉，会删掉一整套 K2 迁移工具。**
- **第二次错**抓到 `domains/intentconfig`（1,824 行）——
  手工 grep 得到外部 import 方 2 个但仍在零导入名单里，
  因为那 2 个在 **`examples/intent_analysis_demo` 与 `tests`** 下：
  **是 main 包，但不在 `./cmd/` 目录里。**

**正确枚举**（不要按目录猜）：
```bash
go list -f '{{if eq .Name "main"}}{{.ImportPath}}{{end}}' ./... | grep -v '^$'
for m in <结果>; do go list -deps "$m"; done | grep '^<module>/' | sort -u
comm -13 reachable.txt allpkgs.txt        # 真·零导入
```

**怎么落地**：
- 引用任何「N 个零导入包」的数字，**必须同时给出基准**；
  没有基准的数字**不可复现、不可采信**（本仓已有一个：105 号的「31」）。
- 归类时先问三句：**① 有没有 main 包消费它？② 消费它的是 server 还是运维/示例工具？
  ③ 它的 README/注释是否明写「等集成者」？** 三句都答完再谈 A/B/C。
- 排除「非运行时」时也要写明排除项（CI guard / SQL 目录 / deploy 配置），
  否则数字无法被别人复算。

**同族**：§12（codegraph 死代码判定不可信）、§16（grep 引用数有毒）、
§17（构造函数不可见）、§20（共享 SQL 片段 helper）、§21（helper 名单本身可能不全）。
**这一族全是「便宜的死代码判定手段」的失效形态**：
§22 是其中最贵的一个失效——**它不是判错某一个包，而是让整份清单按错误的身份分类。**

## §23 判「某值从哪来」必须枚举赋值点，关键词缺失不等于能力缺失

**规则**：要回答「这个值是不是从上游响应里读出来的」，
**禁止只搜关键词**（`Retry-After` / `retry_after`）。必须**枚举该字段的每一个赋值点**
（`grep "<Field>:"` 或 `grep "\.<Field> = "`），逐个判定值的来源。

**证据（我自己先用了不合格的取证方式，2026-10-01 R89-AI，122 号）**：
问「现役是否尊重供应商返回的 `Retry-After`」。
- **第一遍（不合格）**：`grep "Retry-After"` 只看到 `Set("Retry-After", …)` 在给**自己的客户端**
  加响应头 ⇒ 得到「不解析」的印象。**这个取证方式有缺陷**：
  它没回答「`RetryAfter` 这个 Go 字段的值是谁填的」。
- **第二遍（正确）**：`grep "RetryAfter:"` 枚举出**全部 4 个赋值点**，
  逐个判定来源，全部是**网关自己的**（`cfg.HostedTasks.DispatchRetryAfterSeconds` 配置 /
  `QuotaError` 自己的租户配额 / `DefaultOverflowRetryAfter` 自己的队列溢出），
  **没有一个来自解析上游响应** ⇒ 结论成立，且精确得多。

**而且第二遍还多给出一条第一遍完全看不到的关键事实**：
**管道其实已经通了**——
`domains/credential/writer.go:167/357` 是
`coolingDuration(failure.Kind, failure.RetryAfter)`，
`:596` 的实现是「**`retryAfter > 0` 就优先用它（并有 `maxCoolingDuration` 上限），
否则按 kind 取默认**」；`domains/dispatch/planner.go:221` 有 `RetryAfter: out.RetryAfter`。
**⇒ 缺的只是最上游「从响应里读出来填进去」这一步。**
把结论从「缺一整套机制」修正成「**机制建好了，只差一个解析**」，
**修法成本与优先级完全不同**。

**怎么落地**：
- 问「这个字段/参数的值从哪来」⇒ **枚举赋值点**，
  每个赋值点标注「来源是上游响应 / 配置 / 自己的内部状态」。
- 只有当**所有赋值点**都枚举完、且都判定过，才能下「不读上游」的结论。
- **更重要的副产品**：枚举赋值点会顺带暴露**管道是否已存在**。
  「完全没有」与「管道全通只差入口」是两种完全不同的修法量级，
  而**只看关键词时这两种情况长得一模一样**。

**残留风险（如实登记）**：本轮只枚举了 `RetryAfter:` 的**字面赋值**。
若某处用 `resp.Header.Get("Retry-After")` 读出后**以别的变量名**传递，则抓不到。
**⇒ 下结论时必须写明这个边界，不得宣称「绝对没有」。**

**同族**：§16（grep 引用数有毒）、§20（共享片段 helper）、
§21（helper 名单可能不全）、**§19（名字像表的不一定是表）**。
**共同点：全都是「用一次检索就下结论」的错误形态，
而正确做法都是「再换一种检索把结论复核一遍」。**

## §24 代码推断与真库观测矛盾时：先假设自己漏了写方，再找一个能分辨的额外维度

**规则**：当「只读代码得出的结论」与「真库量出来的数字」冲突时，
**不要先去找一个说得通的巧合去解释观测**。顺序固定为三步：

1. **先假设自己漏了写方**，而不是先假设「代码对、数据旧」。
   用**第二、第三种检索形态**复核写方全集（`X:` / `.X = ` / 全仓 `X = |.X:`），
   并把「这条值有没有第二个来源」（包装类型、另一个包的同名结构）单独查一遍。
2. **找一个能区分两种解释的额外维度**：时间（按月/按日）、版本、租户、状态。
   判据是**两种解释在这个维度上的预测不同**：
   - 「我漏了写方」⇒ 新旧数据**都该有**该现象；
   - 「build 更替 / 状态迁移」⇒ 现象会在**某个边界处断裂**。
3. **要两个独立信号在同一点断裂**才敢定性。单一信号的断裂可能是巧合，
   两个语义不同的列在同一边界同步断裂，才是证据。

**证据（R89-AL / 125 号，2026-10-01）**：
只读代码的结论是「完整决策 trace 只在『候选耗尽且零次尝试』时落库，
成功请求恒无 `planned_candidates`」——听起来已经足够硬，可以直接发报告。
**真库一跑**：`rows_with_planned_cands = 27,229`，其中**成功行 9,736 条**，与推断直接矛盾。
若就此发报告，就是一条**方向相反**的结论。
按本条三步走完：三种检索形态确认 `ExecuteResult.Trace` 生产零赋值（唯一的 `Trace:`
字面量在 `executor.go:2577`，赋给 `ExecuteError`）⇒ 不是我漏了；
再按月拆分 ⇒ 9,736 **全部落在 2026-09**，2026-10（当前 build）成功行带候选池的**为 0**，
且 `candidates_tried` 在**同一边界**从 `8/16/14/15/13…` 断裂为**恒 1**
⇒ 两个独立信号同点断裂，才定为「回归」。

**为什么值得单列一条**：这个失效形态与 §20/§21/§22/§23 都不同。
前几条是「检索口径不对导致漏看」，本条是「**结论已经写完且自洽，才发现前提错了**」——
代码推理链完整、注释互相印证（其中一条还是错的）、读起来毫无破绽。
**注释的一致性不能替代真库的一致性**：本例 `routing_tracker.go:36` 写着
「候选池会被独立持久化到 `decision_trace`」，与 `auto_route.go:839` 的说法直接冲突，
**两句都是「读起来对」的话**，只有真库的按月断档能判哪句在一般路径上成立。

**怎么用**：
- 手里有「代码结论」又有「真库数字」且两者冲突时，**冲突本身就是本轮最有价值的信号**，
  值得单独花一轮查清，而不是取其一。
- 报「回归 / 数据被压平」前，**必须给出旧值的真实分布**（不只给新值），
  否则「一直是 1」与「从 N 变成 1」在报告里长得一样。

**同族**：§20/§21/§22/§23。
**共同点：全都是「同一次检索/同一次推理就下结论」的错误形态；
正确做法都是「再换一种方式把结论复核一遍」——
区别只在于这一次要复核的不是检索面，而是**推理链的前提**。**

## §25 「重构后某能力消失」固定三查：赋值语句的历史、被删代码旁的注释、守卫测试的处置

**触发场景**：发现某个字段/分支/能力「现在永远是空/零/不生效」，
且怀疑是某次重构造成的。**不要只报告现象，要给出是哪一次提交。**

**第 1 查 —— 定位增删该赋值的全部提交**（不是"最近改过这个文件的提交"）：

```bash
git log --oneline -S "<被删的赋值语句>" -- <file>
```

用**完整的赋值语句**而不是函数名/字段名做 `-S`。
本例 `-S "result.Trace = trace"` 全历史只有 **2 条**命中（加一条、删一条），干净可读；
若用函数名或字段名检索，返回的是一长串无关提交，**根本读不出这是一次「加了又删」**。

**第 2 查 —— 读被删代码周围的注释**。
注释里对**「谁来写」**的承诺，是判定「**漏搬**」与「**有意废弃**」的决定性证据。
本例删除前的注释写着
`// result.Trace (planned candidates) ... it lives on DecisionLogEntry, written separately by the sync phase`，
而删它的提交做的正是 retire 那个 **sync** loop ⇒ **它删掉的正是被注释承诺的写入方**
⇒ 漏搬。**没有这条注释就只能报「现状」，报不出成因性质。**

**第 3 查 —— 守卫测试在那个提交里被怎么处置了**：

```bash
git show <commit> --stat -- <被删代码所在目录>
git grep -n "<断言目标>" <commit>^ -- '<dir>/*_test.go'   # 提交前有没有守卫
git grep -n "<断言目标>" HEAD     -- '<dir>/*_test.go'   # 现在还有没有
```

**若守卫测试与被守卫行为在同一个提交被删除，该提交的一切测试通过记录都不构成证据。**
本例 `executor_glm_test.go`（76 行，含 `len(result.Trace.PlannedCandidates) != 3` 的精确断言）
被 `f7eb0eb1b` 整个删除，而该提交信息写「651 tests PASS」
⇒ **门是绿的，因为门本身没了。**

**为什么第 3 条对 AI 生成的重构提交尤其重要**：
一次提交同时删掉 4,000 行代码与其测试时，
**「651 tests PASS」是最容易被误读为安全的信号**——
读报告的人会默认"测试全绿说明删的是冗余代码"，
而真相是**门和被守卫对象一起没了**。

**与既有条目的区别**：
§24 是「结论与真库矛盾时怎么复核」；
本条是「**现象与代码矛盾时怎么定位到提交**」。
共同点是**都要落到一个可复核的具体坐标**（时间断点 / commit hash），
而不是停在「看起来像是……」。**「像是某次重构弄丢的」不是结论，`f7eb0eb1b` 才是。**

**同族**：§17（注释承诺的接线默认不成立）、§13（注释承诺默认不成立）、
§24（代码与真库矛盾）、以及「变异后仍绿」家族——
但本条比变异测试更极端：**变异测试能证明门曾有效；连门一起删，事后无法回溯。**

## §26 「某能力静默失效」的第 4 查：读 commit body 找作者的 PORT 清单

**背景**：§25 三查能把「现象」定位到具体 commit。**但定位到 commit 还不够——
你要回答的是「有意废弃」还是「漏搬」**，而这决定修法是「补回 5 行」还是「需要一整套补偿设计」。

**第 4 查 —— 读那个 commit 的完整 body，找作者自列的 PORT / 迁移清单。**

大规模重构提交（尤其「retire / delete N 行循环」这类）的 commit body 往往**自带一份
「原本会被静默丢弃、需要移植」的功能清单**。本例 `f7eb0eb1b` 的 body 原文：

> **PORT**: MM-1/MM-2 outbound attachment transforms into `forwardForDispatch` —
> **their only consumer was the retired loop**, so **the feature had been silently inert
> in production** since dispatch_v2 became the default path.

**这句话等于作者自己定义了失效模式**：「唯一消费者是被删代码 ⇒ 功能静默失效」。
有了这个定义，定性问题就从推测变成**是/否判断**：
被删能力**是否属于这一类**？**是否在清单上**？
本例两者都是「是 / 否」⇒ **漏项**，证据强度远高于「有意废弃」。

**配套纪律 —— 承诺与陈述要分开**：
若 commit body 引用了**决策记录文档**（本例 `AUDIT_24H_20260817.md §E`），
**必须核实该文件在不在仓库里**。本例 `git ls-files | grep -i AUDIT_24H_20260817` → 无匹配
⇒ **从仓库内既不能证实也不能证伪**它是否列过该能力，
**必须把这条写进诚实边界**，**不要用「作者说了什么」替代「作者承诺了什么」**。

**怎么用**：
- 判定「漏搬 vs 有意废弃」时，先问「**作者当时知不知道这个失效模式**」。
  知道（且为同类功能建了清单）⇒ 漏项；不知道 ⇒ 才需要考虑「有意但未记录」。
- 若找到 PORT 清单却发现**某同类能力不在清单上**，这就是一条**可执行的根因**，
  比「该字段当前为空」这种现象有价值一个数量级。

**同族**：§25（三查：赋值历史 / 被删代码旁的注释 / 守卫测试处置）、§13、§17、§24。
**共同点：全都是「别停在现象，去找一个可复核的坐标」——
§25 找 commit hash，§26 找 commit body 里的那份清单。**

### §25 补充：交给别人拍板之前，先自己跑一遍门

「只读代码 + git 历史」能证明**「这里曾经有、现在没了」**，
但**不能证明「补回去就对」**。一个补丁在拍板前必须自己验掉三个问题：

1. **会不会编译不过**（§9.4 第 1 步：失败必须是断言，不是编译失败）；
2. **会不会被相邻的错误路径绕过**（例：本条修法在 `derr == nil && res != nil` 时才写 trace，
   否则失败请求拿不到候选池——**这是设计取舍，必须明说而不是碰巧**）；
3. **会不会让既有测试变红**（整包跑，不是只跑自己那条）。

**为什么这一步不能省**：若这条缺陷的根因正是「一次重构删了 3,619 行、并让 651 个测试全绿」，
那么在评估它的修法时，**没有理由不先确认修法本身是绿的**。

**成本对比**：「提案」与「已验证的补丁」在决策成本上是两件不同的事——
前者需要用户自己判断风险，后者只需要用户判断**要不要**。

⚠️ **临时实证的失败要如实保留，不要只留最后一次**。
本条实际失败了三次（导入路径写错 → 候选被 `Routable:false` 过滤 → 才得到有效证据），
**如果只看最后一次，报告就写不出「夹具必须显式 `Routable: true`」这条**——
而那正是下一个要写同款实证测试的人会踩的坑。

## §27 「某段时间数据缺失」：先看逐日分布的**形状**，再谈成因

**规则**：拿到「这段时间少了 N 条」时，**先出逐日分布表，不要先给成因**。
分布的**形状**决定假设空间，比总量有用一个数量级。

| 形状 | 指向 |
|---|---|
| 单调渐变 | 滚动发布 / 灰度迁移 |
| **0% / 100% 整天跳变** | 开关、构建差异、实例集合变化 |
| **出现 1%~99% 的中间值** | **多节点 fleet 里部分实例行为不一致**（最有价值的一档） |
| 逐渐变小但不为 0 | 抽样 / 降级 / 背压 |

**证据（R89-AP / 129 号）**：总量 256,422 只能描述成「一大片缺失」；
逐日分布才暴露出 `0% → 74% → 93% → 0%（连续 5 天）→ 100% 并永久保持`
这个**先恢复、后又全丢、再永久恢复**的形状
⇒ 直接**证伪了「滚动发布新旧 build 并存」**（滚动发布给单调渐变），
并把假设空间收窄到「多节点 fleet 部分实例不含该写入路径」。

**配套纪律 —— 排除一个假设要拿代码说话**：
本轮排除了「有人关了 S4 停写开关 `storage.request_logs_write_enabled`」这个
**看起来最合理的解释**，依据是一行代码的位置：
台账 `INSERT` 在 `client.go:1283`，而 `logsWrite := requestLogsWriteEnabled()` 的首次使用在 `:1327`，
**晚 44 行 ⇒ 台账写入根本不在该开关的守卫内。**

⚠️ **「最合理的解释」恰恰是最该先验证的那个**——
它一旦被写进报告，读的人会直接采信，而**排除它的成本只有读几行代码**。

**同族**：§10.1（口径必须和数字一起发布）、
[[计数类结论：口径必须和数字一起发布]]、[[真库门 SKIP 了不要引用旧数字]]。
**共同点：全都是「数字本身干净，但口径/形状没被一起发布」——
而形状或口径一旦说清，假设空间会自己塌缩。**

## §28 「终态缺失」不能区分「从未写入」与「写入后被删除」

**规则**：看到某个东西「不在库里」时，**不要直接说「从未产生」**。
**终态缺失无法区分「从未写入」与「写入后被删」**——两者在数据库里长得一模一样，
而**性质完全不同**：一个是缺口，一个是数据被销毁。

**下结论前必须先查删除路径本身是否原子**：

| 写法 | 是否存在丢失路径 |
|---|---|
| 单条数据修改 CTE：`WITH batch AS (DELETE ... RETURNING ...), inserted AS (INSERT ... SELECT FROM moved)` | **无**。失败整体回滚，行留在源表 |
| 手写 `INSERT;` 换行 `DELETE;` 两条语句 | **有**。除非有显式错误处理兜住 |
| 先 `DELETE` 后 `INSERT` | **必然有** |

**证据（R89-AQ / 129 号自查更正）**：129 号曾从「hot 没有 + 月分区没有」直接推出
「这 25 万行从未写入」。**方法上不严密**——它是从终态反推历史。
本轮补了三项独立排除才敢定性：
① `promote_usage_ledger_hot_to_partition` 主体是**单条 CTE**（DELETE…RETURNING 喂给 INSERT）
⇒ 结构上无「删了没插」路径；
② **hot 无滞留老行**（`min(ts)` 距查询时刻仅 8.5 小时，符合 8 小时保留）
⇒ promote 未停摆，若停摆则 9 月老行仍会留在 hot 里等着；
③ **绕过视图直查分区的逐日 `COUNT(*)`** 与视图口径逐日一致 ⇒ 空洞确实在分区内部。

⚠️ **顺带一条容易踩的**：`promote_credit_ledger_default_batch` 是**手写两条语句**，
带 `RAISE WARNING '... INSERT failed (%), rows preserved in _default'`。
**同一套 promote 体系里两种写法并存**——查一个表的 promote 安全性，
**不能推广到同一体系的其他表**。

## §28 附则：`reltuples` 不能支撑「某分区是空的」

`pg_class.reltuples` 是**规划器估算值**。本文件实测：分区内 `reltuples` 之和
2,065,828 vs 父表 `COUNT(*)` 2,065,722，**差 106 行**；
且它把一个**实际有 2 行**的分区报成 **0**。

⇒ **凡涉及「某处为空 / 某物不存在」的断言，一律用 `COUNT(*)`。**
这是 §「计数类结论：口径必须和数字一起发布」的数据库版——
**估算值可以用于排序和粗略比例，不能用于存在性断言。**

**同族**：§27（数据缺失先看形状）、§10.1、§24、§25。
**共同点：全都是「数字/结论看起来干净，但它的**来源与精度**没被一起说清」——
本条是最危险的一种：它会直接产出「不存在」这种**不可逆的强断言**。**

## §29 「历史数据异常」不能用**今天**的代码解释——要回到当时的提交去看

**规则**：要排除一个**历史**假设时，问的问题是「**当时那段代码长什么样**」，
**不是**「现在这段代码长什么样」。

**为什么**：今天的代码可能已经修过、已经加过门、已经换过写法。
用今天的代码去排除九月的现象，**排除的可能是「后来的那个问题」，不是「当时的那个问题」**。

**最短取证路径**：

```bash
# 1) 找到窗口起点附近、且当时实际在跑的提交
git log --format="%h %ad %s" --date=short -- <相关文件> | head

# 2) 读那个版本里「当时是否已有该判据」
git show <commit>:<文件路径> | grep -n "<当时的判据>"
```

**证据（R89-AR / 130 号）**：129 号用**当前代码**排除了 S4 停写开关
（`logsWrite := requestLogsWriteEnabled()` 首次使用比台账 INSERT 晚 44 行，
所以台账写入不在该开关守卫内）。
**方法隐患正是用 2026-10 的代码解释 2026-09 的行为。**
本轮回到 `a15df5cc6`(08-15) 与 `507410f19`(08-27) 才发现
**该文件当时根本没有 `logsWrite` 这个符号**
⇒ 排除结论**不仅成立，而且更强**：从「今天不守」升级为「**当时也守不了**」。

## §29 附则：提交**日期**也是排除依据

本轮最强候选是 `rate_multiplier`——它同时满足两个特征：
① 「代码引用了新增列」；② 「Citus 分布式 DDL 渐进下发能产生 74%/93% 这类中间值」。
**是提交日期把它排除的**：`39b8efbe0`（2026-09-22）里**代码与迁移
`736_maas_rate_multiplier.sql` 同进同出**，不存在「代码先于迁移」的窗口；
且 09-22 **晚于**缺口窗口（09-03~09-12）。

⇒ **只查代码不看日期，会把一条红鲱鱼写成成因。**
候选越像，越要先对日期。

**同族**：§25（三查）、§26（commit body 的 PORT 清单）、§28（终态缺失的歧义）、§24。
**共同点：全都是「**拿到的证据与要回答的时间点不在同一时刻**」——
§29 是**时间维度**的版本，前几条是**检索形态与推理前提**维度的版本。**

## §30 「不可达」类结论有**两条腿**，证伪它必须同时推翻两条

**规则**：读到「零可达路径 / 永不可达 / 死代码 / 从未执行」这类结论时，
**先问「它有几条腿」——把每条腿单独列出来，逐条查完再下判断。**

典型的两条腿：

| 腿 | 形态 |
|---|---|
| 腿 A | **点存在**（代码在那里，账本/对象/handler 已装配） |
| 腿 B | **点走不到**（守卫恒假 / 分支不可达 / 构造点全部不可达） |

**只推翻一条就宣布推翻整个结论 ⇒ 得到的是方向相反的结论。**

**证据（R89-AT / 132 号，本轮我自己犯的）**：
本轮去证伪待裁决 38「`paramledger` 非流式还原点**零可达路径**」。
第一步查到：`restoreClientEcho` **唯一调用点存在**、位于活路径 `executeOpenAI`、
由 dispatch 唯一路径驱动、账本在 `main.go` 确实被注入。
**我当场读成「38 号被推翻」——完全读反了。**
93 号的原话是「**无任何可达路径**」，**不是「无调用点」**；
**调用点存在恰恰是 93 号描述的一部分**（「还原点在那儿，但走不到」）。
真正没查的是**腿 B**：`if !params.SuppressSuccessWrite && params.W != nil` 的守卫，
而 `responses.go` 同一字面量里 `IsStream: isStream` 与 `SuppressSuccessWrite: !isStream`
**逻辑互补** ⇒ native 非流式时守卫**恒假** ⇒ 93 号完全正确。

⚠️ **若不查腿 B 就发报告，会产出一条「P1 被推翻」的错误结论**——
而那条 P1 是**本会话唯一做过变异验证的**（红绿对照 + `cmp` 逐字节还原）。
**「我推翻了它」和「我验证了它的一条腿」是两件事，而人极易把前者当成后者。**

**同族**：§24（代码 vs 真库矛盾，先假设自己漏了写方）、
§25（守卫测试与被守卫行为同批被删 ⇒ 测试通过记录不构成证据）。
**本条是它们的第三种形态**：前两条是「结论的前提错了」，本条是「**只验了一条腿就宣布结论**」。

**怎么用**：
- 复核任何「不可达」结论时，把「它凭什么这么说」逐句拆成可独立验证的断言；
- **每条断言都独立取证，不要因为其中一条成立就顺势宣布整体成立/不成立**；
- 尤其当结论是**别人（子代理/更早的轮次）给的**时，
  **最危险的不是它错，而是它对得太整齐、让你以为不用再查剩下的腿。**

## §34 「X 表都应该具备 Y 属性」这类需求描述，必须**逐表实测**，不能采信描述

**规则**：需求文档、注释、架构图里写的整齐描述（「所有 X 表都是 Y」），
**其整齐程度通常高于实际状态**——**因为描述写的是意图，不是现状**。
核对时必须逐表实测属性，而不是读一眼描述就采信。

### 落地纪律三条

**① 逐表实测，别采信描述。**
本轮实测（`pg_class.relam` → `pg_am`）推翻了「所有大数据表都是 hot+columnar 分区」：
**hot 侧 100% 是 heap（且这是对的——columnar 不支持行级 UPDATE/DELETE，
而需求同时要求「更新、删除只能在 hot 表中进行」），
分区侧只有 8/22 个 `ensure_*_partition` 会建出 columnar。**

**② 把「未声明 / 靠默认」单列一档，不要并进「设计为 X」。**

| 档 | 本轮数量 | 含义 |
|---|---|---|
| 显式声明 columnar | 7 | 设计选择 |
| 显式声明 heap | 2 | 设计选择（且有注释说明理由） |
| **完全未声明（靠数据库默认）** | **13** | **设计缺失** |

⚠️ **「靠默认」不是一种设计选择，它是「设计缺失」的一种伪装。**
把它算进「设计为 heap」会**掩盖真正的风险**：
**换库 / 换 PG 版本 / 换 Citus 配置，都可能让这 13 个函数静默翻转访问方法。**

**③ 报告要给出「混用的具体后果」，而不只列一张状态表。**
本轮若只列状态表，读者得到的是「有的 columnar 有的 heap」——**没有行动价值**。
真正的后果是：**`usage_ledger_2026_08`=columnar(0 行) vs `_2026_09`=heap(2.07M 行)**
⇒ **任何跨月查询都会同时扫两种访问方法**，而 columnar 不支持点查与索引下推
⇒ **月度边界处查询计划出现断崖，且随时间推移只会累积更多混合分区。**

⇒ **顺带一条定位方法**：核对「是否都具备属性 Y」时，
除了数「是」，还要同时找**状态不一致的相邻样本**（同表不同分区/不同环境），
**不一致的样本往往比一致的样本更能说明问题**。

**同族**：§22（零导入是相对量，基准必须写明）、§31（先数再定性）、
§28（终态缺失的歧义）。
**共同点：全都是「**需求/注释里的整齐描述，比实际状态整齐**」——
而整齐的描述最容易被直接采信，直到有人去逐个数。**

## §35 核对「保留/积压/超期」时，**阈值必须来自该对象自己的配置**，不能套用全局默认

**规则**：任何「超期 / 积压 / 残留」类数字，报出去之前先问两句：
① **「这个阈值是谁定的」**——是全局默认，还是**该对象自己的配置**？
② **「该对象的保留机制本身是不是还开着」**——若它已被显式关闭，**那条全局规则对它根本不适用**。

⇒ **数字越刺眼，越要先确认量它的尺子是不是这一把表的尺子。**

### 两个形态（R89-BA / 139 号，本轮我自己都踩了）

**形态 A：套用全局阈值去量一张用自己阈值的表**
全局 `lifecycle.hot_retention_hours = 8`，而 `model_probe_runs` 用的是
`lifecycle.model_probe_runs_ttl_days = 14`，**且它的 promote 已被显式关闭**
⇒ 用 8h 量它：**99.5% 看起来超期，实际 0% 超期**。
⚠️ **「超期比例 99.5%」在报告里极有说服力，而它完全无害。**

**形态 B：grep 命中了「解释为什么被移除」的那段注释**
`awk '/func promoteSpecs/,/^}/' | grep -c model_probe` → **3**
⇒ 我据此写下「`promoteSpecs()` 里确实有 `model_probe_runs`」，
**而那 3 处全在注释里，spec 是被注释掉的**。
更糟的是我接着差点把三处**一致的正确注释**（`:84`、`:1382`、settings「除 model_probe_runs_hot」）
当成「过期描述」——**它们全都对**。
⇒ **grep 命中注释 ≠ 代码存在。**
这与 §13（注释承诺的接线默认不成立）互为镜像：
**注释承诺的不算，注释宣告的移除也不算——都得看真实代码。**

**证据（139 号）**：同一轮里两个错都指向同一个动作——
**看到「刺眼的数字」或「整齐的命中」就下结论**。
若不是继续读原文（spec 注释块）与继续查配置（TTL setting），
会发出两条**方向完全相反**的假 P1。

**同族**：§27（数据缺失先看形状）、§32（盲区是否引入新实体）、§33（先证明后果再量化规模）、
§28（终态缺失的歧义 / `reltuples` 不可支撑存在性断言）。
**共同点：全都是「**数字本身干净，但尺子/前提可能不是这一把**」。**

## §35 增补（140 号）：**阈值有三个来源，以「生效值」为准** —— 代码默认值 ≠ 注释里的值 ≠ 线上值

**§35 原文**：「核对保留/积压/超期时，阈值必须来自该对象自己的配置，不能套用全局默认。」
**本轮补上第三层** —— 「阈值是谁定的」其实有**三个候选来源**，必须查到底：

| 层 | 来源 | 本例的值 | 性质 |
|---|---|---|---|
| ① | **代码默认值**（`resolvePromoteConfig` 的 fallback 实参） | **24h** | 配置存在时**永不生效** |
| ② | **注释/文档里写的值** | **24h** | 描述的是**当初的意图**，未必是现状 |
| ③ | **配置项的当前生效值**（`settings_kv`） | **8h** | **只有这一层是真相** |

### 证据（140 号）：三方一致地骗人

`request_logs_bodies_hot` 最老行 **9.07h**，越过理论上限 9.0h ⇒ 我判为**疑似泄漏**。
追查四跳，**前三跳全部指向 24h**：

1. SQL 函数 `promote_request_logs_bodies_hot_to_partition(p_retention interval DEFAULT '24:00:00')`
   用 `ts < now() - p_retention` 做截止 ⇒ 阈值是参数，不是写死；
2. Go 调用点 `bg/partition_manager.go:1503` `SELECT fn($1::interval, $2::int)`，
   实参来自 `resolvePromoteConfig(s.label)`；
3. `bg/partition_manager.go:1719-1727` `case "request_logs_bodies":`
   读 `lifecycle.request_logs_bodies_retention_hours`，**默认 24**，
   注释写明「默认降到 24h，运维可通过该 key 覆盖」；
4. **第 4 跳才是真凶**：`settings_kv` 里该 key = **8**（scope=platform）
   ⇒ **9.07h 完全正常，promote 健康。**

⚠️ **在读到 `settings_kv` 之前，「泄漏」这个判断是站得住的** ——
代码、SQL、注释三方一致地说 24h。**若不做第 4 跳，就会发出 139 号之后连续第二条假 P1。**

⇒ **纪律**：**任何从代码推出的配置值，在用它做判定前必须回读一次生效值。**
**这一步成本是一条 SQL，省掉它就是一条方向相反的报告。**
**代码与注释一致 ≠ 配置生效。**

### 附带发现（本轮唯一真问题，P3）

**2026-07-13 那次「bodies 容量决策（3.4GB 膨胀 ⇒ 默认降到 24h）」在生产上从未生效**（线上是 8h）。
该覆盖是**代码明示支持**的（注释第 4 句就写了「运维可以覆盖」）⇒ **不是 bug**；
但 **读代码的人会以为 hot 里有 24h 取证缓冲，实际只有 8h** ——
一次「超过 8 小时就查不到 body」的排障困惑会被误归因到「promote 坏了」。

### 同族与推广

**同族**：§27 / §28 / §32 / §33 / §34 / §35 —— **全都是「数字本身干净，但尺子/前提可能不是这一把」。**

**推广到零行表（本轮另一条）**：7 张 `_hot` 表在本实例 hot 与父表**同为 0 行**，
promote 函数 7/7 存在、非测试 Go 写方命中 6–26 个文件
⇒ **0 行是「本实例没触发」的事实，不是接线缺陷**；
但也**绝不能写成「7 张表已验证健康」** ——
**零行时任何保留期口径都返回「无超期」，这不是证据。**
⇒ **自动化巡检必须对零行表单独标注 `no-data` 而不是 `pass`**，
否则就是「0 行等于合规」—— 本会话已发现的**第 6 处「未定义编码进 0/NULL」同族问题**。

## §36 聚合类数字必须先问「**NULL 行去哪了**」—— 三值逻辑会整块吃掉数据且不报错

**规则**：任何 `WHERE` 条件里出现 `col = 'x'` / `col <> 'x'` 且 `col` **可空**时，
**一个占大头的 NULL 群体可以在你眼皮底下整块消失，而输出仍然是一个干净、自洽、可信的整数。**

### 证据（141 号 / R89-BC，本轮**我自己连踩两次，方向相反**）

**坑 1 —— `<>` 吃掉 NULL**：
算「排除 probe 后」的量时用了 `resolution_path <> 'resolve_probe'`。
`NULL <> 'x'` → `NULL` → 不满足 `WHERE` ⇒
**本库 30 天 932,706 行里有 579,028 行（62%!）`resolution_path IS NULL`，被整块丢掉。**
⇒ 我一度算出「**63.4% 的请求是诊断探针**」——
**这个数字是假的，真实 probe 占比 1.28%，量级错 50 倍。**
⚠️ **若直接发出，会是一条量级完全错误的 P1。**

**坑 2 —— 改对了却在别处再踩一次**：
换成 `IS DISTINCT FROM` 之后，我在 CTE 里写 `NOT is_probe OR is_probe` 想表示「全部」，
**但 `is_probe` 对 NULL 行本身是 NULL** ⇒ `NULL OR NULL` = NULL ⇒ **又被过滤掉同一批 579,028 行**。
⇒ `requests` 一度显示 353,678，真值 **932,706**。

### 落地纪律

1. **排除某类行一律用 `IS DISTINCT FROM` / `IS NOT DISTINCT FROM`，不用 `<>` / `=`。**
2. **报「占比」之前，先单独打一次 `count(*) FILTER (WHERE col IS NULL)`。**
   **NULL 占比大到能改变结论时（≥1% 就该警惕），两种口径的差值必须写进报告。**
3. **自查问句**：「我这个过滤条件，会不会是靠 NULL 的三值逻辑在悄悄筛掉数据？」会 ⇒ 换写法。
4. **在 CTE / 派生列里做布尔运算时**，`NOT x OR x` **不是恒真**（x 为 NULL 时是 NULL）；
   要「全部」就**别加这个条件**。

### 与 §34 同族

**§34** 是「**属性**可能靠数据库默认」；
**本条** 是「**集合**可能靠三值逻辑少算」。
**共同点：都是「你以为你在量 A，其实你在量 A 减去某个隐式子集」**，
而**输出都是一个不会自己报警的干净数字**。

**同族**：§27 / §28 / §32 / §33 / §35 —— 「数字本身干净，但尺子/前提可能不是这一把」。

### §36 增补（142 号）：临时审计查询比生产代码更危险

**142 号把本条做成全仓机械扫描（321 处 SQL 比较站点 × `information_schema.is_nullable` 交叉核对），
结果：生产代码零缺陷；而 141 号我自己临时敲的两条查询，两次都没带守卫。**

| | 本仓生产代码 | 审计者临时查询 |
|---|---|---|
| 可空列上的 `<>` | **几乎 100% 带 `IS NOT NULL AND`** | **两次都没带** |
| 后果 | 零缺陷 | 一度算出「63.4% 的流量是探针」，真值 1.28%，**错 50 倍** |

**⇒ 纪律升级**：
> **临时审计查询的 `WHERE` 条件，默认假设「可空」，直到核对过 `information_schema`。**
> 一条「跳过 NULL 行」的过滤，**在生产代码里通常有人替你补上守卫，
> 在你自己临时敲的 SQL 里则毫无保护** ——
> **而后者恰恰是要用来给生产代码定性的那一条。**

**配套**：
1. 报「占比」前先打一次 `count(*) FILTER (WHERE col IS NULL)`；
2. 排除类条件统一写 `IS DISTINCT FROM`（对 NULL 返回 TRUE，语义明确）；
3. **用可能含 NULL 的查询去给「NULL 相关缺陷」定性，是自指的** ——
   与 §32「统计必须用含 hot 的视图」、§24「先假设自己漏了写方」同族：
   **连测量工具本身都要先验证它没被待验证的问题污染。**

### §36 另一侧：约定存在但无门禁（142 号实证）

本仓事实上遵守「**对可空列做排除式比较必须写 `IS NOT NULL AND col <> 'x'`**」——
`client_model` 抽样 **14 处全部带守卫**。但这条约定
**不在任何文档里、不由任何测试强制** ⇒ 一次无关重构就可能悄悄去掉半句。
**建议加机械守卫测试**，但**必须是「报告而非 fail」**（行级启发式必然有假阳性）。

**同族**：§27 / §28 / §32 / §33 / §34 / §35。

## §37 「端点存在性」必须三维度核对，且必须先问「有没有人会碰到它」

**规则**：判断「前端调的端点后端有没有」时，**三个维度要同时过，缺一即错**：

1. **路径全等**（不是「这个名字在仓库里出现过」）
2. **方法匹配**（GET / POST / PUT / DELETE…）
3. **鉴权 wrapper**（注册时收了几个 wrapper）

### 证据（143 号，94 号 P3 的重新定性）

94 号记「前端调 3 个不存在端点」，本轮逐项核对：

| 前端调用 | 后端实况 | 94 号判定 | 实际 |
|---|---|---|---|
| `GET /api/admin/dashboard/session-recent` | `.go` 零命中 | 不存在 | ✅ 对 |
| `GET /api/admin/dashboard/session-anomalies` | `.go` 零命中 | 不存在 | ✅ 对 |
| `POST /api/admin/dashboard/session-export` | **`main.go:6887` 注册 `GET /api/admin/session-export`（带 `wrapAdmin`）** | 不存在 | ❌ **错：存在，但路径多一层 `/dashboard`、方法也不同** |

⚠️ **「新增端点」与「改一个字符串常量」的修法成本差一个数量级** ——
**只查①会同时产生假阳性（本例）与假阴性（能力在别名下）两类错误。**

### 第四维（两条前序记录都漏了，且它决定定级）

> **④ 「这个坏掉的东西，有没有人会碰到它」必须在定性之前回答。**

**不是问「有没有新实体」，而是问「有没有人会撞上它」。**

§31（可能是一类问题要真去数）、§32 / §35 / §36。

## §38 「时区正确」不是「函数里写了 `SET LOCAL TIME ZONE`」，而是「时区不依赖任何人的环境配置」

**要问三个问题**（缺一不可）：

1. **函数里设了没有？** —— **看覆盖率，不看有没有**
   （证据 144 号：本仓 20 个 promote 函数里**只有 11 个**设了 `SET LOCAL TIME ZONE`）。
2. **没设的那些，函数体里到底有没有时间敏感运算？** ——
   `date_trunc('month', …)`（timestamptz 版用会话时区）、
   `timestamp`（无时区）× `timestamptz` 的隐式 cast。
3. **上层有没有兜底？** —— 证据：**本仓 Go 侧 `SET TIME ZONE` / `TimeZone=` 零命中**
   ⇒ **会话时区完全由容器决定，没有任何一层代码把它钉住**
   ⇒ **一次无害的容器加固（`docker-compose.yml` 加 `TZ=UTC`）就会静默改变 9 张表的语义。**

### 机制可合成证明，不必等表里有数据

```sql
SET TIME ZONE 'Asia/Shanghai';
SELECT (TIMESTAMP '2026-10-01 02:00:00' < now() - interval '8 hours');  -- TRUE
SET TIME ZONE 'UTC';
SELECT (TIMESTAMP '2026-10-01 02:00:00' < now() - interval '8 hours');  -- FALSE
```
**同一个值，判定相反。** ⇒ 保留期确实随会话时区漂移。

⚠️ **「该表零行所以无法验证」不是不验证的理由** ——
与 §31 / §36 同源：**别让「没有数据」把「可以验证的东西」一并挡掉。**

### 潜伏风险必须两栏写

| 栏 | 本例 |
|---|---|
| 机制成立吗 | ✅ 成立（已合成证明） |
| 今天会发生吗 | ❌ 本机不发生（容器与 PG 均为 Asia/Shanghai，两层一致） |

**只报其中一栏就是误导。** 140 号「如实登记为待核实、不报缺陷」的处理是对的，
**本轮只是把它从「待核实」变成「已核实」**——**而不是反过来把它升级成缺陷。**

### 补齐硬化时逐个看函数体

本轮 9 个缺失函数里**只有 2 个真有暴露面**（`auto_route_selections` 做月分桶、
`handoff_logs` 做 timestamp×timestamptz 混比）⇒ **不能按名字批量补。**

**同族**：§27 / §28 / §32 / §33 / §34 / §35 / §36 / §37。

## §39 「一个检索形态对所有目标都返回 0」时，先怀疑形态，不要先下结论

**规则**：凡是产出「N 个目标**全部**零命中 / 零导入 / 零引用」这类**整齐结论**的扫描，
**先把路径口径打印出来核对一遍**，再相信那个 0。

### 证据（145 号）：错前缀让 18 个子包「全部零导入」

`go.mod` 第一行是 `module github.com/kaixuan/llm-gateway-go`。
用**漏了 `github.com/`** 的前缀去扫 `domains/hooks` 的 18 个子包 ⇒
**形态 1 对 18 个包一律返回 0**；
而形态 2（不锚定 module 前缀，只匹配 `hooks/<pkg>"`）给出了真实分布：

| 子包 | 真实生产引用文件数 | 若采信形态 1 会得到 |
|---|---|---|
| `audit` | **23**（`cmd/gateway/main.go` …） | 0 |
| `response` | **16**（`domains/streaming/handler.go` …） | 0 |
| `goal` | 7 | 0 |
| 其余 8 个（台账列为零导入的） | 1~4 | 0 |

⚠️ **若采信形态 1，就会把 11 个在生产主链路上跑着的包报成死代码。**

### 落地

## §40 判定「零引用 / 未使用」前先看目录构成；同一份工具输出只写一次解析

### 形态 A：**「零 import」可能正是守卫包该有的形态**

一个目录里同时有 `scan.go` 与 `guard_test.go`，而 `scan.go` 只被**同包的** `guard_test.go` 调用
⇒ **它不靠被 import 生效，它靠 `go test ./...` 直接执行**。

**证据（146 号）**：本轮我在这点上**错了三次**——
① 差点把 5 个自包含守卫（`metricguard`/`partguard`/`routeguard`/`sqlguard`/`sqlreadguard`，
合计 2,051 行）报成「守卫从未运行」；
② 差点把「仅测试引用」的守卫包报成未使用 ——
**`go list .Imports` 不含 `TestImports`**。

⇒ **判定未使用要同时看三层**：生产 import / `TestImports` / `XTestImports`，
**再看一眼目录里有没有 `*_test.go` 自测**。
（同 §22：零导入是设计约束不是事故。）

### 形态 B：同一份数据被三个坏解析读出三个矛盾结论

**同一份 `go list` 输出，本轮连写了三个解析变体**（分别按空格 / `|` 分隔、取不同字段），
得到 **37 个 / 1 个 / 277 个** 三个互相矛盾的清单。

⇒ **纪律**：
1. **先固定输入文件与分隔符，再写一次解析**，写完立刻用**一个已知答案的包**做 sanity check；
2. **`len .Imports` 是「我引入了谁」，不是「谁引入了我」** ——
   **方向搞反会得到一份「所有不依赖任何人的包」的荒谬清单**；
3. **一个分析结果若与同一份数据的另一次分析矛盾，先怀疑解析，不要先怀疑数据。**

### 与 §39 的关系

§39 是「**检索形态坏了却输出整齐结论**」；
本条是「**同一份数据被三个坏解析读出三个矛盾结论**」。
**共同点：都产出干净、自洽、可信的清单，而它们都是错的。**

**同族**：§22 / §31 / §35 / §36 / §37 / §39。

## §41 给「注释承诺的接线从未落地」定级前，先分清这条注释是「承诺它有」还是「声明它没有」

| | 承诺已接线 | 明确声明未接线 |
|---|---|---|
| 例 | `domains/hooks/promptoptimization`：「设 `PROMPT_OPTIMIZATION_ENABLED=1` 即可启用」（还给了环境变量表与触发条件） | `db/dbxmanifest`：「**No production data path routes through the framework yet**… legacy repositories stay authoritative」 |
| 实际 | 无人 import；环境变量包外 0 读取 | 确实无人 import，**与自述一致** |
| 定性 | **P2 缺陷**（文档与事实不符；面向使用者时影响更大） | **不是缺陷**（最多是「迁移待收口」的运维事实） |

> **判别式：区别不在「有没有接线」，而在「文档是否如实」。**

### 落地：判「零引用包」时，先把包注释读完并分三类

1. **承诺已接线** → 查成文手册在哪（有没有像 `docs/hooks/prompt-optimization.md` 那样的可操作文档）；
2. **明确声明未接线**（并点名继任者/权威方）→ **不是缺陷**；
3. **两者都没说** → **最危险的一种**：下游无法判断该信什么，**需要人工补文档**。

**只有 ① 才是缺陷，③ 需要人工补文档。**

### 为什么这条重要

本会话前几轮累计了多例「注释承诺的接线从未落地」（§13）。
若不写清对照，很容易滑成 **「零引用 + 有注释 = 缺陷」的机械判断** ——
**而 `db/dbxmanifest` 正是这一机械判断的反例。**

**同族**：§13 / §14 / §22 / §39 / §40。
**共同点：都在提醒「别把『看起来不对』直接读成『缺陷』」。**

## §42 守卫文档的最高形态：**主动论证自己会在什么条件下失效、失效方向是安全还是危险**

**证据（148 号）**：`internal/rowsguard` 用**精确到 `file:line`** 的豁免表
（第一眼看着很脆 —— 改一次行号就全失效），但注释把它显式转成了**安全方向的脆弱性**：

> 「注意 key 含行号：改动文件行号漂移会让豁免**失配**（而不是静默放过）
> —— 失配时报的是『该行未被豁免且缺守卫』，**方向是安全的**。
> 真正需要豁免的新站点会因行号变化而重新暴露出来，**这是刻意设计**。」

### 新增守卫的文档模板应包含三句

1. **本门守什么** —— 判据落在**产物特征**上，而不是「文件里出现过某个 helper 名」
   （后者在多站点文件里删掉其中一处不会变红；`rowsguard` 注释明写 R65 已实证该缺口）；
2. **豁免表的每一项为什么可以不看**（key 精确到 `file:line`，以便失配时重新暴露）；
3. **本门在什么条件下会失效、失效方向是安全还是危险。**

### 判别式（对 §41 的补充）

| 桶 | 形态 | 定性 |
|---|---|---|
| ① | **承诺已接线** | 缺陷 |
| ② | **明确声明未接线** | 不是缺陷 |
| ③ | 两者都没说 | 需补文档 |
| **④** | **主动论证自己会怎么坏** | **本仓文档的标杆形态，应被复制而不是被修** |

**同族**：§13 / §14 / §22 / §39 / §40 / §41。

本条更进一步：「看起来脆弱」的设计往往正是刻意设计的。**

## §43 把一个不可见维度接进 UI 之前，先查它在源表里的**取值分布是不是恒定的**

**「某维度在 A 表有、在 B 页面没有」有两种成因，处置相反**：

| | 成因 | 处置 |
|---|---|---|
| ① | **B 页面根本没做这个聚合** | 补 B |
| ② | **B 页面做了另一种聚合，而 A 表那个维度是「预留但从未启用」** | **补了也白补 —— 先补写入方** |

**证据（149 号）**：`provider_error_details.resolved` 有列、36,401 行**全部 `false`**、
前端 0 命中。**若只按「页面没展示 → 把表接上去」处置，接上去的是 36,401 行 `false` 的假信息。**

### 落地：接 UI 前先看值域

- **分布是常量**（全 true / 全 false / 全 0）⇒ **它其实没被启用**，**先补写入方**；
- **分布有变化** ⇒ 它真在用，接 UI 即可。

### 与 131 号同族、方向相反

- **131 号**：「未定义」不可编码进 0/NULL —— **该区分的没区分**；
- **本条**：**预留了区分位却永远不填**。
- **两者都要在「值域是否恒定」这一步先查一眼。**

**同族**：§35 / §36 / §37 / §39 / §40 / §41 / §42。

## §44 三条检索/归属纪律（本轮同时踩中）

### ① `head -N` 作用在 `grep -rn` 上 = 静默截断 = 制造「不存在」的结论

`grep -rn` 的输出**按路径排序**，`head` 切掉的永远是**字典序靠后**的那一类
（本轮切掉的恰好是**真正的生产写方** `taskprofile/` 与 `selection_writer.go`）。

**落地：任何要据此下「不存在 / 没有 / 零」判断的 grep**
**要么不用 `head`；要么先 `wc -l` 看总量；要么先 `awk -F: '{print $1}' | sort -u` 看文件分布。**

### ② 交叉验证时，两条检索若指向完全不同的文件集，先怀疑过滤条件，不要先怀疑世界

本轮「测试文件在写」与「生产文件在写」**同时成立**，差别只在**过滤与截断**。

### ③ 真库结论必须先声明归属：**读这个库的实例，未必跑着本 worktree 的代码**

凡结论依赖「代码里有没有接线」，**必须先确认写入实例的 commit sha**，
否则那是**用本仓的静态阅读去回答远端的运行时行为**。
**150 号因为这一条而没有发出 P1 —— 这是纪律，不是保守。**
（判据：`ps aux` 若本机无网关进程，则真库必然由别处写入。）

**同族**：§37（存在性四维度）/ §39（形态坏了却输出整齐结论）/ §40（同一份数据的矛盾解析）。

### §44 增补 ④ 判「有没有 X」之前，先确认「X 会声明在哪」——不要只查你正在读的那个文件

指标 / 配置 / 常量常常声明在**专门的配套文件**里
（本轮：`*_metrics.go`；150 号：`*_writer.go` 之外的 `registry.go`）。

**落地：判「有没有导出 / 有没有注册 / 有没有常量」时**
**先按文件名模式列一遍整个包**（`*_metrics.go` `*_prometheus.go` `*_config.go` `*_const.go`），
**再决定查哪里**；**优先用「同包/同目录全部文件」而不是「当前这个文件」作为检索范围。**

### §44 四种错误的共同点

| | 错误 | 本轮/前序实例 |
|---|---|---|
| ① | 截断了范围 | 150 号：`head -6` 切掉真正的生产写方 |
| ② | 过滤错了 | 150 号：`grep -vE "CREATE\|migration"` |
| ③ | 归属错了 | 150 号：真库由远端实例写入 |
| **④** | **范围本身就选窄了** | **151 号：只查 `selection_writer.go`，漏了同包的 `selection_metrics.go`** |

**共同点：都把「我看到的」当成了「全部」。**

### §45 核对「等价性」时，分母是**丢失路径数**，不是指标个数

151 号为某写入器坐实了「丢弃指标存在且完好」。下一轮被问的是「另一个写入器**有没有等价指标**」。

⚠️ **只答「有」是不够的**：答案表面与前者一致（「有，完好」），
但**强度完全不同** —— 实测发现它只覆盖了**一半**的丢失路径。

**落地：判「A 是否有 B 的等价物」时**
1. **先枚举 A 的丢失路径**（本轮 3 条：入队满 / 批量插入失败 / pool 未配置），
   **逐条问「这一条被计了吗」**，得到 `已覆盖 N / 总 M`；
2. **不要数指标个数**——指标数量与覆盖率无关（本轮 1 个指标，覆盖率 1/2）。

**配套三条：**

- **同包姊妹实现的不对称，是「无意分歧」的最强信号。**
  本轮两个写入器**同包、同构型、共用 `poolExec` 接口**，
  却在同一件事上做了不同决定，且**没有任何注释说明是有意为之**。
  ⇒ 反过来：**若两侧注释各自都诚实（`Help` 各写各的范围），
  那分歧就来自实现而非声明** ⇒ 不能用「作者本意」替实现开脱。

- **指标的 `Help` 文本自己声明的范围，就是它的验收范围。**
  本轮 `tuning` 侧 Help 写 `dropped because the writer queue was full`，
  **它从未声称覆盖插入失败** ⇒ 这**不是「承诺了却没实现」**，
  **设计范围本身就窄** ⇒ 定级更轻。
  ⚠️ 对照 `selection` 侧 Help 写 `queue full **or a failed insert**` 且**代码确实两条都实现了**。
  ⇒ **「Help 覆盖面」是可以直接拿来做验收断言的，比读实现更快且不会漏。**

- **同一机制的两个计数器可能单位不同。**
  本轮发现同一次批量失败（2 行）：内部 atomic `+2`（**行**）、
  Prometheus 计数器 `+1`（**批**），而该指标 Help 写的是 `rows lost`。
  ⇒ **凡把两个计数放一起对账（对账脚本 / 告警阈值 / 宽度核对），
  必须先确认两者的单位**；**偏小倍数随批大小变化 ⇒ 不是固定系数 ⇒ 不会自己报警。**

**实证测试要写成「正反对照」**：本轮断言的不是「指标存在」，
而是**丢失路径是否被计入**。**单侧通过不构成「不对称」的证据**，
**两侧同时通过才构成**（一边证明没计、一边证明计了）。

**测试要自带证伪护栏**：变异测试的失败信息里直接写
「若如此，说明上游已补齐，本报告的结论被证伪，必须改写」——
**这样将来有人真的补上代码时，报告会自己响，而不是继续挂着当结论。**

**同族**：§41（注释三桶）/ §44（把「我看到的」当成「全部」）/ §31（发现后必须真的去数）。
本条是它们的**量化形态**：§44 说「别只看一个文件」，§45 说「看全了还要**数出分母**」。

### §46 数字越刺眼，先确认「生产读的是不是这一列」——**尺子不对，结论必错**

**落地：任何一个「某表某列几乎全空」的数字，在写进报告之前必须过三问：**

1. **生产代码读的是这一列吗？** 去看**真实的查询表达式**，不是去看这一列本身。
   153 号：`session_dim.project_id = 1/1,212,805` 刺眼到可以直接发 P1，
   但 `admin/turns_sessions.go:50` 真正读的是
   `COALESCE(NULLIF(ss.gw_project_id,''), sd.project_id)`，
   **而 `session_summaries.gw_project_id` 有 321,093 行非空（95.9%）** ⇒ **尺子选错了表。**
2. **有回落层级吗？** 缺失常常是**被兜底接住了**，不是「没有」。
   762 的两级口径（权威值 → `app:<application_code>`）就是典型：
   **level-1 空 + level-2 满 = 功能正常，只是权威层从未被使用。**
3. **台账里查过吗？** 153 号的 `1/120 万` 与我实测的 `1/1,212,805` **数值吻合到量级一致**
   ⇒ 那是 R32 已登记、762 已修的旧问题。**吻合得太漂亮的那个数字，往往是旧结论的复现，不是新发现。**

**⇒ 判别式：先量「生产查询表达式的输出」，再决定要不要为「某张表的某列」发报告。**

⚠️ **这条与 §35 是同一条纪律的两个方向**：
§35 说「阈值必须来自对象自身配置」；
**§46 说「量必须来自生产真正消费的那个字段」** ——
两者都是**尺子问题**，而尺子问题产生的错误**输出都是干净自洽的数字，不会自己报警**。

**同族**：§45（等价性要数分母）/ §30（先数再定性）/ §28（`reltuples` 不能支撑存在性断言）/ §44（别把「我看到的」当「全部」）。
**共同点：全部都是「量」这一环出错，而量是报告里最像证据、最少被质疑的部分。**

### §46 附：普查类结论必须钉住「分母是什么」以及「分母不包括什么」

153 号普查出 70 个丢弃站点，**但真正的盲区是另外 43 处非阻塞 `default:` + 55 处裸 return**
——它们**既无日志也无计数器，完全不在 70 之内**。

⇒ **写普查表时必须同时写「本表的分母是什么」和「本表的分母不包括什么」。**
只写前者，读者会把 70 当成「全部丢弃点」，那是**范围选窄的另一种形态（§44④ 的统计版）**。

**同族**：§40（同一份工具输出只写一次解析）/ §31（发现缺陷后必须真的去数）。

### §47 「看起来正确」的过滤器会静默地把每一行都判成空 —— `re.match(r'\S')` 陷阱

**本轮实例**：静默丢弃普查脚本对 2,169 个 `.go` 文件跑出 **`0` 个 `select` 型 `default:` 分支**。
按 §39 没有接受这个 0，而是去查，查出两个 bug，**第二个是任何 Go/缩进语言都会踩的**：

```python
if not re.compile(r'\S').match(line):   # ❌ 只锚定「位置 0」
    continue                            # → '\tcase ch <- v:' 第 0 位是制表符 = 空白
```

- `.match()` 锚定**字符串开头**；`\S` 要求该位置是非空白 ⇒ **任何带缩进的行都判为「空」**。
- 而 **Go 源码几乎全是缩进的** ⇒ 这个过滤器**对全部输入返回空集**，且**不报错、不抛异常**。
- ⇒ **正确写法是 `if not line.strip():`**，或 `re.search()`。

⚠️ **同族陷阱（同一晚连踩）**：判定「有没有计数器」只搜 `.Add/.Inc/.Store/Counter/metric/stats.`
⇒ **漏掉裸 `x++`**，而本轮 `admin/telemetry.go:800` 恰恰是 `errCount++`。
⇒ **算「有没有」的正则，永远要拿一个已知为真的样本先验一遍。**

### §47 三条通用纪律（本轮全部实证）

1. **返回 0 时先怀疑形态**（§39 的再次确认）。**「0」比「错数字」更危险，因为它看起来像结论。**
2. **grep 命中数 ≠ 站点数 ≠ 缺陷数**，中间每一层都要单独自洽（§45 的分母纪律）。
3. **⚠️ 报出来的数字必须自己带「上界 / 下界 / 误判方向」三件套** ——
   本轮输出「61 处完全静默」时，**必须同时写明「其中至少 8 类已判为良性」与「形态分类器已实证会误判」**。
   **只给一个干净整数的报告，读者会当它是缺陷数。**

**同族**：§39（形态坏了却输出整齐结论）/ §45（分母）/ §46（尺子不对结论必错）/ §40（同一份输出只解析一次）。

### §48 判「发送」还是「接收」：箭头**前面**有没有 `:=`

154 号用 `re.compile(r'^.*<-\s*[^=]')` 判「向 channel 发送」，
**它同时匹配接收** ⇒ 35 处**接收循环的终止条件**（`case v := <-ch:` + `default: return`，
语义是「队列空了，循环结束」）被误算成「发送丢弃」，
**把 61 虚报成 61（真实 28）**，并据此把 `domains/dispatch` 整包列成了下轮入口——**而那 8 处真缺陷 0 处**。

**正确判据（只看箭头前面）：**

| 形态 | 判别 | 语义 |
|---|---|---|
| `case <-ch:` | 箭头前**为空** | **接收** |
| `case v := <-ch:` | 箭头前**含 `:=`** | **接收** |
| `case v, ok := <-ch:` | 同上 | **接收** |
| `case ch <- v:` | 箭头前是 LHS 表达式，**无 `:=`** | **发送（可丢）** |
| `case ch <- struct{}{...}:` | 同上 | **发送（可丢）** |

⇒ **最省事的写法：`is_send = ("<-" in ce) and (":=" not in ce[:ce.index("<-")]) and ce[:ce.index("<-")].strip() != ""`**

⚠️ **两条通用纪律（本轮与 154 号连踩）**：
1. **§47 的「正则要先拿已知样本验一遍」，本轮又踩了一次——而且样本就是我自己上一轮写在报告里的那个。**
   ⇒ **把自己上一轮报告里的例子当测试用例**，是最便宜的正则自检。
2. **⚠️ 分类器的误差必须双向声明**：本轮 28 这个数 **可能偏高**（形态误判，已证 1 处）
   **也可能偏低**（计数器在包裹函数里会漏判）。
   ⇒ **只写一个方向就是误导。**（§47 三件套的第三件：上界/下界/误判方向。）

**同族**：§47（`\S`+`.match()` 静默吞掉所有缩进行）/ §45（分母）/ §46（尺子不对结论必错）/ §39（返回 0 先怀疑形态）。
**本族四条的共同点：全部产出一个「看起来干净自洽」的错误数字，而错误出在分类这一步，不在数字这一步。**

### §49 判「静默丢弃」的四道过滤器 —— 最关键的一道是「返回值能不能传播给调用方」

156 号把 154 号的 61 处收敛到 **0 个确认缺陷**，四道过滤器依次砍掉 54% / 32% / 37% / 100%：

### §49 过滤器 ③ 是最容易被漏掉、也最有效的一道

**`return err` / `return false` 本身就是最响的信号。**

⇒ **判「丢失是否静默」时，四个问题缺一不可：**
`① 有没有日志` `② 有没有计数器` `③ 有没有返回值/错误往上传` `④ 有没有注释论证丢了无害`

### §49 第六个扫描器 bug（本条线累计 6 个）：空 `default:` 不等于「直接结束」

```go
select {
case ch <- v: return nil
default:
}                       // 块是空的
return nil, ErrSaturated   // ← select 块外的代码照样执行
```

**Go 的 `select` 不是语句块作用域**，`default:` 块结束**不等于**函数结束。
扫描器必须判断「select 之后是否还有可达代码」，
否则会把「空 default + 落到 select 之后」误判成「空 default = 静默丢弃」。

### §51 「内容寻址去重」与「按 mtime 清理」是互相矛盾的两套时间观

**本轮实例（158 号）**：`request_attachments` 10,652 行只对应 **80 份文件（平均复用 133×，最高 1,155×）**，
而去重命中**从不 touch mtime**（全包 `Chtimes` 命中 0），
清理端点又**纯按 `ModTime()` 删、零引用检查** ⇒ **删掉 1 份文件 = 平均 133 个请求的引用变悬空。**

**判别式：凡同时满足下面三条，就要去查清理路径——**
1. **存储是内容寻址的**（key 由 hash 决定 ⇒ 同一份内容只有一份文件）；
2. **存在跨请求/跨时间的复用**（去重命中是常态，不是例外）；
3. **清理按文件自身的时间属性（mtime / created-at）判断，而不是按「最后一次被引用」判断。**

⇒ ①② 都会让「文件的存在期」与「引用的存在期」**脱钩**；
③ 是唯一一处还能把它们对齐的机会——**而它恰好是错的**。

⚠️ **正确的尺子（§46 再次生效）**：判断「这份文件还有没有人要」，
**必须查引用表（`request_attachments.created_at`）而不是文件 mtime**。
本例正是用引用表测出 14 天跨度，才让结论站住。

### §51 守护要对称：危害小的一侧有绊线，危害大的一侧没人管

### §52 「先证明后果，再量化规模」的后半段：后果要**分维度刻画**，不是给一个形容词

158 号定了「机制成立 + 规模已量化」，但**明确留了一句「后果严重度未核」**。
159 号补完后发现：**光给一个形容词（「会丢数据」）是不够的，结论会随维度翻转。**

同一件事在四个维度上的答案是**互相冲突**的：

| 维度 | 答案 |
|---|---|
| 会不会让请求失败 | **不会**（`continue`，注释写「不吞掉原请求」） |
| 会不会影响其它附件 | **不会**（逐个附件独立处理） |
| **用户会不会知道** | **不会**（无任何面向客户端的提示） |
| **模型实际看到什么** | **看不到那张图**（provider 收到 404） |

⇒ 综合定性是 **「静默语义损坏」**，而不是「请求失败」。
⚠️ **「静默」这一维往往才是定级的决定项** —— 它比失败更难排查，且**不产生任何可观测的业务侧信号**。

**⇒ 判「后果严重度」时至少要答这四问：**
`① 会不会让请求失败` `② 会不会波及其它对象` `③ 当事方知不知道` `④ 有没有留下痕迹`
**四问的答案常常互相矛盾**（本例：①②否、③否、④有两处 Warn）⇒ **必须逐维列表，不要写成一句形容词。**

### §53 响应里的 `0` 也会撒谎：「没删到」和「没检查到」长得一样

### §55 切换类配置必须有「不变式检查」：谁会因为这个开关而语义失效？

162 号补完了 160 号的待核，结论是：

**同族**：§53（部署形态 + `0` 会撒谎）/ §51（内容寻址 vs mtime 清理 / 守护要对称）/ §46（尺子）/ §30（不可达的不是缺陷）。

### §56 待裁决项在等产品拍板时，**先把实现成本问掉**——否则你无法判断该不该拍

### §56 ⚠️ 但「修法便宜」有一个隐含前提，必须写出来

修法 2（引用差集）**依赖「行表比文件活得久」**——
而 `Repository.DeleteOlderThan`（行侧清理）是**零生产调用方**（R87-j-1，158 号已坐实），
**若将来它被接上，引用数据会先于文件消失**。

⇒ **只做修法 2 而不做修法 1（加下界），等于把「误删」换成了「漏删」。**
⇒ **两件事必须一起做** —— 这是本轮最容易被漏掉的一步。

### §56 顺带一条判断：「更简单的那个选项」有时正是缺陷本身

产品若答「保留期以**首次写入时间**为准」——那**表面上更简单**（直接用现成 mtime），
**但那恰恰是 158 号指出的缺陷本身**（与内容寻址去重语义矛盾）。
⇒ **这种情形应被显式记录为「已接受的取舍」，而不是当作「已解决」。**
⇒ **审计报告要预判这两种答案各自意味着什么，别只等一个「是/否」。**

**同族**：§33（先证后果再量化）/ §35（阈值来自对象自身配置）/ §51（内容寻址 vs mtime 清理）/ §46（尺子）。

### §57 判据自己写错时，会输出一个「干净自洽的 0」——**0 或反常整齐时先怀疑判据**

164 号第一条 SQL 同时算三项，第二项我写成 `split_part(hash,'',1)`（**分隔符是空串，返回空串**），

⚠️ **形态与 §47/§48/§50 完全同族：判据/分类条件写错 ⇒ 输出一个干净、自洽、完全错误的数字，且不报任何错。**
**本条线的检测器缺陷已达八个。**

**⇒ 落地三条：**
1. **判据写完后，先拿一个「已知为真」的样本单跑一次**（本轮：`shape_ok=80/80` 已是已知为真那一列）。
2. **同一批查询里，「通过」与「全灭」两类结果都值得怀疑** ——

## §58 「静默」是「端点 × 缺陷」的属性 —— 且一个概念被两个字段表达时，先数写方

**前���：判「静默丢弃」前，先看响应体形状。**

§50 的四问（日志 / 计数器 / 返回值能否传播 / 注释论证无害）之外，还要再加一问：

> **这个端点的响应体是回显型的，还是自造 / 空的？**

- **回显型** ⇒ 未生效的差异会自己跑进响应 ⇒ **不静默**。
  本轮实例：`admin/storage_config.go:344-349` 的 `storageConfigPut` 末尾直接调
  `h.storageConfigGet(w, r)`，于是提交 `storage_type:"oss"` 会收到 `{"storage_type":"local"}`
  ⇒ 13 个字段被丢弃这件事**在响应里明摆着** ⇒ 定性是「契约不诚实」，**不是**静默丢弃。
- **自造型 / 空体 / 只回 `{"ok":true}`** ⇒ 同一个缺陷**立刻变成货真价实的静默丢弃**。

**⇒ 同一段代码换个 handler 形状，定级就翻。**
所以结论必须写成 `端点 A 上的静默丢弃`，不能只写「静默丢弃」——
**「静默」是「端点 × 缺陷」的属性，不是「缺陷」本身的属性。**

**后半：一个概念被两个字段表达时，先数写方，不要先看读方。**

本轮起手看到的是 GET 里 24 行 `case "oss"` / `case "s3"` 读逻辑（显眼），
**先查写入方才发现 0 个** —— 而那 24 行只是症状，真正的问题是「两个表示里
唯一生效的那个（env）没有任何 UI/DB 入口，另一个（`settings_kv`）没有任何写入方」。

**落地顺序固定为：**
1. `grep '<概念关键词>'` 列出**全部**出现点；
2. 按 **读 / 写** 两栏分开列；
3. **先数写方**（0 ⇒ 那一侧全死，再去谈读的语义）；
4. 写方为 0 时，**去真库确认那些键真的 0 行** ——
   本轮 `settings_kv` 实测 0 行，把「看着像死代码」升级成**可证不可达**。

⚠️ 计数要**自己数一遍**（§30/§31）：本轮 `StorageConfigUpdateRequest` 声明 19 / 消费 6 / 丢弃 **13**，
`S3UseSSL` 因是 `*bool` 而非 `*string` 极易在肉眼扫 `req.S…` 时漏掉 ⇒ **13 不是 11**。

**同族**：§50（返回值能否传播）/ §16（否定结论分轮登记，不外推）/ §41 桶②（明确声明未接线 = 不是缺陷）/ §56（把实现成本问掉再登记）。
**本条的教训方向与 §57 相反**：§57 是「同一批结果里反常整齐更危险」，
本条是「**先看到的显眼结构往往只是症状，要按 读/写 分栏再排序**」。

## §59 尺子错分两种形态：静默的伤结论可信度，响亮的只伤轮次 —— 但都要记

前八次检测器缺陷（§47 / §48 / §50 / §57）**全部是静默的**：
输出一个干净、自洽、**完全错误**的数字，不报任何错。

R89-CB（166 号）又出现三次尺子错误，但**形态相反 —— 全部大声 `ERROR`、零行输出**：

| # | 我写的 | 真相 | 结果 |
|---|---|---|---|
| 1 | `min(created_at)` on `request_logs` | 该表时间列叫 **`ts`** | `ERROR: column "created_at" does not exist` |
| 2 | `ORDER BY n` 在 `GROUP BY 2` 子查询里 | PG 不允许同层引用输出别名 | `ERROR: column "n" does not exist` |
| 3 | `gw_session_id` on `session_turns` | 该表叫 **`session_id`** | `ERROR` + HINT |

**⇒ 两种形态必须分开记，不要混进同一份清单：**

| 形态 | 症状 | 伤什么 | 记法 |
|---|---|---|---|
| **静默** | 输出干净自洽的错误数字 | **结论可信度** | playbook 正文 + 对照样本 / 变体测试 |
| **响亮** | `ERROR`，零输出 | **轮次** | 一条前置动作即可，不必长篇 |

**⇒ 唯一的前置动作：写任何聚合 SQL 之前，先查一次列名。**

本仓已确认三组列名互不相同，**直接推翻「三张主表结构一样」的默认假设**：

| 表 | 时间列 | 会话列 |
|---|---|---|
| `request_logs` | **`ts`** | `gw_session_id` |
| `session_turns` | **`ts`** | **`session_id`** |
| `request_wal` | **`created_at`** | `gw_session_id` |

**⇒ 推论**：本仓里任何「三表 union 后统一按 `created_at` 分月 / 按 `gw_session_id` 关联」的写法都是**错的**，
跨表聚合必须显式写各自的列名。

**同族**：§47（`\S` + `.match()`）/ §48（箭头前有没有 `:=`）/ §50（返回值真的存在吗）/
§57（判据自己写错）/ **§46（尺子不对结论必错）**。
**§46 与本条是同一件事的两端**：§46 说「尺子不对结论必错」，本条说「尺子不对有两种表现，**识别形态决定记法**」。

## §60 JOIN 里未限定表名的列会静默绑定到另一张表 —— 若那一侧没命中，NULL 列看起来像一个真实结论

§47/§48/§50/§57 记的检测器缺陷是「**判据写错 ⇒ 输出错误数字**」。
R89-CC（167 号）踩的是更隐蔽的一层 —— **不是算错，是没连上**：

```sql
-- 错：status 未限定表名，PG 绑定到 w.status（request_wal 的列）
SELECT status, count(*) FROM request_logs r LEFT JOIN request_wal w ON …
--   → 262432 行，status 全空   ← 看起来像一个真实结论
-- 对：加前缀
SELECT r.<col>, count(*) FROM request_logs r LEFT JOIN request_wal w ON …
```

**为什么它比前几次更危险**：前几次判据写错，输出的是一个**具体的错值**（`0/80`、61 而不是 28）。
**这一次的输出是「全空」—— 而「全空」本身就是一个看起来合理的结论形状。**
它不需要你算错，**只需要你没 JOIN 上**。

**⇒ 两条落地规则：**

1. **JOIN 多表时，出现在 `SELECT` / `GROUP BY` / 聚合里的列一律加表前缀。**
   本仓尤其危险 —— `request_wal` 与 `request_logs` **共享大量列名**：
   `request_id` / `gw_session_id` / `tenant_id` / `prompt_tokens` / `completion_tokens` /
   `compression_strategy` / `error` / `status` …
2. **「某列全空」这个结论，必须配一个「JOIN 命中率」的分母。**
   本轮若先查了 `has_wal_row`（= 0/262,432），就立刻知道那不是「status 为空」而是「这批行根本不在另一张表里」。
   **⇒ 判据：看到 `GROUP BY <col>` 输出 `(empty)` 占 100% 时，先问「这一列非空的对照组长什么样」。**

**⇒ 本轮拦下它的两件事**（都不是「数字不对」）：
- playbook **§57**「同一批结果里『通过』与『全灭』都要怀疑」；
- 自己写的那句判别问题 —— **正常流量侧的 `status` 对照我从头到尾没查过**，
  而「旁路流量没有 status」若成立，正常流量就该有可对照的 status。

**同族**：§47（`\S`+`.match()` 静默吞行）/ §48（箭头前有没有 `:=`）/ §50（返回值真的存在吗）/
§57（判据自己写错）/ **§59（尺子错的两种形态）**。
**§59 说「尺子错分静默与响亮」，本条说「静默里最危险的一类：不是算错，是没连上」。**

## §61 每条证据都要单独配对照组；「两组都是 100%」的那一列不是判别器 —— 且证据表要按强度排序

**由来**：167 号把「`request_class='immediate'` 占 100%」列为「这是合成数据」的**第一条**证据。
它听起来**极像**一个写入方签名（具体枚举值、恰好 100%），实际却是
`telemetry/client.go:3814-3822` `requestClassArg` 的**兜底返回值** +
`:3827-3837` `normalizeRequestClassAndDueAt` 的**每次写入前强制值** ——
**对所有流量恒为 100%**。补跑对照组后：正常流量 798,205/798,205 也是 `immediate`。

**⇒ 规则一：每条证据单独问「对照组长什么样」。**
若在 167 号就跑了对照组，这条证据当场作废。
**⚠️ 这与 §60 是同一条纪律的两个方向**：
- **§60**：「某列**全空**」要配 **JOIN 命中率** 分母；
- **§61**：「某列**全满**」要配 **对照组分布**。
**两者都是：单侧分布不构成结论。**

**⇒ 规则二：判别器的必要条件是「两组分布不同」。**
写证据表时逐行问：**「如果这批是正常流量，这一列会长什么样？」**
两侧相同 ⇒ 这一列不进表。

**⇒ 规则三：证据表按强度排序，最强那条放第一。**
本轮最强的是 `request_wal` 命中率（0/262,432 vs 99.99%，因为它是**主路径旁证表**），
`api_key_id`（0.002% vs 99.98%）第二；被撤回的 `request_class` 最弱。
**⚠️ 摘要有 tendency 点名第一条 ⇒ 排错序 = 强调错的东西。**

**⇒ 规则四（推论）：默认值、兜底值、常量列，永远不能当判别器。**
入库前先问「这个字段的默认值是什么」。本仓已确认两列：
- `request_class` —— `requestClassArg` 兜底 `"immediate"`；
- `request_type` —— `telemetry/client.go:3811` 注释：「Returns "main" for a plain client request (the column DEFAULT)」。
**⇒ 凡是 Go 侧写着 `omitempty` + 指针 + 有 DEFAULT 的列，先去 `information_schema.columns` 查 default。**

**同族**：§47 / §48 / §50 / §57 / §59 / **§60（单侧全空要配 JOIN 命中率）**。
**§60 与 §61 是同一条纪律的两端：一端管「全空」，一端管「全满」。**

## §63 「没有 X」有两种读法：「不属于这一类」与「在到达这一步之前出局了」—— 必须用控制流确认是哪一种

**⇒ 规则二：判断字段是否为空时，「我统计了哪些列」必须写出来；取数顺序固定为
身份 → 结局 → 中间产物。**

**没先看「身份」（api_key_id）**。

**⇒ 规则三：一次错误的读法可能连累下游推理。**

## §64 「配了闸门 + 从不触发」有两种解释，必须用「那个 key 到底有多少流量」分辨

**由来**（R89-CG / 171 号）：统计四道闸门触发情况时，

**组合起来极像「闸门配了但从不生效 = fail-open 坏了」。**

⇒ 「0 触发」被「几乎没流量」完全解释 ⇒ 不是缺陷。**

**⇒ 判别式：**

```
「0 触发」的两种解释：
  (a) 闸门没生效 ⇒ 该 key 的实际流量 ≫ 阈值，却一次没触发   ← 缺陷
  (b) 没流量     ⇒ 该 key 的实际流量 ≪ 阈值                ← 正常
⇒ 必须查「该 key 的实际请求数 / token 数」，再和阈值比大小
```

**⇒ 与既有条目的关系（三者配套，缺一不可）：**

- **§52** 是**定级纪律**（机制成立 ≠ 发 P1）。

**⇒ 顺带记一条「未解项的登记纪律」**：
查了两层还没查清的问题（如「阈值列是 NULL 却触发 40 万次限流」），
**正确做法是把它写进报告的「未解项」并排进下一轮顺位**，**而不是**：
① 猜一个最可能的解释写进结论；② 或者干脆不提（那会让「40 万次限流」看起来像已完全解释）。
**⇒ 报告里允许、并且应该出现「我不知道」这句话。**

**同族**：§16 / §50 / §52 / §61 / §62 / §63。

## §65 读「0 = 无限制」这类注释时，必须同时确认 NULL 走哪条路 —— NULL 与 0 在这里语义完全相反

**由来**（R89-CH / 172 号）：`domains/authentication/verifier.go:118` 的注释只说
「A per-key value of **0** means "unlimited"」，**一个字都没提 NULL**。
而实际行为是：

| `api_keys.rate_limit_rpm` | `EffectiveRPM()` | 语义 |
|---|---|---|
| **`0`** | `0` | **显式无限制**（`rate_limit.go:70-73` 直接 return，不检查） |
| **`NULL`** | `tierDefaults[keyTier][0]` = **system→300 / production→60 / default→12 / applicant→6** | **按 tier 限额限流** |

**⇒ 语义完全相反。** 运维按注释理解「留空 = 不限」会得到相反结果。
**强化证据**：89 个 `is_system=true` 的 key 里 **88 个是 NULL、只有 1 个是 0** ——
**不是孤例配置，是家族性默认行为。**

**⇒ 规则一：凡是有「0 / NULL / 空字符串 / -1」多态取值的配置列，读注释时必须问
「另外几个取值分别是什么」。**
本仓已确认的多态列（按此表复核）：`api_keys.rate_limit_rpm`（本条 ✅ 已确认）；
`rate_limit_tpm` / `rate_limit_concurrent` / `budget_usd` **同类嫌疑，尚未逐列核实**。

**⇒ 规则二：查「某配置是否生效」时，先查 `information_schema` 的 nullable 与 DEFAULT，再读代码。**
本轮关键一步是发现 `api_keys` 还有 `is_system` 与 `key_tier` 两列 ——
**若没先查列名、只看到 `rate_limit_rpm` 是 NULL，会得出「没配限流所以不该限流」的错误结论。**

**⇒ 规则三：注释与测试用例都是「作者当时的理解」，不是「契约」。**
本轮 `verifier_test.go:124-125` 覆盖了 `default` 与 `production` 两个 tier 的 NULL 回落，
**唯独没覆盖 `system`** —— 而出问题的恰恰是 `system`（自检 key 的 tier）。
**⇒ 「测试覆盖了 X」不等于「X 的所有取值都被覆盖」。**

**同族**：§64（配了却不触发要看实际流量）/ §63（「没有 X」的两种读法）/ §59（尺子错的两种形态）/
§61（默认值不能当判别器）/ **§55（切换类配置必须有不变式检查）**。
**§55 与本条是同一族的两端**：§55 说「配置切换要有守卫」，本条说「**配置本身的多态取值要有文档**」。

## §66 读到一个「豁免分支 / 守卫分支」时，必须确认触发它的那个字段有生产写入方 —— 守卫存在 ≠ 守卫可达

**由来**（R89-CI / 173 号）：`domains/streaming/rate_limit.go:66` 有一段写得完整、注释明确的

```go
if keyInfo == nil || rl == nil || keyInfo.IsInternal {
	return rateLimitOutcome{Skipped: true}
}
```

`ratelimit/redis_sliding.go:338-339` 还专门写了
「**Internal callers (IsInternal=true) are always allowed through**」
—— **看上去这个守卫是好的**。实际是**死代码**：`KeyInfo.IsInternal` **全仓零写入点**。

**⇒ 规则一：看到 `if … <field> { return / skip / allow }` 这类守卫，不要只读守卫本身，要读 `<field>` 的写入方。**
一个守卫的有效性 = **守卫分支存在** × **它的输入在生产里真的会被置位**。
后者经常被忽略，因为**读守卫时眼睛跟着控制流走，不会回头找赋值**。

**⇒ 规则二：判「这个字段有没有生产写入方」要用两种检索形态：**
- 形态一（赋值形态）：`<field>:|\\.<field> =|<field>\\s*=`（覆盖复合字面量字段、显式赋值、构造传参）；
- 形态二（全出现点计数）：`<field>`，再**剔除**测试文件 / vendor / **同名不同符号**。

本轮形态一「全仓 1 命中 = 声明本身」直接定性；
形态二用于排除 `telemetry.IsInternalAutoEntry` / `georesolve.IsInternal` 这类**同名干扰项**。
**⚠️ 同名不同符号是这一条最大的误判来源** —— 不剔除就会得出「有很多处赋值」的错误结论。

**⇒ 规则三（与 §41 桶① 配套）：§41 让你「别把注释当承诺」，§66 让你「也别把代码当接线」。**
一个分支写在那里、逻辑完整、测试覆盖了它能走通的那半边
（本轮 `verifier_test.go` 确实覆盖了 `EffectiveRPM` 的各种取值），
**完全可能仍然是不可达的**。
**⇒ 判断「接线了没有」的标准是：有生产写入方（规则二），而不是「代码里看得到」。**

**同族**：§41（注释三桶）/ §55（切换类配置要有不变式检查）/ §65（多态取值要有文档）/
§16（0 行不等于缺陷）/ **§12（死代码判定不可信 —— 本条是它的可执行版）**。

## §67 找到「事件确实发生」的证据 ≠ 证明了因果链 —— 中间隔着「口径」这一关

**由来**（R89-CJ / 174 号）：花了三轮（171→173）搭出一条完整因果链，
然后用 `credential_probe_queue` 找到了「已发生」，
**差点就此宣布 P1**。查 `reason_code` 才发现失败主因是连接层错误，不是限流。

**⇒ 规则一：「我预测的事件发生了」只证明前半条链，不证明后半条。**
典型形态：**事件 A（我观测到的）与事件 B（我归因的）发生在不同层**，
A 落在表里、B 落在表外 ⇒ **B 在这张表里天然不可见**。

**⇒ 规则二：先问「这两件事是不是同一个口径」，再问「相关性有多强」。**

| 口径 | 语义 | 落点 |
|---|---|---|
| 网关入口 429 | **「没跑」** | 在业务表**之前**，**不进业务表** |
| 探测真实失败 | **「跑了但失败」** | `credential_probe_queue.failed` |

**⇒ 事件 A 在表外、事件 B 在表内 ⇒ 表里 B 的分布，永远无法验证表外的 A。**

**⇒ 规则三（承接 §33）：时序吻合不能替代因果。**
本轮 09-27（限流停止次日）自检成功率回到 85.9%，**吻合得非常漂亮** ——
**但那只是把 (a)「两者无关」/ (b)「限流是次生效应」从五五开推向 (b) 更可能，不是「证明了 (b)」。**
**⇒ 报告里要写成「更可能」+「需要什么证据才能定」，不是「因为 A 所以 B」。**

**⇒ 规则四（自我批评，可执行）：当一条因果链很长（≥3 环）且我为它建了多轮报告时，
要主动去问「如果这条链是错的，我会在哪个数据上最先看到」，并在本轮就查那个数据。**
本轮那个数据是 `reason_code` 的原因分布 —— **它在第一轮就该查，我拖到了第四轮。**
**⇒ 落地：链条每延长一环，就写下「下一环的证伪信号是什么」，下一轮优先查它。**

**同族**：§33（先证伪再量化）/ §46（尺子不对结论必错）/ §63（「没有 X」的两种读法）/
§52（机制成立 ≠ P1）/ §16（连续否定要分轮列边界）。

## §68 两个变量共变时，先找一个「只可能由其中一个解释」的维度 —— 共变的两个东西可以由第三个原因同时驱动

**由来**（R89-CK / 175 号）：`connection_error` 与网关限流**精确共变**
（09-10 的 0–16 → 09-23 的 6,399 → 09-27 回到 29），看起来就是「限流打爆 worker」。

**⇒ 规则一：共变 ⇒ 只是「同源」的证据，不是因果方向的证据。**
两个变量同时被**第三个原因**驱动时，它们会完美共变，而因果方向可以完全相反。
**要找因果，必须找一个「在解释 A 下会变、在解释 B 下不会变」的维度。**

**⇒ 规则二：判别维度优先选「另一个子系统在同一时间窗的表现」。**

| 候选维度 | 本例结果 | 判别力 |
|---|---|---|
| 探测面自己的 `reason_code` | `rate_limit_exceeded` 仅 57 行 | ★★★ 排除「限流被记成 connection_error」 |
| **同期业务面成功率** | **87%–94%（峰值）** | ★★★ **排除「上游整体故障」** |
| worker 侧日志 | 不可得 | —— |

**⇒ 规则三（本轮最大的方法论收获）：当探测面与业务面表现相反时，
先怀疑「它们测的不是同一批东西」，而不是「其中一边坏了」。**
本轮若只盯着探测面 0.93% 的成功率，会得出「自检系统崩了」——
**而加上业务面这一维，结论变成「自检可能在正确报告业务探不到的坏端点」，方向完全相反。**

**⇒ 规则四：连续两轮改写同一结论时，第三轮要主动去找「推翻我的那个维度」，
而不是继续加固现有解释。**
171→172→173 都在加固「限流是因」；174 号第一次转向（找 `reason_code`）是对的；
**175 号第二次转向（找业务面对照）才真正换掉了框架。**

**同族**：§67（事件发生 ≠ 因果成立）/ §33（先证伪再量化）/ §46（尺子不对结论必错）/
§61（单侧分布要配对照组）/ §64（「0 触发」要看实际流量）。

## §69 怀疑「两个主体共用一个桶」时，去读那个保存桶状态的数据结构的 key 是什么 —— 不要靠机制推测

**由来**（R89-CL / 176 号）：175 号留下「自检 key 与业务 key 是否落进同一个限流桶」的疑问，
并写明「`CheckRPMCtx(keyID, limit)` 按 keyID 分桶，但 `AdmitRPMWithBudget`
**是否有跨 key 共享计数未核**」。

**答案：读 `ratelimit/minute_bucket.go` 就有了** —— **9 处状态访问全部以 `keyID` 为键**
（`a.current[keyID]` 计数、`a.queues[keyID]` 等待队列、`releaseWaitersLocked(keyID,…)`、
`cancel(keyID,…)`、`delete(a.queues, keyID)`），`current`/`queues` 都是 `map[int]…`，
**零个全局桶、零个跨 key 共享计数**。

**⇒ 落地三步：**
1. 问「A 和 B 共用桶吗」时，**去读那个保存桶状态的数据结构的 key 类型**；
2. **数一数有几处状态访问**（本例 9 处）—— 只有 1 处就可能漏看，**数全了才敢下结论**；
3. `map[int]X` 里的 `int` 究竟是什么，是这类问题**唯一需要确认**的东西。

**⇒ 与既有条目的关系**：
§66（守卫存在 ≠ 守卫可达）问的是「**输入有没有写入方**」；
**本条问的是「两个行为主体会不会共享状态」，答案是去数据结构里看键。**
**两者都是「读机制不如读数据结构」。**

**同族**：§66 / §67（共变 ≠ 因果成立）/ §68（共变要另找判别维度）/
§46（尺子不对结论必错）/ §16（否定结论分轮登记，不外推）。

## §70 一个字段在两个出口上待遇不同时，先确认「哪个出口是我一直在查的」—— 查错出口会让你以为字段不存在

**由来**（R89-CM / 177 号）：`rlOutcome.Reason`
**进了 Prometheus**（`llm_gateway_rate_limit_rejections_total` 带 `reason` 标签、有 `unknown` 兜底），
**但没进 `request_logs`**（`captureAndEmitRateLimited` 闭包签名里根本没有 `Reason` 的位置）。

于是：
- 171 号问「触发的是并发/速率/预算哪种闸门」→ 查 `request_logs` → 四种塌缩成一个
  ⇒ **我以为代码没记**；
- 176 号问「09-28 那 1,274 次是配额还是背压」→ 同样查 `request_logs` ⇒ **同样查不出**。

**⇒ 而真相是：它被记了，只是记在另一个出口。**

**⇒ 落地三条：**
1. **当某个「看起来没被记录的字段」查不到时，先列出它的所有写入出口**
   （内存状态 / 指标库 / 日志 / 业务表 / 响应头 / trace 字段），**逐一确认哪个出口有、哪个没有**；
2. **本仓的可观测性出口至少有 5 个**：`request_logs`（`error_kind` / `request_status`）、

3. **审计方要特别警惕**：本仓里 **「数据侧查不到」已经被我误当成「不存在」至少 3 次**

**⇒ 与既有条目的关系**：§46「尺子不对结论必错」讲的是**尺子量错对象**；
**本条讲的是**尺子本身没坏、但**你手里拿的是这一把，而那一把上没有这个刻度**。

**同族**：§46 / §59（尺子错的两种形态）/ §61（单侧分布要配对照）/

### §71 查「为什么」之前先问「这个维度在不在我要查的那张表里」—— 本仓的诊断维度体系与 `request_logs` 基本正交

**由来**（R89-CO / 179 号）：对全仓 `*_metrics.go` 的 label 求差集 ——
**16 个 label 里 14 个在 `request_logs` 上没有对应列**，只有 `success` / `task_type` 两个例外；
**`status` 这个看似最基础的维度也没有** —— 业务表上叫 `request_status`，
且是 **view 从 `status_code` 推导出来的**（`db/request_logs_view_schema.go:405`），
**不是一张真实列**。

**⇒ 这把 177 号从一个实例提升为一类：**
「查数据查不到原因」在绝大多数细粒度诊断问题上都是**常态**，而不是「代码没记」。

**⇒ 落地三条：**
1. **遇到「查数据查不到原因」时，先做一次 label↔列 的差集核对**，
   而不是先怀疑「代码没记」；
2. **本仓可观测性出口有 6 个**（§70 列了 5 个，本条补第 6 个）：
   `request_logs`（业务列）/ Prometheus（高基数 label）/ `slog` /
   HTTP 响应头（`X-LLM-Gateway-RateLimit-Scope` 等）/ `gwtrace` 字段 /
   **view 派生列**（`request_status` ← `status_code`，**不是存储值**）；
3. **view 派生列要单独标出来** —— 查它等于查一个计算表达式，不是查数据。
   本仓 `request_status='rate_limited'` 就是这样来的，
   **我在 172 号正是靠这一条才确认那批 429 是网关自己发的（正例）**。

**⇒ 出口分工（背下来直接用）：**

| 想回答 | 去哪 | ❌ 不要去 |
|---|---|---|
| 「为什么被拒/限流/降级」 | `/metrics` 的 `*{reason,outcome,result}` | `request_logs` |
| 「key/provider 配额打满了吗」 | `/metrics` + `api_keys` | `request_logs` |
| 「租户→apikey 用量与对账」 | `request_logs` / `usage_ledger` | `/metrics` |
| 「压缩/脱敏是否生效」 | `compression_strategy` + `session_turns` | `/metrics` |
| 「流量结构（模型/协议/端点）」 | `request_logs` **真实列** | 同名 label |

**一句话：「为什么」走指标，「是多少 / 归谁」走业务表。**

**⇒ 与既有条目的关系**：§70 说「查错出口会让你**以为字段不存在**」；
**本条说「这不只是个别字段 —— 整类诊断维度都这样，所以要在开工前就问，
而不是查不出来才回头换表」**；并把 §70 的表述强度从「一个字段」升级为「一整类」。

**同族**：§16（否定结论分轮登记）/ §41（注释与代码都不是契约，架构取舍同样不是）/
§46（尺子不对结论必错）/ §59（尺子错的两种形态）/ §70（查错出口）。


### §72 把「死代码」和「死代码所服务的对象」分开验 —— 前者只证明「没人调」，后者才决定「危害多大」

**由来**（R89-CP / 180 号）：139 号以「函数存在但永不被调用」定了 P3，
理由是「会让人误以为该表有月度归档」。**但本轮量到那 8 个
`promote_*_default_batch` 函数服务的 `_default` 分区合计 0 行**
⇒ **「有归档」这个误判连落脚的地面都没有** ⇒ 危害远小于 139 号的表述。

**⇒ 落地三条：**
1. **「N 个死函数」本身不是定级依据** —— 定级要看**它们本该服务的那个对象**：
   对象有数据 ⇒ 死函数是**真缺口**；对象本身是空的/不存在的 ⇒ 死函数是**纯噪音**；
2. **⚠️ 差集类结论必须两段做**：先求「声明 vs 消费」差集（本轮：29 vs 20），
   **再对差集里的每一项追一层「它服务的对象是否存在 / 有数据」** ——
   **只看第一段会把噪音当缺口**；
3. **「没人调」有四种形态**：Go 代码 / 非 Go 文本 / SQL 侧 trigger·rule·事件触发器 /

### §73 「某列全 NULL」先分「没人写」与「写了但失败」—— 两者的判别数据不在同一张表里

**由来**（R89-CQ / 181 号）：`system_probe_runs` 的 `request_url` / `err_detail` /

- `credential_selfcheck.go:850` 的 INSERT **确实不写这些列**（这半成立）；
- 而 `systemmonitor/audit.go:121` **确实要写**（还多写一个不存在的 `total_tokens`），
  **但它必然失败**（这半是「写了但没成功」）。

**⇒ 落地三条：**
1. **「列全 NULL」有两种机制，判别数据不在那张表里** ——
   「没人写」要查**各写入方的列清单**（本轮两个写入方一列一列比对才看得出来）；
   「写了但失败」要查**台账 / id 段 / 非空计数**（本轮 `http_status` 非空 = 0 是决定性的）。
   ⚠️ **只查「有没有写入方提到这个列名」会漏掉第二类** ——
   **「提到了」不等于「成功写进去了」**；
2. **⚠️ 一个 SQL 里有多个错位时，第一个错位会掩盖后面所有错位** ——
   本轮 `total_tokens`（不存在）掩盖了 `$16 extrasJSON → response_body_preview` 的传参错位。
   ⇒ **修第一个之前，不要宣称「只错了一处」**（§70 同族：
   **要问「修好第一个之后，第二个会立刻显形吗」**）；
3. **⚠️ 迁移「未执行」有三种形态，判定方式完全不同**：

   | 形态 | 例子 | 危险度 |
   |---|---|---|
   | `.skip` 后缀 | `startup/336_….sql.bak.skip`（180 号） | 低（人眼可见） |
   | **版本号被同号文件占用** | `domain/346` vs `startup/346`（本轮） | **高（文件完全正常）** |
   | 目录不被执行器扫描 | `sql/migrations/domain/`（本轮） | 中 |

   ⇒ **判「某迁移是否执行过」必须三方对齐：文件名 + `schema_migrations.version` +
   `schema_migrations.description`。**
   ⚠️ **只查 `version` 存在与否会得到「已执行」的错误结论**
   （本轮 346 就在台账里，只是描述对不上）。

**⇒ 判定「唯一阻断点」的手法（本轮用的是它）**：
把**同一条 INSERT 逐列做差集**（去掉可疑列再插一次）——
**成功 ⇒ 该列是唯一阻断点，修法可精确到一个列名，不必动表结构以外的任何东西。**
⚠️ **本轮在这步踩了个类型坑**：`task_id` 是 `bigint` 不是 `text`，

**若就此收手，就会把「类型错」当成「列缺失」的证据**（两者报错行不同、原因不同）。
⇒ **试插报错时先确认报的是不是你想验的那一条**（§10：读包围/读原文，不靠猜）。

**⇒ 与 180 号 §72 的关系**：§72 说「死代码还要看它服务的对象」；
**本条说「死写入方还要看它是『没被调用』还是『被调用但失败』——

### §77 判断「文件在应用后是否被改过」要用 git 提交历史，不要用 mtime —— checkout 会把所有 mtime 刷成同一天

**由来**（R89-CU / 185 号）：本轮第一遍用文件 mtime，得到
「70 条跨度 08-25→10-01、几乎全可疑」—— **这个结论等于没判**，
因为本仓库是 10-01 拉取的，**mtime 反映的是写入工作树的时间，不是内容改动时间**。
换 `git log --reverse` vs `git log -1` 后才得到可用结论：**11/70 被改过**。

**⇒ 落地三条：**
1. **「文件是否被改过」的权威判据是版本历史，不是文件时间戳** ——
   ```bash
   git log --reverse --format=%as -- <path>   # 首次提交日
   git log -1          --format=%as -- <path> # 最近提交日
   # 两者不等 ⇒ 内容被改过
   ```
   ⚠️ **clone/checkout 会把 mtime 全部刷成 checkout 时间**
   ⇒ **mtime 在 CI、在同事机器、在容器里都不成立**（§59 的形态 B，同一个根）；
2. **⚠️ 「建议修法」里带前提的条件，必须在推荐之前把前提验掉** ——
   184 号写「补录前必须人工核对这 70 个文件没被改过」，
   **本轮验了，结论是 11 个改过 ⇒ 推荐方案 A 直接不可用**。
   ⇒ **把前提留在报告里当「注意事项」，等于把风险转移给读者。**
   ⚠️ **本会话已发生两次**：
   ① 181 号的「根因」被 182 号推翻；② 184 号的「修法 A」被 185 号证伪 ——
   **两次都是「方向看起来对、但少验了一层」。**
3. **⚠️ 「重放迁移」的危险不只在重复执行，还在「重放的不是当初那版」** ——
   本轮发现 11 条已改过 ⇒ **方案 C（删台账重放）的危害比原先写的大一档**。

**⇒ 报告写法的一条纪律**：
**推荐动作时写成「A′：先做可验证的那部分，把不可验证的单独摘出来」** ——
本轮据此把「补录 70 条」改成「**补录 59 条 + 11 条人工裁决**」，
**而不是因为 11 条有问题就否掉整个方案**（否则会因噎废食，同样是坏结论）。

**⇒ 与既有条目的关系**：
§74/§75 说「先确认键、再确认机制会做什么」；
**本条说「推荐动作之前，先把动作成立的前提验掉」——
一个带未验前提的推荐，在报告里和已验证的推荐读起来一模一样。**

**同族**：§33（双向证据）/ §37（四维评估）/ §41（注释三桶）/ §45（命中 ≠ 引用）/
§59（尺子错的形态 B）/ §74（撞车归因）/ §75（尺子要先量）/ §76（缺校验 vs 校验会拒绝）。

### §79 读到一个「已发生的事故」注释，先问「它现在还成立吗」，再去问「当时造成了什么」—— 顺序反了会先入为主

   **先核当前真库状态**（本轮：`update_session_summary` 已是修好的 `::numeric` 版本）
   **再决定要不要去查历史后果**；
   ⚠️ **若当前已修好，历史后果多半也被后续修复抹平了** ——
   **拿现在去推过去，会把「当时有洞」读成「现在还在漏」**；
2. **⚠️ 查「数据有没有丢」必须设对照组，且对照组要和实验组只差一个变量** ——
   本轮实验组 = 「有 ≥10000 行的会话」、对照组 = 「只有 <10000 行的会话」，
   **两侧都是「有 `gw_session_id` 的会话」** ⇒ **唯一变量就是 token 大小**。
   ⚠️ **若不设对照组，973 这个绝对数会被读成「丢了 973 个会话」** ——
   **而真实背景是 59.99% 的小上下文会话本来就没有汇总**（§61 的绝对值陷阱）；
3. **⚠️ 证伪之后要说清「机制仍成立、数据结论已否」是两件事** ——
   **563 的 `DECIMAL(10,6)` 溢出机制是真的**（3.04% 的行确实在阈值之上），
   **但「因此丢了数据」已被否证** ⇒ **两个结论必须分栏写**，
   **否则会被读成「整个问题都不存在」**（§33 的双向要求）。

**⇒ 附一条纪律（本轮现学的）**：
**当你在报告里写「这一步是相容的解释，登记为待下一轮」——
如果判别维度是现成可查的，就当场查掉，不要留。**
本轮「平均轮次」一条 SQL 就把「相容的解释」变成了「已证实的机制」
（1.02 轮 vs 4.59 轮，**覆盖率差异由轮次数解释，与 token 大小无关**）。
**⇒ 「待下一轮」的成本是读者会以为这件事已经定了。**

**⇒ 与 §78 的关系**：
§78 说「跨轮引用数字前先对齐口径」；
**本条说「读到一个现成的事故叙述时，先验它现在还成不成立，再决定要不要顺着它查」——
注释里的事故叙述自带很强的说服力，最容易让人跳过第一步。**

**同族**：§16（否定结论分轮登记）/ §33（双向证据）/ §41（注释三桶，「注释宣告的历史 ≠ 当前状态」）/
§45（命中 ≠ 引用）/ §61（单侧分布要配对照）/ §71 / §75 / §76 / §77 / §78。


### §80 「覆盖率极低」先查分母里有多少是该被排除的流量 —— 0.09% 与 100% 只差一个正确的分母

**由来**（R89-CX / 188 号）：`auto_route_selections` 1,747 行 vs `request_logs` 1,907,827 行
= **0.09%**，第一反应是「auto 路由几乎没生效」。
**但分母里 1,208,778 行是 `probe_triggered`、697,310 行 `task_type` 为空
—— 两者都是 167 号早已定性的主动节点探测流量。**
**剔除后真实业务请求 = 1,746 ⇒ 覆盖率 = 100%。**

**⇒ 落地三条：**
1. **算覆盖率之前，先把分母按「该不该被计入」拆开** ——
   本仓的探测流量占 `request_logs` 行数的 **72.8%**（167 号），
   **任何以 `request_logs` 为分母的比例，不先剔除它就是错的**；
2. **⚠️ 「X 只有 N 条」这句话，必须配一句「同期该有的量级是多少」** ——
   本轮若只写「1,747 条」会读成「太少」；
   **写「真实业务同期只有 1,746 条，覆盖率 100%」才是同一组数据的正确表述**（§59 的绝对值陷阱）；
3. **⚠️ 成簇的数据分布要先问「本来就成簇吗」** ——
   本轮先假设「连续流量中间断了 33 小时」（150 号的读法），
   **逐小时展开才发现是 4 段各自独立的簇** ⇒
   **分桶粒度选错，会把「本来就少」读成「中途丢了」**（§35 的粒度纪律）。

**⇒ 与既有条目的关系**：
§61 说「单侧分布要配对照」；
**本条说「配对照之前先确认对照组没被污染流量稀释」——
分母里混入 72.8% 的非业务流量时，对照组与实验组会一起失真。**

**⇒ 附一条（187/188 两轮现学的）**：
**把两个不同定义的成功率相除，得到的方向性结论要降级表述。**
本轮 `auto_route_selections.success=26.8%` vs `request_logs.error_kind 为空=8.0%`
⇒ **可以说「看不出 auto 路由拉低了成功率」，不能说「auto 路由把成功率提升了 3.35 倍」**
—— **两个 success 字段定义不同、且两个集合不是同一批请求。**

**同族**：§33（双向证据）/ §35（阈值与粒度来自对象自身）/ §37（四维评估）/
§59（尺子错的两种形态）/ §61（配对照）/ §63（「没有 X」的两种读法）/ §71 / §75 / §79。


### §81 找出一个「唯一的异常行」时，先问「它的同类有几个」—— 样本量为 1 时，任何统计与归因都不成立

**由来**（R89-CY / 189 号）：`auto_route_selections` 里恰好 1 行 `tenant_id` 为空、`success` 为 NULL。
它同时踩中两个「唯一」，非常像一条有故事的坏数据。

**⇒ 落地四条：**
1. **「唯一的异常行」几乎总是「没有对照组」** ——
   本轮真正的对照组是**同一时间窗内的另外 60+ 行**（全部正常）
   ⇒ **有对照组才能说「孤例」，没有对照组只能说「异常」**；
2. **⚠️ 样本量为 1 时不要做分组统计** ——
   硬答会得到一个 n=1 的百分比，然后被当成结论引用（§10.1 的量化纪律）；
3. **⚠️「唯一的异常行」里，「唯一」这个性质本身要先统计验证** ——
   本轮初稿写「该行是全表唯一一条 `task_type='agent'`」，
   **那是我用带 `LIMIT 1` 的查询看单行时顺手推断的**；
   补统计才发现 `agent` 有 **81 行**（`request_logs` 侧 80 行）
   ⇒ **「我只看到一行」与「全表只有一行」是两回事**（§45 的又一次印证）。
   ⚠️ **具体触发点：用 `LIMIT 1` 取详情后，没有回头做一次不带 LIMIT 的 `count(*)`。**
4. **⚠️ 「一列全空」先找注释里的设计声明** ——
   `routing_source` 1,747 行全空，本轮差点报「死列」，
   **读到「仅在 `role_route` 命中时映射」才知道那是设计**（§41 桶②）。

**⇒ 与 §80 的关系**：
§80 说「先拆分母」（解决「比例算错」）；
**本条说「先看同类有几个」（解决「孤例被当成系统性缺陷」）。**

**同族**：§10.1（量化结论自己数一遍）/ §16 / §33 / §41（注释三桶）/ §45（命中 ≠ 引用）/
§59 / §61（配对照）/ §63 / §71 / §75 / §79 / §80。


### §82 「某个字段全空/全假」先查它是**什么时候**被写的 —— 事后回填的字段，空值往往不是「没发生」，而是「按设计没发生」

**由来**（R89-CZ / 190 号）：`success` 只有 1 行是 NULL、`reward` 只有 1 行是 NULL。
**我原本准备把它当成一条「坏数据」继续追**，直到读到
`// Outcome fields are deliberately absent: they are backfilled later by AutoRouteSettleWorker`
—— **它根本不是写入时就有的字段**，而空值对应的是一条**明确的降级路径**（`abandon`）。

**⇒ 落地三条：**
1. **查「某字段为什么空」之前，先查它是写入时填的还是事后回填的** ——
   **事后回填的字段，它的 NULL 往往对应一条显式的降级分支，而不是写入失败**；
   本轮那条分支在 `settle_worker.go:433-441`，且注释写明了设计意图；
2. **⚠️ 降级分支被正确触发 ≠ 上游问题已解决** ——
   **本轮查清的是「网关侧对它的处理是对的」，未查清的是「它是怎么坏的」**
   ⇒ **两者必须分栏写**，否则读者会以为问题已经关闭；
3. **⚠️ 「某字段只有 1 行为空」要和「哪些字段同时为空」一起看** ——
   本轮 `success IS NULL` 与 `reward IS NULL` **恰好都是那同一行**，
   而 `abandon()` 的代码正好只写 `settled_at`+`reward_source`、不写这两个
   ⇒ **多个字段同时为空，是「同一条代码路径」的最强指纹**
   （比逐个字段单独查快得多，§63「先数写方」的变体）。

**⇒ 与 §81 的关系**：
§81 说「先问同类有几个」（**告诉你有多少**）；
**本条说「再问清它的写入时机」**（**告诉你为什么**）——
**缺后者就会把设计当缺陷。**

**同族**：§33（双向证据）/ §41（注释三桶）/ §45 / §59 / §61 / §63（先数写方）/
§71 / §75 / §79 / §80 / §81。


### §83 在 Citus / 分区父表上跑 `count(*)` 之前，先逐分区数一遍 —— 父表聚合会把同一个数放大三个数量级

**由来**（R89-DA / 191 号）：`SELECT count(*) FROM request_wal WHERE status='pending'` = **666,046**，
逐分区数只有 **515（hot）+ 5（月分区各 1）= 520**。**差 1280 倍。**
**若直接写进报告，就是一条凭空出现的 P1「数据积压」。**

**⇒ 落地三条：**
1. **分区父表上的 `count(*)` / `sum()` 必须先与逐分区统计对账** ——
   本仓是 **Citus 13.3 + citus_columnar**，父表聚合会重复计数；
   ```sql
   SELECT count(*) FROM <parent> WHERE …;        -- 666,046
   SELECT count(*) FROM <parent>_hot WHERE …;    -- 515
   -- 逐分区
   SELECT c.relname, count(*) FROM pg_inherits i
     JOIN pg_class c ON c.oid = i.inhrelid
     JOIN pg_class p ON p.oid = i.inhparent
     JOIN pg_namespace n ON n.oid = p.relnamespace
    WHERE n.nspname='public' AND p.relname='request_wal' GROUP BY 1;
   ```
   ⚠️ **本会话已因此算错 4 次**（`request_logs` 时间列、分区归属的 `regexp_match`、Citus 父表聚合…）
   ⇒ **这是本仓的高频陷阱，不是偶发**（§59 的高频形态）；
2. **⚠️ 「数据没落库」要先问「它卡在哪张表」再问「为什么没往下走」** ——
   本轮先查 `request_logs`（0 行）就以为「没落库」，
   **改问「经过了哪些表」才发现它在 WAL 里躺着，且状态是 `pending`**；
   ⇒ **「查不到」常常是「查错了表」，而那张表正在告诉你它停在哪一步**（§70 的表亲形态）；
3. **⚠️ 读到「intended behavior」时，把它拆成「设计」与「代价」两栏** ——
   本轮这条设计是**故意的**，但代价是**该请求永久停在 `pending`**，
   **且下游两处（`request_logs` 缺行、auto_route 走 abandon）都是它的表现**
   ⇒ **只写「符合设计」会漏掉代价，只写「有代价」会误报缺陷**（§37 的四维在单条记录上的应用）。

**⇒ 与 §82 的关系**：
§82 说「先问字段是写入时填的还是事后回填的」；
**本条说「先问这条记录停在哪张表、哪个状态」——
两者都是在问「它在流程的哪一步」，只是一个在字段层、一个在记录层。**

**同族**：§33 / §41（注释三桶）/ §45 / §59（尺子错的两种形态）/ §61 / §63 / §70 /
§71 / §75 / §79 / §80 / §81 / §82。


### §84 看到「intended behavior / 静默丢弃」的注释时，先问「丢的是哪一侧」—— 一个已知盲点被修一半，比完全没修更难发现

**由来**（R89-DB / 192 号）：`request_logger.go` 注释写「Late updates after migration are
**silently dropped, which is the intended behavior**」。
**单条看确实符合设计；但 191 号顺着它找到的那条记录只是冰山一角，
本轮一量就是 66.6 万条 —— 其中 40.3 万对应 171 号早就报过的限流事件。**

**⇒ 落地三条：**
1. **「单条符合设计」不能推广到「这类都符合设计」** ——
   191 号在单条上验证了机制，**但没问「有多少条走在这条路径上」**；
   ⚠️ **规模一出来，性质就可能变**（P3 单点 → P2 规模）；
2. **⚠️ 看到一个已识别的盲点被修复时，要数「它覆盖了几个出口」** ——
   本轮 `handler.go:8110` 的注释说明 2026-08-26 已修「限流早退不落 `request_logs`」，
   **但同一事件还要写 `request_wal`，那一侧没修**
   ⇒ **「`request_logs` 里有行」不等于「这个事件的记录是完整的」**（§71 的出口分工，换方向用）；
3. **⚠️ 「一个字段有值、配套字段全空」是最强的路径指纹** ——
   本轮 66.6 万行 **`client_model` 100% 有值而 `completed_at` 0.02% 有值**，
   **一眼就说明「终态 UPDATE 丢了」**；
   ⇒ **遇到大批「半成品」记录，先找那个「有值」与「空值」的分界**，
   **它直接告诉你流程停在哪一步**（§82 的字段层 + §83 的记录层，合起来用）。

**⇒ 与既有条目的关系**：
§82 问「字段什么时候写的」、§83 问「记录停在哪张表」；
**本条问「同一个事件有几个出口，哪些被修了」——
前两条定位单点，本条防止把「修了一半」读成「已经修好」。**

**同族**：§33 / §41（注释三桶，「intended behavior」也要问覆盖面）/ §45 / §59 / §61 /
§70 / §71（出口分工）/ §75 / §79 / §80 / §81 / §82 / §83。
