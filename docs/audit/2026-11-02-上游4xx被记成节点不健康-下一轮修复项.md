## 一、事实链（2026-11-02 生产日志逐环可查）

事故本体（外部客户端把 embedding 模型名塞进 `POST /v1/chat/completions`）：

```
routing_resolve  client_model=qwen3-embedding:0.6b request_modality=text
                 top_credential_id=99005 top_raw_model=qwen3-embedding:0.6b
upstream_call_starting upstream_url=http://192.168.31.30:11434/v1/chat/completions
upstream_http_attempt   upstream_status=400   ×3（17:56:29 / 17:56:34 / 17:56:45）
ERROR executor failed    error="all 0 candidates failed"
ERROR http_request       status=503  response_bytes=315
```

⇒ **上游回的是 4xx（请求侧错误）**，但网关把它当成「这个节点不健康」处理：
盲重试三次、把 (凭据,模型) 绑定翻红（`avail=false`，5 分钟冷却）、把探针
队列行按 `http_400` 退避到 **6 小时**（`next_run_at=+6h`）。

⇒ 后果不是这一条请求失败，而是**连坐**：

```
WARN router: URSM v2 authoritative view filtered out every candidate
     view_sample="[prov=19 cred=99005 model=qwen3-embedding:0.6b avail=false]"
WARN [candidate_diag] db_empty model=qwen3-embedding:0.6b
     cache_key=qwen3-embedding:0.6b|default|modality:embedding plan_count=0
ERROR http_request path=/v1/embeddings status=503
```

⇒ **`/v1/embeddings` 对所有租户 503**（该凭据上所有绑定同时不可路由）。

## 三、下一轮要做的事

### ① 4xx（请求侧错误）不得进入「节点不健康」阶梯

现状：上游 4xx ⇒ 重试三次 ⇒ 绑定翻红 ⇒ 探针退避 6 小时 ⇒ 候选池清空。

目标：上游 4xx 归入**请求侧错误**（`client_bug` / `param_rejected` 族），
只影响**这一对 (凭据,模型)** 的本次请求，**不**：

- 把凭据推入 `availability_state=cooling`；
- 把绑定翻红（`credential_model_bindings.available=FALSE`）；
- 把探针队列行按 6 小时退避（那把「等一小时再试」的探针变成盲区）。

仓内已有同族的既有结论与工具：

- `errorsx/stream_unwrap.go`：已经记录过这条事故记述——
  「请求侧参数错误被当成节点故障，盲重试三连 502，node_probe_state 记 3 连败
  + 300s 退避，随后整个模型候选清空（candidate db_empty），健康节点被停
  5 分钟」⇒ 仓库里**已经有**「按内层状态码/错误体重新分类」的能力
  （`client_bug` / `param_rejected` 族），本轮只是**没有覆盖 4xx 这条路**。
- `bg/node_probe.go` 的 `isGatewaySideProbeError` 与
  `credentialSpecificDecryptFailure`：已经有「不是节点问题 ⇒ 不写可用性」
  的先例，本轮可照抄形状。

### ② 失败归因粒度：按 (凭据,模型) 而不是凭据级

`v_routable_credential_models.is_routable` 的门槛含
`c.availability_state='ready'` ⇒ **凭据级**一次失败 ⇒ 该凭据上**所有**模型
一起不可路由 ⇒ 一个租户的坏请求影响全部租户。

目标：把「这条 (凭据,模型) 对此刻不可用」与「这个凭据整体不可用」分开；
凭据级冷却只留给**凭据级**证据（鉴权失败、余额不足、端点不可达）。

### ③ 落地纪律

- 改动在**请求热路径**上 ⇒ 单独一轮、完整回归（`./domains/streaming/...`
  72s+、`./bg` 36s+、外加本包锁步门全绿），不与别的改动混做。
- 验收口径（三条都要有证据，不能只跑通）：
  1. 上游 4xx 的请求**仍然失败**（语义不变），但**不再**改写凭据/绑定状态；
  2. 同一时刻该凭据上**其它**模型仍可路由（不再连坐）；
  3. 探针队列行**不出现** 6 小时退避（该退避只留给「模型确实没被上游提供」，
     例如 404 `model_not_served`）。
- 既有属主裁决（2026-10-17）「推理不是 assistant 答案 ⇒ 必须 failover」
  与 `internal/emptyoutcome` 的语义**不动**：本条只改**归因与阶梯**，
  不改「什么算失败」。

## 五、实施记录（2026-11-02 第三轮）

### 5.1 重新取证：真正的放大器入口不是探针写红 binding

实施前把整条链逐环读了一遍（只读取证），结论与 §二 的登记**不同**：

| 环 | 位置 | 是否「断链」 |
|---|---|---|
| 上游 400（正文不匹配任何形态正则） | `errorsx/classify.go` → `ClassifyResponseStatus` default ⇒ `KindTransient` | **未断**（分类层） |
| 同节点盲重试 ×3 | `executor_chat.go` attempt 梯子（`IsRetryable(KindTransient)=true`） | **未断** |
| 写 `node_probe_state`（该对被拉黑 5 分钟） | `executor.go` `transientSuppressErrorCode` → `recordTransientDispatchFailure` | **未断**（放大器 #1；它连 HTTP 状态码都不看，把 400 记成了 `http_5xx`） |
| 3 连败 ⇒ **整个凭据** cooling（其下全部 binding、全部租户） | `domains/nodehealth/reducer.go` → `domains/credential/writer.go` | **未断**（放大器 #2） |
| 探针再打一次 400 ⇒ `root_cause=protocol` ⇒ 退避 6h | `bg/` 侧（`probe_http_400` 写 binding、`probeBackoffForDirectOutcome` 停 6h） | bg 侧，与请求路径是两套机制 |

⇒ **事故里那 3 次盲重试（17:56:29/34/45）刚好凑满 3 连败阈值** ⇒
一条客户端错单 ⇒ 整凭据 cooling ⇒ `/v1/embeddings` 对所有租户 503。
⇒ 「探针把 binding 写红」只是**同一次事故的另一半**，且它带可区分的
reason 前缀（`probe_http_400`），不是把整凭据摘掉的那一跳。

### 5.2 实施口径

1. **新增独立 kind `errorsx.KindRequestRejected`（"request_rejected"）**
   —— 上游回了 4xx，而错误体里**没有**任何模型级/凭据级/配额级/限流级/
   上下文级/审核级裁决 ⇒ 归「请求侧错误」。
   分类点：`errorsx/classify.go` 的 `ClassifyErrorWithBody` **状态兜底**处
   （400 / 413 / 422），位置在**所有**正文正则之后 ⇒ 只补空白，不抢既有裁决。
2. **归责**：`PenaltyOf(KindRequestRejected) = PenaltyNone`
   ⇒ 凭据不冷却、熔断不计数、绑定不翻红、URSM 不记失败。
3. **动作**：`DecideNextAction` 新分支 ⇒ `ActionSwitchNode`
   ——**不盲重试同一节点**（同 body 必然再败）、**不扇出探针**，
   但**允许换一个兄弟候选**。
4. **判据入口收敛**：`errorsx.IsRequestSideError(kind)`
   = `IsClientBug(kind) || kind == KindRequestRejected`
   —— 所有「共享节点健康状态写入」的闸门（凭据冷却 / 熔断 / 绑定翻红 /
   URSM / 探针扇出 / 路由节点失败样本 / bg 质量样本）统一问它。
   `IsClientBug` 本身**不动**（它还管「上游正文是否原样透传给客户端」，
   那是客户端体验问题，与归因分开）。
5. **闭集登记**（漏登记 ⇒ 静默退化，本轮逐处补齐并各有行为测试钉死）：
   - `domains/dispatch/planner.go` `isCentralPolicyKind`
     —— 漏登记会被**重写**成 `KindTransient`（放大器原样回来）；
   - `domains/streaming/attempt_outcome.go` `taskActionForKind`
     —— 漏登记 ⇒ `unmapped_kind:` ⇒ FailClosed；
   - `domains/streaming/executors/executor_nodehealth.go` `nodeHealthErrorKind`
     —— ⇒ `ErrorKindRequest` ⇒ reducer 直接返回 nil effects
     （不写状态、**且不累计 consecutive_failures**）；
   - `domains/credentialstate/manager.go` `UpdateOnFailure` 早退；
   - `domains/streaming/executors/route_node_recorder.go`、
     `domains/streaming/executors/executor_dispatch.go`、
     `credentialhealth/checker.go`、`domains/credential/writer.go`。

### 5.3 与计划稿的差异（逐条说明理由）

| 计划稿（§三） | 实际实施 | 理由 |
|---|---|---|
| ① 4xx 归入「client_bug / param_rejected 族」 | **新增独立 kind**，不复用 `KindClientBug` | `KindClientBug` 在 `terminalActionKind` 里 ⇒ 终态失败 ⇒ **放弃跨凭据故障转移**。211 生产实测：943 个在册模型里 **577 个只有 1 个凭据，但 366 个由 ≥2 个凭据服务、198 个由 ≥4 个服务** ⇒ 400 可能是**这一把钥匙**的权限/档位问题，兄弟凭据能服务同一个模型。复用 client_bug 会把可用性一起关掉。 |
| ② 失败归因粒度改成按 (凭据,模型) | **未改 schema**；改为「请求侧错误根本不写任何共享状态」 | 目标（一次坏请求不得连坐其它模型/租户）用「不写共享状态」达成，且不动 schema/迁移面。凭据级证据（鉴权/配额）仍走凭据级冷却——那条是有凭据级证据的。 |
| ③ 验收口径 3：探针队列行不出现 6 小时退避 | **未改探针侧退避策略**；请求侧不再产生这类行 | 6 小时退避来自 `probeBackoffForDirectOutcome` 的 **protocol 根因**分支，而 protocol 根因本身是**正确**的：探针发的是规范请求，被拒说明「这一对 + 这一形态」不合（重探测治不好，只有改配置）。事故里的病根是**探针形态用错**（已于当轮第一轮修好）。改退避策略会重新打开「协议不匹配对被反复探测」的 churn。请求侧不再入队 ⇒ 验收口径 3 由「不产生该行」满足。 |
| ① 不盲重试 | **已断**（`IsRetryable` 不含新 kind ⇒ executor 不再构造 `retryableError`） | 连带效果：`domains/streaming/executors/reqprobe_integration_test.go` 的 `TestExecuteOpenAIReqProbeStripFailsStillErrors` 调用序列由 3 次变 2 次——去掉的那次正是「同节点盲重试」，是本轮要消除的行为。 |

### 5.4 新发现的观察（**未修**，登记）

1. **上游用 4xx 报限流时没有正文级规则**：仓内对限流**只认状态码 429**
   （`ClassifyResponseStatus`），没有任何正文规则。于是
   `HTTP 400 + {"error":{"message":"rate limit exceeded"}}` 此前落
   `KindTransient`（默认兜底，**偶然**），本轮起落 `KindRequestRejected`。
   ⇒ 若要精确归因，需新增一条正文规则映射到 `KindRateLimit`；
   本轮**刻意不加**——正文正则有误伤风险，而「不惩罚节点」是更保守的方向
   （过度冷却正是本次事故的成因）。
2. **`errorsx.DecideFailover` 与 `ActionDecision.EnqueueProbe` 是死代码**
   （前者只在 errorsx 包内被测；后者全仓无消费方）。本轮仍按同口径维护
   了它们的分支，防止将来接线时把老口径带回来。
3. **`ClassifyResponseBody` 的兜底是 `""`（body-only 分类器）**，
   与 `ClassifyErrorWithBody` 的状态兜底**不是同一层语义**，不构成口径
   分裂：两个调用方都只取 model_not_found/model_deprecated，权威 kind 来自
   `ClassifyErrorWithBody`。本轮不动它。

**三条验收口径的实测结果**：

| 口径 | 实测 | 判定 |
|---|---|---|
| ① 请求仍然失败，但不改写凭据/绑定状态 | 客户端仍得 **HTTP 502** `All embedding providers failed`（与改动前**逐字节同形** ⇒ 语义不变）；`node_probe_state` 行**逐字段未变**（`last_direct_ok=t` / `consecutive_failures=0` / `next_retry_at` 未推后）；`credentials` 行 `availability_state=ready` / `state_updated_at` 未变 | ✅ |

新旧两个 kind 都是 502。⇒ 本轮只改**归因**，不改「什么算失败」。

### 7.2 缺口一：404 的**绑定级**处置（§六.7 的「唯一已知代价」）

§六.5 的结论是硬的：裸 404 只有两种读法，而**两种都排除 transient**：

- 「这个账号/部署里没有这个模型」⇒ 这一对 (凭据,模型) 不可用；
- 「这个凭据的端点路径配错了」⇒ 这一对 (凭据,模型) 不可用。

两种读法的正确处置**都在绑定级**（只冷却这一对，不动账号）。
而处置矩阵此前**缺这一档**——裸 404 只能落请求侧（什么都不写）或节点侧
（罚节点 ⇒ 3 连败整凭据 cooling ⇒ 全租户 503，事故本体）。

**本轮落地**：新增独立 kind `errorsx.KindModelUnavailable`（"model_unavailable"），
作为**第三类处置**补进矩阵：

| 处置 | 证据指向 | 写什么 | 跨凭据转移 | 熔断/账号冷却 |
|---|---|---|---|---|
| 请求侧 `request_rejected` | 这次请求 | **什么都不写** | 保留 | 无 |
| **绑定级 `model_unavailable`（新）** | **这一对** | **只写这一对的冷却** | **保留** | **无** |
| 节点/凭据级 `transient`/`auth`/… | 节点/账号 | 罚节点/账号 | 视 kind | 有 |

失败 ⇒ **放弃跨凭据故障转移**。而 404 可能是**这一把钥匙**的权限/档位
问题，兄弟凭据能服务同一个模型（211 实测：943 个在册模型里 366 个由 ≥2 个
凭据服务、198 个由 ≥4 个服务）⇒ 必须保留转移。

（`PenaltyBinding` 不进账号级断路器）。断路器按 provider+credential 记账
⇒ 一次绑定级失败连坐该凭据上的**全部**模型 ⇒ 3 次即整凭据熔断 ⇒
全租户 503（事故本体）。

### 7.3 缺口二：4xx 正文形态 ⇒ 节点侧罚则（§五.4.1 / F3 的敞口）

§五.4.1 登记：「上游用 4xx 报限流时没有正文级规则」，并列出了同族审计轮
F3 的观测：`400 + "too many requests"` 落 `KindConcurrent`（**罚节点**），
而 `400 + "rate limit exceeded"` 落 `KindRequestRejected`（不罚节点）
⇒ 语义相近的两种正文得到**相反**处置。

**复核（211，45 天窗口）**：4xx 正文里含 rate limit / too many requests /
rate_limit 的行数 = **0** ⇒ 这条不一致在网**从未发生过**。

**但它是一条敞着的放大链**：并发/过载正文规则此前**没有状态门** ⇒
一个 4xx 正文只要带「too many requests / rate limit / 稍后重试 / 并发过大」
就落 `KindConcurrent` ⇒ 节点侧罚则（绑定拉黑 5 分钟 + URSM 记失败 +
credentialhealth 降级 + nodehealth 连败累计）⇒ **3 连败后整凭据 cooling**
⇒ 全租户 503。⇒ 事故的放大链换了一副正文面孔，原样回来。

**本轮落地**：并发/过载正文规则**不在请求侧状态族上生效**
（`errorsx.classify.go` 新增 `isRequestRejectionStatus`：
400/404/413/414/422）。口径依据：**状态码是上游对「这次请求」的裁决**；
4xx = 上游拒收 ⇒ 按 §三 ① 的裁决不得罚节点；429/5xx 才是容量/节点级信号，
规则**逐字不变**。

★ **与 §五.4.1 建议的方向相反，理由记实**：§五.4.1 说「若要精确归因，
需新增一条正文规则映射到 `KindRateLimit`」——那条建议**与事故教训相悖**：
`KindRateLimit` 会把 (凭据,模型) 按 `http_429` 拉黑并参与连败累计 ⇒
把放大器的两条腿放回来。本轮取**保守方向**（不惩罚节点），并让它对
**所有** 4xx 正文形态一致 ⇒ 两种正文不再分叉。

## 八、实施记录（2026-11-02 第五轮：请求热路径的模态门 —— F10 / F11）

### 8.1 本轮定位

第四轮（§七）把**探针侧**的模态权威源落地了（F25/F26/F27）。本轮做**剩下
的那一半**：**请求热路径**上的模态门（F10/F11）。

§四.1 登记的判据是「**路由与探针都必须以登记模态为准**」。第四轮只落地了
探针那一半；请求侧当时的状态是：

| 环节 | 第四轮之后的状态 |
|---|---|
| 初始候选解析 | ✅ 过模态门（`resolveCandidatesForRequest` → `GetCandidatesByModality`） |
| **dispatch 换替代模型时的候选再解析** | ❌ 无模态过滤（`GetCandidates`，$3 为空 ⇒ 全放行） |
| **同步探针恢复节点后的候选刷新** | ❌ 无模态过滤（同上） |

⇒ **模态门只管了第一段路**：请求一开始按模态选对了候选，中途换模型 / 探针
后刷新时又把别的模态的绑定请了进来。

★ 这两处都在**活路径**上（不是死代码）：

- F10 的触发条件 `SyncNoCandidateProbe` **默认开启**
  （`LLM_GATEWAY_SYNC_NO_CANDIDATE_PROBE` 未设即开，`cmd/gateway/main.go`
  两处 wiring），211 上该 env 未设 ⇒ 生产是开的；
- F11 的 dispatch pipeline **恒久接线**（`cmd/gateway/main.go:7962`），
  且 `/v1/responses` 明确带 `DispatchModelAlternatives`（auto-route 换模态
  的入口）⇒ 生产可达。

### 8.3 缺口一：F10（探针后刷新绕过了模态门）

**现场**：`domains/streaming/executors/executor.go` `refreshedCandidatesAfterProbe`
用 `e.Provider.GetCandidates(...)` 重新解析候选 ⇒ $3 为空 ⇒ 模态接受判据的
「全放行」臂 ⇒ 登记为其它模态的绑定会被塞回本次请求。

**落地**：改走新的统一入口 `Executor.resolveCandidatesByModality(ctx, model,
profile, tenantID, modality)`，模态取自 `ExecParams.RequestModality`。

★ **模态为空的语义被钉死**：空 = 「本次请求没有模态概念」⇒ 走无过滤旧路
（不误伤压缩摘要链、探针自检等没有模态概念的调用方）；非空 = 必须过门。

### 8.4 缺口二：F11（换模态路径没过门 + 三个入口根本没带模态）

F11 是**两处**缺陷，不是一处：

**① 消费侧**：`domains/streaming/executors/executor_dispatch.go`
`dispatchCandidatesForModel` 在模态为空时走无过滤的 `GetCandidates`
⇒ 换替代模型时可能选中 embedding 绑定 ⇒ 上游 400 ⇒ 绑定翻红。
（`/v1/responses` 明确带 `DispatchModelAlternatives` ⇒ 这条路径生产可达。）

**② 生产侧**：`DispatchRequestModality`（本轮改名 `RequestModality`）
**只在 `/v1/chat/completions` 被赋值**（`handler.go`）。`responses.go` /
`messages.go` / `durable_runner.go` 三处**已经**从 `resolveCandidatesForRequest`
拿到了模态，却**没有回填**进 `ExecParams` ⇒ 那三个入口的执行器拿不到模态 ⇒
即使①修好了，三条入口仍然是无模态过滤的。

⇒ 于是本轮把模态提为**执行器内唯一的权威载体**：

| 改动 | 位置 | 说明 |
|---|---|---|
| 字段改名 | `executors.ExecParams.DispatchRequestModality` → **`RequestModality`** | 名字原来只对 dispatch 成立，但它承载的是**整个请求生命周期**的模态；改名是为了让「谁在用它」不再有歧义 |
| 单一入口 | `executors.Executor.resolveCandidatesByModality` | 执行器里**每一次**候选再解析都走它 ⇒ 「给初始候选上过门的那道模态」也一定给后续候选上过门 |
| 消费侧 | `executor_dispatch.go` | 换替代模型的候选解析改走统一入口 |
| 生产侧 ×4 | `responses.go` / `messages.go` / `durable_runner.go` / `handler.go`（D5 模型级回退） | 回填 `RequestModality` |

★ **D5 模型级回退的一个额外发现**：它的候选是用 `upstreamBody` 解析的
（可能与原始 body 的模态不同，例如附件被改写），而模态原来被**直接丢掉**
（`_`）⇒ 本轮改成**取这次解析自己的返回值**（`fbModality`），而不是外层那个
`requestModality`。否则就是「一批候选、按另一道模态去复核」。

★ **provider 过滤不了模态时怎么办**（原先没有明确口径）：**不退回无过滤的
查询**，而是拿不到候选（调用方退回**已经过模态门的那一份**）。理由：无过滤
的查询正是把 embedding 绑定塞回 chat 请求的那条路 ⇒「宁可不换候选，也不换
成一个模态不对的候选」。

## 九、实施记录（2026-11-02 第六轮：F12 —— 诊断路径不再用名字推断）

### 9.1 F12 是什么

12h 审计轮 P3-12 登记：`domains/streaming/handler.go` 的诊断入口对**文本
请求**有一道**名字粗筛**（`modelname.InferModality(clientModel) == "embedding"`）
⇒ 只有「名字看着像 embedding」的模型才会去查库诊断 ⇒ 名字不含 embed 字样的
embedding 模型**永远拿不到诊断** ⇒ 客户端拿到**没有原因的 503** ⇒ 它会无限
重试，而它重试的每一个字节都注定失败。

★ 与 §四.1 的口径冲突：这条路径上**名字推断参与了判决**（决定给不给
「有原因的错误」），而 §四.1 定的口径是「路由与探针都必须以登记模态为准，
名字推断绝不参与裁决」。

### 9.2 实施前的生产取证（211）

**① 漏判面（实测，不是推断）**：登记为 embedding 的在册模型共 16 个，
`modelname.InferModality` 对其中 **4 个**返回 "text"：

| 模型 | InferModality | 在册登记模态 |
|---|---|---|
| `bge-m3` | text ❌ | embedding |
| `nemotron-3-embed-1b` | text ❌ | embedding |
| `nemotron-3.5-embed-1b` | text ❌ | embedding |
| `nemotron-3.5-embed-8b` | text ❌ | embedding |

（其余 12 个名字被认得出：`arctic-embed-l` / `nv-embed-v1` /
`doubao-embedding-*` / `qwen3-embedding*` / `text-embedding-3*` /
`llama-nemotron-embed-1b-v2`。）

**② 这四个模型名在 21 天窗口（2026-10-12 → 11-02）里贡献了 522 次注定失败的
请求**（全部按 503 答复）：

| 客户端模型 | 零候选（503） |
|---|---|
| `nemotron-3-embed-1b` | 263 |
| `nemotron-3.5-embed-1b` | 127 |
| `nemotron-3.5-embed-8b` | 132 |
| **合计** | **522** |

**③ 对照组**：同期 `qwen3-embedding:0.6b`（名字被认得出）拿到的是
**400 modality_mismatch**（3 次）⇒ 两种请求的**唯一差别就是名字**。

**④ 这条路径是热路径**：同窗口日均 **2,000–7,200 次**零候选（占全部请求的
30–50%）⇒ 「零候选 ⇒ 503 ⇒ 客户端重试」是常态，不是边角。

**⑤ 它不是放大器**：这些请求走的是**路由侧模态门**（登记模态）⇒ embedding
绑定根本没进候选 ⇒ 上游不会被调用 ⇒ 绑定不会被翻红。⇒ 本项是**错误质量**
问题（503 谎称「网关暂时没资源」，实际是「你这个请求永远成不了」），不是
连坐问题。（另核：discovery 的模态写入是**只升不降**的 ⇒ 名字推断也**不能**
把在册的 embedding 降级成 text ⇒ 权威源不会被污染。）

**⑥ 修完之后，这些请求会拿到什么**（用**生产注册表的真实状态**跑了一遍
诊断查询的三个输出）：

| 请求模型 | 登记模态 | 忽略模态过滤后可路由 | 诊断结论 | 客户端拿到 |
|---|---|---|---|---|
| `nemotron-3-embed-1b` | **embedding** | true | 不匹配 | **400 modality_mismatch**（改前是 503） |
| `glm-5.3-flash`（对照） | text | true | 接受 | **503**（与改前一致 ⇒ 无误伤） |

⇒ 修好之后，那 522 次注定失败且被劝退的请求会拿到**有原因、可据以行动**
的 400（"这个模型是 embedding 登记的，接不了 chat"），而不是"网关暂时没
资源" ⇒ 客户端不再无限重试。

### 9.3 为什么不是「给粗筛补别名」

两条理由，逐条记实：

1. **补别名治不了类**：`modelname.InferModality` 同时是 `discovery`
   **播种** `models_canonical.modality` 的来源（`discovery/discovery.go`、
   `discovery/canonical_match.go`）⇒ 让它继续猜「哪些名字是 embedding」等于
   让**权威源**继续依赖名字推断 ⇒ 与 §四.1 相反。
2. **粗筛没买到性能**：实测（211，`EXPLAIN (ANALYZE, BUFFERS)`）两条查询的
   代价几乎一样：

   | 查询 | 执行耗时 | buffers |
   |---|---|---|
   | 「查库的粗筛」（只取登记模态） | **3.34ms** | 346 |
   | 完整诊断（登记模态 + 忽略模态过滤后的可路由性） | **3.86ms** | 346+ |

   ⇒ 粗筛**没有省下任何东西**，只贡献了错误答案。

   ★ 复测（三种请求名 × 各 3 次，共 9 次）：`nemotron-3-embed-1b`（embedding
   登记）、`glm-5.3-flash`（普通文本）、`no-such-model-xyz`（不存在）——
   **9 次合计 36.7ms ⇒ 每次约 4ms，三种形态没有差别** ⇒ 零候选路径上的
   「多问一次」是**均匀的小额开销**，与请求名无关（也不与「模型是不是
   embedding」有关）⇒ 不存在「只在坏情况下才贵」的隐患。

⇒ **直接去掉粗筛**：判决权 100% 交给登记模态
（`provider.ModelModalityMismatch` 查库）。

★ **判决一个字节都没变**：判决本来就由 `ModelModalityMismatch` 计算
（登记模态 + 「忽略模态过滤后是否可路由」两件事必须同时成立），粗筛只决定
「跑不跑它」。⇒ 现在跑它的次数变多，**结论完全不变**——普通文本模型仍然
拿到「不是模态问题」⇒ 仍然走「零候选即 503」的既有路径。

### 9.4 顺带补的一道闸：判决必须关于本次请求的模态

去掉粗筛后，**文本请求也会去问 resolver** ⇒ resolver 可能报回一份**别的
模态**的判决（陈旧结果 / 串台）。若照单全收，一次文本请求可能被告知
「你的请求没有图片能力」——那比 503 更糟（把服务端的问题说成了客户端的问题）。

⇒ handler 增加一致性闸：`mismatch.RequestedModality`（规范化后）必须等于
本次请求的模态，否则忽略 ⇒ 退回「零候选即 503」。

## 十、实施记录（2026-11-02 第七轮：F-A —— 两个分类器不得在同一 (status, body) 上分叉）

### 10.1 F-A 是什么（**第一轮自己引入**的缺陷）

第一轮（§七，提交 `4fe043dc3`）给**并发/过载正文规则**加了状态门
`isRequestRejectionStatus`（400/404/413/414/422 ⇒ 不落节点侧罚则）。

★ 但那一轮**只给 `ClassifyErrorWithBody` 加了门**（该函数 1218 / 1237 行），
  **漏了 `ClassifyResponseBody`**（修前是 1682 / 1699 行的**裸规则**）
  ⇒ 这正是 LESSONS §606「修了主路径、漏了旁路」的**又一次**复发，
  而且复发在**同一轮、同一个不变量**上。

后果：同一个 (status, body) 在**两个分类器**上分叉——

| (status, body) | `ClassifyErrorWithBody` | `ClassifyResponseBody`（修前） |
|---|---|---|
| 400/404/413/414/422 + 并发/过载正文 | `KindRequestRejected` / `KindModelUnavailable`（请求侧 / 绑定级） | `KindConcurrent`（**节点侧罚则**） |

⇒ 既违反本轮「4xx 正文不得落节点侧罚则」的既定不变量，也违反仓内
「两个分类器不得在同一 (status, body) 上分叉」的纪律（V20 / R30 锁步）。

### 10.2 实测：分叉面到底有多大（全状态码 × 全语料）

★ **先对量具，再读数**：写了一个**临时**特征化程序（跑完即删、**未入库**），
  对两个分类器在 **400..599 全部状态码** × 17 条正文语料上做逐格对照，
  比对「是否落节点侧罚则」。

读数（分叉方向：**`ClassifyResponseBody` 判罚则 / `ClassifyErrorWithBody` 判非罚则**）：

| 分叉类型 | 格数 | 性质 |
|---|---|---|
| **罚则分叉** | **10** = 5 个请求侧状态（400/404/413/414/422）× 2 种并发正文形态（中/英） | ★ **F-A**，且**只有这一处** |
| 「`ClassifyResponseBody` 返回 ""（不表态）而 `ClassifyErrorWithBody` 按状态兜底」（429 ⇒ `rate_limit`、503 ⇒ `concurrent`） | 15 | **既有设计**，不是分叉：正文分类器没命中任何规则时返回空；且方向安全（正文分类器**没有**把请求推进罚则） |

⇒ 结论：F-A 成立，且它的**完整**形态就是上表第一行那 10 格。

### 10.3 修法

`errorsx/classify.go` 的 `ClassifyResponseBody` 两条并发/过载规则**逐字补门**，
与 `ClassifyErrorWithBody`（1218 / 1237 行）完全一致：

```go
if !isRequestRejectionStatus(status) && concurrentOverloadCJKRe.Match(body) { … }   // 1708 行
if !isRequestRejectionStatus(status) && concurrentOverloadRe.Match(body)    { … }   // 1728 行
```

★ 口径依据与第一轮同一条：**状态码是上游对「这次请求」的裁决**；4xx = 上游
  拒收了这次请求 ⇒ 按事故教训（§三 ①：上游 4xx 不得进入「节点不健康」阶梯）
  不得罚节点。429 / 5xx 才是容量/节点级信号，规则照旧。
★ 为什么现在补（**潜伏 ≠ 不存在**）：`ClassifyResponseBody` 的生产调用点只有
  2 处（`executor_chat.go:1673` / `executor_anthropic.go:1266`），且都只与
  `KindModelNotFound` / `KindModelDeprecated` 比较 ⇒ 今天**不**触发罚则；
  但它是**公开分类器** ⇒ 任何新调用点接上就是一条敞着的放大链
  ⇒ 门必须落在分类器里，不依赖调用点自律。

  ⇒ 那张表里每一行 404 都写着「terminal / not_recoverable」，而实际上那次
  尝试**被故障转移救回来了**（网关换兄弟凭据后成功）；
- **agent 客户端放弃**：看到 `retryable:false` 就硬失败这一轮，而**这一对
  (凭据,模型) 是绑定级、探针阶梯会自愈的**。

**先量具、再读数**：用 `DecideNextAction` **驱动真实策略**枚举
`AllErrorKinds()` 的每个 kind（上下文取「有兄弟候选 + 还有尝试预算 +
同节点重试预算 0」），对照恢复投影：

```
kind                    action           genRetr  effRetr  term
transient               switch_node      true     true     false
timeout                 switch_node      true     true     false
network                 switch_node      true     true     false
auth                    switch_node      false    false    false   ← 显式排除
request_rejected        switch_node      false    false    false   ← 显式排除

concurrent              switch_node      true     true     false
```

⇒ 三个「网关会换兄弟候选、但客户端被告知不可重试」的 kind：
`auth` / `request_rejected` / **`model_unavailable`**。前两个**既有且合理**
（凭据级不可用 ⇒ 换的是凭据不是请求；请求侧语义错误 ⇒ 重发同一请求必然
再败 ⇒ 两者客户端重试都无用）；第三个就是 **F-1**。

**修法**：把 `KindModelUnavailable` 登记进 `ProjectRecovery` 的候选故障转移
分支（与 `empty_response` / `no_available_channel` 同臂），reason =
`model_unavailable_candidate_failover`。

**口径依据（为什么它是「可重试」，而 `request_rejected` 不是）**：
**404 = 绑定级证据，不是请求侧证据** —— 它的两种读法（这个账号里没有这个
模型 / 这个凭据的端点路径配错了）都指向**这一对 (凭据,模型)**，都排除
「请求本身不合法」⇒ 客户端**重发同一个请求是有意义的**：
- 兄弟凭据可能服务同一个模型（211 实测：943 个在册模型里 366 个由 ≥2 个
  凭据服务、198 个由 ≥4 个服务）⇒ 跨凭据故障转移有实质价值；
- 绑定级冷却之后，这一对会被候选查询排除 ⇒ 下一次尝试落
  `KindNoAvailableChannel`（**本来就**是 candidate_failover ⇒ 客户端本来
  就会被告知可重试）⇒ 两者的客户端口径必须一致。

⇒ 这也正是第一轮为什么**不能**复用终态 kind `KindModelNotFound`：后者是
`fail_terminal`（没人服务这个模型，重试无用），前者是 `switch_node`
（这一对暂时不行，换个兄弟可能行）。

**★ 生产影响面 = 0（部署前改动）**：211 实测 `candidate_failure_logs` 里

### 14.3 为什么「单一 kind 字符串」表达不了

4xx 与 5xx 的「无可用后端」在**下游策略上是相反的**：

| | 4xx（中转 "No enterprise provider is available for this request path"） | 5xx（中转 "No available channel for model X under group Y"） |
|---|---|---|
| 证据指向 | **这一对 (凭据,模型)** —— 确定不提供 | **中转整体/分组** —— 暂时没有通道 |
| 归责层级 | 绑定级 | 凭据级 |
| 语义性质 | **确定性** | **瞬时** |
| 冷却该多长 | **长**（绑定级 15min） | **短**（凭据级 30s） |
| 免费档该被容忍吗 | 不该（但绑定级冷却已经把它摘出候选池 ⇒ 容忍是**无害**的） | **该**（这正是 245 free-capacity plan 的立论） |

⇒ 一个 kind 字符串**同时**要表达「要长冷却」和「要短冷却、要被容忍」⇒
  **表达不了** ⇒ 必须**按归责层级分写**。

### 16.1 F-E 是什么（外部独立复核的第 2 条）

第七轮（F-A）落地时，`errorsx/classify_dual_classifier_lockstep_test.go` 里
有 5 道门，核心是**门 1「罚则单调性」**：断言
「`ClassifyResponseBody`（正文分类器）**不得**比 `ClassifyErrorWithBody`
（状态+正文分类器）更狠」。

★ 复核发现这条门**对它自己声称的覆盖面不成立**：

- 门 1 用的是**手写的 3 项清单** `nodePenaltyKindSet()`
  （`concurrent` / `upstream_overloaded` / `rate_limit`），
  而它的注释写的是「**落节点侧罚则**的 kind 集合」⇒ **两者不一致**。
- `KindStreamTimeout`（经 `nodeHealthErrorKind` 落
  `nodehealth.ErrorKindTimeout` ⇒ `isBindingScoped=false` ⇒ **凭据级**）
  **不在**那 3 项里 ⇒ 门 1 直接跳过它。
- 而 `eofWithoutDoneRe`（截断流信号）这条正文规则**只存在于
  `ClassifyResponseBody`** ⇒ 同一个 (status, body) 在两个分类器上分叉。

⇒ 于是 **5 道门全绿**，而分叉真实存在。

### 16.2 先量：分叉有多大、方向在哪

用探针（`go test` 临时文件，跑完即删）跑 15 条语料 × 400..599 全状态码，
把两分类器的裁决差异全列出来：

| 分叉形态 | 方向 | 说明 |
|---|---|---|
| `rb=""`（正文分类器无命中） vs `wb=<状态兜底>` | **不更狠** | `ClassifyResponseBody` **没有状态兜底**（不命中就返回 `""`），而 `ClassifyErrorWithBody` 有（400/413/414/422 → `request_rejected`；404 → `model_unavailable`；其余 → `ClassifyResponseStatus`）⇒ 两个分类器**结构上**就不同 ⇒ 「相等」不是它们之间可成立的不变量 |
| `rb=stream_timeout` vs `wb=<其它>` | ★ **更狠**（在 4xx 上） | 4xx 上 `wb` 落请求侧（400/413/414/422 → `request_rejected`；405/406/409/… → `unsupported_feature`）或绑定级（404 → `model_unavailable`）⇒ 而 `rb=stream_timeout` 是**凭据级** ⇒ 正文分类器比状态分类器更狠 |
| `rb=stream_timeout` vs `wb=<凭据级>`（5xx/401/402/429/408/407…） | 同严重度 | 两侧都是凭据级，只是 kind 不同 ⇒ 不构成「更狠」 |

⇒ ⇒ **危险方向只在 4xx** ⇒ 修法就落在这里。

### 16.3 修法（3 处）

1. **给截断流规则加状态门**（`errorsx/classify.go`）：
   `if eofWithoutDoneRe.Match(body)`
   ⇒ `if eofWithoutDoneRe.Match(body) && SeverityOf(classifyStatusFallback(status)) == SeverityCredential`。
   ★ 口径：「eof without done」= **上游的流被截断**（没吐 `[DONE]`）
     ⇒ 它是**上游/节点级**故障的证据 ⇒ 只有当**状态码本身的裁决**也是
     「凭据/节点级」时，它才是节点级信号；请求侧/绑定级状态族
     （400/413/414/422、404、405 族）上它只是「上游拒收了这次请求」的
     错误描述 ⇒ 按事故教训（§三 ①：上游 4xx 不得进入「节点不健康」阶梯）
     不得罚节点。
   ★ 口径与 F-A 给并发/过载规则加门的那一条**同源**。
   ★ **配套抽取**：`ClassifyErrorWithBody` 的状态兜底 switch 原样抽成
     `classifyStatusFallback(status)`（**不抄第二份** ⇒ 不会漂移），
     两处共用 ⇒ 门判据与「状态分类器」的兜底**永远同源**。
   ★ 门不是「≥500」而是「状态兜底裁决是凭据级」：429（容量状态族）在
     兜底里落 `rate_limit`（凭据级）⇒ 截断信号在 429 上**照旧生效**
     （`errorsx/classify_test.go` 的 `TestClassifyResponseBody_ConcurrentOverload`
     钉的就是 429 这一格）。
2. **严重度判据进生产代码**（`errorsx/penalty.go`）：
   `SeverityOf(kind)` ⇒ 三档（请求侧 < 绑定级 < 凭据级）+ `IsNodeFaultPenalty(kind)`。
   ★ 它是 nodehealth 归责在 errorsx 侧的**镜像**（errorsx 无法 import
     executors / nodehealth —— 那是它们的反向依赖）。
3. **门 1 改成它自称的判据**（`errorsx/classify_dual_classifier_lockstep_test.go`）：
   从「**相等**」改成「**严重度序**」（`SeverityOf(rb) <= SeverityOf(wb)`），
   集合从手写 3 项改成 `IsNodeFaultPenalty` **推导**。
   ★ 为什么必须是严重度序而不是相等：见 §16.2 第一行 —— 两个分类器
     **结构上**就不同（一个有状态兜底、一个没有）⇒ 「相等」不成立。
     ★ 那版门禁之所以要靠「手写 3 项」才能一直绿，正是因为它用了一个
       比自己注释**更强**的判据 ⇒ 覆盖面与注释脱节 ⇒ 漏法。

### 16.4 门禁

| 门 | 位置 | 断言 |
|---|---|---|

  ——而它**正是**本条发现逃过 5 道门的直接原因。
