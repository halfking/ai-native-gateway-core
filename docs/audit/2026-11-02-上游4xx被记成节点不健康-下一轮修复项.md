## 一、事实链（2026-11-02 生产日志逐环可查）

事故本体（外部客户端把 embedding 模型名塞进 `POST /v1/chat/completions`）：

```
routing_resolve  client_model=qwen3-embedding:0.6b request_modality=text
                 top_credential_id=99005 top_raw_model=qwen3-embedding:0.6b
upstream_call_starting upstream_url=http://192.168.31.30:11434/v1/chat/completions
upstream_http_attempt   upstream_status=400   ×3（17:56:29 / 17:56:34 / 17:56:45）
ERROR executor failed    error="all 0 candidates failed"
ERROR http_request       status=503  response_bytes=315
```

⇒ **上游回的是 4xx（请求侧错误）**，但网关把它当成「这个节点不健康」处理：
盲重试三次、把 (凭据,模型) 绑定翻红（`avail=false`，5 分钟冷却）、把探针
队列行按 `http_400` 退避到 **6 小时**（`next_run_at=+6h`）。

⇒ 后果不是这一条请求失败，而是**连坐**：

```
WARN router: URSM v2 authoritative view filtered out every candidate
     view_sample="[prov=19 cred=99005 model=qwen3-embedding:0.6b avail=false]"
WARN [candidate_diag] db_empty model=qwen3-embedding:0.6b
     cache_key=qwen3-embedding:0.6b|default|modality:embedding plan_count=0
ERROR http_request path=/v1/embeddings status=503
```

⇒ **`/v1/embeddings` 对所有租户 503**（该凭据上所有绑定同时不可路由）。

## 二、本轮修了什么、没修什么

**已修（触发源）**：`13c17e182`

- 文本请求不再接受登记为 `embedding` 的模型 ⇒ 上游**根本不会被调用**
  ⇒ 绑定不会被翻红 ⇒ 别的租户不会被连坐。
- 实证（211，2026-11-02 02:41，build_seq 2935）：
  `POST /v1/chat/completions {"model":"qwen3-embedding:0.6b"}` →
  **400 `code=modality_mismatch`**；同一时间窗内该 request_id
  **零 `upstream_call_starting`**；凭据 `state_updated_at` 未变（02:04:35）。

**未修（放大器）**：本条。

## 三、下一轮要做的事

### ① 4xx（请求侧错误）不得进入「节点不健康」阶梯

现状：上游 4xx ⇒ 重试三次 ⇒ 绑定翻红 ⇒ 探针退避 6 小时 ⇒ 候选池清空。

目标：上游 4xx 归入**请求侧错误**（`client_bug` / `param_rejected` 族），
只影响**这一对 (凭据,模型)** 的本次请求，**不**：

- 把凭据推入 `availability_state=cooling`；
- 把绑定翻红（`credential_model_bindings.available=FALSE`）；
- 把探针队列行按 6 小时退避（那把「等一小时再试」的探针变成盲区）。

仓内已有同族的既有结论与工具：

- `errorsx/stream_unwrap.go`：已经记录过这条事故记述——
  「请求侧参数错误被当成节点故障，盲重试三连 502，node_probe_state 记 3 连败
  + 300s 退避，随后整个模型候选清空（candidate db_empty），健康节点被停
  5 分钟」⇒ 仓库里**已经有**「按内层状态码/错误体重新分类」的能力
  （`client_bug` / `param_rejected` 族），本轮只是**没有覆盖 4xx 这条路**。
- `bg/node_probe.go` 的 `isGatewaySideProbeError` 与
  `credentialSpecificDecryptFailure`：已经有「不是节点问题 ⇒ 不写可用性」
  的先例，本轮可照抄形状。

### ② 失败归因粒度：按 (凭据,模型) 而不是凭据级

`v_routable_credential_models.is_routable` 的门槛含
`c.availability_state='ready'` ⇒ **凭据级**一次失败 ⇒ 该凭据上**所有**模型
一起不可路由 ⇒ 一个租户的坏请求影响全部租户。

目标：把「这条 (凭据,模型) 对此刻不可用」与「这个凭据整体不可用」分开；
凭据级冷却只留给**凭据级**证据（鉴权失败、余额不足、端点不可达）。

### ③ 落地纪律

- 改动在**请求热路径**上 ⇒ 单独一轮、完整回归（`./domains/streaming/...`
  72s+、`./bg` 36s+、外加本包锁步门全绿），不与别的改动混做。
- 验收口径（三条都要有证据，不能只跑通）：
  1. 上游 4xx 的请求**仍然失败**（语义不变），但**不再**改写凭据/绑定状态；
  2. 同一时刻该凭据上**其它**模型仍可路由（不再连坐）；
  3. 探针队列行**不出现** 6 小时退避（该退避只留给「模型确实没被上游提供」，
     例如 404 `model_not_served`）。
- 既有属主裁决（2026-10-17）「推理不是 assistant 答案 ⇒ 必须 failover」
  与 `internal/emptyoutcome` 的语义**不动**：本条只改**归因与阶梯**，
  不改「什么算失败」。

## 四、附：同一轮暴露的另外两处口径差异（观察，未动）

1. **`provider_models.modality` 陈旧**：provider 19 的两条 embedding 记录
   `modality='text'`（`updated_at=2026-11-02 01:55:17`），而
   `models_canonical.modality='embedding'`（权威）。路由与探针都必须以
   **登记模态**（`models_canonical`）为准；按 `provider_models.modality` 判会
   把 embedding 模型当文本模型。
2. **部署引擎两侧的 dirty 排除集不一致**：`scripts/deploy-seamless-docker.sh`
   的部署机侧排除 `VERSION` / `version.json` / `web/public/version.json` /
   **`web/public/menu-config.json`**，目标机侧只排除前三个 ⇒ 目标机上的
   工作树会恒定带 `-dirty` 后缀（本机 `web/public/menu-config.json` 是构建
   产物，每次构建都变）。本轮**刻意不动**：该文件是共享部署引擎，且
   192.168.31.32 的自动化在用它，改动会影响对方的部署流程 ⇒ 交由该主机
   操作者一并处置。
