## 三、根因分析：DB 中 `error_kind='transient'` 的三种可能性

### 可能性 A：时序窗口问题（最可能）★★★★

**证据链：**
1. 审计档提到「glm-5.3-flash-trial 大量（15+ 笔/2h）」
2. e2242e078 修复提交时间：2026-11-13 12:48:58 +0800
3. 部署时间：未明确记录（需查询 211 部署日志）
4. DB 查询时间窗口：未明确（审计档只说「活体验证」）

**推断：**
- DB 中的 `transient` 记录很可能是 **修复部署之前**的请求
- 修复部署之后的请求才会正确归因为 `quota_permanent`
- 审计档的「遗留：LastKind→客户端响应面仍走 transient 兜底」描述可能是指**旧数据**，而非新代码行为

**验证方法：**
```sql
-- 查询 glm-5.3-flash-trial 配额错误的时间分布

    DATE_TRUNC('hour', event_at) AS hour,

WHERE client_model LIKE '%trial%'

  AND event_at > '2026-11-13 00:00:00'

```

### 可能性 B：fallback 路径问题（低概率）★

**理论场景：**
如果 `execErrTyped.LastKind` 不是 `KindQuotaPermanent`（例如被误判为其他 Kind），
`classifyUpstreamCredentialFailure` 会返回空 `credCode`：

```go
func classifyUpstreamCredentialFailure(kind errorsx.ErrorKind, upstreamStatus int) (...) {
    switch kind {
    case errorsx.KindQuotaPermanent:
        return "upstream_quota_permanent", ...
    // ...
    }
    return "", "", 0, ""  // ← 空返回
}

// handler.go:5782
if credCode != "" {  // ← 空 credCode 不进此分支
    logCtx.failAndMark(credCode, ...)
}
// 可能走了其他 fallback 路径，例如 model_not_found
```

**反驳证据：**
- 审计档明确提到「executor 归因 `[quota_permanent]`」
- 如果 executor 已经返回 `KindQuotaPermanent`，handler 不可能再误判
- 专项钉测验证了 `KindQuotaPermanent` → `"upstream_quota_permanent"` 映射正确

**但仍需确认的边界情况：**
- 是否存在 `Exhausted=true` 但 `credCode=""` 的其他路径？
- 日志中的 `X-Gateway-Last-Kind` header 是否为 `quota_permanent`？

### 可能性 C：并发写入竞态（极低概率）★

**理论场景：**
多个 goroutine 可能同时写入同一 `request_id` 的日志行，导致字段级覆盖。

**反驳证据：**
- `RequestLogContext.EmitFailure` 使用 `terminalMu` 互斥锁保护终态转换
- 即使有竞态，也应该是整行覆盖，而非字段级不一致
- DB 约束（`request_id` 主键）保证最多一行

## 四、审计档「遗留」描述的澄清

审计档 §二 F3 写道：

> **F3 活体**：glm-5.3-flash-trial 主动触发 → executor 归因 **`[quota_permanent]`**
> （修复前 request_rejected）✔。遗留：LastKind→客户端响应面仍走 transient 兜底
> （503 而非 quota 族的 502/insufficient_quota——错误传递链另一层，登记）。

### 4.1 「transient 兜底」的两种可能解读

#### 解读 1：指 DB error_kind='transient'（本调查对象）
- **不成立**：代码验证显示 `error_kind` 必定为 `"upstream_quota_permanent"`
- 如果 DB 中确实有 `transient`，则是时序窗口问题（修复前的旧数据）

#### 解读 2：指客户端响应的 HTTP 状态码（非 DB 字段）
- **可能成立**：`classifyUpstreamCredentialFailure` 返回 `http.StatusBadGateway (502)`
- 但审计档说「503 而非 502」
- 需要查看实际响应：`writeErrorJSONWithDebugProto(..., credHTTPStatus, ...)`
  其中 `credHTTPStatus` 应该是 502

### 4.2 P0-D quotaHeld 修正逻辑

handler.go:5804-5808 有 quotaHeld 特殊处理：

```go
// P0-D quotaHeld：Tried=0 + quota 族 = 未打上游的全额度耗尽。
if status, retryAfter, ok := applyQuotaHeldHTTPHeaders(w, execErrTyped.Tried, execErrTyped.LastKind, execErrTyped.RetryAfterSeconds); ok {
    credHTTPStatus = status  // ← 可能改写为 429
    debugInfo["retry_after"] = retryAfter
    debugInfo["quota_held"] = true
}
```

如果 `Tried=0`（quota_held），HTTP 状态会从 502 改写为 **429**。
但智谱 trial 配额应该 `Tried >= 1`（真实打了上游），不应该走这个分支。
