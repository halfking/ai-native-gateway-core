### 3.4 本轮实施：admin auto-route 索引端点 SQL 改写（真缺陷，已实施 + 已验证）

**根因**：端点 SQL 写成
「CTE `latest_bucket`（`GROUP BY` 取 `MAX(bucket)`）+ `JOIN` 回同一个视图」，
PG 因此**把同一批行扫两遍**：

```
EXPLAIN (ANALYZE, BUFFERS)（252 真库，2026-10-19 23:5x）
  CTE  : Parallel Append → HashAggregate，431,820 行 × 3 loops
  外层 : Parallel Append（JOIN 回同一视图），143,940 行 × 3 loops
  ⇒ Execution Time 1789 ms、Buffers shared hit=29988
```

**改写**：改成「元组 IN 子查询」——`WHERE (cmi.credential_id, cmi.raw_model, cmi.bucket) IN (SELECT … MAX(bucket) … GROUP BY credential_id, raw_model)`，
PG 只需扫一遍（HashAggregate + 半连接）：

```
Execution Time 739 ms（同一台库、同一份数据、只换写法）⇒ -59%
```

**⚠ 为什么不改成 DISTINCT ON（教科书写法）**：实测**更慢**——DISTINCT ON 让 PG 对 431,820 行做
external merge Sort，溢出 **58,944 kB** 到磁盘（`work_mem` 仅 8MB），Execution **2980 ms**，比原写法还差 67%。
⇒ 改写方向由**真库实测**决定，不由直觉决定（AGENTS.md 判据纪律第 19 条）。

**语义等价性（真库逐行对账）**：

```
old_minus_new | new_minus_old | old_rows | new_rows
             0 |             0 |     1079 |     1079
```

**等价性成立依赖三条**（已写进代码注释 + 门）：
1. **逐对**取 `MAX(bucket)`，不是全局 `MAX`（桶是稀疏的，全局最大值只落在最后一次有指标变化的桶上，典型 1~2 行，会把整个索引藏起来）；
2. `canonical_id` 过滤必须留在 **IN 子查询之外**（否则语义从「先按对取最新桶、再过滤」变成「在过滤后的行里取最新桶」）；
3. `models_canonical` 的 LEFT JOIN 位置不影响结果（按主键唯一查）。

**收益**：该端点 25.69 h 内被调 **637 次**（均值 3.1 s）⇒ 每次省 ~1.05 s ≈ **每天省约 27 分钟数据库时间**。

**门**：`admin/auto_route_index_snapshot_sql_test.go`（4 条）
—— 反向（不得出现双扫形态）/ 正向（必须用元组 IN + **逐对** GROUP BY）/ 位置（`canonical_id` 过滤必须在子查询外）/ 参数编号。
