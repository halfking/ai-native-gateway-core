七、遗留风险

R1 已修i18n 值质量棘轮（原 5 项红）

原现象：de-DE 1108>1107 / es-ES 1017>1016 / ja-JP 698>697 / zh-TW 665>664， 外加 sameAsSource.zh-TW 760>758。

归因（两棵树对拍得出）：键 sessionAnalytics.state.loadingStats 由 ba7b54c4a 以英文原文写进 6 个非英语语种，后来进入引用集 ⇒ 被计入「没翻」。 在 614b72e9c^ 与 614b72e9c 两棵树上该 4 语种数字逐条相同 ⇒ +1 非本轮引入；本轮引入的只有 sameAsSource.zh-TW +2（繁简同形词被计入）。

修法：6 语种补真译 + zh-TW 改台湾用语/排版 ⇒ 不抬基线（棘轮只许降不许升），i18n-locale-value-count.mjs 现 PASS， localeValueQuality 12/12 绿。

R6 中211 与 154/245 连的是两个不同的库

211 = Docker 内 acc-pg17@172.21.0.9； 154/245 = 172.16.2.210，且 211 宿主机到后者 5432 不可达。 ⇒ 同一时间窗下 211 的 60 个 model、154 的 447 个 model，差在数据源不在口径。

后果：跨机数字不可直接比较； 「三机统计口径一致」要成立，还需明确谁是统计口径的基准库（产品/运维裁决，本轮未擅自改指向）。

R7 中ja-JP 6 条简体残留（硬闸 0）

i18n-cjk-native-simplified-guard 在 ja-JP 报 6 条用户可见简体残留： dashboard.board.probeScopeTitle / liveTopology.ribbon.storage / settings.timezone.hint / marketPrices.refHint / priceCompare.confSuspect / priceCompare.tabPlatforms。

基线同红：本轮修复前后两棵树残留键完全一致，非本轮引入； 且日文正字与该门禁的「简体专用字表」有重叠（横/称 在日文里本就是正字）⇒ 不宜由本轮直接改文案，需门禁侧确认字表口径后由对应轮次收口。

R2 中供应商成本是「跨单位相加」

total_cost = internal_cost + external_cost（美元 + 积分）。 这是本包既有口径（ModelRanking / UserRanking 同样如此），UI 上以 $ 显示会失真。

未擅自改动 —— 改口径会影响既有排序与其它页面，属产品裁决。 若 owner 要求，需要一轮专门的「成本分列」改造。

R3 中请求级 / 会话级不可相加

模型与供应商走 model_usage_aggregates（请求级）， 用户与任务走 project_task_aggregates / user_session_aggregates（会话级）。 两者不可相加 —— 已在 UI 的 top5.scopeNote 文案里显式披露（8 语种）。

R4 低任务维度的跳转落点

仓内没有独立的任务详情路由 ⇒ 任务行跳回 /admin/session-analytics/users 并带 task 定位参数。 后续可补 /admin/session-analytics/tasks/:task 详情页。

R5 低Top5 与全量排行的排序字段不同

Top5 排序字段固定（模型按请求数、供应商按请求数、用户按 Token、任务按会话数）， 与全量排行页可切换的排序字段不同；数据同源同窗口 ⇒ 数字自洽。

R8 低共享工作区的并行在途改动

并行会话的 W2-Q2 团队预算改动（admin/team_handlers.go 等） 在审计期间一度编译不过（undefined: timeWhere）。本轮未触碰这些文件， 验证与提交一律走隔离 worktree（git worktree add --detach）⇒ 既不碰别人的在途状态， 也拿到「提交树的真实样子」。

八、通用式（本轮沉淀）

  1. 「Top N 榜单」不是「把已有列表截前 N」 —— 上游端点只给 3 条时，前端聚合出的「Top5」既不是 Top5， 数据也可能来自错误的列。维度榜必须由该维度自己的列聚合。
  2. 权限门是端点的属性，不是页面的属性 —— admin-only 端点挂到全员可见的页面，普通用户必然拿到空数据 + 403 噪音。
  3. 同一区块不要混两种缓存语义 —— 实时腿与缓存腿并排，读者无法判断数字新旧。要么统一数据源，要么标注每个卡片的来源与新鲜度。
  4. 补 i18n 键会激活此前「查不到就不查」的门禁 —— 键从「全语种缺失」变成「存在」时，占位符/死参数门禁才开始检查它。
  5. default 在 vue-i18n v9 是保留键 —— 当插值参数传进去既不显示，又会被门禁判死参数。
  6. 改菜单要连带记账 —— navCounts 的 ITEMS/PATHS/FOLDED/groupItems 四档 + 三份方案文档的数字，是「菜单真源 ↔ 文档」的闭环。
  7. 门禁红了先分清「谁引入的」 —— git stash push -u 隔离到基线复跑，是区分「本轮引入」与「基线同红」最快的判据。
  8. 共享工作区上并行会话的在途改动会挡住编译 —— 验证走隔离 worktree，既不碰别人的在途状态，也能拿到「提交树的真实样子」。
  9. 部署前的祖先检查是唯一能提前发现跨车冲刷的动作 —— 本次是部署后读 /healthz 才发现被回退。
  10. 「HEAD 同红」不等于「你引入的」——归因要两棵树对拍：在 变更前 与 变更后 两棵树上跑同一量具、 逐条比对差异，才能分清「基线同红」与「本轮引入」。 本轮实测：并行车把 4 个语种的 +1 归因给审计轮，实测两树数字逐条相同 ⇒ 归因不成立； 而本轮真正引入的那 +2，恰恰不是被指认的那一项 ⇒ 「谁引入」要用差集，不用印象。
  11. 「统计口径正确」要对着库直查复刻同一段 SQL，而不是只看接口 200 —— 接口 200 只证明「通」， 不证明「数得对」。本轮把 API 返回行数与 211 库内 count(distinct …) 对拍（60/14/6/1 全等） ⇒ 才敢说口径与数据管道一致。
  12. 数字对不上时，先分清「口径差」还是「数据源差」 —— 本轮 211(60) vs 154(447) 的差异， 根因是两机连两个不同的 PostgreSQL（而不是聚合逻辑不同）； 不先查 DB 指向就改 SQL，等于对着错库调口径。
