## 二、copy-quality 为什么**可以**扩到源码面（先量再落盘）

上一轮量过：`.vue` 里 3084 条硬编码中文里只有 4 处 AI 腔 ⇒ 扩面不会爆红。
但**判据不能原样搬**：把拉丁规则套到源码字面量上，首量 15 条命中里几乎全是假阳性 ——
`'row in summary.by_model'` 是**代码表达式**不是文案；
`'dashboardBoard inject missing — mount …'` 是给开发看的 console 警告；
`'${label} · ${health} · …'` 是紧凑标签的**合法分隔符**。

⇒ **源码面只管中文**（`localeOfContent`：含汉字 ⇒ zh-CN 规则；不含 ⇒ 跳过）。
理由：源码面要管的是「**还没搬进语言包的中文文案**」；
英文文案在仓里的既定做法就是进语言包，那边已经有门。

## 三、★ 新门：Vue 3 的普通属性不做插值

### 3.1 形态

```html
<span title="$t('common.close')">   →  title 的值就是字符串 "$t('common.close')"
<span :title="$t('common.close')">  →  绑定形式才求值
```

实测（`@vue/compiler-dom` 3.5.43）：

```js
compile('<div title="$t(\'common.close\')">hi</div>', { mode: 'module' })
// ⇒ { title: "$t('common.close')" }      ← 静态字符串，不是表达式
```

**编译不报错、vue-tsc 不报错、运行时也不报错** —— 只有用户看得见：
tooltip / placeholder 变成字面量 `$t('…')`，而且它**比原文长得多**，还会撑宽版面。

同族：Vue 3 也**移除了属性里的 mustache 插值** ⇒ `text="{{ x }}"` 同样渲染成字面量。

### 3.2 为什么之前没有门

- `keys_referenced` / `localeKeyParity`：只管「键在不在」。
- `callSiteParams.bindingKind`：**按变量名**判「静默吞错的变量有没有消费者」，
  不是通用的「普通属性里放 i18n 调用」判据。

⇒ 上一轮在模板里插了 **563 个 `$t()`**，任何一处落进普通属性都会静默把键路径显示给用户，
而**没有门会报**。

### 3.3 ★ 门首跑抓到 2 处真缺陷（不是假阳性）

`web/src/views/AgentRegistryView.vue` 的**邻居列表**（上下游）：

```html
<span class="kind-tag kind-{{ n.kind }}">{{ n.kind }}</span>   ← Vue 3 不插值
```

而**同文件 421 行**用的是正确写法：

```html
<span class="kind-tag" :class="'kind-' + a.kind">{{ kindLabel(a.kind) }}</span>
```

并且 648–650 行确实有三条按 kind 区分的配色规则：

```css
.kind-llm_endpoint { background: color-mix(in srgb, var(--accent) 18%, transparent); color: var(--accent-h); }
.kind-mcp_server   { background: var(--success-bd); color: var(--success); }
.kind-agent        { background: var(--warning-bd); color: var(--warning); }
```

⇒ **主列表的徽章是按 kind 上色的，邻居列表的徽章从来都是同一个默认色**
（`.kind-tag` 本身只有 padding/圆角，没有背景色）。用户看到的是「同一个列表里两种颜色」。

**修法**：与 421 行同款 —— `class="kind-tag" :class="'kind-' + n.kind"`。

### 3.4 门的判据纪律

| 纪律 | 做法 |
|---|---|
| 只看 `<template>` 块 | `<script>` 里的字符串不是模板 |
| **先剥 HTML 注释** | 仓内的修复说明注释里会原样写出被修的那段（`text="{{ tabErrors.pricing }}"`），不剥就会把注释当缺陷 |
| 绑定/指令放行 | `:x` / `@x` / `#x` / `v-x` 的值会被求值 |
| 非空下限 | 扫过的属性数必须 > 3000 —— 「一个属性都没扫到」也是绿的（假绿） |
| 双向自证 | 10 条夹具：会触发 3 条、不误触发 7 条 |

## 四、等级量表：为什么要**搬进语言包**而不是换个词

copy-quality 在 `web/src/types/quality-api.ts` 报出空洞词「卓越」（DESIGN.md §7 禁用词表）。
若只换词（卓越 → 最优）能过门，但有三个问题被留下：

1. 等级文案在源码里是**硬编码中文** ⇒ **7 个非中文语种显示中文徽章**；
2. 源码字面量 + 语言包 = **两个真值源**；
3. 换词只解决**这一个词**，解决不了「量表没有本地化」。

⇒ 做法与上一轮的 `headlineState` 同款：**字母是稳定 code，文案是语言包里的词**。

- 语言包：`common.terms.qualityGrade.{s,a,b,c,d}`（5 key × 8 语种 = 40 条译文）
- 取词：`web/src/utils/qualityGradeLabel.ts`（键名写成**字面量** ⇒ 静态扫描器看得见 ⇒
  「8 个语种都有这个键」仍然有门在管）
- 调用点：`ProvidersView.vue`（徽章 tooltip）、`provider-detail/QualityTab.vue`（徽章旁文字）

### 4.1 8 语取值与两条硬约束

| | zh-CN | zh-TW | en-US | ja-JP | de-DE | es-ES | fr-FR | ar-SA |
|---|---|---|---|---|---|---|---|---|
| S | 最优 | 最優 | Best | 最優 | Optimal | Óptimo | Optimal | الأفضل |
| A | 优秀 | 優秀 | Excellent | 優秀 | Sehr gut | Excelente | Très bon | ممتاز |
| B | 良好 | 良好 | Good | 良好 | Gut | Bueno | Bon | جيد |
| C | 一般 | 一般 | Fair | 普通 | Befriedigend | Regular | Moyen | مقبول |
| D | 较差 | 較差 | Poor | 不良 | Mangelhaft | Deficiente | Médiocre | ضعيف |

两条约束来自 `localeValueQuality` 门：

1. **各语种的值不得与 en-US 逐字相同**（否则「未翻译」棘轮 +1）⇒
   de-DE 不能写 `Best`、fr-FR 不能写 `Excellent`、es-ES 不能写 `Operator`。
2. **非中日语种的值不得含汉字**；en-US 的值不得含汉字。

行为保持不变：未知等级**回显原字母**（两个调用点原本都这样），等级缺失时
各调用点沿用各自的占位（表格空串 / 详情页「—」）。

### 4.2 「operator」的三语种去舞台味

`common.terms.operator` 在**授权面板列头**与**路由日志详情标签**两处出现，语义是「操作人」。
en-US 原文是 `Actor`（读着像舞台演员）、es-ES `Actor`、fr-FR `Acteur` 同病 ⇒
各自换成自然词：en `Operator` / es `Operador` / fr `Opérateur`；
de `Ausführender`、ja `操作者`、zh `操作人`、ar `المنفّذ` 保持（本来就是审计语境的标准词）。

## 六、移动端（web-mobile/）纳入覆盖，以及它的 126 处存量

### 6.1 为什么移动端本来**完全没有**被这道门覆盖

移动端是**另一个包**，语言包布局也不同：

| | web 控制台 | web-mobile |
|---|---|---|
| 语言包位置 | `web/src/locales/<locale>/**.ts` | `web-mobile/src/i18n/<locale>.ts`（扁平） |
| 语种数 | 8 | 2（zh-CN / en-US） |
| 源码面 | `web/src/**` | `web-mobile/src/**` |

这道门原来只扫 `web/src/locales/**` ⇒ 移动端的 3909 × 2 条文案**从未进入过** AI 腔判据的视野。

### 6.2 扩过去之后量到了什么

| 规则 | 条数 | 位置 |
|---|---|---|
| 破折号当标点（§7 第 8 条） | 126 | `web-mobile/src/i18n/en-US.ts` |
| 装饰性中点串（§7 第 6 条） | 2 | 移动端 zh-CN + en-US 各 1 |
| 否定转折当骨架（§7 第 7 条） | 3 | 移动端 zh-CN |

⇒ **5 处非破折号的当场改掉**（否定转折按第 7 条改成正面陈述，中点串改成正常并列），
126 处破折号**登记为棘轮基线**（见 6.4）。

### 6.3 为什么破折号不一次性全改

126 条里绝大多数是「短标签 — 解释」句式（`Failed to load — tap to retry`），
长的是诊断说明段落（`★★ This endpoint has no pagination (… — only ORDER BY …)`）。
一次性手改 126 条产品文案的风险是**语义漂移**（移动端那些段落在讲后端契约的细节），
而本轮的主线是「门扩面 + 门抓到的真缺陷」。

⇒ 按**仓内对同类存量债务的既有做法**处理：登记基线 + 只许降
（对照：`localeValueBaseline.json` 里 ar-SA 有 **1102** 条「值=英文原文」登记在案）。
**改写是下一轮的工作项**，本轮只负责让它**可见、可量、不可增长**。

### 6.4 棘轮基线的设计

- 桶 = `<树>/<语种>`（语言包面）+ `<树>/source`（源码面）。
  ★ **必须按树分桶**：web 的 en-US 与 web-mobile 的 en-US 是两个地方，
  混在一个桶里 ⇒ web 侧新冒的违规会被移动端存量淹没。
- 默认跑法即**棘轮门**：任一桶超基线 ⇒ exit 1；低于基线 ⇒ 提示可降。
- `--strict` = 零容忍（不看基线），用于清干净之后。
- `--update-baseline` **只许降不许升**（要抬 ⇒ 报错拒绝）⇒ 把「抬基线掩盖问题」堵死。
- 基线里写**显式的 0 值桶**（12 个桶）⇒ 「某个桶现在是干净的」这件事在基线里看得见。

**门的牙用变异测试验过**（隔离副本，不碰仓库）：

| 变异 | 期望 | 实测 |
|---|---|---|
| web 侧语言包冒 2 处违规（空洞词 + 中点串） | 红 | `web/zh-CN: 2 > baseline 0` ⇒ exit 1 ✓ |
| `--update-baseline` 试图抬基线 | 拒绝 | `❌ 棘轮只能降不许升，拒绝写入基线：web/zh-CN: 0 → 2` ⇒ exit 1 ✓ |

## 七、量具口径的一处澄清

中文棘轮门数的是「**注释剥离后**的 CJK **连续段**数」，不是字数。

本轮 −4 的构成（逐文件对拍 HEAD vs 工作树）：

```
  -5     12 →     7  src/types/quality-api.ts      ← 等级表 5 个标签（每段 1 段）
  +1      6 →     7  src/views/DispatchWaterfallPreview.vue  ← 一句话被逗号拆成两段
  合计 delta -4
```

⇒ **把一句话拆成两段，计数会涨**。这不是缺陷，是口径：门数的是「段」不是「字」。
（也说明「让句子更可读」的改写有时会让棘轮计数 +1 —— 棘轮留了余量即可。）
