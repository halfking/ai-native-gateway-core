# R60 轮留证：**新装库缺列族** —— 「文件存在 ≠ 迁移会运行」（2026-10-21）

> 起因：R59 分流里留下的最后一处关键发现 —— 「新装库缺列」**不是一条，是一类**。
> 本轮把它量清楚、归因清楚，并给它加了一道**能抓住这一类**的门。
> **对生产的写入 = 0**（生产侧只做只读查询；本地实验库用一次性库，退出即 DROP）。

---

## §1 一句话结论

**installer 的全新安装路径，出来的库比生产少 23 个列**；其中 `provider_models.source` 缺了
⇒ **全新安装连库都开不了**（`db.Open` 的 ensure 链直接 42703，已实测复现两条门）。
⇒ ⇒ 成因**不是一条**，是**三条通道叠在一起**：
**① startup 通道里有一批文件从未被登记；② domain 通道 installer 根本不跑；③ root 通道也不跑。**
⇒ ⇒ 而既有的空棘轮 `sql/schema/startup_known_gaps.tsv`（0 known gaps）**对这一类完全隐形**
—— 它数的是「已登记迁移**失败**」，不是「文件**从未运行**」。

## §2 测量：两侧逐列求差集（一次性库 vs 生产 252）

| 对象 | 读数 |
|---|---|
| 一次性库 `itgate_r59_shape` | **8965** 个 (schema, table, column) —— ＝ installer 路径的精确复刻（prereqs → 01-schema 基线 → 282 条已登记 startup 迁移） |
| 生产 252（`llm_gateway`，**只读**） | **14106** 个 (schema, table, column) |
| 生产有、新装没有、且所在关系在**两边都存在** | ★ **23 条** ⇒ 即 `sql/schema/fresh_install_column_gaps.tsv` 的全部数据行 |
| 生产有、新装**整个关系都没有** | 259 个关系（其中 42 个在 `maintain` schema、217 个在 `public`，多数是 `bak_20260920_*` 人工备份表）⇒ 属**另一种**差异，本轮不并入登记册 |

复算命令（可重跑）：

```bash
# 一次性库（oracle = installer 路径的复刻）
KEEP_DB=1 bash scripts/audit/probe-onetime-db-shape.sh
docker exec llm-gateway-pg psql -U llm_gateway -d itgate_r59_shape -tAc \
  "select table_schema||'.'||table_name||'.'||column_name
   from information_schema.columns where table_schema not in ('pg_catalog','information_schema') order by 1;"

# 生产（只读）
ssh 252 'podman exec pg-252-pg17 psql -U llm_gateway -d llm_gateway -tAc \
  "select table_schema||'.'||table_name||'.'||column_name
   from information_schema.columns where table_schema not in ('pg_catalog','information_schema') order by 1;"'
```

⚠ **量具踩坑三连（本轮全部踩过，改量具时别再踩）**：
① 登记册 `installed_startup_migrations.tsv` 的数据行格式是 **`<index>\t<文件名>`** ——
文件名在**第 1 列**；取第 0 列会拿到序号 ⇒ 已登记集合全空 ⇒ 门报 84 条假缺口。
② `pg_class.relkind` 是 `"char"` 类型 ⇒ `||` 拼接会报 `operator is not unique: text || "char"`
⇒ 必须 `relkind::text`。
③ 列名是 **三段**（`schema.table.column`）⇒ 按两段切会把表名读成 `public` ⇒ 误判「表不存在」。

## §3 成因分解：三条通道

| 通道 | 例子 | 谁投递 | installer 跑不跑 |
|---|---|---|---|
| **① startup 但未登记** | `361b_provider_models_source_prelude.sql`（`provider_models.source`）、`375_offline_requests_status.sql`、`376_offline_activation_code.sql`、`387_session_analysis_inference.sql`、`427_task_type_centroids_model.sql`、`016_outbound_body.sql` | 文件躺在 `sql/migrations/startup/` | **不跑**（只跑 `StartupFiles` 登记的那 282 条） |
| **② domain 通道** | `sql/migrations/domain/361_standard_provider_models.sql`（`provider_models.source` 的原始出处）、`domain/350_model_iq.sql`（`models_canonical.standard_iq*`） | domain 通道 | **不跑** |
| **③ root 通道** | `sql/migrations/075-omnifree-schema.sql`（`credentials.is_free_tier` 等 3 列 + `provider_catalog.*` 3 列） | root 迁移目录 | **不跑** |

★ **仓内已有同形态的先例**：`installer/internal/dbinit/runner.go` 里 851 / 855 / 856 / 857
四条都是同一形状的补登记，注释原文写得很清楚：

> 「这条迁移此前**从未被登记**：文件躺在 `sql/migrations/startup/` 里，deploy 的目录扫描会捡到它，
> 但安装器只跑 StartupFiles，于是每台全新安装的机器上……」

⇒ ⇒ **这不是新形态，是已知形态的第 N 次复发**；本次复发没人看见，是因为
**现有棘轮管的是另一个维度**（见 §5）。

⚠ **`361b` 自己的注释已经把话说尽了**（原文）：
「provider_models.source 由 domain/361 的防御性 ALTER 添加，投递路径是 scripts/init-local-db.sh / installer，
**从不经过 apply-db-revision-sequence 的 startup 通道**。host-first 部署的库只走 startup 通道，
列缺失时启动 ensure 链在 db open 就炸」⇒ ★ **它当年修的是「host-first 部署」那条通道，
而 `llm-gw-installer`（Go 安装器）是**另一条**通道 —— 它没被这次补丁覆盖。**

## §4 已实测致命的一条：新装库**连库都开不了**

`sessions`/`provider_models` 缺 `source` ⇒ `db.Open` 的 ensure 链直接失败：

```
ERROR: column "source" of relation "provider_models" does not exist (SQLSTATE 42703)
  ensure asr catalog seed (provider_models glm-asr)
```

⇒ **两条既有真库门复现**（R59 的 75 条失败清单里就有它们）：

| 门 | 失败点 |
|---|---|
| `db::TestEnsureAsrCatalogSeed_RealDB` | `first run: ensure asr catalog seed (provider_models glm-asr): ERROR: column "source" of relation "provider_models" does not exist` |
| `sql-migrations-startup::TestMigration715FreshChainApplyMigrations` | `db.Open (full startup chain) failed: …` ⇒ **这条测的正是「真实新装路径」**：它读的链来自 `installed_startup_migrations.tsv`（= `StartupFiles`） |

⇒ ⇒ ★★ **「全新安装 = 装完即炸」已被实测坐实**（不是推演）。
⇒ ★ 而**生产没事**（实测 `prod_provider_models.source = 1`）⇒ ⇒
**这是「新装 ≠ 升级」这个形态**：生产是**升级**出来的（有历史列），
新装是**从基线 + 登记链**长出来的（没有那些列）。

## §5 为什么既有门看不见这一类（判据覆盖缺口）

| 既有物 | 它管什么 | 为什么看不见「文件从未登记」 |
|---|---|---|
| `sql/schema/startup_known_gaps.tsv`（**空棘轮**，0 known gaps） | 「**已登记**的迁移在全新安装上**失败**」 | 它数的是 `failed=0`，**不是** `missing=0` ⇒ 一个从未被登记的文件**根本不会出现在统计里** ⇒ ★ 这道门在缺 23 列时**照样是绿的** |
| `db::TestEnsureAsrCatalogSeed_RealDB` | ASR 种子在真库上幂等 | 只能看见**一个实例**（`provider_models.source`） |
| `sql-migrations-startup::TestMigration715FreshChainApplyMigrations` | 真实新装链跑完能 `db.Open` | 同上，只在**恰好撞上** `source` 时才红 |

⇒ ⇒ ★ **新门补的就是这个维度**：把「**未登记的文件**」也纳入可检范围。

## §6 本轮新增：缺列登记册 + 一道真库门

### §6.1 登记册 `sql/schema/fresh_install_column_gaps.tsv`（新，23 条）

每行 = `<table>\t<column>\t<severity>\t<reason>`；`severity` ∈ {fatal, high, medium, low, benign}。
**棘轮方向**：只登记「**此刻仍然缺**」的列 ⇒ 修好一个缺口 = **删一行**；新缺口冒出来 = **补一行 + 写理由**。
⇒ 删掉整个登记册**不会**让门变松，只会让门 A 立刻变红。

### §6.2 门 `sql/schema/fresh_install_column_gaps_test.go`（新）

| 判定 | 内容 | 需不需要库 |
|---|---|---|
| **A**（有牙） | 扫**未登记**的 startup 文件 ⇒ 它们加的列在**物理表**上缺失 ⇒ 必须出现在登记册里，否则红 | 要 |
| **B**（不过期） | 登记册每行必须**此刻仍然缺**；已修复 ⇒ 红（提示删行） | 要 |
| **C**（形状） | 排序、去重、reason 必填、severity 在白名单里 | 不要 |
| **自检** | 纯函数合成数据证明检测函数**能红也能绿**（5 个子用例 + 过期检测 1 例） | 不要 |

★ **判据与被测对象同层**（AGENTS.md 判据纪律第 1 条）：「全新安装缺哪列」的答案在**真库**里，
不在 SQL 文本里 ⇒ **oracle = 一次性库**（＝ installer 路径的精确复刻）。
⚠ **试过静态解析基线并放弃**：解析 `01-schema.sql` 只能抓到 271 张表里的 220 张
（`CREATE TABLE` 块一复杂就漏）⇒ 差集全是假阳性 ⇒ **不可用**。

### §6.3 变异验证（全部转红，且逐字还原 / md5 一致）

| 变异 | 结果 |
|---|---|
| **M1** 从登记册删掉 `provider_models.source` 一行 | 红（门 A）：`361b_provider_models_source_prelude.sql: provider_models.source` |
| **M2** 伪造一个未登记的 startup 文件（加一个库里没有的列） | 红（门 A）：`zz_r60_mutation_probe.sql: provider_models.mutation_probe_col` |
| **M3** 在克隆库里把 `provider_models.source` 补上 | 红（**门 B**）：`登记册 … 里有 1 行已经不再缺（缺口被修好了）：provider_models.source` |

⇒ ★ **M3 同时证明了修法是通的**：一旦那个文件被登记（列被加上），
门 A 不再报（文件变成已登记），门 B 报「这行过期了，请删掉」⇒ **修复 ⇒ 登记册缩小**。

⚠ **M3 的第一次尝试不算数**：克隆库时源库还有会话（`being accessed by other users`）⇒
门红在**连接错误**上，不是预期判据 ⇒ 重做（先 `pg_terminate_backend`）后才拿到有效的红。
⇒ 记录这一点是因为它正是「红的是不是预期那条判据」这条纪律的现场。

## §7 诚实边界（本轮**没有**回答的）

1. **登记册是「生产 vs 新装」的差集，不是「产品实际引用了哪些列」的穷举。**
   ⇒ 那 23 列里，产品**真的**会引用哪几列，本轮**没有**逐条查
   ⇒ 例如 `provider_models.source` 已被实测（致命），`prompt_injection_detections.*` 四列
   **未实测**有没有产品路径引用。
2. **门 A 只扫 `sql/migrations/startup/` 里未登记的文件** ⇒ domain 通道与 root 通道的缺口
   **检不出来**（那 7 列只靠登记册 + 人工复核）。
3. **门 A 只认物理表**（relkind ∈ r/p）⇒ 加在视图上的列不判
   ⇒ **S4 退役改名那一跳是盲区**（`request_logs` 现在是视图，物理表是 `_request_logs`）
   ⇒ `_request_logs.outbound_body` 这条已手工写进登记册并标注了盲区。
4. **那 259 个「生产有、新装整个没有」的关系**（42 个在 `maintain`、217 个在 `public`，
   多数是 `bak_20260920_*` 人工备份表）**本轮没有逐个定性** ⇒ 登记为待办。
5. **门 A 的判定依赖 SQL 解析**（`ALTER TABLE … ADD COLUMN`）：
   解析器有已知噪声（`ALTER TABLE IF EXISTS`、`schema.` 限定、`DROP COLUMN` 误配）
   ⇒ 本轮修了 3 处，但**没有**穷举边界形态 ⇒ 门 A 可能漏报（**只会漏，不会误报**）。
