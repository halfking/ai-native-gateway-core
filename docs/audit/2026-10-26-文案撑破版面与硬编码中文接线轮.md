## 0. 一句话结论

**上一轮的译文确实撑破了版面**：德语页的页头标题宽被压成 **0px（完全消失）**、法语页 **28px（逐字竖排）**。
根因不是「德语太长」，而是 `PageHeader.vue` 的 flex 规则**把「谁让路」写死成了标题**。
修法是翻转这条规则（标题不让路、操作区换行），而不是把德语改短。

顺带查清两件事：

1. **量具有盲区**：`ui-sweep.mjs` 的折行判据写的是 `w > 0` ⇒ **宽度恰为 0 的元素（最坏形态）不可见**。
2. **界面根本没在用语言包**：`FreePoolView.vue` 有 **245 段硬编码中文** ⇒ 德/法/阿语页上整排按钮是中文。
   语言包里的 key **大多早就存在** ⇒ 这是**接线缺陷**，不是缺文案。

## 1. 版面回归（真实缺陷，本轮引入的回归）

### 1.1 现象

`/free-pool` 页头（`PageHeader.vue`，42 个视图共用）：

| 语种 | 标题宽 | 标题高 | 观感 |
|---|---|---|---|
| en-US | 142px | 29px | 正常 |
| **de-DE** | **0px** | 720px | **标题完全消失** |
| **fr-FR** | **28px** | 288px | **逐字竖排** |
| ar-SA | 146px | 29px | 正常 |

### 1.2 机制（读 CSS 读出来的，不是猜的）

```css
.app-page-header__main   { min-width: 0; }            /* 标题区：可缩到 0 */
.app-page-header__actions { flex-shrink: 0; }          /* 操作区：按内容宽度占位、不让步 */
```

两者相加超出容器时，**被牺牲的永远是标题**。

触发器是翻译后的按钮更长（德语 `Anmeldedaten in die DB schreiben` 248px vs 中文「写入 DB 凭据」）——
但那只是触发器；根因是这条规则让「谁让路」写死成了标题。任何更长的文案都会复现。

### 1.3 修法（翻转「谁让路」）

```css
.app-page-header__main    { flex: 0 0 auto; max-width: 50%; }   /* 标题不让路 */
.app-page-header__actions { flex: 0 1 auto; min-width: 0; flex-wrap: wrap; justify-content: flex-end; }
```

移动端（≤768px）堆叠时解除 `max-width: 50%`（否则窄屏标题被压成半宽）。

### 1.4 实测（修后）

| 语种 | 标题宽 | 标题高 |
|---|---|---|
| en-US | 155px | 29px |
| **de-DE** | **237px** | **29px** |
| **fr-FR** | **236px** | **29px** |
| ar-SA | 146px | 29px |

## 2. 量具盲区（仓内门禁 `ui-sweep.mjs`）

### 2.1 判据

```js
if (w > 0 && w < 44 && h > w * 2.2 && h > 90) {   // ← w > 0
```

`w > 0` 把**宽度恰为 0** 的元素挡在门外 —— 而 0 宽恰恰是「被兄弟节点挤没了」的**最坏形态**。
⇒ **门报绿，页面是坏的**（标题完全消失，页面其余部分照常渲染）。

### 2.2 修法

- 判据放宽到 `w >= 0`；
- 新增排除项 `visibility: hidden`（仍有布局盒但人看不见）；
- 加两条夹具：
  - **零宽文本必须被抓**（夹具形态取自真实缺陷：`flex-shrink:0` + `min-width:0` 的真实 flex 结构）；
  - **零宽但 `visibility:hidden` 不得误报**（反向对照）。

### 2.3 放宽前先量差值（「先判量具、再判数据」）

4 语种 × 19 路由 = 76 页：**新旧判据命中数完全一致、0 页有差值** ⇒ 放宽不引入假阳性。

### 2.4 自证读数

| 套件 | 修前 | 修后 |
|---|---|---|
| 探针自检（10 夹具 × 5 判据） | 47/50 | **50/50** |
| 弹层探针（9 夹具） | 21/21 | 21/21 |
| 步骤驱动器（4 夹具） | 6/6 | 6/6 |

⚠ 第一版夹具翻过两次车，都记在这里：
① 夹具的 flex 结构不足以把标题压到 0（操作区不够宽）⇒ 期望 `verticalText=1` 实测 0；
② 反向对照夹具带了 `overflow:hidden` ⇒ 顺手命中了**内容裁切**判据（`clipped` 期望 0 实测 1）。

## 4. 同一批文案有两处真值（`header.*` 与顶层 `error.*` 副本）

### 4.1 `freePool.header.*` —— 死命名空间

- 8 个语种各一份，**全仓 `freePool.header` 0 命中**；
- 与 flat 层是同一批文案的**第二份副本**；
- 已经**分叉**：zh-TW / ja-JP 的 flat 层还写着**简中原文**（「一键建设」），
  而 `header.*` 里是正确译文（「一鍵建置」/「一括セットアップ」）。

⇒ 视图找不到 flat 层的 5 个键（`refresh` / `bridgeOAuth` / `importEnv` / `discover` / `quickEntry`）
⇒ **直接把中文硬编码进了组件** —— 这就是 §3 的成因链。

### 4.2 `error.*` 的顶层扁平副本 —— 同样是死的，同样已经分叉

- zh-CN 只有 `error.*`；其余 7 个语种**各多留了 10 个顶层副本**（成功类消息）；
- 这 10 个副本 **0 引用**（死键），且**值已分叉**：zh-TW / ja-JP 的顶层副本是中文
  （「探活未通过」），`error.*` 里才是正确译文（「探活未通過」/「動作確認失敗」）。

### 4.3 处置

1. 把 `header.*` 里**值正确**的 5 个键**提升**到 flat 层；
2. 删掉 `freePool.header.*`（11 键 × 8 语种 = 88 个死键）；
3. 删掉 10 个顶层 `error.*` 死副本（× 7 语种 = 70 个）；
4. 顺带把 zh-TW / ja-JP 的 5 个 flat 键（`bootstrap` / `bootstrapSyncing` /
   `showKeyForm` / `hideKeyForm` / `showAddForm`）修回正确译文（值取自 `header.*`）。

**结果**：8 语种键集合**完全一致**（各 **312** 键）—— 此前 zh-CN 比其余语种少 10 个键。

## 5. 门禁暴露出来的真相（`untranslated` 指标为什么会涨）

接线后 `untranslated` 指标：de-DE 1102 → **1109**，fr-FR 1100 → **1104**。

### 5.2 为什么之前门看不见

这 11 条**此前根本没被显示**：视图硬编码中文 ⇒ 这些 locale 值是**死代码** ⇒ 不在引用集里 ⇒

⇒ 这又是一次「**门报 0 ≠ 干净**」：门的盲区不是判据写错，而是**人口**（真正显示的键）不对。

### 5.3 处置：不改文案，改基线

按仓内既有裁决「**文件内一致优先于指标好看**」+「专有名词天生与参照语种逐字相同 ⇒
保留 + 单列清单，而不是硬造生硬词」：11 条**全部保留**。

基线**人工抬高**（仓内规则：「把基线调高必须人工显式改 JSON 并在 commit 消息里写明理由」）：

| 指标 | 旧 | 新 | 理由 |
|---|---|---|---|
| `untranslated.de-DE` | 1102 | 1109 | +7 = §5.1 的 7 条德语同形词 |
| `untranslated.fr-FR` | 1100 | 1104 | +4 = §5.1 的 4 条（含 1 条文件内一致） |
| `sameAsSource.zh-TW` | 2161 | 2162 | +1 = 繁简同形词（`例如:` / `聚合模式` / `健康` / `{n} 秒前` …） |

⚠ **抬基线的根因是分母变了**：referenced keys **5011 → 5152（+141）**
⇒ 原始数字不可比，必须重铸（仓内既有规则：「口径/人口变了必须配套重铸基线」）。
