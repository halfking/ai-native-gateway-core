## 二、取证：线上长什么样，设计是什么样

### 2.1 线上截图 vs 原型截图（部署前，154）

| 维度 | 线上 154（部署前） | 设计方案 |
|---|---|---|
| 行数 | **177 行**，绝大多数是 `error_kind=no_traffic_5min` 的**后端心跳** | 只有真实请求 |
| 阶段取值 | **全部为空**（只有节点名，没有值） | 每段有值（已通过 / N 处 / 候选数 / 模型名…） |
| 裸键 | 屏上直接出现 `liveStageTree.stage.first_by…` | 无裸键 |
| 错误 | `no_traffic_5min` **裸错误码**上屏 | 来源徽标 + `error_kind` + tooltip |
| 时间列 / 列头 / 图例 | **都没有** | 都有（设计第 8 轮） |
| 完整 / 紧凑双模式 | **没有** | 有（第 6 轮） |
| 最右错误列 | **没有** | 有（第 9 轮，右缘恒定） |
| 摘要行 | 只有状态 | 状态·错误·会话·模型链·供应商·排队·耗时·token·成本·可信度·缓存 |
| 全屏统计层 | 只有「请求数/成功率」两行 | KPI×16 + 周期统计 + 五维分类 + 口径说明（第 17 轮） |

### 2.2 根因（四类，逐条取证）

**根因①：后端心跳被当请求渲染。**
`web/src/composables/liveStreamStore.ts` 的 `liveStreamState.requests` 里混着 `type='idle_marker'` 的心跳帧（`status='idle'`、`error_kind='no_traffic_5min'`、`request_id` 形如 `idle-global-model-…`），而 `/live2` **从未过滤**。
⇒ 修：`isIdleMarker()` 判定 + 视图层 `realRequests`（过滤候选也只用真实请求，否则下拉里混进心跳模型）。

**根因②：线上 SSE 把动作明细摊平到顶层，前端只读嵌套 `detail` ⇒ 阶段取值全空。**
`admin/live_stream_lifecycle.go` 的 `flattenActionEvent` 先 `delete(m,"detail")` 再把 detail 的键拷到顶层。抓包实测动作帧**没有 detail 对象**（`mutations/decision/score/candidates/raw_model/ttfb_ms/status/attempt/tier` 全在顶层）。
而 `web/src/lib/liveStageTree.ts` 只读 `action.detail` ⇒ **每个阶段取值都是空**、审批拒绝判不出失败、注入命中判不出告警、最终模型退化成原始名。REST 回退 `/api/admin/request-actions` 才是嵌套形状。
⇒ 修：`actionDetail()` —— **嵌套 detail 优先 + 顶层平铺补齐**，两种形状都吃。

**根因③：裸 i18n 键上屏 + 裸错误码上屏。**
`t('liveStageTree.stage.' + s.key)` 是**动态键**，对 `first_byte` 取到不存在的 `liveStageTree.stage.first_byte` ⇒ 界面直接显示这串字符（仓内的 i18n 引用扫描器抓不到动态键 —— 这就是「动态键是引用扫描器盲区」的又一处实证）。
⇒ 修：所有阶段名改**逐字面量 `t()`**；错误码按 `error.kind.*` 逐条映射（15 种），未知码回落原始码（不编）。

**根因④：设计主档 §16.7 自认「生产端 `/live2` 的 Vue 实现仍未同步第 6/7/8/9 轮任何改造」** —— 版面层整体缺失。

### 2.3 ★ 机制原因：Maestro 资产里没有一条断言是「界面 == 设计方案」

上一轮加了 flow 12 与 `assert-stage-tree.mjs`，但它们验的是**行为与存在性**（入口可点、元素在、数据是活的、胶囊读数 == 带数）。
**没有一条断言是「界面长成设计那样」** ⇒ 于是「177 行心跳」「阶段值全空」「裸键上屏」「缺双模式/错误列/统计层」**全都是绿的**。
⇒ 本轮把设计方案里的**可观测事实**逐条写成断言（版面件齐、列头与带同宽、瓦片同一行、完成态不画 ✓、错误列右缘恒定、树宽 1400、胶囊带窗口…），
并把「紧凑模式」从「一个模式」升级成**一份独立的设计契约**（原型第 6/7/8/9 轮）。

### 3.3 紧凑模式（**整段重建**，原型的第 6/7/8/9 轮）

原型实测过的一版里，紧凑模式是**另一套版面**，不是完整模式的缩小版。本轮按原型重建：

| 契约 | 原型取值 | 本实现 |
|---|---|---|
| 瓦片 | 28×28，**无边框无底色**，圆角 7px | 同（`CTILE=28`） |
| 图标 | 15px 线性描边，绝对定位左上 | 同（复用仓内 `web/src/types/stageTree.ts` 的 `STAGE_ICONS`，它就是原型 `ICON` 的移植） |
| 状态角标 | 纯字形（不画实心圆）；**完成态不画 ✓** | 同（`COMPACT_STATE_GLYPH`） |
| 小数字 | 瓦片内右下角 | 同 |
| 轨道 | 只画在段与段之间的短线；发送向右、回程向左 | 同（`data-rail` + `::after`） |
| 方向 | 发送末端向右箭头、回程起点向左箭头 | 同 |

### 3.4 统计全屏层

分**两把尺**、各自标注、不混算：
- 主体＝**内存实时窗口**（与树同源）：KPI×16 + 周期统计（分钟桶）+ 分类统计 5 维 + 口径说明区；
- 折叠区＝**DB 直查** `StatsPanel`（与 `/live` 一致的那把尺）。
缓存命中率**不可跨口径合并**（OpenAI 包含口径 / Anthropic 并列口径）：两种口径并存时给 `null`（不混算），另报 covered/excluded 覆盖面。

### 3.5 i18n

8 语种补 **90 个新键**（mode/legend/header/clientType/session/window/newPill/band.queue/error.*（15 种错误码）/stats.kpi/trend/dim/notes/db），
改 `stats.readout` 格式、`value.meter`、`value.injection`，新增 `decision.warnShort` 与 `band.attempts`。
纪律：① 新键一律**逐字面量 `t()`**（动态键是引用扫描器盲区）；② 8 语种键集合平价；③ **en-US 值不得含汉字**；④ 各语种「值等于 en-US / 等于 zh-CN」的计数是**只许降不许升的棘轮**（`src/i18n/localeValueBaseline.json`）—— 本轮新增键在 8 语种逐个核对，无同值项。

## 四、与设计方案的**偏差登记**（有意为之，不是漏做）

| # | 设计原型 | 本实现 | 理由 |
|---|---|---|---|
| 1 | 阶段列序＝owner 初版列举序（鉴权→审批→注入→脱敏→压缩→路由→供应商） | **代码真实管线序**（鉴权→**脱敏**→**审批**→注入→路由→**压缩**→供应商） | 主档 §5.2 明定「阶段顺序＝代码真实管线顺序」；差异已在主档登记 |
| 2 | 紧凑瓦片角标用**单字**（网/供/它） | **来源色圆点**（名称与判据在 tooltip + 最右错误列） | 单字在 8 语种里既不可实现、又必然与 en-US/zh-CN 同值 ⇒ 撞 i18n 值棘轮；且整段文案会压到相邻瓦片上 |
| 3 | 紧凑模式**无列头** | 同（隐藏） | 原型 `body.mode-compact .stagehead{display:none}`：紧凑是「单行流水」不是「按列对照的表」 |
| 4 | 错误 tooltip 含 **HTTP 码** | 不含 | 生产 `reply` 动作的 `detail.status` 只有 `success`/`failure`，**不带 HTTP 码** ⇒ 拿不到就不编 |
| 5 | 摘要行含 **▤N 帧**（响应帧数） | 不含 | 实时流帧里**没有**帧数字段 ⇒ 未上报 ≠ 0，不显示 |
| 6 | 原型「压缩」格显示 `-22%` 压缩率 | 显示「已压缩 / 未压缩」 | 生产动作帧不带压缩率；只报**事实**（压没压） |
| 7 | 接收轨在原型里**绝对定位**按列对齐 | 与发送轨**同身份对齐**（首字节↔供应商列、还原↔脱敏列、计量↔审批列、回复↔鉴权列） | 沿用原型同一做法，但用 CSS Grid 实现（可维护、不错位） |

### 7.5.7 ★ 为什么之前几次是「0 带」——两个独立原因（都不是产品问题）

| 现象 | 真因 | 证据 |
|---|---|---|
| 造完 8 发 + 1 发失败带，页面仍 0 带 | **密钥被自己连发打成 429** ⇒ 被限流挡在**网关入口** ⇒ **根本没进实时流** | 流量返回码分布：**429 × 15**、503 × 4、200 × 3、000 × 3、401 × 1 |
| 流量在、页面仍 0 带 | 窗口是**有界滚动窗口**；生产流量持续进入 ⇒ 合成请求 1~2 分钟被挤掉 | 前后两次断言间隔几十秒 ⇒ 带数 1 → 0 |

★ 推论：**页面的窗口由「全部流量」（生产 + 合成）供给** ⇒ 生产有流量时**根本不需要造流量**；
合成流量只在**生产空闲**时才需要，而且**必须小批量**（连发会被 429 挡掉，白打）。
★ 通用式：**「造流量」本身也会被限流**——造流量的返回码必须逐条看，
否则会以为「请求发出去了 = 流里有」（本轮 15 条 429 是这么被藏住的）。

### 7.5.17 ★★★ 可追溯性的**耐久性**加固：部署 SHA 一度**没有任何 ref 指向**

收尾复核时发现一个此前一直没人查的洞：**「可追溯」这件事本身不可靠**。

- 两个部署 SHA（`6840a7be5` = seq 3050、`8ab0d2e56` = seq 3051）
  **对象在库里，但 `git branch --contains` / `git tag --contains` 全部为空**
  ⇒ 它们是 cherry-pick 出来的**游离提交** ⇒ **`git gc` 之后可能被剪掉**
  ⇒ 「当时能查到的 SHA」在**一段时间后**就查不到了；
- 而两个部署源树只在 `/private/tmp/deploy-frozen-154-stage-parity{,2}`
  ⇒ **系统清理会抹掉**（`/private/tmp` 本来就是易失目录）。

⇒ 「证据」如果只活在**临时目录 + 游离对象**里，它就**不是证据**。

**修法（三处同时做）**：

1. **建仓内 durable ref**（annotated tag，标签消息本身就是文档）：
   `deploy-154/seq3050-6840a7be` / `deploy-154/seq3051-8ab0d2e56`
   ⇒ 两个 SHA 从此**从仓内 ref 可达**，`git gc` 剪不掉；
2. **把基点写进标签消息**（机器可解析的 `base=<sha>` / `cherry-picks=<sha,…>`）
   ⇒ 复核者不用翻部署目录就知道它由什么拼成；
   ★ **踩到的坑**：一开始采集器用 `TAG^` 取基点 ⇒ 部署树是 `base → cherry1 → cherry2 → cherry3`，
   **`TAG^` 是上一笔 cherry-pick、不是基点** ⇒ 算成「10 个文件」冒充「25 个文件」
   ⇒ **看起来 PASS、其实是错的** ⇒ 改为解析标签消息，并把「改动文件数 == 25」写成**硬判据**；
3. **写仓内部署清单**：`docs/audit/2026-11-18-154部署清单-3050与3051.md`
   （两版各 25 个文件的逐文件 blob SHA、并行车零泄漏核对表、**只凭本仓即可复核的命令**）
   ⇒ 证据**不再依赖任何临时目录**。

★ 通用式：**「证据的耐久性」也是证据的一部分**——
一份「当时可查、过后即逝」的证据，等于**没有证据**。
⇒ 判据：**把证据放到【会被清理的地方】⇒ 它迟早会被清理**；
⇒ **锚点要落在【会被长期保留的地方】**（仓内 tag + 仓内文件）。

★ 另一条通用式（本轮同一处踩到）：**「用 `TAG^` 当基点」是个隐蔽的错**——
因为**多笔 cherry-pick 的提交链**里，`^` 指的是**上一笔**而不是**基点**。
⇒ 凡是要「相对基点的差异面」，**基点必须显式记录**（打 tag、写消息、写清单），**不许靠 `^` 推**。

## 八、通用式（本轮沉淀）

1. **「功能打开」不等于「功能对」** —— 上轮把入口打开就收工，差异被 Maestro 资产**全绿放过**；
   ⇒ **入口存在的功能，必须有一份「界面 == 设计」的断言**。
2. **断言要问「界面 == 什么」** —— 「元素在不在」与「界面 == 设计方案」是两条独立断言；前者绿不代表后者绿。
3. **动态 i18n 键是扫描器盲区** —— `t('prefix.' + k)` 既抓不到引用、又会在键名错位时把**键字符串本身**印到屏幕上。
4. **同一条数据可能被上游摊平** —— 线上 SSE 把 detail 摊到顶层、前端只读嵌套 detail ⇒ **取值全空但页面不报错**；
   ⇒ **前端读动作帧必须同时吃两种形状**（嵌套优先 + 平铺补齐）。
5. **两种模式不是同一套版面的缩放** —— 紧凑模式是**另一份设计契约**；两套节点同时在场会**抢同一批网格列**。
6. **`v-html` 注入的 SVG 拿不到 scoped 属性** —— 选择器不匹配 ⇒ 退回浏览器默认（黑色填充、无描边）⇒ 画面上一坨黑块；
   ⇒ 必须 `:deep()`。**「图标不显示」先怀疑 scoped，而不是图标数据。**
7. **量具会老化** —— mock 的时间戳固定在启动时刻 ⇒ 跑久了全部掉出时间窗 ⇒ **被误判成产品缺陷**；
   ⇒ 「断言红」先问「是不是量具坏了」。
8. **量具也要分组** —— 「所有瓦片在同一行」是错的判据（每带一行）；正确判据是「**同一条带内**的瓦片同行」。
9. **断言会随页面改动而失效** —— 本轮重写了统计浮层，flow 里还留着**旧面板**的文案断言 ⇒ 首跑报红
   ⇒ 这正是 flow 的价值（**真红**优于假绿）；但也意味着**改了界面就要同步改断言**，否则红的是断言不是产品。
10. **`$VAR` 后面紧跟中文标点 ⇒ 变量名被吞** —— UTF-8 locale 下 bash 会把多字节字符算进变量名，
   `$STAGE_TREE_CDP）` 取的其实是变量「STAGE_TREE_CDP）」 ⇒ `set -u` 报 unbound variable（本轮实测踩到）⇒ 一律写 `${VAR}`。
11. **低峰时段验「有数据的版面」要自己造流量** —— 部署后生产站恰好无流量（页面诚实显示 0 请求），
    版面断言会**全部落空**（断言通过但什么都没验到）⇒ 用临时密钥打真实请求，验完即删。
12. **★★「红清单一致」≠「数值一致」** —— 棘轮类闸门的失败信息里带**具体计数**；
    对拍存量红时**只比用例名会漏掉「本轮把量顶高了」**（本轮一轮就藏了 7 个语种 +1、+2）。
    ⇒ **对拍要拿失败详情全文做逐字节 diff**，不是比用例名单。
13. **棘轮是「只许降不许升」，基线红也不许加** —— 「反正这条已经红了」是错的推理：
    **红不改变失败状态，但量本身就是纪律对象**；增量的红会在下一次治理时被一起清算。
14. **技术单位/缩写不该占 i18n 键** —— 仓内 `ms` 的写法（直接内联、不占键）就是标准答案：
    **占键 ⇒ 逼出「各语种逐字相同」的假缺陷**。`tok` / `ms` / `SSE` 都属这一类。
15. **繁简同形词会虚高 sameAsSource 棘轮** —— `命中`/`命中`、`得分`/`得分` 这类**合法**的同形词，
    在字节级指标里照样计数 ⇒ 新增 zh-TW 文案要与 zh-CN **逐字区分**（本轮改成 `已命中` / `評分`）。
16. **★ 线上实时流是「有界滚动窗口」，不是「近 5 分钟全量」** —— 页面读数写着「近 5 分钟」，
    但流里只保留**最近若干条请求**；生产流量持续进入 ⇒ **合成验收请求 1~2 分钟就被挤出去**
    ⇒ 「造流量」与「跑断言」必须**紧挨着执行**，否则页面诚实显示 0 请求、
    **断言照样全绿（等于什么都没验到）**。⇒ **验「有数据的版面」要把造流量和断言绑成一条命令。**
17. **★「没评估到」≠「评估失败」** —— 同一条量具老化（本轮 §7.5.6）在两个方向上各咬一次：
    **行为层**在 0 带时全绿（等于什么都没验到），**设计层**在 0 带时报 15 条红（等于误判成产品坏了）。
    ⇒ **验收工具必须自证量具有效**：把「依赖真实数据」的断言列成清单，
    无数据时标「○ 未评估」+ 整体报**专属退出码 2**（0=全绿／1=产品问题／2=量具失效）。
    ⇒ **退出码要能区分「红」与「没测」**，否则量具问题会被当成产品缺陷去查（比假绿更危险）。
18. **★ 量具会老化 ⇒ 造流量与断言要「成对」** —— 本轮先造一次流量跑两个断言，
    行为层还有 1 条带、设计层隔几十秒就 0 条 ⇒ **每一次断言前都要有自己的流量**，
    或把断言**并行**跑（缩短窗口），不能「造一次、跑两遍」。
19. **★★ 同一件事写了两遍口径 ⇒ 必然漂移** —— 两个断言工具各写一份判定，
    一个打印「PASS（N 条断言）」、另一个打印「PASS」⇒ **复核方按字符串比对时直接对不上**；
    且两份都先后犯过「只数第一层 ⇒ 第二层的红被吃掉、照样报 PASS」。
    ⇒ **判定口径单点化（`result.mjs` 的 `summarize()`）+ 给它写自检（`selftest.mjs`，不碰浏览器就能跑）**。
    ★ **验收工具的结论行本身就是交付物**——它是别人据以判断「绿/红/没测」的唯一凭据。
20. **★★★ 「回归跑出一堆红」的第一嫌疑是**量具与跑法**，不是被测系统** —— 本轮部署后回归 12 个 flow ⇒ 红 5，
    其中 2 条红**与产品完全无关**：
    ① **视口没覆写**（`run-local.sh` 漏传 `--screen-size` ⇒ 默认 1024×625 ⇒ 折叠线以下 `assertVisible` 判 false
    ⇒ 换成 1440×1400 重跑同一条 flow **全绿**）；
    ② **这个 flow 不属于这个回归集**（`10-mcp-gateway` 要自带 MCP 网关与 token ⇒ URL 打不开 ⇒ **必然假红**）。
    ⇒ **归因方法＝同一条 flow 换掉量具后还红不红**；红才归到产品。
    ⇒ 推论：**「红」的数量不是结论，红的**归因**才是**——否则会把量具缺陷算成产品回归（或反过来）。
21. **★★★ 「分支 diff 显示 D」≠「合并结果里没有」** —— 本轮收尾自查时 `scripts/check-skills-package.py`
    在分支 diff 里显示为删除 ⇒ 第一反应是「我误删了门禁脚本」。实际是：
    它在**我分支的 merge-base 里就不存在**（由并行车在我分叉**之后**加入 origin/main）
    ⇒ **合并结果树里它是 origin/main 的版本，不会丢**。
    ⇒ 判据必须是**合并结果树**（`git merge-tree --write-tree` 的产物），不是分支 diff。
    ★ 推论：**「我这条线上没有它」与「合并后它还在不在」是两个问题**，前者容易制造假警报。
22. **★★「跑在生产上的是哪一份」要按「发布单元」判，不要按「目录树」判** ——
    生产 release 目录里**只有**二进制 + `web/` + `web-mobile/` + `configs/` + 版本元数据，
    **`maestro/` 与 `scripts/` 根本不随生产发布**（仓内开发侧资产）。
    ⇒ 拿「仓里目录树」推断「生产跑的是哪份」必然出错；
    ⇒ **真正随生产走的前端产物**要**三方对拍 sha256**：服务器文件 = 公网抓取 = 本地 dist（本轮 `2064586b…` 全等）。**
23. **★★★「参数没传进去」和「页面挂了」在 Maestro 里长得一样（都是第一步就红）** ——
    失败现场的 `url` 里**主机段为空** ⇒ 变量没传进去（`https://dashboard/` ⇒ 展开成了 `/dashboard`）；
    主机段正常但 `resource-id="main-frame-error"` ⇒ 才是服务端/页面问题。
    ⇒ 根因是 bash 的**前缀赋值 + 同命令引用 = 旧值**（`FOO=x cmd "$FOO"` 拿到空）⇒ 修法：**先 `export` 再调用**。
24. **★「第一步就红」有三种可能：变量没传进去 / 机器被压爆 / 页面真的挂了** ——
    本轮复验时全量 vitest 在后台跑，**load average 119** ⇒ 浏览器打开页面极慢 ⇒ Maestro 超时。
    ⇒ **跑 Maestro 前先看负载**；三种可能**都要靠现场区分**，不能一律归到「产品坏了」。
25. **★★★「合并无冲突」≠「合并结果能过门禁」** —— `git merge-tree` 退出码 0 只证明**文本不冲突**；
    ⇒ 本轮把合并结果落成**真实本地提交**（`git commit-tree` + detached checkout，不推送、不碰 main）
    再实跑全部门禁 ⇒ **全绿且零新增红**，且 **build 出的前端 chunk 与在役生产逐字节相同**
    ⇒ **合 main 不会改变生产所服务的内容**。
26. **★「构建会不会改写受版本控制的文件」是一条必须自己验的门禁** ——
    本轮发现 `pnpm build` 的第一步 `export-menu-config.mjs` 会重写 `web/public/menu-config.json`
    的 `exported_at` 时间戳 ⇒ **每跑一次 build 工作树就变脏** ⇒ 易把时间戳误提交进仓。
    ⇒ 修法二选一：**文件改出 git 跟踪**（纯构建产物），或 **`exported_at` 取内容哈希而非时间戳**
    （内容不变 ⇒ 文件不变 ⇒ build 不脏树）。登记 **L14**。
27. **★★★★「造流量」必须造【在途】请求 —— 造「已完成」的请求，页面根本看不到** ——
    实测：`max_tokens: 8` 的瞬时请求 ⇒ SSE **确实有帧**（直抓 `/api/admin/live-stream` 看到
    `arrive` / `sanitize_applied`），但请求在帧到达页面前就已完成 ⇒ 页面窗口 `bands: 0`
    ⇒ 依赖「有带」的断言全部「未评估」⇒ 设计层报「量具失效」（退出码 2）。
    改用 `stream:true` + `max_tokens:1000` 的在途请求 ⇒ 页面立刻看到带（`bands 4→9`、`inFlight 4→8`）。
    ⇒ 纪律的后半句：**造流量与断言要成对**，且**造出来的流量还必须在途**。
28. **★★★「没评估到」要一路追到【为什么没数据】，而不是停在「没数据」** ——
    停在「没数据」会得出「页面坏了」的错误结论；一路追到「SSE 有帧 ⇒ 帧到了但请求已完成
    ⇒ 窗口只留活着的请求」才找到真正的量具缺口。⇒ **量具失效必须归因到具体机制，再改配方。**
29. **★ 采集器自己也会产假红** ——
    ① `grep -c` 0 命中时**仍打印 0 但退出码 1** ⇒ `$(grep -c … || echo 0)` 得到 **"00"**
    ⇒ 把「0 次失败」误判成 FAIL ⇒ 用 `|| true`；
    ② 临时密钥**应用码重名** ⇒ 接口 **409**（"该租户+应用+别名组合已有可用密钥"）⇒ 造不出流量
    ⇒ 用**每轮唯一**的应用码，且失败时打印**接口原文**（否则只看到「造流量失败」四个字＝没信息）。
30. **★★★「证据的耐久性」也是证据的一部分** —— 部署 SHA 一度**没有任何 ref 指向**
    （cherry-pick 出的**游离提交** ⇒ `git gc` 后可能被剪掉），而部署源树只在 `/private/tmp`
    （系统清理会抹掉）⇒ **「当时可查、过后即逝」的证据等于没有证据**
    ⇒ **锚点要落在会被长期保留的地方**（仓内 tag + 仓内清单文件）。
31. **★「用 `TAG^` 当基点」是个隐蔽的错** —— 多笔 cherry-pick 的提交链里，
    `^` 指的是**上一笔 cherry-pick**而不是**基点** ⇒ 算出的「改动文件数」偏小
    ⇒ **看起来 PASS、其实是错的** ⇒ **基点必须显式记录**（tag 消息 / 清单文件），
    并把「改动文件数 == 25」写成**硬判据**（而不是只判「有差异」。
