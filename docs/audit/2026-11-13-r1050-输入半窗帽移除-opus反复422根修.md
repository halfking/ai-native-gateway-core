## 一、为何「反复出现且修不干净」——历史修复逐轮回顾（问题的一半答案在史里）

| 轮次 | 修了什么 | 没修什么 |
|---|---|---|
| 2026-11-10 opus55 预算门双根因 | 估计器从「字节=token」换校准估计（chars/3.5、blob/5）；未知窗口降为 advisory | **已知窗口保留 W/2 输入硬帽**（当轮明确登记「minimax 1.18MB 仍 422，旋钮待 owner」） |
| 2026-11-11 max_tokens 封顶 | body 侧输出预留按半窗封顶 ⇒ 输入**至少**拿半窗 | 半窗帽仍把输入**至多**钉在半窗——修复意图（输入≥半窗）与实现（输入≤半窗）方向相反 |
| 本轮 r1050 | 删 `Resolve` 的 `spec.ContextWindow/2` min 项 | —— |

**反复出现的结构原因**：每轮修复都把「误报边界」往外推一截，但半窗帽作为一个
**与预留无关的独立 min 项**始终存在——会话只要长大到跨过它就永久卡死，而且：

1. **422 是终态**（`retryable=false`、`KindRequestRejected`、不进熔断/健康）——客户端重试同形状必败；
2. **会话缓存重放出站体**——ZCode 客户端侧压缩不改变网关侧 v2 缓存的合并结果，
   重试拿到的是同一（或更大）出站体（gw_f9fdc2de 10:23 失败 → 10:52 客户端已压缩到
   18 条消息/15KB 仍失败，出站 70 条/85KB+tools）；
3. **fit 数学性不可行**（见 §二）⇒ 压缩兜底也救不回。

## 二、事故定案（211 取证 + 真实数据复现）

- 当日 4 笔（7 天窗口仅此 4）：04:31 sonnet-5；10:20 / 10:23 / 10:52 opus-4-8，
  后两笔同会话 gw_f9fdc2de **重试同败**——「反复出现」的实体。
- 全链：`contextbudget.Check` 校准估计超限 → `sessioncontext.Fit` 不可行
  （`ErrProtectedContext`）→ `ContextBudgetError` → 三协议面 422
  `input cannot fit the selected bucket budget`。
- **真实数据复现**（hotzone 镜像 + final_full 出站缓存 + ZCode 实测 tools 体积 225KB）：
  opus-4-8（200k 窗）× max_tokens=32000 ⇒ 旧预算 = min(500k, **100k**, 200k−32k) = 100k；
  事故出站 body 336KB（messages 85KB + tools 225KB + system 15KB + framing）⇒
  **校准估计 109,337 > 100,000**（仓内真实代码逐字节复现）⇒ 拒。
- **fit 不可行的数学**：fit 字节目标 = InputTokens×3 = 300KB；`Fit` 只裁 messages，
  tools+system（~240KB，不可裁）+受保护区（最近工具组）> 300KB ⇒ ErrProtectedContext。
  ZCode 固定载荷（tools+system ≈ 70k 估计 token）吃掉 100k 预算的七成，会话历史
  只有 ~30k token 余量——**一个正常长度的 agent 会话必然跨过**。
- **层级倒置实锤**（测试夹具调试中挖出）：预算门（W/2=100k）比 prepare 段预裁剪
  （`CompressMessagesIfNeededWithReserve`，0.8×(W−reserve)=134k 触发）**更严** ⇒
  预裁剪根本没机会先干活，dispatch 级 fit 只在预裁剪结构性失败（system 洪泛等
  r1048 形状）时可达。半窗帽不只错在数值，还错在**打乱了两层压缩的先后设计**。

## 三、修复（internal/contextbudget/budget.go 一行语义 + 全链重钉）

```go
// 旧：limit := min(MaxInputTokens, spec.ContextWindow/2, spec.ContextWindow-spec.OutputReserve-spec.SafetyMargin)
// 新：limit := min(MaxInputTokens, spec.ContextWindow-spec.OutputReserve-spec.SafetyMargin)
```

- 容量等式由 `W−预留−安全边际` 独立保证；body 侧输出预留仍按半窗封顶
  （2026-11-11 语义不变）⇒ 输入恒 ≥ 半窗（兑现 11-11 的修复意图），输出保底不变。
- 事故形状新预算：200k−32k = **168k > 109,337** ⇒ 放行；ask ≥ 半窗时新旧同值
  （封顶预留=半窗 ⇒ W−W/2=W/2），交界行为钉死。
- 真超窗（est > W−预留）仍拒/走 fit——上游容量裁决权分层哲学（2026-11-10）不变；
  估计器对 CJK 低估（runes/3.5 ≈ 0.29 token/字）的残余误差由上游 context_length
  错误 + 网关既有恢复链兜底（`handleContextLengthRecovery` 成熟在役）。
