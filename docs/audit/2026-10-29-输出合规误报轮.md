## §0 结论一句话

211 生产实测（24h）：输出合规拦掉 **6 个请求**，每个**已经流出** 3806~10529 个
chunk，客户端最终只拿到 **801 字节**（keepalive + 空错误帧）；而 21 条审核单的
`rule_id` / `reason` / `field_path` / `payload_digest` **全部为空**。根因 =
强制输出守卫的**待检缓冲越界**返回了一个**不带任何元数据、也不打任何日志**的
`ShouldBlock` ⇒ 客户端整条响应作废 + 审核单空白 ⇒ 审核员既说不出「因为什么规则
被拦」，也**批不了**（放行键是 (租户, 规则)，规则为空 ⇒ 批准等于什么都没做 ⇒
同一个误报无限复发）。本轮三件事：**① 守卫不再杀响应**（越界降级放行 + 留痕，
出厂上限 1 MiB → 8 MiB 且可配）；**② 拦截审核工作台**（原始会话内容的有界摘录 +
人工标注 + 规则级读数 + 误报累计到阈值自动放行）；**③ 管理面**（输出合规全局
开关的专属入口 + 标注/读数端点 + 前端审核页显示命中的规则与原始内容）。

## §2 根因链：为什么审核单是空白的

```
强制输出守卫（domains/hooks/outputcompliance/stream_compliance.go）
  └─ 待检缓冲累计超过 1 MiB 上限
       └─ overCapacityResult() 返回 &response.ChunkResult{ShouldBlock: true}
            ★ **Metadata 为空、且不打任何日志**
            └─ 写者看到 ShouldBlock ⇒ 判定「策略拦截」
                 ├─► 渲染失败终帧 ⇒ 客户端整条响应作废
                 └─► 登记审核单（只有 rule/reason/field/digest 四个来源）
                      └─ 四个来源**全部来自拦截元数据** ⇒ 全部为空 ⇒ **空白审核单**
```

★ **关键点**：审核单不是「记录失败」，它**准确地记录了一个没有元数据的拦截**。
上一轮（917）把审核单落库是对的，但**上游**（守卫）从来没给过它可记录的东西 ⇒
★ **落库这件事本身救不了「上游没说话」**。

★ **审批为什么也救不了**：放行键 = (租户, scope, 规则, 载荷摘要)。规则为空 ⇒
即使审核员点了「批准」，写进放行表的也是一条**空规则**的放行 ⇒ 既放行不了这次
拦截，也**没有把规则**记下来 ⇒ 下一次照样拦、照样空白 ⇒ **无限复发**。

## §3 三件事的落点

### 3.1 守卫不再杀响应（`domains/hooks/outputcompliance/`）

| 动作 | 形态 | 为什么 |
|---|---|---|
| 出厂上限 1 MiB → **8 MiB** | `LLM_GATEWAY_OUTPUT_GUARD_PENDING_MAX_BYTES` 可配 | 1 MiB 正好落在真实 agent 响应的分布里 ⇒ 那台误报机器的来源 |
| 默认模式 **release** | 放行已逐帧检查过的帧、后续帧逐帧放行 | 「装不下」是**容量**问题，不是**违规**问题 ⇒ 不该杀业务 |
| 降级**留痕** | `policy_rule=builtin.guard.capacity_exceeded` + `policy_degraded` + 摘录 | 不杀 ≠ 不可见 ⇒ 运维看得到「守卫在什么规模上让过步」 |
| 严格模式 **block** 保留 | fail-closed 不变，但**必须带规则名/原因** | 需要严格保证的部署仍有路可走；且审核单不再是空白的 |
| 降级也**登记审核单** | 走同一张审核表 | 与拦截同一条留痕路径 ⇒ 运维只有一个地方要看 |

★ **代价必须写明**：降级之后**不再做 lane 合并检查** ⇒ 跨帧拼接才看得出的形态
（一个被拆成多帧的凭据）在降级段可能漏检。这是「不杀业务」的代价，不是「更安全」。
需要严格保证的部署：调大上限，或用 `block` 模式 + 全局开关做取舍。

### 3.2 拦截审核工作台（`domains/sanitizerules/block_review_workbench.go` + 迁移 921）

| 能力 | 形态 | 为什么 |
|---|---|---|
| **证据** | 被拦内容以**有界摘录**（≤4 KiB）落进**证据表** `sanitize_block_evidence`，7 天 TTL | 审核员要判断「这次拦得对不对」，**必须看得到内容**；★ 单独一张表 ⇒ 917 的「审核记录表不含载荷原文」契约**不破** |
| **标注** | `false_positive` / `true_positive` / `rule_too_broad` / `needs_rule`，与 approve/reject **正交** | 状态回答「现在放不放行」，标注回答「这次拦得对不对」⇒ 后者是规则优化的**唯一**输入 |
| **自动优化** | 同租户同规则的误报标注累计到阈值（默认 3）⇒ 自动写入该租户该规则的 7 天放行（`source=auto_label`） | 误报**必须有出口**，否则审核员只能反复点「批准」；★ 与人工批准**同键同语义** ⇒ 撤销/过期/可见性同一条路；★ 规则是全局的，但误报是**租户事实** ⇒ 动作收窄到「租户 + 规则 + 一周」 |
| **读数** | 按规则聚合；误报率的分母是**有判断的记录数**（不是总量） | 用总量做分母 ⇒ 「没人看的记录」会把误报率稀释成**假绿** |

★ **合成规则不参与自动放行**（`builtin.guard.capacity_exceeded`）：那是**基础设施性**
规则（缓冲越界），不是内容规则 ⇒ 放行它对业务没有意义（容量问题靠上限/开关解决）。

### 3.3 管理面（`admin/sanitize_rules_output_check.go` + `web/`）

  approve/reject 正交）；**读数端点** `GET .../blocked-reviews/insights`。
