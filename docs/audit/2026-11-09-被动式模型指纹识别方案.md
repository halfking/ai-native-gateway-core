**时间**: 2026-11-09  
**目标**: 通过真实用户会话分析识别模型，零额外成本，难以规避  
**状态**: 设计方案

---

## 📋 执行摘要

### 核心思路

**从主动探针转向被动分析**：不发送额外的探测请求，而是从**真实用户会话**中提取统计特征，建立模型指纹。

### 优势

✅ **零成本**：不需要 240 次探针请求  
✅ **难规避**：上游无法区分监控流量和正常流量  
✅ **覆盖全面**：每个真实请求都是数据点  
✅ **实时检测**：流式响应时即可分析  

### 业界研究

| 论文 | 方法 | 准确率 | 关键特征 |
|------|------|--------|----------|
| **Traffic Analysis on Cloud LLM** (arXiv:2609.31877) | 加密流量元数据分析 | 97.7% | 包大小、方向、时序、突发结构 |
| **Browser Agent Fingerprinting** (arXiv:2605.14786) | UI行为追踪 | 96% F1 | 操作序列、交互时序 |
| **Inter-Token Timing** (arXiv:2502.20589) | Token间隔时间 | 高（未公布数值）| ITT分布 |

## 🔍 可提取的被动特征

### 1. 时序特征（Timing Fingerprints）⭐⭐⭐⭐⭐

**最有效**的被动信号，每个模型有独特的生成速度模式。

#### 1.1 Time-to-First-Token (TTFT)
```
TTFT = 第一个token返回时间 - 请求发送时间
```

**特征**：
- Opus: TTFT ~800-1200ms（推理深）
- Sonnet: TTFT ~400-600ms
- Haiku: TTFT ~200-400ms（快速）
- 量化模型: TTFT 显著降低

**采集**：从 SSE 流的第一个 chunk 时间戳

#### 1.2 Inter-Token Time (ITT) 分布
```
ITT_i = token_i 返回时间 - token_{i-1} 返回时间
```

**特征**：
- 每个模型的 ITT 分布形状不同
- 均值、方差、中位数、P95 都是指纹
- 量化模型 ITT 更短且更稳定

**采集**：SSE 流中每个 `data:` 块的时间戳差

**示例**（假设）：
```
Opus:   ITT_mean=45ms, ITT_std=12ms, ITT_p95=68ms
Sonnet: ITT_mean=35ms, ITT_std=8ms,  ITT_p95=52ms
Haiku:  ITT_mean=25ms, ITT_std=5ms,  ITT_p95=36ms
```

#### 1.3 吞吐量（Tokens/Second）
```
Throughput = total_tokens / (last_token_time - first_token_time)
```

**特征**：
- Opus: ~22 tokens/s
- Sonnet: ~28 tokens/s
- Haiku: ~40 tokens/s
- 量化模型: 可能 2x+ 更快（attest 的检测阈值）

---

### 2. Token 计数特征（Usage Fingerprints）⭐⭐⭐⭐

#### 2.1 Prompt Token 签名
```
对于固定的 system prompt，不同模型的 token 计数不同
```

**特征**：
- 同族模型可能共享分词器（Claude系列）
- 跨族模型分词器不同（Claude vs GPT）
- 量化不影响分词

**采集**：从 `usage.prompt_tokens` 字段

**示例**：
```
System: "You are a helpful assistant."
Opus:   7 tokens
GPT-4:  6 tokens
Haiku:  7 tokens (同族)
```

**应用**：
- 构建"标准提示词"的 token 签名表
- 真实请求的 prompt_tokens 与表对比
- 异常 → 可能换模型或注入隐藏 prompt

#### 2.2 Output Token 密度
```
Output_Density = completion_tokens / prompt_tokens
```

**特征**：
- 不同模型的输出详细程度不同
- Opus 倾向更详细（密度高）
- Haiku 更简洁（密度低）

---

### 3. 内容特征（Content Fingerprints）⭐⭐⭐

#### 3.1 词汇偏好（Vocabulary Bias）
```
统计高频词、特定短语的使用频率
```

**特征**：
- Opus: 偏好 "certainly", "specifically", "comprehensive"
- GPT-4: 偏好 "absolutely", "essentially", "crucial"
- Haiku: 更简洁，少用修饰词

**采集**：对 `content` 做词频统计（TF-IDF）

#### 3.2 格式偏好（Formatting Patterns）
```
Markdown 使用习惯、列表结构、代码块风格
```

**特征**：
- 是否使用 `###` vs `**bold**`
- 列表是否用 `-` vs `1.`
- 代码块是否标注语言

**采集**：正则匹配格式元素

#### 3.3 拒绝模式（Refusal Patterns）
```
当遇到敏感请求时的拒绝用语
```

**特征**：
- Opus: "I cannot assist with..." "I'm not able to..."
- GPT-4: "I'm sorry, but I can't..." "As an AI..."
- 每个模型的拒绝用语相对固定

---

### 4. 行为特征（Behavioral Fingerprints）⭐⭐⭐⭐

#### 4.1 思考链（Thinking）长度
```
对于相同复杂度的问题，思考token数不同
```

**特征**：
- Opus: 更深入思考，thinking tokens 多
- Haiku: 思考简短

**采集**：从 Anthropic 的 `thinking` 字段

#### 4.2 Tool Use 模式
```
对于相同场景，调用工具的频率和风格
```

**特征**：
- 是否倾向多次调用
- 参数构造风格
- 错误重试模式

**采集**：`tool_calls` 数量和内容

### Phase P3: 实时检测（1周）

#### P3-1: 被动判定逻辑
```go
// domains/modelcredibility/passive_verdict.go

type PassiveVerdict struct {
    TimingScore   float64  // 时序特征匹配度 (0-100)
    TokenScore    float64  // Token签名匹配度
    ContentScore  float64  // 内容特征匹配度
    
    OverallScore  float64  // 综合分
    Confidence    float64  // 置信度（样本量相关）
    
    Anomalies     []string
}

// EvaluatePassive 被动判定
func EvaluatePassive(observed *PassiveFeatures, baseline *PassiveFingerprint) PassiveVerdict {
    // 1. 计算 ITT 分布的 JSD
    // 2. 对比 TTFT/Throughput 偏差
    // 3. 验证 Token 签名
    // 4. 内容特征相似度
    
    // 综合打分
    overall := timingScore*0.6 + tokenScore*0.25 + contentScore*0.15
    
    // 置信度取决于样本量
    confidence := min(1.0, sampleCount / 100.0)
    
    return PassiveVerdict{...}
}
```

#### P3-2: 融合主动+被动
```go
// domains/modelcredibility/verdict.go 扩展

type Input struct {
    // ... 现有字段 ...
    
    // 新增：被动特征
    PassiveFeatures    *PassiveFeatures
    PassiveBaseline    *PassiveFingerprint
}

func Evaluate(in Input, cfg Config) Result {
    // ... 现有维度 ...
    
    // 新增：被动维度
    var passiveScore float64
    if in.PassiveFeatures != nil && in.PassiveBaseline != nil {
        pv := EvaluatePassive(in.PassiveFeatures, in.PassiveBaseline)
        passiveScore = pv.OverallScore * pv.Confidence  // 置信度加权
        
        scores.Measured = scores.Measured.Mark(DimPassive)
        
        // 时序异常
        if pv.TimingScore < 60 {
            anomalies = append(anomalies, AnomalyPassiveTimingMismatch)
        }
    }
    
    scores.Passive = passiveScore
    
    // 权重分配（被动优先，因为覆盖全量）
    SubScoreWeights[DimPassive] = 0.35      // 最高（新增）
    SubScoreWeights[DimBehavioral] = 0.20   // 从 0.25 调整
    SubScoreWeights[DimIdentity] = 0.20     // 从 0.30 调整
    SubScoreWeights[DimCapability] = 0.15   // 保持
    SubScoreWeights[DimConsistency] = 0.10  // 保持
    
    // 主动+被动双重告警
    if passiveScore < 70 && behavioralScore < 70 {
        // 两个独立维度都异常 → 高度可疑
        if verdict == VerdictUnknown {
            verdict = VerdictSuspected
        }
    }
    
    // ...
}
```

## 📊 效果对比

### 主动探针 vs 被动分析

| 维度 | 主动探针 | 被动分析 | 融合方案 |
|------|----------|----------|----------|
| **成本** | 高（240请求/节点） | 零 | 低 |
| **覆盖** | 定期扫描 | 全量实时 | 全面 |
| **准确率** | 高（JSD明确） | 中（需样本积累） | 最高 |
| **可规避性** | 易（识别探针） | 难（真实流量） | 最难 |
| **冷启动** | 快（立即探测） | 慢（需积累） | 快 |
| **检测延迟** | 分钟级 | 秒级 | 秒级 |

### 建议策略

**初始验证**（新凭据）：
1. 主动探针快速判定 → 立即获得 verdict
2. 同时启动被动采集 → 积累基线

**持续监控**（已验证凭据）：
1. 被动分析为主 → 零成本实时监控
2. 主动探针降频 → 每周1次或异常时触发

**异常处理**：
1. 被动检测到漂移 → 触发主动探针复核
2. 两者都异常 → 高置信度告警

## 💡 关键洞察

### 为什么被动比主动更难规避

1. **流量不可区分**：上游无法分辨哪些是监控请求
2. **统计稳健性**：即使上游随机放行/拦截，长期统计仍会暴露
3. **多维交叉验证**：时序+Token+内容，全部伪造成本极高

### 为什么需要主动+被动结合

1. **冷启动问题**：新凭据需要立即判定，被动需要样本积累
2. **低频模型**：使用量小的模型被动样本不足
3. **双重保险**：两个独立维度同时异常 → 高置信度

### 论文支持

- **Traffic Analysis** (97.7% 准确率) 证明时序特征足够强
- **ITT Fingerprinting** 证明加密流量仍可提取
- **Browser Agent** (96% F1) 证明行为序列可区分模型
