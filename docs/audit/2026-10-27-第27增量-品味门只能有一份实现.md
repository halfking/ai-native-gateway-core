## §5 覆盖移植：退役 ≠ 覆盖缩水

★ 孤儿门的 7 条判据里，**5 条与主实现重叠** ⇒ 退役本身不丢覆盖。
★ **但重叠的那 5 条里，V2（彩色侧边条）是主实现的弱版** —— 孤儿门那份认 **5 种写法**，
主实现第 1 版只认 **1 种**（`border-left:` 简写）：

| 写法 | 孤儿门 | 主实现第 1 版 | 主实现本轮后 |
|---|---|---|---|
| ① `border-left: 3px solid <色>`（简写） | ✅ | ✅ | ✅ |
| ② `border-left-width: 3px` + 颜色在 `border:`（长写） | ✅ | ❌ **漏** | ✅ |
| ③ 颜色写在**同族 modifier 规则**里（`.row` + `.row.is-ok`） | ✅ | ❌ **漏** | ✅ |
| ④ 伪元素画的窄色条（`::before` + 绝对定位 + ≤4px + 通高） | ✅ | ❌ **漏** | ✅ |
| ⑤ `box-shadow: inset 3px 0 0 <色>`（inset 阴影伪装） | ✅ | ✅ | ✅ |

⇒ ★★ **退役孤儿门若不移植 ②③④ ⇒ 门会变弱**（三种写法直接绕过一条硬禁）
⇒ ⇒ 本轮把 ②③④ 全部移植进主实现（`sideEdges` / `sideColor` / `buildColoredBorderIndex` /
`isStripePseudo` / `detectSideStripe`）⇒ ★ **退役 = 覆盖不许缩水**。

★ 移植**当场抓到一个真仓假阳性** ⇒ 而它的根因**不在移植的代码里，在提取器里**：

```
❌ web/src/components/live-topology/ClientRequestPanel.vue 272
   [V2-colored-side-stripe]  ★ 原来左沿是 3px 粗边（`border-left-width: 3px`），那是 craft-floor …
```

★ 那行代码在**一段 CSS 注释里**，注释本身在说「这条粗边**已经改掉了**」。
⇒ 根因：`extractCssBlocks` 按「括号深度归零」**逐行**切块 ⇒ **多行 CSS 注释被切成碎片**
⇒ 碎片里没有完整的 `/* … */` ⇒ 事后 `stripCssComments` **剥不掉**
⇒ ⇒ **注释里写的声明被当成真声明**。

⇒ ★★★ **根因修在提取器**（不修在移植的判据上）：新增 `maskCssComments`（**掩成等长空格**、
保留换行 ⇒ 行号与偏移都不变）⇒ **掩在切块之前** ⇒ 注释不再参与深度计算 ⇒ 不再被切碎；
另加一条「只有**含 `{` 的块**才是规则」⇒ 注释/空行不单独成块。
⇒ ★ **抬升门 `elevation.ts` 共用本提取器 ⇒ 一并受益**（实测：抬升层 65 层 / 不同取值 4 种 /
非规范配方 **0 处**，无漂移）。

★ 这条是本轮「量具自己会错」的第四例（前三次：第 11 增量「探针查得太早」/ 第 24 增量「区间守恒闸
算错区间」/ 第 26 增量「列表当单串」）。

## §12 通用式（已写入 `LESSONS.md` §474）

1. **★ 门红 ≠ 门对**：4 条分歧逐条判，判据是「craft-floor 原话 + 两份实现的文档」，
   不是「哪份实现更久」。
2. **★ 「注释里的承诺不算证据」对**注释**与对**文档**一样成立**：孤儿门两处
   「实现 < 自己的文档」⇒ 退役它的理由是硬证据，不是「它更差」。
3. **★ 退役 = 覆盖不许缩水**：孤儿门能认 5 种写法而主实现只认 1 种 ⇒
   先把缺的写法移植过来，再退役。
4. **★ 对拍脚手架必须先自证**：喂 CSS 样本给一个按 `.vue` 解析的实现 ⇒
   「11 条分歧」里 7 条是脚手架的错。
5. **★ 提取器的「区间」是一等公民**：逐行切块会把多行注释切碎 ⇒ 注释里的声明
   被当真 ⇒ 根因修在提取器（掩成等长空格 + 只有含 `{` 的块才是规则）。
6. **★ 一个概念只有一种画法**：移动端三处「精选」标记（按钮 / 标题 / 徽标）
   必须同一种画法，即使门只判其中一处。
7. **★ 门要覆盖全部应用**：移动端此前无人看守 ⇒ 同一个硬禁在两个应用里口径不同。
8. **★ 「有洞」不等于「该补」**：★ 量出 V3 还有一处 80 处的盲区 ⇒ ★ 试过补 ⇒ 多报 44 处
   ⇒ ★ 而其中一部分**按仓内自己的口径应当判绿** ⇒ ⇒ **回退** ⇒ ★★ 补之前先问
   「**这洞的口径对不对**」⇒ ★ 回退也要把**量测**写进文档（★ 让下一轮知道它有多大）。
9. **★ 既有门红要就地修**：★ 全量 Go 门红 3 条 ⇒ **都不是本轮引入**（对照树同样红）
   ⇒ ★ 但它们都**挡着验收** ⇒ ⇒ 归因清楚后就地修（★ 普查表补 3 条 + 生成器清单重生成
   ⇒ ★ 都是「按门自己写的修法」执行 ⇒ ★ 门把「怎么修」写在错误信息里 = 好门）。
10. **★ 「改完还红」≠「改错了」；★「0 命中」在量具选错时是【假阴性】**：验收时 parity 报
    「键 `x` 缺 8 语种」⇒ 第一版修法只改了一半 ⇒ 复跑仍红 ⇒ ★ 「改完还红」有三种读法
    （还有第二处来源 / 修法不完整 / 门错了）⇒ ★★ **先列来源清单，别急着改第二处** ⇒ ★★ 定位
    必须用「**事实源真正走的那条路径**」的量具（parity 走 `scanner.ts` 的 `scanAll`，**不是**
    `callSiteParams.ts` 的新扫描器 ⇒ 我先用新扫描器查 ⇒ **0 命中** ⇒ 差点判「没有来源」
