## §0 摘要：一句话结论

★★ **「多环境同一标准」这件事，此前只被当成【迁移集合】的问题；本轮实测证明它至少是三个独立的问题，而其中两个此前【完全没人查过】。**

| 层 | 问题 | 本轮结论 |
|---|---|---|
| **① 执行集合** | 新装环境能跑到哪些迁移？ | ★ **312 条**（= 安装器登记清单 = 分发包）⇒ 仓内 **581 条 startup 里有 271 条新装永远跑不到** |
| **② 执行效果** | 这些迁移在环境里建出了什么？ | ★ 期望集 **834** 条索引中，★ **369** 条新装有、★ **342** 条**只因 `01-schema.sql` 是一份 dump 才有**、★ **49** 条新装**必然缺**、★ **74** 条合法退役 |
| **③ 执行顺序** | 同一套迁移、同样的编号，终态一样吗？ | ★★ **不一样**。★ 实测 211 上 `708`（删死列）先跑、`456`（加回死列）后跑 ⇒ ★★ **死列复活、索引复活**；★ 而 local 是 `456 → 708` ⇒ **两个环境终态相反** |

⇒ ⇒★ **结论一**：新装环境**没有任何一条**期望索引是因为「安装器自己有 bug」而缺（`installer-bug=0`）⇒ ⇒ **49 条缺口 100% 归因于「创建迁移不在安装器可达集」** ⇒ ⇒ 修法唯一。
⇒ ⇒★ **结论二**：★ **342 / 834 = 41%** 的期望索引，新装环境能拥有它们**只因为 `01-schema.sql` 是一份 pg_dump** ⇒ ⇒ **安装器基线不可由安装器自身的迁移集复现** ⇒ ⇒ 仓内脚本自己写着这句话（§6.3）。
⇒ ⇒★ **结论三**：★★ 本轮在修 bug 的过程中，**又挖出 R161/R162 两轮都漏掉的一类假数据**（`ON ONLY`）⇒ ⇒ **它掩盖了 7 条真缺口** ⇒ ⇒ 「三环境在索引层面完全一致」这个 R161 结论的一部分是假的（§3）。

## §3 头号发现一：★「`ON ONLY <table>`」被吃成表名 `ONLY` ⇒ ★ **7 条真缺口被彻底掩盖**

### §3.1 现象

★ 期望集推导的正则原本是：

```
CREATE … INDEX <name> ON <table> …
```

⇒ ⇒ 而仓内真实 SQL 有 **`ON ONLY <table>`** 这种形态（★ 分区父表索引的常见写法，★ 实测 17 条）。
⇒ ⇒ 老正则的表名捕获组是 `[a-z0-9_."]+` ⇒ ⇒ **`ONLY` 被当成了表名**。

### §3.2 危害：**假退役** ⇒ **掩盖真缺口**

★★ 缺口台账的状态判定顺序是：索引在？→ 父索引的子索引？→ **表在不在？** → 缺。
⇒ ⇒ 表名写成 `ONLY` ⇒ ⇒ `pg_class` 里当然没有一张叫 `ONLY` 的表 ⇒ ⇒ 判成 **`retired`**（已退役）⇒ ⇒ **不是缺口**。

★ 实测被掩盖的：

| 索引 | 真实表 | 修前四环境状态 | 修后 |
|---|---|---|---|
| `idx_routing_decision_log_canonical_ts` | `routing_decision_log` | retired / retired / retired / retired | ★ **missing ×4** |
| `idx_routing_decision_log_cred_ts` | 同上 | retired ×4 | ★ **missing ×4** |
| `idx_routing_decision_log_identity_hash` | 同上 | retired ×4 | ★ **missing ×4** |
| `idx_routing_decision_log_model_ts` | 同上 | retired ×4 | ★ **missing ×4** |
| `idx_routing_decision_log_request_id_ts` | 同上 | retired ×4 | ★ **missing ×4** |
| `routing_decision_log_ts_idx` | 同上 | retired ×4 | ★ **missing ×4** |
| `idx_tool_usage_stats_tool_date` | `tool_usage_stats` | retired ×4 | ★ **missing ×4** |

★★ **⇒ 7 条真缺口（四环境全缺，其中 6 条在生产也缺）在 R161/R162 两轮里一直被标成「已退役」⇒ ⇒ 从未进过任何工单。**

★★ **方向很重要**：R162 修的是「**假缺口**」（★ 害处：会诱导人去「补建」被刻意退役的索引）；本条是「**假退役**」（★ 害处：**会掩盖真缺口**）⇒ ⇒ **两个方向都会骗人，只修一个方向等于没修。**

### §3.3 另一组被掩盖的：4 条新装缺口

★ 同一 bug 还掩盖了 4 条**只有新装环境缺**的索引（★ 它们在 local/252/211 都在）：

- `idx_session_turns_effective_session`（★ 迁移 727）
- `idx_session_turns_credential_ts`（★ 迁移 729）
- `idx_session_turns_digest_null`（★ 迁移 744）
- `idx_usage_facts_occurred_at`（★ 迁移 749）

★★ 而这 4 条**恰好**是原始目标第 4 条（★ 「优化请求的列表、查询、写入过程的效率，**不要有表扫描或慢 SQL**」）最该关心的那类索引 ⇒ ⇒ **它们此前被标成「已退役」，等于从未被任何人看见。**

### §3.4 顺带澄清两条「巧合对了」的

★ `idx_request_logs_client_model_trgm` / `idx_request_logs_credential_model_ts`（★ 表是 `request_logs`）修前也判 `retired`，修后**仍然**判 `retired` —— ★ 因为 860 已把 `request_logs` 改名成 `_request_logs` ⇒ ⇒ **这两条是真退役**，只是此前「蒙对了」。

### §3.5 修法与互证

★ 修法：两侧（Python 工具 + Go 门）**都**显式容忍 `ON ONLY` ⇒ ⇒ 并各加一条自证钉死。
★★ **★ 关键**：★ 这个 bug **两侧一模一样** ⇒ ⇒ **互证对那批是零信息**（★ R162 教训的又一次实证）⇒ ⇒ 所以两侧都必须改，且自证必须**点名这个形态**。
★ Python 侧自证：`expect/no-only-as-table-name` + `expect/only-form-table-resolved`；Go 侧：`dbObjExpect` 的表名逐条比对（★ `TestDbObjectExpectSetMatchesIndependentDerivation` 现在连**声明列**一起逐条比）。

## §4 头号发现二：★「删列 ⇒ PG 级联删索引」⇒ ★ **假缺口的第三种来源**

### §4.1 现象与机制

★ PG 的 `DROP COLUMN` 会**自动删掉**依赖该列的索引（★ 不需要、也不会留下 `DROP INDEX` 语句）。
⇒ ⇒ 而期望集的推导是「**建了 − 被显式 DROP**」的差集 ⇒ ⇒ **这类索引永远看不到自己被删** ⇒ ⇒ **永远留在期望集里** ⇒ ⇒ 永远被判成「该建没建」。

★ 实测命中 5 条：

| 索引 | 表 | local | fresh | 252 | 211 |
|---|---|---|---|---|---|
| `idx_sessions_last_full_at` | `sessions` | retired-by-column-drop | retired-by-column-drop | retired-by-column-drop | ★ **present** |
| `idx_stats_reconciliation_diffs_tenant` | `stats_reconciliation_diffs` | retired-by-column-drop | present | present | present |
| `idx_stats_adjustments_type` | `stats_adjustments` | retired-by-column-drop | present | present | present |
| `idx_stats_reconciliation_diffs_run_tenant_dim_metric` | `stats_reconciliation_diffs` | retired-by-column-drop | present | present | present |
| `idx_goal_run_steps_tenant_request` | `goal_run_steps` | retired | retired-by-column-drop | retired-by-column-drop | retired-by-column-drop |

★★ **⇒ 新增第 5 态 `retired-by-column-drop`**（★ **不是**缺口）⇒ ⇒ 「缺口台账」终于能区分「没建」与「**合法地不在了**」。

### §4.2 因果链的实测钉死（★ 不是推测）

★ 迁移 708（`708_session_bodies_s1a.sql`）里有：

```sql
ALTER TABLE public.sessions
    DROP COLUMN IF EXISTS last_full_request,
    DROP COLUMN IF EXISTS last_full_response,
    DROP COLUMN IF EXISTS last_full_payload_at;
```

★ 并且**带后置断言**（★ 列还在就 `RAISE EXCEPTION`）⇒ ⇒ **708 一旦跑成功，那三列必然消失**。
★ 实测四环境：

| 环境 | `sessions.last_full_payload_at` 列 | `idx_sessions_last_full_at` 索引 |
|---|---|---|
| 252 | **无** | **无** |
| fresh（新装） | **无** | **无** |
| local | **无** | **无** |
| 211 | ★ **有** | ★ **有** |

⇒⇒★ **列与索引的存在性逐字同步** ⇒⇒ **因果链钉死** ⇒⇒ ★★ 而 211 的「例外」不是随机噪声，是 §5 的**顺序倒置**。

### §4.3 保守口径（★ 为什么只取「直接键列」）

★ 解析索引的**声明键列**时，★ **表达式索引不取列名**（★ `lower(email)` / `(a->>'b')` 一律跳过）。
★★ 理由：★ 取错列名 ⇒ 把活索引误判成「被列级联退役」⇒ ⇒ **假缺口从「缺」翻成「不该有」** ⇒ ⇒ **两个方向都会骗人** ⇒ ⇒ 只在**证据明确**时退役。
★ 已知未穷尽：★ 表达式索引与 `INCLUDE` 列不做退役判定（★ ⇒ 保守方向：可能仍留一条假缺口，★ 不做假退役）。

## §5 头号发现三：★★ **同一套迁移，顺序不同 ⇒ 终态相反**

### §5.1 硬证据（★ 两个环境的账本时间戳）

★ `gateway_db_revision_sequences.applied_at`（★ 各环境自己的账本）：

| 环境 | `456_session_v2_display_columns.sql`（**加**死列） | `708_session_bodies_s1a.sql`（**删**死列） | 终态 |
|---|---|---|---|
| **local** | 2026-10-20 **21:58:43** | 2026-10-20 **21:59:32**（★ 49 秒后） | ★ 456 → 708 ⇒ **列被删** ⇒ 索引随 PG 级联消失 |
| **211** | 2026-10-17 **00:34:14** | 2026-10-11 **00:16:56**（★ 早 6 天） | ★ 708 → 456 ⇒ **列被加回** ⇒ 索引复活 |

⇒ ⇒★ **⇒ 211 上 `sessions` 现在还带着那三个本该被 708 删掉的死列**（★ `last_full_request` / `last_full_response` / `last_full_payload_at`，★ 且 `last_full_payload_at` 是 `timestamptz`、另两个是 `jsonb`）。
⇒ ⇒★ **⇒ 而且 211 上还多了一个本该被删掉的索引** ⇒ ⇒ **211 的 schema 比其它环境【更旧】**，尽管它的账本里写着「708 已应用」。

### §5.2 为什么这比「多一条索引」严重

★★ **708 的意图是删掉三列「零读写、100% NULL」的死列**（★ 迁移自己的注释这么写）。
★★ **⇒ 211 上这三列没删掉 ⇒ ⇒ 每一行 `sessions` 都还在背着两个 jsonb 列** ⇒ ⇒ 这是**写放大 + 存储 + TOAST** 的真实成本。
★★ ⇒ 而且它**悄悄复活**：★ 708 的后置断言在**当时**是过的（★ 那时列确实被删了）⇒ ⇒ **没有任何报错、没有任何告警** ⇒ ⇒ 只有把两个环境的**执行顺序**摆在一起才看得见。

### §5.3 顺序从哪来（★ 三层口径互不相同）

| 口径 | 456 与 708 的相对位置 | 来源 |
|---|---|---|
| ★ 迁移**编号** | 456 < 708 | 编号本身 |
| ★ 仓内 `sql/migrations/startup/` **文件名序** | 456 < 708 | 文件名 |
| ★ 安装器 `StartupFiles` **apply-order** | 456 = index 6，708 = index 158 ⇒ **456 → 708** | `installed_startup_migrations.tsv` |
| ★ 部署通道脚本**清单序** | 456 在第 283 行，708 在第 823 行 ⇒ **456 → 708** | `scripts/apply-db-revision-sequence.sh` |
| ★★ **211 的实际执行序** | ★★ **708 → 456** | ★★ `gateway_db_revision_sequences.applied_at` |

⇒ ⇒★ **⇒ 两条通道声明的顺序都是 456 → 708，而 211 实际跑成了 708 → 456** ⇒ ⇒ **执行顺序既不等于编号序，也不等于清单序** ⇒ ⇒ **「登记了」与「按什么顺序登记的」是两件事**。

★★ **⇒ 推测（已标注为推测）**：★ 456 在 211 上大概率**先失败过、后来才重试成功**（★ 它的账本行时间是 10-17，比 708 晚 6 天）⇒ ⇒ **旧迁移的重试跑在新迁移之后 ⇒ 撤销了新迁移的效果**。
★★ ★★ **这条推测本轮没有直接证据**（★ 需要 211 的迁移执行日志）⇒ ⇒ 列在 §9 诚实边界里。

### §5.4 机器可读的指纹

★ §4.2 那张表里，★ `idx_sessions_last_full_at` 在**三个环境**判 `retired-by-column-drop`、在 **211** 判 `present` ⇒ ⇒ **这就是「顺序倒置」的机器可读指纹**（★ 将来任何环境出现同一形态，都会被这道门立刻看见）。
