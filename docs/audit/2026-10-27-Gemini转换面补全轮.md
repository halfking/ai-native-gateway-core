## 1. 本轮要解决什么

§433 的「本轮明确没做」清单里剩三项（原生模型列表 / `:countTokens` / `citationMetadata` 捕获 /
原生出站 executor）。本轮先做其中**两份保留厂方文档明确写死**的一项：

> `docs/vendor-formats/gemini.md` §特殊字段（IR 映射）
> | `citationMetadata` | Gemini 在响应中提供引用元数据，IR 需要捕获并可在序列化为 OpenAI 时映射为 annotations | |

⇒ **判据成立**：厂方文档要求 IR 捕获。

## 2. ★ 缺口定性：**能力缺口**，不是「本轮症状」

实测（修复前）：`internal/ir` **根本没有承载引用元数据的字段** ⇒
`ParseGeminiResponse` 解析完就把 `citationMetadata` 扔了 ⇒
引用在**解析那一步**就没了，后面任何序列化都无从谈起。

⇒ 与 §433 通用式十同源：**「压根没实现」与「实现错了」是两族**。
  本项属前者 ⇒ 它是**独立能力**，不修它，用户报的「认证没通过」也不会好；
  但它确实是**厂方文档写死的契约**，且实现面很小 ⇒ 值得单独一轮补上。

★ 明确本轮**不做**的（避免把无关特性拖进这一轮）：
原生模型列表（需 `cmd/gateway/main.go` 接线 + 数据形状决策）、
`:countTokens`（需要**诚实**的 token 计数；用估算值会误导客户端 ⇒ 独立设计题）、
原生出站 executor（另起一节）。

## 3. 实现

### 3.1 IR 承载

```go
// internal/ir/response.go
type ResponseCitation struct {
	URL        string `json:"url,omitempty"`
	Title      string `json:"title,omitempty"`
	StartIndex int    `json:"start_index,omitempty"`
	EndIndex   int    `json:"end_index,omitempty"`
}
// InternalResponse.Citations []ResponseCitation
```

★ **归一字段名**：Gemini 原生叫 `uri`，OpenAI 叫 `url` ⇒ IR 里统一叫 `URL`
（否则序列化侧到处要做别名判断 ⇒ 又是一份「同一句话两份」）。

### 3.2 解析（Gemini → IR）

`ParseGeminiResponse` 读 `candidates[0].citationMetadata.citations[]`
（字段 `uri` / `title` / `startIndex` / `endIndex`）⇒ 写入 `resp.Citations`。

★ **无 URI 的引用不进 IR**：客户端点不动 ⇒ 丢弃（而不是产出一个 url 为空的 annotation）。

### 3.3 序列化（IR → OpenAI / IR → Gemini）

- **OpenAI**（厂方文档指定的映射方向）：`message.annotations[]`，
  每项 `{"type":"url_citation","url_citation":{url,title,start_index,end_index}}`。
- **Gemini**（往返）：`candidates[0].citationMetadata.citations[]`，字段名回到 `uri`。

★ **两个「不凭空补 0」的纪律**：
  `start_index` / `end_index` 为 0 时**不发这个键** ⇒
  否则等于**声称**「这段引用从偏移 0 开始」，而上游可能只是没给跨度信息。

★ **没有引用时，两个方向都不新增任何键** ⇒ 普通响应的报文**逐字不变**
  （不塞一个空的 `annotations: []` ⇒ 不给客户端 SDK 引入新的空字段）。

# 子项 ②：Gemini 原生出站 executor

## 6. ★ 缺口定性：**死配置**（catalog 承诺了，dispatcher 一律跳过）

§433 结尾写下的那句「仍不实现」的原文：

> 描述的「Gemini executor + `x-goog-api-key` 出站头」**仍未实现**。

实测（修复前）：

| 事实 | 位置 |
|---|---|
| catalog 把 `gemini-generate` 列为合法 outbound 协议 | `provider/catalog/protocol.go:25` |
| DB CHECK 约束含 `gemini-generate` | `sql/schema/01-schema.sql:11641` |
| Web UI 的协议下拉里有 `gemini-generate` | `web/src/views/ProvidersView.vue:1272` |
| 协议归一化把 provider 配的 `gemini` **映射成** `gemini-generate` | `provider/catalog/protocol_normalize.go:120` |
| dispatcher 把每个 `gemini-generate` 候选**整条跳过** | `executor_dispatch.go`（`routeUnsupportedGemini`） |

⇒ ★ **这不是「功能没做」，是「配置即死」**：运维在 UI 里把 provider 协议选成
`gemini-generate`（或把 `gemini` 写进配置让归一化器转过去）⇒ 该 provider
**永远不会被选中**，且失败形态是 `KindUnsupportedFeature` ⇒ 不毒化凭据统计，
但也**永远不产出一包响应**。

★ 而 `provider/catalog/contract_test.go` 里那条 `ProtocolGeminiGenerate: false`
**就是这件事的账本**——它明文写着「gemini-generate 在 executor_dispatch.go:842
是显式 unsupported」⇒ 本轮把它翻成 `true`，并同时把**判据留在门里**。

## 7. 实现（照抄仓内既有的设计书，不自创协议）

`docs/供应商协议优化.md` §8.3「Gemini executor 新增实现」**逐条点名了四个配料**：

> - 复用 `internal/upstreamurl.GenerateContentURL(cand.BaseURL, model)`（需要在 upstreamurl 包加 `GenerateContentURL` 函数，路径模板 `:generateContent` / `:streamGenerateContent`）
> - 序列化：直接走已有 `SerializeGemini`（IR 层）
> - Header：`x-goog-api-key: <key>` 或 `?key=<key>`（与 endpoint 的 `header_profile_code` 关联）
> - 流式走 `internal/ir/parse_gemini_stream.go` 已有的解析路径

⇒ 本轮**照这四条实现**，不新增协议语义：

| 配料 | 实现位置 | 备注 |
|---|---|---|
| URL | `internal/upstreamurl/upstreamurl.go` → `GenerateContentURL` | ★ **base URL 拥有版本段**（`/v1beta` 保留、`/v1` 保留；无版本才默认 `/v1beta`） |
| 请求体 | `ir.SerializeGemini` | IR 层 SSOT，不重写 |
| 凭据 | `x-goog-api-key` 头 | ★ **不用 `?key=`**（见 §8） |
| 流式 | `ir.ParseGeminiStreamChunk` | ★ 顺带补了它吞厂商错误帧的洞（§7.2） |

### 7.1 URL 构造（`upstreamurl.GenerateContentURL`）

```
POST {base}/v1beta/models/{MODEL}:generateContent
POST {base}/v1beta/models/{MODEL}:streamGenerateContent?alt=sse
```

三条判定：

1. **版本段归 base URL 所有**：base 配了 `/v1beta` 就用 `/v1beta`，配了 `/v1` 就用
   `/v1`，**都没有**才默认 `/v1beta`（厂方格式文档写死的那个版本）。
   ⇒ ★ **绝不把 `/v1` 改写成 `/v1beta`**——那是「在运维配置的路径上静默改协议」。
2. **模型在 URL 里，不在 body 里** ⇒ Gemini 的 API 是**模型作用域**的。
   ⇒ body 里**不带** `model` 字段（多了反而会让厂商困惑）。
3. ★ **粘贴完整 endpoint URL 当 base 也能用**：`/models/{model}:{action}` 后缀会被
   剥掉再重建（与 OpenAI 家族 `Build()` 对「粘贴完整路径」的处理同款）。
   ⇒ 幂等性由 `TestGenerateContentURL_Idempotent` 钉住。

### 7.2 ★ 顺带发现并修掉的一个洞：IR 流解析器**吞掉厂商错误帧**

`ir.ParseGeminiStreamChunk` 的原始结构体里**没有 `error` 字段** ⇒ 一帧
`data: {"error":{"code":429,"message":"resource exhausted","status":"RESOURCE_EXHAUSTED"}}`
解析出来是一个**空 chunk**（既无 candidates 也无 usage）⇒ 与「心跳保活帧」**不可区分**
⇒ **厂商错误被静默吞掉**，客户端只看到一段被截断的流。

★ 修在 **IR 层**（事实源），不在 executor 层：
`internal/ir/parse_gemini_stream.go` 增加 `error` 字段 + 在 usage/candidate 分支**之前**
判定 ⇒ 产出 `ChunkTypeError`。
⇒ 与 Ollama 解析器同款分支（`parse_ollama_stream.go` 早就有）。

★ 顺序很关键：错误判定必须**在** usage/candidate 分支**之前**——
错误帧两者都没有，放后面就永远走不到。

## 8. ★ 凭据形态：**只走头，不进 URL**

厂方 API 两种都收（`x-goog-api-key` 头 / `?key=` query），
`docs/供应商协议优化.md` §8.3 也把两种都列了。**本轮只走头**：

- `?key=` 会进**每一条** access log、**每一条** upstream-URL 日志行、
  **每一行**记录请求 URL 的 telemetry ⇒ 凭据落盘。
- 头形态对厂商完全等价（Google 自己的 SDK 就用头）。

⇒ **反向钉**：`TestGeminiExecutor_BuildRequest_CredentialNeverInURL`
断言 **URL 里既不含凭据、也不含任何 query**。
★ 这条判据的含义：「厂商接受」≠「我们要用」。

## 9. 客户端侧线格式：**只接 OpenAI Chat 一种，其余 fail closed**

| 客户端协议 | 本轮状态 |
|---|---|
| `openai-completions`（含 **Gemini 原生客户端**） | ✅ 已接 |
| `anthropic-messages` | ❌ `KindUnsupportedFeature`（fail closed） |
| `openai-responses` | ❌ `KindUnsupportedFeature`（fail closed） |

★ **为什么 Gemini 原生客户端算「OpenAI Chat 客户端」**：
Gemini 入向 handler（`domains/streaming/handler_gemini.go` step 6）在派发**之前**
就把 Gemini body 转成了 OpenAI 形状 ⇒ dispatcher 用 `ir.DetectProtocol` 看到的是
`openai-completions` ⇒ 响应也是 OpenAI 形状 ⇒ **由 Gemini handler 自己再转回 Gemini 形状**。
⇒ ★ **`gemini-generate` 这个字符串永远不会作为「入向客户端协议」出现**（这一点值得钉死，
否则下一个人会以为 executor 要自己处理 Gemini 形状的响应）。

★ **其余两种为什么 fail closed 而不是「尽力转一下」**：
错形状的 200 比明确的「没接线」错误更糟——客户端 SDK 会在离病因很远的地方解析失败。
⇒ 与已上线的 Ollama-native executor 同一口径（`finalizeOllamaUpstreamBody` gate 2）。

## 10. 本轮明确没做（留给下一轮，别重复排查）

- **Gemini 原生模型列表**（`GET /v1beta/models`）——需要 `cmd/gateway/main.go` 接线
  （并行会话正在改该文件），且要决定返回形状（原生 Gemini 形状 vs OpenAI `/v1/models` 形状）。
- **`:countTokens`**——需要**诚实**的 token 计数。用估算值会误导客户端
  （客户端会拿它做配额判断）⇒ 独立设计题，不能顺手用估算糊过去。
- **`anthropic-messages` / `openai-responses` 客户端侧线格式**（§9）——需要 Anthropic
  SSE 严格帧（`message_start` → `content_block_delta` → `message_stop`）与 Responses
  的 `response.completed` 编排；两者在 IR 层都有序列化器，但**流式终态的编排**
  （谁写 `message_start`、谁写 `response.completed`）尚未接线。
- **Gemini 上游的 `header_profile_code` 联动**——§8.3 提到凭据形态与
  `header_profile_code` 关联；本轮固定走 `x-goog-api-key`，未接 profile 表。
- **Gemini 上游的上下文超限压缩恢复**（Ollama 路径有 `handleContextLengthRecovery`
  的递归重试）——本轮只做一次尝试，不做压缩重发。
