## 1. 本轮要解决什么

§433 的「本轮明确没做」清单里剩三项（原生模型列表 / `:countTokens` / `citationMetadata` 捕获 /
原生出站 executor）。本轮先做其中**两份保留厂方文档明确写死**的一项：

> `docs/vendor-formats/gemini.md` §特殊字段（IR 映射）
> | `citationMetadata` | Gemini 在响应中提供引用元数据，IR 需要捕获并可在序列化为 OpenAI 时映射为 annotations | |

⇒ **判据成立**：厂方文档要求 IR 捕获。

## 2. ★ 缺口定性：**能力缺口**，不是「本轮症状」

实测（修复前）：`internal/ir` **根本没有承载引用元数据的字段** ⇒
`ParseGeminiResponse` 解析完就把 `citationMetadata` 扔了 ⇒
引用在**解析那一步**就没了，后面任何序列化都无从谈起。

⇒ 与 §433 通用式十同源：**「压根没实现」与「实现错了」是两族**。
  本项属前者 ⇒ 它是**独立能力**，不修它，用户报的「认证没通过」也不会好；
  但它确实是**厂方文档写死的契约**，且实现面很小 ⇒ 值得单独一轮补上。

★ 明确本轮**不做**的（避免把无关特性拖进这一轮）：
原生模型列表（需 `cmd/gateway/main.go` 接线 + 数据形状决策）、
`:countTokens`（需要**诚实**的 token 计数；用估算值会误导客户端 ⇒ 独立设计题）、
原生出站 executor（另起一节）。

## 3. 实现

### 3.1 IR 承载

```go
// internal/ir/response.go
type ResponseCitation struct {
	URL        string `json:"url,omitempty"`
	Title      string `json:"title,omitempty"`
	StartIndex int    `json:"start_index,omitempty"`
	EndIndex   int    `json:"end_index,omitempty"`
}
// InternalResponse.Citations []ResponseCitation
```

★ **归一字段名**：Gemini 原生叫 `uri`，OpenAI 叫 `url` ⇒ IR 里统一叫 `URL`
（否则序列化侧到处要做别名判断 ⇒ 又是一份「同一句话两份」）。

### 3.2 解析（Gemini → IR）

`ParseGeminiResponse` 读 `candidates[0].citationMetadata.citations[]`
（字段 `uri` / `title` / `startIndex` / `endIndex`）⇒ 写入 `resp.Citations`。

★ **无 URI 的引用不进 IR**：客户端点不动 ⇒ 丢弃（而不是产出一个 url 为空的 annotation）。

### 3.3 序列化（IR → OpenAI / IR → Gemini）

- **OpenAI**（厂方文档指定的映射方向）：`message.annotations[]`，
  每项 `{"type":"url_citation","url_citation":{url,title,start_index,end_index}}`。
- **Gemini**（往返）：`candidates[0].citationMetadata.citations[]`，字段名回到 `uri`。

★ **两个「不凭空补 0」的纪律**：
  `start_index` / `end_index` 为 0 时**不发这个键** ⇒
  否则等于**声称**「这段引用从偏移 0 开始」，而上游可能只是没给跨度信息。

★ **没有引用时，两个方向都不新增任何键** ⇒ 普通响应的报文**逐字不变**
  （不塞一个空的 `annotations: []` ⇒ 不给客户端 SDK 引入新的空字段）。

**就是这件事的账本**——它明文写着「gemini-generate 在 executor_dispatch.go:842

## 7. 实现（照抄仓内既有的设计书，不自创协议）

`docs/供应商协议优化.md` §8.3「Gemini executor 新增实现」**逐条点名了四个配料**：

> - 复用 `internal/upstreamurl.GenerateContentURL(cand.BaseURL, model)`（需要在 upstreamurl 包加 `GenerateContentURL` 函数，路径模板 `:generateContent` / `:streamGenerateContent`）
> - 序列化：直接走已有 `SerializeGemini`（IR 层）
> - Header：`x-goog-api-key: <key>` 或 `?key=<key>`（与 endpoint 的 `header_profile_code` 关联）
> - 流式走 `internal/ir/parse_gemini_stream.go` 已有的解析路径

⇒ 本轮**照这四条实现**，不新增协议语义：

| 配料 | 实现位置 | 备注 |
|---|---|---|
| URL | `internal/upstreamurl/upstreamurl.go` → `GenerateContentURL` | ★ **base URL 拥有版本段**（`/v1beta` 保留、`/v1` 保留；无版本才默认 `/v1beta`） |
| 请求体 | `ir.SerializeGemini` | IR 层 SSOT，不重写 |
| 凭据 | `x-goog-api-key` 头 | ★ **不用 `?key=`**（见 §8） |
| 流式 | `ir.ParseGeminiStreamChunk` | ★ 顺带补了它吞厂商错误帧的洞（§7.2） |

### 7.1 URL 构造（`upstreamurl.GenerateContentURL`）

```
POST {base}/v1beta/models/{MODEL}:generateContent
POST {base}/v1beta/models/{MODEL}:streamGenerateContent?alt=sse
```

三条判定：

1. **版本段归 base URL 所有**：base 配了 `/v1beta` 就用 `/v1beta`，配了 `/v1` 就用
   `/v1`，**都没有**才默认 `/v1beta`（厂方格式文档写死的那个版本）。
   ⇒ ★ **绝不把 `/v1` 改写成 `/v1beta`**——那是「在运维配置的路径上静默改协议」。
2. **模型在 URL 里，不在 body 里** ⇒ Gemini 的 API 是**模型作用域**的。
   ⇒ body 里**不带** `model` 字段（多了反而会让厂商困惑）。
3. ★ **粘贴完整 endpoint URL 当 base 也能用**：`/models/{model}:{action}` 后缀会被
   剥掉再重建（与 OpenAI 家族 `Build()` 对「粘贴完整路径」的处理同款）。
   ⇒ 幂等性由 `TestGenerateContentURL_Idempotent` 钉住。

### 7.2 ★ 顺带发现并修掉的一个洞：IR 流解析器**吞掉厂商错误帧**

`ir.ParseGeminiStreamChunk` 的原始结构体里**没有 `error` 字段** ⇒ 一帧
`data: {"error":{"code":429,"message":"resource exhausted","status":"RESOURCE_EXHAUSTED"}}`
解析出来是一个**空 chunk**（既无 candidates 也无 usage）⇒ 与「心跳保活帧」**不可区分**
⇒ **厂商错误被静默吞掉**，客户端只看到一段被截断的流。

★ 修在 **IR 层**（事实源），不在 executor 层：
`internal/ir/parse_gemini_stream.go` 增加 `error` 字段 + 在 usage/candidate 分支**之前**
判定 ⇒ 产出 `ChunkTypeError`。
⇒ 与 Ollama 解析器同款分支（`parse_ollama_stream.go` 早就有）。

★ 顺序很关键：错误判定必须**在** usage/candidate 分支**之前**——
错误帧两者都没有，放后面就永远走不到。

## 8. ★ 凭据形态：**只走头，不进 URL**

厂方 API 两种都收（`x-goog-api-key` 头 / `?key=` query），
`docs/供应商协议优化.md` §8.3 也把两种都列了。**本轮只走头**：

- `?key=` 会进**每一条** access log、**每一条** upstream-URL 日志行、
  **每一行**记录请求 URL 的 telemetry ⇒ 凭据落盘。
- 头形态对厂商完全等价（Google 自己的 SDK 就用头）。

⇒ **反向钉**：`TestGeminiExecutor_BuildRequest_CredentialNeverInURL`
断言 **URL 里既不含凭据、也不含任何 query**。
★ 这条判据的含义：「厂商接受」≠「我们要用」。

## 9. 客户端侧线格式：**只接 OpenAI Chat 一种，其余 fail closed**

| 客户端协议 | 本轮状态 |
|---|---|
| `openai-completions`（含 **Gemini 原生客户端**） | ✅ 已接 |
| `anthropic-messages` | ❌ `KindUnsupportedFeature`（fail closed） |
| `openai-responses` | ❌ `KindUnsupportedFeature`（fail closed） |

★ **为什么 Gemini 原生客户端算「OpenAI Chat 客户端」**：
Gemini 入向 handler（`domains/streaming/handler_gemini.go` step 6）在派发**之前**
就把 Gemini body 转成了 OpenAI 形状 ⇒ dispatcher 用 `ir.DetectProtocol` 看到的是
`openai-completions` ⇒ 响应也是 OpenAI 形状 ⇒ **由 Gemini handler 自己再转回 Gemini 形状**。
⇒ ★ **`gemini-generate` 这个字符串永远不会作为「入向客户端协议」出现**（这一点值得钉死，
否则下一个人会以为 executor 要自己处理 Gemini 形状的响应）。

★ **其余两种为什么 fail closed 而不是「尽力转一下」**：
错形状的 200 比明确的「没接线」错误更糟——客户端 SDK 会在离病因很远的地方解析失败。
⇒ 与已上线的 Ollama-native executor 同一口径（`finalizeOllamaUpstreamBody` gate 2）。

## 10. 本轮明确没做（留给下一轮，别重复排查）

- **Gemini 原生模型列表**（`GET /v1beta/models`）——需要 `cmd/gateway/main.go` 接线
  （并行会话正在改该文件），且要决定返回形状（原生 Gemini 形状 vs OpenAI `/v1/models` 形状）。
- **`:countTokens`**——需要**诚实**的 token 计数。用估算值会误导客户端
  （客户端会拿它做配额判断）⇒ 独立设计题，不能顺手用估算糊过去。
- **`anthropic-messages` / `openai-responses` 客户端侧线格式**（§9）——需要 Anthropic
  SSE 严格帧（`message_start` → `content_block_delta` → `message_stop`）与 Responses
  的 `response.completed` 编排；两者在 IR 层都有序列化器，但**流式终态的编排**
  （谁写 `message_start`、谁写 `response.completed`）尚未接线。
- **Gemini 上游的 `header_profile_code` 联动**——§8.3 提到凭据形态与
  `header_profile_code` 关联；本轮固定走 `x-goog-api-key`，未接 profile 表。
- **Gemini 上游的上下文超限压缩恢复**（Ollama 路径有 `handleContextLengthRecovery`
  的递归重试）——本轮只做一次尝试，不做压缩重发。

## 13. ★ 合并后的两处红灯：**归属判定**（不是「我这边红 = 我这边错」）

合并 `origin/main`（并行会话的新提交）后跑全量扫描，两处红灯：

| 红灯 | 现象 | 归属 |
|---|---|---|
| `TestBridgeDeferredModeNormalStreamByteIdentical/responses_passthrough_normal_stream` | legacy 与 deferred 两份输出**只差 `created_at` 一个字段**（1793035633 vs 1793035634） | **不是本轮引入** |
| `TestRouterShadowDiffDoesNotChangeLegacyOrder` | `shadow counter "identical"=0` + 日志里 `redis: connection refused` | **环境依赖**（本机无 Redis） |

★ 归属按仓内纪律做（LESSONS §430 通用式十：「**「我这边红」≠「我这边错」⇒ 归属判定的唯一可靠办法是
【同机同命令、两个 checkout 各跑一遍】**」）：

- 同一命令在**本轮工作树**与**干净 `origin/main` worktree** 各跑 20 次
  ⇒ **两边都是 0/20 失败** ⇒ 行为一致。
- 失败 diff 里**唯一**的差异是 `created_at` ⇒ 该字段来自
  `internal/ir/response.go:1124` 的 `time.Now().Unix()`（IR 没带 `Created` 时取墙钟）
  ⇒ 该测试把**两次独立运行**的输出做**逐字比对** ⇒ 只要两次运行跨过一秒边界就必红
  ⇒ ★ **它是一个先天的 flaky 测试**，在**机器有并发负载**时（当轮并行会话同时跑着 4 个测试二进制）
  命中率显著上升。
- ★ 本轮 diff **没有碰** Responses 的 `created_at` 路径（`internal/ir/response.go` 的改动
  只有「加 `Citations` 字段 + 加 annotation/citationMetadata 序列化器」）。

⇒ 结论：**两处红灯都不归本轮**，且都不阻塞本轮推送。
★ 但它们是**真实的仓库缺陷**（一个 flaky 门 + 一个依赖 Redis 的门），已登记给下一轮：
**逐字比对类门要么固定时间源，要么把时间戳字段排除在比对之外。**

| Gemini 原生模型列表 | ✅ **本轮做** | `domains/streaming/models.go`（原生形状，复用同一数据源）+ `main.go` 一行路由 |
| `:countTokens` | ⏸ **登记** | 见 §17 的诚实性论证 |

## 15. ★★★ 客户端线格式：**复用仓内既有的桥，而不是自己手搓帧**

上一轮把 `anthropic-messages` / `openai-responses` 判为「未接线」，理由是
「Anthropic SSE 严格帧 + Responses 的终态编排未接线」。本轮复查发现**这个理由
站不住**：

- 仓内**早就有**两条现成的转换：
  `streaming.StreamOpenAIToAnthropicSSE`（`domains/streaming/anthropic_stream.go`）
  与 `streaming.StreamOpenAIToResponsesSSE`（`domains/streaming/responses_bridge.go`），
  它们**已经挂在 Executor 上**（`OpenAIToAnthropicStream` / `OpenAIToResponsesStream`，
  `cmd/gateway/main.go:1978` / `:2043` 接线）。
- 而**本 executor 本来就产出 OpenAI 形状的帧** ⇒ **同一份转换直接可用，零新增接线**。

⇒ ★★★ **通用式（本轮最值钱的一处）**：
**「这个能力没接线」常常不是「这段逻辑不存在」，而是「这段逻辑在【另一个协议】的
路径上已经写好了，只是没有接过来」** ⇒ ★★ 先去找「已经写好的那一半」，再决定
要不要自己写 ⇒ ★★ 自己是最后手段。

⇒ **实现方式**：`io.Pipe`。
executor 把 Gemini 流转成 OpenAI 形状的帧写进管道，另一侧的桥读管道、写客户端。
管道无缓冲 ⇒ **转换仍然是流式的**（不整段缓冲到内存）。

⇒ ★ **为什么不能直接调用 `streaming.StreamOpenAIToAnthropicSSE`**：
`domains/streaming` **导入** `domains/streaming/executors` ⇒ 反向导入即**循环依赖**
⇒ ★★ 这条约束反过来印证了「桥必须由 main.go 注入、executor 只持有回调」的设计
（仓内既有形状）—— ★ **不要为了方便把桥直接 import 进来**。

⇒ **非流式**侧不需要桥：IR 层已有 `SerializeAnthropicResponse` /
`SerializeResponsesResponse`，且 `IRConverter` 接口本来就带这两个方法 ⇒ 零接线。

## 16. ★ `header_profile_code` 联动（§8.3 明确要求的那一条）

`docs/供应商协议优化.md` §8.3 写的是「Header：`x-goog-api-key: <key>` 或 `?key=<key>`
（**与 endpoint 的 `header_profile_code` 关联**）」。

⇒ 本轮把出站请求**应用 endpoint 的 header profile**
（`provider_header_profiles` 表，`HeaderProfileCache.load(catalogCode, protocol)`），
与 `executor_chat.go` 的 OpenAI 路径同款。

⇒ ★ **为什么要它**：本 executor 只发 `x-goog-api-key`；而**Gemini 兼容中转**
（不是 Google 官方）的 profile 可能声明 `Authorization: Bearer` ⇒ 没有这条联动，
这类端点会直接 401。

⇒ ★ **应用顺序在凭据头之后** ⇒ profile 声明的凭据头**覆盖**默认形态 ——
这正是该机制存在的意义（它就是用来表达「这个端点要另一种凭据形态」的）。

## 17. `:countTokens`：**为什么仍然登记**（不是「不想做」，是「不能诚实做」）

Gemini 的 `:countTokens` 要给客户端一个**诚实的** token 计数。本仓**没有**
Gemini 的分词器（`internal/` 下没有任何 tokenizer 实现）⇒ 本地估算不满足「诚实」。

⇒ **唯一诚实的实现是把请求【转发给上游】让 Google 自己算**。
但那是**第三条出站动作**（`:countTokens` 的响应形状 `{"totalTokens":N}` 与
`GenerateContentResponse` 完全不同 ⇒ 不走 `ProtocolHandler` 那条通用路径），
需要独立的请求/响应通道 ⇒ **独立一轮**，不塞进本轮。

⇒ ★ 登记时把「诚实的实现方式」一并写下来（转发上游），免得下一轮又从
「本地估算」这个不诚实的方向开始想。

## 18. ★ `Gemini 原生模型列表`：本轮做掉了（登记理由已被更强的事实取代）

★ **登记理由变了**：上一轮登记的理由是「要动 `cmd/gateway/main.go`，而并行会话
正在改该文件 ⇒ 避让」。本轮复查时，并行会话的 `main.go` 改动落在
**行 913 / 2574 / 3883 / 6788**（summarize handler 一族），而 Gemini 的 mux 注册在
**行 6794~6796** ⇒ ★ **两处相距 25 行，三方合并不会重叠** ⇒ 避让的前提消失 ⇒ 本轮做。

⇒ **实现**（`domains/streaming/models.go` + `cmd/gateway/main.go` 一行路由）：

· **路由**：`mux.HandleFunc("/v1beta/models", modelsHandler.ServeGeminiModels)`。
  ★ Go 的 `ServeMux` 对已注册的子树模式 `/v1beta/models/` 会把 `/v1beta/models`
  **301 重定向**到带斜杠的形态 ⇒ **不注册精确路由也能被访问到**（多一次跳转）；
  ⇒ 仍然显式注册（一次跳转也是一次往返）。
· **数据源**：**复用 `ModelsHandler` 的同一个可路由模型查询**
  （为此把 `serveFromDB` 的取数部分抽成 `loadEntries(ctx)`）⇒
  ★ **同一份「网关能服务哪些模型」的真值，只有线格式不同** ⇒
  两个数据源就是两份关于「网关能服务什么」的真值 ⇒ 会漂移。
· **输出形状**：厂商原生形状
  `{"models":[{"name":"models/…","displayName":…,"supportedGenerationMethods":[…],"inputTokenLimit":…}]}`
  （与仓内 Google 扫描器读的 `googleModelEntry` 同款）。
· ★ **`supportedGenerationMethods` 只列网关【真的】支持的动作**
  （`generateContent` / `streamGenerateContent`）⇒ **不列 `countTokens`**
  ⇒ ★ **网关不实现它**（见 §17）⇒ ★ **列一个自己做不到的方法 =
  给客户端一个它会当真、然后失败的承诺**。

⇒ ★ **一个诚实的边界**：`/v1/models`（无斜杠）**仍然是 OpenAI 形状**
（那是 OpenAI SDK 的既有契约，已被占用）⇒ ★ **Gemini 的 GA 路径（`/v1`）拿到的
仍是 OpenAI 形状的列表** ⇒ 本轮只解决 `v1beta` 这条厂商原生路径

⇒ 若将来要让 GA 路径也返回原生形状 ⇒ 需要**重新分配 `/v1/models` 的归属**
⇒ 那是产品决策，不是本轮的工程量。

## 20. ★★★ 凭据收口面**必须覆盖每一个被服务的 Gemini 路由**

### 20.1 缺陷

本轮把模型列表挂上去之后（§18），**只挂不认**会留下一个比原缺陷更难查的形状：

| 路由 | 客户端形态 | 修复前的表现 |
|---|---|---|
| `POST /v1beta/models/{m}:generateContent` | `x-goog-api-key` 头 | ✓ 能用 |
| `GET /v1beta/models`（原生列表） | `?key=` query | ✗ **401 missing_key** |

★ **同一个客户端、同一个 key**，一个通一个不通 ⇒ 用户看到的是
「网关时好时坏 / 认证是坏的」⇒ 排查成本极高。

★ **根因不是「模型列表忘了带 key」**，而是**收口面漏了一条路由**：
`internal/auth.IsGeminiNativePath`（`?key=` 这一形态的收口面）此前只认
**generateContent 两个动作**，而模型列表是**第三条被服务的 Gemini 路由**
（它自己的 mux 条目，不在 `/v1beta/models/` 子树里 ⇒ 靠「前缀」推不出它）。

⇒ 这正是 §433 通用式的**第三次兑现**：★ **凭据收口面必须覆盖每一个
被服务的路由**，而不是「生成动作的那几个」。

### 20.2 修法（**只往保守方向**）

`geminiNativePathRe` 增加一个**精确锚定**的分支：

```
^(?:/(?:v1beta|v1)/models/[^/:]+:(?:generateContent|streamGenerateContent)|/v1beta/models$)
```

★ **精确锚定（`$`）而不是前缀**：`/v1beta/models` 是**一条独立路由**，
不是一族路由的前缀 ⇒ `/v1beta/modelsXYZ` **必须不在**收口面内
（否则 `?key=` 会在一堆没人服务的路径上变成凭据源）。

★ **`/v1/models`（无斜杠）仍然不在**收口面内：那是 OpenAI SDK 的既有契约
（OpenAI 形状的列表）⇒ 把它拉进来会让 `?key=` 在一条非 Gemini 路由上
变成凭据源 ⇒ **收口面宁窄勿宽，但宽的部分必须是「已服务的 Gemini 路由」**。

### 20.3 三侧对拍（本轮新增的钉）

★ 这次**两侧都有门**的纪律必须再执行一遍，因为**本轮多了一条路由**：

| 侧 | 门 | 钉住什么 |
|---|---|---|
| 挂载面（`cmd/gateway`） | ★ `TestGeminiModelListIsMounted` | **从 main.go 源码**读出挂载语句（不是读常量 ⇒ 不自证）＋ 反向钉：`/v1/models` **没有**被换成原生形状 |
| 解析面（`domains/streaming`） | ★ `TestGeminiNativeModelListIsServedAndScoped` | 服务处理函数**在本包内**（编译期钉）＋ 收口面覆盖它 ＋ **反向**：generateContent 解析器**不认**它（两条路由不许混）＋ `/v1/models` 不在收口面内 |
| 收口面（`internal/auth`） | ★ `TestIsGeminiNativePath` ＋ `TestExtractClientKey_QueryKeyIsScopedToGeminiNativePaths` | 精确锚定（`/v1beta/modelsXYZ` 不在面内）＋ `?key=` 在模型列表上是凭据 |

★ **漂移门也要跟着改**：`TestGeminiNativePathMatchesHandlerParser` 的
「已服务路由」判定原本是 `served(p) && handlerOK`（**前缀** ∧ **解析器**）
⇒ 模型列表**两条都不满足**（不在前缀子树下、解析器也不认它）⇒
必须显式登记为「已服务的精确路由」⇒ ★ **否则漂移门会把这条路由
当成「没人服务的路径」，反过来要求收口面**别**覆盖它** ⇒
★ **门自己会写下「收窄」的要求** —— 这是本轮差点踩的坑。
