## §2 ★ 为什么「现有索引」全都承不住它 —— 三层排除

### 2.1 第一层：252 上的索引清单（只读查询 `pg_indexes`）

★ 名字带 api_key 的索引**只有 4 个**，而它们的**键全是 `(session_id, turn_no DESC)`**，
`api_key_id` 只出现在**谓词**里：

```
idx_session_turns_api_key_numeric     ON ONLY session_turns (session_id, turn_no DESC) WHERE api_key_id ~ '^[0-9]+$'
idx_session_turns_hot_api_key_numeric  ON session_turns_hot (session_id, turn_no DESC) WHERE api_key_id ~ '^[0-9]+$'
session_turns_2026_09_session_id_turn_no_idx / session_turns_2026_10_session_id_turn_no_idx1
```

⇒ ⇒ 它们承的是「**按 session_id 找该会话的轮次**」，**不是**「按 api_key 找行」。
⇒ ⇒ ★★ **「按 api_key 过滤会话」这条路从来没有被索引承重过。★★**

★ ★★ **同名不同义是最贵的一种坑**：★ 索引名 `idx_session_turns_api_key_numeric` 让人以为它承 api_key，
★★ 而它的键是 `(session_id, turn_no)` ⇒ ⇒ **排查索引时要看 `pg_get_indexdef` 的【键列】，不要看名字。★★**

### 2.2 第二层：为什么「普通 btree」也承不住

★ canonical 视图 `public.request_logs_with_current_month`（118 列）把 `api_key_id` 投影成

```sql
CASE WHEN t.api_key_id ~ '^[0-9]+$' THEN t.api_key_id::bigint END
```

（唯一真值源：`db/request_logs_view_schema.go` 的 `SessionFamilyAPIKeyIDExpr`）
⇒ ⇒ 过滤谓词是**表达式**，不是裸列 ⇒ ⇒ **普通 btree(api_key_id) 用不上。**

### 2.3 第三层：为什么「部分索引」也承不住

★ PG 的「谓词蕴含」判定是**语法的** ⇒ ⇒ 它无法证明
「`CASE WHEN api_key_id ~ '^[0-9]+$' THEN api_key_id::bigint END = 113` 蕴含 `api_key_id ~ '^[0-9]+$'`」
⇒ ⇒ **写在 CASE 里的过滤条件用不上以该正则谓词建的部分索引。**

★ ★★ **这一条仓里早就写死了**（不是本轮的发现）：
★ `db/request_logs_view_schema.go` 的 `SessionFamilyAPIKeyIDNumericPredExpr` 注释里已经用 252 实测记着
★ 「CASE 形式过滤 1,350.8 ms / 裸正则过滤 1,569.3 ms / ★ **裸正则 + 部分索引 4.57 ms（295×）**」
★ ⇒ ⇒ ★★ **⇒ 本轮要做的，是把那条「实验里临时建的索引」变成【生产迁移】，★ 且形态要覆盖【视图用的 CASE 形式】。★★**

## §6 收益边界与成本侧（★ 记账）

### 6.1 ★ 收益只来自「索引替掉逐行 Filter」这一件事 ⇒ 边界由命中率决定

★ 实测三点（全部实测，非推算）：

| 命中率 h | buffers 收益 | 机制 |
|---|---|---|
| ≈ 0% | **218×** | 索引直接判定「无此 key」，**连窗都不扫**（与 906 记录的 295× 同族） |
| ≈ 50% | **2.00×** | 省掉「读全窗 + 逐行 CASE 判断」；剩下的堆读是 37,624 条命中行本身的必需代价 |
| ≈ 100% | **1.00×** | 命中的就是整窗 ⇒ 堆页两臂都要读 ⇒ 索引只剩「多一次索引探测」的净成本 |

★ **可外推的公式**：★ 命中率 h 时，A 臂的额外成本 ≈ (1−h)×窗内行数，B 臂恒为 0
★ ⇒ **buffer 收益倍数 ≈ 1 + (1−h)×窗内行数 / 命中行数**
★ ⇒ h=50% ⇒ ≈2×（实测 2.00×，吻合）；h→1 ⇒ →1×（实测 1.00×，吻合）；h→0 ⇒ 发散（实测 218×，被「索引探测恒定开销」截断在 ~13 blocks）。

### 6.2 ★ 成本侧必须记账（三条）

1. ★ **索引体积**：★ 合成库实测表达式索引总体积 ≈ **39.7 MiB**（Oct 分区 10.5 MiB / 348k 行；Sept 分区 24.0 MiB / 798k 行）
   ⇒ ⇒ 对 252 的 4.7 GB `session_turns` 而言是**同一量级的写入放大**。
2. ★ **建索引期间的写入阻塞**：★ 普通 `CREATE INDEX` 持 SHARE 锁 ⇒ 阻塞写入；
