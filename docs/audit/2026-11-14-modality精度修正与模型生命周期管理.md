# 第一部分：第一轮交付

## 一、Modality 规则精度修正

### 1.1 问题

211 生产库中 `o1-mini` / `o3-mini-high` / `o4-mini-high` 的 `modality='text'`，
但规则表里有 `{"o1-"/"o3-"/"o4-", "vision", 1}` 前缀规则。前缀规则会把
`o1-mini` 这类名字推断成 vision，而它们按 OpenAI 文档疑似**纯文本推理模型**。

### 1.2 修复

`modelname/modality_defaults.go` 在优先级 0（精确匹配）加入例外，压过优先级 1 的前缀：

```go
{"o1-mini", "text", 0},      // 纯文本推理
{"o1-preview", "text", 0},
{"o1-pro", "text", 0},
{"o1", "vision", 0},         // bare o1 支持 text+image
{"o3-mini-high", "text", 0},
{"o3-pro", "text", 0},
{"o3-mini", "vision", 0},
{"o4-mini-high", "text", 0},
```

`modality_defaults_test.go` 新增 15 条用例钉住两个方向：
- 精确例外生效（o1-mini/o1-preview/o1-pro/o3-mini-high/o3-pro/o4-mini-high → text）
- 前缀规则未被误伤（o1 / o1-2024-12-17 / o3-mini / o3-2025-01-31 / o4-mini → vision）

验证：`go test ./modelname/` 全绿。

## 二、模型生命周期管理

### 2.1 设计

| 层 | 内容 |
|---|---|
| DB 列 | `models_canonical.released_at TIMESTAMPTZ`（NULL = 年龄未知） |
| 索引 | `idx_models_canonical_released`（`released_at DESC NULLS LAST`） |
| 设置 | `settings_kv['model_lifecycle.stale_threshold'] = "2 years"` |
| 路由 | 候选 SQL 加年龄闸：manual_priority 豁免 / NULL 放行 / 超阈值排除 |
| 工具 | `cmd/tools/backfill-release-dates`（发布日期回填） |

**语义三臂**（刻意设计，不是疏漏）：
1. `manual_priority > 0` → 永远保留（运营可钉任何模型）
2. `released_at IS NULL` → **放行**（未知年龄 fail-open；大多数行尚无日期，
   排除它们会清空候选池）
3. 已知日期且超过阈值 → 排除

### 2.2 迁移 966

幂等设计（`IF NOT EXISTS` / `ON CONFLICT DO NOTHING` / DO 块内检测列类型），
因为 211 上的列在迁移文件写出前已被手工建立（当时是 `date` 类型），
naive ALTER 会 abort 整条迁移链。

# 第二部分：第二轮批判性复核（首轮三个真缺陷）

> 触发：复核「上一轮交付是否真的能上线」时，用 211 真实 schema 做 PREPARE 校验，
> 三个缺陷同时暴露。**这三个缺陷若直接部署，第一个会让路由全挂，后两个会静默
> 清空候选池或误删在用模型。**

## 缺陷 1（P0，上线即崩）：SQL 别名越界

**现象**：候选 SQL 外层是 `SELECT ... FROM matched mo`，`matched` CTE 里才有
`LEFT JOIN models_canonical mc`。首轮把过滤条件写成 `mc.released_at`，
**在 211 生产 schema 上 PREPARE 直接报错**：

```
ERROR:  missing FROM-clause entry for table "mc"
LINE 315:         OR mc.released_at IS NULL
```

后果：任何文本请求加载候选时 SQL 解析失败 → 路由不可用。

**根因**：CTE 只投影了 `_mc_id` / `_mc_cw_override` / `_mc_cw`，没有把
`released_at` 带出来；外层无从引用 `mc`。

**修复**：
- CTE 投影增加 `mc.released_at AS _mc_released_at`
- 外层过滤改用 `mo._mc_released_at`

**验证**（这是首轮完全缺失的验证）：
- 211 生产 schema `PREPARE cand_probe(text,text,text) AS <候选SQL>` → `PREPARE` 成功
- `EXPLAIN (COSTS OFF) EXECUTE cand_probe('glm-5.3-flash','default','text')` → 正常出计划

## 缺陷 2（P1，静默清空候选池）：COALESCE 位置错误导致 NULL 传播

**现象**：首轮把 `COALESCE` 写在阈值子查询**内部**：

```sql
OR age(now(), released_at) <= (
     SELECT COALESCE((value::text)::interval, '2 years'::interval)
       FROM settings_kv WHERE key = '...')
```

设置行**不存在**时，子查询返回 **0 行**（不是返回 NULL 行）⇒
`age(...) <= NULL` 求值为 NULL ⇒ 三臂 OR 链为 NULL ⇒ **该行被丢弃**。

这与设计意图（未知阈值 ⇒ 用默认 2 年 ⇒ 放行）**完全相反**：
任何没执行 settings 插入的环境，所有有日期的模型会被静默剔除。

**修复**：COALESCE 提到**外层**，包裹整个子查询结果：

```sql
OR age(now(), _mc_released_at) <= COALESCE(
     (SELECT (value #>> '{}')::interval FROM settings_kv WHERE key = '...'),
     '2 years'::interval)
```

顺带把 `value::text` 改为 `value #>> '{}'`：前者只是**碰巧**能解析
（PostgreSQL 容忍 jsonb 字符串的外层引号），后者才表达「解包 jsonb 标量」的真实意图。

**验证**：真库行为门 `TestModelLifecyclePredicate_RealDB` 三个 case：
| Case | 设置 | 期望选中 |
|---|---|---|
| A | 无设置行 | fresh + unknown + manual（**首轮缺陷在此会丢掉 fresh**） |
| B | `5 years` | 全部 4 行（放宽阈值应重新纳入 stale） |
| C | `1 day` | unknown + manual（unknown 仍放行、manual 仍豁免） |

变异验证：把测试谓词改回首轮形态 ⇒ Case A 实测
`got [unknown stale-pin], want [fresh unknown stale-pin]` ⇒ **红**（fresh 被丢）；
还原 ⇒ 绿。

## 缺陷 3（P1，误删在用模型）：发布日期粗前缀匹配写错数据

**现象**：首轮回填 SQL 用 `LIKE 'deepseek-%'`、`LIKE 'glm-4%'`、`LIKE 'gpt-4%'`
这类粗前缀批量赋日期，导致：

| 模型 | 首轮写入 | 真实情况 | 后果 |
|---|---|---|---|
| `deepseek-v4.1-flash` | 2024-01-08 | 2026 年新模型 | 被标 2 年前，**有 126 请求/7天** ⇒ 会被过滤 |
| `deepseek-v4-pro` / `v3.x` / `r1` 等 47 个 | 2024-01-08 | 均晚于 2024-01 | 同上 |
| `glm-4-flash` / `glm-4-air` / `glm-4-plus` | 2024-01-16 | 2024-06 之后 | 误标 |
| `gpt-4.1` / `gpt-4.1-mini` / `gpt-4.1-nano` | 2023-03-14 | 2025-04 | 误标 |
| `claude-opus-4-5` ~ `4.9` / `claude-sonnet-4-5` ~ `4-8` | 2024-11-20 | 后续版本 | 误标 |

**根因**：**版本号前缀相同不代表同一代模型**。回填工具首版用
`strings.HasPrefix(name, pattern+"-")` 做家族覆盖，把「家族」当成了「同一发布日」。

**修复**：
1. **数据侧**：清除 61 条粗匹配写入的错误日期（回到 NULL = fail-open 安全态），
   只保留 32 条可核实的精确日期
2. **工具侧**：`backfill-release-dates` 改为**仅精确名匹配**，文件头写明
   「a wrong date is worse than no date, because a wrong date silently removes a
   live model from routing」

**验证**：清理后复查
```
STALE(>2y): 43 models / 34 offers  →  7 天内真实流量：0 条
fresh(<=2y): 11 / 8
null(fail-open): 4341 / 4086
```
**stale 集合零流量** ⇒ 过滤不会误伤任何在用模型。

## 缺陷 4（次要）：迁移非幂等

首轮迁移 966 用裸 `ALTER TABLE ... ADD COLUMN`，而 211 上列已存在 ⇒
`column "released_at" already exists` ⇒ 整个事务 ROLLBACK。
且首轮脚本用了 `settings_kv.description` 列——该列**不存在**。

**修复**：DO 块检测列存在性 + 类型升级（date → timestamptz）、
`CREATE INDEX IF NOT EXISTS`（沿用 211 手工建的索引名
`idx_models_canonical_released` 以收敛而非重复）、`ON CONFLICT DO NOTHING`。

**验证**：scratch 库连跑两次迁移，第二次输出
`INSERT 0 0` + `relation ... already exists, skipping`，无报错。

# 第四部分：遗留与建议

## 4.1 已登记不修

1. **gpt-5 / gpt-6 系列 `context_window=NULL`**：需原厂窗口值，运营裁决。
   当前 inline 媒体在未知窗口下 advisory 放行，不阻断。
2. **modality 双实现**（`catalog/display.go` 读侧展示推断 vs
   `modelname.InferModality` 写侧）维持平行，结构性收敛另案。
3. **1592 个模型 `released_at` 仍为 NULL**：多为地区变体 / niche 模型，
   fail-open 放行，按需补充。

## 4.2 运营注意

1. **阈值调整**：`PATCH /api/admin/settings` 改
   `model_lifecycle.stale_threshold`（PostgreSQL interval 字面量，如 `"18 months"`）。
2. **保留旧模型**：在 `model_offers.manual_priority` 设 > 0 即豁免年龄闸。
3. **观察项**：部署后观察候选池大小与 stale 模型请求的 fallback 行为。

## 4.3 本轮教训（值得记住）

1. **「功能做出来」≠「能上线」**：首轮三个缺陷全部逃过了单元测试，
   因为它们只在**真实 schema** + **设置缺失** + **真实数据分布**下才暴露。
   SQL 类改动必须至少做一次目标库 PREPARE。
2. **CTE 的作用域是硬边界**：`WITH x AS (...) SELECT ... FROM x` 里，
   子查询的别名在外层**不存在**，投影什么才能用什么。
3. **COALESCE 的位置决定语义**：包在子查询里救不了「无行」，必须包在子查询结果外。
4. **粗前缀批量赋日期 = 数据污染**：版本号前缀相同 ≠ 同一代模型。
   宁可 NULL（fail-open）也不要猜错（fail-closed 误杀）。
5. **迁移必须幂等**：生产上「列已存在」是常态（手工修补、并行会话），
   裸 DDL 会 abort 整条链。
