## §4 「零依赖 mock」为什么必须自己写

仓内 mock 都不能当**探针目标**：

| 实现 | 依赖 | 缺口 |
|---|---|---|
| `scripts/mocks/llm-mock-upstream/server-v3.py` | **aiohttp**（本机未装 ⇒ 起不来） | — |
| `tests/stress/mocks`（Go） | 无 | **不提供 `/v1/models`** |
| `tests/local/mocks`（Go） | 无 | 不提供 `/v1/models`，响应体固定 |

而凭据健康探针是**两步法**（`bg/credential_probe_v2.go:probeCredentialWithCapability`）：
**Step 1 `GET /v1/models`** → Step 2 一条 mini chat ⇒
**mock 不提供 `/v1/models` ⇒ Step 1 失败 ⇒ 凭据被判 `health_status='unreachable'`**
⇒ 被路由候选过滤（`domains/streaming/models.go`：`COALESCE(c.health_status,'unknown') IN ('healthy','unknown')`）
⇒ 症状极具迷惑性：**mock 明明在跑，却一个请求都收不到**（计数器 requests=0）。

⇒ ★ 新增 `scripts/mocks/llm-mock-upstream/server-stdlib.py`：
**只用 Python 标准库**（`http.server` + `json`）⇒ 不需要装任何东西 ⇒ 补齐 `/v1/models` + `/v1/chat/completions`（回显 model、支持 stream）+ `/healthz` + `/admin/stats`。
⇒ 文件头写明了「为什么仓内另外两个 mock 不够用」与「两步探针」这条机制链。

## §5 本轮三条实测发现（均未改产品代码）

### §5.1 ★ 本地 provider 的 base_url 硬编码 `127.0.0.1` ⇒ 容器形态下永远不可达

* 证据：`admin/local_provider.go:defaultLocalBaseURLForCode` 硬编码
  `http://127.0.0.1:11434/v1`（ollama）/ `8082`（llamacpp）/ `1234`（lmstudio）/ `8000`（vllm）/ `8080`（mlx）；
  种子化模板是 `http://{host}:{port}/v1`（`sql/schema/02-seed.sql`），`{host}` 最终落到 127.0.0.1。
* 实测：网关跑在容器 `llm-gateway-local-8782` 里 ⇒ 凭据的 base_url 指向**容器自己**
  ⇒ 探针报 `Get "http://127.0.0.1:8901/models": dial tcp 127.0.0.1:8901: connect: connection refused`。
* ★ **与本仓既有约定冲突**：本仓对「容器 → 宿主」一律用 **`host.docker.internal`**
  （`docs/全面测试/deploy-test.md`：本地 PG 就是 `host.docker.internal:5432`；`internal/safehttpclient` 也把它列为精确匹配的白名单）。
  ⇒ ⇒ **本机本地推理后端（ollama/vllm/llamacpp/lmstudio/mlx）在容器形态下全部接不上**。
* ⇒ **修复点**：`defaultLocalBaseURLForCode` 的 host 段应按**部署形态**取
  （容器 ⇒ `host.docker.internal`；宿主机 ⇒ `127.0.0.1`）。
  ⚠ **本轮未改**：一刀切会打挂「ollama 与网关同容器/同网络」的场景 ⇒ 形态判定 + 覆盖开关属**属主决策**。

### §5.2 ★ 种子化的 mock provider 缺两样东西

`providers` 里 2433 `mock-openai` / 2434 `mock-anthropic`：
* base_url = `http://127.0.0.1:8901`（**无 `/v1`** ⇒ 探针拼出的 URL 是 `.../models` 而不是 `.../v1/models`）；
* **没有任何凭据**（`credentials` 里 provider_id∈{2433,2434} 为 0 行）⇒ 即使 mock 在跑也路由不到。

⇒ ⇒ 两条都是**种子形态问题**，不是产品逻辑缺陷；本轮用 admin API 现场补齐（建凭据 + 显式挂模型 + 改 base_url）后即可用。

### §5.3 ★ URSM v2 权威节点镜像决定「候选能不能活」

日志原文（本轮实测，`docker logs llm-gateway-local-8782`）：

```
"msg":"router: URSM v2 authoritative view filtered out every candidate",
"model":"glm-5.3-flash","input_candidates":1,"views_returned":1,
"view_sample":["prov=2433 cred=10 model=glm-5.3-flash avail=false"]
"msg":"executor: no candidates after router","reasons":{"availability_check_failed":1}
```

⇒ ⇒ ★ **候选查询本身是通的**（`candidates_count=1`）⇒ 是**路由层的 URSM v2 权威视图**把它全拒了
⇒ ⇒ 与写路径、与 provider_models / 绑定 / 定价**都无关**（那 8 个绑定在 `v_routable_credential_models` 里 `is_routable=t`）。
⇒ ⇒ 对本轮结论：**3 个模型仍 503 是「镜像覆盖」问题，不是「模型请求与落库」链路的问题**（同一条链路对另外 5 个模型全通）。

### §5.4 量具边界：12 RPM ⇒ 突发必然 429（不是缺陷）

* `X-Ratelimit-Limit: 12`（`keyInfo.EffectiveRPM()`，本机 key 的 `rate_limit_rpm` 为 NULL ⇒ 取默认 12）。
* ⇒ ★ 首轮**无节流**的 14 连发 ⇒ 12 之后全部 **429 "Rate limit exceeded"** ⇒
  **那是网关自己的每 key 限流在工作，不是上游故障、也不是数据问题**。
* ⇒ 本轮改为 **5.5s/次**（≤12 RPM）⇒ 48 次请求零 429 ⇒ **口径记录下来，免得下轮误判**。

## §7 诚实边界

1. ★ **mock 路径的「成功」不等于真实上游可用**：mock 证明的是**网关侧**的路由/写库/计费链路自洽；
   真实上游的可用性只有 `glm-5.2` 一条被实测（zhipu，1.7s~11.3s 延迟、tokens 正常）。
2. ★ **3 个模型（`deepseek-v4-flash`/`glm-5.3-flash`/`minimax-m2.7`）仍 503**：原因是 URSM v2 镜像覆盖（§5.3），
   本轮**未深挖**该子系统（它有自己的门与文档）；⇒ 但它们的**失败也照样落库**（`success=false` 行），写路径覆盖到了。
3. ★ **未验证的**：流式（SSE）落库、成本口径（mock 无定价 ⇒ `cost_usd=0`）、
   多租户/越权路径、生产（211/252）上的同类验证。
4. ★ **本轮没有改任何产品代码**（除新增测试夹具 `server-stdlib.py`）⇒ 三条发现都是**取证 + 定位修复点**，未擅自修。
5. ⚠ **`server-stdlib.py` 是测试夹具**：不校验 token、不做配额 ⇒ 只能监听回环/本机；默认 `MOCK_BIND=127.0.0.1`。
