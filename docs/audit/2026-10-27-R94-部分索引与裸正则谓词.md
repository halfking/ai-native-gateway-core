# R94 · 会话列表残留的 ~1.5 s：enrich 查询**扫 82,297 行堆、全部过滤掉、产出 0 行**

> 轮次标签 **2026-10-27 R94**（与本系列 R91/R92/R93 同批）；实测时钟 **2026-10-24**。
> 上一轮：R93（`docs/audit/2026-10-27-R93-enrich查询才是500的真凶-视图与history重复扫同一批行.md`）。

## 0. 一句话结论

★ **R93 把 `?model=` 从「恒 500@30s」修成 200，但端点仍要 ~1.5 s** ⇒ 归因是
**enrich 查询把 82,297 行堆全扫了一遍、全部被过滤掉、最后产出 0 行**
⇒ 真因：**探针会话（`sys:probe:*`）的 `api_key_id` 全是 NULL** ⇒ 过滤条件**无法从索引判定**
⇒ 必须回表 ⇒ 修法 = **部分索引**（`WHERE api_key_id ~ '^[0-9]+$'`）+ **把过滤写成裸正则**
⇒ 实测 **1,350.8 ms → 4.57 ms（295×）**，口径**逐行等价**（生产非空批次双向 EXCEPT ALL）。

## 2. 归因（252 生产只读实测）

### 2.1 ★ 端点的钱花在哪：pg_stat_statements **窗口差分**

★ 纪律：共享库**单次读数没有可比性** ⇒ 用**受控窗口差分**（窗口内只打 N 次端点请求，
前后各取一次快照，按 queryid 相减）。

6 次 `?model=` 请求的窗口：

| 语句 | calls | 窗口总耗时 | 均值 |
|---|---|---|---|
| ★ 新形态 enrich（`DISTINCT ON (x.session_id)`） | 6 | **9,143 ms** | **1,523.8 ms** |
| 列表查询（`FROM public.sessions s`） | 8 | 137 ms | **17.2 ms** |
| 另一条列表查询 | 8 | 33 ms | 4.1 ms |

⇒ ★★ **enrich 是端点的绝对主力**；列表查询（R92 的 V2 形态 + 迁移 905 的 model 索引）
**只占 17.2 ms** ⇒ ★ **R92 的修法确实生效**，剩下的全是 enrich。

### 2.2 ★★ enrich 为什么还这么慢

生产 EXPLAIN（真实批次 = 端点返回的 20 个 `sys:probe:*` 会话）：

    Index Scan using session_turns_2026_09_heap_tenant_id_session_id_turn_no_idx
      Index Cond: (session_id = ANY('{sys:probe:cred18:20260924, … 20 个}'))
      Filter: (CASE WHEN (api_key_id ~ '^[0-9]+$') THEN (api_key_id)::bigint END IS NOT NULL)
      Rows Removed by Filter: **82,297**
      Buffers: shared hit=66,606

⇒ ★★ **扫 82,297 行堆，全部被过滤掉，最终产出 0 行**，却花了 1,350~1,569 ms。

### 2.3 ★ 为什么这些行全被过滤掉

| 事实 | 读数（252） |
|---|---|
| `session_turns.api_key_id` 的类型 | **text**（不是 bigint） |
| `sys:probe:%` 的行数 | 462,394 |
| 其中 `api_key_id` **非空**的行数 | **0**（`min`/`max` 都是 NULL ⇒ 唯一一组是 NULL） |

⇒ ★ **探针流量整条链路的 `api_key_id` 都是 NULL** ⇒ 过滤条件
`(CASE WHEN api_key_id ~ '^[0-9]+$' THEN api_key_id::bigint END) IS NOT NULL`
**在索引里判定不了** ⇒ 必须回表 ⇒ 必须把 82,297 行堆读出来才能发现「它们都不合格」。

★ ⇒ **端点这一页其实不需要 api_key 标签**（探针会话没有 api_key）⇒
**这 1.5 s 是纯浪费**。

### 2.4 ★ 排除项

- **统计陈旧** ✗：`session_turns` 的 `last_analyze` 是 2026-10-19、`2026_10` 的
  `last_autoanalyze` 是 2026-10-24 ⇒ 统计新鲜。
- **缺 `(session_id, turn_no)` 前导索引** ✗：父表**已有**
  `idx_session_turns_session (session_id, turn_no DESC)`，且 2026_09 上有
  `session_turns_2026_09_heap_session_id_turn_no_idx`（valid）⇒ **不是缺索引**，
  是**索引里没有 api_key_id ⇒ 判定不了过滤条件 ⇒ 回表**。
- **视图/投影太宽** ✗：R93 已把 113 列投影换掉。
- **PG 17 index skip scan 退化** ✗：`enable_indexskipscan=off` 后计划不变。

## 3. 修法：部分索引 + 裸正则谓词（两条腿缺一不可）

### 3.1 ★ 为什么必须改**代码**（不只是加索引）

★ **PG 的「谓词蕴含」判定是语法的** ⇒ 它能认出

    WHERE api_key_id ~ '^[0-9]+$'   蕴含   部分索引的 WHERE api_key_id ~ '^[0-9]+$'

但**认不出**

    WHERE (CASE WHEN api_key_id ~ '^[0-9]+$' THEN api_key_id::bigint END) IS NOT NULL

⇒ ★★ **两种写法口径完全等价，但只有裸正则能被规划器认出来**
⇒ ⇒ 只加索引、不改代码 ⇒ **索引白建**（实测 1,569.3 ms，与改前同量级）。

★ 而这两个写法**逐情形等价**：

| `api_key_id` | CASE 形式 | 裸正则 | 同否 |
|---|---|---|---|
| NULL | CASE 得 NULL ⇒ 排除 | NULL ⇒ 排除 | 同 |
| 非数字（如 `abc`/`''`/`' 18'`/`'18.5'`） | 得 NULL ⇒ 排除 | false ⇒ 排除 | 同 |
| 纯数字（如 `'18'`/`'0018'`） | 得 18 ⇒ 保留 | true ⇒ 保留 | 同 |
| 超 int64 的纯数字串 | ★ CASE 在 **WHERE 求值**时报 22003 | WHERE 不报错，**入选行的 SELECT 列表**才报 | ★ 裸正则**更宽松**，不是回归 |

⇒ 生产真实**非空**批次逐行对拍（252，同一事务内同一快照）：
`old_rows=20 / new_rows=20 / **only_new=0 / only_old=0**` ⇒ **逐行一致**。

### 3.2 修法本体

- **代码**：新增常量 `db.SessionFamilyAPIKeyIDNumericPredExpr`
  = `t.api_key_id ~ '^[0-9]+$'`，用于 `db.SessionFamilyLatestTurnPerSessionSQL`
  的**聚合腿**（每 source 一份）。
- **迁移 906**：两条**部分索引**
  - `public.session_turns (session_id, turn_no DESC) WHERE api_key_id ~ '^[0-9]+$'`
    （`idx_session_turns_api_key_numeric`，分区父表 ⇒ 自动传播）
  - `public.session_turns_hot (session_id, turn_no DESC) WHERE api_key_id ~ '^[0-9]+$'`
    （`idx_session_turns_hot_api_key_numeric`）

★ 为什么用**部分索引**而不是普通索引：
探针流量（`api_key_id` 全 NULL）在普通索引里**一行都省不掉**⇒ 索引巨大且规划器仍要回表。

### 3.3 ★ 选型实测（252 生产，事务内 CREATE INDEX + EXPLAIN ANALYZE + ROLLBACK ⇒ 零残留）

| 形态 | 探针批次执行时间 | 备注 |
|---|---|---|
| CASE 形式过滤（无部分索引，= 2843 生产形态） | 1,350.8 ms | `Rows Removed by Filter: 82,297` |
| 裸正则过滤（无部分索引） | 1,569.3 ms | 口径等价，但同样慢 |
| ★★ **裸正则过滤 + 部分索引** | **4.57 ms** | ★ **295×** |
| （对照）`INCLUDE(api_key_id)` 的普通索引 | 0.62 ms | ★ 但需 **ANALYZE（实测 35.9 s）** 且索引体积大得多 ⇒ **出局** |

★ 索引构建时长：父表 **6,026 ms** + hot **21 ms**（对比 905 的 18,512 ms + 28 ms）
⇒ ★ SHARE 锁窗口从 ~18.5 s 缩到 **~6 s**。

## 8. 通用式（并入 `LESSONS.md` **§368**）

1. ★★★★ **「口径等价」不等于「能被规划器认出来」** ⇒ ★ **PG 的谓词蕴含判定是语法的**：
   CASE 形式与裸正则口径逐情形等价，但**只有裸正则**能被部分索引吃掉 ⇒
   ★ **「等价的两条路」里只有一条能吃到索引** ⇒ 写门要钉**规划器能不能认**，不是钉「对不对」。
2. ★★★★ **「扫了 N 行、全部被过滤掉、产出 0 行」是最贵的浪费形态** ——
   它**不报错、不超时、结果正确** ⇒ ★ 只能靠 **`Rows Removed by Filter`** 这一个读数看见。
3. ★★★★ **「输出 0 行」要先问「输出 0 行是不是应该」** ——
   本轮端点那一页**根本不需要 api_key 标签**（探针会话没有 api_key）⇒ 这 1.5 s 是纯浪费。
4. ★★★ **回表与否取决于「过滤列在不在索引里」**，而不只是「有没有合适的索引」⇒
   ★ 索引里**没有**判定所需的那一列 ⇒ **有索引也照样回表**。
