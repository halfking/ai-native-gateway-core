## 4. ★★★★ 判定第三步：一条**此前没人写下的机制事实**（实测）

⇒ ⇒ ★★ **peer 的建议 (a) 是「`SET statement_timeout` + `DROP`」** ⇒ ⇒ **看起来当前代码已经这么做了**
⇒ ⇒ ★★★ **但这里有一个必须实测才能回答的问题**：

> `psql -c "SET statement_timeout='120s'" -c "DROP ..."` —— **这两条 `-c` 是同一个会话吗？**
> ⇒ ⇒ **若是不同连接 ⇒ SET 对 DROP 无效 ⇒ 防护是假的。**

⇒ ⇒ ★★★★ **实测（容器 `acc-b02-pg-20261021`，PG 17.11）**：

| 测法 | 命令形态 | `SHOW statement_timeout` |
|---|---|---|
| **测法 1** | **同一条 `psql`** 的两个 `-c`（= 当前脚本的形态） | **`1s`** ⇒ ★ **SET 生效** |
| **测法 2** | **两次独立 `psql`**（SET 一次、DROP 一次） | **`0`** ⇒ ★ **不跨连接** |

⇒ ⇒ ★★★★ **⇒ 结论：当前脚本的 `SET` + `DROP` 是同一条 `psql` ⇒ **同一会话** ⇒ SET 生效**
⇒ ⇒ ⇒ ⇒ **⇒ peer 的建议 (a) 已被当前代码满足** ⇒ ⇒ ⇒ ⇒ ⇒ ★★ **这条机制事实此前没人写下来过 ⇒ 本轮补记**

⇒ ⇒ ★★ **顺带**：这个问题的**危险方向**是「看起来做了、其实没做」⇒ ⇒ 若不实测，
⇒ ⇒ **大概率会误判成「已修」**（因为代码看起来完全对）⇒ ⇒ ★ **⇒ 这正是「读代码不如跑一次」的又一例**。

## 5. 判定第四步：★ **「卡住」的机制是 Citus 特有的**（本地不可复现）

⇒ ⇒ ★★ peer 的证据日志里有一行**决定性线索**（第 9 行）：

```
!! CREATE itgate_factmatrix_a1 FAILED: NOTICE:  Citus partially supports CREATE DATABASE for distributed databases
```

⇒ ⇒ ★★★★ **⇒ `llm-gateway-pg` = `kx-citus-pg17`（Citus 分布式实例）**
⇒ ⇒ ⇒ **⇒ 「DROP 会卡」是【多节点协调】特有的** ⇒ ⇒ ⇒ **⇒ 单节点 PG 上复现不了**

⇒ ⇒ ★★ **本地实测（容器 `acc-b02-pg-20261021`，单节点 PG 17.11，配置 `statement_timeout=0 / lock_timeout=0 / idle_in_transaction_session_timeout=0` = 与生产同）**：

| 实验 | 形态 | 结果 |
|---|---|---|
| A | 裸 `DROP ... WITH (FORCE)`（有活跃会话持有该库） | **rc=0，1~5s，库被删** ⇒ **不卡** |
| B | 裸 `DROP`（**不带** FORCE，有活跃会话） | 立即报错「being accessed by other users」⇒ **不卡** |
| C | 持锁长事务 + 裸 `DROP ... WITH (FORCE)` | **rc=0，1s，库被删** ⇒ **不卡** |
| D | ★ **当前代码完整形态**（terminate + SET 120s + DROP FORCE） | **5s，零报错** |

⇒ ⇒ ★★ **⇒ 单节点上四种形态都不卡** ⇒ ⇒ **⇒ 佐证「卡住」依赖 Citus 多节点协调**
⇒ ⇒ ⇒ ⇒ **⇒ 也说明：本地复现不了 ≠ 告警是假的** ⇒ ⇒ ⇒ ⇒ ⇒ ★ **⇒ 两件事要分开说**

## 9. 诚实边界

1. ★ **「Citus 上会卡」这一条，本轮**没有在 Citus 上直接复现**（本机无 Citus 集群）
   ⇒ ⇒ 本轮采信 peer 的**历史日志证据**（它确有 `Killed: 9` 原文），但**未独立复现**
   ⇒ ⇒ ⇒ ★ **「机制成立、当前已修」这个判定，依据的是【当前代码的形态】+【时间线】，不是【在 Citus 上重跑一次】**
2. ★ **本地四组实验都在单节点 PG 17.11 上做** ⇒ ⇒ 它们的结论是「**单节点不卡**」
   ⇒ ⇒ ⇒ **不能推出「Citus 也不卡」** ⇒ ⇒ ⇒ ★ **它们只用于【佐证 Citus 特异性】，不用于【证明已修】**。
3. ★ **当前代码的「已修」判定，依据是【代码形态 + psql 会话语义实测】**
   ⇒ ⇒ **不是**「在 Citus 上跑一次矩阵脚本验证不卡」⇒ ⇒ ⇒ ★ **这条更强的主张本轮没做**（需要那台机器 + 那批跑批）。
4. ★ **peer 的建议 (b)「先 terminate → 再 DROP（**不带 FORCE**）」当前代码**未采纳**
   ⇒ ⇒ 现状是「terminate + SET 120s + DROP **带** FORCE」
   ⇒ ⇒ ⇒ ★ **两者都做比只做一个更稳** ⇒ ⇒ ⇒ **⇒ 但改不改 = 属主决策**（本轮**未擅自改**）
   ⇒ ⇒ ⇒ ⇒ ⇒ ★★ **注意：peer 的建议 (b) 里「不带 FORCE」这一条，其实会**引入**新风险**：
   ⇒ ⇒ ⇒ ⇒ ⇒ **裸 DROP 在有活跃会话时**直接报错**（本轮实测 B 组）⇒ ⇒ ⇒ ⇒ ⇒
   ⇒ ⇒ ⇒ ⇒ ⇒ **⇒ 「不带 FORCE」需要配合 terminate 真的断开了所有会话才安全** ⇒ ⇒ ⇒ ⇒ ⇒
   ⇒ ⇒ ⇒ ⇒ ⇒ **⇒ 而 `WITH (FORCE)` 是【兜底】**（即使 terminate 漏了也能踢掉）⇒ ⇒ ⇒ ⇒ ⇒
   ⇒ ⇒ ⇒ ⇒ ⇒ **⇒ 两者的差别是「兜底强度」，不是「对错」** ⇒ ⇒ ⇒ ⇒ ⇒ ★ **本轮不改，且登记为属主项**
5. ★ **本轮没有触碰 peer 的任何文件**（`scripts/audit/check-verdict-coverage.py` / `scripts/ursmcheck/verdict_coverage_test.go` 未读未改）
