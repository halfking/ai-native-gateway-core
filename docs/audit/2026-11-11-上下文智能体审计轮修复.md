## 0. 为什么要审这一轮

第二轮刚交付「上下文智能体」这一整块新能力面（9 个新文件 + 26 条断言 + MCP 本地工具 + HTTP 门面），第三轮前半又交付了 957 迁移。新能力面的默认风险是「**看起来能跑，实际上没生效**」——本轮就抓到了 5 条这种形态的缺陷，其中 3 条会让**核心目标整体失效**（分层装配不生效、长期记忆恒空、提交语义与契约相反）。

★ 审计纪律沿用仓内既有两条：
- **结论必须带 `file:line` 与可复现的读数**，不写「疑似」当结论；
- **每条修复必须有门，且门要有牙齿** ⇒ 变异验证（把修复改回缺陷形态 ⇒ 门必须变红），否则不算修完。

## 1. 缺陷清单与处置

### P0-1　装配只认顶层键：嵌套同名键会被优先命中（出站体被改坏）

**证据**：`domains/contextagent/assemble.go` 的 `indexOfKey` 只检查「键前面一个字节是 `{` 或 `,`」，**不跟踪括号深度、也不跟踪字符串态**。

**复现**（审计轮实跑）：

```
输入: {"metadata":{"messages":["decoy"]},"model":"gpt-4","messages":[{"role":"user","content":"hi"}]}
输出: {"metadata":{"messages":[{"role":"user","content":"NEW"}]},"model":"gpt-4","messages":[{"role":"user","content":"hi"}]}
```

⇒ 顶层 `messages` **原封未动**（记忆层被静默丢弃），而**嵌套**数组被替换成整份新消息数组（出站体被改坏）。同一函数被 `spliceOrInsertTopLevelArray` 复用 ⇒ `"tools"` 注入同源缺陷。

**修复**：`indexOfKey` 改为深度感知 + 字符串态跟踪（只接受**深度 1** 的键）。

**门**：`TestAssemble_NestedMessagesKeyIsNotTouched` / `TestInjectToolSpecs_NestedToolsKeyIsNotTouched`（变异 M1 ⇒ 红）。

---

### P0-2　「首条即 user」时装配**整体失效**（最常见的请求形状拿不到任何一层）

**证据**：`assemble.go` 的 `splitHeadAndTail` 在首条即 user 时 `head = append(head, msgs[:0]...)` ⇒ `head` 仍是 **nil**；而 `Assemble` 用 `if head == nil` 当失败标志 ⇒ 把「没有 system 头」与「找不到 user」混为一谈。

**复现**：请求体 `{"model":"m","messages":[{"role":"user","content":"hi"}]}` ⇒ `Assemble` 返回 `ok=false`、`Outcome.Assembled=false`，而 PG/Memora 的查询**照跑**（真实 IO + 延迟后把结果丢掉）。

**修复**：`splitHeadAndTail` 返回显式 `ok` 标志；`head` 允许为空。

**门**：`TestAssemble_WorksWithoutSystemMessage`（变异 M2 ⇒ 红）。

---

### P0-3　`/resolve` 的 `submit=false` **仍然打上游**；`submit=true` 打**两次**

**证据**：`service.go` 的 `HandleResolve` 在 `if !req.Submit` 判断**之前**无条件跑了一次 `agent.Process`；而 `Agent.Process` 第 [5] 步（`loop.go`）**无条件** `a.Submitter.Submit(ctx, body)`。

**复现**（审计轮实跑）：`SUBMIT=FALSE upstream_submit_calls=1`、`SUBMIT=TRUE upstream_submit_calls=2`。

⇒ 客户端驱动形态产生**非预期**的上游调用 + 计费 + 记录里混入一次真实交互；网关驱动形态**双倍**成本与上游副作用。更糟的是默认接线下第一次 `Process` 用的是**没有 AuthHeader** 的 `LoopbackSubmitter` ⇒ 回灌不带凭据 ⇒ 401 ⇒ `HandleResolve` 直接 500，**客户端连装配好的请求体都拿不到**。

**修复**：`Request.AssembleOnly` 出口（第 [5] 步之前返回，**一次上游都不打**）；`HandleResolve` 只跑**一次** `Process`，按 `submit` 二选一。

**门**：`TestAgentProcess_AssembleOnlyNeverSubmits` / `TestHandleResolve_SubmitFalseNeverSubmits` / `TestHandleResolve_SubmitTrueSubmitsExactlyOnce`（变异 M3 ⇒ 红）。

---

### P0-4　记忆命名空间与写侧**永不同构** ⇒ Memora 召回恒空（L2 是死路）

**证据**：写侧口径是 `memory.UserID(tenantID, apiKeyID, memory.TaskID(r, body, apiKeyID))`（生产调用点 `domains/streaming/executors/context_summarize.go`、`:1497`；`domains/hooks/compression/compaction.go:484`）。读侧是 `Identity.Namespace()`，**自己拼字符串**，三处发散：

| 维度 | 写侧 | 读侧（审计轮实跑） |
|---|---|---|
| api_key_id | 凭据明文的稳定哈希 | **恒为 0**（`IdentityFacts.APIKeyID` 从未被赋值） |
| task 分量 | `memory.TaskID`：`X-Task-Id` 原值 / `X-Session-Id`→`s:` / body `task_id`→`m:` / body `session_id`→`s:` / 兜底 `gateway:auto:` | `X-Gw-Task-Id`（**另一个头名**）、**无前缀** |
| task 头 | `X-Task-Id` | `X-Gw-Task-Id` |

⇒ `search_memory` 与 L2 层的检索**必然 0 命中**。而 `identity.go` 的注释却声称「与 `domains/memory.UserID` 同构」——**注释与实现不符**；既有门 `TestRecognize_NamespaceMatchesMemoryUserID` 只比**字符串格式**（手工构造带正确字段的 Identity）⇒ 门无牙。

**修复**：
1. 把哈希实现**迁到** `domains/memory`（新增 `domains/memory/namespace.go`：`StableHashKey` / `APIKeyIDFromToken` / `NamespaceFor`），写侧（executors）改为委托 ⇒ 单一真源；
2. 读侧一律经 `memory.NamespaceFor` 派生；**没有模型面凭据 ⇒ 命名空间留空**（fail-closed，召回**跳过**并显式说明，不拿猜出来的分量去查）。

**门**：`TestRecognize_NamespaceMatchesWriteSideFormula`（与写侧公式**逐段对拍**）/ `TestRecognize_NoModelCredentialMeansNoNamespace` / `TestRecognize_NamespaceUsesWriteSideTaskVocabulary`（变异 M4 ⇒ 红）。

### P0-5　L0 索引的「步号」**≠** `turn_no` ⇒ 模型按索引取回**别的轮**

**证据**：`session_request_summaries.step_index` 的实现在 `domains/analysis/request_summary.go:88` 是 `i+1`，`i` 来自 `loadRequestLogs`（同文件 `:144-151`）的 `ORDER BY ts ASC LIMIT 100` 的**稠密行号**。而 L1 明细层按 `session_bodies_unified.turn_no = N` 取（`loader.go:113-118`）⇒ 两者**不是同一个序列**：

- 某一轮摘要写失败时（`saveSummary` 只记日志、不重试）该轮没有摘要行 ⇒ 后续行的 `step_index` 仍按行号递增 ⇒ **与轮次号错位**；
- `ts` 序与轮次分配序（advisory lock 单调分配 `turn_no`）不保证一致；
- `LIMIT 100` ⇒ 超过 100 轮的会话根本没有摘要。

⇒ 模型拿索引里的「步N」去调 `load_step_detail`，取回的是**另一轮**的正文（静默给错数据）。

**修复**：索引层改为按 `request_id` join `session_turns` / `session_turns_hot` 取**权威 `turn_no`**（两臂都要查：写入只落 hot，促销搬进冷表，与 `db.SessionFamilyTurnsForSessionSQL` 同形状）。没有权威轮次号的摘要行**不列出**（列一个寻址不到的步号比不列更糟）。

**门**：`TestPGIndexLoader_UsesAuthoritativeTurnNo`（含 SQL 形状门：必须出现 `SELECT t.turn_no,` / `t.request_id = s.request_id` / 两处 `public.session_turns`，且**整条 SQL 不得出现 `step_index`**）（变异 M5 ⇒ 红）。

> ★ 这条门的**第一版不够硬**：它只查 `t.turn_no` 是否出现，而变异把投影改成 `s.step_index` 后 `ORDER BY t.turn_no` 仍然命中 ⇒ **门没红**。⇒ 收紧成「整条 SQL 不得出现 `step_index`」后才抓住（变异验证实测：收紧前 NO-TEETH，收紧后 RED）。

### P1-1　回灌凭据**必然是管理令牌** ⇒ 数据面 401 ⇒ 同步回环不可达

**证据**：`/resolve` 挂在 `middleware.NewAdminTokenMiddleware` 后面，该中间件只接受 `Authorization: Bearer <admin token>`（`middleware/admin_token_mw.go:62-81`）⇒ `service.go` 取到的 `Authorization` 恒为管理令牌；数据面明确「只接受 sk-* 形态的 API key」（`domains/authentication/verifier.go:328-331`）⇒ 回灌 POST `/v1/chat/completions` 必然 401 ⇒ `/resolve` 返回 500。**同步回环这条主路径在默认配置下不可达。**

**修复**：
- 回灌凭据与命名空间统一改用**模型面凭据**（`sk-*` 明文）：运维用 `LLM_GATEWAY_CONTEXT_AGENT_MODEL_KEY` 配置；调用方自选需显式开启 `LLM_GATEWAY_CONTEXT_AGENT_ALLOW_REQUEST_CREDENTIAL=1` + `X-Model-Key` 头（**默认关**：凭据决定命名空间 ⇒ 客户端自选 = 放大同租户内的记忆读取面，上一轮已拍板）。
- 没有凭据时 `submit=true` **早失败并说人话**（400），而不是拿管理令牌去打数据面换一个含义不明的 500。

**门**：`TestHandleResolve_SubmitTrueNeedsModelCredential` / `TestHandleResolve_LoopbackCarriesModelCredential` / `TestHandleResolve_RequestCredentialNeedsExplicitOptIn`（变异 M6 ⇒ 红）。

### P1-2　`stream:true` ⇒ 记忆工具回环**静默失效**

**证据**：装配保留 `stream` 原始字节 ⇒ 上游按流式返回 SSE；而 `DetectMemoryToolCalls` 走 `json.Unmarshal`（`tool.go:141`）对 SSE 必然失败。审计轮实跑：`SSE body → detected memory tool calls = 0`。

**修复**：网关驱动形态（服务端跑完整循环）把顶层 `stream` **强制改写为 `false`**（字节级、深度感知定位）；客户端驱动形态**不动** `stream`（保留客户端的流式偏好）。改写会在 `Outcome.Notes` 里留痕。

**门**：`TestForceNonStream_RewritesTopLevelStream` / `TestForceNonStream_IgnoresNestedStream` / `TestForceNonStream_AlreadyFalseIsNoop`（变异 M8 ⇒ 红）。

---

### P1-3　MCP 工具的 `task` / `project` 参数是**死代码**

**证据**：`cmd/gateway/context_agent.go` 的 `contextIdentityFromMCP` 读 `args["task"]` / `args["project"]`，但两个本地工具的 `AllowedParams` 分别是 `{step_index, session_id}` 与 `{query, top_k, session_id}`，**都不含**这两个；而 `mcp/policy.go` 的 `validateParams` 对未列入白名单的参数**直接拒绝**（`ErrForbidden`）⇒ handler 根本走不到。

**修复**：**删掉**这两段读取（而不是加进白名单）：`project` 不参与记忆寻址；`task` 会决定命名空间 ⇒ 让客户端自选 = 放大同租户内的记忆读取面。作用域只由**凭证**（tenant + key）与 `session_id` 参数决定。

### P1-4　`tools/list?group=…` 的过滤对本地工具**不生效**

**证据**：上游分支有 group 过滤（`mcp/server.go`：`if group != "" && (meta == nil || meta.Group != group) { continue }`），而 `localToolViews` **没有 group 参数** ⇒ 本地工具无条件进清单。审计轮实跑：`tools/list?group=something-else → 仍列出 search_memory`。

**修复**：`localToolViews(id, group)` 套用同一过滤条件。

**门**：`TestLocalTool_GroupFilterApplies`（变异 M7 ⇒ 红）。

---

### P2-1　`/resolve` 出参的编码未写明 ⇒ 客户端会把 base64 当请求体转发

**证据**：`ResolveResponse.Body []byte` 经 `encoding/json` 编成 **base64 字符串**，但字段名是 `body`（`RecordResponse` 明确用了 `_b64` 后缀，`/resolve` 没有）⇒ 客户端按字面 JSON 解析会拿到 base64 却以为它是请求体。

**修复**：字段改名为 `body_b64` / `response_body_b64`（与 `/record/{id}` 的 `*_b64` 同一约定），并订正「submit=true 时 Body 返回最终响应体」的**错误注释**。

**门**：`TestResolveResponse_FieldsAreExplicitlyBase64`。

---

### P2-2　注入 `tools` 到空对象产出**非法 JSON**

**证据**：`spliceOrInsertTopLevelArray` 的插入分支无条件补逗号 ⇒ `{}` ⇒ `{"tools":[...],}`（尾逗号 ⇒ 非法 JSON）。同时它取「第一个出现的 `{`」⇒ 对数组体 `[{"a":1}]` 会插进**嵌套对象**。

**修复**：空对象不加逗号；插入分支要求**首个非空白字节就是 `{`**。

**门**：`TestInjectToolSpecs_EmptyObjectStaysValidJSON`（变异 M9 ⇒ 红）。

---

### P2-3　`Plan.LoadSteps` 生产路径恒空 ⇒ L1 明细在装配里不可达

**证据**：`MakePlan` 只从 `PlanInput.AvailableSteps` 填 `LoadSteps`，而 `Process` 构造 `PlanInput` 时不传 ⇒ `plan.LoadSteps` 恒空 ⇒ `loadLayers` 的 L1 分支永不进入。

**处置（**不是**缺陷，是设计边界，写成显式契约）**：

★ L1 **不进装配**，走记忆工具按需取。理由不是「实现没来得及」，而是**自动装载会放大一个已知缺陷**：生产上 `request_delta` 常常是「客户端完整历史」而不是本轮增量（仓内 FIXME-14372/14373，实测 45–146× 放大）⇒ 一步的正文可能是整份历史的重复；自动装 N 步 ⇒ 同一份历史被注入 N 次 ⇒ 上下文预算直接爆，而且是在**已经付了 IO 代价之后**才发现装不下。

⇒ 闭环靠 **L0 索引给权威步号 + 模型调 `load_step_detail` 精确取回那一步**（P0-5 修的就是这个对齐）。`Plan.LoadSteps` / `PlanInput.AvailableSteps` 保留为「按需装载」的预算算式（`MakePlan` 是纯函数、可完整单测），但生产路径**不填**。

**门**：`TestL1DetailIsOnDemandNotAutoLoaded`（钉住「L1 不进装配」＋「索引步号可被工具精确取回」）。

## 2. 结构性边界（**不是**可修的缺陷，诚实登记）

★ **MCP 侧召不回数据面的长期记忆**：MCP 凭证（`mcp.Key` / `HashSecret`）与数据面 `sk-*` 凭据是**两套凭证体系** ⇒ 即便哈希口径完全一致，两边的 `api_key_id` 也必然不同 ⇒ 命名空间不重叠。

⇒ 处置：命名空间推导已统一到 `domains/memory` 单一真源（口径一致），但**边界本身不能靠改代码消除**。工具在「没有命中」时**显式带上边界说明**（`Identity.MemoryNamespaceNote`），不让读数被读成「记忆是空的」。

★ **回灌轮次可能落在另一个任务分区**：写侧任务词表里 `m:`（body 来源）与 `gateway:auto:`（body 哈希来源）**无法用头复现** ⇒ 回灌请求**不造近似头**（造了更糟：会落到一个再也召不回来的分区）。能复现的两种（`X-Task-Id` 原值 / `X-Session-Id`→`s:`）会带上，保证回灌轮次落在同一分区。

★ **`/resolve` 的租户来自请求头**（`X-Gw-Tenant-Id`）：该端点只认管理令牌 ⇒ 属管理员能力，不是越权面；但它同时是 PG 查询的隔离条件 ⇒ 管理员需知道自己在声明哪个租户。

## 4. 本轮**明确没做**

| 项 | 原因 |
|---|---|
| **不动 957 迁移** | 逐项对拍全部通过，没有可修的东西 |
| **不改写侧记忆写入路径** | 生产变更克制：命名空间口径是**搬实现**（哈希迁进 `domains/memory`）不是**改语义**；写侧的 `memory.UserID(tenant, apiKeyID, memory.TaskID(...))` 三个分量一字未动 |
| **不让客户端自选 `api_key_id`** | 会扩大同租户内的记忆读取面（上一轮已拍板）⇒ `X-Model-Key` 默认**不生效**，需显式开启 |
| **不统一 MCP 凭证与数据面凭证** | 两套凭证体系本身不同源 ⇒ 只能登记边界，不能靠改代码消除 |
| **L1 不自动装载** | 见 P2-3：会自动放大 FIXME-14372/14373 的历史重复放大 |
| **不改 L0 摘要的生成口径** | `step_index` 的**生成**侧（`domains/analysis`）不动 ⇒ 只在**读侧**对齐（改生成侧会动既有数据与运营全景页） |
| **不内联 chat 热路径** | 属设计档 P5 阶段，仍未动 |
| **不改 `request_delta` 的差集基准** | 属主决策⑭/⑮，未拍板 |
