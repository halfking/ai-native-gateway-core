## 二、haiku 流式：Vapeur 模型级封锁（直连证实，网关无责）

- 网关日志（两次 T2 失败同因）：`[unsupported_feature] upstream 400:
  {"message":"Operation not allowed"}`，chat 腿 stream=true 490ms 被 400。
- 直连 Vapeur 对照（不带网关）：
  - `POST /v1/chat/completions stream=true` → **400 `{"message":"Operation not allowed"}`**
  - 同请求 non-stream → 200 正常
  - `POST /v1/responses stream=true` → **502 包「该供应商不支持 Responses API 流式请求」**
  - claude-opus-5-5 chat 流式直连 → 200 正常（对照：封锁是 haiku 模型级，不是 claude 族级）
- **结论**：Vapeur 对 claude-haiku-5-5 的流式两条腿都封死，且是持续性封锁而非上午轮
  推测的「偶发过载相关」。网关行为（unsupported_feature 分类、单候选快速失败不盲重试）
  符合设计。**修正上午轮登记**：「chat 腿 400 Operation not allowed（偶发，过载相关）」
  → 对 haiku 是持续封锁；对 opus 不成立（流式正常）。
- 给使用方：haiku 走 Vapeur 只能非流式；流式需求换 opus 或其它凭据。

## 三、P7 ★ 钉扎凭据被 fp_slot 预过滤剔除 → 硬 pin 收窄成 0 候选（已修）

### 3.1 现象与取证链

glm-5.3 钉扎请求两轮失败（15:34:39 cred29 / 15:41:46 cred19），同窗未钉扎请求正常。
关键日志序列（15:41:46，间隔 12ms）：

```
candidates_resolved        candidates_count=12
cred_fp_slot prefilter skip  credential_id=63      ← 钉扎凭据被 fp 预过滤剔除
goal_retry_exhausted       all 0 candidates failed: dispatch: no routable credential/model available
```

### 3.2 根因（三层叠加）

1. **r1024 激活了休眠 8 周的语义合并**：admin 的 `X-LLMGW-Preferred-Credential`
   （8e71eb4e19，2026-08-23）与内部探针 `X-LLM-Pin-Credential`（400f014ada，08-13）
   落到同一个 `ExecParams.PinCredentialID` 字段；但 `SetAdminAPIKey` 一直没接线，
   admin 钉扎恒返回空（死代码）。r1024 接线后**硬 pin 语义第一次真正生效**——
   与 `sticky_router.go` 文档化的软回退契约（「若首选凭据不可用，必须能降级到
   其他候选」）相悖，且 `dispatchRoute` 的硬过滤注释只写了探针场景
   （「probe verdict is attributable to that exact node」）。
2. **fp_slot 预过滤先于硬 pin 过滤执行**：`Execute` 的预过滤循环把
   `RoutingEligibleForTenant=false` 的候选剔掉（钉扎凭据 63 在批次压力下指纹槽
   被其它 holder 占满）；随后 `dispatchRoute` 的硬 pin 过滤只保留钉扎凭据——
   它已经不在集合里 → refs 空 → `all 0 candidates failed`，未触任何上游。
3. **单候选模型走的是另一条兜底**：gpt/opus 等只有 cred 63 一个候选，fp 预过滤
   全剔时触发 `cred_fp_slot all saturated, degrading to full candidate set`
   （fpSlotDegraded，无槽继续执行），所以同窗它们只是 preflight WARN 而不是失败。
   多候选 + 钉扎的组合恰好落在两条兜底的缝隙里。

### 3.3 修复（一层抽取 + 一条豁免）

- `domains/streaming/executors/executor.go`：预过滤循环原样抽成
  `fpPrefilterCandidates`，并加一条豁免——**钉扎候选不受 fp 预过滤剔除**
  （`params.PinCredentialID != nil && cand.CredentialID == *params.PinCredentialID`）。
  对不可入座的钉扎节点，设计好的继续路径是 dispatch Acquire 循环的
  「`dispatch fp slot saturated, running without slot`」降级执行（既有行为，
  `TestForwardForDispatchDegradesWhenFpSlotSaturatesAfterPrefilter` 钉住），
  而不是在预过滤层就丢掉。
- 语义取舍（明示）：保持 admin 钉扎 = 硬 pin（QA 复现需要「钉谁测谁」，r1024
  起的既成行为），只修「预过滤先把钉扎对象偷走」这一层缝隙。软回退语义属于
  `dctx.stickyCredID`（会话粘性，首尝试后自然失败转移），两条通道不混。
- 豁免面评估：PinCredentialID 只可能来自内部探针头（`origin_mw.go` 对外剥离
  `X-LLM-Pin-Credential`）或 admin token 验证的钉扎头——豁免不可被普通客户端
  利用。非钉扎路径逐字节不变。

### 3.4 判据与变异验证

- `executor_dispatch_fpslot_test.go::TestFpPrefilterKeepsPinnedCandidateWhenSlotSaturated`
  （同层驱动 `fpPrefilterCandidates`）：miniredis 占满 cred 63 的指纹槽
  （DefaultLimit=1，other-session 先 Acquire）→
  ①带 pin：钉扎饱和候选必须存活（len==2）；②去 pin：同候选必须被剔（只剩 29）。
- 变异验证：撤豁免（退回纯 RoutingEligible 判定）→ 红在
  「pinned saturated candidate must survive the prefilter」（正确断言）；恢复后绿。
- 回归：`CGO_ENABLED=0 go test ./domains/streaming/executors/ -count=1` 全绿
  （43.5s，含既有 fp degrade 用例）；`go build`/`go vet`/`gofmt -l` 干净。
