## §0 一句话结论

**R77 轮留下的「应用侧 ~5.4s 缺口」不存在。**
真正的成因有两条，都不是「应用里有一段说不清的耗时」：

1. **R77 轮用「最好的一次读数」（464ms）当基线** ⇒ 真实分布是 **p50 2.3s / p90 21.9s / max 106s**（n=119）;
2. **252 是共享库，尾延迟由库级负载决定** ⇒ 同一条 SQL、同一冻结窗口，**隔离跑只要 391~500ms**，跑在负载里就是 5.5s~106s。

⇒ **代码层能修的是「响应完整性」，修不了「24h 窗口的尾延迟」。**
本轮落地：**步骤顺序改为成本升序**（band → bucket → agg → estimated-orig）+ **每步耗时留痕**，
让「便宜且必需的数据不再被一条慢查询饿死」，并让下一次同类问题**一眼可定位**。

## §2 定位链（四步，每步都有可复算的证据）

### §2.1 第一步：拿到「服务端视角的真实 SQL」

`log_min_duration_statement = 1s`（252）⇒ **慢于 1s 的语句连完整 SQL 文本都进日志**。

取 PG 容器日志（真实通道是 conmon 的
`overlay-containers/<id>/userdata/ctr.log`，**不是** `docker logs`），
按 `stderr F` / `stderr P` 标志**重组字节级碎片**后，抽出 07:30:10 那次 app 请求的 agg 语句
（5,487.570 ms）。

### §2.2 第二步：与仓内源码逐字对拍

把 app 的语句与「从仓内 `db.SessionFamilyTurnsSourceSQL()` / `SessionFamilyBodiesSourceSQL()`
生成的 SQL」做归一化 diff：

```
app len: 11449   mine len: 11447   IDENTICAL: False
replace APP: '...t.ts >= $T AND t.ts <= $T AND ( $B OR t.success)...' || MINE: '...$1 ... $2 ... $3...'
```

差异**全部**是归一化假象（两个时间戳被同一个正则替成 `$T`、字面量 `'t'` 替成 `$B`、空白）。
⇒ ★ **应用没有「偷偷改过的 SQL」**，R77 的形状结论继续成立。

> ⚠ 量具教训（当场复核）：第一次 diff 输出「空 diff ⇒ 两侧相同」，
> 实际是**两侧 grep 模式都打空**（模式 `^[0-9]+_` 与文件真实格式不符）⇒
> **「diff 返回 0」≠「两者相同」**：必须断言两边存在且非空。

### §2.3 第三步：量真实耗时分布（而不是取最好的一次）

慢查询日志窗口 **4.2h**，`duration ≥ 1s` 的记录 **740 条**。从中筛出 compression/stats 的 agg：

| 指标 | 值 |
|---|---|
| 样本数 n | 119 |
| min | 1,004 ms |
| **p50** | **2,296 ms** |
| **p90** | **21,921 ms** |
| max | 105,991 ms |

⇒ ★★ **R77 轮对拍的 464ms 是「最好的一次」**，不是基线。
⇒ R77 的**相对**结论（EXISTS 只求值一次 = 1.85×）因是**同窗口交错 A/B**仍然可信；
但它的**绝对**数字（464ms / 860ms）**不可再引用**。

### §2.4 第四步：同一 SQL、同一窗口、隔离跑

用 app 那次请求的**原窗口**（`'2026-10-22 23:30:04.757168Z'` ~ `'2026-10-23 23:30:04.757168Z'`）


⇒ ★ **同一条 SQL 隔离跑 391ms，挂在负载里 5,487ms** ⇒ **差的是环境，不是语句。**

## §5 本轮落地

### §5.1 代码：`admin/compression_stats.go`

1. **步骤顺序 = 成本升序**：`band` → `bucket` → `agg` → `estimated-orig`。
   * 隔离态实测成本：`band` **40ms** / `bucket` **220ms** / `agg` **280ms** / `est-orig` >10s；
   * 前置两条便宜步只花 ~260ms ⇒ **agg 仍剩 ~9.7s** ⇒ agg 的成功率几乎不变；
   * 而旧顺序下 agg（p50 2.3s / p90 21.9s）**经常吃满 10s** ⇒ band/bucket 一个都跑不到
     ⇒ `hourly_series` / `token_band_*` 整段缺失（生产实测）。
2. **每步耗时留痕**：`slog.Info("compression_stats step", step/elapsed_ms/budget_ms/skipped/err)`。
   ⇒ R77 之所以要靠「掐断的读数」猜缺口，就是因为**缺这一步的耗时**。

### §5.2 为什么**不**给 band/bucket 加独立预算

R77 的形状门第②条明确要求「必需步骤不得有独立预算上限」——**门在守的是「核心数字不得被跳过」**。
若给 band/bucket 加预算，它们会变成「可跳过」⇒ 与该门立意相反。
⇒ **正解是调顺序（顺序是数据），不是加预算（那会让它们变成可跳过）。**

### §5.3 门

* 新文件 `admin/compression_stats_order_test.go`（2 条）：
  * `TestR78CompressionStatsCheapStepsMustRunBeforeExpensiveRequired`
    ⇒ 断言 band/bucket 在 agg **之前**、且二者**不得**有独立预算；
  * `TestR78CompressionStatsSlowAggMustNotStarveCheapSteps`
    ⇒ 行为腿：agg 吃满剩余预算时，便宜步**已拿到数据**，降级原因**只点名 agg**。
* **R77 的门文件一字未改**（`admin/compression_stats_shape_test.go`）⇒ 8 条门全绿，
  证明 R78 没有破坏 R77 的三条判据。
* **变异 M5**（把 agg 换回第一位）⇒ 顺序门红；**M6**（给 band/bucket 加预算）⇒ 预算门红；
  两次均**文件级备份 + md5 还原**（3ff81c34… / 1ed6ccf4…）+ **残留自检**通过。
* `go build ./...` 绿、`go vet ./admin/` 绿、**`go test ./admin/` 全包 79.463s 全绿**。
