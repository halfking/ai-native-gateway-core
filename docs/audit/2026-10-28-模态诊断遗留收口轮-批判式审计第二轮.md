## 1. 审计 C（最严重）：部署脚本的两处真缺陷

### 1.1 缺陷 1：逃生门被 git 无条件覆盖 ⇒ 「两条出路」实际只有一条

上一轮的门在目标机侧写了「两条出路：① 走 --via；② 显式 export DD_BUILD_SHA」。
**但部署机侧第 533 行是无条件赋值**：

```bash
DD_BUILD_SHA="$(git -C "$DD_REPO_ROOT" rev-parse --short=8 HEAD 2>/dev/null || true)"
```

⇒ 运维在**部署机**上 `export DD_BUILD_SHA=<号>` 会被这一行静默吃掉（该行在
`--via` 分支里，且在取号之后才转发）⇒ 声明的身份永远到不了目标机 ⇒ 目标机
侧撞上 fail-closed ⇒ 报错写着「显式 export 后重跑」，而运维照做后**依然被拒**
（同一个号又被覆盖回空）⇒ 死路。

**修正**（`scripts/deploy-seamless-docker.sh`）：显式给的号优先，不再被 git 覆盖；
dirty 后缀只对 git 取到的号追加（声明的号是运维自称，追加 -dirty 反而让
「声明的号 ↔ 实际树」的关系更难读）。

### 1.2 缺陷 2：--via 路径上门不执行 ⇒ 空号被发到目标机

上一轮的门装在**目标机侧**（脚本末尾），但 `--via` 路径的流程是：

```
部署机: 取号 → tar 同步 → ssh 目标机执行引擎 → exit
目标机: 独立跑一份引擎（无 .git）⇒ 撞上目标机侧的门 ⇒ die
```

⇒ 空号确实会被**发到目标机**（转发时 `DD_BUILD_SHA=''`），由目标机侧 die兜住。
后果不是「静默说谎」，而是**报错落在远端**：运维看到的是「211 上部署失败」，
而根因在部署机（部署树不是 git 检出）⇒ 排查方向被带偏。

**修正**：在**部署机侧**转发 ssh 之前加一道同语义的门（号为空 ⇒ 不发这次 ssh），
错误落在信息最全的地方；目标机侧的门保留（它是最后一道防线，直跑路径靠它）。

### 1.3 修正后的三道闸（语义一致、位置不同）

| 位置 | 触发条件 | 作用 |
|---|---|---|
| 部署机侧（--via 分支，转发 ssh 前） | 号为空 | 不发这次 ssh（不把空号发到远端） |
| 部署机侧（取号段） | 显式号存在 | 保留显式号，不被 git 覆盖 |
| 目标机侧（引擎末尾） | deploy 模式 + 号为空 + 无 .git | fail-closed die（直跑路径的最后防线） |

### 1.4 新增行为门：tests/deploy_seamless_version_identity_test.sh

★ **上一轮只加了实现没加测试 ⇒ 有功能没牙齿。** 而且当时的实现有两处真缺陷，
而 grep 文本门（「脚本里有没有 die」）对这两处**都是绿的**。

本轮的门是**行为门**：把引擎里那段身份闸的**真代码**（不是复制品）抠出来
驱动，断言它**真的拒绝**。9 条断言：
① 无 .git + 无号 ⇒ 拒绝，且拒绝理由来自**第一道门**（"同步树形态"）；
②拒绝信息点名 DD_BUILD_SHA；③ 非 deploy 模式（--status/--probe-only）不被拦；
④ 显式给号 ⇒ 放行（逃生门可用）；⑤ 放行日志回显号；⑥ 部署机侧显式号不被 git
覆盖；⑦ 部署机侧未给号时从 git 取号；⑧ --via 侧身份门在转发 ssh 之前；
⑨ 反空洞断言（抽取片段必须含取号语句）。

**三个变异臂（逐个被抓红）**：
- M1「显式号被 git 覆盖」⇒ 红（且**报的是那一条**，不是误导性的另一条）；
- M2「第一道门降级为 log」⇒ 红（**这条暴露了门自己的一个洞**：原本只断言
  「整体拒绝」，而第二道门会兜住 ⇒ 掩盖了 M2；修法是断言「拒绝理由来自
  第一道门」）；
- M3「--via 侧的门被删」⇒ 红。

**门自身的三处坑（都是本轮实测踩出来的）**：
1. **反空洞**：按「找某个 if 条件」抽片段时，把条件改成 `if true; then` 就抽不出
   ⇒ 片段为空 ⇒ 「显式号不被覆盖」那条**空洞通过**（断言空片段恒真）⇒ 门对
   目标变异没有牙。修法：按**稳定注释锚点**取整段 + 断言片段含取号语句。
2. **逐档/逐处 vs 聚合**：verdict gate 有多处 `$3 IN (...)`，并成集合会互相
   掩盖（改窄一处，另一处仍含该模态 ⇒ 检不出）。修法见 §2.3。
3. **`$var` 紧跟全角括号**：中文注释里的 `$rc）` 在 UTF-8 locale 下会被并入
   变量名 ⇒ bash 报「未绑定的变量」（仓里 verify.sh 的注释早记着这条，本轮
   亲自踩了一次）。

## 2. 审计 B：锁步门的覆盖边界与缺口

### 2.1 覆盖边界未声明（声明 > 事实）

上一轮的门对拍的是 `candidateQuerySQLBase()` 的**接受臂**，但生产真正执行的是
`candidateQuerySQL()` = base **替换 verdict gate** 后的产物。门本身是对的
（gate 是数据驱动的**排除**层，Go 侧 `ModalityAccepts` 建模的是**静态接受集**，
职责分层不同）—— 但**门头注释没写这件事**，读者会以为它管「全部模态裁决」。
⇒ 本轮补了覆盖边界声明（写清三层：接受臂 / gate 排除层 / gate 的上游对齐门）。

### 2.2 真实缺口：gate 的模态列表与臂的媒体模态集合可以分叉

gate 用 `AND NOT (... $3 IN (...) ...)` 排除「有负向读级记录」的模型。若 gate
的模态列表比臂**少**一个（如少 audio），则：audio 请求走臂（被接纳），但
audio 的负向读级**不触发排除** ⇒ 实测「看不见」的模型仍被路由到 ⇒ **静默的
质量退化**（没有 4xx、没有日志）。

上游 `candidate_query_sql_shape_test.go` 钉的是「gate 的模态列表与接受臂
**那一处**的列表不漂移」，但没有「gate 的列表 ⊇ 臂内**所有**媒体模态」这条
判据 ⇒ 本轮补上。

### 2.3 判据形态：逐处比对（三次返工才做对）

- 第一版：扫**整条生产 SQL** 找 `$3 IN (...)` ⇒ **错**：SQL 里还有第三处
  `$3 IN ('audio','video','image')`（routing_scope 的 CASE 分支，与模态无关）
  ⇒ audio 被「顺带算进 gate 列表」⇒ 改窄 gate 检不出。
- 第二版：按档（缺省/严格）取集合 ⇒ **错**：严格档 = 缺省段 + 追加段，
  改追加段被缺省段掩盖。
- 第三版：按档取差集 ⇒ **错**：两段列表本来就相同 ⇒ 差集为空 ⇒ 判据失效。
- **第四版（落地）**：**逐处**列表，每一处都必须覆盖臂内媒体模态集合 ⇒
  改窄任意一处都当场报红（并点名是第几处）。

**变异臂**：M-A（缺省段少 audio）红、M-B（严格段追加少 video）红。

## 3. 审计 A：我自己搞坏的本地测试库

上一轮重建本地 `llm_gateway_test` 时用了「01-schema 快照 + 重放 900 条 startup
迁移」的配方 ⇒738/740/815 三条迁移 abort（视图链重建不收敛）⇒
`request_logs_with_current_month` **0 列**（主库同表118 列）⇒ 我亲手把
本地环境里的近期窗口读面搞成了坏视图。

**根因**：01-schema.sql 是**终态快照**，重放迁移等于把已经应用过的变更再应用
一次 ⇒ 视图/分区/序列全部进入「已存在」冲突态。正确配方只有两遍快照
（记忆里 pg-verify-environment-gotchas 写的也是「00-prereqs → 01-schema 两遍
→ 02-seed」，**没有「重放 900 条迁移」这一步**——是我自己加的）。

**修正**：从**健康的主库** `llm_gateway`（迁移 885、含 915 函数、视图链 118 列
正常）导出 schema-only，重建测试库，再补 886~915（逐条独立事务，避免一条
abort 连累后续）。**结果**：584 表 / 视图链 118 列 / 915 函数在位 / provider
全包 **85 PASS / 0 FAIL**（比上轮多 1 条 = 本轮新增的 gate 判据）。

★ **教训**：把「本地环境重建」当成了「顺手做的事」，而它其实有配方，且配方
里没有的那一步（重放迁移）就是破坏源。⇒ 重建环境必须照配方，且重建后要验
**读面**（视图列数、函数存在性），不能只看「表建出来了」。
