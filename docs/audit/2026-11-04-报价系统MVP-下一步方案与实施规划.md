## §0 本轮三个增量结论（先说结论）

**结论一：骨架三件的行业答案全部拿到一手出处，且与《风暴档》预判同构——方案从"我们要这么做"升级为"业界都这么做，我们按业界形态落"。** 报价单版本化 = ERPNext「Cancel and amend，禁止静默改已发出报价」＋ Invoice Ninja 七态状态机；快照 = Invoice Ninja line_items 内嵌 JSON + exchange_rate + Odoo purchase_price 创建时定格；审批 = DealHub「三维阈值触发（折扣深度×交易规模×毛利下限）+ 政策内自动放行、只审例外 + 并行 SLA + 全程审计 + 阈值突破率自校准」。

**结论二：LLM 计费生态调研给出零售价（P5）的完整参照系——one-api/new-api/LiteLLM/OpenRouter 全部收敛到「输入价 + 输出价 + 子资源扩展位」的原子结构，基础价与商业折扣（分组倍率）是两个正交轴、折扣从不直接改基础价。** 这正面支持《风暴档》§3.7 的"成交不改价"：零售价落库时，`model_credit_rates`/`tenant_model_rates` 存基础价，客户折扣走 `discount_pct`（939 已有该列）——两者混写一行是对账失真的根源，业界没有一家这么做。

**结论三：迁移号落定 942–948 七个（对应《风暴档》§5 八件里的七张表，分享访问日志并进 shares 表的伴生审计表占 948 之外的第 949 号）；实施分期 W1 两轮提交、W2 两轮提交，每轮带独立验收门——把《风暴档》§7 的路线图变成可执行的任务卡。**

| **Invoice Ninja**（10.5k★，源码 v5-stable 实读） | Quote + QuoteInvitation + line_items JSON | ① 状态机七态：DRAFT/SENT/APPROVED/CONVERTED/REJECTED/CANCELLED/**EXPIRED=-1**；② **Expired 是派生态不是存储态**：读取时按 `due_date`+客户时区现算，不用定时任务刷库（消灭状态刷写竞态）；③ line_items **内嵌 JSON 快照**（数量/单价/税/折扣逐行固化）+ 文档级 exchange_rate；④ 公开分享 = **按联系人发令牌**（`QuoteInvitation.key`）+ sent/viewed/opened 三时点埋点 + 接受即签署（签名/时间/IP 落库） |
| **Kill Bill**（5.8k★） | Catalog→Plan→Phase→PriceList | ① 价格目录**按生效日期版本化**（effectiveDate 即版本）；② 下架挡新增、**不抹存量**（已签合同引用旧版本继续有效）——「已发报价单引用旧价快照」的目录侧对应物；③ `effectiveDateForExistingSubscriptions` 存量缓变通知期 |
| **Odoo sale+sale_margin** | sale.order 四态 + locked 布尔 | ① 锁定是**正交布尔**不是状态（`locked` + tracking）；② **成本在报价时点定格**：行上存 `purchase_price` 快照，`margin`/`margin_percent` `store=True` 预计算落库——之后成本主数据变了报表不漂 |
| **DealHub / Pricefx（Deal Desk）** | 政策内自动放行、只审例外 | ① 触发维度收敛为三个：**折扣深度 × 交易规模 × 毛利下限**；② 三层 SLA（标准自动 / deal desk 24-48h / 高管 72h）；③ 审批**并行不串行**；④ **阈值突破率是阈值定错的信号**——突破率过高说明阈值该调；⑤ 具体数值各来源均标 e.g.（>20% 折扣、70% GM），**不存在行业标准数** |

### 1.2 LLM 计费生态侧（价格表示 · 倍率 · 预算 · 比价）

| 来源 | 核心抽象 | 直接可抄的设计点 |
|---|---|---|
| **one-api**（songquanpeng，README+源码） | 三倍率乘法 + quota 积分 | 公式 `quota = ceil((prompt + completion×completionRatio) × modelRatio × groupRatio)`；**倍率分解进消费日志**（"倍率：%.2f × %.2f × %.2f"）——每笔消费可精确复算；pre-consume（预扣）→失败退回→post-consume（补差）三段式 |
| **new-api**（QuantumNous，源码实读） | 倍率系超集 + 表达式计费 DSL | ① `ModelPrice` 按次价表与倍率表并列，查到按次价就按次计费；② **cache_ratio 表**（读默认 1.0/写默认 1.25，Claude 0.1）；③ `tier()` **把命中档位显式记入日志**——"为什么是这个价"可解释性；④ 阶梯条件用完整上下文长度 `len` 不用 `p`（缓存命中会压低 p 造成误判档） |
| **LiteLLM**（BerriAI） | 真实 $/token 价 + 四层预算 | ① 价格条目 = 价格 + 能力位 + **`deprecation_date`/`successor_model`/`source`（退役日期与来源 URL 进价格表）**——报价单自动失效的现成参照；② key/user/team/end-user 四层预算 + `budget_duration` 周期 + soft/hard 两态 + **多窗口并存**（$10/24h + $100/30d）；③ 价格表显式 0 才算 free，缺省 ≠ 0（**NULL≠0 的业界同构**） |
| **OpenRouter**（API 实测） | pricing 扁平对象 + overrides + 逐 provider 端点价 | ① `overrides` 数组：**按输入长度分档**（`min_prompt_tokens`）与**按时段分档**两种正交形态；② 同模型逐 provider 价格表 + **区域加价显性化**（$3→$3.30 约 +10%）；③ **`max_price` 硬闸 vs `sort=price` 偏好分离**——红线与择优是两个旋钮；④ 免费模型 prompt/completion="0" 显式 |
| **Lago**（getlago） | Metric→Charge→Plan→Subscription→Invoice | ① **计量与定价分离**（metric ↔ charge 多对多带配置）；② **graduated（分段累进）vs volume（整量落档）必须显式声明**——报价单若支持阶梯价，这是第一个要定的语义；③ wallet 的 paid/granted 双轨 + `rate_amount` 汇率 + `applies_to.fee_types`（这笔积分能抵什么） |
| **OpenMeter**（README 级） | Meter→Entitlements→Credits→Plans | ① entitlement（有没有权限/上限）与 credit（还剩多少）**分开建模**；② 产品目录版本化 |

**共性归纳（两轮调研合流）**：
1. **报价单自包含快照**：行项目、汇率、成本、毛利在创建时点全部物化进报价单本身（Invoice Ninja + Odoo），主数据只在新报价时生效；过期态**读取时派生不落库**。
2. **版本边界 = 提交/发出时刻**，发出后修订 = 取消旧版 + 新版（ERPNext），锁定是正交布尔（Odoo）。
3. **审批三维触发 + 例外路由 + 突破率自校准**（DealHub）；数值必须用自家毛利结构定。
4. **价格原子结构 = {输入价, 输出价, 子资源扩展位}**，基础价 × 商业折扣正交分解、**每一层独立进日志**（one-api 三倍率 / OpenRouter 区域加价 / new-api tier()）。
5. **失效有日历**：LiteLLM `deprecation_date`/Kill Bill effectiveDate——价格与报价都有"从哪天起算"的一等概念。

## §3 方案：报价系统 MVP 的三个设计决议（把调研接进《风暴档》）

### 3.1 决议 A —— 版本化采用「发出即锁 + 修订即新版」的 ERPNext/Invoice Ninja 双源形态

《风暴档》§3.4 只定了「发出即锁版本」。本轮细化：

- **版本边界 = sent 时刻，不是 draft 时刻**（ERPNext：submit 冻结送审版）。draft 可以反复改，`pending_approval` 起禁止改内容，`sent` 后任何改动 = **新版本行 + 旧版本 superseded**，禁止原地 UPDATE。
- **快照物化**（Invoice Ninja line_items + Odoo purchase_price 双源）：`sales_quote_items` 每行存**创建时点的** `cost_in_per_1m`/`cost_out_per_1m`/`currency`/`fx_rate`/`sale_price`/`margin`/`margin_pct`/`confidence`（C3 档）——之后 940 表怎么更新、汇率怎么变，已存行不动。毛利**预计算落库**（`store=True` 范式），报表永远读快照列，不做实时 join。
- **Expired 是派生态**（Invoice Ninja）：`expired` 不落库，查询时 `status='sent' AND valid_until < now()` 现算（加 `EXPIRED=-1` 兼容位）。避免定时任务刷状态 + 刷写竞态。
- **`locked` 正交布尔**（Odoo）映射到审批：审批中 `locked=true`，审批通过解锁进入 sent。

### 3.2 决议 B —— 审批采用 DealHub 三维阈值 + 「只审例外」

《风暴档》§3.3 的「两维分层红线（模型档×客户档）」保留为**毛利下限**维，本轮补齐业界三维结构：

- **触发条件 = 三维**：① 毛利下限（两维分层表，settings_kv）；② **折扣深度**（报价价 < 标准档系数的差 >X%）；③ **单笔金额**（建议 ≥$500 触审，待裁决）。任一触发即 `pending_approval`。
- **政策内自动放行**：三维全不触发 ⇒ 直发，**不进人审**——DealHub 判据「A deal goes to an approver only when it crosses one of those rules」。MVP 单级审批（super/运营负责人）照旧。
- **审批记录加一列 `trigger_reasons jsonb`**：记「哪三个维度、各自读数、各自阈值」——审计可复算。
- **突破率自校准**（DealHub）：漏斗看板加「审批触发率 + 按维度分布」——触发率过高（建议 >40%，待裁决）说明阈值定错，这是红线数值的第一手调参信号，比拍脑袋改数值可靠。

### 3.3 决议 C —— 零售价快照采用「基础价 × 折扣正交」的业界共识结构

- 报价单的零售价列拆两轴：**基础零售价**（积分 per 1M，引用 `effectiveModelRates` 兜底链的读数）× **折扣系数**（客户商谈折扣）——**折扣永不写回基础价**（one-api 三倍率/one-api 分组倍率、OpenRouter 区域加价同构；与本仓 939 `discount_pct` 与单价列的乘法关系同形）。
- 每行毛利分解进快照：`{rate_in, rate_out, tokens_est, discount, confidence}`——与第 45 增量流水 `detail` 五因子**同构**，报价毛利与实收毛利在 W3 对齐时有逐列对账面。
- **阶梯价 MVP 不做**（Lago graduated/volume 之辨是独立裁决面），报价单行价只有单一标准档；`market_price_reference.dimension` 预留（940 已按 dimension 分行）。

## §6 实施规划（任务卡 · 每卡带验收门）
