## §0 结论一句话

上一轮（第 33 增量）的拦截审核队列 / 放行表 / 硬阻断清单全部是**进程内**的，
本轮把它们落库（迁移 917 三表，重启可回溯、放行跨重启存活）；审批语义按用户
口径改为**规则级 7 天放行**；拦截记录补**客户端类型**与**匹配说明**（内置规则
说明表）；硬阻断开关页支持**单条开关**与**一键全开/全关**（写穿透 DB，重启后
管理面清单仍生效）。已部署 211 并完成部署后验证。

## §2 持久化的三个语义决定（记录在案）

1. **「同一客户端」按租户解释**。放行键 = 租户 + 规则（r1039 的放行表本来就是
   租户边界）；client_type 记录在审核单与放行行上供展示/追溯，但不参与放行键
   ——按 client_type 收窄需要穿透整条检测热路径（egressReleaseAllowed 只有
   租户上下文），扩大失败面。ZCode 这类客户端以 API key（租户）接入，语义等价。
2. **审批放行不带载荷摘要**。用户口径是「同样的规则放行一周」，不是「同一次
   载荷放行」；摘要绑定的精确放行仍是管理面手动授予的选项（POST
   egress-releases 带 payload_digest）。
3. **多实例部署的清单同步在启动时**。管理面保存写 DB + 本进程；其它实例在
   重启时装载。211 是单实例部署；多实例热同步留 TODO（Redis 通知通道已有，
   接入点明确）。

## §6b 部署后自愈记录（当轮抓到并修复）

1. **迁移执行通道异常（根因已解）**：部署日志与台账（gateway_db_revision_sequences）都记录
   917 已应用（content_sha=execution_sha=feea9cd2…），但 acc-pg17/llm_gateway 里
   三表缺失，全机所有库都无此表 ⇒ 台账说谎。手动按同一文件重放（幂等）一次
   成功（7 条语句全过），证明 DDL 本身无问题。**根因**（本审计轮查实）：
   序列脚本容器通道的 `docker exec` 缺 `-i` ⇒ psql 从 stdin 读到立即 EOF ⇒
   **一条语句都不执行却 exit 0** ⇒ 台账 INSERT 照写（912/913、917、919/920
   五条迁移失踪同一根；与 §535「台账停在旧号而列却在」互为镜像）。24h 审计
   第 5 轮已在 09:58 修复该脚本（我 08:34 的部署踩在修复之前）。**防线已由
   24h 审计第 6 轮通用化**：apply-db-revision-sequence.sh 的 ledger_artifact_probe
   逐迁移（900~920）产物探针，917 的探针正是三表 to_regclass 全 NOT NULL——
   本审计轮核实该条目已覆盖，不再在部署引擎另立平行门（同一件事一份机制）。
2. **种子行语义缺陷（本轮自伤，当轮止血+根治）**：迁移种下的默认行
   （rules='[]'、updated_by=''）被 LoadHardBlockState 当成「管理员显式保存的空
   清单」⇒ 211 首次启动把硬阻断清单覆盖成空（含请求侧 fail-closed 一并失效，
   启动日志 allows=[] 实证）。止血：SQL 直写 `["input:*"]` + updated_by='ops-
   recovery-917'，重启后 `allows=[input:*]` 恢复出厂默认；根治：装载判据改

   判据钉三种形态（种子行/显式空清单/管理过清单）。

## §8 批判性审计（2026-10-29 审计轮，用户指令「审计→修正→提交推送」）

对上一轮全部改动复核，抓到 **2 个真缺陷 + 1 个弱判据**，全部当轮修复：

1. **no-rows 错误映射用错了类型（真缺陷）**：postgres_block_review.go 判
   `pgx.ErrNoRows`，而 Store 走 database/sql（pgx stdlib）实际返回
   `sql.ErrNoRows` ⇒ 判据恒不命中。后果：① 首次登记（无同键 pending）每次
   误报「dedupe 查询失败」WARN；② 按 ID 决定不存在的审核单返回 503 而不是
   404。修：全部改判 `sql.ErrNoRows`（与 postgres.go 的 storeError 同口径），
   新判据钉住「no-rows ⇒ (found=false, err=nil)」「缺单 ⇒ ErrNotFound」。
2. **错误「清洗」没有真的在洗（真缺陷）**：旧 sanitizeDBErr 只按 " - " 截断
   驱动消息——消息里没有该分隔符时**参数原文照传**（被拦载荷可能携带机密）。
   修：退役该函数，全部走 storeError（固定文案，绝不透传驱动文本）；判据从
   「长度 ≤120」改为「秘密词不得出现」（旧断言恒绿——长度合格 ≠ 没泄密）。
   顺带修出 storeError 无 nil 守卫的引入点（upsert/save 成功被当失败）。
3. **部署后核对象（并入上游机制，不另立门）**：审计第 6 轮同期把
   ledger_artifact_probe 通用化为 900~920 逐迁移探针，917 三表已在其列；
   本轮曾拟在部署引擎另加对象门，核实上游覆盖后**撤回**（同一件事一份
   机制，避免两个真值源漂移）。
4. **复核确认无问题的项**：规则级 7 天放行的键（EgressReleaseAllowed 空摘要
   记录 = 同键全放行）；审批放行与硬阻断清单的判定顺序（清单先行、放行其次，
   不放行未开闸的规则）；登记三级降级线；租户隔离（列表/放行/审核均按租户）；
   211 当前生效清单 = ["input:*]（种子行修复后装载日志实证）。
