## §3 修法：三组都走投递迁移

### §3.1 取号

startup 序列的三位数已用满 ⇒ 沿 983b／983c／999a 的**字母后缀**先例取 999b／999c／999d。

★ 字母后缀件的**文件名解析不出纯三位数字前缀** ⇒ 对【投递路径契约门】与【installer 强制 embed 门】两道门都隐形 ⇒ ⇒ 必须进 `sql/schema/startup_migration_nonplain.tsv` 登记册（★ 999a 那次漏登记 ⇒ 静默漏登记；本轮一开始就登记了）。

### §3.2 999b — `system_probe_runs.total_tokens`

- 内容：补 `total_tokens` 列（`ADD COLUMN IF NOT EXISTS`）＋ 锁守卫 ＋ 成对 down 件。
- 同批恢复 `admin/systemmonitor_handlers.go` 的读侧聚合（`SUM(total_tokens)`）⇒ `total_tokens_1h` 不再硬编码 0。
- ★ **口径边界不变**：探针**运行**口径的 token，不是请求口径（`usage_ledger`／`session_turns` 的事）。

### §3.3 999c — `tool_usage_stats` 族的 134 形状列

两张表各加 13 列：

```
tool_name / date / total_calls / success_calls / failed_calls / timeout_calls
avg_duration_ms / p50_duration_ms / p95_duration_ms / p99_duration_ms
unique_users / unique_sessions / top_users
```

外加：`tool_id`／`tenant_id`／`usage_date` 去 NOT NULL ＋ hot 表 `UNIQUE (tool_name, date)` ＋ 旧行按 `usage_date` 回填 `date`。

★ **三处关键设计（只在真库验过之后才敢这么写）**：

1. **唯一约束只建在 hot 表**
   - 父表 `tool_usage_stats` 是**分区表**（基线 `PARTITION BY RANGE (created_at)`）⇒ PostgreSQL 要求分区表上的唯一约束**必须包含全部分区键** ⇒ 建 `UNIQUE (tool_name, date)` 在父表上会直接报错。
   - 而写侧的 UPSERT 目标是 **`tool_usage_stats_hot`** ⇒ `ON CONFLICT (tool_name, date)` 需要落在哪张表，约束就得建在哪张表 ⇒ hot 表由 348 建为**独立表**（非分区表）⇒ 约束可建。
   - 读侧（父表 ∪ hot 的 `UNION ALL`）不依赖任何唯一约束 ⇒ 父表不加约束不影响读。

2. **三个 NOT NULL 都要去（含 `usage_date`）**
   - 代码的 INSERT 给的是 `date`（134 形状），**不给 `usage_date`** ⇒ 不去就会因 NOT NULL 违反而失败。
   - 去 NOT NULL **不删数据**，只是允许「按 tool_name 口径写入的行」没有旧口径的键。

3. **两套键并存（如实说明，不掩饰）**
   - 库里此后同时存在：`tool_id` 形状（335/348 定的旧口径）＋ `tool_name` 形状（本迁移补的 134 口径）。
   - 本迁移**不删旧列、不动旧数据** ⇒ 旧口径历史数据仍在、既有读面不受影响；新口径由 `domains/toolexecution` 的 UPSERT 独占写入。
   - ★ `tool_name` 的取值来源是**同一仓内**的执行明细表 `session_tools.tool_name`（706 建、在通道里）⇒ 两套键指向同一批工具，可对账。

### §3.4 999d — `licenses`／`releases` 的 `tenant_id`

两列 ＋ 两个索引（`idx_licenses_tenant_created`：`tenant_id, created_at DESC`；`idx_releases_tenant_published`：`tenant_id, published_at, build_seq DESC`）。★ **不改读面的租户隔离语义**（owner 决定）。

### §4.4 ★ 真库抓到的三个坑（★ 第三个只有真库能抓）

**坑① `cannot add column to a partition`**

```
ERROR:  cannot add column to a partition
CONTEXT:  SQL statement "ALTER TABLE tool_usage_stats_2026_07 ADD COLUMN ..."
```

★ PostgreSQL **不允许**直接对分区子表 `ALTER TABLE … ADD COLUMN`；★ 而**父表加列本来就会自动传播到全部分区子表** ⇒ ⇒ 我那段「用 DO 块遍历 `pg_inherits` 给每个子表补列」是**多余且有害**的 ⇒ 删掉。

★ 静态核对抓不到这个（它读起来完全合理）；★ 只有真库能抓。★ 保留那段注释（写明「为什么这里曾经有一段遍历 `pg_inherits` 的 DO 块，而它被删了」），免得有人按「父表加列不传播」的旧认知再写回来。

**坑② `usage_date` 漏去 NOT NULL**

★ 写侧的 INSERT 给的是 `date`（134 形状），不给 `usage_date` ⇒ 只去掉 `tool_id`／`tenant_id` 仍会失败 ⇒ 第三列也要去。

**坑③ 读侧扫 NULL 进 string 会报错**

★ 补列后，父表里**旧口径的行 `tool_name` 是 NULL**（新列，老行没值）⇒ 读侧 list 查询（hot ∪ 父表 `UNION ALL`）会把这些行带出来 ⇒ 而 Go 侧 `ToolName` 是 `string`（不是 `sql.NullString`）⇒ `database/sql` 扫 NULL 进 `*string` 会**直接报错**：`converting NULL to string is unsupported` ⇒ ⇒ **只要父表里有一行旧数据，`ListStats` 就整个失败**。

修法：读侧 list 查询的父表腿加 `p.tool_name IS NOT NULL`（★ `GetStats` 那条不用改：它按 `tool_name` 精确查，`NULL = $1` 不成立 ⇒ 天然只命中新口径行）。

★ 真库验证：造一行旧口径数据后对比 ⇒ 修好的查询只返回 `tool_name` 非空的行；未修的对照会把 NULL 行带出来。

   - 解法：★ 该脚本自带降级路径（`check_toolchain`：找不到 `PSQL_CMD` 的首词 ⇒ 打印一句人话并 `exit 3` ⇒ ★ `exit 3` 是契约里的「量具不可用」而不是崩溃）⇒ ⇒ **跑门时把 docker 从 PATH 里排除**（0.07s 通过）。
   - 同理，本机 `~/.local/bin/psql` 是个 shell shim（转发到容器），★ 它的 `connect_timeout` 不生效 ⇒ `TestV1FamilyRetirementProbeDoesNotEchoPassword`（★ 故意用不可达端口 1 做负控）会一直等 ⇒ 该门按设计在「PATH 里没有 psql」时 `t.Skip`（★ 门里写明了这条分支）⇒ 干净 PATH 下 0.00s 跳过。
   - ⇒ ★ 这两条门本轮**没有真正跑过**（是环境限制、不是产品缺陷）。
3. ★ **三台现役版本本轮未动、未复核**（★ 本轮零部署）。
4. ★ 机器负载：中段曾到 296（★ 别的会话起的 Android 模拟器占 342% CPU）⇒ 早期的超时红有机器因素；清理残留进程后负载降到 17。

## §10 本轮通用式（三条，★ 可复用的教训）

1. ★ **「只加列」的迁移要连带问一句：★ 写侧真的提供那些列吗？**
   —— 组 B 的教训 ＝ 写侧不提供的 NOT NULL 列会让 INSERT **仍然失败** ⇒ ⇒ 加列前先对拍写侧的列清单（★ 不只是读侧）。

2. ★ **「分区表」上有三种操作要分别对待：**
   —— 加列：父表自动传播到所有子表；删列：父表自动传播；★ **直接 `ALTER` 分区子表一律非法**（`cannot add column to a partition`）⇒ ⇒ 不要写遍历 `pg_inherits` 的 DO 块。

3. ★ **真库验证要跑完整生命周期**（up／幂等重放／down／再 up），而不是只跑一次 up —— ★ 幂等重放会暴露「唯一约束已存在」这类**只在第二次犯**的错。
