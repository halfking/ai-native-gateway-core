## §2 dashboard 聚合漏时间窗（真缺陷，已修）

### 2.1 定位

`admin/dashboardapi/session_health.go` 的 `/api/admin/dashboard/session-health` 由三段查询拼成：

| 段 | 函数 | 改前的时间窗 |
|----|------|--------------|
| 健康度分布 | `queryDistribution` | **无** ⇒ 全表聚合 |
| 健康度趋势 | `queryHealthTrend` | `first_request_at >= NOW() - INTERVAL '%d days'` |
| Top Issues | `queryTopIssues` | **无** ⇒ 全表聚合 + `GROUP BY issue` |

⇒ ★★ **同一个响应里「分布 = 全量」「趋势 = 近 N 天」** ⇒ 这不是「两种口径各有道理」，
是**同一端点内的口径不一致**（缺陷，不是设计）。

### 2.2 生产实测（154 所连的库 = 252 共享库，同一条聚合语句，四种形状）

| 形状 | 耗时 | 计划形态 |
|------|------|----------|
| M1 无窗口（复现 500/15s） | **1,451 ms** | `Parallel Seq Scan`（83 万行，无 Filter） |
| M2 + `first_request_at` 窗口 | **660 ms** | `Parallel Seq Scan` + `Filter: (first_request_at >= (now() - '7 days'::interval))`，`Rows Removed by Filter: 238,466` |
| M3 + `last_request_at` 窗口 | 330 / 465 / 3,074 ms（多次重测） | ★ `Index Scan using idx_session_summaries_tenant_time`，`Index Cond: (last_request_at >= (now() - '7 days'::interval))` |
| M4 带 `tenant_id` 无窗口 | ~1.4 s | `Seq Scan` + `Filter: (tenant_id = 'default')`，`Rows Removed by Filter: 292`（**99.96% 的行都是 default 租户** ⇒ tenant 等值不收窄） |

⇒ ★ **绝对耗时不稳**（同形状 330 / 465 / 3,074 ms）⇒ **只承诺计划形态，不承诺毫秒数**
（沿用 873 迁移文件头的原话）。

### 2.3 修法

`queryDistribution` 与 `queryTopIssues` 各补一行与 `queryHealthTrend` **逐字同款**的窗口谓词：

```sql
first_request_at >= NOW() - INTERVAL '%d days'   -- N = params.Days（默认 7）
```

⚠ **只补窗口，不补** trend 那条 `health_score IS NOT NULL`：distribution 的 `total` 口径
包含「没有 health_score 的会话」，加了那条会把 `total` 改窄 ⇒ 那是**另一个口径变更**，
不在本次修复范围内。

⚠ **保留 `first_request_at` 而不是改成 `last_request_at`** 的理由**不是性能，是口径一致性**：
`queryHealthTrend` 用的就是 `first_request_at` ⇒ 若 distribution 改用 `last_request_at`，
**同一个响应里两个数字又变成两种口径**（本次修的正是这个不一致）⇒
要换就得**三条查询一起换**（语义变更：近 N 天「活跃」vs 近 N 天「新建」）⇒ 属主拍板。

### 2.4 口径等价实测（支持「两列几乎等价」这一事实）

```
by_first_7d | by_last_7d | new_but_idle_7d | total
------------+------------+-----------------+--------
     115870 |      115874 |               0 |  831352
```

⇒ 两口径在这张表上**几乎完全一致**（差 4 行，且「先创建后空闲 7 天」的会话 = 0）。

## §3 ★ 机制订正一：**PG 17.10 允许「非首列」当 index qual**

### 3.1 现象

生产 M3 的计划把 `Index Cond: (last_request_at >= …)` 放在
`idx_session_summaries_tenant_time (tenant_id, last_request_at DESC)` 上 ——
**条件落在一个 btree 索引的第二列，而首列 `tenant_id` 上没有任何等值约束**。
按「首列必须先有等值约束，后续列才能当 index qual」的旧先验，这在 PG 17 上不可能。

### 3.2 三次假设，逐个被实测推翻

| # | 假设 | 判决 | 证据 |
|---|------|------|------|
| H1 | **RLS 注入的租户等值**提供了首列约束（`session_tenant_binding` 那个想法的同源版本） | ✘ **证伪** | `session_summaries` 的 `relrowsecurity=t` 但 `relforcerowsecurity=f`，而 `current_user = llm_gateway` **就是表 owner** ⇒ owner 绕过 RLS；`count(*)` 在开关 RLS 前后都是 831,386；**且把 RLS 关掉后计划一字不变** |
| H2 | 克隆表没复现 ⇒ 生产与克隆的 PG 版本不同（skip scan 是 PG 18 特性） | ✘ **证伪** | 生产与本地容器**同为 PG 17.10**；生产上 `pg_settings` 里**没有** `enable_indexskipping`（PG 18 才有的 GUC） |
| H3 | 「非首列 ⇒ 一定用不上索引」 | ✘ **证伪** | 本地最小复现：`CREATE INDEX (tenant_id, last_request_at DESC)` + `WHERE last_request_at >= …` ⇒ 默认走 `Seq Scan`，但 `SET enable_seqscan = off` ⇒ **`Index Only Scan` + `Index Cond: (last_request_at >= …)`**（`Heap Fetches: 0`）⇒ **PG 17.10 就是支持**；生产同样强制索引复现（`Index Cond` 不变） |

⇒ ★★ **结论：PG 17.10 支持把非首列作为 index qual**（我的先验是错的）。
⇒ ⇒ **「非首列 ⇒ 用不上索引」这条推理链在仓内还有两处受害者**，见 §3.4。

### 3.3 影响

1. ★★ **「需要给 `session_summaries` 建窗口列索引 ⇒ 要向属主申请 DDL 窗口」这条建议作废** ——
   `idx_session_summaries_tenant_time` **已经在库里** ⇒ 改用 `last_request_at` 是**零 DDL**。
2. ⇒ 上一轮列在「待属主裁决」里的 **「需共享生产库 DDL 窗口」** 这一项，**可以撤销**。

### 3.4 被这条订正推翻的既有结论（**不改历史文件**）

`sql/migrations/startup/855_session_analytics_time_window.sql` 的文件头写着：

> 没有任何以 `last_request_at` 打头的可用索引（`idx_..._tenant_time` 的**前导列是 tenant_id**，
> partial 索引的前导列是 archived_at），所以 30 天窗的 WHERE **只能走全表顺序扫**

⇒ ★ 这条前提**被今天的实测推翻**（该索引确实能当 index qual）。
⇒ ★★ **但 855 这个迁移本身仍然成立、仍然必须保留**（它解决的是**输出组数**
`104,299 → 1,832`，砍的是写放大，与计划形态无关）。
⇒ ★ **历史迁移文件不可改**（`docs/db-changelog.md` 是唯一 sha256 登记表）⇒
⇒ **订正只写在本文档与 `LESSONS.md`**，不动 855 的字节。

## §4 ★ 机制订正二：克隆实验为何没复现（**成本模型 + 索引集**，不是机制）

克隆表（831,339 行合成数据，分布照生产只读采样）上，`last_request_at` 窗口**没有**转成
Index Scan。逐项排查后，差异**不是**语义差异：

1. ★ **克隆表的索引集 ≠ 生产**：生产有 **22 条**索引（含被 M3 选中的
   `(tenant_id, last_request_at DESC)`），克隆表只补了
   `(last_request_at DESC, session_key DESC) WHERE last_request_at IS NOT NULL`。
2. ★ **成本模型随表体量变化**：克隆表 seq scan 只要 ~95ms（便宜）⇒ planner 直接选它；
   同一形状在生产（表大 3 个数量级）才会选索引。最小复现也印证了这点：
   小表默认 `Seq Scan`（cost 12,781），`enable_seqscan=off` 才露出 Index Cond。

⇒ ★★★ **通用式（写进 LESSONS）**：
**「生产规模克隆表」只能证否（某方案一定不行），不能证成（某方案一定行）** ——
计划形态是**表体量 × 索引集 × 统计信息 × 参数**的联合产物；
克隆表缺索引集 ⇒ 连「形态能不能变出来」都验证不了。
⇒ ⇒ **生产形态只能到生产上量**（只读 EXPLAIN）。

### 6.2 EXPLAIN：主因是 **JOIN**，不是窗口列

生产只读 EXPLAIN（`statement_timeout=180s`）：

| 形状 | 耗时 | Buffers | 计划要点 |
|------|------|---------|----------|
| 现状（`first_request_at` 窗口） | **35,119 ms** | 74,098 | `Parallel Hash Right Join`（`session_dim` 290,994×3 行，hash 表 34 MB）+ `Parallel Seq Scan on session_summaries` + `Filter` |
| 换 `last_request_at` 窗口 | （截断） | **311,658** | ⇒ **更贵**：索引 seek + 回堆 ⇒ buffers 涨 4.2 倍 |

⇒ ★★★ **⇒ 「把窗口列换成 `last_request_at`」解决不了 MV 刷新的主因**（而且更贵）。
⇒ ⇒ ★ **正解方向**是 JOIN 形态（`session_dim` 有 `gw_session_id` 唯一索引，873k 行 / 377 MB），
或把 `task_id/client_id` 落到 `session_summaries` 上 ⇒ **需要属主定方向 + 生产 DDL**。
