## §0 结论（一句话）

**拦截本身是合理的（规则面已是「最少干扰」姿态），不合理的是「拦截说不清自己」**：24 条真实拦截的审核单
`rule_id / reason / 证据` **全空**，且**读时归因**（本该补齐历史空白单的那套机制）**被一个全局
`LIMIT 50` 打败** ⇒ 审核员面对的是 24 张「不知道因为什么被拦」的清单 ⇒ 规则优化没有输入 ⇒
**精准度无法提升**。本轮把这两处补上：守卫侧失败**逐条自带规则名/原因/证据**，读时归因改为
**逐单窗口 + 逐单预算**。

## §3 根因链与修法

### F1 守卫侧失败**逐条自带归因**（`domains/hooks/outputcompliance/`）

守卫侧的 fail-closed 分支此前返回**裸 error** ⇒ `blockedChunkResult` 拿不到规则 ID ⇒
审核单 `rule_id/reason` 全空：

| 形态 | 原返回 | 修后规则 ID |
|---|---|---|
| 检查器报错 / 返回空结果 | `fmt.Errorf("check stream lane %q: %w")` | `builtin.guard.check_failed` |
| 工具参数 lane 不许安全改写（已签名/敏感） | `errors.New("cannot safely rewrite signed or sensitive tool stream lane")` | `builtin.guard.rewrite_refused` |
| 脱敏结果不是合法 JSON | `errors.New("redacted tool arguments are invalid JSON")` | `builtin.guard.redact_invalid` |
| 请求态缺失（无法跨帧检查） | 挂 `capacity_exceeded`（**假归因**） | `builtin.guard.no_request_state` |
| 帧改写后无法重新编码（3 处） | 挂 `capacity_exceeded`（**假归因**） | `builtin.guard.frame_encode_failed` |
| 非流式：body 变换失败 | 无元数据的 `ShouldBlock` | `builtin.guard.check_failed` |

★ 三条 fail-closed 错误现在返回 `*errorsx.PolicyBlockError`（带 `RuleID/Reason/Path/Evidence`）⇒
流式 chunk 路径（`blockedChunkResult` ⇒ metadata）与 flush 路径（错误上送）**两条路都能拿到归因**。

### F2 守卫规则的内建展示说明（`domains/sanitizerules/builtin_rules_meta.go`）

★审核单的「规则语义」行取自内建说明表 ⇒ ★★ 守卫规则**不在表里** ⇒ ★★ 审核面退化成一句
「（托管规则，表达式与适用范围见规则配置）」⇒ ★★ 那是**指向错误事实源**的提示（这些根本不是
托管规则）★★ ⇒ ★★ 审核员会去托管规则里找一条永远找不到的规则 ★★。
⇒ 本轮把 6 条守卫规则逐条登记（名称 +语义 + **处置方向**：容量/形态/上游可用性，**不是改规则表达式**）。

### F3 证据传播（`domains/streaming/`）

- **flush 路径丢证据**：lane 级拦截的错误**自带 Evidence**，但写者只取 rule/reason/field/digest
  ⇒ 证据被丢 ⇒ 审核面看不到「当时拦的是哪段内容」。⇒ 补 `w.blockEvidence = policyBlockEvidenceFromError(err)`。
- **非流式四个登记点无证据**：`messages.go` ×2、`responses.go` ×2 只登记 rule/reason/field/digest
  ⇒ 补 `policyBlockEvidenceFromError` / `policyBlockEvidenceFromMetadata`。

### F4 读时归因**逐单窗口**（`admin/sanitize_rules_review_context.go` + `domains/sanitizerules/`）

★ 旧读法把**整批**审核单并成一个时间窗，再按 `ORDER BY last_seen DESC LIMIT 50` 取**最近**的 50 条：

- 211 实测：该批 **24 条待审单横跨 40 小时**（10-29 08:45 → 10-31 01:03），
  时间跨度内 egress 事件 **56 行** ⇒ ★★ 50 条预算被**最新**的事件吃光 ⇒ ★★ 早期的审核单
  一条候选都没有，且「撞上限」被记成**整批**截断 ⇒ ★★ 归因档位一律降级成
  「unknown（请人工判断）」★★ ⇒ ★★ **读时归因对真正需要它的那批历史空白单等于没生效** ★★。
- 修法：**每个审核单一个窗口**，一次往返（`unnest + LATERAL`），**逐单预算**（截断只影响那一条）。
- 真库实测（§5）：修后 10-29 那批 24 条中 **17 条**得「守卫侧拦截」档、**7 条**得「候选规则」档
  （不再一律 unknown）；候选集与手工逐单 SQL 逐条一致。

### F5 两处「读数与事实相反」的小修

- **放行表不写 `builtin.guard.*`**：`grantReviewRelease` 此前会给合成守卫规则写一条 egress 放行行
  ⇒ 那是一条**永远匹配不上的死行**（放行读面只按内容规则匹配）⇒ 与 `maybeAutoRelax` 的同一口径跳过。
- **启动日志 `output_compliance_enabled` 恒 false**：`goal_control.go` 用 `len(interceptors) > 3` 判定，
  而该切片最多 3 个（goal + audit + oc；SmartSaniGuard 的两个是之后装到链上的）⇒ ★★ 恒假 ⇒ ★★
  与同一份启动日志里的 `output compliance guard configured pending_max_bytes=1048576` **互相矛盾**，
  且矛盾的那一条更显眼 ⇒ 运维据此读成「输出合规没开」⇒ 按「装上即真」修。

## §6 211 上的数据修正（一条，可逆）

★ `rv-22` 的 `label='false_positive'` 是 **921 终验时的功能验证标注**（§1 ③）⇒
★ 读数里「误报率」的分母是**有判断的记录数**（`false_positive / labeled`）⇒ ★★ 留着它，
`unattributed` 桶会被读成 **24 条里 1 条误报 = 100% 误报率** ⇒ ★★ 极可能把运营引向
「这些拦截都是误报 ⇒ 去放宽规则」——**而那正好会伤到精准度** ★★。

```sql
-- 执行于 211（acc-pg17 / llm_gateway），窄谓词 + 幂等
UPDATE sanitize_block_reviews
SET label = '',
    label_comment = '921 终验（2026-10-29 20:49）的**功能验证**标注，非人工判读结论；2026-10-31 拦截归因轮清除 label：误报率读数的分母是「有判断的记录数」，留着它会让 unattributed 桶读成 100% 误报（会误导运营去放宽规则）。原值 false_positive，原注记「拦截点无归因（guard 越界），标误报」保留在本注记里。'
WHERE id = 22 AND label = 'false_positive' AND label_comment LIKE '921 终验%' AND degraded = false;
-- ⇒ UPDATE 1
```

**改前/改后读数**（与生产读面同一条 SQL）：

| | total | labeled | false_positive |
|---|---|---|---|
| 改前 | 24 | **1** | **1**（⇒ 桶内误报率 100%） |
| 改后 | 24 | **0** | **0**（⇒ 不再有「100% 误报」的失真读数） |

★ `labeled_by` / `labeled_at` **保留**（事实留痕），只清 `label`（判读维度）。
★ **可逆**：把 `label` 置回 `'false_positive'` 即恢复原状态（原注记保留在本注记里）。
