# F3 智谱 trial 配额归因验证手册

## 一、问题背景

审计档 `2026-11-13-211错误盘点-转换格式族三修复.md` §二 F3 报告：
- ✅ executor 归因 `[quota_permanent]`（修复前 `request_rejected`）
- ⚠️ 遗留：「LastKind→客户端响应面仍走 transient 兜底」

本手册提供完整的生产数据验证步骤，用于确认 DB 中的 `error_kind` 是否正确。

## 三、手动验证步骤（SSH 不可用时）

### 3.1 连接 211 数据库

```bash
# 方式 1: 通过 SSH
ssh 211  # 或 ssh 211-mesh
docker exec -it acc-pg17 psql -U postgres -d llm_gateway

# 方式 2: 如果在 211 机器上
docker exec -it acc-pg17 psql -U postgres -d llm_gateway
```

### 3.2 执行验证 SQL

将 `scripts/verify-f3-quota-attribution.sql` 中的 SQL 复制粘贴执行，或：

```sql
-- 核心验证查询
SELECT 
    CASE 
        WHEN event_at < '2026-11-13 12:50:00+08' THEN 'before_deploy'
        ELSE 'after_deploy'
    END AS deployment_phase,
    error_kind,
    COUNT(*) AS cnt,
    MIN(event_at AT TIME ZONE 'Asia/Shanghai') AS earliest,
    MAX(event_at AT TIME ZONE 'Asia/Shanghai') AS latest
FROM _request_logs
WHERE client_model = 'glm-5.3-flash-trial'
  AND error_message LIKE '%no active%quota%'
  AND event_at BETWEEN '2026-11-13 10:00:00+08' AND '2026-11-13 14:00:00+08'
GROUP BY 1, 2
ORDER BY 1, 2;
```

### 3.3 辅助验证查询

```sql
-- 查看最近 24 小时的分布（确认没有新的误归因）
SELECT 
    error_kind,
    COUNT(*) AS cnt
FROM _request_logs
WHERE client_model = 'glm-5.3-flash-trial'
  AND error_message LIKE '%no active%quota%'
  AND event_at > NOW() - INTERVAL '24 hours'
GROUP BY 1
ORDER BY 2 DESC;

-- 采样查看具体记录
SELECT 
    event_at AT TIME ZONE 'Asia/Shanghai' AS event_time,
    request_id,
    error_kind,
    upstream_status_code,
    client_status_code,
    error_message
FROM _request_logs
WHERE client_model = 'glm-5.3-flash-trial'
  AND error_message LIKE '%no active%quota%'
  AND event_at > NOW() - INTERVAL '3 hours'
ORDER BY event_at DESC
LIMIT 5;
```

### 5.1 访问请求日志页面

2. 导航到「监控」→「请求日志」
3. 过滤条件：
   - 模型：`glm-5.3-flash-trial`
   - 时间范围：2026-11-13 10:00 ~ 14:00
   - 状态：失败
4. 检查 `error_kind` 列

### 5.2 预期结果

- 12:50 之前的记录：`error_kind` 显示为 `request_rejected` 或 `transient`
- 12:50 之后的记录：`error_kind` 显示为 `upstream_quota_permanent`

## 六、结果判定

### 6.1 验证通过条件（全部满足）

✅ **条件 1**：部署前（< 12:50）的记录 `error_kind` 为 `request_rejected` 或 `transient`  
✅ **条件 2**：部署后（≥ 12:50）的记录 `error_kind` 为 `upstream_quota_permanent`  
✅ **条件 3**：最近 24 小时无新的 `transient` 误归因  
✅ **条件 4**：采样记录的 `upstream_status_code = 400`  
✅ **条件 5**：采样记录的 `client_status_code = 502` 或 `429`（quota_held）

### 6.2 验证失败情况及处理

❌ **情况 1**：部署后仍有 `transient` / `request_rejected`  
→ 检查部署是否成功：`curl https://llm.itestu.cn/version` 应返回含 `e2242e078` 或更新的 commit  
→ 检查是否是旧请求被延迟写入

❌ **情况 2**：所有记录都是 `upstream_quota_permanent`（包括部署前）  
→ 可能的原因：查询时间窗口不准确，或数据被迁移/清理

❌ **情况 3**：数据库中完全没有匹配记录  
→ 检查查询条件：`client_model` / `error_message` 是否正确  
→ 扩大时间窗口重试

### 7.3 找不到匹配记录

```sql
-- 检查是否有该模型的任何请求
SELECT COUNT(*), MIN(event_at), MAX(event_at)
FROM _request_logs
WHERE client_model = 'glm-5.3-flash-trial'
  AND event_at > '2026-11-13 00:00:00+08';

-- 检查错误消息的准确文本
SELECT DISTINCT error_message
FROM _request_logs
WHERE client_model = 'glm-5.3-flash-trial'
  AND success = false
  AND event_at > '2026-11-13 10:00:00+08'
LIMIT 5;
```
