## 3. 写放大测量（一次性 PG 17.11 @ 211）

### 3.1 仪器与夹具保真度

- 服务器参数按生产对齐：`shared_buffers=2GB`、`work_mem=64MB`、
  `gin_pending_list_limit=4MB`、`max_wal_size=4GB`、`checkpoint_timeout=900s`、
  `random_page_cost=1.1`。
- 夹具 200,000 行，**长度分布逐桶抄录生产经验分布**（不用拟合——拟合出来的均值差 9%
  就足以让 trigram 条数差 9%）。
- ★ **夹具保真度当场自检**：合成数据的 `show_trgm` distinct 平均 **85.10**，
  生产实测 **84.59**，偏差 **+0.6%**。超 ±12% 即报错。
  （第一版夹具用逆 CDF 拟合，均值偏 9% ⇒ trigram 偏 9% ⇒ 自检当场报红。）

### 3.2 结果（`perTx=1` = `session_turns_hot` 活写的真实形状：每行一个事务）

| 臂 | 语句 µs/row | 扣客户端往返 | **Δ(扣往返)** | 索引体积 | WAL B/row | planner | 选择性查询耗时 |
|---|---|---|---|---|---|---|---|
| A 无索引（基线） | 28.72 | 13.34 | — | 5.3 MB | 290 | 顺序扫 | **64.19 ms** |
| **B GIN trgm 全列（= 877）** | 125.13 | 109.75 | **+96.4** | 65.8 MB | **14,844 ~ 45,832** | **Bitmap Index Scan** | **0.77 ms** |
| C GIN `left(search_text,150)` | 129.83 | 114.45 | +101.1 | 65.8 MB | 19,455 | 顺序扫 | 64.62 ms |
| D GIN `WHERE length(...) <= 150` | 131.63 | 116.25 | +102.9 | 65.8 MB | 19,449 | 顺序扫 | 63.42 ms |
| E btree `(tenant_id, ts DESC)` | 31.86 | 16.48 | **+3.1** | 16.4 MB | 458 | Bitmap Index Scan | **13.26 ms** |

客户端往返 15.4µs/次（校准值：同一连接上量 `SELECT 1` 的空往返）。
needle 命中率 **400/200,000 = 0.2%**（先量命中率，再看计划——纪律）。

### 3.3 交叉校验（第二套完全不同的方法）

Go 基准是「客户端逐条 INSERT + 客户端墙钟」；交叉校验是「**服务器端** PL/pgSQL
循环 + `clock_timestamp()`，**零往返**；WAL 用服务端 LSN 差」。

| 方法 | GIN 臂 µs/row | GIN 臂 WAL B/row | 基线 µs/row | 基线 WAL B/row | **Δ** |
|---|---|---|---|---|---|
| Go 基准（共享库，交错测） | 109.75 | 14,844 | 13.34 | 290 | +96.4 µs / +14,554 B |
| Go 基准（顺序独占 + CHECKPOINT） | 109.75 | 45,832 | 13.34 | 290 | — |
| **隔离交叉校验（独立静库、243,489 行表、20,000 次单行事务）** | **46.83** | **3,727** | 8.5 | ~200 | **+38.3 µs / +3,527 B** |

★ **2026-10-20 复跑复核**（在同一个 `wa-pg17` 容器上连跑三遍，脚本已修成幂等）：

| 轮次 | plain µs/row | GIN µs/row | Δ µs/row | plain WAL B/row | GIN WAL B/row | Δ B/row |
|---|---|---|---|---|---|---|
| 第 1 遍 | 8.569 | 48.530 | **+39.96** | 138 | 3,892 | **+3,754** |
| 第 3 遍（在因子脚本跑过之后） | 8.464 | 51.877 | **+43.41** | 184 | 4,276 | **+4,092** |

⇒ 与文档里记的 **+38.3 µs / +3,527 B** 一致（波动来自检查点 FPI），
**结论可复现**。⚠ 复跑时发现**脚本原本跑第二遍就会炸**（见 §7），已修。

★ **两套方法不一致，这不是噪声，是有原因的**：
GIN 索引页被持续改写 ⇒ **每次检查点之后，每个被改页要写一次 8KB 全页镜像（FPI）**。
FPI 是"每页每检查点"的一次性成本，摊到多少行上取决于**测量窗口长度**：
共享库里 242 秒的窗口跨了 4 次检查点，WAL 被算到 14.8~45.8 KB/行；
独立静库 20 秒的窗口只有 1 次检查点，落到 3.7 KB/行。

⇒ **报告口径：GIN 的 WAL 成本区间是 3.5 ~ 15 KB/行**，下界取隔离测，
上界取共享库测。生产 `checkpoint_timeout=900s` ⇒ 实际落在**区间偏上**。

### 3.4 ★ 基准与生产对照（代表性的独立验证）

| | 基准预测 | 生产实测 |
|---|---|---|
| GIN 索引体积 | 318 ~ 365 B/行 | `session_turns_2026_10_search_text_idx` 75 MB / 227,088 行 = **346 B/行** ✓ |
| hot 侧 GIN 索引体积 | — | 5,440 kB / 7,078 行 = 790 B/行（含已轮转但未清理的死条目） |

⇒ 基准的**绝对量**在生产上对得上（偏差 < 10%）。

### 3.5 ★ 方案 (b) 的否证：在生产宽度下它**就是**方案 (a)

| 判据 | 实测 |
|---|---|
| 部分索引 `length(search_text) <= 150` 覆盖的生产行 | **199,944 / 200,000 = 99.972%** |
| 表达式索引 `left(search_text,150)` 与原值不同的行 | **56 / 200,000 = 0.028%** |
| 真正截断到 `N=64` 会漏检的行 | **4,000**（语义已改变） |

⇒ 因为生产 `search_text` 最大 148 字符，**任何 N ≥ 148 的表达式/部分索引都与全列索引
逐值相同**；要真的省下写放大就必须 N < 148，而那会**改变搜索语义**
（落在第 N 位之后的 needle 被漏掉）。
⇒ **方案 (b) 从决策表里删掉**：它不是第三个选项，它是 (a) 换个写法。

### 3.6 读侧收益（如果 `?q=` 真的有人用）

有选择性 needle（命中率 0.2%）：

| 形态 | 耗时 | 相对顺序扫 |
|---|---|---|
| 无索引（顺序扫） | 64.19 ms | 1× |
| 仅 btree `(tenant_id, ts DESC)` | 13.26 ms | **4.8×** |
| GIN trgm（= 877） | **0.77 ms** | **83×** |

★ **btree 那一档有一个前提**：`admin/logs.go` 只对 `tenant_admin` 加
`rl.tenant_id = $n`；**超管没有租户过滤** ⇒ btree 完全帮不上，退化为全分区顺序扫。
GIN 不依赖租户过滤，这是它相对 btree 的**唯一**结构性优势。

## 5. 建议

### 5.1 不回滚 877（现在）

理由：① 成本已经付掉，回滚是净亏损（删索引 + 将来再上要重付分钟级构建）；
② 它的**读侧能力是 btree 替代不了的**（超管无租户过滤，btree 帮不上）；
③ 它的**绝对量并不贵**：CPU 1.3~3.4 CPU-秒/天可以忽略，WAL 120~525 MB/天
在 `max_wal_size=4GB` / `checkpoint_timeout=900s` 下不会造成容量问题，
代价主要是索引体积（363 MB/月）相对分区（1.3 GB）的增速。

### 5.2 把 `?q=` 从"默认能力"降级为"显式启用"（**这才是本轮真正的动作**）

现状是：一条**零需求**的路径默认对每个管理端用户开放着，永远在付写放大。
改成显式启用（feature flag）后：
- 零需求时，**GIN 索引可以随时删掉**（写放大归零），能力开关一开再重建即可；
- 真有需求时，**按 (a) 重建**（它是唯一能同时服务超管与租户的形态）。

### 5.3 明确一条触发条件（写下来，避免下一个人重新争论）

> **任一 7 天窗口内，生产出现 ≥ 1 次带 `q=` 的 `GET /api/logs`**
> ⇒ 保留 877，不做降级。
>
> **30 天内仍为 0**
> ⇒ 删掉 `idx_session_turns_search_trgm`（父壳 + 各分区子索引）与
> `idx_session_turns_hot_search_trgm`，把 `?q=` 置为显式启用。
>
> 测量口径固定为 `[?&]q=`（token 精确），**不用裸 `q=`**。

**取数方式（唯一口径，别再手写 one-liner）**：


⚠ **窗口必须在轮转覆盖前读取**：154 的 logrotate 是 `daily` + `rotate 52`
⇒ 只有 ≈53 天可回溯，**超期就取不到那段历史**。
⇒ 要长期看趋势，**每次取数把读数落到台账里**（§2.3 的「台账」小节就是台账，
已有 2026-10-20 的两批读数、两个窗口），不要指望"以后再从日志里翻"。

⚠ 三个会让读数**静默变小**的坑（glob 漏轮转、awk 读不了 `.gz`、
`delaycompress` 的未压缩轮转文件）已写进脚本注释与 §2.3；
**脚本在"轮转文件一个都没命中"时会告警**，就是为了不让"0 次"静默通过。

```bash
# 一次性 PG 17（参数按生产对齐）
docker run -d --name wa-pg17 -p 15432:5432 -v /tmp/wapg:/var/run/postgresql \
  -e POSTGRES_PASSWORD=wa -e POSTGRES_DB=wabench postgres:17-alpine \
  -c shared_buffers=2GB -c work_mem=64MB -c maintenance_work_mem=512MB \
  -c gin_pending_list_limit=4MB -c max_wal_size=4GB -c checkpoint_timeout=900s \
  -c random_page_cost=1.1 -c effective_cache_size=6GB -c max_connections=50

# 主基准（在**同一台机**上跑，客户端往返才不是噪声）
TEST_PG_URL='postgres://postgres:wa@/wabench?host=/tmp/wapg' \
  go test -tags=integration ./sql/migrations/startup/ \
    -run TestMigration877WriteAmplification -v -count=1

# 交叉校验 + 因子分解（**必须在 PG 所在机**上执行：psql 在容器内，
# 文件要先拷进容器；两段 SQL 的文件名必须与 psql -f 的路径一致）
scp sql/audit/2026-10-19-877-write-amplification-cross-check.sql 211:/tmp/
scp sql/audit/2026-10-19-877-write-amplification-factors.sql     211:/tmp/
ssh 211 '
  docker cp /tmp/2026-10-19-877-write-amplification-cross-check.sql wa-pg17:/tmp/
  docker cp /tmp/2026-10-19-877-write-amplification-factors.sql     wa-pg17:/tmp/
  docker exec wa-pg17 psql -U postgres -d wabench \
    -f /tmp/2026-10-19-877-write-amplification-cross-check.sql
  docker exec wa-pg17 psql -U postgres -d wabench \
    -f /tmp/2026-10-19-877-write-amplification-factors.sql'
```

★ 基准**必须与 PG 同机**：从 Mac 连过去时单次往返 200µs 以上，
会把"基线 215µs/行"整体变成往返噪声（差 5~15 倍）。

★ **2026-10-20 修掉一个「跑第二遍就炸」的缺陷**（复现时才暴露）：
两个 SQL 脚本的辅助函数**同名**（`xc_time`），而它们的签名不同 ——
交叉校验是 3 参、因子分解是 4 参（`id_off` **带默认值**）。
带默认值的那个**也能接 3 参调用** ⇒ 同一次调用有两个同优候选 ⇒ PG 报

```
ERROR:  function xc_time(regclass, integer, integer) is not unique
HINT:  Could not choose the best candidate function.
```

⇒ 交叉校验脚本在**干净库**上跑第一次没事，**在同一库上跑第二次必炸**。
⇒ 修法：① 交叉校验开头按签名清空本族（`xc_%`）辅助函数；
② 因子分解改用**独立前缀 `xf_`**，两个脚本彻底隔离。
⇒ 现在三个脚本（交叉校验 ×3、因子分解 ×2、交叉校验再跑）在同一容器上**全部 exit=0**，
且互不干扰。**教训**：可复现脚本必须**能重复执行**——「跑一次对」不等于「可复现」。
