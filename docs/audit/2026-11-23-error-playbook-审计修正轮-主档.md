## 三、发现

### F1 ★★★ 全局执行闸漏接首次修正路径（已修）

`AnalyzeUnknown` 的「门控执行一次修正」：

```go
if !mutating || confidence >= confidenceFloor {
    rec, execErr := e.ExecuteEntry(ctx, &probe, ev, TriggerAutoAnalyze)
```

只看「是否变更类」与 0.80 置信度门，不查 `cfg.AutoExecute`。而标准模式（`HandleEvent`）的闸是 `!Enabled || !AutoExecute || !entry.AutoExecute`。也就是说同一道闸在两条自动执行路径上只接了一条。

- 设置项文档：短描述「标准模式允许自动执行」，长描述「**全局执行闸**」，开关族头注「是否让系统『自己动生产状态』是 owner 的决策面」。代码只实现了窄的那个。
- 灰度实况：`auto_execute=false`、`auto_analyze=true`、`enabled=true`、LLM 已接。未知错误累计 ≥5 次 ⇒ LLM 提案；若提案是变更类（`set_settings_kv` / `disable_pi_rule` / `call_admin_api` 非 GET·HEAD·OPTIONS）且置信度 ≥0.80 ⇒ **当场执行**。
- 至今是否发生：**没有**。全量 206 条留痕里变更类动作执行 0 条；5 次自动分析全部是 `prompt_analysis`。这是潜在暴露。
- 修法：`blockedByGlobalGate := mutating && !cfg.AutoExecute`；被拦下时落 `awaiting_approval` 并写明是哪道闸（两闸同时不过 ⇒ 报置信度门）。只读方案不受全局闸约束（不改变生产状态，属于 `auto_analyze` 的分析面）。全局闸开时行为不变。
- 设置项短描述与长描述自相矛盾，本轮**未改文案**（它显示在设置页上，属并行车资产）；按长描述「全局执行闸」修行为。

### F2 ★★★ 观察者看着被观察对象死了 22 小时，一声没吭（量具已重写）

摄取 SQL 的两处缺陷由 `f712ea685` 修掉了，但三件事没人收口：

1. `FetchWindow` **没有任何测试**——假 source 测不到 SQL，默认驱动的单测也测不到 pgx 的数组取值行为。本轮补真库契约测试 `TestRealDBSQLSourceFetchWindow`：真库 + 与生产同款 pgx stdlib 驱动，用连接局部的 TEMP 表镜像 392 的列类型（不依赖也不碰目标库真实表）。把两个缺陷原样注回，分别红在 `22P02` 与 `unsupported Scan`（证据 §2.2）。
2. 采样器把 `awaiting_approval>0` 报成异常（全局闸关时命中必然落 awaiting_approval，是设计稳态 ⇒ 每轮都「异常」），而真正的约束一条不报。新判据：全局闸漂移 / 闸关时自动化执行变更类动作 / `last_24h` 失败数 / **开关开着却不出活** / 自上一轮无新留痕。自测 A2 用合成数据复现「开关开、null、零留痕」，首版对此静默（实况：11 轮）。
3. `last_run_at` 是引擎的**进程内存**值，蓝绿切换即清零（16:23Z 样本里它又是 null）。单凭 null 不能判死，新判据要求配合「最近 15 分钟无新留痕」。

### F3 ★★ 收口口径（量具已重写）

- 跨轮重复计数：每轮 top-100 快照直接相加，同一条留痕被计「它在首页存活了几轮」次。改为收口时全量分页（上限 1 万行，触顶如实标注截断），数字只来自完整集合。自测 B1。
- top-100 截断：留痕约 200 条/天。
- 代理②误标：`awaiting_approval` 占比被解释成「置信度门拦下待放行」，闸关时它由闸门决定、恒接近 100%。文案随全局闸取值而变，并明示**自动化指标给不出真误报率**（没有「这次命中对不对」的 ground truth）。新增「人工判定样本」：按条目列出待确认留痕里的真实错误消息。

### F9 ★★★ Worker 从未循环过（已修，自功能诞生即存在）

`bg.SpawnLoop` 的监督器对 `runFn` 的「正常返回」语义是「有意退出、不重启」（`bg/base_worker.go` supervise：只有 panic 才退避重启）。而 playbook worker 传进去的函数体是「一轮 → 睡一个间隔 → **返回**」，没有 `for` ⇒ **每个进程生命周期只跑一轮**，只有部署或重启时才会再跑。

- 生产实况（211，今天实测）：夜间 04:17–07:13 的「正常节奏」（每 7–15 分钟一轮，共 16 轮）其实是**并行车的部署节奏**（整夜每 7–10 分钟部署一次），轮次时间戳逐一对应镜像构建后 3–5 分钟；白天 07:13 之后的形态是「每次进程启动跑首轮，然后长时间静默」——09:35→14:26 空了 4 小时 51 分。
- 今天 16:07:58 CST 起 worker 停更 50+ 分钟（`last_run_at` 停在旧值）、容器日志无任何报错。重写后的采样器一落地，对这个形态报 `anomalies=[]` —— 当场暴露了自己刚修好的判据的另一个漏洞（首版只认 null），进而暴露了本缺陷。
- 修法：`runFn` 自己带 `for { 一轮 → 睡 → select ctx.Done }`。既有测试只直接调 `RunOnce`、从不经过 `Start`，所以一直没被发现。新增 `TestWorkerStartLoopsAcrossRounds`：countingSource + 断言「3 秒内必须完成 ≥5 轮 FetchWindow」+ 取消 ctx 后循环退出。
- 缺陷自首版 `3643a6408` (2026-11-21 23:36) 起存在（`worker.go` 整个历史里 `Start` 从未有 `for`）。之前所有关于「worker 在跑」的判断（包括并行车的、我上轮的、我这轮前面的）都建立在「有留痕 = 在循环」这个错误前提上。

### F4 ★★ 留痕归属（已修）

管理面手动执行 / 手动分析直接调引擎的自动化入口 ⇒ `executed_by` 恒为 `"error_playbook"`。能执行变更动作并留快照的功能，留痕答不出「是谁按的」。新增 `ExecuteEntryAs` / `AnalyzeUnknownAs`，处理器两处改走带 `piAppliedBy(r)` 的入口。`trigger_source` 取值不动（前端按闭集翻译，新值会渲染成裸键）——手动分析因此仍记为 `auto_analyze`，要靠 `executed_by` 区分。

### F5 待确认行没有处置入口（待 owner）

原始主档的设计是「否则记 awaiting_approval / skipped（管理面可见、可手动执行）」——它按设计就是只读留痕。全局闸关时每个有命中的轮次落一行，现速约 200 条/天，30 天保留 ⇒ 约 6000 行，且无法 approve / dismiss。这不是 bug，是设计边界在灰度态下的放大。选项：加审批流 / 同条目折叠重复 / 维持现状。**未改**。

### F6 条目 #3 的样本与方案语义不符（待 owner 判断）

`quota_permanent` 条目的 18 条待确认留痕：8 条 `rps exhausted`、8 条 `rpm exhausted`（上游类型都是 `quota_exceeded_error`、HTTP 429）、2 条「已达到 Token Plan 用量上限」。前 16 条是每分钟限流语义。灰度态下不执行动作所以无害；但若将来给该条目挂「凭据下线」类方案，这 16 条会不会被永久下线，取决于分类口径。**未改**，作为人工判误报的首要样本登记。

## 八、通用式

1. **接手先读上一轮留下的证据档**。并行车的轮次证据里写着三件 settings，它就在我上轮 `ls` 的输出里。
2. **判「开关关没关」先列全旋钮**。这个功能有 7 个，我只看了条目级标志。留痕的 `reason` 原文是最便宜的证据，我当时把它投影掉了。
3. **「开着却不出活」是一个独立信号**：进程内 `last_run_at` 为 null 且留痕总数不动。观察类量具要先问「被观察对象死了它报不报」，并给量具做一次「注回事故」的变异。
4. **进程内存指标重启清零**，单凭 null 不判死；要配一个持久化的佐证量。
5. **git 命令的非零退出有两种含义**（不是祖先 / 对象不存在）。`2>/dev/null && … || …` 会把报错吞成结论；对象存不存在先 `cat-file -t`。
6. **设置项自称「全局」，要按代码路径逐条核**。同一道闸在两条自动执行路径上只接了一条，读任何单独一段代码都看不出来。
7. **「该报的报出来」与「不该报的不报」要各有一条臂**。把设计稳态报成异常的量具，每轮都红，等于没有。
8. **首页快照不能跨轮相加**。
9. **没有 ground truth 时，交付可判定的样本，而不是一个比例**。
10. **变异臂要写明它考验哪条断言**。变异没让预期的测试红，先查变异语义，再怀疑测试。`switch` 换条件不换函数体，就是另一个变异。
11. **变异的「施加 → 运行 → 还原」必须是一个原子块**；中途还原会让后面的运行打在未变异代码上并显示通过。
12. **jq 的 `a // b` 吞 `false`**。取可能为 false 的字段用 `if has(k)`。本轮取证脚本第一版因此把 `auto_execute` 的历史写成 `null -> null`。
