## 一、现有恢复检测机制盘点

### 1.1 三条恢复路径（代码实测）

| 路径 | 触发条件 | 检测频率 | 实现位置 | 判定 |
|---|---|---|---|---|
| **主动探测** | 定期轮询（periodic）| 每 15min–1h | `bg/credential_probe_v2.go` | ✅ 有，但覆盖面受限 |
| **被动探测** | 真实请求成功 | 实时 | `bg/node_probe_write_through.go` | ✅ 有，但无流量 = 无检测 |
| **事件驱动** | 配额重置事件 | 实时 | `onQuotaRecovered` 四处 | ⚠️ F5 已修，但仅覆盖配额族 |

### 1.2 探测优先级（probe_model_scope.go）

```go
// 探测范围门（featured ∪ 24h 用量模型）
// §640 F2：恢复源（periodic / credential_recovery）豁免此门
```

**关键判断**：
- **featured 模型**：人工标记的核心模型，固定优先级
- **24h 用量模型**：有真实流量的模型，动态优先级
- **豁免**：恢复复检（credential_recovery）绕过范围门

**盲区**：
1. **冷模型**：既不在 featured 也无 24h 流量 ⇒ 永不探测（除非恢复源触发）
2. **免费凭据**：流量少 ⇒ 易掉出 24h 窗口 ⇒ 探测频率下降

### 1.3 恢复时间线（probe 成功 → 可路由的延迟）

```
探测提交 → 队列消费 → 直连调用 → 成功判定 → write-through 镜像
  ↓
credentialstate.RestoreOnSuccess (内存+Redis)
  ↓
cmb.available = TRUE (DB，下次 view 刷新可见)
  ↓
v_routable_credential_models (5min 刷新)
  ↓
autoroute 索引 (5min 刷新)
```

**关键延迟点**：
- **view 刷新**：5min 周期（不是实时）
- **索引刷新**：5min 周期（与 view 独立）
- **最坏情况**：探测成功 → 10min 后才进路由候选池

## 二、免费供应商的特殊困境

### 2.1 免费供应商的识别（真库实测需补充）

**假设清单**（需新会话验证）：
- freellmapi 系（omnifree 种子引入，项5 已修断链）
- 个人注册的免费 tier 账号
- 试用期凭据

### 2.2 免费供应商 vs 付费供应商的差异

| 维度 | 免费供应商 | 付费供应商 | 对恢复检测的影响 |
|---|---|---|---|
| **流量密度** | 低（用户优先选付费） | 高 | 免费凭据易掉出 24h 用量窗 ⇒ 探测频率↓ |
| **配额窗口** | 严格（1req/min, 1000/day） | 宽松 | 正常使用易撞配额 ⇒ 频繁标记 unavailable |
| **恢复承诺** | 通常无 Retry-After | 有 Retry-After | 免费凭据的 recover_at 只能靠推断（5h 边界） |
| **探测成本** | 吃配额（探测 = 真实调用） | 同左，但配额大 | 免费凭据探测 1 次 = 用户可用次数 -1 |
| **商业优先级** | 低（用户不付费） | 高 | featured 标记倾向付费模型 |

**关键矛盾**：
- **探测代价高**：免费凭据配额少，探测 1 次就占用户配额 ⇒ 不敢频繁探测
- **恢复收益高**：免费凭据是成本为 0 的候选 ⇒ 恢复后应优先使用
- **检测难度大**：无流量 + 不在 featured ⇒ 依赖主动探测，而主动探测又受范围门限制

### 2.3 当前机制对免费凭据的盲点

| 盲点 | 表现 | 根因 |
|---|---|---|
| **探测频率不足** | 免费凭据 429 后，下次探测可能 1h+ | featured 外 + 无流量 ⇒ 低优先级 |
| **恢复事件缺失** | 免费 API 通常无配额重置通知 | onQuotaRecovered 只覆盖有 API 的供应商 |
| **配额推断不准** | 1req/min 的 recover_at 推断为 5h | inferQuotaRecoverAt 按保守估计 |
| **探测模型错配** | 探测用 featured 模型，免费凭据可能只支持基础模型 | credential_recovery fail-fast 分支未覆盖 |

## 三、根因分析（五层剥离）

### 3.1 直接原因（L1）

**配额 API 有读数却无动作路径**（项6 根因 1）：
- `balance_quota_probe.go` 调用厂商 API 读配额
- 读到 `MaxUsedPercent < 100`（已有余额）
- 但 `SetOnPlanCapacityAvailable` 只在 `balance_floor` 守卫下触发
- ⇒ **有余额但未用尽 ⇒ 不满足 balance_floor ⇒ 不触发恢复**

### 3.2 机制缺陷（L2）

**恢复触发条件过严**：
- 凭据级恢复只认三种证据：
  1. 真实请求成功（被动探测）
  2. 主动探测成功（periodic / recovery）
  3. 配额完全用尽后重置（balance_floor 守卫）
- **缺失**：配额部分恢复（如从 90% 降到 50%）不触发

### 3.3 优先级偏差（L3）

**探测资源向付费/热模型倾斜**：
- featured 模型优先（人工标记）
- 24h 用量模型次之（有流量）
- 冷模型/免费凭据排最后（探测预算耗尽后跳过）

### 3.4 可观测性不足（L4）

**无法快速回答「有多少凭据实际已恢复但系统未感知」**：
- `v_routable_credential_models` 只看系统状态（cmb.available）
- 无对照：系统认为 unavailable 的凭据，实际调用会不会成功？
- ⇒ 需要**影子探测**或**定期对账**

### 3.5 设计假设过时（L5）

**原设计假设**（推测，需验证）：
1. 大部分凭据是付费的，配额充足
2. 有流量的模型自然会被真实请求探测到（被动探测为主）
3. 免费凭据占比小，手工管理可接受

**现实偏离**：
1. 免费凭据占比上升（omnifree 种子 + 个人注册）
2. 免费凭据配额严格，频繁 429 ⇒ 大量标记 unavailable
3. 无流量 ⇒ 被动探测失效 ⇒ 依赖主动探测，而主动探测覆盖不足

## 五、优化方案（分阶段）

### P0：止血（1 周）—— 修复已知缺陷

#### P0-1：balance_floor_guard 放宽（F-B 已实施？需验证）

**问题**：配额 API 有读数但 `MaxUsedPercent < 100` 时不触发恢复。

**修复**（AGENTS 项6 F-B）：
```go
// balance_floor_guard: 用尽族挂起 + MaxUsedPercent < 100 ⇒ SetOnPlanCapacityAvailable
if credentialState.QuotaExhausted && planUsage.MaxUsedPercent < 100 {
    SetOnPlanCapacityAvailable(credID, model)
    // → OnQuotaRecharged 快速探测
}
```

**验收**：211 上实测，plan sweep 的 `restored` 计数 > 0。

#### P0-2：credential_probe_v2 fail-fast 探测模型回退梯（F-A 已实施？需验证）

**问题**：探测模型与凭据支持模型不匹配 ⇒ 探测失败 ⇒ 误判凭据不可用。

**修复**（AGENTS 项6 F-A）：
```go
// credential_probe_v2 fail-fast 分支：
// 配额族失败 ⇒ ≤3 个备选 chat 绑定模型各试一发，
// 按 node_probe_state.last_direct_ok 优先
```

**验收**：配额族探测失败后，日志中出现「fallback to model X」。

#### P0-3：免费凭据探测频率专项提升

**问题**：免费凭据掉出 24h 窗口后，探测频率骤降。

### P1：机制增强（2-3 周）—— 多路径恢复检测

#### P1-1：影子探测（Shadow Probing）

**目标**：在不影响主探测的前提下，定期验证「系统认为 unavailable 的凭据是否实际已恢复」。

**设计**：
```go
// 每小时一轮，从 unavailable 池随机抽样 N 个（N=10）
// 按 unavailable_at 升序（最早被标记的优先）
// 发起轻量探测（仅调用 1 次，不进队列）
// 成功 ⇒ 立即 restore + 记录「影子探测命中」指标
// 失败 ⇒ 不改状态（避免重置 recover_at）
```

**成本控制**：
- 每小时 10 次探测调用（vs 当前 ~100+ 次主探测，增量 <10%）
- 只探测 unavailable 池（不与主探测竞争资源）

**验收**：
- 指标 `shadow_probe_hit_rate`（命中率）
- 若命中率 >5% ⇒ 说明有大量「已恢复但未感知」的凭据

#### P1-2：配额渐进恢复（Gradual Recovery）

**目标**：配额从 90% → 50% 时就开始恢复，而非等到 0% → 重置。

**设计**：
```go
// balance_quota_probe 增加渐进恢复判据
if credentialState.QuotaExhausted && planUsage.MaxUsedPercent < 80 {
    // 配额降到 80% 以下 ⇒ 部分恢复
    SetQuotaPartiallyRecovered(credID, availablePercent)
    // ⇒ cmb.available = TRUE，但带「配额受限」标记
    // ⇒ 路由评分降权（capacity 维度），但仍可作为候选
}
```

**权衡**：
- 优势：恢复更快（不等完全重置）
- 风险：提前恢复的凭据可能再次快速 429 ⇒ 需配合节奏校准冷却（§642 W1）

#### P1-3：免费凭据专用探测池

**目标**：免费凭据单独分配探测预算，不与付费凭据竞争。

**设计**：
```go
// probe_policy.go 增加凭据分层
type TierPolicy struct {
    Tier string // "free" / "paid" / "enterprise"
    ProbeInterval time.Duration
    MaxConcurrent int
}

freeTierPolicy := TierPolicy{
    Tier: "free",
    ProbeInterval: 30 * time.Minute, // 比 paid 更频繁（付费可能 1h）
    MaxConcurrent: 20, // 独立预算
}
```

**前置条件**：
- 凭据表需增加 `tier` 列（或从 billing_mode 推断）
- 免费供应商清单需维护（可从 omnifree 种子同步）

### P3：架构优化（1-2 个月）—— 长期方案

#### P3-1：事件驱动恢复（Event-Driven Recovery）

**目标**：从「定期轮询」升级为「事件驱动 + 轮询兜底」。

**事件源**：
1. 厂商配额 API 的 webhook（如 OpenAI usage alerts）
2. 用户主动报告（「这个模型又能用了」）
3. 跨网关实例的成功信号广播（Redis pub/sub）

**设计**：
```go
// 事件总线
type RecoveryEvent struct {
    Source      string // "webhook" / "user_report" / "peer_gateway"
    CredentialID int
    Model       string
    Evidence    string // "quota_reset" / "manual_test" / "peer_success"
}

// 订阅者立即触发探测（优先级最高）
func OnRecoveryEvent(e RecoveryEvent) {
    SubmitProbe(e.CredentialID, e.Model, source="event_driven", priority=URGENT)
}
```

#### P3-2：探测成本优化

**目标**：降低探测对用户配额的占用。

**方案 A**：HEAD 请求探测（若上游支持）
```
GET /v1/models ⇒ 只验证鉴权，不消耗生成配额
```

**方案 B**：最小 token 探测
```
prompt = "hi"  // 1 token
max_tokens = 1
⇒ 每次探测成本 ~$0.00001（vs 普通探测 ~$0.001）
```

**方案 C**：探测结果跨凭据共享
```
// 同一供应商的多个凭据，若一个探测成功 ⇒ 其他凭据也标记「可能已恢复」
// ⇒ 降低探测频率，但保持恢复及时性
```

## 七、验收标准（P0+P1 实施后）

### 7.1 功能验收

- [ ] P0-1：plan sweep 的 `restored` 计数在配额部分恢复时 >0
- [ ] P0-2：配额族探测失败后，日志出现 fallback 记录
- [ ] P0-3：免费模型（≥5 个）标记为 featured
- [ ] P1-1：影子探测每小时运行，`shadow_probe_hit_rate` 指标可见
- [ ] P1-2：配额降到 80% 以下时，凭据状态变为「部分可用」
- [ ] P1-3：免费凭据探测间隔 ≤30min（vs 付费 ≥1h）

### 7.2 指标验收

**基线采集**（P0 实施前）：
```sql
-- 1. 当前 unavailable 凭据数
SELECT COUNT(*) FROM credential_model_bindings WHERE available = FALSE;

-- 2. 当前免费凭据可用率
SELECT 
    COUNT(*) FILTER (WHERE available = TRUE) * 100.0 / COUNT(*) as available_pct
FROM credential_model_bindings cmb
JOIN credentials c ON cmb.credential_id = c.id
WHERE c.billing_mode IN ('free', 'trial'); -- 需确认列名

-- 3. P95 探测间隔（最近被探测时间）
SELECT percentile_cont(0.95) WITHIN GROUP (ORDER BY EXTRACT(EPOCH FROM (NOW() - last_probe_at)))
FROM node_probe_state;
```

**目标读数**（P0+P1 实施后，1 周稳态）：
- unavailable 数：↓ 30%（从 ~2700 → ~1900）
- 免费凭据可用率：↑ 至 ≥60%（从 31.8%）
- P95 探测间隔：↓ 至 ≤30min（从 ~1h+）
- 恢复延迟 P95：≤15min（新指标，需新建采集）
