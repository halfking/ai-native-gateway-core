### 2.3 ③usage_facts occurred_at 索引/分区评估（静态）

**schema 现状**：
- `usage_facts` 已 `PARTITION BY RANGE (occurred_at)`，主键 `(fact_id, occurred_at)`，UNIQUE `(event_id, revision, occurred_at)`
- 4 个二级索引：`idx_usage_facts_request` / `_tenant_time` / `_provider_time` / `_model_time`，均含 `occurred_at DESC` 二级列
- **无 occurred_at 自身前导索引**
- **分区策略**：仅 `usage_facts_default` DEFAULT 分区，**无按日/按月分区函数**

**性能瓶颈确认**（rollup.go 查询分析）：
- `providerModelDaySQL` (rollup.go:227) — `WHERE occurred_at >= $1 AND occurred_at < $2 AND provider_id IS NOT NULL`
- `totalDaySQL` (rollup.go:312) — `WHERE occurred_at >= $1 AND occurred_at < $2 AND status <> 'success'`
- `internalTenantDaySQL` (rollup.go:344) — `WHERE occurred_at >= $1 AND occurred_at < $2 AND traffic_class = 'business'`
- `internalModelDaySQL` (rollup.go:412) — `WHERE occurred_at >= $1 AND occurred_at < $2`
- `internalPersonDaySQL` (rollup.go:475) — `WHERE occurred_at >= $1 AND occurred_at < $2`

5 个 rollup 查询全部用纯 `occurred_at >= $1 AND occurred_at < $2` 范围条件，前 3 个无其他维度过滤或仅含 IS NOT NULL。

**索引可用性评估**：
- `_tenant_time` / `_provider_time` / `_model_time`：3 个有 `tenant_id`/`provider_id`/`canonical_id` 前导，rollup 查询中 3 个 WHERE 子句无对应过滤维度 → 索引**无法加速**
- `_request_time`：`request_id` 前导，rollup 查询无 `request_id` 过滤 → 索引**无法加速**
- 唯一可用：分区裁剪（partition pruning by occurred_at），但只有 DEFAULT 分区时无收益

**结论**：P3 登记项「usage_facts 无 occurred_at 前导索引且不进 partition_manager ensureSpecs」属实，**rollup 每日全表扫线性退化**为客观存在。本轮未实跑 scratch 真库（缺 env）；建议下一轮落地：
1. 加 `CREATE INDEX ... ON usage_facts (occurred_at DESC)`（或挂在 start_revision ensureSpecs）
2. 加按日分区函数（参照 mock_probe_history_daily_partition 模式）
3. 迁移号需 fetch 核对：R65 后 747（session_mirror_outbox_source_claim）/748（8oz，已用）/800（provider_endpoint_protocols，已用），下一可用 749 或 801
