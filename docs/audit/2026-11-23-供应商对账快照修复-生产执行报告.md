## 五、根因确认与证据链

### 5.1 时区边界错位的技术证据

#### 证据1：代码层（2026-11-20时区轮修复）
- **文件**：`bg/report_rollup_worker.go:111-118`
- **修复**：Worker使用`settings.SystemDayStart`（Asia/Shanghai）
- **聚合函数**：`domains/reportrollup/rollup.go:144-152` 使用`day.Location()`
- **结论**：修复后代码正确使用CST边界

#### 证据2：数据层（11-17 UTC vs CST对比）
```
UTC边界（旧快照）：23,459请求 / $843.57
CST边界（新快照）：27,446请求 / $2,127.73
差异：+3,987请求 / +$1,284.16
差异发生在：11-17晚上16:00-24:00 UTC（即11-18凌晨00:00-08:00 CST）
```

#### 证据3：费用口径（成功vs失败请求）
```
成功请求：占51.2%，产生99.93%费用，平均$0.0955/请求
失败请求：占48.7%，产生0.07%费用，平均$0.0001/请求
```
**推论**：漏计的8小时窗口主要是高成本成功请求 ⇒ 费用差异42.9%远大于请求数差异4.7%

### 5.2 11-18异常数据的解释

**旧快照11-18：26,391请求（高于预期）**
- 原因：混合了两种边界
  - 11-17晚8小时（UTC: 11-17 16:00-24:00 = CST: 11-18 00:00-08:00）被计入11-18
  - 11-18当天数据（UTC: 11-18 00:00-24:00 = CST: 11-18 08:00 - 11-19 08:00）
- 因此11-18看起来"多了"，实际是吃了11-17的残余

**新快照11-18：22,905请求（符合预期）**
- 原因：统一CST边界
  - 11-18当天数据（CST: 11-18 00:00-24:00）
  - 11-17晚8小时被正确归入11-17
