## 二、口径纪律（本轮最有价值的部分）

### ★ ① 后端的 `total_cost` 是**跨单位相加**，页面拒绝展示它

视图 `user_session_aggregates` 里**没有** `total_cost` 列，只有：

```
internal_cost = SUM(session_summaries.total_cost_usd)     -- 美元
external_cost = SUM(session_summaries.total_credits_charged) -- 积分
```

而后端查询写的是 `SUM(internal_cost + external_cost) as total_cost`
⇒ **美元 + 积分**直接相加，单位不同。

**处置**：

- 总览页**不展示**「总花费」卡，改为从**同源**的 `trends.cost` 分别求和出
  「内部成本（美元）」与「外部成本（积分）」两张卡
  （缺日不补零 ⇒ 缺日贡献就是 0 ⇒ 求和与区间总额一致）；
- 排行表的服务端排序键只有 `total_cost` 这一个混合口径，无法拆分
  ⇒ 保留该列，但**页面顶部显式写明口径**（`sessionAnalytics.costNote`）：
  「花费一列是内部成本（美元）与外部积分的合计。两种单位不同，只适合做相对比较，
  不能当作同一个金额。」

> **通用式**：前端拿到一个数字前，先问它的**单位**是什么、单位能不能相加。
> 口径没对表的数字，展示得越好看越有害。

### ★ ② `avg_context_size` 是后端写死的假值 ⇒ 不展示

`admin/session_analytics/queries.go:238`：

```go
// TODO: avg_context_size 需要从 sessions 表获取
current.AvgContextSize = 8192 // 暂时使用默认值
```

⇒ 总览页**不做**「平均上下文长度」卡。宁可少一张卡，不展示一个恒等于 8192 的假指标。

### ★ ③ `growth` / `success_rate` / `cache_rate` 都是 0–100 百分比，不是 0–1 比率

- `calculateGrowth` 返回 `(current-previous)/previous*100`；
- `getModelStats` 的 SQL 里 `SUM(success_count)/SUM(request_count)*100`。

⇒ 前端直接按百分比渲染（`unit.percent`），**不再乘/除 100**。

### ★ ④ 陈旧态（503 `analytics_view_stale`）不是错误态

服务端在写响应**之前**检查物化视图新鲜度，超预算就 503 拒绝返回过期数字
（`mv_guard.go`，预算 90 分钟）。前端把这一态与普通失败分开：

- `stale = true` ⇒ 渲染「聚合数据正在刷新」横幅（**不是**「加载失败，请重试」）；
- 陈旧与错误**互斥**，不会同时出现（否则用户既刷新又重试，两个动作都没意义）。

### ★ ⑤ 权限闸门：后端才是真源

后端 `isAdminFromRequest` 放行 `super_admin` / `tenant_admin` / `admin_key`，
且**专门为 `tenant_admin` 做了租户隔离** ⇒ 前端路由用 `requiresAuth` 而非 `requiresSuper`，
菜单项只 `hideForTenant`（租户门户隐藏）。粗粒度前端闸门不该把 tenant_admin 挡在门外。

> 文档数字的替换**用门禁自身的正则做等长剥标签 + 偏移回写**，
> 避免误伤同数字的其它语境（如「1049 个环境变量」「407 项设置」）。

### ★ 文档里藏着一处**门禁抓不到的旧口径漂移**（本轮顺手对齐）

`simple-mode-concept.html` 的正方括号注释写着
「本数由四十九改为五十」，而同一份稿里折叠条数用的是 49
⇒ 门禁的 `fold1` 正则恰好命中的是那个 **49**，于是
「文档漂移值」被当成了「期望值」——**门禁绿着，文档是错的**。

本轮把全部折叠数表述按**门禁自己的算术**（`FOLDED = ITEMS − EXPOSED` = 67 − 14 = 53）
统一对齐，共 13 处（分组计数徽标 / 高级面板条数 / 台账条数 / 图标数 /
页内条目构成 `52 项页内条目 + 1 条站外链接 = 53`）。
**这类漂移只有靠人读文档才能发现** —— 门禁的判据是「文档值 == 期望值」，
而不是「文档值 == 真源值」。

**通用式**：门禁锁的是「文档与常量一致」，不是「文档与现实一致」。
两者同时错时门禁是绿的 ⇒ 改口径时必须**自己算一遍真源**（`ITEMS − EXPOSED`），
不能只把常量改成和文档一样。

**顺带消掉一个既有死键**：8 个语种的 `nav.item.sessionAnalytics` 文案**早已存在**却零引用，
`config/navCoverage.test.ts` 的文件头早就把它点名为「可交付未交付」
（“8 个语种的 `nav.item.sessionAnalytics` 文案早已存在却零引用”）。
本次挂菜单 ⇒ 该键第一次被真正引用。

### 7.4 本轮撞到的 3 个「量具错」，以及它们各自的归属

| # | 现象 | 归属 | 处置 |
|---|---|---|---|
| ① | flow 在「人员」表头上红 | **量具错**（不是产品缺陷）：可排序表头是 `<button>{{人员}}<span v-if>▲</span></button>`，Vue `whitespace:condense` 把文本与条件 span 之间的换行折成**一个空格** ⇒ DOM 文本是「人员 **」** ⇒ `text:` 全匹配必红 | 断言改 `.*人员.*`（4 处可排序表头同理）。**证据**：Maestro 层级快照原文 `"text": "人员 "` |
| ② | 探针报「菜单里没有 `/admin/session-analytics` 入口」 | **量具错**：顶栏导航是**分组下拉**，面板 Teleport 到 body 且 `v-if="activeGroup && openGroupId"` ⇒ **分组未展开时菜单项根本不在 DOM 里** | 改成走真实用户路径：展开分组 → 点入口 → 断言落地路径 |
| ③ | 探针报「详情页没有任务列表表」 | **量具错 + 数据态**：任务列表不是常驻第二张表，而是**点项目行**才切的 tab；且 211 上 `sessions.task` 非空行数 = **0** ⇒ `task_count` 全 0 ⇒ 渲染的是**空态**（产品行为正确） | 判据改成互斥二选一（有表 ⇒ 表头齐全且有行；无表 ⇒ 必须出现该层空态文案），并把「任务层无数据」登记为 L8 |
| ④ | 「探针另发一次 API 与页面逐字相等」这条断言**必然会假红** | **量具错**：线上有活流量 ⇒ 页面渲染那一刻的数与探针几秒后另取一次**必然可能不等**（实测同一会话总会话数 10 分钟内从 14,746 涨到 14,761） | 对拍基准改成**抓页面自己收到的那份响应**（CDP `Network` 域 + `getResponseBody`）⇒ **同源、同时刻** ⇒ 严格相等，**不需要容差**；并加一条断言「已捕获页面自己的响应」把「基准同源」本身变成可验项 |

> ★ **通用式（4 条）**：
> ① **可排序表头 = 带尾随空格的文本** ⇒ `text:` 断言一律 `.*….*`；
> ② **「元素不在 DOM 里」有两种原因——没渲染 与 还没展开** ⇒ 判据要问「用户能不能点到」，不能问「DOM 里有没有」；
> ③ **空数据 ≠ 产品缺陷** ⇒ 断言要写成「有数据 ⇒ 内容对；无数据 ⇒ 空态对」的互斥二选一，否则量具会把数据态当缺陷报；
> ④ **对拍基准必须与被测页面同源** ⇒ 探针另发一次请求当基准，在有活流量的生产上**必然**产生假红；正确解法是抓页面自己收到的那份响应。
