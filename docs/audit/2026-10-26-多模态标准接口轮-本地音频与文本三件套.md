## 1. 网关仓改动

### 1.1 文本三件套（domains/streaming/summarize.go + summarize_test.go）

- 三个端点共用 `SummarizeService`，LLM 编排经**环回** /v1/chat/completions
  （转发调用方 Authorization，路由/预算/审计/故障转移全量复用 chat 面）。
  与 audio_transform 同款架构。
- 鉴权抽成包级 `authenticateNoRPM`（不消耗 RPM——环回 chat 步已计一次）；
  audio_transform 的 authenticateTransform 改为薄委托（同一把尺子一份实现）。
  环回 HTTP 细节同样收敛为包级 `loopbackChatCompletions`。
- 提示词移植自三个已验收 SKILL.md（task-classifier / title-writer /
  session-summarist，2026-10-26 方案 §3.2），网关侧硬校验：
  - title：≤max_chars（默认 20 字）、禁用开头（关于/有关/对于/浅析/浅谈）、
    实体信号（数字/拉丁）择优、全违规点名重试一轮、再败 502；
  - classify：受控词表（默认 8 类 + 二级标签，可 vocab 覆盖）、词表外
    task_type 判违规重试、自造 sub_types 过滤；
  - summarize：<3000 字单次渲染（minutes/brief 两风格）；≥3000 字
    map(段结构化抽取)→reduce(时间线合并)→render(纪要渲染)，缺节重试、
    单段 JSON 失败降级为原文摘录不中断管线；段数上限 10（调用数 ≤12 落在
    默认 12 RPM 内）；环回 429 等窗口单次重试。
- `<think>` 块剥离（qwen3 系 reasoning 混入 content 的既有坑）。
- reasoning_effort 缺省：title/classify=none、summarize 各层=low（方案
  §3.2 编排器参数表原样落地）；调用方可覆盖。

### 1.4 两个潜伏缺陷修复（本轮被本地音频注册踩出）

**缺陷一：启动播种凭据明文落库 ⇒ admin 面解密即死。**
`SeedProvidersFromCatalog`（启动期从 catalog 播种本地供应商）的
`ensureLocalCredentialsForSeededProviders` 把占位 key **明文**写进
credentials.secret_ciphertext（旧注释自称「首次使用时由路由器处理加密」
——不实）。症状：211 实测 refresh-models run **1ms 内失败**，错误被
summarizeProviderRefreshError 的 default 分支吃成 "models request failed"，
真实错误（api_models_error 列）是 "credential decrypt failed"。
修复双层：
- 前向：SeedProvidersFromCatalog 接收加密器（main.go 注入
  adminHandler.EncryptCredentialBytes），占位 key 走真 Fernet/AES 链路；
- 回溯：admin `decryptCred` 对**精确等于** localNoKeyPlaceholder 的明文
  直通（占位值是全仓公开常量，不构成秘密；密文列出现该值 ⇔ 播种写过）。
- 回归测试 admin/local_provider_plaintext_credential_test.go（含反向：
  乱密文仍必须解密失败——容忍是精确匹配，不是放松）。

**缺陷二：同一明文在运行时路由面把候选整个丢掉。**
provider/client.go 的凭据解密（fetchReveal/fetchExtraKeys）同样拒明文 ⇒
enrichWithAPIKeys 拿不到 key ⇒ audioCandidateSelection 过滤 ⇒ ASR/TTS
恒 no_provider。**这也是 llamacpp/lmstudio/mlx/vllm 四个老牌本地供应商
播种凭据「从未真正可路由」的根因**（此前无人经网关路由它们，未暴露）。
修复：常量提升到 provider/catalog.LocalNoKeyPlaceholder（admin 侧别名引用，
同一把尺子一份实现），provider 解密缝同样精确直通。

**缺陷三：探针不认 thinking 模型 ⇒ node_probe_failed 活锁（bg/）。**
探针载荷固定 max_tokens=32 且不带 think:false；thinking 默认开启的模型
（qwen3/qwen3.8 系）把 32 token 全烧进 reasoning、content 恒空 ⇒
credentialProbeHasOutput 只认 content/tool_calls ⇒ 判 inconclusive ⇒
节点永远翻不了绿；叠加 Mac 冷加载（18-21GB 模型 20-160s）撞 10s 探针
超时，形成 node_probe_failed 活锁（211 实测：本地 chat 模型在部署重启后
全数不可路由，只能靠手动补种 URSM 短暂续命、60s 对账器又翻回去）。
修复：credentialProbeHasOutput 的 **chat 臂**加认 message.reasoning
（ollama）/ message.reasoning_content（deepseek 风格）——「探针问的是
节点活着吗（liveness），r1029 管的是能不能交付给用户（deliverability），
两个问题两种答案」；业务面（emptyoutcome/中继 failover）一字不动。
这正是《嵌入与会话总结优化方案-2026-10-26》§14.4 预留的网关补丁一。
既有负例夹具（reasoning-only 判死）按新契约移为 chat 正例（messages/
responses 两臂维持原判），理由写进测试注释。

## 5. 本轮踩出的坑（运维/代码双重）

1. **admin 刷新路径与 discovery.Service 是两条登记腿**：前者 enroll 出的
   provider_models.canonical_id 为空（后者才有 canonical 绑定链）⇒ 新模型
   「offers 可见但不可路由」。用手工绑定 API（InsertManualCredentialModel）
   收口。
2. **手工绑定默认 admin_protected=TRUE**，而 modelsRoutableSQL 与候选 SQL
   都排除 protected 行 ⇒ 绑定完还是不可见。数据面 UPDATE 清标志收口。
3. **modality 推断只在 discovery.Service 腿**：admin 登记腿落 text；
   whisper-*/tts- 前缀规则（modality_defaults.go）对 admin 腿无效。
4. **错误映射器会吃真因**：summarizeProviderRefreshError 的 default 分支把
   "credential decrypt failed" 报成 "models request failed"——排障时必须
   去读 credentials.api_models_error 列拿原文。
5. **凭据状态健康但 URSM 索引 5 分钟桶**：新绑定要等 auto_index_refresher
   桶滚动才进 credential_model_index_hot（no_provider 的主要等待来源）。
6. **Mac ollama 的 LRU 驻留 vs 探针 10s 超时 = 活锁**：模型被挤出后每次
   探针触发 20-160s 冷加载 ⇒ 永远超时。MAX_LOADED_MODELS 3→5 的 plist
   补丁未落到**实际在跑的服务实例**上（Ollama.app 与 launchd 双实例之争，
   枢纽坑#2 复发）⇒ 需要用户侧一次彻底处置（退 app + 重启 Mac）；
   embedding:8b 在 32K ctx 下占 10GB，与双 chat 大模型常驻内存吃紧。
7. **部署引擎的 DD_REPO_ROOT 解析会漂**：第 5 次部署（01:52）同步到 211
   的竟是上游 abc92693 的树（main.go 仅 1 处 summarize）⇒ 镜像静默丢了
   本轮全部端点（/v1/summarize 404 而非 400）。用 `LLM_GATEWAY_ROOT=<绝对
   路径>` 显式钉根后恢复正常（第 6 次部署远端树 main.go 10 处、
   summarize.go/whisper_stt.go 俱全）。**多 checkout 并存的机器上部署必须
   钉根**。
8. **qwen3:30b-a3b 当 map 模型不可用**（网关侧契约限制）：qwen3 hybrid 不
   认 effort 硬分离，max_tokens 预算被 reasoning 烧穿 ⇒ content 空 ⇒
   chat 面 empty_response 故障转移 ×3 把阶段预算全烧掉。方案文档 §3.2 的
   fallback（map 层用 qwen2.5:7b）是正解；map 层 max_tokens 已提到 3000。
9. **ollama 对非 thinking 模型收到 reasoning_effort 直接 400**（真根因，
   10-27 凌晨钉死）：`"qwen2.5:7b" does not support thinking`。修复在
   **reqprobe**（internal/reqprobe/diagnose.go 新增 thinking 能力族判据 ⇒
   剥 reasoning_effort/think 免费重试）——对所有调用方生效，与仓内
   「参数被拒点名剔除」的既有机制同一形态；summarize 层另加同判据的
   环回兜底（双保险）。教训：**chat 面会把上游 400 吞成 503**，上游错误
   细节只在 upstream_http_attempt 日志里——排障必须看执行器日志，不能只
   看客户端信封。
10. **nginx 300s proxy_read_timeout vs 10 分钟管线预算**：27b 渲染 2-4 分钟，
   叠加 map/reduce 后超 300s 被 nginx 掐断；**且被掐断的在途请求会把渲染
   模型的 node_probe_state 打脏**（request_failure → 探针梯子翻红），下
   一轮立刻 no_provider，形成「看似随机」的 503。211 nginx 的 llm 网关
   location 已提 proxy_read/send_timeout 660s（手工改 conf + reload；引擎
   切流只重写 upstream 行，不会被部署覆盖）。

## 7. 批判式审计轮补记（2026-10-27，本轮）

上一轮的收尾声明经全量复核后，抓到并修掉 **一个真回归 + 一个险些成型的半残状态**：

### 7.1 探针 liveness 修复的语义越界（真回归，已修）

上一轮把「reasoning 也算探针存活证据」直接写进了 `credentialProbeHasOutput`——
而该函数是**共享判据**：credential 探针与 node/model/active 探针的共享入口
`probeResponseHasOutput`（probe_responses_fallback.go）都消费它。后果：
model 级探针的 deliverability 语义被降级成 liveness——reasoning-only
（max_tokens 被 thinking 烧穿、content 为空、**用户会拿到空回答**的形态）
被判为探针成功 → bg 包 4 条测试翻红
（TestNodeProbeRequiresSemanticResponse / TestProbeOtherEntryPointsRequireOutput /
TestModelProbeObservationPreservesConsensus / TestProbeFallbackConsumersRetainInconclusiveState）。

**语义分层修法**（2026-10-27 审计轮定下的界线）：
- `credentialProbeHasOutput` 恢复原语义（reasoning 一律不算输出）——
  node/model/active 探针经共享入口维持 deliverability；
- 新增 `credentialProbeHasLivenessEvidence`（仅 chat 形态、仅 content 全空时
  认 reasoning）——**只许 credential 探针**（credential_probe_v2 chat 臂）以
  `hasOutput || livenessEvidence` 叠加调用；
- 夹具分层：credential 路径（miniChat）reasoning-only 为正例；共享判据由
  TestCredentialProbeSharedValidatorExcludesReasoning 反向锁定。
