## 一、现状审计

### 1.1 会话总结功能现状

#### 核心组件
- **Summarizer** (`domains/sessionsummary/summarizer.go`)
  - 支持全量总结 (`GenerateSummary`) 和增量滚动总结 (`GenerateRollingSummary`)
  - 使用 LLM 生成标题、摘要、关键主题、用户意图
  - 已实现智能体类型识别 (agent_type) 和专家领域识别 (expert_type)
  - 输出包含标签 (tags) 用于分类
  - 支持多消息源 (V1 request_logs / V2 session_bodies)

#### 执行机制
- **SessionLifecycleWorker** (`bg/session_lifecycle_worker.go`)
  - 周期性扫描不活跃会话
  - 配置驱动的回收策略: soft_close / notify_only
  - 发布 `session.closed` 事件触发总结链路
  - **关键发现**: 2026-11-20 闭环审计轮已修复 - 此前零生产接线，UPDATE 引用不存在的列

- **SessionSummaryWorker** (`domains/analysis/workers/session_summary_worker.go`)
  - 订阅 `EventSessionClosedSummary` 事件
  - 调用 Summarizer 生成总结
  - 执行 closeHooks (元数据 final / 项目归属)
  - **容错设计**: summarizer 为 nil 时仍执行零成本钩子

#### 数据存储
- **session_summaries** 表 (迁移 358, 606, 655, 560 等)
  - 字段: title, summary, key_topics, user_intent
  - 扩展字段: agent_type, expert_type, tags (迁移 606)

  - 支持租户隔离和 RLS

### 1.3 当前缺口

❌ **缺口1: 任务/项目表不完整**
   - 没有独立的 `tasks` 表用于存储任务实体
   - 任务信息依赖 ACC 外部系统，本地无完整镜像
   - 无法在本地进行任务级别的元数据管理

❌ **缺口2: 总结未参考任务/项目上下文**
   - 总结生成时未考虑会话所属任务/项目
   - 同一任务下的多个会话总结独立生成，缺少连续性
   - 无法识别任务内的重复/相似会话

❌ **缺口3: 长会话分层总结未实现**
   - 当前只有 10 轮窗口的简单截断 (`capByTurn`)
   - 超长会话（>50轮）缺少分层汇总策略
   - 增量总结 (rolling) 有实现但缺少层级管理

❌ **缺口4: 归一化策略缺失**
   - 同一任务/项目下的相似会话未识别
   - 标题/摘要存在语义重复
   - tags 字段未做归一化处理

❌ **缺口5: PI 智能体路由未专门配置**
   - 总结任务未显式路由到本地快速模型
   - 没有专门的任务类型标识 (task_type)
   - 缺少成本优化策略

## 二、业界最佳实践分析

### 2.1 长会话分层总结方案

基于 Langfuse、OpenAI、Anthropic 等系统的实践，主流方案有：

#### 方案A: 滑动窗口 + 递归汇总
```
[第1-10轮] → 摘要S1
[第11-20轮] + S1 → 摘要S2
[第21-30轮] + S2 → 摘要S3
...
```
- **优点**: 保持上下文连续性
- **缺点**: 摘要链式传递，后期可能丢失早期细节

#### 方案B: 分段独立总结 + 元总结
```
[第1-20轮] → 摘要S1
[第21-40轮] → 摘要S2
[第41-60轮] → 摘要S3
合并 [S1, S2, S3] → 元摘要Meta
```
- **优点**: 各段独立，并行生成
- **缺点**: 需要额外的元总结步骤

#### 方案C: 混合方案 (推荐)
```
Stage 1: 滑动窗口总结 (实时)
  - 每10轮生成增量摘要
  - 保留最近3个窗口的详细内容
  
Stage 2: 分段归档总结 (定期)
  - 每50轮生成段落摘要
  - 压缩历史窗口
  
Stage 3: 会话关闭时生成元总结
  - 合并所有段落摘要
  - 提取全局主题和演进路径
```

### 2.2 任务/项目关联模式

#### Langfuse 模式
- **Trace → Session → Request** 三层结构
- Trace 关联 user_id / session_id / tags
- 支持自定义元数据和标签

#### GitHub Projects 模式
- Issue → Project 多对多关联
- 通过 labels 和 milestones 归类
- 支持自动化规则

#### 推荐模式: 灵活关联 + 推断增强
```
会话 (sessions)
  ├─ 显式关联: X-Gw-Task-Id / X-Gw-Project-Id (ACC 来源)
  ├─ 推断关联: session_project_attribution (规则/LLM)
  └─ 任务本地镜像: tasks 表
       ├─ task_id (主键)
       ├─ project_ref (外键 → project_dim)
       ├─ metadata (JSONB)
       └─ tags (归一化标签)
```

### 3.2 分层总结实现策略

#### 3.2.1 三层架构

```go
// Layer 1: 滑动窗口总结 (实时)
type WindowSummarizer struct {
    windowSize   int  // 默认 10 轮
    overlapSize  int  // 默认 3 轮
    maxWindows   int  // 最多保留 5 个窗口
}

// Layer 2: 段落总结 (定期)
type SegmentSummarizer struct {
    segmentSize  int  // 默认 50 轮
    triggerMode  string // "count" | "time" | "close"
}

// Layer 3: 元总结 (会话关闭时)
type MetaSummarizer struct {
    maxSegments  int  // 最多合并 10 个段落
    includeEvolution bool // 是否包含演进路径
}
```

#### 3.2.2 触发时机

| 层级 | 触发时机 | 输入 | 输出 |
|------|---------|------|------|
| Window | 每完成 10 轮 | 最近 10 轮消息 + 前窗口摘要 | 窗口摘要 |
| Segment | 每完成 50 轮或会话暂停 24h | 最近 5 个窗口摘要 | 段落摘要 |
| Meta | 会话关闭 | 所有段落摘要 | 元摘要 (存入 session_summaries) |

## 六、风险与缓解

### 风险1: 长会话分层总结性能开销
**缓解**: 
- 异步处理，不阻塞主流程
- 分层存储，只在需要时加载
- 设置最大层数限制

### 风险2: 本地模型质量不足
**缓解**: 
- 保留云端备用方案
- 设置质量监控指标
- 人工抽样审核

### 风险3: 数据库迁移影响生产
**缓解**: 
- 所有迁移 idempotent
- 新增列带 DEFAULT
- 零停机迁移策略

### 风险4: 相似度检测误判
**缓解**: 
- 设置合理阈值 (0.85)
- 人工审核队列
- 提供手动纠正接口
