## 2. 复核发现的新缺陷

### 2.1 标记到了 API，却没有到达消费者

第四轮给 `user_profile.list` 的降级加了 `degraded: true` + 原因。
但前端 `api/admin.ts` 的返回类型里**根本没有 `degraded` 字段**，
`UserProfileListView.vue` 也从不过问。于是：

| | 修复前页面显示 |
|---|---|
| 后端 200 + 降级 | 空表格 +「没有用户」 |
| 后端 200 + 真的没有 | 空表格 +「没有用户」 |

**产出正确，但没到达消费者。** 本轮补上类型 + 消费 + 渲染。

### 2.2 `UserProfileListView` 把三种情况渲染成同一张页面

```js
} catch {          // ← 无参 catch，连 console 都进不去
  users.value = []
}
```

① 请求成功确实为空 ② 后端降级 ③ 请求 500 —— 三者渲染结果**完全相同**。
第 ③ 种尤其糟：它把 console 错误也吞了，而本任务的原始要求之一正是
「逐页检查 console 错误并修正」。

修法：catch 记 console **且** 展示给用户；降级/失败时**不得显示**
「没有用户」——那句话是把「不知道」讲成「知道」。

### 2.3 契约 C 的日期控件判据认不出本仓自己的日历组件

`DATE_FILTER_RE` 只认 `el-date-picker` / `daterange` 一族，
**不认 `KxDatePicker`，也不认 `type="month"`**。实测 5 个已接
`KxDatePicker` 的视图被判「日期✗」。

判据对产品实际形态失明 ⇒「列表需要日期选择控件」这条要求在这些页面上
**根本无法被验证**。修后缺日期控件 51 → 46。

## 8. T1：19 处 42P01 的逐条定性

判据是「**该降级是否会被页面当成真值**」，不是「降级是否语义正确」——
后者往往站得住，前者才是缺陷。

### 8.1 真正被当成真值的：5 处（已修）

| 端点 | 修前载荷 | 消费方 | 危害 |
|---|---|---|---|
| `GET /api/usage/hot-keys` | `[]` | `DashboardView` 抽屉 | 「没有热点 key」实为视图未迁移 |
| `GET /api/usage/by-model` | `[]` | 同上（抽屉模型页） | 同上 |
| `GET /api/usage/by-provider` | `[]` | `BoardProviderSection` / `ProviderUsageExplorer` | 「无供应商用量」实为降级 |
| `GET /api/admin/usage/trend-series` | 空 `series` | 看板趋势卡 | 图表零值被读成「这段时间零用量」 |
| `GET /api/admin/usage/trend-models` | 空 `models` | 模型下拉 | 下拉空 = 「没模型可用」 |

**结构性问题**：前三个返回的是**裸 JSON 数组**，而数组没有位置放字段。
这不是「忘了加字段」，是**载荷形状本身让标记无处安放**。

修法：新增 `admin.DegradedListResponse{items, degraded, degraded_reason,
missing_view, hint}`（恒发 `degraded`，无 omitempty），
三个端点改返回该信封；两个趋势端点在既有结构体上加同名字段。
前端新增 `unwrapDegradedList()` 解包，4 个消费方全部改用 `.items`，
并在三处**抑制了空态**——降级时显示原因而不是「暂无数据」
（把「不知道」讲成「知道」比不显示更糟）。

### 8.2 确实不该当真的：其余已定性

- `usage.go` / `usage_credits.go` 的 summary、dashboard 两处**原本已带标记**
  （`degraded` + `missing_view` + `hint`），第 5 轮表格里「前端未消费其空列表」
  这条理由对它们不成立 —— 已从范围表删除这两个文件。
- `dashboard_board_queries.go` / `dashboard_board_aux.go`：降级后**转走
  request_logs 回退路径**，返回的是真实聚合值而非空值，页面不会误判为真值。
  真正的问题在别处（回退路径本身的正确性），不在标记。
- `aggregate_read_guard.go` / `session_analytics_mv_guard.go`：内部守卫，
  不产出页面载荷。
- `dashboard_degrade.go`：机制定义文件。

## 9. 判据自身的两处盲区（本轮新发现）

前一轮修完「门漏 42P01 一族」后，本轮复核发现**那扇门自己还有两个洞**。

### 9.1 递归盲区：门根本没扫过子包

`TestDegradePayloadsCarryMarker` 用 `os.ReadDir(".")` 单层列举，
`dashboardapi/` 与 `dashboarddegrade/` 两个子包**完全不在扫描范围内**。
实测子包有 **12 处** 42P01 判定，第五轮的「19 处」一条都没算进去。

改法：换成 `collectGoFiles()` 递归遍历（`filepath.WalkDir`，排除
`testdata` 与隐藏目录，结果排序让报错稳定），范围表键改成相对路径。

⚠️ 子包那 12 处**并非真缺陷**——它们统一走各自的 `writeDegraded`
（内含 `Metadata{Degraded: true}`）。但「门是绿的」与「门扫过那些文件」
是两件事；非递归遍历把后者的缺失伪装成了前者的成立。

### 9.2 口径盲区：「19 处」这个数字本身是错的

范围表用 `strings.Count(code, helper)` 计数，会把**判定函数体**也算成降级站点：

```go
func isMissingSessionDim(err error) bool {
    return dashboarddegrade.IsMissingRelationError(err) && ...
}
```

这是谓词，不是「写出降级载荷的站点」。`session_active.go` 因此被报成
「2 处 42P01 但只调了 1 次 `writeDegraded`」——把一个谓词说成了一次绕过标记的写入。

改法：抽出 `countDegradeSites()`，与 `findUnmarkedDegradeSites()`
用**同一套**排除规则（跳注释、跳 `func ` 声明行、跳 `return ` 判断式）。
**两个门用同一套口径**，否则就会出现「一个门数站点、另一个门找标记」
而两者元素集合不相交——那正是本轮最初写出的 bug。

**现行计数：22 处 / 11 个文件**（第五轮口径下是 19 处 / 8 个）。
数字变化来自两处修正：递归 +12，口径修正 −9（去掉定义文件与判定函数）。

### 9.3 换来的新门（全部带反向对照）

## 16. 补上 T3 暴露的判据空档：「渲染得少」原本无人管

第 14.5 节记下：T3 的 B 组批量跑里 `/dashboard` 只有 97 个元素，
而隔离复跑是 1836。当时我判断那是瞬时态、没有深究。
**本轮回头查了，发现那不是孤例——它是一类漏网的真实缺陷。**

### 16.1 空档有多大

判据里与「内容多少」有关的只有一条：

```js
const hollow = results.filter(r => !r.p0.length && !r.p1.length && r.textLen < 120)
```

单一绝对阈值 120 字。而 `reports/final*.json` 四轮实测：

| 轮次 | `/dashboard` scanned | textLen | P1 | 旧判据结论 |
|---|---|---|---|---|
| `final.json` | 1866 | 4126 | 0 | 干净 |
| `final2.json` | 1860 | 4139 | 0 | 干净 |
| `final3.json` | **141** | **768** | **0** | **干净** ← 少渲染 92% 被放过 |
| `final-clean.json` | 1861 | 4102 | 0 | 干净 |

`final3.json` 那一轮，`/dashboard` 只渲染出 141 个元素（同页正常 1861），
因为 768 > 120，**被算进了「干净」**。
那一轮的「64 路由干净」结论里，就藏着一张没渲染出来的看板。

同类二态翻转还有三处（同样在四轮之间反复）：

| 路由 | 两种取值 |
|---|---|
| `/` | 1861 ↔ 141 |
| `/routing-v2` | 57 ↔ 2259 |
| `/admin/proxy` | 344 ↔ 12 |

⇒ 这些页面在**同样的代码上本来就会时好时坏**，而旧判据一次都没报。

### 16.2 为什么不能用绝对阈值

同一批 54 条路由的 `scanned` **跨路由差四个数量级**（0 … 56038）：

| 阈值 | 命中条数 |
|---|---|
| `scanned < 200` | 21 |
| `scanned < 500` | 26 |
| `scanned < 1000` | 32 |

⇒ 任何单一绝对阈值都会把二三十条真实页面判成「可疑」。

## 13. T4：两数据源的「覆盖行集」（本轮已核，含一次自我纠正）

第 7 节记的盲区是「只核了 cost 口径一致，没核覆盖的行是否一样」。
本轮对 `request_logs_with_current_month` 这对 hot/冷数据源做了实测。

实测环境：本地 `llm-gateway-pg-amd64`（kx-citus-pg17），2026-10-03 20:4x。

### 13.1 结论：覆盖行集一致，`UNION ALL` 不会重复计数

| 检查 | 结果 |
|---|---|
| `request_logs_hot` id ∩ `request_logs` id | **0 行**（两腿行集不相交） |
| hot 的 ts 范围 | 2026-10-03 12:31:29 → 20:48:18 |
| 母表的 ts 范围 | 2026-09-03 15:28:04 → **2026-10-03 12:30:03** |
| 边界关系 | **首尾相接、不重叠**（母表止于 12:30:03，hot 起于 12:31:29） |

这正是 `UNION ALL` 成立的前提：两腿在**时间轴上互斥**，
所以既不会漏（无空档）也不会重（无交集）。
迁移函数 `promote_request_logs_hot_to_partition` 的职责就是把过期行
从 hot 搬进母表分区，搬完即从 hot 删除——行集守恒靠的就是这个。

### 13.2 曾经存在的数据丢失缺陷，上游已修（2026-08-25）

`sql/migrations/startup/341_hot_table_independence.sql` 里的旧实现是：

```sql
DELETE FROM request_logs_hot WHERE id IN (SELECT id FROM _promote_hot_batch);
BEGIN
  INSERT INTO request_logs SELECT * FROM _promote_hot_batch ON CONFLICT ...;
EXCEPTION WHEN OTHERS THEN
  RAISE WARNING '... rows preserved in hot table', SQLERRM;   -- ← 谎报
END;
```

`DELETE` 在异常子块**之外**，而 `SELECT *` 位置对齐在两表列集漂移时
必然失败 ⇒ 每批都被 `DELETE` 掉又没插进母表，**整批静默丢失**，
而那条 WARNING 还宣称行已保留在 hot 表。

`deploy/sql/schemas/baseline/01-schema.sql:3683` 的注释确认上游已改为
**单条 data-modifying CTE**（delete 与 insert 原子提交，错误向上抛），
并改为显式列名以防再次错位。

> 本轮独立发现该缺陷后**未改任何代码** —— 核对时发现 baseline 已是修复版。
> 这与第 7 节同型：上游写得比本轮更早也更好。

### 13.3 一次自我纠正：我的第一版算式是错的

我最初按「视图行数 − (hot + 母表) = 超额」去核对，得到 167,113 行差额，
一度像是要报「视图比两腿多出十几万行」的缺陷。

**那个算式本身错了**：线上部署的视图定义远比迁移 459 的两腿版本复杂，
`pg_get_viewdef` 实测它还 `UNION ALL` 了 `session_turns_hot` /
`session_turns`（实测 784 / 1,686,637 行），并对 session_turns 做了 LEFT JOIN。
拿两腿去减一个四肢的构造，差额当然对不上。

教训与第 8 节同源：**「门是绿的」与「门量的是我以为的那个东西」是两回事**。
量总体之前先确认总量本身的定义——`pg_get_viewdef` 看到的才是真实部署形态，
迁移文件里写的是「某次重建时的形态」，两者会长期不一致。

### 14.4 决定：不改默认行为，只把开关和归因留下

理由是证据不支持动它：

## 19. 查到底的结果：4 个文件里藏着 2 处真缺陷

| **`dashboard_board_fallback.go`** | — | ⚠ **这里有真缺陷，而且不在「标记」上** |

第五轮表格给的统一理由（「载荷形状与前端展示未定」）把 4 个文件混为一谈，
而它们的 42P01 后果**根本不同**：前三个要么写 503、要么已被上轮修掉，
第四个是**静默把错误变成空数组**。

### 19.1 缺陷 A：`fallbackBoardPies` 逐维度静默吞错

`admin/dashboard_board_fallback.go`（修前）：

```go
for key, dimType := range types {
    items, err := h.fallbackDimPie(ctx, tenantID, tr, dimType)
    if err != nil {
        out[key] = []boardPieItem{}   // ← 错误在这里消失
        continue
    }
```

七个维度各查一次，**任何一个失败都只留下一个长度为 0 的数组**。
42P01（聚合视图未迁移）与「这段时间真的没有任何客户端」
产出**逐字节相同的载荷**。

消费方 `BoardDistGrid.vue` 把每个维度画成一张排行榜卡，
`items.length === 0` 走的是「暂无数据」分支 —— 用户读到的是
「这段时间没有任何客户端」，真相是「没算出来」。

这与 §8 那 5 处裸数组降级、§17 的 credits 降级显示 0 完全同型，
但**位置更深一层**：前面几处降级在 handler 边界就返回了，
这里是**在函数内部就吞掉了**，所以 `resolveBoardPies` 的 error 返回值
**永远为 nil**，调用方根本没有机会知道发生过降级。

### 19.2 缺陷 B：`dashboard_board.go` 用 `_` 丢弃错误

```go
pies, _ := h.resolveBoardPies(ctx, filterTenant, tr)
trends, _ := h.resolveBoardTrends(ctx, filterTenant, tr, providerID)
```

即使 A 修好并让 `resolveBoardPies` 返回错误，这两行也会把它丢掉，
`pies` 变 nil、`trends` 变 nil，载荷里没有任何痕迹。
`resp` 里 `"pies": nil` 序列化成 `null`，前端 `?? []` 之后
又是「空数组 = 没有数据」。

**A 与 B 必须一起修**：单修 A 的话降级信息到不了载荷；
单修 B 的话没有信息可传。

### 19.3 修法

- `fallbackBoardPies` 改为返回 `(pies, boardPieDegradation, error)`，
  逐维度记账 `Keys` 与 `MissingView`；**仍发空数组**
  （前端 `?? []` 兜底与既有渲染路径不变），只是把事实记进账本。
- `resolveBoardPies` 透传账本。
- 新增 `applyBoardDegradation(payload, pies, trendsErr)`：
  恒发 `degraded` / `degraded_pies` / `degraded_trends`（**无 omitempty**）。
- handler 与 `buildBoardPayload`（Redis 缓存路径）**两侧都调用**它。

为什么饼图要单独一套而不是复用 `degradedList`：
饼图的降级是**部分**的 —— 六个维度算得出来、第七个算不出来。
整体置 `degraded=true` 会让页面把好的那六个也标成不可信，
所以 `degraded_pies.dimensions` 列的是**具体维度名**。

### 19.4 前端消费（否则又是一次「产出正确但没到消费者」）

`board.ts` 导出 `isBoardPieDegraded(board, dimension)`，判据**刻意不看
items 是否为空**：空列表在正常情况下完全合法（真·没有新客户端），
只有服务端点名了这个维度才算降级。

`BoardDistGrid` / `BoardModelDist` 在降级格显示原因而非空态，
用 warning 色（**刻意区别于 muted**：空态是「确实没有」，降级是「不知道」）。

### 24.1 缺陷：下钻失败被讲成「没有错误」

`BoardDistGrid.vue` 的错误下钻（修前）：


用户点开某个错误类型的「下钻」，**意图是看这个错误由什么造成**。
后端 `handleDashboardBoardErrorDrill` 失败时走 `writeInternalErr`

⇒ **用户点开「错误下钻」是为了看错误，屏幕上写的是「没有错误」**。

判据用的是与 T1/T2b 完全相同的那个：「这一处失败，页面会不会把它
渲染成一条**事实**」。会，就修。

### 24.2 修法

`errorDrillError` 状态 + 模板 `v-else-if="errorDrillError"` 分支，
`role="alert"`，danger 配色（**刻意区别于 muted**：空态是「确实没有」）。
文案带出服务端给的 `error.detail`；取不到可读原因才退回通用文案。
i18n 新增 `board.drillFailed` × 8 语种。

### 24.3 判据：4 例三态 + 4 次变异（第 3 次逃过，且逃得有价值）

`BoardDistGrid.drillFailed.test.ts`（4 例）：

| 例 | 断言 |
|---|---|
| ① 请求失败 | 出现失败态、**同一面板内**不含「暂无数据」、带出服务端原因 |
| ② 成功有数据 | 渲染行，无失败态 |
| ③ 成功但为空 | 显示「暂无数据」，**无**失败态（防反向 bug） |
| ④ 重试失败 | 失败态出现，且**上一次的行不再显示** |

变异：

| # | 变异 | 结果 |
|---|---|---|
| 1 | `catch` 退回 `{ errorDrillItems.value = [] }` | ✅ 2 红 |
| 2 | 删模板失败态分支、保留错误状态（有状态没消费者） | ✅ 2 红 |

**加载期间旧行被 loading 分支遮住，失败态也遮住**，旧行泄漏在当前模板下不可见。

⇒ 那行清空在**今天不承担风险**，抽掉它不报红不是判据失效，
是**判据选的维度（渲染结果）看不见它** —— 而那正是它当前安全的原因。
我把它连同这段推理一起写进代码注释，并写明它是防「将来把 v-else-if 链

> **与 §21、§20 的元教训同族，但这一条更细一层**：
> 前两次是「判据红了而产品没问题」「判据漏了接线」；

> 绿灯在这里**不是恒绿，也不是缺陷**——它准确描述了「当前模板结构

> 这个判断的依据是探针，不是推理。**

| **`request_status` 白名单** | 见下 | ⚠ **两条路径确实不同** |

### 26.2 实测差异：0.27%，且是**设计选择**不是缺陷

同一时间边界下逐项隔离（避免把窗口差异误算成口径差异）：

```
all_status 77,117 | whitelisted 76,910 | excluded 207 | minute_requests 70,266
```

被排除的 207 条是什么：

| status | 条数 | 性质 |
|---|---|---|
| `in_progress` | 1619（全 30 天）/ 179（近 7 天） | **进行中**，尚未产生终态结论 |
| 空串 | 46（全 30 天）/ 0（近 7 天） | 状态未落 |

关键代码事实：

- 回退路径 5 处明细查询**都有** `request_status IN ('success','failure','rate_limited')`
- minute 路径读聚合表，`Requests` 在写入时就是**无条件 +1**
  （`domains/stats/minute_entry.go:103`），只在 `SuccessCount`/`FailureCount` 上分档

⇒ 排除 `in_progress` 是**正确的**：它没有终态结论，
且长请求 `ts` 落在过去但仍在跑（实测 9-26 有 315 条、近两天降到 15/44，
与「当天在跑的长请求」这个解释一致），计入会让「已完成请求数」虚高。

**所以这不是缺陷，而是一个「必须钉住的契约」**：真正的风险是将来有人
「顺手统一」——给 minute 也加白名单会把 `in_progress` 丢掉；
把回退白名单放宽会把未落状态的行算进去。两者都是把两件不同的事混成一件。

## 32. 完成度审计后的返工：验证者指出的三处作用域缺陷

§30 标记完成之后，独立验证返回了三处**真实缺口**。全部属实，
而且第三处正是我自己在 §17 埋下、却一直没接到消费端的那一环。

### 32.1 缺陷一：`degraded_reason` 被覆盖

`dashboard_board_queries.go` 的两个降级分支写**同一对**载荷顶层键：

```go
if scanErr != nil {
    payload["degraded"] = true
    payload["degraded_reason"] = view              // ← 整屏降级原因
}
if creditsDegradedView != "" {
    payload["degraded"] = true
    payload["degraded_reason"] = creditsDegradedView   // ← 覆盖上面那个
}
```

两者同时发生时，整屏降级原因被积分原因**覆盖丢失**。

### 32.2 缺陷二：`degraded` 布尔作用域混淆

前端 `BoardHeroRow` 的积分判据是 `summary.degraded === true`。
但 `degraded` 在载荷顶层是 **board 整体**（pies/trends）的标记 ——
于是**整屏 pies 降级、数字完全正常**时，积分卡也会写「此数不可信」。

§8.1 修 credits 时我读的是 `summary.degraded`，
而 §19 我把同一个键用在了 board 顶层。两个作用域共用一个键，
**两边单独看都合理，合起来就互相污染**。

### 32.3 缺陷三：`degraded_summary` 从来没有前端消费

这是「产出正确但没到消费者」的最后一环：后端自 §17 起就写
`degraded_summary`，而前端 `BoardSummary` 类型里**根本没有这个字段**，
首屏照常显示「总请求 0 / Token 0 / $0.00」。

**这是整个看板最不该骗人的一屏** —— 用户会据此判断
「这段时间没有流量」，甚至去排查业务。

### 32.4 修法：按作用域拆键

| 键 | 作用域 | 前端消费点 |
|---|---|---|
| `degraded_summary` / `summary_missing_view` / `summary_hint` | 整个 summary | `BoardHeroRow` 首屏横幅（新增） |
| `credits_missing_view` / `credits_hint` | 其中一个指标 | `BoardHeroRow` 积分卡（判据收窄到只看它） |
| `degraded` / `degraded_pies` / `degraded_trends` | 载荷顶层（board 整体） | `BoardDistGrid` / `BoardModelDist` |

- 整屏分支不再碰顶层键；credits 分支的 `degraded_reason` 加 `"credits: "` 前缀。
- `creditsDegraded` 由 `summary.degraded` 收窄为 `!!summary.credits_missing_view`。
- 新增 `summaryDegraded` + 首屏横幅（`role="alert"`、`grid-column: 1/-1` 跨四列）。
- i18n 新增 `v2.summaryDegraded` × 8 语种。

### 32.5 判据：`TestBoardSummaryDegradationScopeIsolated` + 5 例前端三态

**为什么之前没发现**：`TestBoardFallbackErrorsPropagate` 只查
`degraded_summary` 这个键**在不在**，完全没查**作用域**。
键在、但与另一个作用域共用同一对顶层键，照样过。

新判据断言的是「整屏降级分支**不碰**顶层键」，且依赖
「credits 分支」作为范围切片的边界（找不到它就 `t.Fatal` 判据失效）。

反向对照三次，全部报红：

| # | 变异 | 结果 |
|---|---|---|
| A | 整屏分支写回 `degraded` / `degraded_reason` | ✅ 红（点名两个后果） |
| B | `creditsDegraded` 退回读 `summary.degraded` | ✅ **2 红**（④⑤ 作用域边界） |
| C | 删横幅分支、保留 `summaryDegraded` 计算 | ✅ 红 |

变异 C 的失败信息本身是证据：渲染出的是
`总请求0 … 总费用$0.00000 … 按定价 × token 计算` —— 一屏 0，
没有任何一个字说明「这是没算出来」。

> **本轮的元教训**：§19 引入 board 顶层 `degraded` 时，
> 我核了「调用方有没有调」「实参是不是零值」，
> 却没核**这个名字在载荷里是否已经被别的作用域占用**。
> 同一个名字在两处合法用法下各自成立，合起来互相污染。

### 37.2 缺陷：`BoardUsageTrendSection` 把降级画成「零用量」

```js
const resp = await getUsageTrendSeries(...)
series.value = resp.series ?? []      // ← degraded:true 时空序列被当真值
```

后端 200 + `degraded:true` + 空序列，图表画一条零线，
用户读到「这段时间一点用量都没有」——而真相是「聚合视图没迁移，没算出来」。

**它为什么躲过所有既有判据**（这一条最值得记）：

| 侧 | 状态 |
|---|---|
| 服务端 | 对（有标记、恒发、无 omitempty） |
| 前端类型 | 对（`api/usage.ts` 声明了 `degraded`） |
| 组件 | **不报错**，图表照常渲染 |
| 契约测试 | 只检查「载荷带标记」，**不检查有人读** |

从**任何一侧**看都自洽。这与 §33 的「providers 维度漏消费」同族，
但更深一层：那次是**同一个概念下少一个分支**，
这次是**整个降级链路的后半段从未存在过**。

### 37.3 修法

`seriesDegraded` / `seriesMissingView` 状态 +
`trend-sec__degraded` 分支（`role="status"`、warning 配色）。

**判据刻意只认 `resp.degraded`，不从 `series.length === 0` 推断** ——
那正是 T1 要挡的形状（空序列有两义：真的零用量 / 没算出来）。

配色也刻意区别于 `.trend-sec__err`（danger，请求失败）：
**降级是「请求成功但数据源缺失」，失败是「请求本身失败」**，
两者的排查方向完全不同。

i18n 新增 `usageTrend.degraded` × 8 语种。

### 37.4 新增一道**端到端闭环门**（这才是根本判据）

`web/src/hooks/degradeConsumersParity.test.ts`（3 例）：
列出 8 个「后端已自报降级」的端点，逐个断言**至少有一个非测试文件
真的读了那个字段**，并另有一条「消费点文件必须真实存在」
（清单与现实不符时红，而不是静默跳过）。

> 这道门把 §19/§33 的「手工维度对账」升级成**常驻判据**。
