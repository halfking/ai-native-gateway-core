## 0. 一句话

上一轮声称「已修 usage_enhanced 的静默全 0」。本次复核发现：那句话
**对自己的文件都不成立**——同文件里第三个同形状的降级点被漏掉了；
而且降级标记虽然到了 API 层，**没有任何前端消费者**。

## 1. 复核推翻的两句既有结论

### 1.1 「P0 0 / P1 0 / 干净 63」是对当前部署态成立的

**不成立。** 那份扫描跑于 15:17，而 `UsageCost.vue` 改于 16:58、
`ui-audit.mjs` 改于 16:42。**报告比被审计对象旧了 1.5 小时。**

「报告是绿的」与「被测物是那个版本」是两件事。本轮补跑了干净扫描。

> 教训：任何运行时结论都必须带上**被测构建的时间戳**，否则「绿」只是在
> 描述一个已经不存在的东西。

### 1.2 「本轮已修降级载荷」对自己文件都成立

**不成立。** `degrade_marker_test.go` 只扫 `IsSchemaBehindError(`，
于是漏掉了同文件内 `usageCostTrend` 的 **42P01** 降级点：

```go
// admin/usage_enhanced.go:202（修复前）
if IsMissingRelationError(err) {
    ReportMissingRelation(...)        // ← 返回值被丢弃
    writeJSON(w, 200, CostTrendResponse{ Entries: []CostTrendEntry{}, ... })
}
```

用户看到的是**一张空饼图 + total_cost 0**，和另外两个端点形状完全一致。
把门扩到两个 helper 家族后才暴露（`degrade_marker_test.go` 的
`degradeHelpers`）。

> 教训：只扫一族却宣称覆盖两族，比不扫更坏——它制造了「已覆盖」的错觉。

## 2. 复核发现的新缺陷

### 2.1 标记到了 API，却没有到达消费者

第四轮给 `user_profile.list` 的降级加了 `degraded: true` + 原因。
但前端 `api/admin.ts` 的返回类型里**根本没有 `degraded` 字段**，
`UserProfileListView.vue` 也从不过问。于是：

| | 修复前页面显示 |
|---|---|
| 后端 200 + 降级 | 空表格 +「没有用户」 |
| 后端 200 + 真的没有 | 空表格 +「没有用户」 |

**产出正确，但没到达消费者。** 本轮补上类型 + 消费 + 渲染。

### 2.2 `UserProfileListView` 把三种情况渲染成同一张页面

```js
} catch {          // ← 无参 catch，连 console 都进不去
  users.value = []
}
```

① 请求成功确实为空 ② 后端降级 ③ 请求 500 —— 三者渲染结果**完全相同**。
第 ③ 种尤其糟：它把 console 错误也吞了，而本任务的原始要求之一正是
「逐页检查 console 错误并修正」。

修法：catch 记 console **且** 展示给用户；降级/失败时**不得显示**
「没有用户」——那句话是把「不知道」讲成「知道」。

### 2.3 契约 C 的日期控件判据认不出本仓自己的日历组件

`DATE_FILTER_RE` 只认 `el-date-picker` / `daterange` 一族，
**不认 `KxDatePicker`，也不认 `type="month"`**。实测 5 个已接
`KxDatePicker` 的视图被判「日期✗」。

判据对产品实际形态失明 ⇒「列表需要日期选择控件」这条要求在这些页面上
**根本无法被验证**。修后缺日期控件 51 → 46。

## 3. 已明确划出的范围边界（带数字）

`IsMissingRelationError`（42P01，可选视图未迁移）在 admin 包内共有
**19 处 / 8 个文件**，本轮**不纳入** degraded 契约：

| 文件 | 理由 |
|---|---|
| `dashboard_degrade.go` | 本机制的定义文件，不产出页面载荷 |
| `aggregate_read_guard.go` / `session_analytics_mv_guard.go` | 内部守卫，不直接产出页面载荷 |
| `dashboard_board_queries.go` / `dashboard_board_aux.go` | 看板载荷形状与前端展示口径未定 |
| `usage.go` / `usage_credits.go` / `usage_trend_series.go` | 多端点共用载荷形状，前端未消费其空列表 |

不定性的理由：这些降级在**语义上更站得住**（真的没有数据源，而不是
算不出来）。但页面上同样与「没有数据」同形。

**关键是登记了计数而不是登记「已覆盖」**：`degrade_marker_test.go`
每次运行都会输出「已登记但未纳入 degraded 契约的降级点：N 处（M 个文件）」，
且范围表两边都卡（表里有而代码里没有、或反之，都会红）。下一轮从确切
数字起步，而不是从零重新搜索。

## 4. 兄弟项目同步（本轮补做，附证据）

原始目标要求「接入的页面有部分是 ai-session-manager 及
ai-native-maintain 中的，也需要同步修正」。此前只验证过它们
「工作树干净且与 origin 同步」——**那不等于页面级修正已到位**。

本轮实跑三仓的门：

| 仓库 | selftest | 契约 A | 契约 B | strict |
|---|---|---|---|---|
| `llm-gateway-go-3/web` | exit 0 | 0 | 0 | exit 0 |
| `ai-session-manager/web` | exit 0 | 0 | 0 | exit 0 |
| `ai-native-maintain/maintain-web` | exit 0 | 0 | 0 | exit 0 |

并把 `DATE_FILTER_RE` 的修正**同步到两个兄弟仓**。它们当前尚未使用
`KxDatePicker`（实测 0 处），所以在它们那里是**潜伏**而非已发作；
但三仓各持一份脚本副本，只要有人接入统一日历组件就会踩中。
两个兄弟仓同样做了变异自检（移除形态 → 自检拒绝放行）。

## 6. 本轮遗留（带证据，不粉饰）

1. **扫描器 `domcontentloaded` 导致的间发 P1 假阳性。**
   本轮 18:0x 那次扫描在 `/dashboard` 报 4 条 `net::ERR_ABORTED`
   （`/api/admin/live-stream`、3 条 `/api/routing/resolve`）。
   独立探测（沉降 6s）显示 **requestfailed = 0**，相关 75 个响应全 200。
   判定为页面拆除时飞行中请求被中止，非产品缺陷。
   ⚠️ 样本量为 1（15:17 那轮 P1=0，本轮 P1=1），属**间发**，不排除偶发真失败。
   **本轮不改扫描器**：改等待策略会动到全部 64 条路由的判定，
   风险大于收益。留给下一轮单独评估。

2. **约 100 处 `catch {`** 分布在 views 下，其中数据加载类静默吞错的
   数量未逐一核查。已修 1 处（`UserProfileListView`）。
   其余未动——全改是巨大范围扩张。本条**没有完成度可报**。

3. **19 处 42P01 降级未纳入契约**（见第 3 节，带计数与范围表）。

4. `work_type` 维度 98% 落在 `unknown`（实测 475,914 / 5,748 / 1,940），
   数据为真但信息量低；它不在 UI 下拉框，仅作 API 能力。

## 7. 合并上游时发现：我上一轮写得不如上游

推送时远端已被并行工作推进 30+ 提交，合并后发现上游改了
`admin/usage_enhanced.go` 的 cache-economics 压缩计数查询——
**上游的版本比我的正确**：

| | 我写的 | 上游写的 |
|---|---|---|
| 表 | `FROM request_logs rl` | `FROM request_logs_with_current_month rl` |
| 问题 | **裸母表读不到最近 8h**（hot 分区仅保留 8h）⇒ 当月面板是真盲区 | hot∪母表双腿视图，两腿都吃 ts 谓词下推 |

我上一轮只核了「两表 cost 口径一致」，**没核「两表覆盖的行是否一样」**。
成本对得上不代表行集对得上 —— 这是我在第四轮埋下的一个盲区，
由上游在合并时替我补上。

> 教训：核对两个数据源时，「聚合值一致」与「覆盖范围一致」是两条独立的
> 命题。只验前者会漏掉 hot/冷分层、软删除、分区裁剪这类差异。
