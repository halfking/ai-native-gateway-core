## 二、取证中发现并根修的两个网关缺陷

### Defect-1（严重）：大请求体入口归约平方级耗时 ⇒ 120 秒超时

**现象**：ZCode/3.19.1 的 7,757,461 字节 `/v1/messages` 请求（glm-5.3-flash）在 14:02–14:13 UTC 连续 6 笔、每笔**恰好 120.01 秒**后 503（`request_processing_timeout`），路由日志为零——卡在 `LargeIngress` 入口归约（>256KB 即触发 `sessioncontext.Reduce`，预算 120s）。同一会话 1.18MB 的请求每笔也要白等约 2.2 秒。

**根因（211 真机用真实归档请求体 + 真实规则集复现并采 profile）**：`Reduce` 带历史守卫耗时 **128~141 秒**，其中 **95.7% 在 `largebody.(*compressedFile).ReadAt`**——

- `compressedFile.ReadAt` 用顺序解压模拟定位读取：「往回读」一律**回卷到文件开头重放到目标**（注释自述 "inefficient for random access but maintains correctness"），代价 O(偏移)。帧格式本就是「每 64KiB 一帧、帧帧独立」，随机访问这一半从没实现。
- `Reduce` 对每条历史消息给守卫开 3 个以上独立 reader，每个都是归档 `SectionReader`，而归约器共用一个文件游标 ⇒ 每次 reopen 都是一次「往回读」⇒ 3953 条消息 × 约 8 次回卷 × 平均解压 3.8MB ≈ **118GB zstd 输出**，与会话长度呈平方级。profile 分解：zstd/huff0 90.4s、GC 46.5s、syscall 16.7s、正则仅 3.6s。

**修法**（两层各自独立钉住）：

| 层 | 改动 |
| --- | --- |
| `internal/largebody` | 懒建**帧目录**（只读 12 字节帧头、零解压、O(帧数) 次 pread）；回退 / 大跨步前进直接跳到目标所在帧头（`FrameReader.reopenAt` 复用解码器）；小幅前进维持顺序丢弃；目录建不出来退回旧行为。新增 `FramesDecoded()` 作为「重复解压」的确定性量具 |
| `internal/sessioncontext` | ≤64KB 的消息**读一次、全程走内存**（守卫 `open()` 给独立游标的内存 reader）；`query` 的词项只算一次（原先每条消息重算两次） |

**验证**：

- 211 真机、真实归档、真实规则：**128.4s → 5.04s**；归约输出 **SHA-256 新旧逐字节一致**（`c47e3a55…fc28d83`，守卫省略 2269 条不变）。
- 钉测：定位读取逐字节等于源 / 回退 O(一帧)（变异回旧行为 ⇒ 「10 次 reopen 解码 800 帧」红）/ 帧头损坏降级；归约解码帧数与归档帧数同阶（实测 33 帧归档 × 9420 次守卫 open 只解码 101 帧；摘掉内存复用 ⇒ 19133 帧红）。
- 门禁：`go build ./...`、vet、largebody / sessioncontext / contextbudget / sanitize / provider / streaming（146s）/ cmd/gateway 全绿。

### Defect-2：候选为空归因被小计数闸抢头条

`[candidate_diag] db_empty` 按固定顺序报「第一道有命中的闸」：sonnet-5-5 的 11 条 offer 里凭据配额态挡住 8 条、供应商停用 5 条，而 `credentials.manual_disabled` 只沾到 1 条却被报成头条——「解除人工停用标记」，运维照着解一个不相干的标记，模型照样 503。

修法：单闸独占时整句逐字不变；多闸命中时按命中 offer 数降序列出全部闸并标明主因与处置（同数按既有优先序），`cause_class` 取主因闸。线上已验证：新容器启动后的 96 条归因里 35 条多闸场景均为新格式（例：gpt-5.4-mini「凭据配额态 8 条 > 供应商停用 4 条 > … > 人工停用 1 条 ⇒ 主因=凭据配额态」）。

## 五、通用式

1. **「流式解压 + 模拟 seek」是平方级的温床**——任何「多 reader 共用一个顺序游标」的访问模式都会退化；帧式格式既然为随机访问设计，就该真的按帧定位。
2. **归因要按「挡住多少」排，不是按「谁排在前面」报**——多因重叠时，固定顺序会让小计数因抢头条。
3. **客户端报障的模型 ≠ 日志里最显眼的失败**——同一时段另一个真实缺陷（7.7MB 超时）藏在报障模型之外，按「状态码 × 耗时 × 请求体大小」列表才能把它和路由失败分开。
4. **「恢复了」要定责到时间线**——凭据/绑定行的更新时间戳比「部署后好了」可靠。

### 6.1 候选为空（三个协议面）

### 6.2 入口拒绝（LargeIngress）

- **日志句子与客户端句子两分开**（`ingressRejection` + 纯函数 `ingressClientFacing`）：日志/遥测仍是稳定英文（排障与看板的检索锚点），客户端拿到本地化的「事实 + 性质 + 处置」。
- 事实以旁键给机器：`body_bytes` / `preprocess_budget_seconds` / `messages` / `limit_bytes`（仍在既有的 `gateway_debug` 下）。
- 错误 `type` 跟状态码一致（`ingressErrorType`）：此前入口拒绝**一律** `invalid_request_error`——401/403/408/413/429/503 全顶着「请求不合法」；Anthropic 面经 `anthropicErrorType` 映射到 SDK 认识的闭集（新增 413 → `request_too_large`、408 → `request_timeout`）。
- Anthropic 信封补 `code`：共享的 `writeErrorAnthropic` 只拿 code 推导 type、从不输出它——Anthropic 协议的客户端（ZCode）此前拿不到机器可读的错误码。
- **状态码与 retryable 合同不变**：超时＝网关侧处理能力，503 可重试；放不下＝输入问题，422 不可重试（`TestLargeIngressProcessingDeadlineIsRetryable` 钉的合同）。
- 预算 120s 收敛为单一常量 `largeIngressPrepBudget`（行为与文案同源）。

zh-CN 文案（超时）：`网关未能在 120s 内预处理完这个请求（请求体 1.0 MiB (1100128 bytes)）。这是网关侧的处理能力限制，并不是拒绝了你的输入——可以稍后重试。如果反复超时，说明会话历史大到无法在时限内准备好：请新开会话或精简历史。`
