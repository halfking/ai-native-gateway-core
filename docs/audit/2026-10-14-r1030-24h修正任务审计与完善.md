## 二、D1：迁移 862 的守卫腿被无守卫 COMMENT 击穿（真缺陷）

### 2.1 缺陷本体

`sql/migrations/startup/862_partition_family_leading_ts_idx.sql`（f43501d16，2026-10-14
05:xx）给 `session_turns` 与 `_request_logs` 两个分区父表建无谓词 `(ts)` 索引。
创建腿带守卫，注释腿没有：

```sql
DO $build_request_logs_ts$
BEGIN
  IF to_regclass('public._request_logs') IS NOT NULL THEN
    EXECUTE 'CREATE INDEX IF NOT EXISTS idx_request_logs_ts ON public._request_logs (ts)';
  ELSE
    RAISE NOTICE 'migration 862: public._request_logs not found (skip request_logs leg)';
  END IF;
END $build_request_logs_ts$;
...
COMMENT ON INDEX idx_session_turns_ts IS '...';   -- 顶格，无条件
COMMENT ON INDEX idx_request_logs_ts IS '...';    -- 顶格，无条件  ← 击穿点
```

**这不是「守卫多余」，而是「守卫自己被击穿」**：文件头注释亲口写着
「对已按 736 先例预应用（旧名、同名索引）的环境，IF NOT EXISTS 按索引名命中，幂等跳过」，
而**预应用环境恰恰就是 `public._request_logs` 不存在的环境**（它们还是旧名 `request_logs`）。
迁移自己声明要容忍的场景，被自己下一行的 COMMENT 取消。

### 2.2 取证（隔离 PG18 18.6，逐字复现）

```bash
# mktemp 全新实例，零风险隔离；agent 上无 docker，走 initdb + pg_ctl
initdb -D $D/data -U audit --auth=trust -E UTF8
pg_ctl -D $D/data -o "-p 54999 -k $D -c listen_addresses=''" -l $D/log start
createdb ... probe
psql -v ON_ERROR_STOP=1 -c "CREATE TABLE public.session_turns (...);" \
     -f sql/migrations/startup/862_partition_family_leading_ts_idx.sql
```

实测输出（修复前）：

```
BEGIN / SET / CREATE INDEX / DO / COMMIT
NOTICE:  migration 862: public._request_logs not found (skip request_logs leg)
ERROR:  relation "idx_request_logs_ts" does not exist      ← 第 62 行
psql 退出码 3
```

**注意 COMMIT 已经在 COMMENT 之前**——索引是真的建好了，脚本却失败。

### 2.3 影响面（按运行器真实口径判定，不是按感觉）

`installer/internal/dbinit/runner.go:1145 applySQL` 逐文件执行
`psql -v ON_ERROR_STOP=1`，**只按退出码**决定是否记账；`applyMigrationsOnce` 的
自愈链不覆盖这条 SQL 文件。推论：

- 该迁移在这些环境**永远不被记为 applied**，每次启动重放、每次同样失败——
  一个**永久迁移卡点**（而不是一次性抖动）；
- 因为 `IF NOT EXISTS` 已命中，重放**不会**重复建索引，所以不会造成 DDL 风暴，
  也不会把库改坏——这正是它能长期潜伏的原因：索引在、账不在、没人报错到人眼前；
- 命中人群正是迁移注释里点名的「预应用环境」，以及**该族从未建起的新装库**
  （installer 的目标场景）。

另附一处顺带核实（非缺陷，记录以免下轮重查）：862 没有 `dbinit:no-transaction` 标记，
于是 `applySQL` 会给它加 `--single-transaction`，而文件自带 `BEGIN/COMMIT`。
psql 对「已在事务中再 BEGIN」只发 WARNING，`COMMIT` 会提前结束外层事务——所以
COMMENT 实际跑在单语句自动提交模式。两种包裹方式下缺陷结论一致（都非零退出），
但**这解释了为什么索引已提交而退出码仍失败**。

### 2.4 修法

两条 `COMMENT ON INDEX` 与各自创建腿**同守卫**：

```sql
DO $comment_862_indexes$
BEGIN
  IF to_regclass('public.idx_session_turns_ts') IS NOT NULL THEN
    COMMENT ON INDEX idx_session_turns_ts IS '...';
  END IF;
  IF to_regclass('public.idx_request_logs_ts') IS NOT NULL THEN
    COMMENT ON INDEX idx_request_logs_ts IS '...';
  END IF;
END $comment_862_indexes$;
```

PL/pgSQL 里 `COMMENT` 无返回行、可直接执行（已在真库跑通，非纸面推演）。
