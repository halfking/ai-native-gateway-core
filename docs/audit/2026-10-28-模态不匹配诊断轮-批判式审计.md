## 1. 实锤问题清单

### 1.1 诊断 SQL 两处列选择缺陷（潜伏缺陷，本轮核心发现）

`provider/modality_mismatch.go` 的 `modalityMismatchSQL`：

- **缺陷 A（canonical 解析）**：`matched` CTE 选 `mo.canonical_id`。
  一个只能通过 `model_aliases` 解析的 offer（`mo.canonical_id IS NULL`）会被读成
  「未解析」⇒ `resolved` CTE 丢掉它 ⇒ 诊断静默退回 no_candidate。
  **危害形态：保守漏诊**（该 400 的仍 503），不是误诊。
- **缺陷 B（routable 判定）**：`EXISTS` 臂 `JOIN provider_models pm ON pm.canonical_id = m.canonical_id`。
  alias-only offer 的 `provider_models.canonical_id` **本来就是 NULL**——那正是
  「alias-only」的定义——按 canonical_id join 会把**恰好是本诊断要看见的那些行**丢掉。

**为什么说是潜伏**：211 生产当前 0 条 alias-only offer（实测查询空结果），
所以已部署版本今天不会错。但这是数据分布的巧合，不是正确性。

**修复**：
- `matched` 改选 `mc.id AS canonical_id`（= `COALESCE(mo.canonical_id, ma.canonical_id)`，与路由器同源）；
- `EXISTS` 改走 `v_routable_credential_models.binding_id IN (matched.offer_id)`
  （`model_offers.id` 就是 binding id，视图是 cmb ⋈ pm；不再依赖任何 canonical_id 列）。

**两轮红-绿的真实过程（如实记）**：
1. 第一轮只修了缺陷 A，夹具**仍然红**——`routable=false`。
   手工在事务里重放 SQL：`matched` 解析正确（mc 解析到了），EXISTS 仍 false
   ⇒ 才暴露缺陷 B。**「修了一半」是修完不重跑就会带出去的**。
2. 夹具第一版还有自己的缺陷：用 `Client`（连接池）跑诊断，而 fixture 在
   `tx`（另一连接）未提交 ⇒ 诊断**永远**看不见 fixture，测试恒红。
   修法 = 诊断 SQL 直接在 tx 连接上执行。⇒
   ★ **「跨连接的夹具」是隐形单向门：夹具方法本身要先验证「看得见」。**

### 1.2 「判据与路由器逐字同源」的声明过强

上一轮提交说「模态接受表与路由器模态门逐字同源」。审计核对：
- 仓内 `provider/candidate_query_sql_shape_test.go` 用**字面量**锁的是 SQL 里的接受臂；
- 我的 `ModalityAccepts` 是 Go 抄本；我写的交叉测试对拍的是**两份 Go 抄本**
  （`ModalityAccepts` vs 测试里手写的 `routerAcceptsModality`），**没有**
  任何机制锁住「Go 抄本 ↔ SQL 原文」。
- ⇒ 三份表达（SQL 原文 / Go 判据 / 测试镜像），第二三份会一起漂。
  本轮**没有**加自动锁步（成本/收益：SQL 是字符串模板，锁步判据要先做模板
  解析；留给下一轮，见 §5）。声明降级为「**语义同源，靠
  TestModalityAccepts_PinsTheAcceptanceTable + 手工对拍维持**」。

### 1.3 接线守卫缺口（测试文件的测试≠调用点的测试）

上一轮的「协议一致性测试」调的是 `diagnoseModalityMismatch` 共享函数——
**调用点被删/被挪，测试仍绿**（我在上一轮提交信息里承认过这类缺口，但只给
行为测试补了位，没锁调用点）。本轮照仓内先例
（`cmd/gateway/auto_route_wiring_guard_test.go`）补**源码守卫**
`modality_mismatch_wiring_guard_test.go`：三个协议文件的调用必须存在、
且 fallback 标记必须出现在调用之后。

守卫自己的第一版就红了一次：`strings.Index` 从文件头找 fallback，
被 messages.go 里**更早的无关** `overloaded_error`（518 行 session-store 错误）
干扰，把正确顺序报成倒序 ⇒ 修为「从调用点之后开始找」。
⇒ ★ 守卫也要在真实文件上跑过才有资格提交。

守卫变异：改名调用点 ⇒ build failed 被抓（非断言路径，如实记——
「调用点挪到 fallback 之后」这类纯语义变异无法用文本守卫覆盖，留待行为测试）。

## 5b. 合并冲突照出的第四个缺口：缓存键相撞（合并时发现）

推前合并 origin/main 时，并行会话已把 `ModelAlternativesFinder.Find` 重构成
**缓存架构**（key = tenant+taskType，冷/热路径 + 后台刷新）。语义冲突：
- 缓存键不含 modality ⇒ 同一 (tenant, taskType) 下，vision 请求会命中
  「含 text-only 模型」的缓存列表 ⇒ **模态过滤形同虚设**（缓存层直接把它
  绕过去了）；
- 查询缝 `queryFn` 是 4 参 ⇒ modality 传不进 SQL；
- 自动合并还把 `result.RequestedModality` 错误搬进了无 `result` 变量的
  `queryAlternativesSQL`（编译失败才暴露——**文本合并干净 ≠ 语义合并干净**，
  正是 §493 的「git 合干净了 ≠ 语义合干净了」在本轮的实例）。

修法：查询缝加第 5 参贯穿到 SQL 的 $5；缓存键加 modality 维度；补回归钉
`TestFind_CacheKeyIncludesModality`（text+vision 两次必须真查询、同键第三次
必须走缓存——双向：既防过滤被绕过，也防缓存语义回归）。
