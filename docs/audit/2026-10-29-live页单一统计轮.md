## 1. 关键设计：clients 组的数据源（本轮最重要的决定）

stats 事件链**不携带客户端身份列**：Event JSON 有 agent_name/client_profile/
identity_hash，但落 `usage_facts` 时被丢弃（表无这些列）⇒ stats_usage_daily
没有 client 维度。扩日桶维度 = 分区表 DDL + rollup 引擎改动 —— 不为本轮引入
这条风险面（DDL 还需单独授权）。

**落点：客户端组恒直查 request_logs**（`GET /api/admin/topology/clients-today`）：
- day = `ts >= UTC 日桶起点`；5m/1h = `ts >= now()-interval`（窗口家族同款解析）；
- ★ **day 模式以 rollup 水位封顶**（`ts <= MAX(source_max_occurred_at)`）：
  providers/models 组的 day 数字来自 rollup（≤1h 滞后、止于水位），客户端若
  不封顶就会多出最后一小时的量 —— **同一面板三组对不上账**。封顶后三组同界；
  水位 NULL（日桶未就绪）时不封顶（providers/models 本来就是 0，属已知边缘，
  一小时内自愈）；
- 客户端取键与前端 `clientKeyOf` **逐字同款**：agent_name → client_profile →
  client_protocol → identity_hash 前 8 位 → 'unknown'（口径分叉会让「图上 3 个
  客户端、组里 5 行」）；
- 水位查询失败降级为「不封顶」（fail-open，辅助查询不拖垮端点）；
- 水位封顶在**响应回显**（source_high_watermark）—— 对齐了什么可被审计。

## 6. 明确没做 / 如实记

1. **clients 维度不进日桶**（usage_facts 无身份列；扩列 = DDL + rollup 改动，
   独立工程）—— 代价：clients 组 day 数字恒为实时口径（以水位封顶对齐），
   rollup 表里永远查不到历史客户端分布；
2. `theme.logoAssets.test.ts` 2 红未修（上游品牌轮带入，登记不擅动）；
3. 折叠态 / 区间选择仍不持久化（与上一轮一致）；
4. 总量行的在途/排队是**拓扑窗口口径**（与 DB 区间无关），以分隔线 +
   「未测量隐藏」表达两观测层差异，不进一步混算。
