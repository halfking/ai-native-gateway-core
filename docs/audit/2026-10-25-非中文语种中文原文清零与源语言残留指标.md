## 1. 怎么发现的（不是「门报红」，是「门根本没在看」）

起点是上一轮破折号清零留下的一个读数：移动端语言包扫描时发现**非英文语种的值里混着中文原文**。
顺手把同一口径量到 Web 端 `web/src/locales/`，量具是**结构口径**（不是字符口径）：

> **铁证口径**：某语种的值 **== zh-CN 的值** 且 **zh-CN 的值 != en-US 的值**
> ⇒ 该条**不可能**是巧合同形 ⇒ 一定是「键在、值没翻」。

| 语种 | 铁证未本地化 | 值含汉字 | 既有闸门看得见吗 |
|---|---|---|---|
| de-DE / es-ES / fr-FR | 447 | 452 | ✅ `cjkInNonCjkLocale`（棘轮） |
| ar-SA | 447 | 453 | ✅ `cjkInNonCjkLocale`（棘轮） |
| **ja-JP** | **800** | 3533 | ❌ **零覆盖** |
| **zh-TW** | **1209** | 4323 | ❌ **零覆盖** |

**为什么 ja-JP / zh-TW 是零覆盖**：`localeValueQuality.ts` 的 `CJK_NATIVE_LOCALES = {zh-CN, zh-TW, ja-JP}`
把这两个语种从「值含汉字」这道闸里**整体豁免**（理由正当：日文/繁中用汉字是正常的）。
⇒ 但「**整段留了简体原文**」这件事，在那两道闸的视野里根本不存在。

## 2. 口径陷阱（这一段是本轮最有价值的部分）

### 2.1 「与源语言逐字相同」必须限定「源值含汉字」

zh-CN 的值里本来就有 ASCII 术语（`API` / `OAuth` / `Webhook`）。
若口径只判「目标值 == 源值」，这些**跨语种共用术语**会被误判成未翻译：

| 口径 | 每个拉丁语种的命中 |
|---|---|
| 目标值 == 源值（不限源值字符） | 582 ~ 595 |
| 目标值 == 源值 **且源值含汉字** | **447** |

⇒ 差出来的 135~148 条全是**误报**。指标 4 因此必须带这个限定条件。

### 2.2 「含汉字」不能直接判 ja-JP / zh-TW

- **字符表法对日语会误伤**：日文正字里的「号 / 画 / 点 / 状 / 独 / 猫 / 献 / 声」与简体同形。
- **数据推导法对日语被片假名污染**：`模 / 型 / 商 / 查` 在日文里只以片假名外来语（モデル）出现 ⇒ 被误列成「简体独有字」。
- ⇒ 本轮**不给 ja-JP / zh-TW 做精确判据**，只做**可见化登记**（保守口径 + 棘轮），并在文档里如实标注它不是缺陷精确条数。

### 2.3 推导「简体独有字表」时必须过滤非汉字

从数据推导时，统计口径是「字符出现次数」⇒ **全角标点与拉丁字母也会进表**。

| 版本 | 表大小 | 拉丁语种「含简体字」读数 |
|---|---|---|
| 不过滤 | 376 | es-ES **436** / fr-FR **424** ← 样本却是**地道西语/法语**，明显假阳性 |
| **只收汉字** | **374** | es-ES / fr-FR / de-DE / ar-SA 各 **359** ✅ 自洽 |

差出来的 2 个字是全角标点（如 `，` / `·`）——它们在 zh-CN 里出现、在 zh-TW 译文里没出现 ⇒ 被误列。

### 2.4 两套口径必须并列发布

「值与源语言逐字相同」是**保守口径**（含合法同形词）；「值含简体独有字」是**精确口径**（对 zh-TW 有效，对 ja-JP 无效）。实测对照：

| 语种 | 保守口径（== 源语言） | 精确口径（含简体独有字） | 差（合法同形词，看不出翻没翻） |
|---|---|---|---|
| zh-TW | 1363 | **534** | 829 |
| 拉丁 4 语种 | 447 | **359** | 88 |

⇒ **zh-TW 的真实未翻译是 534 条，不是 1363 条**——这就是为什么「报告必须自陈口径」不是形式主义：
同一批数据，两个口径差 **2.5 倍**。

6. 不写空洞形容词 / 不用「不是 X，而是 Y」句式。
7. **不 commit**（由主会话统一验证后提交，避免与并行会话抢提交）。

## 4. 落地：闸禁加第 4 个指标 `sameAsSource`

### 4.1 改了什么

| 位置 | 改动 |
|---|---|
| `web/src/i18n/localeValueQuality.ts` | 新增 `SOURCE_LOCALE='zh-CN'`；`LocaleQuality` 增 `sameAsSource` + 采样；`measure()` 增 `sourceValues` 形参并计算该指标；`measureAll()` 复用**同一份已缓存**的 zh-CN 值表（不额外加载 8 语种，避免门变计时敏感门）；`Baseline` 增 `sameAsSource`；`writeBaseline()` 增棘轮（只许降不许升）；`buildBaseline()` 增该字段 |
| `web/src/i18n/localeValueQuality.test.ts` | 增该指标的棘轮断言 + 基线覆盖断言 + 草稿同形断言；自证用例 8 → **13** 条 |
| `web/scripts/i18n-locale-value-count.mjs` | 输出与比较增 `same-as-source` 一行 |

### 4.2 指标的口径（写死在文件头，读者不用猜）

> `sameAsSource` = 值与**源语言 zh-CN** 逐字相同，**且源值含汉字**。

- **只统计被源码引用的键**（与其余三个指标同一批引用集）。
- **源语言自身不登记**（它与自己逐字相同是恒等式，无意义）；**en-US 登记**（必须是 0 ⇒ 英文界面不得留中文原文）。
- ⚠ **它是指示器，不是缺陷精确条数**：ja-JP / zh-TW 的「保存 / 模型 / 取消」这类**繁简同形 / 通用汉字**会被一并计入；
  而目标语种留了**另一种写法**的原文（少一个字、换了标点）**不被计入** ⇒ 两个方向合起来，它**既不是上界也不是下界**。

### 4.3 自证：量具必须有牙（13 条，双向）

| 用例 | 断言 |
|---|---|
| L9 | 与源语言逐字相同且源值含汉字 ⇒ **计入** |
| L10 | 与源语言逐字相同但源值是 ASCII 术语（`OAuth` 这类跨语种共用）⇒ **不计入** |
| L11 | 源语言没有该键 ⇒ **不计入** |
| L12 | 已本地化（与源语言不同）⇒ **不计入** |
| L13 | 未被引用的「还留着原文」键 ⇒ **不计入** |

⇒ 13/13 PASS。**变异思维**：L10 就是指标 2.1 那条陷阱的固化 —— 若有人把「源值含汉字」这个限定条件删掉，
L10 立刻变红。

### 6.1 ★ 第二类未翻译：**残留英文**（本轮已量出精确口径，可直接开工）

本轮只治了「**中文**原文」。但 4 个拉丁语种里还有另一类未翻译：**值与 en-US 逐字相同**。
其中**合法共用技术术语**（`Provider` / `Token` / `JSON` / `OK` …）与**漏译的界面文案**混在一起，
不能用「与 en-US 相同」直接当缺陷 ⇒ 这里给出一个**可判定的口径**：

> **漏译判据**：某语种的某键值 **== en-US 的值**，而**另外 3 个拉丁语种里至少有一个译成了别的**
> ⇒ 别的语种证明这条**是可以翻的** ⇒ 这个语种**漏译了**。
> （排除空串：空值天然「逐字相同」。）

| **去重并集** | | **739 个键**（至少一个语种漏译） |

3. **移动端 `web-mobile`**：只有 en-US / zh-CN 两个语种 ⇒「8 语言全同步」的承诺目前**只在 Web 端成立**。
4. **视觉验收**：本轮全是文案层改动，**未经浏览器目视验证**；
   译文普遍比中文长（德/法/西语），**存在撑破按钮/列头宽度的风险** ⇒ 下一轮应跑 `ui-sweep` 的溢出检测做一次目视回归。
5. **一个已知未修的边角**：`routing.ts` 里 `canonicalLabel: 'Canonical：'` 用的是**全角冒号 U+FF1A**
   （不是汉字 ⇒ 本轮的口径扫不到），且 **en-US 同一处也是全角** ⇒ 属上游遗留，本轮未动（保持两侧一致）。
6. **ja-JP / zh-TW 里仍有大量「合法汉字」**（ja 7125 条 / zh-TW 8821 条含汉字）⇒ 门对它们**故意豁免**
   （`CJK_NATIVE_LOCALES`）⇒ 若将来要治理 zh-TW 的简体残留，需要的是**第 2 条**那个精确判据，而不是放宽这条豁免。
7. **「同步的扁平键」与嵌套键的措辞差异（存量）**：全语种量到**每个语种约 150 处**
   扁平别名与嵌套键措辞不同（如 `de-DE: common.add` 扁平 `"Add"` vs 嵌套 `"Hinzufügen"`）——
   这类多为**历史遗留**（扁平块由 `fix-all-parity.mjs` 自动生成）⇒ 本轮只修了**本轮引入的**那一处
   （`settings.outputCompliance`），其余留给下一轮连同 §6.1 一起处理。
