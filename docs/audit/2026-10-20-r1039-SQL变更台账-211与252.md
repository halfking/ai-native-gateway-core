### 3.0bis ★ 第二轮（2026-10-21）新增了一条**会跑 DDL 的 boot 自愈**（不是迁移）

第二轮部署在数据库迁移这一步**中止**（审计文档 §1.5），根因是 `db/db.go` 的 boot ensure 链
**自己**要给 `_request_logs` 建带 `provider_id` 的索引、却**从不补这一列** ⇒
任何不带该列的库上整条 boot 迁移报 `42703` ⇒ **网关起不来**。
修法是让 ensure 链补上它自己索引的列：

```sql
-- db.go ensureRequestLogSchema（幂等，可空，无默认值）
ALTER TABLE _request_logs ADD COLUMN IF NOT EXISTS provider_id BIGINT;
```

**对 211 / 252 的影响**：

| 机器 | `_request_logs.provider_id` | 后果 |
|---|---|---|
| 211 | 由 v1→v2 改名而来 ⇒ **已有该列** | `ADD COLUMN IF NOT EXISTS` 是 **no-op** ⇒ **零影响** |
| 252 | 同上（v2 族完整）⇒ **已有该列** | 同上 ⇒ **零影响** |

⇒ **不需要手工执行任何 SQL**；两台机下次重启时这条语句自动跑，且是 no-op。
⚠ 若某台机器的 `_request_logs` 是**最小基线形态**（没有 `provider_id`），
则该语句会**新增一列可空 BIGINT**（无默认值、无数据回填）⇒ 无数据风险。

> ★ **2026-10-21 合并上游后的订正**：本节原先写的「另一处改动是纯守卫：ensure 链
> 现在按 `to_regclass` 判断族表在不在」——**那一条上游已经有了**（上游的族级早退
> 探两个表、hot 侧的 `work_type` 闸、以及 `recent_success_rate` 砍掉旧腿）。
> **本轮最终留在 `db/db.go` 上的只有三处**（都是上游**没有**的）：
>
> | 本轮改动 | 形态 | 对 211/252 的影响 |
