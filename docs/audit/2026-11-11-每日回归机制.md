# 每日回归机制（2026-11-11 · 协议转换审计轮 · 剩余任务②）

> **一句话**：仓内已经有大量门，但它们全挂在 **push/PR** 上；**每日**才会暴露的那一类回归
> （时间相关漂移、偶发失败、外部依赖变化、数据随时间变化导致的断言失效）此前**没有任何机制在跑**。
> 本轮把「每日回归」的**内容**落地成可执行入口，并把**节奏**的规格写清楚（节奏本身由平台侧提供）。

---

## 一、机制的两半（内容 vs 节奏）

| 半边 | 谁负责 | 仓内可验证？ |
|---|---|---|
| **内容**（跑什么） | `scripts/audit/daily_regression.sh` | ✅ 可执行、可门禁 |
| **节奏**（什么时候跑） | codeup Flow **定时触发** | ❌ **控制台侧配置**，见 §四 |

把两半分开，是因为**只有一半能写进仓里**。另一半如果写成"看起来跑起来了"的东西，
就是第 27 处纪律「缺覆盖的全绿」的同款——门绿着，而它要保护的东西从没被触发过。

## 二、内容：仓内部分（可验证）

### 2.1 入口

```bash
bash scripts/audit/daily_regression.sh              # 影响面 + IR 变异门 + 载体接线门
bash scripts/audit/daily_regression.sh --full       # 再加全量 go test ./...
bash scripts/audit/daily_regression.sh --emit-report  # 落报告到 docs/audit/
```

Makefile 入口：`make daily-regression`（载体与本地每日跑都走这一条 ⇒ 同一份内容）。

### 2.2 六个阶段

| 阶段 | 内容 | 失败后果 |
|---|---|---|
| ① | **派生** IR 影响面包集合 | 空集 ⇒ **fail-closed**（rc≠0） |
| ② | 影响面套件（`go test <派生集合>`） | rc≠0 |
| ③ | `internal/ir` 全套 + **覆盖率门禁 ≥75%** | rc≠0 |
| ④ | IR 变异门 ×4（client-error / gemini-only-loss / coerce-numeric / toolcall-canonical） | rc≠0 |
| ⑤ | CI 载体接线门 | rc≠0 |
| ⑥ | （`--full`）全量 `go test ./...` | rc≠0 |

### 2.3 ★ 为什么包集合是**机器派生**的 ★

派生口径：**传递依赖闭包里含 `internal/ir` 的包**。

```bash
go list -f '{{.ImportPath}} {{join .Deps " "}}' ./... \
  | grep -w "$MODULE/internal/ir" | awk '{print $1}' | sed "s#^$MODULE#.#"
```

理由：**手抄清单 = 必然漂移**（仓内 LESSONS 同款坑）。新增一个 `import internal/ir` 的包，
**自动**进每日回归，**不需要改任何清单**；反过来，若有人新增包却忘了加进去，
每日回归**不会**覆盖它——而门还是绿的⇒ 覆盖缺口被静默掩盖。

⇒ 这条性质由 `tests/daily_regression_wiring_test.sh` 的**判据④**钉住（见 §三）。

### 2.4 ★ 为什么"派生为空"要 fail-closed ★

派生不出来 ≠ 没有影响面。若这里放行，每日回归会在"其实没覆盖任何东西"的状态下**报绿**。

⇒ 脚本在派生为空时**当场 rc≠0**，并打印：

```
✘ 派生出的影响面包集合为空 ⇒ ⇒ 【判据不存在】⇒ ⇒ fail-closed（rc≠0）
   （若确无影响面，请改判据口径，而不是让本脚本静默通过）
```

## 三、接线门：`tests/daily_regression_wiring_test.sh`

| 判据 | 内容 |
|---|---|
| ① | 入口脚本存在 |
| ② | Makefile 的 `daily-regression` target 存在且**引用入口脚本**（入口与 target 不得脱节） |
| ③ | 载体 `.workflow/` 下**每个**流水线配置里有**非注释行**调 `make daily-regression` |
| ④ | ★ **派生性（行为级）** ★ |
| ⑤ | 变异臂：把载体里的调用挪进注释 ⇒ 必须判红（证明③有牙） |

### ★ 判据④ 为什么是行为级 ★

"集合是派生的"这件事**没法靠 grep 判准**（写成常量也可能长得像）。
唯一能验的办法是**让派生源失效**：用 PATH shim 把 `go list -f` 的输出换成空的
（`go list -m` / `go test` / `go tool` 全部**透传真实 go** ⇒ 脚本只会在"派生为空"这一处红 ⇒ 归因精确）。

⇒ 派生源被换成空之后，入口脚本**必须 rc≠0 且给出专属失败串**。

⇒ ★★ 这条**同时钉住两件事**：★「派生为空必须红」+ ★「集合不是手抄常量」——
★★ 因为若有人把集合改成手抄常量，shim 就拦不住它 ⇒ ⇒ 判据④变红 ★★。

## 四、节奏：平台侧限制与**待人工动作**（诚实边界）

### 4.1 事实

**codeup Flow 的"定时触发"是控制台（UI）侧配置，YAML 表达不了。**

证据（2026-11-11 实测检索）：

1. 官方《YAML 流水线》schema 的顶层节点只有 `name` / `sources` / `stages`；
   `sources.<id>.triggerEvents` 是**代码源事件**（push / tagPush），**没有 cron**。
   来源：<https://help.aliyun.com/zh/yunxiao/user-guide/yaml-preliminary-experience/>
2. 云效开发者社区的答复（两处独立来源一致）：定时触发在
   **「流水线的编辑页面 → 触发设置 → 定时触发」** 里配置，支持**周期触发**与**单次触发**（Cron 表达式）。
   来源：<https://developer.aliyun.com/ask/596061>、<https://help.aliyun.com/document_detail/153764.html>

⇒ ⇒ **仓内 `.workflow/main-verify.yml` 写不出每日触发** ⇒ ⇒
⇒ ⇒ 仓内能做的只有：把**内容**做实 + 把**节奏的规格**写清楚 + 把**接线**门禁化。

### 4.2 ★ 待人工动作（一次配置）★

> ⚠ **这是人工动作，不是自动门禁。** 仓内**无法**验证控制台状态
> ⇒ ⇒ **"已登记" ≠ "已生效"** ⇒ ⇒ 第一次配置后请在云效流水线页**核对一次**
> ⇒ ⇒ 并在 §五 记录核对结论。

| 项 | 值 |
|---|---|
| 位置 | 云效 → 项目 `llm-gateway-go` → 流水线 → 编辑 → **触发设置** → **定时触发** |
| 模式 | **周期触发**（Cron） |
| Cron | `0 3 * * *`（每日 03:00，**服务器时区**） |
| 触发后跑 | 与 push/PR 相同的流水线 ⇒ 步骤里已有 `make daily-regression` |

### 4.3 ★ 如果不想动控制台：仓内自跑的替代口径 ★

`scripts/audit/daily_regression.sh` 是**纯 bash + go**，不依赖云效 ⇒
任何能执行 cron 的机器（211/154/245 之一、或任一运维机）都能直接排：

```cron
30 3 * * * cd /path/to/llm-gateway-go && bash scripts/audit/daily_regression.sh --emit-report
```

⇒ ★ 这条**不依赖平台** ⇒ ⇒ 仓内可自证（脚本存在 + 接线门有牙）⇒ ⇒
⇒ ★★ **推荐先用这条把机制跑起来**（当天就能生效），控制台定时触发作为**第二重保险** ★★。
