二、根因：缺陷为什么会同时发生

上一轮把「管理员管理用户密钥」当成纯前端任务做，而后端其实早有一套完整的密钥端点 （/api/keys 的 CRUD + reveal + approve + enable/disable/revoke）。于是出现两类问题：

① 前端按错误契约接后端

  • 以为 enabled 就是「状态」，没读鉴权谓词
  • 后端「静默失败」被前端当「成功」渲染出去
  • 空输入字符串没归一 ⇒ 必 400
  • 把「关弹层 / 切实体 / 关容器」当成一件事

② 复用了不该复用的读面

  • getKeys() 无过滤参数 ⇒ 只能拉全量回前端筛
  • 多租户下 = 越权下发（浏览器拿到其它租户密钥元数据）
  • 后端明明有 reveal，一个字没接
★ 通用式：「端点已存在」≠「端点语义与你的用法一致」。 setKeyEnabled 只写 enabled 不写 status —— 在 KeysView 无害， 换到「用户密钥管理」这个新场景，它立刻变成一个骗人的成功提示。

四、密钥状态语义（按真 status，不是 enabled 布尔量）

status徽章可启用可吊销说明
active正常—✅正常可用
pending待审核✅✅已提交待审核
throttled已限流✅✅仍可用但被限流 —— 显示成「禁用」会误导管理员去点启用
disabled已禁用✅✅临时禁用，可恢复
revoked已吊销❌❌终态，不可恢复，需重新签发
★ 「已吊销」与「已禁用」必须区分。 吊销是终态 —— 后端 setKeyEnabled 对它明确 409。 吊销语义不会被偷偷推翻。

十、本轮可复用的通用式

  • 端点已存在 ≠ 端点语义与你的用法一致 —— 复用前先读它的写入面，不只读路由
  • 鉴权谓词是唯一权威 —— UI 必须按谓词建模，否则必然出现「显示正常但不可用」
  • v-model.number 的空值不是 null —— Vue 3 的 looseToNumber 对 '' 返回原串
  • 一次性状态要在三个时机清零 —— 关弹层 / 切实体 / 关容器是三件不同的事，漏一个就是跨实体泄露
  • 守卫自己也要被审计 —— 本轮第一版断言 not.toContain('v-model.number') 命中了文件头描述缺陷的注释 ⇒ 假阳性 ⇒ 改查属性用法形态
  • 权威 DDL 优于代码里的枚举 —— status 的 5 个取值域来自表约束 CHECK，不来自任何 TS 类型或 Go 常量
  • 读面的过滤口要开在服务端 —— 「拉全量回来前端筛」在多租户下是越权下发
  • 归因用 stash 对拍，不靠印象 —— 每个门禁数字都量了改动前/后两遍
  • 部署闸门失败先问「谁引入的」 —— 用 git show <rev>^:file 的 sha256 对拍 DB 记录值，字节级锁定漂移来源
  • 管道会吃掉退出码 —— deploy.sh | tail -80 永远返回 0 ⇒ 必须 set -o pipefail，否则「失败」会被读成「成功」
  • 共用一个 PG 就是共用一份债 —— 154/245/252 同库 ⇒ 一次台账漂移同时卡住三套环境
  • 上线的每一行都要问「它带着谁一起上线了」 —— 本轮 211 带上了并行提交的 captcha 契约缺陷
