# 2026-11-13 ZCode glm-5.3-flash「All providers unavailable」根修轮（/v1/messages 跨供应商故障转移缺失）

## §0 结论一句话

**ZCode 经 /v1/messages 调 glm-5.3-flash 间歇性全灭的直接原因＝anthropic 协议入口从未把跨供应商故障转移许可交给 dispatch**（chat 面与 responses 面早有、messages 面漏设 ⇒ ExecParams 零值 false）⇒ 首供应商 bigmodel coding 三凭据对特定 body 全部 400 后请求直接终态「All providers unavailable」，而同窗口 resolve 面里 10 个跨供应商候选（provider 18 当天 869 次真实成功）一个都没被试过。修复＝补三字段接线 + 共享语义源 + AST 三面同形钉测；211 已部署（f0ed6187@3031 槽b），生产实测真实流量跨供应商逃生成功。

## §3 根因

### 3.1 主根因（网关侧，本轮修复对象）：三协议入口不同形

`qr.AllowProviderChange = params.DispatchAllowProviderChange`（executor_dispatch.go:463）⇒ `providerSwitchAllowed`（planner.go:301）只放行同供应商兄弟；换模 `AllowModelChange` 同样未设。三入口接线状态：

| 入口 | 文件 | DispatchAllowProviderChange |
|---|---|---|
| chat `/v1/chat/completions` | handler.go:4981 | ✅ `hasMultipleProviders(candidates)` |
| responses `/v1/responses` | responses.go:825 | ✅ `responsesDispatchOptions(...)` |
| **anthropic `/v1/messages`** | **messages.go（修前）** | ❌ **未设置 ⇒ 零值 false** |

「同一缺陷只修一半」的**协议面形态**：chat/responses 各自修复时（dispatch V2 引入期）都没检查第三个入口。缺陷不在 dispatch 切换逻辑——`PlanSwitchCred`/`providerSwitchAllowed` 各自的单测全绿，许可位是假值时它们的行为也完全正确；**唯一能抓住这类缺陷的层是入口装配层**（这也是钉测采用 AST 形状门的理由）。

### 3.2 次因（厂商侧，登记不修）：bigmodel coding 1210 的触发面

- 直连二分（复用 provider 32 凭据）：`metadata` 字段 → 400 1210（**digest 与生产逐字节一致**）；已排除：stream、tools（含 55 个富 schema 工具）、tool_choice（string+object 形）、tool 历史/混合 tool_calls、130KB 体积、内容数组、连续同角色、空 assistant、空参数、stop、temperature/top_p/top_k、user、stream_options、parallel_tool_calls、reasoning_effort、service_tier、未知字段、max_tokens 128000。
- 经网关复测：anthropic `metadata.user_id` 被正确消费（ir.User → openai `user`，knownFields 不进 Extensions）⇒ **网关没有泄漏 metadata**，1210 的真实触发是「特定凭据 × 特定 body」组合：生产里同一粘性会话 760KB body 在 cred 62 上持续 200，而 cred 22 对 <100B 的合成 body 也 400（03:05:44 留痕）；cred 22 随即进入 1302 速率限制（429）。
- **定性：厂商侧按凭据/账号维度的参数校验差异，错误体不给字段级归因（1210 是伞码）。** 网关的正确行为＝request_rejected 归因到「这次请求 × 这个端点」并换候选——这正是修复后生效的路径。真实失败 body 未落库（request_wal_bodies 对失败请求 0 行），无法重放定位到字段；如需继续定位，需先补失败请求 outbound body 落库（登记 §7-③）。

## §6 通用式

1. **「同一缺陷只修一半」的协议面形态**：每加一个协议入口（messages/responses/ollama…），都要对「入口装配清单」重跑一遍——dispatch 许可、模态、模态门、pin 头这类**装配型字段**没有运行时错误，漏了就是静默阉割。三面同形要用门钉住，不能靠 review 记性。
2. **许可位类缺陷的特点**：所有被许可的路径单测全绿（它们收到假许可时的行为也正确）⇒ 行为测试抓不住，**装配层形状门是唯一抓手**。
3. **失败请求的 outbound body 不落库 ⇒ 厂商伞码（1210 这类无字段归因的错误）永远无法定位**——本次只能排除法。取证半径由落库策略决定。
4. **「节点全部可用但请求全灭」时先查调度许可，再查上游**：resolve 面健康 + 真实流量全灭的组合，指向 dispatch 边界（许可/粘性/预算），不指向候选池。
