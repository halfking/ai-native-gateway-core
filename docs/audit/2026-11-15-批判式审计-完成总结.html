一、结论与根因

问题 ① — 跨窗 limit 播种缺失（P1 数据正确性风险）

维度详情
严重性P1 - 数据正确性风险
位置domains/streaming/key_concurrent_gate.go:247-263 SnapshotAndResetMinute
根因重置前未保存 oldLimit，从刚 make() 的空 map 取值恒为 0
触发条件长请求跨窗口（持续时间 > 60s）
影响观测样本 peak_in_flight > 0 而 concurrent_limit = 0 自相矛盾
→ 运维用观测数据推断「key 是否受帽约束」会误判
→ DB 表积累脏数据（peak 有值但 limit 为 0）
错误实现（初版）： 
g.minuteLimit = make(map[int]int)  // ← 重置为空 map，旧值丢失
for id, inFlight := range g.used {
    if inFlight > 0 {
        g.minutePeak[id] = inFlight  // ✓ 播种了 peak
        // ✗ limit 播种缺失——从空 map 取值恒为 0
    }
}
修正实现： 
oldLimit := g.minuteLimit  // ← 重置前保存旧值
g.minutePeak = make(map[int]int)
g.minuteRejected = make(map[int]int)
g.minuteLimit = make(map[int]int)
for id, inFlight := range g.used {
    if inFlight > 0 {
        g.minutePeak[id] = inFlight
        if limit := oldLimit[id]; limit > 0 {  // ✓ 从旧值继承
            g.minuteLimit[id] = limit
        }
    }
}

问题 ② — writer 启动条件过严（P2 功能完整性缺陷）

维度详情
严重性P2 - 功能完整性缺陷
位置cmd/gateway/main.go:7494 KeyConcurrencyStatsWriter 启动条件
根因条件 keyVerifier.Enabled() 在 lite 模式（有 DB 无 apikey 表）返回 false
影响lite 模式下：并发闸仍在执法（内存 key 有帽就执行），但观测写入完全不启动
→ 有并发限制活动，但观测数据黑洞（无法分析是否卡在帽上）
错误条件（初版）： 
if keyVerifier != nil && keyVerifier.Enabled() && dbConn != nil {
    // ✗ lite 模式（无 apikey 表）时 Enabled() 返回 false
    //   → 有 DB 但完全不写观测
}
修正条件： 
if dbConn != nil {
    // ✓ 观测写入不依赖 keyVerifier.Enabled
    //   lite 模式下内存 key 的并发执法与观测仍有意义
    // ✓ 仍保留表缺席自愈（迁移 965 未部署前 WARN 不停 worker）
}
