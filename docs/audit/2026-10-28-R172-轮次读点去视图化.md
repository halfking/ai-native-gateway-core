## §0 一句话

把 `TurnWriter` 的三处轮次读点（冲突读回 / `GetTurn` / `ListTurns`）从
`public.session_turns_with_current_month` 视图改成**两臂窄投影直查**，
**保留视图那条反连接**（⇒ 等价性是结构性的，不依赖任何数据前提），
并把键谓词**推进两臂内部**（⇒ 反连接从「逐 hot 行求值」缩到「逐候选行求值」）。

## §1 为什么要改（读点的定位）

### 1.1 三处读点是什么

| 读点 | 位置（改前） | 口径 |
|---|---|---|
| ① 冲突读回 | `turn_writer.go` `appendTurnInLockedTx` 的 `RowsAffected()==0` 分支 | `WHERE tenant_id=$1 AND request_id=$2` `ORDER BY partition_date ASC LIMIT 1`，取 3 列（session_id / turn_no / partition_date） |
| ② `GetTurn` | `TurnWriter.GetTurn` | `WHERE tenant_id=$1 AND request_id=$2` `LIMIT 1`，取 43 列 |
| ③ `ListTurns` | `TurnWriter.ListTurns` | `WHERE tenant_id=$1 AND session_id=$2` `ORDER BY turn_no ASC LIMIT $3`，取 43 列 |

★ **它们都不在热路径上**：`GetTurn` 只有测试调用；`ListTurns` 没有生产调用方
（`cmd/gateway/lite_telemetry_sink.go:287` 与 `storage/consistency.go:147` 调的是
**另一个** bodies lister 接口）；冲突读回只在幂等冲突时触发。
⇒ ⇒ **本轮的收益是结构性的（去掉写侧最后的会话族视图依赖）+ 省规划/IO，
不是「把热路径变快」**。这一点必须写在最前面，否则读数会被过度解读。

### 1.2 视图的代价

`public.session_turns_with_current_month` 的 hot 臂带一个**相关反连接**：

```sql
FROM session_turns_hot hot
 WHERE NOT (EXISTS (SELECT 1 FROM session_turns archived
                    WHERE archived.tenant_id::text = hot.tenant_id::text
                      AND archived.request_id = hot.request_id))
UNION ALL
SELECT … FROM session_turns;
```

⇒ 每次**规划**都要展开「两臂 × 65 列 + 一个 Nested Loop Anti Join」，
而且这个反连接是**逐 hot 行**求值的（EXPLAIN 里那条 `Subquery Scan` 就是它）。

## §2 ★★ 关键设计决策：为什么**保留**反连接（变体 C），而不是去掉它（变体 B）

### 2.1 两个变体

**变体 B（去反连接）**

```sql
(SELECT … FROM session_turns_hot WHERE <键谓词>)
UNION ALL
(SELECT … FROM session_turns   WHERE <键谓词>)
```

**变体 C（本轮采用：保留反连接 + 谓词推进）**

```sql
(SELECT … FROM session_turns_hot hot
  WHERE <键谓词>
    AND NOT EXISTS (SELECT 1 FROM public.session_turns archived
                     WHERE archived.tenant_id::text = hot.tenant_id::text
                       AND archived.request_id = hot.request_id))
UNION ALL
(SELECT … FROM session_turns WHERE <键谓词>)
```

### 2.2 变体 B 的等价性**依赖一个数据前提**

B ≡ 视图 需要「hot ∩ 父表 = ∅」。这个前提**大体成立**：

* `promote_session_turns_hot_to_partition` 是**单语句 CTE**
  （`installer/.../897_session_turns_promote_final_success_self_heal.sql:251-264`：
  `WITH moved AS (DELETE FROM session_turns_hot … RETURNING h.*),
        inserted AS (INSERT INTO session_turns (…) SELECT … FROM moved)`）
  ⇒ DELETE 与 INSERT 在**同一语句** ⇒ 原子 ⇒ 一行是**搬家**不是**复制**
  ⇒ 同一 `request_id` 不会同时存在于两边；
* 写入侧的幂等守卫是 `WHERE NOT EXISTS (ExistsByKeySQL($3::varchar, $4))`
  ⇒ 幂等键就是 **(tenant_id, request_id)**（不带分区键）⇒ 跨分区也拦得住；
* 并发侧 `AppendTurn` 先按 `request:<request_id>` 取 pg advisory lock
  ⇒ 两个事务不会同时穿过上面的 NOT EXISTS；
* 实测：本地真库 hot∩父表 = **0** 对（hot 16 / 父表 2742）；252 生产 = **0** 对
  （hot 7,263 / 父表 1,133,441）。

★★ **但前提不是恒真的**：

* `cmd/tools/validate_sessions_v2/repair.go:301` 往父表回填 v1 轮次时
  **没有存在性守卫** ⇒ 它跑完可能造出同键的两份；
* 而 **canonical 视图**（`request_logs_with_current_month`，113 列，仓内约 95 处读点）
  **根本没有反连接** ⇒ 仓内主读面早已接受「不按 request_id 去重」的语义。

### 2.3 ★★ 仓内已有的一个自相矛盾（本轮撞上并订正）

* `admin/session_view_dependency_risk_test.go` 的
  `nativeSessionReaderBlockExemptions` 写着：
  「视图的 anti-join（hot 去掉已 promote 的行）是**承重**的 ⇒ 裸 hot ∪ 父表会把
  已 promote 的轮次**数两遍**」。
* 而**同一份审计文档** `docs/audit/2026-10-27-R90-turns-sessions-过滤路径500与两腿改写.md`
  的 §4.1(b) 写着：hot 与父表按 `(tenant_id, request_id)` 配对 **0 行**
  ⇒「视图的 anti-join 剔除 0 行 ⇒ 视图 ≡ hot ∪ 父表」。
* `db/request_logs_view_schema.go:928-933`（R92）也写着同一条结构性结论。

⇒ ★ **§5.4 的豁免理由比 §4.1 的实测更保守**：promote 是 MOVE 不是 COPY，
「已 promote 的轮次」**不会**在两边同时存在 ⇒ 「数两遍」在那条论证下不成立。
⇒ ⇒ **本轮不去改那条豁免**（那是另一个读点 `turns_sessions.go` 的登记，
且实测该腿 < 20 ms 不是瓶颈），但**本轮自己的等价性不建立在那个保守假设上**。

### 2.4 决策

**选变体 C**：C 的两条臂与视图**逐字同源**（反连接谓词照抄）⇒ 等价性是
**结构性的**：不依赖「hot ∩ 父表 = 0」，不怕任何非原子回填路径；
而「谓词推进两臂」把反连接的**求值范围**从「整张 hot 表」缩到「命中键谓词的候选行」。

## §3 等价性论证（四维，逐维可查）

### 3.1 反连接逐字同源（第一维 · 承重）

视图的 hot 臂反连接谓词（本地与 252 的 `pg_get_viewdef` 都是这个形态）：

```
archived.tenant_id::text = hot.tenant_id::text AND archived.request_id = hot.request_id
```

★ **不含 `partition_date`**（⇒ 同键跨分区也算命中）。
★ 本轮产物的反连接**逐字照抄**，且 hot 臂的别名就用 `hot`（与视图同名）⇒
守卫可以把「产物里的反连接」与「**线上此刻的**视图定义里的反连接」做
归一化后的**包含比对** ⇒ **视图语义一改，这道门立刻红**（判据 2）。

### 3.2 投影逐字等价（第二维）

视图的每一列都是**裸列**（`hot.<col>` / `session_turns.<col>`，**无任何表达式**）
⇒ 视图读到的值 = 直接读对应底表同一列的值。
⇒ 本轮把**视图那一层的裸列**原样搬进两臂，把 `COALESCE` 留在**外层**
（与改前「视图外再包 COALESCE」的层次完全一致）。

★ 改前 `GetTurn` 与 `ListTurns` 各写了一份 43 列 SELECT 列表，两份**逐字相同**
这件事**没有任何机制保证** ⇒ 本轮让两臂投影与外层投影**从同一张表渲染** ⇒ 结构上不可能漂移。

### 3.3 RLS 可见集一致（第三维）

视图带 `security_invoker = true`（757 迁移的自检强制它）⇒ 视图的 RLS 语义由**底表**决定：

| 对象 | RLS | 策略 |
|---|---|---|
| `session_turns`（父表） | ON | `session_turns_tenant_isolation`：`tenant_id::text = current_setting('app.current_tenant')` |
| `session_turns_hot` | OFF | — |
| `session_turns_with_current_month` | OFF（视图自身） | security_invoker ⇒ 由底表决定 |

⇒ 两种形态读的是**同样两张表**、在**同一个调用者身份**下读 ⇒ 可见行集一致。

### 3.4 谓词与 UNION ALL 可交换（第四维）

过滤是合取式 ⇒ 与 UNION ALL 可交换；反连接是**逐行**谓词（不引用外层列）
⇒ 「先过滤再反连接」与「先反连接再过滤」同集。★ 两条合起来 ⇒ **C ≡ 视图**。

## §4 守卫（四道判据 + 一个真库腿）

新文件 `domains/session/v2/turn_writer_family_reads_test.go`：

1. **产物形状**（静态）：恰好两臂（顶层 `UNION ALL` × 1、顶层 `FROM` × 1 ⇒
   ★ 两条臂**被括号包住**，否则外层 `ORDER BY/LIMIT` 只作用于最后一条臂）；
   hot 臂 × 1 / 父表臂 × 1 / 反连接里的父表引用 × 1；口径钉
   （`ORDER BY partition_date ASC LIMIT 1` / `LIMIT 1` / `ORDER BY turn_no ASC LIMIT $3`）
   逐字不变；排序键必须在投影里（否则 42703）；反连接**必须在**且三处**逐字相同**。
   ★★ **两条臂的键谓词必须【逐字相同】**（`TestTurnFamilyReadsArmsKeyPredicatesMatch`）——
   ★★ **这条判据是被变异臂逼出来的**（M8 臂：把父表臂的谓词改成
   `… AND tenant_id IS NOT NULL` ⇒ **在当前数据上结果不变**（`tenant_id` 恒非空）
   ⇒ 真库等价判据抓不到 ⇒ 「`tenant_id = $1` 这个子串仍出现两次」的形状判据也抓不到
   ⇒ ⇒ **门漏了** ⇒ ⇒ 唯一可靠的判据是**逐字比对两条臂的键谓词**。
   ⇒ ★★ 这也是「真库判据只能证明【当前数据】」的典型：语义差异可能在**别的数据**上显形。
2. **投影冻结**（静态）：43 列名单**精确计数**、**逐列**比对、列序不许改
   （列序 = Scan 顺序）；外层必须逐项包 `COALESCE`、两臂内部**不得**包。
3. **调用点**（AST）：三处读点必须调用对应 helper（名字与参数逐字相符：
   `TurnConflictLookupSQL("$1","$2")` / `TurnByRequestSQL("$1","$2")` /
   `TurnsBySessionSQL("$1","$2","$3")`）；**任何** SQL 文本里不得再出现视图名
   （★ 判据落在「调用点」而不是「源码里有没有这个词」——注释里提到不算违规）。
4. **真库等价**（真库）：**嵌入产品 SQL** 与视图形态放在**同一条语句、同一个快照**里
   对拍（`EXCEPT ALL` 双向 + 有序序列逐行）；
   ★ 前提检查：线上视图仍是反连接形态（否则 `t.Fatalf`，不是 skip）；
   ★ 判据 2：产物的反连接谓词归一化后**必须逐字出现在线上视图定义里**。

★ **为什么第 4 条要「嵌入产品 SQL」**：另写一份等价 SQL 是**手写复刻**，
它对了不代表产品对了 ⇒ 对拍的必须是线上真正发出去的那一条。

## §5 实测读数

### 5.1 ★★ 一次自我纠偏：第一版 252 读数是**测量形态**的伪影

第一版脚本用 `(SELECT tenant_id FROM r171_par_key)` 取键 ⇒ **谓词里出现子查询**
⇒ planner 无法把它当常量下推 ⇒ 全部变成 `Seq Scan` ⇒ 读数「view exec 23~57 ms」。
★ 那**不是**产品形态的读数，是**量具**的读数。改成**字面量**键后（§5.2）
view 的执行时间回到 ~1 ms 量级。
⇒ ★★ **教训**：「view 很慢」这个结论，在量具形态不对时是**量具造的**，
不是事实源说的。LESSONS §475 的同族问题（单次读数无分辨力）在这里又出现了一次，
但这次错在**谓词形态**而不是**采样次数**。

### 5.2 252 生产规模 · 三轮交错复测（字面量谓词，真产品 SQL）

样本：tenant `default`；父表腿 request_id `d9e73b23…` / session `gw_4aa55cf3…`。

|---|---|---|---|---|
| ① 冲突读回 | 视图 | 8.655 / 14.033 / 17.427 | 0.394 / 0.488 / 0.784 | 2 / 312 |
| ① 冲突读回 | **产品** | 6.647 / **6.902** / 16.741 | 0.387 / 0.489 / 0.515 | 3 / **222** |
| ② `GetTurn` | 视图 | 7.948 / 11.187 / 27.518 | 0.627 / 0.701 / **1.739** | 3 / **872** |

* **节点形状**：视图形态三处都多一个 `Subquery Scan`（= 逐 hot 行求值的反连接子查询），

  ⇒ 视图的反连接对 hot 表做了**全表**求值；产品形态只对候选行求值；
* **长尾**：视图形态的 `ListTurns` 出现 **51.255 ms** 的尖刺，
  产品形态三轮全在 0.529~0.724 ms ⇒ ★★ 产品形态**消掉了这个长尾**
  （★ 按 LESSONS §475：单次读数无分辨力，但「三轮都不过 0.8 ms vs 出现 51 ms 尖刺」
  是**分布层面**的差异，不是单点）；
* **规划**：产品的中位数在三处都低于视图（6.9 vs 14.0 / 8.6 vs 11.2 / 11.0 vs 22.8 ms）
  ⇒ 规划省 1.3~2.1×；★ 但区间高度重叠 ⇒ **只说「分布整体偏低」，不说「快 N 倍」**。

## §8 本轮通用式（候选，见 `LESSONS.md` §480）

1. ★★★★★ **「等价性」的最强形态是【与事实源同源】，不是【与某个读数相同】** ——
   本轮的产物的反连接谓词与**线上视图定义**逐字同源 ⇒ 视图语义一改，门立刻红；
   而「两臂 ≡ 视图（因为 hot∩父表=0）」这种说法把「前提」藏在了论证里，
   一旦前提被破（`repair.go` 能造出重复），**读端就静默出错**。
   ⇒ **把前提从论证里挖出来，塞进产物里**。
2. ★★★★★ **「保守的等价论证」和「事实」会同时存在于仓内** ——
   R90 审计的 §4.1(b) 与 §5.4 在**同一份文档**里互相矛盾（一边实测 0 配对，
   一边说 anti-join 承重）⇒ ★ **读到一处「承重」的断言，必须回到该文档的实测节**
   ⇒ 也必须回到**事实源**（promote 是 MOVE 还是 COPY）。
3. ★★★★ **量具的形态错误会造出「看起来很严重」的结论** ——
   谓词里放子查询 ⇒ planner 不能下推 ⇒ 全 `Seq Scan` ⇒ 读出「view 慢 23~57 ms」。
   ★ 第一版读数是**量具的**，不是事实的 ⇒ **先验量具，再验结论**。
4. ★★★★ **有分辨力的判据是【访问路径 + buffer 计数】，不是【执行时间中位数】** ——
   视图形态多一个 `Subquery Scan`（逐行反连接）、`GetTurn` 形态多读 4× buffer
   ⇒ 这两条可复现；执行时间中位数两形态只差 1~2× 且区间重叠。
5. ★★★★ **谓词推进能把「逐全表求值」缩成「逐候选行求值」** ——
   同一张反连接，推/不推谓词，代价差一个量级（buffer 872 → 222）。
   ⇒ ★ **改读法时优先想「能不能把谓词推进去」**，而不是「能不能删掉它」。
6. ★★★ **判据用的正则必须先确认引擎支持** ——
   Go 的 RE2 **不支持负向先行断言** `(?! …)` ⇒ 判据写不出来时，改用
   「总数 − 子类数」的算法，而不是换个语言偷偷用 PCRE。
7. ★★★ **「顶层」计数要按深度算，不能按空白形态算** ——
   `strings.Count(sql, "FROM public.session_turns ")` 会因换行+制表符而 0 命中
   （判据恒绿）；`strings.Count` 还会把反连接里的 FROM 算进去（判据恒红）。
8. ★★★ **「新增文件」会撞上「登记簿」这类按【文件】管的门** —— 本轮新增
   `internal/sessionfamily/turns_reads.go` 后撞上两道按文件管的门：
   ① 会话族「裸父表读法」门（判据单位是**一条字符串字面量** ⇒ 跨字面量的
   「两面 UNION」看不见 ⇒ 按仓内先例具名登记 + 另加一道**正面证明**门）；
   ② canonical 读点登记簿（**注释里的提及**也算数 ⇒ 本文件在注释里提到
   canonical 视图名就被要求登记 ⇒ 归 `classNoRead`）。
   ⇒ ⇒ ★ **新增文件前先问「仓里有哪些按文件管的门」** ⇒ 否则第一次提交就被门拦。
9. ★★★ **新增【测试】文件也会断掉【另一个构建配置】的整包编译** —— 本轮新增的守卫用
   `realDBPool`（定义在 `//go:build !integration` 的文件里）⇒ 不加 tag 时
   `go vet -tags=integration ./domains/session/v2/` 报 `undefined: realDBPool`
   ⇒ ⇒ ★★ 而 `make` 的注释写着「唯一跑全仓的是 integration job 的
   `go test -tags=integration ./...`」⇒ ⇒ **这个包在那个作业里根本编译不过**
   ⇒ ⇒ ★★ **同一次排查还发现：基线树（origin/main）逐字同样红**
   （`turn_writer_idempotency_lookup_test.go`，R169 引入）⇒ ★ 既有缺陷，
   本轮同族修掉（各 1 行 build tag）⇒ ★★ 修完全仓 `-tags=integration` vet 干净。
   ⇒ ⇒ ★ **「新增文件 ⇒ 查它依赖的符号在哪个 build tag 下定义」**，
   以及 ★★ **「默认构建全绿 ≠ 全仓构建全绿」**。
10. ★★★ **注释会随代码漂移** ——
   `session_writer_v2_nil_before_commit_pin_test.go` 的注释里写着
   「该分支**必须**在 session_turns_with_current_month 查到行」⇒ 改完代码它就是**假的**
   ⇒ ★ 改读点时**必须**把这类描述一并订正（注释是事实源）。
