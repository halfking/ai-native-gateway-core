### ⚠️ D7 的前置问题第二次换（§9.132.3）——**补齐定价是行为变更，不是数据补全**

`CalcCost` / `AssignRequestCost`（`domains/streaming/usage.go`）**没有 `billing_mode` 入参**；
对照组实测：订阅制 + 正价的 308 行里 **120 行照样产出成本（39%）**
⇒ **订阅制不豁免记账**（路由侧 `calculateCostPenalty` 豁免，两侧不一致）。

⇒ **在你决定「要不要补齐在用模型定价」之前，必须先定这一条**：

> **订阅制凭据（`token_plan` / `code_plan` / `agent_plan` / `monthly` / `free`）要不要算成本？**

- 若**要** ⇒ 补价会让这些凭据上现在 cost=0 的行开始产出非零成本
  （本窗口 `r1_plan` 有 **9,608 行单价 NULL**、另有 **233 行是显式 `0/0`**，共约 9,841 行受影响），
  这是**一次计费数据的行为变更**，必须进发布方案与回滚方案（D9）。
- 若**不要** ⇒ 需要在 `AssignRequestCost` 里加豁免分支（**改产品行为**），
  否则「路由豁免、记账不豁免」的差异会一直在。

⚠️ 附带一个只指出不擅改的实现事实：`CalcCost` 的
`if priceIn == 0 && priceOut == 0 { return nil }`（`usage.go:208`）
把**「显式免费」与「从未定价」合并成同一件事** ——
而路由侧对同一情况的处理是「未知价格不是免费 = 最大惩罚」（`strategy_cost.go:12`）。
⇒ **同一句语义在两个子系统里方向相反。**
⚠️ 另有两格**未解释**、如实记在审计 §9.132.4：无单价却有成本 77 行、正价组成本与成功数对不齐；
`price_change_events` 是套餐历史不是单价历史，**无从查证**。

## 🟡 D7-f　失败流量算不算钱（2026-10-04 **暂定采纳**，见下方状态栏）

> **状态**：本轮以**问卷超时自动采纳推荐项**的方式收到「失败流量不计费，
> 但要把 `rate_limited` 显式标注出来」。⚠️ **这不是你的显式确认** ——
> 收到的是 `responseSource=automatic_timeout`。故本项标为**暂定**，等你一句显式「就这样定」再转正。

**口径**：`failure` 与 `rate_limited` **不产生成本**；`rate_limited` 必须在数据里**可显式识别**。

**为什么这个口径站得住**（实测，不是推断）：

| 类别 | 行数 | 有 cost | 从未联系上游 | 结论 |
|---|---:|---:|---|---|
| `rate_limited` | 403,031 | 0 | **394,614 行 100%**（`outbound_model`/`provider_id`/`completion_tokens` 全 0、均值延迟 51.6ms） | **0 成本是正确的**，它根本没打上游 |
| `failure` | 1,453,695 | 31（0.002%） | 真实打上游但失败 | 不计费是**口径选择**，不是事实 |

⚠️ 口径一旦定为「失败不计费」，就必须处理两处**会凭空造成本**的实现事实：

1. **`AssignRequestCost` 没有 `billing_mode` 入参**（`usage.go:252`）⇒ **补齐定价会让
   现在 cost=0 的失败行开始产出非零成本**，除非先加豁免分支。
2. **`CalcCost` 把「显式免费」与「从未定价」合并**（`usage.go:208`，`priceIn==0&&priceOut==0→nil`）⇒
   「失败不计费」与「没配价」在实现里**是同一件事**，无法只改其一。
   ⇒ 这两项合起来意味着：**只定口径不改代码，行为会与口径相反。** 必须写进 D9。

**「显式标注」的落点（好消息，§9.150.4）**：

（`hook.go:1082` 已在读它；由 `request_log_pipeline.go:1257/1260`、`embeddings.go:97` 显式写入，
而 `ResolveRequestStatus` 永远不会产出它），
**但 `entryToProcessedRequest` 没把它带进 `ProcessedRequest`，`session_turns` 也没有 `request_status` 列**
⇒ **信号在内存里存在、落库时被丢弃**。
⇒ 标注 = **写入时把这一列原样落库**，**不需推断、不需回填**，退役前后都成立。

> ⚠️ **本节在 §9.124 被大幅修正。** 原版本写「PASS 2 = ok=214 fail=3，重跑会在 625 中止」。
> 两处都不对：
> 1. **3 条是我在人造库上量的数**（只跑链、不跑 baseline 的 startup-only 库）。
>    真实路径下是 **11 条**。
> 2. **第一现场不是 625，是 `01-schema.sql`。** 重跑 installer 会先炸在 baseline 上，
>    根本走不到 217 条链。
> 详见审计文档 §9.124。

**背景**：`InitSchema`（`installer/internal/dbinit/runner.go:716`）的顺序是
**`00-prereqs` → `01-schema` → `02-seed` → 217 条启动迁移**。三件套无条件全量重放，
217 条也无条件全量重放，既没有"这条应用过吗"的判断，也不查版本表；
唯一调用点 `runInstall` 里也**没有"这个库已装过吗"的探测**。

**实测**（真 installer 路径建库：prereqs + baseline + seed + 217 条链跑完，再按同一顺序重跑）：

| 阶段 | 结果 |
|---|---|
| PASS 1（安装） | baseline OK；链 **ok=217 fail=0** |
| PASS 2 `00-prereqs.sql` | **ok** |
| PASS 2 `01-schema.sql` | **1665 条 ERROR**　← **重跑 installer 的真实中止点** |
| PASS 2 `02-seed.sql` | **ok** |
| PASS 2 217 条链 | **ok=206 fail=11** |

⚠️ **11 是「文件数」不是「缺陷数」**：门用 `--single-transaction + ON_ERROR_STOP=1`，
每个文件只报**第一个**错误。`614` 一个文件里就有 4 条无守卫 `ADD CONSTRAINT`
和 4 条无守卫 `CREATE INDEX`，只暴露了第一个。真实缺陷数更多。

⚠️ **1665 是「错误行数」不是「文件数」**：`01-schema.sql` 是一份裸 `pg_dump` baseline，
整份文件没有一处 `IF NOT EXISTS`，所以它的每个表/函数/policy/触发器都是一条重放错误。
按形态聚合：1130 relation 已存在、168 多重主键、103 函数已存在、75 分区索引、
72 policy 已存在、38 约束已存在、32 触发器已存在、30 已是分区，其余 17 条是前面失败的次生结果。

**链上 11 条按机制分组**（完整原因见 `sql/schema/startup_rerun_known_gaps.tsv`）：

| 机制 | 条数 | 文件 |
|---|---|---|
| **[M1]** `CREATE OR REPLACE VIEW` 不能丢列 / 不能改列名 | 5 | 568、625、637、640、656 |
| **[M2]** 无守卫 `CREATE VIEW`，关系已存在 | 2 | 577、`session_turns_hot_bootstrap` |
| **[M3]** 无守卫 `CREATE POLICY` | 1 | **520** |
| **[M4]** `CREATE TABLE IF NOT EXISTS` 之后紧跟的 `ADD CONSTRAINT` 无守卫 | 1 | 614 |
| **[M5]** 迁移自带的幂等守卫自己在重跑时抛异常 | 1 | 610 |
| **[M6]** 视图链重建时列引用歧义 | 1 | 738 |

⚠️ **这里要更正 §9.119 和 §9.124 两处说法。**

**§9.124 我写「520 与 351 是同一机制」—— 错在把「PG 规则」当成了「缺陷形态」。**
两者触发的 PG 规则确实同一（没有 `CREATE POLICY IF NOT EXISTS`），但缺陷形态不同、
**修法也不同**：

- **351**：**没写守卫** ⇒ §9.115 补了 `DROP POLICY IF EXISTS`；
- **520**：**守卫写错了名字**。它 drop 的是
  `durable_task_settlement_tenant_isolation` 和 `..._super_admin_bypass`，
  而全链扫描证实**这两个名字没有任何迁移创建过**（只出现在 520 自己那两行）；
  它真正创建的 `durable_task_settlement_access` **一条守卫都没有**。
  ⇒ 修法只是补对名字，不必新写守卫。

**§9.119 我推测「非幂等 CREATE POLICY 至少还有别的实例」—— 全量枚举后被证伪。**
枚举全链 **88 条** `CREATE POLICY`：85 条有同名 `DROP POLICY IF EXISTS`、
2 条有 `pg_policies` 存在性守卫（`547` 的写法）、**无守卫的只有 520 这一条**。
⇒ **520 是全链唯一的非幂等 `CREATE POLICY`，规模 = 1 个文件、约 1 行代码。**
那个推测听起来更有警示力，但它是错的，收回。详见 §9.125.2。

⚠️ **[M5] 值得单独看**：610 里有一处 `RAISE EXCEPTION '608: saved pre-extension view
already exists while canonical view lacks request_class'`。它是**一次性的状态检查**——
第一次跑时该状态不存在所以通过；重跑时状态已变成「已存在」，守卫自己抛错。
**这个守卫设计得就不该在重跑时触发**：它的谓词只描述「当前形状」，不描述「我是不是已经做过」。

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| **E1** | 视图重写类（[M1]/[M6]）改 `DROP VIEW IF EXISTS` + `CREATE VIEW` | 需先枚举下游视图/函数依赖；**改已应用过的生产迁移**；**完全不解决 baseline 的 1665** |
| **E1′**（新增，推荐先做） | **只修 614 + 520**：614 补 `IF NOT EXISTS`/存在性守卫（一次修 8 条，占 18 条的 44%），520 补对 `DROP POLICY` 的名字（一次修 1 条） | 纯机械、不动视图链、**不碰下游依赖**；但只覆盖 18 条里的 9 条，且**仍不解决 baseline** |
| **E2** | 保留 `REPLACE`，把重写定义改成**并集**（取链上最宽列集） | 放弃 625「显式列清单」的原始意图；仍要人工保证并集正确；**不解决 baseline** |
| **E3** | 给 `InitSchema` 加"已初始化"守卫 | **最治本**（去掉"重放"这个前提，链和 baseline 一起不再重放）；但改 installer 行为契约，且对"补跑漏掉的迁移"场景失效 |
| **E4** | 把 `01-schema.sql` 改成可重跑（补 `IF NOT EXISTS` 等守卫） | 1665 条，工作量按错误形态分 8 类，**不是机械替换**（如 168 条多重主键、75 条分区索引需要判断） |

- **D11-a**：选 **E3**（推荐）——去掉"重放"这个前提，链的 11 条一起消失；
- **D11-a′**：选 **E3 + E1′**（若你想在 E3 落地前先降一点风险）；
- **D11-e**（新增）：**先只做 E1′**（614 + 520，纯机械、约 9 条/18 条），
  其余登记为已知缺口。适合「不想动 installer 行为契约、但想少留一点坑」的场景。
- **D11-b**：选 E1 + E4（真正支持重跑，但工作量大）；
- **D11-c**：选 E2；
- **D11-d**：本轮不修，只在 D9 的发布流程里避开重跑，并把本条记为已知缺口。
  **门已就位**（§9.124），所以这条不再是"没人知道"，而是"知道了但选择不改"。

⚠️ 无论选哪个，**D9 都必须写明：发布流程不得包含"对已有库重跑 installer"**。
⚠️ **注意 D11-d 是目前唯一与实测完全自洽的选项**：E1/E2 只修链的 11 条，
**修不了 `01-schema.sql` 的 1665 条** —— 也就是说选了 E1 或 E2，**重跑 installer 照样会炸**，
只是炸得晚一点。
