## D2　决定 B：那 16 个已有列的**语义**是否与 v1 等价

| | |
|---|---|
| **性质** | 逐列语义对账（不能只比列名） |
| **硬阻断** | **第一列就断了** |
| **证据** | §9.109 |

`credential_id`：会话侧是 `text`，v1 是 `bigint` ⇒ 运行时 **42883**
（`db/db.go:72` 的 `QueryExecModeSimpleProtocol` 会把参数内联成字面量，所以**只在运行期炸**，
PREPARE 验不出来）。且**会话族没有 `credential_id` 索引**。

- **D2.1 修法**：
  - **B1-a**：SQL 里加 `::bigint` cast（改动面小，语义恒等）　**（推荐）**
  - **B1-b**：改入参类型为 `text`（更干净，但波及写入侧）
- **D2.2 索引**：是否同时补会话族 `credential_id` 索引？
  - **B2-a**：补（推荐，否则修完类型仍会全扫）
  - **B2-b**：不补，先记为已知性能债

⚠️ 曾有一条「v1 `bigint` 42P08 潜伏部署阻断」的结论**已被我收回**（§9.102）：
根因是 SimpleProtocol 内联参数、服务端不做类型推导 ⇒ 生产不可能发生。
现在剩下的只是**类型不兼容**，严重度低得多。
