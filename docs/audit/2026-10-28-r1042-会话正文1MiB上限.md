## 二、洞一：三方向各拿一半 ⇒ 实际 1.5 MiB

★ 旧实现（合并前）：

```go
rec.RequestDelta  = boundMessages(rec.RequestDelta,  MaxTurnBodyBytes/2)
rec.ResponseDelta = boundMessages(rec.ResponseDelta, MaxTurnBodyBytes/2)
rec.OutboundBody  = boundMessages(rec.OutboundBody,  MaxTurnBodyBytes/2)
```

★ ⇒ 实际总量上限 = 3 × 512 KiB = **1.5 MiB**。

★★ 修法：★ **1 MiB 是【每轮总量】**，三个方向**共享**一份预算，
★ 按「请求 → 响应 → outbound」依次分配（★ outbound 最后 ⇒ 它是「可从别处重建」的那一份
★ ⇒ 优先级最低）。

### 2.1 共享预算引出的第二处（★ 旧行为在旧口径下无害，在新口径下是灾难）

★ 旧 `boundMessages` 的第一行是：

```go
if len(msgs) == 0 || budget <= 0 { return msgs, false }
```

★★ 「额度用完 ⇒ 原样放行」——★ 在【各方向各自限额】的旧口径下无害（那个额度本来就该放行）；
★★ ★ 但在【共享预算】的新口径下 ⇒ ★★ 后两段**整段保留** ⇒
★★ ⇒ 总量 = 1 MiB + 后两段的全部 ⇒ ★★ **实测 3.67 MiB**。

⇒ ⇒ ★★ **通式：★ 口径变更必须改【量】——★★ 同一个「安全兜底」在新口径下可能是灾难**，
★★ ★★ 因为它的含义从「这个方向没配额了」变成了「**这个方向完全不用管**」。

## 三、洞二（★ 实测新发现）：额度与裁剪**不同单位** ⇒ 上限根本不是上限

★ 这是本轮最值钱的一处发现。

★★ 额度衡量的是**JSON 编码后**的字节（★ 落库进 `jsonb` 列，★ 落库形态是 JSON 数组）；
★★ 而旧裁剪按**原始字节**数：

```go
n := budget - 24            // ★ 原始字节
m.Content = m.Content[:n]   // ★ 裁原始字节
```

★★★ 而 Go 的 `encoding/json` 会把 `<` `>` `&` 转成 `\u003c` `\u003e` `\u0026`
★★★ （**1 字节 → 6 字节**）⇒ ★★★ 裁完再编码，体积最多膨胀 **6 倍**
⇒ ⇒ ★★★ 裁剪后的消息**仍然装不进额度**，而旧实现**照样把它塞进数组**。

★ 探针实测（额度 1 MiB，内容全是 `<`）：

```
★ 总量 = 1572892 字节（上限 1048576，超出 524316）
```

★★ ⇒ **超上限 50%** ⇒ ⇒ ★★ 「上限」根本没有上限。

### 3.1 修法：按编码后大小裁

★ 新增 `fitMessage`：★ 以「整条消息编码后 ≤ limit 字节」为约束，
★ 用**二分**求最长可用前缀（★ 编码后大小对内容长度**单调** ⇒ 二分成立），
★ 最后再**回退到 UTF-8 边界**。

★★ ★★ 为什么 UTF-8 校验**不能**放进二分条件：★
★★ 「前缀是合法 UTF-8」**不单调**（★ `"中"` 的前 1 字节、前 2 字节都非法，
★★ ★★ 前 3 字节才合法）⇒ ⇒ 二分只管大小，★ 二分完再回退边界（★ 回退只会变小 ⇒ 仍装得下）。

★★ ★★ 裁剪阶梯（★ 从「最舍不得丢」到「最舍得丢」）：
★★ ① `ContentRaw`：解码 → 收缩结构 → 重新编码（★ 见第四节）
★★ ② `Content`（纯文本）：按编码后大小二分前缀
★★ ③ `ToolCalls` / `Name` / `ToolCallID`：结构开销，依次丢弃

## 四、洞三（★ 实测新发现）：`ContentRaw` 任意字节截断 ⇒ 产出**非法 JSON**

★ 旧 `truncateMessage` 的 `ContentRaw` 分支：

```go
m.ContentRaw = m.ContentRaw[:n]   // ★ 任意字节截断（只有 UTF-8 边界回退）
```

★★★ 问题不在 UTF-8，而在 **JSON 合法性**：★
★★★ provider 原生内容是**结构体**（如 `[{"type":"text","text":"…"}]`），
★★★ 截在结构中间 ⇒ 产出 `[{"type":"text","te` ⇒ **非法 JSON**。

★★★ ★★★ 后果比「写大了」严重得多：★
★★★ ★★ 落库路径 `safeJSONMarshal(rec.RequestDelta)` 遇到非法 JSON ⇒ **报错**
★★★ ★★ ⇒ **那一轮正文根本写不进去**（★ 不是写小了，是**写失败** ⇒ 整轮正文丢失）。

★ 修法：★ `ContentRaw` 走「**解码 → 收缩结构 → 重新编码**」：

| JSON 形状 | 收缩方式 |
|---|---|
| 字符串 | 截断（UTF-8 边界） |
| 数组 | 保留前 N 个元素（★ 二分 N） |
| 对象 | 保留前 N 个键（★ **按 key 排序取前缀 ⇒ 确定性**） |
| 数字 / 布尔 / null | 不可收缩 ⇒ 丢弃正文，**保住 role / tool_calls** |

★★ ⇒ 产出**恒为合法 JSON**；★ 收不动时**丢弃正文但保住结构**
★★ ⇒ ★★ 宁可少存，不可存坏（★ 坏数据在读侧才炸，且更难查）。

★★ 顺带加固：★ 脱敏后的 `ContentRaw` 现在要过一道 `json.Valid`
★★ （★ 脱敏替换文本含 `<` `>` ⇒ 在 JSON 字符串内合法；跨结构边界才可能破坏结构）
★★ ⇒ 非法就丢掉正文，而不是让整轮写失败。

## 五、两处「不精确」也一并收掉

### 5.1 截断标记是在**预算之外**追加的

★ `markTruncation` 在 `boundBodiesRecord` **之后**才追加标记（★ 追加进 `ResponseDelta` 数组），
★ ⇒ 若不预留，★ 落库行会比 1 MiB 多出标记体积（★ 实测 75 字节 + 1 逗号）。

★ 修法：★ 预留额度**实算**（不拍脑袋）：

```go
var truncationMarkerAllowance = func() int {
    b, err := json.Marshal([]Message{truncationMarker()})
    if err != nil { return 128 }
    return len(b)
}()
```

★★ ★★ 为什么要**实算**而不是拍个 128：★
★★ ★★ 预留量大于实际增量 ⇒ 就在总账上留下**掩盖记账误差**的余量
★★ ★★ ⇒ 记账一旦有偏，测试看不见 ⇒ ★★ 实算 ⇒ 永远贴着 ⇒ ★★ 零余量。

### 5.2 记账口径必须与**落库形态**一致

★★ `messagesWireSize` 旧实现是「逐条 `messageWireSize` 求和」，
★★ 而落库是 **JSON 数组**（★ `safeJSONMarshal(rec.RequestDelta)`）⇒
★★ ★★ 差 (n+1) 字节（方括号 + 元素间逗号）⇒ ⇒ ★★ 记账与事实源**不同口径**。

★ 修法：★ `messagesWireSize` 改成直接 `json.Marshal(msgs)` 取长度（★ 与落库同形态）。

## 六、★★ 本轮最值钱的一处自伤自愈：判据必须**独立于实现**

★ ★★ 第一版判据是这么写的：

```go
total := messagesWireSize(rec.RequestDelta) + messagesWireSize(rec.ResponseDelta) + ...
```

★★★ 问题：★ **实现也用 `messagesWireSize` 记账**。
★★★ ★★ 若【量具本身】与【事实源】不同口径（★ §5.2 就是这么错的），
★★★ ★★ 则量具错了 ⇒ 测试会**跟着一起错** ⇒ ⇒ ★★ **假绿**。

★ 修法：★ 判据改用**独立复算**：

```go
func persistedBytes(t *testing.T, msgs []Message) int {
    b, err := json.Marshal(msgs)
    if err != nil { t.Fatalf("★ 落库形态编不出来 ⇒ ⇒ 那一轮写不进去：%v", err) }
    return len(b)
}
```

★★ ★★ 并把「**编不出来**」也当成失败（★ 编不出来 = 落库直接报错 = 比写大了更糟）。

### 6.1 反向守卫：上限必须【贴着】

★ ★★ 只有「≤ 上限」的断言是**单向**的 ⇒ ★★ 若上限收得过紧
★★ （★ 比如把内容整段丢掉），断言会**空洞地**通过 ⇒ ★★ 那不叫「上限」。

★ ⇒ 加了反向断言：`total < MaxTurnBodyBytes-4096` ⇒ 红（★ 疑似把内容整段丢了）。

★ ★ 这条反向守卫在变异台 M03 里**直接救了场**（★ M03 会让内容被整段丢弃，
★ ★ 单向断言看不见，M03 的正向断言也不红 ⇒ ★★ 只有反向守卫能抓住它）。

## 十、诚实边界（★ 留给下一轮）

★ ① ★★ **上限是【行为变更】**：★ 从 1.5 MiB 收到 1 MiB ⇒ ★★ 已落库的历史行**不受影响**
★★ （★ 只影响新写入）⇒ ★★ 且截断标记会把被切的那轮标出来 ⇒ 事后可查。
★★ ★★ 但**没有任何门在盯「截断率」** ⇒ ★★ 若某类请求天然超 1 MiB ⇒
★★ ★★ 会持续被切 ⇒ ★★ 下一轮应加一条「截断率」观测（★ 不是加一个上限，是加一个**信号**）。

★ ② ★★ **「丢弃正文」是兜底而非常态**：★ `ContentRaw` 形状不可收缩时（★ 数字 / 布尔 / null）
★★ ★★ 会丢掉正文只留结构 ⇒ ★★ 下一轮应统计这条路径的命中率。

★ ③ ★★ **`fitMessage` 的二分是 O(log n) 次 marshal**：★ 单条消息很大时会重复编几次
★★ ⇒ ★★ 超大消息场景的 CPU 开销**未测**（★ 本轮用例最大 2 MiB，实测无感）。
