## §1 网关侧缺陷：`gw_session_*` 命名空间被自家守卫判死

### §1.1 现象（211 生产读数）

- `session_compressor` 日志持续出现 `invalid session_id` 与 `final cache commit failed`。
  修复前 1 小时窗口：**57 次 + 57 次**，涉 5 个活跃会话。
- `gw_session_*` 命名空间 **7124 轮**会话的 `compression_reason` **全空**
  ⇒ **压缩命中 0**；同期其它 `gw_*` 命名空间 **131283 轮**压缩正常。
- 受影响会话出站消息数：**平均 531 / 最大 1598 条**（平均 412236 tok、最大 1913478 tok）；
  正常命名空间 **平均 7 / 最大 167 条** ⇒ **≈ 76 倍膨胀**。
- 相邻轮次出站消息数在 **1 ↔ 548** 之间震荡 ⇒ 缓存永不落地，每轮从头累积。

### §1.2 根因链（四步，全部有仓内落点）

1. 客户端发 `session_<32hex>`（211 实测：47 个 distinct 会话 ID 中 **45 个 32hex + 2 个
   uuid-with-dashes**）。
2. `internal/sessionid/sessionid.go:54` `DeriveGatewayID` 派生成 `gw_session_<32hex>`。
3. `domains/hooks/compression/session_id_validator.go` 的 forbidden 列表含 `"session"`，
   旧判据是 **`strings.Contains(lower, f)`（子串）** ⇒ **网关自有命名空间整体被判死**。
4. ⇒ `session_compressor.go:311`（Prepare）走 `fallbackResult`（降级为「无会话模式」）、
   `:1009`（CommitFinal）直接报错 ⇒ 压缩历史断链、缓存永不落地。

★ 为什么长期没被发现：`docs/archive/process/specs/2026-07/session-forensics.md:219` 当时写的是
「生产数据都是 `gw_<uuid>` 形式，不会触发」——**这个前提在 211 已经失效**（客户端换了 ID 惯例），
于是守卫一直误伤却没人看见。

### §1.3 修法与两套实现的取舍（★ 本轮最关键的一次「自我否决」）

**上游并行会话 `02845e210` 已就同一根因提交了修法**（`keywordPrefixWithEntropy`）：
仅 `session` 关键字享有「**前缀段 + 分隔符 + ≥8 位非占位尾**」豁免；
`test` / `demo` / `default` / `temp` / `placeholder` 任何位置命中仍拒。
（该会话首版豁免面过宽——按形态一刀切放行全部关键字——被既有用例 `demo-user-456` 当场抓回，
故收窄为 **per-keyword 裁决**。）

**本会话同期独立产出的实现**（`hasHighEntropySuffix` 形态闸：结尾 ≥16 位连续 hex 即放行）
经对拍后**主动退役**，理由三条：

1. **功能重复**：同一根因，两套实现并存 = 两条真相源；
2. **本会话那套更宽**：形态闸不分关键字 ⇒ `test_<32hex>` / `demo_<32hex>` 也会被放行
   ⇒ **守卫被削弱**，与仓库最新教训（`LESSONS.md §568`：「豁免必须窄到『有真实熵的前缀惯例』
   且每种关键字单独裁决」）直接冲突；
3. **本会话那套更严**：形态闸要求结尾 16 位连续 hex ⇒ **`session_<uuid-with-dashes>` 形态会被误拒**
   ⇒ 会把 211 上真实存在的 2 个 uuid 形态会话重新打死（**修 A 引入 B**）。

⇒ 结论：**采用上游 per-keyword 窄豁免**，本会话保留**非重复**的两项贡献（见 §1.4）。

### §1.4 本会话保留下来的两项贡献

1. **e2e 路径覆盖**（`domains/hooks/compression/session_id_validator_r1029_e2e_test.go`）：
   上游补的是**校验器单测**（7 用例）；本会话补的是**压缩链整路径**——
   `Prepare` 不降级 + `CommitFinal` 不报错 + **缓存里真查得到条目**（比读内部字段更贴近真实后果），
   并带**反向自证**：真占位符 `test-session-123` 仍走降级路径（守卫没被削弱）。
   ★ 其中**uuid 形态单独成条**（`gw_session_<uuid-with-dashes>`）——
   它是「**修 A 不能引入 B**」那道防线的锚：若豁免被实现成「结尾必须是连续 hex」，
   这条用例立刻红。
   ★ **变异臂**（证明用例有牙齿，不是恒绿）：把上游豁免临时关掉
   （`keywordPrefixWithEntropy` 开头加 `return false`）⇒ **两条 e2e 立刻红**，
   报错正是生产形态 `session_id contains forbidden keyword 'session'`；
   还原后全绿（还原用 `cp` 备份回写，★ `git diff` 对该文件为空 ⇒ 逐字还原）。
2. **真实生产 ID 逐个复核**：把 211 库里 47 个 distinct `gw_session_*`（7448 轮）逐个喂给
   **上游真实实现**（不是复制一份判据）⇒ **47/47 全部放行**（含 2 个 uuid-with-dashes 形态）。

## §2 附图现象：网关字节干净，落点在客户端渲染层

### §2.1 三条独立证据（网关返回字节未被改写）

1. **DB 原文正则**：211 库 `session_turns.response_preview` 共 **21958** 条；
   含 `\n- ` 的 **4247** 条；而「连续 ≥10 行每行 ≤2 字符」与「连续 ≥10 行单字符」两种逐字切分形态
   —— **各 0 条** ⇒ 网关侧不存在逐字切分。
2. **IR 层字节级**：`ParseOpenAIResponse` → `SerializeOpenAIResponse` /
   `StreamChunk.SerializeOpenAI` / `SerializeResponses` / `normalizeOpenAIStreamContent`
   全部输出原样保留 markdown 列表与换行（探针为临时件，已从工作区删除，未入仓）。
3. **具体会话回读**：`gw_session_a41fb6452717cc67ce916c9259420154`（turn 129644）的
   `response_preview` 里 `- ` 列表与真实换行都在。

### §2.2 客户端 CSS 成因（证据取自 `/Applications/MiniMax Code.app` 的真实产物）

从 `app.asar`（353103418 字节）提取客户端真实 CSS（419 条规则）后逐条比对：

| 规则 | 作用 | 为什么会坏 |
|---|---|---|
| `.message-content` = `flex-1 relative max-w-full overflow-hidden text-pretty` | 消息正文容器 | 它是 flex item 且 `overflow≠visible` ⇒ **flex 自动最小尺寸被置 0** ⇒ 可被固定宽兄弟挤到 0 宽 |
| 兄弟占位：`flex:none; min-width:min(var(--chat-table-reading-width),var(--chat-table-viewport-width))` | 736px 固定宽兄弟 | 窄视口下**不可收缩** ⇒ 正文容器被吃光 |
| `.matrix-markdown code,div,li,p,pre,span{overflow-wrap:break-word;word-break:break-word}` | 断行规则 | 容器宽塌到 1~2 字符时 ⇒ **逐字断行**（这才是「一列单字符」的直接机制） |
| `.matrix-markdown ul ul>li::before{content:"○"}`（三级 `▪`）+ `li ol,li ul{margin:0 0 0 1.2em}` | 嵌套列表缩进 | 每级叠加缩进 ⇒ **bullet 逐级右移** |
| `.mavis-chat-markdown-flow{display:grid;grid-template-columns:minmax(0,1fr)}` | markdown 流容器 | grid item 同样需要 `min-width:0` 才不被内容顶开 |

★ 为什么「上方 `PROJECT:` / `GOAL:` 段落正常、只有列表塌陷」：
段落是流的直接子盒（拿整宽），而**列表项的可用宽 = 容器宽 − 各级缩进(1.2em × 层数) − marker 宽**
⇒ 中等窄度下段落仍完整、**嵌套越深列表项被饿得越狠** ⇒ 呈现出「段落正常 + 列表逐字一列 + 逐级右移」。

### §2.3 量化阈值（实测，浏览器逐档量测）

| 视口宽 | `.message-content` 实宽 | `li` 高度 | 形态 |
|---|---|---|---|
| 1280px | 544px | 24px | 正常（单行） |
| 900px | 164px | 96px | **塌陷**（逐字一列） |
| 800px | 64px | 360px | 塌陷 |
| 768px | 32px | 1200px | 塌陷 |
| 740px | 4px | 1200px | 塌陷 |
| 700px | 0px | 1200px | 塌陷 |
| 600px | 0px | 1200px | 塌陷 |

⇒ **触发条件**：`.message-content` 实宽 ≲ **164px**（本布局下视口 ≲ **900px**）时列表项开始逐字断行；
≲ **700px** 时正文容器宽 = 0 ⇒ 完全塌陷。
⇒ ★ 所以「**某些时刻**」= **当时视口宽度 / 兄弟占位布局**决定的，与网关的任何逻辑分支无关。

### §2.4 落点与修法建议

- **落点**：MCode 客户端渲染层（`MiniMax Code.app` 产物），**不在本网关仓**。
  本仓 `web/`、`web-mobile/`、`llm-gateway-client/`、`ai-session-manager` 均无该 markdown 渲染器
  （`ConversationMessagesPanel.vue` 用 `<pre>` 纯文本、`ChatMessageList.vue` 纯文本）
  ⇒ **本仓无法提交该修复**，只能交付定位 + 复现 + 建议。
- **给客户端仓的修复建议（按优先级）**：
  1. **固定宽兄弟改可收缩**：`flex: 0 1 auto; min-width: 0`（或窄视口媒体查询下沉/换行）；
  2. **给 `.message-content` 宽度下限**（如 `min-width: 280px`），或去掉 `overflow-hidden`
     （去掉后 flex 自动最小尺寸恢复为 min-content，塌陷随之消失）；
  3. `.mavis-chat-markdown-flow` 的 grid item 补 `min-width: 0`；
  4. `li` 断行属性改 `word-break: normal; overflow-wrap: break-word`
     （`word-break: break-word` 已废弃且会影响 min-content 参与塌陷）；
  5. 嵌套列表缩进改用 `padding-left`（内容盒内缩进）而非 margin 叠加，
     或限制**总缩进宽度**（如 ≤ 3 级、每级 ≤ 0.8em）。
