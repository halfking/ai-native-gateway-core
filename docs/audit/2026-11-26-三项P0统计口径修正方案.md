## 一、L87：对账快照日界统一修正

### 1.1 问题描述

**现象**：14 天对账快照里，7 天用 UTC 日界（08:00+08 起算）、7 天用上海日历日（00:00+08 起算）⇒ 同一 `report_date` 标签代表不同的 24 小时区间。

**受影响日期**（实测证据见主档 §六 D-01）：
- 11-11, 11-12, 11-13, 11-14, 11-15, 11-16（6 天，UTC 日界）
- 11-22（1 天，UTC 日界）

**根因**：`MissingRollupDates` 追赶路径用 pgx v5 扫描 `date` 列，pgx 固定返回 `time.UTC`，导致日窗计算从 UTC 00:00 起算。

**影响**：
- 对账页「供应商对账」与「内部对账」两张表的这 7 天数字，与看板英雄区、请求日志**必然不等**
- 11-22 在用户可见区间内（上周），内部对账差 +7,800、外部对账差 +8,399

### 1.2 修正方案

#### 步骤 1：备份现有快照

```bash
# 在 211 生产库执行（通过 SSH 隧道 or 252 本地）
pg_dump -h 127.0.0.1 -p 15432 -U llm_gateway -d llm_gateway \
  -t report_snapshots \
  -a --inserts --data-only \
  -f /tmp/report_snapshots_backup_$(date +%Y%m%d_%H%M%S).sql
```

#### 步骤 2：DRY RUN 确认影响面

执行 `scripts/audit/rollup-date-boundary-fix.sql` 的 DRY RUN 部分（已写入该文件）：

```sql
-- 查看将被删除的 56 行（8 scope × 7 天）
SELECT report_date, scope, scope_key, request_count, total_cost_usd, created_at
FROM report_snapshots
WHERE report_date::text IN ('2026-11-11', '2026-11-12', '2026-11-13', '2026-11-14', 
                             '2026-11-15', '2026-11-16', '2026-11-22')
ORDER BY report_date, scope, scope_key;
```

**预期输出**：每天 8 个 scope（daily_total, daily_by_provider, daily_by_model, daily_grain, internal_tenant, internal_person, internal_model, internal_grain）

#### 步骤 3：删除受影响快照

```sql
BEGIN;

DELETE FROM report_snapshots
WHERE report_date::text IN ('2026-11-11', '2026-11-12', '2026-11-13', '2026-11-14', 
                             '2026-11-15', '2026-11-16', '2026-11-22');

-- 预期删除行数：56（如果每天都有完整快照）

COMMIT;
```

#### 步骤 4：重新生成快照（上海日历日）

**方案 A**：通过管理端 API（推荐，可审计）

```bash
# 需要 super_admin JWT
for date in 2026-11-11 2026-11-12 2026-11-13 2026-11-14 2026-11-15 2026-11-16 2026-11-22; do
  curl -X POST https://api.example.com/api/admin/report-rollup/run \
    -H "Authorization: Bearer $ADMIN_JWT" \
    -H "Content-Type: application/json" \
    -d "{\"date\": \"$date\"}"
  echo "Triggered rollup for $date"
  sleep 2
done
```

**方案 B**：等待 worker 自动追赶（每天 02:30 UTC+8 检查缺失日期）

注意：worker 会自动检测到这 7 天缺失并重新生成，但需要等到次日凌晨。

#### 步骤 5：验证修正结果

```sql
-- 验证 11-11（示例，其余日期重复执行）
SELECT
    rs.report_date,
    rs.scope,
    rs.request_count as snapshot_count,
    (SELECT COUNT(*)
     FROM usage_facts
     WHERE occurred_at >= '2026-11-11 00:00:00+08'::timestamptz
       AND occurred_at < '2026-11-12 00:00:00+08'::timestamptz
       AND CASE
             WHEN rs.scope IN ('daily_total', 'daily_by_provider', 'daily_by_model', 'daily_grain')
             THEN true  -- 外部：全流量
             ELSE traffic_class = 'business'  -- 内部：仅 business
           END
    ) as facts_count,
    rs.request_count - (SELECT COUNT(*)
                        FROM usage_facts
                        WHERE occurred_at >= '2026-11-11 00:00:00+08'::timestamptz
                          AND occurred_at < '2026-11-12 00:00:00+08'::timestamptz
                          AND CASE
                                WHEN rs.scope IN ('daily_total', 'daily_by_provider', 'daily_by_model', 'daily_grain')
                                THEN true
                                ELSE traffic_class = 'business'
                              END
                       ) as diff
FROM report_snapshots rs
WHERE rs.report_date = '2026-11-11'
  AND rs.scope IN ('daily_total', 'internal_tenant');
```

**预期结果**：`diff` 应全为 0，证明新快照已对齐上海日历日窗口。

### 1.3 代码层防复发（可选）

**问题根源**：`domains/reportrollup/rollup.go:752-770` 的 `MissingRollupDates` 用 `generate_series(...)::date` 扫回 `time.Time`，pgx v5 对 `date` 列固定返回 UTC Location。

**修正方案**：在 `MissingRollupDates` 返回后，显式转换为系统时区：

```go
// domains/reportrollup/rollup.go:770 附近
for rows.Next() {
    var d time.Time
    if err := rows.Scan(&d); err != nil {
        return nil, err
    }
    // 修正：pgx date 列固定返回 UTC，需转换为系统时区
    d = settings.SystemDayStart(d)  // 转为 Asia/Shanghai 00:00:00
    dates = append(dates, d)
}
```

**验证**：补一个真库门，断言「对账快照 daily_total 请求数 = 同日 usage_facts 上海日历日窗口全量」。

## 二、L88：会话与统计页模型榜复制放大

### 2.1 问题描述

**现象**：「会话与统计」页「模型榜」用 `unnest(ss.models_used)` 展开模型行，把**整会话**的 `total_cost_usd` 与 `request_count` **复制到每一个模型行**。

**实测放大率**（W，11-17..11-23，984 宇宙内 38,112 会话）：
- 费用：$8,598.1243 → $9,840.6756（**+14.45%**）
- 请求数：77,120 → 118,727（**+54.0%**）

**状态**：
- 复制语义在现役与 HEAD **都有** ⇒ **现网正在放大**
- 披露文案（`modelUsageExpansionReason`）只存在于**并发会话的未提交工作树**中 ⇒ **现网用户看不到提示**

### 2.2 修正方案

**本轮不实施修正**，理由：
1. 并发会话已有在制代码做披露（`web/src/components/analytics/SessionStatsRankings.modelCostDisclosure.spec.ts`）
2. 本轮只补充**当窗实测放大率**（+14.45%），订正主档 F1 登记的「+70.9%」是历史值

**待并发会话提交后的两种方案**：

#### 方案 A：先上披露（快速止血）

优点：不改数字语义，只加提示
缺点：数字仍然放大，用户需要自己理解

#### 方案 B：改为按模型分摊（正确但需 owner 拍板）

```go
// admin/dashboardapi/session_overview.go:666-668 附近
// 当前：
// SELECT unnest(ss.models_used) AS model, ss.request_count, ss.total_cost_usd ...

// 修正为：
// SELECT 
//   unnest(ss.models_used) AS model,
//   ss.request_count / array_length(ss.models_used, 1) AS request_count,
//   ss.total_cost_usd / array_length(ss.models_used, 1) AS total_cost_usd,
//   ...
```

**注意**：分摊会改变面板数字，属口径变更，需 owner 明确决策。

### 2.3 本轮交付

**仅补充实测数据**，登记进主档 §八 L96：

> **L96**：F1 登记的「+70.9%」是历史时点值；实测窗口起 11-12 = **+71.3%**（可复现），起 11-17 = **+14.45%**；膨胀率 = 加权平均「每会话模型数」− 1

## 三、L89：请求日志「含探测」与供应商对账不等

### 3.1 问题描述

**现象**：前端文案宣称「开启含探测 = usage_facts 全量 = 供应商对账」，但实测**少 6,282 条（−3.3%）**。

**差集构成**（W，usage_facts 有、两臂都没有的行）：

| traffic_class | status  | 行数  | 费用     | token   |
|---------------|---------|-------|----------|---------|
| probe         | failure | 4,978 | $0.0000  | 146,770 |
| probe         | success | 1,303 | $0.1812  | 267,248 |
| business      | success | 1     | $0.0001  | 5,692   |

**根因**：探测臂用 `INNER JOIN usage_facts`（`db/session_probe_arm_source.go:188-197`），只纳入「probe_hot 里有行、且事实表里有 fact」的行 ⇒ **有 6,281 条探测事实既不在业务两臂、也不在探测臂**。

### 3.2 修正方案

#### 方案 A：改文案，披露真实集合（推荐，零生产写）

修改两处文案：

**① `web/src/views/RequestLogsView.vue:101`**

```vue
<!-- 当前 -->
<el-tooltip content="开启后显示所有请求，包含探测请求（与供应商对账数据一致）" placement="top">

<!-- 修正为 -->
<el-tooltip content="开启后显示业务请求与部分探测请求（探测请求仅包含有使用记录的请求；完整探测请求见供应商对账）" placement="top">
```

**② `web/src/locales/zh-CN/requests.ts:67`**

```typescript
// 当前
includeProbesHint: '开启后显示所有请求，包含探测请求（与供应商对账数据一致）',

// 修正为
includeProbesHint: '开启后显示业务请求与部分探测请求（探测请求仅包含有使用记录的请求；完整探测请求见供应商对账）',
```

#### 方案 B：改探测臂为 LEFT JOIN（需 owner 决策）

```go
// db/session_probe_arm_source.go:188-197
// 当前：INNER JOIN usage_facts（只有有 fact 的行才进）

// 修正为：LEFT JOIN usage_facts（所有探测行都进，无 fact 的填 NULL）
```

**注意**：
- LEFT JOIN 会让「含探测」口径与「供应商对账」分叉（后者只含有 fact 的行）
- 需要 owner 决定：「含探测」是指「所有探测请求」还是「有使用记录的探测请求」

### 3.3 推荐方案

**先上方案 A（改文案）**，理由：
1. 零生产写，风险最小
2. 披露真实集合定义，避免用户误解
3. 给 owner 时间决定探测臂的真实语义

## 六、风险与回滚

### L87 回填风险

**风险点**：
- 删除快照后，对账页会短暂显示缺失日期
- 重新生成期间（约 5-10 分钟），用户可能看到不完整数据

**缓解措施**：
1. 在低峰时段执行（建议凌晨 02:00-04:00 UTC+8）
2. 提前备份快照表
3. 执行前通知用户「对账数据维护中」

**回滚方案**：
```bash
# 从备份恢复
psql -h 127.0.0.1 -p 15432 -U llm_gateway -d llm_gateway \
  -f /tmp/report_snapshots_backup_YYYYMMDD_HHMMSS.sql
```

**风险点**：几乎没有（静态文案修改）

**验证**：前端构建 + 部署到 staging 验证 tooltip 显示正确
