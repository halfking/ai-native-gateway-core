## 0. 摘要

### 0.1 三句话结论

1. **两份规划总体成立，且互补不重复**：《价格档》管「行情 → 评分 → 路由参数」这条**成本侧**链路，《运营档》管「菜单 → 计费闭环 → 用户自助」这条**商业侧**链路；两线在 `model_credit_rates`（零售价）、市场参考价页面、四方对账三个点交汇。本轮对两档共 **46 项承重论断**做了代码级复核：**40 项完全成立、4 项内容成立但引据有偏、2 项需要设计修订**（§1）。
2. **审计新挖出 3 处规划未见的真问题**：① `TenantRevenueUSD` 把 CNY 分当美分除 100，**毛利字段混币种**（《价格档》引用了 0.1、运营档引用了 0.01，两档各执一词而底层本就冲突）；② `credit_ledger` 的「0 行」读数**可能是量具口径假象**（写入方直写 `credit_ledger_hot`，计数打父表）——《运营档》P0-2 的前提需要先重测；③ `/ops/*` 路径前缀**已被 opsplatform 组占用**（`/ops/vibecoding` 在役 + 5 条 `/ops/*` 重定向），《运营档》的菜单路径全部要改前缀。
3. **实施规划收敛为 6 个工作流（W1–W6）、4 个阶段（P0–P3）、16 条待裁决（A-1…A-16）**：P0 全是数据与地基动作（含一处**建议立刻修的路由零价缺陷**——且修法比《价格档》原方案更细：必须按 `billing_mode` 分档，否则会把 87.6% 的周期套餐错打成「未知价」）。

### 0.2 一句话给决策者

> **商业骨架与行情层都已存在，缺的是四根线：把价填真（P0 数据清理）、把账记全（credit_ledger 三列 + 单位口径统一）、把行情接进来（三张表 + 同步器）、把入口收成一节（operations 菜单组）——而路由侧唯一要立刻动的是那个「零价=最便宜」的不自洽。**

### 1.3 审计发现（AF 清单）

#### AF-1（★★★★ 单位口径冲突——两档各执一词，底层本就矛盾）

- **现象**：《运营档》说 `cents_per_credit=0.01`，《价格档》说「默认 0.1 分/积分」。**两个都对——引用了两个不同的源**：DDL 默认 `0.1`（`db/maas_schema.go:28`、迁移 007:16、`defaultCentsPerCredit=0.1` `domains/reportrollup/rollup.go:151`）；**生产种子行写 0.01**（`02-seed.sql:484`，currency=CNY）。
- **更深一层（本轮新发现的生产级缺陷）**：同一个值在两处消费**单位语义相反**——
  - `maas/bills.go` `AmountCentsFromCredits`：`amount_cents = credits × cents_per_credit` ⇒ 把它当 **CNY 分**（配合 currency=CNY 记账单金额）；
  - `maas/consumption_detail.go:116`：`TenantRevenueUSD = credits × cents_per_credit / 100` ⇒ 把它当**美分**除 100 折 USD。
  ⇒ 当 currency=CNY、cents_per_credit=0.01 时，`TenantRevenueUSD` 实为 **CNY 元**却以 USD 名义与真 USD 的 `UpstreamCostUSD` 相减 ⇒ **`GrossMarginUSD` 混币种**（偏大约 7.2 倍的假毛利）。这正是《价格档》「毛利只有一处算」要依赖的那个字段。
- **设计裁定（进 §2.4 与 A-14）**：`cents_per_credit` 语义钉死为**分/积分（账单币种的分）**；`consumption_detail` 的 USD 换算必须经 `CNYToUSDFX`（或按 `currency` 分档）；P0 增加一条「毛利口径修复」任务。

#### AF-2（★★★ `/ops/*` 前缀已被占用——《运营档》菜单路径需全改）

- **现象**：`web/src/router.ts:363-367` 已有 5 条 `/ops/* → /maintain/ops/*` 重定向；`:368` 有在役路由 `/ops/vibecoding`（菜单挂在 `opsplatform` 组，`appNav.ts:234`）。「ops」在本仓前端语义已锚定为**运维平台**。
- **修订**：运营管理组的新页面路径一律改用 **`/operations/*`**（overview/plans/campaigns/customers/pricing/market-prices/price-compare/reconciliation）；组 id 用 `operations`（现无冲突，现有组 id：tenant-portal/models-routing/tenant-users/requests-sessions/data-ops/opsplatform/guide/chat）。

#### AF-3（★★★★ `credit_ledger`「0 行」可能是量具口径假象——P0-2 前提要重测）

- **现象**：《运营档》据 `SELECT count(*) FROM credit_ledger`（父表）= 0 断言「积分流水不存在 ⇒ 用户侧没有底账」。
- **复核**：**写入方不仅存在，而且是 2026-07 数据生命周期架构的刻意设计**——`writeLedgerWithBalance`（`maas/service.go:672-693`）**直写 `credit_ledger_hot`**（注释明言「never the parent table」），由 `bg/partition_manager.go:1806` 的 `promote_credit_ledger_hot_to_partition` 定期提升进月分区；另有 `bg/ledger_reconciliation.go` 整套 hot↔request_logs 对账 job。**计数打父表读不到未提升的 hot 行。**
- **两个连带后果**：
  1. `ListLedger`（`service.go:643`，租户「我的账本」端点的底座）`FROM credit_ledger` **只读父表** ⇒ 提升滞后窗口内的最近流水对租户不可见——**读侧必须 hot ∪ 分区两臂并读**（与 LESSONS §609「backfill 只读 hot 漏 77%」同族教训，这次是同一张表的正反两面）。
  2. `ReconcileTripartite` C 侧（`reconcile.go:45-50`）同样只读父表 ⇒ C 侧系统性低估，`LedgerConsume` 字段不可信。
- **修订**：P0-2 第一步改为「**先量真**」：`credit_ledger_hot` + 各月分区分别计数 + 确认 promoter 在跑；若 hot 有行，「打通流水」退化为「读侧两臂并读 + 对账口径修正」。

#### AF-4（★★★ CostWeight 默认 0.15 非 0——《价格档》的「同族默认 0」引据错了一半）

- **现象**：`router_scoring.go:93` `CostWeight: envFloat("LLM_GATEWAY_ROUTING_W_COST", 0.15)` —— **执行层成本分在生产是活的**；`:24-26` 注释「默认 0（关闭）」与代码矛盾（注释过时）。IQWeight/OutlierWeight/CacheAffinityWeight 默认 0（:94,97,100）属实。
- **两个后果**：① 新维度 `MarketAdvantageWeight` **默认 0 的设计原则仍正确**，但范本只能引 IQ/Outlier/CacheAffinity，不能引 CostWeight；② **零价不自洽缺陷（AF-15）在执行层已实际参与排序**（0.15 权重）⇒ 修复优先级上升为 P0 立即项。

#### AF-5（★★ board-operational 是白名单孤儿，且后端隔离未落实）

#### AF-7（★ 键形状：credential_model_bindings 主键是代理键）

PK = `id`（迁移 612 补）；`(credential_id, provider_model_id)` 是 **UNIQUE 约束**（`sql/objects/constraints/..._cmb_unique_credential.sql`）。《价格档》`supplier_market_position` 以组合键做逻辑主键**可行**（PG 允许 FK 指向 UNIQUE 约束），DDL 注释写明即可。

#### AF-8（★★ 两档主键风格不一致：canonical_name vs canonical_id）

《价格档》`market_price_reference` PK 用 `canonical_name`（text，行情侧名字空间），《运营档》`tenant_model_rates` 用 `canonical_id`（bigint，网关侧）。**两者其实各自正确**（前者是同步输入空间、后者是租户配置空间），但消费侧必须能互跳。**统一设计**：`market_price_reference` 增加 `canonical_id bigint NULL` 解析列 + 部分唯一索引（解析成功者唯一）；网关侧消费（评分、路由投影）优先走 id，未解析行走名字匹配并计数（`unresolved` 进同步台账拒绝族统计）。

#### AF-9（★★ 两档编号体系冲突）

两档各有自己的 §10「待裁决 10.1–10.7」与「P0-1…」，编号互相冲突（如《价格档》P0-4=修零价、《运营档》P0-4=支付通道）。本文统一重编号：裁决 = **A-1…A-16**（§3.5），任务 = **W1…W6 × T 编号**（§3.1）。

#### AF-10（★★★ TripartiteOK 的判据真相——《运营档》P0-3 的验收门写错了对象）

`reconcile.go:21-22` 注释与 `:65` 实现明写：**`TripartiteOK` 只比 bucket vs bill**（`BucketsMatchBill` 是出账正确性硬门），ledger 侧因「套餐额度覆盖用量时不产生钱包流水」**允许 lag/diverge**，只作观测。《运营档》P0-3「三方对账跑绿 = TripartiteOK 成立 ⇒ C 侧非空」把 C 侧塞进了它不参与的谓词。**修订**：P0 验收拆两门——① `BucketsMatchBill`（既有硬门）；② 新增「C 侧可解释率」观测门（ledger 差额 = 套餐额度扣减 + 欠费放行之和，可对账到行）。

#### AF-11（★★★ 欠费现状 = 放行 + Warn——计费目前是观测不是执行）

`domains/streaming/handler.go:7160-7171`：扣费失败（含 `InsufficientCreditsError`）只 `slog.Warn("maas charge failed")`，**请求照常成功**；`reqLog.CreditsCharged` 留空。连带：`BackfillCreditConsumptionBuckets`（`maas/credit_buckets.go:42`）从 request_logs 按 token **反算应计**积分灌桶 ⇒ **桶（应计）≠ 流水（实扣）的差 = 欠费/未扣**。这解释了「桶 266 行 vs 流水 0 行」的另一种可能成因（钱包从未充值 ⇒ 全部扣费失败回滚 ⇒ 流水空、桶由回填器填满）。**设计含义**（A-15）：是否硬拦截欠费是产品决策，默认维持放行 + 告警；但「欠费台账」必须先可见（见 §2.4）。

#### AF-12（★ `chargeTokensWithMultiplier` 的门）

`service.go:141` `if !s.Enabled() || tenantID == "" || tenantID == "default"` ⇒ 计费是否发生取决于部署是否注入 pool + 租户归属。P0 观测项：生产 `maas.Enabled` 状态与 charge 调用成功率（日志 `maas charge failed` 计数）。

#### AF-13（★ 消费桶双写路径）

桶有两个写者：热路径提交后累加（`service.go:248-257`，实扣口径）与启动回填（`credit_buckets.go`，应计口径，`ON CONFLICT DO UPDATE` 直接覆盖）。**应计覆盖实扣** ⇒ 桶上做账单要意识到口径是「应计」。《运营档》§1.1 把桶直接当「消费桶=扣费」引用，需带此注脚。

#### AF-14（★ 通知域可复用面比《运营档》写的更宽）

`domains/notification/` 含 email/dingtalk/lark/webhook/wechat + approval_notifier/inspector_notifier ⇒ 预算告警三通道（站内/邮件/企微）都有现成 sender。

#### AF-15（★★★★ 零价缺陷的正确修法必须按 billing_mode 分档——对《价格档》P0-4 的实质修订）

- 《价格档》主张 `blended <= 0 → 中性`（不再当最便宜）。**复核后发现这个一刀切会误伤**：177 条有价绑定里 **155 条是 `token_plan`**（周期套餐，钱已付、边际成本≈0）——对它们，「0/0 + 价格分 100」**语义上是对的**（executors 侧同样给 round-1 计费模式 0 惩罚，两层在这 155 条上其实**一致**）。
- **真正错的是**：`per_token`/`token` 模式 + 0/0 或未知价（=《价格档》点名的 141 空价中属按量计费的那部分 + 9 条对称占位价）被 autoroute 当「最便宜」（100）而 executors 当「最贵」（1.0）——**同一子集两层相反**。
- **修订后的修复规格（W5-T1）**：两层的判定统一为**先 billing_mode 后价格形态**——
  1. `billing_mode ∈ round-1 {free, token_plan, code_plan, agent_plan, monthly}`（`provider/billing.go:8-16`）⇒ 边际≈0，维持优待（autoroute 100 / executors 0 惩罚，**现状不动**）；
  2. 其余模式且 `blended <= 0` 或价未知 ⇒ **中性**（autoroute：价格分按「无信号」处理——建议给池中位值而非 100，并落 `price_signal_absent` 日志；executors：`calculateCostPenalty` 的 1.0 是否同步降为中性**留待影子数据裁决**，见 A-4）；
  3. `is_free` 标记语义同步收窄为「round-1 计费模式」而非「价格算出来是 0」（`index.go:577-582` 的 CASE 分支）。
- **必须同时改两处**（`scoring.go:245-247` + `scoring_simplified.go:260-262`，v2 主链经 `scoring_v2.go:55` 走后者）+ 连带修正两处 `free or unknown` 注释与既有测试期望值。
