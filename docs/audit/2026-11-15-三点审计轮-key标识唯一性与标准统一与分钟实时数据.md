# 2026-11-15 三点审计轮——apikey 并发限制（key 标识唯一性 / 标准统一 / 分钟实时数据）

> 前序：本轮是「并发限制双重标准深度审计报告」（同日早轮，b72aef5f7：
> executors 四处对齐 ConfiguredConcurrent）之后，用户追加的三点审计。

## 一、任务与结论总览

| 审计点 | 用户要求 | 审计结论 | 处置 |
|---|---|---|---|
| ① key 标识唯一性 | 并发的 key 的键值不为 null，应按每个 key 唯一标记 | 闸以 `keyInfo.ID`（int，来自 `ak.id` 主键）为 map 键，生产 Verify 链恒>0；**但无 ID≤0 防御守卫**——坏缓存/畸形构造会把所有无效身份聚到共享桶 `used[0]`，不同 key 互相挤占误拒 | 加守卫：`ID<=0` → WARN + bypass（宁不执法不共享桶）+ 钉测 |
| ② 标准统一 | 并发限制由 apikey 设定统一标准，不得多处不同标准 | executors 4 处已对齐（上轮 b72aef5f7）✅；**但并发闸只盖 chat/messages/responses 三个生成面**——embeddings/audio(STT/TTS)/images/videos/count_tokens 六面既不被硬闸盖、也不传 KeyConcurrentLimit（软告警跳过）= 同 key 不同端点不同标准 | 闸扩面到六面 + 身份回退解析（这些面不写 context memo）+ AST 钉测防回退 + main.go 陈旧 slog 文案订正 |
| ③ 分钟实时数据 | 并发数据定时更新，写入每个 key 的实时数据，按分钟 | 全新观测面：闸内分钟累计（peak/rejected/limit）+ bg worker 每 60s UPSERT 进迁移 965 新表 `api_key_concurrency_minute` | 闸扩展 + worker + 迁移 965 四通道登记 |

## 二、点①：key 标识唯一性

### 审计发现

- 闸的桶键 = `keyInfo.ID`（`map[int]int`）。身份来源链：
  `prepareSanitizeRequest`（chat/messages/responses 写 context memo）→
  `VerifiedKeyInfoFromContext` → ID 来自 `SELECT ak.id`（serial 主键，恒>0）。
- **缺口**：`serve()` 无 `ID<=0` 守卫。ID=0 的异常身份（坏缓存条目/测试夹具/
  未来构造路径）会全部落 `used[0]`——一个共享桶，不同「key」互相占用并发槽，
  制造与「211 空 session 共享窗口」同族的误拒形态。
- 对照：executors 侧 limiter.AcquireAll 已有 `keyID > 0` 守卫（limiter.go:583），
  闸侧缺同款。

### 修复（key_concurrent_gate.go serve）

```go
if keyInfo.ID <= 0 {
    slog.Warn("key_concurrent_gate: non-positive key id, bypassing", ...)
    next.ServeHTTP(w, r)
    return
}
```

钉测：`TestKeyConcurrentGate_NonPositiveIDNeverBuckets`（ID=0×2 笔+负 ID 全放行；
采样面同样无 key≤0 样本）。变异臂：删守卫 ⇒ 第二笔被共享桶误拒 ⇒ 红。

## 三、点②：标准统一（不得多处不同标准）

### 审计发现（三个残留缺口）

1. **闸覆盖面缺口**（主要）：并发闸只 Wrap 三个生成面。同一把 key（显式帽 N）
   在 `/v1/embeddings`、`/v1/audio/transcriptions|speech`、`/v1/images|videos/generations`、
   `/v1/messages/count_tokens` 上**不受并发帽约束**——这些面的 handler 也不设
   `KeyConcurrentLimit`（executors per-key 软层同样跳过）。
2. **身份回退缺失**：上述六面的 handler 各自直接 `keyVerifier.Verify`，不写
   `sanitizeVerifiedKeyContextKey` ⇒ 直接 Wrap 闸会因读不到身份而**空转**
   （静默 no-op——比不包更隐蔽）。
3. **陈旧文案**：main.go:7472 slog 仍写 `NULL=tier default`——与 explicit-only
   （NULL=uncapped）语义相反，误导运维。

### 修复

1. **闸扩面**（main.go）：六面全部 `keyConcurrentGate.Wrap(...)`：
   - `/v1/embeddings`、`/v1/audio/transcriptions`、`/v1/audio/speech`、
     `/v1/images/generations`、`/v1/videos/generations`、`/v1/messages/count_tokens`
2. **不包面（有意，登记理由）**：`/v1/audio/refine|analyze`、`/v1/summarize*`、
   `/v1/classify`、`/v1/mcp`——其 LLM 步**环回 chat 面携带同一把 key**，
   chat 闸已计一次；外层再包 = 一次逻辑调用占两个并发槽（与
   `authenticateNoRPM` 的 RPM 不双计纪律同款——audio_transform.go:79 注释）。
   直连打爆这些面最终仍被环回 chat 步的同 key 闸拦住，无绕过。
3. **身份回退**（key_concurrent_gate.go）：`SetVerifier(KeyIdentityVerifier)` +
   `resolveIdentity`——context memo 缺失时按 Bearer token 自行 Verify
   （cache-backed：Verify 内部有 60s TTL cache + singleflight，handler 内的
   二次 Verify 是 map 命中，零额外 DB 开销）。回退失败 = 无身份 = 豁免直通
   （无效 key 由各 handler 自己的鉴权拒绝，闸不越权）。
4. **AST 钉测**：`TestKeyConcurrentLimitProducersUseConfigured`
   （key_concurrent_limit_pin_test.go）——扫描本包全部 `KeyConcurrentLimit`
   赋值点：必须含 `ConfiguredConcurrent`、不得含 `EffectiveConcurrent`。
   变异验证：改回一处 ⇒ 红（还原绿）。
5. **文案订正**：`config_source` slog 改 `explicit-only: NULL/0=uncapped, N=cap`。
6. **守卫门联动**：`dataplane_guard_surface_test.go` 的 head 提取器扩展
   **透传中间件解包**——`keyConcurrentGate.Wrap(inner)` 的守卫分类锚 = inner
   （六面守卫类各异：exempt count_tokens ≠ registeredGap embeddings，不能共享
   一个台账键）。变量名+构造器双重钉（`streaming.NewKeyConcurrentGate` 赋值闭包）。

### 标准现状（收口后）

| 执法/观测点 | 口径 | 覆盖面 |
|---|---|---|
| KeyConcurrentGate（硬 429） | `ConfiguredConcurrent`（explicit-only） | chat/completions/messages/responses + embeddings + audio STT/TTS + images/videos + count_tokens |
| executors AcquireAll(per-key 软告警) | `ConfiguredConcurrent`（上轮对齐） | 经 executors 的生成面 |
| 环回 LLM 步（refine/analyze/summarize/mcp） | 由环回跳的 chat 闸执法（同 key） | 单次计槽不双计 |
| RPM/TPM 链 | `EffectiveRPM`/`EffectiveTPM`（各列独立语义，非并发维度） | 不变 |

## 四、点③：分钟实时数据（迁移 965）

### 设计

```
KeyConcurrentGate（进程内）
  ├─ used[keyID]             实时在飞（既有）
  ├─ minutePeak[keyID]       窗口内峰值（新）
  ├─ minuteRejected[keyID]   窗口内 429 次数（新）
  └─ minuteLimit[keyID]      生效帽（新）
        │ 每 60s
        ▼
SnapshotAndResetMinute() → bg.KeyConcurrencyStatsWriter
        │ UPSERT（batch）
        ▼
api_key_concurrency_minute（迁移 965）
  (minute_ts, api_key_id, instance_id) PK
  in_flight / peak_in_flight / rejections / concurrent_limit
```

关键语义：
- **空窗口零写**：无活动 key 无行（零行=零并发），表极小。
- **跨窗播种**：窗口切换时仍在飞的请求播种为新窗口 peak 下界
  （否则长请求跨窗出现 peak=0 而 in_flight=1 的自相矛盾读数）。
- **幂等 UPSERT**：同分钟双窗口 peak 取 GREATEST、rejections 累加（并集语义）。
- **instance_id 进主键**：蓝绿双槽并行期各写各行（进程内计数 per-instance）；
  聚合读面按 `(api_key_id, minute_ts)` SUM/MAX 取全域视图。
- **retention 7d**：worker 每小时 trim（`LLM_GATEWAY_KEY_CONCURRENCY_RETENTION` 可调）。
- **失败自愈**：表缺席（down 迁移）WARN 不停 worker；执法完全不受影响。
