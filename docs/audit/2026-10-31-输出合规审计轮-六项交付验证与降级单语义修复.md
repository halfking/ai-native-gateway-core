## §3 F2：降级单语义错误（本轮修正）

### §3.1 定性

迁移 917 对 sanitize_block_reviews 的契约是「每次 output/egress **硬阻断**一条」；
921 的降级留痕设计（finish() 的 `w.degraded` 分支复用 `registerPolicyBlockReview`）
让它突破了这条契约。三重后果：

1. **灌爆**：降级不是小概率事件 —— 缓冲上限是存储审计定死的 1 MiB wire cap
   （10-30 审计轮 A3 的裁决），长响应（glm-5.3 reasoning 流）持续越界，
   ~230 条/天 ⇒ 审核面的「显示所有被拦截的请求」被非拦截遥测淹没。
2. **死操作**：对降级单点「批准」会为 `builtin.guard.capacity_exceeded` 写一条
   7 天放行 —— 而放行表只被内容规则读面（security/sanitize/output_sensitive.go 的
   `egressReleaseAllowed`）消费，合成哨兵规则**没有任何消费方** ⇒ 看起来能操作、
   实际什么都不做（拒绝同理；标注也无法喂自动优化——maybeAutoRelax 已显式豁免
   `builtin.guard.*`）。
3. **徽标失真**：pending_count 把降级单计成「待审拦截」。

### §3.2 修法（迁移 926；遥测语义，不回退 921 的留痕设计）

- `sanitize_block_reviews` 末尾追加 `degraded BOOLEAN NOT NULL DEFAULT false`，
  并回填 `rule_id LIKE 'builtin.guard.%'` 存量行（回填边界见迁移头注释：block
  模式部署的容量终断是硬阻断、会被标成 degraded —— 当前在跑部署全为 release）。
- 登记链：`PolicyBlockReviewInput.Degraded` → `BlockReviewInput.Degraded` →
  两条 Add 路径（DB / 内存）都携带；finish() 降级路径置 `Degraded: true`。
- 消费口径三处：待审数改 `CountPendingBlockDecisions`（pending 且非降级）；
  insights 读数 `WHERE NOT degraded`（DB + 内存同口径）；前端渲染只读遥测行
  （降级徽标 + 说明行；隐藏批准/拒绝/标注操作；证据/上下文/归因照常展示）。
- 让号记录：925 曾被 session_bodies 叶 TRP 索引 heal 占用后撤销（db-changelog
  有记录）⇒ 按「后到者取下一个空闲号」取 **926**。登记面七点全齐
  （正本 / embeddata×2 / dbinit runner / 部署序列 / db-changelog+sha256 / tsv
  随测试重生成）+ 静态契约门（migration_926_sanitize_block_review_degraded_test.go，
  含防回退断言「只加列不接消费面等于没修」）。

## §4 F3：insights 带租户过滤恒 503（既有缺陷，本轮顺带修掉）

`BlockReviewInsightsDB` 的拼接是 `FROM sanitize_block_reviews` + ` AND tenant_id=$N`
—— **没有 WHERE 前缀**，租户过滤时生成非法 SQL。触发条件：租户管理员打开读数
（tenant 恒非空）或 super_admin 带 `?tenant_id=`；无过滤路径语法恰好合法，这正是
10-29/10-30 两轮终验（都是 super_admin 无过滤）没抓到它的原因。修法与回归门：
`WHERE NOT degraded` 起头（与 F2 的排除口径合并落地）+ sqlmock 断言 SQL 形状
（`TestPgInsightsTenantFilterIsLegalSQL`：WHERE 必须先于 AND）。
