## 2. ② 压缩格口径：先量，再定，后接

### 量的结果（211 生产 acc-pg17 `llm_gateway`，session_turns 解耦表）

| 口径 | 7 天（36,509 turns） | 全量（119,510 turns） |
|---|---|---|
| token_band ∈ {preliminary, forced}（旧格判据） | 3,676（10.1%） | 5,579（4.7%） |
| compression_strategy ∉ {'', 'delta_append'}（实际改写） | 4,665（12.8%） | 8,932（7.5%） |
| 两口径并集 | 4,745 | — |

- **band=below 但实际压缩了：7 天 1,069 条**。机理（`window.go`）：
  滑窗压缩有三个与绝对档位（200k/400k token）**无关**的触发器——
  COUNT（消息数 ≥50）、相对窗口（contextWindow×0.8×3.5 字符）、IDLE；
  它们触发时 band 可以是 below。211 全量 strategy 分布只有
  `sliding_window_count/token_absolute/token`（LLM summary 环回 + memo 回放）。
- **band 越线但什么都没改成：7 天 80 条**（summary 失败且 mechanical trim
  无收缩——档位观测在，实际压缩没发生）。
- 4xx 恢复环回族（mechanical_trim/smart_window_llm/llm_summary/…）：
  **211 全量 0 条**——接入它们对本实例读数零影响，但同一把尺
  （compression_strategy 字段）天然覆盖，顺手包含。
- delta_append：211 全量 0 条；排除是语义判据（会话增量组装不是压缩）。

**结论：差异系统性存在（7 天 +29%，全量 1.6×），值得换判据。**

### 定与接

- 后端 SSE `LiveRequest` 新增 additive 字段 **`compressed bool`**（omitempty）：
  判据 = `entry.CompressionStrategy ∉ {"", "delta_append"}`。同一把尺覆盖
  滑窗 LLM summary 环回、memo 回放、mechanical_trim、4xx 恢复全族。
- ★ 顺带修正 `TokenBand` 字段注释的**错误声明**（「preliminary|forced =
  本条请求触发过上下文压缩」——实测为假，§507 通式七「语义与直觉不符
  必须写进注释」的镜像：注释写错了同样会误导下一个人）。
- 前端：`gatewayModuleStats` 压缩桶判据从 `token_band ∈ {pre,forced}` 换成
  `compressed === true`（注释带实测读数）；store/graph 类型补字段；DEV
  预览夹具改标 compressed（1/6 密度，band 故意混 below/forced 两态）。
- 测试：Go 端 omitempty 双向断言扩到五键 + 两个负例（delta_append 不算、
  band=forced 无 strategy 不算）；前端 filter 判据测试改写
  （below+compressed 计入、forced 无 compressed 不计入）。

### 9.2 ★ 本轮新抓的真缺陷：passthrough 模型被并成一行（两轮共有）

§8 漏掉的一个口径缺陷——**models-today 的 `GROUP BY canonical_id` 把
canonical_id=0 的所有 passthrough 模型合并成一行、名字 `MAX()` 任选**：

- 图口径 `modelKeyOf`（liveTopologyGraph.ts:155）：canonical 空 ⇒ 按**原始名
  分节点**——189 个 raw 名 = 189 个模型节点；
- 211 生产实测（acc-pg17 llm_gateway，stats_usage_daily）：canonical_id=0
  每天 **127~189 个不同 raw 名**（10-28：189 名 / 13,877 请求）⇒ 旧 SQL
  把它们并成 **1 行**，名字 MAX 任选；
- 恰违背该 SQL 注释自己写的理由（「图上 5 个模型、栏里 8 行对不上账」）——
  方向反了：**图上 N 个、栏里 1 行**。且 10-29 当天榜首全是 passthrough
  （MiniMax-M3 / glm-5.3-flash / glm-5.3 …），旧口径把整栏信息毁掉；
- 归属：默认口径来自上一轮（bebca697c），本轮 by=provider 照抄同型——
  「注释声明与事实不符」族（§507 通式七）在**分组语义**上的形态。

**修法**（SQL 与 Go 折叠键必须同步，只修一边=白修）：

- 两条 SQL 分组键加 `CASE WHEN canonical_id = 0 THEN COALESCE(raw_model_name,'')
  ELSE '' END`（canonical>0 别名仍合并；=0 每 raw 名一行；NULL/'' 同组）；
- by=provider 的 models/kept 带 `raw_key`，JOIN 双条件（只按 canonical_id
  JOIN 会把 canonical=0 多名**交叉放大**）；raw_key 必须 COALESCE 钳非 NULL
  ——`NULL = NULL` 不成立 ⇒ 空/NULL 名组会被 JOIN **静默丢行**（本轮自己
  踩到，写进注释）；
- Go 折叠键从 `map[int]int` 改 `(canonical, raw)` struct 镜像 SQL CASE。
