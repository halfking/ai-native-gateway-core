## 一、探针的盲区：按 class 名找弹层

### 现象

`SessionSummaryDrawer` 明明被点开了，探针报「点击后未出现弹层」——
和「点击没反应」在报告上长得一模一样，于是第一反应是「撞上产品缺陷了」。

### 真因

旧探针的选择器是：

```js
document.querySelectorAll('[class*="drawer"],[class*="modal"],[class*="dialog"]')
```

而 `SessionSummaryDrawer` 的根是：

```
components/SessionSummaryDrawer.vue:191  <div class="ssd-backdrop" ...>
components/SessionSummaryDrawer.vue:192    <aside class="ssd-panel card" ...>
```

**两个 class 都不含 drawer / modal / dialog**。判据只覆盖了它认识的名字，
于是对它完全瞎。

这与本项目此前踩过的两次同族：

- 页面探针扫 `main *`，而主区其实是 `<section class="main-body">` ⇒ 105 页恒报 0 违规
- 模型选择器只展开默认视图的 15 个折叠区 ⇒ 把「我没遍历到」写成「集合里没有」

**共同点：判据的元素集合没有先证明覆盖全集，「没找到」就被当成了「不存在」。**

### 修法

改成**按几何 + 定位找，再做点击前后差分**：

1. 候选 = `position: fixed|absolute` 且可见且尺寸够大的元素
2. **再把「铺满视口的定位层」内部尺寸够大的后代也收进来** —— 居中弹窗的面板
   常常是 `position: static` 的 flex 盒子（`.mp-dialog` / `.user-info-dialog` 都是），
   只收定位元素会把候选缩回到遮罩，量出 1440px 的「面板宽度」并恒判绿
3. 点击前拍一张、点击后拍一张，**只有新出现的才算这次触发打开的**
   —— 顺手挡掉页面上常驻的 fixed 元素（全局导航抽屉）被每条 case 重复量一遍
4. 在**排除遮罩之后**的候选池里取最外层（沿 parentKey 上溯）

第 2 步和第 4 步都是这轮改出来又立刻被自检抓回来的：

- 改完第 1 步就上真页面，`.mp-dialog` / `.user-info-overlay` / `.ssd-backdrop`
  全部量成 **1440px**（量到遮罩了）——「按几何」并不自动等于「量到本体」
- 补完第 2 步，自检立刻报 `found: drawer-body` 而不是 `drawer`：
  「最外层」的深度是按**全集**算的，遮罩把每个后代都压成 depth≥1，于是选不出最外层

每一步都有对应夹具锁住（见下）。

### 判别力验证（变异测试）

| 变异 | 自检结果 |
|---|---|
| 候选筛选改回「按 class 名」（即本轮修掉的盲点） | **11/14 红** — `ssd-*` 夹具 found 实测 null |
| 去掉点击前后差分 | **13/14 红** — 常驻 `app-nav-drawer` 被误认成新弹层 |
| 收候选时不收遮罩内静态后代 | 真实 sweep 量出 1440px 遮罩 |

## 二、步骤驱动器：manual 里有「能力缺口」不是「不可测」

`NodeDetailDrawer` 原被标 manual，理由写的是
「本 harness 只能点可见元素、不能操作下拉选择」。

**复核后这个理由不成立**：候选表要的不是原生下拉，而是
「开 ModelPicker → 点热门模型 → 点解析 → 点明细」四步，
驱动器只是**没有「点弹窗里的条目」这个动作**。

这类 manual 是驱动器的能力缺口，混进报告里会让「没写」看起来像「测不了」。
所以给驱动器补了类型化步骤：

| 步骤 | 动作 |
|---|---|
| `'sel'` / `{click}` | 等可见 + 点击 |
| `{fill: [sel, v]}` | 填输入框 |
| `{select: [sel, v]}` | 选原生 `<select>` |
| `{wait: sel}` | 只等可见（等异步渲染的表格） |
| `{waitMs: n}` | 纯等待 |

**未知动作类型必须抛错，不能静默跳过** —— 静默跳过会让「清单里写了 4 步」
与「实际只做了 1 步」在报告上长得一样。

驱动器自检 4 个夹具 6 条判据，含两条反向对照（选择器写错必须抛、
动作类型不认识必须抛）。变异验证：

- 把「抛错」改成 `continue` ⇒ **5/6 红**
- 把点击包进 `try{}catch{}` ⇒ **5/6 红**

## 四、400 的分类：业务拒绝 ≠ 前端缺陷

`SessionSummaryDrawer` 流程里有一条 400：

```
POST /api/logs/session-summary → 400
{"error":{"detail":"日志条数不足，至少需要 2 条同会话记录"}}
```

这是**正确的产品行为**（本地这个会话只有 1 条日志），但旧规则「任何 console
error 都算 P1」会让这条 case 永远红。

改成分三类，**不是一律 P1，也不是删掉**：

| 类 | 判据 | 处理 |
|---|---|---|
| ① 未捕获异常 | `pageerror` | P1 |
| ② 非业务 HTTP 错误 | 5xx，或 4xx 但无 `error.detail` | P1 |
| ③ 业务级 4xx | 4xx 且带 `error.detail` | 见下 |

第 ③ 类的关键判断：**服务端明确拒绝了请求并给了原因，这时缺陷不是「发了 400」
而是「前端把它吞了」**。所以 case 可以声明 `expectErrorSurfaced`，
把 400 从噪声变成一条**正向检查**：

```js
expectErrorSurfaced: '.ssd-error'   // 声明后：静默吞掉才判红
```

实测 `.ssd-error` 可见 ⇒ 该 400 记为 note
「业务 4xx 1 条已按预期呈现：日志条数不足，至少需要 2 条同会话记录」。

同时去掉了一处重复计数：Chromium 会为每个失败请求打一条
`Failed to load resource: …`，它和 response 监听里那条是同一个 400。
不去重的话同一个错误会既进 notes 又进 P1。

**本门的限制**：只验「错误被显示」，不验「文案对不对」。
