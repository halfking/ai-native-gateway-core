## 2. ★ 量具修正：本轮先修了两个**读数工具**的缺陷

### 2.1 页巡检对比脚本：把 `apiSum` 当成了慢页判据

R72g 收尾时用的对比脚本输出「页数：2800=1 2805=1」⇒ **TSV 解析只读到 1 行**，
结论无效。本轮重写为 Python 版（`/tmp/kx-page-compare.py`），并**逐列核对语义**
（读 `scripts/audit/page-sweep-cdp.mjs` 头部注释，不靠猜列名）：

| 列 | 真实语义 | 曾被误读为 |
|---|---|---|
| `idleMs` | navigate → 网络静默 300ms 的墙钟（**慢页判据列**） | — |
| `slowApiMs` | 页内**单个** API 的最慢耗时（**单 API 慢判据列**） | — |
| `apiSumMs` | 页内**所有** API 耗时**之和** | 「慢页」判据 ❌ |
| `apiPeak` | `apiMaxConcurrencyHint`（**并发数**） | 「毫秒」❌ |
| `maintain503` | `/api/admin/maintain\|/api/free-discovery` 的 503 数（设计内降级，单列不计入 fail） | 页面缺陷 ❌ |

⇒ 修正后的判据：`idleMs > 2000` 才是慢页；`apiSumMs` 只作参考量。
**通用式：量具的「列语义」必须回到工具源码核对，不能靠列名猜。**

### 2.2 API 扫的 `200000` 状态码：客户端超时，不是服务端慢

3 个 SSE 端点（`probe/stream` / `live-stream` / `system-monitor/stream`）在扫里
状态码是 `200000`。读脚本才知：

```bash
c=$(curl -sS -m 30 ... -w '%{http_code}' ... || echo "000")
```

SSE 端点先收到 200 响应头、再撞 30s 客户端超时 ⇒ curl 非零退出 ⇒ `|| echo "000"`
把 `"000"` **追加**到已写出的 `"200"` 后面 ⇒ `"200000"`。
⇒ 这是**客户端超时标记**，不是「HTTP 200000」，更不是服务端慢。
★ 三个基线（2800 / 2802）里同样各 3 个 ⇒ 数量未变。

### 2.3 `-run` 过滤静默跳过断言（R65 同款，本轮又遇到一次）

新门写完后用 `-run 'Attachments'` 跑，**只跑到 3 条**——第 4 条
（`TestNoSessionFamilyReaderFiltersOnJoinRightSide`）名字里没有 "Attachments"
⇒ 被静默跳过。⇒ 补跑该条 + **全包跑**才算数。

## 5. ★ 本轮引入的回归：`/api/admin/attachments` 500

### 5.1 根因链（三段都可复现）

1. **2026-10-20（迁移 890 轮）把附件元数据列的落点从 v1 宽表换成
   `session_turn_details.attachments`**（`admin/data_lifecycle_attachments.go`
   文件头自证）。读端谓词也跟着换了列。

2. **两个列的空值形态不一样**：
   - v1 宽表：无附件 ⇒ **SQL NULL**；
   - 会话族特征层：`attachments` 是 jsonb，**2026-09-06～09-20 那段历史分区里
     空附件被写成 JSON `null` 标量**，2026-09-21 起才改成 SQL NULL。

   ⇒ 生产实测（252 共享库）：

   | 谓词 | 命中行数 | 说明 |
   |---|---|---|
   | `d.attachments IS NOT NULL` | **454,963** | 其中 **446,891** 行是 JSON null（根本没有附件） |
   | `d.attachments` 是非空数组 | **8,072** | 真正有附件 |
   | `t.attachment_count > 0` | **8,090** | 会话族的规范信号 |

3. **谓词落在 LEFT JOIN 的右表（details 侧）** ⇒ 规划器无法用会话族的任何
   索引去满足 `ORDER BY ts DESC LIMIT 50` ⇒ 全扫两表 + hash join + top-N sort。

### 5.2 生产实测（252 共享库，EXPLAIN ANALYZE）

| 形状 | Execution Time | 计划要点 |
|---|---|---|
| 旧：`rl.attachments IS NOT NULL` | **17,582 ms** | Parallel Seq Scan（session_turns 1,067,701 行 + session_turn_details 1,055,459 行）→ Parallel Hash Join → top-N sort；**17k temp 溢写**；255k buffers |
| 新：`rl.attachment_count > 0` | **1,317 ms**（13.4×） | 谓词**下推进两臂** → `session_turns_2026_09_heap_attachment_count_idx` / `session_turns_2026_10_attachment_count_idx`（索引谓词逐字相同）→ 无 temp 溢写 |

⇒ 17.6s > 10s ctx deadline ⇒ **500**（154 日志：`WARN attachments: list query
failed "timeout: context deadline exceeded"` + `duration_ms:10001`）。

### 5.3 修法（**无 DDL**）

新增常量 `attachmentsPresencePredicate = "rl.attachment_count > 0"`，三处会话族
读端统一用它：

| 端点 | 改前 | 改后 |
|---|---|---|
| `GET /api/admin/attachments` | `WHERE rl.attachments IS NOT NULL` | `WHERE rl.attachment_count > 0` |
| `GET /api/admin/attachments/stats` | `WHERE attachments IS NOT NULL AND jsonb_typeof(attachments)='array'` | `WHERE rl.attachment_count > 0 AND jsonb_typeof(rl.attachments)='array'` |
| `POST /api/admin/attachments/cleanup/preview` | `WHERE rl.attachments IS NOT NULL AND jsonb_typeof(...)='array'` | `WHERE rl.attachment_count > 0 AND jsonb_typeof(...)='array'` |

★ **为什么不丢行**：`{attachment_count > 0}` ⊇ `{details 有非空数组}`
（8,090 ⊃ 8,072；差的 18 行是 count>0 但 details 无数组）⇒ 换谓词只会**多**出
18 行，不会少掉任何真正带附件的请求；`jsonb_typeof='array'` 本身已蕴含
NOT NULL ⇒ stats / preview 的结果集不变。

★ **为什么不用 `rl.has_attachments IS TRUE`**：那一列是
`CASE WHEN attachment_count IS NULL THEN NULL WHEN >0 THEN true ELSE false END`，
规划器**推不出**它蕴含索引谓词 `attachment_count > 0`（NULL 分支）⇒ 部分索引
用不上 ⇒ 退回全扫。

★ **清理写路径（`session_turn_details_hot` 直清）保持原样**：它的语义是
「把 hot 上任何非空 attachments 置 NULL」，与读端「挑出有附件的请求」不是
一回事，且 hot 表只有几千行 ⇒ 不受全扫影响。

### 5.4 门与变异

新门 `scripts/ursmcheck/session_family_attachments_predicate_test.go`（4 条）：
① 谓词常量**逐字** = `rl.attachment_count > 0`（AST 取 `BasicLit` 真实值，
**不看注释**）；② 该常量被**≥3 处**引用（三个会话族读端都得到它）；③ 会话族
SQL 字面量里不得再出现 `rl.attachments IS NOT NULL`；④ 谓词不得含
`has_attachments` / `jsonb_typeof` / `COALESCE` / `IS TRUE` 这类会让规划器
**推不出**索引谓词的包装。

★ 变异 M1~M3（真应用 + 全包跑 + md5 按**原路径**还原）：
M1 常量退回 `rl.attachments IS NOT NULL` ⇒ 红；
M2 列表端点手写回退 ⇒ 红；
M3 统计端点改用手写字面量（少一处常量引用）⇒ 红。

### 7.3 ★★★ 本轮最有价值的一条：**「一批端点同时 500」的第一嫌疑是【连接池被一个慢查询占满】，不是「它们各自的 SQL 都有问题」**

修前同一批里 3 个端点同时 500（attachments / session-health / data-lifecycle/metrics）；
**只修了 attachments 一个**，另外两个**自动从 500 变成 200**（虽然它们自己仍 >2s）。

机制（同库实测）：
- 修前 attachments 的查询**独占一条连接 10+ 秒**（17,582ms，见 §5.2）；
- 同一个库上还有更长的查询（`pg_stat_statements` 实测）：
  `WITH mp AS MATERIALIZED (...)` **3 次 / mean 19,050ms / max 48,946ms**、
  `compression/sessions` 的 `COUNT(DISTINCT ...)` **389 次 / mean 1,972ms / max 29,655ms**、
  `count(*) FILTER (WHERE p_req.id IS NOT NULL ...)` **127 次 / mean 2,872ms / max 28,284ms**；
- ⇒ 慢查询把连接池占满 ⇒ 后来者**拿不到连接** ⇒ 每个请求撞自己的
  ctx deadline（10s / 15s / 30s 各不相同）⇒ **表现为「一堆端点超时」，
  而它们的 SQL 其实一个都没变**；
- ⇒ 修掉那个 10s 占用 ⇒ 连接释放 ⇒ 另外两个端点当场恢复。

⇒ ⇒ **通用式**：
1. ⭐⭐⭐⭐⭐ **「同时多个端点超时」的第一嫌疑 = 池/IO 争用，而不是 N 个独立缺陷**
   ⇒ ⇒ **归因要问「谁在占着连接」，不能只问「谁超时了」**。
2. ⭐⭐⭐⭐ **判据：修掉一个慢查询后，另一批端点有没有自动恢复** ——
   恢复了 ⇒ 它们是**连带受害者**（不是各自的缺陷）；没恢复 ⇒ 才是各自的缺陷。
3. ⭐⭐⭐⭐ **「同一端点前后两次读数」必须用同一脚本、同一口径**（本轮两次都用
   `kx-api-sweep2.sh` + 同一路由表）⇒ 否则会把「环境变化」读成「修复生效」。
4. ⭐⭐⭐ **每个请求的 ctx deadline 不同（10s/15s/30s）⇒ 池饱和时，
   「超时」会按 deadline 长短分层** ⇒ 看到三种不同超时值时，
   要想到「同一个瓶颈 + 不同 deadline」。

### 7.4 ★ 订正一：**154 连的库与 252 是【同一个 PG 实例】**

⇒ ⇒ ★★★★ **「零和」事实（本轮第二个重要发现）**：

attachments 不再独占连接 10 秒 ⇒ 那些本来就慢的端点**拿到了更多连接与 IO**

2. **「回归」与「既有缺陷」要分开**：`session-analytics` 的 500 是

3. ★ **本轮没有把生产变成「全绿」**：修好了 4 个（+3 个连带恢复），
