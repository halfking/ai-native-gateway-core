# LLM Gateway Go-3 优化总控提示词

> 这是后续每个优化任务的统一入口。将本提示词与某个具体任务提示词一起交给执行代理。

```markdown
你正在维护一个生产级 Go LLM Gateway。请严格遵循以下工作协议。

## 一、执行前检查

1. 阅读仓库根目录的 README、go.mod、Makefile、相关设计文档和最近提交记录。
2. 只依据当前代码中真实存在的类型、函数、路由、表和配置进行实现；任务文档中的代码仅为意图示例，不得直接复制不存在的API。
3. 先搜索现有实现，优先复用现有抽象、错误分类、指标、日志、测试工具和迁移模式。
4. 列出预计修改的文件、依赖关系、风险和测试计划。
5. 如果发现目标已经实现、名称不同或架构不适配，停止扩大范围，给出差异报告并采用最小兼容方案。

## 二、实现约束

1. 不改变既有协议语义、租户隔离、认证边界、错误分类、超时、取消传播和故障降级行为。
2. 不引入未评估的全局缓存、无限增长 map、后台 goroutine 或第三方依赖。
3. 不在日志、测试输出、trace 属性、错误响应或 artifact 中暴露 API key、Bearer token、密文、完整请求体或用户内容。
4. 数据库变更必须包括：前向迁移、回滚方案、依赖检查、幂等性说明和验证SQL。
5. 生产配置、数据删除、外部通知、批量迁移和破坏性操作默认先提供 dry-run，不直接执行。
6. 所有新增后台任务必须支持 context 取消、退出等待、超时和错误降级。
7. 指标标签必须控制基数，禁止使用 request_id、原始用户输入或完整错误正文作为高频 label。

## 三、测试协议

按改动范围执行：

1. 格式化和静态检查：`gofmt`、相关 `go vet`、项目既有 lint 命令。
2. 受影响包的单元测试。
3. 相关集成测试；外部依赖不可用时使用项目已有 mock/testcontainer，不伪造通过结果。
4. 并发相关改动运行 `go test -race`。
5. 解析器/协议改动运行 fuzz smoke、回归样本和 round-trip 测试。
6. 数据库改动运行迁移结构测试、SQL静态检查和可回滚验证。
7. 前端改动运行项目已有的类型检查、单元测试和构建检查。

每条命令都要记录退出码。失败时报告真实输出、根因判断和是否为环境限制。

## 四、交付格式

完成后输出：

### 1. 结果摘要
- 已完成内容
- 未完成内容
- 是否建议合并/部署

### 2. 文件变更
- 文件路径和关键行范围
- 每个变更解决的问题

### 3. 验证结果
- 执行过的命令
- 成功/失败
- 失败的具体原因

### 4. 风险与回滚
- 兼容性风险
- 数据风险
- 性能风险
- 回滚步骤

### 5. 后续建议
只列出确实需要后续处理的事项，不要扩展无关范围。
```

# 第一轮执行任务：建立真实基线，不立即大规模改造

```markdown
# 任务：为 LLM Gateway 优化建立可复现基线

## 目标
在修改功能代码之前，确认当前仓库真实存在的测试、性能、并发、可观测性和数据生命周期基线。此任务原则上只新增报告、测试脚本或最小测试修复，不进行大规模架构重构。

## 检查范围
1. `internal/ir`：解析、序列化、流式和工具调用测试覆盖。
2. `domains/dispatch`：队列、Governor、DimensionIndex、QueuedRequest和取消路径。
3. `domains/streaming`：流式中断、客户端断连、上游错误和资源清理。
4. `domains/authentication`：keystore同步、快照、撤销传播和并发访问。
5. `bg`：partition manager、promote、cleanup、错误聚合和后台任务退出。
6. CI与开发工具：`.github/workflows`, `.golangci.yml`, `Makefile`及项目脚本。
7. 数据层：hot表、父表、迁移、MV、promote函数和回滚脚本。

## 执行步骤

### 1. 代码和测试盘点
输出：
- 每个领域的关键包
- 已有测试命令
- 缺少的测试类型
- 可能的高风险路径

### 2. 运行最小验证集
先运行与仓库实际配置匹配的命令，例如：
- 受影响包的 `go test`
- 项目已有的 `make test` 或等价命令
- `go vet`（如果项目当前支持）
- 对并发重点包运行 `go test -race`

不得因为某个全仓库命令耗时过长就声称全部通过；应记录实际范围。

### 3. 性能基线
仅对已有或容易隔离的函数添加 benchmark。优先覆盖：
- OpenAI/Anthropic/Gemini request parse
- response serialization
- queue enqueue/dequeue
- candidate selection
- streaming chunk transformation

要求使用 `b.ReportAllocs()`，记录基准环境和结果。不得先引入 sync.Pool、缓存或替换JSON库。

### 4. 并发基线
对现有并发测试运行 race detector。若失败：
- 保存最小复现命令
- 定位共享状态和访问路径
- 区分真实竞态、测试不稳定和第三方依赖问题
- 不要通过扩大锁范围或禁用测试来掩盖问题

### 5. 数据生命周期基线
只读检查：
- hot表保留时间
- promote调度周期
- promote失败重试和告警
- 分区是否提前创建
- MV刷新和drift检查
- 迁移是否幂等、是否存在依赖冲突

不直接连接或修改生产数据库。

### 6. 输出报告
创建：
`docs/perf/<date>-optimization-baseline.md`

报告必须包含：
- 代码版本和环境
- 执行命令与退出码
- benchmark结果
- race/vet/lint结果
- 数据生命周期检查结果
- P0/P1/P2问题分级
- 建议的下一步最小变更

## 验收标准
- [ ] 基线报告可由其他工程师按命令复现
- [ ] 所有失败都真实记录，没有“环境失败=通过”的表述
- [ ] 未引入无必要的依赖和架构变更
- [ ] 至少产出一个可执行的下一步修复任务
- [ ] 报告明确区分代码缺陷、测试缺陷和环境限制
```

# 第二轮执行任务：CI门禁的最小实现

```markdown
# 任务：在现有CI基础上增加最小安全门禁

## 目标
在不破坏现有流水线的前提下，为受影响的Go包增加格式化、vet、race和基础测试门禁。

## 执行前
1. 阅读所有现有 workflow，识别实际使用的CI平台和Go版本。
2. 找出当前已经运行的测试命令，避免重复创建冲突的workflow。
3. 检查 `.golangci.yml` 是否已有规则；不要盲目启用全量linter导致不可控遗留噪音。

## 实施原则
1. 优先修改现有workflow，而不是新增多个重复workflow。
2. PR门禁运行确定性、耗时可控的测试集合。
3. nightly任务可运行更长的race/fuzz，但不得使用 `|| true` 掩盖失败；如果需要非阻塞，应明确上传结果并创建告警。
4. 所有超时必须高于race模式的实际基线，并设置合理上限。
5. 只对真实存在的包使用路径，不复制规划文档中的假路径。

## 验收标准
- [ ] PR流水线有确定性的基础测试门禁
- [ ] 核心并发包有race检测
- [ ] vet或现有lint工具实际运行
- [ ] 失败日志可定位到包和测试
- [ ] 未改变生产部署流程
- [ ] CI耗时和失败率有记录
```

# 代理分工建议

| 阶段 | 代理角色 | 主要产出 |
|---|---|---|
| 第一轮 | 基线审计代理 | 可复现基线报告 |
| 第二轮 | CI工程代理 | 最小测试/lint/race门禁 |
| 第三轮 | IR测试代理 | fuzz、round-trip、协议回归 |
| 第四轮 | 可观测性代理 | 指标、trace和runbook改进 |
| 第五轮 | 性能代理 | profile、benchmark和小步优化 |
| 第六轮 | 数据/容量代理 | retention、promote、分区和恢复演练 |
| 第七轮 | URSM迁移代理 | shadow/canary/authoritative分阶段方案 |

## 每轮之间的发布门

下一轮开始前必须确认：
- 当前轮测试已通过或失败已登记
- 没有新增未解释的高严重级别问题
- 变更范围与工作包一致
- 有可执行的回滚步骤
- 相关文档和指标已更新
