## 任务6：性能基线、Profiling与热路径优化

```markdown
# 任务：建立并优化 LLM Gateway 热路径性能基线

## 目标
在不改变协议语义、租户隔离、错误分类和故障转移行为的前提下，测量并优化：
1. 请求解析与IR构建
2. 路由和候选筛选
3. 多层调度队列入队/出队
4. 上游协议序列化
5. 流式响应转换
6. 日志与指标写入

## 必须先做
1. 阅读 go.mod、现有 benchmark、metrics 定义和性能文档。
2. 使用 `git log --since=<目标范围>` 确认近期变更。
3. 记录基线：Go版本、CPU/内存、请求大小、并发度、供应商模拟方式。
4. 不得直接引入新的缓存、sync.Pool或第三方JSON库，除非有基准数据证明收益。

## 实施步骤
### 1. 建立可重复基准
为现有核心函数添加 benchmark，覆盖：
- 简单文本请求
- 多轮消息
- 工具调用
- 多模态请求
- 大型流式响应
- 错误/重试路径

每个 benchmark 必须使用 `b.ReportAllocs()`，记录 ns/op、B/op、allocs/op。

### 2. Profiling
在隔离测试环境生成：
- CPU profile
- heap profile
- allocs profile
- mutex profile
- block profile
a
禁止使用真实凭据或真实用户内容。所有样本必须脱敏或合成。

### 3. 优化规则
- 只优化已被 profile 证明的热点。
- 保持上下文取消、超时和资源释放语义。
- 对共享对象池进行清零，避免跨请求数据泄漏。
- 大请求必须保留大小上限和背压。
- 优化前后运行功能测试、`go test -race`和基准回归。

### 4. 输出
生成 `docs/perf/<date>-hot-path-baseline.md`，包含：
- 测试环境
- 基准命令
- 原始数据
- 优化差异
- 回归风险
- 未采纳方案及原因

## 验收标准
- [ ] 每个优化点都有前后基准数据
- [ ] p95/p99或benchmark结果没有功能回归
- [ ] race、单元测试和关键集成测试通过
- [ ] 内存分配或延迟有可重复的改善
- [ ] 没有引入未审查的全局缓存或无限增长结构
```

## 任务7：分布式追踪与可观测性增强

```markdown
# 任务：完善端到端可观测性

## 目标
为一次请求建立从入口到上游、存储和响应的可关联观测链路，同时控制高基数标签和性能开销。

## 必须先做
1. 阅读当前 OpenTelemetry、Prometheus、结构化日志和 waterfall 实现。
2. 列出已有指标和 span，禁止重复创建同名指标。
3. 检查 trace_id、request_id、tenant_id 的脱敏和生命周期。
4. 确认哪些组件运行在请求上下文之外，避免错误复用已取消的 context。

## 推荐 span 结构
```text
request
├── authenticate
├── parse
├── dispatch
│   ├── queue.total
│   ├── queue.model
│   ├── queue.credential
│   ├── governor.acquire
│   └── forward
│       └── upstream.request
├── response.transform
└── persistence
```

## 实施要求
### 1. 统一属性
允许的低基数属性：
- protocol
- provider
- model_family
- error_kind
- queue_layer
- outcome

禁止将以下内容直接作为 metric label：
- 原始请求ID
- 用户输入
- API key
- 完整模型名（除非经过基数评估）
- 任意上游错误正文

### 2. 采样与成本控制
- 配置生产采样率和错误强制采样。
- 大 payload 只记录大小、摘要或哈希，不记录原文。
- span 属性和日志字段设置长度上限。
- 所有 exporter 必须有超时和失败降级，不能阻塞请求主路径。

### 3. 监控面板
增加以下视图：
- 请求端到端延迟分解
- 各调度层等待时间
- 上游成功率、重试率和错误类型
- Redis/DB降级状态
- hot表 promote 延迟
- digest fallback、credential decrypt smoke gate 状态

### 4. 告警
告警必须有：阈值、持续时间、严重级别、抑制策略和运行手册链接。避免只按单个请求触发告警。

## 验收标准
- [ ] 成功、失败、取消、重试路径均可关联
- [ ] 指标无明显高基数爆炸
- [ ] exporter故障不影响请求处理
- [ ] 追踪开销通过基准验证
- [ ] 面板和告警均有对应runbook
```

## 任务8：持续Fuzzing与协议兼容性矩阵

```markdown
# 任务：建立IR层持续Fuzzing和协议兼容性测试

## 目标
验证 OpenAI、Anthropic、Gemini、Responses 等协议解析、序列化和流式转换在畸形输入、未知字段、工具调用和多模态数据下不会崩溃或静默丢失关键语义。

## 必须先做
1. 阅读现有 parser/serializer 和已有 fuzz/property tests。
2. 使用实际类型定义，不得复制不存在的函数名或字段。
3. 明确哪些字段是严格保留、语义保留、允许丢失或必须报错。
4. 不得把“解析失败”误判为测试失败；需区分拒绝非法输入和panic/数据损坏。

## 测试矩阵
至少覆盖：
- 每个协议的 request parser
- 每个协议的 response parser
- 每个协议的 serializer
- 流式 SSE chunk 拼接和中断
- 工具调用跨块拼接
- 未知扩展字段
- 超大字段、空值、错误类型、重复字段

## 关键不变量
1. 任意输入不得 panic。
2. 序列化结果必须是合法目标协议，或返回明确且可分类的错误。
3. 关键字段（角色、文本顺序、工具调用ID、模型映射）不得静默丢失。
4. 不支持的字段必须通过现有 protocol-loss 机制报告。
5. 附件和敏感字段不得出现在测试日志中。

## CI策略
- PR：每个目标运行短时 fuzz smoke test和固定回归样本。
- Nightly：延长 fuzz 时长并保留失败样本。
- 发现crash后自动把最小化样本加入回归测试。
- Fuzz失败样本不得上传到公开artifact，除非确认已脱敏。

## 验收标准
- [ ] 所有现有协议目标都有fuzz入口
- [ ] 兼容性矩阵记录每条路径的支持等级
- [ ] 至少包含流式中断和工具调用跨块回归测试
- [ ] fuzz crash可稳定复现
- [ ] CI不会因随机低概率结果产生不可诊断失败
```

## 任务9：URSM v2渐进迁移

```markdown
# 任务：制定并执行 URSM v2 渐进迁移方案

## 目标
在可回滚、可观测和租户隔离的前提下，将路由流量从旧实现迁移至 URSM v2，禁止一次性删除旧路径。

## 阶段0：盘点
1. 阅读 URSM v2 manager、router integration、recovery gate 和配置解析。
2. 列出所有模式：off、shadow、canary、authoritative及其实际语义。
3. 确认 Redis/DB不可用、空manifest、冷启动和节点镜像场景。
4. 明确 readyz 与实际请求可用性的差异。

## 阶段1：Shadow
- 旧路由继续服务。
- v2只计算决策并记录差异。
- 按租户、模型族、供应商比较：候选集合、排序、拒绝原因和延迟。
- 差异必须可解释，不能只记录布尔值。

## 阶段2：Canary
- 只对明确配置的租户/模型族启用。
- 设置最大流量比例、自动回滚阈值和人工暂停开关。
- 监控错误率、延迟、空候选率、成本和故障转移次数。
- Redis故障时验证 outage mirror 不绕过 recovery gate。

## 阶段3：Authoritative
- 分批扩大范围，每次变更保留观察窗口。
- 旧路径保留为回退实现，但不再双写不必要状态。
- 对每个阶段记录配置、时间、负责人和结果。

## 回滚条件
任一条件持续超过规定窗口即回退：
- 错误率显著高于基线
- 空候选或错误路由增加
- p95/p99延迟回归
- 租户间数据/决策串扰
- recovery gate语义被绕过

## 验收标准
- [ ] 每个阶段都有独立开关
- [ ] 可按租户/模型族回滚
- [ ] Redis/DB故障场景有自动化测试
- [ ] 差异指标和回滚条件已配置
- [ ] 完成迁移前不删除旧实现
```

## 任务10：容量规划、数据保留与安全合规

```markdown
# 任务：建立容量规划、数据保留和安全审计体系

## 目标
根据真实写入量、查询量和故障场景制定容量模型，同时确保请求体、凭据元数据、错误日志和快照符合最小保留原则。

## 必须先做
1. 盘点所有 hot 表、分区表、物化视图、快照和对象存储。
2. 读取实际 retention 配置和 promote/cleanup 调度实现。
3. 统计过去至少7天：写入速率、表大小、索引大小、promote延迟、失败重试、磁盘增长。
4. 不得直接改变生产保留时间；先生成容量和风险报告。

## 容量模型
至少计算：
- 每日请求日志行数和字节数
- 请求/响应body的TOAST增长
- candidate failure logs增长
- 10分钟聚合表增长
- 每月分区和索引增长
- Redis key数量和内存峰值
- 备份、恢复和故障重放空间

给出 30/90/365 天预测，并包含增长率上下界。

## 保留策略审计
对每类数据记录：
- 数据用途
- 默认保留时间
- 配置入口
- 清理任务
- 失败时的重试与告警
- 是否含敏感信息
- 删除/归档是否可验证

重点检查：
- API key snapshot 不含密钥材料且权限正确
- 日志和错误响应不暴露token、完整请求体或上游密文
- 删除和归档操作具备租户边界
- 备份中敏感数据有加密和访问审计

## 容量告警
建立基于趋势而非单点阈值的告警：
- 磁盘预计耗尽时间
- hot表 promote 积压
- 分区创建失败
- MV刷新持续失败
- Redis内存水位
- 连接池耗尽

## 恢复演练
设计并记录：
1. PostgreSQL只读/不可用
2. Redis重启且无持久化
3. promote任务中断
4. 分区缺失
5. 快照过期
6. 错误聚合水印异常

每个场景必须有：检测信号、自动动作、人工动作、回滚和验证SQL。

## 验收标准
- [ ] 输出容量报告和增长预测
- [ ] 所有数据类型有明确保留和清理责任
- [ ] 敏感数据扫描无高风险泄露
- [ ] 告警包含可执行runbook
- [ ] 至少完成一次恢复演练并记录结果
```

---

## 推荐执行顺序

1. **任务6：性能基线** —— 先测量，避免盲目优化。
2. **任务7：可观测性** —— 为后续迁移和容量规划提供证据。
3. **任务8：Fuzz与兼容性** —— 降低协议改动风险。
4. **任务10：容量与保留审计** —— 防止优化放大存储和合规风险。
5. **任务9：URSM v2迁移** —— 只有在前述指标和回滚能力完备后执行。

## 通用执行约束

- 先读代码和测试，再设计；不得凭文件名猜实现。
- 任何数据库迁移先验证当前schema、依赖和回滚路径。
- 任何外部通知、生产配置变更、数据删除或大规模迁移必须先生成 dry-run 结果。
- 所有优化必须保留可观测性、租户隔离、取消传播和故障降级语义。
- 完成后必须运行与改动相关的最小测试集，再运行完整回归；失败必须如实报告。
