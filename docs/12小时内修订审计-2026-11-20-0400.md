### D2（P2）`FlexibleString` 无钉测 + 两条不可达死分支

- **取证 A（无钉测）**：`grep -rn FlexibleString --include=*.go` 除定义处外**零命中** ⇒ 该类型**没有任何测试**。提交信息自称「✅ 修复验证：成功解析 code:400 的错误响应」，但**那段验证没有留在仓里** ⇒ 任何人把 `FlexibleString` 改回 `string`，CI **不会红**。
- **取证 B（死分支）**：`json.Number` 对**任何** JSON 数字都解析成功（整型 + 浮点型都是它的合法形态）。实测：

  ```

  400.5 -> json.Number err=<nil> val="400.5"
  ```

  ⇒ 原实现的第三条（`int64`）与第四条（`float64`）分支**永远不可达**（`json.Number` 已先一步吃掉全部数字形态）⇒ 两条死面 + 多余的 `strconv` 依赖。

  1. 删两条死分支 + `strconv` import；
  2. 补 `internal/ir/stream_flexible_string_test.go`（4 个测试）：

### D3（P1）`settings.timezone` 测试钩子**数据竞争**（`-race` 实测复现）

- **取证**：注入钩子的**写**面（`SystemTimezoneLocationForTest`）在 `tzMu.Lock()` 下进行，而**读**面（`SystemTimezoneName` / `SystemTimezoneLocation`）原先是**裸读** `tzTestHook`（不持任何锁）⇒ Go 内存模型下的数据竞争。
- **实测复现**：本轮写探针（并发读 + 反复注入/摘除）跑 `go test -race` ⇒

  ```
  WARNING: DATA RACE
  Read at …: settings.SystemTimezoneName()           settings/timezone.go:87
  Previous write at …: settings.SystemTimezoneLocationForTest()  settings/timezone.go:200
  ```

- **影响**：`tzTestHook` 恒为 nil（生产面），故**生产无竞争**；但**测试面竞争真实存在** ⇒ 任何「并发跑 settings 包」或将来把钩子用于热切换的场景都会踩到；且 `-race` 门一旦接入 CI 就会红。
- **处置**：新增 `testHookSnapshot()`，读面一律经 `tzMu.RLock()` 取出**后立即释放再调用**（钩子是纯函数、不回调本包 ⇒ 无死锁）⇒ 读写两侧现共处同一把锁。
- **钉测**：补 `settings/timezone_race_test.go`（并发读 + 200 轮注入/摘除）⇒ 配 `-race` 跑才有判别力，已在注释里写明。
- **判定**：修复前 `-race` 红 ⇒ 修复后 `go test -race ./settings/` PASS（2.15s）。

## 六、执行规划（给下一轮）

1. **每轮第一动作＝取门禁基线**（不是直接读 diff）：`go build ./...`（**`-mod=vendor`**）+ `go test ./internal/ir/ ./settings/ ./admin/ ./internal/sqlguard/` + web 四道 i18n 门 + `vue-tsc`。**任何「既存红」先与本档 §二 / 上一轮 §八 对账再动手**。
2. **跨仓同步的固定姿势**（本轮已验证）：逐仓 `stash push -u` → `merge origin/main` → `stash pop` → **逐条定性冲突**（判「哪边是超集」而不是「哪边后到」）→ 复核在途件完整性 → `go build`。
3. **迁移编号冲突的处置序**：先查「同编号是否已被**已落地**件占用」⇒ 若被占用，再查「本件是否实为已落地件的**副本**」（用 **SHA / patch-id / 目的 / 逐字差量**四路取证）⇒ 判为副本则**隔离不并入**（改号会造出第二份语义重复件）⇒ 判为新工作才改号 + 补齐六点位。
4. **i18n 棘轮**：**改写优先于抬基线**（本轮 3 项超限全部改写回落，未抬基线）；只有真正无法改写的合法同形才按既有格式人工抬基线并在 `baselineRaiseReason` 写明理由。
5. **依赖系统时区的判据一律钉时区**（`settings.SystemTimezoneLocationForTest`）+ 补一条**与偏移无关的不变量断言** ⇒ 防「薛定谔红」。
6. **量具台账随迁移同步**：新增 `sql/migrations/startup/98X__` 后必须重跑 `expect` + `reconcile --columns` + `reachability` 三命令（缺 `--columns` 会误报假 gap）。

## 七、通用式（本轮沉淀）

1. **「编号冲突」的第一嫌疑是「副本」，不是「要改号」** —— 本轮 `-3` 的 `972` 初判为「改号到 973」，复核后是「已落地 `977` 的陈旧副本」⇒ 若当初照初判改号，会造出**第二份语义重复的迁移**并把两件都接进投递链。⇒ **先取证再处置**。
2. **修测试 ≠ 改期望值** —— D5 的正解不是把 `from` 的期望值改成 `2026-09-30 16:00:00 UTC`，而是**钉住时区**并补**与偏移无关的不变量**；前者只是把「薛定谔红」换成「写死一个偏移的绿」。
3. **「本包此前全绿」是最强的归因证据** —— D5 靠「时区轮前整个 admin 包 `ok`」才敢定性为「本轮引入」，而不只是「现在是红的」。
4. **棘轮超限先问「能不能改写」** —— 抬基线 = 把新债固化进门槛；改写 = 不动门槛。**指标是指示器，不是缺陷数**（仓内 baseline 编年史里已明写），所以要先分「真未翻译」与「合法同形」两类再分别处置。
5. **共享工作区默认有别人的在途件** —— 本轮 5 仓里有 2 仓有并行会话在跑（一个 Maestro 测试进程正跑着）。**先 `stash push -u` 再 merge、pop 后逐条定性冲突**，比直接 merge 稳得多。
6. **构建通道选错 ⇒ 满屏假红** —— `-mod=mod` 撞 proxy 超时，症状与「代码坏了」完全一样；5 仓都带 `vendor/` ⇒ **一律 `-mod=vendor`**。
7. **★ 死分支与死面是同一类债** —— D2 的两条不可达分支、D4 的整份陈旧副本，代价都不是「跑不起来」而是「让下一个读代码的人以为它有用」；清死面应与清死分支同批做。
