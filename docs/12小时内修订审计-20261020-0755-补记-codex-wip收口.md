## 二、三处必须先补齐的缺口

### 2.1 探针持久化没有独立预算（门禁红的真正原因）

**旧形态**：

- `bg/credential_probe_v2.go` 的 `writeHealth`：`context.WithTimeout(ctx, 5*time.Second)`
  —— **继承父 ctx**。探针自己把 deadline 用尽后，这次健康记录就是写不进去的，
  而失败被 `slog.Warn` 吞掉 ⇒ **表恒不变，且看不出原因**。
- `bg/node_probe.go` 的 `emitSyncAudit`：`auditDB.Exec(ctx, ...)` —— 直接用父 ctx。
  父 ctx 一过期，这一轮探针的**审计证据**就没了。

**新形态**（本次落地）：

- 新增 `probePersistenceBudget(ctx)`：用 `context.WithoutCancel(ctx)` 摘掉调用方的
  deadline（它可能已经耗尽），再给**自己的** 5s 预算；
  `context.AfterFunc` 只在**显式取消**（`context.Cause` 非 `DeadlineExceeded`）时才掐断写入
  ⇒ 「预算耗尽」不丢弃记录，「调用方撤回结果」才丢弃。
- `writeHealth`：进入即判断 `ctx.Err() == context.Canceled` ⇒ **不写**（调用方已撤回结果）。
- `emitSyncAudit`：审计是**已完成**一轮的证据 ⇒ 即便调用方已取消也要落库，
  故用 `context.WithTimeout(context.WithoutCancel(ctx), …)`，**不**联动取消。

两个函数的取消语义**故意不同**：健康状态是「活状态」，调用方撤回就不该写；
审计是「已完成事实」，撤回也必须留痕。

### 2.2 新的 CAS 不引入调用方回归（逐个核过）

`ModelAvailabilityCache.Set` 现在要解析 `fields["updated_at"]`（解析失败即报错返回）。
全仓 `Set` 调用方只有 4 处，**全部**经 `modelAvailabilityFields(...)`，
而该函数**恒定**写入 `updated_at` ⇒ 无调用方会踩到解析失败。
读侧 `ModelAvailabilityReader.Read` 用 `SafeHGetAll` 只取已知字段，
新增的 `observed_at_us` 字段被自然忽略 ⇒ 读侧无回归。

### 2.3 pgxmock 填不了 `**time.Time` —— 错的是测试，不是生产代码

门禁报 `destination kind 'ptr' not supported for value kind 'struct'`。查 pgxmock v4.9.0
`rows.go` 的扫描分支：值必须是**可赋值给目标元素类型**的；目标是 `**time.Time`（可空时间戳），
于是值也得是 `*time.Time`；给 `time.Time` 或 `pgtype.Timestamptz` 都不行。

而**真实 pgx 是支持的**（`pgtype.TryPointerPointerScanPlan` 存在，v5.9.2）
⇒ 生产代码的 `**time.Time` 扫描形状是**既有模式**（该文件里 `last_attempt_at` 本来就这么扫），
错的是测试把行值写成了 `time.Time`。

⇒ 改测试：时间列以 `*time.Time` 交给 mock（真实 pgx 返回 `time.Time`，
赋值后的净效果一致）。**没有**为了迁就 mock 去改生产代码的扫描形状。

## 三、仓内既有 ratchet 指出的一处**真实**缺陷：LIMIT 0 的静默空转

`bg/batch_limit_guard_ratchet_test.go` 的 `TestSqlLimitBatchFieldsAreNormalisedSomewhere`
在本次落地时**红了**（`model_availability_backfill.go:181`，`LIMIT $3` 绑了裸 `w.batchSize`）。
该 ratchet 明确要求：批次上限必须走**归一入口**（方法调用），因为 `LIMIT 0` 只扫 0 行，
worker 会变成一个**什么都不做却照样打「cycle done」的静默空转**。

这次它是**真阳性**，不是误报：批次上限是 struct 字段，绕开构造器直接赋值即可为 0
（本次新增的门禁就是直接赋 `w.batchSize = 0` 构造 worker 的）。

⇒ 落地：新增 `effectiveBatchSize()`（非正 ⇒ 读作「未设置」⇒ 取默认 200），
SQL 实参改走该方法。仓内既有 `b.scanLimit()` 就是同款形态。
