## 二、P0 / P1 缺陷（须本轮处理）

### D0（P0）熔断器 per-model 改造的**键空间分裂**：写路径与读路径/探针路径不在同一命名空间

- **位置**：`domains/credential/breaker.go:990-1012`（`GetOrCreatePerModel`，key = `"<providerID>/<model>"`）、`:966-985`（`GetOrCreate`，key = `"<providerID>/<credentialID>"`）、`:1063-1066`（`Manager.ReleaseProbe` 走 **credential 键**）
- **缺陷机制（两重，均已实测复现）**：
  1. **跨凭据连坐**：per-model 键**丢弃了 credentialID**。同 provider 下 credential 7 的失败，会让 credential 9 在**同一模型**上被判熔断。
  2. **探针槽永不释放**：`Manager.ReleaseProbe(providerID, credentialID)` 按 credential 键查找，而 per-model 断路器只存在于 per-model 键下 ⇒ 查得 nil ⇒ **`ReleaseProbe` 是空操作**，半开探针槽（`halfOpenProbes`）不释放。

- **生产可达性**：**高**。写路径已切 per-model（`domains/streaming/executors/executor_dispatch.go:970`、`context_summarize.go:539/552/560`），而 `ReleaseProbe` 在同两个文件的 5 处仍按 credential 键调用（`executor_dispatch.go:843/853/915/1016`、`context_summarize.go:502/528/543/556/569`）。

- **硬证据（本轮复现实验，已删除临时文件）**：

  ```
  === RUN   TestRepro_PerModelKeyDropsCredentialID
      breaker key (provider=1, cred=9, model=gpt-4) = "1/gpt-4"
      breaker credentialID = 7 (requested 9)
      state seen by cred9 = closed
      DEFECT CONFIRMED: breaker carries credentialID=7, not the requested 9 (first-creator wins)
  --- FAIL: TestRepro_PerModelKeyDropsCredentialID (0.00s)

  === RUN   TestRepro_ReleaseProbeMissesPerModelBreaker
      DEFECT CONFIRMED: credential-keyed lookup returned nil
                        => ReleaseProbe was a NO-OP for per-model breakers
  ```

- **第三处连带**：`domains/credential/state_sync.go:131` 的 DB 上卷走 `GetCredentialState(credentialID)`，该函数按 `b.credentialID` 字段匹配（`breaker.go:1042`）——per-model 断路器的 `credentialID` 是**首个创建者**的 id（`NewPerModel` 把它存进结构体，`breaker.go:243`）⇒ **其它凭据的熔断状态永远不会上卷到自己的 DB 行**，运维看到的 `circuit_state` 与实际不符。

- **建议修法**：
  1. per-model 键改为 `"<providerID>/<credentialID>/<model>"`，并同步 `NewPerModel` 的 `key` 字段（`breaker.go:241`）；
  2. 新增 `Manager.ReleaseProbePerModel(providerID, credentialID, model)`，生产调用点（9 处）全部改调它；
  3. `GetCredentialState` 的匹配条件补上 model 维度（按 `b.credentialID == credentialID` **且** 该凭据名下的任一 per-model 断路器），或改为遍历该 credential 关联的 per-model 断路器；
  4. 补钉测：跨凭据不连坐 + ReleaseProbe 后半开槽确实释放。

### D1（P1）签名 thinking 直通 ⇒ 真凭据逐字节出网（脱敏旁路）

- **位置**：`security/sanitize/input_protocols.go:856-857`（分流判定）、`:908-949`（`sanitizeSignedThinkingBlock`）；`security/sanitize/detector.go:337-345`
- **缺陷机制**：r1057 契约是「检出敏感 + 需改写 ⇒ 拒整请求(400)」；r1058 改为「**只检测、不改写、原样放行 + WARN**」。判定条件 `signedThinkingBlock(block)` **只看 `signature` 字段非空**——该字段**完全由客户端控制**。命中即整块 thinking 文本（含真凭据）不脱敏直出网。
- **生产可达性**：高。sanitize input 中间件挂在入站请求面。代码注释中「客户端伪造会在上游被拒」的论证**只对 Anthropic 官方上游成立**；对**不验签的上游**（自建 vLLM / Ollama / 内部代理）等于无条件脱敏旁路。
- **旁证**：本轮自带的新测试 `security/sanitize/r1058_signed_thinking_bearer_test.go:157-182` **明确钉死**了该行为——含 `password=MySecretPass123` 的请求体被断言「逐字未动地到达下游 handler」。
- **建议修法**：保留「不改写」（签名覆盖字节，改写在密码学上不可能），但恢复**分级阻断**——`sanitizeSignedThinkingBlock` 检出后区分「散文误报」与「真凭据」（复用 `credibleBearerCandidate` 同族判据），真凭据 ⇒ 400/422 拒整请求；仅散文误报放行，且把 WARN 升级为 ERROR 并带规则名。

### D6（P1）MaaS 幂等重放返回**零值空响应**

- **位置**：`domains/ledger/service.go:179-183`、`:339-343`；`domains/inventory/service.go:148-153`、`:275-279`、`:388-392`、`:490-494`；`domains/trading/service.go:50-55`

## 四、看着危险、实则安全（明确排除，避免误伤）

| # | 模式 | 结论与依据 |

## 九、通用式（可复用纪律）

1. **「键空间分裂」比「键写错」更隐蔽**：熔断器改造只改了写路径的键（per-model），读路径（`Allow`）跟着改了，但**探针释放路径（`ReleaseProbe`）与状态上卷路径（`GetCredentialState`）没跟着改** ⇒ 系统同时存在两套命名空间。★ **凡是把实体标识从 A 维度切到 B 维度（如 per-credential → per-model），必须枚举「所有以该实体为参数的 API」逐个确认键空间**，否则必然漏。
2. **「契约声明」≠「实现遵守」**：`ports.go` 写 QuotePort 是无副作用纯函数，实现却 INSERT 两张表；`types.go` 写幂等键必填，实现零校验。★ **契约里的 "MUST" 要有一条对应的守卫测试**，否则文档只是愿望。
3. **「与主流程隔离」的新代码，其守卫常是同包的老测试**：`admin/diagnostic_handler.go` 违反的是 admin 包**早于本轮就存在**的守卫 ⇒ 本轮 CI 红不是「守卫生气」，而是「新代码没读同包纪律」。★ **新增文件前先看同包有没有 `*_guard_test.go`**。
4. **「示例文件」也是编译产物**：带 build tag 的示例文件一旦 tag 失配就编译失败，且它引用的是**当时**的 API 形态。★ 示例要么改名 `.go.example`，要么随主代码一起维护。
5. **「只检测不改写」在密码学上正确，在安全上可能是缺口**：签名块不可改写 ⇒ 只能拒不能改；于是「拒」与「放行」之间必须有**分级**（真凭据拒 / 散文放行），否则就是把「误报」换成「漏报」。★ **不可改写的通道，补偿控制只能加在「判据」上，不能指望「改写」**。
6. **「加一个并列 API」不等于修复命名空间分裂**（P0-a 实做新增）：原计划是「保留旧 API + 加一个 `ReleaseProbePerModel`」，实做时发现并列 API 恰恰是分裂的温床——两套命名空间并存于同一张 map，调用点选哪个全靠自觉，下一次改造照样会漏。★ **根治方向是让命名空间在类型层面唯一**：把「不带作用域维度」的方法从类型上删掉，让编译器替你守门（反射门禁再补一道，钉住方法集）。**用「删 API」换「加注释禁令」，是本轮性价比最高的一处决策。**
7. **「实体身份」与「状态键」可以不是同一个字段，但必须显式分开**（P0-a 实做新增）：nodehealth 的 `Node.Model` 是**节点健康状态键**（允许回退到标准化名以保证键非空），而熔断作用域必须是**offer 身份**且与准入逐字节一致。两者在退化候选上会不同。★ **一旦发现两个子系统用同一实体但取法不同，就不要在某个调用点"顺手统一"，而要把差异显式建模成两个字段**（本轮即新增 `Observation.BreakerScopeModel` / `Decision.BreakerScopeModel`），否则统一只是把分裂推到了别处。
8. **「修完但没有门禁」＝没修**（阶段 3/4 实做新增）：D7/D9/D14 的**修复**落地后，四个 MaaS 域仍是 `[no test files]` ⇒ 按本轮纪律「改回修复 ⇒ 门禁转红」，这三项**无法证明门禁非恒绿**，等于没修。★ **提交一个修复时，必须同时回答「哪条门禁会因为它被改回而转红」**；答不出来 ⇒ 这条修复不该单独提交。
9. **具体类型依赖是把测试挡在门外的墙**（阶段 3/4 实做新增）：`pool *pgxpool.Pool` 看着无害，但它让「跨租户写」这类**只体现在 SQL 与分支顺序上**的缺陷**无法被观察**——不连真库就测不了。★ 把依赖收窄成**窄接口**（`maasidem.Pool`）不是为了架构洁癖，是**可测性的前提**；且这是**放宽**（`*pgxpool.Pool` 天然满足）而非收紧，既有调用方零改动。**注意兼容方向**：接口参数比原具体类型更宽 ⇒ 既有调用方无需改动 ⇒ 收窄依赖的改造成本远低于直觉。
10. **跨租户缺陷必须用「拒绝路径上零写入」来钉，不能只断言错误码**（阶段 3/4 实做新增）：错误码对了但写库已经发生，等于没修。★ 本轮的做法是「**不设** `ExpectBegin`/`ExpectExec`」——任何写库调用都会让 mock 直接报错，测试随即失败；这条断言比错误码断言更接近「真的拒绝了」。
11. **变异实验要区分「编译错误」与「断言失败」**（阶段 3/4 实做踩坑）：D6 的第一版变异直接删掉了 `err` 声明 ⇒ 测试**编译不过**、根本没跑起来——这是「红」但**不是判别信号**。★ 变异必须**保持可编译**，让失败信息指向被测行为（如 `request payload 未被序列化："{}"`）。同理，**变异锚点没命中 ⇒ 脚本必须显式报 SKIP**，不允许静默当作「已验证」——本轮 D9/D6 的第一版锚点缩进不符，正是靠这条纪律避免了「假验证」。
