## 1. 执行摘要

### 1.1 部署概述
- **功能描述**: 添加 SSE 帧 JSON 验证层，拒绝上游供应商发送的格式错误帧
- **影响范围**: 所有流式请求，特别是 MiniMax 和 GLM 模型
- **预期收益**: 减少因格式错误导致的流式处理失败，提高系统稳定性
- **测试状态**: 245 环境已验证 4 小时，965 个请求，0 错误

### 1.2 风险等级评估

| 维度 | 等级 | 说明 |
|------|------|------|
| 整体风险 | **中低** | 功能独立，测试充分，有回滚方案 |
| 技术复杂度 | 低 | 逻辑简单，无外部依赖 |
| 影响范围 | 中 | 影响所有流式请求 |

| 业务影响 | 中低 | 短暂服务中断（2-3 秒） |

### 1.3 推荐决策
**✅ 推荐部署**，但需满足以下条件：

4. 团队成员待命

## 2. 风险识别与分析

### 2.1 技术风险

#### 风险 T1: 假阳性 - 有效帧被错误拒绝
**描述**: 验证逻辑过于严格，将有效的 SSE 帧判断为无效  
**可能性**: 低（10%）  
**影响**: 高 - 导致流式请求失败  
**证据**:
- ✅ 245 环境 965 个请求，0 个假阳性
- ✅ 33 个测试用例覆盖各种有效帧格式
- ✅ 包含 OpenAI、Anthropic、MiniMax、GLM 真实格式

**缓解措施**:
1. 验证逻辑仅检查 JSON 语法，不检查语义
2. 空载荷和 `[DONE]` 标记被视为有效
3. 非 `data:` 行（event、comment）直接通过
4. 已在测试环境充分验证

**监控**:
- 监控成功率是否下降
- 检查日志中是否有客户反馈

**应急预案**:
- 如发现假阳性，立即回滚
- 收集被拒绝的有效帧样本用于修复

---

#### 风险 T2: 性能退化
**描述**: 验证逻辑增加处理延迟或资源消耗  
**可能性**: 极低（5%）  
**影响**: 中 - 响应时间增加，影响用户体验  
**证据**:
- ✅ 基准测试显示验证开销 ~100ns-1µs
- ✅ 相比解析成本仅增加 ~10%
- ✅ 无额外内存分配（除验证时的临时变量）
- ✅ 245 环境无性能异常

**缓解措施**:
1. 验证在解析前执行（fail-fast）
2. 无全局状态或锁竞争
3. 验证成本远低于后续处理

**监控**:
- P95/P99 延迟变化
- CPU 和内存使用率
- QPS 变化

**应急预案**:
- 如延迟显著增加（>50%），回滚
- 分析性能瓶颈，优化验证逻辑

---

#### 风险 T3: 边缘情况未覆盖
**描述**: 存在未测试到的特殊 SSE 帧格式  
**可能性**: 低（20%）  
**影响**: 中 - 特定场景下可能失败  
**证据**:
- ⚠️ 测试覆盖了已知格式，但可能有未知变体
- ✅ 验证逻辑保守（只拒绝明显无效的帧）
- ✅ 已覆盖 minimax-m3、glm-5.2、OpenAI、Anthropic

**缓解措施**:
1. 采用宽松验证策略（只拒绝明确无效的帧）
2. 记录所有被拒绝的帧样本
3. 持续监控和迭代改进

**监控**:
- 检查 malformed_sse_frame 日志
- 关注客户反馈的异常

**应急预案**:
- 收集新的边缘情况样本
- 快速迭代修复并重新部署

## 5. 应急预案

### 5.1 回滚触发条件

**立即回滚（P0 - 0-2 分钟决策）**:
- 服务无法启动或频繁重启
- 成功率 < 50% 持续 5 分钟
- 出现 panic 或 crash
- 数据库连接完全失败
- 大量客户投诉

**考虑回滚（P1 - 5-10 分钟决策）**:
- 成功率 < 85% 持续 10 分钟
- Malformed SSE frame 率 > 10%
- 大量假阳性（有效帧被拒绝）
- 响应时间显著增加（>2x）
- MiniMax/GLM 模型完全不可用

**监控观察（P2 - 持续监控）**:
- 成功率 85-90% 波动
- Malformed SSE frame 率 1-5%
- 少量错误日志（<10 条/分钟）
- 性能轻微退化（<20%）

---

### 5.2 回滚执行流程

**自动化回滚（推荐）**:
```bash
# 执行回滚脚本
./scripts/rollback-154.sh

# 预计耗时: 1-2 分钟
# 包含: 停止服务 → 恢复备份 → 启动服务 → 验证
```

**手动回滚（备用）**:
```bash
# 1. 登录服务器
ssh -p <PORT> root@<154-IP>

# 2. 停止服务

# 3. 恢复备份
cd /opt/llm-gateway-go
mv gateway gateway.failed
mv gateway.backup.YYYYMMDD_HHMMSS gateway

# 4. 启动服务
systemctl start llmgo-154.service

# 5. 验证
systemctl status llmgo-154.service
curl http://localhost:8781/api/system/version
```

**回滚后验证**:
- [ ] 服务状态: running
- [ ] 版本号已回退

## 6. 灰度发布方案（可选）

### 6.1 方案概述
如果风险偏好更保守，可以考虑灰度发布：

**阶段 1: 10% 流量（1 小时）**
- 部署到单个实例或限制路由权重
- 监控关键指标
- 无异常后进入下一阶段

**阶段 2: 50% 流量（2 小时）**
- 扩大部署范围
- 持续监控
- 无异常后进入下一阶段

**阶段 3: 100% 流量（全面部署）**
- 所有实例更新
- 持续监控 24 小时

### 6.2 适用场景
- 生产环境流量非常大
- 对稳定性要求极高
- 有多实例部署能力

### 6.3 本次部署建议
**不推荐使用灰度发布**，理由：
- ✅ 功能已在 245 环境充分验证
- ✅ 逻辑简单，风险可控
- ✅ 有快速回滚能力
- ⚠️ 单实例部署，灰度成本高
- ⚠️ 灰度部署会延长整体部署时间

**推荐**: 直接全量部署 + 密切监控 + 快速回滚准备
