## 三、P0 —— 流程闭环断裂（改动正确但接线是断的）

### P0-A｜reasoning 烧光输出预算的「免费重试」在生产上**永远不会发生**（C7）

**声称**（`AGENTS.md` 层3 + 提交说明）：「加倍 `max_tokens` 同候选**免费重试一次**（`reasoningBudgetBumped` 旗标仿 `ctxLenRecoveryRetry`）；二次仍烧完走既有 empty failover」，并称 211 部署验证「reasoning 加倍重试日志命中 1 次」。

**实测（本轮新写探针测试，复刻生产 dispatch 路径）**：

```
PROBE RESULT: sentMax=[300] res=false err=[transient] reasoning exhausted completion budget; retrying with doubled max_tokens
```

⇒ **只发出 1 次上游调用**，`max_tokens` 停在 300，**加倍的 2048 从未上线**。

**根因（读码定位）**：
1. `domains/streaming/executors/executor.go:2803-2814`：`dispatch_v2 是唯一执行路径`（旧同步候选循环已退役）⇒ 生产**必然**走 `executeViaDispatch`。
2. `executor_dispatch.go:445-448`：`dctx = &dispatchCtx{ … retryPerCred: 0 … }`，注释明写「Dispatch mover owns same-node retry. Protocol-local loops must perform exactly one HTTP call」⇒ 协议内循环的重试预算为 **0**。
3. `executor_dispatch.go:716`：`paramsCopy.DispatchAttempt = true`。
4. `executor_chat.go:2910-2915`：`effectiveOpenAIRetryBudget(0, true)` ⇒ **0**（只有 `dispatchAttempt=false` 时才兜底成 1）。
5. `executor_chat.go:1184`：`for attempt := 0; attempt <= effectiveMaxRetries+mnfBonus || probeRetry; attempt++` ⇒ 预算 0 ⇒ **循环只跑 1 次**。
6. `executor_chat.go:2588-2606`：bump 分支 `return nil, &retryableError{…}` ⇒ 循环因预算耗尽而退出 ⇒ `lastErr` 原样上抛。

**为什么"免费"是假的**：本文件的三个既有"免费重试"机制**各有一套预算豁免**，bump 一个都没用：
- `mnfBonus`（`:1743`）——**改循环上界** `attempt <= effectiveMaxRetries+mnfBonus` ⇒ 即使 `maxRetries=0` 也多给一次迭代；
- `ctxLenRecoveryRetry`（`:1202-1204`）——**`attempt--`** 抵消自增 ⇒ 不消耗预算；
- `probeRetry`（`:1208-1211`）——**`attempt--` + `probeNoDelay`**。

`b2a836b77` 的 bump **既没改上界、也没 `attempt--`** ⇒ 它消耗的是**唯一的**那一次迭代 ⇒ 自己把自己挤出去了。

**影响**：★ **「minimax 不行 / glm 可行」这个用户原始症状（层3）根本没被治好**。生产仍然：reasoning 烧光 ⇒ `empty_response` ⇒ 全候选 503。**AGENTS.md 里"211 部署验证命中 1 次"的读数需要重新审视**——那条日志（`executor: reasoning exhausted the completion budget; retrying same candidate…`）是在 `return` **之前**打的 ⇒ **日志命中 ≠ 重试真的发生** ⇒ 这正是「错的量具比没量具危险」的典型形态。

**修法（采纳仓内既有形态）**：照 `mnfBonus` 写法给 bump 一个预算豁免。

⇒ **`h.passiveSink.Submit(...)`（全仓唯一调用点）在生产上永远不执行** ⇒ 955 表恒空 ⇒ 该特性整体无效。

## 九、通用式（本轮沉淀）

★ **通用式一：修好函数 ≠ 修好产品。**
⇒ 本轮三条最贵的缺陷（P0-A / P0-B / P1-A）**全部**是「新逻辑正确但接线断了」，而**全部**躲过了单测——因为单测直接调用新函数，**绕过了接线点**。
⇒ **纪律：每条声称「闭环」的链路，必须有一条从生产入口出发的测试**（走真实接线点 + 生产形态的参数），而不是只测新函数的纯逻辑。
⇒ ★ 尤其当生产形态与测试形态**参数不同**时最危险：P0-A 的测试用 `maxRetries=2`，生产用 `0` ⇒ **测试形态把缺陷完全遮住了**。

★ **通用式二：日志命中 ≠ 行为发生。**
⇒ P0-A 里那条 `slog.Warn("…retrying with doubled max_tokens")` 打在 `return` **之前** ⇒ **重试根本没发生，日志照样出现**。
⇒ **纪律：验证一个「重试/补偿」是否真的发生，要断言【可观测的外部效果】（如上游收到的第 2 次请求的内容），不是断言日志行出现。**
⇒ 与仓内既有通式「日志推进不能作为『已落库』证据」同族（同一次事故的两种形态）。

★ **通用式三：便宜的归一化 helper 要被所有同语义比较点共用。**
⇒ P1-A 的根因是**同一个概念有两套字符串**（`"openai-completions"` vs `"openai-chat"`），而仓内**早已**有 `canonicalInboundWire()` 这个正解，只是没被格式门用上。
⇒ **纪律：出现「口径差」时，先在仓内找同族 helper；找到了就复用，不要在新位置再写一遍比较。**

★ **通用式四：独立聚合 ≠ 同一行。**
⇒ P1-D 的 `min(currency)` 与 `min(price)` 是**两个独立聚合**，产出的是**两行各自的最值**，却被当成「同一行的两个字段」使用 ⇒ 跨币种比值。
⇒ **纪律：SQL 里凡是要「同行的多个字段一起取」，必须用 `array_agg(… ORDER BY …)[1]` 或 `GROUP BY` 保证行绑定；不能靠多个 `min()` 的巧合。**
