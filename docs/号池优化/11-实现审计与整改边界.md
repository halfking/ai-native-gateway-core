## 2. 本次修复

### RPM 记账时序

原实现先调用 `CheckCredentialRPM`，再获取 Global/Pool/Credential semaphore。请求如果在并发层超时，仍会占用 RPM 窗口，导致后续真实请求被错误拒绝。

现在的顺序是：

```text
rate-limit 开关检查
  -> 获取 global
  -> 获取 provider pool
  -> 获取 credential semaphore
  -> 原子预留 credential RPM
  -> 获取 identity/key soft-cap
  -> 返回 release
```

RPM 预留失败时会释放已经获取的三个硬限制层。新增回归测试覆盖“并发获取失败不消耗 RPM”。

## 3. 方案必须修订的边界

### 不采用“5ms 熔断”作为硬指标

5ms 不是熔断动作的可验证 SLA。现有 breaker 是同步内存状态机，实际目标应定义为：

- 错误分类完成后，在同一请求路径内禁止继续选择该 credential；
- 状态传播延迟以 p99 指标衡量，而不是写死 5ms；
- 401/封禁类永久隔离，429 按 `Retry-After` 或指数退避冷却；
- 跨进程状态需要 Redis/数据库一致性方案后再承诺时间指标。

### 不直接引入 DB JSONB Pipeline

当前 `provider.Policy` 来自既有查询和缓存，仓库中没有 `provider_policies.routing_pipeline` 字段。新增 JSONB 配置前必须先完成：

1. 迁移 up/down；
2. policy 读取、校验、缓存失效和回滚；
3. tenant/provider/model 作用域确认；
4. staging 验证；
5. 失败时回退现有路由。

### 不把“随机兜底”当作无限制兜底

随机兜底只能从已经通过租户、模型、生命周期和安全过滤的候选中选择，不能绕过 breaker、RPM、并发或手动禁用状态。若无可用候选，应返回结构化 no-candidate 结果并触发现有 degraded/probe 流程。

## 4. 下一步实施顺序

1. 先为现有路由建立 selection seam 和可观测指标，不改变默认行为。
2. 独立实现并测试 Smooth WRR，输入使用现有 `provider.Candidate`，不新建重复 credential model。
3. 将 WRR 作为同层候选排序/选择策略接入 `Router.PlanCandidates`，保留现有 tier、sticky、protocol affinity 和 StateManager 过滤顺序。
4. 只有在真实指标证明需要时，再实现水位监控；优先从已有 Prometheus/Redis/数据库聚合能力取数。
5. 不在第一阶段改造 `Limiter.AcquireAll` 为 WFQ；先解决 RPM/TPM 预留、队列容量、取消、超时和公平性测试。
6. 每一阶段通过 `go test`, `go test -race`, `go vet`, `go build` 后再进入下一阶段。

## 5. 当前已验证范围

- 已修复 RPM 预留在并发获取失败前记账的问题。
- 已新增对应单元测试。
- 尚未实现 WRR、Pipeline、水位监控和 WFQ，因此这些能力没有实现验证证据。
