## 2. Smooth WRR 算法选型

### 2.1 候选算法对比

| 算法 | 复杂度 | 分布平滑度 | 实现难度 | Go 生态 |
|---|---|---|---|---|
| **Nginx Smooth WRR** | O(N) | ★★★★★ | ★★☆☆☆ | 标准实现, 参考 nginx |
| **Weighted Random** | O(1) | ★★★★☆ | ★☆☆☆☆ | 简单随机 |
| **Edf Weighted** | O(logN) | ★★★★★ | ★★★★☆ | 堆实现 |
| **Interleaved WRR** | O(1) | ★★★☆☆ | ★☆☆☆☆ | 固定序列 |

**决策**：采用 **Nginx Smooth WRR**（平滑加权轮询）

理由：
1. **最平滑**：无突发聚集，A:3/B:2/C:1 → A,B,A,C,A,B（不会出现 A,A,A,B,B,C）
2. **O(N) 低开销**：N=候选数（通常 <50），每次选路 O(N) 可接受
3. **Go 生态成熟**：cc-relay 已有 Go 参考实现
4. **可预测性强于 Bandit**：确定性的调度序列，方便调试和预期

### 2.2 Nginx Smooth WRR 原理

```
currentWeight = [0, 0, ...]  // 每个候选的当前权重
totalWeight = sum(weights)

每轮选路：
  1. 每个候选: currentWeight[i] += configuredWeight[i]
  2. 选择 currentWeight 最大的候选
  3. 被选中的: currentWeight[selected] -= totalWeight

示例 weights [3, 2, 1]:
  Step 1: [3, 2, 1] → 选 A, A → [0, 2, 1]
  Step 2: [3, 4, 2] → 选 B, B → [3, 0, 2]
  Step 3: [6, 2, 3] → 选 A, A → [3, 2, 3]
  Step 4: [6, 4, 4] → 选 A, A → [3, 4, 4]
  Step 5: [6, 6, 5] → 选 B, B → [6, 3, 5]
  Step 6: [9, 5, 6] → 选 A, A → [6, 5, 6]
  ...
  结果序列: A,B,A,A,B,A... (分布均匀)
```

## 3. 多策略融合设计

### 3.1 三引擎架构

行业最佳实践表明，单一调度算法无法覆盖所有场景。我们设计**三引擎可切换架构**：

```
                    ┌──────────────────────┐
                    │   RoutingStrategy    │
                    │  (配置可选, 动态切换) │
                    └──────┬───────────────┘
                           │
          ┌───────────────┬┴───────────────┬───────────────┐
          ▼               ▼                ▼               ▼
   ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌────────────┐
   │ Smooth WRR │  │   Bandit   │  │ Priority-  │  │ Composite  │
   │ (Scheduler) │  │ (Exploit)  │  │ Based      │  │ (Scoring)  │
   └──────┬─────┘  └──────┬─────┘  └──────┬─────┘  └──────┬─────┘
          │               │               │               │
          └───────────────┴───────────────┴───────────────┘
                          │
                          ▼
                 ┌──────────────────┐
                 │  Candidate Pool  │
                 │  (健康/限流过滤)  │
                 └──────────────────┘
```

### 3.2 策略适用场景

| 策略 | 适用场景 | 配置建议 |
|---|---|---|
| **Smooth WRR** | RPM/TPM 差异明确的账号池, 需要确定性调度 | weights = RPM/TPM 归一化 |
| **Bandit** | 账号质量未知, 需要探索/利用平衡 | 默认策略, 自适应学习 |
| **Priority-Based** | 多级账号 (VIP/普通/免费), 资源隔离 | tier 分级 + fallback |
| **Composite Scoring** | 多目标优化 (价格+速度+成功率) | maxllm_gate 模式 |

### 3.3 权重自动计算

```
weight_i = (rpm_i / max_rpm) * 1000 + (tpm_i / max_tpm) * 500

动态调整：
  - 每次 429 后: weight *= 0.7（缩权）
  - 冷却恢复后: weight 恢复原值
  - 连续成功: weight += 5（上探）
```

## 4. 号池水位预警设计

### 4.1 水位指标

```
整体可用吞吐量 = Σ(credential_i.available_rpm * weight_i)
安全线 = 整体可用吞吐量 * 150%  (保留 50% 余量)
预警水位 = 整体可用吞吐量 < 安全线
紧急水位 = 整体可用吞吐量 < 安全线 * 50%
```

### 4.2 预警分级

| 级别 | 条件 | 动作 |
|---|---|---|
| **INFO** | 单账号 RPM 使用率 > 80% | 日志记录 |
| **WARN** | 整体可用吞吐量 < 安全线 | 飞书通知 + Prometheus Alert |
| **CRITICAL** | 整体可用吞吐量 < 安全线 × 50% | 飞书 @所有人 + 电话告警 |
| **EMERGENCY** | 无可用账号 | P0 oncall 立即处理 |

### 4.3 号补充建议

```
建议补充量 = (安全线 - 当前可用吞吐量) / 单账号平均吞吐量

例：
  当前可用吞吐量 = 1000 RPM
  安全线 = 1500 RPM
  单账号平均吞吐量 = 500 RPM
  → 建议补充 (1500-1000)/500 = 1 个账号
```
