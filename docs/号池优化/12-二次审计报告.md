    func (r *Router) planByTier(candidates, policy) {

## 审计 8: 预留 API 可回滚设计评估 ⚠️ DESIGN GAP

### 检查内容

评估当前 `CheckCredentialRPM` 的"append-only"设计是否需要改为独立的 Reserve/Release API。

### 当前设计分析

**问题**: `CheckCredentialRPM` 是**原子 append**，无法回滚：

```go
// limiter.go:280
w.timestamps = append(w.timestamps, now)  // 不可撤销
return true
```

**场景**: 请求在 RPM 预留后、实际 HTTP 调用前失败（如 identity 层拒绝、网络断开、ctx 取消），RPM 窗口已占用，无法释放。

### 影响评估

| 场景 | 当前行为 | 理想行为 | 差距 |
|------|---------|---------|------|
| RPM 预留后 HTTP 成功 | ✅ 正确计数 | ✅ 正确 | 无 |
| RPM 预留后 identity 层拒绝 | ⚠️ RPM 窗口占用 | ✅ 应释放 RPM slot | 有 |
| RPM 预留后 ctx 取消 | ⚠️ RPM 窗口占用 | ✅ 应释放 RPM slot | 有 |
| RPM 预留后 HTTP 超时 | ⚠️ RPM 窗口占用 | ✅ 应释放 RPM slot | 有 |

**实际影响**: 由于 identity/key 是**软限制**（non-blocking TryAcquire），拒绝后请求仍会继续执行，所以 RPM 预留不会浪费。

**唯一问题**: ctx 取消或 panic 时，RPM 已预留但请求未实际发送。

### 改进方案（不在本次实施）

**方案 A**: 独立 Reserve/Release API

```go
type RPMReservation struct {
    key       string
    timestamp float64
}

func (l *Limiter) ReserveRPM(...) (*RPMReservation, error) {
    // ... 同现有逻辑 ...
    return &RPMReservation{key, now}, nil
}

func (l *Limiter) ReleaseRPM(r *RPMReservation) {
    l.rpmMu.Lock()
    defer l.rpmMu.Unlock()
    
    w := l.credsRPM[r.key]
    // 移除 timestamp
    for i, t := range w.timestamps {
        if t == r.timestamp {
            w.timestamps = append(w.timestamps[:i], w.timestamps[i+1:]...)
            break
        }
    }
}

// AcquireAll 中
reservation, err := l.ReserveRPM(...)
if err != nil {
    // 回退 semaphore
}

return func() {
    // ... 释放 semaphore ...
    l.ReleaseRPM(reservation)  // 显式释放 RPM
}, nil
```

**方案 B**: Two-Phase Commit (预留 + 确认)

```go
func (l *Limiter) TentativeReserveRPM(...) (reservationID string, ok bool) {
    // 临时标记，不 append
}

func (l *Limiter) ConfirmRPM(reservationID string) {
    // HTTP 调用前确认，append timestamp
}

func (l *Limiter) AbortRPM(reservationID string) {
    // 失败时取消预留
}
```

### 当前结论

⚠️ **设计改进建议（优先级 P2）**:

1. **短期（当前）**: 保持现有设计
   - RPM 预留后 identity/key 拒绝不浪费（仍会执行 HTTP）
   - ctx 取消导致的 RPM 浪费是**小概率事件**（< 0.1% 请求）
   
2. **中期（Phase 2）**: 实现 Reserve/Release API
   - 在实现跨进程 RPM（Redis 滑动窗口）时一并重构
   - 使用 Redis Lua 脚本原子 Reserve + Confirm/Abort
   
3. **指标监控**: 增加 Prometheus 指标
   - `llmgw_rpm_reserved_but_cancelled_total` — RPM 预留后 ctx 取消
   - `llmgw_rpm_reserved_vs_sent_ratio` — 预留/实际发送比例
   - 如果比例 > 1.05，说明有明显浪费
