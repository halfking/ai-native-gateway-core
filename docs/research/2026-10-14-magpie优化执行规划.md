## 3. P0 任务卡

### P0-A 等待有界 + 可读终态

- **目标**：交互请求首字节前等待 ≤240s；终态对客户端可读、可机器解析。
- **现状锚点**：`domains/streaming/survival_coordinator.go`、`survival_wiring.go renderSurvivalTerminal`、
  `attempt_outcome.go`（deadline 终态 5 处）、在途 `settings/spec_survival.go`。
- **设计**：
  1. 沿用在途 240s 默认与 `survival.interactive_deadline_seconds`；durable 模式（86400）不受影响；
  2. 终态契约：非流式响应加 `Retry-After: <earliest_recovery_sec>`（无值时取 30）；JSON 错误体新增
     `error.retry_after_seconds` 与 `error.attempts`（**新增字段，不改 code/type**，兼容既有客户端）；
  3. 流式已发 200 的情况：终态帧携带同名字段（chat 帧 `code` 已有，见 r1028）。
- **判据**：`survival_terminal_contract_test.go`——全候选红夹具下断言 ①总耗时 ≤ deadline+ε ②Retry-After 头在场
  ③字段可解析；**前提在场配对**：同夹具 deadline 调到 18000 时等待确实被延长（证明判据驱动的是真实等待路径）。
  变异：删 Retry-After 写入 → 红；默认值改回 18000 → 红。
- **上线验证**：本地制造全灭（禁用某模型全部绑定），curl 计时 + 看头；245 灰度观察 W1。
- **回滚**：settings 键调大即可（热加载）。**估时** 1.5（在途基础上）。

### P0-B 剔参学习收敛进 reqprobe

- **目标**：严格中转的「未知字段 400」从「每字段一次事故 + 一次代码修」变为「一次同候选重试 + 学习共享」，覆盖全部出站腿。
- **现状锚点**：`internal/reqprobe/{diagnose,strip,types,coordinator,redis}.go`；
  `executors/reqprobe_integration.go`（`maxParamStrips=3`、`reqprobeApplyLearned`）；
  `executor_chat.go:822`（首发应用）、`:1608-1633`（剥参重试）；`executor_anthropic.go:1238-1262`（只记录）；
  原生 Responses 腿 `executor_chat.go:781-793`（`StripStreamOptions`/`AdaptChatParamsToResponsesWire`）。
- **设计**：
  1. **拒绝即学习（白名单族）**：对 magpie `optionalFields` 同族字段（store/metadata/service_tier/
     prompt_cache_key/prompt_cache_retention/safety_identifier/parallel_tool_calls/verbosity/
     enable_thinking 等）在**上游点名拒绝时立即**写学习记录；非白名单字段维持「剥后成功才学习」；
  2. **骨架按线格式**：`skeletonParams` 中的 `stream_options` 改为按 wire 判定——目标为
     openai-responses/anthropic/gemini 时可剥（该线格式本无此字段，usage 由终态事件提供，r1026 结论），
     openai-chat 时仍保护（剥掉会丢 usage）。**这一条把 paramrefusal 与 reqprobe 的策略冲突收敛为单一规则**；
  3. **出站 choke point 统一**：Anthropic 执行器与原生 Responses 腿接入同一 `reqprobeApplyLearned` +
     剥参重试钩子；静态 `StripStreamOptions` 保留为兜底但改由 reqprobe 学习覆盖记录；
  4. **诊断正则吸收**：pydantic JSON `{"detail":[{"type":"extra_forbidden","loc":["body","x"]}]}`、
     Kimi「at position N」消息内字段（magpie `refusedInMessages`）迁入 `diagnose.go`；
  5. 学习键统一 (provider_id, upstream_model, wire_protocol)，Redis 共享（本仓优势，保留）。
- **判据**：`p0b_reqprobe_convergence_test.go`
  - raw-logs 真实失败体回放：vapeur stream_options 三腿、thinking、Bedrock `output_config.effort`、kimi `web_search`；
  - 断言首次 400 → 同候选重试成功 → 第二次请求首发即不带该字段（学习生效）→ **另一实例**（第二个 Store 客户端连同一 miniredis）也不带；
  - 前提在场：chat 线 stream_options **仍保留**（骨架按线格式的负向钉子）；model/messages 被点名不剥；
  - 变异：去掉「拒绝即学习」→ 第二次请求仍带字段 → 红；骨架恢复全局保护 → responses 腿用例红；
    Anthropic 腿去掉接入 → 红。
- **上线验证**：E1 指标；`/api/admin/request-anomalies`（r1027 格式错误表）记录 recovered。
- **回滚**：建议 settings `reqprobe.learn_on_refusal_enabled`（默认 true，热加载）。**估时** 3。

### P0-C 失败归责矩阵 + rest 分级 + 单一重置解析器

- **目标**：每一种失败先判「谁该受罚（无 / 模型绑定 / 凭据 / provider）、罚多久」，再动 breaker；
  客户端错误永不冷却节点；配额冷却对齐上游声明的重置时刻。
- **现状锚点**：`errorsx/classify.go`（`KindClientBug` 已是「不冷却」语义，L24-29、376-435）；
  `domains/credential/breaker.go:108-140`（per-kind 策略）、`495-505`（隔离）；
  `writer.go:348-414`（绑定级冷却）、`596 coolingDuration`、`682-740 parseQuotaResetTimestamp`（UTC）；
  `executors/executor_nodehealth.go:182 ApplyNodeHealthDecision`、`:397 recordProtocolCircuitFailure`；
  在途 `errorsx/reset_time_parser.go`、breaker `RecordFailureWithReset`（未接线）。
- **设计**：
  1. **归责矩阵**：新增 `errorsx/penalty.go`（建议名）`PenaltyOf(kind) → {Target: none|binding|credential|provider, Policy}`，
     作为 breaker/writer 的唯一前置判定；矩阵初值对齐 magpie：client_bug / shape / context_length /
     content_refusal / proxy → none；model_not_found / model_deprecated / 模型级 quota → binding；
     auth / credit / account_restricted → credential；upstream_down → provider；
  2. **闭集钉子**：测试枚举 `errorsx` 全部 ErrorKind 常量，未登记即红（同 r1019 动词表封闭性钉子做法）；
  3. **单一解析器**：合并 `parseQuotaResetTimestamp` 与在途 `ParseQuotaResetAt` 为 `errorsx.ParseQuotaReset`；
     时区规则：文案自带时区（`UTC+8`、`+08:00`、`北京时间`）按其解释，无时区按 UTC 并打 `tz_assumed` 日志；
     中文「将在/将于 … 重置」、英文 `resets in 0h 19min`、`\uXXXX` 解码（magpie `wordsOf/resetsWhen`）；
  4. **rest 分级**：credit 30min 平坦重探；quota 对齐 resetAt（夹 30s~2h，超过 2h 交 quota 探活周期收回）；
     rate 优先 Retry-After，否则 1m 翻倍上限 30m，30m 内再犯计连续；未知 1m→10m；
  5. **接线**：resetAt 随 `upstream.Error` 与 Retry-After 一起穿透到 `ApplyNodeHealthDecision` / `recordProtocolCircuitFailure`。
- **判据**：`p0c_penalty_matrix_test.go`（闭集 + 每类目标）；`p0c_reset_parse_test.go`（WorkBuddy/GLM「余额不足」1113/
  Factory/OpenAI 文案样本、带时区与不带时区两组、`\u` 转义样本）；`p0c_wiring_test.go`——**同层驱动请求路径**：
  json-word 400 后节点不进冷却（r1027 回放）、quota 429 带「resets in 19min」后冷却 ≈19min；
  前提在场：同凭据其它模型绑定仍可选。变异：矩阵把 client_bug 改成 credential → 红；接线处丢 resetAt → 红。
- **上线验证**：E2、E3；154 观察 r1027 同型请求不再引发 no_candidate 级联窗。
- **回滚**：建议 settings `routing.penalty_matrix_enabled`（false 回旧 per-kind 路径）。**估时** 3。

### P0-D 全灭时 probeOne / quotaHeld + 立即出口

- **目标**：候选全部在冷却时，不再「所有请求轮流打所有节点 + 无界等」，而是每请求最多半开探测一个、
  或直接给出带恢复时间的 429。
- **现状锚点**：`executors/executor.go:2533`（全灭 → `ProbeSync` 救援）、`bg/node_probe.go:1632 ProbeSync`、
  `attempt_outcome.go:437-445`（wait_recovery_window）、`domains/streaming/handler.go:5347-5390`（全员 429 聚合）。
- **设计**：
  1. **probeOne**：全灭时按冷却到期时间排序，只对**最早到期**的一个候选发起本请求的真实调用（即半开探测，成功即恢复），
     同一 (model) 维度用 Redis `SET NX PX` 做单飞，并发请求不重复探测同一节点；
  2. **quotaHeld**：若剩余候选全部是 quota/credit 类冷却，**不探测**，立即返回 429 + `Retry-After`（最早 resetAt）+
     原上游拒绝摘要；
  3. 其余情况（transient 类全灭）进入 P0-A 的有界等待，等待期间每轮仍只 probeOne；
  4. 与 URSM/reconciler 关系：probeOne 成功走既有 `ApplyProbeForTenant(success=true)` 路径，不另写状态。
- **判据**：`p0d_probe_one_test.go`——3 候选全冷却、到期时间不同：断言上游调用只命中最早到期者 1 次；
  10 并发请求下该节点探测调用 = 1（单飞）；全 quota 冷却时上游调用 = 0 且 429 带 Retry-After。
  前提在场：去掉冷却时 3 候选正常轮转（证明夹具候选可达）。变异：排序改随机 → 红；去单飞 → 并发用例红。
- **上线验证**：W2 ≤1.2；154 日志 `ProbeSync` 频率下降。
- **回滚**：建议 settings `routing.probe_one_enabled`。**估时** 2.5。
