## 〇、结论（先读这一节）

1. **v5 的 magpie 基线已经过期。** v5 用的是 magpie `591ed58b` / `v0.1.1228`（2026-10-14）。
   到现在 magpie 已推进 **994 个提交、139 个版本**。其中**五个网关扩展点全部是 2026-10-15 新增**，
   异步 Bun 钩子是 2026-10-16 新增（见 §1.2 的创建时间表）。
   ⇒ **v5 里"不建议照搬：JS 中置件"那条判断，形成时 magpie 的插件运行时还不存在**，
   插件问题在 v5 体系里**从未被真正回答过**。这正是本文要补的洞。

2. **插件结论：magpie 的五个扩展点里，有 3 个是本仓当前架构的天然补位，1 个需要范式变更，1 个不建议照搬。**

   | magpie 扩展点 | 能否用于本仓网关层 | 判断 |
   |---|---|---|
   | 观察者（observer） | **能，且低风险** | 本仓有实时拓扑/采集，但缺**统一请求级观察者接口**与有界丢弃语义 |
   | 路由策略（strategy） | **能，且收益高** | 本仓策略散在多层，收敛成"只排序"的 `Strategy` 可直接消掉重复 |
   | 预算（budget） | **能** | 本仓 key 级限额语义是"令牌桶"，magpie 是"预约-释放"，需先读现状再定改法 |
   | 中间件（middleware） | **需要范式变更** | magpie 的 `onProvider` **按每次上游尝试改 body**，这是进程外插件做不到的 |
   | 工具（tool） | **暂不建议** | 本仓暂无真实工具点需求 |

3. **本仓扩展机制当前是 5 套并存、其中 2 套在生产里是死的或关着的**（§3.5）。
   在谈"要不要加插件"之前，先要把扩展点收敛成**一条链 + 一份失败策略表**，
   否则新增插件只会变成第 6 套并行机制。

4. **本仓 `plugin-runtime` 有一个已声明但未落地的数据面空洞**（§3.6）：
   能力表已含 `request.mutate` / `request.block` / `response.mutate` / `response.block` / `tool.execute`，
   但 `SandboxEnforcer` 在没有真沙箱时一律拒绝；5 条 capability 路由只挂了 2 条。
   ⇒ 这是"声明与实现不同源"，与本仓 LESSONS 里反复出现的"同一口径两处实现"同族，
   应当**先补齐或明确判死**，而不是在它之上再叠一层。

5. **非插件域有一条可直接落地的新增项**：magpie 的 rest/失败归责词表已达 **19 类**
   （`internal/gateway/routing.go:270-325`），本仓 `errorsx.PenaltyOf` 闭集明显更窄。
   这是 P0-C 的自然增量，不需要新机制，只需要补 kind + 归责 + 门禁（§4 域 B / §6-P0-3）。

## 二、magpie v0.1.1367 能力清单

### 2.1 定位

跨平台桌面应用（macOS/Windows/Linux）+ TUI + Web UI + CLI + Docker + Termux。
内核是**一个本地网关**：把任意 agent（Claude Code / Codex / Gemini CLI / OpenCode 等 60+ 种）
的配置文件改写成指向本地网关，于是"任意 agent 用任意 provider 或订阅"。
订阅账号（Claude/ChatGPT/Copilot/Gemini/Grok 等）由插件提供，网关只把请求转给插件的 fetch。

### 2.2 请求路径（逐段）

依据 `docs/subsystems/gateway-routing.md` 的 "Runtime path"，并回源码核对：

| 段 | 做什么 | 证据 |
|---|---|---|
| 1. 读体 | 有界读体（默认 512 MB decoded），解 `gzip`/`zstd`；ChatGPT 账号的轮次压回 zstd ≤2 MiB | `internal/gateway/request_bounds.go`；`provider.CodexCompressed` |
| 2. 身份与记录 | 建立网关会话身份、可选记录 | `internal/gateway/middleware.go` `serveAgent` |
| 3. 异步钩子 | Bun 钩子 `onRequest` 补上下文（可回滚），`onResponse` 事后通知 | `internal/plugin/gateway.go`、`internal/gateway/gateway_hooks.go` |
| 4. 中间件链 | `gwmw.Agent`：`Begin` → 每中间件 `Run.Request` → 每上游尝试 `Run.Tried` → `Run.Wrap`（包响应写者） → `Run.End` | `internal/gwmw/gwmw.go` |
| 5. 脱敏 | 发厂商前遮蔽，回包逐事件还原；**要求遮蔽却无人提供 ⇒ 503，什么都不发**（失败关闭） | `internal/gateway/redact.go`、`gwmw.Masking` |

| 8. 一次尝试 | 按 provider 的实际能力选线格式（直通或翻译），转发 | `internal/gateway/gateway.go` `attempt`/`forwardOnce` |

### 2.3 路由与可用性

- **rest/失败归责词表 19 类**（`internal/gateway/routing.go:270-325`）：
  `credit / quota / rate / other / auth / canceled / foreign / floor / update / verify / refused / shape / prompt / effort / proxy / overflow / room / slow / loop / restricted`。
  语义分工清楚：**内容/形状/安全拒绝不罚账号**（`failRefused`/`failShape`/`failPrompt`/`failEffort`），
  账号级证据才罚凭据（`failCredit`/`failQuota`/`failRate`/`failAuth`）。
- **车道与限流**：每 key/account 有 `MaxConcurrency` 车道 + `QueueLimit`/`QueueWait` 队列（超限 429）；
  `MaxRPM` 为滚动 60 秒窗，等待超过 2 分钟直接 429 + `Retry-After`。
- **Sink**：429 但配额未耗尽的 key 退到队尾（`internal/gateway/sink.go`）。
- **亲和**：会话粘在回答它的 key/account 上，让厂商 prompt cache 命中；模式 auto/session/turn/off/strict。
- **全灭**：只半开探测最早到期者（probeOne），或直接 429（quotaHeld）。
- **路由策略点**：Smart 是内核，其余（Ordered/Rotate/LeastUsed/Pace/Weighted）是 `plugins/rotation` 提供的。

### 2.4 协议翻译

Chat / Responses / Anthropic Messages / Gemini / Vertex AI 五套方言，hub-and-spoke（IR 中枢）。
要点：翻译路径强制上游流式、同协议直通不强制、上游整包回时拆成流（`wholeAsStream`）；
`unfit` 记忆"这个模型在这家 provider 的这个协议上会拒"（仅内存）；工具历史配对、密封推理、
Gemini thoughtSignature 编进 call id。

> 该域 v5 已深挖，本文不重复。**增量见 §2.9**。

### 2.5 用量 / 额度 / 预算

- **额度感知**：magpie 读每个订阅账号的"还剩多少"（`Allowance`、窗口续期时间、每周节奏），
  路由按余量决策（`routes.Seat.Known/Learns/Used/Soon/Pace`）。
- **预算点**（`internal/gwbudget/gwbudget.go`）：`Reserve(who, body, model, now) (release, refused)`，
  **预约式**——先按预估扣住、结束释放；拒绝带 `RetryAfter`/`ResetAt`。
  拒绝态：429 `gateway_key_limit`（带 `Retry-After`、`X-Magpie-Limit-Reset`）；
  有限额却无人提供 limiter ⇒ 503 `gateway_key_limit_off`（**失败关闭**，`X-Should-Retry: false`）。
- **用量行**：终局一行带 `tries`；被拒但已计费的尝试另写 `handed_on:true` 子行，共享 `route_id`。

### 2.6 隐私

`internal/redact` + `internal/masking`：可逆 Mask（发厂商）+ 不可逆 Scrub（落盘）。
id 安全（不把 UUID/32 hex 误当秘密）、工具 schema 安全（改描述不改语法）、跨事件还原、
按 provider 跳过遮蔽（`provider.SkipsRedaction`）。

### 2.7 会话与观测

- 决策 trace 在**决策点当场写**（候选 Order / Left / Tries / Swapped），磁盘留 30 天 / 200 MB。
- 路由 trace 只存**名字和大小，不存正文**；正文只在内存里留最近 10 份（≤64 MiB 总量）。
- `usage.Observer` 观察点 + OTLP 导出（`internal/otlp`、`plugins/otel`）。
- UI 侧每个请求给"速度"或"为什么没有速度"。

- 钩子：`onRequest`（改请求体）、`onProvider`（**按每次上游尝试改体**）、`onEvent`（改单个 SSE 事件）、
  `onResponse`（改整体响应）。
- 限制：250ms/请求钩子与 onProvider、50ms/事件、1s 加载；失败开放；请求级 runtime 池。
- 实测：约 1–1.6 µs/事件，0.2–0.7 ms/次 80KB 体的 `onRequest`（`docs/subsystems/gateway-middleware.md:52`）。
- 另有 `strategies`（20ms）与 `onUsage`（250ms，队列 1024，**满了丢弃并计数，请求永不等待**）。

**异步 Bun 钩子**（`internal/plugin/gateway.go`）：
`onRequest(body, ctx)` 补上下文，**抛错/超时/非法/改了 tool 声明、`model`、`stream` 一律回滚**；
`onResponse` 事后尽力通知，不阻塞客户端 EOF。
`origin` 由宿主判定（`local` / `gateway-key` / `remote`），**不暴露 key、对端地址、客户端自称的来源**。

## 三、llm-gateway-go 现状

### 3.1 请求路径

**HTTP 中间件链**（`cmd/gateway/main.go:7724-7740`，外向内）：

```
Recovery → RequestID → Logging → Locale(i18n) → CORS → Prometheus → Tracing
        → Auth → Origin(trusted proxies) → SecurityHeaders → publicSurface(maintain/mobile) → mux
```

两处顺序是踩坑后改的，有注释自陈：Logging 必须在 Auth **之外**（否则 401 不落日志，
客户端拿 `X-Request-Id` 去查命中 0 次）；maintain/mobile 必须**组合在链内**（否则运维面不带安全响应头）。

**数据面有两套路径**：

| 路径 | 开关 | 说明 |
|---|---|---|
| v1（生产默认） | 无 | 4 个入口 `/v1/chat/completions`、`/v1/messages`、`/v1/responses` 直派 `relay.{ChatHandler,MessagesHandler,ResponsesHandler}`；前飞（auth/key 校验/model policy）与后飞（telemetry/request WAL/audit）**全部 inline**（`cmd/gateway/main_pipeline.go:1-80`） |
| v2 Hook Pipeline | `LLM_GATEWAY_USE_V2_PIPELINE`（或 legacy `LLM_GATEWAY_V2_ENABLED`），**默认关** | 同样 4 个入口被 `v2DispatchHandler` 包一层，先跑 preflight Pipeline（tracing/security/audit），再落到 v1 handler，最后 postflight（metrics/cache_save/audit）。**开关启动时读一次，改要重启**（`main_pipeline.go:160-168`、`:1112`） |

### 3.2 路由 / 熔断 / 重试

### 3.5 扩展机制全景 ★（**这是本仓最大的结构性问题**）

| # | 机制 | 位置 | 生产状态 | 阶段词表 |
|---|---|---|---|---|
| 1 | HTTP 中间件链 | `middleware/` | **活**（启动时静态构建） | 无阶段，线性链 |
| 2 | Hook Registry | `domains/hooks/` | **死**：`NewHookRegistry` 只在 `domains/hooks/registry.go:34` 定义，**全仓无生产调用方**；`registry.Execute` 在包外零调用 | 5 阶段：`pre_routing/routing/pre_upstream/post_upstream/post_response` |
| 3 | Request Pipeline | `domains/pipeline/` | **关**（`LLM_GATEWAY_USE_V2_PIPELINE` 默认 false） | 15 阶段：含 `governance`/`transform`/`response` |
| 4 | 执行器生命周期钩子 | `domains/streaming/executors/executor_chat.go:60-90` `ExecuteHooks` / `WithStreamContinuation` | **活**（直调，非注册表） | 无 |
| 5 | 响应拦截链 | `domains/hooks/response/`、`domains/streaming/native_response_intercept.go` | **活**（Go 类型，body 级改/拦） | 无 |

**另外**：`domains/interception/` + `domain/governance/` 提供决策引擎
（continue/block/mutate/suspend/terminate）+ dispatch gate + 审批创建器，挂在 v2 的 `PhaseGovernance`。

**结论**：一个请求面上并存 **5 套扩展机制**，其中 2 套（Registry、Pipeline）在生产里分别是**死的**和**关着的**。
`domains/hooks` 自述"提供统一的插件化架构，所有企业功能都可以通过 Hook 形式动态加载"，
但它的注册表从未被构造——**这是一处"框架在、链路不通"**，
和 v5 里 `smartretry`（生产零引用）是同一种形态，只是这次更隐蔽（因为它有完整的 README、99% 覆盖率声明和 Prometheus 指标）。

### 3.6 plugin-runtime 专章 ★

**是什么**：本仓的插件是**独立进程**（unix socket），由网关**安装、监管、授权、反向代理**。

| 部件 | 能力 | 证据 |
|---|---|---|
| Installer | catalog → ticket → 下载 → 解包（防目录逃逸与符号链接逃逸）→ manifest ed25519 验签 → 原子切换 | `plugin-runtime/installer.go`、`manifest_verify.go`、`extractor.go` |
| Supervisor + HealthLoop | 精确健康检查（不只看 socket 在不在，还看是否 200）→ 降级 → 自动重启（带退避、次数上限） | `plugin-runtime/health_check.go`、`health_loop.go`、`supervisor.go` |
| 能力注册表 | 路径前缀 → 必需能力；manifest 声明的能力是白名单，未声明即拒 | `plugin-runtime/capability.go` |
| 沙箱策略 | deny-by-default：非独立 OS 用户 / 无内存上限 ⇒ 不可信；敏感环境变量一律剥离 | `plugin-runtime/sandbox_policy.go` |
| 权益闸 | 按租户查模块授权，未授权 403 | `plugin-runtime/entitlement_client.go`、`cmd/gateway/plugin_apiproxy_init.go` |
| API 反代 | 网关 → 插件：unix socket，注入 HMAC 签名上下文（pluginID/tenant/ts/nonce） | `plugin-runtime/apiproxy.go`、`context_token.go` |

**两处硬缺口**：

1. **数据面能力已声明但被自我否决。**
   `plugin-runtime/types.go:67-78` 已定义 `request.mutate`、`request.block`、`response.mutate`、
   `response.block`、`tool.mutate`、`tool.block`、`tool.execute`；
   而 `plugin-runtime/sandbox.go:11-17` 自陈"**data-plane write capability (mutate/block/tool.execute)
   is refused until a real sandbox is available**"，且 `DefaultSandboxPolicy().Available = false`
   （`sandbox_policy.go:48-59`）。
   ⇒ **能力词表已经想清楚了，执行被策略挡住**。这是好消息：接口没白设计，只差一个真沙箱。

2. **5 条 capability 路由只挂了 2 条。**
   `capability.go:19-23` 声明 `sessions` / `analytics` / `bodies` / `interception-policies` / `events`；
   `cmd/gateway/plugin_canon_init.go:201-204` 只注册了 `sessions`（3 条）与 `analytics`（1 条）。
   `bodies`、`interception-policies`、`events` **在全仓找不到 handler**。
   ⇒ 「插件下发拦截策略」「插件抓取请求体」「插件投递事件」这三件事，
   **在能力表里存在，在运行时不存在**。

**所以：本仓插件当前是"数据面消费方 + API 扩展方"，不是"请求面拦截方"。**
网关把请求**转给**插件的 API（`/plugins/{pluginId}/api/...`），但没有任何第三方代码能改一个在途请求。

**另**：全仓**没有脚本引擎**（无 goja / otto / lua / wazero / starlark）——
⇒ 第三方代码目前**无法**用脚本改写在途请求。

## 五、插件专题：magpie 五个点 vs 本仓

### 5.1 契约差异表

| 维度 | magpie | 本仓现状 | 可否直接搬 |
|---|---|---|---|
| 进程内 | JS 引擎 moejs（Go 写）跑在网关进程内 | 无脚本引擎 | **需引入依赖 + 合规评审** |
| 失败策略 | 逐点声明（开放/关闭/永不失败） | 由每个 hook 自行实现 `OnError`，无集中策略表 | **可搬（纯 Go，纯设计）** |
| 超时 | 逐点声明（20/50/250ms） | pipeline 无统一超时 | 可搬 |
| 权限面 | 中间件只见 agent 的体与模型，**见不到凭据** | `DTOProfile` 已有 none/summary/redacted 三档 | 本仓更强 |
| 插件进程 | Bun，独立，有完整 Bun API | 独立进程 + 沙箱策略 + 验签 + 权益 | 本仓更强 |
| 第三方改请求 | 可以（进程内） | 不可以 | **这是唯一的范式差** |
| 观察者 | 字段级 allow-list、队列满丢弃计数 | 无统一接口 | 可搬 |

### 5.2 唯一真正的范式差：`onProvider`

magpie 的 `Run.Tried(body, to)` **按每次上游尝试改请求体**——
"这一次试 DeepSeek 就换成 DeepSeek 的体，这一次试 Kimi 就换"。这解决了一个真实问题：
不同 provider 的方言/能力不同，且**每次尝试的上下文不同**（模型名、思考预算、缓存指令）。

进程外插件**做不到**这件事（插件拿不到在途请求的改写权，除非做进程内 hook）。
⇒ 若本仓将来要支持"按 provider 改写"，只有两条路：
**(a) 进程内脚本引擎**（moejs/goja 类），**(b) 把"按 provider 的改写"下沉为 Go 侧的**类型化**改写点**（不是脚本）。

**建议走 (b)**：本仓已有 `domains/streaming` 的 body 级改写能力（ResponseInterceptor），
把它从"响应侧"扩到"按候选改写"是**类型化**的、可测的、可门禁的；
而引入脚本引擎是**合规面**的事（v5 明确"不建议照搬 JS 中置件"，该判断至今没有被推翻，
只是需要在新证据下复核——见 §5.4）。

### 5.3 本仓的三个硬缺口（按修复价值排序）

1. **扩展点没收敛**（D1）：5 套机制、2 套死/关。**先收敛，再谈插件。**
2. **声明与实现不同源**（D7 + §3.6 两处硬缺口）：能力词表有 6 个数据面能力，
   执行被沙箱策略全拒；5 条 capability 路由只挂 2 条。
   ⇒ 这两处是**"表里有、运行时没有"**，与本仓 LESSONS 的"同一口径两处实现"同族。
3. **缺"关掉后"的可验证语义**（D8）：magpie 每个点都有 on/off 对照测试，
   "关掉 ⇒ 请求原样发出"是被断言出来的，不是被相信的。

### 5.4 对 v5"不建议照搬 JS 中置件"的复核

v5 的原话：「JS 中置件（合规与 S4 路线已定）」。复核结论：
**该判断的依据没有失效**（本仓 S4 改造矩阵承担改写职能，脚本会引入第二套改写机制），
但**理由需要更新**：

- magpie 现在的 JS 中置件是**社区插件生态**的载体（6 个现成包：param-override / model-map /
  system-prompt / word-guard / think-tags / antigravity-cloak）。
  本仓的等价需求（按 provider 改体、按模型改参数、词表护栏）**目前分散在多个 Go 包里**。
- ⇒ 真正的取舍不是"JS vs Go"，而是"**一个统一的、按点声明的改写契约**"，
  用 Go 类型实现（路径 (b)）还是用脚本实现（路径 (a)）。
- **建议**：先做 (b) 的**契约**（§6-P1-2 的 Strategy、§6-P1-4 的 RewritePoint），
  把"改写点"这件事的语义、超时、失败策略定死；**脚本引擎作为实现选项留到 P3**，
  且**必须**在 S4 改造矩阵收敛之后。

|---|---|---|---|
| **P1-1** | **统一请求级观察者** | 抽 `domain.Observer`：`Begin/Watch/Attempt/End` + 字段级 allow-list + **有界队列、满则丢弃并计数、请求永不等待**（照 magpie `usage.Observer` 的 `Bodies` 三档与 `onUsage` 队列语义）。挂到 v1 真实路径（不是 v2） | ① 观察者**永不影响请求结果**的断言；② 队列满时**丢弃计数增加且请求不阻塞**的断言；③ 观察者关闭 ⇒ 无观测、无开销 |
| **P1-2** | **策略只排序的契约** | 抽 `Strategy`：`Order(pool string, seats []Seat) []int`，**只排序**，不碰 rest/亲和/规则/pin；`Seat` 至少含 Key/Account/Known/Used/Soon/Pace/Weight/Resting/Tokens。失败开放（panic/超时/非排列 ⇒ 原顺序），**每条路线仍会被试**。把现有 weighted/quality/autoroute 策略**适配**成它（不新建第二套） | ① 非排列返回 ⇒ 原顺序（红测）；② panic ⇒ 原顺序；③ 超时（建议 20ms）⇒ 原顺序；④ 现有策略迁移前后**候选集合与顺序一致**的对拍 |
| **P1-3** | **预算的预约-释放语义** | 先读本仓 key 级限额现状（billguard / ratelimit / governor），再决定是否引入"先预留、结束释放"。**本项先出结论再出码**，禁止直接照搬 | ① 现状读数（谁在扣、什么时候扣、失败退不退）；② 若引入：预留—释放—拒绝三态的断言，含并发双花 |
| **P1-4** | **按候选改写的类型化契约** | 把 §5.2 的 (b) 路径定成接口：`RewritePoint{Point, Provider, Model}` + 失败策略 + 超时 + **只允许改目标字段**（字节保真） | ① 改写只动目标字段的原字节对拍；② 改写失败 ⇒ 原样发出；③ 同一请求不同候选互不污染 |
| **P1-5** | **失败策略表** | 给每个 phase/点写死"失败是终止还是继续"，写进文档并落进门禁（`domains/pipeline` 的 `OnError` 目前是逐 hook 自实现，无集中表） | ① 策略表与实现同源的门禁；② 变异的"关键 phase 的 hook 失败被吞"必须红 |
