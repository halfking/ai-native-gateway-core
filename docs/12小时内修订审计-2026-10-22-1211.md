- **证据（本机 macOS arm64 / bash 3.2.57）**：

    ⇒ `_llmgw_run_bounded` **必然**走纯 bash 回退分支（`"$@" &` + `set -m` + 轮询 `kill -0`）；
  - 挂死时的进程画像：`ursmcheck.test` 运行 **18 分 36 秒**、**只用了 39.61s CPU**
    ⇒ 不是在算，是在**等**；且 Go 测试的 `-timeout=900s`（15min）**没有把它打断**；
  - 被反复 spawn 的子进程 `/bin/bash ../252-monitor/pg17-disk-watch.sh`：
    **ELAPSED 10s / TIME 0:00.01 / 无任何子进程** ⇒ 阻塞在 bash **内建**里；
  - `sample <pid> 3` 的调用栈：**`read (in libsystem_kernel.dylib)`** 是最深的叶帧
    ⇒ bash 阻塞在一次 **`read` 系统调用**上；
  - 子进程 PID 每隔几秒就变（84727 → 86217 → …）⇒ 门在**反复**拉起该脚本；
  - 采样期间抓到一个**长寿看门狗**：`sleep 570`（= 9.5 分钟）在脚本的直接子进程
    早已退出后**仍然存活** ⇒ 它**持有命令替换管道的写端**
    ⇒ 读端（bash 的 `read`）**永远等不到 EOF**。
- **机制（为什么拿不到 EOF）**：`de()` 写成 `out=$(_llmgw_run_bounded … …)`，
  即用**命令替换**捕获输出 ⇒ bash 必须在管道上读到 **EOF** 才继续。
  回退分支里 `"$@" &` 把命令放进**后台作业**（`set -m` 让它自成进程组），
  它的 stdout 继承了那条管道的**写端**；
  ⇒ **只要该进程组里还有任何一个进程活着**（脚本自己的注释就写着
  「`kill -9 <子进程>` 之后，`bash -c 'sleep 60; …'` 里那条 sleep **会活下来**」），
  **写端就不会关闭** ⇒ 读端永远等不到 EOF ⇒ **命令替换无限期阻塞**。
  ⇒ 观测到的 `sleep 570` 正是这样一个**长寿看门狗**（它的存活期比直接子进程长得多）。
- **为什么是真缺陷（且是仓里的老账）**：
  ① 「超时这道闸若自己漏进程，就等于把 2026-10-10 事故原样复现一遍」——
     这条注释说的是**超时**；而在**没有 `timeout` 的机器上**，这段回退连
