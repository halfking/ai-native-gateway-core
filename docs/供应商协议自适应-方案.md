# 供应商协议「自适应」— 分析、方案与实施规划

> 状态：**方案稿（待审计确认后实施）**。本文不含任何代码改动，零生产写、零 schema 变更、零在役切换。
> 取证环境：本仓 `main` @ `227fece285`；生产只读勘察 llm.itestu.cn（供应商 36）。
> 写作纪律：每条断言标注 **【事实】**（有代码/接口证据）、**【推断】**（由事实演绎但未实证）、**【不确定】**（未验证，需实施前确认）。

---

## 一、需求

供应商 36（vapeur）下挂 474 个模型，横跨 8 家厂商，但供应商只有一个 `protocol` 字段，所有模型共用同一线格式（wire format）与上家通讯。需求是：在供应商设置的「协议」下拉里增加一个 **自适应** 选项，选中后按**请求模型**解析其**原厂推荐协议**，并用该协议与上游通讯。

即：把「一个供应商一种线格式」升级为「一个供应商，按模型各用其原厂线格式」。

---

## 二、现状事实盘点

### 2.1 生产供应商 36 的实际形态【事实】

| 项 | 值 |
|---|---|
| code | `vapeur` |
| display_name | `Vapeur AI (OpenAI兼容)` |
| base_url | `https://api.vapeur.ai/v1` |
| **protocol** | **`openai-responses`** |
| category | `third_party_relay`（第三方聚合中转） |
| 凭据 | 3 个（`vapi-new` / `hxt-20261126` / `hxt-20261128`），其中 `vapi-new` status=disabled |
| 模型 | **474 行**，覆盖 claude-* / gpt-* / o3 / o4-mini / gemini 系 / deepseek-v4* / qwen3.x-4 / doubao-seed-* / grok-4.x / kimi-k2.x-k3 / MiniMax-M2.5 / 大量图像视频模型 |

**这一条决定了整个方案的基调**：vapeur 是**聚合中转**，不是原厂。它的 474 个模型全部通过同一组 base_url 暴露。**【推断】** 它对绝大多数模型只提供 OpenAI 兼容入口（`/v1/chat/completions` 与 `/v1/responses`），未必为 claude-* 提供 `/v1/messages`、为 gemini-* 提供 `generateContent`。这条推断的验证方式见 §5。

### 2.2 协议 SSOT 已存在，且已有一个「零调用点」的推荐函数【事实】

`provider/catalog/protocol_normalize.go` 提供三个入口：

| 函数 | 作用 | 生产调用点 |
|---|---|---|
| `NormalizeProviderProtocol(raw)` | 别名归一 → 五值枚举，未知值返回 error | **12 处**（admin/discovery/bg/provider 各层） |
| `RecommendedProtocolForModel(model)` | 按模型名推荐协议 | **0 处（死代码）** |
| `RecommendedProtocolForBaseURL(baseURL)` | 按官方域名推荐协议 | 1 处（`admin/providers.go:905` 创建供应商兜底） |

`RecommendedProtocolForModel` 的规则（`docs/vendor-formats/` 为依据）：

```
gpt-5* / codex* / o1|o3|o4 系列  → openai-responses
claude*                          → anthropic-messages
gemini*                          → gemini-generate
其余（deepseek/qwen/kimi/grok…）  → openai-completions（ok=false）
```

它的注释里已经写下了本方案最重要的一条约束【事实，原文】：

> 推荐值只作为「未显式配置时的默认」；运行时是否走原生 Responses 传输仍由凭据的 `SupportsNativeResponses` 能力闸门决定——**第三方中转的 gpt-5 大多只暴露 /chat/completions，不能凭模型名强行切换线格式**。

也就是说：**需求要的机制，仓里九个月前就写好了判定体，但从来没有接线。**这正好是本仓纪律「写了判定体 ≠ 门在承重」的又一例。

### 2.3 `cand.Protocol` 是全链路唯一的线格式维度【事实】

候选加载出口之后，所有执行器、响应解析、用量证据、缓存口径都以 `cand.Protocol` 为准：

| 消费点 | 位置 | 作用 |
|---|---|---|
| 分发路由 | `executor_dispatch.go:1170 classifyDispatchRoute(cand.Protocol, flags)` | anthropic / ollama / gemini / 其余走 OpenAI |
| 请求体转换 | `executor_anthropic.go:482 prepareAnthropicRequestBody` | OpenAI 体 → Anthropic 体（IR 转换器，自带 legacy 回落） |
| 同上 | `executor_gemini.go:1418` | OpenAI 体 → Gemini 体（`ir.ParseOpenAI` → `ir.SerializeGemini`） |
| Responses 闸门 | `executor_chat.go:902-1011` | `cand.Protocol == openai-responses && SupportsNativeResponses && 有 ResponsesBodyBytes` |
| 出站 URL | `upstreamurl.MessagesURL / ChatCompletionsURL / GenerateContentURL` | 按协议选路径 |
| 用量/缓存/诊断 | `reconciliation.ParseUsageEvidence(…, cand.Protocol)`、`CacheTokenConventionForProtocol`、`diagnosticProtocol` | 口径随协议 |

**【事实】由此得出一条关键结论：请求体转换是内建的，翻协议不需要另写转换器。**
**【事实】也因此得到单一插入点：只要在「候选加载出口」把 `cand.Protocol` 解析成具体协议，下游 20+ 处读取点全部自动继承，一处都不用改。**

### 2.4 候选加载出口有两处，都是归一函数的调用点【事实】

- `provider/client.go:2364` — `loadCandidatesByModalityDB`（主路径，模态候选）
- `provider/client.go:1332` — `getCandidates`（另一条候选查询）

两处结构相同：`SELECT p.protocol` → `NormalizeProviderProtocol` 归一，未知值保持原样交给执行器 default 分支。

### 2.5 「多协议端点」机制已存在，但生产不可用【事实】

`provider_endpoint_protocols` 表（迁移 `800_`）就是为「一个供应商 N 种协议」设计的：

- 列：`(provider_id, protocol)` UNIQUE、独立的 `base_url`、`is_primary`、`vendor_native`（发现侧 family 串）、`weight`、健康列
- 消费方：`internal/endpointselect/selector.go` 的四阶段 `Select(cand, wantProtocol, wantFamily)`
- 闸门：`settings/p4_feature_flags.go:62` `FF_ENDPOINT_SELECTOR` **默认 false**
- **缺口**：`grep provider_endpoint_protocols admin/*.go` 只命中数据生命周期表名 ⇒ **没有任何 admin API，也没有任何 UI CRUD**。运营只能靠 SQL 建行。设计文档 `供应商协议优化-实施规划.md §12.2` 自陈「admin UI endpoint CRUD + SettingsTab 卡片」仍是 P1 待办。

**【事实】结论：这张表不能作为「自适应」的唯一依赖——它今天在生产上填不进去。**

### 2.6 能力表只覆盖 Responses 一种能力【事实】

`credential_model_capabilities` 的 CHECK 约束把 `capability` 限定为单一值 `native_responses_nonstream`。**没有按协议维度的通用能力位。** 若要按协议存证据，需扩 CHECK（schema 变更）。

### 2.7 既有「线格式切换失败即回落」的成熟模式【事实】

`executor_chat.go:2116-2197` 有一段完整的「模式回退」实现，注释里直接点名了生产案例：

> 此前该方向完全没有降级…于是 **vapEUR 上 gpt-5.3-codex 的 chat 腿 400（code 4006 "The requested operation is unsupported."）必然 503**，而探针走 responses 腿拿到 200，节点还被判为健康。

它的守门条件是三合一：`cand.Protocol == openai-responses` **且** `chatRequiresResponses(状态码, 错误体)` **且** 每请求至多一次。触发后返回 `retryableError` + `meterExtraUpstreamCall` 补记配额。

**【事实】这段就是「自适应」失败回落可以直接复用的骨架，不必新造。**

### 2.8 探针侧直接读 `p.protocol`，绕过候选加载【事实】

`bg/node_probe.go:3695` 有 `AND pep.protocol = COALESCE(p.protocol, 'openai-completions')`；`bg/model_probe.go:1028,1532` 用 `desc.Protocol == "anthropic-messages"` 布尔判断。两者都不经过候选加载出口。

**【事实】若 `p.protocol` 存成 `adaptive`：**
- `pep.protocol = 'adaptive'` 匹配不到任何行 → 回落 `p.base_url`（安全降级）
- 探针协议判断落 `else` → 按 OpenAI chat 探测（安全降级）

**【推断，但极重要】安全降级 ≠ 正确**：这正是 §2.7 那个 vapEUR 事故的同型复现——探针走 chat 腿、真实流量走推荐腿，两者分叉，节点健康判定会失真。**所以探针必须一并解析自适应，否则会把「配置正确但探针走错腿」变成新的误判源。**

**【实施状态 2026-11-28】模型级探针已接线**（`bg/adaptive_probe_protocol.go`）：五个带模型上下文的入口——`model_probe.go` 的 featured cycle Layer 4 / `probeModel` / `verifyTargetModality`，以及 `active_probe_executor.go` 的 `Run` / `runModelsList`——统一先经 `resolveProbeProtocol(ctx, db, providerID, protocol, rawModel)` 消解，判定体与数据面是同一个纯函数 `catalog.ResolveAdaptiveProtocol`。声明值按 provider 缓存 60s（`adaptiveProbeCacheTTL`），负结果同样缓存，避免逐 (credential, model) 探测打穿一条两行的表。

**剩余边界（如实登记，未接线）**：
- ~~`node_probe.go:3695/3741` 的 `AND pep.protocol = COALESCE(p.protocol, 'openai-completions')` —— 自适应下匹配不到任何 `provider_endpoint_protocols` 行 ⇒ 回落 `p.base_url`。~~ **【已收口 §13.6】** 两条 SQL 与其逐字钉住的判据**原样不动**，改在 `resolveDirectTarget` 返回前消解（`alignAdaptiveDirectTarget`）。
- 无模型上下文的探针（`credential_probe_v2.go`、`modality_semantic_probe.go`、`balance_floor_guard.go`、`capability_backfill.go`、`model_credibility_source.go`）仍按 chat 默认口径探测——它们本来就没有「按模型」这个维度，基协议 = `openai-completions` 与现状等价；等到需要「基协议 ≠ completions」的自适应供应商时再接线。

### 2.9 前端现状：下拉硬编码 5 项，且有一对重复值【事实】

`web/src/views/provider-detail/SettingsTab.vue:314-320`：

```html

<option value="openai-responses">OpenAI Responses</option>
```

协议随 `save()`（`:178`）经 `updateProvider` 一起提交。

### 2.10 `providers.protocol` 列无 CHECK 约束【事实】

`sql/objects/tables/providers.sql:16`：`protocol text NOT NULL`。⇒ **存 `adaptive` 在 DB 层完全合法，零迁移。**

### 2.11 「供应商级键值设置」通道是**封闭枚举**，不是通用 KV【事实】

`provider_settings` 表 + `PUT /api/providers/{id}/settings/{key}`（`admin/provider_settings.go:120`）看似通用 KV，实际写入口有**硬编码白名单**：

```go
allowedKeys := map[string]bool{
    "compression.mode":          true,
    "cache.enabled":             true,
    "format_conversion.enabled": true,
}
if !allowedKeys[settingKey] { → 400 invalid setting key }
```

前端覆写区同样只认这三个键（`SettingsTab.vue:83-142`）。

**【事实】结论：任何新设置的 `provider_settings` 键都要同时改后端白名单 + 值校验器 + 前端覆写区 + 8 语种，不是「通道现成可直接写」。** 这条直接削弱了 §6 方案 C 的「零风险」优势——它是把成本从「改读取点」换成了「改写入侧白名单 + UI」，并非真的免费。

## 四、核心结论：单一插入点

**自适应不是一种新协议，而是一种「协议选择策略」。**它必须在对的时间被消解成具体协议，且消解点只能是候选加载出口。

```
providers.protocol = 'adaptive'
        │
        ├─ 候选加载出口（provider/client.go 两处）
        │     cand.Protocol = ResolveAdaptive(cand.RawModel)   ← 唯一消解点
        │
        └─ 之后：分发型、请求体转换、出站 URL、响应解析、用量证据
                 全部照旧读 cand.Protocol（零改动）
```

由此得到三条落地判据：

1. **下游 20+ 处 `cand.Protocol` 读取点无需改动** —— 它们读到的已经是具体协议。
2. **请求体不用新写转换器** —— `prepareAnthropicRequestBody` / gemini 的 `ir.ParseOpenAI→SerializeGemini` 已内建。
3. **消解失败必须给出确定值** —— 不能把 `adaptive` 漏给执行器（会落 default 分支按 chat 处理，行为与配置不符，正是 §2.1 注释里点名的 `"openai-response"` 旧事故同型）。

## 五、最关键风险：上游是否真的支持推荐协议

**【推断】** vapeur 这类聚合中转，对 claude-* 大概率只提供 OpenAI 兼容入口。若直接按模型名把 `claude-*` 切到 `anthropic-messages`，出站会打 `https://api.vapeur.ai/v1/messages`，若该路径不存在则 404。

**【事实】** `admin/providers.go` 的注释与 `protocol_normalize.go:105-107` 的注释都独立地写下了同一条警告。也就是说，**这个坑在九个月前就被预见到了，但从未被工程化处理。**

### 5.1 可用的「支持性」证据源盘点

| 证据源 | 覆盖 | 生产可用性 |
|---|---|---|
| `SupportsNativeResponses`（凭据能力闸门） | **仅 openai-responses** | ✅ 可用，已有回落 |
| `provider_endpoint_protocols` 行 | 5 种协议 | ❌ 无 CRUD，运营填不进去 |
| `credential_model_capabilities` | 仅 `native_responses_nonstream` | ⚠ 扩需改 CHECK |
| Redis FpSlots / 节点态 | 与协议无关 | ❌ |
| **实证首请求 + 负向记忆** | 5 种协议 | ✅ 无需前置配置 |
| 主动探测（发一次真请求） | 5 种协议 | ⚠ 消耗上游额度 |

### 5.2 推荐的支持性模型：三段闸门

```
闸门 1（声明层）  该协议的端点是否被声明可用？
        ├─ openai-responses：不需要声明 —— 有 SupportsNativeResponses 独立兜底
        └─ 其余：需要 provider_settings['protocol.adaptive.allowed'] 列出，或扩展表有行
                 若一项都没声明 ⇒ 自适应退化为「显式基协议」= 今天的行为，零风险

闸门 2（实证层）  首请求按推荐协议发；失败按 §2.7 同款条件（状态码 + 错误体形状）判定
                 为「该协议不被支持」⇒ 负向记忆（provider, model, protocol，带 TTL）
                 ⇒ 同请求当场用基协议重试一次（复用 retryableError 骨架）

闸门 3（探针层）  探针同样解析自适应，并优先探「声明可用」的那条腿
                 避免 §2.7 那个「探针走 chat、流量走 responses」的分叉
```

**关键性质**：闸门 1 未配置时，整条链路行为**逐字节等于今天**。这是「不会把现在能跑的模型打挂」的形式化保证。

## 六、落库形态对比（Q1）

| 方案 | 形态 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A** | `providers.protocol = 'adaptive'`，无回退列 | 完全贴合用户原话（就在下拉里）；零迁移（列无 CHECK）；单一真相 | 丢失「基协议」显式语义；探针/发现会拿到 `adaptive`（§2.8，安全降级但需另处理） |
| **B** | A + 新列 `protocol_fallback` | 基协议显式可配 | schema 变更（新增列，走全套投递）；UI 要多一个「回退协议」下拉，认知负担 |
| **C** | `providers.protocol` 保持具体值 + `provider_settings['protocol.adaptive']='true'` | 对既有读取点零风险 | **不在「协议」下拉里** —— 不满足用户原话；且 §2.11 已证实该通道是三键封闭枚举，「通道现成」的优势不成立 |

### 推荐：**A + provider_settings 承载「声明可用协议」**

理由：
1. 用户在「协议」下拉里选到「自适应」是本需求的**原始诉求**，B/C 都要在这一条上打折。
2. 列无 CHECK ⇒ 零迁移、零 schema 变更（符合本轮纪律）。
3. 基协议不需要新列：**默认基协议恒为 `openai-completions`**（这是全仓 12 处 `COALESCE(p.protocol,'openai-completions')` 已经确立的既有默认，不是我们新发明的）。真要覆盖，用 `provider_settings['protocol.adaptive.base']`，属可选增强，不进 P0。
4. 「哪些协议真能用」用 `provider_settings['protocol.adaptive.allowed']`（CSV）承载 —— **但需先扩 §2.11 那个三键白名单**（后端 `allowedKeys` + `validateSettingValue` + 前端覆写区 + 8 语种）。这笔成本是真实的，不是零。在 `provider_endpoint_protocols` 补上 CRUD 之后，该键作为其降级替身可以退役。

**【事实，已消解】** 原「`setting_key` 是否有白名单」的疑问：**有，且是三键硬编码**（§2.11）。⇒ 闸门 1 若走 `provider_settings`，P0 必须包含「扩白名单」这一项。

### 6.1 若不想动 `provider_settings` 白名单：闸门 1 的替代形态

| 形态 | 成本 | 评价 |
|---|---|---|
| **a. 不做闸门 1，只靠闸门 2（负向学习）** | 最低 | 每个 (模型, 协议) 组合首次撞一次 404，之后自愈。**代价：用户会看到零星失败请求**；流式客户端可能直接报错一次 |
| **b. 用 `provider_endpoint_protocols` 行作声明** | 中（需 SQL 建行，无 CRUD） | 语义最正，但运营今天填不进去 ⇒ 事实上等于「不做」 |
| **c. 扩 `provider_settings` 白名单** | 中（后端 + 前端 + 8 语种） | 可控、可回滚、有 UI；**推荐** |
| **d. 新列 `providers.protocol_allowed`** | 高（schema 变更，五点投递） | 违反本轮「零 schema」纪律，P1 |

**推荐 c**，但 c 与 a 的取舍应由需求方拍板（见 §11 待决项）。

### 13.7 A4 交付轮：`provider_endpoint_protocols` 的 admin CRUD（后端，不动 schema）

**缺口**（§7 A4）：这张表此前**没有任何 admin 入口**——运营只能连库写 SQL 才能声明端点，`protocol.adaptive.allowed` 只是过渡替身。后果是可运营性为零：端点行的 `base_url`/`weight`/`is_primary` 变更没有审计、没有校验、极易写出违反 `provider_endpoint_protocols_one_primary` 部分唯一索引的行。

**交付面（零 schema 变更／零 DDL）**：新文件 `admin/provider_endpoints.go`，挂进既有 `/api/providers/{id}/` 前缀分发（**不新增 mux 注册**，`admin/providers.go` 两处接线：`case "endpoints"` + `strings.HasPrefix(subPath, "endpoints/")`）。

| 方法 | 路径 | 语义 |
|---|---|---|
| GET | `/api/providers/{id}/endpoints` | 列出该供应商全部协议端点（**含停用行**），`ORDER BY is_primary DESC, weight DESC, id ASC` |
| PUT | `/api/providers/{id}/endpoints/{protocol}` | 按 `(provider_id, protocol)` upsert；**201=新建、200=更新**；未给出的字段保持原值（`COALESCE` / `CASE WHEN $n` 部分更新） |
| DELETE | `/api/providers/{id}/endpoints/{protocol}` | 删一行；主端点拒删 |

**写入约束（为什么这样收敛）**：

- **`adaptive` 在端点行被拒绝**（400）。端点行描述「上游真实提供的具体线格式」，选择器不是线格式——把它写成端点行的 `protocol` 会让协议与传输错配。协议先过 `NormalizeProviderProtocol` 别名归一，再校验落在表 CHECK 的五值（`providerEndpointProtocols`），单测 `TestProviderEndpointProtocolsMatchTableCheck` 与 `sql/objects/tables/provider_endpoint_protocols.sql` 的 CHECK 逐字对拍。
- **主端点保护取「先提升再降级」，不做「零主端点」**：置 `is_primary=true` 时在同一事务里先 `UPDATE ... SET is_primary=false WHERE provider_id=$1 AND is_primary=true AND protocol<>$2` 摘旧主，再落新行（避开 23505）；反之**拒绝把当前主端点直接降级/停用/删除**（409 `promote another endpoint first`）——选择器 Stage 4 的回落语义依赖有主端点。
- **`base_url`** 必须是带主机的 http(s)；`kind=local` 的供应商复用 `validateLocalBaseURL` 的回环/私网约束，与 `providers.base_url` 同口径。
- **`weight` 1..999**（对齐表约束）、`notes` ≤500；`vendor_native`/`notes` 传空串落 NULL。
- 写后 `provider.InvalidateAllCandidateCache()`：候选载入会把该表聚合成每个候选的 `endpoints` JSONB（`provider/client.go:2045`），不失效就要等缓存 TTL 才生效。

**并发诚实点（本轮补的守卫）**：DELETE 的「读 `is_primary`」与「`DELETE ... AND is_primary = false`」之间没有事务边界，并发 PUT 可能已把该行提升为主端点 ⇒ 语句命中 0 行。原实现报 200「endpoint deleted」——**删了没删都是 200**，比显式冲突更危险。现按 `RowsAffected()==0` 报 409。

**判据**：`admin/provider_endpoints_test.go` 12 个顶层测试（细分子用例 20+）——创建 201／更新 200 且部分更新不动未给字段／提升主端点时先摘旧主／拒绝降级与停用主端点（两条 409）／拒绝 `adaptive`·未知协议·`weight` 0 与 1000·`notes` 501·非 JSON（并断言**零 SQL**）／`base_url` 四种坏形态／供应商不存在 404／DELETE 三分支（可删·主端点 409·不存在 404·**并发提升命中 0 行 409**）／LIST 顺序与字段／非 `super_admin`·`admin_key` 403／协议集合对拍表 CHECK／接线锚点（分发器调用点 ≥2、写路径失效缓存 ≥2）。

**真库实证**（一次性 `postgres:15-alpine` 容器，跑完即 stop，`docker ps -a` 计数 0；临时测试文件用后删除）：7 步全绿——201 建档 → 201 建非主 → 200 部分更新（`weight=70` 生效、`base_url`/`vendor_native` 保留）→ 200 提升为主（旧主自动降级）→ 200 旧主可改 `is_primary:false` → 200 `notes:""` 清成 `null` → 409 拒绝降级主端点；LIST 顺序正确；DELETE 主端点 409、DELETE 旧主 200。

**影响面（如实，写进代码头注释）**：写这张表**今天就会影响探针**——`bg/node_probe.go` 的 `resolveDirectTarget` 无视 `FF_ENDPOINT_SELECTOR` 直接按协议匹配行取 `base_url`（§13.6 已让它在自适应下按消解后协议匹配）；路由侧则要 `FF_ENDPOINT_SELECTOR=true` 才消费（默认 false，A6 未接线）。

**诚实边界**：① **管理面 API-only**——admin 前端 SettingsTab 卡片已在 §13.8 交付。② LIST 对不存在的供应商返回空列表 200（不校验供应商存在性），PUT 则 404——两者不一致是有意的（列表天然可空），运维若需「供应商存在性」请走 `GET /api/providers/{id}`。③ 路由快照 `admin-routes.txt` 按「路由+方法」计，本轮新增子路径会在下一轮门读数里体现，需同步口径头。

**门读数**：`go build ./...` EXIT=0；`go vet ./admin/` EXIT=0；`go test ./admin/ -count=1` **ok 85.1s**（改动前基线同量级，无回归）。**负控实测能红**：摘掉 `RowsAffected()==0` 守卫 ⇒ `TestProviderEndpointDelete/并发提升后命中_0_行必须报冲突而非成功` FAIL（`want 409, got 200`），恢复 ⇒ PASS。

> ★ 通用式：**「删了没删都报 200」是写路径最隐蔽的一类谎**——读-判-写跨了事务边界时，判断条件可能已经过期，语句的 `AND` 守卫性条件会把「已过期」静默翻译成「无操作成功」。凡有守卫性 `WHERE`（`AND is_primary = false`、`AND enabled = true`、`AND version = $n`），都要用 `RowsAffected()` 把「无操作」显式分流成冲突。
