## 3. 缺陷证据（逐条）

### 3.1 D1 / D2 —— 探针可路由性判据（最重的一条）

**原判据**（`bg/probe_gateway_routability.go:97`）：

```sql
OR COALESCE((
    SELECT bool_or(v.unavailable_reason ~ '^(provider_|credential_|lifecycle_|availability_|quota_|recent_probe_unreachable)')
      FROM v_routable_credential_models v
     WHERE v.credential_id = $1 AND v.raw_model_name = $2
), false)
```

**实测**：`sql/objects/views/v_routable_credential_models.sql:33-38` 的排除原因 CASE 实际产出**九类**：

```
provider_* / credential_* / lifecycle_* / availability_* / quota_* /
recent_probe_unreachable / model_unavailable / model_manual_disabled /
binding_unavailable / node_probe_failed
```

**原判据只覆盖前六类** ⇒ 漏掉后四类。而 `node_probe_failed` 恰是**上一版提交自己实测到的残留主因**
（10 个残留对里 7 个）⇒ **判据对它不咬 ⇒ 网关轮照跑 ⇒ 残留 `no_candidate` 不归零**。

**D2 的事实订正**（原注释称"两张表已经漂移"）：

- `sql/objects/views/model_offers.sql:5` —— `model_offers` **本身是视图**，基表是
  `credential_model_bindings JOIN provider_models`，它的 `available` 列**就是 `cmb.available`**
  ⇒ **不存在漂移**；
- `provider/client.go:2068` —— 路由层**自己**的候选查询用的就是资格视图
  `AND v.is_routable = TRUE` ⇒ **资格视图才是路由层的判据面**。

⇒ 原注释的前提与代码相反。**修法**：判据改为**直接读路由层自己那一列**
（`NOT bool_or(v.is_routable)`），既补上四类漏判，又**不枚举 CASE 出来的文本**（枚举必然随视图演进而漂移）。

### 3.2 D3 —— 一行脏 capabilities ⇒ 全站鉴权瘫痪

```go
// domains/authentication/keystore_sync.go:163
info, scanErr := scanKeyStoreRow(rows)
if scanErr != nil {
    return scanErr        // ★ 整批装载中止 ⇒ kv.keyStore 不更新 ⇒ 全站 Key 不可用
}
```

`scanKeyStoreRow` 把 jsonb 直接扫进 `*[]string` ⇒ pgx 的 JSONCodec 走 `json.Unmarshal`
⇒ 一行 `{"a":1}` / `["x",1]` 就报错 ⇒ **整批中止**。这不是 403，是**认证面整体瘫痪**。

**修法**：新增 `domains/authentication/capabilities.go`（容错解析 `parseCapabilityList`），
扫描改为读 `::text` 后自行解析；**坏行被隔离**（跳过这一把 Key ＋ 告警），不牵连整批。
坏 Key 不进副本 ⇒ 它的请求拿不到授权 ⇒ **fail-closed**。

### 3.3 D9 —— schema 错误被降级为放行

```go
// domains/authentication/verifier.go:414
if !errors.As(verifyErr, &invalid) {
    if stale, staleAge := kv.getStaleCache(rawKey); stale != nil {
        return stale, nil    // ★ 列缺失(42703) / 脏值 ⇒ 带旧能力放行
    }
}
```

与 `capabilitygate` 包头宣称的 fail-closed 口径相反。**本轮不擅自改**（它会改变既有鉴权行为，
且"stale 兜底"是上一次刻意设计的行为）⇒ 登记待 owner（§5.2）。

### 3.4 D10 —— 跳过路径把 0 写进队列主状态

跳过后 `gateway.round` 的 `httpStatus`/`latencyMs` 恒为 0，而队列结果取的是
`gw.httpStatus`/`gw.latencyMs` ⇒ `credential_probe_queue.result_http_status` 变成 **0**，
直连轮真实的 429/502 与延迟丢失（队列是复检面板与退避判定的读数面 ⇒ 0/0 = "没有信息"）。

**修法**：**队列结果**在跳过时取直连轮读数；**不**把它写进网关轮自己的列
（`node_probe_runs.gateway_http_status` 必须继续如实表示"网关轮没跑"）。

### 3.5 D5 / D6 / D13 —— 方案A 的唯一性闸

**实测**（本轮现算）：投递面 `files=()` 372 条里，`800_provider_endpoint_protocols.sql` 与
`856_usage_ledger_ts_cover_agg_idx.sql` **各出现两次**（不同轮次的重复登记，不是两个不同文件）；
而 `scripts/lib/deploy-surface.sh` 的**唯一真源** `deploy_surface_extract` **本来就去重**
（注释原文："去重且保留首次位置（800 出现两次 ⇒ 首次才是投递起点）"）。

⇒ 新的 `migration_version_conflict_count` **按数组条目计数** ⇒ 800/856 的「同键文件数」被算成 2
⇒ **唯一性闸误判为冲突 ⇒ 方案A 的推断被误关** ⇒ 这两个文件在历史库上会被**重放**。
这正是仓内那条既有教训的复现：**同一口径写了两份 ⇒ 迟早分叉**。

**修法**：
1. 计数改为**按不同文件**（同一 basename 只计一次）；
2. 删除 `files=()` 里的两处**重复登记**（生效位置一直是首次登记处 ⇒ **不改变投递顺序与投递内容**）；
3. 契约测试新增 3 组断言：**投递面无重复登记** / **空版本键在调用侧被挡住** /
   **闸的计数口径与部署脚本真身逐字一致**（去注释归一后比较 ⇒ 抄本漂移即红）。

## 6. 本轮方法论记要（三条）

1. **「查对了表」不等于「判据成立」**：本轮最重的一条缺陷，是判据**查的表是对的**、
   **枚举的理由集是错的** ⇒ 判据对它要治的那一族**不咬**。
   ⇒ 通用式：**判据要问「路由层自己那一列」，不要在 Go 侧枚举视图 CASE 出来的文本** ——
   枚举必然随视图演进而漂移。
2. **「一行坏数据」与「一批数据」的边界**：能力读路径把**逐 Key 独立**的语义
   放进了**全有或全无**的通道 ⇒ 一行脏值 ⇒ 全站瘫痪。
   ⇒ 通用式：**判据的失败粒度必须与数据的独立粒度一致**。
3. **同一口径写两份 ⇒ 迟早分叉**：方案A 的闸与仓内唯一真源 `deploy-surface.sh`
   在「投递面是否去重」上分叉了 ⇒ 闸误关。
   ⇒ 通用式：**新判据落地时，先找唯一真源；找不到就当场立一个并把抄本钉住**
   （本轮已把「抄本 vs 真身逐字一致」做成契约断言）。
