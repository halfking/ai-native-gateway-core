# 会话健康检查（session_inspector）模块优化方案

## 一、目标
在现有 hook 插件架构基础上，**完善**而非重写 session_inspector 模块，围绕四个核心场景
补齐配置项、业务逻辑、后台 worker、API 与文档，使其与 compression / prompt_injection /
output_compliance / cache / session_audit / rate_limit 联动。

## 三、设计方案

### Phase 1：设置项（settings/spec_modules.go）

新增一个子分类 `CategoryInspector` 复用 `CategorySession`（避免新增 category 引发 i18n 改动），
挂在 `ModuleSpecs()` 中 `session_inspector.enabled` 之后。

**22 个新配置键**（用户研究汇总 + LiteLLM/Helicone/Kong 最佳实践）：

```
总开关（已有）
  session_inspector.enabled

A. Token 使用量监控（5 个）
  session_inspector.token.max_total              int   100000  # 硬上限
  session_inspector.token.soft_warning_pct       int   80      # 软警告百分比
  session_inspector.token.warn_action            enum  log|metadata|block  # 警告动作
  session_inspector.token.include_output         bool  true    # 是否计 output token
  session_inspector.token.reset_cycle            enum  never|hourly|daily|weekly  # 计数周期

B. 不活跃会话检测与回收（5 个）
  session_inspector.idle.timeout                 string 30m    # TypeDuration
  session_inspector.idle.absolute_max_lifetime   string 168h   # 最长生命周期
  session_inspector.idle.cleanup_interval        string 5m     # 后台 worker 扫描间隔
  session_inspector.idle.cleanup_batch_size      int   500
  session_inspector.idle.recycle_action          enum  soft_close|notify_only  # 用户选了"软关闭"

C. 高频请求检测（6 个）
  session_inspector.rate.rpm_limit               int   60      # 每分钟请求数
  session_inspector.rate.burst_limit             int   100     # 突发窗口上限
  session_inspector.rate.burst_window_seconds    int   5
  session_inspector.rate.max_concurrent          int   4       # 单会话并发
  session_inspector.rate.strategy                enum  fixed|sliding|token_bucket
  session_inspector.rate.observe_only            bool  false   # 仅观察不阻断

D. 会话生命周期管理（3 个）
  session_inspector.lifecycle.auto_extend_on_activity  bool  true
  session_inspector.lifecycle.max_sessions_per_tenant  int   1000
  session_inspector.lifecycle.eviction_policy         enum  lru|fifo|none

E. 告警与可观测性（4 个 — 用户选"全都要"）
  session_inspector.alert.enabled                bool  true
  session_inspector.alert.notify_channels        string JSON  []   # 复用 feishu_bot/wechat_bot
  session_inspector.alert.webhook_urls           string JSON  []
  session_inspector.alert.prometheus_enabled     bool  true
```

### Phase 2：业务逻辑层（`domains/hooks/session-inspector/`）

**2.1 新建 `config.go`**（参照 `domains/hooks/sessionaudit/config.go`）
- `Config` struct + `LoadConfig()` + `get*` helpers
- 全部默认值与 spec 保持一致

**2.2 扩展 `inspectors.go`**
- `TokenLimitInspector` 改用 config（保留原有 NewTokenLimitInspector 兼容旧调用）
- `InactiveInspector` 改用 config
- `HighFrequencyInspector` 改用 config
- 新增 `SessionLifecycleInspector` — 软关闭超期会话
- 新增 `ErrorRateInspector` — 会话错误率超阈值（与 session_health 联动）
- 新增 `ConcurrentSessionInspector` — 配合 max_concurrent 检查
- severity 与 `response` 联动：warning/critical 影响是否阻断

**2.3 改写 `hook.go`**
- Enabled() 读 `session_inspector.enabled` 配置
- 持有 *Config（每次 Execute 调 LoadConfig 热更新）
- Execute 末尾：
  1. findings 写入 `env.Metadata[MetaKeySessionFindings]`（保留）
  2. 通过 `EventBus` 发布 `SessionHealthFindingEvent`（新增类型）→ 通知子模块消费
  3. `promauto` 暴露 4 个 counter：findings_total / soft_warning / recycle / block
  4. 严重 findings (severity>=critical) 调用 `response` 模块的 `Warn/Sanitize` 动作
- 维护一个 `inspectorRegistry` 让 `LoadConfig` 后能动态热替换 inspector

**2.4 新建 `event.go`**
- `SessionHealthFindingEvent` 类型
- `SessionHealthRecycleEvent` 类型（异步回收任务）

**2.5 三个 wiring 点改成"读 config + 动态构造"**
- `cmd/gateway/main_pipeline.go:349`
- `cmd/gateway-v2/main.go:243`
- `cmd/gateway/main_v2_pipeline.go:220`

### Phase 3：后台回收 worker（`bg/session_lifecycle_worker.go`）

参照 `bg/session_health_worker.go` 模板（同样有 Start/Stop/run/ticker/sweep 骨架）：

```
SessionLifecycleWorker
  ├─ 读 config (idle.timeout / cleanup_interval / cleanup_batch_size / recycle_action)
  ├─ 每 cleanup_interval 触发 sweep()
  ├─ SQL: SELECT gw_session_id, tenant_id, last_active_at
  │        FROM session_dim
  │        WHERE status='active' AND last_active_at < NOW() - $1
  │        LIMIT $2
  └─ 对每个候选：
       recycle_action=soft_close:
         UPDATE session_dim SET status='closed', closed_at=NOW()
       recycle_action=notify_only:
         EventBus.Publish(&SessionHealthRecycleEvent{...})
```

注册到 `cmd/gateway/main.go` 与 `cmd/gateway-v2/main.go`（参考 healthWorker 注册位置 `main.go:2131-2135`）。

### Phase 4：admin 模块定义与 API（`admin/`）

**4.1 增强 `modules.go:191-204`**
- `ConfigKeys`: 列出 22 个新 key（供 `/api/admin/modules/session_inspector` 返回详细配置）
- `DocsURL`: `/docs/modules/session-inspector.md`
- `Dependencies`: 关联 5 个相关模块（Required=true）
  - `compression`、`cache`、`prompt_injection`、`output_compliance`、`session_audit` 全部 Required
  - 与 security-engine.md 第 3.2 节"可选依赖"中的描述一致
- `Integration`: 保留 nil（本模块无外部集成）

**4.2 增强 `admin/session_health_api.go`**
- 新增 `GET /api/admin/sessions/<id>/inspector-findings` — 返回当前会话最新 findings
- 新增 `GET /api/admin/sessions/inspector-stats` — 平台级统计（活跃/空闲/关闭/告警数）
- 新增 `POST /api/admin/sessions/<id>/recycle` — 手动触发单会话回收（用户选了"软关闭"）
- 复用 `Handler.getOrComputeHealth` / `fetchSessionSummaryByID` 等已有 helper

**4.3 路由注册 `registerModuleRoutes` 不变，新增的端点单独注册**

### Phase 7：兼容与回滚保障

- **不破坏现有 API**：`session_inspector.enabled` 默认 true，热更语义不变
- **不破坏 hook 链路**：保留 `NewTokenLimitInspector(int)` 等构造函数，新代码默认读 config
- **不破坏 wiring 三个点**：仅把硬编码数字换成 `sessioninspector.DefaultConfig()` 返回值
- **不破坏依赖**：`Dependencies` Required 是软约束（管理员仍可单独启用，但前端会提示；与现有 disguise / wechat_bot / session_analytics 一致行为）
- **数据库零迁移**：所有读写都用现有 `session_dim.status / last_active_at` 字段

## 五、风险与缓解

| 风险 | 缓解 |
|---|---|
| 新增 spec 在旧 DB 中无默认值 | 复用 `EffectiveValue` 的 default 机制，无需迁移 |
| 后台 worker 高频扫描拖慢 DB | cleanup_interval 默认 5min，batch_size=500；可在 admin 调高 |
| Findings 写入 EventBus 引入新依赖 | 沿用 memory_bus（已存在），无需新框架 |
| 三个 wiring 点的硬编码行为被覆盖 | 保留 `NewTokenLimitInspector(int)` 老 API，新 `NewInspectorHookWithConfig()` 走 config |
| 软关闭改 status='closed' 影响现有业务 | 现有 `session_dim.status` 已有 'active/closed/idle' 三态，复用 closed 态即可 |
