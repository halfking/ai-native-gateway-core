# 看板與會話統計的統計標準

「看板」「會話與統計」「供應商對賬」是同一批模型呼叫流水在**三套口徑**下的三種彙總。這一頁把每個數字的演算法、資料來源、時間視窗寫清楚，並給出三個模組數字為什麼對不上的**逐項拆解**——用於對齊資料、自查偏差。

> 實測口徑：2026-11-23 21:05（Asia/Shanghai）生產環境實測。全部數字取自**同一瞬時點**（單條 SQL 內完成），視窗＝`NOW()-7 天`；供應商對賬側另按日曆日閉區間 `2026-11-17 ~ 2026-11-23` 實測並與事實表逐日對拍。

## 三個模組是什麼關係

| | 看板 | 會話與統計 | 供應商對賬 |
| --- | --- | --- | --- |
| 統計實體 | 一筆模型呼叫算一條（**請求級**） | 一個會話算一條，取該會話的**累計值**（**會話級**） | 一筆模型呼叫算一條（**請求級**，依供應商聚合） |
| 真源 | 請求級事實表 `usage_facts` | 會話彙總表 `session_summaries` + 會話宇宙 | 日快照表 `report_snapshots` |
| 時間視窗 | 系統時區日曆日：今天-(N-1) 日零點 → 此刻 | 滾動 N 天（首次請求落在最近 N 天內） | **日曆日閉區間**（整日，含末日整天） |
| 探測流量 | 依 `traffic_class` 剔除（可切換） | 依**會話宇宙**規則剔除 | **不剔除**（全流量，含未指派） |
| 成熟度 | 即時 | 即時 | **T+1 快照**（當日未結束的日期會滯後） |

**結論先說**：三個模組的數字**本來就不該相等**——實體不同、視窗不同、探測剔除規則不同、成熟度不同。跨模組比較必須先對齊這四項，不能直接相減。

### 最重要的一條：探測流量幾乎免費

探測（健康檢查／自我檢查）流量在事實表裡單列 `traffic_class='probe'`：

| 口徑（同一視窗） | 請求數 | 費用 |
| --- | --- | --- |
| 排除探測 | 81,265 | $8,854.70 |
| 含探測 | 189,534 | $8,856.87 |
| **探測部分** | **108,271** | **$2.17** |

⇒ **請求數差 2.3 倍，費用卻只差 $2.17。** 凡是「請求數差很多、費用差不多」的現象，先懷疑探測口徑，而不是資料算錯。

## 看板：每個數字怎麼來的

| 卡片／模組 | 演算法 | 說明 |
| --- | --- | --- |
| 總請求數 | 視窗內終態請求筆數 | 只含成功／失敗／限流等終態紀錄，不含未完成的串流 |
| 成功率 | 成功筆數 ÷ 總筆數 | 狀態為成功的請求佔比 |
| 總 Token | 每筆輸入字量 + 輸出字量分別累加 | 快取命中的字量依各上游口徑計入 |
| 總費用 | 每筆費用累加（美元） | 美元是付給上游供應商的成本口徑 |
| 總積分 | 平臺向租戶計費的積分數 | ★ 見下方「積分卡」 |
| 平均延遲 | 每筆延遲累加 ÷ 總筆數 | 毫秒 |
| 活躍模型／活躍供應商 | 視窗內有實際流量的去重計數 | 不是「平臺可用總數」 |
| 活躍金鑰 | 目前處於啟用狀態的金鑰數量 | **配置口徑，與時間範圍無關** |
| 錯誤數 | 優先依失敗原因分佈逐類累加；無該分佈時用「總請求 × (1 − 成功率)」推算 | 推算值與真實值可能差幾筆 |
| 餅圖（模型／供應商／租戶／客戶端…） | 依維度分組累加請求／Token／費用 | 來自分鐘統計表，與上方卡片不是同一個真源 |
| 用量趨勢圖 | 依時間桶累加請求／Token／費用／積分 | 同樣來自分鐘統計表 |

### 時間視窗怎麼算

- 「今天」＝系統時區（預設 Asia/Shanghai）今日零點 → 此刻；「近 7 天」＝6 天前的零點 → 此刻；「近 30 天」同理。**起點是日曆日零點，終點是當下時刻**，不是整日。
- 自訂區間依所選兩天彙總，含末日整天。
- 頁面每 10 秒自動重新整理；即時通道線上時新完成的請求會即時累加。

### 積分卡（口徑特殊，務必注意）

積分卡顯示的值**不是視窗內的積分消耗**：請求級事實表的積分欄目前恆為 0（實測全表 298,037 列全為 0），頁面顯示的實際是「基線快照之後的即時增量」。因此：

- 切換「今天／近 7 天／近 30 天」，積分卡的數字**完全一樣**（實測三者同為 86,925）。
- 同一頁的用量趨勢圖另有積分合計（分鐘統計表口徑，近 7 天 1,767,183），與積分卡不是同一個數。

需要可信的積分帳目時，請以「用量成本」「對賬報表」頁為準，不要用看板積分卡做時間序列比較。

## 會話與統計：每個數字怎麼來的

| 模組 | 演算法 | 說明 |
| --- | --- | --- |
| 總會話數 | 視窗內首次請求時間落窗的會話筆數 | 會話級計數，不等於請求數 |
| 活躍／新／已關閉會話 | 依會話的最後／首次請求時間是否落在最近 24 小時內劃分 | 與主視窗無關的 24 小時口徑 |
| 總費用（美元） | 各會話累計費用求和 | 一個會話的**全部**費用記在會話列上 |
| 總請求數 | 各會話累計請求數求和 | 同樣取會話累計值，不是視窗內發生的請求數 |
| 輸入費用／輸出費用 | 各會話的輸入／輸出費用分別求和 | 兩者相加＝總費用 |
| 平均會話費用／單請求費用 | 總費用 ÷ 會話數（÷ 請求數） | 分母是會話累計值 |
| 成功率／快取率（對齊行） | 請求級視圖的成功筆數 ÷ 請求總數 | 只有請求級口徑才有這兩項 |
| 會話分析對齊指標行 | 物化視圖會話級彙總 | 每 15 分鐘更新一次；視窗＝上海日曆日整天 |
| Top5 使用者／Top5 供應商 | 會話分析排行端點（使用者／模型／供應商／任務） | 供應商由 SQL 按 `model_usage_aggregates.provider` 聚合（**不是**由模型名稱前綴推導），**含費用**、可依費用排序；Top5 四維在「會話分析 → 使用者」頁呈現 |
| 輪次對拍 | 會話請求數 vs 輪次數 | 差值超過 10% 時頁面會給出提示條 |

### 會話宇宙（哪些會話被算、哪些沒算）

會話側只統計同時滿足以下三條的會話：

1. 在會話表裡登記過的會話；
2. 有歸屬使用者（依使用者鍵或金鑰歸屬鍵取其一，都為空則不計）；
3. 不是探測會話：既不是人工標記的探測位，也不是依「使用者／客戶端類型／標題」模式判定的自我檢查、部署閘門、測試、驗證類會話。

### 對賬模組內部：零重複計算

對賬頁的供應商列（含「未指派」）**加總恰好等於頁面總數**：

- 供應商列加總 = 178,841 請求 = 頁面總請求數 ✓
- 供應商列費用加總 = $8,612.07 = 頁面總費用 ✓
- 其中「未指派」（`provider_id IS NULL`）= 79,801 筆 / 100% 失敗 / $0.00 —— 這些是**探測流量沒有供應商歸屬**（探測不打到上游供應商），不是漏算。

## 數字對不上時怎麼自查

1. **先對齊視窗**：看板＝日曆日零點起；會話與統計面板＝滾動 N 天；對齊行＝上海日曆日整天；供應商對賬＝日曆日閉區間。四者同一預設下仍不是同一個視窗。
2. **再對齊實體**：請求數對請求數、費用對費用；不要拿「會話數」和「請求數」比。
3. **再對齊探測口徑**：看板可切「含探測」；會話統計依會話宇宙規則剔除；**對賬永遠含探測**。請求數差很多而費用接近 ⇒ 先看探測。
4. **再對齊成熟度**：對賬是 T+1 快照，**當日資料必然滯後**；對比前先確認快照覆蓋到哪一天。
5. **看降級標記**：卡片出現「降級／不可信／未算出」時，那幾個 0 不代表沒有流量。
6. **看板趨勢圖 ≠ 看板卡片**：趨勢圖來自分鐘統計表，與上方卡片（請求級事實表）不是同一個真源（30 天視窗實測相差約 13.8%）。
7. **「今天」檔位曾失敗（2026-11-23 已修）**：會話與統計的「今天」檔位先前因資料庫側連接索引缺失而穩定 30 秒逾時（2026-11-23 已補索引，查詢耗時由 121.8 秒降到 0.19 秒）。若頁面仍顯示該檔位失敗，代表索引又被清掉了，請讓值班同學檢查 `idx_session_dim_session_key` 是否在位。

## 已知限制（2026-11-23 實測）

1. **會話宇宙的探測剔除過寬（D1/D2，2026-11-23 實測確認）**：會話統計剔掉的 19,512 筆請求、$7,021.91 費用，在請求日誌裡 **100% 屬於業務流量**。會話統計因此比看板（排除探測口徑）低約 **$7,021.91（79%）**。**看板（請求級）的數字自始不受影響** ⇒ 精確的費用對賬請以看板為準，或把對賬頁切到「業務」口徑後再比。
2. **跨窗會話（E）**：18 個會話的首次請求早於視窗、但視窗內仍在活躍，目前被整體排除，漏算 3,191 筆 / $281.38（佔看板費用 3.2%）。
3. **無會話歸屬的呼叫（F）**：381 筆直連 API / 腳本呼叫沒有會話，看板會計入、會話統計不會。
4. **對賬快照的當日滯後**：對賬是 T+1 口徑，**當天（今天）的資料不完整**，與看板的即時數字直接相減必然出現差額。
5. 看板積分卡不隨時間範圍變化（見上）。
6. 看板趨勢圖（分鐘統計表）與上方卡片（請求級事實表）在 30 天視窗實測相差約 13.8%（160,451 vs 140,969 筆）。
