# ボードとセッション統計の集計ルール

「ボード」と「セッション統計」は、同じモデル呼び出しのストリームを**2 つの集計ルール**でまとめたものです。このページでは、両タブのすべての数値の求め方・データ元・時間範囲を明記し、両者の数字が一致しない理由を一項目ずつ対照表で示します。データの突合と偏差の自己点検に使ってください。

> 実測基準：2026-11-23 02:27（Asia/Shanghai）本番環境で実測し、本番 DB の読み取り専用クエリと突き合わせ。

## 2 つのタブの関係

| | ボード | セッション統計 |
| --- | --- | --- |
| 集計対象 | 1 回のモデル呼び出し = 1 行（**リクエスト単位**） | 1 セッション = 1 行、そのセッションの**累計値**を保持（**セッション単位**） |
| 真値の出所 | リクエスト単位の事実テーブル `usage_facts`（Redis キャッシュ基準値 + ライブ差分） | セッション集計テーブル `session_summaries`（即時クエリ）+ マテリアライズドビュー（キャッシュ面） |
| 時間範囲 | システムタイムゾーンの暦日：本日-(N-1) 日 0 時 → 現在 | パネル＝過去 N 日のローリング（初回リクエストが過去 N 日内）、整合行＝上海暦日の終日 |
| プローブ流量 | リクエスト単位の事実テーブルのトラフィック区分で除外 | セッション側の「セッション宇宙」ルールで除外 |

**先に結論**：2 つのタブの数字は**本来 같くなるべきではありません**——集計対象（リクエストかセッションか）、時間範囲、除外ルールがすべて異なります。比較する場合はまずこの 3 つをそろえてからで、単純に引き算してはいけません。

## ボード：各数字の求め方

| カード／モジュール | アルゴリズム | 備考 |
| --- | --- | --- |
| 総リクエスト数 | 期間内の終端リクエスト行数 | 成功／失敗／レート制限などの終端記録のみ。完了しないストリームは含まない |
| 成功率 | 成功行数 ÷ 総行数 | 応答が返ったリクエストの割合 |
| 総トークン | 各リクエストの入力トークン + 出力トークンを合算 | キャッシュヒットの扱いは各プロバイダの基準に従う |
| 総費用 | 各リクエストの費用（米ドル）を合算 | 米ドルは上流プロバイダに支払うコスト基準 |
| 総クレジット | プラットフォームがテナントに課金したクレジット数 | ★ 下「クレジットカード」参照 |
| 平均レイテンシ | 各リクエストのレイテンシ合算 ÷ 総行数 | ミリ秒 |
| アクティブモデル／プロバイダ | 期間中に実際にトラフィックがあったものの重複排除カウント | 「プラットフォームで利用できる総数」ではない |
| アクティブキー | 現在有効な状態にあるキーの数 | **設定ベースであり、時間範囲に依存しない** |
| エラー数 | 失敗原因の内訳から合算。取得できない場合は「総リクエスト × (1 − 成功率)」で推定 | 推定値は実際と数件ずれることがある |
| 円グラフ（モデル／プロバイダ／テナント／クライアント…） | 维度ごとにリクエスト／トークン／費用を集計 | 分単位統計表由来で、上のカードとは別の真値 |
| 使用量トレンド | 時間バケットごとにリクエスト／トークン／費用／クレジットを集計 | 同じく分単位統計表由来 |

### 時間範囲の計算

- 「今日」＝システムタイムゾーン（既定 Asia/Shanghai）の本日 0 時 → 現在、「直近 7 日」＝6 日前の 0 時 → 現在、「直近 30 日」も同様です。**開始は暦日の 0 時、終了は現在の瞬間**で、1 日全体ではありません。
- カスタム範囲は選んだ 2 日分を集計し、末日の全日を含みます。
- ページは 10 秒ごとに自動更新します。ライブチャネルが有効なら完了したリクエストは即時に加算されます。

### クレジットカード（特殊なルールです）

クレジットカードの値は**選択した期間に消費されたクレジットではありません**。リクエスト単位の事実テーブルのクレジット列は現在常に 0 です（実測：全 298,037 行が 0）。画面に出るのは「キャッシュ基準値以降のライブ差分」です。したがって:

- 「今日／直近 7 日／直近 30 日」を切り替えても、クレジットカードの数字は**まったく変化しません**（実測：3 つとも 86,925）。
- 同じページの使用量トレンドには別のクレジット合計（分単位統計表基準、7 日で 1,767,183）があり、カードの数字とは別物です。

信頼できるクレジット台帳が必要な場合は「使用量コスト」「照合レポート」ページを参照してください。ボードのクレジットカードを時系列比較に使わないでください。

## セッション統計：各数字の求め方

| モジュール | アルゴリズム | 備考 |
| --- | --- | --- |
| 総セッション数 | 初回リクエストが期間内に収まるセッション行数 | セッション単位の件数であり、リクエスト数ではない |
| アクティブ／新規／終了セッション | セッションの最終／初回リクエストが過去 24 時間内かどうかで区分 | 本期間とは独立の 24 時間基準 |
| 総費用（米ドル） | 各セッションの累計費用を合算 | 1 セッションの**全費用**がセッション行に載る |
| 総リクエスト数 | 各セッションの累計リクエスト数を合算 | 同じくセッションの累計値であり、期間内に発生したリクエスト数ではない |
| 入力費用／出力費用 | 各セッションの入力／出力費用を個別に合算 | 両者の合計が総費用 |
| セッション平均費用／リクエスト平均費用 | 総費用 ÷ セッション数（÷ リクエスト数） | 分母はセッション累計値 |
| 成功率／キャッシュ率（整合行） | リクエスト単位のビューにおける成功行数 ÷ リクエスト総数 | この 2 指標はリクエスト単位の基準でのみ存在する |
| セッション分析の整合行 | マテリアライズドビューのセッション級集計 | 15 分ごとに更新。範囲＝上海暦日の終日 |
| Top5 ユーザー／Top5 プロバイダ | セッション分析の概要 API | プロバイダはモデル名の接頭辞から推定し、リクエスト数で並べ替え。**費用は含まれない** |
| ターンの突き合わせ | セッションのリクエスト数とターン数 | 差が 10% を超えるとページが通知を表示 |

### セッション宇宙（どのセッションが数えられるか）

セッションは次の 3 つをすべて満たす場合のみ集計されます:

1. セッションテーブルに登録されたセッション;
2. 所有者がいること（ユーザーキーか API キーの所有者キーを採用し、どちらも空なら数えない）;
3. プローブセッションでないこと（手動でプローブ指定されたものを除き、「所有者／クライアント種別／タイトル」のパターンで判定されるセルフチェック・デプロイゲート・テスト・検証系も除外）。

### なぜここの費用がボードより小さいのか

セッション宇宙の 3 番目のルールは、**一部の実業務セッション**をプローブと判定して除外します。2026-11-23 の本番 DB 実測（同じ 7 日間）:

- セッション側で除外された 15,898 セッションの主リクエストは、リクエスト単位の事実テーブルでは **100% 業務トラフィック**であり、合計 $6,452.73;
- 同期間にリクエスト単位の事実テーブルで実際にプローブと区分された流量は合計 **$1.81** のみ。

つまり両タブとも「プローブを除外」と表示していますが、**除外対象は同一の 요청ではない**のです。これがセッション統計の費用がボードより大きく下がる第 1 の理由です。

## 2 タブの数字の対照（2026-11-23 実測、7 日間）

| 指標 | ボード | セッション統計（パネル） | セッション統計（整合行） |
| --- | --- | --- | --- |
| 集計対象 | リクエスト | セッション＋セッション累計リクエスト | セッション／リクエスト |
| リクエスト数 | 65,774 | 72,098 | — |
| 費用（米ドル） | 8,013.93 | 2,717.62 | 2,468.73（内部コスト） |
| クレジット | 86,925（範囲に依存しない） | — | 0 |
| トークン | 3,245,804,009 | — | — |
| 成功率 | 95.31% | — | 94.64% |
| セッション数 | — | 19,235 | 17,390 |

差の要因を 1 つずつ対応付けると:

- **リクエスト数 72,098 > 65,774**: セッション側のリクエスト数は「選ばれたセッションの累計リクエスト数」であり、期間境界をまたぐセッションは期間後の分まで丸ごと加算されます。さらにセッションテーブルには重複行があり（実測: 同一セッションキーで最大 30 行）、それも合算対象になります。
- **費用 2,717.62 < 8,013.93**: セッション宇宙が上記の $6,452.73 の業務トラフィックをプローブとして除外しています。加えてボードは**セッションに属さない呼び出し**（直接 API 呼び出し、スクリプト呼び出し）も数えており、実測ではボード費用の 2 割程度がこれです。
- **クレジット 0 vs 86,925**: セッション側にもリクエスト単位の事実テーブルにも信頼できるクレジット残高が現在無く、画面上の値はライブ差分から来ています。
- **成功率 95.31% vs 94.64%**: いずれもリクエスト単位の基準ですが、一方は `usage_facts`、他方はリクエストログのマテリアライズドビュー由来で、範囲も異なります。

## 数字が合わないときの自己点検

1. **まず範囲をそろえる**: ボード＝暦日 0 時から、セッション統計パネル＝過去 N 日のローリング、整合行＝上海暦日の終日。同じプリセットでも 3 つは同一範囲ではありません。
2. **次に集計対象をそろえる**: リクエスト数はリクエスト数と、費用は費用と。セッション数とリクエスト数を比べないでください。
3. **低下表示を探す**: カードに「低下／信頼できない／算出できず」と出ている場合、その 0 はトラフィック無しの意味ではありません。
4. **プローブ切替を確認する**: ボードの「プローブ除外／含める」はヒーロー区 summarise だけ切り替えます。分布図とトレンド図は常に業務基準です。
5. **「今日」は失敗し得る**: セッション統計の「今日」は DB 負荷で 30 秒の予算を超えてエラーになることがあり、そのとき画面に出るのは失敗であり 0 ではありません。

## 既知の制約（2026-11-23 実測）

1. セッション統計の「今日」は本番 DB 上で 30 秒のタイムアウトが安定的に発生します（セッション宇宙の結合におけるインデックス問題で、範囲が小さいほど計画が劣化します）。「直近 7 日」「直近 30 日」は動作します。
2. セッション側の集計はセッションテーブルの重複行も合算するため、リクエスト数と費用が高めに出ます。
3. ボードのクレジットカードは時間範囲で変化しません（上記）。
4. ボードのトレンド図（分単位統計表）と上のカード（リクエスト単位の事実テーブル）は 30 日間で約 13.8% の差（160,451 対 140,969 リクエスト）があります。
5. プローブ除外は両側で同一の流量を除外していません（上記）。
