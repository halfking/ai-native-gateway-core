# ボードとセッション統計の集計ルール

「ボード」「セッション統計」「プロバイダ照合」は、同じモデル呼び出しのストリームを**3 つの集計ルール**でまとめたものです。このページでは、各数値の求め方・データ元・時間範囲を明記し、3 つのモジュールの数字が一致しない理由を**項目ごとに分解**して示します。データの突合と偏差の自己点検に使ってください。

> 実測基準：2026-11-23 21:05（Asia/Shanghai）本番環境で実測。すべての数値は**同一時点**（1 つの SQL 文内）で取得し、範囲＝`NOW()-7 日`。プロバイダ照合側は暦日閉区間 `2026-11-17 ~ 2026-11-23` で別途実測し、事実表と日ごとに突合しました。

## 3 つのモジュールの関係

| | ボード | セッション統計 | プロバイダ照合 |
| --- | --- | --- | --- |
| 集計対象 | 1 回のモデル呼び出し = 1 行（**リクエスト単位**） | 1 セッション = 1 行、そのセッションの**累計値**を保持（**セッション単位**） | 1 回のモデル呼び出し = 1 行（**リクエスト単位**、プロバイダごとに集計） |
| 真値の出所 | リクエスト単位の事実テーブル `usage_facts` | セッション集計テーブル `session_summaries` + セッション宇宙 | 日次スナップショット表 `report_snapshots` |
| 時間範囲 | システムタイムゾーンの暦日：本日-(N-1) 日 0 時 → 現在 | 過去 N 日のローリング（初回リクエストが過去 N 日内） | **暦日閉区間**（終日を含む、末日は全天） |
| プローブ流量 | `traffic_class` で除外（切替可） | **セッション宇宙**のルールで除外 | **除外しない**（全流量、「未割り当て」を含む） |
| 成熟度 | リアルタイム | リアルタイム | **T+1 スナップショット**（当日が終わる前の日付は遅延する） |

**先に結論**：3 つのモジュールの数字は**本来同じになるべきではありません**——集計対象（リクエストかセッションか）、時間範囲、プローブ除外ルール、成熟度がすべて異なります。比較する場合はまずこの 4 つをそろえてからで、単純に引き算してはいけません。

### 最重要の 1 つ：プローブ流量はほぼ無料

プローブ（ヘルスチェック／セルフチェック）流量は、事実テーブルで `traffic_class='probe'` として別立てされています:

| 集計基準（同じ範囲） | リクエスト数 | 費用 |
| --- | --- | --- |
| プローブ除外 | 81,265 | $8,854.70 |
| プローブ込み | 189,534 | $8,856.87 |
| **プローブ分** | **108,271** | **$2.17** |

⇒ **リクエスト数は 2.3 倍違うのに、費用は $2.17 しか違いません。** 「リクエスト数は大きく違うのに費用はほぼ同じ」という現象は、計算誤りではなく、まず**プローブの集計基準**を疑ってください。

## ボード：各数字の求め方

| カード／モジュール | アルゴリズム | 備考 |
| --- | --- | --- |
| 総リクエスト数 | 期間内の終端リクエスト行数 | 成功／失敗／レート制限などの終端記録のみ。完了しないストリームは含まない |
| 成功率 | 成功行数 ÷ 総行数 | 応答が返ったリクエストの割合 |
| 総トークン | 各リクエストの入力トークン + 出力トークンを合算 | キャッシュヒットの扱いは各プロバイダの基準に従う |
| 総費用 | 各リクエストの費用（米ドル）を合算 | 米ドルは上流プロバイダに支払うコスト基準 |
| 総クレジット | プラットフォームがテナントに課金したクレジット数 | ★ 下「クレジットカード」参照 |
| 平均レイテンシ | 各リクエストのレイテンシ合算 ÷ 総行数 | ミリ秒 |
| アクティブモデル／プロバイダ | 期間中に実際にトラフィックがあったものの重複排除カウント | 「プラットフォームで利用できる総数」ではない |
| アクティブキー | 現在有効な状態にあるキーの数 | **設定ベースであり、時間範囲に依存しない** |
| エラー数 | 失敗原因の内訳から合算。取得できない場合は「総リクエスト × (1 − 成功率)」で推定 | 推定値は実際と数件ずれることがある |
| 円グラフ（モデル／プロバイダ／テナント／クライアント…） | ディメンションごとにリクエスト／トークン／費用を集計 | 分単位統計表由来で、上のカードとは別の真値 |
| 使用量トレンド | 時間バケットごとにリクエスト／トークン／費用／クレジットを集計 | 同じく分単位統計表由来 |

### 時間範囲の計算

- 「今日」＝システムタイムゾーン（既定 Asia/Shanghai）の本日 0 時 → 現在、「直近 7 日」＝6 日前の 0 時 → 現在、「直近 30 日」も同様です。**開始は暦日の 0 時、終了は現在の瞬間**で、1 日全体ではありません。
- カスタム範囲は選んだ 2 日分を集計し、末日の全日を含みます。
- ページは 10 秒ごとに自動更新します。ライブチャネルが有効なら完了したリクエストは即時に加算されます。

### クレジットカード（特殊なルールです）

クレジットカードの値は**選択した期間に消費されたクレジットではありません**。リクエスト単位の事実テーブルのクレジット列は現在常に 0 です（実測：全 298,037 行が 0）。画面に出るのは「キャッシュ基準値以降のライブ差分」です。したがって:

- 「今日／直近 7 日／直近 30 日」を切り替えても、クレジットカードの数字は**まったく変化しません**（実測：3 つとも 86,925）。
- 同じページの使用量トレンドには別のクレジット合計（分単位統計表基準、7 日で 1,767,183）があり、カードの数字とは別物です。

信頼できるクレジット台帳が必要な場合は「使用量コスト」「照合レポート」ページを参照してください。ボードのクレジットカードを時系列比較に使わないでください。

## セッション統計：各数字の求め方

| モジュール | アルゴリズム | 備考 |
| --- | --- | --- |
| 総セッション数 | 初回リクエストが期間内に収まるセッション行数 | セッション単位の件数であり、リクエスト数ではない |
| アクティブ／新規／終了セッション | セッションの最終／初回リクエストが過去 24 時間内かどうかで区分 | 本期間とは独立の 24 時間基準 |
| 総費用（米ドル） | 各セッションの累計費用を合算 | 1 セッションの**全費用**がセッション行に載る |
| 総リクエスト数 | 各セッションの累計リクエスト数を合算 | 同じくセッションの累計値であり、期間内に発生したリクエスト数ではない |
| 入力費用／出力費用 | 各セッションの入力／出力費用を個別に合算 | 両者の合計が総費用 |
| セッション平均費用／リクエスト平均費用 | 総費用 ÷ セッション数（÷ リクエスト数） | 分母はセッション累計値 |
| 成功率／キャッシュ率（整合行） | リクエスト単位のビューにおける成功行数 ÷ リクエスト総数 | この 2 指標はリクエスト単位の基準でのみ存在する |
| セッション分析の整合行 | マテリアライズドビューのセッション級集計 | 15 分ごとに更新。範囲＝上海暦日の終日 |
| Top5 ユーザー／Top5 プロバイダ | セッション分析のランキング API（ユーザー／モデル／プロバイダ／タスク） | プロバイダは `model_usage_aggregates.provider` を SQL で集計（**モデル名の接頭辞からの推定ではない**）、**費用を含む**（費用順の並べ替え可）。Top5 の 4 次元は「セッション分析 → ユーザー」ページに表示 |
| ターンの突き合わせ | セッションのリクエスト数とターン数 | 差が 10% を超えるとページが通知を表示 |

### セッション宇宙（どのセッションが数えられるか）

セッションは次の 3 つをすべて満たす場合のみ集計されます:

1. セッションテーブルに登録されたセッション;
2. 所有者がいること（ユーザーキーか API キーの所有者キーを採用し、どちらも空なら数えない）;
3. プローブセッションでないこと（手動でプローブ指定されたものを除き、「所有者／クライアント種別／タイトル」のパターンで判定されるセルフチェック・デプロイゲート・テスト・検証系も除外）。

D1/D2/D3 で除外されたセッションの範囲内リクエストを、リクエストログの `origin_stage` で分類すると:

| 除外理由 | リクエスト数 | 費用（米ドル） | うち `origin_stage='business'` | 割合 |
| --- | --- | --- | --- | --- |
| 手動でプローブ指定 | 12,364 | 5,145.16 | 12,364 | **100%** |
| パターン判定のプローブ | 5,946 | 1,876.67 | 5,946 | **100%** |
| 所有者なし | 1,202 | 0.08 | 1,202 | **100%** |

⇒ セッション側で除外された 19,512 リクエスト、$7,021.91 の費用は、リクエストログ上 **100% 業務トラフィック（`origin_stage='business'`）** で、プローブは 1 件もありません。**これがセッション統計がボードを下回る第 1 の理由であり、現在最大の単一偏差です。**

## 3 つのモジュールの数字の対照（2026-11-23 実測）

| 指標 | ボード（プローブ除外） | セッション統計（パネル） | プロバイダ照合 |
| --- | --- | --- | --- |
| 集計対象 | リクエスト | セッション＋セッション累計リクエスト | リクエスト（プロバイダごとに集計） |
| リクエスト数 | 81,265 | 58,180（宇宙内）/ 77,687（宇宙外の全量） | 178,841（「未割り当て」を含む） |
| 費用（米ドル） | 8,854.70 | 1,551.41（宇宙内） | 8,612.07 |

### 照合モジュールの内部：二重計上はゼロ

照合ページのプロバイダ行（「未割り当て」を含む）は、**合計がちょうどページ総数と一致します**:

- プロバイダ行の合計 = 178,841 リクエスト = ページのリクエスト総数 ✓
- プロバイダ行の費用の合計 = $8,612.07 = ページの総費用 ✓
- うち「未割り当て」（`provider_id IS NULL`）= 79,801 件 / 失敗率 100% / $0.00 —— これは**プロバイダ紐付けのないプローブ流量**（プローブは上流プロバイダに到達しない）であり、集計漏れではありません。

## 数字が合わないときの自己点検

1. **まず範囲をそろえる**: ボード＝暦日 0 時から、セッション統計パネル＝過去 N 日のローリング、整合行＝上海暦日の終日、プロバイダ照合＝暦日閉区間。同じプリセットでも 4 つは同一範囲ではありません。
2. **次に集計対象をそろえる**: リクエスト数はリクエスト数と、費用は費用と。セッション数とリクエスト数を比べないでください。
3. **次にプローブの集計基準をそろえる**: ボードは「プローブ除外／含める」を切り替えられます。セッション統計はセッション宇宙のルールで除外します。**照合側は常にプローブを含みます**。リクエスト数が大きく違い、費用は近いなら、まずプローブを見てください。
4. **次に成熟度をそろえる**: 照合は T+1 スナップショットなので**当日のデータは必ず遅延します**。比較する前に、スナップショットがどの日までを含んでいるかを確認してください。
5. **低下表示を探す**: カードに「低下／信頼できない／算出できず」と出ている場合、その 0 はトラフィック無しの意味ではありません。
6. **ボードのトレンド図 ≠ ボードのカード**: トレンド図は分単位統計表由来で、上のカード（リクエスト単位の事実テーブル）とは別の真値です（30 日間で約 13.8% の差）。
7. **「今日」は失敗し得る（2026-11-23 修正済み）**: セッション統計の「今日」は DB 側の結合インデックス不在により 30 秒のタイムアウトが安定的に発生していました（2026-11-23 にインデックスを追加し、問い合わせは 121.8 秒から 0.19 秒へ）。まだ画面がエラーを示す場合はインデックスが再度失われています。担当者に `idx_session_dim_session_key` の有無を確認してもらってください。

## 既知の制約（2026-11-23 実測）

1. **セッション宇宙のプローブ除外が広すぎる（D1/D2、2026-11-23 実測で確認）**: セッション統計が除外した 19,512 リクエスト、$7,021.91 の費用は、リクエストログ上 **100% 業務トラフィック** です。よってセッション統計はボード（プローブ除外基準）より約 **$7,021.91（79%）** 低くなります。**ボード（リクエスト単位）の数値は当初から影響を受けません** ⇒ 費用の厳密な突合はボードを使うか、照合ページを「業務」基準に切り替えてから比較してください。
2. **窓をまたぐセッション（E）**: 初回リクエストが範囲より前ですが範囲内では活動中のセッションが 18 件あり、現在はまとめて除外されているため、3,191 件 / $281.38（ボード費用の 3.2%）が漏れています。
3. **セッション未紐付けの呼び出し（F）**: 直接 API 呼び出しやスクリプト呼び出し 381 件にはセッションがありません。ボードは数えますが、セッション統計は数えません。
4. **照合スナップショットの当日遅延**: 照合は T+1 基準なので**当日（今日）のデータは不完全**です。ボードのリアルタイム値と直接引き算すると必ず差が出ます。
5. ボードのクレジットカードは時間範囲で変化しません（上記）。
6. ボードのトレンド図（分単位統計表）と上のカード（リクエスト単位の事実テーブル）は 30 日間で約 13.8% の差（160,451 対 140,969 リクエスト）があります。
