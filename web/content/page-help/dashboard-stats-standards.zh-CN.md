# 看板与会话统计的统计标准

「看板」「会话与统计」「供应商对账」是同一批模型调用流水在**三套口径**下的三种汇总。这一页把每个数字的算法、数据来源、时间窗口写清楚，并给出三个模块数字为什么对不上的**逐项拆解**——用于对齐数据、自查偏差。

> 实测口径：2026-11-23 21:05（Asia/Shanghai）生产环境实测。全部数字取自**同一瞬时点**（单条 SQL 内完成），窗口＝`NOW()-7 天`；供应商对账侧另按日历日闭区间 `2026-11-17 ~ 2026-11-23` 实测并与事实表逐日对拍。
>
> ★ 订正（2026-11-23 日期范围对齐轮）：「会话与统计」页签的日期范围已与「看板」页签**统一**（同一控件、同一段日历日）⇒ 下表中与会话统计相关的实测值仍是**统一前**（滚动窗口）的测量值，需按新窗口重测；看板与对账侧的数值不受影响。

## 三个模块是什么关系

| | 看板 | 会话与统计 | 供应商对账 |
| --- | --- | --- | --- |
| 统计实体 | 一笔模型调用算一条（**请求级**） | 一个会话算一条，取该会话的**累计值**（**会话级**） | 一笔模型调用算一条（**请求级**，按供应商聚合） |
| 真源 | 请求级事实表 `usage_facts` | 会话汇总表 `session_summaries` + 会话宇宙 | 日快照表 `report_snapshots` |
| 时间窗口 | 系统时区日历日：今天-(N-1) 日 零点 → 此刻 | **与看板同一区间**（系统时区日历日：今天-(N-1) 日 零点 → 末日 24:00；可自定义起止） | **日历日闭区间**（整日，含末日全天） |
| 探测流量 | 按 `traffic_class` 剔除（可切换） | 按**会话宇宙**规则剔除 | **不剔除**（全流量，含未落定） |
| 成熟度 | 实时 | 实时 | **T+1 快照**（当日未结束的日期会滞后） |

**结论先说**：三个模块的数字**本来就不该相等**——实体不同、窗口不同、探测剔除规则不同、成熟度不同。跨模块比较必须先对齐这四项，不能直接对减。

### 最重要的一条：探测流量几乎免费

探测（健康检查/自检）流量在事实表里单列 `traffic_class='probe'`：

| 口径（同一窗口） | 请求数 | 费用 |
| --- | --- | --- |
| 排除探测 | 81,265 | $8,854.70 |
| 含探测 | 189,534 | $8,856.87 |
| **探测部分** | **108,271** | **$2.17** |

⇒ **请求数差 2.3 倍，费用却只差 $2.17。** 凡是「请求数差很多、费用差不多」的现象，先怀疑探测口径，而不是数据算错。

## 看板：每个数字怎么来的

| 卡片/模块 | 算法 | 说明 |
| --- | --- | --- |
| 总请求数 | 窗口内终态请求条数 | 只含成功/失败/限流等终态记录，不含未完成的流 |
| 成功率 | 成功笔数 ÷ 总笔数 | 状态为成功的请求占比 |
| 总 Token | 每笔输入字量 + 输出字量分别累加 | 缓存命中的字量按各上游口径计入 |
| 总费用 | 每笔费用累加（美元） | 美元是付给上游供应商的成本口径 |
| 总积分 | 平台向租户计费的积分数 | ★ 见下方「积分卡」 |
| 平均延迟 | 每笔延迟累加 ÷ 总笔数 | 毫秒 |
| 活跃模型 / 活跃供应商 | 窗口内有实际流量的去重计数 | 不是「平台可用总数」 |
| 活跃密钥 | 当前处于启用状态的密钥数量 | **配置口径，与时间范围无关** |
| 错误数 | 优先按失败原因分布逐类累加；无该分布时用「总请求 × (1 − 成功率)」推算 | 推算值与真实值可能差几笔 |
| 饼图（模型/供应商/租户/客户端…） | 按维度分组累加请求/Token/费用 | 来自请求级日志，与上方卡片同源（同一探测口径） |
| 用量趋势图 | 按时间桶累加请求/Token/费用/积分 | **与上方卡片同源**：同一张请求级事实表 `usage_facts` ＋ 同一个探测谓词 ⇒ 各桶之和与卡片逐项相等 |

### 时间窗口怎么算

- 「今天」＝系统时区（默认 Asia/Shanghai）今日零点 → 此刻；「近 7 天」＝6 天前的零点 → 此刻；「近 30 天」同理。**起点是日历日零点，终点是当前时刻**，不是整日。
- 自定义区间按所选两天汇总，含末日全天。
- 页面每 10 秒自动刷新；实时通道在线时新完成的请求会即时累加。

### 积分卡（口径特殊，务必注意）

积分卡显示的值**不是窗口内的积分消耗**：请求级事实表里的积分列当前恒为 0（实测全表 298,037 行全为 0），页面显示的实际是「基线快照之后的实时增量」。因此：

- 切换「今天 / 近 7 天 / 近 30 天」，积分卡的数字**完全一样**（实测三者同为 86,925）。
- 同一页的用量趋势图与积分卡现在**同源**（都读请求级事实表 `usage_facts`）⇒ 各桶积分之和 = 积分卡。

需要可信的积分账目时，请以「用量成本」「对账报表」页为准，不要用看板积分卡做时间序列比较。

## 会话与统计：每个数字怎么来的

| 模块 | 算法 | 说明 |
| --- | --- | --- |
| 总会话数 | 窗口内首请求时间落窗的会话条数 | 会话级计数，不等于请求数 |
| 活跃会话 / 新会话 / 已关闭会话 | 按会话的最后/首次请求时间落在最近 24 小时内划分 | 与主窗口无关的 24 小时口径 |
| 总费用（美元） | 各会话累计费用求和 | 一个会话的**全部**费用记在会话行上 |
| 总请求数 | 各会话累计请求数求和 | 同样取会话累计值，不是窗口内发生的请求数 |
| 输入费用 / 输出费用 | 各会话的输入/输出费用分别求和 | 两者相加＝总费用 |
| 平均会话费用 / 单请求费用 | 总费用 ÷ 会话数（÷ 请求数） | 分母是会话累计值 |
| 成功率 / 缓存率（对齐行） | 请求级视图的成功笔数 ÷ 请求总数 | 只有请求级口径才有这两项 |
| 会话分析对齐指标行 | 物化视图会话级汇总 | 每 15 分钟刷新一次；窗口＝上海日历日整天 |
| Top5 用户 / Top5 供应商 | 会话分析排行端点（用户／模型／供应商／任务） | 供应商由 SQL 按 `model_usage_aggregates.provider` 聚合（**不是**由模型名前缀推导），**含费用**、可按费用排序；Top5 四维在「会话分析 → 用户」页呈现 |
| 轮次对拍 | 会话请求数 vs 轮次数 | 差值超过 10% 时页面会给出提示条 |

### 会话宇宙（哪些会话被算了、哪些没算）

会话侧只统计同时满足以下三条的会话：

1. 在会话表里登记过的会话；
2. 有归属用户（按用户键或密钥归属键取其一，都为空则不计）；
3. 不是探测会话：既不是人工标记的探测位，也不是按「用户 / 客户端类型 / 标题」模式判定的自检、部署闸门、测试、验证类会话。

### 对账模块内部：零重复计算

对账页的供应商行（含「未落定」）**求和恰好等于页面总数**：

- 供应商行求和 = 178,841 请求 = 页面总请求数 ✓
- 供应商行费用求和 = $8,612.07 = 页面总费用 ✓
- 其中「未落定」（`provider_id IS NULL`）= 79,801 笔 / 100% 失败 / $0.00 —— 这些是**探测流量没有供应商归属**（探测不打到上游供应商），不是漏算。

## 数字对不上时怎么自查

1. **先对齐窗口**：看板与会话与统计面板＝**同一段日历日**（今天-(N-1) 日零点起；看板算到此刻，面板算到末日 24:00 ⇒ 覆盖同一批已发生的数据，两页用同一个日期范围控件）；对齐行＝上海日历日整天；供应商对账＝日历日闭区间。后两者与前两者仍不是同一个窗口。
2. **再对齐实体**：请求数对比请求数，费用对比费用；不要拿「会话数」和「请求数」比。
3. **再对齐探测口径**：看板可切「含探测」；会话统计按会话宇宙规则剔除；**对账永远含探测**。请求数差很多而费用接近 ⇒ 先看探测。
4. **再对齐成熟度**：对账是 T+1 快照，**当日数据必然滞后**；对比前先确认快照覆盖到哪一天。
5. **看降级标记**：卡片出现「降级 / 不可信 / 未算出」时，那几个 0 不代表没有流量。
6. **看板趋势图与看板卡片现在同源**：两者都读请求级事实表 `usage_facts`、用同一个探测谓词 ⇒ 各桶之和应与卡片逐项相等。若对不上：先看载荷里的 `degraded` 标记（降级到预聚合表时探测口径会不同），再看时间窗口是否对齐。
7. **「今天」档位曾失败（2026-11-23 已修）**：会话与统计的「今天」档位此前因数据库侧连接索引缺失而稳定 30 秒超时（2026-11-23 已补索引，查询耗时从 121.8 秒降到 0.19 秒）。若页面再显示该档位失败，说明数据库侧的索引又被清掉了，请让值班同学检查 `idx_session_dim_session_key` 是否在位。

## 已知限制（2026-11-23 实测）

1. **会话宇宙的探测剔除过宽（D1/D2，2026-11-23 实测确认）**：会话统计剔掉的 19,512 笔请求、$7,021.91 费用，在请求日志里 **100% 属于业务流量**。会话统计因此比看板（排除探测口径）低约 **$7,021.91（79%）**。**看板（请求级）的数字自始不受影响** ⇒ 精确的费用对账请以看板为准，或把对账页切到「业务」口径后再比。
2. **跨窗会话（E）**：18 个会话的首次请求早于窗口、但窗口内仍在活跃，当前被整体排除，漏算 3,191 笔 / $281.38（占看板费用 3.2%）。
3. **无会话归属的调用（F）**：381 笔直连 API / 脚本调用没有会话，看板会计入、会话统计不会。
4. **对账快照的当日滞后**：对账是 T+1 口径，**当天（今天）的数据不完整**，与看板的实时数字直接相减必然出现差额。
5. 看板积分卡不随时间范围变化（见上）。
6. **降级态的探测口径**：看板的饼图与趋势在**主路径失败、整体降级**到预聚合表时，那两张表恒为「排除探测」口径 ⇒ 含探测模式下会与英雄区不一致（此时载荷会带 `degraded` 标记，不是静默降级）。
