# 看板与会话统计的统计标准

「看板」和「会话与统计」是同一批模型调用流水在**两套口径**下的两种汇总。这一页把两页每个数字的算法、数据来源、时间窗口写清楚，并给出两页数字为什么对不上的逐项对照——用于对齐数据、自查偏差。

> 实测口径：2026-11-23 02:27（Asia/Shanghai）生产环境实测 + 生产库只读对拍。

## 两页是什么关系

| | 看板 | 会话与统计 |
| --- | --- | --- |
| 统计实体 | 一笔模型调用算一条（**请求级**） | 一个会话算一条，取该会话的**累计值**（**会话级**） |
| 真源 | 请求级事实表 `usage_facts`（Redis 缓存基线 + 实时增量） | 会话汇总表 `session_summaries`（即时查询）+ 物化视图（缓存面） |
| 时间窗口 | 系统时区日历日：今天-(N-1) 日 零点 → 此刻 | 面板＝滚动 N 天（首请求时间在最近 N 天内）；对齐行＝上海日历日整天 |
| 探测流量 | 按请求级事实表的流量分类剔除 | 按会话侧的会话宇宙规则剔除 |

**结论先说**：两页的数字**本来就不该相等**——实体不同（请求 vs 会话）、窗口不同、剔除规则不同。跨页比较必须先对齐这三项，不能直接对减。

## 看板：每个数字怎么来的

| 卡片/模块 | 算法 | 说明 |
| --- | --- | --- |
| 总请求数 | 窗口内终态请求条数 | 只含成功/失败/限流等终态记录，不含未完成的流 |
| 成功率 | 成功笔数 ÷ 总笔数 | 状态为成功的请求占比 |
| 总 Token | 每笔输入字量 + 输出字量分别累加 | 缓存命中的字量按各上游口径计入 |
| 总费用 | 每笔费用累加（美元） | 美元是付给上游供应商的成本口径 |
| 总积分 | 平台向租户计费的积分数 | ★ 见下方「积分卡」 |
| 平均延迟 | 每笔延迟累加 ÷ 总笔数 | 毫秒 |
| 活跃模型 / 活跃供应商 | 窗口内有实际流量的去重计数 | 不是「平台可用总数」 |
| 活跃密钥 | 当前处于启用状态的密钥数量 | **配置口径，与时间范围无关** |
| 错误数 | 优先按失败原因分布逐类累加；无该分布时用「总请求 × (1 − 成功率)」推算 | 推算值与真实值可能差几笔 |
| 饼图（模型/供应商/租户/客户端…） | 按维度分组累加请求/Token/费用 | 来自分钟统计表，与上方卡片不是同一个真源 |
| 用量趋势图 | 按时间桶累加请求/Token/费用/积分 | 同样来自分钟统计表 |

### 时间窗口怎么算

- 「今天」＝系统时区（默认 Asia/Shanghai）今日零点 → 此刻；「近 7 天」＝6 天前的零点 → 此刻；「近 30 天」同理。**起点是日历日零点，终点是当前时刻**，不是整日。
- 自定义区间按所选两天汇总，含末日全天。
- 页面每 10 秒自动刷新；实时通道在线时新完成的请求会即时累加。

### 积分卡（口径特殊，务必注意）

积分卡显示的值**不是窗口内的积分消耗**：请求级事实表里的积分列当前恒为 0（实测全表 298,037 行全为 0），页面显示的实际是「基线快照之后的实时增量」。因此：

- 切换「今天 / 近 7 天 / 近 30 天」，积分卡的数字**完全一样**（实测三者同为 86,925）。
- 同一页的用量趋势图里另有积分合计（分钟统计表口径，近 7 天 1,767,183），与积分卡不是一个数。

需要可信的积分账目时，请以「用量成本」「对账报表」页为准，不要用看板积分卡做时间序列比较。

## 会话与统计：每个数字怎么来的

| 模块 | 算法 | 说明 |
| --- | --- | --- |
| 总会话数 | 窗口内首请求时间落窗的会话条数 | 会话级计数，不等于请求数 |
| 活跃会话 / 新会话 / 已关闭会话 | 按会话的最后/首次请求时间落在最近 24 小时内划分 | 与主窗口无关的 24 小时口径 |
| 总费用（美元） | 各会话累计费用求和 | 一个会话的**全部**费用记在会话行上 |
| 总请求数 | 各会话累计请求数求和 | 同样取会话累计值，不是窗口内发生的请求数 |
| 输入费用 / 输出费用 | 各会话的输入/输出费用分别求和 | 两者相加＝总费用 |
| 平均会话费用 / 单请求费用 | 总费用 ÷ 会话数（÷ 请求数） | 分母是会话累计值 |
| 成功率 / 缓存率（对齐行） | 请求级视图的成功笔数 ÷ 请求总数 | 只有请求级口径才有这两项 |
| 会话分析对齐指标行 | 物化视图会话级汇总 | 每 15 分钟刷新一次；窗口＝上海日历日整天 |
| Top5 用户 / Top5 供应商 | 会话分析总览接口 | 供应商由模型名前缀推导，按请求数排序，**不含费用** |
| 轮次对拍 | 会话请求数 vs 轮次数 | 差值超过 10% 时页面会给出提示条 |

### 会话宇宙（哪些会话被算了、哪些没算）

会话侧只统计同时满足以下三条的会话：

1. 在会话表里登记过的会话；
2. 有归属用户（按用户键或密钥归属键取其一，都为空则不计）；
3. 不是探测会话：既不是人工标记的探测位，也不是按「用户 / 客户端类型 / 标题」模式判定的自检、部署闸门、测试、验证类会话。

### 为什么这里的费用比看板少

会话宇宙的第三条规则会把**一部分真实业务会话**判成探测而剔除。2026-11-23 生产库实测（同 7 天窗口）：

- 被会话侧剔除的 15,898 个会话，其主请求在请求级事实表里 **100% 属于业务流量**，合计 $6,452.73；
- 同一窗口，请求级事实表里真正标为探测的流量合计只有 **$1.81**。

也就是说：两页虽然都声称「排除探测」，但**剔除的不是同一批请求**。这是会话与统计费用明显低于看板的首要原因。

## 两页数字对照（2026-11-23 实测，7 天窗口）

| 指标 | 看板 | 会话与统计（面板） | 会话与统计（对齐行） |
| --- | --- | --- | --- |
| 统计实体 | 请求 | 会话 + 会话累计请求 | 会话 / 请求 |
| 请求数 | 65,774 | 72,098 | — |
| 费用（美元） | 8,013.93 | 2,717.62 | 2,468.73（内部成本） |
| 积分 | 86,925（与窗口无关） | — | 0 |
| Token | 3,245,804,009 | — | — |
| 成功率 | 95.31% | — | 94.64% |
| 会话数 | — | 19,235 | 17,390 |

差异来源，逐项对上：

- **请求数 72,098 > 65,774**：会话侧的请求数是「被选中会话的累计请求数」，一个跨窗会话的窗后请求也整段计入；同时会话表存在重复行（实测同一会话键最多 30 行重复），聚合时被一并累加。
- **费用 2,717.62 < 8,013.93**：会话宇宙把上面那 $6,452.73 的业务流量判成探测剔除了；此外看板还统计了**没有归属会话**的调用（直连 API、脚本调用），实测这部分约占看板费用的两成。
- **积分 0 vs 86,925**：会话侧与请求级事实表的积分列当前都没有可信存量，页面上的积分来自实时增量。
- **成功率 95.31% vs 94.64%**：请求级口径 vs 请求级口径，但一个按 `usage_facts`、一个按请求日志物化视图，窗口也不同。

## 数字对不上时怎么自查

1. **先对齐窗口**：看板＝日历日零点起；会话与统计面板＝滚动 N 天；对齐行＝上海日历日整天。同一预设下三者仍不是同一个窗口。
2. **再对齐实体**：请求数对比请求数，费用对比费用；不要拿「会话数」和「请求数」比。
3. **看降级标记**：卡片出现「降级 / 不可信 / 未算出」时，那几个 0 不代表没有流量。
4. **看探测开关**：看板上「排除探测 / 含探测」只切英雄区汇总；分布图与趋势图始终是业务口径。
5. **「今天」档位曾失败（2026-11-23 已修）**：会话与统计的「今天」档位此前因数据库侧连接索引缺失而稳定 30 秒超时（2026-11-23 已补索引，查询耗时从 121.8 秒降到 0.19 秒）。若页面再显示该档位失败，说明数据库侧的索引又被清掉了，请让值班同学检查 `idx_session_dim_session_key` 是否在位。

## 已知限制（2026-11-23 实测）

1. **会话侧的费用与请求数偏高（重复计数，待修）**：「会话与统计」的费用与请求数来自会话级汇总，而 `sessions` 表是**按天分区的会话历史表**（同一会话每天续一行），统计的连接未按会话去重 ⇒ 同一会话被累计多次。2026-11-23 生产库实测（同 7 天窗口）：会话侧报出的费用比按会话去重后高约 **61%**、请求数高约 **36%**（最贵的那个会话被累计了 3 次）。**看板（请求级）的数字不受此影响** ⇒ 比较费用时以看板为准，或先按会话去重再看会话侧数字。
2. 会话侧聚合会连会话表里的重复行一起累加，会话口径的请求数与费用因此偏高。
3. 看板积分卡不随时间范围变化（见上）。
4. 看板趋势图（分钟统计表）与上方卡片（请求级事实表）在 30 天窗口实测相差约 13.8%（160,451 vs 140,969 笔）。
5. 探测剔除在两侧不是同一批流量（见上）。
