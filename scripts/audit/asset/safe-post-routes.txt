# safe-post-routes.txt —— 「可安全 POST」的端点白名单
#
# ★★ 用途（R157 轮 · D15）：★ `scripts/audit/api-sweep.sh` 是 **GET-only** 的巡检
# ★★ ⇒ ★★ 那些「只接受 POST」的端点**全部**返回 405 ⇒ ★★ 上一轮实测 **110 条**
# ★★ ⇒ ★★ 也就是说：**这 110 条端点【从未被巡检验证过】**。
#
# ★ ★★ 本文件是那 110 条的**白名单**：★ 只有列在这里的端点，★ 巡检才会对它发 POST。
#
# ★★★ 「可安全 POST」的判定口径（三条全满足才进白名单）：
#
#   ① **参数校验先于任何副作用**：★ 空 body ⇒ 必然在**改任何东西之前**就返回 4xx
#      ⇒ ★★ 于是「探它一下」**不产生副作用** ⇒ ★★ 这才是「安全」的真正含义。
#   ② **不外呼、不写库**：★ 纯参数校验 / 纯查询。
#   ③ **不是幂等性未知的写操作**：★ 例如 promote / drop / vacuum-full / register
#      ⇒ ★★ 那些**即使**校验在前，★ 也不该被批量探（★ 它们的副作用**可能**在校验之后）。
#
# ★★★★ ★★ 一条**实测反例**（★ R157 轮当场踩到，★ 值得单独记）：
#   ★ 我最初把 `/api/admin/auto-route/tuning/analyze` 与 `…/proposals/generate` 也列进来了
#   ★（★ 理由：★ 它们「先校验 days 参数」）。
#   ★ ⇒ ★★ **实测打过去 ⇒ 两个都返回 500** ⇒ ★★ 追源码才发现：
#   ★★ 这两个端点**根本不读 body**（★ 只读 query 参数）⇒ ★★ 空 body 会**走正常路径**
#   ★★ ⇒ ★★ **真的去跑分析 / 真的去生成提案** ⇒ ★★ **副作用真的发生了**。
#   ★ ⇒ ★★★ **所以「先校验了参数」不等于「参数校验会拦住空 body」**
#   ★★★ ⇒ ★★★ **白名单的真正判据是：★ 空 body ⇒ 必然在【任何副作用之前】被 4xx 拦下**
#   ★★★ ⇒ ★★★ **只看「有没有参数校验」是不够的** —— ★ 要看「**这个校验拦不拦得住空 body**」。
#   ★ ⇒ ★★ 下面那两条**已被移出白名单**（★ ★ 它们的副作用在校验之后）。
#
# ★ ★★ 白名单里的每一条都**逐条读过源码**（★ 行号指明出处）⇒ ★★ 可复核。
#
# ★ ★★ 探测方式：★ POST 一个**空 JSON body**（`{}`）⇒ ★ 期望 **400/422**（★ 不是 405）
# ⇒ ★★ 405 ⇒ ★ 路由**没注册**或**方法不匹配** ⇒ ★★ 400 ⇒ ★ 路由活着、校验拦住了。
# ⇒ ★★★ **反过来**：★ 若某条返回 **2xx 或 5xx** ⇒ ★★ **它不该在白名单里**
# ⇒ ★★★ ⇒ ★★ 把它**移出去**（★ 别留着 ⇒ ★ 下次探测就会真的产生副作用）。
