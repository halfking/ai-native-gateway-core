## 推荐解决方案

### 方案A：物化视图（推荐）
创建物化视图预聚合 7天/30天的统计数据：

```sql
CREATE MATERIALIZED VIEW routing_analytics_7d AS
SELECT
  DATE_TRUNC('hour', ts) AS time_bucket,
  l1_task_type,
  COUNT(*) AS request_count,
  SUM(CASE WHEN success THEN 1 ELSE 0 END) AS success_count,
  ...
FROM request_logs_with_current_month_without_customer_id
WHERE ts >= NOW() - INTERVAL '7 days'
  AND is_auto_request = TRUE
GROUP BY time_bucket, l1_task_type, ...;

CREATE UNIQUE INDEX ON routing_analytics_7d (time_bucket, l1_task_type, ...);
```

定时刷新策略：
- 每5-15分钟 `REFRESH MATERIALIZED VIEW CONCURRENTLY routing_analytics_7d`
- 或使用 PostgreSQL 13+ 的增量刷新特性

**优点**：
- 查询从15秒降至 <100ms
- 实现简单，PostgreSQL 原生支持
- 数据准确性高（定期全量刷新）

**缺点**：
- 刷新期间占用数据库资源
- 数据有5-15分钟延迟

### 方案B：统计表（备选）
创建独立统计表，通过触发器或定时任务增量更新：

```sql
CREATE TABLE routing_analytics_stats (
  time_bucket TIMESTAMPTZ NOT NULL,
  l1_task_type TEXT,
  metric_type TEXT,  -- 'count', 'success_rate', etc.
  metric_value NUMERIC,
  window_days INT,  -- 7 or 30
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  PRIMARY KEY (time_bucket, l1_task_type, metric_type, window_days)
);
```

**优点**：
- 更灵活的增量更新策略
- 可以存储多个时间窗口（7天、30天）
- 刷新开销更小

**缺点**：
- 实现复杂度更高
- 需要额外的更新逻辑和错误处理

### 方案C：查询优化（临时缓解）
如果无法立即实施物化视图：
1. 增加超时时间：15秒 → 30秒
2. 添加索引：`CREATE INDEX ON request_logs (ts, is_auto_request, l1_task_type) WHERE is_auto_request = TRUE;`
3. 缩短查询窗口：7天 → 3天

**注意**：这只是缓解，不解决根本问题。

## 关键决策记录

### 为什么不直接优化现有查询？
1. 视图已经去掉了 customer_id LATERAL JOIN（migration 575）
2. 数据量（314K+）导致任何聚合查询都需要全表扫描
3. 添加索引无法解决 GROUP BY 的性能问题
4. 唯一有效方案是预聚合（物化视图或统计表）

### 为什么推荐物化视图而不是统计表？
1. **实现简单**：PostgreSQL 原生支持，无需额外更新逻辑
2. **数据一致性**：全量刷新保证数据准确
3. **维护成本低**：不需要处理增量更新的边界情况
4. **性能足够**：5-15分钟延迟对分析场景可接受

如果未来需要更低延迟（<1分钟），再考虑升级为统计表方案。

),

  SELECT ... FROM request_logs_with_current_month_without_customer_id
  WHERE ts >= NOW() - INTERVAL '7 days'
  GROUP BY ...
)
SELECT 
  COALESCE(mv_data.time_bucket, base_data.time_bucket) AS time_bucket,
  mv_data.request_count AS mv_count,
  base_data.request_count AS base_count,
