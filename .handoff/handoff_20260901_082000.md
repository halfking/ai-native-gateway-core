## 完成的工作（全部本地未提交）

### 1. 刷新器运行时指标（`bg/metrics.go`, `bg/materialized_view_refresher.go`）

新增 4 个指标：
```
gateway_mv_refresh_total{view, outcome}                     # outcome: success|failed|skipped_no_lock|skipped_follower|skipped_missing_view
gateway_mv_refresh_duration_seconds{view}                    # histogram, 仅 success 时 observe
gateway_mv_refresh_last_success_unix{view}                   # 用于 staleness 告警
gateway_mv_refresh_coordination_result_total{result}         # redis_leader|redis_follower|redis_fallback
```

接线点：`refreshAll`（协调结果）、`refreshView`（成功/失败/跳过 + 耗时）。`view` 是闭集标签（两个物化视图名），无高基数维度，通过了 `TestNoHighCardinalityLabels` 门禁。

### 2. Go 侧一致性检查（新文件 `bg/mv_consistency.go`）

`CheckMVConsistency(ctx, pool, viewName) (MVConsistencyResult, error)`：
- **routing_analytics_7d**：按 `(task_type, model)` FULL OUTER JOIN 物化视图 vs 基表，SQL 与 `verify-mv-consistency.sh` 的查询逐字对齐。
- **routing_audit_summary_7d**：按 `tenant_id` 对比（之前完全没有覆盖这个视图）；`tenant_id` COALESCE 成 `''` 哨兵值，避免 NULL-tenant 两侧因 JOIN 语义产生假性漂移（呼应迁移 632 里 unique index 的哨兵值教训）。
- 阈值：`MVDriftAlertPct=5%` AND `MVDriftAlertAbs=100`（两者都超才算 breach，过滤小 bucket 噪声）。
- 视图不存在 → 返回零值、不报错（consumer 本来就会退化到基表查询）。
- SQL 报错 → 返回 error，调用方据此增加 `RoutingAnalyticsMVConsistencyErrorsTotal` 且**不更新** `_last_unix`（陈旧时间戳本身就是信号）。

接线点：`refreshView` 在 REFRESH 成功后调用 `checkConsistency`，一致性检查失败不会让刷新本身失败（REFRESH 已经成功了）。

`CheckMVConsistency` 的 DB 参数收窄成 `mvConsistencyDB` 接口（只要 `QueryRow`/`Query`），这样生产传 `*pgxpool.Pool`、测试传 `pgxmock.PgxPoolIface` 都能满足，不需要额外适配层。

### 3. 指标零值预初始化（`metrics/routing_analytics_mv_drift.go`）

补了 `init()`，对两个闭集 view 值预置 4 个 gauge 为 0，确保刷新器第一次跑之前 `/metrics` 也能看到这几条时间序列（否则 Grafana 面板首次部署时会"看不见"而不是"看见 0"）。

### 4. 离线脚本语义修正（`scripts/monitoring/verify-mv-consistency.sh`）

原脚本的问题：`psql` 失败直接 `exit 2`，跳过 textfile 写入，导致 node_exporter 长期保留上一次成功的旧值，看起来"一直健康"实际是检查器挂了。

修正：
- 抽出 `write_prom_metrics()` 统一写 5 个指标（新增 `_consistency_last_unix` 和 `_consistency_errors_total`，此前只写 3 个）。
- 视图不存在（新装环境）时也刷新 `_last_unix`，避免误报 staleness。
- `psql` 失败时先调用 `write_error_metrics "query_failed"` 再 `exit 2`，让 staleness/error 告警能感知到检查器本身挂了。
- `bash -n` 语法检查通过。

### 5. Prometheus 告警规则（新文件 `deploy/prometheus/rules/routing-analytics-mv-consistency.yml`）

放在 `rules/` 目录（**不是** `alerts/` — 探索阶段确认 `alerts/` 目录未被 `docker-compose.yml` 挂载，规则不会被加载）。5 条告警：

| 告警名 | 触发条件 | for | severity |
|---|---|---|---|
| RoutingAnalyticsMVDriftHigh | `breach_count > 0` | 20m | warning |
| RoutingAnalyticsMVConsistencyCheckStale | `time() - last_unix > 3600` | 15m | warning |
| RoutingAnalyticsMVConsistencyCheckErroring | `increase(errors_total[15m]) > 0` | 5m | critical |
| RoutingAnalyticsMVRefreshFailing | `rate(refresh_total{outcome="failed"}[10m]) > 0` | 20m | critical |
| RoutingAnalyticsMVRefreshStale | `time() - last_success_unix > 1200` | 5m | critical, page |

配套契约测试 `deploy/prometheus/rules/routing_analytics_mv_consistency_test.go`，断言告警名/指标名/`for`/无高基数标签，全部通过。

### 6. 单元测试

- `bg/mv_consistency_test.go`：6 个用例（视图缺失、无漂移、小漂移+breach 判定、SQL 错误、不支持的视图、audit summary tenant 维度），全部用 `pgxmock` 构造确定性场景，无需真实数据库。
- `metrics/routing_analytics_mv_drift_test.go`：2 个用例（5 个指标的名称+label 契约、显式的高基数标签防回归）。
