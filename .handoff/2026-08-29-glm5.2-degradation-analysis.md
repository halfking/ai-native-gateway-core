# GLM-5.2 网关降级问题分析与修复方案

## 问题描述

直连 sp1 供应商中的 spi-3 的 glm-5.2 模型工作正常，但通过网关访问时经常被降级，导致无法正常使用。

## 根本原因分析

基于代码审查，发现以下几个核心问题：

### 1. 过于激进的降级策略 (credentialhealth/checker.go)

**问题点：**
- 默认失败率阈值为 80% (line 88)，且窗口期为 1 小时
- GLM 模型可能有短暂的瞬态错误（如 rate_limit、concurrent overload），但这些不应该导致长时间降级
- 最小样本数仅为 5 个请求，样本量过小容易误判

**相关代码：**
```go
// credentialhealth/checker.go:85-95
WindowDuration:   1 * time.Hour,
FailureThreshold: 0.80, // 80% failure rate
MinSampleSize:    5,
DegradedCooldown: 15 * time.Minute,
```

**GLM-5.2 特定问题：**
```go
// credentialhealth/checker.go:122-132
// rate_limit 的阈值为 95%，最小样本 8，冷却 1 分钟
"rate_limit": {FailureThreshold: 0.95, MinSampleSize: 8, DegradedCooldown: 1 * time.Minute},
```

GLM 的智谱 API 在高峰期可能返回较多 429 rate_limit，但现有配置可能仍不够宽容。

### 2. 权重路由器的惩罚过重 (domains/routing/weighted_router.go)

**问题点：**
- 错误率惩罚公式：`errorPenalty = 1.0 - (errorsPerMin / ErrorRateBaseline)`
- 默认 ErrorRateBaseline = 10 错误/分钟 (line 28)
- 延迟惩罚公式：`latencyPenalty = 1.0 - (excessMs / 10000.0)`
- 默认 LatencyBaseline = 2000ms

**相关代码：**
```go
// domains/routing/weighted_router.go:305-318
errorPenalty := 1.0 - (float64(errorsPerMin) / wr.config.ErrorRateBaseline)
if errorPenalty < wr.config.MinWeight {
    errorPenalty = wr.config.MinWeight
}
```

**影响：**
- 如果 GLM-5.2 在 1 分钟内出现 10 个错误，权重直接降为 0.1（最小值）
- 一旦权重过低，即使后续请求成功，也需要很长时间才能恢复

### 3. 缓存失效策略过于频繁

**问题点：**
```go
// domains/routing/weighted_router.go:230, 245
func (wr *WeightedRouter) RecordError(credentialID string, statusCode int, err error) {
    // ...
    wc.invalidateCache() // 每次错误都失效缓存
}

func (wr *WeightedRouter) RecordSuccess(credentialID string, latency time.Duration) {
    // ...
    wc.invalidateCache() // 每次成功也失效缓存
}
```

每次请求后都失效缓存，导致下次选择时需要重新计算权重，增加了 CPU 开销。

### 4. 错误分类过于严格 (errorsx/failover_policy.go)

**问题点：**
```go
// errorsx/failover_policy.go:74-78
case KindRateLimit:
    decision.Scope = ScopeModel
    decision.RetryAfter = parseRetryAfter(retryAfterHeader, DefaultRateLimitCooldown)
    decision.EnqueueProbe = true
    decision.ProbeFanout = 1
```

Rate limit 错误会触发 30 秒的冷却期（DefaultRateLimitCooldown = 30s），对于智谱 GLM 这种有固定 QPM/RPM 限制的模型，这个策略可能过于保守。

### 5. 缺乏请求队列和平滑机制

**当前架构缺陷：**
- TCP 连接保持、队列管理、数据转换、路由决策紧密耦合
- 没有多层队列缓冲突发流量
- 缺少请求平滑机制（smoothing/throttling）

## 修复方案

### 方案 1: 调整 GLM-5.2 专用降级策略 (立即生效)

**目标：** 为 GLM 模型配置更宽容的降级阈值

```go
// 在 credentialhealth/checker.go 的 defaultKindThresholds() 中添加：
func defaultKindThresholds() map[string]KindThreshold {
    return map[string]KindThreshold{
        // ... 现有配置
        
        // GLM 特定优化：rate_limit 更宽容
        "rate_limit": {
            FailureThreshold: 0.98,  // 从 0.95 提升到 0.98
            MinSampleSize:    15,    // 从 8 提升到 15，需要更多样本
            DegradedCooldown: 30 * time.Second, // 从 1 分钟缩短到 30 秒
        },
        
        // 并发过载也应更宽容
        "concurrent": {
            FailureThreshold: 0.95,
            MinSampleSize:    12,
            DegradedCooldown: 2 * time.Minute,
        },
    }
}
```

### 方案 2: 优化权重路由器配置

**目标：** 减少权重惩罚，加快恢复速度

```go
// 为 GLM 模型创建专用的 WeightConfig
func GLMWeightConfig() WeightConfig {
    return WeightConfig{
        BaseWeight:        1.0,
        ErrorRateBaseline: 20,   // 从 10 提升到 20，容忍更多错误
        LatencyBaseline:   3000, // 从 2000ms 提升到 3000ms，GLM 推理较慢
        MinWeight:         0.3,  // 从 0.1 提升到 0.3，避免完全排除
    }
}
```

### 方案 3: 优化缓存策略 (减少 CPU 和序列化开销)

**当前问题：** 每次请求都失效缓存，导致频繁重算

**改进方案：**

```go
// domains/routing/weighted_router.go
type weightCache struct {
    weight          float64
    at              time.Time
    errorsPerMin    int
    consecutiveFail int
    avgLatency      time.Duration
    version         uint64 // 新增：版本号，用于增量失效
}

type WeightedCandidate struct {
    Candidate      *Candidate
    LatencyTracker *LatencyTracker
    ErrorDetector  *health.ErrorDetector
    cache          atomic.Pointer[weightCache]
    cacheVersion   atomic.Uint64 // 新增：原子版本计数器
}

// 改进：仅在显著变化时失效缓存
func (wc *WeightedCandidate) maybeInvalidateCache(significant bool) {
    if significant {
        wc.cacheVersion.Add(1)
    }
}

func (wr *WeightedRouter) RecordError(credentialID string, statusCode int, err error) {
    wr.mu.RLock()
    wc, ok := wr.candidates[credentialID]
    wr.mu.RUnlock()
    if !ok {
        return
    }
    if wc.ErrorDetector != nil {
        wc.ErrorDetector.OnError(health.ErrorEvent{
            CredentialID: credentialID,
            StatusCode:   statusCode,
            Error:        err,
            Timestamp:    time.Now(),
        })
    }
    // 仅在连续失败或错误率显著上升时失效
    consecutiveFails := 0
    if wc.ErrorDetector != nil {
        consecutiveFails = wc.ErrorDetector.GetConsecutiveFails(credentialID)
    }
    significant := consecutiveFails >= 3 // 连续 3 次失败才失效
    wc.maybeInvalidateCache(significant)
}
```

### 方案 4: 多层队列和请求平滑机制

**架构改进：**

```
请求流 → 全局队列 (burst buffer) 
       → 凭据队列 (per-credential throttling)
       → 路由决策 (cached candidate selection)
       → TCP 连接池 (connection reuse)
       → 上游请求
```

**实现要点：**

1. **全局队列（Burst Buffer）：**
   - 容量：1000 请求
   - 超时：5 秒
   - 目的：吸收突发流量，避免直接压垮路由层

2. **凭据队列（Per-Credential Queue）：**
   - 已有实现：`domains/dispatch` 中的 `ConcurrencyMode`、`MaxQueueDepth`、`MaxQueueWaitMS`
   - 需要确保 GLM-5.2 的 credential 配置了合理的队列参数

3. **智能路由缓存：**
   - 缓存候选列表 30 秒（当前是每次查询数据库）
   - 仅在 credential 状态变化时失效

### 方案 5: Redis 和数据库降级容错

**目标：** 在 Redis 和 DB 不可用时仍能提供服务

**当前问题：**
- `credentialhealth/checker.go` 依赖 DB 查询历史记录
- `domains/routing/weighted_router.go` 的状态完全在内存中，但初始化依赖 DB

**改进方案：**

```go
// 内存状态快照（持久化到本地文件）
type CredentialSnapshot struct {
    CredentialID     int       `json:"credential_id"`
    Model            string    `json:"model"`
    LastSuccessAt    time.Time `json:"last_success_at"`
    RecentErrorRate  float64   `json:"recent_error_rate"`
    Weight           float64   `json:"weight"`
    SnapshotAt       time.Time `json:"snapshot_at"`
}

// 定期（每 10 秒）将内存状态快照到本地文件
func (wr *WeightedRouter) SnapshotToFile(path string) error {
    wr.mu.RLock()
    defer wr.mu.RUnlock()
    
    snapshots := make([]CredentialSnapshot, 0, len(wr.order))
    for _, id := range wr.order {
        wc := wr.candidates[id]
        weight := wr.computeWeight(wc)
        errorsPerMin := 0
        if wc.ErrorDetector != nil {
            errorsPerMin = wc.ErrorDetector.GetErrorsPerMinute(id)
        }
        snapshots = append(snapshots, CredentialSnapshot{
            CredentialID:    wc.Candidate.CredentialID,
            Model:           wc.Candidate.RawModel,
            RecentErrorRate: float64(errorsPerMin) / 60.0,
            Weight:          weight,
            SnapshotAt:      time.Now(),
        })
    }
    
    data, err := json.Marshal(snapshots)
    if err != nil {
        return err
    }
    return os.WriteFile(path, data, 0644)
}

// 启动时从本地文件恢复（如果 DB/Redis 不可用）
func (wr *WeightedRouter) RestoreFromFile(path string) error {
    data, err := os.ReadFile(path)
    if err != nil {
        return err
    }
    var snapshots []CredentialSnapshot
    if err := json.Unmarshal(data, &snapshots); err != nil {
        return err
    }
    // 仅加载 5 分钟内的快照
    cutoff := time.Now().Add(-5 * time.Minute)
    for _, snap := range snapshots {
        if snap.SnapshotAt.Before(cutoff) {
            continue
        }
        // 恢复候选者权重...
    }
    return nil
}
```

### 方案 6: 针对 GLM-5.2 的特殊处理

**数据库配置调整（立即可操作）：**

```sql
-- 为 sp1/spi-3 的 glm-5.2 模型设置更高的优先级和保护
UPDATE credential_model_bindings cmb
SET 
    admin_protected = TRUE,  -- 防止自动降级
    manual_priority = 100    -- 提高优先级
FROM provider_models pm, credentials c, providers p
WHERE cmb.provider_model_id = pm.id
  AND cmb.credential_id = c.id
  AND c.provider_id = p.id
  AND p.name = 'sp1'  -- 或使用 provider_id
  AND pm.raw_model_name = 'glm-5.2'
  AND c.label LIKE '%spi-3%';

-- 调整 glm-5.2 的上下文窗口（如果配置不正确）
UPDATE models_canonical
SET context_window_override = 128000
WHERE normalized_name = 'glm-5.2'
  AND (context_window_override IS NULL OR context_window_override < 128000);
```

## 实施计划

### 第一阶段：紧急修复（立即执行）

1. **数据库配置调整：** 执行上述 SQL，为 GLM-5.2 设置保护和优先级
2. **调整降级阈值：** 修改 `credentialhealth/checker.go` 中 rate_limit 的阈值配置
3. **监控验证：** 观察 245 服务器日志，确认降级频率下降

### 第二阶段：架构优化（1-2 周）

1. **优化权重路由器：** 实施方案 2 和方案 3
2. **多层队列：** 验证并优化 `domains/dispatch` 的队列配置
3. **本地快照：** 实施方案 5，增强容错能力

### 第三阶段：长期改进（1 个月）

1. **解耦架构：** TCP 连接池独立管理
2. **智能路由缓存：** 减少数据库查询压力
3. **全面压测：** 验证改进效果

## 总结

GLM-5.2 频繁降级的根本原因是：

1. **降级策略过于激进**：80% 失败率阈值、5 样本最小量对智谱 API 的波动不够宽容
2. **权重惩罚过重**：错误率基线过低，导致短暂问题产生长期影响
3. **缺乏多层缓冲**：突发流量直接冲击路由层，没有队列平滑
4. **缓存策略低效**：频繁失效导致重复计算和 CPU 浪费

通过上述方案的组合实施，可以：
- **立即见效**：数据库配置 + 阈值调整
- **中期改善**：权重优化 + 缓存改进
- **长期稳定**：架构解耦 + 容错增强
